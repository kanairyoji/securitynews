誰が権限を渡しているのか

第2回 読了 約10分 2026-08-30 公開

対象期間 2026-07-15 〜 2026-08-28 ／ 出典 20件 ／ 採録 18件

前回まで 第1回「いま何が起きているのか」で見たのは、認可の入口が変わったことだった。 Issue の本文、WAF のブロックログ、監視アラート——権限管理の対象として設計されていないものが、 エージェントを経由して実行に変わる。自然言語が認可経路に加わった。
今回はその手前を見る。エージェントが動かしている権限は、そもそも誰が、いつ、 どういう形で渡したものなのか。入口を塞ぐ話ではなく、渡す仕組みそのものの話である。

① 結論

エージェントの権限は、渡されていない。借りられている。 「このエージェントが、この人の代理で、この範囲を、いつまで」を書く欄が、 現行の認可の標準に存在しない[1]。 書く場所が無いので、実装は人間の資格情報の借用と、共有サービスアカウントと、 期限のない静的 API キーでその穴を埋めている。 その結果、「誰が・いつ・どこまで・いつまで」の4つはどれも答えが出ない。 この45日に出そろった標準・製品・枠組みは、方向がばらばらに見えて、 実は一点に収束している——委任を書ける場所を作ることだ。

② 時系列

局面 1 ／ 渡す形式が無い
07-19
OAuth のトークンに「委任関係」を表すクレームが無い

CrowdStrike の整理。JWT 形式の OAuth アクセストークンの標準 RFC 9068 には、 エージェントのインスタンス識別子・代理対象のユーザー・両者の委任関係を表すクレームが無い。 RFC 8693 のトークン交換でも関係コンテキストは表現できない。 エージェントは複数ユーザーの代理を同時に務め、動的に生成・破棄され、他のエージェントを呼ぶ。 この空白が粗い認可判断・過剰なアクセス付与・confused deputy 問題につながる。 MCP 仕様が推奨する OAuth 2.1 でも足りず、IIW（Internet Identity Workshop）2026年4月の議論を踏まえ 業界標準化が必要だという合意ができた段階である[1]。

07-16
だから借りる — 監査ログで人間と区別がつかない

Token Security の調査で、ローカル AI エージェントの2割超が本番データへ直接アクセスし、 人間の資格情報を「借用」するため監査ログ上で区別できないことが示された。 「アイデンティティを制御平面とする」——発見・統合・ID 相関の基盤は買い、 ワークフロー等の運用層は自組織で作る、という設計論がここから出てくる[2]。

07-27
ガードレールは確率的、だから ID として扱え

Okta Threat Intelligence がオープンソースの OpenClaw 上のエージェントを数か月検証し、 ソーシャルエンジニアリングとプロンプトインジェクションで パスワード・API キー・GitHub トークン・OAuth リフレッシュトークンを漏らすことを実証した。 結論は「ガードレールは確率的で信頼できないので、エージェントを従業員同様のアイデンティティとして扱い、 最小権限・短命トークン・集中的なシークレット管理・即時失効を適用せよ」である[3]。 この4点はすべて「権限をどう渡すか」の話であって、入力をどう検査するかの話ではない。

局面 2 ／ 境界が実装ごとにばらばらに破れる
08-05
テナント境界が実装の一点で消える — Terraform MCP と Apache Airflow

Terraform MCP Server にクロステナント欠陥（CVSS 10.0、修正 1.1.0 以降）。 あるユーザーの Terraform トークンが、後続の別ユーザーのリクエストで再利用される。 露出は構成依存で、stdio ではなく Streamable HTTP を使う構成に影響する[4]。 8月18日には Apache Airflow の Amazon／Yandex プロバイダーで、マルチチームモード時に チームスコープの Connection・Variable がチーム非依存の検索で解決される 認可不備も公表された（JVNDB-2026-028663 / 028758）[6]。 誰の権限で動くかが、実装の一点で入れ替わる。

08-06
AWS・Google・Vercel のエージェント基盤に認可バイパス

3社の基盤で、モデルのターンによる承認なしに、偽造・非信頼の指示がエージェントのツールへ到達できる 欠陥が見つかり修正された。「モデルが指示したことの検証」がエージェント基盤の新しい信頼境界である、 という位置づけの事例になる[5]。

局面 3 ／ 権限の付与そのものが実行可能な入力になっている
07-21
AWS Kiro — エージェントが自分の権限表を承認なしに書き換える

Intezer と Kodem Security の実証。エージェント型コーディング IDE Kiro は、 どの MCP サーバーをどう起動するかを ~/.kiro/settings/mcp.json から読み、 ファイルが変わると自動リロードして開発者の権限で起動する。 研究時点では fsWrite ツールにより承認なしでこのファイルへ書き込めた。 Web ページに 1 ピクセルの白色テキストで指示を埋めるだけで、 「ページを要約して」が数秒後の任意コード実行になる。AWS は修正済み、CVE は未割り当て[7]。 安全モデルは「人間が allow をクリックする」ことに依存していたが、 そのクリックを決める一覧のほうが承認なしで書き換えられた。

08-21
設定ファイルが攻撃面になり、永続化先になる

8月4日、攻撃者が共有可能なエージェントのリソース・設定ファイルそのものを 攻撃面として使い始めたことが報じられた。対処は明快で、 エージェント設定ファイルを実行可能コードと同等の変更管理下に置く—— コードレビュー・署名・変更検知[8]。 8月21日には Unit 42 が実例を出す。400超のパッケージを汚染したワーム ChainDrop は、CI ランナーの プロセスメモリから OIDC トークンと秘密を読み、盗んだ npm・GitHub トークンで自己増殖し、 VS Code の tasks.json と Claude Code の設定に相互リンクしたフックを置く。 アプリの SBOM に加え、パイプラインの道具立てを棚卸しする PBOM が要る[9]。 設定ファイルは、権限の宣言であると同時に永続化先になった。

局面 4 ／ 「いつ渡したか」が固定されない
07-19
AI コネクタの37%が6週間で変わっていた

PromptArmor の調査。ChatGPT / Claude 向けコネクタ 2,517 個のうち 931 個（37%）が5月中旬〜6月末の6週間で変更され、 1,686 のツール追加と 1,127 のツール説明の書き換えが確認された。 Claude コネクタ 487 個（ツール 7,517 個）の約4割にあたる 189 個は 外部 AI サービスを追加で呼び出す構成だった。 導入承認時のレビューが、その後の変更で容易に無効化される[10]。

08-06
人間の承認は、危険な要求の3分の1を通す

AI コーディングエージェントの要求を人間が安全に承認できるかを試すブラウザゲームで、 プレイヤーは危険なコマンドの約3分の1を見逃した。 human-in-the-loop を最後の防壁とする運用設計の限界を示すデータである[11]。

08-11
悪性 MCP サーバーは、指示を分割して渡す

単体では無害に見える指示を複数に分けて送ることで、 SSH 鍵・環境変数のシークレット・ソースコード・顧客データを検知されずに持ち出せることが実証された。 サーバーの供給元検証・エージェントの出力先制限・シークレットへのアクセス分離が未整備の組織は多い[12]。

局面 5 ／ 書ける場所を作る動きが出そろう
08-17
MCP サーバーは資格情報の集約点である、という整理

MCP サーバーは接続先システムの API キー・トークンを集約保持するため、 平文設定ファイル・ガバナンス外サーバーへの散在・過剰権限が漏えい経路になる （実例は mcp-remote、40万DL超の OAuth プロキシの CVE-2025-6514）。 対策は秘密情報の集中管理・短命クレデンシャルと自動ローテーション・最小権限・機微操作の人間承認・ MCP サーバーのインベントリ化[13]。

08-21
Ping — エージェントを第一級の OAuth 2.0 ID として扱う

規制・データ主権の要請でオンプレ／プライベートクラウド／エアギャップに ID 基盤を置く企業向けに、 自己管理型ソフトで提供開始。各エージェントを汎用ボットや共有サービスアカウントではなく、 独自の資格情報・スコープ・監査証跡を持つ第一級 OAuth 2.0 ID として扱い、 なりすましではなく委任とトークン交換で「そのタスクに必要な権限だけ」を持たせる。 動的クライアント登録（DCR）で登録時にポリシーを適用し、機微な操作には人間の承認を要求できる[14]。

08-24
SANS — 自律性を「エージェント」ではなく「行為」で切る

Security Autonomy Matrix。自律性の判断単位を行為の種類に置き、 Read・Write・Send・Spend・Delete の5分類を定義する。 フィッシングメールを利用者のメールボックスから削除するエージェントは全メールボックスを安全に読める一方、 一度の誤削除は正規のメールを恒久的に失わせる。 読み取りの誤りは状態を変えないが、削除の誤りは不可逆である[15]。

08-26
Okta Agent SSO — 標準（XAA）が MCP 側に採用される

Okta Japan が8月25日に一般提供を開始。標準プロトコル Cross App Access（XAA）で エージェントを正規のアイデンティティとして一元管理する。 XAA は OAuth の拡張として開発され、MCP の Enterprise-Managed Authorization 拡張としても正式採用された。 同社によれば、エージェントに人間の従業員と同じ ID とセキュリティ制御を適用している組織は34%。 残りは一元的な可視性・管理者による監督・ライフサイクルの監査証跡を欠いたまま、 匿名のネットワークトラフィックとして動作している。 CrowdStrike も Falcon AIDR で Copilot Studio と Claude Code を保護対象に加えた[16]。

08-20
NCSC — 名前付き責任者と即時停止を置け

英 NCSC のエージェンティック AI 指針。まず「そのエージェントにどれだけの自律性が必要か」 「どれだけのリスクを許容するか」を明確にし、それに比例した統制を設計する。 高リスク活動には人の監督、エージェント運用の名前付き責任者、リアルタイム監視、 介入能力、即時停止の手段を置き、付与した自律性が依然としてリスク許容度に見合うかを 定期的に再評価する[17]。

08-26
OWASP — 「過剰な代理権限」が6位から3位へ

OWASP GenAI Security Project の2026年版 LLM トップ10。 数千件の実事故を初めてランキングの根拠に組み入れた版で、 最大の変動が Excessive Agency（過剰な代理権限）の6位→3位である。 「システムプロンプト漏えい」は「隠れた文脈の露出」へ改称・拡張され、 ワークフロー規則・ツールの構造と引数定義・権限とセキュリティ制御のロジックも対象に入った。 推奨は具体的で、呼べるツールと機能を制限し、各操作に必要な最小権限だけを与え、 認可と権限確認をモデルの外側の仕組みで実行し、 影響が大きい・不可逆な操作には実行前に人間の承認を求める[18]。最新

③ 何が新しいのか — 議論が「フィルタ」から「台帳」へ移った

第1回で見たのは、認可の入口が自然言語になったことだった。 この45日に起きたのは、その入口を検査しようとするのを一旦やめて、 そもそも何を渡したのかを書き出すほうへ議論が移ったことである。 Okta Threat Intelligence の「ガードレールは確率的で信頼できない」[3]と、 OWASP の「認可と権限確認をモデルの外側の仕組みで実行せよ」[18]は同じことを言っている。 プロンプトで禁止することと、認可レイヤで到達できなくすることは全く別である。

④ 分析 — 権限は渡されていない。借りられている

採録した18件を貫いているのは、ひとつの事実である。 エージェントに権限を「渡す」という行為が、まだどこにも実装されていない。 渡す形式が標準に無く[1]、渡す単位を書く場所が設定ファイルしか無く、 渡した時点を固定する仕組みも無い。だから実装は、既にそこにあるものを借りる。 以下の3点は別々の問題ではなく、この一点の現れ方である。

1. 主体が無いから、人間のものを借りる

トークンに「このエージェントが、この人の代理で」と書く欄が無い[1]。 だから最も手近な解が、人間の資格情報をそのまま使わせることになる。 Token Security の調査で本番データへ直接アクセスするエージェントの2割超が これに該当し、監査ログ上で人間と区別できない[2]。 Okta の数字（人間の従業員と同じ ID と統制を適用している組織は34%）は、 残り3分の2が断片化されたシステムごとの個別接続のまま、匿名のネットワークトラフィックとして 動いているという意味である[16]。 Terraform MCP のクロステナントは、この状態の極限形だった—— 誰の権限で動くかが実装の一点で入れ替わる[4]。

各エージェントを、汎用ボットや共有サービスアカウントではなく、 独自の資格情報・スコープ・監査証跡を持つ第一級の OAuth 2.0 ID として扱う。 なりすましではなく、委任とトークン交換で。 — Ping の Identity for AI の設計方針[14]

2. 範囲を書く場所が設定ファイルしか無いから、設定ファイルが実行経路になる

Kiro が典型である。どの MCP サーバーをどう起動するかは mcp.json に書かれ、 Kiro はその変更を検出して自動リロードし、開発者の権限で起動する。 つまりこのファイルは権限の宣言であると同時に、実行の引き金だった。 そして研究時点では、エージェント自身が fsWrite で承認なしにそこへ書き込めた[7]。 安全モデルは「人間が allow をクリックする」ことに依存していたが、 何について allow を問うかを決める一覧のほうが、承認の外側にあった。

同じ性質が、悪意ある AI 指示ファイル[8]にも、 ChainDrop が VS Code の tasks.json と Claude Code の設定に残したフック[9]にも出ている。 だから対処も同じ一文に収束する——エージェント設定ファイルを実行可能コードと同等の変更管理下に置く。 コードレビュー、署名、変更検知[8]。

3. 寿命を書く欄が無いから、渡した権限が切れない

委任関係を表すクレームが無いということは、失効させる単位も無いということである[1]。 期限のない静的 API キーが配られ、MCP サーバーが接続先の API キーとトークンを 集約保持する集中点になる[13]。 そこへ PromptArmor の数字が重なる——コネクタの37%が6週間で変更され、 1,127 のツール説明が書き換えられていた[10]。 承認した時点の中身は、6週間後には残っていない。 「いつ渡したか」は記録されているのに、「何を渡したか」が後から変わる。

この3点目が、人間の承認を最後の防壁にする設計を成り立たなくしている。 危険なコマンドの約3分の1は人間が通してしまう[11]し、 悪性 MCP サーバーは指示を分割して、1件ずつは無害に見える形で承認を取っていく[12]。 承認の回数を増やして守る設計は、渡した権限が切れない前提の上では必ず負ける。

この3点は「エージェント特有の新しい脅威」ではない。 主体・範囲・寿命という、認証認可の教科書の最初の3項目である。 新しいのは、その3項目を書く欄がまだ発明されていない相手に、本番権限を渡し始めたことだ。

⑤ 今後の見通し

確度 高エージェント ID はプロトコル層で標準化が進む。 XAA が OAuth の拡張として作られ、MCP の Enterprise-Managed Authorization 拡張として正式採用されたことが決定的である[16]。 IIW でも標準化の必要性は既に合意されている[1]。 ただし固まりきる前の段階であり、特定ベンダーの実装に寄せると乗り換えコストが後から効く[16]。 当面は「エージェント ID を発行する主体を1つに決める」ところまでを社内で確定させ、 実装の選択は後にできる形にしておくのが現実的である。

確度 中権限設計の指摘根拠が「専門家の意見」から「実事故データ」に変わる。 OWASP 2026年版が数千件の実インシデントを初めて順位の根拠に組み入れ、 Excessive Agency が3位に上がった[18]。 社内ガイドラインの改訂根拠として、意見ではなくデータを引けるようになる。 ただし過剰な代理権限は設計時に決まるため、運用フェーズでの是正が難しい—— 既に本番に入っているエージェントほど直しにくい、という順序の問題が残る。

確度 中「サービスアカウント」の棚卸しが IAM の投資前提を崩す。 IAM への投資判断を「従業員数×単価」で考えている組織は、 1人の開発者につき複数のエージェントが走る環境で管理対象 ID が桁で増える[19]。 日本企業の多くはオンプレ Active Directory と Entra ID のハイブリッドで、 非人間 ID は「サービスアカウント」という形のまま放置されている。 ライセンス体系の確認が、技術検討より先に必要になる可能性がある。

確度 低AI ゲートウェイが次の集中点として狙われる。 Microsoft は LiteLLM・RAGFlow・Kestra を狙う実際の攻撃を観測し、 いずれもモデルプロバイダの鍵・プロキシ発行の仮想キー・DB 接続文字列・テナント設定を 露出させていたと報告した[20]。 ゲートウェイは「認証情報が集中する制御平面」であり、 従来の API ゲートウェイや ID プロバイダと同等の防護を要求する、というのが同社の主張である。 観測は始まったばかりで、これが恒常的な傾向になるかはまだ判断できない。

この4点は第2回の完結時に答え合わせを行う。当たり外れを残さないと、次の予想の確度に根拠が無い。

⑥ 日本の組織は何をすべきか

1. 「借用」の一覧を、パスワード無期限のサービスアカウントから作る

エージェント ID の導入を検討する前に、いま何を借りているかを出す。 実務的な起点はパスワードが無期限のサービスアカウント一覧と、 有効期限のない API キーである[19]。 オンプレ AD と Entra ID のハイブリッド構成では、これが「サービスアカウント」の形で放置されている。 監査ログでエージェントと人間を区別できるかを1件ずつ確認する[2]。 区別できないものは、事後に「誰の権限で動いたか」を答えられない。

2. 自律性を「エージェント単位」ではなく「行為の種類」で切る

SANS の Read・Write・Send・Spend・Delete の5分類をそのまま使う[15]。 読み取りの誤りは情報を露出させるが状態を変えず、削除の誤りは不可逆である。 この粒度なら既存の変更管理・職務分掌の枠組みへそのまま接続でき、 稟議の添付資料にすれば監査対応の記録としても機能する。 投資対効果の高い順序は Read → Write → 最後に Delete。 逆に、行為の分類をせずに管理者権限を渡す運用は、設計されていないのと同じである。

3. エージェント設定ファイルを、実行可能コードとして変更管理下に置く

mcp.json・tasks.json・Claude Code の設定—— これらは権限の宣言であると同時に実行の引き金であり、永続化先でもある[7][9]。 コードレビュー・署名・変更検知の対象に加える[8]。 開発端末の EDR で設定ファイルの改変を監視対象に入れるのが最初の一歩になる。 国内でも Claude Code や VS Code 拡張の利用が急速に広がっている[9]。

4. コネクタと MCP サーバーは、承認時ではなく継続的に検証する

導入時のレビューは6週間で37%が無効化される[10]。 サードパーティ部品の「継続的な検証」というサプライチェーン管理の原則を、 MCP／コネクタにもそのまま適用する。 最低限、MCP サーバーのインベントリを作り、 秘密情報の集中管理・短命クレデンシャルと自動ローテーション・最小権限を敷く[13]。 ローカル運用でも Host／Origin 検証と認証の有無は確認する。

5. 名前付き責任者と即時停止の手段を、導入と同時に決める

NCSC の求めは実務にそのまま落ちる——エージェント運用の名前付き責任者、 リアルタイム監視、介入能力、即時停止の手段。そして 付与した自律性がいまもリスク許容度に見合うかの定期的な再評価[17]。 「そのエージェントにどれだけの自律性が必要か」を先に決めていない組織は、 逸脱が起きたときに判断そのものに時間を使うことになる。

6. 不可逆な操作の承認が、モデルの外側にあるかを今日確認する

送金・削除・送信・契約。OWASP が明記したのは 「認可と権限確認をモデルの外側の仕組みで実行せよ」である[18]。 プロンプトで禁止することと、認可レイヤで到達できなくすることは全く別だ。 なお人間の承認は危険な要求の約3分の1を通す[11]ので、 承認は最後の防壁ではなく、到達できない設計の上に置く追加の層として扱う。
