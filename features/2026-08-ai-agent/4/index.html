どこから鍵を取られて、エージェントは動いたのか

第4回 読了 約10分 2026-09-19 公開

対象期間 2026-09-05 〜 2026-09-18 ／ 出典 21件 ／ 工程を突き合わせた事案 14件

前回まで 第1回「いま何が起きているのか」で見たのは、認可の入口が変わったことだった。 第2回「誰が権限を渡しているのか」で分かったのは、権限は渡されていない——借りられているということ。 第3回「その範囲は、確かめられるのか」では、確かめられるのはモデルの外だけで、 その外もまだ穴だらけだと分かった。
ここまでは自分たちのエージェントの話だった。今回は向きを変える。 攻撃を実行したエージェントは、どこから鍵を手に入れたのか。
第4回が答える問い

エージェントを動かした資格情報は、どのシステムから、どの手口で取られたのか。 同じ鍵は、自組織のどこに置いてあるのか。

採るもの エージェントが関与した侵害のうち、①どのシステムが攻撃されたか ②何が取得されたか ③どの段階で気づけたか—— の2つ以上が公表・報告から分かるもの。工程の突き合わせには、本サイトのインシデント事例DBに 登録済みで攻撃工程を記録してある14件を使った。
採らない ①
生成 AI で文章やマルウェアを書いただけの事案。鍵の取得経路が変わらないため、 ディープフェイク詐欺と AI 製フィッシングは落とした
採らない ②
「AI が使われた」とだけ言い、手口も取得物も出ていないもの
採らない ③
責任の所在・法的な帰責。第5回で扱う
採らない ④
モデルの能力向上そのもの（大テーマ共通の基準）

① 結論

攻撃側のエージェントは、自前のインフラでは動いていない。誰かの正規の鍵で動いている。 工程まで公表された14件を同じ軸で並べると、取られたものの筆頭は人のパスワードではなく API キーとトークン（7件）で、環境変数・設定ファイル（4件）がそれに続く。 手口に新しいものはほとんど無い——露出したダッシュボード、メール確認前のキー発行、パスワードスプレー、 以前に流出した管理者の資格情報。
新しいのは鍵の置き場所のほうだ。環境変数、CDN のキャッシュ、評価用のダッシュボード、 プラグインの自動更新、そしてエージェント自身。 そのうえ、工程に判定を書けた61段のうち43段（70%）は 「検知の機会はあったのに見逃した」だった。止めるために足りないのは新しい道具ではなく、 鍵がどこにあるかの把握と、すでにある検知点を実際に見ることである。

この回の含意

攻撃側のエージェントは、盗んだ鍵で正規の経路を通ってくる。 被害側のログでは正規の API 呼び出しに見え、しかも呼び出し先が 被害者自身の AI エンドポイントであることすらある。 区別すべきは「AI か人か」ではなく、その鍵はどこに置いてあり、誰が使ってよいものだったかである。

⑤ 今後の見通し

確度 高 鍵の置き場所は増え続ける。指示ファイル（CLAUDE.md・AGENTS.md）、プラグイン、MCP の設定と、 この1か月だけで3つ増えた。いずれも利用者と同じ権限で動き、既存の資産管理の対象外にある。

確度 中 使用量と請求が当面の一次検知であり続ける。操作記録が SIEM に届く割合（第3回で見た10〜20%）が 改善する材料は、この期間には出ていない。

確度 低 エージェント攻撃を記述する共通の語彙が整う。ATT&CK に当てはめた報告は出てきているが （Unit 42 の50超の技術）、鍵の入手経路を記述する粒度は各社ばらばらで、 突き合わせは当面できない。

⑥ 日本の組織は何をすべきか

1. 機械の鍵を棚卸しする

人の認証情報の管理台帳はあっても、API キー・トークン・環境変数の台帳は無いことが多い。 置き場所は少なくとも、CI/CD、クラウドの環境変数、リポジトリ、エージェントの設定・指示ファイル、 そして自己ホストの AI 基盤[19]。まず「どこに何の鍵があるか」を書き出す。

2. 鍵に寿命を与える

14件で取られたもののうち最多は静的な API キーだった。 失効しない鍵は、盗まれた瞬間から気づくまでずっと有効である。 ローテーションと期限を、人のパスワードと同じ強さで運用に入れる。

3. 使用量と請求を検知に使う

METR は3週間・60万ドル相当を消費されるまで気づかなかった。逆に Zeabur の利用者は 使用量の急増で気づいた。AI サービスの消費量とクラウドの課金に、閾値と通知を設定する。 日次の確認では、6時間で終わる作戦には間に合わない。

4. 公開面の「順序」を点検する

RubyGems はメール確認前にキーを発行できた。METR は認証に失敗したときに 通してしまう実装だった。自社にも、認証の強度ではなく 手続きの順序と失敗時の既定に同じ穴が無いかを見る。

5. すでにある検知点を実際に見る

61段のうち43段は、痕跡があったのに見られていなかった。新しい製品を買う前に、 いま出ているログのうち誰も見ていないものを数えるほうが早い。

6. 自動更新に人のレビューを挟む

10体のエージェントによる10時間の攻撃で、唯一止まった場所は Terraform への裏口追加がブランチ保護の複数人レビューで拒否された1か所だった[5]。 基盤コードと、プラグイン・拡張の自動更新は、人の承認を必須にする。
