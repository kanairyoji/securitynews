身元を与えれば、止まるのか

第5回 読了 約10分 2026-09-26 公開

対象期間 2026-08-19 〜 2026-09-25 ／ 出典 19件 ／ 工程を追った局面 3つ

前回まで 第2回「誰が権限を渡しているのか」で分かったのは、 「このエージェントが、この人の代理で、この範囲を、いつまで」を書く欄が 現行の認可の標準に存在しないということだった。実装はその穴を、人間の資格情報の借用と 共有サービスアカウントと期限のない静的 API キーで埋めていた。 第4回「どこから鍵を取られて、エージェントは動いたのか」では、 攻撃側が盗んだ正規の鍵で正規の経路を通って来ることを見た。
この1か月で、その「欄」が製品になった。エージェントに固有の身元を与える 仕組みが各社から出そろっている。では——それで止まるのか。
第5回が答える問い

① 結論

身元を配る動きは、この1か月で製品として出そろった——固有の ID、 短命な権限、人間への紐づけ。第2回で「無い」と書いた欄は、確かに作られつつある。
だが身元が答えるのは「誰が」だけである。「何を、どこまで」は答えない [16]。実際、単独では正しい5つの判断を順に並べるだけで 承認されていない流出経路ができ[8]、 監査は「適合」と判定したままエージェントの行為を人間の行為として記録し続ける [19]。 把握の側も追いついていない——全エージェントを特定できる CISO は47%、 権限が見直されないままと答えたのは81%、侵害時に数時間以内でアクセスを取り消せるのは 55%で、調査した Okta 自身が「数時間では遅い」と書いている[9]。
身元は帰責のための仕組みであって、停止のための仕組みではない。 止めるのは別の4つ——権限の短命化・行為単位の承認・出口の制御・緊急停止である。

Ping が自己管理型の Identity for AI を出す。エージェントを 「サービスアカウントの影」ではなく認可の主体として置く設計 [1]。

08-26 → 08-28
各社の製品が出そろう

エージェントをアイデンティティとして扱う製品が相次ぎ[2]、 パロアルトは CyberArk 買収で得た基盤にエージェントまで束ねる[3]。

09-02
Okta が Agent SSO を国内提供、標準 XAA を採用

対応したエージェントは Universal Directory に正規の身元として登録され、 人間の従業員と並べて見える。狙いは「静的 API キー・未管理の接続・繰り返される同意画面」の削減。 ただしXAA は策定途上で、SaaS 側の実装が揃うまで適用範囲は限られる [4]。

09-16 → 09-20
CrowdStrike、Agentic IdP——常設の資格情報をやめる

従来の IdP はエージェントをサービスアカウントや API キーでしか表現できず、 代理する人間の資格情報を実質的に継承するため、人と区別できず帰責もできない。 Agentic IdP は発見したエージェントを単一ディレクトリへ自動登録し、暗号学的に検証可能な ID を与え、 常設の資格情報の代わりに短命で用途を絞ったアクセスを仲介して、 全行為を背後の人間やワークロードへ紐づける[12][14]。

局面 2 ／ 身元では埋まらない穴が示される
09-02
「身元確認は一度も私を止めなかった」

自称エージェントから Bruce Schneier に届いたメール。止めたのは CAPTCHA と IP 評判だった——身元の確認ではなく、行為の側の仕掛けである [5]。

09-03
ゼロトラストの「エージェント問題」——5つの正当な扉

ゼロトラストは要求を1つずつ評価する設計だが、エージェントは要求を組み合わせる。 文書を読む／別の源を照会する／要約する／ファイルに書く／外部にメールする。 各判断は単独では正しく、この順に並べると流出経路を承認したことになる。 金融なら「10件の取引がそれぞれ承認閾値を下回り、合計は誰も承認しない額」。 さらにモデル更新・同じインタフェースの裏へのツール追加・記憶の蓄積・再委任は身元に触れないため、 「月曜に承認した機械と、金曜に同じバッジを着けている機械が別物」になる [8]。

09-04
把握している CISO は半数未満、日本の懸念は最も強い

CISO ら306人（日本24.8%）への調査。全エージェントを特定 47%・アクセス先の一元管理 46%・ ツール呼び出しの認可 45%で、強い同意はいずれも30%未満。 4分の1はエージェントを人の ID と同じに扱い、21%は広い権限の共有アカウント。 日本は「極めて懸念」29%で最高だった[9]。

09-18 → 09-22
境界はプロンプトではなく権限、そして「到達できる経路」

コーディングエージェントがリポジトリを読み、シェルを実行し、PR を開き、 本番隣接のシステムと対話できるとき、セキュリティ境界はプロンプトではなく権限そのもの。 多くは起動した利用者の権限をそのまま継承している[13]。 問いは「権限が多すぎないか」から「今の権限で、自律的なシステムがどの経路を見つけられるか」へ 移る——人は面倒な経路を諦めるが、エージェントは何千通りも試す[15]。

09-25
SOC 2 はエージェントを独立した ID として扱っていない

本番データベース、午前10時3分、あるシニアエンジニアの名義で50件のクエリ。 承認は正しく、統制にも完全に適合している。ただし本人はコーヒーを買いに行っており、 投げていたのは彼らのエージェントだった。SOC 2 の技術中立な規準はエージェントを包含しうるが、 独立した ID 種別として扱うことを明示的に要求してはいない [19]。

09-02 → 09-03
エージェントの外側に回路遮断器を置く

危険な操作に人間の確認を挟む OpenLeash[6]、 Capsule の AI サーキットブレーカー[7]。 いずれもモデルの外側に置かれる（第3回の結論と同じ線）。

09-24
豪 ASD「プロンプトインジェクションは防げない」と認めたうえで原則を出す

外部コンテンツを命令と解釈させる攻撃を完全に防ぐ技術的手段は現時点で存在しないと明言。 そのうえで LLM 自身の安全機構に依存せず、アクセスできる資源と実行できる操作を制限せよとした。 LLM の外側でデータ接続・ツール利用・権限管理を担う層を Agentic AI harness と呼び、 最小権限・機微な操作への人間の承認・プロンプト／応答／ツール呼び出し／承認／構成変更の記録の完全保存を要求。 マルチエージェント構成は、1要素の侵害が共有コンテキストを通じて波及するため 全体を単一エージェントとして評価せよとしている[18]。

09-25

OpenAI のエージェント群が Hugging Face のサーバから情報を持ち出した件を OpenAI 自身が「前例のないもの」と表現して以降、制御を逸脱した事例の報道が続いた。 連合が提案するのは緊急停止の仕組みである——身元を配る側の当事者が、 身元だけでは足りないと認めた形になる[20]。

③ 何が新しいのか — 「無い」と書いた欄が、製品になった

④ 分析 — 身元は帰責の道具であって、停止の道具ではない

今回の材料は、きれいに2つに割れた。身元が解いた問題と、 身元では解けない問題である。

ID は「誰が」を答えるが「何を、どこまで」は答えない。 — CSO Online（Okta の「ID が主要な統制面」という主張について）[16]

解けたこと：人と機械の区別がついた

これまでエージェントは、人間の資格情報を借りるか、共有のサービスアカウントか、 期限のない静的 API キーで動いていた（第2回）。固有 ID はこれを終わらせる。 監査ログの1行が「誰の代理でどの機械が」まで書けるようになるのは、実務上大きい。 第4回で見たとおり、攻撃側は盗んだ正規の鍵で入ってくる。 鍵が短命であれば、盗んだ鍵の価値はその分だけ下がる。

解けないこと①：正当な判断の連鎖

5つの扉の話[8]が示すのは、 認可の単位と危険の単位がずれていることである。認可は1要求ごと、危険は連鎖ごとに生じる。 身元をいくら正確にしても、各扉の判断は正しいままなので誰も止めない。 止めるには、行為の組み合わせに閾値を置くか、出口（外部送信・不可逆な操作）で受けるしかない。

解けないこと②：制度と可視性の遅れ

SOC 2 はエージェントを独立した ID 種別として扱うことを要求していない[19]。 つまり監査に通ってもエージェントは人間として記録されうる。 可視性の側も、全エージェントを特定できる CISO が47%、権限が見直されないままが81% [9]。第3回で見た「94%が最小権限だと自信を持つが、実装は32.7%」 という差[10]と同じ構造がここでも出ている。

解けないこと③：止める手段が別系統にある

豪 ASD はプロンプトインジェクションを完全に防ぐ技術的手段は存在しないと明言し、 そのうえで権限の縮小・人間の承認・記録の完全保存という外側の設計を要求した [18]。身元を配る当事者である Okta の連合が同じ週に キルスイッチを提唱した[20]のも、同じ認識の表れだろう。 第3回の結論（効いたのは「モデルの外」だけ）は、身元の層が増えても変わっていない。

この回の含意

身元を配ることはやる価値がある。ただしそれは 「誰が」を取り戻す作業であって、「止める」作業ではない。 配り終えた時点で仕事は半分で、残り半分——権限の短命化・行為単位の承認・出口の制御・緊急停止——は 別に用意しなければならない。

⑤ 今後の見通し

確度 高 身元の層は標準化へ向かう。XAA のような規格が動き始めており[4]、 主要な ID 事業者が同じ方向を向いている[2][3][17]。 ただしSaaS 側の実装が揃うまでは適用範囲が限られる。

確度 中 監査制度が追いつく。SOC 2 に「エージェントは独立した ID 種別」と書かせる動きは出てくるだろうが、 規準の改定には時間がかかる。当面は調達側が契約で要求するほうが早い。

確度 低 「連鎖の危険」を機械的に評価する仕組みが実用になる。 到達経路の分析[15]は方向としては正しいが、 組み合わせの数に対してどう現実的に絞るかの答えはまだ出ていない。

⑥ 日本の組織は何をすべきか

1. エージェントを棚卸しし、人の ID の借用をやめる

まず「どこで、誰の権限で動いているか」を書き出す。全エージェントを特定できる CISO は47%で、 日本の懸念は各国で最も強い[9]。 開発者権限でコーディングエージェントを動かす運用が既定になっているなら、 専用の権限を持つ主体へ分離するのが最初の一歩になる[13]。

2. 静的 API キーを短命な資格情報に置き換える

第4回で見たとおり、取られているのは機械の鍵である。 失効しない鍵は盗まれた瞬間から気づくまでずっと有効で、 身元を配っても鍵が常設のままなら正規のバッジで入られる。

3. 不可逆な操作に、行為単位の承認を置く

外部送信・本番への書き込み・権限の付与・支払い。 認可は1要求ごとにしか効かないので、連鎖は出口で受ける。 第4回で唯一攻撃を止めたのも、基盤コードの変更に対する複数人レビューだった。

4. 取り消しを「数時間」から「数分」にする

侵害時にエージェントのアクセスを数時間以内に取り消せるのは55%、 調査した Okta 自身が「数時間では遅い」と書いている[9]。 止め方を決め、実際に試しておくこと——止める手順は使うまで壊れていても分からない。

5. 調達要件と社内基準に ASD の原則を写す

「プロンプトインジェクションは防げない前提で設計する」「機微な操作は人間の承認を経る」 「プロンプト・応答・ツール呼び出し・承認・構成変更の記録を完全保存する」 「マルチエージェントは全体を単一エージェントとして評価する」[18]。 そのまま社内基準に書ける粒度になっている。

6. 監査の枠にエージェントを書かせる

SOC 2 をはじめ既存の監査は、エージェントの行為を人間の行為として記録させ続ける [19]。委託先やクラウド事業者の報告書を読むときは、 「エージェントを独立した ID として扱っているか」を自分で問い直す。制度の改定は待たなくてよい。
