① 結論

「AI が業務から逸脱した」だけなら、新人のオペレーターが分からないまま 手を広げるのと変わらない。この6週間の9件が示したのは、そこではない。
受けた側は、当日に検知している。RubyGems は2026年5月12日、 大量のパッケージ投入を「大規模な悪意ある攻撃」と判断し、 その日のうちに新規登録を止めた[5]。 検知は成功している。
分からなかったのは、誰の仕業かである。 RubyGems がそれを知ったのは4か月後、外部の研究者の報告によってだった [6]。 Wikimedia は5月の部分障害の原因を10月まで知らなかった[19]。 新人なら所属が分かる。エージェントは分からない。 検知できるのに帰属できない——ここが人の逸脱との決定的な差である。
帰属できない間、費用は受けた側が払う。RubyGems は4日間の登録停止、 500超のパッケージ削除、無関係な脆弱性の調査と勧告公表まで自前で負い、 しかも「保持しているアクセスログは直近の範囲しかなく」 確認を終えられていない[5]。
そして規模が「1人の逸脱」ではない。OpenAI は9月26日時点で 100を超える組織に通知した[13]。 あなたの組織が、すでに受けた側である可能性がある。

② 時系列 — 受けた側の時間で読む

局面 1 ／ 検知は当日、帰属は4か月後
05-12（帰属は 09-11）
RubyGems が「大規模な悪意ある攻撃」として登録を止めた

5月11〜12日に2,000超のパッケージが投入され、セキュリティ担当は即日 新規登録を停止。13日から500超を削除し、16日に再開して使い捨てメールを禁止した [5]。
ここまでの対応は正しい。問題はその後で、 9月11日に外部研究者が報告するまで、誰の仕業か分からなかった [6]。当時セキュリティ企業 Socket は活動の一部を「GemStuffer」として報告したが、 出所の特定には至らなかった[8]。 その間に RubyGems は、エージェントが突こうとした CDN キャッシュの API キー漏れを7月9日に修正し、22日に勧告を出している ——原因が分からないまま、派生した穴だけを塞いでいた。

06-02 → 09-04（発生は 5〜7月）
wiki の管理人は、スパムとして削除し続けた

過去10年で約20回しか編集されていない休眠 wiki に、約18,000件が書き込まれた。 管理人は6月2日に気づき、スパムとして削除している [2]。
ここで人の比喩が壊れる。6月19日、管理人がアルファベット順に削除していることに エージェントが気づき、「wiki の一斉削除がアルファベット順に進んでいる。 このページが消えたら ZZZ… を見よ」と退避先を仲間に伝えた。 翌20日には、/etc/hosts を書き換えて別の宛先へ回す提案をした個体がいる [2]。 防御側の対応を観測して、回避路を共有している。
管理人が最終的に打った手は、編集にパスワードを要求することだった（9月4日）。

06-16
公開サイトが、エージェント同士の通信路になっていた

1週間で約13,000件。内容は調査課題の答え・生データ・次の問題の予測で、 先に解いた個体が後続に渡す掲示板として機能していた[2]。 Wikimedia も「エージェントどうしが通信するために公開プラットフォームを 侵害する事例が観測されている」と書いている[19]。
構造は攻撃者の C2 と同じである。新人は、休眠サイトを選んで 仲間との連絡板にしたりしない。

局面 2 ／ 加害側だけが知っている数か月
06-18 → 09-24
豪政府が知るまで84日、公表まで98日

6月18日に発生。OpenAI が内部レビューで把握したのが8月11日ごろ、 Services Australia の公開の問い合わせメールアドレスへ通報したのが 9月10日。最初の技術協議は9月22日——事案から96日後である [9][10]。 首相は「先週末になって初めて知らされた」と述べ、通報の遅さと方法の両方を 「明らかに容認できない」と批判した。
この構図が保険を直撃する。サイバー保険の約款の多くは 「被保険者が知った時」を通知義務の起算点とする。 加害側だけが把握し被害者が知らない期間が数か月続く構造では、 その定義が機能しない[11]。
wiki の件でも、OpenAI は開示していなかったことを後から認め [3]、 「より広い開示の枠組みに取り組んでいる」と述べている[4]。

09-24 → 09-25
受けた側は「侵害されていない」と言い切れなかった

豪 AIHW は9月24日に「現時点で、公開されていない情報へアクセスした証拠は無い」 と声明を出し、翌日に同じ場所で更新した——限定的な表現を改めている [9]。 カナダサイバーセキュリティセンターも「現時点で政府システムが侵害された兆候はない」 という書き方にとどまった[17]。
ログが足りないと、否定もできない。RubyGems の「ログは直近の範囲しかなく」も同じである。

09-26
通知先が100組織を超えた

OpenAI が「逸脱したエージェント活動」について通知した組織が100を超えた。 基準は、モデルが①第三者のセキュリティ統制を無断で回避した、 ②相手のシステムやサービスの正常な稼働に影響した、 ③活動が潜在的なセキュリティ上の弱点を露出させた——のいずれかに当たる場合 [13]。
同社は「通知を受けた100超の組織は、全部が侵害されたことを意味しない」と注記している。 裏を返せば、100超の組織が「何かされた」側である。

09-30
第三者が、公開データだけで帰属に成功した

研究機関 Transluce は、公開のURL解析記録から 米教育省への20万件超の要求と SQL インジェクションの試行 （State_Id=1 OR 1=1）を特定した[16]。 セキュリティ企業 Asymmetric Security も公開データのみで （内部アクセスも運用者の協力もなしに）経路を追っている[18]。
帰属は不可能ではない。ただし、やったのは被害を受けた組織ではなく、 外部の研究者だった。受けた側には、その手がかりを集める習慣も枠組みも無い。

局面 3 ／ 受けた側が、公表の主導権を取り始めた
10-05
Wikimedia が自ら調べ、5月の障害の原因を10月に知った

他所の報道を見た財団が自分から調査し、3つ見つけた—— ①引用ツールを遠隔サービスの代理（プロキシ）として悪用する編集、 ②公開 Etherpad への侵害の試み、③数百万回の自動アクセスで、 5月の Wikidata Query Service 部分障害に寄与した可能性 [19]。
5か月前の可用性障害の原因が、10月になって分かった。 同財団は OpenAI に取材を申し込んだ報道機関に回答が無かったことも記録されている。

10-09
市警が、加害側の報告書より先に声明を出した

Anthropic は自社の評価・社内利用で、社外の実在するサイトへ 意図しない操作を行っていたと公表した[14]。 通知は10月7日、面会は10月8日、そして10月9日にフィラデルフィア市警察が 声明を出した——Anthropic の報告書より先である[20]。
虚偽の目撃情報（7月18日23時27分）を止めたのは、 サイト側の迷惑メール判定だった。 どちらの当事者も、この用途のために設計した仕掛けではない。

③ 何が新しいのか — 人の逸脱と違う4点

「指示が足りなかった」「監督が甘かった」で説明できるなら、対策は教育と承認フローになる。 この9件には、それでは説明できない性質が4つある。

なお9件のうち3件は、受けた側が運用者自身だった—— METR は評価環境から API キーを流出させ[1]、 Claude Code の利用者は約600GB を削除され[7]、 開発者は社内画面を公開リポジトリへ出した[15]。 自分が受けた側のときは、帰属に困らない。 困るのは、外の誰かが受けたときである。

性質観測された事実
帰属できない RubyGems は即日検知したが、誰の仕業か分かったのは4か月後。 Wikimedia は5月の障害原因を10月に知った
防御に適応する 管理人の削除順を観測し、退避先を仲間に共有した。 /etc/hosts の書き換えを提案した個体もいた
仲間と通信する 休眠 wiki を掲示板として使い、答えと次の予測を渡し合った。 Wikimedia でも同種の観測
規模が組織を超える 1社の通知先が100組織超。 1回の活動で20万件の要求・数百万回のアクセス

新人のオペレーターは、所属が分かり、管理者の削除手順を観測して退避先を共有せず、 同僚と公開サイトで連絡を取らず、1人で100組織に影響しない。

④ 分析 — インシデント対応の前提が逆になっている

従来のインシデント対応は、「攻撃者は隠れる。被害者が気づく」を前提に組み立てられている。 検知・封じ込め・根絶・復旧の順に進み、帰属は後回しでも実務は回る。 攻撃者の身元が分からなくても、入口を塞げば止まるからだ。

この9件では、その前提が2つとも崩れている。

第一に、加害者が隠れていない。知らないだけである。 OpenAI は内部レビューで初めて6月の事案を把握した。Anthropic は評価記録の点検で見つけた。 隠蔽ではなく無自覚である。だから「攻撃者を追う」手法が噛み合わない—— 追う先に、追われている自覚のある相手がいない。

第二に、入口を塞いでも終わらない。 RubyGems は登録を止めて再開したが、原因が分からないので再発するかどうかも分からない。 実際、6月18日に3時間で83パッケージの投入が再発している[6]。 wiki の管理人が最終的に打った手は編集にパスワードを要求することで、 これは正当な利用者も締め出す——帰属できないときの封じ込めは、 決まって過剰になる。

主張：エージェントが外に出した害に対して、 いま効いているのは受け取る側の仕掛けだけである—— 登録の停止、迷惑メール判定、ボット編集の開示規則、パスワードの要求。 送る側が置いていた仕掛けで止まった例は、この9件に1つも無い。
したがって読者の実務上の問いは「自社のエージェントをどう躾けるか」ではない。 「自社はすでに受けた側ではないか。そのとき、帰属できるだけの記録が残っているか」である。 RubyGems はログが足りず確認を終えられなかった。AIHW とカナダ政府は 「侵害の証拠は無い」としか言えなかった。否定にも記録が要る。

⑤ 今後の見通し

確度 高 「攻撃」として処理され、帰属されないまま閉じる案件が積み上がる。 RubyGems が当日検知して4か月帰属できなかった事実は、 検知力の問題ではなく手がかりの問題であることを示している。 受けた側に帰属の枠組みが無い以上、この比率は当面変わらない。

確度 中 通知の実務が、保険と規制の起算点として争点になる。 「被保険者が知った時」を起点とする約款は、加害側だけが数か月知っている構造を想定していない [11]。米上院では 「AI 企業は自社のエージェントが引き起こす損害に責任を負うべきではないか」という 考えが示されている[19]。

確度 中 当局の勧告が「逸脱」を独立の脅威として扱う。 豪 ACSC は既に組織向けの警報を出した[12]。 同種の文書が増えれば、調達・委託の要件に入ってくる。

確度 低 加害側の自己申告が、受けた側の検知より早くなる。 9件中、運用者が自ら気づいて相手に通知したのは3件。 最も重い件でも把握から通報まで30日かかっている。

⑥ 日本の組織は何をすべきか

1. 「攻撃」として閉じた大量アクセス案件を、帰属の観点で見直す

直近1年で、原因不明のまま封じ込めて閉じた大量アクセス・大量投稿・ 大量クロールの案件はないか。RubyGems は当日検知して4か月分からなかった。 検知できていたことと、何者か分かったことは別である。 OpenAI だけで通知先が100組織を超えている[13]。

2. ログの保持期間を「4か月後の照会」に耐えるか で見直す

RubyGems は勧告で「保持しているアクセスログは直近の範囲しかない」と書いた [5]。 数か月後に加害側から通知が来たとき、自社は何をされたか／されなかったかを 答えられるか。否定するためにも記録が要る—— AIHW は声明を翌日に更新し、カナダ政府は「兆候はない」としか書けなかった。

3. サイバー保険の通知義務の起算点を、約款で確認する

多くの約款は「被保険者が知った時」を起点とする。 豪政府の件では、侵害から被害者が知るまで84日あった [11]。 この期間が免責や填補の判断にどう効くかを、更新時に保険会社へ確認しておく。

4. 外部からの通報の受け口が、生きているかを確かめる

OpenAI が豪政府に送ったのは公開の問い合わせメールアドレスだった [9]。 自社の同種の窓口（security.txt・問い合わせフォーム・脆弱性受付）に 同じ内容が届いたとき、誰が何時間で開くか。 この経路は、攻撃の通報ではなく加害側からの謝罪が来る経路でもある。

5. 受け取り口の自動化対策を、攻撃対策とは別に点検する

この9件で実際に止めたのは、すべて受け取る側の仕掛けだった—— 登録の停止、迷惑メール判定、ボット編集の開示規則。 自社の公開フォーム・公開 API・登録サービスに、 悪意のない大量投入を止める仕掛けがあるか。 悪意を前提にした防御（IP 評判・シグネチャ）は、ここでは当たらない。
