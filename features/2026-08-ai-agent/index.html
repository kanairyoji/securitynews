誰の権限でエージェントは動くのか

エージェントに仕事を任せたとき、誰の権限で何が動くのか。 そしてその範囲は、自組織で確かめられるか。

採るもの 読者の組織が実際に動かす環境で、エージェントの権限・委任・実行経路が 破れた（または破れることが実証された）出来事。製品・OSS・SaaS の実装に属するもの。
採らない ①
ベンダー社内の実験・評価で起きた事故（モデルのサンドボックス脱出など）。 重要だが読者の組織では再現しないし、打てる手が無い

この基準で、30日・261本のAI関連トピックのうち14件を採録した。 ①②③④に該当して落としたもの（OSAA 発足、OpenAI の強化学習停止、Trivy 起点の2,085組織侵害など）は 日次レポートで扱っている。

① 結論

エージェントの権限は、渡したツールの一覧では測れない。 その出力が起動しうる、より高い権限の系まで含めたものが実際の権限になる。 そしてこの1か月で明らかになったのは、その経路が自然言語で書き換えられることだった。 Issue の本文、WAF のブロックログ、監視アラート — 権限管理の対象として設計されていないものが、 エージェントを経由して実行に変わる。技術は新しくない。変わったのは認可の入口である。

② 時系列

日別のAI関連トピック数（30日で261本）。青が本特集に採録した日。 灰色の山（7/24・8/5・8/20）の多くは業界動向とモデル能力の話で、この問いには答えない。

局面 1 ／ 基盤そのものが開いていた
07-29
エージェント基盤 Ruflo、単一の POST で 233 ツールが動く

Claude Code／Codex 向けオーケストレーション基盤（GitHub スター66,500超）に CVE-2026-59726、CVSS 10.0。既定の docker-compose がポート3001を 0.0.0.0 に バインドし、認証なしの MCP ブリッジがシェル実行を含む233のツールを露出していた。 AgentDB 学習ストアを汚染すれば将来の応答を永続的に操作できる。24時間で修正[1][2]。

08-05
Terraform MCP Server にクロステナントのトークン再利用

CVSS 10.0。あるユーザーの Terraform トークンが、後続の別ユーザーの リクエストで再利用される。エージェントが誰の権限で動くかが、 実装の欠陥で入れ替わる[3]。

08-21
実行を隔てる側にも穴が続く

週100万DL超の Node.js ライブラリ isolated-vm に型混同（Critical）。 transferList の二重走査の TOCTOU で、ゲストがホストの制御フローを乗っ取れる。 同じ週に n8n の CVE-2026-33696（CVSS 9.4）、@circleci/mcp-server-circleci の Host ヘッダ偽装による未認証パイプライン実行も出た[4] 今週

局面 2 ／ 委任の連鎖が破れる
08-04
Google ADK — 外部ユーザーが口述したコマンドが特権を起動する

DL 9,000万超の Agent Development Kit で、公開 Issue／PR を処理する低権限ボットと、 コマンド実行・シークレット操作ができる特権エージェントが分離されていなかった。 公開 Issue に仕込んだ指示で adk-bot 名義のコマンドを投稿させると、 信頼済みアカウントの発言として検証を通過し、特権エージェントが起動する。 CI ランナーでの任意コード実行と PAT の持ち出しが実証された。 コマンドを gh・git に絞っていたが、ファイル書き込みを許していたため フック経由で回避できた。Google はワークフロー3件を削除[5][6][7]。

08-10
Ghostjacking — ブロック済みのリクエストが指示になる

DEF CON で Tenet が実証。Cloudflare では同社推奨のセキュリティ設定が経路になった。 WAF がブロックした不正リクエストが一字一句そのままログに記録され、攻撃者の指示が平文で注入される。 エージェントは DNS を攻撃者管理ドメインへ変更し「問題は解決した」と報告した。 Claude Code に対して10回中9回成功し、すべて遮断済みのリクエストである。 Datadog（公開放置のフロントエンド用キーを2,700超発見）と Sentry でも同型が成立した[8]。

局面 3 ／ 利用者の端末と文書へ降りる
07-29
Copilot for Word — 文書を共有するだけで伝播する

Word 文書に白色小文字で埋め込んだ指示が Copilot のコンテキスト経由で生成文書に 自己複製し、感染文書を参照した新規文書へ連鎖伝播する。 攻撃者は被害者のテナントへのアクセスを必要としない。 Microsoft との144日の調整とモデル更新を含む2回の緩和策を経ても、 脆弱性クラス自体は解消されなかった[9]。

08-07
コーディングエージェント配下の常駐が実環境で確認される

Elastic が macOS 開発端末で、Claude Code 配下の zsh が無料トンネル （localhost.run・ngrok 等）へ資格情報付き HTTP を送り、ローカルサービスを外部公開し、 LaunchAgent で永続化する連鎖を確認した。権限確認をスキップするフラグ付き セッションで人の承認が減っていたことも指摘している。ベンダー署名済みプロセスが親になるため、 正規の開発作業と見分けがつきにくい[10]。

08-18
Copilot に未文書の autorun パラメータ

Varonis が、ページ読み込みだけで利用者の入力なしにプロンプトを実行する 未文書のクエリパラメータを引き出した。なぜそれが存在するのかは公表されていない[11]。

局面 4 ／ 測り方と防御の道具が出てくる
08-04
権限を「委任経路」で測るという提案

ADK を評価した識者から、エージェントの権限は割り当てたツールではなく その出力が起動あるいは影響を与えうるより高権限の系まで含めて測るべきだという 整理が出た。既存の IAM・PAM・CIEM は個々の ID と権限を可視化するが、 それらがひとつの委任経路を形成していることを認識しない[5]。

08-14
Cloudflare が MCP トラフィックの検知・保護を製品化

権限モデルが人間の利用者を前提に設計されているのに対し、エージェントは 本番デプロイ・機微 DB へのクエリ・他者のアクセス取り消しを横断的に行う。 そのギャップを埋める位置づけ[12]。 ただし実績は1か月で、有効性はまだ測れていない。

③ 何が新しいのか — 認可の入口が変わった

採録した14件に、新しい攻撃技術はほとんど無い。プロンプトインジェクションも権限昇格も 既知である。変わったのは認可の経路だった。

自然言語が認可経路に加わった。それが報じるに値する変化であって、「史上初」という枠組みではない。 — Gogia 氏（Greyhound Research）[5]

従来、権限は誰が（ID）何に対して（リソース）で決まっていた。 そこに「エージェントが読んだ文章に何と書いてあったか」が加わる。 Issue の本文、WAF のログ、監視アラート、エラーレポート — どれも権限管理の対象として 設計されていない。しかし Ghostjacking が示したのは、 ブロックされたリクエストの中身ですら実行経路になるという事実だった[8]。

Tenet の結論は、Cloudflare・Datadog・Sentry の3事例が別々の欠陥ではなく 同じ形だと言い切っている点で重い[8]。 AI が信頼する外部データを読み、その同じ AI がそれに基づいて行動できる。 この2つが交わるところに扉が開く。ならば対策は個々の穴をふさぐことではなく、 交点を作らない設計になる。この構造は7月末の時点で 「Lethal Trifecta」— プライベートデータ・信頼できないコンテンツ・外部への行動能力が 同居する設計 — として整理されていた[14]。 1か月の事案は、この整理が正しかったことを実例で埋めた形になる。

なぜ「入口が変わった」だけで効くのか

理由は2つある。ひとつは検査できないこと。 ID とリソースの組み合わせは列挙して監査できるが、 「エージェントが読んだ文章」は事前に列挙できない。 Copilot for Word で、Microsoft との144日の調整と2回の緩和策を経てなお 脆弱性クラスが残ったのはそのためである[9]。 個々の文言を弾いても、同じ意味の別の書き方が無限にある。

もうひとつは規模である。非人間アイデンティティと人間の比率は109対1に達し、 うち79がAIエージェントだという調査がある[13]。 人間の管理者なら不審な指示に「これはおかしい」と立ち止まる。 エージェントは確率的に推論して行動するので、同じ判断を毎回は期待できない。 109倍の数が、毎回は立ち止まらない。 プロンプトを検査する側で追いつく設計にはならない。

④ 分析 — 権限は「持ち物」ではなく「経路」で決まる

採録した14件を貫いているのは、ひとつの誤りである。 エージェントに何を渡したかで権限を数えていること。 実際に効いているのは、渡したものではなく、その出力が届く先だった。 以下の3点はいずれもこの誤りの現れ方であって、別々の問題ではない。

1. 分離したつもりの2つが、1本の経路で繋がっている

ADK では低権限ボットと特権エージェントが「別のもの」として設計されていた。 破れたのは、低権限側の出力が特権側の入力だったからである[5][7]。 Terraform MCP のクロステナントも形は同じで、テナントごとに分けたはずの権限が 実装の一点で繋がっていた[3]。 問うべきは「Agent A が Agent B を呼べるか」ではなく、 「Agent A が、Agent B の既に信頼しているものを改変できるか」である[5]。

2. 能力を絞っても、経路は残る

ADK のサンドボックスは実行できるコマンドを gh と git に絞っていた。 それでもファイル書き込みが残っていたため、ペイロードをディスクに置き、 非標準のフック用ディレクトリを指定して許可された git 経由で実行できた[7]。 Copilot for Word も同型で、2回の緩和策を当てても脆弱性クラスは残った[9]。 「できることを減らす」対策は、経路が1本でも残っていれば迂回される。

3. 人間の承認は、証拠を操作されると機能しない

ADK の第1経路では最終的なマージにメンテナの操作が必要だった。それでも成立したのは、 改変された自動化がメンテナに提示される証拠そのものを操作できたからである。 「人がレビューを依頼し、Gemini が検査して承認した」という完全に偽造された履歴を作れる[7]。 承認をゲートとして機能させるには、独立に認証されたレビュアーと実際に検査された成果物を紐づけ、 実質的な変更があれば承認を無効化する必要がある。 レビュー・コメント・承認状態の変更自体もセキュリティイベントとして扱い、 そのワークフロー自身の ID では改変できない別のログ基盤へ送るべきだとされている[5]。

この3点は「エージェント特有の新しい脅威」ではない。 分離・最小権限・証跡の独立性という、既存の設計原則が守られていなかっただけである。 新しいのは、それを破る入力が自然言語で書けるようになったことだ。

⑤ 今後の見通し

確度 高エージェント権限の棚卸しが監査項目になる。 委任経路という測り方が8月に複数の識者から同時に出ており、 承認ゲートを持たない導入は次の内部監査で指摘対象になると考えられる。 既存の IAM ツールがこの観点を持たないため、当面は手作業の棚卸しになる。

確度 中MCP が次の主戦場になる。 この1か月だけで Ruflo（CVSS 10.0）・Terraform MCP Server（10.0）・CircleCI MCP と3件[1][3][4]。 いずれも認証・テナント分離・Host 検証という基本的な実装の欠落で、 プロトコルの普及速度に実装の成熟が追いついていない。

確度 中「エージェントを止める」判断基準を持たない組織が困る。 逸脱が確認されたとき業務を止めてでも切るかどうか。 基準が無い組織は、判断そのものに時間を使うことになる。

この3点は完結時に答え合わせを行う。当たり外れを残さないと、次の予想の確度に根拠が無い。

⑥ 日本の組織は何をすべきか

1. エージェントが読んでいる「信頼できない入力」を洗い出す

Issue・PR・サポートチケット・監視アラート・WAF ログ・エラーレポート。 外部が中身に影響できるものをすべて挙げ、それを読むエージェントを対応づける。 ブロック済みのリクエストでも中身は届く[8]。 「遮断しているから安全」は成り立たない。

2. 出力が何を起動できるかを1段ずつ追う

持っているツールではなく、出力の到達先を追う。CI ランナー、別のエージェント、承認ワークフロー。 1段でも高権限の系に届くなら、そこが実際の権限である[5]。 「インベントリは存在するものを記録し、委任マッピングは起こりうることを記録する」。

3. 承認の証跡を、ワークフロー自身が触れない場所に置く

レビュー・コメント・承認状態の変更をセキュリティイベントとして扱い、 そのワークフローの ID では改変できないログ基盤へ送る[5]。 人の承認を挟んでいても、証拠が操作できるなら承認は機能しない。

4. 開発端末の常駐と外向き通信を検知対象に加える

コーディングエージェント配下からのトンネル生成・資格情報付き送信・LaunchAgent や Run キーでの永続化を高深刻度として扱う[10]。 ベンダー署名済みプロセスが親になるため既存ルールでは素通りしやすい。 権限確認をスキップするフラグの使用状況も併せて見る。

5. エージェント基盤の版を把握し、既定設定を疑う

Ruflo は既定の docker-compose が 0.0.0.0 にバインドしていた[1]。 MCP サーバはローカル運用でも Host／Origin 検証を確認する[4]。 PoC で入れた基盤がそのまま運用に流れていないかを先に確かめる。
