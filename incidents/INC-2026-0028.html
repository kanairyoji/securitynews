INC-2026-0028Snowflakeの脆弱性をAIが見逃しAIが発見

SnowflakeのCI/CDワークフローに混入したスクリプトインジェクションをGitHub Copilotが共著者としてレビューし「問題なし」で見逃し、Wizの自律攻撃AIが5日後に発見・悪用しJira認証情報を窃取——「AIが見逃しAIが見つける」を実証した正規開示事案

脆弱性不正アクセス・侵害続報が止まり調査も完了有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備既知の脆弱性の悪用
初報: 2026年8月17日 最終更新: 2026年8月19日

2026年6月、Snowflake の公開リポジトリ snowflakedb/snowflake-connector-net の
GitHub Actions ワークフローに、スクリプトインジェクション脆弱性が混入しました
（6月18日・PR #1218）。当該コミットには AIコーディング支援「GitHub Copilot」が
共著者として関与し、マージされた PR とコード変更をレビューして「問題なし」と
判定していましたが、Copilot 自身が脆弱なコードを書いたのかは不明であると Wiz は
後に明確化しています。5日後の6月23日、
セキュリティ企業 Wiz の自律型攻撃AI「red agent」が公開リポジトリの定期スキャンでこれを
発見し、細工した GitHub Issue のタイトルを使って GitHub Actions ランナー上で任意コマンドを
実行させ、Jira の認証情報を帯域外コールバックで窃取しました。窃取したトークンでは
Snowflake のエンジニアリング・セキュリティコンプライアンス・バグバウンティ管理の
Jira プロジェクトへの読み取りアクセスが可能でした。これは Snowflake の HackerOne 経由の
正規の脆弱性開示プログラムを通じた許可された調査であり、Snowflake は報告と同日に修正、
翌日に Jira トークンを失効・ローテーションし、監査ログで露出5日間に Wiz 以外の第三者
アクセスがなかったことを確認しました。Wiz は調査で参照したデータをすべて削除しています。
「AIが脆弱性を作り込み、別のAIが自律的に発見・悪用する」構図を実企業のケースで示した
象徴的事案として、公表・報道から確認できた範囲を、事実と本記録の評価を分けて整理します。

2026年8月20日 訂正更新履歴へ
2026年8月19日の CSO Online の報道を受けて訂正。Wiz が当初の開示を更新し「Copilot は 共著者としてマージされた変更をレビューし問題なしと判定したが、Copilot 自身が脆弱 コードを書いたかは不明」と明確化したため、タイトル・リード・年表・攻撃の解剖・図の 「Copilot Autofix が混入させた」という断定を「共著コミットで混入し、Copilot は レビューで見逃した（作成者は不明）」に改めた。GitHub Advanced Security のスキャンが 検出に失敗していた事実と、Wiz CTO の「人間と AI の帰属の確立自体が難しい」という 指摘を追記した。訂正の経緯は discrepancies（primary_source_revised）に記録した。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

Snowflake の公開リポジトリの GitHub Actions ワークフロー（jira_issue.yml）で、 Issue タイトルをサニタイズしていた安全なパターンが直接シェル展開に置き換わり、 スクリプトインジェクション脆弱性が混入した（2026年6月18日・PR #1218。コミットの 共著者である GitHub Copilot はレビューで「問題なし」と判定して見逃し、Copilot 自身が 書いたかは不明と Wiz が明確化。GitHub Advanced Security も検出しなかった）。任意ユーザーが Issue を作成できるため認証不要でコマンド実行が可能になり、Wiz の自律型攻撃AI red agent が 5日後に定期スキャンで発見。細工した Issue タイトルで Jira 認証情報（API トークン・ ユーザーメール・ベース URL）を base64 化して帯域外コールバックで窃取した。トークンでは Snowflake の複数 Jira プロジェクトへの読み取りが可能だった。正規の HackerOne 開示であり、 Snowflake は同日修正・翌日ローテーション・監査ログでの影響確定を行った。

  1. 1. 初期侵入確認済[1] [2]
    Wiz の red agent が公開リポジトリの定期スキャンで jira_issue.yml のスクリプト インジェクションを検出し、任意ユーザーが作成できる Issue のタイトルにペイロードを 埋め込むことで、GitHub Actions ランナー上でのコマンド実行の足がかりを得た。
    根拠: Wiz ブログ、The Register の報道
  2. 2. 実行確認済[1]
    細工した Issue タイトルがテンプレート展開され、GitHub Actions ランナー上で任意の シェルコマンドが実行された。red agent は最初の失敗（コメント文字による）を自ら分析し、 修正版ペイロードで実行に成功した。
    根拠: Wiz ブログ
  3. 3. 認証情報アクセス確認済[1] [2]
    実行されたコマンドが、ランナー環境の Jira 認証情報（API トークン・ユーザーメール・ ベース URL）を base64 エンコードした。トークンは qa@snowflake.net で認証され、 snowflakecomputing.atlassian.net の複数プロジェクトへの読み取りが可能だった。
    根拠: Wiz ブログ
  4. 4. 持ち出し確認済[1]
    base64 化した認証情報を、外部リスナー（OAST 型サーバー）への HTTP リクエストの URL パラメータとして帯域外コールバックで送信した。
    根拠: Wiz ブログ

AIが脆弱性を作り込み、別のAIが自律的に発見・悪用する構図が正規開示のケースで完結して観測された概観出典 [1] [2]

The Register（2026年8月17日）および Wiz のブログによれば、Snowflake の公開リポジトリ
snowflakedb/snowflake-connector-net の GitHub Actions ワークフローに、GitHub Copilot が
共著者として関与したコミットによりスクリプトインジェクション脆弱性が混入した
（2026年6月18日。Copilot 自身が書いたかは不明で、Copilot はレビューで「問題なし」と
判定していた）。5日後の6月23日、Wiz の自律型攻撃AI「red agent」が公開リポジトリの
定期スキャンでこれを発見・悪用し、Jira の認証情報を窃取した。

重要なのは、これが悪意ある攻撃ではなく、Snowflake の HackerOne 経由の正規の脆弱性開示
プログラム（VDP）を通じた許可された調査だった点である。Snowflake は Wiz の報告と同日に
修正し、翌日に Jira トークンをローテーションし、監査ログで露出5日間に Wiz 以外の第三者
アクセスがなかったことを確認して公表した。Wiz は調査で参照したデータをすべて削除している。

本記録がこの事案を扱うのは、被害の大きさゆえではなく、「AIが脆弱性を作り込み、別のAIが
自律的に発見・悪用する」という新しい攻防の構図が、実企業のケースで初期から終息まで
完結して観測された象徴的な先例だからである。

脆弱性はIssueタイトルの直接シェル展開で、Copilot Autofixが既存のサニタイズを外して混入した原因・手口出典 [1] [2] [4]

Wiz のブログによれば、対象は .github/workflows/jira_issue.yml ワークフローで、
攻撃者が制御できる github.event.issue.title（Issue のタイトル）がシェルスクリプトに
直接展開される構造だった。Issue の作成（issues: opened イベント）は任意のユーザーが
行えるため、認証なしで GitHub Actions ランナー上のコマンド実行につながった。

混入の経緯が本事案の核心である。元のワークフローは、Issue タイトルを環境変数に渡し
jq --arg で安全に処理するサニタイズ済みのパターンを採っていた。ところが2026年6月18日、
Copilot Autofix が共同著者となったコミット（PR #1218・コミット 4a1b8ce）が、この安全な
パターンを削除し、TITLE=$(echo '${{ github.event.issue.title }}' | sed ...) のような
直接シェル展開に置き換えた。GitHub のテンプレート展開が sed のエスケープより先に行われる
ため、シングルクォートを含む Issue タイトルで echo の文字列を破壊し、任意コマンドを
注入できる状態になった。

Wiz は「AIエージェントは、なぜ元のコードがサニタイズしていたのかという履歴的文脈を欠く」
と指摘し、構造化データパーサーの直接シェル展開への置換をブロックするガードレールが
必要だとしている。

なお、「誰がこの脆弱な変更を書いたのか」については続報で重要な明確化があった。
Wiz の当初の開示は Copilot が脆弱コードを書いたと示唆していると受け取られ批判を
受けたため、Wiz はブログを更新し「Copilot はマージされた PR とコード変更を確認した
共著者であり、重大な脆弱性に気づかないまま問題なしと判定した。Copilot 自身が
脆弱性を混入させたのかは不明」と明確化した（CSO Online・2026年8月19日）。
Wiz の共同創業者兼 CTO の Ami Luttwak 氏は「複数のエージェントがすべての PR を
走査・更新する世界では、人間と AI の間の明確な帰属の確立自体が難しくなっている。
PR の共著者を見るだけでは足りない」と述べている（原文英語）。また、GitHub Advanced
Security が最終リビジョンをスキャンして脆弱なワークフローを抽出していたにも
かかわらず、インジェクションを検出できなかったことも判明している。「AI が書いたか」
は不明でも、「AI のレビューと自動スキャンの双方が見逃した」ことは確定している。

Wizのred agentは細工したIssueタイトルでJira認証情報を帯域外コールバックで窃取した発覚の端緒出典 [1] [2]

Wiz の red agent は、公開リポジトリの定期スキャンで jira_issue.yml を「信頼されない
ユーザー入力によるスクリプトインジェクション」として検出した。悪用は、Issue のタイトルに
ペイロードを埋め込み、テンプレート展開後に echo 文字列を抜け出して、Jira の認証情報
（API トークン・ユーザーメール・ベース URL）を base64 エンコードして外部リスナー
（帯域外コールバック）へ送信するものだった。

Wiz によれば、red agent は最初のペイロードがコメント文字で失敗した後、bash の構文エラーを
自ら分析して修正版を試し、成功させたという。攻撃の試行錯誤自体が自律的に行われた点は、
自律型攻撃AIの実用段階を示している。

窃取されたトークンは qa@snowflake.net で認証され、snowflakecomputing.atlassian.net の
Jira にアクセスでき、エンジニアリング・セキュリティコンプライアンス・バグバウンティ管理の
各プロジェクトへの読み取りアクセスが可能だった。

Snowflakeの初動は「同日修正・翌日ローテーション・監査ログでの影響確定・透明な開示」で完結した組織の対応出典 [1] [2]

Snowflake の対応は短時間で完結した。Wiz の報告（2026年6月23日）と同日にワークフローを
修正し（PR #1402・コミット 1dc7766）、翌6月24日に Jira トークンを失効・ローテーションした。
さらに監査ログを精査し、混入から修正までの露出5日間に、異常なアクセスはすべて Wiz の
テスト IP に一致し、Wiz 以外の第三者のアクセスがなかったことを確認した。

Snowflake は The Register に対し「直ちに調査・是正し、不正アクセスの証拠は見つからなかった。
Wiz と協力してこの学びを業界に共有し、セキュリティのベストプラクティスの普及を促す」と
コメントした。Wiz も調査と PoC 検証で参照したデータをすべて削除したとしている。

「修正・失効・ログでの影響範囲確定・透明な開示」という初動の型が短時間で完結しており、
CI/CD シークレット漏えい時の対応手順のベンチマークとして参照できる。ただしこれは
正規の開示プログラム経由の許可された調査であり、攻撃者が同じ脆弱性を先に見つけていれば、
同型の窃取が悪意をもって行われ得た点は変わらない。

AIによる脆弱性の混入と発見が同一の時間軸で起きる時代には、AI提案のレビューと短寿命シークレットが前提になる評価・解釈出典 [1] [2]

本記録の作成者の整理として、この事案の先例性は3点にある。

第一に、「AIが脆弱性を作り、AIが見つける」というサイクルが、実企業のコードで5日という
短い時間軸で完結して観測された。Copilot Autofix の混入（6月18日）から red agent の発見
（6月23日）まで5日であり、攻撃側のAIが公開リポジトリを定期スキャンする以上、混入から
悪用可能な状態が発見されるまでの猶予は従来より短い。

第二に、AIレビュー・自動スキャンの通過が安全の保証にならないことが実証された。
本件では、安全なパターンを不安全な直接展開に置き換える変更を、共著者の Copilot が
「問題なし」と判定し、GitHub Advanced Security のスキャンも検出しなかった
（変更を書いた主体が人間か Copilot かは不明と Wiz が明確化している）。さらに Wiz の
CTO が指摘するとおり、複数のエージェントが PR を走査・更新する開発では、そもそも
人間と AI の帰属の確立自体が難しくなっている。AIの関与したコードは「支援＝安全」
ではなく、人間のコードと同じ静的解析・セキュリティレビューを要する。

第三に、Snowflake の対応の型（同日修正・翌日ローテーション・監査ログでの影響確定・透明な
開示）が、CI/CD シークレット漏えい時のベンチマークになる。とくに「監査ログで露出期間の
第三者アクセスの有無を言い切れる」状態は、事前のログ保全があって初めて可能になる。

以上は本記録の作成者の評価を含み、Snowflake・Wiz の公表そのものではない。日本の組織にも、
AI支援開発の普及とともに同型のリスクは直接当てはまる。

CISO・経営層への示唆
  • AIの関与したコード変更は「AIレビュー通過」を安全の根拠にできない——人間コードと同じ審査ラインに乗せる
    本件のコミットでは、既存のサニタイズ済みパターンが不安全な直接シェル展開に 置き換わり、共著者の Copilot はレビューで「問題なし」と判定し、GitHub Advanced Security のスキャンも検出しなかった（Copilot 自身が書いたかは不明と Wiz が明確化）。 AIエージェントは「なぜ元のコードが安全処理をしていたか」の文脈を欠くため、 善意の変更が脆弱性を作り込み、AIレビューがそれを通過させうる。
    取るべき行動 AI提案の PR・コミットに、人間の変更と同等（またはそれ以上）の静的解析とセキュリティ レビューを必須化するポリシーを定める。とくにワークフロー・IaC・認証まわりの AI 変更は 自動マージの対象から外す。
  • 攻撃側AIが公開リポジトリを常時スキャンする前提で、修正サイクルと露出窓を測る
    混入（6月18日）から Wiz red agent の発見（6月23日）まで5日。自律型攻撃AIが公開資産を 定期スキャンする以上、脆弱な状態が発見・悪用されるまでの猶予は従来より短い。
    取るべき行動 公開リポジトリ・公開資産の変更に対する自組織側の脆弱性検出も自動化・常時化し、 「攻撃側AIより先に自分で見つける」体制にする。修正・トークンローテーションまでの 目標時間を短く設定する。
  • 「侵害されていない」と言い切るには、露出期間の第三者アクセスを監査ログで確認できる状態が要る
    Snowflake は監査ログで、露出5日間の異常アクセスがすべて Wiz のテスト IP に一致し、 第三者アクセスがなかったことを確認して公表できた。この否定形の断言は、事前のログ保全が あって初めて成立する。
    取るべき行動 CI/CD・連携基盤（Jira 等）のアクセス監査ログの保全と保持期間を事前に定義し、 インシデント時に「露出期間中に誰がアクセスしたか」を短時間で言い切れる状態にする。
セキュリティ技術者への示唆
  • 信頼されない入力をrun:に直接展開しない——テンプレート展開はシェル評価より先に起きる
    脆弱パターンは `github.event.issue.title` を run: のシェル行に直接展開しており、 GitHub のテンプレート展開が sed のエスケープより先に行われるため、シングルクォート1つで コマンド注入が成立した。Issue 作成は任意ユーザーが行える。
    取るべき行動 Issue/PR のタイトル・本文などの信頼されない入力は、必ず env: で環境変数に渡し、 `"$VAR"` としてクォートするかパーサー（jq --arg 等）で処理する。run: への `${{ ... }}` 直接展開を禁止する lint ルールを CI に入れる。
  • 信頼されないトリガーのワークフローは権限最小化する——issues/pull_request_targetは要注意
    本件は `issues: opened` トリガーで任意ユーザーが実行を起こせた。信頼されないトリガーの ワークフローがシークレット（Jira トークン）にアクセスできたことが窃取につながった。
    取るべき行動 外部トリガー（issues・pull_request_target 等）のワークフローに付与するトークン・ シークレットをジョブ単位で最小化・短寿命化し、機微な連携先トークンは信頼されない トリガーのジョブからアクセスできないよう分離する。
  • CI/CDランナーのエグレスは、シークレット窃取の最後の共通検知点である
    窃取は base64 化した認証情報を帯域外コールバック（外部リスナーへの HTTP）で送出する 段を必ず持つ。本件は正規調査だが、悪意ある攻撃者なら同じ経路で送出できた。
    取るべき行動 CI/CD ランナーからの外向き通信を依存取得先の許可リストに限定し、未知宛先への送信を 検知・遮断する。エグレスログを保全し、事後に「何が送られたか」を遡れるようにする。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ GitHub Copilot Autofix 等のAIコーディング支援が生成・変更する PR を、人間コードと同等の審査なしにマージしている本件は AI の「修正」がサニタイズを外して脆弱性を作り込んだ。AI提案を「支援＝安全」と みなす運用だと、善意の変更が脆弱性の混入経路になる。
システム構成□ GitHub Actions 等の CI/CD で、Issue/PR タイトルなど信頼されない入力を run: のシェル行に展開するワークフローがあるテンプレート展開がシェル評価より先に起きるため、直接展開はスクリプトインジェクションに 直結する。任意ユーザーがトリガーできれば認証不要でコマンド実行が可能になる。
認証・認可□ 信頼されないトリガーのワークフローが、連携先（Jira 等）のトークンなど機微なシークレットにアクセスできる本件では Issue トリガーのワークフローが Jira トークンにアクセスでき、それが窃取された。 シークレットのスコープと寿命が二次被害の範囲を決める。
運用・監視□ CI/CD ランナーからの外向き通信を統制しておらず、エグレスの許可リスト・監視がないシークレットの送出はランナーからの外向き通信として現れる。エグレス統制がなければ、 コマンド実行後に窃取を止める機会がない。
運用・監視□ CI/CD・連携基盤のアクセス監査ログの保全・保持期間が定義されておらず、「露出期間中に誰がアクセスしたか」を短時間で言い切れないSnowflake は監査ログで第三者アクセスの不在を確認して公表できた。ログがなければ 「侵害されていない」と断言できず、公表時の不確実性が残る。
