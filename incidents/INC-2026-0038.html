INC-2026-0038Rustクレートarrayrefが乗っ取りで汚染

Rustの人気クレートarrayref（累計2.45億DL）がメンテナのアカウント乗っ取りで汚染——偽装依存proc-macro1のbuild.rsがcargo build時に3OS対応の窃取型を実行、旧版をyankして汚染版だけを「最新」に見せる、86〜107分で削除

脅威・攻撃キャンペーン委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備委託先・供給元起因
初報: 2026年8月20日 最終更新: 2026年8月21日

2026年8月20日、Rust のパッケージレジストリ crates.io で、メンテナ David Roundy 氏の
アカウントが乗っ取られ、同氏が保有する人気クレート arrayref（0.3.10）・internment
（0.8.7）・append-only-vec（0.1.9）の悪意ある版が公開されました。3つの版はいずれも、
正規の proc-macro2 を模した偽装依存 proc-macro1 を新たに取り込んでおり、proc-macro1 の
中身は本物の proc-macro2 のコピーでビルドは通常どおり通る一方、Cargo がコンパイル時に
自動実行する build.rs に窃取型マルウェアが仕込まれていました。cargo build／check／test の
いずれでも OS とアーキテクチャを判別して Windows・Linux・macOS 用のペイロードを取得・実行し、
ブラウザ（Chrome・Brave・Edge）のデータに触れて C2（23.254.165[.]112）へ通信し、
Registry Run（Windows）・LaunchAgent（macOS）・systemd ユーザサービス（Linux）で永続化
します。攻撃者は同時に arrayref 0.3.5〜0.3.9 を yank し、汚染版 0.3.10 だけが yank されて
いない「最新」に見える状態を作りました。arrayref は累計2億4,538万ダウンロード・直近90日で
約5,390万ダウンロードされ、暗号・GUI・ブロックチェーン系を含む数百のクレートが依存する
ため、汚染版が「最新」だった約86〜107分の間にビルドした CI・開発環境は感染しえます。
Rust Security Response Team は公開から86〜107分で悪意ある版を削除し、悪意ある yank で
隠された正規版を復元、アカウントを予防的にロックしました。安全なのは arrayref 0.3.9 以前です。
RustSec は本記録の作成時点で実被害の証拠は確認していないとする一方、Wiz はこのキャンペーンの
基盤が北朝鮮系とされる Mastra・Axios 攻撃と重なると指摘しています（帰属は未確定）。ここでは、
Rust 公式ブログ・RustSec 勧告・研究各社（Wiz・StepSecurity・Nextron ほか）の公表から
確認できた範囲を、観測事実と本記録の評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者はメンテナ David Roundy 氏の crates.io アカウントを乗っ取り、arrayref 0.3.10・ internment 0.8.7・append-only-vec 0.1.9 に偽装依存 proc-macro1 を加えて公開した。proc-macro1 は 正規の proc-macro2 のコピーでビルドは通るが、Cargo が実行する build.rs が OS 別の窃取型を 取得・実行し、ブラウザ資格情報等を C2（23.254.165[.]112 等）へ送って永続化する。攻撃者は 旧版を yank して汚染版だけを「最新」に見せた。Rust Security Response Team は86〜107分で削除し 正規版を復元、アカウントをロックした。

  1. 1. 初期侵入公表・報道に基づく[1] [6]
    攻撃者がメンテナ（David Roundy 氏）の crates.io アカウントを乗っ取り、正規クレートの 悪意ある版を公開できる状態を得た。Rust Security Response Team は端末または認証情報の 侵害の可能性が高いとしている。
    根拠: Rust 公式ブログ・StepSecurity の分析
  2. 2. 永続化公表・報道に基づく[6]
    攻撃者は事前に囮クレート（arone・aronenao、8月18日）となりすましアカウント dtolney・ 無害な proc-macro1 1.0.106（当日未明）を用意して公開履歴を作り、07:11:15 に proc-macro1 1.0.107 を武器化した。これにより正規クレートが取り込む「信頼できそうな依存」として 振る舞える基盤を確保した。
    根拠: StepSecurity の検証済み時系列
  3. 3. 検知回避公表・報道に基づく[1] [6] [3]
    proc-macro1 の中身を正規 proc-macro2 のコピーにしてビルドを通常どおり通し、arrayref 本体には 悪意あるコードを入れず依存マニフェストの変更だけにとどめた。さらに旧版 0.3.5〜0.3.9 を yank して汚染版だけを「最新」に見せた。Unix ではペイロードの子プロセスを切り離して Cargo のジョブ管理から逃し、Windows では wscript.exe 経由で画面を出さずに起動した。
    根拠: Rust 公式ブログ・StepSecurity・Xakep
  4. 4. 実行公表・報道に基づく[1] [6] [3]
    被害者が cargo build/check/test を実行すると、proc-macro1 の build.rs が OS・アーキテクチャを 判別して Windows・Linux・macOS 用のペイロードを取得・実行する。Unix は /tmp/rust-setup、 Windows は %TEMP%\rust-setup.ps1（+ rust-setup-launch.vbs）として落とされる。
    根拠: Rust 公式ブログ・StepSecurity・Xakep
  5. 5. 永続化公表・報道に基づく[6] [3]
    ペイロードは Windows で Registry Run、macOS で LaunchAgent、Linux でユーザ権限の systemd サービスとして永続化する。Linux の stage-2 は $HOME/.config/AzureKits・ $HOME/.config/ServiceKit に MonoService・MonoXpc を置く（StepSecurity）。
    根拠: StepSecurity・Xakep
  6. 6. 認証情報アクセス公表・報道に基づく[6] [8]
    ペイロードは Chrome・Brave・Edge のプロファイル DB に触れて保存済みログインや拡張機能の 設定を読む。Nextron が解析した Windows 版は origin_url と username_value の列のみを読み、 password_value は直接抽出しなかった。CI 上で発火した場合は CI トークン・署名鍵等が対象に なりうる。
    根拠: StepSecurity・Nextron（Xakep 経由）
  7. 7. C2通信公表・報道に基づく[6] [3]
    C2 へ HTTPS POST（パス /49890878）でビーコンし、ホスト名・ユーザ名・OS 情報を送る。 コマンドは kill・minicfg・startup・runscript。主 C2 に到達できない場合は5日ごとに 10ドメインを生成する DGA にフォールバックする。通信は AES-128-GCM（ハードコード鍵 "i am botking"）で暗号化される（StepSecurity）。
    根拠: StepSecurity・Xakep

メンテナのアカウント乗っ取りで3つの人気クレートが汚染され、偽装依存proc-macro1のbuild.rsがビルド時に発火した原因・手口出典 [1] [6] [3]

Rust 公式ブログ（2026年8月20日・security-response team）と StepSecurity ほかの分析に
よれば、攻撃者は arrayref・internment・append-only-vec を保有するメンテナ David Roundy 氏の
アカウントを乗っ取り、2026年8月20日に3クレートの悪意ある版（arrayref 0.3.10・internment
0.8.7・append-only-vec 0.1.9）を公開した。

3つの版はいずれも、新たな依存として proc-macro1 を取り込んでいた。proc-macro1 は正規の
proc-macro2 を模した名前で、中身は本物の proc-macro2 のソースコードのコピーだったため、
プロジェクトのビルドは通常どおり通る。悪意は、Cargo がコンパイル時に自動実行する build.rs に
仕込まれていた。つまり cargo build・cargo check・cargo test のいずれでもマルウェアが発火する。
arrayref の公開履歴10年で最初に追加された依存が、この proc-macro1 だった。

StepSecurity によれば、武器化された proc-macro1 1.0.107 はビルド専用の依存として base64・
rustls・ureq（いずれも通信・暗号化用途）を持ち、マニフェストの変更だけでダウンロード能力の
存在が読み取れた。攻撃者は事前準備として、8月18日に別の悪意ある囮クレート（arone・
aronenao）を公開し、当日未明には GitHub になりすましアカウント dtolney（proc-macro2 の
作者 David Tolnay 氏を模倣）と対応する crates.io アカウントを作り、無害な proc-macro1 1.0.106 を
武器化の約5時間前に公開して公開履歴を整えていた。乗っ取られたメンテナ（Roundy 氏）と
なりすまされた開発者（Tolnay 氏）は別人である。

旧版をyankして汚染版だけを「最新」に見せ、build.rsがOS別に窃取型を落として永続化した被害規模・影響範囲出典 [1] [6] [3] [8]

攻撃者は arrayref 0.3.10 を公開した直後（07:15:24〜07:15:40 UTC）、0.3.9 から 0.3.5 までを
約4秒間隔でスクリプト的に yank した。これにより、汚染版 0.3.10 だけが yank されていない
「最新」に見える状態が作られ、Cargo が新規解決で汚染版を選びやすくなった。

build.rs の不正コードは、被害者の OS とアーキテクチャを判別して Windows・Linux・macOS 用の
ペイロードを取得する。StepSecurity・Xakep によれば、Unix 系ではペイロードを /tmp/rust-setup
として保存して実行し（子プロセスを切り離して Cargo のジョブ管理から逃す）、Windows では
%TEMP%\rust-setup.ps1 を rust-setup-launch.vbs 経由の wscript.exe で画面を出さずに起動する。
永続化は Windows が Registry Run、macOS が LaunchAgent、Linux がユーザ権限で動く systemd
サービスによる。

StepSecurity の解析では、ペイロードは C2 へ HTTPS POST（パス /49890878）でビーコンし、
ホスト名・ユーザ名・OS 情報を送り、インストール済みアプリを列挙し、Chrome・Brave・Edge の
プロファイルから保存済みログインや拡張機能の設定を読む。ただし Nextron が解析した Windows 版は
ブラウザ DB の origin_url と username_value の列のみを読み、password_value（パスワード本体）は
直接抽出しなかった。コマンドは kill・minicfg・startup（永続化）・runscript（PowerShell/シェルの
実行）で、主 C2 に到達できない場合は5日ごとに10ドメインを生成する DGA にフォールバックする。

Rust Security Response Teamは86〜107分で削除し、悪意あるyankで隠された正規版を復元した組織の対応出典 [1] [2]

Rust Security Response Team は、報告（07:54 UTC）を受けて悪意ある版を削除した。削除までの
時間は proc-macro1 が約52分、arrayref が86分、internment が90分、append-only-vec が107分で
ある。同チームは、悪意ある yank によって隠された arrayref・internment・append-only-vec の
正規版を復元し、攻撃者所有の proc-macro1・proc-macro-en・aovine・arone・aronenao・tinymember
（全バージョン）を削除し、乗っ取られたアカウントを予防的にロックした。安全なのは arrayref
0.3.9 以前である。

RUSTSEC-2026-0260 によれば、汚染版 arrayref 0.3.10 は削除までに2,285回ダウンロードされた
（同クレートの通常のトラフィックの10%未満）。Rust Security Response Team は「悪意ある版が
実際に使われた証拠は今のところ見つかっていない」とし、著者が悪意を持って行動したとは
考えておらず端末または認証情報が侵害された可能性が高いとしている。

本記録の作成者の整理として、「削除が速かった」ことと「安全だった」ことは別である。build.rs は
ダウンロードではなくビルドで発火し、CI が汚染版を解決してビルドすれば秘密情報が抜かれうる。
さらに、いったん Cargo.lock に 0.3.10 が固定された環境や ~/.cargo/registry/cache に .crate が
残った環境は、削除後もローカルから汚染版でビルドしうる。RustSec の「実利用の証拠なし」は
「安全の確認」ではなく「今のところ確認されていない」という段階の記述である。

基盤は北朝鮮系とされるMastra・Axios攻撃と重なるが、本件の帰属は未確定帰属出典 [4] [8] [3]

Wiz は、本キャンペーンの基盤が、北朝鮮系とされる Mastra（npm）・Axios（npm）のサプライ
チェーン攻撃と重なると分析した。具体的には、C2 エンドポイント /49890878 のパターンが
Microsoft が Mastra 攻撃に帰属させたものと一致すること、arrayref の C2 IP と Mastra 基盤が
SSL 発行者（WIN-A6QF8AHPQH1）を共有すること、被害者が報告した通信先 23.254.167[.]216 が
Google の Axios（UNC1069）分析に登場すること、両キャンペーンが Hostwinds LLC の
23.254.164.0/23 レンジを使うことである。Microsoft は Mastra を「DPRK / Sapphire Sleet」、
Mandiant は Axios を UNC1069 経由で北朝鮮に結び付けている。

ただし Wiz・RustSec・Rust 公式ブログのいずれも、本件（arrayref）を特定のグループに
帰属させてはいない。Xakep も「専門家は今のところ本件を具体的なグループに結び付けて
いない」と報じている。本記録では、基盤の重なりを観測事実として記録し、帰属は未確定として
扱う。

なお、直前に npm でも同種の事案が続いている。本DBには、Shai-Hulud 亜種の npm ワーム
ChainDrop（INC-2026-0025）と、OSS スキャナ Trivy の侵害を起点とする TeamPCP／Shai-Hulud
（INC-2026-0024）が登録済みで、いずれも北朝鮮系との関連や自動実行・正規配布経路の悪用が
共通する。攻撃面が npm から crates.io（Rust）へ広がった点が本件の新しさである。

「ビルドで発火する」「旧版をyankして最新を偽装する」ことが、SBOMの版照合を無効化する評価・解釈出典 [1] [6] [4]

本記録の作成者の整理として、この事案の先例性は3点にある（いずれも公表事実に基づく
本記録の評価であり、各社の見解ではない）。

第一に、悪意がパッケージの公開 API ではなく build.rs にある点。arrayref 本体には1行の
悪意あるコードもなく、汚染版はマニフェスト（依存の記述）を変えただけだった。API を
呼ばなくても、依存の解決とビルドだけで発火する。SBOM で「どの版を使っているか」を
照合しても、依存の build.rs が何を実行するかは見えない。防御は、レジストリ側の挙動分析
（build 依存に通信クレートが増えていないか）か、ビルド環境の実行時検知に寄る。

第二に、旧版の yank による「最新」の偽装。攻撃者は 0.3.5〜0.3.9 を秒単位で yank し、汚染版
だけを yank されていない最新に見せた。「複数の安定版が突然 yank される」こと自体が調査の
合図になる。バージョン範囲指定（^0.3 等）で解決している環境は、この偽装で汚染版を掴みやすい。

第三に、削除の速さと安全の混同。汚染版は86〜107分で消えたが、その間にビルドした CI は
感染しえ、Cargo.lock 固定やローカルキャッシュ経由で削除後もビルドしうる。国内で Rust を
採用する組み込み・金融・Web3 の開発組織は、8月20日 07:15〜09:25（UTC）にビルドした環境の
Cargo.lock と ~/.cargo/registry/cache を確認し、該当すれば CI トークン・署名鍵・ブラウザ
資格情報を無条件に入れ替えるべきである。

CISO・経営層への示唆
  • 依存の悪意は「公開API」ではなく「ビルド時に走るコード」に入る——SBOMの版照合だけでは捕まらない
    arrayref 本体には1行の悪意あるコードもなく、汚染版は依存マニフェストを変えただけだった。 悪意は Cargo がコンパイル時に実行する build.rs（取り込んだ proc-macro1 内）にあり、 パッケージの API を呼ばなくてもビルドだけで発火する。「どの版を使っているか」を照合する SBOM では、依存の build.rs が何をするかは見えない。
    取るべき行動 ソフトウェア部品表（SBOM）に加えて、ビルドパイプラインの挙動（ビルド中の子プロセス生成・ 外向き通信）を監視対象にする。Rust に限らず、npm の install script・PyPI の setup.py など 「ビルド／インストール時に任意コードが走る」エコシステムを同じリスクとして扱う方針を定める。
  • 「削除が速かった」は「安全だった」ではない——ビルドで発火し、ロック・キャッシュ経由で削除後も残る
    汚染版は86〜107分で削除されたが、その間にビルドした CI は感染しえ、Cargo.lock に 0.3.10 が 固定された環境や ~/.cargo/registry/cache に .crate が残った環境は削除後もビルドしうる。 RustSec の「実利用の証拠なし」は安全の確認ではなく「今のところ確認されていない」段階の記述。
    取るべき行動 インシデント公表時に「該当時間帯にビルドした自組織の環境」を能動的に洗い出す手順を持つ。 レジストリからの削除を復旧完了とみなさず、ロックファイル・ローカルキャッシュの確認までを 対応の完了条件にする。
  • 攻撃面がnpmからRust（crates.io）へ広がった——単一言語の監視では足りない
    本DBには npm の ChainDrop（INC-2026-0025）・Trivy 起点の TeamPCP（INC-2026-0024）が登録済みで、 いずれも北朝鮮系との関連が指摘される。本件は同種の手口が Rust へ及んだもので、Wiz は基盤の 重なりを指摘する。攻撃者は「まだ監視が薄いレジストリ」を次々に狙う。
    取るべき行動 自組織が使う全パッケージエコシステム（npm・PyPI・crates.io・Composer 等）を棚卸しし、 依存監視・公開直後の取り込み猶予・build/install スクリプトの審査を横断的に適用する。 1つの言語だけを監視している状態を解消する。

    build.rs はダウンロードではなくビルドで発火し、ブラウザ資格情報・CI トークン・署名鍵に 到達しうる。汚染版が「最新」だった時間帯にビルドした環境は、削除後も痕跡が残る。
    取るべき行動 Cargo.lock を arrayref 0.3.10・internment 0.8.7・append-only-vec 0.1.9 で検索し、 ~/.cargo/registry/cache から該当 .crate を探す。ハッシュ（arrayref 25ad7009…）で照合する。 該当すれば /tmp/rust-setup・%TEMP%\rust-setup.ps1・自動起動項目（Run キー・LaunchAgent・ systemd user）・$HOME/.config/AzureKits を確認し、CI トークン・署名鍵・ブラウザ資格情報を 無条件にローテーションして環境を再構築する。安全版は arrayref 0.3.9 以前。
  • 「複数の安定版が秒単位で一斉にyankされる」ことは調査の合図——最新の偽装に使われる
    攻撃者は 0.3.5〜0.3.9 を約4秒間隔で yank し、汚染版 0.3.10 だけを yank されていない「最新」に 見せた。バージョン範囲指定（^0.3 等）で解決している環境は汚染版を掴みやすい。
    取るべき行動 依存の版履歴の監視で「複数安定版の一斉 yank」をアラート対象にする。CI は --locked で Cargo.lock を固定してビルドし、範囲指定による自動的な最新解決を避ける。版に最低公開日数の 猶予を設ける。
  • build-dependenciesに通信クレート（ureq・rustls・reqwest等）が増える差分を見る
    武器化された proc-macro1 はビルド専用依存として base64・rustls・ureq を持ち、マニフェストの 変更だけでダウンロード能力の存在が読み取れた。build.rs はネットワークもファイルも触れる。
    取るべき行動 依存更新のレビューで build-dependencies の差分、特に通信・ダウンロード・エンコード系 クレートの追加を重点的に確認する。ビルドを外向き通信を遮断した隔離環境で行い、build.rs が 外部へアクセスできないようにする。
  • ビルドは「任意コード実行」と同じ前提で隔離する——CI・開発端末を汚染境界にしない
    cargo build/check/test のいずれでも build.rs が発火し、Unix では子プロセスを切り離して Cargo のジョブ管理から逃げ、Windows では wscript 経由で画面を出さずに起動した。ビルド環境が そのまま資格情報の宝庫（ブラウザ・CI シークレット）だと被害が大きい。
    取るべき行動 ビルドを使い捨ての隔離環境（エフェメラルな CI ランナー・コンテナ・ネットワーク制限）で 行い、開発端末では個人のブラウザ資格情報と開発用シークレットを分離する。ビルド時の 子プロセス生成・外向き通信を実行時検知の対象にする。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ Rust（crates.io）を採用しており、arrayref・internment・append-only-vec のいずれかに直接または推移的に依存しているarrayref は数百のクレートが依存し Rust 環境の約4分の3に存在する。推移的依存でも Cargo.lock が 0.3.10 を解決していれば、8月20日の該当時間帯のビルドで発火しえた。
運用・監視□ CI・開発端末でのビルド時の挙動（子プロセス生成・外向き通信・自動起動項目の変更）を監視していない悪意は build.rs のビルド時実行にあり、SBOM の版照合では見えない。ビルド環境の実行時監視が なければ、発火を検知できない。
委託・第三者部品□ 依存を範囲指定（^0.3 等）で解決し、CI で Cargo.lock を固定（--locked）していない、または公開直後の版を取り込む猶予期間を設けていない攻撃者は旧版を yank して汚染版だけを「最新」に見せた。範囲指定で自動的に最新を解決する 構成は、この偽装で汚染版を掴む。
認証・認可□ パッケージ公開アカウント・CI シークレット・署名鍵の管理が、ビルド環境から到達可能な形になっている起点はメンテナのアカウント乗っ取りであり、被害側では build.rs が CI トークン・署名鍵・ ブラウザ資格情報に到達しうる。公開アカウントの多要素認証とシークレットの分離・短命化が 被害の上限を決める。
体制・契約□ 使用するパッケージエコシステムが複数（npm・PyPI・crates.io 等）あるのに、依存監視・スクリプト審査を一部の言語にしか適用していない同種の手口が npm から Rust へ広がっている。1つの言語だけを監視している状態では、次に狙われる エコシステムを取りこぼす。
