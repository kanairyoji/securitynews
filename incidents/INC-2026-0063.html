INC-2026-0063npm正規プロベナンス付きで悪性10版が公開

npmパッケージ「@7nohe/openapi-react-query-codegen」の公開ワークフローが第三者のコメント1行で起動し、悪性10版が正規のnpmプロベナンス証明つきで公開された——証明書は「どのワークフローが作ったか」しか示さず、そのワークフローが信頼できるソースだけを扱ったかは示さない

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている日本に波及した海外事案設計・実装上の不備権限管理の不備設定不備
初報: 2026年8月28日 最終更新: 2026年8月30日

2026年8月28日20時（UTC）ごろ、npmパッケージ「@7nohe/openapi-react-query-codegen」の
保守されている全リリース系統に対し、約20分間隔の2波で悪性の10版が公開されました。
週間ダウンロードは約15万で、当時 latest タグは悪性の 3.0.4 を指していました。
入口は同リポジトリの公開ワークフローで、プルリクエストに「npm publish」という
文字列のコメントが付いたら起動する条件になっており、コメントした人物がリポジトリと
どういう関係かは検査していませんでした。第三者のアカウントが fork から
プルリクエストを開いてこの一言をコメントするだけで、リポジトリの信頼済み ID で
fork の中身が公開できる状態でした。
本件の重い点は、10版すべてが GitHub Actions の trusted publishing による
有効な npm プロベナンス証明を持っていたことです。証明書の検証は成功し、
npm audit signatures は警告を出しません。プロベナンスは「どのワークフローが
成果物を作ったか」を証明しますが、「そのワークフローが信頼できるソースだけを
扱ったか」は証明しません。導入判断の根拠を署名の有無に置いていた組織は、
その前提を見直す必要があります。
パッケージの保守者は福岡在住の日本人開発者で、当日22時50分（UTC）に
問題のトリガを削除する修正を投入し、npm は23時11分ごろまでに悪性10版を削除しました。
本記録は、公表・分析から確認できた範囲を、観測事実と評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は公開リポジトリのリリース用ワークフロー定義を読み、プルリクエストへの 「npm publish」というコメントで起動し、かつコメント投稿者の権限を検査していないことを 把握した。fork からプルリクエストを開いてそのコメントを付けることで、リポジトリの 信頼済み ID を持つランナー上で fork のコードを実行させ、npm へ悪性10版を公開した。 起動契機の都合で証明書は「main ブランチの正常なコミット」を指したため、 プロベナンスの検証は成功する。利用側では binding.gyp と preinstall の2系統で発火し、 クラウド・レジストリ・CI のシークレットを収集して自己増殖する。

  1. 1. 偵察公表・報道に基づく[1] [2]
    公開リポジトリのワークフロー定義は誰でも読める。攻撃者はそこから 「プルリクエストへの特定文字列のコメントで公開が起動する」「投稿者の権限を 検査していない」「公開用の OIDC トークンを発行する権限がジョブに付いている」 という3点を把握できた。特別な認証情報も内部知識も要らない。
    根拠: Socket・SafeDep の分析（ワークフロー定義の引用）
  2. 2. 初期侵入公表・報道に基づく[1] [3]
    2026年8月28日19時59分（UTC）、p00paboot を名乗るアカウントが fork から プルリクエスト #215 を開き、15秒後に「npm publish」とコメントした。 ワークフローはコメント本文の一致だけを条件にしていたため起動し、 プルリクエストの HEAD（fork 側の中身）をチェックアウトした。
    根拠: Endor Labs の分析（プルリクエスト番号・アカウント名・時刻）
  3. 3. 実行公表・報道に基づく[1] [2]
    ワークフローが fork のコードで依存をインストールする過程で、攻撃者が 仕込んだ処理がランナー上で実行された。このジョブは npm への公開用に OIDC トークンを発行する権限を持っていたため、攻撃者はリポジトリの 信頼済み ID でパッケージを公開できる状態に到達した。
    根拠: Socket・SafeDep の分析
  4. 4. 検知回避公表・報道に基づく[1]
    公開された10版には有効な npm プロベナンス証明が付いた。起動契機の都合で 証明書が指す参照は既定ブランチの正常なコミットになり、検証は成功する。 さらに binding.gyp 側では、Unicode エスケープで平文の文字列を隠し、 「os」「node」といった検索されやすい語を残さないようにしていた。
    根拠: Socket の分析（証明書が指すコミットと Unicode エスケープの復号）
  5. 5. 認証情報アクセス公表・報道に基づく[1] [3]
    利用側の環境で発火したペイロードは、クラウド（AWS・Azure・Google Cloud）・ Vault・Kubernetes の認証情報、パッケージレジストリの認証情報、 GitHub Actions のシークレット、AI エージェントの設定ファイルを探索・収集した。 Endor Labs は Actions ランナーのメモリからの取得にも言及している。
    根拠: Socket・Endor Labs の分析
  6. 6. 横展開公表・報道に基づく[1] [3]
    収集したレジストリのトークンを使って別のパッケージを改変・公開する 自己増殖機能を持つ。Endor Labs は npm に加えて RubyGems と PyPI への 増殖経路を挙げている。本件の感染から実際に別パッケージが汚染された事例が 確認されたかは公表されていない。
    根拠: Socket・Endor Labs の分析
  7. 7. 持ち出し公表・報道に基づく[1]
    収集した情報は攻撃者側へ送出される。Socket は、攻撃者が作成した公開の GitHub リポジトリを経由して暗号化した収集物を持ち出す経路を挙げている。
    根拠: Socket の分析

2026年8月28日19時59分（UTC）、p00paboot を名乗る GitHub アカウントが

このリポジトリのリリース用ワークフローは、プルリクエストに付いたコメントの
本文がちょうど「npm publish」だったときに起動する条件になっていた。起動すると
プルリクエストの HEAD（fork 側の中身）をチェックアウトし、依存をインストールして
npm へ公開する。コメントした人物がリポジトリの共同保守者なのか、通りすがりの
第三者なのかは検査していなかった。GitHub が提供する判定材料
（コメント投稿者とリポジトリの関係を示す値）は参照されていない。

結果として、20時00分から20時02分にかけて第1波の4版（0.5.4 / 1.6.3 / 2.2.1 /
3.0.3）が公開された。20時18分に外部の研究者 Charlie Eriksen 氏が issue #217 で
これを報告したが、その1分後の20時19分から20時21分にかけて、より確実に発火する
仕掛けを足した第2波の4版（0.5.5 / 1.6.4 / 2.2.2 / 3.0.4）が公開された。
当時 latest タグは悪性の 3.0.4 を指しており、npm install をそのまま実行すると
汚染された版が降ってくる状態だった。

悪性10版はすべて有効なプロベナンス証明を持ち、しかも証明書は「正常なコミット」を指していた原因・手口出典 [1] [2]

本件で最も重い事実は、10版すべてが GitHub Actions の trusted publishing による
有効な npm プロベナンス証明を持っていたことである。証明書の検証は成功し、
npm audit signatures はこれらの版を危険とは判定しない。

Socket によれば、証明書が指し示すビルド元は、正常版 3.0.2 のコミット（d42d1733）が
置かれた main ブランチだった。プルリクエストのコメントを契機に起動した場合、
GitHub が渡す参照はリポジトリの既定ブランチになるためである。つまり
「main ブランチの正常なコミットからビルドされた」という記録が付いた成果物の中身が、
fork にあった攻撃者のコードだった。

ここから導かれる結論は単純である。プロベナンスは「どのワークフローが成果物を
作ったか」を証明する仕組みであって、「そのワークフローが信頼できるソースだけを
扱ったか」は証明しない。署名や証明書の有無を導入判断の根拠にしていた組織は、
それが何を保証していて何を保証していないのかを確認し直す必要がある。

なお、このリポジトリには fork のコードを特権付きで動かすことで知られる
pull_request_target 型のワークフローは存在しなかった。危険な構成は
その1種類だけではない、ということでもある。

実行の引き金は2系統あり、片方はインストール時スクリプトを止める設定では防げない原因・手口出典 [1] [2] [3]

第1波の4版は binding.gyp だけで発火した。これはネイティブモジュールを
ビルドするための設定ファイルで、インストールの過程で node-gyp が読み込む。
本件の binding.gyp は、Unicode エスケープで文字列を隠した Python の式を
条件に埋め込み、そこから OS のコマンド実行に到達して同梱の JavaScript を
起動する作りになっていた。平文で「os.system」や「node」と書かれていないため、
文字列の検索では見つからない。

第2波の4版は、同じ binding.gyp に加えて preinstall スクリプトを持つ。
こちらは依存のインストール前に確実に走る。攻撃者は報告を受けた後に、
より確実な引き金を足しにきたことになる。

重要なのは、インストール時スクリプトの実行を止める設定（ignore-scripts 相当）を
入れていても、binding.gyp 経由の発火は残りうるという点である。
「スクリプトを止めているから安全」という前提は、この事案では成立しない。

同梱されていたローダーは約5.7MB の単一ファイルで、XOR による難読化の下に
暗号化された第2段が入っていた。第2段はクラウド（AWS・Azure・Google Cloud）・
Vault・Kubernetes の認証情報、パッケージレジストリの認証情報、
GitHub Actions のシークレット、AI エージェントの設定ファイルを探して収集し、
盗んだレジストリのトークンで別のパッケージへ広がる機能を持つ。
Endor Labs は増殖先として npm に加えて RubyGems と PyPI を挙げている。

気づいたのは外部の研究者で、止まるまで約3時間かかった組織の対応出典 [2] [4] [6]

第1波の公開から18分後の20時18分、外部の研究者が issue #217 で悪性版の公開を
報告した。保守者側の監視や npm の自動検知ではなく、外部からの指摘が最初の
検知になっている。個人が保守する OSS で夜間に起きた事象としては、
これは決して遅い部類ではない。

一方、実際に止まるまでには時間がかかった。保守者がコメント起動のトリガを
削除する修正を投入したのは22時50分、npm が悪性10版を削除したのは23時11分ごろで、
第1波の公開から約3時間11分が経っている。この間、latest タグは悪性版を
指し続けていた。

修正の内容は、問題のトリガを削除し、あわせてチェックアウト時に認証情報を
ランナー上に残さない設定を加えるというものだった。本記録の作成者が
2026年8月30日に現行の定義を確認したところ、リリース用ワークフローの起動条件は
バージョンタグの push のみになっており、コメントによる起動経路は残っていなかった。
npm レジストリ側でも悪性10版は削除済みで、latest は正常版の 3.0.2 を指している。

当事者からの説明は修正コミットだけで、利用者は「自分が踏んだか」を第三者の記事から判断するしかない未確定事項出典 [4] [5] [6]

本記録の作成者が2026年8月30日に確認した範囲では、リポジトリの README・
pinned issue・GitHub Security Advisory のいずれにも本件の説明は無かった。
当事者の資料として確認できたのは、コメント起動トリガを削除する修正コミット
（2026年8月28日）だけである。攻撃者が開いたプルリクエスト #215 のページは
参照できなくなっていた（HTTP 404）。

個人が無償で保守する OSS に、企業と同じ体裁のインシデント報告を求めるのは
現実的ではない。ただし利用側から見ると、事実として次の状態にある——
「どの版が危険か」「何をすべきか」を知る手段が、Socket・SafeDep・Endor Labs
といった第三者ベンダーの記事しかない。悪性版が消えた今、レジストリの
バージョン一覧を見ても異常は分からず、ロックファイルに悪性版のバージョン番号が
残っていても、それが危険だったと気づく手掛かりが公式には存在しない。

露出期間に取得した組織の数も、実際に窃取された認証情報の範囲も公表されていない。
利用側は「通知が来ないから無関係」と判断できる材料を持たない。

これは「日本の開発者が保守する OSS」が踏み台になった事案でもある評価・解釈出典 [1] [3] [4]

当該パッケージの保守者は、GitHub のプロフィールに福岡在住と表示している
個人開発者である（所属として福岡の企業を掲げているが、パッケージが同社のもので
あるという表示は無い）。日本の組織の被害は公表されておらず、本記録も
日本国内の被害を確認していない。

それでも、この事案は日本の読者にとって二重の意味を持つ。
利用側としては、日本の開発現場で使われている可能性のあるツールが
約3時間だけ汚染されていたという事実がある。開発側としては、
自社・自分が公開している OSS の公開ワークフローが同じ形をしていないか、
という問いが直接向けられている。

本記録の評価としては、後者のほうが射程が長い。コメントや外部トリガで
パッケージを公開する仕組みは、少人数の保守体制で「レビュー後にワンライナーで
リリースしたい」という実用的な要求から生まれる。その利便性が、権限の検査を
1つ落としただけで、リポジトリの信頼済み ID を第三者に貸し出す穴になる。
自組織が npm・PyPI・RubyGems・Maven などにパッケージを公開しているなら、
「誰がその公開を起動できるか」を今日確認する価値がある。

数え方: 悪性版をインストールした端末・CI ランナーを隔離し、既知の正常なイメージから作り直したうえで、到達し得た認証情報（npm・GitHub のトークン、クラウドの鍵、CI のシークレット）を失効・再発行する　副作用: 環境の再構築と全面的な鍵のローテーションは連携先の停止リスクと作業負荷が大きい。 順序を誤って鍵の交換を先にすると、持続化物が残った環境で新しい鍵が再び盗まれる　数値の出所: Socket の推奨

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
コメント1行がリポジトリの信頼済み ID を第三者に貸し出し、正規の証明書つきで悪性版が配られた経路

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察現実的な検知機会なし
公開情報を読む行為に検知機会は無い。防げるとすればワークフロー定義の側で、 コード審査や自動チェックによって危険な構成を出荷前に見つけるしかない。
侵入を防げた公開ワークフローの構成監査（外部トリガ・権限検査の欠落・特権トークンの有無を機械的に検査する）
初期侵入機会はあったが検知できず
見知らぬアカウントによるプルリクエストとコメントは GitHub の通知に現れる。 ただし深夜の15秒という間隔では、人による監視は現実的に間に合わない。 機械側で「投稿者の権限を検査する」以外に止める手段は無かったと評価できる （本記録の判断）。
侵入を防げた公開ジョブの実行前にコメント投稿者とリポジトリの関係を検査する（共同保守者以外では起動しない）
侵入を防げた公開は外部から起動できない契機（タグの push・保護されたブランチ）に限定する
実行機会はあったが検知できず
ワークフローの実行記録は残るが、平時から見ている運用でなければ 気づけない。個人保守の OSS ではランナーの挙動監視は現実的でない。
侵入を防げた公開権限を持つジョブでは fork のコードをチェックアウトしない（信頼できる参照のみをビルド対象にする）
影響を限定できたチェックアウト時に認証情報をランナーへ残さない設定（保守者が事後に追加した対策）
検知回避機会はあったが検知できず
署名検証だけを見ている限り検知できない。一方、公開されたパッケージの中身に 数MBの単一ファイルが増える・binding.gyp が追加されるといった変化は、 版間の差分を比較すれば見える。差分監視は数少ない有効な検知点である。
検知できた導入判断を署名・証明書の有無で終わらせず、版間の内容差分（新規ファイル・インストール時フックの追加）を確認する
検知できた自組織が公開するパッケージの新規リリースを即時に通知させる（意図しない公開の検知）
認証情報アクセス公表されていない
個々の利用組織で収集を検知できたかは公表されていない。ビルドジョブが 本来触らないシークレットや環境変数を列挙する挙動は、CI 環境の監視で 異常として拾える余地がある。
影響を限定できたCI のシークレットをジョブ単位の最小権限・短命トークンにする
影響を限定できた開発者端末とビルド環境を分け、個人の資格情報をビルド環境に置かない
横展開公表されていない
各レジストリ側での検知状況は公表されていない。
侵入を防げたパッケージ公開権限を多要素認証と信頼された公開経路に限定し、公開の起動元を絞る
持ち出し公表されていない
正規のサービス（GitHub）への通信に紛れるため、宛先ドメインだけを見る 統制では区別が付きにくい。
検知できたビルド環境からの外向き通信を依存取得先の許可リストに限定し、記録を保全する

判断評価評価の根拠と留保
保守者はワークフローの修正を投入したが、README の告知・pinned issue・ GitHub Security Advisory のいずれの形でも、利用者向けの説明を出していない （本記録の作成者が2026年8月30日に確認した範囲）部分的に機能本記録の作成者の評価である。個人が無償で保守する OSS に企業と同じ体裁の インシデント報告を求めるのは筋が違う。ただし「危険な版の一覧」と 「取得していた場合にすべきこと」の2点は、GitHub Security Advisory を 1本立てれば足りる分量であり、生態系全体の損失を考えると出す価値は大きい。
利用者に対しては、Socket が「影響を受けた版をインストールした端末・ランナーを ネットワークから隔離し、環境を作り直したうえで、到達し得たすべての認証情報を 失効・再発行する」よう推奨している。これは当事者ではなく第三者ベンダーの助言である評価材料なし推奨に従った組織がどれだけあったか、実際に窃取された鍵がどう使われたかは 公表されておらず、効果を評価する材料が無い。
CISO・経営層への示唆
  • 「署名されているから安全」は成立しない——プロベナンスは出所を示すだけで、中身の安全は示さない
    悪性10版はすべて有効な npm プロベナンス証明を持ち、証明書は正常な main ブランチのコミットを指していた。署名検証を通す運用は、この10版を 素通しする。
    取るべき行動 ソフトウェア調達・依存導入の基準に「署名・プロベナンスの検証」を入れている場合、 それが何を保証していて何を保証していないかを1枚にまとめ、基準を書き直す。 署名の検証は「出所の確認」であって「安全性の確認」ではないと明記する。
  • 露出が3時間でも、事後対応は「環境の作り直し＋鍵の総入れ替え」になる——時間の短さは作業量を減らさない
    悪性版は約3時間だけ配布されたが、その間に取得した環境では クラウド・レジストリ・CI のシークレットが収集され得る。持続化物を残したまま 鍵だけを替えると、新しい鍵がその場で盗まれる。
    取るべき行動 供給網事案の対応手順を「①該当環境の隔離 ②既知の正常なイメージからの再構築 ③到達し得た認証情報の失効・再発行」の順序で定義し、順序を守ることを 完了条件に含める。鍵の交換だけで終える運用になっていないか確認する。
  • 自組織が OSS を「公開する側」なら、公開を起動できる人の範囲が加害範囲になる
    本件で狙われたのは利用者ではなく公開の仕組みそのものである。 コメント1行で第三者がリポジトリの信頼済み ID を使えた。同じ構成の ワークフローは、少人数保守の利便性を求めた結果として広く存在しうる。
    取るべき行動 自組織が npm・PyPI・RubyGems・Maven 等にパッケージを公開しているなら、 公開ジョブの起動契機と権限を棚卸しし、「外部の第三者が起動できるか」を yes / no で答えられる状態にする。公開権限を持つジョブの一覧を 資産管理の対象に加える。
  • 当事者が個人の OSS 保守者である事案では、利用者向けの説明は期待できない——調べる役割を自組織側に置く
    保守者は2時間半で穴を塞いだが、利用者向けの告知は確認できていない。 悪性版が削除された今、レジストリを見ても異常は分からず、 情報源は第三者ベンダーの記事だけである。
    取るべき行動 供給網事案の影響確認を「供給元からの通知待ち」にせず、 依存パッケージに関する第三者ベンダーの公表を能動的に確認する役割を CSIRT または開発基盤チームに割り当てる。ロックファイルを版番号で 検索できる状態（記録の保全）を平時から用意しておく。
セキュリティ技術者への示唆
  • インストール時スクリプトを止めていても binding.gyp 経由では発火する——「フックを無効化したから安全」は本件では偽
    第1波の4版は preinstall を持たず、binding.gyp だけで発火した。 これはネイティブビルドの経路で処理されるため、インストール時スクリプトの 実行を抑止する設定では止まらない。第2波でようやく preinstall が足された。
    取るべき行動 依存の取得時に走りうる経路を列挙し直す（インストール時スクリプト・ binding.gyp によるネイティブビルド・Python の起動時フック等）。 ネイティブビルドを必要としない依存では、ビルドを行わない設定を検討する。
  • 公開権限を持つジョブで fork のコードをチェックアウトしてはいけない
    本件のワークフローは、コメントを合図にプルリクエストの HEAD（fork 側）を チェックアウトし、公開用の OIDC トークンを発行する権限を持ったまま 依存のインストールを実行した。攻撃者のコードが特権付きで走る構図である。
    取るべき行動 自社リポジトリのワークフローを、①外部から起動できる契機を持つか ②その契機で fork のコードをチェックアウトするか ③そのジョブが 書き込み権限や公開用トークンを持つか、の3点で洗い出す。 3つが揃うジョブは即座に起動契機を変えるか、投稿者の権限検査を入れる。
  • 版間の差分を見る——署名を見るより、新しいファイルが増えたかを見るほうが効く
    悪性版には数MBの単一 JavaScript ファイルと binding.gyp が新たに同梱されていた。 署名検証は通るが、直前の正常版との差分では明らかに異常である。
    取るべき行動 依存の更新時に、直前の版との差分（新規ファイル・インストール時フックの追加・ 極端に大きい単一ファイル）を確認する仕組みを導入する。難しければ、 新規リリースを一定期間置いてから取り込む待機期間を設ける。
  • 悪性版が消えた後に残る唯一の手掛かりはロックファイルとビルドログである
    悪性10版は公開から約3時間で npm から削除された。レジストリのバージョン一覧を 見ても、その版が存在したことすら分からない。
    取るべき行動 ロックファイル・SBOM・CI のビルドログを、供給網事案の調査に耐える期間 （最低でも数か月）保全する。ロックファイルを版番号で全文検索できる状態にし、 推移的な依存も含めて確認できるようにしておく。
  • ビルド環境からの外向き通信が、この種の攻撃で残された共通の検知点である
    取得・実行時に発火する汚染パッケージは、収集した情報を外へ送る段階を必ず持つ。 本件では攻撃者が作成した公開リポジトリを経由する経路が挙げられており、 正規サービス宛の通信に紛れる。
    取るべき行動 ビルド・CI 環境からの外向き通信を依存取得先の許可リストに限定し、 通信記録を保全する。GitHub のような正規サービス宛でも、 ビルドジョブが普段行わない書き込み操作を区別できるかを確認する。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ @7nohe/openapi-react-query-codegen をフロントエンド開発で利用している（推移的な依存も含む）2026年8月28日20時00分〜23時11分ごろ（UTC）に取得・インストールした環境は、 クラウド・レジストリ・CI のシークレットが収集された可能性がある。 悪性版は削除済みのため、確認はロックファイル・SBOM・ビルドログでしかできない。
委託・第三者部品□ 依存の導入可否を署名・プロベナンス証明の有無で判断する運用になっている本件の悪性10版はすべて有効な証明を持ち、検証は成功する。 証明の有無を関門にしている限り、この種の攻撃は素通りする。
運用・監視□ 自組織が OSS パッケージを公開しており、公開ジョブが外部から起動できる契機（コメント・fork からのプルリクエスト等）を持つ本件の入口はまさにこの構成である。起動契機と投稿者の権限検査が1つ欠けるだけで、 リポジトリの信頼済み ID を第三者に貸し出すことになる。
認証・認可□ CI のシークレットが長命・広権限で、ジョブ単位の限定や短命トークン化がされていない収集対象はまさに CI のシークレットである。盗まれた鍵の寿命と権限が、 二次被害の上限を決める。とくにパッケージ公開用のトークンは自己増殖の燃料になる。
運用・監視□ 依存の取得時にインストール時スクリプトを無効化していることを「対策済み」と扱っている第1波の4版は binding.gyp だけで発火しており、インストール時スクリプトの 抑止では止まらない。対策の有効範囲を実際の発火経路と照らして再確認する必要がある。
体制・契約□ 依存 OSS の事故情報を、供給元からの通知に依存して受け取る建て付けになっている本件では当事者からの利用者向け告知が確認できず、情報源は第三者ベンダーの 記事だけである。通知を待つ運用では、事案の存在自体を知らないまま終わる。
