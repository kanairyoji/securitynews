INC-2026-006629CM の注文照会 API から15万件流出

韓国のファッションEC「29CM」で注文情報を照会する連携APIへの外部からの異常アクセスにより15万9,852件の顧客情報が流出——同社は経路を即日遮断してKISAへ自主申告し、2日後に公表と本人別の項目通知、30日間の自己照会窓口まで用意した

不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年8月29日 最終更新: 2026年8月30日

韓国のファッション・ライフスタイル系オンラインセレクトショップ「29CM」
（ファッションプラットフォーム大手 MUSINSA の系列）は、2026年8月27日に
注文情報を照会する連携機能（API）へ外部から異常なアクセスが発生し、
一部顧客の個人情報が流出した事実を確認したと公表しました。
流出は合計15万9,852件で、内訳は氏名のみが13万8,841、氏名・メールアドレス・
携帯電話番号・配送情報までが2万1,011です。決済情報・ID・パスワードは
流出項目に含まれないとしています。
同社は異常アクセスの確認直後に当該経路を遮断し、韓国インターネット振興院（KISA）へ
自主申告したうえで、8月29日に自社サイトで公表しました。対象顧客には流出した項目を
個別に案内し、サイト上には本人認証を経て自分の流出内訳を確認できるボタンを
公表日から30日間設けています。あわせて「注文内容に言及して決済・返金・配送の
エラーを案内する SMS・電話・メールに特に注意してほしい」「29CM は SMS や
メールでパスワードや認証番号の入力を求めることはない」と、二次被害の型を
具体的に挙げて注意を促しました。
日本の EC 事業者にとっての読みどころは、流出量そのものよりも
「認証を経た利用者向けの照会 API が、外部からの異常なアクセスで
他人の情報を返しうる」という構図と、確認から公表までを2日で回した
対応の段取りにあります。本記録は、同社と報道が公表した事実と、
本記録の作成者による評価を分けて整理します。

壊れたのは「注文情報を照会する連携機能」——顧客が自分の注文を見るための経路から、他人の情報が15万9,852件出た概観出典 [1] [2] [3]

29CM が公表したのは次の範囲である。2026年8月27日、注文情報を照会する
連携機能（API）に外部から異常なアクセスが発生し、一部顧客の個人情報が
流出した事実を確認した。流出は合計15万9,852件で、氏名のみが13万8,841、
氏名・メールアドレス・携帯電話番号・配送情報までが2万1,011である。
決済情報・ID・パスワードといったアカウント情報は流出項目に含まれず、
安全に保護されているとしている。

注目すべきは、壊れた場所が管理画面でも基幹データベースでもなく、
「顧客が自分の注文状況を見るための機能」だったことである。この種の機能は
利用者にとっての利便の中心にあり、外部の配送・決済・カスタマーサポートの
仕組みと連携するために API として切り出されていることが多い。
日々正常に動いている経路であるがゆえに、異常なアクセスが混じっても
「機能が落ちていない」限り気づきにくい。

本記録の評価として、この事案の価値は流出量よりも位置にある。EC の
注文照会・配送追跡・返品受付は、ほぼすべての事業者が持つ機能であり、
同じ構図を自社に当てはめて点検できる。

同社が公表したのは「異常なアクセスが発生した」までで、認可の不備かどうかは示されていない未確定事項出典 [1] [2] [3]

本記録が事実として扱えるのは「連携機能（API）に外部から異常なアクセスが
発生した」という一文までである。認証を回避されたのか、認証は通ったうえで
他人の注文を引けたのか、識別子を順に変えて総当たりされたのか、
正規の連携先の認証情報が悪用されたのか——いずれも公表されていない。

日次ニュースの解説では「認証を要する API が、認可の粒度不足で他人の注文を
引ける」という設計上の欠陥の類型が示された。EC で繰り返し出ている型では
あるが、本件がその型であるという公表も報道も無い。本記録は、
この読みを事実として扱わず、本記録の作成者による解釈として齟齬の記録に置く。

実務への影響は具体的である。「どこが壊れていたか」が公表されないと、
同業他社は自社の点検範囲を決められない。認可の欠落なのか、
レート制限の不在なのか、連携先の資格情報の管理なのかで、
手を入れる場所はまったく異なる。

遮断は即日、公表は2日後、通知は「項目別に本人へ」——確認から公表までの段取りは参考になる組織の対応出典 [1] [2] [3]

同社が公表した対応は次の4つである。第一に、異常アクセスの確認直後に
当該アクセス経路を遮断した。第二に、KISA へ自主申告した。第三に、
流出対象の顧客には流出した項目を個別に案内した。第四に、サイトに
本人認証を経て自分の流出内訳を確認できるボタンを置き、告知の掲載日から
30日間運用した。あわせて、他サイトと同じパスワードを使っている顧客には
変更を勧めている。

本記録の評価として、注目すべきは第三と第四の組み合わせである。
本件の流出は「氏名のみ」と「氏名・メール・携帯・配送情報まで」の2層に
分かれており、必要な自衛の程度が層ごとに違う。全員に同じ文面を送れば、
配送情報まで出た2万1,011の層に必要な警戒が伝わらず、氏名のみの層には
過剰な不安を与える。項目別の個別案内と自己照会の窓口は、この差を
利用者側で解消させる仕組みである。

同社の注意喚起の書き方も具体的だった。「注文内容に言及して決済・返金・
配送のエラーを案内する SMS・電話・メールに特に注意してほしい」
「29CM は SMS やメールでパスワードや認証番号の入力を求めることはない」
（いずれも原文韓国語）と、想定される次の一手を名指ししている。
配送情報が出た事案で最も起きやすいのは、注文の実在を装ったスミッシングである。
抽象的な「不審な連絡にご注意ください」より、被害の抑止に効く書き方である。

決済情報とパスワードが無事でも、氏名・電話番号・配送先が揃えば詐取の成功率は上がる評価・解釈出典 [1] [2] [3]

同社は決済情報・ID・パスワードが流出項目に含まれないことを明示した。
これは事実として重要であり、アカウント乗っ取りや不正決済の直接的な材料が
出ていないことを意味する。

一方で、本記録の評価としては、2万1,011の層に残った組み合わせを軽く見るべきではない。
氏名・携帯電話番号・配送先住所・そして「その人が実際に注文をした」という文脈が
そろうと、詐取の側は「あなたの◯◯の配送でエラーが出ています」という
実在する取引に紐づいた文面を作れる。受け取る側から見て、これは無差別の
スミッシングとは別物である。パスワードが漏れていないことは、
利用者に「何もしなくてよい」と伝える理由にはならない。

同社が「注文内容に言及する連絡」を名指しで警告したのは、この差を
理解した書き方である。日本の事業者が同種の告知を書くときにも、
「流出していないもの」の列挙で終えず、「残った組み合わせで何ができてしまうか」
まで書くほうが、利用者の行動を変えられる。

CISO・経営層への示唆
  • 本人通知は「全員に同じ文面」ではなく、流出項目の層ごとに分けて出せるように平時から用意しておく
    本件の流出は「氏名のみ」と「氏名・メール・携帯・配送情報まで」の2層に 分かれており、必要な自衛の程度がまったく違う。29CM は項目別の個別案内と 自己照会の窓口を用意し、層の差を利用者側で解消させた。
    取るべき行動 インシデント対応計画に「通知文面は流出項目の層ごとに分ける」と書き、 層の判定に必要なデータ（誰にどの項目が出たか）を事故時に出せるかを あらかじめ確認する。日本では個人情報保護法の漏えい等報告（規則7条）で 1,000人を超える漏えいの速報・確報と本人通知が義務になるため、 層別の文面の雛形を、報告様式とあわせて平時に作っておく。
  • 「決済情報とパスワードは無事」で告知を終えると、残った組み合わせの危険が伝わらない
    本件では決済情報・ID・パスワードが流出しなかったことが明示された。 一方で、氏名・携帯電話番号・配送先と「実際に注文した」という文脈が そろえば、実在の取引を装った詐取が成立する。同社はそこまで踏み込んで 「注文内容に言及する SMS・電話・メールに注意」と名指しで警告した。
    取るべき行動 告知の雛形から「流出していない項目の列挙で締める」構成を外し、 「残った項目の組み合わせで何ができてしまうか」と 「当社は◯◯を求めない」の2文を必ず入れる。広報・法務と 事前に文面を合意しておく。
  • 当局への申告を先に済ませ、公表と本人通知を同時に出す順序を決めておく
    29CM は確認直後に経路を遮断して KISA へ自主申告し、その2日後に公表と 個別案内を同時に出した。件数の確定を待って公表が遅れる型には陥っていない。
    取るべき行動 「経路の遮断」「当局への報告」「本人通知」「対外公表」の4つについて、 誰がいつ判断するかを順序つきで文書化する。日本では速報の期限 （おおむね3〜5日以内）が先に来るため、件数の確定を公表の前提条件にしない 運用に切り替える。
  • 壊れた場所を公表しない判断は、自社を守る一方で業界の点検を止める
    同社は「連携機能（API）への異常なアクセス」以上を説明していない。 認可の欠落なのか、レート制限の不在なのか、連携先の資格情報の管理なのかで 他社が手を入れる場所はまったく違う。結果として、この事案から 同業他社が得られる具体的な手掛かりは限られている。
    取るべき行動 自社の公表方針に「攻撃者を利さずに他社の点検に資する粒度」の水準を 定義しておく。製品名やパラメータを出さなくても、 「認可のチェック漏れ」「レート制限の不備」といった分類までは 出せる場合が多い。出す・出さないを事故中に議論しない。
セキュリティ技術者への示唆
  • 会員向けの照会 API は、認証を通ったことと「その人のデータか」を分けて検証する
    本件で壊れたのは管理画面でも基幹データベースでもなく、 顧客が自分の注文を見るための連携機能だった。認証済みの利用者が 他人の識別子を渡したときに何が返るかは、認証の層では決まらない。
    取るべき行動 注文照会・配送追跡・返品受付・領収書発行など、識別子を受け取る エンドポイントを列挙し、それぞれについて「別の利用者の識別子を渡すと どうなるか」を実際に試す。サーバ側で所有者の検証を毎回行い、 識別子の推測困難性に頼らない。
  • 大量取得は認証・認可では止まらない場合がある。呼び出し量と応答件数に上限を置く
    15万9,852件という規模は、1件ずつの照会が大量に成立して初めて到達する。 個々の呼び出しが正規の形をしていれば、認証も認可も通ってしまう。
    取るべき行動 照会系 API に、呼び出し元（アカウント・トークン・IP）単位のレート制限と、 1回の応答で返す最大件数の上限を実装する。上限値を決めるために、 まず平常時の呼び出し量と応答件数の分布を計測する。
  • 応答に含める項目を用途ごとに削れば、同じ穴が開いても出る情報は減る
    本件では2万1,011の層で配送情報まで出た。配送先住所と電話番号は、 注文一覧の表示には必ずしも要らない。返す項目が多いほど、 1回の悪用で持ち出せる価値が上がる。
    取るべき行動 照会系 API の応答スキーマを画面の用途ごとに分け、 配送先住所・電話番号・メールアドレスは、それを表示する画面からの 呼び出しでのみ返す。既存の「全部返す」エンドポイントは 用途別に分割して段階的に廃止する。
  • 事後に対象を特定できるかは、API のアクセスログに何を残しているかで決まる
    同社は件数を項目別の内訳まで確定させて公表できた。これはアクセスログから 「誰の情報が返されたか」を追えたことを示唆する（本記録の推定）。 呼び出しの記録しか無く、返した対象が分からなければ、 本人通知の対象すら決められない。
    取るべき行動 照会系 API のログに、呼び出し元・引数・応答した対象の識別子・件数を 残しているかを確認する。個人情報そのものをログに書かずに 対象を追えるよう、識別子だけを記録する設計にする。 保持期間が事故の発覚までの想定期間を下回っていないかも確認する。
  • 流出確認ページを新設すると、それ自体がフィッシングの模倣対象になる
    29CM は本人認証を経て自分の流出内訳を確認できるボタンをサイトに置いた。 利用者にとって有用な仕組みだが、「流出を確認してください」という 誘導は詐取の側にとっても使いやすい文脈になる。
    取るべき行動 確認ページは自社ドメインの既存導線（ログイン後のマイページ等）に置き、 メールや SMS から直接リンクを踏ませる設計を避ける。 あわせて自社名を含む新規ドメインの登録監視を、事故の発生直後から始める。
