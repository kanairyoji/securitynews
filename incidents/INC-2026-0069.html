INC-2026-0069Zeabur の環境変数から利用者の API キー流出

台湾のデプロイ基盤 Zeabur が「以前に流出していた高権限 AWS 管理者認証情報」で東京リージョンの共有クラスタに入られ、利用者が預けたプロジェクト環境変数（OpenAI・Anthropic・Stripe・GitHub の鍵）が照会された——被害は Zeabur ではなく利用者それぞれの第三者サービスの請求として現れた

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年8月28日 最終更新: 2026年8月31日

台湾のクラウドデプロイ基盤（PaaS）Zeabur は、2026年8月27日に内部サービス用の
認証情報が不正に使われ、利用者のプロジェクト環境変数の記録が照会されたことを
検知したと公表しました。翌8月28日にステータスページで第一報を出し、8月29日には
経路として「以前に流出していた高権限の AWS 管理者認証情報で東京リージョンの
共有 AWS クラスタに入り、そこから VPN で制御系ネットワークへ移り、主データベースに
接続した」と説明しています。

この事案の要点は、被害が Zeabur のサービス障害としてではなく、
利用者それぞれの第三者サービスの請求として現れたことにあります。
Zeabur の環境変数には、利用者が自分で設定した OpenAI・Anthropic・OpenRouter の
API キー、AWS のアクセスキー、Stripe のシークレットキー、GitHub のトークンなどが
入っていました。攻撃者はそれらを狙って照会し、利用者からは AI サービスの
使用量が突然跳ね上がったという報告が上がりました。Zeabur は8月30日時点で、
提出された補償請求の約63%を検証済みとし、2026年9月30日までに支払いを終える方針を
示しています。

一方、ハッカー側は8月29日にフォーラムで、Zeabur のソースコード・データベース
バックアップ・GCP サービスアカウント・Stripe の API キーを含む約612GB を
盗んだと主張しました。Zeabur はこの主張について「完全なデータセットを取得した
証拠は見つかっていない」と述べています。主張の真偽は確認されていません。

日本の読者にとっての読みどころは、日本の組織が当事者だからではなく、
PaaS の環境変数機能を「秘密の保管庫」として使う構図が日本の開発現場でも
ごく普通だからです。本記録は、Zeabur とメディアが公表した事実と、
本記録の作成者による評価を分けて整理します。

侵害されたのは Zeabur だが、請求が来たのは利用者だった——PaaS の環境変数は「他人の秘密の集積所」である概観出典 [1] [2] [4]

Zeabur が公表した事実は次のとおりである。2026年8月27日、内部サービス用の
認証情報が不正に使われ、プロジェクト環境変数の記録を取得する用途に
使われたことを検知した。8月29日の第一次調査報告では、攻撃者が
漏洩した AWS 管理者認証情報で東京リージョンの共有クラスタに入り、
そこから VPN アクセスを得て主データベースに接続した経路が示された。
環境変数への照会は「特に AI サービスの API キーと、そのまま使える認証情報」を
狙った標的型のクエリとして検出されている。

この構図で重要なのは、Zeabur が失ったものと、利用者が失ったものが違うことである。
Zeabur 自身は、アカウントの認証情報・個人情報・サーバのデータ・支払い情報には
アクセスされていないと述べている。一方で、利用者が環境変数に入れていたのは
OpenAI・Anthropic・OpenRouter の API キー、AWS のアクセスキー、
Stripe のシークレットキー、GitHub のトークンであり、これらは
Zeabur のものではなく利用者が第三者と結んだ契約の鍵である。
被害は Zeabur のサービス障害ではなく、利用者それぞれの請求書に現れた。

本記録の評価として、これは PaaS の環境変数機能の位置づけの問題である。
環境変数の管理機能は「アプリに設定値を渡す仕組み」として作られており、
鍵管理サービス（AWS Secrets Manager・HashiCorp Vault など）のような
アクセス記録・鍵のローテーション・利用者単位の暗号化を前提としていない。
それでも実運用では秘密の保管庫として使われる。便利さの分だけ、
基盤側が1回破られたときに全利用者の第三者契約が同時に開く。

経路は「流出済みの高権限 AWS 管理者認証情報」——最初の穴がいつ開いたかは公表されていない原因・手口出典 [1] [4]

Zeabur が8月29日と8月31日に示した経路は次の4段である。
①以前に流出していた高権限の AWS 管理者認証情報を攻撃者が入手していた。
②その認証情報で東京リージョンの共有 AWS クラスタにアクセスした。
③クラスタから VPN アクセスを得て、同社の制御系ネットワークに移った。
④制御系ネットワークから主データベースに接続し、環境変数を照会した。

同社は8月31日に、侵害された AWS クラスタが「段階的に廃止しつつある
エッジサービス」のものであり、コアのバックエンドサービスは別のクラウド基盤に
構築されデバイス単位の VPN アクセス制限で保護されているため
直接の影響は受けていないと補足している。

本記録の評価として、この補足には二つの読み方がある。事実として、
コアが別基盤にありデバイス制限で守られていたことは被害を限定した。
一方で、廃止途中の環境から制御系ネットワークと主データベースへ
到達できてしまったという事実は残る。廃止予定の環境は、監視の対象からも
権限の棚卸しからも先に外れやすい。攻撃者にとっては、稼働中の環境より
入りやすく、かつ内側に接続されている。

公表されていないのは①である。高権限の認証情報がいつ・どこから流出したのか、
なぜ流出後も有効なままだったのかを Zeabur は説明していない。
ここが本事案の根であり、説明が無い限り、同種の再発を防ぐ手立てを
他社が学ぶことはできない。

「完全なデータセットを取得した証拠は無い」と「612GB を盗んだ」が並立したまま残っている未確定事項出典 [1] [3] [4]

8月29日、ダークウェブ脅威インテリジェンスの Dark Web Intelligence が、
ハッカーフォーラムで Zeabur からの窃取を主張する投稿を確認したと伝えた。
主張の内訳は、ソースコード、PostgreSQL・MongoDB のデータベースバックアップ、
AWS のインフラ秘密鍵、GCP のサービスアカウント（プロジェクト所有者権限つき）、
Google Workspace の管理者アクセス、GitHub のプライベート PAT、
Stripe の API キー、Kubernetes クラスタの管理者アクセス、
WireGuard VPN のアクセス、そして約612GB の顧客データベースである。

Zeabur は同日、システムの記録・観測された攻撃者の活動・その他の証拠に基づいて
「攻撃者が完全なデータセットを取得した証拠はまだ見つかっていない」と述べた。
8月29日の第一次調査報告でも、顧客情報やサーバ設定については集約的な操作は
観察されたが、大規模な読み出し・エクスポートの直接証拠は見つかっていないとしている。

本記録は、この二つを並立したまま記録する。第三者によるサンプルの照合など、
主張を検証した報告は本記録の作成者が確認した範囲では見当たらない。
「証拠が見つかっていない」は「起きていない」とは違い、
「612GB を盗んだ」も証明されていない。

なお Zeabur は8月31日、この不確かさ自体が悪用されていると警告した。
フォーラムやチャットグループに同社が把握する状況と矛盾する流出情報が現れ、
一部は利用者に対する詐欺や支払いの誘導に使われている疑いがあるという。
事故の直後は、当事者の公表より攻撃者の主張のほうが速く広く出回る。

補償を「請求 → 個別審査 → 9月30日までに支払い」の型で回している補償出典 [1]

Zeabur は、認証情報の不正利用によって利用者に生じた追加の請求について、
補償の受付を行っている。8月30日時点で、提出された補償請求の約63%が
検証を終えて補償処理の段階に進み、約21%が審査中で、12〜24時間以内の
返答を目指すとしている。支払いは2026年9月30日までに完了する予定である。

本記録の評価として、この対応の設計は妥当である。本事案の損害は
「利用者が第三者サービスから受け取る請求書の金額」という、
被害者側にしか分からない形で現れる。基盤側が一律の金額を決めることはできず、
個別審査以外の方法が無い。進捗を割合で公開し、返答の目標時間を示すことは、
待たされる側の不安を減らす。

一方で、分母が公表されていないことは記録しておく必要がある。
「63%が検証済み」という数字は、請求が10件でも1万件でも同じ形で書ける。
補償の規模も、影響を受けた利用者の数も、これでは分からない。
対応の速さを示す数字と、被害の規模を示す数字は別物であり、
本事案では前者だけが公表されている。

日本の開発現場に効くのは「東京リージョン」ではなく「環境変数に何を置いているか」評価・解釈出典 [1] [2] [4]

本事案で東京リージョンが出てくるのは、Zeabur の共有 AWS クラスタが
そこにあったからであって、日本の組織が当事者だからではない。
日本の利用者の多寡も公表されていない。地理的な近さを日本への波及と
読み替えるべきではない。

日本の読者に効くのは別の点である。PaaS の環境変数に第三者サービスの
認証情報を置く構図は、日本の開発現場でもごく普通だという事実である。
Vercel・Render・Railway・Fly.io・Heroku、そして各社の社内 PaaS でも、
デプロイの設定画面に API キーを貼るのは日常の作業になっている。
生成 AI の利用が広がったこの1年で、そこに置かれる鍵の種類は増え、
1本あたりの金銭的な価値も上がった。

本記録の評価として、本事案から取り出すべき問いは3つである。
第一に、自社の鍵が今どこにいくつあるかを言えるか。
第二に、基盤側が破られたときに、その鍵で何ができてしまうか——
利用上限は設定してあるか、権限は最小か、有効期限はあるか。
第三に、基盤側が破られたことを、自分たちはどう知るか——
Zeabur の利用者は「AI サービスの使用量が突然跳ね上がった」ことで気づいた。
つまり、請求のアラートが実質的な侵害検知として働いた。
これは褒められた検知手段ではないが、何も無いよりは良い。

緩和策
数え方: PaaS・CI/CD の環境変数機能を「設定値の受け渡し」に限定し、第三者サービスの認証情報は鍵管理サービス（AWS Secrets Manager・HashiCorp Vault 等）から実行時に取得する　副作用: 起動時の依存が増え、鍵管理サービスの障害がアプリケーションの起動障害に 直結する。ローカル開発・プレビュー環境での取り回しも複雑になり、 移行そのものに工数がかかる　数値の出所: 本件で環境変数が主データベースへの接続から照会された構図に基づく本記録の整理
数え方: 第三者サービスの API キーに利用上限・支出上限を設定し、流出時の損害を請求額で頭打ちにする　副作用: 正規の利用が繁忙期に上限へ当たり、サービスが止まる。 上限値を決めるには平常時の使用量の計測が先に要る　数値の出所: 利用者側で AI サービスの使用量が跳ね上がった事実に基づく本記録の整理
数え方: 恒久的なクラウドのアクセスキーを廃し、短命の一時認証情報（IAM ロールの引き受け・OIDC 連携）に置き換える　副作用: 古いツール・スクリプト・CI の設定が一時認証情報に対応しておらず、 棚卸しと書き換えが必要になる。移行期間中は両方式が併存し、 かえって管理対象が増える　数値の出所: 「以前に流出していた高権限の認証情報」が有効なまま使われた構図に基づく本記録の整理
数え方: 廃止予定の環境を、廃止が完了するまで監視・権限棚卸しの対象から外さない運用ルールを設ける　副作用: 廃止作業のコストが下がらず、「動いていない環境」への監視費用が かかり続ける。廃止の期限管理を別途行わないと、対象が減らない　数値の出所: 侵害されたクラスタが「段階的に廃止しつつあるエッジサービス」だった点に基づく本記録の整理
数え方: 実行環境（データプレーン）から制御系（コントロールプレーン）への到達をネットワークで遮断し、VPN 接続にデバイス単位の制限をかける　副作用: 運用者の作業経路が制限され、緊急時の対応に手数が増える。 デバイス証明書の配布・失効の運用が新たに必要になる　数値の出所: Zeabur のコア基盤側でこの制限が被害の拡大を止めた事実に基づく本記録の整理

layer 0 の「以前の流出」は、時期も経路も公表されていない（破線）。 layer 1〜4 は Zeabur が8月29日・8月31日に公表した経路である。 侵害されたのは段階的に廃止中のエッジサービスのクラスタで、 コアのバックエンドは別基盤にありデバイス単位の VPN 制限に守られて 直接の影響を免れた（layer 2 の分岐）。被害が現れたのは Zeabur ではなく、 利用者それぞれの第三者サービスの請求である（layer 6）。 約612GB の窃取という攻撃者側の主張は、当事者の裏付けが無い（layer 7）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
第一報の時点で、影響を受けうる環境変数の「名前の形」 （ACCESS_TOKEN・AWS_ACCESS_KEY_ID・STRIPE_SECRET_KEY・OPENAI_API_KEY など 25種類以上）を列挙して公表した機能した本記録の作成者の評価である。この種の事案で利用者が最初に必要とするのは 「自分は何をローテーションすればよいか」であり、名前の形の列挙は その問いに直接答える。件数や影響利用者数の確定を待たずに出した点も、 利用者の行動を早める効果がある。
検知の翌日に第一報を出し、その2日後に侵入経路（AWS 管理者認証情報 → 東京クラスタ → VPN → 主データベース）を公表した。影響を受けた 利用者数・変数の件数は公表しないまま経路を先に出している部分的に機能本記録の作成者の評価である。経路の公表は速く、粒度も十分である。 一方で、影響を受けた利用者数・プロジェクト数・変数の件数が いずれも公表されず、補償請求の分母も示されていないため、 規模の説明は欠けたままである。段階的廃止中のエッジサービスから 制御系ネットワークへ到達された点についても、なぜそうなっていたかの 説明は無い。
認証情報の不正利用によって利用者に生じた追加請求について、 個別審査による補償を行い、2026年9月30日までに支払いを完了するとした。 8月30日時点で提出された請求の約63%が検証済み部分的に機能本記録の作成者の評価である。進捗を割合で公開し返答の目標時間 （12〜24時間）を示した点は、待たされる側への配慮として機能している。 一方、分母（請求件数）も総額も公表されていないため、 この数字からは対応の速さしか読み取れず、被害の規模は分からない。
CISO・経営層への示唆
  • 「基盤を使う」ことは「基盤に自社の第三者契約の鍵を預ける」ことだと、契約と棚卸しの両方に書く
    本件で流出したのは Zeabur の秘密ではなく、利用者が OpenAI・Anthropic・ Stripe・GitHub・AWS と結んだ契約の鍵である。Zeabur 自身は アカウント情報・個人情報・支払い情報にはアクセスされていないと述べており、 基盤側の被害申告だけを見ていると自社の損害を見落とす。
    取るべき行動 利用中の PaaS・CI/CD・SaaS について、「そこに預けている第三者サービスの 認証情報の一覧」を作り、四半期ごとに棚卸しする。委託・利用契約の レビュー項目に「当社が預けた認証情報が漏えいした場合の通知義務と補償」を 加える。基盤側の事故公表を待つのではなく、自社が何を預けているかを 自社で把握しておく。
  • AI サービスの API キーは「請求額がそのまま損害額になる」新しい種類の資産である
    本件の被害は、利用者の AI サービス使用量の急増という形で現れた。 従来の認証情報の流出は「データが取られる」被害だったが、 生成 AI の従量課金では「使われた分だけ課金される」金銭損害が直接発生する。 Zeabur は補償の受付を開始し、2026年9月30日までの支払いを予定している。
    取るべき行動 全社で利用している生成 AI サービスのキーを洗い出し、 サービス側で設定できる利用上限・支出上限を必ず設定する。 上限の設定値は、平常時の使用量を計測してから決める。 月次の請求額の急変を検知するアラートを、経理ではなくセキュリティ側でも受ける。
  • 「廃止予定の環境」は、監視と権限棚卸しから最初に落ちる。落とさない仕組みを作る
    Zeabur が侵害されたのは「段階的に廃止しつつあるエッジサービス」の AWS クラスタであり、そこから制御系ネットワークと主データベースに 到達された。稼働中の環境より入りやすく、かつ内側に接続されている、 という状態が生まれていた。
    取るべき行動 廃止予定・移行中・検証用の環境について、「いつまでに消すか」を 期限つきの台帳で管理し、期限までは監視と権限棚卸しの対象から 外さないことをルール化する。廃止の完了を誰が確認するかを決めておく。
  • 事故の直後は、当事者の公表より攻撃者の主張のほうが速く広く出回る
    Zeabur では、公表の翌日にハッカーフォーラムで612GB の窃取が主張され、 同社は「完全なデータセットを取得した証拠はまだ見つかっていない」と 反論した。さらに8月31日には、同社が把握する状況と矛盾する流出情報が フォーラムやチャットに現れ、一部が利用者への詐欺や支払いの誘導に 使われている疑いがあると警告している。
    取るべき行動 インシデント対応計画に「攻撃者の主張が出たときの対応」を項目として持つ。 自社の顧客・利用者に向けて、公式の情報源（ステータスページ・特定の告知ページ）を 事故の初期に一本化して周知し、「当社からの連絡はこの経路のみ」と明示する。 取引先・顧客を狙う便乗詐欺の監視を、事故の発生直後から始める。
  • 補償の進捗を割合で出しても、分母が無ければ規模の説明にはならない
    Zeabur は「提出された補償請求の約63%が検証済み」と公表したが、 請求件数も、影響を受けた利用者数も、補償の総額も公表していない。 対応の速さは伝わるが、事故の大きさは伝わらない。
    取るべき行動 自社が事故を公表する側になったとき、「対応の進捗を示す数字」と 「被害の規模を示す数字」を別々に用意する。規模がまだ確定しないなら 「確定していない」と書く。割合だけを出して規模の説明に代えない。
セキュリティ技術者への示唆
  • PaaS の環境変数は鍵管理サービスではない。復号の境界がどこにあるかを確認する
    本件では、攻撃者が主データベースへ接続したところから環境変数の値を 照会できている。これは値が平文か、アプリケーション層で復号可能な形で 保存されていたことを示唆する（本記録の推定）。Zeabur は暗号化の有無や 鍵の管理方法を公表していない。
    取るべき行動 利用中の PaaS について、環境変数の保存時の暗号化の有無と、 誰が復号できるか（基盤の運用者は見られるのか）をドキュメントで確認する。 確認できない場合は、そこに第三者サービスの認証情報を置かない前提で 設計し直す。長期的には、実行時に鍵管理サービスから取得する形へ移す。
  • 恒久的なクラウドのアクセスキーを1本でも残していると、それが将来の侵入口になる
    Zeabur は「以前に流出していた高権限の認証情報」が使われたと述べている。 流出がいつ起きたかは公表されていないが、流出後も有効なまま 使えたことは確かである。恒久キーは、漏れた瞬間ではなく 漏れたことに気づいた瞬間まで有効であり続ける。
    取るべき行動 AWS・GCP・Azure の恒久的なアクセスキーを列挙し、 IAM ロールの引き受け・OIDC 連携による短命の一時認証情報に置き換える。 置き換えられないものは、最終利用日を監視して未使用のものを削除し、 定期ローテーションを自動化する。公開リポジトリとビルド成果物に対する 鍵文字列の走査（secret scanning）を CI に組み込む。
  • データプレーンからコントロールプレーンへ到達できる経路を洗い出す
    本件の経路は「共有 AWS クラスタ → VPN → 制御系ネットワーク → 主データベース」 である。逆に、コアのバックエンドは別の基盤にあり、 デバイス単位の VPN アクセス制限で守られていたため直接の影響を免れた。 同じ会社の中で、境界の有無が被害の範囲を分けた。
    取るべき行動 自社のクラスタ・実行環境から、管理系のネットワーク・管理データベースへ 到達できる経路を実際に試して確認する。VPN 接続にデバイス証明書を必須にし、 実行環境からの接続元は明示的に拒否する。到達が必要な操作は、 監査可能な API に限定する。
  • 秘密情報を持つテーブルへの問い合わせは、件数とパターンを監視する
    Zeabur は本件の照会を「特に AI サービスの API キーと、そのまま使える 認証情報を狙った標的型のクエリ」として識別した。正規の接続経路から 正規の形の問い合わせが来る型では、外向き通信の異常としては現れない。 検知点は問い合わせの側にしか無い。
    取るべき行動 秘密情報を保持するテーブルについて、単位時間あたりの問い合わせ件数・ 取得行数・アクセスするアカウントの分布を計測し、平常時からの逸脱で アラートを上げる。しきい値を超えたら自動で接続を落とす仕組みまで 用意しておく。
  • 第三者サービスの使用量アラートは、実質的な侵害検知として働く
    本件で利用者が異常に気づいた端緒は「AI サービスの使用量が突然跳ね上がった」 ことだった。基盤側の侵害を利用者が知る手段は無く、 請求の急増だけが外から見える症状だった。
    取るべき行動 利用中の第三者 API（生成 AI・決済・地図・SMS など）について、 使用量と課金額のしきい値アラートを設定し、通知先にセキュリティ担当を含める。 あわせて、キーごとに用途を分けておくと、どのキーが悪用されたかを 使用量の内訳から特定できる。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ PaaS・CI/CD・コンテナ基盤の「環境変数」機能に、第三者サービスの API キーやトークンを保存している本件で照会されたのは、まさにこの形で保存された値である。 環境変数の管理機能は設定値の受け渡しのために作られており、 鍵管理サービスのような復号の境界・アクセス記録・ローテーションを 前提としていない。基盤側が1回破られると、全利用者の第三者契約が同時に開く。
認証・認可□ クラウド（AWS・GCP・Azure）の恒久的なアクセスキーが残っており、最終利用日やローテーションの管理がされていないZeabur の侵入口は「以前に流出していた高権限の AWS 管理者認証情報」である。 恒久キーは、漏れたことに気づくまで有効であり続ける。 1本でも残っていれば、それが将来の侵入口になりうる。
システム構成□ 実行環境（クラスタ・コンテナ）から、管理系のネットワークや管理データベースへネットワーク的に到達できる本件の被害は、クラスタ → VPN → 制御系 → 主データベース、という到達で成立した。 同じ会社の中でも、デバイス制限のあったコア基盤は直接の影響を免れている。 境界の有無が被害範囲を決めた。
運用・監視□ 廃止予定・移行中・検証用の環境が、監視・権限棚卸しの対象から外れている侵害されたのは「段階的に廃止しつつあるエッジサービス」のクラスタだった。 稼働中の環境より入りやすく、それでいて内側に接続されている状態は、 廃止作業が長期化するほど生まれやすい。
データの保持□ 生成 AI サービスの API キーに、利用上限・支出上限を設定していない本件の実害は AI サービスの使用量の急増として現れた。 従量課金の API キーは、流出すると請求額がそのまま損害額になる。 上限の設定は、流出を防げなくても損害を頭打ちにできる数少ない手段である。
体制・契約□ 利用している基盤・SaaS に「自社が何を預けているか」の一覧が無く、事故時に何をローテーションすべきか即答できないZeabur の利用者が最初に必要としたのは「自分は何をローテーションすればよいか」 であり、同社は変数名の形を列挙してそれに答えた。 預けたものの一覧が自社に無ければ、通知を受けても行動に移せない。
