INC-2026-0075Softaculous の更新がBGP乗っ取りで汚染

Softaculous の更新配信 IP が33時間 BGP ハイジャックされ、Let's Encrypt のドメイン検証まで迂回経路を通ったため正規の TLS 証明書が発行された——利用者に証明書警告は出ず、更新パッケージに署名が無かったため悪性の Virtualizor 更新がそのまま適用された

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因
初報: 2026年8月31日 最終更新: 2026年9月1日

ホスティング事業者向けソフトウェアを提供する Softaculous は2026年8月31日、
同社が使う IP アドレス帯（162.55.80.0/24・ドイツの Hetzner の空間）が
2026年8月28日20時57分（協定世界時）から8月30日6時10分まで、およそ33時間にわたり
BGP ハイジャック（経路の不正広告）を受けたと公表しました。乗っ取られた帯には、
VPS 管理パネル Virtualizor のソフトウェア更新エンドポイントと、
Softaculous の顧客・請求ポータルが含まれていました。

この事案の要点は二つあります。一つは、認証局のドメイン所有確認まで
同じ迂回経路を通ったことです。攻撃者は Let's Encrypt から
virtualizor.com・api.virtualizor.com・files.virtualizor.com を含む
29ドメイン分の技術的に有効な TLS 証明書を取得しており、
迂回された通信に証明書の警告は出ませんでした。
もう一つは、更新パッケージに暗号署名が無かったことです。
Softaculous は「当社の製品更新クライアントは更新パッケージの暗号的な検証を
まだ行っていなかったため、改変されたパッケージがその理由で拒否されることは
なかった」（原文英語）と述べています。結果として、迂回中に更新を確認した
少数の設置環境へ悪性の Virtualizor 更新パッケージが配信されました。

日本の読者にとっての読みどころは、「配布経路の乗っ取りだけで、
暗号による信頼の連鎖がまるごと迂回された」という構図にあります。
TLS は「通信相手が正しいか」を、証明書は「そのドメインの持ち主か」を
保証する仕組みですが、いずれも経路が乗っ取られた状態では
攻撃者の側で成立してしまいました。残る最後の砦はパッケージ署名でしたが、
それが実装されていませんでした。本記録は、Softaculous が公表した事実と、
本記録の作成者による評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

経路の不正広告によってベンダー宛の通信を攻撃者のサーバへ引き込み、 その状態のまま認証局のドメイン所有確認を通して正規の TLS 証明書を取得し、 証明書の警告を出さずに更新エンドポイントを装って悪性のパッケージを配信した。 受け取る側に更新パッケージの署名検証が無かったため、そのまま適用された。 攻撃者の帰属・悪性パッケージの機能・配信件数は公表されていない。

経路を乗っ取られた時点で、TLS も証明書も攻撃者の側で成立した概観出典 [1] [2] [3]

Softaculous が公表した事実は次のとおりである。2026年8月28日20時57分ごろ
（協定世界時、以下同じ）、AS62390 が中継事業者 AS6204 を経由して
162.55.80.0/24 の広告を開始した。この帯は Hetzner のアドレス空間の一部で、
Hetzner 自身は 162.55.0.0/16 として広告している。より細かい範囲の広告は
標準的な経路選択の下で優先されるため、これを受け入れたネットワークでは
Softaculous 宛の通信が攻撃者のサーバへ向かった。乗っ取られた帯には、
Virtualizor のソフトウェア更新エンドポイントと、
Softaculous の顧客・請求ポータルが含まれていた。

攻撃者は Let's Encrypt から、virtualizor.com・api.virtualizor.com・
files.virtualizor.com を含む29ドメイン分の技術的に有効な TLS 証明書を
取得した。認証局の自動のドメイン所有確認が、同じハイジャックされた経路を
通ったためである。迂回された通信に証明書の警告は出なかった。

本記録の評価として、この事案が示したのは
「経路が乗っ取られた瞬間に、経路の上に載っている信頼の仕組みが
まとめて無効になる」という順序である。TLS は通信路を暗号化し、
証明書はドメインの持ち主であることを保証する。しかしその「持ち主であること」の
確認自体が経路を通って行われるなら、経路を握った者が持ち主になれる。
公開鍵基盤の弱点そのものであり、新しい発見ではないが、
実際にベンダーの更新配信で成立した例は多くない。

最後の砦になるはずだったパッケージ署名が、実装されていなかった原因・手口出典 [1] [2]

Softaculous は公表文で次のように述べている——「当社の製品更新クライアントは
更新パッケージの暗号的な検証をまだ行っていなかったため、
改変されたパッケージがその理由で拒否されることはなかった」（原文英語）。

本記録の評価として、ここが本事案の中心である。経路の乗っ取りは
配布インフラの外側で起きる事象であり、ベンダーが単独で防ぐことはできない。
これに対してパッケージ署名は、配布経路がどれだけ汚染されても
「そのパッケージをベンダーが作ったか」だけを鍵で確かめる仕組みであり、
経路から独立している。署名があれば、この攻撃は
「更新の取得に失敗する」という障害で終わっていた。

同社は今後すべてのパッケージにコード署名の仕組みを導入し、
インフラを移行する方針を示した。2026年9月1日には Virtualizor 3.2.9.9 を公開し、
管理パネルに点検用の「Security Analyzer」を追加している。

日本の読者に対して意味を持つのは、この構図が
ソフトウェアを配る側すべてに当てはまることである。
自社製品の更新、社内向けのエージェント配布、
機器のファームウェア更新のいずれについても、
問うべきことは同じ一つに集約される——
「配布サーバへの経路が今日まるごと乗っ取られたとして、
受け取る側は偽物を拒否できるか」。
できないなら、TLS を張っていることは答えになっていない。

被害の観測点がベンダー側に無く、確定的な影響一覧を作れない被害規模・影響範囲出典 [1] [2] [3]

Softaculous は、悪性の更新パッケージが「迂回中に更新を確認した
少数の設置環境」へ配信されたことを確認したとし、
「一般的な Virtualizor 利用者全体ではなく少数のサーバに影響した」
（いずれも原文英語）と表現している。一方で件数は示していない。
理由も明示されている——「悪性の応答は攻撃者のシステムが返したもので、
当社のログには一切届いていないため、影響を受けたサーバの
確定的な一覧を作ることはできない」（原文英語）。

本記録の評価として、これは調査の不足ではなく、
傍受型の攻撃に固有の構造である。通常のサプライチェーン汚染では、
ベンダーの配布サーバに「誰がいつ何を取りに来たか」のログが残る。
経路を乗っ取られた場合、そのやり取りはベンダーに一切届かない。
被害の観測点が存在しないので、影響範囲の確定は原理的にできない。

その帰結として、Softaculous はすべての Virtualizor 運用者に対し、
自分のサーバを「侵害されたものとしてではなく、点検の対象として」
扱うよう求めている。示された手順は具体的である。
/etc/systemd/system/java-jre-update.service の有無を確認し、
あれば削除せずに同社へ連絡する。Virtualizor の API 認証情報を更新し、
アクセス元を信頼できる IP に限定する。未承認の SSH 鍵・アカウント・
スケジュールタスク・外向き接続を監査する。顧客エリアの API キーを再生成する。
期間中に顧客エリアへログインしたなら、そのパスワードと
使い回している先のパスワードをすべて変更する。
カード情報を入力したなら明細を確認する。

同社は、Softaculous 本体・Webuzo・SitePad・Backuply など
他製品を狙う悪性パッケージは確認していないとしつつ、調査は継続中としている。

上流からの通知は無く、気づいたのは自分だった——12時間の空白が意味するもの組織の対応出典 [1] [3]

Softaculous の記述で見落とされやすいのは、Hetzner から能動的な通知は無く、
発生からおよそ12時間後に自社から連絡したという一文である。

対処そのものは速い。しかし、その対処が始まるまでに12時間かかっている。

本記録の評価として、ここには一般化できる教訓がある。
経路の異常は、自分のサーバの中には現れない。
CPU も、ディスクも、アプリケーションのログも正常である。
攻撃者側へ流れた通信は自分のログに残らないので、
「アクセスが減った」という形でしか間接的に見えない。
経路の異常を検知するには、RIPE の経路情報サービスや
BGPStream のような外部の経路監視を、自分の広告する範囲に対して
仕掛けておく必要がある。Softaculous 自身、事後の再構成を

加えて、8月29日8時50分にいったん止まった迂回が、
同日20時ごろに再開して10時間続いている点も重要である。
「一度収まった」ことは終息の根拠にならない。
経路の撤回が確認できるまで、警戒を解くべきではなかった。

事案の重さは配信数ではなく、Virtualizor が何を管理する製品かで決まる評価・解釈出典 [1] [2] [3]

配信された設置環境は「少数」とされている。しかし本記録の評価として、
この事案の重さは配信数では測れない。

Virtualizor は、ホスティング事業者が仮想専用サーバを作成・販売・管理するための
管理パネルである。つまり 1台の Virtualizor は、その下にぶら下がる
多数の顧客の仮想サーバに対する管理権限を持つ。
1台が侵害されれば、影響はその事業者の顧客全体に及びうる。
Softaculous が API 認証情報の更新とアクセス元の制限を
最優先の手順に置いているのは、この構造による。

これは日本の中小ホスティング事業者・VPS 再販事業者にそのまま当てはまる。
さらに一段抽象化すれば、「多数のテナントに対する管理権限を1か所に集めた
製品」の更新経路は、それ自体が重要インフラであるという命題になる。
仮想化基盤の管理パネル、構成管理サーバ、
エンドポイント管理（MDM・RMM）のコンソール、CI/CD の実行基盤は
いずれも同じ性質を持つ。これらの更新をどこから、どう検証して取っているかは、
平時に一度棚卸ししておく価値がある。

なお、経路の検証には RPKI（経路の起源を暗号的に検証する仕組み）がある。
本事案で RPKI が有効だったかどうかを Softaculous は述べておらず、
本記録も断定しない。一般論として、RPKI の起源検証は
「その自律システムがその範囲を広告してよいか」を検査するものであり、
正しく登録・検証されていれば今回のような不正な広告を弾きうる。
自社が広告する範囲について経路の登録（ROA）を出しているか、
上流と自社の双方で検証を有効にしているかは確認に値する。

  • 単位・母数の曖昧さ「72%」が何の割合かで、一次資料と報道の説明が異なる

期間中に作られた顧客エリアのセッションを無効化し、 該当期間のログイン利用者にパスワードの変更と使い回し先の変更を、 カード情報を入力した利用者に明細の確認を求めた。 Virtualizor 運用者には API 認証情報の更新とアクセス元の制限を求めた機能した本記録の作成者の評価である。確定的な一覧を作れない以上、 「全員を点検の対象とし、侵害されたものとは決めつけない」という 枠の置き方は妥当である。Softaculous 自身がこの区別を 公表文で明示している点も、無用な混乱を避けるうえで有効である。
CISO・経営層への示唆
  • 「配布経路が乗っ取られても受け取る側が偽物を拒否できるか」を、自社が配るすべてのものについて問う
    本事案では TLS も証明書も攻撃者の側で成立し、 経路から独立して働く仕組みはパッケージ署名だけだった。 それが実装されていなかったため、悪性の更新がそのまま適用された。
    取るべき行動 自社が外部・社内に配布しているソフトウェア（製品の更新、 社内エージェント、機器のファームウェア、設定配布）を列挙し、 それぞれについて署名検証の有無を確認する。無いものは 実装計画を持つか、更新の承認制とハッシュ照合で暫定的に補う。
  • 上流の通信事業者が経路の異常を通知してくれる前提を置かない
    Softaculous は「Hetzner からの能動的な通知は無く、 発生からおよそ12時間後に当社から連絡した」と記している。 通報後の対処は数分だったが、通報までが12時間だった。
    取るべき行動 自社が広告する IP アドレス範囲に対する経路監視を、 上流に依存せず自前で（または監視サービスで）持つ。 検知したときに誰が上流へ連絡するかを、連絡先とともに手順化する。
  • 影響範囲を確定できない事案があることを前提に、対外説明の型を用意する
    傍受型の攻撃ではベンダー側に観測点が無く、 誰が影響を受けたかを原理的に確定できない。 Softaculous は「侵害されたものとしてではなく点検の対象として 扱ってほしい」という枠を明示して、この制約を乗り切った。
    取るべき行動 自社が同種の事案に遭ったときの公表の型を用意する。 「確定できないこと」と「その理由」を先に書き、 受け手が自力で完結できる点検手順を列挙する構成にする。 件数が出せないことを理由に公表を遅らせない。
  • 一度収まった異常を終息と判断しない
    8月29日8時50分に迂回はいったん止まったが、 同日20時ごろに第二波が始まり10時間続いた。 経路が完全に撤回されたのは8月30日6時10分ごろである。
    取るべき行動 事象の終息判定の基準を、症状の消失ではなく 原因の除去の確認に置く。経路事案なら「不正な広告の撤回を 外部の観測点で確認したこと」を終息条件として手順に書く。
セキュリティ技術者への示唆
  • 更新の取得元が正規ドメイン・正規証明書であっても、中身の真正性は別問題として検証する
    本事案では利用者側から見て接続先も証明書も正規のものであり、 警告は一切出なかった。判別する手段は受け取ったパッケージの 署名検証以外に存在しなかった。
    取るべき行動 自動更新を有効にしている製品を洗い出し、 その製品が更新パッケージの署名を検証しているかをベンダーに確認する。 検証していない製品は自動更新を切り、更新のたびに 公開されたハッシュと突き合わせる運用へ切り替える。
  • 自社ドメインに対する証明書の発行を証明書透明性ログで監視する
    攻撃者は Let's Encrypt から29ドメイン分の有効な証明書を取得した。 発行そのものは証明書透明性ログに記録されるため、 監視していれば発行の時点で異常に気づく機会があった。
    取るべき行動 自社の全ドメインについて証明書透明性ログの監視を設定し、 未承認の発行を検知したら通知が飛ぶようにする。 あわせて DNS の CAA レコードで発行できる認証局を限定する （設定前に、実際に使っている認証局をすべて棚卸しすること）。
  • Virtualizor を運用しているなら、痕跡の有無にかかわらず点検の全項目を実施する
    ベンダー側にログが無く、影響を受けたサーバの確定的な一覧が存在しない。 「連絡が来ていないから対象外」という推論が成り立たない。
    取るべき行動 /etc/systemd/system/java-jre-update.service の有無を確認し、 あれば削除せず Softaculous へ連絡する。Virtualizor の API 認証情報を更新してアクセス元を信頼できる IP に限定し、 未承認の SSH 鍵・アカウント・スケジュールタスク・外向き接続を監査し、 顧客エリアの API キーを再生成する。Virtualizor 3.2.9.9 へ更新する。
  • 自社が広告する範囲について経路の登録を出し、上流と自社の双方で起源検証を有効にする
    攻撃者は Hetzner の通常の広告より細かい範囲を広告することで 経路選択の優先順位を奪った。経路の起源を暗号的に検証する仕組みは、 この型の広告を弾きうる。
    取るべき行動 自社が保有する IP アドレス範囲について地域インターネットレジストリで 経路の登録（ROA）を作成し、上流の通信事業者が起源検証を 有効にしているかを契約担当経由で確認する。 自社のルータ側でも検証を有効にする。
