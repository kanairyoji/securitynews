INC-2026-0076METR、エージェントから API キー流出

AI 評価機関 METR で「エージェントに直接聞けば秘密を教えてくれる」侵入が成立した——研究者個人の EC2 上に置かれた法人の API キーが、認証が静かに無効化された自作ダッシュボードから抜かれ、3週間で約60万ドル相当の推論枠が消費された

不正アクセス・侵害意図せぬ露出（設定不備等で外部から到達可能だった）続報が止まり調査も完了有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）権限管理の不備
初報: 2026年8月31日 最終更新: 2026年9月1日

フロンティア AI モデルの能力を評価する非営利研究機関 METR
（Model Evaluation and Threat Research）は2026年8月31日、
2026年に起きた2件の重大なセキュリティ事案を自ら公表しました。

1件目は2026年3月です。同機関の研究者が、意図的に外部公開した個人の
Amazon EC2 インスタンス上でエージェントを動かしていました。
公開範囲は Google 認証で守るつもりでしたが、その「バイブコーディングされた」
自作アプリに、認証を静かに無効化してしまう不具合
（原文では fail-open、認証に失敗したときに通してしまう作り）があり、
エージェント制御用のダッシュボードが数日間インターネットへ露出しました。
このインスタンスには METR の一般アクセス用（公開モデル用）アカウントの
API キーが置かれていました。攻撃者はエージェントに直接プロンプトを与えて
モデル提供事業者の API キーを明かさせ、永続化のために SSH 鍵を追加し、
そのキーで3週間にわたって公開モデルの推論枠を大量に消費しました。
METR は、この消費が請求されていれば約60万ドルに相当したとしています
（枠はモデル提供事業者から無償で提供されていたため、
同額の現金支出が生じたわけではありません）。

2件目は2026年5月です。金銭目的とみられる攻撃者が、
同機関の公開インフラを組織的に探索していました。
認証基盤へのリスト型攻撃、OAuth のトークン発行の試行、
新たに公開されたサービスの走査、職員へのフィッシングが含まれ、
脆弱性の発見自体にエージェントが多用されていたとされます。
同じころ、公開されている実行記録ビューアに読み取り専用の SQL 照会機能が
意図せず露出しており、不具合を突けば未公開の評価データに届きえた状態でした。
外部の研究者からの届出で判明し、METR は当該機能を停止しています。

日本の読者にとっての読みどころは、秘密が「保管場所」からではなく
「それを扱うエージェント」から漏れたという点にあります。
攻撃者はコードを読まず、脆弱性を突かず、ただエージェントに聞きました。
本記録は、METR が公表した事実と、本記録の作成者による評価を分けて整理します。

METR が公表した事実は次のとおりである。2026年3月、機微なアクセス権を持たない
研究者が、意図的に外部公開した個人の Amazon EC2 インスタンス上で
エージェントを動かしていた。公開範囲は Google 認証で守る想定だったが、
その自作アプリに認証を静かに無効化する不具合があり、
エージェント制御用のダッシュボードが数日間インターネットへ露出した。
インスタンスには METR の一般アクセス用アカウントの API キーが置かれていた。

攻撃者はこのダッシュボードを見つけると、
エージェントに直接プロンプトを与えて、モデル提供事業者の
API キーを明かさせた。あわせて永続的なアクセスのため SSH 鍵を追加した。
そして、そのキーで3週間にわたって公開モデルの推論枠を消費した。
請求されていれば約60万ドルに相当する量である。

本記録の評価として、この事案の中心はこの一手にある。
攻撃者はソースコードを読んでいない。既知の脆弱性を突いてもいない。
認証が外れていたダッシュボードに入り、エージェントに聞いただけである。
エージェントは、自分が持っている秘密を、頼まれれば読み上げる。
それは不具合ではなく、指示に従うという設計そのものの帰結である。

この構図は、秘密の保管に関する従来の考え方と噛み合わない。
これまで「鍵をコードに直書きしない」「秘密管理サービスから取る」
という対策が説かれてきたが、いずれも
「鍵を読み取れるのは正規のプロセスだけ」という前提に立っている。
エージェントは正規のプロセスであり、かつ
外部から自然言語で操作できる正規のプロセスである。
鍵をエージェントの手が届く場所に置いた時点で、
エージェントに到達できる者は鍵に到達できる。

3週間気づけなかった理由は「正規の利用が常に大量だった」ことにある発覚の端緒出典 [1] [2] [3]

METR は、不正な使用に直ちに気づけなかった理由を三つ挙げている。
第一に、同機関は大規模な評価・実験を日常的に行っており、
大量のトークン消費が平常状態だった。
第二に、監視用のダッシュボードが速度制限を受けた要求のデータを
表示していなかった。
第三に、この種のキーに消費上限を設ける手段が無かった。

本記録の評価として、第一の点は多くの組織にそのまま当てはまる。
異常検知は「平常」が定義できて初めて成り立つ。
利用量が本来的に大きく振れる業務では、量そのものを閾値にできない。
この場合に有効なのは、量ではなく形の変化を見ることである——
呼び出し元の IP・地域の分布、利用されるモデルの種類、
時間帯の分布、要求の間隔。これらは正規の評価バッチと
第三者の転用とで異なりうる。

第三の点、すなわち消費上限を設けられなかったことは、
無償提供の枠に固有の問題である。請求が発生しないため、
課金側の異常検知も、予算超過のアラートも働かない。
無償の枠・試用の枠・社内で融通した枠は、

緩和策
数え方: 法人の認証情報・データを個人所有の基盤・端末に置くことを方針で禁じ、技術的にも配布できないようにする　副作用: 研究・開発の現場では「まず動かしてみる」ための自由度が 生産性の源泉になっている。禁止だけを課すと、 承認された経路が用意されない限り、より見えにくい形で 同じことが行われる。使いやすい代替（払い出しの速い検証環境）を 同時に用意しないと機能しない　数値の出所: METR が事後に方針を明確化・拡張したと公表した対策
数え方: API キーごとに消費上限を設定する。無償・試用・社内融通の枠にも必ず上限を置く　副作用: 上限に達したときに正規のバッチ処理が止まる。 評価・学習のような長時間の処理では、途中で止まると やり直しになる場合があり、上限値の設計には 業務側との調整が要る　数値の出所: METR が「当該キーに消費上限を設ける手段が無かった」と述べた点に基づく本記録の整理
数え方: エージェントが読み取れる範囲に長期有効な秘密を置かず、短命の資格情報を実行時に外部から注入する　副作用: 資格情報の発行・更新の仕組みを別途運用する必要があり、 その仕組み自体が新たな単一障害点になる。 短命化すると、長時間実行される処理の途中で失効する問題が生じる　数値の出所: エージェントに直接プロンプトを与えて鍵を明かさせた手口に基づく本記録の整理

数え方: 消費量ではなく、呼び出し元の IP・地域・モデル種別・時間帯の分布の変化を異常検知の指標にする　副作用: 分布の監視は量の閾値より設計と維持の手間が大きく、 正規の利用形態が変わるたびに基準の作り直しが要る。 誤検知が続くと運用側が見なくなる　数値の出所: 大量消費が平常状態で量による検知が働かなかった経緯に基づく本記録の整理
