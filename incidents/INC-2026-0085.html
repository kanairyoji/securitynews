INC-2026-0085Dropbox、Lenovo ID 連携で乗っ取られる

Dropbox は Lenovo が「このメールアドレスの持ち主だ」と言えばパスワードを求めずに扉を開けていた——Lenovo 側のメール検証の不備で他人のメールアドレスの Lenovo ID を作れたため、約5,000アカウントが乗っ取られた

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因
初報: 2026年9月2日 最終更新: 2026年9月5日

Dropbox は2026年9月上旬、約5,000名の利用者に対し、
Lenovo ID で Dropbox にログインできる旧来の連携を悪用され、

不正アクセスの期間は2026年8月4日から8月21日です。

結果として、攻撃者は Dropbox のパスワードを一度も入力せずに、

「壊れたのはコードではなく、信頼の前提だった」という点にある。

ID フェデレーションは、認証を他所に委ねる仕組みである。
委ねる側（Dropbox）は、委ねられる側（Lenovo）が
「このメールアドレスの持ち主である」ことを
どれだけ厳密に確かめているかを、技術的に検証できない。
Lenovo が「確認した」と言えば、Dropbox はそれを信じるしかない。
これは仕組みの欠陥ではなく、仕組みの前提である。

問題は、Dropbox がその前提に何も足していなかったことである。
BleepingComputer は
「Dropbox の ID 紐づけの処理は、攻撃者がそのメールアドレスを
支配しているという Lenovo の主張を、
既存の Dropbox のログイン手段による確認を求めずに信頼した」
と書いている（原文英語）。

ここに一つ、本件を象徴する利用者の証言がある。
ある利用者は「当時おかしなことが一つあった。
Lenovo ID を作った覚えは無いのに、Dropbox のログイン画面が
自分のメールアドレスに対して『Continue with SSO』を
出すようになっていた」と述べている（原文英語）。
攻撃者が他人のメールアドレスで ID を作った瞬間、
被害者のログイン画面の見え方が変わっていた。
これは異常の兆候として画面に出ていたが、
利用者にはその意味が分からなかった。

実務的な結論は、外部 ID プロバイダを信頼するときの
足し算にある。他所の ID で既存アカウントに入れるとき、
少なくとも一度は自社側の認証（パスワードまたは二要素）で
本人であることを確認する。
これは Dropbox が事後に追加した対策そのものである——
Lenovo ID で認証する際に Dropbox のパスワード入力を必須にした。
事故の後に入れられる対策は、事故の前にも入れられた。

二要素認証を有効にしていたアカウントは、一つも被害に入っていない被害規模・影響範囲出典 [1] [2] [4]

Dropbox は Reuters に対し、
影響を受けたアカウントはいずれも二要素認証を
有効にしていなかったと述べたとされる。

本記録の評価として、この一文が本件でいちばん実用的である。

本件の攻撃は、Dropbox のパスワードを迂回した。
パスワードが強いか弱いか、使い回しているかどうかは無関係だった。
パスワードという層が丸ごと飛ばされている。
その状況で残った唯一の壁が二要素認証だった。

ただし、この 0 という数字の読み方には注意が要る。
二要素認証を有効にしていたアカウントに対して攻撃が試みられ、
そこで止まったのか。それとも、
そもそも対象の選び方の段階で外れていたのか。
Dropbox は説明していない。
本記録は「二要素認証の有無が被害の成否を分けた」ことを
強く示唆する材料として扱い、証明されたとは書かない。

被害の広がりについては、報道間で表現が異なる。
The Register は Dropbox が Bloomberg に
「影響を受けた利用者の3分の1未満のファイルにアクセスがあった」と
述べたと報じ、9to5Mac は「約1,500アカウントから
ファイルがダウンロードされた」としている。
5,000の3分の1は約1,667であり、両者はおおむね整合する。
ただし「参照された」と「ダウンロードされた」は別の事象であり、
それを区別した値は確認できていない。

なお、Bitcoin セキュリティ企業 Casa の共同創業者は、
攻撃者が自身の "IMPORTANT.rtf" という1ファイルのみに
アクセスを試み、そのファイルはアップロード前に
ローカルで暗号化されていたと述べている。
これは個人の証言であり Dropbox の確認は無いが、
クラウドに置く前に自分で暗号化しておくという習慣が
機能した例として記録しておく価値がある（本記録の整理）。

使っていない連携が、使われないまま扉として残っていた評価・解釈出典 [1] [2]

Lenovo は本件について
「Lenovo ID と Dropbox の間のレガシーな連携に関するもので、
特定の Dropbox アカウントを不適切に認証させるために
利用され得た」と説明している（原文英語）。

注目すべきは、影響を受けた利用者の一部は
Lenovo アカウントを持っていなかったことである。
BleepingComputer はこれを明記している。
つまり、当該の利用者にとって Lenovo ID 連携は
「使っていない機能」だった。使っていないのに、
その経路から入られている。

本記録の評価として、ここが本件の一般化できる部分である。

SaaS のサードパーティ・ログイン連携は、増えはするが減らない。
提携が始まったときに有効化され、提携の実態が薄れても
設定は残る。連携を切ると既存利用者がログインできなくなる恐れがあるため、
「念のため残す」判断が積み重なる。
その一つひとつが、外部の ID プロバイダの
本人確認の強度に自社の安全を委ねる経路である。

日本企業が今日できることは、棚卸しである。
自社が管理者として運用している SaaS（グループウェア、
ストレージ、CRM、人事、経費）の管理コンソールを開き、
有効になっているサードパーティ・ログイン連携の一覧を出す。
ソーシャルログイン、メーカーID、旧来の提携先の SSO が
有効なまま残っていないかを確認する。

確認の観点は三つある。

第一に、使っていない連携を無効化する。
使用実績（過去90日のログイン件数）を出せるなら、
ゼロのものから切る。

第二に、残す連携については「その ID プロバイダの
メール所有確認をどれだけ信じるか」を明示的に決める。
信じきれないなら、自社側の認証を一段足す
（Dropbox が事後に入れた対策がこれである）。

第三に、組織として使う SaaS では SSO を強制し、
個別のソーシャルログインを塞ぐ。
経路を1本にすれば、信頼の前提も1つで済む。

加えて、全アカウントでの多要素認証の必須化である。
本件で被害に遭ったアカウントは、いずれも
二要素認証を有効にしていなかった。

Dropbox の対応そのものは速い。
Lenovo ID 経由で認証された全セッションを失効させ、
該当アカウントと Lenovo の紐づけを断ち、
Lenovo ID による認証時に Dropbox のパスワード入力を必須にした。
影響を受けた利用者へ通知し、Dropbox と個人メールの
パスワード変更、二要素認証の有効化を推奨している。
データ保護当局へ報告したともされる。

一方で、本記録の作成者が確認した範囲では、
Dropbox は本件について公開の告知ページを出していない。
本記録が依拠した事実は、影響を受けた利用者への通知メールの
引用と、Dropbox・Lenovo が報道機関へ行った説明である。
規模（約5,000）は Reuters へ、ファイルへのアクセス範囲は
Bloomberg へ、それぞれ別に語られている。

本記録の評価として、この形には二つの問題がある。

第一に、影響を受けていない利用者が判断できない。
通知が来ていない利用者は、自分が対象外なのか、
通知が届いていないだけなのかを確かめる手段がない。
公開の告知ページがあれば、そこに
「対象者には個別に通知しています」と書ける。

第二に、同じ ID プロバイダを信頼している他のサービスが
動く契機にならない。Lenovo Identity Provider Services を
使っているのが Dropbox だけとは限らない。
検証処理の不備の内容が公表されていないため、
他のサービスは自分たちが同じ影響を受けたかを判断できない。

国内の読者にとっての含意は、自社が事故を公表するときの形にある。
個別通知と公開告知は役割が違う。
個別通知は「あなたが対象です」と伝えるもので、
公開告知は「これが起きた、対象者にはこう連絡している」と
全体に示すものである。前者だけを行うと、
対象外の利用者と、同じ構造を持つ他社が置き去りになる。

対応の評価

判断評価評価の根拠と留保
Lenovo ID 経由で認証された全セッションを失効させ、 影響を受けたアカウントと Lenovo の紐づけを断った。 そのうえで、Lenovo ID による認証時に Dropbox アカウントのパスワード入力を必須とする要件を追加した機能した本記録の作成者の評価である。 「不正に作られた Lenovo ID を特定して止める」のではなく、 Lenovo ID 経由のセッションを全部失効させ、 紐づけそのものを断っている。 経路が信頼できないと分かった時点で、 その経路を丸ごと閉じる判断は妥当である。 パスワード必須化は、**信頼の前提に自社側の確認を足す** という本件の本質的な修正になっている。
影響を受けた利用者へ個別に通知し、規模（約5,000）を Reuters に、ファイルへのアクセス範囲を Bloomberg に それぞれ説明した。**本記録の作成者が確認した範囲では、 公開の告知ページは出していない。** Lenovo 側の検証処理の不備の具体的な内容、 連携がなぜパスワードなしのログインを許す設計だったかも 説明していない不十分本記録の作成者の評価である。個別通知の内容自体は 具体的で（原因・期間・推奨される行動が書かれている）、 通知としては十分である。 一方、**公開の告知が無いため、通知が来ていない利用者は 自分が対象外なのか通知が届いていないだけなのかを 確かめられない。** また、The Register が明記するとおり 「なぜこの連携がパスワードなしのアクセスを許したのか」を Dropbox は説明していない。 同じ構造を持つ他のサービスが自らを点検する材料が 提供されていない点で、不十分と評価する。
影響を受けた利用者へメールで個別に通知し、 Dropbox と個人メールのパスワード変更、 二要素認証の有効化を推奨した部分的に機能本記録の作成者の評価である。 原因と期間と推奨行動が書かれた通知は実用的である。 **一方、本件はまさに利用者のメールアドレスが 攻撃の起点になった事案である。** 「個人メールのパスワードも変えるように」と 推奨している点は的確だが、 公開の告知ページがあれば、利用者は通知メールが 本物かどうかを照合できた。 個別通知だけの構成は、なりすましメールに つけ込まれる余地を残す。
CISO・経営層への示唆
  • SaaS のサードパーティ・ログイン連携を棚卸しし、使っていないものを無効化する
    本件で悪用されたのは Lenovo ID と Dropbox の レガシーな連携であり、影響を受けた利用者の一部は Lenovo アカウントを持っていなかった。 使っていない機能が扉として残っていた。
    取るべき行動 自社が管理者として運用している SaaS の管理コンソールで、 有効になっているサードパーティ・ログイン連携の一覧を出す。 使用実績（過去90日のログイン件数）を確認し、 ゼロのものから無効化する。残すものについては、 「その ID プロバイダのメール所有確認をどれだけ信じるか」を 文書として明示的に決める。
  • 組織で使う SaaS は SSO を1本に強制し、信頼する ID プロバイダの数を減らす
    ID フェデレーションでは、信頼する側は信頼される側の 本人確認の強度を検証できない。 信頼する ID プロバイダの数だけ、 検証できない前提が増える。
    取るべき行動 主要な SaaS で SSO を強制し、 個別のソーシャルログイン・メーカーID連携を 管理者設定で塞ぐ。あわせて、IdP が単一障害点になるため、 緊急用の管理者アカウントと IdP 障害時の復旧手順を 別途用意しておく。
  • 全アカウントでの多要素認証の必須化を、期限を切って進める
    本件の攻撃はパスワードの層を丸ごと迂回した。 その状況で残った壁が二要素認証であり、 影響を受けたアカウントはいずれも 二要素認証を有効にしていなかった。
    取るべき行動 自社が使う SaaS で多要素認証の必須化を管理者設定で有効にし、 期限を切って全アカウントに適用する。 当面できないサービスについては、 未設定のアカウントに機微な操作（一括ダウンロード・ 共有リンクの作成・管理者権限）を許さない設定にする。
  • 事故の通知は「個別通知」と「公開告知」を両方出す
    本記録の作成者が確認した範囲では、Dropbox は 影響を受けた利用者への個別通知は行ったが、 公開の告知ページを出していない。 通知が来ていない利用者は自分の状況を確かめられず、 同じ ID プロバイダを信頼する他社も動く契機を得られない。
    取るべき行動 自社の事故公表の手順に「個別通知と同時に公開告知を出す」を 入れる。公開告知には、対象者への連絡方法と、 「当社は本件についてメールでパスワードや決済情報を尋ねません」 という一文を必ず含める。利用者が通知メールの真偽を 照合できる先を用意することが目的である。
セキュリティ技術者への示唆
  • 外部 ID プロバイダの「このメールアドレスの持ち主だ」という主張を、そのまま既存アカウントへの入場券にしない
    Dropbox は Lenovo の主張を、既存の Dropbox のログイン手段による 確認を求めずに信頼した。結果として、 Dropbox のパスワードを入力せずに他人のアカウントへ入れた。
    取るべき行動 自社サービスで外部 ID による既存アカウントへの ログイン（アカウントリンク）を実装している場合、 **初回のリンク時に自社側の認証（パスワードまたは二要素）を 必ず要求する**設計に変える。 「同じメールアドレスだから同一人物」という前提を コードから外す。
  • 自社を ID プロバイダとして提供している場合、メール所有確認を迂回できる経路が無いか点検する
    本件の起点は Lenovo 側のメールアドレス検証処理の不備であり、 攻撃者は他人のメールアドレスで Lenovo ID を登録できた。 検証の不備は、信頼している側の全サービスに波及する。
    取るべき行動 ID の新規登録・メールアドレスの変更・アカウントの 復旧の3経路それぞれについて、 「確認用リンクまたはコードの到達と入力を経ずに メールアドレスが有効化される経路」が無いかを点検する。 管理者による手動作成、一括インポート、 旧システムからの移行データが典型的な抜け道になる。
  • 「不審なサインイン」通知は、個別の利用者への連絡で終わらせず、事象として集計する
    複数の利用者が Dropbox から不審なサインインの通知を受け取り、 自らパスワードを変更していた。検知は動いていたが、 連携そのものを止める判断につながるまで 不正アクセスは約2週間続いた（本記録の読み）。
    取るべき行動 不審なサインイン通知の発生件数を利用者単位ではなく 全体で集計し、平常時の発生率からの逸脱を アラート条件にする。**同じ認証経路（同じ IdP、 同じ連携）に偏って発生している場合を特に検知条件に入れる。**
  • 新しい認証経路からのログイン直後の大量ダウンロードを検知条件にする
    本件では3分の1未満のアカウントでファイルが 参照・ダウンロードされた。 Dropbox がこれをリアルタイムに検知したという記述は無い。
    取るべき行動 ログイン後の一定時間内のダウンロード量・件数について、 当該アカウントの平常値からの逸脱をアラート条件にする。 特に、初めて使われた認証経路・初めての端末からの ログイン直後は、しきい値を下げる。
