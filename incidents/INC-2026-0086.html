INC-2026-0086VOISINGのBIツールから顧客情報流出

VOISINGが社内で使うBIツールが破られ、アカウント・ファンコミュニティ・オンラインストアの全顧客（最大約17万人）の氏名・住所・購買履歴・「推し」の情報が持ち出された——侵入から窃取まで6日、窃取から把握まで3時間半、公表の4日後には一部がSNSと特定サイトで公開されていた

不正アクセス・侵害続報が続いている日本の組織が当事者既知の脆弱性の悪用公表されていない／不明
初報: 2026年8月18日 最終更新: 2026年8月24日

2.5次元アイドルグループ「いれいす」などの事務所を運営する
株式会社VOISING（東京都港区）は2026年8月18日、
同社が社内で利用しているBIツール（ビジネスインテリジェンスツール）が
外部からの不正アクセスを受け、ツール内に保管されていた顧客の個人情報が
不正に取得（ダウンロード）されたと公表しました。

同社の公表によれば、不正アクセスは8月10日1時2分ごろに始まり、
8月16日18時47分から20時21分にかけてデータがダウンロードされました。
同社は同日23時55分に事態を確認し、翌17日1時55分までにシステムの停止と
ネットワークからの遮断を終えています。
対象は、アカウントサービス「VOISING ID」・ファンコミュニティ「VOISING CONNECT」・
「VOISING ONLINE STORE」・ファンクラブ「いれらぶ」・旧アカウント・旧オンラインストアを
利用した全ての顧客（退会者・休眠者を含む）で、8月20日の第二報では
対象人数の最大値を約17万人（精査途中の暫定値）としています。
項目は氏名・住所・電話番号・メールアドレス・生年月日・性別・購買履歴・
決済金額記録・サービス加入状況・応援対象タレント（推し）の選択情報です。
クレジットカード番号・口座情報・パスワードは当該システムに保持しておらず、
漏えいしていないとしています。

同社は不正アクセスの原因とみられる脆弱性に修正プログラムを適用し、
関連するすべてのパスワード・アクセスキーを無効化・変更したうえで、
所轄警察署への通報と個人情報保護委員会への速報の提出を済ませ、
8月18日12時ごろから対象者へ個別のメールを送っています。
さらに8月24日の第三報で、外部の専門機関と連携した監視により、
8月22日にSNS上で10件、8月23日に特定サイト上で約5万件（可能性）の
本件関連データの公開を検知したと公表しました。

この事案の要点は、破られたのが顧客向けのサービスそのものではなく、
その裏側で全サービスの顧客データが1か所に集まっていたBIツールだった
ことにあります（本記録の評価）。BIツールの製品名・提供形態・脆弱性の内容は
いずれも公表されていません。

同社が公表した事実は次のとおりである。

2026年8月10日1時2分ごろから、同社が利用するBIツール
（ビジネスインテリジェンスツール）に対する外部からの不正アクセスが開始され、
8月16日18時47分から20時21分にかけて、同ツール内に保管されていたデータが
不正に取得（ダウンロード）された。同社は「現時点で不正アクセスの原因とみられる
脆弱性に対する修正プログラムの適用、および関連するすべてのパスワード・
アクセスキーの無効化・変更を完了」したとしている。
製品名・脆弱性の内容は公表されていない。

本記録の評価として、この事案の構図は
「顧客が触るシステムは破られていないのに、顧客の全データが出た」という点にある。
VOISING ID・VOISING CONNECT・VOISING ONLINE STORE・ファンクラブ・
旧ストアという複数のサービスの顧客データが、分析のために
BIツールという1か所に集約されていた。攻撃者はサービスを一つずつ破る必要がなく、
集約先を1回破れば全部に到達できた。

BIツールは、業務上の性質として全社のデータを読み出す権限を持つ。
各サービスのデータベースへの接続資格情報を内部に保持し、
分析者が問い合わせを投げれば生データを返す。
その機能をそのまま攻撃者が使った形である（本記録の読み。
同社は持ち出しの手段を公表していない）。

同種の構図は、2026年8月に公表された BI プラットフォーム Metabase の
ゼロデイ悪用事案（INC-2026-0009）でも見られた。Metabase では
攻撃者が顧客インスタンスの管理者権限を得て、接続先データベースの
資格情報の窃取とデータのエクスポートに至っている。
ただし本件のBIツールが Metabase であるとは公表されておらず、
本記録は「BIツール経由という構図が同じ」という以上の関連付けをしない。

対策の方向は、BIツールを「分析の道具」ではなく
「全顧客データへの入口」として資産台帳・脆弱性管理・監視の対象に置く
ことである。BIツールは情報システム部門ではなくマーケティングや事業部門が
導入することが多く、パッチ適用の責任者が曖昧になりやすい（本記録の一般的な整理）。

    取るべき行動 自社で使っているBI・分析・ダッシュボード製品（事業部門が導入したものを含む）を 洗い出し、それぞれについて「どのデータベースにどの権限で接続しているか」 「どこから到達できるか」「誰がパッチを当てる責任者か」の3列を埋める。 埋まらない行を最優先で是正する。
  • 分析基盤に置く顧客データは、項目と保持期間を絞る
    本件では退会者・休眠者を含む全顧客の氏名・住所・電話番号・生年月日が 分析基盤にそのまま保管されていた。置いてある分だけが被害の対象になる。
    取るべき行動 分析に生の識別子（氏名・住所・電話番号・生年月日）が本当に必要かを 業務部門と確認し、不要なら仮名化・丸めを義務づける。 退会者・休眠者のデータは分析基盤から一定期間で削除し、 サービス側の退会処理と連動させる規程を置く。
  • 件数が分からなくても、対象の定義と項目が示せれば公表する
    同社は把握の2日後に、件数を「調査中」としたまま「以下のサービスを利用した 全てのお客様」と対象を定義して公表し、同日から個別メールを送った。 4日後には実際にデータの公開が起きており、待っていれば自衛が遅れていた。
    取るべき行動 事故公表の手順書に「件数の確定を公表の条件にしない」と明記し、 対象を「サービス単位」「期間単位」で定義できるよう、 各サービスの顧客母集団を平時から把握しておく。 暫定値を出すときは本件のように「精査途中の暫定的な数値」と明記する。

    同社は外部専門機関と連携してSNS・特定サイトを監視し、 公開を検知した8月22日・23日の翌日に第三報で件数・項目を公表した。 対象者にとって「既に出回っているか」は自衛の強度を決める情報である。

  • 製品名と脆弱性を公表するかを、再発防止策の公表時に判断する
    同社はBIツールの製品名・脆弱性を公表していない。 同じ製品を使う他社が自社のパッチ状況を確認する手がかりが無い。
    取るべき行動 自社が被害に遭った場合の公表方針として、調査完了後に 「製品名・脆弱性の識別子（CVE）・修正版の有無」を公表するかを あらかじめ決めておく。提供元との契約に、脆弱性の公表に関する 取り扱いを入れておく。
セキュリティ技術者への示唆
  • BIツールの管理画面・API をインターネットに直接公開しない
    本件では外部からBIツールへの不正アクセスが開始された。 BIツールは全社のデータベースへの接続資格情報を内部に持つため、 外部から到達できる状態は、全データベースが外部から到達できる状態に近い。
    取るべき行動 BIツールの到達経路を確認し、VPN・IP制限・IdP 経由の認証（SSO＋多要素）の 後ろに置く。埋め込みダッシュボードを外部に公開している場合は、 公開用の別インスタンスに分け、顧客の個票を持たない集計データだけを渡す。
  • BIツールの脆弱性情報を購読し、修正版の適用を期限つきで運用する
    同社は「原因とみられる脆弱性に対する修正プログラムの適用」を行った。 修正プログラムが侵入時点で提供済みだったかは公表されていないが、 BI製品は SQL インジェクション・認可欠如の脆弱性が繰り返し公表されている （2026年8〜9月の Metabase の例）。
    取るべき行動 使用中のBI製品のセキュリティアドバイザリ（GitHub Security Advisories・ ベンダーのブログ・JVN/KEV）を購読し、Critical は N 日以内に適用する 期限を定める。自社ホストの場合はバージョンを台帳に記録し、 月次で最新版との差を確認する。
  • 分析基盤への取り込み時に仮名化・項目削減を行い、接続資格情報は読み取り専用・最小範囲にする
    本件では氏名・住所・電話番号・生年月日・購買履歴・推しの情報が 生のまま分析基盤にあり、そのまま持ち出された。 決済情報とパスワードは置いていなかったため漏れていない—— 置かなければ漏れないことを同社自身が示している。
    取るべき行動 ETL/ELT の段階で氏名・住所・電話番号・生年月日を仮名化または丸め、 分析に必要な粒度（年代・都道府県）だけを残す。 BIツールがデータベースに接続するアカウントは読み取り専用で、 分析に必要なビュー・スキーマだけに権限を絞る。
  • 大量エクスポートを検知して自動でセッションを切る
    本件のダウンロードは18時47分から20時21分まで94分間続き、 同社が把握したのは終了の3時間34分後である。 進行中に止められていれば持ち出し量は減っていた（本記録の読み）。
    取るべき行動 BIツールの監査ログ（問い合わせ・エクスポート・API呼び出し）を SIEM に集約し、 「1セッションで N 行以上のエクスポート」「深夜・休日の全件問い合わせ」を アラート条件にして、閾値超過時にトークンを自動失効させる。 BIツール自体に行数上限やエクスポート権限の設定があれば有効にする。
  • 侵害されたツールの内部にあった鍵はすべて漏れたと見なして作り直す
    同社は「関連するすべてのパスワード・アクセスキーの無効化・変更」を行った。 BIツールは接続先データベースの資格情報を内部に保持するため、 ツールが侵害されればその鍵も漏れたと見なすのが妥当である。
    取るべき行動 BIツールが保持している接続資格情報・APIキー・サービスアカウントを 平時から一覧にしておき、侵害時にすべてを一括で失効・再発行できる 手順とスクリプトを用意する。鍵の一覧が無いと「すべて」を作り直せない。
