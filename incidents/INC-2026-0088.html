INC-2026-0088イノベーションのGitHubから6.3万名分流出

「ITトレンド」運営のイノベーションで、設定ファイルに直書きされた GitHub の認証情報が第三者に使われ、リポジトリに置かれていた顧客62,689名分の氏名・メールアドレスが流出した——同社は原因を「認証情報のハードコーディング」と「個人情報のリポジトリ保存」という独立した2つの問題に分け、3日後の確定報で件数を確定し、さらに3日後に件数を2名分訂正した

不正アクセス・侵害続報が続いている日本の組織が当事者認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備
初報: 2026年8月4日 最終更新: 2026年8月10日

法人向け IT 製品の比較・資料請求サイト「ITトレンド」などを運営する
株式会社イノベーション（東京都渋谷区）は2026年8月4日、
同社グループがソフトウェア開発とシステム管理に利用している GitHub の認証情報が漏えいし、
これを用いた第三者による不正アクセスが発生したと公表しました（速報）。
ソースコードのほか、リポジトリ内のファイルに記載されていた個人情報の一部が
流出した可能性があり、速報時点の対象は最大約60,000件の氏名・メールアドレス
（一部は電話番号を含む）でした。

8月7日の確定報で、同社は漏えいが確認された件数を62,691名分
（氏名62,631件・メールアドレス62,691件・電話番号506件）とし、
原因を次の独立した2つの問題として説明しています。
①社内の開発システムの一部で、GitHub にアクセスするための認証情報が
プログラムの設定ファイル内に直接記載された状態で運用されており、
これを第三者が不正に取得して悪用した。
②本来データベース等でのみ保管すべき個人情報が、社内の分析・開発作業の過程で
GitHub 上のリポジトリ内にも保存されていた。
顧客情報を格納する本番データベースへの不正アクセスや本番環境からの漏えいは
確認されておらず、流出はリポジトリに含まれていたものに限定されるとしています。
8月10日には件数を62,689名分（メールアドレス62,689件）に訂正しました。
訂正の理由は、調査結果を社内で集計・共有する過程での記載誤りです。

対策として、悪用された認証情報（アクセストークン）の無効化、トークンの権限と
発行ワークフローの見直し、レビュールールの強化、リポジトリへのアクセス監視の強化、
個人情報をリポジトリに保存しない運用ルールへの見直しと既存リポジトリの点検、
個人情報のアップロードを検知する仕組みの導入を実施済みとしています。

この事案の要点は、GitHub のトークン1本で「ソースコード内の本番の鍵」と
「リポジトリに混入した顧客情報」の両方に到達できたこと、そして同社が
その2つを別の問題として切り分けて対策を示したことにあります（本記録の評価）。
認証情報がどのように第三者の手に渡ったか、不正アクセスの時期、
どのサービスの顧客が対象かは公表されていません。

公表されていない・確定していないこと6
  • 設定ファイルに直接記載されていた認証情報が、どのように第三者の手に渡ったか公表されていない
    確定報は「この認証情報を第三者が不正に取得し、悪用した」と述べるが、 取得の経路（公開リポジトリへの誤コミット、端末のマルウェア感染、別の侵害からの横展開、 退職者・委託先からの持ち出し等）は示していない。「設定ファイル内に直接記載」は **漏れやすい置き方**の説明であり、**漏れた経路**の説明ではない（本記録の読み）。 同じ置き方をしている他社にとって、経路は自社への当てはめを左右する最も重要な情報である
  • 不正アクセスの発生時期・期間と、同社が判明した日時・手段公表されていない
    速報は「判明しました」とのみ述べ、不正アクセスがいつ始まり、いつまで続き、 何によって気づいたか（GitHub の通知・監査ログ・外部からの連絡）を示していない。 滞留期間が分からないため、検知の速さは評価できない
  • 対象となった顧客がどのサービス（ITトレンド等）の利用者か公表されていない
    同社は「当社が保有するお客様情報」とのみ述べ、サービス名を示していない。 ITmedia の問い合わせにも「詳細な事実関係が確定していない」として回答を控えた。 法人向け資料請求サイトの利用者であれば企業の担当者名とメールアドレスであり、 標的型メールの名簿になり得る（本記録の推定）
  • 流出したソースコードの範囲と、ソースコード内に含まれていた認証キー・パスワードの用途公表されていない
    速報は「ソースコードに含まれる各種認証キー・パスワードの無効化と再発行」を 概ね完了したとしており、ソースコード内に本番系の鍵があったことを示唆する。 どのシステムの鍵か、その鍵で到達できた範囲、鍵が実際に使われた形跡の有無は公表されていない
  • 個別連絡の実施状況と、連絡先を把握していない対象者の扱い公表されていない
    確定報は「当社でご連絡先を把握している方には、個別にご連絡を実施」とし、 把握していない対象者の人数や公表による周知の扱いを示していない
  • 個人情報保護委員会への確定報告の内容調査中
    同社は確定報告を「期限内に提出する予定」としている。提出の有無・内容は公表されていない

設定ファイルに直書きされた GitHub の認証情報1本が、ソースコードと顧客情報の両方への入口になった原因・手口出典 [1] [2]

同社が確定報で示した原因は次の2点である。

  1. 認証情報の管理方法に不備があったこと——社内の開発システムの一部において、
    外部サービス（GitHub）にアクセスするための認証情報が、プログラムの設定ファイル内に
    直接記載された状態で運用されていた。この認証情報を第三者が不正に取得し、悪用したことが
    今回の不正アクセスの直接の原因だった。
  2. 個人情報がリポジトリ内に保存されていたこと——本来は厳重に管理されたデータベース等で
    のみ保管すべき個人情報が、社内の分析・開発作業の過程で GitHub 上のリポジトリ内にも
    保存されている状態があった。このため、1 の不正アクセスの結果、個人情報の流出につながった。

同社は「以上の2点は独立した要因であるため、後述の再発防止策につきましても、
単一の対策に頼るのではなく、それぞれに対応する形で講じております」と述べている。

本記録の評価として、この切り分けは的確である。1 だけなら流出するのはソースコードで、
2 だけなら個人情報はリポジトリの中にとどまる。両方が揃ったとき、トークン1本が
顧客情報への入口になる。さらに速報は「ソースコードに含まれる各種認証キー・パスワードの
無効化と再発行」を行ったとしており、リポジトリの中には本番系の鍵も置かれていたと読める。
つまり同社のリポジトリには「顧客情報」と「本番の鍵」の両方が入っており、
GitHub のトークンはその両方への到達点だった。

ただし、公表されていないことが一つある。認証情報がどうやって第三者の手に渡ったかである。
「設定ファイル内に直接記載」は漏れやすい置き方の説明であって、漏れた経路の説明ではない。
公開リポジトリへの誤コミットか、開発者端末のマルウェア感染か、別の侵害からの横展開か。
同じ置き方をしている他社が自社への当てはめをするには、この経路が要る。

流出はリポジトリの中のものに限られ、本番データベースは破られていない——「置いてあった分」だけが出た被害規模・影響範囲出典 [2] [3]

確定報は、対象の範囲を次のように限定している。

  • 顧客情報を格納している本番データベースへの不正アクセスは確認されていない
  • 本番環境からの情報漏えいは確認されていない
  • 個人情報の不正利用等による被害は確認されていない
  • 本件における個人情報の流出は、GitHub 上のリポジトリに含まれていたものに限定される

電話番号506件である。速報の「最大約60,000件」から確定報で62,691名分へ、訂正で62,689名分へと
推移した。訂正の理由は集計・共有過程での記載誤りで、調査範囲に誤りは無いとしている。

本記録の評価として、二点を記録する。

第一に、被害の大きさが「本番データベースの規模」ではなく「リポジトリに混入していた量」で
決まった点である。同社の顧客基盤の全体像は公表されていないが、流出はリポジトリに
置かれていた6.3万名分にとどまった。置いていなければ出なかったという意味で、
データの置き場所そのものが被害の上限を決めている。

第二に、対象の項目が氏名・メールアドレス（一部電話番号）で、法人向け IT 製品の
資料請求サイトの顧客であれば、企業の担当者名と業務用メールアドレスの名簿になる
（本記録の推定。同社はサービス名を公表していない）。クレジットカードや住所は含まれないが、
「IT 製品の資料を請求した担当者」という属性は、ベンダーを装った標的型メールの材料になり得る。

速報から3日で件数を確定し、原因と対策を論点別に公表した——さらに3日後に2名分を訂正した組織の対応出典 [1] [2] [3] [4]

同社の公表を並べると次のとおりである。

  • 8月4日: 速報。最大約60,000件、項目・件数は精査中。認証情報の無効化とアカウント遮断（完了）、
    ソースコード内の認証キー・パスワードの無効化と再発行（概ね完了）
  • 8月5日: ITmedia の取材に「詳細な事実関係が確定していない」として個別回答を控える
  • 8月7日: 確定報。62,691名分。原因2点と論点別の再発防止策。本番環境は無事。関係当局へ確定報告を予定
  • 8月10日: 訂正。62,689名分（メールアドレス2件の記載誤り）

本記録の評価として、良い点が二つある。

第一に、確定報が原因を2つに分け、それぞれに対策を対応させていることである。
国内の事故公表では「不正アクセスを受けた」「セキュリティを強化する」で終わるものが多いが、
同社は「認証情報の置き方」と「個人情報の置き場所」を別の問題として示し、
前者にはトークンの権限・発行ワークフローの統制とリポジトリのアクセス監視、
後者には運用ルールの見直しと既存リポジトリの点検、アップロード時の検知と自動チェックを
対応させた。読者が自社に当てはめる単位で書かれている。

第二に、速報時点で本番の鍵を作り直していることである。「ソースコードに含まれる各種
認証キー・パスワードの無効化と再発行」は、リポジトリが読まれた以上その中の鍵は全て
漏れたと見なす対応で、経路が分からない段階の判断として妥当である。

改善の余地として、認証情報が漏れた経路、不正アクセスの時期、対象サービスが
いずれも示されていないことを挙げる。また、確定報の3日後に件数を2名分訂正したことは、
訂正幅は小さいが「確定」と銘打った数字の集計過程に誤りがあったことを示しており、
公表前の突合の手順に課題があったと読める（本記録の読み）。

同じ日次ニュースに並んだ TVING（鍵の直書き）と VOISING（分析基盤）は、同じ場所を突かれている評価・解釈出典 [2]

ここからは本記録の作成者による整理であり、同社の公表には無い。

本件が日次ニュースに載った2026年9月3日、韓国の政府調査団は動画配信 TVING の
3,954万アカウント流出（INC-2026-0091）の原因を「ソースコード内にハードコードされた
運用環境の接続キー」と結論づけた。攻撃者は開発環境の鍵で入り、ソースコードの中の
本番の鍵を拾って利用者データベースに到達している。本件と TVING は規模が3桁違うが、
「開発用の入口 → ソースコード内の本番の鍵」という経路は同じである。

同じ日の VOISING（INC-2026-0086）は BI ツール、前日のコロナ（INC-2026-0084）は
外部クラウドと、いずれも「顧客向けの本番システムではなく、業務のために顧客データを
置いていた周辺のシステム」が破られている。本件のリポジトリもその一つである。

読者が確認すべきことは三つある。
(1) リポジトリ・設定ファイル・CI の変数に本番の認証情報が直書きされていないか
（シークレットスキャンで機械的に探せる）。
(2) 開発・分析の作業で本番の個人情報をリポジトリや分析基盤に持ち込んでいないか
（テストデータは仮名化する）。
(3) GitHub のアクセストークンが個人単位で無期限に発行され、権限が組織全体に及んでいないか
（細粒度トークン・有効期限・IP 制限・組織の監査ログ）。
同社の再発防止策はこの三つに対応しており、事案の規模にかかわらず持ち帰れる。

判断評価評価の根拠と留保
経路となった認証情報の無効化とアカウントの遮断に加え、ソースコードに含まれる 各種認証キー・パスワードを速報時点で無効化・再発行した機能した本記録の作成者の評価である。リポジトリが読まれた以上その中の鍵は全て漏れたと見なす 対応は妥当で、速報時点で「概ね完了」まで進めている。鍵の一覧を持っていなければ 3日以内に「概ね完了」とは言えないため、鍵の棚卸しがある程度できていたと読める

    同社は原因を「設定ファイルへの直接記載」と「個人情報のリポジトリ保存」の独立した2点に分け、 それぞれに対策を示した。片方だけ直しても、もう片方が残れば同じ構図が起きる
    取るべき行動 リスク台帳に「ソースコード・設定ファイル・CI 変数に本番の認証情報が無いか」と 「リポジトリ・開発環境・分析基盤に本番の個人情報が無いか」を別の項目として置き、 それぞれの点検結果と責任者を四半期ごとに確認する

    本件では GitHub のトークン1本で、ソースコード内の認証キー・パスワードと 顧客62,689名分の個人情報の両方に到達できた。本番データベースは破られていない

  • 速報→確定報→訂正の3段階は妥当だが、「確定」と銘打つ数字は公表前に二重に突合する
    同社は速報から3日で件数を確定し原因と対策を公表したが、その3日後に集計・共有過程の 記載誤りで2名分を訂正した。訂正幅は小さいが「確定」の信頼に関わる
    取るべき行動 事故公表の手順に「件数は調査担当と公表担当が別々に集計して突合する」工程を入れ、 突合の記録を残す。暫定値と確定値の区別を公表文で明示する
  • 経路を公表しないと、同じ置き方をしている他社は「置き方を直す」以上の対応ができない
    同社は認証情報が「直接記載」されていたことは公表したが、どうやって第三者の手に渡ったかは 公表していない。誤公開と端末侵害では、他社が取るべき対応が異なる
    取るべき行動 自社が被害に遭った場合の公表方針として、調査完了後に「経路の種別」を公表するかを あらかじめ決めておく。公表できない場合も、業界団体や取引先への限定共有の枠を用意する
セキュリティ技術者への示唆
  • 設定ファイル・ソースコード・CI の変数から認証情報を追い出し、履歴を含めてスキャンする
    本件の直接の原因は「GitHub にアクセスするための認証情報が、プログラムの設定ファイル内に 直接記載された状態で運用されていた」ことである
    取るべき行動 gitleaks・trufflehog 等でリポジトリの全履歴をスキャンし、見つかった鍵は例外なく無効化・ 再発行する。以後は pre-commit と CI のシークレットスキャンで混入を止め、 認証情報はシークレットマネージャや実行時の環境注入で渡す。GitHub のシークレットスキャン・ プッシュ保護を組織全体で有効にする
  • 開発・分析に本番の個人情報を持ち込まない。持ち込んだ形跡はリポジトリからも履歴からも消す
    本件では「社内の分析・開発作業の過程で、一部の個人情報が GitHub 上のリポジトリ内にも 保存されている状態」があり、62,689名分が流出した。置いていなければ出なかった
    取るべき行動 本番データから開発・分析用データを作る工程で氏名・メールアドレス・電話番号を仮名化し、 リポジトリには置かない。既存リポジトリを氏名・メールアドレスのパターンで検索し、 見つかったファイルは履歴から削除して、フォーク・クローンの残存も確認する。 プッシュ時に個人情報のパターンを検知して遮断するフックを入れる（同社が導入中と公表）
  • GitHub のトークンは細粒度・有効期限つき・最小権限で発行し、盗まれても単体では使えないようにする
    本件では盗まれた認証情報1本で組織のリポジトリに到達できた。同社は再発防止策として トークンの権限・発行ワークフローを組織で統制する仕組みへ切り替えた
    取るべき行動 クラシックな個人アクセストークンを廃止し、細粒度トークンにリポジトリ単位・読み取り専用・ 有効期限を設定する。組織の SSO を必須にし、可能なら IP 許可リストを設定する。 CI からのアクセスは GitHub App や OIDC の短命トークンに置き換える
  • 組織の監査ログを監視し、未知の送信元・大量クローン・深夜のアクセスを検知する
    同社は不正アクセスの時期と判明の手段を公表しておらず、再発防止策として 「アクセス状況の監視を強化」としている。事前の監視が十分でなかったと読める
    取るべき行動 GitHub 組織の監査ログ（git.clone・repo.download_zip・org.add_member 等）を SIEM に取り込み、 初めての送信元・短時間の多数リポジトリのクローン・トークンの新規作成をアラート条件にする
  • リポジトリが読まれたら、中の鍵は全て漏れたと見なして作り直す。作り直せる一覧を平時に持つ
    同社は速報時点で「ソースコードに含まれる各種認証キー・パスワードの無効化と再発行」を 概ね完了した。一覧が無ければ3日で「概ね完了」とは言えない
    取るべき行動 ソースコード・設定ファイルに含まれる（または過去に含まれていた）認証情報の一覧を 用途・接続先・失効手順つきで持ち、侵害時に一括で失効・再発行できるスクリプトと手順を用意する
