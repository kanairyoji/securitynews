INC-2026-0091TVING 3,954万件流出の政府調査結果

韓国の動画配信 TVING で3,954万アカウントと開発プロジェクト361件が持ち出された事案について、政府の民官合同調査団が原因を「開発者の接続キーの窃取 → ソースコードにハードコードされた運用環境の接続キー43個 → 平文のDB接続情報」の連鎖と断定——2024年の模擬侵入で同じ直書きを指摘されながら放置し、1回目の持ち出しは CPU 100% の警報で止めたが、2回目は攻撃者が CPU 使用率を10%以下に抑えて24GBを持ち出した

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備権限管理の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）公表されていない／不明
初報: 2026年6月1日（KISA への申告）／2026年9月3日（調査結果の公表） 最終更新: 2026年9月3日

韓国の科学技術情報通信部（과기정통부）は2026年9月3日、CJ ENM 系の動画配信サービス
「TVING（티빙）」で5月末に起きた侵害事案について、民官合同調査団の調査結果を公表しました。
攻撃者は開発者が持つ「開発環境接続キー」を事前に窃取して開発環境（ソースコードの
共同管理プラットフォーム）に入り、そこにあった開発プロジェクト361件（30.35GB）全てを持ち出し、
そのソースコード内にハードコードまたは平文で保存されていた「運用環境接続キー」43個のうち
2個を使ってクラウド（AWS）上の運用環境に侵入、平文で保存されていた利用者データベースの
接続情報（ID・パスワード）を得て、3,954万アカウント（重複を含む。ログイン可能な
有効アカウント2,206万・休眠850万・退会887万・テスト11万）の情報を持ち出しました。

流出した項目は ID・パスワード（一方向暗号化）・氏名・携帯電話番号・メールアドレス・生年月日・
連携情報（CI）・決済履歴など20項目70種です。携帯電話番号とメールアドレスは一部が暗号化されて
いましたが、暗号鍵も一緒に持ち出されたため平文と同等と判断されました。

調査団が指摘した問題は、①鍵の管理体制の欠如（直書き・平文保存・社内メッセンジャーでの共有・
全開発者に全プロジェクトの権限）、②異常行為の検知・監視体制の欠如（CPU 負荷の警報だけに依存）、
③情報保護ガバナンスの不足（役職員265名・開発149名に対し専任の情報保護人員は4名前後、
異常発生から CISO への共有まで約14時間）、④情報保護活動の不足（2024年の模擬侵入で
接続キーの直書きを指摘されながら未改善、新設 VPN のログが6日分しか保存されていなかった）、
⑤侵害事故の申告遅延（認知から24時間を超えて KISA に申告し、過料の対象）です。
攻撃者が開発環境接続キーをどうやって手に入れたかは、フィッシング・マルウェア・サプライチェーン・
鍵の共有と誤用・脆弱性の5つのシナリオを精査しても確認できませんでした。

TVING は同日、謝罪と補償（1人あたり最大300万ウォンのハッキング・フィッシング保険1年分、
5,000ウォン分のポイント、視聴環境の格上げ、クーポン）と、2030年までに情報保護投資を約4倍、
5年で人員を3倍にする計画を公表しました。政府は9月に是正計画を提出させ、10〜12月の履行を
2027年1月から点検し、不十分なら是正命令を出す方針です。

日本の読者にとっての要点は、「模擬侵入で見つかった鍵の直書きを直したか」という問いを
経営層がそのまま自社に投げられること、そして「開発用の入口 → ソースコード内の本番の鍵」という
経路が同じ日に国内のイノベーション（INC-2026-0088）でも公表されたことにあります（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

layer 0 の攻撃者が、layer 1 の「事前に窃取した開発環境接続キー」（窃取経路は不明）で layer 2 の開発環境に入り、 全開発者に全プロジェクトの権限があったため361プロジェクト全てを持ち出した。layer 3 のソースコード内には 運用環境接続キーが43個あり（2024年の模擬侵入で指摘済み・未改善）、うち2個で layer 4 の AWS 運用環境に侵入、 平文の DB 接続情報を窃取した。layer 5 の1次の試みは CPU 100% の警報で遮断されたが、2次は仮想サーバ経由で CPU 10% 以内に抑え、layer 6 の利用者 DB から24GB（3,954万アカウント・20項目70種）を外部へ流出させた。 layer 7 は対応と当局で、認知から29時間後の KISA 申告、6/3 の調査団構成、9/3 の調査結果公表と過料・履行点検を示す。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入機会はあったが検知できず
開発環境の接続記録は90日保存されていたが、許可された IP・端末に限る接続制御や 多要素認証が無く、未知の送信元からの接続が検知・遮断されなかった
侵入を防げた開発環境への接続を許可された端末・IP に限り、多要素認証を必須にする（調査団の再発防止策）
影響を限定できた開発者のアクセス権を担当プロジェクトに限定し、鍵1本で全プロジェクトに到達できない構成にする
検知できた鍵の発行・使用・変更・廃棄の履歴管理と常時点検を行い、未知の送信元からの使用を検知する
収集機会はあったが検知できず
開発環境の保安ログから事後に361件の流出を確認できたが、短時間の全件クローンをリアルタイムに検知する仕組みは無かった

認証情報アクセス機会はあったが検知できず

侵入を防げた模擬侵入・脆弱性診断の指摘事項に措置期限と責任者を付け、未措置を経営に報告する（調査団の再発防止策「発見された脆弱性の措置体系」）
横展開機会はあったが検知できず
運用環境への接続を許可された IP・端末に限る制御が無く、開発者の鍵が未知の場所から使われても検知されなかった
影響を限定できた運用環境接続キーの利用元を IP 許可リストで絞り、開発者の鍵に管理者権限・仮想サーバ生成権限を持たせない

認証情報アクセス現実的な検知機会なし
平文の設定ファイルの読み取り自体を検知する仕組みは一般的でなく、置かないことが唯一の対策である
侵入を防げたDB の接続情報をシークレット管理サービスに置き、アプリケーションが実行時に取得する構成にする。DB への接続元を特定のサブネットに限定する
実行検知した
18時00分に DB サーバの CPU 使用率100%で異常兆候の警報が発生し、TVING が作業を遮断した。 ただし警報は「負荷」としてしか扱われず、鍵の窃取と侵入には31日朝まで気づかなかった
検知できたストレージへの未知のオブジェクト挿入と DB への大量照会（行数・転送量）を CPU 負荷とは別の指標で検知する
検知できた警報の原因を「誰が・どの鍵で・何を照会したか」まで確認する初動手順を定め、負荷警報でも接続元を確認する
検知回避機会はあったが検知できず
CPU 負荷以外の指標（新規仮想サーバの生成・外向きの大量送信・DB からの大量読み出し）があれば検知できた
検知できた新規の仮想サーバ生成・削除、外向きの大量送信を監査ログからアラートにし、削除されても監査ログ側に痕跡が残るようにする
侵入を防げた1次の警報を「攻撃の疑い」として扱い、鍵の一斉無効化と接続元の遮断を24時間以内に行う初動手順を持つ
持ち出し機会はあったが検知できず
24GB の外向き送信と DB からの一括読み出しは検知されなかった。ネットワーク・データの流れをリアルタイムに検知・遮断する体制が無かった
影響を限定できた運用環境からの外向き通信を許可先に限定し、大量送信を検知して遮断する
検知できたDB からの大量読み出し（行数・時間帯・接続元）を監視し、閾値超過で接続を切る（調査団の再発防止策「大量データ照会の監視体系」）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
情報保安チームへの伝播（5月31日10時10分）ではなく、緊急対応チャネル開設（同15時09分）を認知時点として KISA に申告し、結果として24時間を超過した不十分本記録の作成者の評価である。調査団は「情報保護担当者・部署長・CISO・代表者のいずれかが 侵害事故の発生を知った時」を認知時点とする指針（2025年8月）に基づき10時10分を認定した。 認知時点の解釈で争う姿勢は、当局との関係で不利に働いた
1次の流出の試みで CPU 100% の警報が出た際、当該作業を遮断したが、鍵の無効化や接続元の遮断、 侵害としての調査には進まなかった（報道資料から読める範囲）不十分本記録の作成者の評価である。遮断から2次流出まで25時間あり、この間に運用環境接続キーの一斉無効化と 接続元の遮断ができていれば、2次流出は起きていない（本記録の読み。調査団は「監視体制があれば 大規模流出に至らなかった」と判断している）
鍵の無効化・再発行の時期は報道資料に記載が無い評価材料なし本記録の作成者の評価である。調査団は再発防止策として鍵管理体系の構築を求めており、事故時の無効化の経過は評価する材料が無い
政府の民官合同調査団による調査を受け入れ、調査結果を「謙虚に受け入れる」と表明した機能した本記録の作成者の評価である。韓国の制度（2025年5月から先行稼働した侵害事故調査審議委員会・ 10月1日法定化）の下で、当事者の自社調査より踏み込んだ事実が公表された。 日本の事故公表と比べて経路・時刻・鍵の数・警報の閾値まで出ている点が読者にとって有用である
補償として保険・ポイント・視聴環境の格上げ・クーポンのパッケージを設け、申請期間（9月7日〜30日）と 適用日（10月6日）を公表した。総額は明らかにしなかった部分的に機能本記録の作成者の評価である。報道は1人あたり約2万ウォン相当と評価し、総額と財務負担を 明らかにしなかった点を指摘している。休眠・退会アカウント（1,737万）の保持者への補償の扱いも 報道資料からは読めない
CISO・経営層への示唆
  • 「模擬侵入で見つかった鍵の直書きを直したか」を経営が確認する。直していなければ、当局に対して「知っていて放置した」証拠になる
    調査団は「2024年の模擬侵入で接続キーのハードコードの脆弱性を発見しながら改善措置を取らなかった」ことを 名指しで指摘した。知らなかったのではなく、知っていて直さなかった
    取るべき行動 過去2年分の模擬侵入・脆弱性診断の報告書から「未措置」「リスク受容」の項目を抽出し、 認証情報の直書き・平文保存に関するものは期限を切って是正する。未措置の理由と承認者を記録する
  • 検知が一度働いても、それを「攻撃」と認識して鍵を止めなければ、攻撃者は閾値を学習して戻ってくる
    1次の流出の試みは CPU 100% の警報で遮断されたが、負荷警報としてしか扱われず、 25時間後の2次では攻撃者が CPU を10%以内に抑えて24GB を持ち出した
    取るべき行動 警報の初動手順に「接続元と使用された鍵の確認」を入れ、説明のつかない大量照会があれば 24時間以内に関連する鍵の一斉無効化と接続元の遮断を判断する権限を現場に与える
  • 開発149人に保安専任4人という比率は、当局が「限界がある」と認定する水準である
    調査団は役職員265名・開発149名に対し情報保護専任4名前後で、常時監視・脆弱性点検・ 異常行為監視に限界があると判断した。TVING は5年で人員3倍・投資4倍を約束した
    取るべき行動 自社の開発人員と情報保護専任人員の比率を算出し、常時監視・脆弱性点検・異常行為監視・ 事故対応の4つの機能を誰が担っているかを一覧にする。空欄があれば外部委託を含めて埋める
  • 認知時点の解釈で当局と争わない。24時間の起点は「担当者が知った時」である
    TVING は緊急対応チャネル開設（15時09分）を認知時点と主張したが、調査団は情報保安チームへの 伝播（10時10分）を認定し、24時間超過で過料の対象とした
    取るべき行動 日本の個人情報保護法の速報（概ね3〜5日）・確報（30日／60日）の起点を「担当部署が知った時」として 手順書に明記し、事実確認を待たずに速報を出す運用にする
  • 暗号化していても、鍵が同じ環境にあれば「平文と同等」と当局に判断される
    携帯電話番号とメールアドレスは一部が暗号化されていたが、暗号鍵も一緒に流出したため 調査団は平文で流出した情報と同等と判断した
    取るべき行動 個人情報の暗号化について「鍵はどこにあるか」「環境ごと侵入されたときに鍵も取られるか」を 技術部門に問い、鍵管理サービスや HSM への分離を計画する
セキュリティ技術者への示唆
  • ソースコード・環境変数から本番の接続キーを追い出し、数を数えて0にする
    361プロジェクトに運用環境接続キーが43個（ハードコード41・平文3）含まれ、そのうち2個で 運用環境に侵入された。開発者8名の端末からも運用環境接続キー52個が見つかった
    取るべき行動 シークレットスキャンで全リポジトリ・全ブランチ・履歴・環境変数・開発者端末の設定ファイルを 走査し、見つかった鍵を全て無効化・再発行してシークレット管理サービスに移す。 走査を CI とプッシュ保護で常時化し、鍵の数を月次で報告する
  • 開発者の鍵1本で全プロジェクト・全環境に届く構成をやめる
    全開発者に全開発プロジェクトへのアクセス権が付与されており、鍵1本で361件全てが読めた。 運用環境接続キーの1つは仮想サーバ生成権限を持っていた
    取るべき行動 リポジトリのアクセス権を担当プロジェクト単位にし、運用環境の鍵は用途別・最小権限・短命にして、 開発者の鍵に仮想サーバ生成・管理者権限を持たせない。運用環境への接続は IP 許可リストと 多要素認証を必須にする
  • 本番環境の中に DB の接続情報を平文で置かない
    運用環境に入った攻撃者は、利用者 DB への接続情報（ID・パスワード）が平文で保存されているのを見つけて窃取した
    取るべき行動 DB の接続情報をシークレット管理サービスに置いてアプリケーションが実行時に取得する構成にし、 DB への接続元を特定のサブネット・ロールに限定する。設定ファイル内の平文パスワードを定期的に走査する
  • CPU 負荷以外の指標で「大量照会」「新規仮想サーバ」「外向き大量送信」を検知し、削除されても残る監査ログを取る
    1次は CPU 100% で検知されたが、2次は CPU 10% 以内・仮想サーバ経由・24GB の外部送信・仮想サーバ削除で 警報が鳴らなかった。監視が CPU 負荷だけだった
    取るべき行動 DB の読み出し行数・転送量・接続元、クラウドの仮想サーバ生成と削除、ストレージへのオブジェクト挿入、 外向きの送信量を監査ログから SIEM に集め、閾値超過でアラートと自動遮断を行う。 監査ログは攻撃者が消せない別アカウントに保存する
  • ログ保存方針を新設機器にも適用し、窃取経路を追えるだけの期間を保存する
    新設の VPN 機器にログ管理方針が適用されず約6日分しか接続記録が無く、調査団は5つのシナリオを 精査しても開発環境接続キーの窃取経路を確認できなかった
    取るべき行動 VPN・開発環境・クラウド・端末の監査ログの保存期間を少なくとも90日（できれば180日）にし、 新設機器の受け入れ手順に「ログ転送と保存期間の確認」を入れる。四半期ごとにログの網羅性を点検する
