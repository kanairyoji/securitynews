INC-2026-0098Trezor の委託先に削除済みのはずの注文データ

ハードウェアウォレットの Trezor が、物流委託先 ShipMonk の侵害で「契約と方針に基づき削除済みと書面で確認していた」2019年11月〜2021年8月の注文データ約67,000名分が残っていて漏れたと追加公表——8月の初報13,689名は90日の保持方針の範囲内だったが、3週間後に委託先の分析環境（Metabase）に5年前のデータが残っていたことが分かった。ShipMonk は公表しておらず、侵入口は Metabase のゼロデイ SQL インジェクション CVE-2026-72898

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因未知の脆弱性の悪用ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年8月13日（Trezor の初報。追加公表は9月4日） 最終更新: 2026年9月5日

暗号資産のハードウェアウォレットを製造・販売する Trezor（チェコ）は2026年9月4日、
配送・物流の委託先 ShipMonk で起きた侵害について、9月2日に ShipMonk から
「侵害は以前の説明より大きかった」と知らされ、米国の顧客約67,000名分の注文データが
追加で影響を受けたと公表しました。追加分は2019年11月〜2021年8月の注文に関するもので、
氏名・メールアドレス・電話番号・配送先住所・注文番号が含まれます。

Trezor は8月13日の初報で、ShipMonk から8月10日に侵害の通知を受け、2026年5月10日〜8月8日の
注文に関する11,742名（氏名・メール・電話・配送先住所）と1,947名（氏名・市・メール）が
影響を受けたと説明し、「90日で注文データを削除または匿名化する自社の方針の範囲に
被害が限られた」と位置づけていました。今回の追加分はその前提を覆すもので、Trezor は
「ShipMonk との関係の全期間を通じて、契約・データ方針・過去のやり取りに基づき、
データ削除の書面での確認を繰り返し求め、受け取っていた。この確認を受けていたにもかかわらず、
データが彼らのシステムで削除されていなかったことに、非常に落胆している」（原文英語）と述べています。

ShipMonk 自身は本記録の作成時点で公表を行っていません。報道によれば、ShipMonk が顧客に送った
通知メールは、侵入口を BI ツール Metabase の脆弱性（ゼロデイの SQL インジェクション、
のちに CVE-2026-72898）としており、Metabase から ShipMonk への通知は8月6日でした。
ShipMonk には恐喝グループ ShinyHunters から恐喝メールが届いたと報じられています。

この事案の要点は、侵入の手口ではなく、発注側が90日で消す方針を持ち、委託先から削除の書面確認まで
得ていても、委託先の分析環境には5年前の注文データが残っていたことにあります。
日本の EC・決済・暗号資産の事業者も、3PL（物流委託先）や BI・分析の委託先に顧客データの写しを
持たせています。本記録は Trezor の公表と報道から確認できた範囲を整理し、
ShipMonk・Metabase 側の事実は報道によるものとして分けて記録します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は BI ツール Metabase の未認証 SQL インジェクションのゼロデイ（CVE-2026-72898）を 悪用して、Trezor の物流委託先 ShipMonk の Metabase インスタンスに管理者として到達し、 接続先に保持されていた注文データ（2026年5〜8月分に加え、削除済みのはずの2019年11月〜 2021年8月分）にアクセスした。手口の記述は Metabase の公表と報道に基づき、 ShipMonk の公表は無い。ShinyHunters による恐喝が報じられている。

    トレードオフ: メール通知は流出したメールアドレス宛てになり、なりすましと区別しにくい。 専用アドレスを公表して見分けの基準にしたが、送信元の偽装は防げない
  • Trezor は ShipMonk と「経緯の確定に向けて直接連絡を取っている」と述べ、自社での外部調査の起用は公表していない。ShipMonk は外部の IT 専門家を入れたと通知（報道）
    理由は公表されていない
    トレードオフ: 侵害は委託先の環境で起きており、発注側が調査主体になれない。委託先の調査結果を待つ形になり、 範囲の確定は委託先の速度に従う

侵入は委託先の委託先で起きた——Metabase のゼロデイ SQL インジェクションから ShipMonk の分析環境に入り、そこに Trezor の注文データがあった原因・手口出典 [2] [4] [5] [6] [7]

Trezor の公表は侵入の手口に触れていない。手口は報道による。

BleepingComputer は、ShipMonk が顧客（荷主）に送った通知メールを確認し、次の記述を伝えた。

2026年8月6日、Metabase から、何者かが Metabase のソフトウェアの脆弱性を悪用して、
あなたのアカウントとあなたの顧客に関するデータにアクセスしたと知らされました。
（ShipMonk の顧客向け通知・原文英語）

Metabase は BI（ビジネスインテリジェンス）ツールで、接続したデータベースの中身を
集計・可視化する。2026年8月6日に Metabase が公表した脆弱性は、認証無しで到達できる
パスワードリセットの API を起点とする SQL インジェクションで、成立するとインスタンスの
管理者権限に至り、接続先データベースの保存資格情報と、その接続で読めるデータ全体に
到達できる（INC-2026-0009。のちに CVE-2026-72898、CVSS 10.0、CISA の KEV に収載）。
同じ脆弱性で Framework・Tally の顧客データも窃取されている。

The Hacker News は Halborn の分析として、「Trezor のケースでは、ShipMonk が Metabase の
インスタンスに保存していた顧客の注文詳細が露出した」（原文英語）と伝えた。
つまり構造は Metabase（ソフトウェア供給元）→ ShipMonk（Trezor の物流委託先）の分析環境
→ Trezor の顧客の注文データ の3段で、Trezor から見れば委託先の、さらにその道具の欠陥で
自社の顧客が被害を受けた形である。

本記録の評価として、原因は3つに分けられる。①委託先の道具のゼロデイ（Metabase）、
②委託先起因（ShipMonk の環境で起きた）、そして③削除されているはずのデータが残っていた
という委託先のデータ管理の問題である。①②は Trezor が直接制御できない。
③は契約と確認で制御しようとし、それでも防げなかった点が本件の中心になる。

初報は「90日の保持方針の範囲」だったが、3週間後に5年前の注文約67,000名分が委託先に残っていたことが分かった被害規模・影響範囲出典 [1] [2] [3] [5]

90日後に、Trezor eShop での購入に関する全ての顧客データを削除または匿名化します。
90日を選んだのは、配送・返品・返金や交換という注文の一生をカバーする最短の窓だからです。
その後は、あなたの住所や電話番号を保持する理由がありません。（原文英語）

本記録の評価として、追加分は初報の約5倍で、しかも保持方針の90日をおよそ5〜7年超えていた
データである。「90日で消える」という前提は Trezor 側では守られていたと読めるが、
委託先の側では守られていなかった。初報と追加分の重なりは公表されておらず、
実人数の合計は分からない。

発注側は「削除の書面確認」を繰り返し受け取っていた——確認書は削除の証明にならなかった波及・関係先出典 [1] [2] [3]

Trezor の9月4日の更新で最も重い記述は次の2文である。

ShipMonk との関係の全期間を通じて、私たちは契約・データ方針・過去のやり取りに基づき、
データ削除を確認する書面での保証を繰り返し求め、受け取っていました。
この確認を受けていたにもかかわらず、データが彼らのシステムで削除されていなかったことに、
非常に落胆しています。（原文英語）

ここから分かるのは、Trezor が委託先に対して①契約に削除を書き、②自社の方針と同じ90日を
委託先にも求め、③削除の書面確認を繰り返し取っていた、という3点である。
発注側が委託先のデータ管理に対して取れる手段として、これは標準的な水準を超えている（本記録の評価）。

それでも残っていた。ShipMonk が公表していないため、なぜ残ったかは分からない。
考えられる形は、本番の注文システムからは削除されたが分析環境（Metabase の接続先）に
写しが残っていた、バックアップや別系統に残っていた、削除処理そのものが不備だった、の
いずれかだが、これは本記録の推定であり、当事者の説明は無い。

本記録の評価として、この事案が示すのは「削除の書面確認」と「削除の証跡」の違いである。
書面確認は委託先の申告であり、どのシステム・どの写し・どのバックアップまで消したかを
示さない。分析環境は本番から切り離されて運用されることが多く、削除の対象から漏れやすい。
発注側が確かめるには、委託先のデータの所在の一覧（本番・分析・バックアップ・ログ）と
所在ごとの削除の証跡を求めるか、監査権を行使するしかない。

  • 8月10日: ShipMonk から侵害の通知
  • 8月13日: ブログで公表。対象者へ専用アドレスからメールで個別に通知。「メールが届いていなければ対象外」と明示
  • 8月14日: 1,947名に「より古い注文が含まれる」と注記
  • 9月2日: ShipMonk から追加の通知
  • 9月4日: ブログを更新し追加分を公表。対象者へ直接通知。詐欺メール・偽の電話・手紙・なりすまし・物理的な安全上のリスクに注意を呼びかけ

Trezor は初報で「私たちのシステムは侵害されておらず、あなたの Trezor デバイスは安全です」
（原文英語）と述べ、9月4日にも「ハードウェアウォレットの安全性には影響しない」とした。
ShipMonk については「経緯の確定に向けて直接連絡を取っている」（8月13日）と述べている。

ShipMonk 自身の公表は、8月14日の SecurityWeek の時点でも9月5日の The Hacker News の時点でも
確認されていない。報道によれば ShipMonk は顧客（荷主）への通知メールで、影響を受けたシステムを
保全し、外部の IT 専門家を入れて調査したと述べている。

本記録の評価として、Trezor の対応は速く、内容も「何が漏れ、何が漏れていないか」を明確に
分けている。特に、暗号資産のハードウェアウォレットの購入者にとって配送先住所は
「その住所に暗号資産を持つ人が居る」ことを示すため、Trezor が「物理的な安全上のリスク」まで
注意喚起に含めたのは正確である。一方、ShipMonk が公表しない限り、なぜデータが残っていたか、
他の荷主がどうなったかは誰にも分からない。委託先の沈黙は委託元の公表の限界になる
（INC-2026-0013 の CEVA Logistics と同じ構図）。

公表は確認していない。

（INC-2026-0013）。CEVA は「注文後最大90日間保持する」と荷主の通知に書かれており、
荷主の通知対象は直近90日分の購入者になった。本件はその逆で、90日の合意があったのに
5年前のデータが残っていたケースであり、CEVA の事案と並べると「保持期間の合意」と
「合意が守られているかの確認」が別の問題であることが分かる。

約66,000名の氏名・ユーザー名・メールが露出し、その後にリカバリーシードを狙う

フィッシングへの注意を強く書いているのは、この経験に基づくと読める（本記録の推定）。

「90日で消す」を自社で守っても、委託先の分析環境に写しが残れば通知対象は5年分に広がる——契約と確認書では止まらず、所在と証跡で確かめる評価・解釈出典 [1] [2] [4] [5]

この事案の要点は3つである。

  1. 最短の保持方針と、委託先との同条件の合意と、削除の書面確認まで揃っていた発注側でも、
    委託先の分析環境に5年前のデータが残っていた。発注側の統制として上位の水準にあった
    Trezor で起きたことが、この事案を先例にする。
  2. 侵入口は委託先の道具のゼロデイで、発注側にも委託先にも事前に防ぐ手段は乏しかった。
    防げなかった侵入の被害の大きさを決めたのは、侵入の手口ではなく「そこに何が残っていたか」だった。
  3. 配送先住所は業種によって重みが変わる。暗号資産のハードウェアウォレットの購入者の住所は、
    なりすましの材料であるだけでなく、物理的な接触の標的リストになる。
    Trezor がそれを注意喚起に書いた点は、他の事業者が自社の商品で同じ判断をするときの参照になる。

日本の読者にとっての読みどころは、日本の組織が当事者だからではなく、
3PL・BI・分析・コールセンターの委託先に顧客データの写しを持たせる構図が国内の EC・
決済・暗号資産交換業でも普通にあることにある。個人情報保護法は委託先の監督を委託元に
求めるが、監督の実務は「契約に削除を書く」「削除の確認書をもらう」で止まりがちである。
本件は、その2つを満たしていても消えていなかった例として、委託先のデータの所在の一覧と
所在ごとの削除証跡を求める根拠になる。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
委託先からの通知の3日後（初報）・2日後（追加）にブログで公表し、同時に対象者へメールで直接通知した機能した本記録の作成者の評価である。暗号資産の購入者の連絡先と住所が漏れた場合、 フィッシングは公表を待たずに始まるため、早い通知が合理的である。範囲が後で広がることは 委託先起因の事案では避けにくく、Trezor はそれを「ShipMonk から知らされた」と明示して更新した
件数・期間・項目・7か国・保持方針・委託先名・削除確認の経緯を公表し、侵入の手口・帰属・ShipMonk 側の事情は公表しなかった機能した本記録の作成者の評価である。委託先名を明示し、「削除の書面確認を受け取っていたのに 削除されていなかった」と自社の統制の限界まで書いた公表は珍しく、読者が自組織の委託先管理を 見直す材料になる。手口は Trezor の知りうる範囲外であり、書かないのは妥当
対象者へ専用のアドレスからメールで個別に通知し、「届いていなければ対象外」と公表に明記した部分的に機能本記録の作成者の評価である。対象者が自分の該当を確認できる基準を示した点は良いが、 フィッシングが「Trezor からの通知」を装う場面で、正規の通知もメールであることは 対象者にとって判断を難しくする。同社は「個人情報を求めるメッセージに注意」と併記している
Trezor は ShipMonk と「経緯の確定に向けて直接連絡を取っている」と述べ、自社での外部調査の起用は公表していない。ShipMonk は外部の IT 専門家を入れたと通知（報道）評価材料なし本記録の作成者の評価である。ShipMonk の調査の結果（なぜ残っていたか・他の荷主）は 公表されておらず、評価できる材料が無い
CISO・経営層への示唆
  • 委託先からの「削除の書面確認」は削除の証明ではない。所在の一覧と所在ごとの証跡を求めないと、5年前のデータが分析環境に残る
    Trezor は契約に削除を書き、委託先にも90日を合意させ、削除の書面確認を繰り返し受け取っていた。 それでも ShipMonk のシステムに2019〜2021年の注文データが残り、侵害で漏れた
    取るべき行動 顧客データを渡している主要な委託先（3PL・コールセンター・BI/分析・決済代行）に、 「預けたデータがどのシステムにあるか（本番・分析・バックアップ・ログ）」の一覧を出させ、 所在ごとの削除の証跡（削除ジョブの記録・件数）を年1回以上求める。出せない委託先は 次回更新で監査権を契約に入れる
  • 自社の保持方針を短くしても、通知対象の広さは委託先の保持実態で決まる
    Trezor は90日で消す方針を自社で守り、初報はその範囲に収まった。 3週間後の追加分は方針の90日をおよそ5〜7年超えたデータで、初報の約5倍だった
    取るべき行動 リスク評価で「委託先に預けたデータの保持実態が自社の方針と一致していない」場合の 通知対象の人数を試算し、経営層に示す。委託先ごとに「最悪の場合の通知対象」を持つ
  • 委託先の道具（BI ツール等）のゼロデイは、自社にも委託先にも事前に防げない。被害の大きさは「そこに何が残っていたか」で決まる
    侵入口は Metabase のゼロデイで、公表時点で既に悪用されていた。同じ脆弱性で Framework・Tally も被害を受けた。被害の差を決めたのは、分析環境に何が入っていたかだった
    取るべき行動 委託先に渡すデータの項目を「配送に要る最小」に絞り、委託先の分析環境には氏名・住所・電話を 入れない（仮名化・集計値のみ）ことを契約と技術仕様に書く。自社の分析環境でも同じ原則を適用する
  • 商品の性質によって配送先住所の重みは変わる。暗号資産・高額品・医療品の購入者名簿は物理的な標的リストになる
    Trezor は「詐欺メール・偽の電話・手紙に加え、物理的な安全上のリスクにさらされる可能性」を 注意喚起に書いた。ハードウェアウォレットの購入者の住所は「そこに暗号資産を持つ人が居る」ことを示す
    取るべき行動 自社の商品・サービスで「購入者の住所が漏れたときの二次被害」を業種の文脈で評価し、 物理的なリスクがある場合は通知文と対策（配送先の匿名化・受取拠点の選択肢）に反映する
  • 委託先が公表しない場合、発注側の公表が唯一の一次情報になる。委託先名・経緯・自社の統制の限界まで書けるかを平時に決めておく
    ShipMonk は公表しておらず、なぜデータが残っていたか・他の荷主はどうかは誰にも分からない。 Trezor は委託先名と削除確認の経緯まで公表した
    取るべき行動 委託先起因の事故の公表方針（委託先名を出すか・委託先の説明をどう引用するか・ 自社の統制で防げなかった点をどう書くか）を法務・広報と平時に決め、雛形を持つ
セキュリティ技術者への示唆
  • 保持期限の自動削除を、本番データベースだけでなく分析環境・バックアップ・ログにも実装する
    Trezor 側の90日は守られたと読めるが、委託先の分析環境（Metabase の接続先）には 5年前の注文が残っていた。削除ジョブが本番だけを対象にしていると、写しが残る
    取るべき行動 データの所在（本番・レプリカ・分析用 DWH・BI の接続先・バックアップ・ログ）を一覧にし、 所在ごとに保持期限と削除ジョブを実装する。削除の実行結果（件数・日時）を記録し、 委託元に証跡として出せる形にする。バックアップは暗号鍵の破棄で期限切れを実現する
  • BI・分析ツールは「接続先の全データに到達できる管理者」を1つの Web アプリに置いている。公開網に直接置かない
    Metabase のゼロデイは未認証の API から管理者権限に至り、接続先の保存資格情報と全データに 到達できた。ShipMonk・Framework・Tally の被害はいずれもこの経路である
    取るべき行動 BI ツールを VPN・IP 制限・SSO の前段の内側に置き、インターネットから直接到達できないようにする。 接続先には読み取り専用で必要な列だけを見せるビュー用のアカウントを使い、 個人を特定する列（氏名・住所・電話）は分析環境に入れないか仮名化する
  • 委託先の環境で自社データがどう扱われているかは、自社のログには映らない。委託先に監査ログの提出を求める
    Trezor は「何が漏れたか」を ShipMonk の通知に依存し、3週間後に範囲が約5倍に広がった。 発注側は委託先のログを持たない
    取るべき行動 委託契約に、自社データへのアクセスログ（問い合わせ・エクスポート）の保持期間と、 事故時の提出義務を書く。定常的には、委託先が持つ自社データの件数を四半期ごとに報告させ、 自社の想定（直近90日分の注文数）と突き合わせる
  • 配送に要るデータと分析に要るデータを分け、分析側には注文番号と集計値だけを渡す
    ShipMonk の Metabase インスタンスには氏名・メール・電話・配送先住所・注文番号が そのまま入っていた（Halborn の分析・報道）。配送には要るが、分析にはこの形で要らない
    取るべき行動 委託先への提供データを「配送用（本番・90日）」と「分析用（仮名化・集計）」に分け、 分析用には個人を特定する列を含めない。委託先の BI ツールが本番 DB を直接参照している場合は、 仮名化したビューか別のスキーマを参照させる
法務・コンプライアンスへの示唆
  • 委託先の監督は「契約に削除を書く」「確認書をもらう」で終わらない。監査権と証跡提出の条項が無いと、確認書は削除の申告にとどまる
    Trezor は契約・方針・書面確認の3つを揃えていたが、委託先のシステムにデータが残っていた。 委託元は委託先の申告を信じるほかなかった
    取るべき行動 委託契約に、①データの所在の一覧の提出、②所在ごとの削除証跡の提出、③監査権（自社または 第三者による）、④事故時の第一報の期限と範囲の更新義務、⑤委託先が公表しない場合の 委託元による公表の権利、を入れる。既存契約は次回更新で追加する
