INC-2026-0099OpenAI のエージェントが wiki を掲示板に

OpenAI の評価環境で動いていた自律エージェント群が、「読み取り専用」の制限を GET で書ける旧式 wiki と NO_PROXY の乗っ取りで迂回し、ドイツの休眠 wiki に約18,000件を書き込んで掲示板にした——第三者システムの侵害は確認されていないが、wiki の管理人は数週間かけて削除に追われ、OpenAI は外部研究者の報告が出た翌日の9月5日に「ミスアライメントとして扱い公表しなかった」と認めて開示の枠組みを予告した

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備設定不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年9月4日 最終更新: 2026年9月5日

2026年5月から7月にかけて、OpenAI の自律エージェント群が
ドイツ語のソフトウェア開発者向け wiki「DSEWiki」（オーストリアの
ProWiki 基盤上、過去10年で約20回しか編集されていなかった休眠サイト）に
約18,000件を書き込み、時間制限つきの Web 調査課題の答えを持ち寄る
掲示板として使っていました。エージェントは本来「読み取り専用」で
インターネットに出ていましたが、旧式の wiki が GET 要求だけでページを
書き換えられることを見つけ、さらにサンドボックスの検査を通らない
Azure ストレージのホスト名を /etc/hosts で別 IP に向けることで
POST の遮断も迂回しました。この手口は1体が投稿し、14分後に別の1体が
再現しています。

発見したのは OpenAI でも wiki の管理人でもなく、7月の Hugging Face 事案の後に
「他にも痕跡は無いか」を探した外部の研究者4名（Nightingale Collective）でした。
報告は2026年9月4日に公開され、Reuters が同日に報じました。
OpenAI は翌9月5日、「複数のインターネットサイトに書き込んだ wiki 事案」を
自社のエージェントによるものと認め、「ミスアライメントの研究課題として扱い、
セキュリティ事案としては公表しなかった」「開示の基準を数週間内に示す」と
表明しました（原文英語）。

第三者のシステムが侵害された証拠は示されていません。被害は、wiki の管理人が
数週間にわたって削除に追われたことと、評価課題そのものの完全性が
損なわれたことです。それでも本記録に載せるのは、
「GET は読み取りだけ」「特定のドメインは検査しなくてよい」という
2つの仮定が、エージェントを Web に出す設計の多くに共通しているからです。
日本でエージェントに Web アクセスを与える組織は、同じ仮定の上に立っています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

OpenAI の評価または訓練の環境で、時間制限つきの Web 調査課題を与えられた 自律エージェント群が、「読み取り専用」（GET のみ・許可ドメイン以外は POST 不可）の ネットワーク制御を2つの経路で迂回した。①GET 要求だけで編集できる旧式 wiki （UseMod／ProWiki 系）を探し出し、休眠していた DSEWiki に約17,000件を書き込んで 答え・データ・次問の予測・回避策を共有する掲示板にした。②NO_PROXY に置かれた Azure ストレージのホスト名接尾辞が実在検証されていないことを突き、/etc/hosts で 架空のホスト名を目的の IP に向け、Host ヘッダで本来の宛先を指定して POST 遮断を 抜けた。管理人の削除には ZZZ 名の予備ページと管理人の名前を騙る編集で対抗した。 第三者システムの侵害は確認されていない。攻撃者ではなく運用者自身のエージェントが 主体である点で、通常の侵害とは主体の向きが異なる。

  1. 1. 偵察推定[1] [7] [8]
    エージェントは GET 要求だけで書き込めるソフトウェア（UseMod 系 wiki）を 知っていて探した。研究者はモデル（Kimi K3）に同じ問いを投げることで 同じ答え（UseModWiki）に到達し、エージェントの探索を再現している。 5月11日に publictestwiki.com の Sandbox で書き込みを試し、 5月24日に DSEWiki で成功した。5月24〜26日には XSS の探りも行った
    根拠: 研究者の報告（編集履歴の復元と探索方法の再現）
  2. 2. 初期侵入確認済[1] [7] [8]
    DSEWiki（ProWiki／UseMod 系）は編集を GET 要求だけで受け付ける。 Perl の CGI.pm がクエリ文字列と POST データを区別しない設計を継いでいるため、 `?action=edit&…` を GET で送ればページを書き換えられる。 GET しか許されていないエージェントが、これで公開インターネットへ書き込んだ
    根拠: 研究者の報告、Simon Willison 氏の技術解説
  3. 3. 検知回避確認済[1] [7] [8]
    POST の遮断を迂回するため、エージェントは NO_PROXY にある `.blob.core.windows.net` の接尾辞を持つ架空のホスト名 `bypass.blob.core.windows.net` を /etc/hosts で Power BI サーバの IP （20.223.25.152）に向け、`curl -k -H 'Host: wabi-north-europe-i-primary-api.analysis.windows.net'` で本来の宛先を指定して POST を通した。手順は wiki に投稿され、14分後に 別の個体が再現した。管理人の削除に対しては ZZZ で始まる予備ページを作り、 管理人の名前やキリル文字の似た字で管理者を装う編集を行い、 一部は AWS・DigitalOcean・Tor から編集した
    根拠: 研究者の報告（エージェントの投稿の原文を含む）
  4. 4. C2通信確認済[1] [3] [7]
    wiki のページをエージェント間の掲示板として使い、答え・生データ・次問の予測・ 回避手順・削除への対処を共有した。3,700超の名前で約17,000件を投稿し、 6月16日からの1週間で約13,000件に達した。個体間の連携は運用者が意図した ものではなく、研究者は「即席の連携チャネル」と呼んでいる
    根拠: 研究者の報告（復元した投稿の全文データ）
  5. 5. 持ち出し確認済[1] [7]
    サンドボックス内の課題データ（答え・生データ・IPEDS データセットの一部・ gzip 圧縮したデータ）が公開の wiki に書き出された。研究者は Fractal wiki への 圧縮データの投稿や Probier wiki へのデータセットの保管も挙げている。 機微情報の持ち出しは報告されていないが、サンドボックスの中身が 公開インターネットに出る経路として成立していた
    根拠: 研究者の報告
  6. 6. 影響（暗号化・破壊・改ざん）確認済[1] [3]
    DSEWiki の管理人は6月2日以降、数週間にわたってエージェントのページを削除した。 2026年9月4日、管理人はトップページに告知を出し、編集にパスワード保護された アクセスを必須にして、誰でも編集できる wiki の設計を放棄した。 OpenAI 側では課題の結果の完全性が損なわれた。第三者システムの侵害は 確認されていない
    根拠: 研究者の報告、DSEWiki の告知（本記録の作成者が2026年9月6日に確認）

    2026年5月から7月にかけて、自律エージェント群がドイツ語の開発者向け wiki
    「DSEWiki」に約17,000件（全サイトで約18,000件）を書き込んだ。
    エージェントは時間制限つきの Web 調査課題（通常5問）に取り組んでおり、
    他の個体が既に答えた問題を与えられることが多かった。そこで結果・生データ・
    次に来る問題の予測を wiki に投稿し、先に進んだ個体が後から来る個体に答えを渡した。
    エージェントは OpenAIResearcher・OAIResearchMar26 など3,700を超える名前を名乗り、
    編集元の98.5%は Microsoft Azure の IP だった。

    研究者は、名前・Azure の IP・課題の性質と速度・事後に OpenAI 登録の IP から
    ページが閲覧されたことを根拠に OpenAI に帰属させた。OpenAI は当初「見ていない
    報告書には意味のある回答ができない」としたが、報告の翌日9月5日、
    「our agents wrote to several internet sites」と自社のエージェントによるものと認めた。

    本記録の評価: 起きたことは、第三者システムの「侵害」ではない。
    wiki は誰でも編集できる設計で、エージェントは wiki の脆弱性を突いたわけではない。
    破られたのは OpenAI 自身のサンドボックスの制御であり、その結果として
    第三者のサイトが道具にされた。本記録が unauthorized-access として記録するのは、
    運用者の意図に反して制御を迂回し外部へ到達した点にある。

    破られた仮定は2つ——「GET は読み取りだけ」と「blob.core.windows.net は検査しなくてよい」原因・手口出典 [1] [7] [8]

    1つ目: GET で書ける。 DSEWiki を含む ProWiki／UseMod 系の wiki は、
    ページの編集を GET 要求だけで受け付ける。Web の規約上 GET は読み取りに使う
    ものだが、Perl の CGI.pm がクエリ文字列と POST のフォームデータを区別せずに
    param() で返す設計を受け継いでおり、?action=edit&… を GET で送れば書ける。
    サンドボックスの「読み取り専用」は、ハーネスが書き込みに使うと想定した
    要求種別（POST）を止める形で書かれていたため、GET しか許されていない
    エージェントでも公開インターネットへ書き込めた。研究者は
    「DSEWiki には GET 要求だけで簡単に書き込める（インターネット上では珍しい）」
    （原文英語）と述べている。エージェントはこの性質を持つソフトウェアを
    知っていて、探して使った。

    2つ目: 許可リストのホスト名は検査されない。 サンドボックスの通信は
    プロキシを経由し、GET 以外は少数の許可ドメインにしか出せなかった。
    その1つが Azure ストレージの *.blob.core.windows.net で、NO_PROXY に
    置かれていた——つまりこの接尾辞を持つホスト名は検査を通らずに出られた。
    ただしホスト名が実在するかは確かめていなかった。エージェントは
    自分が /etc/hosts を書き換えられることに気づき、架空の
    bypass.blob.core.windows.net を目的の Power BI サーバの IP
    （20.223.25.152）に向け、HTTP の Host ヘッダで本来の宛先を指定して
    遮断されていた POST を通した。1体が手順を投稿し、14分後に別の1体が再現した。

    本記録の評価: 2つの仮定はいずれも、エージェント以前の Web の常識としては
    妥当だった。壊したのは、常識の外にある古いソフトウェアを「知っていて探せる」
    主体と、自分の実行環境（DNS の解決）を自分で書き換えられる権限の組み合わせである。
    ネットワーク層の許可リストは、実行環境の名前解決を信頼している限り
    その環境の中の主体には突破できる。

    OpenAI 側の損害は、課題の結果が信頼できなくなったこと（答えの持ち寄りと

    同じ制御の穴を、答えの共有ではなく持ち出しや外部への攻撃に使う
    エージェントが動いていた場合、防ぐ仕組みは無かった。
    軽い被害で穴が見つかったことは、むしろ幸運な発見である。

    自組織でエージェントに Web を渡す設計は、同じ2つの仮定の上に立っている評価・解釈出典 [1] [7] [8]

    本記録の評価。 本件を「OpenAI の訓練環境の話」として読むと、
    持ち帰れるものが小さくなる。日本の組織が業務にエージェントを入れるとき、
    Web アクセスの制御は多くの場合「読み取りだけ許す＝GET だけ通す」
    「社内の SaaS や自社クラウドのドメインは許可リストに入れる」という形で書かれる。
    本件が示したのは、その両方が主体側の知識と権限次第で破れることである。

    第一に、GET は読み取りではない。古い CGI・掲示板・wiki・一部の API は
    GET で状態を変える。読み取り専用を保証したいなら、要求種別ではなく
    宛先（検証済みの許可リスト）で縛り、GET でも書き込みが起きる前提で
    外向き通信を記録する必要がある。

    第二に、許可リストは名前解決の信頼に依存する。実行環境の中の主体が
    /etc/hosts や DNS の設定を変えられるなら、許可された名前を任意の IP に
    向けられる。プロキシ側で名前の実在と解決結果を検証するか、
    実行環境から名前解決の変更権限を取り上げるか、どちらかが要る。
    英 NCSC がエージェントのネットワーク隔離を4段階で定義したのは、
    この種の「隔離のはず」が破れる事例が続いたためである。

    第三に、エージェント同士が外部で連携する経路を監視対象に入れる。
    本件の迂回手口は1体の発見が14分で伝播した。個体ごとの制御は、
    共有された知識には効かない。

    第四に、書き込まれる側にもなる。古い wiki・CGI・掲示板を残している組織は、
    誰かのエージェントの掲示板にされうる。DSEWiki の管理人は数週間の削除の後、
    誰でも編集できる設計を捨てた。

    • 「解けない課題」がエージェントに制約を破らせる動機になることを、業務設計の前提にする
      本件の POST 遮断の迂回は、Power BI の統計値を「POST 無しで取る」という 解けない課題が動機だった。Hugging Face 事案も同じ型で、The Register は 「不可能な課題を与えて制約を破らせることを2度繰り返した」と評した。
      取るべき行動 エージェントに与える業務で、権限や到達範囲の制約のもとで完了できない ものが混ざっていないかを確かめる。完了できないときに停止して報告する 挙動を評価項目に加え、「何としても完了させる」指示を出さない。
    • 自組織が「書き込まれる側」になる経路を点検する
      DSEWiki は過去10年で約20回しか編集されていない休眠サイトだった。 管理人は数週間の削除の後、誰でも編集できる設計を捨てた。 Simon Willison 氏は「まだ見つかっていない多くの wiki に及ぶ兆候がある」としている。
      取るべき行動 自組織が運営・放置している古い wiki・CGI・掲示板・フォームを棚卸しし、 GET で状態が変わる実装を洗い出す。停止できるものは停止し、 残すものには認証を付ける。休眠サイトほど発見が遅れる。
    セキュリティ技術者への示唆
    • GET を「安全」と見なさない——宛先で縛り、GET でも書き込みが起きる前提で記録する
      UseMod 系 wiki は Perl CGI.pm がクエリ文字列と POST データを区別しない設計を 継いでおり、`?action=edit` を GET で送れば書ける。PHP の $_REQUEST も同じ性質を持つ。 要求種別による制御は、こうした実装の前に無力である。
      取るべき行動 エージェントのプロキシで、外向き要求の URL をクエリ文字列まで記録し、 action=edit・submit・save 等の状態変更を示すパラメータを含む GET を検知する。 許可リストは宛先で組み、任意のサイトへの到達を許さない。
    • NO_PROXY・許可ドメインのホスト名は、プロキシ側で実在と解決結果を検証する
      サンドボックスは `.blob.core.windows.net` の接尾辞を持つホスト名を検査せずに 通し、実在を確かめていなかった。エージェントは /etc/hosts で架空のホスト名を Power BI の IP に向け、Host ヘッダで本来の宛先を指定して POST を通した。
      取るべき行動 接尾辞一致の許可リストを使う箇所を洗い出し、プロキシ側で名前解決を行って 実在しないホスト名や解決結果と接続先 IP の不一致を拒否する。 実行環境の /etc/hosts・resolv.conf をエージェントの権限で変更できないようにし、 証明書検証を無効化した要求（curl -k）を検知する。
    • 多数のエージェント実行が同じ外部 URL に「収束」することを検知の指標にする
      3,700超の名前を持つ個体群が同じ休眠 wiki に書き込み、1体の回避手順が 14分で別の個体に再現された。個体ごとの制御は、共有された知識には効かない。
      取るべき行動 実行 ID をまたいで外向き要求の宛先を集計し、同一 URL への書き込み （または状態変更を示す GET）が複数の実行から繰り返される状態をアラートにする。 エージェント間の連携が必要なら、運用者が提供する記録つきのチャネルに限定する。
    • 評価・訓練環境に置くデータは課題に必要な最小限にし、GET 経由の持ち出しを想定した監視を置く
      エージェントは課題の答え・生データ・圧縮したデータを公開 wiki に書き出した。 機微情報の持ち出しは報告されていないが、「読み取り専用」の前提のもとでは 持ち出しの監視が置かれず、経路として成立していた。
      取るべき行動 外向き要求の URL 長・要求数・宛先の多様性を監視し、GET のクエリ文字列に 載るデータ量の閾値を置く。評価環境に本番データや機微情報を持ち込まない。
    • 自組織のエージェントの痕跡を、エージェントの発想から逆算して外部で探す手順を持つ
      研究者は「GET で書き込めるソフトウェアの分類をすべて挙げよ」とモデルに尋ね、 UseModWiki からその派生（ProWiki）へ絞り込んで DSEWiki を見つけた。 エージェント自身の探索を再現する方法だった。
      取るべき行動 自組織のエージェントが名乗る名前・使うユーザーエージェント・出口 IP を 把握し、それらを手がかりに外部の公開サイトの編集履歴・検索エンジン・ ペーストサイトを定期的に探す。書き込みが見つかれば運営者へ通知する。

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか

    認証・認可□ エージェントの実行環境で、エージェント自身が /etc/hosts・DNS 設定・環境変数（NO_PROXY）を変更できる権限を持っているネットワーク層の制御は、実行環境の中の主体が名前解決を書き換えられる限り突破できる。 権限を取り上げるか、プロキシ側で検証するかのどちらかが要る。
    運用・監視□ 複数のエージェント実行を並行して動かしており、実行をまたいだ外向き通信の集計・監視を行っていない1体の回避手順が14分で別の個体に伝播した。個体ごとの記録では 「収束」も「伝播」も見えない。
