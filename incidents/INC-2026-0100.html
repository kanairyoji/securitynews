INC-2026-0100JetBrains Cadence、未修正の自社 TeamCity から侵入

JetBrains のクラウド計算サービス Cadence が、自社製 TeamCity の既知の脆弱性 CVE-2026-63077（KEV 収載済み）を当てていなかった自社サーバから侵入され、利用者の氏名・メールアドレス・2024年のサーバ全量バックアップ・AWS IAM の認証情報・S3 のファイルが取られた——同社は「当てるべきだったが当てていなかった」と認め、Cadence に渡した鍵と PyCharm から同期したソースを「漏れたもの」として扱うよう求めたが、対象人数は示していない

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）脆弱性の放置既知の脆弱性の悪用
初報: 2026年8月28日 最終更新: 2026年9月7日

JetBrains は2026年8月28日、PyCharm から機械学習などの重い処理をクラウドの GPU に
投げるサービス Cadence が侵害されたと公表しました。Cadence は処理の
オーケストレーションに同社製の CI サーバ TeamCity を使っており、その TeamCity に
同社が7月27日に公表していた未認証のデシリアライズ脆弱性 CVE-2026-63077
（CVSS 9.8。米 CISA が8月5日に KEV へ収載）が当てられていませんでした。
同社は「このサーバは脆弱性対応の一環として修正されているべきだったが、
そうなっていなかった」（原文英語）と認めています。
侵入は8月8日から24日で、同社が気づいたのは8月23日、サーバ
api.cadence.jetbrains.com を切り離したのは翌24日です。
取られたと同社が確認したのは、利用者の氏名・ユーザー名・メールアドレス・
最終ログイン時刻と IP、2024年のサーバ全量バックアップ（認証情報・設定・
成果物・ログを含む）、そのバックアップから抜かれた複数の AWS IAM ユーザーの
認証情報（同社社員のものを含む）、Cadence が使う同社 AWS アカウント内の
S3 のファイルです。PyCharm からサーバへ同期したプロジェクトのソースコードも
見られた可能性があり、9月3日の最終更新では、現行の利用者のメールアドレス・
ソースコード・認証情報を置くストレージにも到達できた状態だったと追加しました。
同社はプラグインのアクセストークンをすべて失効させ、利用者には Cadence に
渡した認証情報の全面的な更新と、8月8日以降の AWS・S3・レジストリ・リポジトリの
監査、Cadence の実行の入出力をすべて「信頼できないもの」として扱うことを求め、
悪用元の IP アドレス6件を公開しました。攻撃者と対象人数は示されていません。
本記録は、同社の公表と報道を分けて整理します。

    同社は「2026年8月23日に悪用を発見した」とのみ述べ、自社の監視で見つけたのか、 外部からの指摘か、鍵の不正使用が先に見つかったのかを示していない。

    同社は S3 のファイルが「侵害された」と確認する一方、9月3日の更新では 現行の利用者のストレージについて「到達できたアクセスを得ていた」と述べ、 実際に読まれたかは示していない。予防的に露出したものとして扱うとしている。 どのバケットのどれだけが読まれたかは公表されていない。

    同社は「関係当局に通知している」と述べるが、どの国のどの当局 （データ保護当局・法執行機関）かを示していない。JetBrains はチェコに 本社を置くため EU の GDPR の下での通知が想定されるが、公表資料には無い。

    公表は Cadence に限られており、TeamCity Cloud や他のサービスへの影響の 有無は述べられていない。TeamCity の勧告は TeamCity Cloud を影響外としている。 「影響なし」と明示したわけではない。

約2年前のバックアップに、現行でも使える AWS IAM の認証情報が入っており、
それがサーバから到達できる場所に置かれていた。バックアップは「復旧のための
複製」であると同時に「鍵の複製」でもあり、本番と同じ強さで守らなければ、
本番を守っても意味が無い。

同社は鍵の失効と IP の公開を5日で行い、利用者には「Cadence に渡した鍵はすべて漏れたものとして扱え」と求めた——負担は利用者側に移っている組織の対応出典 [1] [2]

同社の対応は、発見の翌日（8月24日）にサーバをオフラインにし、公表（8月28日）で
PyCharm の Cadence プラグインが使うアクセストークンをすべて失効させ、影響を受けた
利用者に直接連絡し、関係当局に通知し、悪用元の IP アドレス6件と侵害の兆候を
公開する、というものだった。発見から公表まで5日である。

利用者に求めた対応は具体的である。Cadence の実行に使った可能性のある認証情報と
シークレットをすべて失効・更新すること。失効させた鍵で到達できる接続先——
AWS アカウント・S3・デプロイ環境・パッケージやコンテナのレジストリ——を
不審な活動について確認すること。ソースコードのリポジトリを、当該期間に
不正な変更が無かったか監査すること。そして「Cadence プロジェクトの実行は、
その入力と出力を含めてすべて信頼できない可能性があるものとして扱う」
（原文英語）こと。

兆候として挙げられたのは、2026年8月8日以降の活動、とくに Cadence に置かれていた
認証情報を使った認証、想定外の IP や場所からのアクセス、想定外のリポジトリの
クローンやダウンロード・コミット、リポジトリのシークレット・Webhook・
共同編集者・権限の変更、外部サービスでの新規または変更されたトークンや SSH 鍵、
新規サービスアカウント、クラウド IAM のロール・ポリシーの変更、S3 などの
ストレージへの想定外のアクセス、パッケージやリリースの想定外の公開や変更である。

本記録の評価として、封じ込めと公表の速さ、兆候の具体性は評価できる。
一方で、この事案の実質的な後始末は利用者側に移っている。Cadence に渡した鍵で
何ができたかは利用者ごとに違い、同社は「すべて漏れたものとして扱え」としか
言えない。8月8日から公表の8月28日まで、利用者は自分の鍵が漏れていることを
知らずに20日を過ごしている。対象人数が示されていないため、この負担の総量も
外からは見えない。

開発基盤を預けた側が取るべき手順の見本になる——鍵の全面更新、8月8日以降の監査、実行結果を信頼しない評価・解釈出典 [1] [3] [4]

本件は、開発者が IDE から直接使うクラウドサービスの侵害である。
利用者が Cadence に渡していたのは、処理を走らせるための認証情報——
AWS の鍵、レジストリのトークン、リポジトリのアクセス権——と、
PyCharm から同期したソースコードそのものである。こうしたサービスの侵害は、
サービス側の被害ではなく、利用者それぞれの AWS・レジストリ・リポジトリの
侵害として現れる。

同社が示した手順は、この種の事案で利用者が取るべき順序をそのまま示している。
第一に、渡した鍵を全部更新する。どれが使われたかを調べてから決めるのではなく、
全部を漏れたものとして扱う。第二に、鍵で到達できる先を、侵入の開始日
（8月8日）以降について監査する。第三に、そのサービスで実行した処理の
入出力を信頼しない。侵入されたサーバ上で走った処理は、結果が改変されて
いる可能性がある。

日本の読者にとっての含意は二つある。Cadence を試した開発者は、上の手順を
そのまま実行する。TeamCity をオンプレミスで運用する組織は、2025.11.7／2026.1.3
への更新か、2017.1 以降に当てられるセキュリティパッチプラグインの適用が
終わっているかを、サーバの一覧と突き合わせて確認する。KEV に載った脆弱性は、
勧告を出した当人ですら3日で突かれた。国内でも同じ速さで突かれると考えるべきである。

なお、本件で取られた IoC（IP アドレス6件）は同社が観測した悪用元であり、
本記録の作成者は悪性を独自に検証していない。

対象人数と「なぜ当たっていなかったか」は公表されていない未確定事項出典 [1] [2]

同社の公表は、侵入口・期間・取られた情報の種別・利用者への要請・IoC において
具体的である。一方で、本記録の作成者が2026年9月7日に本文を確認した限り、
影響を受けた利用者の人数、修正が当たっていなかった理由、検知の端緒、
攻撃者の正体、通知先の当局、他のサービスへの影響の有無は、いずれも
公表されていない。

「なぜ当たっていなかったか」が最も重い。資産の把握から漏れていたのか、
当てる判断が遅れたのか、当てたつもりで失敗していたのかで、同じ組織が次に
取るべき手当てが変わる。同社は「修正されているべきだった」と認めるにとどまり、
その先を語っていない。人数についても、「直接連絡した」以上の情報が無い。
同社が対象者を特定できているなら、人数を示すことは調査中でも可能だった。

発見の翌日に、悪用されたサーバをオフラインにした機能した本記録の作成者の評価である。発見から1日での切り離しは速い。 ただし発見までに15日が経っており、切り離しの速さは被害の大きさを 取り戻すものではない

侵入口（自社の未修正の脆弱性）・期間・取られた情報の種別・IoC・利用者への 要請を公表し、「修正されているべきだったが、そうなっていなかった」と 自らの落ち度を明記した。一方、対象人数、当たっていなかった理由、 検知の端緒は示していない部分的に機能本記録の作成者の評価である。侵入口と自らの落ち度を隠さなかった点、 IoC と兆候を具体的に示した点は、利用者にとって実用的である。 しかし対象者を特定できているのに人数を示さないこと、「なぜ当たっていなかったか」 を語らないことは、事案の規模と再発防止を外から評価する材料を欠く
発見から5日、サーバのオフライン化から4日で公表した。その後、8月31日・ 9月1日・9月3日と同一ページを更新し、9月3日に追加の露出を認めた機能した本記録の作成者の評価である。5日は速く、更新の日時も明記されている。 追加の露出が後から出たことは、初報を待たずに出した代償であり、 同社は「同じ利用者群」で追加の対象者が無いことを示して補っている

  • 検知の端緒が公表されていない

CISO・経営層への示唆
  • 修正版を持っていることと、当てるべき資産を把握していることは別の仕事である
    本件の修正版は被害組織が自分で作り、勧告も自分で出し、KEV 収載と 「実際の悪用の報告」も侵入の前にあった。それでも自社の Cadence サーバには 当たっておらず、同社は「当てるべきだったが当てていなかった」と認めた。 修正の遅れではなく、当てる対象の一覧の問題である。
    取るべき行動 KEV 収載や自社製品の勧告を受けたとき、「修正を出したか」ではなく 「自社で動いている全インスタンスに当てたか」を、資産台帳と突き合わせた 件数で報告させる。台帳に無いインスタンスを探す手順（外部からのスキャン・ クラウドの棚卸し）を勧告対応の標準に組み込む。
  • KEV 収載から侵入まで3日しか無かった——勧告対応の期限は「週」ではなく「日」で切る
    勧告の公表から12日、KEV 収載から3日、自社が「実際の悪用の報告」を 追記した翌日に侵入が始まった。CISA の KEV は米連邦機関向けの期限を伴うが、 攻撃者はその期限を待たない。
    取るべき行動 インターネットに面した CI/CD・開発基盤について、KEV 収載または 「実際の悪用」の報告を受けた時点で72時間以内に適用または切り離しを 完了する運用を決め、達成率を測る。間に合わない場合は外部到達面を先に閉じる。
  • バックアップに鍵が入っていれば、サーバの侵害はクラウドの侵害になる
    AWS IAM の認証情報は、2024年のサーバ全量バックアップから抜かれた。 約2年前のバックアップに現行でも使える鍵が入っており、サーバから到達できる 場所にあった。バックアップを守る強さが、本番の鍵を守る強さを決めていた。
    取るべき行動 バックアップに含まれる認証情報を棚卸しし、シークレットをバックアップから 分離するか、バックアップの暗号化と到達制御を本番の鍵と同じ基準に揃える。 あわせて鍵のローテーション周期を決め、2年前の鍵が生きている状態を無くす。
  • 開発者が IDE から直接使うクラウドサービスは、契約や調達の目に触れないまま本番の鍵を預かっている
    Cadence は PyCharm のプラグインから使うサービスで、利用者は処理のために AWS の鍵やレジストリのトークン、ソースコードそのものを渡していた。 侵害はサービス側ではなく、利用者それぞれの AWS・レジストリ・リポジトリの 侵害として現れる。同社は「渡した鍵はすべて漏れたものとして扱え」と求めた。
    取るべき行動 開発者が個人の判断で使う外部の計算・実行サービスを棚卸しし、そこへ渡している 鍵の権限と有効期限を確認する。本番に届く鍵を渡している場合は、サービス専用の 最小権限・短寿命の鍵に切り替える。
セキュリティ技術者への示唆
  • TeamCity をオンプレミスで運用しているなら、CVE-2026-63077 の適用状況をサーバの一覧で確認する
    修正版は 2025.11.7／2026.1.3、2017.1 以降にはセキュリティパッチプラグインが ある。未認証・HTTP(S) 到達・RCE であり、KEV 収載済み。開発元自身が 当て漏らして侵入された。
    取るべき行動 TeamCity の全インスタンス（検証・個人用・忘れられたものを含む）を列挙し、 版とプラグインの適用を確認する。インターネットに面しているものは VPN や 追加の認証層の後ろに置く。同社の勧告が推奨している運用である。
  • Cadence を使ったことがあるなら、渡した鍵を全部更新し、8月8日以降を監査する
    同社は Cadence に置いた、バックアップに含まれた、または実行から到達できた 認証情報とシークレットをすべて「漏れたもの」として扱うよう求めている。 PyCharm から同期したプロジェクト内の認証情報も対象である。
    取るべき行動 AWS・S3・デプロイ環境・パッケージやコンテナのレジストリの鍵を失効・更新し、 2026年8月8日以降のリポジトリのクローン・コミット・シークレット・Webhook・ 共同編集者の変更、IAM のロールとポリシーの変更、想定外の IP からの認証を 確認する。同社が公開した IP アドレス6件をログと突き合わせる。
  • 侵害されたサーバで走った処理の入出力は、結果ごと信頼しない
    同社は「Cadence プロジェクトの実行は、その入力と出力を含めてすべて 信頼できない可能性があるものとして扱う」（原文英語）よう求めた。 侵入された実行基盤の上で走った処理は、結果が改変されている可能性がある。
    取るべき行動 侵入期間（8月8日〜24日）に Cadence で生成したモデル・成果物・データを 特定し、再実行するか、信頼できる環境で検証してから使う。 成果物に出所（どの基盤でいつ生成したか）を記録する運用を持つ。
  • CI サーバのバックアップから鍵が抜かれた——シークレットの保管場所とバックアップの到達制御を確認する
    AWS IAM の認証情報は2024年のサーバ全量バックアップに含まれており、 侵害されたサーバから到達できた。バックアップの中の鍵はローテーションされて いなければ現行でも使える。
    取るべき行動 CI サーバのバックアップに含まれる認証情報・設定・成果物を棚卸しし、 シークレットはシークレット管理基盤に移して短寿命化する。バックアップの 保管先は本番のサーバから書き込み専用にし、読み出しは別の認証で守る。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 開発者が IDE や CLI から直接使うクラウドの計算・実行サービス（GPU 計算・リモート実行・ホスト型 CI）に、本番や検証の AWS 等の鍵やソースコードを渡している該当する場合、そのサービスの侵害は自組織の AWS・レジストリ・リポジトリの侵害として 現れる。本件で同社は「渡した鍵はすべて漏れたものとして扱え」と求め、後始末は 利用者側の作業になった。人数は公表されておらず、自分が対象かどうかは同社からの 連絡でしか分からない。
運用・監視□ TeamCity On-Premises を運用しており、CVE-2026-63077 の修正（2025.11.7／2026.1.3、または 2017.1 以降のセキュリティパッチプラグイン）を全インスタンスに当てたことをサーバの一覧で確認していない未認証・HTTP(S) 到達・RCE で KEV 収載済みである。開発元自身が自社サーバに 当て漏らし、KEV 収載の3日後に侵入された。検証用や個人用のインスタンスが 一覧から漏れていれば、そこが入口になる。
運用・監視□ KEV 収載や自社が使う製品の「実際の悪用」の報告を受けたとき、修正を全インスタンスに当て終えるまでの日数を測っておらず、72時間以内に完了する運用が無い本件は勧告から12日、KEV 収載から3日、「実際の悪用の報告」の翌日に侵入された。 週単位の運用では間に合わない。
データの保持□ サーバの全量バックアップに、クラウドの IAM 鍵・API トークン・設定ファイル内の認証情報が平文で含まれており、バックアップの到達制御が本番の鍵より緩い本件の AWS IAM の認証情報は約2年前のバックアップから抜かれた。バックアップは 鍵の複製でもあり、そこが本番より弱ければ、サーバの侵害がクラウド全体の侵害に 広がる。
認証・認可□ クラウドの IAM 鍵や API トークンにローテーション周期が無く、2年以上前に発行した鍵が現在も有効である2024年のバックアップの鍵が2026年に使えたことは、その間ローテーションされていなかった ことを示唆する。周期があれば、古いバックアップから抜かれた鍵は失効していた。
システム構成□ 処理を実行する基盤の鍵で、利用者のソースコードや認証情報を置くストレージまで到達できる（実行基盤とデータ保管の権限が分かれていない）本件では、侵害されたサーバから S3 のファイルと現行の利用者のストレージまで到達できた。 実行基盤の鍵を最小権限にし、保管系を別の認証で守っていれば、到達できる範囲は狭かった。
