INC-2026-0104Mathspace、未修正の Metabase から108万人分流出

豪州の数学学習プラットフォーム Mathspace が、自社ホストの Metabase に8月6日公開の重大な勧告と修正版を当てていなかったため管理者権限を取られ、豪州・NZ の生徒・保護者・教職員・自社スタッフ 1,079,819人の氏名・メールアドレス・アカウント詳細を持ち出された——侵入は8月10日、持ち出しは8月27日、修正は8月29日で、修正時に推奨された侵害チェックをしなかったため「既に入られていた」ことに気づいたのは9月3日。同社は「勧告を拾い上げなかった」「侵害チェックをしなかった」と自ら認め、両プロセスを改めると明言している

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）脆弱性の放置既知の脆弱性の悪用ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年9月5日 最終更新: 2026年9月7日

豪州シドニーに本拠を置く数学学習プラットフォーム Mathspace は2026年9月5日（9月6日更新）、
社内レポーティングに使う自社ホストの Metabase の脆弱性を突かれて管理者権限を取られ、
豪州・ニュージーランドの生徒・保護者・教職員・自社スタッフ 1,079,819人の情報が
ダウンロードされたと公表しました。取られたのは user ID・username・姓名・メールアドレス・
国・タイムゾーン・user type・メール確認状態・最終アクティブ日・最終ログイン日・登録日で、
学習記録・成績・パスワード（ハッシュ）・認証トークン・SSO や API の資格情報は含まれません。

同社の説明で目を引くのは、原因を自ら明快に書いている点です。Metabase は8月6日に重大な勧告と
修正版を公開していましたが、「既存の脆弱性通知プロセスはこの勧告を特定・エスカレーションしなかった」。
不正アクセスは8月10日（豪州東部標準時）に始まり、8月27日に豪州のレポーティング DB から
情報がダウンロードされ、同社が別の Metabase の通知に気づいて更新したのは8月29日でした。
しかも更新時に「潜在的に影響を受けたシステムに推奨される追加の侵害チェックを完了していなかった」ため、
修正前に既に侵入されていたと確認できたのは過去のアクセスログを見直した9月3日です。

9月3日に Metabase をオフラインにし、API キーの失効・Snowflake の DB アクセスアカウントの無効化・
DB パスワードの変更・ログの保全を行い、9月4日に学校の連絡先への通知と豪州・NZ の4当局への報告、
9月6日から個人への通知を始めました。公開・売買・悪用の証拠は無く、攻撃者の身元は不明としています。
報道は同じ Metabase の脆弱性で Trezor/ShipMonk・Framework・Tally が被害を受け、恐喝集団
ShinyHunters の関与が伝えられているとしていますが、Mathspace 自身は攻撃者を特定していません。

本記録は、「勧告が出た（8/6）→侵入（8/10）→持ち出し（8/27）→修正（8/29）→侵害確認（9/3）」という
順序、つまり修正が持ち出しの2日後で、修正しても侵害チェックをしなければ「塞いだ後に既に
入られていた」ことに気づけないという構造を、Metabase を自社ホストする国内組織にも当てはまる
先例として記録します。同社が「以前の連絡ではアカウント詳細を十分に説明していなかった」と
自ら訂正した点も、訂正の記録として残します。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

自社ホスト版の更新は利用者の作業だった。Mathspace は自社ホストで、更新は勧告の23日後になった。

同社の説明で重要なのは、更新の後の記述である。

並べると、勧告（8月6日）→侵入開始（8月10日・豪州東部標準時）→豪州のレポーティング DB からの
ダウンロード（8月27日）→更新（8月29日）→侵害の確認（9月3日）である。修正は持ち出しの2日後で、
間に合っていない。加えて、修正時に侵害チェックをしなかったため、「塞いだ後に既に入られていた」
ことに気づくまでさらに5日を要した。同社は「なぜ最初の勧告がエスカレーションされなかったか、
なぜ侵害チェックがもっと早く完了しなかったかを調査しており、インシデント対応の一環として
両方のプロセスを変更する」（原文英語）と述べている。

本記録は原因の分類を「脆弱性の放置（patch-management）」「既知の脆弱性の悪用
（vulnerability-exploit）」に加え「ガバナンス（governance）」とした。勧告を拾い上げる
プロセスの不全を同社自身が原因として挙げているためである（本記録の判断）。

持ち出されたのは 1,079,819人の氏名・メールアドレスと12項目のアカウント詳細で、パスワード・学習記録は含まれない——ただし「氏名とメールアドレスだけより多い」と同社が自ら訂正した被害規模・影響範囲出典 [1]

同社は「合計 1,079,819人が影響を受け、生徒・教職員・保護者を合わせた数である。豪州と
ニュージーランドの人のみが影響を受けた」（原文英語）とし、範囲の調査は完了して影響を受けた
アカウントとレコードを特定したと述べている。Mathspace スタッフの記録も含まれる。

持ち出された項目は、user ID・username・姓・名・メールアドレス・国・タイムゾーン・user type・

本記録の評価として、この留保は重要である。生徒のメールアドレスが学校ドメインなら、

なお、現在利用していない人も対象になりうる。「アカウントが現在アクティブである必要は無い。

Metabase は本記録の作成時点でもオフラインで、「不正なアカウントとセッションへの対処と、

いない」としている。

本記録は、脆弱性が CVE-2026-72898 であることを「8月6日の Metabase の重大な勧告と修正版」という

ついて伝えたものとして、Mathspace の公表と分けて扱う（discrepancies 参照）。

自社ホストの BI ツールが顧客 DB に直結する構造は VOISING・ShipMonk と同型で、Metabase を自社ホストする国内組織は同じ勧告の対象だった——「勧告を受け取る経路」と「修正後に侵害を確認する手順」の2つが本件の教訓評価・解釈出典 [1] [2] [3] [4]

1. 構造は珍しくない。 社内の分析・レポーティング用の BI ツールが、顧客データを持つ
データベース（本件では豪州・米国の Snowflake と Cloud SQL）に直接接続している構造は、
VOISING（INC-2026-0086。社内 BI ツール経由で最大約17万人）、ShipMonk（INC-2026-0098。
委託先の Metabase に5年前のデータが残っていた）と同型である。BI ツールは「読むための道具」なので
接続先 DB に広い読み取り権限を持ちやすく、管理者権限を取られれば接続先の全データが読める。
本件では豪州の DB からのダウンロードのみが確認されているが、米国の Snowflake にも Metabase の
アクセスアカウントがあったことは封じ込めの記述から分かる。

23日かかったこと自体は、自社ホストのソフトウェアでは珍しくない。本件が先例として価値を持つのは、

いなかった」と認めた点が共通する。

5. 公表の質。 原因を自ら明快に書き、通知の順序の理由を説明し、「以前の連絡は項目を十分に

CISO・経営層への示唆
  • 「勧告を受け取る経路」が無ければ、修正版があっても当たらない。自社が使うソフトウェアの公式勧告が誰に届き、誰が優先度を判断するかを確認する
    Mathspace は8月6日の勧告を「脆弱性通知プロセスが特定・エスカレーションしなかった」と認めた。 勧告は CEO ブログ・GitHub Security Advisory・顧客通知・CVE/KEV・JPCERT/CC の注意喚起と 複数の形で出ていたが、8月29日まで届かなかった
    取るべき行動 自社ホストで使っているソフトウェア（BI・CI/CD・監視・チケット等）を一覧にし、それぞれの 公式セキュリティ勧告の購読先（GitHub の Security Advisory の Watch・ベンダーの通知メール・ JPCERT/CC 注意喚起）と、届いた勧告を誰がどの基準でエスカレーションするかを今月中に確かめる。 「誰も購読していない」ソフトウェアがあれば、それが本件の Metabase に当たる
  • 既知の脆弱性を後から当てるときは「既に入られている前提」で侵害チェックをする——修正だけでは「塞いだ後に既に持ち出されていた」ことに気づけない
    Mathspace は8月29日に更新したが推奨された侵害チェックをせず、8月27日に持ち出しが 完了していたことを知ったのは9月3日だった。KEV 収載の脆弱性は「実際に悪用されている」 脆弱性なので、公開から日数が経ってから当てる場合は侵害の可能性が高い
    取るべき行動 脆弱性対応の手順に「KEV 収載または CVSS 9 以上で、公開から一定日数（例: 3日）を過ぎてから 当てる場合は、修正と同時にベンダー推奨の侵害チェック（不正な管理者アカウント・セッション・ API キー・ログのパターン）を実施し、結果を記録する」を加える。チェックの完了を修正の完了条件にする
  • 社内向けの BI ツールは「読むだけの道具」だが、顧客 DB への広い読み取り権限を持つ。侵害されれば顧客データの全量が出る
    本件の Metabase は豪州・米国の Snowflake と Cloud SQL に接続しており、管理者権限を取られた 結果 108万人分が読まれた。VOISING（INC-2026-0086）・ShipMonk（INC-2026-0098）も同型である
    取るべき行動 自社の BI・分析ツールが接続している DB と、そのアカウントの権限（全テーブルの読み取りか、 ビューに限定か）を棚卸しする。個人情報の生データに直接届く構成なら、マスク済みビューや 集計テーブル経由に変える計画を立てる。インターネットから直接到達できる BI ツールは 認証プロキシの背後へ移す
  • 対象に子どもが含まれる場合、学校（保護者と接点を持つ組織）を先にした通知と、通知の真正性を確認する方法の提示は参考になる
    Mathspace は学校を先にし（9月4日）、学校がコミュニティとの連絡を調整できるようにした上で 個人に通知した（9月6日）。学校の要望で前倒しし、通知メールの真正性を確認する方法 （窓口へ新規メール・自分で公式サイトへ）を示した
    取るべき行動 自社のサービスが子どもや、保護者・所属組織を介して連絡すべき利用者を持つ場合、 通知の順序（所属組織→個人）と、所属組織が自組織の対象者を請求できる窓口を、 インシデント対応計画に前もって書いておく。通知メールが本物かを利用者が確かめる方法も 雛形に入れる
  • 原因を自ら明快に書き、訂正を明示し、事後レビューの結果を同じ場所で報告すると約束する公表は、信頼を保つ
    Mathspace は「勧告を拾い上げなかった」「侵害チェックをしなかった」と2点を具体的に書き、 「以前の連絡は項目を十分に説明していなかった」と訂正し、レビュー結果の報告を約束した
    取るべき行動 公表文の雛形に「原因（自社のプロセスのどこが機能しなかったか）」「以前の連絡との差分」 「事後レビューの報告時期と場所」の3欄を置く。訂正が必要になったとき、黙って差し替えず 「以前は〜と説明していた」と書く方針を決めておく
セキュリティ技術者への示唆
  • GitHub Security Advisory とベンダーの通知を機械的に受け取り、自社の SBOM／資産一覧と突き合わせて担当者にチケットを切る
    Metabase の勧告は GitHub Security Advisory（GHSA-vwf4-m7j8-wcjf）として8月6日に出ていた。 人が読むメールに頼ると「特定・エスカレーションされない」ことが起きる
    取るべき行動 自社ホストの OSS・製品ごとに GitHub の Security Advisory の Watch（または OSV・GHSA の API）を設定し、CVSS・KEV 収載と突き合わせて自動でチケットを作る。KEV 収載は CISA の JSON フィードで日次に取り、自社の資産一覧と照合する
  • 修正を当てる手順に、ベンダーが推奨した侵害チェックを組み込む——Metabase の場合は不正な管理者アカウント・セッション・API キーの確認と接続先 DB 資格情報のローテーション
    Mathspace は8月29日の更新時にこれを省き、9月3日に「過去のアクセスログの精査」で 侵入に気づいた。同じチェックを8月29日にしていれば5日早く封じ込められた
    取るべき行動 Metabase を自社ホストしている場合、今すぐ ①バージョンが修正版（0.58.24 / 0.59.21 / 0.60.17 / 0.61.11 / 0.62.9 / 0.63.5 以上）か、②修正前に作られた管理者アカウント・API キー・ セッションが無いか、③Metabase の勧告が示した侵害指標がログに無いか、④接続先 DB の 資格情報を更新したか、を確認する。他のソフトウェアでも、勧告の「侵害の確認方法」を 修正手順の必須項目にする
  • BI ツールのサービスアカウントは接続先 DB で最小権限にし、大量取得をデータ基盤側のクエリ履歴で検知する
    Metabase の管理者は接続先 DB へ任意のクエリを発行でき、本件では 108万件がダウンロードされた。 同社が気づいたのは7日後で、ダウンロードの記録はログにあった
    取るべき行動 Snowflake・BigQuery 等のクエリ履歴で、BI ツールのサービスアカウントによる行数の多い取得や 平時と異なる時間帯のクエリをアラート化する。BI ツール側のエクスポート件数にも上限としきい値を 置く。個人情報のカラムはマスク済みビュー経由でしか読めないようにする
  • 社内向け BI ツールをインターネットに直接さらさない。さらすなら未認証エンドポイントを前段で遮る
    本件の脆弱性は未認証のエンドポイントへの SQL インジェクションで、インターネットから 到達可能なインスタンスは全て対象だった（INC-2026-0009）。社内レポーティング用の Metabase がインターネットから到達できた
    取るべき行動 社内向けの Metabase・Grafana・Redash 等は VPN か IdP 連携の認証プロキシの背後に置く。 やむを得ず公開する場合は、WAF や前段のプロキシで未認証エンドポイント（Metabase では パスワードリセット API 等）への外部からのアクセスを遮る。JPCERT/CC の注意喚起が示した 一時的回避策はこの形だった
  • 侵害確認の当日に「アプリ DB の複製とアクセスログのエクスポート」を行った保全の手順を、自社でも前もって決めておく
    Mathspace は9月3日に Metabase を止めると同時にアプリケーション DB を複製しログを保全し、 その後の調査で8月10日・27日を特定できた。ログが無ければ「いつから・何が」は分からなかった
    取るべき行動 主要な社内ツールごとに「止める前に保全するもの」（アプリ DB・アクセスログ・セッション表・ API キー一覧）を手順に書き、ログの保存期間が調査に足りるか（本件は最低24日遡る必要があった）を 確認する。可能ならログを外部の収集基盤へ転送しておく
