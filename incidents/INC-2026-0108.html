INC-2026-0108ベトナム関連 APIS の2.2億件の旅客記録が露出

ベトナムに関連する乗客事前情報システム（APIS）の Elasticsearch クラスタ「pax-info」が、直接は 401 を返すのにクラウド経由の別経路と既定の認証情報の連鎖で誰でも読める状態にあり、2017年1月〜2026年4月にベトナムを発着・経由した旅客210,318,069件・乗員10,465,631件（合計220,783,700件）の氏名・生年月日・国籍・旅券番号と有効期限・便名・座席・手荷物参照が露出していた——研究者 Kinryū Labs が6月3日に発見・通報し、6月8日に遮断。運用主体は特定されず、ベトナム当局は回答せず、ログが無いため複製の有無は分からない。日本発着の旅客も含まれうる

意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ日本に波及した海外事案設定不備認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年9月8日 最終更新: 2026年9月8日

セキュリティ研究者グループ Kinryū Labs は2026年6月3日、ランサムウェア活動の調査の一環で露出したデータベースを調べていた際に、ハノイの Viettel 割当 IP 空間で 「pax-info」と名づけられたElasticsearch クラスタ（29インデックス・約107GB） を発見しました。2つの主要インデックスに旅客210,318,069件と乗員10,465,631件、合計220,783,700件の記録があり、2017年1月から2026年4月にベトナムを発着または経由した多国籍の旅客・乗員の氏名・生年月日・性別・国籍・旅券（渡航文書）番号と有効期限・発行国、便名・日付・航空会社・出発地／目的地／経由地・座席・手荷物参照・予定／推定／実際の発着時刻を含んでいました。BleepingComputer が2026年9月8日に報じ、本記録はその日次ニュースを起点とします。

クラスタはインターネットから直接は HTTP 401（Unauthorized）を返し、単純な無認証公開ではありませんでした。研究者はクラウド経由の別の経路から到達し、そこで既定の認証情報が通ったと説明しています。FOFA はこのホストとポートを2022年10月に初めて記録し、2023年7月にデータベースと識別していましたが、第2の経路から旅客データが取れるようになった時期は特定できず、露出の実際の期間は不明です。

研究者は6月3日からベトナム当局・データに含まれる航空会社・各国の CERT に通報し、6月8日に遮断されました。Singapore Airlines のセキュリティチームが対応の調整を助け「関係者に働きかけ、封じ込めの措置を取った」（原文英語）と伝えています。しかしどのベトナムの組織がシステムを運用していたかは特定されておらず、ベトナム当局は BleepingComputer の事前の問い合わせに回答していません。身代金要求のメモや見慣れないインデックスは無く、売買の痕跡も見つかっていませんが、サーバのログが無いため誰かが複製したかは分かりません。

APIS は各国の当局が航空会社から入国・出国前に受け取る旅客・乗員の身元・旅券・便の情報で、対象は「ベトナムを発着・経由した旅客」であり運航した航空会社の顧客全体ではありません。日本からベトナムへは年間100万人規模が渡航しており、駐在員・出張者・観光客の記録が含まれうるため、本記録は「日本に波及した海外事案」として置きます。件数は渡航の記録であって人数ではなく、複数回渡航した人は繰り返し現れます。本記録は、研究者の発見と報道から確認できた範囲を整理します。運用主体の公式声明は存在せず、本記録は一次公表を欠いた記録です。

直接は 401 を返す「守られた」データベースが、クラウド経由の別経路と既定の認証情報の連鎖で読めた——単純な無認証公開ではない原因・手口出典 [1] [2]

Kinryū Labs が BleepingComputer に説明した到達の経路は次のとおりである。

  1. インターネットから直接エンドポイントに接続すると HTTP 401「Unauthorized」が返り、データベースには入れない
  2. しかし「クラウドベースの経路」からはクラスタに到達でき、そこで既定の認証情報が通った

つまり、設定不備が2つ連鎖している。1つ目は、直接の経路には認証を置いたが、別の経路（クラウド側）が同じ認証を通らずに到達できたこと。2つ目は、その経路で提示できる認証情報が既定値のままだったことである。Elasticsearch の露出事案の多くは「認証なしで公開されていた」型だが、本件は「認証はあったが、迂回できる経路と弱い認証情報が残っていた」型である（本記録の整理）。

本記録は原因を「設定不備」と「認証情報の悪用（既定値）」の2つに置いた。「クラウド経由の経路」の具体的な構成（クラウド事業者の内部ネットワークか、別ホストのプロキシか、公開された API か）は報道時点で明かされておらず、研究者が後日公開する技術的な詳細で明らかになる可能性がある。

FOFA はこのホストとポートを2022年10月に初めて記録し、2023年7月にデータベースと識別していた。ホスト自体は少なくとも3年半前からインターネットから見えていたことになる。ただし、第2の経路から旅客データが取れる状態がいつからかは特定できておらず、露出の期間は不明である。

露出したのは9年4か月分・2.2億件の「ベトナムを発着・経由した旅客・乗員」の身元と便の情報——件数は渡航の記録であり人数ではない被害規模・影響範囲出典 [1] [2]

対象は「2017年1月〜2026年4月にベトナムを発着または経由した旅客・乗員」であり、運航した航空会社の顧客全体ではない。研究者が確認したサンプルには韓国・中国・カナダ・ニュージーランド籍などがあり、アジア太平洋・欧州・中東の多数の国際航空会社の便が含まれていた。研究者は自分たちのベトナム渡航の記録と突き合わせて、データが本物であることを確認している。

数値の読み方に注意が要る（本記録の整理）。

  1. 件数は渡航の記録であって人数ではない。複数回渡航した人は繰り返し現れ、乗員は便ごとに現れるため、人数は件数よりはるかに少ない
  2. 「露出していた範囲」であって「閲覧・複製が確認された範囲」ではない。ログが無いため後者は測れない
  3. 国籍別の内訳は示されておらず、日本籍・日本発着の記録の件数は不明

日本との関係について。日本とベトナムの間には直行便が多数あり、日本からベトナムへの渡航者は年間100万人規模である（一般的な統計に基づく本記録の記述であり、本件の記事には無い）。9年4か月の記録に日本の駐在員・出張者・観光客の旅券番号と渡航歴が含まれている可能性は高い（本記録の評価）。本記録が「日本に波及した海外事案」として置く理由はここにある。

発見から5日で遮断、運用主体は分からないまま——通報を受けた航空会社（Singapore Airlines）が「関係者に働きかけ」て閉じた組織の対応出典 [1] [2]

経過を並べると次のとおりである。

  • 6月3日: Kinryū Labs が発見。同日からベトナム当局・航空会社・各国 CERT に通報
  • 6月8日: アクセスが遮断される。Singapore Airlines のセキュリティチームが研究者に「関係者に働きかけ、封じ込めの措置を取った」と連絡
  • 9月8日: BleepingComputer が報道（遮断から3か月）

発見から遮断まで5日は、露出事案として速い部類に入る。しかし特徴的なのは、遮断に至った経路が運用主体ではなく航空会社だったことである。研究者はベトナム当局にも通報したが、当局が対応したかは分からず、BleepingComputer の問い合わせにも回答が無い。運用主体は今も特定されていない。Singapore Airlines が「関係者に働きかけた」と述べていることから、航空会社が自社の旅客データを預けている先（ベトナムの当局または委託先）に連絡し、そこで遮断されたと読める（本記録の推定）。

本記録の評価として、この構図には2つの含意がある。

第1に、APIS のようにデータの本人（旅客）と運用主体（当局）と提供者（航空会社）が分かれているシステムでは、露出の通報先が複数あり、誰が責任を持って閉じるかが曖昧になる。本件では航空会社が動いたことで閉じたが、航空会社に通報していなければ長引いた可能性がある。

第2に、運用主体が公表しないため、本人への通知は無い。2.2億件の記録の本人は、自分の旅券番号と渡航歴が露出していたことを、報道以外から知る手段が無い。旅券番号は再発行しない限り変わらないため、露出の影響は旅券の有効期限まで続く。

Changi Airport Group は「調査した」と述べたがコメントを控えた。データに便が含まれる航空会社がクラスタを運用した、または自社ネットワークが侵害された兆候は無い。

旅券番号と渡航歴の組み合わせは、身分詐称と「渡航を知っている前提」の偽装連絡に使える——本人にできることは限られ、組織側の備えが要る評価・解釈出典 [1] [2]

本記録の評価である。

露出した項目のうち、氏名・生年月日・国籍・旅券番号・有効期限は身元確認の中核で、便名・日付・座席・経由地は「その人がいつどこへ行ったか」を示す。この組み合わせは次の用途に使える。

  1. 身分詐称——旅券番号と生年月日を知っていれば、航空会社・ホテル・レンタカー・通信事業者の本人確認の一部を通せる場合がある
  2. 標的型の偽装連絡——「○月○日の△△便で入国した記録について」と、実際の渡航を引用した入国当局・航空会社・大使館を装うメールや電話は、本人にとって疑いにくい
  3. 人物の追跡——特定の人物の渡航パターン（頻度・経由地・同行者の推定）を9年分たどれる。駐在員・政府関係者・記者・活動家にとっては物理的な安全の問題になる

本人にできることは限られる。旅券番号は再発行しない限り変わらず、渡航歴は変えようがない。「自分が含まれるか」を確認する手段も無い（運用主体が公表しないため）。

したがって備えは組織側に要る。海外拠点を持つ組織、社員の海外出張が多い組織は、「渡航を知っている前提」の偽装連絡が来ることを想定し、社員に周知する必要がある。APIS を運用する側（各国の当局・委託先）にとっては、本件は「認証を置いた」だけでは足りず、到達経路の全部に同じ統制がかかっているか、既定の認証情報が残っていないかを確かめる必要を示す。

なお、露出したのは「ベトナムの APIS」であり、日本の APIS（法務省・財務省が航空会社から受け取る事前旅客情報）ではない。日本の APIS の運用状況は本件と無関係である。ただし、日本人の記録がベトナム側の APIS に含まれている以上、日本の当局が直接できることは少なく、本人への注意喚起と旅券の相談窓口の案内が現実的な対応になる。

CISO・経営層への示唆
  • 「認証を置いた」は「全経路に認証がある」を意味しない。データベースへの到達経路を全部数え、直接以外の経路に同じ統制があるかを確かめる
    本件のクラスタは直接の接続には 401 を返していた。露出したのはクラウド経由の別経路と既定の認証情報の連鎖であり、 「認証あり」の確認だけでは見つからない
    取るべき行動 個人情報を持つデータベース・検索エンジンについて、到達経路（直接・VPC 内部・ピアリング・踏み台・プロキシ・ クラウドの管理経路）を一覧にし、経路ごとに認証とネットワーク制限の有無を確認する。 外部の攻撃面管理（ASM）の結果に「認証あり」と出たホストも対象から外さない
  • データの本人・運用主体・提供者が分かれるシステムでは、露出の通報が誰に届けば閉じるかを事前に決めておく
    本件で遮断に至ったのは運用主体ではなく航空会社の調整だった。研究者は当局にも通報したが、当局の対応は分からない。 通報先が複数あると、誰も動かない可能性がある
    取るべき行動 自社が委託・提供している個人データについて、「露出の通報を受けたら誰に連絡し、誰が閉じる権限を持つか」を 契約または運用取り決めに書く。自社が提供者の立場なら、委託先の露出を自社が通報される場合の手順も決める
  • 海外拠点・海外出張の多い組織は、社員の旅券番号と渡航歴が自社の統制の外で露出しうる前提で備える
    本件の記録には日本発着の旅客が含まれうる。旅券番号は再発行しない限り変わらず、渡航歴は変えようがない。 本人が「含まれるか」を確認する手段も無い
    取るべき行動 「○月○日の便で入国した記録について」のように実際の渡航を引用する入国当局・航空会社・大使館を装う 連絡が来ることを社員に周知し、正規の連絡の来方（メールの送信元・手続きの場所）を併せて示す。 駐在員・頻繁に渡航する社員には旅券の相談窓口を案内する
  • 長期に蓄積した身元情報は、露出したときの影響が期間に比例する。保持期間を決め、過ぎた記録を減らす
    本件は9年4か月分の記録が1つのクラスタにあった。保持期間が短ければ、露出の影響は直近の記録に限られた
    取るべき行動 個人の身元情報（旅券・免許証・マイナンバー等）を持つシステムの保持期間を法令・業務の必要から定め、 期間を過ぎた記録の削除または匿名化を年次で実施する。削除できない場合は、古い記録を別の統制の下に分離する
セキュリティ技術者への示唆
  • Elasticsearch／OpenSearch の既定の認証情報を初期構築で必ず変え、既定値が残っていないかを定期的に検査する
    本件では第2の経路で既定の認証情報が通った。認証を有効にしても、既定値のままなら誰でも通る
    取るべき行動 構築手順書に「既定の認証情報の変更」を必須の項目として入れ、構成管理（Ansible・Terraform 等）で 既定値の使用を禁止する。定期的な検査で、既知の既定値（elastic/changeme 等）による認証試行を全ホストに行い、 通ったものを即時修正する
  • クラウド内部の経路（VPC 内・ピアリング・踏み台・管理用のプロキシ）にも、直接の経路と同じ認証とネットワーク制限をかける
    本件は直接の経路には認証があったが、クラウド経由の経路で到達できた。内部経路を「信頼できる」と みなす設計は、その経路のどこかが外部から到達可能になった瞬間に破れる
    取るべき行動 データベースのリスナーを内部経路からも認証必須にし、セキュリティグループ・ネットワーク ACL で 接続元を必要なホストに限定する。踏み台・プロキシからの接続も監査ログに残す。 「内部だから認証不要」の設定を棚卸しして無くす
  • 露出の検知を自社でも行う。FOFA・Shodan・Censys で自社の IP 空間とクラウドの割当を定期的に検索し、見えているサービスを把握する
    本件のホストは FOFA に2022年10月から記録され、2023年7月にデータベースと識別されていた。 運用主体が同じ検索をしていれば、少なくともホストが見えていることは分かった
    取るべき行動 自社の IP 空間・クラウドの割当・ドメインを対象に、月次で外部の検索エンジンを検索し、 新しく見えたサービスを担当者に通知する。データベース系のポート（9200・27017・6379 等）が 見えた場合は即時に確認する
  • アクセスログを保全し、露出が判明したときに「誰が何を読んだか」を答えられる状態にする

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Elasticsearch・OpenSearch・MongoDB などのデータベースをクラウド上で運用しており、直接の経路には認証があるが、VPC 内部・ピアリング・踏み台・管理用のプロキシ経由の経路の認証・ネットワーク制限を確認していない本件のクラスタは直接の経路には 401 を返していた。露出したのは別経路と既定の認証情報の連鎖で、 「認証あり」の確認だけでは見つからない
認証・認可□ データベース・ミドルウェアの既定の認証情報を初期構築で変更する手順が無い、または既定値が残っていないかを定期的に検査していない本件では第2の経路で既定の認証情報が通った。認証を有効にしても既定値のままなら誰でも通る
データの保持□ 旅券番号・免許証番号・マイナンバーなどの身元情報を長期（数年以上）にわたって1つのデータベースに蓄積している本件は9年4か月分の記録が1つのクラスタにあり、露出の影響が期間に比例した。旅券番号は再発行しない限り変わらない
委託・第三者部品□ 自社の顧客・社員の個人データを、海外の当局・事業者・委託先に提供しており、露出の通報を受けたときに誰が閉じる権限を持つかが決まっていない本件で遮断に至ったのは運用主体ではなく航空会社の調整だった。通報先が複数あると誰も動かない可能性がある
体制・契約□ 海外拠点を持つ、または社員の海外出張・駐在が多く、社員の旅券番号と渡航歴が自社の統制の外（各国の APIS・航空会社・ホテル等）で保持されている本件の記録には日本発着の旅客が含まれうる。「渡航を知っている前提」の偽装連絡への備えは組織側にしかできない
運用・監視□ 自社の IP 空間・クラウドの割当を FOFA・Shodan・Censys 等で定期的に検索しておらず、外部から見えているサービスを把握していない本件のホストは FOFA に2022年10月から記録されていた。運用主体が同じ検索をしていれば、ホストが見えていることは分かった
