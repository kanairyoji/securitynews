INC-2026-0130Weverse の決済 API から42万件が流出

HYBE 傘下のファン向けプラットフォーム Weverse で、決済情報を処理する API のアクセス制御の不備から、422,584件（アカウントID単位）の内部識別番号と購入・返金の履歴（決済手段・決済代行会社名・金額・日時）が外部の行為者に取得された——同社自身は気づいておらず、外部の報告者が韓国インターネット振興院（KISA）に脆弱性を知らせ、KISA からの連絡で発覚した。日本では WEVERSE JAPAN 株式会社が9月6日に告知し、日本語の問い合わせ窓口を設けた

不正アクセス・侵害初報のみ日本に波及した海外事案権限管理の不備設計・実装上の不備
初報: 2026年9月6日 最終更新: 2026年9月14日

HYBE 傘下の Weverse Company が運営するファン向けプラットフォーム Weverse で、顧客の決済に関する情報が外部に流出しました。日本では WEVERSE JAPAN 株式会社が2026年9月6日に「一部顧客の個人情報流出」について告知しています。

告知によれば、9月3日、韓国インターネット振興院（KISA）から「外部の報告者が Weverse サービスのセキュリティ脆弱性を指摘している」との連絡があり、社内点検の結果、一部顧客の情報が流出した事実を確認しました。流出はアカウントID単位で422,584件です。同社が個人情報と位置づけるのは内部識別情報（登録時に社内で振る内部番号）で、ほかに購入タイプ（決済手段）・決済代行会社名・通貨単位・購入金額・取消金額・購入日時・購入状態・返金日時が含まれます。氏名や連絡先は含まれていないと同社は説明しています。

同社は9月4日に KISA へ侵害事故を報告し、決済情報処理 API のアクセス制御を強化して内部識別情報を応答から除いたとしています。さらに「不正な攻撃によって個人情報へ不法にアクセスした外部の行為者」に情報の回収を求め、告訴手続きを進める予定です。今後は外部に露出しているすべての API を全数調査します。

本記録に載せるのは、認可の漏れた API が、自社の監視ではなく外部の報告と当局経由で見つかった典型例であり、日本の利用者も多いサービスで起きたからです。一次資料は Weverse Shop に掲載された告知（日本語版・英語版）で、報道と照合しました。評価・示唆は本記録の判断として分けて書きます。

告知には、露出がいつ始まったか、自社のログやモニタリングで事前に兆候をつかめていたかは書かれていない。今後の措置に「配信プロセスにおける統制とセキュリティモニタリングの検出感度を強化」が挙がっていることから、リリース時の確認と監視のいずれも今回は機能しなかったとみられる（本記録の推定）。

ここからは本記録の作成者の評価である。

第一に、発見したのは外部だった。 42万件を返す API の異常な呼び出しに、同社の監視は気づいていない。外部の報告者が KISA に知らせなければ、露出は続いていた可能性がある。自社の API を外部から見える形で棚卸しし、1つの呼び出し元が大量の識別子を順に照会する動きを検知する仕組みが要る。

第二に、応答に「内部でしか使わない番号」を含めていた。 同社の対策の1つは内部識別情報の除去である。画面に出さない項目でも API の応答に載っていれば外から読める。「内部でのみ使う」という前提は、その値が応答に含まれた時点で崩れる。

第三に、個人情報に当たらない項目の扱いが被害の実態を決める。 同社は購入履歴を「個人情報に該当しない一般情報」と分類した。法令上の分類としてはそうでも、利用者から見れば自分の購買行動が外に出たことに変わりはない。日本のファン向けサービスや EC も、購入履歴を返す API を同じ構造で持っている。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
件数と項目を具体的に示し、項目を「個人情報」と「一般情報」に分けて告知した一方、 露出の期間と脆弱性の内容は示さなかった部分的に機能本記録の作成者の評価である。件数と項目の明示は具体的だが、露出期間が無いため、 利用者は「いつの購入が対象か」を判断できない
各国語の告知を Weverse Shop に掲載し、日本向けの問い合わせ窓口を示したうえで、対象者へ個別に案内する機能した本記録の作成者の評価である。日本語で窓口を示した点は、日本の利用者にとって実用的である
CISO・経営層への示唆
  • 自社の API の穴は、外部の報告者や当局から知らされる前提で窓口を整えておく
    本件は外部の報告者が KISA に知らせ、KISA から連絡を受けて発覚した。 自社の監視は流出に気づいていない
    取るべき行動 脆弱性の受付窓口（security.txt、報告の受付フォーム）を公開し、JPCERT/CC や IPA 経由の連絡を 受けたときの初動（当日の点検・翌日の当局報告）を手順化する
  • 「個人情報ではない」項目の流出も、利用者から見れば事故である
    同社は購入の手段・金額・日時を「個人情報に該当しない一般情報」と分類したが、 内部番号と結びついた購買行動が42万件分外に出ている
    取るべき行動 インシデントの重大度と通知の判断を、法令上の個人情報の該当性だけでなく 「利用者が知ったら困るか」「他の情報と結びつくか」の観点でも評価する
  • 外に出ている API の数を経営として把握する
    同社は再発防止として外部に露出しているすべての API の全数調査を掲げた。事故の後で初めて数えることになった
    取るべき行動 外部公開 API の台帳を作り、件数・所管・認可方式・最終点検日を定期的に報告させる。 台帳に無い API が見つかったら是正の対象にする
セキュリティ技術者への示唆
  • API の認可は「ログインしているか」ではなく「そのデータの持ち主か」で試験する
    同社は決済情報処理 API のアクセス制御を強化した。外部から照会できた決済履歴が42万件に及んだ
    取るべき行動 決済・注文・返金を返す API に、他人の識別子で照会したときに拒否されるかを確かめる試験を 自動テストとして組み込み、リリースの条件にする
  • 画面に出さない項目は API の応答から削る
    同社は対策として応答から内部識別情報を除去した。「内部でのみ使う番号」も応答に載れば外から読める
    取るべき行動 主要な API の応答をスキーマで定義し、画面で使っていない項目を洗い出して削る。 レスポンスに内部 ID・他人の情報が混ざっていないかを定期的に差分で確認する
  • 識別子を順に変える大量照会は、API ゲートウェイで検知できる
    42万件の取得は、通常の利用ではありえない件数の照会として記録に残るはずである（本記録の評価）
    取るべき行動 呼び出し元（トークン・IP）ごとの照会件数と、異なる識別子の数を監視し、閾値を超えたら 警報と一時遮断を行う。閾値は通常の利用者の上位の分布から決める
  • 検知の感度はリリースの工程と一緒に見直す
    同社は今後の措置に「配信プロセスにおける統制」と「モニタリングの検出感度」を並べて挙げた
    取るべき行動 新しい API を公開するときに、認可の試験結果と監視の設定をリリース判定の項目に入れ、 監視の無い API を本番に出さない

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 注文・決済・返金の履歴を返す API があり、他人の識別子で照会したときに拒否されるかを試験していない本件は決済情報処理 API のアクセス制御の不備から42万件が取得された
システム構成□ API の応答に、画面では使わない内部識別子や他の項目を含めている同社の対策の1つは応答からの内部識別情報の除去である

体制・契約□ 外部公開 API の台帳が無く、件数と所管を答えられない同社は事故の後に全 API の全数調査を掲げた
体制・契約□ 外部の報告者や当局から脆弱性の連絡を受けたときの窓口と初動の手順が決まっていない本件は KISA 経由の連絡が発覚の端緒だった。受けた当日に点検できるかが被害の確定を左右する
