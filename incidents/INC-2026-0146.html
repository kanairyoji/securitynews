INC-2026-0146Cisco メールGWにゼロデイ悪用

Cisco Secure Email Gateway のメール解析処理に SQL インジェクションの脆弱性（CVE-2026-76461・CVSS 9.8）があり、細工したメールを1通送るだけで認証も利用者の操作もなしに機器の OS 上で root 権限のコマンドを実行される——Cisco は2026年9月に実際の悪用を把握したとして9月14日に修正版を公開し、米 CISA は同じ日に KEV へ収載して連邦機関に9月17日までの対処を指示した。回避策は無く、root を取られた機器ではログを消されている可能性があるため、周辺機器のログとの突合が求められている

脆弱性続報が続いている日本に波及した海外事案設計・実装上の不備未知の脆弱性の悪用
初報: 2026年9月14日 最終更新: 2026年9月16日

企業のメールの出入り口に置かれる Cisco Secure Email Gateway（旧 IronPort）に、認証なしで遠隔から root 権限のコマンドを実行できる脆弱性 CVE-2026-76461（CVSS 9.8）が見つかりました。原因は、機器がメールを解析するときの入力検証の不備です。攻撃者は悪意ある SQL 文を仕込んだメールを、標的の組織へ1通送るだけで済みます。アカウントも、受信者のクリックも要りません。メールを受け取って処理することがこの製品の仕事である以上、攻撃の到達経路はふさげません。Cisco は2026年9月14日に advisory（cisco-sa-esa-inj-2bLVGmhX）を公開し、「2026年9月に、Cisco PSIRT は本脆弱性の実際の悪用を把握した」（原文英語）と述べています。物理機器と仮想機器の別を問わず、設定の内容にもよらず影響を受けます。回避策は提供されていません。米 CISA は公開と同じ2026年9月14日に、この脆弱性を「悪用が確認された脆弱性カタログ」（KEV）へ追加し、連邦民間行政機関に2026年9月17日までの対処を指示しました。公開と収載が同日であることは、世に出る前から悪用されていたゼロデイであることを示します。日本では JPCERT/CC が翌9月15日に注意喚起（JPCERT-AT-2026-0027）を出し、対策とあわせて侵害調査の実施を検討するよう求めました。同センターは「同製品について、過去に別の脆弱性（CVE-2025-20393）を悪用した侵害事案が国内で発生していることを確認しています」と書いています。ただし本脆弱性による国内の被害は、本記録の作成者が2026年9月16日に確認した範囲では公表されていません。本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

悪意ある SQL 文を含む細工したメールを、影響を受ける Cisco Secure Email Gateway へ 送信する。機器がメールを解析する処理で入力検証が不十分なため、SQL 文がそのまま 実行され、基盤となる OS 上で root 権限のコマンド実行に至る。認証も受信者の操作も 不要である。悪用後の具体的な活動（何を取得し、どこへ送ったか）は公表されていない。 Cisco は、root を取得した攻撃者がログや侵害の痕跡を削除している可能性があるとし、 機器のログだけでなくネットワーク・ファイアウォールのログと突合するよう求めている。

  1. 1. 初期侵入確認済[1] [4]
    攻撃者が、悪意ある SQL 文を含む細工したメールを標的組織へ送る。 影響を受ける機器がそのメールを解析した時点で悪用が成立する。 認証は不要で、受信者がメールを開く必要も無い。
    根拠: Cisco の advisory（cisco-sa-esa-inj-2bLVGmhX）
  2. 2. 実行確認済[1] [2]
    実行された SQL 文を通じて、基盤となる OS 上で root 権限の任意コマンド実行に至る。 Cisco は影響を「物理機器・仮想機器を問わず、設定にかかわらず」としている。 実際の攻撃で何が実行されたかは公表されていない。
    根拠: Cisco の advisory と CISA KEV の記述
  3. 3. 検知回避公表・報道に基づく[1] [3]
    Cisco は「攻撃者が侵害の痕跡を削除した可能性がある」と明記している。 root 権限を取得した以上、機器上のログは攻撃者の制御下にある。
    根拠: Cisco の advisory と JPCERT/CC の注意喚起
  4. 4. 認証情報アクセスunconfirmed[1]
    本件で資格情報が取得されたかは公表されていない。一般に、メールゲートウェイには ディレクトリ連携（LDAP バインド）、管理者アカウント、隔離メールへのアクセス、 通過するメール本文と添付という機微な資源が集まる。
    根拠: 公表資料に記載なし（本記録の作成者による位置づけ）

メールを検査する機器が、そのメールの中身を SQL 文として実行していた——攻撃者に要るのは宛先だけである原因・手口出典 [1] [6] [8]

Cisco の説明では、脆弱性は「Cisco Secure Email Gateway 向け Cisco AsyncOS ソフトウェアのメール解析処理」にあり、原因は「メール解析ロジックにおける入力検証の不十分さ」です。攻撃者は悪意ある SQL 文を含む細工したメールを、影響を受ける機器を通して送るだけで、任意の SQL 文を実行させ、基盤となる OS 上で root 権限のコマンド実行に至ります（原文英語）。

この経路の性質を、ほかの境界機器の脆弱性と区別して読む必要があります。VPN 装置や管理画面の脆弱性は「管理面をインターネットに出しているか」で被攻撃面が変わりますが、メールゲートウェイは受信すること自体が業務です。機器の設定を絞っても、送信元を選ぶこともできません。Cisco は「物理機器・仮想機器を問わず、機器の設定にかかわらず脆弱である」としています。認証は不要、受信者の操作も不要です。攻撃者に必要なのは、標的の組織のメールアドレスだけです。

本記録の評価として、この構造は「外向きの侵入経路を減らす」という常道が効かない類型です。効くのは、版を上げること（回避策は提供されていません）、機器そのものを侵害前提で監視すること、そして機器が持つ資格情報を失われたものとして扱うことの3つに絞られます。

公表と KEV 収載が同じ日だった——ゼロデイとして先に使われ、防御側は初日から後追いである概観出典 [1] [2] [4]

CISA は Cisco の公表と同じ2026年9月14日に、この脆弱性を KEV へ追加しました。Rapid7 はこの点を明示して、「開発元の公表と同じ日に KEV に追加されたことは、CVE-2026-76461 が公表前にゼロデイとして悪用されていたことを示す」（原文英語）と書いています。Cisco 自身の記述も「2026年9月に、Cisco PSIRT は本脆弱性の実際の悪用を把握した」です。つまり、修正版が出た時点で、攻撃はすでに動いていました。

連邦民間行政機関の対応期限は2026年9月17日で、収載から3日です。KEV の期限は2〜3週間が置かれることが多く（INC-2026-0068 の PaperCut では14日）、3日という設定は短い部類に入ります。あわせて、この脆弱性はBOD 26-04 に基づくフォレンジック調査の要件（forensicTriage）の対象にも指定されました。当てて終わりではなく、侵害されていないかを調べることまでが求められている、という位置づけです。

本記録の評価として、日本の組織にこの期限の法的な効力はありませんが、「当局が悪用を確認し、3日で対処せよと自国の機関に命じた」という事実は、社内で緊急の停止や再起動を通すときの根拠として使えます。

回避策は無く、root を取られた機器のログは信用できない——調べる先は機器の外にある対策・注意喚起出典 [1] [3] [4] [8]

Cisco は回避策を提供していません。対処は修正版への更新のみです。対象と修正版は次のとおりです。15.5 系以前は 15.5.5-0141、16.0 系は 16.0.4-3021、16.5 系は 16.5.0-780。Cisco は最新の 16.5.0-780 への移行を強く推奨しています。

侵害調査について、Cisco は mail_logs に不審な SQL 文が残っていないかを確認するよう案内し、検出例として次のコマンドを挙げています。

cisco-esa> grep -i "COPY.*TO PROGRAM" [mail_logs]

出力が1行でもあれば悪性の活動の可能性があるとされます。機器がクラスタを構成している場合は、各機器のログを確認する必要があります。さらに Cisco は、悪用に成功した攻撃者は root 権限でコマンドを実行できるため、ログや侵害の痕跡が削除されている可能性があると明記し、ネットワークやファイアウォールのログと突合して、外部の悪性 IP との通信が無いかを確認するよう勧めています。JPCERT/CC の注意喚起もこの点を引いています。

本記録の評価として、ここが本件の実務上の勘所です。調査対象を機器の中に限ると、攻撃者が消したあとの綺麗なログを見て「痕跡なし」と結論づけることになります。メールゲートウェイの前後（境界のファイアウォール、プロキシ、DNS の記録、SIEM に転送済みのログ）に残った通信のほうが、攻撃者の手が届きにくい層です。侵害の判断は、そちらを主にして下すべきです。あわせて、機器に保存された LDAP バインドや管理者のアカウント、API の鍵は、侵害の有無が確定するまで漏えいした前提で更新するのが安全です。

JPCERT/CC は「同じ製品で国内の侵害事案を確認している」と書いた——本脆弱性ではないが、狙われる製品であることの裏付けである波及・関係先出典 [3]

JPCERT/CC は2026年9月15日の注意喚起（JPCERT-AT-2026-0027）で、対象版を示したうえで「同製品について、JPCERT/CCでは、過去に別の脆弱性（CVE-2025-20393）を悪用した侵害事案が国内で発生していることを確認しています」と書き、対策と侵害調査の両方を検討するよう求めました。情報提供の呼びかけも添えられています。

これは本脆弱性（CVE-2026-76461）による国内被害の報告ではありません。別の脆弱性による過去の事案です。区別したうえで読む必要があります。ただし、①同じ製品が国内で実際に侵害の対象になった実績があること、②注意喚起が「対策」だけでなく「侵害調査」を並べたこと——この2点は、国内の利用組織が本件を「まだ日本には来ていない海外の話」として扱えないことを意味します。

本記録の評価として、国内の稼働台数も露出台数も公表されていない以上、自組織の資産台帳で「Cisco Secure Email Gateway／IronPort を持っているか」を確かめるところから始めるほかありません。メールゲートウェイは情報システム部門ではなく、メール基盤の運用委託先が管理していることも多く、版数の把握と更新の依頼先が社内に無いという状態が起こりがちです。

攻撃者も、被害組織も、悪用の始まりも公表されていない未確定事項出典 [1] [4] [9]

公表されていないことを列挙します。悪用を受けた組織の名称・国・業種・件数。root 権限を取られた機器で、メールの本文・添付・保存された資格情報がどこまで扱われたか。攻撃者の主体と動機。悪用がいつ始まったか（advisory は「2026年9月」に把握したと書くのみです）。Cisco がどのように悪用を把握したか。クラウド版で個別に連絡した顧客の数。

分かっている数字も、意味を限定して読む必要があります。보안뉴스が伝えた Shadowserver の「400台超」は、インターネットから見えている台数であって、攻撃された台数でも、侵害された台数でもありません。本脆弱性はメールの受信経路から悪用されるため、そもそも「見えている台数」では被攻撃面を測れないという限界もあります。

本記録は、続報（被害組織の公表、国内事例の有無、実証コードの公開、攻撃者の帰属）が出た時点で更新します。status は updating のままとします。

id: CVE-2026-76461　cvss: 9.8　概要: Cisco Secure Email Gateway 向け Cisco AsyncOS ソフトウェアのメール解析処理における SQL インジェクション（CWE-89）。悪意ある SQL 文を含む細工したメールを送ることで、 認証されていない遠隔の攻撃者が任意の SQL 文を実行し、基盤となる OS 上で root 権限の任意コマンド実行に至る。物理機器・仮想機器を問わず、 機器の設定にかかわらず影響を受ける　exploited: はい
affected_versionsCisco Secure Email Gateway 向け Cisco AsyncOS（物理機器・仮想機器）。 Cisco の advisory によれば修正版は 15.5 系以前が 15.5.5-0141、16.0 系が 16.0.4-3021、 16.5 系が 16.5.0-780 で、16.5.0-780 への移行が強く推奨されている。 JPCERT/CC は対象を「16.5系の16.5.0-780より前」「16.0系の16.0.4-302より前」 「15.5系以前の15.5.5-014より前」と記しており、下2桁の表記が資料間で一致しない （齟齬に記録した）。利用組織は開発元の advisory で直接確認する必要がある
exploitation_status実際の悪用が確認されている。Cisco は「2026年9月に、Cisco PSIRT は本脆弱性の 実際の悪用を把握した」（原文英語）としている。米 CISA は公表と同日の 2026年9月14日に KEV へ収載し、連邦民間行政機関に2026年9月17日までの対処を指示した。 被害組織・件数・攻撃者は公表されていない。2026年9月15日時点で公開された 実証コードは無いと Rapid7 は述べている
緩和策
item: 修正版（16.5.0-780・16.0.4-3021・15.5.5-0141）への更新　副作用: メールの出入り口の更新であり、適用中はメールの滞留・遅延が起こりうる。 クラスタ構成では各機器の更新と再起動の順序を設計する必要がある。 回避策が提供されていないため、更新を先送りする選択肢は 「侵害前提の運用を続ける」ことと同義になる
item: mail_logs の確認（grep -i "COPY.*TO PROGRAM"）とクラスタ各機器のログの確認　副作用: root を取られた機器ではログが削除されている可能性があるため、 「出力なし＝安全」とは読めない。周辺機器のログとの突合が別途要る
item: 機器に保存された資格情報（LDAP バインド・管理者・API）の更新　副作用: ディレクトリ連携の再設定を伴うため、認証・隔離メールの参照などの 機能が一時的に止まりうる。業務時間外の作業計画が要る
indicators
item: mail_logs に残る不審な SQL 文（Cisco の検出例: grep -i "COPY.*TO PROGRAM" [mail_logs]）　補足: 出力が1行でもあれば悪性の活動の可能性がある。クラスタ構成では各機器のログを確認する
item: メールゲートウェイから外部の未知の IP への通信、外部からの想定外のダウンロード・アップロード　補足: Cisco がネットワーク・ファイアウォールのログとの突合を求めている層。攻撃者が消しにくい
item: 機器上のログの欠落・不自然な時刻の空白　補足: Cisco は痕跡が削除されている可能性を明記している。欠落そのものを疑いの根拠として扱う

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
1通のメールが root 権限のコマンド実行に変わる経路と、消される痕跡・残る痕跡
攻撃者は標的組織のメールアドレス宛に、悪意ある SQL 文を含む細工したメールを送る（layer 0→1）。 Cisco AsyncOS のメール解析処理が入力検証を欠くため、SQL 文が実行され（layer 2）、 基盤 OS 上で root 権限のコマンド実行に至る（layer 3）。 機器にはディレクトリ連携の資格情報と通過するメールが集まる（layer 4）。 機器上のログは攻撃者が消しうるが、境界機器の通信記録は残りやすい（layer 5）。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入機会はあったが検知できず
悪用の痕跡は mail_logs に不審な SQL 文として残りうる（Cisco の検出例は COPY ... TO PROGRAM の文字列）。ただし root を取られた後は削除されうるため、 機器の中のログだけに頼る検知は成立しない。
侵入を防げた修正版（16.5.0-780・16.0.4-3021・15.5.5-0141）へ更新する。回避策は提供されていない
検知できたmail_logs を機器の外（SIEM・ログ基盤）へ継続的に転送し、機器上の削除では消えない場所に保全する
実行公表されていない
アプライアンスは利用者が EDR を入れられる機器ではないため、 ホスト側で実行を捉える手段が乏しい。検知できたかどうかは公表されていない。
影響を限定できたメールゲートウェイからの外向き通信を、更新・レピュテーション照会など必要な宛先に限定し、それ以外を遮断・記録する
影響を限定できた機器のネットワーク区画を分け、内部の重要システムへ直接到達できないようにする
検知回避機会はあったが検知できず
機器の外に転送済みのログ、境界のファイアウォール・プロキシ・DNS の記録は 攻撃者の手が届きにくい。突合できる体制があれば、消された分を補って判断できる。
検知できたメールゲートウェイのログを常時外部へ転送し、保全期間を定めておく
検知できた侵害調査では機器のログを主資料にせず、周辺機器の通信記録と突合する（Cisco・JPCERT/CC の推奨）
認証情報アクセス公表されていない
攻撃者が何を取得したかが公表されていないため、検知の機会も評価できない。
影響を限定できた侵害の有無が確定するまで、機器に保存された LDAP バインド・管理者・API の資格情報を漏えい前提で更新する
影響を限定できたメールゲートウェイに持たせるディレクトリ用アカウントを読み取り専用・専用アカウントにし、他システムと共用しない

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「受け取ることが仕事」の機器は、公開範囲を絞る対策が効かない——更新の速さが唯一の変数になる
    VPN や管理画面なら公開をやめる選択肢があるが、メールゲートウェイは インターネットからのメールを受け取ることが業務である。Cisco も 「設定にかかわらず脆弱」としており、回避策は提供されていない。
    取るべき行動 メールゲートウェイ・DNS・WAF のように「止められない受信口」に当たる機器を 資産台帳で区別し、緊急更新の判断を待たずに実施できる事前承認 （実施者・時間帯・影響の説明文）を用意しておく。
  • 当局が「当てたか」ではなく「侵害されていないか」まで求めた事案である
    CISA は KEV 収載時に BOD 26-04 のフォレンジック調査の要件の対象にも指定し、 JPCERT/CC も「対策と侵害調査の実施を検討」と並べて書いた。 悪用が先行していた以上、更新は再侵入を止めるだけで、 既に入られていた場合の被害は止まらない。
    取るべき行動 緊急更新の完了報告に「侵害調査の実施有無」と「機器が保持する資格情報の更新」の 2列を加え、更新完了だけで案件を閉じない運用にする。
  • メールゲートウェイの管理を委託している場合、版数の把握と更新の依頼経路が社内に無いことがある
    メール基盤は運用委託先が管理していることが多く、社内の資産台帳に 版数が載っていない、あるいは更新の依頼先が不明という状態が起こる。 本件は公表から期限（米連邦機関）まで3日という速さで動いた。
    取るべき行動 メール基盤の委託契約で、緊急の脆弱性が出たときの連絡経路・着手期限・ 報告様式を確認する。確認できない場合は、今回の件を使って 委託先へ版数と対応状況の回答を求め、経路そのものを作る。
  • 国内で「まだ被害が公表されていない」ことは、国内が対象外であることを意味しない
    JPCERT/CC は同じ製品について、過去に別の脆弱性（CVE-2025-20393）を悪用した 侵害事案が国内で発生していることを確認したと書いている。 国内の稼働台数・露出台数は公表されておらず、被害の有無は外から測れない。
    取るべき行動 「国内報道が出たら動く」という運用をやめ、JPCERT/CC の注意喚起と CISA KEV の収載を自社の着手条件に組み込む。着手条件は文書化して 担当者の判断に依存させない。
セキュリティ技術者への示唆
  • root を取られた機器のログは証拠にならない——調べる先を機器の外に置く
    Cisco は、悪用に成功した攻撃者が root 権限でコマンドを実行できるため ログや痕跡が削除されている可能性があると明記し、ネットワークや ファイアウォールのログとの突合を求めている。
    取るべき行動 メールゲートウェイの mail_logs と system ログを SIEM へ常時転送し、 保全期間を決める。調査時は転送済みログ・境界のファイアウォール・ プロキシ・DNS の記録を主資料にし、機器上のログは参考として扱う。
  • 「出力なし」を安全の証明として報告しない
    Cisco の検出例（grep -i "COPY.*TO PROGRAM"）は、痕跡が残っていた場合に 見つけるための手順である。削除されていれば出力は空になる。 空の出力を「侵害なし」と報告すると、調査の打ち切り理由になってしまう。
    取るべき行動 調査結果は「検出された／検出されなかった（ただしログ削除の可能性があるため 通信記録での確認が別途必要）」の形で記載する。クラスタ構成では 各機器のログを個別に確認し、確認した機器名を残す。
  • 機器が抱えている資格情報を洗い出しておくと、侵害時の初動が速い
    メールゲートウェイにはディレクトリ連携の LDAP バインド、管理者アカウント、 API の鍵、通過するメールと隔離メールが集まる。本件で何が取得されたかは 公表されていないが、root を取られた機器では全てが読める前提になる。
    取るべき行動 機器ごとに「保存されている資格情報の一覧」と「更新手順・所要時間・ 影響する業務」を平時に作っておく。侵害が疑われた日に調べ始めると、 更新の可否判断だけで半日が消える。
  • 露出台数の統計を、自組織の被攻撃面の指標として使わない
    Shadowserver の「400台超」は管理面などがインターネットから見えている台数で、 本脆弱性はメールの受信経路から悪用される。見えていない機器も対象になる。
    取るべき行動 外部からの可視性ではなく、資産台帳の「製品名・版数・メールの受信有無」で 対象機器を特定する。外部スキャンの結果が0件でも、対象外の証明にはしない。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Cisco Secure Email Gateway（旧 IronPort ESA）または Cisco AsyncOS を、物理・仮想のいずれかで運用しているCisco は物理機器・仮想機器を問わず、機器の設定にかかわらず影響を受けるとしている。 メールを受信している時点で成立条件を満たす。
運用・監視□ 対象機器の版数を即座に答えられない、または版数を把握しているのが運用委託先だけである修正版は 16.5.0-780・16.0.4-3021・15.5.5-0141 で、系列ごとに番号が異なる。 版数が分からなければ、当たっているかどうかも判定できない。 米連邦機関の対応期限は収載から3日だった。
運用・監視□ メールゲートウェイのログを機器の中にしか置いておらず、SIEM や外部のログ基盤へ転送していないroot を取られた機器ではログが削除されうる。転送していなければ、 Cisco が案内する mail_logs の確認そのものが成り立たない。
認証・認可□ メールゲートウェイに、Active Directory を読める LDAP バインドアカウントや、他システムと共用の管理者アカウントを保存しているroot を取られた場合、機器に保存された資格情報は読まれた前提になる。 共用していれば、メール基盤の侵害がディレクトリや他システムへ広がる。
運用・監視□ 緊急の更新を「変更管理の次回の窓」まで待つ運用になっている本件は公表時点で既に悪用されており、回避策が無い。 待つ期間はそのまま、侵害前提で運用する期間になる。
体制・契約□ 脆弱性対応の着手条件が「国内報道が出たら」になっており、JPCERT/CC の注意喚起や CISA KEV の収載を条件に含めていない本件では Cisco の公表（9月14日）→ KEV 収載（同日）→ JPCERT/CC の注意喚起（9月15日）の 順で情報が出た。国内の被害公表を待つと、着手はさらに遅れる。
