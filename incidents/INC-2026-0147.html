INC-2026-0147タイ3BB の内部網が侵害される

タイの大手固定ブロードバンド事業者 3BB（Triple T Broadband）の内部網が侵害され、攻撃者は2024年2月に修正・KEV 収載済みだった FortiGate SSL-VPN の脆弱性（CVE-2024-21762）を2年以上あとに悪用して入り込み、正規の遠隔管理ツール MeshCentral を C2 として居座って加入者認証（RADIUS）の資格情報を狙っていた——発覚は攻撃者が踏み台に置いた公開ディレクトリを Hunt.io が2026年6月3日に見つけたためで、3BB・Triple T Broadband・旧親会社 Jasmine のいずれも事案を認める公表をしていない

不正アクセス・侵害脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）脆弱性の放置既知の脆弱性の悪用認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年9月15日 最終更新: 2026年9月16日

脅威情報企業 Hunt.io が、タイのホスティング事業者 Bangmod のインフラ上にあるサーバ 92.63.180[.]133:8888 で、認証のかかっていない公開ディレクトリを2026年6月3日に発見しました。中身は298ファイル・30のサブディレクトリ・約19MB で、攻撃用スクリプト、権限昇格ツール、総当たりツール、資格情報の収集スクリプト、侵害した機器の一覧、そして遠隔管理ツール MeshCentral のエージェント設定が含まれていました。ファイルは Exploit・Victim・Config・History といった運用上の分類で整理されており、稼働中の作業場そのものでした。同社の分析によれば、これらはタイ最大級の固定ブロードバンド事業者 3BB（Triple T Broadband）と、かつて同社を保有していた Jasmine を狙って作られたものです。初期侵入は FortiGate 60F の SSL-VPN でした。攻撃者は8本のシェルスクリプトでファームウェアの版を特定し、CVE-2018-13379・CVE-2022-42475・CVE-2023-27997・CVE-2024-21762 を順に試したうえで、CVE-2024-21762 の攻撃コードを使って遠隔コード実行に至っています。この脆弱性は2024年2月にフォーティネットが修正し、米 CISA が同年2月9日に KEV へ収載して連邦機関に2月16日までの対処を命じたものです。Hunt.io が公開ディレクトリを見つけた2026年6月3日は、その期限から838日後にあたります。侵入後、攻撃者は PwnKit や Dirty COW で root を取り、正規の遠隔管理ツールMeshCentral を C2 として導入して機器を「TH-3BB」というデバイス群にまとめ、55を超える内部 IP へ SSH のパスワードスプレーを行い、SSH 秘密鍵・PHP の設定・データベースの資格情報・SNMP のコミュニティ名を探しました。最終的な狙いは加入者の認証情報が入った RADIUS データベース（radius_corp・radiusinfo）です。痕跡の消去スクリプトは、ウェブシェルやログを消す一方で、MeshCentral のエージェントだけは意図的に残し、居座りが生きているかを確認して終わります。本記録の作成者が2026年9月16日に確認した範囲で、3BB・Triple T Broadband・Jasmine のいずれも本件を認める公表をしていません。攻撃者の帰属も示されていません。本記録は、Hunt.io の調査報告に基づく事実と、本記録の作成者による評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

インターネットに面した FortiGate 60F の SSL-VPN に対し、8本のシェルスクリプトで ファームウェアの版を判定し、既知の FortiOS 脆弱性を順に試したうえで CVE-2024-21762 を悪用して遠隔コード実行を得る。PwnKit・Dirty COW・SUID の バックドアインストーラで root を取り、正規の遠隔管理ツール MeshCentral を C2 として導入して「TH-3BB」のデバイス群にまとめる。55を超える内部 IP への SSH パスワードスプレー、FTP・MySQL への接続試行、SSH 秘密鍵・PHP 設定・ データベース資格情報・SNMP コミュニティ名の探索を経て、 加入者認証の RADIUS データベース（radius_corp・radiusinfo）に迫る。 最後に、悪用とバックドア設置の痕跡・ウェブシェル・ログ・シェル履歴を消し、 MeshCentral のエージェントだけを残して永続化の生存を確認する。

参照・持ち出された情報

    2年以上前に修正され KEV にも載った FortiGate の脆弱性が、まだ入口として通用していた原因・手口出典 [1] [2] [3]

    初期侵入は FortiGate 60F の SSL-VPN でした。攻撃者は8本のシェルスクリプトでファームウェアの版を判定し、CVE-2018-13379・CVE-2022-42475・CVE-2023-27997・CVE-2024-21762 という FortiOS の代表的な脆弱性を順に試し、版が一致した CVE-2024-21762 の攻撃コードを投入して遠隔コード実行を得ています。

    CVE-2024-21762 は2024年2月に修正が出て、米 CISA が同年2月9日に KEV へ収載し、連邦機関に2月16日までの対処を命じた脆弱性です。ランサムウェアでの悪用も「確認済み」と分類されています。Hunt.io が攻撃者の作業場を見つけた2026年6月3日は、その期限から838日後です。

    同時に攻撃者は、F5 BIG-IP に対して CVE-2021-22986・CVE-2022-1388・CVE-2023-46747 を探索し、その背後にある CodeIgniter 製の社内営業ポータルも偵察していました。いずれも既知・修正済みの脆弱性です。

    本記録の評価として、本件に新しい技術はひとつもありません。新しいのは「既知の脆弱性の在庫を束ねた攻撃キット」が、通信事業者という規模の標的に対して用意され、版の判定から攻撃・権限昇格・居座り・痕跡消去まで一式で運用されていたことです。境界機器の脆弱性は、公表直後の数週間だけ危ないのではありません。修正されないまま放置された機器は、何年経っても入口として売買・再利用されます。

    居座りに使われたのはマルウェアではなく、IT 部門が使う正規の遠隔管理ツールだった概観出典 [1] [2] [3]

    侵入後、攻撃者は PwnKit（polkit）と Dirty COW、および SUID のバックドアを仕掛けるインストーラで複数の Linux ホストの root を取り、オープンソースの遠隔管理ツール MeshCentral を C2 として導入しました。侵害したホストは「TH-3BB」というデバイス群にまとめられ、指令先はwww.ayuthayatech[.]com です。エージェントの一部は root 権限で動作していたと報告されています。

    MeshCentral は、企業の IT 部門が端末を遠隔管理するために使う正規のソフトです。検知の観点では、これが厄介です。マルウェアの署名は当たらず、通信はHTTPS の遠隔管理として成立し、プロセス名も見慣れたものになります。「許可された管理ツールかどうか」を判定できるのは、その組織の資産管理と運用ルールだけです。

    横展開では、55を超える内部 IP に対する SSH のパスワードスプレー、FTP・MySQL への接続試行、パスワード無しでの MySQL 認証の試行、SSH 秘密鍵・PHP の設定ファイル・データベースの資格情報・SNMP のコミュニティ名の探索が行われました。Triple T Broadband 自身の PKI が発行した OpenVPN 証明書も見つかっています。

    本記録の評価として、この組み合わせ——既知の脆弱性での侵入と、正規ツールでの居座り——は、EDR の有無より先に「許可された管理ツールの一覧を持っているか」を問います。一覧が無ければ、MeshCentral の通信を見ても、それが自社の運用なのか攻撃者の運用なのかを判定できません。

    狙いは加入者の認証情報だった——通信事業者の RADIUS は「顧客名簿」ではなく「顧客そのものへの鍵」である被害規模・影響範囲出典 [1] [2] [3]

    Hunt.io によれば、攻撃者の最終目的は RADIUS の認証データベース（radius_corp・radiusinfo）からの加入者資格情報の抽出でした。スクリプトは、機微なファイルの読み出し、PHP ウェブシェルの設置、SSH 鍵の注入、データベース権限の改変までを行えるように作られています。

    通信事業者の RADIUS が持つのは、氏名や住所ではなく、加入者が回線に接続するための認証情報です。ここを取られると、個人情報の漏えいという枠に収まりません。加入者になりすました接続、回線の乗っ取り、そこから先の通信の観測——被害の形が変わります。3BB の加入者は数百万規模とされています。

    ただし、実際に持ち出されたかは公表されていません。Hunt.io の報告は攻撃者が残した作業場の解析であり、3BB の環境を調べたものではありません。当事者3社（3BB・Triple T Broadband・Jasmine）のいずれも本件を認める公表をしておらず、加入者への通知の有無も分かりません。

    本記録の評価として、日本の読者が置き換えて読むべき対象は「自社の RADIUS／ディレクトリ／証明書発行基盤」です。本件では自社 PKI が発行した OpenVPN 証明書まで攻撃者の手に渡っています。認証の土台が取られたとき、パスワードの変更だけでは終わらず、証明書の失効と再発行まで含めた復旧計画が要ります。

    痕跡消去スクリプトは、ウェブシェルとログを消したうえで「居座りが生きているか」を確認して終わる発覚の端緒出典 [1] [2]

    攻撃者は、脆弱性の悪用とバックドアの設置に伴う痕跡、PHP ウェブシェル、MeshCentral の導入スクリプト、システムのログ、シェルの履歴を消すスクリプトを用意していました。ここまでは珍しくありません。特徴的なのは、このスクリプトが MeshCentral のエージェントだけは意図的に残し、最後に永続化の仕組みが動いているかを確かめて終わる点です。

    つまり、消しているのは「どうやって入ったか」の証拠であり、残しているのは「これからも入れる経路」です。侵害された側から見ると、調査で最初に当たるはずの侵入経路の痕跡が消えていて、正規ツールとして動いている遠隔管理だけが残っている、という状態になります。

    そして本件の発覚は、被害側の検知ではありません。攻撃者が自分の作業場を認証もかけずにインターネットへ晒しており、それを Hunt.io が2026年6月3日に見つけたためです。

    本記録の評価として、ここから引ける教訓は2つあります。第一に、侵入経路の痕跡が消えていることは「侵害が無かった」ではなく「消せる権限を取られた」の証拠として読むべきだということ。第二に、自社の検知が働かなくても、外部の脅威情報企業や当局からの連絡で事案を知ることがあるということです。外部からの通報を受け取る窓口（security@ の運用、報告への一次応答の手順）が無ければ、知らせたくても知らせられません。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    既知の FortiGate 脆弱性から加入者認証データベースへ——正規ツールで居座り、経路の痕跡だけを消す
    攻撃者はタイのホスティング事業者上に作業場を置き（layer 0）、FortiGate 60F の SSL-VPN の 版を判定して CVE-2024-21762 を悪用する（layer 1→2）。PwnKit・Dirty COW で root を取り（layer 3）、 正規の遠隔管理ツール MeshCentral を C2 として「TH-3BB」のデバイス群を作る（layer 4）。 55を超える内部 IP へ SSH のパスワードスプレーを行い（layer 5）、 加入者認証の RADIUS データベースに迫る（layer 6）。 最後にウェブシェルとログを消し、MeshCentral だけを残す（layer 7）。 発覚は被害側の検知ではなく、晒された作業場を Hunt.io が見つけたことによる。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    偵察機会はあったが検知できず
    版の判定と複数 CVE の試行は、SSL-VPN のアクセスログに 短時間の連続した異常な要求として残りうる。境界機器のログを 集約していなければ見えない段階である。
    検知できた境界機器（VPN・ロードバランサ）のログを外部へ集約し、版判定を狙う連続要求や既知の攻撃パターンを検知対象にする
    影響を限定できたSSL-VPN の接続元を業務上必要な国・ネットワークに限定する
    初期侵入機会はあったが検知できず
    2024年2月に修正が出ており、KEV にも収載されている。 修正を当てていれば侵入自体が成立しない段階であり、 検知以前に構成の問題である。
    侵入を防げた境界機器の脆弱性を、KEV 収載を着手条件として期限付きで更新する（本件の悪用は期限から838日後に痕跡が見つかった）
    影響を限定できた保守切れ・更新できない境界機器を台帳で区別し、更新できない期間の代替（接続元制限・多要素認証・撤去）を決める
    権限昇格機会はあったが検知できず
    PwnKit・Dirty COW はいずれも古く、既知の検知パターンがある。 内部の Linux ホストにホスト型の監視が無ければ素通りする。
    侵入を防げた内部サーバの OS を更新し、PwnKit・Dirty COW など公知の権限昇格の修正を当てる
    検知できたSUID ビットの新規付与と、想定外のバイナリの出現をファイル整合性監視で捉える
    永続化機会はあったが検知できず
    MeshCentral は正規のソフトであり、マルウェアとしては検知されない。 「自社で許可した遠隔管理ツールの一覧」が無ければ、 正規の運用と攻撃者の運用を区別できない。
    侵入を防げた許可する遠隔管理ツール（RMM）を一覧化し、それ以外の実行と通信をアプリケーション制御で遮断する
    検知できたサーバから外部への持続的な HTTPS 接続先を棚卸しし、未登録の管理用ドメインへの接続をアラートにする
    認証情報アクセス機会はあったが検知できず
    設定ファイルの横断的な読み出しや、認証を伴わない MySQL 接続の試行は、 データベース側の接続ログに残りうる。監査ログを取っていなければ残らない。
    検知できたデータベースの接続元を限定し、パスワード無し・匿名の認証を無効化したうえで失敗ログを監視する
    影響を限定できたRADIUS・ディレクトリ・PKI を別の管理区画に置き、一般の運用ホストから直接到達できないようにする
    横展開機会はあったが検知できず
    1つの内部ホストから55を超える内部 IP への SSH 接続試行は、 ネットワークの流量記録でも認証の失敗ログでも捉えられる形である。 内部から内部への通信を見ていなければ気づけない。
    影響を限定できた内部から内部への SSH を管理用の踏み台経由に限定し、直接の横断を遮断する
    検知できたSSH の認証失敗を集約し、短時間に多数の宛先へ試行する送信元を検知する
    検知回避機会はあったが検知できず
    ログをホスト外へ転送していれば、消去そのものが記録の欠落として残る。 本件の発覚は被害側の検知ではなく、攻撃者が晒した作業場の発見による。
    検知できたサーバのログとシェル履歴を即時に外部のログ基盤へ転送し、ホスト上の削除では消えないようにする
    検知できた侵害調査では、侵入経路の痕跡が消えていることを「侵害なし」ではなく「消せる権限を取られた」の兆候として扱う

    CISO・経営層への示唆
    • 境界機器の脆弱性は「公表直後だけ危ない」ではない——2年以上前の既知の穴が現役の入口として使われる
      本件の初期侵入は CVE-2024-21762 で、2024年2月に修正・KEV 収載済みである。 攻撃者はその版がまだ生きていることを前提に道具を組んでいた。 修正されないまま放置された機器は、年単位で入口として再利用される。
      取るべき行動 インターネットに面した機器の版数と修正状況を四半期ごとに棚卸しし、 KEV 収載済みで未対応のものを「期限超過」として経営に報告する一覧に載せる。 更新できない機器は撤去・置換の予算計画に移す。
    • 通信事業者や SaaS のように「他人の認証情報を預かる組織」は、漏えいの意味が一段重い
      本件の狙いは個人情報ではなく、加入者が回線に接続するための RADIUS の認証情報だった。取られれば、なりすまし接続や回線の乗っ取りに直結する。 3BB の加入者は数百万規模とされる。
      取るべき行動 自社が預かる認証資産（RADIUS・ディレクトリ・PKI・API 鍵）を洗い出し、 それぞれについて「取られた場合に失効・再発行できるか、何時間かかるか」を 机上で確認する。証明書は失効と再発行の手順まで含めて確かめる。
    • 自社の検知が働かなくても、外部からの連絡で事案を知ることがある——受け取る窓口が無ければ知らせてもらえない
      本件の発覚は、攻撃者が認証をかけずに晒していた作業場を 脅威情報企業が見つけたことによる。被害側の検知ではない。 当事者3社はいまも公表していない。
      取るべき行動 外部からの脆弱性・侵害の連絡を受ける窓口（security@ 等）を公開し、 一次応答の時間と担当を決める。連絡が来たときに誰が事実確認を始めるかを 平時に決めておく。
    • 正規の遠隔管理ツールが居座りに使われる以上、「許可したツールの一覧」が防御の前提になる
      攻撃者は MeshCentral を C2 に使った。オープンソースの正規ソフトであり、 署名検知もマルウェア判定も当たらない。判定できるのは 自社が許可したツールかどうかだけである。
      取るべき行動 遠隔管理ツール（RMM）の許可リストを作り、資産管理と紐づける。 許可外の RMM の実行・通信を遮断する仕組みを情報システム部門に持たせ、 委託先が持ち込むツールも一覧に登録させる。
    セキュリティ技術者への示唆
    • 版の判定を狙う連続要求は、侵入の直前に必ず現れる
      攻撃者は8本のスクリプトで FortiGate のファームウェア版を特定してから 攻撃コードを選んでいる。侵入の成立前に、境界機器へ特徴的な 要求が並ぶ段階が存在する。
      取るべき行動 境界機器のアクセスログを SIEM へ集約し、短時間に複数の既知エンドポイントを 叩く要求（版判定・脆弱性探索）を検知ルールにする。 機器のローカルログだけに頼らない。
    • 内部から内部への SSH を見ていないと、55宛先へのスプレーも素通りする
      本件では侵害ホストから55を超える内部 IP へ SSH のパスワードスプレーが 行われた。境界の監視だけでは、この段階は一切見えない。
      取るべき行動 内部の SSH を踏み台経由に限定し、直接の横断を遮断する。 認証失敗ログを集約し、短時間に多数の宛先へ試行する送信元を アラートにする。SNMP のコミュニティ名など古い共有秘密の棚卸しも併せて行う。
    • 痕跡が消えていることを「侵害なし」と読まない——本件の消去スクリプトは居座りだけを残した
      消去スクリプトはウェブシェル・ログ・シェル履歴を消す一方、 MeshCentral のエージェントを意図的に残し、永続化が生きているかを 確認して終わる。侵入経路の証拠だけが消える。
      取るべき行動 サーバのログとシェル履歴を即時に外部へ転送する。調査では 「ログの欠落した時間帯」を探索の起点にし、残っている正規ツールの 設定・登録先（デバイス群名・指令ドメイン）を確認する。
    • 自社 PKI が発行した証明書まで取られた場合、パスワード変更では復旧が終わらない
      攻撃者は Triple T Broadband 自身の PKI が発行した OpenVPN 証明書を 見つけている。証明書は、パスワードと違って「変えれば済む」ものではない。
      取るべき行動 VPN・内部通信に使う証明書について、失効（CRL／OCSP）の反映経路と 再発行の所要時間を平時に確認する。失効させたときに止まる業務の一覧も 作っておく。

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ インターネットに面した VPN 装置・ロードバランサがあり、その版数と修正状況を即座に答えられない本件の初期侵入は2024年2月に修正済みの CVE-2024-21762 である。 攻撃者は版を判定してから攻撃コードを選ぶ。版が古いこと自体が入口になる。
    運用・監視□ 境界機器のログを機器の中にしか置いておらず、SIEM やログ基盤へ集約していない版判定を狙う連続要求も、侵入後のログ消去も、機器の外に記録が無ければ 事後に確認できない。本件では消去スクリプトがログとシェル履歴を消している。
    運用・監視□ 許可した遠隔管理ツール（RMM）の一覧が無く、サーバから外部への持続的な接続先を棚卸ししていない攻撃者は正規ツールの MeshCentral を C2 に使った。 許可リストが無ければ、正規の運用と攻撃者の運用を区別できない。
    認証・認可□ RADIUS・ディレクトリ・PKI が一般の運用ホストから直接到達できる場所にある本件の狙いは加入者認証の RADIUS データベースであり、 自社 PKI が発行した VPN 証明書も攻撃者の手に渡っている。 認証の土台が同じ区画にあると、1台の侵害がそのまま全体の認証の喪失になる。
    運用・監視□ 内部から内部への SSH が自由で、認証失敗のログを集約していない55を超える内部 IP へのパスワードスプレーは、内部の通信を 見ていなければ検知できない。境界の監視だけでは見えない段階である。
    体制・契約□ 外部から脆弱性・侵害の連絡を受ける窓口と一次応答の手順が決まっていない本件は外部の脅威情報企業が攻撃者のインフラを見つけて表に出た。 自社の検知が働かない場合、外部からの連絡が唯一の入口になる。
