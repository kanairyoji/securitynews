INC-2026-0152CenterPoint、顧客情報の窃取を認める

米テキサス州の電力・ガス大手 CenterPoint Energy が、外部向けシステムの1つを通じて顧客の個人情報が第三者に取得されたと SEC への Form 8-K で認めた——きっかけは「749万件の顧客レコードを盗んだ」とする攻撃者のオンライン投稿で、攻撃者は BleepingComputer に対し、同社の公開 API で数百万の ID を順に辿っただけであり、レート制限も WAF も自動アクセス対策も無かったと述べている。同社は件数・項目・攻撃者をいずれも公表しておらず、電気・ガスの供給に影響は無い

不正アクセス・侵害意図せぬ露出（設定不備等で外部から到達可能だった）続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備公表されていない／不明
初報: 2026年9月14日 最終更新: 2026年9月17日

CenterPoint Energy（米テキサス州ヒューストン。インディアナ・ミネソタ・オハイオ・テキサスの4州で約700万件の計量顧客に電気とガスを供給）は2026年9月14日、米証券取引委員会（SEC）へ Form 8-K を提出し、外部向けシステムの1つを通じて、一部の顧客の個人情報が権限のない第三者に取得されたと認めました。

きっかけは同社が2026年9月に認知したオンライン投稿です。「4d722e4d656f77」を名乗る攻撃者が749万件の顧客レコード（氏名・電話番号・供給先および請求先の住所・口座番号・請求額・社会保障番号の一部）を盗んだと主張し、犯罪フォーラムで公開しました。

注目すべきは手口として語られた内容です。攻撃者は BleepingComputer に対し、同社の公開 API で数百万の ID を順に辿ってデータを抜いたと説明し、レート制限も WAF も自動アクセスへの対策も無かったと述べています。脆弱性の悪用ではなく、認可の設計が欠けていたという主張です。ただしこれは攻撃者の言い分であり、同社は件数も項目も攻撃者も公表していません。

電気・ガスの供給に影響は無く、同社は財務への重大な影響は見込んでいないとしています。一方で、8月17日から9月1日の間に侵害が起きたと主張する集団訴訟が複数、連邦裁判所へ提起されています。本記録は、日本の電力・ガス・通信の顧客ポータルが同じ構造を持つことを踏まえ、「認証済みでも ID を列挙できれば全件が取れる」型の先例として整理します。一次資料は SEC 提出書類で、評価・示唆は本記録の判断として分けて書きます。

認証を通した先で ID を数えられる API は、脆弱性が無くても全件流出する（本記録の評価）評価・解釈出典 [1] [2]

ここからは本記録の作成者の評価である。攻撃者の主張が事実である前提での整理であることを断っておく。

第一に、これは「壊れた認可」であって「侵入」ではない。 攻撃者が語った手口には、エクスプロイトもマルウェアも出てこない。正規の窓口に、正規の形式で、番号を変えながら問い合わせただけである。Web アプリケーションのリスク分類では最上位に置かれ続けている種類の欠陥だが、境界防御の製品を並べても検知にはつながらない。

第二に、契約者番号は「推測できる識別子」である。 公益事業・通信・保険の顧客 ID は、発番の都合で連番に近い並びになりやすい。ID が推測できるうえ、「自分の ID か」を検証していないなら、1アカウントで全顧客分が引ける。対策は3つの層に分かれる。①ID を推測困難にする、②要求された ID が要求者のものかを毎回検証する、③レート制限で列挙そのものを止める。このうち②が本質であり、①と③は時間を稼ぐ手段にすぎない。

第三に、公益事業の顧客データは「住所と支払能力の束」である。 供給先住所は在宅の実態を示し、請求額は世帯の規模を推測させる。口座番号と社会保障番号の一部が加われば、なりすましによる料金支払いの切り替えや、公共料金を装ったフィッシングの材料になる。電気とガスの供給が止まらなかったことと、顧客が被る被害の大きさは別の話である。

第四に、日本の読者にとっての含意は構造の同型性にある。 電力・ガス・通信・水道の顧客ポータルは、契約者番号やお客さま番号を引数に取る API を持つ。マイページの「請求明細を取得する」というごく普通の機能が、認可の検証を1か所落とすだけで全件取得の窓口に変わる。日本ではこの種の事故が「不正アクセス」として括られ、原因が API の認可欠落だったことまで公表されない例が多い。本件も、同社の公表からは原因が読めない。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
8-K で「外部向けシステムの1つを通じて個人情報が取得された」ことは認めた一方、 件数・項目・攻撃者・原因はいずれも示さなかった不十分本記録の作成者の評価である。攻撃者は既に件数・項目・手口を公開しており、 顧客は自分の社会保障番号の一部が出たかどうかを知りたい段階にある。 8-K は投資家向けの開示であり、顧客が取るべき行動を示す文書が伴っていない
第三者のサイバーセキュリティ専門家を起用し、法執行機関・規制当局へ報告した評価材料なし調査が継続中であり、結果が出ていないため評価できる材料が無い
CISO・経営層への示唆
  • 顧客ポータルの API を「外部公開システム」として棚卸しの対象に入れる
    侵害されたのは同社の外部向けシステムの1つで、攻撃者は公開 API だったと主張している
    取るべき行動 インターネットから到達できる API の一覧（エンドポイント・引数・応答項目・認可の方式）を作り、 顧客識別子を引数に取るものを洗い出して、認可の検証が実装されているかを個別に確認させる
  • 「脆弱性の管理」だけでは防げない類型があることを経営として理解する
    攻撃者が語った手口には脆弱性の悪用が無く、正規の要求を大量に繰り返しただけだとされる。 パッチ適用率や脆弱性診断の件数では、この欠陥は可視化されない
    取るべき行動 セキュリティの報告指標に「認可の設計レビューを実施した API の割合」を加え、 脆弱性スキャンとは別枠で進捗を管理する
  • 攻撃者が先に公開した場合の顧客向け説明を、投資家向け開示とは別に用意する
    8-K は件数も項目も示さず、一方で攻撃者は社会保障番号の一部まで含むと公開している
    取るべき行動 インシデント時の開示計画に、規制当局向けの開示と同時に出す顧客向けの説明文 （分かっている範囲・分かっていない範囲・取るべき行動）を組み込み、両者を同じ日に出す
  • 大量の正常アクセスを「異常」として見る監視に投資する
    列挙による窃取は、個々のリクエストが正常であるため既存の検知に掛からない
    取るべき行動 API ゲートウェイで利用者単位・エンドポイント単位の応答レコード数を日次で集計し、 平常の分布から外れた場合に自動で遮断する仕組みへの投資を判断する
セキュリティ技術者への示唆
  • 要求された ID が要求者のものかを、サーバ側で毎回検証する
    攻撃者は「数百万の ID を順に辿った」と述べており、これが事実なら本人確認が抜けていた
    取るべき行動 顧客識別子を引数に取るすべてのエンドポイントで、セッションの主体と対象レコードの所有者の一致を サーバ側で検証する。テストコードに「他人の ID を指定すると 403 になる」検査を入れる
  • 外部に出す識別子を推測困難な値にする
    契約者番号や顧客 ID は発番の都合で連番に近くなり、列挙の的になる
    取るべき行動 API の引数と URL に業務上の連番（契約者番号）を使わず、ランダムな識別子を割り当てて対応表で内部変換する。 既存システムでは、外部公開面だけでも置き換える
  • レート制限を「1IP あたり」ではなく「1アカウント・1トークンあたり」で設ける
    自動アクセスへの対策が無かったと攻撃者は述べている
    取るべき行動 API ゲートウェイでアカウント単位・トークン単位のレート制限と日次の総応答件数の上限を設定し、 超過時に遮断して通知する。IP 単位だけでは分散アクセスで回避される
  • 列挙のパターンそのものを検知ルールにする
    個々のリクエストは正常応答であり、エラー率の監視では気づけない
    取るべき行動 同一利用者からの要求で、対象 ID が連続または規則的に変化するパターンを検知する。 短時間に多数の異なる顧客レコードへ到達した場合に警報を出す

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 顧客向けポータル・アプリが、契約者番号や顧客 ID を引数に取る API を公開している攻撃者は公開 API の ID を順に辿って749万件を取得したと主張している
認証・認可□ API のエンドポイントで、要求された ID が要求者本人のものかをサーバ側で検証していない箇所がある認可の検証が1か所抜けるだけで、1アカウントから全顧客分が引ける
システム構成□ 外部に出す識別子として連番に近い業務上の番号（お客さま番号・契約番号）を使っている推測可能な識別子は列挙の的になる
運用・監視□ API のレート制限が無い、または IP 単位でしか設けていない自動アクセスへの対策が無かったと攻撃者は述べている
運用・監視□ API の応答レコード数を利用者単位で集計・監視していない列挙による窃取は正常応答の積み重ねであり、量を見なければ検知できない
体制・契約□ 漏えいの認知が外部（攻撃者の公開・報道）に依存しており、自社の監視で気づく想定になっていない同社は攻撃者のオンライン投稿を認知して調査を開始している
