INC-2026-0164AWS 中東2リージョンでデータ喪失確定

AWS が2026年9月15日の Health Dashboard 更新で、中東の戦闘により損壊したバーレーン（me-south-1）とアラブ首長国連邦（me-central-1）のインフラについて、一部のデータとリソースの復旧を断念すると確定した——バーレーンは3月に1つのアベイラビリティゾーン、4月にもう1つが損壊してリージョン全体が利用不能になり、AWS は「損害は複数のアベイラビリティゾーンにまたがり、リージョンおよびマルチAZのサービスが耐えるよう設計された範囲を超えた」と説明した。当該リージョンにのみ置かれていたデータは失われ、UAE では mec1-az2 の復旧不能が確定した。大半の顧客は2つめのゾーンが落ちる前に他リージョンへ移行していたとされる

システム障害続報が続いている有名事象として記録（日本と直接の関係は薄い）物理的要因
初報: 2026年9月15日 最終更新: 2026年9月17日

Amazon Web Services（AWS）は2026年9月15日、AWS Health Dashboard の更新で、中東の戦闘により損壊したバーレーン（me-south-1）およびアラブ首長国連邦（me-central-1）のインフラについて、一部のデータとリソースの復旧を断念すると確定しました。

経過はこうです。バーレーンでは2026年3月に me-south-1 のmes1-az2が損壊し、AWS は顧客に他リージョンへの移行を推奨していました。ところが4月にもう1つのアベイラビリティゾーン（AZ）も損壊し、リージョン全体が利用不能になりました。AWS は「損害はわれわれのインフラの複数のアベイラビリティゾーンにまたがり、リージョンおよびマルチAZのサービスが耐えるよう設計された範囲を超えた」（原文英語）と説明し、「影響を受けた全インフラを評価し、リージョンが利用不能になる前に移行されていなかったデータとリソースを復旧するあらゆる手段を尽くした」（原文英語）としています。当該リージョンにのみ置かれていたデータとリソースへのアクセスは回復できません。

UAE の me-central-1 では、mec1-az2 の復旧不能が確定し、残る mec1-az1 と mec1-az3 は復旧作業が続いています。AWS は、大半の顧客は2つめのゾーンが落ちる前にバックアップ等を用いて他リージョンへワークロードを移行していたと述べています。次回の更新は me-central-1 が数か月内、me-south-1 は2027年初頭の予定です。

ここが重要です。マルチAZ構成は1つのデータセンターの障害を前提とした冗長化であり、地域全体に及ぶ物理的破壊は想定の外にあります。リージョンの全損に備える手段はマルチリージョン構成しかないという教科書的な結論が、実際のデータ消失を伴って確認されました。

攻撃の帰属について Health Dashboard は触れていません。報道はイランによるドローン攻撃と結びつけていますが、本記録では AWS の説明と報道を分けて扱います。本記録の作成者は Health Dashboard の本文を取得できておらず、AWS の文言は報道が引用したものに依拠します。

マルチAZは「1つのデータセンターが落ちる」前提の冗長化であり、地域全体の破壊はその外にある評価・解釈出典 [1] [2] [3]

ここからは本記録の作成者の評価である。

第一に、AWS の説明は設計の限界を正確に述べている。 マルチAZ構成は、同一リージョン内で互いに隔離された複数のデータセンター群にまたがって配置することで、1つのデータセンターの障害のリスクを下げる仕組みである。「リージョンおよびマルチAZのサービスが耐えるよう設計された範囲を超えた」という文言は、弁明ではなく設計の前提の説明として読むのが正しい。

第二に、それでも顧客側の想定は外れた。 多くの組織は「マルチAZにしてあるからデータセンター1つが落ちても大丈夫」と理解し、そこで止めている。リージョンの全損に備える手段はマルチリージョン構成しかない——この教科書的な結論が、今回は実際のデータ消失を伴って確認された。設計資料の上での結論と、実際に消えた事例があることの差は大きい。

第三に、時間差が救いになった。 バーレーンでは3月に1つめの AZ が落ちた時点でAWS が移行を推奨し、4月に2つめが落ちるまでの間に大半の顧客が他リージョンへ移ったとされる。つまり本件で顧客のデータを救ったのは冗長構成ではなく、警告を受けてから動くための1か月と、移行できる状態にあったかどうかである。逆に言えば、移行の手順と権限を平時に用意していなかった組織が取り残された可能性が高い（本記録の推測。残った顧客の内訳は公表されていない）。

第四に、災害の想定を「自然災害」に限っていると本件は視野に入らない。事業継続計画の多くは地震・水害・電源喪失を前提に書かれている。武力衝突・海底ケーブルの切断・法的措置（データの差し押さえや制裁による利用停止）は、リージョン単位で相関する事象であり、同じ想定の枠に入れておく必要がある。日本国内でも複数リージョンの利用は進むが、同一国内のリージョン間で相関する事象は残る。

第五に、「復旧不能の確定」までに半年かかったことは顧客の判断を難しくした。 3月・4月の損壊から9月15日の確定まで約6か月、顧客は「戻ってくるかもしれないデータ」を待つ状態に置かれた。その間に再構築を決めたか待ったかで、コストと復旧の時期は大きく変わったはずである（本記録の観測）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
1つめの AZ（mes1-az2）が損壊した2026年3月の時点で、リージョン内での復旧を待たせるのではなく 顧客に他リージョンへの移行を推奨した機能した本記録の作成者の評価である。結果として大半の顧客が4月の全損前に移行できた。 「1つ落ちたら残りも危ういと考えて動く」判断が、本件では顧客のデータを救った唯一の要因である
復旧不能の理由を「損害が複数の AZ にまたがり、リージョンおよびマルチAZのサービスが 耐えるよう設計された範囲を超えた」と、設計の前提に即して説明した機能した本記録の作成者の評価である。「あらゆる手段を尽くした」と併記して復旧の断念を明言した点も含め、 顧客が自らの構成を見直すために必要な情報を出している。 一方で失われた量・顧客数・「大半」の中身を示していないため、影響の規模は外から測れない
CISO・経営層への示唆
  • マルチAZはリージョン全損に備える構成ではない——その差を経営の言葉で把握する
    AWS は「損害は複数の AZ にまたがり、リージョンおよびマルチAZのサービスが耐えるよう 設計された範囲を超えた」と説明し、当該リージョンにのみ置かれていたデータは失われた
    取るべき行動 重要システムの一覧に対し「単一AZ／マルチAZ／マルチリージョン」のどれで構成しているかを 列に持たせ、マルチAZ止まりのものについては「リージョンが全損したら復旧できない」と 明記して経営に示す。許容するかどうかの判断を記録に残す
  • 事業継続計画の災害の想定に、武力衝突・海底ケーブル・法的措置を加える
    本件の原因は地震でも水害でもなく戦闘によるデータセンターの物理的損壊である。 リージョン単位で相関する事象は自然災害に限らない
    取るべき行動 事業継続計画の想定事象に、武力衝突・大規模停電・海底ケーブル障害・ 制裁や法的措置によるサービス利用停止を追加し、各事象で「どのリージョンが同時に失われるか」を 書き出す。同一国内の複数リージョンで相関する事象も洗い出す
  • 「移行を推奨された1か月」で動ける状態にあるかが、最後の分かれ目になる
    3月に1つめの AZ が落ちてから4月の全損までの約1か月で、大半の顧客が他リージョンへ移行した。 冗長構成ではなくこの猶予のうちに動けたかどうかが結果を分けた
    取るべき行動 主要システムについて、他リージョンへ退避する手順・所要時間・必要な権限・費用の 承認経路を文書化し、年1回、実際に別リージョンで立ち上げる演習を行う。 演習では暗号鍵と構成情報が退避先で使えるかまで確認する
  • クラウド事業者の「復旧可否の判断」に半年かかりうることを前提に、待つ／捨てるの判断基準を決める
    3月・4月の損壊から9月15日の復旧断念の確定まで約6か月、顧客は戻るかもしれないデータを待つ状態にあった
    取るべき行動 重要システムごとに「事業者からの復旧見込みが示されない期間が何日を超えたら 再構築に切り替えるか」の閾値を決めておく。判断の権限者と、再構築の費用の出どころも併せて決める
  • 契約の不可抗力条項とデータ喪失時の責任範囲を、更新前に読み直す
    AWS は補償や SLA 上の扱いを示していない。武力衝突は多くの契約で不可抗力に該当する
    取るべき行動 主要なクラウド・SaaS の契約について、不可抗力条項の範囲、データ喪失時の責任上限、 リージョン全損時の扱いを法務と確認する。重要データについては自社側でのバックアップ保持を 契約とは別の前提として決める
セキュリティ技術者への示唆
  • リージョン外にバックアップがあるかを、システム単位で確認する
    失われたのは「当該リージョンにのみ置かれていたデータとリソース」である。 リージョン内に複製があっても、リージョンが消えれば同時に失われる
    取るべき行動 バックアップの保存先リージョンを一覧化し、本番と同一リージョンに閉じているものを洗い出す。 重要データはリージョン間レプリケーションまたは別リージョンへの定期コピーに切り替える
  • 復旧に必要な暗号鍵・構成情報・イメージが同じリージョンに閉じていないかを確かめる
    データを別リージョンに持っていても、復号の鍵や構成情報が失われたリージョンにあれば復旧できない
    取るべき行動 鍵管理サービスの鍵・シークレット・マシンイメージ・インフラ定義（IaC）・ コンテナレジストリの所在を棚卸しし、いずれも復旧先リージョンから使える状態にする。 実際に別リージョンだけで立ち上げて確認する
  • AZ 単位の障害と、リージョン単位の喪失を、別の演習として分けて行う
    本件は AZ が1つ落ちた段階（3月）とリージョンが全損した段階（4月）で、取るべき行動が違った
    取るべき行動 障害演習を「AZ 1つ停止」と「リージョン全損」の2種類に分け、後者では 別リージョンでの新規構築と外部バックアップからの復元を実際に通す。 所要時間を測って復旧目標時間（RTO）と突き合わせる
  • クラウド事業者の Health Dashboard の更新を、人ではなく仕組みで拾う
    本件の移行推奨（3月）と復旧断念の確定（9月15日）は、いずれも Health Dashboard の更新で示された。 気づくのが遅れれば猶予を使い切る
    取るべき行動 利用しているリージョン・サービスについて Health Dashboard の通知（AWS Health の イベント通知等）を運用の連絡先へ配信し、リージョン規模の事象は担当者へ即時に届くようにする。 通知が届くことを定期的に確認する
