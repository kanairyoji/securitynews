INC-2026-0166繋のコーポレートサイトにバックドア設置

株式会社繋のコーポレートサイト（WordPress）に第三者が管理者権限のアカウントを不正に作成し、サーバ上にバックドア等の不正プログラムを設置していた——問い合わせフォームの投稿157件に含まれる氏名・メールアドレス・住所・電話番号が閲覧・取得可能な状態にあった。持ち出しの直接の証跡は無いが「調査に利用できる記録（ログ）が限定されている」ため漏えいの可能性を否定できないとし、侵入経路も記録の制約で特定に至らなかった。対象期間は2024年3月から2026年6月まで飛び飛びの7区間で、いずれも約2週間ずつに区切られている

不正アクセス・侵害続報が止まり調査も完了日本の組織が当事者公表されていない／不明設計・実装上の不備
初報: 2026年7月20日 最終更新: 2026年8月27日

株式会社繋（つなぐ）は2026年8月27日、同社が運営するコーポレートサイト（https://tsng.co.jp/）への不正アクセスについて、外部専門機関による調査の結果を公表しました。

同社が異常を確認したのは2026年6月29日です。直ちにサイトの公開を停止して証拠保全を行い、外部専門機関の調査を実施した結果、第三者により管理者権限を持つアカウントが不正に作成され、サーバ上にバックドア等の不正プログラムが設置されていたことが確認されました。これらの操作により、サイトとそのデータベースに保存されていた情報は第三者が技術的に閲覧・取得可能な状態にあったと同社は述べています。

対象は、問い合わせフォームへの投稿157件に含まれる氏名・メールアドレス・住所・電話番号です。投稿の時期は2024年3月6日〜3月19日、2024年4月17日〜4月30日、2024年6月15日〜6月28日、2024年11月1日〜11月14日、2025年12月1日〜12月14日、2025年12月26日〜2026年1月8日、2026年5月28日〜6月29日の7区間で、いずれも約2週間ずつに区切られています。これらは「本サイトのメール送信ログ等に保持されていた」ものです。

同社は持ち出しを直接示す記録や証跡は確認されていないとしながら、「調査に利用できる記録（ログ）が限定されていること等から、情報が外部へ漏えいした可能性を完全に否定することはできない」と結論しました。最初の侵入経路も、記録の制約により特定に至っていません。

注目すべき点が2つあります。ひとつは、残っていたログの範囲が、そのまま「特定できた被害範囲」になっていること。約2週間ずつの飛び飛びの7区間という形は、実際の露出範囲ではなくログの保持の都合を反映している疑いがあります（本記録の推測。同社はログの保持方針を説明していません）。もうひとつは、検索エンジンの検索結果に同社とは無関係な内容が同社サイトの情報として表示される事象が残っていることです。サイトを新環境で作り直しても、外部の索引に残った改ざんの痕跡は自力では消せません。

事実は同社の公表文に、評価・示唆は本記録の判断として分けて書きます。

残っていたログの範囲が、そのまま「特定できた被害範囲」になっている評価・解釈出典 [1] [2]

ここからは本記録の作成者の評価である。

第一に、対象期間の形が不自然である。 7区間のうち6つがきっちり14日間で、しかも2024年3月・4月・6月・11月、2025年12月、2026年1月、2026年5〜6月と飛び飛びに散っている。問い合わせの投稿がこの期間にだけ集中したと考えるより、ログの保持期間や定期削除の設定がその形を作ったと考えるほうが自然である（本記録の推測。同社は説明していない）。もしそうなら、特定された157件は「残っていた分」であって「露出した分」ではない。同社が「漏えいした可能性がある」と書けたのは、たまたまログが残っていた区間だけである。

第二に、ログが足りないことが二度効いている。 同社は「調査に利用できる記録（ログ）が限定されていること等から、情報が外部へ漏えいした可能性を完全に否定することはできない」とし、さらに「最初にどのような経路で侵入したかについては、取得可能であった記録等に制約があるため、特定には至っておりません」としている。被害範囲の確定にも、原因の特定にも、同じ理由で届かなかった。ログの保全は平時の地味な投資だが、事故の後に取り返す手段が無い唯一の材料である。

第三に、公開用サイトに個人情報が「残ってしまう」構図は広く共有されている。 WordPress の問い合わせフォームでは、送信内容をメールで転送するだけのつもりでも、プラグインの機能やメール送信のログとしてサーバ上に蓄積されることがある。同社の再発防止策「お問い合わせ情報等の個人情報を Web サイト環境内に保存しない構成への変更」は、その保持が意図したものではなかったことを示している。フォームの入力がどこに何日残るかを把握している組織は多くない（本記録の評価）。

第四に、「業務システムとは分離されていた」ことが被害を限定した。 同社はコーポレートサイトの環境が、通常業務のシステムおよび顧客から預かる業務データの環境と分離されていると明記した。侵害されたのは広報用のサイトであり、受託業務のデータには届いていない。公開サイトは最も侵害されやすく、最も分離しやすい資産である。ここが繋がっている組織では、同じ侵入が事業の中核に届く。

第五に、検索エンジンに残った改ざんは、サイトを作り直しても消えない。改ざんされたサイトに置かれた無関係なページ（多くは広告・誘導を目的とするもの）は、検索エンジンの索引に取り込まれる。自社サーバから削除しても、外部の索引が更新されるまで表示は残る。同社が再開後も注意喚起を続けているのはこのためである。復旧の完了を「サイトが再開したこと」で判定すると、この残務が視界から外れる。

第六に、二段階の公表（7月20日の第一報・8月27日の調査結果）は妥当な形である。第一報は「改ざんを確認した」という事実だけを21日後に出し、調査結果は59日後に出した。調査を待って一度だけ出すより、先に事実を置いてから精査の結果を足すほうが、利用者が自分の投稿の有無を気にかける時間を確保できる。一方で第一報には「詳細はこちらのページをご確認ください」とあるだけで、いつ続報を出すかの見通しが示されていない（本記録の指摘）。

管理者権限を取得され、バックドアを置かれた後の参照を、 サイト側の仕組みで検知することは現実的に難しい。 この段階は「そもそも公開環境に個人情報を置かない」ことで対処する。
影響を限定できた問い合わせフォームの投稿内容を Web 公開環境に保存しない構成にする　本記録の作成者が挙げた統制。同社が再発防止策として挙げたのと同じである。 侵害されても持ち出される個人情報が存在しない状態を作る。
影響を限定できたメール送信ログ・フォームのプラグインが保持する投稿履歴の保存期間を明示的に設定する　本記録の作成者が挙げた統制。本件では2024年3月の投稿が2026年6月まで残っていた。 残す期間を決めていなければ、既定の設定のまま蓄積し続ける。
影響（暗号化・破壊・改ざん）機会はあったが検知できず
自社名や自社ドメインでの検索結果を定期的に確認していれば、 無関係な内容の表示に気づけた。改ざんの発覚が検索結果の異常からもたらされる例は多い。
検知できた自社ドメインの検索結果と、検索エンジンの管理コンソールの警告を定期的に確認する　本記録の作成者が挙げた統制。無料で運用でき、改ざんの早期発見に最も効く手段のひとつである。
復旧を早められた復旧の完了条件に「外部の索引から不正なページが消えること」を含める　本記録の作成者が挙げた統制。サイトの再開だけでは復旧は終わらない。 削除の申請と再クロールの促進を、作業として計画に入れる。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
異常を確認した当日にコーポレートサイトの公開を停止し、証拠保全を同時に開始した機能した本記録の作成者の評価である。停止と証拠保全を同時に行ったことで、 限られた記録の中でも「管理者アカウントの不正作成」「バックドアの設置」までは 特定できている。改ざんの露出を止める判断としても正しい
既存の WordPress 環境およびデータベースを再利用せず、新たな環境を構築して 必要なコンテンツのみを移行した機能した本記録の作成者の評価である。バックドアは複数仕掛けられることが多く、 侵入経路が特定できていない本件では、洗浄して戻す方針は根拠を持てない。 あわせて個人情報をサイト環境に置かない構成へ変えており、 「元に戻す」ではなく「同じ事故が起きても被害が出ない形にする」復旧になっている
6月29日の異常確認から21日後に事実のみの第一報を出し、 59日後に調査結果を詳細とともに公表する二段階の形をとった部分的に機能本記録の作成者の評価である。二段階の形自体は妥当だが、 第一報に「いつごろ続報を出すか」の見通しが無く、 7月20日から8月27日までの38日間、対象かもしれない人は待つことしかできなかった
「持ち出しの直接の証跡は無い」と「ログが限定されているため漏えいの可能性を 完全には否定できない」を並べて書き、侵入経路が特定できなかったことも明記した機能した本記録の作成者の評価である。「確認されていない」と「無かった」を混同させない書き方であり、 中小規模の事業者の公表としては水準が高い。 調査の限界を認めた公表は、読者が自分の risk を過小評価することを防ぐ
CISO・経営層への示唆
  • 事故調査の解像度は、平時に取っていたログの量で決まる——後から取り返せない
    本件では「調査に利用できる記録（ログ）が限定されている」ことを理由に、 漏えいの有無も侵入経路も確定できなかった。外部専門機関を入れても、 残っていない記録は復元できない
    取るべき行動 公開サイトを含む外部向け資産について、アクセスログ・認証ログ・ファイル改変の記録を どこに何日分残しているかを一覧にする。侵害されたサーバの外に保存されているかを 確認し、90日以上の保持を目安に設定する。委託先が運用している場合は契約で保持期間を定める
  • コーポレートサイトを「情報を持たない広報物」と見なす前に、実際に何が残っているかを確かめる
    本件で漏えいの可能性が生じたのは、問い合わせフォームの投稿内容が メール送信ログ等としてサーバに残っていたためである。 2024年3月の投稿が2026年6月まで残っていた
    取るべき行動 自社の公開サイトについて、フォームの投稿がどこに何日残るかを実際に確認する。 メール転送だけのつもりでも、プラグインやログに蓄積されていることがある。 残す必要が無ければ、サイト環境の外へ出す構成に変える
  • 「持ち出しの証跡は無い」と「持ち出されていない」を、社内でも社外でも混同させない
    同社は両者を並べて書き、ログの制約ゆえに漏えいの可能性を否定できないと結論した。 証跡が無いことは、調べた結果として無いのか、調べる材料が無かったのかで意味が正反対になる
    取るべき行動 事故の公表文の雛形に「確認できたこと／確認できなかったこと／確認する材料が無かったこと」の 3区分を設ける。経営への報告でも同じ区分を使い、材料が無い項目を 「問題なし」に丸めない運用にする
  • 復旧の完了条件に、外部の索引（検索エンジン）からの消去を含める
    同社はサイトを新環境で再開した後も、検索結果に無関係な内容が表示される事象が残り、 利用者へ注意喚起を続けている。自社サーバの復旧では終わらない
    取るべき行動 Web サイトの侵害を想定した復旧手順に、検索エンジンの管理コンソールでの 削除申請・再クロールの要求・キャッシュの状況確認を作業として明記する。 担当と所要見込みを事前に決めておく
  • 公開サイトは、事業システムから分離しておけば侵害の影響を広報物の範囲に閉じ込められる
    同社はコーポレートサイトの環境が、通常業務のシステムおよび顧客から預かる業務データの 環境と分離されており、それらへの影響を示す事実は確認されていないと明記できた
    取るべき行動 公開サイトが、社内ネットワーク・認証基盤・業務データと接点を持っていないかを確認する。 同一サーバでの同居、同じ認証情報の使い回し、業務システムへの API 接続が典型的な接点である
セキュリティ技術者への示唆
  • 管理者権限アカウントの新規作成を、即時通知の対象にする
    本件では第三者により管理者権限のアカウントが不正に作成されていた。 管理者の追加は日常の運用ではめったに起きない操作であり、通知に向く事象である
    取るべき行動 CMS・クラウド・SaaS のいずれについても、管理者権限の付与・アカウントの作成を 運用担当者へ即時通知する設定にする。あわせて四半期に1回、管理者一覧を棚卸しする
  • 公開領域のファイルの追加・変更を検知する
    バックドアの設置は必ずファイルの追加または変更を伴う。 本件では設置されたまま気づかれず、異常が確認されるまで残っていた
    取るべき行動 公開ディレクトリのファイルのハッシュを定期的に照合し、 コンテンツ更新以外の変更を通知する。WordPress であれば 本体・テーマ・プラグインの配布物との差分照合を行う仕組みを入れる
  • 侵害されたサイトは洗浄して戻さず、作り直す
    管理者アカウントの不正作成とバックドアの設置は、一方を消されても戻れるようにする 二重の足場である。侵入経路が特定できていない状態で洗浄しても、 取りこぼしが無いことを示せない
    取るべき行動 侵害時の復旧手順を「新環境を構築し、必要なコンテンツのみを移す」形で用意しておく。 移行の対象（記事・画像・設定）と、移さないもの（実行可能ファイル・プラグインの実体・DBのユーザ表）を あらかじめ決めておく
  • フォームのプラグインとメール送信ログの保存期間を、既定のままにしない
    本件の対象期間は約2週間ずつの飛び飛びの7区間で、最も古いものは2024年3月である。 残っていたログの範囲が、そのまま特定できた被害範囲になっている
    取るべき行動 利用中のフォーム・メール関連プラグインが投稿内容を保持する場所と期間を確認し、 保持しない設定にするか、保存期間を明示的に設定する。 設定後に実際に投稿して、どこに何が残るかを目で確かめる
  • 自社ドメインの検索結果を、定期的に確認する仕組みに載せる
    改ざんは、閲覧者や検索結果の異常から発覚することが多い。 本件でも検索エンジンに同社と無関係な内容が表示される状態が残った
    取るべき行動 検索エンジンの管理コンソールを登録し、セキュリティの警告を運用の連絡先へ届くようにする。 自社名・自社ドメインでの検索結果を月1回確認する作業を、運用の手順に加える
