INC-2026-0171Brevo の CDN 改ざんで10万サイト汚染

メール配信SaaS の Brevo で、アプリケーションのソースコードにハードコードされていた全アカウント権限・長期有効の Cloudflare API キーが奪われ、攻撃者が Cloudflare Worker を作って CDN のエッジで応答を書き換えた——2026年9月14日の約5時間半、自社サイトと顧客サイトに埋め込まれたフォーム・チャット・SDK の各スクリプトへ ClickFix の偽「人間確認」ページが注入され、Sansec は影響を受けた可能性のあるサイトを10万超と推計した。Worker はレスポンスヘッダの Content-Security-Policy を削除したため、オリジンのサーバとファイルは無改変で、通常の完全性チェックでは検知できなかった。WordPress サイトでは管理者としてログイン中の訪問者に偽プラグインを導入しようとした

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備設計・実装上の不備
初報: 2026年9月15日 最終更新: 2026年9月18日

メール配信・CRM の SaaS である Brevo（旧 Sendinblue）は2026年9月14日、攻撃者が同社の Cloudflare API キーを悪用して悪性の Cloudflare Worker を作成し、CDN のエッジで応答を書き換えたと公表しました。約5時間半のあいだ、同社のサイトと、顧客が自社サイトに埋め込んでいる JavaScript に悪性コードが注入されました。

奪われたキーの性質が被害の規模を決めています。Brevo の事後報告によれば、それは全アカウント権限を持つ長期有効の API キーで、アプリケーションのソースコードにハードコードされていました。攻撃者はこのキーで Cloudflare の Worker・ルート・DNS レコードを同社のゾーン全体にわたって作成でき、その操作は警報を発生させませんでした。

改ざんの入り口は自社サイトだけではありません。書き換えられたのは brevo.com・sendinblue.com・sibforms.com の各ページに加え、顧客がサイトに貼り付けているBrevo フォームのスクリプト・Conversations ウィジェット・SDK ローダーでした。セキュリティ企業 Sansec は、影響を受けた可能性のあるサイトを10万超と推計しています。

注入されたのは ClickFix——偽の「Cloudflare、あなたが人間であることを確認」ページを表示し、訪問者に Windows でコマンドを貼り付けて実行させる手口です。さらに WordPress サイトでは、管理者としてログイン中の訪問者に対して悪性プラグインを導入しようと試みました。BleepingComputer が VirusTotal 上で確認した検体は「Web Media Optimizer」を名乗り、プラグイン一覧から自身を隠し、must-use プラグインへ自己複製し、攻撃者のサーバから読み込む JavaScript を差し替え続ける作りでした。

もっとも実務的な含意はここにあります。エッジで書き換えられたため、オリジンのサーバとファイルは最後まで無改変でした。 ファイルのハッシュを比べる通常の完全性チェックは、この攻撃を捉えません。本記録は Brevo のステータスページに掲載された事後報告（一次資料）と Sansec の調査、BleepingComputer・SecurityWeek の報道で事実を確認し、評価・示唆は本記録の判断として分けて書きます。なお同社は2026年9月10日にも SSO の実装不備による別事案を公表しており、本記録とは別にINC-2026-0124 として記録しています。両者の関連について同社は答えていません。

エッジで書き換えたため、オリジンのファイルは最後まで無改変だった原因・手口出典 [1] [3]

本件で最も学ぶべき点は、検知できなかった理由である。Brevo は事後報告でこう書いている。

Because the Worker rewrote responses at the edge and removed security headers such as Content-Security-Policy, our origin servers and files remained unmodified and standard integrity checks did not detect the change.（Worker がエッジで応答を書き換え、Content-Security-Policy などのセキュリティヘッダを削除したため、オリジンのサーバとファイルは無改変のままであり、通常の完全性チェックではこの変更を検知できなかった。原文英語）

サプライチェーン攻撃の対策として一般に勧められるのは、配信するファイルのハッシュを監視すること、Subresource Integrity（SRI）を使うこと、リポジトリの改ざんを検知することである。そのいずれも、この攻撃には効かない。 改ざんは自社の資産の上では起きておらず、利用者のブラウザに届く直前の経路で起きたためである。しかも Worker はContent-Security-Policy ヘッダを削除しており、注入されたスクリプトを止めるはずの防御も同時に外されていた。

キーの性質も見ておく必要がある。Brevo の説明では、それは長期有効（long-lived）で全アカウント権限（full account permissions）を持ち、アプリケーションのソースコードにハードコードされていた。この3つが揃うと、1本の文字列が「DNS を含む配信基盤全体の管理権限」と同じ意味を持つ（本記録の整理）。

気づいたのは自社の監視ではなく、外部のセキュリティ企業だった発覚の端緒出典 [1] [2] [3]

WordPress に入った偽プラグインは、Brevo の復旧では消えない波及・関係先出典 [2] [3]

この事案の影響は、Brevo が Worker を削除した時点で終わっていない。

BleepingComputer が VirusTotal 上の検体から確認したところ、導入されるwm.zip は「Web Media Optimizer」を名乗る WordPress プラグインで、実体は永続的なバックドアかつ JavaScript ローダーだった。挙動は次のとおりである。

  • プラグイン一覧から自身を隠す
  • must-use プラグインのディレクトリへ自己複製して永続化する
  • 攻撃者の glegchner[.]com/ads.php へ定期的に通信し、Base64 で符号化されたJavaScript の URL を受け取って訪問者のページへ注入する
  • 最後に有効だった JavaScript の URL を控えとして保存し、攻撃者のサーバが落ちても読み込みを続けられるようにする
  • ハードコードされた認証キーを持ち、パスワードを知らなくてもWordPress 管理者の有効なログインセッションを生成できる

つまり、導入されてしまったサイトは、Brevo 側の復旧とは無関係に侵害され続ける。BleepingComputer は、9月14日にログイン状態で該当サイトを訪れた WordPress 管理者に対し、その日に導入・有効化された見慣れないプラグインを確認して削除し、管理者パスワードを変更するよう呼びかけている。

  • 悪性 WordPress プラグインが実際に導入されたサイト数

  • 影響を受けた10万超のサイトの国別内訳（日本のサイトの被害を確認した公表は見つかっていない）

なお「10万超」という数字は、Sansec が推計した悪性スクリプトを配信しうる状態だったサイトの数であり、被害の実数ではない。Brevo 自身はこの数値を示していない。

委託先の完全性チェックは「相手のオリジン」ではなく「自分に届くもの」を見ないと成立しない（本記録の評価）評価・解釈出典 [1] [2] [3]

ここからは本記録の作成者の評価である。

第一に、第三者スクリプトの管理は「どのドメインを許すか」で止まっている組織が多い。本件では、許可したドメイン（sibforms.com）から、許可した名前のスクリプトが、正しい TLS で配信されてきた。変わったのは中身だけである。配信元を信頼するという前提そのものが攻撃対象になった。

第二に、Content-Security-Policy を「相手が付けてくれるもの」として当てにできない。 Worker は CSP ヘッダを削除した。自社サイトが自ら CSP を設定し、外部スクリプトの読み込み先と実行可能な内容を自分の側で宣言していれば、注入されたコードの一部は止まった可能性がある（本記録の評価。実際に止まったという報告は無い）。第三者の配信するスクリプトに integrity 属性を付けられるかは、そのスクリプトが更新されるかどうかに依存するため万能ではないが、「自分の HTML に書ける防御は自分で書く」という原則は変わらない。

第三に、長期有効の広範な権限を持つキーは、それ自体が単一障害点である。本件のキーは全アカウント権限を持ち、期限が無く、コードの中にあった。短命化（有効期限）・最小権限・秘密管理基盤への集約（Brevo は HashiCorp Vault の導入を挙げた）のどれか1つでも効いていれば、被害の形は変わっていた。

第四に、SaaS の事後報告の質は、利用者が事故から回復できるかを左右する。 Brevo はステータスページに分単位の時系列と根本原因、影響した資産・しなかった資産を公開した。この情報があるから、利用者は「自社のサイトが16:07〜20:30 UTC に該当スクリプトを配信していたか」を自分で確認できる。一方で、悪性プラグインへの対処の呼びかけを行ったのは Brevo ではなく報道側だった。供給元の復旧と、利用者側に残った被害の後始末は別の仕事である（本記録の評価）。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
ソースコード内の API キーから CDN のエッジを経て、10万超の顧客サイトの訪問者まで届いた経路
layer 0 は攻撃者。layer 1 は奪われた Cloudflare API キーと、それで作られた悪性 Worker。 layer 2 は書き換えの対象となった Brevo の配信物。layer 3 は顧客サイトと WordPress。 layer 4 は訪問者と管理者。オリジンのサーバとファイルは無改変のままで、 改ざんはエッジでのみ起きている。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。

認証情報アクセス公表されていない

侵入を防げたリポジトリとビルド成果物に対する秘密情報の走査を CI に組み込み、検出時にマージを止める

実行機会はあったが検知できず

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
ステータスページに分単位の時系列、根本原因（ソースコードにハードコードされた 全アカウント権限・長期有効の Cloudflare API キー）、影響した資産と影響しなかった資産、 再発防止策を公開した機能した本記録の作成者の評価である。「キーがソースコードにあった」「その操作は警報を 発生させなかった」「通常の完全性チェックでは検知できなかった」という3点を 自ら書いている点は、事後報告として質が高い。利用者はこの情報から 自社サイトの該当時間帯を突き合わせられる
公表はステータスページの事後報告で行い、影響を受けた個別のサイトの特定・通知は行わなかった不十分本記録の作成者の評価である。悪性 WordPress プラグインは導入されれば Brevo の復旧後も残り続けるにもかかわらず、利用者側の点検手順を呼びかけたのは 報道側だった。影響時間帯にスクリプトを配信した顧客への個別の注意喚起は、 供給元にしかできない仕事である
CISO・経営層への示唆
  • 第三者スクリプトの利用を「どのベンダーを使っているか」ではなく「どのページに何が埋まっているか」で把握する
    本件で改ざんされたのは、顧客が自社サイトに貼り付けたフォーム・チャット・SDK の スクリプトである。契約しているベンダー名だけを把握していても、 どのページのどの機能が影響を受けるかは判断できない
    取るべき行動 自社の全ページで読み込んでいる外部スクリプトを機械的に列挙し、 ベンダー・用途・設置ページ・設置した部門の一覧を作る。 マーケティング部門が独自に入れたタグも対象に含める
  • SaaS 供給元の事故に備えて、「自社が何時から何時まで影響を受けたか」を自分で言える状態にする
    Brevo は分単位の時系列を公開したが、影響を受けた個別サイトの特定・通知は行っていない。 利用者は自分で突き合わせるしかない
    取るべき行動 主要な外部スクリプトについて、配信元・読み込みページ・アクセスログの保管期間を 確認しておく。供給元が時間帯を公表したときに、その時間帯の自社の訪問者数を すぐ出せるようにする
  • 委託先・供給元の「秘密情報の扱い」を、契約と点検の対象に入れる
    原因は供給元のソースコードに残っていた全権限の API キー1本だった。 利用者側でどれだけ防御を積んでも、この種の原因は止められない
    取るべき行動 重要な SaaS について、秘密情報の管理方法（秘密管理基盤の利用、キーの有効期限、 権限の範囲、シークレットスキャンの実施）を調達時の確認項目に加える。 既存の契約先には年次のアンケートで確認する
  • 供給元の復旧と、自社に残った被害の後始末を別々に管理する
    Brevo が Worker を削除しても、その間に WordPress へ導入された悪性プラグインは残る。 しかも一覧から自身を隠し、must-use ディレクトリへ複製する
    取るべき行動 供給元の事故報告を受け取ったときに「自社側で残るものは何か」を必ず一項目として 検討する手順を、インシデント対応計画に入れる。ウェブサイトの管理を外部委託している 場合は、委託先へ点検を指示する経路も決めておく
セキュリティ技術者への示唆
  • 配信物の完全性は、オリジンではなく「外から取得したもの」で確認する
    Brevo は「オリジンのサーバとファイルは無改変のままで、通常の完全性チェックでは この変更を検知できなかった」（原文英語）と説明している。改ざんは CDN のエッジで起きた
    取るべき行動 外部の複数地点から自社サイトの主要ページと JavaScript を定期取得し、 期待するハッシュおよびセキュリティヘッダ（CSP 等）の有無と突き合わせる監視を作る。 差分が出たら警報にする
  • Content-Security-Policy を自分の HTML で宣言し、外部任せにしない
    攻撃者の Worker は CSP ヘッダを削除した。応答ヘッダに依存する防御は、 経路を握られた時点で無効になる
    取るべき行動 CSP を meta タグとヘッダの両方で設定し、script-src に許可する配信元を列挙する。 report-uri／report-to で違反を収集し、実際の読み込み先を棚卸しする材料にする
  • CDN・DNS 基盤の監査ログを、アプリのログと同じ重みで警報の対象にする
    Worker・ルート・DNS レコードの作成が警報を発生させず、検知まで5時間かかった。 Brevo 自身が再発防止策に「Cloudflare の全監査イベントの監視」を挙げている
    取るべき行動 CDN・DNS・証明書発行の監査イベントを収集し、①Worker やエッジ関数の作成・更新、 ②ルートの追加、③DNS レコードの追加、④新しいサブドメインの証明書発行を 個別の警報にする。深夜・休日の変更は特に上位の警報にする
  • API キーに有効期限と最小権限を与え、コードから追い出す
    奪われたのは「長期有効」「全アカウント権限」「ソースコードにハードコード」という 3条件が揃ったキーだった
    取るべき行動 CDN・クラウド・SaaS の API キーを棚卸しし、有効期限の有無・権限の範囲・ 保管場所を一覧にする。期限の無いキーから順に、秘密管理基盤（Vault 等）へ移し、 権限をゾーン・操作単位に絞る。CI にシークレットスキャンを入れて再発を止める
  • WordPress の must-use プラグインとプラグイン一覧の差分を監視する
    導入された偽プラグインは、プラグイン一覧から自身を隠し、 must-use プラグインのディレクトリへ自己複製して永続化する
    取るべき行動 wp-content 以下（特に mu-plugins）のファイル追加・変更を監視し、 管理画面の一覧ではなくファイルシステムを正とする点検を定期実行する。 2026年9月14日に管理者としてログインしたまま該当サイトを閲覧した端末があれば、 その日に追加されたプラグインを確認して削除し、管理者パスワードを変更する

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 自社サイトに外部 SaaS のフォーム・チャット・解析・SDK のスクリプトを埋め込んでいる本件で改ざんされたのは、顧客が自社サイトに貼り付けた3種のスクリプトだった。 Sansec は影響を受けた可能性のあるサイトを10万超と推計している
システム構成□ 配信物の完全性を、オリジンのファイルのハッシュやリポジトリの監視だけで確認している本件の改ざんは CDN のエッジで起き、オリジンのファイルは最後まで無改変だった
認証・認可□ CDN・クラウド・SaaS の API キーに有効期限が無く、権限が全体に及ぶものがある奪われたキーは全アカウント権限を持つ長期有効のもので、 ゾーン全体にわたる Worker・ルート・DNS レコードの作成を許した
運用・監視□ CDN・DNS の設定変更（エッジ関数・ルート・レコードの作成）が警報の対象になっていないBrevo では一連の作成操作が警報を発生させず、検知まで5時間を要した
運用・監視□ 自社または委託先が運用する WordPress サイトで、プラグインの追加をファイル単位で監視していない導入された偽プラグインは管理画面の一覧から自身を隠し、 must-use ディレクトリへ複製して供給元の復旧後も残り続ける
体制・契約□ SaaS 供給元の事故報告を受けたときに、自社側に残る被害を検討する手順が無いBrevo の復旧は自社資産の正常化までで、利用者の WordPress に残ったバックドアは対象外だった
