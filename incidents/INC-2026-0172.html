INC-2026-0172Plugin4Shell でSHA固定が破られる

AIコーディングエージェント4種（Claude Code・Codex・GitHub Copilot・Gemini CLI）が、マーケットプレイスがコミットハッシュで固定したプラグインを取得したあと、手にしたコードがそのハッシュと一致するかを検証していなかった——プラグインのリポジトリを支配する者が、ピン留めされた SHA と同じ名前のブランチを作って既定ブランチにすると、git は ref を優先するためエージェントは「固定版を導入した」と報告しながら別のコードを実行する。Air Security は Plugin4Shell と名付け、既定で有効なプラグインの自動更新と組み合わさることでゼロクリックの遠隔コード実行になると指摘した。Anthropic は Claude Code 2.1.179、OpenAI は Codex 0.146.0 で修正し、GitHub Copilot は未修正、Google は Gemini CLI を廃止予定として修正しない

脆弱性委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年9月17日 最終更新: 2026年9月18日

セキュリティ企業 Air Security は2026年9月17日、主要なAIコーディングエージェント4種 ——Anthropic の Claude Code、OpenAI の Codex、Microsoft の GitHub Copilot、Google の Gemini CLI——に共通する脆弱性を Plugin4Shell として公表しました。プラグインのコミットハッシュによる固定（SHA ピン留め）が、実際には効いていないという指摘です。

仕組みはこうです。マーケットプレイスは各プラグインを「レビュー済みの1つの版」に固定するため、コミットハッシュ（コードの特定の断面を指す長い文字列）を記録します。ところがエージェントは、その断面を取得するだけで、手元に来たコードが本当にそのハッシュのものかを検証していません。攻撃者がプラグインのリポジトリを支配していれば、ピン留めされた SHA とまったく同じ名前のブランチを作り、それをリポジトリの既定ブランチに設定できます。git は「名前が有効な ref であり同時にオブジェクトIDでもあるとき、ref を優先する」（原文英語）ため、エージェントは「固定版を導入した」と報告しながら、攻撃者のコードをチェックアウトします。

これがゼロクリックになるのは、プラグインの自動更新があるためです。Air によれば Claude Code と Codex は既定で導入済みプラグインを自動更新します。利用者がすでに信頼して入れたプラグインが、確認を求められることなく差し替わります。プラグインは利用者と同じ権限で動くため、差し替わったコードは利用者のファイル、保存された認証情報、ログインできるシステムに到達します。

重要な限定が2つあります。第一に、GitHub はコミットSHA に似たブランチ名・タグ名の作成を許していないため、GitHub 上のリポジトリから導入したプラグインにはこのブランチの手口が効きません。各エージェントの既定カタログは GitHub を指しています。第二に、Air は「マーケットプレイスは Bitbucket や自社の git サーバでもホストでき、それらも対応構成である」として、GitHub の措置では不十分だと反論しています。

対応は分かれました。Anthropic は Claude Code 2.1.179、OpenAI は Codex 0.146.0 で修正し、GitHub Copilot は未修正、Google は Gemini CLI を廃止予定として修正しないと回答しています。2026年9月18日時点で CVE は採番されておらず、4ベンダーのいずれもこの問題についてセキュリティアドバイザリを公表していません。実際の攻撃に使われた形跡も報告されていません。本記録は Air Security の公表と報道で事実を確認し、評価・示唆は本記録の判断として分けて書きます。

「レビュー済みのコミットに固定した」という表示のまま、別のコードが動く概観出典 [1] [2] [3]

Air Security が公表した事実は次のとおりである。

  • マーケットプレイスは各プラグインをコミットハッシュ（SHA）で1つのレビュー済みの版に固定する
  • しかしエージェントは、取得したコードがそのハッシュと一致するかを検証していない
  • Claude Code・Codex・GitHub Copilot が実行するのは、おおむね次の2行である

git clone <plugin repo> ./ git checkout aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa

  • 攻撃者がピン留めされた SHA と同じ名前のブランチを作り、リポジトリの既定ブランチに設定すると、git は「名前が有効な ref であり同時にオブジェクトIDでもあるとき ref を優先する」（原文英語）ため、攻撃者のブランチがチェックアウトされる
  • Gemini CLI は別の経路である。git fetch origin <sha> のあと git checkout FETCH_HEAD を実行するため、既定ブランチを FETCH_HEAD と名付けると、取得したコミットではなくそのブランチが解決される
  • 修正は1行の断言で済む。Air はtest "$(git rev-parse HEAD)" = "<pinned-sha>" || abort を示している

利用者から見える表示は変わらない。エージェントは「固定版を導入した」と報告しながら、別のコードを実行する。ここが本件の核心である。

ゼロクリックになるのは、プラグインの自動更新があるため原因・手口出典 [1] [2] [3]

脆弱性そのものは「検証の欠落」だが、利用者の操作を一切要さない攻撃に仕立てているのは別の機能である。

Air によれば、Claude Code と Codex は既定で導入済みプラグインを自動更新する。上流でピン留めされたコミットが差し替われば、利用者が何もしなくてもプラグインが入れ替わる。すでに信頼して導入したものが、確認を求められることなく変わる。

攻撃の筋道は2つ挙げられている。

  1. 無害なプラグインを自分でマーケットプレイスへ登録し、レビューを通したうえで、あとから中身を悪性のものへ差し替える
  2. 正規の作者のリポジトリを乗っ取り、そのプラグインを導入している全エージェントへ悪性版を押し出す

2 について、同じ研究チームは以前 SkillJacking・RepoJacking としてリポジトリ乗っ取りが実際に規模を持って成立することを示している。Air の主張は「乗っ取りは大規模に起きる。そして Plugin4Shell は、それを封じ込めるために作られた仕組みを破る」（原文英語）というものである。

プラグインは利用者と同じ権限で動く。したがって差し替えられたコードは、その人のファイル、保存された認証情報、ログインできるシステムに到達する。

GitHub 上では成立しないが、それは前提条件であって修正ではない対策・注意喚起出典 [1] [2] [3]

影響範囲には明確な限定がある。GitHub はコミットSHA に似たブランチ名・タグ名の作成を許していない。 GitHub の広報は The Register にこう答えている。

SHA の悪用を防ぐため、GitHub はコミットSHA に似たブランチ名・タグ名を利用者が作ることを許していない。この緩和により、報告された脆弱性は GitHub 上では悪用できない。（原文英語）

The Hacker News が2026年9月18日に確認したところ、Anthropic のコミュニティカタログ、および Claude Code と Copilot の既定カタログのプラグインは、すべて GitHub リポジトリを指していた。自動更新が既定で有効なのも、各エージェント自身の組み込みマーケットプレイス（GitHub 上）に限られ、外部のものは無効か任意である。既定のマーケットプレイスからしかプラグインを入れていない利用者は、ブランチ名を使う手口の対象にならない。

それでも、これを「対処済み」と読むのは早い（本記録の評価）。理由は3つある。

  • Air の反論: マーケットプレイスは Bitbucket や自社の git サーバでもホストでき、Copilot はそうした構成にも対応している。対応している以上、影響は残る
  • Gemini CLI の手口は別: 既定ブランチを FETCH_HEAD と名付ける経路について、GitHub のハッシュ状の名前を禁じる規則が明確に塞いでいるとは確認されていない
  • コードホストの規則は、いつでも自社の外にある: 今日の GitHub の仕様が明日も同じである保証を、利用者側は持っていない

本来の防御はエージェント側の1行の検証であり、コードホストの禁止規則はその代わりにはならない。

エージェントの「信頼の根拠」は、まだ検証されていない前提の上に積まれている（本記録の評価）評価・解釈出典 [1] [2] [3]

ここからは本記録の作成者の評価である。

第一に、破られたのは実装ではなく「安心の設計」である。 SHA ピン留めは、供給網攻撃への対策として推奨されてきた仕組みである。「レビュー済みの版に固定してあるから安全」という説明が、利用者にも監査にも通ってきた。本件はその説明の根拠が検証されていなかったことを示した。対策として機能していると信じられていたものが、実は表示だけだったという形は、2026年9月14日の Brevo の事案（CDN のエッジで書き換えられ、オリジンのファイルは無改変のため完全性チェックが働かなかった。INC-2026-0171）と同じ構図である。

第二に、権限の設計がそのまま被害の上限になる。 プラグインは利用者と同じ権限で動く。開発者の端末には、ソースコード・クラウドの資格情報・SSH 鍵・本番への接続情報が揃っている。エージェントに与えた権限が、そのまま供給網攻撃の到達範囲になる。

第三に、修正の配布が製品の寿命に依存している。 4製品のうち、2つは修正され、1つは未修正、1つは「廃止予定だから直さない」である。利用者が選んだ製品の事業上の位置づけが、脆弱性が直るかどうかを決めている。これは技術の問題ではなく調達の問題であり、CISO が扱うべき論点である。

第四に、この種の問題は今後 CVE の外側で増える。 開示から公表まで3か月あったにもかかわらず、CVE も各社のアドバイザリも出ていない。AIエージェントの拡張機能は、OS のパッケージやライブラリと違い、脆弱性情報の流通経路がまだ整っていない。当面、利用者は研究者の公表と報道を自分で拾い、自社の利用状況と突き合わせる必要がある。

事案の詳細

affected_versionsClaude Code は 2.1.179 より前、Codex は 0.146.0 より前が影響を受ける。 GitHub Copilot は修正が提供されておらず全バージョンが対象。 Gemini CLI は廃止予定として修正されないため、すべての導入が影響を受けたままとされる。 ただし成立の条件は「プラグインのリポジトリを支配できること」と 「そのリポジトリを置くコードホストがコミットSHA に似たブランチ名を許すこと」であり、 GitHub 上のリポジトリから導入したプラグインにはブランチ名の手口が効かない （Gemini CLI の FETCH_HEAD の手口については、GitHub の規則が塞いでいるとは確認されていない）
exploitation_status実際の攻撃に使われた形跡は報告されていない（2026年9月18日時点。The Hacker News の確認）。 Air Security は2026年5月に4エージェントすべてに対して動作する実証を作成している。 攻撃者に求められるのは、悪性プラグインを自ら登録してレビュー通過後に差し替えるか、 正規の作者のリポジトリを乗っ取ることであり、未知の脆弱性や認証情報の窃取は要らない

item: エージェントの権限（到達できるファイル・資格情報・ネットワーク）を絞る　副作用: エージェントが実行できる作業が減り、利用者が権限を戻そうとする圧力が生じる。 絞る範囲は業務内容に応じて個別に決める必要があり、一律の設定では運用が回らない

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
ピン留めされた SHA と同じ名前のブランチを作ることで、固定版の表示のまま攻撃者のコードが実行される経路
layer 0 は攻撃者（プラグインのリポジトリを支配する者）。layer 1 はコードホストと マーケットプレイス。layer 2 はエージェントの取得・チェックアウト処理と、 そこで抜けている検証。layer 3 は実行される攻撃者のコードと到達先。 GitHub はハッシュ状のブランチ名を禁止しているため、この経路は Bitbucket・自社 git サーバで成立する。実際の悪用は確認されていない。

CISO・経営層への示唆
  • AIコーディングエージェントの拡張機能を、ソフトウェア資産として台帳に載せる

    取るべき行動 どのエージェントを誰が使い、どのプラグイン・スキルをどのマーケットプレイスから 導入しているかを一覧化する。導入を許可制にし、一覧に無いものを検出する仕組みを決める
  • 「CVE が出ていない＝問題が無い」と読める運用を点検する
    本件は2026年6月にベンダーへ開示され9月に公表されたが、CVE は採番されず、 4ベンダーのいずれもアドバイザリを出していない。 CVE を起点にした脆弱性管理では捕捉できない

  • 採用する開発ツールの「製品の寿命」を、セキュリティの判断材料に入れる
    Google は Gemini CLI を廃止予定として本件を修正しないと回答した。 利用者が選んだ製品の事業上の位置づけが、脆弱性が直るかどうかを決めている
    取るべき行動 主要な開発ツールについて、提供者の保守方針（サポート期限・修正の提供範囲）を 調達時に確認し、契約または記録に残す。廃止予定が公表された製品は、 移行の期限を決めて計画に載せる
  • 自社の git サーバ・Bitbucket を拡張機能の配布に使っているかを確認する
    GitHub はコミットSHA に似たブランチ名を許さないためこの手口が効かないが、 Bitbucket や自社サーバでは成立する。Copilot はそうした構成にも対応している
    取るべき行動 社内で独自のプラグイン・スキルのマーケットプレイスを立てていないかを確認し、 立てている場合は、コードホストがハッシュ状のブランチ名を許すかを検証する。 許す場合は、ホスト側の禁止設定かエージェント側の更新のどちらで塞ぐかを決める
セキュリティ技術者への示唆
  • Claude Code は 2.1.179 以降、Codex は 0.146.0 以降へ更新する
    修正はエージェント側にしか入れられない。マーケットプレイスは利用者のために この問題を直せない（検証は利用者の端末で行われるため）
    取るべき行動 利用中の版を確認し、2.1.179／0.146.0 以降へ更新する。 更新後も、すでに差し替えられたプラグインが取り除かれるかは公表されていないため、 導入済みプラグインを一度棚卸しし、不要なものは削除する
  • ピン留めを信頼する前に、ピン留めが検証されているかを確かめる
    マーケットプレイスがコミットハッシュで固定していても、 エージェントが `git rev-parse HEAD` と突き合わせていなければ意味を持たない

  • プラグイン・拡張機能の自動更新を、既定のまま使うかを意識的に決める
    本件がゼロクリックになったのは自動更新のためである。 一方で自動更新を止めると、修正の適用も止まる
    取るべき行動 エージェントごとに自動更新の設定を確認し、既定のマーケットプレイス（GitHub 上）からの 更新は許し、外部ホストからの更新は手動にする、といった方針を決めて設定に反映する。 決めた内容を開発環境の標準設定として配布する
  • エージェントに与える権限を、端末の全権限から切り離す
    プラグインは利用者と同じ権限で動く。開発者端末には本番への接続情報や クラウドの資格情報が揃っていることが多い
    取るべき行動 エージェントを専用のコンテナ・専用アカウントで動かし、 参照できるディレクトリと到達できるネットワークを限定する。 長期有効な資格情報は端末から取り除き、短命なトークンに置き換える
