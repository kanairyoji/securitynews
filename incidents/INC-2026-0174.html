INC-2026-0174OpenAI フォーラムから従業員アカウント乗っ取り

OpenAI のコミュニティフォーラム（Discourse）に HEIF 画像を1枚上げるだけで任意コード実行に至り、そこから OpenAI 従業員の ChatGPT・Codex アカウントが乗っ取られ、内部モノレポ openai/openai に PR が作られた——入口は画像検査の FastImage が HEIF を読めず ImageMagick 経由で libheif に攻撃者のファイルが直接渡る経路（CVE-2026-32882・CVSS 8.8）で、フォーラムの侵害が本体アカウントに届いたのは OpenAI 側のサインインの不備による。研究者3名は Claude Opus 5 で実用的なエクスプロイトを3時間以内に組み上げ、発見から内部リポジトリ到達まで72時間を切った。OpenAI は報告から約14時間で修正し6,500米ドルを支払った

脆弱性不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用設計・実装上の不備脆弱性の放置
初報: 2026年9月18日 最終更新: 2026年9月19日

セキュリティ研究企業 Hacktron の研究者3名は2026年9月18日、OpenAI のコミュニティフォーラム（community.openai.com）に画像を1枚アップロードするところから始めて、OpenAI 従業員のChatGPT・Codex アカウントを乗っ取り、社内のモノレポ openai/openai にプルリクエストを作成するところまで到達した研究を公表しました。発見から内部リポジトリ到達までは72時間を切っています。

入口は画像処理でした。フォーラムが動く Discourse は通常 FastImage で画像を検査しますが、FastImage は HEIF 形式に対応していなかったため、HEIF ファイルは ImageMagick の変換処理へ回され、その先の libheif が攻撃者の作ったファイルを直接パースする位置に置かれていました。研究者はこの libheif にヒープバッファオーバーフローを見つけ（後に CVE-2026-32882、Discourse 側の深刻度 CVSS 8.8）、画像アップロード経由のリモートコード実行とDiscourse の管理者アクセスを得ています。

そこから先が本件の要点です。フォーラムを取られただけでは本体サービスには届かないはずでした。研究者によれば、OpenAI 側のサインインの不備により、フォーラムの侵害が ChatGPT と Codex のアカウント乗っ取りに転化しました。乗っ取った従業員のアカウントでは Codex が OpenAI の GitHub組織に接続されており、研究者は「内部コードを実際には読まずに影響を示すため」として、その Codex に指示して内部モノレポへプルリクエスト（#1186742）を開かせ、そこで試験を止めています。

手順の速さも記録に値します。2026年7月24日に Claude Opus 4.8 でエクスプロイトを組もうとして失敗し、翌25日に公開された Claude Opus 5 を使うと3時間以内に動くものができたと研究者は書いています。

対応は速く進みました。OpenAI は報告から約14時間で修正し、9月1日に6,500米ドルを支払っています。Discourse は報告の3日後（7月28日）に勧告 GHSA-vhm9-85gw-x335 を公開し、画像処理のサンドボックス化を追加しました。

本記録は、外部の掲示板SaaSの画像処理という「本体の外側」から、本体サービスのアカウントと社内リポジトリまで一本の線がつながった事例として整理します。事実は Hacktron の公表とDiscourse の勧告に基づき、評価・示唆は本記録の判断として分けて書きます。

連鎖の起点は本体の外側にあった。フォーラムは製品ではなく、OpenAI のバグバウンティでも対象から明示的に除外されていた（OpenAI のコメント）。それでも、そこから本体のアカウントと社内リポジトリに届いている。

FastImage が HEIF を読めず、ImageMagick 経由で libheif に攻撃者のファイルが直接渡っていた原因・手口出典 [1] [2]

画像アップロードを受けるサービスは、まず「これは本当に画像か」を検査する。Discourse はその検査に FastImage を使う。ところが FastImage は HEIF 形式に対応していなかった。対応していない形式は検査を素通りし、ImageMagick（magick コマンド）の変換処理へ回される。ImageMagick は HEIF/HEIC を libheif で読む。

結果として、攻撃者が任意に作った HEIF ファイルが、libheif のパーサに直接届く経路ができていた。研究者はこの libheif にヒープバッファオーバーフローを見つけ、境界外の読み書きを足がかりに、Discourse の Docker イメージ（Debian 12 ベース）上でリモートコード実行を成立させている。

もう一点、下流に効く事情がある。研究者によれば、該当箇所のコードは前年に上流で変更されていたが、その変更はセキュリティ修正として文書化されず、CVE も付与されなかった。そのため Debian のパッケージ（12 の 1.19.7、13 の 1.19.8）には古い実装が残り続けていた。静かに直された不具合は、下流のディストリビューションには届かない。

Discourse は2026年7月28日に勧告 GHSA-vhm9-85gw-x335 を公開した。CVE は CVE-2026-32882、深刻度は CVSS v3.1 で 8.8（AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H）。PR:L が示すとおり、必要なのは「画像をアップロードできる利用者」であることだけで、フォーラムは誰でも登録できる。修正版は 2026.7.0・2026.6.1・2026.5.2・2026.1.6 で、あわせて画像処理のサンドボックス化が防御層として追加された。

フォーラムの侵害が本体アカウントに届いたのは、OpenAI 側のサインインの不備による波及・関係先出典 [1] [3]

本件で最も移植性のある論点はここである。フォーラムが1つ落ちただけなら、被害はフォーラムの中で終わるはずだった。

研究者は次のように書いている——「脆弱性をエスカレートさせるのは Discourse に限った話ではない。フォーラムの侵害を ChatGPT と Codex へのアクセスに変えたのは、OpenAI のサインインの問題だ」（原文英語）。つまり、「OpenAI でサインイン」を外部のフォーラムに提供していたことが、フォーラム側の侵害を本体側の権限に変換する経路になった。

さらにその先がある。乗っ取られた従業員のアカウントでは、Codex が OpenAI の GitHub 組織に接続されていた。Codex は指示を受けてコードを書き、PR を出すエージェントである。したがってアカウントを取られるということは、そのアカウントが連携している先すべてに指示を出せるということを意味した。研究者は「ChatGPT と Codex にはさまざまなサービスを接続できるので、理論上到達しうる範囲は非常に広く、GitHub・Slack・メールを含む」と述べている。

具体的な仕組みは公表されていない。 OpenAI 側からの技術的な説明も無い。同じように「自社のサインインを外部サービスに提供し、かつ本体アカウントにエージェントと外部連携をぶら下げている」組織は、自社の該当性を判断できない状態にある（本記録の評価）。

報奨の扱いには留保が付いている。OpenAI は「Discourse がホストする community.openai.com に対する試験は、当社のバグバウンティの対象から明示的に除外されている。今回の報奨はOpenAI 側の発見に対するものであり、Discourse に対する行為に対するものではない」（原文英語）とコメントした。対象外の資産に対する試験だったが、そこから本体に届いたという構図であり、バウンティの範囲設定と実際の攻撃面が一致していなかったことを示している（本記録の評価）。

「使えるエクスプロイトを書ける人は希少」という前提が、この事案では成り立っていない（本記録の評価）評価・解釈出典 [1] [2] [3]

ここからは本記録の作成者の評価である。

第一に、この事案の新しさは脆弱性ではなく所要時間にある。 画像パーサのメモリ破壊も、外部サービス経由の侵害も、新しい話ではない。新しいのは、7月23日の調査開始から7月25日の内部リポジトリ到達まで72時間を切ったことである。研究者自身が「ソフトウェアは長くセキュリティの複雑性から恩恵を受けてきた。脆弱性を確実に動くエクスプロイトに変えるには、これまで希少な専門知識が必要だった。AI はこの希少な専門知識を計算資源に変えることで、その保護を取り払っている」（原文英語）と書いている。7月24日に Claude Opus 4.8 で組めなかったものが、翌25日に公開された Claude Opus 5 では3時間以内に動いた、という記述も同じことを示している。防御側の前提のうち、「そこまでやる攻撃者はいない」に依存していた部分は、順番に外れていく。

第二に、攻撃面の定義を「自社の製品」で切ると足りない。 起点は製品ではなくコミュニティフォーラムであり、バウンティの対象からも外れていた。業務で使う SaaS・フォーラム・ヘルプセンター・ステータスページは、自社のサインインとつながっている限り本体の攻撃面である。 対象外と決めるのは自社の都合であって、攻撃者の都合ではない。

第三に、アカウントに「エージェント」がぶら下がっている時代の被害は、従来と別物である。乗っ取られた従業員の Codex は GitHub 組織に接続されていた。アカウントを取ることは、そのアカウントが連携している先へ指示を出せることを意味する。従来の「メールが読まれる」「ファイルが取られる」とは、影響の形が違う。連携の棚卸しは、パスワード管理と同じ頻度で必要になっている。

第四に、「静かな修正」は下流に届かない。 該当コードは前年に上流で直っていたのに、セキュリティ修正として記録されず CVE も付かなかったため、Debian のパッケージには古い実装が残った。依存ライブラリのバージョンを CVE の有無だけで判断していると、この種の穴は見えない。コンテナイメージのベースOSに含まれるライブラリまで含めて、実際のバージョンを把握しておく必要がある。

第五に、日本の組織にとっての当てはまりは具体的である。 Discourse は国内でもコミュニティフォーラムやユーザー会の基盤として使われている。加えて、ImageMagick 経由で画像変換を行う構成は Discourse に限らない。利用者からの画像アップロードを受け、サーバ側で変換しているサービスは、変換処理をサンドボックス化しているかを確認する価値がある。これは Gyazo の事案（INC-2026-0155）で「アップロードを受ける入口から先に何が届くか」を問うた論点と同じ場所である。

    取るべき行動 リスク評価で「悪用の難易度が高い」を理由に優先度を下げている項目を洗い出し、 前提が今も成り立つかを見直す。公開面の脆弱性は難易度ではなく到達性で優先する

    取るべき行動 コンテナイメージのベースOSに含まれるライブラリまで含めて実際のバージョンを把握し、 CVE の有無にかかわらず上流の最新版との乖離を可視化する。重要な依存はバージョン差分も追う

  • 画像・ファイルの変換処理はサンドボックスに入れる
    libheif のパーサ不具合が、そのままフォーラムサーバ上のリモートコード実行になった。 Discourse は修正後、防御層として画像処理のサンドボックス化を追加している
    取るべき行動 変換処理を別プロセス・別コンテナに切り出し、読み取り専用ルート・シェル無し・ 外向き通信禁止で動かす。変換プロセスからの子プロセス生成を警報にする

  • コンテナのベースOSに含まれる画像ライブラリのバージョンを把握する
    脆弱だったのはアプリケーションのコードではなく、Discourse の Docker イメージ （Debian 12 ベース）に含まれていた libheif 1.19.7 である
    取るべき行動 イメージの SBOM を生成し、OS パッケージ層まで含めて依存を把握する。ベースイメージの 更新を定期的に行い、更新しない場合は該当ライブラリの上流の変更を追う

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 利用者からの画像・ファイルのアップロードを受け、サーバ側で変換・サムネイル生成を行っている本件はアップロードされた画像がデコーダに直接届く経路でコード実行に至った。 ImageMagick 経由の変換は Discourse に限らず広く使われている
委託・第三者部品□ Discourse・フォーラム・ヘルプセンター等の SaaS／OSS を自社ドメインで運用している起点は本体の製品ではなく、外部ソフトウェアで動くコミュニティフォーラムだった。 Discourse は国内でもユーザー会・コミュニティ基盤として使われている
認証・認可□ 自社のサインイン（SSO・ソーシャルログイン）を外部サービスに提供しているフォーラム側の侵害が本体サービスのアカウント乗っ取りに転化したのは、サインインの不備による
認証・認可□ 従業員の業務アカウントに AI エージェントや外部連携（GitHub・Slack・メール）がぶら下がっているアカウントの奪取が、そのまま連携先への指示に変わった。Codex は GitHub 組織に接続されていた
運用・監視□ 脆弱性管理を CVE の有無で判断しており、コンテナのベースOS層のライブラリを追えていない該当コードは前年に上流で直っていたが CVE が付かず、Debian のパッケージに古い実装が残っていた
体制・契約□ バグバウンティ・ペネトレーションテストの対象範囲から、コミュニティ資産や外部連携を外している本件のフォーラムは OpenAI のバウンティ対象から明示的に除外されていたが、そこから本体に届いた
