INC-2026-0175CrowdSec の私有リポジトリ170個が流出

フランスのセキュリティ企業 CrowdSec の私有 GitHub リポジトリ約170個が2026年5月22日にコピーされ、9月16日にフォーラムへ公開された——入口は退職直後の従業員の端末で、5月11日の TanStack npm 汚染（CVE-2026-45321）で GitHub の OAuth トークンを抜かれていた。会社は引き継ぎのためアカウントを残しており、コピーの3日後に削除している。流出したのは SaaS コンソール・データサイエンス資産・ブロックリストの合意形成アルゴリズムと、利用者83名のメールアドレスおよび2020年の潜在投資家51名の情報で、9月17日の第一報は「クライアントデータも氏名も何も漏れていない」としていた

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年9月17日 最終更新: 2026年9月18日

CrowdSec（フランスのセキュリティ企業。OSS の侵入検知エンジンと、利用者の検知を持ち寄って作る悪性 IP のブロックリストを提供している）は2026年9月18日、同社の私有 GitHub リポジトリ約170個が2026年5月22日にコピーされていたことを報告しました。コピーされたコードは9月16日にオンラインのフォーラムへ公開され、同社はそこで事態を知っています。

使われたのは、退職したばかりの従業員のアカウントの GitHub OAuth トークンでした。その端末は2026年5月11日の TanStack npm 供給網攻撃（CVE-2026-45321）で侵害されており、汚染版のインストール時に GitHub トークン・SSH 鍵・クラウド認証情報が抜かれています。CrowdSec は引き継ぎ作業のためにこの従業員の GitHub アクセスを残しており、コピーの3日後（5月25日）に組織から削除しましたが、それは侵害を知ってのことではありません。

持ち出されたのは、SaaS コンソールのコード・データサイエンスのスクリプトとモデル・自動化スクリプトと、どの IP をブロックリストに載せるかを決める「合意形成アルゴリズム」です。あわせて、利用者83名のメールアドレスと、2020年時点の潜在投資家51名の氏名・メールアドレス・出資の文脈が含まれていました。CrowdSec は利用者約15万のうち83名は 0.05% 未満だとしています。

本記録が重く見るのは、同社の説明が1日で変わった点です。9月17日の第一報は「クライアントデータ、ログイン情報・パスワード、氏名、組織名、その他いかなるものも漏えいしていない」（原文英語）とし、原因も「バックドア化された部品が私有コードを読めるAPI キーを盗んだ」と説明していました。翌18日の報告は、悪性の TanStack 版は自社コードから見つからなかったとして原因を退職者のアカウントに置き換え、第一報が否定していた投資家の氏名と利用者のメールアドレスの流出を認めています。

日本の組織は当事者ではありませんが、①汚染された OSS が開発者端末を経由して数か月後に別の形で発火すること、②退職者アカウントの残置がその受け皿になること、③初報を急いだ結果、否定した事実を翌日に認めることになったことの3点で先例になると判断し、公表・報道から確認できた範囲を、事実と評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

2026年5月11日に npm へ公開された汚染版 @tanstack/* を退職直後の従業員の端末が取得し、 インストール時の認証情報窃取コードが GitHub の OAuth トークンを持ち出した。11日後の 5月22日 05:52〜06:01 UTC、そのトークンで CrowdSec の私有リポジトリ約170個がコピーされ、 117日後の9月16日にオンラインのフォーラムへ公開された。基盤・データベースへの侵入や コードの改変は無かったとされる。流出コードに含まれていた AWS 認証情報は8月17日に試されたが、 権限が SNS の1トピックに限られていたため進んでいない。

    汚染された npm パッケージは開発者端末で止まらず、11日後に別の会社のリポジトリを開けた概観

    連鎖は次のとおりである。

    1. 2026年5月11日 19:20 UTC、42の @tanstack/* パッケージに計84の悪性版が npm へ公開される（CVE-2026-45321・CVSS 9.6）。インストール時に約2.3MB の難読化スクリプトが動き、AWS・GCP・Kubernetes・Vault・GitHub・npm・SSH の認証情報を集めて持ち出す
    2. 悪性版は 20〜26分で外部研究者に検知され、同日中にレジストリから消える。しかし、その間に取得した端末では既に認証情報が抜かれている
    3. 抜かれた中に、CrowdSec を退職したばかりの従業員の GitHub OAuth トークンがあった
    4. 5月22日 05:52〜06:01 UTC、そのトークンでカナダ・トロントからCrowdSec の私有リポジトリ約170個がダウンロードされる
    5. 9月16日 20:00 UTC、コードがオンラインのフォーラムに公開される。CrowdSec はここで初めて事態を知る

    CrowdSec の説明では、使われたのはコードの読み出しだけで、基盤やデータベースへのアクセスは無く、コードの改変も無かった。一方で、コピーから公開までの117日間、同社はこのコピーに気づいていない。

    退職者のアカウントが残っていたことが、供給網の汚染を自社のリポジトリにつなげた原因・手口

    技術的な起点は TanStack の汚染だが、それだけでは CrowdSec のリポジトリには届かない。届いたのは、退職した従業員の GitHub アカウントが組織に残されていたからである。CrowdSec は「本人が残作業を終えられるように」アクセスを残していたと説明している。

    残置の期間そのものは短い。コピーは5月22日、アカウントの削除は5月25日で、差は3日である。ただしこの削除は侵害を認識してのものではなく、引き継ぎ終了に伴う通常の処理だった。偶然、3日で閉じたというのが正確な読み方である（本記録の評価）。

    同社は、この従業員の他のアクセス権は退職時に削除済みだったとし、それがAWS 側で不審な動きが見られなかった理由だと説明している。削除されていなかったのはGitHub だけで、被害もそこに閉じた——権限の棚卸しが結果として被害範囲を決めている。

    なお同社は当時、開発者端末への EDR 導入を必須としていなかった。事後に、コードやシステムを扱う従業員の端末へ EDR（Aikido Security 製）を展開したとしている。

    出たのはコードだけではない——利用者83名のメールと、2020年の投資家51名の情報が混ざっていた被害規模・影響範囲

    公開されたアーカイブに含まれていたのは、次のとおり。

    • 私有コード: SaaS コンソール、データサイエンスのスクリプトとモデル、自動化スクリプト、そしてブロックリストの合意形成アルゴリズム
    • 利用者83名のメールアドレス（同社の利用者は約15万。0.05%未満）。データサイエンスチームが製品の使われ方を調べるために保持していたもの
    • 2020年時点の潜在投資家51名の氏名・メールアドレス・出資の文脈。同社は「公開される想定ではなかった2020年の仕組みに由来する」としている

    CrowdSec は、コードは4か月近く前のもので大きく変わっているとしている。また、アーカイブに含まれていた認証情報のうち使えるものは1つ——AWS のassertible-zapier-sns-sender だけで、これも SNS の1トピックへの publish に制限されていた。8月17日、IP 23.234.84.102 からこの認証情報で GetCallerIdentity・ListTopics を試す動きがあったが、それ以上は進んでいない。他のトークンは既にローテート済みか、インターネットからは使えないものだったとしている。

    ブロックリストの「閾値」が見えるようになったが、汚染には依然として大きな費用がいるとしている業務・事業への影響

    CrowdSec の製品の中核は、利用者が持ち寄った検知を突き合わせて悪性 IP を判定する合意形成アルゴリズムである。流出により、何件の検知でブロックリストに載るかという閾値が外部から見えるようになった。これはそれまで非公開だった。

    同社は、ブロックリストの汚染（無害な IP を載せさせる）は依然として現実的ではないとし、根拠として「アルゴリズムは数十の異なる自律システム（AS）にまたがる数十の検証済みエンジンからの数十件の目撃を要求する」と述べている。加えて、ネットワークの規模ゆえに統計的な異常は目立つこと、閾値は必要に応じて変更できることを挙げている。

    本記録の評価としては、この説明の当否は外部から検証できない。 攻撃費用が高いという主張の根拠はアルゴリズムの仕様そのものであり、その仕様が公開されたのが本件だからである。「変更できる」ことと「変更した」ことも別である。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    汚染された npm パッケージが、退職者のトークンを経て別会社の私有リポジトリに届いた経路
    layer 0 は TanStack のワークフローを踏み台にしたアクター。layer 1 は npm に公開された 汚染版と、それを取得した退職直後の従業員の端末。layer 2 は端末から抜かれた認証情報のうち、 実際に使われた GitHub の OAuth トークンと、残置されていたアカウント権限。 layer 3 はコピーされた約170の私有リポジトリ。layer 4 はそこに含まれていた個人情報・ アルゴリズムの閾値・AWS 認証情報と、9月16日の公開である。 同じ汚染からは Mistral AI・OpenAI にも波及したと報じられている（帰属は presumed）。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    初期侵入機会はあったが検知できず
    当時、開発者端末に EDR は導入されていなかった（同社が事後に導入したと述べている）。 npm の install スクリプトからの外向き通信は、端末側で検知しうる事象だった（本記録の評価）
    検知できた開発者端末に EDR を入れ、パッケージ導入時の子プロセス生成・外向き通信を監視する
    影響を限定できた依存の導入を CI の隔離環境に閉じ、開発者端末では ignore-scripts を既定にする
    影響を限定できた依存のバージョンを固定し、取得元のレジストリをプロキシ経由に限定する
    認証情報アクセス現実的な検知機会なし
    窃取データは Session/Oxen メッセンジャーのファイル送信網を使って持ち出されており、 攻撃者が管理する C2 ドメインが無い。宛先のブロックでは止められない
    影響を限定できた開発者端末に長命のトークンを置かず、短命の認証（OIDC・デバイス連動）に寄せる
    影響を限定できたGitHub の PAT・OAuth 連携アプリの棚卸しと有効期限の強制を行う
    収集機会はあったが検知できず
    **約9分で170リポジトリのクローンという速度と量は、通常の開発者の挙動とは明確に異なる。** ただし CrowdSec が自力で参照できたログにはトークンの痕跡が残っておらず、 事後の追跡は GitHub のサポートに依存した
    検知できた組織の監査ログで、短時間の大量クローン・異常な地理位置からのアクセスに警報を置く
    侵入を防げた退職時にアカウントを即時に組織から外す（引き継ぎのための残置をやめる）
    侵入を防げた私有リポジトリへのアクセスを IP 許可リスト・SSO 必須で絞る
    持ち出し現実的な検知機会なし
    外部での公開であり、被害組織側の統制では検知できない。実際、CrowdSec は 第三者からの連絡で知っている
    復旧を早められた自社名・自社の識別子を対象にした外部監視（リークサイト・フォーラム）を置く
    影響（暗号化・破壊・改ざん）検知した
    CrowdSec は事後の調査でこの試行を特定できている（IP・API 呼び出しまで把握）。 ただし8月17日の時点で警報として扱えていたかは示されていない
    影響を限定できたコードに残る認証情報の権限を最小に絞る（本件はこれが効いた）
    検知できた使われていない認証情報の呼び出しに警報を置く

    コードの公開を知った翌日（2026年9月17日）に第一報を出し、さらに翌日（9月18日）に 詳細な最終報告を出した部分的に機能本記録の作成者の評価である。速さそのものは評価できるが、第一報が 「氏名も組織名も何も漏えいしていない」と**否定の形で断定**し、翌日それを撤回したことで、 以後の説明の信頼が目減りしている。**確認できていない範囲は「確認中」と書けば足りた**
    最終報告では、露出した投資家51名・利用者83名の内訳、流出した AWS 認証情報の識別子と 権限、悪用試行の IP・API 呼び出し、合意形成アルゴリズムの閾値が見えるようになったことまで 踏み込んで説明した機能した本記録の作成者の評価である。とくに「使えた認証情報は1つで、権限は1トピックへの publish だけだった」という粒度は、他社が自社の該当性を測る材料になる。 一方で、**どの汚染パッケージがいつ端末に届いたかは示されておらず**、 同じ経路を踏んだかを他社が照合する手がかりは欠けている
    判明直後（9月16日・17日）に、流出コードに含まれていた認証情報をすべてローテートした機能した本記録の作成者の評価である。8月17日の試行が観測されていたことからも、 残っていた認証情報の無効化は妥当な優先順位だった
    CISO・経営層への示唆
    • 供給網の汚染は「踏んだ日」ではなく「踏んだ端末の権限が生きている間」効き続ける
      汚染版 npm がレジストリから消えたのは公開から約4時間半後だが、抜かれたトークンが 使われたのは11日後、その結果が外に出たのは4か月後である。 インシデントの終わりをパッケージの削除で数えると、実害の始まりを見落とす
      取るべき行動 供給網汚染の通知を受けたら「該当パッケージを消したか」ではなく 「その環境から到達できた認証情報をすべてローテートしたか」で完了を判定する。 ローテートの対象一覧（トークン・鍵・クラウド認証情報）を事前に用意しておく
    • 退職者アカウントの「引き継ぎのための残置」を、例外運用として明文化する
      本件で供給網の汚染と自社のリポジトリをつないだのは、この残置である。 期間はわずか数日だったが、その窓に当たっている
      取るべき行動 退職時のアクセス削除を即時とし、残置が要る場合は期限・対象リポジトリ・承認者を 記録する例外申請にする。残置中のアカウントは監視対象に上げる
    • 初報では「確認できていないこと」を否定形で断定しない
      CrowdSec の第一報は「氏名も組織名も何も漏えいしていない」としたが、翌日、 投資家51名の氏名と利用者83名のメールアドレスを認めている。 **訂正の対象になったのは事実ではなく、断定した姿勢のほうである**
      取るべき行動 公表文の型を用意し、「確認できた事実」「確認中の事項」「現時点で確認できていないこと」の 3区分で書く。否定形の断定は、確認の方法まで示せるときだけ使う
    • 自社のログだけで追えない侵害があることを前提に、外部への照会経路を用意する
      CrowdSec が参照できたログにはトークンの痕跡が無く、出所の特定は GitHub のサポートに 依存した。SaaS 上の資産では、監査ログの保持期間と粒度が調査の上限を決める
      取るべき行動 主要な SaaS について、監査ログの保持期間・取得できる項目・提供事業者への照会手順を 事前に確認する。必要なら上位プランや外部保管でログの保持を延ばす
    セキュリティ技術者への示唆
    • 開発者端末での依存導入を、素のまま実行させない
      汚染版のインストール時に約2.3MB の難読化スクリプトが動き、AWS・GCP・Kubernetes・ Vault・GitHub・npm・SSH の認証情報を集めて持ち出した。当時 CrowdSec の開発者端末に EDR は無かった
      取るべき行動 npm の install スクリプトを既定で無効化（ignore-scripts）し、必要なものだけ許可する。 依存の初回導入は隔離した環境で行い、開発者端末には EDR を入れる
    • 持ち出し先が「正規のメッセンジャー網」の場合、宛先ブロックは効かない
      本件の窃取データは Session/Oxen メッセンジャーのファイル送信網で持ち出されており、 攻撃者が管理する C2 ドメインが存在しない
      取るべき行動 検知の主軸を宛先ではなく挙動に置く（パッケージのインストール処理からの子プロセス生成、 ~/.ssh・~/.npmrc・クラウド認証情報ファイルの読み取り）。EDR のルールをこの観点で点検する
    • GitHub 組織の監査ログに「短時間の大量クローン」の警報を置く
      約9分間で約170の私有リポジトリがダウンロードされている。通常の開発者の挙動とは 速度も量も異なるが、検知されていない
      取るべき行動 組織の監査ログ（git.clone 等）を取り込み、単位時間あたりのクローン数・ 普段と異なる地理位置・退職者アカウントの活動に警報を置く
    • コードに残る認証情報は、消すのと同じくらい「権限を絞る」ことが効く
      流出したアーカイブの中で使えた認証情報は1つだけで、それも SNS の1トピックへの publish に制限されていた。8月17日の試行はそこで止まっている
      取るべき行動 シークレットスキャンで見つかった認証情報を消すだけでなく、 残さざるを得ないものは権限を単一の操作・単一の資源に絞る。 用途の広いキーを1つ置くより、狭いキーを複数置く
    • CI/CD のワークフローに fork からの実行経路を残さない（汚染側の教訓）
      TanStack 側の起点は pull_request_target が fork のコードを実行し、 GitHub Actions のキャッシュ汚染とランナーメモリからの OIDC トークン抽出で npm の公開権限が奪われたことだった
      取るべき行動 pull_request_target で untrusted なコードをチェックアウトしない。 キャッシュの読み書きを信頼境界で分け、id-token: write を与えるジョブを 公開処理だけに限定する

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    委託・第三者部品□ 2026年5月11日 19:20〜23:55 UTC に @tanstack/* を取得した環境があるその窓で取得した端末・CI は、AWS・GCP・Kubernetes・Vault・GitHub・npm・SSH の 認証情報が持ち出された前提で扱う必要がある。TanStack は日本国内でも採用例が多い
    認証・認可□ 退職者・異動者のアカウントを「引き継ぎのため」一時的に残す運用がある本件で供給網の汚染と自社リポジトリをつないだのはこの残置である。 残置期間が数日でも、その窓に当たれば同じ結果になる
    運用・監視□ 開発者端末に EDR を導入しておらず、依存導入時の挙動を監視していない汚染パッケージの実行は端末上で起きる。CrowdSec は当時これを必須としておらず、 事後に導入している
    運用・監視□ GitHub / GitLab の組織監査ログを取り込んでおらず、大量クローンの警報が無い約9分で170リポジトリという明確な異常が検知されず、判明までに117日かかっている
    データの保持□ 私有リポジトリに、個人情報（利用者・取引先・投資家）や認証情報が同居している本件で追加の被害を生んだのはコードそのものではなく、そこに混ざっていた 83件のメールアドレスと51名の投資家情報、そして AWS の認証情報である
    体制・契約□ インシデントの初報を、確認完了を待たずに公表する運用になっている第一報の否定的な断定が翌日に撤回され、説明の信頼が損なわれた。 「確認中」と書ける型を持っているかどうかで結果が変わる
