INC-2026-0179Codex のサンドボックス脱出2件

OpenAI のコーディングエージェント Codex に、サンドボックスの外でコマンドを実行できる欠陥が2つ見つかった——重いほうの「Heapjack」は、他人のリポジトリを Codex に開かせてコードについて質問しただけで、そのリポジトリの作者が利用者の端末でサンドボックス外のコマンドを実行できる。最も厳しい読み取り専用モードでも成立し、承認も画面表示も出ない。もう1つの「Overpatch」は Codex CLI の apply_patch が、パッチに書かれた宛先の親フォルダへ書き込み権限を広げる挙動を突く。研究者は2026年8月12日に報告し、OpenAI は8日以内に修正したが、CVE もセキュリティアドバイザリも出ていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年9月15日 最終更新: 2026年9月20日

セキュリティ企業 Accomplish の主席研究者 Oren Yomtov 氏は 2026年9月15日、OpenAI のコーディングエージェント Codex のサンドボックスを抜ける手法2つを公表しました。「Two ways out.（出口が2つ。うち1つは、パッチが承認も無しにディスクのどこへでも書けるようにする）」（原文英語）という書き出しです。

重いほうが Heapjack です。他人のリポジトリを Codex で開き、コードについて質問する——それだけで、そのリポジトリを書いた者が利用者の端末でサンドボックス外のコマンドを実行できます。研究者によれば、これは Codex の最も厳しい読み取り専用（read-only）モードでも成立し、承認を求める表示も画面への出力も出ません。

もう1つが Overpatch です。Codex CLI の workspace-write モードでは、エージェントはプロジェクトのフォルダ内にしか書き込めず、ホームディレクトリを狙うシェルコマンドは拒否されます。研究者は Codex 自身のパッチ適用ツール apply_patch を使ってそこへ書き込みました。このツールはパッチに書かれた各パスの親フォルダに対して書き込み権限を与えるため、パッチの中に /tmp を1つ混ぜておくと、ディスクの根（/）への書き込み権限が広がります。

報告は2026年8月12日、修正は8日以内でした（研究者の記述）。修正版はCodex Desktop ビルド 26.818.21641（Heapjack）と Codex CLI 0.149.0（Overpatch）です。本記録が2026年9月21日に確認したところ、Codex CLI 0.149.0 は 2026年8月20日に公開されており、その変更記録には apply_patch の権限拡大を防ぐ修正（#39614）と、シンボリックリンクの差し替えに対する堅牢化（#39659）が確かに含まれていました。

ただし OpenAI はこれをセキュリティ修正として公表していません。openai/codex のセキュリティアドバイザリは2026年9月21日時点で1件のみで、それは2025年9月の別件（CVE-2025-59532）です。本件に CVE は採番されておらず、0.149.0 の変更記録は241行の項目のうちの2行として、ほかの不具合修正と区別なく並んでいます。

日本の読者にとっての要点は、製品の欠陥そのものよりも運用のほうにあります。この2件は「エージェントに他人のコードを読ませる」という、いま日常的に行われている操作がそのまま端末の乗っ取りになりうることを示しました。更新は必須ですが、更新だけでは同じ形の次の欠陥は止まりません。

Codex はコマンドライン版とデスクトップ版があり、ほかのエージェントと同じく、モデルの操作をサンドボックスの中で実行する。その前提が2つの経路で崩れていた、というのが本件である。

Heapjack——信頼を分ける秘密が、信頼していない側と同じメモリに置かれていた原因・手口出典 [1] [2]

Heapjack が狙うのは node_repl という部品である。研究者の記述によれば、Codex Desktop が導入時に、共通設定ファイル ~/.codex/config.toml へ[mcp_servers.node_repl] のブロックを書き込む。

「Codex Desktop は導入時に、グローバルな ~/.codex/config.toml へ[mcp_servers.node_repl] のブロックを書き込む。同意を求める仕組みは無く、切るための設定も無い」（原文英語）

設定は共通ファイルに置かれるため、Codex CLI しか使っていない利用者も、一度も尋ねられないまま同じ道具を引き継ぐと研究者は述べている。

node_repl は1つの Node.js プロセスの中に、信頼される実行文脈（OpenAI 自身のコード）と信頼されない実行文脈（エージェントのコード）を持つ。信頼される側は、実行のたびに作られるランダムなトークンを示すことで自分が信頼側であることを証明する。

問題はここにある。

「Node のプロセスは1つ、V8 のアイソレートは1つ、ヒープは両方の文脈で共有されている。トークンはそのヒープに置かれた1つの文字列にすぎない」（原文英語）

非信頼側のコードは v8.getHeapSnapshot() でヒープの写しを取り、UUID の形をした文字列を片端から試す。判定は返ってくるエラーで付く。

「誤ったトークンには not authorized が返る。正しいトークンに誤った引数を添えると、本物の検証エラーが返る」（原文英語）

トークンを得た非信頼側は、信頼側が親プロセスと話すのと同じパイプに自分の要求を書き込む。親（サンドボックスの外にいるネイティブのプロセス）はトークンを検めて正当と判断し、要求どおりに動く。実証では macOS の open コマンドを使い、Codex のプロセスツリーの完全に外側でアプリケーションを起動してみせた。

同じ到達範囲は、任意の Unix ソケットにも及ぶ。研究者は明らかな標的としてDocker デーモンのソケットを挙げ、さらに共通設定ファイルを編集する道具にも手が届くと述べている。

Overpatch——パッチに `/tmp` を1行混ぜると、ディスクの根まで書き込み権限が広がった原因・手口出典 [1] [2] [3] [4] [5]

Overpatch は、公開されている Codex CLI 側の欠陥である。

workspace-write モードでは、エージェントはプロジェクトのフォルダ内にしか書き込めず、ホームディレクトリを狙うシェルコマンドは拒否される。研究者は Codex 自身のパッチ適用ツールapply_patch を使って、そこへ書き込んだ。

仕掛けは単純である。このツールはパッチに書かれた各パスの親フォルダに対して書き込み権限を与える。したがって、パッチの中に /tmp を名指しする変更を1つ混ぜると、その親、すなわちディスクの根（/）への書き込み権限が広がる。

実証のパッチは2つの変更からなる。

  1. /tmp を名指しするが、それ自体は何の役にも立たない変更
  2. シンボリックリンクを経由して、ホームディレクトリの .zshrc に1行を追記する変更

1 番目を取り除くと、2 番目の書き込みは拒否される。研究者の言葉では「その変更は失敗する。ディレクトリの上にファイルを書くことはできないからだ。これはパッチの中に、権限を広げるためだけに入っている」（原文英語）。

書き込みが通れば、開発者が次に開いたターミナルが、攻撃者の行をサンドボックスの外で実行する。

本記録が GitHub で確認したところ、Codex CLI 0.149.0（2026年8月20日公開）にはこの2つの側面に対応する修正が実際に入っている。

  • #39614「apply_patch が書き込み権限を広げるのを防ぐ」——「すでに書き込み可能なパッチ対象の親から権限を導出すると、意図した作業領域の外への書き込みを不必要に許してしまいうる」（原文英語）。修正は、現行のサンドボックス方針ですでに書き込み可能な対象については、親フォルダの権限を追加で導出しないというもの
  • #39659「サンドボックス外のパッチのファイル操作を堅牢にする」——「apply_patch のパスは検証のあとにシンボリックリンクへ置き換えられうるため、承認されたのとは別のファイルへ到達しうる」（原文英語）。修正は、必要なサンドボックスが迂回される場面ではシンボリックリンクの追跡を止めるというもの

ただし、この対応づけは本記録の作成者による推定である。 研究者も OpenAI も、Overpatch の修正がこの2つのプルリクエストであるとは明示していない（discrepancies を参照）。

2件に共通するのは「強制する側が、強制される側の内側にいた」こと評価・解釈出典 [1] [2]

研究者は2件の共通点をこう書いている。

「強制を行う当のものが、強制される当のものの内側に座っていた」（原文英語）

内訳は次のとおりである。

  • apply_patch は、攻撃者が渡した入力から自分の権限を計算していた
  • node_repl は、信頼と非信頼を分ける秘密を、非信頼側と同じメモリに置いていた

いずれの場合も、サンドボックスは内側から「これを通せ」と言われて通していた。

この型の欠陥は新しくない。 BleepingComputer によれば、2026年7月にPillar Security の研究者が Cursor・Codex・Gemini CLI・Google Antigravity を横断して同じ考え方を実証している——サンドボックスの中に留まったエージェントがファイルを書き、サンドボックスの外にいる信頼されたツールが、あとでそれを実行するという形である。

研究者の投稿に対する反応も引かれている。「V8 の文脈が隔てるのはグローバル変数であってメモリではない。だからあのサンドボックスは、ヒープが同意した覚えのない約束にすぎなかった」（原文英語）。別の者は、信頼の境界を「間仕切り（a room divider）」と呼んだ。

本記録としての評価を1つだけ書く。 エージェント製品の「モード」表示——読み取り専用、作業領域のみ書き込み可——は、利用者が自分のリスクを見積もる唯一の手がかりとして使われている。Heapjack が読み取り専用モードで成立したことは、この手がかりが、現時点では約束として扱えないことを意味する。更新は必要だが、更新は「次の同型の欠陥」までの距離を変えない。運用側で持つべき前提は「エージェントに読ませたコードは、実行させたコードと同じ」である。

CISO・経営層への示唆
  • エージェント製品の脆弱性は CVE とアドバイザリの外側で流通していると前提を置く
    本件は CVE が採番されず、ベンダーのアドバイザリも出ていない。修正は 241行のリリースノートの2行として届いた。同じ形は本DBの Plugin4Shell（INC-2026-0172）でも 起きている。**脆弱性管理の入口を CVE とアドバイザリに置いている限り、この層は入ってこない**
    取るべき行動 利用中のAIエージェント製品について、CVE 以外の入手経路を決める—— リリースノートの購読、ベンダーの GitHub リポジトリの watch、研究者の公表の定点観測。 「誰が見るか」を人に割り当て、月1回の棚卸しに入れる
  • 「読み取り専用モードだから安全」という説明を、リスク評価の根拠に使わない
    Heapjack は**最も厳しい読み取り専用モードで成立した**。 モード表示は利用者がリスクを見積もる唯一の手がかりになっているが、 本件はそれが保証ではないことを示した
    取るべき行動 エージェント利用の社内規程で「モードによる安全性」を根拠にしている箇所を洗い出し、 **端末の隔離・権限の分離といった外側の対策に置き換える**。 モードは多層防御の1層として扱い、単独の根拠にしない
  • 外部のコードをエージェントに読ませる作業を、業務として定義して場所を決める
    本件の入口は「他人のリポジトリを開いて質問する」という、いま日常的に行われている操作である。 OSS の調査、取引先のコードレビュー、応募者の課題確認—— **誰がどの端末でやっているかを把握していない組織が多い**
    取るべき行動 外部コードをエージェントに読ませる作業を洗い出し、 本番の認証情報を持たない使い捨ての環境（別ユーザー・仮想マシン・コンテナ）で行う運用に寄せる。 費用と手間が見合わないなら、その作業を許可制にする
  • 「直っているが知らされていない」期間があることを、対応計画の前提に織り込む
    報告から修正まで8日、研究者の公表まではさらに26日あった。 この間、利用組織は判断の材料を持たない。**ベンダーの修正の速さと、 利用者が知る速さは別の指標である**
    取るべき行動 AIエージェント製品については「最新版を当て続ける」を既定方針にし、 個別の脆弱性情報を待って判断する運用から外す。 更新の遅延を許容する例外は、理由と期限を記録して管理する
セキュリティ技術者への示唆
  • Codex CLI は 0.149.0 以降、Codex Desktop は 26.818.21641 以降へ更新する
    これが研究者の示した唯一の直接的な対策である。Codex CLI 0.149.0 は 2026年8月20日に公開されており、`apply_patch` の権限拡大を防ぐ修正（#39614）と シンボリックリンクの差し替えへの堅牢化（#39659）を含む

  • `~/.codex/config.toml` の `[mcp_servers.node_repl]` を、端末ごとに確認する
    この記載は Codex Desktop が導入時に、同意を求めずに書き込む。 共通ファイルであるため、**Codex CLI しか使っていないつもりの利用者も同じ道具を引き継ぐ**
    取るべき行動 資産管理の一環として、Codex を入れている端末の `~/.codex/config.toml` の中身を確認する。 設定の削除で回避できるかは公表されていないため、**削除を対策として案内しない**

    実証は macOS の `open` を使い、launchd 経由で Codex のプロセスツリーの完全に外側で アプリケーションを起動した。**親子関係を頼りにした検知では追えない**
    取るべき行動 開発者端末のEDRで、エージェントの実行中に launchd（macOS）・systemd（Linux）経由で 起動されるプロセスを可視化できるか確認する。取れないなら、何が取れるかを先に把握する
  • シェルの起動ファイルの変更を、書いたプロセスごと記録する
    Overpatch の最終段は `.zshrc` への1行の追記に集約される。 ファイルの変更だけを見ると開発者自身の編集と区別がつかない
    取るべき行動 `.zshrc`・`.bashrc`・`.profile` の変更を、**書き込んだプロセス名と親プロセス**まで 含めて記録する。検知ルールを作る前に、平常時にどれだけ書き換わるかを1週間測る

    研究者は、トークンを得たあとの到達先として**任意の Unix ソケット**を挙げ、 Docker デーモンのソケットを「明らかな標的」と名指ししている。 ここに届けば、事実上そのホストの root と同等である
    取るべき行動 開発者端末で Docker デーモンのソケットに触れられるユーザー・プロセスを確認する。 エージェントを走らせるユーザーがそこに含まれているなら、分離を検討する

運用・監視□ 開発者が OpenAI の Codex（CLI または Desktop）を業務で使っている本件の影響範囲そのもの。Desktop を入れた端末は、同意なく共通設定へ書き込まれた `node_repl` を持ち、CLI のみの利用者もそれを引き継ぐ
運用・監視□ 自社以外のリポジトリ（OSS・取引先・応募者の課題）をエージェントに読ませる作業があるHeapjack の入口はこの操作そのものである。開いて質問しただけで、 書いた者に端末のコマンド実行を与えうる
システム構成□ エージェントを走らせる端末が、本番の認証情報・Docker デーモンのソケット・社内ネットワークに届く脱出が成立したときの到達範囲を決めるのはここである。 研究者は Docker デーモンのソケットを明らかな標的として挙げている
体制・契約□ 脆弱性管理の入口が CVE とベンダーのアドバイザリになっている本件には CVE もアドバイザリも無い。この入口だけに頼っていると、 エージェント製品の脆弱性は**構造的に視界へ入らない**
認証・認可□ AIエージェントを、利用者本人と同じ権限で動かしているサンドボックスが破れたとき、攻撃者が得るのは**そのエージェントを動かしている利用者の権限**である。 開発者が管理者権限や広い本番権限を持っているほど、脱出1回あたりの損失が大きくなる
運用・監視□ 開発者端末で、シェルの起動ファイルの変更やプロセスツリー外の起動を記録していないOverpatch の最終段（.zshrc への追記）と Heapjack の最終段（プロセスツリー外の起動）は、 どちらもこの2つの記録があれば見える。無ければ、成立しても何も残らない
