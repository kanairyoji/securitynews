INC-2026-0180偽 npm「indexed-btree」10本

正規ライブラリ sorted-btree を装った npm パッケージ「indexed-btree」など10本が、インストール時の仕掛けを一切持たずに配られた——悪性のローダーはライブラリ本来のメソッドの中に隠され、アプリが特定のキーでそれを呼んだ瞬間に動く。GitHub が2026年6月に入れた「インストール用スクリプトを既定で止める」措置は、インストール時に何も起こらないため発火しない。第2段は Ethereum のテストネット上のスマートコントラクトから取り、収集した端末情報は Slack と Telegram へ送る。npm は2026年9月3日に10本を一斉に削除したが、本記録が9月21日に確認した時点でも削除後の17日間で1,900万回引かれており、偽装用の GitHub リポジトリ（上流の開発履歴をまるごと写して著者名を1人に書き換えたもの）は今も残っている

脅威・攻撃キャンペーン続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因
初報: 2026年9月17日 最終更新: 2026年9月21日

セキュリティ企業 Checkmarx（研究部門 Checkmarx Zero）は 2026年9月17日、正規ライブラリ sorted-btree を装う npm パッケージ indexed-btree を中心とする攻撃を公表しました。BleepingComputer が9月20日に報じ、日本の読者にも届く範囲に入りました。

手口の要点は1つです。インストール時には何も起こりません。

「供給網の領域でこれまで見てきた一般的な攻撃と違い、このパッケージはインストール前・インストール後のスクリプトにまったく依存していない。代わりに、すべてがアプリケーションのコードから実行時に動く」（原文英語）

悪性のローダーは、ライブラリ本来のメソッド BTree.prototype.set—— Checkmarx の言葉では「誰もが絶えず呼ぶ主要な関数」（原文英語）——の中に置かれ、キーの値が 100 のときに別プロセスを起こして難読化された第1段を動かします。インストールは正常に見え、GitHub が2026年6月に導入した npm v12 の承認機構は発火しません。

動き出した後は、端末の情報（OS・アーキテクチャ・ホスト名・CPU・メモリ・稼働時間）を攻撃者の Slack と Telegram へ送り、Ethereum のテストネット（Sepolia）上のスマートコントラクトを指令の取得先として繰り返し参照します。攻撃を終えるときは、自分のファイルと、メソッドに仕込んだ起動部分を消す機能も持ちます。

本記録が 2026年9月21日に npm と GitHub の公開情報を確認したところ、次のことが分かりました。

  • 悪性版が置かれていたのは 2026年6月18日から9月3日までの77日間で、npm は9月3日 10時12分〜13分（UTC）のおよそ40秒のうちに10本すべてを削除している（Checkmarx の公表より2週間前）
  • それでも 削除後の17日間（9月4日〜20日）に10本は合計1,900万回以上引かれている。偽物である indexed-btree 単体の取得回数は、本物の sorted-btree の約3倍にあたる
  • 偽装用の GitHub リポジトリは、上流の本物のリポジトリの開発履歴（2018年から106件）をまるごと写し、著者名を作りたてのアカウント1つに書き換えたものだった。そのアカウントとリポジトリは、削除から18日たった9月21日もまだ残っている

日本の読者にとっての含意は、点検の当て方が変わることです。「インストール時に走るスクリプトを止める」対策は効いています。効いているからこそ、攻撃はインストールの外へ出ました。 取得したパッケージの一覧を見るだけでは、この形は見つかりません。

    インストールでは何も起きない。アプリがそのメソッドを呼んだ瞬間に動く概観出典 [1] [2]

    Checkmarx が公表した事実は次のとおりである。

    • indexed-btree は、正規のライブラリ sorted-btree を装った npm パッケージである
    • 悪性のローダーは BTree.prototype.set——Checkmarx の言葉で「誰もが絶えず呼ぶ主要な関数」（原文英語）——の中に隠されている
    • 起動の条件は キーの値が 100 のときで、切り離した Node.js のプロセスを起こして難読化された第1段（sharedLoad.min.js）を動かす
    • したがって インストールは正常に見え、npm v12 の承認機構は1つも発火しない
    • Checkmarx はこれを「標準的なテイント解析の道具と、ほとんどの静的走査をすり抜ける、よく作り込まれたやり方」（原文英語）と評している

    公表の書き出しはこうである。

    「indexed-btree は、正規の sorted-btree パッケージ——ありふれたB木・索引の道具——を装った悪性の npm パッケージである。供給網の領域でこれまで見てきた一般的な攻撃と違い、このパッケージはインストール前・インストール後のスクリプトにまったく依存していない。代わりに、すべてがアプリケーションのコードから実行時に動く」（原文英語）

    本件の要点は、防御が効かなかったことではない。効いたので、攻撃側が場所を移したことである。

    2026年6月に入った「インストール用スクリプトの停止」を、迂回ではなく回避している原因・手口出典 [1] [2] [5]

    GitHub は2026年6月、npm に一連の対策を入れた。BleepingComputer の整理によれば、中心は次の2つである。

    • preinstall・install・postinstall といった依存関係のライフサイクル用スクリプトを、明示的に承認しない限り止める
    • Git のリポジトリや遠隔のURLから、許可なく依存関係を自動で取ってこない

    indexed-btree は、この1つ目を破っていない。使っていないだけである。 インストール時に動くものが無ければ、止める仕組みも承認を求める仕組みも働かない。

    Checkmarx はこれを、自分たちの以前の予測が当たった形だとしている——「npm がライフサイクル用スクリプトを止めれば、攻撃側の手口は移るだろう」（原文英語）。

    同じ日のニュースに、反対側の実例も並んでいた。 CrowdStrike が同じ2026年9月20日に公表した PhantomRaven は、依存関係を npm の参照ではなく HTTP の URL で指定し、インストール時に攻撃者のインフラから本体を取ってきて preinstall を動かす。こちらは npm v12 の承認機構に実際に止められている。

    つまり、2026年6月の措置は効いている。効いている範囲が、インストールの時間帯に限られているというだけである。本記録としては、ここが本件から取り出せる最も実務的な点だと考える。

    動き出したあとは、端末情報を SNS へ送り、指令はブロックチェーンから取る原因・手口出典 [1] [2]

    第1段が動いたあとの流れは、Checkmarx の分析によれば次のとおりである。

    1. 端末の指紋を取る——OS・アーキテクチャ・ホスト名・CPU・メモリ・稼働時間
    2. 攻撃者の Slack のチャンネルと Telegram のチャットへ送る。いずれも接続情報はコードに直接書き込まれている（その値は本記録には載せない）
    3. 指令は Ethereum のテストネット（Sepolia）上のスマートコントラクトから取る。Checkmarx は「平のドメインに要求を出す代わりに、契約が公開している取得・設定の関数を繰り返し参照する」（原文英語）と説明している
    4. マルウェアは自分で X25519 の鍵の組を作り、コードに書き込まれた公開鍵との間で共有の秘密を計算し、そこから導いた AES の鍵で、契約に格納された第2段を復号する
    5. 攻撃を終えるときは、自分のファイルと、メソッドに仕込んだ起動部分を消す

    指令の取得先をブロックチェーンに置く形は、本DBでも記録している（[INC-2026-0025] npm ワーム ChainDrop）。遮断すべき宛先が、公開のインフラの中に紛れるという点で、通信の遮断による対処を難しくする。

    5 の自己削除は、事後の調査に直接効く。第2段が動いた環境では、あとからパッケージの中身を見ても起動部分が残っていない可能性がある。「今のファイルを見て異常が無い」ことは、動かなかったことの証明にならない。（この含意は本記録の判断である。Checkmarx は機能の存在のみを述べている。）

    第2段の内容が公表されていないため、影響の段階を評価する材料が無い
    影響を限定できた　Checkmarx・BleepingComputer の推奨。第2段が不明である以上、 「何を取られたか」を特定してから動く方針は取れない

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • 供給網の対策を「インストール時」に置いている限り、攻撃は実行時へ移ると想定する
      2026年6月の npm の措置は実際に効いている（同日公表の PhantomRaven はこれに阻まれた）。 効いたからこそ、本件はインストールの外へ出た。 **防御の位置が公表されると、攻撃はその外側へ動く**
      取るべき行動 自社の供給網対策が、依存関係の**取得時点**だけを見ていないか確認する。 実行時の挙動（子プロセスの生成・外向き通信）を取れているかを、 本番と CI のそれぞれについて答えられるようにする
    • 「広く使われている」ことを安全の根拠にしない
      本件では、**偽物の取得回数が本物の約3倍**だった。 取得回数は自動化された取得・鏡・攻撃者自身の操作を含み、利用者の信頼を表さない。 GitHub 上の開発の歴史も、上流から写して作れる（本記録が確認した）
      取るべき行動 依存関係の採否の基準から「ダウンロード数」「星の数」「コミットの多さ」を外すか、 補助的な材料に格下げする。代わりに**公開からの経過時間**と **リポジトリの作成日と履歴の整合**を見る
    • 該当したときの手順を、原因が分からない段階で動ける形にしておく
      本件では第2段の内容が公表されていない。 「何を取られたか」を特定してから対応する方針では**いつまでも動けない**。 推奨されているのは「秘密情報をすべて更新し、環境を作り直す」である
      取るべき行動 開発環境・CI の秘密情報の一覧と、更新にかかる時間・停止の影響を先に把握する。 「全部更新する」という判断を、誰がどの条件で下すかを決めておく
    • 削除されたことは、自社が無事であることを意味しない
      npm は Checkmarx の公表より**2週間早い9月3日**に削除している。 それでも削除後17日間で1,900万回引かれており、 **依存関係の定義にこの名前を残したままの環境が大量にある**。 自社がそこに含まれるかは、レジストリ側の対応では分からない
      取るべき行動 「レジストリが消したから終わり」ではなく、自社のロックファイル・ビルド記録に対して 名前の探索を実施する。実施した日付と範囲を記録に残す
    セキュリティ技術者への示唆
    • 10本の名前を、推移的な依存まで含めて探す
      直接の依存として書いていなくても、別のパッケージが依存していれば入る。 本件の8本は2026年7月24日に一斉公開されており、 **7月下旬以降に作られたロックファイルが対象になる**
      取るべき行動 `npm ls <名前>` や依存ツリーの出力で10本を探す。 併せて、過去のビルド記録（CI のログ）でも取得の有無を確認する。 該当したら秘密情報を更新し、環境を作り直す
    • 取得の失敗を、異常として拾えるようにする
      削除後も毎日20万〜70万回の取得が続いている。 これらの環境では、取得が失敗しているか、中身の無い置き換え版が入っている。 **ビルドの失敗を「たまに落ちる」で流している組織では、これが合図として使われない**
      取るべき行動 依存関係の取得が失敗したときのログを残し、パッケージ名まで含めて検索できるようにする。 「前は通っていた依存関係が落ちるようになった」という事象を拾う
    • Node.js のアプリケーションからの子プロセスの生成を記録する
      第1段は切り離したプロセスを起こして動く。 ライブラリが実行時に別プロセスを起こす必要は通常なく、 **観測できれば異常と判定しやすい**
      取るべき行動 本番と CI の Node.js プロセスについて、子プロセスの生成を記録できるか確認する。 取れるなら、平常時にどれだけ発生するかを1週間測ってから検知の条件を決める
    • ビルド環境からの外向き通信の宛先を把握する
      第1段の送出先は Slack と Telegram、指令の取得先はブロックチェーンの接続業者である。 **どちらも「悪性ドメインの一覧」では止まらない。** 止められるとすれば、送信元がビルド環境であることを条件にした許可制である
      取るべき行動 CI の外向き通信を一定期間記録し、実際に必要な宛先を列挙する。 その一覧を許可の基準にできるかを検討する（まず記録から始める）
    • リポジトリの作成日と、開発履歴の最古の日付を突き合わせる
      本件の偽装用リポジトリは**2026年6月18日に作られたのに、2018年7月24日からの 変更が106件入っており、そのすべてが同じ1アカウントの名前**だった。 上流の履歴を写して著者名を書き換えたものである
      取るべき行動 新しい依存関係を採用するとき、リポジトリの作成日・変更の最古の日付・ 著者の数を確認する。3つが食い違うものは採用を保留する

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    委託・第三者部品□ JavaScript／TypeScript のアプリケーションで npm の依存関係を使っている本件の影響範囲そのもの。10本はB木・索引・キャッシュ・順位付けを装っており、 サーバ側で順序付きのキー値データを扱う用途に紛れ込む
    委託・第三者部品□ 依存関係の安全性の判断を、インストール時の走査や承認機構に任せている本件はインストール時に何もしないため、この層では一切引っかからない。 **効かない対策に頼っていることに気づけない**のが最大の危険である
    運用・監視□ 本番・CI で、プロセスの生成や外向き通信を記録していない実行時に動く攻撃を捉えられる観測点は、事実上この2つしかない。 記録が無ければ、動いたかどうかを事後にも判定できない
    委託・第三者部品□ 新しく公開されたパッケージ・新しい版を、待機期間なしに取り込んでいる本件の悪性版は公開から77日以内にすべて削除された。 数週間の待機があれば、取り込む前に削除されていた可能性が高い
    体制・契約□ 依存関係の採否を、ダウンロード数・星の数・コミット数で判断している偽物の取得回数が本物の約3倍で、開発履歴は上流の写しだった。 **この3つはいずれも攻撃者が作れる**
    データの保持□ 開発環境・CI に、有効期間の長い認証情報を置いている第2段の内容が公表されていない以上、該当した環境では 「秘密情報がすべて取られた前提」で動くことになる。 長期の認証情報が多いほど、そのときの更新の負担と影響が大きくなる
