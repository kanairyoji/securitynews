INC-2026-0181dforge-mcp が来歴証明つき悪性版

MCP サーバの npm パッケージ「@dforge-core/dforge-mcp」の悪性版 0.2.21 が、GitHub Actions の OIDC 信頼済み公開で、正規の来歴証明（プロベナンス）つきのまま配られた——攻撃者はリポジトリへ push できる開発者アカウントを使い、「決して自動では動かない」と注記されていたリリース用ワークフローに main への push で動く3行を足して、手作業の承認なしに公開できる形へ書き換えた。ローダー「GHAPPIER」はインストール時ではなく MCP サーバの起動時に動く。悪性版は35分38秒のあいだ最新版で、保守者は約22分後にワークフローを元に戻した。CloudSEK は同じローダーを65リポジトリ・22アカウントで見つけ、別の検体が北朝鮮系とされる PolinRider と一致したとするが、帰属は自ら確認できていない

委託先・再委託先起因で委託元多数に波及脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備
初報: 2026年9月20日 最終更新: 2026年9月22日

インドのセキュリティ企業 CloudSEK は 2026年9月20日、MCP サーバの npm パッケージ @dforge-core/dforge-mcp に悪性版が公開されていた件を分析し、そこに載っていた未報告のローダーを GHAPPIER と名付けて公表しました。Infosecurity Magazine が9月21日に報じています。

本件の要点は、悪性版に正規の来歴証明（プロベナンス）が付いていたことです。

「来歴証明が保証するのは、成果物がどこで作られたかであって、ソースが正直だったかではない」（CloudSEK・原文英語）

本記録が2026年9月22日に npm レジストリと GitHub の公開記録を照会すると、CloudSEK の説明は分単位で裏づけられました（時刻はいずれも協定世界時）。

  • 9月9日 16時25分、保守者とは別の、リポジトリへ push できる開発者アカウントが、リリース用ワークフローに「main への push で起動する」3行を足した。そのファイルの冒頭には「決して自動では起動しない。公開は常に意図したものになる」（原文英語）と書かれていた
  • 14分後の16時39分、同じアカウントがワークフローを書き換え、push のたびに人手を介さず公開する形にした
  • 16時44分に 0.2.20（壊れていて導入に失敗する版）、17時19分に 0.2.21（ローダーを載せた版）が公開された
  • 17時42分、保守者がローダーのファイル（skills/indexe.cjs・3,508行）を消し、ワークフローを手動公開に戻した。17時55分に 0.2.22 が公開され、0.2.21 が最新版だったのは 35分38秒だった
  • 0.2.20 と 0.2.21 は、9月22日時点でレジストリから消えている。OSV にも GitHub の脆弱性データベースにも、この件の勧告は無い

日本の読者にとっての含意は、来歴証明の検証を「安全の証明」として扱わないことです。 npm audit signatures はこの版を通します。守るべきは証明ではなく、リリース用ワークフローの起動条件そのものでした。

  • 最初の悪性版 0.2.20 は壊れていて導入に失敗し、次の 0.2.21 がローダーを載せて35分38秒のあいだ最新版だった

「来歴証明が保証するのは、成果物がどこで作られたかであって、ソースが正直だったかではない。レジストリはリポジトリの CI の身元を信頼するので、push の権限がそのまま公開の権限だった」（原文英語）

本DBは同じ論点の先例を記録している（[INC-2026-0063]）。あちらは第三者のコメント1行で公開ワークフローが起動した事案で、本件はワークフローの起動条件そのものを書き換えた事案である。どちらも、証明は正しく、証明の対象が攻撃者の手の内にあった。

「決して自動では起動しない。悪い版の番号は npm に載った瞬間に恒久化する（72時間の取り消し猶予は別として）ので、公開は常に意図したものになる」（原文英語）

保守者は危険を正しく理解しており、手動起動だけに絞っていた。 しかしその制約はワークフローの定義の中にあり、定義を書き換えられる者は制約も外せた。push できるアカウントが1つ奪われれば、手動起動という歯止めは3行で消える。

ローダーを入れたファイル名は indexe.cjs——既存の index.cjs に1文字足した名前である。CloudSEK によれば、本体は99KB のファイルの 3,320行目の1行だった。

インストールでは動かず、MCP サーバの起動で動く原因・手口出典 [1] [4]

CloudSEK によれば、ローダーはパッケージの導入時ではなく、MCP サーバが起動したときに動く。0.2.21 を取得しても MCP サーバを起動しなかった環境では、ローダーは動いていない。

その先は 4段の連鎖で、最後の段は汎用の遠隔シェルであり、動いた瞬間に自分をディスクから消す。別の被害リポジトリで見つかった第2の検体は、約0.20米ドルの空の Ethereum 取引から設定を読むため、停止させるドメインも差し押さえるホストも無い。

MCP サーバは AI エージェントの道具として、開発者の端末で、開発者の権限のまま動くことが多い。インストール時の承認機構（本DB [INC-2026-0180] で論じた npm の措置）はここでも発火しない。「起動したら動く」形は、インストール時の防御の外側にある。（この位置づけは本記録の判断である。）

同じローダーが65リポジトリに、帰属は確定していない帰属出典 [1] [4]

CloudSEK は GHAPPIER を少なくとも65の公開リポジトリ・73ファイル・22アカウントで見つけた。別の被害者のリポジトリにあった第2の検体は、OpenSourceMalware が2026年3月から追跡しているPolinRider と完全に一致した。

PolinRider は、ほかの研究者が北朝鮮に帰属させている。CloudSEK は「自分たちが行えた独立の確認1件では、それを裏づけられなかった」（原文英語）と明記している。本記録も帰属を置かない。

CloudSEK は、PolinRider が記録上行っている認証情報の収集が、保守者側のアカウントへ入った最もありうる経路だとしている。開発者の端末の感染が、別の開発者のパッケージの公開権に化けるという連鎖である。

  • 保守者による利用者向けの告知も見つからない
  • CloudSEK によれば、取り下げから5日後も連鎖の各段が応答していた

版が消えると、利用者は「自分の環境に 0.2.21 が入ったか」をレジストリでは確かめられない。手がかりは自分のロックファイルとビルドの記録だけになる。 CloudSEK が「0.2.21 を固定したロックファイルは、それ自体を侵害の指標として扱え」（原文英語）と勧めるのはこのためである。

今日できる点検対策・注意喚起出典 [1] [4]

CloudSEK の推奨は次のとおりである。

  1. 0.2.22 以降に固定する
  2. 0.2.21 を固定したロックファイルを、それ自体で侵害の指標として扱う
  3. 最終段の本体（自己削除する）ではなく、連鎖が残す痕跡を探す
  4. 報告書に挙げられた接続先（ソケットの端点1つと配布元のホスト名2つ）を遮断する
  5. リリース用ワークフローの起動条件（トリガ）の変更に警報を付ける——本件では、公開できる状態になる14分前にこの変更が入っていた

本記録として足すのは、自社がパッケージを公開する側である場合の点検である。

  • リリース用ワークフローの定義ファイルを、コード所有者の承認なしに変更できないようにする
  • 信頼済み公開の設定で、公開を許すワークフローと環境（承認者つき）を絞る
  • push できるアカウントの一覧を棚卸しし、公開権と同じ重さで扱う

  • 来歴証明や署名の検証を「安全の証明」として報告しない
    本件の悪性版は正規の来歴証明を持ち、`npm audit signatures` を通った。 証明は「どこで作られたか」を保証するだけで、ソースが正直かは保証しない。 本DBは同じ形を2度記録している（INC-2026-0063）
    取るべき行動 供給網対策の報告で「署名・来歴を検証している」を成果として挙げている場合、 それが何を保証し何を保証しないかを併記させる。検証の導入を理由に、待機期間や差分確認を省かない
  • 自社が OSS やパッケージを公開しているなら、「push できる者」を「公開できる者」と同じ重さで管理する
    信頼済み公開は長期の公開トークンを無くしたが、公開の権限をリポジトリの CI の身元へ移した。 本件では push できるアカウント1つで、手動起動という歯止めが3行で外れた
    取るべき行動 自社が公開する各パッケージについて、push 権を持つアカウントの一覧と、公開までに人の承認が 入るかどうかを棚卸しする。承認が入らないものから順に、承認者つきの環境を設定する
  • 開発者の端末の感染を、自社の製品や公開物への入口として扱う
    CloudSEK は、感染した開発者の端末からキャッシュされた git の認証情報が取られた可能性を挙げ、 PolinRider の認証情報収集を最もありうる経路としている。端末1台の感染が、別の開発者の パッケージの公開権に化ける
    取るべき行動 開発者端末の侵害を想定した対応手順に、その開発者が持つリポジトリ・公開権限の即時の失効を含める。 失効の対象の一覧を、平時から作っておく
  • 取り下げられた悪性版は、レジストリでは追えなくなる前提で備える
