INC-2026-0182Red Heron が N-day を連続悪用

中国語話者とみられる攻撃者「Red Heron」が、公開された脆弱性を数日から数週間で次々と武器化し、自前ホスティングの開発基盤と境界機器を渡り歩いた——Acronis によれば、Gitea の遠隔コード実行（CVE-2026-60004）の修正版公開の2日後に公開 PoC を改造し始め、翌日には7か国1,386台を走査、台湾の産業オートメーション企業から数百のリポジトリ（SCADA/HMI の道具を含む）を持ち出し、別の台湾の環境では Proxmox の3ノード全体の root 権限に達した。同じ攻撃者か近い関係にあると GreyNoise がみる主体は、2026年6月から9月に UniFi OS・FlowiseAI・WordPress・Linux カーネル・Gitea・Nuclio・Zyxel GS1900・SENAITE・Proxmox VE を順に狙い、WordPress では29か国49組織（日本2件を含む）に侵入、Zyxel GS1900 では48か国996台から設定と認証情報を抜いた（うち564台は出荷時のままの認証情報）。CISA は9月21日に GS1900 の脆弱性を KEV に収載した

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ日本に波及した海外事案既知の脆弱性の悪用脆弱性の放置設定不備
初報: 2026年9月13日 最終更新: 2026年9月22日

シンガポールのセキュリティ企業 Acronis（研究部門 TRU）は 2026年9月13日、中国語話者とみられる攻撃者 Red Heron が Gitea の遠隔コード実行の脆弱性CVE-2026-60004 を使って多国籍の侵入を行ったと公表しました。2026年9月21日には、脅威観測の GreyNoise が、同じか近い関係にある主体が6月以降に少なくとも10種類の製品の脆弱性を順に悪用していたと公表し、同じ日に米 CISA が、そのうちの Zyxel GS1900 スイッチの脆弱性（CVE-2026-7273）を悪用が確認された脆弱性（KEV）に加えました。台湾の iThome が9月22日にこの2つを台湾の被害に焦点を当てて報じています。

事実として書けることは次のとおりです。

  • Gitea は 7月27日に修正版 1.27.1 を出した。Red Heron は 7月29日に公開の PoC を複製して改造を始め、7月30日には7か国 1,386台を走査し終えていた（Acronis）
  • 台湾の産業オートメーション企業1社から 数百のリポジトリ——監視製品・産業制御環境で使う SCADA/HMI の道具・IoT 連携・社内業務アプリ——が持ち出された（Acronis）
  • 別の台湾の環境では、Synology NAS 上の Gitea から入り、Proxmox の root 権限を得て3ノードすべてで仮想マシンの丸ごとの控え（バックアップ）を起動した（Acronis）
  • WordPress の連鎖した脆弱性で 29か国49組織に侵入し、うち1つの西側の政府組織からは18,000件超の記録を持ち出した。日本の被害は2件と表に載っている（GreyNoise）
  • Zyxel GS1900 では 48か国996台から設定・認証情報（ハッシュ）・ネットワーク情報を抜いた。564台は出荷時のままの認証情報だった（GreyNoise）

日本の読者にとっての含意は、「修正版が出てから当てるまで」の猶予がもう数日しか無いということです。 本件の攻撃者は PoC を貼り合わせる段階で何度も打ち間違えており、高度な技術を持つ集団には見えません。それでも、修正版の公開から走査の完了まで3日でした。

関係した組織

Acronis（Acronis Threat Research Unit）報告したベンダー確認済

関係定常の脅威探索で Linux 用の埋め込み型マルウェア JITTERLY を見つけ（8月4日）、 それを辿って攻撃者の認証なしで公開されていた中継サーバを発見した。 2026年9月13日に分析を公表した

影響中継サーバに残っていた操作履歴・標的一覧・盗んだリポジトリ・マルウェアから 攻撃の全体を再構成した。帰属は「中国に結びつく文脈で活動している」と **中程度の確度**で評価し、既知のグループとの結びつきは「十分な証拠を見つけていない」としている

GreyNoise報告したベンダー確認済

関係自社のおとり網（Global Observation Grid）で2026年6月から1つのIPアドレスを追跡し、 9月21日に分析を公表した。攻撃者を「Red Heron と同一か関係がある」とする

影響根拠として、同じ C2 ドメイン・同じマルウェア系統・7月の Gitea の悪用・その他の手口の一致を挙げている。 攻撃者のIPアドレスは「被害者への配慮と運用上の危険」を理由に伏せている

台湾の産業オートメーション企業（名称非公表・2社）被害組織推定

関係Acronis が確認した被害者のうち、最も多くのデータを持ち出された1社と、 最も深い横展開を受けた1社（新竹の Synology NAS 上の Gitea を起点に Proxmox へ）

影響1社目は単一のホストから**数百のリポジトリ**を持ち出された。 そのホストには攻撃の道具が実行のたびに作る「poc-*」ディレクトリが**130個超**残っており、 Acronis はこれを攻撃の回数のおおよその目安とみている。 2社目は **Proxmox の root 認証チケット**を取られ、3ノードで仮想マシンの控えを起動された。 **控えの取得が完了したかは書かれていない**

カナダの再生可能エネルギー企業（名称非公表）被害組織推定

関係Acronis が「本キャンペーンで最も広範に侵害された」とした被害者

影響22回の攻撃セッション、41個の自動登録アカウント、61件のデータベースの取得が記録されていた。 人事・CRM・認証サービス・社内ポータルを含むアプリケーション一式と、 JWT・内部トークン・SSH ホスト鍵などの設定上の秘密が持ち出され、 authorized_keys には「root-shell」などと名付けた SSH 鍵が置かれていた

西側の政府組織（名称・国名非公表）被害組織推定

関係GreyNoise が WordPress の侵入のうち「最も悪質なデータ窃取」とした被害者

影響2026年7月22日、WordPress の連鎖した脆弱性で侵入され、管理者アカウント13件を抜かれ、 正規の利用者を装う管理者アカウントを足されたうえで、 バックエンドのデータベースから**18,000件超の機微な記録**を持ち出された

WordPress で侵入された日本の組織（名称非公表・2件）被害組織関係未公表

関係GreyNoise が「政府や中小企業が中心で、上の政府組織ほど深刻ではない」として 国別の件数だけを示した表に、**日本 2** と記載されている

影響**組織の名前・業種・被害の中身はいずれも公表されていない。** 本記録が把握しているのは件数だけである

Zyxel GS1900 スイッチの利用組織（48か国・不特定）波及先（取引先・利用事業者）関係未公表

関係2026年8月17日ごろ、設定と認証情報を抜かれた996台のスイッチの持ち主

影響国別ではイタリア133台・米国129台・台湾123台が多い。 **GreyNoise が示した国別の表に日本は載っていない。** 抜かれたのは設定・root 級の認証情報（ハッシュ）・ネットワーク情報

Gitea製品・部品の供給元確認済

関係悪用された CVE-2026-60004 を含む製品の開発元

影響2026年7月27日に修正版 1.27.1 を公開し、「できるだけ早く更新するよう強く勧める」（原文英語）とした

Zyxel Networks製品・部品の供給元確認済

影響2026年6月16日にセキュリティ勧告を出し、対象の11機種に修正版のファームウェアを公開した。 GreyNoise が悪用を観測した8月17日は、その**2か月後**にあたる

CISA（米国サイバーセキュリティ・インフラストラクチャセキュリティ庁）注意喚起主体確認済

影響CVE-2026-60004 を2026年8月25日に（対応期限8月28日）、 CVE-2026-7273 を9月21日に（対応期限9月24日）収載した

Red Heron（および GreyNoise のいう「悪意あるサイバー主体」）推定加害者推定

影響Acronis は、簡体字中国語の運用資料、台湾を中国の一部として扱う分類、 戦略的な情報収集の優先順位に沿う標的の選び方から、**中国に結びつく文脈で活動している**と 中程度の確度で評価した。外部から渡されたとみられる標的一覧や第2のサーバの存在から、 **複数人による運用**とみている。GreyNoise は UTC+8 の時間帯で活動している可能性を挙げる

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

公開された脆弱性の PoC を数日で自動化し、インターネットに公開された開発基盤 （Gitea・FlowiseAI・Nuclio 等）・CMS（WordPress）・境界機器（UniFi OS・Zyxel GS1900）・ 仮想化基盤（Proxmox VE）を広く走査して侵入する。侵入後はソースコードとデータベースを持ち出し、 設定上の秘密と SSH 鍵で永続化し、Linux では JITTERLY とルートキット SIXZUT を置く。 台湾では開発基盤から仮想化基盤の root 権限まで横展開した

  1. 1. 偵察third_party_research[1]
    FOFA を使って Gitea を探し、7か国1,386台について誰でも登録できるかを50並列で確かめた。 標的は簡体字の業種分類と確度で整理され、台湾については外部から渡されたとみられる477台の一覧があった
    根拠: 攻撃者の中継サーバに残った標的一覧（Acronis の分析）
  2. 2. 初期侵入third_party_research[1] [2] [6]
    Gitea では使い捨てアカウントを自動登録し、リポジトリを作って CVE-2026-60004 を突く。 WordPress では CVE-2026-63030 と CVE-2026-60137 の連鎖、Zyxel GS1900 では CVE-2026-7273 を使う
    根拠: Acronis・GreyNoise の分析
  3. 3. 実行third_party_research[1] [2]
    Gitea のサービスアカウントの権限で Git フックとしてコマンドを実行する。 Windows の WordPress ではウェブシェルから PowerShell を動かした
    根拠: Acronis・GreyNoise の分析
  4. 4. 永続化third_party_research[1] [2]
    authorized_keys に「root-shell」などと名付けた SSH 鍵を置き、raw TCP の裏口（認証キーつき）を開く。 Linux では JITTERLY を /usr/lib/configd/ のような正規に見える場所へ移し、ルートキット SIXZUT で守る。 WordPress では正規の利用者を装う管理者を足し、登録日を過去に書き換えた
    根拠: Acronis・GreyNoise の分析
  5. 5. 検知回避third_party_research[1] [7]
    SIXZUT が15の Linux 関数を差し替えてファイル・プロセス・通信を隠し、JITTERLY の停止を防ぎ再起動させる。 Gitea のデータベースから攻撃の痕跡を消す機能もあった（1社では効かず130個超が残った）。 裏口の指令を Prometheus の metrics 要求に見せかけた例もある
    根拠: Acronis・The Hacker News
  6. 6. 認証情報アクセスthird_party_research[1] [2]
    Gitea のデータディレクトリごと gitea.db を持ち出し、bcrypt のハッシュを hashcat で解く。 設定から JWT・内部トークン・SSH ホスト鍵を取り、Zyxel GS1900 からは root 級の認証情報（ハッシュ）を抜いた
    根拠: Acronis・GreyNoise の分析
  7. 7. 横展開third_party_research[1]
    台湾の環境で、Synology NAS 上の Gitea から Proxmox の root の認証チケットを得て、 クラスタ管理 API から3ノードへ本体を配置した。JITTERLY は SOCKS・逆ポート転送・中継の機能を持つ
    根拠: Acronis の分析
  8. 8. 収集third_party_research[1] [2]
    リポジトリをファイルシステムから直接取り出し（--dump-fs）、 Proxmox では vzdump で仮想マシンの控えを起動した。WordPress ではデータベースの資格情報を設定ファイルから探した
    根拠: Acronis・GreyNoise の分析
  9. 9. 持ち出しthird_party_research[1] [2]
    リポジトリ・データベース・政府組織の18,000件超の記録を持ち出した。 別のサーバから中継サーバのデータを写し取るスクリプトもあった
    根拠: Acronis・GreyNoise の分析
  10. 10. C2通信third_party_research[1]
    JITTERLY は独自の枠組みの raw TCP で、msgpack を AES-128-GCM で暗号化して C2 と通信する。 Adaptix C2 の Gopher と互換の形をとる
    根拠: Acronis の分析

    脆弱性は Gitea の diffpatch の API にある。同じ細工したパッチを2回送ると、Git の三方向マージの経路が働いて、本来は索引だけに置かれるはずのファイルがディスクに書き出され、Git のフック（hooks/post-index-change）として Gitea のサービスアカウントの権限で実行される。リポジトリへの書き込み権限が要るが、Acronis は次の点を指摘している。

    「Gitea は既定で誰でも利用者登録できる状態で出荷される。登録が開いたままの環境では、外部の攻撃者はアカウントを登録し、リポジトリを作り、細工したパッチを送るだけで、事前の認証情報なしにコードを実行できる」（原文英語）

    Red Heron は実際に word_word_NNN という形の使い捨てアカウントを自動登録していた。

    台湾の産業オートメーション企業から、SCADA/HMI の道具を含む数百のリポジトリが持ち出された被害規模・影響範囲出典 [1] [4]

    Acronis が確認した被害の中で持ち出されたデータが最も多かったのは、台湾の産業オートメーション企業1社である。単一のホストから数百のリポジトリが取られ、中身は次のようなものだった（Acronis の記述）。

    • 監視製品
    • 産業制御環境で使う SCADA/HMI の道具
    • IoT 基盤との連携
    • ネットワークの盗聴（スニッファ）の道具
    • サーバの設定
    • 社内業務のアプリケーション

    このホストには、攻撃の道具が実行のたびに作る「poc-」ディレクトリが130個超*残っていた。痕跡の消去が効いておらず、Acronis はこれを攻撃を繰り返した回数のおおよその目安とみている。

    本記録として重く見るのは、持ち出されたのが「ある会社の情報」ではなく、その会社が顧客の工場に納める道具の設計そのものであることだ。ソースコードの流出は、その製品を使う側の脆弱性探しの材料になる。被害企業の顧客にどう伝わったかは公表されていない（本記録の判断）。

    別の台湾の環境では、NAS 上の Gitea から入り、Proxmox の3ノードすべての root 権限に達した原因・手口出典 [1]

    Acronis が「本キャンペーンで最も深い横展開」とした経路は次のとおりである。

    1. 新竹にある Synology NAS 上の Gitea で CVE-2026-60004 を使い、コードを実行する
    2. 列挙専用のアカウント（pvenum02。Acronis は「pve」は Proxmox Virtual Environment を指すと中程度の確度でみる）を登録し、専用の道具で調べ直す
    3. Proxmox の root の認証チケット（root@pam）を取り、クラスタ管理 API の全権を得る
    4. 3つのノード（tapve01〜03）に本体を置き、vzdump で仮想マシンの控えを3ノードすべてで起動する

    Acronis はこう要約している。

    「Synology NAS 上の Gitea の遠隔コード実行から始まり、その下にある Proxmox クラスタのroot 級の権限、3ノードへの本体の配置、そして仮想マシンの丸ごとの像を持ち出す試みで終わった」（原文英語）

    開発基盤と仮想化基盤が同じ認証情報・同じ管理網でつながっていたことが、この経路を成り立たせた（本記録の判断。Acronis は root 認証チケットの入手経路を具体的には書いていない）。

    Gitea（Acronis の推奨を本記録が整理）

    1. 1.27.1 以降に更新する
    2. 不要なら誰でも利用者登録できる設定を止める。使っていなければ diffpatch の経路を制限する
    3. VPN や認証つきのリバースプロキシを置けるなら、インターネットに直接出さない
    4. 勧告の公開（7月28日）以降に作られたアカウントとリポジトリを確認する
    5. diffpatch への想定外の要求と、見慣れない引数のついた /api/v1/metrics への要求をログで探す（Red Heron は metrics の API を装って裏口の指令を通していた）

    8. 侵害されていたら、Gitea に置いていた認証情報・トークン・SSH ホスト鍵はすべて漏れた前提で更新し、ホストは掃除ではなく作り直す（SIXZUT は自己復元するため）

    CISO・経営層への示唆
    • 修正版の公開から悪用までの猶予は「数日」と置いて、更新の手順を組み直す
      Gitea は修正の2日後に改造が始まり、3日後に走査が終わっていた。 CISA の KEV 収載は修正の29日後である。KEV や月例の更新サイクルを合図にしている組織は、 本件では1か月近く無防備だった
      取るべき行動 インターネットに公開している製品について、「重大な修正と公開 PoC が出たら何日で当てるか」の目標を 製品ごとに決める。本件を例に、Gitea と Zyxel の修正が自社で何日で当たったかを確かめる
    • 「開発基盤」と「境界機器」を、情報システム部門の管理台帳に載せる

      取るべき行動 社内で自前運用している Gitea・GitLab・Proxmox・NAS・管理型スイッチを洗い出し、 インターネットから届くものを一覧にする。持ち主が不明なものは停止を含めて判断する
    • ソースコードの流出を、顧客への影響として評価する
      台湾の被害企業から持ち出されたのは、顧客の工場に納める SCADA/HMI の道具の設計である。 自社の製品のコードが取られると、それを使う顧客の設備が次の標的になりうる
      取るべき行動 ソースコードの流出を想定したとき、どの製品のどの顧客に、何を、いつ伝えるかを決めておく。 製造業・機器ベンダーは、製品の脆弱性の受付と公表の窓口（PSIRT）が機能するかを確認する
    • 攻撃者の「粗さ」を安心材料にしない
      本件の攻撃者は打ち間違いを重ね、自分の中継サーバを認証なしで公開していた。 それでも公開 PoC の自動化だけで、数十か国の組織に侵入している。 防御の前提を「高度な国家の部隊」に置くと、この種の広く撃つ攻撃への備えが後回しになる
      取るべき行動 脅威の想定に「公開 PoC を数日で自動化して広く撃つ相手」を明示的に入れ、 外部公開資産の修正の速さを経営への報告の指標に加える
    セキュリティ技術者への示唆
    • Gitea を運用しているなら、更新・登録の停止・侵害の確認を今日行う

      取るべき行動 /etc/ld.so.preload と Acronis が挙げた痕跡の確認を、オフラインのディスク像・ 既知の正常なカーネルからの起動・EDR の記録で行う手順を用意する
    • 管理型スイッチの管理画面をインターネットから外し、出荷時の認証情報を変える

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ Gitea などのソースコード管理を自前で運用し、インターネットから届く状態にしている本件の中心の経路。誰でも登録できる既定の設定のままなら、認証情報なしで侵入が成立した
    システム構成□ Zyxel GS1900 などの管理型スイッチ・NAS の管理画面が、社外から届くGS1900 では996台が抜かれ、半数超が出荷時の認証情報だった。小規模拠点や工場でよく使われる機器である
    運用・監視□ 外部公開資産の修正の適用を、月例の更新や KEV の収載を合図にしている本件の Gitea は修正の3日後に走査され、KEV 収載は29日後だった。合図が遅すぎる
    システム構成□ 開発基盤・NAS と仮想化基盤（Proxmox 等）の管理網や認証情報がつながっている台湾の環境では開発基盤から仮想化基盤の root 権限まで横展開し、仮想マシンの丸ごとの控えが狙われた
    委託・第三者部品□ 産業制御・監視製品などを顧客に納めており、その製品のソースコードを自社の開発基盤に置いている台湾の産業オートメーション企業からは SCADA/HMI の道具のリポジトリが取られた。 自社の流出が顧客の設備の危険に直結する
    データの保持□ ソースコード管理の中に、デプロイ鍵・トークン・パスワードなどの秘密を置いているカナダの被害企業では JWT・内部トークン・SSH ホスト鍵・デプロイ鍵が取られた。 侵害されると、置いていた秘密をすべて更新する必要がある
