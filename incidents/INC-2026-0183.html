INC-2026-0183TraderTraitor がインドIT事業者に侵入

北朝鮮の TraderTraitor（Jade Sleet・UNC4899）が暗号資産ビジネスで使ってきた macOS バックドア FLATROOF と ROOFDECK が、暗号資産と関わりの無いインドの IT サービス事業者の DevOps エンジニアの MacBook で見つかった——SentinelOne によれば、バックドアは2026年3月18日にはディスク上にあり、3月29日に Cursor IDE の起動とともに動き出した。攻撃者は4月19日に LayerZero Labs が自社事件の分析を公表した翌日に第3段へ乗り換えて元のバックドアを消し、6月1日まで通信を続けた。エンジニアの端末は AWS・OVH・OpenStack を Terraform と Ansible で操作するクラウド認証情報とソース管理の権限を持っていた。初期侵入の経路と、盗まれたものの中身は公表されていない

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年9月18日 最終更新: 2026年9月22日

米国のセキュリティ企業 SentinelOne（研究部門 SentinelLABS）は 2026年9月18日、北朝鮮の攻撃者 TraderTraitor（Microsoft の呼称 Jade Sleet、Mandiant の UNC4899）のmacOS バックドア FLATROOF と ROOFDECK が、暗号資産と関わりの無いインドの IT サービス事業者で見つかったと公表しました。The Hacker News が9月21日、台湾の iThome が9月22日に報じています。

2つのバックドアは、2026年3〜4月に暗号資産の基盤 KelpDAO（LayerZero のブリッジ） が攻撃された事件で使われたものです。SentinelOne はその検体で自社のテレメトリを探し、無関係な2件目の被害者としてこの事業者を見つけました。

  • 3月18日、バックドアはすでにディスク上にあった。11日間は動かなかった
  • 3月29日、エンジニアが Cursor IDE で作業フォルダを開くと、Cursor の子プロセスとして2つのバックドアが起動し、それぞれ別の C2（FLATROOF は Telegram、ROOFDECK は分散型の Nostr）へつないだ
  • 4月20日——LayerZero Labs が自社事件の分析を公表した翌日——攻撃者は第3段の「loginwindow」を取り込み、元の2つのバックドアを自ら消した
  • 6月1日、最後の通信が観測された

この端末は AWS・OVH・OpenStack を Terraform と Ansible で操作するエンジニアのもので、クラウドの認証情報とソース管理の権限を持っていました。何が持ち出されたか、顧客の環境へ及んだかは公表されていません。

日本の読者にとっての含意は2つあります。 TraderTraitor は2024年に、委託先 Ginco の従業員を偽の採用試験で感染させて DMM Bitcoin から約482億円相当を奪った主体です（警察庁・FBI・DC3 の公表）。その道具が暗号資産の外、IT サービス事業者の DevOps 担当者に向いたことは、日本の委託元にとって「委託先の開発者端末」が入口になりうることを示します。もう1つは、攻撃者が被害者側の公表を読んで道具を入れ替えたことです。

暗号資産のための道具が、暗号資産と関わりの無い IT 事業者の DevOps 端末で見つかった概観出典 [1] [2]

SentinelOne は、2026年3〜4月の KelpDAO（LayerZero のブリッジ）への攻撃で使われたmacOS バックドア FLATROOF（別名 Gaslight）と ROOFDECK で自社のテレメトリを探し、無関係な2件目の被害者を見つけた。インドの小規模な IT サービス事業者で、暗号資産との関わりは無い。

「クラウドエンジニアリングの権限とソース管理の権限を持つエンジニアを、エンドポイントの監視で特別な集団として扱うことを勧める」（SentinelOne・原文英語）

被害にあったのは、AWS・OVH・OpenStack を Terraform と Ansible で操作する DevOps エンジニアのApple Silicon MacBook である。報告の題名「Don't Call Us, We'll Call Your APIs」（こちらから電話はしない、お前の API に電話する）が示すとおり、SentinelOne は攻撃者の狙いを、暗号資産そのものではなくクラウドとソース管理の鍵とみている。

帰属について SentinelOne は、検体の解析と LayerZero Labs の事件とのインフラの重なりから、北朝鮮の国家支援の Lazarus の下位集団 TraderTraitor としている。

バックドアは Cursor IDE の子プロセスとして起動し、IDE を使う時間だけ通信した原因・手口出典 [1] [2]

SentinelOne が示した端末上の経過は次のとおりである（時刻は協定世界時）。

日時 出来事
3月18日 2つのバックドアがディスク上にあることが確認される
3月25〜28日 Cursor は使われているが、悪性の動きは無い
3月29日 5時00分41秒 エンジニアが Cursor で作業フォルダ ~/DevOps-Automation/cloudshield を開く
同 5時00分53秒 Cursor の子プロセスとして2つのバックドアが nohup で起動（引数 --type=renderer で描画プロセスを装う）
同 5時00分55秒 FLATROOF と ROOFDECK がそれぞれ別の C2 へ接続
同 5時00分58秒 Telegram への接続。xattr と chmod で実行できる状態に整え直す
3月30日〜4月19日 Cursor を使っている時間に限って通信が続く
4月14日 18時25分 FLATROOF が ROOFDECK の検疫属性を外して再び使える状態にする

2つのバックドアはいずれも Rust で書かれた ARM64 の macOS 向けで、FLATROOF は Telegram の Bot API を、ROOFDECK は分散型プロトコル Nostr の中継サーバを C2 に使う。ROOFDECK の命令は暗号的に署名され、検証されてから実行される。永続化は Launch Agent による。

収集の対象は、ブラウザ（Chrome・Firefox・Safari）のデータ、端末のコマンド履歴、アプリの一覧、プロセスの一覧、システムの構成情報、ログインのキーチェーンである。

IDE の子プロセスとして動き、IDE を使う時間だけ通信することは、開発者の端末の通常の動きに紛れる。SentinelOne が「IDE の子プロセスで、IDE の正規の署名を持たないもの」を監視せよと勧めるのはこのためである。

攻撃者は被害者側の公表の翌日に道具を入れ替え、元のバックドアを消した原因・手口出典 [1]

2026年4月19日、LayerZero Labs が KelpDAO への攻撃の分析を公表した。その翌日の4月20日、本件の端末で次のことが起きた（SentinelOne による）。

  • 8時48分59秒、ROOFDECK が第3段「loginwindow」を取り込む（macOS の正規プロセスと同じ名前）
  • 39秒後、loginwindow が新しい C2 ドメインへ接続する
  • 13時15分、loginwindow が元の FLATROOF と ROOFDECK を rm -f で消す

第3段はその後も6月1日まで通信を続け、6月17日にファイルがゴミ箱へ移された。

攻撃者は、別の被害者が公表した分析を読み、公表された道具を別の被害者の端末から引き上げたと読める（この読みは本記録の判断である。SentinelOne は時間の前後関係を示している）。公表は他の被害者を守るが、同時に攻撃者への警報にもなる。本件では、公表された検体で探した結果として見つかったのは、すでに入れ替えが終わった後の端末だった。

入口は分かっていない——偽の採用面接と細工した Terraform のロックファイルは「この攻撃者の手口」にとどまる未確定事項出典 [1] [3]

SentinelOne は初期侵入の経路を書いていない。報告が挙げるのは、この攻撃者の既知の手口である。

  • 偽の採用面接。「Northwind」「Novacart」といった架空の会社を名乗り、課題としてNorthwind-IAC・novacart-interview・terraform-candidate-repo・gtn-candidate-repo といったリポジトリを渡す（gtn-candidate-repo は LayerZero Labs の事件でも使われた）
  • 細工した Terraform のロックファイル。.terraform.lock.hcl の取得元をregistry.hashicorp-aws[.]com・registry.hashicorp-aws[.]io・registry.hashicorp-terraform[.]io といった正規に似せたドメインに向け、terraform init を実行した時点で攻撃者のコードを取らせる

本件の端末でも4月13日に terraform-candidate-repo が複製されている。しかしそれはバックドアの確認（3月18日）より後であり、入口とは言えない。報道には「偽の採用面接と武器化した Terraform プロジェクトでエンジニアを誘導した」と書くものがあるが（iThome）、SentinelOne の報告はそこまで言っていない。

SentinelOne は、偽のレジストリのドメインが消されたきっかけを「求職者の1人が、似せたドメインを不審と報告したこと」（原文英語）と書いている。

同じ攻撃者は、日本の DMM Bitcoin を委託先の従業員の感染から崩した背景・過去事例出典 [1] [4]

警察庁は2024年12月24日、FBI・DC3 とともに、TraderTraitor が DMM Bitcoin から約482億円相当（4,502.9BTC）の暗号資産を窃取したと特定したと公表した。入口は、LinkedIn でリクルーターになりすまし、ウォレットのソフトウェアを提供する委託先 Ginco の従業員に採用前試験を装う悪性の Python スクリプトを実行させたことだった。

本件はその系列の道具が、暗号資産の外の IT サービス事業者で見つかった例である（SentinelOne は「暗号資産と関わりの無い被害者」と題している）。IT サービス事業者の DevOps 担当者は、自社だけでなく顧客のクラウドの鍵を持ちうる。日本の企業がインドを含む海外の事業者に開発・運用を委託するのは珍しくない。委託先の開発者端末は、委託元から見えない入口である（本記録の判断）。

同じ日（9月18日）に日米豪独の当局が出した WaterPlum の共同勧告（INC-2026-0168）も、開発者を偽の求人で狙い、雇用主の環境へ入る危険を強調している。WaterPlum と TraderTraitor は別の集団として追跡されている。

SentinelOne の勧告——クラウドの鍵を持つ開発者を「特別な集団」として監視する対策・注意喚起出典 [1]

SentinelOne の推奨は次のとおりである（いずれも原文英語からの訳）。

  1. クラウドエンジニアリングの権限とソース管理の権限を持つエンジニアを、エンドポイントの監視で特別な集団として扱う
  2. ホームディレクトリから実行される署名の無いバイナリ、IDE の正規の部品ではない IDE の子プロセス、それらからの外向きの TLS 通信を探す
  3. これらの利用者が受け取った面接の持ち帰り課題や、頼んでいないリポジトリの報告を追う。「リクルーターが送ったことはテレメトリだけでは見えない」
  4. 会社の端末を外部の採用面接に使わせない方針と、その強制の方法を検討する
  5. 機密のアクセス権を持つ開発者への教育。偽のレジストリのドメインは、求職者の1人の報告で消された
  6. 開発者は、.terraform.lock.hcl を含むプロジェクトを実行する前に、取得元のレジストリがregistry.terraform.io の既知の名前空間かを確かめる。正規のレジストリにも悪性のものは置かれうる

CISO・経営層への示唆
  • 北朝鮮の暗号資産窃取の攻撃者は、暗号資産を扱わない会社も入口にする
    本件の被害者は暗号資産と関わりの無い IT サービス事業者だった。狙われたのは、 クラウドとソース管理の鍵を持つ DevOps 担当者の端末である。 同じ攻撃者は DMM Bitcoin を委託先 Ginco の従業員から崩した
    取るべき行動 「暗号資産を扱わないから北朝鮮は関係ない」という前提をリスク評価から外す。 自社と委託先で、クラウドとソース管理の管理権限を持つ者の一覧を作り、その端末を重点の監視対象に指定する
  • 委託先の開発・運用担当者の端末を、自社のクラウドへの入口として契約と監査の対象にする
    IT サービス事業者の DevOps 担当者は顧客のクラウドの鍵を持ちうる。 本件では顧客への波及は公表されていないが、端末は AWS・OVH・OpenStack の認証情報を持っていた
    取るべき行動 委託先に、自社環境の鍵を持つ担当者の端末の監視（EDR）・鍵の保管方法・侵害時の通知期限を契約で求める。 委託先が持つ自社環境の鍵を棚卸しし、長期有効のものから短期の認証に置き換える
  • 会社の端末で外部の採用面接や課題をこなすことを禁じ、その理由を説明する
    SentinelOne はこれを推奨として挙げ、「リクルーターが課題を送ったことはテレメトリだけでは見えない」とする。 偽の採用面接は TraderTraitor と WaterPlum の両方の手口である
    取るべき行動 就業規則・端末の利用規程に、会社の端末で外部の面接・課題を行わないことを明記する。 開発者が不審な課題やリポジトリを受け取ったときの報告窓口を作り、報告を責めない運用にする
  • 被害の公表は攻撃者にも読まれる前提で、公表の前に自社の遡及調査を終える
    LayerZero Labs の公表の翌日に、攻撃者は別の被害者の端末で公表された道具を消した。 公表された検体で探したときには、入れ替えが終わっていた
    取るべき行動 自社が被害を公表する場合、IoC の公開の前に、関係先（同業・委託先）との非公開の共有と遡及調査の時間を取る。 他社の公表を受けて自社を調べる場合は、公表された名前・ハッシュだけでなく挙動で探す
セキュリティ技術者への示唆
  • IDE の子プロセスを監視する
    本件のバックドアは Cursor の子プロセスとして起動し、引数で描画プロセスを装い、 IDE を使う時間だけ通信した。SentinelOne は「IDE の正規の部品ではない子プロセス」を着眼点に挙げる
    取るべき行動 EDR で、IDE（VS Code・Cursor 等）の子プロセスのうち、IDE の署名を持たないもの・ホームディレクトリから 起動するものを検知する規則を作る。まずクラウドの管理権限を持つ開発者の端末から始める
  • Terraform のロックファイルと provider の取得元を確かめてから init する
    この攻撃者は .terraform.lock.hcl の取得元を registry.hashicorp-aws[.]com のような似せたドメインに向ける。 `terraform init` を実行した時点で攻撃者のコードが取られる
    取るべき行動 外部から受け取ったリポジトリでは、init の前に .terraform.lock.hcl と required_providers の取得元を確認する。 CI と開発端末で、registry.terraform.io 以外の provider 取得元を既定で拒否する設定（プロキシ・ミラー）を検討する
  • 開発者端末からの Telegram・Nostr など業務外の C2 経路を把握する
    FLATROOF は Telegram の Bot API、ROOFDECK は Nostr の中継サーバを C2 に使った
    取るべき行動 開発者端末の DNS・プロキシの記録で、api.telegram.org や Nostr の中継サーバへの通信を洗い出し、 業務上の必要が無い端末からの通信を調べる
  • クラウドの鍵を開発者の端末に長く置かない
    端末はクラウドの認証情報とキーチェーンを持ち、キーチェーンは収集対象だった。 端末が75日以上取られていた場合、長期有効の鍵はそのまま使われうる
    取るべき行動 AWS 等のアクセスキーを短期の認証（SSO・一時的な認証情報）に置き換え、 長期有効のキーが残っていないかを定期的に棚卸しする

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 開発・運用担当者の端末に、クラウドの長期有効のアクセスキーやソース管理の認証情報が置かれている本件で狙われた資産そのもの。端末が取られると鍵がそのまま持ち出されうる
委託・第三者部品□ 海外を含む外部の IT サービス事業者に、自社のクラウドやリポジトリの操作権限を渡している本件の被害者は IT サービス事業者で、担当者の端末は顧客のものを含むクラウドの鍵を持ちうる
運用・監視□ 開発者の macOS 端末に EDR が入っていない、または IDE の子プロセス・署名の無いバイナリを監視していない本件のバックドアは IDE の子プロセスとして動き、IDE を使う時間だけ通信した
体制・契約□ 会社の端末で外部の採用面接や持ち帰り課題を行うことを禁じていない偽の採用面接は TraderTraitor と WaterPlum の既知の手口である
システム構成□ Terraform を外部から受け取ったリポジトリで実行し、provider の取得元を制限していない細工したロックファイルで init 時に攻撃者のコードが取られる手口が記録されている
