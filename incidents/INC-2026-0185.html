INC-2026-0185BigCommerce 連携アプリの鍵で顧客データ流出

SaaS型EC基盤 BigCommerce の連携アプリ「Ribon」「Ribon 1.5」のアプリキーが、開発元 Fastr のシステム侵害で奪われ、攻撃者が加盟店の顧客データをページ送りで取り出し、一部の店舗ページには悪性スクリプトを埋め込んだ——BigCommerce 自身の基盤は破られておらず、盗まれたのは「その基盤を正規に呼び出せる鍵」だった。英国の酒類通販 Master of Malt では2026年9月13日17時21分から17日21時12分（BST）まで顧客の氏名・メール・電話番号・配送先住所が読み出され、パスワードとカード情報は別に保管されていたため無事だった。影響した店舗数は BigCommerce の「ごく少数」と報道の「数百店」で食い違っている

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年9月21日 最終更新: 2026年9月22日

SaaS 型の EC 基盤 BigCommerce は 2026年9月17日、連携アプリ「Ribon」「Ribon 1.5」 の API 認証情報（アプリキー）が侵害されたことを確認しました。両アプリは Be A Part Of（Fastr 傘下のブランド）が運営する買い物体験の最適化アプリで、BigCommerce の説明によれば 侵害されたのは Fastr のシステムです。

攻撃者はこの鍵を使って、2026年9月13日から17日まで、加盟店の BigCommerce 環境にある買い物客のデータにアクセスし、あわせて一部の店舗ページに悪性スクリプトを埋め込みました。

英国の酒類通販 Master of Malt は被害を受けた加盟店の1つで、アクセスされた期間を 9月13日17時21分（BST）から9月17日21時12分（BST） と特定し、攻撃者が顧客データを 「ページ送りで」（page by page） 取り出していたと説明しています。読み出されたのは氏名・メールアドレス・電話番号・配送先住所で、パスワードと決済カード情報は BigCommerce が別に保管しているため含まれていません。同社は英国の情報コミッショナー（ICO）へ報告し、ケース番号 IC-569770-Y1R9 が2026年9月19日付で発行されています。

本件の要点は「基盤は破られていないのに、基盤のデータが出た」という形です。 BigCommerce は自社の基盤が侵害されたことを明確に否定しており、それは正しいとみられます。破られたのは、その基盤を正規に呼び出せる鍵を預かっていた第三者でした。加盟店から見ると、自社のシステムにも、契約している基盤にも問題が無いのに、顧客データが持ち出されたことになります。

日本の EC 事業者も、BigCommerce・Shopify・国内カートに多数の外部アプリをつないでいます。「どのアプリに、どの範囲のデータを読む権限を渡しているか」は、導入したときにしか意識されず、その後は棚卸しされないのが普通です。本記録はその棚卸しの材料として残します。

    基盤は破られていない。破られたのは、基盤を正規に呼び出せる鍵を預かっていた第三者だった概観出典 [1] [2]

    BigCommerce は SaaS 型の EC 基盤で、加盟店は自前でサーバを持たずに店舗を運営する。基盤には 1,200 を超える第三者アプリが接続でき、加盟店はその中から必要なものを導入する。

    今回、攻撃者が手に入れたのはその第三者アプリの1つ Ribon（と Ribon 1.5）のアプリキーだった。BigCommerce の説明によれば、鍵は開発元 Fastr のシステムが侵害されたことで奪われた。

    鍵を手にした攻撃者は、2つのことをした。

    1. 加盟店の顧客データを読み出した。 Master of Malt の説明では、攻撃者は「ページ送りで」（page by page）データを取り出していた。これはアプリに与えられた権限の範囲で行われた正規の API 呼び出しである
    2. 一部の店舗ページに悪性スクリプトを埋め込んだ。 BigCommerce はこれを「ごく少数の加盟店のストアフロント」としている

    加盟店の側から見ると、自社のシステムにも、契約している基盤にも問題が無い。それでも顧客データが出た。BigCommerce が「自社の基盤は破られていない」と言うのは事実として正しく、同時に、加盟店にとっては何の慰めにもならない。

    読み出されたのは氏名・メール・電話・配送先住所で、パスワードとカード情報は「別に置いていた」から残った被害規模・影響範囲出典 [1] [2] [3]

    パスワードとカード情報が残ったのは、BigCommerce がこれらを顧客レコードとは別に保管していたからである。アプリに渡された鍵の権限が顧客レコードに届いても、その先には届かなかった。

    これは偶然ではなく設計の結果である。 同じ基盤に同じ権限で全部が置かれていれば、同じ鍵で全部が出ていた。連携アプリに権限を渡す設計では、「この鍵で何がどこまで読めるか」が被害の上限をそのまま決める。

    店舗数の説明が食い違っており、加盟店は自分が対象かどうかを外から判断できない波及・関係先出典 [1] [2] [3]

    影響の広がりについて、3つの言い方が並んでいる。

    • BigCommerce: 悪性スクリプトが埋め込まれたのは「ごく少数の加盟店のストアフロント」
    • SecurityWeek: Ribon は「数百の BigCommerce 店舗」に導入されていた
    • Master of Malt: 影響は「自社の顧客をはるかに超えて、ほかの数百店に及ぶ可能性がある」

    これらは矛盾していない。「スクリプトを埋め込まれた店舗」と「Ribon を入れていた店舗」と「データを読み出された店舗」は別の集合でありうる。しかし 3つのうちどれが何件なのかは、どこにも書かれていない。

    公表されている加盟店名は Master of Malt だけである。米国の法律事務所が本件に関する相談者を募る際にも、「複数の小売事業者が顧客へ通知を始めている」としか書かれていない。

    加盟店の側は、BigCommerce からの個別通知が来たかどうかでしか自分が対象かを知ることができない。通知が来ていない加盟店が、「影響が無いと確認された」のか「まだ確認されていない」のかを区別する材料は無い。本記録はこの点を、委託先起因の事案で毎回問題になる「被害なしと確認された範囲の非開示」として記録する。

    • アプリキーはどこに、どんな形で保管されていたのか（コード内か、秘密管理の仕組みか）
    • 鍵に有効期限はあったのか。ローテーションは行われていたのか
    • 加盟店ごとに別の鍵だったのか、アプリ共通の1本だったのか
    • 鍵の不正利用に「開発者が気づいた」（9月17日）のは、何を見てだったのか

    このいずれにも答えが無い。 BigCommerce の声明は自社の対応に限られ、Fastr と Be A Part Of は報道機関の問い合わせに回答していない。

    比較として、同じ「第三者の鍵が奪われて多数のサイトに波及した」事案であるBrevo の件（INC-2026-0171）では、当事者が分単位の時系列と、鍵がアプリケーションのソースコードにハードコードされていたことまで公開した。そこまで書かれてはじめて、読者は自社の鍵の置き場所を点検できる。本件では、読者が持ち帰れるのは「連携アプリの鍵は奪われうる」という一般論までである。

    加盟店が今できるのは、アプリに渡した権限の棚卸しと、アプリ経由の読み出しの可視化対策・注意喚起出典 [1] [2]

    EC 基盤に連携アプリをつないでいる事業者が、本件から実際に動かせることを挙げる。

    1. 導入済みアプリの一覧を出し、使っていないものを外す。試しに入れて放置されたアプリは、権限だけが生き続ける
    2. 各アプリに渡している権限の範囲を確認する。「顧客の読み取り」が要るアプリと、要らないアプリを分ける。買い物体験の最適化に顧客レコード全件の読み取りが要るかを、導入時に問い直す
    3. アプリ経由の API 呼び出しの記録を見る。本件の攻撃者は「ページ送り」で顧客データを取り出していた。これは呼び出しの回数と時間帯に必ず現れる。1つのアプリの鍵からの大量の連続読み出しを検知できるかを確かめる
    4. 鍵の失効手順を先に確認しておく。事故のときに止めるのは「アプリのアンインストール」なのか「鍵の失効」なのか、誰が何分でできるのかを試しておく
    5. 店舗ページに読み込まれる外部スクリプトの一覧を作る。本件では店舗ページへのスクリプト注入も行われた。何が読み込まれているかを知らなければ、増えたことにも気づけない

    1〜2は基盤の管理画面だけで今日できる。 3〜5は基盤側の機能に依存するため、できないなら「できない」ことを事業者に確認し、リスクとして記録しておくほうがよい。

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    判断評価評価の根拠と留保
    BigCommerce は、該当する加盟店の店舗から Ribon アプリをアンインストールして 攻撃者のアクセスを断った（加盟店の同意を個別に取る前に基盤側で実施したとみられる）機能した**本記録の作成者の評価である。**鍵の失効だけでなくアプリの削除まで行ったことで、 同じ鍵での再アクセスの余地を残さなかった。**基盤事業者が加盟店に代わって止められる**のは SaaS 型の強みであり、本件ではそれが機能している
    BigCommerce は「自社の基盤は侵害されていない」「侵害されたのは Fastr のシステム」 「該当する加盟店へ直接通知した」「開発元の調査にログを提供している」ことを 報道機関への声明で述べた一方、**影響を受けた加盟店の数、読み出されたデータの範囲、 埋め込まれたスクリプトの機能、影響が無いと確認された範囲**には触れていない部分的に機能**本記録の作成者の評価である。**「基盤は無事」という事実を最初に置く構成は、 基盤事業者としては自然だが、読者が最初に知りたいのは「自分の店・自分のデータはどうか」である。 公開の場（ステータスページ等）に1本の記録が残っていれば、加盟店は個別通知を待たずに確認できた
    CISO・経営層への示唆
    • SaaS の連携アプリは「委託先」として契約と棚卸しの対象に入れる
      本件で破られたのは基盤ではなく、マーケットプレイスの連携アプリの開発元だった。 加盟店はその会社と直接の契約を持たないことが多く、**侵害されても通知が来る保証が無い**
      取るべき行動 導入している連携アプリを一覧にし、提供元の社名・与えている権限・侵害時の通知の約束を 1行ずつ埋める。埋まらない欄がある時点でリスクとして記録し、 基盤事業者に「アプリ提供元の侵害時に誰がいつ知らせるか」を確認する
    • 「基盤は侵害されていない」という説明を、自社の被害の否定として読まない
      BigCommerce の説明は事実として正しいが、加盟店の顧客データは実際に読み出された。 **責任分界の説明と、被害の有無は別の話である**
      取るべき行動 事故の報告を受けたときは「誰のシステムが破られたか」と「自社のデータがどうなったか」を 分けて確認する。社内報告の様式にもこの2行を分けて設ける
    • 個人データの保管を「同じ権限で全部」にしない設計が、事故の日に効く
      本件でパスワードと決済カード情報が出なかったのは、BigCommerce がこれらを 顧客レコードと別に保管していたからである。**同じ場所に同じ権限で置いていれば同じ鍵で出ていた**
      取るべき行動 自社サービスで、連携先やアプリに渡す権限で「どこまで読めるか」を洗い出し、 認証情報・決済情報・本人確認書類を別の権限の下に置き直す計画を持つ
    • 「影響が無いと確認された範囲」を出さない事故報告は、確認できない不安を取引先に残す
      BigCommerce は該当店舗へ個別に通知したが、対象外の範囲を示していない。 通知が来ない加盟店は「無事」なのか「未確認」なのかを判断できない
      取るべき行動 自社が事故を起こす側になったときの報告の型に、 **「影響を確認した範囲」と「影響が無いと確認した範囲」と「まだ確認できていない範囲」**の 3つを分けて書く欄を設ける
    セキュリティ技術者への示唆
    • 正規の鍵による正規の呼び出しは、量と形でしか見分けられない
      攻撃者は盗んだアプリキーで、アプリに許された API を呼んだだけである。 認証は成功しており、エラーも出ない。異常は**ページ送りでの連続取得**という形に出た
      取るべき行動 アプリ・連携先ごとの API 呼び出しについて、1日あたりの件数・ページングの深さ・ 時間帯の分布を取り、閾値を超えたときに通知する。**連携先単位で見ないと全体の平均に埋もれる**
    • 店舗ページ・サービス画面が読み込む外部スクリプトの一覧を持つ
      本件では顧客データの読み出しに加えて、店舗ページへのスクリプト注入も行われた。 一覧が無ければ、増えたことにも、変わったことにも気づけない
      取るべき行動 本番ページの HTML から読み込まれる外部スクリプトの URL を定期的に収集して差分を取る。 可能なら CSP と SRI で、想定外の読み込みを止める
    • 連携先へ渡す鍵は、テナントごとに分け、短命にし、失効の手順を試しておく
      1本の鍵が多数の加盟店に届いた可能性がある形になっている（鍵の設計は公表されていない）。 本件で止められたのは、開発者が失効させ、基盤側がアプリを外せたからである
      取るべき行動 自社が連携先に鍵を出す側であれば、テナント単位の発行と有効期間を設計に入れる。 受け取る側であれば、**鍵を止めるのに何分かかるか**を平時に計っておく
    • 事故の時刻は「分」で押さえられるようにログを残す
      Master of Malt は開始17:21・終了21:12（BST）まで特定できた。 この精度があると、影響を受けたレコードの範囲を絞り、顧客への通知を当日に出せる
      取るべき行動 API 呼び出しの記録に、呼び出し元（アプリ・鍵の識別子）・対象レコードの範囲・時刻を残し、 保持期間を事故対応に足りる長さにする

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    委託・第三者部品□ EC 基盤・SaaS のマーケットプレイスから第三者アプリを導入しているアプリの提供元は自社の直接の取引先ではないことが多く、侵害されても通知の経路が無い。 本件の入口はそこだった
    認証・認可□ 連携アプリ・外部サービスに、顧客レコードを読める権限の鍵を発行している鍵が奪われれば、認証に成功した正規の呼び出しとして全件が読み出されうる
    運用・監視□ アプリ・連携先ごとの API 呼び出しの量や形を監視していない本件は4日間続いた。基盤側でも加盟店側でも止まらず、気づいたのは開発元だった
    データの保持□ 顧客レコードと、認証情報・決済情報・本人確認書類を同じ権限の下に置いている本件で決済情報が残ったのは、別に保管されていたという理由だけである
    システム構成□ 自社サイト・店舗ページが外部のスクリプトを読み込んでおり、その一覧を持っていない一部の加盟店ではストアフロントに悪性スクリプトが埋め込まれた
    体制・契約□ 委託先・連携先の事故報告で「影響が無いと確認された範囲」を求めていない本件では対象外の範囲が示されず、通知が来ない加盟店は自社の状態を判断できない
