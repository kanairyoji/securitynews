INC-2026-0188Check Point 管理サーバにゼロデイ悪用

ファイアウォールの設定・ログ・管理者操作を一手に握る Check Point Security Management Server に、パストラバーサルとファイルアップロードの不備（CVE-2026-93616・CVSS 9.8）があり、認証を持たない攻撃者が任意のスクリプトを置いて実行できる——攻撃は2026年7月23日に少数の標的に対して行われており、緊急ホットフィックスが出たのは約2か月後の9月22日だった。同社は「攻撃を受けた顧客を少数把握している」と述べ、侵害の手がかり（1,001字を超える利用者名のログイン試行など）を公開した。米 CISA は同日、本件と VPN 側の CVE-2026-85102 を KEV へ収載し、期限を3日後の9月25日とした

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備未知の脆弱性の悪用
初報: 2026年9月22日 最終更新: 2026年9月23日

Check Point Security Management Server は、配下のゲートウェイのセキュリティポリシーを保管・配信し、管理者の変更を処理し、システムのログを集める中枢です。そこに、認証を持たない攻撃者が任意のスクリプトをアップロードして実行できる脆弱性 CVE-2026-93616 が見つかりました。種別はパストラバーサル（ディレクトリトラバーサル）とファイルアップロードの組み合わせで、CVE のレコードにおける CVSS は 9.8 です。

重いのは時間差です。Check Point によれば、この脆弱性を使った攻撃は2026年7月23日に少数の標的に対して行われていました。緊急ホットフィックスが出たのは約2か月後の2026年9月22日です。同社は「本脆弱性は実際に悪用されている。Check Point は攻撃を受けた顧客を少数把握している」（原文英語）と述べ、侵害の手がかり（IoC）をアドバイザリ sk1000171 で公開しました。

影響は主力の管理サーバだけではありません。Security Management Server、Multi-Domain Security Management Server、Log Server、Multi-Domain Log Server、SmartEvent の5製品が対象です。修正は R82.20 向けの Security Hotfix と、各系列の Jumbo Hotfix Accumulator（R82.10 は Take 45 以上、R82 は Take 127 以上など）で提供されます。直ちに当てられない場合の緩和策は、TCP/19009 への到達を信頼できる IP に限ること（SmartConsole の Manage & Settings → Permissions & Administrators → Trusted Clients）と、管理サーバをファイアウォールの背後に置くことです。

同じ日、CISA は本件と、VPN 側の証明書検証の不備 CVE-2026-85102 をそろって KEV（悪用が確認された脆弱性カタログ）へ収載し、対応期限を3日後の9月25日としました。CVE-2026-85102 は9月9日に修正が出ていたもので、Check Point はその時点で悪用の証拠を持っていませんでしたが、9月12日から悪用の試みが始まり、小規模事業所向けの Spark 製品の利用者が狙われています。本記録の作成者が2026年9月23日に確認した範囲では、JPCERT/CC の2026年の注意喚起一覧に本件の注意喚起はありません（Check Point については2026年6月10日の CVE-2026-50751 が直近です）。本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

認証を持たない攻撃者が、Check Point の管理サーバの Web サービスへ到達し、 パストラバーサルとファイルアップロードの不備（CVE-2026-93616）を突いて 任意のスクリプトを置き、サーバ上で実行する。2026年7月23日に少数の標的に対して 行われた攻撃で、悪用後に何が行われたかは公表されていない。 Check Point は、cpm.elg に残る1,001字を超える利用者名のログイン試行、 その時刻と一致するコアダンプ、ReflectionUtils のエラーログに現れる「../」を 手がかりとして示している。

    根拠: Check Point のアドバイザリ sk1000171
  2. 2. 実行確認済[1] [3]
    置かれたスクリプトが管理サーバ上で実行される。 2026年7月23日の攻撃で何が実行されたかは公表されていない。
    根拠: Check Point のアドバイザリ（アップロードしたスクリプトの実行）
  3. 3. 内部探索unconfirmed[1]

    根拠: 公表資料に記載なし（製品の役割からの評価）

    管理サーバはポリシーを配る側であり、掌握されれば配下のゲートウェイの 防御の設定そのものを変えられうる。ログを集める側でもあるため、 調査の材料の信頼性にも影響する。本件でそうした操作が行われたかは公表されていない。
    根拠: 公表資料に記載なし（製品の役割からの評価。Security Affairs も企業ネットワーク全体への影響を指摘）

破られたのは「守る機器」ではなく「守り方を決める機器」だった原因・手口出典 [1] [3] [4] [5]

Check Point Security Management Server は、配下のゲートウェイのセキュリティポリシーを保管・配信し、管理者の変更を処理し、システム全体のログを集める中枢です。

CVE-2026-93616 は、その管理サーバの Web サービスにおけるパストラバーサルとファイルアップロードの不備です。Check Point のアドバイザリ sk1000171 は「ディレクトリトラバーサルとファイルアップロードの脆弱性により、認証されていない攻撃者が Check Point Management Server 上に任意のスクリプトをアップロードして実行できる」（原文英語）と説明しています。要求が到達できるファイルとフォルダの範囲を、サービスが正しく制限していませんでした。

本記録の評価として、この位置はゲートウェイの1台が破られるのとは意味が違います。ポリシーを配る側を握られると、攻撃者は個々の機器を破る必要がなくなります。管理サーバには、配下の機器の構成、管理者の操作の記録、そして組織全体のログが集まっています。ログを集める側を握られることは、「何をされたか」を後から調べる材料の信頼性が落ちることも意味します。

なお、CISA と FBI は2024年5月以降、パストラバーサルの類を出荷前に取り除くようソフトウェア企業へ求めており、この種の欠陥は「2007年以来『許されないもの』と呼ばれてきた」（原文英語）としています。本件はセキュリティ製品の中枢でそれが起きた事例です。

攻撃は7月23日、修正は9月22日——利用組織は61日間、存在すら知らされていなかった概観出典 [1] [5]

Check Point は、CVE-2026-93616 を用いた攻撃が 2026年7月23日に少数の標的に対して行われたとしています。緊急ホットフィックスが出たのは2026年9月22日、その差は61日です。

この61日をどう読むかは注意が要ります。Check Point は、攻撃をいつ把握したかを公表していません。したがって61日は「把握から修正まで」ではなく、「攻撃が起きてから修正が世に出るまで」です。把握が遅れていた可能性も、把握したうえで修正に時間がかかった可能性も、どちらも否定できません。

利用組織の側から見える事実は単純です。その間、脆弱性の存在も、攻撃が起きていたことも知らされていませんでした。侵害の手がかり（IoC）が公開されたのも9月22日です。7月23日前後のログの保全期間が過ぎている環境では、公開された手がかりを当てはめる対象そのものが残っていないことになります。

本記録の評価として、ここから引き出せる実務的な結論は「重要機器のログの保全期間を、ベンダーが IoC を出すまでの時間に耐えられる長さにする」ことです。90日を下回る設定では、本件のような時間差に届きません。

対象は管理サーバだけではない——ログ収集機とイベント分析機も同じ穴を持つ被害規模・影響範囲出典 [1] [3] [5]

Check Point が示した影響製品は5つです。

  • Security Management Server
  • Multi-Domain Security Management Server
  • Log Server
  • Multi-Domain Log Server
  • SmartEvent

対象版は、R82.20（Jumbo Hotfix 未適用）、R82.10 の Take 44 以下、R82 の Take 126 以下、R81.20 の Take 166 以下、R81.10 の Take 190 以下（サポート終了）、および R81・R80.40・R80.30・R80.20・R80.10・R80（いずれもサポート終了）です。修正は R82.20 向けの Security Hotfix と、各系列の Jumbo Hotfix Accumulator（R82.10 は Take 45 以上、R82 は Take 127 以上など）で提供されます。

本記録の評価として、見落としやすいのは Log Server と SmartEvent です。資産台帳で「管理サーバ」として登録されているのは Security Management Server だけで、ログ収集専用機やイベント分析機は別の分類に入っていることがあります。対象を製品名で機械的に突き合わせないと、当たっていない機器が1台残ります。

もう1点、サポート終了版（R81.10 以下）を使っている場合、Jumbo Hotfix の提供そのものが期待できません。この場合の選択肢は版の更改か、緩和策（到達制限）での封じ込めのどちらかになり、いずれも3日では終わりません。サポート終了版が残っていること自体が、緊急時に取れる手を奪っているという読み方が要ります。

当てるだけでは足りない——「当てたことは、攻撃されていなかったことを示さない」対策・注意喚起出典 [1] [3] [4] [5]

Check Point は sk1000171 で侵害の手がかり（IoC）を公開しました。The Hacker News はこの点について「修正を適用しても、それ以前に攻撃されていたかどうかは分からない」（原文英語）と明記しています。

  1. cpm.elg のログに残るlogin(loginRequest=LoginRequest{authenticationInfo=… の項目のうち、利用者名が1,001字以上のもの。正規の運用でそのような長さは使われない
  2. コアダンプファイルの生成時刻が、上記のログイン試行の時刻と一致すること
  3. ReflectionUtils のエラーログに現れるディレクトリトラバーサルの並び（「../」など）

直ちに当てられない場合の緩和策は、TCP/19009 への到達を信頼できる IP に限ることと、管理サーバをファイアウォールの背後に置くことです。前者は SmartConsole のManage & Settings → Permissions & Administrators → Trusted Clients で設定します。Check Point 自身が「一時的な措置にすぎない」としています。

本記録の評価として、Trusted Clients の設定は運用を止めうる点に注意が要ります。管理端末、監視システム、自動連携の仕組みなど、管理サーバへ正規に到達している相手を洗い出せていない状態で絞ると、自分の運用が先に止まります。平時に「誰が管理サーバへ到達しているか」の一覧を持っているかどうかが、緊急時にこの緩和策を使えるかを決めます。

VPN 側は「修正が出た3日後」に狙われた——公開された修正は攻撃者への地図でもある背景・過去事例出典 [3] [4] [5]

同じ日に KEV へ収載されたもう1件、CVE-2026-85102 は、Check Point のゲートウェイが VPN 接続を確立する際の証明書の検証における不備です。認証を経ていない攻撃者にゲートウェイ上でのコード実行を許しうるもので、修正は2026年9月9日に公開されました（sk1000117）。対象は Security Gateway と Spark ファイアウォールで、Site-to-Site VPN またはリモートアクセス VPN を使っている場合に該当します。

公開の時点で、Check Point は悪用の証拠を持っていませんでした。オランダの NCSC-NL は「まもなく悪用の試みが起きると予想する」として緊急の適用を促しています。そして実際に、9月12日から悪用の試みが始まりました。修正公開の3日後です。標的は小規模事業所向けの Spark 製品の利用者で、通信は匿名化基盤（VPN サービス・プロキシ）から送られ、証明書の主体名には CN=vpn,OU=users,O=global などが使われました。

本記録の評価として、この3日は「悪用の証拠が無い＝急がなくてよい」という判断の危うさを示します。修正が公開されれば、その差分から脆弱性の位置を割り出せます。とくに小規模事業所向けの製品は、専任の運用担当がいない場所に置かれがちで、攻撃側から見れば修正が当たるまでの時間が長いことが期待できます。拠点・子会社・店舗に置かれた小型機の更新を、本社の機器と同じ速度で回せるか。本件は、その差がそのまま露出期間になることを示しています。

CISO・経営層への示唆
  • 重要機器のログの保全期間は「ベンダーが IoC を出すまでの時間」に耐える長さにする
    本件では、攻撃が2026年7月23日、IoC の公開が9月22日で、61日の差があった。 保全期間が60日の環境では、公開された手がかりを当てはめる対象が残っていない。 調査ができないことは「被害が無かった」ことにはならない。
    取るべき行動 管理サーバ・境界機器・認証基盤のログについて、保全期間を90日以上に設定し、 機器の外へ転送する。予算の制約で全ログが無理なら、 認証・管理操作・エラーログに絞って長期保全する層を分ける。
  • 「セキュリティ製品だから安全」ではなく「攻撃者にとって最も価値のある的」と位置づける
    破られたのはポリシーを配り、管理者の操作を処理し、ログを集める中枢だった。 Security Affairs は「管理サーバは配下のポリシー・管理者の活動・システムログを 制御するため、侵害は企業ネットワーク全体に広い影響を持ちうる」（原文英語）としている。 セキュリティ製品の管理面は、業務システムより高い優先度で扱う対象である。
    取るべき行動 資産の重要度評価で、セキュリティ製品の管理サーバ・ログサーバ・ イベント分析機を最上位の区分に置く。到達制御・特権の分離・ ログの二重化を、業務系の基幹システムと同じ水準で適用する。
  • サポート終了版を残していること自体が、緊急時に取れる手を奪う
    本件の対象には R81.10 以下のサポート終了版が含まれるが、 これらに Jumbo Hotfix の提供は期待できない。残された選択肢は 版の更改か緩和策での封じ込めで、いずれも KEV の3日には収まらない。
    取るべき行動 保守サポートの期限を資産台帳の必須項目にし、期限切れの機器を 四半期ごとに経営へ報告する。更改の予算がつかない場合は、 「緊急時に更新できない機器」として残存リスクを文書で承認する。
  • 拠点・子会社の小型機を、本社の機器と同じ速度で更新できるかを測っておく
    CVE-2026-85102 では、修正公開の3日後から悪用の試みが始まり、 小規模事業所向けの Spark 製品の利用者が狙われた。専任の運用担当がいない場所に 置かれた機器は、攻撃側から見れば修正が当たるまでの時間が長い。
    取るべき行動 直近の緊急更新について、本社・拠点・子会社それぞれの「公開から適用までの 実日数」を測る。差が大きい層には、集中管理か更新の自動化か 運用委託かのいずれかを当てる判断材料にする。
セキュリティ技術者への示唆
  • 対象を「管理サーバ」ではなく製品名の一覧で突き合わせる
    影響するのは Security Management Server だけでなく、 Multi-Domain Security Management Server・Log Server・ Multi-Domain Log Server・SmartEvent を含む5製品である。 資産台帳の分類が「管理サーバ」「ログ収集」「監視」に分かれていると、 製品名での突き合わせを怠ったぶんだけ漏れる。
    取るべき行動 アドバイザリに列挙された製品名をそのまま検索語にして資産台帳を検索し、 該当した機器をすべて一覧にする。版数は Jumbo Hotfix の Take 番号まで記録する。
  • 到達制限をかける前に「誰が管理サーバに到達しているか」を知っておく
    緩和策は TCP/19009 への到達を信頼できる IP に限ることだが、 管理端末・監視システム・自動連携の仕組みを洗い出せていなければ、 絞った瞬間に自分の運用が止まる。緊急時にその洗い出しから始めると間に合わない。
    取るべき行動 管理サーバへの接続元を平時に記録・集計し、Trusted Clients に 登録すべき一覧を作っておく。四半期ごとに実績と突き合わせて更新する。
  • 侵害確認は「長さ」のような単純な指標から始める
    Check Point が示した手がかりの中心は、cpm.elg に残る利用者名が 1,001字以上であることだった。正規の運用でその長さは使われないため、 複雑な相関分析をしなくても機械的に拾える。
    取るべき行動 利用者名・パラメータの異常な長さ、パストラバーサルの並び（「../」）、 コアダンプの生成時刻といった単純な指標を、定期のログ検査に組み込む。 該当が出たときにだけ詳細な調査へ進む二段構えにする。
  • LivePatch と Jumbo Hotfix の関係を取り違えない
    Check Point は2026年9月16日に LivePatch で別の脆弱性（CVE-2026-91843）を 修正したが、その LivePatch では CVE-2026-93616 は修正されない。 「最近パッチを当てたから大丈夫」という判断が成立しない構造になっている。
    取るべき行動 どの修正がどの CVE に対応するかを、適用記録に CVE 番号で紐づけて残す。 LivePatch の Take 番号と Jumbo Hotfix の Take 番号は別系統であることを 手順書に明記する。
