INC-2026-0190EvilTokens 摘発とデバイスコード悪用

MFA を回避してトークンだけを奪う「デバイスコード・フィッシング」を売る犯罪サービス EvilTokens が、世界1万超の組織・1万2,000超のメールボックスを侵害したのちテイクダウンされた——マイクロソフトのデジタル犯罪対策ユニットが2026年9月15日の米連邦裁判所命令に基づき50のサイトを差し押さえ、175超のドメインを停止し、英ロンドン警視庁が9月18日に令状を執行して2名を逮捕した。攻撃連鎖の全段に AI が組み込まれ、奪ったメールボックスを読んで「誰になりすまし、誰を狙えば最も金が取れるか」まで提示していた。利用者は約1,000人、月額500ドル・初期費用1,500ドルで売られていた

脅威・攻撃キャンペーン続報が続いている有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）設計・実装上の不備認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年9月22日 最終更新: 2026年9月23日

EvilTokens は、2026年2月に現れたフィッシング基盤の売買サービス（PhaaS）です。マイクロソフトによれば、これを使った攻撃は世界1万超の組織で1万2,000を超えるメールボックスを侵害しました。同社のデジタル犯罪対策ユニット（DCU）は2026年9月15日の米連邦裁判所命令に基づき、運用に使われていた50のサイトを差し押さえ、関連基盤の175を超えるドメインを停止しました。英ロンドン警視庁は9月18日に大ロンドン圏で令状を執行し、詐欺に使う物品の作成とマネーロンダリングの疑いで2名を逮捕しています（いずれも保釈）。

中核の手口は デバイスコード・フィッシングです。スマートテレビ・プリンタ・会議機器など「画面に文字を打ちにくい機器」のために用意された正規の OAuth の流れ（デバイス認証フロー）を悪用します。攻撃者が自分でこの流れを開始し、表示されたコードを餌のメールで利用者に渡す。利用者が正規のマイクロソフトのログイン画面でそのコードを入力して承認すると、攻撃者側のセッションが認可されます。利用者はパスワードを攻撃者に渡していませんし、MFA も正しく通っています。それでもトークンが攻撃者の手に渡る——認証が、それを要求した端末と強く結びついていないためです。

もう一つの特徴は AI が攻撃連鎖の全段に組み込まれていたことです。DCU の Steven Masada 氏は「AI は単に説得力のある文面を書く手助けをしていたのではない。誰を狙い、誰になりすまし、その関係をどう突けば最大の金額を引き出せるかを決める助けをしていた」（原文英語）と述べています。奪ったメールボックスを AI が走査し、送金の権限、未処理の請求書、役員のやり取りを見つけ出し、文脈に合ったビジネスメール詐欺（BEC）の文面を生成していました。

価格は初期費用1,500ドル・月額500ドル。Telegram で販売・サポートされ、44種類のテンプレート、アンチボット転送、B2B 送信ツール、SMTP 送信ツールなどの別売品がありました。利用した犯罪者は約1,000人。マイクロソフトは、FBI の IC3 に寄せられた苦情のうち少なくとも13件（被害申告額 約170万ドル）をEvilTokens の活動と関連づけられたとしつつ、「多くは報告されず、全ての被害者を特定の攻撃に結びつけられるわけでもないため、これは控えめな見積もりである」と述べています。マイクロソフトの最優先の助言は「可能な限りデバイスコード・フローを遮断すること」です。本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者（EvilTokens の購入者）が、正規の OAuth デバイス認証フローを自ら開始して デバイスコードを取得し、44種類の主題から選んだ餌のメールでそのコードを標的に渡す。 標的が正規のマイクロソフトのログイン画面でコードを入力して承認すると、 攻撃者のセッションが認可され、アクセストークンが攻撃者の手に渡る。 その後、AI がメールボックスを走査して送金の権限・未処理の請求書・役員のやり取りを見つけ、 Microsoft Graph で組織構造を偵察し、信頼されている相手になりすます BEC の文面を生成する。 居座りには悪性の受信トレイルールの作成や、新しい端末への受信トレイのアクセス付与が使われた。

  1. 1. 偵察確認済[1]
    攻撃者は EvilTokens の管理画面で、配信方法（Cloudflare Workers／Bunny か PHP ホスティング）、 取得モード、レイアウトとテンプレート、コードの表示形式、ページの言語、CAPTCHA、 AI モードなどを選んで展開を組み立てる。44種類の主題のテンプレートが用意されていた。
    根拠: Microsoft Security Blog（EvilTokens の管理画面の分析）
  2. 2. 初期侵入確認済[1] [2]
    攻撃者が正規の OAuth デバイス認証フローを開始してデバイスコードを取得し、 「要対応：パスワードの有効期限切れ」のような切迫感のある餌のメールで コードを標的に渡す。標的が正規のマイクロソフトのログイン画面でコードを入力して 承認すると、攻撃者のセッションが認可される。
    根拠: Microsoft Security Blog（デバイスコード・フィッシングの説明と攻撃連鎖）
  3. 3. 認証情報アクセス確認済[1] [2]
    承認によりアクセストークンが攻撃者の手に渡る。パスワードは窃取されておらず、 MFA も正規に完了しているため、資格情報の変更だけでは断てない。 EvilTokens はトークンの自動更新機能を備えていた。
    根拠: Microsoft Security Blog（トークンの窃取と自動更新の機能）
  4. 4. 内部探索確認済[1] [4]
    攻撃者は Microsoft Graph を用いて組織の構造と権限を把握し、 AI の補助でメールボックスの内容を走査して、送金に関する情報・ 未処理の請求書・役員のやり取りといった「金になる関係」を特定する。
    根拠: Microsoft Security Blog と DCU の説明（Masada 氏の記述）
  5. 5. 永続化確認済[1]
    通信を隠すための悪性の受信トレイルールが作られる。場合によっては、 トークンを使って新しい端末に受信トレイへのアクセスを与えることもあり、 これはとくに息の長い居座りの手口である。
    根拠: Microsoft Security Blog（受信トレイルールと新規端末への付与）
  6. 6. 影響（暗号化・破壊・改ざん）確認済[3] [4]
    侵害したメールボックスの文脈を使い、信頼されている相手になりすます ビジネスメール詐欺（BEC）の文面を生成して送る。EvilTokens は 詐欺の進め方そのものを提案する機能を備えていた。マイクロソフトは IC3 の13件・約170万ドルの被害申告を EvilTokens の活動に関連づけている。
    根拠: Microsoft DCU の公表と CyberScoop・The Record の報道
参照・持ち出された情報

    破られたのは MFA ではなく「認証した端末と、認証を求めた端末が別でよい」という前提だった原因・手口出典 [1] [2]

    デバイスコード認証は、スマートテレビ・プリンタ・会議機器・一部の Teams 機器のように画面に文字を打ちにくい機器のために用意された、正規の OAuth の流れです。機器に短いコードが表示され、利用者は別の端末のブラウザでそのコードを入力して認証を完了します。

    マイクロソフトはこの設計の代償を明記しています。「認証が別の端末で完了するため、要求を開始したセッションは、利用者の元の文脈と強く結びついていない」（原文英語）。攻撃者はこの性質を突きます。自分でデバイスコードの流れを開始し、表示されたコードを餌のメールで利用者に渡す。 利用者は正規のマイクロソフトのログイン画面でコードを入力し、承認します。その瞬間、認可されるのは攻撃者のセッションです。

    ここが本件の要点です。利用者はパスワードを攻撃者に渡していません。MFA も正しく機能しています。フィッシングサイトに認証情報を入力したわけでもありません。それでもトークンが渡る。「MFA を入れたから認証情報を狙う攻撃は終わった」という理解が、そのまま穴になっている構図です。マイクロソフト自身、「トークンを狙うフィッシングは新しいものではないが、組織が MFA を導入するにつれ、この数年ではるかに一般化し、産業化した」（原文英語）としています。

    奪われたトークンは、メールの持ち出しと居座りに使われました。通信を隠す悪性の受信トレイルールが作られ、場合によっては新しい端末に受信トレイへのアクセスを与えることもできます。後者はとくに息の長い居座りの手口です。

    AI は文面を書いていたのではない——「誰を狙い、誰になりすますか」を決めていた評価・解釈出典 [1] [3] [4]

    マイクロソフト DCU の Steven Masada 氏の言葉が、本件の位置づけを端的に示しています。「AI は単に攻撃者がより説得力のあるメッセージを書く手助けをしていたのではない。誰を狙い、誰になりすまし、その関係をどう突けば最大限の金額を引き出せるかを決める助けをしていた」（原文英語）。

    具体的には、侵害後の段階で次のことが行われていました。

    • AI の補助でメールボックスの中身を走査し、送金に関する情報・未処理の請求書・役員のやり取りを探す
    • Microsoft Graph による偵察で組織の構造と権限関係を把握する
    • 見つけた文脈に合わせて、信頼されている相手になりすます BEC の文面を生成する
    • キーワードに引っかかった受信メールを Telegram で通知し、トークンは自動更新、管理者の存在も検知する

    利用者は約1,000人。初期費用1,500ドル・月額500ドルで、この能力が技術力の無い犯罪者にも開かれていました。「高度な攻撃は限られた相手しか使えない」という前提は、サービス化によって崩れています。

    検知の勘所は「入口」ではなく「トークンが使われた後」にある再発防止出典 [1] [2]

    EvilTokens は、従来のメールゲートウェイや端末側の対策をすり抜けるために多段の配送経路を用意していました。餌のメールには悪性URL・PDF・HTML添付が使われ、多段の転送、偽の CAPTCHA、侵害された正規サイト、そしてVercel・Cloudflare Workers・AWS Lambda のような正規のクラウド基盤が経由地に使われています。2026年4月の観測では、自動化基盤で短命のポーリングノードを数千個立ち上げ、Node.js の処理でシグネチャやパターンに基づく検知を避けていました。

    本記録の評価として、この作りに対して「入口で止める」発想だけを置くのは分が悪い戦いです。経由地が正規の基盤であり、餌の文面は AI が個別化し、利用者が入力するのは本物のマイクロソフトのログイン画面だからです。

    現実的な勘所は、トークンが使われた後にあります。

    1. 新しい端末・見慣れない所在地からの、デバイスコード・フローによるサインイン
    2. 受信トレイのルールの作成（とくに特定の差出人の削除・移動・既読化）
    3. Microsoft Graph を使った組織構造や権限の一括照会
    4. 侵害されたアカウントから社内外へ送られる、文脈に合った支払い関係のメール

    いずれも「認証が成功した後の振る舞い」です。マイクロソフトは Microsoft Defender XDR の検知とハンティングクエリを公開しているため、自組織のログで同じ問いを立てられるかを確認する材料になります。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    正規のログイン画面を経由してトークンが攻撃者に渡る流れと、AI が入っている位置
    攻撃者は自らデバイス認証フローを開始してコードを取得し（layer 1）、 餌のメールで標的に渡す（layer 2）。標的は正規のマイクロソフトのログイン画面で コードを入力して承認し（layer 3）、攻撃者のセッションが認可される（layer 4）。 奪ったメールボックスは AI が走査し、なりすまし先と送金の機会を選び出す（layer 5）。 出口は BEC による金銭の詐取（layer 6）。テイクダウンで止まったのは 攻撃者側の基盤であって、フローの設計そのものではない。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    偵察現実的な検知機会なし
    攻撃者側の基盤での準備であり、標的となる組織から観測できる段階ではない。 ドメインの新規登録や証明書の発行を広く監視する事業者側の層でのみ見える。
    検知できた自社を装うドメインの新規登録・証明書発行の監視（ブランド保護）
    初期侵入機会はあったが検知できず
    デバイスコード・フローによるサインインは、サインインログで フローの種別として識別できる。普段このフローを使っていない組織にとっては、 出現そのものが異常である。餌のメール側は、正規のクラウド基盤を経由し AI が個別化するため、文面や送信元での検知は分が悪い。
    侵入を防げた条件付きアクセスで、可能な限りデバイスコード・フローを遮断する（マイクロソフトの第一の助言）
    影響を限定できたTeams 機器等で必要な場合は、例外を当該機器の資源アカウントに限定し、デバイス登録サービスの資源を条件付きアクセスから除外する
    検知できたデバイスコード・フローによるサインインを監視対象にし、利用実績の無い組織では検知即対応とする
    認証情報アクセス機会はあったが検知できず
    トークンの発行そのものは正規の操作として記録される。 異常として立ち上がるのは、発行後の利用（所在地・端末・API の使い方）である。
    影響を限定できた侵害が疑われる場合はパスワードの変更だけでなく、セッションとリフレッシュトークンを失効させる
    影響を限定できた継続的アクセス評価（CAE）などで、条件の変化時にトークンを再評価する
    内部探索機会はあったが検知できず
    Graph API を介した組織情報の一括照会や、短時間での大量のメール参照は、 監査ログで異常として捉えうる。本件では、この層の検知が どの程度機能したかは公表されていない。
    検知できたGraph API の大量照会・ディレクトリの一括取得を監視項目にする
    検知できたメールボックスの一括参照・大量の検索操作を監査ログで監視する
    永続化機会はあったが検知できず
    受信トレイルールの作成・変更は監査ログに残る。 とくに「特定の差出人を削除・移動・既読化する」ルールは、 詐欺の進行を隠すために作られる典型である。
    検知できた受信トレイルールの作成・変更を監視し、隠蔽型のルール（削除・移動・既読化）を警報にする
    検知できた端末の登録・参加のイベントを監視し、想定外の端末の追加を検知する
    影響（暗号化・破壊・改ざん）機会はあったが検知できず
    支払い口座の変更依頼など、金銭の流れを変える要求は、 メールの外の経路（電話など既知の連絡先での確認）で止められる層である。 技術的な検知に頼り切らない運用の設計が要る。
    侵入を防げた振込先の変更は、メール以外の既知の連絡先への架電で必ず確認する運用にする
    影響を限定できた一定額以上の送金に複数名の承認を要求し、承認者のうち1名は依頼元と別経路で確認する

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • 「MFA を入れたから認証情報の攻撃は終わった」という整理を、いま更新する
      デバイスコード・フィッシングでは、利用者はパスワードを渡しておらず、 MFA も正しく完了している。それでもトークンが攻撃者に渡る。 マイクロソフト自身、組織の MFA 導入が進んだこの数年で トークンを狙う攻撃が一般化・産業化したとしている。
      取るべき行動 経営向けのリスク説明から「MFA により認証情報の窃取は対処済み」という記述を外し、 「トークンとセッションの保護」を独立した課題として予算と KPI を付ける。 直近の四半期の目標に、デバイスコード・フローの遮断状況を入れる。
    • 犯罪の能力がサービスとして売られる以上、「高度な攻撃は自社には来ない」は成り立たない
      EvilTokens は初期費用1,500ドル・月額500ドルで、約1,000人が使った。 AI による標的選定・なりすまし先の選定・詐欺の筋書きの提案まで含まれていた。 技術力の無い犯罪者が、高度な侵害後の作業を実行できる。
      取るべき行動 脅威モデルの前提を「標的型か否か」から「自社の規模でも採算が合うか」に切り替える。 1万超の組織が1〜2アカウントずつ侵害された本件の分布を、 中堅・中小規模の組織のリスク評価の根拠として使う。
    • 金銭被害の公表値は「確認できた下限」——自社の被害想定に使わない
      マイクロソフトは IC3 の13件・約170万ドルを関連づけつつ、 「多くの事案は報告されず、全ての被害者を特定の攻撃に確実に結びつけられるわけでもない。 これは控えめな見積もりである」と自ら注釈している。 1万2,000のメールボックスに対して13件という比は、報告と紐づけの限界を示す。
      取るべき行動 外部事例の被害額を自社のリスク算定に引くときは、 母数（何件中の何件か）と紐づけの方法を必ず併記する。 紐づけの根拠が示されていない数値は、根拠として採用しない。
    • テイクダウンは「この基盤が止まった」であって「手口が終わった」ではない
      マイクロソフトは2026年4月の時点で、デバイスコード・フィッシングに対応した 基盤が少なくとも10種類に増えていたとしている。EvilTokens はその1つである。 設計上の代償（認証の完了が別端末でよいこと）は残る。
      取るべき行動 摘発の報道を受けた社内共有では、「止まったもの」と「残るもの」を分けて書く。 残るもの（手口と設定の穴）に対して、自社で閉じる作業を期限つきで割り当てる。
    セキュリティ技術者への示唆
    • デバイスコード・フローの利用実績を調べ、使っていなければ塞ぐ
      マイクロソフトの第一の助言は「可能な限りデバイスコード・フローを遮断すること」である。 このフローを実際に必要とするのは、会議室の Teams 機器やサイネージなど 限られた用途で、多くの組織では「誰も使っていないのに開いている」状態にある。
      取るべき行動 サインインログでデバイスコード・フローの利用実績を過去90日ぶん集計する。 実績が無ければ条件付きアクセスで遮断する。実績があれば、 どの機器・どのアカウントかを特定してから例外の範囲を決める。
    • 例外の作り方まで踏み込む——「Teams 機器があるから遮断できない」で止めない
      マイクロソフトは「Teams 機器が必要とする場合は、例外を特定の Teams 機器の 資源アカウントに絞り、条件付きアクセスポリシーからデバイス登録サービスの資源を 除外すること」（原文英語）と具体的に示している。全体を開けたままにする必要はない。
      取るべき行動 例外の対象とする資源アカウントを台帳にし、機器の入れ替え時に見直す運用を作る。 例外の数と対象を四半期ごとに棚卸しし、増え続けていないかを確認する。
    • 検知の重心を「認証の後」に置く
      餌のメールは AI で個別化され、経由地は正規のクラウド基盤で、 利用者が入力するのは本物のログイン画面である。入口での識別は分が悪い。 一方、受信トレイルールの作成、Graph の一括照会、想定外の端末の追加は いずれも監査ログに残り、正規の業務との区別がつけやすい。
      取るべき行動 ①デバイスコード・フローのサインイン ②隠蔽型の受信トレイルールの作成 ③Graph による組織情報の一括照会 ④端末の新規登録、の4つを検知ルールとして実装し、 自社のログで同じ問いが立てられるかを確認する。 マイクロソフトが公開したハンティングクエリを出発点にする。
    • 侵害の後始末を「パスワード変更」で終わらせない
      窃取されたのはトークンであり、パスワードではない。 EvilTokens はトークンの自動更新機能を備えていた。 パスワードを変えてもセッションが生きていれば、攻撃者のアクセスは続く。
      取るべき行動 アカウント侵害時の手順書に「セッションとリフレッシュトークンの失効」 「受信トレイルールの確認と削除」「登録端末の確認」を必須項目として加える。 手順を実機で一度実施し、所要時間を測っておく。

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    認証・認可□ Microsoft 365（Entra ID）を利用しており、デバイスコード・フローを条件付きアクセスで遮断していない本件の攻撃連鎖の入口そのものである。遮断していなければ、 利用者が正規のログイン画面でコードを入力するだけで攻撃者のセッションが認可される。
    認証・認可□ デバイスコード・フローの利用実績を、サインインログで即座に示せない遮断の可否は利用実績で決まる。実績が分からなければ、 遮断も例外の設計もできず、「念のため開けたまま」になる。
    運用・監視□ 受信トレイルールの作成・変更を監視していない通信を隠す受信トレイルールは、侵害後の居座りと詐欺の進行に使われる。 監視していなければ、本人も気づかないまま関係者が騙され続ける。
    運用・監視□ アカウント侵害時の手順が「パスワードの変更」で終わっており、セッションとトークンの失効を含まない窃取されたのはトークンであり、パスワードの変更では攻撃者のアクセスは切れない。
    体制・契約□ 振込先の変更を、メールのやり取りだけで確定できる運用になっている本件の出口は BEC による金銭の詐取である。メール以外の既知の連絡先での 確認を挟まなければ、AI が生成した文脈に合う文面を見抜くことは難しい。
    システム構成□ Vercel・Cloudflare Workers・AWS Lambda など正規のクラウド基盤への通信を、宛先の評判だけで判断しているEvilTokens はこれらの正規基盤を経由地に使っていた。 評判ベースの遮断では、正規の業務利用と攻撃の経由を区別できない。
