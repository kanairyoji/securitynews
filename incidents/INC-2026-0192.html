INC-2026-0192WordPress にコメント経由のRCE

WordPress コアに、匿名の訪問者が投稿したコメント1件でスクリプトを仕込める保存型クロスサイトスクリプティング（CVE-2026-93485・通称 Comment2Shell）が見つかり、2026年9月17日の 7.1.1 で修正された——コメントは保存時の検査（KSES）を通るが、表示時の整形（wpautop）が引用符で囲まれた属性値の中の改行を扱えず、良性の HTML がその場で動くイベントハンドラに変わる。ログイン中の管理者がそのページを開くと、管理者のセッションでプラグインを導入でき、Web シェルによるサーバ上のコード実行にまで届く。影響は 4.7 から 7.1 までの約10年分の版におよび、既定の「コメント承認」は迂回できる経路が複数ある

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年9月17日 最終更新: 2026年9月23日

WordPress は 2026年9月17日、保守とセキュリティのリリース 7.1.1 を公開し、11件のセキュリティ修正を入れました。そのうち1件が、アカウントを持たない攻撃者が到達できる唯一のもの（The Hacker News）にあたります。

WordPress 自身の記述は次のとおりです（原文英語）。

wpautop() における保存型クロスサイトスクリプティングにより、認証されていない訪問者がスクリプトを注入できる（コメントの承認を条件とする）。報告者は Rafie Muhammad（Awesome Motive, Inc.）。

識別子は CVE-2026-93485（採番は Patchstack・CVSS 3.1 で 7.1・CWE-79）、研究者が付けた通称は Comment2Shell です。

仕組みは「2つの処理のすき間」です。WordPress はコメントを保存するときに危険な HTML を落とし（KSES と呼ばれる処理）、表示するときに段落などへ整形します（wpautop()）。Patchstack の解説によれば、wpautop() の正規表現は引用符で囲まれた属性値の中にある「>」を認識できず、タグが途中で分断されます。その結果、攻撃者が仕込んだ文字列がブラウザから見ると「その場で動くイベントハンドラ」の位置へ移動します。皮肉なことに、攻撃の成立に必要な文字列（属性値の中の改行を --> へ変える変換）はKSES 側が供給していました。

スクリプトはページを読み込んだだけで動き、クリックは要りません。動くのは開いた人の権限で、ログイン中の管理者が開いた場合は、その管理者のセッションを使ってプラグインを導入でき、Web シェルを置けばサーバ上のコード実行に届きます。

影響範囲は 4.7 から 7.1 までで、修正は 7.1.1・7.0.5・6.9.8 と、セキュリティ修正の対象である全ブランチ（4.7.36 まで遡る）へバックポートされました。既定では新規投稿者のコメントは承認待ちになりますが、Patchstack は「モデレーションはセキュリティ機能ではない」（原文英語）とし、研究者は承認を経ずにページへ載せる経路を複数示しています。2026年9月23日時点で悪用の報告はなく、CISA の KEV カタログにも収載されていません。

匿名コメント1件がページに載るだけで動くスクリプトになった——クリックは要らない概観出典 [1] [2] [3]

WordPress 7.1.1（2026年9月17日）のセキュリティ修正一覧に載った本件の記述は次のとおりである（原文英語）。

Stored cross-site scripting in wpautop() allows an unauthenticated visitor to inject script (subject to comment approval), reported by Rafie Muhammad (Awesome Motive, Inc.).

（訳: wpautop() における保存型クロスサイトスクリプティングにより、認証されていない訪問者がスクリプトを注入できる（コメントの承認を条件とする）。報告者は Rafie Muhammad）

識別子と評価は次のとおりである。

  • CVE-2026-93485（採番機関は Patchstack、公開は2026年9月18日）
  • CWE-79（ウェブページ生成時の入力の不適切な無害化）
  • CVSS 3.1 で 7.1（AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:L）
  • 影響範囲は WordPress 4.7 から 7.1 まで（7.1 は 7.1.1 未満、7.0 は 7.0.4 以下、6.9 は 6.9.7 以下……とブランチごとに範囲がある）
  • 通称は研究者が付けた Comment2Shell

攻撃の入口は通常のコメントフォームである。アカウントは不要で、仕込まれたスクリプトはページが読み込まれた時点で動く。クリックなどの操作は要らない。スクリプトはそのページを開いた人の権限で動くため、閲覧者が管理者であれば管理者の権限で動く。

保存時の検査と表示時の整形のすき間で、良性の HTML がイベントハンドラに変わった原因・手口出典 [3] [5]

WordPress はコメントを扱うときに2つの処理を通す。

  1. 保存するとき——KSES（コメントの無害化処理）が、許可されていない HTML を落とす（サニタイズ）
  2. 表示するとき——wpautop() などが、改行を段落やタグへ整形する

Patchstack の解説によれば、本件はこの2つのすき間にあった。

  • 攻撃者は、許可されている HTML タグの属性値の中に改行を置いたコメントを投稿する
  • KSES は素通しする。そこには「落とすべき危険な記法」が何も無いためである。しかも KSES はプレースホルダー変換の過程で、属性値の中の改行を --> に変える—— 攻撃に必要な文字を WordPress 自身が供給していた
  • 表示時、wpautop() の正規表現は引用符で囲まれた属性値の中の「>」を認識できず、タグを途中で分断する。分断の結果、攻撃者の文字列がブラウザからはその場で動くイベントハンドラに見える位置へ移る

研究者の解説では、blockquote の cite 属性に置いた改行が KSES を通り、wpautop() や wptexturize() を含む整形の連鎖を経て JavaScript の実行に至る、と説明されている。

表示側には条件がある。ブロックテーマ（Twenty Twenty-Two 以降の WordPress の既定）は該当し、同じ整形処理でコメントを出すクラシックテーマも該当する（研究者の解説は Twenty Twenty-One を挙げる）。

注目すべきは、攻撃者が「危険な入力」を送っていないことである。送ったのは許可された HTML であり、それを危険に変えたのは WordPress 自身の整形処理だった。

コード実行に必要な最後の1手は「管理者がそのページを開くこと」——そこからプラグイン導入で Web シェルが置ける被害規模・影響範囲出典 [2] [3] [5] [6]

スクリプトが動いた先の話である。

スクリプトは開いた人の権限で動く。ログインしていない訪問者が開けば、その訪問者のブラウザで動くだけである。しかしログイン中の管理者が同じページを開いた場合、スクリプトは管理者のセッションを使ってプラグインを導入できる。導入するプラグインに Web シェル（攻撃者が送ったコマンドを実行する小さなファイル）を含めれば、サーバ上での任意のコード実行に届く。

「管理者のブラウザからプラグインを入れてサーバを取る」という経路自体は以前から知られたもので、本件に固有のものではない。本件が新しいのは、その最初の1手を、アカウントを持たない誰もが、コメントフォームから打てたという点にある。

公開された CVSS（7.1）は、この最後の段階までを織り込んだ評点ではない。ベクタは機密性・完全性・可用性への影響をいずれも「低」としており、スコープの変化（S:C）でブラウザ側の影響を拾っている形である。数字だけを見て「中程度」と判断すると、到達点を見誤る。

「コメント承認」は迂回できる——モデレーションをセキュリティ機能として数えない対策・注意喚起出典 [1] [3] [5] [6] [7]

WordPress の記述には「コメントの承認を条件とする」という但し書きが付いている。既定では、初めて投稿する人のコメントは承認待ちになり、そのままではページに出ない。しかし Patchstack は「モデレーションはセキュリティ機能ではない」（原文英語）と書き、研究者は承認を経ずにページへ載せる経路を3つ挙げている。

  1. WordPress にあらかじめ用意されている「A WordPress Commenter」アカウントでの投稿
  2. コメント承認の設定が無効にされている場合
  3. 承認待ちのコメントが、以前にコメントした人には見える性質を使い、細工したリンクで開かせる

加えて、一度承認された投稿者のコメントは以後自動で承認される（既定の挙動）。つまり「無害なコメントを1回通しておく」だけで、以後の投稿は審査を経ずに載る。

対処は更新である。

  • 7.1 系は 7.1.1、7.0 系は 7.0.5、6.9 系は 6.9.8 へ。古いブランチも 4.7.36 まで遡って修正が出ている
  • 自動バックグラウンド更新に対応しているサイトは、更新が自動で始まる
  • すぐに更新できない場合は、投稿のコメントを閉じる／サイト全体でコメントを止めることで入口を塞げる。WAF やセキュリティプラグインが当該コメントを弾く場合もある
  • 更新は、すでに加えられた変更を元に戻さない。 狙われた可能性があるサイトは、見覚えのないプラグインやファイルの有無を確認する必要がある

なお WordPress は 9月22日に 7.1.2 を出している。こちらは本件とは別の脆弱性（CVE-2026-87902・未認証のローカルファイル取り込み）の修正で、7.1.1 も影響を受ける。9月17日に更新したサイトも、5日後にもう一度更新する必要があった。

「入力の無害化」と「出力の整形」を別々のチームが持つと、すき間は誰の担当でもなくなる（本記録の評価）評価・解釈出典 [3] [5]

ここからは本記録の作成者の評価である。

本件の教訓は WordPress に限らない。保存時に無害化し、表示時に整形するという設計はごく一般的で、自前のアプリケーションでも普通に採られている。問題は、

  • 無害化の担当は「危険な記法を落とせばよい」と考える
  • 整形の担当は「渡ってくるのは無害化済みのデータだ」と考える

という前提が、両者のあいだで一度も突き合わされないことにある。本件では、無害化を通った良性の HTML を、整形処理が危険なものへ作り変えた。さらに、攻撃に必要な文字列を供給したのは無害化処理そのものだった。どちらの処理も単体では「正しく」動いている。

実務に落とすと次の2点になる。

  1. 無害化したデータを後から書き換える処理を、無害化と同じ強度で検査する。段落整形・タイポグラフィ変換・埋め込み展開・翻訳・要約など、「表示のために整える」処理はすべてこの位置にある
  2. 最終的にブラウザへ届く文字列で検査する。 中間の状態で「安全だ」と確認しても、その後の変換が安全性を壊す。テストは入口ではなく出口に置く

加えて本件は、「承認」「レビュー」「人の目」を安全装置として数えることの危うさも示している。コメント承認は本来スパム対策であって、攻撃対策として設計されていない。同じことは、社内の承認フロー・コードレビュー・投稿前チェックにも当てはまる。運用上の手続きを、技術的な統制の代わりに置かない。

事案の詳細

cves
id: CVE-2026-93485　cvss: 7.1　概要: WordPress コアの wpautop() における保存型クロスサイトスクリプティング（CWE-79）。 認証されていない訪問者が投稿したコメントが、表示時の整形処理でイベントハンドラへ変換され、 ページの読み込みだけで実行される。ログイン中の管理者が開いた場合は、 管理者セッションでのプラグイン導入を経てサーバ上のコード実行に至りうる。 採番は Patchstack、CVSS 3.1 で 7.1、通称 Comment2Shell。　exploited: いいえ
affected_versionsWordPress コア 4.7 から 7.1 まで（7.1 は 7.1.1 未満、7.0 は 7.0.4 以下、6.9 は 6.9.7 以下など ブランチごとに範囲がある）。修正版は 7.1.1・7.0.5・6.9.8 ほか、セキュリティ修正の対象である 全ブランチへ 4.7.36 まで遡ってバックポートされている。 表示側の条件として、ブロックテーマ（Twenty Twenty-Two 以降の既定）、 および同じ整形処理でコメントを表示するクラシックテーマ（例: Twenty Twenty-One）が対象になる。
exploitation_status実際の悪用は確認されていない。The Hacker News は2026年9月22日時点で 「攻撃に使われた形跡は無く、米政府の実際に悪用された脆弱性の一覧にも入っていない」としている。 本記録の作成者が2026年9月23日に取得した CISA の KEV カタログ（2026.09.22 版・1,721件）にも CVE-2026-93485 は収載されていない。 なお、同じ 7.1 系で9月22日に修正された別の脆弱性（CVE-2026-87902）については、 パッチ公開から5時間以内に探索行為が観測されたと Patchstack が報告している（本件とは別の脆弱性）。
緩和策
item: WordPress を 7.1.1（各ブランチの修正版）へ更新する　副作用: コアの更新でテーマ・プラグインとの相性問題が出る可能性がある。 なお9月22日に 7.1.2 が出ているため、9月17日以降に 7.1.1 へ上げたサイトも 5日後に再度の更新が必要になった
item: 投稿のコメントを閉じる、またはサイト全体でコメントを止める　副作用: 読者との双方向のやり取りが失われる。既存のコメントの表示をどうするかの判断も要る
item: コメント承認の運用を見直す（自動承認を止める）　副作用: モデレーションの負荷が増える一方で、迂回経路があるため防御としては不完全である
item: 管理者アカウントで日常的にサイトを閲覧しない（管理用と閲覧用を分ける）　副作用: 運用の手間が増え、コメント確認などの日常業務の動線が変わる
item: 管理画面からのプラグイン導入・ファイル編集を禁止する設定にする　副作用: プラグインの更新・導入を配備の仕組み側で行う必要があり、緊急時の対応手順を用意しておかないと かえって更新が遅れる

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
匿名コメントの投稿から、表示時の整形によるスクリプト実行を経てサーバ上のコード実行に至る経路
layer 0 は攻撃者と公開されているコメントフォーム。layer 1 は保存時の無害化（KSES）と 保存されたコメント、表示時の整形（wpautop）。layer 2 はイベントハンドラとして実行される スクリプトと、それを開いた管理者、管理者セッションで導入されるプラグイン、そして Web シェル。 右側は修正（7.1.1 以降）。コメント承認は経路上にあるが迂回可能であることを示す。 サーバ上のコード実行まで至った事例は公表されていない。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入機会はあったが検知できず
コメントはデータベースに保存され、管理画面でも読める。ただし見た目は 通常の HTML であり、危険な記法が含まれていないため、人の目でも スパムフィルタでも異常として拾いにくい。
侵入を防げたコメントを閉じる（投稿単位またはサイト全体）
影響を限定できたWAF やセキュリティプラグインで当該パターンのコメントを弾く
実行現実的な検知機会なし
実行されるのは閲覧者のブラウザであり、サーバ側のログには通常のページ表示としか残らない。 Content-Security-Policy を設定していれば、インラインのイベントハンドラの実行を 止められる可能性があるが、WordPress の既定では設定されていない。
侵入を防げたWordPress を 7.1.1（または各ブランチの修正版）へ更新する
影響を限定できたインラインスクリプトを禁じる Content-Security-Policy を設定する
権限昇格機会はあったが検知できず
プラグインの新規導入は管理画面の操作としてサイト上に痕跡が残り、 ファイル変更監視を入れていれば検知できる。既定では通知も監査ログも無い。
影響を限定できた管理者アカウントでの日常的なサイト閲覧を避ける（管理作業用と閲覧用を分ける）
侵入を防げた管理画面からのプラグイン導入・ファイル編集を禁止する（DISALLOW_FILE_MODS 等）
検知できたファイル変更監視と管理操作の監査ログを入れる
影響（暗号化・破壊・改ざん）公表されていない
WordPress も Patchstack も、修正前に仕込まれたコメントや不正なプラグインを 検出する公式の手順を示していない。事後確認は運営者側の資産（ファイル一覧・ プラグイン一覧・Web サーバのログ）に依存する。
検知できた見覚えのないプラグイン・ファイルの有無を確認する（更新は既存の改変を元に戻さない）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • CMS のコア更新を「月次のパッチ作業」ではなく、公開当日に動く対象として扱う
    本件は認証不要でコメントフォームから到達でき、影響範囲は 4.7 から 7.1 までの約10年分の版に及ぶ。 さらに WordPress は9月17日の 7.1.1 に続いて9月22日に 7.1.2 を出しており、 月次の定例作業では2回とも取り逃す
    取るべき行動 自社サイト・関係会社サイト・キャンペーンサイトの WordPress の版と自動更新の設定を棚卸しし、 コアのセキュリティリリースは公開当日に適用する運用（または自動更新の有効化）へ切り替える
  • 「人の承認」を技術的な安全装置として数えない
    WordPress の記述は「コメントの承認を条件とする」だが、Patchstack は 「モデレーションはセキュリティ機能ではない」とし、迂回経路が複数示されている。 一度承認された投稿者は以後自動承認される点も効いている
    取るべき行動 自社の統制一覧から「承認・レビュー・目視確認」に依存している項目を抜き出し、 迂回されたときに何が起きるかを1つずつ確認する。技術的な統制で置き換えられるものは置き換える
  • 委託先が構築・運用しているサイトについて、更新の責任が誰にあるかを契約で確認する
    WordPress サイトは制作会社が構築し、更新は誰も担当していないという状態になりやすい。 本件の修正は 4.7 まで遡って出ているが、適用されなければ意味が無い
    取るべき行動 保守契約の範囲に「コアのセキュリティリリースの適用」と「適用の報告」が含まれているかを確認し、 含まれていない場合の担当を決める。休眠サイト・キャンペーンサイトも対象に入れる
  • 更新だけでは終わらない——「更新は既存の改変を元に戻さない」ことを手順に書く
    すでにコメントが仕込まれ、管理者が開いていた場合、更新後も不正なプラグインやファイルは残る。 公式には事後確認の手順が示されていない
    取るべき行動 脆弱性対応の手順に「更新後の確認」（プラグイン一覧・管理者アカウント一覧・ ファイル変更の有無・直近のコメント）を明記し、誰がどこまで見るかを決める
セキュリティ技術者への示唆
  • 無害化（サニタイズ）を通ったデータを、後段の整形処理が書き換えていないかを見る
    本件は KSES を通った良性の HTML を、表示時の wpautop() が分断して イベントハンドラに変えた。しかも攻撃に必要な文字列は KSES 側が供給していた。 どちらの処理も単体では正しく動いている
    取るべき行動 自社アプリで「保存時に無害化し、表示時に整形する」構造になっている箇所を洗い出し、 整形処理の入出力に対するテストを、XSS の観点で追加する
  • 検査は入口ではなく、ブラウザへ届く最終出力に置く
    中間の状態で安全を確認しても、その後の変換が安全性を壊す。 本件は「保存されたデータ」を見る限り危険に見えない
    取るべき行動 レンダリング後の HTML を対象にした自動テスト（イベントハンドラ属性や javascript: スキームの出現を検出する）を継続的インテグレーションへ入れる
  • 管理者セッションでの閲覧を減らし、管理画面からの変更経路を塞ぐ
    本件がサーバ上のコード実行に届く最後の1手は「ログイン中の管理者がページを開くこと」と 「管理者セッションでプラグインを導入できること」である
    取るべき行動 管理作業用と閲覧用のアカウントを分ける。本番では DISALLOW_FILE_MODS 等で 管理画面からのプラグイン導入・ファイル編集を止め、配備の仕組み経由でのみ変更する
  • Content-Security-Policy でインラインのイベントハンドラを止める
    本件の実行はページ内のインラインイベントハンドラとして起きる。 WordPress の既定では CSP は設定されない
    取るべき行動 公開サイトに CSP を導入し、インラインスクリプトとイベントハンドラを禁じる。 既存テーマ・プラグインの動作確認を伴うため、report-only から段階的に進める
  • コメント・問い合わせなど「匿名の入力が保存されて後で表示される」経路を棚卸しする
    保存型 XSS は、入力した本人ではなく後で見る人（多くは管理者）に当たる。 本件はその典型で、入口は最も無防備な公開フォームだった
    取るべき行動 匿名入力が保存され管理画面で表示される経路（問い合わせ・応募・アンケート・レビュー）を列挙し、 管理画面側の表示でもエスケープが効いているかを実際の値で確認する

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ WordPress 4.7〜7.1 のコアを使い、投稿へのコメントを受け付けている入口は通常のコメントフォームで認証は不要。表示側はブロックテーマ（近年の既定）が該当する
運用・監視□ コアの自動バックグラウンド更新を無効にしている、または更新を月次の作業にしている7.1.1（9月17日）と 7.1.2（9月22日）は5日違いで出ており、定例作業では両方を取り逃す
運用・監視□ 管理者アカウントで日常的にサイトの公開ページを閲覧しているサーバ上のコード実行に届く条件が「ログイン中の管理者が当該ページを開くこと」である
認証・認可□ 管理画面からのプラグイン導入・ファイル編集を許可したままにしている管理者セッションを奪われたときに、そのままサーバ上のコード実行へつながる
体制・契約□ サイトの制作・運用を委託しており、コア更新の責任範囲を契約で確認していない休眠サイトやキャンペーンサイトは更新の担当が不在になりやすい
データの保持□ 自社アプリで、保存時に無害化し表示時に整形する構造の処理を持っている本件の原因は個々の処理の誤りではなく、無害化と整形のあいだのすき間だった
