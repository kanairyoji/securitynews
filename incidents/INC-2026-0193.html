INC-2026-0193WordPress 7.1.2 で未認証LFI修正

WordPress コアのページテンプレート解決に、認証を持たない攻撃者がテーマの外にある読み取り可能な PHP ファイルを読み込ませられる欠陥（CVE-2026-87902）が見つかり、2026年9月22日の 7.1.2 で修正された——サーバ環境とテーマの前提が揃うとコード実行にまで届く。影響は 4.7.0 から 7.1.1 までで、5日前に出たばかりの 7.1.1 も対象に含まれる。Patchstack は修正公開当日の11時49分（UTC）に最初の悪用試行を観測し、同日15時34分（UTC）には PEAR の pearcmd.php を使ってサーバ上へファイルを書き込む試みが始まった。翌23日にはトラフィックが初日の10倍を超え、Patchstack は「探索から実際の侵害へ移った」と述べている。WordPress の自己評価は CVSS 4.0 で 9.2（Critical）、CVE を採番した HackerOne の評価は CVSS 3.1 で 8.1 と割れている。CISA は9月25日に KEV カタログへ収載し（連邦政府機関の是正期限は9月28日・フォレンジック・トリアージの対象）、CrowdSec は9月23日から27日の5日間で一致する要求 322,680件・一意の IP アドレス 30,813件（9月28日時点）を記録した——ただし同社は「一致した要求は試行であり、成功したものを確認できない」と明記している。国内ではエックスサーバーが9月24日に注意喚起を出し、9月25日の21時ごろから22時ごろにかけて「攻撃成立条件に該当するサイト」の WordPress 本体を事業者側で更新した

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年9月22日 最終更新: 2026年10月3日

WordPress は 2026年9月22日、セキュリティのみのリリース 7.1.2 を公開しました。修正は1件、CVE-2026-87902（GHSA-7hp8-65ch-5whp）です。

WordPress 自身の記述は「認証されていない攻撃者が、特定の条件下でページテンプレートの解決を操作し、有効なテーマのフォルダの外にある読み取り可能なローカルの PHP ファイルを取り込ませられる。サーバ環境とテーマの前提が満たされた場合、リモートコード実行につながりうる」（原文英語）です。深刻度は Critical としています。

影響範囲は 4.7.0 から 7.1.1 まで。5日前（9月17日）に出たばかりの 7.1.1 も含まれます。修正はブランチごとに 7.1.2／7.0.6／6.9.9／6.8.10／6.7.9／6.6.9 と出され、セキュリティ修正の対象である全ブランチへ 4.7.37 まで遡ってバックポートされました。

仕組みはパス・トラバーサルです。発見者 Robert Ressl の解説によれば、ページテンプレートを決める処理は、リクエストのクエリ変数（pagename）からpage-{値}.php という名前を組み立てます。この値が、隣接するコードが使っているパスの検査を通っていませんでした。二重にエンコードされたトラバーサルは最初の処理を素通りし、後段のデコードで区切り文字として効きます。

ただし読み込めるのはサーバ上に既にある .php ファイルで、それが「読み込まれると何か役に立つことをする」ファイルでなければコード実行にはなりません。Ressl の実証では、PHP の設定register_argc_argv が有効で、PEAR の実行用ファイルが読み取り可能という条件のもとで、2回のリクエストに分けてコード実行を成立させています（隔離したラボ3環境・WordPress 7.0.2・実行権限は Web サーバのアカウント）。実サイトでの検証は行っていないと明記されています。

評点は割れています。 WordPress と発見者は CVSS 4.0 で 9.2（Critical）、CVE を採番した HackerOne は CVSS 3.1 で 8.1 としています。

そして Patchstack は、修正公開と同じ日に悪用の試行を観測しました。同社の時系列では、9月22日11時49分（UTC）に最初の試行（wp-links-opml.php など標準ファイルを読ませる確認行為）を遮断し、同日15時34分（UTC）にはPEAR の pearcmd.php を使ってディスクへファイルを書き込む最初の試みが現れています。

1日で段階が変わりました。 9月23日の更新で Patchstack は、「このCVEに対するトラフィックは初日の夜に見た量の10倍以上で動いており、はるかに広い範囲のサイトに届いている」「探索から実際の侵害へ移った」（いずれも原文英語）と述べています。書き込み先は /tmp と /var/tmp で、luci_<乱数>.php・zeta_<乱数>.php・wp-pear-rce-flag.php といった名前が観測されました。アクセスされるとシェルコマンドを実行する短いタグが書き込まれています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

認証を持たない攻撃者が、公開されているページの URL（クエリ変数 pagename）に 二重エンコードしたトラバーサルを入れてリクエストする。WordPress はその値から page-{値}.php というテンプレート候補名を組み立てるが、パスの検査を通していないため、 有効なテーマのフォルダの外にある読み取り可能な PHP ファイルが取り込まれる。 取り込まれたファイルが「読み込まれた時点で何かをする」もの（PEAR の実行用ファイルなど）で、 かつ PHP の register_argc_argv が有効であれば、2回のリクエストに分けてコード実行に至りうる。 実証は隔離したラボでのみ行われ、実サイトでの侵害は公表されていない。

    テンプレート候補名 page-{値}.php の組み立てにパスの検査が無いため、 有効なテーマのフォルダの外にある読み取り可能な PHP ファイルが取り込まれる。 成立には、有効なテーマの直下に page- で始まるフォルダがあること、 匿名でアクセスできる公開ページがあり、カスタムテンプレートが割り当てられていないことが要る。
    根拠: WordPress のリリース告知／発見者の技術解説／CVE レコード（CWE-98）
  3. 3. 実行確認済[3] [4]
    取り込まれた PHP ファイルが「読み込まれた時点で何かをする」ものである場合に実害が出る。 発見者の実証では、PEAR の実行用ファイルを取り込ませて攻撃者の制御下にある PHP ファイルを生成し （1回目）、次にそのファイルを本件の欠陥経由で取り込ませた（2回目）。 PHP の register_argc_argv が有効であることが条件である。

5日前に出たばかりの 7.1.1 も対象——認証不要でテーマ外の PHP ファイルを読み込ませられる概観出典 [1] [2] [6]

WordPress 7.1.2（2026年9月22日）はセキュリティのみのリリースで、修正は1件である。

  • CVE-2026-87902（GHSA-7hp8-65ch-5whp）、WordPress の評価は Critical
  • 説明は「認証されていない攻撃者が、特定の条件下でページテンプレートの解決を操作し、有効なテーマのフォルダの外にある読み取り可能なローカルの PHP ファイルを取り込ませられる。サーバ環境とテーマの前提が満たされた場合、リモートコード実行につながりうる」（原文英語）
  • 影響は 4.7.0 から 7.1.1 まで
  • 修正は 7.1.2／7.0.6／6.9.9／6.8.10／6.7.9／6.6.9、さらにセキュリティ修正の対象である全ブランチへ 4.7.37 まで遡ってバックポート
  • 自動バックグラウンド更新に対応しているサイトでは、更新が自動的に始まる
  • 謝辞は Robert Ressl（責任ある開示に対して）

注意が要るのは日付である。WordPress は9月17日に 7.1.1 を出したばかりだった（11件のセキュリティ修正・うち1件が匿名コメント経由の保存型 XSS）。その 7.1.1 も本件の影響を受ける。 定例の更新作業を月1回にしている運用では、9月の2本のうちどちらか、あるいは両方を取り逃すことになる。

組み立てたテンプレート名がパスの検査を通っていなかった——読み込めるのは「既にあるファイル」だけ原因・手口出典 [3] [4]

発見者 Robert Ressl の技術解説によれば、欠陥はページテンプレートを決める処理にある。

  • WordPress は、リクエストのクエリ変数（pagename・page_id。匿名の POST でも受け付ける）からテンプレート候補の名前 page-{値}.php を組み立てる
  • 二重にエンコードされたトラバーサル（%252e%252e のような形）は最初の処理を素通りし、後段のデコードでディレクトリの区切りとして効く
  • 組み立てた名前が、隣の行のコードが使っているパスの検査を通っていなかった
  • 「正規化」と「封じ込め」は別物である——発見者の言葉では「パスの正規化は行き先を決めるが、その行き先がテーマのフォルダ内にとどまることは保証しない」（原文英語）

Patchstack の解説によれば、7.1.2 の修正は2段構えである。①該当する値にパスの検査を追加し、②解決されたテンプレートのパスが許可されたフォルダ内にあることを確かめる仕組みを新設した。

ここまでは「ファイルの取り込み」であって、コード実行ではない。読み込まれるのはサーバ上に既に存在する .php ファイルであり、そのファイルが「読み込まれた時点で何か役に立つことをする」ものでなければ実害は小さい。WordPress の説明にある「一部のサーバでは」はこの意味である。

コード実行に必要な前提は2つ——テーマの「page-」フォルダと、PHP の register_argc_argv被害規模・影響範囲出典 [3] [4] [6]

発見者がラボで成立させた連鎖には、次の前提が要った。

WordPress 側

  • 有効なテーマの直下に「page-」で始まるフォルダがあること（例: page-templates/）。古い既定テーマなどが該当し、現行の既定テーマは該当しない
  • 匿名でアクセスできる公開済みのページがあること
  • そのページにカスタムテンプレートが割り当てられていないこと

サーバ側

  • PEAR の実行用ファイル（pearcmd.php）が読み取り可能であること
  • PHP の設定 register_argc_argv が有効であること
  • PEAR の出力先が書き込み可能であること

連鎖は2回のリクエストに分かれる。1回目で PEAR の入口を取り込ませて攻撃者の制御下にあるPHP ファイルを生成させ、2回目でそのファイルを本件の欠陥経由で取り込ませる。実証は隔離したラボ3環境・WordPress 7.0.2 で行われ、実行権限は Web サーバのアカウント、OS の権限昇格は実証されていない。発見者は実サイトでは検証していないと明記している。

Patchstack は、サイト運営者が自分の露出度を測る2つのチェックとして「有効なテーマに page- で始まる直下フォルダがあるか」「PHP の register_argc_argv が有効か」を挙げ、どちらも修正ではないと断っている。register_argc_argv は PHP 8.5 で既定が無効、それ以前のバージョンでは既定が有効で、Patchstack は「既定の Docker イメージや cPanel 環境で一般的」と指摘している。

ここからは本記録の作成者の評価である。

本件の評点が 9.2（WordPress・CVSS 4.0）と 8.1（HackerOne・CVSS 3.1） で割れているのは、「前提条件の多さをどう数えるか」の違いに見える。しかし運用側にとって重要なのはどちらの数字でもなく、自社が前提を満たしているかどうかである。

本件の前提は、調べられる形になっているという点で珍しい。

  • 有効なテーマの直下に page- で始まるフォルダがあるか——ファイル一覧を見れば分かる
  • PHP の register_argc_argv が有効か——設定を1つ見れば分かる

どちらも数分で確認でき、結果は「更新を今夜やるか、週末でよいか」という判断に直結する。脆弱性情報を読んだあとに、自社の条件を実際に確認する工程を持っているかどうかが、優先度付けの精度をそのまま決める。

同時に、「条件が揃わないから安全」と結論を止めないことも要る。条件はテーマの入れ替えやホスティングの移行で変わる。本件では、更新そのものが2段構えの防御（パスの検査の追加と、テンプレートのパスが許可された場所にあるかの確認）を入れており、条件に依存しない対処は更新だけである。

もう1つ、PEAR のような「入っているが使っていない部品」の扱いも本件の論点である。発見者は、直ちに更新できない場合の緩和として register_argc_argv の無効化と使っていない PEAR 構成要素の削除を挙げている（いずれも欠陥自体は直さない）。サーバ上に残っている未使用の実行可能なファイルは、単体では無害でも、ファイル取り込みの欠陥と組み合わさると部品として使われる。

侵害の有無・前提に当てはまるサイトの割合・探索主体はいずれも公表されていない未確定事項出典 [1] [5] [6] [7]

  • 前提条件に当てはまるサイトの割合（該当テーマの数、register_argc_argv が有効な環境の割合）

経過は次のとおりです。

  • 9月24日: 注意喚起を公表（エックスサーバー・XServer ビジネス・XServer for WordPress）。「現時点では、弊社サービスにおいて本脆弱性を悪用した被害は確認しておりません」としつつ、自動更新を有効にしている場合も管理画面で完了を確認するよう求めた

  • 9月25日 21時ごろ〜22時ごろ: 「現時点で判明している攻撃成立条件に該当する WordPress サイト」について、事業者側で WordPress 本体を各系統の最新版へ更新した

  • 更新を完了できなかった場合は、その利用者にメールで個別に案内し、利用者自身での更新を依頼

  • 条件に該当しないサイトは更新の対象外。同社は新たな攻撃手法が公開される可能性もあるとして、利用者自身での更新を引き続き求めている

ここには共用ホスティングを使う側が知っておくべき前提が2つあります。

1つは、事業者が利用者のサイトのコアを更新しうるということです。本件では個別の同意を取らずに実施されています。更新で表示や動作が壊れる可能性は利用者側に残ります——同社は更新後にサイトの表示・動作を確認するよう求めています。

もう1つは、対象が「攻撃成立条件に該当するサイト」に絞られていることです。条件の判定は同社が行い、その基準は公表されていません。つまり「事業者が見てくれたから大丈夫」とは言えません。条件は後から広がりえます（同社自身がそう述べています）。自社サイトの版を自分で確認する必要は消えません（本記録の評価）。

なお公的機関の動きとしては、JVN iPedia が JVNDB-2026-035982 としてCVSS v3 基本値 8.1 で掲載（最終更新9月29日）、JPCERT/CC が9月30日の Weekly Report【7】で「特定の構成で WordPress を使用している場合、遠隔の第三者が認証不要でコードを実行する可能性があります」として取り上げ、Patchstack が悪用を確認していることを紹介しています。

  • アクセスログを「応答の中身」の観点でも確認できるようにしておく
    探索行為はページ URL への通常のリクエストに見える。 Patchstack は、ページ URL に対して想定外のファイルの中身が返っていないかを勧めている
    取るべき行動 応答サイズ・応答内容の異常（PHP ソースや設定ファイルの断片）を検出できるよう、 ログの保持期間と項目を見直す
