INC-2026-0194Arista VCO にゼロデイ悪用

多拠点の SD-WAN を一手に配る Arista VeloCloud Orchestrator（オンプレ版）に入力検証の不備（CVE-2026-93952・CVSS v3.1 で満点の 10.0）があり、テナントにも運用者にもなっていない攻撃者が特権機能へ届く——Arista は外部からの通報で知り、実際の悪用を把握したとして2026年9月22日に公表した。成立条件は「VeloCloud Edge から VCO への認証を証明書ベースにしていること」と「Edge の認証証明書の公開部分を攻撃者が入手できること」、そして VCO の管理画面へネットワーク到達できることで、侵入後は `.vcnode.js` と `vc-sysmond` を置いて常駐する。米 CISA は同日 KEV へ収載し期限を3日後の9月25日としたが、6.1 系と 7.0 系には公表時点で修正版が無い

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備未知の脆弱性の悪用
初報: 2026年9月22日 最終更新: 2026年9月24日

多拠点をつなぐ SD-WAN の設定を一括で配る管理基盤 Arista VeloCloud Orchestrator（VCO）のオンプレミス版に、入力値の検証不備（CWE-20）による脆弱性 CVE-2026-93952 が見つかりました。遠隔の攻撃者が本来は高い権限を要する内部機能へ到達し、VCO ホストと、VCO が管理するデータの機密性・完全性・可用性を損なえます。CVSS v3.1 の基本値は満点の 10.0、CVSS v4.0 では 9.5 です。

Arista は2026年9月22日（現地時間）にセキュリティアドバイザリ 0183 を公開し、外部からの通報で知ったことと実際に悪用されていることを把握していることを明らかにしました。成立条件は3つで、①VeloCloud Edge から VCO への認証が証明書ベースで構成されていること、②Edge の認証証明書の公開部分へ攻撃者が到達できること、③VCO のウェブインターフェースへネットワーク到達できることです。VCO のテナント資格情報も運用者資格情報も要りません。

対象は VCO On-Prem の 5.2.0〜5.2.3.15、6.1.0〜6.1.3.7、6.4.0〜6.4.2.7、7.0.0〜7.0.0.2 です。ホスト版（Dedicated を含む）も影響を受けましたが、Arista 側で修正済みとされています。修正版が出たのは 5.2 系（5.2.3.16 以上）と 6.4 系（6.4.2.8 以上）だけで、6.1 系と 7.0 系は公表時点で修正版が無く、到達制限が当面の唯一の防御になります。

米 CISA は公開と同じ2026年9月22日に KEV（悪用が確認された脆弱性カタログ）へ収載し、連邦民間行政機関の対応期限を3日後の9月25日としました。同じ日に収載された4件のうち残る3件は F5 BIG-IP APM（INC-2026-0187）と Check Point 管理サーバ・VPN（INC-2026-0188）で、3社とも「機器を束ねて管理する場所」の製品です。

Arista のアドバイザリは侵害の手がかりを具体的に示しています。/usr/local/sbin/.vcnode.js、/usr/local/sbin/vc-sysmond、/etc/systemd/system/vc-sysmon.service の存在、vc-sysmond の MD5 dc78e206eaeadec59fc5801fe4556bd0、nginx のログに残る x-vc-opt ヘッダ、そして 142.93.149.77 と 104.248.126.159 の2つの IP アドレスです。本記録の作成者が2026年9月24日に確認した範囲では、JPCERT/CC の2026年の注意喚起一覧に本脆弱性の注意喚起はなく、国内の被害公表も見当たりません。本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は、VCO のウェブインターフェースへネットワーク到達できる位置から、 VeloCloud Edge の認証証明書の公開部分を用いて細工した要求を送り、 入力値の検証不備を突いて特権的な内部機能へ到達する。テナント資格情報も 運用者資格情報も要らない。侵入後は `/usr/local/sbin/.vcnode.js` と `/usr/local/sbin/vc-sysmond` を置き、systemd ユニット `vc-sysmon.service` で 常駐させる。実際の攻撃で SD-WAN の設定が書き換えられたか、 どのデータが持ち出されたかは公表されていない。

  1. 1. 初期侵入確認済[1] [4]
    攻撃者が VCO のウェブインターフェースへ細工した要求を送る。 入力値の検証不備により、本来は高い権限を要する内部機能へ到達する。 VCO のテナント資格情報も運用者資格情報も不要である。
    根拠: Arista セキュリティアドバイザリ 0183 と CISA KEV の記述
  2. 2. 永続化確認済[1]
    `/usr/local/sbin/.vcnode.js` と `/usr/local/sbin/vc-sysmond` を配置し、 systemd ユニット `/etc/systemd/system/vc-sysmon.service` で常駐させる。 `vc-sysmond` の MD5 は dc78e206eaeadec59fc5801fe4556bd0。 製品の正規の部品に似せた名前が使われている。
    根拠: Arista セキュリティアドバイザリ 0183 の侵害指標
  3. 3. C2通信確認済[1]
    VCO ホストから外部への HTTP／HTTPS 通信。Arista は「VCO ホストから発生する 予期しない外向きの HTTP／HTTPS 活動」を確認対象として挙げている。 通信先・頻度・内容は公表されていない。
    根拠: Arista セキュリティアドバイザリ 0183 の監視対象
  4. 4. 影響（暗号化・破壊・改ざん）unconfirmed[1]
    VCO は配下の VeloCloud Edge へ設定を配る立場にある。掌握されれば、 全拠点のルーティングとトンネルの設定、および VCO が管理するデータ （データベースの内容・認証情報・証明書・暗号鍵）に手が届く。 本件で実際にそれが行われたかは公表されていない。
    根拠: 公表資料に記載なし（Arista が監視対象として挙げる項目からの位置づけ。本記録の作成者による評価）

狙われたのは機器ではなく「機器へ設定を配る場所」——1台で全拠点のトンネルとルーティングが動く原因・手口出典 [1] [5] [6]

VeloCloud Orchestrator（VCO）は、SD-WAN の設定・監視・トラフィック制御を拠点横断で一括して配る管理基盤です。各拠点に置かれた VeloCloud Edge はVCO から方針を受け取って動きます。つまり VCO は、境界機器そのものではなく、境界機器に「どう振る舞え」と命じる場所です。

CVE-2026-93952 は、その VCO のオンプレミス版にある入力値の検証不備（CWE-20）です。遠隔の攻撃者が、本来は高い権限を必要とする内部機能へ到達でき、VCO ホストと VCO が管理するデータの機密性・完全性・可用性を損なえます。CVSS v3.1 は満点の 10.0、v4.0 は 9.5 です。

成立条件は3つあります。

  1. VeloCloud Edge から VCO への認証が証明書ベースで構成されていること
  2. 攻撃者が Edge の認証証明書の「公開部分」に到達できること
  3. 攻撃者が VCO のウェブインターフェースへネットワーク到達できること

VCO のテナント資格情報も運用者資格情報も要りません。 Arista は、ウェブインターフェースへの到達を管理ネットワークに限っている構成は露出が小さいとしつつ、修正版への更新を求めています。

本記録の評価として、押さえるべきは必要な材料が「秘密」ではないことです。条件の2つ目は証明書の公開部分であり、定義上、秘密鍵ではありません。「証明書ベースにしてあるから、資格情報より強い」という直感は、この脆弱性では成り立ちません。

侵入した先で常駐の仕掛けが置かれている——Arista は具体的な手がかりを公開した対策・注意喚起出典 [1] [4]

Arista のアドバイザリは、侵害の有無を確かめるための具体的な手がかりを挙げています。清浄な VCO には存在しないはずのものです。

  • /usr/local/sbin/.vcnode.js（先頭がドットの隠しファイル）
  • /usr/local/sbin/vc-sysmond
  • /etc/systemd/system/vc-sysmon.service（systemd のユニット）
  • vc-sysmond の MD5 ハッシュ dc78e206eaeadec59fc5801fe4556bd0
  • nginx のアクセスログに残る x-vc-opt という HTTP ヘッダ
  • 142.93.149.77 と 104.248.126.159 の2つの IP アドレスとの通信

あわせて、VCO ホストからの予期しない外向きの HTTP／HTTPS 通信、管理者の作業として説明がつかない設定変更、想定外のコマンド実行やファイル生成、データベースの抽出、認証情報・証明書・暗号鍵への予期しないアクセスを見るよう求めています。

侵害が疑われる場合の順序も示されています。修復の前に、VCO のウェブアクセスログ、バックエンドのアプリケーションログ、システムログ、データベースログ、ファイルシステムのタイムスタンプを保全すること。修復後は、認証情報の入れ替え、管理者操作の確認、配下機器の状態の検証、信頼できる資材からのオーケストレータの復元です。

本記録の評価として、この手がかりの公開には実務上の意味があります。サービス名が vc-sysmon、実行ファイルが vc-sysmond と、製品の正規の部品に見える名前が選ばれています。「見慣れない名前を探す」という運用では見つかりません。清浄な状態のファイル一覧を持っていない環境では、この種の常駐は事実上検出できない——という前提で、平時のベースライン取得を計画する材料になります。

修正版が出たのは半分だけ——6.1 系と 7.0 系は「当てる」という選択肢が無い被害規模・影響範囲出典 [1] [3] [4] [5]

影響を受けるのは VCO On-Prem の次の4範囲です。

  • 5.2.0 〜 5.2.3.15 → 5.2.3.16 以上で修正
  • 6.4.0 〜 6.4.2.7 → 6.4.2.8 以上で修正
  • 6.1.0 〜 6.1.3.7 → 公表時点で修正版なし
  • 7.0.0 〜 7.0.0.2 → 公表時点で修正版なし

ホスト版（Dedicated を含む）も影響を受けましたが、Arista 側で修正済みです。Arista EOS、CloudVision、Wi-Fi アクセスポイント、VeloCloud Gateway・Edge は影響を受けません。

本記録の評価として、6.1 系・7.0 系の利用組織が置かれている状況は「パッチ適用の遅れ」とは質が違います。適用できるものが存在しないため、到達制限（VCO のウェブインターフェースを信頼できる管理ネットワークに限る）、公開された IP アドレスの遮断、外向き通信の監視、そして侵害調査だけが手段です。この期間の長さは Arista にしか決められず、公表もされていません。

あわせて、対処の判断を難しくしているのは版の新しさが安全を意味しないことです。最も新しい 7.0 系が未修正で、より古い 5.2 系に修正版が出ています。「最新版に追随していれば早く直る」という前提は、この事案では成り立ちません。

同じ日に3社4件——管理面の製品が同時に KEV へ並んだ日として記録する概観出典 [2] [8]

CISA は2026年9月22日、4件を KEV へ追加し、いずれも9月25日を期限としました。

  • Arista VeloCloud Orchestrator CVE-2026-93952（本件・CVSS v3.1 10.0）
  • F5 BIG-IP APM CVE-2026-94127（CVSS 9.8）——INC-2026-0187
  • Check Point CVE-2026-85102（証明書検証の不備・9.8）とCVE-2026-93616（パストラバーサル・9.8）——INC-2026-0188

3社とも、社外との境界か機器の管理面に置かれる製品です。Eclypsium が同じ週に「攻撃の焦点がインフラ機器そのものから、それを管理するシステムへ移っている」と報告していることと重なります。

本記録の評価として、運用側にとっての意味は「1件ずつ順番に処理する」前提が崩れることです。対象機器の洗い出し・変更管理の承認・停止時間の確保・侵害調査を、3系統ぶん同時に走らせる必要がありました。加えて本件は修正版が半分しか無いため、承認を取っても作業が終わりません。緩和策の適用状況を、パッチ適用とは別の台帳で追い続ける必要があります。

Arista で実悪用のゼロデイが2026年に3件目——同じ製品系統では2件目になる背景・過去事例出典 [4]

BleepingComputer は、Arista が2026年に修正した実悪用のゼロデイとして、5月の CVE-2026-7473（Extensible Operating System＝EOS）と7月の CVE-2026-16812（オンプレミス版 VeloCloud Orchestrator）を挙げています。本件は同年3件目で、オンプレ版 VCO としては2件目にあたります。

本記録の評価として、これは製品選定の是非の話ではなく、同じ製品で短期間に繰り返す前提で運用を組むという話です。2か月前に緊急対応をした機器に対し、また緊急対応が要ります。そのたびに「どの機器が・どの版で・誰が保守していて・止めると何が止まるか」を調べ直しているなら、その調査こそが恒久的な負債です。

本件の記録を、次の同種事案でそのまま再利用できる形（台帳の1行）に落としておくことが、実務上の最短の投資になります。

item: 修正版（5.2.3.16 以上／6.4.2.8 以上）への更新　副作用: VCO は配下の Edge へ設定を配る中枢であるため、更新と再起動の間、 設定変更と監視が止まる（既に配られた設定で Edge は動き続ける）。 6.1 系・7.0 系を使っている場合はそもそも適用できず、 「更新する」という対処自体が選べない

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
証明書の公開部分と管理画面への到達だけで、全拠点へ設定を配る場所が掌握される経路
攻撃者は Edge の認証証明書の公開部分を手に入れ（layer 0→1）、 VCO のウェブインターフェースへ細工した要求を送る（layer 2）。 入力値の検証不備により特権的な内部機能へ到達し（layer 3）、 .vcnode.js と vc-sysmond を置いて systemd で常駐させる（layer 4）。 VCO は配下の Edge へ設定を配る立場にあり、VCO が抱える資源 （データベース・認証情報・証明書・暗号鍵）にも手が届く（layer 5）。 痕跡は nginx ログの x-vc-opt ヘッダとファイルの存在に残るが、 機器の外へ転送していなければ調査が成立しない（layer 6）。

CISO・経営層への示唆
  • 「修正版が無い」状態を、業務判断として扱える形に用意しておく
    本件では 6.1 系と 7.0 系に修正版が無いまま実悪用が確認された。 適用できるものが存在しない以上、現場が持てる手は到達制限・遮断・監視・ 侵害調査だけになる。判断を現場に丸投げすると、 「ベンダー待ち」という名の無策が続く。
    取るべき行動 重要な管理基盤について「修正版が無い期間の代替措置」を事前に定義する。 到達経路を絞る、外向き通信を止める、監視を厚くする、という3点を 誰の承認で実施するかまで決め、ベンダーの提供時期に依存しない形にする。
  • 管理基盤は「機器の一部」ではなく最上位の特権資産として扱う
    VCO は全拠点のルーティングとトンネルの設定を配る場所で、 掌握されれば配下の機器すべてに波及する。同じ日に KEV へ並んだ F5 BIG-IP APM と Check Point 管理サーバも同じ性質の製品だった。
    取るべき行動 ネットワーク機器の台帳とは別に、それらを束ねる管理基盤 （オーケストレータ・管理サーバ・コントローラ）の一覧を作り、 更新の優先度・監視の水準・特権アクセスの承認を最上位に設定する。
  • 同じ日に複数の緊急対応が重なる前提で、順序の基準を決めておく
    2026年9月22日、CISA は3社4件を同じ期限で KEV へ追加した。 洗い出し・承認・停止時間の確保・侵害調査を同時に3系統走らせる必要があり、 その場の判断で並べ替えると数日が溶ける。
    取るべき行動 緊急対応の順序を「社外に面しているか」「実悪用が確認されているか」 「修正版があるか」の3条件で機械的に決める規則を先に作る。 同時に来たときに議論しないで済むようにしておく。
  • 同じ製品で年に何度も緊急対応が起きる前提で、調査コストを資産化する
    Arista では2026年に実悪用のゼロデイが3件（EOS・オンプレ VCO の2件）出ている。 そのたびに「どの機器が・どの版で・誰が保守し・止めると何が止まるか」を 調べ直しているなら、その調査時間そのものが恒久的な負債になる。
    取るべき行動 緊急対応の記録を、次回そのまま使える台帳の行として残す （版数はビルドまで、保守の実施主体、停止時の影響業務、到達制限の現状）。 対応が終わった時点で台帳を更新することを完了条件に含める。
セキュリティ技術者への示唆
  • 「証明書ベースだから強い」は本件では成り立たない——必要なのは公開部分だった
    成立条件は Edge の認証証明書の「公開部分」への到達であり、秘密鍵ではない。 証明書ベース認証を採用していること自体が、この脆弱性では前提条件になっている。
    取るべき行動 Edge から VCO への認証方式（証明書ベースか事前共有鍵か）を全拠点について 棚卸しし、証明書ベースの環境を優先して対処する。認証方式を 「セキュリティ上の強度」ではなく「この脆弱性の該当条件」として記録する。
  • 常駐の仕掛けは製品の正規の部品に似せた名前で置かれる
    置かれたのは vc-sysmond と vc-sysmon.service で、VeloCloud の正規の 部品に見える。隠しファイル .vcnode.js も同様である。 「見慣れない名前を探す」運用では見つからない。
    取るべき行動 管理基盤の導入直後に /usr/local/sbin と /etc/systemd/system の ファイル一覧とハッシュを取得してベースラインにし、定期的に差分を取る。 既存機器でベースラインが無い場合は、同一版の清浄な機器から作る。
  • 侵害調査の起点になるログが、その機器にしか無い状態を解消する
    調査の起点は nginx のアクセスログ（x-vc-opt ヘッダ）、バックエンドの アプリケーションログ、システムログ、データベースログである。 いずれも VCO 上にあり、機器上でコードを実行された後は信頼性が下がる。
    取るべき行動 VCO のログを常時外部の基盤へ転送し、保全期間を明文化する。 転送されていない環境では、まず証拠の保全（スナップショット・ログの退避）を 行ってから更新や再構築に進む。
  • 版の新しさは安全を意味しない——系列ごとに修正の有無が違う
    最も新しい 7.0 系が未修正で、より古い 5.2 系に修正版が出ている。 「最新に追随していれば早く直る」という前提は本件では逆になる。
    取るべき行動 資産台帳の版数欄を系列とビルドまで持たせ、脆弱性情報の該当判定を 系列単位で行う。更新後は実機から取得した版数で突き合わせ、 委託先が実施した場合も実機の出力を報告に添えさせる。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Arista（旧 Broadcom）VeloCloud Orchestrator のオンプレミス版を自社で運用しており、版が 5.2.0〜5.2.3.15・6.1.0〜6.1.3.7・6.4.0〜6.4.2.7・7.0.0〜7.0.0.2 のいずれかに該当する対象版であることが前提条件になる。ホスト版（Dedicated を含む）は Arista 側で修正済みのため、自社で運用しているかどうかが最初の分岐になる。
認証・認可□ VeloCloud Edge から VCO への認証を証明書ベースで構成しているArista はこの構成に限って露出があるとしている。逆に、この設定を 即座に答えられない組織は「影響を受けない」とも言えない状態にある。
システム構成□ VCO のウェブインターフェースが、管理ネットワーク以外（インターネットや業務ネットワーク全体）から到達できる成立には VCO のウェブインターフェースへのネットワーク到達が要る。 到達範囲が広いほど、修正版が無い期間の危険が長く続く。
運用・監視□ VCO のログ（nginx アクセスログ・アプリケーションログ・システムログ・データベースログ）を機器の中にしか置いておらず、外部へ転送していないArista が示す侵害調査は、これらのログを起点にする。 転送も保全もしていなければ、確認手順そのものが成り立たない。
運用・監視□ 管理基盤の清浄時のファイル一覧・サービス一覧のベースラインを取得していない常駐の仕掛けは製品の正規の部品に似た名前で置かれる。 差分を取れない環境では、公開されたハッシュと一致しない別検体を見つけられない。
体制・契約□ 修正版が提供されていない期間の代替措置を、誰の承認でどこまで実施するかが決まっていない本件では 6.1 系・7.0 系に修正版が無い。決めていなければ、 実悪用が確認されている期間に「ベンダー待ち」の状態が続く。
