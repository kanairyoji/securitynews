INC-2026-0195AI 開発支援の助言から Shai-Hulud

攻撃者が SaaS 事業者に侵入したうえで、開発者が使用中の AI コーディング支援のセッションを乗っ取り、支援に「汚染された外部パッケージを入れなさい」と勧めさせた——Mandiant によれば、開発者がその助言を受け入れたことで汚染 PyPI パッケージ経由の情報窃取型が入り、GitHub の OAuth トークンが奪われ、自己増殖する Shai-Hulud ワームが約100の内部リポジトリへ広がって機密と自社製品のソースコードが持ち出された。攻撃者は被害企業の公式名前空間のパッケージも汚染し、別の従業員が後日その版を取得して二次感染が起きた。被害企業名・時期・使われていた支援ツールの名称はいずれも公表されていない

脅威・攻撃キャンペーン委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）認証情報の悪用（使い回し・推測可能・窃取）委託先・供給元起因
初報: 2026年9月16日 最終更新: 2026年9月24日

Google 傘下の Mandiant が、AI コーディング支援そのものが侵入の入口になった事例を公表しました。攻撃者はまず匿名の SaaS（ソフトウェア・アズ・ア・サービス）事業者に侵入し、開発者の作業端末で動作中の AI コーディング支援のセッションを乗っ取りました。Mandiant は、環境の中で信頼された解釈者として動いていたその支援が、攻撃者が汚染した外部パッケージの導入を開発者に勧め、意図せずトロイの木馬として機能したと説明しています。

開発者が助言を受け入れたあと、攻撃者は同じセッションを使って汚染された PyPI パッケージ経由で情報窃取型を導入し、GitHub の OAuth トークンを奪いました。続いて自己増殖する Shai-Hulud ワームを展開し、約100の内部コードリポジトリへ広げて、リポジトリの機密情報と自社製品の独自ソースコードを持ち出しています。さらに攻撃者は被害企業の公式名前空間にあるパッケージも汚染し、別の従業員が後日その版を取得したことで二次感染が起きました。

Mandiant が示した対策は3点です。①AI が推薦する第三者の依存関係を、暗号学的なチェックサムと承認リストに突き合わせて確認する。②生の API キー・長命の OAuth トークン・その他の機密を、拡張機能が直接届く場所に置かない。③依存関係の取得を、組織が管理する内部リポジトリ経由にする。

本記録の作成者が2026年9月24日に確認した範囲では、被害企業の名称、侵入と発覚の時期、使われていた AI コーディング支援ツールの名称・提供元、セッションの乗っ取り方、最初に SaaS 事業者へ侵入した経路、汚染されたパッケージの名称、下流の顧客への影響の有無は、いずれも公表されていません。出典は Mandiant のレポートと、それを伝えた報道です。本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

参照・持ち出された情報

    侵入の入口になったのは脆弱性でも添付ファイルでもなく、開発者が信頼している「助言」だった原因・手口出典 [1] [2] [3]

    この事例の要点は、経路の一段目にあります。攻撃者は SaaS 事業者に侵入したのち、開発者の端末で動作中の AI コーディング支援のセッションを乗っ取りました。そのうえで、乗っ取ったセッションの中から、汚染された外部パッケージの導入を開発者に勧めさせたのです。

    Mandiant はこの支援を「環境の中で信頼された解釈者（trusted interpreter）」と表現し、助言を実行することで支援が意図せずトロイの木馬として機能したと説明しています。開発者は普段どおりに支援へ質問し、普段どおりに答えを受け入れました。不審なメールも、見慣れないファイルも、警告画面もありません。

    本記録の評価として、ここには防御側の前提の崩れが2つあります。

    1つ目は、疑う契機が構造的に存在しないことです。利用者教育は「怪しいものを疑え」という形をとりますが、本件で怪しいものは何もありません。助言の内容（このパッケージを入れなさい）は、支援が普段から出している助言と見分けがつきません。

    2つ目は、助言と実行の距離がゼロになっていることです。AI コーディング支援は提案するだけでなく、承認を得れば導入まで進みます。「読んでから考える」時間が設計上存在しないため、判断の機会が失われています。

    Mandiant が示した3つの統制が、いずれもAI の出力を賢く検査する話ではなく、助言が実行に変わる経路を絞る話であることは、この構造と整合しています。

    一段目の汚染が、自己増殖のワームと自社名前空間の汚染という二段の増幅を受けた被害規模・影響範囲出典 [1] [2] [3]

    導入された汚染 PyPI パッケージは情報窃取型を運び、GitHub の OAuth トークンを奪いました。ここから先は、人の操作を必要としません。

    • 自己増殖する Shai-Hulud ワームが展開され、約100の内部リポジトリへ広がった
    • リポジトリの機密情報（シークレット）と、同社製品の独自ソースコードが持ち出された
    • 攻撃者は被害企業の公式名前空間のパッケージも汚染した
    • 別の従業員が後日その汚染版を取得し、二次感染が起きた

    本記録の評価として、二次感染の経路が重要です。二人目の従業員は、外部の見知らぬパッケージを入れたのではなく、自社の名前空間にある自社のパッケージを取得しました。社内のどの規程にも触れない、正しい手順です。

    これは「信頼の連鎖」が二重に破れた形です。一人目は AI の推薦を信頼し、二人目は自社の名前空間を信頼しました。どちらも、平時に疑うべき対象ではありません。承認リストや社内レジストリへの集約といった対策は、名前空間そのものが汚染された場合には効きません。効くのは、公開する版に対する署名・来歴の検証と、公開権限の分離です。

    なお、二次感染が「封じ込めの後」だったのか「封じ込めの前」だったのかは公表されていません。後だとすれば、封じ込めの完了判定に自社レジストリの汚染確認が入っていなかったことになります。これは本記録の作成者の読みであり、資料の裏付けはありません。

    公表されていないものが多く、読者は「自社が該当するか」を確かめられない未確定事項出典 [1] [2]

    本件は、防御側が学べる構造を示す一方で、確かめるための材料を欠いています。本記録の作成者が2026年9月24日に確認した範囲で、公表されていないのは次のとおりです。

    • 被害企業の名称・国・規模・業種、事案の時期（侵入・検知・封じ込め）
    • 使われていた AI コーディング支援ツールの名称・提供元・版
    • セッションの乗っ取りの具体的な方法
    • 最初に SaaS 事業者へ侵入した経路
    • 汚染されたパッケージの名称（外部パッケージ・PyPI・公式名前空間のいずれも）
    • 下流の顧客・利用組織への影響の有無

    本記録の評価として、実務上の影響は明確です。利用組織は自社の依存関係を照合できず、「使っていたか」を確かめる術がありません。また、支援ツールの名称が伏せられているため、「自社が使っている製品に固有の問題なのか、開発者端末を取られた後ならどの製品でも成立するのか」も判断できません。

    本記録としては、後者（端末を取られた後はどの製品でも成立しうる）を前提に読むことを勧めます。根拠は、Mandiant が示した統制がいずれも製品固有の設定ではなく、依存関係の取得経路と機密の置き場所という環境側の設計に向いていることです。これは本記録の作成者の解釈であり、Mandiant がそう述べたわけではありません。

    日本でも AI コーディング支援の業務導入は進んでおり、統制の空白がそのまま当てはまる評価・解釈出典 [1] [2] [3]

    日本の開発組織でも AI コーディング支援の導入は急速に進んでいます。導入の稟議では生産性と情報漏えい（コードを外部へ送るか）が論点になりがちですが、本件が示すのは第三の論点です。すなわち、支援が推薦したものを、誰の承認で、どの経路から取得するかです。

    本記録の評価として、今日から確認できるのは次の3点です。

    1. 依存関係の追加が AI の推薦だけで完結していないか。社内の承認リストまたはプライベートレジストリを経由する構成になっているか。
    2. 拡張機能・支援ツールから、生の API キーと長命の OAuth トークンへ直接手が届いていないか。 端末上の設定ファイルや環境変数に平文で置かれていれば、セッションを取られた時点で同時に取られます。
    3. 自社の公式名前空間のパッケージに、公開時の署名・来歴の検証と公開権限の分離があるか。 無ければ、二次感染の経路が開いたままです。

    いずれも製品の入れ替えを伴わず、設定と手順の範囲で着手できます。逆に言えば、着手していない組織では、本件と同じ経路がそのまま通ることになります。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    「信頼された助言」から自己増殖と自社名前空間の汚染へ至る二重の信頼の破れ
    攻撃者は SaaS 事業者へ侵入したのち（layer 0→1）、開発者端末で動作中の AI コーディング支援のセッションを乗っ取り（layer 2）、汚染された外部パッケージの 導入を開発者に勧めさせる（layer 3）。開発者が受け入れると汚染 PyPI パッケージ経由で 情報窃取型が入り GitHub の OAuth トークンが奪われる（layer 4）。 自己増殖する Shai-Hulud ワームが約100の内部リポジトリへ広がり、 機密と独自ソースコードが持ち出される（layer 5）。 さらに公式名前空間のパッケージが汚染され、別の従業員が後日その版を取得して 二次感染が起きる（layer 6）。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    初期侵入公表されていない
    侵入経路が公表されていないため、この段階の検知機会は評価できない。
    検知できた開発者端末を含む全端末で、侵入後の挙動（資格情報アクセス・外向き通信の変化）を監視する
    実行現実的な検知機会なし
    利用者から見れば、支援が普段どおりの助言を返しただけである。 助言の内容も形式も正規のものと区別がつかない。 利用者教育や画面上の警告では気づく契機が生じない（本記録の評価）。
    侵入を防げた依存関係の追加を、社内の承認リストまたはプライベートレジストリ経由に限定する
    侵入を防げたAI が推薦した第三者の依存関係を、暗号学的なチェックサムと承認リストに照合してから導入する
    侵入を防げた開発端末から公開パッケージレジストリへの直接到達を止め、内部リポジトリ経由にする
    認証情報アクセス機会はあったが検知できず
    パッケージ導入の直後に、端末上の資格情報の読み出しと外部への通信が起きている。 端末側の監視で「導入直後に資格情報の保管場所へアクセスする」挙動を 捉えられる余地はあった（本記録の評価。実際に検知されたかは公表されていない）。
    影響を限定できた生の API キー・長命の OAuth トークン・機密を、拡張機能や支援ツールが直接届く場所（環境変数・平文の設定ファイル）に置かない
    影響を限定できたOAuth トークンに有効期限を必須化し、無期限トークンを組織設定で禁止する
    検知できたパッケージ導入の直後に発生する資格情報保管場所へのアクセスを監視対象にする
    横展開機会はあったが検知できず
    単一のトークンから短時間に多数のリポジトリへアクセスが発生する。 リポジトリ横断のアクセス頻度を見ていれば、増殖の段階で気づける余地があった （本記録の評価。実際に検知されたかは公表されていない）。
    影響を限定できたトークンの権限をリポジトリ単位に絞り、組織全体へ届く権限を既定にしない
    検知できた単一の資格情報による短時間の多数リポジトリアクセスをアラートにする
    持ち出し公表されていない
    持ち出しの経路と時期が公表されていないため、検知の機会も評価できない。
    影響を限定できたリポジトリに平文の機密を置かない運用（秘密管理基盤への外出し）を徹底する
    影響を限定できたシークレット走査を公開前と保存時の双方で回し、検出時は自動失効させる
    影響（暗号化・破壊・改ざん）機会はあったが検知できず
    自社の名前空間に対する公開操作は、公開権限を持つ者の正規の操作と 区別しにくい。公開のたびに署名・来歴を検証していれば、 取得側で弾ける余地があった（本記録の評価）。
    侵入を防げた自社が公開するパッケージに署名と来歴（プロベナンス）を付け、取得側で検証を必須にする
    侵入を防げたパッケージの公開権限を個人トークンから切り離し、承認を伴う公開経路に一本化する
    影響を限定できた封じ込めの完了判定に「自社レジストリ・自社名前空間の汚染確認」を含める

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • AI コーディング支援の導入審査に「推薦したものをどう入れるか」を加える
      導入の稟議は生産性とコードの外部送信に集中しがちだが、本件の入口は 「支援が推薦した依存関係を、開発者がそのまま導入できる」という経路だった。 支援ツールの安全性をいくら評価しても、この経路が開いていれば同じことが起きる。
      取るべき行動 AI コーディング支援の利用規程に、依存関係の追加は社内の承認リストまたは プライベートレジストリ経由に限る旨を明記する。既に導入済みの組織は、 現在の開発端末から公開レジストリへ直接到達できるかを今日確認する。
    • 「疑えば防げる」型の対策が効かない攻撃が出てきた——教育の限界を前提に設計する
      利用者から見れば、支援が普段どおりの助言を返しただけである。 不審なメールも警告画面も無い。利用者教育や注意喚起では、 気づく契機そのものが生じない。
      取るべき行動 セキュリティ教育の効果を前提にした統制（「怪しい推薦は入れない」等）を 統制表から外し、技術的に経路を絞る統制へ置き換える。 教育は残してよいが、監査で「統制」として数えない。
    • 自社が公開しているパッケージ・成果物が、社内の二次感染の経路になる
      二人目の従業員は自社の公式名前空間からパッケージを取得した。 社内規程に照らして正しい手順であり、承認リストや社内レジストリへの 集約では止まらない。
      取るべき行動 自社が公開する成果物（社内向け・社外向けを問わず）について、 公開権限の保有者、公開に必要な承認、署名・来歴の有無を一覧にする。 署名も承認も無いものがあれば、そこが二次感染の経路として残っている。
    • 事案の詳細が公表されない前提で、学びを構造として取り込む
      被害企業名・時期・ツール名・パッケージ名がいずれも公表されていない。 「自社が該当するか」を照合で確かめることはできず、 情報を待っても材料は増えない可能性が高い。
      取るべき行動 ベンダーレポートの事例を扱う際は、照合できる指標（IoC・パッケージ名）の 有無で対応を分ける。指標が無い事例は「経路の構造」を自社の構成図に 当てはめる演習として扱い、指標待ちで滞留させない。
    セキュリティ技術者への示唆
    • 支援ツールと拡張機能から、生の鍵と長命トークンを引き離す
      情報窃取型が奪ったのは GitHub の OAuth トークンだった。 支援ツールやその拡張が読める場所（環境変数・平文の設定ファイル・ ホームディレクトリ）に機密があれば、セッションを取られた時点で同時に失う。
      取るべき行動 開発端末上の ~/.netrc・~/.npmrc・.env・シェルの環境変数・ 各種設定ファイルに平文の鍵とトークンが無いかを走査し、 秘密管理基盤または短命トークンへ置き換える。
    • トークンの権限をリポジトリ単位に絞る——自己増殖はトークンの射程で止まる
      Shai-Hulud は自己増殖して約100の内部リポジトリへ広がった。 広がる範囲は、奪われたトークンが到達できる範囲で決まる。 組織全体に届く権限を既定にしていると、被害はそのまま全社になる。
      取るべき行動 GitHub の組織設定で、細粒度の個人アクセストークンを必須にし、 リポジトリ単位の許可と有効期限を強制する。 既存の無期限トークン・組織全体スコープのトークンを棚卸しして失効させる。
    • 単一の資格情報による多数リポジトリへの短時間アクセスをアラートにする
      自己増殖の段階では、人の操作では起こりえない頻度でリポジトリへの アクセスが発生する。内容ではなく頻度と広がりで捉えられる。
      取るべき行動 監査ログを取り込み、同一トークン・同一利用者による単位時間あたりの リポジトリ数をしきい値監視に入れる。しきい値は平常時の実測から決める。
    • 封じ込めの完了判定に「自社レジストリ・自社名前空間の汚染確認」を入れる
      本件では、公式名前空間の汚染版を別の従業員が後日取得して二次感染が起きた。 端末の初期化とトークンの失効だけでは、汚染された成果物が残る。
      取るべき行動 インシデント対応手順の封じ込めチェックリストに、 自社が公開しているパッケージ・コンテナイメージ・成果物の 版ごとのハッシュ照合を追加する。照合に使う正解値を平時に保存しておく。

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    運用・監視□ 開発者が AI コーディング支援（エディタ拡張・CLI・エージェント）を業務で使っている本件の経路は、支援が動作中のセッションを乗っ取られたところから始まる。 使っていない組織には当てはまらないが、使っている組織では 製品の違いによらず経路の構造が同じになりうる。
    委託・第三者部品□ 開発端末から npm・PyPI などの公開レジストリへ直接到達でき、依存関係の追加に承認の関門が無い推薦されたパッケージがそのまま導入できるかどうかが分岐点になる。 内部リポジトリ経由に限定していれば、汚染パッケージの導入自体が止まる。
    認証・認可□ 開発端末上に、生の API キーまたは有効期限の無い OAuth トークン・個人アクセストークンが置かれている情報窃取型が奪ったのはこの種の資格情報である。 短命化・秘密管理基盤への外出しができていれば、被害は端末1台に留まりうる。
    認証・認可□ GitHub 等のトークンに組織全体へ届く権限を与えており、リポジトリ単位の制限をかけていない自己増殖が届く範囲は、奪われたトークンの射程で決まる。 約100リポジトリという規模は、権限設計の結果として現れた数である。
    委託・第三者部品□ 自社の名前空間でパッケージ・コンテナイメージ・成果物を公開しており、署名・来歴の検証を取得側で行っていない二次感染はこの経路で起きた。承認リストや社内レジストリへの集約では 「自社名前空間の汚染」を止められない。
    体制・契約□ インシデント対応の封じ込め完了の判定に、自社が公開している成果物の汚染確認が含まれていない端末の初期化とトークン失効だけでは、汚染された成果物が残り、 別の従業員が正しい手順で取得して再発火する。
