INC-2026-0196Elsevier のドメインが恐喝ページへ

学術出版と医療情報の大手 Elsevier のウェブアドレス3つ（www・論文投稿の submit・看護／医学教育の evolve）が、2026年9月21日の夜に約2時間20分ものあいだ恐喝集団 LAPSUS$ の画面へ HTTP 302 で飛ばされた——止まったのは学生の試験だけではない。Sorami Consulting によれば、薬剤情報データベース GSDD の本番認証エンドポイント（api.gsdd.net/auth/AccessToken）までが、トークンの代わりに攻撃者のページを返していた。Elsevier は「限定的で短期間の事象」「中核基盤・顧客データ・研究コンテンツ・運用システムが侵害された兆候は無い」と報道機関への声明で述べたが、開始時刻・終了時刻・原因の仕組みは公表していない

資産の失効・乗っ取り（ドメイン等）不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年9月21日 最終更新: 2026年9月24日

2026年9月21日の夜（米中部時間）、Elsevier のウェブアドレス3つwww.elsevier.com（同社ホームページ）、submit.elsevier.com（研究者の論文投稿ポータル）、evolve.elsevier.com（Sherpath・HESI・EAQ・SimChart・Shadow Health へのサインイン入口）が、恐喝集団 LAPSUS$ の画面へ HTTP 302 でリダイレクトされました。Cloudskope の観測では、最初の報告が19時49分、解消が22時09分で、同社は約78分のリダイレクト窓としています。ScienceDirect は影響を受けていません。

Reddit 上の反応は、試験や実習記録から締め出された看護・医学の学生の声が中心でしたが、DataBreaches.net が伝えた Sorami Consulting の報告によれば、影響の広がりは学生向けのポータルにとどまりません。薬剤情報データベース GSDD（Gold Standard Drug Database）の本番の認証エンドポイントapi.gsdd.net/auth/AccessToken が、有効なアクセストークンを返す代わりに攻撃者の管理下のページへトークン要求を飛ばしていた、としています。ClinicalPharmacology も対象に挙げられています。

原因は公表されていません。Cloudskope は DNS または CDN のエッジでの変更と推定し、中国語のフォーラムには「Cloudflare のリダイレクトルールが書き換えられた」という主張があったと伝えています。Elsevier は9月22日12時30分（米中部時間）にDataBreaches.net へ声明を出し、「限定的で短期間の事象であり、特定のウェブ資産のトラフィックが一時的にリダイレクトされたもの」「中核基盤・顧客データ・研究コンテンツ・運用システムが侵害された兆候は無い」（原文英語）と述べましたが、開始時刻・終了時刻・原因の仕組みは示していません。

本記録の作成者が2026年9月24日に確認した範囲では、Elsevier の Evolve サポートセンターの告知一覧（2026年9月9日〜23日の新規・更新分）に本件の告知はなく、掲載されている最新の告知は9月18日の「無効な Evolve アクセスコードのエラーの解消方法」です。つまり利用者が自分で確認できる公式の記録が、事案の当事者側に残っていません。本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

破られたのは中身ではなく「行き先」——サーバは無事でも利用者は攻撃者の画面に着く原因・手口出典 [1] [2] [3]

この事案で起きたのは、Elsevier のサーバやデータベースへの侵入ではありません。利用者と利用システムが「どこへ着くか」を決める層が書き換えられました。Cloudskope は原因を DNS または CDN のエッジでの変更と推定し、MITRE ATT&CK の T1584.001（インフラの侵害：ドメイン）に分類しています。

利用者の側から見ると、いつもどおりのアドレスを開き、いつもどおりのリンクを踏み、返ってきたのが恐喝集団の画面でした。URL の入力にも、リンクの選び方にも、間違いはありません。

Elsevier の声明は「中核基盤・顧客データ・研究コンテンツ・運用システムが侵害された兆候は無い」と述べています。本記録の評価として、この説明は技術的には正しくても、利用者の被害の説明にはなっていません。利用者が Elsevier のサーバへ到達できていない以上、サーバが無事であることは利用者にとっての安全を意味しないためです。

「うちのシステムは破られていない」と「利用者は安全だった」は別の命題である。この区別は、自社が同じ立場に立ったときの説明文の設計にそのまま効きます。

止まったのは学生の試験だけではない——薬剤情報 API の認証が攻撃者のページを返していた波及・関係先出典 [2] [3]

Reddit 上で目立ったのは、試験やシミュレーション記録から締め出された看護・医学の学生の声でした。しかし DataBreaches.net が伝えたSorami Consulting の報告によれば、影響はそこで終わりません。

Elsevier と GSDD（Gold Standard Drug Database）の本番の認証エンドポイント、具体的には api.gsdd.net/auth/AccessToken が、有効なアクセストークンを返す代わりにトークン要求そのものを攻撃者の管理下のページへ飛ばしていたとされています。ClinicalPharmacology も対象に挙げられています。（Cloudskope はこの部分を「未確認の報告」としており、確定度が資料で異なります。）

本記録の評価として、これは3つの意味で重い事実です。

  1. 臨床の意思決定支援が参照する先が変わった。電子カルテやオーダリングが薬剤情報 API を参照している構成では、参照の失敗は機能の停止として現れます。最悪の場合、改ざんされた応答を受け取る余地も理屈の上では生じます。
  2. 人が見る画面ではなく、機械が呼ぶ API が飛ばされた。人であれば見慣れない画面に気づきますが、システムはHTTP 302 に素直に従います。気づく主体が居ません。
  3. 認証の入口だった。トークン要求には資格情報が載ります。それがどこへ渡ったかは外部から検証できず、Elsevier も言及していません。

日本の医療機関・調剤薬局でも、電子カルテやオーダリングが外部の薬剤情報データベースを API で参照する構成は一般的です。本記録の評価として、確認すべきは「外部 API の応答先が変わったことを検知できるか」と「参照に失敗したときに安全側に倒れる設計か」の2点です。ベンダー任せにしていると、異常時に何が起きるかを誰も把握していない状態になります。

セキュリティ技術者への示唆
  • 自社の主要ドメインは「外から」監視する——内部の死活監視では気づけない
    書き換えられたのはサーバではなく行き先である。サーバ側の死活監視は すべて正常のまま、利用者だけが別の場所へ着く。 本件で最初に気づいたのも利用者と外部の観測者だった。
    取るべき行動 主要ドメインについて、外部の拠点から HTTP のステータスコード・ 最終到達先・TLS 証明書の発行者と指紋を定期取得し、想定値との差分で アラートする仕組みを置く。取得間隔は分単位にする。
  • 機械が呼ぶ API ほど、リダイレクトに素直に従う
    人は見慣れない画面に気づくが、システムは HTTP 302 に従って 資格情報を新しい宛先へ送る。気づく主体が居ない。
    取るべき行動 外部 API の呼び出しで、リダイレクトの自動追従を既定で無効にする。 追従が必要な場合は許可する宛先ホストを明示列挙し、 それ以外では資格情報を送らずに失敗させる。
  • 応答が「期待した形か」を検査する——成否だけを見ない
    トークンを返すはずのエンドポイントが HTML の画面を返していた。 呼び出し側が HTTP 200 の有無だけを見ていれば「成功」と解釈しうる。
    取るべき行動 認証・データ取得の呼び出しに、応答の Content-Type と スキーマの検査を入れる。想定外の形式を受け取ったら安全側に倒し、 資格情報の再送を止める。
  • DNS・CDN・レジストラを「本番系と同じ重さ」の管理対象にする
    行き先を決める層を取られれば、サーバの堅牢さは意味を持たない。 この層の管理は、歴史的に少人数の担当者と共用アカウントに寄りがちである。
    取るべき行動 DNS・CDN・レジストラの管理アカウントを棚卸しし、 フィッシング耐性のある多要素認証、ドメインロック、変更の承認記録、 変更通知の宛先を揃える。退職者のアカウントが残っていないかも確認する。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 自社のシステムが、外部の情報提供元（薬剤情報・与信・地図・認証など）の API を本番で参照している本件で飛ばされたのは人が見る画面だけでなく、機械が呼ぶ認証エンドポイントだった。 参照先が変わったことを検知できなければ、資格情報の送出先が変わったことにも気づけない。
認証・認可□ 外部 API の呼び出しでリダイレクトを自動追従する設定になっており、宛先ホストを検証していない追従する設定では、行き先が変わった瞬間に資格情報が新しい宛先へ渡る。 呼び出し側で止められる唯一の地点がここになる。
運用・監視□ 自社の主要ドメインについて、外部からの応答（ステータス・最終到達先・証明書）を監視していないサーバ側の死活監視は正常のままになる。外形監視が無ければ、 気づくのは利用者からの問い合わせになり、時間がかかる。
体制・契約□ DNS・CDN・レジストラの管理アカウントの棚卸しと多要素認証・ドメインロックの適用が済んでいない本件の原因は特定されていないが、いずれの層であっても この管理層を取られれば同じ結果になる。対策は層ごとに独立している。
運用・監視□ 外部サービスの障害対応手順に「認証エンドポイントが対象だった場合の資格情報の失効」の分岐が無い可用性の問題として処理すると、資格情報が外へ渡った可能性が検討されないまま 復旧で案件が閉じる。
体制・契約□ 重要な外部サービスの契約に、事案時の影響時間帯の提示と公開記録の維持が書かれていない本件では当事者のサイトに記録が残らず、時刻も公表されなかった。 契約に書いていなければ、提供側の判断に委ねられる。
