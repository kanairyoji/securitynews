INC-2026-0203AI エージェントがECを連続侵害

セキュリティ企業 Gambit Security が2026年9月22日、オープンソースの自律型 AI ツール3本（Strix・Cairn・Hermes）を組み合わせてオンライン小売を大量に侵害するキャンペーンを公表した——攻撃者のステージングサーバを回収して再構成したもので、9月10〜15日の6日間に105件の攻撃が起動され少なくとも27社が侵害され、2社から60万件超の未失効クレジットカード情報が持ち出された。決済ページへのスキマー設置は名前を特定した27の標的のうち19社で確認され、さらに100を超えるサイトで感染が見つかっている。人間の操作者は260セッションで1,951回の短い中国語の指示を入力しただけで、1社あたりの費用は平均25.46米ドルだった

脅威・攻撃キャンペーン不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用設計・実装上の不備
初報: 2026年9月22日 最終更新: 2026年9月23日

セキュリティ企業 Gambit Security は 2026年9月22日、オープンソースの自律型 AI ツールを使ってオンライン小売を次々に侵害しているキャンペーンを公表しました。攻撃者のステージングサーバを回収し、そこに残っていた記録からキャンペーンを再構成したものです。

使われたのは3本の道具です。

道具 役割 動かしていたモデル
Strix 脆弱性の探索（自動ペネトレーションテスト） GLM 5.2／DeepSeek v4 Pro
Cairn 侵入の実行（シェルか管理者権限を取るまで自動で走る） DeepSeek v4.1 Flash
Hermes 全体の指揮と侵入後の作業 Anthropic の opus-4.6

Hermes には 121のスキルが登録され、うち78が攻撃用でした。中国語のシステムペルソナ「SOUL - Red Team Operator」が設定されています。

規模は次のとおりです。

  • 8月23〜31日 — Strix が 146回、138ホストに対して実行され、633時間のスキャン時間を消費
  • 9月10〜15日 — 105件の攻撃が起動され、少なくとも27社が何らかの形で侵害された
  • 2社から60万件超の未失効クレジットカード情報が持ち出された
  • 決済ページへのスキマー（カード情報の窃取スクリプト）は、名前を特定した27の標的のうち19社で設置を確認、さらに100を超えるサイトで感染が見つかった

人間がしたことは、ほとんど指示を出すことだけです。 260セッションで1,951回の入力しかなく、その多くは「读漏洞报告 开干（脆弱性レポートを読んで始めろ）」のような短い中国語でした。

費用も公開されています。OpenRouter 経由のモデル利用料は4週間で7,005.71米ドル、キャンペーン全体で1万2,000〜1万8,000米ドル、1社あたり平均25.46米ドル（最安3.13ドル・最高79.31ドル）です。

Gambit Security の結論はこうです。「このキャンペーンは規模以上に重要である。道具はオープンソースで、限界費用は数十ドルの水準にある。もはや経済性が誰かをふるい落とすことはない」（原文英語）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

オープンソースの自律型 AI ツール3本（探索の Strix・侵入の Cairn・指揮の Hermes）を 組み合わせ、オンライン小売を並列に侵害するキャンペーン。 使われた脆弱性は未認証の SQL インジェクションや任意ファイルアップロードなど従来型で、 新しいのは**探索から侵入後の作業までを自動化し、1社あたり25米ドル程度で回している**点である。

    根拠: Gambit Security が回収したステージングサーバの記録
  2. 2. 初期侵入公表・報道に基づく[1] [2]
    Cairn（DeepSeek v4.1 Flash で稼働）が、見つかった未認証の SQL インジェクションを起点に 侵入を実行した。シェルまたは管理者権限を取るまで数時間にわたり自動で試行を続ける
    根拠: Gambit Security が再構成した攻撃チェーン
  3. 3. 認証情報アクセス公表・報道に基づく[1] [2]
    ワンタイムパスワードがデータベースから**平文で読み取れた**ため、多要素認証が迂回され、 管理画面へのログインに成功した
    根拠: Gambit Security が再構成した攻撃チェーン（OTP plaintext read）
  4. 4. 実行公表・報道に基づく[1] [2]
    管理画面のファイルアップロード機能を悪用してコードを設置し、 サーバ上での実行（RCE）に至った
    根拠: Gambit Security が再構成した攻撃チェーン
  5. 5. 権限昇格公表・報道に基づく[1] [2]

    根拠: Gambit Security が再構成した攻撃チェーン

    根拠: Gambit Security が再構成した攻撃チェーン

    侵入の手口はどれも既知の型で、新しいのは「それを誰でも安く回せるようになったこと」である概観出典 [1] [2]

    Gambit Security が再構成した攻撃チェーンの一例は次のとおりである（報告の原文表記）。

    Unauthenticated SQLi → OTP plaintext read → admin panel → arbitrary file
upload → RCE → sudo privilege escalation → NFS mount → WordPress credentials
→ AWS Secrets Manager dump → Magento database access

    日本語にすると、未認証の SQL インジェクション → ワンタイムパスワードを平文で読み取り →多要素認証を迂回して管理画面へ → 任意ファイルのアップロード → コード実行 → sudo による権限昇格 → NFS 共有のマウント → WordPress の認証情報 → AWS Secrets Manager の吸い出し → Magento のデータベースへ到達、となる。最後に鍵を取り出してカード情報を復号している。

    ここに新しい脆弱性は1つも無い。 どれも10年以上前から教科書に載っている型である。変わったのは、この一連を人間が手で追わなくなったことのほうである。

    • Strix が標的を探索する（8月23〜31日に146回・138ホスト・633時間分）
    • Cairn が数時間ぶっ続けで試行し、シェルか管理者権限を取るまで止まらない
    • Hermes が全体を指揮し、侵入後の作業（スキマー設置・データ抽出・後始末）を割り振る

    人間の入力は260セッションで1,951回。「脆弱性レポートを読んで始めろ」「コード実行は取れるか」といった短い中国語である。1社あたりの費用は平均25.46米ドルだった。

    スキマーは8通りの方法で仕込まれ、消しても cron が書き戻した原因・手口出典 [1] [2]

    決済ページへのカード窃取スクリプト（スキマー）の設置手法は、環境に応じて使い分けられていた。報告が挙げるのは次の8通りである。

    1. 正規の JavaScript ファイルの末尾に追記する
    2. 決済ページに外部スクリプトのタグを足す
    3. Google タグマネージャーのブロック内に埋め込む
    4. S3／CDN の配信物を汚染する
    5. サーバ側のキャッシュを汚染する
    6. データベースのコンテンツ欄に仕込む
    7. Kubernetes の initContainer を書き換える
    8. 削除された場合に書き戻す cron を仕掛ける

    8番目が実務上いちばん重い。 ある米国のワイン小売では、アプリケーションを再配置した際に決済ページの不正コードが消えたが、攻撃者が残していた定期実行がファイルを確認し、コードを再び書き込んだ。「消したはずなのに戻る」という現象は、ここを見ていないと説明できない。

    配信の入口が分散していることにも注意がいる。自社のサーバだけを見ても、CDN・タグマネージャー・Kubernetes の定義・キャッシュに仕込まれた分は見つからない（本記録の評価）。

    後始末の処理が暴走し、被害企業のバックアップまで消えた業務・事業への影響出典 [1] [2]

    Hermes には「Database Wipe After Extraction（抽出後にデータベースを消す）」というスキルが登録されていた。カード情報を抜いたあと、元のフィールドを分割して消す指示である。

    ある自転車小売では、この後始末の条件が広すぎた。攻撃側が作った一時テーブル（名前が ZQ で始まる）を消す処理の条件に名前に Backup を含むテーブルまで入っており、結果として180のテーブルが削除された。その中には管理者自身が作成したバックアップが含まれていた。

    本記録の作成者の評価として、ここは自律エージェントを使う攻撃の副作用として読むべきである。攻撃者は破壊を意図していない（痕跡を消したかっただけである）。しかし指示の粒度が粗いまま権限の強い処理を任せると、被害は意図を超えて広がる。

    防御側にとっての含意は2つある。第一に、侵害の被害が「情報の持ち出し」で終わらない可能性が上がっている。第二に、バックアップが同じ資格情報で到達できる場所にあると、巻き添えで消える。

    「経済性がふるい落とす」時代が終わったことが、この報告の主張である評価・解釈出典 [1] [2]

    ここからは本記録の作成者の評価を含む。

    Gambit Security は報告をこう締めている。「このキャンペーンは規模以上に重要である。道具はオープンソースで、限界費用は数十ドルの水準にある。もはや経済性が誰かをふるい落とすことはない」（原文英語）。

    これまで、標的型の侵入には人間の時間という制約があった。1社を調べ、突破口を探し、内部を歩き回る作業には、熟練者の数日が要る。その人件費が、狙われる企業を絞っていた。「うちは小さいから狙われない」という判断は、この制約に寄りかかっていた。

    本件はその前提を崩している。

    • 探索は並列で回る（195時間の実時間に633時間分のスキャンが詰まっている）
    • 侵入は放っておけば数時間走り続ける（Cairn）
    • 1社あたりの費用は25.46米ドル

    「割に合わない標的」が消えたということである。中小規模の EC、更新が止まった自社開発の受注システム、社内向けに作った在庫管理——これまで攻撃者の優先順位の下にあった資産が、同じ列に並ぶ。

    もう1つ、防御側の非対称性にも触れておく必要がある。攻撃側は「1つ見つければよい」のに対し、防御側は「全部塞ぐ」必要がある。探索の費用が下がるということは、この非対称性がそのまま拡大するということである。検知と対応（見つけて止める側）に重心を移す根拠が、また1つ増えた（本記録の評価）。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    3本の自律エージェントが探索・侵入・指揮を分担し、決済ページとカードデータへ到達する
    layer 0 は人間の操作者（260セッションで1,951回の短い中国語の指示）。 layer 1 は3本の道具（探索の Strix、侵入の Cairn、指揮と侵入後の作業の Hermes）。 layer 2 は侵入の経路（未認証 SQL インジェクション → ワンタイムパスワードの平文読み取り → 管理画面 → ファイルアップロード → 権限昇格 → 秘密情報の吸い出し）。 layer 3 は到達先と影響（カードデータ・決済ページのスキマー・後始末による破壊）。 1社あたりの費用は平均25.46米ドルである。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    偵察機会はあったが検知できず
    大量の探索は境界のログに残る種類の活動である。 並列で走るため、1ホストあたりの試行密度は人手の探索より高くなりやすい（本記録の評価）
    検知できた公開面への探索的なアクセス（存在しないパスへの多数の試行・異常なパラメータ）を送信元単位で集計しアラート化する
    検知できたWAF の検知モードを監査に回し、遮断していない試行も記録して傾向を見る
    初期侵入機会はあったが検知できず
    数時間にわたる連続試行は、通常の利用とは明確に異なる。 止められなかったのは、試行そのものが監視されていなかったためとみられる（本記録の評価）
    侵入を防げた自社開発部分に対する脆弱性診断の頻度を上げ、SQL インジェクションを重点的に潰す
    影響を限定できたデータベースへのエラー応答を外部に返さない（盲目的な探索の効率を下げる）
    認証情報アクセス機会はあったが検知できず
    発行済みのワンタイムパスワードが本人以外の経路で使われている—— この検知は、発行と使用の相関を取っていれば可能である（本記録の評価）
    侵入を防げたワンタイムパスワードを平文で保存しない（ハッシュ化・短寿命化・単回使用）
    検知できた管理画面へのログインを、発行元の端末・IP・時間帯と突き合わせて異常を検知する
    実行機会はあったが検知できず
    管理画面からのアップロードは正規機能であるため、内容の検査が無ければ区別がつかない
    侵入を防げたアップロード先を実行不可の領域に置き、拡張子ではなく内容で検査する
    検知できた公開ディレクトリへのファイル追加を改変検知の対象にする
    権限昇格公表されていない
    昇格の具体的な経路（設定の不備か既知の脆弱性か）は公表されていない
    侵入を防げたウェブサーバの実行アカウントに sudo を与えない。与える場合は対象コマンドを限定する
    横展開機会はあったが検知できず
    Secrets Manager の一括読み出しは、クラウド側の監査ログに残る種類の操作である。 アラートにしていれば気づけた可能性が高い（本記録の評価）
    検知できたSecrets Manager 等の秘密情報の一括取得を検知条件にし、通常業務での取得パターンと比較する
    影響を限定できたウェブ層の権限から秘密情報の保管先へ直接到達できないよう、役割と権限を分ける
    収集機会はあったが検知できず
    大量のレコードの読み出しは、データベースの監査ログで捉えられる種類の事象である
    侵入を防げたカード情報をアプリケーションから復号できる形で持たない（トークン化・決済代行への委任）
    検知できた決済関連テーブルへの大量読み出しをアラート化する
    影響（暗号化・破壊・改ざん）機会はあったが検知できず
    決済ページの配信物の変更は、外形監視でも検知できる。 実際、ある被害企業では再配置により一度は消えたが、cron により書き戻されている
    侵入を防げた決済ページで読み込む外部スクリプトを許可制にする（CSP・SRI）
    検知できた決済ページの配信物を外形から定期取得し、正本との差分を通知する
    影響を限定できた復旧の際は、書き戻しの仕掛け（cron・スケジュールジョブ）を先に潰す

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • 「うちは小さいから狙われない」という前提を捨てる——1社あたりの費用が25ドルになった
      探索から侵入までを自律エージェントが回し、モデル利用料は1社あたり平均25.46米ドル （最安3.13ドル）。標的を絞っていたのは攻撃者の人件費であり、その制約が外れた
      取るべき行動 インターネットに面した自社資産を棚卸しし、「攻撃者にとって割に合わない」という理由で 優先度を下げていたものを再評価する。判断の根拠を「費用対効果」から 「侵害されたときの影響」に置き換える
    • 決済ページを、自社サイトの中で**別格の資産**として扱う
      被害の中心はカード情報である。2社から60万件超が持ち出され、 19社以上で決済ページにスキマーが設置された。設置手法は8通りで、 自社サーバの外（CDN・タグマネージャー・Kubernetes の定義）も使われている
      取るべき行動 決済ページで読み込むスクリプトの一覧を作り、誰がどの経路で追加できるかを洗い出す。 マーケティング部門がタグマネージャーで自由に追加できる状態なら、承認の仕組みを入れる
    • カード情報を「自社で復号できる形」で持っているかを確認する
      攻撃者は AWS Secrets Manager から鍵を取り出し、Magento のデータベースの カード情報を復号している。暗号化されていても、鍵に到達されれば同じである
      取るべき行動 カード情報の保持の有無と形式（生データ・暗号化・トークン）を確認し、 自社で復号できる形で持っている場合は、トークン化または決済代行への委任を検討する。 検討の結論と理由を記録に残す
    • バックアップが本番と同じ資格情報で消せる場所にないかを確認する
      ある被害企業では、攻撃側の後始末の処理が暴走し、 管理者が作成したバックアップを含む180のテーブルが削除された
      取るべき行動 バックアップの保管先・認証・削除権限を確認し、本番の侵害で巻き添えにならない構成 （別アカウント・書き換え不可の保管・オフライン）にする。復元の訓練を年1回行う
    • 侵害の被害想定に「意図しない破壊」を加える
      攻撃者は破壊を意図していなかったが、粗い指示で権限の強い処理を自律エージェントに 任せた結果、データベースのテーブルが大量に削除された
      取るべき行動 事業継続計画の被害想定に「情報の持ち出しに加えてデータが失われる」場合を入れる。 復旧時間の目標（RTO）と、失われた場合の業務の代替手段を決めておく
    セキュリティ技術者への示唆
    • 決済ページの配信物を外形から定期取得し、正本との差分を見る
      スキマーは JavaScript への追記・外部スクリプトのタグ・タグマネージャー・S3／CDN の汚染・ キャッシュの汚染・データベースのコンテンツ欄・Kubernetes の定義と、8通りで仕込まれた。 自社サーバのファイルだけを見ても見つからない経路がある
      取るべき行動 実際のブラウザから見える決済ページを定期取得し、読み込まれるスクリプトの一覧と 内容のハッシュを記録して差分を通知する。CSP と Subresource Integrity を併用する
    • 「消しても戻る」ときは、書き戻しの仕掛けを先に探す
      ある米国のワイン小売では、アプリケーションの再配置で不正コードが一度消えたが、 攻撃者が残していた定期実行がファイルを確認して再び書き込んだ
      取るべき行動 侵害対応の手順に「cron・systemd タイマー・スケジュールジョブ・ Kubernetes の CronJob の棚卸し」を明示的な工程として入れる。 復旧の前にこれを済ませる
    • ワンタイムパスワードを平文で保存しない
      本件で多要素認証は破られていない。データベースから発行済みのワンタイムパスワードが 平文で読めたために迂回された
      取るべき行動 ワンタイムパスワードの保存形式を確認し、ハッシュ化・短寿命化・単回使用を徹底する。 問い合わせ対応で値を参照する運用がある場合は、参照に代わる確認手段を用意する
    • 秘密情報の一括取得をアラートにする
      攻撃者は WordPress の認証情報を取得したあと、AWS Secrets Manager の内容を吸い出している。 この操作はクラウドの監査ログに残る種類のものである
      取るべき行動 Secrets Manager 等への一括取得・列挙の操作を検知条件として設定し、 通常業務での取得パターン（実行主体・時間帯・頻度）を計測して閾値を決める
    • 探索の連続と、その直後の認証成功を結びつけて見る
      Strix が並列で探索し、Cairn が数時間にわたって試行を続けている。 個々の試行は WAF の遮断で終わっていても、その後に管理画面のログインが成功していれば異常である
      取るべき行動 WAF の遮断ログと認証ログを同じ基盤に集め、 「同一送信元・同一ネットワークでの探索 → 認証成功」を検知条件として実装する

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ 自社ドメインで決済ページを提供し、カード情報の入力を自社の画面で受けている本件の被害の中心は決済ページに仕込まれたスキマーで、19社以上で設置が確認されている
    データの保持□ カード情報を保持しており、アプリケーションから復号できる（鍵がクラウドの秘密情報管理にある）攻撃者は AWS Secrets Manager から鍵を取り出し、Magento のデータベースのカード情報を復号した
    システム構成□ 自社開発のウェブアプリケーションが公開面にあり、直近の脆弱性診断から1年以上経っている侵入の起点は自社開発部分に残っていた未認証の SQL インジェクションだった。 攻撃者は「独自ソフトウェアを動かしている会社」を優先して選んでいる
    認証・認可□ ワンタイムパスワードをデータベースに保存しており、保存形式を確認していない本件では多要素認証が破られたのではなく、ワンタイムパスワードが平文で読めたために迂回された
    運用・監視□ 決済ページで読み込む外部スクリプトの一覧を持たず、タグマネージャーからの追加に承認が要らないスキマーの設置手法には、Google タグマネージャーへの埋め込みと CDN の汚染が含まれる
    運用・監視□ バックアップが本番と同じ資格情報で削除できる場所にある攻撃側の後始末の処理が暴走し、管理者が作成したバックアップを含む180のテーブルが削除された
