INC-2026-0215パルグループが老朽化 VPN から侵害

アパレル・雑貨のパルグループホールディングス（3COINS・CIAOPANIC 等約50ブランド）で2024年6月16日にデータセンターの約100台のサーバが一斉に停止し、フォレンジック調査で侵入経路が「老朽化したメンテナンス用のリモート VPN → 老朽化した勤怠システムのサーバ → Active Directory サーバ」だったと判明した——AD 配下の全端末が不正アクセス可能な状態に至り、大阪本社・関連会社・店舗のクライアント PC にも影響が及んだため同社はインターネットを遮断し、店舗にポケット型 Wi-Fi 900台を配って営業を続けた。復旧は既存データセンターへの再構築ではなく AWS への移行を選び、7月29日に POS・店舗システム、8月5日に販売管理システムを復旧させた。役職員の氏名・住所・給与振込口座番号・メールアドレスと休職者の傷病情報に漏えいの可能性があるとして6月17日に個人情報保護委員会へ報告している。侵入手段（脆弱性か認証情報か）・ランサムウェアであったか・漏えいの確定と件数はいずれも公表されていない

不正アクセス・侵害システム障害続報が止まり調査も完了日本の組織が当事者脆弱性の放置公表されていない／不明
初報: 2024年6月28日 最終更新: 2026年9月25日

株式会社パルグループホールディングス（東証プライム・証券コード2726。「3COINS」「CIAOPANIC」「Kastane」「un dix cors」など約50ブランドを展開）のデータセンターに集約されていた約100台のサーバが、2024年6月16日（日）に一斉に停止しました。各店舗の売上が見られなくなり、システムへのログイン、商品の発注・移動もできなくなっています。同社は6月28日、第三者による不正アクセスが原因だと公表しました。

侵入経路が示されたのは、2年後の2026年6月25〜26日に行われた講演（AWS Summit Japan 2026。同社 IT統括室リーダーと復旧を支援した TOKAI コミュニケーションズの担当者）で、その内容を再構成した記事が2026年9月25日に公開されました。フォレンジック調査で分かった経路は次のとおりです。

老朽化したメンテナンス用のリモート VPN から侵入し、同じく老朽化した勤怠システムのサーバを経由してActive Directory サーバを攻撃した

これにより AD の管理下にある全ての端末が不正アクセス可能になりました。被害はデータセンターにとどまらず、ネットワークでつながる大阪本社・関連会社・店舗のクライアント PCにも広がり、同社は感染拡大の防止のためインターネットを遮断しています。結果としてメールと社内ファイル共有も止まりました。

小売業なので、本社が止まっても店舗は営業しなければなりません。同社は復旧作業の前に本社の感染 PC を交換し、基幹システムから分離していた SNS 専用回線で本社の接続を確保し、店舗にはポケット型 Wi-Fi を900台配布しました。EC サイト「PAL CLOSET」と SNS 用の基盤を別環境に置いていたため、この2つは被害を免れています。

復旧先には、既存データセンターの別環境・別事業者のデータセンター・AWS の3案が検討され、AWS への移行が選ばれました。7月29日に POS・店舗システム、8月5日に販売管理システムを復旧し、8月末の他社ブランド事業の譲受にも間に合わせています。

個人情報については、現役・過去の役職員の氏名・住所・給与振込銀行口座番号・メールアドレス、および休職者の傷病の情報に漏えいの可能性があるとして、6月17日に個人情報保護委員会へ報告されています。PAL CLOSET の会員情報は別システムのため漏えいしていないとされました。

この事案を記録する理由は2つあります。第一に、入口が「基幹システム」ではなく、誰も更新していなかった保守用の経路と勤怠システムだったことです。第二に、止まった基盤をそのまま建て直さず、クラウドへ移す判断を事故の最中に通した経過が、講演という形で当事者の口から語られている点です。

本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。ランサムウェアであったか、身代金の要求があったか、漏えいが確定したかはいずれも公表されておらず、推測で補いません。

入口は「老朽化したメンテナンス用のリモート VPN」と勤怠システムのサーバだった原因・手口出典 [5]

フォレンジック調査で判明した経路は、2026年6月の講演で次のように説明されている。

攻撃者は老朽化したメンテナンス用のリモート VPN から侵入し、同じく老朽化した勤怠システムのサーバを経由して「Active Directory」（AD）サーバを攻撃した。これにより、AD の管理下にある全ての端末に不正アクセスが可能になった

3つの段が並んでいる。保守用に残されたリモート接続、業務の主役ではない勤怠システム、そして認証の中心である ADである。守る側の資産一覧では前2つの優先度は低くなりやすい。それでも AD に到達されれば、配下の端末は全て射程に入る（本記録の評価）。

一方で、「老朽化」が何を指すのかは公表されていない。未適用の修正か、使い回しや初期設定のままの認証情報か、多要素認証の無い保守経路そのものか。製品名もバージョンも示されていないため、読者は自社の同種資産を「どの条件に当てはまれば危ないのか」で点検することができない。本記録は、この点を未確定事項として残す。

  • 基幹システムから分離していた SNS 専用回線を使って本社のインターネット接続を確保した
  • 店舗にポケット型 Wi-Fi を900台配布した

講演では、EC サイト「PAL CLOSET」と SNS 用の基盤を別環境に置いていたことが「唯一の救い」と語られている。この2つは被害を免れ、本社と店舗の連絡手段の確保につながった。同社はこれを「解決策ではなく、店舗運営をするための応急処置」と位置づけている。

6月28日の公表時点（12時時点）では、全店が通常営業しており各種決済も利用できた。EC も通常営業だった。残っていた利用者への影響は、店舗の PAL CLOSET アプリのポイント付与が翌日反映できていないという点である。

社内側の影響はこれとは別に残った。第1四半期の決算サマリー（7月30日公表）では、既存店客数・客単価の推移の欄に「現在、復旧作業中でございます。」と記されている。決算発表そのものも、当初予定の7月9日から7月30日へ延期された。売上は過去最高を更新した四半期でありながら、自社の数値を出せない状態が続いていたことが、当事者の資料に残っている（本記録の読み）。

止まった基盤を建て直さず、事故の最中にクラウド移行の承認を取った復旧の経過出典 [5]

復旧方法として検討されたのは3案である。

  1. 既存のデータセンターの別環境で新規構築する
  2. 別事業者（TOKAI コミュニケーションズ）のデータセンターを新規契約して新規構築する
  3. AWS で新規構築する

同社はそれまで、経営判断としてセキュリティ上の理由からデータセンターを選択してきた。講演ではクラウド化に強く反対する役員もいたため調整に時間がかかったとされ、説得の結果、一部のサーバを除いてクラウド化の承認を得たと説明されている。

復旧の順序はこうである。

  • 7月2日：AWS 環境の整備を開始。更新検証用に構築済みだった環境を流用し、クローン方式でシステムとデータを復旧する方針を採った
  • 7月8日：POS システムと販売管理システムのデータ復旧に着手。通信ログを取得し、セキュリティグループで業務に使うポートのみ許可。AWS 上に AD サーバを構築
  • 7月29日：POS システムと店舗システムを復旧
  • 8月5日：販売管理システム・POS サーバ・AD サーバなど主要サーバの移行を完了

当初の移行目標は9月末だった。これが前倒しされたのは、8月末に予定されていた女性向けアパレルブランド「w closet」の事業譲受のために販売管理システムを8月初めに使える状態にする必要があったからだと説明されている。講演では「本来であれば年単位のプロジェクトを一気にやり遂げた」と語られている。

復旧の過程では、フォレンジック調査と SOC の調査で攻撃に使われた検体を検知・駆除できることを確認したうえで、全 EC2 インスタンスに EDR を導入している。復旧環境に同じものを持ち込まない確認を工程に入れている点は、移行の速度とは別に評価できる（本記録の評価）。

復旧後の再構築で、認証を AD のログインだけに依存する形から変えた再発防止出典 [5]

復旧後の再構築として、講演では次の内容が挙げられている。

  • インターネット回線を統合し、UTM を通過した通信の全ログを SIEM に取り込む。怪しい動きはアラートで配信し、早期に初動対応できるようにした
  • 約1000店舗の IP-VPN を、1週間かけて SD-WAN に切り替えた
  • 認証は以前は AD のログイン認証だけだった。認証局を設けて証明書ベースの認証を採用し、多要素認証も加えた
  • 閉域網を BroadLine に切り替え、AWS とは AWS Direct Connect で接続して冗長化した
  • AWS 側では操作ログの収集・振る舞い検知・脆弱性検査の機能を活用した
  • RPO・RTO に基づく復旧訓練を実施し、最終試験では以前は約2か月かかった業務復旧を約6時間で完了した

入口が保守用の VPN、経由地が勤怠システム、到達先が AD だったこの事案に対し、認証の作りを変えたこととログを1か所に集めたことは、経路の各段に対応している（本記録の評価）。一方で、保守用の接続経路そのものをどう棚卸ししたか、勤怠システムのような非基幹システムの更新をどう回す体制にしたかは、公表された内容からは読み取れない。老朽化した資産が入口だった事案としては、ここが最も知りたい部分である。

漏えいの可能性は役職員の情報と休職者の傷病情報、確定は公表されていない被害規模・影響範囲出典 [1]

2024年6月28日の公表による個人情報の記載は次のとおりである。

当社の現役職員・過去に在籍されていた役職員のお名前・ご住所・給与振込銀行口座番号・メールアドレスや休職者の傷病の情報が漏洩する可能性があります

休職者の傷病の情報が含まれる点は重い。要配慮個人情報にあたる性質の情報が、役職員の口座番号とともに同じ範囲に入っている。

一方、PAL CLOSET の会員情報については、「今回トラブルが発生したシステムとは別システムで運用しているため WEB、アプリ等を含め漏洩しておりません」と明記されている。EC と SNS を別環境に置いていたという構成が、被害を免れた理由と、会員情報の否定の根拠の両方になっている。

件数は公表されていない。 また、本記録の作成者が確認した範囲では、その後に漏えいの確定・件数・本人通知の完了を示す公表は見当たらない。「可能性」の段階のまま2年が経過していることになる。個人情報保護委員会への報告は障害の翌日（6月17日）に行われている。

評価——この事案から日本の読者が持ち帰れるのは「棚卸しの外にあった資産」である評価・解釈出典 [1] [2] [5]

以下は本記録の作成者の評価である。

第一に、入口は守る対象として意識されていなかった資産だった。メンテナンス用のリモート VPN と勤怠システムのサーバ。どちらも売上に直結せず、更新の優先度が上がらない。だが前者は外向きの入口で、後者は内側のネットワークに居る。「重要システム」の定義を業務の重要度で切ると、この2つは必ず外側に落ちる。入口になりうるかどうかは、業務上の重要度と無関係である。

第二に、AD に到達された時点で影響範囲は「全端末」に変わる。本件では AD 配下の全端末が不正アクセス可能な状態になり、データセンターの外（本社・関連会社・店舗の PC）まで影響が及んだ。ネットワークが平坦であれば、1台の踏み台から認証の中心までの距離は短い。

第三に、事業が止まらなかったのは「分けてあった」からである。 EC と SNS 用の基盤が別環境だったことで、店舗と本社の連絡手段を作り直せた。これは事故後の判断ではなく、事故の前に済んでいた構成である。分離の価値は平時には見えず、止まったときに初めて回収される。

第四に、復旧の選択は技術ではなく意思決定の問題だった。 3案のうち AWS が選ばれた経緯として、講演では「クラウド化に強く反対する役員もいた」「調整に時間がかかった」と語られている。事故の最中に方針転換の合意形成をしたことになる。これを美談としてだけ読むのは危うい。平時に選択肢を比較しておけば、その調整の時間は復旧に使えたはずである。

第五に、公表の粒度と学びの粒度は別である。当事者の公表文は「第三者による不正アクセス」までで、経路は書かれていない。経路が分かったのは2年後の講演である。読者にとって有用な情報が、公表ではなく講演という経路で出てきたという事実そのものが、この事案の記録に値する部分である。講演は文書として公開されておらず、記事の再構成を通じてのみ参照できる。

CISO・経営層への示唆
  • 「重要システム」の一覧に入らない資産こそ入口になる
    入口は保守用のリモート VPN、経由地は勤怠システムのサーバだった。どちらも売上に直結せず、 更新と監視の優先度が上がりにくい資産である
    取るべき行動 資産台帳を「業務の重要度」ではなく「外部から到達できるか」「認証基盤に到達できるか」で 並べ替え、保守用経路と非基幹システムに更新期限と責任者を割り当てる。 保守終了（EOL）を過ぎた機器は期限付きの隔離計画とセットで台帳に残す
  • 事業継続の分離は、事故の前に済んでいなければ回収できない
    EC と SNS 用の基盤が別環境だったことで、店舗と本社の連絡手段を作り直せた。 これは事故後の工夫ではなく事故前の構成である
    取るべき行動 事業が止まったときに最初に必要になる系統（連絡手段・売上の把握・決済）を洗い出し、 基幹系と障害の影響が共有されない構成にする。分離の妥当性を年1回、 「基幹系が全断したときに何が残るか」で検証する
  • 復旧方式の選択肢は平時に比較しておく。事故の最中の合意形成は復旧時間を食う
    復旧方式は3案が比較され、従来の方針（データセンター）からクラウドへ転換したが、 強く反対する役員もいたため調整に時間がかかったと説明されている
    取るべき行動 大規模障害時の復旧方式（既存環境の再構築／別拠点／クラウド）を平時に比較し、 判断基準と決裁の経路を文書化する。復旧のための一時的な例外（調達・稟議）を 事前に承認しておく
  • 「漏えいの可能性」で止めない。確定報まで出す前提で工程を持つ
    役職員の口座番号と休職者の傷病情報という重い範囲に可能性が示されたが、 本記録の作成者が確認した範囲では確定報・件数・本人通知の完了の公表が見当たらない
    取るべき行動 初報の時点で「いつまでに何を確定させて追加公表するか」を社内の工程として決め、 確定できなかった場合もその理由を出す。要配慮個人情報が範囲に入るときは 通知の方法と完了の確認を工程に含める
  • 復旧で構成を変えるなら、同じ侵害を持ち込まない確認を工程に入れる
    本件はフォレンジックと SOC の調査で検体を検知・駆除できることを確認したうえで 新環境を立ち上げ、全インスタンスに EDR を導入している
    取るべき行動 復旧計画に「侵害の除去の確認」と「新環境での検知の動作確認」を明示の工程として入れ、 完了の判定者を決める。移行の期日に押されて省略されない位置に置く
セキュリティ技術者への示唆
  • 保守用のリモート接続は、既定で閉じておく
    侵入は「老朽化したメンテナンス用のリモート VPN」から始まった。 常設されていれば、更新されない期間がそのまま露出期間になる
    取るべき行動 保守経路を常時接続から申請ベースの都度開放に変える。残す場合は多要素認証・ 送信元制限・接続記録の常時監視を必須にし、四半期ごとに棚卸しして 使っていない経路を閉じる
  • 非基幹サーバから認証基盤へ到達できる経路を潰す
    勤怠システムのサーバが Active Directory サーバへの踏み台になり、 AD 配下の全端末が不正アクセス可能になった
    取るべき行動 サーバ間通信を既定拒否にし、業務上必要な経路だけを明示的に許可する。 認証基盤（AD）への管理系アクセスは専用の管理端末・専用経路に限定する
  • ログは事故の後に集めても間に合わない。集約の場所を先に作る
    侵入経路の特定はフォレンジックで可能だったが、復旧後に「UTM を通過した全ログを SIEM に 取り込む」構成へ変えたと説明されており、事案当時は集約されていなかったと読める
    取るべき行動 境界・認証基盤・サーバの記録を1か所へ集約し、保持期間を侵害の想定滞留時間より長く取る。 認証失敗の急増と、通常発生しないサーバ間通信に警報を置く
  • 復旧用の検証環境を平時から本番と同じ手順で作っておく
    AWS に用意していた更新検証用の環境をそのまま復旧に流用し、クローン方式で復旧している。 これが約1か月での主要サーバ移行を支えた
    取るべき行動 本番相当の検証環境を別障害ドメインに置き、復元手順を定期的に実行して所要時間を実測する。 RPO・RTO を訓練の実測値で更新する（本件の最終試験では約2か月→約6時間に短縮した）
  • 店舗・拠点のネットワークは、本社の全断を前提に設計する
    インターネットの遮断でメールとファイル共有が止まり、店舗はポケット型 Wi-Fi 900台の配布で つないだ。復旧後は約1000店舗の IP-VPN を SD-WAN へ切り替えている
    取るべき行動 拠点側に代替の接続手段（モバイル回線等）を事前に確保し、認証・決済が本社経由でなくても 成立する構成を用意する。切替手順を訓練に含める

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 保守・運用のためのリモート接続経路（VPN・リモートデスクトップ・保守回線）が常設で残っている本件の入口は老朽化したメンテナンス用のリモート VPN だった。業務の重要度が低い経路でも、 外部から到達できる点は基幹システムと同じである
運用・監視□ 勤怠・入退室・複合機のような非基幹システムが、更新計画と監視の対象から外れている経由地は老朽化した勤怠システムのサーバだった。内部に居る資産は、 更新されないまま踏み台として使える状態で残る
認証・認可□ Active Directory の管理者権限が、通常の端末・通常の経路から使えるAD サーバが攻撃された時点で、配下の全端末が不正アクセス可能な状態になった。 影響範囲は AD の管理範囲とそのまま一致する
システム構成□ EC・連絡手段・決済などの事業継続に不可欠な系統が、基幹系と同じ基盤・同じネットワークに載っている本件で被害を免れたのは別環境に置かれていた EC と SNS 用の基盤だけで、 そこが復旧期間中の連絡手段の土台になった
運用・監視□ 境界・認証基盤・サーバのログが1か所に集まっておらず、保持期間も把握していない復旧後に全ログを SIEM に集約する構成へ変えている。集約が無い状態では、 侵入の検知も滞留時間の判定もできない
体制・契約□ 大規模障害時の復旧方式（既存環境の再構築／別拠点／クラウド）を平時に比較しておらず、決裁の経路も決まっていない本件では事故対応と並行して方針転換の合意形成が必要になり、調整に時間がかかったと説明されている
