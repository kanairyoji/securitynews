INC-2026-0216Cloudflare でテナント間の残留データ露出

Cloudflare の Containers と Sandboxes で、同じサーバに同居した他の顧客のコンテナが使い終えて返したディスク領域の中身を、あとから来たコンテナが読めていた——原因は共有ディスクの構成で「新しく割り当てるブロックをゼロで埋める」既定の動作を外していたことで、64KiB のブロックに4KiB だけ書き込むと残り60KiB に前の利用者のデータが残っていた。研究者は本番環境の試験で24回中18回・4大陸の22台中20台から残留物を回収し、ディレクトリ構造・SQLite データベース・Chromium のプロファイル・.env・認証情報ファイルが含まれていた。Cloudflare は2026年9月4日の報告当日に修正を展開し、稼働中のコンテナのディスクとイメージのキャッシュの掃除を9月19日に終え、9月24日に公表した。攻撃側は対象の顧客・ワークロード・データを選べず、残留データの存在も保証されない。露出がいつから始まっていたかは公表されていない

意図せぬ露出（設定不備等で外部から到達可能だった）脆弱性続報が止まり調査も完了有名事象として記録（日本と直接の関係は薄い）設定不備設計・実装上の不備
初報: 2026年9月24日 最終更新: 2026年9月25日

Cloudflare は2026年9月24日、同社の Containers（顧客のプログラムを共有サーバ上のコンテナで動かすサービス）と、その上で動く Sandboxes（信頼できないコードや AI エージェントが書いたコードを安全に実行する用途で売られている）に、同じサーバに同居した他の顧客のコンテナが使い終えて返したディスク領域の中身を読めてしまう欠陥があったことを公表しました。

仕組みはこうです。各コンテナのディスクは Linux の dm-thin（シンプロビジョニング）で作られ、領域は 64KiB 単位で割り当てられます。コンテナが削除されると、そのブロックは複数の顧客アカウントにまたがる共有プールへ戻ります。このプールには新しく割り当てるブロックをゼロで埋める処理を省く設定が入っていました。そのため、再利用されたブロックに4KiB だけ書き込むと、残りの60KiB には前の利用者のデータが残ったままになり、生のディスクとして読み出せました。

報告したのはセキュリティ企業 Accomplish の Oren Yomtov 氏で、2026年9月4日15時26分（UTC）にCloudflare のバグバウンティ（HackerOne）経由で報告しています。研究者側の記述によれば、本番環境での試験で24回中18回、4大陸にまたがる22台のうち20台で残留物が見つかり、回収されたものにはディレクトリ一覧・SQLite データベース・Chromium のプロファイル・.env ファイル・認証情報ファイルが含まれていました。Cloudflare 自身も「ディレクトリ構造、データベースのページ、構造として完全な SQLite データベース」が含まれていたとしています。

対応は速く、報告と同じ9月4日のうちに修正を統合してロールアウトを開始し、9月7日に完了、すでに稼働中のコンテナのディスクと各サーバに用意されたイメージ層のキャッシュまで掃除し終えたのが9月19日、公表はその5日後の9月24日でした。

影響の限定条件も示されています。実行には有償の Workers アカウントが必要で、どの顧客・どのワークロード・どのホスト・どのデータを狙うかは選べず、残留データが存在する保証もありません。稼働中の他顧客のデータを書き換えられること、ワークロードを停止させられることは示されていません。

この事案を記録する理由は、「信頼できないコードを安全に実行する場所」として売られている基盤の分離が、計算やメモリではなくディスクの後片付けで破れた点にあります。AI エージェントに使い捨ての実行環境を与える構成はいま急速に広がっており、その実行環境が他人の秘密情報を拾ってくる側になりうることを、実測付きで示した事例です。

本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。露出がいつから始まっていたか（設定がいつ入ったか）とテレメトリの保持期間は公表されておらず、推測で補いません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

研究者が有償の Workers アカウントで Containers 上にコンテナを起動し、未使用領域に4KiB を書き込んで 64KiB のブロックの割り当てを誘発し、そのブロック全体を生のディスクとして読み戻すことで、 先に同じサーバで動いていた他の顧客のコンテナの残留データを回収した。 実際の攻撃者による悪用は確認されていない（確認の範囲は保持されていたテレメトリ）。

    「使い終えたディスクを掃除しない」設定ひとつで、隣の顧客の中身が読めていた概観出典 [1]

    Cloudflare の説明によれば、起きていたことは次のとおりである。

    • Containers は各コンテナに書き込み可能なルートディスクを与える。作りは Linux のdm-thin（device mapper thin provisioning）で、領域は 64KiB 単位で割り当てられる
    • コンテナが削除されると、そのブロックは複数の顧客アカウントのワークロードに供される1つのプールへ戻る
    • そのプールには、新しく割り当てるブロックをゼロで埋める処理を省く設定が入っていた（ゼロ化は通常は既定で有効である）
    • 結果として、再利用されたブロックに小さい書き込み（4KiB）を行うと、書いていない残り60KiB には前のコンテナのデータが残ったままになり、生のディスクとして読み出せた

    計算の隔離でもメモリの隔離でもなく、後片付けの省略が分離を破っていた。そしてこの欠陥は、信頼できないコードを安全に動かす場所として売られているSandboxes にもそのまま及んでいた。Sandboxes は Containers の上で動くため、同じディスクの作りを共有していたからである（本記録の整理）。

    本番で24回中18回、4大陸の22台中20台から残留物が出た被害規模・影響範囲出典 [1] [2] [3]

    研究者の手法は単純である。未使用の領域に4KiB のブロックを1つ書き込み、そのブロック全体を生のディスクとして読み戻す。書いていない60KiB に前のコンテナのデータが残っていた。

    規模については、報道が伝える研究者の報告値として次の数字が示されている。

    • 本番環境での試験で、24回中18回で残留物が見つかった
    • 4大陸にまたがる22台の物理サーバのうち20台で見つかった
    • いずれの回も、サーバを選んだのは Cloudflare である（顧客はホストを指定できない）

    回収された中身は、Cloudflare の記述では「ディレクトリ構造、データベースのページ、構造として完全な SQLite データベース」であり、研究者側の記述では「ディレクトリ一覧、SQLite データベース、Chromium のプロファイル、.env ファイル、認証情報ファイル」（原文英語）で、これらを他の顧客のファイルだと述べている。

    .env と認証情報ファイルが並んでいる点に実務上の意味がある。残留データの取得は次の侵害の材料になりうる。もっとも、どの顧客の何が取れるかを攻撃側が選べないという制約もそのまま効いており、狙った組織の秘密を抜く手段としては使えない（本記録の評価）。

    攻撃側が選べないこと、できなかったことも示されている評価・解釈出典 [1] [3]

    Cloudflare が明示した限定条件は次のとおりである。

    • 実行には有償の Workers アカウントが必要だった
    • 特定の顧客・ワークロード・ホスト・データを狙うことはできない（原文英語。ホストの割り当ては Cloudflare が行う）
    • 残留データが存在する保証はない
    • 稼働中の他顧客のデータを書き換えられること、ワークロードを停止させられることは示されていない

    つまり、これは標的型の攻撃に使える欠陥ではなく、無作為に他人の残り物を拾える欠陥である。そのぶん「誰が何を取られたか」を事後に特定することも難しくなる。Cloudflare は顧客への個別通知については述べていない（本記録の確認）。

    以下は本記録の作成者の評価である。無作為であることは、影響が小さいことを意味しない。同じ基盤に多数のテナントが載る構成では、無作為な抽出を繰り返すだけで、いずれかの顧客の秘密情報に当たる確率は積み上がる。研究者の実測が「24回中18回」という高い割合だったことは、その積み上がりが速いことを示している。

    注目すべきなのは、ゼロ化を有効に戻すだけでは終わらなかったことである。その変更は「これから割り当てるブロック」に効くが、すでに稼働中のコンテナのディスクに割り当てられていたブロックと、各サーバに用意された起動用イメージ層のキャッシュは掃除されない。後者は新しいコンテナが引き継いで読める。そのため Cloudflare はサーバを順次空けて再起動する作業を、負荷の低い時間帯に行っている。

    修正の投入は数時間、残留物の掃除は15日。 これは緩い対応ではなく、「設定を直す」と「すでに配られた領域を回収する」が別の仕事であることを示している（本記録の評価）。

    悪用の有無は「保持していたテレメトリの範囲で」見つからなかった未確定事項出典 [1]

    Cloudflare は悪用の有無を次のように調べたとしている。

    • 研究者の実証コードと、自社で再現した攻撃から検知の署名を作った
    • それを保持していた過去のディスク I/O のテレメトリに当てた
    • 4KiB の書き込みと読み出しの特徴的な並び、ext4 のディレクトリブロックのチェックサムによる検証などを手掛かりにした
    • 見つかったのは研究者と自社エンジニアによる許可された検証のみで、「この手法が他者に使われた証跡は見当たらない」とした

    ここには2つの留保がある。第一に、調べられたのは保持されていた記録の範囲であり、その保持期間は公表されていない。第二に、ゼロ化を省く設定がいつ入ったのかも公表されていない。この2つが分からないと、未検査の期間があるかどうかが判断できない。Cloudflare 自身も「どれだけの期間 露出していたかは、この説明からは明らかでない」と読める書き方にとどめている（本記録の読み）。

    「悪用は確認されていない」という結論は、それを確認できるだけの記録があった場合にのみ意味を持つ。本件はその前提が示されていない（本記録の評価）。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    削除されたコンテナのディスクブロックが、掃除されずに次の顧客へ渡る流れ
    layer 0 は共有サーバ上で先に動いていた他の顧客のコンテナ。layer 1 は削除によって返却された 物理ブロックと、それを受け取る共有プール（ゼロ化を省く設定が入っていた）。 layer 2 はあとから同じサーバに割り当てられた研究者のコンテナ。 layer 3 は回収された中身。layer 4 は修正と掃除の範囲である。 ホストの割り当てを行うのは Cloudflare であり、攻撃側は対象を選べない。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    内部探索現実的な検知機会なし
    自コンテナ内での構成の観察であり、提供者側から見て異常な操作として現れない
    侵入を防げた共有ストレージのプールでは割り当て時のゼロ化（または discard/trim による消去）を既定から外さない
    侵入を防げたテナント間で物理ブロックを再利用するプールを、アカウント境界で分離する
    収集機会はあったが検知できず
    事後に Cloudflare は「4KiB の書き込みと読み出しの特徴的な並び」から検知の署名を作れている。 つまり**記録の上では見分けられる挙動**だった。事案発生時にその検知は置かれていなかった
    検知できたディスク I/O の記録に、割り当て直後のブロック全体読み出しのような不自然な並びを検知する規則を置く
    影響を限定できたコンテナのルートディスクへの生アクセス（ブロックデバイス層への直接読み出し）を制限する
    影響（暗号化・破壊・改ざん）公表されていない
    データを取られた側（他の顧客）に検知の機会は無い。自社のコンテナは正常に動作しており、 残留ブロックが読まれたことは利用者側から観測できない
    影響を限定できた使い捨ての実行環境に、失効可能でない長期の認証情報を置かない
    影響を限定できたサンドボックスへ渡す秘密情報を短命の資格情報に置き換え、利用後に確実に失効させる

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    判断評価評価の根拠と留保
    報告から20日後、掃除の完了（9月19日）から5日後に公表した。研究者側の公表と同日である機能した本記録の作成者の評価である。修正の完了後・掃除の完了後という順序は妥当で、 時系列を分単位で開示し、限定条件と「できなかったこと」まで書いている点も評価できる。 ただし**露出の開始時期とテレメトリの保持期間の欠落は、公表の質の中で最も重い欠落**である
    顧客側の対応は不要とし、影響を受けた可能性のある顧客への個別通知については述べなかった部分的に機能本記録の作成者の評価である。「対応は不要」は修正の観点では正しいが、 **サンドボックスに .env や認証情報ファイルを置いていた利用者にとっては不要ではない**。 残留データとして回収されうる対象に認証情報が含まれていた事実が示されているのだから、 「置いていた秘密情報の失効を検討せよ」という案内は成立したはずである
    CISO・経営層への示唆
    • 「安全な実行場所」として売られている基盤も、他テナントとの同居を前提に扱う
      Sandboxes は信頼できないコード（AI エージェントが書いたコードを含む）を安全に動かす用途で 売られていたが、ディスクの後片付けの省略でテナント間の分離が破れていた
      取るべき行動 外部のサンドボックス・コンテナ実行環境に置くデータを分類し、 「他テナントに読まれても致命的でないもの」に限る方針を明文化する。 専用インスタンス・専有ホストの選択肢と価格差を把握しておく
    • 使い捨ての実行環境に長期の認証情報を置かない
      残留ブロックから回収された対象に .env ファイルと認証情報ファイルが含まれていた。 提供者は「顧客の対応は不要」としており、失効の案内は出ていない
      取るべき行動 サンドボックス・CI・エージェント実行環境へ渡す資格情報を短命（分〜時間単位）の発行に切り替え、 長期キーの持ち込みを禁止する。持ち込みが必要な場合は失効手順と棚卸しの期日を決める
    • 「悪用の証跡なし」は、記録の保持期間と露出期間が分かって初めて意味を持つ
      Cloudflare は保持していたディスク I/O テレメトリの範囲で悪用の証跡が無いとしたが、 保持期間も露出の開始時期も公表していない
      取るべき行動 委託先・クラウドの事故報告を受け取ったとき、「調査対象期間」「記録の保持期間」 「露出の開始時期」の3点を必ず確認する。回答が無い場合は、自社側で 「置いていた期間ぶんは露出したものとして扱う」判断基準を持つ
    • 提供者からの通知が来ない事故がある。自社の判断基準を先に決めておく
      対象を選べない欠陥では、誰が影響を受けたかを提供者も特定できない。 本件で顧客への個別通知の記述は無く、利用者は自社の影響を知る手段を持たない
      取るべき行動 利用しているマルチテナント基盤ごとに「その基盤に何を置いているか」の一覧を持ち、 提供者が欠陥を公表した時点で自動的に棚卸し・失効の判断に入る手順を定める
    セキュリティ技術者への示唆
    • 共有ストレージでは、領域を返すときと渡すときのどちらかで必ず消す
      dm-thin のプールでゼロ化を省く設定が入っていたため、64KiB のブロックに4KiB だけ書くと 残り60KiB に前の利用者のデータが残った
      取るべき行動 シンプロビジョニング・薄いボリューム・仮想ディスクを扱う自社基盤で、 割り当て時のゼロ化または解放時の discard/trim が有効かを実測で確認する。 性能のために消去を外している箇所を洗い出し、テナント境界をまたぐものは戻す
    • 設定を直しても、すでに配られた領域は残る
      ゼロ化を戻す変更は新規割り当てにしか効かず、稼働中コンテナのディスクと各サーバの イメージ層キャッシュは掃除されないため、Cloudflare はサーバを順次空けて再起動した
      取るべき行動 データ残留の修正計画に「既に割り当て済みの領域」「キャッシュ・スナップショット・ イメージ層」の掃除を別項目として立て、完了の判定方法を決める。 設定変更の完了を修正完了と呼ばない
    • 残留データの読み出しは、記録の上では見分けられる挙動である
      Cloudflare は事後に「4KiB の書き込みと読み出しの特徴的な並び」から検知の署名を作り、 過去のテレメトリに当てている。つまり検知可能な特徴があった
      取るべき行動 自社がマルチテナントのストレージを提供する場合、割り当て直後のブロック全体読み出しや 未書き込み領域の走査に相当する I/O 列に検知を置く。 テレメトリの保持期間を「露出の想定期間より長く」設計する
    • エージェント用サンドボックスの中身は、外に出る前提で組む
      7月以降、Claude Cowork・Claude Code・Cursor CLI・Docker・OpenAI Codex・Cloudflare と、 同じ研究チームによる6件の脱出が公表されている。分離の実装は成熟していない
      取るべき行動 サンドボックスに投入するリポジトリ・データセット・資格情報を最小限にし、 作業結果の持ち出し経路を1本に絞って監査する。 実行環境ごとに「破れたときに何が漏れるか」を書き出しておく

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ 他社と共有されるマルチテナントのコンテナ実行環境（Cloudflare Containers・Sandboxes 等）を使っている同居する相手と物理ブロックを再利用するプールを共有していた。 ホストの割り当ては提供者が行うため、利用者は同居相手を選べない
    データの保持□ サンドボックス・一時コンテナに .env や長期の API キー・認証情報ファイルを置いている残留ブロックから回収された対象に .env と認証情報ファイルが含まれていた。 提供者からの失効の案内は出ていない
    システム構成□ AI エージェントが書いたコードや外部から受け取ったコードを、外部のサンドボックスで実行しているSandboxes はまさにこの用途で売られており、同じディスク実装を共有していたため影響を受けた
    運用・監視□ 自社がマルチテナントのストレージ・仮想ディスクを提供しており、性能のために消去処理を外している箇所がある本件の原因は、既定で有効なゼロ化を外していたことだった。 テナント境界をまたぐプールでは、その省略が即座に他テナントのデータ露出になる
    体制・契約□ 委託先・クラウドの事故報告を受けたときに「調査対象期間・記録の保持期間・露出の開始時期」を確認する手順が無い本件では「悪用の証跡なし」の結論だけが示され、保持期間と露出の開始時期は示されていない。 この2つが無いと結論の範囲を評価できない
    運用・監視□ 利用している外部基盤ごとに「そこへ何を置いているか」の一覧を持っていない対象を選べない欠陥では提供者も影響先を特定できず、個別通知は来ない。 自社の影響を判断する材料は「何を置いていたか」だけになる
