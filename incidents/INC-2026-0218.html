INC-2026-0218HALMEK up 管理画面に不正アクセス

50代以上の女性向け情報サイト「HALMEK up」の管理画面が、従業員1名の ID とパスワードを窃取されて不正アクセスを受けた——ハルメクホールディングスは2026年9月9日に不正アクセスを確認し、2日後の9月11日に公表した。管理画面へのアクセスに必要なパスワードを変更し、外部専門家の協力を得て調査を進めている。現時点の調査では顧客管理情報へのアクセスはログ上確認されておらず、雑誌の発行や通信販売事業への影響も否定している。認証情報がどのように窃取されたか、管理画面に多要素認証があったか、不正アクセスがいつから続いていたかは、いずれも公表されていない

不正アクセス・侵害続報が続いている日本の組織が当事者認証情報の悪用（使い回し・推測可能・窃取）公表されていない／不明
初報: 2026年9月11日 最終更新: 2026年9月25日

50代以上の女性向け情報誌の発行と通信販売事業を手がける株式会社ハルメクホールディングスは2026年9月11日、同社グループが運営するウェブサイト「HALMEK up」の管理画面が不正アクセスを受けたことを公表しました。日次ニュース（Security NEXT）に載ったのは9月25日です。

不正アクセスを確認したのは2026年9月9日。原因は従業員1名の ID とパスワードが窃取されたことで、同社は管理画面へのアクセスに必要なパスワードを変更しました。外部専門家の協力を得て調査を進めており、システム会社・関係機関への報告も行っています。

現時点の調査では、顧客管理情報へのアクセスはログ上確認されていません。雑誌の発行や商品販売（通信販売）事業への影響も否定しています。一方で「被害の全容把握には今しばらく時間を要する」としており、調査は続いています。

この事案の読みどころは、侵入口が脆弱性ではなく「人が持っている鍵」だったことです。攻撃者は脆弱性を突いていません。正規の従業員の ID とパスワードで、正面から入っています。そのため、アクセスそのものは正規の操作と見分けがつきません。同社が「顧客管理情報へのアクセスはログ上確認されていない」と、ログを根拠にした言い方をしているのは、この構図と整合します。

本記録は、公表資料に基づく事実と、本記録の作成者による評価を分けて整理します。

ここからは本記録の作成者の評価です。

本件で攻撃者が使ったのは脆弱性ではありません。正規の従業員の ID とパスワードです。この違いは、防御と調査の両面で効いてきます。

防御の面。 脆弱性であれば、更新すれば塞がります。認証情報であれば、変更すればその1本は塞がりますが、窃取の経路が残っていれば次の1本が同じように取られます。公表文は「従業員の ID・パスワード管理体制を含むセキュリティ対策の強化」に触れていますが、どう窃取されたかが公表されていない以上、対策が経路に届いているかを外部からは判断できません。

調査の面。 正規の認証情報で入られた場合、アクセスログに残るのは「その従業員がログインして操作した」という記録です。不正であることを示す印が無い。同社が「顧客管理情報へのアクセスはログ上確認されていない」と、ログを根拠にした限定的な言い方をしているのは、この構図と整合します。本記録は、この表現を「流出していない」と読み替えません。

ここから引き出せる実務上の含意は2つあります。

1つ目は、管理画面に ID とパスワードだけで入れる状態を残さないことです。多要素認証、接続元の制限、管理画面そのものを公開面から外す——どれか1つでも入っていれば、窃取された認証情報だけでは入れません。本件で多要素認証があったかは公表されていませんが、1アカウントの認証情報の窃取で管理画面に到達できたことは事実として残ります。

2つ目は、管理画面から顧客データへ到達できる設計かどうかを、事故の前に確かめておくことです。到達できない設計なら「顧客管理情報へのアクセスは確認されていない」は構造上の保証になります。到達できる設計なら、それはログの読み取り結果でしかありません。同じ文言でも意味の強さが違います。 自社の公表文が前者を言えるかどうかは、設計で決まります。

窃取の経路も、多要素認証の有無も、侵入の期間も公表されていない未確定事項出典 [1] [2]

2026年9月26日時点で、次の点は公表されていません。

  • ID とパスワードがどのように窃取されたか。 フィッシングか、情報窃取型マルウェアか、他サービスからの使い回しか、端末の侵害か。同じ手口への備えを他組織が取る手がかりがありません
  • 管理画面に多要素認証があったかどうか。 対策として導入するとも書かれていません
  • 不正アクセスがいつ始まり、どれだけ続いていたか（調査中）
  • 管理画面から顧客管理情報へ到達できる設計だったのか。これが分からないと「ログ上確認されていない」の意味の強さが判断できません
  • サイトの記事・コンテンツが改ざんされたかどうか。 閲覧者への影響にも触れられていません
  • 関係機関への報告先（個人情報保護委員会・警察等の具体名）
  • ログの保存範囲と期間

CISO・経営層への示唆
  • 管理画面の侵入口は脆弱性ではなく「従業員が持っている鍵」であることが多い
    本件で使われたのは正規の ID とパスワードである。脆弱性の管理をどれだけ徹底しても、 認証情報が外へ出れば同じ結果になる。しかも侵入は正規の操作として記録される。
    取るべき行動 **管理画面を持つ資産の一覧**を作り、各行に「ID とパスワードだけで入れるか」を書く。 入れる行から順に、多要素認証・接続元制限・公開面からの分離のいずれかを入れる。
  • 「ログ上確認されていない」と「流出していない」は別のことだと、社内でも外向きでも区別する
    正規の認証情報による侵入は、ログ上「その従業員の操作」として残る。 不正であることを示す印が無いため、ログの読み取りだけで否定するには限界がある。
    取るべき行動 公表文の雛形に、**判断の根拠（何のログを、どの期間分、どう確認したか）を書く欄**を設ける。 確認できた範囲と確認できなかった範囲を分けて書けるようにしておく。
  • 全容が固まる前に「分かっていること／分かっていないこと」を分けて出す型を持つ
    本件は検知から2日で公表し、被害の全容把握には時間を要すると明示している。 調査の完了を待てば公表は数週間から数か月後になり、その間、利用者は判断材料を持てない。
    取るべき行動 初報の雛形を「確認した事実／影響が無いと確認できた範囲／調査中の範囲／問い合わせ窓口」の 4区分で用意し、**影響範囲が未確定でも出せる状態**にしておく。
  • 自社サイトのお知らせ欄だけの公表は、外部に届くまで時間がかかる
    本件の公表は9月11日だが、日次ニュースに載ったのは9月25日で、14日の差がある。 その間、取引先や利用者が事案を知る機会は限られていた。
    取るべき行動 公表の到達経路を複数持つ（自社サイト・プレスリリース配信・取引先への直接連絡）。 **誰に届けば目的を果たすのか**を事前に決め、経路をそれに合わせる。
セキュリティ技術者への示唆
  • 管理画面を公開インターネットから見えない場所へ移す
    窃取された認証情報は、管理画面に到達できて初めて使える。 到達経路を絞れば、認証情報だけでは入れない。
    取るべき行動 管理画面の接続元を社内ネットワーク・VPN・許可 IP に制限する。 CMS の管理パスを既定のままにせず、公開面のインデックスからも外す。
  • 管理者ログインは「操作の内容」ではなく「ログインの文脈」で監視する
    正規の認証情報による侵入は、操作そのものからは見分けられない。 普段と違う時刻・地域・端末・回数といった文脈にしか差が出ない。
    取るべき行動 管理者アカウントのログインについて、時刻帯・接続元・利用端末のベースラインを取り、 外れたときに通知する。**通知先を当番制にして、受け取る人を決める。**
  • 記事の編集権限と顧客データへの到達を、別の系統に分ける
    「顧客管理情報へのアクセスは確認されていない」が構造上の保証になるかどうかは、 管理画面から顧客データへ到達できるかで決まる。
    取るべき行動 コンテンツ管理と顧客管理を別システム・別権限にする。 同じ画面に同居している場合は、顧客データの参照に**追加の認証**を要求する。
  • 認証情報の窃取経路を潰す——端末側の対策を認証の対策と同じ優先度で扱う
    本件の窃取経路は公表されていないが、近年の管理画面侵害では 情報窃取型マルウェアとフィッシングが主要な経路である。 パスワードを変えても、端末が汚染されていれば新しいものも取られる。
    取るべき行動 管理画面にアクセスする端末を特定し、EDR の導入状況とブラウザに保存された 認証情報の有無を点検する。**ブラウザのパスワード保存を管理画面に対して無効化する。**
