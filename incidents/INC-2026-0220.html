INC-2026-0220無効化済み GitHub Actions が復活し再感染

2026年5月に汚染され GitHub に無効化された2つの GitHub Actions（actions-cool/issues-helper と actions-cool/maintain-one-comment）が、9月16日に再び到達可能になり、リリースタグが5月18日に投入された悪意あるコードを指したままだったため、バージョンタグで参照していた全ワークフローがペイロードの取得と実行を再開した——新しい侵害も新しいエクスプロイトも起きていない。変わったのは「ダウンロードできるようになった」ことだけである。issues-helper だけで GitHub の依存関係グラフ上に約15,000のリポジトリが並ぶ。両リポジトリは9月25日に再び無効化された。誰が、なぜ再有効化したのかは公表されていない

委託先・再委託先起因で委託元多数に波及資産の失効・乗っ取り（ドメイン等）続報が続いている有名事象として記録（日本と直接の関係は薄い）ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）委託先・供給元起因失効・期限切れ（ドメイン・証明書）
初報: 2026年9月24日 最終更新: 2026年9月25日

セキュリティ企業 Socket が2026年9月24日、無効化されていたはずの GitHub Actions が復活し、悪意あるコードの配信が再開していたと報告しました。

経緯はこうです。2026年5月18日、Mini Shai-Hulud キャンペーンでactions-cool/issues-helper と actions-cool/maintain-one-comment の2つの GitHub Actions に悪意あるコードが投入されました。翌5月19日、GitHub のセキュリティチームが両リポジトリを無効化し、攻撃は止まりました。

ところが9月16日、両リポジトリが再びアクセス可能になりました。そしてリリースタグは掃除されないまま、5月18日に投入された悪意あるコードを指し続けていました。

結果として、コミット SHA ではなくバージョンタグで参照している全ワークフローが、次の実行時からペイロードの取得と実行を再開しました。悪意あるコードは Bun を導入して index.js を実行する形で、中身は難読化されています。日次サマリーは、このコードが CI/CD パイプラインから資格情報を収集して攻撃者のサーバへ送ると伝えています。

新しい侵害は起きていません。新しいエクスプロイトもありません。変わったのは、「ダウンロードできるようになった」ことだけです。

issues-helper だけでも、GitHub の依存関係グラフ上に約15,000のリポジトリが並びます。両リポジトリは9月25日に再び無効化されました。

この事案が先例になるのは、無効化を修復と取り違えると、同じコードが数か月後に動き出すことを実証したからです。利用側は何も変えていません。自分のリポジトリを一切触らなくても、参照先の状態が戻るだけで被害が再開します。本記録は、報告に基づく事実と、本記録の作成者による評価を分けて整理します。

ここからは本記録の作成者の評価です。

本件が示したのは、インシデント対応における「止める」と「直す」の違いです。

2026年5月の対応は速い。汚染の翌日にリポジトリが無効化され、攻撃は止まりました。対応としては正しい第一手です。

しかし、無効化はリポジトリの「状態」であって、中身の修復ではありません。タグは悪意あるコードを指したまま残りました。つまり、無効化が解除された瞬間に、5月と同じ攻撃が再び成立する構成のまま4か月が経ちました。

利用側から見ると、この構造はさらに厄介です。

  • 5月に対応した組織は、アクションを取り除くか SHA に固定したでしょう。この層は安全です
  • しかし「GitHub が無効化したので、うちのワークフローは失敗するようになった。じゃあこのアクションはもう使えないんだな」で止めた組織は、参照をタグのまま残しています。9月16日にそれが動き出しました
  • 4か月という間隔は、事案の記憶が薄れるのに十分な長さです

一般化すると、こうなります。依存先が「取得できない」ことを理由にワークフローが止まっているとき、それは解決ではなく待機です。 取得できる状態に戻れば、待機は解除されます。

ここから導かれる実務は、Socket の勧告とほぼ同じです。第三者アクションを完全なコミット SHA で固定すること。タグは可変です。指す先はいつでも変わりえます。SHA は不変で、指す先の内容が変わることはありません。これは本件に限らず、GitHub Actions のサプライチェーン全般に効きます。

もう1点、「無効化された依存先」を検知する仕組みを持つことも挙げておきます。5月19日の無効化でワークフローが失敗し始めたとき、その失敗が「依存先が侵害されて無効化された」ことによるものだと分かっていれば、9月の再開は起きませんでした。CI の失敗は、それ自体がセキュリティの信号になりえます。

委託・第三者部品□ GitHub Actions のワークフローで第三者のアクションをバージョンタグで参照しているタグは可変であり、指す先がいつ変わっても利用側には分からない。 本件はタグが悪意あるコードを指したまま残り、再有効化だけで配信が再開した。
