INC-2026-0225WAF を1文字で迂回 PeopleSoft 悪用再開

Mandiant と Google Threat Intelligence Group が2026年9月25日、恐喝集団 ShinyHunters（UNC6240）による Oracle PeopleSoft の脆弱性 CVE-2026-35273（CVSS 9.8・未認証の遠隔コード実行）の大規模悪用が再開したと公表した——攻撃側は6月の防御ガイダンスに適応し、リクエストパスの1文字を URL エンコードして「/%50SEMHUB/」とするだけで、脆弱なエンドポイント /PSEMHUB/ を文字列一致で遮断していた WAF を迂回した。パッチを当てず WAF で塞いだつもりだった組織が破られ、5月27日〜6月9日のゼロデイ期に高等教育へ集中していた標的は、高等教育・テクノロジー・IT サービス・医療・農業・運輸・政府の7業種へ世界規模で広がっている。Oracle は6月10日に定例外のパッチを出しているが、アラート本文は実際の悪用に一切触れていない

初報: 2026年9月25日 最終更新: 2026年9月26日

Mandiant と Google Threat Intelligence Group（GTIG） は 2026年9月25日、恐喝集団 ShinyHunters（Mandiant の追跡名 UNC6240）によるOracle PeopleSoft の脆弱性 CVE-2026-35273 の大規模悪用が再開したと公表しました。

この脆弱性は、PeopleSoft Enterprise PeopleTools のEnvironment Management Hub（PSEMHUB）に対する認証不要・遠隔からのコード実行で、CVSS 3.1 基本値 9.8 です。Oracle は 2026年6月10日に定例外の Security Alert とパッチを出しています。

今回のレポートの要点は、攻撃側が防御側のガイダンスに適応したことです。

6月時点で Mandiant は「すぐにパッチを当てられない場合は、境界で /PSEMHUB/* への外部アクセスを遮断せよ。WAF の本文検査ルールだけに頼るのは不十分である」（原文英語）と述べていました。攻撃者はこの3か月後、パスの1文字を URL エンコードするというただそれだけの変更で、その遮断をすり抜けています。

リクエストパス
従来 /PSEMHUB/hub
今回 /%50SEMHUB/hub （P を %50 に置換）

多くの WAF・リバースプロキシは URL デコードする前の文字列で /PSEMHUB を照合します。一方 PeopleSoft を載せている WebLogic はデコードしてから脆弱なサーブレットへ振り分けます。結果として、「WAF でルールを入れたから塞がったはずだ」と考えていた組織が破られました。

被害の広がりも変わりました。ゼロデイ期（2026年5月27日〜6月9日）は高等教育に集中しており、Mandiant が通知した100を超える組織の68%が大学・カレッジでした。今回は数十のシステムに web shell が仕掛けられ、業種は高等教育・テクノロジー・IT サービス・医療・農業・運輸・政府の7つに広がっています。

Mandiant の結論は一行です。「WAF ルールとパスによる遮断は、パッチの代わりにはならない」（原文英語）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

インターネットに露出した Oracle PeopleSoft の Environment Management Hub（PSEMHUB）に対し、 CVE-2026-35273（認証不要の遠隔コード実行、CVSS 9.8）を悪用する大規模キャンペーン。 9月の再開では、リクエストパスの `P` を `%50` に URL エンコードすることで 文字列一致の WAF ルールを迂回し、パッチ未適用のまま境界で塞いでいた組織を破った。 侵入後は web shell 2種・Neo-reGeorg トンネル・MeshCentral エージェント・ EV 証明書で署名されたバックドア（SIDEEYE）を用い、データ窃取と恐喝へ進む。

  1. 1. 偵察公表・報道に基づく[1]
    悪用の前に、標的サーバへ `/%50SEMHUB/hub` 宛ての POST を5〜15回送り、 直列化された Java オブジェクトを投げる。未修正のサーバはホストの OS 名を 応答として返すだけで、ファイルの書き込みもサービスの停止も起きない。 これで悪用可能かどうかを静かに確認する
    根拠: Mandiant が観測した一連の挙動（2026年9月25日レポート）
  2. 2. 検知回避公表・報道に基づく[1] [2]
    リクエストパスの `P` を `%50` に置き換え、`/%50SEMHUB/hub` として要求する。 WAF・リバースプロキシは URL デコード前のリテラルな文字列で照合するため一致せず、 WebLogic はデコードしてから脆弱なサーブレットへ振り分ける
    根拠: Mandiant が観測したリクエストパス（2026年9月25日レポート）
  3. 3. 初期侵入公表・報道に基づく[1] [3]

    「WAF で塞いだ」と思っていた組織が、パスの1文字を URL エンコードされただけで破られた概観

    今回のレポートの中心は、たった1文字の置き換えである。

    従来:  POST /PSEMHUB/hub
今回:  POST /%50SEMHUB/hub      ← "P" を "%50"（P の URL エンコード）に置換

    なぜこれで通るのか。理由は2つの層で文字列の解釈が違うことにある。

    • WAF・リバースプロキシ — 多くの実装は、URL デコードする前のリテラルなパス文字列に対してルールを照合する。/PSEMHUB という文字列は /%50SEMHUB には含まれないので、ルールに一致しない
    • WebLogic（PeopleSoft の実行基盤） — リクエストパスをデコードしてからアプリケーションへ振り分ける。/%50SEMHUB/hub は /PSEMHUB/hub として処理される

    Mandiant はこう書いている。「多くの WAF やリバースプロキシのルールは URL デコード前のリテラルなパスに一致させるが、PeopleSoft のアプリケーションサーバはリクエストをデコードして脆弱なサーブレットへ振り分ける。これにより、WAF ルールで露出を緩和できたと考えていたかもしれないシステムでも、攻撃者はエンドポイントへ到達できる」（原文英語）。

    同社はさらに、防御側は「パーセントエンコード・大文字小文字の混在・その他の非正規化された変種のいずれもが使われうると想定し、正規化したパスに対して遮断を強制すべきである」（原文英語）と付け加えている。

    これは PeopleSoft に固有の話ではない。「境界機器が生の文字列で照合し、アプリケーションがデコード後の値で動く」という組み合わせは、あらゆる仮想パッチに共通する構造である（本記録の評価）。

    web shell を置いたあと、攻撃者が持ち込む道具は次のとおりである。

    ① 2つの web shell（いずれも PSEMHUB.war ディレクトリに設置）

    • x.jsp — コマンド実行。コマンドは16進エンコードして POST で渡し、出力に R: を付けて返す。OS を自動判定し、Linux では/bin/sh という文字列を文字コードの配列から組み立てる。いずれも静的な文字列シグネチャを避けるためである
    • u.jsp / u2.jsp — 大きなバイナリを150KB ずつ Base64 で分割アップロードして結合する。HTTP のリクエストサイズ制限を避けつつ、PeopleSoft 本来のファイル分割機構を使わないことで検知も避けている

    ② トロイの木馬化されたインストーラ（Ple64.exe ＝ SIDEEYE）

    5.2MB のバイナリで、メディアプレイヤー Light Alloy の署名付きインストーラを装う。中身は3段階の実行チェーンで、最終段の C++ 製バックドアはメモリ上で動く。機能はブラウザやデスクトップアプリからの認証情報の窃取、プロセス・ファイル操作、対話型のリバースシェル、リバースプロキシである。

    問題は署名である。 この検体は有効な Extended Validation（EV）証明書で署名されていた。発行は Sectigo、名義は実在する開発元の名前である。Google は Sectigo に失効を申請したとしている。「EV 証明書で署名されているから正規のものだ」という判定は、ここで破れている。

    ③ トンネルと遠隔管理

    • tunnel.jsp / tunnel.jspx — オープンソースの Neo-reGeorg によるHTTP/HTTPS 上の SOCKS5 トンネル。内部探索と横展開に使う
    • MeshAgent（オープンソースの遠隔管理 MeshCentral のエージェント）— Linux では /tmp 配下に、PeopleSoft のサービスアカウント権限で置かれる。正規の運用ツールであるため、エンドポイント製品では止まりにくい

    1. CVE-2026-35273 の Oracle パッチを当てる。「WAF ルールとパスによる遮断は、パッチの代わりにはならない」

    日本の組織にとっての要点は「仮想パッチをいつまで置いておくか」を決める仕組みがあるかどうかである評価・解釈

    日本の組織が名指しされた事案ではない。それでも本記録に残す理由は3つある（本記録の評価）。

    第一に、破られたのは製品ではなく運用の判断である。パッチを当てた組織は今回の波の対象外である。破られたのは「基幹システムはすぐに止められないから、まず WAF で塞いで様子を見る」という、どの組織でも日常的に行われている判断をしたところである。PeopleSoft を使っていなくても、この判断は必ずどこかでしている。

    第二に、仮想パッチには期限が要る。 WAF ルールや境界での遮断は、パッチ適用までの時間を稼ぐためのものである。ところが実務では、いったん「遮断済み」と記録されると、そこで対応が完了したことになりやすい。本件では、その状態が3か月続いたところを突かれた。仮想パッチを入れたときに恒久対応の期限を同時に記録し、期限が来たら未適用として再び上がってくる仕組みがあるかどうかが分かれ目になる。

    第三に、遮断の実装が正規化を行っているかは、確認しないと分からない。「/PSEMHUB/* を塞いだ」という記録があっても、それが URL デコード後の正規化されたパスに対する照合なのか、生の文字列に対する照合なのかは、ルールを見ないと判別できない。今回の迂回は、その違いだけで成立している。

    加えて、PeopleSoft が持っているデータの性質も考慮に値する。人事・給与・学籍という、組織のほぼ全員分の個人データが入っている基幹システムであり、6月の波で高等教育が68%を占めたのは、大学がこの製品を広く使っているからである。日本でも同じ構図が成り立つ（本記録の評価）。

    WAF が「遮断した」記録を出さないため、**防御側から見ると何も起きていないように見える。** 遮断ログだけを監視していると、迂回されたことに気づけない（本記録の評価）

    侵入を防げたCVE-2026-35273 の Oracle パッチを適用する（WAF ルールでは代替できない）

    ②の方式ではディスクに何も残らない。 **JSP ファイルの作成を条件にした検知は②を取り逃がす**とレポートが明記している

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • 仮想パッチには「いつまで」を必ず付ける。付けないと、それが恒久対応になる
      今回破られたのは、6月10日のパッチを当てずに WAF ルールで代替した組織である。 WAF を入れた時点で対応済みとして台帳から消えると、**3か月後に迂回された時点で 誰も「未適用である」ことを把握していない**状態になる
      取るべき行動 緩和策で一時対応した脆弱性に、恒久対応の期限を同じ台帳の項目として記録する運用にする。 期限を過ぎたものは自動的に未対応として再掲されるようにし、 「緩和済み」と「対応完了」を別の状態として区別する
    • 脆弱性の緊急度を、ベンダーのアラートの言い回しだけで判断しない
      Oracle の Security Alert は定例外の緊急公開でありながら、実際の悪用に触れていない。 「いま攻撃されている」という情報は Mandiant（6月11日）と CISA の KEV 収載（6月12日・ 期限3日・ランサムウェア使用 Known）から来ている
      取るべき行動 脆弱性対応の優先度判定の入力に、ベンダーのアラートに加えて KEV への収載と期限、脅威インテリジェンスの観測を明示的に組み込む。 「ベンダーが悪用に触れていないこと」を、悪用されていない根拠として扱わない
    • 基幹システムに「止められない」以外の選択肢を用意しておく
      PeopleSoft のような人事・給与・学籍の基幹システムは、緊急パッチのために 止めることが難しい。その制約が「まず WAF で」という判断を生んでいる。 一方で Mandiant は、EMHub と Integration Broker は管理用の部品であり、 **止めても利用者のセッションには影響しない**と明記している
      取るべき行動 基幹システムについて「業務を止めずに切り離せる部品」がどれかを、 平時のうちに製品ベンダーの資料で確認して一覧にしておく。 緊急時に「全体を止めるか、何もしないか」の二択にならないようにする
    • 被害が出た前提での恐喝対応を、技術対応とは別に準備する
      UNC6240（ShinyHunters）はデータを盗んでリークサイトでの公開を材料に 身代金を要求する集団であり、Mandiant は被害組織に「恐喝の連絡に備えよ」と勧告している。 2026年6月9日には実際に被害機関のデータが公開された
      取るべき行動 恐喝の連絡を受けたときの一次窓口・意思決定者・外部の支援先（弁護士・当局・専門事業者）を あらかじめ決め、連絡先を技術チーム以外からも参照できる場所に置く。 支払いの可否についての組織の方針を、実際に迫られる前に決めておく
    • 「うちの業種は狙われない」は、3か月で覆りうる
      6月は通知先の68%が大学・カレッジで、実質的に高等教育向けのキャンペーンだった。 9月には高等教育・テクノロジー・IT サービス・医療・農業・運輸・政府の7業種に広がっている。 **標的を決めているのは業種ではなく、露出した製品とバージョンである**
      取るべき行動 脅威情報を業種の一致で取捨選択せず、**自組織が使っている製品名とバージョンで** 引っかかるようにする。資産台帳の製品・バージョン情報の鮮度を、 脆弱性対応の前提条件として定期的に点検する
    セキュリティ技術者への示唆
    • WAF のルールが「URL デコード後の正規化されたパス」に効いているかを実際に試す
      今回の迂回は `P` を `%50` に置き換えただけで成立している。 WAF はデコード前の文字列で照合し、WebLogic はデコード後の経路で処理するという 解釈のずれが原因である
      取るべき行動 遮断しているパスについて、パーセントエンコード変種・大文字小文字の混在・ 二重エンコードで実際にリクエストを送り、遮断されるかを検証する。 ルールは正規化後のパスに対して書き直す
    • WAF の「遮断ログ」だけを見ていると、迂回されたことに気づけない
      迂回が成立すると WAF はルールに一致しないので、**遮断の記録が出ない。** 防御側から見ると何も起きていないのと区別がつかない
      取るべき行動 WAF の遮断ログに加えて、**保護対象のアプリケーション側のアクセスログ**で 当該エンドポイントへの到達を監視する。遮断しているはずのパスに アプリケーション側でリクエストが届いていたら異常として扱う
    • web shell の検知を「ファイルの作成」に依存させない
      観測された実行方法の一方は、POST の応答にコマンド出力を直接返す方式で、 **ディスクに何も残らない。** レポートは 「JSP ファイルの作成に依存する検知ではこの方式を識別できない」と明記している
      取るべき行動 WebLogic（および同種のアプリケーションサーバ）の Java プロセスが cmd.exe / /bin/sh / bash を起動した事象を検知条件として登録する。 その配下での `base64 -d`・`curl`・`/dev/tcp`・`start /b` の実行も併せて見る
    • 1台で web shell が見つかったら、負荷分散の背後の全ノードを調べる
      攻撃者は POST を連続して送ることで、**負荷分散の全ノードに web shell が 配られるようにしている。** 最初に見つかった1台だけを直すと、残りが残る
      取るべき行動 侵害対応の手順に「同一サービスを構成する全ノードの点検」を独立した工程として書く。 点検対象は `PSEMHUB.war` と `PORTAL.war` 配下の製品同梱でない .jsp / .jspx / .exe とする
    • 「有効な署名がある」ことを信頼の根拠にしない
      バックドアを載せたインストーラは、実在する開発元名義の**有効な EV 証明書**で 署名されていた。署名の有効性だけを見る制御はこれを通してしまう
      取るべき行動 実行制御・許可リストを、署名者ではなくハッシュまたは配置場所で運用する。 少なくとも**ウェブアプリケーションの配備ディレクトリからの実行可能ファイルの起動**は、 署名の有無にかかわらず検知・遮断の対象にする

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ Oracle PeopleSoft Enterprise PeopleTools 8.61 または 8.62 を運用しているCVE-2026-35273 の影響を受けるのはこの2バージョンである。 パッチは2026年6月10日に提供されており、適用済みであれば今回の波の対象外となる
    システム構成□ PSEMHUB や Integration Broker のエンドポイントがインターネットから到達できる悪用の入口は `/PSEMHUB/hub` である。EMHub と Integration Broker は 管理・システム間通信用の部品で、止めても利用者のセッションには影響しない
    運用・監視□ パッチを当てられない脆弱性に WAF ルールや境界での遮断で対応した記録があるが、恒久対応の期限を管理していない今回破られたのは、6月から3か月間パッチを当てずに WAF で代替していた組織である。 緩和策が「対応完了」として台帳から消えると、迂回された時点で誰も未適用だと知らない
    運用・監視□ WAF のルールが URL デコード後の正規化されたパスに対して照合しているかを検証していない迂回は `/PSEMHUB/` を `/%50SEMHUB/` にするだけで成立した。 生の文字列に対する照合であれば、同じ手が通る
    運用・監視□ web shell の検知が、公開ディレクトリへのファイル作成の監視に依存している観測された実行方法の一方はファイルを書かず、POST の応答に出力を返す。 ファイル作成を条件にした検知では捉えられない
    認証・認可□ ウェブ層のサービスアカウントから、データベース接続文字列やクラウドの認証情報が読めるMandiant は侵害時の対応として、psappsrv.cfg のデータベース接続文字列・ Integration Broker の認証情報・ウェブ層から到達できるクラウドの認証情報の 総入れ替えを求めている。読める範囲がそのまま被害の範囲になる
