INC-2026-0226Storm-3168 が Azure 資源を7分で破壊

Microsoft が2026年9月25日、侵害された Azure のサービスプリンシパル2つを使った破壊活動の詳細を公表した——Sysdig が7月に「初めて文書化されたエージェント型ランサムウェア作戦」として報告した JADEPUFFER を同社は Storm-3168 として追跡しており、今回が同集団の Azure 上の活動の初の詳細な観測になる。2026年6月初旬、1つ目のサービスプリンシパルが約15時間30分かけて300回以上の読み取りで環境を棚卸しし、2つ目が2サブスクリプションを5秒で列挙した。存在しないストレージアカウントへの ListKey が失敗した1秒未満後に破壊が始まり、35分間で150回以上、うち破壊の連続は約7分間で100回以上のストレージアカウント削除試行だった。侵害されたサービスプリンシパルの client ID・client secret・tenant ID は、以前に被害組織の従業員が公開 GitHub Issue へ平文で書いており、編集で消したあとも公開の編集履歴から読める状態だった

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備設定不備
初報: 2026年9月25日 最終更新: 2026年9月27日

Microsoft は 2026年9月25日、Azure 環境で起きた大規模な資源破壊とクラウド資格情報の収集について、観測の詳細を公表しました。

追跡名は Storm-3168。Sysdig が2026年7月に「初めて文書化されたエージェント型ランサムウェア作戦」として報告したJADEPUFFER と同一の脅威アクターだと Microsoft は述べています。同集団の Azure 上の活動が詳細に公開されたのは今回が初めてです。

起きたことは次のとおりです（すべて Microsoft の観測）。

  • 2026年6月初旬、同一テナントに属する2つのサービスプリンシパルが侵害されていた
  • 1つ目が約15時間30分・300回以上の読み取りで仮想マシン・サブスクリプション・リソースグループを棚卸しした
  • その約90分後、2つ目が2つのサブスクリプションを5秒で列挙した
  • 16時間後、2つ目が App Service の構成ストアを列挙し、存在しないストレージアカウントへの ListKey に失敗した
  • その1秒未満後に破壊が始まった。35分間で150回以上の破壊・資格情報収集の操作、うち破壊の連続は約7分間で100回以上のストレージアカウント削除試行
  • 最後の破壊活動の約30分後、30回以上の ListKeys でストレージアカウントのアクセスキーを取得した

止まった部分もあります。 Azure のリソースロックとストレージアカウント単位の削除保護が一部の削除を拒否しました。SQL データベースの削除は全て失敗しましたが、理由は防御ではなく攻撃側がサポートされない API バージョンを使ったことです。

初期侵入の経路は確定していません。ただし Microsoft は、侵害されたサービスプリンシパルの client ID・client secret・tenant ID が、被害組織の従業員によって公開の GitHub Issue へ平文で書かれていたこと、編集で消したあとも Issue の公開編集履歴から読める状態だったことを指摘し、「公開された資格情報は、失効または更新するまで有効であり続ける。元の掲載を消すだけでは是正にならない」（原文英語）と述べています。

日本の組織が当事者だという公表はありません。それでも本記録が扱うのは、人ではなく自動化されたものが動いている前提でクラウドの被害の速度が変わっていることが、この観測で数字として示されたからです。気づいてから止めるまでの時間が、7分より長い組織は間に合いません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

同一 Azure テナント内の2つのサービスプリンシパル（ワークロード ID）を侵害し、 既存のロール割り当ての範囲で環境全体を列挙したうえで、 ストレージアカウント・Key Vault・Function App・App Service プランを大量に削除し、 復旧資源（Site Recovery / Backup の保護ロック）にも削除を試み、 最後にストレージアカウントのアクセスキーを収集した。 偵察に約15時間30分、破壊の連続は約7分。

  1. 1. 初期侵入公表・報道に基づく[1]
    侵害されたサービスプリンシパルとして Azure Resource Manager に対して API を呼び出す。ユーザーエージェントは `python-requests/2.34.2`、 2つのサービスプリンシパルは Storm-3168 に結びつく同一のネットワーク指紋を共有していた
    根拠: Microsoft Security Blog（2026年9月25日）
  2. 2. 内部探索公表・報道に基づく[1]
    1つ目のサービスプリンシパルが約15時間30分にわたり300回以上の読み取りで 仮想マシン・サブスクリプション・リソースグループ・リソースを列挙した。 その約90分後、2つ目が2サブスクリプションを5秒で列挙し、 16時間後に App Service の構成ストアを列挙した（露出した資格情報の探索とみられる）
    根拠: Microsoft Security Blog（2026年9月25日）
  3. 3. 権限昇格公表・報道に基づく[1]
    **権限昇格は観測されていない。** すべての破壊操作は、その ID に既に 割り当てられていたロールの範囲で実行された。ストレージの削除は **グループ経由で付与された** Storage Account Contributor、 アプリ資源の削除は直接付与の Contributor、 SQL の削除試行は直接付与の SQL DB Contributor が通した
    根拠: Microsoft Security Blog（2026年9月25日）
  4. 4. 影響（暗号化・破壊・改ざん）公表・報道に基づく[1]
    存在しないストレージアカウントへの ListKey 失敗の1秒未満後に破壊を開始。 35分間で150回以上の破壊・資格情報収集操作、うち約7分間で100回以上の ストレージアカウント削除試行。大半は成功した。 同一リソースグループの Key Vault・Function App・App Service プランも削除。 Azure SQL データベースの並行削除は、サポートされない API バージョンのため全て失敗
    根拠: Microsoft Security Blog（2026年9月25日）
  5. 5. 影響（暗号化・破壊・改ざん）公表・報道に基づく[1]
    復旧手段そのものを狙った。Azure Site Recovery のロックと Azure Backup の保護ロックに対する削除が複数回試みられ、 いずれも失敗した。terraform・バックアップにちなんだ名前の ストレージアカウントが破壊対象に含まれていた
    根拠: Microsoft Security Blog（2026年9月25日）
  6. 6. 認証情報アクセス公表・報道に基づく[1]
    最後の破壊活動の約30分後、ストレージアカウントの一覧を要求し、 30回以上の ListKeys に成功してアクセスキーを取得した。 対象には Azure Site Recovery 関連のストレージアカウントが含まれていた
    根拠: Microsoft Security Blog（2026年9月25日）

偵察に15時間半、破壊に7分——同じテナントの中で速度が3桁違った概観出典 [1]

Microsoft が2026年9月25日に公表した観測は、時間の刻みが細かいことに意味があります。

段階 所要 内容
1つ目のサービスプリンシパルの列挙 約15時間30分 300回以上の読み取り
2つ目のサービスプリンシパルの列挙 5秒 2サブスクリプションの VM・リソースグループ
最後の棚卸し → ListKey 失敗 70秒 存在しないストレージアカウント宛
ListKey 失敗 → 破壊開始 1秒未満 —
破壊の連続 約7分 100回以上のストレージアカウント削除試行
破壊・資格情報収集の全体 35分 150回以上の操作
最後の破壊 → ListKeys 約30分後 30回以上成功

同じテナントの中で、同じ種類の列挙が15時間半と5秒で行われています。 Microsoft はこの速度差と、削除用トークン2つが同じ70秒間に同時に有効だったこと、操作の時間間隔から「自動化された、あるいはスクリプト化された実行」を強く示すと述べています。

壊された対象は、ストレージアカウント（大半が実際に削除された）、Key Vault、Function App、App Service プランです。SQL データベースの削除は並行して試みられましたが、全て失敗しました。理由は防御ではなく、攻撃側がサポートされない API バージョンを使ったためです。

止めたのは「権限」ではなく「ロック」だった原因・手口出典 [1]

この事案で防御が効いた箇所は、はっきりしています。

  • Azure のリソースロック
  • ストレージアカウント単位の削除保護

この2つが、一部のストレージアカウントの削除を拒否しました。Microsoft の言葉では「侵害された ID が広い管理権限を持っていてもなお有効であり続ける、独立した安全装置の価値を示している」（原文英語）。

逆に、権限は何も止めませんでした。 操作はすべて、その ID に既に割り当てられていたロールの範囲で通っています。

破壊操作 通した権限
ストレージアカウントの削除 グループ経由で付与された Storage Account Contributor
Key Vault・Function App・App Service プランの削除 直接付与の Contributor
SQL データベースの削除試行 直接付与の SQL DB Contributor

注目すべきは、ストレージの破壊を通したのがグループ経由の付与だという点です。ID 単体の権限一覧を見ているだけでは、この権限は見えません。

狙われたのは復旧手段そのものでもあります。 Azure Site Recovery のロックと Azure Backup の保護ロックに対しても削除が試みられ（いずれも失敗）、terraform やバックアップにちなんだ名前のストレージアカウントが対象に含まれていました。

公開 GitHub Issue の編集履歴に、client secret が残っていた発覚の端緒出典 [1]

初期侵入の経路は確定していません。Microsoft は「不明である」と明記しています。

ただし、ひとつの事実が示されています。侵害されたサービスプリンシパルの client ID・client secret・tenant ID は、被害組織の従業員によって公開の GitHub Issue へ平文で書かれていました。 Issue は後に編集されて秘密は削除されましたが、公開されている編集履歴からは読める状態が続きました。

Microsoft はここで一般則を述べています——「露出した秘密を削除したり伏せ字にしたりしても、その秘密が無効になるわけではない。インターネット上のいかなる公開の場所に露出した資格情報も、侵害されたものとして扱い、速やかに失効または更新すべきである」（原文英語）。

「消したから大丈夫」は成立しません。 GitHub の Issue とコメントは編集履歴を公開しており、Pull Request の差分、CI のログ、チャットの編集前メッセージなども同じ性質を持ちます。

もうひとつ、2026年の年初から観測されていた活動があります。Storm-3168 に結びつくインフラが、複数の顧客の Azure App Service に対して、WordPress の管理系パス・PHP-CGI・LangFlow のコード検証エンドポイント/api/v1/validate/code・web shell と思われるパスを繰り返し探索していました。ただしこれらは、後に破壊が起きたサブスクリプションとは重なっていません。 App Service から Azure Resource Manager へ資格情報が渡る経路も見つかっていません。経路として提示されているわけではない点に注意が要ります。

「7分で終わる破壊」に、人間の対応手順は間に合わない（本記録の評価）評価・解釈出典 [1]

ここからは本記録の作成者の評価です。

この観測から読み取るべき点は、攻撃の新奇性ではなく時間の配分だと考えます。

1. 検知の機会は破壊の側ではなく偵察の側にある。破壊は7分で終わりました。アラートを受けてから人が状況を把握し、ID を無効化するまでに7分で到達できる組織は多くありません。一方、その前には約15時間30分・300回以上の読み取りという、きわめて目立つ偵察がありました。ここを見ていないなら、破壊の側でどれだけ早く鳴らしても遅いと考えます。「サービスプリンシパルによる、平常時より桁違いに多い列挙操作」は検知条件として書けるはずのものです。

2. 権限の見直しは、この事案では効かなかった側である。すべての操作は既存のロール割り当ての範囲で通りました。つまり権限設計は「正しく」機能していて、その正しさが破壊を通したことになります。最小権限は当然に必要ですが、それだけでは破壊は止まりません。止めたのはリソースロックと削除保護という、権限とは独立に働く層でした。ここに投資の優先順位を置き替える理由があります。

3. 復旧資源を「守る対象」として明示的に扱う。攻撃側は Site Recovery と Backup の保護ロックを消しにかかっています。バックアップがあることと、バックアップが消せないことは別です。自社の復旧手段が、本番と同じ ID・同じサブスクリプション・同じロールの射程に入っていないかを確認する価値があります。

4. 「エージェント型」という語には留保を置く。 Microsoft は "Agentic-driven" と題し、AI が組み立てる攻撃への移行というより広い傾向を指摘しています。ただし、本文が示す証拠は「自動化またはスクリプト化された実行」までです。 LLM の関与を直接示す証拠は書かれていません。防御側にとって重要なのは、その区別ではなく速度です。人手でやっていた頃の前提（攻撃者も休む・打鍵に時間がかかる）が成り立たなくなったことだけが、確実に言える変化だと考えます。

  • 被害組織はどこか（名称・業種・国・規模のいずれも不明）
  • サービスプリンシパルはどうやって侵害されたのか（GitHub Issue の秘密が使われたかは「確認できなかった」）
  • 被害組織はいつ気づき、どう止めたのか——防御側の時間軸が一切無い
  • 復旧できたのか、データは失われたのか
  • 30回以上取得されたアクセスキーで、データが持ち出されたのか
  • 「エージェント型」の中身（LLM の関与を示す証拠は書かれていない）

とくに3点目のため、本記録は「侵入から検知まで」「検知から封じ込めまで」を算出できません。この観測は攻撃側の操作ログから構成されており、防御側が何をしたかは記録の外にあります。

    Microsoft は「**この秘密が、ここで述べた活動に使われたかどうかは確認できなかった**」 （原文英語）と明記している。 **報道や要約では「GitHub Issue から漏れた資格情報で侵害された」と 読めてしまいやすいが、一次資料はそこまで述べていない。** 本記録は初期侵入の経路を未確定として扱う。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「7分で終わる破壊」を前提に、対応手順の時間目標を置き直す
    破壊の連続は約7分だった。アラートから人が判断して ID を無効化するまでに 7分で到達できる体制は、多くの組織にとって現実的ではない。 **人の速度で守れる範囲を超えた事象が実際に起きている。**
    取るべき行動 **「人が間に合う前提の対策」と「人を待たずに効く対策」を台帳の上で分ける。** 後者（リソースロック・削除保護・共有キーの無効化・自動失効）を先に埋め、 前者は偵察段階の検知に振り向ける。 自社の「アラートから ID 無効化まで」の実測値を1度測ることから始める。
  • 復旧手段が、本番と同じ ID の射程に入っていないかを確認する
    攻撃側は Site Recovery と Backup の保護ロックを消しにかかった。 バックアップがあることと、バックアップが消せないことは別である。
    取るべき行動 **復旧資源を別サブスクリプション・別の管理 ID の下に置き、 本番のワークロード ID からは触れないようにする。** 年1回、「本番を全権限で操作できる ID から、バックアップを消せるか」を 実際に試して確認する（検証環境で行う）。
  • 公開の場に出た秘密は「消した」では終わらないと、規程に書く
    侵害されたサービスプリンシパルの資格情報は、従業員が公開 GitHub Issue に 平文で書いたものだった。編集で消したあとも、公開の編集履歴から読める状態が続いた。 Microsoft は「露出した資格情報は侵害されたものとして扱え」と明記している。
    取るべき行動 **「公開の場に秘密を出したら、削除ではなく失効・再発行」を規程に明記する。** 報告した従業員を責めない運用（無過失の申告経路）をあわせて用意する。 申告されない露出のほうが危険だからである。
  • ワークロード ID を、人のアカウントと同じ棚卸しの対象に入れる
    本事案で動いたのは人のアカウントではなくサービスプリンシパルである。 破壊を通した権限は**グループ経由で付与**されており、 ID 単体の権限一覧を見ても現れない。
    取るべき行動 **サービスプリンシパル・マネージド ID の一覧、所有者、付与ロール （グループ経由の継承を含む）、最終利用日を四半期ごとに棚卸しする。** 所有者が不明な ID と90日以上未使用の ID を削除候補として扱う。
セキュリティ技術者への示唆
  • 偵察段階（列挙操作の急増）を検知条件として書く
    破壊は7分、偵察は約15時間30分・300回以上の読み取りだった。 **実用的な検知窓は偵察のほうにしかない。**
    取るべき行動 **ワークロード ID ごとの読み取り／列挙操作の平常値を記録し、 桁違いの増加をアラートにする。** あわせて Defender for Resource Manager を 有効化する。「どの ID が、平常時に何回読むか」を先に測っておくことが前提になる。
  • リソースロックと削除保護を、重要資源の既定にする
    本事案で実際に削除を止めたのはロックと削除保護だけである。 侵害された ID が広い管理権限を持っていても、これらは独立して効いた。
    取るべき行動 **ストレージアカウント・Key Vault・復旧資源に CanNotDelete のリソースロックと ストレージアカウント単位の削除保護を設定し、 Infrastructure as Code のテンプレートに既定として埋め込む。** ロックの有無を定期的に検査するポリシーを置く。
  • ストレージの共有キーを無効化し、ListKeys を監視対象にする
    攻撃側は破壊の約30分後に30回以上の ListKeys を成功させ、 Site Recovery 関連を含むストレージのアクセスキーを取得した。 キーは失効させない限り有効であり続ける。
    取るべき行動 **共有キーによるアクセスを無効化して Entra ID 認証へ統一する。** やむを得ず残す場合は、ListKeys の短時間の多数回呼び出しをアラートにし、 キーの自動ローテーションを設定する。
  • ワークロード ID の認証を、秘密からフェデレーションへ移す
    client secret は文字列であり、Issue・ログ・設定ファイル・チャットに 容易に貼られる。貼られた瞬間から、失効させるまで有効である。
    取るべき行動 **ワークロード ID フェデレーション（OIDC）へ移行し、 client secret を発行しない構成を既定にする。** 移行できない箇所については、秘密の有効期限を短くし、 コード・Issue・CI ログに対する秘密の走査を常時化する。
  • 「グループ経由で付与された権限」を可視化する
    ストレージの破壊を通したのは、グループ経由で付与された Storage Account Contributor だった。ID の直接付与だけを見ていると気づけない。
    取るべき行動 **権限の棚卸しを「実効権限（継承込み）」で出力する仕組みを作る。** 「この ID は何を削除できるか」という問いに、 1コマンドで答えられる状態にしておく。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ Azure のサービスプリンシパル（またはマネージド ID）に、サブスクリプション横断の Contributor 級の権限を与えている本事案の破壊は、すべて既存のロール割り当ての範囲で通った。 権限昇格は観測されていない。広い権限を持つワークロード ID が1つ奪われれば、 同じ範囲がそのまま破壊の射程になる。
認証・認可□ ワークロード ID の認証に client secret（文字列の秘密）を使っており、有効期限が長い侵害された ID の client secret は公開 GitHub Issue に平文で書かれ、 編集で消したあとも公開の編集履歴から読めた。 秘密は貼られた瞬間から、失効させるまで有効であり続ける。
システム構成□ 重要なストレージアカウント・Key Vault にリソースロックや削除保護を設定していない本事案で実際に削除を止めたのはこの2つだけである。 権限設計は破壊を止めなかった。独立して働く層があるかどうかで結果が分かれた。
システム構成□ バックアップ・復旧資源が、本番と同じサブスクリプション・同じ管理 ID の射程にある攻撃側は Site Recovery と Backup の保護ロックを消しにかかった。 復旧手段が同じ ID で消せるなら、バックアップは保険にならない。
運用・監視□ ワークロード ID による読み取り・列挙操作の平常値を記録しておらず、急増を検知できない破壊は7分で終わるが、その前に約15時間30分・300回以上の列挙があった。 平常値が無ければ、この唯一の検知窓を使えない。
運用・監視□ 公開の場に秘密が出たときの手順が「削除」までで、「失効・再発行」になっていないMicrosoft は「露出した資格情報は侵害されたものとして扱い、 速やかに失効または更新せよ。元の掲載を消すだけでは是正にならない」と明記している。
