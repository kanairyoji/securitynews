INC-2026-0227Supabase 上の1万6千 DB が公開状態

UpGuard が2026年9月25日、開発基盤 Supabase 上で16,326のデータベースがテーブルを認証なしで読める状態にあったと公表した——Supabase 利用の痕跡がある約30万ドメインを指紋照合して一件ずつ問い合わせた結果で、半数超に個人情報の兆候、一部にパスワードや認証トークン、ごく少数にクレジットカードとみられるデータが含まれていた。原因は攻撃ではなく行レベルセキュリティ（RLS）の未設定で、API 経由で作られたテーブルは既定で RLS が有効にならない。AI にコードを書かせる開発が広がり、生成されたコードが前提とする一手順が抜けたまま公開される構図が、同一基盤上で1万6千件規模になった

業界横断事象・統計（被害者が不特定多数、統計の推移が主）意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）設定不備設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年9月25日 最終更新: 2026年9月27日

UpGuard（米国のセキュリティ企業）は 2026年9月25日、開発基盤 Supabase 上で 16,326 のデータベースが認証なしでテーブルを読める状態にあったと公表しました。

調査は、Supabase 利用の痕跡がある約30万のドメインを指紋照合で洗い出し、1件ずつ users テーブルの有無を問い合わせる方法で行われています。UpGuard は「この設定の失敗に関する調査としては過去最大であり、先行研究の合計のおよそ10倍の規模」だとしています。

中身の内訳は次のとおりです。

  • 半数超のデータベースに何らかの個人情報の兆候があった
  • より少ない割合にパスワードまたは認証トークンが含まれていた
  • ごく少数にクレジットカードとみられるデータが含まれていた

攻撃ではありません。 侵入も脆弱性の悪用も起きていません。原因は 行レベルセキュリティ（Row Level Security・RLS）が有効になっていないことです。Supabase は2025年3月以降、画面（UI）から作ったテーブルには RLS を既定で有効にしましたが、API 経由でプログラムから作ったテーブルは既定で有効になりません。

ここに、AI にコードを書かせる開発が重なりました。TechCrunch は「生成されたコードにはしばしば安全上の欠陥が含まれ、あるいは開発者が知らない特定の設定を必要とすることがある」と指摘しています。書かれたコードは動きます。動くが、守られていません。

Supabase の CISO Bil Harmer 氏は TechCrunch に対し、調査は見ていないとしつつ「プロジェクトは既定で安全（secure by default）」であり、セキュリティは同社と顧客の共同責任だと述べています。

日本の組織が当事者だという公表はありません。それでも本記録が扱うのは、同じ構図が日本でそのまま成立するからです。Supabase は個人開発と社内ツールで広く使われており、「現業部門が作った小さなアプリ」「委託先が作った小規模ツール」が棚卸しの対象から外れている組織は少なくありません。

攻撃は起きていない——認証をかけていないデータベースが1万6千件あっただけである概観出典 [1] [2]

UpGuard が2026年9月25日に公表した調査の結論は、単純です。

Supabase 上の 16,326 のデータベースが、認証なしでテーブルを読める状態にありました。

調べ方はこうです。

  1. BuiltWith の技術指紋データと、BigQuery 上の Chrome UX Report データセットから、Supabase 利用の痕跡がある約30万のドメインを洗い出す（公開されている JavaScript ファイルの中に、Supabase のキー名とデータベースのアドレスが書かれている）
  2. 各データベースへ users テーブルの有無を問い合わせる
  3. 応答から到達可能性を判定する

個々の行は読んでいません。 UpGuard はテーブルの定義（スキーマ）から露出の種類を評価したと述べています。

中身の内訳は次のとおりです。

区分 UpGuard の表現

パスワードまたは認証トークン より少ない割合（a smaller percentage）

件数は示されていません。 この記録では、割合の表現をそのまま残します。

UpGuard は、この調査を「この設定の失敗に関する調査としては過去最大であり、先行研究の合計のおよそ10倍の規模」と位置づけています。

原因は RLS の未設定——ただし「画面から作ったか、API から作ったか」で既定値が違う原因・手口出典 [1] [2]

露出の原因は 行レベルセキュリティ（Row Level Security・RLS） です。

Supabase は PostgreSQL をそのまま公開する構造を持ち、ブラウザ側の JavaScript から anon キー（公開してよい鍵）で直接データベースへ問い合わせます。誰がどの行を読めるかを決めるのは RLS のポリシーだけです。RLS が無ければ、anon キーを持つ誰でも——つまりインターネット上の誰でも——テーブルを読めます。

ここで重要なのが既定値の差です。

テーブルの作り方 RLS の既定
画面（UI）から作成（2025年3月以降） 有効
API 経由でプログラムから作成 有効にならない

つまり、手で作れば守られ、コードで作れば守られません。

UpGuard はもうひとつの型も挙げています。公開用の anon キーが、秘密鍵のように扱われている事例です。「鍵を隠しているから安全」という理解は、この基盤では成立しません。anon キーは公開されている前提で、RLS で守るのが設計です。

そして、ここに AI にコードを書かせる開発が重なりました。TechCrunch の指摘が正確です——「AI の道具でウェブサイトやアプリを簡単に作れる一方、生成されたコードにはしばしば安全上の欠陥が含まれ、あるいは開発者が知らない特定の設定を必要とすることがある」（原文英語）。

生成されたコードは動きます。 画面は表示され、データは保存され、テストは通ります。RLS が無いことは、動作では現れません。

例に挙がったデータの中身——在外自国民の所在、OTP の中継、平文パスワード被害規模・影響範囲出典 [1] [2]

UpGuard と TechCrunch が挙げた例です。いずれも 16,326 件のうちの1件であり、全体の代表ではありません。

  • インドのプラットフォーム——65,467人の個人情報・金融情報、10万件超の非公開メッセージ。TechCrunch は「インドのアダルト配信サイトにおけるセックスワーカーとの私的な会話」と説明
  • フィリピンのワンタイムパスコード配信サービス——2,000人超と10万件超の SMS。TechCrunch は「オンラインアカウントの本人確認用のワンタイムパスコードを受け取るための仮想 SIM ファーム」と説明している。配車サービスのやり取りも巻き込まれていた
  • 米国の車寄せ（バレー）サービス——10万人超の顧客の連絡先と車両情報（TechCrunch は「数千のナンバープレート」としており、表現に幅がある）
  • フランスにあるアフリカのある国の領事館——25,000人の自国民の住所と緊急時の滞在先
  • カナダの移民・移住サービス——約5,000件の記録、うち 884件が平文のパスワード

並べると、性質の違いが見えます。

住所や電話番号の漏えいは「詐欺の材料」ですが、在外自国民の所在一覧や、OTP を中継するサービスの記録は性質が違います。前者は誰がどこにいるかを追跡する材料であり、後者は他サービスの本人確認を突破する材料です。同じ「個人情報の漏えい」という言葉でくくると、この差が消えます。

「既定で安全」と「1万6千件が公開状態」は、両立してしまう（本記録の評価）評価・解釈出典 [1] [2]

ここからは本記録の作成者の評価です。

Supabase の CISO は TechCrunch に対し「プロジェクトは既定で安全（secure by default）」であり、セキュリティは同社と顧客の共同責任だと述べました。

この主張は、事実として間違っていません。画面から作ったテーブルには RLS が既定で有効になります。それでも 16,326 件が公開状態にありました。両立してしまうのです。

なぜかというと、「既定」が効く経路と、実際に使われる経路がずれているからです。AI にコードを書かせる開発では、テーブルは画面からではなく API から作られます。既定値が守るのは、いま最も使われていない経路のほうでした。

ここから引き出せる論点は3つあります。

1. 「既定で安全」は、どの経路の既定かを確認しないと意味がない。製品を評価するとき、「安全な既定値がある」という説明を受けたら、「それは UI 経由ですか、API 経由ですか、IaC 経由ですか」と聞く価値があります。自社の開発が実際に通る経路で既定が効かなければ、その既定は存在しないのと同じです。

2. 「動くこと」と「守られていること」を分けて検査する。 RLS の欠落は、動作テストでは絶対に現れません。認証を持たない状態でデータが読めるかを、リリース前に1回試すだけで防げます。これは高度な検査ではなく、curl 1本で足ります。この1回が入っていない開発工程が、1万6千件を生みました。

3. 共同責任という言葉の実務上の意味。「共同責任」は法的な整理としては妥当ですが、利用者側から見ると「あなたが設定しなければ公開されます」という宣言です。基盤を選ぶとき、責任分界点そのものより、「間違えたときにどちらに倒れるか」を見るべきだと考えます。間違えたときに公開に倒れる製品は、間違えたときに閉じる製品より、同じ人員でははるかに運用が難しくなります。

最後に、日本の組織にとっての読み方です。この事案で危ないのは、情報システム部門が把握しているシステムではありません。現業部門が作った小さなアプリ、委託先が「ついでに」作ったツール、実証実験のまま本番に残ったもの——棚卸しの対象から外れているものです。1万6千件という数字は、「把握されていないものの数」の話だと本記録は読みます。

人数も、期間も、悪用の有無も分かっていない未確定事項出典 [1] [2]

2026年9月27日時点で、次の点は公表されていません。

  • 何人分の個人情報が露出していたのか。 公表は「データベースの数」であり人数ではない
  • 露出はいつ始まり、いまも続いているのか。 開始時点も解消の有無も示されていない
  • UpGuard 以外の誰かが取得したのか。 認証なしで読める状態だった以上、取得されていないことの証明はできない
  • 本人への通知は行われたのか。 所有者への通知は述べられているが、その先は分からない
  • 日本の組織が運用するデータベースが含まれていたか。 国別の内訳が無い
  • パスワード・認証トークン・カードデータの正確な件数

とくに2点目のため、本記録は露出が未解消であることを前提に扱います。UpGuard が通知したのは「重大な露出」についてであり、16,326件の全てではありません。

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
UpGuard は、**重大な露出についてアプリケーションの所有者へ通知**したうえで、 **個々のデータベースの所在（ドメイン・組織名）を公表しなかった。** 例示は業種と国、件数のみに留めている部分的に機能**本記録の作成者の評価である。** 未修正の露出を名指しすれば被害を増やすため、非公表の判断は妥当と考える。 不十分なのは**「自分が該当するかを確認する方法」が示されていない**点である。 RLS の有無を自分で確かめる手順（認証なしでの読み取りを1回試す）は レポートの中核から導けるはずのもので、 **読者が自己点検に移れる形で示されていれば、公表の価値はさらに大きかった**
Supabase は本調査についてのリリースを出していない。 確認できるのは CISO が TechCrunch の取材に述べたコメント （「調査は見ていない」「プロジェクトは既定で安全」「共同責任」）のみである評価材料なし**本記録の作成者の評価である。** 公表の要否を判断する材料（同社が調査結果をいつ受け取ったか、 通知や修正の支援を行ったか）が公表されていないため、評価できない。 **評価できないこと自体を記録に残す**
CISO・経営層への示唆
  • 「安全な既定値」は、自社の開発が実際に通る経路で効くかを確認する
    Supabase は2025年3月以降、画面から作ったテーブルには RLS を既定で有効にした。 それでも16,326件が公開状態だった。 **AI にコードを書かせる開発ではテーブルは API 経由で作られ、 そこには既定が効かない。**
    取るべき行動 基盤製品の評価で「既定で安全」という説明を受けたら、 **「UI 経由か、API 経由か、IaC 経由か」を必ず確認する。** 自社の開発が通る経路で既定が効かないなら、 **その既定は存在しないものとして統制を設計する。**
  • 現業部門と委託先が作った小規模アプリを、棚卸しの対象に入れる
    露出していたのは、情報システム部門が構築した基幹システムではなく、 個々の開発者・事業者が作った小さなアプリケーションである。 **1万6千件という数字は「把握されていないものの数」でもある。**
    取るべき行動 **「個人情報を扱うかどうか」を基準に、規模に関係なく台帳へ載せる。** 委託契約に「データベース基盤を使う場合の申告」を条項として入れる。 **咎めない申告経路**を先に用意しないと、申告されないものが残る。
  • 「共同責任」を、間違えたときにどちらへ倒れるかで読む
    Supabase の CISO は「プロジェクトは既定で安全」「セキュリティは共同責任」と述べた。 主張自体は正しいが、利用者側から見れば **「あなたが設定しなければ公開されます」という宣言**でもある。
    取るべき行動 基盤の選定基準に、責任分界点の記述だけでなく **「設定を忘れたときに閉じるか、公開されるか」**を入れる。 公開に倒れる製品を選ぶ場合は、**検査の工程をセットで予算化する。**
  • 取得されたかを後から調べられるかを、導入時に決めておく
    認証なしで読める状態が続いていた以上、「取得されていない」ことの証明はできない。 **多くの小規模プロジェクトは、アクセスログの保持期間そのものが短い。**
    取るべき行動 個人情報を扱うプロジェクトについて、 **ログの保持期間を要件として定め、契約・設定の両方で確認する。** 「漏れたか分からない」という状態は、 **監督官庁への報告でも本人通知でも最も説明が難しい**ことを前提に決める。
セキュリティ技術者への示唆
  • 認証なしでデータが読めないことを、リリース前に必ず1回試す
    RLS の欠落は動作テストでは現れない。画面は表示され、データも保存される。 **「動くこと」と「守られていること」は別に検査しないと分からない。**
    取るべき行動 **anon キーだけを持った状態で、各テーブルへ問い合わせを1回投げる。** データが返ってきたら公開されている。 この確認を CI に組み込み、**新しいテーブルが追加されたら自動で走る**ようにする。
  • テーブルを API・マイグレーションで作るときは、RLS の有効化を同じ変更に含める
    画面から作ったテーブルには RLS が既定で有効になるが、 **API 経由で作ったテーブルは既定で有効にならない。** AI が生成するコードは後者の経路を通る。
    取るべき行動 **マイグレーションの雛形に `ENABLE ROW LEVEL SECURITY` と ポリシーの定義を最初から入れておく。** RLS が無効なテーブルを検出する検査をスキーマの検証に加え、 **見つかったら CI を落とす。**
  • anon キーは公開されている前提で設計する
    anon キーはブラウザ側の JavaScript に書かれるため、 誰でも読める。**「鍵を隠しているから安全」は、この基盤では成立しない。** UpGuard は、公開鍵が秘密鍵のように扱われている事例を挙げている。
    取るべき行動 **anon キーを秘密情報の管理対象から外し、代わりに 「このキーで何ができるか」を RLS で定義する。** service_role キー（全権限）がクライアント側のコードや 公開リポジトリに出ていないかを別途走査する。
  • AI が生成したコードは、動作ではなく「前提の欠落」を疑って読む
    生成されたコードは動く。動くが、 **開発者が知らない設定を前提にしていることがある**（TechCrunch の指摘）。 欠落は実行時のエラーにならないため、テストでは見つからない。
    取るべき行動 生成コードのレビュー観点に、 **①認証・認可はどこで効いているか ②既定値に依存している箇所はどこか ③公開される値と秘匿すべき値の区別**——の3点を明示的に加える。 「動いたので完了」をレビューの終了条件にしない。
  • 露出の点検を、外から見える情報で行う
    UpGuard は、**公開されている JavaScript ファイルの中の Supabase のキー名とデータベースのアドレス**を指紋として使った。 **同じことは誰にでもできる。**
    取るべき行動 自組織のドメインについて、**公開 JavaScript に含まれる バックエンドのエンドポイントと鍵を一覧化**する。 攻撃者と同じ視点で自社を1度見る。 BuiltWith や Chrome UX Report のような公開データに 自社が載っていることも前提に置く。

システム構成□ ブラウザやモバイルアプリから、バックエンドのデータベースへ直接問い合わせる構成を採っている（BaaS・マネージド PostgreSQL 等）この構成では、アクセス制御はデータベース側の行レベルの仕組みだけが担う。 アプリケーション層で認可を書いていても、 クライアントが直接叩ける経路が別に開いていれば意味を持たない。

委託・第三者部品□ AI 支援で生成したコードを、動作確認のみでレビューを終えている生成コードは動くが、開発者が知らない設定を前提にしていることがある。 欠落は実行時エラーにならないため、テストでは見つからない。
運用・監視□ 個人情報を扱うプロジェクトで、アクセスログの保持期間を要件として決めていない認証なしで読める状態が続いた場合、「取得されたか」を後から調べる手段は ログしかない。保持期間が短ければ、 **漏えいの有無を判断できないまま報告・通知の判断を迫られる。**
