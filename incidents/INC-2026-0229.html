脆弱性続報が続いている日本に波及した海外事案未知の脆弱性の悪用設計・実装上の不備
初報: 2026年9月27日 最終更新: 2026年10月1日

Citrix（Cloud Software Group）は 2026年9月27日、NetScaler ADC と NetScaler Gateway の脆弱性8件（CVE-2026-88771〜88778）を公表しました。この公報が本件の初報です。

そのうち2件は、修正が公開される前から悪用されていました。

CVE 内容 成立条件 CVSS v4
CVE-2026-88771 入力値検証の不備により未認証の攻撃者が任意のコマンドを実行（CWE-20） すべての NetScaler ADC / NetScaler Gateway の構成（既定構成・追加機能の有効化不要） 9.5
CVE-2026-88772 メモリオーバーフローにより遠隔コード実行または DoS（CWE-119） DTLS が有効（VPN 仮想サーバでは既定で有効） 9.5

Citrix の公報は「未緩和の NetScaler 環境における CVE-2026-88771 とCVE-2026-88772 の悪用が観測されている」（原文英語）と述べています。

CISA は同日、両者を KEV カタログへ収載し、「報告とパートナーの脅威インテリジェンスにより、脅威アクターがこれらの脆弱性を世界的に悪用していることを確認した」（原文英語）としました。連邦機関の対処期限は 2026年9月30日です。

この事案が重いのは、規模の大きさではなく、防御側に残された材料の少なさです。

  • 回避策が示されていません（CVE-2026-88771・88772 のいずれにも）
  • 公開の IoC 一覧がありません。 IoC は NetScaler Console 経由でのみ提供されます
  • 「先月当てたばかり」が安全の根拠になりません。 8月に別の脆弱性を直した版（報道によれば 14.1-73.32 / 13.1-63.21）も、今回の影響範囲に入ります
  • 更新すると、侵害の痕跡が消えます。 CISA は「更新はフォレンジックの可視性の喪失をもたらしうるため、更新の適用前に証跡を保全することが重要である」（原文英語）と明記しています

日本の組織が被害に遭ったという公表はありません。それでも本記録が扱うのは、NetScaler が国内でも自治体・大学・金融のリモートアクセス基盤として広く使われており、「当てる前に調べる」という順序を、緊急時に実行できるかどうかがそのまま先例になるからです。

【続報 2026年9月29日】材料の少なさは、ベンダーではなく調査会社が埋めた

Mandiant（Google Cloud）と Google Threat Intelligence Group（GTIG）は2026年9月29日、自ら CVE-2026-88772 の実地悪用を確認していたと公表しました。公報の2日後に、防御側が欲しかったものがまとめて出ました。

分かったことは4つです（すべて Mandiant / GTIG の公表による）。

  1. 時期。 キャンペーンは「少なくとも9月上旬から」続いていました。修正の公開は9月27日ですから、悪用は修正に2週間以上先行していたことになります
  2. 範囲。 北米と欧州の、政府・金融サービス・技術・教育・法務および専門サービスの組織が影響を受けた可能性が高いとしています。組織名と件数は依然として出ていません
  3. 入口。 認証前の暗号ハンドシェイクで、UDP/443 の DTLS レコードを壊した形で送ると NetScaler Packet Processing Engine（NSPPE）のヒープが壊れ、FreeBSD 上で root 権限のシェルコードが動くという筋です（GTIG は「悪用コードそのものは持っていない」と明記しています）
  4. その後。 攻撃者は httpd.conf を書き換えて .deb や .sig を PHP として実行させる仕掛けを作り、/bin/sh に setuid を立て、crontab から自分の設置パスを消していました。道具は PHP ウェブシェル WHIPSHOT と Python トンネラ SLAPSHOT で、少なくとも1件ではこの経路で内部探索と資格情報の窃取が手作業で行われたとしています

そして、この日はじめて照合できる材料が公開されました。 Mandiant は IoC（IP アドレス2件・HTTP ヘッダ名・URI パス・ファイルパス）、YARA 5本、Google Security Operations の検知ルール8本、そして装置のログで何を見るかを出しました。9月27日の CISA の指示（「更新の前に侵害の兆候を確認せよ」）に対して、確認の材料が NetScaler Console の外にも存在する状態に、ようやくなりました。

なお Unit 42 は9月28日の時点で、自分たちの狩猟指針は「本件で観測された TTP ではない」と明記していました。 2日のあいだ、防御側は手口を知らないまま止めるか当てるかを決めていたことになります。同社は同日、Cortex Xpanse の観測で 50,277 台が露出していたと述べています（2026年9月27日時点）。

インターネットに面した NetScaler ADC / NetScaler Gateway に対し、 修正の公開前から CVE-2026-88771（未認証の任意コマンド実行）と CVE-2026-88772（DTLS 経由のメモリオーバーフロー）が悪用された。 **【続報 2026年9月29日】Mandiant / GTIG が CVE-2026-88772 側の手口を公表した。** 認証前の **UDP/443 の DTLS ハンドシェイク**で NSPPE のヒープ境界を壊し、 FreeBSD 上で **root 権限**のシェルコードを実行する。その後 **`/etc/httpd.conf` を書き換えて `.deb` / `.sig` を PHP として実行させ**、 **`/bin/sh` に setuid を立て**、**crontab から自分の設置パスを消す。** 道具は PHP ウェブシェル **WHIPSHOT** と Python トンネラ **SLAPSHOT** で、 少なくとも1件では**この経路で内部探索と資格情報の窃取が手作業で行われた。** **CVE-2026-88771 側の手口は、いまも公表されていない**—— Mandiant が直接観測したのは 88772 だけである。

【続報】攻撃者は、装置の中に住み続ける仕掛けを作っていた原因・手口出典 [10]

2026年9月29日、Mandiant / GTIG が手口を公表しました。同社は被害組織のインシデント対応を担当した立場から、CVE-2026-88772 の実地悪用を自ら確認したとしています。以下はすべて同社の公表によるもので、攻撃者が実際に行ったことです。

入口——UDP/443 の DTLS ハンドシェイク

NSPPE（NetScaler Packet Processing Engine）は、認証前の暗号ハンドシェイクで受信した DTLS レコードの構造を解析します。 ここに壊した形または断片化した形のレコードヘッダを送ると、パケットエンジンのヒープのメモリ境界が壊れ、制御の流れが逸れて、FreeBSD 上で root 権限のシェルコードが実行される——という筋です。

重要な留保が付いています。GTIG は「悪用コードそのものは保有していない」（原文英語）と明記し、この機序は前線のテレメトリからの推定であると述べています。断定された機序ではありません。

配送路が UDP/443 であることは、防御の選択肢に直結します（後述）。

残る痕跡——2つのログ

悪用の試行は、装置に2種類の痕跡を残していました。

  1. Syslog の SSL ハンドシェイク失敗。 ClientVersion が DTLSv1.0、Reason がHandshake failure-Internal Error の SSL_HANDSHAKE_FAILURE イベント
  2. NSPPE プロセスの停止（/var/log/messages）。NSPPE-<##> exit with orphan rings と、ウォッチドッグ（pitboss）によるNOT restarting NSPPE-<##>

Mandiant は「同一装置で、DTLS ハンドシェイク失敗の数分後に NSPPE の停止が続いていれば、悪用の強い兆候であり、高い優先度で調査すべきである」（原文英語）と述べています。これが本件で初めて公開された、確度の高い検知条件です。

永続化——Web サーバの設定を書き換える

侵入に成功した攻撃者は、/etc/httpd.conf を書き換えて、スクリプトでないファイル種別を PHP として実行させるようにしました。観測されたのは2通りです。

  • .deb をパッケージに見せる方法。 AddHandler application/x-httpd-php .deb を足し、/netscaler/gui/vpn/scripts/linux にウェブシェルを .deb の名前で置く
  • アイコン要求に見せる方法（より隠れる）。 /vpn/media/ 配下の .ico への要求を、同名の .sig ファイルへ写すAliasMatch を足し、.sig を PHP として実行させる。つまり画像を取りに来ているように見える要求で、ウェブシェルが動きます

Mandiant は「アクセスログでは HTTP 404 を返しているのに、処理時間が長く応答が数キロバイトある GET 要求が見えた」と述べています。404 だから何も無かった、とは読めません。

権限——/bin/sh に setuid を立てる

悪用そのものは root で動きますが、その後の Web 要求は非特権のWeb サービス権限で処理されます。 そこで攻撃者は

chmod u+s /bin/sh

を実行し、以降の Web 要求が昇格した権限で動くようにしました。設定変更と合わせて反映するため、装置ごと再起動（/netscaler/nsshutdown -R）するか、httpd を再起動しています。境界装置の予期しない再起動は、それ自体が調査の入口になります。

道具——WHIPSHOT と SLAPSHOT

名前 種別 何をするか
WHIPSHOT PHP ウェブシェル Base64 のコマンドを、装置固有の HTTP ヘッダ名に隠して受け取る。error_reporting(0) で誤りを黙らせ、応答には HTTP 404 を立てつつ、本体にトンネルの応答を入れて返す
SLAPSHOT Python トンネラ ループバックの一時ポートに待ち受け、内部ネットワークの任意のホストへ TCP を中継する。独自の通信形式（4バイトの長さ＋JSON）で open / push / pull / exch / close / ping を持つ

SLAPSHOT は /tmp/.uxdport に使用中のポートを書き、/tmp/.uxdlock で二重起動を防いでいます。15分でセッションを閉じ、10分 何も来なければ自分のファイルを消してプロセスを終える——痕跡と検知面を小さく保つ設計です。

少なくとも1件の侵入では、この中継を通して内部探索と資格情報の窃取が手作業で行われました。

痕跡消し

設置用のウェブシェルは、/etc/crontab から自分の設置パス（/vpn/scripts/linux）への参照を正規表現で消していました。 攻撃者は、調べられることを前提に動いています。

【続報】88771 の側は、認証フィールドにコマンドを書き、ウェブシェルを CSS に化けさせていた原因・手口出典 [16] [17]

LevelBlue の THOR チームの公表（2026年9月30日）によれば、CVE-2026-88771 の事後活動として観測されたのは次である。

入口の痕跡は認証ログにある。攻撃者が仕込んだ利用者名には、装置自身のプロセス異常終了メッセージを模したpitboss と NSPPE を含む文字列が使われ、そのうしろにセミコロンでコマンドが続き、最後に # が置かれていた（以降の正規の引数をコメントとして飲み込ませる形である）。注入された実物として公開されたのは、

  • 実行可否の確認だけを行うもの（whoami）
  • 外部から Perl スクリプトを取って perl に直接流し込むもの（curl … | perl）
  • 外部からファイルを取るもの（wget）
  • /flash/nsconfig/ns.conf をウェブ公開ディレクトリの .js ファイルへ書き出すもの
  • /flash/nsconfig ディレクトリ全体を固めてウェブ公開ディレクトリの .html ファイルに置くもの

の5種である。後の2つは装置の設定ファイルを、外から HTTP で取れる場所へ、正規の資源に見える拡張子で置くという形をとっている。

第二段は2本が解析された。

1本目の Perl スクリプト（update_c08937.pl）は、
- /flash/nsconfig/ns.conf を書き換えて sec_monitor という局所アカウントを作り、superuser 権限を与える
- /flash/nsconfig を /tmp 配下の .tgz に固めて外部へ送り、送った後に書庫を消し、自分自身も消す
- /bin/sh の許可属性を 6555 に変える（setuid / setgid を立てる）
- /var/netscaler/logon/LogonPoint/.local_journal に PHP のウェブシェルを置く（先頭にドットを付けた、ログ部品に見える名前である）
- /etc/httpd.conf を書き換えて PHP の実行を有効にし、そのウェブシェルを「正規の NetScaler の CSS 資源に見える URL」に対応づける——公開された名前は LogonUISimple.html.style.min.css と、その16進のランダムな変種である

ここまでの段階は、Mandiant が9月29日に公表した CVE-2026-88772 の事後活動と「/etc/httpd.conf を書き換えて PHP を実行させる」「/bin/sh に setuid を立てる」の2点で型が一致する。 ただし道具の名前・設置パス・URL の化け方はいずれも一致しない。 同一の攻撃者かどうかは、どちらの公表も述べていない（unknowns に残した）。

本件でもっとも実務的に重いのは、作業の順序です。

CISA は注意喚起で次のように述べています（原文英語）。

  • 「可能であれば、パッチ適用の前に侵害の兆候を確認することが推奨される」

KEV の両エントリには forensicTriage: Yes の印が付いており、required action は BOD 26-04 の「Forensics Triage Requirements」に従うことを求めています。「当てれば終わり」という扱いを、当局が明示的に否定している形です。

理由は単純です。修正が公開される前に悪用されていたので、更新を当てても「自分が先に踏まれていたか」は分かりません。そして更新の過程で、踏まれていた証拠のほうが先に消えます。

Citrix 自身の侵害時手順（CTX694799）は、順序を次のように定めています。

  1. 証跡の保全が最初。 VPX なら潜在的に侵害されたインスタンスのスナップショットを取る。隔離の前にシステム時刻・タイムゾーン・NTP 設定を記録する。ローカルのログに加えてリモート syslog サーバと NetScaler Console のログを保全する。technical support bundle を生成し、Packet Engine のコアダンプを採取する（この処理でウォームリスタートが起き、SSH は切断される）。MPX / SDX の物理装置は、メモリ保全の後に電源を落とし、書き込みブロッカを使ってビット単位のディスクイメージを2部作り、証拠保全用と解析用に分け、証拠の連鎖（chain of custody）を記録する
  2. 装置をネットワークから隔離する
  3. 資格情報をすべて失効させる。 装置に保存されていたサービスアカウントのパスワードと秘密（LDAP サービスアカウント・RADIUS の共有秘密・OAuth トークン・API キー・SNMP コミュニティ名）をそれぞれのシステム側で変更する。その装置を経由して認証した利用者アカウントのパスワードも変更する。装置に置かれていた証明書と秘密鍵を失効させる
  4. 接続先を調べる。 認証サーバ・機微なシステム・Web 層・管理用踏み台を確認する
  5. 再構築して復元する。 MPX は消去して再インストール、VPX はインスタンスの置き換えを推奨。ファームウェアを最新にしてから、侵害より前の日付だと確認できたバックアップで設定を戻す

Citrix は「Cloud Software Group はフォレンジック調査を支援しない」と明記しています。調査の能力は、利用者側にあるか、契約している外部にあるかのどちらかです。

また、公報は「NetScaler Management Services を公衆インターネットへ公開してはならない」と繰り返しています。これは今回の脆弱性の回避策ではありませんが、本件の影響を小さくする方向に効きます。

今日打てる手——ただし 88771 には効かないものがある

Mandiant は緩和策を3系統で示しました。順序と適用範囲に注意が要ります。

第1に、修正版の適用（14.1-73.37 / 13.1-64.23 以降）。同社の第1推奨です。

第2に、隔離。 侵害が確認または疑われる装置はネットワークから外します。ここで同社が加えているのが HA（冗長構成）の扱いです—— 2台を独立に評価し、両方の検証が終わるまで設定の同期を止める。 止めなければ、書き換えられた httpd.conf が待機系にも複製されます。これは公報にも CISA の注意喚起にも無かった指摘です。

第3に、当てられない場合の代替。 ここが重要です。

  • DTLS を、必要のないインターネット向け Gateway 仮想サーバで無効化する
  • 上流のファイアウォールまたはエッジルータで、着信 UDP/443 を遮断する。 Mandiant は「装置内の ACL だけに頼ると、通信は落とされる前に脆弱なパケット処理エンジンに届いてしまう」（原文英語）と明記しています。装置の中で止めるのでは遅い、という指摘です
  • 上流での送信元 IP の許可制（負荷分散だけに使っている装置などで）

そして同社は自ら限界を書いています。「上記の DTLS と UDP/443 の制御は CVE-2026-88772 に固有のものであり、CVE-2026-88771 の緩和として頼ってはならない。両方に対処するには、修正済みの NetScaler ビルドの適用が依然として必須である」（原文英語）。

証跡の取り方が1つ増えた

Mandiant は、仮想装置について「再起動の前に、可能な限り、メモリ状態を含む完全な VM スナップショットを取る」（原文英語）としています。chmod u+s /bin/sh を反映するために攻撃者が装置を再起動させているため、再起動はこちらの都合でなく起きうることになります。メモリを含めたスナップショットは、その前にしか取れません。

ここからは本記録の作成者の評価です。

本件が先例として重いのは、脆弱性の深刻さではありません。CVSS 9.5 のゼロデイは境界装置では珍しくなく、NetScaler 自体、過去に繰り返し同じ立場に立ってきました。

新しいのは、当局が「当てる前に調べよ」と明示し、ベンダーが「調査は支援しない」と明示したという組み合わせです。この2つが並ぶと、調査能力を持たない組織には実行できない指示になります。

実際に何が要るかを数えてみます。

  • 装置のスナップショットを取る権限と保存先（VPX ならハイパーバイザ側の作業）
  • リモート syslog（装置内のログだけでは、消えるものが多い）
  • コアダンプを取る覚悟（ウォームリスタートが起き、その間サービスが止まる）
  • 物理装置なら書き込みブロッカと証拠保全の手順
  • 装置に保存されたすべての秘密の棚卸し（LDAP・RADIUS・OAuth・API キー・SNMP・証明書と秘密鍵）
  • 「その装置経由で認証した利用者」の一覧

最後の2つが、たいていの組織で用意されていません。境界装置は、認証情報が集まる場所です。 VPN と認証を1台に寄せた構成では、その1台の侵害が「社内のほぼ全員の認証が攻撃者の手を通った」という意味になります。しかし「そこに何の秘密が置いてあるか」の台帳は、たいてい装置の設定ファイルの中にしかありません。

ここから引き出せる論点を3つ挙げます。

1. 「当てる前に調べる」は、事前に決めておかないと実行できない。緊急パッチが出た日に、スナップショットの保存先を探し、コアダンプでサービスが止まることを事業部門に説明し、証跡の保管方針を決めることはできません。平時に「境界装置が侵害疑いになったときの初動手順」を1枚にしておく必要があります。決めるべきは技術ではなく、止める権限と、何を捨てるかです。

2. IoC がベンダー製品経由でしか出ないとき、どうするか。本件の IoC は NetScaler Console 経由で提供されます。これは「その製品を導入していない組織は照合できない」ことを意味します。さらに、運用を外部に委ねている組織は、委託先が照合したかどうかを自分では確認できません。委託契約に「ベンダー提供の IoC による照合の実施と報告」を明示的に含めているかは、点検に値します。

3. 報告者が利用者側の金融機関だったという事実。 Citrix の謝辞に並ぶのは、JPMorgan Chase の XOR Team と個人研究者です。報道によれば、watchTowr はフォレンジック調査の過程で見つかったと述べています。つまり本件は、誰かの侵害調査から製品の脆弱性が逆算された可能性が高い形です。これは防御側にとって悪い知らせではありません。自組織の侵害調査の結果を、製品ベンダーへ返す経路を持っているかという問いに変わるからです。国内では、この経路が「ベンダーの営業窓口」しか無い組織が多いはずです。

最後に、前日の混乱について一言残します。公報の前日、IT 供給元から「直ちに NetScaler を停止せよ」と電話を受けた管理者が現れ、同様に止めた組織が続きました。この警告の出どころは確認されていません。結果として「情報は正しかった」わけですが、出どころの分からない指示で本番を止めるかどうかという判断は、本記録の INC-2026-0224（Kiteworks）とまったく同じ形です。この型の判断は、今後も繰り返し来ます。

事案の詳細

影響を受けたサービスCitrix NetScaler ADC（旧 Citrix ADC）および Citrix NetScaler Gateway（旧 Citrix Gateway）。 企業ネットワークの境界で VPN・リモートアクセス・負荷分散・利用者認証を担う装置。 **Secure Private Access Hybrid 構成で使われる NetScaler インスタンスも対象**。 Citrix が管理するクラウドサービスと Citrix 管理の Adaptive Authentication は Cloud Software Group が更新する

ログの有無**利用者側で「自分が踏まれたか」を判定する材料が薄い。** IoC は NetScaler Console 経由でのみ提供され、公開の一覧が無い。 さらに CISA は「更新はフォレンジックの可視性の喪失をもたらしうる」としており、 **順序を間違えると判定の機会そのものが消える。** Citrix の手順は、装置内のログだけでなく **リモート syslog サーバと NetScaler Console のログの保全**を求めている—— これは逆に、**リモート syslog を出していない装置では、残るものが少ない**ことを意味する。 **【続報 2026年9月29日】判定の材料は大きく増えた。** Mandiant / GTIG が示したのは装置に実際に残る痕跡で、 ①Syslog の `SSL_HANDSHAKE_FAILURE`（`ClientVersion` が **DTLSv1.0**・ `Reason` が **`Handshake failure-Internal Error`**）と、 ②`/var/log/messages` の **NSPPE 停止**（`exit with orphan rings`・ pitboss の `NOT restarting`）である。 **同一装置でこの2つが数分以内に続いていれば悪用の強い兆候**とされる。 あわせて `/etc/httpd.conf` の差分・`/bin/sh` の setuid ビット・ `/tmp/.uxdport` と `/tmp/.uxdlock` の有無・ `/netscaler/gui/vpn/scripts/linux` 配下の `.deb` / `.sig` / `.php`・ Web アクセスログの「**404 を返しているのに処理時間が長く応答が数キロバイト**」の GET 要求が判定に使える。**NetScaler Console を持たない組織でも照合できる形である。** ただし限界が2つ残る——**①これらは CVE-2026-88772 の悪用の痕跡であり、 すべての構成が対象の 88771 経由で入られた場合に何が残るかは分からない。** **②攻撃者は `/etc/crontab` から自分の設置パスを消していたため、 痕跡が消されている前提で見る必要がある**

判断評価評価の根拠と留保
Citrix は、**修正版を用意した日に、8件の脆弱性と2件の悪用の観測を同時に公表**した。 前日から外部で噂が流れ、装置を停止する組織が出ていた段階での公表にあたる部分的に機能**本記録の作成者の評価である。** 悪用を隠さずに明記し、成立条件・CWE・CVSS・確認手順まで示した点は評価できる。 とくに**各 CVE の成立条件を、設定の具体的な行（`add vpn vserver ... -dtls OFF` 等）と 確認コマンド（`show ns tcpparam | grep "Enhanced ISN Generation"`）で 示している**のは、利用者が該否を自力で判定できる形であり、実務的に良い。 不十分なのは**回避策が無いこと**である。修正版へ上げられない事情 （検証期間・冗長構成・保守契約）を持つ組織に、取れる手が残らない。 「Management Services を公開しない」は一般則であって本件の回避策ではない
**IoC を NetScaler Console 経由でのみ提供**し、公開の一覧を出さなかった。 攻撃の手口の詳細（エンドポイント・要求の形）も公表していない不十分**本記録の作成者の評価である。** CISA が「更新の前に侵害の兆候を確認せよ」と求めている一方で、 **確認の材料が特定の管理製品の中にしか無い**という組み合わせは、 指示として完結していない。 ベンダーが手口を伏せる判断は理解できるが、 **IoC は製品の外でも使える形（ファイル名・パス・ログの見どころ）で 出す余地があった**と考える。 **【続報 2026年9月29日】この「余地があった」という評価は裏付けられた。** Mandiant / GTIG が、まさに**製品の外でも使える形**—— ログのパターン・ファイルパス・HTTP ヘッダ名・YARA 5本——で公開した。 **同じ情報を、2日早く Citrix が出せない理由は見当たらない。** なお **Citrix の公報は9月30日時点でも改訂されておらず** （更新履歴は2件・いずれも 2026-09-27）、 **Mandiant の公表や WHIPSHOT への参照は追加されていない。** 評価は `insufficient` のまま据え置く
**Mandiant / GTIG は、被害組織のインシデント対応で得た手口を 公報の2日後に公開した**——IoC・YARA 5本・検知条件・緩和策を含む。 一方で**攻撃者の帰属は行わず**、名前付きアクターも UNC 番号も付けなかった機能した**本記録の作成者の評価である。** 評価できるのは3点。①**製品に依存しない形で出した**こと （ログのパターン・パス・ヘッダ名は、NetScaler Console が無くても照合できる）。 ②**自分の限界を明記した**こと——「悪用コードは保有していない」 「機序はテレメトリからの推定」「DTLS と UDP/443 の制御は 88772 にしか効かない」。 ③**帰属を付けなかった**こと。被害組織を直接調査した立場で、 付けられたはずのものを付けていない。 **本記録が続報で書ける内容の大半は、この1本に依拠している。** 留保として、**同社が直接観測したのは CVE-2026-88772 のみ**であり、 88771 については他者の公表を引く形でしか触れていない点は discrepancies に記録した
CISO・経営層への示唆
  • 「境界装置が侵害疑いになったときの初動」を、平時に1枚にしておく
    本件では当局が「更新の前に侵害の兆候を確認せよ」と求め、 ベンダーは「フォレンジック調査は支援しない」と明記している。 スナップショットの保存先、コアダンプでサービスが止まることの合意、 証跡の保管方針を、緊急パッチが出た日に決めることはできない。
    取るべき行動 **「境界装置の侵害疑い」を独立した発動条件として手順を1枚にする。** 書くべきは技術ではなく、**誰が装置を止められるか・何分以内に集まるか・ コアダンプでサービスが止まることを誰が許可するか**である。 年1回、実際にスナップショットと support bundle を取る訓練をする。
  • 「先月当てたばかり」を安全の根拠にしない運用へ切り替える
    8月に別の脆弱性を修正した版が、今回の影響範囲に入っている。 境界装置では「直近で更新した」ことが次の脆弱性への防御にならない。 加えて 13.1 系は保守終了の12日後に修正が出ており、 保守終了系統の運用はベンダーの善意に依存している。
    取るべき行動 **境界装置の版と保守期限を、資産台帳の必須項目にする。** 「現在の版」「保守終了日」「次の計画更新日」を並べ、 **保守終了が近い装置は更新計画を先に立てる。** 「緊急時には修正が出た」を前提にした延命は方針として認めない。
  • ベンダー提供の IoC で照合したかを、委託先に報告させる
    本件の IoC は NetScaler Console 経由でのみ提供され、公開の一覧が無い。 装置の運用を外部に委ねている組織は、 委託先が照合したかどうかを自分では確認できない。
    取るべき行動 **運用委託の契約・SLA に「ベンダー提供の IoC による照合の実施と結果報告」を 明示的に含める。** 含まれていない契約は、次の更新時に条項を足す。 当面は、緊急時に「照合したか／結果は何か」を書面で求める運用で補う。
  • 境界装置に集まっている秘密の量を、経営が把握する
    Citrix の侵害時手順は、装置に保存された LDAP サービスアカウント・ RADIUS の共有秘密・OAuth トークン・API キー・SNMP コミュニティ名・ 証明書と秘密鍵の失効と、装置経由で認証した利用者のパスワード変更を求めている。 これは装置1台の侵害が、組織のほぼ全員の認証に及ぶことを意味する。
    取るべき行動 **「この装置が取られたら、何を失効させるのか」の一覧を作る。** 装置の設定ファイルの中にしか無い状態をやめ、台帳として持つ。 一覧の長さが、そのまま境界装置1台のリスクの大きさである。
  • 出どころの分からない緊急警告への応じ方を、あらかじめ決めておく
    公報の前日、IT 供給元から「直ちに NetScaler を停止せよ」と電話を受けた 管理者が現れ、同様に止めた組織が続いた。 警告の出どころは確認されていないが、結果として情報は正しかった。 この型の判断は繰り返し来る。
    取るべき行動 **「検証できない警告で本番を止めるか」の判断者と手続きを決めておく。** 判断の時点で分かっていたこと・分からなかったことを、その場で記録する。 「何も起きなかった」は判断の正しさを証明しないため、 **手順が機能したかで事後評価する**と決めておく。
  • 「材料が来る前の2日間に何をするか」を決めておく
    本件では、当局の指示（9月27日「更新の前に侵害の兆候を確認せよ」・ 9月28日 英国 NCSC「公開された IoC を用いて全面調査せよ」）が、 照合材料の公開（9月29日 Mandiant / GTIG）より**先に出た。** Unit 42 は9月28日の時点で「これは本件で観測された TTP ではない」と 自ら明記している。**指示の側が材料の側より2日早かった。** この順序は、ベンダーが手口を伏せるかぎり繰り返される。
    取るべき行動 **手口が分からない段階で取れる行動は「隔離」と「証跡の保全」の2つだけである**と 決めておく。この2つは IoC を必要としない。 **「IoC が出たら調べる」は行動計画ではない**—— 材料が来るまでの時間に何をするかを書いていない手順は、 本件と同じ形の事案で毎回2日間空白になる。 逆に、**材料が公開された時点で遡って調べ直す**ことを 手順の中に明示的に入れる（9月28日に「白」と判定した装置は、 9月29日以降に再判定する対象である）。
  • 冗長構成の切り替えが、侵害の複製になりうることを前提に手順を書く
    攻撃者が書き換えたのは **`/etc/httpd.conf`（設定ファイル）**であり、 **設定は HA で同期される。** 「片方を隔離して、もう片方に切り替えて業務を続ける」という もっとも自然な事業継続の判断が、そのまま待機系の汚染になりうる。 **この指摘は Citrix の公報・CISA の注意喚起・各国 NCSC のいずれにも無く、 Mandiant が2日後に加えたものである。**
    取るべき行動 **境界装置の侵害疑い時の手順に「切り替えの前に設定同期を止める」を 明示的に1行入れる。** そして**両系を独立に評価する**と決めておく。 あわせて、**事業継続の判断者（切り替えを決める人）が この制約を知っているか**を確認する—— 知らなければ、セキュリティ側が止めるより早く切り替えが実行される。
セキュリティ技術者への示唆
  • 今日、成立条件を設定ファイルで機械的に判定する
    Citrix の公報は、各 CVE の成立条件を具体的な設定の行と確認コマンドで示している。 推測ではなく、自分の装置が該当するかを確定できる。
    取るべき行動 `/nsconfig/ns.conf` または `show ns runningConfig` に対して判定する。 **DTLS**: `add vpn vserver` の行に `-dtls OFF` が**無ければ既定で有効**（88772 該当）。 `add lb vserver ... DTLS` も該当。 **88778**: `show ns tcpparam | grep "Enhanced ISN Generation"` が DISABLED なら該当。 **88776**: `add lb vserver.*ORACLE.*`。 **88777**: `add (lb|cs) vserver .* FTP`・`set lsn group .* -rtspalg ENABLED`・ `add lb vserver .* DNS .* -dns64 ENABLED`・`add nat64`。 **CVE-2026-88771 は判定不要——すべての構成が該当する。**
  • 更新の前に、取り返しのつく順序で証跡を取る
    修正の公開前に悪用されていたため、更新を当てても 「自分が先に踏まれていたか」は分からない。 そして更新の過程で、踏まれていた証拠のほうが先に消える。
    取るべき行動 VPX は**スナップショット**、続いて**system time・timezone・NTP 設定の記録**、 **リモート syslog と NetScaler Console のログの退避**、 **technical support bundle**、最後に **Packet Engine のコアダンプ** （`/var/core/<N>` の `NSPPE-*`。**ウォームリスタートが起き SSH が切れる**）。 物理装置はメモリ保全後に電源を落とし、書き込みブロッカでイメージを2部作る。
  • 装置に置いた秘密を、更新の有無にかかわらず全部回す
    侵害が確認できなくても、確認できないだけである可能性が残る。 境界装置に保存された秘密は、失効させるまで有効なままである。
    取るべき行動 LDAP サービスアカウント・RADIUS 共有秘密・OAuth トークン・API キー・ SNMP コミュニティ名を**それぞれのシステム側で**変更し、 装置上の**証明書と秘密鍵を失効**させる。 **その装置経由で認証した利用者のパスワードも変更対象に含める。** 影響が大きい作業なので、優先順位（管理者→サービスアカウント→一般利用者）を決めて進める。
  • リモート syslog が出ていない境界装置を、今日洗い出す
    Citrix の手順が「ローカルのログに加えてリモート syslog サーバと NetScaler Console のログを保全せよ」と書いていることは、 裏返すと**リモート syslog を出していない装置では残るものが少ない**という意味である。
    取るべき行動 境界装置すべてについて、**syslog の転送先が設定されているか**と **転送先での保存期間**を一覧にする。 保存期間が「悪用の開始時期が分からない」本件のような事案に足りるかを見る。 足りなければ、まず保存期間の延長が投資として効く。
  • 復元に使うバックアップが「侵害より前」だと言える状態にしておく
    Citrix の手順は「バックアップから復元する場合、侵害より前の日付であることを 検証せよ」と求めている。しかし本件では悪用の開始時期が公表されていない。
    取るべき行動 設定バックアップを**日付つきで複数世代**残し、 「いつの設定に戻せるか」を月単位で遡れる状態にする。 世代が1つしか無い運用は、この指示を実行できない。
  • 今日できる4つの点検を、いま実行する（IoC の値を待たない）
    Mandiant / GTIG が2026年9月29日に公開した痕跡は、 **NetScaler Console を持たない組織でも装置上で確認できるもの**である。 IP アドレスやハッシュ値を照合する必要がない点検が4つある。 9月28日時点ではできなかったことが、いまはできる。
    取るべき行動 ①**`/bin/sh` に setuid ビットが立っていないか**を見る（最短で終わる）。 ②**`/etc/httpd.conf` に `AddHandler` / `AliasMatch` / `php_flag engine` の 追加が無いか**を見る（`.deb` と `.sig` が PHP として登録されていないか）。 ③**`/netscaler/gui/vpn/scripts/linux` 配下に `.deb` / `.sig` / `.php` が 置かれていないか**を見る。 ④**`/tmp/.uxdport` と `/tmp/.uxdlock` の有無**を見る。 **④は10分の無通信で自分から消える設計なので、無いことは白の根拠にならない。** ①〜③のほうが残りやすい。**すべて陰性でも「侵害なし」とは書かない**—— 攻撃者は `/etc/crontab` から自分の設置パスを消していた。
  • DTLS ハンドシェイク失敗と NSPPE 停止の相関を、いま遡って検索する
    Mandiant は「**同一装置で、DTLS ハンドシェイク失敗の数分後に NSPPE の停止が 続いていれば、悪用の強い兆候であり、高い優先度で調査すべき**」（原文英語）と 述べている。**これは装置に最初から残っていた痕跡であり、 リモートへ転送済みであれば、装置を更新した後でも遡れる。** 悪用は少なくとも9月上旬から続いていた。
    取るべき行動 SIEM・リモート syslog に対して**2026年9月1日以降**を対象に、 ①`SSL_HANDSHAKE_FAILURE` で `ClientVersion` が **DTLSv1.0** かつ `Reason` が **`Handshake failure-Internal Error`** のもの、 ②`/var/log/messages` の `NSPPE-<##> exit with orphan rings` および pitboss の `NOT restarting NSPPE-<##>` を検索し、 **同一装置で数分以内に続く組み合わせ**を抽出する。 あわせて、**DTLS を無効化している（または使っていない）装置への 着信 UDP/443** も見る。 検索範囲の下限を9月1日に置くのは、 「少なくとも9月上旬から」という下限しか公表されていないためである。
  • Web アクセスログで「404 なのに重い応答」を探す
    WHIPSHOT と各ウェブシェルは **応答に HTTP 404 を立てて「存在しないページ」を装う。** Mandiant は「アクセスログでは HTTP 404 を返しているのに、 **処理時間が長く応答が数キロバイトある** GET 要求が見えた」と述べている。 **ステータスコードだけで絞ると、これは 404 の山に埋もれる。**
    取るべき行動 装置の Web アクセスログを、**ステータスコードではなく 「処理時間」と「応答サイズ」で絞る。** `404 かつ 処理時間が長い かつ 応答が数 KB 以上` の要求を抽出する。 あわせて **`/vpn/media/` 配下の `.ico` への要求**と、 **装置が本来使わない HTTP 要求ヘッダ名**の出現を見る （ヘッダ名の実値は Mandiant のブログにある。本記録は転記しない）。 **このログを装置外へ転送していない場合、更新や再構築で消える。** 転送設定は、点検より先に手を付ける価値がある。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ NetScaler ADC / NetScaler Gateway をインターネットに面して運用しているCVE-2026-88771 は「すべての構成」が対象で、追加機能の有効化を要さない。 該否の判定を待つ余地が無く、修正版への更新が唯一の対処である。
システム構成□ VPN 仮想サーバで DTLS を明示的に無効化していないDTLS は VPN 仮想サーバで既定で有効である。 `-dtls OFF` を書いていない装置は CVE-2026-88772 の成立条件を満たす。
認証・認可□ 境界装置に LDAP・RADIUS・OAuth・API キー・証明書の秘密が保存されているCitrix の侵害時手順は、これらすべての失効と、装置経由で認証した利用者の パスワード変更を求めている。装置1台の侵害が組織全体の認証に及ぶ。
運用・監視□ 境界装置のログをリモート syslog へ転送していない、または保存期間が短い悪用の開始時期が公表されていないため、遡る範囲を決められない。 装置内のログだけでは、更新や再構築で消える。
運用・監視□ 「更新の前に侵害の兆候を確認する」手順（スナップショット・コアダンプ）が決まっていないCISA は更新前の証跡保全を求め、Citrix はフォレンジック調査を支援しないと明記している。 平時に決めていなければ、緊急の日には実行できない。
システム構成□ NetScaler を HA（冗長構成）で運用しており、侵害疑い時に 「設定同期を止める」手順が無い攻撃者が書き換えるのは `/etc/httpd.conf`（設定ファイル）であり、 **設定は HA で同期される。** 「片方を隔離して他方に切り替える」という自然な事業継続の判断が、 **そのまま待機系の汚染になりうる。** Mandiant は両系を独立に評価し、検証が終わるまで同期を止めるよう求めている。
システム構成□ インターネットから装置への着信 UDP/443 を、上流のファイアウォールまたは エッジルータで制御していないCVE-2026-88772 の悪用は **UDP/443 の DTLS** で配送される。 Mandiant は「**装置内の ACL だけに頼ると、通信は落とされる前に 脆弱なパケット処理エンジンに届いてしまう**」としている。 **装置の中で止めるのでは遅い。** ただしこの制御は **CVE-2026-88771 には効かない**——修正版の適用は依然必須である。
運用・監視□ 装置の Web アクセスログ・Syslog・`/var/log/messages` を 装置外（リモート syslog / SIEM）へ転送していない**攻撃者は `/etc/crontab` から自分の設置パスを消し、 SLAPSHOT は10分の無通信で自分の痕跡を消す。** 装置上に残るものは消されうるため、**装置の外に出ていたものだけが残る。** 悪用は少なくとも9月上旬から続いており、遡れる保存期間が必要になる。
運用・監視□ 境界装置の主要バイナリの権限・`httpd.conf`・crontab の平時の状態を 記録していない本件の痕跡は**差分で見つかる**もの（`/bin/sh` の setuid・ `httpd.conf` への `AddHandler` / `AliasMatch` の追加）である。 平時の状態を持っていない組織は、**いまの状態が正常かどうかを比較できない。**
認証・認可□ Citrix Virtual Apps and Desktops を NetScaler Gateway の背後で運用しており、 StoreFront / Delivery Controller のイベントログを集めていない本件では**少なくとも1件で資格情報の窃取が起きている。** Mandiant は下流の Citrix 基盤で想定外の対話ログオン・予期しない RDP・ 資格情報ダンプの痕跡を調べるよう求めている。 **装置の中で検知できなくても、その先で検知する機会は残っている。**
委託・第三者部品□ 境界装置の運用を外部に委ねており、IoC 照合の実施と報告が契約に無い本件の IoC は NetScaler Console 経由でのみ提供される。 委託先が照合したかどうかを、委託元は自分では確認できない。
