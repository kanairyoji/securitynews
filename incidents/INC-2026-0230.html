2026年8月11日に修正された SharePoint Server の CVE-2026-65660 が、研究者が技術詳細を公開した2日後の9月24日から悪用され始めた——Microsoft は9月25日に「観測された攻撃の確かな証拠を得た」と改訂し、CISA は同日 KEV へ収載して9月28日を期限に切った。ところが同じ Microsoft の助言は、機械可読の欄では悪用状況を「No」、悪用可能性の評価を「可能性は低い」、CVSS の時間的指標を「未実証」のまま据え置いている。さらに本 CVE は当初「なりすまし・CVSS 6.5」に分類され、8月27日の改訂で遠隔コード実行へ変わったが、その改訂は「情報の変更のみ」と記録された。SafeControls の型チェックを Register 指令の引用符の未エスケープで迂回する欠陥で、認証済みの低権限で足り、匿名アクセスを許す構成では既知の認証バイパスと連鎖して未認証の遠隔コード実行に届く

欠陥の形はこうです。SharePoint には、危険なサーバ側クラスの読み込みを止めるSafeControls という仕組みがあります。ところが ToolPane が Web パーツのマークアップから Register 指令を組み直すとき、属性値を二重引用符で囲みながら、値の中の引用符をエスケープしません。攻撃者はこの隙間から指令を追加で差し込み、型チェックが走った後・コントロールが読み込まれる前に任意の .NET クラスを登録できます。そこから XamlServices.Parse() を経て、直列化データの復元でコードが実行されます。

Microsoft の分類では認証済み・低権限で足り、利用者の操作は不要です。研究者は、既に修正済みの別の認証バイパスと連鎖させれば、匿名アクセスを許す構成のサーバで未認証の遠隔コード実行に届くことも示しています。

そして本記録が最も重いと考えるのは、Microsoft の助言の中の不整合です。本記録の作成者が MSRC の API から取得した同一の応答の中で、

  • 改訂履歴（v1.2・9月25日）: 「2026年9月25日時点で、Microsoft は本脆弱性の悪用に対する観測された攻撃の確かな証拠を得た」（原文英語）
  • しかし exploited の欄: No
  • 悪用可能性の評価: 「悪用の可能性は低い（Exploitation Less Likely）」
  • CVSS の時間的指標: E:U（Exploit Maturity が Unproven・未実証）

が同時に並んでいます。助言の機械可読データで脆弱性を自動トリアージしている組織は、悪用が認められた後も、本件を低優先度に置き続けることになります。

日本の組織が被害に遭ったという公表はありません。それでも本記録が扱うのは、国内のオンプレミス SharePoint が「認証済みの利用者が多数いる」前提で構成されているのが普通であり、「認証が要る」は緩和要因として弱いという点、そしてベンダーの分類を優先度の根拠にしてよいのかという問いが、そのまま自組織の脆弱性管理の設計に跳ね返るからです。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

オンプレミス SharePoint Server の ToolPane が Web パーツのマークアップから Register 指令を組み直す際、属性値の中の引用符をエスケープしないため、 SafeControls の型チェックを通過した後に任意の .NET クラスを登録できる（CVE-2026-65660）。 そこから `XamlServices.Parse()` を経て直列化データの復元でコードを実行し、 web シェルを設置する。認証済み・低権限で成立し、 **匿名アクセスを許す構成では既に修正済みの認証バイパスと連鎖して未認証になる。** 実際に観測された試行は、二段構えの巨大な POST だった。

型チェックの後に、引用符の隙間からクラスを差し込む原因・手口出典 [4] [6]

SharePoint には SafeControls という仕組みがあります。ページや Web パーツのマークアップを解析するとき、信頼されていないサーバ側のクラスが実体化されるのを止めるための一覧です。

欠陥は、ToolPane がそのマークアップを処理するところにあります。ToolPane は、タグの接頭辞を ASP.NET のコントロールへ対応づけるRegister 指令を組み直します。そのとき、属性値を二重引用符で囲むのですが、値の中に含まれる引用符をエスケープしません。

攻撃者はこの未エスケープの引用符から指令を追加で差し込めます。差し込まれた指令が効くのは、型チェックが走った後・コントロールが読み込まれる前です。つまり、SafeControls の検査を通過した後に任意の .NET クラスを登録できます。

そこから先は、XamlServices.Parse() を呼ばせて、直列化データの復元（deserialization）でコードを実行させます。研究者が公開した連鎖には ExpandedWrapper の総称型・ObjectDataProvider・LosFormatter が含まれ、メモリ上で動く web シェル——他の復元手法がぶつかるレジストリ権限の問題を回避するもの——が実物として示されています。

Microsoft の分類では、認証済みで低権限の利用者で足り、利用者の操作は不要です。助言の FAQ は「影響を受けるサーバに低いレベルのアクセスを持つ認証済みの攻撃者が、特別に細工した要求を送ってサーバ上でコードを実行しうる。利用者の操作は不要である」（原文英語）と述べています。

そして連鎖があります。研究者は、既に修正済みの ToolPane の認証バイパスと組み合わせれば、匿名アクセスを許す構成のサーバで未認証の遠隔コード実行に届くことを示しました。認証バイパス側は6月9日の修正で塞がれているため、その修正を当てたサーバはこの経路にさらされません。

カナダ CCCS も同じ点を独立に述べています——「他の SharePoint の脆弱性と連鎖させると、匿名アクセスを許す構成のSharePoint サーバで未認証の遠隔コード実行が成立しうる。したがって、過去の SharePoint のセキュリティ更新を完全に適用していない組織は、侵害の危険が高まりうる」（原文英語）。

「認証が要る」は緩和要因として弱いということです。国内のオンプレミス SharePoint は、たいてい従業員全員が認証済みの利用者です。そして過去の更新の取りこぼしが1つあれば、認証さえ不要になります。

実際に飛んできた要求は、二段構えの 500KB 級の POST だった発覚の端緒出典 [3] [4] [6]

悪用の具体的な形が分かっているのは、Previdian の観測のおかげです。

2026年9月24日の約12:00 UTC、同社の SharePoint ハニーポット1台に対し、単一の送信元から6つのパスへ12件の POST が届きました。

  • 一段目: 本体 7,834 バイト。payload の解析ではActivitySurrogateDisableTypeCheck のガジェットと識別された
  • 二段目: 本体 535,404 バイト。各パスで一段目の直後に続き、AxHost+State と ActivitySurrogateSelector+ObjectSurrogate を用いるActivitySurrogate のガジェットを含む
  • 作成されようとした web シェル: /_layouts/15/sphealth.aspx

Previdian は、観測された payload がViettel の研究に記された SafeControls の引用符注入の手法と一致するとしつつ、一段目の包み方に意味のある差があると述べています。つまり、公開された markup をそのまま流しているのではなく、手を入れた誰かが使っているということです。

同社は範囲についても明確です——「これは2つの異なる脆弱性の連鎖の試みを捉えたものである。実行者を特定するものでも、暗号化された最終 payload を明らかにするものでも、他所での侵害を示すものでもない」（原文英語）。

本記録は、観測された送信元の IP アドレスを転記しません。悪性を検証しておらず、照合先のテレメトリも持たないためです。利用組織が見るべきは、要求の形（二段構えの巨大な POST）と作成されようとしたファイルのパスのほうです。

検知の手がかりとして使えるものを整理します。

  • _layouts 配下に、製品同梱でない .aspx が増えていないか（観測された例は sphealth.aspx という、いかにも正規に見える名前だった）
  • ToolPane 関連のパスに対する 500KB 級の POST
  • 直列化データの復元の失敗・例外（SharePoint / .NET のログ）
  • IIS の machine key への不審なアクセス（カナダ CCCS が挙げる観点）
  • AMSI の検知。カナダ CCCS は SharePoint の Web アプリケーションでAMSI の統合を有効にし、要求本文スキャンを全文モードにすることを推奨している（巨大な POST の本体を検査させるには、この設定が要る）

ただし限界もあります。研究者が示した メモリ上で動く web シェルはファイルを残しません。.aspx の増加を条件にした検知は、その経路を取り逃がします。

これが実務で何を意味するか。脆弱性管理を自動化している組織の多くは、後者を読んでいます。ベンダーの API やフィードから「悪用済みか」「悪用可能性の評価」を取り込んで優先度を付ける仕組みでは、本件は悪用が認められた後も低優先度に留まります。改訂履歴の自由記述まで読み取る実装は稀です。

もうひとつ、分類の変更の記録のされ方があります。本 CVE は当初「なりすまし・CVSS 6.5」として提示されました（報道による）。8月27日の v1.1 で名称と影響が遠隔コード実行へ変わりましたが、その改訂は「これは情報の変更のみである」と記録されています。助言には旧名称の記事と新名称の記事が両方残っています。

「情報の変更のみ」は、再評価を促さない言葉です。8月11日に「なりすまし・6.5」でトリアージを終えた組織が、8月27日の改訂で優先度を見直す動機は生まれません。しかし実際に変わったのは、影響そのものでした。

ここから引き出せる論点を3つ挙げます。

1. ベンダーの分類を、優先度の唯一の根拠にしない。本件では、CVSS 6.5 のなりすましが CVSS 8.8 の遠隔コード実行に変わり、44日後に悪用されました。分類が変わったことを掴む仕組みが要ります。現実的なのは、自社に影響のある製品の助言を「改訂日」で監視することです。内容の差分を読むのは重いので、改訂があった CVE を再トリアージの待ち行列に入れる運用で足ります。

2. 「認証済み」を緩和要因として扱う運用を見直す。オンプレミス SharePoint で「低権限の認証済み利用者」は、たいてい従業員全員です。さらに過去の更新の取りこぼしが1つあれば、認証すら要らなくなります。「PR:L（低権限が必要）」を減点材料として使うなら、その低権限を持つ人数を数えてからにするべきです。

3. 研究者の公開と悪用の間隔は、もはや「数日」を前提にする。本件は2日でした。同じ研究者の CVE-2026-55040 も、詳細が公開された直後に悪用されたと報じられています。修正の公開日ではなく、技術詳細が公開された日が実質的な期限です。この間隔を縮める方法は防御側にありません。できるのは、修正から詳細公開までの期間（本件では6週間）を使い切らないことだけです。

最後に、サポート終了の話を1つ。SharePoint Server 2016 と 2019 は2026年7月15日にサポート終了しており、本件の修正はその後に提供されました。これは「終了後も守られる」証拠ではなく、次は無いかもしれないという警告です。加えて研究者は SharePoint 2013 も影響を受けると述べています。2013 は2023年4月にサポートが終わっており、修正は出ません。 「助言に載っていない」ことは「影響を受けない」ことではありません。

システム構成□ SharePoint に匿名アクセスを許すページがある匿名アクセスを許す構成では、既に修正済みの ToolPane の認証バイパスと 連鎖することで未認証の遠隔コード実行が成立しうる。 過去の更新を完全に適用していない組織は危険が高まる。
認証・認可□ 低権限の認証済み利用者が事実上「全従業員」である「認証が要る」という緩和要因が実質的に機能しない。 CVSS の PR:L を減点材料として使っている運用は、本件で優先度を誤る。
