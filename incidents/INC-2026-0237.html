INC-2026-0237タイムズカーから660万件・免許証画像も

カーシェアリング「タイムズカー」の Web システムが不正アクセスを受け、約660万件のアカウント情報が第三者に取得されたことが確認された——検知は2026年9月25日9時07分、遮断の完了は翌26日7時25分で、公表は検知と同日（第1報）、取得の確認は3日後（第2報）である。漏えいした項目には氏名・住所・生年月日・電話番号・メールアドレスに加えて**運転免許情報と本人確認書類の情報（運転免許証・学生証などの画像）**が含まれ、退会済みの会員と「入会を申し込んだが入会が完了していない者」も対象に入った。**連携サービスIDは計9件**で、JR西日本グループの WESTER ID がその1つであるため、JR西日本も同日に自社利用者向けの告知を出している。侵入経路・手口、660万件の内訳、免許証画像の件数、パスワードのハッシュ方式、残る8件の連携サービス名はいずれも公表されていない

不正アクセス・侵害続報が続いている日本の組織が当事者公表されていない／不明
初報: 2026年9月25日 最終更新: 2026年9月28日

タイムズモビリティ株式会社と親会社のパーク24株式会社は2026年9月28日、カーシェアリングサービス「タイムズカー」の Web システムが不正アクセスを受け、約660万件のアカウント情報が第三者に取得されたことを確認したと公表しました（第2報）。

経緯は短く、そして速い。

  • 9月25日 9時07分 — タイムズカー Web システムに対する外部からの不正アクセスを検知
  • 9月25日 — 第1報を公表（「個人情報漏えいの可能性について」）。この時点では「不特定多数に公開された事実」「不正利用された事実」はいずれも確認されていないとした
  • 9月25日 — 西日本旅客鉄道が、タイムズカーに WESTER ID を登録している利用者向けの告知を公表
  • 9月26日 7時25分まで — 不正アクセス経路の遮断、攻撃元との通信の遮断、遮断後にアクセスできないことの確認を完了
  • 9月28日 — 第2報。外部専門機関の調査により、対象システムに保存されていた会員情報の一部が第三者に取得されたことを確認。件数は約660万件

「漏えいの可能性」から「取得の確認」まで3日です。この速さ自体は評価できますが、記録として重いのは中身のほうです。

漏えいした項目には、氏名・住所・生年月日・電話番号・メールアドレスに加えて、運転免許情報と本人確認書類の情報（運転免許証や学生証などの画像）が含まれます。カーシェアは入会時に免許証の画像を提出させる業態であり、その画像が保管されていて、保管されたまま漏れたという構図です。対象には退会済みの会員と、入会を申し込んだが何らかの事由で入会が完了していない者も入っています。

もう1つは連携サービスID が計9件含まれていた点です。両社が名前を挙げたのは JR西日本グループの会員サービス「WESTER ID」1件だけで、残る8件のサービス名は公表されていません。JR西日本は同日、自社システムへの不正アクセスは発生していないこと、WESTER のパスワードは自社が管理しており本件で流出するものではないことを明示し、あわせて他サービスとのパスワード使い回しの解消を呼びかけました。1社の侵害が、ID 連携を通じて他社の利用者への告知を必要とした事案です。

なお、侵入の経路・手口は公表されていません。660万件の内訳（現会員・退会済み・入会未完了・法人）も、免許証画像が何件含まれていたかも、パスワードがどの方式で保管されていたかも示されていません。

この時間の使い方は、国内の公表としては速い部類に入ります。検知と同日に第1報、翌朝までに遮断完了、3日後に取得の確認という順序で、いずれの段でも「分かっていること」と「分かっていないこと」を分けて書いています。

第1報の時点では「漏えいの可能性」でした。第2報でそれが「第三者に取得されたことを確認」に変わっています。この2つは意味が違います。 前者は外部から到達できた範囲の話で、後者は実際に持ち出された範囲の話です。本記録は第2報の約660万件を「流出の事実が確認された範囲」として扱います。

漏れたのは免許証の画像で、これはパスワードのように変更できない被害規模・影響範囲出典 [1] [3] [6]

第2報が挙げた漏えい項目は次の通りです。

  • 氏名、住所、生年月日、電話番号、メールアドレス
  • 法人会員の所属部署名
  • 運転免許情報
  • 本人確認書類の情報（運転免許証や学生証などの画像）
  • パスワード（復元できない形式で保管していると両社は説明）
  • 連携サービスID（計9件）

クレジットカード情報は漏えいしていないことを確認したと明記されています。

対象者の区分も広い。

  • タイムズカー会員および退会済みの会員
  • そのうち入会を申し込んだが、何らかの事由により入会が完了していない者
  • タイムズビジネスサービス会員および退会済みの会員

カーシェアは、入会時に運転免許証を撮影させて本人確認を行う業態です。確認のために受け取った画像が、確認のあとも保管されていたことが、この公表から読み取れます。退会済みの利用者と入会未完了の申込者が対象に含まれるのも同じ構図です。

免許証の画像は、パスワードと違って変更できません。番号は再発行しなければ変わらず、顔写真・住所・生年月日は一体で写っています。なりすましによる口座開設・携帯契約・他のシェアサービスへの入会に転用されうる資料が、無効化の手段を持たないまま外に出たことになります（本記録の評価）。

ただし、画像が含まれていたアカウントが何件だったかは公表されていません。660万件すべてに画像があったのか、一部だったのかは分かりません。

連携サービスID 9件のうち名前が出たのは1件で、JR西日本だけが自社の利用者に告知した波及・関係先出典 [1] [3] [4] [5]

第2報は、漏えいした連携サービスIDが「計9件」であるとしたうえで、具体名としては JR西日本グループの会員サービス「WESTER ID」の1件だけを挙げました。

JR西日本は第1報を受けた9月25日、WESTER ポータルで告知を出しています。内容は3点です。

  • タイムズカーに WESTER ID を登録している利用者について、漏えいの可能性がある情報に WESTER ID が含まれる可能性がある
  • JR西日本のシステムへの不正アクセスは発生していない

    本件は検知と同日に「漏えいの可能性」として第1報を出し、 その日のうちに JR西日本が自社利用者向けの告知を出した。 確定（第2報）を待っていれば、連携先の告知も3日遅れていた。
    取るべき行動 **「確定していないことを確定していないと書いて出す」第一報のひな型を用意し、 公表の判断基準（検知から何時間以内に出すか）を平時に決めておく。** あわせて、次にいつ何を公表するかの予定を第一報に書く運用にする。
  • 「復元できない形式で保管」だけでは、利用者は自分の判断材料を持てない
    両社はパスワードについて「復元できない形式で保管しており不正利用のおそれはない」と 説明したが、方式は示していない。一方 JR西日本は「他サービスと同じパスワードを 使っている場合は変更を」と呼びかけた。
    取るべき行動 **漏えい時の広報文では、認証情報の保管方式について言える範囲を具体的に書き、 同時に「使い回しがある場合は変更する」という利用者側の行動を必ず添える。** 大丈夫だと言い切る一文だけで済ませない。

  • 会員データと画像ストレージへの一括読み出しを、件数のしきい値で見る
    本件では約660万件が取得されている。 正常な業務で会員レコードと本人確認書類の画像が一括で読み出される場面は限られる。
    取るべき行動 **会員データベースと画像ストレージについて、 単位時間あたりの読み出し件数のしきい値を決めて監視し、 超過時に通報し、必要なら自動で絞る。** まず現状の正常値を測るところから始める。
  • 会員基盤からの外向き通信を既定で禁止にする
    持ち出しの手段・経路は公表されていない。 外向き通信が既定で許可されている構成では、持ち出しの段で止める手がかりが無い。
    取るべき行動 **会員データを保持する系からの外向き通信を既定で禁止し、 必要な宛先だけを明示的に許可する。** 通信量と宛先の記録を、 フォレンジックに足る期間（最低でも数か月）保全する。

    本件は「9月26日7時25分までに経路の遮断・攻撃元との通信の遮断・ 遮断後のアクセス不能確認を完了」と時刻を添えて公表した。 これは作業の記録が残っていなければ書けない。
    取るべき行動 **封じ込めの作業を実施時刻つきで記録する様式を用意し、 「遮断した」だけでなく「遮断後に到達できないことを確認した」までを1組にする。** 訓練のときから同じ様式で書く。
  • 退会・申込中断のデータに、消す仕組みを実装する
    規程で保持期間を決めても、削除が手作業なら残る。 本件の対象には退会済みと入会未完了が含まれていた。
    取るべき行動 **退会・申込中断から一定期間が過ぎたレコードと画像を、 バッチで自動削除する処理を実装し、削除の実行記録を残す。** 削除対象の件数を月次で出し、残高が増えていないかを見る。
  • 連携している外部 ID の一覧を、システム側から出せるようにする
    本件では連携サービスID が「計9件」と公表されたが、 利用者は自分がどれを連携していたかを思い出すしかない。
    取るべき行動 **利用者が自分の連携状況を画面で確認・解除できるようにし、 運用側も連携先ごとの対象件数を即座に出せるようにしておく。** 事故時の通知範囲の特定が、これで一段速くなる。
