Apple が2026年9月28日、CoreGraphics の境界外書き込み **CVE-2026-86950** を修正し「**iOS 27 より前の版で、特定の個人を狙った極めて高度な攻撃において悪用された可能性がある報告を承知している**」と認めた——報告したのは **Meta の製品セキュリティチーム**で、修正は iOS / iPadOS 26.7.1 と macOS Tahoe 26.7.1（報道では macOS Sequoia 15.8.1 も）に入った。CoreGraphics は 2D 描画と PDF の描画を OS 全体で担う部品のため、悪意ある「ファイル」の届き方は Web・メール添付・メッセージのプレビューなど多岐にわたりうるが、**Apple は届け方・標的・攻撃者・件数のいずれも公表していない。** CISA の KEV には本記録の確認時点（catalogVersion 2026.09.27）で収載が無い

読み方に注意が要る書き方です。Apple は「悪用された」と断定していません。「悪用された可能性がある」という「報告」を「承知している」という三重の留保です。本記録はこの表現をそのまま保存します。ただし、Apple がこの一文を添える更新は、実務上は「当てるまで待てない1件」として扱われてきました。

同じ日に公開された iOS 27.0.1・macOS Golden Gate 27.0.1・watchOS 27.0.1・visionOS 27.0.1 については、Apple のセキュリティリリース一覧に「この更新に公開された CVE エントリはありません」と記されています。つまり 27 系は本件の対象外という整理です。

CoreGraphics が対象である以上、「どこから来るファイルか」を絞れない原因・手口

CoreGraphics は、2D のベクタ描画・画像の描画・文字の描画・PDF の描画をOS 全体で担う基盤の部品です。アプリが独自に持っている機能ではなく、OS がファイルを「見せる」ときに通る場所にあります。

ここに境界外書き込みがあるということは、「ファイルを描画しようとした瞬間」が攻撃の成立点になりうるという意味です。そして Apple は、そのファイルがどう届くのかを公表していません。

SecurityWeek は、CoreGraphics の役割から次のように指摘しています（Apple の記述ではありません）。

CoreGraphics は OS 全体で 2D グラフィックスと PDF の描画を扱うため、Web ページ・メールの添付・メッセージアプリ経由で届きえ、添付やリンクの自動プレビューがゼロクリックの悪用を可能にしうる。（原文英語）

この「自動プレビュー」という点が、防御側にとっての要所です。利用者が何もタップしなくても、OS やアプリが受信物を先に描画してしまう経路があるならば、「怪しいものを開かない」という教育は効きません。

裏を返すと、Apple 自身が「狙い撃ちされる少数の個人」向けに用意しているロックダウンモードが、まさにこの経路を閉じる作りになっています。 Apple の説明では、ロックダウンモードはメッセージの添付の多く（特定の画像・動画・音声を除く）を遮断し、リンクのプレビューを無効にし、複雑な Web 技術を遮断します。ただし Apple は「ロックダウンモードが CVE-2026-86950 に効く」とは述べていません。本記録は、同じ型の攻撃経路に対する既存の機能として紹介します。

報告者が Meta の製品セキュリティであることが、前年と同じ並びを作っている発覚の端緒

Apple が謝辞に挙げているのは Meta Product Security です。OS の提供元ではなく、メッセージングを運ぶ側の企業のセキュリティチームがOS のゼロデイを見つけて報告した形です。

同じ並びは前年にもありました。2025年8月、WhatsApp は自社の iOS / macOS アプリの脆弱性 CVE-2025-55177 が Apple の ImageIO のゼロデイCVE-2025-43300 と組み合わせて、200人未満の利用者を狙ったゼロクリック攻撃に使われたとみられると公表しています。

本件が WhatsApp 経由だったかどうかは公表されていません。 SecurityWeek は Meta に確認を求めたと書いており、2026年9月29日時点で回答は公表されていません。報告者が誰かと、どのアプリが悪用されたかは別の問いです。混ぜて読むと、事実でないことを事実として持ってしまいます。

それでも、この並びには実務上の意味があります。狙い撃ち攻撃の最初の観測者は、OS の提供元ではなく「運び手」の側であることが多い——メッセージの配送基盤には、異常な受信物の痕跡が集まるためです。

KEV に入っていない——当局の期限は「危険の大きさ」ではない当局対応

本記録の作成者は2026年9月29日、CISA の KEV カタログ（catalogVersion 2026.09.27・全1,728件）を取得して確認しました。

  • CVE-2026-86950 の収載はありません。
  • 2026年に収載された Apple 製品の脆弱性は 8件です。
  • もっとも紛れやすいのが CVE-2026-20700（2026年2月12日収載・Apple Multiple Buffer Overflow・CWE-119・対処期限 2026年3月5日）で、これは本件とは別のものです。

KEV に入っていないことは、危険が小さいことを意味しません。 KEV は米連邦民間行政機関に期限つきの対処を義務づける仕組みであり、収載の有無は運用上の都合や情報の確度に左右されます。本件は、ベンダー自身が「悪用された可能性の報告を承知している」と書いた案件です。

国内側では、JVN のフィード（2026-09-29 14:35 JST 更新）とJPCERT/CC の注意喚起一覧に、本件の掲載を見つけられませんでした。「発出されていない」と確定したわけではなく、探して見つからなかったという意味です。国内の注意喚起を待つ運用では、この型の更新には間に合いません。

報道の CVE 番号が食い違っている——番号で管理している組織ほど危ない未確定事項

同じ脆弱性について、報道の CVE 番号が一致していません。

出典 記載された CVE
Apple（勧告 149226・149228） CVE-2026-86950

Apple 自身の勧告が CVE-2026-86950 である以上、こちらが正です。そして CVE-2026-20700 は2026年2月12日に KEV へ収載済みの別件であることを、本記録は KEV カタログの原本で確認しました。BleepingComputer の記事は、本件の説明と、2月に修正された dyld のゼロデイの説明の両方に同じ CVE-2026-20700 を当てており、記事内で整合していません。

実務への影響は小さくありません。脆弱性管理を CVE 番号で回している組織では、「2月に対処済み」という記録と突き合わせて「対応不要」と判断しうるためです。一次資料（ベンダーの勧告）で番号を確定させてから台帳に入れる、という順序が要ります。

日本の組織にとっての意味は「少数の端末を先に上げられるか」にある評価・解釈

本件は日本の組織が当事者として挙がった事案ではありません。それでも記録に値すると考えるのは、次の3点です（以下は本記録の評価です）。

1. 狙われるのは「組織」ではなく「人」である。 Apple の表現は「特定の標的とされた個人」です。組織の防御が厚いかどうかではなく、役員・広報・経営企画・研究者・記者と接する立場の人の端末が対象になります。端末が私物（BYOD）であれば、組織の更新管理の外にあります。

2. 更新管理が整っている組織ほど、1件だけの緊急更新が通りにくい。 MDM で OS 更新を段階的に配っている組織では、検証・段階配信・業務影響の確認に日数がかかります。平常時には正しい運用が、この型の更新では遅れの理由になります。「悪用が報告された1件だけの更新を、検証を飛ばして当てる」判断を誰が下せるのかを、事前に決めておく必要があります。

3. iOS 27 へ上げるという選択肢がある。 Apple の整理では 27 系は本件の対象外です。26 系に留まる方針の組織は、「留まる理由」と「留まる間に当てる更新」の両方を持っているかを点検する機会になります。

なお、本記録は IoC を持ちません。 Apple は公表しておらず、利用者が自分の端末を確認する公開の手がかりもありません。できるのは、当てることと、狙われうる少数の人の端末を先に上げることです。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Apple は、**悪用の可能性・部品・影響・対処・報告者・対象機種**を公表した一方で、 **届け方・標的・件数・時期・攻撃者・IoC を公表しなかった。** 勧告に載せた CVE は1件のみで、他の修正内容は併記していない部分的に機能**本記録の作成者の評価である。** 悪用の可能性を隠さず勧告に明記し、報告者を謝辞に挙げた点は評価できる。 1件だけの更新として切り出したことも、利用者が優先度を判断しやすい形である。 不十分なのは、**「この更新を急ぐべき利用者は誰か」の手がかりが無いこと**である。 「特定の標的とされた個人」という表現だけでは、 組織の管理者が**自組織の誰の端末を先に上げるべきか**を決められない。 属性を伏せたまま「狙い撃ちの対象になりうる職務の例」を示す余地はあったと考える
CISO・経営層への示唆
  • 「悪用が報告された1件だけの更新」を、通常の月次更新と別の扉で通す
    本件の更新に載っている CVE は1件だけで、ベンダー自身が 「極めて高度な攻撃で悪用された可能性がある報告を承知している」と書いている。 MDM で検証と段階配信をしている組織では、この1件も通常の列に並び、 検証と配信の日数がそのまま露出期間になる。
    取るべき行動 **「ベンダーが悪用に言及した更新」だけを通す速い経路を、平時に作っておく。** 決めるのは技術ではなく、**検証を省く判断を誰が下せるか・何時間以内に配るか・ 業務影響が出たときに誰が受けるか**である。 年1回、実際に緊急配信を通して所要時間を測る。
  • 狙われるのは組織ではなく人である——「その人の一覧」を持つ
    Apple の表現は「特定の標的とされた個人」であり、組織の防御の厚さと無関係に 個人が狙われる型である。役員・広報・経営企画・研究者・ 外部の記者や活動家と接する職務の端末が対象になりうる。 私物端末であれば、組織の更新管理の外にある。
    取るべき行動 **「狙い撃ちされうる職務」の一覧を作り、その人の端末が管理下にあるかを確認する。** 管理外（BYOD・私物）なら、更新の督促と連絡経路を人ベースで持つ。 一覧は人事異動のたびに見直す。**長さは10〜20人程度で足りることが多い。**
  • CVE 番号は一次資料で確定してから台帳に入れる
    本件では報道の CVE 番号が食い違い、片方（CVE-2026-20700）は 2026年2月に KEV へ収載済みの別件である。 番号で脆弱性管理を回していると、「2月に対処済み」という記録と突き合わせて 「対応不要」と誤判定しうる。
    取るべき行動 **脆弱性台帳への登録は、ベンダーの勧告か NVD を根拠として行う運用にする。** 報道を起点にしてよいが、**番号の出所を台帳に残す。** すでに登録済みの番号と一致したときは、**同一かどうかを勧告の本文で確認する。**
  • KEV に無いことを「待ってよい」の根拠にしない
    本記録の確認時点で CVE-2026-86950 は KEV に収載されていない。 KEV は米連邦機関に期限を課す仕組みであり、収載の有無は 危険の大きさをそのまま表すものではない。国内の注意喚起も確認できていない。
    取るべき行動 **社内の優先度判定で「KEV 収載」を唯一の引き金にしていないかを点検する。** 「ベンダーが悪用に言及した」「境界に面している」「標的型の観測がある」を 独立した引き金として持つ。
セキュリティ技術者への示唆
  • 今日、26 系に留まっている端末の台数と持ち主を数える
    Apple の整理では iOS 27 系は本件の対象外で、悪用が報告されたのは 「iOS 27 より前の版」である。26 系に留まる方針の組織は、 留まる間に出る緊急更新を当て続ける前提に立っている。
    取るべき行動 MDM の在庫から **OS の版ごとの台数**を出し、 26.7.1 未満の端末と持ち主を一覧にする。 **対象機種（iPhone 11 以降、iPad Pro 12.9 インチ第3世代以降ほか）に 入らない古い端末は、そもそも更新が来ない**ため別枠で扱う。
  • 「開かせる攻撃」ではなく「描画させる攻撃」として緩和を考える
    CoreGraphics は OS がファイルを見せるときに通る部品である。 添付やリンクの自動プレビューが効く経路では、 利用者が何もしなくても描画が始まりうる（SecurityWeek の指摘）。 「怪しいものを開かない」という教育はこの型に効かない。
    取るべき行動 狙われうる少数の端末について、**メッセージの添付とリンクのプレビューを 遮断する設定**（Apple のロックダウンモードはこれを含む）の適用可否を検討する。 **ただしロックダウンモードは構成プロファイルの新規インストールと MDM 登録を遮断するため、先に登録を済ませた端末で検証する。** **本件に効くとは Apple が述べていない**ことを前提に、費用対効果で判断する。
  • iOS の端末では「踏まれたか」を自力で判定しない前提を置く
    Apple は IoC を公表しておらず、個人の端末には詳細なログが残らない。 EDR で iOS を観測できる範囲も限られる。 自力の解析に時間を使うと、端末を専門機関へ渡す機会を失う。
    取るべき行動 **狙い撃ちの疑いが生じたときの手順を1枚にする**—— 端末の使用を止める、機内モードにする、初期化しない、 バックアップを取る、相談先（人権団体のセキュリティラボ・ フォレンジック事業者・所轄の窓口）を決めておく。 **「初期化して様子を見る」は証拠を消す。**
  • 26 系と 27 系が混在する前提で、更新の通知先を分ける
    同じ日に 27 系の更新（CVE の掲載なし）と 26 系の更新（悪用の言及あり）が出た。 一律の「更新してください」では、急ぐべき人に急ぐ理由が届かない。
    取るべき行動 配信と通知を**版ごとに分ける**。26 系には「悪用が報告された1件の修正である」 という理由を添え、27 系には通常の更新として案内する。 **理由を書かない通知は後回しにされる。**
