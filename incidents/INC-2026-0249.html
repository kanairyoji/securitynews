INC-2026-0249MCP 公式 SDK で OAuth 資格情報漏えい

MCP 公式の Python SDK（`mcp`）に、**接続先の MCP サーバが「クライアントの OAuth 資格情報をどこへ送るか」を決められる**欠陥が公表された（GHSA-qx49-fqc8-xw99・CVSS 3.1 で 7.5・**CVE は未付与**）——悪性サーバが探索要求に 404 を返すと SDK が旧方式へ退避し、**issuer の検証が走らない経路**に入る。クライアントは client secret・認可コード・PKCE の検証鍵を攻撃者のトークン端点へ送り、攻撃者はそれを本物の認可サーバへ渡して**アプリに付与されていた権限そのままのアクセストークンを得る**（Cycode が端から端まで実証）。修正は 1.30.0 / 2.2.0 だが、**機械対機械の2つのプロバイダでは `issuer=` を渡すまで挙動は変わらない**。悪用の報告は無い

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年9月28日 最終更新: 2026年9月29日

2026年9月28日、MCP（Model Context Protocol）公式の Python SDK（PyPI のパッケージ名 mcp）に、OAuth の資格情報が第三者へ渡りうる欠陥の勧告 GHSA-qx49-fqc8-xw99 が公開されました。

勧告の要約は1文です。

SDK の OAuth クライアント機能は、クライアントが接続した MCP サーバに、そのクライアントの OAuth 資格情報がどこへ送られるかを決めさせていた。（原文英語）

成立の筋は次のとおりです。悪性の MCP サーバが探索要求に 404 を返すと、SDK は旧方式へ退避します。その経路では検証すべき URL が空になるため、issuer の検証が走りません。攻撃者は「本物のログイン先である」と偽って名乗るメタデータを返し、クライアントはclient secret・認可コード・PKCE の検証鍵を攻撃者のトークン端点へ送ります。攻撃者はそれを本物の認可サーバへ渡し、アプリに付与されていた権限そのままのアクセストークンを得ます。 Cycode はこの一連を、PKCE を強制する本物の認可サーバに対して端から端まで実証したとしています。

この記録が扱う要点は3つです。

  • 利用者から見て、異常が何も見えません。 承認画面は本物のログイン画面です。Cycode の言い方では「見えるのは完全に普通のログイン画面と、そのあと MCP サーバの接続が失敗したように見えることだけ」です。

  • client secret は長期有効です。 一度渡れば、変更するまで使われ続けます。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

悪性の MCP サーバが探索要求に 404 を返してクライアントを旧方式へ退避させ、 **issuer の検証が走らない経路**で偽の認可サーバ設定を渡す。 クライアントは client secret・認可コード・PKCE の検証鍵を攻撃者のトークン端点へ送り、 攻撃者はそれを本物の認可サーバへ渡して**アプリの権限そのままのアクセストークン**を得る。 **Cycode が実験環境で端から端まで実証した経路であり、現実の攻撃の報告は無い。**

  1. 1. 初期侵入公表・報道に基づく[2]
    クライアントが**攻撃者の管理する MCP サーバへ接続する。** 入口は名簿・カタログの汚染（正規サーバに似た名前での登録）か、 エージェントを誘導するプロンプトインジェクション。 **この段階では OAuth はまだ始まっていない**
    根拠: Cycode の解説記事（攻撃の前提条件として提示）
  2. 2. 検知回避確認済[1] [2]
    悪性サーバが**探索要求に 404 を返す。** SDK は旧方式へ退避し、**検証対象の URL が空になるため `issuer` の検証が走らない。** 「URL が得られていたら検証する」という条件つきの検査が、 **条件を満たさない経路を作られることで無効化される**
    根拠: Cycode の解説記事と勧告の記述（issuer がすべての探索経路で検証されていない）
  3. 3. 認証情報アクセス確認済[1] [2]
    クライアントが **client secret・認可コード・PKCE の検証鍵** （`PrivateKeyJWTOAuthProvider` では署名済みアサーション）を **攻撃者のトークン端点へ送る。** 対話型プロバイダでも、**利用者が承認するのは本物のログイン画面**であるため、 見た目に異常が無い
    根拠: 勧告の記述と Cycode の実証
  4. 4. 影響（暗号化・破壊・改ざん）確認済[1] [2]
    攻撃者が盗んだ資格情報を**本物の認可サーバへ渡し、正規のアクセストークンを得る。** Cycode は**ユーザー情報の端点を呼んで乗っ取りを確認した**としている。 **トークンには元のアプリに付与されていた権限がそのまま乗る。** client secret は長期有効であるため、**変更するまで繰り返し発行できる**
    根拠: Cycode の実証（PKCE を強制する本物の認可サーバに対して端から端まで）

接続先のサーバが「資格情報の送り先」を決められた概観

MCP は、AI アプリケーションを外部のツールやデータへ繋ぐための公開仕様です。本件はその公式の Python SDK（PyPI のパッケージ名 mcp）の欠陥で、2026年9月28日に勧告 GHSA-qx49-fqc8-xw99 として公開されました。

勧告の要約は1文です。

SDK の OAuth クライアント機能は、クライアントが接続した MCP サーバに、そのクライアントの OAuth 資格情報がどこへ送られるかを決めさせていた。（原文英語）

勧告が挙げる不備は2つです（いずれも原文英語）。

  1. 認可サーバのメタデータの issuer が、すべての探索経路で検証されていなかった
  2. 保存済み・事前設定済みのクライアント資格情報が、それが属する認可サーバに結びつけられていなかった

対象となるプロバイダは4つで、人の介在が要るかどうかで採点が分かれます。

プロバイダ 人の介在 採点
OAuthClientProvider 要る（利用者がサインインを始める） 6.5
ClientCredentialsOAuthProvider 要らない 7.5
PrivateKeyJWTOAuthProvider 要らない 7.5

対象外も勧告が明記しています——SDK で MCP サーバ側を作っている実装、ローカル（stdio）のクライアント、自前で用意したトークンを付けて呼ぶクライアント。

404 を返すだけで検証が飛ぶ——「条件つきの検査」が抜け道になった原因・手口

Cycode の解説によれば、成立の筋はこうです。

  1. MCP クライアントはログインのため、接続先のサーバに「認可サーバ（ログイン先）はどこか」を尋ねます。
  2. 悪性のサーバがこの探索要求に 404 を返すと、SDK は旧方式へ退避します。
  3. 退避した経路では、検証すべき URL が空になります。issuer の検証は「手順1で URL が得られていたら、ログイン先の身元を確かめる」という条件つきだったため、空なら検査そのものが走りません。
  4. 攻撃者は「本物のログイン先である」と名乗る設定を返します。利用者に見えるのは本物のログイン画面です。
  5. SDK は client secret・認可コード・PKCE の検証鍵を、攻撃者のトークン端点へ送ります。

PKCE（Proof Key for Code Exchange）は、認可コードを盗まれても再利用させないための一度きりの値です。その検証鍵まで一緒に渡してしまうため、PKCE の保護も外れます。

Cycode はここまでを実証したうえで、次を確認したと述べています。

攻撃者は、盗んだコード・検証鍵・client secret を本物のログイン先のトークン端点に送り、正規のアクセストークンを受け取り、ユーザー情報の端点を呼んで乗っ取りを確認した。（原文英語）

得られるトークンには、元のアプリに付与されていた権限がそのまま乗ります。読み書き両方の権限、内部 API への権限、管理操作の権限を持つアプリであれば、攻撃者はそれをすべて引き継ぎます。そして client secret は長期有効です——変更するまで使われ続けます。

「条件つきの検査」という形は、本件に固有のものではありません。「値が取れていれば検証する」という書き方は、値が取れない経路を作られた時点で検証なしの経路になります。

上げただけでは直らない2つのプロバイダがある対策・注意喚起

対処は「1.30.0 または 2.2.0 以降へ上げる」ですが、それで終わらない部分があります。

①機械対機械の2つのプロバイダは、issuer= を渡すまで挙動が変わりません。勧告は ClientCredentialsOAuthProvider と PrivateKeyJWTOAuthProvider について、「issuer= を渡すまで、上げても何も変わらない」という趣旨を明記し、issuer= の指定は 3.0 で必須になると予告しています。The Hacker News はさらに、1.30.0 でのこの警告が Python が既定で隠す非推奨警告として出るため見落としやすいと指摘しています。

②非推奨の RFC7523OAuthClientProvider には issuer= の選択肢がありません。他のプロバイダへ移す必要があります。

③保存済みの OAuth クライアント登録を一度消す必要があります。勧告は「クライアントが再登録されるよう、保存済みの OAuth クライアント情報を一度消すこと」（原文英語）を求めています。古い登録は認可サーバに結びつけられておらず、そのままでは結びつかないためです。

④信頼できないサーバへ接続した可能性があるなら、回します。「そのようなクライアントが信頼できない MCP サーバへ接続した可能性がある場合は、client secret を変更し、認可サーバでトークンを失効させること」（原文英語）。

⑤古い版に回避策はありません。 The Hacker News は「古い版では、信頼できる MCP サーバにのみ接続する以外の回避策は無い」と書いています。

対処の順序を1行にすると、「上げる → issuer= を渡す → 保存済み登録を消す →疑いがあれば secret を回す」です。最初の1つで止めると直りません。

入口は「どの MCP サーバに繋ぐか」——名簿の汚染とプロンプトインジェクション評価・解釈

本件が成立するには、クライアントが攻撃者の MCP サーバに接続する必要があります。Cycode は現実的な入口として2つを挙げています。

  • 名簿・カタログの汚染。 MCP サーバの一覧サイトやレジストリに、正規のサーバと紛らわしい名前（タイポスクワッティング）で登録する。
  • プロンプトインジェクション。 AI エージェントに悪性のサーバを選ばせるよう誘導する。

ここが本件の性格を決めています。従来の脆弱性は「自分の資産に穴がある」ことでしたが、本件は「自分の資産が、どこへ繋ぐかを自分で決めていない」ことが危険の源です。エージェントにツールを選ばせる設計では、接続先の選定が実行時に、人の確認なしで行われます。

Cycode は「人の介在が要る」という条件が危険を過小に見せていると述べています—— ①利用者は正規のログイン画面をためらわずに承認する、②AI エージェントは侵害されたサーバを自動で選びうる、③DNS の乗っ取りや内部ネットワークの侵害があれば人の介在そのものが消える。

以下は本記録の評価です。 日本の組織にとっての意味は、「MCP を使っているか」ではなく 「接続先の名簿を誰が管理しているか」にあります。社内でエージェントを組んでいる部署が、公開の一覧から MCP サーバを選んで繋いでいるなら、その一覧が実質的に「許可された接続先の台帳」として機能してしまっています。

修正は21日早く出ていたが、「セキュリティ修正」とは書かれていなかった未確定事項

The Hacker News によれば、issuer の検証は 2026年9月7日に 1.30.0 と 2.2.0 のリリースノートへ載っており、セキュリティ修正ではなく「挙動の変更」の項目として記載されていたとされます。勧告が出たのは9月28日、21日後です（この日付は報道に依拠しており、本記録はリリースノートの原文を確認していません）。

この21日間に何が起きるかを考えると、実務上の含みがあります。

  • 依存の自動更新を入れている組織は、気づかないうちに直っていた可能性があります。
  • 一方、「セキュリティ修正が出たら上げる」という運用の組織は、上げる理由が21日間存在しませんでした。
  • そして機械対機械のプロバイダを使っている実装は、上げていても issuer= を渡していない限り直っていません。

CVE が付いていないことも、同じ問題の別の面です。CVE 番号を鍵にして脆弱性管理を回している仕組みでは、本件は入口に現れません。 GHSA の識別子、あるいはパッケージ名と版の範囲で拾う仕組みが必要です。

  • CVE が付かない脆弱性を拾う経路を、今のうちに用意する
    本件は2026年9月29日時点で CVE が付いていない。 AI エージェントの基盤ライブラリでは、GHSA だけで公表される事案が起きている。 CVE 番号を鍵に回している台帳・SBOM の照合・調達時の確認には現れない。
    取るべき行動 **パッケージ名と版の範囲で拾う仕組み（依存関係の警告・SCA）を、 CVE ベースの仕組みと並列に持つ。** どちらか一方しか無い組織は、**どちらの穴に落ちるかを把握しておく。** 新しい基盤（MCP・エージェント framework）は、 **公式リポジトリの勧告一覧を人が定期的に見る**運用で補う。
  • 「どの MCP サーバへ繋ぐか」を、実行時の判断から運用の判断へ引き上げる
    本件の前提は「攻撃者のサーバに接続する」ことである。 Cycode は入口として名簿の汚染とプロンプトインジェクションを挙げている。 エージェントに接続先を自律的に選ばせる設計では、 **接続先の選定が人の確認を経ずに実行時に決まる。**
    取るべき行動 **社内で使う MCP サーバの許可一覧を作り、それ以外への接続を止める。** 一覧に載せる条件（提供元・運用者・更新の追い方）を決め、 **追加は申請制にする。** 公開のカタログをそのまま接続先の根拠にしない。
  • エージェントに渡している OAuth の権限を棚卸しする
    攻撃者が得るトークンには、元のアプリに付与されていた権限がそのまま乗る。 読み書き両方・内部 API・管理操作の権限を持つアプリであれば、 乗っ取りの被害範囲はそのまま広がる。
    取るべき行動 **エージェントや MCP クライアントに与えている OAuth のスコープを一覧にし、 「読み取りで足りるもの」を読み取りに落とす。** 管理操作の権限を持つ実装は、**接続先を固定したものだけに限る。** 一覧の権限の広さが、そのまま本件の被害想定になる。
セキュリティ技術者への示唆
  • 今日、`mcp` の版と使っているプロバイダを突き合わせる
    該否は版だけでは決まらない。 「HTTP 経由のクライアントである」「対象4プロバイダのいずれかを使っている」 「自分が完全に管理していないサーバへ接続しうる」の3つが揃って該当する。
    取るべき行動 依存の一覧から `mcp` の版を出し（1.9.1〜1.29.1 / 2.0.0a1〜2.1.1 が対象）、 コードを `OAuthClientProvider`・`ClientCredentialsOAuthProvider`・ `PrivateKeyJWTOAuthProvider`・`RFC7523OAuthClientProvider` で検索する。 **`RFC7523OAuthClientProvider` が出たら、移行が必要な実装である。** **MCP サーバ側の実装と stdio のクライアントは対象外**なので、先に除外して数を絞る。
  • 上げたあと、`issuer=` を渡したことをテストで固定する
    `issuer=` を渡していない場合の警告は、Python が既定で隠す非推奨警告として出る。 人のレビューでは見落とすし、次に誰かが書くコードで同じ抜けが再発する。
    取るべき行動 **機械対機械のプロバイダを生成する箇所で `issuer` が必須であることを、 単体テストか型・設定の検査で固定する。** あわせて `python -W error::DeprecationWarning` などで **非推奨警告を落ちる設定にして CI を回す**——本件のような 「警告として出るだけの重要な変更」を拾える。
  • 保存済みの OAuth クライアント登録を消し、無人の実装の再登録を検証する
    古い登録は認可サーバに結びつけられていないため、消して再登録させる必要がある。 しかし無人で動くバッチやエージェントでは、 **再登録の失敗がそのまま業務停止になる。**
    取るべき行動 **保存済み登録の削除は、検証環境で再登録まで通してから本番に入れる。** 再登録に人の操作が要る実装を先に洗い出し、 **作業の順序（止める→消す→再登録→動作確認）を書いておく。**
  • 「どのサーバへ繋いだか」をアプリのログに残す
    攻撃が成立したとき、クライアント側に見えるのは 「普通のログイン画面」と「接続が失敗した」ように見える結果だけである。 接続先の記録が無ければ、後から疑う起点すら作れない。
    取るべき行動 MCP サーバへの接続について、**URL・時刻・使ったプロバイダ・ 取得したトークンの識別子（値は残さない）をログに出す。** 認可サーバ側のトークン発行ログと突き合わせられる形にする。 **値そのものは書かない**——ログが次の漏えい元になる。
  • client secret を「長期有効な共有秘密」のまま置かない
    勧告も Cycode も、client secret が長期有効であることを危険の中心に挙げている。 一度渡れば、変更するまで攻撃者はトークンを発行し続けられる。
    取るべき行動 **secret の定期的な変更手順を、止めずにできる形（新旧併存の期間を設ける）で用意する。** 可能なら**共有秘密から短命の資格情報（ワークロード ID・ 署名鍵の自動交代）へ寄せる。** 少なくとも「いま使っている secret がいつ作られたか」を把握する。
