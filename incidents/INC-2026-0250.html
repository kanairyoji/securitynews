INC-2026-0250ChatGPT の偽 Custom GPT で RAT

Huntress が2026年9月28日、**ChatGPT の正規機能「Custom GPT」を入口にした ClickFix 攻撃**を公表した——Google 検索の「chatgpt」に出る**広告枠**から chatgpt.com 上の偽の「Plus 5.6」へ誘導し、そこで返る1通のメッセージが「予備のドメイン」として Google Sites のページへ導く。Cloudflare を模した確認画面で端末に PowerShell を貼らせ、**Canon の署名済みアプリに悪性 DLL をサイドロード**させて、`.wav` に埋めたローダから RAT を展開する。Huntress の SOC は当該 Google Sites ドメイン起点で**40件以上**の事案に対応し、うち2件は Custom GPT 経由と確認した。OpenAI は9月25日までに当該 Custom GPT を削除したが、**9月27日に同じキャンペーンの別の Custom GPT が見つかっている**。RAT の C2 は **DNS over HTTPS** で解決するため**社内 DNS のログに現れない**

脅威・攻撃キャンペーン続報が続いている有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）
初報: 2026年9月28日 最終更新: 2026年9月29日

Huntress は 2026年9月28日、ChatGPT の正規機能「Custom GPT」を入口にしたClickFix 攻撃の分析を公表しました。

Custom GPT は、利用者が用途に合わせて自分用の ChatGPT を作れる機能です。作られたものは chatgpt.com 上のページとして存在し、上部に名前、その下に作成者のプロフィールが表示されます。

攻撃の入口は、次の順序です。

  1. 利用者が Google で 「chatgpt」 を検索する
  2. 広告枠（sponsored）の結果が、chatgpt.com 上の Custom GPT へ導く（URL には Google 広告のクリック追跡パラメータが付いている）
  3. その Custom GPT は 「Plus 5.6」という名前で、新しいモデルのように見える（作成者欄には "community builder" と出る）
  4. 何を入力しても返るのは1通だけ——「サービス提供状況のお知らせ」として「主ドメインで提供が制限されている」とし、Plus への課金か「予備のドメイン」の利用を促す
  5. その「予備のドメイン」は Google Sites 上のページで、Cloudflare 風の CAPTCHA 確認画面を表示し、端末のターミナルにコマンドを貼らせる（ClickFix）

ここから先は、8段の連鎖です。Canon の署名済みアプリを土台に改変した Canon のログ用 DLL を読み込ませ、.wav ファイルに埋め込んだローダを経て、独自の暗号化ファイルシステム（monitor.raw）から RAT を取り出します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

Google 検索の広告枠から chatgpt.com 上の偽 Custom GPT へ誘導し、 そこで返る固定応答が Google Sites の ClickFix ページへ導く。 利用者が貼った PowerShell を起点に、8段の連鎖で **署名済みの Canon（第2版は Stardock）アプリへの DLL サイドロード**、 **`.wav`（第2版は NuGet パッケージ）に埋めたローダ**、 **独自の暗号化ファイルシステムからの RAT 展開**に至る。 **C2 の名前解決は DNS over HTTPS で行われ、社内 DNS のログに現れない。**

  1. 1. 初期侵入確認済[1]
    利用者が Google で「chatgpt」を検索し、**広告枠**の結果から chatgpt.com 上の偽 Custom GPT「Plus 5.6」に到達する。 URL には Google 広告のクリック追跡パラメータが付いており、 **攻撃者が広告費を払って最上位に出していた**ことが分かる。 Custom GPT は何を入力しても同じ「サービス提供状況のお知らせ」を返し、 **「予備のドメイン」として Google Sites のページへ導く。** そこで **Cloudflare 風の CAPTCHA 画面**が、 端末のターミナルへコマンドを貼るよう指示する（ClickFix）
    根拠: Huntress の分析（事案の調査と当該 Custom GPT の画面・URL の確認）
  2. 2. 実行確認済[1]
    利用者が貼ったコマンドで **PowerShell がスクリプトを取得して実行する。** 取得先のホストは**10進数の数値**で書かれており、 「点で区切られた IP アドレス」を探す検知や URL フィルタには見えない。 取得されるスクリプトは**1行27,581文字・整数配列による二重の難読化**で、 復号後のコードは**ディスクに書かれない。** 最終的に MSI を**無音でインストール**する （`ARPSYSTEMCOMPONENT=1` で「プログラムと機能」から隠れ、 **インストール完了と同時に実行**される。ファイル名は毎回新しい GUID）
    根拠: Huntress の解析（各層を復号して再実装した結果）
  3. 3. 検知回避確認済[1]
    **署名済みの正規アプリを土台にする。** 第1版は **Canon の CaptureOnTouch の署名済み実行ファイル**（署名は有効）が 自分のフォルダから **Canon のログ用 DLL** を読み込む挙動を利用する。 置かれているのは**署名が外れ、チェックサムも合わない改変版**で、 違いは**輸入表に1項目多いこと**だけ。 Windows はライブラリのコードより先にその項目を読み込む。 ローダは **`.wav` ファイルの中**（本物の録音の一部を暗号文で上書き）にあり、 取り出されるのは**文字列が1つも読めない位置独立の機械語**である。 確認された機能は **AMSI の無効化・.NET ランタイムのホスティング （ディスクに置かずに実行）・`ntdll` の再読み込みによる EDR のフックの回避・ 仮想環境の検出・偽の「LOADING...」画面。** 第2版では**ローダを Microsoft の NuGet パッケージの圧縮データの途中に差し込み**、 **要求ごとに難読化を変えてハッシュを無意味にし**、 **MSI から Mark-of-the-Web を剥がして SmartScreen の警告を消す**
    根拠: Huntress の解析（検体の逆アセンブルと復号の再実装）
  4. 4. 永続化確認済[1]
    **HKCU の Run 値とタスクスケジューラの両方**に同じ名前 （第1版は `Canon Configuration Reader`、第2版は `Stardock DeElevation Tool`）で 登録され、どちらも土台の実行ファイルを起動する。 RAT の設定に入っているスクリプトが **150秒ごとに Run 値を、875秒ごとにタスクを作り直し**、 さらに**シャットダウン時にも Run 値を書き直す。** Huntress は**「片方を消しても数分で戻る。プロセスを止めてから両方を消せ」**と 順序を明示している
    根拠: Huntress の解析（`monitor.raw` を復号して取り出したタスクスクリプト）
  5. 5. C2通信確認済[1]
    RAT は C2（報告では "Gate"）の名前解決を **DNS over HTTPS（Cloudflare・Google・Quad9）**で行う。 Huntress は「その問い合わせは通常の HTTPS 通信の中を通るため、 **ローカルの DNS ログには一切現れない**」（原文英語）と述べている。 **C2 のアドレスは回収された検体のどこにも含まれていなかった**—— 暗号化された設定にあるか、実行時に渡されるか、コードの奥にあると推測されている
    根拠: Huntress の解析（RAT から復号した約1,500の文字列）
  6. 6. 収集確認済[1]
    RAT はまず**ホストの棚卸し**を行う——導入されているウイルス対策（WMI 経由）・ Defender の状態・ドメインとドメインコントローラ・ネットワークアダプタ・ 開いているポート・導入済みソフトウェア・有効な Windows の機能・ **仮想環境の検出も兼ねる詳細なハードウェア指紋。** 操作系の機能として**遠隔デスクトップ・画面の配信・ カメラ・マイク・システム音声の取得**、 **17種のブラウザの把握と既定ブラウザの起動**、 **ホスト全体のファイル内容を検索する機能**を持つ。 観測された後続の動きは、**正規に署名された GOMCam の実行ファイルを置き、 使い捨てのプロファイルで Chrome を起動する**というものだった
    根拠: Huntress の解析（RAT の文字列と感染端末での観測）

本物の chatgpt.com にいるまま騙される経路が作られた概観

Huntress が2026年9月28日に公表したキャンペーンは、ChatGPT の正規機能「Custom GPT」を入口にしています。

Custom GPT は、利用者が用途別に自分用の ChatGPT を作れる機能です。作られたものは chatgpt.com 上のページとして公開され、上部に名前、その下に作成者の欄が表示されます。

攻撃者が作ったものの名前は 「Plus 5.6」でした。新しいモデルの名前のように見えます。作成者欄には "community builder" と出るため、Custom GPT が何かを知っている人には見分けが付きますが、知らない人には普通の ChatGPT の画面に見えます。

到達経路も日常的です。Huntress が調べた事案のいくつかでは、被害者は Google で「chatgpt」と検索していました。そして広告枠（sponsored）の結果が、chatgpt.com 上のこの Custom GPT へ導いていました。URL には Google 広告のクリック追跡パラメータ（gad_source・gad_campaignid など）が付いており、攻撃者が広告費を払って検索結果の最上部に出していたことが分かります。

この Custom GPT は、何を入力しても同じ1通を返すよう設定されていました。「サービス提供状況のお知らせ」として「主ドメインでの提供が制限されている」と述べ、Plus への課金か「予備のドメイン」の利用を促します。

「予備のドメイン」は Google Sites 上のページです。そこには Cloudflare 風の CAPTCHA 確認画面があり、利用者にコマンドをコピーしてターミナルに貼るよう指示します（ClickFix）。

ここまでの経路に、脆弱性は1つも使われていません。利用者が確認できることは全部正しいのです——ドメインは本物の chatgpt.com、リンク先は本物の Google Sites、検索結果は本物の Google。「URL を確認する」という習慣が、この経路では守りになりません。

8段の連鎖は、各段が次の段を隠すために存在する原因・手口

Huntress の言葉を借りると、「我々が見る ClickFix の連鎖はたいてい2段か3段だが、これは8段あり、各段は次の段を隠すために存在する」（原文英語）。

要点だけを段ごとに並べます（すべて Huntress の解析による）。

1. 貼らされる PowerShell。スクリプトを取得して実行するだけですが、取得先のホストが10進数の数値で書かれています。 Windows はこれを IP アドレスとして解決しますが、「点で区切られた IP アドレス」を探す検知ルールや URL フィルタにはIP が1つも見えません。

2. 二重に隠された中間スクリプト。 1行で27,581文字、そのほとんどが負の整数3,036個の配列です。固定値を足して文字に戻し、ディスクに書かずに実行します。ダウンロード URL などの文字列は、さらに別の鍵で個別に符号化されています。

3. 見えないインストーラ。 MSI を無音でインストールします。名前は毎回新しい GUID で、同じ名前が二度使われません。 MSI は「Advanced Printer Configuration Reader」と名乗り、ARPSYSTEMCOMPONENT=1 によって「プログラムと機能」から隠れます——利用者が「いま何を入れたのか」を探しても見つかりません。さらにインストール完了と同時に実行するため、再起動もログオンも待ちません。

4. 署名済みの正規アプリを土台にする。展開される177個のファイルのうち、意味があるのは8個です。残りは正規に署名された .NET ランタイムなどの「装飾」で、全体が正規のインストーラらしく見えます。土台になるのは Canon の CaptureOnTouch の署名済み実行ファイルで、署名は有効なままです。置き換えられたのは、その実行ファイルが読み込む Canon のログ用 DLL の側です。この DLL は署名が外れ、ヘッダのチェックサムも中身と合っていませんが、デバッグ情報のパスは Canon のビルド環境を指し、コンパイル時刻は2015年のままで、Canon が呼ぶ関数も残っています。違いは輸入表に1つだけ余計な項目があることだけで、Windows はライブラリ自身のコードより先に、その項目を読み込みます。

5〜6. .wav に埋めたローダと、独自の暗号化ファイルシステム。ローダは音声ファイルの中に置かれています—— 本物の録音の一部を暗号文で上書きしたもので、Huntress は「厳密にはステガノグラフィではない。ファイルのヘッダをそのまま信じる自動解析の大半をすり抜けるだけの粗い手口だ」としています。取り出されるのは位置に依存しない341KBの機械語で、文字列が1つも読めません（すべて実行時に組み立てて復号する）。機能として確認されたのは AMSI の無効化・.NET ランタイムのホスティング（ディスクに置かずにコードを実行）・ntdll の再読み込みによるEDR のフックの回避・仮想環境の検出・偽の「LOADING...」画面です。最終段は monitor.raw という独自の暗号化ファイルシステム（索引1,128件・復号すると315フォルダ806ファイル）に入っており、持続化の設定も RAT 本体もここから出てきます。

7. 消しても戻る持続化。 HKCU の Run 値とタスクスケジューラの両方に同じ名前で登録され、150秒ごとに Run 値、875秒ごとにタスクを作り直します。さらに Windows のシャットダウン時にも Run 値を書き直す監視役がいます。Huntress は「片方を消しても数分で戻る。プロセスを止めてから両方を消せ」と順序を明示しています。

8. RAT。遠隔デスクトップ・画面の配信・カメラ・マイク・システム音声の取得、17種のブラウザの把握と既定ブラウザの起動、ホスト全体のファイル内容を検索する機能、そして EXE・DLL（rundll32 / regsvr32 経由）・MSI・PowerShell・バッチ・VBScript・JScript・ZIP の追加投下と実行。侵入後にまず行うのはホストの棚卸し——導入されているウイルス対策（WMI 経由）・Defender の状態・ドメインとドメインコントローラ・ネットワークアダプタ・開いているポート・導入済みソフトウェア・詳細なハードウェア指紋です。

C2 の名前解決が DNS over HTTPS で行われ、社内 DNS のログに出ない帰属

本件で防御側にとって最も重い一行は、ここだと考えます（本記録の評価）。

Huntress の報告によれば、RAT は C2（報告では "Gate" と呼ばれる）を見つけるためにDNS over HTTPS を使い、Cloudflare・Google・Quad9 の解決サーバへ問い合わせます。

その問い合わせは通常の HTTPS 通信の中を通るため、ローカルの DNS ログには一切現れない。（原文英語）

多くの組織で、マルウェアの発見は DNS のログから始まります——見慣れないドメインへの問い合わせ、生成されたような名前、短い TTL。その入口が閉じています。

さらに、C2 のアドレスは回収された検体のどこにも入っていませんでした。 Huntress は暗号化された設定にあるか実行時に渡されるのだろうと推測しています。つまり、検体を手に入れても通信先が分からないということです。

残る手がかりはプロセスの挙動です。Huntress が挙げているのは次の型です（同社の検知の手がかりであり、本記録が検証したものではありません）。

  • powershell.exe が msiexec.exe を起動する（%TEMP% 配下の MSI を無音で）
  • Canon / Stardock の実行ファイルが、正規の導入先ではなく%LOCALAPPDATA%\Programs\ から動いている——とくに msiexec.exe が起動元のとき
  • Canon Configuration Reader / Stardock DeElevation Tool という名前のRun 値・タスク
  • 署名の外れた Canon のログ用 DLL、あるいは同じフォルダにある見慣れない DLL 群
  • 第2版では、ヘッダのチェックサムが中身と合わない Stardock の DLL

本記録は、悪性のドメイン・IP・ハッシュを転記していません。照合先のテレメトリを持たないまま IoC を並べても検知には使えず、誤検知の材料になるためです。プロセスの挙動にもとづく上の型は、自組織の EDR で今日試せます。

日本の組織にとっての意味は「ChatGPT を検索で開く人がいる」ことにある評価・解釈

以下は本記録の評価です。

本件の入口は、日本でもそのまま成立します。日本語環境で成立しない要素は見当たりません。 Google で「chatgpt」を検索する人、広告枠を疑わない人、Custom GPT という機能を知らない人は、どの国にもいます。

そして守りの難しさは、次の組み合わせにあります。

  1. 利用者が確認できることが全部正しい。ドメインは chatgpt.com、リンク先は Google Sites。「怪しい URL を開かない」という教育は、この経路には届きません。
  2. 止められる場所が「貼る」しかない。 ClickFix は、攻撃者のコードを利用者自身の手で実行させる手口です。端末側で PowerShell の実行を制限していない組織では、入口の1手で全部が動き始めます。
  3. 痕跡が薄い。 MSI は「プログラムと機能」から隠れ、署名済みアプリが土台で、C2 の名前解決は社内 DNS に出ません。

日本の組織に固有の論点を1つ挙げるなら、「AI ツールの入口を業務でどう配っているか」です。社内で ChatGPT を使わせている組織が、ブックマークや SSO のポータルではなく「検索してアクセスしてください」という案内で済ませているなら、本件の入口はそのまま社内に開いています。URL を配る、という地味な運用が、この型に対する最も安い対策です。

もう1つは「どの ClickFix にも共通する1点」です。本キャンペーンの8段は精巧ですが、成立の前提は「利用者がコマンドを貼って実行する」ことだけです。ここが止まれば、残りの7段は動きません。

判断評価評価の根拠と留保
Huntress は、**入口（Custom GPT・検索広告・Google Sites）から RAT の機能・持続化の消し方・プロセスの挙動にもとづく検知の手がかりまで**を公開した。 第2版の存在と、**RAT が第1版と同一ファイルである**ことも示している機能した**本記録の作成者の評価である。** とくに評価できるのは**持続化の消し方に順序を明示した**点である （「片方を消しても数分で戻る。プロセスを止めてから両方を消せ」）。 インシデント対応の現場で**間違いやすい箇所を先に潰している。** また **C2 のアドレスが検体に無い**ことを正直に書き、 推測であると明示している点も、材料の限界を読者に渡している
Huntress は OpenAI に当該 Custom GPT を連絡し、 **9月25日までに削除された。** しかし**9月27日に別の Custom GPT が見つかり、公表時点で稼働していた**不十分**本記録の作成者の評価である。** Huntress の対応（通報）そのものは妥当だが、 **結果として2日で再発している。** 評価すべき相手は通報側ではなく**プラットフォーム側の設計**である—— 「Custom GPT が外部リンクを含む固定応答を返す」「検索広告が Custom GPT の URL を最上位に出せる」という組み合わせに対して、 **OpenAI と Google が何を変えるのかは公表されていない**
CISO・経営層への示唆
  • 業務で使う AI ツールの入口を、検索ではなく URL で配る
    本件の入口は「Google で chatgpt を検索する」という最も一般的な動作である。 広告枠から到達する先は**本物の chatgpt.com** で、 「怪しい URL を開かない」という教育は届かない。 社内の案内が「検索してアクセス」で済んでいる組織は、この入口をそのまま開いている。
    取るべき行動 **利用を認めている AI サービスの URL を、ブックマーク・SSO ポータル・ 社内ポータルの固定リンクとして配る。** 案内文から「検索して」という表現を消す。 **無料の個人利用を黙認している場合も、入口の URL だけは示す。**
  • ClickFix を「利用者教育の1行」に落とし込む
    本件の8段は精巧だが、成立の前提は **「利用者がコマンドをコピーしてターミナルに貼って実行する」ことだけ**である。 ここが止まれば残りは動かない。 そして ClickFix は偽 CAPTCHA・偽エラー・偽の「予備ドメイン」と 見せ方を変え続けている。
    取るべき行動 **「画面の指示でコマンドを貼らせるものは、すべて攻撃である」**という 1行を、全社の教育と入社時研修に入れる。 見せ方（CAPTCHA・エラー・更新の案内）を覚えさせるのではなく、 **「貼らせる」という行為そのものを合図にする。** 貼ってしまった人が**すぐ申告できる窓口**を併せて示す。
  • テイクダウンを対策として数えない
    Huntress の通報で Custom GPT は9月25日までに削除されたが、 **2日後には同じキャンペーンの別の Custom GPT が現れた。** RAT は第1版と1バイトも違わない同一ファイルで、替わったのは包装だけである。
    取るべき行動 **プラットフォームへの通報は行うが、対策の完了とは見なさない。** 自組織の対策は「入口を消す」ではなく **「貼らせるコマンドが実行できない」「実行されたら気づける」**に置く。 通報の結果を待つ時間を、検知の確認に使う。
  • DNS のログに依存した検知の前提を点検する
    本件の RAT は C2 の名前解決を DNS over HTTPS で行い、 **社内の DNS ログには現れない。** C2 のアドレスは検体にも入っていない。 DNS を起点にした検知・脅威ハンティングの運用は、この型に効かない。
    取るべき行動 **「DNS のログが使えないとき、何で気づくのか」を検知設計の前提として問い直す。** 端末側の DoH を社内ポリシーで無効化して社内解決サーバへ寄せるか、 **プロセスの親子関係・持続化の作成・署名の整合**に検知を移す。 どちらも取れない場合、**その空白を経営に説明できる形で残す。**
セキュリティ技術者への示唆
  • 今日、powershell から msiexec が起動する型をアラートにする
    Huntress が最初に挙げている検知の手がかりがこれである （`%TEMP%` 配下の MSI を `/qn /norestart` で無音インストール）。 ある事案では Defender が MSI を隔離したが、**すでに実行済みで、 Run 値とタスクが連鎖を続けた**。
    取るべき行動 EDR で **`powershell.exe` の子として `msiexec.exe` が起動する**規則を作り、 まずアラートで様子を見る。誤検知の大半は正規の配布・更新と重なるため、 **起動元のパスが `%TEMP%` 配下であることを条件に加える。** 検体の隔離で終わらせず、**Run 値とタスクの有無まで確認する運用**にする。
  • 署名済みアプリの「置かれている場所」と「隣の DLL」を見る
    土台の実行ファイル（Canon / Stardock）の署名は有効なままである。 署名が外れているのは**横に置かれた DLL** であり、 そのヘッダのチェックサムも中身と合っていない。 署名の検証だけでは通り抜ける。
    取るべき行動 **正規の導入先ではない場所（`%LOCALAPPDATA%\Programs\` 配下など）から 署名済みアプリが動いていないかを洗い出す**——とくに `msiexec.exe` が起動元のとき。 あわせて**実行ファイルと同じフォルダにある DLL の署名の有無**を見る規則を作る。 「署名があるから安全」を検知の前提から外す。
  • 持続化の除去は順序を守り、15分後に再確認する
    Run 値とタスクの両方に同名で登録され、 **150秒ごとに Run 値、875秒ごとにタスクが作り直される。** シャットダウン時にも書き直される。片方を消しても数分で戻る。
    取るべき行動 手順を**「プロセスを止める → Run 値を消す → タスクを消す → 15分後に両方を再確認」**の順で書く。 **「消したのに戻る」という現象が出たら、この型を疑う。** 対応記録に、消した時刻と再確認の時刻を残す。
  • ハッシュを指標にした検知の限界を、この検体で確認する
    第2版は**要求ごとに難読化を変える**ため、 中間スクリプトのハッシュは指標として無意味である。 MSI のファイル名も毎回新しい GUID で、同じ名前が二度使われない。 一方で **RAT 本体は第1版と1バイトも違わない。**
    取るべき行動 **ハッシュは「最終段」には効くが「配送段」には効かない**という前提で 指標を分ける。配送段は**挙動**（プロセスの連鎖・書き込み先・起動方法）で拾う。 社内の指標一覧を見直し、**ハッシュしか無い脅威がどれだけあるかを数える。**
  • 端末の DNS over HTTPS を棚卸しする
    RAT は Cloudflare・Google・Quad9 の DoH を使って C2 を解決する。 ブラウザや OS で DoH が有効なままだと、 **悪性の名前解決が社内の DNS ログを通らない。**
    取るべき行動 **ブラウザと OS の DoH 設定を、管理ポリシーで社内解決サーバへ寄せる。** 業務上 DoH が要る端末は例外として台帳に残す。 **「社内 DNS を通っていない端末が何台あるか」を数える**ことから始める。
