INC-2026-0251Pgpool-II の watchdog に脆弱性7件

JPCERT/CC の JVN が2026年9月29日、PostgreSQL 用ミドルウェア **Pgpool-II** の脆弱性 **7件**（CVE-2026-92867〜CVE-2026-92873）を公表した——**うち6件は高可用性のための watchdog のメッセージ処理**にあり、最も重いものは不正なフェイルオーバー要求で**任意のメモリアドレスに32ビット値を書き込める**（CVSS 4.0 で 8.7・CVSS 3.0 で 8.8）。残る1件はクライアント証明書の Common Name に **NUL バイト**を仕込むと**パスワードなしで別のユーザーとして接続できる**認証迂回である。修正は 4.7.3 / 4.6.8 / 4.5.13 / 4.4.18 / 4.3.21 で、**3.5系から4.2系はサポート終了のため修正版が出ない**。開発者は「watchdog を止める」「watchdog への到達を信頼できる網に限る」等の回避策をリリースノートに書いているが、**JVN 側には回避策の記載が無い**。悪用の報告は無く、本記録の確認時点で **NVD への登録も CISA KEV への収載も無い**

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年9月29日 最終更新: 2026年9月29日

2026年9月29日、JPCERT/CC が運営する JVN（JVN#22475874）とJVN iPedia（JVNDB-2026-000140）に、Pgpool-II の脆弱性 7件 が公表されました。同日、開発者（Pgpool Global Development Group）が修正版4.7.3 / 4.6.8 / 4.5.13 / 4.4.18 / 4.3.21 を公開しています。

Pgpool-II は PostgreSQL の前段に置くミドルウェアで、接続プーリング・負荷分散・高可用性を担います。7件のうち6件は、その高可用性のための watchdog（ノード間の死活監視とリーダー選定）のメッセージ処理にあります。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**watchdog の待ち受け（既定 TCP 9000）またはハートビートの受信（既定 UDP 9694）へ 到達できる位置から、不正な形式のメッセージを送る。** メッセージの処理でメモリが破壊され（任意アドレスへの32ビット書き込み・ 任意長データのスタックへの書き込み・固定長配列の越境）、 プロセスの異常終了、または任意コード実行に至りうる。 認証鍵の検査を迂回すれば**任意のノードをリーダーへ昇格**させられ、 ハートビート処理の不備では**スタックメモリの内容がログへ出る**。 別経路として、**X.509 証明書の Common Name に NUL バイトを仕込むと、 パスワードなしで別のユーザーとして接続できる**。 **以下は公表資料から読み取れる成立経路であり、現実の攻撃は報告されていない。**

  1. 1. 偵察公表・報道に基づく[5]
    **watchdog が待ち受けているかを探す。** 既定は TCP 9000（watchdog）と UDP 9694（ハートビート受信）である。 **この段階は本件に固有のものではなく、一般的なポートの探索で足りる。** 実際にそのような探索が観測されたという公表は無い
    根拠: 設定項目の説明（既定の待ち受けポート）。攻撃の観測は公表されていない
  2. 2. 初期侵入確認済[2] [3]
    **watchdog へ不正な形式のメッセージを送る。** **認証鍵は既定で空＝認証無効**であり、 鍵を設定していても **CVE-2026-92873 では認証鍵の検査を迂回される。** 開発者は CVE-2026-92871 について 「**watchdog のポートへ接続できる攻撃者は、 対象ノードの watchdog プロセスをクラッシュさせられる**」（原文英語）と書いている
    根拠: 開発者のリリースノートの記述（各 CVE の成立条件）
  3. 3. 実行確認済[2] [3]
    **メッセージの処理でメモリが破壊される。** フェイルオーバー要求の処理では 「**意図しないメモリアドレスへ値が書き込まれ、メモリ破壊に至る**」 （CVE-2026-92867・原文英語）、 「**任意の長さのデータをスタックへ書き込む**」（CVE-2026-92870・原文英語）。 watchdog メッセージの処理では 「**作り込まれたメッセージの処理により固定長の配列を越えた書き込みが起こりうる。 これを悪用すると Pgpool-II のプロセスがクラッシュするか、 メモリが破壊される**」（CVE-2026-92869・原文英語）
    根拠: 開発者のリリースノートの記述
  4. 4. 権限昇格確認済[1] [2] [3]
    **認証の判断をずらす。** 2つの経路がある。 ①**CVE-2026-92873**——「**攻撃者は認証鍵の検査を迂回し、 自分が選んだ watchdog ノードをリーダーへ昇格させられる**」（原文英語）。 ②**CVE-2026-92868**——X.509 証明書の Common Name の NUL バイトの扱いの不備により 「**悪意あるクライアントが、パスワードなしで別のユーザーとして Pgpool-II サーバへ接続できる**」（原文英語）。 **②は watchdog を使っていない環境でも成立する**
    根拠: 開発者のリリースノートと JVN の想定される影響
  5. 5. 影響（暗号化・破壊・改ざん）確認済[1] [2] [3]
    **想定される影響は JVN が挙げている。** Pgpool-II のプロセスが異常終了したり任意のコードを実行されたりする （CVE-2026-92867）、クライアント証明書の認証が回避される（CVE-2026-92868）、 プロセスが異常終了する（CVE-2026-92869・92870）、 watchdog プロセスが異常終了する（CVE-2026-92871）、 クラスタに関する情報が漏えいする（CVE-2026-92872）、 任意の watchdog ノードがリーダーノードに昇格する（CVE-2026-92873）。 **Pgpool-II は PostgreSQL の前段に置く中継役であるため、 プロセスが落ちればその先のデータベースへの経路が途絶える**（本記録の評価）
    根拠: JVN の想定される影響と開発者のリリースノート

7件のうち6件は、高可用性のための watchdog にある概観出典 [1] [2] [3] [5]

Pgpool-II は PostgreSQL の前段に置くミドルウェアで、接続プーリング・負荷分散・高可用性を担います。公式サイトの説明は「PostgreSQL のための接続プーリング・ロードバランシング・高可用性の機能を備えたオープンソースのミドルウェア」です。

2026年9月29日に公表された7件のうち、6件は watchdog のメッセージ処理にあります。watchdog は複数の Pgpool-II ノードが互いの生死を見張り、どのノードがリーダーになるかを決める機能です。内訳は次のとおりです。

  • フェイルオーバー要求メッセージの処理——CVE-2026-92867（任意アドレスへの32ビット書き込み）・CVE-2026-92870（任意長データのスタックへの書き込み）
  • watchdog メッセージ全般の処理——CVE-2026-92869（配列の上限検査の不備による境界外書き込み）
  • ノード間の認証——CVE-2026-92871（認証情報を欠いたメッセージでNULL ポインタ参照）・CVE-2026-92873（認証鍵の検査の迂回）
  • ハートビート受信——CVE-2026-92872（スタックメモリの内容がログへ出る）

残る1件、CVE-2026-92868 だけがクライアント証明書認証の側にあります。

ここから、実務上の順序が決まります。まず見るのは版番号ではなく構成です。 watchdog は既定で無効（use_watchdog = off）なので、単体構成で接続プーリングと負荷分散だけに使っている環境は、6件の対象外です。逆に、冗長化のために watchdog を入れている環境が、その冗長化の部品で狙われるという形になっています。

最も重いのは、不正なフェイルオーバー要求で任意のアドレスに書き込めるもの原因・手口出典 [1] [2] [3] [4]

CVE-2026-92867（CVSS 4.0 で 8.7・CVSS 3.0 で 8.8）について、開発者はこう書いています。

攻撃者は Pgpool-II の watchdog に不正な形式のフェイルオーバー要求メッセージを送ることができ、意図しないメモリアドレスへ値が書き込まれ、メモリ破壊に至る。（原文英語）

JVN が挙げる想定される影響は「Pgpool-II のプロセスが異常終了したり、任意のコードを実行されたりする」です。書き込めるのは任意のアドレスへの32ビット値であり、これが任意コード実行へ至る条件は公表されていません。

同じ「フェイルオーバー要求の処理」には CVE-2026-92870 もあります。開発者の記述は「攻撃者は Pgpool-II の watchdog に不正な形式のフェイルオーバーメッセージを送り、任意の長さのデータをスタックへ書き込める」（原文英語）です。こちらの想定される影響はプロセスの異常終了にとどまりますが、CVSS 4.0 では 8.7 で、必要な権限が無し（PR:N）と採点されています。

注意すべきは、CVSS の版によって順位が入れ替わることです。

  • CVE-2026-92867 は 4.0 で 8.7・3.0 で 8.8（権限は「低」）
  • CVE-2026-92870 と CVE-2026-92871 は 4.0 で 8.7・3.0 で 7.5（権限は「無し」）
  • CVE-2026-92873 は 4.0 で 6.9・3.0 で 7.3
  • CVE-2026-92869 は 4.0 で 7.1・3.0 で 6.5

どちらの版で並べるかで「上から3件」の顔ぶれが変わります。台帳に片方だけを入れている組織は、社内の優先順位が外の勧告の並びと食い違うことを知っておく必要があります（本記録の評価）。

証明書の Common Name に NUL バイトを仕込むと、別人として通る原因・手口出典 [1] [2] [3]

7件のうち唯一 watchdog に依らないのが CVE-2026-92868（不適切な証明書検証・CWE-295・CVSS 4.0 で 6.9・3.0 で 6.5）です。

開発者の記述は、X.509 証明書の Common Name フィールドに含まれる NUL バイトの扱いが不適切であるために、証明書認証を使っているとき「悪意あるクライアントが、パスワードなしで別のユーザーとしてPgpool-II サーバへ接続できる」（原文英語）というものです。あわせて「そのような証明書を提示することで、本来は拒否されるべき認証が正規の利用者として通ってしまう可能性がある」（原文英語）とも書かれています。

これは古典的な落とし穴です。証明書の中の文字列を、NUL バイトで終わる文字列として扱う実装と、長さを持った文字列として扱う実装が混在すると、「どこまでが名前か」の解釈がずれます。認証の判断がその名前に依存していれば、判断そのものがずれます。

対象はクライアント証明書認証を使っている環境に限られます。開発者が挙げる回避策は「クライアント証明書認証以外の認証方式を使う」（原文英語）です。ただし証明書認証はパスワードを配らないために選ばれていることが多く、「他の方式に変える」は運用としては軽い作業ではありません（本記録の評価）。

認証鍵は既定で空——設定していても、昇格の検査は迂回される評価・解釈出典 [1] [2] [3] [4] [5]

watchdog のノード間通信には認証鍵（wd_authkey）があります。本記録の作成者が設定項目の説明で確認したところ、既定値は空で、その場合 watchdog の認証は無効になります。説明は「すべての watchdog の通信に使う認証鍵を指定する。すべての Pgpool-II が同じ鍵を持たなければならない。異なる鍵を持つ watchdog からのパケットは拒否される」（原文英語）です。

この既定値が、今回の7件の読み方を変えます。

  • CVE-2026-92870（スタックへの任意長書き込み）は、開発者の記述では認証鍵が設定されていないときに成立します。つまり既定のまま watchdog を有効にした環境が対象です。
  • CVE-2026-92871（NULL ポインタ参照）は逆に、認証鍵を設定しているときに、認証情報を欠いたメッセージで成立します。
  • CVE-2026-92873 は認証鍵の検査自体を迂回して、「攻撃者が選んだ watchdog ノードをリーダーへ昇格させられる」（原文英語）ものです。

並べると、鍵を設定していない環境と設定した環境の双方に、それぞれの当たり方があることになります。「認証鍵を入れたから watchdog の通信は守られている」という前提は、本件では成り立ちません（本記録の評価）。

リーダーの昇格が攻撃者の思い通りになると何が起きるかは、構成次第です。watchdog のリーダーは仮想IPの保持やフェイルオーバーの指示に関わるため、昇格の操作は「どのノードにトラフィックを向けるか」の操作になりえます。 ただし本件でそこまでの影響が公表されているわけではありません—— JVN の記述は「任意のウォッチドッグノードがリーダーノードに昇格する」まで、JVN iPedia は「ノード間通信の改ざん」までです。

3.5系から4.2系には、修正版が出ない対策・注意喚起出典 [1] [2] [3] [5]

JVN の対策の節は、修正版5本を挙げたうえでこう書いています。

Pgpool-II 3.5系から4.2系まではサポートが終了しているため、修正版がリリースされません。4.3より前のバージョンを利用している場合は、上記最新バージョンへアップグレードしてください。

7件のうち6件の影響範囲は「3.5系から4.2系までのすべてのバージョン」を含みます（CVE-2026-92868 は 4.0系から4.2系）。つまり古い版を使っている環境は、当たっているのに直せません。選べるのは次の3つだけです。

  1. 系列をまたいでアップグレードする（4.3.21 以降へ）
  2. watchdog を止める（use_watchdog = off）——冗長化を手放す
  3. watchdog への到達を信頼できる網に限る——設定ではなくネットワーク側の作業

2 と 3 は開発者が挙げる回避策で、古い版でも取れる手です。ただし 2 は高可用性そのものを捨てることになります。3 は到達範囲を管理側の網に閉じる話で、watchdog の待ち受けは既定で TCP 9000、ハートビートは既定で UDP 9694 です（本記録の作成者が設定項目の説明で確認）。

CVE-2026-92868（証明書認証）については、回避策は他の認証方式への変更だけです。古い版で証明書認証を続ける選択は、この1件を抱え続けることを意味します。

悪用の報告は無いが、狙われるのは管理系のポートである評価・解釈出典 [1] [2] [3] [5]

実際の攻撃はどこにも報告されていません。修正版の公開と公表は同日で、報告は開発者との調整を経ています。その意味で、本件は協調開示が期待どおりに運んだ事案です。

それでも、次の2点は残ります（いずれも本記録の評価）。

1つ目。watchdog の待ち受けは「管理系だから守られている」と暗黙に扱われがちな位置にあります。既定で TCP 9000 と UDP 9694、認証鍵は既定で空。冗長化のために複数拠点・複数サブネットへノードを分けると、その間の経路をどこまで閉じられているかは構成ごとに違います。クラウドのセキュリティグループや仮想網の設定で「サブネット内は全許可」にしている環境では、同じ網に入れた他のワークロードから到達できます。

2つ目。攻撃の結果が「障害」と見分けづらいことです。 6件のうち4件の想定される影響はプロセスの異常終了です。不正なメッセージで落とされたのか、別の理由で落ちたのかは、ログを見て初めて分かります。 watchdog のログを取っていない環境では、後から区別する手がかりが残りません。

この2つは、悪用が報告されていない今のうちに手を打てるものです。到達範囲を閉じることと、watchdog のログを残すこと—— どちらも版を上げるかどうかとは独立にできます。

システム構成□ PostgreSQL の前段に Pgpool-II を置いており、版が 4.7.2 以前である影響を受ける版の範囲である（4.7.0〜4.7.2／4.6.0〜4.6.7／4.5.0〜4.5.12／ 4.4.0〜4.4.17／4.3.0〜4.3.20／4.2系以前）。 ただし版だけでは該否が決まらず、有効にしている機能を併せて見る必要がある。
システム構成□ 高可用性のために watchdog を有効にしている（既定は無効）7件のうち6件は watchdog のメッセージ処理にあり、 watchdog を使っていない環境はその6件の対象外である。 **該否を分ける最大の分岐がここにある。**
認証・認可□ クライアント証明書認証を使って Pgpool-II への接続を認証しているCVE-2026-92868（証明書の Common Name の NUL バイトの扱い）はこの場合にだけ成立し、 **watchdog を使っていない環境でも当たる。** 回避策は他の認証方式への変更しかない。
運用・監視□ watchdog の待ち受け（既定 TCP 9000）とハートビート（既定 UDP 9694）へ、ノード以外から到達できる認証鍵は既定で空＝認証無効であり、設定していても昇格の検査は迂回されうる。 **到達できる範囲がそのまま攻撃可能な範囲になる。** クラウドで「サブネット内は全許可」にしている構成はとくに確認が要る。
体制・契約□ Pgpool-II のようなデータベースの前段の中継役が、資産台帳に載っていない台帳に無ければ、版・待ち受けポート・有効な機能のいずれも即答できない。 **本件の該否の判定に必要な情報がちょうどその3つである。**
運用・監視□ 脆弱性の検知を NVD からの取り込み（CVE 番号起点）だけで行っている本記録の確認時点で7件はいずれも NVD に登録がなく、 読めるのは JVN・JVN iPedia・開発者のリリースノートだけだった。 **国内の公表が先に立つ事案は実在する。**
委託・第三者部品□ サポートが終了した Pgpool-II 3.5系から4.2系を使い続けている**修正版がリリースされない。** 残る手は系列をまたぐアップグレードか、 watchdog の停止・到達範囲の制限といった回避策だけになる。
