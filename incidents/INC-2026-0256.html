INC-2026-0256Authlib に署名検証回避の脆弱性

CERT/CC が2026年9月28日、Python の OAuth／OIDC ライブラリ **Authlib** に**署名検証を丸ごと迂回できる脆弱性**（**CVE-2026-96760**・VU#762428）を公表した——**JWS の JSON 直列化形式で `signatures` を空の配列にすると、検証が一度も走らないまま「検証済み」として payload が返る**。鍵も資格情報も要らない。翌9月29日に JPCERT/CC の **JVN** が **JVNVU#99151548** として国内向けに伝えたが、本文は CERT/CC への参照だけである。**開発元からの回答は無く、修正版も出ていない**（CERT/CC「ベンダーからの声明は受け取っていない」原文英語）。**本記録の作成者が最新版 v1.8.0（2026年8月30日公開）の該当コードを取得して読んだところ、空の配列を弾く処理は入っていない**——当該ファイルの最終更新は2026年2月25日で、本記録の確認時点（9月30日）まで修正は入っていない。**CVSS は NVD にも CERT/CC にも無く**、悪用の報告も無い（**KEV 未収載を本記録の作成者が確認**）

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年9月28日 最終更新: 2026年9月29日

2026年9月28日、CERT/CC が Vulnerability Note VU#762428 を公表しました。Python の OAuth 1.0／OAuth 2.0／OpenID Connect ライブラリ Authlib に、署名の検証を丸ごと迂回できる欠陥があるというものです。翌 9月29日、JPCERT/CC の JVN が JVNVU#99151548 として国内向けに伝えました。

  1. 直すものが無い。 公表から本記録の作成時点まで、修正版は出ていません。読者が今日できるのは「自分のコードのどこが JSON 側の経路を通るか」を数えることだけです。

空の配列を渡すと、検証は一度も走らないまま「検証済み」として返る原因・手口出典 [1] [3] [5]

欠陥は JsonWebSignature.deserialize_json() にある。JWS の JSON 直列化形式——コンパクト形式（xxx.yyy.zzz）ではなく、payload と signatures を持つ JSON オブジェクトとして表現する形式——を検証する経路である。

NVD の記述はこうである。

Authlib（v1.7.2 以下）には署名検証の迂回の脆弱性がある。JsonWebSignature.deserialize_json() メソッドは、JSON 直列化形式の JWS オブジェクトを受け取ると、署名の有無を確認せず、暗号鍵を要求することもなく、payload を検証成功として返す。（原文英語）

なぜそうなるのかは、コードの形を見ると分かる。本記録の作成者が取得した v1.8.0 の該当箇所は、次の構造をしている。

headers = []
is_valid = True
for header_obj in obj["signatures"]:
    jws_header, valid = self._validate_json_jws(...)
    headers.append(jws_header)
    if not valid:
        is_valid = False

rv = JWSObject(headers, payload, "json")
if is_valid:
    return rv
raise BadSignatureError(rv)

is_valid は True で始まる。そして False に落ちるのは、ループの中で検証が失敗したときだけである。signatures が空の配列なら、ループは一度も回らない。is_valid は True のまま、payload が返る。

これは「検証に失敗した」のではなく「検証をしていない」状態である。攻撃者は鍵を持つ必要がない。署名を偽造する必要もない。署名の欄を空にするだけでよい（本記録の評価）。

CERT/CC は影響を「アプリケーションが、Authlib の検証に依拠している箇所で、攻撃者の用意した内容を正当なものとして受け入れうる」（原文英語）と述べている。認証の判断・マイクロサービス間の通信・認可の主張（claims）・データの完全性——JWS で運んでいるものが何であれ、その前提が消える。

「コンパクト形式しか使っていない」は、攻撃者の側から崩せることがある原因・手口出典 [5]

ここは公表資料に書かれていない。本記録の作成者がコードを読んで確認した点である。

Authlib には、入力の形を見て行き先を決める deserialize() がある。v1.8.0 の実装はこうである。

if isinstance(s, dict):
    return self.deserialize_json(s, key, decode)

s = to_bytes(s)
if s.startswith(b"{") and s.endswith(b"}"):
    return self.deserialize_json(s, key, decode)
return self.deserialize_compact(s, key, decode)

渡された値が dict のとき、あるいは文字列が { で始まり } で終わるとき、JSON 側の経路へ回される。

つまり、アプリケーションが

jws.deserialize(request_supplied_token, key)

のように受け取った値をそのまま渡しているなら、攻撃者は xxx.yyy.zzz の代わりに{"payload": "...", "signatures": []} を送りつけるだけで、脆弱な経路へ切り替えさせられる。

該否を「自分たちが使っている形式」で判断してはいけない、ということである。判断の基準は形式ではなく呼び出し方である—— deserialize_json() を直接呼んでいるか、deserialize() に外から来た値を渡しているか。前者だけを探すと、後者を取りこぼす（本記録の評価）。

本件では、原典である CERT/CC のノートにも CVSS が無く、修正版も無い。 日本語の記事が「詳細は JVN を参照」と書き、JVN が「詳細は CERT/CC を参照」と書き、CERT/CC が「修正版が出るのを待て」と書く—— この連鎖の末端に、読者が使える指示は残っていない。だからこそ、該否の判定を自分のコードで行うしかない。

今日できるのは、呼び出し箇所を数えて経路を塞ぐことだけである対策・注意喚起出典 [1] [5]

修正版が無い以上、取れる手は「入力の側で閉じる」か「経路を使わない」かのどちらかである（以下はすべて本記録の評価であり、CERT/CC・JVN・開発元が示した回避策ではない）。

  1. 依存の確認。 authlib が直接の依存か、間接の依存かを調べる。pip show authlib ／ ロックファイル ／ SBOM のいずれでもよい。間接依存で入っている場合、自分のコードに deserialize が現れないことがある。
  2. 呼び出し箇所の棚卸し。 deserialize_json( と deserialize( の両方を探す。後者は入力の形で JSON 側へ回るため、コンパクト形式のつもりでも該当する。
  3. 検証の前に形を弾く。 外から受け取る JWS がコンパクト形式だけなら、{ で始まる入力を検証に渡す前に拒否する。 JSON 形式を使う必要があるなら、signatures が空でないことを自前で確認してから検証に渡す。
  4. 戻り値を信じない。 検証後に JWSObject の headers が空でないことを確かめる。空なら、署名は一つも検証されていない。
  5. 移行の検討。 開発元は authlib.jose を非推奨とし、別ライブラリ（joserfc）への移行を予告している。ただし本記録は移行先の検証を行っていない。

いずれも一時しのぎである。 修正版が出たら置き換える必要があり、そのために「どこに入れたか」を記録に残しておくことが要る。

事案の詳細

影響を受けたサービス**Authlib**（Python の OAuth 1.0／OAuth 2.0／OpenID Connect ライブラリ）の `authlib.jose` モジュール。欠陥は **JWS の JSON 直列化形式の検証** （`authlib/jose/rfc7515/jws.py` の `JsonWebSignature.deserialize_json()`）にある。 **入力の形で経路を決める `deserialize()` も、 dict または `{` で始まり `}` で終わる文字列を渡されると同じ経路へ回す** （本記録の作成者が v1.8.0 の原文で確認）
バージョン**影響を受ける版（CERT/CC・NVD の記載）**: **1.7.2 以前**。 **修正版**: **存在しない**（本記録の確認時点）。 **最新版は 1.8.0**（2026年8月30日公開）で、 **本記録の作成者が確認した範囲では同版にも空の配列を弾く処理は無い**—— ただしこれは**本記録の読みであり、公式の判断ではない**
外部からの到達性**特別な前提を要さない。** 攻撃者が用意した JWS を検証させられる経路があれば成立する （外部からのトークン・アサーション・署名付きの要求など）。 **鍵の入手も署名の偽造も不要**で、`signatures` を空の配列にするだけでよい。 **したがって到達性を絞る余地は小さい**—— 到達させたくない相手は、通常そのまま認証の入口に来る（本記録の評価）
手法**`{"payload": "...", "signatures": []}` の形の JWS を検証に渡す。** 検証の可否を保持する変数が `True` で初期化され、 **要素が0個のループは一度も回らない**ため、 失敗と判定される機会が無いまま「検証済み」として payload が返る。 **フェイルオープンの型である**（本記録の評価）

  • 署名付きで受け渡される要求・応答の完全性（マイクロサービス間の通信を含む）

CISO・経営層への示唆
  • 「修正版が無い脆弱性」は、脆弱性管理の手順から落ちる
    多くの組織の手順は「勧告を受け取る→該当を調べる→修正版を当てる」で組まれている。 **本件は3段目が存在しない。** CERT/CC が示した対策は「リポジトリを見張れ」だけで、 **いつ出るのかの見通しも無い。** 手順が「当てる」で終わっていると、**この案件は宙に浮いたまま忘れられる。**
    取るべき行動 **修正版が無い案件を置く場所を、脆弱性管理の台帳に作る。** 「対応中」でも「対応不要」でもない**第3の状態**として、 **暫定の手当て・再確認の期日・誰が見張るか**を1件ずつ持たせる。 本件については**「該当箇所を特定したか」を9月30日から1か月以内に報告させる**、 といった形にしないと、修正版が出た日に何も起きない。
  • 「最新版に上げた」が答えにならない場合がある
    勧告には「1.7.2 以下が影響を受ける」と書かれている。 **そのまま読むと 1.8.0 へ上げれば済むように見える。** しかし 1.8.0 は**勧告の29日前**に出た版であり、 本記録の作成者が確認した範囲では**同じコードのままである。** **版番号の比較だけで該否を判断すると、直っていないのに直ったことになる。**
    取るべき行動 **脆弱性の報告を受けたとき「修正が入った版はどれか」を、 影響範囲の記載とは別に確認する規則にする。** 修正コミット・リリースノート・開発元の声明のいずれかで**修正の事実**を確かめる。 **どれも無いなら「未修正」として扱う**—— 本件のように、影響範囲の上端と最新版の間に、 **本件とは無関係に出た版**が挟まることがある。
  • 認証の土台は、1行の実装の癖で崩れる
    本件は暗号の破れでも鍵の漏えいでもない。 **検証結果を保持する変数を `True` で初期化した、という書き方**だけで、 **鍵も署名も要らずに認証を通せる状態**になっている。 **「認証には強い暗号を使っている」という説明は、この種の欠陥に対して何も言っていない。**

  • 国内向けの公表があっても、判断材料が日本語で揃うとは限らない

  • 該否の判定は「使っている形式」ではなく「呼び出している関数」で行う
    `deserialize()` は**入力の形で行き先を決める**。 dict、あるいは `{` で始まり `}` で終わる文字列は JSON 側へ回る （本記録の作成者が v1.8.0 のコードで確認した）。 **「うちはコンパクト形式の JWT だけ」という前提は、 入力を握っている相手には通じない。**
    取るべき行動 **`deserialize_json(` と `deserialize(` の両方を探す。** 後者については、**渡している値が外部由来かどうか**を1件ずつ見る。 外部由来なら、**検証の前に形を制限する** （コンパクト形式だけを受けるなら `{` で始まる入力を拒否する）。
  • 検証関数の戻り値は「検証が行われた」ことを意味しない
    本件では、**署名が0個でも例外は飛ばず、正常に payload が返る。** `try / except BadSignatureError` で囲んでいても、**例外は来ない。** **「例外が出なかったから検証できた」という読み方が、そのまま穴になる。**
    取るべき行動 **検証後に「何が検証されたか」を確かめる**—— 戻り値の headers が空でないこと、期待するアルゴリズムであること、 期待する鍵の識別子（kid）であることを確認する。 **共通のラッパに寄せて、呼び出し箇所ごとの書き漏らしを無くす。**
  • 間接依存に入っているライブラリは、自分のコードを検索しても見つからない
    Authlib は他のライブラリやフレームワークの依存として入ることがある。 その場合、**自分のコードに `deserialize` は一度も現れない。** それでも、**依存側が JSON 直列化形式の検証を通していれば該当する。**
    取るべき行動 **ロックファイルまたは SBOM で `authlib` の有無と版を確認する。** 入っていた場合は、**どの依存が引き込んでいるかを辿る** （`pip show` の Required-by、依存グラフの出力など）。 そのうえで、**引き込んでいる側が JWS の検証をしているかを読む。**
  • 「来ていなかった」と後から言うには、要求の本体が残っていないといけない
    迂回された要求は**正規の要求として処理される**ため、 エラーも警告も残らない。 アクセスログには成功した要求として並ぶ。 **区別できるのは、要求の本体に `signatures` が空の JWS があるかどうか**だけである。
    取るべき行動 **署名付きのトークンを受ける経路について、 要求の本体（またはその要約・ハッシュ）を保存しているかを確認する。** 保存しているなら、**`"signatures"` が空配列の JWS を過去分から探す。** 保存していないなら、**「確認できない」と書いて報告する**—— 「痕跡は無かった」と書いてはいけない。
  • 暫定の手当ては、入れた場所を記録に残さないと後で外せない
    修正版が無いため、当面の対応は**アプリケーション側の検査の追加**になる。 これはライブラリの外に検証の一部を持つということであり、 **修正版が出たあとも残る。** 残ったまま忘れると、**どちらが効いているのか分からなくなる。**
    取るべき行動 **暫定の検査を入れた箇所に、CVE 番号と「修正版が出たら見直す」旨を コメントとして残し、同じ一覧を脆弱性管理の台帳にも持つ。** **修正版の公開を検知する仕組み**（リポジトリの監視・依存の更新通知）を 同時に用意する。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 認証・認可の判断に JWS／JWT を使い、その検証を Authlib（`authlib.jose`）で行っている本件は認証の可否を決める関数そのものの欠陥である。 **鍵の管理も暗号の選択も、この経路の前では効かない。**

運用・監視□ 脆弱性管理の手順が「修正版を当てる」で完結しており、修正版が無い案件の置き場所が無い本件には修正版が存在しない。 **CERT/CC が示した対策は「リポジトリを見張れ」だけで、期日が無い。** 手順に受け皿が無いと、案件が宙に浮いたまま忘れられる。
運用・監視□ 署名付きトークンを受ける経路で、要求の本体を保存していない迂回された要求は正常な要求として処理され、エラーが残らない。 **本体が残っていなければ、過去にさかのぼって確認する手段が無い。**
