INC-2026-0257AWS AgentCore SDK に2件の欠陥

BeyondTrust が2026年9月28日に公表した技術解説によれば、**Amazon Bedrock AgentCore の Python SDK** には**パッケージ名をそのままシェルコマンドに変えられる**欠陥が2件（**CVE-2026-12530**・**CVE-2026-16796**）あり、AI エージェントのサンドボックス内でコマンドを実行して**実行ロールの一時的な AWS 資格情報**を読み出せた——いずれも `install_packages()` の引数の区切り文字の扱いの不備（**CWE-88**）で、**CVSS 3.1 で 7.3・CVSS 4.0 で 8.4**。1件目は 1.6.1 で拒否文字の一覧を厳格な検証に置き換えて修正されたが、**その修正自体が pip の extras 構文で迂回され**、2件目として 1.18.1 で再修正された。**Firecracker のサンドボックス分離そのものは破られていない**——破れたのは SDK がインストールコマンドを組み立てる部分である

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年9月29日 最終更新: 2026年9月29日

2026年9月28日、BeyondTrust（Phantom Labs）が Amazon Bedrock AgentCore のPython SDK に関する技術解説を公表し、翌29日に報道されました。扱われているのは CVE-2026-12530 と CVE-2026-16796 の2件で、AWS はそれぞれ 2026年6月17日（セキュリティ情報 2026-044）と2026年7月23日（同 2026-065）に公表済みです。

欠陥はいずれも、Code Interpreter クライアントの install_packages()というヘルパにあります。このメソッドは渡されたパッケージ名からpip install のコマンド行を組み立ててサンドボックス内で実行しますが、パッケージ名の検証が不十分で、名前の形をしたシェルコマンドが通ってしまいました。

この記録が扱う要点は4つです。

  • 修正が修正を呼んだ。 1件目は拒否文字の一覧（ブロックリスト）を正規表現による許可（アローリスト）に置き換えて直されました。その許可の書き方が角括弧の中を素通しにしていたため、2件目が生まれています。
  • サンドボックスは破られていません。 BeyondTrust はFirecracker による分離は設計どおりに機能したとしています。破れたのはサンドボックスの中でコマンド行を組み立てる SDK の側です。
  • 取られるのは、そのサンドボックスに紐づいた実行ロールの資格情報です。 microVM の中から 169.254.169.254 のメタデータサービスへ問い合わせれば一時的な資格情報が返ります。そこから先の被害の広さは、そのロールに何を許しているかで決まります。
  • ログには普通の pip install が成功したようにしか見えません。 BeyondTrust は、CloudTrail のデータイベントと AgentCore の可観測性ログが既定で無効であること、失敗したツール呼び出しだけを見る監視では成功した悪用を取り逃がすことを指摘しています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**`install_packages()` へ渡るパッケージ名に、名前の形をしたシェルコマンドを混ぜる。** 1件目は**改行**で次の行にコマンドを置く形、 2件目は **pip の extras 構文（角括弧）の中にコマンド置換を置く**形。 SDK が組み立てた `pip install` のコマンド行がシェルで解釈され、 **Code Interpreter のサンドボックス内で任意のコマンドが走る。** そこから **169.254.169.254** のメタデータサービスへ問い合わせて **実行ロールの一時的な AWS 資格情報**を取得し、 その権限の範囲で AWS の資源へ届く。 **Firecracker による microVM の分離は破られていない。** **以下は公表資料と報道から読み取れる成立経路であり、現実の攻撃は報告されていない。**

  1. 1. 初期侵入公表・報道に基づく[1] [2] [6]
    **パッケージ名として、攻撃者が制御する文字列を届かせる。** 入り口は利用者の入力欄とは限らない—— **エージェントが読み込む文書やウェブページ（プロンプトインジェクション）、 リポジトリに置かれた依存関係ファイル**も同じ経路になる。 **「利用者は社内の人間だから安全」という前提はここで崩れる** （本記録の評価）
    根拠: BeyondTrust が挙げた3つの入力経路（報道経由で把握）
  2. 2. 実行公表・報道に基づく[1] [2] [6] [7]
    **SDK が組み立てた `pip install` のコマンド行が、シェルで解釈される。** CVE-2026-12530 では**拒否文字の一覧に改行が入っていなかった**ため、 パッケージ名の後に改行を置き次の行にコマンドを書く形で通った。 CVE-2026-16796 では**正規表現による許可規則が pip の extras 構文（角括弧）の中を素通しにしていた**ため、 角括弧の中にコマンド置換を置く形で通った。 **どちらも pip が解釈する前にシェルが解釈する**
    根拠: AWS のセキュリティ情報2本（`--index-url` / `-r` の悪用、 引数の区切り文字の無害化の不備）と、報道が伝える BeyondTrust の解説
  3. 3. 認証情報アクセス公表・報道に基づく[6] [7]
    **サンドボックス内から 169.254.169.254 のメタデータサービスへ問い合わせ、 Code Interpreter の実行ロールに紐づく一時的な AWS 資格情報を読み出す。** 報道が伝える BeyondTrust の記述は 「**その microVM の中にはメタデータサービスがおり、 求めてきたコードに対して実行ロールの資格情報を渡す**」（原文英語）。 **実行ロールを付けていないカスタム構成、および AWS 既定のシステムインタプリタでは この段が成立しない**
    根拠: 報道が伝える BeyondTrust の解説（メタデータサービスのアドレスを明示）
  4. 4. 影響（暗号化・破壊・改ざん）公表・報道に基づく[1] [2] [6] [7]
    **取得した一時的な資格情報の権限の範囲で、AWS の資源へ届く。** BeyondTrust は、**サンドボックス内でコードが走った後の影響は 実行ロールに与えた権限しだいであり、権限が過大であれば 他の AWS サービスにも及びうる**としている。 **どこまで届いたのかという実証の範囲は公表されていない。** **Firecracker による分離そのものは破られていない**—— 外へ出るのは資格情報であって、サンドボックスからの脱出ではない
    根拠: AWS のセキュリティ情報と、報道が伝える BeyondTrust の解説

破れたのはサンドボックスではなく、その中でコマンド行を組み立てる SDK だった概観出典 [1] [2] [6] [7]

Amazon Bedrock AgentCore の Code Interpreter は、AI エージェントが書いたコードを隔離した環境で走らせるための仕組みです。隔離には Firecracker の microVM が使われています。

今回の2件は、その隔離を破るものではありません。 BeyondTrust はFirecracker による分離は設計どおりに機能したとしています。欠陥があったのは、サンドボックスの中で pip install のコマンド行を組み立てる SDK のヘルパ（install_packages()）のほうです。

つまり構図はこうなります。

  • エージェントが「このパッケージを入れて」という文字列を受け取る
  • SDK がその文字列を pip install のコマンド行に埋め込む
  • 検証をすり抜けた文字列が、パッケージ名ではなくコマンドとして解釈される
  • サンドボックスの中で、攻撃者が指定したコマンドが走る

ここまでは「サンドボックスの中だけの話」です。問題はその先です。microVM の中には、実行ロールの一時的な資格情報を返すメタデータサービスがいる（169.254.169.254）ため、サンドボックス内でコマンドが走ればその資格情報を読み出せます。

隔離は「中で何が走ってもよい」ための仕組みではありません。中から取れるものが外へ効く資格情報であれば、隔離が保たれていても被害は外へ出ます（本記録の評価）。

1件目の修正が、そのまま2件目の入口になった原因・手口出典 [1] [2] [3] [4] [7]

2件は別の欠陥ではなく、同じメソッドをめぐる連続した2手です。

CVE-2026-12530（1.1.3 以上 1.6.1 未満・2026年6月17日公表）は、パッケージ名を無害化する処理が拒否する文字の一覧（ブロックリスト）でできていたことによります。AWS の記述は「install_packages() メソッドの検証が不完全であり、作り込んだ引数が無害化を迂回できた。これにより攻撃者は pip の --index-urlフラグでパッケージの解決先を悪意あるサーバへ向けたり、-r フラグでサンドボックス内の任意のファイルを読ませたりできた」（原文英語）です。報道によれば、セミコロン・アンパサンド・パイプ・バッククォート・ドル記号は弾いていたのに、改行が抜けていたとされます。

AWS は 1.6.1 で、拒否する文字の一覧をより厳格な検証規則へ置き換えて修正しました。

その修正が迂回されたのが CVE-2026-16796（1.18.1 未満・2026年7月23日公表）です。AWS の記述は「install_packages() メソッドにおける引数の区切り文字の不適切な無害化により、認証済みの遠隔の利用者が、作り込んだパッケージ名の引数を通じて Code Interpreter のサンドボックス内で任意のコマンドを実行できるおそれがある」（原文英語）です。報道によれば、置き換えた正規表現による許可規則が、pip の extras 構文（pandas[performance] のような角括弧）の中身をほぼ何でも受け入れていたため、角括弧の中にコマンド置換を書けばpip が解釈する前にシェルが解釈したとされます。

実務上の含意は1つです。「直りました」という告知を、版を止める根拠にしてはいけません。 1件目の公表（6月17日）から2件目の公表（7月23日）までは 36日です。同じメソッドが、同じ種類の理由で、もう一度当たっています。

修正の方針そのものに目を向けると、1.18.1 で入ったのは報道によればシェルの引用（quoting）とより狭い許可規則です。文字列を検査して通す方式から、シェルに渡す前に引用符で囲う方式へ重心が移って初めて、この種類の穴が閉じます（本記録の評価）。

資格情報が出るかどうかは、3つの条件のうち「実行ロールを付けたか」で決まる被害規模・影響範囲出典 [1] [2] [3] [4] [6] [7]

AWS と BeyondTrust の記述をあわせると、サンドボックス内でのコマンド実行とAWS 資格情報の露出は別の段です。後者に至るには3つの条件が要ります。

  1. install_packages() に、攻撃者が影響を与えられる入力が届くこと。 BeyondTrust が挙げる経路は3つ——利用者が入力したライブラリ名、エージェントが読む内容を通じたプロンプトインジェクション、信頼できないリポジトリやノートブックに置かれた依存関係ファイル。
  2. SDK が脆弱な版であること（1.18.1 未満）。
  3. 実行ロールを付けたカスタムの Code Interpreter を使っていること。

実務でいちばん効くのは 3つ目です。AWS 既定のシステムインタプリタはロールを持たないため、コマンドが走っても取り出せる資格情報がありません。逆に、カスタムの Code Interpreter に実行ロールを付けているなら、その1つのロールに許した範囲が、そのまま被害の上限になります。

BeyondTrust は、ロールの権限が過大であれば他の AWS サービスにも影響が広がりうるとしています。ただし「どこまで届いたか」の実証の範囲は公表されていません——本記録は具体的な到達先を書きません。

なお CVSS のベクタは2件とも S:U（スコープ変更なし）、4.0 では SC:N/SI:N/SA:N（後続システムへの影響なし）と採点されています。サンドボックスの外の AWS 資源へ資格情報で届くという結果は、この点数には表れていません。 点数だけを見て優先順位を決めると、この事案は小さく見えます（本記録の評価）。

ログには「pip install が成功した」としか残らない評価・解釈出典 [6] [7]

BeyondTrust が挙げている検知上の指摘は、この事案でもっとも実務に効く部分です。

  • どちらの通し方も、ログ上は普通の pip install が成功した記録に見える。 Infosecurity Magazine は「攻撃者の活動は AWS のログ上では正規のアプリケーションの動きに見えうる」（原文英語）と伝えています。
  • CloudTrail のデータイベントと AgentCore の可観測性ログは既定で無効。つまり何も設定していない環境では、そもそも見るべき記録が残っていません。
  • 失敗したツール呼び出しへの警報は、成功した悪用を取り逃がす。エージェントの監視は「エラーが出たら知らせる」形になりがちですが、この事案で起きるのは「成功」です。
  • 見るべきはコマンドの中身であり、メタデータサービスのアドレス（169.254.169.254）やその符号化された形への参照が手がかりになる、とされています。

ここから、エージェント基盤の監視について一般化できる点が1つあります。エージェントは「外から来た文字列を、実行に変える装置」です。従来のアプリケーションでは入力と実行の間に人が書いたコードが挟まりますが、エージェントでは入力そのものが実行の内容を決めます。だとすれば、記録すべきは結果の成否ではなく、実行された内容そのものです（本記録の評価）。

なお、既定で無効のログを有効にすると費用が増えます。 BeyondTrust の「既定でログを有効にせよ」という推奨は、その費用を引き受ける判断とセットでなければ実行できません（本記録の評価）。

悪用は報告されていないが、報告されないことが自然な作りである未確定事項出典 [1] [2] [6] [7]

AWS のセキュリティ情報2本も、BeyondTrust の解説を伝える報道も、現実の攻撃には触れていません。

ただし、この事案は悪用されても気づきにくい形をしています。

  • 悪用が成功したときの痕跡は「pip install が成功した」という記録である
  • その記録を残す仕組み（CloudTrail のデータイベント・AgentCore の可観測性）は既定で無効である
  • 取られるのは一時的な資格情報であり、それを使った先の操作はそのロールに許された正規の操作として記録される

「悪用の報告が無い」は、「悪用されていない」ではありません。本件では、報告が上がる経路そのものが既定では塞がっていると読むべきです（本記録の評価）。

公表されていない事項は、ほかに次のとおりです—— 報告から公表までの期間、2件が同一の報告に由来するか、脆弱な版がどれだけ使われているか、1.6.1 での修正が具体的にどう書かれていたか、実行ロールを経由して他のサービスへ到達した実例があるか。

打てる手は「版を上げる」「ロールを外す」「入力を固定する」の3つに整理できる対策・注意喚起出典 [1] [2] [6] [7]

AWS と BeyondTrust が挙げている対処を、先に効く順に並べ直します。

① 版を上げる。 bedrock-agentcore を 1.18.1 以降にします。2件とも閉じる唯一の版です。1.6.1 は1件目しか直っていません。

② 実行ロールを外す／絞る。 BeyondTrust はコードが AWS へアクセスする必要が無いなら実行ロールを使わない（AWS 既定のシステムインタプリタを使う）、必要があるなら IAM の権限を厳しく絞ることを推奨しています。これは版上げが済んでいても効き続ける手です——次の同種の欠陥が出たときの被害の上限を、いま決めておくことになります。

③ 入力を固定する。 AWS の回避策は「利用者由来・外部から影響を受けうる文字列を install_packages() へ直接渡さない」「アプリケーションのコード内で、固定のハードコードされた承認済みパッケージ名の一覧に呼び出しを限る」「動的なパッケージ名はPyPI の厳格な命名規則に照らして検証してから SDK のメソッドを呼ぶ」（いずれも原文英語）です。BeyondTrust も「エージェントが拡張できる一覧ではなく、固定のパッケージ一覧を使う」としています。

④ ログを既定で有効にする。 CloudTrail のデータイベントと AgentCore の可観測性ログを有効にし、失敗ではなくコマンドの内容に対して警報を出す——具体的にはメタデータサービスのアドレスへの参照です。

副作用も書いておきます。②はエージェントにできることを減らし、③はエージェントが自分で依存関係を解決するという設計の利点を捨てます。 ④は費用が増えます。 「AI エージェントに自律的にパッケージを入れさせる」という設計を採るなら、この3つの代償のどれかを払う必要があります（本記録の評価）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • AI エージェントに与えたロールの権限を、「被害の上限」として先に決めておく
    本件で資格情報の露出に至る3条件のうち、 組織が自分の判断だけで外せるのは**「実行ロールを付けているか」**である。 SDK の欠陥は次も出るが、**ロールに許した範囲は自分で決められる。** CVSS のベクタは `S:U`・`SC:N` と採点されており、 **点数を見ているだけでは、この広がりは見えない。**
    取るべき行動 **エージェント基盤ごとに「このエージェントが乗っ取られたら何が起きるか」を ロールの権限から1枚にまとめ、経営の承認事項にする。** AWS へのアクセスが要らないエージェントは**ロール無しを既定**にする。 要るものは、**サービス・リソース・条件（呼び出し元）まで書いた IAM に絞る**。 脆弱性が出た日ではなく、**エージェントを本番に出す日にこれを決める。**
  • 「修正済み」の告知を、その製品の監視をやめる根拠にしない
    本件では**1件目の修正がそのまま2件目の入口になり、 2本の公表の間隔は36日**だった。 同じメソッド・同じ欠陥種別（CWE-88）で、直し方の方針を変えないまま 列挙を細かくしたために同種の穴が残った。
    取るべき行動 **同一の部品で短期間に2件目が出た製品を「要注意」として台帳に印を付け、 次の告知まで版の追随を自動化する。** 依存関係の更新を人手の判断に委ねている場合は、 **少なくともこの印の付いた部品だけは自動追随に切り替える。** 判断の材料として、**1件目と2件目の間隔を記録に残す。**
  • エージェント基盤のログを「既定で無効のまま」本番に出さない
    CloudTrail のデータイベントと AgentCore の可観測性ログは**既定で無効**である。 本件の悪用は成功しても**普通の `pip install` の成功にしか見えない**ため、 **記録が無ければ、後から調べることすらできない。** 費用が増えるため、有効化は技術判断ではなく予算の判断になる。
    取るべき行動 **エージェント基盤を本番に出す条件に「実行内容が記録されていること」を入れる。** 費用は先に見積もり、**保存期間を短くしてでも記録は取る**という順序で決める。 「失敗したら知らせる」型の警報しか無い場合は、 **成功した実行の内容を見る警報を1本足す。**
  • 「隔離しているから安全」という説明を、資格情報の所在まで下りて検算する
    本件で **Firecracker の分離は破られていない。** それでも被害が外へ出るのは、**隔離された空間の中に 外へ効く資格情報を返す仕組みが置かれている**からである。 隔離の強さと、隔離の中に置いたものの強さは別の話である。
    取るべき行動 **サンドボックス・コンテナ・仮想環境を「安全な場所」として説明している 設計書を洗い出し、その中から到達できる資格情報・秘密・内部エンドポイントを 列挙させる。** 列挙が出てこない設計書は、**隔離の議論が資格情報の議論に下りていない。**
セキュリティ技術者への示唆
  • 今日、`bedrock-agentcore` の版と実行ロールの有無を突き合わせる
    該否は「1.18.1 未満であること」と 「実行ロールを付けたカスタムの Code Interpreter を使っていること」で決まる。 **1.6.1 へ上げただけの環境は2件目の対象に残っている。**
    取るべき行動 依存関係の固定ファイル（`requirements.txt`・`poetry.lock`・`uv.lock` 等）で **`bedrock-agentcore` の版**を確認し、 あわせて **Code Interpreter に実行ロールを付けているか**を確認する。 **両方が当たる環境だけを一覧にして、そこから作業する。** 1.18.1 以降でなければ上げる。
  • `install_packages()` へ届く文字列の出どころを、コードを追って1つずつ確かめる
    入力経路は利用者の入力欄だけではない。 **エージェントが読み込む文書やウェブページ（プロンプトインジェクション）、 リポジトリに置かれた依存関係ファイル**も同じ経路になる。 **「社内利用だから入力は信頼できる」は、この3経路のうち1つしか塞がない。**
    取るべき行動 `install_packages()` の呼び出し箇所を全部洗い、 **引数がどこから来るかを呼び出し元へ遡って書き出す。** モデルの出力が引数になっている箇所があれば、 **固定のハードコードされた一覧に置き換える**か、 **PyPI の命名規則（`^[A-Za-z0-9._-]+$` に相当する厳格な形）で検証してから渡す。**
  • 自分たちのコードでも、外部由来の文字列をシェルのコマンド行に連結していないか探す
    本件の原因は AgentCore に固有のものではなく、 **CWE-88（引数の区切り文字の不適切な無害化）**という古典である。 **拒否する文字を列挙する方式は、列挙の漏れが穴になる**—— 本件では1回目に改行が、2回目に角括弧の中身が漏れた。
    取るべき行動 リポジトリ全体で **`shell=True`・文字列連結によるコマンド生成・ `os.system`** を検索する。 見つかったら、**引数を配列で渡す形（`subprocess.run([...])`）へ書き換える**か、 **`shlex.quote()` で囲う。** **「危ない文字を弾く」実装が残っていたら、その方針自体を置き換える対象として扱う。**
  • メタデータサービスへの参照を、エージェント基盤の検知項目に足す
    BeyondTrust は **169.254.169.254 への参照、およびその符号化された形**が 手がかりになるとしている。 一方で、**失敗したツール呼び出しだけを見る監視は成功した悪用を取り逃がす。**
    取るべき行動 CloudTrail のデータイベントと AgentCore の可観測性ログを有効にしたうえで、 **サンドボックス内で実行されたコマンドの本文**を検索できるようにする。 **`169.254.169.254`・`169.254.169.254` の10進や16進の表記・ `ECS_CONTAINER_METADATA_URI` 等の環境変数名**を検知の対象に入れる。 **警報の条件を「失敗」ではなく「内容の一致」にする。**

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Amazon Bedrock AgentCore の Python SDK（`bedrock-agentcore`）を 1.18.1 未満で使っている**CVE-2026-16796 は 1.18.1 未満のすべての版に当たる。** 1件目の修正が入った 1.6.1 以降でも対象である。 版だけで該否は決まらないが、**ここが外れていれば以下は見なくてよい。**
認証・認可□ カスタムの Code Interpreter に実行ロール（IAM ロール）を付けている**コマンド実行から資格情報の露出へ進むかどうかを分ける条件である。** AWS 既定のシステムインタプリタはロールを持たないため、 仮にコマンドが走っても取り出せる資格情報が無い。 **付けている場合は、そのロールの権限がそのまま被害の上限になる。**
データの保持□ `install_packages()` の引数に、モデルの出力・利用者の入力・外部文書に由来する文字列が届きうる成立に要る1つ目の条件である。 **エージェントが読み込む文書経由のプロンプトインジェクションや、 リポジトリの依存関係ファイルも同じ経路**になるため、 「入力欄を塞いだ」だけでは外れない。

運用・監視□ エージェント基盤の警報が「ツール呼び出しの失敗」を条件にしている**本件で起きるのは「成功」である。** 失敗を条件にした警報は原理的に鳴らない。 見るべきは**実行されたコマンドの内容**である。
