INC-2026-0266Linux cBPF に Spectre-v2 の新変種

Spectre-v2 の新変種「Branch Target Reuse（BTR）」が VUSec（アムステルダム自由大学）と Scuola Superiore Sant'Anna から2026年9月29日に公表された。JIT エンジンが解放したコード領域を再利用しても CPU が古い分岐先の予測（BTB エントリ）を無効化しないため、投機的な use-after-free が成立する。Linux カーネルの cBPF JIT を的にした実証では、既定の緩和策を有効にしたままの Intel 機から root のパスワードハッシュを平均3分（Raptor Cove）・5分（Lion Cove）で読み出した。Linux は CVE-2026-64507・CVE-2026-64508 として IBPB のフラッシュを取り込み、Oracle は GraalVM のコードキャッシュ配置の無作為化を投入した。挙動は Intel・AMD・Arm の試験した全 CPU で確認されている

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年9月29日 最終更新: 2026年9月30日

2026年9月29日、VUSec（アムステルダム自由大学）と Scuola Superiore Sant'Annaの研究者が、Spectre-v2 の新変種「Branch Target Reuse（BTR、分岐先の再利用）」を公表しました。的になるのは JIT エンジン——ブラウザ・言語ランタイム・OS カーネルが実行時に機械語を生成し、使い終わったら領域を解放して作り直す仕組みです。

仕掛けは1点に尽きます。JIT がコードを解放して同じ番地に別のコードを置いても、CPU は古い分岐先の予測（BTB エントリ）を捨てていない。研究者の記述は「現代の CPU は自己書き換えの後にアーキテクチャ上のコードの一貫性を回復するが、古い間接分岐の予測エントリを必ずしも無効化しない」（原文英語）。その結果、投機実行だけが古い入口へ飛ぶ——研究者はこれを「投機的な execute-after-free」と呼んでいます。飛び先は新しいコードの、本来は入口ではない途中の位置になるため、ソフトウェア側の防御（Spectre 対策の命令列）を飛び越え、命令の境界をずらした読み方（misaligned）で別の意味の命令列を作れます。

実証は Linux カーネルの cBPF JIT に対して2本です。cBPF は eBPF と違って非特権の利用者が使えるため、攻撃面として価値があります（seccomp・ソケットフィルタ・Docker や Chrome のパケットフィルタが依存しています）。完全に更新された既定設定の Intel 機から、動作中の su プロセスのメモリを追ってroot のパスワードハッシュを読み出しました。 速度は 毎秒8バイト、所要は平均 3分（Raptor Cove）・5分（Lion Cove）。cBPF の constant blinding（定数の目隠し）を有効にした環境でも、攻撃者が制御する命令をジャンプのオフセットに埋め込む形に作り替えて、5分で同じ結果に到達しています。

ハッシュは平文のパスワードではありません。 攻撃者はこれを offline やクラウドの計算資源で解く必要があり、成否はハッシュのアルゴリズムとパスワードの強度に左右されます。

他の JIT エンジンも無傷ではありません。 Firefox の SpiderMonkey ではIntel の CPU で古い予測が平均6〜7件生き残り、毎秒36バイト（Raptor Cove）・62バイト（Lion Cove）の読み出し速度が見積られました（ブラウザでの完全な実証には至っていません）。Oracle の GraalVM では、サンドボックスの最も厳しいモードを守るメモリマスクの処理を投機的に飛び越えられましたが、GC と再コンパイルが古い予測を消すため実験では完遂していません（研究者は「この制約は本質的なものではないと思われる」としています）。

修正はソフトウェア側です。 Linux カーネルはCVE-2026-64507（x86/bugs: Enable IBPB flush on BPF JIT allocation）とCVE-2026-64508（bpf: Support for hardening against JIT spraying）として、cBPF プログラムが過去に実行された領域を再利用するときに全コアで IBPB（間接分岐予測器のバリア）を発行する緩和策を取り込みました（公開は2026年7月25日）。Oracle は GraalVM のコードキャッシュの配置を無作為化する変更を2026年8月19日に取り込みました。Mozilla は IBPB ベースの緩和策を検討したうえで、サイト分離の完成と展開を優先しています。Arm は「整列した cBPF の実行で BTR を悪用する複雑さは、新たなカーネルの緩和策を正当化しない」と回答しました（原文英語）。AMD は SecurityWeek に対し「論文は自社製品における新たな脆弱性を明らかにしていない」「記述された手法は既存の Spectre-v2 の指針で緩和される」と述べています（原文英語）。

挙動そのものは試験した全 CPU で確認されています——Intel・AMD・Arm。VUSec は「間接分岐予測は現代の CPU に固有のものであり、BTR は予測器とコードの実際の状態との非同期を突く。予測器とコードを同期させる仕組みを持つ CPU は現時点で存在しないので、ベンダーがそれを追加するまで、あなたの CPU は脆弱である」（原文英語）としています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**JIT が解放したコード領域を CPU の分岐先バッファ（BTB）が覚えたままにする**性質を突く。 攻撃者は非特権の cBPF プログラム（訓練用）を入れて対象の間接分岐をそこへ飛ばし、 **BTB にエントリを作る。** 次に**それを解放し、同じ番地に別のプログラム（標的用）を置く。** 間接分岐をもう一度踏ませると、CPU は**古い BTB エントリ**を使って **「もう存在しない入口」へ投機的に飛ぶ**（投機的な execute-after-free）。 飛び先は新しいコードの**本来の入口ではない位置**になるため、 **Spectre 対策の命令列を飛び越え、境界をずらした命令列として実行される。** 触れたデータの痕跡は **Flush+Reload** でキャッシュの時間差から読み取る。 **既定設定の Intel 機で毎秒8バイト・3〜5分で root のパスワードハッシュに到達した。** **これは研究による実証であり、現実の攻撃は報告されていない。**

  1. 1. 偵察確認済[1]
    **KASLR を破り、カーネルのアドレスを求める。** end-to-end の実証では、この後にモジュール領域の穴を埋め、 プロセスのページテーブルを辿って `su` プロセスのメモリの位置を特定する。 **読み出しが毎秒8バイトと遅いため、「どこを読むか」を先に絞る工程が要る**
    根拠: 論文の end-to-end 実証の記述（KASLR の破壊とポインタ追跡）
  2. 2. 実行確認済[1]
    **非特権の cBPF プログラム（訓練用）を登録し、対象の間接分岐をそこへ飛ばして BTB にエントリを作る。** 実証ではカーネルの cBPF のディスパッチャの 間接分岐を使っており、**訓練と悪用が同じ分岐（自己訓練）である**ため、 領域をまたいだ訓練を防ぐ既存の仕組み（eIBRS・BHI_NO）が効かない
    根拠: 論文の第5節・第7節（自己訓練であることの明記）
  3. 3. 検知回避確認済[1]
    **訓練用のプログラムを解放し、同じ番地（の一部が重なる位置）に 標的用のプログラムを置く。** BPF JIT のアロケータは 小さなプログラムを大きな割り当てにまとめて**空間を使い回す**ため、 これが成立する。**CPU は命令キャッシュを同期するが BTB は同期しない**ので、 古いエントリが残る。実証では**x86-64 で対象プールの大半、 ARM64 で97.6%**の再利用率を得ている
    根拠: 論文の第5節・第7節（BPF JIT アロケータの空間再利用と再利用率）
  4. 4. 権限昇格確認済[1]
    **間接分岐をもう一度踏ませると、CPU が古い BTB エントリを選び、 標的用のコードの「古い入口」へ投機的に飛ぶ。** 飛び先は本来の入口ではないため、 **Spectre 対策として先頭に置かれた命令列を飛び越え、 命令の境界をずらした命令列（misaligned）として実行される。** constant blinding を有効にした環境では、 **攻撃者が制御する命令をジャンプのオフセットに埋め込む**形で同じことを行った ——**「暗黙の定数」は目隠しの対象外だった**
    根拠: 論文の第7節（既定設定と constant blinding 有効時の2本の実証）
  5. 5. 収集確認済[1] [5]
    **投機実行中にアクセスした秘密のデータの痕跡を、 Flush+Reload でキャッシュの時間差から1バイトずつ読み取る。** 速度は**毎秒8バイト**。実証では動作中の `su` プロセスのメモリから **root のパスワードハッシュ**を回収した。 SpiderMonkey では Intel で平均6〜7件のエントリが生き残り、 **毎秒36バイト（Raptor Cove）・62バイト（Lion Cove）**という速度が見積られた （こちらは完全な実証に至っていない）
    根拠: 論文の第6節・第7節と BleepingComputer の記述
  6. 6. 影響（暗号化・破壊・改ざん）確認済[1] [5] [6]
    **root のパスワードハッシュが非特権の利用者に渡る。** 所要は既定設定で平均3分（Raptor Cove）・5分（Lion Cove）、 constant blinding を有効にした環境でも5分。 **得られるのはハッシュであり平文のパスワードではない**—— 攻撃者は offline またはクラウドの計算資源で解く必要があり、 成否はハッシュのアルゴリズムとパスワードの強度に左右される。 GraalVM ではサンドボックスの arena の外へ到達しうることが示された （実験では完遂せず）
    根拠: 論文の第7節・第6.3節と BleepingComputer・SecurityWeek の記述

命令キャッシュは同期されるのに、分岐先の予測は同期されないという非対称が残っていた概観出典 [1] [4] [5] [6]

JIT エンジンは、実行時に機械語を作っては捨てる仕組みです。ブラウザの JavaScript エンジン、言語ランタイム、そして Linux カーネルのBPF も同じことをします。作ったコードを置く領域は使い終わったら解放され、別のコードに使い回されます。

CPU の側から見ると、これは自己書き換えコード（SMC）です。データとして書いた領域を、後から命令として読む。そのため CPU には一貫性を回復する仕組みがあります。x86 では命令キャッシュとデータキャッシュを自動的に再同期し、ARM ではソフトウェアがキャッシュ管理の命令を発行します。これがあるから JIT は成り立ちます。

BTR が突いたのは、この一貫性の回復に含まれていなかったものです。

現代の CPU は自己書き換えの後にアーキテクチャ上のコードの一貫性を回復するが、古い間接分岐の予測エントリ（すなわち分岐先）を必ずしも無効化しない（原文英語）

つまり、命令キャッシュは同期されるのに、分岐先バッファ（BTB）は同期されない。解放されたコードの入口を指す予測が、そのコードより長生きします。新しいコードが同じ番地に置かれた後で、CPU がその古い予測を選ぶと、投機実行だけが「もう存在しない入口」へ飛びます。

研究者はこれを投機的な execute-after-free と呼んでいます。ソフトウェアの use-after-free とよく似た形ですが、原因となるソフトウェアのバグは一つも要りません。

飛び先が「本来の入口ではない位置」であることが効きます。

  • Spectre 対策としてコードの先頭に置いた命令列を飛び越えられる
  • 命令の境界をずらして読むと、別の意味の命令列になる（misaligned）

研究者は論文の要旨で「この前提を覆す」と書いています。2018年以降、SMC を使った投機実行攻撃は現実的でないと考えられてきました ——先行研究（SCSB）の攻撃の窓が極端に短かったためです。BTR はその窓をBTB の古さに置き換えました。

非特権で使える cBPF が、既定設定の Intel 機から root のハッシュを3分で渡した原因・手口出典 [1] [4] [5] [6]

実証の的は Linux カーネルの cBPF JIT です。選んだ理由が重要です。

eBPF は特権が要りますが、cBPF は非特権の利用者が使えます。そして cBPF は今も広く使われています——seccomp（システムコールの制限）、ソケットフィルタ、Docker や Chrome のパケットフィルタです。つまり攻撃者がローカルで非特権のコードを走らせられるなら、JIT エンジンへの入口があるということです。

手順は次の形です。

  1. 攻撃者が cBPF プログラム（訓練用）を入れ、対象の間接分岐をそこへ飛ばしてBTB にエントリを作る
  2. 訓練用を解放し、同じ番地に別のプログラム（標的用）を入れる
  3. 間接分岐をもう一度踏ませる。CPU は古い BTB エントリを使い、標的用のコードの「古い入口」へ投機的に飛ぶ
  4. 境界をずらした命令列として実行され、秘密のデータに触れる。触れた痕跡は Flush+Reload でキャッシュの時間差から読み取る

結果は、完全に更新された既定設定の Intel 機から毎秒8バイトです。速度は遅いのですが、研究者の指摘が的を射ています——「毎秒わずか数バイトの読み出しでも、注意深いポインタ追跡によって秘密に到達するのに必要なデータ量は少なくて済む」（原文英語）。

実際の手順は、カーネルのアドレスを求めてプロセスのページテーブルを辿り、動作中の su プロセスを見つけ、そのメモリから root のパスワードハッシュを読み出すものです。所要は平均3分（Raptor Cove）・5分（Lion Cove）。

2本目の実証がさらに重い意味を持ちます。 cBPF にはconstant blinding（JIT spraying 対策として定数を目隠しする機能）があります。研究者はこれを有効にした環境でも、攻撃者が制御する命令をジャンプのオフセットに埋め込む形に作り替え、5分でハッシュに到達しました。論文の言い方では、「暗黙の定数」を使えば目隠しは迂回できるということです。

なお得られるのはハッシュであり平文のパスワードではありません。攻撃者はこれを offline またはクラウドの計算資源で解く必要があり、成否はハッシュのアルゴリズムとパスワードの強度に左右されます（BleepingComputer の指摘）。

ブラウザとサンドボックスは「まだ完遂していない」段階にある被害規模・影響範囲出典 [1] [5] [6]

cBPF 以外の2つは、危険度が違います。 ここを混ぜると誤解します。

Firefox（SpiderMonkey）。 古い予測が領域の再利用を越えて生き残ることは実証されました。Intel の CPU で平均6〜7件が残り、そこから毎秒36バイト（Raptor Cove）・62バイト（Lion Cove）という読み出し速度が見積られました。ただし完全なブラウザの実証には至っていません——被害側の分岐の投機実行の窓を延ばす技術と、Firefox の不正確なタイマーを迂回する秘密の通信路が別途必要です。Zen 4・Cortex-A76・Cortex-X3ではエントリが1件も生き残りませんでした。

ここで効いてくるのがサイト分離（site isolation）です。Mozilla はまだ展開を完了していないため、他のタブの内容が攻撃者と同じアドレス空間に載りうる状態にあります（SecurityWeek）。Mozilla が IBPB ベースの緩和策よりサイト分離の完成を優先しているのは、これが根本的な手当てだからです。

GraalVM（GraalPy）。 こちらはサンドボックスの検査を飛び越えられることが示されました。GraalVM は最も厳しいサンドボックスのモードでソフトウェアによる分離（SFI）を使い、メモリアクセスを arena という領域内にマスクして閉じ込めます。BTR はこのマスク処理を投機的に飛び越えてarena の外を読めます。

ただし実験では完遂しませんでした——GraalVM 自身のコンパイルと GC が、使う前に古い予測を消してしまったためです。研究者の評価は「この制約は本質的なものではないと思われる」（原文英語）。つまり今できないだけで、設計上できないのではありません。

整理すると、危険度の順は次のようになります（本記録の評価）。

  • cBPF: 既定設定の Intel 機で end-to-end の実証あり。いま対処すべき
  • SpiderMonkey: 部品は揃っているが完成していない。サイト分離の進捗に依存
  • GraalVM: 経路は示されたが GC に阻まれている。緩和策は既に投入済み

ベンダーは「実証を見せろ」と言い、研究者は17か月かけて2本作った組織の対応出典 [1] [6]

開示の経過は、脆弱性の内容そのものと同じくらい読む価値があります。

2025年4月、研究者は Intel・AMD・Arm と Linux カーネルのセキュリティチームへBTR を開示しました。この時点で示したのはJIT エンジンに対する予備的な攻撃面の分析と推奨する緩和策です。

各者の反応を論文はこう記しています。

影響を受ける当事者は問題を認め、内容を非公開期間に置いたが、cBPF の constant blinding のような費用のかかる緩和策を展開する必要を正当化するために、完全な end-to-end の実証を要求した（原文英語）

研究者は応じました。2本の end-to-end の実証（うち1本は constant blinding も迂回する）を作り、他の JIT エンジンへ分析を広げ、2026年5月に共有しました。その後に Linux カーネルと Oracle が緩和策を投入しています。

緩和策の中身は次のとおりです。

  • Linux: x86 向けに、cBPF プログラムが過去に実行された cBPF/eBPF の領域を再利用するときに全コアで IBPB を発行する。CVE-2026-64507・CVE-2026-64508 として2026年7月25日に公開。IBT の有無に関わらず適用される（復帰経路のガジェットのため）
  • Oracle: GraalVM のコードキャッシュの配置を無作為化して領域の再利用を妨げる（プルリクエスト #14261・2026年8月19日）
  • Mozilla: IBPB ベースの緩和策を検討したが、サイト分離の完成と展開を優先
  • Arm: 「整列した cBPF の実行で BTR を悪用する複雑さは、新たなカーネルの緩和策を正当化しない」（原文英語）
  • ハードウェアベンダー全体: IBPB 等の緩和する仕組みは既に存在し、BTR の緩和はソフトウェア側で展開されるべき

AMD は公表後、SecurityWeek に対して「論文は自社製品における新たな脆弱性を明らかにしていない」「記述された手法は既存の Spectre-v2 の攻撃に対する指針で緩和される」と回答しました（原文英語）。Intel と Arm は同社の取材に回答していません。

最初の開示から公表まで約17か月です。 その大半は「費用のかかる対策を正当化するための実証を作る」ことに費やされました。これは研究者に立証責任が置かれたという構図であり、研究者がそこまでやらなければ緩和策は入らなかったということでもあります（本記録の評価）。

この種の欠陥は CVE を追っても見えず、ハードウェアの更新でも消えない評価・解釈出典 [1] [5] [6]

読者の実務に落とすとき、本件には扱いにくい性質が3つあります。

①CVE が指しているのは CPU ではなく Linux である。 CVE-2026-64507・CVE-2026-64508 はいずれも CNA が Linux で、対象は Linux カーネルです。CPU ベンダー側に CVE はありません。したがって「影響を受ける CPU の一覧」も存在しません。CVE の記述を読んでも「自社のどの機器が危ないか」は分かりません。分かるのは「カーネルを上げれば緩和策が入る」ということだけです。

②ハードウェアを新しくしても解決しない。研究者の結論は明快です——「予測器とコードを同期させる仕組みを持つ CPU は現時点で存在しないので、ベンダーがそれを追加するまで、あなたの CPU は脆弱である」（原文英語）。Lion Cove は IBT に競合状態が無い最初の Intel 世代であり、その点では進歩していますが、BTR そのものが消えたわけではありません（cBPF では endbr64 を JIT コードに埋め込めないため IBT は障壁を上げるものの、復帰経路を使う迂回が残ります）。

③「遅い読み出し」を軽視できない。 毎秒8バイトという数字は、1秒あたりの量としては小さいものです。しかしポインタを辿って必要な場所だけ読むという手順と組み合わせると、3分でハッシュに届きます。 速度で危険度を測る判断は、この事案では外れます（本記録の評価）。

では実務として何を見るべきか。答えは「誰が非特権のコードを走らせられるか」です。

BTR は攻撃者がローカルで非特権のコードを実行できることを前提にします。裏を返せば、それができない環境では成立しません。共用サーバー、マルチテナントのホスト、CI のランナー、利用者がスクリプトを持ち込める解析環境—— 「同じカーネルの上に、信頼の度合いが違うものが同居しているか」が判定条件です。

投機実行の脆弱性は2017年以来、「結局のところ分離しかない」という同じ結論に戻ってきています。Mozilla がサイト分離を優先しているのも、Oracle が配置の無作為化を選んだのも、同じ方向です。細かな緩和策の積み上げではなく、境界そのものを引き直すことが効く対策である、というのが本件から読み取れる一貫した含意です（本記録の評価）。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
JIT が解放した番地を CPU の予測器だけが覚えており、投機実行がそこへ飛ぶ
非特権の利用者が **cBPF の訓練用プログラム**を入れ、 対象の間接分岐をそこへ飛ばして **BTB にエントリを作る。** **訓練用を解放し、同じ番地に標的用のプログラムを置く**と、 **命令キャッシュは同期されるが BTB は同期されない**ため古いエントリが残る。 間接分岐をもう一度踏ませると、CPU は古いエントリを使って **「もう存在しない入口」へ投機的に飛ぶ**（投機的な execute-after-free）。 飛び先は本来の入口ではないので、 **Spectre 対策の命令列を飛び越え、境界をずらした命令列として実行される。** 痕跡は **Flush+Reload** でキャッシュの時間差から読み取り、 **毎秒8バイト・3〜5分で root のパスワードハッシュに到達する。** **constant blinding はジャンプのオフセットに命令を埋め込む形で迂回された。** **研究による実証であり、現実の攻撃は報告されていない。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 投機実行の脆弱性の判定条件は「誰が自社の機器で非特権のコードを走らせられるか」に尽きる
    BTR は**攻撃者がローカルで非特権のコードを実行できること**を前提にする。 リモートから無認証で成立する経路は示されていない。 つまり**共用ホスト・マルチテナント・CI のランナー・利用者がスクリプトを 持ち込める解析環境**が判定の対象であり、 **CPU の型番の一覧を待つ必要はない。**
    取るべき行動 **「同じカーネルの上に、信頼の度合いが違うものが同居している箇所」を 棚卸しして一覧にする。** これを投機実行の脆弱性が出るたびに 使い回す判定の台帳にする。新しい変種が出たときに読むのは CPU の一覧ではなく この台帳であり、**対処の優先順位はここから決まる。**
  • ハードウェアの脆弱性は CVE を追っていても見えない
    本件の CVE 2件は**いずれも CNA が Linux で、対象は Linux カーネル**である。 **CPU ベンダー側に CVE は無く、影響を受ける型番の一覧も存在しない。** CVSS の基本値も CVE レコードに記載が無い。 **「CVE と CVSS で優先順位を決める」運用では、本件は評価すらできない。**
    取るべき行動 **ハードウェア・マイクロアーキテクチャの脆弱性を、CVE とは別の経路で拾う。** 情報源として研究機関の公表（VUSec 等）とベンダーのセキュリティ情報ページを指定し、 担当と巡回の頻度を決める。判断は CVSS ではなく **「自社に非特権のコードが入る箇所があるか」**で行うと決めておく。
  • 緩和策の適用は「入れるか」ではなく「性能の代償を誰が決めるか」の問題になる
    Linux の緩和策は**全コアに対して IBPB を発行する**ものであり、 **実測の性能影響は公表されていない。** しかも本件では**ベンダー自身が「費用のかかる緩和策を展開する必要を 正当化するために完全な実証を要求した」**—— 費用と危険の秤にかける判断が、当事者の側にも存在したということである。
    取るべき行動 **投機実行の緩和策について、「性能が落ちても入れる系統」と 「測ってから決める系統」を平時に分けておく。** 分ける基準は上記の「信頼の度合いが違うものの同居」である。 seccomp のフィルタを頻繁に張り直す系（コンテナの大量起動）は **測る側**に入れ、測定の手順を先に用意する。
  • 「攻撃が遅い」ことを危険度の低さと読み替えない
    毎秒8バイトという読み出し速度は、数字としては小さい。 しかし**ポインタを辿って必要な場所だけを読む**手順と組み合わせると、 **3分で root のパスワードハッシュに届いた。** 研究者自身が「毎秒わずか数バイトの読み出しでも end-to-end の実証が作れる」と 述べている（原文英語）。
    取るべき行動 **報道の「毎秒○バイト」という数字を、そのまま経営への報告に使わない。** 報告する数字は**「目的の達成までの時間」**にする。 本件では3〜5分であり、**これは攻撃者が1回のセッションで完了できる時間**である。
セキュリティ技術者への示唆
  • JIT が解放した領域を再利用するとき、CPU の予測器は同期されていないと前提する
    BTR の根は「**命令キャッシュは同期されるが BTB は同期されない**」という 非対称である。研究者は「予測器とコードを同期させる仕組みを持つ CPU は 現時点で存在しない」（原文英語）と述べている。 **ソフトウェアのバグを一つも必要としない**ため、 コードレビューでは見つからない。
    取るべき行動 **自前で実行時にコードを生成・解放する仕組みを持っている場合 （JIT・動的なトランポリン・実行可能領域の使い回し）、 「解放した領域を同じ番地に使い回すか」を確かめる。** 使い回す設計なら、**再利用の前に予測器をフラッシュする**か、 **配置を無作為化して再利用を妨げる**（GraalVM の方式）。 領域を使い回さないことがいちばん簡単な対処である。
  • constant blinding のような「定数を隠す」対策は、暗黙の定数で迂回される
    cBPF の constant blinding は JIT spraying に対する主要な緩和策だが、 研究者は**ジャンプのオフセット**という暗黙の定数に 攻撃者が制御する命令を埋め込み、**5分で同じ結果**に到達した。 論文は同じ考え方が**配列添字のマスク**にも当てはまるとしている。
    取るべき行動 **「攻撃者が値を制御できる場所」を、明示的な定数だけで数えない。** JIT が生成するコードでは**ジャンプのオフセット・アラインメントの詰め物・ 即値の一部**も攻撃者の制御下に入りうる。 自前のハードニングを設計するときは、 **生成されたバイト列全体を攻撃者が影響を与えられる入力として扱う。**
  • IBT／BTI は障壁を上げるが、投機の窓を消すわけではない
    研究者の評価では、**Lion Cove が IBT に競合状態の無い最初の Intel 世代**であり、 それ以前の世代は **endbr64 の検査の前に1命令を投機実行できる。** その1命令で BTB にエントリを注入でき、別の間接分岐を訓練できる。 競合状態が無い世代でも、**JIT コードに endbr64 を埋め込めれば迂回が残る。**
    取るべき行動 **IBT／BTI を「有効にしたから済んだ」とは扱わない。** 既定で無効な環境（Ubuntu は既定で無効）ではまず有効化を検討し、 そのうえで**競合状態の無い IBT と constant blinding の併用**を目標にする。 どちらも「本質的な対策ではない」と論文が明記していることを前提に、 **分離（サイト分離・ホストの分離）を本筋の対策として計画する。**
  • cBPF を「古い仕組み」として視界から外さない
    eBPF は特権が要るが、**cBPF は非特権の利用者が使える。** しかも **seccomp・ソケットフィルタ・Docker や Chrome のパケットフィルタ**が 今も cBPF に依存している。 **本件で最も危険な経路が cBPF だったのは、 「古い」ことと「攻撃面として現役」であることが両立していたため**である。
    取るべき行動 **自社の機器で BPF JIT が有効かどうか（`net.core.bpf_jit_enable` 等）を棚卸しし、 カーネルの版と併せて記録する。** そのうえで CVE-2026-64507・CVE-2026-64508 の修正が入った版へ上げる。 **seccomp を止める形の回避は選ばない**—— より大きな危険を招く。
