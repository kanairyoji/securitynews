INC-2026-0267SailPoint IdentityIQ に無認証RCE

SailPoint が2026年9月28日、アイデンティティガバナンス製品 IdentityIQ に**認証不要の遠隔コード実行**の脆弱性 CVE-2026-12342（CWE-20）を公表した。ウェブサービス API へ送られた内容の入力検証が不十分で、**認証を経ていない者が IdentityIQ サーバ上でコードを実行できる**。CVSS v3.1 基本値は **9.6（Critical）**、ベクタは `AV:A/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H` で、**攻撃元区分は隣接ネットワーク（AV:A）だが権限も利用者操作も要らず、影響範囲の変化（S:C）が付いている**。対象は「IdentityIQ の全バージョン」で、8.5 は 8.5p2 まで・8.4 は 8.4p4 まで・8.3 は 8.3p5 まで、およびそれ以前の全バージョン。修正は **IIQSR-983** で「影響を受けるサポート対象の各バージョンに対して」提供された。回避策・発見者・悪用の有無はいずれもアドバイザリに記載がない。本記録の作成時点で CISA KEV（カタログ 2026.09.29）に未収載、NVD の解析状況は `Received` のまま

初報: 2026年9月28日 最終更新: 2026年9月30日

2026年9月28日、SailPoint はセキュリティアドバイザリ「SailPoint IdentityIQ Improper Form Validation Vulnerability – CVE-2026-12342」を公表し、アイデンティティガバナンス製品 IdentityIQ に認証不要の遠隔コード実行（RCE）の脆弱性があることを明らかにしました。

記述は短く、次の一文です（原文英語）。

この脆弱性は IdentityIQ の全バージョンに影響し、提出されたウェブサービス API の内容に対する不適切な入力検証に起因して、認証されていない利用者が IdentityIQ サーバ上で遠隔コード実行を行うことを可能にする。

ベクタを分解すると、成立の前提がきわめて軽いことが分かる。

要素 値 意味
AV:A 隣接ネットワーク 同一の論理ネットワーク上にいる必要がある
AC:L 低 特殊な条件は要らない
PR:N 権限不要 アカウントも認証も要らない
UI:N 利用者操作不要 誰かにクリックさせる必要もない
S:C 影響範囲の変化 脆弱な部品の外へ影響が及ぶ
C:H／I:H／A:H いずれも高 機密性・完全性・可用性のすべてに全面的な影響

PR:N と UI:N が同時に付いた RCE は、事前条件がほぼ無いということである。フィッシングも認証情報の窃取も要らない。API に到達できさえすれば成立する。

唯一の制約が AV:A（隣接ネットワーク）である。そしてこの1点が、本件の実務上の深刻度を決める。AV:A は「攻撃者がすでに同じネットワークにいる」という条件だが、これは侵入の途中段階として日常的に成立する状態である（本記録の評価）。フィッシングで従業員の端末を1台取った攻撃者は、その時点で「隣接ネットワーク」にいる。

なお、同じベクタで AV:A を AV:N に変えると基本値は 10.0 になる（本記録の作成者による算出）。9.6 という数字は、AV:A による減点をS:C が押し戻した結果である。SailPoint が AV:A を選んだ理由は説明されていない。

IdentityIQ はアイデンティティガバナンス・管理（IGA）の製品である。役割は、人事システム・ディレクトリサービス（Active Directory／LDAP）・クラウドサービス・業務アプリケーションを横断して、誰がどの権限を持つかを棚卸しし、申請と承認を通して払い出し、退職時に剥奪することにある。この役割を果たすために、IdentityIQ は構造上次のものを抱える。

  • 接続先システムごとの特権アカウント（コネクタが各システムへ読み書きするための資格情報）
  • 全従業員・全権限の一覧（誰がどこに何の権限を持つかの写像）
  • 権限を付与・剥奪する実行権限（ワークフローによる自動プロビジョニング）

つまり IdentityIQ サーバ上でコードが実行できる状態は、接続先システム群への到達手段と、権限を自分に付与する能力を同時に得る状態である。CVSS の S:C（影響範囲の変化——脆弱な部品の外へ影響が及ぶ）が付いているのは、まさにこの構造を反映している。

ここから導かれる実務上の帰結が2つある。

  1. 「認証基盤の脆弱性」は、認証で守れない。 多要素認証を全社に入れていても、PR:N（権限不要）の脆弱性には効かない。認可の強化も効かない。効くのは到達性の制限とパッチだけである。
  2. 侵害された場合の調査が難しい。 IdentityIQ は正規の手段として権限を付与・変更する。攻撃者が IdentityIQ を通して権限を付けた痕跡は、接続先システムのログでは正規のプロビジョニングと区別が付きにくい。IdentityIQ 側の監査ログが保存され、外部へ転送されているかが分かれ目になる。

なお、アドバイザリはこうした影響の評価を一切書いていない。上記は本記録の作成者による整理であり、SailPoint が公表した内容ではない。

  1. IIQSR-983 を適用する。 唯一の根本対処である。
  2. IdentityIQ のウェブサービス API がインターネットから到達できないことを実測する。 AV:A という評価の前提そのものであり、成立していなければ実効的な深刻度は AV:N（10.0 相当）で読むべきである。

  4. IdentityIQ のコネクタが各システムで持つ権限を棚卸しし、最小化する。 RCE が成立した後の影響範囲を決めるのはこの権限である。
  5. IdentityIQ の監査ログを外部へ転送し、権限付与の経路を可視化する。侵害された場合、接続先システムのログでは正規のプロビジョニングと区別が付きにくい。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
隣接ネットワークからの無認証の要求が IdentityIQ サーバでのコード実行になり、接続先システム群へ及ぶ経路
layer 0 は攻撃者と、AV:A（隣接ネットワーク）という前提が満たされる状態。 layer 1 は IdentityIQ のウェブサービス API と入力検証の不備。 layer 2 は IdentityIQ サーバが抱えるもの（コネクタの資格情報・権限の写像・ 権限付与の実行権限）。layer 3 は影響が及ぶ接続先システム群で、 CVSS の S:C（影響範囲の変化）が指す範囲にあたる。layer 4 は公表の経路。 **脆弱なエンドポイントとパラメータは公表されていないため、 layer 1 の内訳は示せない。** layer 2・layer 3 の項目は IdentityIQ が アイデンティティガバナンス製品として一般に持つ構造として示したものであり、 本脆弱性で到達できると公表された範囲ではない（本記録の整理）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • アイデンティティ基盤そのものを、最上位の保護対象として台帳の先頭に置く
    IdentityIQ は接続先システムごとの特権アカウント、全従業員・全権限の写像、 権限を付与・剥奪する実行権限を構造上まとめて抱える。 本脆弱性の CVSS に S:C（影響範囲の変化）が付いているのは、 壊れたときに影響が製品の外へ及ぶことを反映している
    取るべき行動 IGA・IdP・特権アクセス管理（PAM）・ディレクトリサービスを「他の業務システムと 同じ列」で管理している台帳を分ける。これらについては、 パッチ適用の目標日数・到達性の制限・監査ログの転送先・ 侵害時の切り離し手順を個別に定め、経営として承認する
  • 「認証を固めた」ことが、認証基盤の脆弱性には効かないと理解する
    本脆弱性は PR:N（権限不要）・UI:N（利用者操作不要）である。 多要素認証・条件付きアクセス・特権の分離といった投資は、 認証の前段で成立する脆弱性に対して何も効かない。 効くのは到達性の制限とパッチだけである
    取るべき行動 セキュリティ投資の説明資料で、「認証強化」が守る範囲と守らない範囲を 明示的に分けて書く。IGA・IdP 自体の脆弱性については、 パッチ適用の所要日数と到達性の制限状況を別指標として経営に報告する
  • ベンダーが CVSS を付けた脆弱性は、値ではなくベクタの前提で判断する
    本件の 9.6 は AV:A（隣接ネットワーク）という前提での値であり、 AV:N なら 10.0 になる。しかも API がインターネットから到達できるかどうかは 製品ではなく自組織の構成で決まる。加えて同製品の CVE-2026-12341 では、 ベンダー評価 8.8 に対し NVD が 9.8 を付けており、評価は動く
    取るべき行動 脆弱性対応の判断基準を「CVSS の数値」から「ベクタの前提が自組織で 成り立っているか」に書き換える。とくに AV・PR・UI の3要素について、 自組織の構成に当てはめた再評価を担当者に求める手順にする
  • サポート終了バージョンの存在を、脆弱性公表時点で即答できる状態にする
    アドバイザリは「全バージョンが影響を受ける」としながら、修正は 「サポート対象の各バージョン」に提供したとしている。 どのバージョンがサポート対象かの一覧は示されておらず、 差分にあたる組織は修正を入手できない可能性がある
    取るべき行動 重要システムについて、現在のバージョンとベンダーのサポート終了日を 台帳の列に持ち、四半期ごとに更新する。サポート終了が近いものは、 脆弱性公表を待たずにバージョンアップの予算と時期を確保する
  • パッチの識別子とバージョン番号が一致しない製品は、適用記録で管理する
    本件の修正は IIQSR-983 という社内識別子で示され、 適用後のパッチレベル番号（8.5p3 等）は公表されていない。 「版数が上がったか」では適用完了を判定できない
    取るべき行動 脆弱性対応の完了報告の様式を「対象システム数／適用済み数」で統一し、 判定根拠の列に「版数」か「ベンダー識別子の適用記録」かを明記させる。 版数で判定できない製品を一覧化し、代替の判定方法を決めておく
セキュリティ技術者への示唆
  • IdentityIQ のウェブサービス API の到達性を、外部と内部の両方から実測する
    CVSS の AV:A（隣接ネットワーク）という前提が自組織で成り立っているかは、 構成図ではなく実測でしか分からない。インターネットから到達できるなら 実効的な深刻度は AV:N（10.0 相当）である。 社内からの到達範囲も、全端末セグメントから届くなら前提として広すぎる
    取るべき行動 自社の公開 IP レンジに対する外部からのポートスキャンと、 利用者端末セグメント・拠点網・VPN の各起点から IdentityIQ の API ポートへの到達性を実測する。到達できた経路を一覧にし、 業務上必要なものだけを残して残りを塞ぐ
  • IIQSR-983 を適用し、適用の事実を版数以外の方法で記録する
    アドバイザリは修正を IIQSR-983 として示すのみで、 適用後のパッチレベル番号を公表していない。 「今後のパッチレベルには含まれる」とあるため、 後日のパッチ適用でも解消するが、現時点では判定基準がない
    取るべき行動 IIQSR-983 を適用し、適用日・対象インスタンス・適用者を構成管理の記録に残す。 検証環境で先に適用し、SCIM 連携・アグリゲーション・ ワークフローによるプロビジョニングが従来どおり動くことを確認してから本番に入れる
  • IdentityIQ のコネクタが各接続先で持つ権限を洗い出し、最小化する
    RCE が成立した場合、攻撃者が最初に手にするのは IdentityIQ が保持している 接続先ごとの資格情報である。脆弱性を塞ぐことと、 塞ぐ前に成立した場合の影響範囲を小さくすることは別の作業である
    取るべき行動 接続先システムごとに、コネクタアカウントの権限を 「属性の読み取りのみ」「特定 OU への書き込みのみ」といった単位まで絞る。 ドメイン管理者相当の権限をコネクタに与えている接続先を先に洗い出し、 優先して置き換える
  • IdentityIQ の監査ログを外部へ転送し、申請の無い権限付与を検出できるようにする
    IdentityIQ は正規の手段として権限を付与するため、 接続先システムのログでは攻撃者による付与と正規のプロビジョニングの 区別が付きにくい。IdentityIQ 側の記録が唯一の手がかりになる
    取るべき行動 IdentityIQ の監査ログとアプリケーションサーバのログを ログ収集基盤へ転送する。「申請・承認の記録が無い権限付与」 「特権グループへの追加」を突き合わせる検出を作り、 アラートの宛先を IGA の運用担当と SOC の双方にする
  • CPE が付いていない CVE を、スキャナ任せにしない運用にする
    NVD 上の本 CVE の解析状況は2026年9月30日時点で Received であり、 CPE（機械可読な製品識別子）が付与されていない。 CPE 照合に依拠する資産管理・脆弱性スキャンの仕組みは、 この状態では本 CVE を自組織の資産に結び付けられない
    取るべき行動 重要システムについては、ベンダーのアドバイザリ一覧を直接購読する経路を作る （SailPoint の場合は Security Advisories ページ）。 スキャナの検出結果が0件であることを「該当なし」と記録せず、 NVD の vulnStatus が Analyzed になっているかを確認する手順を足す

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ SailPoint IdentityIQ を自社設置型（オンプレミスまたは自社管理のクラウド基盤上）で 運用しており、バージョンが 8.5p2／8.4p4／8.3p5 以下、 または IIQSR-983 を適用していないアドバイザリの対象は「IdentityIQ の全バージョン」である。 認証も利用者操作も要らずに IdentityIQ サーバ上でコードを実行される可能性がある。 SaaS の Identity Security Cloud は本アドバイザリの対象ではない
システム構成□ IdentityIQ のウェブサービス API が、インターネットから、 あるいは利用者端末セグメントを含む広い社内ネットワークから到達できる （到達性を実測で確認していない場合も該当とみなす）CVSS の AV:A（隣接ネットワーク）という前提は、自組織の構成で成り立っているとは限らない。 インターネットから到達できるなら実効的には AV:N（同ベクタで 10.0 相当）であり、 端末セグメントから届くなら「端末1台の侵害」が RCE の前提条件を満たす
認証・認可□ IdentityIQ のコネクタアカウントに、接続先システムでのドメイン管理者相当、 あるいは広範な書き込み権限を与えているRCE 成立後に攻撃者が手にするのは、IdentityIQ が保持している接続先ごとの資格情報である。 この権限の強さが、脆弱性1件の影響がどこまで広がるかを決める
運用・監視□ IdentityIQ の監査ログ・アプリケーションサーバのログを外部の収集基盤へ転送しておらず、 申請・承認の記録と実際の権限付与を突き合わせる仕組みがないIdentityIQ は正規の手段として権限を付与するため、接続先システムのログでは 攻撃者による付与と正規のプロビジョニングが区別しにくい。 IdentityIQ 側の記録が無ければ、侵害されたかどうかを後から判定できない
体制・契約□ IdentityIQ のバージョンがベンダーのサポート期間を終えている、 またはサポート終了日を把握していないアドバイザリは影響を「全バージョン」としながら、修正の提供を 「サポート対象の各バージョン」に限定している。 差分にあたる場合、IIQSR-983 を入手できるかが公表資料からは判断できない
運用・監視□ 脆弱性の検知を CPE 照合型のスキャナに依存しており、 ベンダーのアドバイザリ一覧を直接購読する経路がないNVD 上の本 CVE は2026年9月30日時点で Received（CPE 未付与）である。 CPE が付くまでスキャナは本 CVE を自組織の資産に結び付けられず、 検出結果0件が「該当なし」と誤読される
