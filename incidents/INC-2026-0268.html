INC-2026-0268Star Blizzard が偽招待で100組織超

Microsoft Threat Intelligence が2026年9月29日、ロシア FSB 第18センター配下とされる Star Blizzard の2026年の活動を公表した。**標的型のスピアフィッシングから、1回のキャンペーンで数十〜数百通を送る大量配信へ移り**、**2026年1月以降に少なくとも13件**のキャンペーンを実施、**100を超える組織に影響**した（主に米国と英国）。**3月以降は侵害した WordPress・cPanel サイト上に作ったアカウントを送信元に使う**（Microsoft は「高い確度」で同グループによる侵害と評価）。配送手法は ClickFix から **RedFlick** へ変わり、**利用者の操作は1回で済む**。PDF を装った LNK と MSI が「Internet Quality Test Connection」等の**正規の通信部品を装ったスケジュールタスク**を作り、Python 製バックドア **CosmicPulse** を導入する。誘い文句は **Chatham House・Atlantic Council・IISS** 等を主催者に見せかけた非公開会合への招待で、**ウクライナ支援に関わる NGO・シンクタンク・政府・金融機関**が狙われた。**CosmicPulse の導入が確認されたのは「少なくとも1件」で、実際に侵害された組織数は公表されていない**。日本の組織が標的になったという記載はない

脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）公表されていない／不明

Microsoft の説明は次のとおりです（原文英語）。

2026年、Microsoft は Star Blizzard が、もっぱら標的を絞ったスピアフィッシング作戦から、より大規模なフィッシングキャンペーンも行うように移行したことを観測した。大規模なフィッシング作戦は、これまでこのアクターでは見られなかった規模で観測され、1キャンペーンあたり数十通から数百通のメールに及んだ。

誘い文句は「非公開会合への招待」です。 Chatham House・Atlantic Council・IISS・USUBC といった実在のシンクタンク・NGO を主催者に見せかけた、非公開の円卓会議や戦略対話への招待が中心でした。1月・2月はウクライナのUkr.net 利用者に対する税務調査の通知・罰金の引き落とし通知、7月はキーウのホテルへの断水のお知らせ、8月は国際金融機関の職員への支払通知と、地域と業種に合わせて使い分けられています。

感染の流れも「返信させる」ことを前提に組まれています。 初報のメールには添付が無く、受信者が返信すると、パスワード付きの RAR または ZIP が送られます。パスワードはメール本文の画像として渡されます（文字列ではないため、添付の自動検査を通りにくい）。書庫の中身は PDF を装った LNK ファイルで、開くと MSI が導入され、「Internet Quality Test Connection」「Network Configuration Manager」「System Health Monitor」という、正規の通信部品のような名前のスケジュールタスクが作られます。最終段は Python 製のバックドア CosmicPulse です。

数え方に注意が必要です。 Microsoft が述べたのは「100を超える組織に影響した」ことであり、侵害された組織の数は公表されていません。 CosmicPulse の導入が確認されたと明記されているのは「少なくとも1件の事案」です。

ここでは、Microsoft の報告本文と CISA ら5か国の共同勧告（2023年）を直接取得して確認できた範囲に、The Hacker News・CyberScoop の報道で補える点を加えて整理します。日本の組織が標的になったという記載は、いずれの資料にもありません。

RedFlick は利用者の操作を1回に減らした——ClickFix との違いはそこにある評価・解釈出典 [1] [3]

Microsoft は RedFlick の位置づけをこう説明している（原文英語）。

この手法は、CosmicPulse を導入できるようになるまでに被害者が複数の操作を完了する必要があった、同アクターの従来の ClickFix ベースの感染連鎖からの顕著な departure である。対照的に、RedFlick の感染の流れは利用者の操作を1回しか必要とせず、侵害の過程における摩擦を減らしている。

ClickFix（2025年） は偽の CAPTCHA ページで、被害者自身にコマンドを貼り付けて実行させる手法だった。つまり「①ページを開く ②指示を読む③コマンドをコピーする ④実行する」の4段が要る。

RedFlick では、パスワード付き書庫を展開したあと、PDF を装った LNK を1回開くだけで連鎖が始まる。

ここが防御の設計に直接効く（以下は本記録の評価）。

  • 利用者教育の効き方が変わる。 ClickFix は「知らないコマンドを自分で実行させられる」形なので、「コマンドを貼らない」という1行の教育が効いた。RedFlick は「添付を開く」だけであり、日常の業務動作と区別が付かない。
  • 摩擦の削減は成功率の向上を意図している。 Microsoft 自身が「より多くの標的に到達し、検知を回避し、侵害成功の可能性を高める能力を改善するとみられる」と述べている。大量配信と操作1回の組み合わせが、本件の設計意図である。
  • 一方で、パスワードを画像で渡す設計は依然として返信を必要とする。初報のメールには添付が無い。返信するまで、悪性の中身は届かない。つまり「見知らぬ招待に返信しない」という1点が、依然として最初の分かれ目である。

パスワードをメール本文の画像として渡す点も意図的である。文字列でないため、添付書庫を自動で展開して中身を検査する仕組みが働きにくい（本記録の評価）。Microsoft が公開した例ではLiveCrown8142（6月）・LiteRaspberry9415（7月）・BirdMouseCrab（8月）というパスワードが使われている。

感染連鎖は「正規の Windows 機能を正規の名前で使う」——スケジュールタスク名が最も具体的な手がかりである原因・手口出典 [1] [3]

Microsoft は感染連鎖の変種を3系統に分けて説明している。

① 1月〜3月（VHDX 変種）

  1. パスワード付き ZIP の中に VHDX（仮想ディスク）が入っている
  2. VHDX の中身は、PDF を装った悪性 LNK ＋ BAT スクリプト ＋ 囮の PDF
  3. LNK が conhost.exe（ウィンドウを隠して）→ cmd.exe → BAT を実行
  4. BAT が囮の PDF を開き、SSH.exe を PermitLocalCommand 有効で呼び出す
  5. SSH が攻撃者のサーバから MSI を取得
  6. MSI がスケジュールタスクを作成し、control.exe で遠隔のCosmicPulse ダウンローダ（コントロールパネル項目 CPL を装う）を取得・実行

② 4月（3つのスケジュールタスク）

タスク名 役割
Internet Quality Test Connection 端末名と利用者名を UTF-16／Base64 で符号化して C2 へ送る。WebDAV の UNC パス経由で Shell32.dll の Control_RunDLL を使い遠隔 DLL を実行
Network Configuration Manager 補助タスク。net.exe を呼んで WebDAV リダイレクタの処理を有効化する
System Health Monitor control.exe でハードコードされた C2（103.245.213[.]217）にアクセスし次段を実行

③ 7月（PDF にコマンドを隠す変種）

  1. ZIP の中にパスワード付き RAR、その中に LNK
  2. LNK が conhost ＋ curl で攻撃者のサーバから PDF を取得
  3. PowerShell が PDF 内のマジックヘッダ「cAB」を探し、208 バイトの Base64 符号化データを取り出す
  4. 復号したコマンドが第2の MSI を取得
  5. MSI がさらに2つのタスク（補助タスクと CPL ダウンローダ）を作成

最終段（CosmicPulse）

  • ダウンローダが ZIP 2つをディスクに落とす
  • HKEY_CURRENT_USER\Software\Classes\.mollis レジストリに暗号化された AES 鍵を書き込む
  • ZIP①は Python 3.8（64ビット）と起動器、ZIP②は暗号化された CosmicPulse 本体
  • 起動器がレジストリから鍵を読み、埋め込みの AES-ECB 鍵で復元し、CosmicPulse（別名 YESROBOT）を復号する
  • このダウンローダは、以前の報告で NOROBOT／BAITSWITCH と呼ばれていたものである（The Hacker News）

ここから読める設計方針は1つである。 LNK・MSI・スケジュールタスク・conhost.exe・control.exe・net.exe・curl・SSH.exe・WebDAV・Python—— 使われているものはすべて Windows の正規の機能か、正規に配布される実行ファイルである。悪性であることを示すのは、それらの組み合わせと名前でしかない（本記録の評価）。

したがって最も具体的で、検索に書ける手がかりはスケジュールタスク名になる。「Internet Quality Test Connection」「Network Configuration Manager」「System Health Monitor」——いずれも Windows の正規のタスク名ではない。 Microsoft の Defender 検知名はTrojan:Script/RedFlick・Backdoor:Script/CosmicPulse・Backdoor:Python/CosmicPulse である。

公開されたハンティングクエリは7日しか遡らないが、キャンペーンは9か月続いている対策・注意喚起出典 [1] [3]

本件で最も実務的な落とし穴はここである。

Microsoft が公開した Defender XDR 向けのハンティングクエリは3本（conhost／curl の検出、SSH の PermitLocalCommand、スケジュールタスク）で、いずれも 7d（過去7日間）で書かれている。 Microsoft Sentinel 向けのクエリは 30d である。

一方、キャンペーンは 2026年1月から続いている。公表（9月29日）までの期間は約 271日（本記録の作成者による算出）。

期間
公開クエリの遡及（Defender XDR） 7日
公開クエリの遡及（Sentinel） 30日
実際に遡るべき期間 約271日（1月〜9月）

The Hacker News はこの点を明示している—— Defender の Advanced Hunting は生データを最長30日保持するため、1月まで遡るにはより長期のログ保管（例: Microsoft Sentinel）が必要になる。

つまり、クエリをそのまま実行して0件だったことは「該当なし」を意味しない（本記録の明示）。やるべきことは次の2段である。

  1. クエリの期間を延ばして実行する。
  2. 延ばせなかった場合、それを「記録の保存期間が届かなかった」として記録する。届かないという結果そのものが、自組織の検知能力についての答えになる。

検知に使える材料を、遡りやすい順に並べると次のようになる（本記録の評価）。

  • スケジュールタスク名の3つ——文字列で検索でき、正規のタスク名と衝突しない。端末側の設定として残るため、過去のログが無くても現在の状態を調べられる。これが最も費用の安い確認である。
  • HKEY_CURRENT_USER\Software\Classes\.mollis レジストリの存在——同じく現在の状態として調べられる。
  • 公開された C2 ドメイン・IP への外向き通信——プロキシ・ファイアウォールの記録から探せる。公表時点で secure-dns-hub[.]com は現用中とされている。
  • SSH.exe の外向き接続——業務で使わない組織では強い手がかりになる。The Hacker News は「業務上不要な外向き SSH 接続を遮断または制限する」ことを挙げている。
  • PDF を装った LNK の実行、書庫からの LNK 実行—— Microsoft の検知名に対応する挙動である。

一方で、クエリを延ばしても拾えない層がある。 8月中旬のステガノグラフィは「識別子を隠すため」とだけ述べられており、媒体も方式も公表されていないため検知を設計できない。また、送信元として使われた WordPress・cPanel サイトのドメインは痕跡表に含まれていないため、自組織のサイトが送信元に使われていないかを痕跡で確認する手段が無い（本記録の整理）。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
初報メールへの返信を起点に、正規の Windows 機能だけで CosmicPulse に至る経路
layer 0 は攻撃者と、なりすまされた組織・送信元として侵害されたサイト。 layer 1 は2段のメール（初報は添付なし／返信後にパスワード付き書庫）。 layer 2 は端末上の実行連鎖（LNK → MSI → スケジュールタスク）。 layer 3 は C2 とバックドア本体。layer 4 は帰属と報告の経路。 **赤の分かれ目は layer 1 の「返信」である**—— 初報のメールには悪性の中身が無く、返信しなければ書庫は届かない（本記録の評価）。 **CosmicPulse が何を収集・持ち出したのかは公表されていないため、 layer 3 の先は描けない。** また侵害された送信元サイトのドメインは 痕跡表に含まれていないため、その経路は痕跡で追えない。

検知できた「署名があるから安全」を検知の前提から外す　`conhost.exe`・`control.exe`・`net.exe`・`curl`・`SSH.exe`・ Python インタプリタはすべて正規の実行ファイルである。 署名の有無ではなく**呼び出しの連鎖**で判断する必要がある（本記録の評価）
影響を限定できたネットワーク保護と Microsoft Edge の SmartScreen を有効にする　Microsoft が推奨として挙げた設定
C2通信検知した

検知できた公表された16ドメイン・6 IPv4 に加え、本文中の 103.245.213[.]217 も遮断・検索の対象に含める　**痕跡表と本文で網羅範囲が違う。** 表だけを自動取り込みすると 103.245.213[.]217 が漏れる（本記録の評価）
検知できた外向き通信の記録を、少なくともキャンペーンの開始時期（2026年1月）まで遡れる保存期間で持つ　**公開クエリの遡及は7日（Sentinel は30日）である。** 届かない場合は「届かなかった」ことを記録する（本記録の評価）
影響を限定できた侵害が確認された端末は再構築し、その端末から到達できた範囲の資格情報を入れ替える　CosmicPulse が何を収集・持ち出したのかは公表されていないため、 駆除では影響範囲を確定できない（本記録の評価）
認証情報アクセス機会はあったが検知できず
**多要素認証が入っていても止まらない段である。** AiTM でセッションクッキーを盗まれた場合、認証は正しく行われるため サインインの成否だけでは区別が付かない。 手がかりは**サインイン元の異常・セッションの再利用・ メール転送規則の追加**の側にある（本記録の評価）
侵入を防げたフィッシング耐性のあるサインイン方法（FIDO2／証明書ベース／パスキー）へ移行する　Microsoft が推奨として明示した設定であり、 **AiTM に対して実効性のある唯一の対策である**（本記録の評価）。 全社一斉の移行は困難なため、標的像に当たる部門（国際政策・外交・ ウクライナ関連の研究）から先に入れるべきである

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「100組織超に影響」と「侵害された組織数」を混ぜて報告しない
    Microsoft が述べたのは「影響した（affect）」100超であり、 CosmicPulse の導入が確認されたと明記されたのは「少なくとも1件の事案」だけである。 この2つを混ぜると、経営への報告で脅威の規模を過大に、 あるいは自組織の確認作業の必要性を過小に伝えてしまう
    取るべき行動 脅威情報を経営に上げる様式に「標的とされた数／影響を受けた数／ 侵害が確認された数」の3欄を設け、公表資料で埋まらない欄は空欄のまま 「公表されていない」と記す。報道の見出しの数値をそのまま転記しない
  • 標的像を「国籍」ではなく「関わっている問題」で自組織に当てはめる
    Microsoft が示した標的は「ウクライナを政治的・財政的に支援してきた 国際 NGO・西側シンクタンク・政府・金融機関」であり、国籍で書かれていない。 標的には現職・元職の外交職員、多国間組織、国際金融機関の職員が含まれる。 **一方で、日本の組織が標的になったという記載はどの資料にも無い**
    取るべき行動 自組織の部門・プロジェクトのうち、ウクライナ関連の政策・支援・復興、 国際安全保障、多国間の金融・国際機関との関わりを持つものを一覧にする。 その一覧を、フィッシング耐性認証の導入順序と注意喚起の宛先の優先順位に使う。 **「日本は標的になっていない」を根拠に先送りしない**
  • 大量配信への移行は「自組織が名簿に載る確率」を上げたと理解する
    従来の Star Blizzard は標的を絞ったスピアフィッシングだった。 2026年は1キャンペーンあたり数十〜数百通の大量配信に移り、 少なくとも13キャンペーンが行われている。 Microsoft は大量配信基盤の採用によって「初期の標的候補を大幅に広げた」と評価している
    取るべき行動 「うちは国家系アクターの標的になるほど重要ではない」という前提で 決めていた投資水準を見直す。とくに**初報メールへの返信という 人の行為が起点である**ため、注意喚起の対象を経営層・研究者だけでなく 秘書・広報・総務など外部からの連絡を日常的に受ける部門へ広げる
  • 脅威情報に付いてくる「遡及期間」を、自組織のログ保管期間と突き合わせて予算判断する
    Microsoft が公開したハンティングクエリは7日（Sentinel 向けは30日）しか遡らないが、 キャンペーンは2026年1月から約271日続いている。 ログを保管していない組織は、クエリを渡されても実行できない
    取るべき行動 主要な脅威情報が公表されてから何日ぶんを遡る必要があったかを、 過去1年ぶん振り返って数える。その日数を満たすログ保管期間を 費用とあわせて経営判断の材料にする。 **「遡れなかった」ことを対応記録に残す運用**を先に決める
  • 自組織のウェブサイトが「攻撃者の送信元」になりうることを、リスク一覧に入れる
    2026年3月以降、Star Blizzard は侵害した WordPress・cPanel サイト上に アカウントを作ってフィッシングメールを送っている。 Microsoft は「高い確度で」同グループによる侵害と評価している。 **被害は自組織のデータではなく、自組織の名前と信用である**
    取るべき行動 管理外になっているキャンペーンサイト・イベントサイト・旧サイトを棚卸しし、 CMS のバージョン・管理者アカウント・メール送信機能の有効無効を確認する。 **メール送信が不要なサイトでは送信機能を止める。** SPF／DKIM／DMARC を自社の全ドメインに設定し、DMARC のレポートを実際に読む
セキュリティ技術者への示唆
  • まず3つのスケジュールタスク名と .mollis レジストリを全端末で検索する
    「Internet Quality Test Connection」「Network Configuration Manager」 「System Health Monitor」はいずれも Windows の正規のタスク名ではなく、 `HKEY_CURRENT_USER\Software\Classes\.mollis` も正規のものではない。 **端末の現在の状態として残るため、ログの保存期間に依存せず調べられる。** 公開クエリが7日しか遡らない問題を回避できるのはこの層だけである
    取るべき行動 端末管理の仕組み（Intune・構成管理ツール・EDR のライブ応答）で 全端末のスケジュールタスク一覧と当該レジストリキーの有無を収集し、 3つの名前を文字列で照合する。**端末管理が届いていない端末 （個人所有・退職者・長期不在者）を先に洗い出し、別途確認する**
  • 公開された痕跡は「表」だけでなく本文からも拾う
    4月の変種の説明に出てくるハードコードされた C2（103.245.213[.]217）は、 Microsoft の痕跡表に含まれていない。 **表を自動で取り込む仕組みだけでは取りこぼす**
    取るべき行動 脅威情報から痕跡を取り込む手順に「本文中に現れる指標を人が拾う」段を足す。 取り込んだ痕跡の件数（本件では SHA-256 が5件・ドメインが16件・IPv4 が6件＋本文の1件）を 記録し、元資料と突き合わせられるようにする
  • control.exe が遠隔のパスを引数に起動される事象と、WebDAV の有効化を検知対象にする
    感染連鎖の中核は `control.exe` による CPL（コントロールパネル項目）を装った DLL の遠隔読み込みと、`net.exe` による WebDAV リダイレクタの有効化である。 いずれも Windows の正規機能だが、**通常の業務ではこの組み合わせは現れない**
    取るべき行動 `control.exe` の起動を、引数に UNC パス（`\\`）や HTTP(S) の URL を含むものに絞って アラートにする。`net.exe` による WebClient サービスの開始も同様に監視する。 **業務で WebDAV を使っていないなら、WebClient サービス自体を無効化する** （SharePoint のエクスプローラ表示等への影響を先に棚卸しすること）
  • 「署名があるから安全」を検知ロジックの前提から外す
    使われているのは `conhost.exe`・`cmd.exe`・`control.exe`・`net.exe`・ `curl`・`SSH.exe`・`msiexec.exe`・Python 3.8 インタプリタで、 すべて正規の実行ファイルであり署名も有効である。 悪性であることを示すのは組み合わせと名前だけである
    取るべき行動 既存の検知ルールのうち「署名済みプロセスを除外している」条件を洗い出し、 本件に出てくる実行ファイル（とくに `control.exe`・`conhost.exe`・ `SSH.exe`・`curl`）を除外対象から外す。 除外を外した結果の誤検知量を測り、引数・親プロセスで絞り込む
  • 初報メールへの返信という起点を、技術側からも塞ぐ
    RedFlick の連鎖は、受信者が初報のメール（添付なし）に返信しなければ始まらない。 パスワードが本文の画像で渡されるため、添付書庫の自動展開・検査も働かない。 **メールの入口で止められる材料は、差出人アドレスの並びと 「パスワード付き書庫＋本文の画像」という組み合わせである**
    取るべき行動 差出人の表示名・ローカル部分に著名機関名や自組織名を含み、 登録ドメインが一致しないメールに警告バナーを付す。 パスワード付き書庫の添付を本文の画像とセットで受信した場合に 隔離・確認の対象にする。**遮断ではなく警告から始め、 誤検知率を測ってから強める**
  • AiTM（Evilginx）に対しては、多要素認証の有無ではなくサインインの後を見る
    Microsoft は2026年を通じて Evilginx のスピアフィッシング作戦を観測しており、 2023年の CISA 共同勧告も EvilGinx によるセッションクッキーの窃取と 多要素認証の回避を挙げている。**RedFlick とは別系統で並行している手口である**
    取るべき行動 条件付きアクセスと継続的アクセス評価（CAE）を有効にし、 サインイン元・デバイス・セッションの整合が崩れた場合に失効させる。 **メールボックスの転送規則の追加・変更を監視対象にする**（2023年の勧告が挙げた手口）。 標的像に当たる部門から順に、フィッシング耐性のあるサインイン方法へ移行する
