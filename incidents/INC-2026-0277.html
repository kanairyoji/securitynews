INC-2026-0277Zimbra の SNMP 注入で認証秘密値まで

Microsoft Threat Intelligence が2026年9月30日、Zimbra Collaboration Suite の SNMP 通知経路の未認証コマンド注入（CVE-2026-73570／CVSS v3.1 8.9・CWE-78）を悪用する実地の攻撃連鎖を公表した——細工したメール（SMTP 要求）1通で zimbra サービスアカウントとしてコマンドが実行でき、攻撃者は Jetty と mailboxd の複数の経路に JSP ウェブシェルを多重に置き、PAM 設定を symlink で差し替えて root を取り、zimlog.service という正規に見える systemd ユニットで永続化し、`zmlocalconfig -s` と LDAP 照会でサーバが一か所に集めている認証秘密値——事前認証キー・認証トークン署名鍵・二要素認証の秘密値——を抜き、Zimbra 自身の SSH 鍵でクラスタ内の他ノードへ広がっていた。狙われたのは個々の利用者のメールボックスのパスワードではなく、サーバ側の秘密値である。修正は2026年7月20日の 10.1.20 で出ており、公開（8月13日）より前の7月28日〜8月7日に2種類のスキャナが注入点を探っていた。CISA は8月21日に KEV へ収載し、期限は3日後の8月24日だった。被害組織名・件数・帰属はいずれも公表されていない。Zimbra 自身の Security Center は 10.1.20 の SNMP コマンド注入の修正を「TBD」と記すだけで CVE 番号を載せていない

脅威・攻撃キャンペーン脆弱性不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用設計・実装上の不備脆弱性の放置
初報: 2026年9月30日 最終更新: 2026年10月1日

何が起きたか。 Microsoft Threat Intelligence が2026年9月30日、Zimbra Collaboration Suite（ZCS）の未認証コマンド注入 CVE-2026-73570 を悪用した実地の攻撃連鎖を公表した。細工したメール1通（SMTP 要求）で、認証も利用者の操作も要らずに zimbra サービスアカウントとしてコマンドが実行できる。成立条件は、任意パッケージ zimbra-snmp が入っていて SNMP 通知が有効なことである。

どこが重いか。 攻撃者が狙ったのは個々の利用者のメールボックスのパスワードではなく、サーバが一か所に集めている秘密値だった。zmlocalconfig -s でLDAP・MySQL・Postfix・Amavis・複製の各サービスの資格情報を取り、得た LDAP 資格情報で事前認証キー（zimbraPreAuthKey）・認証トークンの署名鍵（zimbraAuthTokenKey）・二要素認証の秘密値（zimbraTwoFactorAuthSecret）を引き出している。Microsoft は、zimbraAuthTokenKey が「Zimbra が基盤全体で利用者のセッショントークンに署名するための鍵材料であり、この値にアクセスできれば任意のアカウントのセッショントークンを生成できる」（原文英語）と明記した。パスワードを変えても、二要素認証を入れていても、この鍵が出た時点でセッションを偽造されうる。

永続化と広がり。 JSP ウェブシェルは Jetty と mailboxd の複数の経路に多重に置かれ、1つ消されても残るようにしてあった。公開ディレクトリへの書き込み権限を一時的に開けて置いたあと元に戻すことで、権限の点検では見えにくくしている。権限昇格は /etc/pam.d/sudo を退避し、zmmailboxd.out のログをPAM 設定への symlink に置き換えて特権部品 zmmailboxdmgr を呼ぶという手順で、最終的に zimbra アカウントに NOPASSWD: ALL を与えている。再起動後も残るように zimlog.service という正規のログ部品に見える systemd ユニットを/etc/systemd/system/ に置き、時刻を既存のユニットに合わせて改竄していた。横展開は Zimbra 自身の SSH 鍵（/opt/zimbra/.ssh/zimbra_identity）を使い、ホスト鍵の検証を切った非対話 SSH でクラスタ内の他ノードへ入っている。

持ち出しは未完了とされている。 メールボックスのバックアップを固め、AzCopy を取って Azure Blob Storage へ送ろうとした形跡があるが、Microsoft は「利用できる証拠では転送が完了したことを確認できない」（原文英語）と述べた。

時間の並びが本件の読みどころである。 修正（10.1.20）は 2026年7月20日に出た。公開は8月13日だが、2種類のスキャナが注入点を探っていたのは7月28日〜8月7日—— 公開より前である。CISA は8月21日に KEV へ収載し、期限を3日後の8月24日に置いた。それでも9月30日の公表時点で、複数の地域・業種の組織で侵害が観測されている。

公表されていないこと。 被害組織の名前・件数・具体的な業種と地域・帰属。そして、Zimbra 自身の Security Center は 10.1.20 の「SNMP 監視部品のコマンド注入」の修正を「TBD」と記すだけで CVE 番号を載せていない（本記録の作成者が2026年10月1日に確認した）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**細工したメール1通で `zimbra` サービスアカウントとしてコマンドを実行し、 JSP ウェブシェルを4経路に多重に置き、製品自身の特権部品と PAM を使って root を取り、 正規に見える systemd ユニットで永続化し、サーバが一か所に集めていた サービス資格情報と認証秘密値を抜き、Zimbra 自身の SSH 鍵でクラスタ内へ広がり、 メールボックスデータを固めてクラウドストレージへ送ろうとした**（転送の完了は未確認）。 **もっとも重い段階にマルウェアは関与していない**—— Microsoft は「素の対話シェルだけで行われた」と述べている

    根拠: Microsoft Threat Intelligence（2026年9月30日）。 **日付の範囲が示されているのはこの段階だけである**

    根拠: Microsoft（2026年9月30日）。 **「Zimbra の脆弱性の悪用により、攻撃者は `zimbra` サービスアカウントとして 直接コマンドを実行できた」**（原文英語）

    根拠: Microsoft（2026年9月30日）。 **「公開ディレクトリへの書き込みを一時的に有効にしてウェブシェルを置き、 その後ディレクトリの権限を元に戻すことで、 基本的な権限の点検では変更が見えにくくなっていた」**（原文英語）

権限昇格は、製品が持っている特権部品を踏み台にして成立している原因・手口

Microsoft が示した権限昇格は、外部のエクスプロイトを使っていない。製品自身が持っている特権部品を順番に使っている。

  1. サーバに必要な Zimbra の補助部品があり、メールボックス管理部品のログディレクトリが書き込み可能であることを確認する
  2. /etc/pam.d/sudo を退避する
  3. zmmailboxd.out のログファイルを、PAM 設定への symlink に置き換える
  4. 特権部品 zmmailboxdmgr を呼ぶ——ログへの書き込みがsymlink をたどって PAM 設定の書き換えになる
  5. PAM のセッションフック（pam_exec）を足し、ローカルのスクリプトを呼ばせる
  6. 正規の補助部品 zmstat-fd を通じて sudo セッションを起こす——フックが root として走り、zimbra アカウントに NOPASSWD: ALL を与える

防御の観点で重いのは、どの段も「正規の部品の正規の動作」だという点である。マルウェアの検体を探す発想では、ここに引っかかるものが無い。Microsoft 自身がこの点を総括している—— 「本キャンペーンでもっとも重い帰結のいくつか、たとえば持ち出しに向けたメールストア全体の退避は、マルウェアファミリを一切伴わず、素の対話シェルだけで行われた」（原文英語）。

したがって、検知の設計は「振る舞い」側に置くしかない。ログファイルが symlink に変わる、サービスアカウントがsudoers に無制限の権限を得る、/etc/systemd/system/ にアプリケーションの外からユニットが入る—— これらはいずれもファイル1つ・設定1行の変化として現れる。

多重に置かれたウェブシェルと、正規に見せる細工原因・手口

ウェブシェルは意図的に多重化されていた。 Jetty 側の2経路（/jetty_base/webapps/・/jetty/webapps/）とmailboxd 側の2経路（/mailboxd/webapps/・/work/zimbra/jsp/）の計4種の経路に JSP が置かれ、1つ消されても残るようにしてあった。

見えにくくする細工が3つある。

  • 公開ディレクトリの書き込み権限を一時的に開けて置き、置いた後で元に戻す。 Microsoft は「基本的な権限の点検では変更が見えにくくなる」と述べている
  • zimlog.service という、Zimbra のログ部品に見える名前を選んでいる。ただし置き場は /etc/systemd/system/ で、Zimbra のアプリケーションディレクトリの外である
  • そのユニットの時刻を、既存の systemd ユニットに合わせて改竄している（/tmp から sudo で移してから時刻を合わせる）

永続化はこれだけではない。 * * * * * と @reboot の cron、SSH の authorized_keys への追記、useradd / adduser による局所アカウントの作成、OpenRC の init.d スクリプト、シェルの起動ファイル（.bash_profile / .zprofile）、そして memfd_create によるメモリ上での実行が併用されていた。「1つ見つけて消した」で終わる形にはなっていない。

探すべき場所と、入れ替えるべき鍵対策・注意喚起

Microsoft が示した対処を、実施の順に並べ替えて整理する。順序が重要なのは、鍵を入れ替える前に永続化を取り切らないと、入れ替えた鍵がまた抜かれるためである。

1. 更新する。 ZCS を 10.1.20 以降へ上げる。

2. すぐに当てられないなら、成立条件を外す。任意パッケージ zimbra-snmp を削除し、SNMP 通知を無効にし、SNMP と SMTP の到達を信頼するホストだけに制限する。

3. 侵害の有無を探す（場所で探す）。
- すべてのメールボックスノードの Zimbra アプリケーションディレクトリとサーブレットの作業ディレクトリに、見覚えのない JSP・生成された *_jsp.java・コンパイル済みのサーブレット成果物が無いか
- 最近の権限変更が無いか（置いて戻す細工の痕跡）
- systemd のユニットに、所有者・有効化・時刻が不自然なものが無いか
- cron・authorized_keys・局所アカウント・init.d・シェル起動ファイル
- Zimbra の Java や jspawnhelper がネイティブのシェルを起動していないか
- 注入の署名——Microsoft は「正規の snmptrap 呼び出しの直後にシェルのメタ文字が続き、wget または curl の呼び出しがあって、末尾の # で残りの正規の引数を飲み込む形」を挙げている
- 注入経路からの DNS コールバック（帯域外検査サービス宛て）

4. 鍵を入れ替える。 Microsoft は 「すべてのドメインの zimbraPreAuthKey を入れ替える」ことを明示的に求めている。本記録はこれに加えて、zmlocalconfig -s で見える範囲のサービス資格情報（LDAP・MySQL・Postfix・Amavis・複製）と、zimbraAuthTokenKey・zimbraTwoFactorAuthSecret の扱いを自組織の手順として決めておくべきだと考える（本記録の判断）。とくにセッショントークンの署名鍵は、入れ替えれば全利用者のセッションが切れるため、「切れることを前提にした入れ替え手順」を平時に書いておかないと、事後に実行できない。

5. 逆接続の警報を重く扱う。 Microsoft は 「リバースシェルの接続が確認された場合、ペイロードが隔離されていなくても攻撃者のアクセスがあったことを意味する」と述べている。検体が取れなかったことを「未侵害」の根拠にしない。

6. サービスアカウントの爆発半径を縮める。名前空間・seccomp・AppArmor で zimbra サービスアカウントを閉じ込める。これは本件の修正ではなく、次のコマンド注入級の脆弱性への備えである。

「サーバ側に鍵が集まっている」構造は、Zimbra に限らない（本記録の評価）評価・解釈

ここから先は本記録の判断である。

本件の技術的な中身は Zimbra に固有だが、構造は固有ではない。自前運用のメール基盤・認証基盤・業務システムは、たいてい「サービスが自分で使うための秘密値」を、サーバ上の設定ファイルやディレクトリサービスに一か所へ集めて持っている。 Zimbra の場合は zmlocalconfig と LDAP がその一か所だった。1つのコマンド注入でサービスアカウントが取れると、その一か所がそのまま取れる。

そして、取れたものの中に「利用者の認証を迂回できる鍵」が入っていた。ここが本件のもっとも重い点である。個々のパスワードが漏れたのなら、変更すれば止まる。セッショントークンの署名鍵が漏れたら、パスワードの変更も二要素認証も止めない。 つまり「認証情報が漏れたか」を点検する発想では、本件の被害を測れない。測るべきは「認証を成立させている鍵が漏れたか」である。

日本の読者にとっての当てはめは2段ある。

第1段は、同じ製品を使っているかどうか。 Zimbra は国内でも大学・自治体・ISP・中小企業の自社メール基盤として使われている。zimbra-snmp を入れて SNMP 通知を有効にしているかは、構築時の判断としてしか記録されていないことが多い。 「入れた覚えがない」で済ませず、実機で確認する必要がある。

第2段は、製品を使っていない組織にも効く。自組織の基盤について、「サービスアカウントが取られたとき、同時に取られる秘密値の一覧」が書けるか。書けないなら、侵害時に何を入れ替えるべきかを事後に決めることになる。本件では入れ替えるべき対象が公開資料から読み取れたが、それは Microsoft が属性名まで書いたからである。自組織の基盤について同じ一覧を持っているのは、自組織だけである。

最後に、公報の読み方について1つ。 Zimbra 自身の Security Center には、この修正がCVE 番号無しの「TBD」として載っているだけである（本記録の作成者が2026年10月1日に確認した）。製品の公報だけを見て「自分に関係する脆弱性か」を判断する運用は、本件では機能しない。 KEV・NVD・CERT の側から入ってくる識別子を、自組織の資産一覧に突き合わせる経路を別に持つ必要がある。

  • 侵害された組織の名前・件数。「複数の地域・複数の業種」という記述だけで、規模が分からない
  • 業種と地域の内訳。 否定形（「単一に限られていない」）でしか示されていない。日本が含まれるかも分からない
  • 帰属。 国家背景・犯罪集団のいずれにも触れておらず、Microsoft 自身の命名も無い。探索の段階で「2種類の異なるスキャナ」が観測されており、後段の侵害が同一の主体によるものかも述べられていない
  • メールボックスデータが実際に外へ出たのか。 「準備完了・実行未確認」である。本記録は「持ち出された」と書かないが、実務上は出たものとして扱うほかない

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Zimbra Collaboration Suite（ZCS）を自前で運用しており、 バージョンが **10.1.20 より前**である**これが本件の直接の該当条件である。** 修正は2026年7月20日に出ている。 **CISA が KEV へ収載し8月24日を期限としていることも、緊急度の根拠になる**
システム構成□ ZCS に任意パッケージ **`zimbra-snmp`** を入れており、 SNMP 通知（`snmp_notify`）を有効にし、`swatchdog` が動いている**成立条件そのものである。** 監視のために入れる正当な構成なので、 **「入れた覚えがない」で済ませず実機で確認する必要がある。** 当てられない場合の緩和策は、この部品の削除と通知の無効化である
認証・認可□ メール基盤や業務システムが、**セッショントークンの署名鍵・事前認証キー・ 二要素認証の秘密値**をサーバ側に保持しており、 **その入れ替え手順が文書化されていない****本件でもっとも重い被害はここである。** 鍵が出た時点でパスワード変更も二要素認証もセッションの偽造を止めない。 **入れ替えると全利用者のセッションが切れるため、 手順が無いと事後に実行できない**
システム構成□ メールサーバやアプリケーションサーバを**複数ノードのクラスタ**で運用し、 **ノード間の自動連携にサービスアカウントの SSH 鍵**を使っている本件の横展開は **Zimbra 自身の SSH 鍵（`/opt/zimbra/.ssh/zimbra_identity`）**で、 ホスト鍵の検証を切った非対話 SSH により成立した。 **1台だけ調査して終える運用では、広がった先が残る**
