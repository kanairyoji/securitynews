INC-2026-0278Cisco SD-WAN Manager 認証回避が悪用

Cisco が2026年9月30日、Catalyst SD-WAN Manager（旧 vManage）の API 認証回避の脆弱性 CVE-2026-76504（CVSS 9.8・CWE-177）を帯域外の勧告で公表し、**2026年9月のうちに Cisco PSIRT が実地での悪用を把握していた**ことを明らかにした——URI のエンコーディングの扱いが WildFly 側（デコード後の文字列で認証の要否を判定）と Cisco 自身の `AppServerLoginModule`（生の文字列で `j_security_check` を判定）で食い違うため、`/%6a_security_check` へ1回 POST するだけでパスワード検査の分岐を飛ばし、内部用アカウント名 `viptela-reserved-cloudops` を名乗って**管理者権限の API セッションを無から作れる**（VulnCheck が再現・武器化）。**全ての構成が影響を受け回避策は無い**。米 CISA は同日 KEV に収載し連邦機関の期限を10月3日（3日後）に設定、VulnCheck は**インターネットに露出した vManage を約1,500台**観測している。**悪用の主体・被害組織数・最初の悪用時期はいずれも公表されていない**

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）未知の脆弱性の悪用設計・実装上の不備
初報: 2026年9月30日 最終更新: 2026年10月1日

Cisco は2026年9月30日、Catalyst SD-WAN Manager（旧 vManage）のAPI 認証回避の脆弱性 CVE-2026-76504（CVSS 基本値 9.8・CWE-177）について帯域外の勧告（cisco-sa-sdwan-webauth-xr8beuuU）を公表しました。勧告は「2026年9月、Cisco PSIRT はこの脆弱性の実地での悪用を把握した」（原文英語）と述べており、公表の時点で既に悪用されていたゼロデイです。

成立すると、認証を経ていない遠隔の攻撃者が admin 利用者の権限で API に到達します。Cisco は「影響を受ける製品はシステムの構成にかかわらず脆弱」とし、回避策は存在しない（"There are no workarounds that address this vulnerability."）と明記しました。暫定の緩和は「信頼できないネットワークからのアクセスを塞ぐ」ことだけです。

なぜ1回の POST で管理者になれるのか。 VulnCheck が検証した内容はこうです。

  • vManage の前段には service-proxy（Envoy）、後段には WildFly（Undertow）上のJava アプリが載っている。j_security_check は「ログイン前なので誰でも通す」security-constraint の対象で、これは正常な設計である
  • WildFly の security-constraint の照合はパスをデコードしてから判定する。一方、Cisco 自身の AppServerLoginModule.login() はrequest.getRequestURI()（生のパスを返すとサーブレット仕様で決まっている）にj_security_check という部分文字列が含まれるかを見て、実際にパスワードを検査する loginUser() を呼ぶかどうかを決めている
  • したがって /%6a_security_check（j を %6a に書いた形）を送ると、WildFly 側は「認証不要の入口」と見なして通し、Cisco 側は「j_security_check ではない」と判断してパスワード検査の分岐に入らない
  • 分岐の else 側は「既に本人確認が済んでいるセッションの継続」を想定した経路で、残る関門は isInternalUser(userId) だけ。これは内部用アカウント名（viptela-reserved-dca / -cloud / -cloudops / -uc の4つ）との部分一致を見るだけである
  • 4つのうち viptela-reserved-cloudops と viptela-reserved-uc はRBAC の制約も抜けるため、パスワードは何でもよく、管理者権限の JSESSIONID が払い出される

米 CISA は同じ9月30日に本件を KEV カタログへ収載し、連邦民間行政機関（FCEB）の是正期限を 2026年10月3日（3日後）に設定しました。VulnCheck は10月1日、再現と武器化を済ませたうえでインターネットに露出した vManage を約1,500台観測していると述べています。

本記録として押さえておきたいのは、これが Cisco SD-WAN に対する今年8本目のKEV 収載であるという指摘（watchTowr の Jake Knott）です。SD-WAN Manager は大規模ネットワークの設定・監視を1画面で握る基盤であり、そこに admin で入られることは、個別の機器1台を取られることと意味が違います。

悪用の主体・手口の中身・被害組織の数・最初の悪用時期は、Cisco も CISA も公表していません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

`/%6a_security_check` へ1回 POST し、利用者名に `viptela-reserved-cloudops` （または `-uc`）を入れるだけで、パスワードの検査を経ずに管理者権限の `JSESSIONID` が払い出される。原因は WildFly の security-constraint が パスをデコードしてから認証の要否を決める一方、Cisco の `AppServerLoginModule.login()` が 生のパスで `j_security_check` か否かを判定し、パスワード検査の実行を決めていること。 **実地での悪用は2026年9月に Cisco PSIRT が把握しているが、 侵入後に何が行われたかは公表されていない。** 以下の chain のうち initial-access と credential-access は VulnCheck の再現に基づく事実、 それ以降は「公表されていない」ことの記録である。

  1. 1. 偵察unconfirmed[1] [4]
    インターネットに露出した vManage の探索。VulnCheck Target Intelligence は **約1,500台**を観測している（2026年10月1日時点）。 **実際の攻撃者がどのように標的を選んだかは公表されていない。**
    根拠: VulnCheck の露出台数の観測（攻撃者側の偵察の記述は無い）
  2. 2. 初期侵入確認済[1] [3] [4]
    `POST /%6a_security_check` を送る。WildFly の security-constraint は パスを**デコードしてから**照合するため「認証不要の入口」として通る。 一方 Cisco の `AppServerLoginModule.login()` は `request.getRequestURI()`（生のパス）に `j_security_check` が含まれるかで パスワード検査 `loginUser()` の実行を決めているため、 **検査の分岐に入らない**。本文は `j_username=viptela-reserved-cloudops&j_password=anything123` のような形で、 **パスワードは任意の文字列でよい**。`%6a` は一例であり、 **任意の1文字を符号化すれば成立する**（Rapid7 の注記）。
    根拠: VulnCheck の再現（HTTP 200 と `Set-Cookie: JSESSIONID=...` の取得）、Cisco 勧告の CWE-177、Rapid7 の注記
  3. 3. 認証情報アクセス確認済[4]
    利用者名として `AdminConstants.INTERNAL_USERS` の4つ （`viptela-reserved-dca` / `-cloud` / `-cloudops` / `-uc`）のいずれかを名乗る。 `isInternalUser()` は**部分一致**で判定するだけであり、 パスワードの照合は行われない。**4つのうち `-cloudops` と `-uc` の2つは RBAC も抜け**、`GET /dataservice/admin/user` などの管理者向け端点が応答する。 残る2つは「Access forbidden: role not allowed」で止まる。
    根拠: VulnCheck が jar から抽出した定数と、4つすべてに対する実測
  4. 4. 内部探索unconfirmed[1] [3] [4]
    **公表されていない。** VulnCheck の再現は `GET /dataservice/admin/user` が応答したところで止まっている（研究としての確認）。 実際の攻撃者が管理者セッションで何を照会したか—— 配下機器の一覧、テンプレート、認証情報、証明書——についての記述は、 Cisco・CISA・Rapid7・VulnCheck のいずれにも無い。
    根拠: 記述が無いことの記録（4資料を通じて侵入後の挙動の記載が無い）
  5. 5. 影響（暗号化・破壊・改ざん）unconfirmed[1] [2]
    **公表されていない。** Cisco が述べるのは「admin 利用者として API に到達できる」 という能力までである。設定の改変、配下機器への不正な配信、 認証情報の持ち出し、他システムへの横展開が実際に起きたかどうかの記述は無い。 CISA KEV のランサムウェア利用欄は "Unknown" である。
    根拠: Cisco 勧告の影響の記述と、CISA KEV の記載（被害の具体は無い）

悪用が先で勧告が後——「2026年9月に PSIRT が把握した」とだけ書かれている概観出典 [1]

Cisco の勧告（cisco-sa-sdwan-webauth-xr8beuuU、2026年9月30日13:00 GMT、版 1.0 Final）は次の2点を同時に伝えています。

  • CVE-2026-76504 は Catalyst SD-WAN Manager の API のセッションに基づく認証の仕組みに存在し、認証を経ていない遠隔の攻撃者がadmin 利用者の権限で API に到達できる（CVSS 基本値 9.8・CWE-177）
  • 「2026年9月、Cisco PSIRT はこの脆弱性の実地での悪用を把握した」（原文英語）

つまり公表の時点で既に悪用されていたゼロデイです。勧告はさらに「影響を受ける製品はシステムの構成にかかわらず脆弱」とし、「この脆弱性に対処する回避策は無い」と書いています。設定で逃げる道は示されていません。

暫定の緩和として挙げられているのは、オンプレミス利用者が「信頼できないネットワークからのアクセスを塞ぐ」こと、インターネット越しのアクセスが必要なら「既知の信頼できるホストに限定し、SD-WAN の制御部をフィルタリング装置の後ろに置く」ことだけです。Cisco はこの緩和を入れても更新は適用せよと明示しています。

脆弱性の発見経路として勧告が挙げているのは「Cisco TAC のサポートケースの対応中に発見された」ことです。これは、顧客環境で何かが起きて問い合わせがあり、その調査で見つかった形と読めますが、Cisco はそうは書いていません（本記録の評価）。

1つのパスを2つのコードが別々に読んでいた——デコードする側とデコードしない側原因・手口出典 [1] [3] [4]

VulnCheck が公表した解析は、根本原因を「同じ文字列を見ている2つのコードの不一致」と結論しています。再現の筋道は次のとおりです（すべて VulnCheck の直接検証による）。

1. 2つのエラーが違った。 素の /j_security_check に誤ったパスワードを送ると「Invalid username or password」、/%6a_security_check に同じものを送ると「LOGIN000 / userInfo is null」が返りました。エラーが違うのは通る経路が違うからで、後者ではパスワードの比較に到達する前に何かが失敗しています。

2. どこで止まっているか。 vManage は前段に service-proxy（Envoy）、後段に WildFly（Undertow）上の Java アプリ（standalone-viptela.xml）が載った構成です。web.xml では j_security_check が「<!-- No auth-constraint means everybody has access! -->」という注釈つきのsecurity-constraint に入っています。これは正常な設計で、ログインする前にセッションは存在しえないためです。実際の認証処理は JAAS のログインモジュールcom.viptela.vmanage.server.auth.AppServerLoginModule にありました。

3. 分岐の条件。 逆コンパイルした login() は次の条件で本物のパスワード検査 loginUser() を呼ぶかを決めていました。

} else if (request.getRequestURI() != null && (isBasicAuth
    || request.getRequestURI().contains("j_security_check")
    || request.getRequestURI().contains("samlLoginResponse"))) {
    userInfo = this.loginUser(userId, password, request, ...);

getRequestURI() はサーブレット仕様で「リクエスト行の生のパスを返す」と決まっているため、%6a_security_check には文字列 j_security_check が含まれません。条件が偽になり、パスワード検査が一度も走らない。

4. else 側に落ちる。 そこは「すでに信頼されたセッションの継続」を想定した経路で、残る関門は isInternalUser(userId) だけです。これはAdminConstants.INTERNAL_USERS の4つの名前（viptela-reserved-dca / -cloud / -cloudops / -uc）との部分一致を見るだけでした。

5. RBAC で2つに絞られた。 4つすべてでセッションは発行されましたが、-dca と -cloud は管理者向けの端点で「Access forbidden: role not allowed」。-cloudops と -uc は通り、GET /dataservice/admin/user が応答しました。パスワードは anything123 で構いません。

VulnCheck の結論はこうです。WildFly の security-constraint の照合はパスをデコードしてから認証の要否を決める。Cisco の login() はデコードしていない生のパスで検査の実行を決める。この食い違いにより「無からセッションを作り出せる」。

Cisco の勧告が示した IoC（%6a を含む j_security_check への POST）について、Rapid7 は重要な注記を添えています——%6a は一例にすぎず、攻撃者はリクエスト中の任意の1文字を符号化できる。%6a だけを検索条件にすると見落とします。

CISA は収載から3日の期限を切り、「緩和策が無ければ利用中止」まで書いた当局対応出典 [2] [3]

  • 名称: Cisco Catalyst SD-WAN Manager Hex Encoding Vulnerability
  • 収載日: 2026年9月30日 ／ 是正期限: 2026年10月3日
  • 要求事項: 「ベンダーの指示に従って緩和策を適用し、CISA の BOD 26-04『リスクに基づく更新の優先順位付け』および CISA の Forensics Triage Requirements に適合させること。クラウドサービスについては BOD 26-04 の該当指針に従い、緩和策が利用できない場合は当該製品の利用を中止すること」（原文英語）
  • ランサムウェアでの利用: Unknown（不明）

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
1つのパスを2つのコードが別々に読み、パスワード検査の分岐が飛ぶ
`POST /%6a_security_check` は、WildFly の security-constraint には **デコード後の `j_security_check`** として「認証不要の入口」と見なされて通る一方、 Cisco の `AppServerLoginModule.login()` では **デコード前の生のパス**を見るため「`j_security_check` ではない」と判定され、 パスワード検査 `loginUser()` が呼ばれない。 else 側に落ちた先の関門は内部用アカウント名の部分一致だけで、 `viptela-reserved-cloudops` を名乗れば管理者権限の `JSESSIONID` が払い出される。 **侵入後に何が行われたかは公表されていない。**

復旧を早められた侵害が疑われた場合に備え、設定の既知良好状態の保全と、管理者資格情報・証明書の失効手順を用意する

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Cisco は定例のパッチ公開日を待たず、**帯域外（out-of-band）の勧告**として 2026年9月30日に公表し、修正版・IoC・暫定の緩和を同時に出した機能した**本記録の評価。** 悪用が進行している状況で、修正版・IoC・緩和を同時に出し、 同日に KEV 収載まで至っている点は機能したと見る。 ただし**「回避策は無い」と書かれた以上、更新できない組織に残る手は到達の遮断だけ**であり、 20.9 より前の系列を使う組織には短期の選択肢が乏しい
悪用の主体・被害組織数・最初の悪用時期・侵入後の挙動を**公表しない**という選択評価材料なし**本記録の評価。** 公表しない理由が示されていないため、妥当性を判断できない。 記録としては「出されていない」という事実と、 その結果として利用者が IoC での自力調査に依存することだけを残す
CISO・経営層への示唆
  • 「管理基盤1台」の格付けを、配下の機器の総数で決める
    Catalyst SD-WAN Manager は大規模ネットワークの設定・監視を1画面で握る基盤である。 watchTowr の指摘のとおり「企業が管理・設定・監視に使う single-pane-of-glass」であり、 admin で入られることは機器1台の侵害とは意味が違う。 それでも資産台帳では「サーバー1台」として扱われていることが多い。
    取るべき行動 **資産台帳に「この1台が握っている配下の機器数・拠点数」の欄を設け、 格付けをその数で決める。** 管理基盤の更新は、 配下機器の更新より高い優先度と短い許容期間を割り当てる。
  • 「回避策は無い」と書かれた勧告に備えた意思決定の筋道を持つ
    本件の勧告は回避策が無いと明記し、暫定の緩和は 「信頼できないネットワークからの到達を塞ぐ」ことだけだった。 設定変更で凌ぐという選択肢が存在しない。
    取るべき行動 **「更新か遮断しかない」場合に誰が何時間で遮断を決めるかを、 平時に決めておく。** 管理基盤への外部からの到達を即時に落とす手順 （経路・担当・影響を受ける運用）を文書にし、年1回実際に試す。
  • 当局の是正期限の短さを、自組織の優先度判断の入力にする
    CISA は収載から**3日**という期限を設定した。 これは KEV の通例（3週間程度）から外れた短さであり、 被害の詳細が公表されていない状況で得られる**数少ない深刻度の信号**である。
    取るべき行動 **KEV の収載を監視するだけでなく、是正期限の短さを優先度の加点要素として 運用基準に書き込む。** 期限が1週間未満のものは、 自組織が FCEB でなくとも緊急扱いにする閾値として使う。
  • 20.9 より前のような「系列内の修正が無い」層を、事前に把握しておく
    本件の対応表で 20.9 より前は「修正版へ移行」としか書かれていない。 緊急時に移行を始める組織は、検証と停止時間の確保から始めることになる。
    取るべき行動 **管理基盤・ネットワーク機器の版数を棚卸しし、 「ベンダーが系列内の修正を出さない版」を一覧にする。** その一覧にある資産は、緊急事態を待たずに移行計画を立てる。
セキュリティ技術者への示唆
  • パスの符号化・正規化の不一致を、自社の構成でも疑う
    本件の原因は、前段（WildFly の security-constraint）が**デコード後**のパスで 認証の要否を決め、後段（Cisco の `login()`）が**デコード前**の生のパスで 検査の実行を決めていたことである。どちらのコードも単体では間違っていない。 **「2つが同じ文字列を別の解釈で読む」構成そのものが欠陥**だった。
    取るべき行動 **プロキシ・WAF・アプリの3層で、パスの正規化がどこで行われるかを図にする。** 認証・認可の判定に使う文字列が、どの層でデコードされた値なのかを確認し、 判定は1か所に集約する。前段で正規化して拒否する設定を入れる。
  • IoC の例示をそのまま検索条件にしない
    Cisco が示したのは `%6a`（`j` の符号化）を含む要求だが、 Cisco 自身が「任意の1文字を符号化できる」と述べ、Rapid7 も強調している。 `%6a` で grep すると `%6A`（大文字）も `_security_chec%6b` も漏れる。
    取るべき行動 **ログ検索は「符号化が1つでも含まれる `*_security_check` 風のパス」として 正規表現で書く**（例: `%[0-9A-Fa-f]{2}` を含み `security_check` で終わるパス）。 併せて利用者名 `viptela-reserved-` の側からも検索し、2方向で突き合わせる。
  • 製品内部の「内部用アカウント」の存在を前提に監視条件を作る
    本件で鍵になったのは `viptela-reserved-dca` / `-cloud` / `-cloudops` / `-uc` という Cisco の内部用アカウント名で、`isInternalUser()` は**部分一致**で通していた。 これらは顧客環境の運用で人が使う名前ではない。
    取るべき行動 **製品の内部用・予約済みアカウント名を認証ログから洗い出し、 それらによるアクセスを常時警報の対象にする。** ベンダー文書に記載が無ければ、認証ログに現れる利用者名を 平常時に棚卸しして基準線を作る。
  • 調査に使うログの保持期間を、勧告が出る前に確認しておく
    Cisco の IoC は2つのログを指すが、**既定の保持期間は勧告に書かれていない**。 悪用は2026年9月のうちに始まっており、 いま見てログが残っていなければ過去の悪用は確認できない。
    取るべき行動 **管理基盤のログを本体の外（SIEM・ログ収集基盤）へ転送し、 保持期間を侵害調査に耐える長さに決める。** 転送していない機器の一覧を作り、優先度の高いものから対処する。
  • 管理 API の「認証の後ろにもう一段」を設計に入れる
    本件は認証そのものを飛ばされた。認証の実装に不備があっても、 到達元の制限・相互 TLS・踏み台経由の強制があれば、 攻撃者はまず到達の壁を越える必要がある。
    取るべき行動 **管理 API の到達経路を、認証とは独立した層（送信元制限・クライアント証明書・ 専用ネットワーク）で一段絞る。** 「認証があるから到達は自由でよい」という 設計判断をしている箇所を洗い出す。
