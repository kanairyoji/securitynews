INC-2026-0279Warlock の開発元は中国系 Longlegs

Symantec が2026年10月1日、Warlock ランサムウェアの開発元は**中国系（China-nexus）の脅威アクター Longlegs**（別名 Storm-2603。同社は過去の活動群 CL-CRI-1040・CamoFei・ChamelGang とも結び付けている）であると述べ、**直近2か月で少なくとも4組織**——**水道事業者と通信事業者という重要インフラ2者**、地方政府機関、大学——を侵害したと公表した。被害はポルトガル語圏・スペイン語圏の国々（欧州・アフリカ・中南米）に集中。初期侵入は依然として**オンプレミス Microsoft SharePoint Server の脆弱性（ToolShell 等）**で、webshell で ASP.NET のマシンキーを奪い、署名済みの `__VIEWSTATE` を偽造して SharePoint のアプリケーションプール内でコード実行する。**署名済みの脆弱なドライバ K7RKScan（CVE-2025-1055）でセキュリティ製品を落とし**（重要インフラの一件では約2時間で**40台以上**）、**ドメインの SYSVOL 共有に置いた検体が通常のドメイン複製で配られて33台以上で暗号化**に至った。VS Code のトンネル機能（`code-insiders.exe tunnel service install`）を署名済みの遠隔接続手段として常用している。**【続報・2026年10月2日】Symantec が「2026年7月の CISA 勧告」としか書かなかった対象は、CISA が2026年7月14日に公表した勧告の6件（CVE-2026-32201・CVE-2026-45659・CVE-2026-56164・CVE-2026-58644・CVE-2026-50522・CVE-2026-55040）と特定できた**（ただし番号を並べたのは報道側で、Symantec 自身は本稿に挙げていない）

脅威・攻撃キャンペーンランサムウェア被害（暗号化・リークサイト恐喝が中心）続報が続いている有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用脆弱性の放置設計・実装上の不備

1つ目は帰属です。 Symantec は Warlock を開発しているのは中国系（China-nexus）の脅威アクター Longlegs（別名 Storm-2603）だとし、同社が過去に追っていた活動群 CL-CRI-1040・CamoFei・ChamelGang とこのグループを結び付けています。Warlock は2025年6月に現れ、その数週間後に Microsoft SharePoint Server のゼロデイ連鎖ToolShell（CVE-2025-49704・CVE-2025-49706・CVE-2025-53770・CVE-2025-53771）を突いた攻撃者が Warlock を展開していたことで広く知られました。

2つ目は直近の標的です。 過去2か月でこのグループは少なくとも4組織を攻撃しました。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

オンプレミス SharePoint Server の脆弱性で侵入し、複数版に同時に webshell を置いて ASP.NET のマシンキーを収集。奪ったキーで署名を偽造した `__VIEWSTATE` を使い アプリケーションプール内でコード実行する。以後は正規の署名・正規のサービス・ 環境常駐の道具で進み、**署名済みの脆弱なドライバ（K7RKScan・CVE-2025-1055）で セキュリティ製品を落として**から、**ドメインの SYSVOL 共有に置いた検体を 通常のドメイン複製に運ばせて**暗号化する。 重要インフラ1組織では、最初の観測（7月22日）から暗号化（7月31日未明）まで9日、 AV/EDR 無効化の全域への展開は約2時間だった。

  1. 1. 初期侵入確認済[1]
    オンプレミス SharePoint Server の複数の脆弱性を悪用して侵入する。 重要インフラ1件では2026年7月22日、PowerShell で SharePoint の LAYOUTS ディレクトリに webshell（`layout2sp.aspx`）が 書き込まれたのが最初の観測である。 **このグループは複数の SharePoint の版のディレクトリへ同時に webshell を落とす**—— どの版が実際に入っていても動くようにするためである。
    根拠: Symantec が示した PowerShell の1行（`[IO.File]::WriteAllBytes(...layouts\layout2sp.aspx...)`）と、複数版への同時設置の記述
  2. 2. 認証情報アクセス確認済[1]
    webshell の役目は **SharePoint ファームの ASP.NET マシンキーの収集**である。 マシンキーが手に入ると、攻撃者は**正しく署名されたペイロードを偽造**できる。
    根拠: Symantec の記述（webshell の機能はマシンキーの収集であり、それを使って署名済みペイロードを偽造する）
  3. 3. 実行確認済[1]
    2026年7月28日午後、Computer 1 で base64 符号化された PowerShell が 一定間隔で繰り返し実行された。内容は `System.Workflow.ComponentModel` アセンブリの読み込みで、 **このアセンブリが公開する型が、偽造した署名済み `__VIEWSTATE` を 任意コード実行に変えるデシリアライズのガジェットになる**。 同じ処理が同日午後に Computer 2 でも2回動いた。 続いて `msiexec /q /i` で3つのペイロードが取得された （`litter.catbox.moe` から1つ、`s3.wasabisys.com` から2つ・**90分の間に3種類**）。
    根拠: Symantec が示したコマンド列（`[void][Reflection.Assembly]::Load('System.Workflow.ComponentModel...')` と3本の msiexec）
  4. 4. 内部探索確認済[1]
    7月24日に `net user /domain`・`whoami` が実行され、 同日 `nltest /domain_trusts` で Active Directory のドメイン信頼関係が列挙された。 7月27日には `oastify.com`（Burp Collaborator）のサブドメインへ 外向きの HTTP 要求が出ており、**標的自身のドメイン名が サブドメインに埋め込まれていた**。Symantec はこれを、 注入したコードが特定のホストで実行されたことを確認する走査ツールの挙動と評している。 7月28日夜以降は **NetExec（`nxc.exe`）**で AD の列挙・認証情報のスプレー・ 遠隔コマンド実行が行われた。
    根拠: Symantec が示したコマンド列と oastify.com への要求、nxc.exe の使用
  5. 5. 権限昇格確認済[1]
    7月28日から29日にかけて、ドメインアカウント **`SPSEPRDSetup`** を `net localgroup administrators SPSEPRDSetup /add` で さらに3台（Computer 3・4・5）のローカル Administrators グループへ 繰り返し追加した。Symantec は、SharePoint が SPS／SP を頭に付けた セットアップ用のサービスアカウントを作ることが多いため、 **名前の擬装とみられる**としている。
    根拠: Symantec が示したコマンドと擬装についての評価
  6. 6. 永続化確認済[1]
    2つの系統が併用されている。①**DLL サイドローディング**—— `ssvagent.exe`・`logger.exe`・`doexe.exe` と、 対になる DLL（`gsdll64.dll.tmp`・`doexeloc.dll.tmp`・`doexeloc.dll`）を Windows システムフォルダの下位（`\0409\`）や ProgramData に配置する。 7月30日〜31日未明に記録されたのは、この対が Computer 1 に 再出現したことのみだった。②**VS Code のトンネル**——Computer 4 で `code-insiders.exe tunnel service install --accept-server-license-terms` を 実行し、サービスとして常駐させた。 **VS Code Insiders のバイナリは Microsoft 署名で、 トンネルは Microsoft 自身の基盤を中継する。**
    根拠: Symantec が示したファイル名・配置先と、トンネル導入のコマンド
  7. 7. 検知回避確認済[1]
    7月31日未明、AV/EDR を無効化する道具（`a.exe`）が **内部 IP のネットワーク共有をマウントして複製し起動する定型の1行コマンド**で 多数のホストへ配られ、**約2時間のうちに40台以上で実行が記録された**。 この道具は脆弱なドライバを利用したとみられるが **正体は不明のまま**で、Symantec は 「同グループの他の最近の攻撃では **K7RKScan**（署名済みだが脆弱なドライバ・ **CVE-2025-1055**）を使っていた」と述べている。 K7RKScan はカーネル層で保護されたセキュリティプロセスを終了させられる。
    根拠: Symantec が示した1行コマンドと40台以上・約2時間の観測、K7RKScan と CVE-2025-1055 についての記述
  8. 8. 影響（暗号化・破壊・改ざん）確認済[1]
    保護が無効化された端末から順に Warlock が現れた。 `run.exe`・`rune.exe` と身代金要求文 「how to restore your files.txt」が**33台以上**で記録された。 配布元は**ドメインの SYSVOL 共有**（`\\<ドメイン>\SYSVOL\<ドメイン>\scripts\run\`）で、 1行コマンドで Public プロファイルへ複製して起動する形である。 3台のホストでは**複製サービス `dfsrs.exe` を親プロセスとして** 同じ SYSVOL パスから検体が届いた記録が取れ、 **別途の配布機構ではなく通常の SYSVOL 複製で届いたことが確認された**。
    根拠: Symantec が示した1行コマンド、33台以上の観測、dfsrs.exe を親とする3台の記録

webshell の置き方に工夫があります。 Symantec によれば、このグループは SharePoint の LAYOUTS ディレクトリに複数の SharePoint の版に対して同時に webshell を落とします——どの版が実際に入っていても動くようにするためです。webshell の役目はSharePoint ファームの ASP.NET マシンキーの収集で、奪ったキーで正しく署名されたペイロードを偽造し、SharePoint のアプリケーションプール内で遠隔コード実行を成立させます。

配布の仕組みが本件の勘所です。 最終段階で攻撃者は、ドメインの SYSVOL 共有（\\<ドメイン>\SYSVOL\<ドメイン>\scripts\run\）にrun.exe と rune.exe を置きました。SYSVOL はすべてのドメインコントローラへ自動的に複製され、ドメイン全体から読める場所です。Symantec は3台のホストから、複製サービスdfsrs.exe を親プロセスとして run.exe・rune.exe が同じ SYSVOL パスから届いた記録を取っており、「別途の配布機構ではなく通常の SYSVOL 複製で届いたことを確認した」としています。

つまり攻撃者は、1台ずつ押し込む代わりに組織が正常に運用している複製の仕組みに乗せたわけです。AV/EDR 無効化の道具の配布も同じ発想で、内部 IP のネットワーク共有をマウントして複製し起動する1行コマンドが定型的に使われています。

署名済みの道具で検知を抜ける——脆弱なドライバと VS Code のトンネル原因・手口出典 [1]

Longlegs の検知回避には、正規に署名されたものを使うという共通点があります。

1. 脆弱なドライバ（BYOVD）。 セキュリティ製品を落とすために、署名済みだが脆弱なドライバ K7RKScan（CVE-2025-1055）を悪用します。これはカーネル層で保護されたセキュリティプロセスを終了させられるもので、Symantec は「bring-your-own-vulnerable-driver（BYOVD）技法の明確な例」としています。なお重要インフラ1件の侵入で使われた a.exe について、Symantec は「脆弱なドライバを利用したとみられるが、その正体は不明のままである」とし、「同グループの他の最近の攻撃では K7RKScan を使っていた」と述べるにとどめています。

2. VS Code のトンネル。 Computer 4 ではcode-insiders.exe tunnel service install --accept-server-license-terms が実行され、VS Code 内蔵のトンネル機能がサービスとして導入されました。Symantec の指摘は明快です——VS Code Insiders のバイナリは Microsoft の署名が付き、トンネルは Microsoft 自身の基盤を中継するため、開発者や IT 管理者の端末から出て当然とされる通信に紛れやすい。

3. ペイロードの取得先。 後続のペイロードはcatbox.moe や wasabisys.com といった正規のクラウドファイル共有・ストレージから取られています。Symantec は90分の間に2つの異なるホスティングサービスと3つの別名のパッケージが使われたことから「複数のペイロードを用意しており、単一の配送経路に依存していなかった」と評しています。

4. 環境常駐の道具。 偵察とコマンド実行は net・whoami・nltest のような標準の道具が多用され、横展開には NetExec（nxc.exe）—— CrackMapExec の後継として活発に保守されているオープンソースの道具——が使われました。

5. アカウント名の擬装。 ローカル Administrators へ追加されたドメインアカウントは SPSEPRDSetup でした。Symantec は「SharePoint は SPS／SP を頭に付けたセットアップ用のサービスアカウントを作ることが多いため、擬装の試みとみられる」としています。

署名・正規サービス・標準の道具・それらしい名前という4点が重なると、1つ1つの事象は「見慣れたもの」に見えます（本記録の評価）。Symantec が公表した IoC も、ハッシュ19件のうち6件は「疑わしいファイル」という分類で、確定した悪性ではありません。

狙われている SharePoint の不備は6件に特定できた——2026年7月14日の CISA 勧告が対象対策・注意喚起出典 [3] [4]

Symantec の分析は「2026年7月に CISA が勧告で警告した、より新しい SharePoint の不備」と述べるだけで番号を示していませんでした。2026年10月2日の報道を起点に、本記録はこの勧告を特定しました。

対象は米 CISA の "CISA Urges SharePoint Hardening After New Exploitations"（2026年7月14日公表・8月26日改訂）で、挙がっている CVE は次の6件です。

  • CVE-2026-32201
  • CVE-2026-45659
  • CVE-2026-56164
  • CVE-2026-58644
  • CVE-2026-50522
  • CVE-2026-55040

影響はサポート対象のオンプレミス SharePoint Server 全版（Subscription Edition・2019・2016）に及びます。CISA は「サイバー脅威アクターがこれらの脆弱性を悪用して、オンプレミスのSharePoint Server インスタンスへの不正アクセスを得ている」（原文英語）とし、悪用後の活動として IIS のマシンキーの窃取とデシリアライズの手法による永続化を名指ししています。これは本記録が追った侵入の手口とそのまま一致します。

勧告が求めている対処は6つです。

  1. SharePoint Server をインターネットへ直接露出させない
  2. 最新の更新を適用し、適用が成功したことを検証する
  3. AMSI 統合を有効にし、全要求本文の検査を設定する
  4. IIS のマシンキーを回転させる前に、侵害痕跡を探す
  5. 悪用の検知に足るログ取得ができているかを確認する
  6. SharePoint 管理センターへの外部アクセスを遮断する

4番目の順序は見落としやすい点です。先に鍵を回すと、偽造されたペイロードが弾けるようになる代わりに、既に入られていた痕跡を読む手がかりが失われます。本記録が追った侵入では、webshell の役目がまさにマシンキーの収集でした。

ただし、この6件を挙げたのは報道（SecurityWeek）です。 Symantec 自身は本稿に番号を示しておらず、「同グループの手持ちに含まれるかもしれない」という推定の表現で書かれています（齟齬に記録）。自組織の SharePoint については、どれが使われたかの特定を待たずに6件すべてを対象にするのが妥当です（本記録の判断）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Symantec は被害組織の**業種と言語圏までを出し、組織名と所在国を出さない**という 範囲で公表した。IoC（ファイルハッシュ19件・ネットワーク2件）と 具体的なコマンド列は出している部分的に機能**本記録の評価。** 防御に使える材料（コマンド・配布経路・ドライバ・IoC）は 十分に出ている。帰属（「中国系」）の根拠と、 被害組織側の対応の経過が出ていないため、 CISO が意思決定に使える部分は技術側に偏る
CISO・経営層への示唆
  • 「ドメイン全体に一斉配布できる経路」を資産として棚卸しする
    本件の暗号化は、攻撃者が作った配布機構ではなく **組織が正常に運用している SYSVOL 複製**で広がった。 `dfsrs.exe` を親とする記録がそれを裏づけている。 同じ性質の経路は SYSVOL だけでなく、GPO・配布サーバー・ EDR や RMM の遠隔実行機能にもある。
    取るべき行動 **「1回の操作で全端末に届く経路」の一覧を作り、 それぞれに承認・記録・警報を付ける。** 一覧に載った経路は、通常の変更管理より厳しい扱いにする。 棚卸しの単位は「技術」ではなく「全端末に届くか」である。
  • 検知から封じ込めまでの猶予を「約2時間」で見積もる
    本件では AV/EDR 無効化の道具が**約2時間で40台以上**に広がり、 保護が落ちた端末から順に暗号化が始まった。 検知してから人を集めて判断する運用では間に合わない。
    取るべき行動 **「EDR の保護が広範囲で無効化された」を、人の判断を待たずに 自動で封じ込めに入る条件として定義する**（セグメントの切断・ 認証の一時停止など）。 自動化できないなら、2時間以内に誰が何の権限で切れるかを明記する。
  • 重要インフラでは「金銭目的か国家背景か」を分けずに備える
    本件は Warlock というランサムウェアでありながら、 Symantec は開発元を中国系の脅威アクターとし、 標的に水道事業者・通信事業者・地方政府が入っている。 Dark Reading の言う「犯罪集団のように見え APT のように振る舞う」状態である。
    取るべき行動 **脅威シナリオを「動機」で分けるのをやめ、 「どの経路でどこまで広がるか」で分ける。** ランサムウェア対策と標的型攻撃対策を別の予算・別の体制で持っている場合は、 検知と封じ込めの部分を統合する。
  • ベンダーの分析から「自組織の判断材料」として取れる層を見極める
    本稿は攻撃側の記述であり、**被害組織の検知・封じ込め・復旧・ 身代金の方針はいずれも書かれていない。** 帰属の根拠も示されていない。CISO が意思決定に使える部分は技術側に偏る。
    取るべき行動 **ベンダーレポートを読むときに「事実／ベンダーの評価／ 書かれていないこと」の3欄に分けて整理する様式を使う。** 「書かれていないこと」の欄が自組織の判断に効く項目で埋まる場合は、 そのレポートを意思決定の根拠にしない。
セキュリティ技術者への示唆
  • SYSVOL 配下への実行ファイルの出現を、最優先の警報にする
    本件で暗号化の直前に起きたのは、SYSVOL の `scripts\run\` に `run.exe`・`rune.exe` が置かれたことである。 **ここに実行ファイルが現れた時点が、ドメイン全体への配布が始まる前の 最後の分岐点**だった（本記録の評価）。
    取るべき行動 **全ドメインコントローラの SYSVOL 配下を対象に、 `.exe` / `.dll` / `.ps1` の作成・変更をファイル完全性監視で検知し、 即時の警報にする。** 正規のログオンスクリプト更新と区別するため、 変更の承認記録と自動で突き合わせる。
  • SharePoint のパッチを当てたら、マシンキーをローテーションする
    本件の webshell の役目は **ASP.NET のマシンキーの収集**であり、 奪ったキーで**正しく署名されたペイロードを偽造**している。 **キーが漏れた後は、パッチを当てても偽造された要求を 署名の正当性では弾けない。**
    取るべき行動 **ToolShell の影響を受けた可能性があるオンプレミス SharePoint ファームは、 パッチ適用とマシンキーのローテーションを1つの作業として扱う。** ローテーションはファームの全ノードで揃え、 実施記録を残す（当てたが回していない環境が残りやすい）。
  • 署名済み・正規サービスの通信を「見慣れたもの」として通さない
    本件の遠隔接続は **VS Code のトンネル**（Microsoft 署名・Microsoft の基盤を中継）、 ペイロードの取得先は **catbox.moe と wasabisys.com**（正規のクラウド共有）、 検知回避は**署名済みの脆弱なドライバ**だった。 署名も宛先も正規であるため、属性だけでは弾けない。
    取るべき行動 **「誰が署名したか」ではなく「どこに置かれ、どのプロセスが起動したか」で 判定する条件を作る**（例: `C:\Windows\debug\` 配下の `code-insiders.exe`、`w3wp.exe` を親とする `msiexec`）。 サーバーからの外向き通信は宛先の許可制にする。
  • EDR の稼働状況を、EDR 以外の経路で監視する
    本件では保護を落とす道具が先に全域へ配られた。 **保護が落ちた後の端末からは EDR の記録が上がってこない**ため、 EDR の管理画面だけを見ていると「静かになった」ようにしか見えない。
    取るべき行動 **EDR エージェントの稼働台数・心拍を資産管理やログ収集基盤の側で数え、 台数の急減を単独の警報条件にする。** 併せて改ざん防止（tamper protection）を有効化し、 無効化の試行を外部へ即時転送する。
  • 帯域外検証用ドメインへの通信を検知条件に入れる
    本件では `oastify.com`（Burp Collaborator）のサブドメインへ 外向き要求が出ており、**標的自身のドメイン名が埋め込まれていた**。 自組織が正規の脆弱性診断を行っていない限り、 この宛先への通信に業務上の説明は付かない。
    取るべき行動 **oastify.com・interact.sh 等の帯域外検証用ドメインへの DNS 照会を 警報にし、自組織・委託先の診断の予定と突き合わせる台帳を持つ。** 予定が無ければ侵害調査に入る。
  • ベンダーが「某月の勧告」と書いたら、番号まで突き合わせてから作業に入る
    Symantec は「2026年7月に CISA が警告した、より新しい SharePoint の不備」と 書くだけで番号を示していなかった。**番号が分からないままでは 自社の適用状況を照合できない。** 本記録は CISA の勧告（2026年7月14日・8月26日改訂）を特定し、 対象が **CVE-2026-32201・CVE-2026-45659・CVE-2026-56164・ CVE-2026-58644・CVE-2026-50522・CVE-2026-55040 の6件**であることを確認した。 加えてこの勧告は、**マシンキーの回転の前に侵害痕跡を探す**という 順序を明記している——順序を逆にすると痕跡を読む手がかりが先に消える。
    取るべき行動 **ベンダーレポートに「某月の当局勧告」と出てきたら、勧告本体を引き当てて CVE 番号・影響版・推奨手順まで自組織の台帳に落とす。** SharePoint については ToolShell の4件と上記6件の**計10件**を1つの対象集合として扱い、 パッチ適用の検証 → 痕跡調査 → マシンキーの回転 の順で回す。 AMSI 統合と全要求本文の検査、SharePoint 管理センターへの外部アクセス遮断も 同じチェックリストに入れる。

自組織に当てはまるか

観点自社に当てはまるか該当する場合に何が起きうるか
