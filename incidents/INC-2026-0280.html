INC-2026-0280KillSec 解体——10か国の共同作戦

2026年9月30日、ドイツ・ハンブルク州刑事局（LKA Hamburg）とハンブルク検察が主導し10か国が参加した国際共同作戦**「Operation KillSwitch」**により、ランサムウェア／データ恐喝グループ **KillSec**（2024年ごろから活動）の**リークサイトと中核サーバー5台が押収**された——**3名を仮逮捕**、ギリシャ・ルーマニア・スペイン・英国で**8か所を捜索**し、少なくとも**110テラバイト**の窃取データを以後のアクセスから保全した。捜査対象は**全世界で約1,000件の攻撃**で、そのうち**約500件が成功**したと認定、**ドイツ国内が70件以上（うちハンブルク関係18件）**。**主たる運営者（アドミン）と目されるのは16歳**、開発者と目される者は**2026年8月に18歳になった**が一部の犯行時は未成年だった。ほかに交渉役と affiliate の容疑者を特定。捜査当局は**同グループが AI を使ってランサムウェアの基盤構築・運用と標的の選定を行っていた**と述べている。Europol・Eurojust と民間の Bitdefender・Group-IB が支援

初報: 2026年10月1日 最終更新: 2026年10月1日

2026年9月30日、ランサムウェア／データ恐喝グループ KillSec に対する国際共同作戦 「Operation KillSwitch」 が実施されました。主導したのはドイツ・ハンブルク州刑事局（LKA Hamburg）とハンブルク検察で、捜査は2025年に始まっています。

押収と逮捕の内容は次のとおりです。

  • ダークウェブのリークサイトを押収（押収告知に差し替え）。サイトに置かれていた少なくとも110テラバイトの窃取データを以後の不正アクセスから保全した
  • 中核サーバー5台を当局の管理下に置いた——グループの運営に使われていた主サーバーと、被害組織から奪ったデータを保管していた複数のサーバー
  • 3名を仮逮捕し、ギリシャ・ルーマニア・スペイン・英国で8か所を捜索
  • 暗号資産を含む犯罪収益の追跡に着手

容疑者の構成で最も注目されたのは年齢です。

  • 主たる運営者（アドミン）と目される人物は16歳
  • 開発者と目される人物は2026年8月に18歳になったが、一部の犯行の時点では未成年だった
  • ほかに交渉役（negotiator）と affiliate の容疑者を特定

規模について当局は、捜査対象を全世界で約1,000件の攻撃とし、現時点で約500件が成功したと認定しています（「分析の継続で数字は変わりうる」と留保つき）。ドイツ国内の事案は70件以上で、そのうち18件がハンブルクに関係します。なお押収前の KillSec のリークサイトには約450の被害組織が掲載されていました。

手口は、脆弱性と脆弱に保護された入口（クラウドストレージを含む）を突いて侵入し、機微な内部データを自前の基盤へ複製して、リークサイトでの公開を盾に恐喝するという形です。Europol は KillSec が「相当額（substantial）」の身代金を得ていたとしています。捜査で判明した点として当局が挙げたのが、同グループが AI を使ってランサムウェアの基盤を構築・運用し、標的候補を選定していたことです。

作戦にはベルギー・フィンランド・ドイツ・ギリシャ・オランダ・ルーマニア・スペイン・スイス・英国・米国の当局が参加し、Europol と Eurojust、民間からは Bitdefender と Group-IB が支援しました。

本記録として押さえておきたいのは、組織の中核が「サーバー」ではなく「人」であるという当局・民間双方の見方です。Group-IB の Dmitry Volkov は「サーバーは数週間で置き換えられるが、基盤を作り、すべての攻撃を承認する人々は置き換えられない」（原文英語）と述べています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

KillSec の手口は、**フィッシング・RDP への総当たり・既知の脆弱性の悪用・ クラウドストレージの設定不備**（Group-IB）という4つの経路で組織に侵入し、 機微な内部データを自前の基盤へ複製して、 **ダークウェブのリークサイトでの公開を盾に恐喝する**ものである。 RaaS として affiliate を募り（参加費 250〜1,000 米ドル・身代金の 12〜20% が取り分）、 Windows と VMware ESXi の暗号化プログラムを開発し、 **窃取データを別途販売するデータブローカーとしても機能**していた。 **各段階の技術的な詳細（使われたマルウェア・コマンド・滞留時間）は公表されていない。** 以下の chain は Group-IB と当局が示した経路の記述に基づく概括であり、 **特定の被害組織の侵害を追ったものではない。**

  1. 1. 初期侵入推定[1] [2] [4]
    Group-IB が挙げた4経路——**フィッシング・RDP への総当たり・ 既知の脆弱性の悪用・クラウドストレージの設定不備**。 当局の表現は「脆弱性と、クラウドストレージを含む 脆弱に保護された IT システムへの入口を悪用した」である。 **いずれも広く知られた経路であり、新規の技法は挙げられていない**（本記録の評価）。
    根拠: Group-IB press release の TTP 記述と、ハンブルク警察・Europol の概括的な記述
  2. 2. 収集確認済[1] [2] [6]
    侵入後、**機微な内部データを自社（攻撃者）の基盤へ複製**した （ハンブルク警察・SecurityWeek）。 押収された窃取データは**少なくとも110テラバイト**で、 **被害組織から奪ったデータを保管する専用のサーバーが 複数運用されていた**（押収された5台の内訳）。 **収集に使われた道具・選別の方法・滞留時間は公表されていない。**
    根拠: ハンブルク警察の記述（機微な内部データを複製）、押収サーバーの内訳、110テラバイトという量
  3. 3. 持ち出し確認済[1] [2]
    複製したデータを攻撃者側の保管サーバーへ持ち出した。 押収された5台のうち複数が**窃取データの保管用**とされている。 **持ち出しの経路・プロトコル・宛先は公表されていない。**
    根拠: 押収された5台のサーバーの内訳（主サーバーと窃取データ保管用の複数サーバー）
  4. 4. 影響（暗号化・破壊・改ざん）確認済[1] [2] [3] [4] [6]
    **恐喝。** 窃取データをダークウェブのリークサイトに掲載すると脅し、 支払わなければ公開する（支払いを拒んだ場合、 ファイルが**無償で配布される**こともあった——SecurityWeek）。 Telegram チャンネルも併用。 **窃取データを別途販売するデータブローカーとしても機能**していた（Group-IB）。 Windows と VMware ESXi 向けの暗号化プログラムも開発していたが、 **当局の記述の中心はデータ窃取型の恐喝**である。 Europol は「相当額（substantial）」の身代金を受け取っていたとする。
    根拠: Europol・ハンブルク警察の恐喝の記述、SecurityWeek の無償配布の記述、Group-IB の暗号化プログラムとデータ販売の記述

Group-IB の記述はより具体的で、4つを挙げています。

  • フィッシング
  • RDP への総当たり攻撃
  • 既知の脆弱性の悪用
  • クラウドストレージの設定不備

恐喝の形は、窃取した企業データを使って「支払わなければ公開する」と脅すもので、支払いを拒んだ被害組織のファイルは無償で配布されることもあったとSecurityWeek は伝えています。

本記録の評価として1点だけ付け加えます。16歳が主たる運営者と目され、AI が基盤の構築に使われていたという2つの事実の組み合わせは、「ランサムウェアの運営に必要な技術的習熟の量が下がっている」という読み方を誘います。ただし当局はそうした因果を述べておらず、本記録もその推論を確定したものとして扱いません。言えるのは、約500件の成功した攻撃に使われたのはフィッシング・RDP 総当たり・既知の脆弱性・クラウドの設定不備というありふれた4経路だったということです。

4つのありふれた入口から約500件、そのデータ110TB が押収で当局の手に移った
KillSec は2024年ごろから、フィッシング・RDP 総当たり・既知の脆弱性・ クラウドストレージの設定不備という4経路で組織に侵入し、 機微データを自前の保管サーバーへ複製してリークサイトと Telegram で恐喝していた。 RaaS として affiliate を募り（参加費 250〜1,000 米ドル・身代金の 12〜20%）、 窃取データの別途販売も行っていた。 2026年9月30日の Operation KillSwitch で**リークサイトと中核サーバー5台、 110テラバイトのデータが当局の管理下**に移り、3名が仮逮捕された。 **押収によって、被害組織が掲載一覧を外部から確認する手段も同時に失われた。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
当局は**役割（アドミン・開発者・交渉役・affiliate）と年齢（16歳・18歳）を公表し、 国籍・所在国・逮捕された3名の役割の対応を公表しない**という範囲を選んだ部分的に機能**本記録の評価。** 捜査上の制約として妥当な範囲と考えられるが、 **押収によってリークサイトという唯一の外部確認手段が消えた**ため、 被害組織の側に残る手段が「当局の分析を待つ」だけになっている点は 記録に残す必要がある
**リークサイトを停止させるのではなく押収して押収告知に差し替え**、 さらに Operation KillSwitch の専用サイト（法執行機関の動画を含む）へ 遷移させる形にした機能した**本記録の評価。** 「サーバーは置き換えられるが人は置き換えられない」という Group-IB の見方と整合しており、 **押収告知と専用サイトは抑止を狙った設計**と読める
CISO・経営層への示唆
  • 「暗号化されていないから被害ではない」という線引きをやめる
    KillSec の恐喝の中心は**データの窃取と公開の脅迫**であり、 当局の記述も「機微な内部データを複製した」ことに置かれている。 窃取データは**別途販売**もされていた。 業務が止まらないため、組織の中で事案として扱われにくい。
    取るべき行動 **インシデント対応の起動条件に「暗号化の有無」ではなく 「機微データが外部へ出た可能性」を置く。** 公表・本人通知・当局報告の判断基準も、 データ窃取型の恐喝を前提にした版を用意する。
  • 外部監視（リークサイト）に依存した被害把握の弱さを認識する
    本件では**リークサイトが押収され、押収告知に差し替わった**。 結果として、外部の調査者・被害組織・報道が 「誰が掲載されていたか」を確認する手段が失われた。 自社が含まれるかを確かめる経路は、いま当局の分析を待つしかない。
    取るべき行動 **「自社が被害に含まれるか」を外部の掲載情報に頼らず判定できるようにする**—— 外向きの大量転送、機微データの異常な読み出し、 未知の宛先への通信の記録を自社側で保持する。 保持期間を侵害調査に耐える長さに決める。
  • 攻撃の規模と技術的な高度さを切り離して評価する
    約500件の成功を支えたのは**フィッシング・RDP 総当たり・ 既知の脆弱性・クラウドの設定不備**という4つのありふれた経路だった。 主たる運営者と目されるのは16歳で、 当局は基盤の構築と標的の選定に AI が使われていたと認定している。
    取るべき行動 **防御投資の優先順位を「攻撃者の高度さ」ではなく 「自組織に残っている基本的な入口」で決める。** 露出した RDP、公開設定のクラウドストレージ、 未修正の外部公開資産、パスワードのみの認証—— この4つが残っているかを四半期ごとに確認する。
  • 押収された自社データの行き先について、当局とのやりとりの窓口を持つ
    押収された**110テラバイト**の扱い（被害組織への通知・返却・削除）は 公表されていない。被害組織から見れば、 自社のデータが押収物として当局の手元にある状態が続く。
    取るべき行動 **海外当局の作戦で自社データが押収された場合の照会経路を、 法務と連携して事前に整理する**（自国の窓口・弁護士・ 業界団体のどこを通すか）。 個人データが含まれる場合の通知義務の判断も併せて検討する。
  • 解体の報道を「脅威の消滅」と読まない
    当局は他の構成員の捜索を続けており、 **残る affiliate の総数は公表されていない。** Group-IB は「サーバーは数週間で置き換えられる」と述べている。 RaaS の構成員は別のブランドへ移ることが一般的である。
    取るべき行動 **解体の発表を受けても、当該グループの TTP に対する 防御の優先度を下げない。** 脅威情報の管理台帳では「グループ名」ではなく 「侵入経路と手口」を単位にして対策の有効性を追う。
セキュリティ技術者への示唆
  • インターネットに露出した RDP を資産台帳で名指しして潰す
    Group-IB は KillSec の侵入経路に **RDP への総当たり攻撃**を挙げている。 当局も「脆弱に保護された IT システムへの入口」としている。 総当たりが成立するのは、露出と弱い認証が揃っているときである。
    取るべき行動 **外部から自組織の 3389/TCP と RDP ゲートウェイを走査し、 見つかったものを台帳に載せて期限付きで閉じる。** 業務上必要なものは VPN・多要素認証・接続元 IP 制限の後ろへ移し、 例外は申請制にして期限を切る。
  • クラウドストレージの公開設定を継続的に走査する
    当局は侵入の入口に**クラウドストレージ**を明示し、 Group-IB は**設定不備（misconfiguration）**を挙げている。 設定不備は一度直しても、新しいバケット・共有の作成で再発する。
    取るべき行動 **匿名アクセス可能なバケット・共有・公開リンクを定期的に走査する仕組みを作り、 検出を是正の起票に直結させる。** 新規作成時に公開を既定で禁止する組織ポリシーも併せて入れる。
  • 外向きの転送量を宛先ごとに記録し、基準線との乖離を検知する
    押収された窃取データは**少なくとも110テラバイト**で、 攻撃者は**専用の保管サーバーを複数運用**していた。 全体の量が判明したのは攻撃者側のサーバーが押収されてからである—— **被害組織側で量を把握できていた形跡は示されていない。**
    取るべき行動 **プロキシ・ファイアウォールのログから、宛先ごとの 外向き転送量の基準線を作り、乖離を警報にする。** サーバーからの外向き通信は宛先の許可制にする。
  • ESXi を含む仮想化基盤の管理面を分離する
    Group-IB は KillSec が **Windows と VMware ESXi の暗号化プログラム**を 開発していたとしている。 ESXi が暗号化されると、その上の全仮想機器が同時に止まる。
    取るべき行動 **ESXi の管理インターフェイスを業務ネットワークから分離し、 到達できる端末を限定する。** ホスト上の SSH を既定で無効にし、 バックアップを仮想化基盤の認証から切り離した保管先に置く。
  • 恐喝の監視を「自社名」だけでなく「取引先名」でも行う
    KillSec は窃取データを**別途販売するデータブローカー**としても 機能しており、被害組織は金融・医療・政府機関・大企業に及ぶ。 自社のデータが取引先経由で出ることもある。
    取るべき行動 **リークサイト・恐喝 Telegram の監視対象に、 主要な委託先・取引先の名称も入れる。** 検出時の照会手順（契約上の通知義務の確認を含む）を決めておく。
