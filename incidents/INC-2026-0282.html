INC-2026-0282Fakturownia 侵害で請求書流出

ポーランドの請求書・簡易会計 SaaS **Fakturownia**（利用事業者60万社超）が2026年9月28日、**システムの脆弱性を突かれてサーバへ不正アクセスされた**と公表した——同社の一次公表によれば**不正アクセスは9月27日 3:20ごろから9月28日 17:45ごろまで**続き、**約2,250アカウントについては2022〜2026年のデータが広範に抜き出された**。影響対象として挙げられたのは**会社・利用者のアカウント情報（氏名・NIP・住所・メール・電話）、パスワードのハッシュ、API トークンと連携鍵、銀行口座番号と支払履歴、2024年10月16日以前に登録された取引先情報、2021年3月22日以前に発行された請求書の全文、倉庫文書と操作ログ**で、**支払カード情報と KSeF（国の電子インボイス制度）の証明書は侵害されていない**とされる。財務省も KSeF 側の侵害・流出は検出されなかったと表明した。**「Fingerprint」を名乗る人物が6TBの請求書を盗んだと主張しているが、真正性も全体像も独立に検証されていない**

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用
初報: 2026年9月29日 16:15（Fakturownia の初報） 最終更新: 2026年10月1日 16:00（Fakturownia の更新1）

ポーランドの請求書発行・簡易会計 SaaS Fakturownia は、2026年9月28日にサーバへの不正アクセスを検知したと公表しました。同社のサービスは60万社を超える事業者が使っているとされます。

同社の一次公表（fakturownia.pl/incydent。初報は9月29日 16:15、更新1は10月1日 16:00）から確認できた事実は次のとおりです。

  • 権限のない第三者がシステムの脆弱性を利用し、保存データの一部に到達した
  • 不正アクセスの期間は2026年9月27日 3:20ごろ〜9月28日 17:45ごろ
  • 検知と最初の遮断は9月28日 13:35、アクセス権の失効は同日 18:01
  • 約2,250アカウントについては、2022〜2026年のデータが広範に抜き出された
  • 影響対象として挙げられたデータ項目は、会社・利用者のアカウント情報（氏名・NIP・住所・メールアドレス・電話番号）、パスワードのハッシュ、API トークンと連携用の鍵、銀行口座番号と支払履歴、2024年10月16日以前に登録された取引先情報、2021年3月22日以前に発行された請求書の全文、2019年6月6日以前の請求書明細行、倉庫文書と操作ログ、添付ファイルのメタ情報
  • KSeF（Krajowy System e-Faktur。国の電子インボイス制度）にアクセスするための証明書は侵害されておらず、当該データは安全なままである
  • 対応として、アプリケーション鍵とサービスのパスワードのローテーション（9月28日 18:56〜20:14）、新規に構築したサーバへの移行（同日 20:44〜21:51）、API トークンの交換と IP 制限（9月28〜29日）、PDF 生成部分の強化（9月29日）
  • UODO（個人データ保護庁）・CERT Polska・CBZC（サイバー犯罪対策中央局）へ報告し、外部の専門家とともに調査している
  • 利用者には、パスワードの再設定、連携の API 鍵の更新、請求書に記載された銀行口座番号の確認、二要素認証の有効化、予期しない支払依頼を既知の電話番号で確認することを求めている

ポーランド財務省は、KSeF 側の検証では制度の安全性の侵害もKSeF 内のデータの流出も検出されなかったと表明しました（報道による）。デジタル問題担当のクシシュトフ・ガフコフスキ副首相は「これもまた民間企業に影響する別のサイバーインシデントである。責任者は追跡されており、重大な結果に直面することになる」（原文ポーランド語・報道の英訳経由）と述べました。

一方で、「Fingerprint」を名乗る人物がポーランドのセキュリティ媒体Zaufana Trzecia Strona の記者に接触し、アプリケーションのディレクトリ、顧客情報、データベースダンプの画面写真を示したうえで、6テラバイトの請求書を盗んだと主張していると報じられています。この数値も、示された資料の真正性も全体像も、独立に検証されていません（The Record の記述）。同一の名前は、ポーランドの医療系ソフトウェアMyDr および Medyc の侵害についても犯行を主張しています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表されているのは「システムの脆弱性を利用してサーバ上の 保存データの一部に到達された」という1文と、到達期間 （9月27日 3:20ごろ〜9月28日 17:45ごろ）、 抜き出された範囲（約2,250アカウントの2022〜2026年のデータ）だけである。** 脆弱性の種類・所在、権限昇格や横展開の有無、 持ち出しの経路と量はいずれも示されていない。 対応の一覧に PDF 生成部分の強化が含まれるが、 **公表はそれが侵入経路だったとは述べていない。**

  1. 1. 初期侵入確認済[1]
    **権限のない第三者がシステムの脆弱性を利用し、 Fakturownia のサーバに到達した**（2026年9月27日 3:20ごろ）。 **脆弱性の種類・所在は公表されていない。** 認証の突破を伴ったのか、認証前に到達できたのかの区別も示されていない。
    根拠: Fakturownia の公表「osoba nieuprawniona wykorzystała lukę w systemie」および到達開始時刻
  2. 2. 収集確認済[1]
    **保存データの広範な取得。** 公表によれば **約2,250アカウントについて2022〜2026年のデータが広範に抜き出された**。 対象には**請求書の全文（2021年3月22日以前発行分）、 取引先情報（2024年10月16日以前登録分）、銀行口座番号と支払履歴、 API トークンと連携鍵、パスワードのハッシュ、倉庫文書、操作ログ**が含まれる。 **取得の手段（データベースの直接参照か、 アプリケーションの機能を通じた列挙か）は公表されていない。**
    根拠: Fakturownia の公表（影響項目の一覧と「約2,250アカウント・2022〜2026年」という範囲）
  3. 3. 認証情報アクセス確認済[1]
    **パスワードのハッシュ、API トークン、連携用の鍵が 影響対象として挙げられている。** 同社はこれらを**ローテーション・交換の対象として扱った** （9月28日 18:56〜20:14 に鍵とサービスパスワード、 9月28〜29日に API トークン）。 **ハッシュの方式・ソルトの有無は公表されていない。**
    根拠: Fakturownia の公表（影響項目にハッシュ・トークン・鍵が含まれ、対応としてローテーションが実施されたこと）
  4. 4. 持ち出しunconfirmed[1] [2]
    **持ち出しの経路・量は公表されていない。** 攻撃者を名乗る人物が6テラバイトの請求書を持ち出したと主張しているが、 **真正性も全体像も独立に検証されていない**（The Record の留保）。 **Fakturownia はデータ量に言及していない。**
    根拠: The Record の報道（攻撃者の主張と、それが未検証であることの明記）
  5. 5. 影響（暗号化・破壊・改ざん）確認済[1] [2]
    **公表された影響は、保存データの一部への到達と抜き出しである。** 同社は**支払カード情報・連携経由で保存されたデータ・ KSeF 用の証明書は影響を受けていない**とし、 財務省も**KSeF の侵害と KSeF 内データの流出は検出されなかった**とした。 **抜き出されたデータの悪用（なりすまし請求・振込先すり替え）の 実例は公表されていない。** 同社は利用者に**請求書記載の銀行口座番号の確認**と **予期しない支払依頼の電話確認**を求めている。
    根拠: Fakturownia の公表と、報道が伝える財務省のコミュニケ

公表された影響対象のデータ項目は次のとおりです。

  • 会社・利用者のアカウント情報（氏名・NIP（納税者番号）・住所・メールアドレス・電話番号）
  • パスワードのハッシュ（「暗号化された」とされるが方式は非公表）
  • API トークンと連携用の鍵
  • 銀行口座番号と支払履歴
  • 2024年10月16日以前に登録された取引先（kontrahent）情報
  • 2021年3月22日以前に発行された請求書の全文
  • 2019年6月6日以前の請求書明細行
  • 倉庫文書と操作ログ、添付ファイルのメタ情報

支払カード情報と、連携経由で保存されたデータは影響を受けていないとされます。KSeF にアクセスするための証明書も侵害されていないと明記されています。

ここで重要なのは、この一覧の中身が「Fakturownia の顧客のデータ」に収まっていないことです（本記録の評価）。請求書の全文と取引先情報は、利用事業者の取引相手—— Fakturownia と契約していない第三者——の氏名・住所・口座番号を含みます。請求書 SaaS の侵害は、契約者数の次元ではなく「契約者 × その取引先」の次元で影響が広がる構造です。

影響を受けた顧客の総数は、まだ特定中とされています。公表されている約2,250アカウントは「2022〜2026年のデータが広範に抜き出された」範囲であり、列挙された項目の射程と同じとは書かれていません。

原因は「システムの脆弱性」の一語——種類も所在も公表されていない原因・手口出典 [1]

公表されている原因は、「権限のない第三者がシステムの脆弱性を利用した」という記述だけです。どの構成要素か、既知の脆弱性を放置していたのか、未知のものだったのかは示されていません。分析は CERT Polska とともに継続中とされています。

対応の一覧に「PDF 生成部分の安全性強化」（9月29日）が含まれている点は記録に残しておきます。請求書 SaaS の PDF 生成は、外部からの入力をテンプレートに流し込む処理であり、過去に多くのサービスでサーバ側のファイル読み出しやコード実行の経路になってきた部分です。ただし公表は「これが侵入経路だった」とは述べていません。 本記録は経路を断定しません（この段落の読みは本記録の評価です）。

なお同社は公表ページで、ブラウザに Fakturownia のタブを開いたままにしていると、ログイン試行が無くても二要素認証の SMS が自動送信される事象についても注意を掲示しています。インシデントそのものとは別の案内ですが、「身に覚えのない 2FA の SMS」が利用者の不安の種になる局面で先に説明を置いたものと読めます（本記録の評価）。

KSeF への波及は否定された——制度側と事業者側の双方が表明波及・関係先出典 [1] [2]

この事案が注目された理由のひとつは、Fakturownia がKSeF（Krajowy System e-Faktur。ポーランドの国の電子インボイス制度）と連携していることです。多くの事業者に利用が義務づけられる制度です。

否定は双方向から出ています。

  • ポーランド財務省: 検証ではKSeF の安全性の侵害も、KSeF 内に保持されたデータの流出も検出されなかった（報道による）
  • Fakturownia: KSeF にアクセスするための証明書は侵害されておらず、当該データは安全なままである（一次公表）

つまり、「制度の中のデータ」は無事で、「制度につながる事業者が自前で持っていたデータ」が出たという形です（本記録の整理）。

この区別は日本でも同じ形で現れます（本記録の評価）。電子インボイスや公的な申請基盤の安全性は、基盤そのものの堅牢さと、それに接続する無数の SaaS の堅牢さの掛け算で決まります。基盤側が「侵害されていない」と言えることは、利用者の請求データが守られたことを意味しません。

6TB という数字は攻撃者の主張であり、裏付けは無い未確定事項出典 [2]

報道では、「Fingerprint」を名乗る人物がポーランドのセキュリティ媒体 Zaufana Trzecia Strona の記者に接触し、アプリケーションのディレクトリ、顧客情報、データベースダンプの画面写真を示したうえで、6テラバイトの請求書を盗んだと主張したと伝えられています。

The Record は明示的に留保を置いています——「この数値も、盗まれたとされる資料の真正性と全体像も、独立に検証されていない」（原文英語）。

Fakturownia の公表には、データ量への言及がありません。本記録はこの6TBを figures に残しますが、「報道が伝えた攻撃者の主張」「流出の可能性が否定できない範囲」として扱い、断定の根拠には使いません。

同じ名前は、ポーランドの医療系ソフトウェア MyDr（8月時点でポーランドのサイバー当局が、約1,880万人と1万2,000超の医療機関に関係しうる過去データへの不正アクセスがあったとした事案）とMedyc（Qbusoft が開発）の侵害についても犯行を主張しています。同一主体であるかどうかは確認されていません。

日本の読者が引き取るべき点——請求 SaaS は「取引先の台帳」を預かっている評価・解釈出典 [1] [2]

本節は本記録の評価です。 Fakturownia も当局もこうは述べていません。

日本の CISO・技術者がこの事案から引き取れる論点は3つあります。

1つめ。請求・会計 SaaS は、自社の情報ではなく「取引関係の台帳」を預けている場所です。 流出したとされる項目は、口座番号・支払履歴・取引先情報・請求書全文です。これは「誰が誰にいくら払っているか」の一覧であり、ビジネスメール詐欺（BEC）にとって最も価値の高い材料です。自社の被害額ではなく、取引先に生じる誤送金として跳ね返ります。

2つめ。API トークンと連携鍵が影響項目に入っていることの意味です。請求 SaaS は、会計・銀行・EC・在庫と連携します。SaaS 1社の侵害が、そこに繋いだ先の権限まで持ち出す形になります。自社が「Fakturownia 相当のサービス」に発行したトークンを棚卸しできているか、権限が最小か、IP 制限が掛かっているかが問われます。

3つめ。公的基盤の「安全宣言」の読み方です。財務省は KSeF が侵害されていないと表明し、それは事実として記録されます。しかし利用者の請求データは出ています。「制度は無事」と「自分の請求書は無事」は別の文です。

検知できたテナント横断の読み出し（単位時間あたりの別テナント件数）にしきい値を置き、超過をアラートにする
影響を限定できた口座番号・取引先情報・請求書全文といった高価値列を暗号化し、復号鍵をアプリケーションとは別の権限で管理する
影響を限定できた古いデータ（本件では2021年以前の請求書全文・2019年以前の明細行）の保持期間を定め、オンラインのデータベースから落とす
認証情報アクセス公表されていない
トークンがその後に使われたかどうかの記述は無い。 **IP 制限を「交換と同時に」導入していることから、 交換前のトークンの悪用を想定していたと読める** （本記録の評価。公表はそう述べていない）
影響を限定できた発行済み API トークンに有効期限と発行元 IP の制限を最初から掛け、一括失効の手順を演習する
影響を限定できたパスワードのハッシュに十分な計算コストの方式（argon2 等）とソルトを用い、方式を公表できる状態にしておく
検知できたトークンの利用元 IP・UA の急な変化を検知の対象にする
持ち出し公表されていない

侵入を防げた請求書の振込先変更は、請求書そのものではなく既知の連絡先への電話など別経路で確認する運用を、取引先と相互に取り決める

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**アプリケーション鍵・サービスのパスワード・API トークンを すべてローテーション・交換し、API トークンには IP 制限を導入した**機能した**抜き出された資格情報の悪用を公表時点で止める手として、 最も効く順序で実施されている**（アクセス権失効 → 鍵 → 基盤 → トークン）。 ただし**悪用の有無が公表されていない**ため、 結果としての有効性は確認できない（本記録の評価）
**サービスを停止せず、新規に構築したサーバ基盤へ移行した** （9月28日 20:44〜21:51）評価材料なし移行先の基盤が同じ脆弱性を持たない保証は公表されていない。 **再侵入の有無が示されるまで評価できない**
**影響を受けた顧客の総数が未確定の段階で、 データ項目・日付の境界・約2,250アカウントという内側の数字を公表した**部分的に機能**項目と日付の境界まで出したのは評価できる**—— 利用者が「自分の請求書が対象か」を日付で判断できる。 一方で**総数の見通し（いつ特定できるか）が示されていない**（本記録の評価）
CISO・経営層への示唆
  • 請求・会計 SaaS は「取引関係の台帳」を預けている場所だと位置づけ直す
    流出対象として挙げられたのは、口座番号・支払履歴・取引先情報・ 請求書全文である。これは**誰が誰にいくら払っているかの一覧**であり、 BEC（ビジネスメール詐欺）にとって最も価値が高い材料である。 **自社の情報ではなく、取引先に生じる誤送金として跳ね返る。**
    取るべき行動 **委託先評価の台帳に「その SaaS が保持している第三者（取引先）の 情報」の欄を作り、請求・会計・購買・人材系を優先して埋める。** 取引先情報を含む SaaS については、侵害時の通知先に 自社の購買・経理部門を含める連絡経路を先に決めておく。
  • 公的基盤の「侵害されていない」という表明を、自社データの安全と読み替えない
    財務省は KSeF の侵害も KSeF 内データの流出も検出されなかったと表明し、 Fakturownia も KSeF 証明書は安全としている。それは事実である。 **それでも利用事業者の請求書・口座番号は出た。** 制度の堅牢さと、制度に接続する SaaS の堅牢さは別の問題である。
    取るべき行動 **電子インボイス・公的申請・eKYC など「制度につながる SaaS」を 一覧にし、制度側の安全性ではなく SaaS 側の実装・運用を評価対象にする。** 社内向けの説明文でも「基盤は安全」と「自社データは安全」を書き分ける。
  • 取引先からの「振込先変更」を請求書以外の経路で確認する運用を、相手と相互に取り決める
    Fakturownia が利用者に求めた行動には **請求書記載の口座番号の確認**と**予期しない支払依頼の電話確認**が 含まれる。口座番号と請求書全文が出た以上、 次に来るのは**本物の取引関係を知った上でのすり替え**である。
    取るべき行動 **一定額以上の振込先変更は、請求書・メール以外の経路 （既知の電話番号）での確認を必須にする規程を作り、 主要取引先と相互に合意して文書化する。** SaaS 侵害の通知を受けたら、当該 SaaS 経由の請求書の振込先を 遡って照合する手順を併せて用意する。
  • 第一報の品質は「時刻・項目・境界・利用者の行動」で測る
    本件の公表は、到達期間を分単位で示し、影響項目に日付の境界を付け、 利用者が取るべき行動を具体的に書いている。 **一方で総数と個別通知の予定は示していない。** どちらも自社が公表側に立ったときの判断材料になる。
    取るべき行動 **自社の第一報のひな型に、 ①到達・検知・封じ込めの時刻 ②影響項目と日付の境界 ③利用者が今日できること ④まだ分かっていないことと特定の見通し の4区画を作る。** 「調査中」だけで埋まる区画が無いかを演習で確認する。
  • 鍵を「全部替える」判断の代価（連携が止まる）を事前に見積もっておく
    本件では検知から約8時間半で鍵のローテーションと基盤移行まで到達した。 その代価として、**利用事業者は連携の API 鍵を更新する作業を負った。** 速度は、代価を払う覚悟が事前にあって初めて出る。
    取るべき行動 **「自社が発行した鍵・トークンを全部失効させたとき何が止まるか」を サービス単位で書き出し、所要時間と顧客への影響を見積もる。** 見積もりが出ていないサービスは、失効の演習を年1回入れる。
セキュリティ技術者への示唆
  • 請求書 SaaS の「入力を解釈する処理」を脆弱性管理の最前面に置く
    原因は「システムの脆弱性」の一語だが、 対応の一覧には**PDF 生成部分の安全性強化**が含まれている。 請求書 SaaS の PDF 生成は、利用者の入力をテンプレートに流し込み、 外部参照を解決しうる処理である。 **公表は経路を明言していない**が、点検すべき場所の候補は示している。
    取るべき行動 **PDF・帳票生成、CSV/XML 取り込み、画像変換、テンプレート描画を 一覧にし、依存ライブラリのバージョンと外部参照（URL・ファイルパス）の 扱いを確認する。** 外部参照を既定で禁止し、 生成処理を最小権限の別プロセス・別ネットワークで動かす。
  • テナント横断の読み出しに件数のしきい値を置く
    **約2,250アカウント分を横断して取り出す操作**は、 通常の利用と量・順序の両面で異なる。 本件では到達から検知まで約34時間かかっている。
    取るべき行動 **「単位時間あたりに触れた別テナントの数」をメトリクスとして出し、 しきい値超過をアラートにする。** アプリケーションの認可（テナント境界）だけに頼らず、 データベース側の監査ログでも横断読み出しを可視化する。
  • 古いデータをオンラインのデータベースに置き続けない
    流出対象には**2021年3月22日以前の請求書全文**と **2019年6月6日以前の明細行**が含まれる。 **攻撃者が持ち出したのは、現在の業務に必要ではないデータである。** 日付の境界が公表されたことで、保持期間の設計がそのまま被害範囲になった ことが見える（本記録の評価）。
    取るべき行動 **請求書・明細・添付の保持期間を法令上の必要年数で定め、 それを超えた分は検索可能なオンライン領域から 分離保管（暗号化・別権限）へ移す。** 移行前に「何年分がオンラインにあるか」を数えて記録に残す。
  • API トークンには最初から有効期限と IP 制限を掛け、一括失効を演習する
    本件では API トークンが影響項目に入り、 対応として**交換と IP 制限の導入**が同時に行われた。 **IP 制限が事後に導入されたという事実は、 それ以前は掛かっていなかったことを示す**（本記録の評価）。
    取るべき行動 **発行済みトークンの一覧に「有効期限・許可元 IP・最終利用日時」を 持たせ、未使用のトークンを自動失効させる。** 全トークンの一括失効と再発行を、年1回は本番で演習する。
  • パスワードハッシュの方式を「公表できる状態」にしておく
    公表は「暗号化されたパスワードのハッシュ」とするだけで、 方式・ソルトの有無を示していない。 そのため**利用者は「再設定で足りるのか、使い回し先も替えるべきか」を 判断できない**（本記録の評価）。
    取るべき行動 **ハッシュ方式（argon2id 等）とパラメータを、 インシデント時にそのまま公表できる形で文書化しておく。** 古い方式が残っているアカウント群があれば、 次回ログイン時の再ハッシュで棚卸しを完了させる。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 請求・会計・購買の SaaS に、取引先の口座番号・請求書全文を預けている本件で流出対象となったのは、まさにこの範囲である。 自社が契約していない第三者（取引先）の情報が SaaS 1社の侵害で外に出る構造になっている。
データの保持□ 請求書・明細・添付を、保持期間を定めずオンラインのデータベースに置き続けている本件では2021年以前の請求書全文と2019年以前の明細行が対象に入った。 **保持期間の設計がそのまま被害範囲になる。**
認証・認可□ 外部サービスへ発行した API トークンに、有効期限・許可元 IP・最終利用日時の管理が無い本件では API トークンと連携鍵が影響項目に入り、 事後に IP 制限が導入された。 失効と再発行の手順が無いと、鍵の総入れ替えに時間がかかる。
システム構成□ 帳票・PDF 生成やファイル取り込みなど「外部入力を解釈する処理」が、本番データベースと同じ権限で動いている本件の対応には PDF 生成部分の強化が含まれる。 入力を解釈する処理は外部公開面の中でも攻撃面が広く、 そこから本番データへ到達できる構成は被害を広げる。
運用・監視□ テナント横断の読み出しに対する件数しきい値やアラートが無い本件は到達から検知まで約34時間を要した。 2,250アカウント分の横断読み出しは、量で気づける種類の操作である。
体制・契約□ 取引先との間で「振込先変更の確認経路」を文書で取り決めていない口座番号と請求書全文が出た事案では、 次の実害が振込先のすり替えとして現れる。 確認経路の取り決めが無いと、請求書そのものが唯一の根拠になってしまう。
