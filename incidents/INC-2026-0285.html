INC-2026-0285悪性npm 101件が WhatsApp 加入

セキュリティ企業 OX Security が2026年9月28日、**WhatsApp の OSS ライブラリ Baileys を悪用した悪性 npm パッケージ101件**を「**PhantomSub**」と名付けて公表した——これらを導入した開発者が WhatsApp の認証を通すと、**ソケット層に仕込まれた処理が本人の同意なくアカウントを攻撃者側の群・チャネルへ加入させ、気づかれないよう通知をミュートする**。累計ダウンロードは**約49万回**、直近30日だけで**約11万6,000回**で、**公表時点で npm から削除されていたのは16件**にとどまる。購読の仕込み方は3種——**19件は実行時に GitHub からチャネルIDを取得**し、**60件はソースコードに平文で埋め込み**、**14件は符号化・難読化して隠す**。確認されたチャネルの多くは**インドネシアの小規模なボット販売・市場チャネル**で、**フォロワー数がボットスクリプト・ボット作成代行・「プレミアム」APK・SNS 水増しサービスを売るための信用指標として使われていた**。パッケージ名も公開者も異なるのに**同一のチャネルID・遠隔のチャネル一覧・GitHub アカウントが繰り返し現れ**、OX は「**チャネルを共有しているとは、受益者を共有しているという意味だ**」と述べている

脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年9月28日（OX Security の公表） 最終更新: 2026年9月30日（報道）

セキュリティ企業 OX Security は2026年9月28日、WhatsApp 用のオープンソースライブラリ Baileys を悪用した悪性 npm パッケージ101件を発見し、この活動を「PhantomSub」と名付けて公表しました。

公表（OX Security のブログ）から確認できた内容は次のとおりです。

何が起きるか

  • 開発者がこれらのパッケージを使ってWhatsApp の認証を通すと、仕込まれたコードが本人の同意なく、そのアカウントを攻撃者側の群（グループ）・チャネルへ加入させる
  • 気づかれないように通知をミュートするものもある
  • 仕込みはWhatsApp のソケット層に対して行われる

規模

  • パッケージ101件
  • 累計ダウンロード約49万回、直近30日で約11万6,000回
  • 2026年9月28日時点で npm から削除されていたのは16件（残りは公開されたままだった）
  • ダウンロードの多いもの: ourin-baileys（130,589回）、@nexustechpro/baileys（62,155回）、@badzz88/baileys（52,173回）、levvleys（37,007回）。ほかに neuralwhatsapp・my-auto-follow などの名前が確認されている

3つの仕込み方

方式 件数
実行時に GitHub からチャネルIDを取得（新版を出さずに宛先を変えられる） 19件
ソースコードにチャネルIDを平文で記述 60件
チャネルIDを符号化・難読化して隠す 14件

誰が得をするのか

  • 確認されたチャネルの多くはインドネシアの小規模なボット販売・「市場」チャネルだった
  • フォロワー数が、ボットスクリプト・ボット作成代行・「プレミアム」APK・SNS の水増しサービスを売るための信用指標（social proof）として使われていた
  • 具体例として、Fyxzpedia.ID – Utama（4,800フォロワー）、CORTANA TECH（1,300）、「I LOVE YOU」（2,400）、MONTE – BMG（1,000）、Neural（798）などが挙がっている
  • ある群はMobile Legends: Bang Bang や TikTok のアカウントを宣伝しており、紐づく電話番号は「Dan」という名前のインドネシアのWhatsApp ビジネスアカウントにつながった
  • パッケージ名も公開者も違うのに、同一のチャネルID・遠隔のチャネル一覧・GitHub アカウントが複数のパッケージで繰り返し現れた。 OX Security は「チャネルを共有しているとは、受益者を共有しているという意味だ」と述べている

先行する公表

  • 2026年8月: SafeDep が Baileys を複製した npm パッケージ群を発見。導入者の WhatsApp アカウントを秘密裏に攻撃者チャネルへフォローさせ、ボットが送る画像・動画に広告URLを差し込んでいた
  • 2026年9月: Xygeni のセキュリティ研究チームが、開発者の認証済み WhatsApp ボットセッションを攻撃者のニュースレターチャネルへ購読させる変種@dappaoffc/baileys-mod を公表

推奨

  • 自分の WhatsApp の群への加入履歴を確認し、不審な群を遮断・報告する
  • 悪性 Baileys パッケージを検出する手順を用意する
  • 個人の WhatsApp アカウントの連携を要求するパッケージは使わない

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**正規の OSS ライブラリ Baileys を複製し、 WhatsApp のソケット層へ「群・チャネルへの購読」処理を足したものを 別名で npm に公開する。** 開発者が導入して WhatsApp の認証を通すと、 **そのセッションで本人の同意なく攻撃者側の群・チャネルへ加入させ、 気づかれないよう通知をミュートする。** 宛先（チャネルID）の持ち方は3種——**実行時に GitHub から取得する19件、 ソースに平文で書く60件、符号化・難読化する14件。** **公開者が違っても同一のチャネルID・チャネル一覧・GitHub アカウントが 繰り返し現れ、受益者が共有されている。** 目的は**フォロワー数を信用指標として、 ボットスクリプト・ボット作成代行・「プレミアム」APK・ SNS 水増しサービスを売ること。**

  1. 1. 初期侵入確認済[1] [2]
    **開発者が npm から Baileys 系のパッケージを導入する。** 名前は **ourin-baileys・@nexustechpro/baileys・@badzz88/baileys・ levvleys・neuralwhatsapp・my-auto-follow** など、 **「Baileys の派生」に見えるもの**が並ぶ。 **正規の Baileys プロジェクトは侵害されていない**—— 攻撃者は正規コードを複製し、数行を足して別名で公開している。 **累計約49万回・直近30日で約11万6,000回**取得されており、 **ourin-baileys 1件で130,589回（累計の約27%）**を占める。
    根拠: OX Security の分析（101件の特定、パッケージ名、ダウンロード数）
  2. 2. 実行確認済[1] [2]
    **開発者が WhatsApp の認証を通した時点で、 仕込まれた処理が実行される。** **WhatsApp のソケット層**に対して、 **本人の同意なく群・チャネルへの購読操作**が差し込まれる。 **ライブラリの正規の機能を、ライブラリの内側から呼ぶ**形であるため、 外から見て不自然な通信は生じにくい（本記録の評価）。
    根拠: OX Security の分析（ソケット層への購読操作の注入）
  3. 3. C2通信確認済[1] [2]
    **19件は、実行時に GitHub からチャネルIDの一覧を取得する。** これにより**新しい npm バージョンを公開せずに 宛先（チャネル）を差し替えられる**。 残りは**ソースに平文で記述（60件）**または **符号化・難読化して埋め込み（14件）**である。 **公開者が異なるパッケージ間で、 同一のチャネルID・遠隔のチャネル一覧・GitHub アカウントが 繰り返し現れた。**
    根拠: OX Security の分析（3方式の内訳と、チャネルID・GitHub アカウントの重複）
  4. 4. 検知回避確認済[1] [2]
    **気づかれにくくするための細工が3つある。** ①**加入後に通知をミュート**して、 開発者が群の存在に気づきにくくする。 ②**14件はチャネルIDを符号化・難読化**して静的な検査を避ける。 ③**19件は宛先をコードに書かない**（実行時に GitHub から取得）。 さらに、**パッケージ名と公開者を分散させる**ことで 1件の削除が全体に波及しないようにしている （**公表時点で削除済みは16件のみ**）。
    根拠: OX Security の分析（ミュート、難読化14件、GitHub からの取得19件、削除16件）
  5. 5. 影響（暗号化・破壊・改ざん）確認済[1] [2]
    **確認された影響は「同意のない群・チャネル加入」と 「通知のミュート」である。** その結果、**チャネルのフォロワー数が水増しされ、 ボットスクリプト・ボット作成代行・「プレミアム」APK・ SNS 水増しサービスを売るための信用指標として使われていた。** 確認されたチャネルの多くは**インドネシアの小規模な ボット販売・市場チャネル**で、 **Fyxzpedia.ID – Utama（約4,800）・「I LOVE YOU」（約2,400）・ CORTANA TECH（約1,300）・MONTE – BMG（約1,000）・Neural（798）**などが 挙がっている。ある群は**Mobile Legends: Bang Bang や TikTok の アカウント**を宣伝しており、紐づく電話番号は **「Dan」名義のインドネシアの WhatsApp ビジネスアカウント**に つながった。 **実際に加入させられたアカウント数は公表されていない。**
    根拠: OX Security の分析（チャネルの性格とフォロワー数、宣伝内容、紐づく電話番号）

盗まれたのは資格情報ではなく「フォロワーになる権利」だった概観出典 [1] [2]

この事案で持ち出されたものは、資格情報でもデータでもありません。開発者の WhatsApp アカウントが「フォロワー」として使われたのです。

仕組みは単純です。

  1. 開発者が Baileys（WhatsApp 用の OSS ライブラリ）のフォーク・複製を npm から導入する
  2. WhatsApp の認証を通す（QR コードの読み取り等で自分のアカウントを連携させる）
  3. 仕込まれたコードが、そのセッションで本人の同意なく攻撃者側の群・チャネルへ加入させる
  4. 通知をミュートして、気づかれにくくするものもある

仕込みはWhatsApp のソケット層に対して行われます。ライブラリの正規の機能を、ライブラリの内側から呼ぶだけなので、外から見て不自然な通信は出ません（本記録の評価）。

目的は金銭です。 ただし直接の窃取ではありません。確認されたチャネルの多くはインドネシアの小規模なボット販売・「市場」チャネルで、フォロワー数が、ボットスクリプト・ボット作成代行・「プレミアム」APK・SNS の水増しサービスを売るための信用指標（social proof）として使われていたとされます。

つまり開発者のアカウントは、「この売り手は信用できる」という見かけを作るために使われました。

101件のうち削除されたのは16件、直近30日でも11万6,000回取得されていた被害規模・影響範囲出典 [1] [2]

1つめ。公表時点でも現役でした。累計の約24%が直近30日に集中しており、削除は16件しか進んでいない。つまり85件は、公表の瞬間にも取得可能だったことになります。

2つめ。偏りが大きい。 ourin-baileys 1件で累計の約27%を占めます。次が @nexustechpro/baileys（62,155回）、@badzz88/baileys（52,173回）、levvleys（37,007回）。上位4件で約28万回——全体の6割近くです（本記録の算出）。

一方で、被害の規模を示す数値はひとつも公表されていません。何件が実際に WhatsApp の認証を通したのか、何アカウントが加入させられたのかは分かりません。ダウンロード回数には CI の再実行・ミラー・自動取得が含まれるため、被害者数の代わりには使えません（本記録の評価）。

仕込み方は3種類で、遮断の難しさが違う——19件は宛先を後から替えられる原因・手口出典 [1] [2]

OX Security は、購読の仕込み方を3種類に分けています。

方式 件数 性質
実行時に GitHub からチャネルIDの一覧を取得 19件 新しい npm バージョンを出さずに宛先を替えられる
ソースコードにチャネルIDを平文で記述 60件 読めば分かる。隠す努力をしていない
チャネルIDを符号化・難読化して隠す 14件 静的な検査を避ける意図がある

この3分類は、防御側にとって意味が違います（本記録の評価）。

  • 平文の60件は、依存パッケージのソースを読む・文字列を検索するだけで見つかります。逆に言えば、誰も読んでいなかったということです
  • 難読化の14件は静的な検査を避ける意図があり、実行時の挙動（どこへ接続し、何を購読するか）を見る必要があります
  • GitHub から取得する19件は最も厄介です。パッケージのコードを調べても宛先が書かれていない。しかも攻撃者は新版を公開せずにチャネルを差し替えられるので、「このバージョンは安全」という判定が成り立ちません

なお、3方式の合計は93件で、全体の101件に8件足りません。 残り8件の分類は、本記録の確認範囲では特定できませんでした（齟齬・留保に記録）。

そして「同じ受益者」の指摘です。パッケージ名も公開者も違うのに、同一のチャネルID・遠隔のチャネル一覧・GitHub アカウントが複数のパッケージで繰り返し現れた。OX Security の言葉を引きます—— 「チャネルを共有しているとは、受益者を共有しているという意味だ」。誰が公開したかに関わらず、そのチャネルの持ち主がすべてのパッケージからフォロワーを回収していくという指摘です。

この手口は、今回初めて見つかったものではありません。

  • 2026年8月: SafeDep が Baileys を複製した npm パッケージ群を発見。導入者の WhatsApp アカウントを秘密裏に攻撃者チャネルへフォローさせ、ボットが送る画像・動画に広告URLを差し込んでいた
  • 2026年9月: Xygeni が変種 @dappaoffc/baileys-mod を公表。開発者の認証済み WhatsApp ボットセッションを攻撃者のニュースレターチャネルへ購読させるものだった
  • 2026年9月28日: OX Security が101件をまとめて公表

2か月で3回、別のベンダーが別の切り口で見つけているという事実は、この生態系に継続的な収益性があることを示します（本記録の評価）。

SafeDep の報告には、本件より一段進んだ挙動があります—— ボットが送る画像・動画への広告URLの差し込み。これは群への加入にとどまらず、セッションを使って能動的にメッセージを操作している形です。

本件の101件についてそこまで行われたかは公表されていません。しかしセッションを握った側に何ができるかを考えると、群への加入は最も軽い使い方です（本記録の評価）。メッセージの送信、連絡先の読み出し、なりすましも技術的には同じ権限の内側にあります。

これは「依存パッケージの乗っ取り」ではなく「見た目が同じ別物の配布」である評価・解釈出典 [1] [2]

本節は本記録の評価です。

供給網の事案としての型が普段のものと違う点を整理します。

  • 正規プロジェクト（Baileys）は侵害されていません。メンテナのアカウントが奪われたわけでも、正規のバージョンに悪性コードが混ぜられたわけでもない
  • 攻撃者がしたのは、正規のコードを複製し、数行を足して別名で公開することです
  • 名前は ourin-baileys・@nexustechpro/baileys・@badzz88/baileys・levvleys・neuralwhatsapp・my-auto-follow など、「Baileys の派生」に見えるものが並びます

つまり依存関係の改ざんを検知する仕組み（ロックファイル・署名・バージョン固定）は、この手口に対して無力です。最初から別のパッケージを選ばせることで成立しているからです。

防御の軸は3つになります（本記録の提案）。

  1. 何を選んだか——フォーク・類似名のパッケージを選ばせないための台帳と承認（公開者・初公開日・本家との関係を確認する）
  2. 何を渡したか——個人や業務のアカウントをパッケージに連携させるという行為自体を管理対象にする。本件の被害は「認証を通した瞬間」に発生している
  3. 何が起きたか——WhatsApp 側の加入履歴を点検する。OX Security の推奨の1番目がこれである

2番目が本件の核心です。 npm のパッケージに脆弱性があるかどうかではなく、そのパッケージに自分のアカウントを丸ごと預けたかどうかが被害の分岐点でした。「依存パッケージの脆弱性を数える」活動では、この事案は1件も検出されません。

日本の読者が引き取るべき点——業務の WhatsApp ボットは「連携した人のアカウント」で動いている対策・注意喚起出典 [1] [2]

本節は本記録の評価です。 OX Security はこうは述べていません。

日本では WhatsApp の業務利用は欧米・東南アジアほど一般的ではありません。それでも引き取るべき論点は残ります。

1つめ。同じ構造は LINE・Slack・Discord・Telegram の非公式クライアントにも成立します。本件の鍵は「WhatsApp」ではなく、「非公式 API を叩くライブラリに、本人のアカウントを連携させる」という形です。海外拠点・取引先対応・個人開発でこの形を使っていないかを確認する価値があります。

2つめ。業務ボットは「誰かの個人アカウント」で動いていることがあります。本件が狙ったのは認証済みのセッションです。業務用の通知ボット・自動応答が、担当者個人の電話番号とアカウントで動いていれば、被害はその個人に及びます。ボットが使っているアカウントの名義を棚卸しする必要があります。

3つめ。「被害が軽い」ことが発見を遅らせます。この事案の直接の被害は「知らない群に入れられた」「通知がミュートされた」です。気づきにくく、気づいても報告されにくい。だからこそ49万ダウンロード・2か月で3回の公表という規模まで育ちました（本記録の評価）。軽微に見える異常（知らない群・勝手なミュート・見知らぬチャネルの購読）を報告させる経路を作っておくことが、この種の事案に対する実効的な検知になります。

**被害が軽微に見えることが、発見を遅らせた**（本記録の評価）。 「知らない群に入っている」「通知がミュートされている」は、 報告されにくい事象である。 **その結果、2か月で3回別のベンダーが公表する規模まで育った**
検知できた軽微に見える異常（知らない群への加入・勝手なミュート・見知らぬチャネルの購読）を報告させる経路を作り、報告に対して必ず反応する
影響を限定できた業務ボットが使うアカウントを担当者個人のものと分離し、名義と連携先を棚卸しする

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「依存パッケージの脆弱性を数える」活動では、この種の事案は1件も見つからない
    本件は正規プロジェクト（Baileys）の侵害ではない。 **攻撃者は正規コードを複製し、数行足して別名で公開した。** ロックファイル・バージョン固定・署名はいずれも **「最初から別のものを選んだ」ことに対しては無力**である。 既知の脆弱性（CVE）も付いていない。
    取るべき行動 **供給網の管理に「何を選んだか（選定）」の軸を足す。** 著名プロジェクトのフォーク・類似名パッケージを導入する際に、 **公開者・初公開日・本家との関係を記録して承認する**手続きを定める。 既存の依存についても、著名プロジェクトのフォークが 紛れていないかを一度棚卸しする。
  • 「アカウントをソフトウェアに連携させる行為」を管理対象として定義する
    本件の被害が発生したのは**WhatsApp の認証を通した瞬間**である。 パッケージの脆弱性ではなく、 **本人のアカウントを丸ごと預けたこと**が分岐点だった。 非公式 API のライブラリは、この預託を前提にしている。
    取るべき行動 **「業務または個人のアカウントを外部ソフトウェア・ ライブラリに連携させる行為」を社内規程の対象に明記する。** 対象（メッセージング・SNS・クラウドストレージ・会計）を列挙し、 **連携してよいアカウントの種類（専用アカウントのみ等）を定める。**
  • 業務ボットが「誰の名義のアカウント」で動いているかを棚卸しする
    本件が奪ったのは**認証済みのセッション**である。 業務の通知ボット・自動応答が担当者個人の電話番号と アカウントで動いていれば、**被害はその個人に及ぶ** （本記録の評価）。
    取るべき行動 **自動化・ボット・RPA が使っているアカウントの一覧を作り、 「名義」「連携しているソフトウェア」「権限の範囲」を記録する。** 個人名義のものを専用アカウントへ移す計画を立てる。
  • 被害が軽微に見える事象を報告させる経路を作る
    この事案の直接の被害は **「知らない群に入れられた」「通知がミュートされた」**である。 **気づきにくく、気づいても報告されにくい。** その結果、**累計約49万ダウンロード・2か月で3回の公表**という 規模まで育った（本記録の評価）。
    取るべき行動 **「不審だが被害が軽い」事象の報告窓口を明示し、 報告に対して必ず何らかの反応を返す運用にする。** 報告例（知らない群・勝手な設定変更・見知らぬ購読）を 社内向けの文書に具体的に書く。
  • 同じ構造が他のメッセージング基盤でも成立することを前提に点検範囲を決める
    本件の鍵は「WhatsApp」ではなく、 **「非公式 API を叩くライブラリに本人のアカウントを連携させる」** という形である。 日本では WhatsApp の業務利用は限られるが、 **同じ形は他の基盤でも作れる**（本記録の評価）。
    取るべき行動 **海外拠点・取引先対応・個人開発で使っている メッセージング連携ライブラリを洗い出す。** 公式 API（Business API 等）で代替できるものを特定し、 非公式 API に依存している箇所を記録する。
セキュリティ技術者への示唆
  • 新規に追加された依存のソースを機械的に検査する（60件は平文だった）
    **101件のうち60件は、チャネルIDをソースコードに平文で 書いていた。** 隠す努力をしていないということであり、 **ソースを読む・文字列を検索するだけで見つかった** （本記録の評価）。
    取るべき行動 **依存追加時に、パッケージの実体（node_modules ではなく公開物）に対して 外部URL・長い ID 列・難読化された塊・eval 相当の処理を 機械的に検索する手順を CI に入れる。** 検出されたら人が読む。
  • 実行時に外部から設定を取ってくる依存を異常として扱う
    **19件は実行時に GitHub からチャネルIDの一覧を取得していた。** **新版を出さずに宛先を替えられる**ため、 **「このバージョンは安全」という静的な判定が成り立たない。**
    取るべき行動 **開発環境・CI からの外向き通信を宛先の許可リストに限定する。** 依存パッケージが実行時に外部から設定・一覧を取得する挙動を、 実行時の検査またはネットワーク監視で検出する。
  • 非公式 API ライブラリの検証は、業務と無関係な専用アカウントと隔離環境で行う
    本件の被害は**認証を通した瞬間**に発生する。 **試しに動かしてみる**という行為そのものが被害の引き金になる （本記録の評価）。
    取るべき行動 **非公式 API ライブラリの評価用に、 業務と連絡先を共有しない専用アカウントと隔離環境を用意する。** 評価手順に「認証直後に群・チャネルの加入状況を確認する」工程を入れる。
  • 加入・購読・ミュートの状態を定期点検の対象にする
    攻撃側の細工のひとつは**加入後に通知をミュートする**ことだった。 **利用者が設定していないミュートが入っている**こと自体が 異常の印である（本記録の評価）。
    取るべき行動 **ボット運用の手順書に「群・チャネルの加入一覧と ミュート状態の定期確認」を入れる。** 前回との差分を残し、意図しない追加があれば遮断・報告する。
  • フォーク・類似名のパッケージを選ばないための確認項目を決める
    名前は **ourin-baileys・@nexustechpro/baileys・@badzz88/baileys・ levvleys・neuralwhatsapp・my-auto-follow** など、 **「Baileys の派生」に見えるもの**が並ぶ。 **本家と見分ける手掛かりは名前の中には無い**（本記録の評価）。
    取るべき行動 **導入前に確認する項目を固定する**—— ①本家リポジトリから辿れるか ②公開者が本家のメンテナか ③初公開日が新しすぎないか ④本家との差分が説明できるか。 **4項目のどれかが答えられないパッケージは入れない。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 著名な OSS プロジェクトのフォーク・類似名パッケージが依存に含まれており、本家との関係を記録していない本件は正規プロジェクトの侵害ではなく、 **複製＋数行の追加を別名で公開したもの**である。 本家との関係を確認していなければ、名前だけでは見分けられない。
認証・認可□ 業務または個人のメッセージング・SNS アカウントを、外部のライブラリ・ツールに連携させている本件の被害は**認証を通した瞬間**に発生した。 連携という行為が管理対象になっていなければ、 どこで何を預けたかが分からない。
運用・監視□ 自動化・ボットが担当者個人の名義のアカウントで動いている奪われるのは認証済みのセッションである。 個人名義で動いていれば、被害はその個人の連絡先・履歴に及ぶ。
システム構成□ 開発環境・CI から外向きの通信が自由にできる19件は**実行時に GitHub からチャネルIDの一覧を取得**していた。 外向き通信の制限が無ければ、宛先を後から替えられる仕掛けが機能する。
体制・契約□ 「不審だが被害が軽い」事象を報告させる経路が無い本件の直接の被害は「知らない群に入れられた」である。 報告されない事象が積み上がって、 約49万ダウンロードの規模まで育った。
データの保持□ 非公式 API ライブラリの検証を、業務アカウント・業務環境で行っている試しに動かすという行為そのものが被害の引き金になる。 隔離された専用アカウントが無ければ、評価と被害が同時に起きる。
