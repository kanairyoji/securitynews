INC-2026-0287新韓銀行で2.5万名の与信情報流出

韓国の新韓銀行（신한은행）が2026年10月1日、外部の非認可者が「非正常な方法」で一部サービスに接近し、顧客約2万5,000名の貸付申込関連の個人・信用情報が流出したと公表した。流出項目は顧客名・電話番号・CI（連携情報）・年間所得・算出限度などで、住民登録番号66件と CI 97件が含まれる。銀行は認知直後に非常対応体制を敷いて外部 IP を遮断し関連サービスを停止、鄭相赫（정상혁）行長名の謝罪文で「損害は責任を持って全額補償する」と表明した。金融監督院は前日（9月30日）から緊急の現場調査に入っている。流出の経路・手口と侵害の時期は公表されておらず、一部報道はクレデンシャルスタッフィングの可能性を挙げるにとどまる【続報・2026年10月2日】보안뉴스がセキュリティ業界の見立てとして手口を具体的に報じた——**初期侵入は貸付募集人が申込状況を照会するモバイル照会サービス「M 신한」と推定**され、攻撃者はダークウェブ等で事前に窃取した他プラットフォームの認証情報を無作為に大量投入して本人認証を突破した（速度制限・アカウントロックが無かったとみられる）。**侵入後は取得した顧客番号を改変して一般顧客向けの照会 API へ反復要求し、データを掻き集めた**——認証（Authentication）は通ったが、要求されたデータの閲覧権限をサーバ側で交差検証する認可（Authorization）が欠けていた典型的な Broken Access Control である。**確認された10余りの IoC の IP はすべて海外**で、自動化されたボット／AI エージェントによる攻撃の可能性が指摘されている。**いずれも銀行が認めた説明ではない**【続報2・2026年10月2日〜3日】**攻撃に使われたとされる道具の名前が初めて挙がり、当局の対応が業界横断に広がった**—— 보안뉴스は手口を**オープンソースで公開された AI ベースの自律型ペネトレーションテストツール**の悪用と推定し、 金融各社が当局の関連機関から「**AI エージェントを悪用した自動化攻撃が金融業界で発生したと推定され、さまざまな国の海外 IP を通じて攻撃が行われた**」との通知を受けたと報じた。 뉴시스（10月3日）はより具体的に、**ジニアンズ（Genians）セキュリティセンター長が、国内複数箇所への攻撃に使われたウェブサーバの一部から中国語ベースの AI 自律型侵入テストツール「ARTEX AI」に関連する文字列を確認した**と述べたと伝えたが、 **同記事は「実際の新韓銀行への攻撃過程で ARTEX AI が活用されたかは確認されていない」と明記している。** **金融保安院は2026年9月に金融業界を狙った AI Agent ベースの攻撃の試みを実際に探知したと表明**し、新韓銀行の事故の届出を受けた直後に**攻撃者の IP 等の脅威情報を銀行業界へ共有**した。 金融委員会は**10月2日に金融監督院・金融保安院・主要銀行・カード会社と「金融圏緊急状況対応会議」を開催**、金融業界全体へ**緊急セキュリティ点検**（外部に露出した電算システム・サービス、認証・アクセス統制の脆弱性）を指示した。 **ウリ銀行と NH農協銀行も攻撃を受けたが、情報流出の被害は確認されていない。** **ARTEX AI が本件に使われたことは誰も確認していない** 韓国の新韓銀行（신한은행）は2026年10月1日、外部の非認可者が「非正常な方法」で一部サービスに接近し、顧客約2万5,000名の個人・信用情報が流出したことを確認したと公表しました。

  • 規模 — 約2万5,000名。うち住民登録番号が66件、CI（連携情報）が97件
  • 項目 — 顧客名・電話番号・CI・年間所得・算出限度など、貸付（ローン）申込に関わる個人信用情報
  • 対応 — 認知直後に非常対応体制を敷き、外部 IP の遮断・関連サービスの停止・セキュリティの新規適用を実施
  • 経営の表明 — 鄭相赫（정상혁）行長名の謝罪文。「損害を受けた場合は責任を果たし全額補償する」
  • 当局 — 金融監督院（금융감독원）が前日（9月30日）から緊急の現場調査に入っている

日本の読者にとって重いのは、流出した項目の性質です。

漏れたのは住所や生年月日といった属性情報ではなく、年間所得と「算出限度」——つまり審査の結果そのものです。これは「この人はいくらまで借りられるか」という情報であり、貸付を装った詐欺の精度を直接上げます。本記録の評価として、名簿としての価値が属性情報とは別の次元にあります。

もう1つは CI（連携情報）です。韓国の本人確認制度で使われる、サービスをまたいで同一人物を結びつけるための識別子で、利用者側で変更できません（本記録の補足）。件数は97件と小さいものの、住民登録番号66件と合わせて「取り替えられない識別子」が外に出ています。

手口は公表されていません。報道には「認証を迂回する非正常な方法」「貸付募集人向けの『早見照会』の仕組みの弱点」「クレデンシャルスタッフィングの可能性」という記述が並びますが、いずれも銀行が認めた説明ではありません。銀行が述べたのは「非正常な方法で一部サービスに接近された」という事象の側だけです。

韓国の銀行では2026年7月のウリ銀行（우리은행）でも顧客情報の流出が起きており、報道はこれを「銀行業界のセキュリティが問われる」文脈で並べています。

本記録は経路を確定しません（以下は本記録の評価）。ただし、3つの記述が共通して指しているのは「本体のバンキングではなく、周辺の照会系」です。貸付の仮審査・事前照会のような仕組みは、顧客が入力した情報に対して審査結果（限度額）を返すという性質上、入力だけで出力が得られる窓口になりがちです。ここは、本人認証の強度と、照会そのものの速度制限・件数制限が別々の問題になる場所です。

報じられた筋は「認証を総当たりで抜き、顧客番号を付け替えて API から掻き集めた」——銀行は確認していない原因・手口出典 [6]

  1. 初期侵入——貸付募集人が申込の受付状況を確認するモバイル照会サービス「M 신한」が初期侵入経路と推定される。攻撃者はダークウェブ等で事前に窃取した他プラットフォームのアカウント情報を無作為に大量投入して本人認証の手続を突破した。
  2. 統制の欠落（入口）——「このサービスが内部者あるいは関係者向けのものであることを考慮しても、一定回数以上のログイン試行に制限を置くスロットリングやレート制限、アカウントのロックが無かったとみられる」。
  3. 横展開——侵入後、取得した顧客番号を改変して一般顧客向けの照会サービスのAPI へ反復的に要求を送り、データを掻き集めた。
  4. 統制の欠落（内側）——「アカウントの奪取による『認証』の後、そのアカウントが要求したデータに実質的な閲覧権限があるかをサーバ側で交差検証する『認可』の手続が不備だったのではないか」。同紙はこれを「典型的な認可の欠陥（Broken Access Control）」と呼んでいます。

同紙はさらに、「通常の金融業界の環境では、外部網と内部網の間の緩衝地帯（DMZ）を通じて非正常なトラフィックと API 要求を厳格に統制すべき」であり、「大量の非正常な情報呼び出しを実時間で遮断する『ランタイム防御』の体系がまともに働かなかった」と指摘しました。

匿名の金融セキュリティ専門家の評として、次の発言を伝えています（原文韓国語）。

本件は高度化した標的型ハッキングや単純なパッチ漏れではなく、基本中の基本である API 要求の改変および権限検証の不備で発生した明白なアプリケーションセキュリティの失敗である

この筋が重要なのは、2万5,000名という規模の説明になっている点です（本記録の評価）。募集人1人の資格で入った者が、顧客番号を付け替えるだけで一般顧客の情報を引き出せる状態であれば、流出の規模は「入れた資格の数」ではなく「照会を何回送れたか」で決まります。入口の総当たり対策と、内側の認可検証は別の統制であり、どちらか一方では規模を抑えられません。

ただし繰り返しになりますが、銀行はいまも「非正常な方法で一部サービスに接近された」としか述べておらず、金融監督院の調査結果も出ていません。上の4段は伝聞として読む必要があります。

「AI エージェントの攻撃」という評価には、それを示す証跡が示されていない（本記録の評価）評価・解釈出典 [6]

記事自身も、匿名の専門家の評としてこう締めています（原文韓国語）。

実務上の読み方はここにあります。 攻撃側が AI であったかどうかは、防御側の打ち手を変えません。本件で欠けていたと指摘されているのは、速度制限・アカウントロック・サーバ側の認可検証・照会量の監視という、いずれも AI 以前からある統制です。

対象者への個別通知ではなく、**ホームページとアプリに「自分の情報が流出したかを 確認できる照会メニュー」を設ける**方法を採り、専任の相談センターを置いた部分的に機能**本記録の作成者の評価である。** 公表と同日に照会の手段を出した点は機能している—— 顧客が「自分は対象か」を当日に確かめられる。 一方、**漏れたのは年間所得と算出限度であり、貸付を装う詐欺に直結する情報である。** 自己照会だけでは「何に注意すべきか」が届かない。 **個別通知と、手口を添えた注意喚起が別途必要になる。**
認知直後に**外部 IP を遮断**し、**関連サービスを停止**した （「スーパーSOL」「タンギョヨ」など主要サービスは本件と無関係と報じられている）評価材料なし**本記録の作成者の評価である。** 遮断と停止は実施されたと公表されているが、 **認知の日時・停止の範囲・復旧の時期がいずれも公表されていないため、 判断の速さと影響を評価できない。**
**流出項目と件数（約2万5,000名、住民登録番号66件、CI 97件）を具体的に示した**一方で、 **経路・手口、侵害の時期、接近された「一部サービス」の名称は示さなかった**部分的に機能**本記録の作成者の評価である。** 住民登録番号66件・CI 97件という内訳まで出したのは、 規模の実態を顧客が判断できる形であり評価できる。 一方、**手口が出ないため、同種の照会系を持つ他の金融機関は自社の点検箇所を 特定できない。** 報道が3つの異なる推測を並べる状態になっているのは、 説明の空白が埋められていないためである。
CISO・経営層への示唆
  • 審査の結果（与信限度・年間所得）は、属性情報より悪用の精度を上げる
    本件で漏れたのは住所や生年月日ではなく、年間所得と算出限度である。 「この人はいくらまで借りられるか」を知っている相手からの貸付の勧誘は、 顧客にとって見分けが難しい。
    取るべき行動 **自社が保持する「審査・スコアリングの結果」を洗い出し、 属性情報とは別の機微度で分類して保護水準と保持期間を決める。** 漏えい時の通知文に「どの情報が漏れたか」ではなく 「**その情報でどんな詐欺が来るか**」を書けるよう、文例を平時に用意する。
  • 本体の認証を守っても、周辺の照会系から情報は出る
    報道は3つの異なる推測を並べるが、いずれも本体のバンキングではなく 貸付の照会系を指している。보안뉴스は「ログイン認証に基づくバンキングサービス自体が 直接ハッキングされたのではないとみられる」と書いている。
    取るべき行動 **「入力すれば審査結果が返る」仕組み（仮審査・事前照会・募集人向けの照会）を システム台帳の中で別枠にし、本人認証・権限・速度制限・記録の4点を個別に点検する。** 本体の多要素認証の有無を、周辺の照会系の安全性の根拠にしない。
  • 自己照会だけの通知は、公表を知らなかった顧客に届かない
    銀行は公表と同日にホームページとアプリへ照会メニューを設けたが、 個別通知の方法と時期は公表されていない。 顧客が事故を知って自分で調べに来ることが前提になる。
    取るべき行動 **自己照会の手段と個別通知を、どちらか一方ではなく併用する前提で手順を作る。** 自己照会は「早く出せる」ことが利点であり、 個別通知は「届く」ことが利点である——**代替にならない。**
  • 当局が先に動き、公表が後になる順序は起こりうる
    報道によれば金融監督院は公表の前日（9月30日）から緊急の現場調査に入っていた。 公表が10月1日である。
    取るべき行動 **監督当局への報告と対外公表の順序・時間差を、平時に方針として決めておく。** 当局の検査が先に入っている状態で公表が遅れると、 「隠していた」という読み方を招く（本記録の評価）。
  • 変更できない識別子は、件数が小さくても別に数える
    本件では約2万5,000名の中に住民登録番号66件・CI 97件が含まれた。 住民登録番号と CI は利用者側で変更できない。
    取るべき行動 **漏えいの集計を「件数の合計」で終わらせず、 『変更できる情報（パスワード等）』と『変更できない識別子（公的番号・連結用ID）』に 分けて報告させる。** 後者はゼロでない限り、対応の設計が変わる。
セキュリティ技術者への示唆
  • 照会系は「認証の強度」と「照会の量」を別々に制御する必要がある
    報道が挙げる手口の候補（認証の迂回、クレデンシャルスタッフィング、 募集人向け照会の弱点）はいずれも、1回の照会が不正かどうかでは判定できない。 不正は「量」と「分布」に現れる。
    取るべき行動 **照会 API に、主体（利用者・端末・接続元・募集人コード）ごとの速度制限と 1日あたりの件数上限を入れ、超過時に自動で遮断する。** 併せて照会の記録を主体別に集計し、平常の分布から外れた増加を通報させる。
  • 応答に変更できない識別子を含めない
    流出項目に CI（連携情報）が含まれている。 CI はサービスをまたいで同一人物を結びつける識別子で、利用者側で変更できない。
    取るべき行動 **照会・審査の応答に含める項目を見直し、公的番号と連結用 ID は 応答に出さない（必要な場合はマスクするか、内部参照用の別 ID に置き換える）。**
  • 「外部 IP を遮断できた」ことは、記録が残っていた証拠でもある
    銀行は認知直後に外部 IP を遮断したと述べている。 接続元を特定できたということは、照会の記録が残っていたことを意味する（本記録の評価）。
    取るべき行動 **照会系のアクセス記録（接続元・主体・件数・応答の内容区分）を 機器や application の外へ転送し、調査に足る期間保全する。** 遮断の判断は記録の粒度に依存する。
  • 停止の範囲を事前に決めておかないと、止める判断が遅れる
    本件では「関連サービスの停止」と公表されたが、範囲と復旧時期は示されていない。 主要サービス（スーパーSOL 等）は無関係と報じられている。
    取るべき行動 **サービスを機能単位で切り分け、「この系統だけ止める」操作を平時に用意して試験する。** 全体を止めるか何も止めないかの二択しかない構成では、判断が遅れる。
