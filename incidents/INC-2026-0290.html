攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

認証を必要とせず、細工した HTTP / HTTPS 要求を FortiMail の管理インタフェースへ送ることで、 パストラバーサルと NULL バイトの無害化不備を突いて **基盤システム上の任意の場所にファイルを書き込む。** Fortinet が公開した IoC からは、書き込みの後に **共有ライブラリの先読み（`ld.so.preload`）による永続化**と、 **保存機能を使ったメールの外部転送の設定**が行われた形跡が読み取れる。 **ただし後段の機序は Fortinet が説明しておらず、本記録の読みである。**

  1. 1. 初期侵入確認済[1] [3]
    **認証されていない攻撃者**が、FortiMail の管理インタフェースへ **細工した HTTP または HTTPS 要求**を送る。 パス名の制限ディレクトリへの不適切な限定（CWE-22）と NULL バイト・NULL 文字の不適切な無害化（CWE-158）により、 **基盤システム上の任意の場所へファイルを書き込める。**
    根拠: Fortinet 勧告 FG-IR-26-175（CVE-2026-104286 の記述）
  2. 2. 実行推定[1] [3]
    書き込まれたファイルにより**任意のコードまたはコマンドが実行される。** BleepingComputer は「脆弱な機器上で未認可のコードまたはコマンドを実行するために 悪用されている」と報じている。 **Fortinet の勧告自体は「任意のファイルの書き込み」までを記述し、 実行に至る機序は説明していない**（書き込めるファイルの場所から 実行につながると読める）。
    根拠: BleepingComputer（2026年10月1日）、Fortinet の IoC（追加・改変されたファイル）
  3. 3. 永続化推定[1] [3]
    侵害された機器では、**`/data/etc/ld.so.preload` が追加され、 `/data/lib/liblog.so` が置かれている**（Fortinet の IoC）。 あわせて `/bin/smit`・`/data/etc/httpd.conf`・`/data/migadmin.tar.gz` が改変されている。 **これは共有ライブラリを先読みさせて正規のプロセスの挙動を書き換える形の永続化である** （**本記録の評価。Fortinet は用途を説明していない**）。
    根拠: Fortinet 勧告の IoC 一覧（ファイル7点と SHA-256）
  4. 4. 持ち出し推定[1] [3]
    Fortinet が示したログの例の1つは、 **`archive234` という保存用アカウントを CLI から設定し、 転送先を遠隔の `79.141.169.187` の `/uploads` に向ける**内容である。 BleepingComputer は 「攻撃者が侵害した FortiMail から保存データを外部のサーバへ送るよう 設定した可能性を示す」と書いている。 **Fortinet はこれを攻撃者の目的として説明していない**ため、 **段階としては「読み取れる形跡」である。**
    根拠: Fortinet 勧告のログの例（archive account の設定）、BleepingComputer の解釈

認証の前に届く要求でファイルを書き込める——しかも直す版がまだ無い概観出典 [1] [3]

Fortinet の勧告（FG-IR-26-175、2026年10月1日）の記述は短く、 実務上の要点は3つです。

第一に、攻撃の前提条件がほぼ無い。 欠陥は CWE-22（パストラバーサル）と CWE-158（NULL バイトの不適切な無害化）の 組み合わせで、 「認証されていない攻撃者が、細工した HTTP または HTTPS 要求により、 基盤となるシステム上に任意のファイルを書き込むことを許す可能性がある」 （原文英語）。 認証が要らず、要求を1つ投げられる位置にいれば届きます。 CVSS v3.1 は 9.8（Critical）。

第二に、すでに悪用されている。 勧告には「実際に悪用されているとの報告がある」と明記されています。 Fortinet は IoC まで公開しており、 侵害された機器で追加されたファイル4点・改変されたファイル3点、 攻撃元の IP 2件、確認に使えるログの例が示されています。 IoC を出す段階に至っているということは、 侵害された実機の解析が済んでいるということです（本記録の評価）。

第三に、修正版が存在しない。 Fortinet が挙げる FortiMail 8.0.2 / 7.6.7 / 7.4.9 はいずれも 「予定（upcoming）」であり、 本記録の作成者が2026年10月2日に確認した時点で入手できません。 つまり現時点で取れる手は回避策だけです。 そして 7.2 系には修正版の予定すら示されず、 7.4 系以降への移行が必要とされています。

この3つが重なると、利用者の選択は 「IBE を切るか、管理面をインターネットから外すか、製品を止めるか」に絞られます。

CISA は収載から3日で期限を切り、「塞ぐ」ではなく「調べる」まで求めた当局対応出典 [2]

CISA は2026年10月1日に CVE-2026-104286 を KEV カタログへ収載しました （本記録の作成者が catalogVersion 2026.10.01 を直接取得して確認）。 注目すべき点が3つあります。

期限が2026年10月4日——収載から3日です。 KEV の猶予は通常3週間程度が多く、 3日は「修正版が無いので塞ぐ以外の手を取れ」という性格の期限です。 要求事項には 「緩和策が利用できない場合は製品の利用を停止する」ことまで書かれています。

forensicTriage: Yes が立っています。 KEV の項目に「CISA の Forensics Triage Requirements に従う」ことが含まれており、 これは既に侵害されていないかを調べる義務です。 塞ぐだけでは要求を満たしません。 ところが——これが本事案の構造的な問題ですが—— 悪用がいつ始まったかが公表されていないため、 どこまで遡って調べるべきかの起点が分かりません（本記録の評価）。

ランサムウェアキャンペーンでの使用は Unknown です。 恐喝に使われているという情報は、この時点ではありません。

なお KEV の要求は米連邦民間機関に対する拘束であり、 日本の組織に法的な義務は生じません。 ただし「3日で調べて塞げ」という判断そのものが、 この脆弱性の危険度についての当局の読みです （本記録の評価）。

回避策が「IBE の無効化」である点から、脆弱な経路が読める対策・注意喚起出典 [1] [3]

勧告が示す回避策は2つです。

1. IBE（Identity Based Encryption）機能を無効にする

config system encryption ibe
set status disable
end

2. 管理インタフェースへのインターネットからのアクセスを無効にする、 または信頼する内部ネットワークに限定する

ここに読み取れることがあります。 勧告は影響を受ける構成要素を管理インタフェース（GUI）としていますが、 回避策の1つ目がIBE の無効化です。 さらに Fortinet が示した IoC のログの例には IBE の復号エラー（Invalid Base64 Encoding at pos 0）が含まれています。 これらを合わせると、 脆弱な処理は GUI のうち IBE に関わる経路（暗号化メールの受信者が ブラウザで復号する画面）にあると読めます。 これは本記録の作成者の推定です—— Fortinet は脆弱な関数も経路も説明していません。

実務上の判断に直結する問題が残ります。 IBE を使っていない組織は安全なのでしょうか。 勧告はそう書いていません。 そして IBE の無効化と管理面の遮断が 等価なのか、併用が必要なのかも書かれていません。 安全側に寄せるなら両方を実施するのが妥当です（本記録の評価）。

なお回避策には副作用があります。 IBE を無効にすれば外部の相手に暗号化メールを送る運用（受信者がブラウザで開く形）が 止まります。 管理面をインターネットから外せば遠隔からの管理が止まります。 どちらも「とりあえず実行」では業務が止まる種類の変更です。

侵害の痕跡は「ライブラリの先読み」と「保存データの外部転送」に現れている原因・手口出典 [1] [3]

ld.so.preload の追加は、 共有ライブラリを他のライブラリより先に読み込ませる仕組みで、 正規のプロセスの関数呼び出しを書き換えるために使われます。 liblog.so という名前のライブラリが同時に置かれていることから、 ログ出力に関わる関数を差し替えて痕跡を隠す、 あるいは常駐の足場を作っていると読めます （本記録の作成者の評価です。Fortinet は用途を説明していません）。 webconsole・mailservice という名前は正規の部品に似せたもので、 httpd.conf の改変はweb の経路を攻撃者側に向けるための変更とみられます。

もう1つ重いのがログの例です。 Fortinet が示した例の1つは、 archive234 という名前の保存用アカウントを CLI から設定し、 転送先を 79.141.169.187 の /uploads に向けるという内容です。 FortiMail の保存機能はメールのアーカイブを外部に送る仕組みなので、 これが攻撃者の設定であれば 通過するメールがそのまま外部へ流れることになります。 BleepingComputer も同じ読みを示していますが、 Fortinet はこれを「攻撃者の目的」とは述べていません。

つまり、この機器が狙われる理由は機器そのものではなく、 そこを通るメールにあるということです（本記録の評価）。

「悪用の開始時期が不明」なのに「フォレンジック調査」を求められる構造未確定事項出典 [1] [2] [3]

この事案には、実務者を困らせる不整合があります。

CISA は forensicTriage: Yes として、 既に侵害されていないかを調べることを要求しています。 しかしFortinet は悪用がいつ始まったかを公表していません。 BleepingComputer も 「Fortinet はいつから悪用されたか、何台が侵害されたか、誰が背後にいるかを 明らかにしていない」と書いています。

調査する側には、次が分かりません。

  • どこまで遡ってログを見ればよいのか（1か月か、半年か）
  • 自組織が狙われる側だったのか（標的が特定の業種・地域に偏っていたのか）
  • 侵害の規模（広範な走査か、絞った攻撃か）

結果として、現実的な手は 「IoC のファイル7点の存在確認と、2つの IP との通信の有無を、 手元に残っているログの全期間で見る」ことになります。 これはログの保存期間が調査の深さをそのまま決めるという意味です （本記録の評価）。

なお本記録は、IoC の悪性を独自に検証していません。 照合先のテレメトリを持たないため、 ここに挙げたハッシュと IP はFortinet の勧告の記載をそのまま引いたものです。

メールゲートウェイは「境界の外側に置かれた、メールが平文で通る機器」である評価・解釈出典 [1] [2] [3]

FortiMail のような製品の位置づけを考えると、 この脆弱性の重さが見えます。

メールセキュリティゲートウェイは、 組織のメールが出入りする経路の上に置かれます。 添付の検査やリンクの書き換えをするため、 中身を見られる位置にあることが設計の前提です。 そして管理のために web の画面を持ち、 運用の都合でそれがインターネットから見える構成になりやすい。

つまりこの種の機器は、 「外から届く」「中身が見える」「落とされると全社のメールに影響する」という 3つの条件を同時に満たします。 攻撃者から見れば、 1台を取るだけでメールの収集と組織内への足がかりの両方が手に入ります。

本件の IoC が 保存データの外部転送の設定を含んでいることは、 この構造がそのまま使われたことを示しています（本記録の評価）。

2026年に入ってから、境界に置かれる機器（VPN・メールゲートウェイ・ ファイル転送装置・ネットワーク機器）の認証前の脆弱性が 繰り返し悪用されています。 共通するのは「守るための機器が、守られていない」という点です。 エンドポイントには EDR が入り、サーバには監視が入っていても、 アプライアンスは中が見えず、ログも機器の中にしか無いことが多い。 本件で CISA がフォレンジック調査まで求めたのは、 この種の機器では「侵害されたかどうか」を後から調べる手立てが薄いという 認識の表れだと読めます（本記録の評価）。

判断評価評価の根拠と留保
Fortinet は**修正版が提供できていない段階で**勧告を公表し、 **IoC まで同時に公開した。** CISA は**同日に KEV へ収載し、3日という短い期限を切った。**機能した**本記録の作成者の評価である。** この判断は妥当だと考える。 すでに悪用されている脆弱性では、 **黙っていて守られるのは攻撃者だけ**である。 とくに評価したいのは**IoC を同時に出した**点で、 これにより利用者は「塞ぐ」と「既に入られていないか調べる」の両方に着手できる。 CISA が3日の期限とフォレンジック調査を課したのも、 修正版が無い状況では筋が通っている。 一方で**不足が2つある。** 第一に、**悪用の開始時期が示されていない。** フォレンジック調査を求めるなら、 **どこまで遡るべきかの目安が無ければ作業が設計できない。** 第二に、**IBE を使っていない構成が安全なのかが書かれていない。** 回避策が IBE の無効化であるのに、 影響を受ける構成要素は GUI とされており、 **自組織が対象かどうかを利用者が判定できない。**
CISO・経営層への示唆
  • 「修正版が無い脆弱性」では、意思決定は技術ではなく業務停止の判断になる
    本件で取れる手は**IBE を切る・管理面を外から切る・製品を止める**の3つで、 **いずれも業務に影響が出る。** 修正版（8.0.2 / 7.6.7 / 7.4.9）は「予定」であり、 本記録の作成者が2026年10月2日に確認した時点で入手できない。 CISA は期限を3日とし、 「緩和が利用できない場合は**製品の利用を停止する**」ことまで要求している。 **これは技術部門だけでは下せない判断である。**
    取るべき行動 **「修正版が無い重大脆弱性が自社の境界機器に出たとき、 誰が業務停止を判断するか」を事前に決めておくこと。** 具体には、①対象機器ごとに「止めたら何が止まるか」を1行で書いた一覧を持つ、 ②暗号化メール・遠隔管理といった機能を切る判断の権限者を定める、 ③判断に要る情報（影響する取引先・代替手段）を平時に用意しておく。 **緊急時に調べ始めると、3日の期限には間に合わない。**
  • 境界に置くアプライアンスは、侵害されたかを後から調べる手立てが最も薄い
    CISA が `forensicTriage: Yes` として調査を要求したのは、 **この種の機器では侵害の確認が難しい**という認識の表れと読める（本記録の評価）。 アプライアンスには EDR を入れられず、 ログは機器の中にしか無いことが多い。 本件の IoC には**`ld.so.preload` によるライブラリの先読み**が含まれており、 これは**機器のログ出力そのものを書き換えうる形**である （用途は Fortinet が説明していないが、 ログを汚染されれば機器内のログは証拠にならない）。
    取るべき行動 **境界に置く機器すべてについて「syslog を機器外に送っているか」を 棚卸しし、送っていない機器を今期中に潰すこと。** 費用は収集先の容量として見積もる。 あわせて**機器の構成（管理者・転送先・cron・ファイアウォール規則）の 定期的な取得と差分比較**を運用に組み込む。 **機器が掌握された後に機器の中を見ても、それは攻撃者が見せたい内容である。**
  • サポートの切れた系列を運用していると、緊急時に「移行」を要求される
    **FortiMail 7.2 系には修正版が示されず、7.4 系以降への移行が必要**とされた。 これは版を上げる作業ではなく**系列を乗り換える作業**で、 設定の互換性の確認と試験が要る。 **緊急の対応としては時間がかかりすぎる**（本記録の評価）。 理由は Fortinet が説明していないが、 サポート期間の扱いによるものと読める。
    取るべき行動 **境界機器の台帳に「ベンダーのサポート期限」の欄を設け、 期限の6か月前に移行を起案する運用にすること。** 本件のように**緊急時に移行を迫られる**と、 試験を省いた移行か、脆弱なまま運用を続けるかの二択になる。 平時の更新は費用の問題だが、緊急時の移行は事故の原因になる。
  • メールゲートウェイの侵害は、情報漏えいであると同時に「出口の掌握」である
    Fortinet が示したログの例には、 **保存用アカウントを追加して外部サーバへ送る設定**が含まれている。 FortiMail は組織のメールが通過する位置にあるため、 掌握されれば**通過するメールがそのまま流れる**ことになりうる （BleepingComputer も同じ読みを示しているが、 **Fortinet はこれを攻撃者の目的として述べていない**）。 さらにメールゲートウェイは**組織の全員に届くメールを操作できる位置**でもある。
    取るべき行動 **「メールゲートウェイが侵害された場合」を想定した対応計画を、 個別に作っておくこと。** 含めるべきは、①通過したメールを侵害期間について漏えいと見なすかの判断基準、 ②機器が持つ資格情報（LDAP / AD の連携用アカウント、 API キー、証明書）の入れ替えの手順、 ③取引先への通知の判断。 **機器の復旧（塞ぐ）と、漏えいの評価（何が出たか）は別の作業である。**
セキュリティ技術者への示唆
  • 最初の一手は版の更新ではない——修正版が存在しないため、到達性を断つことから始める
    欠陥は**認証の前に到達できる**管理インタフェースの要求処理にある。 修正版（8.0.2 / 7.6.7 / 7.4.9）は未提供で、 待っている間も悪用は続いている。 **到達性を断つことだけが、今日できる確実な対処である。**
    取るべき行動 **今日のうちに2つを実施する**—— ①**管理インタフェース（GUI）へのインターネットからの到達を断つ** （信頼する内部ネットワークに限定）、 ②**IBE を使っていなければ無効化する** （`config system encryption ibe` → `set status disable` → `end`）。 **勧告はこの2つを等価とも併用必須とも書いていないため、 安全側に寄せて両方を実施する。** IBE を業務で使っている場合は、 切る前に相手方への連絡と代替手段を用意する。
  • IoC の確認は「ファイルの有無」と「2つの IP との通信」の2本で足りる
    Fortinet は**追加・変更された7つのファイルを SHA-256 付きで**、 **攻撃に関連する2つの IP** を公開している。 悪用の開始時期が不明なため期間を絞れないが、 **確認そのものは具体的である。**
    取るべき行動 **次の順で確認すること**—— ①機器上に `/data/etc/ld.so.preload`・`/data/lib/liblog.so`・ `/data/bin/webconsole`・`/data/bin/mailservice` が存在するか （**存在自体が異常**）、 ②`/bin/smit`・`/data/etc/httpd.conf`・`/data/migadmin.tar.gz` が 勧告のハッシュと一致するか、 ③ファイアウォールのログで 79[.]141.169.187 と 45[.]129.0.192 への／からの 通信が**手元に残っている全期間**にあるか、 ④機器の構成に**見覚えのない保存アカウント**（例: archive234 のような名前）や **cron のジョブ**が追加されていないか。
  • 機器のログを機器の中だけに置いていると、フォレンジック調査が成立しない
    Fortinet が示したログの例には、 **IBE の復号エラー・認証失敗・保存アカウントの追加・cron の実行**が含まれる。 **攻撃の痕跡はログに出ていた。** しかし IoC に `ld.so.preload` と `liblog.so` が含まれることから、 **ログ出力の経路自体を書き換えられうる**と読める（本記録の評価）。 機器内のログだけに頼る構成では、 侵害後に「残っているログが信用できない」状態になる。
    取るべき行動 **FortiMail の syslog を機器外の収集先へ転送し、 最低でも次の4つを検知・通知の対象にすること**—— ①IBE の復号エラー、②管理者の認証失敗の多発、 ③保存アカウント（archive account）の追加・変更、 ④cron のジョブの追加。 **転送は侵害後ではなく今設定する**—— 侵害されてからでは、送られるログも疑わしい。
  • 侵害が見つかった機器は、設定を引き継いだ復旧をしてはならない
    IoC には**改変された設定ファイル（`/data/etc/httpd.conf`）と アーカイブ（`/data/migadmin.tar.gz`）**が含まれる。 設定のバックアップから復元すると、 **攻撃者の仕込みも一緒に戻る可能性がある**（本記録の評価）。 また機器は LDAP / AD の連携用アカウントや証明書を保持しているため、 **機器の掌握は資格情報の漏えいを含む。**
    取るべき行動 **侵害の痕跡が見つかった場合は、①機器を初期化して再構築し、 ②設定は手作業で再投入（バックアップからの一括復元を避ける）、 ③機器が保持していた資格情報（LDAP / AD 連携用、API キー、証明書）をすべて入れ替える。** 所要時間とメールの停止時間を見込んだ手順を、 **侵害が見つかる前に書いておく。**
  • 「IBE を使っていないから無関係」とは勧告から判断できない
    勧告は影響を受ける構成要素を**管理インタフェース（GUI）**とし、 回避策の1つが**IBE の無効化**である。 IoC のログに IBE の復号エラーが現れることから、 脆弱な経路は IBE に関わると読めるが、 **Fortinet は経路を特定して説明していない。** **「IBE を無効にしていれば安全」とは勧告のどこにも書かれていない。**
    取るべき行動 **IBE の利用状況にかかわらず、影響する版に該当するなら 対象として扱うこと。** 判定条件は「**版が 8.0.0〜8.0.1 / 7.6.0〜7.6.6 / 7.4.0〜7.4.8 / 7.2.0〜7.2.9 のいずれかであるか**」であり、 機能の有効・無効ではない。 **到達性を断つ回避策（管理面をインターネットから外す）は、 経路の特定に依存しないため確実性が高い。**
