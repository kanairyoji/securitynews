INC-2026-0291UAT-11587 が台湾等でAntino配布

Cisco Talos が2026年9月30日、中国に連なる攻撃集団 UAT-11587 が 2025年9月から2026年7月にかけてアジア8か国の政府・政策組織を狙い、 未記録のバックドア Antino を配布していたと公表。 端緒は2026年3月の台湾の学術界・シンクタンク・市民社会への標的型フィッシングで、 メール本文に Gmail の添付プレビュー画面を画像で再現する手口が使われた。 続報で C2 の仕組みが分かった——Antino は専用のサーバを持たず、 **Microsoft Graph 経由で攻撃者の Outlook のメールボックスを10秒ごとに見に行き、 件名の `command_req_<セッションID>` で指示を受け取り、OneDrive で生存確認と ファイルの転送を行う。** 通信は通常の Microsoft 365 の利用に紛れる。 帰属の根拠も具体化し、**10件の Antino の実行形式が中国本土向けの Rust の ミラー `rsproxy.cn` を参照**し、配布に使われた CloudFront の配信は **Arctic Wolf が UNC6384 の配布で報告したものと同一**だった。 最大の波は2026年6月8〜9日で、**インドで約57台の端末が新たに観測された**

Cisco Talos は2026年9月30日、中国に連なると高い確度で評価する攻撃集団 UAT-11587 が、2025年9月から2026年7月にかけて アジア8か国（台湾・インド・フィリピン・カンボジア・パキスタン・タイ・ ミャンマー・シリア）の政府・政策組織を狙い、 これまで記録のなかったバックドア「Antino」 を配布していたと公表した。 Talos は確認10件・推定5件の被害環境と、 もう1件の標的とされた環境を特定し、 8か国で約350台のエンドポイントが侵害されたとしている。 追跡の端緒は、2026年3月に台湾の学術界・シンクタンク・ 市民社会の政策コミュニティへ向けられた標的型フィッシングだった。 攻撃者はメール本文の HTML の中に Gmail の添付ファイルの プレビュー画面を Base64 の PNG 画像4枚で再現し、 正規の添付に見える「カード」の全体を 攻撃者が管理する Cloudflare Pages の URL へのリンクで包んでいた。 クリックすると HTA ファイルが落ちて感染の連鎖に入る。 餌には「Taiwan Information Warfare」と題した資料や 台湾財政部が公開した立法委員の費用に関する函釈の完全な複製が使われ、 リンクは // で始まる形で書かれていた—— 完全な URL しか取り出さない検査の仕組みを避けるためとみられる（Talos の指摘）。 Antino は偵察・シェルと PowerShell の実行・ファイル転送・ メモリ上でのシェルコードの読み込み・永続化に対応し、 目的は情報収集と評価されている。 Talos は Symantec が Jewelbug に帰属させた Antino 関連の活動との重なりを認めたが、 結びつきを独自に検証できたとは述べていない。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

標的型フィッシングのメール本文に、 **Gmail の添付ファイルのプレビュー画面を Base64 の PNG 画像4枚と 多層の div で再現したカード**を作り、その全体を **攻撃者が管理する Cloudflare Pages の URL（`//` で始まる形で記載）**への リンクで包む。 クリックすると**HTA ファイル**がダウンロードされ、 **`mshta.exe` によって実行**されて感染の連鎖に入る。 最終的に配置されるのは**バックドア Antino**で、 偵察・シェルと PowerShell の実行・ファイル転送・ メモリ上でのシェルコードの読み込み・永続化に対応する。 目的は**情報収集**と評価されている。

  1. 1. 偵察推定[1] [3]
    標的の職務と関心に合わせた餌が用意されている。 台湾向けでは**講演の依頼**（約50分・謝礼3,500元という具体つき）、 **「Taiwan Information Warfare」と題した資料**（2025年の TikTok 研究・ 両岸の議題・情報操作）、 **台湾財政部が公開した函釈の完全な複製**が使われた。 **誰にどの餌を送るかが事前に決められていた**と読める。
    根拠: Talos が公開したフィッシングの実物と餌の資料（iThome Security の報道）
  2. 2. 初期侵入確認済[1] [3]
    **標的型フィッシングのメールが届く。** メール本文の HTML の中に、 **多層の div と Base64 で符号化され MIME の区分に埋め込まれた PNG 画像4枚**で**Gmail の添付ファイルのプレビューカードが再構成**されている。 カード全体が**攻撃者が管理する Cloudflare Pages （`my-<プロジェクト名>.pages.dev`）の URL へのリンク**で包まれ、 **リンクは `//` で始まる形**で書かれている。 URL には **`?m=<標的識別子>`** が付き、受信者ごとの追跡ができる。 **続報で配送が通った理由が具体化した。** 攻撃者は**正規のメール配信事業者を使い、技術的な送信元には自分のドメインを、 表示される From には装う組織のドメインを置いた。** その結果、**SPF は通り（実際の送信ドメインが許可されていたため）、 DMARC は不一致で失敗した。** それでも届いたのは、**装われたドメインの DMARC ポリシーが 拒否も隔離もしない「監視」（p=none）だったため**である （原文英語: "the displayed domain used a non-enforcing p=none policy, which requested monitoring rather than quarantine or rejection"）。 **つまり、なりすまされた側の設定が、受信側の防御を無効にしている。**

  • ファイルの転送
  • メモリ上でのシェルコードの読み込み（in-memory shellcode loading）

なりすまされた側の p=none が、受信側の DMARC 判定を無力にしていた評価・解釈出典 [1] [5]

メールが届いた理由が、続報で具体的に分かりました。ここは自組織でただちに点検できるところです。

攻撃者の作りは次のとおりです。

  • 正規のメール配信事業者を使って送信した

  • 技術的な送信元（エンベロープ）には自分のドメインを置いた → SPF は通ります（そのドメインは自分で許可しているため）

  • 表示される From には、装う組織のドメインを置いた → DMARC は不一致で失敗します

  • それでも配送された。 理由は、装われたドメインの DMARC ポリシーが拒否も隔離もしない「監視」（p=none）だったためです（原文英語: "the displayed domain used a non-enforcing p=none policy, which requested monitoring rather than quarantine or rejection"）

読みどころは、失敗したのが受信側の設定ではないという点です。受信側の検査は正しく「不一致」と判定しました。判定の結果をどう扱うかを決めているのは、なりすまされた側のポリシーです。つまり他組織の DMARC の設定が、自組織の受信箱の安全を左右します。

ここから2つの行動が出ます（本記録の評価）。

  1. 自組織の DMARC を p=none のまま放置しない。 p=none は「自社を装ったメールを他社に配送させる」状態です。自社の被害ではなく、取引先・顧客の被害として現れます。監視のために p=none から始めるのは正しいが、期限を決めて quarantine・reject へ進めること

  2. 受信側では、DMARC が失敗したメールを「送信側のポリシーに従う」だけで終わらせない。とくに政府機関・学術機関・シンクタンクを装うメールは、装われた側が p=none のままである可能性を前提に、自社側の規則で隔離の対象にする

本件の標的が政府・学術・シンクタンクであることを踏まえると、装われる側の組織ほど p=none のままになっている可能性があります。自組織が「装われる側」になりうるかで考えると、優先順位が上がります。
