INC-2026-0296GitLab 自前 AI Gateway に RCE

GitLab が2026年10月2日、自前でホストする AI Gateway に CVSS 9.9 の重大な脆弱性 CVE-2026-90970（CWE-1336）を公表した。Duo Agent Platform を使えるログイン済みの利用者が、細工したフロー設定でプロンプトテンプレートのサンドボックスを脱出し、AI Gateway 上で任意のコマンドを実行できる。対策版は 19.2.4・19.3.2・19.4.1 で、GitLab がホストする AI Gateway は修正済み。回避策は示されておらず、侵害の有無を確かめる手順も提供されていない

初報: 2026年10月2日 最終更新: 2026年10月7日

2026年10月2日、GitLab が AI Gateway の重大な脆弱性CVE-2026-90970（CVSS 3.1 基本値 9.9・CWE-1336）を公表しました。AI Gateway は GitLab のインスタンスと AI モデルをつなぐサービスで、GitLab Duo の AI 機能を支えます。

GitLab の説明は次のとおりです——「GitLab は AI Gateway の問題を是正した。一定の条件下で、Duo Agent Platform へのアクセス権を持つ認証済みの利用者が、細工したフロー設定によってプロンプトテンプレートのサンドボックスを脱出し、AI Gateway 上で任意のコマンドを実行できる可能性があった」（原文英語）。

対象は、自前で AI Gateway をホストしている組織だけです。 GitLab は自社が運用する AI Gateway を既に修正しており、GitLab.com・GitLab Dedicated・GitLab がホストするゲートウェイを使うSelf-Managed の利用者は対応不要としています。自前でホストしている組織には、勧告の公開に先立って個別に連絡したとも述べています。

対策版は 19.2.4・19.3.2・19.4.1 です。影響する版は18.1.6 以降 19.2.4 未満・19.3 系の 19.3.2 未満・19.4 系の 19.4.1 未満で、19.2.4 より下の系列には対策版が示されていません。

回避策は示されていません。 また、更新する前に攻撃を受けていたかどうかを確かめる手順も提供されていません。 悪用の有無について GitLab の勧告は触れておらず、米 CISA は10月2日に CVE レコードへ「悪用: なし（none）」の評価を追加しています。

自前で立てている組織だけが対象です。 GitLab Duo Self-Hosted という形で、AI の要求と応答のデータを自社環境の内側にとどめたい組織に向けて提供されている選択肢です。データを外に出したくないという判断で選んだ構成が、今回は自分で更新しなければならない対象になっています（本記録の整理）。

GitLab は、勧告を公開する前に、自前でホストしている顧客へ個別に連絡したと述べています。

9.9 という点数は「低い権限で足りる」と「影響がゲートウェイの外へ出る」から来ている原因・手口

CVSS ベクタは CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H です。9.9 まで上がっている理由は、2つの要素にあります（本記録の読み解き）。

  • PR:L（低い権限で足りる）——必要なのは「Duo Agent Platform にアクセスできるログイン済みの利用者」であって、管理者ではありません。開発者が普通に持っている権限で届く可能性があります。
  • S:C（スコープ変更）——影響が脆弱なコンポーネントの外へ及びます。任意のコマンド実行がゲートウェイの実行環境で起きるため、そこから先に到達できるものすべてが射程に入ります。

一方で PR:N（権限不要）ではありません。 誰でも外部から撃てる種類ではなく、「ログインできる人」が前提です。 この区別は実務上重要です—— インターネットに露出しているかどうかより、「Duo Agent Platform を誰が使えるか」のほうが効きます（本記録の評価）。

自前のゲートウェイが何を持っているかも、影響の大きさを決めます。GitLab の導入手引きによれば、自前のゲートウェイは JSON Web Token（JWT）の署名鍵を保持しており、機微な資格情報として扱うべきものとされています。ゲートウェイは GitLab 本体と、組織が契約している AI モデルの提供元にも接続しています。

欠陥の場所は、カスタムフローのプロンプトテンプレートです。カスタムフローは、Duo Agent Platform 上で利用者が作る「複数の手順を自動化する AI のワークフロー」です。利用者が書ける設定が、テンプレートエンジンの評価に乗っているという構造が、CWE-1336（テンプレートエンジンで使われる特殊要素の不適切な無害化）の中身です。

これを「同じミスの繰り返し」と断じる材料は、本記録にはありません（2月の修正の射程がどこまでだったかが公表されていないため）。ただし、利用者が書いた設定をテンプレートとして評価する機構は、そこに閉じ込めようとする限り破られ続ける種類の問題です（本記録の評価）。

読者が自組織に引き寄せるべきは、製品の評価ではなく設計の問いです—— 「自社の製品や内製ツールで、利用者が書いたテキストをテンプレートとして評価している場所はどこか。そこが破れたとき、何に到達できるか。」

AI エージェントの基盤は、この構造を大量に持ち込みます。プロンプト・ツール定義・フロー設定——いずれも「利用者が書けるテキストを実行系が解釈する」形です。サンドボックスの内側に置くという設計は、サンドボックスが破れた時点で一段も残りません。

回避策も、侵害の確認手順も示されていない対策・注意喚起

勧告には、更新以外の選択肢が書かれていません。

  • 回避策（workaround）の記載が無い。本記録の作成者が GitLab の CVE レコードを取得して確認しましたが、そこにも記載はありませんでした。
  • 更新する前に攻撃を受けていたかを確かめる手順が無い。ログに何が残るのか、どのような痕跡を探せばよいのかの記述がありません。
  • 19.2.4 より下の系列（18.1.6〜19.1 系）に対策版が無い。 GitLab の導入手引きは「GitLab の minor バージョンに合うゲートウェイのイメージを使う」よう指示していますが、19.2.4 のゲートウェイが GitLab 19.1 以前で動くかは勧告に書かれていません。古い系列への修正の予定も示されていません。

更新の手順自体は示されています。 Docker で動かしている場合はコンテナを止めて削除し、新しいイメージのタグ（例: self-hosted-v19.4.1-ee）を取得して起動します。Helm の場合はチャートのイメージ設定を新しいタグに変えます。

「侵害の確認手順が無い」ことの意味は、実務では小さくありません（本記録の評価）。CVSS 9.9 の任意コマンド実行に対して、更新した組織は「自分は侵害されていなかった」と言えないまま運用を続けることになります。自前でホストしているゲートウェイはJWT の署名鍵を持ち、GitLab 本体と AI モデルの提供元に接続しているため、「念のため鍵を入れ替えるか」の判断を各組織が自力で下すことになります。

本記録としての助言は、更新に加えて次の2つを自組織で決めることです（いずれも GitLab は求めていません）—— ①ゲートウェイの実行環境のログを遡って確認できる期間はどれだけか。②署名鍵と AI モデル提供元の資格情報を、更新に合わせて入れ替えるか。

GitLab の脆弱性は実際に悪用されてきた系譜がある背景・過去事例

本件そのものに悪用の報告はありません（2026年10月2日時点で CISA の評価は「悪用: なし」）。ただし、GitLab という製品が置かれている文脈は別です。

  • 2021年11月以降、CISA が実際に悪用されたと判定した GitLab の脆弱性は5件あり、うち1件はランサムウェアの集団に悪用されました。

本件はこの5件には含まれません。

文脈として置く理由は、「悪用の報告が無い」を「急がなくてよい」と読み替えないためです（本記録の評価）。前月の CVE-2026-85706 は、修正の翌日に KEV 入りしています。 評価は時点のものであり、変わります。

なお本件は前月の事案とは対象も前提も違います——前月のものは認証不要で GitLab 本体、本件は認証が必要で自前の AI Gatewayです。同列に扱わないでください。

CISO・経営層への示唆
  • 「データを外に出さないために自前で立てた」構成は、自分で守る対象になる
    本脆弱性で対応が要るのは、**自前で AI Gateway をホストしている組織だけ**である。 **GitLab がホストするゲートウェイを使っている組織は、 GitLab 側の修正で終わっている。** **AI の要求・応答を自社環境にとどめたいという判断で選んだ構成が、 今回は自分で更新しなければならない対象になった**（本記録の整理）。
    取るべき行動 **AI 関連の基盤について「自前で立てたもの」の台帳を作り、 それぞれに更新の責任者と適用期限を割り当てる。** **データの所在を理由に自前を選んだ構成ほど、更新の手当てが抜けやすい**—— 選定時の稟議に**「誰がこれを更新し続けるか」を必ず書かせる。** **「外に出さない」と「安全」は同じではない。**
  • 攻撃面は「インターネットに露出しているか」ではなく「誰が使えるか」で決まることがある
    本脆弱性の CVSS ベクタは **`PR:L`（低い権限で足りる）** である。 **必要なのは管理者権限ではなく、Duo Agent Platform にアクセスできる ログイン済みの利用者であること**だけである。 **一方 `S:C`（スコープ変更）により、影響はゲートウェイの外へ及ぶ。** **露出の有無より、AI 機能の利用権限の広さのほうが効く**（本記録の評価）。
    取るべき行動 **AI 支援機能の利用権限を「全社に開放」から「必要な部門・役割」へ 絞れるかを検討し、絞れないならその判断を記録に残す。** 脆弱性管理の優先度づけでも、**`PR:N`（権限不要）か `PR:L`（低権限）かで 対応の速度を分ける基準**を持つ。 **AI 機能の普及を推進する施策と、権限を絞る施策は衝突する**—— **どちらを取るかを明示的に決める。**
  • 同じコンポーネントで同じ分類の欠陥が繰り返されるかを追う
    GitLab は2026年2月にも AI Gateway で **CVE-2026-1868**（CVSS 9.9・CWE-1336・ 認証済み利用者が細工したフロー定義から到達）を修正している。 **同じコンポーネント・同じ分類・同じ到達経路で、8か月に2度である。** **今回の勧告は2月の件に言及していない。**
    取るべき行動 **採用している基盤について「同じコンポーネントで過去に出た脆弱性の分類」を 記録し、繰り返しが起きていないかを四半期ごとに見る。** 繰り返しが見えたら、**個別の更新ではなく『その機構を使い続けるか』の 判断に上げる。** **ベンダーの勧告は過去の類似案件に触れないことが多い**—— **繰り返しの検出は利用者側の仕事である**（本記録の評価）。
  • 「悪用の報告が無い」は時点の情報であって、優先度を下げる根拠ではない
    本件について CISA は2026年10月2日時点で「悪用: なし」と評価している。 **しかし前月の CVE-2026-85706（GitLab CE/EE）は、 修正の翌日に KEV へ収載され、連邦政府機関に3日の期限が課された。** **2021年11月以降、CISA が実際に悪用されたと判定した GitLab の脆弱性は5件あり、 うち1件はランサムウェアの集団に悪用された。**
    取るべき行動 **脆弱性の対応期限を「悪用の有無」ではなく 『深刻度 × 自組織での到達可能性』で決める運用にする。** 悪用の情報は**期限を前倒しする材料としてのみ使い、 後ろ倒しの材料にはしない。** **製品ごとに「過去に KEV 入りした件数」を把握しておくと、 初動の判断が速くなる**（本記録の助言）。
セキュリティ技術者への示唆
  • 利用者が書いたテキストをテンプレートとして評価する場所を洗い出す
    本件の分類は **CWE-1336（テンプレートエンジンで使われる特殊要素の 不適切な無害化）** で、**欠陥はカスタムフローのプロンプトテンプレートにある。** **利用者が書ける設定が、テンプレートエンジンの評価に乗っている**という構造である。 **AI エージェントの基盤は、この構造を大量に持ち込む**—— プロンプト・ツール定義・フロー設定（本記録の評価）。
    取るべき行動 **自社の製品・内製ツールで『利用者が書いたテキストをテンプレートとして 評価している場所』を列挙し、それぞれについて 「評価が破れたとき、何に到達できるか」を書き出す。** **サンドボックスの内側に置く設計は、サンドボックスが破れた時点で 一段も残らない**——**評価を行うプロセスの実行権限・ネットワーク到達範囲・ 読める資格情報を、破れる前提で最小化する。**

    取るべき行動 **コンテナ・Helm で動かしている補助的な基盤（AI ゲートウェイ・ ベクタデータベース・埋め込みサービス等）を資産台帳に載せ、 イメージタグを定期的に棚卸しする。** **「GitLab は最新です」と「GitLab の AI Gateway は最新です」は 別の主張である**——**台帳の単位を製品名ではなく稼働中のイメージにする。**
  • 侵害の確認手順が無い脆弱性では、ログの遡及可能期間が判断の分かれ目になる
    **GitLab は、更新前に攻撃を受けていたかを確かめる手順を示していない。** ログに何が残るのか、何を探せばよいのかの記述が無い。 **CVSS 9.9 の任意コマンド実行に対して、更新した組織は 「侵害されていなかった」と言えないまま運用を続けることになる**（本記録の評価）。
    取るべき行動 **AI Gateway の実行環境について、 ①ログを外部へ転送しているか ②遡れる期間はどれだけか ③プロセス起動・外向き通信・ファイル書き込みが記録されているか の3点を今すぐ確認する。** **確認手順が提供されない脆弱性は今後も出る**—— **「後から調べられる状態」を平時に作っておくこと自体が対策である。**
  • ゲートウェイが保持する鍵と資格情報を、更新とセットで棚卸しする
    **自前の AI Gateway は JWT の署名鍵を保持しており、 GitLab の導入手引きは機微な資格情報として扱うよう求めている。** **ゲートウェイは GitLab 本体と、組織が契約している AI モデルの提供元にも 接続している。** **任意コマンド実行が成立していれば、これらすべてが射程に入る** （本記録の評価）。
    取るべき行動 **AI Gateway が保持・参照する秘密（JWT 署名鍵・AI モデル提供元の API キー・ GitLab への接続資格情報）を列挙し、更新作業の手順書に 「入れ替えるかどうかの判断」を工程として組み込む。** **入れ替えないと決めるなら、その判断と理由を記録に残す。** **GitLab はこれを求めていない**——自組織の判断になる。
