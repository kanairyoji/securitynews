INC-2026-0301ハナ銀行で顧客89名の情報流出

ハナ銀行（韓国）が2026年10月2日、**行員向けの営業支援システム（ODS）への外部からの異常アクセス**により 顧客89名の住民登録番号・氏名・住所・勤務先名など7項目が流出したと公表。 2日間で韓国の銀行4行が続けて流出を公表する連続事案の3例目で、 **「AI エージェントを悪用した自動化攻撃」との見方が金融当局・業界から出ているが、 銀行自身は手口を「外部のハッキングエージェント」と述べるにとどまる

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年10月2日 最終更新: 2026年10月3日

ハナ銀行（하나은행・韓国）は2026年10月2日、外部からのハッキングにより 顧客89名の個人情報が流出したと公表した。 流出した項目は住民登録番号・氏名・住所・電子メールアドレス・電話番号・携帯電話番号・勤務先名の7つである。 銀行の説明によれば、流出は外部のハッキングエージェントが 行員向けの営業支援システム「ODS（영업지원시스템）」に試みた異常なアクセスに起因する。 ハナ銀行の関係者は「このシステムはインターネットバンキング・モバイルバンキングの取引システムとは別のチャネルであり、 顧客の金融取引情報の流出とは関係がない」と述べている。 銀行は、10月1日に他の金融機関を狙ったハッキングの試みを認知した直後に 金融監督院（금융감독원）など関係機関へ報告し、 侵害の痕跡を確認した後に当該 IP と類似システムの緊急遮断・点検を完了、 全社の非常対応体制と緊急対応タスクフォースを立ち上げたとしている。 流出対象の顧客には個別通知を進めており、実被害が生じた場合は規定に従って全額補償する方針だという。 本件は2日間で韓国の銀行4行（新韓・KB国民・ハナ・BNK釜山）が続けて流出を公表した連続事案の3例目で、 金融当局は金融各社に対し 「AI エージェントを悪用した自動化攻撃が金融業界で発生したと推定され、 さまざまな国の海外 IP を通じて攻撃が行われた」と通知したと報じられている。 ただしハナ銀行自身は「AI」という語を用いておらず、 攻撃に使われたとされるツールの特定・攻撃者の帰属・侵入の原因はいずれも公表されていない。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**外部のハッキングエージェントが、行員向けの営業支援システム（ODS）へ異常なアクセスを行い、 顧客89名分の7項目を取得した。** **これがハナ銀行が公表した攻撃の全体像であり、段階ごとの機序は公表されていない。** 報道が伝える業界・当局の見方では、連続事案の全体が 「オープンソースの AI 自律型ペネトレーションテストツールによる自動化された無差別攻撃」と推定されているが、 **ハナ銀行の事案についてこれを裏づける公表はない。**

  1. 1. 初期侵入確認済
    **外部のハッキングエージェントが、行員向けの営業支援システム（ODS）に対して 異常なアクセスを試み、成立した。** **悪用された脆弱性・認証の突破方法は公表されていない。**
    根拠: ハナ銀行の説明（報道経由。「외부 해킹 에이전트가 영업지원시스템(ODS)에 시도한 비정상적 접근」）
  2. 2. 収集確認済
    **顧客89名分の住民登録番号・氏名・住所・電子メールアドレス・電話番号・携帯電話番号・勤務先名が 取得された。** **一度に取得されたのか、反復的な照会の積み上げなのかは公表されていない。**
    根拠: ハナ銀行の説明（流出項目7つと89名という人数）
  3. 3. 持ち出し確認済
    **取得された個人情報が外部へ出た。** ハナ銀行は流出を認めているが、**持ち出しの経路・宛先・データ量は公表されていない。**
    根拠: ハナ銀行の説明（「유출된 것으로 파악된다」＝流出したものと把握している）

この事案で下された判断
  • **原因も期間も確定しない段階で、流出の事実・項目・人数を即日公表した。**
    理由は公表されていない
    トレードオフ: 原因が固まるまで待てば説明は正確になるが、 **同業で同種の攻撃が続いている局面では、自社だけ黙ることが業界全体の対応を遅らせる。** 先に出せば「原因が分からないまま公表する」ことになり、 **報道の見出しが推測（AI ハッキング）で埋まる余地を残す。**
  • **当該 IP と「類似システム」を緊急遮断し、点検を完了させた。**
    理由は公表されていない
    トレードオフ: 営業支援システムを止めれば**行員の顧客対応業務が止まる**。 止めなければ同じ経路での流出が続きうる。
  • **対象顧客へ個別通知を行い、実被害が生じた場合は関連規定に従って全額補償する方針を示した。**
    理由は公表されていない
    トレードオフ: 補償方針を先に出せば顧客の不安は下がるが、**被害と本件の因果の判定という難題を抱える。** 示さなければ89名は自力で備えるしかない。

抜かれたのは「取引の経路」ではなく、行員が顧客を扱う画面の側だった概観出典 [1] [2] [3]

ハナ銀行の説明で実務上もっとも重いのは、侵害されたのが顧客向けのバンキングではなく 行員向けの営業支援システム（ODS）だったという点です。

銀行は「このシステムはインターネットおよびモバイルバンキングの取引システムとは別のチャネルであり、 顧客の金融取引情報の流出とは関係がない」と述べています。 取引の経路が守られたのは事実として重要です。 しかし流出した7項目には住民登録番号と勤務先名が含まれます。 韓国の住民登録番号は日本のマイナンバーに相当する一意の国民識別番号で、 本人の意思では事実上変更できません。 つまり「取引情報は漏れていない」ことと「被害が軽い」ことは同じではありません（本記録の評価）。

もう一つの要点は規模の小ささです。89名は、同じ2日間に公表された新韓銀行の2万5,000名と比べれば 0.4% にも満たない。 ただし母数が公表されていないため、 「攻撃が途中で止まったのか」「もともと到達できたのが89名分だったのか」は判断できません。 銀行が当該 IP と「類似システム」を緊急遮断したと述べていることから、 広がる前に切った結果である可能性はありますが、銀行はそう説明していません（本記録の評価）。

自社の被害を確認する前に、他行の攻撃情報で動いていた組織の対応出典 [2] [3]

時系列で特徴的なのは、ハナ銀行が10月1日の時点で「他の金融機関を狙ったハッキングの試み」を認知し、 その直後に金融監督院など関係機関へ報告していることです。 自社の侵害が確認されたのはその後です。

つまり業界で起きている攻撃の情報が、自社の確認作業と当局報告の引き金になっています。 新韓銀行の事案が知られた後、金融各社は当局の関連機関から 「AI エージェントを悪用した自動化された攻撃が金融業界で発生したと推定され、 さまざまな国の海外 IP を通じて攻撃が行われた」という通知を受けたと報じられています。

対応の内容として公表されているのは、 ①全社の非常対応体制の稼働、②当該 IP と類似システムの緊急遮断・点検の完了、 ③緊急対応タスクフォースの招集、④対象顧客への個別通知、⑤実被害時の全額補償方針の5つです。 「類似システム」をどこまで止めたのか、業務への影響があったのかは公表されていません。 ここが分からないため、この対応が「素早い封じ込め」だったのかは評価できません（本記録の評価）。

「AI エージェントによる攻撃」は当局・業界の見方で、銀行は認めていない帰属出典 [1] [2] [3]

報道の見出しは「AI ハッキング」ですが、ハナ銀行の説明に「AI」という語はありません。 銀行が使っているのは「外部のハッキングエージェント（외부 해킹 에이전트）」という表現だけです。

一方で、報道が伝える業界・当局側の見方は次のようなものです。

  • 攻撃に使われたのはオープンソースサイトで公開されている AI ベースの自律型ペネトレーションテストツールと推定される - 新韓銀行の事案は、既に窃取されていた顧客情報を使ったクレデンシャルスタッフィングを AI で自動化した例 - 新韓銀行では「利用者の識別とデータのアクセス権限をサーバ側で相互検証できていないときに生じる認可の欠陥」が悪用されたとセキュリティ専門家は分析している
  • 同種の攻撃は国内の複数企業で同時多発的に起きている（業界関係者の発言）

これらはいずれも推定であり、ハナ銀行の事案について当事者が確認したものではありません。 本記録はこの点を区別して扱います—— ハナ銀行について確認できる事実は「ODS への外部からの異常アクセス」までで、 そこに AI が使われたかどうかは公表されていません。

なお「AI が使われたか」より実務に効く論点は別にあると本記録は考えます。 韓国の専門家（티오리 代表）は 「無差別のクローリングのような AI の攻撃を受けたからといって、 それだけで被害企業のセキュリティ水準が低かったと単純に断じるのは難しい。 セキュリティは100%完璧にはなり得ないので、 攻撃者より一歩遅れて侵入されても被害範囲がその場で止まるように内外の設計をすべきだ」と述べています。 攻撃の自動化で「侵入される回数」は増える前提に立ち、1回あたりの被害の上限を設計で決める—— 本件の89名という数字は、その設計が効いたのかどうかを示す材料になりえますが、 材料（母数・遮断の範囲）が公表されていないため確かめられません（本記録の評価）。

CISO・経営層への示唆
  • 顧客向けチャネルを固めても、行員向けの業務システムが同じ顧客データを抱えている
    本件で破られたのは**行員向けの営業支援システム（ODS）**で、 インターネット・モバイルバンキングは無関係だと銀行は説明している。 連続事案の他行も**モバイル営業支援システム**など業務側が狙われたと報じられている。 **顧客向けの入口には多要素認証・不正検知・WAF を積む一方、 業務用の画面は「社内だから」で軽い認証のまま外に出ている**組織は珍しくない（本記録の評価）。 しかし抱えているデータは同じ、あるいは業務側のほうが項目が多い。
    取るべき行動 **「顧客の個人情報に到達できる画面」を顧客向け・業務向けの区別なしに棚卸しし、 インターネットからの到達性と認証の強度を一覧にすること。** 具体には、①対象システムごとに「外から到達できるか」「多要素認証があるか」 「一括照会の上限があるか」を3列で埋める、 ②埋まらない欄がある業務システムを優先改修の対象にする、 ③委託先・外注が使う業務システムも同じ表に入れる。
  • 同業で攻撃が走っているという情報を、自社の点検と当局報告の引き金として定義しておく
    ハナ銀行は**10月1日に他の金融機関を狙った攻撃の試みを認知した直後に当局へ報告し、 その後に自社の侵害を確認している。** **自社の被害が確定するのを待たずに動いた**ことが、 結果として確認から1日以内の公表につながっている（本記録の評価）。 攻撃が自動化されて業界を横に走る局面では、 **「他社が落ちた」は自社の監視アラートと同じ価値を持つ。**
    取るべき行動 **「同業で同種の攻撃が確認された」を社内のインシデント発動条件に明記すること。** 具体には、①業界団体・当局・ISAC からの通知を受けた時点で誰が何時間以内に何を点検するかを決める、 ②点検対象（同種システム・同種の認証方式）を事前に対応づけておく、 ③当局・監督官庁への第一報を「被害確定後」ではなく「疑いの時点」で出す方針を経営として承認しておく。

    流出した7項目には**住民登録番号**が含まれる。 日本のマイナンバーに相当する一意の識別子であり、 **本人の意思では事実上変更できない。** 銀行は「実被害が生じた場合は全額補償」と述べているが、 **番号の悪用は年単位で後から起こり、本件との因果の立証が困難**である（本記録の評価）。

  • 攻撃が自動化された前提では、評価軸は「侵入されたか」から「どこで止まったか」に移る
    韓国の専門家は「無差別の攻撃を受けたからといってそれだけで被害企業の水準が低いと断じるのは難しい。 攻撃者より一歩遅れて侵入されても**被害範囲がその場で止まるように内外を設計すべきだ**」と述べている。 本件の89名という数字は、新韓銀行の2万5,000名と比べれば小さい。 **しかし母数も遮断の範囲も公表されていないため、設計が効いた結果なのかは確かめられない。** **自社では確かめられる**——止まる仕組みを作り、実測しておけば、 事故時に「どこで止まったか」を説明できる（本記録の評価）。

    取るべき行動 **業務システムの照会ログに、量と広がりの異常検知を掛けること。** 具体には、①アカウントあたりの時間当たり照会件数、 ②1セッションで触れた顧客 ID の種類数、 ③深夜・休日の照会、④海外 IP からのアクセス——の4つを閾値付きで監視し、 超過時は自動で速度制限か遮断に落とす。
  • 認可はサーバ側で毎回検証する。画面側の制御は制御ではない
    同じ連続事案の新韓銀行について、専門家は 「**利用者の識別とデータのアクセス権限をサーバ側で相互検証できていないときに生じる認可の欠陥**」の 悪用例と分析していると報じられている（**ハナ銀行の事案についての分析ではない**）。 ID を差し替えるだけで他人のデータが返る実装は、 **自動化されたツールにとって最も見つけやすい欠陥**である（本記録の評価）。
    取るべき行動 **顧客データを返すすべての API で「このセッションの主体がこのデータに到達してよいか」を サーバ側で毎回検証していることを、コードではなくテストで担保すること。** 具体には、①利用者 A のトークンで利用者 B の ID を指定する試験を回帰試験に入れる、 ②一覧系・検索系・帳票出力系も対象にする（詳細画面だけ守られている例が多い）、 ③外注開発分についても同じ試験を納品条件にする。
  • 自動化されたペネトレーションテストツールは、守る側も同じ速度で使える
    報道では、攻撃に使われたのは**オープンソースで公開された AI ベースの自律型 ペネトレーションテストツールと推定される**とされている。 同じツールは防御側にも開かれている。 専門家も「攻撃者より先に AI などを活用して脆弱性を見つける先制的な努力」を挙げている。
    取るべき行動 **外部に露出している自社の業務システムに対して、自動化された探索を定期的に自分でかけること。** 具体には、①四半期ごとに外部到達面の自動スキャンと認可欠陥の探索を実施する、 ②オープンソースの自律型ツールが見つける種類の欠陥（認可・列挙・速度制限なし）を チェックリストにする、③見つかった欠陥の修正期限を重大度別に定める。
  • 封じ込めの手段として「同じ作りのシステムを横断して止める」が選べるようにしておく
    ハナ銀行は**「当該 IP と類似システム」を緊急遮断**したと説明している。 1つの画面の欠陥は、**同じ基盤・同じ認証方式で作られた他の画面にも同じ形で存在する**ことが多い。 個別に調べてから止めていては間に合わない（本記録の評価）。
    取るべき行動 **「同じ作り」のグループ分けを平時に作り、グループ単位で遮断できる手段を用意すること。** 具体には、①業務システムを認証方式・基盤・開発委託先で分類した台帳を持つ、 ②グループ単位で外部到達を止める操作手順（WAF・ロードバランサ・FW のルール）を用意し演習する、 ③止めた場合に影響する業務を1行で書いておく。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 従業員・代理店・外注が使う業務システム（営業支援・顧客管理・モバイル業務アプリ）が インターネットから到達でき、そこから顧客の個人情報を照会できる本件で破られたのはまさにこの位置のシステムである。 **顧客向けチャネルの防御がどれだけ厚くても、 同じデータに届く別の入口が薄ければそこが使われる。**
認証・認可□ 業務システムの認証が ID とパスワードだけ、 または多要素認証が一部の利用者・一部の経路でしか必須になっていない連続事案のうち新韓銀行の例は**既に窃取された認証情報を使った クレデンシャルスタッフィングの自動化**と報じられている。 **使い回された認証情報は、攻撃の自動化によって総当たりの対象になる。**
認証・認可□ 顧客データを返す API で、認可（このセッションがこのデータに到達してよいか）の サーバ側検証を回帰試験で担保していない認可の欠陥は**自動化された探索が最も速く見つける種類の欠陥**である。 画面を隠す・パラメータを暗号化するといった対策は、 **サーバ側で検証していなければ防御にならない。**
データの保持□ 一意の国民識別番号（マイナンバー・住民登録番号相当）や勤務先情報を 業務画面で平文表示している本件の流出項目には住民登録番号と勤務先名が含まれる。 **変更できない識別子と所属の組み合わせは、 なりすましと標的型の詐欺に長期間使える。** 表示の必要性を見直すだけで、流出時の損害の性質が変わる。
運用・監視□ 業務システムの照会ログに対して、件数・速度・対象の広がりの異常検知を掛けていない業務システムを通る照会は**正規の形で届く**ため、 量と広がりでしか異常を見分けられない。 検知の仕組みがなければ、本件のように **他社の被害情報をきっかけに点検して初めて気づく**ことになる。
体制・契約□ 「同業で同種の攻撃が確認された」ことを起点に自社の点検・当局報告を開始する手順が 文書化されていないハナ銀行は他行への攻撃の認知を起点に動いた。 **自動化された攻撃は業界を横に走る**ため、 自社のアラートを待つ運用では出遅れる。
