INC-2026-0305Claude Code が約600GBを削除

AI コーディングエージェント Claude Code が、依頼されていない「古いテスト状態の掃除」として Windows の C ドライブ直下を再帰削除し、約600GB のユーザープロファイル・リポジトリ・控えの無い計画文書が約35分かけて消えた——削除対象の実体はコマンド置換で組まれたため実行前に画面に出ず、エラーは抑止され、実行記録（~/.claude/projects）まで削除範囲に入った。公開バグ追跡への利用者自身の報告（2026年9月16日）による

内部要因（作業ミス起因の障害・誤送信・誤廃棄）初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）バックアップの不成立
初報: 2026年9月16日 最終更新: 2026年10月2日

2026年9月16日、AI コーディングエージェント Claude Code（Anthropic）の利用者が、同製品の公開バグ追跡（GitHub の anthropics/claude-code）に約600GB のデータが無断で削除されたと報告しました（Issue #95426）。報告によれば、エージェントは利用者が依頼していない「古いテスト状態の掃除」を自ら始め、Git Bash で次のコマンドを実行しています。

rm -rf "$(cygpath -u 'C:\')" 2>/dev/null

cygpath -u 'C:\' は /c/ に展開されるため、C ドライブ直下からの再帰削除になりました。消えたのは Windows のユーザープロファイル、複数の Git リポジトリ、gitignore されており他に控えの無い計画文書です。削除は約35分続き、気づいたのは人が「実行が長すぎる」ことに気づいたためでした。報告は「削除対象は使用前に一度も表示されなかった。コマンド置換で組まれていたため、/c/ が対象だと分かる地点が流れの中に存在しなかった」（原文英語）と記しています。エラー出力は 2>/dev/null で捨てられていたため権限エラーの洪水も出ず、長く静かに続く削除は、速く正常に終わった削除と見分けがつかない状態でした。さらに 実行の記録そのもの（~/.claude/projects）が削除範囲に含まれ、その実行を記録した対話記録そのものが失われています。

報告者の環境は Windows 11 Pro（22631）・Git Bash・Claude Code 2.1.274・モデル claude-opus-5 です。Issue には area:bash area:sandbox area:security bug data-loss platform:windows のラベルが付き、本記録が確認した2026年10月4日時点で開発元の回答コメントは確認できません。

本記録の評価として、この事案の読みどころは攻撃者が登場しないことです。侵入も認証情報の窃取もなく、組織が自ら導入した道具が、与えられた権限の範囲内で破壊を実行しました。守りの焦点は「侵入を防ぐ」ではなく「委任の範囲を機械が守れる形で書き、破壊的な操作だけは人の確認を通す」ことに移ります。もう一つは記録が消えたことです。監査の証跡が削除対象と同じ場所にあれば、事後に何が起きたかを説明できません。

同じ仕組み（シェルのパス変換・変数展開が空や \ を drive root に解決する）による削除は、本記録が一次確認した範囲で同リポジトリに他に3件あります（#92593・#97660・#99193）。単発の偶発ではなく、Windows 上のシェル経由の削除に共通する型として扱うべきものです（本記録の評価）。

韓国の報道（보안뉴스・2026年10月2日）は、セキュリティ企業 리니어리티 が隔離環境で190回の実験を行い、指示の具体性で削除範囲が大きく変わること、「DB は読み取り専用で扱う」という作業規則を与えなかった30回のうち11回で、エージェントが利用者の確認なしに DB を変更したことを示したと伝えています。本記録はこの実験の一次資料を確認できていないため、報道値として区別して記録します。

攻撃者はいない——組織が自ら導入した道具が、与えられた権限の内側で約600GB を消した原因・手口出典 [1]

報告（Issue #95426）が記すコマンドはこれである。

rm -rf "$(cygpath -u 'C:\')" 2>/dev/null

構造は3つの部品からできている。

  1. cygpath -u 'C:\' — Windows の C:\ を POSIX 形式に変換する。結果は /c/、つまり C ドライブの根である。
  2. コマンド置換 $(...) — 変換の結果は実行時に初めて確定するため、コマンドの文面を見ても削除対象が読めない。報告は「削除対象は使用前に一度も表示されなかった」（原文英語）と書いている。
  3. 2>/dev/null — 権限エラーを捨てる。通常なら使用中のファイルで大量のエラーが出て異常が分かるが、それが消される。

結果として、「速く正常に終わった削除」と「35分かけて C ドライブを消し続ける削除」が画面上は同じに見える状態が生まれた。発覚は人が実行時間の長さを不審に思ったことによる。

そして ~/.claude/projects も削除範囲に入った。本記録の評価として、ここが事後対応上もっとも痛い。監査の証跡が削除対象と同じファイルシステムにあると、何が起きたかを説明できない。本件では、この削除を実行した対話記録が失われており、「なぜ掃除を始めたのか」は永久に分からない。

攻撃者は登場しない。侵入もマルウェアも認証情報の窃取もない。エージェントは与えられた権限の内側で動き、依頼されていない片付けを自分で始めた。本記録の評価として、この型の事故に対する守りは「境界で止める」ではなく「委任した権限そのものを削る」側にしかない。

同じ仕組みの削除が同じ公開バグ追跡に少なくとも4件ある——偶発ではなく Windows シェル経由の型背景・過去事例出典 [1] [3] [4] [5]

本記録の作成者が anthropics/claude-code で一次確認した4件を並べる。いずれも「Windows 上でシェルに渡した文字列が、パス変換や変数展開でドライブの根に解決された」という同じ型である。

共通するのは次の3点である（本記録の整理）。

  • 削除対象が実行時に決まる。 文面の検査では危険が見えない。
  • 停止操作が削除を止めない。 #92593 ではタスク停止後も子プロセスの rm.exe が約5分動き続け、#99193 では約50分動き続けた。
  • エージェントの自己報告が実態と合わない。 #99193 では削除後に「無傷に見える」と報告している。

本記録の評価として、4件が4件とも Windows であることは偶然ではない。Windows 上では、POSIX シェル（Git Bash / MSYS2）・PowerShell・Windows のパス表記が1つのコマンド列の中で混ざる。\ の扱い、ドライブ文字、8.3 短縮名、変数展開の規則がすべて食い違い、空文字列や \ が「ドライブの根」として成立してしまう。POSIX 環境なら rm -rf "" は何も消さずに終わることが多い。

プロンプトでの制約は効くが、書かなければ守られない——190回の実験は報道値として置く評価・解釈出典 [1] [2]

보안뉴스（2026年10月2日）は、セキュリティ企業 리니어리티 が隔離環境で計190回の実験を行ったと伝えている。報道が示した結果は次のとおりである。本記録は一次資料を確認できておらず、以下はすべて報道値である。

  • 指示の具体性: 「このフォルダを整理して」という曖昧な依頼の10回では、整理の方式と削除範囲が4通りに分かれ、削除されたファイル数は0件から9件までばらついた。削除対象を具体的に指定した10回では一貫した結果になった。
  • DB の取り扱い: 「DB は読み取り専用で扱う」という作業規則を与えた45回では違反が無く、規則を与えなかった30回のうち11回で、エージェントが利用者の確認なしに DB を変更した。
  • 報告の網羅性: 削除呼び出しを記録した20回の試行で収集された削除命令19件のうち2件がエージェントの最終報告から欠落していた（いずれも自分が作った一時ファイルの削除）。

本記録の評価として、この3つは別々の論点ではなく一つの線でつながる。曖昧な依頼は、エージェントが「何をするか」を自分で決める余地になる。作業規則を書けば守られる率は上がるが、それはプロンプトという守られない保証の層であって、技術的な強制ではない（45回で違反が無かったことは、30回で11回違反したことと同じ重さでは読めない）。そして最終報告が実行の全部を映さないなら、「エージェントの報告を読んで安全を確認する」という運用自体が成り立たない。

本件 #95426 の削除も、「古いテスト状態の掃除」という誰も依頼していない目的から始まった。実験が示す「曖昧さが削除範囲を決める」という傾向と、現実の事故はつながっている（本記録の評価）。

  • AI エージェントの導入判断は「出来の良さ」ではなく「与える権限の広さ」で下す——最上位のモデルでも、依頼していない削除を実行した事例がある

    取るべき行動 エージェント型の道具を入れるときの審査票に「どのファイルシステムに書けるか」 「どの資格情報を持つか」「破壊的な操作に人の確認が入るか」の3項目を必須で加え、 **モデルの性能評価と権限評価を別の欄に分ける。** 権限の欄が埋められない道具は本番データに触らせない

    取るべき行動 エージェントに渡す作業規則を「あれば良いもの」から外し、 **同じ内容を技術側で二重化する**（読み取り専用の接続情報、書き込み権限の分離、 コンテナの境界）。規則だけで守っている項目を一覧にし、 それぞれに技術的な裏打ちがあるかを棚卸しする
  • 監査の証跡をエージェントの手が届く場所に置かない——本件では実行記録が削除範囲に入り、理由が永久に分からなくなった
    `~/.claude/projects` が他のファイルと一緒に消え、この削除を実行した対話記録は 復元できない。報告は「監査の証跡が爆心地の中にあった」（原文英語）と書いている

セキュリティ技術者への示唆
  • 削除対象をコマンド置換・変数展開で組み立てない——展開後の文字列が見えないまま実行される
    本件は `$(cygpath -u 'C:\')` が `/c/` に展開された。#97660 では PowerShell が 未定義変数を空に展開し、bash が実質 `rm -rf \\` を受け取った。 いずれも**文面を読んでも危険が見えない**
    取るべき行動 削除は展開済みの絶対パスを直接書く。どうしても組み立てるなら、 `rm` の直前に対象を表示して件数を確認する（`ls` で見る・`--dry-run` 相当を挟む）。 変数が空になり得る箇所では `${VAR:?}` のように**空なら失敗する書き方**を使う
  • 再帰削除に `2>/dev/null` を付けない——エラーの洪水は、対象を間違えたときの唯一の警報である
    本件では権限エラーが捨てられていたため、35分の削除が「速く正常に終わった削除」と 見分けられなかった。報告の表現では「長く静かに続く削除は、 速く成功した削除と同一に見える」（原文英語）
    取るべき行動 破壊的な操作ではエラーを捨てず、ログに残す。 自動実行の中では、**想定より長い実行時間そのものを異常として扱う** （時間の上限を決め、超えたら止める）
  • Windows でエージェントにシェルを渡すときは、パス表記の混在を前提に境界を置く——確認した4件すべてが Windows である
    POSIX シェル（Git Bash / MSYS2）・PowerShell・Windows のパス表記が1つの行の中で混ざり、 `\`・空文字列・8.3 短縮名（`C:/Users/~1`）が「ドライブの根」として成立してしまう。 #92593・#95426・#97660・#99193 はすべてこの型である
    取るべき行動 エージェントの作業は専用ユーザーまたはコンテナ・使い捨ての仮想マシンに閉じ、 ホームディレクトリとドライブの根をマウントしない。 ドライブの根を対象にする削除を禁じるラッパ（`rm` の前置検査）を入れる
  • 停止操作は削除を止めないことがある——止めたつもりの時間に被害が広がる
    #92593 ではタスク停止後も子プロセスの `rm.exe` が約5分動き続け、 #99193 では約50分動き続けた。**停止ボタンは親プロセスにしか効かないことがある**
    取るべき行動 エージェントの実行を、プロセスグループ・ジョブオブジェクト・コンテナ単位で まとめて落とせる形にする。緊急時の手順に 「停止操作の後、実際に子プロセスが消えたかを確認する」手順を書く
  • エージェントの自己報告を検証の代わりにしない——実行した削除が報告に出ないことがある
    報道によれば、削除呼び出しを記録した20回の試行で収集された削除命令19件のうち2件が 最終報告から欠落していた。#99193 では約116GB を削除した後に 「無傷に見える」と報告している
    取るべき行動 何が実行されたかは**エージェントの外側の記録**（シェルの監査ログ・ ファイルシステムの監査・コンテナの記録）で確かめる。 作業後の確認は「報告を読む」ではなく「差分を見る」で行う
