2026年10月2日、デンマーク工科大学（DTU）が、自らの ID・アクセス管理システム「DTUBasen」に対する標的型のサイバー攻撃を受け、大量のデータが持ち出されたと公表しました。

侵入の形は明快です。 DTU の説明によれば、何者かが DTU のプロファイル（利用者アカウント）を侵害し、それを使って DTUBasen にログインしたとされています。その結果、2003年まで遡る個人データへのアクセスが成立しました。

規模は「特定できない」と公表されました。 DTU は「何の情報が持ち出されたか、何名が影響を受けたかを正確に特定することはできない」と明言しています（原文英語）。代わりに示されたのはシステムが保持している母数です—— 現役利用者 約40,000名・元利用者 約160,000名、合わせて最大20万名。

含まれる項目が重い。 現役利用者についてはデンマークの個人識別番号（CPR番号）・氏名・自宅住所・顔写真、勤務先メールアドレス・職位・執務場所などの勤務情報、そして本人が登録していれば近親者の氏名・関係・電話番号です。元利用者については自宅住所・顔写真・近親者情報が6か月で自動削除される一方、CPR番号と氏名は残り続けます。

DTU は通知の形を2つに分けました。 CPR番号を保持している現役・元の職員と学生の「ほぼ全員」にはe-Boks（デンマークの公的電子私書箱）で個別通知を行い、直接連絡できない相手（ゲスト・外部パートナー・近親者）に届けるために公開告知を同時に出し、「該当しそうな人に共有してほしい」と呼びかけています。

日本の読者にとっての含意は2点です。 第一に、ID・アクセス管理システムが単一の侵害点になりうること。認証を集約する仕組みは、同時に全員の属性情報を1か所に集めた台帳でもあります。第二に、「元利用者のデータを何年持つか」が被害規模を決めること。 DTU の母数20万名のうち8割（約16万名）は元利用者です。現役の4万名を守る設計をしていても、過去23年分が同じ箱に入っていれば、被害は5倍になります。

  • 侵害されたシステム——DTUBasen。DTU のID・アクセス管理（identity and access management）システム
  • 侵入の形——何者かが DTU のプロファイル（利用者アカウント）を侵害し、それを使って DTUBasen へのアクセスを得た
  • 持ち出されたもの——大量のデータ。2003年まで遡る個人データへのアクセスが成立した
  • 規模——特定できない。 DTUBasen が保持する母数は現役 約40,000名・元利用者 約160,000名（合計で最大20万名）
  • 封じ込め——DTU の IT インシデント対応チームが攻撃を封じ込め、外部の専門家と協力して範囲を調査した
  • 届け出——デンマーク・データ保護庁（Datatilsynet）へ届け出、さらなる捜査のため関係当局へ付託

この事案の核心は、侵害された対象の性質です。

ID・アクセス管理システムは、認証を集約するために作られます。利用者が1か所でログインすれば、各システムへ入れる——運用の手間を減らし、権限の棚卸しを可能にする、正しい設計です。

しかし同じ仕組みは、全員の属性情報を1か所に集めた台帳でもあります。 DTUBasen が保持していたのは、認証に必要な最小限ではありません—— CPR番号・氏名・自宅住所・顔写真・勤務先情報・近親者の連絡先です。

そして23年分が入っていました。 DTU 自身が「2003年以降のいずれかの時点で DTU の職員・学生・ゲスト・外部パートナーであった人は、情報が含まれている可能性がある」と述べています。

母数の内訳を見ると、設計の帰結がはっきりします（本記録の整理）。

層 人数 割合
現役利用者 約40,000名 20%
元利用者 約160,000名 80%

被害の母数の8割は、もう DTU と関係のない人です。 現役の4万名を守る設計をしていても、過去23年分が同じ箱に入っていれば、被害は5倍になります。

DTU は「何が出たか特定できない」と明言した。これは調査しなかったのではない被害規模・影響範囲

DTU の公表文には、次の一文があります。

「残念ながら DTU は、何の情報が持ち出されたか、あるいは何名が影響を受けたかを正確に特定することはできないと認めざるを得ない」（原文英語）

この書き方を、2つの読み間違いから区別しておきます（本記録の整理）。

  • 「まだ調査中だから分からない」のではありません。公表文は、IT インシデント対応チームが封じ込めを行い、外部の専門家と協力して範囲を調査したうえでこの結論を示しています。
  • 「隠している」のでもありません。 DTU は母数（40,000／160,000）を具体的に示し、項目も層ごとに分けて列挙しています。

つまり「調べたが確定できなかった」という形です。

この形が意味するのは、記録（ログ）が持ち出しの内容を特定できる粒度で残っていなかったということです（本記録の読み。DTU はそのようには説明していません）。ID・アクセス管理システムへのログインは記録されていたはずですが、「そのセッションがどのレコードを読んだか」までは残っていなかったと読めます。

結果として、個々の対象者は「自分の情報が出たかどうか」を知ることができません。だから DTU の案内は全員向けの一般的な自衛手段になります——不審な連絡への警戒、パスワードの使い回しの解消、Borger.dk での CPR番号に対する信用警告（credit alert）の登録の検討。

ここに実務上の教訓があります（本記録の助言）。「何が出たか言えない」と公表した組織は、対象者に『あなたは安全です』と言うこともできません。通知の負荷は母数の全員に広がり、恒久的な警戒を求める形になります。

一般のアカウントから台帳全体に届いたのか、それは公表されていない原因・手口

DTU が示した侵入の経路は、次の一文です。

「攻撃は、権限のない者が DTU のプロファイルを侵害し、それを使って DTUBasen へのアクセスを得るというものだった。これにより、2003年まで遡る個人データへのアクセスが可能になった」
（原文英語）

起点は正規の利用者アカウントです。 脆弱性の悪用ではありません。

しかし、2つの重要な点が公表されていません（本記録の整理）。

  • そのプロファイルをどう侵害したのか。フィッシングか、パスワードの使い回しか、情報窃取型マルウェアか、多要素認証の突破か。示されていません。
  • そのプロファイルがどの権限を持っていたのか。 管理者アカウントだったのか、一般の利用者アカウントで台帳全体が読めたのかが区別されていません。

後者の区別は、他組織が自組織を点検するうえで決定的です。

  • 管理者アカウントだった場合——特権アカウントの保護の問題。対策は多要素認証の強化・特権アクセス管理・踏み台の分離。
  • 一般アカウントで台帳全体が読めた場合—— ID 管理システムの認可の設計の問題。対策は「自分の情報しか見えない」という原則の徹底と、一括照会の権限の分離。

DTU が公表しなかったことで、読者はどちらの対策を優先すべきか判断できません。

ただし、DTU 自身の助言に手がかりがあります（本記録の読み）。対象者への案内に、次の2項目が含まれています。

  • 「DTU のパスワードを使い回しているサービスのパスワードを変更する」
  • 「予期しないログインまたは認証の要求を承認しない」

1つ目は認証情報の使い回し、2つ目は多要素認証の疲労攻撃（承認要求を繰り返し送って押させる手口）を念頭に置いた助言と読めます。 ただし DTU は、本件の手口がそれであったとは述べていません。

通知を2つに分けた。届かない相手のために「共有してほしい」と頼む形になった組織の対応

DTU は通知の方法を、届く相手と届かない相手で分けました。

①e-Boks での個別通知
- 対象——CPR番号を保持している現役・元の職員、およびほぼ全ての現役・元の学生
- 手段——e-Boks（デンマークの公的な電子私書箱。公的機関からの通知を受け取る仕組み）
- 「できるだけ速やかに個別の通知を受け取ることになる」とされる

②公開告知
- 対象——ゲスト・外部パートナー、および DTUBasen に登録された近親者
- 理由——DTU はゲストと外部パートナーの CPR番号をごく少数しか保持しておらず、近親者の CPR番号は保持していない
- 「DTU が直接連絡できない人々に届けるために、同時にこの公開告知を出している。影響を受けうる元学生・元職員・ゲスト・外部パートナーへ共有してほしい」と呼びかけている（原文英語）

②の形を、評価と留保に分けます（本記録の評価）。

  • 評価できる——届かない層の存在を認め、その理由を具体的に説明し、代替手段を取っている。 「通知した」で済ませず、CPR番号を保持していないから届かないという理由まで書いています。公開告知を検索可能な形で自サイトに置き、「更新する」と明言しています。
  • 留保——到達は保証されません。 元学生・元職員への通知を、現役の関係者による口コミに委ねる形です。2003年まで遡る23年分の対象者に、この方法でどこまで届くのかは測れません。

DTU が案内した自衛手段は次のとおりです。

  • 不審なメール・SMS・電話に特に注意する—— とくに送信者や発信者が、本人や DTU との関係について情報を知っているように見える場合
  • 予期しない問い合わせへの返信で、パスワードその他の秘密情報を開示しない
  • 予期しないログイン・認証の要求を承認しない
  • DTU のパスワードを使い回しているサービスのパスワードを変更する
  • Borger.dk で CPR番号に対する信用警告（credit alert）の登録を検討する
  • 氏名・住所の保護（name and address protection）を受けている人は特に警戒する—— 情報が権限のない者の手に渡った場合、望まない接触・所在の特定・その他の嫌がらせのリスクが高まりうる（原文英語）

最後の項目は、この種の公表で見ることが少ない配慮です（本記録の注記）。DV 被害者など、住所を隠して生活している人にとって、自宅住所の流出は詐欺とは別種の危険になります。 DTU はその層を名指しして警告しています。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**「何が持ち出されたか、何名が影響を受けたかを正確に特定できない」と 明言し、代わりにシステムが保持している母数（現役約40,000名・ 元利用者約160,000名）と項目を層ごとに公表した。**機能した**公表の誠実さという点では機能したと評価できる**（本記録の評価）。 **「分からない」ことを分からないと書き、母数と項目は具体的に示している。** **この順序が逆になった事案は多い**—— 小さい数字を先に出し、後から段階的に増やす形である。 **留保**：**この誠実さは、記録が十分に残っていなかったことの帰結でもある。** **「特定できない」と言わずに済む状態を作るのが本来の目標であり、 その点では失敗している**（本記録の評価。DTU はそう述べていない）。
**通知を2経路に分けた。CPR番号を保持している現役・元の職員と ほぼ全ての現役・元の学生には e-Boks で個別通知し、 直接連絡できないゲスト・外部パートナー・近親者のために 公開告知を同時に出して「共有してほしい」と呼びかけた。**部分的に機能**届かない層の存在を認め、その理由を具体的に説明し、 代替手段を取っている点は評価できる**（本記録の評価）。 **「通知した」で済ませていない。** **ただし到達の測定が無く、元利用者が母数の8割を占めることを 踏まえれば、実効性は限定的と見るべきである。** **公表ページを「更新する」と明言している点は、 継続的な到達の経路として機能しうる。**
**IT インシデント対応チームによる封じ込めののち、 外部の専門家を起用して範囲の調査を行った。**評価材料なし**起用した組織・調査の範囲・結論の根拠が公表されていないため 評価できない。** **調査の結論が「何が持ち出されたか特定できない」であることだけが 分かっている。** **調査報告書の公表予定についての言及は無い。**
CISO・経営層への示唆
  • ID・アクセス管理システムは「認証の集約点」であると同時に「全員の名簿」である
    侵害されたのは DTUBasen——**DTU の ID・アクセス管理システム**である。 **認証を集約する仕組みは運用上正しい設計だが、 同じ仕組みが全員の属性情報を1か所に集めた台帳にもなる**（本記録の整理）。 **DTUBasen が保持していたのは認証に必要な最小限ではない**—— **CPR番号・自宅住所・顔写真・近親者の連絡先**まで入っていた。 **一つのアカウントの侵害が、20万名分の台帳の流出につながっている。**
    取るべき行動 **自社の ID 管理システム（Active Directory・IdP・人事システム連携）が 保持しているデータ項目を、実際に一覧として書き出す。** **「認証に必要か」を項目ごとに問い、必要でない項目を 別の保管先へ分離する計画を立てる。** **とくに回復不能な識別子（マイナンバー・生年月日）と、 本人以外の情報（緊急連絡先・近親者）が入っていないかを確認する。** **入っている場合、それは「認証基盤の事故」が 「全社員と家族の個人情報の事故」になる設計である。**
  • 「元利用者のデータを何年持つか」が、そのまま被害規模を決める
    DTU の母数20万名のうち、**元利用者は約160,000名——8割**である （本記録の算出）。 **保持されていたデータは2003年まで、23年分遡る。** **現役の約40,000名を守る設計をしていても、 過去23年分が同じ箱に入っていれば被害は5倍になる。** **DTU には削除の設計があった**（自宅住所・顔写真・近親者情報は 元利用者について6か月で自動削除）—— **しかし最も回復不能な CPR番号と氏名は対象外だった。**
    取るべき行動 **自社の主要なシステムについて「退職者・卒業生・解約顧客のデータを 何年保持しているか」を、設計ではなく実データで確認する。** **削除の設計がある場合、「何が削除され、何が残るか」を項目単位で 確認する**——DTU のように、部分的な削除が 最も重要な項目を残していることがある。 **保持の理由（法令・税務・同窓会・統計）を項目ごとに書かせ、 理由が無いものを削除する。** **「念のため残す」は理由ではない。**
  • 「何が出たか特定できない」と言わずに済む記録設計を、事故の前に作る
    DTU は外部の専門家と協力して調査したうえで **「何の情報が持ち出されたか、何名が影響を受けたかを 正確に特定することはできない」と結論している（原文英語）。** **これは誠実な公表だが、同時に記録設計の失敗の帰結でもある** （本記録の評価。DTU はそうは述べていない）。 **「特定できない」組織は、対象者に『あなたは安全です』と言えない**—— 通知の負荷が母数の全員に広がり、 **恒久的な警戒（信用警告の登録）を20万名に求める形になる。**
    取るべき行動 **自社の機微なデータを持つシステムについて、 「認証の記録」と「データアクセスの記録」が別々に残っているかを確認する。** **前者だけでは、事故のときに『何が出たか』を答えられない。** **記録の遡及可能な期間を確認し、 『この期間より前に始まった侵害は範囲を確定できない』という事実を 経営へ報告する。** **事故のときに最も高くつくのは、記録が無いことである。**
  • 「届かない相手」の存在を認めた通知設計を、平時に用意しておく
    DTU は通知を2経路に分け、**e-Boks で届かない層 （ゲスト・外部パートナー・近親者）の存在を、理由とともに公表した** ——**CPR番号を保持していないため直接連絡できない。** **そのうえで公開告知を出し「影響を受けうる人へ共有してほしい」と 呼びかけている。** **誠実な対応だが、到達は保証されない**—— **元利用者が母数の8割を占めるため、実効性は限定的である** （本記録の評価）。
    取るべき行動 **自社が保持する個人データについて「本人に連絡する手段を 持っているか」を層ごとに確認する**（現役／退職者／元顧客／ 本人以外として登録された人）。 **連絡手段が無い層があれば、それは事故のときに通知できない層である。** **その層のために、公開告知のひな形・掲載場所・ 更新の方針を平時に決めておく。** **さらに「本人以外の情報（緊急連絡先・近親者）を保持するなら、 その人への通知手段も要る」という原則を持つ。**
  • 住所を隠して生活している層への警告を、通知に明示的に含める
    DTU は**「氏名・住所の保護（name and address protection）を 受けている人は特に警戒すべきである。情報が権限のない者の手に 渡った場合、望まない接触・所在の特定・その他の嫌がらせの リスクが高まりうる」**と明記した（原文英語）。 **この種の公表で、この層を名指しして警告する例は少ない** （本記録の注記）。 **DV 被害者やストーキングの対象者にとって、自宅住所の流出は 詐欺とは別種の、身体的な危険になる。**
    取るべき行動 **個人データ侵害の通知のひな形に、 「住所の保護を受けている層への個別の警告」を項目として入れる。** **自社が自宅住所を保持しているシステムを特定し、 その層が含まれうるかを確認する。** **通知の文面を法務・人事と事前に合意しておく**—— 事故のあとで書くと、この配慮は落ちる。
セキュリティ技術者への示唆
  • ID 管理システムの「一括照会・エクスポート」を、通常の権限から切り離す
    **一つのプロファイルの侵害から、20万名分の台帳全体に到達している。** **DTU は、侵害されたプロファイルが管理者だったのか 一般利用者だったのかを公表していない**—— **この区別が無いため、読者は「特権の保護」と「認可の設計」の どちらを優先すべきか判断できない**（本記録の評価）。 **どちらであっても、一括で読み出せる状態だったことは確かである。**
    取るべき行動 **自社の ID 管理システムで「自分以外の情報を一覧で読める権限」を 持つアカウントを列挙する。** **一括照会・エクスポートの機能を、通常のログイン権限から分離し、 別の承認（2名以上）と記録を要する操作にする。** **「管理者だから全部見える」という設計を、 「操作ごとに昇格する」設計へ移す。** **一般利用者の権限で台帳全体が読めないことを、 実際にテストして確認する。**
  • 認証の記録だけでなく「どのレコードを読んだか」を残す
    **DTU の「何が持ち出されたか特定できない」という結論は、 セッション単位の活動の記録が十分でなかったことを示す** （本記録の読み。DTU はそうは説明していない）。 **ログインは記録されていたはずである**—— 侵害を検知し、封じ込め、プロファイルの侵害という経路まで 特定できている。 **足りなかったのは「そのセッションが何を読んだか」である。**
    取るべき行動 **機微なデータを持つシステムについて、 データアクセスの記録（誰が・いつ・どのレコードを・何件読んだか）を 有効にし、外部の収集先へ転送する。** **保持期間を決め、実際に遡れることを確認する** （有効にしただけで、容量上限で巻き取られている例がある）。 **容量が問題になるなら、全件ではなく 「機微な項目を含む応答」だけを記録する方針を検討する。**
  • 多要素認証を「承認を押すだけ」の形から変える
    **侵入の起点は正規の利用者プロファイルの侵害である。** **DTU は手口を公表していないが、対象者への助言に 「予期しないログインまたは認証の要求を承認しない」を 挙げている（原文英語）。** **これは多要素認証の疲労攻撃（承認要求を繰り返し送って 押させる手口）を念頭に置いた助言と読める**（本記録の読み。 DTU は本件の手口がそれであったとは述べていない）。
    取るべき行動 **ID 管理システムへのアクセスに、フィッシング耐性のある認証 （FIDO2・パスキー・端末バインドの証明書）を必須にする。** **当面それが難しい場合は、プッシュ通知の承認を 番号照合（number matching）の形に変える。** **「承認を押すだけ」の多要素認証は、 押させられる攻撃に対して無力である。** **認証要求の連続・短時間の繰り返しを警報に上げる。**
  • ID 管理システムからの大量読み出しに、件数の上限と警報を置く
    **「大量のデータがダウンロードされた」とされているが、 その挙動が検知されたという記述は無い**（本記録の読み）。 **ID 管理システムから数万件のレコードが読み出される挙動は、 平常時の分布から大きく外れる**—— **閾値による検知が成立しやすい類の動きである。**
    取るべき行動 **ID 管理システムの照会・エクスポート機能に、 1利用者・単位時間あたりの件数の上限と、 上限に近づいた時点の警報を設ける。** **上限値は平常時の分布を測ってから決める**—— 測らずに決めると、鳴り続けるか鳴らないかのどちらかになる。 **外向きの通信量も併せて監視し、 平常時から外れた転送を警報に上げる。**
  • 回復不能な識別子を、認証基盤の通常の応答から外す
    流出項目に**CPR番号（デンマークの個人識別番号）**が含まれる。 **DTU は「CPR番号その他の個人データが権限のない者の手に渡った場合、 なりすまし詐欺に使われうる」と警告している（原文英語）。** **パスワードは変えられるが、CPR番号は変えられない**—— **流出した時点で、なりすましの材料としての価値が恒久的に残る。** **DTU の削除の設計は、自宅住所と顔写真を6か月で消す一方、 CPR番号を残していた。**
