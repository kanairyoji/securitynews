2026年10月1日、Dell が Container Storage Modules（CSM）の複数の重大な脆弱性を勧告 DSA-2026-448 で公表しました。 CVSS 3.1 基本値 10.0 が2件含まれています。

CSM は、Kubernetes から Dell のエンタープライズストレージを使うための部品です。 クラスタの中で動き、ストレージアレイの管理者資格情報を預かる立場にあります。本勧告の深刻度は、この位置づけから来ています。

公表された6件の内訳はこうです。

CVE CVSS 内容
CVE-2026-63688 10.0 csm-authorization-storage の gRPC サーバで認証が欠落。未認証の攻撃者が登録された全ストレージアレイの管理者資格情報を取得できる
CVE-2026-63692 10.0 認可プロキシとテナントサービスで認証が欠落。未認証の攻撃者が認証制御を迂回し管理者権限を得られる

対策は更新のみです。 1.17.0 未満の全版が影響し、1.18.0 以降で修正されます。Dell は「更新以外に回避策や緩和策は無い」と明記しており、加えて「JWT の署名用の秘密を直ちに入れ替えること」を求めています。

日本の読者にとっての含意は2点です。 第一に、ストレージ連携の部品が「クラスタとストレージの両方の管理権限」を握る位置にあること。 攻撃面としてはクラスタの内側ですが、影響はクラスタの外（ストレージアレイ全体）へ出ます。第二に、鍵が製品に埋め込まれていた場合、更新だけでは終わらないこと。 Dell が JWT 署名鍵の入れ替えを求めているのは、更新前に偽造されたトークンが更新後も有効でありうるからです（本記録の読み）。

攻撃面はクラスタの内側だが、影響はストレージ基盤の全体へ出る概観

2026年10月1日、Dell が勧告 DSA-2026-448 で公表した内容は次のとおりです。

  • 対象製品——Dell Container Storage Modules（CSM）
  • 影響する版——1.17.0 未満の全版
  • 対策版——1.18.0 以降
  • 回避策——無い（Dell が明記）
  • 追加で求められる措置——JWT の署名用の秘密を直ちに入れ替えること
  • 公表された自社コードの脆弱性——6件（CVSS 10.0 が2件・9.9 が1件・9.8 が2件・9.6 が1件）
  • 第三者部品の脆弱性——golang.org/x/crypto・github.com/golang-jwt/jwt/v4・google.golang.org/protobuf・golang.org/x/net のものも併せて修正

CSM が何をする部品かを押さえると、点数の意味が分かります。

CSM は、Kubernetes から Dell のエンタープライズストレージを使うための橋渡しです。 クラスタの中で動きますが、ストレージアレイの管理者資格情報を預かる立場にあります。

だから「クラスタの内側にある部品の脆弱性」が、「ストレージ基盤全体の管理権限の喪失」になります（本記録の整理）。

Dell 自身の表現がそれを示しています。

「この脆弱性は、csm-authorization のセキュリティモデルの完全な迂回を可能にし、サポートされる5つの Dell ストレージ製品系列に及ぶストレージ基盤の完全な管理権限を攻撃者に与えるため、重大であると考えられる」（CVE-2026-63688 について。原文英語）

「5つの製品系列に及ぶ」という点が重要です。 影響は1つのアレイにとどまりません—— CSM が登録している全アレイの管理者資格情報が、1か所から取れます。

方向を整理すると、こうなります（本記録の整理）。

  • 入口——クラスタの内側（またはネットワーク越しに到達できる gRPC・認可プロキシ）
  • 出口——ストレージアレイの管理者権限（CVE-2026-63688・CVE-2026-63692・CVE-2026-54472・CVE-2026-61421）と、Kubernetes クラスタ全ノードの root（CVE-2026-67269）、クラスタ全体の Secret と RBAC（CVE-2026-67273）

どちらの向きにも抜けます。

CVSS 10.0 が2件という点数は「認証を置いていなかった」ことから来ている原因・手口

CVSS 3.1 で 10.0 に達するのは、簡単ではありません。次のすべてが同時に成立する必要があります。

  • AV:N——ネットワーク越しに攻撃できる
  • AC:L——攻撃の条件が容易
  • PR:N——権限が一切不要（未認証）
  • UI:N——利用者の操作が不要
  • S:C——影響が脆弱な部品の外へ及ぶ（スコープ変更）
  • C:H/I:H/A:H——機密性・完全性・可用性のすべてに高影響

CVE-2026-63688 のベクタはCVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H——上のすべてが立っています。

原因の性質を2群に分けると、対策の優先順位が見えます（本記録の整理）。

第1群：認証を置いていなかった（2件・いずれも 10.0）

  • CVE-2026-63688——csm-authorization-storage の gRPC サーバに重要な機能に対する認証が欠落。未認証のリモート攻撃者が登録された全ストレージアレイの管理者資格情報を取得できる
  • CVE-2026-63692——認可プロキシとテナントサービスに認証が欠落。未認証の攻撃者が認証制御を迂回し、認可サービスの完全な管理権限を得て全テナントにまたがるストレージ資源へのアクセス・操作ができる

これは「認証の実装を誤った」のではありません（本記録の読み）。認証を置いていないという形です。gRPC のサーバは、HTTP の API と違って「ブラウザから叩けない」ため守られている感覚を生みやすい——しかし到達できれば認証が無い（本記録の評価。Dell はそうは述べていません）。

第2群：鍵・資格情報を製品に埋め込んでいた（2件・いずれも 9.8）

  • CVE-2026-54472——CSM Authorization モジュールにハードコードされた資格情報。未認証のリモート攻撃者が暗号学的に妥当な管理者トークンを偽造し、CSM Authorization プロキシの管理者権限を得られる。Dell は「全テナントにまたがるストレージアクセスポリシーの権限のない管理が可能になる」としている
  • CVE-2026-61421——karavi-authorization の JWT 認証部品にハードコードされた暗号鍵。しかもその署名用の秘密は「公開されている（publicly available）」。知っている攻撃者はトークンを偽造できる

第2群が第1群より点数が低いのは S:U（スコープ変更なし）の差と考えられますが、実務上はこちらのほうが厄介です（本記録の評価）。理由は更新で終わらないことです—— 更新前に偽造されたトークンが、更新後も有効でありうる。 だから Dell は「JWT の署名用の秘密を直ちに入れ替えること」を求めています。

第3群：権限と入力処理（2件）

  • CVE-2026-67269（9.9）——ContainerStorageModule のカスタムリソースの調整処理（reconciler）の権限管理の不備。低権限のリモート攻撃者が権限を昇格し、クラスタノードで root を取れる。 Dell は「単一のカスタムリソースの投入によってKubernetes クラスタの全ノードを侵害できる」としている
  • CVE-2026-67273（9.6）——テンプレートエンジンで使われる特殊要素の不適切な無害化。低権限の攻撃者が権限を昇格し、機微な情報へアクセスし、RBAC の改変ができる。Dell は「クラスタ全体の Kubernetes Secret への読み取りアクセスと、クラスタスコープの RBAC リソースを作成する能力を与え、意図された Kubernetes のアクセス制御を実質的に迂回する」としている

CVE-2026-67269 の「単一のカスタムリソースの投入で全ノード」という記述に注目すべきです（本記録の評価）。Kubernetes のカスタムリソースを作る権限は、開発者に広く配られていることが多い—— 「クラスタ管理者ではない人」が持っている権限です。

更新だけでは終わらない。鍵の入れ替えを Dell が求めている対策・注意喚起

Dell が示した措置は2つです。

  1. 1.18.0 以降への更新（これ以外の回避策・緩和策は無いと明記）
  2. JWT の署名用の秘密を直ちに入れ替えること

2つ目を見落とさないでください（本記録の助言）。

ハードコードされた鍵による脆弱性では、更新が修正の完了を意味しません。

  • CVE-2026-61421 の署名用の秘密は「公開されている」。つまり、更新前の期間に誰でもトークンを偽造できた可能性がある
  • 偽造されたトークンは、鍵を替えなければ更新後も検証を通る（本記録の読み。Dell はこの理由を説明していない）

したがって対応の順序はこうなります（本記録の整理。Dell はこの順序を示していません）。

  1. 1.18.0 以降へ更新する
  2. JWT の署名用の秘密を入れ替える
  3. CSM が登録しているストレージアレイの管理者資格情報を入れ替える ——CVE-2026-63688 で取得されうる対象そのものである
  4. クラスタの RBAC を確認する——CVE-2026-67273 でクラスタスコープの RBAC リソースが作成されうる。更新しても、作られたものは残る

3と4は Dell が求めた措置ではありません。 本記録が「脆弱性の内容から、更新だけでは残るもの」として挙げた項目です。

一方で、入れ替えには副作用があります。 鍵と資格情報の入れ替えは、連携を一時的に壊します——ストレージへのアクセスが止まれば、そのストレージを使っている全ワークロードが影響を受けます。 「どの順序で、どの業務を止めて行うか」の段取りが要ります。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「クラスタとストレージの境界に置く部品」は、両側の管理権限を握っている
    CSM は Kubernetes から Dell のストレージを使うための橋渡しだが、 **ストレージアレイの管理者資格情報を預かる立場**にある。 **Dell 自身が「サポートされる5つの Dell ストレージ製品系列に及ぶ ストレージ基盤の完全な管理権限を攻撃者に与える」としている（原文英語）。** **攻撃面はクラスタの内側だが、影響はクラスタの外へ出る**（本記録の整理）。 **CVE-2026-67269 は逆向きで、クラスタ全ノードの root に至る。**
    取るべき行動 **自社のインフラで「2つの領域の境界に立ち、両側の資格情報を預かる 部品」を列挙する**（ストレージ連携・CSI ドライバ・クラウド連携の コントローラ・CI/CD のランナー・バックアップのエージェント）。 **それぞれについて「侵害されたら、どちらの側の何が失われるか」を 1行で書き出す。** **この種の部品は「補助的な部品」として資産台帳の優先度が 低く置かれていることが多い**——**権限の大きさで優先度を付け直す。**
  • 鍵が製品に埋め込まれていた脆弱性は、更新だけでは終わらない
    **CVE-2026-61421 では、JWT の署名鍵が製品にハードコードされ、 しかもその秘密は「公開されている」とされる（原文英語）。** **CVE-2026-54472 も資格情報のハードコードである。** **Dell は更新に加えて「JWT の署名用の秘密を直ちに入れ替えること」を 求めている**——**更新前に偽造されたトークンが、 鍵を替えなければ更新後も検証を通るためと読める** （本記録の読み。Dell はこの理由を説明していない）。
    取るべき行動 **脆弱性対応の手順に「更新で終わるか／鍵と資格情報の入れ替えが要るか」の 判定を組み込む。** 判定の目安は **「脆弱性の分類がハードコードされた資格情報・暗号鍵（CWE-798・CWE-321）か」 「認証を迂回できる期間があったか」である。** **入れ替えには停止時間が要るため、 「更新は適用したが鍵は替えていない」状態が残りやすい**—— **対応の完了条件に鍵の入れ替えを明記する。**
  • ベンダーの勧告を直接取り込む経路を持つ。NVD だけでは検知できない
    **本記録の作成者が6件の CVE について NVD を照会したところ、 いずれも未登録だった**（2026年10月4日時点。勧告の公表から3日後）。 **採点・ベクタの記載は Dell 自身のものしか存在しない。** **脆弱性管理の仕組みが NVD を参照している場合、本件は検知されない** （本記録の評価）。
    取るべき行動 **自社が使っている主要な製品について、ベンダーの勧告ページ・ RSS・メーリングリストを直接購読する経路があるかを確認する。** **「スキャナが見つけてくれる」という前提を検証する**—— スキャナのデータ源が NVD だけなら、公表直後の数日は空白になる。 **とくに CVSS 9.0 以上が出やすい基盤部品 （ストレージ・ネットワーク・認証）については、 ベンダー直の経路を必須にする。**
  • 「悪用の報告が無い」を、優先度を下げる根拠にしない
    **本件について悪用の報告は無い。** だが性質を見るべきである （本記録の評価）—— **①CVSS 10.0 の2件は未認証（`PR:N`）で到達できる。 ②CVE-2026-61421 の署名用の秘密は「公開されている」ため、 実証コードを書く必要すらない。③回避策が無いため、 更新するまで攻撃面は開いたままである。** **The Hacker News は Dell 製品の脆弱性 CVE-2021-21551 と CVE-2026-22769 が近年実際に悪用されていることを挙げている。**
    取るべき行動 **脆弱性の対応期限を「悪用の有無」ではなく 『深刻度 × 自組織での到達可能性 × 回避策の有無』で決める運用にする。** **悪用の情報は期限を前倒しする材料としてのみ使い、 後ろ倒しの材料にはしない。** **とくに「回避策が無い」と明記された勧告は、 更新するまで何も打てないことを意味する**—— **その事実を期限の設定に反映させる。**
セキュリティ技術者への示唆
  • gRPC や内部向けの API に認証を置いているかを、実際に叩いて確認する
    **CVE-2026-63688 は `csm-authorization-storage` の gRPC サーバに 重要な機能に対する認証が欠落していたものである。** **CVE-2026-63692 は認可プロキシとテナントサービスの認証の欠落。** **いずれも「認証の実装を誤った」のではなく「置いていない」形である** （本記録の読み）。 **gRPC のサーバは、ブラウザから叩けないため守られている感覚を 生みやすいが、到達できれば認証が無い**（本記録の評価。 Dell はそうは述べていない）。
    取るべき行動 **自社の製品・内製システムで、内部向けとされている API （gRPC・内部 REST・管理用エンドポイント）を列挙し、 認証が有効かを実際に認証情報なしで叩いて確認する。** **「ネットワークで守られている」という前提を、 クラスタの内側から到達できるかで検証する**—— 同じクラスタ内のポッドは、既定で互いに到達できる。 **NetworkPolicy を既定拒否にしているかを併せて確認する。**
  • Kubernetes のカスタムリソースを作れる権限が、どこまで配られているかを数える
    **CVE-2026-67269 について Dell は 「単一のカスタムリソースの投入によって Kubernetes クラスタの 全ノードを侵害できる」としている（原文英語）。** **必要な権限は管理者ではなく「低権限のリモート攻撃者」である。** **カスタムリソースの作成権限は、開発者に広く配られていることが多い** ——**「クラスタ管理者ではない人」が持っている権限である** （本記録の評価）。
    取るべき行動 **`kubectl auth can-i --list` を各 ServiceAccount・各名前空間で 実行し、カスタムリソースを作成できる主体を一覧にする。** **オペレータが監視しているカスタムリソースの種類ごとに、 「誰が作れるか」を確認する**—— **オペレータは特権で動くため、そこへ渡る入力は特権への入力である。** **CI/CD のサービスアカウントが広い権限を持っていないかを特に確認する。**
  • 更新後に「作られたもの」が残る脆弱性を見分ける
    **CVE-2026-67273 は、クラスタ全体の Secret の読み取りと 「クラスタスコープの RBAC リソースを作成する能力」を与える （原文英語）。** **更新しても、更新前に作成された RBAC リソースは残る** （本記録の読み。Dell はこの点に触れていない）。 **同様に、更新前に取得された資格情報・偽造されたトークンも残る。**
    取るべき行動 **脆弱性の内容から「更新後も残るもの」を洗い出す習慣を持つ**—— **①作成されたリソース（RBAC・ServiceAccount・Secret） ②読み取られた資格情報 ③偽造されたトークン ④残置された永続化。** **本件では、クラスタスコープの ClusterRole と ClusterRoleBinding の 作成時刻を監査ログと突き合わせ、 正当な自動化によるものと区別する。** **区別がつかない場合、それ自体が記録設計の欠陥である。**
  • 構成モジュールごとの版を一覧で持つ。製品全体の版だけでは足りない
    **勧告は CSM 全体として「1.17.0 未満が影響・1.18.0 で修正」としているが、 報道は部品ごとに別の版表記を伝えている**—— **「CSM Authorization version 2.4.0」（CVE-2026-63688）、 「CSM Operator version 1.12.0」（CVE-2026-67269）。** **本記録は対応表を確認できなかった。** **「1.17.0 未満が影響・対策は 1.18.0」の間に 1.17.x があることも 読み取れない**（本記録の注記）。
    取るべき行動 **CSM のようなモジュール構成の製品について、 稼働中のモジュールとその版を一覧で取得する手順を用意する** （コンテナイメージのタグ・Helm のリリース情報・ カスタムリソースの `status`）。 **「製品のバージョンは最新です」という報告を、 モジュール単位の一覧で裏取りする。** **版の対応表が勧告に無い場合は、ベンダーへ照会する**—— 推測で「影響なし」と判断しない。
  • ストレージアレイの管理者資格情報を、連携部品に預けたまま放置しない
    **CVE-2026-63688 で取得されうるのは 「登録された全ストレージアレイのストレージバックエンド 管理者資格情報」である（原文英語）。** **CSM は、登録された全アレイの管理者資格情報を1か所に 集めて保持している**（本記録の整理）。 **一つの部品の認証の欠落が、全アレイの管理権限の喪失になる。**
    取るべき行動 **連携部品に預けている資格情報を列挙し、 それぞれが「管理者権限」なのか「必要な操作に限った権限」なのかを 確認する。** **ストレージ連携に管理者権限が必要なのかをベンダーへ確認し、 より狭い権限で動かせるなら切り替える。** **切り替えられない場合は、その事実を記録に残す**—— **「この部品が落ちると全アレイが落ちる」という依存を 経営へ報告する材料になる。** **併せて、資格情報の定期的な入れ替えの手順を用意しておく** （本件の対応で必要になる）。

観点自社に当てはまるか該当する場合に何が起きうるか
