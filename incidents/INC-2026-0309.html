Fortra が2026年10月1日、特権アクセス管理製品 Core Privileged Access Manager（BoKS）の脆弱性8件を公表した。最も重いのは CVE-2026-79901（CVSS 9.9）で、BoKS keytab による Active Directory サービスアカウント管理を使っている環境では、サービスアカウントのパスワードが「現在の Unix タイムスタンプを種にした予測可能な擬似乱数列」から生成されていた。サービスプリンシパルを知り、パスワード変更時刻を推定できる攻撃者は候補を限られた数に絞ってオフラインで検証できる。BoKS への管理者権限もキータブへのアクセスも不要で、普通の認証済み AD アカウントがサービスチケットを要求できれば成立する。ほかに crlserver のコマンドインジェクション（9.1・root 実行）と自動登録機能のスタックバッファオーバーフロー（9.8・未認証）がある

2026年10月1日、Fortra が特権アクセス管理製品Core Privileged Access Manager（BoKS）の脆弱性8件を公表しました。 うち3件が重大（critical）です。

最も読むべきは CVE-2026-79901（CVSS 9.9）です。 BoKS keytab による Active Directory サービスアカウント管理を使っている環境で、boks_keytabmd が生成する AD サービスアカウントのパスワードが、「現在の Unix タイムスタンプを種にした予測可能な擬似乱数列」から作られていました（原文英語）。

攻撃の成立条件が軽いことが問題です。 Fortra 自身の説明によれば——

「標準的な認証済みの Active Directory アカウントは、通常、影響を受けるアカウントに割り当てられた SPN に対するサービスチケットを要求できる。BoKS、サービスホスト、またはそのキータブへの管理者アクセスは通常は必要ない。以前に取得したサービスチケットが、代わりにオフライン検証のための材料を提供することもある」（原文英語）

つまり、必要なのは①サービスプリンシパルの名前を知っていること、②パスワードの変更時刻を推定できること、③適切な Kerberos のチケット材料を持っていることだけです。 「特権アクセス管理の製品に入る」必要がありません。 ドメイン内の普通のアカウントから始まります。

残る2件の重大な脆弱性も押さえておきます。

  • CVE-2026-79898（CVSS 9.1）——crlserver のコマンドインジェクション。CRL の URL を追加する権限を持つ認証済み利用者が、BoKS Master 上で root としてシェルコマンドを実行させられる。 BCC と WSI（REST / SOAP API）はネットワーク越しに到達でき、ローカルの sudo / suexec の規則を要しない
  • CVE-2026-12627（CVSS 9.8）——boks_autoregisterd のスタックバッファオーバーフロー。未認証のリモート攻撃者が自動登録サービスへ到達できればメモリ破壊を起こせる

Fortra は、いずれの脆弱性についても実際の悪用は報告していません。

日本の読者にとっての含意は2点です。 第一に、「秘密を作る場所」の乱数の品質が、製品の信頼の全体を決めること。 特権アクセス管理の製品は、パスワードを管理するために導入されます—— その製品が作るパスワードが時刻から予測できたのでは、導入の目的そのものが崩れます。第二に、更新しただけでは終わらないこと。 脆弱な版が生成したパスワードは、更新後も使われ続けます（本記録の読み。Fortra はこの点を明示していません）。

パスワードを管理する製品が、時刻からパスワードを作っていた概観

2026年10月1日、Fortra が公表した内容のうち最も重いのはCVE-2026-79901（CVSS 9.9）です。

Fortra 自身の説明（原文英語）を訳します。

「BoKS keytab 管理を使っている環境では、影響を受ける版のboks_keytabmd が、現在の Unix タイムスタンプを種にした予測可能な擬似乱数列から Active Directory サービスアカウントのパスワードを生成する。サービスプリンシパルを知り、パスワードの変更時刻を推定できる攻撃者は、限られた候補の集合を再現し、候補をオフラインで検証できる」

BoKS は特権アクセス管理（PAM）の製品です。 Unix / Linux のサーバ群を中央で管理し、アカウントとアクセス制御のポリシーを適用します。パスワードを安全に管理するために導入される製品です。

その製品が、現在時刻を種にしてパスワードを作っていました。

Unix タイムスタンプは秒単位の整数です。 パスワードの変更時刻を「ある1日のうち」まで絞れれば、候補は約86,400通りになります（本記録の整理。Fortra は候補数を示していません）。「ある1時間のうち」なら3,600通りです。 オフラインで検証できるなら、この規模は問題になりません。

分類は CWE-338（暗号学的に弱い擬似乱数生成器の使用）です。

これは実装の細部の誤りではありません（本記録の読み）。「秘密を作る場所に、秘密でないものを種として渡していた」という設計の判断です。 時刻は、攻撃者から見て公開情報です。

必要なのは「ドメイン内の普通のアカウント」だけである原因・手口

CVE-2026-79901 で注目すべきは、成立条件の軽さです。

Fortra の説明（原文英語）を訳します。

「標準的な認証済みの Active Directory アカウントは、通常、影響を受けるアカウントに割り当てられた SPN（サービスプリンシパル名）に対するサービスチケットを要求できる。BoKS、サービスホスト、またはそのキータブへの管理者アクセスは通常は必要ない。以前に取得したサービスチケットが、代わりにオフライン検証のための材料を提供することもある」

攻撃の流れを整理します（本記録の整理）。

  1. 攻撃者は、ドメイン内の普通の認証済みアカウントを持っている
  2. 影響を受けるサービスアカウントの SPN に対して、サービスチケットを要求する（AD の通常の動作であり、特別な権限は要らない）
  3. パスワードの変更時刻を推定し、Unix タイムスタンプから候補のパスワードを再現する
  4. サービスチケットを使って、候補を1つずつオフラインで検証する ——BoKS にも AD にも通信を発生させない
  5. 一致した候補が、そのサービスアカウントのパスワードである

この手順は、Kerberoasting と呼ばれる既知の手法の構造です（本記録の注記。Fortra はこの用語を使っていません）。通常の Kerberoasting は、サービスアカウントのパスワードが弱い場合に辞書攻撃で破るものです。 本件が重いのは、「弱いパスワードを使っていた組織」ではなく「製品が作ったパスワードを使っていた組織」が対象になるからです（本記録の評価）。

CVSS 9.9 のベクタはCVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H です。

  • PR:L（低い権限で足りる）——管理者ではなく、ドメイン内の普通の認証済みアカウント
  • S:C（スコープ変更）——影響が BoKS の外（Active Directory）へ及ぶ

PR:N（権限不要）ではありません。 誰でも外部から撃てる種類ではなく、「ドメインに足場がある」ことが前提です。 この区別は実務上重要です—— インターネットに露出しているかどうかより、「ドメイン内に足場を取られたときに何が起きるか」で考えるべき脆弱性です。

「以前に取得したサービスチケットが、代わりにオフライン検証の材料を提供することもある」という一文も重いです（本記録の評価）。過去にチケットを取っていれば、いま AD にアクセスできなくても検証を進められます。

CVE-2026-79898（CVSS 9.1・CWE-78・コマンドインジェクション）

Fortra の説明（原文英語）を訳します。

「Fortra BoKS Manager には crlserver のコマンドインジェクションの脆弱性がある。BCC、WSI の REST または SOAP API、あるいはcacrl コマンドラインインタフェースを通じて CRL の URL を追加する権限を持つ認証済み利用者が、BoKS Master 上で root としてcrlserver にシェルコマンドの置換を処理させられる可能性がある。BCC と WSI はネットワークから到達できる管理の経路を提供し、ローカルの sudo / suexec の規則を必要としない。cacrl を root 以外で使う場合はそのような規則が必要である」

押さえるべきは2点です。

  • 到達先が BoKS Master 上の root です。特権アクセス管理の中枢で任意のコマンドが動きます
  • BCC と WSI はネットワーク越しに到達でき、ローカルの sudo / suexec の規則を要しません—— 「サーバにログインできる人」ではなく「管理 API を叩ける人」が対象です

ベクタは CVSS:3.1/AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H で、PR:H（高い権限が必要）です。 CRL の URL を追加する権限を持つ認証済み利用者が前提であり、誰でも叩けるわけではありません。 ただし S:C（スコープ変更）が立っており、影響は crlserver の外へ出ます。

CVE-2026-12627（CVSS 9.8・CWE-121・スタックバッファオーバーフロー）

「Fortra の Core Privileged Access Manager（BoKS）にはboks_autoregisterd のスタックベースのバッファオーバーフローの脆弱性がある。自動登録サービスへのネットワークアクセスを持つリモート攻撃者が、クライアント応答の処理中にメモリ破壊を引き起こせる可能性がある」（原文英語）

ベクタは CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H—— PR:N（権限不要）です。

3件のうち、これだけが未認証で到達できます（本記録の整理）。「自動登録サービスがどこから到達できるか」が、そのまま攻撃面の大きさになります。 BoKS の自動登録は、新しいホストを BoKS の管理下へ組み入れるための機能とみられます（本記録の推定。Fortra は機能の説明をしていません）—— 運用上「常時開けておく必要があるか」を問うべき種類のサービスです。

CISO・経営層への示唆
  • 「秘密を作る製品」の乱数の品質が、その製品の価値の全体を決める
    **BoKS は特権アクセス管理の製品であり、 パスワードを安全に管理するために導入される。** **その製品の `boks_keytabmd` が、 「現在の Unix タイムスタンプを種にした予測可能な擬似乱数列」から AD サービスアカウントのパスワードを生成していた（原文英語）。** **これは実装の細部の誤りではなく、 「秘密を作る場所に、秘密でないものを種として渡していた」という 設計の判断である**（本記録の読み）。 **時刻は、攻撃者から見て公開情報である。**
    取るべき行動 **自社が導入している「秘密を作る製品・機能」を列挙する** （特権アクセス管理・パスワードマネージャ・証明書の発行・ トークンの発行・API キーの生成・一時パスワードの発行）。 **それぞれについて、乱数源と鍵の長さが文書で示されているかを確認する。** **示されていないものがあれば、ベンダーへ照会する。** **調達の要件に「暗号学的に安全な乱数源を使うこと」を 明記する**——**明記しなければ、確認する機会が無い。**
  • 更新の完了を「パッチの適用」ではなく「秘密の作り直し」で定義する
    **CVE-2026-79901 と CVE-2026-9864 は、いずれも パスワードの生成の脆弱性である。** **更新は新しく生成されるパスワードを直すが、 すでに生成されたパスワードは直さない。** **低いエントロピーで作られた秘密は、作り直さないかぎり 低いままである**（本記録の評価）。 **本記録は Fortra がこの指示を出しているかを確認できなかった** ——勧告ページ本体へ到達できなかったためである。
    取るべき行動 **脆弱性対応の完了条件に、 「この脆弱性によって作られた・漏れた可能性がある秘密を 作り直したか」の項目を加える。** **判定の目安は「脆弱性の分類が、秘密の生成・保管・ 伝送に関わるものか」である** （CWE-338・CWE-798・CWE-321・CWE-522 など）。 **作り直しには停止時間が要るため、 「更新は適用したが秘密は替えていない」状態が残りやすい**—— **残っていないかを、対応の記録で確認できるようにする。**
  • 特権アクセス管理の製品は「止めると誰も入れなくなる」位置にある
    **BoKS は Unix / Linux のサーバ群を中央で管理し、 アカウントとアクセス制御のポリシーを適用する製品である。** **CVE-2026-79898 の到達先は「BoKS Master 上の root」であり、 特権アクセス管理の中枢で任意のコマンドが動く。** **一方で、更新のために BoKS を止めると、 それが認証・認可を担っているサーバ群へのアクセスに影響する** （本記録の整理。Fortra は更新の副作用を述べていない）。
    取るべき行動 **特権アクセス管理の製品について、 「製品が止まったときに、誰がどうやってサーバへ入るか」を 文書化し、実際に試す。** **代替経路（ローカルの root パスワード・コンソールアクセス・ 緊急用のアカウント）が機能することを、定期的に確認する。** **代替経路が無いと、緊急の更新を適用できない**—— **「止められないから更新できない」という理由で 脆弱性が残り続ける構造を避ける。**
  • 「悪用の報告が無い」は、オフラインで進む攻撃には当てはまらない
    **CVE-2026-79901 の攻撃はオフラインで進む。** **Fortra 自身が「候補をオフラインで検証できる」と書いている。** **攻撃者が行うのは①サービスチケットの要求 （AD の通常の動作であり、ログには正常な要求として残る）と ②自分の環境での候補の検証（組織のネットワークには何も残らない） だけである**（本記録の整理）。 **したがって「悪用された痕跡」が通常の意味では残らない。** **見えない攻撃は報告もされない。**
    取るべき行動 **脆弱性の優先度づけに「攻撃が観測可能か」の軸を加える。** **オフラインで進む攻撃（パスワードの推測・鍵の再現・ ハッシュの解析）については、 「攻撃されたか」を問うのをやめ、 「脆弱な状態で作られた秘密を作り直したか」を問う。** **前者は答えられないが、後者は答えられる**（本記録の助言）。 **報告書の様式も、この違いを反映させる。**

  • 自動登録のような「導入時だけ要る機能」を常時開けていないか確認する
    **CVE-2026-12627（CVSS 9.8）は `boks_autoregisterd` の スタックバッファオーバーフローで、 「自動登録サービスへのネットワークアクセスを持つ リモート攻撃者」が未認証で到達できる（原文英語）。** **本件で確認できた中で、未認証で到達できる最も重い脆弱性である。** **自動登録は、新しいホストを管理下へ組み入れるための機能と みられる**（本記録の推定。Fortra は機能の説明をしていない）—— **常時必要とは限らない。**
    取るべき行動 **「導入時・登録時だけ必要な機能」を列挙し、 常時有効になっていないかを確認する** （自動登録・ブートストラップ・初期設定の API・ 既定の管理アカウント）。 **必要なときだけ開ける運用に変えられるかを検討する。** **変えられない場合は、到達できる範囲を 「新規ホストが置かれるネットワーク」に限定する。** **攻撃面は、機能の有無ではなく到達範囲で決まる。**
  • 独自に書いたプロトコルのパーサを洗い出す
    **本件には、独自のパーサ・独自の処理に由来する脆弱性が複数ある**—— **CVE-2026-79896 は `boks_portmux` が使う 「独自の TLS ClientHello パーサ（custom TLS ClientHello parser）」の 境界外読み取り、CVE-2026-79900 は `boks_ksllogsd` が ダイジェスト名の長さを検証せずに固定長16バイトの領域へ コピーしていたもの（原文英語）。** **後者は「OpenSSL が名前を認識するかは検証していたが、 長さが収まるかは検証していなかった」という形である**—— **検証を1つ行ったことで、もう1つの検証を忘れている。**
    取るべき行動 **自社の製品・内製ツールで、標準ライブラリを使わずに 自分で書いたプロトコルのパーサを列挙する** （TLS のハンドシェイク・独自の管理プロトコル・ バイナリの設定ファイル）。 **それぞれについて、固定長の領域へコピーしている箇所を 特定し、長さの検証があるかを確認する。** **「値の妥当性」と「値の長さ」は別の検証であることを コードレビューの観点に入れる。** **可能なら標準ライブラリへ寄せる**—— 独自のパーサは、監査の目が少ない。
  • 一時ファイルの作成を、umask ではなくファイル記述子の権限で守る
    **CVE-2026-79899 は `bccgethostcert` が 「制限的な umask を先に設定せずに予測可能な一時ファイルを 作成する」ものである（原文英語）。** **BoKS Master 上のローカル利用者が `BOKS_tmp` 配下を読める場合、 **CA の秘密またはホストの秘密鍵の材料を取得できる可能性がある。** **さらに「証明書の取得が成功した後に残された CA の秘密の材料」も 対象とされており、後片付けの漏れも含まれている。**
    取るべき行動 **自社のコードで一時ファイルを作っている箇所を列挙し、 ①名前が予測可能でないか ②作成時の権限が 作成者のみに限られているか ③処理の後に削除されるかを 確認する。** **umask に依存せず、`mkstemp` 相当の関数と 明示的な権限指定を使う。** **秘密を一時ファイルに書く設計そのものを見直す**—— メモリ上で渡せるなら渡す。 **削除は、異常終了の経路でも必ず通るようにする。**
