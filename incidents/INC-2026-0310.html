第一に、6件のうち4件が CVSS 9.8 で、ベクタがすべて CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H です。 PR:N——権限が要りません。 AC:L——条件も要りません。つまり HCSS のサーバにネットワークから到達できれば、認証を通らずに成立します。

  • CVE-2026-82828（8.8・CWE-863）——不適切な認可。「権限を持たない一般利用者が、管理者権限相当の操作を実行できる」（原文英語）。PR:L——何らかのアカウントが1つあれば足ります

9.8 の4件は、ベクタまで同一です。

ここが本件の形です（本記録の読み）。4件の性質はまったく違います——パスの扱い、認証の有無、鍵の管理、隠された入口。しかし到達の条件が同じです。 「HCSS のサーバにネットワークから届くかどうか」だけが成立の分かれ目になっています。

日立産機システムの公表文には、こう書かれています（原文英語）。

「緩和策なし」の意味を、実務の言葉にします（本記録の整理）。

  • 「この機能を切れば当面しのげる」が無い。 CVE-2026-82825 の「重要な API」も、CVE-2026-82829 の「隠しアカウント」も、具体的に何かは公表されていません。切る対象が特定できません

ただし到達範囲を絞ることには副作用があります（本記録の評価）。HCSS はブラウザから使う設計です。製品の説明では「インストール後は PC・タブレット・スマートフォンのブラウザから利用できる」ことが利点として挙げられています。絞り込みは、この利点を削ることと同義です。 現場の端末・タブレットからの操作、遠隔からの監視、別拠点からの印字内容の配信が止まる可能性があります。 絞る前に「誰がどこから HCSS を使っているか」を把握しておかないと、生産が止まります。

止まるのは情報ではなく、印字である評価・解釈

HCSS が何をするソフトウェアかを押さえると、この6件の意味が変わります。

HCSS は日立の産業用連続インクジェット（CIJ）プリンタをクライアント／サーバ構成で集中管理するソフトウェアです。ブラウザから印字内容（メッセージ）を設計し、中央のデータベースで管理して、複数台のプリンタと画像検査装置の状態を1つの画面で監視します。（以上は製品の公開された説明にもとづきます。）

印字されるのは、賞味期限・ロット番号・製造日です。

ここから、9.8 の4件の帰結を読み替えます（本記録の評価）。

  • CVE-2026-82824（パストラバーサル）——「ファイルへのアクセス・作成・変更・削除」。印字内容のテンプレート・設定・ログが対象になりえます
  • CVE-2026-82825（重要な API の認証の欠落）——「機微な情報の不正な取得または改変、あるいは不正な操作」。プリンタへの指示そのものが「不正な操作」の対象です
  • CVE-2026-82827（JWT 署名鍵のハードコード）——「不正な Bearer トークンを生成して管理機能を悪用」。管理者としてログインした状態を作れます
  • CVE-2026-82829（隠された機能）——「隠しアカウントまたはハードコードされた認証情報による不正アクセス」。認証の仕組みを通らない入口です

つまり、取れるのは情報ではなく印字の制御です。

帰結として考えられるのは2つです（いずれも本記録の推定であり、日立産機システムは影響の形を述べていません）。

  1. ラインが止まる。 印字ができなければ、多くの業種では製品を出荷できません。ランサムウェアに暗号化されたときと同じ結果になりますが、暗号化は要りません——設定を壊すだけで足ります
  2. 誤った情報が印字された製品が出る。 これはより厄介です。間違った賞味期限・間違ったロット番号は、気づくのが出荷後になりえます。 回収の範囲を決めるための情報が、まさに汚染された側にあります

2つ目のほうを重く見るべきだと本記録は考えます。 止まったことは分かります。間違っていたことは分かりません。

ここに1つ、実務上の論点があります（本記録の評価）。

HCSS は日本のベンダーが作り、日本の工場にも入っている製品です。 その脆弱性を、海外の政府機関が制御システムの勧告として扱いました。 製品の分類がそこにあるということです。

一方で HCSS は、PLC でもセンサでもありません。 ブラウザから使う Web アプリケーションであり、クライアント／サーバ構成で動き、JWT で認証します。 本件の6件の CWE——パストラバーサル・認証の欠落・ハードコードされた鍵・不適切な認可・平文通信——は、すべて Web アプリケーションの脆弱性の語彙です。

この二重性が、資産台帳から抜け落ちる原因になります。

  • 情報システム側の台帳には、工場の設備として買われたものは載りにくい
  • OT 側の台帳には、プリンタとその管理ソフトは「設備の付属品」として一行で済まされやすい

本件への最初の対応は、更新ではなく台帳の確認です（本記録の助言）。「HCSS が自社のどこで動いているか、版は何か、どのネットワークから到達できるか」が答えられなければ、更新の計画は立ちません。

悪用の有無は公表されていない——「確認されていない」とも書かれていない未確定事項

本件について、悪用の有無は公表されていません。

重要な区別をします（本記録の確認）。日立産機システムの公表文にもカナダ・サイバーセンターの勧告にも、「悪用は確認されていない」という明示の否定はありません。 触れていないだけです。 「否定された」と「書かれていない」は違います。

そのうえで、公表後の難度について一点だけ記しておきます（本記録の評価）。

CVE-2026-82827（ハードコードされた JWT 署名鍵）とCVE-2026-82829（隠しアカウントまたはハードコードされた認証情報）は、「秘密がコードの中にある」種類の脆弱性です。 こうした脆弱性は、脆弱な版と対策版を比べれば秘密そのものが取り出せます。 つまり公表の時点から、再現の難度が下がります。

したがって本件は「悪用の報告が無いから様子を見る」で置いておける種類ではないと本記録は考えます。 4件の 9.8 が未認証で成立し、緩和策が無く、秘密がコードに埋まっている——この3つが揃っています。

到達範囲の把握が、更新までの唯一の守りになる対策・注意喚起

緩和策が「なし」であるため、更新までの守りは「ネットワークから届かないようにする」に限られます。 これは4件の 9.8 がすべて AV:N／PR:N であることの裏返しです。

一方で、到達範囲を示す数は公表されていません。 インターネットから到達できる HCSS がどれだけあるかという集計を、本記録の作成者も見つけられませんでした。 つまり「自社がどうか」を外部の情報から推し量ることはできません。

自社で確認するほかありません（本記録の助言）。

  • HCSS のサーバの IP とポートを特定する
  • その宛先に、どのネットワークから到達できるかを実際に試して確かめる（設定の読み合わせではなく通信で確かめる。工場のネットワークは、図面と実態が合わないことが多い）
  • インターネットから到達できる場合は、更新の優先度を最上位に上げる
  • 到達できる端末・利用者を列挙してから絞る（絞ってから列挙すると生産が止まる）

なお、HCSS が「ブラウザからどこでも使える」ことを利点として売られている製品であることを忘れないでください。 その利点のために広げられた到達範囲が、そのまま攻撃面になっています（本記録の評価）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「設備の付属ソフト」が資産台帳の空白に落ちる
    **HCSS は産業用インクジェットプリンタを集中管理する Web アプリケーションである。** **情報システムの台帳には「工場の設備として買われたもの」として 載りにくく、OT の台帳には「プリンタの付属品」として 一行で済まされやすい**（本記録の評価）。 **本件の脆弱性は、カナダ・サイバーセンターが 「制御システム」の勧告として扱った一方、 6件の CWE はすべて Web アプリケーションの語彙である。** **分類の境界に落ちる製品ほど、誰も版を把握していない。**
    取るべき行動 **「業務に使っているが、情報システム部門が買っていないソフトウェア」 を洗い出す調査を一度行う。** **問い方を「ソフトウェアを教えてください」ではなく **「ブラウザで開いて使っている、工場や現場の画面を挙げてください」 にする**——後者のほうが答えが返る（本記録の助言）。 **洗い出したものに、版と提供元と更新の責任者を記録する。** **責任者が空欄のものが、次に本件と同じ位置に立つ。**
  • ベンダーが「緩和策はない」と書いたとき、対応の選択肢は更新時期の判断だけになる
    **日立産機システムは 「■ Mitigations and Workarounds / None」と明記している（原文英語）。** **対処は V4.0.0 というメジャー版への更新のみである。** **4件の CVSS 9.8 が未認証（`PR:N`）で成立し、 2件は秘密がコードに埋まっているため、 利用者側の設定で直せる部分が無い**（本記録の整理）。 **「様子を見る」は、未認証で成立する4件を開けたままにすることと 同義になる。**
    取るべき行動 **脆弱性の受け入れ判断の様式に 「ベンダーが緩和策を提示しているか／していないと明記しているか／ 触れていないか」の3択の欄を設ける。** **「緩和策なし」と明記されたものは、 評点の高さと関係なく更新の計画を即座に立てる対象として扱う** ——**評点は成立のしやすさを示すが、 「他に打つ手があるか」は示さない**（本記録の助言）。 **メジャー版への更新は互換性の確認と停止時間を伴うため、 生産の計画と合わせる段取りに1週間以上かかることを前提に動く。**
  • 製造業では「情報が盗まれる」より「誤った情報が印字されて出荷される」のほうが重い
    **HCSS が印字するのは賞味期限・ロット番号・製造日である。** **9.8 の4件は「ファイルを作成・変更・削除できる」 「管理 API を認証なしで呼べる」 「管理者の Bearer トークンを作れる」—— 印字内容そのものを握れる形である**（本記録の読み）。 **ラインが止まったことは分かる。 印字が間違っていたことは、出荷後まで分からない。** **しかも回収の範囲を決めるための情報（ロット番号）が、 汚染された側にある**（本記録の評価。日立産機システムは 影響の形を述べていない）。
    取るべき行動 **事業影響の評価に「データの完全性が壊れたときに、 壊れた事実を外部の記録から検証できるか」の観点を加える。** **具体的には、印字・ラベル・出荷記録について、 HCSS とは別系統（上位の生産管理・出荷の記録・取引先側の受領記録）で 突き合わせられるかを確認する。** **突き合わせられないなら、 「全量回収」以外の選択肢が無いことを経営として認識しておく** （本記録の助言）。
  • 日本のベンダーの製品を、海外の政府機関の勧告で知る経路が実際にある
    **本記録の起点は、カナダ・サイバーセンターが2026年10月2日に出した 制御システム向け勧告 AV26-993 である。** **日立産機システムの公表は9月30日であり、 一次資料は最初から存在していた。** **しかし、その公表に気づく仕組みを持っていない組織は、 海外の勧告が流通するまで知らないことになる**（本記録の整理）。
    取るべき行動 **自社が使っている製品のベンダーについて、 脆弱性情報の公表ページを個別に購読する** （日立の場合は `hitachi.com/products/it/software/security/`）。 **あわせて、JVN・CISA の ICS 勧告・カナダ・サイバーセンターのような 「中継する側」も見る**—— **一次資料に気づけなかったときの二重化になる。** **購読の対象は、上の「設備の付属ソフト」の洗い出しの結果から作る** （本記録の助言）。
セキュリティ技術者への示唆
  • 到達範囲を「設定の読み合わせ」ではなく「実際の通信」で確かめる
    **4件の CVSS 9.8 はすべて `AV:N`（ネットワーク経由）かつ `PR:N`（権限不要）である。** **成立の分かれ目は「HCSS のサーバに届くか」だけである。** **一方で、インターネットから到達できる HCSS がどれだけあるかの 集計は存在せず、自社で確かめるほかない**（本記録の確認）。 **工場のネットワークは、図面と実態が合わないことが多い** （本記録の評価）。
    取るべき行動 **HCSS のサーバの IP とポートを特定し、 ①インターネット側 ②事務系ネットワーク ③工場ネットワークの それぞれから実際に接続を試す。** **届いた経路を記録し、業務に必要なものだけ残す。** **絞る前に「誰がどの端末からどの画面を使っているか」を 列挙しておく**——**HCSS は PC・タブレット・スマートフォンから 使える設計であり、絞り方を誤ると印字の運用が止まる。**
  • 「秘密がコードの中にある」脆弱性は、更新だけでは終わらない
    **CVE-2026-82827 はハードコードされた JWT 署名鍵（CWE-321）、 CVE-2026-82829 は隠しアカウントまたはハードコードされた 認証情報（CWE-912）である。** **更新は「新しい版の鍵の作り」を直すが、 脆弱な版が運用されていた期間に発行された Bearer トークンや、 その期間に露出した可能性のあるアカウントは別の作業である。** **CVE-2026-82826（平文通信）の期間に流れた認証情報も同じ。** **これは本記録の読みであり、日立産機システムはこの指示を 出していない。**
    取るべき行動 **脆弱性対応の完了条件に 「この脆弱性によって作られた・漏れた可能性がある秘密を 作り直したか」の欄を加える。** **判定の目安は CWE の分類である**—— **CWE-321・CWE-798・CWE-259・CWE-912・CWE-319・CWE-522 が 付いているものは、更新のあとに秘密の作り直しが要る。** **あわせて「どのトークン・どのアカウントが存在するか」を 列挙できる状態にしておく**—— **列挙できなければ、作り直す対象を決められない。**
  • CVSS のベクタが同一の脆弱性が複数並んだら、「個別のパッチでは済まない」と読む
    **本件の 9.8 の4件は、ベクタまで完全に同一である （`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`）。** **性質は4つとも違う**——パスの扱い・認証の有無・ 鍵の管理・隠された入口。 **しかし到達の条件が同じであり、 「どれか1つを塞いでも残る3つで同じ場所に着く」構造である。** **対処が V4.0.0 というメジャー版への更新であることも、 この読みを支える**（本記録の推定。 日立産機システムは理由を述べていない）。
    取るべき行動 **脆弱性の一覧を受け取ったら、 評点の高さではなくベクタの重複で並べ替える。** **同一ベクタが3件以上並んでいたら、 「個別のパッチで順次対応」ではなく 「到達範囲の遮断」を先に打つ判断に切り替える** ——**ベンダーの修正を待つあいだ、 そこが唯一効く場所である**（本記録の助言）。
  • 産業用の「Web アプリケーション」には、Web アプリケーションの検査を当てる
    **本件の6件の CWE は、 パストラバーサル（CWE-35）・認証の欠落（CWE-306）・ 平文通信（CWE-319）・ハードコードされた鍵（CWE-321）・ 不適切な認可（CWE-863）・隠された機能（CWE-912）である。** **すべて Web アプリケーションの検査で見つかる種類のものである** （本記録の整理）。 **HCSS はクライアント／サーバ構成でブラウザから使い、 JWT で認証する——姿は普通の Web アプリケーションである。**
    取るべき行動 **工場・現場で使っている「ブラウザから開く画面」を列挙し、 OT の資産としてではなく Web アプリケーションとして扱う。** **自社で検査できないものは、 調達の段階で「脆弱性検査の実施と結果の提示」を要件に入れる。** **少なくとも「認証なしで呼べる API があるか」 「秘密がクライアント側・設定ファイル・バイナリに埋まっていないか」 の2点は、受け入れ時に確認する項目として定型化する。**
