INC-2026-0315OpenAI が「蒸留」工作を遮断

OpenAI は2026年9月30日、同社のモデルから「保護された推論（protected reasoning）」を 抽出しようとする協調的なキャンペーンを検知・遮断したと公表した。活動は2026年7月1日に 少量で始まり、7月24〜25日に4,000人を超える利用者から16,000件の要求へ急増、 7月28日までに15,000人を超える利用者のクラスタとして完全に遮断された。 手口は「ある会話で得た暗号化された推論を別の会話へ持ち込み、モデルに復号・転記させる」ことで、 OpenAI は「暗号化を破られたのでもデータベースを侵害されたのでもなく、 保存された利用者の会話に直接アクセスされたのでもない」と明記している。 帰属については「すべての実行者が単一の主体に由来するかは不明」としながら、 中核のクラスタを Kimi の開発元である中国 Moonshot AI の関係者（individuals associated with Moonshot AI）に帰した。技術的証拠は公表していない

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**正規のアカウントから正規の API・UI を使い、 保護された推論を可視な形で再現させるプロンプトのパターンを大量に投入した。** **特徴的なのは、ある会話で得た暗号化された推論を 別の会話へ持ち込み、モデルに復号・転記させる形である。** **暗号化の破り・データベースの侵害・保存された会話への直接のアクセスは いずれも行われていない（OpenAI の明記）。** **活動は7月1日に少量で始まり、7月24〜25日に 4,000を超えるアカウントから16,000件の要求へ急増し、 7月28日までに15,000を超えるアカウントのクラスタとして遮断された。**

  1. 1. 偵察確認済
    **抽出が成立する経路を探す段階。** **OpenAI は「活動は時間とともに進化し、 敵対的蒸留が、層をなす適応的な防御を必要とする より広いセキュリティの課題であることを裏づけた」と述べている（原文英語） ——試行しながら形を変えていたことを示す。** **同時期に独立の研究者が、同じ攻撃の種類について 「暗号化された推論の記録がセッション・利用者・モデルをまたいで 互換である」構造を文書化し、責任ある開示を行っている。** **どちらが先だったかは公表されていない。**
    根拠: OpenAI 公表文「What we observed」節／arXiv:2608.09867 のアブストラクト
  2. 2. 初期侵入確認済
    **多数のアカウントを用意し、サービスの正規の経路から接続する。** **OpenAI は対応として「不正なアカウントを禁止または制限し、 サインアップと基盤の管理を強化し、 関連するネットワークの監視を拡大した」と述べている（原文英語） ——不正なアカウントが相当数あったことを含意する。** **また「関連する活動が第三者のサービスを通って動いていた場合、 その提供者と協力してアカウントを特定・遮断した」としており、 中継を経た接続も含まれていた。**
    根拠: OpenAI 公表文「How we responded」節
  3. 3. 収集確認済
    **保護された推論が可視な形で再現されるよう、 モデルとの対話を操作する。** **OpenAI の表現では 「保護された推論が要求者に見える形で再現されるように モデルとの対話を操作した」（原文英語）。** **7月24〜25日に、関連する抽出パターンを用いた 16,000件の要求が4,000を超えるアカウントから行われた。** **これらの数値は試行であり、成功数ではない（脚注1）。**
    根拠: OpenAI 公表文「What we observed」節および脚注1
  4. 4. 検知回避確認済
    **保護を迂回する形として、暗号化された推論を別の文脈へ移す。** **「ある会話から暗号化された推論をコピーし、 別の会話のモデルに対して、隠された推論の内容を 復号し転記するよう求める」（原文英語）。** **研究の側では、強いモデルの暗号化された推論を 同じ事業者のより弱い・保護の薄いモデルへ入れることで、 強いモデルを直接破らずに中身を平文で出させる形が示されている （arXiv:2608.09867 のアブストラクト）。** **第三者のサービスを経由する迂回も確認されている。**
    根拠: OpenAI 公表文「What we observed」「How we responded」節／arXiv:2608.09867 のアブストラクト
  5. 5. 持ち出し推定
    **再現された推論を要求者の側で取得する。** **OpenAI は、取得された推論の量・成功した抽出の件数を 公表していない。** **対策として「推論を露出させうるストリーミング出力を 検知して保留する検査を追加した」と述べており（原文英語）、 出力の経路に検査を入れる形で止めに回っている。**
    根拠: OpenAI 公表文「How we responded」節
  6. 6. 影響（暗号化・破壊・改ざん）推定
    **抽出された推論が別のモデルの学習に使われれば、 元のモデルの安全策を伴わない能力の複製が成立する。** **OpenAI の記述（原文英語）—— 「敵対的蒸留は、安全と国家安全保障の risk をもたらす。 抽出された推論は、元のモデルの利用者向け出力に適用されていた 安全策を保持しないまま、別のモデルの学習に使われうる。 規模が大きくなれば、蒸留は、安全への同等の投資を必要とせずに 先端能力の移転を加速させうる」。** **ただし、実際に学習に使われたかは公表されていない （「使われうる」という可能性の表現である）。**
    根拠: OpenAI 公表文「Why this matters」節

侵入はされていない——破られたのは暗号ではなく「推論の記録の持ち運びやすさ」だった概観

この事案を読むとき、最初に押さえるべきは「何が起きていないか」です。

OpenAI の公表文は、該当部分を否定形で書いています（原文英語）。

「実行者は当社の暗号化を破っておらず、データベースを侵害しておらず、保存された利用者の会話に直接アクセスしてもいない。そうではなく、彼らはモデルとの対話を操作し、保護された推論が要求者に見える形で再現されるようにした——当社の利用規約に違反する、協調的で規模の大きいやり方で」

つまり、侵害された資産はサーバやデータベースではありません。 破られたのは「保護された推論（protected reasoning）」の保護です。

保護された推論とは何か。OpenAI の説明はこうです（原文英語）。

「保護された推論とは、モデルが課題を解き進めるための内部の記録である。それを抽出することは、最終的な回答から伏せられている情報を明らかにし、他者がモデルの能力を再現する助けになりうる」

本記録が本件を「不正アクセス」ではなく「脅威・攻撃キャンペーン（threat-campaign）」として記録したのは、この構造によります。 正規の経路から、正規の手順で、規約に反する目的で、大量に使われた。 防御の設計の観点では、これは侵入の検知とは別の問題です ——認証も認可も通っている利用が、量とパターンによって攻撃になる。

手口は「別の会話に持ち込んで復号させる」ことだった原因・手口

OpenAI が挙げた手口は、1文で説明できます（原文英語）。

「当社は、実行者が保護された推論を新しい方法で抽出しようとするのを見た。ある会話から暗号化された推論をコピーし、別の会話のモデルに対して、隠された推論の内容を復号し転記するよう求めるというものを含む」

ここで効いているのは、鍵の強度ではなく、「暗号化された推論の記録が、どの文脈でも通用してしまう」という性質です。

OpenAI が対策として挙げた一文が、裏側からこれを確認しています（原文英語）。

「当社は、他の利用者の暗号化された推論を既に所持している者が、それを再生して中身を復元できた経路を閉じた」

「他の利用者の（another user's）」という語が重要です。 自分の推論を自分で復号するのではなく、他人の暗号化された推論を手元で再生できた、ということです。

同じ構造を、独立の研究者が先に文書化していました。 OpenAI が「独立したセキュリティ研究者」としてリンクした論文"Stealing Reasoning Traces from Proprietary LLM APIs"（arXiv:2608.09867・2026年8月10日投稿）のアブストラクトは、クライアント側に返される暗号化された推論の記録がセッション・利用者・モデルをまたいで互換である、という構造上の欠陥を示したとしています。 強いモデルの暗号化された推論を、同じ事業者のより弱い・保護の薄いモデルに入れると、強いモデルを直接破ることなく、弱いモデルが中身を平文で出力してしまう、という筋です。

OpenAI の表現を借りれば、これは同社固有の問題ではありません（原文英語）。

「この操作は OpenAI のモデルに固有の脆弱性ではなく、敵対的蒸留に対する集団的な防御を強めるために、Frontier Model Forum を通じて業界のパートナーとこの件についての情報を共有した」

本記録が事案の型を「脅威・攻撃キャンペーン」とし、あわせて「脆弱性」の性格も併記したのは、「キャンペーンとしての事案」と「設計上の性質としての論点」の両方が同時に成立しているためです。

日本の組織にとっての論点は、自社が「抽出される側」にも「踏み台にされる側」にもなりうること評価・解釈

この事案は、一見すると「大手 AI 事業者どうしの争い」です。 日本の組織に当てはまる点を、3つに整理します（以下はいずれも本記録の評価です）。

1つ目。LLM を自社サービスに組み込んでいる組織は、同じ種類の抽出の対象になります。 本件で狙われたのは「保護された推論」ですが、構造は「正規の API を、規約に反する目的で、大量に使う」ことです。 自社が独自に調整したモデル、プロンプトに埋め込んだ業務知識、社内文書を参照する仕組み——いずれも「出力を大量に集めて複製する」対象になりえます。 これは侵入の検知では見えません。 認証は通っており、1本1本の要求は正常です。

2つ目。「暗号化されているから安全」が成り立たない場合があります。 本件で再生されたのは、暗号化されたままの推論の記録です。 暗号文のまま持ち運べて、別の場所で復号させられるなら、暗号化は保護になっていません。 自社でセッションの状態・思考の過程・中間結果をクライアントに返す設計をしている場合、「その値は、別のセッション・別の利用者・別のモデルで通用しないか」を確認する必要があります。 これは本件から最も直接に移せる教訓です。

3つ目。自社の環境が、他者の抽出の足場に使われる可能性があります。 OpenAI は「関連する活動が第三者のサービスを通って動いていた場合、その提供者と協力してアカウントを特定・遮断した」と述べています（原文英語）。 つまり、経路の途中にいた事業者が巻き込まれています。 自社が AI の API を再販・中継している、あるいは自社のクラウド環境から外部の AI サービスへ大量の要求が出ている場合、気づかないうちにこの図の中に入っていることがあります。

    取るべき行動 **自社サービスがクライアントへ返している「不透明な値」を列挙する** ——**セッションの状態、暗号化された文脈、 署名付きのトークン、キャッシュの鍵など。** **それぞれについて「別の利用者・別のセッション・別の環境で 使ったらどうなるか」を試す**（本記録の助言）。 **動いてしまうものがあれば、それが本件と同じ構造である。** **設計の方針として「暗号化された値には必ず 所有者と有効期限を結び付ける」を明文化する。**
  • 自社が、他者の抽出の「踏み台」として使われる側になりうる
    **OpenAI は「関連する活動が第三者のサービスを通って動いていた場合、 その提供者と協力してアカウントを特定・遮断した」と 述べている（原文英語）。** **経路の途中にいた事業者が巻き込まれている**（本記録の整理）。 **AI の API を再販・中継している組織、 自社のクラウド環境から外部の AI サービスへ 大量の要求が出ている組織は、 気づかないうちにこの図に入っていることがある。** **加えて、Anthropic の報告について二次情報は、 代理のアカウント群の所在にシンガポールと日本が多かったと 伝えている**（本記録は未検証。discrepancies を参照）。
    取るべき行動 **自社から外部の AI サービスへ出ている通信の量と宛先を、 月次で見る仕組みを作る。** **とくに①開発・検証の環境からの大量の要求 ②再販・中継している経路③共用の API キーの3つを見る。** **併せて、外部の AI 事業者から 「貴社の環境からこういう活動が出ている」という連絡が来たときの 受け口と初動の手順を決めておく**（本記録の助言） ——**本件では OpenAI が第三者の提供者に連絡を取っている。**
  • 対策を終えてから公表する順序は、業界共通の構造的な問題では正しいことがある
    **OpenAI は遮断（7月28日までに）から公表（9月30日）まで 約2か月を置き、その間に調査・緩和・研究者と業界との共有を 済ませたと自ら説明している（原文英語）。** **この順序が成り立つのは、同社が 「この操作は OpenAI のモデルに固有の脆弱性ではない」と 認めているためである** ——**公表が先行すれば、対策を持たない他社が晒される**（本記録の評価）。 **そのうえで、業界の枠組み（Frontier Model Forum）への 非公開の共有で時間差を埋めている。**
    取るべき行動 **自社の公表の方針に「業界共通の構造的な問題の場合」の 分岐を入れる。** **①自社固有か業界共通かの判定②業界共通なら どの枠組み・どの相手に先に伝えるか ③公表までに何を終えている必要があるか、を事前に決めておく** （本記録の助言）。 **判定の根拠と共有の記録を残すこと** ——**「隠していた」と「順序を選んだ」を後から区別できるのは 記録だけである。**
セキュリティ技術者への示唆
  • クライアントへ返す「状態」は、所有者に結び付けないと別の文脈で再生される
    **本件の中核はこれである。** **OpenAI は対策として 「利用者・ワークスペース・組織・モデルファミリをまたいで、 隠された推論の保護を強化した」 「他の利用者の暗号化された推論を既に所持している者が、 それを再生して中身を復元できた経路を閉じた」と 述べている（原文英語）。** **対策の内容が、問題の形をそのまま示している** ——**保護が「利用者・ワークスペース・組織・モデル」の どの軸にも結び付いていなかった**（本記録の整理）。
    取るべき行動 **自社がクライアントへ返す不透明な値（セッションの状態・ 暗号化された文脈・キャッシュの参照）に、 所有者の識別子と有効期限を埋め、受領時に検証する。** **検証は「復号できるか」ではなく 「この要求者のものか」を見る**（本記録の助言）。 **試験として、利用者 A の値を利用者 B の要求に差し替えて 投げるケースを回帰試験に入れる。** **通ってしまえば本件と同じ構造である。**
  • 検知は入力だけでなく出力の側にも置く——ストリーミングでは「保留して検査」が要る
    **OpenAI は 「推論を露出させうるストリーミング出力を検知して保留する検査を 追加した」と述べている（原文英語）。** **入力（プロンプト）の検査だけでは、 「復号して転記せよ」のような無害な見た目の指示を止められない** （本記録の評価）。 **一方、出力の側なら「内部の推論が混ざっている」ことを 内容として判定できる。** **ストリーミングで返す設計では、 返し始めてから止めるのが難しいため、 検査の位置が設計の制約になる。**
    取るべき行動 **自社の LLM の応答経路に出力側の検査を1段入れる。** **検査の対象は①システムプロンプトの断片 ②内部の思考・中間の推論③秘匿すべき識別子・鍵の形。** **ストリーミングを使っている場合は、 一定の単位で保留してから流す作りに変える**（本記録の助言） ——**返し切ってからの検知では止められない。** **検査に掛かった応答はログに残し、 プロンプトの形を指紋として蓄積する。**
  • 量の検知は「量が出るまで鳴らない」——パターン単位で数える
    **本件の時系列を見ると、7月1日から少量で始まり、 7月24〜25日の急増（16,000件・4,000超のアカウント）で 「high-volume spikes」として浮かび、 その後の調査で15,000超のクラスタが特定されている。** **つまり、約3週間の少量期がある**（本記録の整理）。 **1アカウントあたりの量で閾値を引くと、 4,000アカウントに分散された活動は1つも閾値に届かない。**
    取るべき行動 **プロンプトを正規化して指紋化し、 「同じ指紋の合計」をアカウントをまたいで数える検知を作る。** **正規化は、固有名詞・数値・空白を落として テンプレートの骨格だけを残す程度でよい**（本記録の助言）。 **アカウント単位の閾値と、指紋単位の閾値の両方を持つこと。** **あわせて、アカウントの作成の時期・接続元・支払いの手段での 相関を定期に走らせる。**
  • 「返す必要のない内部状態」を返さないのが、最も確実な対策である
    **本件で狙われた保護された推論は、 最終的な回答には含まれない内部の記録である。** **OpenAI の説明では 「それを抽出することは、最終的な回答から伏せられている情報を 明らかにし、他者がモデルの能力を再現する助けになりうる」 （原文英語）。** **暗号化して返す設計は、 「返す」という前提を保ったまま保護を足す形であり、 本件ではその保護が文脈をまたいで通用してしまった** （本記録の評価）。 **返していなければ、再生される対象が存在しない。**
    取るべき行動 **自社の応答に含めている内部状態を棚卸しし、 「なぜクライアントに返す必要があるのか」を1件ずつ書く。** **書けないものを削る**（本記録の助言）。 **継続のために必要なら、値そのものではなく サーバ側に保持した状態への参照（不透明な ID）だけを返し、 中身はサーバから出さない設計に寄せる。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 自社サービスがクライアントへ「暗号化された状態」や「不透明な値」を返しており、それが利用者・セッション・組織に結び付いているかを答えられない
データの保持□ LLM の応答に内部の思考・中間の推論・システムプロンプトの断片が含まれており、出力の側での検査が無い
運用・監視□ 自社の AI サービスに対する「正規の大量利用」を、パターン単位（アカウントをまたいだ合計）で数える仕組みが無い
委託・第三者部品□ 外部の AI サービスへの自社からの通信量・宛先を把握しておらず、API キーが共用されている／再販・中継の経路がある
体制・契約□ 自社サービスの利用規約に「出力を他のモデルの学習に用いない」旨の条項が無い、または違反時の措置の手順が決まっていない
体制・契約□ 業界共通の構造的な問題を見つけたときに「どこへ先に伝え、いつ公表するか」の方針が無い
