Apache HTTP Server の開発チームが2026年10月1日に 2.4.69 を公開し、20件の CVE に対処した。 開発チーム自身の深刻度評価は「中（moderate）」5件と「低（low）」15件で、 最上位の「クリティカル」「重要」は1件も付いていない。 一方で CVE レコードに記載された CVSS 3.1 の基本値は、 mod_http2 の解放済みメモリ使用（CVE-2026-57941）が 9.8（CRITICAL）、 WebDAV の mod_dav_fs の整数オーバーフロー（CVE-2026-93546）が 8.8 であり、 ベンダーのラベルと点数が逆向きに見える更新になっている。 報道が「CVSS 9.8」と結びつけた mod_vhost_alias の CVE-2026-63292 は、 CVE レコードでは 7.5（可用性のみ）で、成立には VirtualDocumentRoot と 既定より大きい LimitRequestFieldSize という構成の条件が付く

初報: 2026年10月1日 最終更新: 2026年10月4日

Apache HTTP Server の開発チームは、現地時間2026年10月1日に 2.4.69 を公開し、20件の CVE に対処した。 Apache 自身の深刻度評価は「中（moderate）」5件・「低（low）」15件で、4段階の上2つ（クリティカル・重要）は付いていない。

ところが CVE レコードに記載された CVSS 3.1 の基本値は、同じ「中」の中で大きく散らばっている。最も高いのは mod_http2 の解放済みメモリ使用 CVE-2026-57941 の 9.8（CRITICAL・無認証で到達）、次が WebDAV の mod_dav_fs の整数オーバーフロー CVE-2026-93546 の 8.8（書き込み権限のある認証済み利用者）である。「ベンダーが低く評価しているから急がない」という判断は、この更新では成立しない。

報道（Security NEXT）は見出しで「CVSS 9.8」と mod_vhost_alias を並べたが、本記録が CVE レコードを確認したところ mod_vhost_alias の CVE-2026-63292 は 7.5 で、影響は可用性のみ（C:N/I:N/A:H）だった。 9.8 が付いているのは mod_http2 の CVE-2026-57941 である。さらに CVE-2026-63292 の成立条件は、VirtualDocumentRoot にホスト名のフォーマット指定子を使っていて、かつ LimitRequestFieldSize を既定より大きくしている構成で、8192 バイトを超える Host ヘッダを受け取ったときに限られる。

更新以外の回避策・悪用の有無・侵害の確認手順は、いずれも公表されていない。読者側の作業は、版の確認（2.4.69 未満か）→ 有効なモジュールの確認 → 構成条件の確認の順で優先度を絞り込むことになる。

「クリティカルは無い」と「CVSS 9.8」は、どちらも同じ更新の説明である概観

2.4.69 が対処したのは20件。 Apache 自身の深刻度ラベルは「中」5件・「低」15件で、上位2段階（クリティカル・重要）は1件も付いていない。

一方、CVE レコードの CVSS 3.1 基本値は次のように散らばっている（本記録が「中」の5件を確認）。

  • CVE-2026-57941（mod_http2 / 解放済みメモリ使用）— 9.8 CRITICAL。AV:N/AC:L/PR:N/UI:N/C:H/I:H/A:H
  • CVE-2026-93546（mod_dav_fs / 整数オーバーフロー）— 8.8。PR:L（書き込み権限のある WebDAV 利用者）
  • CVE-2026-63292（mod_vhost_alias / スタックオーバーフロー）— 7.5。影響は可用性のみ
  • CVE-2026-59685（Windows の 8.3 形式パス処理 / 境界外書き込み）— 7.5。影響は機密性のみ
  • CVE-2026-42528（mod_dav / 共有ロックのオーバーフロー）— 4.3

同じ「中」の中で 4.3 から 9.8 まで開いている。 Apache の深刻度ラベルは「既定構成での現実的な悪用可能性」を含んだ評価で、CVSS は条件を揃えた機械的な尺度である。どちらかが間違っているのではなく、測っているものが違う。 運用上の結論は単純で、ラベルだけで優先度を決めてはいけないということになる。

無認証で届くのは mod_http2 の 9.8 で、mod_vhost_alias は構成の条件が付く原因・手口

優先度は「有効にしているモジュール」で決まる。

HTTP/2 を有効にしている構成（mod_http2）が最優先である。 CVE-2026-57941 は共有された session->bbtmp の再入により解放済みメモリを使うもので（CWE-416、Apache の一覧では「use-after-free / wild write」）、CVSS ベクタは無認証・利用者操作なし（PR:N/UI:N）で機密性・完全性・可用性すべてに高い影響。 HTTP/2 は多くの公開サーバで既定に近い形で有効になっており、条件が少ない。

WebDAV を提供している構成（mod_dav / mod_dav_fs）は認証の壁がある。 CVE-2026-93546 は多数の XML 名前空間を宣言した PROPPATCH 要求で整数オーバーフローを起こし、ワーカープロセスを落とすだけでなく、ディレクトリのプロパティデータベースを永続的に壊す。書き込み権限を持つ認証済み利用者が前提（PR:L）だが、破壊が「永続的」である点は、再起動で戻らないという意味で重い。

mod_vhost_alias（CVE-2026-63292）は条件が二つ重なる。 CVE レコードの記述は、VirtualDocumentRoot にホスト名のフォーマット指定子を使っていて、かつ LimitRequestFieldSize を既定より大きくしている組み合わせで、8192 バイトを超える Host ヘッダを受けたときにスタックが溢れる、というものである。既定の LimitRequestFieldSize（8190）のままなら、8192 バイトの Host ヘッダはそもそも受け付けられない（本記録の読み）。多数のテナントをホスト名で振り分けるレンタルサーバ的な構成が該当しやすい。

Windows 上の httpd（CVE-2026-59685）は環境で切れる。 8.3 形式のファイル名が展開されて伸びる場合のパス処理で境界外書き込みが起きるもので、Linux 等では該当しない。

回避策も侵害の確認手順も示されておらず、作業は版・モジュール・構成の3段で絞る対策・注意喚起

公表されているのは「2.4.69 へ更新せよ」だけである。回避策・IoC・悪用の有無は、Apache の一覧にも CVE レコードにも書かれていない。

現実的な手順は3段階になる（本記録の整理）。

  1. 版の棚卸し。 httpd -v で 2.4.69 未満かを確認する。ディストリビューションのパッケージ版はバックポートで番号が一致しないことがあるので、配布元の勧告と突き合わせる必要がある（本記録は各ディストリビューションの勧告は確認していない）。
  2. 有効モジュールの確認。 httpd -M で http2_module・dav_module・dav_fs_module・vhost_alias_module が載っているかを見る。使っていないモジュールを落とすこと自体が攻撃面の削減になる。
  3. 構成条件の確認。 VirtualDocumentRoot を使っているか、LimitRequestFieldSize を既定から上げていないか。上げている場合は、上げた理由が今も有効かを確かめる。

更新に伴う副作用も小さくない。 HTTP/2 と WebDAV を含むモジュールの更新であり、リバースプロキシや WebDAV 連携の挙動確認なしに本番へ入れるのは避けるべきである（本記録の評価）。

ベンダーの深刻度ラベルを運用の優先度にそのまま使うと、この更新では判断を誤る評価・解釈

これは本記録の評価である。

この事例の価値は、脆弱性そのものよりも「評価の二重性」にある。多くの組織の脆弱性管理は、ベンダーの深刻度ラベルか CVSS のどちらか一方をトリガーにして期限を決めている。今回はその二つが逆向きに見える。ラベルだけを見る運用では「クリティカル無し」で先送りされ、無認証で到達する 9.8 が後ろに回る。一方 CVSS だけを見る運用では、VirtualDocumentRoot を使っていない組織が関係のない 7.5 に工数を割く。

使えるのは「ベクタ＋構成」である。 PR:N/UI:N の脆弱性は条件が少なく、構成条件つきの脆弱性は自組織の設定を見れば該当・非該当が切れる。「点数の高さ」ではなく「条件の少なさ」で並べると、両方の評価を矛盾なく使える。

もう一つの含意は報道の読み方である。 本件では報道が「CVSS 9.8」という数字と mod_vhost_alias の説明を同じ記事に並べており、点数と CVE の対応を取り違えやすい形になっていた（本記録が CVE レコードで確認して食い違いを特定した）。数字を自社の優先度判断に使うなら、CVE 単位で一次情報へ戻る手間は省けない。

item: 2.4.69 への更新（20件すべてがこの版で解消する）　副作用: **HTTP/2 と WebDAV を含む広い範囲の更新である。** リバースプロキシ構成・WebDAV 連携・`mod_rewrite` の挙動確認なしに本番投入すると、 **脆弱性ではなく互換性で止まる危険がある。** **再起動が必要**なため、停止時間の調整も要る。
item: 使っていないモジュールを無効化する（mod_http2・mod_dav・mod_dav_fs・mod_vhost_alias・mod_proxy_* 等）　副作用: **HTTP/2 を落とすと性能（多重化）が下がる**ため、 公開サイトでは利用者体験に影響しうる。 WebDAV は利用部門が把握していない運用（ファイル共有）に使われていることがあり、 **止める前に利用実態の確認が必要。**
item: `LimitRequestFieldSize` を既定より上げている場合、その必要性を再確認して戻す （CVE-2026-63292 の成立条件を外す方向の措置）　副作用: **大きなヘッダ（長い Cookie・認証トークン・SAML の一部）を使うアプリが 400 系で落ちる可能性がある。** **これは Apache が回避策として示したものではなく、 CVE レコードの条件記述から本記録が導いた措置である。**
item: WebDAV の書き込み権限を持つ利用者を必要最小限に絞る（CVE-2026-93546・42528 の前提を狭める）　副作用: 共同編集・アップロード運用が止まる部署が出る。 **権限の棚卸しには利用部門との調整が必要で、即日では終わらない。**

CISO・経営層への示唆
  • ベンダーの深刻度ラベルと CVSS が食い違う前提で、脆弱性対応の起動条件を設計しておく
    **本件は「クリティカル無し」と「CVSS 9.8」が同じ更新に同居している。** ラベルを起動条件にしている組織では無認証で到達する 9.8 が後回しになり、 CVSS だけを見る組織では該当しない構成に工数を割く。
    取るべき行動 脆弱性管理の規程で、**期限の起動条件を「ベンダーのラベル」単独にしていないかを確認する。** 最低限、**CVSS ベクタの `PR`（必要な権限）と `UI`（利用者操作）が共に不要なものは、 ラベルに関係なく最短の期限に乗せる**規則を入れる。
  • 「悪用の報告が無い」を優先度を下げる根拠に使わない
    Apache も CVE レコードも**悪用について沈黙している。** 沈黙は「安全」ではなく「情報が無い」である。 無認証で到達する欠陥は、報告が出た時点では既に広く試されている。
    取るべき行動 **自組織の脆弱性台帳で「悪用情報なし」を理由に延期した案件を洗い出し、 ベクタが `PR:N/UI:N` のものを例外として前に出す。** KEV 収載を待つ運用になっていないかを点検する。
  • Web サーバの更新は停止時間の調整を伴うため、モジュール単位の必要性判断を先に済ませておく
    20件のうち自組織に当たるのは有効モジュールと構成で決まる。 **普段から「何を有効にしているか」を把握していない組織は、 更新のたびに全件を調べ直すことになり、判断が遅れる。**
    取るべき行動 **サーバごとの有効モジュール一覧（`httpd -M` の出力）を構成管理に取り込み、 脆弱性公表時に突き合わせられる状態にする。** 使っていないモジュールは平時に落としておく。
  • 侵害の確認手順が示されない脆弱性では、ログの遡及可能期間が対応の質を決める
    本件では IoC が公表されていない。 確認できるのは**子プロセスの異常終了のような間接的な痕跡**だけで、 それも保存期間を超えていれば見られない。
    取るべき行動 **Web サーバのエラーログ・アクセスログの保存期間と外部転送の有無を確認する。** 最低でも「更新作業の前後を遡れる」期間（90日が目安）を確保する。
セキュリティ技術者への示唆
  • 優先度は点数ではなく「成立条件の少なさ」で並べる
    CVE-2026-57941 は `PR:N/UI:N` で条件が少なく、 CVE-2026-63292 は `VirtualDocumentRoot` と `LimitRequestFieldSize` の 二重の構成条件が要る。**7.5 と 9.8 の差より、条件の差のほうが実務では大きい。**
    取るべき行動 **自組織の構成に当てはめて、条件が揃っている CVE だけを抽出する。** HTTP/2 が有効なら CVE-2026-57941 を最優先で当て、 `VirtualDocumentRoot` を使っていなければ CVE-2026-63292 の優先度を下げてよい。
  • WebDAV を「社内だから安全」として残している構成を洗い出す
    CVE-2026-93546 は**認証済み利用者がプロパティデータベースを永続的に壊せる**ものである。 WebDAV は目的を終えた後も有効なまま放置されやすく、 **権限を持つ利用者が広いまま残っていることが多い。**
    取るべき行動 `httpd -M` で `dav_module` / `dav_fs_module` を確認し、 **使っていなければ無効化、使っているなら書き込み権限の保有者を棚卸しする。** プロパティデータベースのバックアップ有無も確認する（破壊は永続的である）。
  • `LimitRequestFieldSize` のような「過去に困って上げた値」が攻撃の前提になることを知っておく
    CVE-2026-63292 の成立条件には**既定より大きい `LimitRequestFieldSize`** が含まれる。 既定のままなら 8192 バイトの Host ヘッダは受け付けられない（本記録の読み）。 **一度上げた制限値は理由が忘れられ、戻されないまま残る。**
    取るべき行動 構成ファイルで既定から変更している制限値（`LimitRequest*`・各種タイムアウト）を列挙し、 **変更理由と現在の必要性を記録する。** 不要なら戻す。必要なら「この値が前提になる脆弱性がある」と台帳に注記する。
  • Windows 上の httpd を資産台帳から落とさない
    CVE-2026-59685 は Windows 限定の境界外書き込みである。 **業務パッケージに同梱された httpd や検証機の Windows 版は、 Linux 前提の管理台帳から漏れやすい。**
    取るべき行動 **OS 別に httpd の稼働箱を数え直す。** 同梱された httpd はパッケージ提供元の更新を待つ必要があるため、 提供元への確認を並行して始める。
