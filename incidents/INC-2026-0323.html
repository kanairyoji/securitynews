CrowdStrike は2026年9月15日、npm 経由で配布される JavaScript 製の情報窃取ツール「PhantomRaven」についての分析を公表した。

手口は npm の2つの仕組みを組み合わせたものである。配布されるのは正規のツール名に似せた偽装パッケージ（例 transform-jsbi-to-bigint・sort-imports-es6-autofix）で、中身は Hello, world! 程度の無害なコードしか入っていない。 ただし依存先が通常のパッケージ参照ではなく HTTP の URL として書かれており、導入時に npm が攻撃者の基盤からその「依存パッケージ」を取得する。取得されたものが本体で、preinstall スクリプトとして導入の途中で自動実行される。 この URL 形式の依存は npm のウェブ画面に表示されないため、パッケージのページを見るだけでは気づけない。

盗まれるのは端末の環境情報（OS・アーキテクチャ・ホスト名・内部と外部の IP・作業ディレクトリ・プロセスID・Node.js の版・コマンド行引数・環境変数）と、Git / npm の設定にある利用者名・メールアドレス、そしてGitHub Actions・GitLab CI・Jenkins・CircleCI の環境変数（30項目）である。外部 IP の確認には公開サービス（api64.ipify.org）を使い、収集結果は HTTP の GET（クエリ文字列）と POST（JSON）の両方で送り出す。

CrowdStrike はコードがほぼ確実に LLM 生成であると高い確度で評価している（冗長なコメント・プレースホルダのコード・統計的なトークン分析のパターン）。未完成の WebSocket 経路にはプレースホルダの URL（wss://yourserver.com/socket）が残っており、作者の技術水準は低いとみられる。

最も注目すべきは動機である。 CrowdStrike は、この攻撃者が自作の PhantomRaven で企業の資産を侵害し、その侵害を梃子にして評価の高い脆弱性開示プログラムから報酬を請求していた可能性が高いと評価した。アカウント名の一つは jpdhackerone11 で、攻撃者自身がバグ報告と支払いの管理に HackerOne を使っていると主張している。 つまり、受け取った「脆弱性報告」が実は供給網経由の侵害の結果である、という形が現実に起きている（本記録の読み）。

侵害の目的が「報奨金の請求」であるため、攻撃は脆弱性報告として届きうる概観

技術的には単純な情報窃取ツールだが、動機が従来と違う。

CrowdStrike の評価は、この攻撃者が自作の PhantomRaven で企業の資産を侵害し、その侵害を梃子にして評価の高い脆弱性開示プログラムから報酬を請求していた可能性が高いというものである。攻撃者はバグ報告と支払いの管理に HackerOne を使っていると主張しており、アカウント名の一つ（jpdhackerone11）もそれを参照している。2025年8月には、自ら公開した悪性の npm パッケージで遠隔コード実行を達成したと主張した（CrowdStrike はこの主張を検証できていない）。

ここから出てくる運用上の問題は、受け取り側の判定である（本記録の評価）。「あなたのビルド環境でコードを実行できました」という報告が届いたとき、それは脆弱性の指摘なのか、それ自体が侵害の事実なのか。 PhantomRaven の形では後者である——攻撃者は先に偽装パッケージを置き、CI の環境変数を持ち出し、その結果を報告として提出している。

報奨金制度や脆弱性開示窓口を持つ組織は、報告の受理と同時にインシデント対応の判断が必要になる。 窓口の担当者が「報告」として処理して終われば、持ち出された資格情報は残り続ける。

パッケージのページを見ても分からない——依存先が HTTP の URL で書かれている原因・手口

仕組みは2段である。

第1段は偽装パッケージである。 正規のツール名に似た名前（transform-jsbi-to-bigint・sort-imports-es6-autofix が例として挙がっている）で公開され、中身は Hello, world! 程度の無害なコードだけ。 ここが重要で、パッケージの中身を見ても悪性のコードは無い。

第2段は依存先の書き方である。依存が通常のパッケージ参照ではなく HTTP の URL として書かれており、導入時に npm がその URL から「依存パッケージ」を取得する。返ってくるものが本体（PhantomRaven）で、preinstall スクリプトとして導入の途中で自動実行される。 CrowdStrike はこの形をリモート動的依存（remote dynamic dependency）と呼び、ATT&CK では「埋め込まれたペイロード」（T1027.009）に対応づけている—— URL 形式の依存は npm のウェブ画面に表示されないためである。

防御側にとっての含意は2つある（本記録の評価）。①公開レジストリのページを目で見る確認では検出できない。見るべきはパッケージの中身ではなく、マニフェストとロックファイルにHTTP(S) の URL 形式の依存が入っていないかである。②取得は導入時に起きるので、ビルド環境からの外向き通信が許されていること自体が前提になる。

2026年6月の npm の変更は第2段に効く。依存として取り込まれたパッケージの preinstall は既定で実行されず、版12以降では警告とともに止まり、開発者が明示的に承認したときだけ動く。 ただし「承認」は人の操作であり、ビルドが通らない状況で押されやすい（本記録の評価）。

盗まれるのは端末の情報ではなく、CI/CD の資格情報である被害規模・影響範囲

収集対象は大きく4群である。

  • システム情報 — OS・アーキテクチャ・ホスト名・内部と外部の IP アドレス
  • プロセスと実行環境 — 作業ディレクトリ・プロセスID・Node.js の版・コマンド行引数・環境変数
  • 利用者の識別情報 — Git / npm の設定ファイルにある利用者名とメールアドレス
  • CI/CD の環境変数（30項目） — GitHub Actions・GitLab CI・Jenkins・CircleCI の変数（GITHUB_ACTOR・GITHUB_REPOSITORY・GITHUB_RUN_ID・CI_PROJECT_PATH・JENKINS_URL・CIRCLE_PROJECT_REPONAME・npm_config_registry など）

CrowdStrike は、CI/CD の変数を集めるのはアカウントの資格情報を得ようとしているためとみられると述べている。

外部 IP の確認には公開サービス（api64.ipify.org）への HTTP 要求を使う。その応答の成否に関わらず、収集結果を HTTP の GET（クエリ文字列）とPOST（JSON）の両方で送る。 POST の利用者エージェント文字列は Mozilla/5.0 (Windows NT 10.0; Win64; x64) だけで、ブラウザの種類や版といった通常含まれる要素が欠けている。 未完成の WebSecket 経路（原文では WebSocket）にはwss://yourserver[.]com/socket というプレースホルダが残っており、これは悪性のインフラではないと評価されている。

検知の観点では、この「作りの粗さ」が手がかりになる（本記録の評価）—— 同じデータを GET と POST の両方で送るのは正常な実装ではしない。

LLM 生成であることは、腕の問題ではなく参入障壁の問題として読む評価・解釈

CrowdStrike は、コードがほぼ確実に LLM 生成であると高い確度で評価している。根拠は統計的なトークン分析のパターンと、冗長なコメント・プレースホルダのコードである。ブログに示された構造では、グローバル変数と関数の定義のすべてにコメントが付いており、名前から自明な説明が繰り返されている。 同じデータを HTTP の POST と GET の両方で送り出すという不自然な設計も、生成に由来する説明がつくとされる。

評価として重要なのは次の一文である（CrowdStrike の評価）。「eCrime の攻撃者は AI 生成の道具を自分たちの運用に取り込み続ける可能性が高い。これらの道具は eCrime に参加するための技術的な障壁を下げ、道具の作成を加速させる」（中程度の確度。原文英語）。根拠として、2025年後半から2026年初頭にかけてTRAVELING SPIDER INC の関係者と PUNK SPIDER がAI 生成の PowerShell スクリプトを運用に使ったことが挙げられている。

本記録としての読みを足す。 「作者の技術水準は低い」と「組織にとって危険でない」は別の話である。 PhantomRaven が盗むのは CI/CD の資格情報であり、資格情報が渡った後に何ができるかは、盗んだ側の技量よりも盗まれた側の権限設計で決まる。 粗い道具が増えること自体が、検知の負荷を押し上げる——既知のマルウェア族としての特徴量が乏しく、1回しか使われないコードが増える。

止める場所は3つある——取得・実行・持ち出し対策・注意喚起

CrowdStrike が挙げた推奨は次のとおりである（原文英語）。

  • 私設の npm レジストリの導入を検討する（パッケージの導入を制御・遮断・監視できる）
  • --ignore-scripts を既定にし、信頼できるパッケージにだけ選択的にスクリプト実行を許す
  • npm を最新版に更新し、preinstall・postinstall の実行を既定で制限する
  • 依存の取り違えを狙う攻撃について利用者を教育する
  • 既知の脆弱性と問題の確認に npm audit を使う

本記録として、段ごとに整理し直す。

  1. 取得を止める — 私設レジストリ（あるいはプロキシ）経由に限定し、ビルド環境から公開インターネットへの外向き通信を遮断する。 URL 形式の依存は、外に出られなければ取得できない。
  2. 実行を止める — --ignore-scripts を既定にする。npm を版12以降に上げる。承認（npm install-scripts approve）を誰が押せるかを決めておく。
  3. 持ち出しを止める・気づく — ビルド実行環境からの外向き HTTP を監視し、外部 IP 確認サービスへの接続や未知のドメインへの POST を異常として扱う。
  4. 盗まれても損害を小さくする — CI の秘密情報を長命のトークンから短命の資格情報（OIDC 連携など）へ移す。 ビルドジョブに渡す権限を、そのジョブに必要な範囲へ絞る。

副作用は正直に見ておく。 --ignore-scripts を既定にするとネイティブ拡張のビルドが必要なパッケージが動かなくなる。私設レジストリは運用の手間と、更新の遅れを生む。外向き通信の遮断は依存の取得そのものに影響するため、許可先の管理が必要になる。

初期侵入機会はあったが検知できず

実行検知した
**npm 版12以降では、ここが「警告として見える」段階になった。** **ただし見えることと止まることは別である**（本記録の評価）—— **ビルドが通らない状況では、承認の操作が押されやすい。** **版12より前の npm を使っている環境では、警告すら出ずに実行される。**
侵入を防げたnpm を版12以降へ更新し、導入時スクリプトの既定実行を止める
侵入を防げた`--ignore-scripts` を既定の設定にし、 スクリプト実行が必要なパッケージだけを明示的に許可する

検知できたビルド実行環境の外向き通信の記録を取り、 導入処理中に発生した HTTP 取得先の一覧を残す

**外部 IP 確認サービスへの接続は、実用的な検知点になる**（本記録の評価）—— **ビルド実行環境が自分の外部 IP を調べる必要は、通常の処理ではほとんどない。** **一方で、環境情報の読み取り自体はビルド処理と見分けがつきにくい。**
検知できたビルド実行環境から外部 IP 確認サービスへの接続を遮断・警告対象にする
影響を限定できたビルドの実行を使い捨ての環境（毎回作り直すコンテナ）で行い、 端末固有の情報や永続的な設定を持たせない
認証情報アクセス公表されていない
**CrowdStrike は、この段階で防御側が検知できたかどうかを述べていない。** **環境変数の読み取りは、プロセス内部の操作であって 外部から見える事象を伴わない**（本記録の評価）—— **実際に気づける場所は、この後の送信か、 盗まれたトークンが別の場所から使われたときである。**
影響を限定できたビルドジョブへ渡す秘密情報を、長命のトークンから短命の資格情報 （OIDC による都度発行）へ移す

**公表資料はこの段階の検知について述べていない。** **自動で完結するため、人の操作を待つ段階が無く、介入の余地が小さい** （本記録の評価）。
影響を限定できたビルド実行環境を使い捨てにし、収集されうる情報の範囲を そのジョブに必要なものだけに限る

検知できたビルド中の外向き HTTP 要求の宛先と利用者エージェントを記録し、 未知の宛先への POST を警告対象にする
侵入を防げた依存の取得を事前に済ませた成果物（ベンダリング・キャッシュ）を使い、 ビルド時のネットワーク取得を無くす

  • ビルド実行環境からの外向き通信を許可先一覧に限定する
    **本体の取得も持ち出しも、ビルド環境の外向き HTTP に依存している。** **外に出られなければ、URL 形式の依存は取得できず、収集結果も送れない。**
    取るべき行動 ビルド用のネットワークを分け、**レジストリとアーティファクト保管先だけを許可する。** **外部 IP 確認サービスへの接続と、未知の宛先への POST を警告対象にする。**
  • 不自然な通信の作りを検知の手がかりにする（族名に頼らない）
    PhantomRaven は**同じデータを GET と POST の両方で送り**、 **POST の利用者エージェント文字列が極端に短い。** **LLM 生成ゆえの粗さが、そのまま検知の特徴になる**（本記録の評価）。 一方で**C2 ドメインはパッケージレジストリらしい名前**なので、 名前の見た目では弾けない。
    取るべき行動 ビルド環境の外向き通信について、 **利用者エージェント文字列と宛先の組み合わせを記録し、 同一データの重複送信のような不自然な形を調べられるようにする。** **公表された痕跡（ドメイン・IP・ハッシュ）は、 自組織で悪性を確認していない段階では遮断ではなく調査の起点として使う。**
  • 開発者端末と CI の両方で、Git と npm の設定ファイルの中身を点検する
    PhantomRaven は**Git / npm の設定ファイルから利用者名・メールアドレスを読み、 資格情報も探す**（ATT&CK の T1552.001 に対応づけられている）。 **設定ファイルにトークンを平文で置く運用が残っていると、そのまま持ち出される。**
    取るべき行動 **`.npmrc` や Git の資格情報の保存方法を点検し、 平文のトークンが残っていないかを確認する。** 見つかった場合は失効させ、資格情報ヘルパーや都度発行に切り替える。
