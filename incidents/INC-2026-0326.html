INC-2026-0326Epic が MyChart 修正で開発停止

米電子カルテ最大手 Epic Systems が2026年10月、製品開発のほとんどを約6週間止めて 自社製品のセキュリティ修正に人を振り向けていることが報じられた。 患者が自分の診療情報を見る MyChart の**一部の顧客側設定では、外部の者が患者記録に 到達でき、しかもその参照がソフトウェアのログに残らない**と同社の最高セキュリティ責任者が述べている。 欠陥を見つけたのは Anthropic の攻撃的セキュリティ向けモデル Claude Mythos で、 Epic はこれを Project Glasswing の枠組みで自社システムに当てて試験していた。 CVE 番号・対象版・該当設定・悪用の有無はいずれも公表されていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備設定不備
初報: 2026年10月2日 最終更新: 2026年10月4日

2026年10月2日、TechCrunch（Zack Whittaker）が、米電子カルテ最大手 Epic Systems が製品開発のほとんどを止めて自社製品・自社システムのセキュリティ対応に当たっていると報じた。創業者で最高経営責任者の Judy Faulkner は、同年9月に Modern Healthcare に対し、この停止が「およそ6週間続くとみられる」と述べていた（原文英語）。

止めた理由として報じられている中身は、患者向けポータル MyChart の欠陥である。最高セキュリティ責任者 Stirling Martin は The New York Times に対し、「一部の顧客側の MyChart の構成では、外部の者が患者記録に到達でき、その参照がソフトウェアのログに記録されない」と説明した（原文英語）。記録が気づかれずに改変されうるかどうかは、モデルの検査では判定できなかったとされる。

欠陥を見つけたのは人ではなくモデルである。 Epic は Anthropic の攻撃的セキュリティ向けフロンティアモデル Claude Mythos を自社システムに当てて試験しており、これは Anthropic が2026年4月に公表した Project Glasswing（重要ソフトウェアの脆弱性を見つけるための共同の取り組み）の枠組みで提供されたものと報じられている。

本記録が重く見るのは「ログに残らない」という部分である。到達できたかどうかは設定次第だが、参照の記録が無い製品では、利用している医療機関は「自分のところで実際に見られたか」を後から確かめられない。 Epic は CVE 番号・対象版・該当する設定の条件・悪用の有無を公表しておらず、利用側が自機の該当を判断できる材料は出ていない（2026年10月4日時点）。

製品開発を止めるという判断自体が、この事案のいちばん硬い事実である概観

公表されていることは少ない。 CVE 番号も、対象版も、該当する設定も、修正の提供時期も出ていない。確かなのは次の3点である。

  1. Epic が製品開発のほとんどを止めた。 CEO の Judy Faulkner がModern Healthcare に対し、停止はおよそ6週間続くとみられると述べた。
  2. 止めた理由は MyChart の欠陥である。 最高セキュリティ責任者 Stirling Martin はThe New York Times に対し、一部の顧客側の構成では外部の者が患者記録に到達でき、その参照がソフトウェアのログに記録されないと説明した。
  3. 見つけたのは Anthropic の Claude Mythos である。 Epic は Project Glasswing の枠組みでこのモデルを自社システムに当てて試験していた。

「6週間、ほとんどの開発を止める」は、脆弱性対応としては異例に重い判断である。電子カルテの新機能は顧客の業務計画・認証取得・契約に紐づいており、止めれば売上と顧客計画の両方に跳ね返る。その判断を選んだという事実のほうが、公表されていない技術詳細よりも読者にとって読み取れる情報が多い（本記録の評価）。

「外部から到達できる」より重いのは「参照がログに残らない」である原因・手口

報じられた欠陥は2つの欠落が重なっている。

1つめは認可の欠落である。 一部の構成では、本来その患者記録に権限を持たない外部の者が記録に到達できたとされる。これは設定の組み合わせに依存する。

2つめは監査記録の欠落で、こちらは設定の話ではない。 Martin の説明によれば、その参照はソフトウェアのログに記録されない。 この2つが重なると、利用している医療機関は次のどれも言えなくなる。

  • 自機の構成が該当したのか（該当条件が公表されていない）
  • 実際に参照されたのか（参照がログに残らない）
  • 誰の記録が見られたのか（同上）
  • 記録が改変されていないか（改変の可否が未決）

侵害の有無を判断する材料が、利用側の手元に残らない設計だったということである（本記録の評価）。米国では HIPAA 上の侵害評価が必要になるが、評価の入力になるログが無いという状態そのものが問題になる。

本記録は「悪用は確認されていない」とは書かない。確認する手段が無かったのだから、書けるのは「公表されていない」だけである。

日本の読者が取り出せるのは、モデルで自社を検査したときに何が起きるかである評価・解釈

Epic が使っていない組織にとっても、この事案には持ち帰れる形がある（本記録の整理）。

第一に、検査の担い手が変わり始めている。欠陥を見つけたのは外部研究者でもバグバウンティでもなく、ベンダー自身が自社製品に当てたモデルである。これは「公表の起点が利用者側の被害報告ではなくなる」ことを意味する。従来、製品の欠陥は被害や研究者の報告をきっかけに外へ出た。自社検査が起点になると、出てくる件数が増え、しかも「対象版」「CVE」「修正版」が整う前に経営者の発言として先に外へ出ることがある。本件はまさにその形で、台帳に登録する識別子が無い状態で読者の手元に届いている。

第二に、「開発を止める」という選択肢の見積もりである。自社でも同じ検査をやれば、一度に多数の欠陥が出て、通常の開発計画ではさばけない量になりうる。 そのとき止めるかどうかは技術部門では決められない。検査を始める前に「出てきた場合に誰が止める判断をするか」を決めておく必要がある（本記録の評価）。

第三に、監査記録の有無を調達の確認項目にすることである。本件で読者が最も困るのは、自機で参照があったかどうかを確かめられないことである。これは本件固有の話ではなく、患者ポータル・顧客ポータル一般に当てはまる——自社のポータル製品が「誰がどの顧客の記録を見たか」を記録しているかは、脆弱性が出てから調べることではない。

2026年10月4日時点で、本記録が確認できなかったものを並べておく。

  • Epic 自身の公表文（探したが見つからない。確認できたのは報道への発言のみ）
  • CVE 番号・対象版・修正の提供時期
  • 該当する設定の条件（利用側が自機の該当を判断できない）
  • 実際に参照されたかどうか（ログに残らないため、そもそも判定できない構造）
  • 顧客への通知の有無と内容
  • 記録の改変の可否（モデルの検査では判定できなかったとされる）
  • Anthropic 側の公表文（本記録が推定した URL は 404 を返した）

これらは「問題がない」ことを意味しない。とくに参照の有無については、確認手段が欠けていたことが報じられた欠陥の中身である。

CISO・経営層への示唆
  • 「悪用の報告が無い」を安全の根拠にする前に、記録が取れているかを確かめる
    **本件で報じられた欠陥の中身は「外部から到達できる」ことに加えて 「その参照がログに残らない」ことである。** ログが無い製品では、**痕跡が無いことは起きなかったことの証明にならない。** それでも社内報告では「悪用の報告はありません」と書かれがちである。
    取るべき行動 インシデント報告の様式に**「判定に使ったログの種類と保存期間」の欄を作る。** 欄が埋まらない事案は**「悪用なし」ではなく「判定不能」と書かせる。**
  • ベンダーが公表文を出さず経営者の発言だけが外に出る事案を、台帳に載せる経路を作る
    **本件には CVE も対象版も修正版も無い。** 識別子で管理している脆弱性台帳には**登録する欄が無い**ため、 「報道で知っているが台帳には無い」状態になり、**追跡が止まる。**
    取るべき行動 台帳に**「識別子なし・ベンダー未公表」の区分**を作り、 ①照会日と照会先、②暫定の代替策、③次に確認する期日を必須項目にする。 **本件を最初の1件として登録する。**
  • モデルによる自社検査を始める前に、「出てきた場合に止める判断をする人」を決める
    **Epic は製品開発のほとんどを約6週間止めた。** 検査の担い手がモデルになると、**人手の検査では出なかった量の欠陥が一度に出る。** **止めるかどうかは事業計画と顧客契約に跳ね返るため、技術部門では決められない。**
    取るべき行動 検査の導入計画に**「停止基準」と「判断者」**を書く。 基準は件数ではなく**性質**で書く（例: 顧客データに外部から到達でき、かつ監査記録が無いもの）。
  • 患者・顧客ポータルの監査記録を、調達と契約の確認項目に入れる
    **「誰がどの顧客の記録を見たか」が記録されるかは、 脆弱性が出てから調べることではない。** 本件では、利用側の医療機関が**自機で何が起きたかを言えない**状態に置かれた。
    取るべき行動 次の調達仕様に**参照ログの取得範囲・保存期間・利用側が取り出せる形式**を要件として明記する。 既存製品については、**取れていないものの一覧**を作って残存リスクとして登録する。
セキュリティ技術者への示唆
  • 認可の検査と監査記録の検査を、別々の確認項目として持つ
    **本件は「到達できる」と「記録に残らない」が重なった事案である。** 到達の検査（権限のない利用者で他人の記録に届くか）だけを行うと、 **届かなかった場合に監査記録の欠落が見逃される。**
    取るべき行動 ポータルの受け入れ試験に**「参照が監査ログに1件ずつ残るか」**という項目を独立して置く。 **成功した参照・失敗した参照の両方を確認する。**
  • 「一部の設定で成立する」脆弱性に備えて、既定値からの変更点を一覧にしておく
    報じられた成立条件は**「一部の顧客側の構成」**である。 **自機がどの設定を既定値から変えたかを把握していないと、 条件が公表されたときに照合できない。**
    取るべき行動 ポータル製品の設定を**既定値との差分として出力し、構成管理に入れる。** 差分が出ない製品は、**設定画面の内容を定期的に記録して差分を取る。**
  • ベンダー側のログが無い前提で、自分の層で何が見えるかを確かめる
    **参照の成功が製品のログに残らなくても、 前段の WAF・ロードバランサ・認証基盤・ネットワーク記録には痕跡が残ることがある。** **ベンダーのログだけに依存した監視は、ベンダーの実装の欠落をそのまま引き受ける。**
    取るべき行動 ポータルの前段で取れている記録（到達元・認証結果・応答の大きさ）を棚卸しし、 **「製品のログが無い場合に何が言えるか」を文章で書き出しておく。**
  • モデルを使った自社検査の結果を、再現手順と到達条件の形で残す
    **本件では「何がどう成立するのか」が外に出ていないため、 利用側は自機の該当を判断できない。** 自社で検査する側に立ったとき、**同じ形の報告をすると利用部門が動けない。**
    取るべき行動 検査結果には**①成立する設定の条件、②必要な権限、③再現手順、④監査ログに残るか**を 必ず書かせる。**「危険」だけの報告は受け付けない。**
