INC-2026-0327公開 GitHub に有効な資格情報54万件

Truffle Security が2026年10月2日、公開 GitHub リポジトリ 2億2,455万件・ 約584億件のファイルを走査して見つけた資格情報のうち、 **54万3,699件が2026年7月の試験時点でなお有効だった**と公表した。 公開されていた期間の中央値は784日、最古のものは2009年6月の設定ファイルにあった。 有効だった資格情報の **51.8% は GitHub の既定の Push Protection が そもそも遮らない種類**（データベース接続文字列・Google API キー・秘密鍵）で、 **36.8%（19万9,843件）は Push Protection が既定で有効になった2024年2月29日より後に 公開されたもの**だった

業界横断事象・統計（被害者が不特定多数、統計の推移が主）意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）作業ミス・誤操作設計・実装上の不備
初報: 2026年10月2日 最終更新: 2026年10月4日

Truffle Security は2026年10月2日、公開 GitHub リポジトリに置かれたまま現在も認証に成功する資格情報を 54万3,699件 見つけたと公表した。走査の対象は公開リポジトリ 2億2,455万3,295件・エントリ 584億6,746万8,698件で、素材は AI 学習用データセット The Stack v3（クロールは2025年8月7日締め）である。有効性の試験は2026年7月27〜28日に、各資格情報の発行元へ実際に問い合わせる形で行われた。

数字の重みは件数ではなく時間にある。 公開されていた期間の中央値は784日（約2年2か月）。90パーセンタイルは6.3年、最古のものは2009年6月13日付の Erlang の設定ファイルに書かれたデータベースの資格情報で、それが2026年7月の試験でも通った。

「仕組みを入れたのに減っていない」という点がこの調査の要点である。 GitHub は2024年2月29日に Push Protection（資格情報を含む push を既定で止める機能）を公開リポジトリで既定有効にした。それでも有効だった 54万3,699件のうち 19万9,843件（36.8%）は、その日より後に公開されたものである。理由は遮る対象の偏りで、有効だった資格情報の 51.8% は既定の Push Protection がそもそも対象にしない種類（データベース接続文字列・Google API キー・秘密鍵）だった。

種類ごとの「生存率」の差も大きい。 報告によればPostgreSQL の接続 URI は 88%、Google Cloud のサービスアカウントは 54% が有効だった一方、GitHub のトークンは 0.36%、npm のトークンは 0.001% にとどまる。発行元が自動で失効させる仕組みを持っている種類は生き残らず、持たない種類だけが何年も通り続けるという構図である（本記録の読み）。

件数より重いのは、公開期間の中央値が784日あることである概観

この調査の数字は3層に分けて読む。

第1層・量。 公開リポジトリ 2億2,455万件・584億件のエントリを走査し、構造から資格情報と判別できた候補 494万1,427件のうち、発行元に問い合わせて実際に通ったものが 54万3,699件。出現箇所はフォークを含め 110万3,438件。

第2層・時間。 公開されていた期間の中央値は784日（約2年2か月）、90パーセンタイルは6.3年、最古は2009年6月13日の設定ファイルである。件数は「漏れた量」を示すが、784日は「気づかれていない」ことを示す。報告の題が「誰も失効させていない」であるのは、ここを指している。

第3層・遮る側の偏り。 GitHub は2024年2月29日に Push Protection を公開リポジトリで既定有効にした。それでも有効だったもののうち 19万9,843件（36.8%）はその日より後に公開されている。理由は単純で、有効だった資格情報の 51.8% は既定設定が対象にしない種類（データベース接続文字列・Google API キー・秘密鍵）だからである。

読者が自社で確かめるべきことは、この第3層に対応する。「push の保護を有効にしてある」ことは、自社で使っている資格情報の種類が保護対象に入っていることを意味しない。

生存率の差は漏れやすさではなく、失効させる主体がいるかどうかで決まっている評価・解釈

報告が示す種類別の有効率の差が大きい。

種類 有効率
PostgreSQL の接続 URI 88%
Google Cloud のサービスアカウント 54%
GitHub のトークン 0.36%
npm のトークン 0.001%

この差を「開発者の不注意の差」として読むと間違える（本記録の読み）。GitHub と npm のトークンがほぼ生き残っていないのは、発行元が公開を検知して自動で無効化する仕組みを持っているからである。一方データベースの接続文字列には、失効させる主体が存在しない——自社のサーバの資格情報を、誰かが代わりに無効化してくれることはない。

結論はこうなる。自社が管理する資格情報ほど生き残る。外部 SaaS のトークンは発行元が守ってくれるが、データベース・内部 API・踏み台の鍵・証明書の秘密鍵は、自社が気づいて自社で回すしかない。 784日という中央値は、その「自社で回す」が動いていないことの実測値である。

もう一つの含意は、検出範囲の設計である。秘密情報の検出を入れるとき、発行元が自動失効させてくれる種類ばかりを高精度で検出しても、残存リスクはほとんど下がらない。 優先すべきは、失効の主体が自社しかいない種類（接続文字列・秘密鍵・自社発行のトークン）である。

「有効だった」は「悪用された」ではないが、「安全だった」でもない未確定事項

この調査が測っていないことを明確にしておく。

  • 悪用の有無は測っていない。 有効性の試験であって、アクセス記録の調査ではない。「54万件が悪用された」とは言えない。
  • 現在の実数ではない。 素材の The Stack v3 のクロールは2025年8月7日締めで、直近約1年分が入っていない。54万3,699件は下限である。
  • 当事者への通知の有無が分からない。 報告に通知手順の記述を確認できなかった。
  • 国別・業種別の内訳が無い。 日本の組織がどれだけ含まれるかは分からない。

一方で、「悪用の証拠が無い」ことを安全の根拠にもできない。公開リポジトリは攻撃者側も同じ方法で走査できる対象であり、784日という露出期間は、見つけられなかったと考えるには長い（本記録の評価）。自社の資格情報が含まれていたかどうかは、自社で調べるほかない。

遮る仕組みを入れた後も3件に1件は新たに公開されている対策・注意喚起

読者が今日できることを、効く順に並べる（本記録の整理）。

  1. 自組織の公開リポジトリと、公開に転じた過去のリポジトリを棚卸しする。私設だったものを公開にした履歴、アーカイブしたまま公開のままのもの、個人アカウントに置かれた業務コードが抜けやすい。
  2. 履歴（コミット）まで走査する。 現在のファイルから消しても、コミット履歴とフォークには残る。本調査の出現箇所 110万3,438件に対して一意の資格情報 54万3,699件という比は、同じ鍵が複数箇所に散っていることを示している。
  3. 検出の対象を「自社が失効させるしかない種類」から設計する。データベース接続文字列・秘密鍵・内部 API のトークンは、既定の push 保護では止まらず、発行元も助けてくれない。
  4. 見つけた資格情報は「消す」のではなく「回す」。ファイルを消してもコミットに残る。やるべきは失効と再発行であり、その順序を手順書に書く（先に新しい鍵を配り、切り替えてから旧鍵を失効させる）。
  5. 公開の瞬間を止める層を足す。 Push Protection の既定に加え、組織設定で対象パターンを広げる／CI で push 前に走査する。本調査の 36.8% が示すのは、既定だけでは止まっていないという事実である。

副作用も書いておく。 検出パターンを広げると誤検知で push が止まり、開発の手が止まる。 除外リストの運用を決めずに広げると、「全部除外」に行き着いて何も守らなくなる（本記録の評価）。また失効作業は本番停止のリスクを伴う——どのサービスがその資格情報を使っているかが分からないまま失効させると障害になる。

緩和策
item: 公開リポジトリ（過去に公開に転じたもの・アーカイブ済みのものを含む）の棚卸し　副作用: **個人アカウントに置かれた業務コードを洗い出す過程で、 従業員の個人アカウントの調査という扱いの難しい論点に触れる。** 就業規則・プライバシーの整理を先に済ませないと止まる。
item: コミット履歴とフォークを含めた資格情報の走査　副作用: **履歴の書き換え（force push）は共同作業者の手元を壊す。** **走査と失効を先に行い、履歴の掃除は別の作業として計画するほうが安全** （本記録の評価。消すことより回すことが先）。
item: 検出対象を「自社が失効させるしかない種類」（接続文字列・秘密鍵・内部トークン）から設計する　副作用: **パターンを広げると誤検知が増え、push が止まって開発の手が止まる。** 除外の運用（誰が承認し、期限をいつにするか）を決めずに広げると、 **除外だらけになって機能しなくなる。**
item: 見つけた資格情報は失効・再発行する（ファイルから消すだけで終わりにしない）　副作用: **どのサービスがその資格情報を使っているか分からないまま失効させると本番障害になる。** **新しい鍵を配って切り替えたあとに旧鍵を失効させる**順序を手順書に書く必要がある。
item: push の前段（CI・クライアント側フック）に走査を足し、プラットフォームの既定に依存しない　副作用: CI の実行時間が伸び、開発者の体験が落ちる。 **クライアント側フックは回避できるため、CI 側の強制と二重にしないと効かない。**
indicators
item: 自組織の名義（および従業員の個人名義）で公開されているリポジトリの一覧　補足: **最初に作るのはこれ。** **私設から公開に転じた履歴とアーカイブ済みの公開リポジトリが抜けやすい。**
item: 自社が発行している資格情報の種類の一覧と、それぞれの「失効させる主体」　補足: **本調査の生存率の差がそのまま効く観点。** **外部 SaaS のトークンは発行元が自動失効させることがあるが、 自社のデータベース・内部 API の資格情報は誰も止めてくれない。**
item: データベース・内部 API への接続元の記録（どの資格情報がどこから使われたか）　補足: **悪用の有無を後から言えるかどうかはここで決まる。** 記録が無い場合、**「有効な資格情報が公開されていた」以上のことは言えない。**
item: Push Protection の組織設定で、どのパターンが対象になっているかの一覧　補足: **「有効にしてある」ことと「自社の種類が対象である」ことは別。** 本調査の 51.8% は既定の対象外の種類だった。
item: 資格情報を失効させた記録（いつ・どの鍵を・誰が）　補足: **中央値784日という数字の裏返し。** **失効の記録が無い組織は、公開された鍵がまだ通るかどうかを知らない。**

対応の評価

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「秘密情報を push させない仕組みを入れた」を対策完了として報告させない
    **GitHub の Push Protection が公開リポジトリで既定有効になった後も、 有効な資格情報 54万3,699件のうち 19万9,843件（36.8%）が新たに公開されている。** **理由は、有効だったものの 51.8% が既定設定の対象外の種類だったことである。**
    取るべき行動 報告様式に**「保護対象のパターン一覧」と「自社が使う資格情報の種類の一覧」の 突き合わせ結果**を添付させる。 **一覧が無いなら、それを作ることが対策の第一歩である。**
  • 資格情報の失効を「見つけたとき」ではなく「定期的に回す」運用に変える
    **本調査の核は件数ではなく、公開期間の中央値が784日あることである。** **90パーセンタイルは6.3年、最古は2009年のものが2026年に通った。** **気づく仕組みに頼る運用は、気づかなかった場合に何年も放置される。**
    取るべき行動 **自社が失効の主体である資格情報**（データベース・内部 API・秘密鍵）について、 **有効期限と定期更新の期日を台帳の必須項目にする。** 期限の無い鍵が何本あるかを、まず数える。
  • 委託先・退職者・個人名義のリポジトリを調査範囲に含める契約・規程を用意する
    **公開リポジトリに業務の資格情報が入る経路は、自社の管理下にないことが多い**—— **委託先の開発者、退職した従業員の個人アカウント、検証用に作った私物のリポジトリ。** **調査の権限が無いと、棚卸しがそこで止まる。**
    取るべき行動 委託契約に**成果物・検証コードの公開禁止と調査協力**を入れ、 就業規則に**業務コードの個人アカウントへの保存の扱い**を明記する。 退職手続きに**発行済み資格情報の失効**を入れる。
  • 「悪用の証拠が無い」と「有効な鍵が公開されていた」を区別して報告する
    **本調査は有効性を測ったもので、悪用の有無は測っていない。** **自社で同じことが起きたときも、接続元の記録が無ければ悪用の有無は言えない。** **両者を混ぜると、残存リスクが過小に報告される。**
    取るべき行動 報告様式に**「悪用の判定に使える記録があるか」**の欄を作る。 **無い場合は「悪用なし」ではなく「判定不能」と書かせる。**
セキュリティ技術者への示唆
  • 検出の優先順位を「失効させる主体が自社しかいない種類」から付ける
    **有効率の差が大きい**——PostgreSQL の接続 URI は 88%、 Google Cloud のサービスアカウントは 54% が有効だったのに対し、 **GitHub のトークンは 0.36%、npm は 0.001% である。** **差を作っているのは発行元の自動失効の有無である**（本記録の読み）。
    取るべき行動 秘密情報の検出ルールを**接続文字列・秘密鍵・自社発行トークンから整備する。** 外部 SaaS のトークンは**発行元の自動失効が効く前提で優先度を下げてよい** （ただし自動失効の有無をサービスごとに確認する）。
  • 「ファイルから消した」で終わらせず、失効と再発行をセットの手順にする
    **出現箇所 110万3,438件に対して一意の資格情報は 54万3,699件**—— 同じ鍵がフォークと履歴に散っている。 **消しても他の場所に残り、履歴からは取り出せる。**
    取るべき行動 手順書を**「①新しい鍵を発行して配布 → ②切り替えを確認 → ③旧鍵を失効 → ④ファイル・履歴の掃除」**の順に書く。 **③を飛ばした対応は対応ではない**と明記する。
  • コミット履歴とフォークを走査対象に含める
    **現在のファイルだけを見る走査では、過去に置かれて消された鍵が見えない。** **本調査の最古の例は2009年のファイルのものである。**
    取るべき行動 走査を**全履歴（全ブランチ・タグ）**に対して回す設定にし、 **フォーク元・フォーク先の存在を確認する。** 結果は「現存するか」ではなく「通るか」で判定する。
  • 資格情報が実際に使われているかを、接続元の記録で見えるようにする
    **公開された鍵が通るかどうかは発行元に聞けば分かるが、 使われたかどうかは自社の記録しか根拠にならない。** **データベースのように接続記録を取っていない資産では、悪用の有無を言えない。**
    取るべき行動 データベース・内部 API の**接続元（IP・利用した資格情報の識別子）の記録**を取り、 **想定外の接続元が検出できる形にする。** 記録が取れない資産は一覧にして残存リスクに登録する。

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
