INC-2026-0329D-Link DIR-822A に満点の脆弱性

D-Link は2026年9月18日、無線ルータ DIR-822A（ファームウェア A_101）の脆弱性2件を アドバイザリ SAP10516 として公表した（9月21日更新）。 CVE-2026-86296 は DHCP の処理部（`udhcpcd/serverpacket.c` の `strcpy`）における スタックベースのバッファオーバーフローで、**認証も利用者の操作も不要・CVSS v3.1 と v4.0 の いずれも 10.0（満点）**。CVE-2026-86510 は L2TP の制御メッセージ解析部 （`tunnel_set_params`）の領域外書き込みで v3.1 が 9.9・v4.0 が 9.4。 **2件とも実証コード（PoC）が公開済みで、修正ファームウェアは示されていない。** D-Link は台湾の報道に対し、本機種はシンガポール専売であり台湾の利用者に影響はないと答えた

初報: 2026年9月18日 最終更新: 2026年10月4日

D-Link は2026年9月18日、無線ルータ DIR-822A の脆弱性2件をアドバイザリ SAP10516 として公表し、9月21日に更新した。 対象はファームウェア A_101、ハードウェアの版は確認中、販売地域は「Non-US」と記載されている。

1件目の CVE-2026-86296 は、CVSS v3.1 と v4.0 のいずれも 10.0（満点）である。 DHCP の処理部（udhcpcd/serverpacket.c）で strcpy が使われており、スタック上の領域を超えて書き込める。認証は不要、利用者の操作も不要で、実証コードが公開されている。

2件目の CVE-2026-86510 は、L2TP の制御メッセージを解析する tunnel_set_params での領域外書き込みで、CVSS は v3.1 が 9.9・v4.0 が 9.4。成立には低い権限が必要とされ、こちらも実証コードが公開されている。

2件に共通して、修正ファームウェアは示されていない。アドバイザリは調査中とし、製品の終息（EOL）の扱いも「調査中」としている。示されている措置は①インターネットに直接さらさない、②遠隔管理を制限する、③ファイアウォール・ネットワークのアクセス制御で管理画面への到達を信頼できる機器に限る、④地域のサポートサイトで更新を確認するという運用上の回避策だけである。

影響範囲については当事者の説明と資料の記載がずれている。台湾の iThome の報道によれば、D-Link は本機種はシンガポール専売で台湾では販売しておらず、台湾の利用者に影響はない。修正ファームウェアはシンガポール法人が出すと答えたとされる。一方アドバイザリ本文の記載は「Non-US」「地域の範囲は確認中」までで、「シンガポール専売」は確認できていない（本記録が2026年10月4日に取得した範囲）。

本記録がこの事案を扱う理由は、台数の多さではない。 満点（10.0）の脆弱性に実証コードが公開済みで、修正が出ておらず、製品の終息の扱いさえ決まっていないという状態が、家庭用・小規模事業所向けのネットワーク機器では繰り返し起きる形だからである（本記録の評価）。

DHCP の処理部が満点になる理由は、到達の前提が低いことにある原因・手口

CVE-2026-86296 が 10.0 になっているのは、影響の大きさだけが理由ではない。 認証が不要（PR:N）で、利用者の操作も不要（UI:N）という到達の前提の低さが効いている（本記録の読み。ベクタ文字列そのものは取得できていない）。

箇所が DHCP の処理部である点も重い。 udhcpcd/serverpacket.c はDHCP の応答パケットを組み立てる処理であり、ルータが LAN 側の機器に対して常時提供している機能である。DHCP は「つながった機器に無条件で応じる」前提のサービスで、認証という概念がそもそも無い。そこに strcpy（長さを確かめずに写す関数）が使われているため、過大な入力を与えればスタック上の領域を超えて書き込める。

CVE-2026-86510 は L2TP の制御メッセージ解析部（tunnel_set_params）である。 こちらは低い権限が必要とされており、到達の前提が一段高い。ただし点数は v3.1 で 9.9 であり、低いとは言えない。

本記録が強調するのは、この2件が「古典的な形」であることである。 入力の長さを確かめずに固定長の領域へ写すという誤りは、静的解析で検出できる種類に属する。組込み機器のネットワーク処理部にその検査が通っていないことを示している（本記録の評価。D-Link はそう説明していない）。

修正が無い機器では、対策は「ルータの外側」に移る対策・注意喚起

アドバイザリが示している措置は4つで、いずれも運用上の回避策である。

  1. 機器をインターネットに直接さらさない。
  2. 遠隔管理（WAN 側からの管理画面へのアクセス）を制限する。
  3. ファイアウォール・ネットワークのアクセス制御で、管理画面に到達できる機器と利用者を信頼できるものに限る。
  4. 地域のサポートサイトで更新の有無を確認する。

ただし、CVE-2026-86296 については、この回避策が効く範囲に限界がある（本記録の評価）。DHCP の処理部は LAN 側に向けた機能である。インターネットからの露出を止めても、同じネットワークに入れた機器からは届く。 家庭・小規模事業所では「LAN に入れた機器」の信頼度が低い——来客の端末、持ち込みの機器、無線に接続した個人の端末が同じ区画にいる。

したがって、修正が出ないこの機器に対して本記録が示す手は次の2つになる。

  • 交換を前提に計画する。 EOL の扱いが「調査中」である以上、修正を待つ計画は期限を置けない。 期限の無い待機は放置と同じである（本記録の評価）。
  • 交換までの間、信頼できない端末を同じ区画に入れない。ゲスト用のネットワークを分離し、分離できない機器では無線のパスフレーズの共有をやめる。

副作用も書いておく。 家庭用・小規模事業所向けの機器では、ネットワークの分離や管理画面の到達制限を行う担当者がいないことが普通である。 「設定で回避する」という案は、実際には実行されない前提で考えるべきである（本記録の評価）。だから交換の判断が要る。

「自国では売っていない」という説明は、利用者の確認を代替しない評価・解釈

影響範囲についての説明が、資料と当事者の回答でずれている。

  • アドバイザリ本文: 販売地域は「Non-US」、地域の範囲は確認中、ハードウェアの版も確認中。
  • 台湾の報道が伝える D-Link の回答: 本機種はシンガポール専売で台湾では販売しておらず、台湾の利用者に影響はない。修正ファームウェアはシンガポール法人が出す。

本記録は後者を一次資料で確認できていない（iThome の該当記事は 403 で取得できず、アドバイザリ本文に「シンガポール専売」の記載を確認できなかった）。

ここから取り出せる実務上の論点は、並行輸入と中古の存在である（本記録の評価）。「その国で売っていない」ことは「その国に無い」ことを意味しない。通販での個人輸入、海外拠点から持ち帰った機器、中古で流通した機器は販売地域の説明の外側にある。 また、拠点を複数の国に持つ組織では、本社の調達リストに無い機器が現地で買われていることがある。

したがって確認の手順は、「販売地域の説明を読む」ではなく「自組織の機器一覧に DIR-822A が無いことを確かめる」である。 一覧が無い組織では、その一覧を作ることが本件の対応になる。

CISO・経営層への示唆
  • 修正が無く終息の判断も出ていない機器は、「待機」ではなく「交換の計画」として扱う
    **本件は CVSS 10.0・実証コード公開済み・修正ファームウェアなし・EOL の扱いも調査中** という組み合わせである。 **待つ計画には期限を置けない。** **期限の無い待機は放置と同じ結果になる**（本記録の評価）。
    取るべき行動 脆弱性管理の台帳に**「修正が提供されていない」区分**を持ち、 **代替策・受容の承認者・交換の判断期限**を必須項目にする。 **本件のように EOL の扱いが未定の案件は、 「ベンダーの回答期限」を自分の側で切る**（例: 30日で回答が無ければ交換）。
  • 「自国では販売していない」というベンダーの説明を、自組織の確認の代わりにしない
    **D-Link は台湾の報道に「シンガポール専売で台湾の利用者に影響はない」と答えたとされる が、アドバイザリ本文の記載は「Non-US・地域は確認中」である。** **販売地域の説明は、並行輸入・中古・海外拠点からの持ち込みをカバーしない。**
    取るべき行動 ネットワーク機器の台帳に**購入経路（国内正規・海外拠点・個人持ち込み・中古）**の列を足す。 **拠点がある国ごとに現地調達の一覧を取り寄せる。**
  • 在宅勤務・小規模拠点のルータを資産管理の対象に入れる
    **本件の対象は家庭用・小規模事業所向けの無線ルータである。** **この層の機器は資産台帳から外れていることが多く、 修正が出ないまま何年も使われる。** **「設定で回避する」案も、担当者がいないため実行されない**（本記録の評価）。
    取るべき行動 在宅勤務・小規模拠点で使う機器を**会社支給の機種に限定するか、 少なくとも機種とファームウェア版の申告を求める。** **支給機については交換の予算を年度計画に入れる。**
  • 実証コードが公開済みの脆弱性は、優先度の軸を「点数」から「到達の前提」に切り替える
    **本件は2件とも実証コードが公開済みで、 一方は認証も利用者の操作も不要である。** **点数（10.0 と 9.9）の差より、 「誰が到達できるか」（LAN 側の任意の機器か／権限が要るか）の差のほうが 対策の設計に効く。**
    取るべき行動 優先度付けの基準に**①実証コードの公開状況、②必要な権限、③到達経路（WAN／LAN）**を 独立した列として入れる。 **点数順の一覧だけで報告しない。**
セキュリティ技術者への示唆
  • LAN 側に向いた脆弱性には「インターネットにさらさない」が効かないことを明示する
    **CVE-2026-86296 は DHCP の応答を組み立てる処理部の問題であり、 これは LAN 側の機器に向けて常時提供されている機能である。** **アドバイザリの回避策（露出の排除・遠隔管理の制限）は WAN 側からの到達を前提にしており、LAN 側からの到達は止まらない。**
    取るべき行動 回避策を評価するとき、**脆弱性の箇所が WAN 側のサービスか LAN 側のサービスかを 必ず書き分ける。** **LAN 側のものには、区画の分離と 「誰を同じ区画に入れるか」の統制を別に用意する。**
  • DHCP・DNS のように「認証のないサービス」の実装を、露出面として数える
    **DHCP は接続してきた機器に無条件で応じる前提のサービスで、 認証という概念が無い。** **そこに境界検査の欠落があると、認証を前提にした防御がすべて迂回される。**
    取るべき行動 機器の棚卸しで**LAN 側に開いているサービス（DHCP・DNS・UPnP・mDNS）を列挙し、 それぞれの脆弱性情報を追う対象に入れる。** **管理画面だけを見ていると見落とす。**
  • ベンダーのアドバイザリに改訂履歴が無い場合は、確認日と内容を自分の側で記録する
    **SAP10516 は2026年9月18日公表・9月21日更新だが、 何が変わったかはアドバイザリ上では分からない。** **後から「いつ影響範囲が変わったのか」を言えない。**
    取るべき行動 アドバイザリを確認したら、**確認日・そのときの記載内容（対象版・修正の有無・ 回避策）を自分の記録に残す。** **差分が出たときに気づける形にする。**
  • バッファオーバーフローの試行は「機器の調子が悪い」として現れることを前提に監視する
    **失敗した攻撃の試行は、組込み機器では再起動や応答停止として表に出る** （本記録の推定）。 **家庭用機器では記録が残らないため、利用者からは不調としか見えない。**
    取るべき行動 業務で使う小規模拠点の機器については、 **死活監視と再起動の記録を外部（監視サーバ）で取る。** **「最近よく切れる」という申告を、設定の問題として片付けない。**
