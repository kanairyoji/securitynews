INC-2026-0330HFS の認証回避、公開翌日に悪用

Rejetto HFS（HTTP File Server）の認証回避の欠陥 CVE-2026-61500 について、 2026年9月30日に Horizon3.ai が技術解説を公開した**翌日**、悪用が観測された—— VulnCheck のおとり（canary）は2026年10月1日の夜に悪用を検知し、 **中国の1つの IP アドレスから、米国と日本にある実際に脆弱な host が狙われていた**。 欠陥の中身は、**セッション Cookie の署名鍵を `Math.random()` から作っており、 しかも同じ乱数生成器の出力を未認証の client に漏らしていた**こと—— V8 の `xorshift128+` は反転可能なため、攻撃者は数回のログイン応答から内部状態を復元して 署名鍵を割り出し、**管理者のセッション Cookie を偽造して完全な管理者権限と 遠隔コード実行に到達できる**。発見したのは人ではなく Anthropic の攻撃的セキュリティ向け モデル **Claude Mythos**（Project Glasswing）で、**Mythos / Glasswing 由来の CVE で 実地の悪用が確認されたのはこれが2件目**である。 **重要な点は、修正が2026年7月13日の v3.2.1 で既に出ていたことである**—— 公開された技術解説が引火したのは、**79日前に直っていた欠陥を当てていない インターネット上の host** だった

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備脆弱性の放置
初報: 2026年9月30日 最終更新: 2026年10月4日

2026年9月30日（水）、Horizon3.ai の研究者 Zach Hanley が、Rejetto HFS（HTTP File Server）の認証回避の欠陥を技術解説として公開しました。識別子は CVE-2026-61500。管理者のセッション Cookie を偽造でき、完全な管理者権限と遠隔コード実行に到達します。

翌日の2026年10月1日（木）の夜、悪用が観測されました。 VulnCheck の研究者 Patrick Garrity は LinkedIn に「今晩、Rejetto HFS の CVE-2026-61500 の悪用を検知しはじめた」と投稿し、「我々のおとり（canary）が、米国にある実際に脆弱な host を狙う中国の行為者を検知した」（原文英語）と述べました。同氏が The Register に語ったところでは、この夜の活動は中国の1つの IP から発しており、米国と日本にある脆弱なサーバを狙っていました。翌日の金曜（10月2日）には米国の2つの IP（173.239.211[.]248 と173.239.211[.]249。同一のサブネットで、プロキシとみられる）から4件が観測されています。

欠陥の機構は、2つの弱点が噛み合ったものです。 HFS は利用者の認証に使うセッション Cookie を、Math.random() で作ったランダム値を署名鍵として Koa（Node.js のウェブフレームワーク）に渡し、keygrip で署名させていました。攻撃者が署名鍵を割り出せれば、有効なセッション Cookie を偽造できます。これは Math.random() が安全な疑似乱数生成器であれば成り立ちません。ところが V8 の Math.random() が使う xorshift128+ は完全に反転可能で、しかもアプリケーション側が同じ乱数生成器の生の出力を別の経路で漏らしていました（client が受け取る Set-Cookie にそれが載っていた）。Mythos は、漏れている値から Microsoft の SMT ソルバ Z3 を使って内部状態（種）を復元できると判断しました。Hanley は「暗号上の欠陥を突いて実際のアプリケーションの認証を回避するためにSMT ソルバがこう使われたのを、我々の研究者は見た覚えがない」と書いています。

発見したのは人ではなくモデルです。 Horizon3.ai は2026年7月にAnthropic の Project Glasswing に参加して以来、攻撃的セキュリティ向けモデルClaude Mythos を自社の脆弱性研究に使っており、「多くの重大な脆弱性を見つけてきた」としています。Garrity の集計では、Mythos と Project Glasswing 由来のCVE は2026年10月2日時点で286件あり、そのうち実地で悪用されたのは本件より前に1件だけでした——本件は2件目です。

ただし、本記録が最も重く見るのはここではありません。 修正版 v3.2.1 は2026年7月13日に公開されていました。 Rejetto 自身のリリースノートは「これまでのすべての版で複数のセキュリティ脆弱性が見つかり、攻撃者が HFS の管理者権限を得られる可能性がある」として、Hanley と「Claude および Anthropic Research との共同」に謝意を記しています。つまり 9月30日の技術解説は、79日前に直っていた欠陥の解説でした。10月1日に狙われたのは、その79日間に当てていなかった host です。 本件は「ゼロデイの悪用」ではなく「公開された解説が、放置された修正に引火した」事案として読むべきです（本記録の判断）。

ここから読めることは1つです。攻撃者が待っていたのは欠陥ではなく、作り方の説明でした。修正が出た7月13日の時点で、差分を読んで機構を復元することは原理的には可能でした。しかし実際に悪用が始まったのは、暗号上の間違いの連鎖（弱い乱数と出力の漏えい）と、Z3 を使った状態復元という手順が公開された翌日です。公開が変えたのは欠陥の有無ではなく、攻撃の費用です（本記録の評価）。

日本にとっての位置づけ——VulnCheck のおとりは日本にある脆弱な host が狙われたことを観測しています。ただし侵害された組織があるかは公表されていません。 HFS は資産台帳に載りにくい種類のソフトウェアであり、「報告が無いこと」は「無事であること」を意味しません（本記録の読み）。

弱い乱数と出力の漏えいが同じ製品の中で噛み合うと、署名鍵は計算できる原因・手口出典 [1] [3]

Horizon3.ai の技術解説にもとづく機構です（本記録の作成者が本文を確認）。

  1. 署名鍵が乱数任せだった——HFS のコードではCOOKIE_SIGN_KEYS がどこにも設定されておらず、keys=[randomId(30)] として Math.random() に落ちていました。この値が Koa（Node.js のウェブフレームワーク）に渡され、keygrip がすべてのセッション Cookie をその鍵で署名します。
  2. その乱数は反転できた——V8 の Math.random() が使うxorshift128+ は暗号用途向けではなく、出力から内部状態を逆算できます。
  3. 出力が外に漏れていた——アプリケーションは別の経路でMath.random() の生の出力を client に渡していました（client が受け取る Set-Cookie にそれが載る）。
  4. 状態を解く——Mythos は、漏れた値からMicrosoft の SMT ソルバ Z3 を使って内部状態（種）を復元できると判断しました。
  5. 鍵が分かれば Cookie を偽造できる——署名鍵が割れるので、管理者のセッション Cookie を作れます。結果は完全な管理者権限と遠隔コード実行です。

1つだけなら攻撃にならない点が重要です。弱い乱数を使っていても、出力が外に出ていなければ状態は解けません。逆に乱数の出力が漏れていても、それが鍵に使われていなければ害はありません。Hanley の説明もそこを指しています—— 「印象的なのは、Mythos が安全でない疑似乱数生成器を単独で指摘しただけでなく、アプリケーションが別のコード経路から生の Math.random() の出力を漏らしていることを同時に見つけ、その2つを連鎖として認識し、その漏えいが状態復元を可能にするのにちょうど必要な観測を生むと判断したことだ」（原文英語）。

本記録の評価として、ここが設計レビューの実務に効きます。単体の指摘（「Math.random() を使うな」）は静的解析でも出ます。見つけにくいのは組み合わせです。「この値はどこから来て、どこへ出ていくか」を2つの経路にまたがって追う作業は、人のレビューでは工数の壁に当たりやすい。モデルが得意なのはまさにそこだったという読み方ができます。

当てるべき版は v3.2.1 以降だが、探すべきは「台帳に無いサーバ」である対策・注意喚起出典 [1] [2] [3]

対処そのものは単純です。

  • Rejetto HFS を v3.2.1 以降へ更新する（本件と、同時に直された他のセキュリティ上の欠陥に対して）。本記録の確認時点の最新安定版は v3.3.4（2026年9月30日公開）です。
  • インターネットへの露出をやめる（到達できなければ成立しません）。

難しいのは、どこで動いているかを知ることです（本記録の判断）。HFS がよく置かれる場所は、たいていこういう所です。

  • 取引先に大きなファイルを渡すために、部門が一時的に立てたもの
  • 検証用に立てて、そのまま残っているもの
  • 個人の判断で入れたもの（ソフトウェアの購買記録に残らない）

つまり、資産管理台帳とも、脆弱性スキャンの対象リストともずれた場所にあります。 そして HFS はオープンソースの個人開発であり、「ベンダーからの通知」が来ません。 公表を見ている人が組織内にいないまま、インターネットに面して動き続ける——これが本件の実務上の形です。

したがって、取るべき手は更新作業ではなく探索です。

  1. 外から見える自組織の資産を、外から数える（保有 IP レンジと、クラウドの一時的な公開端点を含める）。HFS は既定で HTTP の応答に製品名が出るため、外部からの観測で見つけられる種類のソフトウェアです。
  2. 見つかったものに、持ち主を割り当てる——本件の更新は数分の作業ですが、持ち主が分からない資産は更新されません。
  3. 「ファイルを外へ渡す」業務に、組織として用意した手段を与える。禁止だけでは、同じものがまた立ちます（本記録の判断）。

なお、更新しただけでは侵害の有無は分かりません。管理者 Cookie を偽造された場合、攻撃者は正規の管理者として振る舞います。本記録が確認した資料には、侵害を見分けるための痕跡（ログの行・設置されるファイル）は示されていません。最低限の手当ては、①管理画面のアクセスログで見覚えのない操作を探す、②設定の変更履歴を確認する、③更新後にセッションと管理者資格情報を入れ替えることです（本記録の整理。供給元がそう案内しているわけではありません）。

モデルが見つけた欠陥は、解説と実証コードを連れて来る（本記録の評価）評価・解釈出典 [1] [3]

本件で新しいのは、欠陥の性質ではなく、欠陥が世に出るときの形です。

Garrity の集計では、Mythos / Project Glasswing 由来の CVE は286件（2026年10月2日時点）で、実地の悪用が確認されたのは本件を含めて2件です。比率としては小さい。しかし本件が示したのは、モデルが見つけた欠陥は「実際に動く実証コード」とともに公開されうるということです。Horizon3.ai は Mythos が実証コードを作り、任意のコマンドの実行まで実演したと書いており、The Register によれば手順を示す動画も公開されています。

防御側が使える時間は、公開の設計で決まります。本件では、修正が79日前に出ていたという点が救いでした。当てていれば、10月1日の到達は何も起こしません。逆に言えば、修正が出ていない状態で同じ水準の解説が出た場合、防御側に時間は残りません（本記録の評価）。

日本の CISO にとっての含意は2つです（本記録の判断）。

  1. 「パッチが出た」と「当たっている」の差が、これまでより高くつく。本件の79日は、攻撃の費用が下がるまでの猶予でした。同じ猶予が次もあるとは限りません。
  2. 自組織が「モデルによる脆弱性探索」を導入する場合も、同じ問題が起きる。見つけた欠陥の扱い（供給元への通知、公表の時期、実証コードの保管）に方針が無いと、自社の検査結果が攻撃の材料になりえます。

なお本記録は、同じ Project Glasswing の枠組みで見つかった欠陥の事案としてINC-2026-0326（Epic Systems が MyChart の欠陥修正のために製品開発を約6週間止めた件）を記録しています。あちらは CVE 番号も対象版も公表されず、利用側が該否を判定できませんでした。 本件は識別子と修正版があり、やるべきことがはっきりしています。 モデルが見つけること自体より、見つけたものをどう公表するかで利用側の対処可能性が決まる——2件を並べると、そこが共通の論点として残ります。

分かっていないこと——侵害の有無・帰属・公式の CVSS未確定事項出典 [1] [2] [3]

本記録が確認できていないことを明示します。

  • 日本で侵害された組織があるか——観測されているのは「日本の脆弱な host が狙われた」ところまでです。被害の公表はありません。
  • 攻撃者の帰属——最初の発信元は中国の1 IP、翌日は米国の2 IP で、後者はプロキシとみられると観測者自身が述べています。主体の特定は行われていません。
  • 公式の CVSS 値と影響版の範囲——NVD と CVE.org の原票を本記録の取得手段では参照できませんでした。集計サイトには CVSS 9.8、影響範囲「3.0.0 から 3.2.0」という値がありますが、本記録は確認していません。
  • v3.2.1 で直された脆弱性の全件——リリースノートは「複数」と書くだけで、件数も識別子も示していません。
  • 悪用の成否とその後——おとりへの到達が観測されただけで、実環境での成立は公表されていません。

「確認されていない」は「起きていない」ではありません。本件の場合、気づく手段と通報の経路がどちらも乏しい種類の資産が対象であるため、報告の不在から安全を導かないことが特に重要です（本記録の判断）。

CISO・経営層への示唆
  • **「ゼロデイだったから防げなかった」という説明が成り立たない事案である。** 悪用されたのは79日前に修正が出ていた欠陥であり、 **公開された解説が引火したのは放置された修正だった**
    公表のあとで被害が出ると「新しい攻撃だった」という整理に流れやすい。 本件の時点を並べると、**修正公開（7月13日）→技術解説（9月30日）→ 悪用の観測（10月1日）**であり、**当てていれば成立しない。** モデルによる脆弱性発見が増えるほど、**解説と実証コードが同時に出る**ため、 **この種の「既知だが当たっていない」資産が狙われる速度が上がる**（本記録の評価）
    取るべき行動 **直近3か月で「修正が出たことは把握したが、適用の確認をしていない」 資産の一覧を出させる。** とくに**インターネットに面したもの**に限って、 適用済みかどうかを機械的に確認できる状態（版の取得手段）があるかを問う。 無ければ**「版を外から確認できること」を調達・構築の要件に加える**
  • **台帳に無いソフトウェアが、台帳にあるものより先に狙われる。** HFS は個人・部門が立てる種類の道具であり、 **購買記録にも資産台帳にも載らない**
    本件の対象は、商用製品ではなく**1人の開発者によるオープンソース**である。 **ベンダーからの通知が来ず、公表を見る担当者が組織内にいない。** それでもインターネットに面して動き、**既定で製品名が応答に出る**ため、 **攻撃者からは見つけやすい**（本記録の評価）
    取るべき行動 **外部からの資産観測（自組織の IP レンジに対する定期的な外形スキャン）を 仕組みとして持つ。** 見つかった資産に**持ち主を割り当てるまでを手順に含める** （持ち主が決まらない資産は更新されない）。 あわせて**「ファイルを外へ渡す」業務に、組織として用意した手段を与える**—— 禁止だけでは同じものが別の場所に立つ
  • **自組織がモデルによる脆弱性探索を導入するなら、 「見つけたあと」の方針を先に決める必要がある**
    本件では、モデルが**実際に動く実証コード**まで作っている。 **探索の成果物は、そのまま攻撃の材料になりうる。** 供給元への通知の経路、公表の時期、実証コードの保管と共有範囲に 方針が無いまま始めると、**自社の検査結果が流出したときの被害が大きい** （本記録の判断）
    取るべき行動 **検査の委託契約と社内規程に、①発見の通知先と期限、②実証コードの 取り扱い（保管場所・共有範囲・保存期間）、③第三者製品の欠陥を見つけた場合の 公表方針を明記する。** 既に検査を外部に委託している場合は、 **成果物の保管の仕方を確認する**
  • **「報告が無いこと」を安全の根拠にしない。** 本件の対象資産は、侵害に気づく手段も通報の経路も乏しい
    HFS を立てた部門には監視の仕組みが無いことが多く、 **管理者 Cookie を偽造された場合、攻撃者は正規の管理者として振る舞う。** **侵害を見分ける痕跡は、本記録が確認した資料には示されていない。** 日本の host が狙われたことは観測されているが、**被害の公表は無い**
    取るべき行動 **自組織の該当資産について「侵害されていないと言える根拠」を 1行で書けるかを確認する。** 書けないなら、 **更新と同時にセッション無効化と管理者資格情報の入れ替えを行う** （疑わしきは入れ替える。費用は小さい）
セキュリティ技術者への示唆
  • **署名鍵・トークン・セッション識別子を `Math.random()` 系の 非暗号用途の乱数から作っていないかを、コードで確認する**
    本件の起点は、`COOKIE_SIGN_KEYS` が設定されず `keys=[randomId(30)]` として `Math.random()` に落ちていたことである。 **V8 の `xorshift128+` は反転可能であり、出力が分かれば内部状態が解ける。** **「既定値のまま動いてしまう」作りだったことが本質である**（本記録の読み）
    取るべき行動 **`Math.random`・`rand()`・`mt_rand()` などの呼び出しを全コードで検索し、 鍵・トークン・セッション・CSRF・パスワード再設定に使われていないかを確認する。** 該当があれば **`crypto.randomBytes`（Node.js）等の暗号用途の生成器へ置き換える。** あわせて**署名鍵が未設定のまま起動できる作りを禁止する** （起動時に必須の設定として検査し、無ければ落とす）
  • **「漏らしてはいけない値」が別の経路から出ていないかを、 値の流れとして追う。** 単体の指摘では本件は見つからない
    弱い乱数だけでも、出力の漏えいだけでも、実用的な攻撃には届かない。 **2つが同じ製品の中で噛み合ったときに鍵の復元が現実的になる。** Hanley が「印象的だ」と書いたのは、**モデルがこの2点を連鎖として 認識した**ことである
    取るべき行動 **レビューの観点に「この値はどこから来て、どこへ出ていくか」を追う作業を 明示的に入れる。** とくに**乱数・内部識別子・サーバ側の状態**が、 応答ヘッダ（`Set-Cookie` を含む）・エラーメッセージ・デバッグ端点から 外へ出ていないかを確認する。 **応答に出る値の一覧を作り、それぞれの出所を書く**のが具体的な手である
  • **セッション Cookie が偽造されたときに気づける記録を持つ。** 本件では攻撃者は正規の管理者として振る舞う
    管理者 Cookie を偽造された場合、**認証は「成功」する。** 認証失敗の監視では引っかからない。 **本記録が確認した資料には、侵害を見分ける痕跡が示されていない**—— つまり**利用側が自前で記録を持っていないと判定できない**（本記録の評価）
    取るべき行動 **管理操作（設定変更・利用者追加・ファイル操作）を、 誰が・いつ・どの IP からという形で記録し、保存期間を確認する。** あわせて**管理セッションの発行元 IP・UA の急な変化を警報にする。** 記録が無い製品を外に出すときは、**前段（リバースプロキシ）側で取る**
  • **外から見える自組織の資産を、外から数える手段を持つ。** HFS は応答から製品名が分かる種類のソフトウェアである
    内側の台帳は、部門が立てたものを映さない。 **攻撃者は外から探している**——本件の観測は 「実際に脆弱な host を狙っていた」というものであり、 **相手は該当する host を特定できている**（本記録の読み）
    取るべき行動 **保有 IP レンジに対する定期的な外形スキャンを回し、 「応答に出る製品名と版」の一覧を作る。** クラウドの一時的な公開端点も対象に含める。 **見つかった資産は、台帳に登録するまでを1つの作業にする**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ インターネットから到達できる位置に、ファイル共有・ファイル受け渡しのための小さなサーバを置いている
認証・認可□ セッション Cookie・API トークン・CSRF トークンの生成や署名に使っている乱数の出所を、コードで確認していない
認証・認可□ サーバ側の内部状態（乱数の出力・内部識別子・デバッグ情報）が応答ヘッダやエラーに出ていないかを棚卸ししていない
運用・監視□ 「修正が出たこと」は把握できるが、「適用されたこと」を外から機械的に確認できない
運用・監視□ 管理操作の記録（誰が・いつ・どの IP から）が無い、または保存期間が短い製品を外に出している
体制・契約□ 自組織または委託先が、モデルを使った脆弱性探索を導入している（または検討している）
