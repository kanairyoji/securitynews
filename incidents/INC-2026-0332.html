INC-2026-0332Fireware OS に15件、root 実行可

WatchGuard が2026年9月29日から30日にかけて公開した一連のアドバイザリで、 UTM アプライアンス Firebox の OS「Fireware OS」に**15件**の脆弱性が明らかになった。 もっとも重いのは **CVE-2026-86131（CVSSv4.0 9.2・Critical）**で、 **「BOVPN Over TLS」クライアントの設定処理におけるコードインジェクション**である—— **接続先の VPN サーバを制御できる攻撃者が、接続してきた Firebox 上で root 権限により任意のコマンドを実行できる**。 **本件の要点は、信頼の向きが逆転している点にある**—— 拠点側の Firebox が、**自分が接続していく先のサーバから受け取った設定を信じて実行する**。 ハブ側が落ちれば、**そこへつながるスポークが芋づる式に root を取られる**（本記録の読み）。 残る14件には **fingerd の事前認証スタックオーバーフロー（CVE-2026-81433・8.7）**、 **SAML ログインの認可不備による SSLVPN への不正アクセス（CVE-2026-86101・7.2）**、 **WebUI 管理エージェントのパストラバーサルによる任意ファイル読み取り （CVE-2026-13224・8.2）**などが含まれる。 **アドバイザリ公開時点で悪用は確認されていない。** **修正版は 2026.3.2 / 2026.2.3 / 12.12.3（T15・T35 は 12.5.21）**である

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年9月29日 最終更新: 2026年10月5日

2026年9月29日から30日にかけて、WatchGuard Technologies が複数のセキュリティアドバイザリを公開しました。 対象は同社の UTM アプライアンスFirebox に搭載されている「Fireware OS」で、明らかになった脆弱性は15件です。本記録の作成者が WatchGuard PSIRT の一覧を確認したところ、同じ2日間に公開されたアドバイザリは16件あり、うち15件が Fireware OS、1件は別製品の AuthPoint Authentication Gateway（CVE-2026-95676・7.4）でした。国内媒体が「15件」としているのは Fireware OS の分です。

もっとも重いのは CVE-2026-86131 です。 重要度は4段階でもっとも高い「クリティカル（Critical）」、CVSSv4.0 のベーススコアは 9.2。題名は「Fireware OS Code Injection in BOVPN Over TLS Client Allows Remote Code Execution」（原文英語）——BOVPN Over TLS クライアントのコードインジェクションにより遠隔コード実行が可能です。接続先となる VPN サーバを制御できる場合に、接続してきた Firebox 上でroot 権限により任意のコマンドを実行できます。

ここが本件の読みどころです。 攻撃の向きが、通常の境界機器の脆弱性と逆です。インターネットから Firebox を叩くのではなく、Firebox が自分から接続していった先が攻撃者の手にあるという前提の攻撃です。拠点の Firebox は、本社（ハブ）側のサーバから受け取ったクライアント設定を信じて処理します。 したがってハブ側が1台落ちれば、そこへつながるスポークが順に root を取られるという構造になります（本記録の読み。WatchGuard はこの形では説明していません）。境界機器は「外からの攻撃を防ぐもの」として設計・運用されますが、本件で破れるのは内側向きの信頼です。

残る14件も軽くはありません。 本記録が PSIRT の一覧で確認した範囲では、fingerd の事前認証スタックバッファオーバーフローによる遠隔コード実行（CVE-2026-81433・8.7）、spamd のスタックオーバーフローによる遠隔コード実行（CVE-2026-18145・8.6）、samld の信頼できないデータのデシリアライズによる遠隔コード実行（CVE-2026-13046・7.5）、SAML ログインの認可不備によるSSLVPN への不正アクセス（CVE-2026-86101・7.2）、WebUI 管理エージェントのパストラバーサルによる任意ファイル読み取り（CVE-2026-13224・8.2）が並びます。残りは iked・NetFlow 処理・wgagent 管理 API・診断タスクにおけるサービス拒否（7.1〜8.7）です。

アドバイザリの公開時点で悪用は確認されていません（国内媒体の記述）。修正版は Fireware OS 2026.3.2 / 2026.2.3 / 12.12.3 で、小型機種の T15・T35 は 12.5.21 です。環境によって影響を受ける脆弱性は異なります——どの機能を有効にしているかで該当・非該当が変わるため、「15件すべてが自社に当たる」とは限りません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は悪用が確認されていない脆弱性であり、以下は「公表された機構から 組み立てられる攻撃の筋」である**（実地の攻撃の記録ではない。本記録の構成）。 **CVE-2026-86131 の筋**は、**①攻撃者が BOVPN Over TLS のサーバ側を用意するか 既存のハブを掌握する → ②拠点の Firebox が接続してくる → ③サーバが返すクライアント設定にコードを注入する → ④Firebox 上で root 権限により任意のコマンドが実行される**という流れである。 **前提は「接続先となる VPN サーバを制御できること」**であり、 **インターネット側から無条件に叩ける脆弱性ではない。** **一方 CVE-2026-81433（fingerd）・CVE-2026-18145（spamd）は事前認証であり、 該当サービスが外に出ているなら前提が軽い**（本記録の読み）。

  1. 1. 偵察推定
    **攻撃者は、対象が Fireware OS を動かしていることと、 どの機能が外に出ているかを調べる。** **本件に固有の記録ではなく、境界機器一般の前段である**（本記録の整理）。
    根拠: 本記録の整理（公表資料に偵察段階の記述は無い）
  2. 2. 初期侵入確認済
    **CVE-2026-86131 の場合**——**攻撃者が制御する BOVPN Over TLS サーバへ Firebox が接続し、サーバが返すクライアント設定にコードが注入される。** **CVE-2026-81433・CVE-2026-18145 の場合**—— **fingerd・spamd に対する事前認証のスタックバッファオーバーフロー。** **CVE-2026-86101 の場合**——**SAML ログインの認可不備により SSLVPN への不正アクセスが成立する。**
    根拠: WatchGuard PSIRT のアドバイザリ題名および国内媒体の記述
  3. 3. 実行確認済
    **注入されたコードが Fireware OS 上で動く。** **国内媒体は「root 権限により任意のコマンドを実行できる」と記述している。** **権限分離が効かない**ため、この段階で機器は完全に攻撃者のものになる。
    根拠: 国内媒体の記述（root 権限での任意コマンド実行）
  4. 4. 権限昇格確認済
    **本件では権限昇格の段階が存在しない。** **CVE-2026-86131 は最初から root 権限での実行に至る** （国内媒体の記述）。**HPE Instant On の事案（INC-2026-0333）と同じ性質で、 「ネットワーク機器の脆弱性は、昇格の手間を省く」**（本記録の評価）。
    根拠: 国内媒体の記述（root 権限）
  5. 5. 横展開推定
    **公表されていない。** **以下は本記録の推定である**——境界機器で root を得た攻撃者は、 **通信の経路上にいる**ため、内側への横展開に有利な位置にある。 **BOVPN Over TLS のハブを掌握した場合、 そこへ接続してくる拠点の Firebox が次の対象になる** （CVE-2026-86131 の前提がそのまま満たされる）。
    根拠: 本記録の推定（公表資料に横展開の記述は無い）
  6. 6. 影響（暗号化・破壊・改ざん）確認済
    **サービス拒否8件については、影響は可用性である**—— **境界機器が止まれば拠点の通信が止まる。** **遠隔コード実行4件については、公表されているのは 「root 権限で任意のコマンドを実行できる」という能力までであり、 実際の被害は発生していない**（悪用の確認が無い）。
    根拠: WatchGuard PSIRT の題名（Denial of Service / Remote Code Execution）

インターネット側から Firebox を叩く攻撃ではありません。 Firebox が自分から接続していった先が攻撃者の手にあるときに成立します。

これが何を意味するか。本社と拠点を BOVPN Over TLS でつなぐ構成では、拠点の Firebox はハブ側から受け取った設定を信じて処理します。 ハブ側が1台落ちたとき、被害はそのハブで止まりません—— そこへつながるスポークが順に root を取られます（本記録の読み）。境界機器は「外からの攻撃を止めるもの」として置かれますが、本件で破れるのは内側向きの信頼です。

もう一つの読み筋は、root であることです。 Firebox 上で root を取られた場合、その機器は防御装置ではなく攻撃者の足場になります。 境界機器は内側と外側の両方に足がかかっており、通信の復号・改変・迂回が、検知されずにできる位置にあります（本記録の評価）。侵害された境界機器は、設定を見ても分かりません—— 更新だけで足りると考えないほうがよい理由がここにあります。

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**WatchGuard は15件を CVE 単位の個別アドバイザリとして公開し、 影響する版の範囲と修正版を機種系列ごとに示した。** **まとめの1本は本記録の作成者が確認できなかった。**部分的に機能**評価は本記録の判断である。** **良い点**——**CVE ごとに影響範囲と修正版が機種系列別に書かれているため、 自社の版が該当するかを機械的に判定できる。** **T15・T35 を別系列として明示している点も、旧世代機を使う組織には要る情報である。** **足りない点**——**15件をまとめた1本が見当たらないため、 「全体で何件か」「自社の構成では何件が立つか」を読者が自分で数える必要がある。** **国内媒体が15件と数えて初めて全体像が見えたという順序になっている。** **また CVE-2026-81433 に T15・T35 の修正版が書かれていない理由も示されていない** （本記録の留保: 一覧の取得時点の表示であり、その後更新された可能性は排除できない）。
CISO・経営層への示唆
  • **境界機器が「外から守るもの」だという前提が、本件では成り立たない。** もっとも重い1件は、**拠点の機器が本社側を信じている部分**を突く
    CVE-2026-86131 は、**接続先の VPN サーバを制御できる攻撃者が、 接続してきた Firebox 上で root を取る**という形である。 **ハブ1台の掌握が、そこにつながるスポークの掌握につながる構造**であり、 **被害の見積もりを「機器1台」で止めると小さく見える**（本記録の評価）。 境界機器は冗長化・可用性の観点では管理されているが、 **「その機器が攻撃者のものになったときに何が連鎖するか」**は 設計書に書かれていないことが多い
    取るべき行動 **拠点間 VPN の構成図を出させ、「ハブが落ちたときに何台が root を取られるか」を 数字で答えさせる。** 答えが出ないなら、 **その数字を出せる状態（機器一覧と接続関係の台帳）を作ることを先に指示する。** あわせて**ハブ側機器の更新を、スポークより先に完了させる順序**を決める
  • **「15件」という件数は、自社に立つ件数ではない。** **有効にしている機能の一覧が無いと、影響の判定ができない**
    本件の15件は fingerd・spamd・samld・iked・wgagent・NetFlow・WebUI・ Access Portal と**別々の機能にまたがっている。** 供給元も「環境によって影響を受ける脆弱性は異なる」としており、 **判定には自社の設定を知っていることが前提になる。** **件数の大きさに反応して全件対応を指示すると、 実際には立たない脆弱性に工数を使い、 立っている1件（BOVPN Over TLS）が埋もれる**（本記録の評価）
    取るべき行動 **境界機器ごとに「有効にしている機能の一覧」を出させ、 構成管理の対象にする。** 以後の脆弱性公表に対しては、 **この一覧と突き合わせて「自社に立つのは何件か」を最初に答えさせる。** **一覧が無い場合は、それを作ることを対応の第一歩とする**
  • **サービス拒否8件を「情報は漏れないから軽い」と読まない。** 境界機器が止まれば、拠点の業務が止まる
    本件のサービス拒否は CVSS 7.1〜8.7 の範囲にあり、 **事前認証で成立するものも含まれる**（CVE-2026-86134・86133）。 **境界機器の停止は、情報漏えいより先に業務を止める。** **可用性の損失は、機密性の損失と同じ稟議の枠では語られないことが多く、 結果として対策が後回しになる**（本記録の評価）
    取るべき行動 **境界機器が停止したときの業務影響（拠点数・停止時間あたりの損失）を あらかじめ見積もり、更新作業の停止時間と比較できる形にする。** この数字があると、**「更新のための停止」を業務側と交渉できる**
  • **「公開時点で悪用は確認されていない」は、猶予の説明であって 安全の説明ではない**
    識別子・場所・CVSS 値が公開された時点で、**攻撃側の調査の出発点が揃う。** **境界機器の遠隔コード実行は、公開後に悪用が始まる典型である。** 本記録が同日に記録した別事案（INC-2026-0330）では、 **技術解説の公開から悪用の観測まで1日**だった
    取るべき行動 **「悪用が確認されていない」脆弱性の更新期限を、 悪用が確認されたものと別枠にせず、資産の露出度で決める** （外に面している境界機器は最短枠に入れる）。 **期限を過ぎた資産の一覧が毎週出てくる状態にする**
セキュリティ技術者への示唆
  • **BOVPN Over TLS の接続先（ピア）を固定し、 証明書の検証を必須にして、ピアの変更を警報にする**
    CVE-2026-86131 の前提は**「接続先となる VPN サーバを制御できること」**である。 **攻撃者がハブを掌握する経路と、接続先を差し替える経路の両方が前提を満たす。** **ピアの同一性を確認していなければ、攻撃者のサーバへ接続した拠点機器が そのまま root を取られる**（本記録の読み）
    取るべき行動 **拠点機器の BOVPN 設定を棚卸しし、①接続先が IP・FQDN で固定されているか、 ②サーバ証明書の検証が有効か、③ピアの指定が変更されたときに 構成管理の差分として検出できるかを確認する。** **③が無い環境では、設定のバックアップを日次で取得して差分を取るだけでも効く**
  • **外に出す必要のないサービス（fingerd・spamd・Access Portal・WebUI 管理面）を 止め、何が外から到達できるかを外側から数える**
    15件のうち**事前認証で成立するもの（CVE-2026-81433・86134・86133）**は、 **該当サービスが外に出ているかどうかで危険度が決まる。** **とくに fingerd が外に出ている必要がある構成は、現代ではまず無い** （本記録の評価）。 **内側の設定確認だけでは「実際に外から届くか」は分からない**
    取るべき行動 **保有 IP レンジに対して外側からポートスキャンを実施し、 応答するサービスの一覧を作る。** **WebUI の管理面は、管理網または VPN 経由のみに限定する。** **止められないサービスは、送信元 IP の制限をかける**
  • **T15・T35 のような旧世代機を、本社と同じ版番号で管理しない。 CVE-2026-81433 は T 系の修正版が示されていない**
    15件のうち14件は T15・T35 向けに **12.5.21** が示されているが、 **CVE-2026-81433（fingerd・8.7）だけは 2026.3.2 / 2026.2.3 / 12.12.3 の 3つしか挙がっていない。** **「影響しない」のか「修正が別途」なのかは、本記録が確認した一覧からは読めない** （本記録の確認）。 **旧世代機は支店・店舗に残りやすく、台帳の更新も遅れる**
    取るべき行動 **機種ごとに現在の版と対応する修正版を並べた表を作る** （系列が違えば版番号の大小比較が意味を持たないため）。 **T15・T35 を使っている場合は、CVE-2026-81433 の扱いを供給元に確認する。** **サポート終了が近い機種は、更新ではなく置き換えの判断に回す**
  • **機器の記録を外部へ転送し、管理操作を誰が・いつ・どの IP から行ったかを残す。 root を取られた機器の記録は、その機器の中に置いても意味がない**
    CVE-2026-86131 の結果は **root 権限での任意コマンド実行**である。 **root を取った攻撃者は機器内の記録を消せる。** **侵害を見分ける痕跡について、本記録が確認した資料には記述が無い**—— **利用側が自前で記録を外に出していないと、後から判定できない**（本記録の評価）
    取るべき行動 **境界機器の syslog を発生時に外部のログサーバ・SIEM へ送る設定を確認する** （「設定してあるつもり」になっている例が多いので、実際に届いているかを見る）。 **設定変更・管理者ログイン・ファームウェア操作を警報の対象にする。** **保存期間は、脆弱性の公開日から遡って確認できる長さにする**
  • **更新したあとに「侵害されていないと言える根拠」を1行で書けるか確かめる**
    本件は悪用が確認されていないため、**本記録は侵害を疑うべきだとは書かない。** ただし**BOVPN Over TLS のハブを公開している組織では、 更新前の期間に何が起きたかを後から確認する手段が要る**（本記録の判断）。 **境界機器の侵害は、設定画面を見ても分からない**
    取るべき行動 **更新と同時に、①設定のバックアップを取って公開前の版と差分を取る、 ②管理者資格情報と API キーを入れ替える、 ③VPN のセッションを一度切る、の3つを行う。** 費用は小さく、**後から「確認した」と言える根拠になる**
