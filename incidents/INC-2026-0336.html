INC-2026-0336JCI EasyIO 3製品に脆弱性7件

Johnson Controls がビル管理用コントローラ EasyIO の3製品群について脆弱性5件（CVE 7件）を公表。 ハードコード認証情報を抱える EasyIO FG は End-of-Life で「修正版は出さない」とされ、 オンチップデバッグ（SWD）の2件はファームウェア更新ではなく機器そのものの交換でしか直らない。 CISA が ICS アドバイザリとして取り上げたのは Neo 系の2件のみで、 JVN 経由で日本の読者に届いたのもその2件だった

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月1日 最終更新: 2026年10月5日

2026年10月1日、Johnson Controls がビル自動化（BAS/OT）用のエッジコントローラEasyIO について、製品セキュリティアドバイザリ5件（JCI-PSA-2026-06 / 12 / 19 / 20 / 30）を同日に公表した。 対象は EasyIO FG・EasyIO Neo Series（EC・CW）・EasyIO FS-32 の3製品群で、割り当てられた CVE は合計7件である。

この事案で読むべき点は「脆弱性が7件あった」ことではなく、3種類の「直し方」が並んでいることのほうである（本記録の評価）。

  1. EasyIO FG は修正されない。 ベンダー自身が「No firmware fix is available（ファームウェアの修正は提供されない）」「ソースコードはもはや存在しない」と書いている。2019年より前に製造・販売を終えたEnd-of-Life / End-of-Support 製品で、ハードコードされた認証情報（CWE-798）を抱えたまま恒久的に放置される。 ベンダー評価は 7.2（High）で5件中もっとも高い。
  2. SWD（オンチップデバッグ）の2件は、ファームウェア更新では直らない。修正の説明は「SWD インターフェースをハードウェアから取り除いた」であり、「既存の機器をこのハードウェアリビジョンに交換した顧客が修正済みとみなされる」。ビルに据え付けられた制御機器の物理交換が必要という意味である。
  3. 残りの2件（Neo の CWE-200 / CWE-319）だけが、通常のファームウェア更新で直る（EC V3.3b64 / CW V3.3b26）。

そして、この3種類のうち CISA が ICS アドバイザリとして取り上げたのは3番目の2件だけだった。 ICSA-26-274-04（CVE-2026-64892）と ICSA-26-274-05（CVE-2026-64893）がそれで、残る3本のベンダーアドバイザリは ICSA ID の欄が "ICSA-26-xxx-xx" というプレースホルダのまま公開されている。日本の読者が JPCERT/CC の JVNVU#91842649（2026年10月2日）で受け取ったのも、カナダ Cyber Centre の AV26-991（同日）が参照先として挙げたのも、この経路の情報である。「修正されない EOL 製品のハードコード認証情報」という、いちばん手当てが要る話が、公的な注意喚起の経路にはほとんど乗っていない（本記録の評価）。

いちばん評点が高い EasyIO FG は、ベンダーが「ソースコードがもう無い」と書いて修正を断っている原因・手口

JCI-PSA-2026-12 の Remediation 節の記述を、そのまま引く（原文英語・訳は本記録）。

ファームウェアの修正は提供されない。EasyIO FG シリーズは End-of-Life（EOL）およびEnd-of-Support（EOS）に達している。本製品は2019年より前から製造も販売もされておらず、ソースコードはもはや存在しない。ファームウェアのパッチもコードレベルの修正も発行されない。顧客はサポート対象の現行世代製品（例: EasyIO Neo R1 Series）への移行を推奨される。

抱えている欠陥は、ハードコードされた認証情報（CWE-798）と権限管理の不備（CWE-269）である。ベンダー自身の説明では「ハードコードされた認証情報と不適切な権限管理を通じてシステムへ不正にアクセスし、デバイスへの管理者権限のアクセスに至りうる」（原文英語）。ベンダー評価は 7.2（High）で、今回の5本のうち最も高い。

「ソースコードが無い」という理由は、利用者から見ると交渉の余地が無いという意味である。ベンダーの善意や優先順位の問題ではなく、物理的に直せないと宣言されている。したがって、この機器については「パッチ待ち」という状態が存在しない。取りうるのは、①機器を入れ替える、②到達経路を物理的・論理的に断つ、③リスクを受容して記録に残す、の3つだけである（本記録の評価）。

ハードコードされた認証情報は、緩和策との相性がとくに悪い。ベンダーが挙げる緩和策は「隔離した BAS/OT ネットワークにのみ設置」「エンタープライズ IT ネットワークとの厳格な VLAN 分離」「信頼されたエンジニアリングワークステーションからのみ・ホワイトリストした IP のみ許可」「Telnet 等の安全でないサービスの無効化」などで、すべて「到達させない」系である。 認証情報そのものは変えられないので、到達を許した瞬間に守りが無くなる（本記録の評価）。アドバイザリ自身も「これらの緩和策はリスクを下げるが、脆弱性を完全に是正するものではない」と書いている。

SWD の2件は「ファームウェアを上げる」では直らず、基板からインターフェースを取り去った機器に交換する必要がある原因・手口

JCI-PSA-2026-19（CVE-2026-34493 / 34494、CWE-1191「アクセス制御が不適切なオンチップデバッグ・テストインターフェース」）のRemediation 節は、次のように書いている（原文英語・訳は本記録）。

SWD インターフェースは、CW ファームウェア V3.3b26 および EC ファームウェア V3.3b64 を搭載したデバイスにおいて、ハードウェアから取り除かれた。既存のデバイスをこのハードウェアリビジョンに置き換えた顧客は、是正済みとみなされる。

ここでファームウェア版が出てくるのは、新しい基板リビジョンを示すための目印であって、「その版に更新すれば直る」という意味ではない。 SWD（Serial Wire Debug）は基板上のデバッグ端子であり、ソフトウェア更新で物理的な端子が消えることはない。

影響の説明は「物理アクセスを持つ攻撃者がデバイスの機能を改ざんしうる」である。ところが同じ文書の CVSS ベクタは AV:N（ネットワーク）から始まっている——物理アクセスが前提なら AV:P になるはずで、説明とベクタが整合していない（discrepancies に記録）。

代替の緩和策としてベンダーが挙げるのは、「基板や筐体に権限のない者が到達できないよう物理的なアクセス制御を実施する」 「改ざん検知可能な筐体を使う、またはデバッグヘッダのピンにエポキシ樹脂を塗布してSWD インターフェースへの物理的なプロービングを抑止する」の2つである。「エポキシで埋める」が公式の緩和策として書かれているのは、ソフトウェアで閉じる手段が無いことの裏返しである（本記録の評価）。

読者にとっての含意は、OT 機器のリスク評価に「物理」の軸が要るということである。テナントや清掃業者や工事業者が機械室・天井裏・パイプスペースに入れる建物では、「物理アクセスが前提だから低リスク」という前提が成り立たない（本記録の評価）。

公的な注意喚起の経路に乗ったのは、5本のうち「ファーム更新で直る2本」だけだった対策・注意喚起

CISA が2026年10月1日に出した ICS アドバイザリのうち Johnson Controls 関連は2本である。

  • ICSA-26-274-04 — CVE-2026-64892（CWE-200・機微情報の露出）
  • ICSA-26-274-05 — CVE-2026-64893（CWE-319・平文での機微情報の送信）

この2本は、ちょうど「ファームウェア更新で直る」側の2件である。修正されない FG も、機器交換が要る SWD も、FS-32 も入っていない。

ベンダー側の文書を見ると、これは意図的な線引きというより、連携が途中で止まった形跡に見える（本記録の推定）。JCI-PSA-2026-20 のヘッダには ICSA ID: ICSA-26-274-04 と番号が入っているが、PSA-06・12・19 と、なぜか PSA-30 まで、ヘッダは ICSA ID: ICSA-26-xxx-xx というプレースホルダのままで公開されている（PSA-30 の CVE-2026-64893 は実際には ICSA-26-274-05 として公表されている）。

そしてこの経路の形が、日本の読者が受け取る情報の形をそのまま決めている。 JPCERT/CC の JVNVU#91842649（2026年10月2日）は CISA の同日分6件を転載したもので、Johnson Controls 分は ICSA-26-274-04 / 05 の2件だけである。カナダ Cyber Centre の AV26-991（同日）は3製品すべてを挙げており範囲は広いが、本文は版番号の羅列と「リンクを見て更新を適用せよ」の一文だけで、FG に更新が存在しないことには触れていない。

ここから読める実務上の含意は一つである（本記録の評価）。公的な注意喚起の一覧を入口にしていると、「直せないから手当てが要る」種類の脆弱性ほど見落とす。 CISA / JVN の一覧は網羅の保証ではなく、ベンダー側のアドバイザリページを別経路で監視する必要がある。

同じ CVE の CVSS が、ベンダー・CISA・NVD の三者で揃っていない評価・解釈

CISA が取り上げた2件について、三者の評価を並べる。

CVE-2026-64892 では、同じ v4.0 で 4.8 と 6.3 の開きがある。差はおもに Subsequent System（SC / SI / SA）の扱いで、CISA は3つとも N、NVD 登録値は3つとも H としている。「この機器が落ちた先で何が起きるか」の見積もりが正反対である。ビル制御機器はそれ自体より「その先で動く空調・照明・電源」が本体なので、この軸をどう置くかで結論が変わる（本記録の評価）。

FG についても同様の開きがある。 ベンダーは2つの CVE をまとめて 7.2（High）と評価するが、NVD は CVE-2026-27872・27873 をそれぞれ 5.6（Medium）としている。

さらに NVD 側の7件はすべて vulnStatus が Deferred である。これは NVD が追加の評価を行わない区分で、「NVD の値が今後精緻化される」ことは期待できない。

実務への含意（本記録の評価）。脆弱性の優先度付けを CVSS 一本に寄せている組織は、本件のように「どこの CVSS か」で2点以上動く事案で判断が割れる。少なくとも、台帳に値だけでなく出所（ベンダー / CISA / NVD）を併記しておかないと、後から見た人が再現できない。そして本件でいちばん対応が重い FG は、NVD の値（5.6）だけを見ていると優先度の下のほうに沈む。

報告者のクレジットが、ベンダーと CISA で食い違っている帰属

同じ2件の CVE について、誰が見つけたかの記載が一致しない。

  • CVE-2026-64892 / 64893 — CISA の ICSA-26-274-04 / 05 は、いずれも外部研究者 Gabriele Gardois をクレジットしている。
  • 同じ2件 — ベンダーの JCI-PSA-2026-20 / 30 の謝辞は、いずれも「internal Penetration Test Team（社内ペネトレーションテストチーム）」である。

一方で、FG（PSA-12）と FS-32（PSA-06）の謝辞は Gabriele Gardois であり、SWD の PSA-19 は社内チームとなっている。つまりベンダー側の文書では「外部研究者 2本・社内チーム 3本」と整理されているのに対し、CISA はそのうち社内チームとされた2本を外部研究者の功績として公表している。

本記録はどちらが正しいかを判定しない。ただし、この手の食い違いは同一ベンダーが短期間に複数のアドバイザリをテンプレートから量産したときに起きやすい（本記録の推定）。実際、PSA-20 の緩和策は「デバッグポートへの物理アクセスを防ぐ」から始まっており、CWE-200（機微情報の露出）の内容ではなく、SWD を扱う PSA-19 の文面に近い。 CVSS ベクタが途中で切れている（SA で終わる）のも同じ系統の欠陥である。

読者への含意は、アドバイザリの文面そのものを一次情報として扱いつつ、「作りが荒い文書」であることを前提に読む必要があるということである（本記録の評価）。緩和策の一覧が自機の脆弱性と噛み合わないと感じたら、その違和感は読み手側の誤解ではなく文書側の流用である可能性がある。

緩和策
item: 自組織のビル設備に EasyIO FG が残っていないかを、機種名とファームウェア版（2.0b52 以前）で 棚卸しする。見つかった場合は、パッチ待ちではなく**更改か隔離かの判断を立てる案件として 起票する**　副作用: **「修正は出ない」と分かることで、脆弱性管理の台帳に 恒久的に閉じられない項目が生まれる。** これは管理指標（未対応件数・平均対応日数）を悪化させるので、 **受容リスクとして別枠に移す手続きを先に用意しないと、 現場が台帳から消すインセンティブを持ってしまう**（本記録の評価）。 棚卸し自体も、ビル設備の機器一覧が IT 資産管理の外にあることが多く手間がかかる。
item: EasyIO Neo（EC V3.3b62/63・CW V3.3b24/25）については、 ファームウェアを EC V3.3b64 / CW V3.3b26 へ更新する。 **ただし SWD の2件（CVE-2026-34493 / 34494）はこの更新では直らない**ことを 併せて記録に残す　副作用: **「最新版に上げた＝全部直った」と誤認されやすい。** ベンダー文書は同じ版番号を 「ファームの修正版」としても「SWD を削除した新しいハードウェアリビジョンの目印」としても 使っているため、**版番号だけを見ると区別がつかない。** 更新作業自体も、BAS の制御が止まる時間帯の調整（夜間・休日）が要る。
item: Web 管理インターフェースへの HTTP（ポート80）到達を閉じ、HTTPS/TLS を強制する （CVE-2026-64893 への直接の緩和）　副作用: **古い施工・古い統合監視盤からの接続が切れることがある。** ビル設備は10年以上使われるため、**HTTPS に対応していない上位システムや 現場の携帯端末が残っていると、閉じた瞬間に監視が止まる。** 切り替えの前に、どこから何が接続しているかを実測で洗う必要がある。
item: EasyIO を含む BAS/OT セグメントを、業務 IT ネットワークおよびインターネットから 分離する（VLAN 分離・ACL・エンジニアリングワークステーション限定・VPN 経由のみ）　副作用: **遠隔保守を請け負っているビル管理会社・設備業者の作業経路を同時に塞ぐことになる。** 契約上の保守応答時間（SLA）に影響するため、**セキュリティ部門だけでは決められない。** また FG のようにハードコード認証情報を抱える機器では、 **分離は「到達させない」だけで、到達された後の守りは無い**点を理解しておく必要がある。
item: SWD の2件については、機械室・天井裏・パイプスペースなど機器の設置場所への 物理アクセスを管理する（施錠・入退記録・封印シール）。 ベンダーは**デバッグヘッダへのエポキシ樹脂の塗布**も挙げている　副作用: **樹脂で埋めると、正規の保守でもデバッグ端子が使えなくなる。** 故障解析をベンダー・施工業者に依頼する際の手段を失うため、 **保守契約の条件に抵触しないかを先に確認する必要がある。** 入退管理の強化は、テナント・清掃・工事業者の動線に影響する。
item: **ベンダーのアドバイザリページ（Johnson Controls Trust Center）を、 CISA / JVN とは別経路で監視対象に加える**　副作用: **監視対象を増やすと、読むべき文書の量が増える。** 本件のように**公的な一覧に乗らないアドバイザリが現に存在する**以上、 製品ベンダー単位での購読は避けられないが、 **「誰が読み、誰が自社該当を判定するか」を決めずに購読先だけ増やすと 受信箱に溜まるだけになる**（本記録の評価）。

CISO・経営層への示唆
  • 脆弱性の台帳に「直し方の種類」の欄を作る。パッチ・機器交換・修正なし は別の意思決定である
    **本件は同じ日・同じベンダー・同じ製品群から、3種類の対応が同時に出た。** ファーム更新（運用作業・当日中）、ハードウェア交換（工事・調達・予算）、 修正なし（更改計画かリスク受容）。 **台帳に「未対応」と並べて置くと、承認者には同じ重さに見える。** 結果として、**いちばん金と時間がかかる案件が、いちばん後回しになる。**
    取るべき行動 脆弱性台帳に**「是正手段」の区分（patch / hardware-replacement / no-fix-available / mitigation-only）** を追加し、**no-fix-available と hardware-replacement は セキュリティ部門の是正期限ではなく設備更改計画・予算サイクルへ送る経路を定義する。** **月次の未対応件数レポートから別枠に切り出し、半期の投資判断の議題に載せる。**
  • 公的な注意喚起の一覧だけを情報源にしていると、「直せない脆弱性」ほど取りこぼす
    **本件でベンダーが出した5本のうち、CISA が ICS アドバイザリにしたのは2本だけで、 それは「ファーム更新で直る」側の2本だった。** 日本語で流通した JVNVU#91842649 もその2本である。 **修正が提供されない EasyIO FG の話は、公的な経路にはほぼ乗っていない。** **一覧に載らないことは、重要でないことを意味しない。**
    取るべき行動 自社が使っている**OT / 設備系ベンダーの製品セキュリティアドバイザリページを 個別に購読対象に加え、「誰が読むか」と「自社該当をいつまでに判定するか」を 規程に書く。** 購読先を増やすだけでは効かないので、 **四半期に一度、「この期間に出たアドバイザリ件数」と「自社該当を判定した件数」を 突き合わせて、読み落としの有無を測る。**
  • ビル設備・施設側の制御機器を、IT 資産管理の対象に入れる責任者を決める
    **本件の該当判定はすべて機種名とファームウェア版で行う。** ところが BAS のコントローラは、調達も保守も施設部門や設備管理会社の側にあり、 **IT 資産台帳に載っていないことが多い。** **台帳に無い機器は、アドバイザリが来ても「該当するか分かりません」としか答えられない。** 影響分野としてベンダーが挙げたのは重要製造業・商業施設・政府施設・運輸・エネルギーで、 **自社ビル・工場・データセンターのいずれかが当てはまる組織は多い。**
    取るべき行動 **施設部門・設備管理会社と合同で、制御機器の機種・版・設置場所・遠隔保守経路の 一覧を作る責任者を一人決め、期限を切る。** **既存の保守契約の更新時に「機器一覧とファームウェア版の年次提出」を条件に加える**のが、 継続的に維持するいちばん安い方法である（本記録の評価）。
  • CVSS の値を優先度の根拠にするなら、その値がどこの機関のものかを必ず残す
    **本件では同じ CVE の v4.0 スコアが CISA 4.8 と NVD 6.3 で割れている** （CVE-2026-64892）。CVE-2026-64893 も CISA 5.9 / ベンダー 5.5 / NVD 7.3 と三者三様である。 **さらに、いちばん対応が重い EasyIO FG は NVD の値（5.6）だけ見ると 優先度の下に沈む。** **出所を残していないと、後から「なぜこの順位だったのか」を誰も再現できない。**
    取るべき行動 台帳の CVSS 欄を**「値・バージョン（v3.1 / v4.0）・出所（ベンダー / CISA / NVD）・取得日」**の 4点セットにする。 **複数機関で 1.0 以上開いた案件は、スコアではなく影響の記述で判断する**という 例外規程を書いておく。
セキュリティ技術者への示唆
  • ベンダーが「Fixed」と書いていても、修正の中身がファームウェア更新とは限らない
    **JCI-PSA-2026-19 の Product Status は「Fixed」である。** しかし本文を読むと、修正とは 「SWD インターフェースをハードウェアから取り除いた」 「既存のデバイスをこのハードウェアリビジョンに置き換えた顧客は是正済みとみなされる」 という意味で、**ファームウェアを上げても直らない。** **ヘッダの Status 欄だけを見て台帳を閉じると、直っていない機器が直った扱いになる。**
    取るべき行動 **アドバイザリの取り込み手順に「Remediation 節の本文を読む」を明記する。** 台帳に記録するのは Status 欄の値ではなく、 **「何をすれば是正したことになるか」の一文（修正版番号／交換／手段なし）にする。**
  • ネットワーク側の監視に原理的に映らない脆弱性があることを、検知設計に織り込む
    **CVE-2026-34493 / 34494 は基板上の SWD 端子への物理的なプロービングである。** ベンダーが挙げる検知の手がかりも 「保守時間外の予期しない再起動やファームウェア変更」 「筐体や露出した基板の改ざんの痕跡」という、**目視と突合せに頼るものである。** **SIEM にログを集める設計だけでは、この種の脅威に検知機会が存在しない。**
    取るべき行動 **制御機器の巡回点検項目に「封印シールの状態」「筐体の開閉跡」を追加し、 点検記録をインシデント調査で参照できる形（日付・点検者・写真の有無）で残す。** あわせて**機器の再起動イベントを保守作業記録と自動で突き合わせる**仕組みを作る （保守予定の無い再起動を拾うのが、唯一のソフトウェア側の手がかりである）。
  • ハードコード認証情報を抱える EOL 機器には、「パッチ待ち」という状態が存在しない
    **EasyIO FG についてベンダーは「ソースコードはもはや存在しない。 ファームウェアのパッチもコードレベルの修正も発行されない」と明言している。** **抱えているのはハードコードされた認証情報（CWE-798）で、 利用者側で値を変える手段も無い。** 提示された緩和策はすべて「到達させない」系であり、 **到達を許した時点で守りが無くなる構造である。**
    取るべき行動 該当機器を**「ネットワーク上で発見されたら即座に異常として扱う」対象として 資産台帳に登録する**（本来いるべきセグメント以外で見えたら警報）。 そのうえで、**更改するか・物理的に切り離すか・受容して記録するかを期限付きで決め、 「緩和策を入れたので対応済み」とは書かない**（本記録の評価）。
  • 同じ版番号が「修正版」と「ハードウェアリビジョンの目印」の両方で使われることがある
    **EC V3.3b64 / CW V3.3b26 という同じ版番号が、 PSA-20 / 30 では「ファームウェアの修正版」として、 PSA-19 では「SWD を削除した新しい基板リビジョンの識別子」として使われている。** **版番号の照合だけで該当判定を自動化していると、 ファームを上げただけの機器が「SWD も是正済み」と判定されてしまう。**
    取るべき行動 **CVE 単位で「判定に使える情報（版番号／ハードウェアリビジョン／設置状況）」を 分けて台帳に持つ。** 版番号で自動判定できない CVE には**手動確認フラグを立て、 自動判定の対象から外す。**
  • アドバイザリの緩和策が脆弱性の内容と噛み合わないときは、文書側の流用を疑う
    **CVE-2026-64892（CWE-200・機微情報の露出）の緩和策の筆頭は 「デバッグポートへの物理アクセスを防ぐ」である**—— これは SWD を扱う PSA-19 の内容に近い。 同じ文書の **CVSS ベクタは `SC:N/SI:N/SA` で途中で切れている。** **短期間にテンプレートから量産されたアドバイザリでは、 節ごとに別の脆弱性の文面が混ざることがある**（本記録の推定）。
    取るべき行動 **緩和策が自機の構成と噛み合わないと感じたら、 同じベンダーが同時期に出した他のアドバイザリを並べて読む。** そのうえで**ベンダーの PSIRT（本件では Productsecurity@jci.com）へ 文書の不整合として照会し、照会した事実と日付を記録に残す** （回答を待つ間も、CWE 名から自分で緩和策を立てて先に打つ）。
