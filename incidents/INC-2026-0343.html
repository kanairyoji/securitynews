2026年10月3日、Reuters が独自記事として、ShinyHunters の中心的な構成員とされる人物がヨルダンで拘束され、FBI に協力していると報じました。

拘束されたのは Saif al-Din Khader、オンライン上の別名「Rey」（「ReyXBF」とも）です。 3人の関係者が Reuters に語り、そのうち2人が「火曜日（2026年9月29日）に身柄を取られた」としています。

協力の内容が具体的です。 関係者の1人によれば、Khader は自らの電子機器とデジタル通信を法執行機関に対して案内し、共謀者とされる人物の特定と所在の把握を助けているとされます。「彼の協力は、これらのハッカーを逮捕するための現在の取り組みにとって決定的である」（原文英語）と、関係者の1人は述べました。

FBI は個別の逮捕には触れませんでした。 代わりに「ShinyHunters が関与したとされる今般のサイバー事案について引き続き積極的に捜査しており、すでにパートナーと協働して複数の対象者を逮捕している。責任ある個人の一人一人を裁きにかけるために、いかなる資源も惜しまない」（原文英語）と述べています。

ヨルダン当局の発表は確認されていません。 Reuters も、拘束の正確な経緯と拘置先を確認できなかったとしています。

背景には、同集団による FBI 自身への攻撃があります。 ShinyHunters は2026年9月、BleepingComputer に対し、Oracle PeopleSoft のゼロデイとされる脆弱性で FBI のシステムに侵入し、FBI が管理する AWS GovCloud 環境へ横展開したと主張しました。 窃取したデータは2TB〜3TBで、現職・元職員、採用応募者、医療・精神科の情報、内部サービスの記録を含むと主張しています。 BleepingComputer はゼロデイ・横展開・データ量のいずれも独自に検証できていないと明記しています。 FBI は不正な活動の主張について調査中であることは認めたものの、データが窃取されたことは認めていません。

本記録が注目するのは、摘発の後に何が起きたかです。

9月29日、報道機関と接触していた関係者の連絡用口座が突然閉じられました。 9月30日にはリークサイトが停止し、主要代表者が取材への応答を止めました。 しかし10月1日には、新しいリークサイトが立ち上がっています（BleepingComputer の観測）。

Sekoia と Beazley Security の報告は、この回復力の理由を説明しています。 「6年を経て、ShinyHunters は集団というよりも、創設者を超えて生き延びたブランドかつビジネスモデルである」（原文英語）。初期侵入を担う社会工学の担い手、増幅と勧誘を担う隣接アクター、そして共通のブランドの下での収益化——分業がほぼモジュール化しており、単一の指導者や細胞に依存していないとされます。

防御側への含意は厳しいものです（本記録の判断）。中心人物が1人拘束され、基盤が1日止まり、翌日に別の基盤で再開した。 摘発は、自組織の SaaS と第三者連携のリスクを下げません。

とくに最後の行が重要です。 すでに持ち出されたデータは、拘束によって消えません。 恐喝は後からでもできます。

したがって本記録の結論は、摘発の報道に対して自組織で変える設定は1つも無い、ということです（本記録の判断）。変えるべきは、この集団の手口に対応する構成のほうです ——次の節で扱います。

FBI が公表した手口は「クラウド基盤の第三者ベンダー」であり、これは業種ではなく構成で当てはまる原因・手口出典 [1] [2]

この集団に関する FBI の説明のうち、防御側が使えるのは1文です。

「彼らはしばしばクラウド基盤における第三者ベンダーを標的とし、機微なデータを窃取して、公開するという脅しで被害者を恐喝する」（Brett Leatherman・FBI サイバー部門次長。原文英語）

BleepingComputer の整理はもう少し具体的です。 「この恐喝集団は一般に、第三者の連携事業者を侵害し、窃取した認証トークンを使って連携先の SaaS 環境へアクセスし、顧客データを窃取する」。

ここで重要なのは、攻撃の起点が自組織の外にあることです（本記録の整理）。

社会工学 → 第三者の連携事業者 → 認証トークンの窃取
       → 連携先の SaaS 環境（自組織のテナント）→ 顧客データ

この経路には、自組織の境界防御が1つも登場しません。 ファイアウォール、EDR、VPN——どれも通りません。 使われるのは、自組織が正規に発行した連携の権限です（本記録の評価）。

当てはまる組織の条件は業種ではありません。

  • SaaS を使っている
  • その SaaS に第三者アプリ・連携を入れている
  • 連携に与えた権限の範囲を一覧にできない

この3つが揃っている組織は、業種に関係なく射程にあります。

本記録が指摘したいのは、140という数字の読み方です。 「140を超える組織」が侵害されたとき、そのうち何件が「自分のところは侵害されていない」と考えていたか。 第三者経由の侵害では、自組織のログに侵入の痕跡が出ません ——出るのは「正規のトークンによる正規のアクセス」です（本記録の判断）。

なお、同集団は Oracle PeopleSoft のゼロデイとされる脆弱性によるFBI への侵入も主張していますが、BleepingComputer はこれを独自に検証できていないと明記しており、FBI もデータの窃取を認めていません。 本記録はこれを手口として扱いません（攻撃者側の主張のみであるため）。

防御側にとっての含意は、楽観の材料にはなりません。 内部対立がある集団は、分裂して数が増えます ——Sekoia と Beazley Security が「自己再生を続ける」と書いているのは、この性質を指しています（本記録の解釈）。

日本の組織にとって本件は「摘発の話」ではなく「SaaS 連携の棚卸しの話」である評価・解釈出典 [1] [2]

本件に日本の組織の当事者はいません。 本記録が日本の読者に向けて書けることは、1つだけです（本記録の判断）。

この集団の手口は、日本の組織の構成にそのまま当てはまります。

理由は3つです。

  1. 標的が業種ではなく構成で決まる。 「SaaS を使い、そこに第三者連携を入れている」が条件です。 日本の組織の多くが該当します。
  2. 侵害の起点が自組織の外にあるため、国内か海外かという区分が効かない。 連携事業者が海外であれば、日本の組織も同じ経路に乗ります。
  3. 恐喝が「公開の脅し」で行われるため、日本語のデータでも成立する。 データの価値は買い手ではなく、公開されたときの損害で決まります。

したがって、本件を読んだあとに日本の CISO がやるべきことは、摘発の動向を追うことではありません（本記録の判断）。

自組織の SaaS テナントに、いま何が連携しているかを一覧にすることです。

その一覧が作れない場合、本件の140組織と同じ位置にいます。 本記録の評価では、これが本件から取り出せる唯一の実務的な行動です。

なお、この集団は過去に Salesforce その他のクラウド SaaS 環境を焦点にしたキャンペーンを行っており、その射程には日本の組織も入っていました。 ただし本記録は、本件（Khader の拘束）と日本の組織の間に直接の関係を確認していません。

拘束の時点で恐喝されていたのは、Boeing が手放した航空の電子航法事業だった——「影響は無かった」と「データは取られた」は両立する波及・関係先出典 [6] [7]

この事業体の位置を押さえておきます。

  • 航空の電子航法・デジタル航空の事業です（飛行計画・チャート・航法データ）
  • Boeing が2025年に Thoma Bravo へ105億5,000万ドルで売却しました
  • したがって、現在の運営主体は Boeing ではありません

2つの声明が出ています。 読み方が重要です。

Boeing 「脅威アクターによる、Boeing に関連するとされるデータについての主張を認識している」「Jeppesen ForeFlight のチームとともにこの件を積極的に精査している」

「影響は無かった」は、データが取られていないという意味ではありません。 述べられているのは運用と製品についてであり、データの流出の有無には触れていません（本記録の読み）。

一方で、Krebs の情報源2人は、窃取されたデータが運用上の安全とセキュリティのリスクになりうると述べ、それが FBI の緊急度を高めたとされています。 Krebs はこの主張を独自に検証していないと明記しています。 本記録も、データの種類と量を未確定事項として扱います。

自組織に引き寄せたときの論点を書きます。

①事業を売却した後も、旧親会社の名前で恐喝される。 攻撃者が「Boeing に関連するデータ」と主張し、Boeing が回答せざるを得なかったのがこの構図です。 事業譲渡の契約で、過去のデータの保管責任・侵害時の通知義務・広報の窓口を決めていない場合、売った側と買った側のどちらも説明の主体になれません（本記録の判断）。

②「運用への影響は無い」という回答で、顧客の判断は終わりません。 航法データを使う側（航空会社・運航者）が知りたいのは「運用は止まっていないか」ではなく「自分が受け取っているデータの完全性が担保されているか」です。 前者の回答で後者には答えていません（本記録の評価）。

ここから取り出せる行動を書きます。

①「攻撃者が主張したゼロデイ」を、CVE が付くまで待たずに暴露の母数として数える。 本件では、主張から番号とベンダーの確認までに約3か月かかりました（2026年6月→9月25日）。その間、同じ製品を使っている組織は「主張」しか見ていません。

③委託先のパッチ適用を、自組織の責任として確認する。 FBI の採用サイトの件で外されたのは Accenture の委託要員です（Reuters の報道。Krebs の引用）。委託していたのは作業であって、結果の責任ではありません（本記録の評価）。

    取るべき行動 **主要な SaaS（CRM・人事・会計・問い合わせ管理）について、 ①連携しているアプリと事業者の一覧、②各連携に与えた権限の範囲、 ③最後に使われた日時の3項目を出させる。** **出てこない SaaS があれば、それを監査の所見として記録し、 期限を付けて再提出させる。** **一覧が出たら、使われていない連携を削除する** ——**母数を減らすことが唯一確実に効く**
  • **恐喝を受けた場合の判断を、事案の前に文書化して承認を取っておく**

    取るべき行動 **恐喝を受けた場合の方針を1枚にまとめ、取締役会の承認を得る。** **項目は、公表の時点・通知の範囲・支払の方針・ 外部（弁護士・フォレンジック・当局）への連絡順序。** **あわせて「SaaS に置いているデータのうち、 公開されたら最も損害が大きい項目」を列挙させ、 それを SaaS から外すか暗号化して持つかを検討する**

  • **連携トークンの権限を「読み取りのみ・対象オブジェクト限定・期限つき」に絞る**
    **窃取されるのは、自組織が正規に発行したトークンである** （BleepingComputer の記述）。 **侵入を止める防御は効かない**——**効くのは、 そのトークンで何ができるかの範囲である**（本記録の評価）。 **期限が無いトークンは、第三者側で侵害された瞬間から 無期限に有効な鍵になる**
    取るべき行動 **SaaS の連携ごとに、①操作（読み取り／書き込み／削除）、 ②対象オブジェクト、③有効期限の3つを明示した設定にする。** **既存の連携で「全オブジェクトへの読み書き」になっているものを 洗い出し、必要な範囲へ縮める。** **期限の無いトークンには期限を付け、定期的な再発行を運用に入れる**
  • **連携トークンごとの API 呼び出し量とレコード取得件数に基準値を置く**
    **正規のトークンによる正規の API 呼び出しであるため、 認証の異常としては現れない**（本記録の整理）。 **異常が出るのは量と時間帯だけである。** **大量の顧客データが取得される段階が、 自組織で唯一検知しうる段階である**（本記録の評価）
    取るべき行動 **主要な SaaS の API ログから、連携ごとの平常時の ①呼び出し回数／日、②取得レコード件数／日、③実行される時間帯を測る。** **そのうえで平常時の数倍を超えたら警報を出す設定にする。** **「測ってから閾値を決める」順序を守る** ——**先に閾値を決めると、誤検知で切られる**
  • **SaaS の大量エクスポート経路を列挙し、既定で禁止する**
    **窃取の実行には、何らかの一括取得の経路が使われる** （レポート出力・一括 API・データローダ等。本記録の整理）。 **個別のレコード参照では、140組織規模のデータ量にならない** （本記録の評価）。 **経路を列挙していない組織では、どこを閉じるべきかが決められない**
    取るべき行動 **使っている SaaS ごとに、データを一括で外に出せる機能を列挙する （画面からのエクスポート・レポートのスケジュール配信・ 一括 API・連携アプリ経由）。** **そのうえで既定で禁止し、業務上必要な経路だけを 申請と承認を伴う形で開ける。** **開けた経路には、前項の量の監視を必ず付ける**
  • **第三者連携の侵害を前提に、トークンの一括失効の手順を作って試す**
    **連携事業者が侵害されたという連絡を受けたとき、 最初にやるべきはそのトークンの失効である。** **本記録の評価**——**「できるはず」と「手順がある」は違う。** **連携の一覧が無い組織では、何を失効させるべきかが分からない。** **失効の影響（止まる業務）を把握していない組織では、 判断に時間がかかる**
    取るべき行動 **主要な SaaS について、連携トークンを失効させる手順を文書化し、 検証環境で実行して所要時間を測る。** **あわせて失効したときに止まる業務を列挙し、 業務側の責任者に事前に共有しておく。** **年1回でよいので実際に試す**——**試していない手順は無いのと同じである**
