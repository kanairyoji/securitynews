INC-2026-0344Roundcube 認証前 SQLi が悪用開始

**Roundcube Webmail の virtuser_query プラグインにある認証前 SQL インジェクション（CVE-2026-48842・CVSS 8.1）が、修正公開から120日後に 実環境で悪用され始めた。** **カナダ・サイバーセキュリティセンターは2026年9月21日、 5月25日に出した勧告 AV26-503 を更新し 「公開情報による報告は、CVE-2026-48842 が実環境で悪用されていることを 示している」と記載した**（原文英語）。 **欠陥は `preg_replace()` が置換文字列中のバックスラッシュを エスケープ列として解釈する性質を突くもので、 プラグインが仕掛けていたエスケープを回り込める。** **修正は2026年5月24日公開の 1.6.16 / 1.7.1 で、 4つの関数の `preg_replace()` を `str_replace()` に置き換えている** （Roundcube のコミットで確認）。 **本記録が中心に置くのは「該当判定が版番号だけでは決まらない」点である**—— **影響を受けるのは virtuser_query プラグインを有効にしている環境に限られる。** **一方で、有効にしている環境では認証を要しない** （CVSS の PR:N）。 **なお本記録の確認時点（2026年10月5日）で、 本件は CISA の KEV カタログには収載されていない**

この勧告の初版は2026年5月25日に出ていました。 つまり、悪用の報告は修正の公開から120日後です。

欠陥の内容を、NVD の記述のまま引用します。 「Roundcube Webmail 1.6.16 より前の 1.6.x および 1.7.1 より前の 1.7.x は、preg_replace() のバックスラッシュのエスケープの回り込みを通じて、virtuser_query プラグインに認証前の SQL インジェクションを持つ」（原文英語）。

CVSS v3.1 は 8.1（High）、ベクタはAV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H です。

ベクタの読み方を2点だけ押さえます（本記録の整理）。

  • PR:N（権限不要） — 認証を要しません。 プラグインが認証前のユーザ名の照会を扱うためです。
  • AC:H（攻撃条件の複雑度・高） — 条件は自明ではありません。 「1回の HTTP リクエストで」と書いている二次情報もありますが、CVSS の評価は複雑度を高と置いています（本記録はこの食い違いを discrepancies に記録しました）。

原因は実装の細部にあります。 Roundcube のコミットメッセージは「virtuser_query プラグインにおける preg_replace のバックスラッシュのエスケープの回り込みによる認証前 SQLインジェクションを修正する」（原文英語）です。

コミットが変更しているのはplugins/virtuser_query/virtuser_query.php の4つの関数（user2email / email2user / user2host / alias2user）で、いずれも preg_replace() を str_replace() に置き換えています。

元のコードは、問い合わせ文中の %u / %m をpreg_replace() で値に差し替えていました。 preg_replace() は置換文字列の中のバックスラッシュをエスケープ列として解釈します——そのため、バックスラッシュを含む入力を与えると、プラグインが仕掛けていたエスケープを回り込めました。

本記録がこの事案を記録する理由は、2つあります（本記録の判断）。

1つめ。該当判定が版番号だけでは決まりません。 影響を受けるのは virtuser_query プラグインを有効にしている環境だけです。 「Roundcube を使っているか」ではなく「そのプラグインを有効にしているか」を見ないと、自組織が該当するかが分かりません。

2つめ。120日という数字です。 修正は出ていました。 プロジェクトは「本番稼働中の全てのインストールを更新することを強く勧める」と書いていました。 それでも悪用が始まったときに未更新の環境が残っていた。 本記録はこれを「脆弱性の問題」ではなく「更新されない Web メールが残る構造の問題」として読みます。

なお、本記録の確認時点（2026年10月5日）で、本件は CISA の KEV カタログには収載されていません。 KEV を更新の起点にしている組織では、本件は起点に乗らないことになります（本記録の指摘）。

原因は `preg_replace()` が置換文字列のバックスラッシュを解釈する性質であり、同じ誤りが4か所に複製されていた原因・手口出典 [1] [5]

欠陥の中身を、コミットの内容にもとづいて書きます。

virtuser_query プラグインは、ユーザ名とメールアドレスのデータベース照会を行います。 問い合わせ文には %u（ユーザ名）と %m（ドメイン）という差し込みの印が書かれており、実行時にこれを実際の値へ置き換えていました。

その置き換えに preg_replace() が使われていました。

置換前: ... WHERE user = '%u' ...
置換の実装: preg_replace('/%u/', $値, $問い合わせ文)

問題は、preg_replace() が置換文字列の中のバックスラッシュをエスケープ列として解釈することです（NVD とコミットメッセージの記述）。

プラグインは値をエスケープしてから差し込んでいましたが、バックスラッシュを含む入力を与えると、そのエスケープを回り込めました。

修正は、preg_replace() を str_replace() に替えることでした。

置換の方法 置換文字列の解釈
修正前 preg_replace() 正規表現として解釈される（バックスラッシュが効く）
修正後 str_replace() 文字列としてそのまま置かれる

本記録の読みでは、これは「エスケープの実装を直した」のではなく「エスケープを要する経路そのものを無くした」修正です。 後者のほうが安全側です——エスケープの実装を直すと、次に別の回り込みが見つかる余地が残ります。

コミットが変更したのは、同じファイルの4つの関数です。

同じ誤った書き方が4か所に複製されていました。

自組織のコードに引き写すときの教訓はここです（本記録の判断）。1か所で見つけた欠陥は、同じファイル・同じプロジェクト内の同じ書き方をすべて探す。 本件のように、置換の実装が複数の照会関数にコピーされている形は珍しくありません。

具体的な探し方としては、「問い合わせ文を文字列の置換で組み立てている箇所」を一括で探すのが実際的です（本記録の提案）。preg_replace に限りません——sprintf・文字列の連結・テンプレートの差し込みも同じ性質を持ちます。

影響を限定できた更新後に、同じデータベースに置いている資格情報の入れ替えを検討する（露出したと仮定した場合の対処を決めておく）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**Roundcube は、8件の脆弱性を文章で列挙し、 「本番稼働中の全てのインストールを更新することを強く勧める」と 述べた一方、CVE 番号・CVSS 値・深刻度の区分のいずれも 公表に含めなかった。** **oss-security の投稿も「いつものとおり、CVE 番号は公表には 含まれていない」と述べ、CVE の対応は Debian の セキュリティトラッカーを参照するよう案内している**（原文英語）。部分的に機能**評価は本記録の判断である。** **機能した点**——**①修正を8件まとめて公開し、 「本番稼働中の全てのインストールを更新することを強く勧める」と 明確に述べた。 ②脆弱性の内容を具体的に列挙しており、 どの機能が影響を受けるかが読み取れる。 ③修正コミットが公開されており、 本記録のように前提条件（プラグインの有効・無効）を 自分で確認できる。** **不十分な点**——**①CVE 番号と深刻度の区分が無く、 利用側の脆弱性管理の仕組みに乗らない。 ②「認証前」の欠陥が2件含まれていたことが、 列挙の中では他の6件と同じ重みで並んでいる** ——**更新の緊急度を判断する材料として弱い**（本記録の評価）。 **留保**——**オープンソースのプロジェクトであり、 番号の割り当てや深刻度の評価に割ける資源は限られる。 本記録はこれを批判としてではなく、 利用側が前提として織り込むべき条件として記録する。**
**カナダ・サイバーセキュリティセンターは、 5月25日の勧告を9月21日に更新し、実環境での悪用を記載した。** **根拠は「公開情報による報告」とされており、 悪用の手口・観測件数・標的は記載されていない。**部分的に機能**評価は本記録の判断である。** **機能した点**——**実環境での悪用を公的な文書に記載したのは、 本記録が確認した範囲でこの当局のみである。** **CISA の KEV には収載されていないため、 この追記が無ければ本件は「修正済みの古い脆弱性」として 埋もれていた可能性がある。** **不十分な点**——**①悪用の根拠（誰の、どの報告か）が示されておらず、 利用側が確度を評価できない。 ②手口が示されないため、既に悪用された環境が 自分の被害を確認する手段を持てない。** **留保**——**当局が第三者の報告を根拠に注意喚起を出す場合、 出所を示せない事情があり得る。本記録はその有無を確認していない。**
CISO・経営層への示唆
  • **KEV への収載を更新の起点にしていると、本件は起点に乗らない**
    **本記録の確認時点（2026年10月5日）で、 CVE-2026-48842 は CISA の KEV カタログに収載されていない。** **実環境での悪用を記載しているのは、 カナダ・サイバーセキュリティセンターのみである。** **KEV は米国の連邦機関への指示を根拠に持つ仕組みであり、 世界中の脆弱性を網羅する一覧ではない**（本記録の指摘）。 **「KEV に入ったら優先する」という運用は分かりやすいが、 入らない悪用が存在する**
    取るべき行動 **悪用情報の参照先を KEV の1本に絞らず、 少なくとも2本目を運用に入れる。** **具体的には、使っている製品に関する勧告を出している当局 （カナダ・サイバーセキュリティセンター、英 NCSC、JPCERT/CC、 各国の CERT）のうち、自組織の製品構成に当たるものを選ぶ。** **選んだら「誰が読み、誰が自社該当を判定するか」を決める** ——**購読先だけ増やしても受信箱に溜まる**
  • **「使っていることを把握していない Web メール」が 本件の最大の母数である**
    **本件の該当判定には、版番号と有効なプラグインの確認が要る。** **しかしその前に「自組織のどこで Roundcube が動いているか」が 分からなければ、確認にたどり着けない**（本記録の判断）。 **Roundcube はホスティング事業者が提供する Web メールとして、 また部門が独自に立てたサーバとして入っていることがある。** **修正は2026年5月24日に出ていたのに、 120日後の悪用の時点で未更新の環境が残っていた** ——**その多くは「管理されていなかった」ものと考えられる** （本記録の推定）
    取るべき行動 **自組織のドメインで提供されているメール関連のサービスについて、 ①誰が運用しているか（自社／ホスティング／部門）、 ②製品と版番号、③インターネットからの到達範囲の3項目を 棚卸しする。** **ホスティング事業者が運用しているものについては、 更新の責任分担と適用の時期を契約または問い合わせで確認する** ——**「事業者がやっているはず」を確認せずに前提にしない**
  • **CVE 番号が付かない公表の作法を、 脆弱性管理の前提として織り込む**
    **Roundcube の公表には CVE 番号・CVSS 値・深刻度の区分が 含まれていない。** **oss-security の投稿も「いつものとおり、CVE 番号は公表には 含まれていない」と述べ、CVE の対応は Debian の セキュリティトラッカーを参照するよう案内している**（原文英語）。 **多くの組織は CVE 番号を起点に対応の期限を管理している** ——**番号が付かないまま公表されると、台帳に載らず期限も付かない** （本記録の評価）。 **オープンソースのプロジェクトでは、 これは例外ではなく一般的な作法である**
    取るべき行動 **使っているオープンソース製品について、 CVE 番号ではなく「公開されている最新版」を起点にした 確認の仕組みに切り替える。** **具体的には、製品ごとにリリースの通知 （GitHub のリリース購読・プロジェクトのメーリングリスト）を 受け取り、「使っている版」と「最新版」の差を定期的に突き合わせる。** **この形なら、番号が付いていなくても漏れない**
  • **悪用の手口が公表されない事案では、 「痕跡を探す」を対応計画に入れない**
    **本件について公表されているのは 「公開情報による報告は、実環境で悪用されていることを示している」 の1文のみである。** **手口・観測件数・標的・観測の時期はいずれも公表されていない** （本記録の確認）。 **ペイロードの形が分からなければ、 ログで何を検索すべきかが決まらない**（本記録の判断）。 **それでも「調査」を計画に入れると、 結論の出ない作業に時間を使い、更新が遅れる**
    取るべき行動 **悪用の報告があっても手口が公表されていない事案では、 対応計画を「更新する」「到達範囲を絞る」 「露出したと仮定した場合の対処を決める」の3つに限る。** **痕跡の調査は、手口が公表されてから着手する項目として 別に積む。** **なお「露出したと仮定した場合の対処」には、 同じデータベースに置いている資格情報の入れ替えが含まれる**
セキュリティ技術者への示唆
  • **Roundcube の版番号と有効なプラグインの一覧を、 インスタンスごとに出す**
    **該当判定の条件は3つある**—— **①1.6.16 より前または 1.7.1 より前であること、 ②`virtuser_query` プラグインを有効にしていること、 ③到達可能であること**（本記録の整理）。 **②はコミットの変更範囲から確認した前提条件であり、 NVD の記述には明示されていない** ——**版番号だけ見ると、該当しない環境を該当と判定してしまう**
    取るべき行動 **各インスタンスで、①版番号、②設定ファイルの `plugins` の一覧、 ③インターネットからの到達の有無を記録する。** **`virtuser_query` が一覧に入っているものを優先して更新する。** **入っていないものも更新対象には残す** ——**同じ更新で認証前の任意ファイル削除（7番目の欄）も 閉じられるためである**
  • **問い合わせ文を文字列の置換で組み立てている箇所を、 自組織のコードで一括して探す**
    **本件の原因は `preg_replace()` が置換文字列中の バックスラッシュをエスケープ列として解釈する性質である。** **修正は4つの関数で `preg_replace()` を `str_replace()` に置き換えることだった** ——**同じ誤った書き方が4か所に複製されていた** （本記録がコミットで確認）。 **本記録の評価**——**1か所で見つけた欠陥は、 同じプロジェクト内の同じ書き方をすべて探すべきである。** **置換による問い合わせ文の組み立ては、 照会の関数ごとにコピーされやすい**
    取るべき行動 **自組織のコードで、SQL 文を文字列の置換・連結・整形で 組み立てている箇所を一括で探す （`preg_replace` に限らず `sprintf`・文字列の連結・ テンプレートの差し込みも含める）。** **見つかった箇所を、プレースホルダ （プリペアドステートメント）に置き換える。** **置き換えられない箇所は、 「エスケープの実装に依存している箇所」として一覧に残す**
  • **「エスケープを直す」より「エスケープを要する経路を無くす」を選ぶ**
    **Roundcube の修正は、エスケープの実装を強化するのではなく、 正規表現の解釈を伴う置換（`preg_replace`）を 文字列の置換（`str_replace`）に替えることだった** （本記録がコミットで確認）。 **本記録の読み**——**エスケープの実装を直す方針では、 次に別の回り込みが見つかる余地が残る。** **解釈の層を1つ減らすほうが、後から破られにくい**
    取るべき行動 **自組織のコードで、入力を「エスケープしてから別の層へ渡す」 形になっている箇所を洗う （SQL・シェル・正規表現・HTML・LDAP）。** **各箇所について「解釈の層を減らせないか」を検討する** ——**プレースホルダ、引数の配列渡し、 正規表現を使わない文字列操作への置き換えなど。** **減らせない箇所は、その理由を記録に残す**
  • **Roundcube が使うデータベース利用者の権限を、 必要なテーブルと操作に絞る**
    **SQL インジェクションが成立したときの影響の範囲は、 アプリケーションが使うデータベース利用者の権限で決まる** （本記録の整理）。 **CVSS は機密性・完全性・可用性のいずれも「高」と 評価している（`C:H/I:H/A:H`）が、 これは一般的な評価であり、 権限を絞った環境では実際の影響が小さくなる余地がある** （本記録の評価）
    取るべき行動 **Roundcube が接続するデータベース利用者の権限を確認し、 ①他のアプリケーションのデータベースへ到達できないか、 ②`FILE` やストアドプロシージャの実行など 不要な権限が付いていないかを点検する。** **付いていれば外す。** **可能であれば、照会用と管理用（スキーマの変更）の 利用者を分ける**
