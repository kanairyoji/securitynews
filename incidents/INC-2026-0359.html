INC-2026-0359集英社ハピコミュに不正アクセス

集英社のブロガー情報管理システム「HAPPY PLUS COMMUNITY」が2026年9月9日に2度の不正アクセスを受け、ブロガー2,835名の個人情報・案件情報630件・送信メール情報1万1,237件・取引先一覧1万780件が漏洩した——CMS の設定不備に起因する API 認証情報を狙った攻撃で特権ユーザーが不正に作成され、侵害中に100名へテンプレートメール3通が送信されて受信者の通報で発覚した

不正アクセス・侵害初報のみ日本の組織が当事者設定不備認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年9月28日 最終更新: 2026年10月6日

株式会社集英社は2026年9月28日、ファッション誌メディアで活動するブロガーの情報管理・連絡用システム「HAPPY PLUS COMMUNITY（ハピコミュ）」が外部の第三者による不正アクセスを受け、個人情報が漏洩したと公表した。

漏洩したのは、登録ブロガー2,835名の氏名・メールアドレス・住所・電話番号・生年月日・性別・職業・プロフィール情報および画像・SNS アカウント・フォロワー数・結婚状況・子の有無・身長・肌タイプなどの登録情報（2,835件）。あわせて案件情報630件、同システムから送信したすべてのメール情報1万1,237件、取引先一覧1万780件（会社名は全件、メールアドレス26件、電話番号113件）も対象である。対象媒体は non-no、MORE、MAQUIA、LEE、SPUR、BAILA、Marisol、éclat の8誌にわたる。

原因は明確に示されている。利用している CMS の設定の不備に起因して API 認証情報を狙った攻撃を受け、特権ユーザーアカウントが不正に作成され、API リクエストを繰り返し実行された。

発覚の経路がこの事案の特徴である。侵害は2026年9月9日の0時45分〜1時25分と13時42分〜16時46分の2度にわたり、その最中に100名のメールアドレス宛へ、同システムのテンプレートを利用したメールが計3通送信された。14時53分、そのメールを受信したユーザーからの通報で発覚した。自社の監視ではなく、攻撃者が送った迷惑メールの受信者が気づいた。

漏れた項目には身長・肌タイプ・結婚状況・子の有無が含まれる。これは「連絡先の漏えい」ではなく、本人の身体と家族構成に関する記述が、顔と名前と住所に紐づいた状態で外部に出た事案である。読者は、自社が業務委託先・社外協力者について保持している情報の中身を点検する材料として読める。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

第三者が「HAPPY PLUS COMMUNITY」の利用する CMS の設定不備に起因して API 認証情報を狙った攻撃を行い、 特権ユーザーアカウントを不正に作成した。その上で API リクエストを繰り返し実行し、 登録ブロガー2,835名の個人情報・案件情報630件・送信メール情報1万1,237件・取引先一覧1万780件を取得した。 侵害は2026年9月9日の0時45分〜1時25分と13時42分〜16時46分の2回。 2回目の最中に同システムのテンプレートで100名へメール3通が送信され、受信者の通報（14時53分）で発覚した

    根拠: 集英社の公表（「利用している CMS の設定の不備に起因する API 認証情報を狙った攻撃を受け」）
  2. 2. 権限昇格disclosed[1]
    奪取した API 認証情報を用いて、**特権ユーザーアカウントが不正に作成された**。 作成されたアカウントの数と、API 経由で特権アカウントを作成できた理由は公表されていない
    根拠: 集英社の公表（「特権ユーザーアカウントが不正に作成され」）
  3. 3. 収集disclosed[1]
    不正に作成した特権ユーザーで**API リクエストを繰り返し実行**し、 システム内のデータを閲覧・取得した。対象はブロガー2,835名分の登録情報、案件情報630件、 送信メール情報1万1,237件（システムから送信したすべて）、取引先一覧1万780件である
    根拠: 集英社の公表（「API リクエストを繰り返し実行されたことにより、情報が漏洩した」）
  4. 4. 影響（暗号化・破壊・改ざん）disclosed[1]

    根拠: 集英社の公表（「この時間内に100名のメールアドレス宛に、本システムのテンプレートを利用したメールが合計3通送信された」）

    根拠: 集英社の公表（漏洩の判断と件数の特定）

攻撃者が送った迷惑メールの受信者が気づいた——自社の監視では捉えていない発覚の端緒出典 [1]

発覚の経路は公表文にはっきり書かれている。侵害中に攻撃者がシステムのテンプレートを使って100名へメールを3通送り、それを受け取ったユーザーが14時53分に通報した。

ここから読める構図は次のとおりである（本記録の評価）。

  • データの読み出し自体は検知されていない。 1度目の侵害（0時45分〜1時25分）は約40分続いたが、通報があったのは約13時間後の2度目の侵害中である。API リクエストの異常な繰り返しも、特権ユーザーの不正作成も、警報には結びついていない
  • 気づけたのは、攻撃者が「外に出る行動」を取ったからである。情報を読むだけなら外部の誰にも見えない。メールを送った瞬間に、システムの外にいる100名が目撃者になった
  • 通報は偶然に依存している。 受信者が「集英社のシステムから来た見覚えのないメール」を不審と判断し、連絡先を探して報告する、という3段階が成立した。どれか1つが欠ければ発覚はさらに遅れた
  • 集英社はその後不正検知設定を強化したと述べている。強化が必要だったという事実が、侵害時点の検知能力を物語っている

日本の組織にとっての含意は、外部の協力者・取引先を扱うシステムは「社外の人が見ている」という性質を検知の資産として使えることである。社外向けシステムからの送信は、社内システムの異常よりも早く外部から指摘されうる。ただしそれは運に任せる話であり、通報を受け取る窓口と初動の手順が無ければ機能しない。

漏れたのは身長・肌タイプ・結婚状況・子の有無——「連絡先の漏えい」として扱えない評価・解釈出典 [1]

登録項目の一覧は、通常の会員情報の漏えいとは性質が違う。

  • 身体に関する記述 — 身長、肌タイプ
  • 家族に関する記述 — 結婚状況、子の有無
  • 本人を特定する情報 — 氏名、住所、電話番号、生年月日、メールアドレス、プロフィール画像
  • 公開活動に紐づく情報 — SNS アカウント、フォロワー数、職業

これらが同一の個人別画面に揃った状態で漏れている。さらに案件情報630件（どの撮影・イベントに関わったか）と送信メール情報1万1,237件（編集部とのやり取り）が加わる。

本記録はこれを次のように評価する。

  • 対象は「顧客」ではなく「名前と顔を出して活動している個人」である。 SNS アカウントとフォロワー数が揃っているため、漏れた情報と公開されている人物が容易に結びつく。なりすまし・つきまとい・嫌がらせの材料として直接使える
  • 住所と家族構成の組み合わせは、身体的な危険につながりうる。「子どもがいる」「この住所に住んでいる」「この顔・この名前」が揃うことの意味は、メールアドレスの漏えいとは別の次元にある
  • 案件情報と過去のメールは、行動の予測を可能にする。いつどこで撮影に参加したか、編集部とどうやり取りしたかが分かれば、本人や編集部を装った連絡が成立しやすくなる
  • 組織内の「業務上の必要」で集めた項目が、漏えい時のリスクを決める。肌タイプや身長は美容・ファッション媒体の案件選定には合理的な項目である。だが保持し続ける必要があったかは別の問題で、集めた理由の正当性は、漏えいしたときの被害を軽くしない

社外協力者・業務委託先・取材対象を管理するシステムを持つ組織は、この項目一覧を自社の登録フォームと突き合わせる価値がある。

まず開発ベンダーに調査を依頼して不正アカウント削除・設定変更を行い、 その後さらなる被害が無いことを確認するため外部会社によるフォレンジック調査を実施した部分的に機能本記録の作成者の評価である。初動を開発ベンダーに任せて速さを取り、 独立した確認を外部会社に委ねるという二段構えは合理的である。 ただし**原因の特定が開発ベンダーの調査結果に基づくのか、外部会社の調査に基づくのかは 公表されていない**。設定不備という原因が誰の判断によるものかは、評価に影響する

CISO・経営層への示唆
  • 社外協力者を管理するシステムの登録項目を、経営として一度目で見る。身体・家族に関する項目は漏えい時の性質が違う
    本件では身長・肌タイプ・結婚状況・子の有無が、氏名・住所・電話番号・プロフィール画像・ SNS アカウントと同じ画面に揃った状態で漏れた。対象は名前と顔を出して活動する個人である
    取るべき行動 社外協力者・取材対象・業務委託先を管理するシステムの**登録項目一覧を印字して確認する**。 各項目に「なぜ必要か」「いつまで保持するか」を書かせ、答えられない項目を削除する。 削除の判断を情報システム部門に委ねず、事業責任者に行わせる
  • 「気づけたのは外部からの通報だった」を事故報告の必須項目にする。発覚経路は検知能力の通信簿である
    本件は侵害中に攻撃者が送ったメールの受信者が14時53分に通報して発覚した。 1度目の侵害（約40分）も、特権ユーザーの不正作成も、API の大量呼び出しも警報を上げていない
    取るべき行動 インシデントの事後レビューで**発覚経路を「自社監視／外部通報／本人申告／報道」に分類して記録**し、 外部通報が端緒だった件数を年次で経営に報告する。この比率が下がらない限り、 監視への投資は足りていないと判断する
  • 社外の人から不審を報告される窓口を、平時に作って告知しておく
    本件の発覚は、受信者が「集英社のシステムから来た見覚えのないメール」を不審と判断し、 連絡先を探して報告するという3段階が成立した結果である
    取るべき行動 協力者・取引先・顧客が異常を報告できる窓口（メールアドレス・フォーム）を公開し、 受領から初動までの手順と時間目標を定める。報告してくれた相手への返答も手順に含める
  • 本人通知を公表より先に行うなら、通知に「その人の漏洩項目」を含める
    本件では媒体・個人により登録項目が異なるため、一律の公表文では各自の状況が分からない。 集英社は9月25日の個別通知に漏洩内容の詳細を含め、3日後に公表している
    取るべき行動 本人通知の雛形を「共通の説明」と「個別の漏洩項目」の2部構成で用意する。 個別部分を差し込めるよう、通知時点で項目単位の対象者リストを出せる状態にしておく
  • 初動を開発ベンダーに任せる場合、原因の判定は独立した第三者に確認させる
    本件の原因は「CMS の設定の不備」である。設定を構築・運用した側が自らの作業を調べる構図になりうる。 集英社は開発ベンダーの調査に加え、外部会社のフォレンジック調査を実施している
    取るべき行動 インシデント対応手順に「開発・運用ベンダーによる初動」と「独立した第三者による原因判定」を 分けて書く。どちらの調査結果を公表の根拠にするかも事前に決める
セキュリティ技術者への示唆
  • 特権ユーザーの作成・権限付与を即時警報の対象にする。API 経由の作成も含める
    本件では API 認証情報を使って特権ユーザーアカウントが不正に作成され、これが大量取得の前提になった
    取るべき行動 管理者権限の付与・管理者アカウントの新規作成を、経路（画面・API・バッチ）にかかわらず 即時通知する。あわせて管理者一覧を日次で自動取得し、台帳との差分を検出する。 可能なら**API 経由の管理者作成そのものを禁止**し、管理操作を別の認証経路に限定する
  • API の呼び出し回数と返却件数に利用者単位の上限を設け、超過で自動的に止める
    本件は「API リクエストを繰り返し実行された」ことで情報が漏洩した。 集英社は事後に不正検知設定を強化しており、侵害時は反復呼び出しが止まらなかった
    取るべき行動 API ごとに1分あたり・1日あたりの呼び出し上限と返却件数上限を設定し、 上限超過時はトークンを失効させる。上限値は正規の業務の実測値から決め、 例外が必要な処理は別経路・申請制にする
  • API 認証情報を設定ファイルや CMS の設定項目に平置きせず、秘密管理の仕組みに移して定期失効させる
    本件の起点は「CMS の設定の不備に起因する API 認証情報を狙った攻撃」である
    取るべき行動 CMS・アプリケーションが参照する認証情報を秘密管理サービスに移し、 有効期限を設けて自動更新する。設定の点検表を作り、 公開面から参照できる設定項目が無いかを定期的に外部視点で確認する
  • 「システムから送信したすべてのメール」を無期限に保持しない
    本件では送信メール情報1万1,237件が全量漏洩した。 過去の業務連絡は、宛先と内容の組としてなりすましの材料になる
    取るべき行動 送信履歴の保持期間を業務要件から決めて自動削除する。 監査のために必要な場合は、本文を除いたメタデータのみを残す
  • 社外向けシステムからの送信を監視点として使う。外へ出る行動は唯一外部から見える挙動である
    本件で唯一検知につながったのは、攻撃者が100名へテンプレートメールを3通送ったことである。 読み出しだけなら外部の誰にも見えなかった
    取るべき行動 システムからの外部宛送信について、件数・宛先数・使用テンプレート・送信時刻を記録し、 平常値から外れた送信（深夜・大量・想定外のテンプレート）で警報を上げる。 業務時間外の自動送信は既定で停止する
  • 侵害の時間帯を分単位で言えるだけのログを、API 単位で保持する
    集英社は侵害を0時45分〜1時25分、13時42分〜16時46分と分単位で示し、 漏洩件数を項目ごとに特定している。これはアクセス記録が残っていたことを示す（本記録の推定）
    取るべき行動 API のアクセスログに、呼び出し元・認証主体・対象リソース・返却件数を含めて90日以上保全する。 保全先はシステム本体と分離し、改変できないようにする
