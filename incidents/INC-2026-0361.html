INC-2026-0361東産業の公式サイトが wp2shell で侵害

東産業（三重県四日市市）の公式サイトが WordPress の脆弱性を悪用した不正アクセスを受けた——同社は2026年9月14日、「WEBサイトの脆弱性を悪用した第三者による不正アクセスが確認された」と公表し、**不正アクセスの対象となる情報は「お問合せフォームを通じて取得したお客様情報のみ」**とした。脆弱性への対策は実施済みで、**発生時期と影響範囲は調査中**。公表は IPA の注意喚起を参照しているが、**公表本文に CVE 番号の記載は確認できなかった**。ScanNetSecurity は該当脆弱性を **CVE-2026-60137 / CVE-2026-63030（wp2shell）** と特定している。**不正アクセスを確認した日・侵害の期間・対象件数・流出の有無はいずれも公表されていない**

不正アクセス・侵害初報のみ日本の組織が当事者既知の脆弱性の悪用
初報: 2026年9月14日 最終更新: 2026年10月5日

株式会社東産業（三重県四日市市。水処理・インフラ整備・建物設備管理・住宅・浄化槽）は2026年9月14日、同社公式サイトがWEB サイトの脆弱性を悪用した第三者による不正アクセスを受けたことを公表しました。

公表の要点は3つです。

  1. 脆弱性への対策はすでに実施済み
  2. 不正アクセスの発生時期と影響範囲は現在調査中
  3. 不正アクセスの対象となる情報は「お問合せフォームを通じて取得したお客様情報のみ」

対象を絞って言い切った点が、この公表の特徴です。会員基盤や受発注の系統ではなく、問い合わせフォーム経由の情報に限ると明示しています。一方で、件数・情報の項目・侵害の期間・流出の有無はいずれも書かれていません。

脆弱性の側の事情は、公表よりはるかに詳しく分かっています。 ScanNetSecurity は該当脆弱性を wp2shell（CVE-2026-60137 / CVE-2026-63030）と特定しました。これは WordPress 本体の脆弱性2件を連鎖させて認証なしでコード実行に至るもので、IPA は2026年7月22日に注意喚起を出し、実証コードが公開済みであること、前日（7月21日）に CISA の悪用脆弱性カタログ（KEV）へ掲載されたことを示していました。修正版は 6.8.6 / 6.9.5 / 7.0.2 です。

つまり、「広く知られ、実証コードがあり、KEV にも載った本体の脆弱性」が、注意喚起から2か月近く経って実被害の公表として表に出たことになります（注意喚起7月22日 → 公表9月14日で54日。本記録の算出）。ただし侵害がいつ始まったかは公表されていないため、この54日が「放置の期間」だと読むことはできません（本記録の留保）。

日本の組織にとっての読みどころは、攻撃面が「コーポレートサイトの CMS」だったことです。問い合わせフォームは、事業の規模に関係なく個人情報が集まる一方で、資産管理の対象から外れやすい場所です。

問い合わせフォームは「規模に関係なく個人情報が集まるが、資産管理から外れやすい」場所である評価・解釈

以下は本記録の評価です。

本件で対象になったのは、会員基盤でも受発注の系統でもなく、コーポレートサイトの問い合わせフォーム経由の顧客情報でした。

問い合わせフォームには構造的な特徴があります。

  • 事業の規模に関係なく個人情報が集まる。 氏名・連絡先・相談内容が、相手が能動的に書いて送ってくる形で蓄積される
  • 保存先が CMS の中にあることが多い。 プラグインで受け付け、データベースや管理画面に溜める構成だと、CMS が落ちれば中身も落ちる
  • 資産管理の対象から外れやすい。 公開サイトは広報・マーケティングの管掌になりやすく、「個人情報を保持するシステム」の一覧に載っていないことがある
  • 消す動機が弱い。 対応が終わった問い合わせを消す運用は、明示的に決めていなければ行われない

東産業の公表が「問い合わせフォームを通じて取得したお客様情報のみ」と範囲を言い切れたことは、逆に言えばそこが情報の保持場所だったことを示します。

日本の組織が自社に当てはめるときの問いは、「コーポレートサイトの CMS に、いま何件の個人情報が入っているか即答できるか」です。

確認日も件数も改ざんの有無も書かれていない——利用者は自分の影響を判断できない未確定事項

このうち2つは、流出の有無が未確定でも書ける項目です（本記録の評価）。

  1. 侵害の可能性がある期間の目安 — 問い合わせフォームに情報を送った人が、自分が対象かを判断するための最低限の材料
  2. 保持していた情報の項目 — 氏名と連絡先だけなのか、相談内容（健康・家計・設備の状況など）まで含むのか

とくに2つめは、問い合わせフォームの場合に重要です。水処理・住宅設備という事業の性質上、問い合わせ本文には住居の状況や工事の希望が書かれている可能性がありますが、公表はこれに触れていません（本記録の観測であり、実際の項目は不明）。

wp2shell は本体の脆弱性なので、プラグイン管理だけでは守れない対策・注意喚起

対策そのものは単純です。WordPress 本体を 6.8.6 / 6.9.5 / 7.0.2 以降にすること。WordPress.org は該当バージョンに対して強制的な自動更新を有効化しています。

ただし、本件から引ける実務の論点は更新そのものではありません。

  • 「プラグインは管理しているが本体は見ていない」構成が実在する。 WordPress の脆弱性はプラグイン起因が多いため、監視の目がプラグインに寄りやすい。wp2shell は本体の脆弱性である
  • 自動更新が効いていないサイトが残る。 更新を止める設定、ファイル権限の都合、制作会社による固定、保守契約の切れたサイト——いずれも「自動更新が入るはず」という前提を崩す
  • コード実行に至った場合、更新だけでは終わらない。設置されたファイルや作られた管理者アカウントは更新で消えない。公表は「脆弱性への対策は実施済み」までで、ファイルの検査・再構築に触れていない
  • IPA の注意喚起と KEV 掲載が、実質的な期限だった。 7月21日の KEV 掲載・7月22日の注意喚起という公的な合図があり、「気づけなかった」とは言いにくい類の脆弱性である（本記録の評価）

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入公表されていない
**公表されていない。** 侵害の開始時期も確認日も示されていないため、 検知の機会があったかを判断する材料が無い。 一般には、未認証の REST API 呼び出しの急増と 不自然なクエリは Web アプリケーションファイアウォールやアクセスログで見える
侵入を防げたWordPress 本体を 6.8.6 / 6.9.5 / 7.0.2 以降へ更新し、自動更新が実際に効いているかを確認する　**本記録の評価による。** 修正版は2026年7月に出ていた。 「更新の方針がある」ことと「全サイトで効いている」ことは別で、 確認は**サイト単位でバージョンを拾う**以外に方法が無い
影響を限定できた公開サイトの前段に WAF を置き、未認証の REST API 経路を既定で絞る　**本記録の評価による。** 更新が間に合わない窓（実証コード公開から更新まで）を 埋める手段として機能しうる。本件で WAF があったかは公表されていない
実行公表されていない
**公表されていない。** 一般には、公開ディレクトリのファイル追加・更新の監視と、 PHP ファイルの改変検知が機会になる
検知できた公開ディレクトリのファイル変更を検知する（改変監視・デプロイ以外の書き込みを禁止する構成）　**本記録の評価による。** CMS は自身がファイルを書く前提で作られているため、 「書き込みを許す場所」を絞ることが実質的な防御線になる
収集公表されていない
**公表されていない。** 問い合わせデータへの参照が 管理画面経由・データベース直結のどちらであっても、 ログが残っていなければ事後に「見られたか」を言えない
影響を限定できた問い合わせフォームの受領データを CMS の外へ退避し、CMS 側には保持期間を定めて残さない　**本記録の評価による。** CMS が侵害された時に失う情報の量は、 **CMS が保持している量と等しい**。 受け付けたら外へ出す設計は、更新漏れの影響そのものを小さくする
検知できた問い合わせデータへの参照・書き出しを記録し、保存期間を確保する　**本記録の評価による。** 本件も「対象となる情報」までの表現にとどまっている。 **後から「見られていない」と言い切れるかは平時のログ設計で決まる**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**影響の範囲を「お問合せフォームを通じて取得したお客様情報のみ」と限定して公表した。** 一方で、**件数・情報の項目・侵害の期間・流出の有無は示さなかった**部分的に機能**本記録の作成者の評価である。** 取得経路まで特定して「のみ」と書いた点は、 自社のデータの持ち場所を把握していなければ書けないもので、評価できる。 一方で、**「侵害の可能性がある期間」と「保持していた情報の項目」は 流出の有無が未確定でも書ける項目**であり、ここが空いている
**公表に外部の専門機関による調査についての記述は無い。** 「現在調査を行っております」という表現のみである評価材料なし**本記録の作成者の評価である。** 実施の有無そのものが公表されていないため、 評価できる材料が無い
CISO・経営層への示唆
  • コーポレートサイトの CMS は「個人情報を保持するシステム」の一覧に載っているか
    本件で対象になったのは問い合わせフォーム経由の顧客情報である。 公開サイトは広報・マーケティングの管掌になりやすく、 **情報システム部門の資産台帳から外れることがある。** 台帳に載っていなければ、更新・監視・ログ保存の対象にもならない。
    取るべき行動 個人情報を保持するシステムの一覧に、**公開サイトとその CMS・ フォームのプラグイン・データの保存先**が載っているかを確認する。 載っていなければ追加し、**管掌部門と保守委託先を明記**する。
  • 「KEV 掲載」と「国の注意喚起」は、社内の更新期限として扱えているか
    本件で悪用されたとされる wp2shell は、2026年7月21日に CISA の 悪用脆弱性カタログ（KEV）に掲載され、翌22日に IPA が注意喚起を出していた。 **実証コードも公開されていた。** こうした公的な合図を社内の期限に変換する仕組みが無いと、 注意喚起は「読んだ」で終わる。
    取るべき行動 KEV 掲載と IPA 注意喚起を**対応期限の起点**として規程に書く （例: 公開サイトは48時間以内に影響判定、72時間以内に更新または緩和策）。 起点から期限までの実績を四半期で測り、間に合わなかった資産を名指しで残す。
  • 影響範囲を言い切るなら、その根拠を保てる状態を先に作る
    本件の公表は「対象はお問合せフォームを通じて取得したお客様情報のみ」と 範囲を限定した点が優れている。だが**その根拠（資産の把握かログか調査結果か）は 示されていない。**コード実行に至りうる脆弱性で範囲を限定するには、 外部から検証できる材料が要る。
    取るべき行動 公開サイトについて、**「保持している個人情報の種類と件数」を 平時から四半期ごとに記録**しておく。侵害時にこの記録がそのまま 公表の「範囲」の根拠になる。あわせて、範囲を限定して公表する場合の 社内承認の基準（どの証跡があれば「のみ」と書けるか）を決める。
  • 問い合わせデータの保持期間を決めていない組織は、侵害時の被害を自分で大きくしている
    問い合わせフォームのデータは、消す動機が弱いため溜まり続ける。 **侵害時に失う量は、保持している量と等しい。** 本件の件数は公表されていないが、保持期間の定めが無ければ サイトの運用年数ぶんが対象になりうる（本記録の評価）。
    取るべき行動 問い合わせデータの**保持期間（例: 対応完了後1年）と削除の実行者**を決め、 自動削除を仕掛ける。あわせて、受領データを CMS の外（別系統）へ 転送する構成に変える案を、次の改修計画に載せる。
セキュリティ技術者への示唆
  • WordPress 本体のバージョンを、サイト単位で実測して一覧にする
    wp2shell は**プラグインではなく本体**の脆弱性である。 プラグイン更新の運用があっても本体が古ければ防げない。 自動更新は既定で有効だが、更新の無効化設定・ファイル権限・ 制作会社による固定・保守契約切れで**効いていないサイトが残る。**
    取るべき行動 自社ドメイン配下の WordPress サイトを洗い出し、 **`/wp-includes/version.php` 相当のバージョンを実測**して一覧化する （管理画面の表示ではなく実測値を使う）。 6.8.6 / 6.9.5 / 7.0.2 より前のものを即日で更新対象に入れ、 自動更新が無効なサイトは理由を記録する。
  • コード実行に至りうる脆弱性で入られたなら、更新だけで復旧としない
    wp2shell はコード実行（Web シェルの設置を含む）に至る。 **更新は穴を閉じるが、すでに置かれたファイルや作られた管理者アカウントは消えない。** 本件の公表も「脆弱性への対策は実施済み」までで、 ファイルの検査・再構築に触れていない。
    取るべき行動 侵害が確認された公開サイトは、**更新に加えて ①公開ディレクトリの全ファイルを既知の正本と差分比較、 ②管理者・編集者アカウントの全件棚卸し、 ③データベース内の `wp_options` の自動読み込み項目と投稿内のスクリプトの検査、 ④全アカウントのパスワードとソルト（認証キー）の再発行**を手順に入れる。 差分比較ができる正本（Git 等）が無いサイトは**再構築**を既定にする。
  • 問い合わせフォームの保存先を把握し、CMS の中に溜めない
    フォームのプラグインは受領データをデータベースや 公開可能な位置のファイルに保存する構成を取ることがある。 **CMS が侵害された時点で、そこにある分はすべて射程に入る。**
    取るべき行動 使っているフォームのプラグインについて、**保存先（DB のテーブル名・ アップロードされた添付ファイルの置き場・メール送信のみか）を特定**する。 添付ファイルが公開ディレクトリ配下にある場合は配信を拒否する設定を入れ、 受領データは外部（メール・別系統のデータベース）へ出して CMS 側には残さない構成へ寄せる。
  • 公開サイトのログを「1年前の不審なアクセスを追える」保存期間にする
    本件は侵害の開始時期が公表されていない。 **侵害の開始時期を言えるかどうかは、アクセスログの保存期間で決まる。** 公開サイトは共用ホスティングやレンタルサーバのログ保存が 数週間に設定されていることがある。
    取るべき行動 公開サイトのアクセスログ・PHP のエラーログ・ WordPress の監査ログ（プラグイン）の保存期間を確認し、 **最低1年を目標に外部へ退避**する。退避先は同じサーバに置かない。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ コーポレートサイトを WordPress などの CMS で運用し、問い合わせフォームを同じ基盤に載せている本件の対象は問い合わせフォーム経由の顧客情報だった。 **CMS の侵害が、そのまま個人情報の侵害になる構成である。**
運用・監視□ WordPress の本体バージョンを、サイト単位で実測した一覧として持っていないwp2shell は本体の脆弱性である。 **プラグイン管理の運用があっても、本体が古ければ防げない。**
体制・契約□ 公開サイトの管掌が広報・マーケティングにあり、情報システム部門の資産台帳に載っていない台帳に無いシステムは、更新・監視・ログ保存のどれの対象にもならない。 **本件は「個人情報が集まるが管理の外にある」場所で起きた。**
データの保持□ 問い合わせフォームで受け取ったデータの保持期間を決めておらず、CMS 内に溜め続けている侵害時に失う量は保持している量と等しい。 **保持期間の定めが無ければ、運用年数ぶんが対象になりうる。**
運用・監視□ 公開サイトのアクセスログの保存期間が数か月以下で、外部へ退避していない本件は侵害の開始時期が公表されていない。 **「いつから入られたか」を言えるかはログの保存期間で決まる。**
委託・第三者部品□ 公開サイトの制作・保守を外部に委託しており、更新の責任分担が契約で明確になっていない自動更新の無効化や本体バージョンの固定は、 制作会社側の判断で行われていることがある。 **「更新されているはず」という前提が崩れる典型である。**
