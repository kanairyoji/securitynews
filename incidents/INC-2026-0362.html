INC-2026-0362GROWI に非公開ファイル読み取りの脆弱性

国産の社内 Wiki「GROWI」にアクセス制限不備の脆弱性（CVE-2026-100727）——**未認証の第三者が、非公開ページに添付されたファイルを読み取れる**。JVN#24352487 として2026年10月5日に公表された。影響は **v7.5.5 より前のすべてのバージョン**のうち、**ファイルアップロード方法の設定が「Local」の構成**で、Amazon S3 / GCS / Azure Blob Storage を使う構成は影響を受けない。修正版 v7.5.5 は `/uploads` プレフィックスへのアクセスを静的ファイル配信の前に 403 で拒否する。**開発者自身が JPCERT/CC に報告して調整を依頼した経路での公表**で、**悪用の有無・影響を受ける組織数・修正版の公開日はいずれも公表されていない**

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月5日 最終更新: 2026年10月5日

株式会社GROWI が提供する社内 Wiki・ナレッジ共有ソフトウェア GROWI に、アクセス制限不備の脆弱性（CVE-2026-100727 / CWE-552）が見つかりました。JPCERT/CC と IPA が運営する JVN で、2026年10月5日にJVN#24352487 として公表されています。

何が起きるか。 認証されていない第三者が、GROWI 内に保存されている非公開ページのファイルを読み取れます。 ログインも、ページの閲覧権限も要りません。

影響するのは「ファイルアップロード方法が Local」の構成だけです。

読みどころは、CVSS の数字が事案の重さを表していないことです。 CVSS v3.0 の 5.3 は「機密性への影響が Low」という評価ですが、これは1つのファイルが読めることの影響を測った値です。GROWI が置かれる場所——社内の設計書・議事録・手順書・認証情報のメモが集まるナレッジ基盤——を踏まえると、組織にとっての意味は数字より重くなります（本記録の評価）。

もう1つの読みどころは、公表の経路です。 JVN は「この脆弱性情報は、製品利用者への周知を目的に、開発者が JPCERT/CC に報告し、JPCERT/CC が開発者との調整を行いました」と記しています。外部の研究者が見つけて通報した形ではなく、開発者自身が周知を選んだ形です。自社製品の脆弱性を自ら JVN に載せる判断は、国内ベンダーの対応として記録に値します。

一方で、書かれていないこともあります。悪用の有無、影響を受ける組織の数、v7.5.5 がいつ公開されたか、そして修正版へ上げる前に取れる緩和策——いずれも示されていません。

**実際の攻撃事例は公表されていない。** 以下は JVN とベンダ告知に記載された 脆弱性の性質にもとづく**到達の経路**であり、観測された攻撃の再構成ではない。 悪用の有無そのものが公表されていない。

押さえるべきは CVSS ベクタの PR:N/UI:N です。権限が不要（PR:N）で、利用者の操作も不要（UI:N）。つまりログインしていない相手が、誰にも気づかれず単独で実行できる。攻撃の難易度は低い（AC:L）と評価されています。

原因は「ファイルの配信」と「ページの閲覧権限」が別経路だったこと原因・手口

ベンダ告知から読み取れる構造は次のとおりです。

  • GROWI の非公開ページに添付したファイルは、ファイルアップロード方法が「Local」のとき、サーバ上の /uploads 配下に置かれる
  • その /uploads 配下が静的ファイルとして配信されていた——つまり、添付元のページの閲覧権限を確認する経路を通らずに配信されていた
  • 修正版 v7.5.5 は、静的ファイル配信の前段で /uploads プレフィックスへのアクセスを 403 で拒否する形に変えた
  • ベンダ告知は、未認証者による直接のファイルアクセスに加えて、HTML ファイルがインラインで描画されることによるスクリプト実行のリスクにも触れている

これは、Web アプリケーションで繰り返し起きる型です（本記録の評価）。

アプリケーションは「ページを見る権限」で守りますが、ファイルの実体は別の経路（静的配信）で外に出ている。権限の判定がアプリケーション側にしか無く、配信経路がそれを通らなければ、権限は実質的に機能しません。

オブジェクトストレージ（S3 など）を使う構成が影響を受けないのは、ファイルの実体がアプリケーションのサーバの公開領域に置かれず、署名付き URL など別の到達制御を経るからです（本記録の評価）。

CVSS 5.3 は「1ファイルが読める」ことの評価で、ナレッジ基盤の中身は反映されない評価・解釈

以下は本記録の評価です。

CVSS v3.0 の 5.3 は、機密性への影響を Low（C:L） としています。これは「限定された情報が読める」という意味で、1つのファイルを取得できることへの評価です。

しかし、GROWI が置かれる場所を考えると、組織にとっての意味は変わります。

社内 Wiki・ナレッジ共有基盤に集まるのは、たとえば次のようなものです。

  • システムの構成図・ネットワーク図・サーバの一覧
  • 運用手順書（障害対応・バッチの再実行・権限付与の手順）
  • 会議の議事録（人事・取引・価格）
  • 「非公開ページだから」という前提で貼られた認証情報・接続情報のメモ
  • 添付された設計書・契約書・スクリーンショット

つまり、「非公開ページ」という区分そのものが、組織の中でいちばん機微な情報の置き場所になっていることがあります。

CVSS は脆弱性の性質を測る指標で、資産の価値は測りません。本件を「中程度」として後回しにするか、「社内の機微情報が未認証で読める」として即日対応にするかは、自社の GROWI に何が入っているかで決まります。

ここが、CVSS の数字だけで優先順位を付ける運用の限界です。

「自社は Local 構成か」を最初に確認する——影響の有無がそこで決まる対策・注意喚起

ベンダ告知は影響条件を明確にしています。

  • 影響する: ファイルアップロード方法の設定が「Local」
  • 影響しない: Amazon S3 / Google Cloud Storage / Azure Blob Storage

対応の順序は次のようになります（本記録の整理）。

  1. GROWI のバージョンを確認する。 v7.5.5 以降なら対応済み
  2. ファイルアップロード方法の設定を確認する。「Local」でなければ、本脆弱性の影響は受けない
  3. v7.5.5 へ更新する。 GitHub・Docker Hub から入手できる
  4. 更新できるまでの間、/uploads 配下への外部からの到達を前段（リバースプロキシ・WAF・ネットワーク）で遮断する——ただしこれは提供元が示した回避策ではない（本記録の評価。修正版が同じ経路を 403 で拒否していることから導いたもの）
  5. 過去のアクセスを確認する。 /uploads 配下への未認証のリクエストがアクセスログに残っていないかを見る

JVN の対策欄は「アップデートする」のみで、回避策の記載はありません。更新までの窓をどう埋めるかは、利用側で決める必要があります。

開発者自身が JPCERT/CC に報告して周知した——公表経路として記録に値する体制・ガバナンスの変更

JVN には次の一文があります。

この脆弱性情報は、製品利用者への周知を目的に、開発者が JPCERT/CC に報告し、JPCERT/CC が開発者との調整を行いました。

外部の研究者が見つけて通報し、調整の末に公表されたという通常の経路ではなく、開発者自身が JVN へ載せることを選んだ形です。

これが実務上どう違うか（本記録の評価）。

  • 利用者が気づける。 自社サイトの News だけに書けば、更新情報を追っていない利用者には届かない。JVN に載れば、脆弱性情報の収集の仕組み（JVN iPedia・CVE・各社の監視）に乗る
  • CVE 番号が付く。 資産管理・脆弱性管理のツールで突合できるようになる
  • ベンダステータスが残る。 JVN には「該当製品あり」としてベンダの確認が記録される
  • 影響条件が併記された。 ベンダ告知側で「Local 構成のみ」と限定したため、影響の無い利用者が不要な対応をしなくて済む

国産の業務ソフトウェアで、自社の脆弱性を自ら JVN に載せる判断は、日本の調達側（利用企業）が国産製品を評価するときの観点にもなります。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**開発者が自ら JPCERT/CC に報告し、JVN 経由で利用者に周知した。** あわせて自社サイトの News で、 **影響条件（ファイルアップロード方法が「Local」の場合）と 影響しない構成（S3 / GCS / Azure Blob）、修正の内容 （静的配信の前に `/uploads` への到達を 403 で拒否）を公開した**機能した**本記録の作成者の評価である。** 自社の News だけでは 更新情報を追っていない利用者に届かない。 JVN 経由にしたこと、修正版の入手先（GitHub・Docker Hub）まで示したこと、 影響条件を限定して「影響しない構成」を明示したことは、 利用者が**その日のうちに自社の影響を判定できる**形になっている。 ただし**回避策（更新までの窓をどう埋めるか）が示されていない**点は欠けている
CISO・経営層への示唆
  • 社内 Wiki は「資産の重要度」の評価が実態に追いついていないことが多い
    社内 Wiki は業務システムではなく「道具」として導入されるため、 重要度の分類が低く設定されがちである。 だが実際には、**システム構成図・運用手順・議事録・ 「非公開ページだから」という前提で貼られた認証情報**が集まる。 **情報の濃さと、台帳上の重要度がずれている。**
    取るべき行動 社内 Wiki・ナレッジ基盤を**個人情報・機密情報を保持するシステムとして 台帳に登録**し、重要度を実態に合わせて上げる。 あわせて「Wiki に貼ってはいけないもの」を定め、 **すでに貼られている認証情報を棚卸しして秘密管理の仕組みへ移す**。
  • CVSS の数字で優先順位を決める運用は、資産の価値を落とす
    本件の CVSS v3.0 は 5.3（機密性 Low）だが、これは **「1 ファイルが読めること」の評価**であり、 そのファイルが設計書なのか認証情報なのかは反映されない。 **CVSS だけで並べると、社内の機微情報が未認証で読める脆弱性が 「中程度」として後回しになる。**
    取るべき行動 脆弱性の優先順位付けの基準に、**CVSS に加えて 「その資産が保持している情報の種類」**を掛ける軸を入れる。 最低限、台帳で重要度が高い資産の脆弱性は **CVSS が中程度でも即日の影響判定の対象**にする。
  • 国産製品の選定基準に「脆弱性を JVN に載せるか」を入れられる
    本件は**開発者自身が JPCERT/CC に報告して JVN に載せた**。 自社サイトの告知だけなら、更新情報を追っていない利用者には届かない。 JVN に載れば CVE 番号が付き、**脆弱性管理の仕組みで機械的に拾える。** これは製品の品質ではなく**提供元の運用姿勢**の指標である。
    取るべき行動 業務ソフトウェアの選定・更新時のチェック項目に、 **「過去の脆弱性が JVN / CVE として公表されているか」 「影響条件と影響しない構成を明示しているか」**を加える。 既存の導入製品についても、同じ観点で振り返っておく。
  • 「社内向けだから外からは見えない」という前提を文書で確認する
    本件は**未認証で到達できること**が前提の脆弱性である。 社内 Wiki は在宅勤務や協業先との共有のために インターネットへ公開されている構成がありうるが、 **公開していること自体が担当者以外に共有されていないことがある。**
    取るべき行動 社内向けと認識しているシステムについて、 **インターネットから到達できるかを実測**し（外部からの疎通確認）、 公開している理由と制限（VPN・IP 制限・認証の前置）を文書に残す。 公開の必要が無いものは内側へ戻す。
セキュリティ技術者への示唆
  • まず「バージョン」と「ファイルアップロード方法の設定」の2つを確認する
    影響条件はこの2つで決まる。 **v7.5.5 以降なら対応済み。Local 以外（S3 / GCS / Azure Blob）なら影響を受けない。** 逆に言えば、この2つを確認しないまま緊急対応に入ると、 影響の無い環境に工数を使う。
    取るべき行動 社内の GROWI について**バージョンとファイルアップロード方法の設定を記録**し、 「v7.5.5 より前 かつ Local」に該当する環境を特定する。 該当するものを **v7.5.5 以降へ更新**（GitHub / Docker Hub）。 検証環境・停止中のインスタンス・部門が個別に立てたものを数え漏らさない。
  • 静的ファイルの配信経路が、アプリケーションの権限判定を通っているか確認する
    本件の原因は、**非公開ページの添付ファイルが ページの閲覧権限を確認せずに静的配信されていた**ことである。 これは GROWI 固有の問題ではなく、 **自社開発のアプリケーションでも同じ形で起きる型**である （アップロード先を公開ディレクトリに置く構成）。
    取るべき行動 自社で運用するアプリケーションについて、 **アップロードされたファイルの実体の置き場所**を洗い出す。 公開ディレクトリ配下にあるものは、 **①配信をアプリケーション経由にする（権限判定を通す）か、 ②オブジェクトストレージへ移して署名付き URL にする** のいずれかへ寄せる。推測しにくいファイル名は対策ではない。
  • 更新までの窓は前段で塞げるが、提供元の回避策ではないので検証してから入れる
    JVN の対策は「アップデートする」のみで、**回避策の記載が無い。** 修正版が `/uploads` プレフィックスへの到達を 403 で拒否していることから、 前段での遮断が同等の効果を持つと読めるが、 **アプリケーションが内部で同じ経路を使っていれば表示が壊れる。**
    取るべき行動 即時に更新できない環境では、リバースプロキシ・WAF で **外部からの `/uploads` 配下へのリクエストを拒否**する設定を 検証環境で試し、画像・添付の表示が壊れないことを確認してから本番へ入れる。 入れた設定は**更新後に外す**ことを作業票に残す。
  • 「過去に読まれたか」を調べられるログがあるかを、いま確認する
    この脆弱性が**いつの版から存在していたかは公表されていない。** 影響範囲は「v7.5.5 より前のすべてのバージョン」であり、 さかのぼる期間の目安が無い。 **さかのぼれる期間は、ログの保存期間を超えない。**
    取るべき行動 GROWI の前段にある Web サーバ・リバースプロキシのアクセスログを確認し、 **`/uploads` 配下への未認証のリクエスト**を検索する。 ログが残っていない、または保存期間が短い場合は、 **その事実を記録**しておく（後から「無かった」と言えない根拠になる）。 あわせて保存期間を延長する。

観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ GROWI を自社で運用しており、バージョンが v7.5.5 より前である影響範囲は「v7.5.5 より前のすべてのバージョン」である。 **まずバージョンが条件を満たすかで切り分かる。**

認証・認可□ 非公開ページの権限設定を、機微情報の保管の根拠にしている本件は**非公開ページの権限が、添付ファイルの配信経路では 機能していなかった**事案である。 区分だけを根拠にしている情報は、そのまま露出する。
データの保持□ 社内 Wiki に認証情報・接続情報・構成図を添付ファイルとして置いている読み取られるのは**添付ファイル**である。 本文ではなく添付に機微情報が寄っている組織ほど影響が大きい。
システム構成□ 社内 Wiki をインターネットから到達できる位置に置いている本件は**未認証の第三者**が到達できることが前提である。 到達範囲が社内に限られていれば悪用の母集団は狭まる。
運用・監視□ 自社開発のアプリケーションで、アップロードされたファイルを公開ディレクトリ配下に置いている本件と同じ型（**権限判定を通らない静的配信**）が 自社の実装でも起きうる。GROWI を使っていなくても確認の対象になる。
