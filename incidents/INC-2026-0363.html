ホスティング管理ツール「cPanel & WHM」にクリティカル3件——**CVE-2026-93698 は Multilang adminbin の入力検証不備で、低権限のアカウントから root 権限で任意の OS コマンドを実行できる**（CVSS v3.0 9.9）。残る CVE-2026-93697（WHM の Mass Modify Accounts）と CVE-2026-93029（WHM の Manage SSL Hosts）はいずれも格納型 XSS で、**権限を持たない利用者が WHM 管理者のセッション上で操作できる**（同 9.0）。WebPros International は現地時間2026年9月29日に修正版を公開した。**サーバ上の全アカウント・全サイト・全データベースの制御が射程に入る一方、悪用の観測・実証コードの公開は報告されていない**

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備

読みどころは、攻撃に必要な権限の低さです。 CVE-2026-93698 のベクタは AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H。PR:L（低い権限が必要）とは、そのサーバ上の cPanel アカウントを1つ持っていれば足りるという意味です（本記録の評価）。共用ホスティングでは、利用者の1人がこれに当たります。そして S:C（スコープの変更）は、権限の境界を越えてサーバ全体に影響が及ぶことを示します。

つまり、共用サーバの1契約者（あるいは侵害された1契約者）から、サーバ上の全アカウント・全サイト・全データベースが射程に入ります。

残る2件の格納型 XSS も PR:L ですが、UI:R（利用者の操作が必要）です。WHM 管理者がその画面を開いたときに実行される——つまり、攻撃者は仕込んで管理者の操作を待つ形になります。

一方で、書かれていないこともあります。悪用の観測、実証コードの公開、影響を受けるサーバの数、そして日本国内の利用状況と影響——いずれも公表されていません。

CVE-2026-93698 は「root で動く部品に入力を渡す」構造そのものに起因する原因・手口

CVE の説明は1行です。

入力検証が不十分なため、Multilang adminbin 経由で任意のコマンドを実行できる。（原文英語）

adminbin は、一般利用者の操作を特権側で代行する仕組みです（本記録の評価）。cPanel の利用者は root を持ちませんが、一部の操作（設定の変更など）はシステム側の権限を必要とします。そのため、利用者からの要求を受けて root 権限で実行する部品が置かれます。

この構造では、部品の入力検証が唯一の境界になります。検証を抜けた入力は、そのまま root の権限で実行されます。CVSS の PR:L / S:C / C:H / I:H / A:H、そして 9.9 という値は、この「境界が1枚しかない」構造を反映した評価です。

Security NEXT の記述はこれを端的に示しています。

root 権限で任意の OS コマンドを実行されるおそれがあり、管理するアカウントやウェブサイト、データベースなどの制御を奪われるおそれがある

残る2件は格納型 XSS です。権限を持たない利用者が投入した内容が、WHM（管理者の画面）に保存され、管理者が画面を開いたときにそのセッション上で実行されます。 Security NEXT は CVE-2026-93697 について「権限を持たないアカウントの利用者が、WHM 管理者のセッション上でスクリプトを実行し、管理者として操作を行うことが可能となる」と書いています。

XSS は「ブラウザの話」として軽く扱われがちですが、管理画面の XSS は管理者権限の乗っ取りです（本記録の評価）。だからこそ CVSS でも 9.0 が付いています。

共用ホスティングでは「利用者の1人」が攻撃者になりうる評価・解釈

以下は本記録の評価です。

PR:L という条件は、一見すると緩和要因に見えます。「外部から誰でも攻撃できるわけではない」からです。しかし cPanel & WHM が置かれる場所を考えると、意味が変わります。

cPanel & WHM は共用ホスティングの管理基盤です。1台のサーバに多数の契約者（アカウント）が載る構成が一般的です。つまり、PR:L を満たす相手は次のような形で現れます。

  1. 悪意のある契約者。 低額の契約を1つ買えば、条件を満たす
  2. 侵害された契約者のアカウント。 他のサイトの脆弱性や認証情報の使い回しで1アカウントが取られれば、そこが起点になる
  3. リセラー配下の利用者。 権限の階層が深いほど、「低い権限」を持つ人数は増える

そして S:C により、影響は1アカウントに留まりません。 root でのコマンド実行が成立すれば、同一サーバ上の他の契約者のサイト・データベース・メールが射程に入ります。

ホスティング事業者にとっては、1件の侵害が「契約者全員への説明責任」に変わる構造です。そして契約者（サイトの運営者）側からすると、自社サイトに脆弱性が無くても、同じサーバの隣人と管理基盤の更新状況に依存していることになります。

これは利用側の統制が効かない依存です。自社でサイトを持つ日本の組織が本件から引ける問いは、「自社サイトはどこに載っているか」「その管理基盤は誰がいつ更新するのか」です。

日本語の報道には3件目（Manage SSL Hosts）の記述が無い未確定事項

本件の情報の揃い方には偏りがあります。

Security NEXT の記事は、CVE-2026-93698 と CVE-2026-93697 を説明したうえで「のこる2件はいずれも格納型クロスサイトスクリプティング（XSS）の脆弱性」と述べ、CVE-2026-93029 がどの画面の脆弱性かには触れていません。記事の関連リンクも、CVE-2026-93698 と CVE-2026-93697 のアドバイザリ2本と、9月22日の別の脆弱性（CVE-2026-87900）で、CVE-2026-93029 のアドバイザリは挙がっていません。

本記録は脆弱性データベースの記載から、CVE-2026-93029 が WHM の「Manage SSL Hosts」インタフェースの格納型 XSS であることを補いました。

実務上の意味は小さくありません（本記録の評価）。対象の画面が分かれば、管理者が「その画面を開かない」運用で一時的に露出を下げられるか判断できます。画面名が不明なままでは、それもできません。

更新の優先順位は「系列の特定 → 更新 → 管理画面の露出の見直し」の順で付く対策・注意喚起

対応の順序は次のようになります（本記録の整理）。

  1. 自社が使っている系列とバージョンを特定する。 11.138 系・11.136 系・11.134 系・11.110 系で更新先が異なる。WP Squared を使っている場合は 11.138.1.13 以降
  2. 修正版へ更新する。 11.138.0.11 / 11.136.0.45 / 11.134.0.61 / 11.110.0.148 以降
  3. WHM（管理画面）の露出を見直す。 XSS の2件はUI:R——管理者がその画面を開くことが条件である。管理画面をインターネットから直接到達できる位置に置かない（VPN・IP 制限・踏み台の内側）ことは、本件に限らず XSS 全般の露出を下げる（本記録の評価）
  4. アカウントの棚卸し。 PR:L の母集団を減らす。使われていないアカウント・退会済みの契約・検証用に作ったアカウントを消す
  5. 過去の痕跡の確認。 いつの版から存在した不備かは公表されていないため、さかのぼる期間の目安が無い。少なくとも保存しているログの範囲で、adminbin への異常な呼び出しと root での予期しないコマンド実行を確認する

ホスティングを借りている側（サイトの運営者）にできることは限られます。管理基盤の更新は事業者側の作業です。できるのは、事業者に更新の状況を問い合わせることと、自社の cPanel アカウントの認証情報を再発行することです（本記録の評価）。

1週間前にも別のセキュリティリリースが出ている——更新の間隔が短い製品である背景・過去事例

Security NEXT の関連リンクには、本件（9月29日）の1週間前にあたる9月22日のセキュリティリリース（CVE-2026-87900「WP Toolkit のデータベース作成」の脆弱性）も挙がっています。本件とは別の脆弱性です。

ここから読めるのは、cPanel & WHM が「短い間隔でセキュリティリリースが出る製品」であるということです（本記録の評価）。

運用上の含意は2つあります。

  • 「四半期に1回まとめて更新する」運用では間に合わない。 2週間に2回のリリースがある製品を、四半期の窓で扱うことはできない
  • 自動更新の設定が実質的な防御線になる。 cPanel には更新の自動適用の仕組みがあるが、安定性の懸念から手動運用にしている事業者もありうる（本記録の推測。実態は公表資料では分からない）

製品ごとに「セキュリティリリースの頻度」を把握し、更新の運用をそれに合わせる——これが本件から引ける一般的な論点です。

判断評価評価の根拠と留保

CISO・経営層への示唆
  • 自社サイトが「誰の管理基盤の上に載っているか」を把握しているか
    本件はサイトの脆弱性ではなく、**サイトを載せている管理基盤**の脆弱性である。 共用ホスティングでは、**自社サイトに問題が無くても、 同じサーバの他の契約者と、基盤の更新状況に依存する。** これは利用側の統制が効かない依存である。
    取るべき行動 自社が運用する Web サイト（コーポレートサイト・採用サイト・ キャンペーンサイト・子会社のサイト）について、 **ホスティング先と管理基盤の種類（cPanel / Plesk / 自社構築 / クラウド）を 一覧にする。** 共用ホスティングに載っているものは、 **事業者に「セキュリティ更新の適用方針と実績」を問い合わせ**、 回答を記録に残す。
  • 製品ごとの「セキュリティリリースの頻度」に合わせて更新の運用を決める
    cPanel & WHM は本件（9月29日）の1週間前（9月22日）にも 別のセキュリティリリースを出している。 **2週間に2回のリリースがある製品を、四半期の更新窓で扱うことはできない。** 更新の運用が製品の実態に合っていなければ、常に窓が開いたままになる。
    取るべき行動 資産台帳に**「過去1年のセキュリティリリース回数」**の欄を作り、 製品ごとに記録する。回数が多い製品は **自動更新を既定にする**か、**週次の更新窓**を設ける。 手動運用にしている製品は、その理由と代替の緩和策を文書化する。
  • 共用基盤の侵害は「1件の技術対応」ではなく「契約者全員への説明」になる
    CVE-2026-93698 は CVSS ベクタに `S:C` を持ち、 **影響が権限の境界を越えてサーバ全体に及ぶ**と評価されている。 ホスティング事業者の立場では、1台の侵害が **その台に載る全契約者への通知・調査・補償の話**になる。
    取るべき行動 共用基盤・マルチテナントのサービスを提供している場合、 **「1台が侵害されたときの通知対象の洗い出し」を平時に手順化**する （テナント一覧の取得方法・連絡先の鮮度・通知文の雛形）。 年1回、実際に一覧を出して所要時間を測る。
  • 一次資料が機械的に取得できない製品は、脆弱性情報の収集に穴があく
    本件の提供元アドバイザリ（support.cpanel.net）は **自動取得を HTTP 403 で拒否する。** CVE 側に説明とベクタが載っているため最低限の情報は得られるが、 **提供元が示す回避策・悪用の有無は読めない。** 脆弱性情報を自動で集めている組織では、この差が見落としになる。
    取るべき行動 脆弱性情報の収集の仕組みについて、 **「提供元のアドバイザリ本文まで取れているか」を製品ごとに確認**する。 取れない製品は、**CVE / NVD / JVN のどれを代替の情報源にするか**を 決めて記録し、回避策が必要な局面では人が読みに行く手順にする。
セキュリティ技術者への示唆
  • まず「どの系列を使っているか」を確定させる——更新先が4通りある
    修正版は 11.138.0.11 / 11.136.0.45 / 11.134.0.61 / 11.110.0.148 の 4系列と WP Squared 11.138.1.13 に対して出ている。 **「最新版へ」では答えにならない。** 旧系列を使い続けている環境は、その系列の修正版へ上げる必要がある。
    取るべき行動 管理下の cPanel & WHM サーバの**系列とビルド番号を一覧にして実測**し、 各系列の修正版と比較する。 系列が古い（11.110 など）環境については、 **その系列の保守がいつまで続くかを確認**し、移行計画に載せる。
  • 管理画面（WHM）の露出を下げることが、XSS 2件の条件を崩す
    CVE-2026-93697 と CVE-2026-93029 はいずれも `UI:R`—— **WHM 管理者が該当画面（Mass Modify Accounts / Manage SSL Hosts）を 開くことが条件**である。 管理画面がインターネットから直接到達できる位置にあると、 仕込みと待ち受けの両方が成立しやすい。
    取るべき行動 WHM の待ち受けポートへの到達を、**管理用の送信元（VPN・踏み台・固定 IP）に 限定**する。リセラーや契約者が WHM を使う運用がある場合は、 **利用者を洗い出してから**適用する（そのまま絞ると業務が止まる）。
  • root を取られた後に信頼できるのは、サーバ外へ出したログとバックアップだけ
    CVE-2026-93698 は **root でのコマンド実行**に至る。 その後に残るログ・バックアップは、 **同じサーバ上にある限り改変されうる。** 本件はいつの版から存在した不備かも公表されていないため、 さかのぼる期間の目安も無い。
    取るべき行動 cPanel サーバの**認証ログ・adminbin 系の呼び出し・ WHM の操作ログを別系統（ログ収集基盤）へ転送**する。 契約者ごとのバックアップは、 **そのサーバから書き込み・削除ができない位置**に置く （一方向の転送・世代の保持）。
  • 低権限アカウントの棚卸しは、この種の脆弱性の前提条件に直接効く
    3件すべてが `PR:L`——**そのサーバ上の低い権限のアカウントが必要**である。 攻撃できる相手の数は、**そのサーバに存在するアカウントの数**に比例する。 使われていない契約・退会済みのアカウント・検証用に作ったものは、 そのまま攻撃面である。
    取るべき行動 cPanel アカウント・リセラーアカウント・WHM の副管理者を全件棚卸しし、 **最終ログイン日時で並べて未使用のものを削除**する。 残すアカウントには多要素認証を要求する。 棚卸しは四半期ごとに繰り返す。
