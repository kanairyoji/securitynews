INC-2026-0364デンマークCPRで880万人分流出

デンマークの全国民登録「中央個人登録（CPR）」で、民間企業に与えられていた正規の照会権限が悪用され、生存者・出国者・死亡者を含む約880万人分の氏名・住所・CPR 番号へ不正にアクセスされた——CPR 管理局は2026年10月2日夜に9月分の不規則な照会を検知し、当該企業のアクセスを遮断してデータ保護庁と警察へ届け出た。続報で企業は Pays ApS（オーデンセ。従業員2名）と判明し、同社の少なくとも3つのアカウント（管理者アカウントを含む）がパスワード「123456」を使っていたと報じられた。検知の端緒は請求額の異常だった

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因
初報: 2026年10月5日 最終更新: 2026年10月14日

デンマーク研究・教育・デジタル化省は2026年10月5日、同国の全国民登録である中央個人登録（Det Centrale Personregister: CPR）から、約880万人分の氏名・住所・CPR 番号へ第三者が不正にアクセスしたと公表しました。対象には国内に住む人だけでなく、出国した人と死亡した人も含まれ、氏名・住所の保護登録をしている人は含まれないとされています。

手口は CPR システムそのものへの侵入ではありません。公表は、加害者がデンマークの民間企業に与えられていた「CPR を照会する正規の権限」を悪用したと述べています。CPR 法 §38 は、正当な利益を持つ企業が、個人番号・生年月日・氏名などで特定した人物の情報を照会できると定めています。デンマークのデータ保護庁（Datatilsynet）は、有効な CPR 番号を突き止めることを狙った自動照会が非常に多数行われたものだと説明しています（The Record の報道による）。

CPR 管理局は2026年10月2日（金）夜に、9月に行われた不規則な照会活動を検知しました。週末の調査で約880万人分への不正アクセスを確認し、当該企業のアクセスを遮断、データ保護庁へ届け出、警察が捜査を開始しています。担当相のChristina Egelund（研究・教育・デジタル化担当）は「深刻な事案であり、だからこそ国会の産業・デジタル化委員会にも報告した」（原文デンマーク語）と述べ、CPR システムの包括的なセキュリティ点検を指示しました。

CPR は医療・銀行・納税・行政サービスの共通鍵として使われ、10桁の番号は生涯変わりません。登録総数は約1,100万人、デンマークの人口は約600万人強です。本記録は、国家の基幹登録を、そこへ接続する民間企業の権限経由で丸ごと列挙された事案として整理します。日本でも公的な本人確認情報に民間事業者が照会する仕組みがあり、「誰に照会を許したか」の管理と照会量の監視という同じ論点を持ちます。企業名・実行者・企業側の経緯は公表されていません。

2026年10月14日 続報反映（これまでに 2 回更新）更新履歴へ

    CPR 番号は 10桁で先頭が生年月日、医療・銀行・納税・行政サービスで共通に使われる。生涯変わらない設計のため、氏名・住所との組み合わせが一度外に出ると、本人が番号を変えて影響を打ち切ることができない。

    検知されたのは「侵入」ではなく「照会のしかた」——有効な CPR 番号を突き止める自動照会が多数行われた原因・手口出典 [1] [2]

    データ保護庁は本件を、有効な CPR 番号を突き止めることを狙った自動照会が非常に多数行われたものだと説明している（The Record の報道による）。CPR 番号は先頭6桁が生年月日で、続く4桁に規則性があるため、生年月日の範囲を決めれば候補を機械的に作れる。正規の照会口が「候補が有効かどうか」を返すなら、照会の繰り返しで有効な番号を割り出し、その氏名と住所を得られる（本記録の読み。照会 API の仕様は公表されていない）。

    つまり悪用されたのは脆弱性ではなく、設計どおりに動く正規の機能である。CPR 管理局が検知したのも、侵入の痕跡ではなく照会の量とパターンの異常だった。一方で、9月に行われた活動の検知が10月2日だった点は、この監視が「後から気づく」種類のものだったことを示している（本記録の評価）。

    • CPR 法 §38 の「正当な利益」として、どの範囲の照会が許されていたのか

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    判断評価評価の根拠と留保
    当該企業の CPR システムへのアクセスを遮断した部分的に機能本記録の作成者の評価である。即時の封じ込めとしては妥当だが、**攻撃面は「権限を持つ事業者の数」で 決まる**ため、1社の遮断では同型の再発を止められない。点検の範囲が制度に及ぶかが要点になる
    検知から3日（週末を挟んで翌営業日）に公表し、同時に国会委員会へ報告した機能した本記録の作成者の評価である。範囲（約880万人）・対象データ・手口の型（正規権限の悪用）・ 検知日を初報で示し、**保護登録者は含まれない**という除外条件まで明示した点を評価する
    個別通知の方針を示さず、sikkerdigital.dk での案内と相談窓口の時間延長（8時〜24時）で受けた評価材料なし本記録の作成者の評価である。通知の方針が公表されていないため、評価できる材料が無い
    CISO・経営層への示唆
    • 「自社が持つデータ」ではなく「自社が他社に与えた照会権限」を資産として棚卸しする
      本件で破られたのは CPR システムではなく、CPR を照会できる民間企業1社の権限だった。 登録側のセキュリティ投資とは独立に、接続先の数だけ入口が増える
      取るべき行動 自社のデータへ照会・参照できる外部主体（取引先・代理店・SaaS・API 利用者）を一覧化し、 各主体の認証方式・接続元制限・照会上限・監査の有無を表にする。 空欄が残る主体から順に、契約更新のタイミングで条件を追加する
    • 変更できない識別子を扱う業務は、漏えい時に「打ち切る手段が無い」前提で設計を見直す
      CPR 番号は生涯不変で、医療・銀行・納税の共通鍵として使われる。漏れた番号は将来のなりすましの 材料として残り続け、本人が差し替えて影響を止めることができない
      取るべき行動 自社が本人確認の根拠にしている識別子（マイナンバー・基礎年金番号・顧客番号・生年月日の組み合わせ）を 列挙し、**「その値を知っていること」だけで本人と認めている業務**を洗い出す。 該当する業務には追加の確認要素（書類・デバイス・コールバック）を入れる
    • インシデントの公表で「除外条件」まで書くと、読者は自分の立場を判断できる
      省の公表は対象を約880万人としたうえで、**氏名・住所の保護登録をしている人は含まれない**と明示した
      取るべき行動 自社の公表雛形に「対象に含まれる条件」と「含まれない条件」を並べて書く欄を設ける。 件数だけの公表は、本人が自分が対象かを判断できない
    • 監督官庁への届出と立法・監督機関への報告を、公表と同じ工程に組み込む
      CPR 管理局は検知から2日でデータ保護庁へ届け出、大臣は公表と同時に国会委員会へ報告したと述べている
      取るべき行動 インシデント対応手順に「規制当局への届出（期限つき）」「所管官庁・親会社・取締役会への報告」を 公表の前段として明記し、誰が何時間以内に出すかを決めておく
    セキュリティ技術者への示唆
    • 照会 API の防御は「侵入検知」ではなく「列挙検知」で設計する
      悪用されたのは脆弱性ではなく、設計どおりに動く正規の照会機能だった。 データ保護庁は「有効な CPR 番号を突き止めることを狙った自動照会が非常に多数」と説明している
      取るべき行動 照会系 API に、①単位時間あたりの照会数、②不一致（該当なし）の比率、③照会対象の分布の偏り、 ④同一利用者の累積件数の4つの指標を実装し、閾値超過で自動的に絞る（遮断ではなく段階的な減速でよい）。 **不一致率は列挙で跳ね上がるため、正規利用との区別に最も効く**
    • 識別子に生年月日などの推測可能な構造があるなら、照会は「候補の検証」に使えない作りにする
      CPR 番号は先頭6桁が生年月日で、候補を機械的に生成できる。正規の照会口が候補の有効性を返すなら、 繰り返しで有効な番号を割り出せる（本記録の読み）
      取るべき行動 存在しない識別子への応答を存在する場合と区別できない形にする（応答時間も含める）、 照会には識別子以外の照合項目を必須にする、1回の照会で返す項目を用途ごとに最小化する——の3点を点検する
    • 照会ログは「誰が何を照会したか」を後から人数単位で集計できる形で持つ
      CPR 管理局は9月の照会を10月に検知し、週末のうちに対象を約880万人と特定できている。 照会記録が保存されていなければ、この範囲確定はできない（本記録の推定）
      取るべき行動 照会ログに利用者・照会キー・結果の有無・時刻を残し、**対象人数の集計クエリを平時に用意しておく**。 インシデント時に初めて集計方法を考える状態を作らない
    • 外部に開いた照会口の遮断を、1クリックで実行できる手順にしておく
      本件では当該企業のアクセスを遮断することが最初の封じ込めになった
      取るべき行動 外部主体ごとにアクセスを即時無効化する手順（APIキーの失効・証明書の失効・接続元の拒否）を文書化し、 **業務時間外でも実行できる当番と権限**を決める。検知が金曜夜だったことを前提に訓練する
    法務・コンプライアンスへの示唆
    • 「委託先ではない正規の照会権限保有者」の責任分界を契約で定めておく
      悪用されたのは法令（CPR 法 §38）に基づく照会権限であり、通常の委託契約とは枠組みが異なる
      取るべき行動 法令・約款に基づいて自社データへ照会できる外部主体について、事故時の通知義務・調査協力・ アクセス遮断の受諾・監査受け入れを明文化する。委託契約の雛形だけでは覆えない

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    委託・第三者部品□ 自社のデータへ照会・参照できる外部主体（法令に基づく照会権限を含む）が存在する本件は CPR システムではなく、照会権限を持つ民間企業1社が破られて起きた
    システム構成□ 外部へ照会 API・検索機能を提供しており、識別子を鍵に個人情報を返す悪用されたのは脆弱性ではなく正規の照会機能だった
    認証・認可□ 本人確認に用いる識別子に推測可能な構造（生年月日等）がある、または値が変更できないCPR 番号は先頭が生年月日で生涯不変のため、列挙が可能で被害が長期化する
    運用・監視□ 照会数・不一致率・累積件数の異常を自動で検知し、自動で絞る仕組みが無い9月の大量照会が検知されたのは10月2日で、その間に収集が進んだ
    運用・監視□ 外部主体のアクセスを業務時間外に即時遮断できる手順と当番が決まっていない本件の検知は金曜夜で、範囲の確認は週末に行われた
    体制・契約□ 大規模な本人通知の方針（個別通知か窓口対応か）を事前に決めていない約880万人規模では個別通知の実行可否が対応の初期に問われる
