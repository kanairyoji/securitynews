INC-2026-0367ClingSTUN が既知脆弱性24件でIoT乗っ取り

Fortinet FortiGuard Labs が、既知の脆弱性24件を初期侵入に使い分けてインターネットに面した IoT 機器・Linux 機器を乗っ取り、感染機器を遠隔操作のプロキシ中継点に変える Linux バックドア「ClingSTUN」を公表した——同マルウェアは NAT 越えのために公開の STUN サーバ（第二版24か所・第三版13か所）へ正規の STUN バインディング要求を送って外部マッピングを把握し、通信が VoIP・WebRTC に紛れる。配布元IPは3期にわたって入れ替わり、7件の脆弱性を内蔵して自己増殖する。初期侵入の起点に使われた1件は日本のハイテクインター製ルータの脆弱性（CVE-2022-36553）だった

脅威・攻撃キャンペーン脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）脆弱性の放置既知の脆弱性の悪用
初報: 2026年10月5日 最終更新: 2026年10月6日

Fortinet の FortiGuard Labs は 2026年10月5日、ClingSTUN と名付けた Linux 向けバックドアの解析結果を公表しました。インターネットに面した IoT 機器・Linux 機器の既知の未修正の脆弱性を突いて侵入し、感染した機器を遠隔操作されるプロキシ中継点（back-connect proxy）に変えるマルウェアです。

特徴は名前の由来でもある STUN（Session Traversal Utilities for NAT）の悪用です。ClingSTUN は UDP ソケットを開いて無作為のローカルポートに束縛し、公開の STUN サーバへ標準の20バイトのバインディング要求を送ります。これにより NAT の外側から見た IP アドレスとポートを知り、NAT のバインディングを維持し続けます。宛先が正規の公開サービスであるため、生じる通信は通常の VoIP・WebRTC の通信に紛れます。FortiGuard Labs は「これらの第三者サービスを攻撃者の基盤と自動的に分類してはならない」と明確に注意を促し、STUN の通信は疑わしいプロセスの挙動・予期しない UDP 通信・繰り返されるキープアライブと併せて評価せよとしています（原文英語）。

初期侵入は24件の既知の脆弱性を使い分けています。FortiGuard Labs は配布元 IP の違いでキャンペーンを3期に分け、第一期（2日間のみ）は日本のハイテクインター製ルータHWL-2511-SS の CVE-2022-36553のみ、第二期は EnGenius の IoT クラウドサービス（CVE-2025-34035）と D-Link の UPnP（CVE-2024-23625）の2件に切り替え、その後Linear・Realtek・TP-Link・AVTECH・D-Link へ広げ、第三期で Ivanti Connect Secure（CVE-2023-46805・CVE-2024-21887）や新しい CVE-2026-36356・CVE-2025-67038 を加えました。さらに7件の脆弱性を本体に埋め込んで自己増殖します。

本記録は、「新しい脆弱性ではなく、古い脆弱性の束」と「正規サービスを使った通信の隠蔽」という2点を軸に整理します。防御側の論点は、特定の CVE への対処ではなく、サポートが切れた機器がインターネットに面し続ける構造と、正規サービス宛ての通信をどう評価するかにあります。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

既知の未修正の脆弱性（報告時点24件）を使い分けてインターネットに面した Linux 機器へ侵入し、 アーキテクチャ別のペイロードを `/tmp` に落として実行。ウォッチドッグタイマを `ioctl` で停止し、 競合プロセスを排除したうえで、自身を2つの隠しファイルにコピーして3つの起動スクリプトに追記して永続化する。 コマンドライン引数を消去し、`/proc/1/` のメタデータを `/tmp` 経由で自身の `/proc/<pid>` に bind マウントしてプロセスを隠す。公開 STUN サーバへ標準のバインディング要求を送って 外部マッピングを把握・維持し、グループ識別子とポート一覧を定期送信する。 運用者からの20バイトのパケットで遠隔コマンド実行（別途の外向き TCP 接続）と、 7件の内蔵エクスプロイトによる自己増殖が起動する。 **運用者が外部マッピングを得て NAT 越しに制御通信を届ける方法は未解明である。**

  2. 2. 実行disclosed[1] [2] [3]
    ダウンローダが `/tmp` へ移動し、**ARM・Intel 80386・MIPS R3000・PowerPC・AMD x86-64** の 各アーキテクチャ版の ClingSTUN をダウンロードして実行する。 **第三版のダウンローダは前処理として破壊的な動作を行う**——`/proc/mounts` の全エントリを走査し、 マウント先にプロセスIDがありファイルシステム種別が `proc` でないものを アンマウントしてプロセスを停止し、さらに実行パスが `/tmp` 配下のプロセスも停止する
    根拠: FortiGuard Labs による3世代のダウンローダの解析
  3. 3. 検知回避disclosed[1] [2] [3]
    **ウォッチドッグタイマの停止**: `/dev/watchdog` と `/dev/misc/watchdog` を読み書きで開き、 `ioctl` システムコールでタイマを停止する。 **競合プロセスの排除**: `/proc` を走査し、複数の条件に照らしてプロセスを停止する。 **プロセスの隠蔽**: 自身のコマンドライン引数を消去して `ps` でコマンドラインが空に見えるようにし、 root（UID 0）で動作している場合は `/proc/1/` から選んだプロセス情報ファイルを `/tmp` にコピーして **`/tmp` を自身の `/proc/<pid>` ディレクトリに bind マウント**し、 PID 1 から複製したメタデータの背後に自身のプロセス情報を隠す
    根拠: FortiGuard Labs による第二版・第三版（AMD x86-64 版）の解析
  4. 4. 永続化disclosed[1] [2] [3]
    自身を **`/root/.cling`** と **`/usr/local/bin/.cling`** の2か所にコピーして実行権限を与え、 **3つの起動ファイル**——**`/etc/inittab`**・**`/etc/init.d/rcS`**・**`/etc/rc.d/rc.boot`**——に 追記して、機器の起動時に実行されるようにする
    根拠: FortiGuard Labs による解析（ファイルパスの明示）
  5. 5. C2通信disclosed[1] [2] [3]
    UDP ソケットを開いて無作為のローカルポートに束縛し、**公開 STUN エンドポイント**へ 標準の**20バイトのバインディング要求**を送る（第二版は**24か所**へ送り少なくとも半数の成功を要件、 第三版は**13か所**に減らし全エンドポイントの成功を要件とする）。これにより NAT の外側から見た IP アドレスとポートを把握し、NAT のバインディングを維持する。その後、 **グループ識別子とマッピング済みポートの一覧**を同じ STUN エンドポイントへ定期的に送る。 運用者からの**20バイトのパケット**を待ち受け、受信すると追加機能が起動する。 遠隔コマンド実行では、保持している UDP ソケットに制御データグラムが届くと、 コマンド1 がメッセージで指定された宛先へ**別途の外向き TCP 接続**を張り、 コマンドを受け取って実行する。**宛先が正規の公開サービスであるため、 通信は通常の VoIP・WebRTC に紛れる。** FortiGuard Labs は「この経路で別途の調整サーバへの登録は確認されなかった」とし、 **運用者が外部マッピングを得て NAT 越しに制御通信を届ける方法は未解明である**と明記している
    根拠: FortiGuard Labs による STUN 通信の解析と、同社による未解明点の明示
  6. 6. 影響（暗号化・破壊・改ざん）disclosed[1] [2] [3]
    感染機器が**遠隔操作されるプロキシ中継点**（back-connect proxy）として機能するようになる。 FortiGuard Labs は ClingSTUN を「永続的なアクセスを保ち、侵害した機器を 遠隔操作されるプロキシノードに変えることを目的とした Linux の back-connect proxy backdoor」と 位置づけている（原文英語）。**プロキシ網が何の通信を中継しているか（最終用途）、 および感染台数は公表されていない**

STUN の悪用は「宛先が正規サービスである」ことを盾にしており、宛先IPでは判定できない評価・解釈出典 [1] [2] [3]

ClingSTUN の名前の由来である STUN の使い方は、防御側にとって本件の最も実務的な論点である。

何をしているか（公表事実）

  • UDP ソケットを開き、無作為のローカルポートに束縛する
  • 公開の STUN エンドポイントへ、標準の20バイトのバインディング要求を送る
  • 第二版は24か所へ送り少なくとも半数の成功を要件とする。第三版は13か所に減らしすべての成功を要件とする
  • これにより NAT の外側から見た IP アドレスとポートを把握し、NAT のバインディングを維持する
  • その後、グループ識別子とマッピング済みポートの一覧を同じ STUN エンドポイントへ定期的に送り続ける
  • 運用者からの20バイトのパケットを待ち受け、受信すると遠隔コマンド実行と自己増殖が起動する。遠隔コマンド実行では、受信したメッセージで指定された宛先へ別途の外向き TCP 接続を張り、コマンドを受け取って実行する

なぜ厄介か（本記録の評価）

宛先が正規の公開 STUN サービスであるため、生じる通信は通常の VoIP・WebRTC と区別がつかない。宛先 IP やドメインのレピュテーションで悪性判定する仕組みは、ここでは機能しない。FortiGuard Labs もこの点に踏み込んで、「これらの第三者サービスを攻撃者の基盤と自動的に分類してはならない」と注意し、代わりに「疑わしいプロセスの挙動・予期しない UDP 通信・繰り返されるキープアライブと併せて STUN の活動を評価せよ」と述べている（原文英語）。つまり宛先ではなく「誰が送っているか」と「どういう周期で送っているか」で見るよう求めている。IoT 機器やルータが STUN を話し始めること自体が異常である、という機器種別ごとの期待値がないと、この判定はできない（本記録の評価）。

なお FortiGuard Labs は運用者が外部マッピングを取得して NAT 越しに制御通信を届ける方法は未解明のままであると明記している。STUN エンドポイントへポート一覧を送る経路の先が追えていないということであり、C2 の全体像は公表時点で埋まっていない。

永続化・隠蔽・ウォッチドッグ停止は Linux 組み込み機器の作りを前提に組まれている原因・手口出典 [1] [2] [3]

侵入後の挙動のうち、公表されている事実は次のとおりである。

  • ウォッチドッグの無効化: /dev/watchdog と /dev/misc/watchdog を読み書きで開き、ioctl システムコールでウォッチドッグタイマを停止する。（組み込み機器は異常時に自動再起動する設計が多く、これを殺すことで居座りが安定する。本記録の補足）
  • 競合プロセスの停止: /proc を走査し、複数の条件に照らしてプロセスを停止する
  • 永続化: 自身を /root/.cling と /usr/local/bin/.cling の2か所にコピーして実行権限を与え、3つの起動ファイル—— /etc/inittab・/etc/init.d/rcS・/etc/rc.d/rc.boot——に追記して、起動時に実行されるようにする
  • プロセスの隠蔽（2段構え）: ① 自身のコマンドライン引数を消去し、ps などでコマンドラインが空に見えるようにする。② root（UID 0）で動いていれば、/proc/1/ から選んだプロセス情報ファイルを /tmp にコピーし、/tmp を自身の /proc/<pid> ディレクトリに bind マウントして、PID 1 から複製したメタデータの背後に自分のプロセス情報を隠す

FortiGuard Labs は、これらの挙動が既存のボットネットの多くと共通する（ウォッチドッグの停止、競合の排除、永続化、検知回避、遠隔コマンド実行）と述べている。検知名に BASH/Mirai.AEH!tr.dldr が含まれることからも Mirai 系の系譜が示唆されるが、系統関係についての明示的な記述は無い（本記録の注記）。

防御の観点では、/etc/inittab や /etc/init.d/rcS の変更、ドットで始まる隠しファイルの実行権限付与、/proc/<pid> への bind マウントはいずれも通常の運用で起きない事象である。ただし多くの IoT 機器はこれらを監視する手段を持たない——それが本件の本質的な難しさである（本記録の評価）。

感染台数・プロキシ網の用途・運用者の帰属は公表されていない未確定事項出典 [1] [2] [3]

2026年10月6日時点で、次の点は公表されていない。

  • 感染台数・被害組織・国別の分布。影響を受ける利用者は「あらゆる組織」、深刻度は High とされるのみで、プロキシ網の規模が分からない
  • 運用者が外部マッピングを取得し NAT 越しに制御通信を届ける方法。FortiGuard Labs が解析したうえで「未解明」と明記した論点である
  • プロキシ網の最終的な用途。住宅用プロキシとしての転売か、別の攻撃の踏み台か、中継の内容は示されていない
  • 運用者の帰属・動機。既存ボットネットとの系統関係も明示されていない
  • 日本国内の被害の有無。第一期の唯一の侵入口が日本メーカー製ルータの脆弱性だったが、国内の被害は公表されておらず、ハイテクインターによる言及も確認できなかった
  • 悪用された CVE のうち修正が入手できないもの（サポート終了機種）の範囲。「更新を受けられない機器は交換または隔離せよ」との助言はあるが、対応表は無い

最後の点は実務上の分かれ目である。「パッチを当てれば済む範囲」と「機器を捨てるしかない範囲」の切り分けができないと、対策の見積りが立たない（本記録の評価）。

対策の方向性について識者の見解は正面から対立している対策・注意喚起出典 [2] [3]

Infosecurity Magazine は、本件への対処について互いに矛盾する二つの主張を併記している。本記録はどちらかを採らず、対立していること自体を記録する。

  • ColorTokens の Louis Eichenbaum 氏（federal CTO）:「ClingSTUN は、組織がサイバーリスクをパッチで解決しきることはできないという改めての警告である」とし、直ちに修正できない機器の周囲に補完的統制を置くこと、マイクロセグメンテーションで横展開を抑えることを主張した（原文英語）
  • Viakoo の John Gallagher 氏（VP）:セグメンテーションについて正面から反対し、「ネットワークセグメンテーションが安全をもたらすという考えは誤った前提だ」と述べ、代わりに複数ベンダーにまたがる IoT 群への自動ファームウェア修復を主張した。「可視化だけでは救われない」とも述べている（原文英語）

FortiGuard Labs 自身の助言は次のとおりである（原文英語）。

  • インターネットに面した機器を棚卸しし、ファームウェアとサポート状況を追跡する
  • 利用可能なセキュリティ更新を速やかに適用し、現に悪用が確認されている脆弱性を優先する
  • セキュリティ更新を受けられなくなった機器は交換または隔離する
  • 不必要にインターネットに面したサービスを無効化または制限する
  • STUN の活動は、疑わしいプロセスの挙動・予期しない UDP 通信・繰り返されるキープアライブと併せて評価する

本記録の評価: 両者の主張は「どちらが正しいか」ではなく前提の違いで分かれている。Eichenbaum 氏は「直せない機器が残る」ことを前提に被害の限定を論じ、Gallagher 氏は「直せるようにする」ことを論じている。本件が既知脆弱性のみで成立している事実は、一次的には Gallagher 氏の側（修正の適用）を支持する。一方で、悪用された CVE に修正入手不能なものが含まれるかが公表されていないため、「直せない個体がどれだけあるか」が分からず、Eichenbaum 氏の論点も消えない。組織としては、棚卸しでサポート状況を確定させるまで、どちらの戦略が必要かも決められない。

CISO・経営層への示唆
  • 「ゼロデイ対策」より先に、インターネットに面した機器の棚卸しとサポート状況の確定に金を使う
    本件の侵入口は**24件すべてが既知の脆弱性**で、最古は12年前の CVE-2014-8361 である。 未知の脆弱性は一つも使われていない
    取るべき行動 インターネットに面した機器の全数台帳を作り、**機種・ファームウェア版・サポート終了日・ 所有部門**の4項目を埋める。埋まらない機器（所有者不明・版が読めない）を別表にし、 **その件数を経営指標として毎月報告する**。台帳が埋まるまで、どの対策が必要かも決められない
  • 対策の方向性について識者の主張が対立していることを、判断の留保ではなく前提の違いとして読む
    本件では「パッチでは解決しきれないのでマイクロセグメンテーションを」（ColorTokens）と 「セグメンテーションが安全をもたらすのは誤った前提。自動ファームウェア修復を」（Viakoo）が 正面から対立した
    取るべき行動 自組織の IoT 機器を「**更新できる／できない**」で二分し、件数を出す。 更新できる群には修復の自動化を、できない群には隔離・交換の計画を当てる。 **どちらの戦略が主になるかは棚卸しの結果で決まる**ので、先に戦略を選ばない
  • IoT 機器の侵害は「自組織が加害の経路になる」形の損害として経営に説明する
    ClingSTUN の目的はデータの窃取ではなく、感染機器を**遠隔操作のプロキシ中継点**に 変えることである。自組織の情報は出ないが、自組織の回線と IP が他者への攻撃に使われる
    取るべき行動 リスク登録簿に「**自組織の資産が第三者への攻撃の中継に使われる**」項目を立て、 想定される帰結（IP の評判低下による正規通信の遮断、取引先からの照会、 捜査機関からの照会、回線契約上の責任）を書き出す。 **情報漏えいの枠組みだけでは本件の損害が見えない**
  • 脅威レポートの数字を「上限」ではなく「報告時点の下限」として扱う運用にする
    FortiGuard Labs は脆弱性の一覧を「本ブログの日付時点のもの」とし、 収集とシグネチャ更新を継続中であると明記している。一覧は増える前提である
    取るべき行動 レポートに基づく対応を「列挙された CVE の対処」で閉じず、 **侵入口の型**（公開された管理 CGI・UPnP・IoT クラウド連携・VPN 装置）で 棚卸しの対象を定義する。CVE 単位の対応表だけを成果物にしない
セキュリティ技術者への示唆
  • STUN 宛ての通信を遮断リストに入れてはならない。見るべきは宛先ではなく送信元の機器種別である
    ClingSTUN が接触する STUN サーバは**正規の公開サービス**で、通信も標準の 20バイトのバインディング要求である。FortiGuard Labs 自身が 「これらの第三者サービスを攻撃者の基盤と自動的に分類してはならない」と注意している。 遮断すれば正規の VoIP・WebRTC が壊れる
    取るべき行動 機器種別ごとに「話してよいプロトコル」の期待値表を作る。 **監視カメラ・入退管理装置・ルータが STUN（UDP 3478 等）を話し始めたら異常**として警報を上げる。 同時に、本記録に載せた STUN エンドポイントの IP を**そのまま遮断・検知に投入しない**
  • ウォッチドッグが止まった機器、再起動の記録が途絶えた機器を侵害の痕跡として扱う
    ClingSTUN は `/dev/watchdog` と `/dev/misc/watchdog` を開き、`ioctl` で ウォッチドッグタイマを停止する。居座りを安定させるための動作である
    取るべき行動 機器の稼働監視に「**最終再起動からの経過時間が想定より長い**」 「ウォッチドッグによる再起動が観測されなくなった」を指標として加える。 正常な機器がどの周期で再起動するかを先に測っておく
  • 永続化は起動スクリプトに入るため、電源の抜き差しや再起動では除去できない
    ClingSTUN は自身を `/root/.cling` と `/usr/local/bin/.cling` にコピーし、 `/etc/inittab`・`/etc/init.d/rcS`・`/etc/rc.d/rc.boot` の3つに追記する
    取るべき行動 IoT 機器の侵害時の復旧手順を「**ファームウェアの再書き込み（工場出荷状態への戻し）**」で 定義し、再起動で済ませない。手順書に機種ごとの再書き込み方法と所要時間を書いておく。 **再書き込みの前に、同じ脆弱性が塞がっていなければ即座に再感染する**ことも明記する
  • プロセス一覧と `/proc` を信用しない。ClingSTUN は PID 1 のメタデータで自身を隠す
    ClingSTUN はコマンドライン引数を消去して `ps` で空に見せ、root 権限時は `/proc/1/` のプロセス情報ファイルを `/tmp` 経由で自身の `/proc/<pid>` へ bind マウントして隠蔽する
    取るべき行動 エージェントを載せられる Linux 機器では、`/proc` への bind マウントと `/dev/watchdog` への書き込みを監査ルールに追加する。 **エージェントを載せられない機器では「機器側で調べる」前提を捨て、 経路側の通信（周期的な UDP・外向き TCP・上り帯域）で判断する**設計に切り替える
  • 自己増殖用の7件は「インターネットに面していない機器」も対象になる
    内蔵エクスプロイト（Realtek SDK・MVPower・TBK・Linksys・LB-LINK・China Mobile・ KGUARD の DVR/ルータ）は、感染機器から隣の機器を攻撃するために使われる。 初期侵入の24件とは別の集合である
    取るべき行動 **機器セグメント内の機器間通信を既定拒否**にする（監視カメラ同士、DVR 同士が 通信する必要はない）。併せて自己増殖の対象7製品を自組織が保有していないかを 棚卸しで確認する。**面していないから安全、は本件では成り立たない**

システム構成□ 機器セグメントからの外向き通信、および機器間の通信が既定許可になっているペイロードの取得・遠隔コマンド実行用の外向き TCP・自己増殖はいずれも 既定拒否で止められる余地がある。自己増殖はインターネットに面していない機器にも及ぶ
運用・監視□ IoT 機器の侵害時の復旧手順が「再起動」で終わっており、 ファームウェアの再書き込みと脆弱性の修正を含んでいない永続化が3つの起動スクリプトに入るため再起動では消えず、 かつ侵入口を塞がなければ再書き込み後も即座に再感染する
