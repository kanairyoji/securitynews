INC-2026-0375Atlassian 8製品に認証不要の読取

Atlassian が2026年10月5日、自社ホスト型の Data Center 製品8種 （Bitbucket / Confluence / Jira Software / Jira Service Management / Bamboo / Crowd / Crucible / Fisheye）に共通する任意ファイル読み取りの脆弱性 CVE-2026-21589（CVSS v4.0 で 9.3・Critical）を公表した。 **認証を要さず**、ウェブアプリケーションのルートディレクトリ内の特定ファイルを 読み出せる。成立にはファイル名とパスを事前に知っている必要があり、 ディレクトリの一覧は取れない。クラウド版は修正済みで利用者の作業は不要とされ、 自社ホスト型については**悪用の有無を Atlassian は確認できないと明記**している。 同社が CVE として届け出た記録には、勧告が触れていない旧 Server 版も 「全版が影響」として載っており、Server 版の修正版は示されていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月5日 最終更新: 2026年10月6日

Atlassian は現地時間2026年10月5日、自社ホスト型の Data Center 製品8種に共通する脆弱性 CVE-2026-21589 を公表した。同社は CVSS v4.0 の基本値を 9.3（Critical）と評価している。

欠陥の性質は任意ファイル読み取りである。認証を要さない攻撃者が、ウェブアプリケーションのルートディレクトリ内にある特定のファイルを読み出せる。ただし成立には対象ファイルの正確な名前とパスを事前に知っている必要があり、ディレクトリの中身を列挙・一覧することはできない。 Atlassian は「構成によっては機微なファイルが存在し、危険度を高めることがある」と述べている（原文英語）。

対象は Bitbucket / Confluence / Jira Software / Jira Service Management / Bamboo / Crowd / Crucible / Fisheye の Data Center 版で、製品ごとに修正版が示された。クラウド版はすでに修正済みで、クラウド利用者の作業は不要とされ、Bitbucket Cloud は影響を受けない。

すぐに更新できない場合の指示は「可能ならインスタンスをオフラインにする」である。同社は代替として3通りの一時的な遮断規則（WAF / リバースプロキシの URL 遮断、Tomcat の RewriteValve、Bitbucket の urlrewrite.xml）を示しつつ、「これらは限定的であり、パッチの代わりにはならない」と製品チケットに明記している（原文英語）。

悪用についての同社の記述は、クラウドと自社ホスト型で分かれている。クラウドについては「調査で悪用の証跡は見つかっていない」とした一方、自社ホスト型については「あなたのインスタンスが影響を受けたかどうかをAtlassian は確認できない」と述べ、利用者の側でアクセスログを調べることを求めている（原文英語）。

公表されていない・確定していないこと7
  • 自社ホスト型インスタンスへの悪用の有無公表されていない
    **勧告は、自社ホスト型のインスタンスに対する攻撃が観測されたかを述べていない。** 書かれているのは**「あなたのインスタンスが影響を受けたかどうかを Atlassian は確認できない」**という一文である（原文英語）。 クラウドについては「調査で悪用の証跡は見つかっていない」とされているが、 **これは自社ホスト型の状況を何も示さない。** **「悪用の報告なし」ではなく「ベンダーに判定能力が無い」が正しい読みである**（本記録の評価）。
  • どのファイルが機微で、どの構成だと存在するのか公表されていない
    勧告は「構成によっては機微なファイルが存在し、危険度を高める」と述べるだけで、 **対象のファイル名も、そうした構成の条件も示していない。** **読み出せるのは「名前とパスを知っているファイル」**なので、 攻撃の成否は**どのファイルが置かれているか**に直接かかっている。 **利用側は「自機のルートディレクトリに何が置かれているか」を自力で調べるしかない。**
  • CVSS で「後続システム」側の完全性・可用性が High である理由公表されていない
    Atlassian のベクタは `SC:H/SI:H/SA:H`—— **後続システム（subsequent system）の機密性・完全性・可用性のすべてを High** と置いている。 一方で脆弱なシステム側は `VC:H/VI:N/VA:N`（機密性のみ）である。 **読み取りだけの欠陥が後続システムの完全性・可用性をなぜ High にするのかは 説明されていない。** 読み出したファイルに資格情報が含まれる場合の 二次被害を織り込んだとも読めるが、**勧告はそう書いていない**（本記録の読み）。
  • 旧 Server 版の利用者が取るべき行動公表されていない
    CVE 記録は **Bamboo / Bitbucket / Confluence / Crowd の Server 版を 「全版が影響」としながら、修正版を1つも示していない。** 勧告（製品チケット）の側は Server 版に触れていない。 **サポート終了済みの Server 版を動かし続けている組織に対する指示が存在しない。** 残るのは「オフラインにする」か「①の遮断規則を置く」のどちらかだが、 **Atlassian がそれで足りると述べているわけではない**（本記録の整理）。
  • ログに該当する要求が見つかった場合に何をすべきか公表されていない
    Atlassian はアクセスログの調べ方を2通り示している—— ①各要求行を**最大2回まで URL デコード**して `..` が `/`・`\`・`::` と 隣接していないか探す、②同社の遮断パターンを生のログ行に当てる。 しかし**失敗した試行と実際にファイルが返った要求を区別する方法は書かれていない。** **見つかった場合に更新以外に何をすべきかも示されていない。** そのため「痕跡があった」という結論が出ても、次の手が決められない（本記録の評価）。
  • 発見者・報告経路・内部での認知時期公表されていない
    **誰が見つけたのか（外部研究者・バグバウンティ・社内）も、 Atlassian がいつ把握したのかも公表されていない。** 影響を受け始めた版が製品ごとに古いことから長く残っていた経路とみられるが、 **なぜ今見つかったのかは分からない。**
  • Crowd 7.1 系と Bamboo 10.2 系の正しい修正版公表されていない
    **Atlassian 自身の資料の中で数字が割れている**（discrepancies 参照）。 Crowd 7.1 系は 7.1.1 / 7.1.6 / 7.1.7 の3つの数字が別の欄に現れ、 Bamboo は 10.2.4 と 10.2.24 が同じ CVE 記録の中で食い違う。 **どれが正しいのかを Atlassian は明示していない。** 本記録は記述文（description）側の 7.1.1 / 10.2.24 を併記するにとどめ、 **断定しない。**

「名前を知っているファイルだけ読める」という制約は、守る側の安心材料にはならない概観

公表された欠陥の形は限定的に見える。認証は要らないが、読めるのはウェブアプリケーションのルートディレクトリ内に限られ、しかも正確なファイル名とパスを事前に知っている必要がある。ディレクトリの中身を列挙することはできない。Atlassian 自身も、この2点を「良い知らせ」として示している。

それでも CVSS は 9.3 である。 理由は制約の中身を考えると分かる。

  • Atlassian 製品のファイル配置は標準的である。 自社開発のアプリと違い、どの組織でも同じパスに同じ名前のファイルが置かれる。「名前を知っている必要がある」という条件は、製品のソースやドキュメントを読める攻撃者には条件になっていない（本記録の評価）。
  • ルートディレクトリに何を置いているかは利用側の運用で決まる。 Atlassian は「構成によっては機微なファイルが存在し、危険度を高める」と述べるが、どのファイルが危ないのかは示していない。自社の運用で置いたもの——構成ファイル、接続情報、鍵——があれば、そこが被害の中身になる。
  • 対象は開発と運用の中枢である。 ソース管理（Bitbucket）、ドキュメント（Confluence）、課題管理（Jira）、CI（Bamboo）、そして認証（Crowd）。Crowd は他製品の利用者認証を束ねる製品であり、ここから資格情報に届いた場合の広がりは製品1つの話では済まない。

読み取りだけの脆弱性を「情報漏えいのリスク」として片付けると、ここを読み落とす（本記録の評価）。

いちばん重い一文は「あなたのインスタンスが影響を受けたか当社は確認できない」である原因・手口

Atlassian はクラウドと自社ホスト型を明確に分けて書いている。

  • クラウド版——すでに修正済み。利用者の作業は不要。Bitbucket Cloud は影響を受けない。調査で悪用の証跡は見つかっていない。
  • 自社ホスト型（Data Center）——製品ごとに修正版を適用する必要がある。そして「あなたのインスタンスが影響を受けたかどうかを当社は確認できない」（原文英語）。

この一文が本件の実務上の中心である。ベンダーが悪用の有無を判定できない以上、「悪用の報告はありません」はこの事案については成立しない報告文である。言えるのは「ベンダーは判定していない」までで、判定の責任はログを持っている利用側にある。

幸いな点として、自社ホスト型であればログは手元にある。機器の脆弱性（例: INC-2026-0290 の FortiMail）のようにベンダーの IoC に頼る構造ではなく、自分のウェブサーバ・リバースプロキシ・WAF のアクセスログを自分で読める。 Atlassian が示した調べ方は2通りである—— ①各要求行を最大2回まで URL デコードし、.. が /・\・:: と隣接していないか探す、②同社の遮断パターン（下記）を生のログ行に当てる。

遮断・検出に使う正規表現は、本記録が製品チケット CONFSERVER-104488 で実体を確認した次のものである。

(?is).*(?:/|\\|::|%(?:25)*(?:2f|5c)|(?::|%(?:25)*3a){2})(?:\.|%(?:25)*2e){2}(?:/|\\|::|%(?:25)*(?:2f|5c)|(?::|%(?:25)*3a){2}|;|%(?:25)*3b|$).*

%25 の繰り返しを織り込んでいる点に注目する価値がある—— %252e のような二重エンコードまで拾う作りになっている。これは、単純な .. の文字列一致では抜けることを前提にした書き方である。FBI の採用基盤の事案（INC-2026-0189）では、攻撃者が/PSEMHUB/ の P を %50 に置き換えて WAF の規則を素通りした。文字列一致で塞ぐ発想が繰り返し破られているという流れの中で読むべきである（本記録の整理）。

ただし Atlassian は、ログに該当する要求が見つかった場合の次の手を書いていない。失敗した試行と実際にファイルが返った要求をどう区別するのかも示されていない。見つけた側が判断を引き受けることになる。

旧 Server 版の扱いが、勧告と CVE 記録で噛み合っていない評価・解釈

本記録が一次資料で確認したうち、報道が十分に扱っていない点がここである。

Atlassian が CVE 採番機関として届け出た記録には、勧告（製品チケット）が触れていない旧 Server 版が載っている。

Confluence Server 全版が影響。修正版なし

前半4製品には上げる先が無い。 Server 版は Atlassian が2020年に開発を止めた旧来の自社ホスト型の系列で、サポートは終了している。The Hacker News は、Crowd には2023年9月の 5.2 以降 Server 版のリリースが無く、勧告が示した修正版のどれも Server 版ではないと指摘している。後半の3行についても、Server ライセンスでその版を動かせるのかは書かれていない。

ここから読者が取り出せるのは、サポート終了後の資産に対して「勧告の対象外」と「影響あり」が同時に成立しうるということである（本記録の評価）。脆弱性管理の台帳が「勧告に載っている製品」だけを拾う作りだと、CVE 記録にしか載っていない影響範囲が落ちる。本件では、勧告を読むだけでは Server 版の利用者は自機が対象だと気づけない。

The Register はこの状況を Atlassian の移行方針の文脈で書いている—— 2020年に低価格帯の Server 製品の開発を止め、2025年には Data Center 製品も終息させる決定をし、移行ツールは新版のほうが前版より劣っていたと同社が認めた、と。移行を促す側の都合と、移行できていない資産の安全は別の問題である。自組織に「移行途中」「移行できていない」Atlassian 製品があるなら、本件は移行計画の優先順位を見直す材料になる（本記録の評価）。

ベンダー自身の資料の中で修正版の数字が割れている評価・解釈

更新する版を決めるための数字が、Atlassian の資料の中で一致していない。

  • Crowd 7.1 系——製品チケットの「fix version」欄は 7.1.7。同じチケット内の表は 7.1.6 を影響版として挙げている。一方 CVE 記録は 7.1.1 以降が影響を受けないとしている。The Hacker News は、Crowd 7.1 系のリリースノートによれば7.1.1 は2025年11月27日、つまり公表の10か月以上前の版であると指摘している。
  • Bamboo 10.2 系——CVE 記録の構造化された欄は「10.2.4 以降は影響なし」とする一方、同じ記録の記述文は 10.2.24 を修正版としている。

本記録はどちらが正しいかを断定しない。記述文（description）側の 7.1.1 / 10.2.24 を併記するにとどめる。10.2.4 と 10.2.24 の差は「桁の打ち間違い」に見えるが、見えるからといって本記録が正解を決めてよいものではない（本記録の判断）。

実務上の含意は単純である。 自動化された脆弱性管理の仕組みが、どちらの数字を読んでいるかで判定が反転する。 CVE 記録を取り込む製品（多くのスキャナがそうである）はBamboo 10.2.4 を「安全」と判定しうるが、Atlassian の記述文に従えば 10.2.24 まで上げる必要がある。版番号の自動照合に全面的に依存している組織は、本件のように採番側の記録が割れている場合に静かに取りこぼす（本記録の評価）。

  • ベンダーが「悪用の有無を確認できない」と書いた事案を、「悪用の報告なし」と報告させない
    **Atlassian は自社ホスト型について 「あなたのインスタンスが影響を受けたかどうかを当社は確認できない」と明記している。** これは「報告が無い」ではなく「判定する立場に無い」という意味である。 **自社ホスト型の製品では、判定材料は常に利用側の手元にある。** それでも社内報告は「ベンダーは悪用を確認していません」と書かれがちで、 **調べる作業が発生しないまま終わる。**

  • 脆弱性管理の台帳を「勧告に載っている製品」ではなく「CVE 記録の影響範囲」で引く

    取るべき行動 影響判定の手順に**「ベンダー勧告と CVE 記録の両方を読む」**を明記する。 食い違いがあった場合は**広いほうを採る**と決めておく。 本件を最初の適用例として、自組織の Atlassian 資産を **ライセンス種別込みで棚卸しする。**
  • サポート終了済みの資産に「影響あり・修正なし」が起こることを、移行計画の前提に入れる
    **Server 版4製品には上げる先が無い。** サポート終了は「ベンダーが守らない」という意味であり、 **「脆弱性の対象から外れる」という意味ではない。** 本件はその差が明示的に出た例である。 Atlassian は Data Center 製品自体の終息も決めているため、 **同じ状況が次の層でも起こりうる**（The Register の報道）。
    取るべき行動 サポート終了済み・終了予定の基幹ソフトウェアの一覧に、 **「修正が出ない前提での代替策（到達範囲の制限・停止・置き換え）」**を 1行ずつ書き添える。 **移行の遅れをリスク登録簿に金額または影響範囲で載せ、 移行予算の判断材料にする。**
  • 開発・運用の基盤（課題管理・ソース管理・認証）の公開範囲を、経営の判断事項として持つ
    本件の指示は**「可能ならオフラインにする」**から始まる。 これは技術部門が単独で実行できる判断ではない—— **止めれば開発が止まり、社外の委託先・顧客も影響を受ける。** 平時に公開範囲を決めていない組織は、**緊急時に止める判断ができない。**
    取るべき行動 Atlassian 製品のような**内部向け基盤をインターネットに出す必要があるか**を 平時に棚卸しし、必要な場合は**到達元の制限（VPN・IP 制限・ゼロトラストのプロキシ）**を 前提に置く。**「ログイン画面があるから公開して良い」という判断は、 認証前に成立する脆弱性では無効**であることを方針に書く。
セキュリティ技術者への示唆
  • 遮断規則は「文字列一致」ではなく「デコード後の判定」で書く
    Atlassian の遮断正規表現は **`%25` の繰り返しを織り込み、 `%252e` のような二重エンコードまで拾う**作りになっている。 **単純な `..` の一致では抜ける**ことを前提にした書き方である。 FBI の採用基盤の事案（INC-2026-0189）では、 攻撃者が `/PSEMHUB/` の `P` を `%50` に置き換えるだけで WAF の規則を素通りした。
    取るべき行動 自組織の WAF 規則を**「デコード後に判定しているか」**で棚卸しする。 パス名を含む遮断規則については **二重エンコード・大小文字・`\`・`::`・`;` の変形を含む試験ケース**を作り、 規則を入れたあとに**実際に通らないことを確認する。**
  • ウェブアプリケーションのルートディレクトリに置いたファイルを棚卸しする
    **読み出せるのは「名前とパスを知っているファイル」**なので、 **自機に何が置かれているかが被害の上限を決める。** 製品の標準ファイルは攻撃者も名前を知っている。 危ないのは**運用の過程で後から置いたもの**—— 構成の控え、接続情報、鍵、作業中の退避ファイル——である（本記録の評価）。 Atlassian は「構成によっては機微なファイルがある」と述べるだけで、 **何が危ないかは示していない。**
    取るべき行動 各インスタンスのルートディレクトリの**ファイル一覧を取得して差分管理に入れる。** 標準配布に含まれないファイルは**退避先を外に移す**か、削除する。 以後は**配置の手順に「ルート配下に置かない」を明記**する。
  • 緩和策を入れる対象に、ミラーと副系を必ず含める
    Bitbucket の緩和策は**全ノード・ミラー・ミラーファームへの適用と再起動**を要する。 **1か所でも漏らすと迂回経路が残る。** Crucible と Fisheye には WAF 以外の選択肢が無い。 **製品によって打てる手が違う**ことを把握していないと、 「緩和済み」の報告に穴が開く。
    取るべき行動 緩和策の適用表を**製品 × ノード（本体・クラスタ各ノード・ミラー）**の マトリクスで作り、**適用と再起動の両方にチェック欄を置く。** **WAF しか打てない製品（Crucible / Fisheye）は別扱いで記録する。**
  • アクセスログの調査は「どこまで遡れるか」を先に確認してから着手する
    影響を受け始めた版は製品ごとに古く（Crowd Data Center は 2.11.0 以降）、 **いつから悪用が可能だったかの下限が非常に古い。** 一方 Atlassian は**自社ホスト型への悪用の有無を述べていない**ため、 **調査期間の起点を示す情報が無い。** 遡れる範囲を知らずに始めると、 **「見つからなかった」が何を意味するのか言えなくなる。**
    取るべき行動 調査の着手前に**各インスタンスのアクセスログの保存期間を記録**し、 報告書に**「この期間について調べた結果である」と範囲を明示して書く。** 保存期間が短い場合は、**その事実を残存リスクとして登録する。**
  • 版番号の自動照合に依存している部分を把握しておく
    **本件では Atlassian 自身の資料の中で修正版の数字が割れている**—— Bamboo は CVE 記録の一方の欄が 10.2.4、同じ記録の記述文が 10.2.24。 Crowd 7.1 系は 7.1.1 / 7.1.6 / 7.1.7 の3つが別の欄に現れる。 **CVE 記録を取り込むスキャナは「10.2.4 なら安全」と判定しうる。**
    取るべき行動 重要度の高い脆弱性については、**スキャナの判定をそのまま信じず、 ベンダーの記述文（description）側の版番号と突き合わせる**手順を入れる。 食い違った場合は**新しいほうへ上げる**。 本件の2件（Crowd 7.1 系・Bamboo 10.2 系）は **ベンダーへ照会した記録を残す。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Atlassian の Data Center 製品（Bitbucket / Confluence / Jira Software / Jira Service Management / Bamboo / Crowd / Crucible / Fisheye）を 自社で運用しており、インターネットから到達できる
システム構成□ 旧 Server 版、またはサポート終了（EOL）に達した Data Center 版を動かし続けている
認証・認可□ Crowd で複数製品の利用者認証を束ねている、または Atlassian 製品を社外の委託先・顧客と共有している

運用・監視□ WAF やリバースプロキシの遮断規則が、URL デコード前の文字列一致で書かれている
