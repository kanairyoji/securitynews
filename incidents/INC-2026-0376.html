INC-2026-0376Dell DSU に未認証 root 脆弱性

Dell が2026年10月1日、サーバの BIOS・ファームウェア・ドライバを更新するための 管理ツール Dell System Update（DSU）の 2.3.0.0 より前の全版に 5件の脆弱性があると公表した（DSA-2026-324）。 最も重い CVE-2026-86360 は CVSS 9.6 のパストラバーサルで、 Dell は「認証されていない遠隔の攻撃者に悪用されて **root 権限での任意コード実行**に至りうる」と記述した。 ただし同じ勧告が示す CVSS ベクタには **UI:R（利用者の操作が必要）**が立っており、 「認証不要の遠隔」という言葉と噛み合っていない。 修正は 2.3.0.0 以降。悪用の報告は無いとされ、 **2026年10月6日時点で CVE 記録（CVE Program）は未公開**である

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月1日 最終更新: 2026年10月6日

Dell は現地時間2026年10月1日、セキュリティ勧告 DSA-2026-324 を公表し、サーバ管理ツール Dell System Update（DSU） の 2.3.0.0 より前の全版に5件の脆弱性があることを明らかにした。

最も重いのは CVE-2026-86360（CVSS v3.1 基本値 9.6）で、パス名の制限ディレクトリへの不適切な限定（パストラバーサル）である。Dell の記述は次のとおり——「Dell System Update の 2.3.0.0 より前の版には、パス名の制限ディレクトリへの不適切な限定（パストラバーサル）の脆弱性がある。認証されていない遠隔アクセスを持つ攻撃者がこれを悪用し、攻撃者によるファイルシステムへのアクセスに至る可能性がある。この脆弱性が critical とされるのは、認証されていない攻撃者が root 権限で任意のコードを実行するために利用されうるためである。悪用が成功した場合、脆弱なアプリケーションと基盤となるオペレーティングシステムの完全な侵害に至る可能性がある」（原文英語）。

残る4件はいずれも権限昇格またはコード実行につながるもので、CVE-2026-86361（8.2）と CVE-2026-86362（8.2）は低権限のローカル利用者による権限昇格、CVE-2026-63697（7.6）は証明書検証の不備による高権限の遠隔攻撃者のコード実行、CVE-2026-71168（7.3）は低権限のローカル利用者によるパストラバーサル経由のコード実行である。

修正は 2.3.0.0 以降への更新だけで、回避策は示されていない。 Dell は悪用の報告は無いとしている。

本記録が一次資料で確認して重く見た点が2つある。 1つは、同じ勧告が示す CVSS ベクタに UI:R（利用者の操作が必要）が立っていることで、「認証不要・遠隔」という言葉だけを読むと成立条件を見誤る。もう1つは、2026年10月6日時点で CVE Program に CVE-2026-86360 の記録が存在しないことで、NVD や CVE 記録を取り込んで判定する脆弱性管理の仕組みには、この5件がまだ見えない。

狙われているのは「更新を配るためのツール」である概観

Dell System Update（DSU）は、BIOS・ファームウェア・ドライバの更新をLinux / Windows 上で配るための管理ツールである。企業の IT 部門がサーバ群の更新作業に使う。

この位置が本件の重さを決める（本記録の評価）。

  • DSU は管理対象に対して高い権限で動く。 更新を当てるのだから当然である。Dell は CVE-2026-86360 について「認証されていない攻撃者が root 権限で任意のコードを実行する」ために利用されうると書き、「脆弱なアプリケーションと基盤となるオペレーティングシステムの完全な侵害」に至りうるとしている（原文英語）。
  • 更新ツールへの攻撃は、正規の作業に紛れる。攻撃者が更新の経路に入れば、その後サーバに手を入れる行為は「更新作業」として記録に残る。勧告に IoC もログの確認方法も無いため、後から調べる手がかりが示されていない（unknowns 参照）。
  • 更新ツール自身の版が上がっているかは、見落とされやすい。 DSU は「更新のために入れておくもの」であり、それ自体の版を管理対象として台帳に載せている組織は多くない（本記録の評価）。

5件の内訳も同じ方向を示している。パストラバーサル2件（CVE-2026-86360・CVE-2026-71168）、権限／アクセス制御の付与の誤り2件（CVE-2026-86361・CVE-2026-86362）、証明書検証の不備1件（CVE-2026-63697）。「配られる側の経路を検証していない」「配る過程で置くファイルの場所を縛っていない」という形で揃っている（本記録の読み。Dell はこの5件を関連づけて説明していない）。

「認証不要の遠隔」という言葉と、ベクタの UI:R が噛み合っていない原因・手口

本記録が一次資料を読んで最も気になった点である。

Dell の文章はこう書いている（原文英語）——「認証されていない遠隔アクセスを持つ攻撃者がこれを悪用し、攻撃者によるファイルシステムへのアクセスに至る可能性がある」。

一方、同じ勧告が示す CVSS ベクタはこうである。

CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H
  • AV:N ネットワーク越し
  • AC:L 攻撃の複雑さは低い
  • PR:N 権限は不要
  • UI:R 利用者の操作が必要
  • S:C スコープの変更あり
  • C:H/I:H/A:H 機密性・完全性・可用性すべて High

UI:R が立っている。 だから 9.8 ではなく 9.6 なのである（本記録の読み）。つまり攻撃者が一方的に要求を投げて成立するものではなく、どこかで誰かが何かをする必要がある。

DSU の性格を踏まえると、本記録は次のように読む（推定であることを明示する）。DSU は管理者が能動的に起動して更新を取りに行くツールである。したがって「利用者の操作」とは管理者が DSU を実行して更新を取得・適用する行為で、そのときに受け取る内容の中に細工されたパスが含まれていれば書き込み先が制限の外へ出る——という形が自然である。同じ勧告に証明書検証の不備（CVE-2026-63697）が並んでいることも、この読みと整合する（取得元のなりすましが成立しやすくなる）。

ただし Dell は攻撃経路を一切説明していない。この差は実務の判断に直接響く。

  • 攻撃経路が「更新の取得元」なら、取得元の絞り込みと経路の保護が暫定の手になる。
  • 攻撃経路が「DSU が待ち受けるポート」なら、到達範囲の制限が手になる。
  • どちらなのか分からないため、勧告の指示（更新のみ）以外に打てる手が決まらない。

読者が持ち帰れる作法は、CVSS の数字ではなくベクタを読むことである（本記録の評価）。「9.6・認証不要・遠隔・root」という要約だけを見ると一方的に成立する攻撃に見えるが、UI:R は成立条件を変える。逆に、だから安全という話でもない——更新作業は定期的に、管理者の手で、必ず行われる操作である。

CVE 番号はあるのに CVE 記録が無い——スキャナにはまだ見えていない評価・解釈

本記録が確認したもう1つの一次情報である。

2026年10月6日時点で、CVE Program の API を引くとCVE-2026-86360 の記録は「存在しない」と返る（CVE_RECORD_DNE）。CVE 番号は Dell の勧告に載っているが、CVE 記録としては公開されていない。

実務上の含意は単純で、かつ重い（本記録の評価）。

  • CVE / NVD を取り込んで版番号を照合する脆弱性管理の仕組みは、この5件をまだ検出できない。 記録が無いのだから照合の材料が無い。
  • したがって「スキャナが何も言っていない」は本件について安全の根拠にならない。
  • 気づく経路はベンダーの勧告を直接読むか、報道で知るしかない。本記録がこの事案を把握したのも報道（Security Affairs）である。

同じ日の別の事案と並べると対照的である。 Atlassian の CVE-2026-21589（INC-2026-0375）は、ベンダー自身が採番機関として CVE 記録を公表の時点で公開していたため、本記録はその記録から修正版も影響範囲も直接読めた。そして記録と勧告の数字の食い違いまで検出できた。 Dell の場合は比べる相手が存在しない。

「CVE 番号が付いている」と「CVE 記録が公開されている」は別のことである——これを分けて扱わないと、番号を見た時点で台帳に載ったつもりになる（本記録の評価）。

5件中3件はローカルからの権限昇格である評価・解釈

遠隔・root の1件に目が行くが、内訳を見ると重心が違う。

CVE CVSS 成立の前提
CVE-2026-86360 9.6 認証なし・遠隔（ただし UI:R）。パストラバーサル → root でのコード実行
CVE-2026-86361 8.2 低権限のローカル利用者。権限の付与の誤り → 権限昇格
CVE-2026-86362 8.2 低権限のローカル利用者。アクセス制御の不備 → 権限昇格
CVE-2026-63697 7.6 高権限の遠隔攻撃者。証明書検証の不備 → コード実行
CVE-2026-71168 7.3 低権限のローカル利用者。パストラバーサル → コード実行

5件のうち3件が「低権限のローカル利用者」から成立する（本記録が数えた）。

サーバに一般利用者の足場がある環境では、こちらが実務上の入口になる（本記録の評価）。

  • 共有の管理サーバ・踏み台・ジャンプホストに DSU が入っている場合、そこにログインできる人は全員、権限昇格の経路を持つことになる。
  • ローカルの権限昇格は「外から入られてから」の話として軽く見られがちであるが、初期侵入が成立した後の広がりはここで決まる。
  • CVE-2026-63697（証明書検証の不備）は高権限の遠隔攻撃者が前提なので単独の入口にはなりにくいが、上の3件と組み合わせると連鎖が成立しうる（本記録の読み。Dell は組み合わせについて述べていない）。

5件すべてが同じ 2.3.0.0 で解消されるため、対応としては迷う余地が無い——上げるだけである。迷いが生じるのは「上げる対象を把握しているか」のところだけである。

CISO・経営層への示唆
  • 「更新を配るためのツール」を資産台帳の対象に入れる
    **DSU は BIOS・ファームウェア・ドライバの更新を配るためのツールである。** 管理対象に対して高い権限で動くため、 Dell 自身が**「基盤となるオペレーティングシステムの完全な侵害」**に 至りうると書いている。 それでも**「更新のために入れておくもの」は台帳の対象外になりやすく、 ツール自身の版が据え置かれる。**
    取るべき行動 資産台帳に**「管理・運用のために入れているツール」の区分**を作り、 更新ツール・構成管理のエージェント・バックアップのエージェント・ 監視のエージェントを**版つきで登録する。** **本件（DSU）を最初の1件として登録し、棚卸しの起点にする。**
  • 「スキャナが検出していない」を安全の根拠にしない運用にする
    **2026年10月6日時点で、CVE Program に CVE-2026-86360 の記録が存在しない** （本記録が API を引いて確認）。 **CVE 番号は勧告に載っているが、CVE 記録としては公開されていない。** CVE / NVD を取り込んで照合する仕組みには、**この5件がまだ見えない。** 気づく経路は**ベンダー勧告を直接読む**か**報道で知る**しかない。
    取るべき行動 脆弱性対応の判断様式に **「CVE 記録が公開されているか」「スキャナが対応しているか」**の2欄を作る。 **どちらも「いいえ」の事案は、スキャナの結果と無関係に手作業で確認する区分**に入れる。 自組織が使うベンダーの勧告ページを**購読対象として明示的に持つ。**
  • CVSS の数字ではなくベクタを判断材料にする手順を作る
    **Dell の文章は「認証されていない遠隔アクセスを持つ攻撃者」と書く一方、 ベクタには `UI:R`（利用者の操作が必要）が立っている。** 要約だけを読むと一方的に成立する攻撃に見えるが、成立条件は違う。 **逆に、`UI:R` だから安全という話でもない**—— 更新作業は管理者の手で必ず行われる操作である。
    取るべき行動 脆弱性の優先度判断の様式に **CVSS ベクタの `AV` / `PR` / `UI` / `S` を転記する欄**を置く （スコアだけの欄にしない）。 **ベンダーの文章とベクタが食い違う場合は、 その食い違いを記録してベンダーへ照会する。**
  • 回避策が示されない勧告を、更新計画の優先度判断に直結させる
    **DSA-2026-324 には回避策・緩和策の記載が無い。** 示されているのは「2.3.0.0 以降へできるだけ早く更新する」だけである。 **「待つ」という選択肢が存在しない勧告**であり、 通常の月次の更新サイクルに載せるかどうかの判断が要る。
    取るべき行動 勧告を受け取る手順に**「回避策があるか」**という欄を作り、 **無い場合は通常の更新サイクルから外して個別に期限を切る**と決めておく。 本件は**5件すべてが同じ 2.3.0.0 で解消される**ため、 判断としては単純である（対象の把握が唯一の作業になる）。

    取るべき行動 DSU を呼んでいる自動化の一覧を出し、 **検証環境で 2.3.0.0 を先に動かして呼び出し側の互換性を確認する。** **本番の更新作業の予定とぶつからない窓**で入れ替える。

    **勧告には IoC もログの確認方法も無い。** 更新ツールへの攻撃は**正規の更新作業の中に紛れる**ため、 ファイルやアドレスの照合では手がかりが得られない。 残るのは**「予定外の更新実行があったか」**という見方である（本記録の評価）。
    取るべき行動 DSU の実行記録（いつ・誰が・どのホストで）が取れているかを確認し、 **計画された更新作業の記録と突き合わせる。** 取れていない場合は**実行の記録を残す設定を先に入れる** （本件に遡って使えなくても、次に使える）。
  • 更新の取得元と経路を確認する（本件に効くかは不確かだが、独立して意味がある）
    **Dell は攻撃経路を説明していない。** ただし CVSS の `UI:R` と、同じ勧告に並ぶ **証明書検証の不備（CVE-2026-63697）**から、 本記録は「更新の取得の経路が関わる可能性がある」と読む（推定である）。 **取得元のなりすましや経路上の改変は、本件と無関係にも成立する課題である。**
    取るべき行動 DSU が更新を取得する先（Dell のリポジトリ／内部のミラー・配布サーバ）と **その経路の保護（TLS の検証・取得元の固定）**を確認する。 **内部ミラーを使っている場合は、ミラーへの書き込み権限を持つ者の一覧**を出す。
  • ベンダー勧告の版番号を、自機で実際に確認する手順を持つ
    **CVE 記録が未公開なのでスキャナが照合してくれない**（本記録が確認）。 さらに勧告の記載は**「2.3.0.0 より前」**だけで、 **どの版から脆弱だったのかが示されていない。** **「自機の DSU は何版か」を答えられないと、対応の完了を宣言できない。**
    取るべき行動 DSU の版を取得するコマンドを**構成管理または点検スクリプトに入れ、 ホスト一覧に対して一括で取る。** 結果を**対応前・対応後の2回取って記録に残す** （スキャナの結果が無い事案では、これが唯一の証跡になる）。
