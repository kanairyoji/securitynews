米連邦捜査局（FBI）と米シークレットサービス（USSS）は2026年10月6日、共同サイバーセキュリティ勧告 JCSA-20261006-01「FortiBleed Operations Continue Targeting Exposed Systems Leading to Reports of Lockouts」（TLP:CLEAR）を公表しました。

FortiBleed は、インターネットに面した Fortinet FortiGate ファイアウォールと SSL VPN ゲートウェイを標的とする現在も進行中の、世界規模の認証情報侵害キャンペーンです。勧告は SOCRadar が194か国で8万6,644台以上の侵害済み機器を確認したと引用しています。

本記録が中心と見るのは、この事案が「脆弱性の事案ではない」という点です。Fortinet PSIRT は「これは Fortinet の新しい脆弱性ではなく、この活動は最近のいかなるインシデントや勧告とも関係しない」と明記しています（原文英語）。成立させているのは次の3つの組み合わせです。

  1. 使い回し・漏えい済みの認証情報——過去の Fortinet 流出ダンプと情報窃取マルウェアのログを素材にする
  2. 旧来の SHA-256 によるパスワード保存——オフラインでの解読を現実的にする
  3. インターネットに露出した管理機能とゲートウェイ——偵察と総当たりの的になる

つまりパッチを当てるだけでは閉じない。 勧告も「標準的なパッチ適用とパスワードリセットを超えた対処が必要になる」と述べています。

もう一つの特徴は、攻撃の全工程が見えていることです。攻撃者が自らのバックエンドサーバーを誤って公開（オープンディレクトリ）したため、偵察 → 認証情報の収集 → GPU クラスタによるオフライン解読（Hashcat・Hashtopolis）→ハニーポットの除外と標的の優先順位付け → 新規管理者アカウントの作成による永続化 → Active Directory の列挙と総当たりによる横展開 → 初期アクセスの販売という、端から端までの流れが観測されました。この集団はイニシャルアクセスブローカーとして機能しています。

実務上もっとも警戒すべきは ロックアウトです。攻撃者は既存アカウントを削除またはパスワードを変更することがあり、組織が自分の機器から締め出される事例が報告されています。さらに FortiBleed の攻撃連鎖は、ランサムウェア実行部門の侵入口としても観測されています。評価・示唆は本記録の判断として分けて書きます。

    **攻撃者は検証済みの正当な資格情報（T1078）で被害環境の内部へ入り、 Active Directory の列挙（T1087）とパスワードスプレーを行ってアクセスを拡大し、特権アカウントを特定した。** **この工程の帰結として、集団は「動作する VPN 設定」と標的リストを添えて アクセスを販売するイニシャルアクセスブローカーとして機能していた。** **勧告は、FortiBleed の攻撃連鎖がランサムウェア実行部門の初期侵入口として 観測されていると述べている**（具体的な集団名は非公表）

    **【ロックアウト】** 勧告の表題に掲げられた影響である。 **攻撃者がシステム上の元のアカウントを削除するかパスワードを変更した場合、 一部の被害組織は自分の Fortinet 機器から締め出される。** 勧告は「敵対者は正当な管理者がログインできないよう、意図的にアカウントのアクセスを ロック・無効化・改変した（T1531）」とする。 **一定の事例では、既存アカウントを削除して組織のアクセスを阻み、 環境内で横展開を試みるあいだ永続化を維持していた。** **ロックアウトが発生した組織の件数と、締め出された機器の復旧手段はいずれも公表されていない**

これは「新しい脆弱性」の事案ではない——認証情報の使い回し・旧来のハッシュ方式・露出した構成の3つが噛み合っている原因・手口出典 [1] [2]

本件を「FortiGate の脆弱性」と読むと対処を誤る。Fortinet PSIRT は2026年6月19日のブログで明確に否定している。

「これは Fortinet の新しい脆弱性ではなく、この活動は最近のいかなるインシデントや勧告とも関係しない」（原文英語）

Fortinet はこれを既知の認証情報の再利用と総当たり攻撃によるものとしている。成立させているのは、次の3つの組み合わせである。

  1. 使い回し・漏えい済みの認証情報——勧告によれば、攻撃者は過去の Fortinet 流出ダンプと情報窃取マルウェア（インフォスティーラー）のログを素材に、クレデンシャルスタッフィングとパスワードスプレーを行った
  2. 旧来の SHA-256 によるパスワード保存——勧告は「legacy SHA-256 password storage」を大規模な収集と解読を可能にする要因として挙げる。SHA-256 は高速に計算できるため、GPU によるオフライン解読が現実的になる
  3. インターネットに露出した管理機能とゲートウェイ——攻撃の第一歩は露出した FortiGate SSL VPN ポータルの走査である

力点の違いに注意が要る。 Fortinet は「新しい脆弱性ではない（＝製品の欠陥ではない）」と述べ、勧告は「旧来の SHA-256 パスワード保存を悪用する」と述べる。矛盾ではない。製品に欠陥があるのではなく、古い保存方式のまま運用されている状態が悪用されているという同じ事態を、どちらから見るかの違いである（本記録の読み取り）。

対処の方向はここから決まる。パッチを当てるだけでは閉じない。必要なのは、①露出を減らす、②認証情報を入れ替える、③多要素認証を強制する、④パスワードの保存方式を PBKDF2 に移す——という4つである。Fortinet は PBKDF2 への移行のために FortiOS 7.4・7.6・8.0 系の最新版への更新と、旧来方式を排除する設定（set login-lockout-upon-weaker-encryption）を案内している。

最も切迫するのはロックアウト——攻撃者が既存アカウントを削除し、組織が自分の機器を操作できなくなる業務・事業への影響出典 [1]

勧告が表題にまで掲げたのが ロックアウトである。本文はこう述べる（原文英語を本記録が訳した）。

「初期の対応から得られた知見によれば、脅威アクターがシステム上の元のアカウントを削除するかパスワードを変更した場合、一部の被害組織は自分の Fortinet 機器から締め出されることがある。初期侵入の際、脅威アクターはその機器にそれまで存在しなかった新規アカウントを作成する。一定の事例では、脅威アクターは既存アカウントを削除して組織が影響を受けた機器にアクセスできないようにし、環境内で横展開を試みるあいだシステム上の永続化を維持する」

二重の意味で厄介である。

  • 防御側が対処の手段を失う——ファイアウォールの設定を確認し、不正なアカウントを削除し、ログを調べるという対処のすべてが、その機器に管理者としてログインできることを前提にしている
  • 攻撃者は永続化を保ったまま横展開を続ける——締め出しは逃走ではなく、時間を稼ぐ手段である

勧告はこの局面の復旧手順を示していない。 インシデント対応の節は「侵害されたホストを特定し、隔離するかオフラインにする」から始まるが、管理アカウントを削除された機器をどう取り戻すか（物理コンソール経由の復旧・工場出荷状態への初期化など）には触れていない。ロックアウトが発生した組織の件数も示されていない（「一部の被害組織」とのみ）。実務上もっとも切迫する局面の手順が欠けている（本記録の評価）。

なお勧告は REST API キーについても独立した節を設けている。FortiGate の REST API キーは設定・バックアップ作成・監視の自動化を可能にするため、不明または想定外のキーは重大なリスクになるとし、すべての API キーを点検して正当な用途を確認し、不明なキーを削除して正当なキーを更新することを推奨している。管理者アカウントの点検だけでは面が残るという指摘である。

勧告が示した対処は「攻撃面を減らす」から始まる——パッチではなく構成と認証の設計を変える対策・注意喚起出典 [1]

勧告の対処は次の順で示されている（原文英語を本記録が訳した）。順序そのものが意味を持つ——最初に来るのは更新ではなく露出の削減である。

  1. 攻撃面を減らし、管理アクセスを締める——機器の外部からの管理を信頼済みホストで限定する（良い）／local-in ポリシーで限定する（より良い）／インターネット経由の管理を完全に撤去する（最善）
  2. すべての管理・VPN セッションを終了し、認証情報をリセットする——有効な管理セッションをすべて終了し、Fortinet の VPN・管理のパスワードをすべてリセット（特にインターネットに面したもの）、強いパスワードポリシーを強制する
  3. フィッシング耐性のある多要素認証を有効にする——すべてのリモートアクセスと管理アカウントに要求し、外部ゲートウェイと管理インターフェースで強制されていることを確認する
  4. 設定を検証する——ファイアウォールと VPN のユーザーその他の設定に不正な変更が無いかを確認する。できれば既知の正しい設定と比較する。特に見慣れないアカウントの追加に注意する
  5. ログを確認する——ファイアウォール・VPN・認証・ドメインコントローラーのログを、横展開・異常なアクセス・不審なアカウント・不正な設定変更について確認する
  6. 安全な資格情報保存を確保する——PBKDF2 を管理者資格情報の保存に用いていることを確認し、Fortinet の案内に従って旧来の弱いハッシュを削除する（FortiOS v7.2.11 以降で PBKDF2 をハッシュ関数として強制できる）
  7. REST API キーを点検する——すべてのキーの正当な用途を確認し、不明なキーを削除し、正当なキーを更新する

ここからは本記録の作成者の評価である。

第一に、本件は脆弱性管理の枠組みでは捕まらない。 Fortinet は「新しい脆弱性ではない」と明言し、CVE 番号も KEV への収載も存在しない。つまり脆弱性管理の仕組み（スキャナ・CVE の追跡・パッチの適用率）をどれだけ回しても、この事案は検出されず、対処済みにもならない。必要なのは別の3つの台帳である——①インターネットに露出している管理面の一覧、②機器上のアカウントと API キーの一覧、③認証情報の保存方式と更新時期の記録。 「パッチは当たっています」という報告と、本件のリスクはほとんど無関係である。

第二に、8万6,644台という規模は「設定の既定値が長く放置されること」の帰結である。 194か国というのは事実上の全世界で、特定の業種にも地域にも偏っていない。これだけの数が同じ状態にあるのは、攻撃が巧妙だからではなく、①管理をインターネットに出す構成が広く採られ、②旧来のハッシュ方式が既定のまま残り、③多要素認証が後付けの選択肢だったからである（本記録の評価）。境界機器は「置いたら触らない」運用になりやすく、設置時の設計がそのまま年単位で残る。本件への対処は、ほとんどが設置時に決めるべきだった設定の見直しである。

第三に、ロックアウトという影響は、境界機器の管理経路の単一性を突いている。攻撃者が既存の管理アカウントを削除すれば、組織は対処の手段そのものを失う。ログを見る、設定を比べる、不正なアカウントを消す——すべてがその機器にログインできることを前提にしている。ここから出てくる備えは「管理の経路を二つ持つ」ことである——物理コンソールへの到達手段、帯域外の管理網、設定のバックアップ、そして何より設定の正本を外部に持つこと。勧告が「できれば既知の正しい設定と比較する」と述べるのはこの点に触れている。正本が機器の中にしか無ければ、比較対象も復旧の土台も失われる。

第四に、攻撃者がハニーポットを除外し、収益で標的を並べていたという事実は、防御の前提を一つ変える。 これは在庫管理である。侵入できた機器を商品として整え、買い手の価値基準（支払い能力・網の広がり）で並べている。つまり「侵害されたが、まだ何も起きていない」状態が商品として保管されているということだ。認証情報が解読された時点から、実際の攻撃までに時間差がある。だからこそ過去に露出していた機器のパスワードをいま全部入れ替えることに意味がある—— まだ使われていないだけの資格情報が、在庫に入っている可能性がある（本記録の評価）。

第五に、Fortinet の注意喚起（2026年6月19日）から共同勧告（10月6日）まで約3か月半あり、勧告の表題は「Operations Continue」である。製造元が注意を出しても対処が進まなかったことを示す。理由は推測になるが、「脆弱性ではない」というメッセージが「自社は対応不要」と読まれた可能性は考えられる（本記録の推測であり、裏付けは無い）。ベンダーが「製品の欠陥ではない」と言うことと、利用者が「対処しなくてよい」ことは別である。本件で求められている対処（露出の削減・認証情報の総入れ替え・多要素認証・ハッシュ方式の移行）は、いずれも利用者側でしか実施できない。

layer 0 は FortiBleed の運営者と、意図せず公開されたバックエンドサーバー（これにより全工程が可視化された）。 layer 1 は認証情報の素材（過去の Fortinet 流出ダンプ・情報窃取マルウェアのログ）と GPU 解読クラスタ（Hashcat・Hashtopolis）。 layer 2 は標的——インターネットに露出した FortiGate SSL VPN ゲートウェイ（194か国・8万6,644台以上）と、 攻撃者が作成した新規管理者アカウント。 layer 3 は被害組織の内部（Active Directory の列挙・横展開）とロックアウト。 layer 4 は収益化——初期アクセスの販売先となるランサムウェア実行部門と、 注意喚起を行った FBI・USSS・Fortinet。 **点線は帰属が公表されていない関係を表す。本件は新しい脆弱性の悪用ではない。**

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察機会はあったが検知できず
**本記録の評価である（勧告は被害組織側の検知について述べていない）。** インターネットからの走査は常時発生しており、**走査そのものを検知しても行動につながらない。** しかしこの段階で防御側が取れる行動は検知ではなく**確認**である—— **自組織の FortiGate の管理面と VPN ポータルが外部から見えているかは、 攻撃者と同じ方法（外部からの到達性の確認）で把握できる。** 勧告の対処の第一項が「攻撃面を減らす」である理由はここにある
侵入を防げた外部からの機器管理をインターネットから撤去する（最善）、 または信頼済みホスト・local-in ポリシーで限定する　**勧告の対処の第一項であり、本記録も最も効果が高いと評価する。** 認証情報が漏れていても、**到達できなければ使えない。** 勧告は「信頼済みホスト（良い）／local-in ポリシー（より良い）／ インターネット管理の撤去（最善）」と段階を明示している。 **拠点が多い組織では帯域外管理の整備が必要になるため、良い→より良い→最善の順で進める形になる**
検知できた自組織の資産がインターネットからどう見えるかを定期的に外部から確認する　**本記録の評価による。** 境界機器は「置いたら触らない」運用になりやすく、 設置時の構成が年単位で残る。 **資産台帳ではなく「外から見える面の一覧」を持ち、月次で差分を確認する**ことで、 意図せず露出した管理面を見つけられる
認証情報アクセス機会はあったが検知できず
**本記録の評価である（勧告は被害組織側の検知について述べていない）。** **総当たり・パスワードスプレーは認証ログに現れる種類の活動である**—— 失敗の急増、同一アカウントへの異なる接続元からの試行、 異なるアカウントへの同一パスワードでの試行。 **一方、解読はオフラインで行われるため被害組織側からは一切見えない。** つまり**ハッシュが持ち出された時点で、防御側の観測可能性は失われる。** ここが「SHA-256 保存が危険」という指摘の実務的な意味である
影響を限定できた管理者資格情報の保存を PBKDF2 に移し、旧来の弱いハッシュを削除する （FortiOS v7.2.11 以降で強制できる。Fortinet は 7.4・7.6・8.0 系の最新版への更新を案内）　**勧告と Fortinet の双方が挙げる対処である。** **持ち出しを防ぐものではなく、持ち出された後の解読を困難にするものである。** SHA-256 は高速に計算できるため GPU での解読が現実的だが、 PBKDF2 は反復回数によって計算量を上げられる。 **注意点は順序である**——旧来方式を排除する設定は弱い暗号方式のアカウントをロックアウトするため、 **移行前に全アカウントのパスワードを再設定しないと自組織を締め出す**（本記録の評価）
侵入を防げたすべてのリモートアクセス・管理アカウントにフィッシング耐性のある多要素認証を強制する　**勧告の対処の第三項。本件の核心に効く。** **このキャンペーンの収益は「使える平文のパスワード」に依存している。** 解読が成功しても第二要素が無ければ認証は通らない。 **要点は「導入済み」ではなく「全アカウントで強制されている」ことで、 勧告も「外部ゲートウェイと管理インターフェースで強制されていることを確認する」と念を押している。** サービスアカウント・委託先の作業用アカウントが例外になっていれば面は残る
検知できたVPN・管理インターフェースの認証ログで、失敗の急増と総当たりの痕跡を検知する　**本記録の評価による。** 勧告の侵害指標には 「現在総当たり攻撃を行っているか、侵害されたアカウントで認証に成功した IP アドレス」の 一覧が含まれている。 **IP での突合は有効だが変わりやすいため、 「失敗率の急変」「同一パスワードでの複数アカウントへの試行」という 振る舞いでの検知を併せて持つほうが長持ちする**
永続化機会はあったが検知できず
**本記録の評価である（勧告は被害組織側の検知について述べていない）。** **境界機器上の管理者アカウントの新規作成は、頻度の低い、明確に異常な事象である。** 日常的に起こることではないため、**検知の規則として誤検知が少なく、実装も容易な部類に入る。** 勧告が対処として「**見慣れないアカウントの追加に特に注意する**」「**既知の正しい設定と比較する**」を挙げ、 さらに「**よく知られている侵害済みアカウント名の一覧**」を提供しているのは、 **この段階が最も確実に捉えられる機会である**ことを示している
検知できた境界機器の設定を外部に保管し、定期的に差分を比較する（アカウント・管理者権限・local-in ポリシー・API キー）　**勧告の「できれば既知の正しい設定と比較する」に対応する。本記録が最も費用対効果が高いと評価する統制である。** **設定の正本が機器の中にしか無ければ、比較対象も、ロックアウト後の復旧の土台も失われる。** 日次で設定を取得して版管理に入れ、**差分が出たら通知する**だけで、 新規管理者アカウントの追加は翌日には見つかる
検知できたFortiGate 上のアカウント作成・権限変更・API キー発行を監視基盤へ送り、発生時に通知する　**本記録の評価による。** 境界機器のログを SIEM へ送っていない組織は少なくない。 **アカウントと権限の変更だけに絞れば転送量は小さく、 本件で最も重要な事象を確実に捉えられる**
侵入を防げたREST API キーを棚卸しし、不明なキーを削除して正当なキーを更新する　**勧告が独立した節を設けて推奨している。** API キーは設定・バックアップ作成・監視の自動化を可能にするため、 **攻撃者が発行したキーが残っていれば、管理者アカウントを消しても経路が残る。** **管理者アカウントの点検だけでは面が残る**という指摘である。 実施には「どの自動化がどのキーを使っているか」の台帳が要る（本記録の評価）
横展開機会はあったが検知できず
**本記録の評価である（勧告は被害組織側の検知について述べていない）。** **VPN 経由の正当な資格情報による接続は、認証だけ見れば正常に見える。** 捉えられるのは振る舞いである——**平常と違う接続元・時間帯からの VPN 接続、 接続直後の Active Directory の広範な列挙、内部でのパスワードスプレー。** 勧告が「**ファイアウォール・VPN・認証・ドメインコントローラーのログを横展開について確認する**」と 4種類のログを並べて挙げているのは、**単独のログでは判別できない**ことを示している（本記録の読み取り）
検知できたVPN 接続後の内部の振る舞いを監視する（Active Directory の広範な列挙・ 短時間での多数アカウントへの認証試行）　**本記録の評価による。** 正当な資格情報での侵入は認証では止められないため、 **検知は侵入後の行動に移る。** **ディレクトリの列挙は、正規の利用者がほとんど行わない操作である**という性質を使う
影響を限定できたVPN で到達できる範囲を業務単位に区切り、ドメインコントローラーへの直接到達を認めない　**本記録の評価による。** 本件で売られているのは「動作する VPN 設定」である。 **買い手が得る価値は、その VPN から何に到達できるかで決まる。** 到達範囲を業務単位に区切れば、**同じ資格情報でも商品価値が下がり、被害の範囲も区切られる**
侵入を防げた過去にインターネットへ露出していた機器の全アカウントのパスワードを、 侵害の有無を待たずに入れ替える　**勧告の対処の第二項に対応する。本記録が最も見落とされやすいと評価する統制である。** 攻撃者は**ハニーポットを除外し、収益で標的を並べ、在庫として保管**していた。 **つまり「侵害されたが、まだ何も起きていない」状態が商品として存在する。** 解読から実際の攻撃までに時間差があるため、 **いま異常が見えないことは、資格情報が在庫に無いことを意味しない**
影響（暗号化・破壊・改ざん）検知した
**ロックアウトは、起きた時点で否応なく分かる**——管理者がログインできなくなる。 **問題は「気づけるか」ではなく「気づいた時に何ができるか」である**（本記録の評価）。 勧告のインシデント対応の節は「侵害されたホストを特定し隔離する」から始まるが、 **その操作にはその機器への管理アクセスが前提になる。 管理アカウントを削除された機器をどう取り戻すかの手順は勧告に含まれていない。** **実務上もっとも切迫する局面の手順が欠けている**
復旧を早められた境界機器への管理経路を二つ持つ（物理コンソールへの到達手段・帯域外管理網）　**本記録の評価による。本件の影響に直接対応する備えである。** 攻撃者が管理アカウントを削除すれば、**ネットワーク経由の管理はすべて失われる。** **物理コンソール（シリアル接続）への到達手段を拠点ごとに確認しておくこと**が、 遠隔地の機器ではとくに重要になる。 **「誰が現地に行けるか」を含めて手順にする**
復旧を早められた機器の設定の正本を外部に保持し、工場出荷状態からの復元手順と所要時間を測っておく　**本記録の評価による。** ロックアウトされた機器を取り戻す最終手段は初期化と再設定である。 **設定の正本が機器の中にしか無ければ、初期化は業務の全面停止を意味する。** 設定を外部に版管理で持ち、**実際に復元して所要時間を測る**ことで、 「初期化する」という判断が選択肢になる
影響を限定できた機器上の管理者アカウントを複数持ち、少なくとも1つは日常運用で使わない緊急用として 別の資格情報で保管する　**本記録の評価による。** 攻撃者が既存アカウントを削除する手口に対しては、 **削除されずに残るアカウントがあるかどうかが分かれ目になる。** ただし**緊急用アカウントも同じ機器上にあれば同様に削除されうる**ため、 これは経路の二重化（物理コンソール）の代替にはならない。 **併せて、緊急用アカウントのパスワードが旧来のハッシュ方式のまま残っていないかも確認する**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**FBI と USSS は、侵害指標（C2・プロキシノード・ビーコン中継・Hashtopolis に使われた IP アドレス、 総当たりを行っている IP アドレスの一覧、よく知られている侵害済みアカウント名の一覧）、 MITRE ATT&CK v19.1 への対応づけ、インシデント対応の手順、7項目の対処を TLP:CLEAR で公表した。** 一方で**攻撃者の帰属、国別の内訳、ロックアウトの件数、 ランサムウェア集団の特定には触れていない**機能した**本記録の作成者の評価である。防御に使える情報の出し方として水準が高い。** **TLP:CLEAR（制限なく共有可）で出し、 侵害指標に「役割」（C2／プロキシ／ビーコン中継／Hashtopolis）を付し、 対処を「良い／より良い／最善」の段階で示し、 さらに「侵害済みアカウント名の一覧」まで提供している。** **とくに対処の第一項を「パッチ適用」ではなく「攻撃面を減らす」に置いた点が重要である**—— 本件は脆弱性の事案ではないため、順序を誤ると読者が対処を誤る。 「標準的なパッチ適用とパスワードリセットを超えた対処が必要になる」と明記している点も同様である。 **惜しいのは、表題に掲げたロックアウトの復旧手順が含まれていないことである** （下の項目で別に評価した）
**勧告は、ロックアウト（攻撃者が既存アカウントを削除・パスワード変更して組織が自機器から 締め出される）を表題に掲げ、「標準的なパッチ適用とパスワードリセットを超えた対処が必要になる」と警告した。 一方で、締め出された機器をどう取り戻すかの具体的な手順は示していない**不十分**本記録の作成者の評価である。** ロックアウトを表題に掲げ、 「標準的な対処を超えたものが必要」と警告しておきながら、 **インシデント対応の節は「侵害されたホストを特定し隔離する」から始まる。 その操作にはその機器への管理アクセスが前提である。** **締め出された管理者が最初に必要とするのは、物理コンソール経由の復旧か、 工場出荷状態への初期化と設定の復元かという判断材料である。** 機種依存で汎用の手順が書きにくい事情は理解できるが、 **少なくとも「設定の正本を外部に保持しているかを先に確認せよ」という一文があれば、 読者は初期化という選択肢を持てたかどうかを判断できた**（本記録の評価）。 ロックアウトの**件数も示されていない**（「一部の被害組織」とのみ）ため、 読者は自組織の優先度を測りにくい
**勧告は、すべての管理・VPN セッションの終了と、 Fortinet の VPN・管理パスワードの全リセット（特にインターネットに面したもの）を推奨した。 侵害の確認を条件とせず、露出した機器を持つすべての組織に求めている**機能した**本記録の作成者の評価である。** 攻撃者は**ハニーポットを除外し、 収益と網構成で標的に優先順位を付け**ていた。 **これは「侵害されたが、まだ何も起きていない」状態が在庫として保管されていることを意味する。** 解読から実際の攻撃までに時間差があるため、 **「いま異常が見えない」ことは資格情報が在庫に無いことを意味しない。** **侵害の確認を待たずに全リセットを求める判断は、この構造に対して正しい。** 業務の中断という代償を伴うが、代替手段が無い
CISO・経営層への示唆
  • 「脆弱性ではない」事案を捕まえる台帳を、脆弱性管理の外側に持つ
    Fortinet は「これは Fortinet の新しい脆弱性ではない」と明言しており、CVE 番号も KEV への収載も無い。 **脆弱性管理の仕組み（スキャナ・CVE の追跡・パッチ適用率）をどれだけ回しても、 この事案は検出されず対処済みにもならない**
    取るべき行動 脆弱性管理とは別に3つの台帳を持ち、四半期ごとにレビューする—— **①インターネットから到達できる管理面の一覧、②境界機器上のアカウントと API キーの一覧、 ③認証情報の保存方式と最終更新時期の記録。** **経営報告では「パッチ適用率」と並べてこの3点の状態を出す** （パッチ適用率の報告だけでは本件のリスクが見えない）
  • 境界機器の管理経路を二重化し、「自機器から締め出されたとき」の手順を持つ
    **攻撃者が既存の管理アカウントを削除またはパスワードを変更し、 組織が自分の Fortinet 機器から締め出される事例が報告されている。** 対処（ログの確認・設定の比較・不正アカウントの削除）はすべてその機器にログインできることを前提にしている
    取るべき行動 **①拠点ごとに物理コンソール（シリアル接続）への到達手段と「誰が現地に行けるか」を確認して手順書に書く、 ②機器の設定の正本を外部に版管理で保持する、 ③工場出荷状態からの復元を実際に試して所要時間を測る。** **設定の正本が機器の中にしか無ければ、初期化は業務の全面停止を意味する**—— 測っておけば「初期化する」が選択肢になる
  • 露出していた期間があるなら、侵害の確認を待たずに資格情報を総入れ替えする
    攻撃者は**ハニーポットを除外し、収益と網構成に基づいて標的に優先順位を付け**ていた。 **これは「侵害されたが、まだ何も起きていない」状態が商品として在庫に保管されていることを意味する。** 解読から実際の攻撃までに時間差がある
    取るべき行動 **「異常が見えないこと」を安全の根拠にしない方針を明文化する。** インターネットに露出していた境界機器について、 **侵害の痕跡の有無にかかわらず全アカウントのパスワードをリセットする**判断をあらかじめ経営として承認しておく （業務の中断を伴うため、事案発生後に合意形成すると遅れる）。 併せて**多要素認証の強制を同時に実施する**
  • ベンダーの「製品の欠陥ではない」を「対処不要」と読まない運用にする
    Fortinet の注意喚起（2026年6月19日）から共同勧告（2026年10月6日）まで約3か月半あり、 **勧告の表題は「Operations Continue（活動は継続している）」である**
    取るべき行動 ベンダーの告知を受け取ったときの判定を「**自社に脆弱性があるか**」ではなく 「**自社で実施すべき作業があるか**」に変える。 本件で求められている対処（露出の削減・認証情報の総入れ替え・多要素認証・ハッシュ方式の移行）は、 **いずれも利用者側でしか実施できない。** 告知の処理手順に「**利用者側の作業の有無**」を判定する項目を入れる
  • イニシャルアクセスブローカーの存在を前提に、侵害の「次」を想定した計画を持つ
    この集団は**動作する VPN 設定と標的リストを添えてアクセスを販売**しており、 **FortiBleed の攻撃連鎖はランサムウェア実行部門の初期侵入口として観測されている**
    取るべき行動 VPN・境界機器の侵害が確認された場合の対応計画に、 **「アクセスが転売されている前提での範囲設定」**を書き込む—— VPN から到達できた範囲全体を侵害想定に含め、 **ランサムウェアの初動（バックアップの隔離確認・復旧目標時間の確認）を同時に起動する。** **「認証情報が漏れた」で閉じる対応計画では、転売された後の攻撃に間に合わない**
セキュリティ技術者への示唆
  • 自組織の境界機器が外部からどう見えるかを確認し、管理面をインターネットから撤去する
    攻撃の第一歩は**露出した FortiGate SSL VPN ポータルの自動走査**である。 勧告の対処の第一項は「攻撃面を減らし管理アクセスを締める」で、 **信頼済みホスト（良い）／local-in ポリシー（より良い）／ インターネット管理の撤去（最善）**と段階が示されている
    取るべき行動 **外部の視点から自組織の IP 範囲を走査し、到達できる管理インターフェースと VPN ポータルを一覧にする。** 管理面はインターネットから撤去する（最善）。 撤去できないものは **local-in ポリシーで接続元を限定**する。 **「外から見える面の一覧」を資産台帳とは別に持ち、月次で差分を確認する**
  • 境界機器の設定を外部に版管理で保持し、日次で差分を比較する
    攻撃者は**それまで機器に存在しなかった新規の管理者アカウントを作成**して永続化した。 勧告は「**できれば既知の正しい設定と比較する**」「**見慣れないアカウントの追加に特に注意する**」とし、 **「よく知られている侵害済みアカウント名の一覧」も提供している**
    取るべき行動 FortiGate の設定を日次で取得して版管理（git 等）に入れ、**差分が出たら通知する。** 確認対象は**管理者アカウント・権限・local-in ポリシー・REST API キー**。 **これは新規アカウントの追加を翌日には見つけられる、本件で最も費用対効果の高い統制である**（本記録の評価）。 **設定の正本が外部にあることは、ロックアウト後の復旧の土台にもなる**
  • 管理者資格情報の保存を PBKDF2 へ移す——ただしパスワードの再設定を先に行う
    勧告は**旧来の SHA-256 によるパスワード保存**を大規模な解読を可能にする要因として挙げる。 SHA-256 は高速に計算できるため GPU でのオフライン解読が現実的になる
    取るべき行動 **FortiOS を PBKDF2 に対応した版（v7.2.11 以降。Fortinet は 7.4・7.6・8.0 系の最新版を案内）へ更新し、 `set login-lockout-upon-weaker-encryption` で旧来方式を排除する。** **順序に注意する**——この設定は弱い暗号方式のアカウントをロックアウトするため、 **移行前に全アカウントのパスワードを再設定しないと自組織を締め出す**（本記録の評価）。 作業の順序を手順書に明記し、物理コンソールへの到達手段を確保してから着手する
  • すべてのリモートアクセス・管理アカウントで多要素認証が「強制されている」ことを確認する
    **このキャンペーンの収益は「使える平文のパスワード」に依存している。** 解読が成功しても第二要素が無ければ認証は通らない。 勧告は「**外部ゲートウェイと管理インターフェースで強制されていることを確認する**」と念を押している
    取るべき行動 **「導入済み」ではなく「全アカウントで強制」を確認する。** 確認すべき例外は、**サービスアカウント・委託先の作業用アカウント・ 緊急用アカウント・API による認証**である。 **フィッシング耐性のある方式（FIDO2 等）を優先し、SMS・メールのコードは避ける**
  • REST API キーを棚卸しし、不明なキーを削除して正当なキーを更新する
    勧告は独立した節を設け、「REST API キーは設定・バックアップ作成・監視の自動化を可能にするため、 **不明または想定外のキーは重大なリスクになる**」としている。 **攻撃者が発行したキーが残っていれば、管理者アカウントを消しても経路が残る**
    取るべき行動 FortiGate 上の全 API キーを列挙し、**「どの自動化がどのキーを使っているか」の対応表を作る。** 対応先が不明なキーを削除し、正当なキーを更新する。 **対応表が無い状態で更新すると自動化が止まるため、台帳の作成を先に行う**（本記録の評価）
  • 勧告の侵害指標を自組織のログと突き合わせる——ただし精査してから遮断する
    勧告は C2（45.154.12.132）・プロキシノード（154.202.59.169・103.27.186.156）・ ビーコン中継（45.155.250.158）・攻撃連鎖のインフラ（193.8.187.2・193.8.187.42・ 85.11.187.8＝Hashtopolis）と、総当たりを行っている IP アドレスの一覧を示し、 **「侵害指標は遮断等の措置を取る前に調査・精査すること」**を推奨している
    取るべき行動 **ファイアウォール・VPN・認証・ドメインコントローラーの4種類のログ**に対して指標を突き合わせる （勧告が4種類を並べているのは、単独のログでは横展開を判別できないため）。 **ポートは 4332・4432 を含む複数で通常は HTTPS へビーコンするため、 ポートでの絞り込みに頼らない。** IP は変わりやすいので、**「認証失敗率の急変」「同一パスワードでの複数アカウントへの試行」 「VPN 接続直後の Active Directory の広範な列挙」という振る舞いの検知を併せて持つ**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Fortinet FortiGate ファイアウォールまたは SSL VPN ゲートウェイを運用しており、インターネットから管理面または VPN ポータルに到達できる攻撃の第一歩は露出した FortiGate SSL VPN ポータルの自動走査であり、194か国で8万6,644台以上の侵害が検証されている
認証・認可□ 境界機器の管理者資格情報が旧来の SHA-256 で保存されており、PBKDF2 へ移行していない勧告は旧来の SHA-256 パスワード保存を、大規模な収集と GPU によるオフライン解読を可能にする要因として挙げている
認証・認可□ リモートアクセス・管理アカウントの一部（サービスアカウント・委託先の作業用・緊急用・API）で多要素認証が強制されていないこのキャンペーンの収益は解読した平文パスワードが使えることに依存しており、第二要素があれば認証は通らない
運用・監視□ 境界機器の設定の正本を外部に保持しておらず、アカウント・API キーの差分を定期的に比較していない攻撃者は機器にそれまで存在しなかった新規管理者アカウントを作成して永続化し、勧告は既知の正しい設定との比較を推奨している
運用・監視□ 境界機器への管理経路が一つしかなく、物理コンソールへの到達手段と設定からの復元手順を確認していない攻撃者が既存アカウントを削除またはパスワード変更し、組織が自機器から締め出される事例が報告されている
運用・監視□ FortiGate の REST API キーの棚卸しをしておらず、どの自動化がどのキーを使っているかの台帳が無い勧告は不明な API キーが重大なリスクになるとし、独立した節を設けて点検を推奨している
体制・契約□ ベンダーの告知を「自社に脆弱性があるか」で判定しており、「利用者側で実施すべき作業があるか」を見ていないFortinet は新しい脆弱性ではないとしており CVE も KEV 収載も無いが、活動は継続して共同勧告に至っている
体制・契約□ VPN・境界機器の侵害時の対応計画に、アクセスが転売される前提の範囲設定とランサムウェアの初動が含まれていないこの集団はイニシャルアクセスブローカーとして動作する VPN 設定を販売し、ランサムウェア実行部門の侵入口として観測されている
