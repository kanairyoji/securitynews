INC-2026-0381日立エナジーRTU500のEoL版に認証バイパス

CISA は2026年10月6日、日立エナジー（Hitachi Energy）の製品に関する4件の ICS 勧告を同時に再掲した。中心は変電所用の遠隔端末装置 **RTU500 シリーズ CMU ファームウェア**で、**サポート終了（EoL）の 11.x 以前**に 6件の脆弱性があるとされた。最も重いのは **CVE-2026-8065（CVSS v3.1 9.1）**で、 **ファームウェア更新の端点に認証が無く、未認証の攻撃者が細工した POST 要求で 任意のファームウェアを投入できる**。残る5件には **2010年に公表された VxWorks の WDB デバッグサービスの欠陥（CVE-2010-2965・CVSS 9.8）**が含まれる。 発見は **Dragos** の報告で、**日立エナジーは「現行のサポート対象版は影響を受けない」** としつつ、**EoL 版については「これらの脆弱性の影響を受ける可能性が高い（likelihood）」**と 書いた。修正は提供されず、対処は **12.7.8 または 13.9.1 以降への移行**のみである

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表資料に攻撃の観測は含まれていない**（CISA の SSVC は **E:N**——悪用は観測されていない）。 以下は**勧告に記載された脆弱性の性質から組み立てた経路**であり、 **実際に行われた攻撃の記録ではない**（本記録の構成であることを各段階で明示する）。 **CVE-2026-8065 と CVE-2023-46143 が同じ勧告に並んでいる点が設計上の要点である**—— 「認証なしで投入できる」と「投入されたコードの完全性を検証しない」が揃うと、 **正規の更新経路がそのまま乗っ取りの経路になる。**

  1. 1. 偵察[1]
    **RTU500 の Web アプリケーションおよび管理用の端点が到達可能かを確かめる段階。** 勧告は本件の CVSS ベクタをいずれも **AV:N（ネットワーク越し）**としており、 **機器へネットワーク到達性があることが前提になる。** CVE-2010-2965 については入口が **UDP 17185 番**と具体に示されている。 **この段階の記述は勧告に無く、本記録が CVSS ベクタと CVE の記述から構成したものである。**
  2. 2. 初期侵入[1]
    **CVE-2026-8065 —— ファームウェア更新の端点に認証が無い。** 勧告の記述は「未認証の攻撃者が細工した POST 要求を通じて任意のファームウェアを アップロードすることを可能にする」（原文英語）。 **CVE-2026-8066（相対パストラバーサル・CVSS 9.1）はアップロード機能の側にあり、 「未認証の攻撃者が機器のファイルシステム上の任意のファイルを書き込み・上書きできる」** とされる（原文英語）。 **2件が同じ「ファイルを置ける」方向を向いている。**
  3. 3. 実行[1]
    **CVE-2023-46143 —— 完全性検証なしのコード取得（CWE-494・CVSS 7.5）。** 勧告の記述は「未認証の遠隔の攻撃者が、機器上で動作するアプリケーションの一部または 全部を改変することを可能にする」（原文英語）。 **CVE-2026-8065 で投入し、CVE-2023-46143 で検証されずに実行される**という 組み合わせになる（**本記録の読みであり、日立エナジーは2件を関連づけて説明していない**）。
  4. 4. 影響（暗号化・破壊・改ざん）[1]
    **CVE-2026-8067 —— reset 端点の認可不備（CWE-862・CVSS 6.5）。** 「認証された利用者が reset 端点を通じて RTU500 の再起動を引き起こすことができる。 悪用が成功すると一時的な機器の利用不能と、意図された動作の中断を引き起こす可能性がある」 （原文英語）。**CVE-2014-9195（認証の欠如・CVSS 8.1）は 「プロトコルに準拠した通信を用いて任意のコマンドを実行できる」**とされる。 **RTU の可用性と完全性の喪失は、変電所の遠隔監視・操作の喪失を意味する** （本記録の評価。**日立エナジーは系統への影響については述べていない**）。

修正版が出ない脆弱性なので、やることは「移行の計画」しかない概観

本件の性格は、通常の脆弱性対応と違う。

  • 対象は「サポート終了（EoL）版」である。 日立エナジーは「EoL 版はもはやセキュリティ更新で保守されていない」と書き、修正版を出さずに 12.7.8 または 13.9.1 以降への移行を求めた。
  • したがって「パッチを当てる」という選択肢が存在しない。勧告が示す対処は移行だけで、回避策は「多層防御と ICS のベストプラクティス」という一般的な記述にとどまる。
  • 対象が変電所の現場機器である。 RTU500 は遠隔端末装置で、停止調整・現地作業・上位系との互換性確認を伴う。ソフトウェアの更新と同じ速度では進まない（本記録の評価）。

ここから実務の順序が決まる（本記録の評価）。①RTU500 の機種と CMU ファームウェア版の棚卸し（11.x 以前が何台あるか）、②到達性の確認（どのネットワークから Web 面と UDP 17185 番に届くか）、③到達を絞る（修正が無いので、ここが実質的な対策になる）、④移行の計画に期限を付ける。②③を先に置くのは、④が年単位になりうるからである。

これが「EoL 版を使い続ける」ことの具体的な意味である（本記録の評価）。保守が止まった機器には、止まった時点より前の世代の欠陥がそのまま残り続ける。さらに、新しく見つかった欠陥も「現行版は影響を受けない」という形で確認されるため、EoL 版の側には確定的な判定さえ付かない（unknowns 参照）。

日立エナジー自身の説明も同じ方向を向いている—— EoL 版は「当時の要求水準・脅威環境・業界慣行に沿って開発された」もので、「現代の産業制御システムで標準となっている多くのセキュリティ制御と堅牢化を備えていない」（原文英語）。製品の欠陥ではなく世代差として位置づける書き方であり、利用側の読み方としては「個別の CVE を数えるのではなく、世代として扱う」のが対応する（本記録の評価）。

「認証なしで置ける」と「置かれたものを検証しない」が同じ機器に揃っている原因・手口

技術的な要点は、6件の組み合わせ方にある（本記録の読み。日立エナジーは CVE 相互の関係を説明していない）。

  • CVE-2026-8065 —— ファームウェア更新の端点に認証が無い。「未認証の攻撃者が細工した POST 要求を通じて任意のファームウェアをアップロードすることを可能にする」（原文英語）。
  • CVE-2026-8066 —— アップロード機能に相対パストラバーサルがある。「未認証の攻撃者が機器のファイルシステム上の任意のファイルを書き込み・上書きできる」（原文英語）。
  • CVE-2023-46143 —— 取得したコードの完全性を検証しない。「未認証の遠隔の攻撃者が、機器上で動作するアプリケーションの一部または全部を改変することを可能にする」（原文英語）。

「認証なしで置ける」「任意の場所に置ける」「置かれたものを検証しない」の3つが同じ機器に揃っている。 これは正規の更新経路がそのまま乗っ取りの経路になる形である（本記録の読み）。

検知の観点では、ここが最も厳しい（attack 参照）。完全性検証が無いということは、機器側に「自分が正しいかどうか」を判断する仕組みが無いということである。改変された機器は、改変されたことを報告しない。外部からの検証——上位系から稼働中の版を収集して台帳の正本と突き合わせる——を別に持たない限り、この段階の検知機会は現実的に無い。

同日の4件は1つの事案ではない。まとまって見えるのは再掲の都合である被害規模・影響範囲

2026年10月6日に CISA が再掲した4件は、原因も発見経路も別である（本記録の整理）。

読み分けるべき点が3つある（本記録の評価）。

  • -06 だけが「修正が出ない」勧告である。 他の3件には修正版がある（REB500 は 8.3.4.0、SOI は EP2 パッチ、Asset Suite は 9.9.1 が「提供されたら」）。-03 の Asset Suite は修正版が「when available（提供され次第）」と書かれており、当面は緩和策（テスト用サーブレットの無効化）が対処になる。
  • -05 と -04 は組み込んだ外部部品（libexpat・Apache ActiveMQ）が由来である。 製品そのものの実装ではなく、依存部品の更新の遅れとして現れる。 SBOM で追える種類の問題であり、-06 とは対応の仕組みが違う。
  • -03 の Asset Suite が示す形は「テスト用の機能が本番に残っている」である。勧告は HTTPPublishAdapterTestServlet が「非本番環境でのテスト目的に限って使われることを意図したもの」と明記し、PropertiesReloadServlet など4つのサーブレットについても「本番環境での有用性を評価すべき」としている（原文英語）。

つまり4件は、脆弱性対応の仕組みとして見れば4つの別の課題である—— EoL 機器の移行／依存部品の追跡／本番構成の点検。「日立エナジーの勧告が4件出た」とまとめると、この違いが消える。

EoL 版が6件すべての影響を受けるのかは、製造元も確定させていない未確定事項

本記録が一次資料を読んで最も気になった点である。

日立エナジーの記述はこうである（原文英語）——「Dragos が報告した所見は現在サポートされている RTU500 CMU ファームウェア版には影響しないが、EoL 版である 11.x 以前がこれらの脆弱性の影響を受ける可能性が高い（there is a likelihood）」。

「影響を受ける」ではなく「影響を受ける可能性が高い」である。

本記録はこれを、保守が終わった版は検証の対象でもなくなった結果と読む（推定である）。現行版については Dragos の所見を確かめた上で「影響しない」と書ける。EoL 版については、同じ検証が行われていないから確率的な表現になる。

利用側にとっての意味は小さくない（本記録の評価）。
- 「自機が対象かどうか」が確定しないまま、移行を判断することになる。脆弱性管理の手順が「該当の有無を確定させてから優先度を付ける」形になっている場合、本件はその手順に乗らない。
- 逆に「確定していないから保留」という処理になりやすい。 EoL という事実自体が判断材料であり、個別の CVE の該当性より優先すべきである（本記録の評価）。

あわせて、11.x 以前のどの版から脆弱だったのか、各版がいつ EoL になったのかも公表されていない。 機器ごとに優先順位を付ける材料が揃わない。

対処は到達性を絞ることと移行の期限を切ることに尽きる対策・注意喚起

勧告が示す対処（事実）。

  • 日立エナジー（RTU500）: 12.7.8 または 13.9.1 以降への更新。あわせて「適切な多層防御の措置と ICS のサイバーセキュリティのベストプラクティスを実施すること」（原文英語）。具体的な回避策は示されていない。
  • CISA の推奨実務: 制御系機器をインターネットから到達できないようにする／制御系ネットワークと遠隔機器をファイアウォールの内側に置き業務ネットワークから分離する／遠隔アクセスが必要な場合は VPN を使う（ただし VPN 自体も脆弱性を持ちうるし、接続する機器の安全性以上には安全にならない）。
  • 日立エナジーの一般的緩和要因: 制御系を物理的に保護する／インターネットへ直接接続しない／最小限のポートだけを開けたファイアウォールで他のネットワークと分離する／制御系を Web 閲覧・メッセージング・メール受信に使わない／可搬媒体を接続前に検査する／パスワード方針を守る。

ここから本記録が実務の優先順位として示すもの（本記録の評価）。

  1. 棚卸しが先である。 RTU500 の機種と CMU ファームウェア版の一覧（11.x 以前が何台・どこに）。これが無いと以降が全部できない。
  2. 到達性を測る。 Web 面と UDP 17185 番にどのネットワークから届くか。修正版が無いので、ここが実質的な対策になる。
  3. ファームウェア版を上位系から定期的に収集する仕組みを作る。機器が完全性を検証しないので、外から版を数えるしかない（attack 参照）。
  4. 移行の期限を機器ごとに切る。 停止調整を伴うため年単位になりうる。「予定が立っていない」状態を記録に残さないと、EoL は無期限に続く。
  5. 同日の他の3件は別の仕組みで扱う。 REB500・SOI は依存部品の追跡（SBOM）、Asset Suite は本番構成の点検（テスト用サーブレットの無効化）。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
RTU500（EoL 版）の脆弱性の組み合わせ——到達から任意ファームウェア投入、検証なしの実行、可用性の喪失まで
layer 0 は発見と公表の経路（Dragos → CISA／日立エナジー PSIRT）。 layer 1 は攻撃者の到達面——RTU500 の Web アプリケーション／ファームウェア更新端点／ UDP 17185 番（VxWorks WDB）。 layer 2 は機器上で成立する状態——任意のファームウェアの投入（CVE-2026-8065）、 任意のファイルの書き込み（CVE-2026-8066）、完全性検証なしの実行（CVE-2023-46143）。 layer 3 は影響——変電所の遠隔監視・操作の喪失と、再起動による一時的な利用不能（CVE-2026-8067）。 layer 4 は対処——サポート対象版（12.7.8 / 13.9.1 以降）への移行とネットワーク分離。 **点線は本記録が脆弱性の性質から構成した経路で、実際の攻撃の観測ではない （CISA の SSVC は E:N）。**

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察公表されていない
**勧告は検知について何も述べていない**（EoL 版が対象であり、 日立エナジーは移行以外の対処を示していない）。 **本記録の評価としては、ここは検知より「確認」の段階である**—— RTU500 の Web 面と UDP 17185 番が **どのネットワークから到達できるかは、利用側が自分で測れる。**
侵入を防げたRTU500 の管理面をインターネットおよび業務ネットワークから切り離し、 制御系ネットワークをファイアウォールの内側に置く　**CISA の推奨実務の第一項そのものである。** **本記録も、修正版が存在しない本件では最も効果が高いと評価する**—— **直せないものは到達させない以外に手が無い。** 遠隔保守が必要な場合は VPN 経由とするが、CISA 自身が 「VPN も脆弱性を持ちうるし、接続する機器の安全性以上には安全にならない」と 注記している（原文英語）。
影響を限定できたUDP 17185 番（VxWorks WDB）への到達を境界で遮断する　**本記録の評価による。** CVE-2010-2965 は入口が明示された唯一の CVE であり、 **ポート単位で絞れる。** ただし他の5件は Web アプリケーションと更新端点の側にあるため、 **これだけでは足りない。**
初期侵入公表されていない
**勧告は検知の機会に触れていない。** **本記録の評価** —— ファームウェアの投入は**機器側の記録にしか現れない**種類の操作である。 **EoL 機器に十分なログ出力と外部転送があるかは、利用側が確認すべき点になる。** **確認できない場合、「痕跡が無い」ことは「侵害が無い」ことの根拠にならない。**
検知できたファームウェア更新の操作を、作業計画と突き合わせられる記録として残す　**本記録の評価による。** 更新作業は**本来、計画されて行われる**。 **「いつ・誰が・どの機器へ更新を投入したか」の記録を持ち、 計画と突き合わせる**ことで、予定外の投入に気づける。 **IoC が公表されていない本件では、これが現実的な唯一の手がかりである。**
侵入を防げたサポート対象版（12.7.8 / 13.9.1 以降）へ移行する　**勧告が示す唯一の対処である。** **ただし RTU は変電所の現場機器であり、停止調整・現地作業・ 上位系との互換性確認を伴うため、ソフトウェアの更新と同じ速度では進まない** （本記録の評価）。**だからこそ「いつまでに何台」を期限つきで決める必要がある。**
実行現実的な検知機会なし
**本記録の評価である。** **ファームウェアが差し替わった機器は、自分が差し替わったことを報告しない。** 完全性検証が無いということは、**機器側に「正しいかどうか」を判断する仕組みが無い** ということである。 **外部からの検証（版の照合・ハッシュの比較）を別経路で持たない限り、 この段階の検知機会は現実的に無い。**
検知できた機器の稼働中のファームウェア版を上位系から定期的に収集し、 台帳の正本と突き合わせる　**本記録の評価による。** 機器自身が完全性を検証しないなら、**外から版を数える**しかない。 **EoL 機器の一覧（機種・版・設置場所）を持つこと自体が検知の前提になる。**
影響（暗号化・破壊・改ざん）機会はあったが検知できず
**本記録の評価である（勧告は検知について述べていない）。** **この段階は上位の監視制御系から見える** —— RTU の通信断・予期しない再起動・計測値の欠落は運用側が気づく事象である。 **ただし気づけるのは「起きた後」であり、原因が攻撃かどうかは 機器側のログが無ければ切り分けられない**（上の段階の制御が効いていない場合）。
影響を限定できたRTU の通信断・再起動を運用の監視対象として明示し、 「機器の不調」と「意図的な操作」を切り分ける手順を持つ　**本記録の評価による。** EoL 機器は経年による不調も起こすため、 **再起動が「よくあること」として扱われていると、攻撃による再起動が埋もれる。** **件数の推移を記録し、増加を異常として扱う**のが現実的な線である。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • EoL の OT 機器を「脆弱性の件数」ではなく「移行の予定の有無」で管理する
    **本件には修正版が存在しない。** 日立エナジーは EoL 版について**修正を出さず、12.7.8 / 13.9.1 以降への移行だけ**を示した。 さらに**該当性そのものが「可能性が高い」という確率的な表現**にとどまる。 **脆弱性ごとに該当を確定させて優先度を付ける手順では、本件は「保留」に落ちる** （本記録の評価）。 そして RTU は変電所の現場機器であり、**移行は年単位になりうる。**
    取るべき行動 OT 資産台帳に**「サポート状態（現行／EoL）」と「移行予定日」の2欄**を作り、 **EoL かつ移行予定日が空欄の機器を一覧として経営報告の対象にする。** **本件（RTU500 CMU 11.x 以前）を最初の1件として登録し、棚卸しの起点にする。** 脆弱性の件数ではなく**「予定が立っていない台数」**を指標にする。
  • 同じベンダーの勧告が同日に並んでも、1つの課題として扱わない
    **2026年10月6日の4件は原因も発見経路も別である**（本記録の整理）。 RTU500 は EoL 機器の移行、REB500 と SOI は**組み込んだ外部部品 （libexpat・Apache ActiveMQ）の更新**、 Asset Suite は**テスト用サーブレットが本番に残っている**という構成の問題である。 **「日立エナジーの勧告が4件」とまとめると、必要な仕組みが3つあることが見えなくなる。**
    取るべき行動 勧告を受け取る手順に**「この勧告はどの仕組みで解決するか」**という欄を作り、 **①EoL 機器の移行計画／②依存部品の追跡（SBOM）／③本番構成の点検**の いずれかに振り分ける。 **同一ベンダーの勧告を1件の課題として起票しない**と決めておく。
  • 製造元が「可能性が高い」と書いた事案を、確定情報を待たずに判断する
    **日立エナジーは EoL 版について「these vulnerabilities の影響を受ける 可能性が高い」とだけ書いた**（原文英語）。 **保守が終わった版は検証の対象でもなくなるため、確定判定は今後も出ないと見るのが 妥当である**（本記録の推定）。 **「ベンダーの確認待ち」を続けると、判断が止まったまま時間だけが経つ。**
    取るべき行動 脆弱性対応の判断様式に **「該当性が確定しているか／ベンダーの表現は確定的か」**の欄を作り、 **確率的な表現の事案は『EoL という事実』を根拠に優先度を決める**と規程に書く。 **確定を待たない判断経路を明示的に持つ。**
  • 修正版が示されない勧告を、ネットワーク設計の予算判断に直結させる
    **本件で CISA が示した推奨実務の第一項は「インターネットから到達できないようにする」 である。** 修正が無いのだから、**到達性を絞ることが実質的な唯一の対策になる。** **これはパッチ作業の予算ではなく、分離・帯域外管理・遠隔保守経路の設計の予算である** （本記録の評価）。
    取るべき行動 **EoL の OT 機器の一覧と、各機器への到達経路の一覧を並べた資料**を作り、 **移行予算（機器更新）と分離予算（ネットワーク）を別建てで示す。** **移行が年単位になる機器については、分離を先に実施する**と決める。
セキュリティ技術者への示唆
  • RTU500 の CMU ファームウェア版を機器単位で数え、11.x 以前を特定する
    **勧告の対象は「11.x and prior」だけである。** どの版から脆弱なのか、各版がいつ EoL になったのかは示されていない。 **つまり「11.x 以前かどうか」が唯一の判定基準になる**（本記録の整理）。 台数・組織数・国別の内訳は公表されていないため、 **自機の版を数える以外に該当を知る方法が無い。**
