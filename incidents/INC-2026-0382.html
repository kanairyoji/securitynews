INC-2026-0382Exchange に他者メール閲覧の脆弱性

Microsoft は2026年10月2日、Exchange Server 向けのセキュリティ更新を定例日より前に公開し、 **CVE-2026-96940（CVSS 8.8）**を修正した。**認可の不備（weak authorization）**により、 **認証された攻撃者が同一組織内の他の利用者のメールボックスに不正にアクセスし、 メール本文と添付ファイルを読める**。テナント境界を越えるアクセスは生じない。 Microsoft は悪用の確認は無いとしつつ、悪用可能性を **「Exploitation More Likely（悪用の可能性が高い）」**と評価した。 **Exchange Online 側はサービス側の修正が既に展開済みで利用者の作業は不要**であり、 **作業が要るのはオンプレミスの Exchange Server だけ**である。 対象は Subscription Edition RTM・2016 CU23・2019 CU15・2019 CU14。 なお**この更新は単独の修正ではなく9件の CVE をまとめた更新**で、 2026年8月11日版を置き換えるものである（本記録が KB を確認）

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月2日 最終更新: 2026年10月7日

Microsoft は2026年10月2日、Exchange Server 向けのセキュリティ更新を公開し、CVE-2026-96940（CVSS 8.8・重要度 High）を修正した。同月の定例更新日（第2火曜＝10月13日）より前のリリースであり、報道は帯域外（out-of-band）更新として扱った。

Microsoft の記述は次のとおり（原文英語）——「Microsoft Exchange Server における認可の不備は、認証された攻撃者がネットワーク越しに権限を昇格させることを可能にする」。さらに影響についてこう書いている——「悪用に成功した認証済みの攻撃者は、同一組織内の他の利用者のメールボックスへ不正にアクセスし、メールのメッセージと添付ファイルを読み取ることができる。 この脆弱性はテナント境界を越えるアクセスは許さない。」

要点は3つある。

  • 悪用には認証が必要だが、権限の水準は示されていない。成立すれば組織内のメールが横断的に読める。
  • Microsoft は悪用の確認は無いとしつつ、悪用可能性を「Exploitation More Likely（悪用の可能性が高い）」と評価した。
  • クラウドとオンプレミスで対応が分かれる。 Exchange Online には関連するサービス側の修正が既に展開済みで、利用者の作業は不要。 作業が要るのはオンプレミスの Exchange Server だけである。

対象は Subscription Edition RTM・2016 CU23・2019 CU15・2019 CU14。発見・報告は Microsoft の研究者 Jan Mitchell に帰され、外部の研究者ではなく社内の発見である。

本記録が一次資料（KB 文書）を確認して分かった点がひとつある—— 2026年10月2日の更新は CVE-2026-96940 単独の修正ではない。 9件の CVE（CVE-2026-96940 / 55007 / 69355 / 69356 / 69361 / 69375 / 69378 / 69382 / 69641）をまとめた更新であり、2026年8月11日版（Subscription Edition では KB5121573）を置き換えるものである。「1件の緊急修正」として扱うと、残る8件の存在が見えない（discrepancies 参照）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表資料に攻撃の観測は含まれていない**（Microsoft は悪用の確認は無いとしている）。 以下は**勧告の記述から組み立てた経路**であり、**実際に行われた攻撃の記録ではない** （本記録の構成であることを各段階で明示する）。 **本件の特徴は、段階が短いことである**—— 認証済みの足場が1つあれば、そこから直接**他者のメールボックスの読み取り**に届く。 **横展開も権限昇格のための別の脆弱性も要らない。**

  1. 1. 初期侵入[1] [3]
    **組織内の認証済みアカウントが1つ必要である。** Microsoft の記述は「認証された攻撃者（an authenticated attacker）」で、 **必要な権限の水準は示されていない。** 足場の入り方は本件の脆弱性とは別の問題であり、 **フィッシングによる資格情報の窃取・情報窃取マルウェアのログ・ 退職者アカウントの残存・委託先の作業用アカウントなどが考えられる** （**本記録の評価。Microsoft は入口について何も述べていない**）。
  2. 2. 権限昇格[1] [3] [4]
    **CVE-2026-96940 —— 認可の不備による権限昇格。** Microsoft の記述は「認可の不備が、認証された攻撃者がネットワーク越しに 権限を昇格させることを可能にする」（原文英語）。 **認証は正しく通ったうえで、本来の認可の範囲を越える**という形である。 **テナント境界は越えない**と明記されている。
  3. 3. 収集[1] [3]
    **他者のメールボックスの読み取り。** Microsoft の記述は「同一組織内の他の利用者のメールボックスへ不正にアクセスし、 メールのメッセージと添付ファイルを読み取ることができる」（原文英語）。 **対象が「同一組織内」である点が範囲を決める** —— 役員・人事・法務・経営企画のメールボックスも同じ組織内にある （**本記録の評価。Microsoft は読める範囲の上限を示していない**）。

認証を強めても防げない。これは認可の側の欠陥である原因・手口

Microsoft の記述は「weak authorization（認可の不備）」である（原文英語）。認証（authentication）ではなく認可（authorization）の側の欠陥であり、ここが本件の性格を決める（本記録の評価）。

  • 攻撃者は認証を正しく通っている。 多要素認証も条件付きアクセスも「正しい利用者である」ことを確かめる仕組みであり、正しい利用者が本来の範囲を越えることは止められない。
  • したがって対処は更新の適用に尽きる。 Microsoft は回避策・緩和策を示していない。
  • ただし成立には「認証済みの足場」が要る。足場の数を減らすこと（アカウントの棚卸し・多要素認証の強制）は影響の確率を下げるが、脆弱性そのものは消さない（本記録の評価。攻撃の解剖では、初期侵入の段階の対策を「防止」ではなく「影響範囲の限定」として扱った）。

読める範囲は「同一組織内」である。 Microsoft はテナント境界を越えないことは明記したが、組織内で読める範囲の上限は示していない。 役員・人事・法務・経営企画のメールボックスも同じ組織内にある（本記録の評価）。メールは意思決定の過程がそのまま残る場所であり、読まれても何も壊れないため気づく手がかりが無い。

クラウドは直っていてオンプレミスだけが作業を要する被害規模・影響範囲

対応が分かれている（事実）。

環境 状態 利用者の作業
Exchange Online 関連するサービス側の修正を既に展開済み 不要
Exchange Server SE RTM 更新を提供 要
Exchange Server 2019 CU15 / CU14 更新を提供 要
Exchange Server 2016 CU23 更新を提供 要

この非対称が実務上の意味を持つ（本記録の評価）。

  • クラウド側は利用者が気づかないうちに直っている。 直った時期も公表されていない（unknowns 参照）。「related（関連する）」という語が、同一の欠陥の修正なのか別の形の緩和なのかも判然としない。
  • オンプレミスだけが「作業窓を取って適用する」工程を踏む。メールは業務の基幹であり、更新の作業窓は取りにくい。 修正が出てから適用までの間隔が開きやすい。
  • ハイブリッド構成については個別の言及が無い。オンプレミスのサーバが残るので対象に含まれると読むのが自然だが、勧告はそれを明示していない（discrepancies 参照）。しかも本記録が確認した KB の既知の問題に「ハイブリッド構成で委任メールボックスの空き時間情報が取得できない」が挙がっている—— ハイブリッドの組織は、適用そのものに別の影響が出る可能性がある。

本記録が読者に渡したい論点はここである。 「クラウドなら勝手に直る」のは利点だが、同時に「自組織がいつ危険で、いつ安全になったのか」を自分で説明できないという状態にもなる（本記録の評価）。オンプレミスは逆で、危険な期間を自分で測れるが、縮めるのは自分の作業である。

「1件の緊急修正」ではない。同じ更新に9件が入っている再発防止

本記録が一次資料（KB 文書）を確認して分かった点である。

2026年10月2日の Exchange Server 更新は、CVE-2026-96940 単独の修正ではない。 9件の CVE をまとめている—— CVE-2026-96940 / 55007 / 69355 / 69356 / 69361 / 69375 / 69378 / 69382 / 69641。そして 2026年8月11日版（Subscription Edition では KB5121573）を置き換える。

報道からは読み取れない点が2つある（本記録の整理）。

  1. 残る8件が対応の記録に残らない。報道は CVE-2026-96940 に焦点を当てているため、「CVE-2026-96940 の対応済み」と起票すると、同じ更新で直る8件が台帳に現れない。 後から「あの CVE は対応したか」と問われたときに答えられない。
  2. 累積更新なので、8月版を飛ばしていた環境では差分が大きい。 置き換え対象が8月11日版であるということは、8月・9月の更新を当てていない環境では、一度に複数月ぶんが入ることになる（本記録の読み）。既知の問題が3件挙げられていることと合わせて、検証の必要性が上がる。

KB が挙げる既知の問題（事実）—— ①公開カレンダー（.ics）がカレンダーアプリケーションに対して HTTP 500 を返す、②Graph API のみを使う Exchange ハイブリッド構成で、委任メールボックスの空き時間情報（free/busy）が取得できない、③韓国語のワードブレーカーファイルの欠落による ContentEngine のデッドロック。

判断の形はこうなる（本記録の評価）—— 「Exploitation More Likely と評価された認可の欠陥を放置する risk」と「既知の問題3件を抱えた累積更新を検証せずに入れる risk」を並べて比較する。 どちらを選ぶにしても、比較した記録を残すことが要る。

2016 と 2019 が対象に入っていることが、別の判断を同時に呼ぶ評価・解釈

対象に Exchange Server 2016 CU23 と 2019 CU15 / CU14 が含まれている。

これらは延長サポート（Extended Security Update・ESU）の枠にある版である。 本記録が確認した範囲では、Microsoft は「ESU プログラムの Period 2 に登録している組織は2026年10月末までリリースされたセキュリティ更新を受け取る資格がある」とし、「ESU に登録していない組織は、最新のセキュリティ更新を継続して受け取るためにExchange Server Subscription Edition（SE）へ移行すべき」としている（検索結果に現れた Microsoft のサポート文書の記述による。本記録は ESU の条件そのものを一次資料で確認していない—— KB5129955 の本文に ESU の記載は無かった）。

これが意味するのは、本件の対応が2つの判断を同時に呼ぶということである（本記録の評価）。

  • 短期: 2026年10月2日の更新を当てる。 認可の欠陥を閉じる作業である。
  • 中期: 2016 / 2019 を使っている組織は、更新を受け取れる期間そのものが終わりに近づいている。 次に同じ重さの脆弱性が出たとき、更新が提供されない側に回る可能性がある。

本記録の評価として、CISO に渡すべき論点はこちらである。 「今回の脆弱性に対応したか」ではなく、「次に同じものが出たとき、自組織は更新を受け取れる状態にあるか」。 INC-2026-0381（日立エナジー RTU500 の EoL 版）と同じ構図が、OT 機器ではなくメール基盤で起きている—— 保守が終わった版には、終わった時点より後の欠陥に対する修正が来ない。

悪用されたかどうかは、メールボックス監査ログが無ければ確認できない未確定事項

Microsoft は悪用の確認は無いとしつつ、悪用可能性を「Exploitation More Likely（悪用の可能性が高い）」と評価した。

この2つは矛盾しない（本記録の整理）—— 前者は Microsoft の観測範囲の話で、後者は技術的な評価である。 どちらも個々の組織について「悪用されていない」ことを保証しない。

そして確かめる手段が示されていない。

  • IoC もログの確認方法も勧告に無い。
  • 読み取りの脆弱性は何も壊さない。 メールが読まれても業務は動き続ける。添付ファイルが外部へ持ち出されれば DLP やプロキシに現れる可能性はあるが、Exchange の内部で読まれるだけなら外部通信も発生しない。
  • 残るのは「どのアカウントがどのメールボックスにアクセスしたか」の記録—— Exchange のメールボックス監査ログである。ただし Microsoft は本件についてその確認を推奨していない。

本記録の評価として、実務の線はこうなる。 更新を当てる前に、監査ログが取れているかを確認する。取れていれば、公表日より前の期間について、機密性の高いメールボックスへの他者アカウントからのアクセスを見る。 取れていなければ、「悪用されていない」とは書けない——その場合は「確認できなかった」と記録に残すのが正しい扱いである。「痕跡が無い」と「調べる手段が無い」を同じ言葉で書かない。

初期侵入公表されていない

対応の評価

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「認証の強化で足りるか」を脆弱性の種別で切り分ける
    **本件は認可（authorization）の欠陥である。** 多要素認証も条件付きアクセスも**「正しい利用者である」ことを確かめる仕組み**であり、 **正しい利用者が本来の範囲を越えることは止められない**（本記録の評価）。 **Microsoft は回避策・緩和策を示していない。** **「多要素認証を入れてあるから大丈夫」という判断が、この種の脆弱性では成り立たない。**
    取るべき行動 脆弱性対応の判断様式に **「認証の欠陥か／認可の欠陥か」**を区別する欄を作り、 **認可の欠陥には『既存の認証系の対策は効かない』と明記する。** **本件を最初の事例として記録し、同じ判断の再発を防ぐ。**
  • クラウドとオンプレミスで「危険だった期間」の説明可能性が逆になることを理解する
    **Exchange Online は「関連するサービス側の修正を既に展開済み」とされ、 利用者の作業は不要である。** **しかしいつ直ったのかは公表されていない** （本記録が確認。unknowns 参照）。 **オンプレミスは逆で、修正の提供日（2026年10月2日）と自組織の適用日が分かるため、 危険だった期間を自分で説明できる。** **監督官庁や取引先に「いつから安全か」を説明する場面では、この差が出る** （本記録の評価）。
    取るべき行動 **クラウドサービスについては「修正の適用時期を自組織が説明できるか」を 委託先管理の確認項目に入れる。** **オンプレミスについては、修正の提供日と自組織の適用日を台帳に記録する** （後から期間を示せる形にする）。
  • 延長サポートの残り期間を、脆弱性対応とは別の議題として経営に上げる
    **対象に Exchange Server 2016 CU23 と 2019 CU15 / CU14 が入っている。** **これらは延長サポート（ESU）の枠にある版であり、 更新を受け取れる期間そのものに期限がある** （本記録は ESU の条件を一次資料で確認していない—— 検索結果に現れた Microsoft のサポート文書の記述による）。 **「今回の脆弱性に対応したか」と「次に同じものが出たとき更新が来るか」は別の問いである** （本記録の評価）。
    取るべき行動 **メール基盤の版とサポート期限を台帳に記録し、 「サポート期限までの残り月数」を経営報告の定期項目にする。** **本件の対応報告に、Subscription Edition への移行判断の現況を併記する** （2つを同じ資料で扱う）。
  • 報道が焦点を当てた1件ではなく、更新そのものを対応の単位にする
    **2026年10月2日の更新は9件の CVE をまとめたものである**（本記録が KB で確認）。 **報道は CVE-2026-96940 の1件に焦点を当てている。** **「CVE-2026-96940 の対応済み」と起票すると、同じ更新で直る8件が台帳に現れず、 後から問われたときに答えられない**（本記録の評価）。 さらに**この更新は2026年8月11日版を置き換える累積更新**であり、 **既知の問題が3件挙げられている。**
    取るべき行動 **脆弱性対応の起票の単位を「CVE 番号」ではなく「適用する更新（KB 番号）」にし、 その更新が含む CVE を一覧として記録する。** **報道で知った事案については、必ずベンダーの KB を開いて CVE の一覧を転記する**と 手順に書く。
セキュリティ技術者への示唆
  • 更新を当てる前に、メールボックス監査ログが取れているかを確認する
    **本件は読み取りの脆弱性であり、悪用されても何も壊れない。** **IoC もログの確認方法も勧告に無い**（本記録が確認）。 **痕跡が残りうるのは「どのアカウントがどのメールボックスにアクセスしたか」の記録だけ** である（本記録の評価）。 **更新を当ててしまうと、それ以降は塞がるが、 公表日より前の期間を調べる材料は過去のログしか無い。**
    取るべき行動 **Exchange のメールボックス監査ログの有効化状態と保持期間を確認する。** 取れていれば**2026年10月2日より前の期間について、 役員・人事・法務のメールボックスへの他者アカウントからのアクセスを抽出する。** **取れていなければ、報告書に「悪用の有無は確認できなかった」と明記する** （「痕跡なし」と書かない）。
  • 累積更新であることを前提に、検証の範囲を8月版からの差分で決める
    **この更新は2026年8月11日版（Subscription Edition では KB5121573）を置き換える** （本記録が KB で確認）。 **8月・9月の更新を当てていない環境では、一度に複数月ぶんが入る。** **KB は既知の問題を3件挙げている**—— **公開カレンダー（.ics）が HTTP 500 を返す／ Graph API のみを使うハイブリッド構成で委任メールボックスの空き時間情報が取得できない／ 韓国語のワードブレーカーファイルの欠落による ContentEngine のデッドロック。**
    取るべき行動 **現在当たっている更新の版を確認し、8月版からの差分かどうかを把握する。** **既知の問題3件のうち自組織に当てはまるものを先に洗い出す**—— **公開カレンダーを外部に出しているか／Graph API のみのハイブリッド構成か／ 韓国語の環境があるか。** 当てはまるものがあれば**検証環境で先に確認する。**
  • メールボックスへアクセスできるアカウントを棚卸しし、足場の数を減らす
    **本件の成立には「組織内の認証済みアカウント1つ」が要る。** **必要な権限の水準は公表されていない**ため、 **一般の従業員アカウントで成立する可能性を排除できない**（unknowns 参照）。 **認可の欠陥なので認証の強化では防げないが、 足場の数を減らすことは影響の確率を下げる**（本記録の評価。「防止」ではなく「限定」）。
    取るべき行動 **メールボックスへアクセスできる全アカウントを一覧化する**—— 従業員・退職手続き中・委託先の作業用・サービスアカウント・ アプリケーション登録の権限。 **使われていないものを無効化し、残るものに多要素認証を強制する。** **委任（代理アクセス）の設定も同時に棚卸しする。**
  • MSRC の脆弱性ページを直接読んで CVSS ベクタと必要権限を確認する
    **本記録は MSRC の脆弱性ページの本文を取得できなかった** （クライアント側描画のため。discrepancies 参照）。 **したがって CVSS ベクタと「認証された攻撃者」に必要な権限の水準を確認していない。** **PR:L（低権限）か PR:H（高権限）かで、想定すべき足場が変わる**—— **一般利用者アカウントで成立するなら、侵害された1アカウントが 組織全体のメールを読む足場になる**（本記録の評価）。
    取るべき行動 **MSRC の脆弱性ページをブラウザで開き、CVSS ベクタの `PR` と `AC` を転記する。** **FAQ 欄に追加の成立条件や緩和策が書かれていないかも確認する。** **脆弱性管理の記録に CVSS のスコアだけでなくベクタを残す欄を作る。**
