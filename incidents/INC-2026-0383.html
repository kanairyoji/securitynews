INC-2026-0383新ICSマルウェアS7FlipがPLC値を改変

Positive Technologies の産業専門センターは2026年10月6日、マルウェア共有サイト **MalwareBazaar** に投稿された Windows の実行形式を解析し、 **新しい ICS 向けマルウェア「S7Flip」**として公表した。 検体は2026年9月13日に「jeans」というアカウントから `Edge.exe` の名で投稿され、 **投稿者は「Siemens 製機器のある産業環境の Windows 機で見つけた」と説明していた。** S7Flip は**私設ネットワークを走査して 102番（Siemens S7Comm）・502番（Modbus TCP）・ 44818番（Allen-Bradley）を探し**、見つけた機器のレジスタ値に **−10〜+10 の乱数を加える**か、**対象メモリ領域の最下位ビットを反転させる**。 **破壊ではなく「少しずつ狂わせる」**形であり、改変の記録は `logs.csv` に残す。 Windows 側では `aphp.exe` として自動起動に登録する。 **Allen-Bradley への操作は実装の誤りで成立していない。** **実環境での感染は投稿者の説明のみで、被害組織・国・時期はいずれも裏付けが無い**

Positive Technologies の産業専門センター（Центр промышленной экспертизы） は2026年10月6日、同社の技術ブログ（Habr）で、新しい ICS 向けマルウェア「S7Flip」の解析結果を公表した。

発見の経路が通常と異なる。検体はマルウェア共有サイト MalwareBazaar に、2026年9月13日に「jeans」というアカウントから Edge.exe の名で投稿されたもので（SHA-256: e014dadf6d93b312b93e2fc857791c241692da4015da7a24a4d42a946551add2）、投稿時のコメントに「Siemens 製機器のある企業の産業環境の Windows 機で見つけた、おそらく ICS を狙う新しいマルウェアだ」という説明が付いていた。 この説明が解析の端緒になった。

S7Flip の動作（Positive Technologies の分析による）。

  • 私設ネットワークを走査し、3つのポートを探す—— 102番（Siemens S7Comm）・502番（Modbus TCP）・44818番（Allen-Bradley）。
  • 見つけた機器のデータを2通りに改変する。 ①レジスタ値に −10 から +10 の範囲の乱数を加える（ランダム化）、②対象メモリ領域の最下位ビットを反対に書き換える（ビット反転）。
  • 改変の記録を logs.csv に残す（時刻・タグ・ベンダー・変更前の値・変更後の値の5列）。
  • Windows 側では aphp.exe として自動起動に登録する。
  • Allen-Bradley への操作は実装の誤りにより成立していない。

本記録が本件の核心と見るのは、改変の「程度」である（本記録の評価）。−10〜+10 の乱数加算と最下位ビットの反転は、いずれも機器を止めない。 プロセス値が少しずつ狂うだけである。 設備は動き続け、警報も鳴らず、監視画面の数値も「ありえない値」にはならない。 だが制御の判断はその値に基づいて行われる。

一方で、裏付けの範囲は限られている。 実環境での感染は投稿者「jeans」の説明のみであり、被害組織・国・業種・時期はいずれも公表されていない。 帰属についても、Positive Technologies は「4つの検体がいずれも GCC 16.2.0 でコンパイルされ、タイムスタンプが揃い、同じアカウントから投稿されている」ことから共通の作者の可能性を示唆するにとどめ、特定の攻撃者には結びつけていない。

**以下は Positive Technologies の解析で明らかになった検体の動作である**（事実）。 **ただし初期侵入の経路は公表されていない**ため、その段階は推定として扱う。 **検知の機会については、解析が被害組織側の検知について述べていない**ため、 **各段階で本記録の評価であることを明示する。** **本件の設計上の要点は、影響の段階が「破壊」ではなく「改変」である**こと—— **止めずに狂わせるため、通常の可用性の監視には現れない。**

止めるのではなく狂わせる。だから可用性の監視には映らない原因・手口

本記録が本件の核心と見るのは、改変の「程度」である（本記録の評価）。

Positive Technologies が明らかにした改変は2通りである（事実）。

  • レジスタ値に −10 から +10 の範囲の乱数の整数を加える（ランダム化）
  • 対象メモリ領域の最下位ビットを反対に書き換える（ビット反転）

どちらも機器を止めない。

この設計が意味すること（本記録の評価）。

  • 可用性の監視には現れない。 機器は応答し続け、設備も動き続ける。「PLC が落ちた」「通信が切れた」という形の警報は出ない。
  • 警報の閾値に届かない可能性が高い。 ±10 の揺れは、温度・圧力・流量のようなプロセス値の正常範囲の内側に収まることが多い。
  • 「ありえない値」にならない。 監視画面を見ている運転員にも異常として映らない。
  • それでも制御の判断はその値に基づいて行われる。 最下位ビットの反転は、特に「設定値」や「状態フラグ」に乗ると意味が変わる（本記録の読み。ただしどのメモリ領域が対象かは公表されていない）。

従来の ICS マルウェアとの違いはここである（本記録の評価）。停止や破壊を狙うものは、結果が目に見える。 S7Flip の形は、結果が「品質の揺れ」「わずかな効率の低下」「説明のつかない不具合」として分散して現れる。 攻撃として認識されるまでに時間がかかる。

なお「±10 だから軽微」とは言えない。 レジスタの生値に対する加算であり、工学単位に換算した影響の大きさは機器の設定（スケーリング）ごとに異なる（unknowns 参照）。自組織の機器について、どのレジスタがどのプロセス値に対応し、±10 がどれだけの揺れになるかは、各組織が自分で計算するしかない。

成立の前提は PLC の側にある。認証を要求しないのは設計そのものである評価・解釈

S7Flip が成立するために必要なのは3つである（本記録の整理）。

  1. 産業制御ネットワークに到達できる Windows 機があること（エンジニアリング端末・HMI・運用管理用の PC）。
  2. その Windows 機から PLC の 102 / 502 番へ通信できること。
  3. PLC 側が認証を要求せずに読み書きを受け付けること。

3つめはマルウェアの工夫ではない。 S7Comm と Modbus TCP の設計そのものである（本記録の評価）。これらのプロトコルは、閉じたネットワークで使われることを前提に、認証を持たない形で設計されている。

したがって本件への対策は、PLC 側の修正では得られない（本記録の評価）。「脆弱性を直す」という形の対応が存在しない。 残るのは①到達範囲を絞る、②走査を検知する、③値の整合性を見る、の3つである。

ここで INC-2026-0381（日立エナジー RTU500 の EoL 版）との違いが出る。 あちらは「修正版があるが移行していない」状態だった。 本件は「修正という概念が無い」—— プロトコルの世代差であり、個々の機器の更新では解消しない。 両者は同じ「OT の到達性を絞る」対策に収束するが、経営に説明する言葉は違う（本記録の評価）——前者は「移行の予算」、後者は「ネットワーク設計の恒久的な前提」である。

走査の段階がいちばん見つけやすい。OT の通信は定常だから対策・注意喚起

S7Flip の動作のうち、最も検知しやすいのは走査の段階である（本記録の評価）。

理由は OT ネットワークの性質にある。 産業制御ネットワークの通信は、どの端末がどの機器のどのポートへ話すかが設計で決まっている。 「ある Windows 機が多数の機器の 102 / 502 / 44818 番へ順に接続を試みる」のは、平常時には起きない通信である。

さらに 44818 番（Allen-Bradley）への試行が手がかりになる（本記録の読み）。現在の検体では Allen-Bradley への操作は実装の誤りで成立していないが、走査自体は行われる。 つまり Allen-Bradley 機器を持たない組織でも 44818 番への試行が観測される—— これは「自組織に存在しない機器のポートへの接続試行」として、とりわけ目立つ。

対策の順序（本記録の評価）。

  1. 産業制御ネットワークに到達できる Windows 機の一覧を作る。用途・利用者・外部媒体や外部ネットワークへの接続可否。これが本件の攻撃面そのものである。
  2. 許可すべき通信の一覧（どの端末がどの機器のどのポートへ）を作り、それ以外を異常として扱う。
  3. エンジニアリング端末から PLC への通信を、必要な機器・必要なポートに限定する。 S7Flip は走査で到達できた機器しか改変できない。
  4. 自動起動の項目の正本を持ち、増減を比較する。 aphp.exe という具体的なファイル名での照合も併用する（ただし次の版で名前が変われば効かない）。
  5. 重要なプロセス値について、値そのものの整合性を検証する手段を持つ。 これが最後の砦になるが、最も作るのが難しい（下記）。

5 について補足する（本記録の評価）。「値が狂う」攻撃に対しては、値を1系統で見ている限り気づけない。 冗長な計測（別センサ・別経路）や、物理法則上ありえない組み合わせの検出が要る。 これは安全計装（SIS）の考え方と重なるが、同じ仕組みでは捉えられない—— 安全計装は「危険側への逸脱」を見るもので、±10 の乱数は安全側にも危険側にも動く。

マルウェアが自分の改変を記録している。これは調査する側に有利である発覚の端緒

S7Flip は改変の記録を logs.csv に残す（事実）。列は5つ——時刻・タグ・ベンダー・変更前の値・変更後の値。

この動作は3つのことを意味する（本記録の評価）。

  • 作者が「どの値をどう変えたか」を把握したいと考えている。 自律的にばらまくだけのものではなく、結果を見る前提の作りである。
  • 「ベンダー」の列があることから、複数ベンダーへの対応が設計の前提である。 走査する3つのポートが Siemens・Modbus・Allen-Bradley に対応していることと整合する。
  • 調査する側から見れば、これは例外的に恵まれた条件である。 感染機から logs.csv を回収できれば、「どの値がいつどう変えられたか」の一覧がそのまま得られる。

プロセス値の改変は、通常なら事後に特定するのが極めて難しい（本記録の評価）。過去の計測値が「本来いくらだったか」を知る手段が無いためである。 S7Flip の場合はマルウェア自身が変更前の値を記録しているので、復元の材料がある。

ただし前提がある。 感染機から回収できることが必要であり、マルウェアが消去する動作を持つかは公表されていない（unknowns 参照）。実務上は「感染が疑われる端末を初期化する前に、logs.csv を探して保全する」という手順になる（本記録の評価）—— 初期化してしまうと、改変された値の一覧が失われる。

  • 産業制御ネットワークに到達できる Windows 機の一覧を作る

    **S7Flip は改変の記録を `logs.csv` に残す**—— **時刻・タグ・ベンダー・変更前の値・変更後の値の5列** （Positive Technologies の分析による）。 **プロセス値の改変は通常なら事後に特定するのが極めて難しい** （過去の計測値が本来いくらだったかを知る手段が無い）。 **本件はマルウェア自身が変更前の値を記録しているため、復元の材料がある** （本記録の評価）。 **初期化してしまうと、その一覧が失われる。**

  • 重要なプロセス値について、値そのものを検証する手段を1つ作る
    **±10 の乱数加算は値を正常範囲の内側で揺らすため、 閾値による警報では捉えられない**（本記録の評価）。 **気づける可能性があるのは「値そのものの整合性」を見ている場合だけである**—— 冗長な計測との突き合わせ、物理的に整合しない組み合わせの検出。 **安全計装（SIS）とは別物である**—— **安全計装は危険側への逸脱を見るもので、±10 の乱数は安全側にも危険側にも動く。**
    取るべき行動 **重要なプロセス値を3〜5個に絞り、それぞれについて 「別系統の計測があるか」「物理法則上ありえない組み合わせを検出できるか」を確認する。** **1つも無い場合は、まず1つだけ相互検証を入れる** （全系統に広げる前に、仕組みが成立するかを確かめる）。 **あわせて、どのレジスタがどのプロセス値に対応し、 ±10 の加算が工学単位でどれだけの揺れになるかを計算する。**
