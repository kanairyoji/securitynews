Checkmarx（Checkmarx Zero） は2026年10月5日、npm レジストリで3年以上続く供給網キャンペーン MALFEX の分析を公表した。単一の作者に紐づく12個のパッケージ——8個が悪性で、4個は無害な覆い——が2023年8月から公開され、合計40,767回ダウンロードされていた。

本記録が本件の核心と見るのは、ダウンロード数の偏りである（本記録の評価）。

  • 40,767回のうち 37,419回（約92%）が function-flag 1個によるもの。
  • function-flag は2025年7月18日から悪性である。
  • それでも 2026年9月29日時点でアドバイザリが1件も付いていなかった。 Checkmarx の記述は「function-flag と function-color にはアドバイザリがまったく無く、cdn-img-fetch のアドバイザリは 1.0.0 と 1.0.1 の2版しか挙げておらず、悪性の 1.0.2 と 1.0.3 を含まない」（原文英語）。

つまり「14か月間、無印のまま配られ続けた」。

配信経路は3つあり、基盤を共有していない（Checkmarx の分析による）。

14か月間アドバイザリが付かず、その間に37,419回ダウンロードされた概観

本記録が本件の核心と見るのは、ダウンロード数の偏りとアドバイザリの欠落が同じことを指している点である（本記録の評価）。

  • キャンペーン全体のダウンロードは40,767回。
  • そのうち 37,419回（約92%）が function-flag 1個によるもの（本記録が算出）。
  • function-flag は2025年7月18日から悪性である。
  • それでも 2026年9月29日時点でアドバイザリが1件も無かった。

Checkmarx の記述はこうである（原文英語）——「function-flag と function-color にはアドバイザリがまったく無く、cdn-img-fetch について公開されたアドバイザリは 1.0.0 と 1.0.1 の2版しか挙げておらず、悪性の 1.0.2 と 1.0.3 を含まない。」

CloudSEK は同じ状態を「14か月間アドバイザリに捕まらなかった悪性の postinstall」と表現している。

ここから出てくる実務上の結論は1つである（本記録の評価）。

「アドバイザリが無い」ことは「悪性でない」ことを意味しない。

SCA（ソフトウェア構成分析）やレジストリの警告は、アドバイザリのデータベースに依存する。 データベースに載っていないものは、どれだけ丁寧に検査しても「問題なし」と出る。 本件は、その状態が14か月続いた場合に何回ダウンロードされるかを実測で示した事例である。

露出は「名前を自分で指定した環境」に限られる。だから探し方が決まる被害規模・影響範囲

影響範囲を決める事実が公表されている（Checkmarx の記述・原文英語）。

「正規の、あるいは広く使われているパッケージはこの作者のパッケージに一切依存していないため、露出はこれらのパッケージ名を直接インストールしたシステムに限られる。地理的・組織的な標的設定は見つからなかった。この窃取ツールを入れた者は誰でも標的になる。」

この2文が、本件の調査の方法を決める（本記録の評価）。

  • 依存の連鎖をたどる必要が無い。 推移的依存（依存の依存）で巻き込まれる形ではないため、lockfile の中の名前を直接照合すればよい。
  • 「狙われた組織」は存在しない。 業種・地域での絞り込みが無いので、「自社は対象業種か」という問いは意味を持たない。 入れたかどうかだけが問題である。
  • ペイロードが動くのは Windows のみ。 macOS と Linux ではインストール時の処理が静かに失敗する。 したがって「取り込んだ記録はあるが Linux の CI だった」場合、感染は成立していない可能性が高い（本記録の読み。ただし経路2 は読み込み時に動くため、同じ判断が全経路に当てはまるとは限らない）。

探し方の順序（本記録の評価）。

  1. lockfile（package-lock.json・yarn.lock・pnpm-lock.yaml）をリポジトリ全体で検索し、公表されたパッケージ名を照合する。 履歴も見る——過去のコミットに入っていて後に外された場合、その時点で感染が成立している可能性がある。
  2. レジストリのプロキシ・ミラーの取得ログを照合する。 lockfile に残らない取得（開発者が手元で試した場合など）はここにしか残らない。
  3. 該当した環境の OS を確認する。 Windows であれば感染の可能性を前提に扱う。
  4. 該当した環境の資格情報を失効させる（下記の節）。

3つの経路が基盤を共有していない。だから1つ塞いでも残る原因・手口

Checkmarx は配信経路を3つに整理し、「3つの経路は基盤を共有しないが、同じ作者に結びつく」としている（事実）。

経路 起動の契機 取得元 落ちるもの
1 npm install のたび（preinstall.js / postinstall.js） api.imghippo.com gldriver_pre_core.exe / gldriver_pre_asset.exe → Overlord RAT
2 パッケージの読み込み時 （cdn-img-fetch → img-to-native → native-runner の連鎖） movinlike（Node.js 製の情報窃取）
3 npm install のたび（悪性版ごとに別のダウンローダ） 版ごとに別の場所 未回収の実行形式

CloudSEK は同じものを2つの経路（Delivery Arm A / B）に整理しており、数え方が一致しない（discrepancies 参照）。

実務上の意味は3つある（本記録の評価）。

  • --ignore-scripts では経路2 が止まらない。 経路1 と経路3 はインストール時スクリプトを基盤にしているので止まるが、経路2 はパッケージの読み込み時に動く。 「インストール時スクリプトを無効にしたから安全」とは言えない。
  • ネットワーク側の遮断のほうが広く効く。 3つの経路はいずれも外部からペイロードを取得する—— api.imghippo.com・raw.githubusercontent.com/cavecrew/proj・104.234.65.75:700。取得できなければペイロードは動かない。
  • 1つが摘発されても他が残る形になっている。 これが3年続いた理由の一部である（本記録の読み）。5個のパッケージが削除されたあとも、function-flag が残り続けた。

C2 をブロックチェーンから解決するので、宛先の遮断では止まらない帰属

Overlord RAT の C2 の持ち方が特異である。

Checkmarx の記述（原文英語）——「Overlord はハードコードされたコマンド＆コントロールのアドレスを持たない」。代わりに Solana ブロックチェーン上の暗号化されたメモを読んで宛先を解決する。

これが対策に与える影響（本記録の評価）。

  • 「C2 の IP / ドメインを遮断する」という対策が効かない。 攻撃者はブロックチェーン上のメモを書き換えるだけで宛先を変えられる。
  • ブロックチェーンへの参照自体は遮断しにくい。公開の RPC 端点は多数あり、正規の用途と区別しにくい。
  • したがって効くのは「ペイロードを取得させない」「常駐させない」側である。 宛先の遮断に依存しない前提で対策を組む必要がある。

一方 movinlike の送出先は実用的な手がかりになる（本記録の評価）。窃取したデータは Discord の webhook へ送られる。 ビルド環境・開発環境が Discord へ話す理由は通常無い。 遮断すると同時に検知の信号にもなる。

なお Overlord RAT が備える機能（Checkmarx・SecurityWeek の記述）—— 画面取得・キーロガー・ウィンドウ監視・遠隔シェル・ファイル検索、そして「検知されずに悪性の活動を行うための隠しデスクトップ」。 遠隔シェルとファイル検索があるということは、窃取の対象が Discord・ブラウザ・暗号資産ウォレットに限られないということである（本記録の読み。ただし本分析はそこまでの被害を確認していない）。

失敗が可視化されない作りになっている発覚の端緒

本記録が設計上の要点と見る2つめである（本記録の評価）。

Checkmarx の記述（原文英語の要旨）—— 「感染の処理は、ペイロードのダウンロードが失敗してもパッケージのインストールが完了するように実装されている。処理は macOS と Linux では静かに失敗する（fails silently）ため、影響を受けるのは Windows のシステムだけである。」

ここに3つの「見えなさ」が重なっている。

  • macOS / Linux の開発者には何も起きない。エラーも警告も出ない。悪性パッケージを入れたという事実すら残らない。
  • Windows の開発者にも何も見えない。 インストール時スクリプトは実行後に自身を削除する。
  • どちらの場合も「インストールが成功した」という結果だけが残る。

これが「14か月間アドバイザリが付かなかった」ことと噛み合っている（本記録の読み）。誰も異常を報告しないので、報告を起点とする仕組みは動かない。 検出は、ファイルやネットワークの観測から始めるしかなかった。

なお、唯一の例外的な手がかりが CloudSEK の分析にある（本記録の読み）—— movinlike は 64MB の Node.js バンドルとして配られる。 ビルド中に 64MB の実行可能なバンドルが落ちるのは、通常の依存取得とは明らかに異なる挙動である。 大きさそのものが検知の手がかりになりうる。

最もダウンロードされたものが、何を配っていたのか分かっていない未確定事項

本記録が実務上もっとも困ると判断した欠落である。

Checkmarx は3つめのペイロードを「未回収の node.exe 実行形式」としている。 経路3 は function-flag の悪性版ごとに別のダウンローダを仕込み、それぞれ別の場所からペイロードを取得する作りだった。

つまり——37,419回ダウンロードされた最大のパッケージが配っていたものが、何だったのか分かっていない。

取得元が既に失われていると考えられるが、裏付けは無い（本記録の推測）。

この欠落が意味すること（本記録の評価）。

  • function-flag を取り込んだ環境について、「何を実行されたか」が特定できない。
  • したがって影響の範囲を限定する根拠が無い。 「ブラウザの保存資格情報だけ」とも「SSH 鍵も」とも言えない。
  • さらに悪性だった期間が14か月あるため、「いつから感染していたか」も絞りにくい。

本記録の評価として、該当環境の扱いはこうなる。 資格情報の失効は、期間と範囲を絞らずに行うのが安全側である。 具体的には——ブラウザに保存された資格情報、npm / コンテナレジストリのトークン、クラウドの資格情報、SSH 鍵、そして端末に置かれていた長期有効なすべてのトークン。 「取り込んだ記録はあるが被害の証拠は無い」という状態では、証拠が無いことを根拠に範囲を狭めない。

あわせて記録すべきこと——npm が function-flag と function-color を削除せずアドバイザリも付けなかった理由は公表されていない（unknowns 参照）。他の6個にはアドバイザリが出ている。 最大のものがなぜ残ったのかは、エコシステムの側の論点として重要である。

**本記録の評価である。** **②が最も効いている**——**失敗が可視化されない。** **macOS / Linux の開発者は何も起きていないように見え、 Windows の開発者だけが感染するが、やはり何も見えない。** **「インストールが成功した」という結果だけが残る。** **③④は「正規の基盤・正規の署名・正規の画像形式」を使うことで、 種別による検査をすり抜ける形である。** **⑤の 64MB という大きさは、むしろ検知の手がかりになりうる** （本記録の読み——ビルド中に 64MB の実行可能なバンドルが落ちるのは 通常の依存取得とは異なる）。
検知できたビルド環境で生成・取得されたファイルのうち、 実行形式と大きなバイナリを記録する　**本記録の評価による。** **`gldriver_pre_core.exe` / `gldriver_pre_asset.exe` という 具体的なファイル名が公表されている**ため、 **今回に限ってはこれで探せる。** **恒久の手段としては「ビルド中に実行形式が落ちたか」を見る**ほうが効く （名前は変種で変わる）。
影響を限定できた使い捨てのビルド環境を使い、ビルドごとに破棄する　**本記録の評価による。** **本件のペイロードは常駐して資格情報を窃取する。** **ビルドごとに環境を破棄すれば、常駐の期間が1回のビルドに限定される。** **ただし窃取そのものはビルド中に成立するため、「防止」ではない。**
C2通信機会はあったが検知できず
**本記録の評価である。** **C2 をブロックチェーンから解決する設計は、 「C2 の IP / ドメインを遮断する」という対策を無効にする**（本記録の読み）—— **攻撃者はメモを書き換えるだけで宛先を変えられ、 ブロックチェーンへの参照自体は遮断しにくい。** **一方 `movinlike` の Discord webhook への送出は、 「開発環境から Discord への送信」として捉えられる**—— **多くの組織で、ビルド環境が Discord へ話す理由は無い。** **IoC として最も実用的なのはこちらである**（本記録の評価）。
検知できたビルド環境・開発環境から Discord・Telegram 等の メッセージング基盤への通信を遮断する　**本記録の評価による。** **`movinlike` の送出先は Discord の webhook である。** **ビルド環境がこれらへ話す理由は通常無い**ため、 **遮断すると同時に検知の信号にもなる。**
影響を限定できたC2 の遮断に依存しない前提で対策を組む （取得の遮断・常駐の防止・窃取対象の分離）　**本記録の評価による。** **Overlord はブロックチェーンから C2 を解決するため、 宛先の遮断では止まらない。** **効くのは「ペイロードを取得させない」「常駐させない」側である** （上の段階の制御）。
収集公表されていない
**分析は被害側の検知について述べていない。** **本記録の評価** —— **開発者の端末は、組織の中で最も価値のある資格情報が 集まる場所である**—— レジストリのトークン・クラウドの資格情報・SSH 鍵・ ソースコードそのもの。 **Overlord の遠隔シェルとファイル検索は、これらを直接狙える。** **ただし本分析はそこまでの被害を確認していない**（窃取の対象として 挙げられているのは Discord・ブラウザ・暗号資産ウォレットである）。
影響を限定できた開発者の端末とビルド環境から、長期有効な資格情報を排除する （短命のトークン・ハードウェアキーへ移す）　**本記録の評価による。** **窃取そのものは防げないが、盗まれたものの価値を下げられる。** **これは本件に限らず、情報窃取マルウェア全般に効く。**
影響を限定できた本件が疑われる環境について、ブラウザの保存資格情報・ レジストリのトークンを失効させる　**本記録の評価による。** **`function-flag` は14か月間配られていた**ため、 **「いつから感染していたか」を特定するのは難しい。** **取り込んだ記録が見つかった場合は、期間を絞らずに失効させるのが安全側である** （本記録の評価）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「スキャナが検出していない」を安全の根拠にしない運用にする
    **`function-flag` は2025年7月18日から悪性でありながら、 2026年9月29日時点でアドバイザリが1件も無かった**（Checkmarx が確認）。 **その14か月間に37,419回ダウンロードされた。** **SCA（ソフトウェア構成分析）やレジストリの警告はアドバイザリの データベースに依存するため、載っていないものは「問題なし」と出る** （本記録の評価）。 **本件は、その状態が14か月続いた場合に何が起きるかの実測である。**
    取るべき行動 **依存パッケージの管理に「検査で緑だったか」とは別の軸を1つ作る**—— **①作者・公開元の実績（初公開からの期間・他の公開物）、 ②そのパッケージが本当に必要か（代替の有無）**の2点を 新規採用時の確認項目にする。 **公表されたキャンペーンのパッケージ名の一覧を、 アドバイザリの有無にかかわらず lockfile に直接照合する手順を持つ。**
  • 開発環境・CI 環境を「資格情報が最も集まる場所」として扱う
    **Overlord RAT は画面取得・キーロガー・遠隔シェル・ファイル検索・ 隠しデスクトップを備える**（Checkmarx・SecurityWeek の記述）。 **`movinlike` はブラウザ7種の保存データと暗号資産ウォレットを狙う。** **開発者の端末には、レジストリのトークン・クラウドの資格情報・SSH 鍵・ ソースコードが集まる**（本記録の評価）。 **さらに最大のパッケージが配っていたものは正体不明である**—— **何を実行されたか特定できない。**
    取るべき行動 **開発者の端末とビルド環境から長期有効な資格情報を排除する** （短命のトークン・ハードウェアキーへ移す）。 **本件のパッケージを取り込んだ環境が見つかった場合は、 期間と範囲を絞らずに資格情報を失効させる**と事前に決めておく （**正体不明のペイロードがあるため、証拠が無いことを根拠に範囲を狭めない**）。
  • 同じ事案の数値が調査会社で違うことを前提に、どちらを採ったか記録する
    **同じキャンペーンについて Checkmarx は「12個・8個が悪性・3経路」、 CloudSEK は「少なくとも9個・2経路」としている**（本記録が両者を確認）。 **公表日が5日違い、「無害な覆い」を数に入れるかどうかと 経路の切り分けの粒度が違うことによると考えられるが、 両者は互いの数え方に言及していない**（本記録の推測）。 **報道（SecurityWeek）は Checkmarx のみを調査元として伝えている。**
    取るべき行動 **脅威情報の記録に「出典・公表日・採用した数値」の3欄を置き、 複数の分析がある事案では併記する。** **社内の報告に数値を書くときは、どの調査のどの時点の値かを必ず添える** （後から別の数値が出たときに食い違いの原因が分かる）。
  • 「狙われた業種か」ではなく「入れたか」で判断する事案があると理解する
    **Checkmarx は「地理的・組織的な標的設定は見つからなかった。 この窃取ツールを入れた者は誰でも標的になる」とし、 「正規の、あるいは広く使われているパッケージはこの作者のパッケージに 一切依存していないため、露出はこれらのパッケージ名を直接インストールした システムに限られる」としている**（原文英語）。 **業種・地域での絞り込みが無いため「自社は対象か」という問いが意味を持たない** （本記録の評価）。
    取るべき行動 **脅威情報の受け取りの手順に「標的が絞られている事案か／ 入れた者が被害者になる事案か」の区分を入れる。** **後者については、業種の該当性を検討せず、 ただちに lockfile と取得ログの照合に進む**と決めておく。
セキュリティ技術者への示唆
  • lockfile と取得ログの両方で、履歴まで遡って名前を照合する
    **本件は推移的依存で巻き込まれる形ではなく、 「パッケージ名を直接インストールした環境」に限られる**（Checkmarx の記述）。 **したがって名前の照合で確実に判定できる**（本記録の評価）。 **ただし lockfile に残らない取得もある**—— **開発者が手元で試して後に外した場合や、 lockfile を使わない取得である。** **`function-flag` は14か月間悪性だったため、 過去のコミットに入っていた時期も対象になる。**
    取るべき行動 **公表されたパッケージ名（`function-flag`・`function-color`・`cdn-img-fetch`・ `tlxbnhd`・`tldriver`・`mxdriver`・`img-to-native`・`native-runner`）を、 ①全リポジトリの lockfile（履歴を含む）、 ②レジストリのプロキシ・ミラーの取得ログに照合する。** **②が無い場合は、まず取得ログを残す仕組みを入れる** （本件に遡って使えなくても、次に使える）。
  • インストール時スクリプトの無効化では経路2 が止まらないことを前提に組む
    **Checkmarx は配信経路を3つに整理しており、 経路2 はインストール時ではなく「パッケージの読み込み時」に動く** （`cdn-img-fetch` → `img-to-native` → `native-runner` の連鎖）。 **`--ignore-scripts` で止まるのは経路1 と経路3 だけである**（本記録の読み）。 **「インストール時スクリプトを無効にしたから安全」とは言えない。**
    取るべき行動 **`--ignore-scripts` を既定にする**（ネイティブモジュールのビルドが必要な 依存は例外として個別に許可する）。 **あわせて CI のビルド環境から外部への通信を、 レジストリと社内ミラーに限定する**—— **3つの経路はいずれも外部からペイロードを取得するため、 こちらのほうが広く効く。**
  • ビルド環境から Discord・Telegram への通信を遮断し、検知の信号として使う
    **`movinlike` は窃取したデータを Discord の webhook へ送出する** （Checkmarx・CloudSEK）。 **一方 Overlord RAT は C2 のアドレスを持たず Solana ブロックチェーン上の暗号化メモから宛先を解決する**ため、 **C2 の IP / ドメインを遮断する対策は効かない**（本記録の評価）。 **ビルド環境・開発環境が Discord へ話す理由は通常無い。**
    取るべき行動 **ビルド環境と開発環境から Discord・Telegram 等のメッセージング基盤への 通信を遮断し、遮断の発生を監視の信号として扱う。** **C2 の宛先の遮断に依存しない前提で対策を組む**—— 効くのは「ペイロードを取得させない」「常駐させない」側である。
  • ビルド中に実行形式や大きなバイナリが落ちたことを記録する
    **経路1 は `api.imghippo.com` から取得したものを `gldriver_pre_core.exe` / `gldriver_pre_asset.exe` として保存・起動し、 その後スクリプト自身を削除する**（Checkmarx）。 **`movinlike` は 64MB の Node.js バンドルとして配られる**（CloudSEK）。 **ビルド中に実行形式や 64MB のバンドルが落ちるのは、 通常の依存取得とは明らかに異なる挙動である**（本記録の評価）。
    取るべき行動 **ビルド環境で生成・取得されたファイルのうち、 実行形式と一定の大きさを超えるバイナリを記録する。** **今回に限っては `gldriver_pre_core.exe`・`gldriver_pre_asset.exe` という 具体的な名前で探せる**が、 **恒久の手段としては「ビルド中に実行形式が落ちたか」を見るほうを採る** （名前は変種で変わる）。
  • ビルド環境を使い捨てにして、常駐の期間を1回のビルドに限定する
    **Overlord RAT と `movinlike` はいずれも常駐して資格情報を窃取する。** **`function-flag` は14か月間悪性だったため、 同じ環境を使い続けている場合は常駐の期間が長くなる**（本記録の評価）。 **使い捨ての環境ならビルドごとに消えるが、 窃取そのものはビルド中に成立するため「防止」ではない。**
    取るべき行動 **CI のビルドを使い捨ての環境（コンテナ・一時的な仮想マシン）で行い、 ビルドごとに破棄する。** **開発者の端末については、依存の取得と実行を プロジェクトごとに分離した環境で行うことを検討する** （端末そのものに常駐させない）。
