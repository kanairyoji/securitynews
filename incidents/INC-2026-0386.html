CloudSEK は2026年10月5日、報告「Caught in 4K: The Gentlemen Files」を公表した。RaaS 「The Gentlemen」のアフィリエイトであるロシア語話者「Azazel」が運用していた2台のサーバが外部から到達可能な状態で露出しており、CloudSEK がその中身を解析したものである。

本件の性格を決めるのは、二重の裏切りである（CloudSEK の記述。原文英語）—— 「Azazel は標準的なアフィリエイトの手順書に従って動いていたのではない。彼は Leakned というブランドで自前の独立したリークサイトを構築・運営し、被害者のデータを公開して恐喝の収益を Gentlemen のプログラムを通さずに回収していた。これは被害者に対する裏切りと並んで、RaaS 運営者に対する裏切りでもある」。

被害は6か国・24社超。業種は物流・保険・製薬・AI・医療機器・政府関連インフラ。組織名・国名の内訳は公表されていない（公表前に被害組織への通知が開始された）。

侵入経路は2系統である。

経路A —— CI/CD の秘密情報の収穫。 CloudSEK は「確認された全被害に到達したのは侵害された CI/CD の秘密情報だった」としている（原文英語）。露出した GitLab からCI/CD トークン・データベースの資格情報・API キー・SSH 秘密鍵を集め、そこからクラウドやデータベースへ入る。使っていた道具は glato・nord-stream・gitlab-secrets・gitlab-watchman・gitleaks（いずれも公開されている調査用ツール）。1台の GitLab の侵害が無関係な2組織の足場を生んだ事例と、1本の CI/CD トークンの露出が SaaS 基盤の150を超えるデータベースに届いた事例が報告されている。

経路B —— 認証不要の AI 推論 API から数週間の多段侵害。起点は医療画像の AI API における SSRF（検証されない URL 取得）。そこから内部サービスを発見し、Jasypt のマスターキーを回収して暗号化された設定値をまとめて復号、git 履歴に残っていたハードコードの認証バイパス用 JWT を取得、Grafana の管理者ハッシュをオフラインで解析、MinIO のオブジェクトストレージを継続的に同期、Kubernetes の kubeconfig と SSH 秘密鍵を収穫—— 6TB 超を持ち出し、CloudSEK が発見した時点でもまだ転送が続いていた。

そしてもう一点。 Azazel は AI コーディング支援のツール接続（MCP）にリバースシェルを呼び出し可能なツールとして登録し、実際の侵害で C2 として使っていた。 CloudSEK はこれを、実際の犯罪キャンペーンにおける MCP の運用利用の最初の確認例としている（本記録はこの「最初」の主張を検証していない。discrepancies 参照）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は観測に基づく記録である** —— **CloudSEK が露出した加害者側のサーバを解析して組み立てたもので、 推定した攻撃経路ではない。** **ただし被害組織側のログやフォレンジックに基づくものではないため、 各段階の時刻・被害側の検知の有無は分からない**（本記録の限界）。 **経路は2系統あり、性格が大きく違う。** **経路A は横に広い** —— 露出した GitLab から CI/CD の秘密情報を収穫し、 **公開ツールの組み合わせで、組織を問わず同じ手順が通る。** **CloudSEK は確認された全被害に到達したのがこれだったとしている。** **経路B は縦に深い** —— 認証不要の AI 推論 API の SSRF を起点に、 暗号化設定の一括復号・git 履歴の JWT・Grafana・MinIO・Kubernetes と 数週間かけて降りていく。 **CloudSEK は「標準的なアフィリエイトの技量をはるかに超える水準」と評価している。** **そして C2 に AI コーディング支援のツール接続（MCP）が使われていた** —— **侵害した端末へのコマンド送信を、AI 支援ツールの「呼び出せる道具」として 登録する形である。**

  1. 1. 偵察[1] [2]
    **露出した GitLab インスタンスと、認証を要しない AI 推論エンドポイントの探索。** **CloudSEK は Azazel が専用の走査基盤を持っていたことを確認している** —— **識別名 `internet-census-mcp-scanner` で、 外部に開いた AI 支援ツール（MCP サーバ）のポートを探していた。** **つまり偵察の対象に「AI の道具立てそのもの」が入っていた**（本記録の整理）。 **GitLab の探索に使われた具体の走査手段は公表されていない。**
  2. 2. 初期侵入[1] [2] [3]
    **経路A —— 露出した GitLab から CI/CD の秘密情報を収穫する。** **取ったのは CI/CD トークン・データベースの資格情報・API キー・SSH 秘密鍵。** **CloudSEK が特記している点が重要である** —— **「秘密情報は開発者によって Git リポジトリの現在の版からは 削除されていたと思われるが、より前のコミットには残っており、 Azazel はそれを見つけた」**（Infosecurity Magazine の記述。原文英語）。 **使った道具は glato・nord-stream・gitlab-secrets・gitlab-watchman・gitleaks** （いずれも公開されている調査用ツールで、自作のマルウェアではない）。 **経路B —— 認証を要しない AI 医療画像 API の SSRF。** **CloudSEK の記述は「検証されない URL 取得（unvalidated URL fetch）」。** **外部から渡した URL を API がそのまま取得するため、 内部ネットワークのサービスを外から探索できる。**
  3. 3. 認証情報アクセス[1] [2]
    **経路B の中核の段階である。** **①Jasypt のマスターキーを回収し、暗号化されていた設定値をまとめて復号した。** **CloudSEK の記述は「あらゆる保護された値を一括で復号できる状態になった」 （原文英語）。** **②git 履歴から、ハードコードされた認証バイパス用の JWT を取得した。** **③Grafana の管理者パスワードハッシュを取得し、オフラインで解析した。** **④Kubernetes の kubeconfig・SSH 秘密鍵・資格情報を含むコンテナ設定を収穫した。**
  4. 4. C2通信[1] [2] [3]
    **本件で最も新しい要素である。** **Azazel は AI コーディング支援のツール接続（MCP）に リバースシェルの受け口を「呼び出せる道具」として登録し、 侵害した端末へのコマンド送信に使った。** **CloudSEK が挙げた具体の形**—— **①身代金通告の確認用スクリプト `va.py` が ローカルの 127.0.0.1:35367 を呼んでいた、 ②MCP クライアントの識別名が `hermes` だった。** **CloudSEK はこれを「実際の犯罪キャンペーンにおける `exec_in_session` の C2 利用」の最初の確認例としている。** **さらに、自分の基盤管理にも AI の道具立てを使っていたことが確認されている。**
  5. 5. 持ち出し[1] [2]
    **経路B では MinIO のオブジェクトストレージを継続的に同期していた** （CloudSEK の記述は「被害者のオブジェクトストレージのバケットを 継続的に複製していた」。原文英語）。 **6TB 超が持ち出され、発見時点でもまだ転送が続いていた。** **CloudSEK は、ある持ち出しが「観測の間に数百 GB 単位で増えていった」と 記述している。** **持ち出し先は Azazel の専用物理サーバ**—— **中継用（29.2TB・識別名 `forgitlab`）に集め、 長期保管庫（22TB・識別名 `novostnik`）へ移す構成。** **MEGA クラウドへの持ち出し（66.203.124.135:443）と ビーコンの定時通信（141.95.252.30）も確認されている。**

アフィリエイトは運営の管理外で動ける。だから RaaS の銘柄で数える観測は実態を映さない評価・解釈

本件の構造上の核心はここである（本記録の評価）。

CloudSEK の記述（原文英語）—— 「Azazel は標準的なアフィリエイトの手順書に従って動いていたのではない。彼は Leakned というブランドで自前の独立したリークサイトを構築・運営し、被害者のデータを公開して恐喝の収益を Gentlemen のプログラムを通さずに回収していた」。

防御側にとって、これは観測の問題である。

  • The Gentlemen のリークサイトを監視していても、Azazel の被害は現れない。 データは LEAKNED に載る。
  • 「どの群に狙われているか」を問いにした監視は、群の外で動くアフィリエイトを取り落とす。
  • RaaS の銘柄別の被害件数は、群の運営が掲載したものしか数えない。 アフィリエイトが独立して恐喝した分は、どの群の集計にも入らない。

本DBの運用にも同じ問題がある（本記録の整理）。リークサイト掲載を群ごとに集計している観測では、本件の24社超はどの群の数字にも現れない。

実務上の結論は単純である（本記録の評価）—— リークサイトの監視を「自組織の名称・ドメイン」単位にする。 群の名前を追うのではなく、自分の名前が出ていないかを探す。 そうすれば、どのサイトに載っても引っかかる。

なお、Azazel が運営を裏切ったこと自体は、防御側の関心事ではない（本記録の立場）。関心事は「アフィリエイトが運営の管理外で動けるという前提が確認された」ことである。

確認された全被害に到達したのは CI/CD の秘密情報だった原因・手口

CloudSEK の記述は明確である（原文英語）—— 「侵害された CI/CD の秘密情報が、確認された全被害に到達するために使われた」。

24社超・6か国・業種はばらばらである。 それでも共通していたのは、CI/CD に渡された資格情報だった（事実）。

報告が示した3つの例が、それぞれ別のことを教える（本記録の整理）。

例 何が起きたか 読み取れること
1台の GitLab の侵害 無関係な2組織の足場が生まれた 1つのインスタンスに複数組織の資格情報が集まっていた
1本の CI/CD トークン SaaS 基盤の150を超えるデータベースに到達 CI に渡す権限は、境界を越えるように設計されている
政府関連の金融登録簿 12万件超の記録 公的機関も同じ経路で落ちる

2行目が最も重い（本記録の評価）。CI/CD に渡す資格情報は「ビルドとデプロイを通すために必要なもの」として設計される。 その結果、テナント境界や環境境界を越える権限を持つことになる。 1本が出れば150個に届くのは例外ではない。そういう設計だからである。

そしてもう一点、Azazel の掘り方が重要である。 Infosecurity Magazine の記述（原文英語の要旨）—— 「秘密情報は開発者によって Git リポジトリの現在の版からは削除されていたと思われるが、より前のコミットには残っており、Azazel はそれを見つけた」。

つまり「消したつもり」が生きていた（本記録の整理）。ここで肝心なのは、対処が「履歴から消すこと」ではないことである。

  • 履歴の書き換えは難しく、複製されたリポジトリには届かない。
  • フォーク・クローン・ミラー・バックアップのどこかに残る。
  • したがって、一度コミットされた資格情報は「漏れたもの」として無効化するしかない（本記録の評価）。

Azazel が使っていた道具は glato・nord-stream・gitlab-secrets・gitlab-watchman・gitleaks で、いずれも公開されている調査用ツールである。 自作のマルウェアは要らない。 防御側も同じものを使える——攻撃者が見つけられるものは、自分でも見つけられる。

6TB が数週間かけて出ていき、気づいたのは被害組織ではなかった被害規模・影響範囲

経路B（医療画像の AI 企業）の経過を並べる（CloudSEK の記述に基づく事実）。

  1. 認証を要しない AI 医療画像 API の SSRF（検証されない URL 取得）で内部を探索
  2. Jasypt のマスターキーを回収 —— 暗号化されていた設定値を一括で復号
  3. git 履歴からハードコードの認証バイパス用 JWT を取得
  4. Grafana の管理者ハッシュをオフラインで解析
  5. MinIO のオブジェクトストレージを継続的に同期
  6. Kubernetes の kubeconfig・SSH 秘密鍵・資格情報を含むコンテナ設定を収穫

CloudSEK の評価は「標準的なアフィリエイトの技量をはるかに超える水準」である。

しかし、防御側が受け取るべきことは技量の評価ではない（本記録の評価）。

「数週間にわたり」「6TB 超が出て」「発見時点でもまだ転送中だった」。

これは一瞬で終わる持ち出しではない。 継続する大量の外向き通信であり、オブジェクトストレージの読み出し記録に必ず現れる量である。

にもかかわらず、見つけたのは被害組織ではなかった。 加害者側の露出したサーバを第三者が発見したことで分かった。

本記録はこの段階の検知機会を「機会はあったが検知できなかった」と判断する（本記録の評価）。根拠は量と期間である —— 6TB・数週間という規模は、平常時の読み出し量との乖離として現れる。

逆に言えば、必要なのは平常時の値を持っていることである（本記録の評価）。「どのバケットが、普段、誰によって、どれだけ読まれているか」を知らなければ、6TB が出ていても異常として見えない。 検知の道具ではなく、基準値の有無が分かれ目である。

もう一点。 6TB が出たのは、6TB があったからである。 AI の事業者は学習用データ・中間生成物・推論ログを大量に保持しやすい（本記録の評価）。保持しているデータ量そのものが、持ち出しの上限を決める。

AI 支援ツールのツール接続が C2 になった。管理の対象が端末の構成情報に移る評価・解釈

CloudSEK が確認した形を具体に書く（事実）。

  • Azazel は AI コーディング支援のツール接続（MCP）にリバースシェルの受け口を「呼び出せる道具」として登録した。
  • 身代金通告の確認用スクリプト va.py がローカルの 127.0.0.1:35367 を呼んでいた。
  • MCP クライアントの識別名は hermes だった。
  • 別に、外部に開いた AI 支援ツールのポートを探す専用の走査基盤（識別名 internet-census-mcp-scanner）を保有していた。
  • 自分の基盤管理にも AI の道具立てを使っていた。

CloudSEK はこれを「実際の犯罪キャンペーンにおける MCP の運用利用の最初の確認例」としている。 本記録は「最初」を検証していない（確認には網羅的な調査が必要であり、行っていない)。検証していない主張を記録の前提には置かない。

防御側が受け取るべきことは2つある（本記録の評価）。

① 通信の形で見つけられない。 AI 支援ツールと MCP サーバの間の通信は、開発端末では正当なものとして存在しうる。 本件のようにループバック（127.0.0.1:35367）を経由する形は、ネットワーク監視にそもそも出ない。 「外向きの不審な通信」を探す監視では現れない。

② 見るべきものは端末の構成情報である。 「どのプロセスが MCP サーバとして登録されているか」「AI 支援ツールの設定にどのツールが接続されているか」——これは資産管理の情報であり、ネットワークの情報ではない。 多くの組織は現時点でこれを収集していない（本記録の評価）。

実務としては、インストール済みソフトウェアの一覧と同じ重さで「AI 支援ツールに接続されている道具の一覧」を管理対象にする。

そして走査されている側のことも記録しておく。 Azazel は外部に開いた MCP サーバのポートを探す専用の基盤を持っていた。 攻撃者が専用の走査を組むほど対象として認識されている以上、外部露出の棚卸しの項目に「AI 支援ツールのポート」を明示的に加える必要がある（本記録の評価）。

したがって、本件から取るべき行動は「同じ経路を自分で点検すること」に尽きる（本記録の評価）—— 露出した GitLab があるか、git 履歴に資格情報が残っていないか、認証不要の推論エンドポイントが外に出ていないか、オブジェクトストレージの読み出し量の基準値を持っているか。 通知を待つのではなく、攻撃者と同じ道具で自分を見る。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
Azazel の2系統の侵入経路と、RaaS を迂回した恐喝の構造
layer 0 は組織の構図——RaaS 運営 The Gentlemen と、 そのアフィリエイトでありながら自前のリークサイト LEAKNED を運営した Azazel。 恐喝金は運営を通らず Azazel に入った（二重の裏切り）。 layer 1 は偵察——露出した GitLab と、認証を要しない AI 推論エンドポイント、 そして外部に開いた AI 支援ツールのポートを探す専用の走査基盤。 layer 2 は2系統の侵入経路。 経路A は CI/CD の秘密情報の収穫（公開ツール glato・gitleaks 等）で、 確認された全被害に到達した経路。 経路B は AI 医療画像 API の SSRF を起点とする数週間の多段侵害。 layer 3 は経路Bの内部での降下——Jasypt のマスターキーによる設定値の一括復号、 git 履歴のハードコード JWT、Grafana の管理者ハッシュ、 MinIO の継続同期、Kubernetes の kubeconfig。 layer 4 は C2 と持ち出し——AI 支援ツールのツール接続（MCP）に 登録されたリバースシェル、専用物理サーバ（中継29.2TB・保管庫22TB・合計50TB超）。 layer 5 は結果——6か国24社超、6TB 超（転送中に発見）、 SaaS 基盤の150超のデータベース、政府関連登録簿の12万件超。 点線は本記録が報告の記述から補った関係、または公表されていない部分。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察機会はあったが検知できず
**外部からの走査は被害側のログに残りうる段階である。** **本記録の評価** —— **ただしインターネット全体への走査は常時大量にあり、 これだけを手がかりに動くことは現実的でない。** **意味があるのは「自組織の何が外から見えているか」を 自分で確認しておくことである** —— **GitLab の管理画面・サインアップ画面・API エンドポイント、 認証を要しない推論エンドポイント、MCP サーバのポート。** **攻撃者が走査しているものと同じものを自分で数える。**
侵入を防げた外部に露出している資産の棚卸し（GitLab・CI ランナー・ 認証不要の推論エンドポイント・AI 支援ツールのポート）を定期的に行う　**本記録の評価による。** **経路A・経路B のいずれも「外から見えていたこと」が起点である。** **露出を無くせば、この2系統はどちらも成立しない。** **とくに AI 支援ツールのポートは、 攻撃者側が専用の走査基盤を作るほど狙われている** （CloudSEK の確認）——**棚卸しの対象に明示的に加える必要がある。**
侵入を防げたAI の推論エンドポイントに認証を要求する（経路Bの起点を閉じる）　**本記録の評価による。** **経路Bの起点は「認証を要しない AI 医療画像 API」である。** **推論エンドポイントは、業務システムと違って 「モデルに問い合わせるだけ」と認識されやすく、 認証の設計が後回しになりやすい**（本記録の評価）。
初期侵入公表されていない
**CloudSEK は被害側の検知について述べていない** （解析の対象が加害者側のサーバであるため）。 **本記録の評価** —— 段階ごとに検知の難易度が大きく違う。 **経路A の GitLab へのアクセスは、認証を伴う正規のアクセスとして成立する** —— **盗んだトークンで入るため、失敗ログにも異常ログにも残らない。** **残るとすれば「普段と違う接続元からの API 利用」「 普段アクセスしないプロジェクトの履歴の走査」である。** **経路B の SSRF は検知しやすい側である** —— **API サーバから内部アドレス（169.254.169.254・10.0.0.0/8 等）や 外部の未知のホストへの発信が出る。** **推論エンドポイントが置かれたコンテナの外向き通信を 制限・監視していれば現れる。**
侵入を防げたCI/CD に渡す資格情報を短命の動的な資格情報（OIDC による 一時トークン等）に置き換え、長期の静的トークンを置かない　**本記録の評価による。** **経路A の前提は「取れば使える資格情報が置いてあること」である。** **短命の資格情報なら、リポジトリや履歴から見つけても期限が切れている。** **CloudSEK が「確認された全被害に到達したのは侵害された CI/CD の 秘密情報だった」としている以上、ここが唯一の共通点である**（本記録の整理）。
侵入を防げたgit の全履歴（過去のコミット・削除済みブランチ・タグ）を対象とした 秘密情報の走査を定期的に行い、見つかった資格情報は必ず失効させる　**本記録の評価による。** **Azazel は「現在の版からは消えているが履歴に残っている」秘密情報を 掘り出していた。** **ここで肝心なのは「消す」ではなく「失効させる」である** —— **履歴から消す作業（履歴の書き換え）は難しく、 複製されたリポジトリには届かない。** **一度コミットされた資格情報は、漏れたものとして無効化するしかない。** **Azazel が使っていた gitleaks・gitlab-secrets は 防御側も同じものを使える。**
影響を限定できた推論 API を含む外部公開サービスの外向き通信を、 必要な宛先のみに限定する（SSRF の影響を内部探索に広げない）　**本記録の評価による。** **SSRF そのものを防ぐのは入力検証だが、 実装を直すまでの影響を抑えるのは外向き通信の制限である。** **これは影響範囲の限定であって、侵入そのものの防止ではない** —— **URL 検証の欠陥は残るため、修正が必要である。**
認証情報アクセス公表されていない
**CloudSEK は被害側の検知について述べていない。** **本記録の評価** —— **この段階の多くは「読むだけ」の操作であり、 痕跡が残りにくい。** **Jasypt の復号は攻撃者の手元で完結する** —— **マスターキーを取った後は、被害組織のシステムに触らずに 設定値を平文化できる。** **git 履歴の走査も、認証済みの読み取りとして成立する。** **逆に痕跡が残りうるのは Grafana のハッシュ取得（管理 API への到達）と、 kubeconfig を使った Kubernetes API への接続である。** **後者は監査ログに残る** —— **「見慣れないユーザが secret を一覧する」は検知可能な事象である。**
影響を限定できた設定値の暗号化のマスターキーを、アプリケーションと同じ場所に置かない （鍵管理サービス・HSM に分離し、鍵の利用を監査する）　**本記録の評価による。** **Jasypt のような設定値の暗号化は「設定ファイルを見ただけでは パスワードが分からない」ことを目的とする。** **マスターキーが同じサーバの中にあるなら、 侵入した攻撃者にとっては一手増えるだけである**（本記録の評価）。 **鍵が外部の管理サービスにあれば、鍵の利用そのものが記録に残り、 異常な一括復号が検知の手がかりになる。**
検知できたKubernetes の監査ログを有効にし、secret の一覧・取得を 利用主体ごとに監視する　**本記録の評価による。** **kubeconfig を取られた後の操作は、正規の API 呼び出しとして成功する。** **残るのは「誰が何をしたか」の記録だけである。** **とくに「secret の一括列挙」は、 通常の運用では稀であり、攻撃の段階としては特徴的である。**
影響を限定できたGrafana・MinIO・GitLab などの運用系サービスを インターネットから直接到達できない位置に置く　**本記録の評価による。** **本件で使われたのは、いずれも「運用のために便利な場所に置かれやすい」 サービスである。** **経路Bは SSRF から内部に入っているため、 内部に置いても到達されうる**（だから防止ではなく影響範囲の限定にとどまる）。 **それでも、外から直接触れる状態と、 SSRF を経なければ触れない状態では成立の難易度が違う。**
C2通信公表されていない
**CloudSEK は被害側の検知について述べていない。** **本記録の評価** —— **この段階が厄介なのは、通信の形が C2 らしくないことである。** **AI 支援ツールと MCP サーバの間の通信は、 開発端末では正当なものとして存在しうる。** **ローカルのループバック（127.0.0.1:35367）を経由する形は、 ネットワーク監視には出ない。** **検知の手がかりになるのは 「どのプロセスが MCP サーバとして登録されているか」 「AI 支援ツールの設定にどのツールが接続されているか」であり、 これはネットワークではなく端末側の構成情報である。** **現状の多くの組織は、この構成情報を収集していない** （本記録の評価）。
検知できた開発端末の AI 支援ツールの設定（接続されている MCP サーバの一覧）を 資産管理の対象に入れ、承認されていない接続を検出する　**本記録の評価による。** **本件では攻撃者が自分の道具として使っているが、 同じ仕組みは被害側の端末に仕掛けることもできる**（本記録の評価）。 **「AI 支援ツールにどんな道具がつながっているか」は、 インストールされたソフトウェアの一覧と同じ重さで 管理すべき情報になっている。**
侵入を防げた外部に開いた AI 支援ツール（MCP サーバ）のポートを棚卸しし、 インターネットから到達できないようにする　**本記録の評価による。** **Azazel は専用の走査基盤（`internet-census-mcp-scanner`）で これを探していた**（CloudSEK の確認）。 **攻撃者が専用の走査を組むほど対象として認識されている以上、 棚卸しの項目に明示的に入れる必要がある。**
持ち出し機会はあったが検知できず
**CloudSEK は被害側の検知について述べていないが、 本記録はこの段階を「機会はあったが検知できなかった」と判断する。** **根拠** —— **6TB 超が数週間かけて外部へ出て行き、 発見時点でもまだ続いていた。** **これは一瞬で終わる持ち出しではなく、 継続する大量の外向き通信である**（本記録の評価）。 **オブジェクトストレージの同期は、 「どのバケットから、誰が、どれだけ読んだか」の記録に現れる。** **にもかかわらず、発見したのは被害組織ではなく、 加害者側のサーバを見つけた第三者である。** **つまり「気づける量が出ていたのに気づかれなかった」** —— **これが本件で被害側に最も重い事実である。**
検知できたオブジェクトストレージの読み出し量を利用主体ごとに監視し、 平常時からの乖離で警報を出す　**本記録の評価による。** **6TB の継続的な同期は、平常の読み出し量とは桁が違う。** **「どのバケットが、普段どれだけ読まれているか」を 基準値として持っていれば現れる。** **逆にこれを持っていない組織では、 持ち出しは最後まで見えない**（本記録の評価）。
影響を限定できたデータの持ち出しの観点で、保持しているデータ量そのものを減らす （保持期限の設定・不要なデータセットの削除）　**本記録の評価による。** **経路Bで6TB が出たのは、6TB があったからである。** **とくに AI の事業者は学習用データ・中間生成物・ 推論ログを大量に保持しやすい**（本記録の評価）。 **「持っていないデータは出ていかない」は 技術的対策の中で最も確実なものである。**
影響（暗号化・破壊・改ざん）現実的な検知機会なし
**本記録の評価** —— **この段階は被害組織の側では「恐喝を受ける」という形で 必ず認識される。検知の問題ではない。** **ただし、本件に固有の問題がある** —— **被害組織が「どこに自分のデータが載ったか」を把握できない。** **The Gentlemen のリークサイトを監視していても、 Azazel のデータは LEAKNED に載る。** **RaaS の銘柄で監視している観測は、この被害を取り落とす** （本記録の評価。lessons 参照）。
検知できたリークサイトの監視を「RaaS の銘柄」単位ではなく 「自組織の名称・ドメイン」単位で行う　**本記録の評価による。** **本件はアフィリエイトが自前のサイトで恐喝した例であり、 銘柄を追う監視では現れない。** **自組織の名前で探す監視なら、どのサイトに載っても引っかかる。** **「どの群に狙われているか」ではなく 「自分の名前が出ていないか」を問いにする。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • リークサイトの監視を「群の名前」から「自組織の名前」に切り替える
    **本件はアフィリエイトが RaaS 運営の管理外で自前のリークサイトを運営し、 恐喝金を直接回収していた例である**（CloudSEK の記述）。 **The Gentlemen のリークサイトを監視していても、 Azazel の被害は現れない。データは LEAKNED に載る。** **「どの群に狙われているか」を問いにした監視は、 群の外で動くアフィリエイトを構造的に取り落とす**（本記録の評価）。 **RaaS の銘柄別の被害件数も同じで、 アフィリエイトが独立して恐喝した分はどの群の集計にも入らない。**
    取るべき行動 **リークサイト・恐喝サイトの監視の問い合わせ条件を、 群の銘柄ではなく「自組織の名称・ドメイン・主要な子会社名・ 主要な取引先名」に変える。** **委託先・取引先の名称も監視対象に入れる** （自社が載らなくても、データを預けた先が載ることがある）。 **監視を外部サービスに委託している場合は、 その対象が「追跡している群のサイト」に限られていないかを契約・仕様で確認する。**
  • CI/CD に渡す資格情報を、経営の議題として扱う権限の問題に引き上げる
    **CloudSEK は「確認された全被害に到達したのは 侵害された CI/CD の秘密情報だった」としている**（原文英語）。 **24社超・6か国・業種はばらばらで、共通点はこれだけである。** **さらに報告は「1本の CI/CD トークンの露出が SaaS 基盤の150を超えるデータベースに届いた」例を挙げている。** **CI/CD に渡す資格情報は「ビルドとデプロイを通すために必要なもの」として 設計されるため、テナント境界や環境境界を越える権限を持つ**（本記録の評価）。 **1本が出れば150個に届くのは例外ではなく、そういう設計だからである。** **これは技術的な設定の問題ではなく、 「誰がどこまで届く鍵を持つか」という権限の問題である。**
    取るべき行動 **CI/CD のパイプラインが保持している資格情報の一覧と、 それぞれが到達できる範囲（環境・テナント・データベース）を 1枚の表にして経営に提示させる。** **「このパイプラインが侵害されたら何に届くか」を、 システムごとではなくパイプラインごとに評価する。** **長期の静的トークンを短命の動的な資格情報（OIDC による 一時トークン等）へ置き換える計画に、期限と責任者を付ける。**
  • 「気づける量が出ていたのに気づかなかった」を自組織で再現して確かめる
    **経路Bでは6TB 超が数週間かけて出て行き、 CloudSEK が発見した時点でもまだ転送が続いていた**（事実）。 **オブジェクトストレージの継続同期は、読み出し記録に必ず現れる量である** （本記録の評価）。 **にもかかわらず見つけたのは被害組織ではなく、 加害者側の露出したサーバを見つけた第三者である。** **検知の道具が無かったのではなく、平常時の基準値が無かったとみられる** （本記録の推定）—— **「どのバケットが普段どれだけ読まれているか」を知らなければ、 6TB が出ていても異常として見えない。**
    取るべき行動 **自組織のオブジェクトストレージ・データベース・ファイルサーバについて、 「平常時の読み出し量」を利用主体ごとに測り、記録する。** **そのうえで、机上ではなく実際に 「数百 GB を外部へ転送したら何分で警報が出るか」を検証する演習を行う。** **出ない場合は、それが現在の実力である** （本記録の評価。演習で出ないものが本番で出ることはない）。
  • 第三者からの通知に依存した発見を、防御計画の前提にしない
    **本報告が成立した条件は「加害者側のサーバが外部から到達可能だった」ことである** （本記録の整理）。 **加害者の運用上の失敗が、被害の全体像を外部に見せた。** **CloudSEK は、サーバがいつから露出していたか・ いつ・どのように見つけたかをいずれも公表していない。** **本件で分かった24社超は、たまたま見えた分である。** **見えていない分がどれだけあるかは原理的に分からない**（本記録の評価）。
    取るべき行動 **「外部から通知を受けて初めて侵害を知った」件数を自組織で数え、 自力検知との比率を経営報告の定期項目にする。** **外部通知が主な発見経路になっているなら、 それは検知能力の指標として扱う**（通知してくれた相手に依存した状態である）。 **あわせて、外部からの通知を受け付ける窓口（security.txt・ 脆弱性報告の受付）を整備し、通知が届かずに落ちることを防ぐ。**
セキュリティ技術者への示唆
  • git の全履歴を対象に秘密情報を走査し、見つかったら「消す」ではなく「失効させる」
    **Azazel は「開発者が現在の版からは削除したが、 より前のコミットには残っていた」秘密情報を掘り出していた** （Infosecurity Magazine の記述。原文英語）。 **ここで肝心なのは、対処が履歴の書き換えではないことである** （本記録の評価）—— **履歴から消す作業は難しく、 フォーク・クローン・ミラー・バックアップには届かない。** **一度コミットされた資格情報は、漏れたものとして無効化するしかない。** **Azazel が使っていた gitleaks・gitlab-secrets は公開ツールであり、 防御側も同じものを使える。**
    取るべき行動 **全リポジトリの全履歴（過去のコミット・削除済みブランチ・タグ）を対象に 秘密情報の走査を定期実行する**（`gitleaks` 等。 **現在のファイルだけを見る設定になっていないかを確認する**）。 **検出された資格情報は、対象のサービス側で必ず失効させる** （リポジトリから消すだけで完了にしない）。 **走査の結果を「検出件数」ではなく「失効させた件数」で管理する。** **さらに、コミット時に秘密情報を弾く仕組み（pre-commit フック・ サーバ側の push 時検査）を入れて、新規の流入を止める。**
  • 外部露出の棚卸しに「AI の推論エンドポイント」と「AI 支援ツールのポート」を加える
    **経路Bの起点は「認証を要しない AI 医療画像 API」の SSRF である**（事実）。 **推論エンドポイントは「モデルに問い合わせるだけ」と認識されやすく、 認証の設計が後回しになりやすい**（本記録の評価）。 **さらに Azazel は、外部に開いた AI 支援ツール（MCP サーバ）の ポートを探す専用の走査基盤 （識別名 `internet-census-mcp-scanner`）を保有していた** （CloudSEK の確認）。 **攻撃者が専用の走査を組むほど、対象として認識されている。**
    取るべき行動 **外部露出の棚卸しの項目に、次を明示的に加える**—— ①**推論 API のエンドポイント**（認証の有無・URL を受け取るパラメータの有無）、 ②**AI 支援ツール（MCP サーバ）のポート**、 ③**GitLab・Grafana・MinIO などの運用系サービスの管理画面。** **とくに①については「外部から渡された URL を取得する実装があるか」を コードの観点で確認する**（SSRF の有無）。 **あわせて、推論 API を置いたコンテナの外向き通信を 必要な宛先のみに限定する**（SSRF の影響を内部探索に広げない）。
  • 設定値の暗号化のマスターキーを、復号する側と同じ場所に置かない
    **経路Bで Azazel は Jasypt のマスターキーを回収し、 「あらゆる保護された値を一括で復号できる状態」になった** （CloudSEK の記述。原文英語）。 **設定値の暗号化は「設定ファイルを見ただけでは パスワードが分からない」ことを目的とする。** **マスターキーが同じサーバの中にあるなら、 侵入した攻撃者にとっては一手増えるだけである**（本記録の評価）。 **さらに、鍵を取った後の復号は攻撃者の手元で完結するため、 被害組織のシステムには痕跡が残らない。**
    取るべき行動 **設定値の暗号化に使う鍵を、鍵管理サービス（KMS・HSM・Vault 等）へ 分離し、鍵の取得・利用を監査ログに残す。** **そのうえで「短時間に大量の値を復号する」利用を異常として検知できるかを確認する。** **あわせて、ハードコードされた認証バイパス用のトークン（本件の JWT）が 自組織のコードに無いかを探す** —— **開発や試験のために入れた迂回路は、git 履歴に残り続ける。**
  • 開発端末の AI 支援ツールの設定（接続されているツールの一覧）を資産管理の対象にする
    **Azazel は AI コーディング支援のツール接続（MCP）に リバースシェルの受け口を「呼び出せる道具」として登録し、 侵害端末へのコマンド送信に使っていた**（CloudSEK の確認）。 **本件では攻撃者が自分の道具として使っているが、 同じ仕組みは被害側の端末に仕掛けることもできる**（本記録の評価）。 **厄介なのは検知の形である** —— **AI 支援ツールと MCP サーバの間の通信は開発端末では正当なものとして存在し、 本件のようにループバック（`127.0.0.1:35367`）を経由する形は ネットワーク監視にそもそも出ない。** **見るべきものは端末の構成情報である。**
    取るべき行動 **開発端末の AI 支援ツールの設定ファイル （接続されている MCP サーバの一覧）を収集し、 インストール済みソフトウェアの一覧と同じ重さで台帳に載せる。** **承認されていない接続先が増えたことを検出できる状態にする。** **ネットワーク側の監視だけでは見えないことを、 監視設計の前提として明記しておく。**
  • Kubernetes の監査ログで「secret の一括列挙」を検知できる状態にする
    **経路Bの終盤で Azazel は kubeconfig・SSH 秘密鍵・資格情報を含むコンテナ設定を収穫している**（事実）。 **kubeconfig を取られた後の操作は、正規の API 呼び出しとして成功する** （本記録の評価）—— **失敗ログにも異常ログにも残らない。** **残るのは「誰が何をしたか」の監査記録だけである。** **とくに secret の一括列挙は、通常の運用では稀であり、 攻撃の段階としては特徴的である。**
    取るべき行動 **Kubernetes の監査ログを有効にし、 `secrets` に対する `list` / `get` を利用主体ごとに記録する。** **「普段 secret を列挙しない利用主体が列挙した」を警報条件にする。** **あわせて、kubeconfig に埋め込む資格情報の有効期限を短くし、 取られても使える時間を縮める。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 自前または SaaS の GitLab（あるいは同種の CI/CD 基盤）を運用し、パイプラインに本番環境の資格情報を渡しているCloudSEK は確認された全被害に到達したのが侵害された CI/CD の秘密情報だったとしており、24社超・6か国・業種を問わず共通していたのはこの経路だけである
認証・認可□ CI/CD に渡す資格情報が長期の静的トークンであり、到達できる範囲（環境・テナント・データベース）を一覧できていない報告では1本の CI/CD トークンの露出が SaaS 基盤の150を超えるデータベースに届いており、CI に渡す権限は境界を越えるように設計されていることが実例で示された
データの保持□ 過去に git へコミットした資格情報があり、現在のファイルから削除しただけで対象サービス側での失効を行っていないAzazel は現在の版からは削除済みだが過去のコミットに残っていた秘密情報を掘り出していた。履歴の複製には消す操作が届かないため失効以外に対処がない
システム構成□ AI の推論エンドポイントを外部に公開しており、認証を要しない、または外部から渡された URL を取得する実装がある経路Bの起点は認証不要の AI 医療画像 API における検証されない URL 取得（SSRF）であり、そこから数週間の多段侵害と6TB 超の持ち出しに至った
運用・監視□ オブジェクトストレージ・データベースの読み出し量について平常時の基準値を持っておらず、大量の継続的な持ち出しを異常として検出できない経路Bでは6TB 超が数週間かけて出て行き発見時もまだ転送中だったが、気づいたのは被害組織ではなく加害者側のサーバを見つけた第三者である
運用・監視□ リークサイトの監視を RaaS の群の銘柄単位で行っており、自組織名・ドメイン単位の監視になっていない本件はアフィリエイトが運営の管理外で自前のリークサイト LEAKNED を運営した例で、群の銘柄を追う監視では被害が現れない
運用・監視□ 開発端末の AI 支援ツールに接続されているツール（MCP サーバ）の一覧を資産管理の対象にしていない本件では AI 支援ツールのツール接続にリバースシェルが登録され C2 として使われた。ループバック経由のためネットワーク監視には現れず、端末の構成情報でしか見えない
委託・第三者部品□ 自社が SaaS を提供しており、1本の資格情報が複数テナントのデータベースに到達できる構成になっている報告の SaaS 基盤の事例では150超のデータベースに到達されており、その先の利用組織への波及は公表されていないが構造としては供給網の事案と同じである
