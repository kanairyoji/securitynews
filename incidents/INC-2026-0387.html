INC-2026-0387Copilot CLIが暗号化指示で秘密を送信

Adversa AI は2026年10月6日、**GitHub Copilot CLI** が**暗号文として埋め込まれた指示**を 自ら復号して実行し、**開発者のローカルファイル（`.env.prod` 等）の中身を 攻撃者のサーバへ送信する**攻撃連鎖を公表した。 手口は**Cryptographic Context Injection（CCI・暗号による文脈注入）**—— **平文で同じ指示を渡すとプロンプト注入として拒否されるが、 暗号文＋鍵＋「復号せよ」の指示として渡すと、 エージェントは復号を「コーディングの作業」として自分の実行環境で処理し、 復号後の指示を自分のものとして信用する**。 **成立はモデル依存で、Microsoft の `mai-code-1.1-flash` では試行の50%で全連鎖が成立、 OpenAI GPT-5.6 の2モデルは一貫して拒否した**。 **モデル選択が「自動」の利用者は、どちらが使われたか選べも見えもしない。** Adversa AI は2026年9月17日に GitHub の報奨金制度へ報告したが、 **GitHub は内容を検証したうえで「製品の脆弱性ではない」と判断した**

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年10月6日（Adversa AI の公表） 最終更新: 2026年10月7日

Adversa AI の研究者 Rony Utevsky は2026年10月6日、GitHub Copilot CLI に対する攻撃連鎖を公表した。1つのウェブページを取得させるだけで、エージェントが開発者のローカルファイルを読み、その中身を攻撃者のサーバへ送信する。 Adversa AI は所要を「28秒」としている。

手口は Cryptographic Context Injection（CCI・暗号による文脈注入）である。 Adversa AI が2026年8月に xAI の Grok に対して実証した手法と同じもので、同社はこれを「Grok で2か月前に特定したのと同じ脆弱性」と位置づけている。

仕組みの核心は、検査の時点と意味が生まれる時点がずれることである。 Utevsky の説明（原文英語）—— 「静的なガードレールは文字列を読むが、文字列を実行しない。CCI は悪意ある指示を強固な暗号文として送り込み、鍵の材料と『復号せよ』という指示を添えて、エージェント自身のコード実行環境でその復号を実行させる」。

base64 や換字暗号と違う点は、モデルが学習で復号方法を覚えていないことである（The Register の記述）—— 取り込んだ文字列を読む分類器は、暗号文の中身を見ることができない。

攻撃連鎖はこうである。

  1. 利用者が Copilot CLI に特定の URL の取得を依頼する（自律動作モード）
  2. ページには暗号文・Python を使った復号の指示・2つの復号鍵の候補がある
  3. 1つ目の鍵は「ひな型」で、埋めるには手元のファイルを読む必要がある（例: 利用者の .env.prod）——エージェントは読んで鍵文字列に組み込む
  4. そのひな型の鍵では復号が失敗する（設計どおり）
  5. 2つ目の本物の鍵で復号が成功し、復号後の指示が現れる
  6. 指示は「追加の文脈のために別の URL を取得せよ」と言う
  7. その URL には、すでに収穫されたファイルの中身が引数として載っている—— エージェントが取得を実行した時点で、秘密情報が攻撃者の手元に届く

成立はモデルに依存する。 Microsoft の mai-code-1.1-flash は試行の50%で全連鎖を実行し、OpenAI GPT-5.6 の2モデルは同一のペイロードを一貫して拒否した。

Utevsky はこれを「モデルの宝くじ（model lottery）」と呼ぶ（原文英語）—— 「我々が試験した有料アカウントでは、脆弱なモデルは既定ではなく手で選ぶ必要があった。しかしモデル選択を自動のままにしているアカウントでは、ルータが一部のセッションで脆弱なモデルを割り当て、別のセッションでは安全なものを割り当てた。利用者は既定から何も動かしていない。利用者はどちらが選ばれたかを選べもしないし、見えもしない」。

Adversa AI は2026年9月17日に GitHub の報奨金制度を通じて報告した。 GitHub の選別チームは内容を検証したうえで、「製品の脆弱性ではない」として報奨の対象外とした。 GitHub は The Register に対し「利用者が意図的に Copilot CLI に攻撃者が管理するコンテンツや信頼できないコンテンツを取得するよう指示し、その動作を起こしたいことを確認する必要がある。したがって製品の脆弱性ではない」と述べている（原文英語）。Adversa AI はこの判断に同意せず、2026年10月1日時点で連鎖が記述どおり再現することを確認したとしている。

base64 や単純な換字暗号との違いが重要である（The Register の記述）—— それらはモデルが学習の過程で復号方法を覚えているため、取り込み時点の分類器も中身を読める。 強固な暗号はそうではない。鍵がなければ誰も中身を知らない。

そして復号後の平文は、エージェントにとって「外部入力」ではない。 自分の実行環境で生成した結果である（本記録の整理）。外部入力に対する検査をいくら強めても、ここは通る。

帰結は明確である（本記録の評価）—— 入力の検査を強化する方向の対策では、この構造は閉じない。 必要なのは、取り込んだコンテンツを扱う文脈からファイル読み取りとネットワーク送信の能力を外すこと（Adversa AI の提言の4つ目）である。 これは利用者側では実装できず、製品の作り方に属する。

鍵を「ひな型」にすることで、ファイルを読む行為が鍵の構築作業になる原因・手口

連鎖のもう1つの仕掛けは、2つの鍵である（Adversa AI の記述に基づく事実）。

  1. 1つ目の鍵は「ひな型」で、埋めるには手元のファイルを読む必要がある（例: 利用者の .env.prod）
  2. エージェントはファイルを読み、中身を鍵文字列に組み込む
  3. そのひな型の鍵では復号が失敗する（設計どおり）
  4. 2つ目の本物の鍵で復号が成功する

なぜこの迂回が必要なのかを考えると、仕掛けの巧みさが見える（本記録の評価）。

  • 「.env の中身を攻撃者に送れ」という指示は拒否されうる。
  • しかし「この鍵のひな型を、ローカルの値で埋めよ」であれば、ファイルの読み取りは目的ではなく手段になる。
  • さらに1回目の復号が失敗することで、エージェントには「鍵が違ったようだ、次を試そう」という自然な筋道が与えられる。

そして持ち出しも、独立した口実を持っている。 復号後の指示は「追加の文脈のために別の URL を取得せよ」と言う。 その URL の引数に、すでに読んだファイルの中身が載っている（Adversa AI の記述）。

つまり3つの操作が、それぞれ別の口実で正当化されている（本記録の整理）。

操作 与えられた口実 単体で見たときの不審さ
外部 URL の取得 利用者が指示した 無い
.env.prod の読み取り 鍵のひな型を埋めるため 低い（コーディング支援は設定を読む）
外部への送信 追加の文脈を取得するため 低い（資料の取得と同じ形）

どの段階も単体では止まらない。 Adversa AI の提言の2つ目が「1つのペイロードではなく、並びに対して警報を出せ」である理由がここにある。

防御側の実務としては、「外部取得 → 資格情報系ファイルの読み取り → 新規の外部宛先への送信」という順序を条件にすることになる（本記録の評価）。ただしこれには、道具呼び出しの記録が引数まで解決された形で残っていることが前提になる（Adversa AI の提言の1つ目）。

成立率が50%と0%に分かれ、どちらで動くかを利用者は選べも見えもしない被害規模・影響範囲

同一のペイロードに対する結果である。 製品側の防御の差ではなく、モデルの違いだけで分かれている（本記録の整理）。

Utevsky はこれを「モデルの宝くじ」と呼ぶ（原文英語）—— 「我々が試験した有料アカウントでは、脆弱なモデルは既定ではなく手で選ぶ必要があった。しかしモデル選択を自動のままにしているアカウントでは、ルータが一部のセッションで脆弱なモデルを割り当て、別のセッションでは安全なものを割り当てた。利用者は既定から何も動かしていない。利用者はどちらが選ばれたかを選べもしないし、見えもしない」。

ここから、実務上の帰結が3つ出る（本記録の評価）。

① 「50%だから半分安全」ではない。 2回に1回通る攻撃は、1回では止まらない。 利用者は同じ依頼を繰り返すことがあり、攻撃者は何人にも同じページを仕掛けられる。 「試せば通る」と読むべきである。

② 「危険なモデルを避ける」という対策が取れない。 モデル選択を自動にしている利用者は振り分けを制御できず、どのモデルで動いたかを事後にも確認できない（Adversa AI の記述）。対策を立てる前提の情報が得られない。

③ 「GPT-5.6 なら安全」という結論は採れない。 なぜ拒否できたのかの技術的な理由が公表されていない（本記録の指摘。unknowns 参照）。理由が分からなければ、他のモデルへの一般化もできず、モデルの更新で挙動が変わる可能性も排除できない。

本記録の整理では、これはモデルの評価の問題ではなく、製品の情報提供の問題である。 成立率が 50% と 0% に分かれる要素について、利用者が「いま自分はどちらか」を知る手段が無い。 調達の判断にも、インシデント対応の初動にも使えない状態である。

「利用者が指示したのだから製品の問題ではない」という線引きが争点である未確定事項

Adversa AI はこれに同意せず、連鎖が現在も記述どおり動作すると述べている。

本記録はどちらが正しいかを判定しない（本記録の立場）。判定できる材料が無く、また「脆弱性の定義」の問題であって技術的事実の問題ではない。

記録すべきは、防御側にとっての含意である（本記録の評価）。

① 修正は期待できない。 「脆弱性ではない」と判断された以上、修正の予定も影響を受ける版の公表も無い。 対策は利用者側の運用で持つしかない。

② GitHub の論理は、自律動作モードの前提と緊張関係にある。 利用者が指示したのは「この URL を取得せよ」である。 .env.prod を読んで外部へ送ることは指示していない。 自律動作モードは「指示した後の細部は委ねる」ことを前提とした機能であり、委ねた範囲の中で何が起きてもよいとするなら、委ねること自体の安全性が問われることになる（本記録の評価）。

③ この線引きは Copilot CLI だけの問題ではない。 The Register は、自律動作モードが「他のコーディング支援ツール（Anthropic の Claude 等）では既定だが、Copilot CLI では任意設定のままである」と記述している。 既定で自律動作するツールでは、「利用者が確認した」という条件はさらに弱くなる（本記録の評価）。

実務の結論（本記録の評価）—— ベンダーの判断を待たず、自分の運用で閉じる必要がある。 具体的には、取り込みと実行の文脈の分離、道具呼び出しの記録、新規の外部宛先への確認要求である。 これらは本件の有無にかかわらず、AI 支援ツールを業務に入れる際の前提条件として扱うべきものである。

28秒で完了する。人が見て止める設計は成り立たない評価・解釈

Adversa AI の実測は「28秒」である（事実）。同社は「確認なし」かつ「ファイルが出ていったことを示す目に見える表示もない」としている。

この値が対策の設計を規定する（本記録の評価）。

  • 自律動作モードでは、利用者が URL を渡した後の処理は委ねられる。
  • 28秒のあいだに、ファイルの読み取りと外部への送信が完了する。
  • 「画面を見ていて不審に思ったら中断する」という防御は成り立たない。

したがって、人の判断を挟むなら「事後」ではなく「送信の前」である（本記録の評価）。Adversa AI の提言の3つ目がこれに当たる —— 「新しいネットワーク宛先と、作業範囲外への書き込みには確認を求めよ」。

本件の連鎖は、最後の送信が止まれば完結しない。 ファイルを読まれても、送信されなければ外には出ない。 宛先が新規かどうかで絞れば、確認の頻度は抑えられる（本記録の評価）—— 開発作業で頻繁に到達する宛先は限られている。

一方で、Adversa AI の提言の1つ目「すべての道具呼び出しとその引数を、完全に解決した形でセッションごとに記録せよ」は、事後の調査のためのものである。 「完全に解決した形で」が肝心である（本記録の整理）—— 引数が変数や参照のままでは、何を読み、どこへ送ったかが記録に残らない。

現状、多くの組織はこの記録を取っていない（本記録の評価）。つまり本件のような連鎖が起きても、起きたこと自体が分からない。 未確定事項に「実際に被害が生じた事例の有無」を「探索したが発見できなかった」として置いたのは、この構造のためである —— 報告が無いのは、被害が無いことを意味しない。

**本記録の評価** —— **この段階は道具呼び出しの記録に必ず現れる。** **「作業中のプロジェクトとは関係のないファイル（`.env` 系）を 読んだ」という事実である。** **Adversa AI の提言の1つは 「すべての道具呼び出しとその引数を、完全に解決した形で セッションごとに記録せよ」（原文英語）である。** **「完全に解決した形で」が肝心である** —— **引数が変数や参照のままでは、何を読んだかが記録に残らない。** **ただし、1回のファイル読み取りだけでは判断できない** —— **コーディング支援が `.env` を読むことは正当な作業でもありうる。** **意味を持つのは次の段階との組み合わせである。**
侵入を防げた作業範囲（ワークスペース）の外のファイル読み取りに 利用者の確認を要求する　**Adversa AI の提言に基づく** （原文英語: "Confirm new network destinations and writes outside the workspace"）。 **本記録の評価** —— **本件で読まれたのは `.env.prod` であり、 プロジェクト内にあることが多い。** **したがって「ワークスペース外」の条件だけでは捕まらない** （本記録の指摘）。 **必要なのは「資格情報が入りうるファイル（`.env*`・ 鍵ファイル・認証設定）の読み取り」を種別で扱うことである。**
影響を限定できた開発端末の `.env` 系ファイルに本番環境の資格情報を置かない （鍵管理サービス経由で取得する構成に変える）　**本記録の評価による。** **本件の被害は「読まれたファイルに何が入っていたか」で決まる。** **読み取りそのものを防げなくても、 そこに本番の資格情報が無ければ損害は小さい。** **これは影響範囲の限定であり、攻撃の防止ではない。** **ただし AI 支援ツールの利用が広がる状況では、 「端末に平文の資格情報を置かない」ことの価値が上がっている** （本記録の評価）。
実行現実的な検知機会なし
**本記録の評価** —— **この段階を外から検知する現実的な手立てが無い。** **理由** —— **①取り込み時点の検査は暗号文を見るため、意味を判定できない。** **②復号はエージェントの実行環境の中で完結する。** **③復号後の平文は、エージェントにとって「自分が生成した出力」であり、 外部入力としての検査を受けない。** **Adversa AI の表現がこの構造を言い当てている** —— **「静的なガードレールは文字列を読むが、文字列を実行しない」。** **検査を強化しても、検査の対象が暗号文である限り通る。** **ベンダー側が「道具の出力と指示の経路を分離しているか」が 分かれ目になる**（Adversa AI の提言の5つ目）。
侵入を防げた取り込んだコンテンツ由来の文字列を、指示の経路とは別の経路で扱う （道具の出力を指示として解釈しない構造にする）　**Adversa AI の提言に基づく** （原文英語: "Ask vendors whether tool output is separated from the instruction channel"）。 **本記録の評価** —— **これは利用者側では実装できない。** **製品の作り方に属する対策であり、 利用者ができるのは「分離しているかをベンダーに確認する」ことだけである。** **したがって調達・利用の判断の基準として使う。**
検知できた単一の道具呼び出しではなく、呼び出しの並び（外部取得 → 資格情報系ファイルの読み取り → 新規の外部宛先への送信）を 条件として警報を出す　**Adversa AI の提言に基づく** （原文英語: "Alert on the sequence, not one payload"）。 **本記録の評価** —— **どの段階も単体では正当な作業に見える。** **外部の資料を読む・設定ファイルを読む・API を呼ぶ、 いずれもコーディング支援の通常の仕事である。** **組み合わせと順序だけが異常を示す。** **これは実装可能な対策だが、 道具呼び出しの記録が揃っていることが前提になる。**
持ち出し機会はあったが検知できず
**本記録の評価** —— **この段階は検知できる。** **「それまで通信したことのない宛先への送信」であり、 **しかも引数に長い文字列（ファイルの中身）が載っている。** **ネットワーク側でも、道具呼び出しの記録側でも現れる。** **にもかかわらず「機会はあったが検知できなかった」としたのは、 28秒で完了するため人が介入する余地が無く、 自動の警報が無ければ事後に気づくしかないためである。** **Adversa AI は提言に 「新しいネットワーク宛先と、作業範囲外への書き込みには 確認を求めよ」を挙げている** —— **検知ではなく、送信前の確認を入れるのが本筋である。**
侵入を防げたエージェントが新規のネットワーク宛先へ送信する前に 利用者の確認を要求する　**Adversa AI の提言に基づく。** **本記録の評価** —— **これが最も実効的な対策である。** **本件の連鎖は、最後の送信が止まれば完結しない。** **ファイルを読まれても、送信されなければ外には出ない。** **ただし確認要求を増やすと自律動作モードの利点が減る** —— **「宛先が新規かどうか」で絞れば、頻度は抑えられる**（本記録の評価）。
侵入を防げた開発端末からの外向き通信を、許可した宛先に限定する　**本記録の評価による。** **攻撃者のエンドポイントは、許可一覧には無い。** **ただし開発作業では多様な外部資源への到達が必要であり、 許可一覧の運用は現実には難しい**（本記録の評価）。 **実務的には「資格情報を扱う作業を行う端末」に限って 適用するなど、範囲を絞ることになる。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • AI コーディング支援の「自律動作」を、権限委譲の決定として扱う
    **本件の成立条件は、エージェントが利用者の確認なしに ファイルを読み、外部へ送信できることである**（本記録の整理）。 **GitHub の判断は「利用者が指示したのだから製品の問題ではない」だが、 利用者が指示したのは URL の取得だけである。** **`.env.prod` を読んで外部へ送ることは指示していない。** **つまり自律動作モードを有効にすることは、 「どこまで委ねるか」を決める権限委譲の意思決定である**（本記録の評価）。 **ソフトウェアの設定ではなく、権限の付与として扱う必要がある。**
    取るべき行動 **AI コーディング支援ツールの自律動作モードの利用を、 組織として許可制にする。** **許可の条件に「読み取りを許す範囲」「送信を許す宛先」 「確認を要求する操作」を明記する。** **既定で自律動作するツール（Adversa AI によれば一部のツールは既定）については、 導入時に既定を変更する手順を定める。** **判断の記録を残す** —— **誰が、どの範囲の委譲を、どういう理由で許可したか。**
  • ベンダーが「脆弱性ではない」と判断した問題を、自組織のリスクとして持つ
    **GitHub は内容を検証したうえで、脆弱性としては扱わないと判断した** （2026年10月1日）。 **Adversa AI は同日時点で連鎖が記述どおり動作することを確認している。** **この構図から出る帰結は1つである** —— **修正は期待できないので、対策は利用者側の運用で持つしかない** （本記録の評価）。 **脆弱性管理の工程は「CVE が出る・修正が出る・適用する」を 前提に組まれていることが多い。** **本件はそのどれも発生しない。**
    取るべき行動 **脆弱性管理の台帳に「ベンダーが脆弱性と認めていないが 自組織では対策が必要な事項」の区分を作る。** **本件を最初の記録として登録し、 対策（自律動作モードの制限・道具呼び出しの記録・ 外部宛先への確認要求）と担当・期限を紐づける。** **CVE 番号で起票する運用のままだと、この種の事項は台帳に載らない** （本記録の指摘）。
  • 「どのモデルで動いたか分からない」ことを、調達と委託管理の論点にする
    **同一のペイロードに対して、成立率は `mai-code-1.1-flash` で50%、GPT-5.6 の2モデルで0% だった**（事実）。 **にもかかわらず、モデル選択を自動にしている利用者は 振り分けを制御できず、どのモデルで動いたかを事後にも確認できない** （Adversa AI の記述）。 **これは安全性の差が存在するのに、 自分がどちら側にいるかを知れないという状態である**（本記録の評価）。 **インシデント対応の初動でも、調達の比較でも使えない。**
    取るべき行動 **AI 支援ツールの調達・利用の確認項目に次を加える**—— ①**セッションごとに使われたモデルを記録・確認できるか**、 ②**モデルを固定できるか**、 ③**取り込んだコンテンツの出力と、指示の経路が分離されているか** （Adversa AI の提言の5つ目）。 **①②が満たせない場合は、その前提で運用の制限を強める** （自律動作モードを使わない等）。
  • 開発端末に本番環境の資格情報を平文で置かない方針を、AI 支援ツールの普及を理由に前進させる
    **本件で読まれた例として挙げられたのは `.env.prod` である**（事実）。 **開発端末の `.env` 系ファイルには、本番環境のデータベース資格情報・ API キー・署名鍵が入っていることが多い**（本記録の一般的理解）。 **本件の被害は「読まれたファイルに何が入っていたか」で決まる** （本記録の評価）—— **読み取りそのものを防げなくても、そこに本番の資格情報が無ければ 損害は小さい。** **「端末に平文の資格情報を置かない」は以前から言われてきたが、 AI 支援ツールがファイルを自律的に読む状況では、 想定すべき読み取り主体が増えている。**
    取るべき行動 **開発端末の `.env` 系ファイル・鍵ファイルを棚卸しし、 本番環境の資格情報が含まれるものを洗い出す。** **鍵管理サービスから実行時に取得する構成への移行計画に 期限と責任者を付ける。** **移行が難しいものについては、 その端末で AI 支援ツールの自律動作モードを使わない運用にする。**
セキュリティ技術者への示唆
  • 道具呼び出しを、引数まで解決した形でセッションごとに記録する
    **Adversa AI の提言の1つ目** （原文英語: "Capture a per-session trace of every tool call with its arguments fully resolved"）。 **「完全に解決した形で」が肝心である**（本記録の整理）—— **引数が変数や参照のままでは、何を読み、どこへ送ったかが記録に残らない。** **本件の連鎖は28秒で完了し、 ファイルが出ていったことを示す目に見える表示も無い。** **記録が無ければ、起きたこと自体が分からない**（本記録の評価）—— **本記録が「実際に被害が生じた事例の有無」を 「探索したが発見できなかった」として空白に置いたのは、この構造のためである。**
    取るべき行動 **AI 支援ツールの道具呼び出しの記録を有効にし、 読み取ったファイルのパスと、送信した宛先の URL を 引数を展開した形で残す。** **記録をツールのローカルだけに置かず、 端末のログ収集の対象に入れる**（事後の調査で参照できる場所に置く）。 **自組織のツールで記録が取れるかを、まず確認する** —— **取れないなら、それが現在の可視性の限界である。**
  • 1つの操作ではなく、操作の並びを警報の条件にする
    **Adversa AI の提言の2つ目** （原文英語: "Alert on the sequence, not one payload"）。 **本件では3つの操作が、それぞれ別の口実で正当化されている** （本記録の整理）—— **外部 URL の取得は利用者が指示したもの、 `.env.prod` の読み取りは鍵のひな型を埋めるため、 外部への送信は追加の文脈を取得するため。** **どの操作も単体ではコーディング支援の通常の仕事に見える。** **組み合わせと順序だけが異常を示す。**
    取るべき行動 **「外部コンテンツの取得 → 資格情報が入りうるファイル （`.env*`・鍵ファイル・認証設定）の読み取り → 新規の外部宛先への送信」 という並びを警報条件として実装する。** **時間窓を短く取る**（本件は28秒で完了する）。 **実装の前提として、道具呼び出しの記録が揃っていることを確認する。**
  • エージェントが新規の外部宛先へ送信する前に、確認を要求する
    **Adversa AI の提言の3つ目** （原文英語: "Confirm new network destinations and writes outside the workspace"）。 **本記録の評価では、これが最も実効的な対策である** —— **本件の連鎖は、最後の送信が止まれば完結しない。** **ファイルを読まれても、送信されなければ外には出ない。** **確認要求を増やすと自律動作の利点が減るが、 「宛先が新規かどうか」で絞れば頻度は抑えられる**（本記録の評価）—— **開発作業で頻繁に到達する宛先は限られている。** **なお、Adversa AI の「作業範囲外への書き込み」という条件だけでは 本件は捕まらない** ——**読まれた `.env.prod` は プロジェクト内にあることが多い**（本記録の指摘）。
    取るべき行動 **AI 支援ツールの設定で、新規のネットワーク宛先への送信に 確認を要求する設定があれば有効にする。** **無い場合は、資格情報を扱う作業を行う端末に限って 外向き通信を許可した宛先に絞る。** **ファイル読み取りの確認条件は「作業範囲の外」ではなく 「資格情報が入りうるファイルの種別」で設定する。**
  • 信頼できないコンテンツを、道具も資格情報も持たない文脈で扱う
    **Adversa AI の提言の4つ目** （原文英語: "Quarantine untrusted content in a context with no tools and no credentials"）。 **本記録の評価では、これが唯一の根本的な対策である** —— **暗号文であれ平文であれ、取り込んだコンテンツに指示が含まれうる前提で、 そのコンテンツを扱う文脈からファイル読み取りと ネットワーク送信の能力を外す。** **入力の検査を強化する方向では閉じない** —— **検査の対象が暗号文である限り通り、 復号後の平文は「自分の出力」として検査を受けない。**
    取るべき行動 **外部コンテンツの取得（ウェブページ・課題票・ドキュメント）を、 ファイル読み取りと外部送信の権限を持たない別のセッション・ 別のプロセスで行う運用に分ける。** **ツールがこの分離を提供していない場合は、 「取得した内容を人が確認してから作業セッションに渡す」形にする。** **ベンダーに対して、道具の出力と指示の経路が分離されているかを確認する** （Adversa AI の提言の5つ目）——**分離は製品の作り方に属し、 利用者側では実装できない。**
  • 暗号化・符号化された入力を「安全」と扱わない。意味は復号後に生まれる
    **本件の手口は、2026年8月に xAI の Grok に対して実証されたものと同じである** （The Register の記述。本記録はその先行事案を一次資料で検証していない）。 **つまり構造に属する問題であり、Copilot CLI 固有ではない可能性が高い** （本記録の評価。ただし2製品での成立が確認されているだけである）。 **base64 や換字暗号ならモデルが学習で復号方法を知っているため 取り込み時点の検査も中身を読めるが、強固な暗号はそうではない** （The Register の記述）。 **自組織で AI エージェントを作る側にも同じ論点がある**（本記録の評価）。
    取るべき行動 **自組織で AI エージェントを実装している場合、 取り込んだコンテンツに対する検査を「取り込み時点」だけで終わらせない。** **エージェントが自分の実行環境で生成した文字列 （復号結果・デコード結果・外部コマンドの出力）を 指示として扱わない構造にする。** **具体的には、道具の出力を指示の経路とは別のデータとして保持し、 指示として解釈する対象を利用者の入力に限定する。**
