INC-2026-0388Unsloth Studioがモデル閲覧だけでRCE

Pillar Security は、LLM の微調整・量子化に使われる OSS ライブラリ **Unsloth** の ブラウザ操作画面 **Unsloth Studio** に任意コード実行の欠陥があったことを 2026年9月29日に公表した。 **Studio がモデルの情報を調べる処理で `trust_remote_code=True` を既定にしていた**ため、 **利用者がモデルを選んだだけで**——**モデルの重みのダウンロードも、 学習や推論の開始も、実行許可の確認も経ずに**—— **攻撃者が Hugging Face のリポジトリに置いた Python コードが Studio の実行側で動く**。 仕掛けは `config.json` の `auto_map` にリポジトリ内の Python ファイルを指すこと。 **影響は Unsloth 2026.6.9 より前の版で Studio を動かしていた利用者。** **修正版 2026.6.9 では、Studio から Hugging Face のモデルを直接読み込む機能そのものを 取り除き、ローカルのモデルファイルについても同等の経路を閉じた。** **CVE は付与されていない**（Studio がベータであることを理由に Unsloth 側が勧告を出さなかった）。 Pillar Security は、実際に悪用された痕跡も、 この手口のために作られた悪性のモデルリポジトリも発見していないとしている

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備設定不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年9月29日（Pillar Security の公表） 最終更新: 2026年10月7日

Pillar Security は2026年9月29日、Unsloth Studio に任意コード実行の欠陥があったことを公表した。Unsloth は LLM の微調整（ファインチューニング）と量子化に使われるOSS ライブラリで、Studio はそのブラウザ操作画面である。

成立の条件が極端に軽いことが本件の性格を決める。 Pillar Security の記述（原文英語の要旨）——「微調整の実行も、推論の呼び出しも、モデルのダウンロードの明示的な確認も要らなかった。Hugging Face のリポジトリの設定メタデータを調べるという行為だけで、Studio の処理側を動かしている計算機でコードの実行を引き起こすのに足りた」。

仕組みはこうである。

  1. 攻撃者が Hugging Face に、独自の Python コードを含むモデルリポジトリを作る
  2. config.json の auto_map に、そのリポジトリ内の Python ファイルを指す（例: "auto_map": { "AutoConfig": "configuration.UnslothPocConfig" }）
  3. 利用者が Studio でそのモデルを選ぶ
  4. Studio の処理側が load_model_config() でモデル情報を読む
  5. trust_remote_code=True が既定のため、Transformers のAutoConfig.from_pretrained() が参照先のモジュールを取得して取り込む
  6. 取り込み（import）の副作用として、攻撃者のコードが実行される

Pillar Security が特定した該当箇所はstudio/backend/utils/models/model_config.py の load_model_config() で、既定の引数として trust_remote_code=True が宣言されていた。 新しい Transformers を別プロセスで扱う経路でも、同じ設定が直接書かれていた（CSA の記述）。

研究者 Ariel Fogel の言葉（原文英語）—— 「コードはメタデータの確認以外の何物でもないところから動いた」、「モデルの config.json を読むだけで、この悪用を引き起こすのに足りた」。

時系列（CSA の整理による）—— 2026年6月上旬に非公開で開発側へ報告、6月16日までに確認、2026年6月中に修正版 2026.6.9 を公開、2026年9月29日に公開。

修正の仕方が設定の無効化ではなかった点も記録する価値がある（CSA の記述。原文英語の要旨）—— 「開発側は単にフラグを無効にするのではなく、モデルの読み込み経路そのものを作り直し、Studio が情報を調べる際に Hugging Face から任意のモデルを直接読み込まないようにし、さらにローカルに保存されたモデルファイルに同梱されたリモートコードも信用しないようにした」。

CVE は付与されていない。 Studio がベータの機能であることを理由に Unsloth 側が勧告を出さなかったためである（gbhackers の記述）。ただし CSA は「当該コードは既定の PyPI パッケージに入って配布されていた」と指摘している。

Pillar Security は、実際に悪用された痕跡も、この手口のために作られた悪性のモデルリポジトリも発見していないとしている（iThome が Dark Reading を引いて伝えた Ariel Fogel の説明）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は実証に基づく記録である** —— **Pillar Security が実際に攻撃経路を成立させ、 修正版で閉じたことまで確認している。** **ただし実際の被害事例ではない** —— **同社は実際に悪用された痕跡も、この手口のために作られた 悪性のモデルリポジトリも発見していないとしている。** **連鎖が短いことが本件の性格である**（本記録の整理）—— **攻撃者が用意するのは Hugging Face 上の1つのモデルリポジトリだけで、 利用者側に要るのは「Studio でそのモデルを選ぶ」という操作1つである。** **モデルの重みのダウンロード・推論の呼び出し・学習の開始・ リモートコードの実行許可の確認はいずれも不要。** **「情報を読むだけ」のはずの処理が、取り込み（import）の副作用として コードを動かす構造になっていた。**

  1. 1. 初期侵入[2] [4]
    **攻撃者が Hugging Face に、独自の Python コードを含む モデルリポジトリを作る。** **`config.json` の `auto_map` に、 そのリポジトリ内の Python ファイルを指す** （CSA が挙げた例: `"auto_map": { "AutoConfig": "configuration.UnslothPocConfig" }`）。 **リポジトリはモデルの重みを含む必要がない**（本記録の整理）—— **設定ファイルと Python ファイルだけで成立する。** **本記録の評価** —— **公開のモデルハブに置く形であるため、 攻撃者は特定の相手を狙う必要がない。** **名前を既存の人気モデルに似せる、 あるいは一覧に現れるようにしておけば、 選んだ利用者の側で勝手に動く。**
  2. 2. 実行[2] [3] [4]
    **利用者が Studio でそのモデルを選ぶ。** **Studio の処理側が `load_model_config()` でモデル情報を読む。** **この関数は `trust_remote_code=True` を既定の引数として宣言していた** （Pillar Security が特定した該当箇所は `studio/backend/utils/models/model_config.py`。 **新しい Transformers を別プロセスで扱う経路でも 同じ設定が直接書かれていた**）。 **`trust_remote_code=True` のとき、Transformers の `AutoConfig.from_pretrained()` は設定データを返す前に 参照先のモジュールを自動的にダウンロードして取り込む。** **取り込み（import）の副作用として、 そのモジュールに含まれるコードが実行される**（CSA の記述）。 **実行は Studio の処理側を動かしている計算機で、 その操作を行った利用者の権限で起きる。**
  3. 3. 影響（暗号化・破壊・改ざん）[2] [4]
    **攻撃者が用意した Python コードが、 Studio の処理側を動かしている計算機で実行される。** **実行される内容は攻撃者の任意である**（本記録の整理）—— **公表資料は「任意コード実行」としており、 具体的に何が可能かは列挙していない。** **実行主体は Studio を動かしている利用者の権限である** （CVE-2026-93348 の記載は「操作を行う利用者の権限で動作する」と 表現している。別の欠陥だが構造は同じ）。 **Pillar Security は、実際に悪用された痕跡も、 この手口のために作られた悪性のモデルリポジトリも 発見していないとしている。**

「情報を読むだけ」の処理が、取り込みの副作用でコードを動かしていた原因・手口

本件の核心は、2つの動作が同じ呼び出しに同居していたことである（本記録の整理）。

CSA の記述（原文英語の要旨）—— 「trust_remote_code=True が設定されているとき、Transformers の AutoConfig.from_pretrained() 関数は設定データを返す前に、参照されたモジュールを自動的にダウンロードして取り込み、取り込み（import）の副作用としてそのモジュールに含まれるコードを実行する」。

Python の import は、モジュールの中身を上から実行する。 「読み込む」という語感と、実際に起きることが違う（本記録の評価）。

Pillar Security が特定した該当箇所—— studio/backend/utils/models/model_config.py のload_model_config() が trust_remote_code=True を既定の引数として宣言していた。 さらに、新しい Transformers を別プロセスで扱う経路でも同じ設定が直接書かれていた（CSA の記述）。

設計の意図と実際の挙動のずれを並べる（本記録の整理）。

工程 意図 実際
モデルの一覧を見る 選択肢を表示する —
モデルを選ぶ 宣言的なメタデータを読む 参照先の Python を取得して実行する
重みをダウンロードする モデルを取得する （ここまで来ない）
学習・推論を開始する 計算する （ここまで来ない）

Ariel Fogel の言葉がこれを言い当てている（原文英語）—— 「コードはメタデータの確認以外の何物でもないところから動いた」、「モデルの config.json を読むだけで、この悪用を引き起こすのに足りた」。

攻撃者が用意するものも軽い（本記録の整理）—— config.json の auto_map に Python ファイルを指す記述を書き、そのファイルを同じリポジトリに置くだけである。 モデルの重みは不要。

CSA が挙げた具体例—— "auto_map": { "AutoConfig": "configuration.UnslothPocConfig" }。

「信用するかどうか」の判断が、道具の側で既に決まっていた評価・解釈

trust_remote_code という設定の名前が、本来の設計を表している（本記録の整理）。

iThome の記述（原文中国語の要旨を日本語に訳した）—— 「この設定は本来、モデルのリポジトリが提供するコードを信用するか否かを利用者が決めるべきものである。AI の道具が自ら有効にしてしまうと、利用者が明示的に当該コードを信用すると選んでいないにもかかわらず、モデルを処理する際に直接これらのコードが実行されうる」。

つまり「既定で False」であること自体が安全機構である（本記録の評価）。利用者が True にするとき、それは「このリポジトリの作者を信用する」という明示的な判断である。 道具がソースに True を書き込むと、その判断の機会が消える。

そして、これは1つの製品の不具合ではない。

CSA の整理（原文英語の要旨）—— 「本件は、AI の推論・学習のフレームワークがtrust_remote_code=True をソースに直接書き込んで利用者の意思を黙って上書きした、2026年の少なくとも4件の密接に関連する公表のうちの1つである」。挙げられているのは LMDeploy・vLLM・InstructLab（iThome が CSA の分析を引いて伝えている）。

同じ誤りが、独立に、複数のフレームワークで繰り返されている（事実）。

なぜ繰り返されるのかを本記録は推定する（本記録の評価。公表資料に根拠は無い）——

  • trust_remote_code=False のままでは、新しいアーキテクチャのモデルが読めない。 「動かない」という不具合として報告される。
  • 開発側から見ると、True にするのは「対応モデルを増やす」という機能の改善に見える。
  • 利用者から見ると、何も変わっていない。 設定を変えた覚えが無いので、変わったことに気づけない。

実務の結論（本記録の評価）—— 自組織が使っている AI の推論・学習フレームワークについて、trust_remote_code の既定値をソースで確認する。 確認は単純である ——ソースから語を検索し、既定が True になっている箇所を探すだけでよい。 これは1回で終わる作業ではなく、更新のたびに確認する対象である —— 既定値は版で変わりうる。

修正はフラグを倒すのではなく、読み込み経路を取り除くことだった再発防止

開発側の対処の仕方が、本件から学べることの1つである（本記録の評価）。

CSA の記述（原文英語の要旨）—— 「開発側は単にフラグを無効にするのではなく、モデルの読み込み経路そのものを作り直し、Studio が情報を調べる際に Hugging Face から任意のモデルを直接読み込まないようにし、さらにローカルに保存されたモデルファイルに同梱されたリモートコードも信用しないようにした」。

2つのことをしている（本記録の整理）。

① trust_remote_code を False に倒すだけで済ませなかった。 フラグを倒すと「対応モデルが減る」という不具合として再び報告され、いずれ戻される可能性がある（本記録の推定）。読み込み経路を取り除けば、戻すには設計の変更が必要になる。

② ローカルのモデルファイルについても同じ経路を閉じた。 これが重要である（本記録の評価）—— 「Hugging Face から取ってくるのが危ない」という理解だと、手元に落としたモデルファイルは安全に見える。 しかし config.json の auto_map は、ローカルのファイルにも同じように書ける。 どこから来たかではなく、「設定ファイルが指す Python を取り込むか」が問題だった。

一方で、修正には利便性の代償がある（本記録の指摘）。「Studio から Hugging Face のモデルを直接読み込む」機能が無くなった —— これは Studio の主要な使い勝手の1つだったとみられる。 開発側は、機能を残して安全にする道ではなく、機能を取り除く道を選んだ。 公表資料にこの判断の理由の説明は無い（本記録が確認）。

更新の推奨は3資料（CSA・iThome・gbhackers）が一致している —— 2026.6.9 以降への更新。 Pillar Security は 2026.6.9 で再試験し、攻撃経路が閉じたことを確認している（iThome の記述）。

CVE が無いため、脆弱性情報を自動で集める仕組みには載らない未確定事項

本件に CVE は付与されていない（事実）。

  • 依存関係の走査ツールが CVE 番号で判定している場合、2026.6.9 より前の Unsloth を使っていても警告が出ない。

**公表資料は述べていない。** **本記録の評価** —— **コードが実行された後の検知は、 実行された内容に依存するため一般には言えない。** **ただし本件に固有の点がある** —— **微調整・量子化の環境は、 多数のパッケージをダウンロードし、 大量のファイルを読み書きし、 GPU を長時間使う環境である。** **つまり「見慣れないプロセスが動き、 ネットワークに出て、ファイルを書く」ことが 平常の動作として常時起きている**（本記録の評価）。 **異常として浮かび上がらせるのが難しい環境である。**
影響を限定できたモデルを扱う計算機から、他の資産への到達を制限する （クラウドの認証情報・社内ネットワークへの経路を置かない）　**本記録の評価による。** **任意コードが動く前提に立つと、 対処は「動いた後に何に届くか」を縮めることになる。** **とくに学習環境にクラウドの資格情報が置かれている場合、 そこから先への波及が主要な損害になる** （本記録の評価。公表資料は言及していない）。
影響を限定できたモデルを扱う計算機の外向き通信を、 必要な宛先（モデルハブ・パッケージ配布元）のみに限定する　**本記録の評価による。** **ただしモデルハブとパッケージ配布元への到達は必要であり、 そこからの取得が攻撃の経路そのものである**（本記録の指摘）—— **宛先の限定では本件は止まらない。** **効くのは、実行後に攻撃者の基盤へ通信する段階である。**

対応の評価

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「ベータ」の機能も、既定のパッケージで配布されていれば本番の攻撃面である
    **Unsloth 側は Studio がベータであることを理由に 勧告を公表せず、CVE も付与されなかった**（gbhackers の記述）。 **一方 CSA は「当該コードは既定の PyPI パッケージに入って 配布されていた」と指摘している**（原文英語の要旨）。 **つまり「ベータ」という位置づけは開発側の自己申告であり、 配布の実態とは別である**（本記録の評価）。 **利用者側から見れば、パッケージを入れた時点で そのコードは自分の環境にある。**
    取るべき行動 **自組織が使う OSS について、 「ベータ／実験的」と位置づけられた機能が 既定のインストールに含まれるかを確認する。** **含まれる場合は、本番の攻撃面として扱う** （使っていなくても、コードは存在する）。 **ベンダーの位置づけを、自組織のリスク評価の根拠にしない。**
  • AI 関連 OSS の脆弱性管理を、CVE を起票単位にしない運用へ変える
    **本件に CVE は付与されていない**（事実）。 **帰結は3つある**（本記録の評価）—— **①脆弱性情報の自動収集（CVE・NVD を参照する仕組み）に載らない、 ②依存関係の走査ツールが CVE で判定していれば警告が出ない、 ③「更新すべきこと」を知る経路が研究者の公表と報道だけになる。** **同じプロジェクトの別の欠陥（CVE-2026-93348・CVSS 8.6）には CVE があり、成立の条件がより軽いほう（本件）に無い** （本記録が突き合わせて確認）。
    取るべき行動 **AI 関連のパッケージ（モデルの読み込み・推論・学習の フレームワーク）について、 CVE の有無によらず版の更新を定期的に行う運用を作る。** **具体的には、使用しているパッケージの一覧と現在の版を台帳に置き、 上流の新しい版が出たら更新を検討する工程を定める。** **脆弱性管理の台帳に「CVE が無い既知の問題」の区分を作り、 本件を登録する。**
  • モデルを扱う計算機を、他の資産から分離する判断を経営で行う
    **コードが動くのは Studio の処理側を動かしている計算機であり、 操作した利用者の権限で実行される**（本記録の整理）。 **微調整や量子化のための環境は GPU を備えた共有の学習環境で、 他の学習データや資格情報が同居していることが多い** （本記録の一般的理解。公表資料は環境の性質に言及していない）。 **さらにこの種の環境は、多数のパッケージの取得と 大量のファイル操作が平常の動作として常時起きているため、 異常を浮かび上がらせにくい**（本記録の評価）。 **「任意コードが動いたとして、そこから何に届くか」を 縮めておくことが、唯一効く備えになる。**
    取るべき行動 **モデルの取得・微調整・量子化を行う計算機について、 ①クラウドの認証情報を置かない、 ②社内ネットワークへの経路を持たせない、 ③他プロジェクトのデータを同居させない、 の3点を環境の設計要件として決める。** **GPU の調達コストを理由に共有環境へ集約する判断をするときは、 この分離とのトレードオフを明示して記録する。**
  • 利用者の判断を道具が上書きしていないかを、調達・更新の確認項目にする
    **`trust_remote_code` は本来、 「このリポジトリのコードを信用するか」を利用者が決める設定である** （iThome の記述）。 **道具がソースに `True` を書き込むと、その判断の機会が消える。** **CSA は、同じ誤りが2026年に LMDeploy・vLLM・InstructLab でも起きたと整理しており、 本件を含めて「少なくとも4件」としている。** **1つの製品の不具合ではなく、独立に繰り返されている型である** （本記録の評価）。
    取るべき行動 **AI 関連のフレームワークの調達・更新の確認項目に 「安全側の既定を、道具が利用者に代わって変更していないか」を加える。** **具体的には `trust_remote_code` を含む 「信用・実行の許可に関する設定」の既定値をソースで確認させる。** **更新のたびに確認する** ——**既定値は版で変わりうる。**
セキュリティ技術者への示唆
  • 使っているフレームワークの trust_remote_code の既定値をソースで確認する
    **本件の原因は、`load_model_config()` が `trust_remote_code=True` を既定の引数として宣言していたことである** （Pillar Security が特定した該当箇所は `studio/backend/utils/models/model_config.py`）。 **さらに、新しい Transformers を別プロセスで扱う経路でも 同じ設定が直接書かれていた**（CSA の記述）—— **1か所直せば済む形ではなかった。** **CSA は同種の問題が2026年に LMDeploy・vLLM・InstructLab でも起きたと整理している。** **つまり「この製品を直す」ではなく 「自分が使っているものを確認する」が対処になる**（本記録の評価）。
    取るべき行動 **自組織が使う AI の推論・学習フレームワークのソースから `trust_remote_code` を検索し、 既定が `True` になっている箇所を洗い出す。** **1か所ではなく全箇所を見る**（本件は通常の経路と 別プロセスの経路の2か所にあった）。 **見つかった場合は、その道具を使う環境を分離するか、 既定を変える修正を上流へ報告する。** **この確認を、パッケージの更新手順に組み込む。**
  • モデルを選ぶ前に config.json の auto_map を自分で確認する工程を置く
    **攻撃者が用意するのは、`config.json` の `auto_map` に リポジトリ内の Python ファイルを指す記述と、そのファイルだけである** （CSA が挙げた例: `"auto_map": { "AutoConfig": "configuration.UnslothPocConfig" }`）。 **モデルの重みは不要。** **`auto_map` を含むモデルは正当な用途でも存在するため、 「あること」自体は異常ではない**（本記録の評価）—— **新しいアーキテクチャのモデルは独自のコードを要する。** **したがって必要なのは「あるかないか」ではなく 「指されている Python を読んだか」である。**
    取るべき行動 **外部のモデルハブからモデルを取得する前に、 `config.json` を取得して `auto_map` の有無を確認する工程を置く。** **`auto_map` がある場合は、指されている Python ファイルを 読んでから使う**（読まずに使わない）。 **自動化する場合は、 「`auto_map` を含むモデルは人の確認を経てから一覧に載せる」 という形にする。** **組織として使うモデルを確認済みの一覧に限定するのが、 最も確実である**（修正版 2026.6.9 で開発側が取った方針もこれに近い）。
  • 「どこから来たか」ではなく「設定ファイルが何を指すか」で危険を判定する
    **修正版 2026.6.9 は、 Hugging Face からの直接読み込みを取り除いただけでなく、 ローカルに保存されたモデルファイルに同梱されたリモートコードも 信用しないようにしている**（CSA の記述）。 **これが重要である**（本記録の評価）—— **「外部のハブから取ってくるのが危ない」という理解だと、 手元に落としたモデルファイルは安全に見える。** **しかし `auto_map` はローカルのファイルにも同じように書ける。** **問題は出所ではなく、 「設定ファイルが指す Python を取り込むか」である。**
    取るべき行動 **社内のモデル保管場所（共有ストレージ・内部のレジストリ）に 置かれたモデルについても、`auto_map` の確認を行う。** **「社内にあるから確認済み」としない** —— **誰かが外部から持ち込んだものが、確認を経ずに置かれていることがある。** **モデルを社内に取り込む工程（ゲート）を1か所に決め、 そこで確認する。**
  • モデルを扱う環境では、平常の動作が異常の検知を難しくすることを前提に設計する
    **本件の実行は、利用者の側に何の表示も出さず、 モデルの重みのダウンロードも始まらない** （Pillar Security の記述）—— **待ち時間や通信量の変化という手がかりが無い。** **さらに微調整・量子化の環境は、 多数のパッケージをダウンロードし、 大量のファイルを読み書きし、GPU を長時間使う環境である** （本記録の評価）。 **「見慣れないプロセスが動き、ネットワークに出て、 ファイルを書く」ことが平常の動作として常時起きている。** **異常として浮かび上がらせるのが構造的に難しい。**
    取るべき行動 **モデルを扱う環境では、検知ではなく封じ込めに重心を置く**—— ①**この環境から到達できる先を列挙し、不要なものを外す** （クラウドの認証情報・社内ネットワークへの経路）、 ②**外向き通信の宛先をモデルハブとパッケージ配布元に絞る**、 ③**環境を使い捨てにする**（作業ごとに作り直し、 永続する状態を持たせない）。 **③は本件の実行そのものは止めないが、 永続化と横展開の余地を無くす。**
