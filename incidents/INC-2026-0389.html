米ニュージャージー地区連邦検事局は、同州に本社を置く産業系企業の元コア基盤エンジニア Daniel Rhyne（59歳・ミズーリ州カンザスシティ）に 32か月（2年8か月）の拘禁刑が言い渡されたと公表しました。量刑は 2026年9月28日、トレントンの連邦地裁でMichael A. Shipp 判事が下しています。

Rhyne が認めた罪状は2件です。「保護されたコンピュータに損害を与える脅迫に関する恐喝」と「保護されたコンピュータへの意図的な損害」（いずれも原文英語）。

手口の要点は、ランサムウェアが1行も使われていないことです。

  • 2023年11月8日から25日にかけて、管理者アカウントで権限なく社内ネットワークへ遠隔接続した
  • ドメインコントローラにスケジュールタスクを仕込み、管理者アカウントのパスワードをTheFr0zenCrew! に変更し、ドメイン管理者アカウント13件を削除、ドメインユーザー301件のパスワードを同じ文字列に変更した
  • ローカル管理者アカウント2件のパスワードを PsPasswd に変更してサーバ254台を、さらに別の管理者アカウント2件のパスワードを変更してワークステーション3,284台をアクセス不能にした（合計3,538台）
  • 数日にわたってサーバとワークステーションをランダムに停止させた
  • 11月25日午後4時頃、社内のネットワーク管理者たちがパスワードリセットの通知を受け取り始め、他の全てのドメイン管理者アカウントが削除されていることに気づいた
  • 同日、「Your Network Has Been Penetrated」（あなたのネットワークは侵入された）と題した恐喝メールを同僚に送信。サーバのバックアップも削除したので復旧は不可能だと主張し、20ビットコイン（当時約75万ドル）を支払わなければ、今後10日間、毎日40台のサーバをランダムに停止すると脅した

捜査では、犯行計画中の検索履歴も押さえられています。11月22日には隠した仮想マシン上の自分のアカウントから「ドメインユーザーのパスワードの変更方法」「ドメインアカウントの削除方法」「Windows のログの消去方法」を検索し、その約1週間前にはノート PC で「ローカル管理者パスワードを変更するコマンドライン」「リモートでローカル管理者パスワードを変更するコマンドライン」「cmd を使ってリモートでコンピュータをシャットダウンする方法」を検索していました（最後の検索語は原文で usign と綴りを誤っています）。

この事案の読みどころは、「外から入られること」を前提に組んだ防御が丸ごと迂回される点です。使われたのは管理者アカウントとスケジュールタスクという正規の機能だけで、マルウェアも脆弱性の悪用もありません。そして最初に壊されたのは「対応する側の手段」でした——ドメイン管理者アカウントが13件まとめて削除されたため、気づいた時点で管理者はドメインに管理者として入れません。検知が遅れたから被害が広がったのではなく、検知した瞬間に対応能力が無かったという形です。

最初に壊されたのは「対応する側の手段」だった——気づいた時点でドメイン管理者は全滅していた評価・解釈出典 [1] [3]

本記録がこの事案から最も学べると考えるのは、破壊の順序である。

公表された事実関係を時刻で並べると、こうなる。

  1. ドメイン管理者アカウント 13件が削除される
  2. ドメインユーザー 301件と管理者アカウントのパスワードが変更される
  3. 午後4時頃、ネットワーク管理者がパスワードリセットの通知で異常に気づく
  4. 気づいた直後に発見したのは、自分たちがもうドメイン管理者として入れないという事実だった

検察の表現は「他の全ての Victim-1 のドメイン管理者アカウントが削除され、それによって Victim-1 のコンピュータネットワークへのドメイン管理者アクセスが拒否された」（原文英語）である。

これは「検知が遅かった」事案ではない。 滞留は17日あったが、実際に破壊的な操作が始まってから気づくまでは数時間以内である。問題は、気づいた瞬間に対応する権限が無かったことにある。インシデント対応の手順は暗黙に「管理者権限が使える」ことを前提に書かれているが、本件ではその前提が最初に壊された。

評価として、ここが内部者による攻撃の固有の難しさである。外部からの侵入では、攻撃者は権限を奪うために時間と痕跡を使う。内部の基盤エンジニアは最初から最高権限を持っているため、偵察や権限昇格の段階が存在せず、検知のための「前兆」が生まれない。実際、本件で前兆として残っていたのは検索履歴（11月15日頃と11月22日）と隠した仮想マシンであり、どちらも通常のセキュリティ監視では見ない場所である。

もう1つ記録しておく。Rhyne が11月22日に検索していた項目には「Windows のログの消去方法」が含まれている。攻撃の実行手順と並んで、証跡の消去手順が調べられている——内部者は自組織の監査の仕組みを知っているため、監視が「どこを見ていないか」も知っているという前提で設計する必要がある（本記録の評価）。

段階検知の機会効きえた対策

**本記録の評価として、現実的な検知機会は無かったとみる。** 検索はいずれも**本人の端末と本人が立てた仮想マシン**上で行われており、 通常のセキュリティ監視の対象外である。 ただし**「隠した仮想マシン」が基盤エンジニアの端末や管理セグメントに 存在すること自体**は、資産管理の観点では見える可能性があった

影響を限定できた管理者権限を持つ要員の端末を専用の管理端末（PAW）に限定し、汎用の業務端末から特権操作ができないようにする

検知できた管理者アカウントの認証について、接続元・時刻・端末の逸脱を警報にする（業務時間外・自宅回線からのドメイン管理者ログオン等）
検知できた管理操作を踏み台（管理用ジャンプホスト）経由に限定し、セッションを記録する
永続化機会はあったが検知できず
**ドメインコントローラへのスケジュールタスクの新規登録は、 通常運用ではほとんど起きない事象である**（本記録の評価）。 Windows のイベントログではタスクの登録が記録される （タスクスケジューラの運用ログ・セキュリティログの該当イベント）。 **ここは本件で最も検知しやすかった地点**だが、 被害企業での検知状況は公表されていない

侵入を防げたドメインコントローラへの対話的ログオンと管理操作を二人制（承認者の同席・セッション記録）にする

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
被害企業は20ビットコイン（当時約75万ドル）の要求に応じなかった機能した本記録の作成者の評価である。**結果として脅迫は実行されず、恐喝は未遂に終わった。** ただし**支払わないという判断がいつ・どのように行われたかは公表されておらず、 意思決定の巧拙は評価できない**。本件では攻撃者が内部者として特定可能な立場にあり、 外部のランサムウェア攻撃者との交渉とは状況が異なる
被害企業は事案を公表せず、連邦検察も被害企業を「Victim-1」と匿名化した評価材料なし本記録の作成者の評価である。米国の連邦検察が被害者を匿名化するのは通例であり、 被害企業の判断と切り分けられない。 **ただし結果として、本件で最も参考になる「ドメイン管理者が全滅した状態からの 復旧方法」が公開情報として残らなかった**点は記録しておく
CISO・経営層への示唆
  • 「外から入られる」前提の投資だけでは、最高権限を持つ要員に対して何も効かない
    本件で使われたのはマルウェアでも脆弱性でもなく、 職務上与えられていた管理者アカウントとスケジュールタスクという標準機能だけである。 境界防御・マルウェア対策・脆弱性管理のいずれも作動する余地が無い
    取るべき行動 自組織の特権保有者（基盤・ドメイン管理・仮想基盤・バックアップの運用者）を名簿化し、 **「この人物が悪意を持った場合に何が起きるか」を1人ずつ机上で評価する。** 評価の単位は役職ではなく**実際に行使できる操作**にする
  • 単独で「管理権限そのものを消せる」経路を残さない
    ドメイン管理者アカウント13件がまとめて削除され、 被害企業の管理者は誰もドメインに管理者として入れない状態になった。 検知はできたが、検知した時点で対応手段が無かった
    取るべき行動 特権グループの変更・管理者アカウントの削除・バックアップの削除を **二人制の承認が無ければ完了しない操作**に変える。 あわせて**緊急用の管理者アカウント（break-glass）を通常の運用経路と ディレクトリから切り離して保管し、年1回は実際に使って復旧できることを確認する**
  • インシデント対応手順が「管理者権限が使えること」を前提にしていないか点検する
    本件では**最初に壊されたのが対応する側の手段**だった。 手順書の多くは暗黙に特権が使える前提で書かれている
    取るべき行動 対応手順を「管理者権限が使えない」「社内ネットワークに入れない」 「社内メールが使えない」の3条件で読み直し、 各手順が成立するかを確認する。成立しない手順には代替経路を書き足す。 連絡先名簿と手順書の写しを**ドメインに依存しない場所**に持つ
  • 内部不正の対策範囲を「自社の正規従業員」に閉じない
    報道が並べた先行事例では、勤務先を250万ドルで恐喝した Cameron Curry は **業務委託先の契約者**だった（2026年3月に2年の拘禁刑）
    取るべき行動 委託・派遣・業務委託を含めて**特権を持つ全ての個人**を対象に、 権限の棚卸しと操作の記録を適用する。 契約書に監査・ログ取得・権限返却の条項を入れ、契約終了時の権限失効を証跡で確認する
  • 処罰による抑止を前提に設計しない
    本件の量刑は32か月で、2罪状の法定上限の合計15年の約18%である。 先行事例の Curry も2年であり、**内部不正の量刑水準は2〜3年に収まっている**
    取るべき行動 内部不正のリスク低減を「規程と罰則の周知」から **「技術的に単独では成立しない構造にすること」**へ重心を移す。 規程の整備は必要だが、それだけを対策として報告しない
セキュリティ技術者への示唆
  • ドメインコントローラでのスケジュールタスクの作成を、単独で警報にする
    本件の中核の手口は**ドメインコントローラにスケジュールタスクを仕込むこと**だった。 これは通常運用でほとんど起きない変更であり、Windows のログにも記録される。 **本件で最も検知しやすかった地点である**
    取るべき行動 ドメインコントローラのタスクスケジューラ運用ログとセキュリティログから タスクの作成・変更イベントを収集し、**例外なく警報**にする。 正規の変更は変更管理の記録と突き合わせて消し込む運用にする。 「件数が多くて運用できない」場合は、対象をドメインコントローラに限れば日常的には発生しない
  • 「短時間での大量パスワード変更」と「特権グループからの削除」を即時の自動対応に結ぶ
    301件のユーザーアカウントのパスワード変更と13件のドメイン管理者アカウントの削除が、 通知が人に届くまで止まらなかった。 **検知の端緒は自動の警報ではなく管理者が受け取った通知メールだった**
    取るべき行動 単位時間あたりのパスワードリセット数に閾値を置き、 超過時は当該の実行主体（タスク・セッション・アカウント）を**自動で停止**する。 特権グループのメンバー削除とアカウント削除は別系統で即時通知し、 Active Directory のごみ箱機能と「オブジェクトを誤って削除されないように保護する」を有効にする
  • 常時有効な管理者権限を無くし、特権の払い出しを時間限定にする
    Rhyne は17日間にわたり管理者アカウントで権限なく遠隔接続していた。 正規のアカウントによる正規の経路であるため、認証の成否では区別できない
    取るべき行動 特権アカウントを常時有効な状態から外し、**申請・承認・時間限定の払い出し （Just-In-Time）**に切り替える。 管理操作は記録付きの踏み台を経由させ、接続元・時刻・端末の逸脱 （業務時間外のドメイン管理者ログオン等）を警報にする
  • 管理者が使う端末に、承認していない仮想マシンが立っていないかを見る
    Rhyne は犯行の計画に**隠した仮想マシン**上の自分のアカウントを使い、 そこから「ドメインアカウントの削除方法」「Windows のログの消去方法」を検索していた
    取るべき行動 管理セグメントと特権保有者の端末で、承認外のハイパーバイザ・仮想マシンの稼働を 資産管理と EDR で検出する。 管理操作は専用の管理端末（PAW）に限定し、汎用の業務端末から特権操作ができないようにする
  • ディレクトリ自体のオフライン・改変不能なバックアップと、復元の演習を持つ
    恐喝メールは「バックアップも削除した」と主張した（事実かは公表されていない）。 また**ドメイン管理者アカウントが全滅した状態からの復旧方法は公表されておらず、 参考にできる実例が残らなかった**
    取るべき行動 Active Directory のシステム状態バックアップを**ドメイン認証に依存しない保管先**に 改変不能な形で置き、**フォレストの復旧手順を年1回は実際に演習する**。 演習の前提に「ドメイン管理者アカウントが全て使えない」を含める
