INC-2026-0390ボットネットCarbonatoがAI基盤を悪用

ThreatDown は2026年9月22日、**無認証の Docker デーモン API（2375/tcp）**を狙うボットネット **Carbonato** を公表した。侵入後は**ホストのファイルシステムをマウントした特権コンテナ**でホストを掌握し、 **MIT ライセンスのオープンソース AI エージェント基盤 Hermes Agent を改変せずに設置**して、 ペルソナ定義ファイル `SOUL.md` だけを**39行の悪性プロンプト**で上書きする。 これによりエージェントは「上級ハッカー・ペンテスター・エクスプロイト開発者 **GH0ST**」として振る舞い、 運用者が **Telegram** で指示を出すと、AI が端末コマンドを生成・実行し出力を読んで次を決める。 収集対象の最優先は **AI サービスの API キー（14のプロバイダを名指し）**で、SSH 認証情報・アクセストークンが続く。 **5分ごとに隣接ネットワークと Docker ブリッジを調べて同じ連鎖を自走させる**ワーム性を持つ。 発見の経緯は**無認証のまま公開されていた Docker イメージレジストリ**（2026年5月から露出）で、 **59リポジトリ・234イメージタグ・605 blob・4.3GB** を回収し活動を**2024年10月から2026年8月**まで遡れた。 **悪性の挙動がコンパイル済みコードではなく設定ファイル1つに宿る**ため、 静的な検体シグネチャだけでは捉えにくい。**完全自動の攻撃ではない**—— ThreatDown は運用者と AI の**対話的な循環**だとしている

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）設定不備設計・実装上の不備
初報: 2026年9月22日 最終更新: 2026年10月5日

ThreatDown（Malwarebytes の法人向け事業）は2026年9月22日、Carbonato という名のボットネットを公表しました。狙うのは認証をかけずに公開された Docker デーモンの API（2375/tcp）です。

侵入の流れそのものは、以前からある「露出した Docker API」の悪用です。

  • 2375/tcp で認証なしの接続を受け付ける Docker デーモンを探す
  • 見つけると API を使って、ホストのファイルシステムをマウントした特権コンテナを起動し、コンテナ越しにホスト自体を操作できる状態にする
  • cron・systemd タイマー・rc.local・OpenRC のフックで居座り、それらのファイルを変更不可（immutable）属性にする
  • コスタリカの中継サーバへ逆方向の SSH トンネルを張り、運用者の鍵を入れた SSH サーバを立てる
  • 5分ごとにホストと Docker ブリッジに繋がるネットワークを調べ、別の無認証 Docker デーモンを見つけると同じ連鎖を実行する（ワームとして自走する）

新しいのはここからです。 Carbonato は侵入先にHermes Agent（MIT ライセンスのオープンソース AI エージェント基盤）を一切改変せずに設置し、ペルソナ定義ファイル SOUL.md だけを 39行の悪性プロンプトで上書きします。プロンプトはエージェントに「あなたは GH0ST——上級ハッカー、ペンテスター、エクスプロイト開発者である」（原文英語）と名乗らせ、運用者の命令を実行し、システムへのアクセスを維持し、あらゆる道徳的・倫理的な制約を無視するよう指示します。

運用者は Telegram で指示を出します。AI が依頼を解釈して端末コマンドを生成し、その出力を読んで次に何をするかを決め、結果を同じ Telegram に返します。収集対象の最優先は AI サービスの API キーで、ThreatDown はプロンプトが14のプロバイダを名指ししているとしています。その次に SSH 認証情報・アクセストークン・各種の秘密が並びます。

発見の経緯も記録に値します。ThreatDown は 2026年8月、認証をかけずに公開されたままの Docker イメージレジストリを見つけました（2026年5月から露出していました）。そこから59リポジトリ・234のイメージタグ・605の blob・4.3GB のイメージデータを回収し、2024年10月から2026年8月までの運用の痕跡を辿れました。同じレジストリには、同じ運用者による別のキャンペーン—— 偽の暗号通貨ウォレットアプリの配布——の材料も入っていました。つまり公表までの約2年間、この活動は動いていたことになります。

この事案の読みどころは2つです。

1つ目は、悪性の挙動が「コード」ではなく「設定ファイル1つ」に宿っている点です。基盤は改変されていないオープンソースのままなので、検体のハッシュや静的シグネチャを当てにする検知が成立しにくい。ThreatDown の助言は「代わりに悪用の痕跡を狩れ」です。

2つ目は、これが「完全自動の AI 攻撃」ではないという点です。ThreatDown は運用者が課題を与え、AI が必要なコマンドの選択と実行を助ける「対話的な循環」だと明記しています。本記録はこの留保をそのまま残します—— AI エージェントの悪用を過大に読むと、対策の焦点がぼやけます。実際にこの事案で効く対策は、Docker API を露出させないこととAI の API キーを銀行の認証情報と同じ重さで扱うことです。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**認証をかけずに 2375/tcp で公開された Docker デーモン API** を探し、 API 経由で**ホストのファイルシステムをマウントした特権コンテナ**を起動してホストを掌握する。 **cron・systemd タイマー・`rc.local`・OpenRC** の4系統で永続化し、 **ファイルを変更不可属性にして watchdog で復活させる**。 **コスタリカの中継サーバへ逆 SSH トンネル**を張り、Telegram で運用者と繋がる。 侵害後は**改変していない Hermes Agent** を設置し、 **`SOUL.md` を39行の悪性プロンプトで上書き**して GH0ST として振る舞わせ、 **AI サービスの API キー（14プロバイダ）**を最優先に秘密情報を集める。 **5分ごとに隣接ネットワークを走査**して同じ連鎖を自走させる。 **脆弱性の悪用は無い**——成立の前提は認証の不在だけである。

  1. 1. 偵察確認済[1] [5]
    **2375/tcp で認証なしの接続を受け付ける Docker デーモンを探索する。** 初期の探索はインターネット側から行われ、 侵害後は感染ホストが**ホストと Docker ブリッジに接続されたネットワーク**を **5分ごとに**調べる。
    根拠: ThreatDown の記述（"searches for Docker daemons that accept unauthenticated connections on port 2375"、5分ごとのネットワーク識別）
  2. 2. 初期侵入確認済[1] [3]
    発見した**無認証の Docker デーモン API** に接続する。 **認証機構が無いため、到達できること自体が権限の獲得と同義になる。** シンガポール CSA は、この状態を「Docker Remote API が インターネットまたは信頼できないネットワークから認証なしに到達可能」 （原文英語）と表現している。
    根拠: ThreatDown とシンガポール CSA の双方の記述
  3. 3. 権限昇格確認済[1] [3]
    API を使って**特権コンテナを起動し、ホストのファイルシステムをマウントする**。 ThreatDown の記述は「デーモンを使って、ホストのファイルシステムを マウントした特権コンテナを起動する」（原文英語）である。 これによりコンテナ越しに**ホスト自体でコマンドを実行**できる状態になる。 **コンテナの分離を破る脆弱性は使われていない**—— 特権コンテナとホストのマウントはいずれも Docker の正規の機能である。
    根拠: ThreatDown の記述とシンガポール CSA の記述（"legitimate Docker functionality to create a privileged container"）
  4. 4. 永続化確認済[1] [2]
    **cron・systemd タイマー・`rc.local`・OpenRC のフック**の4系統で居座り、 **それらのファイルを変更不可（immutable）属性にする**。 さらに **watchdog スクリプト**が、マルウェアが削除・停止された場合に再起動する。 プロセス名は **`[kworker/u2:0]`**（カーネルスレッドを装う）、 配置は **`/usr/sbin/systemd-logind`**（正規のデーモンを装う）といった 偽装が併用される。
    根拠: ThreatDown の記述（"create persistence hooks through cron, systemd timers, rc.local, and OpenRC, then mark those files immutable"）と Xakep.ru の watchdog の記述
  5. 5. C2通信確認済[1] [2]
    **コスタリカの中継サーバへ逆方向の SSH トンネル**を張り、 **運用者の鍵を入れた SSH サーバ**を立てて常時の遠隔アクセスを確保する。 トンネルの向きは **AS262145**（コスタリカのネットワーク）である。 加えて、新たに感染したホストの情報（コンテナの情報を含む）を **Telegram** で運用者へ通知し、運用者からの課題も Telegram で受け取る。
    根拠: Xakep.ru の記述（コスタリカの中継サーバ経由の逆 SSH トンネル・運用者の鍵を持つ SSH サーバ・Telegram への通知）と ThreatDown の AS262145 の記述
  6. 6. 実行確認済[1] [2]
    **改変していない Hermes Agent**（MIT ライセンス）を設置し、 **ペルソナ定義ファイル `SOUL.md` を39行の悪性プロンプトで上書き**する。 プロンプトはエージェントを **GH0ST**（上級ハッカー・ペンテスター・ エクスプロイト開発者）として振る舞わせ、 **あらゆる道徳的・倫理的な制約を無視する**よう指示する。 以後、運用者が Telegram で与えた課題に対し、 **AI が端末コマンドを生成・実行し、出力を読んで次を決める**。 **完全自動ではなく、運用者と AI の対話的な循環である。**
    根拠: ThreatDown の記述（"overwrites the agent's SOUL.md persona file with the crew's 39-line prompt"、"You are GH0ST — senior hacker, pentester and exploit developer"、対話的な循環であること）
  7. 7. 認証情報アクセス確認済[1] [2]
    プロンプトは収集の優先順位を明示している。 **最優先は AI サービスの API キー**で、 **14のプロバイダを名指し**している。 続いて **SSH 認証情報・アクセストークン・その他の秘密・ データベースの内容**である。 環境変数 **`CARBONATO_API_KEY`** が指標として挙げられている。
    根拠: ThreatDown の記述（"prioritizes the collection of AI API keys"・"names 14 providers"）と Xakep.ru の優先順位の記述
  8. 8. 横展開確認済[1] [5]
    **5分ごと**に、ホストと Docker ブリッジに接続されたネットワークを識別し、 **別の無認証 Docker デーモンを探す**。 見つけると**同じ感染連鎖を実行**する。 ThreatDown は、これにより **運用者が次の課題を与えるのを待たずにネットワーク内へ広がる**としており、 **ワームとしての性質**を持つ。
    根拠: ThreatDown の記述（"Every five minutes, the worm identifies the networks attached to the host and its Docker bridges"・運用者の指示を待たずに広がること）

    AI エージェントは**作業の結果と収集したデータを Telegram へ送る**。 指令と持ち出しの経路が同じである。

本記録の注記として、侵入経路そのものに新しさは無い。露出した Docker API の悪用は暗号資産採掘ボットネットが長く使ってきた手口である。変わったのは侵入後に置かれるもので、固定の機能を持つバックドアではなく指示に応じて手順を組み立てる仕組みが据えられた。

悪性の挙動がコード不在で「設定ファイル1つ」に宿るため、検体のシグネチャでは捉えにくい評価・解釈出典 [1] [2] [3]

本記録がこの事案の中心と考えるのは、ここである。

Carbonato は Hermes Agent を配布されているままの状態で設置する。改変されているのは SOUL.md という1つのペルソナ定義ファイルで、中身は 39行のプロンプトである。

この構造が検知にもたらす帰結は3つある（本記録の評価）。

  1. 検体のハッシュが意味を持たない。 設置されるのは正規の、MIT ライセンスで公開されているソフトウェアである。ファイルの同一性を見る検知は「正規のもの」と判定する
  2. 静的シグネチャの当てどころが無い。 悪性の意図はコンパイル済みのコードではなく平文の設定ファイルにある。ThreatDown の言い方は「代わりに悪用の痕跡（abuse signature）を狩れ」である
  3. 挙動が実行ごとに変わる。 コマンドは AI が生成するため、同じ指示でも実行されるコマンド列が一致する保証が無い。固定のコマンド文字列を条件にした検知規則は外れやすい

一方で、検知の手がかりが消えたわけではない。ThreatDown が挙げた痕跡は、むしろ環境側に残る固定の事実である。

この点は、誤読されやすいので事実のまま記録する。

ThreatDown は、Carbonato を完全に自動化された攻撃ではないとしている。説明されているのは対話的な循環（interactive loop）で、運用者がエージェントに課題を与え、AI が必要なコマンドの選択と実行を助ける形である。

自走するのは「拡散」のほうである。 5分ごとの隣接ネットワークの走査と、新しい無認証 Docker デーモンを見つけたときの感染連鎖は、運用者の指示を待たずに動く。ただしこれは AI の判断ではなく、従来型のワームのロジックである。

AI が担っているのは、侵害後の個別作業の組み立てである。Telegram で与えられた依頼を解釈し、端末コマンドを生成し、その出力を読んで次を決める。ThreatDown は、C2 基盤が各ホストの固有の構成に合わせて環境を推論し適応する最初の文書化された事例だとしている。

本記録の評価として、守る側への含意はこうである。

  • 攻撃の量が自動で増えるという話ではない。 拡散の自動化は従来のワームと同じで、AI が加わったことで感染速度が上がったという説明は示されていない
  • 変わるのは侵害後の「手際」である。 環境ごとの試行錯誤——どのパッケージが入っているか、どこに鍵があるか、何が動いているか——を人間が1台ずつ調べる手間が減る。これは攻撃者1人が扱えるホスト数を増やす方向に効く
  • したがって対策の優先順位は変わらない。 露出の除去・認証の付与・秘密情報の持たせ方が依然として効く。AI 固有の対策を先に探すのは順序が逆である

過大に読まないための留保をもう1つ。本記録が確認できたのはプロンプトの内容と ThreatDown の記述であり、AI エージェントが実際にどの程度うまく動いたか（成功率・失敗の仕方）は分析に示されていない。

つまり、Carbonato が狙っていた設定不備（無認証で公開された Docker の仕組み）と、Carbonato の分析を可能にした設定不備は同じものである。

本記録の評価として、ここから読めることは2つある。

  1. この活動は約2年間、外部に気づかれずに動いていた。公表（2026年9月22日）までの間、露出した Docker API を侵害し続けていた。被害の規模は公表されていないため、2年分の累積がどれほどかは分からない
  2. 帰属の手がかりも、この運用の緩さから出ている。 ThreatDown が挙げたのは、voseo（中米などで使われるスペイン語の二人称）の使用、162のイメージ設定のうち14が America/Costa_Rica と一致する UTC-06:00 を使っていること、Carbo506 という名称（+506 はコスタリカの国番号）、AS262145（コスタリカのネットワーク）への逆 SSH トンネルである。

ただしこれらは所在を示唆する状況証拠であり、帰属ではない。 ThreatDown は既知の攻撃者グループとの結び付けはできていないとしている。本記録も運用者を特定の組織・個人・国家に結び付けない。

対策は政府勧告と分析で一致している——露出をなくし、AI の API キーを認証情報として扱う対策・注意喚起出典 [1] [3]

ThreatDown の推奨（4項目・原文英語）

  • Docker デーモンの API をネットワークに露出させない
  • すべてのレジストリで認証を必須にする
  • 検体ではなく悪用の痕跡（abuse signature）を狩る
  • AI の API キーを銀行の認証情報と同じように扱う

シンガポール CSA の勧告（AD-2026-012・2026年9月30日・5項目）

  • Docker Remote API へのアクセスを制限する
  • SSH または TLS による安全な遠隔アクセスに切り替える
  • 露出していた可能性のあるシステムを侵害の兆候について評価する
  • 認証情報を見直し、交換（ローテーション）する
  • 横展開を監視する

両者は同じ順序を取っている（本記録の注記）。先に来るのは露出の除去で、検知は後ろにある。認証が無いことが成立の前提である攻撃なので、認証をかければ起点が消える。

本記録として補足する評価は2点である。

  1. 「侵害の兆候を評価する」を飛ばさない。 Docker API を閉じるのは数分で終わるが、2024年10月から活動していたことを踏まえると、すでに侵害されている可能性のほうが問題である。永続化は cron・systemd タイマー・rc.local・OpenRC の4系統に分散し、ファイルは変更不可属性にされ、watchdog が復活させる——マルウェアのプロセスを1つ止めただけでは戻らない
  2. 認証情報の交換の範囲に AI の API キーを必ず含める。本件のプロンプトは AI サービスの API キーを最優先にしており、14のプロバイダを名指ししている。SSH 鍵やデータベースの資格情報と違い、AI の API キーは台帳に載っていないことが多い（本記録の評価）——開発者が個人で取得し、環境変数や .env に置かれたまま棚卸しの対象になっていない状態が起きやすい

    取るべき行動 AI 絡みの脅威情報を受けたときは、**「成立の前提になっている条件」を1行で書き出す** 運用にする。本件では「2375/tcp が認証なしで到達可能」であり、 対策はそこを閉じることに尽きる。 AI 固有の対策の検討は、前提条件の除去を終えた後に回す
  • AI サービスの API キーを、認証情報の台帳に載せる
    攻撃者のプロンプトは**AI サービスの API キーを最優先の収集対象**にし、 **14のプロバイダを名指し**している。 ThreatDown の推奨にも「AI の API キーを銀行の認証情報と同じように扱え」とある。 これらのキーは開発者が個人で取得し、台帳の外に置かれやすい
    取るべき行動 AI サービスの API キーを**正式な認証情報として棚卸しの対象に加える**。 発行元・利用用途・保管場所・権限範囲・有効期限を記録し、 **利用上限と送信元制限を設定**して、利用量の急増を警報にする。 個人名義での取得を禁止し、組織の管理下に移す
  • 外部に開いている管理面（Docker API・Kubernetes API・管理コンソール）を定期的に数える
    本件の標的は業種や地域で選ばれておらず、**到達できるものが順に侵害される**。 発見の端緒となった攻撃者側のレジストリも、同じ設定不備で3か月露出していた
    取るべき行動 外部公開面の走査を定期業務にし、**管理用のポート・API・コンソールの 「意図した公開」の一覧と突き合わせる**。 一覧に無いものを見つけたら即時に閉じる手順と権限者を決めておく。 クラウドのセキュリティグループと検証環境を対象から外さない
  • 侵害が疑われるホストは「除去」ではなく「再構築」を既定の方針にする
    永続化は **cron・systemd タイマー・`rc.local`・OpenRC** の4系統に分散し、 **ファイルは変更不可属性にされ、watchdog スクリプトが復活させる**。 プロセスを1つ止めても戻らない構えである
    取るべき行動 インシデント対応の方針として、**サーバの再構築を既定の選択**にし、 そのために**構成を宣言的に管理して再構築できる状態**を平時から保つ。 除去を選ぶ場合の条件（調査の目的・隔離の確実性）を文書化する
  • 「国内の被害が報告されていない」ことを「自組織に関係ない」と読み替えない
    日本の組織が被害に含まれるという記載はどの資料にも無いが、 本件は**到達できる無認証 Docker API を順に侵害する機会主義的な活動**で、 国や業種による標的選定は示されていない
    取るべき行動 脅威情報の評価基準を「自国・自業種の被害報告の有無」ではなく **「成立条件を自組織が満たしているか」**に置く。 本件では「2375/tcp を認証なしで開けているホストがあるか」の点検で判定できる
セキュリティ技術者への示唆
  • Docker デーモンの API を 2375/tcp で露出させず、TLS 認証か SSH 経由に移す
    **2375/tcp は暗号化されない Docker Remote API の既定ポート**で、 認証機構が無い。到達できること自体が権限の獲得と同義になる。 ThreatDown の推奨の先頭、シンガポール CSA の勧告の先頭がどちらもこれである
    取るべき行動 全ホストで Docker デーモンの待ち受けを確認し、 **2375/tcp での公開を止める**（バインドアドレスを localhost か Unix ソケットに限定）。 遠隔操作が必要な場合は **TLS によるクライアント証明書認証（2376/tcp）**か **SSH 経由**に切り替える。あわせて **rootless モード**の採用を検討する
  • 特権コンテナの作成とホストのファイルシステムのマウントを、単独で警報にする
    攻撃は **`--privileged` かつホストのファイルシステムをマウントしたコンテナ**で ホストを掌握する。シンガポール CSA はこれを 「特権コンテナを作成するための正規の Docker 機能」（原文英語）と表現している。 **通常運用ではほとんど起きない操作であり、本件で最も検知しやすい地点の1つである**
    取るべき行動 Docker デーモンの API アクセスログとコンテナ作成イベントを収集し、 **特権コンテナの作成とホストのルートのマウントを例外なく警報**にする。 あわせて admission 制御・seccomp・AppArmor で**ポリシーとして禁止**する （検知だけでなく防止側に置く）
  • 起動関連ファイルの変更と「変更不可属性の付与」を完全性監視の対象にする
    永続化は cron・systemd タイマー・`rc.local`・OpenRC の4系統に分散し、 **それらのファイルが変更不可（immutable）属性にされる**。 **この属性の付与自体が、通常運用では珍しい手がかりになる**
    取るべき行動 `/etc/cron*`・systemd のユニットとタイマー・`/etc/rc.local`・OpenRC の設定を ファイル完全性監視の対象にし、**新規の起動項目**を警報にする。 あわせて**起動関連ファイルへの immutable 属性の付与**を検出する規則を追加する
  • サーバから「外向きに出る SSH」と「メッセージングサービス宛ての通信」を異常として扱う
    C2 は**コスタリカの中継サーバへの逆方向 SSH トンネル**（AS262145 方向）と **Telegram** である。 **サーバは SSH を受けるのが普通で、外へ出すのは向きが逆**であり、 サーバ群から Telegram の API 宛ての通信も通常は発生しない
    取るべき行動 サーバからの外向き通信を**宛先ごとの許可制**にし、既定で遮断する。 **サーバを起点とする外向きの SSH 接続**を警報にし、 承認していない `authorized_keys` の追加と SSH サーバの新規起動も検出する
  • 検体の同一性ではなく「正規のソフトウェアが想定外の場所で動いている」ことを見る
    設置されるのは**改変されていない MIT ライセンスのオープンソース基盤**で、 悪性の意図は **`/root/.hermes/SOUL.md` という平文の設定ファイル39行**にのみある。 さらに実行されるコマンドは AI が生成するため毎回同じにならない。 ThreatDown の助言は「検体ではなく悪用の痕跡を狩れ」である
    取るべき行動 サーバ上で**承認していない実行基盤（AI エージェント・インタプリタ・パッケージ）の 新規導入**を資産管理とアプリケーション制御で検出する。 **想定していないプロセスからの大規模言語モデルの API 宛ての通信**を警報にする。 AI エージェント基盤を正規に使う場合は、 **ペルソナ・システムプロンプトの定義ファイルを完全性監視の対象**にする
  • ネットワークを分割し、サーバ間の管理ポート到達性を既定で塞ぐ
    感染ホストは**5分ごと**にホストと Docker ブリッジに繋がるネットワークを調べ、 別の無認証 Docker デーモンを見つけると同じ連鎖を実行する。 **1台の設定漏れが同一ネットワークの全 Docker ホストの起点になる**
    取るべき行動 サーバ間（東西方向）の 2375/tcp 到達性を既定で遮断し、 **内部での管理ポート宛ての走査（固定間隔の反復を含む）を警報**にする。 あわせて同一ネットワーク内の全 Docker ホストで API の認証設定を統一し、 設定の有無を定期的に機械的に確認する
