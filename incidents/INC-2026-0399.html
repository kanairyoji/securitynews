INC-2026-0399ミスターマックス 会員173万人流出

ミスターマックスの MrMax アプリとオンラインストアのサーバに第三者が侵入、会員最大173万5,154人の氏名・電話番号・メールアドレス・会員IDが流出した——「サービスを構成するソフトウェアの機能を不正に使用して侵入された」とされ、住所・生年月日・クレジットカード情報・パスワード・購入履歴は流出していないと確認されている

不正アクセス・侵害初報のみ日本の組織が当事者設計・実装上の不備既知の脆弱性の悪用
初報: 2026年10月6日 最終更新: 2026年10月7日

ディスカウントストア「MrMax」を運営するミスターマックスは2026年10月6日、MrMax アプリとオンラインストアのサーバに第三者が侵入し、会員の個人情報が流出したことを公表した。流出した可能性があるのは最大173万5,154人分の氏名・電話番号・メールアドレス・会員IDである。

経緯は短い。

  • 2026年10月3日（土）夕方 — MrMax アプリとオンラインストアのサーバにおける不審なアクセスを確認した
  • 同日中 — サービスを一時停止し、外部からのアクセスを遮断した
  • 調査により、アプリやオンラインストアを構成するソフトウェアの機能を第三者が不正に使用してサーバに侵入し、会員の個人情報が流出したことが分かった
  • 2026年10月6日 — 公表した。警察へ相談し、個人情報保護委員会へ報告した

本記録がこの事案を取り上げる理由は、件数ではない。注目すべきは次の3点である。

  1. 「流出していないもの」を一次公表が列挙している。住所・生年月日・クレジットカード情報・パスワード・購入履歴は流出していないと確認したとされる。漏えいの公表で「漏れていない項目」を名指しできる組織は多くない。これはどのデータがどこにあるかを把握していることの表れである（本記録の評価）
  2. 原因の説明が「ソフトウェアの機能の不正使用」で止まっている。脆弱性の種別も製品名も示されていない。同じ作りのアプリ・オンラインストアを運用する他社が、自社が同じ危険にあるかを判断できない
  3. 流出した4項目の組み合わせが、そのままフィッシングの材料になる。氏名・電話番号・メールアドレス・会員IDが揃うと、「MrMax 会員の○○様」と名指しで接触できる。同社は対象会員にメールで謝罪するとともに、なりすましメール・フィッシングメール、同社関係者を名乗る連絡への注意を求めている

よくできているのは、流出した項目と流出していない項目を両方名指しで示したことである。多くの事案では後者が「調査中」のまま残り、利用者はクレジットカード情報の危険まで自分で想像することになる。本件はそれを5項目について名指しで否定した。これはデータの所在を把握していないとできない。

一次公表は原因をこう記している——「第三者が本サービスを構成するソフトウェアの機能を不正に利用してサーバーに侵入」した。報道も同じ表現を伝えている。製品名・機能名・脆弱性の種別はいずれも示されていない。

以下は本記録の作成者による評価である。

この一文から読み取れるのは「外部から到達できる機能が、本来の用途とは違う形で使われた」ということだけである。そして、ここに当てはまる技術的な事象は少なくとも3通りある。

  1. 認証を要しない API の列挙。 会員情報を返す API が認証なし、または弱い識別子だけで呼べる状態にあり、識別子を順に変えて大量に取得された
  2. 想定より広い権限で動く機能の悪用。 管理用の一覧表示や移行用の一括出力が公開面に出ており、一般の認証で到達できた
  3. 入力検証の不足（既知の脆弱性を含む）。 使用しているフレームワーク・プラグインに公表済みの欠陥があり、修正が適用されていなかった

1と2は「設計の問題」であり、修正パッチでは消えない。3は「放置の問題」であり、更新で消える。対策はまったく別のところに向かう。読んだ他社が自社を点検しようとしても、どちらを見ればよいかが決められない。

本記録は原因の分類として 設計・実装上の不備を主、既知の脆弱性の悪用を併記とした。「機能を不正に利用」という語の選び方が〈本来備わっている機能を想定外の形で使われた〉という意味に読めるためである。ただしこれは本記録の読み取りであり、当事者の分類ではない。

修正が完了する前に具体を公開すれば、同じ手口が他社へ向かう危険がある。その判断は理解できる。だが「何も言わない」と「全部言う」の間には段階がある。

  • 層の特定 — アプリ側か、EC の基盤か、共通の会員基盤か
  • 機構の種別 — 認証・認可の問題か、入力検証の問題か、公開範囲の問題か
  • 製品名と版 — 修正後に出せる

本件は層の特定すら示していない。一次公表は「MrMax アプリとオンラインストアのサーバ」とまとめており、両者が会員基盤を共有していたのかも分からない。両方が同時に対象になった理由は、読む側には「同じ基盤だったから」としか想像できないが、その想像を確かめる材料が無い。

日本の小売・EC では、アプリと Web ストアを別のベンダーに作らせ、会員基盤だけを共有する構成が広く使われている。本件がその構成の事故なのかどうかは、同業他社にとって決定的に重要だが、公表からは読み取れない。本記録は続報で原因が示されるかを追跡する。

クレジットカード情報が漏れていないことは重要である。だが「カードが漏れていないから軽い」とは言えない。漏れた4項目には、固有の危険がある。

氏名＋電話番号＋メールアドレス＋会員IDは、「あなたを名指しできる」組み合わせである。

  • 「MrMax 会員の○○様、会員ID××番のポイントに関するお知らせ」という文面が作れる。会員IDを添えられる偽メールは、本物に見える
  • 電話番号があるため、メールと電話を組み合わせた手口が成立する（メールで不安を与え、電話で誘導する形）
  • 住所と購入履歴は漏れていないため、「配送のお知らせ」を装う手口の精度は上がらない。これは実質的な緩和である

同社が注意喚起の対象を「なりすましメール」「フィッシングメール」「同社関係者を名乗る連絡」と具体化したのは適切である。「不審な連絡にご注意ください」では、何に注意すべきか分からない。

ただし、通知の構造に難所がある。

メールアドレスが流出した会員に対して、メールで通知している。つまり攻撃者も同じ宛先を持っている。「MrMax からのお詫び」を装った偽メールは、本物の通知より先に届くこともある。会員の受信箱で本物と偽物が並んだとき、見分ける材料は何か。

この状況で効く手は、設計で用意するものである。

  • 通知メールにリンクを置かない。「ご自身でブラウザから mrmax.co.jp を開いてご確認ください」と案内する。リンクを踏ませない通知は、偽メールの手本にならない
  • 送信元ドメインを1つに固定し、公表文でそのドメインを明示する。「当社からのご連絡は @mrmax.co.jp からのみ送信します」と書く
  • Web サイトの告知とアプリ内通知を正本にする。メールは告知への誘導にとどめる

一次公表からは、これらが行われたかどうかは読み取れない。問い合わせ窓口（security-info@mrmax.co.jp）を示した点は、会員が確認する先を持てるという意味で良い。

もう1点、会員IDが流出していることの扱いに言及が無い。パスワードは流出していないとされるが、IDが判明した状態では、他サービスから漏れたパスワードの使い回しを狙った試行が成立する。再設定を求めないという判断なのか、言及が漏れたのかは公表からは分からない。

本記録が本件で最も評価するのは、土曜日の夕方という時間帯である。

小売業の土曜夕方は売上の山である。その時間にアプリとオンラインストアを止める判断を、検知したその日のうちに下して実行している。これは偶然では起こらない。少なくとも次の3つが揃っている必要がある。

  3. 止める手順が事前にあった。「外部からのアクセスを遮断する」具体的な操作がその場で考え出せるものではない

一次公表はこの3点のいずれにも言及していない。だから本記録は「体制が整っていた」と断定はしない。ただし結果としての所要時間は、何かが機能したことを示している。

「流出していない項目を確認する」のは、流出した項目を特定するより手間がかかる。どこに何があり、侵入された範囲がどこまでだったかを両方押さえないと「漏れていない」と言えない。それを3日でやっている。
