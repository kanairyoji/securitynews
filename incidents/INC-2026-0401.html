INC-2026-0401104人力銀行 履歴書12万件を読取

台湾最大の求人サイト 104人力銀行を運営する一零四資訊科技が、アプリの仕組みを通じて約12万件の履歴書データが権限なく読み取られたことを証券市場の重大情報として開示した——防御と遮断の措置をとり主管機関へ通報し法務部調査局台北市調処へ届け出たが、読み取られた項目・発生時期・原因はいずれも公表されていない

不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年10月6日 最終更新: 2026年10月7日

台湾最大の求人サイト 104人力銀行を運営する一零四資訊科技（台湾証券取引所上場・銘柄コード 3130）は、2026年10月6日17時51分、証券市場の情報公開システム（公開資訊觀測站）に重大情報を開示し、アプリの仕組みに異常な読み取りの状況を察知したことを明らかにした。

調査により確認された範囲は次のとおりである。

  • 約12万件の履歴書データが、権限なく読み取られた
  • 事態の把握後、直ちに防御の措置と遮断を行った
  • 規定に従い関係する主管機関へ通報した
  • 法務部調査局台北市調処へ届け出た（刑事対応）
  • 外部の第三者の情報セキュリティ機関と協力してフォレンジック調査を行い、情報セキュリティの防護を強化している
  • 自社サイトで会員へ公告し、影響を受けた疑いのある利用者へ電子メールで能動的に通知した
  • システムの稼働と事業運営は正常であり、現時点で会社に重大な影響はないと初期判断したが、影響の評価は継続している
  • 重大な進展があれば規定に従い随時情報を更新する

一方、公表されていないことが多い。読み取られた履歴書に含まれる具体的な項目、異常な読み取りがいつ行われたか、原因はいずれも示されていない。

本記録がこの事案を取り上げる理由は、日本の読者にとって次の3点が重要だからである。

  1. 履歴書は、個人情報の中でも密度が高い。求人サイトの履歴書には、氏名・連絡先に加えて学歴・職歴・在職中の勤務先・希望条件・顔写真が揃うことが多い。在職中の転職活動が現在の勤務先に知られるという、他の漏えいには無い害がありうる（本記録の指摘。読み取られた項目は公表されていない）
  2. 「アプリ経由」という経路が示された。 Web ではなくアプリの仕組みを通じた異常な読み取りである。アプリは API を直接呼ぶ構成になりやすく、Web の画面では起こらない一括取得が成立することがある
  3. 上場企業として証券市場の重大情報で開示した。台湾では一定の事案について適時開示が求められる。本件は株主への開示と利用者への通知が同じ日に動いている。日本の上場企業にとっても参考になる形である

本件は、対応の「手順」と公表の「中身」の評価が分かれる事案である。

手順は整っている。遮断・当局通報・刑事届出・市場開示・会員公告・利用者通知・外部調査が、開示の時点ですべて揃っている。本DBが記録してきた事案と比べても、この型の完成度は高い。とくに株主への開示と利用者への通知が同じ日に動いたことは、上場企業の漏えい対応として参考になる。

一方、中身は薄い。読み取られた履歴書に何が含まれていたかが、1つも示されていない。そして履歴書の害の大きさは、まさにその項目で決まる。

履歴書の漏えいは「個人情報が漏れた」では済まない——在職中の転職活動が知られる害がある評価・解釈出典 [1] [2]

以下は本記録の作成者による評価である。 本件で読み取られた項目は公表されていないため、以下は求人サイトの履歴書が一般に含みうる内容についての議論である。

求人サイトの履歴書は、個人情報の中でも特殊な位置にある。含まれうる項目を並べると、それぞれ性質の違う危険を持つ。

項目 漏れたときの危険
氏名・生年月日・住所 なりすましの基本材料
個人の携帯番号・個人のメール 求人を装った詐称の宛先になる
学歴・職歴 経歴を使った信用の詐称に使われうる
在職中の勤務先 転職活動が現在の勤務先に知られる
希望年収・希望条件 交渉上の立場が不利になる
顔写真 なりすまし・合成の材料になる

太字にした項目が、履歴書に固有の害である。

通常の個人情報漏えいの被害は、「詐欺に使われる」「なりすまされる」という形で本人に降りかかる。これらは本人が警戒すれば軽減できる。連絡先を変える、不審な連絡を無視する、パスワードを変える——取れる行動がある。

在職中の転職活動が知られる害は、本人に取れる行動が無い。すでに勤務先に知られてしまえば、取り消せない。そして日本・台湾を含む東アジアの雇用慣行では、これは昇進・評価・人間関係に実際の影響を及ぼしうる。

だからこそ、読み取られた項目を示すことが決定的に重要になる。

  • 氏名と応募履歴だけなら、求職者の多くは「様子を見る」で済む
  • 在職中の勤務先が含まれるなら、求職者は在職先での立場を考え、場合によっては先に説明する判断がありうる
  • 連絡先が含まれるなら、求人を装った詐称への警戒を強める必要がある

これらはまったく違う行動である。「約12万件が読み取られた」とだけ告げられた求職者は、どれを取るべきかを判断できない。

一零四資訊科技は影響を受けた疑いのある利用者へ電子メールで能動的に通知したとしている。個別の通知に項目の説明が含まれていれば、この問題は解消する。だが本記録の作成者は通知の文面も会員向け公告の原文も取得できていないため、含まれているかどうかを確認できない。

市場への開示に項目の記載が無いことは確認できる。そして上場企業の重大情報は、報道を通じて最も広く読まれる一次情報である。ここに項目が無ければ、通知を受けていない利用者（自分が対象かどうか分からない人）は何も判断できない。

本記録は、続報で項目が示されるかを追跡する。

開示された事実

開示文は経路として「App 系統」（アプリの仕組み）に異常な読み取りの状況を察知したと記している。それ以上の具体——どの機能か、認証を要したか、脆弱性があったか——はいずれも示されていない。原因は外部の第三者の情報セキュリティ機関と協力したフォレンジック調査の対象となっている。

以下は本記録の作成者による評価であり、本件の実装についての確認事実ではない。

「アプリ経由」と示されたことには意味がある。スマートフォンアプリは、Web の画面とは違う攻撃面を持つ。

1. アプリは API を直接呼ぶ。 Web の画面では、利用者ができることは画面に出ているものに限られる。アプリは裏で API を呼んでいるため、通信を解析すれば、画面に出ていない機能や引数が見える。「1ページに20件ずつ表示する」という画面の制約は、API に件数の上限が無ければ意味を持たない。

2. クライアント側の制限は回避される。アプリに埋め込んだ鍵、アプリが付けるトークン、アプリ側で掛けている件数の制限—— これらはすべて利用者の端末の上にあり、解析と改変の対象になる。制限はサーバ側に置かなければ守りにならない。

3. 認可の文脈が落ちやすい。求人サイトの履歴書は、「応募があった求人の担当者が、その応募者の履歴書を見る」のが本来の文脈である。この文脈をサーバ側で確認しているかが守りの核心になる。「認証済みのアカウントなら、履歴書IDを指定して1件取得できる」という実装であれば、IDを順に変えるだけで大量に取得できる。識別子を知っていることは、認可の根拠にならない。

本件がこのどれに当たるかは分からない。だが「アプリの仕組み」という経路の示し方は、読む側に点検の方向を与えている。これは MrMax の事案（本DBの INC-2026-0399）が「サービスを構成するソフトウェアの機能」とだけ記して層を示さなかったのと対照的である。

日本の読者が自社で確認できることは具体的である。

  • アプリが呼ぶ API の一覧を作る
  • 各エンドポイントに対応する画面があるかを確認する
  • 各エンドポイントが1回で返す件数の上限を確認する
  • 他人の個人データを返すエンドポイントの認可の条件を読む（識別子を知っていれば取れる実装になっていないか）
  • クライアント側に置いている制限をサーバ側へ移す

    本件は**重大情報の開示（2026年10月6日17時51分）と同日に**、 会員への公告と影響が疑われる利用者への電子メール通知を行っている。 **上場企業では開示が先に出て、 利用者が報道で自分の被害を知るという順序になりがちである**

  • 「遮断した」と書くときは、何を遮断したかを書く
