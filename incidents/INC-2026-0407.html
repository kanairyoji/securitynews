INC-2026-0407SonicWall SMA1000に満点のSSRF

SonicWall は現地時間2026年10月6日、リモートアクセス製品 **SMA1000 シリーズ** （6210・7210・8200v）に **CVSS v3.1 で満点の 10.0** となる **認証前のサーバサイドリクエストフォージェリ（SSRF）CVE-2026-102255** があることを公表し、 修正を当てた版を提供した（勧告 SNWLID-2026-0017）。 **原因は「意図しない代替アクセス経路」（CWE-441）で、 これを通ると認証を経ずにアプライアンス自身にリクエストを発行させ、 内部機能へ到達して不正な操作を行える**（ベンダーの記述。原文英語）。 同じ勧告で、管理者として認証済みの場合に成立する **OS コマンドインジェクション CVE-2026-102256（7.8）**、管理コンソール（AMC）の **Zip Slip CVE-2026-102257（7.2）**、 **格納型 XSS CVE-2026-102258（6.1）** も公表された。 **SonicWall は「本リリースで修正したどの脆弱性についても、 実際に悪用されている証拠は現時点でない」としている**（原文英語）。 **一方で SMA1000 は2026年に入って2度、実際にゼロデイとして悪用されている** （7月の CVE-2026-15409 / 15410、9月の CVE-2026-83548 / 83549）。 **Shadowserver はインターネットに露出した SMA1000 を400台以上観測している**（報道）。 **【続報・2026年10月12日】公表から2日後の10月8日、 Defused の囮装置（decoy）に認証を要さない SSRF トラフィックが届いた。** **翌9日には Previdian（旧 KEVIntel）のセンサーも悪用の試行を観測し、 10月9日から10日までに米国の2つの IP アドレスから135回の試行を記録した** （いずれも第三者の観測。出典8〜11）。 **一方、SonicWall は勧告を更新しておらず 「悪用されている証拠はない」という記述が残ったままである**（出典9・11 の指摘）。 **本記録が2026年10月13日に取得した CISA の KEV カタログ（版 2026.10.08）にも CVE-2026-102255 は収載されていない**（本記録が直接確認。出典12）—— **ただしこのカタログ版の公開は10月8日で、悪用の報告（10月9日）より前である** （本記録の注記）。

認証を一切要さずに、VPN ゲートウェイを内部への踏み台にできる欠陥である。 SonicWall は現地時間2026年10月6日、SMA1000 シリーズの勧告 SNWLID-2026-0017 を公表し、 4件の脆弱性を明らかにした。 中心は CVE-2026-102255 —— Appliance WorkPlace インタフェースに「意図しない代替アクセス経路」があり、 これを悪用すると、認証されていない遠隔の攻撃者が アプライアンスに自分の代理でリクエストを発行させ、 内部機能へ到達して不正な操作を行える（ベンダーの記述。原文英語）。 CVSS v3.1 は 10.0（満点）で、ベクタは AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H。 スコープが C（変更あり）になっている点が満点の理由である（本記録の読み）—— アプライアンス自身の権限の外、すなわち内部ネットワーク側へ影響が及ぶ。 同じ勧告で、認証後に成立する OS コマンドインジェクション（7.8）・ Zip Slip（7.2）・格納型 XSS（6.1）も公表された。 SonicWall は悪用の証拠は無いとしている。 ただし本記録が重く見るのは、SMA1000 の来歴である（本記録の評価）—— 2026年に入って2度（7月・9月）、実際にゼロデイとして悪用されており、 7月の件は CISA がランサムウェア集団との関連を指摘している。 CISA の SSVC 判定は「悪用 none・自動化可能 yes・技術的影響 total」で、 自動化可能とされている（出典2）。 【続報】その懸念は2日で現実になった —— 10月8日に Defused の囮装置へ認証不要の SSRF トラフィックが届き、 10月9日からは Previdian のセンサーが悪用の試行を観測、 10日までに米国の2つの IP から135回を記録した（出典8〜11）。 「automatable: yes」という判定の意味が、観測として裏づけられた形である （本記録の評価）。 ただし確認できているのは「試行」までで、 侵害に至った組織の有無は公表されていない（unknowns 参照）。 SonicWall は勧告を更新しておらず、 CISA の KEV にも本記録の確認時点で収載されていない —— 外部の観測が先に動き、ベンダーと当局の記載が追いついていない状態である （本記録の評価）。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は実際の被害事例ではなく、協調公表された欠陥の記録である。** **SonicWall は「本リリースで修正したどの脆弱性についても、 実際に悪用されている証拠は現時点でない」としている**（出典5。原文英語）。 **CISA の SSVC 判定も「exploitation: none」である**（出典2）。 **本記録が連鎖として書くのは、公表された技術的条件から導ける経路までであり、 実際に観測された攻撃ではない。** **ただし CISA は同じ判定で「automatable: yes（自動化可能）」 「technicalImpact: total」としている**（出典2）—— **成立に認証も利用者の操作も要らないため、 露出している機器を一括して試す形の攻撃が成り立つという判断である** （本記録の読み）。 **本記録が連鎖の起点を「偵察」に置いたのは、 SMA1000 が性質上インターネットに面しているためである**（本記録の整理）—— **VPN ゲートウェイは、探す必要がない。既に見えている。**

  1. 1. 偵察
    **攻撃者は、インターネットに露出した SMA1000 を探す** （本記録が公表された技術的条件から導いた経路。 本件についてそのような探索が行われたかは公表されていない）。 **SMA1000 は社外から社内へ接続させるための装置であり、 設計上インターネットに面している**（本記録の一般的理解）。 **Shadowserver は400台を超える露出を観測しているとされる**（出典5）。 **機種の判別は `WorkPlace` のログイン画面から可能である** （本記録の一般的理解。公表資料は指紋の取り方に触れていない）。
  2. 2. 初期侵入
    **CVE-2026-102255 の経路** —— **`Appliance WorkPlace` インタフェースに存在する 「意図しない代替アクセス経路」を通る。** **SonicWall の記述**（原文英語。出典2・5）—— **「この経路を悪用することで、認証されていない遠隔の攻撃者が、 アプライアンスに自分の代理でリクエストを発行させ、 内部機能へ到達して不正な操作を行えるおそれがある」。** **CWE は 441（意図しない代替経路）と 918（SSRF）の2つ**（出典2）。 **認証も利用者の操作も要らない（PR:N・UI:N）。**
  3. 3. 内部探索
    **SSRF が成立した後、攻撃者はアプライアンスを代理として 内部の機能・資産を探る**（本記録が CWE-918 の性質から導いた一般的な経路。 本件で何に到達できるかは公表されていない）。 **SonicWall の記述にある「内部機能へ到達し、不正な操作を行う」が これに当たる**（出典2。原文英語）。 **CVSS のスコープが C（変更あり）であることが、 影響がアプライアンスの外へ及ぶことを示している**（本記録の読み）。

    **認証後の経路として、2つの実行手段が同じ勧告で公表されている** （本記録の整理。これらは SSRF とは独立した欠陥である）—— **①CVE-2026-102256** —— **管理者として認証済みの遠隔の攻撃者が、 特定の条件下で任意の OS コマンドを実行しうる（CVSS 7.8）。** **②CVE-2026-102257** —— **管理コンソール（AMC）の Zip Slip。 細工した書庫で本来の展開先の外へファイルを展開でき、 コード実行につながる（7.2）。** **公表資料は、これらと CVE-2026-102255 の連鎖には言及していない** （本記録が確認）。

認証の前に、アプライアンス自身を内部への代理人に変える経路があった原因・手口

中心は CVE-2026-102255 である。

SonicWall の記述（出典2。採番元が登録した説明文。原文英語の訳）—— 「SMA1000 の Appliance Work Place インタフェースに、意図しない代替アクセス経路に起因する認証前の SSRF 脆弱性が存在する。この経路を悪用することで、認証されていない遠隔の攻撃者が、アプライアンスに自分の代理でリクエストを発行させ、内部機能へ到達して不正な操作を行えるおそれがある」。

CWE は2つ挙げられている（出典2）—— CWE-441（意図しない代替経路）と CWE-918（SSRF）。

この2つの並びが本件の構造を表している（本記録の読み）。

段 何が起きているか CWE
1 本来意図されていない入り口が存在した 441
2 その入り口を通ると、装置が攻撃者の代理としてリクエストを出す 918

CVSS v3.1 は 10.0（満点）で、ベクタはAV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H（出典2）。

満点になる要因を分解する（本記録の読み）——

  • PR:N・UI:N —— 認証も、誰かに操作させることも要らない。
  • AC:L —— 特別な条件が要らない。
  • S:C（スコープ変更あり） —— 影響が脆弱な部品の権限境界を越える。 本件では「アプライアンス自身」ではなく「その先の内部側」に及ぶ。
  • C:H / I:H / A:H —— 機密性・完全性・可用性のいずれも高い影響。

この S:C が本件を理解する鍵である（本記録の評価）—— SSRF の価値は、装置が到達できる範囲の広さで決まる。 SMA1000 は「社外から社内へ入れるための装置」なので、到達範囲はそのまま社内である。

同じ勧告の残り3件は性格が違い、効く対策も違う原因・手口

勧告 SNWLID-2026-0017 で公表されたのは4件である（本記録が NVD で照合して確認。出典2・3・4・6）。

CVE 内容 CVSS v3.1 認証
CVE-2026-102255 WorkPlace の認証前 SSRF（CWE-441 / 918） 10.0 不要
CVE-2026-102256 OS コマンドインジェクション 7.8 管理者として認証済み
CVE-2026-102257 AMC の Zip Slip（展開先の外へ書き出せる） 7.2 高い権限が必要

本記録が分けて扱うべきと考える理由（本記録の評価）——

① 残り3件には、認証を固める対策が効く。 管理者アカウントの多要素認証、管理コンソール（AMC）への到達経路の限定、管理操作の送信元の制限が、いずれも直接効く。

② CVE-2026-102255 にはそれらが一切効かない。 WorkPlace は利用者が使うインタフェースであり、公開しないという選択肢が無い。 認証の前で成立するので、認証側の対策も届かない。

③ したがって「勧告が1つ出たから1つの対応をする」では足りない。 AMC の露出を絞る作業と、修正版を当てる作業は別であり、前者をやっても CVE-2026-102255 は残る（本記録の整理）。

なお CVE-2026-102256 には記述の不整合がある（discrepancies 参照）—— 説明文は「遠隔の認証済み攻撃者」としているのに、CVSS ベクタは AV:L（ローカル）である。 CVSS を機械的に取り込んで優先度を決めている組織では、この1件の優先度が実態より低く出る可能性がある（本記録の指摘）。

「悪用の証拠はない」は、この製品の来歴と合わせて読む必要がある評価・解釈

ベンダーの記述（出典5。BleepingComputer が勧告から引用。原文英語）—— 「本リリースで対処したいずれの脆弱性についても、実際に悪用されているという証拠は現時点でない」。

CISA の SSVC 判定も exploitation: none である（出典2）。

ここまでは事実である。 以下は本記録の評価である。

同じ判定の残り2項目を併せて読む（出典2）——

項目 値 意味
exploitation none 悪用は観測されていない
automatable yes 偵察から実行までを自動化できる
technicalImpact total 技術的影響は全面的

automatable: yes は、認証も利用者の操作も要らないことの帰結である（本記録の読み）—— 露出している機器を一括して試す形の攻撃が成り立つ。 つまり「狙われるかどうか」が標的としての価値ではなく、「露出しているかどうか」で決まる。

次に、この製品の来歴を置く（出典5。本記録は原典を取得していない。discrepancies 参照）——

  • 2026年7月 —— SMA1000 のゼロデイ2件（CVE-2026-15409 / 15410）が数週間にわたり悪用され、独自のマルウェア（Sou5・OrangeTail・RootRun）が仕込まれた。CISA はこれをランサムウェア集団と関連づけたとされる。
  • 2026年9月 —— 新たなゼロデイ2件（CVE-2026-83548 / 83549）を連鎖させたコード実行が警告された。
  • 過去4年 —— SonicWall の脆弱性19件が CISA の悪用脆弱性リスト（KEV）に追加され、うち13件はランサムウェア攻撃でも悪用された。

本記録の評価 —— 「現時点で悪用の証拠がない」ことと「悪用されにくい」ことは別である。 同じ年に2度、同じ製品系列がゼロデイとして使われている。 さらに9月の事例は SSRF とコマンドインジェクションの連鎖であり、本件の4件と型が重なる（本記録の指摘）。

実務上の結論（本記録の評価）—— 本件の対応を「悪用が確認されたら急ぐ」という条件つきで待機させる判断は、この来歴の下では取りにくい。

本記録がこれを記録として残す理由（本記録の評価）——

① 脆弱性情報の自動処理に影響する。 CVE レコードから影響範囲は取れるが、「どの版へ上げればよいか」は取れない。 資産管理の仕組みで「対応済み」を機械的に判定しようとすると、この1項目が人手に戻る。

② 緊急対応の時間に効く。 深夜や休日に対応する場面で、勧告ページをブラウザで開ける環境が必要になる。

③ 記録としての再現性が落ちる。 JavaScript で描画されるページは、後から内容が変わっても差分が追えない（本記録の指摘）。

実務上は、SonicWall の勧告ページ（SNWLID-2026-0017）をブラウザで直接参照して版番号を確認する必要がある（本記録の注記）。

SSRF の深刻さは装置の到達範囲で決まり、VPN ゲートウェイは最悪の位置にある評価・解釈

本記録が本件から引き出す一般的な論点（本記録の評価）—— 「SSRF の影響は欠陥の難易度ではなく、その装置がどこへ届くかで決まる」。

CVSS が満点になった直接の理由はスコープが C であることだが、スコープが C になるのは装置の設置位置の帰結である（本記録の読み）。

SMA1000 の位置づけを整理する（本記録の整理。出典5 の「政府機関・MSSP・大企業が内部アプリや社内ネットワークへのVPN 接続を提供するために使う」という記述に基づく）——

  • 外側 —— インターネットに面している（公開が前提）。
  • 内側 —— 社内アプリケーション・社内ネットワークへ到達できる（到達できることが製品の機能である）。
  • 認証 —— 本来は「外から内へ」の通過を制御する装置である。

SSRF は、この3つ目を迂回して1つ目から2つ目へ直接つなぐ（本記録の整理）—— 装置の機能そのものを、認証を経ずに使う形になる。

ここから出る設計上の問い（本記録の評価）——

① 境界装置から内部側への通信を、宛先・ポートで絞っているか。 多くの構成では、VPN ゲートウェイは内部ネットワークの平坦な位置に置かれ、広く到達できる。 絞っておけば、同じ欠陥でも得られるものが減る。

② 内部システムは、送信元が境界装置であることを信頼の根拠にしていないか。 SSRF で来る通信の発信元は、正規のゲートウェイである。 送信元 IP での判定は効かない。

③ 境界装置の侵害を前提にした検知を持っているか。 装置上のログは、コード実行まで到達されれば信頼できない。 外部へ転送していないと、事後の調査もできない。

①〜③はいずれも本件の公表資料に書かれていない（本記録の評価による追加）—— ベンダーが示したのは「更新せよ」の1点である。 それは正しいが、次の脆弱性が出るまでの備えにはならない。

  2. 認証を一切要さない（PR:N / UI:N）。

layer 0 は攻撃者——認証情報も利用者の操作も要らない（PR:N / UI:N）。 layer 1 はインターネットに面した SMA1000 の2つのインタフェース—— 利用者向けの WorkPlace（公開が前提）と管理用の AMC。 layer 2 は欠陥——WorkPlace 側の意図しない代替アクセス経路（CWE-441）と そこから成立する SSRF（CWE-918）。CVSS v3.1 10.0・スコープ C。 AMC 側には認証後の3件（OS コマンドインジェクション 7.8・Zip Slip 7.2・ 格納型 XSS 6.1）が並ぶが、いずれも管理者としての認証を要する。 layer 3 は迂回されるもの——WorkPlace の認証。点線で示す。 layer 4 は到達先——アプライアンスが代理として発行するリクエストが 内部機能・社内アプリケーション・社内ネットワークへ届く。 内部側から見た発信元は正規のゲートウェイであり、送信元 IP での判定が効かない。 layer 5 は対処——修正版（版番号は本記録で確定できず）、 内部側への到達範囲の限定、AMC の露出の削減、監査ログの外部転送。 影響を受ける版は 12.4.3-03526 以前と 12.5.0-02952 以前。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 境界装置の脆弱性は「狙われるか」ではなく「露出しているか」で決まる
    **CISA の SSVC 判定は `automatable: yes`（自動化可能）である**（出典2）。 **認証も利用者の操作も要らないため、 露出している機器を一括して試す攻撃が成り立つ**（本記録の読み）。 **Shadowserver は400台を超える露出を観測しているとされる**（出典5）。 **「うちは小さいので狙われない」という判断が、 この型の脆弱性では成立しない**（本記録の評価）。
    取るべき行動 **自組織がインターネットに露出している機器の一覧を持ち、 各機器について「製品名・版・最終更新日・更新の責任者」を記録する。** **一覧の更新を四半期ごとではなく、 構成変更のたびに行う工程として組み込む。** **外部から自組織の露出を確認する仕組み （外形監視・ASM）を持っていない場合は、導入の可否を判断する。**
  • 「悪用の証拠はない」を、対応を遅らせる根拠に使わない
    **SonicWall は本件について悪用の証拠はないとしている**（出典5）。 **しかし同じ製品系列は2026年の7月と9月に、 実際にゼロデイとして悪用されている**（出典5。本記録は原典未取得。 discrepancies 参照）。 **7月の件は CISA がランサムウェア集団との関連を指摘したとされ、 過去4年で SonicWall の脆弱性19件が KEV に入り、 うち13件はランサムウェア攻撃でも使われた**（出典5）。 **9月の事例は SSRF とコマンドインジェクションの連鎖で、 本件の4件と型が重なる**（本記録の指摘）。
    取るべき行動 **リモートアクセス製品の緊急更新について、 「悪用が確認されてから対応する」という運用を見直す。** **判断基準を「悪用の有無」ではなく 「認証を要するか」「露出しているか」に置き換える。** **具体的には、認証不要かつ外部露出ありの脆弱性は 悪用の有無にかかわらず最優先とする基準を文書化する。**
  • 境界装置が内部のどこまで届くかを、経営として把握しておく
    **本件の CVSS が満点になった直接の理由はスコープが C （影響が権限境界を越える）であることだが、 それは装置の設置位置の帰結である**（本記録の読み。出典2）。 **SSRF の被害は「装置が到達できる範囲」で決まる**（本記録の整理）。 **VPN ゲートウェイは内部ネットワークへ広く到達できる位置に 置かれていることが多い**（本記録の一般的理解）。
    取るべき行動 **リモートアクセス装置から内部側へ到達できる範囲 （宛先・ポート）を図にして確認する。** **「この装置が乗っ取られたら、どこまで届くか」を 1枚で答えられる状態にする。** **範囲が広すぎる場合は、装置を内部ネットワークの平坦な位置から 前段のセグメントへ移す設計変更を検討する。**
  • 1つの勧告に載った脆弱性でも、効く対策が違うことを前提に対応を分ける
    **勧告 SNWLID-2026-0017 の4件のうち、 CVE-2026-102255 だけが認証を要さず、残り3件は管理者としての 認証を前提とする**（本記録が NVD で照合。出典2・3・4・6）。 **管理者アカウントの多要素認証や管理コンソールの露出削減は 残り3件に効くが、中心の1件には一切効かない**（本記録の整理）。 **「勧告を1つ受け取ったので1つ対応した」では 最も深刻な1件が残る**（本記録の評価）。
    取るべき行動 **脆弱性対応の記録を、勧告単位ではなく CVE 単位にする。** **各 CVE について「認証の要否」「対象インタフェース」 「適用した対策」を記録し、 対策と CVE の対応関係が追える形にする。** **緩和策で済ませた CVE には、恒久対策の期限を併記する。**
  • 緊急更新の引き金を「KEV 収載」から「露出・認証不要・自動化可能」へ移す
    **【続報】本件は、指標を待つ運用がどれだけ遅れるかを実測で示した** （本記録の評価）。 **公表（10月6日）の2日後に悪用の試行が観測されたのに対し**（出典8・11）、 **本記録の確認時点（10月13日）でも CISA の KEV には未収載、EPSS は 0.5%、 SSVC は `exploitation: none` のままである**（出典2・8・12。本記録が確認）。 **ベンダーの勧告も「悪用の証拠はない」から更新されていないと報じられている** （出典11）。 **つまり、どの公的指標も「まだ安全」と読める状態のまま、 現実には外から叩かれていた。**
    取るべき行動 **緊急更新の発動条件を文書化し、KEV 収載や EPSS の値から切り離す。** **本記録が本件から取り出した条件は4つ** —— **①インターネットに露出している、②認証を要さない、 ③影響が装置の外に及ぶ（CVSS の `S:C`）、 ④同じ製品が過去に実際に悪用されている。** **この条件に当たる勧告が出たときの目標時間を決める （本記録は「48時間以内」を目安として示す）。** **決めた時間を、運用委託先との契約にも書き込む。**
