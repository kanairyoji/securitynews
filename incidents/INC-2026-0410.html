INC-2026-0410Ninja Forms ほかXSS悪用で4系統の裏口

WordPress プラグイン Ninja Forms（CVE-2026-94504・3.15.3 以前）と WPC Product Bundles for WooCommerce（CVE-2026-93836・8.6.6 以前）の格納型XSSが実地で悪用され、管理者の画面で実行された JavaScript が偽プラグイン「WP Smart Thumbnails」を導入して4系統の裏口を作る——Patchstack が10月4日と5日に同一の攻撃者による活動として観測した。Ninja Forms の修正版は観測の14日前に出ていた

脆弱性脅威・攻撃キャンペーン続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備既知の脆弱性の悪用脆弱性の放置
初報: 2026年10月6日 最終更新: 2026年10月7日

WordPress プラグインの格納型XSSが、実地で裏口の設置に使われた。 WordPress セキュリティのベンダーである Patchstack は2026年10月6日、2つの無関係なプラグインの格納型XSSを悪用する攻撃を観測したと公表した。

  • WPC Product Bundles for WooCommerce（CVE-2026-93836・8.6.6 以前・導入3万サイト超）への悪用を10月4日に観測
  • 翌10月5日、Ninja Forms（CVE-2026-94504・3.15.3 以前・導入50万サイト超）への同一の活動を観測

どちらも同じドメイン（imgcdn1[.]com）から同じ JavaScript（/fz/x.js）が配られており、同一の攻撃者とみられる。このドメインは2026年10月1日に登録されている。

攻撃の形が、脆弱性の分類から受ける印象と違う。格納型XSSは「サイトの見た目が書き換わる」程度に受け取られがちだが、本件で起きたのは管理権限の恒久的な奪取である。攻撃者は認証なしで注文データや問い合わせの送信内容に JavaScript を仕込む。ログイン中の管理者がその内容を管理画面で開いた瞬間、スクリプトは管理者のセッションで動く。 Cookie は盗まれない——盗む必要がない。スクリプトはプラグイン導入用の nonce を取得し、「WP Smart Thumbnails」1.2.4（作者名「MediaPress Labs」）を名乗る偽プラグインを導入し、管理者アカウントを作る。

残されるのは4系統の裏口である。

  1. 管理画面から見える管理者アカウント（認証情報はC2が指定）
  2. 管理画面の一覧に表示されない隠し管理者（must-use プラグインで非表示化）
  3. マジックログインURL（サイト最古の管理者としてログインできる）
  4. プラグイン内の認証なしファイルマネージャー

偽プラグインを削除しても 3 と 4 は残る。 永続化の部品は must-use プラグインとして別に置かれ、ファイルの日時は偽装されている。Patchstack は「侵害の判定は更新日時ではなく内容で行え」としている。

観測規模は限定的だが継続している。送信元IPは5件確認され、うち4件は Tor の出口ノードである。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

認証なしで保存できる入力に仕込まれた格納型XSSが、管理者の管理画面で管理者のセッションごと 実行され、WordPress の正規の機能で偽プラグインの導入と管理者アカウントの作成に至る。 最後に must-use プラグインで4系統の裏口を残し、偽プラグインを削除しても2系統が生き残る

  1. 1. 初期侵入確認済
    攻撃者が**認証なしで**、WooCommerce の注文データまたは Ninja Forms の送信内容に 悪意ある JavaScript（x.js の読み込み）を保存する。この時点では何も起きない。 **保存された文字列は、管理者が管理画面で開くのを待つ**
    根拠: Patchstack の記事（両プラグインの格納型XSS・CVE-2026-93836／CVE-2026-94504）
  2. 2. 実行確認済
    **ログイン中の管理者が当該内容を管理画面で開く**と、 `https://imgcdn1.com/fz/x.js` が**管理者のセッションの中で実行される**。 Patchstack は「Cookie は盗まれず、管理者のセッションを流用する」と明記している
    根拠: Patchstack の記事（攻撃の流れ 1.）
  3. 3. C2通信確認済
    スクリプトは攻撃者のサーバー（`/fz/c.php`）に対象サイトの状態を問い合わせ、 **すでに処理済みの段階を判定する**。最後に実行結果をC2へ送信する
    根拠: Patchstack の記事（攻撃の流れ 2. および 6.）
  4. 4. 権限昇格確認済
    スクリプトは管理者のセッションを使って**プラグインのアップロード用 nonce を取得**し、 WordPress の正規の機能で偽プラグイン **「WP Smart Thumbnails」1.2.4（作者名「MediaPress Labs」・スラッグ wp-smart-thumbnails）** を導入する。続いて**管理者の権限で管理者アカウントを作成**する （認証情報はC2が指定したもの）
    根拠: Patchstack の記事（攻撃の流れ 3. および 4.）
  5. 5. 永続化確認済
    `emer-run.php` を実行し、**①管理画面から見える管理者アカウント ②管理画面の一覧に表示されない隠し管理者（must-use プラグインで非表示化） ③サイト最古の管理者としてログインできるマジックログインURL ④認証なしのファイルマネージャー**の4系統を設置する。 部品は `wp-content/mu-plugins/` に `class-wp-token-validate.php`・ `class-wp-query-<8桁16進>.php` として置かれ、**ファイルの日時は偽装される**。 **偽プラグインを削除しても ③ と ④ は残る**
    根拠: Patchstack の記事（攻撃の流れ 5.・永続化の4つの経路）
  6. 6. 検知回避確認済[1]
    隠し管理者は must-use プラグインによって 「ユーザー → ユーザー一覧に表示されず、管理者フィルタにも現れず、 一覧の上の合計数にも数えられない」状態にされる（Patchstack・原文英語）。 永続化の部品は**日時を過去に偽装**して置かれる
    根拠: Patchstack の記事（隠し管理者の説明・日時の偽装）

認証なしで保存した文字列が、ログイン中の管理者のブラウザで管理者の権限ごと動いた原因・手口

格納型XSSは、本件では「管理権限の奪取」として実現した。

両脆弱性に共通するのは、攻撃者が認証なしに保存できる場所（WooCommerce の注文データ、Ninja Forms の送信内容）に入れた文字列が、管理画面に出力されるときエスケープされていなかったことである。Ninja Forms 3.15.4 の変更履歴に「strengthen output escaping in admin submission edit screen」（管理画面の送信内容編集画面における出力エスケープの強化／原文英語）とあり、出力側の不備であったことは提供元自身の記述から読み取れる。

攻撃の成立には管理者がその内容を管理画面で開くことが要る。そこで何が起きるか。

  • スクリプトは https://imgcdn1.com/fz/x.js から読み込まれ、ログイン中の管理者のセッションの中で実行される
  • Cookie は盗まれない。 盗む必要がない。スクリプトは管理者の画面の中にいるため、管理者ができることを直接行える
  • プラグイン導入用の nonce を取得し、WordPress の正規の機能を使って偽プラグインを導入する

ここが本件の要点である。WordPress の管理画面を狙うXSSは、セッションを外に持ち出す攻撃ではなく、管理者の手を借りて正規の操作を行わせる攻撃になる。多要素認証は入口を守るが、すでにログインしている管理者の画面の中で動くスクリプトは多要素認証を通り抜ける（本記録の評価）。

偽プラグインを削除しても2系統の裏口が残る——日時が偽装されているため、更新日時では侵害を判定できない被害規模・影響範囲

導入される偽プラグインは 「WP Smart Thumbnails」バージョン1.2.4、作者名 「MediaPress Labs」、スラッグ wp-smart-thumbnails である。スクリプトは続いて emer-run.php を実行し、永続化の部品を置く。

残るのは4系統である。

# 裏口 偽プラグイン削除後
1 管理画面から見える管理者アカウント（認証情報はC2が指定） 消える（見えるので気づける）
2 管理画面の一覧に表示されない隠し管理者 残る
3 マジックログインURL（サイト最古の管理者としてログイン） 残る
4 プラグイン内の認証なしファイルマネージャー 削除で消える

Patchstack によれば、プラグインを削除しても 3 と 4 の経路は残る。永続化の部品は must-use プラグインとして wp-content/mu-plugins/ にclass-wp-token-validate.php や class-wp-query-<8桁の16進数>.php の名前で置かれる。must-use プラグインは管理画面から無効化できない。

隠し管理者について、Patchstack はこう書いている——「そのアカウントは ユーザー → ユーザー一覧 に表示されず、管理者フィルタにも現れず、一覧の上に出る合計数にも数えられない。サイト所有者が見ることのできない、完全な権限を持つ管理者である」（原文英語）。

侵害の判定を更新日時で行ってはいけない。 置かれるファイルの日時は過去に偽装されている。Patchstack は「日時ではなく内容で確認せよ」としている。

修正版は観測の14日前に出ていた——踏まれたのは「まだ直っていない脆弱性」ではない評価・解釈

本件で見落としてはいけないのは、攻撃が始まったとき修正版はすでにあったことである。

  • Ninja Forms 3.15.4 の公開は 2026年9月21日
  • Patchstack が Ninja Forms への悪用を観測したのは 10月5日
  • 差は 14日（本記録の作成者による算出）

つまり踏まれたサイトが抱えていたのはゼロデイではなく、2週間前に修正版が出ていた既知の脆弱性である。配信元ドメイン imgcdn1[.]com の登録は 10月1日で、修正版の公開より後である。これは攻撃者が公開された修正の内容から攻撃可能な箇所を知って準備した可能性を示す（本記録の推定。Patchstack はこの点に言及していない）。

WPC Product Bundles 側については同じことが言えない。 8.6.7 の公開日が変更履歴に記載されておらず、本記録の作成者も確認できなかった。片方で成り立った推論をもう片方にも当てはめないため、unknowns に残した。

なお両提供元の修正の記述は変更履歴の中にのみあり、独立したセキュリティ勧告は見つけられなかった。WPC 8.6.7 の記述は「Fixed: Vulnerability reported by lhking from Wordfence」の一行である。変更履歴の一行を読まないと、自分が緊急に上げるべき更新なのか判断できない。

脆弱性の「認証の要否」をめぐって報道と登録情報が食い違っている未確定事項

同じ2つの脆弱性について、資料の記述が揃っていない。

  • Patchstack は両方を 「認証不要の格納型XSS」（unauthenticated stored XSS）として記載している
  • BleepingComputer は「どちらも高い深刻度の評点を受け、悪用には認証済みのセッションが必要である」と書いている
  • Patchstack のデータベース側の記述は CVSS 7.1 で、「悪用の成功には特権を持つ利用者の操作（悪意あるリンクのクリックやフォームの送信等）が要る」と説明している

これは同じ事実の別の面を指していると本記録は読む（本記録の評価）。投入（保存）は認証なしでできる。実行には管理者が管理画面で開く操作が要る。「認証が必要」を「攻撃者がログインできなければ成立しない」と読むと、対処の緊急度を下げる判断につながりかねない。攻撃者側に認証は要らない。

修正版の番号についても、Patchstack のデータベース内でNinja Forms の修正版を 3.15.4 とするものと 3.15.5 とするものがある。本記録は記事側の記述（3.15.4 以降）を採り、discrepancies に残した。

緩和策
数え方: Ninja Forms を 3.15.4 以降に、WPC Product Bundles for WooCommerce を 8.6.7 以降に更新する　副作用: **更新は以後の悪用を防ぐだけで、すでに入られたサイトは掃除されない** （Patchstack・BleepingComputer がともに明記している）。 「更新したから終わり」と判断すると、2系統の裏口が残る
数え方: HTTPログで imgcdn1[.]com・/fz/x.js・/fz/c.php を検索し、 wp-login.php への _wplogin パラメータ付きのアクセスを探す　副作用: ログの保持期間が短いと確認できない。初観測は10月4日である
数え方: wp-content/plugins/wp-smart-thumbnails/ の有無と、wp-content/mu-plugins/ の class-wp-token-validate.php・class-wp-query-<8桁16進>.php の有無を、 **更新日時ではなく内容で**確認する　副作用: 日時が偽装されているため、更新日時での選別は空振りする。 内容確認は手作業になりやすい
数え方: データベースで管理者を直接列挙し、管理画面の一覧と**突き合わせる**。 wp_options に残る実行済みの印とマジックログイン用トークンの2項目 （値は detail.indicators に記載）の有無を確認する　副作用: 隠し管理者は管理画面に出ないため、管理画面だけを見ていると 「異常なし」と読めてしまう
数え方: 不正なアカウントと偽プラグインを削除し、mu-plugins の該当ファイルを消去し、 上記2つの option を削除する　副作用: **mu-plugins を消さずに option だけ消すと、新しいトークンが再発行されうる** （Patchstack の記述）。順序を誤ると掃除が完了しない
数え方: 特権アカウントの認証情報を更新し、WordPress の認証用ソルトを再生成する。 **サイト最古の管理者のパスワードは、直接盗まれていなくても侵害されたものとして扱う**　副作用: ソルトの再生成は全利用者のログインセッションを失効させる。 会員サイトでは利用者からの問い合わせが増える

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
認証なしで保存した文字列が、管理者の画面を経由して4系統の裏口に至る経路
layer 0 は攻撃者と配信基盤（imgcdn1[.]com・2026年10月1日登録）。 layer 1 は認証なしで保存できる投入口（WooCommerce の注文データ／Ninja Forms の送信内容）。 layer 2 は**管理者のブラウザ**——ここで管理者のセッションごとスクリプトが動く。 layer 3 は正規の機能を使って置かれる偽プラグインと作成される管理者。 layer 4 は残される4系統の裏口で、**太字の2つは偽プラグインを削除しても残る**。 **検知の機会が最も素直に残るのは layer 3（プラグイン導入と管理者作成）であり、 layer 4 に到達すると管理画面という観測面そのものが汚染される。** 攻撃者の実体・最終目的・被害サイト数は公表されていない。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入機会はあったが検知できず
投入そのものは正規のフォーム送信・注文として届くため、 入力の時点での検知は難しい（本記録の評価）。 ただし送信内容に `<script>` や外部ドメインのURLが含まれることは 機械的に判定できる性質のものである
侵入を防げた　Ninja Forms については**悪用の観測の14日前に修正版が出ていた**。 本件で最も効いたはずの対策である
侵入を防げた　本記録の判断。出力側のエスケープが抜けていても、 保存側で落としていれば管理画面で実行されない
実行機会はあったが検知できず
管理画面から外部ドメインへの JavaScript 読み込みが発生する。 **コンテンツセキュリティポリシーがあればここで止まる**が、 WordPress の管理画面に CSP を敷いている運用は多くない（本記録の評価）
侵入を防げた　本記録の判断。外部ドメインからのスクリプト読み込みを拒めば、 格納型XSSが保存されていても実行に至らない
影響を限定できた　本記録の判断。管理者セッションを持つブラウザで不要な内容を開かない運用にする
C2通信機会はあったが検知できず
管理者のブラウザから imgcdn1[.]com への通信が発生する。 **ドメインは2026年10月1日に登録されており、新規登録ドメインへの通信は それ自体が検知の手がかりになる**（本記録の評価）
検知できた　本記録の判断。imgcdn1[.]com は悪用の3日前に登録されている。 この種の使い捨てドメインに対して効く
検知できた　本記録の判断
権限昇格機会はあったが検知できず
プラグインの新規導入と管理者アカウントの新規作成は、 **どちらも通常は人が意図して行う、頻度の低い操作**である。 ここは検知の機会として最も素直な位置にある（本記録の評価）
侵入を防げた　本記録の判断。**管理者のセッションを奪われても、 管理画面からプラグインを置けなければこの段階で止まる**。 本件の連鎖を断つ最も効く一手である
検知できた　本記録の判断。見える側の管理者アカウント（裏口1）はここで露見する
永続化機会はあったが検知できず
**管理画面を見るだけでは検知できない。** 隠し管理者は一覧・フィルタ・ 合計数のいずれにも現れない。must-use プラグインは管理画面から無効化もできない。 検知するにはデータベースの直接列挙とファイルシステムの確認が要る（Patchstack の手順）
検知できた　本記録の判断。本件は日時を偽装するため、 日時ベースの監視では検出できない
検知できた　Patchstack が公表した確認手順。隠し管理者はこの突き合わせでのみ見える
復旧を早められた　Patchstack の記述による。**option だけ消すと新しいトークンが 再発行されうる**ため、順序が結果を変える
検知回避現実的な検知機会なし
**管理画面という観測面そのものが汚染されている**ため、 その面の中に現実的な検知機会はない（本記録の評価）。 観測を管理画面の外（データベース・ファイルシステム・HTTPログ）へ 出さない限り見えない
検知できた　本記録の判断。**「管理画面で見て異常がない」は本件では無意味である**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「プラグインの脆弱性」を軽い分類として扱っていると、 本件の形（管理権限の恒久的な奪取）を取り違える
    2件とも格納型XSSであり、評点は CVSS 7.1 である。 しかし実際に起きたのは、偽プラグインの導入・管理者アカウントの作成・ 4系統の裏口の設置であり、**うち2系統は偽プラグインを削除しても残る**
    取るべき行動 公開サイトで使っているプラグインの一覧と版を台帳にし、 **「管理画面に利用者の入力を表示するプラグイン」に印を付ける**。 この種のプラグインのXSSは管理権限の奪取と同じ重さで扱うと決め、 更新の緊急度の基準に書き込む
  • 修正版が2週間出ていた。本件で問われたのは脆弱性の発見速度ではなく、 自社が更新を適用する速度である
    Ninja Forms 3.15.4 の公開は2026年9月21日、悪用の観測は10月5日で、 差は14日である（本記録の作成者による算出）。 配信元ドメインの登録は10月1日で、修正版の公開より後である
    取るべき行動 公開サイトのプラグイン更新について、**適用までの目標日数を決めて実測する**。 「更新している」ではなく「公開から何日で当たっているか」を数字で持つ。 本件の14日が自社の実績より短いか長いかを、この四半期のうちに確認する
  • 「更新したから対処済み」という報告を受け取ってはいけない。 更新は以後の悪用を止めるだけで、すでに入られたサイトは掃除されない
    Patchstack と BleepingComputer がともに 「更新は以後の悪用を防ぐが既存の感染は除去しない」と明記している。 さらに偽プラグインの削除でも2系統の裏口が残る
    取るべき行動 脆弱性対応の完了報告の様式を、**「更新した」と「侵害の有無を確認した」の 2項目に分ける**。後者には確認した面（データベース・ファイル・HTTPログ）を 書かせる。公開サイトの運用を外部に委託している場合は、 この2項目を委託先への指示に入れる
  • 提供元のセキュリティ情報が「変更履歴の一行」しかない部品に依存している、 という状態そのものを把握しておく必要がある
    本記録の作成者が確認した範囲では、両提供元の修正の記述は変更履歴の中にのみあり、 独立したセキュリティ勧告は見つけられなかった。 WPC Product Bundles 8.6.7 の記述は 「Fixed: Vulnerability reported by lhking from Wordfence」の一行で、 **公開日も記載されていない**
    取るべき行動 利用している部品ごとに**「脆弱性情報がどこに出るか」を台帳に書く**。 勧告を出さない提供元のものは、第三者のデータベース （CVE・プラグインのセキュリティサービス等）を監視対象に加える。 情報源が無い部品は、それ自体を調達のリスクとして記録する
セキュリティ技術者への示唆
  • 管理画面のXSSは「セッションの持ち出し」ではなく 「管理者の手を借りた正規操作」として実現する。多要素認証はここに効かない
    Patchstack は「Cookie は盗まれず、管理者のセッションを流用する」と明記している。 スクリプトは管理者の画面の中で nonce を取得し、 WordPress の正規のプラグイン導入機能を使っている
    取るべき行動 管理画面に**コンテンツセキュリティポリシーを設定し、script-src を自サイトに限定する**。 併せて管理作業用のブラウザプロファイルを日常利用から分離する。 「多要素認証を入れたので管理画面は安全」という整理を見直す
  • 本番サイトで管理画面からプラグインを導入できる状態が、 この攻撃連鎖の成立条件になっている
    攻撃の中核は、管理者セッションでプラグイン導入用の nonce を取得して 偽プラグインを置くことである。導入ができなければ、 以降の管理者作成・4系統の永続化には進めない
    取るべき行動 `wp-config.php` で `DISALLOW_FILE_MODS` を有効にし、 プラグインの導入・更新は配備の仕組みを通す構成にする。 **この1点で本件の連鎖は権限昇格の段階で止まる**（本記録の判断）
  • 侵害の判定を更新日時で行うと空振りする。本件は日時を偽装する
    Patchstack は、永続化のファイルが**日時を偽装して**置かれるため 「更新日時ではなく内容で確認せよ」としている
    取るべき行動 `wp-content/mu-plugins/` を含めたファイルの完全性監視を、 **ハッシュで**比較する方式に変える。 `class-wp-token-validate.php`・`class-wp-query-<8桁16進>.php` の有無を確認し、 `wp-content/plugins/wp-smart-thumbnails/` を探す
  • 管理者の一覧を管理画面で見ても、隠し管理者は見えない。 観測面を管理画面の外へ出す必要がある
    隠し管理者は must-use プラグインによって一覧・管理者フィルタ・ 合計数のすべてから除かれる。must-use プラグインは管理画面から無効化できない
    取るべき行動 **データベースから管理者を直接列挙し、管理画面の一覧と突き合わせる点検**を 定期の作業に入れる。あわせて `wp_options` に残る実行済みの印と マジックログイン用トークンの2項目（値は本記録の痕跡一覧に記載）の有無と、 HTTPログの `imgcdn1[.]com`・ `/fz/x.js`・`/fz/c.php`・`wp-login.php` への `_wplogin` 付きアクセスを確認する
  • 掃除には順序がある。option を先に消すと、裏口が自分を作り直す
    Patchstack は、mu-plugins の部品を残したまま option を削除すると **新しいトークンが再発行されうる**と述べている。 また最古の管理者のパスワードは直接盗まれていなくても 侵害されたものとして扱うよう求めている
    取るべき行動 復旧手順を「①不正アカウントと偽プラグインの削除 → ②mu-plugins の部品の消去 → ③wp_options に残る2項目の削除 → ④特権アカウントの認証情報の更新と 認証用ソルトの再生成」の順で文書化する。 ソルト再生成は全利用者のセッションを失効させるため、周知の文面も用意しておく

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ WordPress で公開サイトを運用しており、管理画面からプラグインの導入・更新ができる状態になっている管理者セッションでのプラグイン導入が、本件の権限昇格と永続化の前提である
システム構成□ 利用者が入力した内容（注文データ・問い合わせ・応募内容）を管理画面に表示する仕組みがある本件の投入口は、認証なしで保存できてかつ管理者が管理画面で開く場所である
運用・監視□ プラグインの更新を、公開から適用までの日数で実測していない本件の Ninja Forms 側は修正版の公開から14日後に悪用が観測されている
運用・監視□ 侵害の点検を管理画面の表示（ユーザー一覧・プラグイン一覧）だけで行っている隠し管理者は一覧・フィルタ・合計数に現れず、must-use プラグインは管理画面から無効化できない
運用・監視□ ファイルの変更監視を更新日時で行っている（ハッシュで比較していない）本件の永続化ファイルは日時を過去に偽装して置かれる
委託・第三者部品□ 使っているプラグイン・テーマについて、脆弱性情報がどこに出るかを把握していない両提供元の修正の記述は変更履歴の一行のみで、WPC 側は公開日も記載がない
