2026年10月8日、JPCERT コーディネーションセンター（JPCERT/CC） は注意喚起「直近で相次いでいる国内組織における不正アクセスに関する注意喚起」（JPCERT-AT-2026-0030）を公表しました。

直近2026年9月前後で、国内組織における不正アクセスによる個人情報等の漏えい被害が相次いでいるという状況を受けたものです。

本記録が中心と見るのは、この注意喚起が「一つの脆弱性への対処」を求めるものではないという点です。JPCERT/CC は明記しています。

一連の攻撃については、一つの共通するソフトウェアの脆弱性を悪用しているのではなく、標的ごとにさまざまな既知の脆弱性有無についてスキャンし、脆弱性を探索して悪用を試行したり、脆弱性ではないものの、機器の管理不備等を悪用した攻撃を試みている可能性があります

つまり 「この CVE を当てれば終わり」という形の対処にならない。整理された攻撃類型は3つです。

内容
ケースA さまざまなソフトウェアの既知の脆弱性を標的ごとに探索し攻撃試行する。脆弱性ではない機器の管理不備（環境設定ファイルやバックアップファイルの窃取）も含む
ケースB API経由での不正な操作。公開アプリを解析してAPIのエンドポイントやキーを特定し、本来画面操作では実行できない内部APIを攻撃する
ケースC Metabase のSQLインジェクションの脆弱性（CVE-2026-72898） の悪用。これもAPIへの不正なリクエストを通じたもの

もう一つ重要な指摘があります。被害に遭っているのは一般利用者向けのアプリだけではありません。

BI（ビジネスインテリジェンス）ツールや従業員向け管理システムなど、管理・運用側で不特定多数の利用者からのアクセスを想定していないシステムが被害に遭い、内部に保存していた情報が漏えいするケースもあります

「外向けではないから対象外」という線引きが成り立たないということです（注意喚起は末尾でも同じ指摘を繰り返しています）。

JPCERT/CC は自ら情報の限界も示しています—— 「技術的な情報の共有が不足しており、把握している情報は限定的かつ断片的であるものの、攻撃被害の拡大等の状況に鑑み」 公表に至ったとし、「すべての事案で同一の攻撃手法が使用されていることを示すものではありません」 と念を押しています。評価・示唆は本記録の判断として分けて書きます。

  • 被害組織名・被害件数・漏えい規模公表されていない
    **注意喚起は個別の組織名を一切挙げておらず、組織数も漏えい件数の概数も示していない。** **「各被害公表や報道のとおり」とあるが、どの公表を指すかも示されていない。** **これは読者が自組織の対処の優先度を測るうえで最も欲しい情報である**（本記録の評価）。 **一方、JPCERT/CC は調整機関として被害組織から情報提供を受ける立場にあり、 件数を出せば情報提供が止まりかねないという制約が考えられる** （本記録の推定であり、JPCERT/CC がそう述べたわけではない）
  • 攻撃者の帰属（国・既知の集団との関係・動機）公表されていない
    **注意喚起は攻撃者について一切述べていない。** **さらに「すべての事案で同一の攻撃手法が使用されていることを示すものではありません」と しており、単一の主体によるものとも述べていない**（本記録の読み取り）。 **したがって本件を「一つのキャンペーン」として扱うことはできない。** 確認されている痕跡は不審な送信元IPアドレス8件とUser-Agentの例のみで、 **それらにも「調査時点では正規利用されている可能性もあります」という但し書きがある**
  • ケースAで悪用された具体的な脆弱性・製品公表されていない
    **「さまざまな既知の脆弱性」「機器の管理不備等」という括りで、 製品名も CVE も例示が無い。** **「環境設定ファイルやバックアップファイルの窃取など」という手口の例のみが示されている。** **読者が何を点検すべきか決めにくい**（本記録の評価）が、 **JPCERT/CC 自身が「把握している情報は限定的かつ断片的」としているため、 これは情報の制約によるものと読める**。 **本注意喚起の性質上、ケースAは「標的ごとに異なる」ことが要点であり、 特定の製品に収束しないこと自体が情報である**（本記録の読み取り）
  • ケースBの被害が生じた製品・実装パターン公表されていない
    **手口は詳しく示されている（（a）アプリ解析、（b）内部API攻撃の4手口、 （c）窃取APIキーの使用）が、 どの製品・どのフレームワーク・どの実装パターンで起きたかは示されていない。** **「NoSQLインジェクション」という記述から、 対象のシステムが NoSQL データベースを使っていたことは読めるが、 製品名は示されていない**（本記録の読み取り）。 **自組織が該当するかの判定は読者側の作業として残る**
  • 漏えいした情報の類型公表されていない
    **「個人情報等」「内部に保存していた情報」という表現にとどまり、 具体的な項目（氏名・連絡先・認証情報・決済情報など）は示されていない。** **ケースBでは「情報の不正な書き換え等が発生している」とされ、 読み出しだけでなく改変も確認されているが、 何が書き換えられたかは示されていない**（本記録の読み取り）。 **汎用的な対策に「漏えい発生時を想定した、平時からの顧客への 二次被害防止等の呼びかけ（多要素認証など）」が挙げられていることから、 認証情報の漏えいが想定されていると読めるが、明示はされていない**
  • ケースCで8月14日の注意喚起が行き渡らなかった理由公表されていない
    **JPCERT/CC は2026年8月14日に CVE-2026-72898 の注意喚起を公表していたが、 約1か月25日後の本注意喚起で、それが実際の漏えい被害に結びついているケースとして 再掲されている。** **さらにケースCで観測されたアクセスは「8月上旬から9月上旬までの間」とされており、 8月14日の注意喚起より前から悪用が始まっていた可能性がある**（本記録の読み取り）。 **本注意喚起はこの点に触れておらず、 注意喚起が行き渡らなかった理由の分析は含まれていない。** **Metabase が BI ツールであり「不特定多数からのアクセスを想定していないシステム」に あたることが、点検対象から外れた一因である可能性はある** （本記録の推定であり、裏付けは無い）
  • 公表された痕跡（IP・User-Agent）の自組織における悪性検証できない

  • ケースD（Webシェル設置）で狙われた製品・侵入の起点公表されていない
    **10月9日の更新で追加されたケースDの記述は 「公開Webサーバーからアクセス可能なアプリケーションサーバー上に Webシェル設置」である**（出典1）。 **公表されていないのは——①公開Webサーバーへの最初の侵入がどう成立したか （ケースAやケースCと同じ経路なのか別なのか）、 ②アプリケーションサーバーの製品・構成、 ③Webシェルの形式・ファイル名・設置場所、 ④設置後に何が行われたか。** **本記録の読み取り** —— **「公開Webサーバーからアクセス可能な」という 限定が付いていることが、この類型の要点である**（本記録の整理）。 **狙われたのは公開サーバー自身ではなく、その背後にあって 外部から直接は見えないアプリケーションサーバーである。** **多層構成にしていることが防御になるという前提が、 ここでは成り立っていない。** **ただし「どう到達したか」が示されていないため、 対処の具体は本記録として書けない。** **推測で埋めない。**
  • 4ケースのそれぞれが何件の被害に対応するのか公表されていない

**本件は「一つの攻撃」ではなく、JPCERT/CC が複数の報告から整理した攻撃類型である。** **したがって以下の段階は、特定の事案の工程を復元したものではなく、 注意喚起が記述した手口を段階に割り当てたものである**（本記録の整理）。 **とくにケースBは、公表された手口の記述がそのまま段階の順序になっている**—— 公開アプリの解析（偵察）→ 内部APIへの試行（初期アクセス）→ 権限変更・不正アカウント作成（権限昇格・永続化）→ NoSQLインジェクションによるブラインド探索（内部探索）→ 情報の漏えいと不正な書き換え（持ち出し・影響）。 **JPCERT/CC 自身が「すべての事案で同一の攻撃手法が使用されていることを 示すものではありません」「把握している情報は限定的かつ断片的」と 留保を付していることを、各段階で踏まえる。** **MITRE ATT&CK への対応づけは注意喚起に無いため、本記録でも付さない** （日本語の記述から機械的に技術IDへ写さないという方針による）。

本注意喚起を読むうえで最も重要なのは、単一の侵入口が無いという点である。JPCERT/CC はケースAの説明で明確に述べている。

一連の攻撃については、一つの共通するソフトウェアの脆弱性を悪用しているのではなく、標的ごとにさまざまな既知の脆弱性有無についてスキャンし、脆弱性を探索して悪用を試行したり、脆弱性ではないものの、機器の管理不備等を悪用した攻撃（環境設定ファイルやバックアップファイルの窃取など）を試みている可能性があります

ここから二つのことが出てくる（本記録の評価）。

第一に、脆弱性管理の仕組みでは捕まらない部分がある。 ケースBには CVE 番号が存在しない——API の設計と権限管理の問題である。ケースAの「機器の管理不備」も脆弱性ではない——環境設定ファイルやバックアップファイルが到達可能な状態は、脆弱性スキャナでは検出されない。 スキャナ・CVE の追跡・パッチ適用率をどれだけ回しても、これらは「対処済み」にならない。

第二に、3ケースのうち2ケースが API を介している。ケースBは定義上 API への攻撃であり、ケースCについても注意喚起は「本脆弱性も、APIへの不正なリクエストを通じて悪用されるものです」 と明記している。JPCERT/CC が対策を「API経由のアクセスへの対策」と「汎用的な対策」の2段に分け、参考情報に OWASP の API Security Top 10 2023 と REST Security Cheat Sheet を挙げているのは、この共通点を踏まえたものと読める（本記録の読み取り）。

ケースBの手口は具体的である。

  • （a）一般公開しているスマートフォンアプリを解析し、APIのエンドポイントやキーを特定する
  • （b）本来画面操作では実行できない内部APIに対する攻撃
  • ユーザー権限を変更する
  • 不正なアカウントを作成する
  • ヘッダーの有無の切り替えや不正な形式の認証トークンの付与による応答の違いを確認する
  • NoSQLインジェクションによるブラインド探索によってアカウント情報を特定する
  • （c）他のシステムの侵害で窃取したAPIキーを使用する

（a）が示しているのは、攻撃の起点が自社の配布物だということである（本記録の評価）。アプリに埋め込んだキーは、配布した時点で秘密ではない。 （b）が示しているのは、画面側の制限が防御にならないということである—— 画面は入口の一つにすぎず、API は直接叩ける。 （c）は横展開の経路である——一つのシステムの侵害が、そこに保管されていたキーを通じて別のシステムの侵害につながる。

なお、ブラインド探索やNoSQLインジェクションの仕組みについての説明は注意喚起には無く、本記録が補足したものである（齟齬の欄に記録した）。

そして末尾でも——

繰り返しになりますが、管理・運用側で不特定多数の利用者からのアクセスを想定していないシステム（従業員向け、BIツールなど）が被害に遭うケースもあります。こうしたシステムについても上記のような点検などを推奨します

同じ文書内で2度書かれる指摘は、読み飛ばされやすいと書き手が判断したものである（本記録の読み取り）。

実際、ケースCの Metabase はまさに BI ツールである。つまりこの指摘は抽象的な注意ではなく、本注意喚起の中に該当例がある。

ここから引ける教訓は、「外向け／社内向け」という区分で点検対象を決めないことである（本記録の評価）。「想定していない」ことは「到達できない」ことを意味しない。設計上の想定と、実際にインターネットから到達できるかは別の話である。

資産台帳を「外向け／社内向け」ではなく「インターネットから到達できるか」で並べ替える——区分ではなく実測で判定する、というのが本記録の推す行動である。

API経由のアクセスへの対策（6項目）

  1. 単位時間あたりのリクエスト件数を制限し、短時間に繰り返されるアクセスや大量実行を防止する
  2. ログイン・パスワードリセット・SMS送信・検索処理などの悪用のリスクが高い機能には個別にレート制限や利用回数制限を設定する
  3. 非公開APIを含む各APIエンドポイントでアクセス制御を実施し、許可された利用者やHTTPメソッドからのアクセスのみを受け付ける
  4. API利用者やAPIトークンには必要最小限の権限のみを付与する
  5. APIトークンには適切な有効期限を設定し、長期間有効なトークンの使用を避ける
  6. 不要となった、または漏えいが疑われるAPIトークンは速やかに無効化できるようにする

汎用的な対策（7項目） — 地域制限／修正済みアップデートの適用／横展開対策の見直し／検知体制と初動対応の見直し／平時からの顧客への二次被害防止の呼びかけ（多要素認証など）／不要な管理機能の公開停止／保存期間を過ぎたデータを残さない

IPA は「特定の製品の脆弱性を狙った攻撃とは断定されていない」と明記した対策・注意喚起

IPA の注意喚起（出典13）には、他の3本には無い一文があります。

「現段階では、特定のプロダクトやサービスの脆弱性を狙った攻撃とは断定されておらず、公表事例の傾向から、外部公開しているアプリケーションやサービスの侵害、アカウントの侵害が起点となっていることがうかがえます」（出典13。原文引用）。

これは「どこを見ればよいか」を名指ししたものです（本記録の読み）—— 製品名でもCVE番号でもなく、「外部公開しているアプリケーション」と「アカウント」という2つの面を挙げています。

点検の手順が具体的である点も、他の3本と違います。

  1. 外部公開アプリケーションの精査 —— 「直近１ヵ月、その後３ヵ月といったように、段階的に対象範囲を広げて確認」（原文引用）。異常の見分け方として「エラーの出力量、平時との差異」を挙げる。 さらに「今後複数回調査を行う可能性も踏まえ、誰がどのように調査できるかについても把握しておいてください」（原文引用）。
  2. 自組織が利用している外部サービスの洗い出し —— 「サービス単位でログの保有期間はそれぞれ異なることが想定されますので、その整理も必要です」（原文引用）。アカウントの異常として「作ったはずのないアカウントが存在しないか、削除・無効化されているはずのアカウントが有効化されていないか」。
  3. 保有データの再点検 —— 「不要な情報は持たない、という基本原則」。

本記録がもっとも実務的だと見るのは、1と2に共通する「誰がいつどのように確認できるか」を整理させている点です（本記録の判断）—— ログがあるかどうかではなく、調査の主体と手順を事前に決めておけという要求で、これは外部サービスでは特に落ちやすい部分です（サービス提供者と利用者で確認できるログが違う、と原文も書いています）。

誤読しないでほしい点（本記録の註。齟齬13）—— 「特定の製品の脆弱性ではない」は「パッチ適用は的外れ」を意味しません。 IPA 自身が点検項目に「現在未適用の脆弱性対応パッチがないか確認」を挙げており（原文）、JPCERT/CC のケースCはMetabase の CVE-2026-72898 の悪用です（出典1）。否定されているのは「単一の製品が一連の事案の共通原因である」という見立てだけです。

IPA のページには「追記すべき情報がある場合には、その都度このページを更新する予定です」という注釈があります（原文引用）—— JPCERT/CC の注意喚起（出典1）と同じく、更新前提の文書です。 読者側の実務としては、一度読んで終わりにせず再訪が必要です（本記録の判断）。

個人情報保護委員会は、来年4月確定予定の見直し内容を先取りして示した当局対応

政府の一連の注意喚起の起点は、JPCERT/CC（10月8日）ではなく個人情報保護委員会（10月7日）でした（出典14。本記録が PDF を直接取得して確認）。

この文書の特異な点は、制度の先取りです。

「令和８年９月16日に開催した第369回個人情報保護委員会で決議したとおり、今後、ガイドライン（通則編）別添の『手法の例示』等については、現代化を含めた見直しを予定しています。見直しの内容の確定は、来年４月を予定していますが、近時の動向を踏まえて、『手法の例示』として、より参考になると考えられるため、見直し予定の内容を先取りする形でお示しします」（出典14。原文引用）。

別紙として示された技術的安全管理措置（10-6）の「手法の例示」のうち、本記録が目を引かれたのは次の3つです（本記録の選択）。

  • 「個人データを取り扱う情報システムへのアクセスを最小化する。例えば、事前に許可した特定の IP アドレスからのみに限定する方法が考えられる」
  • 「組織内外からのアクセスについて、アクセス要求ごとにアクセス元の場所、アクセス時間、デバイスのセキュリティ状態等の動的コンテキストを評価し、リスクに応じてアクセスの可否を判断する仕組みを導入する」
  • 「組織外ネットワークからのアクセスや、管理者権限でのアクセス、重要な個人データへのアクセスにおいては、識別・認証手法を複数組み合わせる多要素認証（フィッシングに耐性のあるものを含む。）を導入する」

「手法の例示」は従わなければ法違反になるものではありません（出典14）—— 文書自身が「『講じなければならない措置』は、これらに従わなかった場合、法違反と判断される可能性がありますが、『手法の例示』は、文字どおり例を示したものであって、必ずしも例示の内容の全てを講じなければ、法違反と判断されるというものではなく」と明記しています（原文引用）。しかし本記録の評価としては、監督官庁が「より参考になる」として前倒しで示した例示は、事後に安全管理措置の妥当性を問われる場面で参照点になります。

あわせて「WARNING〜不正アクセスによる個人データ漏えい防止のための注意喚起〜」が10月7日に改訂されました（出典15。令和6年12月11日初版）。9つの事例に類型化されており、その1つが「事例９ APIが悪用される事例」です。

原因として挙げられているのは3点（出典15。原文の要旨）—— ①管理対象から漏れているAPIが存在した、②URLや会員ID等のパラメータを書き換えることで他ユーザーのデータにアクセス可能な状態であった、③レスポンスに不要な情報が含まれていたことや会員ID等が連番となっていたことから攻撃者によるAPIの仕様等の推測が容易だった。 対策例は、APIの定期的な棚卸し、「認証（本人確認）に加え、認可（そのユーザーが当該データにアクセスする権限を有するかの確認）を都度行う仕組みを実装する」、会員IDや管理番号にランダムな値（UUID等）を採用すること。

これは JPCERT/CC のケースB（アプリを解析して特定した管理用APIへの不正なリクエスト）と同じ構図です（本記録の対応づけ。齟齬14）—— 違うのは立て方で、JPCERT/CC は攻撃手法として書き、個人情報保護委員会は「措置が十分でない場合、安全管理措置（法第23条）、従業者の監督（法第24条）及び委託先の監督（法第25条）の違反と判断される可能性があります」という枠組みで書いています（出典15。原文引用）。

緩和策
数え方: **APIへのアクセスには単位時間あたりのリクエスト件数を制限し、 短時間に繰り返されるアクセスや大量実行を防止する**　副作用: **正規の自動化（バッチ連携・データ同期・監視）が制限に当たって止まりうる。** 制限値を安全側に寄せすぎると業務が止まり、緩めると大量取得を防げない。 **実装前に正規利用の最大レートを測る必要がある**（本記録の評価）
数え方: **ログイン、パスワードリセット、SMS送信、検索処理などの負荷や悪用のリスクが高い機能には 個別にレート制限や利用回数制限を設定する**　副作用: **正規の利用者がパスワードを忘れた際などに制限に当たり、問い合わせが増える。** SMS送信の制限は本人認証の失敗にもつながるため、 **制限に当たった利用者の救済経路（サポート窓口）を併せて用意する必要がある**（本記録の評価）
数え方: **非公開APIを含む各APIエンドポイントでアクセス制御を実施し、 許可された利用者やHTTPメソッドからのアクセスのみを受け付ける**　副作用: **既存の連携が許可の設計から漏れていると停止する。** **「本来画面操作では実行できない内部API」は、 画面側の実装がそこに依存している場合があり、 一律に閉じると自社アプリが動かなくなる**（本記録の評価）。 **エンドポイントの棚卸しを先に行う必要がある**
数え方: **API利用者やAPIトークンには必要最小限の権限のみを付与する**　副作用: **既存トークンの権限を絞ると、権限に依存していた機能が止まる。** **どのトークンがどの機能に使われているかの台帳が無ければ、 絞った結果どこが止まるかを事前に把握できない**（本記録の評価）
数え方: **APIトークンには適切な有効期限を設定し、長期間有効なトークンの使用を避ける。** **不要となった、または漏えいが疑われるAPIトークンは速やかに無効化できるようにする**　副作用: **期限付きにすると更新の仕組み（ローテーション）が必要になり、 更新に失敗した連携が止まる。** **ケースBの（c）「他のシステムの侵害で窃取したAPIキーを使用する」に 直接効く対策であるため、代償を払う価値はある**（本記録の評価）
数え方: **業務上必要のないサービスや機能（管理機能など）がインターネットに公開されている場合、 公開を停止する**　副作用: **外部から管理していた運用（在宅勤務・委託先の保守）が成立しなくなる。** 代替として VPN・踏み台・接続元制限の整備が必要になり、 **その整備が終わるまでは運用が不便になる**（本記録の評価）
数え方: **法令や契約等で定められた保存期間を過ぎたデータや 利用目的を終えたデータを残さない**　副作用: **過去データに依存した分析・問い合わせ対応・紛争対応ができなくなる。** **一方、漏えいしたときの被害規模を直接下げる唯一の対策でもある**—— **「守る」のではなく「持たない」という方向であり、 他の対策が破られたときにだけ効く**（本記録の評価）
数え方: **サービスの利用地域が限定される場合は、アクセス元の地域を制限する。** **既知の脆弱性の影響を受けるバージョンで運用している場合は、修正済みのアップデートを適用する。** **Webサーバー等が侵害された後の横展開対策を見直す。** **不正アクセス検知体制の点検と検知時の初動対応を見直す。** **漏えい発生時を想定した、平時からの顧客への二次被害防止等の呼びかけ（多要素認証など）**　副作用: **地域制限は海外出張中の利用者や越境の正規利用を妨げ、 VPN・プロキシ経由の正規アクセスも遮断しうる。** **アップデートの適用は互換性の検証と停止時間を要する。** **平時からの顧客への呼びかけは、過度に行うと「またか」と読み流される** （本記録の評価）
**対策は注意喚起の原文（API経由6項目・汎用7項目）に基づき、 副作用は本記録の作成者の評価である。** **JPCERT/CC は副作用に言及していない。** **本記録が副作用を併記するのは、「全部やる」が現実的でない以上、 どこから着手するかの判断に代償の情報が要るためである**（本記録の方針）。 **着手順として本記録が推すのは、①エンドポイントの棚卸し（他の対策の前提になる）、 ②不要な管理機能の公開停止（効果が大きく副作用が限定的）、 ③APIトークンの権限と有効期限**である（本記録の評価）

持ち出し公表されていない
**注意喚起は、個別の被害組織が持ち出しを検知できたかを述べていない。** **本記録として評価できるのは、注意喚起が汎用的な対策に 「不正アクセス検知体制の点検と検知時の初動対応を見直す」を挙げ、 さらに「漏えい発生時を想定した、平時からの顧客への二次被害防止等の呼びかけ （多要素認証など）」まで含めている点である**（本記録の読み取り）。 **後者は「漏えいは起きる」という前提に立った対策であり、 検知と封じ込めの前に備えておく性質のものである。** **注意喚起が「法令や契約等で定められた保存期間を過ぎたデータや 利用目的を終えたデータを残さない」を挙げているのも同じ系統である**—— **持ち出しを防ぐのではなく、持ち出せる量を減らす**（本記録の評価）
影響を限定できた法令や契約等で定められた保存期間を過ぎたデータ、 利用目的を終えたデータを残さない　**注意喚起の汎用的な対策であり、本記録が本注意喚起で最も見落とされやすいと 評価する項目である。** **これは侵入も持ち出しも防がない**—— **他のすべての対策が破られたときにだけ効く。** **効き方は被害規模の縮小である**—— **漏えいした件数が、通知対象・報告義務・二次被害の規模をそのまま決める** （本記録の評価）。 **実施の難しさは技術ではなく合意形成にある**—— 事業側は「あとで使うかもしれない」データを残したがる。 **保存期間を定めて自動削除を実装するところまで進めないと、 方針だけでは減らない**
影響を限定できた漏えい発生時を想定し、平時から利用者へ二次被害防止の呼びかけ （多要素認証の有効化など）を行う　**注意喚起の汎用的な対策である。** **本記録はこれを「自組織の防御」ではなく「利用者の防御」として評価する**—— **漏えいした認証情報が他サービスで使い回されている場合、 被害は自社の外で起きる。** **平時から多要素認証を促しておけば、漏えい後の二次被害が下がる。** **副作用は、過度に行うと読み流されることである**（本記録の評価）—— **漏えい後に初めて呼びかけても、そのときには遅い**という点が要点
影響を限定できたWebサーバー等が侵害された後の横展開対策を見直す　**注意喚起の汎用的な対策である。** **ケースB（c）の「他のシステムの侵害で窃取したAPIキーを使用する」は、 まさに横展開の経路である**（本記録の読み取り）—— **一つのシステムの侵害が、そこに保管されていたキーを通じて 別のシステムの侵害につながる。** **したがって「Webサーバーに何のキーが置かれているか」の棚卸しが、 横展開対策の具体的な中身になる**（本記録の評価）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**JPCERT/CC は、把握している情報が「限定的かつ断片的」であることを明示したうえで、 情報が揃うのを待たずに2026年10月8日に注意喚起を公表した。** 公表の理由を**「攻撃被害の拡大等の状況に鑑み」**としている機能した**本記録の作成者の評価である。情報の限界を明示したうえで出す形として適切だと評価する。** **評価の根拠は、留保の置き方が具体的である点にある**—— **①冒頭で「限定的かつ断片的」と明示、 ②攻撃手法の節に「本項の情報は、JPCERT/CCに寄せられた情報などに基づくものです。 すべての事案で同一の攻撃手法が使用されていることを示すものではありません」と註記、 ③IPアドレスに「調査時点では正規利用されている可能性もあります」と但し書き、 ④「侵害原因や攻撃手法などに関する新たな情報が判明した場合、 本ページを更新していきます」と更新を予告。** **とくに②は重要である**—— **3ケースを並べたことで「これらが同一のキャンペーンである」と 読まれる危険があるが、それを明示的に否定している**（本記録の評価）。 **③も実務に直結する**—— 但し書きが無ければ、読者は8件のIPを遮断リストに投入しかねない。 **惜しい点として、被害の規模（組織数・漏えい件数の概数）が示されていないため、 読者は自組織の優先度を測りにくい**（下の項目で別に評価した）
**JPCERT/CC は、攻撃手法を3ケースに整理し、 不審な送信元IPアドレス8件とUser-Agentの例を観測時期つきで公表し、 API経由のアクセスへの対策6項目と汎用的な対策7項目を示した。** **一方で、被害組織名・被害件数・漏えい規模・攻撃者の帰属は示していない。** **製品名が挙がっているのは Metabase のみである**部分的に機能**本記録の作成者の評価である。** **評価できる点**—— **①対策を「API経由のアクセスへの対策」と「汎用的な対策」の2段に分けたこと。** 本件の共通点が API であることを踏まえた構成で、 **読者は自組織に API があるかどうかで読む範囲を判断できる**（本記録の評価）。 **②痕跡に観測時期を付したこと。** 「9月ごろ」「8月上旬から9月上旬までの間」と書かれているため、 **読者は過去ログを遡る範囲を決められる。** **③「調査時点では正規利用されている可能性もあります」という但し書き。** **誤遮断の事故を避けられる。** **④参考情報に OWASP の2資料と外部ベンダーの分析を並べたこと。** 注意喚起自体は短いが、**深掘りの経路を示している。** **⑤「管理・運用側で不特定多数の利用者からのアクセスを想定していないシステム」への 言及を冒頭と末尾の2か所で繰り返したこと。** **読み飛ばされやすい論点を構造的に強調している**（本記録の評価）。 **不十分な点**—— **①被害の規模が全く示されていない。** 組織数も漏えい件数の概数も無いため、**読者は「どれくらい急ぐべきか」を測れない。** **②ケースAが具体性に乏しい。** 「さまざまな既知の脆弱性」「機器の管理不備等」という括りで、 **製品名も CVE も例示が無いため、読者が何を点検すべきか決めにくい** （JPCERT/CC 自身が「限定的かつ断片的」としているため、 これは情報の制約によるものと読める）。 **③ケースB の手口は詳しいが、どの製品・どの実装パターンで起きたかが示されていない**—— 自組織が該当するかの判定は読者側の作業として残る
CISO・経営層への示唆
  • 「社内向け」「不特定多数を想定していない」システムを点検対象から外さない
    **注意喚起は冒頭と末尾の2か所で同じ指摘を繰り返している**—— **「BI（ビジネスインテリジェンス）ツールや従業員向け管理システムなど、 管理・運用側で不特定多数の利用者からのアクセスを想定していないシステムが被害に遭い、 内部に保存していた情報が漏えいするケースもあります」。** **ケースCの Metabase はまさに BI ツールである。** **「想定していない」ことは「到達できない」ことを意味しない**
    取るべき行動 **①資産台帳を「外向け／社内向け」の区分ではなく 「インターネットから到達できるか」で並べ替える （区分ではなく実測で判定する）、 ②BIツール・従業員向け管理システム・保守用の管理画面を明示的に点検対象に加える、 ③点検結果を「外部から到達できる面の一覧」として持ち、月次で差分を確認する。** **経営報告では「脆弱性対応率」と並べて 「インターネットから到達できる管理機能の件数」を出す**—— **前者だけでは、本件のリスクは見えない**（本記録の評価）
  • 「パッチ適用で閉じない事案」を扱う枠を脆弱性管理の外側に持つ
    **JPCERT/CC は「一つの共通するソフトウェアの脆弱性を悪用しているのではなく」と 明記している。** **ケースBは API の設計と権限管理の問題であり、CVE 番号が存在しない。** **ケースAには「脆弱性ではないものの、機器の管理不備等を悪用した攻撃 （環境設定ファイルやバックアップファイルの窃取など）」が含まれる。** **脆弱性管理の仕組み（スキャナ・CVE の追跡・パッチ適用率）をどれだけ回しても、 これらは検出されず対処済みにもならない**
    取るべき行動 **脆弱性管理とは別に3つの台帳を持ち、四半期ごとにレビューする—— ①公開しているAPIエンドポイントの一覧（非公開・内部APIを含む）、 ②発行済みAPIトークン・キーの一覧（権限・有効期限・利用箇所）、 ③インターネットから到達できる管理機能の一覧。** **①はこの後のほぼすべての対策の前提になる**—— 一覧が無ければ「すべてのエンドポイントでアクセス制御」は実施できない（本記録の評価）
  • 漏えいしたときの被害規模を「持っているデータの量」で管理する
    **注意喚起の汎用的な対策に「法令や契約等で定められた保存期間を過ぎたデータや 利用目的を終えたデータを残さない」が挙げられている。** **本注意喚起が扱っているのは「大量の個人情報等の漏えいにつながっている」攻撃類型であり、 漏えいした件数がそのまま通知対象・報告義務・二次被害の規模を決める**（本記録の評価）。 **この対策は侵入も持ち出しも防がない**—— **他のすべての対策が破られたときにだけ効く**
    取るべき行動 **①主要なデータベース・BIツールが保持する個人情報の「件数」と「最も古い日付」を測る、 ②保存期間を定め、期間を過ぎたデータの自動削除を実装する （方針の明文化だけでは減らない）、 ③削除した件数を定期的に報告させる。** **実施の難所は技術ではなく事業側との合意形成である**—— 事業側は「あとで使うかもしれない」データを残したがる。 **「漏えい時の想定被害件数」を経営指標として置くと、議論が進めやすい**（本記録の評価）
  • 注意喚起を受け取ったときの判定を「自社に該当製品があるか」で終わらせない
    **JPCERT/CC は2026年8月14日に CVE-2026-72898 の注意喚起を出していたが、 約1か月25日後の本注意喚起で、それが実際の漏えい被害に結びついているケースとして 再掲されている**（本記録の作成者が算出）。 **さらにケースCで観測されたアクセスは「8月上旬から9月上旬までの間」であり、 8月14日の注意喚起より前から悪用が始まっていた可能性がある**（本記録の読み取り）
    取るべき行動 **①注意喚起の処理手順に「該当製品の有無」とは別に 「同種の攻撃類型に自社の別システムが該当しないか」の判定項目を入れる、 ②該当なしと判定した場合もその根拠を記録する （後から同じ注意喚起が再掲されたときに、前回の判定を見直せる）、 ③対処の完了を「パッチ適用」ではなく「点検項目の消化」で測る。** **本件で求められている対処（エンドポイントの棚卸し・トークンの権限と期限・ 不要な管理機能の公開停止・保存データの削減）は、 いずれもパッチ適用では代替できない**（本記録の評価）
  • 漏えいは起きる前提で、利用者への二次被害防止の呼びかけを平時から行う
    **注意喚起は汎用的な対策に「漏えい発生時を想定した、 平時からの顧客への二次被害防止等の呼びかけ（多要素認証など）」を挙げている。** **これは自組織の防御ではなく利用者の防御である**（本記録の読み取り）—— **漏えいした認証情報が他サービスで使い回されていれば、被害は自社の外で起きる**
    取るべき行動 **①自社サービスで多要素認証を提供し、有効化率を測る、 ②有効化を促す案内を平時から定期的に行う（漏えい後では遅い）、 ③漏えい時の利用者向け案内の雛形を、 「取るべき行動」を先頭に置いた形で用意しておく。** **副作用は、過度に呼びかけると読み流されることである**（本記録の評価）—— **頻度より、有効化率という結果で測るほうがよい**
セキュリティ技術者への示唆
  • 自社の公開アプリを自ら解析し、そこから見えるAPIエンドポイントとキーを把握する
    **ケースB（a）は「一般公開しているスマートフォンアプリを解析し APIのエンドポイントやキーを特定する」である。** **攻撃の第一歩が自社の配布物の解析であるなら、同じ作業を自分で行えば 攻撃者が見る面がそのまま分かる**（本記録の評価）。 **アプリに埋め込んだキーは、配布した時点で秘密ではない**
    取るべき行動 **①自社のモバイルアプリ・SPA を解析し、埋め込まれているエンドポイントとキーを 洗い出して一覧にする、 ②クライアント側のキーで認可している箇所があれば、サーバー側の認可に移す、 ③一覧を「公開APIの台帳」として維持し、リリースごとに差分を確認する。** **判定の基準は「このキーが公開されても安全か」である**—— **安全でないなら、その設計は配布した時点で破れている**（本記録の評価）
  • 非公開・内部APIにもサーバー側でアクセス制御をかける（画面側の制限に頼らない）
    **ケースB（b）は「本来画面操作では実行できない内部APIに対する攻撃」である。** **具体的な手口として、ユーザー権限の変更、不正なアカウントの作成、 ヘッダーの有無の切り替えや不正な形式の認証トークンの付与による応答の違いの確認、 NoSQLインジェクションによるブラインド探索が挙げられている。** **画面は入口の一つにすぎず、API は直接叩ける**
    取るべき行動 **①APIエンドポイントを棚卸しし（これが前提作業である）、 ②各エンドポイントで「許可された利用者」と「許可されたHTTPメソッド」を定義して サーバー側で検証する、 ③権限変更・アカウント作成のAPIは、利用者向けトークンでは到達できないよう トークンと接続元を分離する。** **副作用に注意する**—— **画面側の実装が内部APIに依存している場合、一律に閉じると自社アプリが動かなくなる。** **だから棚卸しが先である**（本記録の評価）
  • 権限変更とアカウント作成を、経路（画面／API）を問わず監査ログに残して通知する
    **ケースB（b）で挙げられている「ユーザー権限を変更する」「不正なアカウントを作成する」は、 正規の運用では稀にしか起きない事象である**—— **検知の規則として誤検知が少なく、実装も容易な部類に入る**（本記録の評価）。 **見落としの原因は、管理画面の操作ログだけを監査対象にしていることである**—— **API 経由の権限変更が記録に残らない**（本記録の評価）
    取るべき行動 **①権限の変更とアカウントの作成を、画面経由・API経由の区別なく 同一の監査ログに記録する、 ②通知の対象を「権限の昇格」と「管理者権限を持つアカウントの新規作成」に絞って 即時通知する（絞れば通知量は小さく保てる）、 ③記録に「経路」「接続元IP」「User-Agent」を含める。** **③があれば、注意喚起が提供した痕跡（IP 8件・User-Agent）との突合が可能になる** （本記録の評価）
  • APIのアクセスログに認可の失敗を記録し、リクエスト数の急増を検知する
    **ブラインド探索は本質的に大量のリクエストを必要とする**—— 応答の違いを手がかりに内容を1文字ずつ推定するため、 **1件のアカウント情報の特定だけで数百〜数千回の試行が生じうる**（本記録の評価）。 **また「ヘッダーの有無の切り替えや不正な形式の認証トークンの付与による 応答の違いの確認」も大量の失敗を伴う。** **したがってこれらは検知の機会として最も捉えやすい部類に入る**
    取るべき行動 **①APIのアクセスログに認可の失敗（401/403）と 不正な形式のトークンでの試行を記録する （401/403 を記録していない実装は珍しくない）、 ②「同一接続元・同一エンドポイントへのリクエスト数の急増」と 「認可失敗率の急変」で検知する、 ③検知の規則を書く前に、正規利用の最大レートを実測する。** **③を飛ばすと、しきい値を安全側に寄せて業務を止めるか、 緩めて攻撃を通すかのどちらかになる**（本記録の評価）。 **注意喚起の User-Agent（`curl/7.88.1`・`python-requests/2.34.2`）は 正規の自動化でも使われるため単独では判別に使えないが、 認可失敗の急増と組み合わせれば絞り込みに使える**
  • NoSQL でも入力を演算子として解釈させない実装にし、検索APIに件数上限を置く
    **ケースB（b）に「NoSQLインジェクションによるブラインド探索によって アカウント情報を特定する」が挙げられている。** **NoSQLインジェクションは、利用者の入力がクエリの演算子 （比較・正規表現等）として解釈されることで成立する**（本記録による補足）。 **SQL の対策として広く知られるパラメータ化が、 NoSQL では実施されていない実装が残りやすい**—— **「SQL を使っていないからインジェクションは関係ない」という読み違いが起きやすい**
    取るべき行動 **①NoSQL へのクエリで、利用者入力が演算子として解釈されない形に正規化する （型の検証を含める。文字列を期待する箇所にオブジェクトが入る経路を塞ぐ）、 ②検索・一覧取得のAPIで1リクエストあたりの返却件数に上限を設ける、 ③取得総量を監視する。** **②③が要るのは、レート制限では大量取得を塞げないからである**—— **多数のリクエストによる漏えいと、1リクエストでの大量取得は別の経路である** （本記録の評価）。 **注意喚起が参考情報に OWASP の API Security Top 10 2023 と REST Security Cheat Sheet を挙げているのは、この種の実装上の論点を含むためと読める**

観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ BIツール（Metabase 等）や従業員向け管理システムをインターネットから到達できる場所で運用している注意喚起は「管理・運用側で不特定多数の利用者からのアクセスを想定していないシステム」の 被害を冒頭と末尾の2か所で指摘しており、ケースCの Metabase はこの類型にあたる

運用・監視□ 公開しているWebサーバーに環境設定ファイルやバックアップファイルが残っており、外部からの到達性を確認していないケースAには「脆弱性ではないものの、機器の管理不備等を悪用した攻撃 （環境設定ファイルやバックアップファイルの窃取など）」が含まれ、脆弱性スキャナでは検出されない
