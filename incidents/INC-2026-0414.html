INC-2026-0414JPCERT/CC が国内の不正アクセスに注意喚起

JPCERT/CC は2026年10月8日、直近2026年9月前後で国内組織における不正アクセスによる個人情報等の漏えい被害が相次いでいるとして注意喚起（JPCERT-AT-2026-0030）を公表した——普段から散発的に発生するランサムウェア等とは別に、大量の個人情報漏えいにつながる「特に増加している恐れのある攻撃類型」を3ケースに整理している。ケースAはさまざまな既知の脆弱性や機器の管理不備を標的ごとに探索して悪用を試みるもの、ケースBはスマートフォンアプリを解析して特定した管理用APIへの不正なリクエスト（権限変更・不正アカウント作成・NoSQLインジェクションによるブラインド探索・他システムで窃取したAPIキーの使用）、ケースCはMetabaseのSQLインジェクションの脆弱性（CVE-2026-72898）の悪用。BIツールや従業員向け管理システムなど、不特定多数からのアクセスを想定していないシステムの被害も含まれる。不審な送信元IPアドレス8件とUser-Agentの例も公表された

脅威・攻撃キャンペーン業界横断事象・統計（被害者が不特定多数、統計の推移が主）初報のみ日本の組織が当事者既知の脆弱性の悪用設計・実装上の不備権限管理の不備認証情報の悪用（使い回し・推測可能・窃取）脆弱性の放置
初報: 2026年10月8日 最終更新: 2026年10月8日

2026年10月8日、JPCERT コーディネーションセンター（JPCERT/CC） は注意喚起「直近で相次いでいる国内組織における不正アクセスに関する注意喚起」（JPCERT-AT-2026-0030）を公表しました。

直近2026年9月前後で、国内組織における不正アクセスによる個人情報等の漏えい被害が相次いでいるという状況を受けたものです。

本記録が中心と見るのは、この注意喚起が「一つの脆弱性への対処」を求めるものではないという点です。JPCERT/CC は明記しています。

一連の攻撃については、一つの共通するソフトウェアの脆弱性を悪用しているのではなく、標的ごとにさまざまな既知の脆弱性有無についてスキャンし、脆弱性を探索して悪用を試行したり、脆弱性ではないものの、機器の管理不備等を悪用した攻撃を試みている可能性があります

つまり 「この CVE を当てれば終わり」という形の対処にならない。整理された攻撃類型は3つです。

内容
ケースA さまざまなソフトウェアの既知の脆弱性を標的ごとに探索し攻撃試行する。脆弱性ではない機器の管理不備（環境設定ファイルやバックアップファイルの窃取）も含む
ケースB API経由での不正な操作。公開アプリを解析してAPIのエンドポイントやキーを特定し、本来画面操作では実行できない内部APIを攻撃する
ケースC Metabase のSQLインジェクションの脆弱性（CVE-2026-72898） の悪用。これもAPIへの不正なリクエストを通じたもの

もう一つ重要な指摘があります。被害に遭っているのは一般利用者向けのアプリだけではありません。

BI（ビジネスインテリジェンス）ツールや従業員向け管理システムなど、管理・運用側で不特定多数の利用者からのアクセスを想定していないシステムが被害に遭い、内部に保存していた情報が漏えいするケースもあります

「外向けではないから対象外」という線引きが成り立たないということです（注意喚起は末尾でも同じ指摘を繰り返しています）。

JPCERT/CC は自ら情報の限界も示しています—— 「技術的な情報の共有が不足しており、把握している情報は限定的かつ断片的であるものの、攻撃被害の拡大等の状況に鑑み」 公表に至ったとし、「すべての事案で同一の攻撃手法が使用されていることを示すものではありません」 と念を押しています。評価・示唆は本記録の判断として分けて書きます。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は「一つの攻撃」ではなく、JPCERT/CC が複数の報告から整理した攻撃類型である。** **したがって以下の段階は、特定の事案の工程を復元したものではなく、 注意喚起が記述した手口を段階に割り当てたものである**（本記録の整理）。 **とくにケースBは、公表された手口の記述がそのまま段階の順序になっている**—— 公開アプリの解析（偵察）→ 内部APIへの試行（初期アクセス）→ 権限変更・不正アカウント作成（権限昇格・永続化）→ NoSQLインジェクションによるブラインド探索（内部探索）→ 情報の漏えいと不正な書き換え（持ち出し・影響）。 **JPCERT/CC 自身が「すべての事案で同一の攻撃手法が使用されていることを 示すものではありません」「把握している情報は限定的かつ断片的」と 留保を付していることを、各段階で踏まえる。** **MITRE ATT&CK への対応づけは注意喚起に無いため、本記録でも付さない** （日本語の記述から機械的に技術IDへ写さないという方針による）。

  2. 2. 初期侵入[1] [2]
    **ケースA**: 探索した**既知の脆弱性の悪用を試行する。** **ケースB（b）**: **本来画面操作では実行できない内部APIに対する攻撃。** **ケースB（c）**: **他のシステムの侵害で窃取したAPIキーを使用する。** **ケースC**: **MetabaseのSQLインジェクションの脆弱性（CVE-2026-72898）を APIへの不正なリクエストを通じて悪用する**
  3. 3. 権限昇格[1]
    **ケースB（b）**: **内部APIへの攻撃により、ユーザー権限を変更する。 また不正なアカウントを作成する。** **注意喚起は「アプリの管理用APIへの不正なリクエストによって、 情報の不正な書き換え等が発生しているものがあります」としており、 読み出しだけでなく改変が確認されている**
  4. 4. 内部探索[1]
    **ケースB（b）**: **NoSQLインジェクションによるブラインド探索によって アカウント情報を特定する。** **「ブラインド」とは、応答の違い（成否・遅延・エラーの形）を手がかりに 内容を1文字ずつ推定する手法である**（本記録による補足）。 **ケースC**: **MetabaseのSQLインジェクションの脆弱性 （CVE-2026-72898）により、BIツールが保持するデータへ到達する**

    **注意喚起の前提そのものがこの段階である。** **「直近2026年9月前後で国内組織における不正アクセスによる 個人情報等の漏えい被害が相次いでいます」**とされ、 **本注意喚起は「大量の個人情報等の漏えいにつながっている、 特に増加している恐れのある攻撃類型」を取り上げるものだと明記されている。** **被害に遭ったシステムには、BIツールや従業員向け管理システムなど、 管理・運用側で不特定多数の利用者からのアクセスを想定していないものが含まれ、 「内部に保存していた情報が漏えいするケースもあります」とされる。** **漏えいした情報の類型・件数・組織数はいずれも公表されていない**

API経由のアクセスへの対策（6項目）

  1. 単位時間あたりのリクエスト件数を制限し、短時間に繰り返されるアクセスや大量実行を防止する
  2. ログイン・パスワードリセット・SMS送信・検索処理などの悪用のリスクが高い機能には個別にレート制限や利用回数制限を設定する
  3. 非公開APIを含む各APIエンドポイントでアクセス制御を実施し、許可された利用者やHTTPメソッドからのアクセスのみを受け付ける
  4. API利用者やAPIトークンには必要最小限の権限のみを付与する
  5. APIトークンには適切な有効期限を設定し、長期間有効なトークンの使用を避ける
  6. 不要となった、または漏えいが疑われるAPIトークンは速やかに無効化できるようにする

汎用的な対策（7項目） — 地域制限／修正済みアップデートの適用／横展開対策の見直し／検知体制と初動対応の見直し／平時からの顧客への二次被害防止の呼びかけ（多要素認証など）／不要な管理機能の公開停止／保存期間を過ぎたデータを残さない

注意喚起は副作用に触れていないが、実施には代償がある（本記録の評価）。レート制限は正規の自動化（バッチ連携・データ同期・監視）を止めうるため、実装前に正規利用の最大レートを測る必要がある。 「非公開APIを含む各エンドポイントでアクセス制御」も、画面側の実装が内部APIに依存している場合は一律に閉じると自社アプリが動かなくなる—— だからエンドポイントの棚卸しが先である。本記録が推す着手順は、①エンドポイントの棚卸し（他の対策の前提）、②不要な管理機能の公開停止（効果が大きく副作用が限定的）、③APIトークンの権限と有効期限である。

数え方: **APIへのアクセスには単位時間あたりのリクエスト件数を制限し、 短時間に繰り返されるアクセスや大量実行を防止する**　副作用: **正規の自動化（バッチ連携・データ同期・監視）が制限に当たって止まりうる。** 制限値を安全側に寄せすぎると業務が止まり、緩めると大量取得を防げない。 **実装前に正規利用の最大レートを測る必要がある**（本記録の評価）
数え方: **ログイン、パスワードリセット、SMS送信、検索処理などの負荷や悪用のリスクが高い機能には 個別にレート制限や利用回数制限を設定する**　副作用: **正規の利用者がパスワードを忘れた際などに制限に当たり、問い合わせが増える。** SMS送信の制限は本人認証の失敗にもつながるため、 **制限に当たった利用者の救済経路（サポート窓口）を併せて用意する必要がある**（本記録の評価）
数え方: **非公開APIを含む各APIエンドポイントでアクセス制御を実施し、 許可された利用者やHTTPメソッドからのアクセスのみを受け付ける**　副作用: **既存の連携が許可の設計から漏れていると停止する。** **「本来画面操作では実行できない内部API」は、 画面側の実装がそこに依存している場合があり、 一律に閉じると自社アプリが動かなくなる**（本記録の評価）。 **エンドポイントの棚卸しを先に行う必要がある**
数え方: **API利用者やAPIトークンには必要最小限の権限のみを付与する**　副作用: **既存トークンの権限を絞ると、権限に依存していた機能が止まる。** **どのトークンがどの機能に使われているかの台帳が無ければ、 絞った結果どこが止まるかを事前に把握できない**（本記録の評価）
数え方: **APIトークンには適切な有効期限を設定し、長期間有効なトークンの使用を避ける。** **不要となった、または漏えいが疑われるAPIトークンは速やかに無効化できるようにする**　副作用: **期限付きにすると更新の仕組み（ローテーション）が必要になり、 更新に失敗した連携が止まる。** **ケースBの（c）「他のシステムの侵害で窃取したAPIキーを使用する」に 直接効く対策であるため、代償を払う価値はある**（本記録の評価）
数え方: **業務上必要のないサービスや機能（管理機能など）がインターネットに公開されている場合、 公開を停止する**　副作用: **外部から管理していた運用（在宅勤務・委託先の保守）が成立しなくなる。** 代替として VPN・踏み台・接続元制限の整備が必要になり、 **その整備が終わるまでは運用が不便になる**（本記録の評価）
数え方: **法令や契約等で定められた保存期間を過ぎたデータや 利用目的を終えたデータを残さない**　副作用: **過去データに依存した分析・問い合わせ対応・紛争対応ができなくなる。** **一方、漏えいしたときの被害規模を直接下げる唯一の対策でもある**—— **「守る」のではなく「持たない」という方向であり、 他の対策が破られたときにだけ効く**（本記録の評価）

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
JPCERT/CC が整理した3ケース——公開アプリの解析から内部APIの悪用、Metabase の脆弱性までが「API」で結ばれている
layer 0 は攻撃者（帰属は非公表）と、JPCERT/CC が公表した痕跡（IP 8件・User-Agent 3種）。 layer 1 は3つの攻撃類型——ケースA（既知の脆弱性の探索と機器の管理不備）、 ケースB（API経由での不正な操作）、ケースC（Metabase の CVE-2026-72898）。 layer 2 は攻撃の足がかりとなった面——公開スマートフォンアプリ（解析の対象）、 内部API、環境設定ファイル・バックアップファイル。 layer 3 は被害を受けたシステムの類型——一般利用者向けアプリ、 **BIツール・従業員向け管理システム（「不特定多数からのアクセスを想定していない」もの）**。 layer 4 は帰結（個人情報等の大量漏えい・情報の不正な書き換え）と、 注意喚起を行った JPCERT/CC および参照先（OWASP・マクニカ）。 **本図の要点は、3ケースがいずれも API に収束していることである**—— ケースBは定義上 API への攻撃であり、ケースCも「APIへの不正なリクエストを通じて 悪用される」と明記されている。 **点線は、注意喚起が「すべての事案で同一の攻撃手法が使用されていることを 示すものではない」と留保した関係を表す。**

段階検知の機会効きえた対策
偵察機会はあったが検知できず
**本記録の評価である（注意喚起は被害組織側の検知について述べていない）。** **公開アプリの解析そのものは攻撃者の手元で行われるため、防御側からは見えない。** **一方、「応答の違いの確認」は防御側から観測できる種類の活動である**—— **同一の接続元から、ヘッダーや認証トークンを変えた試行が短時間に繰り返される** という形で現れる。 **ただし API のアクセスログを保存し、かつ認可の失敗を記録していなければ見えない** （401/403 を記録していない実装は珍しくない。本記録の評価）。 **ここで防御側が取れる行動は検知より確認である**—— **自社の公開アプリを自分で解析し、そこから見えるエンドポイントとキーを把握する。** 攻撃者と同じ方法で自組織の面を測れる
検知できた公開しているアプリ（とくにスマートフォンアプリ）を自ら解析し、 そこから到達できるAPIエンドポイントとキーの一覧を作る　**本記録の評価である。ケースB（a）に直接対応する。** **「一般公開しているスマートフォンアプリを解析しAPIのエンドポイントやキーを特定する」 のが攻撃の第一歩である以上、同じ作業を自分で行えば攻撃者が見る面が分かる。** **アプリに埋め込んだキーは秘密ではない**—— 配布した時点で解析可能であり、**「クライアントに置いたキーで認可する設計」は この段階で破れる**（本記録の評価）
検知できたAPIのアクセスログに認可の失敗（401/403）と不正な形式のトークンでの試行を記録し、 同一接続元からの試行の急増を検知する　**本記録の評価である。** **ケースB（b）の「応答の違いを確認する」手口は、 大量の失敗を伴う**——成功する組み合わせを探す作業だからである。 **検知の要点は件数ではなく「同一接続元が多様なパターンを試している」ことである。** **注意喚起が提供した User-Agent の例（`curl/7.88.1`・`python-requests/2.34.2`）は 単独では判別に使えないが、「認可失敗の急増」と組み合わせれば絞り込みに使える**
侵入を防げた公開範囲の点検として、環境設定ファイル・バックアップファイルが Web から到達できないことを確認する　**本記録の評価である。ケースAの「機器の管理不備等を悪用した攻撃 （環境設定ファイルやバックアップファイルの窃取など）」に対応する。** **これは脆弱性ではないため、脆弱性スキャナでは検出されない**（本記録の評価）。 **確認は外部からの到達性で行う**—— 設定ファイルやバックアップの命名規則は推測されやすく、 **「置いてあるが参照されない」ファイルが残りやすい**
初期侵入公表されていない
**注意喚起は、被害組織がこの段階で検知できたかを述べていない。** **本記録として評価できるのは、検知の難易度がケースによって大きく違うという点である** （本記録の評価）。 **ケースB（c）の「窃取したAPIキーの使用」は、 正当なキーによる正当な形式のリクエストであるため、 認証だけを見れば正常に見える**—— **捉えられるのは振る舞い（平常と違う接続元・時間帯・取得量）である。** **一方ケースA・ケースCの脆弱性悪用は、 既知の脆弱性であるため検知の規則が既に存在することが多い。** **最も見えにくいのはケースB（b）である**—— 内部APIへのアクセスは、そのAPIが監視対象に入っていなければログにも残らない
侵入を防げた非公開APIを含むすべてのAPIエンドポイントでアクセス制御を実施し、 許可された利用者とHTTPメソッドのみを受け付ける　**注意喚起の対策（API経由のアクセスへの対策・第3項）であり、 本記録もケースBに対して最も効果が高いと評価する。** **「本来画面操作では実行できない内部API」が攻撃されているという指摘は、 画面側で制限していれば安全という前提が成り立たないことを意味する**—— **画面は入口の一つにすぎず、API は直接叩ける**（本記録の評価）。 **実施の前提はエンドポイントの棚卸しである**—— 一覧が無ければ「すべてのエンドポイント」を対象にできない。 **副作用として、画面側の実装が内部APIに依存している場合は 一律に閉じると自社アプリが動かなくなる**
影響を限定できたAPIトークンに有効期限を設定し、必要最小限の権限のみを付与する。 漏えいが疑われるトークンを速やかに無効化できるようにする　**注意喚起の対策（第4〜6項）であり、ケースB（c）に直接対応する。** **「他のシステムの侵害で窃取したAPIキーを使用する」手口に対しては、 キーが漏れることを前提に、漏れたときの有効範囲と有効期間を縮めるしかない** （本記録の評価）。 **要点は二つである**—— **①期限**（長期間有効なトークンは、漏えいから悪用までの時間差を吸収してしまう）、 **②権限**（漏えい前提で被害範囲を区切る）。 **実施には「どのトークンがどの機能に使われているか」の台帳が要る**
侵入を防げた既知の脆弱性の影響を受けるバージョンで運用している場合は、 修正済みのアップデートを適用する　**注意喚起の汎用的な対策であり、ケースA・ケースCに対応する。** **ただし本注意喚起の文脈では、これは対策の一部にすぎない**（本記録の評価）—— **ケースBは脆弱性ではないため、パッチ適用では閉じない。** **本記録が注意を促したいのは順序である**—— 「パッチを当てた」で点検を終えると、**ケースBの面が丸ごと残る**
侵入を防げた業務上必要のない管理機能がインターネットに公開されていないか確認し、 公開を停止する　**注意喚起の汎用的な対策であり、本記録が費用対効果が高いと評価する統制である。** **注意喚起が「管理・運用側で不特定多数の利用者からのアクセスを 想定していないシステム（BIツール・従業員向け管理システム）が被害に遭っている」と 冒頭と末尾の2か所で繰り返しているのは、ここに直結する。** **「想定していない」ことは「到達できない」ことを意味しない**（本記録の評価）—— 設計上の想定と、実際にインターネットから到達できるかは別の話である
権限昇格機会はあったが検知できず
**本記録の評価である（注意喚起は被害組織側の検知について述べていない）。** **権限の変更とアカウントの新規作成は、頻度の低い、明確に異常な事象である**—— **検知の規則として誤検知が少なく、実装も容易な部類に入る**（本記録の評価）。 **要点は、これらの操作が「管理画面経由」だけでなく 「API経由」でも記録されているかである。** **管理画面の操作ログだけを監査対象にしている実装では、 API 経由の権限変更が記録に残らない**—— これが本ケースで最も見落とされやすい点だと本記録は評価する
検知できた権限変更とアカウント作成を、経路（画面／API）を問わず監査ログに記録し、 発生時に通知する　**本記録の評価であり、本ケースに対して最も確実に効く統制である。** **「ユーザー権限を変更する」「不正なアカウントを作成する」のいずれも、 正規の運用では稀にしか起きない。** **通知の対象を「権限の昇格」と「管理者権限を持つアカウントの新規作成」に 絞れば、通知量は小さく保てる**（本記録の評価）。 **重要なのは経路を問わないことである**—— 管理画面のログだけでは API 経由の操作が落ちる
侵入を防げた権限を変更できるAPIを、専用のトークン・接続元・HTTPメソッドに限定する　**本記録の評価である。** **一般利用者向けアプリが使うトークンで 権限変更のAPIが叩けてしまう設計が、本ケースの前提になっている** （注意喚起は「本来画面操作では実行できない内部API」と表現している）。 **利用者向けトークンと管理操作用トークンを分離し、 管理操作のAPIは接続元を限定する**ことで、 **アプリを解析して得たキーでは権限変更に到達できなくなる**
影響を限定できた権限変更・アカウント作成のAPIにレート制限と利用回数制限を個別に設定する　**注意喚起の対策（第2項・「悪用のリスクが高い機能には個別に」）に対応する。** **権限変更やアカウント作成が短時間に繰り返されることは正規運用では起きない。** **制限は攻撃を止めるより「大量に行われること」を止める**ため、 **検知（上記）と組み合わせて初めて意味を持つ**（本記録の評価）
内部探索機会はあったが検知できず
**本記録の評価である（注意喚起は被害組織側の検知について述べていない）。** **ブラインド探索は本質的に大量のリクエストを必要とする**—— 1文字ずつ推定するため、**1件のアカウント情報を特定するだけで 数百〜数千回の試行が生じうる**（本記録の評価）。 **したがってこの段階は、検知の機会としては最も捉えやすい部類に入る**—— **同一の接続元・同一のエンドポイントへのリクエスト数の急増**として現れる。 **注意喚起の対策の第1項（単位時間あたりのリクエスト件数の制限）が この段階に直接効くのはこのためである**（本記録の読み取り）。 **見逃される理由は、API のリクエスト数を監視していないか、 しきい値が実害の出る水準より高く設定されているかのどちらかである**（本記録の評価）
侵入を防げたAPIへのアクセスに単位時間あたりのリクエスト件数の制限を設け、 短時間に繰り返されるアクセスや大量実行を防止する　**注意喚起の対策の第1項であり、本記録もブラインド探索に対して 最も効果が高いと評価する。** **ブラインド探索は試行回数に依存するため、レートを絞れば 現実的な時間内に完了しなくなる**（本記録の評価）。 **副作用は正規の自動化が止まることである**—— **実装前に正規利用の最大レートを測る必要がある。** **測らずに値を決めると、安全側に寄せて業務を止めるか、 緩めて攻撃を通すかのどちらかになる**
影響を限定できた検索・一覧取得のAPIで、1リクエストあたりの返却件数に上限を設け、 取得総量を監視する　**本記録の評価である。** **注意喚起が対策の第2項で 「検索処理など」を高リスク機能として名指ししている点に対応する。** **大量の個人情報の漏えいは、多数のリクエストによるか、 1リクエストでの大量取得によるかのどちらかで起きる**—— **レート制限は前者に効くが、後者には効かない**（本記録の評価）。 **両方を塞ぐには件数上限と総量監視が要る**
侵入を防げたデータベースへのクエリをパラメータ化し、 NoSQL においても入力を演算子として解釈させない実装にする　**本記録の評価である。** **NoSQLインジェクションは、 利用者の入力がクエリの演算子（比較・正規表現等）として 解釈されることで成立する**（本記録による補足）。 **SQL の対策として広く知られるパラメータ化が、 NoSQL では実施されていない実装が残りやすい**—— **「SQL を使っていないからインジェクションは関係ない」という 読み違いが起きやすい領域である**（本記録の評価）。 注意喚起が参考情報に **OWASP の API Security Top 10 2023 と REST Security Cheat Sheet** を挙げているのは、 この種の実装上の論点を含むためと読める
持ち出し公表されていない
**注意喚起は、個別の被害組織が持ち出しを検知できたかを述べていない。** **本記録として評価できるのは、注意喚起が汎用的な対策に 「不正アクセス検知体制の点検と検知時の初動対応を見直す」を挙げ、 さらに「漏えい発生時を想定した、平時からの顧客への二次被害防止等の呼びかけ （多要素認証など）」まで含めている点である**（本記録の読み取り）。 **後者は「漏えいは起きる」という前提に立った対策であり、 検知と封じ込めの前に備えておく性質のものである。** **注意喚起が「法令や契約等で定められた保存期間を過ぎたデータや 利用目的を終えたデータを残さない」を挙げているのも同じ系統である**—— **持ち出しを防ぐのではなく、持ち出せる量を減らす**（本記録の評価）
影響を限定できた法令や契約等で定められた保存期間を過ぎたデータ、 利用目的を終えたデータを残さない　**注意喚起の汎用的な対策であり、本記録が本注意喚起で最も見落とされやすいと 評価する項目である。** **これは侵入も持ち出しも防がない**—— **他のすべての対策が破られたときにだけ効く。** **効き方は被害規模の縮小である**—— **漏えいした件数が、通知対象・報告義務・二次被害の規模をそのまま決める** （本記録の評価）。 **実施の難しさは技術ではなく合意形成にある**—— 事業側は「あとで使うかもしれない」データを残したがる。 **保存期間を定めて自動削除を実装するところまで進めないと、 方針だけでは減らない**
影響を限定できた漏えい発生時を想定し、平時から利用者へ二次被害防止の呼びかけ （多要素認証の有効化など）を行う　**注意喚起の汎用的な対策である。** **本記録はこれを「自組織の防御」ではなく「利用者の防御」として評価する**—— **漏えいした認証情報が他サービスで使い回されている場合、 被害は自社の外で起きる。** **平時から多要素認証を促しておけば、漏えい後の二次被害が下がる。** **副作用は、過度に行うと読み流されることである**（本記録の評価）—— **漏えい後に初めて呼びかけても、そのときには遅い**という点が要点
影響を限定できたWebサーバー等が侵害された後の横展開対策を見直す　**注意喚起の汎用的な対策である。** **ケースB（c）の「他のシステムの侵害で窃取したAPIキーを使用する」は、 まさに横展開の経路である**（本記録の読み取り）—— **一つのシステムの侵害が、そこに保管されていたキーを通じて 別のシステムの侵害につながる。** **したがって「Webサーバーに何のキーが置かれているか」の棚卸しが、 横展開対策の具体的な中身になる**（本記録の評価）
