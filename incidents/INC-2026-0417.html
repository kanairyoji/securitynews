INC-2026-0417PoeLLM が AI 基盤3,400台を侵害

GitHub に置かれた詩から C2 の IP アドレスを導くマルウェア「PoeLLM」が、公開された AI/LLM 基盤を狙って3,400台超のサーバを侵害しボットネット化した——Lumen Black Lotus Labs は2026年10月7日、キャンペーンを「Canto Incognito」と名づけて公表した。詩は nodejs.org のフォークに `dash.css` として置かれた「On the Nature of Connection」で、本文から4語を抜き出して検体内の辞書で数値に変換すると現在の C2 の IPv4 アドレスになる。運用者は詩を書き換えるだけで C2 を移せるため、検体を解析しない限りネットワーク監視には何も現れない。被害サーバは LiteLLM・Ollama・Gotenberg・Gitea の公開インスタンスが中心で、侵害後は XMRig と Iron で暗号通貨を採掘しつつ、自ら走査機・攻撃機に転じて次の被害を作る

初報: 2026年10月7日 最終更新: 2026年10月7日

2026年10月7日、Lumen Technologies の Black Lotus Labs が、公開された AI/LLM 基盤を狙うマルウェア「PoeLLM」とキャンペーン「Canto Incognito」を公表しました。2026年4月から活動しており、3,400台を超えるサーバが侵害されています。被害は米国と西欧に集中し、侵害されたのは LiteLLM・Ollama・Gotenberg・Gitea の公開インスタンスが中心です。

技術的に目を引くのは C2 の隠し方です。検体は GitHub 上の詩から4語を抜き出し、検体内に焼き込まれた辞書で数値に変換して C2 の IPv4 アドレスを組み立てます。詩はnodejs.org のソースをフォークしたリポジトリに dash.css という名前で置かれており、題は「On the Nature of Connection」。運用者は詩の数語を書き換えるだけで C2 を移せます。リンクも添付も暗号文も無いため、詩そのものを見た者には悪性と判断する手がかりがなく、Black Lotus Labs によれば多くの C2 は群衆参加型のセキュリティツールで一度も検出されませんでした。

侵害されたサーバは暗号通貨の採掘（XMRig・Iron、採掘サービスは Kryptex）に使われるだけでなく、自ら走査機・攻撃機に転じて次の被害を作ります。攻撃者の狙いは、AI 基盤が強力な GPU を積み、設定が甘く、インターネットに露出していることにあります。公表資料から確認できた範囲を、観測事実と本記録の評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

公開された LiteLLM・Ollama・Gotenberg・Gitea・Ivanti Sentry の既知の脆弱性 （主経路は LiteLLM の CVE-2026-42271、CVE-2026-48710 との連鎖で認証不要 RCE）を 悪用して ELF マルウェア PoeLLM（ファイル名 libgcrypt）を配置する。検体は GitHub の 詩から4語を抜き出し検体内の辞書で IPv4 に変換して C2 を解決する（詩の書き換えだけで C2 を移せる）。侵害後は XMRig・Iron で Kryptex へ採掘しつつ、3000/4000番ポートを 走査し、見つけた標的へ HTTP POST を送って C2 からの取得を実行させることで自己増殖する。 遠隔シェル機能を備え、SSH 等への分散総当たりの試行も観測されている。

  • Black Lotus Labs は2026年6月初旬に基盤を発見した後、約4か月をかけて解析し、 2026年10月7日に C2 の IP 一覧・抽出ロジック・IoC を伴う形で公表した。 公表と同時に C2 サーバとの双方向の通信を遮断している
    理由は公表されていない
    トレードオフ: **公表を遅らせた分だけ、未感染の組織が自衛する機会が失われた**（本記録の評価）。 発見から公表までの約4か月は、C2 の全容・抽出ロジック・IP 一覧という 「防御側が自前で導出できる情報」を揃えるために使われたとみられるが、 その間に被害は増え続けている。逆に早期公表は、運用者に詩の仕組みの 露見を知らせ、別の配布経路へ移る時間を与えたはずである。 **どちらを取ったかの説明は公表資料に無い。**

詩の4語が C2 の IP アドレスになる——運用者は詩を書き換えるだけで基盤を移せ、ネットワーク監視には何も現れない原因・手口出典 [1] [2] [4]

PoeLLM は libgcrypt という名前の ELF ファイルである。起動すると GitHub のリポジトリに置かれた詩を取得する。リポジトリは nodejs.org のウェブサイトのソースをフォークしたもので、詩は dash.css というファイルに入っている。題は「On the Nature of Connection」、投稿者は GitHub アカウントejejejdfbbebe、最初のコミットは2026年4月13日である。

検体は詩の本文から、固定の文字列を目印にして4語を抜き出す。Black Lotus Labs が示した抽出ロジックは次のとおりである。関数 extract_poem_phrase_field が大文字小文字を区別せずに3語を取る——第1語は "In the silent hum of " と "," の間、第2語は "each pulse of " と " threading" の間、第3語は "Beyond the wall of " と"," の間。第4語は別の処理（0x44a8db–0x44a99b）で、" of distant servers" を探し、直前の空白まで戻り、その語の前4バイトが "the " であることを確かめてから、"the " の次の語を使う。

抜き出した4語は、検体内に焼き込まれた辞書で数値に変換される。2026年9月に観測された版では driver=92・diode=119・decryption=165・string=74 で、これを並べると現在の C2 の IPv4 アドレスになる。運用者が詩の数語を書き換えれば、検体は自動的に新しい C2 を計算する。検体を更新する必要がない。詩は初回コミット以降11回書き換えられており、変わるのは抽出対象の語だけで、解析ロジックは一度も変わっていない。

Black Lotus Labs の Ryan English はこの設計の意味をこう説明している。「詩を使う手口のいちばん興味深い点は、C2 通信に使われる IP アドレスが被害者のネットフローの外からは見えないということだ。他のマルウェアの検体ならハードコードされた予備の C2 アドレスや、インターネット上のどこかに書かれたIP アドレスを指す URL があるかもしれない」「たまたま見かけた人にとっては、これは GitHub にある単なる詩だ。リンクも無く、落とすファイルも無く、高度なモデルでも悪性と判定できそうな暗号文も無い。その詩を参照しているマルウェアを手にしていない限り、研究者がこの詩を悪性だと見分ける理由も、そこに隠された IP アドレスを知る方法も無い」（原文英語）。実際に「このキャンペーンで使われた C2 の多くは、群衆参加型のセキュリティツールで一度も検出されなかった。この層の難読化が C2 の耐久性を高めるのに大いに役立ったことを示している」（原文英語）。

被害は公開された AI 基盤に集中し、侵害後は採掘機と走査機を兼ねて次の被害を作る被害規模・影響範囲出典 [1] [2] [3] [4]

被害サーバは3,400台超（累計）で、米国と西欧に集中している。動いていたソフトウェアは LiteLLM と Ollama（いずれも LLM 実行・ゲートウェイ基盤）が中心で、数百台は Gotenberg（PDF 変換）と Gitea（開発基盤）だった。商用製品ではIvanti Sentry の被害も確認されている。

侵入経路として Black Lotus Labs が最も可能性が高いとみているのは、LiteLLM のMCP 疎通試験用エンドポイント /mcp-rest/test/connection に対するコマンドインジェクション（CVE-2026-42271）である。この脆弱性は当初「認証を要する」ものとして高深刻度で公表されたが、Horizon.ai の研究者が別の脆弱性 CVE-2026-48710 と連鎖させれば認証不要の遠隔コード実行になることを確認している（BleepingComputer 報道）。発見の契機になったのは Ivanti Sentry のCVE-2026-10520 で、2026年6月初旬に侵害された Sentry が専用サーバ5.78.73[.]122 へ通信し、その直後に他の脆弱な機器を走査し始めていた。

侵害された機器は2つの役割を同時に負う。第一に暗号通貨の採掘機である——検体は XMRig と Iron を配置し、ロシアの採掘サービス Kryptex に接続する。第二に走査機・攻撃機である。感染機は 3000番（Gotenberg）と 4000番（LiteLLM）を走査し、見つけた標的の公開ポートへ HTTP POST を送って C2 からマルウェアを取得させる。この結果、ボットネットは自分で自分を増やす。English は「このボットネットの成長を通じて、攻撃者は AI を備えたプロキシの私兵団を実質的に作り上げた。それは今後も増え続け、攻撃・認証情報の窃取・トークンの悪用などにさらなる経路を与える」「もし1つの攻撃サーバがセキュリティコミュニティに通報されても、攻撃者は容易に切り替えて、侵害済みの他の何百台を経由して攻撃を中継できる」（原文英語）と述べている。

検体には遠隔シェル機能もあり、被害サーバ上の AI モデルや公開サービスを下流の侵害に悪用できる作りになっている。ただし採掘と走査を超える成果が実際に挙がったかどうかは「調査中」とされている。 直近には SSH やその他のログインポータルへ向かう通信があり、分散型の総当たり攻撃を試している可能性が指摘されているが、公表資料自身が「その能力の成熟度は不確かなままである」としている。

最盛期は2026年6月中旬で、影響を受けたサーバは約2,200台、1日あたりの稼働は約800台だった。C2 は少なくとも11基が立ち上げられている。インフラの解析では、複数の C2 サーバがルータの管理画面を持ち、そこに脆弱性があった——最初にブラジルのルータだった C2 の管理画面は CVE-2018-21027 とCVE-2018-21028 の影響を受ける状態だったが、Black Lotus Labs はこれが実際に悪用された直接の証拠は見つけていない。

帰属はイタリア語話者との中程度の確度にとどまり、研究者は C2 との通信を遮断した帰属出典 [1] [2] [4]

Black Lotus Labs は、PoeLLM をイタリア語を話す金銭目的の攻撃者に結びつけている。根拠は①検体内および攻撃者の GitHub ページのコメントがイタリア語であること②ネットフローの分析が攻撃者のイタリア所在を示すこと ③テストおよび C2 基盤にイタリア国内のサーバが使われていることである。また 185.119.19.171（イタリア）がC2 とボットネット運用の管理インターフェースであると中程度の確度で評価している。キャンペーン名「Canto Incognito」（匿名の詩歌）は、悪性の指令を詩に隠すことに由来する。

ただしこれは確定的な帰属ではない。 研究者は「確度の高い帰属はできなかった」としており、運用に何人が関わっているかも分からない。他の集団・キャンペーンとのつながりも観測されていない。詩そのものは AI が書いたとみられるという見方も示されている。

対応として Black Lotus Labs は PoeLLM の C2 サーバとの双方向の通信を遮断し、新たな通信の監視を続けると述べている。同社の Lumen Defender の利用者は発見時点からこれらのサーバから保護されているとしている。被害者への通知が行われたかどうかは公表資料に書かれていない。

「AI の導入は速いが、その基盤にパッチを当てて守る作業は追いついていない」——露出面の棚卸しに戻るほかない対策・注意喚起出典 [1] [3] [4]

Black Lotus Labs が示した推奨対応は次のとおりである。①公表された IoC との突合をネットワークログで行う ②外部への露出を定期的に棚卸しし、サービスのポートは可能な限り外部からの到達を制限する ③ルータ・ファイアウォール・IoT の定石（定期的な再起動と適時のパッチ適用）を守る ④外部からの攻撃面を減らすためマネージド SASE の利用を検討する ⑤攻撃面管理・監視のツールを使う。BleepingComputer は加えて、最新の更新の適用、重要資産の公開範囲の縮小、外部アクセスを信頼できる IP に限定することを挙げている。

研究者はこの種の攻撃が今後増えるとみている。「AI は LiteLLM・Ollama・Gotenbergのようなツールの導入を容易にしたが、AI は必ずしも、それらのサービスにパッチが当たっていて攻撃者から守られているかを確かめてはくれない。AI を備えたサーバが増えるにつれ、PoeLLM のようなマルウェアは広がり続ける」（原文英語）。

キャンペーンの特異性についても研究者の見方が示されている。「Canto Incognitoキャンペーンは、複数の AI 関連サービスを標的にしている点で比較的珍しい。今年の他の目立ったキャンペーン、たとえば LiteLLM のサプライチェーン侵害は単一のサービスに絞られ、公開情報によれば約2,500の被害者に影響した。3,000を超える PoeLLM の被害者の集まりは、常に複数の脆弱なサービスを抱えているように見える」「もし攻撃者が1つか2つの脆弱性に絞っていたら、被害者の候補はすぐに枯れていたかもしれない。しかし対象を広げたことで、より大きく、より強力（そしてより儲かる）ボットネットが可能になった」（原文英語）。

「詩」は装飾ではなく、C2 を公開情報の外に出すための設計である——露出した AI 基盤は「GPU 付きの無管理サーバ」として扱われている評価・解釈出典 [1] [2] [3] [4]

以下は本記録の評価である。

第一に、詩という体裁は話題性のためではなく、検知経済を変えるための設計である。一般的なマルウェアは、C2 のアドレスをどこかに書かねばならない。ハードコードすれば検体解析で露出し、ドメインに置けば DNS・証明書・レピュテーションの各層に痕跡が残る。PoeLLM は「平文の英語の単語」を公開リポジトリに置いた。これはコンテンツとしては完全に無害で、静的解析・文字列検査・機械学習のいずれにも引っかからない。C2 の実体は検体の中の辞書にしか存在せず、詩と辞書を両方持たない者には復元できない。 研究者が「多くの C2 が群衆参加型ツールで一度も検出されなかった」と述べているのは、この設計が実際に効いたという意味である。防御側にとっての含意は単純で、外向き通信の宛先を「既知の悪性か」で判定する層は、この種の C2 には効かない。効くのは「許可した宛先以外へ出さない」エグレス制御のほうである。

第二に、標的の選び方が「脆弱性がある製品」ではなく「GPU があって管理が薄い場所」になっている。LiteLLM・Ollama・Gotenberg・Gitea に共通するのは、導入が数分で済み、既定で外部に開き、運用の持ち主が曖昧になりやすいことである。公表資料が「露出した AI/LLM サービスは、ソフトウェアの脆弱性のためだけでなく、有用なデータを含み、採掘に適した強力なハードウェア上で動いていることからも価値がある」（原文英語）と書いているとおり、攻撃者から見れば採掘資源である。自組織が把握していない AI 基盤の数が、そのまま露出面になる。 AI の実験的導入は現場主導で進むため、CMDB にも資産台帳にも載らない。ここは技術ではなく棚卸しの統制の問題である。

第三に、本件は「侵害された機器が攻撃基盤になる」構図を再確認させる。3,000台超が走査機・攻撃機を兼ねている状態は、個々の被害組織にとっては「採掘で電気代とクラウド費用が増える」以上の意味を持つ。自社のサーバが他組織への攻撃元として記録される——通報・ブロックリスト収載・場合によっては法的な照会の対象になる。採掘を「軽い被害」として優先度を下げる判断は、この二次的な帰結を見落としている。

第四に、採掘にとどまっている今の状態を前提にしない方がよい。遠隔シェル機能があり、被害サーバ上には AI モデルと、そのモデルへアクセスするためのトークンがある。研究者が「認証情報の窃取、トークンの悪用などにさらなる経路を与える」と述べているのは、能力としてすでに届いているという意味である。LLM ゲートウェイは定義上、組織内の複数のモデル・API キーへの通り道である。そこを採掘機として運用されている間は、同じ機器から API キーを抜くこともできる。採掘の検知（CPU/GPU 使用率の異常）は入口であって、調査の終点ではない。

運用者は GitHub のリポジトリに置いた詩（layer 1）の数語を書き換えるだけで C2 を 移せる。検体は詩から4語を抜き出し、検体内の辞書で数値に変換して C2 の IPv4 アドレスを組み立てる（layer 2）。侵害されたサーバ（layer 3）は Kryptex への 採掘と、3000/4000番ポートの走査・HTTP POST による配布を同時に行い、 次の被害サーバ（layer 4）を作る。詩そのものは無害なコンテンツなので、 C2 の実体は検体を解析しない限り公開情報からは復元できない。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Black Lotus Labs は2026年6月初旬に基盤を発見した後、約4か月をかけて解析し、 2026年10月7日に C2 の IP 一覧・抽出ロジック・IoC を伴う形で公表した。 公表と同時に C2 サーバとの双方向の通信を遮断している部分的に機能**本記録の評価である。** 抽出ロジックのアドレス範囲まで示した公表は、 防御側が自前で C2 を導出できるという点で質が高い。一方、公表までの約4か月間、 被害は増え続けており（図では late June と early October にピーク）、 被害組織への通知が行われたかどうかは公表資料に書かれていない。 早期の限定共有（ISAC・当該ベンダー）が行われたかが分からないため、 遅れの妥当性は判断できない。
CISO・経営層への示唆
  • 「社内で誰が立てたか分からない AI 基盤」の数が、そのまま露出面になる——AI の資産棚卸しを先に作る
    被害の中心は LiteLLM・Ollama・Gotenberg・Gitea という、導入が数分で済み 既定で外部に開くソフトウェアである。これらは現場の実験として立ち上がり、 資産台帳にも CMDB にも載らないことが多い。公表資料も 「AI はツールの導入を容易にしたが、AI は必ずしも、それらのサービスに パッチが当たっていて守られているかを確かめてはくれない」（原文英語） と指摘している。
    取るべき行動 AI/LLM 関連基盤（ゲートウェイ・推論サーバ・補助ツール）の配備を部門横断で 洗い出し、台帳に載せる。外部到達性を全件で確認し、公開が必要なものだけを 残して認証と IP 制限をかける。新規配備の届け出を、クラウドアカウントの 利用申請と同じ扱いにする。
  • 「採掘されただけ」は軽い被害ではない——自社のサーバが他組織への攻撃元として記録される
    本キャンペーンでは侵害サーバが走査機・攻撃機を兼ねており、3,000台超が 次の侵害を作っていた。研究者は「1つの攻撃サーバが通報されても、 攻撃者は侵害済みの他の何百台を経由して攻撃を中継できる」（原文英語）と 述べている。採掘のコスト増だけを被害と見ると、通報・ブロックリスト収載・ 取引先からの照会といった二次的な帰結を見落とす。
    取るべき行動 暗号通貨採掘の検知を「低優先度のポリシー違反」から「侵害の確定事象」へ 格上げし、封じ込めと全面調査の手順に乗せる。自組織の IP が外部の ブロックリスト・脅威情報に載っていないかを定期的に確認する担当を決める。
  • C2 の宛先レピュテーションに依存した防御は、この設計には効かない——「許可以外を出さない」へ投資の軸足を移す
    C2 アドレスは公開リポジトリの詩と検体内の辞書の組み合わせでしか復元できず、 研究者によれば「このキャンペーンで使われた C2 の多くは、群衆参加型の セキュリティツールで一度も検出されなかった」（原文英語）。 既知の悪性を止める層は、原理的に空振りする。
    取るべき行動 サーバ群の外向き通信をエグレス許可リストで統制する（既定拒否）。 許可リスト化が難しい環境では、少なくとも宛先ポート分布・新規宛先の 出現を監視し、未知の宛先への定常接続を検知対象にする。
  • LLM ゲートウェイは「組織内の複数モデルと API キーへの通り道」である——採掘の検知で調査を終えない
    検体には遠隔シェル機能があり、研究者は「認証情報の窃取、トークンの悪用などに さらなる経路を与える」（原文英語）と述べている。実際の窃取は「調査中」で 未確認だが、能力としては届いている。ゲートウェイを侵害されれば、 そこを通る全モデルの鍵と履歴が射程に入る。
    取るべき行動 LLM ゲートウェイの侵害を前提にしたシナリオで、保持する API キーの 棚卸しと短命化・シークレットマネージャ管理への移行を進める。 採掘の検知時には「同一ホストから出たモデル API 呼び出し・鍵の利用」を 必ず遡って確認する手順を作る。
セキュリティ技術者への示唆
  • 試験用・疎通確認用のエンドポイントを本番構成に残さない——主経路は `/mcp-rest/test/connection` だった
    主たる侵入経路とみられるのは LiteLLM の MCP 疎通試験エンドポイントへの コマンドインジェクション（CVE-2026-42271）である。当初は「認証が必要」と されたが、CVE-2026-48710 との連鎖で認証不要の RCE になることが確認された。 「認証が必要だから低リスク」という前提は連鎖で崩れる。
    取るべき行動 LiteLLM を含む AI 基盤の構成から、試験・デバッグ・疎通確認の エンドポイントを無効化または到達不能にする。最新版へ更新し、 `/mcp-rest/` 配下への外部アクセスをリバースプロキシで拒否する。 「認証必須」とされた脆弱性でも、認証バイパスとの連鎖を前提に優先度を付ける。
  • 走査は 3000番・4000番に向かう——自組織から出ていく分も監視対象にする
    感染機は Gotenberg の 3000番と LiteLLM の 4000番を走査し、見つけた標的へ HTTP POST を送って C2 からの取得を実行させる。入ってくる走査だけを見ていると、 自組織が加害側に回っていることに気づけない。
    取るべき行動 フロー監視で「自組織の IP から外部の 3000/4000番への接続」を検知ルールにする。 併せて外部から自組織の 3000/4000番への接続を遮断し、該当サービスが 公開されていないかを確認する。
  • `libgcrypt` という名前の ELF を疑う——正規ライブラリ名を騙る実行ファイルの出所を検証する
    PoeLLM は `libgcrypt` という名前の ELF ファイルである。プロセス一覧・ ファイル名の目視では正規の暗号ライブラリと区別できない。
    取るべき行動 サーバ上の実行ファイルがパッケージ管理の管理下にあるかを照合する点検を行う （rpm -V / dpkg -V 相当、またはファイル整合性監視）。 公表された2つの IoC（C2 の IP 一覧・検体のハッシュ）と突合する。
  • GPU 使用率は「推論要求数との相関」で見る——AI ワークロードの変動に採掘が紛れる
    AI 基盤の GPU は平常時も高負荷になるため、採掘の負荷が異常として見えにくい。 攻撃者が AI 基盤を選ぶ理由のひとつがこれである。
    取るべき行動 GPU/CPU 使用率を、ゲートウェイが処理した推論要求数と並べて監視する （要求が無い時間帯の高負荷を検知する）。クラウド配備では課金額の 異常検知アラートを設定する。
  • 詩のようなデータは「設定の配布経路」として一般化できる——外部の平文リソースを読む実装を点検する
    本件の本質は「無害に見える公開コンテンツを設定の配布経路にした」ことである。 同じ構造は、自組織のソフトウェアが外部の公開リソース（Gist・Pastebin・ 公開バケット・ブログ本文）から設定値を読む実装にも当てはまる。
    取るべき行動 自組織のアプリケーション・エージェントが実行時に外部から読む 設定・パラメータの経路を洗い出し、改ざんされた場合の影響を評価する。 読み取り先を自組織管理下に限定し、署名検証を入れる。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ LiteLLM・Ollama・Gotenberg・Gitea のいずれかをインターネットから到達できる状態で運用している（検証環境・PoC 環境を含む）本キャンペーンの被害の中心がこの4製品である。走査は 3000番・4000番に向けて 日常的に行われており、公開されていること自体が被害の前提条件になる。 検証用に立てて放置した環境がそのまま対象になる。
システム構成□ AI/LLM 基盤が GPU を積んだサーバ（オンプレ・クラウドいずれも）で動いており、使用率の監視がワークロード指標と紐づいていない攻撃者が AI 基盤を選ぶ理由は GPU そのものである。使用率だけを見る監視では 採掘が AI の負荷変動に紛れる。推論要求数との相関、またはクラウド課金額の 異常としてしか現れない。
運用・監視□ サーバ群からの外向き通信が既定許可で、エグレスの許可リストも新規宛先の監視も無いC2 アドレスは公開情報から復元できず、宛先レピュテーションでは検知できない。 多くの C2 は群衆参加型ツールで一度も検出されなかった。 既定拒否のエグレス制御だけがこの設計に効く層である。
運用・監視□ AI 関連の配備が現場主導で行われ、資産台帳・CMDB に載らない配備が存在しうる露出面の棚卸しは台帳が前提になる。台帳に載らない配備は点検の対象にならず、 公開されたまま残る。本キャンペーンが3,400台に届いたのは、 この種の「持ち主が曖昧な配備」が大量にあるからである。
委託・第三者部品□ 境界機器（Ivanti Sentry 等）の脆弱性対応が、ベンダー通知待ちで、適用までの目標時間が定められていない発見の契機は Ivanti Sentry の CVE-2026-10520 による侵害であり、 侵害された機器は直後に他機器の走査を始めていた。境界機器は 侵害された瞬間に攻撃基盤に転用される位置にある。
体制・契約□ 暗号通貨採掘の検知が「低優先度のポリシー違反」として扱われ、侵害として封じ込め・全面調査の手順に乗らない採掘は侵害の結果であって全体ではない。本件では侵害サーバが走査機・攻撃機を 兼ね、遠隔シェル機能も備えていた。採掘を軽く扱うと、加害側への転用と 認証情報の射程を見落とす。
