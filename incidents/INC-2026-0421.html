INC-2026-0421悪性Firefox拡張16本がウォレット窃取

Socket Threat Research は2026年10月7日、**暗号資産ウォレットの利用者を狙う Firefox 拡張機能16本**を公表した。 **4本は Ethereum ウォレット Rabby Wallet のクローン**で、 **本物の Rabby のコードをほぼそのまま取り込んだ上に、 秘密鍵・ニーモニックの取り込み処理の直後へ窃取関数を差し込んである**（出典1）—— **表示名は `Raabby WaIIet`（r と l を重ねた綴り違い）。** **残る12本は OKX Wallet を模した小型の偽ウォレット**で、 **12語または24語の復元フレーズを受け取って送信する。** **送信先はいずれも攻撃者が用意した Cloudflare Workers のホストで、 15本が `icy-star-f45c[.]workers[.]dev`、 壊れている1本だけが別ホストを使う**（出典1）。 **Rabby クローンは平文の復元フレーズを GET のクエリ文字列に載せて送る** —— **秘密が送信先だけでなく、経路上のリクエストログにも残る形である。** **全16本のマニフェストが Firefox のデータ収集権限を「none」と宣言しており、 実際のコードと矛盾する**（出典1）。 **Mozilla は2026年10月5日までにこれらを非公開にした**（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は、利用者が自分で入力した秘密を奪う経路である** （本記録の整理）。 **脆弱性の悪用ではない** —— **攻撃者が用意するのは「本物と同じ、あるいは本物に見える ウォレットの取り込み画面」であり、 利用者はそこに復元フレーズまたは秘密鍵を入力する。** **Rabby クローンでは、入力された値は正規のウォレット処理にも渡される** （出典1）—— **ウォレットは正常に動くため、入力した側に異常が見えない。** **以下の連鎖は Socket の静的解析の結果に基づく**（出典1）—— **実際に被害が発生した件数・金額は公表されていない**（unknowns 参照）。

  1. 1. 初期侵入
    **利用者が、ウォレットに見える拡張機能を Firefox に導入する。** **16本は Firefox の拡張機能として配布されていた**（出典1）。 **Socket の記述** —— **「拡張機能はウォレットのポータル、デスクトップ用ユーティリティ、 ブラウザのツールを装う」**（原文英語の要旨）。 **Rabby クローンは本物の Rabby のコードを取り込んでおり、 描画される画面には「Rabby Wallet」と出る**（出典1）—— **文書タイトルだけが `Raabby WaIIet`。** **OKX クローンは `Portal WALLET` という名称の React のフロントエンドで、`okui-*` のクラスを残し、 OKX Web3 の公式ヘルプと利用規約へリンクしている**（出典1）。
  2. 2. 検知回避
    **宣言と表示の両方で、実際の挙動を隠している**（出典1）。 **Socket が挙げた点** —— **①全16本のマニフェストが Firefox のデータ収集権限を 「none」と宣言しており、 復元材料を扱って送信するコードと矛盾する。** **②1本の背景スクリプトのコメントは 「ハッシュと単語数だけが端末から出る」と主張しているが、 実際のペイロードは平文のフレーズを引数 `w` に入れている** （FNV-1a の値は重複排除にのみ使われる）—— **Socket はこれを「善意の分析ではなく隠蔽の直接の証拠」と 評価している。** **③Rabby クローンのブランド書き換えが不完全である** —— **描画される画面は「Rabby Wallet」、 文書タイトルは `Raabby WaIIet`、 マニフェストの作者は `Debrunk`。** **④運用者はパッケージ名・版・拡張機能ID・説明文・見せ方を 入れ替えつつ、同じウォレット画面・同じ窃取処理・ 同じ目印・同じ通信先を使い回している**（出典1）。 **さらに Rabby クローンのマニフェストは、 観測された窃取に必要な範囲を超える権限を要求している**（出典1）—— **常駐する背景ページ、全フレームで `document_start` に走る コンテンツスクリプト、`file://*/*`・`http://*/*`・`https://*/*` への 一致、`webRequest` と `webRequestBlocking`、 任意の HTTP/HTTPS ホストへのアクセス、 CSP での `unsafe-eval` と WebAssembly の評価許可、 ストレージ・無制限ストレージ・アクティブタブ・ コンテキストメニュー・通知の各権限。** **Socket は「静的解析では別のフォームグラバーの存在を 確認できなかったため、 閲覧データの窃取が実証されたとするのではなく 『過剰なアクセス』と記述すべきである』としている**（原文英語の要旨）—— **本記録もこの区別に従う。**
  3. 3. 収集
    **利用者が入力した復元フレーズ・秘密鍵を、 正規の処理と同じ地点で受け取る。** **Rabby クローン（背景スクリプト）**（出典1）—— **`background.js` の冒頭で `self._lv` を設置する。** **この関数が受け付けるのは3種類のみ** —— **12語の文字列、24語の文字列、 秘密鍵と整合する64文字の16進文字列。** **メモリ上で重複を排除し、平文を URL エンコードして送る。** **`self._lv` の呼び出しは、正当に見えるウォレット操作の 「直後」に挿入されている** —— **`importPrivateKey`、`createKeyringWithMnemonics`、 ニーモニックのキーリング／アカウント取り込み経路。** **Socket の評価** —— **「この配置により、攻撃者はウォレットが受け取るのと同じ秘密を得る。 一方で下層のウォレットの流れはそのまま残る」**（原文英語の要旨）。 **Rabby クローン（画面側）**（出典1）—— **`977.js` が第2の窃取補助関数を定義し、 画面の取り込み経路にインラインの複製を含む。** **確認された呼び出し地点は、 `generateKeyringWithMnemonic` に渡されたニーモニック、 新規利用者の取り込みで入力された復元フレーズ、 秘密鍵の取り込みで入力された秘密鍵、 パスワード保護されたキーリング作成時に使われた復元フレーズ。** **画面側は `action` を `ui`、背景側は `import` とタグ付けする** —— **複数の経路があるため、同じ秘密について 複数のリクエストが発生しうる**（出典1）。 **OKX クローン**（出典1）—— **フロントエンドが `{ type: "SEED_PHRASE_IMPORT", data: { seedPhrase: rawPhrase }, timestamp: ... }` を送り、 背景側は `SEED_PHRASE_IMPORT` と旧名 `WALLET_SYNC` を受け付け、 前後の空白を除去し、空を拒否し、 ちょうど12語または24語を要求し、平文を重複排除する。**

Socket の記述（出典1。原文英語の要旨）—— Rabby クローンの background.js は冒頭で self._lv を設置する。 この関数が受け付けるのは3種類のみ ——

Socket の評価（原文英語の要旨）—— 「この配置により、攻撃者はウォレットが受け取るのと同じ秘密を得る。一方で下層のウォレットの流れはそのまま残る。」

本記録が重く見るのはこの一文である（本記録の評価）—— ウォレットは正常に動く。

偽サイトであれば、送金が失敗する・画面が違う・URL がおかしいといった「後で気づく」瞬間がある。 本件にはそれが無い。 利用者は本物の Rabby を使っている状態になり、残高も取引も正しく表示される。

本記録の読み —— 二重化は収集の取りこぼしを減らすための設計である。 攻撃者は「1回でも取れれば終わり」の性質を理解している（復元フレーズは1度漏れれば無効化できない）。

こちらは「本物を動かす」部分が無く、純粋なフィッシングである（本記録の整理）—— ただし okui-* のクラスを残し、OKX Web3 の公式ヘルプと利用規約へリンクすることで信用を借りている。

宣言と実装が矛盾したまま配布されていた評価・解釈

全16本のマニフェストが、Firefox のデータ収集権限を「none」と宣言している（出典1）。

一方でコードは、復元フレーズと秘密鍵を扱い、外部へ送信している（出典1）。

Socket はこの矛盾を明示している。

さらに、1本の背景スクリプトのコメントは「ハッシュと単語数だけが端末から出る」と主張しているが、実際のペイロードは平文のフレーズを引数 w に入れている（出典1）—— FNV-1a の値は重複排除にのみ使われる。 Socket の評価 —— 「このコメントとコードの矛盾は、善意の分析ではなく隠蔽の直接の証拠である」（原文英語の要旨）。

本記録の評価 —— ここには2つの別の問題がある。

①隠蔽の意図の証拠としての価値。 「知らずに秘密を扱っていた」という弁明を封じる。 コメントが実装と逆のことを書いているのは、読む者を欺くためにしか説明できない。

②配布前に止まらなかったことの意味。 宣言と実装の矛盾は、機械的に突き合わせられる性質のものである（本記録の評価）—— 「データ収集なし」と宣言しているパッケージがネットワークへ POST / GET する経路を持つかは、静的解析で判定しうる。

ただし、Mozilla による審査の経緯は公表されていない（unknowns 参照）—— 本記録は「審査が機能していなかった」と断定しない。 書けるのは「宣言と実装が矛盾した状態で16本が配布されていた」という事実までである。

権限の広さについても記録しておく（出典1）—— Rabby クローンのマニフェストは Firefox の Manifest V2 で、常駐する背景ページ、全フレームの document_start で走るコンテンツスクリプト、file://*/*・http://*/*・https://*/* への一致、webRequest と webRequestBlocking、任意の HTTP/HTTPS ホストへのアクセス、悪性 Worker への明示的なアクセス、CSP での unsafe-eval と WebAssembly の評価許可、ストレージ・無制限ストレージ・アクティブタブ・コンテキストメニュー・通知の各権限を要求する。

Socket の留保（原文英語の要旨）—— 「コンテンツスクリプトの広さは、観測されたウォレットの秘密の持ち出しに必要な範囲を超えている。静的解析では別のフォームグラバーの存在を確認できなかったため、リスクは『閲覧データの窃取が実証された』ではなく『過剰なアクセス』と記述すべきである。」

本記録もこの区別に従う。 ただし、権限があるということは、運用者が後から機能を追加できたということでもある（本記録の評価）。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
利用者が入力した復元フレーズが、ウォレットと攻撃者の両方へ渡る流れ
layer 0 は利用者——Firefox に拡張機能を導入し、 ウォレットの取り込み画面に復元フレーズまたは秘密鍵を入力する。 layer 1 は配布経路——Firefox の拡張機能として配布された16本。 全16本のマニフェストがデータ収集権限を「none」と宣言していた。 Mozilla は2026年10月5日までに非公開にした。 layer 2 は2つの族——Rabby Wallet のクローン4本 （本物のコードを取り込み、表示名だけ `Raabby WaIIet`）と OKX Wallet を模した小型12本（`Portal WALLET`）。 layer 3 は窃取の地点——Rabby クローンは `importPrivateKey` / `createKeyringWithMnemonics` の直後に `self._lv` を差し込み、画面側の `977.js` にも別経路を持つ。 OKX クローンは `SEED_PHRASE_IMPORT` / `WALLET_SYNC` を 背景スクリプトで受ける。 layer 4 は分岐——正規のウォレット処理（Rabby クローンのみ。 ウォレットは正常に動くため利用者に異常が見えない）と、 攻撃者の Cloudflare Workers への送信。 Rabby クローンは平文を GET のクエリに載せるため、 秘密は Workers だけでなく経路上のリクエストログにも露出する。 layer 5 は帰結——ウォレット資産の完全な制御。 パスワード変更・拡張機能の削除では戻らない。 layer 6 は対処——清浄な環境での新規ウォレット作成と資産移転、 導入の許可制、ハードウェアウォレット、 公表された指標でのログ照合。 なお Rabby・DeBank の正規ホストは本キャンペーンの IoC ではない （Socket が明示）ため、点線で「遮断してはならない」と併記する。

影響（暗号化・破壊・改ざん）公表されていない
**公表資料は、実際の資産流出の観測について述べていない。** **本記録の評価** —— **資産の移動はブロックチェーン上に残るため、 利用者側では残高と取引履歴の監視で気づける。** **ただし気づいた時点で移動は完了している**（本記録の整理）—— **検知が間に合う性質の被害ではない。**
影響を限定できた入力してしまった場合は、清浄な環境で新しいウォレットを作り 資産を移す（パスワード変更では不十分）　**Socket が示した助言である**（出典1）。 **本記録の整理** —— **効果を「影響範囲を限定できた」止まりにしたのは、 移動が攻撃者より先に完了すれば損失を抑えられるが、 既に移動されていれば回復できないためである。**
影響を限定できた資産を複数のウォレットに分け、 日常的に使うものに大きな残高を置かない　**本記録の評価による。** **1つの復元フレーズが漏れたときに失う範囲を区切る。** **副作用** —— **管理すべき復元フレーズの数が増え、 保管の失敗という別の経路が増える**（本記録の一般的理解）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「秘密そのもの」を扱う資産では、通常のインシデント対応が効かないことを前提に置く
    **Socket は「拡張機能のパスワードを変えるだけでは、 盗まれた復元フレーズや秘密鍵は無効化されない」と明示している** （出典1。原文英語の要旨）。 **本記録の整理** —— **復元フレーズは「そのウォレットそのもの」であり、 無効化という操作が存在しない。** **パスワードの変更・拡張機能の削除・端末の初期化では 被害を止められない。** **止める方法は「そのアドレスに資産を置かないこと」だけである。** **本記録の評価** —— **同じ性質を持つ資産は暗号資産に限らない**（本記録の一般的理解）—— **署名鍵・API の長期トークン・証明書の秘密鍵も、 「変更の手順が用意されていなければ無効化できない」。**
    取るべき行動 **①自組織が保有する「漏れたら無効化できない秘密」を一覧にする （署名鍵・長期トークン・証明書の秘密鍵・暗号資産の復元フレーズ等）。** **②それぞれについて「漏えいが判明したときに何をするか」を あらかじめ書き出す** —— **無効化の手順が存在しないものは、それを明示する。** **③存在しないものについては、 「失効させられる形」への移行を計画に入れる （短命のトークン・鍵の委任・多重署名など）。**
  • 拡張機能を「ソフトウェア導入」として管理対象に入れる
    **本件は利用者が自分で拡張機能を導入することで成立する**（出典1）。 **16本は Firefox の拡張機能として配布され、 全16本がデータ収集権限を「none」と宣言していた**（出典1）—— **宣言は実装と矛盾していた。** **本記録の評価** —— **拡張機能は「ブラウザの設定」として扱われ、 ソフトウェアの導入管理の対象から外れていることがある** （本記録の一般的理解）—— **しかし Rabby クローンは1,114個のファイルを含む アプリケーションであり、 全フレームで走るコンテンツスクリプトと 任意ホストへのアクセス権限を持っていた**（出典1）。
    取るべき行動 **①業務端末のブラウザに導入されている拡張機能を一覧化する （把握できていない場合、把握する仕組みを作ることが先）。** **②導入を許可制にするか、少なくとも 新規導入時に記録が残る形にする。** **③本件の16本の拡張機能ID（detail.indicators）で 現在の導入状況を照合する** —— **Mozilla の非公開化が既導入分を消すかは公表されていない** （unknowns 参照）。
  • 「非公開になった」を対処の完了と読まない
    **Socket の記述は 「10月5日時点で Mozilla は悪性拡張機能を非公開にした」である** （出典1）。 **本記録が確認した資料に、 既に導入済みの拡張機能が無効化・削除されるのか、 利用者への通知が行われたかの記載は無い**（unknowns 参照）。 **本記録の評価** —— **非公開化は新規の導入を止める措置であり、 既に端末に入っているものへの措置とは別である。** **「ストアから消えた」というニュースを 「自組織の端末からも消えた」と読み替えてしまう誤りが起きやすい** （本記録の読み）。
    取るべき行動 **①本件のような報道に接したとき、 「配布の停止」と「既導入分の除去」を別の項目として扱う。** **②既導入分については、必ず自組織の端末側で確認する。** **③確認結果（該当なし／該当あり）を記録に残す** —— **「ストアから消えたので確認しなかった」を残さない。**
  • 模倣対象の利用者規模を、自組織の被害規模と混同しない
    **Socket が示した数値は模倣対象のものである**（出典1）—— **Rabby は Chrome ウェブストアで90万人・Google Play で50万回、 OKX は Chrome ウェブストアで100万人超。** **悪性拡張機能の導入数・被害者数は公表されていない**（unknowns 参照）。 **本記録の評価** —— **報道では模倣対象の規模が見出しの数字として使われやすい。** **これを被害規模として報告すると、 対応の優先順位の判断を誤る**（本記録の読み）。
    取るべき行動 **①報告書に数値を載せるとき、 「何の数か」（模倣対象の利用者数か、悪性拡張機能の導入数か、 被害者数か）を必ず添える。** **②導入数・被害者数が不明であることを明示する** —— **「規模不明」は「規模が小さい」ではない。** **③自組織の規模は、端末側の照合結果で出す。**
セキュリティ技術者への示唆
  • 16本の拡張機能IDで、端末の導入状況を遡って照合する
    **Socket は16本の拡張機能ID・版・XPI の SHA-256 を公表している** （出典1。detail.indicators に転記した）。 **拡張機能IDは、名前や説明文と違って パッケージの同一性に結びついている**（本記録の整理）—— **運用者はパッケージ名・版・ID・説明文を入れ替えているが、 公表された16本については ID が確定している。**
    取るべき行動 **①端末管理の仕組みから、 導入されている Firefox 拡張機能のIDを収集する。** **②detail.indicators の16本と照合する。** **③一致があった場合、その利用者が 暗号資産ウォレットの復元フレーズ・秘密鍵を入力したかを確認する** —— **入力していれば、そのウォレットは侵害済みとして扱う（出典1）。** **④Mozilla の非公開化が既導入分を消すかは公表されていないため、 自分で除去する。**
  • ネットワークのログは「目印の文字列」で探す。ホストの遮断は長持ちしない
    **運用者は名前・版・拡張機能ID・説明文・見せ方を入れ替えながら、 同じ画面・同じ窃取処理・同じ目印・同じ通信基盤を使い回している** （出典1）。 **本記録の評価** —— **したがって、入れ替わる部分（ホスト名）での遮断は 一時的な効果しか持たない。** **使い回されている部分がより長く効く指標になる** —— **目印 `EQOx7EIPZSNi`、 綴り違い `Raabby WaIIet`、 メッセージ種別 `SEED_PHRASE_IMPORT` / `WALLET_SYNC`。** **特に Rabby クローンは GET のクエリに `s=EQOx7EIPZSNi` を必ず載せる**（出典1）—— **URL を記録している環境ではこれで照合できる。**
    取るべき行動 **①プロキシ・URL のログを `EQOx7EIPZSNi` で遡って検索する。** **②DNS・プロキシのログを4つの送信先ホストで検索する （detail.indicators 参照）。** **③`workers.dev` 配下への通信を一覧化し、 業務上の必要性を確認する** —— **ただし一括遮断は正規サービスを落とすため、 宛先ごとに判断する。** **④URL のログを保持していない場合、 本件の影響判定ができないことを記録する。**
  • 公表された指標を機械的に取り込まない。正規ホストが混ざっている
    **Socket は明示している**（出典1。原文英語の要旨）—— **「Rabby と DeBank のホストは本キャンペーンの IoC ではなく、 これらのパッケージに現れたことだけを理由に 遮断してはならない。」** **該当するのは `api.rabby.io`・`download.rabby.io`・ `static-assets.rabby.io`・`static.debank.com`・ `static-assets.debank.com`・`matomo.debank.com`** —— **クローンが上流の Rabby / DeBank の設定を そのまま残しているために現れる**（出典1）。 **本記録の評価** —— **「記事に出てきたホストを全部ブロックリストに入れる」という 運用をしていると、正規サービスを落とす。**
    取るべき行動 **①指標を取り込む前に、 記事が「IoC ではない」と明示しているものを除外する。** **②クローン型のマルウェアでは、 上流の正規サービスのホストが必ず混ざることを前提にする。** **③ブロックリストへの追加は、 出典のどの記述に基づくかを記録する形にする。**
  • 「本物が正常に動く」型の窃取を、利用者への説明に織り込む
    **Rabby クローンでは、窃取関数が `importPrivateKey`・`createKeyringWithMnemonics`・ ニーモニック取り込み経路の「直後」に挿入されており、 下層のウォレットの流れはそのまま残る**（出典1）。 **本記録の評価** —— **利用者向けの注意喚起は 「偽サイトに気をつける」「URL を確認する」という形が多い。** **本件にはそれが効かない** —— **本物の Rabby が動いており、残高も取引も正しく表示される。** **気づく手がかりがあるのは 文書タイトルの綴り違い（`Raabby WaIIet`）だけである**（出典1）。
    取るべき行動 **①利用者向けの説明を「挙動が正常でも安全とは限らない」 という形に変える。** **②暗号資産ウォレットについては、 「入手経路を公式サイトからのリンクに限る」を具体的な手順にする** —— **拡張機能の中にある公式ページへのリンクは 正しさの根拠にならない（クローンがそれを残している）。** **③可能ならハードウェアウォレットを前提にし、 復元フレーズをブラウザに入力する機会を無くす。**
  • 宣言された権限と実際の送信コードの不一致を、調査の切り口として覚える
    **全16本のマニフェストが Firefox のデータ収集権限を 「none」と宣言しながら、 復元材料を扱って送信していた**（出典1）。 **さらに1本のコメントは「ハッシュと単語数だけが端末から出る」と 主張していたが、実際は平文を引数 `w` に入れていた**（出典1）—— **Socket はこれを隠蔽の直接の証拠と評価している。** **本記録の評価** —— **この種の矛盾は、調べる側にとって確度の高い手がかりである。** **「宣言」は攻撃者が審査を通るために書くものなので、 実装と食い違う。**
    取るべき行動 **①拡張機能やパッケージを調べるとき、 まず宣言（マニフェスト・権限・プライバシー表示）と 実際のネットワーク送信コードを突き合わせる。** **②コメントと実装の食い違いを、 「バグ」ではなく「意図」として扱う。** **③要求されている権限が用途に対して広すぎる場合、 その権限が今は使われていなくても 「後から機能を追加できる状態」として記録する。**
