ロシアのクラウド基盤が、サイバー攻撃ではなく無人機で止まりました。

2026年10月7日深夜から8日未明にかけて、リャザン州サソヴォにあるYandex のデータセンターが無人機の攻撃を受け、火災が発生しました。Yandex は負傷者はいないとしたうえで、データセンターの稼働が完全に停止したことと、一部のサービスが利用できなくなる可能性を認めました。被害の規模と復旧の見通しは、本記録の作成時点で公表されていません。

技術的には、これは可用性ゾーン1つの喪失として現れました。 Yandex Cloud の告知用チャネルは 01:44（モスクワ時間）に可用性ゾーン ru-central1-b の電源異常を伝え、01:55 には他ゾーンでも新規の VM・Kubernetes クラスタ・データベースの作成に問題が出る可能性があると補足しています。05:26 の時点でも同ゾーンは利用できず、08:26 に「他の可用性ゾーンへの負荷切り替えに必要な作業をすべて完了した」と告知しました（原文ロシア語）。「切り替えが終わった」とは書かれていますが、「ゾーンが戻った」とは書かれていません——本記録の作成時点で、同ゾーンの復旧時期は示されていません。

波及は Yandex の外にも出ています。 Kommersant によれば、不動産ポータルの Cian が11時ごろに障害を告知し、その理由を「インフラ上のパートナーの施設での事案に関連して」と説明しました（原文ロシア語）。デベロッパー数社のサイトも開かなかったと報じられています。自社が Yandex を使っていると言わずに「インフラ上のパートナー」と書く形は、利用者側から依存先を辿れなくする点で、日本の読者にも覚えのある構図です。

本記録がこの事案を日本の読者に向けて置く理由は、帰属や地政学ではありません。 「クラウドの可用性ゾーンは物理的に壊れうる」という、設計上は当然でありながら実例が乏しかった前提が、公開の記録として1件増えたからです。可用性ゾーンの分離は電源・空調・ネットワークの独立性で語られますが、それは「片方が物理的に無くなる」事態まで含めた話として自組織の構成を点検させる材料になります（本記録の判断）。

なお、誰が攻撃したか・何を狙ったかについて、本記録は断定しません。 CNews は「ウクライナの無人機」と記述し、ロシア国防省は7日20時から8日8時（モスクワ時間）までに「ウクライナの飛行機型無人機399機を迎撃・破壊した」と発表してリャザン州を撃墜地域の1つに挙げていますが、データセンターが意図的な標的だったのかは不明であり（CNews も「判然としていない」と明記）、ウクライナ側が実行を主張した発表は本記録では見つけられませんでした。

なぜ「センサーが動かない」のではなく「有効化が止まる」のか

センサー本体は体に付いています。止まったのはその周りにあるものです—— 新しいセンサーを使い始めるための有効化処理、数値を別の端末へ渡す経路、分析と遠隔監視。The Insider が整理した臨床上の意味は2つです（出典15）。

  • データが無いと、CGM の数値に依存する自動インスリン投与（closed-loop）の仕組みが動かない

CISO・経営層への示唆
  • **可用性ゾーンの喪失を「数時間で復旧する障害」として 計画していないか確かめる**
    **本件では、建物そのものが火災で失われ、 復旧の時期は公表されていない。** **給電の回復では戻らない種類の停止である**（本記録の評価）。 **事業継続計画が「ゾーン障害＝一時的」という暗黙の前提を 持っている場合、復旧見込み未定の停止で手順が尽きる。** **なお同じ事業者は2025年3月にも変電所の事故で 可用性ゾーンを失っており、原因は違っても現れ方は同じだった**
    取るべき行動 **主要システムについて「1つの可用性ゾーンが72時間戻らない」 という前提で机上演習を1回行う。** **確かめるのは復旧手順ではなく、 ①その間に業務が続くか、②続かない業務をいつ止めると決めるか、 ③止める判断を誰が下すか、の3点である。** **演習の結果に「復旧を待つ」という選択肢しか出てこない場合は、 それを所見として記録し、次の投資判断に乗せる**
  • **利用している外部サービスの「裏側の基盤」を一覧にしておく**
    **本件では、止まった側（Cian）は理由を 「インフラ上のパートナーの施設での事案に関連して」と説明し、 依存先の名前を出していない**（原文ロシア語）。 **利用者はこの告知から、自分が 特定のデータセンターに依存していたことを知れない。** **同じ書き方は日本でも広く使われている**（「外部サービスの障害」）。 **クラウド事業者の告知と、その上で動くサービスの告知は 互いを参照せずに別々に出る**——**突き合わせたのは報道だけだった** （本記録の整理）
    取るべき行動 **自組織が業務で使っている外部サービス（SaaS・決済・地図・認証・ メール配信）について、①裏側のクラウド事業者、②リージョン、 ③障害告知の参照先 URL の3項目を一覧にする。** **分からないものは「不明」と書いて残す** ——**不明の件数そのものが経営に報告すべき所見である。** **一覧ができたら、同じリージョンに集まっているサービスを数える**
  • **「復旧見込み未定」が続いた場合の判断を、事案の前に決めておく**
    **本件で Yandex は復旧の時期を示していない。** **停止の最中に「別リージョンへ移すか、縮退を続けるか、 業務を止めるか」を決めるのは、最も判断しにくい状況での 最も重い判断になる**（本記録の評価）。 **移行には時間と費用がかかり、 移行を始めた直後に復旧することもある** ——**決め方を先に用意していないと、決められないまま時間が過ぎる**
    取るべき行動 **「障害発生から N 時間で復旧見込みが示されない場合に 代替手段へ移る」という時間の基準を1つ決め、 発動の権限者を名前で定める。** **N は業務ごとに違ってよいが、決めていない業務を残さない。** **あわせて、移行の費用と移行後に戻すための費用を概算し、 発動の判断に数字を添えられるようにしておく**
  • **武力行使・物理的破壊を、可用性のリスク台帳に行として持つ**
    **本件は、サイバー攻撃ではなく物理的攻撃で クラウド基盤が止まった事例である。** **ネットワーク防御・認証・パッチ管理はいずれも関係しない** （本記録の整理）。 **リスク台帳がサイバー脅威だけで構成されている組織では、 この種の事象を扱う行が存在しない** ——**結果として、対策（分散・複製・移行計画）の 投資判断がどの行にも紐づかない。** **なお、クラウドの SLA と保険には一般に 戦争・武力行使の免責条項が置かれる** （本件での Yandex の SLA の扱いは公表されておらず、本記録は未確認） ——**免責の有無は復旧の速さを変えない**
    取るべき行動 **リスク台帳に「委託先・基盤の物理的喪失（災害・事故・武力行使）」の 行を立て、対象のデータセンター・リージョンを具体名で書く。** **そのうえで、契約しているクラウド事業者の SLA と 加入している保険について、戦争・武力行使の免責条項の有無を 法務に確認させ、回答を文書で残す。** **確認の目的は補償の期待値ではなく、 「補償が出ないという前提で復旧計画を書く必要があるか」を 判定することである**
セキュリティ技術者への示唆
  • **1ゾーン喪失中に「新しく作る」操作ができるかを実測する**
    **本件では、既存の稼働は他ゾーンで続いた一方、 新規の仮想マシン・Kubernetes クラスタ・データベースの作成は 他ゾーンでも問題が生じうるとされた**（01:55 の告知）。 **05:26・08:26 の告知も、リソース作成の制限が続くと述べている。** **災害対応の手順はほぼ必ず「新しく作る」操作を含む** ——**代替環境の立ち上げ・インスタンスの増設・ スナップショットからの復元・ロードバランサの再構成。** **既存が動いていても、増やせない時間帯には手順書が動かない** （本記録の判断）
    取るべき行動 **自組織の災害対応手順から「新しく作る」操作を抜き出して一覧にする。** **そのうえで、各操作が制御平面（コントロールプレーン）の どの API に依存しているかを書き添え、 事業者の障害告知で「リソース作成の制限」が出た場合に 動かなくなる手順を特定する。** **代わりに使える手段（事前に起動済みの待機環境・ 別リージョンに作っておいた実行環境）を1つ用意する**
  • **冗長の記述を「系統の数」ではなく「同時に落ちる条件」で読む**
    **2025年3月の先行事例で、Yandex は 「110kV の独立2系統」で給電していると説明したが、 基幹変電所の事故で2系統の両方が停電した** （Yandex の2025年4月7日の声明。原文ロシア語）。 **2026年の本件では、建物そのものが失われた。** **系統が独立していても、上流を共有していれば同時に落ち、 同じ建物にあれば建物ごと失われる**（本記録の評価）
    取るべき行動 **自組織の基盤（オンプレミス・コロケーション・クラウド）について、 「何が壊れたときに冗長の両系統が同時に落ちるか」を 1枚に書き出す。** **確かめる単位は、電源の上流（変電所・受電系統）、 空調、ネットワークの経路、そして建物である。** **クラウドの場合は、可用性ゾーンが別の建物にあるかを 事業者の公開資料で確認し、確認できない場合は 「不明」として記録する**
  • **データの複製先を「別ゾーン」ではなく「別の建物」で確認する**
    **本件では建物が火災で失われ、 損壊した機器とデータ喪失の有無は公表されていない** （本記録の未確定事項）。 **「負荷を他ゾーンへ切り替えた」はトラフィックの話であり、 データの可用性の話ではない**（本記録の注記）。 **単一ゾーンにのみデータを置いていた利用者がどうなったかは、 Yandex も利用者側も説明していない**
    取るべき行動 **重要データについて、①複製先のリージョン／ゾーン、 ②複製の遅延（RPO の実測値）、③復元の所要時間（RTO の実測値）の 3項目を実測して記録する。** **設定値ではなく実測値を取る** ——**一度、実際に別リージョンへ復元して時間を計る。** **単一ゾーンにしか複製が無いデータを洗い出し、 業務上の重要度と照らして移すか移さないかを明示的に決める**
  • **基盤事業者の障害告知を、原因の記述ではなく影響の記述として扱う**
    **本件の告知は 01:44 に「電源異常」として出て、 原因（無人機攻撃による火災）が公表されたのは 約8時間40分後だった。** **08:00 ごろの広報の説明も「インフラの一部に影響を及ぼした事案」 であり、原因には触れていない**（本記録の整理）。 **初報の「電源異常」から復旧の見通しを推定すると誤る** ——**実際には復旧時期が示されない無期限の停止だった**
    取るべき行動 **障害対応の手順に「原因が不明なまま判断する」段を明示的に置く。** **判断の材料は原因ではなく、①影響範囲の告知の推移、 ②自組織の監視で見えている実害、③経過時間の3つに限る。** **あわせて、基盤事業者の告知チャネル （ステータスページだけでなく、本件のように Telegram 等の別経路で出る場合を含む）を 監視対象に登録し、取得できているかを定期的に確かめる**
