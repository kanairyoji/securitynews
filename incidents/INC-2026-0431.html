INC-2026-0431Cisco NX-OSでroot権限RCE 14件修正

Cisco は2026年10月7日、NX-OS Software の定期一括公表として7件のアドバイザリ・ CVE ベースで14件の脆弱性を公表した。うち4件のアドバイザリが「クリティカル」 （CVSSv3.1 基本値 9.8）で、Nexus 3000／9000 シリーズの運用保守機能 NGOAM （CVE-2026-76485・76486・76501）は IP トラフィックの入力検証不備により、 認証なしの遠隔攻撃者が root 権限で任意コードを実行できる。 修正を回避する手段は無く、NGOAM の無効化（no feature ngoam）が 唯一の攻撃面の除去にあたる。Cisco PSIRT は悪用を把握していない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月7日（Cisco のアドバイザリ公表。協定世界時 16:00） 最終更新: 2026年10月9日

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は実際の被害事例ではなく、ベンダーが自社の試験で発見して 公表した脆弱性の記録である**（本記録の位置づけ）。 **Cisco PSIRT は悪用を把握していないとしている**（出典2）。 **以下の chain は、NGOAM の3件（CVE-2026-76485・76486・76501）について、 アドバイザリが示した成立条件と影響から段階を立てたものである** （出典2）—— **実際に観測された攻撃の記録ではない。** **攻撃に必要なものは、アドバイザリの記述に基づけば2つだけである** —— **①対象装置の IP インタフェースへ到達できること、 ②装置で NGOAM 機能が有効であること**（出典2）。 **認証・利用者の関与・事前の権限はいずれも不要である** （CVSS ベクタの PR:N／UI:N。出典2）。

  1. 1. 偵察
    **攻撃者は、NGOAM が有効な Nexus 3000／9000 シリーズの IP インタフェースに到達できる位置を探す**（出典2の成立条件から 本記録が構成した段階）。 **アドバイザリは、管理者が自装置の該当を確認する手段として `show feature | include ngoam` を示している**（出典2）—— **本記録の整理** —— **これは防御側の確認手段だが、 同時に「有効か無効かという1つのビットが 脆弱性の成立を決める」ことを意味する。** **外部からこの状態を判別する手段について、アドバイザリは述べていない** （本記録が確認）。
  2. 2. 初期侵入
    **攻撃者が、対象装置の IP インタフェース宛に細工したパケットを送る** （出典2）。 **アドバイザリが示す原因は「NGOAM が有効なときの IP トラフィックの入力検証の不備」であり、 弱点の分類として CWE-121（スタックベースのバッファオーバーフロー）が 挙げられている**（出典2。本記録が確認。ただし3件のどれに対応するかは 示されていない）。 **成立条件は CVE ごとに異なる**（出典2）—— **CVE-2026-76485 は NGOAM が有効であることのみ。 CVE-2026-76486 はこれに加えて SRv6 または NV Overlay （NV Overlay の場合は、VXLAN EVPN の VNI が NVE インタフェースに 対応付けられ、ピア VTEP が1つ以上学習されていること）。 CVE-2026-76501 はこれに加えて SRv6。** **Nexus 3000 シリーズは SRv6 に対応しないため、 SRv6 を条件とする2件の対象外である。 Nexus 9000 シリーズのうち SRv6 に対応するのは一部の機種である**（出典2）。
  3. 3. 実行
    **認証されていない遠隔の攻撃者が、root 権限で任意のコードを 実行できる**（出典2）。 **アドバイザリの記述は「An unauthenticated, remote attacker ... could execute arbitrary code with root privileges」である** （原文英語）。 **本記録の整理** —— **root 権限は NX-OS の基盤 OS の最高権限であり、 通常の管理者操作より強い。** **スイッチの基盤上でコードが動く状態は、 そのスイッチを通る通信すべてに対する操作が可能な状態を意味する** （本記録の評価。アドバイザリはこの帰結を述べていない）。
  4. 4. 影響（暗号化・破壊・改ざん）
    **2つの影響が示されている**（出典2）—— **①root 権限での任意コード実行、 ②プロセスのクラッシュによる装置の再起動（サービス拒否）。** **アドバイザリの記述は「The attacker could also cause process crashes, leading to a device reload and denial of service」である** （原文英語の要旨）。 **本記録の整理** —— **②は①の副産物ではなく、 別の帰結として記載されている**（本記録の読み）—— **コード実行に失敗した場合でも、装置が再起動する。** **ネットワークスイッチの再起動は、その配下の通信を止める。**

条件は「NGOAM が有効」1つで足り、認証も利用者の関与も要らない原因・手口出典 [2]

本件で優先度を決めるのは、CVSS の値ではなく成立条件である（本記録の整理）。

NGOAM のアドバイザリは3件の CVE を含み、アドバイザリ単位の CVSSv3.1 基本値は 9.8、ベクタは AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H である（出典2。本記録が逐語で確認）—— ネットワーク経由で、攻撃条件は容易、権限不要、利用者の関与不要。

しかし3件の成立条件は同じではない（出典2）——

CVE 必要な条件
CVE-2026-76485 NGOAM が有効であること（これだけ）
CVE-2026-76486 NGOAM ＋ SRv6 または NV Overlay（NV Overlay の場合は VXLAN EVPN の VNI が NVE インタフェースに対応付けられ、ピア VTEP が1つ以上学習されていること）
CVE-2026-76501 NGOAM ＋ SRv6

実務上の意味は明確である（本記録の評価）—— CVE-2026-76485 は追加の設定を一切必要としない。 NGOAM が有効で、IP インタフェースに到達できれば成立する。 他の2件は構成の条件が付くため、対象は狭くなる —— Nexus 3000 シリーズは SRv6 に対応しないため SRv6 を条件とする2件の対象外であり、Nexus 9000 シリーズのうち SRv6 に対応するのは一部の機種だけである（出典2）。

原因は入力検証の不備である —— 「NGOAM が有効なときの IP トラフィックの入力検証の不備」（出典2。原文英語の要旨）。弱点の分類として CWE-121（スタックベースのバッファオーバーフロー）が挙げられているが、3件のどれに対応するかは示されていない（本記録が確認）。

影響は2つ記載されている（出典2）—— ①認証されていない遠隔の攻撃者が root 権限で任意のコードを実行できる、②プロセスのクラッシュにより装置が再起動し、サービス拒否に至る。

②が別の帰結として記載されている点に注意したい（本記録の読み）—— コード実行が成功しなくても、装置は落ちる。 ネットワークスイッチの再起動は、その配下の通信を止める。

確認の第一歩はアドバイザリが示している —— show feature | include ngoam（出典2）。ただし NGOAM が既定で有効なのか無効なのかは、本記録が取得した範囲に記述が無い（未確定事項を参照）—— 既定値に頼らず実測するほかない。

回避策は存在せず、効くのは「無効化」か「更新」の二択だった対策・注意喚起出典 [2]

アドバイザリは、回避策の有無について明確に書いている（出典2）—— 「これらの脆弱性に対処する回避策は存在しない」（原文英語の要旨）。

取れる手は3つで、性質がそれぞれ違う。

①NGOAM の無効化（no feature ngoam） —— アドバイザリは「NGOAM 機能が必要でない場合、これを無効化することで攻撃ベクタが取り除かれ、3件すべての脆弱性に対する緩和策になる」としている（出典2。原文英語の要旨）。これは脆弱性を直すものではなく、攻撃面を消すものである。 アドバイザリ自身が留保を付けている —— 「この緩和策は実験室環境で検証されたものであり、利用者は自身の環境における影響を評価すべきである」（原文英語の要旨）。副作用 —— NGOAM は VXLAN の運用保守（到達性確認・経路の追跡）に使われる機能であり、無効化すると障害切り分けの手段が1つ減る（本記録の評価）。「使っていないから無効化する」の判断には、運用部門が障害対応で使っていないことの確認が先に要る。

②修正版への更新 —— これが恒久対策である。 ただしアドバイザリの本文に修正版の番号の一覧は無く、Cisco Software Checker またはアドバイザリ内の検索欄に対象のリリース番号を入力して確認する形になっている（出典2。本記録が確認）—— したがって「どの版に上げればよいか」を本記録からは示せない。 各組織が自装置のリリース番号で調べる作業が先に入る。

③Live Protect のシールド（暫定措置） —— Cisco は3件すべてについてシールドを提供している（出典2）。アドバイザリ自身の位置づけは「ソフトウェア更新の計画が立つまでの隙を埋めるための暫定的な緩和策である」（原文英語の要旨）—— 「暫定」と明記されている以上、恒久対策として扱わないこと。 本記録はシールドの実効性を独自に検証していない。

作業の順序（本記録の提言）—— ①対象機種すべてで show feature | include ngoam を実行してNGOAM が有効な装置の一覧を作る、②その一覧について SRv6 とNV Overlay の構成を確認して3件のうちどれに該当するかを分ける、③NGOAM が不要な装置から無効化する、④残りについて Software Checker で修正版を調べ、更新の作業窓を確保する。 ①が空であれば、本アドバイザリの対象外である。

アドバイザリが示していないものを整理する。

①攻撃の検知方法。 アドバイザリは、ログの確認箇所・侵害の痕跡・通信の特徴をいずれも示していない（出典2。本記録が確認）。示されているのは設定の確認手段（show feature | include ngoam）だけで、これは「該当するか」を判定するものであり、「攻撃を受けたか」を判定するものではない。

②攻撃が成功した後の判定手段。 本件は root 権限での任意コード実行に至る（出典2）—— root 権限を取られた装置自身のログに依存した事後確認は信頼できない（本記録の評価）。ログの改変も可能である。

では何が観測できるか（本記録の評価）——

確実に気づけるのは、影響の1つとして記載されたプロセスのクラッシュによる装置の再起動である（出典2）。運用監視には必ず残る。 ただし気づけるのは影響が出てからである。

本記録の提言 —— ①原因不明の装置再起動が発生したとき、その装置で NGOAM が有効かどうかを確認する手順を持っておく。 再起動をハードウェア障害として処理すると、攻撃の兆候を見落とす。 アドバイザリはこの手順を示していない。 ②ネットワーク機器の構成を外部に定期的に取得・保存し、差分を検出できるようにする。 装置上での改変に依存しない観測点になる。③到達可能な IP インタフェースの全体を確認する。 アドバイザリは「IP インタフェース」と述べており、管理インタフェースに限定していない（本記録が確認）—— 管理経路の限定だけでは不十分な可能性がある。

悪用状況について —— Cisco PSIRT はアドバイザリ 版1.0（2026年10月7日）の時点で公表・悪用のいずれも把握していないとしている（出典2）。発見は Cisco 社内のセキュリティ試験によるもので、外部の研究者への謝辞は無い（出典2）。本記録の留保 —— 「把握していない」は「悪用されていない」ではない。 成立条件が「NGOAM が有効」1つで足り、認証も不要であるため、公表後に悪用の試みが始まる可能性を前提に扱うのが妥当である（本記録の評価）。公表後の状況・実証コードの公開・KEV への収載は、本記録が確認していない（齟齬3）。
