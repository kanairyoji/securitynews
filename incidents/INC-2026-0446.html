INC-2026-0446AhsayCBSの認証回避＋RCE連鎖が実地悪用

バックアップ管理コンソール AhsayCBS の2つの脆弱性（CVE-2026-105133 の認証不備と CVE-2026-105134 の未認証リモートコード実行）が連鎖させて実地で悪用され、 JSP ウェブシェルと XMRig 採掘機、Microsoft Edge を装う常駐サービス、 脆弱な正規ドライバ WinRing0 が投入された——Huntress は 10.3.4 も影響を受けると訂正し、 修正版が無いため管理画面の到達制限と侵害の調査を勧告している。 【続報・2026年10月15日】**供給元 Ahsay の告知が出ていた**—— 本記録が前回（10月9日）に見ていた「Ahsay Security Advisory」のページではなく、 一般の Announcements のページに、10月9日・10日・12日・13日の4本が並んでいた。 **要点は「修正が出た」ではなく「出た修正が不完全だった」である**—— 10月10日に v10.3.4.0 のパッチが不完全だったとされ、10月12日には v9.15.2.59 と v10.3.4.0 の両方が完全には直っていなかったとして、 v7〜v9 は 9.15.2.70、v10 は 10.3.4.45 のホットフィックスと再起動が指示された。 10月13日には侵害の判定指標（ドライブ直下の見慣れないフォルダ・CBS の webapps 配下の 無作為な名前の .jsp・無認可の RPS 受信先・無認可の Admin 権限アカウント）と、 OS の再インストールからの完全再構築の手順が示された。 Huntress は10月12日に 10.3.4.45 が初期侵入点を緩和することを独自に検証したと追記している。 **同じ10月14日、CISA が2件を KEV に収載し、米連邦機関の対応期限を10月17日とした**

修正版が無い状態で、実地の悪用が始まっている。これが本件の要点である。

2026年10月4日、バックアップ管理コンソール AhsayCBS（Cloud Backup Server）に2つの脆弱性が特定された。

  • CVE-2026-105133（中程度）— filecom/ahsay/obs/api/ApiStructsAction.java のcheckSysPwd 関数に関する認証の不備
  • CVE-2026-105134（致命的）— Replication Receiver の/rps/api/json/UpdateReceivers.do に対する未認証のリモートコード実行。成功するとNT AUTHORITY\SYSTEM としてコードが実行できる

Huntress は、この2つが連鎖して使われているのを観測している——まず CVE-2026-105133 で認証を回避し、次に CVE-2026-105134 で実行を得る。観測の開始は2026年10月7日 23:20:15 UTC。露出していたシステムで未認証のリモートコード実行とウェブシェルの設置が行われた。

侵害後の挙動は採掘である。攻撃者は AhsayCBS のサービス実行ファイル（cbssvcX64.exe）から子プロセスを生み、Alibaba Cloud のオブジェクトストレージから Taskgmr.ps1・msedge.exe・edge.exe・config.json を一時フォルダへ落とした。edge.exe は XMRig（Monero の採掘機）で、Microsoft Edge を装っている。 msedge.exe は正規ユーティリティ NSSM の改変版で、MicrosoftEdgeUpdateSvc という本物の Edge 更新サービスに似せた名前の Windows サービスを作って SYSTEM 権限で採掘機を常駐させた。Taskgmr.ps1 はAI の助けを借りて書かれたとみられる（註釈されたコードから）スクリプトで、タスクマネージャーが開かれたらサービスを止め、閉じられたら再び動かす。さらに一部の事案では、脆弱な正規カーネルドライバ WinRing0x64.sysがcertutil.exe で持ち込まれ、採掘機にハードウェアへの低レベルの到達を与えていた。

そして最も重要なのは、Huntress が当初の報告を訂正した点である。 2026年10月8日 18時（米国東部時間）の更新で、「追加の調査により、Ahsay 10.3.4 も影響を受けると判断した。以前の報告では 10.3.4 は影響を受けないとしていたが、調査結果を反映して改めた」とし、「修正が入手できるようになるまでは、管理用インターフェースへのアクセスを制限し、侵害の痕跡を調査することを推奨する」と述べている（原文英語）。一方、CVE の記載（VulDB・INCIBE-CERT）は影響を 10.3.2 以前とし、解決策を「10.3.4 へのアップグレード」としている。 この食い違いは運用の判断を直接左右する（後述の齟齬参照）。

本記録がこの事案を取り上げる理由は3つある（本記録の判断）。①壊れたのがバックアップの管理基盤である——復旧の最後の拠り所を握られると、ランサムウェアへの耐性そのものが消える。②MSP が主な利用者である——1つの管理コンソールの背後に多数の顧客環境がある。③採掘で終わっているが、同じ入口は何にでも使える—— Huntress は「攻撃者は長期の常駐のために二次的な裏口を隠せている」として、痕跡が見つかった場合は信頼できるバックアップからの完全な再構築を勧めている。

攻撃の経過

**2つの脆弱性を連鎖させ、未認証で SYSTEM 権限のコード実行を得てから、 採掘のための常駐の仕組みを組み立てている。** まず CVE-2026-105133 で認証を回避し、 次に CVE-2026-105134（`/rps/api/json/UpdateReceivers.do`）で実行を得る。 Huntress によれば、攻撃者は**悪性の replication receiver を設定**し、 **CBS アプリケーションが配信するディレクトリへ JSP のウェブシェルを設置**した。 その後、`cbssvcX64.exe` から生まれた子プロセスが Alibaba Cloud のオブジェクトストレージから4つのファイルを一時フォルダへ落とし、 **XMRig の採掘機（`edge.exe`）を Microsoft Edge に見せかけ、 改変した NSSM（`msedge.exe`）を `MicrosoftEdgeUpdateSvc` という 紛らわしい名前の Windows サービスとして SYSTEM 権限で常駐させた。** `Taskgmr.ps1` は**タスクマネージャーの起動を監視してサービスを止め、 閉じられたら再開する**——利用者の目から採掘を隠すための仕掛けである。 一部の事案では**脆弱な正規カーネルドライバ `WinRing0x64.sys`**が `certutil.exe` で持ち込まれ、採掘機にハードウェアへの低レベルの到達を与えた。 **AhsayCBS はバックアップの管理コンソールであり、 侵害されたのは復旧の最後の拠り所である**（本記録の評価）

ルール 内容 設計の理由（Huntress の説明・原文英語）

③「正規だが配り方が異常」を見ること（ルール4）。WinRing0 は正規のドライバである。異常なのはドライバではなく、コマンド行で取りに行く形である。

  • サーバからの出口の通信を既定で拒否する——配送（平文 HTTP）も採掘（ポート 8029）も外向きの通信を通る

1. 管理基盤は、インターネットから到達できるか。

本件の入口は露出した管理用インターフェースである。Huntress の緩和策は「信頼できる IP か VPN に限れ」—— 修正版が無い状態では、これが唯一の予防である。

自社のバックアップ・監視・運用の管理コンソールについて、インターネットから直接到達できるものを一覧にする。委託先が運用しているものも含める（本件の主な利用者は MSP である）。

2. 公開サービスのプロセスは、普段どんな子プロセスを作るか。

Huntress が最初に気づいたのはここである。ウェブシェルからのコマンドは、サービスの直接の子プロセスとして現れる。

これは実測で作れる——平常時の1〜2週間の記録から「このサービスが作る子プロセスの一覧」を作り、それ以外を検知する。とくに cmd.exe・powershell.exe・curl・certutil がサービスの子として現れる形は、ウェブシェルの典型である。

3. 正規に署名された脆弱なドライバを、読み込ませない設定になっているか。

WinRing0x64.sys は正規のドライバである。署名の検査では止まらない。 Windows の脆弱ドライバ遮断リスト（HVCI／WDAC）を有効にするかどうかの一択であり、本件に限らず繰り返し使われている手である（Huntress も「他の無関係な攻撃でも以前に公表されている」と述べている）。

最後に、この事案の「軽さ」について（本記録の評価）。

実被害は計算資源の横取りである。採掘で終わっている。しかし入口は未認証で SYSTEM 権限のコード実行であり、同じ入口でランサムウェアも情報の持ち出しも成立する。

攻撃者は JSP のウェブシェル、改変した NSSM による常駐、AI の助けを借りたとみられる隠蔽スクリプト、脆弱なドライバの持ち込みまで組み立てている——採掘は目的だが、能力はそれ以上である。

脆弱性の優先度は「観測されている悪用の目的」ではなく「取られる権限」で決めるべきである（本記録の判断）。

「修正版が無い」は終わった。代わりに「当てた修正が不完全だった」が2系列で起きた再発防止

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
認証回避とRCEの連鎖 → JSPウェブシェル → Alibaba Cloud から採掘機と改変NSSM → Edgeを装うSYSTEMサービスで常駐
layer 0 は攻撃者（帰属への言及は無い）。 layer 1 が入口——**インターネットに露出した AhsayCBS の管理用インターフェース**で、 CVE-2026-105133（認証の不備）→ CVE-2026-105134（未認証RCE）の連鎖により **NT AUTHORITY\SYSTEM としてコードが実行された**（観測開始は2026年10月7日 23:20:15 UTC）。 layer 2 は足場——**悪性の replication receiver の設定**と **CBS アプリが配信するディレクトリへの JSP ウェブシェルの設置**。 layer 3 は配送——**Alibaba Cloud のオブジェクトストレージ**から `Taskgmr.ps1`・`msedge.exe`・`edge.exe`・`config.json` を一時フォルダへ取得（curl・certutil）。 layer 4 は常駐と隠蔽——**`MicrosoftEdgeUpdateSvc`（本物の `edgeupdate` に似せた名前）**が 改変 NSSM（`msedge.exe`）を SYSTEM 権限で動かし、 `Taskgmr.ps1` が**タスクマネージャーを監視して採掘を隠し**、 **脆弱な正規ドライバ `WinRing0x64.sys`**がハードウェアへのカーネル水準の到達を与える。 layer 5 が結果——**XMRig による採掘（ポート 8029・xmr.kryptex[.]network）**と、 **バックアップの管理基盤が侵害されたという事実そのもの。** 右端は対処——Huntress の Sigma ルール4本と、 **「修正が出るまで管理画面への到達を制限し、 痕跡が見つかれば信頼できるバックアップから完全に再構築する」という勧告である。** **図の要点は3つ。** ①**正規のものばかりで組み立てられている**—— curl・certutil・NSSM・WinRing0・Alibaba Cloud・Microsoft Edge の名前。 悪性と判定しにくいものを並べて、全体として悪性の挙動を作っている。 ②**隠蔽が「人の目」を相手にしている**——タスクマネージャーを見張る仕掛けは、 自動の検知ではなく利用者の気づきを封じるためのものである。 ③**最後の防壁が侵害されている**—— 「信頼できるバックアップから再構築せよ」という勧告の対象が、 バックアップの管理基盤そのものである。

  • バックアップの管理基盤を「守る対象」の最上位に置き直す

    取るべき行動 バックアップの管理基盤（管理コンソール・保管先・復旧の手順書）について、 **①インターネットから直接到達できるか、 ②管理の認証は業務系と分離されているか、 ③基盤そのものが侵害された場合の復旧手順があるか**を確かめる。 ③が無ければ作る——**「バックアップから戻す」計画は、 バックアップの基盤が健全であることを前提にしている。** あわせて**復旧の演習に「管理基盤が信用できない」場面を1つ入れる**

    取るべき行動 脆弱性の対応の手順に、**「修正が無い／情報が食い違う」場合の分岐**を書いておく—— ①**到達の制限**（公開の停止・IP 制限・VPN 越しに限る）を先に決める、 ②**供給元の告知と、観測している第三者（EDR・MDR の事業者）の記述の どちらを優先するかを決める**、 ③**判断を下した日時と根拠を記録に残す**（後で覆るため）。 **本件では、観測している側（Huntress）の情報が CVE の記載より新しく、かつ運用に厳しい方向だった**
  • MSP・システムインテグレータに運用を委ねている部分の「管理基盤の露出」を確認する
    Huntress は AhsayCBS を**主に MSP とシステムインテグレータが使う**ものと説明している。 **1つの管理コンソールの背後に多数の顧客環境がある構図である**（本記録の読み）。 **被害組織の数・名称は公表されていない**ため、 自社が委託先経由で影響を受けているかを外から知る手立ては無い
    取るべき行動 バックアップ・監視・運用を委託している先に対し、 **①自社のデータを扱う管理基盤の製品名と版、 ②その管理画面がインターネットに露出していないか、 ③脆弱性の情報を受け取ったときの通知の約束（何時間以内に何を伝えるか）**を照会する。 **「対策済みです」という回答だけでは足りない**—— **本件は修正版が無い状態の事案であり、 「適用済み」という答えが成立しない局面がある**（本記録の指摘）
  • 採掘で終わった事案を「軽い」と評価しない
    本件の実被害は**計算資源の横取り**である。 しかし使われた入口は**未認証で SYSTEM 権限のコード実行**であり、 **同じ入口でランサムウェアも情報の持ち出しも成立する**（本記録の評価）。 攻撃者は JSP のウェブシェル、改変した NSSM による常駐、 脆弱なドライバの持ち込みまで組み立てている—— **採掘は目的だが、能力はそれ以上である**
    取るべき行動 自社の脆弱性の優先度付けで、**「観測されている悪用の目的」ではなく 「取られる権限」で重みを決める。** 未認証で SYSTEM・root を取られるものは、 **観測が採掘であっても最優先に置く。** あわせて、**過去に採掘機を見つけて除去しただけで閉じた事案**があれば、 同じホストに裏口が残っていないかを改めて確かめる
セキュリティ技術者への示唆
  • 管理サービスのプロセスから生まれる子プロセスを、既知の正常な一覧で絞って検知する
    Huntress が最初に気づいたのは、 **AhsayCBS のサービス実行ファイル（`cbssvcX64.exe`）から生まれた 不審なコマンド行**である。 「AhsayCBS は Web アプリをサービスのプロセス内で動かすため、 設置された JSP のウェブシェルからのコマンドは サービスの直接の子プロセスとして現れる」（原文英語）
    取るべき行動 自社の公開サービス（アプリサーバ・バックアップ基盤・監視基盤）について、 **「このプロセスが普段作る子プロセスの一覧」を実測で作る** （平常時の1〜2週間の記録から）。 それ以外が生まれたら検知する。 **とくに `cmd.exe`・`powershell.exe`・`curl`・`certutil` が サービスの子として現れる形は、ウェブシェルの典型である**（本記録の評価）
  • 一時フォルダから常駐するサービスを、名前ではなく「置き場所」で検知する
    攻撃者は `MicrosoftEdgeUpdateSvc` という **本物の Edge 更新サービス（`edgeupdate`）に似せた名前**のサービスを作り、 一時フォルダの `msedge.exe`（**改変された NSSM**）を **SYSTEM 権限で**動かした。採掘機は `edge.exe` で、こちらも Edge を装っている。 **名前で判定しようとすると、改名で回避される**（本記録の評価）
    取るべき行動 検知ルールを**①実行ファイルの置き場所が `%TEMP%`・`AppData\Local\Temp`・`ProgramData` の直下であるサービスの作成、 ②SYSTEM 権限で動くサービスの新規作成、 ③サービスの一覧の日次の差分**で書く。 **Huntress の Sigma ルールの発想を借りれば、 「元のファイル名が `msedge_exe`」や「`--daemonized` 付き」といった 中身の属性で照合するのも有効である**—— **名前は変えられるが、改変元の実行ファイルの属性は残る**
  • 脆弱な正規ドライバの読み込みを、署名ではなく遮断リストで止める
    一部の事案では、`certutil.exe` で **`WinRing0x64.sys`**が持ち込まれた。 これは OpenLibSys の WinRing0 ライブラリの一部で、 **正規だが脆弱なカーネルドライバ**である。 **署名は有効であり、署名の検査では止まらない**（本記録の指摘）。 本件では防御の無効化ではなく、 **採掘機にハードウェアへのカーネル水準の到達を与えるために使われた**（Huntress の評価）
    取るべき行動 Windows の**脆弱ドライバ遮断リスト（HVCI／WDAC のブロックリスト）を有効にする。** そのうえで、**`WinRing0` の名前と URL が同じコマンド行に現れること**を検知する （Huntress の Sigma ルール4本目。 「正規のハードウェア監視ツールはインストーラの中に同梱して配るため、 コマンド行で取得する形は異常である」）。 **あわせて `certutil.exe` による外部からのファイル取得を検知対象に入れる**
  • 採掘機の隠蔽の仕掛けを逆手に取る——「利用者が気づける症状」を申告の経路に乗せる
    `Taskgmr.ps1` は**タスクマネージャーが開かれたらサービスを止め、 閉じられたら再開する。** さらに**18:00 にタスクマネージャーを終了させ、 夜間に1時間以上開かれていた場合にも終了させる。** **隠蔽の仕掛けがあること自体が、利用者が気づける水準の負荷だったことを示す** （本記録の評価）。時刻の判定は**ローカル時刻**で行われている
    取るべき行動 **「タスクマネージャーが勝手に閉じる」「動作が重い」といった 利用者の体感を、申告の経路として受け付ける**（窓口と文面を用意する）。 技術側では**PowerShell のスクリプトブロックのログを有効化**し、 **プロセスの列挙とサービスの start/stop を組み合わせる挙動**を検知する。 **サービス名での照合は避ける**（改名で回避されるため）
  • サーバからの出口の通信を既定で拒否する——配送も採掘も出口を通る
    攻撃者は**Alibaba Cloud のオブジェクトストレージ** （`imagefiles-backup.oss-ap-southeast-7.aliyuncs[.]com`）から 平文の HTTP で4つのファイルを取得し、 採掘機は**ポート 8029** で Monero のプールへ接続した。 **どちらもサーバからの外向きの通信である**（本記録の評価）。 **正規のクラウドストレージを配送に使うのは、宛先の評判で遮断されにくくするためである**
    取るべき行動 サーバ（とくに公開サービスを動かすホスト）からの**出口の通信を既定で拒否**し、 業務に必要な宛先・ポートだけを許可する。 **バックアップの管理サーバが外部のオブジェクトストレージへ 自発的に取りに行く必要は通常ない**（本記録の判断）。 既定拒否にできない場合は、**非標準ポートへの外向きの接続**と **サーバからの新規の宛先への HTTP** を検知する
