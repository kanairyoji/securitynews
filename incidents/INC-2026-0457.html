INC-2026-0457AWS AgentCore 全エージェント掌握の連鎖

Zenity Labs が2026年10月8日に公表した「AgentCorruption」——Amazon Bedrock AgentCore の設計上の不備と過剰な既定権限が連鎖し、インターネットに公開された1体のエージェントへの単一のプロンプトから、同一 AWS アカウント・同一リージョン内の AgentCore エージェント全体を掌握できた。エージェントにインスタンスメタデータサービスを読ませて一時認証情報を奪い、既定の実行ロールの権限で他のエージェントの列挙・呼び出し・コンテナイメージの取得・他利用者の非公開会話の閲覧・Secrets Manager の認証情報の取得を行い、長期メモリを改変して将来の会話を攻撃者側へ転送させる永続化まで到達した。AWS は既定を変更して修正したが CVE は割り当てられず、AWS 自身は「想定され文書化された動作を脆弱性として誤って描いている」と反論している

脆弱性意図せぬ露出（設定不備等で外部から到達可能だった）続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年10月8日 最終更新: 2026年10月9日

公開されたチャットボット1体に1つのプロンプトを送るだけで、同じ AWS アカウント・同じリージョンにいる AI エージェント全部を乗っ取れた—— Zenity Labs が2026年10月8日にそう公表しました。

研究者が名づけた名前は AgentCorruption です。対象は Amazon Bedrock AgentCore、AWS の AI エージェント実行基盤です。

手順はこうです。まず外部へ要求を出せる道具を持った公開エージェントに、プロンプトで 169.254.169.254（インスタンスメタデータサービス）を読ませます。返ってくるのは、そのエージェントの実行環境に割り当てられた一時認証情報（アクセスキー・シークレットキー・セッショントークン）です。エージェントはそれを素直に攻撃者のサーバーへ送ります。

ここで止まらなかった理由が本件の核心です。 AgentCore が既定で付ける実行ロールの権限が、そのエージェント自身に限定されておらず、同一アカウント・同一リージョンの AgentCore エージェント全体に及んでいました。研究者は盗んだ認証情報で、全エージェントの列挙、各エージェントの呼び出し、Amazon ECR からのコンテナイメージの取得（＝ソースコードの入手）、他の利用者の非公開会話と長期メモリの閲覧、AWS Secrets Manager に保管された認証情報（外部サービスの API キー・OAuth トークンを含む）の取得まで行えたとしています。公開されたカスタマーサポート用のエージェントから、内部の財務エージェントへ移れたとも説明されています。

さらに一度きりで終わりません。 長期メモリに悪意ある記憶を書き込み、以後の会話を攻撃者の管理する宛先へ転送させることができました。Zenity は「利用者は、信頼できる社内エージェントに見えるものと話し続けることになる」と述べています（原文英語）。

修正と、見解の相違も記録します。 Zenity は 2025年12月25日に AWS へ報告し、AWS は新規デプロイでの IMDSv2 の既定化と既定の実行ロールの権限の縮小（エージェント間の呼び出し・非公開会話の読み取り・Secrets Manager へのアクセスの削除）を行いました。Zenity は 2026年9月29日にこれを確認しています。一方で CVE は割り当てられておらず、AWS のセキュリティ速報にも本件に対応する項目はありません（本記録の作成者が2026年10月10日に確認）。AWS は、この研究が「想定され文書化された動作」を脆弱性として誤って描いていると反論しています。 実際に悪用された事例は報告されていません。

日本の読者にとっての論点は単純です。公開エージェントと内部エージェントを同じアカウント・同じリージョンに置いているなら、既定の実行ロールのままでは「1体の侵害」が「全体の侵害」になる構造を抱えていることになります（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**研究者による実証（PoC）であり、実際の攻撃ではない。** 起点は**外部へ要求を出せる道具を持つ、インターネットに公開された1体のエージェント**への 単一のプロンプトである。 そこから**IMDS 経由の一時認証情報の窃取 → 既定の実行ロールの過剰権限を使った 全エージェントの列挙と呼び出し → コンテナイメージ・非公開会話・Secrets Manager の収集 → 長期メモリの改変による永続化**まで到達した。 **具体的な API 名・必要な IAM 操作の一覧・メモリ改変のペイロードは本記録では確認できていない** （Zenity の技術的な詳細記事を取得できなかった）。 以下は公表文と報道から確実に言えることだけを段階として置く。**推定で段階を埋めない。**

  1. 1. 初期侵入[1] [3]
    **インターネットに公開されたエージェント（カスタマーサポート用のチャットなど）へ プロンプトを送り、プロンプトインジェクションで動作を操った。** 研究者は **AWS のオープンソースフレームワーク Strands の Web 用の道具**を備えた 検証用エージェントで実証し、コマンドライン経由でも実施したとされる。 **エージェントが外部へ要求を出せる道具を持っていることが前提である** ——これはエージェントの標準的な構成であり、例外的な設定ではない
  2. 2. 認証情報アクセス[1] [3]
    **エージェントに `169.254.169.254`（インスタンスメタデータサービス、IMDS）を照会させ、 実行環境に割り当てられた一時認証情報 （アクセスキー・シークレットキー・セッショントークン）を取得し、 外部のサーバーへ送信させた。** **内部 AWS サービス向けの証明書・鍵素材、 他アカウントが所有する内部 S3 への事前署名 URL も得られたと報じられている** （ただしアカウント境界を越えたかについては見解が分かれている）
  3. 3. 内部探索[1] [3]
    **取得した認証情報で、同一アカウント・同一リージョン内の AgentCore エージェントを列挙した。** **列挙しやすさの弱点と内部 API の組み合わせにより、 他のエージェントを発見できた**とされる。 **既定の実行ロールの権限が、元のエージェントに限定されず アカウント・リージョン内の全エージェントに及んでいた**ことが前提である。 **具体的な API 名・必要だった IAM 操作の一覧は本記録では確認できていない**
  4. 4. 横展開[1] [3]
    **発見した各エージェントを呼び出し、動作させた。** **公開されたカスタマーサポート用のエージェントから、内部の財務エージェントへ移れた**とされる。 併せて **Amazon ECR からエージェントのコンテナイメージを取得し、 `/app` ディレクトリのソースコード、埋め込まれたパスワード・API キーを得た**とされる
  5. 5. 収集[1] [3]
    **他の利用者とエージェントの非公開の会話、および長期メモリを読み取った。** **AWS Secrets Manager に保管された認証情報 （AWS の外のサービス向けの API キー・OAuth トークン・接続情報を含む）を取得した。** **読み取られた会話の件数・対象の範囲は公表されていない**
  6. 6. 永続化[1] [2] [3]
    **長期メモリに悪意ある記憶を作成し、以後の会話を攻撃者の管理する宛先へ転送させた。** **これにより攻撃は一度きりでなく永続化した。** 研究者は**「利用者は、信頼できる社内エージェントに見えるものと話し続けることになる」**と 述べている（原文英語）。 **また盗んだ認証情報は研究者の端末でも使えたため、 以後はエージェントを経由し続ける必要がなくなった**とされる。 **改変されたメモリの検出・除去の方法は公表されていない**

連鎖の形を分解する（本記録の整理）。

① エージェントの実行環境から IMDS へ到達できた。エージェントは外部へ HTTP 要求を出せる道具を標準的に持つ。研究者は AWS のオープンソースフレームワーク Strands の Web 用の道具を備えた検証用エージェントで実証したとされる。プロンプトで 169.254.169.254 を読ませれば、実行環境に割り当てられた一時認証情報（アクセスキー・シークレットキー・セッショントークン）が返る。エージェントはそれを外部のサーバーへ送った。

② 既定の実行ロールの権限が、エージェント単体ではなくアカウント・リージョン全体に及んでいた。研究者の言葉はこうである—— 「認証情報を得た次の問いは、それで何ができるかだ」「答えは、たくさんのことができる。なぜなら AgentCore のワークロードに既定で付くロールは過剰権限だからだ」（原文英語）。これにより次が可能だったとされる。

  • 全エージェントの列挙（列挙しやすさの弱点と内部 API の組み合わせ）
  • 各エージェントの呼び出し（公開エージェントから内部の財務エージェントへ移れた）
  • Amazon ECR からコンテナイメージの取得（/app ディレクトリ＝ソースコード、埋め込まれたパスワード・API キー）
  • 他の利用者の非公開会話と長期メモリの閲覧
  • AWS Secrets Manager の認証情報（AWS の外のサービス向けの鍵を含む）
  • 内部 AWS サービス向けの証明書・鍵素材、内部 S3 への事前署名 URL

第一に、対策の重心をプロンプトの検閲から権限の設計へ移す必要がある。本件で入力の手段はプロンプトインジェクションだが、被害の範囲を決めたのは「既定の実行ロールがアカウント・リージョン全体に及んでいた」ことである。プロンプトの入口を厳しくしても、インジェクションの成功率はゼロにならない——エージェントは外部の文書・Web ページ・利用者の入力を読んで動くのが仕事である。したがって「1体が乗っ取られる」ことを前提に、乗っ取られた1体で何ができるかを縮めるのが設計の筋である。これは Web アプリの SQL インジェクション対策において入力検証だけでなく DB ユーザーの権限を絞るのと同じ構図である。

第二に、エージェントの実行環境からメタデータサービスへ到達できる構成は、エージェント特有の危険を帯びる。従来のサーバーでも SSRF による IMDS 到達は既知の問題だが、エージェントは「外部へ要求を出す」ことそのものが機能である。つまりSSRF の素材が標準装備されている。 IMDSv2 はホップ制限とトークンで SSRF を難しくするが、エージェントの場合は「エージェント自身が能動的に要求を組み立てる」ため、トークンの取得手順まで指示できる余地が残る（本記録の評価）。メタデータへの経路を塞ぐ（到達不能にする）ことと、実行ロールの権限を縮めることの両方が要る。

第三に、長期メモリの改変は「侵害の後に残るもの」として扱われていない。本件の永続化は、設定でもファイルでもなくエージェントの記憶に埋め込まれた。改変されたメモリの検出・除去・監査の方法は公表されていない。従来のインシデント対応は「どのホストが侵害されたか」「どの資格情報を失効させるか」を軸にするが、エージェント基盤では「どのメモリが汚染されたか」という軸が加わる。この軸に対応する道具と手順を、各組織が自前で用意する必要がある状態である（本記録の評価）。

第四に、CVE が無いことの実務上の影響は小さくない。本件には CVE が割り当てられておらず、AWS のセキュリティ速報にも項目が無い。CVE が無いということは、脆弱性管理の既存の仕組み——CVE の購読、スキャナの検出、SBOM との照合、パッチ適用の記録——に本件が一切載らないという意味である。 責任共有モデルで「クラウド側が直した」ものは、利用者の脆弱性管理台帳に現れない。したがって「マネージドサービスの既定値の変更」を追跡する別の経路（サービスの更新履歴の購読、研究者・ベンダーの発表の定期確認）が要る。同じ週に AWS が別件には速報と CVE を出しているという対照は、この線引きの難しさをそのまま示している。

第五に、公開エージェントと内部エージェントの同居が爆発半径を決めている。本件で起点になったのはインターネットに公開されたカスタマーサポート用のエージェントで、そこから内部の財務エージェントへ移れたとされる。アカウントとリージョンが同じであれば、既定のロールの下では両者は隣人である。 公開エージェントを別アカウントに分離することは、既定ロールの過剰権限が残っていても範囲を区切る手段になる（本記録の評価）。AWS 自身も「別アカウントのリソースへのアクセスは開発者の明示的な許可が必要」と説明しており、アカウント境界が実質的な壁として機能していることを示している。

第六に、当事者と研究者で「脆弱性か否か」の見解が分かれている事案は、記録の仕方を変える必要がある。 AWS は「想定され文書化された動作」とし、Zenity は「安全でない既定」とする。どちらの立場を取るかで、利用者がやるべきことは変わらない—— 既定のまま使えば過剰権限であり、絞るのは利用者の仕事だという点は両者が一致している。 本記録は、見解の相違を解消せずに併記し、利用者の行動に落ちる部分（既定を使うな・分離しろ・メタデータを塞げ）を学びとして取り出す。

CISO・経営層への示唆
  • AI エージェントのリスク評価を「プロンプトの検閲」から「実行ロールの範囲」へ組み替える
    本件で入力の手段はプロンプトインジェクションだが、 **被害の範囲を決めたのは既定の実行ロールがアカウント・リージョン全体に及んでいたこと**である。 **エージェントは外部の文書・Web ページ・利用者の入力を読んで動くのが機能であり、 インジェクションの成功率はゼロにならない**（本記録の評価）
    取るべき行動 エージェント案件の審査項目に **「このエージェントが乗っ取られたとき、その認証情報で何ができるか」**を加え、 **答えを IAM の実際の権限で示させる。** 「プロンプトのガードレールを入れている」は答えとして受け付けない。 **既存のエージェントについても、実行ロールが既定のままかを棚卸しする**
  • マネージドサービスの既定値の変更を追跡する経路を、CVE とは別に持つ
    **本件には CVE が割り当てられておらず、AWS のセキュリティ速報にも項目が無い** （本記録の作成者が2026年10月10日に確認）。 **CVE が無ければ、購読・スキャナ・SBOM の照合・パッチ適用の記録という 既存の脆弱性管理の仕組みに一切載らない。** 同じ週に AWS は**別件には速報と CVE を出している**（2026-127-AWS）
    取るべき行動 脆弱性管理の手順に**「クラウドサービスの既定値・権限設計の変更」を追跡する項目**を足す—— 利用しているマネージドサービスの更新履歴の購読、 **研究者・セキュリティベンダーの発表の定期確認**、 四半期ごとの既定設定の再点検。 **「CVE が無いから対象外」という扱いにしないことを明文化する**
  • 公開エージェントと内部エージェントの同居を、アカウント設計の問題として扱う
    起点は**インターネットに公開されたカスタマーサポート用のエージェント**で、 そこから**内部の財務エージェント**へ移れたとされる。 **AWS 自身が「別アカウントのリソースへのアクセスは開発者が明示的に許可した場合のみ」と 説明しており、アカウント境界が実質的な壁として機能している**
    取るべき行動 **インターネットに公開するエージェントを、内部向けエージェントとは別の AWS アカウントへ分離する** 方針を決める。分離の運用コスト（メモリ・知識ベース・監視の分断）と、 **既定ロールの過剰権限が残っていても範囲を区切れる効果**を並べて判断する。 **既存の構成について「公開エージェントと内部エージェントが同居しているアカウント」を 一覧にすることから始める**
  • 当事者と研究者で「脆弱性か否か」が割れている事案でも、利用者の行動は変わらないと整理する
    **AWS は「想定され文書化された動作」とし、Zenity は「安全でない既定」とする。** **しかし「既定のまま使えば過剰権限であり、絞るのは利用者の仕事」という点は両者が一致している** （本記録の評価）
    取るべき行動 見解が割れている報告を受けたときの判断手順を決める—— **①双方の主張を併記したまま、②「利用者側で設定を変える必要があるか」の1点に絞って判定し、 ③必要なら対応する。** **「ベンダーが脆弱性と認めていないから対応しない」という判断を禁じる。** **責任共有モデルでは、既定値の選択が利用者の責任範囲に落ちることがある**
セキュリティ技術者への示唆
  • エージェントの実行ロールを、エージェントごとに分けて対象リソースを自分自身に限定する
    **既定の実行ロールの権限が、元のエージェントではなく 同一アカウント・同一リージョンの AgentCore エージェント全体に及んでいた。** 研究者は「AgentCore のワークロードに既定で付くロールは過剰権限だ」と述べている（原文英語）
    取るべき行動 エージェントごとに実行ロールを作り、**資源指定にワイルドカードを使わず自分自身の ARN に限定する。** **AWS が既定ロールの権限を縮小した後も、 自分で作った広いロールは自動では縮まらない**ため、 **既存のロールの権限を列挙して棚卸しする。** 棚卸しは「平常時にこのロールがどの API を呼ぶか」の記録から始める
  • エージェントの実行環境からメタデータサービスへの到達を塞ぎ、外向き通信の宛先を限定する
    **攻撃の起点は、エージェントに `169.254.169.254` を読ませて 一時認証情報を取得し外部へ送らせることだった。** **エージェントは外部へ要求を出すことそのものが機能であり、SSRF の素材を標準装備している** （本記録の評価）
    取るべき行動 **IMDSv2 の強制に加え、ネットワークレベルでメタデータへの到達を遮断する。** 併せて**エージェントの外向き通信を宛先の許可一覧で限定し、全件を記録する。** **「エージェントからメタデータサービスへの照会」と 「許可一覧外への送信」を検知規則にする**—— いずれも本来の業務では起きない通信である
  • コンテナイメージに秘密情報を埋め込まない
    **Amazon ECR からエージェントのコンテナイメージが取得され、 `/app` ディレクトリのソースコードと、埋め込まれたパスワード・API キーが得られた**とされる
    取るべき行動 エージェントのイメージを走査し、**パスワード・API キー・接続文字列が 含まれていないかを確認する**（CI に走査を組み込む）。 秘密情報は**実行時に取得する形**に変え、**イメージはソースコードと同じ扱いで管理する**。 **イメージが取得されうる前提で設計する**
  • 秘密情報は実行ロール側だけでなく資源側でも読める主体を限定する
    **AWS Secrets Manager に保管された認証情報 （AWS の外のサービス向けの API キー・OAuth トークンを含む）が取得された。** AWS は修正で既定ロールから Secrets Manager へのアクセス権限を削除したが、 **業務上必要なエージェントには付け直すことになる**（本記録の評価）
    取るべき行動 秘密情報ごとに**資源ポリシーで読める主体を限定する**（実行ロール側の許可だけに頼らない）。 **外部サービス向けの鍵は短命にし、自動更新を入れる**—— AWS の一時認証情報には期限があるが、外部サービスの API キーは長命なことが多く、 **窃取時の被害の長さは鍵の寿命で決まる**
  • 長期メモリの汚染を、インシデント対応の対象として手順に入れる
    **永続化は設定でもファイルでもなく、エージェントの長期メモリに埋め込まれた。** **改変されたメモリの検出・除去・監査の方法は公表されていない**（本記録が最も問題と見る点）
    取るべき行動 インシデント対応手順に**「どのメモリが汚染されたか」という軸を足す**—— ①メモリへの書き込みの履歴を残す、 ②**既知の正常な状態へ戻す手順と、どこまで戻すかの判断基準を平時に決める** （メモリは業務で蓄積した資産でもあるため単純に消せない）、 ③エージェントの応答に含まれる外部宛先への転送を検知する。 **ホストと資格情報だけを対象にした既存の手順では、この永続化を取り除けない**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ Amazon Bedrock AgentCore（または同種のエージェント基盤）で、実行ロールを既定のまま使っている**既定の実行ロールの権限が、同一アカウント・同一リージョンの エージェント全体に及んでいたことが被害範囲を決めた。** AWS 側の既定は修正されたが、**自分で作った広いロールは自動では縮まらない**
システム構成□ インターネットに公開されたエージェントと、内部業務用のエージェントを同一 AWS アカウント・同一リージョンに置いている本件では**公開されたカスタマーサポート用エージェントから内部の財務エージェントへ移れた**とされる。 **アカウント境界は AWS 自身が実質的な壁として説明している**
システム構成□ エージェントに汎用の HTTP 取得・Web 閲覧の道具を与えており、外向き通信の宛先を限定していない**攻撃の起点は「外向きリクエストを行える一般的なツールを備えた公開エージェント」である。** メタデータサービスの照会と認証情報の持ち出しの両方がこの道具で成立した
運用・監視□ エージェントの実行ロールが呼ぶ API を棚卸ししておらず、範囲外の操作を検知する規則が無い列挙・エージェント間呼び出し・コンテナイメージの取得・秘密情報の取得は **いずれも監査ログに残る種類の操作**であり、 **実行ロールの平常時の範囲が分かっていれば検知規則にできる**（本記録の評価）
データの保持□ エージェントの長期メモリ・会話履歴について、書き込みの履歴や改変の監査の仕組みを持っていない**永続化は長期メモリの改変で成立し、その検出・除去・監査の方法は公表されていない。** ホストと資格情報だけを対象にした既存のインシデント対応手順では取り除けない
体制・契約□ 脆弱性管理の対象を CVE が発行されたものに限っており、マネージドサービスの既定値の変更を追跡していない**本件には CVE が無く、AWS のセキュリティ速報にも項目が無い。** 一方で同じ週に AWS は**別件には速報と CVE を出している**—— **CVE の有無で対応を決める運用では本件が台帳に現れない**
