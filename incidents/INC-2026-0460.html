INC-2026-0460Bing 転送を悪用した偽 Claude 配布

Push Security が2026年10月9日に公表した「Adception」——Google 検索広告の遷移先として Bing のクリック追跡 URL（bing.com/ck/a）を指定することで広告審査を回避し、Bing の JavaScript による転送で侵害済みの南米の小売サイトを経由させ、偽の Claude ダウンロードページ claude-desk-code[.]com へ誘導していた。偽ページは Anthropic の正規のインストールコマンドを表示しながら、コピーボタンが差し替えた別のコマンドをクリップボードへ入れる——端末では正規の URL が印字されるが、実際には Base64 で隠した別の URL から .dat ファイルを取得して zsh へ流し込む。2層のクローキング（侵害サイト側は Bing の参照元と特定のブラウザヘッダを要求、偽ページ側は参照元が Google か Bing かを JavaScript で検査し、直接訪問は404へ）により走査からも隠されていた。最終ペイロードは不明。Push は同じ道具立てを AcSig として追跡しており、8つの誘導用ドメインを挙げている

初報: 2026年10月9日 最終更新: 2026年10月9日

「bing.com」と表示される Google の検索広告がありました。 クリックすると、侵害された南米の小売サイトを経由して、偽の Claude ダウンロードページに着きます。

Push Security が2026年10月9日に公表し、Adception と名づけた手口です。名前の意味は「別の検索エンジンの検索結果を広告として買い、そこから悪意あるページへ転送させる」ことです。

仕組みの中心は、遷移先の見え方です。通常の不正広告は攻撃者が持つドメインを遷移先に指定するため、怪しく見えます。本件は遷移先に Bing のクリック追跡 URL（bing.com/ck/a）を指定しました。広告には bing.com と表示されます。 Push はこれが広告側のセキュリティ検査を回避するための設計だと見ています。

経路は4段です。 ① Google の広告クリック用の転送（google.com/aclk?…）→ ② Bing のクリック追跡（bing.com/ck/a?…&u=a1…）—— Bing は HTTP リダイレクトではなく JavaScript で転送するため、応答は 200 で、次の宛先には bing.com の参照元が付きます→ ③ 侵害された南米の小売サイト（homeopatiaalemana[.]com/quienes-somos/。ホメオパシー用品の販売店の「会社概要」ページ）→ ④ 偽の Claude ダウンロードページ（claude-desk-code[.]com）。

走査から隠すための層が2つあります。 侵害サイト側は、Bing の参照元と特定のブラウザヘッダがある要求にだけ 302 を返します。 偽ページ側は、JavaScript で参照元に「Google」か「Bing」が含まれるかを検査し、含まなければ /404.html へ送ります。 つまり URL を直接開くと 404 になり、自動の解析では中身が見えません。

偽ページの仕掛けが本件の要点です。ページには Anthropic の正規のインストールコマンドcurl -fsSL https://claude.ai/install.sh | bash が表示されています。 しかしコピーボタンを押すと、クリップボードには別のコマンドが入ります。その別のコマンドは、まず「Anthropic の公式サイトから Claude をダウンロードします」という体裁のメッセージを印字し、続いて Base64 で隠した URL を実行時に復号して（openssl base64 -d -A）、curl -s で .dat ファイルを静かに取得し、その中身を macOS の zsh へ直接流し込みます。

つまり利用者は、ページ上でも端末の画面上でも正規の Claude の URL を見ています。 実行されているのは、まったく別のスクリプトです。

最終ペイロードは不明です。 Push は「どんなマルウェアが入るのか、そもそも入るのかも分からない」としています。Push は同じ道具立てを AcSig として内部で追跡しており（悪意あるコマンドの取得に HMAC を載せたヘッダを要求することに由来）、同一の macOS 用コマンド・同一のペイロード URL の形・同一のインストーラ画面を使う8つのドメインを挙げています。

日本の読者にとっての論点は3つです。 ①「表示されているドメインが正規だから安全」という判断が成り立たない—— 広告の遷移先が信頼されたドメインでも、そこから転送される。 ②「画面に出ているコマンドと、クリップボードに入るコマンドは別物でありうる」—— コピー＆ペーストによるインストールという開発者の日常の作法が、そのまま攻撃面になっている。 ③開発者向けの AI 道具の導入が、検索広告から始まっている—— 導入経路を会社として決めていない組織が標的になる（本記録の評価）。

第一に、広告の遷移先の表示を信頼の根拠にできない。利用者への指導として「広告の表示先のドメインを確認する」はよく使われる。本件はその指導を無効にする。 表示されるのは bing.com である——正規で、著名で、疑う理由が無い。 そこから転送される。 同じ構造は、他の「信頼されたドメインが任意の宛先へ転送する仕組み」でも成立する（本記録の評価）。追跡用の短縮 URL・クリック計測のリダイレクタ・メール配信事業者の開封追跡・SSO の戻り先の指定—— いずれも「転送する」ことが機能である。 「ドメインを見る」で守れると教えることをやめ、「どこへ着いたか」を見る指導へ移す必要がある（本記録の評価）。

第二に、コピー＆ペーストによるインストールという作法が、そのまま攻撃面である。 開発者向けの道具は「この1行を端末に貼り付けてください」という形で配布されることが多い。 Anthropic の正規の手順もそうである（curl -fsSL https://claude.ai/install.sh | bash）。この作法には、利用者が中身を読まずに実行するという前提が組み込まれている。 本件はその前提を突いた——表示されるコマンドと、クリップボードに入るコマンドを別にする。 さらに端末上の印字も正規の URL にして、二重に一致させている。 この攻撃は Anthropic に固有ではない。 1行インストールを配布している全ての道具に同じ構造がある（本記録の評価）。

第三に、「クリップボードの中身を見る」が実務上の唯一の確認手段になる。 本件で利用者が気づく機会は、貼り付ける前にクリップボードの中身を見ることだけである。 ページの表示を見ても、端末の印字を見ても分からない。 したがって指導は「コピーしたら、実行する前に貼り付けて中身を読む」になる。 具体的には、端末に貼り付けた段階で Enter を押さず、echo の後に && が続いていないか、base64 や openssl による復号が無いか、| zsh や | bash の前に見慣れない処理が挟まっていないかを見る（本記録の評価）。

第四に、開発者向け AI 道具の導入経路を、組織として決めていないことが前提にある。 本件の起点は「claude mac」という検索である。 利用者が検索して、広告をクリックして、自分でインストールしようとしている。 組織が導入経路（配布元・手順・承認）を定めていれば、この経路は使われない。 AI 道具の導入は個人の判断で始まることが多く、その速さが生産性の源でもある——だから禁止は機能しない。 決めるべきは「どこから取るか」である（本記録の評価）。

第五に、侵害された正規のサイトが中継に使われることを、自組織のサイトの問題として読む。 本件の中継点は南米のホメオパシー用品の販売店である。 運営者は被害者でもある。 しかし「自社のサイトが不正広告の中継に使われる」ことは、自社の評判と訪問者の安全に直接響く（本記録の評価）。しかも本件のクローキングは、特定の参照元とヘッダを持つ要求にだけ悪意ある転送を返す——運営者が自分のサイトを普通に見ても気づけない。 検知には「外部から、攻撃者が想定する条件で自サイトを叩く」確認が要る。

第六に、侵害指標の価値が短い。 Push 自身が「短命な侵害指標の価値は限られる」としている ——攻撃者が基盤を素早く入れ替えるためである。 8つのドメインを遮断しても、翌日には別のドメインが使われうる。 効くのは手口に基づく検知である（本記録の評価）—— 「端末に貼り付けられたコマンドに base64 -d と | zsh が同時に現れる」「echo でメッセージを出した直後に curl が走る」といった形の検知。

  • 端末で実行されたコマンドの記録を取り、復号とパイプの組み合わせを検知する
    **本件の実行は、Base64 で隠された URL を実行時に復号し、 取得した内容を zsh へ流し込む形である。** **侵害指標は短命だが、この形は手口として持続する**（本記録の評価）
    取るべき行動 **開発者の端末でシェルの実行記録を取得し、 `base64 -d`／`openssl base64 -d` と `| zsh`／`| bash`／`| sh` が同一のコマンド行に現れる形を検知規則にする。** **誤検知を絞るため、 「`echo` でメッセージを印字した直後に `curl` が走る」 「`curl` の宛先が承認済みの配布元の一覧に無い」といった条件を足す。** **副作用として、正規の運用でも Base64 の復号とパイプを使う場面はあるため、 まず現状でどれだけ出るかを測ってから規則の厳しさを決める**
  • 検索広告・リンクの検査を、表示される遷移先ではなく最終的な着地点で行う
    **本件では広告の表示される遷移先が `bing.com` である。** **さらに Bing は HTTP リダイレクトではなく JavaScript で転送するため、 応答が 302 ではなく 200 になり、 HTTP の応答コードを追うだけの検査では転送を見落とす**（本記録の整理）
    取るべき行動 **URL の検査を行う仕組み（メール・プロキシ・サンドボックス）について、 ①JavaScript による転送を追えるか、 ②最終的な着地点のドメインで判定しているか、 ③クローキングの条件（参照元・ブラウザヘッダ）を再現しているかを確認する。** **③を満たさない検査には、本件の悪意あるページは返らない。** **副作用として、JavaScript を実行する検査は処理の負荷と時間が増える**
  • 開発者の端末で、インストール作業中の未知のホストへの通信を文脈つきで記録する
    **本件のペイロードの取得先（`lake-90[.]com`）は、 正規の Claude のインストールでは現れないホストである。** **ただし開発者の端末は平常時から多数の外部ホストへ通信するため、 宛先だけでは基準を作りにくい**（本記録の評価）
    取るべき行動 **「インストール作業の最中に、承認済みの配布元の一覧に無いホストへ 通信した」という文脈つきの検知を作る。** **具体的には、シェルから起動された `curl`／`wget` の宛先を記録し、 承認済みの一覧との差分を見る。** **副作用として、承認済みの一覧の整備と更新が前提になる** ——**一覧が古いと誤検知ばかりになる**
  • ペイロードの取得に認証（HMAC）が要る攻撃では、サンプルの入手自体が難しいと前提する
    **Push は、悪意あるコマンドが取得される前に ヘッダに HMAC を載せることが要求される点から、 この道具立てを AcSig と名づけている。** **Push 自身も取得されるスクリプトの挙動を記述しておらず、 最終ペイロードは不明である**
    取るべき行動 **「ペイロードが取得できないため中身が分からない」事案では、 検知の設計をペイロードの特徴に依存させない。** **本件で使える手がかりは、ペイロードより前の段階にある** ——**転送の連鎖、クリップボードの差し替え、 実行されたコマンドの形、取得先のホスト。** **解析レポートを読むときに 「どの段階までが確認され、どこから先が不明なのか」を 先に切り分ける習慣をつける**
