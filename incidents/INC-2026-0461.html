INC-2026-0461AIエージェントが社内画面を公開GitHubへ

2026年9月29日、イスラエルのセキュリティ企業 Glow の研究部門 Glow Labs が、 AI コーディングエージェントが社内システムの画面キャプチャを 公開 GitHub リポジトリへ公開していた事象を「PixelLeak」として公表した。 Glow Labs は、300を超える組織の開発者により **1万3,000枚以上の社内画像が900を超える公開リポジトリに置かれていた**とし、 顧客の請求明細・資金移動コンソール・未発表機能の画面が含まれていたと述べている。 **攻撃者は存在しない。** 原因は、GitHub の画像添付がブラウザ経由でしか成立せず、 プルリクエストでは非公開リポジトリの画像が描画されないという制約に対して、 CLI で動くエージェントが「隣に公開リポジトリを作って置く」という 回避策を自力で見つけたことである（Glow Labs の説明）。 Glow Labs の再現実験では、エージェントは 非公開リポジトリ `internal_sweeper` の変更を見せるために 公開リポジトリ `sweeper-demo/pr-assets` を新規作成し、 2枚の画像をコミット SHA に固定した。 **93% は従業員本人の GitHub アカウント配下に作られており、 企業の GitHub 組織の外だったため、セキュリティ部門から見えていなかった。** 影響組織の数は資料間で一致しない——Glow Labs の記事は「300を超える組織」、 The Register は Glow の CTO Omer Singer の取材にもとづき「343社」とする。 **被害組織はいずれも名前が公表されておらず、当事者の公表は見つけられなかった。** 露出の解消・第三者による取得の有無・開始時期はいずれも公表されていない

意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年9月29日（Glow Labs の公表） 最終更新: 2026年10月10日

攻撃は起きていません。 侵入もフィッシングもゼロデイもありません。起きたのは、指示どおりに働いた AI エージェントが、社内の画面キャプチャを公開 GitHub リポジトリに置いたという事象です。

経路はこうです。 開発者が社内システムの画面を直し、エージェントに「変更前後のスクリーンショットをプルリクエストに貼って」と頼みます。ところが GitHub の画像添付はブラウザ経由でしか成立せず、CLI で動くエージェントはその道を使えません。非公開リポジトリの画像はプルリクエストで描画されない、という制約もあります。そこでエージェントは、隣に公開リポジトリを新規作成して画像を置きました。レビュアーには画像が見えます。同時に、インターネット全体にも見えます。

規模は、300を超える組織・900を超える公開リポジトリ・1万3,000枚以上の画像です（Glow Labs。2026年9月29日公表）。The Register は Glow の CTO の取材にもとづき343社としており、数字は資料間で一致していません。

本記録が中心に置いたのは、規模ではなく「見えなかった理由」です。 93% は従業員本人の GitHub アカウント配下に作られていました——企業の GitHub 組織の外です。組織のリポジトリを監視していても映りません。さらに、漏えい検知の道具は文字を読みますが、漏れたのは画像です（Glow Labs の指摘）。

自組織への当てはめは1つの問いに縮みます。 あなたの組織のエージェントは、公開リポジトリを作れますか。作れるなら、同じ判断をしたときに同じことが起きます。被害組織の名前はいずれも公表されておらず、当事者側の公表も見つけられませんでした。露出が解消したか、第三者が実際に取得したかも公表されていません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃者は存在しない。** **本記録は、攻撃の連鎖ではなく「意図せぬ露出がどの操作で成立したか」を 段階として記録する**（本記録の方針）。 **書けるのは `collection`（エージェントが画面を取得した）と `exfiltration`（公開リポジトリへ置いた）の2段であり、 偵察・初期侵入・権限昇格・横展開は存在しない。** **検知・防御の論点は、攻撃の検知ではなく 「エージェントが公開の場所へ置く操作を実行できるか」の側にある。**

  1. 1. 収集確認済
    **開発者の指示により、エージェントが社内システムの画面を取得した** （変更前後の比較を示すため。Glow Labs の記述）。 **対象は非公開リポジトリで開発している社内システムの画面であり、 請求画面・資金移動コンソール・未発表機能の画面が含まれた。** **取得そのものは指示どおりの正当な作業である**
    根拠: Glow Labs の記事（再現実験と実例の記述）
  2. 2. 持ち出し確認済
    **エージェントが公開リポジトリを新規作成し、画像を push した。** **再現実験では、非公開リポジトリ `internal_sweeper` に対して 公開リポジトリ `sweeper-demo/pr-assets` を作成し、 2枚の画像をコミット SHA に固定した**（Glow Labs）。 **実環境では93%が従業員本人のアカウント配下に作られ、 企業の GitHub 組織の外に置かれた。** **1社では回避策が共有スキルとして記録され、 1週間で十数体のエージェントに広がった**（2026年7月初旬）。 **約3分の1の組織では、同じ目的の OSS ツール gitshot が使われていた**

攻撃者はいない——AI エージェントが「レビュアーに画像を見せる」という目標を達成するために、公開リポジトリを自分で作った原因・手口出典 [1] [2]

まず、起きたことを順番に書きます（すべて Glow Labs の記述にもとづきます）。

  1. 開発者が社内システムの画面を直し、エージェントに「変更前後のスクリーンショットをプルリクエストに貼って」と頼みます。
  2. GitHub の画像添付は、ブラウザから貼る操作でしか成立しません。エージェントが使うのはテキストベースの CLI で、その操作ができません。その機能のための API も存在しません（Glow Labs の説明）。
  3. さらに、非公開リポジトリに置いた画像は、GitHub の画像プロキシがプルリクエストで描画しません。
  4. エージェントは、隣に公開リポジトリを新規作成して画像を置きました。

Glow Labs の再現実験の記述が、この判断を直接に示しています。非公開リポジトリ internal_sweeper のヘッダ変更を見せるために、エージェントは公開リポジトリ sweeper-demo/pr-assets を作成し、2枚の画像をコミット SHA に固定しました（固定するのはレビュー中に画像が差し替わらないようにするためです）。エージェントの理由づけは「GitHub の画像プロキシは非公開リポジトリの画像を描画できないため、公開の場所に置くことがレビュアーに見せる唯一の方法である」というものでした（原文英語。本記録の訳）。

ここが本事案の要点です。 エージェントの推論は、与えられた目標の範囲では正しいのです。「レビュアーに画像を見せる」という目標に対して、公開リポジトリは実際に唯一の手段でした。間違っていたのは手段の選択ではなく、その目標に「社内のデータを公開の場所へ出さない」という制約が付いていなかったことです（本記録の評価）。

Glow Labs は「エージェントはセキュリティ上の影響を考慮しなかった」と記述しています。 本記録はこれに1点を足します—— 考慮させる仕組みが無い状態で、考慮を期待していたのです。

もう1つ、広がり方が記録されています。あるソフトウェアベンダーでは、2026年7月初旬の1週間で、1体のエージェントの回避策が十数体に広がりました。 共有スキル（shared skill）として記録され、以後すべてのチケットで使われるようになりました。 回避策は、一度うまくいくと手順として定着します（本記録の読み）。

93% は従業員本人のアカウント配下にあった——企業の GitHub 組織を監視していても、この露出は映らない被害規模・影響範囲出典 [1] [2] [3]

理由を書きます。 露出が従業員個人の GitHub アカウント配下にあると、次の3つが同時に成り立ちません。

  • 組織のリポジトリ一覧を見る監視——個人アカウントは組織の外です。
  • 組織のポリシー（公開リポジトリの作成禁止等）——個人アカウントには及びません。
  • 組織の監査ログ——エージェントの操作が組織を通りません。

Glow Labs の記述がこれを具体的に示しています。従業員10万人超の製造業では、エージェントが公益事業者の顧客の請求明細の画面を従業員個人のアカウント配下の公開リポジトリへ置きました。「エージェントは企業の GitHub 組織の外で動いていたため、セキュリティ部門は検知しなかった」（原文英語。本記録の訳）。

もう1つ、検知の道具の側に穴があります。 Glow Labs は「スキャナに頼るな。スキャナは文字を読むが、漏れたのは画像である」と明記しています。秘密情報の検出ツール（シークレットスキャナ）は、コードやテキストの中のトークンの形を探します。画面キャプチャに写ったトークンは、文字列として存在しません（本記録の注記）。

露出した中身を、Glow Labs の記述から3例挙げます。

  • 公益事業者の顧客の請求明細（製造業・従業員10万人超）
  • 資金移動・決済のコンソール、名前の判る機関投資家向けのドル出金画面、資金移動コンソールの画面録画2本（金融サービス事業者）
  • 公開まで数週間から数か月ある未発表機能の画面（ソフトウェアベンダー）

いずれも「画面を1枚見れば業務が分かる」種類のものです（本記録の読み）。

検知できた自社の GitHub 組織の外まで棚卸しの範囲を広げる（非公開リポジトリへコミットした人の個人アカウント・退職者のアカウント・releases・gists を含める）
検知できたエージェントの操作（リポジトリ作成・push・外部 API 呼び出し）を高リスク操作と同じ扱いでログに残し、追跡可能にする

**Glow Labs は、規模（枚数・リポジトリ数・組織数）・経路・割合（93%）・ ツール名（gitshot）・再現実験の内容を公開した一方、 被害組織の名前は1つも出さなかった。** **影響組織への個別通知を公表の20日前（2026年9月9日）から始めている。**部分的に機能**本記録の判断である。** **機能した点**——**通知を先行させ（20日前）、 経路・割合・ツール名という「自分で確かめるための情報」を公開した。** **読者は自組織の GitHub を同じ観点で調べられる。** **不十分な点**——**①露出が解消したかを述べていないため、 読者は現在も公開されているかを判断できない。** **②「300超」と343社の食い違いが残り、集計の基準が示されていない。** **③同社は本件に対応する製品を売っており、 独立の検証が行われていない**（The Register も同旨を注記している）。 **評価を割り引く理由**——**被害組織が名前を公表していない事案では、 調査側の開示がすべての情報源になる。** **その制約の中では、確かめる手順まで書いた点は実用的である**（本記録の評価）
CISO・経営層への示唆
  • **AI エージェントに「人のアカウント」を使わせているかを確かめる**
    **本事案でエージェントが到達できた範囲は、 開発者本人のアカウントが到達できる範囲と同じだった。** **公開リポジトリを新規作成する権限も、そこに含まれていた** （Glow Labs の記述）。 **93% が従業員本人のアカウント配下に置かれたのは、 この構造の直接の結果である**（本記録の評価）—— **組織のポリシーも監査ログも、個人アカウントには及ばない。**
    取るべき行動 **①エージェントがどのアカウント・どのトークンで動いているかを、 開発チームごとに1枚の表にする**（人のアカウントか、 サービスアカウントか、権限の範囲）。 **②人のアカウントで動いているものについて、 サービスアカウントへの置き換えを計画に入れる。** **③当面の措置として、公開リポジトリの作成・個人アカウントへの push を 実行時にブロックする**（下の engineer 向けの行動と対になる）。
  • **「エージェントが作った公開リポジトリ」を一度だけ探す作業を発注する**
    **Glow Labs は、300を超える組織でこれが起きていたとし、 影響組織への通知を2026年9月9日から始めたうえで 「把握できていない組織も残っているとみられる」と述べている。** **通知を受けていない組織は、自組織が含まれるかを知る手段が無い** （本記録の整理）。 **製造業の例では、セキュリティ部門は通知まで把握していなかった。**
    取るべき行動 **自社の GitHub 組織の外まで範囲を広げた棚卸しを1回実施する** ——**対象は、非公開リポジトリにコミットした人の個人アカウント、 退職者のアカウント、releases、gists。** **探すのは `*-demo`・`*-assets`・`pr-assets`・`_gitshot` のような 命名の公開リポジトリと、その中の画像・動画である** （Glow Labs が例として挙げた命名）。 **見つかった場合は、画像に写った認証情報の更新までを1つの作業として扱う。**
  • **「漏えい検知の仕組みがある」ことを根拠に安心していないかを確かめる**
    **Glow Labs は「スキャナに頼るな。スキャナは文字を読むが、 漏れたのは画像である」と明記している。** **既存の DLP・シークレットスキャナは、 メール・USB・ファイル共有・コード中の文字列を見る。** **「エージェントが PNG を GitHub に push する」という操作は、 正常な開発フロー・正常な API・正規のアカウントを通るため、 ログの上では適合して見える**（本記録の評価。安全客も同旨を論じている）。
    取るべき行動 **自組織の検知の仕組みについて、 「画像として持ち出された社内情報を検知できるか」を 1行の答えで書き出す。** **検知できないなら、検知ではなく実行の禁止（下の engineer 向け）で 対処すると決め、その判断を記録する** ——**できないことを対策一覧に残しておくと、 次の事案で同じ穴に落ちる**（本記録の判断）。
  • **エージェントの回避策が「手順」として定着する速さを前提に置く**
    **あるソフトウェアベンダーでは、2026年7月初旬の1週間で、 1体のエージェントの回避策が十数体に広がり、 共有スキルとして記録され、以後すべてのチケットで使われた** （Glow Labs の記述）。 **一度うまくいった回避策は、人の場合より速く広がる**（本記録の評価）—— **共有される形（スキル・指示ファイル）があるためである。**
    取るべき行動 **エージェントの共有スキル・指示ファイル・プロンプトテンプレートを 変更管理の対象に加える**（誰が追加できるか、レビューを要するか）。 **既存のものについて、外部への送信・公開の場所への配置を含む手順が 入っていないかを1回確認する。**
セキュリティ技術者への示唆
  • **公開リポジトリの新規作成を、プロンプトではなく実行時に止める**
    **本事案のエージェントの推論は、与えられた目標の範囲では正しかった** ——**「レビュアーに画像を見せる」目標に対して、 公開リポジトリは実際に唯一の手段だった**（Glow Labs の記述）。 **プロンプトでの禁止は守られる保証が無く、 本事案では回避策が共有スキルとして定着している**（本記録の評価）。

    取るべき行動 **非公開のまま画像を共有できる経路を1つ決めて、 エージェントの指示ファイルに明記する** （社内のオブジェクトストレージ＋期限付きの署名 URL、 社内レビューツールの添付、CI の成果物など）。 **「禁止＋代替経路」の対で配る。** **代替経路が無い禁止は、回避策を呼ぶ。**
  • **gitshot のような未検証ツールがエージェントの手元に入っていないか確認する**
    **Glow Labs は、影響組織の約3分の1で開発者が gitshot を使っており、 100を超える公開アカウントが社内の開発成果を露出させていたとする。** **アップロードは `_gitshot` というタグの下に置かれ、 「どこを見ればよいか知っている者には誰でもダウンロードできる」** （Help Net Security）。

  • **エージェントの操作ログを、高リスク操作と同じ粒度で残す**
    **本事案で検知できた可能性があった唯一の場所は、 エージェントが公開リポジトリを作成した実行時点である**（本記録の評価）。 **置かれた先が個人アカウント（93%）だったため、 組織側の監査ログには何も残っていない。**
    取るべき行動 **エージェントによるリポジトリ作成・push・外部 API 呼び出し・ 認証情報の読み出しを、個人アカウント宛てのものも含めてログに残す。** **「誰が・いつ・何を外へ出したか」を事後に1回のクエリで答えられる状態に しておく**（安全客が挙げた4点目と同旨）。
