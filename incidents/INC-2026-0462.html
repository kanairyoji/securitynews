INC-2026-0462ChromiumのIDN表示検査を2文字で迂回

2026年10月3日、タイポスクワット監視サービス Have I Been Squatted の Ian Muscat・Leanne Briffaが、 **キリル文字の ө（U+04E9）と Latin k with hook の ƙ の2文字で、 Chromium 系ブラウザの国際化ドメイン名（IDN）の表示検査を すべて通過できることを示した**。 Chromium は IDN をそのまま表示してよいかを `SafeToDisplayAsUnicode()` の 7段の検査で判定し、さらに `GetSimilarTopDomain()` で 約8,462件の著名ドメインとの類似を見るが、 **前者の「全字がキリル文字の偽装」の検査は ハードコードされた28文字の一覧に含まれる文字だけで構成されたときにしか発動せず、 一覧に無い ө が1字混じるだけで通過する**（研究者はこれを「breaker」と呼ぶ）。 **後者は符号から発音記号を落として比較するが、 ө のバーと ƙ のフックは結合記号として残るため、本物と一致しない。** 研究者は аррӏө.com（apple）・oƙta.com（okta）・niƙe.com（nike）を含む **20件のそっくりドメインを実際に登録し、 Chrome 154 で Unicode 表示のまま有効な証明書付きで表示されることを示した**。 **メールクライアントではさらに検査が緩く、 Gmail（ウェブ）は20件すべてを Unicode で表示し、 Outlook Web は正当な IDN まで Punycode で表示した。** .com のゾーンファイル（2026年10月）の全数調査では、 **733,509件の IDN のうち161,894組が ASCII のドメインと見かけ上一致する**。 **本記録の作成者は、Google への事前通知の有無・ベンダーの見解・ 実際の悪用の観測を、いずれも確認できなかった**

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月3日（Have I Been Squatted の公表） 最終更新: 2026年10月10日

2文字で済みました。

キリル文字の ө（U+04E9。カザフ語・モンゴル語・タタール語で使う）と、ラテン文字の ƙ（k with hook。ハウサ語・カライカライ語で使う）。この2文字を混ぜると、Chromium 系ブラウザの偽装ドメインの検査をすべて通過できます（Have I Been Squatted。2026年10月3日公表）。

検査は3層あります。

  1. SafeToDisplayAsUnicode() ——7段の検査。このうち「全字がキリル文字の偽装」を見る検査は、ハードコードされた28文字の一覧に全字が含まれるときにしか発動しません。 一覧に無い ө が1字混じれば、発動しません（研究者はこれを「breaker」と呼びます）。
  2. GetSimilarTopDomain() ——約8,462件の著名ドメインとの比較。符号（skeleton）を作るときに発音記号は落ちますが（ó→o）、ө のバーと ƙ のフックは結合記号として残ります。残るので、本物と一致しません。
  3. 移動時の警告（Safety Tips） ——近似一致のときに出ます。ただし「1文字違い」か「隣接の入れ替え」までで、2文字以上違うと出ません。 TLD の前が5文字未満のドメインには、そもそも働きません。

аррӏө.com（apple）は2文字違いなので③に掛かりません。 oƙta.com（okta）は4文字なので③の対象外です。研究者は20件のそっくりドメインを実際に登録し、Chrome 154 で Unicode 表示のまま、有効な証明書付きで出ることを示しました。

メールのほうがさらに緩いです。 Gmail（ウェブ）は20件すべてを Unicode で表示し、Outlook Web は正当な IDN まで Punycode で表示しました。 どちらもそっくりドメインの検査をしていません（研究者の表現では「Gmail はすべてを復号し、Outlook Web は何も復号しなかった」）。

規模の見積りがあります。 .com のゾーンファイル（2026年10月）の全数調査で、733,509件の IDN のうち161,894組が ASCII のドメインと見かけ上一致します。 ただしこれは「偽装の登録が16万件ある」という意味ではありません—— 防御目的の登録や多言語対応の登録も含まれます（研究者の注記）。

本記録の作成者は、Google への事前通知の有無・ベンダーの見解・実際の悪用の観測を、いずれも確認できませんでした。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない。** **本記録が記録するのは、研究者が実際に登録した20件のドメインで 成立を示した経路である**（本記録の方針）。 **段は `reconnaissance`（そっくりに見える名前を見つけて登録する）と `initial-access`（利用者が表示を信頼する）の2段に絞る** ——**この先（認証情報の入力・マルウェアの配布）は本研究の範囲外であり、 無理に埋めない。** **防御の論点は、表示の検査ではなく 「表示を信頼しない認証方式になっているか」の側にある**（本記録の評価）。

аррӏө.com（apple.com の模倣）が、なぜ3層すべてを通るのかを順に書きます（すべて Have I Been Squatted の記述にもとづきます）。

第1層: SafeToDisplayAsUnicode()——7段の検査。1段でも落ちれば Punycode 表示。

段 аррӏө での結果 理由
ICU の偽装検査 通過 単一文字体系（キリル文字のみ）で、許可された文字だけ
混在文字（script mixing） 通過 混在していない
アイスランド語・ラテン文字のシュワー・中点 通過 該当しない
全字がキリル文字の偽装（whole-script confusable） 通過 ө が一覧に無い

最後の段が本件の鍵です。この検査は、ハードコードされた28文字の一覧に「すべての文字」が含まれるときにしか発動しません。 ө は一覧にありません。 だから1字混じるだけで発動しません。研究者はこの性質を持つ文字を「breaker」と呼び、ө・ї・ү を挙げています（Chrome 154 時点）。

第2層: GetSimilarTopDomain()——約8,462件の著名ドメインとの比較。

ここでは符号（skeleton）を作ります。発音記号は落ちます（ó→o）。m は rn に写されます。ところが ө のバーと ƙ のフックは、結合記号として符号に残ります。

  • oƙta.com の符号 → [o k ' t a . c o r n]
  • аррӏө.com の符号 → [a p p l o - . c o r n]

どちらも本物（okta.com / apple.com）の符号と一致しません。 ƙ は1文字として格納されているため、発音記号を落とす処理では分解できません（研究者の記述）。

第3層: 移動時の警告（Safety Tips）。

これは近似一致で出ます。ただし条件が2つあります。

  • 完全一致・1文字違い・隣接の入れ替えまで。 аррӏө.com は2文字違いなので掛かりません。
  • TLD の前が5文字以上。 oƙta.com は4文字なので対象外です。

なお、よく訪れるサイトに対しても同じ検査が働きますが、訪問履歴が十分でない利用者ではこの層が機能しません（The Register の記述）。

対照例が示されています。 ínstagarm[.]com は、発音記号が落ちて instagarm になり、instagram.com と2文字の入れ替えで一致するため、第3層の警告が出ます（The Register）。つまり第3層は動いています—— 動かないのは「2文字以上違う」「短い」という条件のときです。

研究者の総括がこの節の結論です—— 「それぞれの層が自分だけで判断を下し、どの層も他の層が何を決めたかを確かめていない」（原文英語。本記録の訳）。

キリル文字による15件（いずれも ө などの breaker を含みます）—— apple・openai・skype・sharepoint・pinterest・spacex・shell・xerox・opera・chess・kaspersky・lexisnexis・nexon・one・paychex。Chrome 154（macOS）では、15件すべてが Unicode のまま表示されました。 記事には、аррӏө.com が有効な証明書付きで表示されている画面が載っています。

ƙ による5件——okta・nike・sky・vk・kickstarter。このうち okta（4文字）・sky（3文字）・vk（2文字）は、TLD の前が5文字未満であるため、第3層の警告の対象外です。

本記録が読者に重要と見るのはこの組み合わせです（本記録の評価）—— 短いブランド名を持つ組織は、層が1つ少ない状態に置かれます。 認証の入口を提供する事業者（Okta）がこの条件に当てはまることは、フィッシングの標的としての価値から見て意味があります。

  • IDN（xn-- 形式）: 733,509件
  • ASCII のドメインと見かけ上一致する IDN: 154,567件
  • 組の数: 161,894組（相手方の ASCII 名は133,953件）

この16万という数字の読み方に注意が要ります。 研究者自身が「偽装の登録が16万件あるという意味ではない」と明記しています——防御目的の登録、同一企業による多言語サイト、無関係の登録が含まれます。意味があるのは「そっくりに見える名前を作る余地がこれだけある」ことのほうです（本記録の整理）。

メールクライアントは検査をしていない——Gmail はすべてを Unicode で、Outlook Web は正当な IDN まで Punycode で表示した波及・関係先出典 [1] [3]

ここは本事案で最も実務に近い部分です（本記録の評価）。

研究者は、差出人（From）ヘッダに A-label（xn-- 形式）を入れた試験メールを送り、既定設定のクライアントでの表示を見ています。

  • Gmail（ウェブ）: 20件すべてを Unicode で表示しました。 test@аррӏө.com も applıcation.com も、攻撃者が望む形で出ます。Punycode は別欄（mailed-by）にのみ現れます。
  • Outlook Web: 20件すべてを A-label（Punycode）で表示しました。 café.com のような正当な IDN まで Punycode になります。

研究者の総括——「Gmail はすべてを復号し、Outlook Web は何も復号しなかった」（原文英語。本記録の訳）。どちらもそっくりドメインの検査をしていません。

本記録が取り出す意味を3つ書きます（本記録の評価）。

  1. ブラウザの話として読むと取りこぼします。フィッシングの入口はメールです。ブラウザに3層あっても、メールの段階では0層です。
  2. Outlook Web の挙動は「安全側」ですが、副作用があります。正当な IDN まで Punycode になるため、利用者は xn-- という文字列に慣れてしまいます。慣れると、異常の合図として働かなくなります（本記録の読み）。
  3. SPF・DKIM・DMARC は、この攻撃を止めません。 研究者が明記しています—— 攻撃者が自分で登録したそっくりドメインでは、SPF・DKIM・DMARC はすべて通ります（原文英語。本記録の訳）。認証は「このドメインから送られたこと」を保証するだけで、「このドメインが本物に見える別のドメインであること」は見ません。

研究者の推奨策のうち、メールに関するものを挙げます。

  • メールゲートウェイのそっくりドメイン／なりすまし対策の機能を使う
  • 差出人ドメインが xn-- のメールに印を付ける
  • 外部送信者の表示（external-sender banner）を残す
  • xn-- の名前を DNS・プロキシのログで合図として扱い、許可一覧の外のものは記録・警告・遮断する

したがって本記録は、読者が取る行動を「ブラウザの修正を待つ」側に置きません。 置くのは次の3つです（本記録の判断）。

  1. アドレスバーの目視を安全の根拠から外す。 利用者教育で「URL を確認する」と教えている組織は、教え方を変える必要があります—— 本件は「正しく読める」という前提そのものを崩しています。
  2. 認証をドメインに縛る。 研究者の一文がこの節で最も実用的です—— 「apple.com に登録されたパスキーは、アドレスバーに何が表示されていようと、xn--80a6aa68c8d.com のログインページには応答しない」（原文英語。本記録の訳）。FIDO2・パスキーは、見た目ではなく実際のドメインで判定します。 人が読み間違える問題を、人に読ませないことで解く手です。
  3. xn-- を合図として扱う。 DNS・プロキシのログで xn-- の名前を記録し、許可一覧の外は警告か遮断に回す。正当な IDN を使う取引先がある組織では許可一覧の整備が要りますが、日本の多くの組織では xn-- の宛先はそもそも少ないはずです（本記録の評価。実測はしていない）。

最後に、本件の位置づけを書きます。 これは「Chromium が甘い」事案ではありません。 研究者自身が「Chromium の IDN 検査はどのブラウザよりも厳しく、それでもなお安全性と使いやすさを一部交換している」と書いています。 多言語のドメインを使えるようにすることと、見た目の偽装を全部止めることは、同時には成立しません（本記録の整理）。成立しないのなら、防御の重心を表示の検査から認証の方式に移すのが筋だと本記録は判断します。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察機会はあったが検知できず
**機会はあるが、ほとんどの組織で見ていない**（本記録の評価）。 **検知できる場所は2つある。** **①新規のドメイン登録の監視**—— **研究者は「保護対象のドメインから2文字以内の 新しい `xn--` 登録を監視せよ」と推奨している。** **②自組織のブランドの防御的登録**—— **研究者は「符号の比較を通過してしまう綴り（ө・ү・ƙ を使うもの）を 自ら登録せよ」としている。** **どちらも「気づく」ための仕組みを先に作っていなければ働かない** ——**本記録が確認した限り、 なりすまされた20ブランドの側からの反応は公表されていない**
—
初期侵入現実的な検知機会なし
**利用者による目視では現実的な検知機会が無い**（本記録の評価）。 **理由**——**表示される文字列が本物と見分けられない形で描画され、 証明書も有効であり、メール認証（SPF・DKIM・DMARC）も通る。** **「アドレスバーを確認する」という助言は、 そこにある名前が正しく読めることを前提にしている** （研究者の指摘）。 **ただし機械的な検知は可能である**—— **DNS・プロキシのログに現れる名前は Punycode（`xn--`）であり、 人の目に見える形とは違う。** **見る場所を人の目からログへ移せば、検知の機会は生まれる** （本記録の判断）
侵入を防げた認証をドメインに縛る方式へ移す（FIDO2・パスキー）。表示ではなく実際のドメインで判定されるため、そっくりドメインのログインページには応答しない
検知できたDNS・プロキシのログで `xn--` を含む宛先を記録し、許可一覧の外は警告または遮断する
検知できたメールゲートウェイのそっくりドメイン／なりすまし対策を有効にし、差出人ドメインが `xn--` のメールに印を付ける
影響を限定できた自組織のブランドについて、符号の比較を通過する綴り（ө・ү・ƙ を使うもの）を防御的に登録する。4文字以下のブランド名では特に優先する
検知できた保護対象のドメインから2文字以内の新しい `xn--` 登録を監視する
影響を限定できた利用者教育から「アドレスバーの目視で本物を確認する」を安全の根拠として外し、ブックマーク・パスワードマネージャの自動入力の不発を異常の合図として教える

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**研究者は、迂回の仕組み（どの検査がどの理由で通るか）、 登録した20件のドメインの完全な一覧、 対応する Punycode、Chrome の版、.com ゾーンファイルの全数調査の内訳を すべて公開した。** **各ドメインには、迂回の仕組みを説明する研究用のページを置いている。** **Google 等への事前通知の有無は記事に書かれていない。**部分的に機能**本記録の判断である。** **機能した点**——**①成立を実物で示し、検証可能にした。** **②.com の全数調査で規模の上限を示し、かつ 「偽装が確認されたものではない」と明記して過大な読みを封じた。** **③防御側の行動（パスキー・`xn--` の監視・防御的登録）まで書いた。** **不十分な点**——**ベンダーへの通知と回答の経過が書かれていないため、 読者は「修正を待てるのか」を判断できない**（本記録の評価）。 **本記録はこの不足のため、 「放置されている」とも「報告済みである」とも書かない。**
CISO・経営層への示唆
  • **利用者教育の「URL を目で確認する」を、安全の根拠から外す**
    **本件は、アドレスバーの表示が本物と見分けられない形で描画されることを 実物で示している**（Chrome 154 で15件が Unicode 表示・有効な証明書付き）。 **研究者の指摘は「『アドレスバーを確認せよ』という助言は、 そこにある名前が正しく読めることを前提にしている」である** （原文英語。本記録の訳）。 **前提が崩れている以上、この教育項目は 「やってもよいが、これで安全とは言えない」ものになる**（本記録の評価）。
    取るべき行動 **フィッシング訓練・教育資料の文面を1回見直し、 「URL を確認する」を単独の対策として掲げている箇所を書き換える。** **代わりに置くのは「ブックマークか社内ポータルから入る」 「パスワードマネージャが自動入力しないサイトは疑う」 「心当たりのないメールのリンクは踏まない」である** ——**いずれも人の読解力に依存しない**（本記録の判断）。
  • **4文字以下の短いブランド名を持つなら、防御の層が1つ少ないと認識する**
    **Chrome の移動時の警告（Safety Tips）は、 TLD の前が5文字未満のドメインには働かない** （研究者・The Register の記述）。 **研究者は oƙta.com（4文字）・sƙy.com（3文字）・vƙ.com（2文字）を 実際に登録している。** **さらに近似一致の条件は「1文字違い・隣接の入れ替え」までであり、 2文字以上違う偽装には働かない。**
    取るべき行動 **自組織のブランド名（ドメインの TLD より前の部分）の文字数を数える。** **5文字未満なら、ブラウザ側の警告は期待できないものとして扱い、 防御的登録と `xn--` の監視に予算を振る。** **5文字以上でも、2文字以上の置き換えには警告が働かないため 安心はできない**（本記録の注記）。
  • **なりすまし対策の予算を「表示の検査」から「認証の方式」へ移す**
    **塞ぎ方が文字単位である**—— **Chrome 148 で ҏ・ӿ を塞ぎ、2026年9月11日に м を追加したが、 ө・ү・ї は残っている**（研究者の記述）。 **さらに м の追加は Chrome 155 の分岐より後であり、 Chrome 155 には入らない。** **「修正済み」と「利用者の手元で有効」の間に版ぶんの差がある** （本記録の整理）。 **一方で、パスキーは表示ではなく実際のドメインで判定する**—— **「apple.com に登録されたパスキーは、アドレスバーに何が表示されていようと、 xn--80a6aa68c8d.com のログインページには応答しない」** （研究者。原文英語。本記録の訳）。
    取るべき行動 **①自社の従業員向け・顧客向けのログインのうち、 フィッシング耐性のある認証（FIDO2・パスキー）に移していないものを一覧にする。** **②そのうち「盗まれたら最も痛い」上位3つを選び、 今期の移行対象として決める。** **③移行できないものについては、 そっくりドメインでは認証が通ってしまうことを前提に、 事後の検知（ログイン元・振る舞い）側で手当てすると決めて記録する。**
  • **自組織の利用者が使うメールクライアントの表示挙動を一度確かめる**
    **研究者が試験したのは Gmail（ウェブ）と Outlook Web の2つだけで、 前者は20件すべてを Unicode で表示し、 後者は正当な IDN まで Punycode で表示した。** **どちらもそっくりドメインの検査をしていない。** **デスクトップ版・モバイル版の挙動は公表されていない** （本記録の未確定事項）——**自組織で確かめるほかない。**
    取るべき行動 **自組織の標準メールクライアント（デスクトップ・モバイルを含む）で、 `xn--` 形式の差出人ドメインがどう表示されるかを1回試す。** **Unicode で表示されるなら、ゲートウェイ側で印を付ける設定を検討する。** **Punycode で表示されるなら、 利用者が `xn--` に慣れて合図として働かなくなるため、 「正当な取引先の IDN」の許可一覧を作る**（本記録の判断）。
セキュリティ技術者への示唆
  • **`xn--` を DNS・プロキシのログの検知条件に入れる**
    **人の目に見える文字列と、ログに残る文字列は違う** ——**аррӏө.com はログでは `xn--80a6aa68c8d.com` として現れる** （本記録の整理）。 **研究者は「`xn--` の名前を DNS とプロキシのログで合図として扱い、 許可一覧の外のものは記録・警告・遮断せよ」と推奨している。** **人が読み間違える問題を、機械が読む場所に移す**（本記録の判断）。
    取るべき行動 **①直近30日の DNS・プロキシのログから `xn--` を含む宛先を抽出し、 件数と内訳を見る。** **②正当なもの（取引先の IDN・国際化サイト）を許可一覧にする。** **③以後、許可一覧の外の `xn--` を警告に回す。** **件数が少なければ遮断まで踏み込める** ——**まず件数を測ってから決める。**
  • **自社ブランドについて、符号の比較を通過する綴りを防御的に登録する**
    **`GetSimilarTopDomain()` の符号化では、 発音記号（ó→o）は落ちるが、ө のバーと ƙ のフックは結合記号として残る** ——**残るので本物と一致せず、2層目の検査を通過する**（研究者の記述）。 **つまり「発音記号を使った綴り」は塞がれているが、 「バー・フックを使った綴り」は空いている。**
    取るべき行動 **自社ブランド名について、ө・ү・ƙ を使った綴りを列挙し、 未登録のものを防御的に登録する** （研究者の推奨策。4文字以下のブランド名では優先度を上げる）。 **登録済みのそっくりドメインが第三者のものであれば、 登録者と用途を確認する。**
  • **新規のドメイン登録の監視条件を「2文字以内の `xn--`」まで広げる**
    **аррӏө.com は apple.com から2文字違いである。** **Chrome の近似一致の警告は「1文字違い・隣接の入れ替え」までしか働かない** ——**ブラウザが見ない範囲が、監視の対象にすべき範囲である** （本記録の整理）。
    取るべき行動 **保護対象ドメインの監視条件に、 「`xn--` 形式で、ASCII へ写すと2文字以内の違いになるもの」を加える** （研究者の推奨策）。 **監視の仕組みを持っていない場合は、 少なくとも四半期に1回、主要ブランドについて `xn--` の新規登録を手で確認する。**
  • **ブラウザの版と検査の内容がずれることを前提に、配布の遅れを測る**
    **キリル文字の м は2026年9月11日に Chromium の一覧へ追加されたが、 Chrome 155 の分岐より後だったため Chrome 155 には入らない** （研究者の記述）。 **「修正済み」と「利用者の手元で有効」は別である**（本記録の整理）。
    取るべき行動 **自組織の端末で稼働している Chrome・Edge の版の分布を1回測る。** **最新の安定版より2版以上古い端末がどれだけあるかを知っておく。** **ブラウザの更新が遅れている組織では、 表示の検査に期待できる度合いがさらに下がる**（本記録の判断）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 従業員向け・顧客向けのログインで、フィッシング耐性のある認証（FIDO2・パスキー）を使っていない
