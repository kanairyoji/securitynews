INC-2026-0466流出した国家級 iOS 連鎖が暗号資産窃取へ転用

国家級の顧客向けに使われていた iOS エクスプロイト連鎖「DarkSword」が2026年3月に流出し、それを改造した犯罪版「P7」が暗号資産の窃取に転用された——iVerify が2026年10月8日に実装を分析。iOS 18.4〜18.7 の端末が中国語の賭博・暗号資産サイトを閲覧するだけで SpringBoard 内にインプラントが動き、キーチェーンを端末上で復号して imToken 等のウォレットのシードフレーズと keystore を持ち出す

iVerify は 2026年10月8日、iOS 向けエクスプロイト連鎖 DarkSword の犯罪版インプラント 「P7」 の分析「Sleep, Beacon, Steal, Repeat - The Story of P7 DarkSword Variant」を公表しました。同社が2026年8月に顧客端末1台の警報を調べたところ、通常の DarkSword の検知とは異なる未知の変種だったことが分かったという経緯です。「P7」の名は、攻撃者が改造部分で使った変数の接頭辞 p7_ に由来します。

DarkSword はもともと国家級の顧客向けに使われていた連鎖です。 Google Threat Intelligence Group（GTIG）が2026年3月に報告し、6件の CVE（当時3件はゼロデイ）を連ねて iOS 18.4〜18.7 の端末をウェブページの閲覧だけで侵害するものでした。その完全なキットが2026年3月22日に流出したとされ、以後、金銭目的の集団がこれを改造して使っています（Habr の分析）。

P7 が何をするか。中国語のオンライン賭博サイト・暗号資産ニュースページに隠された iframe から連鎖が送り込まれ、数秒で SpringBoard 内にインプラントが動きます。インプラントは securityd の AppleKeyStore を復号の神託（オラクル）として使い、キーチェーンの項目を端末上で復号して JSON に書き出します ——元の GHOSTBLADE がキーチェーンのデータベースを丸ごと持ち出していたのに対し、P7 は端末上で復号してから送ります（iVerify）。さらに imToken・TokenPocket・Trust Wallet・Bitget・Phantom・Solflare・Uniswap・Tonhub・Bitpie・TronLink のコンテナを探し、imToken の keystore は端末上で復号します（Habr）。C2 とは15秒ごとの /beacon POST（HTTP/1.0）で双方向に通信します。

本記録が収録する理由は、道具の移動です（本記録の評価）。国家級の顧客だけが使えた連鎖が、流出から約4か月で「アフィリエイトの配信チャネルを持つ犯罪サービス」として動いています。 Habr の分析は、配信ページに配信元を識別する channelcode パラメータが仕込まれ、トラフィックブローカーに典型的な訪問者テレメトリが取られていることを指摘し、中国語話者の金銭目的の集団による「エクスプロイト配信サービス」と確度中程度で評価しています。

日本の読者にとっての要点は3つです。 ①6件の CVE はすべて修正済みで、iOS 18.7.3 または 26.3 以降なら連鎖は成立しません ——本件は「古い iOS を使い続けている端末」の問題です。 ②痕跡は再起動かクリーンアップまでしか残りません（永続化しない）——疑いがある端末は再起動する前に sysdiagnose を取る必要があります。 ③ドメインは週単位で入れ替わるため、ドメイン遮断よりも振る舞い（15秒間隔の HTTP/1.0 POST、------HqBound という多部分境界）での検知が要ります（Habr の推奨）。本記録に挙げた痕跡は悪性の検証をしていません ——照合先のテレメトリを持たないため、検知への投入は読者の環境での確認を要します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は特定の被害組織の侵害事案ではなく、 流出したエクスプロイト連鎖を再利用した犯罪キャンペーンである。** **攻撃側の経緯は「国家級の顧客向けに使われていた DarkSword が 2026年3月22日に流出し、金銭目的の集団がこれを改造して アフィリエイト型の配信サービスとして運用している」というものである** （Habr の評価。確度中程度）。 **本記録は、1台の端末が侵害される経路を段として記録する**—— **`initial-access`（中国語の賭博・暗号資産サイトの隠された iframe から バージョンに応じた連鎖を配信）、 `execution`（6件の CVE を連ねて最終的に SpringBoard へインプラントを注入）、 `credential-access`（`securityd` の `AppleKeyStore` を復号の神託として使い キーチェーンを端末上で復号）、 `collection`（暗号資産ウォレット10種のコンテナ・メモ・写真・アプリ一覧を収集）、 `command-and-control`（15秒ごとの `/beacon` POST で双方向通信）、 `exfiltration`（`/war` 等のエンドポイントへ送信）の6段。** **`persistence` は該当しない**——**インプラントは再起動までしか残らない。** **`privilege-escalation` は `execution` の中に含めた** （CVE-2025-43520 によるカーネルでの権限昇格が連鎖の一部であるため）。

  1. 1. 初期侵入推定
    **中国語のオンライン賭博サイト・暗号資産ニュースページに 隠された iframe から連鎖が読み込まれる。** **`group.html` → `loader.js` → `rce_loader.js` の順でページが連なり、 iOS のバージョンに応じた段が選ばれる。** **iOS 13〜17.2.1 の端末には Coruna（別の連鎖）、 18.x には DarkSword が送られる** ——**Habr はこの組み合わせを「DarkCoruna」と呼ぶ。** **ページには配信元を識別する `channelcode` パラメータがあり、 どのディストリビューターが送った訪問者かを数えている。** **ブラウザの localStorage に鍵を書いて再悪用を防いでいる** （`lab_device_uuid`・`__ds_inflight_worker`・`__ds_skip_workers`・ `_x_pe_done`・`_x_try`・`_x_ok`）
    根拠: iVerify の分析（配信元ドメインと localStorage の鍵）および Habr の公開情報分析（誘導サイト・ページの連鎖・配信元識別）
  2. 2. 実行推定
    **6件の CVE を連ねて最終的にインプラントが SpringBoard に注入される。** **CVE-2025-31277・CVE-2025-43529（JavaScriptCore。ブラウザでの遠隔コード実行）、 CVE-2026-20700（dyld。PAC の回避）、 CVE-2025-14174（ANGLE。WebContent から GPU プロセスへ）、 CVE-2025-43510（XNU。GPU プロセスから mediaplaybackd へ）、 CVE-2025-43520（XNU の VFS の競合。カーネルでの権限昇格）** （Habr が GTIG の報告にもとづいて整理）。 **GTIG の報告時点で3件がゼロデイだったが、 いずれも Apple へ報告され iOS 18.7.2・18.7.3・26.1・26.2・26.3 で修正されている。** **SpringBoard が攻撃者の基盤とのすべての通信を担う**（iVerify）。 **永続化はしない——再起動まで動く**
    根拠: Habr の整理（GTIG の報告にもとづく CVE の内訳と修正バージョン）、iVerify の分析（SpringBoard への注入）
  3. 3. 認証情報アクセス推定
    **`securityd` の `AppleKeyStore` サービスを復号の神託（オラクル）として使い、 キーチェーンの項目を端末上で復号して JSON に書き出す**（Habr。 同分析は「Phase 2」と呼ぶ）。 **元の GHOSTBLADE はキーチェーンのデータベースを複製して 攻撃者のサーバーへ送っていた**（iVerify） ——**P7 は端末上で復号してから送る。** **書き出し先は `/private/var/tmp/keychain_c2_dump.json` （`.tmp`・`.done` の併存あり）**
    根拠: iVerify の分析（キーチェーンを端末上で JSON 化する挙動とファイルパス）および Habr の公開情報分析（AppleKeyStore を復号の神託として使う仕組み）
  4. 4. 収集推定
    **暗号資産ウォレットのコンテナを探し、データを収集する。** **imToken・TokenPocket・Trust Wallet・Bitget・Phantom・Solflare・ Uniswap・Tonhub・Bitpie・TronLink**（Habr）。 **imToken の keystore は端末上で復号される。** **iVerify が名前を挙げているのは imToken のみ（`wallet_extract`）で、 `wallet_scan` は一般にインストール済みのウォレットを探すものとしている** 〈齟齬に記録〉。 **ほかに `photos`・`apps`・`disk_scan`・ `memo_scan`（Apple のメモ。`_hq_notestore`・`notes.sqlite*` を複製）・ `photo_scan` を持つ。** **GHOSTBLADE にあった Telegram・WhatsApp・iCloud・Wi-Fi・SMS の 収集機能は削除されている**（Habr） ——**本記録はこれを「諜報の道具から窃取の道具へ」の証拠と読む**
    根拠: iVerify の分析（命令の一覧と痕跡ファイル）および Habr の公開情報分析（対象ウォレット10種・削除された収集機能）
  5. 5. C2通信推定
    **15秒ごとに `/beacon` へ POST を送り、応答に載る命令を実行する**（iVerify）。 **HTTP/1.0 で、iPhone Safari の User-Agent を固定で使う。** **`sleep` コマンドで間隔を変更できる。** **HTTPS を使うが証明書の厳密な検証を行っていない。** **エンドポイント: `/result`（結果）・`/a`（登録）・`/event`（生存通知）・ `/u`（アプリ一覧）・`/nb`（メモ）・`/p`（写真）・ `/war`（キーチェーンとウォレットのデータ）。** **`/p` には `------HqBound` という多部分境界が使われる。** **iVerify が挙げた C2 は `agdx53[.]cc` と `js.gotoiphone[.]com/ios18`。** **Habr は第3ビルドの C2 として `www.y21t8bcya6q9b7155a[.]cc` （2026年5月25日登録）を加えている**
    根拠: iVerify の分析（beacon 間隔・エンドポイント・User-Agent・多部分境界・C2 ドメイン）、Habr の公開情報分析（第3ビルドの C2）
  6. 6. 持ち出し推定
    **収集したデータを C2 のエンドポイントへ送る。** **キーチェーンとウォレットのデータは `/war`、 写真は `/p`、メモは `/nb`、アプリ一覧は `/u`、 命令の実行結果は `/result`**（iVerify）。 **送信は HTTP/1.0 の POST で、 HTTPS を使うが証明書の厳密な検証を行っていない。** **送信量・件数・持ち出された資産額はいずれも公表されていない**
    根拠: iVerify の分析（エンドポイントの用途と送信方式）

目的も変わっています。元の DarkSword については、ウクライナの正規サイト（政府ドメインを含む）に隠された iframe からiPhone 利用者へ連鎖が送られる水飲み場攻撃として報じられていました（Lookout・iVerify の共同分析として伝えられたもの）。P7 の狙いは暗号資産です ——キーチェーンとウォレットのシードフレーズ・keystore。 同じ技術が、諜報から窃取へ移っています。

本記録の評価——流出したエクスプロイトキットの再利用は、防御側にとって「標的の広がり」を意味します。 国家級の作戦なら標的は選別されますが、アフィリエイト型の配信サービスは来た端末を無差別に侵害します。 「自組織は国家に狙われる立場ではない」という前提は、この移動によって無効になります。

(2) 実行と注入 6件の CVE を連ね、最終的にインプラントが SpringBoard に注入されます。 SpringBoard が攻撃者の基盤との通信をすべて担います（iVerify）。永続化はしません——再起動まで動きます（Habr）。

(3) キーチェーンの復号（P7 の新しい点） securityd の AppleKeyStore サービスを復号の神託として使い、キーチェーンの項目を端末上で復号して JSON に書き出します（Habr）。元の GHOSTBLADE はキーチェーンのデータベースを複製して攻撃者のサーバーへ送っていました（iVerify）——P7 は端末上で復号してから送るため、送られる量が減り、攻撃者側での復号の手間も消えます（本記録の整理）。

(4) ウォレットの窃取 imToken・TokenPocket・Trust Wallet・Bitget・Phantom・Solflare・Uniswap・Tonhub・Bitpie・TronLink のコンテナを探します（Habr）。imToken の keystore は端末上で復号されます。 iVerify が名前を挙げているのは imToken のみで、wallet_scan は一般にインストール済みのウォレットを探すものとしています〈齟齬に記録〉。

(5) C2 15秒ごとの /beacon POST（HTTP/1.0、iPhone Safari の User-Agent を固定）。 応答に命令が載る双方向通信で、sleep で間隔を変えられます。 エンドポイントは /result（結果）・/a（登録）・/event（生存通知）・/u（アプリ一覧）・/nb（メモ）・/p（写真）・/war（キーチェーンとウォレットのデータ）（iVerify）。HTTPS は使うが証明書の厳密な検証をしていません。

(6) 命令 約17の処理（Habr）。ls・download・photos・apps・exec（インプラント内で JavaScript を実行）・disk_scan・memo_scan（Apple のメモ）・photo_scan・wallet_scan・wallet_extract（iVerify）、および約50のシェル風の下位命令を持つ execute_command（Habr）。

削った機能も記録に値します（Habr）。読み込みプログラムは GHOSTBLADE のものとバイト単位で同一で、TaskRop と MIG の回避のコードも変更されていません。 一方、データ収集の論理は書き直され、Telegram・WhatsApp・iCloud・Wi-Fi・SMS の収集機能は削除されています。 本記録の評価——これは「諜報の道具から窃取の道具へ」の最も分かりやすい証拠です。 メッセージアプリの中身は、金銭目的の攻撃者には要らない。

6件の CVE はすべて修正済み——成立しているのは未修正の端末が残っているからで、痕跡は再起動で消える対策・注意喚起出典 [1] [2]

防御側にとって最も重要な事実を先に書きます。

DarkSword が悪用する6件の脆弱性はいずれも Apple へ報告され、修正済みです（iOS 18.7.2・18.7.3・26.1・26.2・26.3 で順次修正。Habr の整理）。

つまり P7 は、未修正の端末に対してのみ成立します。 GTIG の報告時点では3件がゼロデイでしたが、P7 の活動時点ではすべて既知です ——本記録が原因軸に「脆弱性の放置」を併記した理由です。

第一の対策は更新です（Habr の推奨）。
- iOS 18.7.3 以降、または 26 系なら 26.3 以降へ更新する
- 高リスクの利用者はロックダウンモードを有効にする

第二に、調べ方には時間の制約があります（本記録の評価）。インプラントは永続化せず、再起動またはクリーンアップまでしか残りません。 したがって痕跡を取るなら再起動する前です。 sysdiagnose で見える痕跡（Habr。再起動・クリーンアップまで有効）——

  • /private/var/tmp/keychain_c2_dump.json とその .done（および .tmp）
  • /private/var/tmp/p7_debug.log
  • /private/var/tmp/c2_wallet_debug.log
  • imToken の keystore に関する出力
  • /private/var/tmp/_hq_notestore と notes.sqlite*（Apple のメモの複製）
  • /var/mobile/Library/Caches/ios_disk_scan.txt

ブラウザの localStorage の鍵—— lab_device_uuid・__ds_inflight_worker・__ds_skip_workers・_x_pe_done・_x_try・_x_ok。

第三に、ドメインで守ろうとしないことです（Habr の明確な推奨）。
- ドメインは週単位で入れ替わる ——振る舞いでの警報を置く（15秒間隔の HTTP/1.0 POST、多部分境界 ------HqBound、channel_code / source フィールド）
- ハッシュのフィードは価値が低い ——各展開でエクスプロイトのファイルが固有になる
- 共用の Alibaba OSS の IP（47[.]79[.]48[.]200）を遮断してはならない ——正規の利用者と共用されている

第四に、暗号資産を扱う利用者への案内です（Habr）。該当するページを閲覧した利用者は、すべてのシードフレーズと keystore が侵害されたものとして扱い、清浄な端末から資金を移すべきとされています。本記録の評価——これが本件で最も実務的な助言です。 キーチェーンが端末上で復号されて持ち出される以上、端末を直しても鍵は戻りません。

最後に本DBの方針を繰り返します。 ここに挙げた痕跡は、本記録が悪性を検証したものではありません ——照合先のテレメトリを持たないためです。 検知へ投入する前に、自環境での確認が必要です。 Habr が示した YARA の案も、P7 の1ビルドでしか試験されておらず、遮断に使う前に追加の検証が必要とされています。

帰属の訂正が1つ含まれている——初期報道が UNC6748 に帰していた基盤は UNC6353 のものだった帰属出典 [2]

本件の資料には、帰属の訂正が含まれています（Habr）。本記録はこれを、帰属が後から動く例として記録します。

訂正の内容—— 2026年3月の初期報道の一部は、static.cdncounter[.]net とsqwas.shapelie[.]com を DarkSword の発信元基盤としてUNC6748 に帰属させていた。 しかし GTIG によれば、この基盤は UNC6353 のものであり、sqwas.shapelie[.]com は GHOSTBLADE の持ち出し先サーバーである。 UNC6748 はサウジアラビア関連の別クラスタである。

TA446 との関係も整理されています。 TA446 は流出した UNC6353 のキットをそのまま再利用しており、両集団の結びつきは「キットの流出」であって、運用上の重なりではない（Habr の評価）。

P7 の運用者については、国家の関与を示す証拠は見られないとされます。 評価は確度中程度で「中国語話者の金銭目的の集団によるエクスプロイト配信サービス」です。 元の DarkSword の開発者は依然として特定されておらず、その開発者と P7 の作者の関係は肯定も否定もされていません。

本記録の整理——同じエクスプロイト連鎖を使っている集団が少なくとも3つ区別されています。

集団 関係 確度
UNC6353 元の DarkSword の運用者。ロシア関連の疑いが報じられている GTIG の帰属（本記録は原典未取得）
TA446 流出したキットをそのまま再利用（2026年3月のキャンペーン） Habr の整理
P7 の運用者 流出したキットを改造。金銭目的・中国語話者とみられる Habr の評価（確度中程度）
UNC6748 DarkSword とは無関係。 サウジアラビア関連の別クラスタ Habr による訂正

本記録が強調するのは、同じ道具を使っていることが同じ集団であることを意味しないという点です（本記録の評価）。流出したキットは「共有された道具」であり、痕跡の重なりだけで帰属を語ると誤ります。 本DBが共有ツールを追跡対象から外している理由と同じ構造です。

P7 は普通の通販サイトからも届いていた——期限切れになった解析ドメインが入口になった波及・関係先

本記録は初報で、P7 の配信を 「中国語の賭博・暗号資産サイトを閲覧するだけで」と書いた（既出の節）。 配信路はそれだけではなかった（出典4）〈重要〉。

Report URI（スコット・ヘルム氏）が記録した連鎖はこうである （出典4 を経由した引用。訳は本記録）——

  • 2026年9月15日、期限切れになっていた電子商取引の解析ドメインecomtrack[.]io が新しい所有者に再登録された。 その計測タグは「とうに気にされなくなった通販サイトのテーマの中にそのまま残っていた」ため、それらの通販サイトは新しい所有者が管理するコードを読み込み始めた。
  • タグは買い物客ごとの端末情報を集めて新しい所有者のサーバへ送る。 - 走査器やクローラは無作為の YouTube 動画か google.com へ送られる。 - 実在の訪問者はトラフィックブローカーによって3者へ売られる——投資詐欺のページ、オンラインカジノ、偽の暗号資産取引サイト。
  • 偽の取引サイトは iOS 18.4.0〜18.7.2 の Safari かを確認して DarkSword を配る。 - Report URI はこのインプラントを P7 と一致させた。2つのモジュールが iVerify の検体と「バイト単位で同一」だった。

本記録がこれを重く扱う理由は2つである（本記録の評価）〈重要〉。

第一に、被害者が訪れたのは普通の通販サイトである。 「買い物客は、テーマの中のスクリプトを忘れていた店を見ただけで、 それ以上に危ないことは何もしていない。 それらの店はどれも悪性ではなかった—— だからこそ URL の評価やサイトの遮断リストは、 この種の攻撃に対してほとんど守りにならない」（出典4。訳は本記録）。 本記録が初報で書いた配信路（中国語の賭博サイト）は、 「怪しいサイトを見るな」という指導で部分的には塞げる。 この経路は塞げない。

第二に、入口になったのは自組織の資産ではない。 期限切れのドメインに残った他人のタグである ——自社サイトの第三者スクリプトの棚卸しという論点であり、 本記録の対象（端末の感染）とは別の層にある。 本記録はこの層を、自組織が「配る側」に立つ場合の論点として applicability に加えた。

なお、本記録は Report URI の原典を取得しておらず、 出典4（iVerify の解説記事）を経由した引用である（本記録の明示） 〈齟齬に記録〉。

広告が描画された瞬間に始まる——「ハーフクリック」は利用者の注意では防げない原因・手口

iVerify は、広告経由の配信を「ハーフクリック攻撃」と呼んでいる （出典4）〈重要〉—— 「表示広告を通じて配られ、広告がページ上で読み込まれた瞬間に 動き始めるエクスプロイト。被害者は何もタップする必要がない」 （訳は本記録）。

同社は既存の2類型の間に置いて説明している（出典4。訳は本記録）——

  • ワンクリック——被害者がリンクを押す。配信はフィッシングの SMS・メール・チャット、または水飲み場攻撃。
  • ハーフクリック——広告を表示するアプリやページを開く。配信はエクスプロイトのコードを載せた標的型の表示広告。
  • ゼロクリック——被害者は何もしない。OS が背後で処理するメッセージや通話。

「この類型が守りにくいのは、被害者が危ないことを何もしていないからである。 添付を開かず、リンクを辿らず、アプリも入れない—— ただ広告を表示するアプリかサイトを使っただけで、 それはほとんどの電話の、ほとんどの時間を説明している」 （出典4。訳は本記録）〈重要〉。 同社は「どの呼び方を好むにせよ、守る側にとっての帰結は同じである—— 利用者が気づく機会すら与えられない攻撃を、 利用者教育では止められない」と結んでいる。

なぜ水飲み場から広告へ移ったのか（出典4。訳は本記録）。 「本年の初め、流出した iOS キットの主な配信路は水飲み場だった。 Google Threat Intelligence Group と iVerify は、 侵害されたウクライナのウェブサイトの悪性のスクリプトタグを通じて DarkSword が配られているのを見つけた。 しかしこの手法は、ある点までしか機能しない。 侵害されたサイトは、たまたま訪れた者に届くだけであり、 その多くはエクスプロイトが触れない iOS を動かしている。 DarkSword が対応するのは iOS 18.4 から 18.7 であり、 iOS 26 の訪問者はすべて攻撃者にとって無駄になる」。 広告はこの無駄を取り除く ——端末・OS のバージョン・場所・関心で絞れるため、 iOS 18.5 のエクスプロイトを持つ者は 18.5 の iPhone にだけ出る枠を買い、 さらに暗号資産に関心のある層へ狭められる。 年次報告の表現では、広告は 「大量キャンペーンの到達と、標的型の精度」を併せ持つ（出典3・4。訳は本記録）。

実際に観測された事例（出典4）〈重要〉—— iVerify のテレメトリは、同一人物に対する2件の別個の DarkSword 攻撃を 記録した。 「この人物について、高価値の標的だと示すものは何も無い。」 1件目は Instagram の閲覧中、ad-track[.]live から配信された広告経由で、 本人は何もクリックしていない。 2件目は後日で、本人がリンクを押しており、 別の脅威アクターが別の DarkSword 変種を使っていた。 いずれも目的は暗号資産の窃取と評価されている。 広告の背後のドメインは今年のワールドカップを題材にしており、 「特定個人のためではなく、到達数のために選ばれた餌」だった。 同社は「広告で支えられたどのプラットフォームにも同種の危険がありうる」 としつつ、「広告が出たプラットフォームの失敗を示すものは何も無い」と 付記している。

【前史・別事案】この技術は犯罪者が採る前に、傭兵型スパイウェアで 実証されていた（出典4 を経由した Citizen Lab の引用）—— 2026年10月、Citizen Lab はイスラエルの広告技術企業 Discover-Tech に ついて公表した。 同社のサーバは広告が描画されると端末の IP と広告識別子を確認し、 選んだ標的にだけ追加の JavaScript を送り、 それ以外には「0バイトの応答」を返していた。 Al Jazeera で少なくとも45台の標的端末が見つかり、 攻撃は「高い確度で」Candiru に結びつけられた。 2026年3月から6月にかけて、関与した需要側プラットフォームの1つは 3,770,286,576 件の入札のうち 441,954,291 件を落札したとみられる。 本記録はこれを本事案とは別の事案として置く ——P7 とは無関係だが、同じ配信技術の先行例である。 Citizen Lab の原典は取得していない〈齟齬に記録〉。

検出の75%は犯罪者だった——「狙われる立場の人を守る」前提の脅威モデルが合わなくなっている評価・解釈

iVerify の年次報告が示した所見のうち、本記録の主題に直結するのは2つである （出典3）〈重要〉。

①「本年の検出の75%は、資格情報と暗号資産を盗む犯罪者によるものだった。 確認できた企業のすべての事例で、影響を受けた人は managing director より下の職位だった」（出典3。訳は本記録）。

②「犯罪集団はその後コードを分岐させて新しい変種を作っており、 その1つが、金融機関の従業員の端末で iVerify が見つけた P7 変種である」 （出典3。訳は本記録）〈重要〉。 本記録は初報で、iVerify が P7 を見つけた経緯を 「自社の顧客端末の1台についての警報から」としか書けていなかった。 ここで被害者の属性が明らかになった ——金融機関の、経営層ではない従業員の端末である。

普及率は約900台に1台（出典3）。 報道が同社共同創業者の説明として伝えた補足はこうである（出典5）—— 消費者の走査1,000回あたり1.07件、企業は0.7件、 走査した消費者端末は「数十万台」（正確な数の開示は断った）、 Fortune 500 企業1社あたり年間およそ65件、 残り25%は Pegasus 等の傭兵型スパイウェア。 「要点は、今年が iOS のスパイウェアが主流になり、 誰にとっても問題になった年だということだ。 いま iPhone を狙ってスパイウェアを使う第一の脅威アクターは政府ではなく、 ただのサイバー犯罪者であり、しかも無差別である」（コール氏。訳は本記録）。 別の調査会社の評は「900に1つは、網の数字であって照準の数字ではない。 傭兵型スパイウェアはメスとして作られたが、いまは網として使われている」 （出典5。訳は本記録）。

留保を省かずに書く（本記録の明示）〈重要〉。 ①母集団は iVerify の検査を受けた端末に限られ、無作為標本ではない。 ②走査の総数は公表されていないため、検出の絶対数は分からない。 ③「1,000走査あたり」は端末数ではない ——同一端末が複数回検査される可能性がある。 ④同社は、無償の端末検査の利用者が2年で4倍になったため 感染率は下がると予想していたと述べている（出典5） ——2年前は「スパイウェアを疑う理由のある要人」が多かったのに対し、 いまは一般の利用者が増えた。それでも率は下がらなかった、という論旨である。 ⑤本記録は報告書の本体を取得していない （ダウンロードに登録が必要）〈齟齬に記録〉。

本記録の評価〈重要〉——本記録はこの事案を初報から 「国家級の道具が金銭目的へ移った形」として扱ってきた。 年次報告はそれを測って示した ——P7 は例外ではなく、75%の側の1件である。 実務上の帰結は1つに絞れる。 「高リスクの要人だけに携帯の防御を厚くする」という配り方が、 この脅威に対しては的を外す。 本件の被害者は金融機関の一般従業員であり、 iVerify が確認した企業の事例では例外なく経営層より下だった。

もう1点、検知の前提が崩れている。 「われわれの知る限り、DarkSword または Coruna の感染を確認した端末で、 Apple の脅威通知を受け取ったものは無い」（出典3。訳は本記録）〈重要〉—— 傭兵型スパイウェアでは通知が発見の端緒になってきたが、 この層ではそれが働いていない。 本記録は、Apple 側の見解を確認していない（本記録の明示）。

残らないから見つからない——再起動で消え、痕跡は2時間で古くなる対策・注意喚起

本記録が初報で書いた「P7 は未修正の端末に対してのみ成立する」は そのまま有効である（既出の節）。 今回の追記で加わったのは、 「成立したあとに見つけられるか」についての条件である（出典4）〈重要〉。

調査が難しい理由は2つある（出典4。訳は本記録）。

第一に、配信側が標的以外に何も見せない。 「ecomtrack[.]io の連鎖では、 データセンターと VPN の IP には一貫して空の応答が返されていた。 一部の住宅回線の訪問者には、最初の要求では配送があり、 その後は何も無かった。」 Discover-Tech のサーバも同じで、 選ばなかった端末には「0バイトの応答」を返していた。 「解析者が感染を再現しようとする時点では、 ページは何も出さない。したがって証拠は端末そのものから来るしかない。」

第二に、端末に残る時間が短い。 「DarkSword は常駐しないため、再起動または更新は、 動作中のインプラントと、調査者が探すであろう多くの痕跡を一緒に消す。 年次報告によれば、一部の DarkSword の痕跡は端末上にごく短時間しか存在せず、 端末上での継続的な監視がその窓の間に捉えなければ、 完全に見落とすことになる。」 実時間での収集ができない場合は2時間以内に、としている（出典4）。

同社が挙げた対策は5つである（出典4。訳は本記録）——

  • 修正する。 「DarkSword の連鎖にあったすべての脆弱性は iOS 26.3 で修正されており、大半はそれより早く修正されていた」（GTIG と iVerify）。 「流通している犯罪版が狙うのは、それらの更新を飛ばした端末である。」
  • BYOD に最小 OS バージョンを強制する。 「iVerify の企業事例で被害を受けた組織は BYOD に大きく依存しており、その MDM は個人の端末に iOS の更新を強制しない。あるバージョンを下回る端末の社内アクセスを遮断すれば、その隙間の多くが閉じる。」
  • 端末上に検知を置く。 「選別するエクスプロイトサーバは、調査者に取得すべきものを何も残さない。端末上の EDR は、悪用が残す副作用をシステムログ・診断情報・端末上の痕跡から見ることができる。」
  • 遠隔測定を実時間で集める。 できない場合は2時間以内に。 - 最もリスクの高い職員にロックダウンモードを使う。 「Google は更新ができない場合に推奨しており、Apple の広報担当は TechCrunch に対し、これが DarkSword の攻撃を遮断するだろうと述べた。端末の動き方を変えるため、全社ではなく短い名簿に合う。」

広告遮断については、同社は限界を明示している（出典4。訳は本記録）—— 「ブラウザでの露出は減らせるが、 広告を表示するすべてのアプリを覆うわけではなく、 乗っ取られたスクリプトの経路にも対処しない。 iOS を更新し続けることと、端末上で検知を動かすことが、 どちらの経路にも通用する対策である。」

本記録の評価〈重要〉——この事案で組織が握れる梃子は、 実のところ1つしかない。 BYOD の端末に対して、組織は更新を強制できない。 できるのは「このバージョンを下回る端末には社内の資産を触らせない」 という接続条件の側である。 そして見つける側では、装備の有無より採取の周期が結果を決める ——月次のフォレンジック採取や利用者の申告を起点にした調査は、 2時間の窓に間に合わない。

  • **ドメイン遮断ではなく、通信の振る舞いで警報を置く**
    **Habr は「ドメインは週単位で入れ替わるため、 振る舞いにもとづく警報を推奨する」としている。** **特徴は15秒間隔の HTTP/1.0 POST、 固定の iPhone Safari の User-Agent、 `------HqBound` という多部分境界、 `channel_code` / `source` フィールドである。** **同分析は「ハッシュのフィードは価値が低い」 （各展開でエクスプロイトのファイルが固有になる）とも述べている。**
    取るべき行動 **①HTTP/1.0 の POST が固定間隔で出ている通信を探す規則を書く** ——**ただし `sleep` コマンドで間隔が変えられるため、 間隔だけを条件にしない。** **②多部分境界 `------HqBound` を含む本文を探す。** **③共用の Alibaba OSS の IP（`47[.]79[.]48[.]200`）を 遮断対象に入れない**——**正規の利用者と共用されている。** **④HTTPS で証明書の厳密な検証をしていない通信を 検知の材料にできるか検討する。**
  • **ブラウザの localStorage を調査の材料として使う**
    **P7 の配信ページは、同じ端末での再悪用を防ぐために localStorage に鍵を書く**（iVerify は「安定性の改良」と位置づける）。 **`cdn.gotoiphone[.]com` の生成元では `__ds_inflight_worker`・`__ds_skip_workers`、 `mzpo30[.]cam` では `_x_pe_done`・`_x_ok`、 ほかに `lab_device_uuid`・`_x_try` が挙げられている。** **本記録の評価**——**攻撃者が「効率のために残した状態」が そのまま痕跡になっている。**
    取るべき行動 **①モバイルのフォレンジックで、 ブラウザの localStorage を取得対象に含める。** **②生成元（オリジン）ごとの鍵の一覧を保存し、 既知の攻撃の鍵と突き合わせられるようにする。** **③Safari の履歴・キャッシュだけを見る手順になっていないか 見直す。**
  • **「修正済みの CVE」を自組織の端末で未修正のまま放置していないか測る**
    **DarkSword が悪用する6件の CVE はいずれも修正済みである** （iOS 18.7.2・18.7.3・26.1・26.2・26.3）。 **P7 が成立しているのは未修正の端末が残っているからであり、 これは攻撃の巧妙さではなく更新の遅れの問題である** （本記録の評価）。 **GTIG の報告時点では3件がゼロデイだったが、 P7 の活動時点ではすべて既知である。**
    取るべき行動 **①MDM で iOS バージョンの分布を出し、 18.7.3 未満（および 26 系で 26.3 未満）の端末を一覧にする。** **②更新できない理由（業務アプリの互換性・端末の世代）を 端末ごとに記録する** ——**理由が分かれば代替策（隔離・ロックダウンモード）を選べる。** **③「ゼロデイだった脆弱性」を、 修正後も未修正端末のリスクとして追跡し続ける。**
  • **流出したエクスプロイトキットの再利用を、脅威情報の追跡に織り込む**
    **P7 の読み込みプログラムは 元の GHOSTBLADE のものとバイト単位で同一であり、 TaskRop と MIG の回避のコードも変更されていない**（Habr）。 **一方でデータ収集の論理は書き直され、 Telegram・WhatsApp・iCloud・Wi-Fi・SMS の収集機能は削除されている** ——**諜報の道具から窃取の道具へ変わった形である**（本記録の読み）。 **コードが同一でも運用者と目的が違う。**
    取るべき行動 **①検知規則を書くとき、 「コードの一致」で帰属を決めない** ——**規則は挙動に対して書き、帰属は別の欄に持つ。** **②既知のファミリの検知が当たったとき、 亜種の可能性を初動で排除しない。** **③本DBと同じ方針で、 共有ツール（流出したキット）を帰属の根拠にしない。**
  • **BYOD で握れる梃子は「更新の強制」ではなく「最小 OS 版での接続遮断」である**
    **iVerify の企業事例で被害を受けた組織は BYOD に大きく依存しており、 その MDM は個人の端末に iOS の更新を強制しない**（出典4。訳は本記録）。 **一方、DarkSword の連鎖の脆弱性はすべて iOS 26.3 で修正済みで、 大半はそれより早く修正されていた**（出典4） ——**成立しているのは、更新を飛ばした端末が残っているためである。** **組織は個人の端末を更新できないが、 古い端末に自社の資産を触らせないことはできる**（本記録の評価）
    取るべき行動 **BYOD の社内アクセス条件に OS バージョンの下限を入れ、 下限未満の端末は遮断する。** **下限は「DarkSword の連鎖が修正された版」を基準に決め、 四半期ごとに引き上げる。** **遮断時の代替手段（貸与端末・Web 限定アクセス）を同時に用意する** ——**用意が無い遮断は例外申請で崩れる**
  • **携帯の防御を「要人の名簿」ではなく全従業員に配り直す**
    **2026年の検出の75%は資格情報と暗号資産を盗む犯罪者によるもので、 iVerify が確認できた企業の事例では、 影響を受けた人は例外なく managing director より下の職位だった** （出典3。訳は本記録）。 **本記録の対象である P7 も、 金融機関の経営層でない従業員の端末で見つかっている**（出典3）。 **配信は広告が描画された瞬間に始まるため、 利用者教育では止められない**（出典4）
    取るべき行動 **「高リスク者だけに端末上の検知を入れる」運用を見直し、 社内資産に触る全端末を対象にする。** **ロックダウンモードは端末の動き方を変えるため、 引き続き短い名簿に限る**（出典4） ——**全社に配るのは検知と OS 版の条件、 短い名簿に配るのはロックダウンモード、と分ける**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。

システム構成□ 業務で使う iPhone に iOS 18.4〜18.7 のままの端末が残っている（または OS バージョンの分布を把握していない）
データの保持□ 暗号資産のシードフレーズ・keystore、または業務アプリの長期トークンをスマートフォンのキーチェーンに置いている
認証・認可□ キーチェーンに保存された認証情報を、サーバー側から失効させる手段が無い
運用・監視□ モバイル端末の警報のうち「既知のシグネチャに一致しない」ものを、調査せずに閉じる運用になっている
運用・監視□ モバイル端末の侵害が疑われたとき、初動として再起動・初期化を行う手順になっている
運用・監視□ モバイルの脅威への対策が、ドメイン遮断とハッシュのフィードに依存している
運用・監視□ **端末の遠隔測定（ログ・診断情報）を実時間、または2時間以内に集める仕組みがあるか** （月次のフォレンジック採取や、利用者の申告を起点にした調査だけになっていないか）**DarkSword は常駐しないため、再起動または更新で 動作中のインプラントと多くの痕跡が一緒に消える。** **一部の痕跡は端末上にごく短時間しか存在しない**（出典4） ——**配信側も標的以外に空の応答を返すため、 後から再現して確かめることができない。** **検知の有無は装備ではなく採取の周期で決まる**（本記録の評価）
