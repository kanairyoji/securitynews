INC-2026-0466流出した国家級 iOS 連鎖が暗号資産窃取へ転用

国家級の顧客向けに使われていた iOS エクスプロイト連鎖「DarkSword」が2026年3月に流出し、それを改造した犯罪版「P7」が暗号資産の窃取に転用された——iVerify が2026年10月8日に実装を分析。iOS 18.4〜18.7 の端末が中国語の賭博・暗号資産サイトを閲覧するだけで SpringBoard 内にインプラントが動き、キーチェーンを端末上で復号して imToken 等のウォレットのシードフレーズと keystore を持ち出す

脅威・攻撃キャンペーン脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用脆弱性の放置
初報: 2026年10月8日 最終更新: 2026年10月11日

iVerify は 2026年10月8日、iOS 向けエクスプロイト連鎖 DarkSword の犯罪版インプラント 「P7」 の分析「Sleep, Beacon, Steal, Repeat - The Story of P7 DarkSword Variant」を公表しました。同社が2026年8月に顧客端末1台の警報を調べたところ、通常の DarkSword の検知とは異なる未知の変種だったことが分かったという経緯です。「P7」の名は、攻撃者が改造部分で使った変数の接頭辞 p7_ に由来します。

DarkSword はもともと国家級の顧客向けに使われていた連鎖です。 Google Threat Intelligence Group（GTIG）が2026年3月に報告し、6件の CVE（当時3件はゼロデイ）を連ねて iOS 18.4〜18.7 の端末をウェブページの閲覧だけで侵害するものでした。その完全なキットが2026年3月22日に流出したとされ、以後、金銭目的の集団がこれを改造して使っています（Habr の分析）。

P7 が何をするか。中国語のオンライン賭博サイト・暗号資産ニュースページに隠された iframe から連鎖が送り込まれ、数秒で SpringBoard 内にインプラントが動きます。インプラントは securityd の AppleKeyStore を復号の神託（オラクル）として使い、キーチェーンの項目を端末上で復号して JSON に書き出します ——元の GHOSTBLADE がキーチェーンのデータベースを丸ごと持ち出していたのに対し、P7 は端末上で復号してから送ります（iVerify）。さらに imToken・TokenPocket・Trust Wallet・Bitget・Phantom・Solflare・Uniswap・Tonhub・Bitpie・TronLink のコンテナを探し、imToken の keystore は端末上で復号します（Habr）。C2 とは15秒ごとの /beacon POST（HTTP/1.0）で双方向に通信します。

本記録が収録する理由は、道具の移動です（本記録の評価）。国家級の顧客だけが使えた連鎖が、流出から約4か月で「アフィリエイトの配信チャネルを持つ犯罪サービス」として動いています。 Habr の分析は、配信ページに配信元を識別する channelcode パラメータが仕込まれ、トラフィックブローカーに典型的な訪問者テレメトリが取られていることを指摘し、中国語話者の金銭目的の集団による「エクスプロイト配信サービス」と確度中程度で評価しています。

日本の読者にとっての要点は3つです。 ①6件の CVE はすべて修正済みで、iOS 18.7.3 または 26.3 以降なら連鎖は成立しません ——本件は「古い iOS を使い続けている端末」の問題です。 ②痕跡は再起動かクリーンアップまでしか残りません（永続化しない）——疑いがある端末は再起動する前に sysdiagnose を取る必要があります。 ③ドメインは週単位で入れ替わるため、ドメイン遮断よりも振る舞い（15秒間隔の HTTP/1.0 POST、------HqBound という多部分境界）での検知が要ります（Habr の推奨）。本記録に挙げた痕跡は悪性の検証をしていません ——照合先のテレメトリを持たないため、検知への投入は読者の環境での確認を要します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は特定の被害組織の侵害事案ではなく、 流出したエクスプロイト連鎖を再利用した犯罪キャンペーンである。** **攻撃側の経緯は「国家級の顧客向けに使われていた DarkSword が 2026年3月22日に流出し、金銭目的の集団がこれを改造して アフィリエイト型の配信サービスとして運用している」というものである** （Habr の評価。確度中程度）。 **本記録は、1台の端末が侵害される経路を段として記録する**—— **`initial-access`（中国語の賭博・暗号資産サイトの隠された iframe から バージョンに応じた連鎖を配信）、 `execution`（6件の CVE を連ねて最終的に SpringBoard へインプラントを注入）、 `credential-access`（`securityd` の `AppleKeyStore` を復号の神託として使い キーチェーンを端末上で復号）、 `collection`（暗号資産ウォレット10種のコンテナ・メモ・写真・アプリ一覧を収集）、 `command-and-control`（15秒ごとの `/beacon` POST で双方向通信）、 `exfiltration`（`/war` 等のエンドポイントへ送信）の6段。** **`persistence` は該当しない**——**インプラントは再起動までしか残らない。** **`privilege-escalation` は `execution` の中に含めた** （CVE-2025-43520 によるカーネルでの権限昇格が連鎖の一部であるため）。

  1. 1. 初期侵入推定
    **中国語のオンライン賭博サイト・暗号資産ニュースページに 隠された iframe から連鎖が読み込まれる。** **`group.html` → `loader.js` → `rce_loader.js` の順でページが連なり、 iOS のバージョンに応じた段が選ばれる。** **iOS 13〜17.2.1 の端末には Coruna（別の連鎖）、 18.x には DarkSword が送られる** ——**Habr はこの組み合わせを「DarkCoruna」と呼ぶ。** **ページには配信元を識別する `channelcode` パラメータがあり、 どのディストリビューターが送った訪問者かを数えている。** **ブラウザの localStorage に鍵を書いて再悪用を防いでいる** （`lab_device_uuid`・`__ds_inflight_worker`・`__ds_skip_workers`・ `_x_pe_done`・`_x_try`・`_x_ok`）
    根拠: iVerify の分析（配信元ドメインと localStorage の鍵）および Habr の公開情報分析（誘導サイト・ページの連鎖・配信元識別）
  2. 2. 実行推定
    **6件の CVE を連ねて最終的にインプラントが SpringBoard に注入される。** **CVE-2025-31277・CVE-2025-43529（JavaScriptCore。ブラウザでの遠隔コード実行）、 CVE-2026-20700（dyld。PAC の回避）、 CVE-2025-14174（ANGLE。WebContent から GPU プロセスへ）、 CVE-2025-43510（XNU。GPU プロセスから mediaplaybackd へ）、 CVE-2025-43520（XNU の VFS の競合。カーネルでの権限昇格）** （Habr が GTIG の報告にもとづいて整理）。 **GTIG の報告時点で3件がゼロデイだったが、 いずれも Apple へ報告され iOS 18.7.2・18.7.3・26.1・26.2・26.3 で修正されている。** **SpringBoard が攻撃者の基盤とのすべての通信を担う**（iVerify）。 **永続化はしない——再起動まで動く**
    根拠: Habr の整理（GTIG の報告にもとづく CVE の内訳と修正バージョン）、iVerify の分析（SpringBoard への注入）
  3. 3. 認証情報アクセス推定
    **`securityd` の `AppleKeyStore` サービスを復号の神託（オラクル）として使い、 キーチェーンの項目を端末上で復号して JSON に書き出す**（Habr。 同分析は「Phase 2」と呼ぶ）。 **元の GHOSTBLADE はキーチェーンのデータベースを複製して 攻撃者のサーバーへ送っていた**（iVerify） ——**P7 は端末上で復号してから送る。** **書き出し先は `/private/var/tmp/keychain_c2_dump.json` （`.tmp`・`.done` の併存あり）**
    根拠: iVerify の分析（キーチェーンを端末上で JSON 化する挙動とファイルパス）および Habr の公開情報分析（AppleKeyStore を復号の神託として使う仕組み）
  4. 4. 収集推定
    **暗号資産ウォレットのコンテナを探し、データを収集する。** **imToken・TokenPocket・Trust Wallet・Bitget・Phantom・Solflare・ Uniswap・Tonhub・Bitpie・TronLink**（Habr）。 **imToken の keystore は端末上で復号される。** **iVerify が名前を挙げているのは imToken のみ（`wallet_extract`）で、 `wallet_scan` は一般にインストール済みのウォレットを探すものとしている** 〈齟齬に記録〉。 **ほかに `photos`・`apps`・`disk_scan`・ `memo_scan`（Apple のメモ。`_hq_notestore`・`notes.sqlite*` を複製）・ `photo_scan` を持つ。** **GHOSTBLADE にあった Telegram・WhatsApp・iCloud・Wi-Fi・SMS の 収集機能は削除されている**（Habr） ——**本記録はこれを「諜報の道具から窃取の道具へ」の証拠と読む**
    根拠: iVerify の分析（命令の一覧と痕跡ファイル）および Habr の公開情報分析（対象ウォレット10種・削除された収集機能）
  5. 5. C2通信推定
    **15秒ごとに `/beacon` へ POST を送り、応答に載る命令を実行する**（iVerify）。 **HTTP/1.0 で、iPhone Safari の User-Agent を固定で使う。** **`sleep` コマンドで間隔を変更できる。** **HTTPS を使うが証明書の厳密な検証を行っていない。** **エンドポイント: `/result`（結果）・`/a`（登録）・`/event`（生存通知）・ `/u`（アプリ一覧）・`/nb`（メモ）・`/p`（写真）・ `/war`（キーチェーンとウォレットのデータ）。** **`/p` には `------HqBound` という多部分境界が使われる。** **iVerify が挙げた C2 は `agdx53[.]cc` と `js.gotoiphone[.]com/ios18`。** **Habr は第3ビルドの C2 として `www.y21t8bcya6q9b7155a[.]cc` （2026年5月25日登録）を加えている**
    根拠: iVerify の分析（beacon 間隔・エンドポイント・User-Agent・多部分境界・C2 ドメイン）、Habr の公開情報分析（第3ビルドの C2）
  6. 6. 持ち出し推定
    **収集したデータを C2 のエンドポイントへ送る。** **キーチェーンとウォレットのデータは `/war`、 写真は `/p`、メモは `/nb`、アプリ一覧は `/u`、 命令の実行結果は `/result`**（iVerify）。 **送信は HTTP/1.0 の POST で、 HTTPS を使うが証明書の厳密な検証を行っていない。** **送信量・件数・持ち出された資産額はいずれも公表されていない**
    根拠: iVerify の分析（エンドポイントの用途と送信方式）

  • 配信ページに配信元を識別する channelcode パラメータがある ——どのディストリビューターが送ってきた訪問者かを数える仕組み。 これはインプラント側にもある（channel_code / source フィールド）

さらに、バージョンで配り分けています（Habr）。iOS 13〜17.2.1 の端末には Coruna（別の連鎖）、18.x には DarkSword が送られ、同分析はこの組み合わせを 「DarkCoruna」 と呼んでいます。これは「来た端末に合うものを出す」配信基盤の作りです（本記録の整理）。

目的も変わっています。元の DarkSword については、ウクライナの正規サイト（政府ドメインを含む）に隠された iframe からiPhone 利用者へ連鎖が送られる水飲み場攻撃として報じられていました（Lookout・iVerify の共同分析として伝えられたもの）。P7 の狙いは暗号資産です ——キーチェーンとウォレットのシードフレーズ・keystore。 同じ技術が、諜報から窃取へ移っています。

本記録の評価——流出したエクスプロイトキットの再利用は、防御側にとって「標的の広がり」を意味します。 国家級の作戦なら標的は選別されますが、アフィリエイト型の配信サービスは来た端末を無差別に侵害します。 「自組織は国家に狙われる立場ではない」という前提は、この移動によって無効になります。

一度ページを見ただけで SpringBoard 内に入り、キーチェーンを端末上で復号してからウォレットのシードを抜く被害規模・影響範囲出典 [1] [2]

技術者向けに、P7 の挙動を段で並べます（iVerify・Habr）。

(1) 到達中国語のオンライン賭博サイト・暗号資産ニュースページに隠された iframe。group.html → loader.js → rce_loader.js の連鎖で、iOS のバージョンに応じた段が選ばれます（Habr）。ブラウザの localStorage に鍵が書かれ、再悪用を防いでいます（lab_device_uuid・__ds_inflight_worker・__ds_skip_workers・_x_pe_done・_x_try・_x_ok）——同じ端末で何度も走らせないための仕組みで、iVerify は「安定性の改良」と位置づけています。

(2) 実行と注入 6件の CVE を連ね、最終的にインプラントが SpringBoard に注入されます。 SpringBoard が攻撃者の基盤との通信をすべて担います（iVerify）。永続化はしません——再起動まで動きます（Habr）。

(3) キーチェーンの復号（P7 の新しい点） securityd の AppleKeyStore サービスを復号の神託として使い、キーチェーンの項目を端末上で復号して JSON に書き出します（Habr）。元の GHOSTBLADE はキーチェーンのデータベースを複製して攻撃者のサーバーへ送っていました（iVerify）——P7 は端末上で復号してから送るため、送られる量が減り、攻撃者側での復号の手間も消えます（本記録の整理）。

(4) ウォレットの窃取 imToken・TokenPocket・Trust Wallet・Bitget・Phantom・Solflare・Uniswap・Tonhub・Bitpie・TronLink のコンテナを探します（Habr）。imToken の keystore は端末上で復号されます。 iVerify が名前を挙げているのは imToken のみで、wallet_scan は一般にインストール済みのウォレットを探すものとしています〈齟齬に記録〉。

(5) C2 15秒ごとの /beacon POST（HTTP/1.0、iPhone Safari の User-Agent を固定）。 応答に命令が載る双方向通信で、sleep で間隔を変えられます。 エンドポイントは /result（結果）・/a（登録）・/event（生存通知）・/u（アプリ一覧）・/nb（メモ）・/p（写真）・/war（キーチェーンとウォレットのデータ）（iVerify）。HTTPS は使うが証明書の厳密な検証をしていません。

(6) 命令 約17の処理（Habr）。ls・download・photos・apps・exec（インプラント内で JavaScript を実行）・disk_scan・memo_scan（Apple のメモ）・photo_scan・wallet_scan・wallet_extract（iVerify）、および約50のシェル風の下位命令を持つ execute_command（Habr）。

削った機能も記録に値します（Habr）。読み込みプログラムは GHOSTBLADE のものとバイト単位で同一で、TaskRop と MIG の回避のコードも変更されていません。 一方、データ収集の論理は書き直され、Telegram・WhatsApp・iCloud・Wi-Fi・SMS の収集機能は削除されています。 本記録の評価——これは「諜報の道具から窃取の道具へ」の最も分かりやすい証拠です。 メッセージアプリの中身は、金銭目的の攻撃者には要らない。

  • **「修正済みの CVE」を自組織の端末で未修正のまま放置していないか測る**
    **DarkSword が悪用する6件の CVE はいずれも修正済みである** （iOS 18.7.2・18.7.3・26.1・26.2・26.3）。 **P7 が成立しているのは未修正の端末が残っているからであり、 これは攻撃の巧妙さではなく更新の遅れの問題である** （本記録の評価）。 **GTIG の報告時点では3件がゼロデイだったが、 P7 の活動時点ではすべて既知である。**
    取るべき行動 **①MDM で iOS バージョンの分布を出し、 18.7.3 未満（および 26 系で 26.3 未満）の端末を一覧にする。** **②更新できない理由（業務アプリの互換性・端末の世代）を 端末ごとに記録する** ——**理由が分かれば代替策（隔離・ロックダウンモード）を選べる。** **③「ゼロデイだった脆弱性」を、 修正後も未修正端末のリスクとして追跡し続ける。**
  • **流出したエクスプロイトキットの再利用を、脅威情報の追跡に織り込む**
    **P7 の読み込みプログラムは 元の GHOSTBLADE のものとバイト単位で同一であり、 TaskRop と MIG の回避のコードも変更されていない**（Habr）。 **一方でデータ収集の論理は書き直され、 Telegram・WhatsApp・iCloud・Wi-Fi・SMS の収集機能は削除されている** ——**諜報の道具から窃取の道具へ変わった形である**（本記録の読み）。 **コードが同一でも運用者と目的が違う。**
    取るべき行動 **①検知規則を書くとき、 「コードの一致」で帰属を決めない** ——**規則は挙動に対して書き、帰属は別の欄に持つ。** **②既知のファミリの検知が当たったとき、 亜種の可能性を初動で排除しない。** **③本DBと同じ方針で、 共有ツール（流出したキット）を帰属の根拠にしない。**
