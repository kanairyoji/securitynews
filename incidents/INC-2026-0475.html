2026年10月12日、Elastic Security Labs は、Web3 のアクセラレータを装った組織 Apex（Apex Arena） の活動を REF8801 として公表しました。

端緒は1つの npm パッケージです。 Elastic の供給網監視ボットが Slack に通知を出し、@apexacc/cli の挙動が不審だと分かりました。よく見ると、このパッケージは公開された時点からすでに悪性でした ——既存パッケージの乗っ取り（supply chain compromise）ではありません。同じ日に、同じ公開者が SafeDep の既報のキャンペーンとつながっていることが分かり、その後ほどなく、同じ攻撃者が @apexacc/audit という別の悪性パッケージを公開しました。

組織の見せ方は入念です。

  • Apex Arena——暗号資産／Web3 の創業者向けの非公開ワークスペースと称する。
  • 200超のポートフォリオと1億2,400万ドル超の調達を標榜。
  • 提供物: スマートコントラクト／Web3 のセキュリティ監査（MCP 経由で配る「Apex Audit」一式）、創業者と投資担当の直接連絡、求職中の人材ディレクトリ、Apex Score というスタートアップ評点。
  • 偽のレビューを並べて、会社や製品を調べた人に正当に見せる。
  • シンガポールの TOKEN2049 など、実際の会場に現れて信用を作る（Elastic は公表前に主催者へ通報しました）。
  • 無償の Claude と Gemini のクレジットを配ると持ちかける。

配られたものは2系統です。

  1. 情報窃取型マルウェアとバックドア ——macOS 向け CloudSyncD と、Windows 向けの独自の情報窃取型マルウェア（窃取データを ZIP にして Telegram 経由で送出）。
  2. 正規のコーディングエージェントの再梱包 ——オープンソースの「Oh My Pi」をほぼそのまま使う。 Apex Copilot v1.6.1 と Oh My Pi v16.3.6 を比べると、同じ場所にある1,363ファイルのうち1,351が内容ハッシュまで完全一致しました。足されているのは、攻撃者のサーバからコマンドを取ってきて実行する起動処理と、OpenRouter 名義のモデル通信を Apex の基盤へ迂回させる処理、そして攻撃者が管理する MCP サーバの登録です。 本物として動く機能が、足された処理を隠します。

本記録がこの事案を残す最大の理由は、監査ツールのほうです。

@apexacc/audit が公開した18のツールハンドラは、すべて嘘を返します（Elastic の検証）。
- audit_full_contract は実行していない Slither の解析結果を称する。
- audit_honeypot は常に「NOT A HONEYPOT」と報告する。
- audit_token_risk は乱数で 55 から 94 の評点を出し、判定は SAFE か WARN にしかならない。

別の試験では、Elastic が「REF8801 Synthetic Notes」という架空のプロジェクトを @apexacc/cli の遠隔採点（apex_score）に投げたところ、5つの分類すべてに同じ 51/100 を返し、「AI採点機は利用できない」と報告しました。 Elastic はこれを「おそらく仮の値」と判断し、主張された障害は検証できないとしています。

つまり、これは2段構えの被害です（本記録の評価）。①端末が侵害される。 ②「監査した」という記録が残る。 ②のほうが長く効きます。 スマートコントラクトの監査は、投資家と利用者に見せる根拠として使われます。 検査をしていない「問題なし」は、脆弱性を残したまま安心を配った状態です。

帰属について。 コミット履歴にロシア語のコードコメントがありますが、Elastic は「それだけでは国籍も主体も立たない」と明記しています（本記録もこの留保を維持します）。

「検証」経路は共通のサーバを使います。 両プロジェクトの起動処理はhxxps://vrf.apexaccs[.]org/api/v1/vrf に POST し、サーバが選んだ exec・args・cmd の各欄を受け取ります。

Windows: 起動処理が直接 {"p":"win32"} を POST し、応答からコマンド行を組み立てます（例: powershell.exe -nop -EncodedCommand <cmd>）。これを %TEMP%\_apex_run.ps1（audit 側は _audit_run.ps1）に書き、同じ一時ディレクトリに VBScript の起動役（_apex_run.vbs / _audit_run.vbs）も書きます。 VBScript は WScript.Shell.Run でpowershell -NoProfile -ExecutionPolicy Bypass -File … を起動します。 その先は wscript.exe → PowerShell → drop.ps1 → bludness.exe → install.exe / exegis.exe → updater_loader.exe → プロセス内シェルコード →ネイティブの情報窃取型マルウェア → ZIP → Telegram です。 途中には Python のローダ（UAC 迂回）、仮想環境の検査、Golang のローダ（AMSI と ETW の改ざんを試みる）が入ります。 Windows 固有のコードは、実行ポリシーとセキュリティ制御の変更も試みます。

macOS: 起動処理が Rust 製の補助（apex-verify-darwin / apex-audit-verify-darwin）を呼び、補助が curl で POST（{"p":"darwin"}）してサーバが選んだコマンドを起動します。インストーラのスクリプト → package.tar.gz → インストーラ → CloudSyncD → ホスト登録／タスク取得、という流れです。

本記録が注目する点を2つ書きます（本記録の評価）。

①コマンドはサーバが選びます。 固定されていません。つまり、解析時に取れた挙動が、別の時点・別の標的で取れる挙動と同じとは限りません。 検体の静的解析で「何をするマルウェアか」を確定できない構造です。

②入口は npm install でも npx でもなく、「インストールしたコマンドを使ったとき」です。 Elastic は bin エントリが呼ばれたときに動くと記述しています。 インストール時のフックだけを監視していると見落とします。

    取るべき行動 **①フォークや再梱包されたパッケージを使うときは、 上流との差分を取る**（ファイル一覧とハッシュの比較で足りる。 Elastic も同じ方法を使っている）。 **②差分のうち、起動処理・ネットワークの宛先・ プラグイン／MCP の登録に関わる箇所を優先して読む。** **③差分が小さいことを安全の根拠にしない** ——**本件の悪性は3か所に集まっていた。**
  • **「動かなかったから安全」と判定しない**
    **本件の Windows の窃取部は、 `.cobra` という目印ファイルを確認して 存在すれば実行を抑止できる**（Elastic）。 **連鎖には仮想環境の検査（anti-VM）も含まれる。** **解析環境の回避にも、特定の環境の除外にも使える仕組みである** （本記録の評価）。
    取るべき行動 **①検体の動的解析で何も起きない場合、 「環境の条件で抑止された可能性」を記録に残す。** **②静的解析で、環境を見て分岐する処理 （ファイルの存在確認・ハードウェア情報・ プロセス名の照合）を探す。** **③サンドボックスの偽装（実機に見せる設定）を 標準の手順に入れる。**
  • **開発端末に長期有効な鍵とウォレットを置かない**
    **本件の窃取対象は、ブラウザのデータ （Chrome の App-Bound Encryption の鍵を含む）、 AI クライアントの設定ファイル、ウォレット、ファイルである** （Elastic）。 **送出は ZIP を Telegram 経由。** **端末が侵害された時点で、そこにあるものは全部取られる** （本記録の主張） ——**「Chrome の App-Bound Encryption の鍵」が 挙がっていることは、ブラウザ側の保護強化を 前提に作られていることを示す。**
    取るべき行動 **①開発端末上の長期有効な資格情報を洗い出す （SSH 鍵・クラウドの長期キー・APIトークン・ ウォレットのファイル）。** **②短期の資格情報へ置き換える** （発行の仕組みが必要なので、置き換えは段階的に）。 **③置き換えられないもの（ウォレット・署名鍵）は 別端末またはハードウェアに分離する。**
  • **配布元の削除を「対処済み」と数えない**
    **本件では、npm のセキュリティチームが @apexfdn/apex を削除した 約11時間後に、同じドロッパーが @copilot-mcp/apex として 別のスコープで再公開されている**（SafeDep の記述。piyolog 経由）。 **同日中に20版超が公開された。** **パッケージ名・ドメインでの遮断は、 相手が名前を変えるだけで無効になる**（本記録の主張） ——**npm の経路では配布元が3回入れ替わっており （arenapex[.]cloud → cloudmain365duo[.]top → fdn4apex[.]com）、 同じことが名前空間でも起きている。**
    取るべき行動 **①悪性パッケージの対処を「名前の遮断」で終わらせず、 公開者（スコープ・発行アカウント）と 振る舞い（postinstall での外部取得・osascript による認証要求・ GitHub リリースからの実行ファイル取得）で検知する規則を書く。** **②自社の記録を、削除前の版が入っていないかで洗う** ——**削除後に遮断しても、入れてしまった端末は残る。** **③OSV・ossf/malicious-packages のような悪性パッケージの 登録簿を、脆弱性情報と同じ経路で取り込む** （本件は MAL-2026-12314 として登録されている）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 開発者が自分の判断で npm パッケージ・MCP サーバ・AI コーディングエージェントを導入できる（導入の判断に人の手順が無い）
システム構成□ AI エージェントの設定（モデルのエンドポイント・MCP サーバの登録先・API キーの置き場）が構成管理の対象に入っていない
運用・監視□ 導入しているセキュリティツールについて、「わざと脆弱な対象を食わせて見つけるかを確かめた」ことがない
データの保持□ 開発端末に長期有効な鍵・ウォレット・APIトークンが置かれている
体制・契約□ ツール提供元・取引先の評価を、ウェブサイトの充実度・レビュー・出展実績で判断している
運用・監視□ npm の監視がインストール時のフック（preinstall／postinstall）だけを対象にしている
認証・認可□ 端末管理・EDR／MDR／MDM の導入時に「どの管理テナントに参加させるか」を審査する手順が無い
体制・契約□ 社外のイベント・取引先・無償提供で配られたソフトウェアを、現場の判断で導入できる
