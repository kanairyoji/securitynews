「GitLab は、特定の条件下で、正規表現の検証が不十分であったために、未認証の利用者が CI/CD 設定中の細工された正規表現を介してGitLab サーバ上で任意のコードを実行できた問題を修正した。」

弱点の種類は整数オーバーフローで、場所は CI/CD の正規表現コンパイラです。これはプロジェクトのパイプライン設定ファイル（.gitlab-ci.yml 等）に書かれた正規表現を解析・コンパイル・評価する部品です（出典4）。rules:if や only/except のパターン照合に使われる種類の処理にあたります。

ここが本件の勘所です。パイプライン設定は「コードではなく設定」として扱われ、レビューの対象からも、権限設計の検討からも外れがちな場所です。ところがその設定ファイルの一行が、サーバ側のコンパイラを壊して任意コード実行に到達したことになります（本記録の整理）。

CVSS 10.0 の内訳も、この性質を映しています。 PR:N（権限不要）・UI:N（利用者操作不要）・S:C（スコープ変更あり）。S:C は「脆弱な部品の権限境界を越えて影響が及ぶ」ことを意味し、CI/CD ランナーやサーバのプロセス権限で任意コードが動く状況と整合します。

ただし「未認証でどう投入するのか」は公表されていません〈未確定事項に記録〉。GitLab の文面は「特定の条件下で」としか言っておらず、公開プロジェクトのマージリクエスト経由なのか、特定機能を有効にしている場合なのかを読者は判断できません。 したがって「自分のインスタンスは条件に当たらないから後回し」という判断は、現時点では根拠を持ちません（本記録の評価）。

修正版の番号が、GitLab は19.3.5・報道と2つの CERT は19.3.4——上げても直らない取り違えが起きうる再発防止出典 [1] [2] [3] [4]

本記録が原本で確認した事実を並べます。

GitLab 自身（出典1）——リリースの題名は 「GitLab Critical Patch Release: 19.4.2, 19.3.5, 19.2.8」。CVE-2026-97229 の影響版は 「19.2 から 19.2.8 未満、19.3 から 19.3.5 未満、19.4 から 19.4.2 未満のすべての版」。ページ本文に現れる「19.3.5」は33か所、「19.3.4」は1か所（本記録がページを取得して数えた）。

BleepingComputer（出典4）——「19.3 before 19.3.4」。CERT-EU（出典2）——「19.4.2, 19.3.4 and 19.2.8 を公開」「before 19.3.4」。CERT-FR（出典3）——「19.3.x versions antérieures à 19.3.4」。

3者が揃って 19.3.4 と書いています。 実務上の意味は明確です——19.3 系を運用していて、報道か CERT の勧告だけを見て19.3.4 へ上げた組織は、GitLab の記述に従えば依然として脆弱なままです（本記録の評価）。

なぜこうなったかは推測できますが、断定はしません。リリース直前に 19.3 系の版番号が繰り上がった（19.3.4 の公開を取り消して 19.3.5 を出した等）と考えれば、3者が同じ誤りを共有していることと、GitLab のページに 19.3.4 が1か所だけ残っていることの両方が説明できます。ただし GitLab は改訂の経緯を公表していません〈齟齬に記録〉。

読者が取るべき行動は1つです。 版番号は必ずベンダーのリリースページで確認する。 CERT の勧告は「上げるべきかの判断」には使えますが、「どの版に上げるか」の確認には一次資料を見る必要があります（本記録の結論）。

悪用の報告は無いが、GitLab は「悪用されるまでの時間が短い」実績を持つ製品である概観出典 [1] [4] [5]

現時点で悪用の報告はありません。 GitLab の公表に記述は無く、CERT-EU・CERT-FR も触れていません。本記録が確認した 2026年10月8日版の CISA KEV（1,739件）にも収載されていません ——もっともこのカタログ版はパッチ公開より前なので、反証にはなりません（T8）。

一方で、同じ製品の直近の履歴は重く読むべきです（出典4・5）。

  • 2026年9月: 最高深刻度 CVE-2026-85706（未認証で資格情報等を読み出せる。弱点はコミット API のパストラバーサルと認証強制の欠落）を修正。
  • 2026年9月11日: CISA が KEV へ収載。是正期限は2026年9月14日——3日（本記録が KEV 原データで確認）。KEV の通常の期限は3週間であり、3日は「すでに実害が出ている」場合に用いられる長さです（本記録の整理）。
  • 2026年1月: 高深刻度の2要素認証迂回（CVE-2026-0723）を修正。
  • 通算: CISA は2021年11月以降、攻撃に悪用された GitLab の脆弱性を5件挙げており、うち1件はランサムウェア集団に悪用された（出典4）。

本記録の評価——「悪用の報告が無い」を待機の理由にできる製品ではありません。自己管理の GitLab は、ソースコードと CI/CD の資格情報（クラウドの鍵・レジストリの認証情報・署名鍵）が集まる場所です。1台の侵害が供給網の侵害に直結する位置にあり、優先度は「CVSS 10.0」よりむしろ「何が置いてあるか」で決まります。

本命以外の23件にも、CI/CD の権限境界を崩すものが混じっている被害規模・影響範囲出典 [1] [2]

CVSS 10.0 に目を奪われると、同時に直った23件を見落とします。 CERT-EU が抜き出しているのは次の3つです（出典2）。

  • CVE-2026-92883（CVSS 8.7） ——構文強調の出力における HTML 属性の無害化不備による XSS。認証済み利用者が細工したリポジトリを置くと、それを閲覧した他利用者のブラウザで任意の JavaScript が動く（出典1）。影響版の起点が 19.1 であり、本命より広い。
  • CVE-2026-16301（CVSS 8.5） ——下流パイプライン生成の認可の不備。開発者（Developer）権限の利用者が、権限無しに保護ブランチでパイプラインを実行できた。
  • キャッシュ汚染（CVSS 8.2） ——マージリクエストのキャッシュキー構成の不備により、保護された CI/CD 変数が露出しうる。

この3つは、いずれも「CI/CD の権限境界」を崩すものです（本記録の整理）。保護ブランチ、保護変数、レビュー済みコードといった前提の上に本番デプロイを載せている組織では、内部の悪意ある利用者・侵害されたアカウント1つの影響範囲が、設計上の想定より広がります。

残りの CVE も認可の不備（Incorrect Authorization）が多数を占めます ——GraphQL のノートウィジェット、ワークアイテム階層、パッケージレジストリ、カスタムロール、細粒度の個人アクセストークン、リポジトリ取り込みの SSRF など（本記録がリリースページ本文から確認）。「認可の網羅的な見直しが一度に入った」リリースだと読めます（本記録の評価）。

【10月13日】「完全な未認証」ではなかった——ただし自己登録を許していれば同じことで、緊急度は下がらない原因・手口出典 [1] [6]

第三者の再現が、ベンダーが書かなかった1行を埋めました。

2026年10月13日、Rapid7 が未パッチの公式 GitLab CE イメージ（19.4.1・Linux amd64・ASLR 有効）で任意コード実行の連鎖を再現したと公表しました。同じ入力は、パッチ済みの 19.4.2 CE イメージでは実行されませんでした（出典6）。

重要なのは、成功したことよりも、成功させるために何が必要だったかです。

「ベンダーが付与した CVSS スコアは悪用が完全に未認証であることを示しているが、エクスプロイトを再現する過程で、攻撃者は契機を引く前に悪性の CI/CD 設定をリポジトリへ仕込む手段を持たなければならないことが分かった。新規の利用者が自己登録してプロジェクトを作れる GitLab インスタンスでは、この制約は無くなる。」（原文英語。本記録の訳。出典6）

具体的な前提は2つです。①悪性の .gitlab-ci.yml、②UTF-8 文字を含むリポジトリパス——この両方を、公開プロジェクトのブランチへコミットできること。Rapid7 は「その機能が許可されている自己管理インスタンスでは、ごく普通のアカウントが公開プロジェクトを作ることでこの前提を満たせる」としています。

機構——検証を通ってから、符号化が変わるときに壊れる

細工した正規表現は、まず US-ASCII のコンパクトな表現としてコンパイルされ、GitLab の正規表現検証を通過します。それが特殊な形の有効な UTF-8 リポジトリパスに対して評価されると、検証が終わった後で Ruby の Onigmo 正規表現エンジンが新しい符号化向けに再コンパイルします。このときコンパイラのプログラムサイズ計算で整数オーバーフローが起き、不正な正規表現命令が生成されます。制御フローの完全性が失われ、Ruby プロセス内で攻撃者が制御するOnigmo VM の操作が実行され、GitLab の git ユーザとしてOS コマンドが走ります（出典6）。

検証の順序が、そのまま弱点になっています（本記録の整理）—— 入力を検査した後に、検査済みの前提（符号化）が変わる経路があった。入力検証の話として一般化できる形です。

それでも緊急度は下がらない、という読み

「未認証ではない」と聞くと緊急度を下げたくなりますが、本記録は下げません（本記録の判断）。理由は3つです。

  1. 前提が消える構成が普通に存在します。 自己登録と公開プロジェクト作成を許していれば、攻撃者は「ごく普通のアカウント」で足ります。自組織がどちらかを知らないまま緊急度を下げるのは、賭けです。
  2. 前提は内部の利用者も満たせます。 社内限定のインスタンスでも、書き込み権限を持つ1アカウントの侵害で成立します—— 「外部に出していないから大丈夫」にはなりません。
  3. Rapid7 自身が、通常のパッチ周期の外で上げることを推奨しています（出典6）。

一方で、緩和策の輪郭はこれで初めて描けるようになりました（本記録の評価）。Rapid7 が挙げるのは①公開プロジェクトへの匿名アクセスの制限②信頼できない利用者による公開プロジェクトの作成・書き込みの禁止で、同社は「これらの統制は、実証された配送経路だけに対処するものであり、脆弱な正規表現コンパイラそれ自体を修復するものではない」と明記しています（原文英語。本記録の訳）。

ベンダーが「特定の条件下で」としか書かないあいだ、前提条件は第三者の再現報告からしか読めません（本記録の指摘）—— 本記録が10月14日に GitLab のリリースページを再取得した時点でも、この点は追記されていませんでした（T12）。
