INC-2026-0477Bricksforgeの未認証RCEが即日悪用

WordPress の商用プラグイン Bricksforge に未認証の任意ファイルアップロード （CVE-2026-85097・CVSS 10.0）が見つかり、Patchstack の観測では **2026年10月7日 21時47分 UTC——修正版の公開と同じ日**から実際の悪用が始まった。 63個の IP から自動化された試行が届き、44 IP が同一ペイロードを数秒内に投げる群と、 3 IP が同一の一時ファイルに対し PHP 拡張子と符号化の25通りを試す群の2つに分かれた。 一方でベンダーの変更履歴に 3.1.8.10 の項目は無く、 同種の修正は 4.0.1（10月8日）に記載されている

脆弱性脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月7日（Patchstack のデータベース掲載） 最終更新: 2026年10月13日

修正版が出た日に、もう攻撃が来ていました。

CVE-2026-85097。WordPress の商用プラグイン Bricksforge に、未認証で任意のファイルをアップロードでき、そのまま PHP として実行させられる不備がありました。CVSS は 10.0（Patchstack・The Hacker News の表記。SecurityWeek は 9.8 と書いており、ここは食い違っています）。影響は 3.1.8.9 以下、修正は 3.1.8.10。

Patchstack の観測では、最初の悪用は2026年10月7日 21時47分17秒 UTC。同社のデータベース掲載も同じ10月7日です。届いた試行は 63個の IP から。内訳が攻撃の性格を語っています—— ①44 IP が同一のペイロードを数秒のうちに56回投げる群②3 IP が同一の一時ファイルに対して PHP の拡張子と符号化の25通りを試す群。 Patchstack は「どちらも回転プロキシか分散インフラ越しの自動化を示すが、それだけで単一の攻撃者に帰属させるものではない」と明記しています（原文英語。本記録の訳）。

手口は3手です。 未認証で nonce を発行するエンドポイントから nonce を取る → GIF と PHP の両方として成立するファイルを上げて MIME 検査を通す →フォーム送信で「書き込み先」を .php に指定する。検証されていなかったのは、この最後の「書き込み先」でした。

そしてもう1つ。 ベンダーの変更履歴には 3.1.8.10 の項目がありません。Pro Forms のファイルアップロードの修正は 4.0.1（10月8日）に書かれており、「アップロード欄が無いサイトも対象」とされています。版の系列が2本あるとき、変更履歴と脆弱性情報のどちらを見るかで「直したつもり」が生まれます。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の悪用が観測されている事案である**（出典1）。 **本記録が記録するのは、Patchstack が示した成立経路と、 同社のテレメトリに現れた自動化された試行の形である。** **侵害後の活動（ウェブシェル設置後に何をしたか）は公表されていない** 〈未確定事項に記録〉ため、段は initial-access・execution・impact の3つにとどめる。

  1. 1. 初期侵入確認済
    **未認証で nonce を取得する。** **`bricksforge_regenerate_nonce` という AJAX のエンドポイントが 認証を要求せずに nonce を発行していたため、 外部の攻撃者がフォーム送信の手続きを完結できた**（出典1）。
    根拠: Patchstack の解析記事における手口の記述（出典1）
  2. 2. 実行確認済
    **GIF と PHP の両方として成立する多重形式ファイルを上げ、 MIME 検査を通して一時ディレクトリに置く。** **続いてフォーム送信の `temporaryFileUploads` パラメータで、 ファイルのパスにその画像を、`url` フィールドに `.php` で終わる宛先を指定する。** **`url` が検証されていないため、プラグインは一時ファイルの内容を 指定された PHP の場所へ書き出す**（出典1・3）。
    根拠: **Patchstack の解析（該当コードは `includes/elements/pro-forms/actions/init.php` と `base.php`）、 および観測された約95%の要求が「サーバ側パスに `.gif`／`.png`、 宛先 URL に PHP 関連拡張子」の組み合わせであったこと**（出典1）
  3. 3. 影響（暗号化・破壊・改ざん）確認済
    **書き出された PHP ファイルがサーバで実行される** —— **未認証の遠隔コード実行が成立し、サイトの完全な制御に至りうる** （出典1・2）。 **侵害後に何が設置されたかは公表されていない**（本記録の注記）。
    根拠: Patchstack・SecurityWeek による影響の記述（出典1・2）

この事案で下された判断
  • **Patchstack は、手口を再現可能な粒度で公開した** —— **未認証 nonce のエンドポイント名、`temporaryFileUploads` の `url` が未検証であること、 GIF/PHP 多重形式で MIME 検査を通す手順、該当コードのファイル名、 攻撃元 IP とそのネットワーク（AbuseIPDB の件数つき）まで記載している**（出典1）。
    理由は公表されていない
    トレードオフ: **防御側は検知条件と事後確認の観点を即日得られる。** **同時に、まだ更新していないサイトに対する攻撃の再現も容易になる** —— **約6,000件の利用サイトのうち更新が遅れたものは、 この公開によって危険が増す側に回る**（本記録の整理）。
  • **Patchstack は自社の緩衝規則（RapidMitigate）を 「最初の攻撃が届く前に稼働させていた」と記述している**（出典1）。 **すなわち、修正版の適用を待たずに防御側の遮断を先行させる方式を採った。**
    理由は公表されていない
    トレードオフ: **緩衝規則は同社の顧客にしか効かない。** **約6,000件の利用サイトの大半は、自力で更新するほかに手段が無い** （本記録の整理）。 **また、仮想パッチが効いていると利用者が更新を後回しにする誘因も生まれる。**

検証されていなかったのは「アップロード先」だった——nonce・MIME 検査・書き込み先の3つが別々に緩かった原因・手口出典 [1] [3]

Patchstack の説明にもとづき、成立の順に並べます（出典1・3）。

第1手: nonce を未認証で手に入れる。 bricksforge_regenerate_nonce という AJAX のエンドポイントが、認証を要求せずに nonce を発行していました。 WordPress の nonce は「正規の画面から来た操作であること」を示す仕組みであり、これが未認証で取れると、以降の手続きが外部から完結します。

第2手: MIME 検査を通る多重形式ファイルを上げる。 GIF と PHP の両方として成立するファイル（polyglot）を送ると、アップロード時の MIME 判定は「画像である」と判断し、ファイルは一時ディレクトリに置かれます。

第3手: 書き込み先を .php に指定する。フォーム送信（temporaryFileUploads パラメータ）では、ファイルのパスに先ほどの画像を、url フィールドに PHP 拡張子で終わる宛先を指定します。 url は検証されていませんでした。プラグインは一時ファイルの内容を url の場所へ書き出し、サーバはそれを PHP として実行します（該当コードはincludes/elements/pro-forms/actions/init.php と base.php）。

到達するエンドポイントは POST /wp-json/bricksforge/v1/form_submit。 観測では、1件だけ /wp-admin/admin-ajax.php のbricksforge_form_submit アクション経由のものがありました（出典1）。

本記録の整理——この3つはどれも単独なら「よくある緩さ」です。 nonce の未認証発行は「nonce は認証ではない」で済まされ、MIME 検査は「拡張子より厳しい」と信じられ、書き込み先の検証は「内部で組み立てる値だから」と省かれます。緩さが3つ重なった結果が、未認証の任意コード実行（CVSS 10.0）です。

公表と悪用が同じ日に起きた——「公表から悪用まで」の猶予は実質ゼロだった発覚の端緒出典 [1] [2] [3]

時系列を並べると、猶予が無かったことが分かります（出典1・3）。

  • 2026年10月7日: Patchstack が脆弱性データベースに掲載（修正版 3.1.8.10）。
  • 2026年10月7日 21時47分17秒 UTC: 最初の悪用の試行を観測。
  • 2026年10月8日: Patchstack が解析記事を公開。
  • 2026年10月8日: ベンダーが 4.0.1 を公開（Pro Forms のアップロードの修正）。

Patchstack は「緩衝規則（RapidMitigate）は最初の攻撃が届く前に稼働していた」と書いています（出典1）——自社の防御については先行できたという主張です。 ただしこれは同社の顧客に限った話であり、約6,000件の利用サイトの多くには当てはまりません（本記録の注記）。

観測された試行の形も、自動化の度合いを示しています。

  • 固有 IP は63個。上位6 IP で全試行の約46%。
  • 群1: 44 IP が同一ペイロードを数秒のうちに56回。
  • 群2: 3 IP が同一の一時ファイルに PHP 拡張子と符号化の25通り。
  • 約95%の要求が「サーバ側パスに .gif／.png、宛先 URL に PHP」の組み合わせ。

Patchstack の留保をそのまま引きます（原文英語。本記録の訳）—— 「どちらの型も、回転プロキシまたは分散インフラ越しの自動化された悪用を示す。それ自体で、この活動を単一の攻撃者に帰属させるものではない。」

本記録の評価——群1と群2の違いは読む価値があります。群1は配布された既成の攻撃コードが一斉に走った形、群2は検査の抜け道を手探りしている形に見えます。後者が存在することは、最初の修正が不完全だった場合にすぐ次の変種が来ることを意味します（断定はしません）。

WordPress プラグインの脆弱性で「パッチが出てから動く」運用は、この時間感覚では間に合いません。 自動更新を有効にしているか、WAF の緩衝規則が入っているか、この2つが実質的な防御線になります（本記録の結論）。

版の系列が2本あり、変更履歴に 3.1.8.10 が無い——「直したつもり」が生まれる構造再発防止出典 [3] [4]

本記録がベンダーの公式変更履歴を確認した結果です（出典4）。

  • 3.1.8.10 の項目は存在しない。
  • 3.1.8.9（2026年8月28日）の項目はあるが、内容はメールデザイナのテンプレート描画のセキュリティ強化で、本件とは別件。
  • 4.0.0（2026年9月17日）で 4.x 系が始まる。
  • 4.0.1（2026年10月8日）に「Pro Forms のファイルアップロードのセキュリティ問題を修正した」とあり、「Pro Forms が有効なすべてのサイトが対象であり、フォームにアップロード欄が無くても影響を受ける」と注意書きが付く。

一方 Patchstack のデータベースは「3.1.8.9 以下が影響・3.1.8.10 で修正」と記載します（出典3）。

本記録の読み——3.x 系を使い続ける利用者向けに個別パッチ 3.1.8.10 が出され、変更履歴には反映されなかった、と読むのが自然です。 ただしベンダーの説明は無いため、断定はしません〈齟齬に記録〉。

実務上の意味は2つあります（本記録の整理）。

①どの版へ上げるかを変更履歴だけで判断すると詰まる。変更履歴に 3.1.8.10 が無いので、「該当する修正は 4.0.1」と読んでメジャー更新に踏み切れず、放置する流れになります。脆弱性情報（CVE・Patchstack）と変更履歴の両方を見る必要があります。

②「アップロード欄が無いから無関係」は成り立たない。ベンダー自身が 4.0.1 の記載で明確に否定しています。フォームの設定を根拠に除外判断をしてはいけません。

Patchstack の「KEV」印は CISA の KEV ではない——悪用の確認元を取り違えないこと帰属出典 [3] [6]

本記録が確認した事実を2つ並べます。

  • Patchstack のデータベース掲載には「Known to be exploited!（KEV）」の印が付いている（出典3）。
  • CISA の KEV カタログ（2026年10月8日版・収載1,739件）にCVE-2026-85097 は入っていない（本記録がカタログの JSON 原本を取得して確認。出典6）。

これは矛盾ではありません。 Patchstack の印は同社自身のテレメトリに基づく「悪用されている」の表示であり、CISA KEV は米政府の収載判断です（本記録の整理）。

本記録の評価——取り違えると2方向に間違えます。 ①CISA KEV に無いことを根拠に「まだ悪用されていない」と判断する ——実際には10月7日から試行が届いています。 ②Patchstack の「KEV」印を CISA の収載と読み、連邦機関の是正期限のような外形的な強制力があると考える ——ありません。

悪用の有無は、情報源ごとに「誰が何を見て言っているか」を分けて読む必要があります（本記録の結論）。WordPress プラグインの脆弱性は CISA KEV に載りにくい領域であり（連邦機関の資産に入りにくいため）、KEV を唯一の悪用判定に使うと、この領域の緊急度を過小評価します。

  • **サイト構築に使っている商用プラグインを資産として台帳に載せる**
    **本件は無料プラグインではなく商用アドオンで起きた。** **商用は「購入した部品」として調達側の管理に入りやすく、 情報システム部門の脆弱性管理の対象から漏れる**（本記録の評価）。 **影響は未認証の遠隔コード実行であり、 コーポレートサイト1本の侵害が自社ブランドの改ざん・顧客への配布経路になる** （出典1・2）。

    取るべき行動 **①主要サイトでプラグインの自動更新を有効にする（検証環境を持つなら 本番の自動更新と検証の併用を決める）。** **②WAF か managed WordPress の仮想パッチを導入し、 更新までの時間を埋める。** **③「更新が遅れてもよいサイト」を明示的に決め、 そのサイトは外部公開の必要性そのものを見直す**（本記録の推奨）。
  • **悪用の判定を CISA KEV だけに依存しない**
    **本件は Patchstack のデータベースでは「悪用されている」と表示される一方、 2026年10月8日版の CISA KEV には収載されていない** （本記録がカタログ原本で確認。齟齬3）。 **WordPress プラグインは連邦機関の資産に入りにくく、 KEV に載りにくい領域である**（本記録の評価）。
    取るべき行動 **①脆弱性の緊急度判定に使う情報源を複数書き出し、 領域ごとにどれが有効かを決める（WordPress 領域は Patchstack・Wordfence 等）。** **②判定の記録に「誰の観測による悪用か」を残す欄を作る。** **③KEV に無いことを待機の理由として使わない旨を手順に明記する**（本記録の推奨）。
  • **ベンダーの変更履歴と脆弱性情報が食い違う前提で、更新の完了基準を決める**
    **Patchstack は「3.1.8.10 で修正」とするが、 ベンダーの公式変更履歴に 3.1.8.10 の項目は無く、 Pro Forms のアップロードの修正は 4.0.1（2026年10月8日）に書かれている** （齟齬2。出典3・4）。 **変更履歴だけを見るとメジャー更新（4.x）が必要に見え、 判断が止まる**（本記録の評価）。
    取るべき行動 **①更新の完了基準を「版番号が修正版以上であること」で定義し、 記録に実際の版番号を残す。** **②食い違いがある場合は、プラグインのファイル（`readme.txt` 等）で 導入済みの版を実測して確認する。** **③3.x 系を使い続ける方針なら、ベンダーに個別パッチの位置づけを問い合わせる** （本記録の推奨）。
セキュリティ技術者への示唆
  • **Bricksforge を 3.1.8.10 以上（4.x 系なら 4.0.1 以上）へ上げる**
    **影響版は 3.1.8.9 以下、修正版は 3.1.8.10**（出典3）。 **4.x 系では 4.0.1 に Pro Forms のファイルアップロードの修正が記載されている** （出典4）。 **ベンダーは「Pro Forms が有効なすべてのサイトが対象であり、 フォームにアップロード欄が無くても影響を受ける」と明記している**（出典4）。
    取るべき行動 **①管理画面でプラグインの版を確認する。** **②3.x 系を使い続けるなら 3.1.8.10 以上、 4.x 系へ移るなら 4.0.1 以上へ上げる。** **③「アップロード欄を使っていない」を除外理由にしない**（本記録の推奨）。
  • **「画像パス＋PHP 宛先」の組み合わせを、ログの検索条件として1回走らせる**
    **Patchstack の観測では、捕捉した要求の約95%が サーバ側パスに `.gif`／`.png`、宛先 URL に PHP 関連の拡張子を 組み合わせたものだった**（出典1）。 **これは誤検知が少なく、かつ事後確認にも使える条件である**（本記録の整理）。
    取るべき行動 **①2026年10月7日以降のアクセスログから `/wp-json/bricksforge/v1/form_submit` と `admin-ajax.php?action=bricksforge_form_submit` への POST を抽出する。** **②要求本体を保存している場合は、`.gif`／`.png` と `.php` が同時に現れるものを探す。** **③該当があれば、次の項目の事後確認に進む**（本記録の推奨）。
  • **`wp-content/uploads` 配下と一時ディレクトリに `.php` が無いかを確認する**
    **成立すると、一時ファイルの内容が攻撃者の指定した PHP のパスへ書き出される** （出典1）。 **正常な運用でアップロード先に `.php` が置かれることはない**（本記録の整理）。 **侵害後に何が設置されたかは公表されていないため、 痕跡の確認は自サイトで行うほかない**（本記録の注記）。
    取るべき行動 **①`find wp-content/uploads -name '*.php'` 相当の確認を行う。** **②2026年10月7日以降に作成・更新された PHP ファイルを一覧する。** **③該当があれば、更新だけで済ませず、 設置物の削除と資格情報（管理者・DB・API キー）の更新まで行う**（本記録の推奨）。
  • **アップロード先のディレクトリで PHP の実行を止める**
    **本件の成立は「書き込める」と「実行される」の2段で、 後者はサーバ側の設定で切れる**（本記録の整理）。 **プラグインの不備は防げないが、 書き出された PHP が実行されなければ影響は大きく下がる**（本記録の評価）。
    取るべき行動 **①`wp-content/uploads` 配下で PHP の実行を禁止する （nginx なら location での `.php` 拒否、Apache なら該当ディレクトリの設定）。** **②設定後にサイトの機能（ギャラリー・フォームの添付）を1回通して確認する。** **③同じ設定をステージング環境にも入れ、構成管理に残す**（本記録の推奨）。
  • **未認証で nonce を発行するエンドポイントの有無を、自作・委託開発のプラグインで点検する**
    **本件の第1手は `bricksforge_regenerate_nonce` が未認証で nonce を出していたこと** （出典1）。 **nonce は「正規の画面から来た操作」を示すだけで認証ではないが、 未認証で発行すると後続の手続きが外部から完結する**（本記録の整理）。
    取るべき行動 **①自社で作った／委託して作ったプラグイン・テーマの `wp_ajax_nopriv_` 系の登録を一覧し、何を許しているかを確認する。** **②REST ルートの `permission_callback` が `__return_true` になっている箇所を洗い出す。** **③ファイルの書き込み先を外部入力から決めている箇所を探し、 許可された拡張子と配置先の白名簿に置き換える**（本記録の推奨）。
