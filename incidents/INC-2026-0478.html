5か月前に直せた穴が、いまも入口として使われています。

CVE-2026-0257 ——PAN-OS の GlobalProtect と Prisma Access における認証バイパス。Palo Alto Networks が自ら発見し、2026年5月13日に公表しました。ベンダーの評価は CVSS v4.0 で 7.8（HIGH）ですが、緊急度は最上位（HIGHEST）とされ、米 NVD は 9.1（critical）を付けています。

CISA の動きが、この脆弱性の性格を語っています。 2026年5月29日に KEV へ収載、是正期限は6月1日——3日。 ランサムウェアキャンペーンでの利用は「Known（確認済み）」（本記録が KEV の JSON 原本で確認）。

それから4か月あまり。ReliaQuest は2026年10月9日、Qilin と Settra のランサムウェア運用が本脆弱性を狙い続けており、不正な VPN セッションを確立して内部ネットワークへの初期侵入を得ていると公表しました（Infosecurity Magazine の報道による）。伴って観測されたのは Cobalt Strike・BloodHound・SharpHound —— 攻撃用ツールとしてありふれた組み合わせです。同社は今後3か月も悪用の試行が続く可能性が「highly likely（可能性が高い）」と評価しています。

そして、この事案で最も実務に効く一文がこれです（原文英語。本記録の訳）——

「この access は組織自身の VPN を経由して来るため、悪性の活動が正規のリモート勤務に似て見え、資格情報の窃取・横展開・データ持ち出し・ランサムウェアの展開が始まるまで検知されない可能性がある。」

さらに——「パッチの適用だけでは、是正前に確立された access を取り除けない可能性がある。」 だから ReliaQuest は「適用後に稼働中の GlobalProtect セッションを全て終了させよ」と指示しています。 直したつもりの組織が、まだ入られている可能性を見る話です。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**段は initial-access から impact までを、ReliaQuest が示した観測の範囲で記録する** （出典2）。 **記述の粒度は粗い**——**同社が公表したのは「何を使ったか」のツール名と 「何が起こりうるか」の列挙であり、各段の具体的な手順は公表されていない** （本記録の注記）。 **本記録は、公表されていない段を埋めない。**

  1. 1. 初期侵入推定
    **CVE-2026-0257 を悪用して認証を回避し、不正な GlobalProtect の VPN セッションを確立する**（出典2・3）。 **攻撃者は正規の社員と同じ経路で内部ネットワークに現れる** —— **マルウェアの送り込みもフィッシングも不要である**（本記録の整理）。 **【2026年10月19日の追記】Unit 42 はこの段を 「本脆弱性で企業ネットワークへの初期の足場を得たうえで、 多要素認証（MFA）の統制を迂回して VPN セッションを確立する」と記述した** （原文英語。本記録の訳。出典4）—— **MFA を入れている組織でも、この入口は塞がらない。**
    根拠: ReliaQuest の2026年10月9日の勧告（出典2 を介して）、CISA KEV の記述（出典3）
  2. 2. 内部探索推定
    **BloodHound・SharpHound を展開し、Active Directory の構成 （権限の経路・管理者グループ・到達可能な資産）を調べる**（出典2）。
    根拠: ReliaQuest が観測した攻撃用ツールの列挙（出典2 を介して）
  3. 3. 横展開推定
    **Cobalt Strike を展開し、横展開と常時接続の足場を作る**（出典2）。 **具体的な手順（どのプロトコルで、どの資格情報を使って動いたか）は 公表されていない**（本記録の注記）。
    根拠: ReliaQuest が観測した攻撃用ツールの列挙（出典2 を介して）
  4. 4. 検知回避確認済
    **【2026年10月19日に判明】侵害した VPN ゲートウェイから vCenter 管理アプライアンスへ移り、ESXi ハイパーバイザ上の セキュリティ統制（execInstalledOnly）を無効化する**（出典4）。 **Unit 42 はこれを「本脆弱性の悪用に続く TTP の最も大きな変化」とし、 「仮想化層への直接のピボット」と呼んでいる**（原文英語。本記録の訳）。
    根拠: Unit 42 の脅威ブリーフ（2026年10月19日更新。自社のインシデント対応に基づく記述。出典4）
  5. 5. 認証情報アクセス確認済
    **【2026年10月19日に判明】独自のツールを使い、 ドメインコントローラの仮想ディスク（VMDK）に対して オフラインで資格情報のダンプを行う**（出典4）。 **Unit 42 はこれを「ゲスト内の EDR とセキュリティ統制を迂回して ドメイン全体の資格情報を得る、高度に洗練された手法」と評している** （原文英語。本記録の訳）。
    根拠: Unit 42 の脅威ブリーフ（2026年10月19日更新。出典4）
  6. 6. 影響（暗号化・破壊・改ざん）推定
    **資格情報の窃取・横展開・データの持ち出し・ランサムウェアの展開に至る** （出典2 の記述。ReliaQuest は「〜が始まるまで検知されない可能性がある」 という形でこれらを列挙している）。 **本記録は、具体的な被害事例を確認していない**（本記録の注記）。 **【2026年10月19日の追記】Unit 42 は、攻撃者がこの初期侵入を 他の攻撃ツールと連鎖させて影響を最大化していると記述した** —— **具体例として Veeam のバックアップ基盤を狙う CVE-2023-27532 を挙げている** （出典4）。 **本記録の整理**——**復旧の拠り所であるバックアップ基盤が 同じ侵入の射程に入っている。** **「暗号化されても戻せる」という前提は、 バックアップ側の脆弱性が未適用なら成立しない。**
    根拠: ReliaQuest の勧告の記述（出典2 を介して）、CISA KEV の「ランサムウェア利用 Known」（出典3）

この事案で下された判断
  • **Palo Alto Networks は、脆弱性の公表時に 「緩和策を適用していない未適用機器に対する限定的な悪用の試行を認識している」 と記載し、同時に設定による緩和策（認証オーバーライド cookie 用の専用証明書・ 当該オプションの無効化）を提示した**（出典1）。 **一方、悪用の規模・攻撃者・被害の内容は公表していない。**
    理由は公表されていない
    トレードオフ: **緩和策を同時に出したことで、停止計画が組めない組織にも 当日取れる手段が与えられた（設定変更は再起動を伴わない）。** **一方で「限定的な悪用」という表現は、 優先度判定を CVSS（7.8）と組み合わせて読むと 「次の定期適用でよい」という判断を招きうる**（本記録の整理）。
  • **ReliaQuest は、パッチ適用後に稼働中の GlobalProtect セッションを 全て終了させることを指示した** —— **「パッチの適用だけでは、是正前に確立された access を 取り除けない可能性がある」という判断にもとづく**（原文英語。本記録の訳。出典2）。
    トレードオフ: **全セッションの終了は、リモート勤務中の全利用者の接続を切る。** **業務時間中に実施すれば業務が止まり、 夜間に実施すれば再接続時の問い合わせが翌営業日に集中する**（本記録の評価）。 **それでも、実施しなければ「適用済みだが侵害継続」の状態が残る。**

入口が自社の VPN であるため、侵入が正規のリモート勤務と区別できない原因・手口出典 [2] [3]

本件の核心は、脆弱性の珍しさではありません。入口の場所です。

ReliaQuest の記述をそのまま引きます（原文英語。本記録の訳。出典2）——

「この access は組織自身の VPN を経由して来るため、悪性の活動が正規のリモート勤務に似て見え、資格情報の窃取・横展開・データ持ち出し・ランサムウェアの展開が始まるまで検知されない可能性がある。」

認証バイパスで成立するのは「不正な VPN セッション」です（出典2・3）。つまり攻撃者は、マルウェアを送り込む必要も、フィッシングで資格情報を取る必要もなく、正規の社員と同じ経路・同じ見た目で内部ネットワークに現れます。

CISA の記述も同じ性格を指しています（原文英語。本記録の訳。出典3）—— 「攻撃者がセキュリティ上の制限を回避して、不正な VPN 接続を確立できる。」

ここから導かれる検知の難しさは2段あります（本記録の整理）。

①入口では区別できない。 VPN の認証ログには「成功」が残るだけです。ユーザ名・端末・時刻が正規のパターンに収まっていれば、異常として上がりません。

②内部に入ってからの活動も、管理業務に似ている。 ReliaQuest が観測したツールは Cobalt Strike・BloodHound・SharpHound。後者2つは Active Directory の構成を調べるツールで、正規のセキュリティ診断でも使われます。

ReliaQuest が示した具体的な検知の糸口は1つだけ、しかし実用的です——「'kali' のようなホスト名を使っているセッションを含む、想定外の接続を調査せよ。」 攻撃者が診断用 OS の既定のホスト名をそのまま使っている事例がある、という意味です（本記録の読み）。本記録の評価——これは「雑な攻撃者を捕まえる」条件であり、本筋の検知にはなりません。 本筋は、VPN セッションの属性（接続元の国・ASN・端末の証明書・接続時間帯）の基準線を持つことです。

「適用しても残る」——パッチの後に全セッションを終了させよという指示の意味再発防止出典 [1] [2]

この事案で最も実務に効く一文は、脆弱性の説明ではなく対処の注意書きにあります（原文英語。本記録の訳。出典2）——

「パッチの適用だけでは、是正前に確立された access を取り除けない可能性がある。」

だから ReliaQuest の指示は4つで、その3番目が重要です（出典2）。

  1. 影響を受ける構成を直ちに更新する。
  2. 不要であれば認証オーバーライドの cookie を無効化する。
  3. パッチ適用後に、稼働中の GlobalProtect セッションを全て終了させる。
  4. 想定外の接続（'kali' のようなホスト名のセッションを含む）を調査する。

ベンダー側の緩和策も、同じ設定を指しています（出典1）—— ①認証オーバーライドの cookie 用に専用の証明書を使い、ポータル／ゲートウェイや他機能と使い回さない。②ポータルとゲートウェイで、認証オーバーライドの cookie の生成・受理の両オプションを無効化する。

本記録の整理——ここには脆弱性管理の一般的な穴があります。 多くの組織の脆弱性対応は「版を上げた」で完了します。 しかし認証に関わる脆弱性では、 ①発行済みのセッション・cookie・トークンが残り、 ②窃取済みの資格情報は版を上げても失効しません。

つまり「適用済み」は「安全」を意味しません。 本件に限らず、認証バイパス・セッション偽造の脆弱性では、適用と同時に ①全セッションの無効化 ②関係する証明書・鍵の再発行③適用前の期間のログの遡り調査、の3点を手順に含める必要があります（本記録の結論）。

ベンダー 7.8・NVD 9.1・KEV 期限3日——3つの数字が違う方向を指している被害規模・影響範囲出典 [1] [2] [3]

同じ脆弱性に、3つの評価が付いています。

  • Palo Alto Networks: CVSS v4.0 で 7.8（HIGH）。ただし緊急度は HIGHEST（出典1）。
  • 米 NVD: 9.1（critical）（出典2 の記述）。
  • CISA KEV: 2026年5月29日収載・是正期限6月1日（3日）・ランサムウェア利用「Known」（本記録が原データで確認。出典3）。

本記録の評価——社内の優先度判定を「CVSS 9.0 以上を最優先」のようなしきい値で回している組織では、本件はベンダー値（7.8）で入ってくると最優先の枠に入りません。 一方、同じ脆弱性に CISA は3日の期限を課しています。 KEV の標準的な期限は3週間であり、3日は「すでに実害が出ている」場合の長さです。

判断を分ける材料は、スコアではなく次の3つです（本記録の整理）。

  • 悪用の事実があるか（KEV 収載・ランサムウェア利用「Known」）。
  • 到達可能な位置にあるか（VPN のポータル／ゲートウェイは外部公開が前提）。
  • 侵害後の到達範囲（VPN セッションは内部ネットワークへの直結）。

この3つは、いずれも CVSS の数字には現れません。 CVSS は「脆弱性の属性」を測る尺度であり、「自組織における緊急度」を測る尺度ではないためです。

そして実際の経過が、どちらの評価が現実に近かったかを示しています。 公表から152日、悪用の報告は5月（Rapid7）・6月（Unit 42）・7月（Arctic Wolf）・10月（ReliaQuest）と切れ目なく続いています（出典2）。

ランサムウェア集団にとって、VPN の既知欠陥は「5か月使える資産」になっている帰属出典 [2] [3]

ReliaQuest が挙げた集団は Qilin と Settra です（出典2）。本記録は Settra を他の資料で確認できていません〈未確定事項に記録〉。Qilin については、CISA の KEV が本脆弱性に「ランサムウェアキャンペーンでの利用: Known」を記録しており、集団名は記載されていませんが、悪用の事実は政府機関の判定として裏付けられています（出典3）。

観測されたツールは Cobalt Strike・BloodHound・SharpHound（出典2）。新規性はありません。 これは評価にあたって重要な点です——攻撃側が投じているのは「新しい技術」ではなく「まだ直っていない入口の探索」です（本記録の評価）。

ReliaQuest の予測——今後3か月にわたる継続の可能性が「高い（highly likely）」（出典2）。

本記録の整理——この構図は、脆弱性の寿命を長く見積もるべき理由を示しています。 ①ランサムウェア運用はアフィリエイト（実行役）に手順を配る構造を持ち、一度組み込まれた侵入手口は長く使い回される。 ②VPN 機器は更新に計画停止を要するため、適用が遅れやすい。 ③「限定的な悪用」としてベンダーが公表した段階と、ランサムウェアの量産的な初期侵入に使われる段階では、組織が受ける脅威の大きさが違う。

したがって「公表直後に適用できなかった脆弱性」は、数か月後にむしろ危険になります（本記録の評価）。半年前の未適用リストを見直す定期作業が、新規公表の追跡と同じだけの価値を持ちます。

侵入後の本筋が仮想化層に移った——ドメインコントローラではなく、その入れ物が狙われる原因・手口出典 [4]

Unit 42 が2026年10月19日の更新で「悪用後の TTP の最も大きな変化」と呼んだのは、仮想化層への直接のピボットです（出典4。原文英語。本記録の訳）。

記述された経路はこうです。

  1. 侵害した VPN ゲートウェイから
  2. vCenter 管理アプライアンスへ移る
  3. ESXi ハイパーバイザのセキュリティ統制（execInstalledOnly）を無効化する
  4. 独自のツールでドメインコントローラの仮想ディスク（VMDK）に対し、オフラインで資格情報をダンプする

なぜこれが効くのか（本記録の整理）。4の時点で、ドメインコントローラの OS は何も気づいていません。 LSASS のメモリは読まれず、DCSync のレプリケーション要求も飛びません。読まれているのは「稼働中の OS」ではなく「その OS が入っているファイル」です。ゲスト内の EDR は、原理的にここを見られません。 Unit 42 の表現では「ゲスト内の EDR とセキュリティ統制を迂回し、ドメイン全体の資格情報を得る、高度に洗練された手法」です。

さらに Veeam のバックアップ基盤を狙う CVE-2023-27532 との連鎖も観測されています（出典4）。復旧の拠り所と、認証の拠り所が、同じ侵入の射程に入っている形です。

日本の読者にとっての意味（本記録の評価）。国内では仮想化基盤の集約が進んでおり、ドメインコントローラ・ファイルサーバ・バックアップサーバが同じ ESXi クラスタの同じデータストアに同居している構成は珍しくありません。この構成では、vCenter の管理者権限1つが、ドメイン全体の資格情報と等価になります。守る側が置くべき線は、ゲスト OS の中ではなく、データストアと vCenter の権限の側にあります。

脆弱性とは別に、設定で管理インタフェースを露出させている組織がある（10月20日の追加指針）対策・注意喚起出典 [1] [2] [4]

2026年10月20日、Unit 42 は同じ脅威ブリーフをもう一度更新しました。内容は脆弱性ではなく構成の話です（出典4）。

「Lunar Peak」と呼ぶキャンペーンのインシデント対応のなかで、組織が繰り返し犯している誤設定を見つけた—— GlobalProtect（GP）のプロファイルを、管理インタフェースのHTTP／HTTPS サービスに割り当てている構成です。

これが何を起こすか。 管理インタフェースが、特定のポート——とくに 4443 と 3879——でインターネットに露出します。 Unit 42 は「多くの場合、管理者が気づかないまま（without administrators' knowledge）」と書いています（原文英語。本記録の訳）。

Unit 42 が示した確認と是正（出典4）。

  • 確認: 外部のブラウザから、自組織の管理 IP アドレスのポート 4443 と 3879 へ、帯域外（社外の回線）で HTTPS 接続を試みる。応答があれば露出している。
  • 是正: Interface Management プロファイルの設定を見直し、最小権限の原則に沿ってアクセス元を制限する。

本記録の評価——この指針の価値は「その場でできる」点にあります。パッチ適用には計画停止の調整が要りますが、外部から2つのポートを叩いて応答を見るだけなら、今日できます。そして露出していた場合、本脆弱性を直しても露出は残ります ——別個の問題だからです。

あわせて実施すべきこと（本記録の整理。出典1・2・4 を踏まえる）。

  1. ポート 4443／3879 の外部到達性を確認する（上記）
  2. CVE-2026-0257 の修正版を適用する（系列ごとのホットフィックス水準はベンダー勧告で確認）
  3. 適用後、稼働中の GlobalProtect セッションを全て終了させる（是正前に確立された access は適用では消えない）
  4. Unit 42 が公開した痕跡で GlobalProtect のログを遡る（IP 9件、想定外のホスト名・MAC アドレス、PoC 由来の固定値）
  5. vCenter／ESXi 側のログを確認する（vCenter への対話的ログイン、execInstalledOnly の変更、ドメインコントローラの VMDK に対するスナップショット・クローン操作）
  6. Veeam など backup 基盤の CVE-2023-27532 の適用状況を確認する

4〜6は「直した後」に行う作業です。 本件で繰り返し出てくる構図は、適用の完了と安全の確認が別物だということです。

判断評価評価の根拠と留保
**Palo Alto Networks は、脆弱性の公表時に 「緩和策を適用していない未適用機器に対する限定的な悪用の試行を認識している」 と記載し、同時に設定による緩和策（認証オーバーライド cookie 用の専用証明書・ 当該オプションの無効化）を提示した**（出典1）。 **一方、悪用の規模・攻撃者・被害の内容は公表していない。** 部分的に機能**本記録の判断である。** **機能した点**——**①自社発見の脆弱性を、悪用の試行を認識した段階で公表した。** **②設定による緩和策を具体的に示した（証明書の使い回しの禁止・ オプションの無効化）。** **③影響・非影響の製品（Cloud NGFW・Panorama は非該当）を明記し、 無駄な作業を防いだ。** **不十分な点**——**①CVSS 7.8（HIGH）と NVD 9.1（critical）の差が解消されないまま 5か月が経過しており、優先度判定を誤らせる材料が残っている。** **②「パッチ適用後にセッションを終了させる」という最も重要な注意は、 ベンダーの勧告ではなく第三者（ReliaQuest）の指示として出ている**〈本記録の評価〉。
**ReliaQuest は、パッチ適用後に稼働中の GlobalProtect セッションを 全て終了させることを指示した** —— **「パッチの適用だけでは、是正前に確立された access を 取り除けない可能性がある」という判断にもとづく**（原文英語。本記録の訳。出典2）。 機能した**本記録の判断である。** **対処の順序（更新 → 不要な cookie の無効化 → 全セッション終了 → 想定外接続の調査）が、 「残存する access」を前提に組まれている点を評価する。** **とくに4番目（想定外の接続の調査）は、 すでに侵害されている組織に対して唯一の発見手段を与えている。** **留保**——**本記録は ReliaQuest の勧告原文を参照できておらず、 評価は報道を介した記述にもとづく**〈齟齬3〉。
CISO・経営層への示唆
  • **「適用済み」を安全の証拠にしない——認証系の脆弱性では残存 access を前提に動く**
    **ReliaQuest の警告**——**「パッチの適用だけでは、 是正前に確立された access を取り除けない可能性がある」** （原文英語。本記録の訳。出典2）。 **認証バイパスでは、版を上げても発行済みのセッションと 窃取済みの資格情報は失効しない**（本記録の整理）。
    取るべき行動 **①脆弱性対応の手順に「認証・セッションに関わる脆弱性の場合」の分岐を作り、 ②全セッションの無効化 ③関係する証明書・鍵の再発行 ④公表日から適用日までの期間のログの遡り調査、を必須工程として書き込む。** **⑤過去1年で適用した認証系の脆弱性について、 これらを実施したかを1回確認する**（本記録の推奨）。
  • **半年前の未適用リストを定期的に見直す——古い脆弱性のほうが危険になる**
    **本件は公表から152日が経っても初期侵入経路として使われている** （出典2。本記録が算出）。 **悪用の報告は5月・6月・7月・10月と切れ目なく続いている。** **ランサムウェア運用はアフィリエイトに手順を配る構造を持つため、 一度組み込まれた侵入手口は長く使い回される**（本記録の評価）。
    取るべき行動 **①未適用のまま残っている脆弱性の一覧を、公表日の古い順に並べて出す （新しい順に見る運用が多いため、意図的に逆順にする）。** **②そのうち KEV 収載済みのものを最優先に引き上げる。** **③四半期に1回、この逆順レビューを定例にする**（本記録の推奨）。
  • **優先度判定を CVSS の数字ではなく「悪用の事実＋到達可能性＋到達範囲」で行う**
    **同じ脆弱性に、ベンダーは 7.8（HIGH）、NVD は 9.1（critical）を付け、 CISA は3日の是正期限を課した**（出典1・2・3）。 **「CVSS 9.0 以上を最優先」という社内基準では、 ベンダー値で取り込むと本件は最優先の枠に入らない**（本記録の評価）。
    取るべき行動 **①優先度判定の基準に「KEV 収載」「外部から到達可能」 「侵害時に内部ネットワークへ直結する」の3つを独立した引き上げ条件として加える。** **②どの情報源の CVSS を採るかを明記する（ベンダー値か NVD 値か）。** **③基準の変更後、直近1年の判定結果を再評価し、 見落としていた案件があるかを確認する**（本記録の推奨）。
  • **VPN を「境界の装置」ではなく「侵害時に内部へ直結する経路」として評価する**
    **本件の攻撃は、組織自身の VPN を経由するため 正規のリモート勤務と区別できない**（出典2）。 **VPN の先が平坦なネットワークであれば、 1つの不正セッションがそのまま内部全体への到達になる**（本記録の評価）。
    取るべき行動 **①VPN 利用者が到達できる宛先の一覧を出す （「社内全部」になっていないかを確認する）。** **②業務に必要な範囲へ絞る計画を立て、 まず管理系プロトコル（SMB・WinRM・RDP）への到達を制限する。** **③VPN 経由の端末を「社内端末」として監視から外していないかを確認する** （本記録の推奨）。
セキュリティ技術者への示唆
  • **PAN-OS／Prisma Access を、系列ごとの修正版へ上げる（版の読み方に注意する）**
    **影響は PAN-OS 10.2／11.1／11.2／12.1 系と Prisma Access 10.2.0／11.2.0 で、 修正は系列ごとに複数のホットフィックス（例: 11.1.4-h33・11.2.4-h17・ 10.2.7-h34・12.1.4-h6 など）として提供されている**（出典1）。 **報道の「PAN-OS 10.2.0・11.1.0・11.2.0・12.1.0 が影響」という記述は 系列の表記であり、単一の版ではない**（齟齬2）。
    取るべき行動 **①`show system info` で現行の版とホットフィックス番号を確認する。** **②ベンダー勧告の該当系列の修正版一覧と突き合わせる （自系列の修正版が複数あり、どれ以上なら良いかが系列ごとに違う）。** **③Prisma Access はベンダーが計画に沿って更新するため、 自組織の更新予定を確認する**（本記録の推奨）。
  • **認証オーバーライドの cookie を無効化し、専用証明書に分ける**
    **ベンダーの緩和策は2つ** —— **①認証オーバーライドの cookie 用に専用の証明書を使い、 ポータル／ゲートウェイや他機能と使い回さない ②ポータルとゲートウェイで、当該 cookie の生成・受理の両オプションを無効化する** （出典1）。 **ReliaQuest も「不要であれば無効化せよ」と指示している**（出典2）。
    取るべき行動 **①GlobalProtect のポータル／ゲートウェイの設定で 認証オーバーライドの cookie が有効かを確認する。** **②業務上不要なら無効化する（再認証の頻度が上がる影響を事前に周知する）。** **③必要な場合は専用証明書へ分け、他用途との共用を解消する**（本記録の推奨）。
  • **パッチ適用後に全ての GlobalProtect セッションを終了させる**
    **ReliaQuest の指示であり、理由は 「パッチの適用だけでは是正前に確立された access を取り除けない可能性がある」** （出典2）。 **適用で終わりにすると、不正セッションが生き残る**（本記録の整理）。
    取るべき行動 **①適用の作業計画に「全セッションの強制終了」を工程として入れる。** **②実施時刻を決め、利用者へ再接続の案内を事前に出す。** **③終了後の再接続の一覧を取得し、想定外の接続元が無いかを確認する** （本記録の推奨）。
  • **VPN セッションの属性の基準線を作り、想定外の接続を抽出する**
    **ReliaQuest の具体的な糸口は「'kali' のようなホスト名を使うセッションを含む 想定外の接続を調査せよ」である**（出典2）。 **ただしこれは既定のホスト名をそのまま使う雑な攻撃者を捕まえる条件であり、 本筋は属性の基準線である**（本記録の評価）。
    取るべき行動 **①直近90日の GlobalProtect の接続ログから、 接続元の国・ASN・ホスト名・端末証明書の有無・接続時間帯の分布を出す。** **②分布の外（未知の国・データセンター ASN・証明書なし・ 同一利用者の多地点同時接続）を抽出する。** **③ホスト名に 'kali' 等の診断用 OS の既定名が含まれるものを即時に調べる** （本記録の推奨）。
  • **AD 列挙（BloodHound／SharpHound）の検知を1つ用意する**
    **ReliaQuest が観測した攻撃用ツールは Cobalt Strike・BloodHound・SharpHound である**（出典2）。 **AD 列挙は短時間に大量の LDAP 問い合わせを生み、 日常の業務端末では起きない形である**（本記録の整理）。
    取るべき行動 **①ドメインコントローラへの LDAP 問い合わせ件数を端末単位で集計し、 上位の端末が何をしているかを確認する（基準線を作る）。** **②非管理端末・VPN 経由端末からの AD 列挙を警告に回す。** **③既存の EDR で BloodHound／SharpHound の検知規則が 有効になっているかを確認する**（本記録の推奨）。
  • **仮想化基盤（vCenter／ESXi）のログを SIEM に入れる—— ゲスト内 EDR では原理的に見えない段がある**
    **Unit 42 が2026年10月19日に記述した手口は、 侵害した VPN ゲートウェイから vCenter へ移り、 ESXi の `execInstalledOnly` を無効化したうえで、 ドメインコントローラの VMDK に対してオフラインで資格情報をダンプするものである** （出典4）。 **読まれるのは稼働中の OS ではなく「その OS が入っているファイル」なので、 ドメインコントローラ側には LSASS アクセスも DCSync も記録されない** （本記録の整理）。
    取るべき行動 **①vCenter の対話的ログイン（とくに VPN の払い出し帯域からのもの）を SIEM に取り込み、管理者アカウントの接続元の基準線を作る。** **②ESXi の詳細設定 `VMkernel.Boot.execInstalledOnly` の変更と SSH／シェルの有効化を警告に回す。** **③ドメインコントローラの VMDK に対するスナップショット作成・クローン・ データストアブラウザ経由のダウンロードを警告に回す。** **④これらのログが現在どこにも集まっていない場合、 「集めていない」こと自体を課題として登録する**（本記録の推奨）。
  • **ドメインコントローラを他の仮想マシンと同じ箱に置かない—— 狙われたのは DC ではなく DC の入れ物だった**
    **攻撃者が触ったのはドメインコントローラの仮想ディスクであり、 到達の経路は vCenter の管理権限である**（出典4）。 **ドメインコントローラ・ファイルサーバ・バックアップサーバが 同じ ESXi クラスタの同じデータストアに同居している構成では、 vCenter の管理者権限1つがドメイン全体の資格情報と等価になる** （本記録の評価。国内で一般的な集約構成を踏まえる）。
    取るべき行動 **①ドメインコントローラの仮想マシンとデータストアを分離し、 専用の vCenter 権限ロールでのみ操作できるようにする。** **②仮想化基盤の管理者と Active Directory の管理者を別アカウントにし、 片方の侵害がもう片方に直結しないようにする。** **③Veeam など backup 基盤の既知脆弱性（本件では CVE-2023-27532）の 適用状況を確認する——復旧の拠り所が同じ射程に入っている**（本記録の推奨）。
  • **管理インタフェースがポート 4443／3879 で外に出ていないかを、今日その場で確認する**
    **Unit 42 は2026年10月20日、IR の現場で繰り返し見た誤設定として、 GlobalProtect のプロファイルを管理インタフェースの HTTP／HTTPS サービスに 割り当てている構成を挙げた。これによりポート 4443 と 3879 が 「管理者が気づかないまま」インターネットに露出する** （原文英語。本記録の訳。出典4）。 **これは CVE-2026-0257 とは別個の問題であり、 脆弱性を直しても露出は残る**（本記録の整理）。
    取るべき行動 **①社外の回線から、自組織の管理 IP アドレスの ポート 4443 と 3879 へ HTTPS 接続を試みる（Unit 42 が示した確認手順）。** **②応答があれば Interface Management プロファイルを見直し、 最小権限の原則でアクセス元を制限する。** **③同じ確認を、PAN-OS 以外の境界機器の管理面についても行う**（本記録の推奨）。
