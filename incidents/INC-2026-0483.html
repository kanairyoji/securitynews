INC-2026-0483Canonicalが年内2度目のDDoS

Canonical の公開ウェブサイトが2026年10月8日から持続的な分散型サービス妨害（DDoS）攻撃を受け、 ubuntu.com・canonical.com・開発者ポータル・そしてセキュリティ勧告のページと Ubuntu Security API までが4時間余り停止した。 同年2度目の DDoS で、犯行を主張した組織は現れていない。 Launchpad・Snap Store・パッケージのリポジトリとミラーは稼働を続け、 更新の配布そのものは止まらなかった

システム障害脅威・攻撃キャンペーン続報が止まり調査も完了有名事象として記録（日本と直接の関係は薄い）容量・リソース枯渇
初報: 2026年10月8日15時09分 UTC（Canonical の Ubuntu Discourse 告知） 最終更新: 2026年10月13日

Canonical は2026年10月8日15時09分（UTC）、Ubuntu Discourse の告知に「Canonical のウェブサイトは持続的な分散型サービス妨害攻撃を受けている。当社のチームは事象の解消に全力で当たっている。最新の状況は当社のステータスページを参照してほしい。一部のサービスは断続的に利用できない可能性がある」と投稿した（原文英語。本記録の訳。出典1）。

影響を受けたのは公開ウェブサイトである（出典2・3）。ubuntu.com、canonical.com、Ubuntu のブログ、開発者ポータル、assets.ubuntu.com、academy.canonical.com、そして jaas.ai・maas.io といった企業向け技術のサイト、さらに——本記録がこの事案で最も重要と考える点だが—— セキュリティ勧告のページと Ubuntu Security API、および Livepatch が一時的に停止した（出典2・3）。利用者は攻撃の最中、セキュリティ勧告を参照できず、再起動なしでカーネルにパッチを当てる仕組みも使えない状態になった。

一方で、配布の経路は生きていた（出典2・3）。Launchpad と Snap Store は事象の間も稼働を続け、ソフトウェアのリポジトリとミラーサーバ、ディスクイメージのサーバ、Ubuntu Single Sign-On も動いていた。 その結果、公開ウェブサイトが止まっている間も、利用者はパッケージの取得と更新の適用を続けられた（出典2）。

停止は4時間余りである。 Security Affairs は「全体の停止は4時間を少し超え、実際の混乱を生じさせた」と記し、OMG! Ubuntu は4時間12分と報じた（出典2・3）。Canonical 自身は停止時間を示していない〈齟齬に記録〉。翌10月9日11時40分（UTC）の更新投稿は「現時点で当社のチームは影響を受けたサービスの復旧作業を続けており、その大半はすでに利用可能になっている。ご辛抱とご理解に感謝する」と述べている（原文英語。本記録の訳。出典1）。

犯行を主張した組織は現れていない（出典2）。これは同年2度目の DDoS である。 前回はより大きな混乱を生み、Launchpad と Snap Store を停止させて一部の利用者が Ubuntu の更新を適用できない状態にした。 その際は The Islamic Cyber Resistance in Iraq（313 Team とも呼ばれる）というハクティビスト組織が犯行を主張し、Canonical は当該事象を「持続的で国境を越えた攻撃」と表現した（出典2）。今回の攻撃が同じ一連のものか、まったく無関係な別の攻撃者が便乗したのかは不明である（出典2 自身がそう記している）。

本記録の評価として、機能した点と不十分な点を分けます。

機能した点。 ①攻撃が進行中の段階で公表している。 原因を「DDoS 攻撃」と明示しており、「障害が発生しています」で濁していません。 ②告知の場を、落ちている可能性のある自社サイトではなくDiscourse とステータスページに置いています（本記録の評価）。これは構成として正しい——自社のウェブが落ちているときに自社のウェブで告知する作りだと、告知自体が届きません。

不十分な点。 ①具体のサービス名が1つも書かれていません。 「一部のサービスは断続的に利用できない可能性がある」だけです。 影響を受けたドメインの一覧は報道が整理したもので、Canonical の告知には無い（本記録が2026年10月13日に確認。T7）。②セキュリティ勧告のページと Security API、Livepatch が止まっていることへの言及がありません。 これは利用者にとって他のページとは意味が違う——脆弱性対応の判断材料が取れなくなるためです。 ③停止時間を示していません〈齟齬に記録〉。4時間12分という値は報道によるものです（出典3）。④更新の間隔が実際の復旧と合っていません。 停止は4時間余りで解消しているのに（出典2・3）、次の投稿は約20時間半後で、しかも「大半は利用可能になった」という表現です（本記録の算出。T3・T5）。

ベンダーのウェブが落ちると、脆弱性対応の判断が止まる評価・解釈

評価の節です。本記録の判断を含みます。 日本の読者に向けた実務上の論点を1つに絞って書きます。

この事案で止まったものの中に、Ubuntu Security API とセキュリティ勧告のページがありました（出典2）。

多くの組織の脆弱性管理は、次の形で組まれています（本記録の整理）。

  1. ベンダーの勧告（または API）から、自社の資産に当たる脆弱性を取る
  2. 深刻度と悪用の状況で優先順位を付ける
  3. パッチを適用する

今回止まったのは1だけで、3は動いていました。 これは一見すると軽い影響ですが、実務では次のことが起きます。

①自動化された処理が黙って失敗する。 勧告を定期的に取得して資産と突き合わせる仕組みを持っている組織では、API が応答しない間、突き合わせが成立しません。 失敗が警報として上がる作りになっていなければ、「脆弱性なし」と読める結果が出ます（本記録の評価）。これは本DBが別の文脈で繰り返し記録している形——測る道具が黙って 0 を返すと、問題が無いように見える——と同じです。

②緊急の判断ができなくなる。 重大な脆弱性の公表と DDoS が重なれば、「自社が影響を受けるか」を調べる手段が止まります。 本件でそれが起きたという報道はありませんが、構造としてはありうる組み合わせです（本記録の評価）。

③Livepatch が止まると、再起動なしの緊急適用ができない。 止まっている間は、従来の再起動を伴う適用に戻すか、待つかの選択になります。

本記録の整理——ここから出る示唆は「Canonical が悪い」ではありません。 脆弱性情報の取得経路を単一のベンダーのウェブに依存していると、そのベンダーが攻撃されたときに自社の脆弱性管理が止まるという依存の構造が見えた、という点です。 勧告は OVAL のデータ、ディストリビューションのメタデータ、NVD、ミラーなど複数の経路で取れます（本記録の評価）。取得が失敗したことを検知できるかも、併せて確認に値します。

今回の攻撃について、犯行を主張した組織は現れていません（出典2）。

    **Canonical は公開ウェブサイトが落ちている状況で、 告知を Ubuntu Discourse とステータスページに出している**（出典1）。 **本記録の評価**——**これは構成として正しい。** **自社のコーポレートサイトに「障害情報」を置く作りだと、 そのサイトが落ちたときに告知が届かない。** **同じ基盤・同じ DNS・同じ CDN に乗せている場合も同様である。**
    取るべき行動 **①自社の障害告知の掲示先が、本体のサービスと別の基盤に乗っているかを確認する （別ドメイン・別 CDN・別の権威 DNS が望ましい）。** **②SNS など第三者の基盤も併用の候補として用意する。** **③告知の掲示先を、平時から利用者・顧客に周知しておく**（本記録の推奨）。
  • **可用性の事案でも「止まったものの一覧」を当事者として出す**
    **Canonical の告知は「一部のサービスは断続的に利用できない可能性がある」 という記述にとどまり、具体のサービス名が無い** （本記録が2026年10月13日に原文を確認。出典1。T7）。 **影響を受けたドメインの一覧と停止時間（4時間12分）を整理したのは 報道である**（出典2・3）。 **本記録の評価**——**利用者は「自分が使っている機能は動くのか」を 知りたいのであり、「一部」では判断できない。** **とくに本件のように、止まったものの中に セキュリティ勧告の経路が含まれる場合は、 その一点を名指しで知らせる価値が高い。**
    取るべき行動 **①障害の告知のひな形に「影響を受けるもの／受けないもの」の 2列の表を入れる。** **②事後に停止時間（開始・終了の時刻）を記録として残す。** **③顧客が自社のログと突き合わせられる粒度（分単位）で出す**（本記録の推奨）。
  • **基盤を分けておくと、同じ攻撃でも落ちる範囲が変わる**
    **今回は Launchpad・Snap Store・リポジトリ・ミラー・ ディスクイメージのサーバ・Ubuntu SSO が稼働を続けた**（出典2）。 **同年1度目の攻撃では Launchpad と Snap Store も停止し、 一部の利用者が更新を適用できなかった**（出典2）。 **Security Affairs は「分散した基盤が被害の抑制に寄与した」と記している。** **本記録の留保**——**攻撃の規模が公表されていないため** 〈未確定事項に記録〉、 **範囲が狭かった原因が構成の変更か攻撃の小ささかは分からない**（本記録の評価）。
    取るべき行動 **①自社のサービスを「止まると事業が止まるもの」と 「止まっても事業は続くもの」に分類する。** **②両者が同じ基盤・同じ経路・同じ DNS を共有していないかを確認する。** **③共有している場合、分離の費用と、 分離しない場合に一緒に落ちる範囲を比較して判断する**（本記録の推奨）。
セキュリティ技術者への示唆
  • **脆弱性情報の取得が失敗したことを警報にする——黙って「0件」を返させない**
    **本件では Ubuntu Security API が一時的に停止した**（出典2）。 **本記録の評価**——**勧告を定期的に取得して自社の資産と突き合わせる処理では、 取得が失敗したときに「該当する脆弱性なし」と読める結果が出る作りになりやすい。** **これは可用性の障害が、静かに検査の失敗へ変わる形である。** **測る道具が黙って 0 を返すと、問題が無いように見える。**
    取るべき行動 **①脆弱性情報を取得する処理に、 「取得の成功」自体を検査する項目を入れる （HTTP の状態コード、件数が前回と比べて異常に少ないか、 最終成功時刻からの経過時間）。** **②失敗したときは「脆弱性なし」ではなく「判定不能」として扱い、 警報を上げる。** **③取得の記録（いつ・どこから・何件）を残し、 後から欠落の期間を確認できるようにする**（本記録の推奨）。
  • **勧告の取得先を複数持ち、片方が落ちても判定を続けられるようにする**
    **本件では勧告のページと API が止まった一方、 リポジトリとミラーは稼働していた**（出典2）。 **本記録の評価**——**Ubuntu の脆弱性情報は ベンダーの API 以外にも、OVAL のデータ、 配布のメタデータ、NVD など複数の経路で取れる。** **1つの経路に寄せていると、その経路の可用性が自社の判定の可用性になる。**
    取るべき行動 **①現在使っている取得経路を洗い出し、 同じホスト・同じドメインに集まっていないかを確認する。** **②代替の経路を1つ用意し、 平時から両方で取得して結果が一致することを確かめておく （障害時に初めて使う経路は動かない）。** **③取得したデータをローカルに保持し、 直近の版で判定を継続できるようにする**（本記録の推奨）。
  • **再起動なしのパッチ適用（Livepatch 等）が止まった場合の代替手順を決めておく**
    **本件では Livepatch が一時的に停止した**（出典2）。 **本記録の評価**——**Livepatch のような仕組みは 「再起動できない本番系に緊急のパッチを当てる」ために使われる。** **止まっている間は、従来の再起動を伴う適用に戻すか、待つかの選択になる。** **待つ判断をするなら、その間の代替の緩和（経路の遮断・機能の停止）が要る。**
    取るべき行動 **①Livepatch に依存しているホストを一覧化する。** **②各々について「再起動できる時間帯」と 「再起動せずに緩和する手段」を記録する。** **③提供の仕組みが止まったことを検知できるかを確認する （適用の成功が一定期間途切れたら警報にする）**（本記録の推奨）。
  • **障害の告知を読み取る側の仕組みも、ベンダーの可用性に依存していないかを見る**
    **Canonical は告知を Ubuntu Discourse とステータスページに出した**（出典1）。 **本記録の経験として記す**——**本記録が2026年10月13日に status.canonical.com を取得したが、事象の履歴を読み取れなかった** 〈齟齬に記録〉。 **本記録の評価**——**ステータスページは人が見る前提で作られており、 機械的に取得して自社の監視に取り込むには向かない形のものがある。**
    取るべき行動 **①依存している外部サービスについて、 障害情報を機械的に取れる経路（RSS・Atom・API・webhook）があるかを確認する。** **②あるものは自社の監視に取り込み、 無いものは「人が見に行く」手順として誰の担当かを決める。** **③自社が提供する側でもある場合、 利用者が機械的に取れる経路を用意する**（本記録の推奨）。
