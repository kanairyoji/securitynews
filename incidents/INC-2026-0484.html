INC-2026-0484AssetViewにSYSTEM権限昇格の脆弱性

2026年10月13日、JPCERT/CC と IPA が JVN#38664315 を公表し、 ハンモックの IT 資産管理製品 AssetView に **SYSTEM 権限を取得できる権限昇格の脆弱性** （CVE-2026-101020・CWE-732・CVSS 4.0 基本値 8.5）があると公開した。 **成立の前提は「管理コンソールまたはクライアントモジュールが動作する Windows に ログインできること」**——つまり**端末を使える一般利用者が SYSTEM になれる**。 回避策は無く、対処はパッチ適用か対策版へのアップデートのみ。 **AssetView Cloud＋ の対策版（Ver 2600.201.11）は公表より15日前の9月28日に出ている**

脆弱性初報のみ日本の組織が当事者設計・実装上の不備権限管理の不備
初報: 2026年10月13日（JVN#38664315 の公表。ハンモックの脆弱性情報ページも同日公開） 最終更新: 2026年10月13日

「端末にログインできる人は、SYSTEM になれる」——これが本件の結論です。

2026年10月13日、JPCERT/CC と IPA は JVN#38664315 を公表し、株式会社ハンモックの IT 資産管理製品 AssetView に権限昇格の脆弱性があると公開しました。CVE-2026-101020、CWE-732（重要なリソースに対する不適切なアクセス権の割り当て）、CVSS 4.0 基本値 8.5（CVSS 3.0 では 7.8）です。

JVN の記述は短く、そして実務上は重いものです。「当該製品の管理コンソールまたはクライアントモジュールが動作する Windows システムにログイン可能な攻撃者によって、SYSTEM 権限を取得される可能性があります」（出典2）。ハンモック側の説明では、SYSTEM 権限で動作するプログラムを一般ユーザー権限で置き換えられる状態であり、この脆弱性を緩和する回避策は無いとされています（出典1）。

AssetView は、管理対象の全端末にクライアントモジュールを入れて使う製品です（出典3）。したがって「攻撃者」として想定すべきは外部の侵入者だけではありません。貸与端末を使う従業員、共用端末を使う派遣社員や協力会社の担当者、あるいはフィッシングで1台の標準ユーザー権限を取った攻撃者が、そのまま SYSTEM へ上がれることを意味します。AssetView 自身が内部不正対策（PC 操作ログ・デバイス制御・Web フィルタリング）を担っている組織では、監視する側の仕組みが昇格の踏み台になります（本記録の評価）。

悪用の報告はありません（JVN とハンモックの公表にいずれも悪用の記述が無く、本記録が確認した範囲で PoC の公開も見つかっていません）。

ただし、対処には注意すべき点が2つあります。 第一に、AssetView Cloud＋ の対策版 Ver 2600.201.11 は、公表の15日前である2026年9月28日にリリースされています（出典1）。クラウド側の更新が先に進んでいた形であり、クライアントの更新が終わっているかは利用組織が自分で確認する必要があります。第二に、オンプレミスの AssetView と AssetView CLOUD の資材は「保守契約ユーザー専用サイト」（要ログイン）にしか置かれていません（出典1）。保守契約が終了している利用者は EC 営業部への問い合わせが案内されており、パッチを自力で取得できません。

「端末にログインできる人が SYSTEM になれる」——前提の低さが本件の本質である概観出典 [1] [2]

2026年10月13日、JPCERT/CC と IPA は JVN#38664315 を公表した。対象は株式会社ハンモックのIT 資産管理製品 AssetView で、脆弱性の分類は CWE-732「重要なリソースに対する不適切なアクセス権の割り当て」、CVE 番号は CVE-2026-101020、JVNDB-2026-000143 である。

JVN が記す想定影響は次の一文である。「当該製品の管理コンソールまたはクライアントモジュールが動作する Windows システムにログイン可能な攻撃者によって、SYSTEM 権限を取得される可能性があります」。

CVSS は 4.0 で基本値 8.5（AV:L/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N）、3.0 で 7.8（AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H）である。AV:L（ローカル）・PR:L（低い権限で足りる）・UI:N（利用者の操作を必要としない）という組み合わせは、「遠隔からは攻撃できないが、端末を触れる人には何の障壁も無い」ことを意味する。

本記録の評価として、この前提の低さが本件の本質である。リモートコード実行の脆弱性は「インターネットに面しているか」で緊急度を切り分けられるが、ローカルの権限昇格は切り分けの軸が「誰が端末を使えるか」になる。貸与 PC を使う従業員、共用端末を使う派遣社員や協力会社の担当者、1台の標準ユーザー権限を取った攻撃者——いずれも成立条件を満たす。

原因は「SYSTEM 権限で動くプログラムを一般ユーザーが置き換えられた」こと——対象のリソースは非公表原因・手口出典 [1] [2]

ハンモックの脆弱性情報ページ（2026年10月13日公開）は、原因を「重要なリソースに対する不適切なパーミッションの割り当て」とし、SYSTEM 権限で動作するプログラムの保護が不完全であったため、一般ユーザー権限でそのプログラムを置き換えられる状態だったと説明している。

想定される影響としてハンモックが挙げるのは3点である。機密性（他のユーザーやシステム領域の機密情報へのアクセス）、完全性（システムファイル・設定・サービス・セキュリティ設定の改竄）、可用性（製品が永続的に停止し復旧不能になるおそれ、およびシステムへの影響）。JVN の「SYSTEM 権限を取得される」という表現より踏み込んで、昇格後に何ができるかを示している。

一方で、どのファイル・ディレクトリ・サービス・レジストリに不適切な権限が付いていたのかはどちらの資料にも書かれていない。本記録の評価として、これは利用組織にとって実務上の制約になる。対象パスが分かれば、パッチ適用前の暫定措置として当該パスの ACL を自前で締めることや、適用後に権限が是正されたことを確認することができる。公表されていないため、利用組織は「ベンダーの言うとおりに上げて、直ったと信じる」以外の検証手段を持たない。

なお、ハンモックは「この脆弱性を緩和する回避策はありません」と明記している。パッチ適用かバージョンアップのいずれかが必須である。

影響版は4系統——Cloud＋ の対策版は公表の15日前にリリースされている被害規模・影響範囲出典 [1] [2]

影響を受けるバージョンは次のとおりである（出典1・2で一致）。

  • AssetView: Ver 13.2.7B より前
  • AssetView CLOUD: Ver 13.2.7B より前（13.2 系）、Ver 13.3.7 より前（13.3 系）
  • AssetView Cloud＋: Ver 2600.201.11 より前

製品ラインは3つだが、AssetView CLOUD が 13.2 系と 13.3 系で対策版を別に持つため、確認すべき版番号は実質4系統になる。ハンモックは、バージョンが分からない場合は管理コンソールを起動してウィンドウタイトルのバージョン情報を見るよう案内している。

本記録が注目したのは、AssetView Cloud＋ の対策版 Ver 2600.201.11 のリリース日である。ハンモックは対処方法欄に「9月28日（月）リリースのVer 2600.201.11へクライアントを更新」と記しており、2026年9月28日は実際に月曜日である。JVN の公表（10月13日）より15日前であり、クラウド側では公表に先行して対策版の配布が始まっていたことになる。

本記録の評価として、これは利用組織に確認作業を求める事実である。Cloud＋ の場合、更新の対象は「クライアント」であり、サーバ側が更新済みでも端末側のクライアントが 2600.201.11 になっているかは別問題である。9月28日から10月13日までの間にクライアントの更新が自動で進んでいた組織もあれば、更新が止まっていて気づいていない組織もありうる。公表日を起点に「これから対応する」と考えるのではなく、まず現行版を数えるのが先になる。

資材は保守契約ユーザー専用サイトにしか無く、契約終了ユーザーは自力で取得できない対策・注意喚起出典 [1]

ハンモックが案内する対処方法は製品ごとに異なる。

AssetView および AssetView CLOUD については、保守契約ユーザー専用サイト（要ログイン）の記事「AssetView 権限昇格の脆弱性対応（JVN#38664315）」からプログラム資材とマニュアルをダウンロードし、マニュアルに従って対策済みパッチを適用するか対策済みバージョンへアップデートする。ページに個別のパッチ番号や名称の記載は無い。

AssetView Cloud＋ については、9月28日リリースの Ver 2600.201.11 へクライアントを更新する。

問い合わせ窓口は契約状態で分かれている。保守契約ユーザーは AssetView サポートグループ（0120-994577、平日9:00〜12:00・13:00〜17:00）、保守契約が終了しているユーザーはEC 営業部（0120-922786、同時間帯）である。

本記録の評価として、この構造には実務上の穴がある。回避策が無い脆弱性で、対処資材がログインを要する会員サイトにしか置かれていないため、保守契約が切れた利用者はパッチを自力で取得できない。その場合に何が提供されるのか（無償のパッチ提供か、保守契約の再締結か、有償対応か）は公表されていない。IT 資産管理製品は一度入れると長く使われ、契約が切れたまま稼働し続ける端末が残りやすい。対処の入手条件が公表されないことは、旧版が現場に残り続ける構造的な要因になる。

内部不正対策の製品が内部不正の踏み台になる——AssetView 固有の反転が起きる評価・解釈出典 [1] [2] [3] [4]

本記録の整理として、本件の重要性は CVSS の数値よりも「製品の役割」にある。

AssetView の製品サイトが挙げる機能は、IT 資産管理、アプリケーション配布、リモートコンソール、モバイルデバイス管理、PC 操作ログ、メール監視・分析、デバイス制御、不正 PC 遮断、画面操作ログ、Web フィルタリング、ファイル暗号化、個人情報検索、エンドポイントセキュリティである。内部不正対策とデータ流出対策が中核に置かれている。

ここに権限昇格の脆弱性があると、2つの反転が起きる。

第一に、監視の無効化である。SYSTEM 権限を取れば、操作ログの収集、デバイス制御、Webフィルタリングといった仕組みそのものを止めたり設定を変えたりできる。ハンモック自身が完全性への影響として「セキュリティ設定が改竄されるおそれ」を挙げている。内部不正を見張るために入れた製品が、内部不正を実行する前に監視を外す手段を提供する形になる。

第二に、最小権限の前提の崩壊である。多くの組織は「利用者に管理者権限を与えない」ことを統制の基礎に置いている。本脆弱性は、標準ユーザーのまま SYSTEM に上がれる経路を全端末に配ってしまう。EDR の除外設定、資産管理エージェントの常駐、管理者権限の剥奪——これらの組み合わせで成り立っていた前提が、エージェント1本の権限設定で崩れる。

なお、AssetView には先行例がある。本記録が本文を確認した直近の例は2025年3月25日のJVN26321838 で、重要な機能に対する認証の欠如（CVE-2025-25060）と開発者への送信データからの機微な情報の取得（CVE-2025-27244）の2件が公表されている。報告者は別の組織（ベリサーブ）であった。製品が継続的に調査対象になっていること自体は健全だが、利用組織の側から見れば「この製品は年単位で脆弱性公表がある」という前提で更新体制を組む必要があるという意味になる（本記録の評価）。

以上は本記録の評価であり、ハンモックや JVN の説明ではない。

**ハンモックと JVN は、脆弱性の種類（CWE-732）・原因の性質（SYSTEM 権限プログラムの 保護不備）・成立の前提（当該 Windows へのログイン）・CVSS とベクタ・影響版・ 対処方法・報告者を公表した一方、不適切な権限が付与されていた具体的なリソースと 再現手順は公表していない**（出典1・2）。 部分的に機能**本記録の判断である。** **機能した点**——**①開発者の公表と JVN の公表が同日に揃い、影響版・対処・CVSS が 一度に読める状態になった。** **②ハンモックが「回避策は無い」と明記したため、 利用組織が無駄な暫定策の検討に時間を使わずに済む。** **③原因の説明（SYSTEM 権限プログラムを一般ユーザー権限で置き換えられる）が JVN の CWE 分類より具体的で、影響の読み替えができる。** **不十分な点**——**①対策資材が保守契約ユーザー専用サイトに限られ、 契約終了ユーザーへの提供条件が書かれていない。** **②Cloud＋ の対策版が9月28日に出ていたことが公表日まで外から見えず、 クライアント更新の確認が公表後になる組織が出る。** **③AssetView CLOUD の対処方法が JVN とベンダーページで食い違っている**〈齟齬1〉。
CISO・経営層への示唆
  • **「管理・監視のために全端末に入れている製品」を、最も優先度の高いパッチ対象に分類する**
    **AssetView のクライアントモジュールは管理対象の全端末に入る**（出典3）。 **そこに SYSTEM 権限昇格があると、影響範囲は「製品1つ」ではなく「全端末」になる** （本記録の評価）。 **さらに本製品は PC 操作ログ・デバイス制御・Web フィルタリングを担うため、 昇格した者が監視機能そのものを改竄しうる** （ハンモックは「セキュリティ設定が改竄されるおそれ」と記載。出典1）。
    取るべき行動 **①資産台帳で「全端末に常駐するエージェント」を列挙する （資産管理・EDR・バックアップ・リモート操作・暗号化）。** **②それらに本番サーバと同じかそれ以上のパッチ適用目標時間を設定する。** **③各エージェントのベンダーの脆弱性情報ページと JVN の該当製品を 購読対象に入れ、担当者を名前で決める**（本記録の推奨）。
  • **保守契約の期限切れを「コストの話」ではなく「セキュリティの話」として管理する**
    **本件の対策資材は保守契約ユーザー専用サイト（要ログイン）にしか置かれていない。 保守契約が終了しているユーザーには EC 営業部の窓口が案内されるだけで、 パッチ提供の条件は書かれていない**（出典1）。 **回避策が無いと明記されているため、資材を取得できなければ対処の手段が無い** （本記録の評価）。
    取るべき行動 **①稼働中の製品について保守契約の有効期限を一覧化し、 期限切れのものに「脆弱性が出たら対処できない」という印を付ける。** **②その状態を許容するかを経営の判断として記録する（黙って放置しない）。** **③期限切れ製品は撤去か契約更新のどちらかに期限を切る**（本記録の推奨）。
  • **CVSS の数値ではなく「成立条件が自組織に当てはまるか」で緊急度を決める運用に変える**
    **本件の CVSS は 4.0 で 8.5、3.0 で 7.8 と版によって異なる**（出典2）。 **また AV:L（ローカル）という属性は、 「遠隔ではないから後回し」という判断を招きやすい**（本記録の評価）。 **しかし成立条件は「端末にログインできること」であり、 共用端末・貸与端末・協力会社端末がある組織では条件が常に満たされている。**
    取るべき行動 **①脆弱性の優先度判定の基準に「成立条件が自組織の構成で満たされるか」の欄を加える。** **②ローカル権限昇格を「低」に固定している運用があれば、 標準ユーザー運用を前提にしている組織では「高」に読み替える規則を書く。** **③CVSS を使う場合は版（3.0 か 4.0 か）を記録に残す**（本記録の推奨）。
  • **同一製品の脆弱性公表が繰り返されているかを、製品選定と更新体制の判断材料にする**
    **AssetView には先行例がある。本記録が本文を確認した直近の例は 2025年3月25日公表の JVN26321838（CVE-2025-25060・CVE-2025-27244）である**（出典4）。 **報告者は別組織であり、製品が継続的に調査対象になっていることを示す** （本記録の整理。製品の優劣の評価ではない）。
    取るべき行動 **①主要な常駐エージェントについて、過去3年の JVN／CVE の公表件数を数える。** **②件数が多い製品には、より短いパッチ適用目標時間と、 更新の自動化（または更新状況の可視化）を割り当てる**（本記録の推奨）。
セキュリティ技術者への示唆
  • **AssetView の現行バージョンを全端末で数え、対策版（13.2.7B／13.3.7／2600.201.11）以上へ上げる**
    **影響版は AssetView が Ver 13.2.7B より前、AssetView CLOUD が Ver 13.2.7B より前（13.2 系）と Ver 13.3.7 より前（13.3 系）、 AssetView Cloud＋ が Ver 2600.201.11 より前である**（出典1・2）。 **回避策は無く、パッチ適用か対策版へのアップデートが必須である**（出典1）。
    取るべき行動 **①管理コンソールを起動し、ウィンドウタイトルのバージョン情報で現行版を確認する （ハンモックの案内する確認方法）。** **②AssetView／AssetView CLOUD は保守契約ユーザー専用サイトの記事 「AssetView 権限昇格の脆弱性対応（JVN#38664315）」から資材とマニュアルを取得する。** **③Cloud＋ は9月28日リリースの Ver 2600.201.11 へクライアントを更新する—— サーバ側ではなくクライアント側の版を見る。** **④更新できない端末の台数と理由を一覧にして残す**（本記録の推奨）。
  • **Cloud＋ 利用組織は「9月28日以降にクライアント更新が通っていたか」を遡って確認する**
    **Cloud＋ の対策版は JVN 公表の15日前（2026年9月28日）にリリースされている**（出典1）。 **公表日を起点に作業を始めると、 「もう更新されている端末」と「更新が止まっていた端末」を取り違える**（本記録の評価）。
    取るべき行動 **①クライアントの版の分布を取り、2600.201.11 未満の端末を抽出する。** **②更新が止まっている端末について原因を切り分ける （長期オフライン・通信経路の遮断・更新処理の失敗）。** **③更新の失敗が検知されずに放置される構成なら、 版の分布を定期的に取る仕組みを作る**（本記録の推奨）。
  • **AssetView のインストール先配下の実行体への書き込みを、ファイル完全性監視の対象に入れる**
    **攻撃の成立は「SYSTEM 権限で動作するプログラムを一般ユーザー権限で置き換える」ことである** （出典1）。 **置き換え対象のパスは公表されていないが、 製品のインストール先配下の実行体という範囲は分かる**（本記録の整理）。
    取るべき行動 **①AssetView のインストール先ディレクトリを EDR／ファイル完全性監視の対象に加える （資産管理エージェントは除外設定に入っていることが多いので確認する）。** **②製品の正規の更新プロセス以外からの書き込みを検知対象にする。** **③SYSTEM として起動した子プロセスのうち、 製品の正規の処理系列に属さないものを記録に回す**（本記録の推奨。脆弱性固有の対策ではない）。
  • **AssetView が収集する操作ログを、端末内に留めず外部のログ基盤へ転送する**
    **SYSTEM 権限を取得すると、セキュリティ設定の改竄が可能になる** （ハンモックの想定影響。出典1）。 **操作ログ・デバイス制御の設定を変えられるため、 記録が端末内にしか無い構成では昇格後の行為が消される**（本記録の評価）。
    取るべき行動 **①AssetView のログが最終的にどこに保存されるかを図に書き、 端末内で完結している経路があるか確認する。** **②SIEM・ログ基盤への転送を即時に行う構成にする。** **③転送が止まったこと自体を警告の対象にする**（本記録の推奨）。
  • **保守契約が切れている AssetView の稼働台数を数え、撤去か契約更新の判断に上げる**
    **対策資材は保守契約ユーザー専用サイトにしか置かれていない**（出典1）。 **契約が切れている端末は、技術的にはパッチを当てられる状態でも 資材を取得できない**（本記録の整理）。
    取るべき行動 **①契約状態と稼働台数を突き合わせ、契約外で動いている台数を出す。** **②EC 営業部（0120-922786）に提供条件を確認し、回答を記録に残す。** **③提供されない場合は撤去の計画を立てる**（本記録の推奨）。
