INC-2026-0487AnyDeskに未認証RCEのPoC公開

2026年10月8日、V12 セキュリティチームの研究者がリモートデスクトップソフト AnyDesk の Linux 版に対する実証コード「AnyPwn」を GitHub へ公開した。 セッションプロトコルの mode 5 ストリームパケット処理がペイロード長を検証せず、 32ビット演算のラップアラウンドで過小なヒープ領域を確保するため、 **利用者が画面共有を承認する前に root 権限でコマンドを実行できる**。 4日後の10月12日に MITRE が CVE-2026-109390（CVSS 9.8）を採番したが、 **修正は2026年6月23日の 8.0.3 で無言のうちに入っており、 ベンダーのアドバイザリは本記録の確認範囲では存在しない**

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月8日（実証コードの公開。CVE の採番は10月12日） 最終更新: 2026年10月13日

直ったのは6月、知らされたのは10月です。

2026年10月8日、V12 セキュリティチームの Rick de Jager 氏が、リモートデスクトップソフト AnyDesk の Linux 版 8.0.2 に対する実証コード「AnyPwn」 を GitHub へ公開しました（出典2）。セッションプロトコルの mode 5 ストリームパケット処理が、リモートから指定されたペイロード長を検証せずに信用するため、32ビット演算のラップアラウンドで過小なヒープ領域が確保され、領域外書き込みが起きます。AnyDesk のサービスは Linux では通常 root で動くため、利用者が画面共有を承認する前に root 権限でコマンドが実行されます（出典2）。

4日後の 10月12日、MITRE が CVE-2026-109390 を採番しました。CVSS 3.1 の基本値は 9.8（AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H）、弱点の種類は CWE-130 です（出典1）。CISA の Vulnrichment は 悪用状況「poc」・自動化可能性「yes」・技術的影響「total」 と評価しています（出典1）。

本件の読みどころは、脆弱性そのものより公表の順序です。報道（出典3）によれば、修正は現地時間2026年6月23日公開の 8.0.3 に入っていたものの、更新履歴では言及されていませんでした。CVE が付いたのは実証コードの公開後です。つまり、6月から10月までの約3か月半、Linux 版の利用者は「これは緊急で上げるべき更新だ」と判断する材料を持っていませんでした（本記録の評価）。

ベンダー自身のアドバイザリは、本記録の確認範囲では存在しません。 AnyDesk のサイト（更新履歴・セキュリティ情報）は自動取得に対して 403 を返すため、本記録は「更新履歴に言及が無かった」という報道の記述を一次資料で裏取りできていません〈齟齬に記録〉。CISA KEV（2026年10月8日版・1,739件）には AnyDesk の項目が1件もありません（本記録が原データで確認）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない**（本記録が確認した範囲。T6）。 **ここに記録するのは、公開された実証コードから読み取れる成立経路の骨格である** （本記録の方針）。 **段は initial-access（TCP 7070 番またはリレー経由でセッションプロトコルに到達）・ execution（mode 5 パケットで整数の一周を起こしヒープを破壊）・ impact（承認前に root でコマンド実行）の3つ。** **権限昇格の段は置かない**——**サービスが最初から root で動いているため、 昇格の操作が要らない**（出典2。本記録の整理）。

  1. 1. 初期侵入確認済
    **AnyDesk のサービスが待ち受けるセッションプロトコルの経路へ到達する。** **実証コードの経路は TCP 7070 番への直接接続（同一セグメント・ または外部から到達可能な環境）である**（出典2）。 **認証は不要**——**CVE の記述は「認証されていないリモートの攻撃者」である**（出典1）。
    根拠: 実証コードの実行手順（`python3 anypwn.py --host <target> --command ...`）と CVE の記述（出典1・2）
  2. 2. 実行確認済
    **mode 5 のストリームパケットで、宣言するペイロード長を `0xfffffff0` にする。** **16バイトのオブジェクトヘッダを32ビット演算で加算すると値が一周して0になり、 確保されるのは0〜15バイトだけになる。 オブジェクトのデータポインタは「確保の先頭＋0x10」のまま、 長さも元の大きな値のままなので、本体の書き込みが領域の外へ出る**（出典1・2）。 **実証コードは、サイズを段階的に変えた100個ずつの mode 5 オブジェクトでヒープを整え、 10本の追加接続で犠牲オブジェクトを並べ、 破壊後に `ret` ガジェットの長い滑走路を含む `0xf000` バイトのオブジェクトを20個散布して ROP 連鎖へ着地させる**（出典2）。
    根拠: 実証コードの README における仕組みの説明と CVE の記述（出典1・2）
  3. 3. 影響（暗号化・破壊・改ざん）確認済
    **破壊したオブジェクトの制御データ（vtable・スタックピボットのガジェット）を通じて 実行を奪い、散布した ROP 連鎖で任意のコマンドを実行する。** **AnyDesk のサービスは Linux では通常 root で動くため、 利用者がデスクトップ操作を承認する前に root でのコマンド実行に至る**（出典1・2）。
    根拠: CVE の記述「被害者がデスクトップ操作を承認しないまま root としてコマンドを実行できる」（出典1）

長さを信用して領域を確保する——32ビットの加算が一周した瞬間に、確保は0バイトになる原因・手口出典 [1] [2]

CVE の記述は短いので、まず正確に写します（原文英語。本記録の訳。出典1）。

「8.0.3 より前の AnyDesk は、ヒープベースのバッファオーバーフローにより、認証されていないリモートの攻撃者が任意のコードを実行できる。Linux では、被害者がデスクトップ操作を承認しないまま root としてコマンドを実行できることが実証されている。セッションプロトコルの mode 5 用ストリームパケットハンドラで、ペイロード長の値が検証されていない。」

研究者の説明は、ここをもう一段ほどいています（出典2。本記録の訳・要約）。

mode 5 のパケットは frame_len（2バイト）・assigned_stream_id（2バイト）・モード前置（1バイト）・mode5_declared_len（可変長整数）・本体、という形をとります。正しいパケットなら、宣言された長さはフレームに残っているバイト数を超えてはいけません。脆弱な経路は、この検証を行う前に、宣言された32ビットの長さから裏付けとなる領域の大きさを計算します。

  • 宣言する長さを 0xfffffff0 にする
  • 0xfffffff0 + 0x10（16バイトのオブジェクトヘッダ）= 0x1_0000_0000
  • 32ビットに切り詰めると 0 になる

0xfffffff0 から 0xffffffff の範囲は、確保されるのが0〜15バイトだけになります。ところがオブジェクトのデータポインタは「確保の先頭＋0x10」のまま、長さも元の大きな値のままです。結果、本体を1バイト書き込むだけで領域の外へ出ます。 4ギガバイトを送る必要はありません——外側のフレームは小さいまま、可変長整数が整数の一周を起こし、本体が溢れる分を供給します（出典2）。

本記録の整理——これは「入力の検証漏れ」より一段深い種類の不備です。検証そのものは存在していて、検証に使う値と、領域確保に使う値が別の順序で流れていることが問題でした。同じ構造は、長さ付きのバイナリプロトコルを自作している箇所に広く潜みます（本記録の評価）。

承認の前に root でコマンドが動く——「画面共有を許可しなければ安全」という前提が崩れる被害規模・影響範囲出典 [1] [2]

リモートデスクトップソフトの利用者が持っている安全の感覚は、おおむね「相手が接続してきても、自分が承認しなければ何も起きない」です。 本件はその前提の外側で成立します（出典1・2）。

研究者の表現は明確です。「サービスは Linux では通常 root で動くため、悪用に成功するとデスクトップ操作の承認より前に root でのコマンド実行に至る」（出典2。原文英語。本記録の訳）。CVE も 「被害者がデスクトップ操作を承認しないまま root としてコマンドを実行できることが実証されている」 と書いています（出典1）。

実証コードが示した成立条件は次のとおりです（出典2）。

  • 対象: AnyDesk Linux 8.0.2（x86_64）・サービスモード（anydesk --service）
  • 経路: TCP 7070 番への直接接続
  • 前提: ヒープの配置は確率的で、狙ったオブジェクトが隣に来ないとコマンド実行ではなくサービスのクラッシュになる
  • オフセットはそのビルド専用（SHA-256 まで README に明記）であり、他のビルドでは動かない

「確率的」「ビルド専用」は、攻撃の難しさを意味しますが、防御側の安心材料にはなりません（本記録の評価）。失敗した場合に起きるのはサービスのクラッシュです。つまり攻撃者は何度でも試せて、防御側から見えるのは「AnyDesk がときどき落ちる」という現象だけになります。

そしてポートの話です。研究者は「同じ脆弱なセッションプロトコルの経路は AnyDesk のリレー接続経由でも到達でき、最小限の Frida トリガで検証した。工数を抑えるため、同梱の最小 PoC は直接の TCP 7070 接続でのみ完全な悪用を示している」と書いています（出典2。本記録の訳）。したがって「7070 番を閉じたから対処済み」とは言えません ——リレーは AnyDesk の標準的な接続経路です（本記録の評価）。

6月に無言で直し、10月に実証コードが出てから CVE が付いた——利用者は優先度を判断する材料を持たなかった再発防止出典 [1] [2] [3] [6]

CVE の採番者が MITRE であることにも意味があります（出典1）。ベンダーが CNA として自ら採番したのではなく、第三者が後から番号を付けた形です。予約時刻と公開時刻が1秒差（2026年10月12日14時40分09秒・10秒）であり、実証コードの公開を受けた事後の処理だと読めます（本記録の評価）。

本記録はベンダーの振る舞いを断定しません。 更新履歴に実際に何が書かれていたかを原本で確認できていないためです（出典6 は 403 を返します）〈齟齬1〉。確認できたのは次の3点です—— ①CVE の参照先にベンダーのアドバイザリが挙げられていない②研究者が「8.0.3 で修正済み」と書いている③研究者が「PoC 動画の公開を受けてベンダーは 8.0.2 のビルドを削除したように見える」と推測の形で述べている（出典1・2）。

実務上の教訓は、ベンダーの善悪ではなく運用の側にあります（本記録の結論）。「セキュリティ修正と書かれていない更新」を後回しにする運用は、無言修正（silent fix）の前では機能しません。 リモート接続ソフトのような「ネットワークに面した常駐サービス」は、更新履歴の文言ではなく、版の新しさで管理する必要があります。

CISA は「poc・自動化可能・影響は全面的」と評価したが、KEV には入っていない対策・注意喚起出典 [1] [4] [5]

CVE レコードには、CISA の ADP（Vulnrichment）による補足が付いています（出典1）。

  • Exploitation: poc ——実証コードは存在するが、実際の悪用は観測されていない
  • Automatable: yes ——偵察から悪用までを自動化できる
  • Technical Impact: total ——成立時の技術的影響は全面的
  • 実証コードの URL に exploit タグが付与されている

「poc」と「automatable: yes」の組み合わせが、本件の緊急度の実質です（本記録の整理）。未認証・利用者操作不要（PR:N／UI:N）で、公開された実証コードがあり、探索と悪用を機械化できる——この条件が揃った脆弱性は、悪用が観測されるまでの時間が短くなります。

一方で KEV には入っていません。本記録が確認した2026年10月8日版（catalogVersion 2026.10.08・収載1,739件）には、AnyDesk の項目が1件も存在しません（出典4）。ただしこのカタログ版は CVE 公開（10月12日）より前であり、「悪用されていない」ことの根拠にはなりません（本記録の留保）。

NVD 側の状態も確認しました——登録はされているが状態は「Received」で、NVD 自身の分析（CVSS の独自評価・CPE の確定）は未了です（出典5）。自動化された脆弱性管理の仕組みは、NVD の分析完了を待って情報を取り込むものが多く、その設計だと本件は「まだ見えない」状態にあります（本記録の評価）。

    取るべき行動 **①リモート接続ソフト（AnyDesk／TeamViewer／RustDesk 等）の導入台数と版を 棚卸しする。保守委託先が持ち込んだ分を忘れやすい。** **②台帳上の重要度を、業務端末ではなくリモートアクセス基盤と同じ区分に置く。** **③その区分に「更新の目標時間」「待ち受けポートの到達範囲」の2つを約束として書く** （本記録の推奨）。
  • **「セキュリティ修正と書かれていない更新」を後回しにする運用を見直す**
    **本件の修正は2026年6月23日の 8.0.3 に入っていたが、 報道によれば更新履歴では言及されていなかった**（出典3）。 **CVE が付いたのは実証コード公開後の10月12日である**（出典1）。 **修正から実証コード公開まで107日**（本記録の算出）—— **この間、更新履歴の文言を判断材料にしていた組織は、 何も知らないまま脆弱な版を動かし続けた。**
    取るべき行動 **①ネットワークに面した常駐サービスについては、 「脆弱性情報の有無」ではなく「版の新しさ」で更新の要否を決める基準に切り替える。** **②自動更新を切っている製品を洗い出し、切っている理由を1件ずつ確認する。** **③更新履歴に依存した判断をしている製品の一覧を作り、 無言修正が起きても困らない運用（定期的な最新化）へ移す**（本記録の推奨）。
  • **ベンダーの情報が「機械で読めるか」を調達・運用の評価項目に入れる**
    **本記録は AnyDesk のページへ3通りの方法で到達を試みたが、 いずれも HTTP 403 が返った**（出典6。T6）。 **CVE レコードの参照先にベンダーのアドバイザリは無く、 更新履歴のページだけが挙げられている**（出典1）。 **脆弱性管理を自動化している組織では、 「人が見れば分かる情報」は実質的に存在しないのと同じである**（本記録の評価）。
    取るべき行動 **①主要ベンダーについて、セキュリティ情報の提供形態 （RSS・CSAF／VEX・メール配信・CVE の自社採番の有無）を一覧にする。** **②提供が無いベンダーの製品は、版の監視（インストール済み版と最新版の比較）で 代替する仕組みを用意する。** **③新規調達時に「脆弱性情報の提供形態」を質問項目へ加える**（本記録の推奨）。
  • **「悪用は未観測」ではなく「自動化できる実証コードが公開済み」を判断の基準にする**
    **CISA の SSVC 評価は Exploitation: poc・Automatable: yes・ Technical Impact: total である**（出典1）。 **未認証・利用者操作不要で、公開された実証コードがあり、 探索と悪用を機械化できる**——**この組み合わせは、 悪用が観測されるまでの時間が短い類型である**（本記録の整理）。 **一方 KEV にはまだ載っておらず、NVD の分析も未了である**（出典4・5）。
    取るべき行動 **①KEV 収載を待つ運用になっていないか確認する。 本件のように KEV 収載前・NVD 分析前の段階で実証コードが出る事案に対応できる経路を作る。** **②実証コードの公開（GitHub・Exploit-DB 等）を監視対象に入れ、 自社資産に該当するものだけを拾う。** **③SSVC の「Automatable: yes」を優先度判定の入力として採用する**（本記録の推奨）。
セキュリティ技術者への示唆
  • **Linux 版 AnyDesk を 8.0.3 以上（実務上は最新の 8.1.0 以降）へ上げる**
    **CVE の影響範囲は「8.0.0 以上 8.0.3 未満」で、修正版は 8.0.3 である**（出典1）。 **8.1.0 が2026年9月23日に公開されており、 最新版へ上げれば本件は解消する**（出典3）。 **実証コードは 8.0.2 に対して公開されている**（出典2）。
    取るべき行動 **①`anydesk --version` で全台の版を集める（サーバ・踏み台・保守端末を含む）。** **②8.0.3 未満を最優先で更新する。** **③更新後に版を記録し、台帳へ反映する。** **④8.0.0 より前の版（7.x 以前）の扱いは公表されていないため、 これも併せて最新化する**（本記録の推奨。未確定事項に記録）。
  • **TCP 7070 番の到達範囲を測る。ただし「閉じたから対処済み」としない**
    **実証コードは TCP 7070 番への直接接続で成立を示している**（出典2）。 **一方、研究者は同じ脆弱な経路がリレー接続経由でも到達できることを Frida で検証したと書いている**（出典2。本記録の訳）—— **リレーは AnyDesk の標準的な接続経路であり、 ポートを閉じても経路が残る**（本記録の評価）。
    取るべき行動 **①AnyDesk を入れた端末の 7070 番へ、外部および他セグメントから到達できるかを実測する。** **②不要な到達経路はホストのファイアウォールで閉じる（緩和としては有効）。** **③ただし更新を「後でよい理由」にはしない。 リレー経由の到達可能性が残るため、根本対処は版の更新である**（本記録の推奨）。
  • **AnyDesk サービスの異常終了を監視対象に入れる**
    **実証コードはヒープの配置に依存するため、 失敗するとコマンド実行ではなくサービスのクラッシュになる**（出典2）。 **攻撃者は何度でも試せるが、防御側に見えるのはクラッシュだけである** ——**つまりクラッシュの回数が、現実的に唯一の合図になる**（本記録の整理）。
    取るべき行動 **①`systemd` のサービス（anydesk）の異常終了を journald から拾い、 回数を日次で記録する。** **②基準線（平常時はほぼ0のはず）から外れたら、接続元の記録と併せて調べる。** **③自動再起動の設定だけで済ませない——再起動の記録を残す**（本記録の推奨）。
  • **長さ付きのバイナリプロトコルを自作している箇所で、同じ型の不備を探す**
    **本件の核心は「検証に使う値」と「領域確保に使う値」が別の順序で流れていたことである** （出典1・2。本記録の整理）。 **`declared_len + header_size` を32ビットで計算すれば、 同じ一周がどの実装でも起きる**——**言語や製品に固有の話ではない。**
    取るべき行動 **①自社製品・内製ツールで、受信した長さから領域を確保している箇所を列挙する。** **②「長さの検証」が確保より前に来ているかを1件ずつ確認する。** **③加算・乗算を行う箇所の型幅（32ビット／64ビット）を確認し、 オーバーフロー検査を入れる。** **④ファジングの対象に、長さフィールドの境界値 （`0xfffffff0`〜`0xffffffff`）を明示的に含める**（本記録の推奨）。
  • **サービスが root で動く必要があるかを設計として問い直す**
    **本件が root でのコマンド実行になったのは、 AnyDesk のサービスが Linux では通常 root で動いているからである**（出典2）。 **同じメモリ破壊でも、権限が分離されていれば影響は1段小さくなる** （一般論。本記録の評価）。
    取るべき行動 **①常駐サービスの実行ユーザを棚卸しし、root で動いているものを列挙する。** **②そのうち、ネットワークからの接続を待ち受けているものを優先して見る。** **③製品側で選択できない場合は、 コンテナ・名前空間・`systemd` の権限制限（`ProtectSystem`・`NoNewPrivileges` 等）で 影響範囲を絞る余地があるかを確認する**（本記録の推奨。製品の対応状況に依存する）。
