INC-2026-0488Twitch拡張がOAuthトークン転送

2026年9月11日、セキュリティ企業 Socket が、ブラウザ拡張 「Twitch Enhanced Viewer | JeetBot」（Chrome 約3万人・Firefox 552人）が Twitch の **アカウント権限を持つ OAuth トークンを、運営元のプロキシへ クエリパラメータ `&auth=` で平文のまま転送していた**と公表した。 ストアの「データを収集しない」表示とプライバシーポリシーには転送の記載がなかった。 転送機構は Firefox 版 85.8.7（9月16日確認）・Chrome 版 85.8.9（9月25日確認）で削除され、 開発元は開示が不十分だったことを認めたが、 **既に転送されたトークンの無効化は利用者自身の再認証に委ねられている**

意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因
初報: 2026年9月11日（Socket の公表） 最終更新: 2026年10月13日

拡張が盗んだのではなく、拡張の「設計どおり」にトークンが外へ出ていました。

2026年9月11日、セキュリティ企業 Socket（調査は Kush Pandya 氏）が、ブラウザ拡張 「Twitch Enhanced Viewer | JeetBot」 の挙動を公表しました（出典1）。Chrome 約3万人・Firefox 552人、合計約3.1万人が入れていた拡張です。広告ブロック・1080p 強制・地域制限の解除・チャンネルポイントの自動収集を謳っています。

仕組みはこうです（出典1）。拡張は Twitch 公式クライアントの Authorization ヘッダを取得し、前置を外して生の OAuth トークンを得ます。そのうえで usher.ttvnw.net（Twitch の動画プレイリスト）への要求を、運営元のプロキシ（既定値 enhanced[.]jeetbot[.]cc）へ差し替え、&auth= というクエリパラメータにトークンを付けて送ります。クエリパラメータに載せた資格情報は、受け手のリクエストログに平文で残ります。

問題はトークンの種類です。 Socket はこれが動画再生用の限定トークンではなく、アカウントに紐づくOAuth トークン（bearer 資格情報）であると判断しています。ウィスパー（個人間メッセージ）の閲覧・送信、チャットへの投稿、アカウント設定の変更、チャンネルポイントの消費ができる種類のものです。パスワードも二要素認証も経ずに使えます（出典1）。

開示はされていませんでした。 ストアの「データ安全性」欄は「データを収集・使用しない」、リンクされたプライバシーポリシーは「利用者データを収集・保存・処理しない」としており、OAuth トークンへの言及はありませんでした（出典1）。

修正は入っています。 Firefox 版 85.8.7 で auth パラメータが空に固定されたことを Socket が9月16日に確認、Chrome 版は 85.8.9 で転送が無いことを9月25日に確認しています（出典1）。開発元（JeetBot）は記事公開後に Socket へ連絡し、トークン取り扱いのリスクと、ストアの説明・プライバシーポリシーでの開示が不十分だったことを認めました（出典1）。

ただし、既に転送されたトークンは利用者が自分で無効化する必要があります。 Socket の推奨は「拡張を更新したうえで、Twitch の設定から全セッションを切断し、再認証する」です（出典1）。拡張の更新だけでは、プロキシのログに残ったトークンは無効になりません（本記録の指摘）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**これは外部からの攻撃ではなく、拡張の設計による資格情報の露出である**（本記録の整理）。 **段は credential-access（Twitch 公式クライアントの `Authorization` ヘッダから OAuth トークンを取り出す）・exfiltration（宛先を運営元プロキシへ差し替え、 `&auth=` でトークンを送る）・collection（プロキシのリクエストログに平文で残る）の3つ。** **悪用（アカウント操作）の段は置かない**——**実際の悪用は公表されていない** 〈未確定事項に記録〉。

  1. 1. 認証情報アクセス確認済
    **コンテンツスクリプトが、Twitch 公式 Web クライアントが使う `Authorization` ヘッダを取得し、拡張のバックグラウンドワーカーへ渡す。** **ワーカーが前置を外して生の OAuth トークンを得る**（出典1）。 **Socket は、これが再生用の限定トークンではなく アカウントに紐づく bearer 資格情報であると判断している。**
    根拠: Socket による拡張コードの解析（出典1）
  2. 2. 持ち出し確認済
    **`usher.ttvnw.net` への動画プレイリスト要求を、 運営元のプロキシ（既定値 `enhanced[.]jeetbot[.]cc`）へ差し替え、 `&auth=` というクエリパラメータにトークンを付けて送る**（出典1）。 **Firefox では blocking な `webRequest` リスナー、 Chrome では `declarativeNetRequest` の `regexSubstitution` ルールで実現している。** **旧版（4.8・2026年1月）は `set-token` エンドポイントへ直接 POST し、 `deno.dev`・`deno.net` を控えに使っていた**（出典1）。
    根拠: Socket による拡張コードの解析と転送先ドメインの特定（出典1）

    **クエリパラメータに載ったトークンが、プロキシのリクエストログに平文で残りうる** （出典1）。 **旧版については、同じトークンを5秒のクールダウンで重複送信しない実装から、 Socket は受信側での保存を推測している**（断定ではない）。

    理由は公表されていない
    トレードオフ: **利用者任せにすることで、サービスの中断は避けられる** （全利用者のセッションを切れば、正規の利用者も再ログインを強いられる）。 **代償は、対処する利用者と対処しない利用者に分かれることである** ——**記事を読まない大多数は、トークンがそのまま有効なまま残る** （本記録の評価）。

    トレードオフ: **「データを収集しない」という表示は、インストール率を上げる** （ストアの表示は利用者の判断材料である）。 **代償は、利用者が実際のリスクを判断できないことである** ——**本件では、約3.1万人が「収集されない」という表示のもとで アカウント権限のトークンを外部へ渡していた**（本記録の評価）。

資格情報を URL のクエリパラメータに載せた——受け手のログに平文で残る形で、約3.1万人分が運営元へ渡っていた原因・手口出典 [1]

Socket が示した経路を順に追います（出典1。本記録の訳・整理）。

  1. コンテンツスクリプトが、Twitch 公式 Web クライアントが使うAuthorization ヘッダを取得し、拡張のバックグラウンドワーカーへ渡す。
  2. ワーカーが前置（OAuth 等）を外し、生のトークンを取り出す。
  3. usher.ttvnw.net（Twitch の動画プレイリストの取得先）への要求を、運営元のプロキシ（既定値 enhanced[.]jeetbot[.]cc）へ差し替える。このとき &auth= というクエリパラメータにトークンを付ける。
  4. トークンはプロキシのリクエストログに平文で残りうる。

実装はブラウザごとに違いますが、結果は同じです（出典1）。Firefox では blocking な webRequest リスナー、Chrome では declarativeNetRequest の regexSubstitution ルールで宛先の差し替えを行っていました。例外はハードコードされた10チャンネル（ロシア語配信者など）だけで、それ以外の視聴では常に転送されていたとされます。

ここで本記録が強調したい点は、手口の巧妙さではありません。 URL のクエリパラメータは、ログに残ることを前提とした場所です。 Web サーバ、プロキシ、CDN、負荷分散装置——経路上のあらゆる装置がアクセスログに URL を丸ごと書きます。資格情報をそこへ載せれば、「意図せず保存される」のではなく「設計上保存される」（本記録の整理）。

旧版はもっと直接的でした（出典1）。版 4.8（2026年1月）は、取得したトークンを set-token という専用エンドポイントへPOST で送っていました。 送信先は主系のほか deno.dev・deno.net の控え付き。同じトークンを5秒のクールダウンで重複送信しないようにしていたことから、Socket は受信側でトークンを保存していたと推測しています（断定ではありません）。これらのエンドポイントは現在停止しています。

転送されたのは再生用の限定トークンではなく、アカウント権限を持つ bearer 資格情報だった被害規模・影響範囲出典 [1]

トークンの種類が、本件の重さを決めています。

Socket の判断——これは動画再生用に限定されたトークンではなく、アカウントに紐づく OAuth トークン（bearer 資格情報）である（出典1）。bearer 資格情報とは「持っている者が本人として扱われる」種類のもので、パスワードの入力も二要素認証も要りません。

Socket が挙げた、トークンでできること（出典1。本記録の訳）。

  • ウィスパー（個人間メッセージ）の閲覧と送信
  • チャットへの投稿
  • アカウント関連の設定の変更
  • チャンネルポイントの消費

本記録の評価——この4つの組み合わせは、「配信を見るための拡張」の権限としては明らかに過大です。 とくにウィスパーの閲覧は、個人間のやり取りの内容そのものに届きます。 チャットへの投稿は、アカウントを使った詐欺・スパムの発射台になります。

そして、二要素認証では止まりません（本記録の指摘）。二要素認証はログインの入口を守る仕組みであり、すでに発行されたセッション資格情報の持ち出しには効きません。 本件の対処が「パスワード変更」ではなく「全セッションの切断と再認証」である理由はここにあります（出典1）。

組織の観点では、同じ構図が業務用 SaaS でも成立します（本記録の整理）。ログイン中のページの Authorization ヘッダを読める拡張は、そのサービスのセッションをそのまま外へ出せます。 拡張の権限表示は「このサイトのデータの読み取りと変更」という一行に丸められるため、利用者にはこの違いが見えません。

ストアの表示は「データを収集しない」、プライバシーポリシーは「処理しない」——開示の欠落そのものが本件の中心である経営責任出典 [1]

Socket が指摘した開示の状態（出典1。本記録の訳）。

  • ストアの「データ安全性」欄: 「データを収集・使用しない」
  • リンクされたプライバシーポリシー: 「利用者データを収集、保存、処理しない」
  • OAuth トークンへの言及: 無し

開発元はこれを認めました（出典1。T5）。「以前の版はプレイリストを取得するために、視聴者の Twitch の OAuth トークンを当社の再生プロキシへ転送していた。トークンの取り扱いについて提起された懸念を受け止め、プライバシーの開示がこれを十分に説明していなかったことを認める」（原文英語。本記録の訳）。

本記録の評価——本件を「悪意ある拡張」として読むと、学べることが減ります。開発元の説明には技術的な筋があります。広告ブロックや画質強制のためにプレイリストを自前のプロキシで取るなら、Twitch の認証を通す必要がある——その実装として最も安易な方法がクエリパラメータへの付与でした。悪意の有無を問わず、資格情報は第三者のログに残ります（本記録の整理）。

したがって読者（CISO・技術者）が持ち帰るべき判定基準は、「作者が信頼できるか」ではありません（本記録の結論）。「この拡張は、ログイン中のサービスの通信を中継するか」です。中継するなら、その拡張はそのサービスのセッション資格情報に届きうる ——ストアの表示がどうあれ、技術的にはそうなります。 Socket が利用者向けの助言としてまさにこの一文を置いています—— 「ログイン済みサービスのトラフィックを中継する拡張は、そのセッション資格情報にアクセスできると考えること」（出典1。本記録の訳）。

修正は5日（Firefox）と14日（Chrome）で入ったが、既に外へ出たトークンの無効化は利用者任せのまま組織の対応出典 [1]

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**転送機構を削除する更新（Firefox 85.8.7・Chrome 85.8.9）は出されたが、 既に転送されたトークンの無効化は利用者自身の再認証に委ねられている**（出典1）。 **Socket の推奨は「拡張を更新し、Twitch の設定から全セッションを切断して 再認証する」である。** 不十分**本記録の判断である。** **機能した点**——**転送機構の削除は5日（Firefox）・14日（Chrome）で入り、 Socket が実機で確認している**（出典1）。 **不十分な点**——**①既に外へ出たトークンの扱いが、 情報を得た一部の利用者の手作業に委ねられている ②プロキシのログの保持期間が公表されていないため、 利用者は「いつまで危険が残るか」を見積もれない ③Twitch 側の一括無効化・通知が行われたかが分からない。**
**ストアの「データ安全性」欄は「データを収集・使用しない」と表示され、 プライバシーポリシーは「利用者データを収集、保存、処理しない」としており、 OAuth トークンの転送は記載されていなかった**（出典1）。 **開発元は記事公開後、この開示が不十分だったことを認めた**（T5）。 不十分**本記録の判断である。** **開発元は事後に開示不足を認め、修正版を出した**（出典1）—— **この部分は機能したと評価できる。** **不十分なのは、開発元自身による公表が確認できないことである** （公式サイト・ストア掲載ページに告知が無い。出典2・3）〈齟齬2〉。 **Socket の記事を読まない利用者には、何も届いていない**（本記録の指摘）。
CISO・経営層への示唆
  • **ブラウザ拡張を「資格情報に届く第三者コンポーネント」として管理対象に入れる**
    **本件で外へ出たのは、アカウント権限を持つ OAuth トークンである**（出典1）。 **拡張がログイン中のページで動く以上、 その拡張はそのサービスのセッション資格情報に届きうる** ——**Socket の助言もこの一点に要約されている**（出典1。本記録の訳）。 **権限表示は「このサイトのデータの読み取りと変更」に丸められ、 利用者には判断材料が渡らない**（本記録の評価）。
    取るべき行動 **①業務端末に入っている拡張の一覧を取得する （Chrome／Edge は企業ポリシーで報告させられる）。** **②「業務で使う SaaS のドメインで動く拡張」を抜き出し、 そこだけでも許可リスト運用に切り替える。** **③新規導入は申請制にし、申請時に「通信を中継するか」を必ず確認項目に入れる** （本記録の推奨）。
  • **二要素認証は「セッション資格情報の持ち出し」には効かないことを、 リスク評価の前提として明文化する**
    **転送されたのは bearer 資格情報であり、 パスワードも二要素認証も経ずにアカウント操作ができる**（出典1）。 **本件の対処が「パスワード変更」ではなく 「全セッションの切断と再認証」である理由はここにある**（本記録の整理）。
    取るべき行動 **①主要な SaaS について、セッションの強制失効（全端末のサインアウト）を 管理者が実行できるかを確認し、手順を書いておく。** **②できないサービスを一覧にし、それが業務上の重要データを持つなら 代替手段（トークンの有効期間の短縮・デバイス束縛）を検討する。** **③インシデント手順の「認証情報の初期化」の節に、 パスワード変更とセッション失効を別項目として書き分ける**（本記録の推奨）。
  • **ストアの「データを収集しない」表示を、審査済みの保証として扱わない**
    **本件ではストアの「データ安全性」欄が「データを収集・使用しない」、 プライバシーポリシーが「収集、保存、処理しない」となっていた一方、 実際にはアカウント権限のトークンが外部プロキシへ渡っていた**（出典1）。 **開発元自身が開示不足を認めている**（T5）。 **本記録が2026年10月13日に確認した時点でも、 Chrome Web Store の掲載は続いている**（出典3。T7）。
    取るべき行動 **①調達・利用許可の判断を、ストアの表示ではなく 「要求している権限」と「通信先」で行う方針を文書化する。** **②重要業務の端末では、拒否リストではなく許可リストを既定にする。** **③過去に許可した拡張について、権限の変更（更新で権限が増える）を 監視する仕組みがあるかを確認する**（本記録の推奨）。
  • **「気づいたのは第三者だった」という事実を、監視の設計の前提にする**
    **確認できる露出は少なくとも約8か月（2026年1月 → 9月11日）続き、 発見したのは利用者でもストアでも Twitch でもなく、 セキュリティ企業 Socket だった**（本記録の算出。出典1）。 **組織側にこの種の露出を自力で見つける手段はほぼ無い**（本記録の評価）。
    取るべき行動 **①自力検知を前提にせず、外部の公表を自組織の資産へ突き合わせる 経路（拡張 ID・ドメインでの遡及検索）を用意する。** **②DNS／プロキシのログの保持期間を確認する ——8か月遡れないなら、露出の有無を後から確認できない。** **③突き合わせの担当と所要時間を決めておく**（本記録の推奨）。
セキュリティ技術者への示唆

    取るべき行動 **①Chrome／Edge の管理コンソールで拡張 ID `pnhhdhhcadcjfckjhpmjneldiegbojfb` の導入端末を検索する。** **②該当者には、Twitch の設定から全セッションを切断して再認証するよう案内する。** **③Firefox の管理下端末では、Socket が示した ID （`twitchenhancedviewer@example.com`）での確認を試す ——ただし本記録は AMO 側でこの ID を公開参照できなかった**（T7。本記録の留保）。
  • **DNS／プロキシのログで転送先ドメインを遡及検索する**
    **転送先は既定値 `enhanced[.]jeetbot[.]cc` で、 旧版は `deno.dev`・`deno.net` を控えに使っていた**（出典1）。 **通信の中身（URL）は TLS で見えないが、宛先は観測できる**（本記録の整理）。
    取るべき行動 **①`jeetbot[.]cc`（サブドメインを含む）・`deno[.]dev`・`deno[.]net` への通信を、 保持しているログの全期間で検索する。** **②`deno.dev`／`deno.net` は正規の開発者向けホスティングであり、 それ自体は悪性ではない——該当があっても拡張の利用と結びつけてから判断する。** **③該当端末が見つかったら、利用者の Twitch セッションの取り消しを優先する** （本記録の推奨）。
  • **自社のサービスで、資格情報が URL のクエリパラメータに載る経路が無いか点検する**
    **本件の技術的な核心は「資格情報をクエリパラメータに載せた」ことである** （出典1）。 **URL は経路上のあらゆる装置（Web サーバ・プロキシ・CDN・負荷分散装置）の アクセスログに書かれる**——**意図せず保存されるのではなく、 設計上保存される**（本記録の整理）。
    取るべき行動 **①自社のアクセスログを `token=`・`auth=`・`key=`・`sig=` 等の パターンで検索し、資格情報が記録されていないか確認する。** **②見つかったら、ヘッダ（`Authorization`）へ移すか、 ログ側でマスクする。** **③外部サービスへのリダイレクト・プロキシ経路で 資格情報を引き継いでいる箇所を洗い出す**（本記録の推奨）。
  • **拡張の権限（`webRequest`／`declarativeNetRequest`）を、 審査の観点として理解しておく**
    **本件の転送は、Firefox では blocking な `webRequest` リスナー、 Chrome では `declarativeNetRequest` の `regexSubstitution` ルールで 実現されていた**（出典1）。 **どちらも「通信の宛先を書き換える」ための正規の仕組みである**（本記録の整理）。
    取るべき行動 **①許可申請の審査で、manifest の `permissions`／`host_permissions` と `declarative_net_request` のルールを見る項目を作る。** **②`<all_urls>` や業務 SaaS のドメインを含む拡張は、 利用者任せにせず個別に判断する。** **③判断できる人が社内にいない場合は、許可リストを小さく保つ方針に倒す** （本記録の推奨）。
  • **「現在の版が安全か」を自分で確かめるまで、解決済みとして記録しない**
    **Socket が転送の無いことを確認したのは Chrome 版 85.8.9 である**（出典1）。 **本記録が2026年10月13日に確認した掲載版は 85.9（更新日2026年10月6日）で、 これより後の版であり、本記録は挙動を検証していない**（出典3。T7）。 **拡張は更新のたびに挙動が変わりうる**（本記録の評価）。
    取るべき行動 **①許可リストに載せた拡張について、版の更新を検知する仕組みを持つ。** **②重要な端末で使う拡張は、更新のたびに通信先を確認する （端末のプロキシログで宛先の変化を見る）。** **③検証できないなら、その拡張を業務端末で使わない判断に倒す**（本記録の推奨）。
