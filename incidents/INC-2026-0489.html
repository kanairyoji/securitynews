    取るべき行動 **①配信履歴・通知テンプレート・差し込み項目を、 個人情報とは別に「なりすまし材料」として棚卸しする。** **②配信履歴の保存期間を決め、必要以上に持たない。** **③緊急配信に認証の手がかり（固定の差出人・事前に周知した合図・ 公式サイトへの掲載との二重化）を用意し、住民側が真偽を確かめられる形にする。**
  • **分単位の時刻を公表する——速さは、書かなければ検証されない**
    **本件の一次公表は、検知（10月11日16時30分）と応急措置（12日3時ごろ）を 時刻付きで書いている**（出典1）。 **その結果、外部の読者が「約10時間30分」という値を自分で出せる** （本記録の算出）。 **「速やかに対応した」という表現では、この検証ができない**（本記録の評価）。
    取るべき行動 **①自組織の公表文の雛形に、検知・封じ込め・公表の各時刻欄を作る。** **②その欄を埋められるよう、インシデント対応の記録様式に 「誰が何時に何をしたか」を残す項目を入れる。** **③時刻を書けない場合は、書けない理由（調査中・ログ未確認）を明記する。**
  • **委託先の侵害は「自組織の名前で住民に偽メールが届く」ところまで想定する**
    **本件では、流出が公表された当日に、 防災メールの正規の送信元アドレス（@raiden.ktaiwork.jp）を差出人に使った クレジットカード会社を装う偽メールが、登録者に届いた**（出典5・6）。 **そして静岡市は、送信元をブロック・迷惑メール設定すると 今後の防災情報が届かなくなると注意している**（出典5。原文は本文に引用）。 **本記録の評価**——**一般的なフィッシング対策（怪しい送信元はブロック）が、 緊急連絡の経路ではそのまま被害に変わる。** **しかも届かなくなったことは、次の災害まで誰も気づかない。**
    取るべき行動 **①住民・職員向けに「正規の送信元アドレスの一覧」を、 配信基盤の外（ホームページ・広報紙・紙の登録案内）に常設する。 偽メールが来てから周知を始めない。** **②注意喚起の文面に「ブロック設定をしないでほしい」旨を入れる雛形を、 平時に用意しておく（本件で静岡市が書いた1文がそれに当たる）。** **③委託先の侵害を想定した広報の雛形を、 「自組織は侵害されていないが自組織の名前が使われている」場合として別に持つ。** **④配信経路が侵害された状況で本人通知をどう出すかを決めておく （同じ経路を使うのか、郵送・報道に切り替えるのか）。**
  • **委託先の情報が「随時更新のブログ1本」に集まる前提で、取得の責任者を決める**
    **本件の続報は、同社の公式ブログ（出典4）の同一 URL が 時刻ごとに差し替わる形で出された** （10月13日15時50分 → 18時47分 → 14日10時40分 → 15時00分 → 16時00分 → 17時12分）。 **NET119 への拡大も、この更新の中で初めて現れた**（T14）。 **本記録の指摘**——**人の目視に依存すると、 「最大件数が出たこと」「対象サービスが増えたこと」に気づくのが遅れる。** **さいたま市は、住民からの指摘で事案を知っている**（出典6。T10）。
    取るべき行動 **①重要な委託先の告知ページを、更新検知の対象に登録する （RSS が無ければ内容のハッシュ監視でよい）。** **②検知した更新を誰が読み、誰が住民向け広報の判断をするかを先に決める。** **③随時更新の資料は、読んだ時刻とともに保存する （後から「あの時点で何が書かれていたか」を示せるようにする）。**
セキュリティ技術者への示唆
  • **連番で並ぶ環境（raiden／raiden2／raiden3）の設定差分を、定期的に突き合わせる**
    **一次公表が挙げた対象は6ドメインで、 2系統（ktaiwork.jp・speecan.jp）に連番の環境が並んでいる**（出典1）。 **同じ作りを複製して展開した構成と読める**（本記録の推定。公表に説明は無い）。 **複製された環境は、1つの穴が全部に効く。 同時に、更新や設定変更が一部の環境にだけ当たる事故も起きやすい**（本記録の評価）。
    取るべき行動 **①同一系統の環境について、公開ポート・認証方式・ 導入済みパッチの一覧を機械的に取得し、差分を出す仕組みを置く。** **②新しい環境を増やすときの手順を、 既存環境からのコピーではなく構成管理のコードからの生成に寄せる。** **③環境ごとの管理者アカウントを分け、1つの資格情報で全環境に入れない形にする。**
  • **「大量の宛先データを一括で読む」ことが正常な基盤では、持ち出しの検知を別の軸で作る**
    **一斉同報は、設計上、配信のたびに名簿を一括で読む**（本記録の整理）。 **したがって読み取り量の多さは異常の合図にならない。** **本件では、同社が「不審な挙動」を確認して検知に至っているが、 何を見たかは公表されていない**（出典1）。
    取るべき行動 **①名簿の読み取りを「配信ジョブに紐づくもの」と 「それ以外」に分け、後者だけを警報の対象にする。** **②管理画面からの一覧出力・CSV 書き出しを個別に記録し、 実行者・件数・時刻を残す。** **③平常時のアクセス量が少ない基盤では、 「深夜の管理画面ログイン」「配信予定が無い日の名簿参照」のように 業務の予定と突き合わせた検知を置く。**
  • **テナント分離を、名簿の到達範囲で確かめる**
    **複数の自治体が同じ基盤を使う構成では、 1組織の資格情報や1つの脆弱性で、他組織の名簿に届くかどうかが被害規模を決める** （本記録の評価）。 **本件では侵入経路も分離の状況も公表されていない**〈未確定事項に記録〉。
    取るべき行動 **①テナント横断の参照が可能かを、実際の操作で確かめる （識別子を書き換えて他テナントのデータが見えないか）。** **②配信 API の権限を、テナント単位ではなく「自テナントの名簿のみ」に絞る。** **③委託元として監査する立場なら、 分離の方式（論理分離かインスタンス分離か）を契約前に確認して記録に残す。**
  • **停止措置の設計を、機能単位であらかじめ切れるようにしておく**
    **報道によれば、停止されたのは「一部環境」である**（出典2）。 **災害情報の配信基盤では、全部止めるか全部動かすかの二択になると、 封じ込めと住民への配信のどちらかを必ず捨てることになる**（本記録の評価）。
    取るべき行動 **①基盤の機能を「管理画面」「名簿の編集」「配信の実行」「外部連携の受信」に分け、 個別に停止できる作りにする。** **②侵害時にどの順で止めるかを、 「配信の継続」を優先順位の上位に置いた形で決めておく。** **③停止したときに利用組織へ自動で通知される経路 （ステータスページ・連絡メール）を用意する。公表文だけに頼らない。**
  • **差出人表示だけでは真偽が判定できない前提で、受信側が確かめられる経路を二重化する**
    **本件の偽メールは、正規の送信元アドレスを差出人に使っていた**（出典5・6）。 **SPF・DKIM・DMARC の設定状況や、認証を通過したかどうかは どの資料にも書かれていない**（本記録の確認。〈未確定事項に記録〉）。 **本記録の評価**——**したがって本件から言えるのは 「受信者の目には本物と同じ差出人で届いた」という事実だけである。** **送信ドメイン認証が設定されていても、 住民の受信環境がその結果を表示しなければ判定には使われない。**
    取るべき行動 **①自組織が住民へ送る配信ドメインについて、 SPF・DKIM・DMARC を設定し、DMARC のポリシーを監視（p=none）から 隔離・拒否へ進める計画を持つ。レポートの受信先を決める。** **②緊急配信の本文に URL を入れない運用に寄せ、 「詳細は公式サイトで確認」の形にする（本文中のリンクを信頼させない）。** **③配信ドメインを委託先の共用ドメインにしている場合、 他の利用組織の事案が自組織の差出人にも影響することを前提に、 独自ドメイン（または専用のサブドメイン）での配信を検討する。** **④同じ内容を、配信・ホームページ・SNS の3経路で出す。 住民が「2つ以上で一致するか」を確かめられる形にする。**
  • **委託先の侵害を住民へ伝えるとき、委託先の社名とサービス名を書く**
    **大分県の公表（出典9）は委託先を「システム業者」とだけ書いている。** **同じ日に静岡市・さいたま市・岡山市など多数の自治体が同じ事業者を原因に 告知を出しているが、大分県の登録者からはそれが見えない**（本記録の評価）。 **piyolog の一覧でも77件のうち14件が事業者名・サービス名を書いていない**（出典8）。 **社名を書かないことの実害**——**住民が「自分の別の自治体での登録も対象か」を 判断できず、問い合わせが各自治体に分散する。** **また、偽メールが届いたときに本物の事案と結び付けられない。**
    取るべき行動 **①委託先侵害時の公表テンプレートに「委託先の社名」「サービス名」を 必須項目として入れる。社名を出さない場合は、出さない理由を内部で記録に残す。** **②委託契約に「侵害時に委託元が委託先名を公表できること」を明記する** （社名公表を妨げる秘密保持条項が残っていないか棚卸しする）。 **③同一事業者を使う他の自治体・組織の告知へリンクするか、 事業者の公表ページへ直接誘導する。**
  • **「復旧した」の範囲を、停止したものの一覧と突き合わせて確認する**
    **本件では、漏洩の可能性が確認された対象が6ドメイン＋NET119／119RAIDEN の3 URL であるのに対し、復旧が公表されたのは2サーバだけである**（出典4・第9報）。 **NET119（音声で119番通報できない人のための経路）の復旧状況は 第9報で一切触れられていない**（本記録の確認）。 **本記録の評価**——**利用組織の側が「自分の使っているサービスは戻ったのか」を 公表文から判定できない状態である。** **復旧の告知は、利用組織数の多いサービスから出る傾向がある** （本記録の推定。資料に説明は無い）。
    取るべき行動 **①自組織が委託先から受けている機能を、サービス名ではなく 「ドメイン／エンドポイント単位」で一覧にしておく。** **②侵害時は、その一覧に対して「停止」「復旧」「調査中」のどれかを 自分で埋めさせる（委託先の告知をそのまま信じない）。** **③委託先の告知に自分の使うエンドポイントが現れないときは、 個別に問い合わせて記録に残す。「書かれていない」は「正常」ではない。**
