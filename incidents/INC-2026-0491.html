INC-2026-0491npm 信頼公開に名前検証の不備

Bloom Security は 2026年10月13日、npm の Trusted Publishing（信頼された公開）に **バインディングの検証をリポジトリの名前（owner/repo のスラッグ）で行い、 GitHub が発行するトークンに含まれる不変の数値ID（repository_id / repository_owner_id）を照合していなかった**不備を公表した。 名前は、リポジトリの改名・移管・削除によって解放され、第三者が取得できる—— **一度も公開に使われていないバインディングであれば、 管理者の GitHub アカウントも npm アカウントも盗まずに、 そのパッケージを公開する資格が手に入る。** 研究者は「SlugFest」と名付け、**1,500 超のパッケージ（累計1,000万超・ 月間100万超のダウンロード）が対象になり得る**と報告した。 **実際の悪用は確認されていない**が、研究者は自前のパッケージに対して 別組織のリポジトリから新しい版を公開する実証に成功している。 報告は**2026年6月6日**に HackerOne 経由で行われ、6月9日に検証されたのち **7月8日以降は応答が途絶え、修正が確認できたのは10月2日**だった（研究者の記述）。 修正は数値IDの照合ではなく、**未検証の設定を48時間で失効させる**方式である。 **本記録が注目するのは、名前を同一性の根拠にした設計である**（本記録の評価）—— **ドメイン失効・パッケージ名の再取得と同じ型の問題が、 「資格情報を持たない公開」という仕組みの中心に入っていた。** **GitHub／npm 自身による本件の公表は、本記録の確認範囲では見つかっていない**〈齟齬1〉

Bloom Security は2026年10月13日、npm の Trusted Publishing（長期有効な公開トークンを持たず、GitHub Actions から OIDC で公開する仕組み）に同一性の検証の不備があったと公表しました（出典1）。研究者は「SlugFest」と名付けています。

仕組みはこうです。管理者が npm trust github --allow-publish を実行すると、npm はリポジトリの名前（owner/repo のスラッグ）とワークフローのファイル名、任意で環境名を記録します。公開のたびに、トークンのリポジトリ名とワークフロー名が一致するかを見ます。

見ていなかったのは、GitHub がトークンに入れているrepository_id と repository_owner_id です。これは改名しても移管しても変わらない数値の識別子です。npm はバインディングを作る時点でこれを受け取らず、保存もしていませんでした。記録されるのは、そのリポジトリから最初の公開が成功した後です（出典1）。

したがって、一度も公開に使われていないバインディングが狙えます。元の所有者がリポジトリを改名・移管・削除すると、その名前は空きます。攻撃者はその名前でリポジトリを作り、期待されているファイル名のワークフローを置いて OIDC トークンを発行させ、他人のパッケージを公開する資格を手に入れます。 管理者の GitHub アカウントも npm アカウントも盗む必要がありません（出典1）。

規模は、1,500 超のパッケージです。累計1,000万回超、月間100万回超のダウンロードがあり、中には月間20万回を超えるものも含まれます（出典2）。実際の悪用は確認されていません（出典1・2）。

本記録がもう一つ記録に残すのは、修正までの時間です。報告は2026年6月6日。6月9日に検証され、7月8日に「修正と、リスクと深刻度の判断に取り組んでいる」という返答が来たのが最後でした。その後6回の催促（HackerOne の調停申請を含む）に応答はなく、研究者が公表前に再検証したところ修正が入っていたとされています（出典1）。本記録が算出した報告から修正までの日数は118日です（T1 → T4）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない**（出典1・2）。 **ここに記録するのは、研究者が実証した成立経路の骨格である**（本記録の方針）。 **段は4つ**——**reconnaissance（未使用のバインディングと解放済みの名前の突き合わせ）・ initial-access（名前の取得とワークフローの設置）・ credential-access（OIDC トークンを公開用の資格情報に交換）・ impact（既存のパッケージ名で悪性の版を公開し、導入時のフックで実行）。** **権限昇格・横展開の段は置かない**——**管理者のアカウントを 一切触らないためである**（出典1。本記録の整理）。

  1. 1. 偵察確認済
    **npm に Trusted Publishing が設定されているパッケージを走査し、 ①そのバインディングから一度も公開が行われていないもの ②参照先の owner/repo が GitHub 上に存在しない（名前が空いている）もの を突き合わせる**（出典1。研究者はこの走査で1,500超を数えた）。
    根拠: 研究者のレジストリ全体の走査結果（1,500超・累計1,000万超のダウンロード）（出典1・2）
  2. 2. 初期侵入確認済
    **空いている owner/repo の名前でリポジトリを作成し、 バインディングが期待しているファイル名のワークフローを置く**（出典1）。 **環境名が設定されている場合はそれも合わせる。** **管理者の GitHub アカウント・npm アカウントには一切触らない。**
    根拠: 研究者の実証（自社保有の npm スコープに対し、別組織の GitHub リポジトリから公開）（出典1・2）
  3. 3. 認証情報アクセス確認済
    **設置したワークフローを動かして GitHub の OIDC トークンを発行させ、 npm のトークン交換に通す。** **npm はトークンのリポジトリ名とワークフローのファイル名を照合するが、 トークンに含まれる repository_id・repository_owner_id は バインディング側に保存されていないため照合されない**（出典1）。 **結果として、所有していないパッケージに対する有効な公開用の資格情報が 得られる。**
    根拠: 研究者の実証と、npm が保存する値・保存しない値の説明（出典1）
  4. 4. 影響（暗号化・破壊・改ざん）推定
    **既存のパッケージ名で、評判をそのまま引き継いだ形で 悪性の版を公開できる。** **導入時のフック（postinstall）を通じて、 開発者の端末や CI で攻撃者のコードが実行される**（出典1）。 **研究者は、AI コーディングエージェントが人の介在なしに パッケージを選んで導入するため、 悪性の依存が広がる速度が上がると主張している**（出典1・2）。 **実際に悪性の版が公開された事実は確認されていない**（本記録の明示）。
    根拠: 研究者による実証（新しい版の公開に成功）と、導入フックに関する説明（出典1・2）

名前は同一性ではない——改名すれば空く値を、信頼の根拠に使っていた原因・手口出典 [1]

Trusted Publishing は、長期有効な公開トークンを置かないための仕組みです。パッケージの管理者が「このリポジトリのこのワークフローからの公開だけを認める」と設定し、GitHub Actions が発行する短命な OIDC トークンで公開します（出典1）。

npm が記録していたもの（出典1）。

  • リポジトリの名前（owner/repo のスラッグ。例 bloom/repository）
  • ワークフローのファイル名
  • 任意で環境名

npm が記録していなかったもの（出典1）。

  • repository_id（リポジトリの不変の数値ID）
  • repository_owner_id（所有者の不変の数値ID）

どちらも GitHub のトークンには入っています。npm はバインディングを作る時点でこれを取得せず、保存もしていませんでした。記録されるのは、そのリポジトリから最初の公開が成功した後です（出典1）。

研究者の表現を引きます（原文英語。本記録の訳）。

「名前は同一性ではない。」

「それは、家の持ち主を見るのではなく、ドアに書かれた住所を見る鍵のようなものだ。」

住所は空きます。リポジトリを改名すれば、移管すれば、削除すれば、所有者アカウントを改名・削除すれば、元の名前は誰でも取得できます（出典1）。

攻撃の手順は4つです（出典1。本記録の整理）。

  1. 一度も公開に使われていないバインディングで、名前が空いているものを探す。
  2. その名前でリポジトリを作る。
  3. 期待されているファイル名のワークフローを置き、OIDC トークンを発行させる。
  4. トークンを公開用の資格情報に交換する。

研究者の記述——「この攻撃には内部情報も、資格情報の窃取も、競合状態も要らない」（出典1。本記録の訳）。

**本記録の判断である。** **機会は導入側に存在する**—— **①依存の更新を自動で取り込まない（版の固定とロックファイルの検査） ②導入時のスクリプト実行を既定で止める （`npm install --ignore-scripts` 相当の運用） ③新しい版の公開元（来歴の中身）が従来と同じリポジトリかを確認する。** **研究者・報道はいずれも、組織側の対策として 「開発者と AI エージェントが何を導入できるかを統制すること」を 挙げている**（出典1・2）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**研究者は、修正が入っていることを再検証で確認したうえで公表した**（出典1）。 **報告（2026年6月6日）から公表（同10月13日）までは129日で、 その間に6回の催促と HackerOne の調停申請を行ったとされる** （本記録の算出と出典1 の記述）。 部分的に機能**本記録の判断である。評価の対象は研究者とレジストリの双方である。** **機能した点**——**①受付とトリアージは3日で済んでいる ②修正は入り、公表は修正後に行われた ③研究者は影響するパッケージの一覧を公開せず、 点検手順を提示する形にした（出典1）。** **不十分と考える点**——**①7月8日以降の応答が途絶え、 調停申請にも反応が無かったとされる（出典1。GitHub 側の説明は無い） ②修正が、研究者の推奨した同一性の照合ではなく 有効期限による緩和であり、既存の信頼関係の点検が 利用者側に残された（出典2） ③識別子（CVE 等）が無いため、 脆弱性管理の仕組みに何も流れない（本記録の指摘）。** **留保**——**本記録は GitHub 側の原本に到達できていないため、 修正の内容・範囲を一次資料で確認していない**〈齟齬1〉。
**研究者は、影響を受けたパッケージの一覧を公開しない方針を採った。** **「問題がなお広く残っているため、 影響を受けたパッケージの一覧は公開しない」**（出典1。本記録の訳）。 部分的に機能**本記録の判断である。** **一覧の非公開は妥当な選択だが、 導入側に残る空白が埋まっていない**（本記録の評価）。 **本記録の整理**——**導入側にできることは、 個別のパッケージの判定ではなく 「悪性の版が入っても実行させない」側の対策である （版の固定・導入時スクリプトの停止・来歴の中身の確認）。**
CISO・経営層への示唆
  • **「資格情報を置かない」仕組みに移したあと、何を同一性の根拠にしているかを確かめる**
    **Trusted Publishing は、長期有効なトークンを置かないための仕組みであり、 供給網の対策として推奨されてきた**（本記録の整理）。 **本件は、その置き換え先が「リポジトリの名前」を 同一性の根拠にしていたという問題である**（出典1）。 **名前は、改名・移管・削除で空く値である。** **対策を進めた組織のほうが影響を受ける構図になっている**（本記録の評価）。
    取るべき行動 **①パスワードレス・トークンレスに移した仕組み （OIDC による公開、クラウドの信頼関係、SSO の連携）について、 「何が一致したら本人と見なすのか」を1件ずつ書き出す。** **②その値が、自分の側の操作（改名・移管・退職・ドメイン更新）で 変わったり空いたりしないかを確認する。** **③変わり得るなら、不変の識別子（数値ID・UUID）での照合に 切り替えられるかを提供元に確認する。**
  • **AI エージェントが導入するパッケージを、調達の対象として統制する**
    **研究者の実測では、AI エージェントによる導入は 1端末あたり月に約70パッケージ、開発者の端末では約350に達した （推移的な依存を除く）**（出典2）。 **本件の乗っ取りは「既存の名前・既存の評判のまま新しい版が出る」形であり、 選定の判断が人から外れるほど見つかる機会が減る**（本記録の評価）。
    取るべき行動 **①開発者と AI エージェントが導入できるパッケージの範囲を決める （社内ミラー・許可リスト・導入の記録）。** **②エージェントが導入した依存を、人が選んだ依存と区別して記録する。** **③導入時のスクリプト実行を既定で止める方針を決め、 必要な場合だけ例外にする。**
  • **改名・移管・退職・サービス終了を「資産の失効」として手順に組み込む**
    **本件の成立条件は、リポジトリの名前が解放されることである**（出典1）。 **同じ型の問題は、ドメインの失効、パッケージ名の再取得、 クラウドのストレージ名の再利用でも起きる**（一般的な事情。本記録の整理）。 **いずれも「自分が手放した名前が、他人の手で使われる」形である。**
    取るべき行動 **①リポジトリの改名・移管・削除、組織名の変更、 担当者の退職の手順に「その名前を参照している信頼関係の点検」を入れる。** **②手放す予定の名前（ドメイン・リポジトリ・アカウント）の一覧を持ち、 参照元を事前に洗い出す。** **③削除より先にバインディングを外す （出典1 の推奨：バインディングされたリポジトリを削除する前に バインディングを削除する）。**
  • **「署名があるか」ではなく「誰が署名したか」で判定する**
    **研究者は、攻撃者が署名した来歴（provenance）も、 署名の存在だけを確かめる検査なら通ると述べている**（出典1。本記録の訳）。 **本件の公開は、仕組みの上では正常な Trusted Publishing である** （本記録の整理）。
    取るべき行動 **①供給網の検査の判定条件を見直し、 「来歴の有無」ではなく「来歴に書かれた公開元が 従来と同じリポジトリか」を見る形にする。** **②重要な依存について、公開元の変化を警報の対象にする。** **③検査の結果を「通った／落ちた」だけでなく、 根拠（どの値を照合したか）を記録に残す。**
セキュリティ技術者への示唆
  • **`npm trust list` を回し、並んでいる名前が今も自分のリポジトリかを確かめる**
    **研究者が管理者向けに挙げた第一の手順である**（出典1・2）。 **本件の危険は「設定したまま公開していないバインディング」に集まる** ——**最初の公開が成功するまで数値IDが記録されないためである**（出典1）。
    取るべき行動 **①自分が公開している各パッケージについて `npm trust list` を実行し、 列挙された owner/repo が今も自分の管理下のリポジトリを指しているかを確認する。** **②改名・移管したものがあれば、バインディングを削除して作り直す。** **③新しくバインディングを作ったら、すぐに1版を公開して検証済みにする （出典1 の推奨。修正後は48時間で失効するため、放置した設定は残らない）。**
  • **自分が実行していない公開イベントを監視する**
    **本件の乗っ取りは、管理者のアカウントを使わずに 正規の公開経路を通る**（出典1）。 **したがって管理者から見える異常は「自分が出していない版が出ている」 という一点に絞られる**（本記録の整理）。
    取るべき行動 **①npm の公開通知（メール・webhook）を有効にし、 受け取る人を決める。** **②自前の CI の実行記録と、レジストリ上の公開履歴を 定期的に突き合わせる（版の数が合うか）。** **③合わない版を見つけたときの手順（非推奨化・撤回・ 利用者への告知）を事前に書いておく。**
  • **導入側では「悪性の版が入っても実行させない」側に寄せる**
    **影響を受けたパッケージの一覧は公表されていない**（出典1）—— **導入側には、自分の依存が対象かを判定する手段が無い**（本記録の指摘）。 **悪性の版は、導入時のフックで実行される**（出典1）。
    取るべき行動 **①導入時スクリプトの実行を既定で止める （CI では明示的に無効化し、必要なパッケージだけ例外にする）。** **②依存の版を固定し、ロックファイルの変更を人がレビューする。** **③社内ミラーを置き、外部レジストリから直接取らない経路にする （新しい版の取り込みに検査の段を入れられる）。**
  • **CI のワークフロー名とイベントの種類を、信頼の条件として点検する**
    **バインディングはワークフローの「ファイル名」を条件にしている**（出典1） ——**攻撃者は同じ名前のファイルを置くだけでよい。** **また報道によれば、npm は issue_comment イベント経由で発行された トークンを拒否するようにした（既存の pull_request_target の制限に加えて）** （出典2）——**イベントの種類も信頼の条件に関わる。**
    取るべき行動 **①公開に使うワークフローを専用のファイルに分け、 そのファイルが何をするかを最小にする。** **②公開を起動できるイベントを限定する （手動実行・タグの作成など。コメントや外部からの入力で動かさない）。** **③環境（environment）の承認を組み合わせ、 ワークフロー名だけが条件にならないようにする。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 自社が公開している npm パッケージで Trusted Publishing を設定しており、そのバインディングからまだ公開していないものがある
委託・第三者部品□ バインディングに書かれたリポジトリを、改名・移管・削除したことがある
認証・認可□ 外部サービスとの信頼関係を、名前（リポジトリ名・組織名・ドメイン名）で結んでいる
運用・監視□ 依存の更新を自動で取り込み、導入時スクリプトの実行を止めていない
運用・監視□ AI コーディングエージェントが、人の確認なしにパッケージを導入できる
体制・契約□ 供給網の検査が「署名・来歴の有無」で合否を決めている
