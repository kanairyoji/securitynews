INC-2026-0496Ivanti ICS ゼロデイ3連鎖で root 奪取

Volexity は2026年10月13日、完全にパッチ適用済み（22.8R2.4 Build 19097）の Ivanti Connect Secure VPN 装置が、認証回避・ファイル書き込み・権限昇格の 3つのゼロデイを連鎖させる手口で未認証のまま root を取られていたと公表した—— 攻撃者 UTA0576 は Web シェルもマルウェアも置かず、コマンドのたびに連鎖全体を 再実行して結果を HTTPS の応答で受け取り、Ivanti のデバッグログと Linux の 監査ログから痕跡を消していたため、Ivanti の Integrity Checker Tool では 検出できない。Ivanti は同日に認証回避と遠隔コード実行を CVE-2026-104935 として 修正し、CISA は同日 KEV へ追加して連邦機関の期限を10月16日に設定したが、 権限昇格の修正は本記録の作成時点で未提供である

脆弱性不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）未知の脆弱性の悪用設計・実装上の不備
初報: 2026年10月13日（Ivanti のアドバイザリと Volexity の分析公表） 最終更新: 2026年11月1日（追加2件の修正版が提供されたことと、CISA の KEV 追加の反映）

「最新版にしてあります」が、この事案では防御になっていません。

Volexity は2026年10月13日、同社のネットワーク監視サービスの顧客で、完全にパッチが適用された Ivanti Connect Secure（ICS）VPN 装置が侵害されていたと公表しました（出典1）。バージョンは 22.8R2.4（Build 19097）。調査の結果、攻撃者は3つの未修正の脆弱性を連鎖させ、認証を経ずに root 権限でコマンドを実行していました。

連鎖は次の3段です（出典1）。

段 内容
認証回避 公開スクリプト welcome.cgi へのリクエストに X-DSCGI-PATH ヘッダを付け、認証が要る wu.cgi へ処理を回す
遠隔コード実行 wu.cgi のアップロード処理が ZIP 検証の前にファイルを書く隙を使い、削除されるまでの数十ミリ秒に Perl スクリプトを実行する（競合状態）
権限昇格 メモリ上の libdsplibs.so にパッチを当てて設定ストア DSCache を書き換え、特権デーモン dsinvoked に Perl を root で起動させる

Ivanti は認証回避と遠隔コード実行を CVE-2026-104935 として2026年10月13日に修正しました。権限昇格の修正は「今後数週間のうちのリリースに含める」とされ、本記録の作成時点では提供されていません（出典1）。

この事案で最も重いのは、痕跡が残らない作り方です。 攻撃者 UTA0576 は Web シェルもバックドアも置かず、コマンドを1つ実行するたびに連鎖全体を再実行し、結果を HTTPS の応答で受け取っていました（出典1）。ディスク上のライブラリは書き換えず、メモリ上のパッチと DSCache の変更は使い終わると元に戻します。 その結果、Ivanti が配布する Integrity Checker Tool（ICT）は何も検出しません——「ICT が綺麗だから無事」とは言えない（出典1）。さらに /home/runtime/dlogs/debuglog と /var/log/audit/audit.log から該当時刻のエントリが削除されていました。

攻撃後の行動は、VPN 装置の先にある Active Directory に向いていました（出典1）。装置に保存された LDAP 用のドメイン認証情報を抜き、その資格で内部のドメインコントローラへ問い合わせ、LAPS のローカル管理者パスワードと BitLocker の回復キー、userPassword 属性を探していました。 自作の Kerberos ツールで Kerberoast と認証情報の検証を行い、パスワードスプレーも実行しています。 装置上の LDAP 通信をパケットキャプチャして平文の認証情報を集める動きもありました。

CISA は同日 CVE-2026-104935 を KEV（悪用が確認された脆弱性カタログ）に追加し、連邦民生機関の対応期限を2026年10月16日——登録から3日後——に設定しました（出典2）。Shadowserver が観測しているインターネット露出中の ICS は5,500台を超えます（出典4）。

帰属は確定していません。 Volexity は「標的の性質から、UTA0576 は諜報ではなく犯罪目的であると低い確度で評価する」と述べています（出典1。原文英語。本記録の訳）。また「2026年に調査した他の攻撃者と同様、UTA0576 はエクスプロイト開発と攻撃後の作業に大規模言語モデルを使っていると中程度の確度で評価する」とも書いています（出典1。本記録の訳）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**3つの未修正の脆弱性を連鎖させ、認証を経ずに root でコマンドを実行する** （出典1）。 **連鎖は毎回最初から実行され、結果は HTTPS の応答で返る。** **バックドア・Web シェル・外向きの C2 は存在しない。** **ディスク上の改変を残さず、ログからは該当エントリを削除する。**

  1. 1. 初期侵入確認済
    **公開スクリプト `welcome.cgi` へのリクエストに `X-DSCGI-PATH: /home/webserver/htdocs/dana/fb/smb/wu.cgi` を付け、 認証保護下の CGI へ処理を到達させた**（出典1）。 **「URL は許可の判定に使われ、ヘッダのパスは処理の宛先の判定に使われる」 という二重構造がこの回避を成立させている**（出典1。本記録の訳）。
    根拠: Volexity のフォレンジック調査とコアダンプ・メモリ解析による連鎖の再構成（出典1）
  2. 2. 実行確認済
    **`wu.cgi` のアップロード処理へ、拡張子 `.zip` を付けた Perl スクリプトを 送る。処理はクライアントが指定したファイル名の MD5 を計算して `/home/runtime/tmp/<MD5(filename)>` へ内容を書き、 その後に ZIP として妥当かを検査して不正なら削除する**（出典1）。 **書き込みから削除までの隙に、同じヘッダ技法で `X-DSCGI-PATH: /home/runtime/tmp/<MD5(filename)>` を指定した 実行リクエストを並列に多数送り、競合状態に勝つ**（出典1）。 **実行されたのは Perl スクリプトで、そこから Bash、さらに Python が動く。** **Python は Base64・zlib で符号化されて渡され `exec()` で実行されるため、 素のスクリプトはメモリ上にしか存在しない**（出典1）。
    根拠: Volexity による `wu.cgi` の処理順序とリクエスト列の再構成（出典1）
  3. 3. 権限昇格確認済
    **`cgi-server` 権限で動くプロセスのメモリ上の `libdsplibs.so` に パッチを当て、共有設定ストア DSCache を書き換えられる状態にする。 既存の保守タスクの起動対象を正規のスクリプトから Perl インタプリタへ 差し替え、特権デーモン `dsinvoked` にそのタスクの実行を依頼して 悪性の Perl スクリプトを引数として渡す。 `dsinvoked` はこれを root で実行する**（出典1）。 **成功の確認には `/etc/shadow` が読めるかどうかを使っていた**（出典1）。 **【2026年11月1日に追記】この段の脆弱性は CVE-2026-111357 である** ——**NVD の記述「特権デーモン dsinvoked が DSCache の設定データを 信頼する扱いを誤っており、root への権限昇格に至る」が 上の記述と一致する**（出典13・本記録の判断）。 **CVSS 3.1 は 7.0（AV:L/AC:H/PR:L）。 CISA は2026年10月30日に KEV へ追加し、期限を2026年11月2日に設定した**（出典11）。
    根拠: メモリイメージとコアダンプの解析（Volexity Volcano。出典1）／CVE-2026-111357 の記述との一致（出典13）
  4. 4. 検知回避確認済
    **権限昇格の後、エクスプロイトスクリプトは メモリ上の DSCache エントリと `libdsplibs.so` を 悪用前の状態へ復元する**（出典1）。 **続いて `/home/runtime/dlogs/debuglog` と `/var/log/audit/audit.log` から悪用に関するエントリを削除し、 ファイルを書き直す**（出典1）。 **実行に使ったスクリプトと一時ファイルは自己削除し、 バックグラウンド処理の出力は `/dev/null` へ捨てる。** **パケットキャプチャには tcpdump を `dsstatmond` にリネームしたものを使い、 8本のファイルをローテーションさせて古い記録を上書きする**（出典1）。 **結果として Ivanti の Integrity Checker Tool は変更を検出しない**（出典1）。
    根拠: ログの書き換え痕とスクリプトの復元処理の解析（出典1）
  5. 5. 認証情報アクセス確認済
    **装置に保存されていた認証情報（LDAP 連携に使うドメイン認証情報）を抽出した** （出典1）。 **さらに装置の Active Directory サービスアカウントの資格で 内部のドメインコントローラへ LDAP 認証し、 LAPS のローカル管理者パスワード・BitLocker の回復情報・ `userPassword` と `unixUserPassword` を持つ属性・ ログオンスクリプトのパスワードを探索した**（出典1）。 **自作の Kerberos 実装（`/tmp/mk.py`）には Kerberoast 機能があり、 認証情報の検証には `/tmp/rr.py` を、 パスワードスプレーには `sp_run.py` を用いた**（出典1）。 **装置上の LDAP 通信のパケットキャプチャ（`/data/.icscap/cap0`）を `h.py` で解析し、平文の LDAP 認証情報・HTTP Basic 認証情報・ NTLM のチャレンジレスポンスの収集を試みた**（出典1）。
    根拠: ツール群（`/tmp/ml.py`・`/tmp/rq5.py`・`/tmp/mk.py`・`/tmp/rr.py`・`h.py`・`sp_run.py`）の解析（出典1）
  6. 6. 内部探索確認済
    **`/etc/resolv.conf` を取得して内部ドメインの名前解決を行い、 ローカルの DNS とホストの偵察を実施した**（出典1）。 **装置の構成データ（認証方式を含む）を収集し、 認証ログを解析して有効な利用者名を `/tmp/pu.txt` に書き出した**（出典1）。
    根拠: 実行されたコマンドと生成ファイルの解析（出典1）
  7. 7. 持ち出し推定
    **Active Directory への問い合わせ結果を `/tmp/` の JSON に書き出し、 zlib 圧縮と Base64 符号化を施して、 エクスプロイト連鎖の HTTPS 応答で送出した**（出典1）。 **「ファイル名・コマンド・後片付けの行動にもとづき、 Volexity は UTA0576 が標的の Active Directory から照会できる情報を 持ち出したと高い確度で評価する」**（出典1。原文英語。本記録の訳）。 **持ち出された情報の量・件数は公表されていない**（本記録の明示）。
    根拠: ファイル名・コマンド・後片付けの痕跡（出典1）
  8. 8. 影響（暗号化・破壊・改ざん）推定
    **装置上で root 権限のコマンド実行が成立し、 ドメイン認証情報と Active Directory の情報が取得された**（出典1）。 **暗号化・破壊・改ざんは行われていない。** **「作戦は、攻撃者の最終目的が明らかになる前に検知・阻止された」** （出典5。原文英語。本記録の訳）。 **Volexity は「行動は横展開とネットワーク全体の侵害の準備を 指し示していたと高い確度で評価する」としている**（出典1・5）。
    根拠: Volexity の評価（出典1・5）

Integrity Checker Tool は何も出さない——「ツールが綺麗だから無事」が成り立たない形だった発覚の端緒

Ivanti は、ディスク上の予期しないファイル変更を見つけるためのIntegrity Checker Tool（ICT）を配布しています。Ivanti 自身もアドバイザリで「ICT を定期的に実行すること」を推奨しています（出典4）。

しかし Volexity は、この連鎖では ICT が何も検出しないと明記しました。 「この攻撃の連鎖はライブラリのコードをメモリ上でのみパッチし、設定ストアのデータを復元するため、ツールはいかなる変更も検出しない。したがって、悪用の証拠を特定するにはフォレンジック調査が必要である」（出典1。原文英語。本記録の訳）。

ログも消されていました（出典1）。削除の対象は次の2つです。

  • /home/runtime/dlogs/debuglog（Ivanti のランタイムログ）
  • /var/log/audit/audit.log（Linux の監査ログ）

さらに、実行に使ったスクリプトと一時ファイルは自己削除し、バックグラウンド処理の出力は /dev/null に捨て、パケットキャプチャには dsstatmond という名前に変えた tcpdump を使って8本のファイルをローテーションさせていました（古いものは上書きされます。出典1）。

ここから読み取るべきことは1つです。 装置の上で装置自身が出すログと検査ツールだけを根拠にすると、この種の侵害は「無かった」と判定されます（本記録の評価）。Volexity が再構成できたのは、外部のネットワーク監視で先に気づき、メモリとディスクのイメージとコアダンプを採って解析したからです（出典1）。

狙いは VPN 装置ではなく、その先の Active Directory——LAPS と BitLocker の鍵を探していた被害規模・影響範囲

攻撃後の行動は、装置の中にとどまっていません（出典1）。

  1. 装置に保存された認証情報の抜き取り——LDAP 連携に使うドメイン認証情報。
  2. Active Directory への問い合わせ——結果を /tmp/ の JSON に書き出し、zlib 圧縮と Base64 で符号化して、エクスプロイトの経路で送出。
  3. 高価値属性の探索——自作の LDAPv3 ツール（/tmp/ml.py・/tmp/rq5.py）で、LAPS のローカル管理者パスワード・BitLocker の回復情報・userPassword と unixUserPassword を持つ属性・ログオンスクリプトのパスワード。
  4. 自作 Kerberos ツール（/tmp/mk.py）——Kerberoast 機能つき。認証情報の検証は /tmp/rr.py。
  5. パスワードスプレー（sp_run.py。結果は sp_out.txt・spray_hits.json）。
  6. LDAP 通信のパケットキャプチャの解析（h.py）——/data/.icscap/cap0 から平文の LDAP 認証情報・HTTP Basic 認証情報・NTLM のチャレンジレスポンスを収集。
  7. 設定と認証ログの偵察——/home/etc/pulse/ の設定ファイル、認証ログから有効な利用者名を抽出して /tmp/pu.txt へ。

LAPS と BitLocker 回復キーが標的だったことの意味は、はっきりしています（本記録の評価）。LAPS はローカル管理者パスワードを端末ごとにばらして AD に預ける仕組みで、BitLocker の回復キーも AD に置けます。 どちらも「AD を守る」前提で成立する設計であり、AD へ到達できる資格が1つあれば、端末の管理者権限とディスクの復号がまとめて手に入ります。

なお Volexity は、LDAP パケットキャプチャの手口が別の攻撃者 UTA0533 が SonicWall SMA で用いたものと類似すると指摘しています（出典1）。

C2 を置かない——コマンドごとに連鎖を再実行し、結果は HTTPS の応答で返っていた評価・解釈

「UTA0576 は、別個のコマンド＆コントロール（C2）チャネルではなく、エクスプロイト連鎖の HTTPS リクエストを通じてコマンドと結果を受け渡しており、侵害された装置にバックドアや Web シェルは配置しなかった」（出典1。原文英語。本記録の訳）。

コマンド1つごとに、連鎖の全体（認証回避 → RCE → 権限昇格）が最初から実行されます（出典1）。実行する Python スクリプトは Base64 と zlib で符号化され、復号・展開して exec() に渡されるため、素のスクリプトはメモリ上にしか存在しません。

これは防御側の前提を2つ崩します（本記録の評価）。

  • 「永続化を探す」が効かない。 置かれたファイル・サービス・cron を探す調査は空振りします。残るのは、再侵入のたびに発生するHTTPS リクエストのパターンだけです。
  • 「C2 通信の宛先を遮断する」が効かない。 外向きのビーコンが無く、通信は攻撃者が開始する内向きの HTTPS です。出口側の遮断・DNS シンクホールは経路に触れません。

Volexity が示した検知の着眼は、この構造に対応しています（出典1）。/dana-na/auth/url_default/welcome.cgi への大量のリクエストを監視し、とくに X-DSCGI-PATH ヘッダの値が URL のパスと一致しない場合に注意する——つまり「許可の判定に使われる名前」と「処理の宛先の名前」が食い違うリクエストを探すわけです。

    取るべき行動 **①VPN 装置の syslog 転送を有効にし、転送先を装置から書き換えられない場所 （追記専用の保管・別系統の権限）に置く。** **②転送が実際に動いているかを、装置側のログ件数と 転送先の件数を突き合わせて月次で確認する。** **③ログの連続性の欠落（時刻の飛び）を検知する規則を作る。**
  • **ドメイン側で「VPN 装置のサービスアカウントの振る舞い」を基準線にして監視する**
    **攻撃者は装置の AD サービスアカウントの資格で ドメインコントローラへ LDAP 認証し、 LAPS・BitLocker・`userPassword` 属性を探索した**（出典1）。 **通信経路としては正規であり、装置側からは異常に見えない。** **一方でドメイン側から見れば、 「認証連携のためのアカウントが属性探索を始めた」という逸脱である**（本記録の評価）。
    取るべき行動 **①VPN 装置のサービスアカウントが通常行う LDAP 操作 （バインドと特定属性の参照）を列挙し、基準線として記録する。** **②基準線の外の操作——LAPS 属性・`msFVE-RecoveryInformation`・ `userPassword` の参照、広範な列挙——を検知対象にする。** **③同アカウントによる Kerberos のサービスチケット要求と 失敗認証の急増（パスワードスプレー）を併せて見る。**
  • **侵害調査の起点を「装置の中」ではなく「装置の前後」に置く**
    **本件で最初に気づいたのは外部のネットワーク監視であり、 端緒は VPN 装置を起点とする横展開の試みだった**（出典1）。 **装置内部の検査ツールとログは、どちらも攻撃者の手が届く範囲にあった**（出典1）。
    取るべき行動 **①VPN 装置の内側のセグメントで、装置を送信元とする通信を ドメインコントローラ・ファイルサーバ・端末向けに分けて記録する。** **②`welcome.cgi` への小さなリクエストに対して 不釣り合いに大きな応答が返っている組を探す （持ち出しが応答に載る形のため）。** **③`/tmp/` 配下の痕跡（`ml.py`・`rq5.py`・`mk.py`・`rr.py`・ `pu.txt`・`sp_out.txt`・`spray_hits.json`）を確認する**（出典1）。
  • **「C2 が無い」攻撃者を想定した検知を1つは持つ**
    **UTA0576 はバックドアも Web シェルも置かず、 コマンドのたびに連鎖を再実行して結果を HTTPS の応答で受け取った**（出典1）。 **外向きのビーコンが存在しないため、 宛先の遮断・DNS シンクホール・C2 の脅威情報が経路に触れない**（本記録の評価）。
    取るべき行動 **①検知の仮説を「ビーコンを探す」から 「正規の入口への異常なリクエスト列を探す」へ1本追加する。** **②境界装置の HTTPS リクエストについて、 同一の送信元から短時間に並列の実行リクエストが来る形 （競合状態を狙う形）を検知する規則を作る。** **③脅威ハンティングの前提を「永続化を探す」から 「再侵入の繰り返しを探す」へ変える。**

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ インターネットに露出した SSL-VPN / リモートアクセスのアプライアンスを運用している
