INC-2026-0500Meta の GitHub 侵害で1,500人分流出

Meta は2026年10月13日までに、従業員から盗まれた認証情報で同社の一部 GitHub リポジトリへ外部の集団が侵入し、ソフトウェアコードと約1,500人分の個人データが 持ち出されたとして本人通知を開始した——持ち出されたデータの99%は製品に関する 事業データで、残り1%の個人データは社内方針に反して誤ってリポジトリへ置かれて いたものだった。Meta は製品の脆弱性でも社内システムの侵害でもないとし、 リポジトリ内のシークレットをローテーションしたうえで、 個人データの誤アップロードを検出する走査を追加したと説明している

不正アクセス・侵害意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年10月13日（SecurityWeek の報道） 最終更新: 2026年10月14日

侵入されたのは Meta の社内システムではなく、Meta が GitHub に置いていたリポジトリです。そして個人データが漏れた理由は、侵入とは別のところにありました。

Meta は2026年10月13日（火）、約1,500人に対して個人情報が影響を受けたとする通知を開始しました（出典1）。大半は米国在住の同社従業員です。侵入は「数週間前」に検知され、外部の集団が従業員から盗まれた認証情報を使って同社の一部の GitHub リポジトリへアクセスしていました（出典1）。

持ち出されたデータの内訳について、Meta は SecurityWeek に対し「99% が事業データ（一部製品に関するソフトウェアコード）で、残り1% が個人データ」と説明しています（出典1。本記録の訳）。

この1% の由来が、この事案の要点です。 Meta は、その個人データは誤ってリポジトリに追加されたもので、本来そこにあってはならず、GitHub への保存は社内方針に反していたと述べています（出典1）。つまり、侵入を防げなかったことと、個人データが流出したことは、別々の失敗が重なった結果です（本記録の整理）。

さらに Meta は、個人データに見えたもののかなりの部分は合成データまたは匿名化されたテストデータであり、攻撃者が本物の記録とテストデータを容易に見分けられない可能性があるとしています（出典1）。また GitHub との調査にもとづき、攻撃者が Meta のデータを特に狙っていたとは考えていないとしています（出典1）。

対応として Meta は、攻撃者のアクセスを遮断し、GitHub と法執行機関に連絡し、影響を受けたリポジトリ内で見つかったシークレットをローテーションしました。加えて、個人データを GitHub に保存させない新たな統制と、誤ってアップロードされた利用者データを検出する能動的な走査を導入しています（出典1）。規制当局への通知も行い、対象者にはクレジットモニタリングとダークウェブ監視サービスを提供しています（出典1）。

本記録は、Meta 自身の公表文書に到達できていません〈齟齬1〉。ここに書いた事実はすべて、SecurityWeek が Meta 広報から得た声明と同社の取材にもとづくものです。

侵入は認証情報1つから——「Meta の製品にも社内システムにも穴は無かった」という形の事案だった原因・手口

Meta 広報の説明は、どこが破れたのかを明確に切り分けています。

「これは Meta のいかなる製品の脆弱性でもなく、Meta の社内システムが侵害されたのでもない。GitHub リポジトリに保持されていた Meta の事業データが、従業員の盗まれた認証情報を使って不適切にアクセスされた——そこには限られた人数の少量の個人データが含まれており、その大半は Meta の従業員だった」（出典1。原文英語。本記録の訳）

破れたのは、外部の SaaS に置いた資産に対する認証の一点です（本記録の整理）。ソースコードを GitHub に置くこと自体は広く行われている運用であり、本件もそこが問題なのではありません。 問題は、そこへの到達が従業員の認証情報1つで成立したことです（本記録の評価）。

なお、認証情報がどのように盗まれたか——フィッシングか、端末に入り込んだインフォスティーラーか、使い回しか——は公表されていません〈未確定4〉。多要素認証の有無と、それがどう回避されたかについても記述がありません。 読者が「自社の同じ入口」を点検するうえで最も要る情報が、公表資料には無い（本記録の評価）。

個人データが漏れた原因は侵入ではなく、「置いてはいけない場所に置いてあった」ことだった被害規模・影響範囲

持ち出されたデータの99% は事業データ（一部製品のソフトウェアコード）で、残り1% が個人データでした（出典1）。

Meta は、この個人データについて次のように説明しています（出典1。本記録の訳）。

  • 誤ってリポジトリに追加されたものであり、本来そこにあるべきではなかった
  • GitHub に保存することは社内方針に反していた
  • 個人データに見えたもののかなりの部分は、合成データまたは匿名化されたテストデータだった
  • そのため攻撃者は、本物の記録とテストデータを容易に見分けられない可能性がある

ここに2つの独立した失敗があります（本記録の整理）。①認証情報が盗まれ、リポジトリへの到達を許したこと。②そのリポジトリに、方針上あってはならない個人データが置かれていたこと。 ①だけなら失われたのはコードだけで、本人通知も当局通知も不要でした。

最後の「テストデータと見分けられない」という説明は、被害の見積もりを難しくする向きにも働きます（本記録の評価）。攻撃者が見分けられないということは、防御側も「この1,500人のうち実在データが何人分か」を攻撃者視点で確定できないということです。 Meta が約1,500人全員に通知し、クレジットモニタリングとダークウェブ監視を提供しているのは、その不確実性を人数の側に寄せて処理した判断と読めます（本記録の評価）。

ソースコードに対するシークレット走査（secret scanning）はGitHub が標準機能として提供しているもので、新しい技術ではありません。 それでも「ローテーションすべきシークレットが見つかった」ということは、走査が全リポジトリに効いていなかったか、検出後の是正が終わっていなかったかのどちらかです（本記録の評価。Meta はいずれとも述べていない）。

より示唆的なのは「個人データの能動的走査」を事後に追加した点です。 シークレット走査と違い、個人データの混入検査は既定で動く機能ではなく、自前で設計して回すものです（本記録の評価）。「方針で禁止している」ことと「禁止が守られていることを機械で確かめている」ことの差が、この事案では1,500人分の通知になりました。

日本の読者にとっての距離——米国の雇用主側の事案だが、構図は国内の開発現場にそのままある評価・解釈

本件は米国の事案であり、日本の組織が当事者ではありません。 それでも本DBに記録する理由は、構図が国内の開発現場と同じだからです（本記録の評価）。

第一に、ソースコード管理を外部 SaaS に置く運用は国内でも一般的です。 自社の「社内システム」の堅牢さとは独立に、SaaS 側のアカウントが1つ破れれば同じことが起きます。

第二に、「テストデータのつもりで本番データを入れてしまう」ことは、規模を問わず起きます。 Meta の説明では、合成・匿名化データと実データが同じリポジトリに混在していました（出典1）。混在しているかぎり、攻撃者にも防御側にも区別は付きません。

第三に、日本では個人情報保護法上、漏えい等が生じた場合の個人情報保護委員会への報告と本人通知が求められる場面があります（本記録の一般的整理であり、本件への適用を述べるものではない）。「どの個人データがどこにあるか」を把握していない状態では、報告の要否も通知の範囲も決められません（本記録の評価）。

CISO・経営層への示唆
  • **「社内システムは無事」は、報告の結論にならない。資産は社外にもある**
    **Meta の説明は「社内システムは侵害されていない」で始まる**（出典1）。 **それは事実だが、ソースコードと1,500人分の個人データは出ている**（出典1）。 **守る対象の所在が社内ネットワークの外（SaaS）へ移っているのに、 報告の枠組みが「社内／社外」のままだと、 起きたことの重さが伝わらない**（本記録の評価）。
    取るべき行動 **①ソースコード・設計書・顧客データを置いている外部 SaaS を一覧にし、 それぞれについて「この SaaS のアカウントが1つ乗っ取られたら何が出るか」を書き出す。** **②取締役会・リスク委員会への報告で、 インシデントの分類を「社内／社外」ではなく「失われる資産」で立てる。** **③SaaS 側の監査ログを自社で保持しているかを、SaaS ごとに確認する。**
  • **規程の存在と、規程が守られていることの検証は、別々に予算を要する**
    **Meta には「個人データを GitHub に置かない」という方針が 既にあった**（出典1）。 **それでも置かれていた。** **事後に追加されたのは方針ではなく、検出の走査である**（出典1）。 **「決めた」と「守られている」の間を埋めるのは機械の検査であり、 それ自体が工数と運用を要する**（本記録の評価）。
    取るべき行動 **①自社の情報取扱規程のうち、「置いてはいけない場所」を定めた条項を抜き出す。** **②各条項について「違反を検出する仕組みがあるか／誰が結果を見るか」を列に書く。** **③仕組みが無い条項を一覧にし、 違反が起きたときの最大影響の大きい順に手当ての予算を付ける。**
  • **本人通知の範囲を「実在データの人数」で絞れない事態を想定しておく**
    **Meta は、合成・匿名化データと実データが混在しており 攻撃者が区別できない可能性があるとしている**（出典1）。 **防御側にとっても同じであり、 結果として約1,500人全員への通知になった**（出典1。後段は本記録の整理）。 **通知費用とモニタリング提供の費用は、 混在の度合いに比例して膨らむ**（本記録の評価）。
    取るべき行動 **①インシデント対応の費用見積もりに「影響範囲が絞れない場合」の 上振れシナリオを入れる（通知・コールセンター・モニタリング提供）。** **②テスト環境・リポジトリに実データを入れない運用を、 費用の話として開発部門に説明する。** **③日本では個人情報保護委員会への報告期限（速報・確報）があるため、 「範囲未確定のまま報告する」場合の社内手順を決めておく。**
  • **外部プラットフォームの事業者を、調査の当事者として契約段階から織り込む**
    **Meta は検知後に GitHub を調査へ引き入れ、 「リポジトリを保護する追加措置」を共同で講じている**（出典1）。 **SaaS 内部の挙動は、利用者側のログだけでは再構成できない**（本記録の評価）。
    取るべき行動 **①主要 SaaS について、インシデント時にログ提供・共同調査を 要請できる契約条項と窓口を確認する。** **②要請から提供までの想定日数を、契約更新時に明記させる。** **③確認結果を、SaaS の重要度順に台帳として残す。**
セキュリティ技術者への示唆
  • **リポジトリの「秘密」は、鍵だけでなく個人データも対象にする**
    **シークレット走査は広く導入されているが、 本件で流出したのはテストデータに紛れた個人データである**（出典1）。 **Meta が事後に追加したのも、個人データの検出走査だった**（出典1）。
    取るべき行動 **①CI に個人データ検出（氏名・メール・電話番号・マイナンバー等の パターン照合）を組み込み、まず検出のみ（ブロックしない）で回して 誤検知率を測る。** **②既存リポジトリの全履歴を一度走査する （削除しても git の履歴には残るため、history も対象にする）。** **③検出時の消し方（履歴の書き換え・リポジトリの作り直し）を 手順として事前に書いておく。**
  • **テストデータは「本番から持ってきて匿名化する」より「生成する」ほうが安い**
    **本件では合成・匿名化データと実データが混在していた**（出典1）。 **匿名化は元データを一度持ち込む工程を含むため、 混入の機会が構造的に残る**（本記録の評価）。
    取るべき行動 **①テストデータの作り方を調べ、 「本番コピー＋マスク」で作っているデータセットを一覧にする。** **②そのうち、生成（フェイカー等）に置き換えられるものを選ぶ。** **③置き換えられないもの（本番同等の分布が要る性能試験など）は、 置き場所をリポジトリの外（アクセス制御付きのストレージ）へ移す。**
  • **GitHub の監査ログを自社側に取り込み、clone の異常を見る**
    **本件の持ち出しは GitHub の正規経路で完結しており、 自社ネットワークのプロキシ・DLP には現れない**（本記録の評価）。 **Meta がどう検知したかは公表されていない**（出典1）。
    取るべき行動 **①GitHub（または利用中のコード基盤）の audit log / git events を SIEM へ転送する。** **②「普段と違う接続元からの clone」「短時間に多数のリポジトリへの clone」 「業務時間外の一括取得」を検知条件として作る。** **③まず30日間、閾値を決めずに分布を測ってから条件を定める。**
  • **人のアカウント以外（PAT・デプロイキー・GitHub App）の棚卸しを同時に行う**
    **本件の入口は従業員の認証情報だったが**（出典1）、 **多要素認証を必須化しても、 個人アクセストークンや連携アプリは別経路として残る**（本記録の評価）。
    取るべき行動 **①組織配下の PAT・デプロイキー・OAuth アプリ・GitHub App を列挙し、 最終使用日と権限の広さで並べる。** **②90日以上使われていないものを失効させる。** **③残すものには有効期限を設定し、更新の担当者を明記する。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ ソースコードや設計資料を外部の SaaS（GitHub / GitLab / Bitbucket 等）に置いている
認証・認可□ コード基盤のアカウントに、フィッシング耐性のある多要素認証を必須化していない（または例外アカウントが残っている）
データの保持□ テストデータを本番データから作っている、または実データとダミーデータが同じリポジトリに混在している
運用・監視□ リポジトリに対するシークレット走査・個人データ走査を、全リポジトリの全履歴に対して回していない
運用・監視□ コード基盤の監査ログを自社の SIEM に取り込んでいない
体制・契約□ 「置いてはいけないデータ」を規程で定めているが、違反の検出を機械で行っていない
