INC-2026-0501SiteGuard SE にOSコマンド注入・悪用済み

JPCERT/CC と IPA は2026年10月14日、EGセキュアソリューションズのホスト型WAF 「SiteGuard Server Edition」の統計機能に OS コマンドインジェクションの脆弱性 （CVE-2026-106931・CVSS v4.0 基本値8.5・緊急）があると公表した—— 製品が動くサーバ上で root または SYSTEM 権限の任意コマンド実行に至る可能性があり、 開発者は自社サイトで「すでに悪用が確認されています」と明記して、 アップデートの前に管理画面から「診断情報」を保管する（攻撃の痕跡が消えるため）よう 求めている。サポート契約者には2026年9月29日に個別通知済みだった

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月14日（JVN#88474777 の公開） 最終更新: 2026年10月14日

WAF 自体が、侵入の足がかりになりました。

2026年10月14日、JPCERT/CC と IPA は JVN#88474777 を公開し、EGセキュアソリューションズが提供するホスト型WAF「SiteGuard Server Edition」の統計機能にOS コマンドインジェクションの脆弱性があると公表しました（出典1）。深刻度は「緊急」、CVE-2026-106931、CVSS v4.0 基本値 8.5（v3.0 で 7.8）です（出典1）。

成立すると、製品が動作するサーバ上で root または SYSTEM 権限で任意の OS コマンドが実行されます（出典1・2）。SiteGuard Server Edition は Web サーバに組み込んで使うホスト型WAF であり、守る対象と同じサーバの上で動きます（出典1）。つまり、WAF が落ちることは Web サーバそのものが最上位の権限で落ちることと同義です（本記録の評価）。

本記録が開発者のお知らせを直接取得して確認した、報道・JVN 本文の要約には現れにくい2点があります（出典2）。

  • 「すでに悪用が確認されています」と開発者自身が明記している（出典2。出典1 にも同旨の一文がある）
  • 「アップデートの前に必ず『診断情報』をダウンロードして保管してください（攻撃の痕跡が消える可能性があります）」と求めている（出典2）

2つ目は、対応の順序に関わります（本記録の評価）。先にアップデートしてしまうと、既に侵害されていた場合の証拠が失われる可能性がある、と開発者が述べているということです。

影響を受けるのは Ver2.20 以降で統計機能が有効なもの（初期値は有効）です（出典1・2）。修正版は Apache版・Nginx版・IIS版が Ver8.00 Update5、FreeBSD Apache版・Nginx版が Ver7.00 Update6。バージョンアップが困難な利用者向けに、統計処理の対象ファイルを差し替える個別パッチがサポート終了版を含めて提供されています（出典1・2）。なお開発者は、直接サポート契約のある利用者へ2026年9月29日に先行して通知していました（出典1・2）。

守るために入れた WAF が、root 権限の実行経路になった原因・手口

SiteGuard Server Edition は、Web サーバ（Apache / Nginx / IIS）に組み込んで使うホスト型の WAF です（出典1）。ネットワーク上の別装置ではなく、守る対象と同じサーバの上で、Web サーバのプロセスと並んで動きます。

今回の脆弱性があるのは、その統計機能です（出典1・2）。成立すると、root または SYSTEM 権限で任意の OS コマンドが実行されます（出典1）。WAF が特権で動くのは、ログの書き込みや設定の読み取りのために必要だからですが、その特権がそのまま攻撃者の取り分になります（本記録の評価）。

統計機能は初期値で有効です（出典1・2）。「使っていないから無効のはず」という推定は成り立ちません——明示的に無効化していないかぎり、有効です（本記録の整理）。

対象は Ver2.20 以降。ただし IIS版の Ver3.10 から Ver4.00 Update4 は影響を受けません（出典1・2）。この例外は、該当期間の IIS版で統計機能の実装が異なっていたことを示唆しますが、理由は公表されていません（本記録の推測）。

「すでに悪用が確認されています」——公表の時点で、これは予防ではなく対処の話になっていた被害規模・影響範囲

開発者のお知らせは、冒頭で次のように述べています（出典2）。

「SiteGuard Server Edition の統計機能に、OSコマンドインジェクションの脆弱性（CVE-2026-106931）が見つかりました。すでに悪用が確認されています。」（出典2）

JVN の本文にも「なお、本脆弱性の悪用が確認されています。」という一文があります（出典1）。

ただし、それ以上の情報はありません（本記録の整理）。何件なのか、いつからなのか、誰が確認したのか、どのような被害が出たのか——いずれも示されていません〈未確定1〉。侵害の有無を確かめるための指標（通信先・ファイル名・ログの特徴）も公表されていません。

ここで CVSS のベクトルを読む意味が出てきます（本記録の評価）。AV:L（ローカル）・PR:L（低権限が必要）——この脆弱性は、インターネットから直接叩けるものではありません。 悪用が確認されているということは、攻撃者が「既にそのサーバ上で低権限のコマンド実行ができる状態」を先に作っているということです（本記録の整理）。

つまり本件は、単独の初期侵入の手段ではなく、侵入後に root を取るための踏み台として使われている可能性が高い（本記録の評価。開発者・JPCERT/CC はそう述べていない）。この読みが正しければ、本件の脆弱性を潰しても、その前段の侵入口は残ります。

アップデートの前に「診断情報」を取る——開発者が示した手順の順序には意味がある組織の対応

開発者のお知らせには、対応手順の前に次の注意があります（出典2）。

「アップデートの前に必ず：『診断情報』をダウンロードして保管してください（攻撃の痕跡が消える可能性があります）」（出典2）

この一文は、JVN 側には記載がありません（出典1。本記録の確認）。開発者のお知らせを直接読まなければ到達しない情報です。

意味するところは明確です（本記録の評価）。①既に侵害されているサーバが実在しうる。②アップデート作業がその証拠を消しうる。③したがって、証拠保全を修正適用より先に置く。

一般に、緊急の脆弱性対応では「まず塞ぐ」が優先されます。 本件で開発者が逆の順序を明示したのは、悪用が既に確認されているからです（本記録の整理）。

実務上の手順としては次の順になります（本記録の整理。出典2 にもとづく）。

  1. 管理画面から「診断情報」をダウンロードして、別の場所に保管する
  2. Web サーバ・OS 側のログ（アクセスログ・認証ログ・シェル履歴）も併せて退避する（本記録の追加）
  3. 修正版へのアップデート、または個別パッチの適用
  4. 保管した診断情報とログを突き合わせ、侵害の兆候を確認する
  5. 兆候があれば、root 権限を取られた前提で、資格情報の再発行と再構築を検討する（本記録の追加）

4 と 5 を飛ばして 3 だけを行うと、既に侵害されていた場合に「塞いだつもりで中に居られる」状態になります（本記録の評価）。

サポート契約者には15日早く届いていた——契約の有無が、知る時期の差になった評価・解釈

開発者は2026年9月29日に、直接サポート契約のある利用者へ本脆弱性と対策を個別に通知しています（出典1・2）。一般公開は10月14日。差は15日です（本記録の算出）。

この運用自体は、脆弱性の調整開示の実務として一般的です（本記録の整理）。修正版を先に準備し、連絡の付く利用者から適用を進め、一般公開は修正が揃ってから行う——情報セキュリティ早期警戒パートナーシップの枠組みもその形です（出典1）。

ただし、読者が自組織に引き写すべき点が1つあります（本記録の評価）。「サポート契約の有無が、脆弱性を知る時期を決める」ということです。

サポート契約を結んでいない製品、あるいは契約の窓口が退職・異動で切れている製品は、一般公開まで情報が届きません。 本件のように悪用が先行している場合、その15日は小さくありません（本記録の評価）。

なお開発者は、サポート終了版を含めて個別パッチを提供しています（出典1・2）。サポートが切れている＝対策が無い、ではない点は実務上重要です（本記録の整理）。

本記録の限界——悪用の実態について、確認できたのは「確認されている」という一文だけ未確定事項

本記録は2026年10月14日に、JVN（出典1）と開発者のお知らせ（出典2）の両方を直接取得して確認しました。 両方に「悪用が確認されている」旨の記載があることは裏が取れています。

一方で、悪用の実態を示す資料には到達できていません〈齟齬1〉。JPCERT/CC の注意喚起（at 番号付き）としての発出、あるいは観測事例の公表があるかは確認できませんでした。

2026年9月以降、国内では公開 Web システムを狙った不正アクセスが相次いで公表されており、JPCERT/CC・IPA・個人情報保護委員会が相次いで注意喚起を出しています（本記録の一般的な状況整理であり、本件との関連を示す資料は無い）。本件がその一連と関係するかどうかは、公表資料からは判断できません（本記録の明示）。

CISO・経営層への示唆
  • **セキュリティ製品を、脆弱性管理の対象台帳に入れる**
    **本件は WAF そのものの脆弱性であり、 成立すれば root / SYSTEM 権限が取られる**（出典1・2）。 **守りの製品は「対策」の欄に書かれ、 「管理すべき資産」の欄から落ちやすい**（本記録の評価）。
    取るべき行動 **①自社の資産台帳に、WAF・EDR・バックアップ・監視エージェントなど セキュリティ製品そのものが登録されているかを確認する。** **②各製品について、脆弱性情報の受け取り経路 （ベンダー通知・JVN・メーリングリスト）と社内の受信者を明記する。** **③特権で動く製品を一覧にし、「これが乗っ取られたら何が起きるか」を書き出す。**
  • **ベンダーのサポート契約を「障害対応のため」ではなく「脆弱性を早く知るため」の投資として見直す**
    **本件では、サポート契約のある利用者は2026年9月29日に通知を受け、 一般公開は10月14日だった**（出典1・2）。 **差は15日である**（本記録の算出）。 **悪用が既に確認されている脆弱性における15日は小さくない**（本記録の評価）。
    取るべき行動 **①主要なセキュリティ製品・ミドルウェアについて、 サポート契約の有無と、脆弱性の先行通知が含まれるかを棚卸しする。** **②契約があっても窓口担当者が異動・退職で切れていないかを確認する （通知先メールアドレスを個人名ではなく部門の代表アドレスにする）。** **③契約を結んでいない製品について、「一般公開まで知らない」ことを 受け入れるか、契約するかを明示的に決める。**
  • **「悪用が確認されている」と書かれた脆弱性は、適用計画ではなく侵害調査から始める**
    **開発者は「すでに悪用が確認されています」と明記し、 アップデートの前に診断情報を保管するよう求めている**（出典2）。 **これは「既に入られているサーバが実在しうる」という前提の指示である**（本記録の評価）。 **パッチ適用だけを完了報告にすると、侵害が残る。**
    取るべき行動 **①脆弱性対応の社内手順に「悪用確認済みの場合」の分岐を作り、 証拠保全 → 適用 → 侵害調査 の順序を明記する。** **②証拠保全の対象（製品の診断情報・OS のログ・Web のアクセスログ）を 製品ごとに事前に決めておく。** **③侵害が確認された場合の権限リセット範囲 （サーバ上の認証情報・DB 接続情報・API キー）を事前に洗い出す。**
  • **サポート終了版でも対策が出ることがある。「EOL だから無理」で止めない**
    **開発者はバージョンアップが困難な利用者向けに、 サポート終了版を含めて個別パッチを提供している**（出典1・2）。 **EOL を理由に対応を諦める判断は、本件では誤りになる**（本記録の評価）。
    取るべき行動 **①自社で稼働中の EOL 製品を一覧にする。** **②本件のような緊急脆弱性が出た場合に、 開発者へ問い合わせる窓口と手順を事前に確認しておく。** **③問い合わせても対策が無い製品については、 停止・置換の期限を決めてリスク台帳に載せる。**

    取るべき行動 **①稼働中の全サーバで SiteGuard Server Edition のバージョンと 統計機能の有効／無効を実際に確認する（想定で済ませない）。** **②IIS版については Ver3.10〜Ver4.00 Update4 の除外に該当するかを確認する。** **③確認結果を一覧にし、適用の優先順位を付ける。**

    **成立時の権限は root または SYSTEM である**（出典1・2）。 **その権限で到達できる範囲が、そのまま復旧すべき範囲になる**（本記録の評価）。
