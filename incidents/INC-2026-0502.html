INC-2026-0502国内EC狙うSQLi、AI関与疑いの326IP

サイバーセキュリティクラウドは2026年10月9日、マクニカが公開した「重点的に確認する IPアドレス」を起点に自社 WAF の観測データ（2026年9月18日〜10月8日）を分析し、 国内の公開 Web システムに対して約40分間で326のIPアドレスを使い分け1,200件超の アクセスを行う攻撃を複数回確認したと公表した——SQLインジェクションでの認証回避に 失敗すると事前に用意した正規アカウントでログインし、ログイン後の画面で改めて SQLインジェクションを試し、それも通らなければ他利用者のポイント窃取を探るという 切り替えが見られ、同社は AI エージェントまたはそれに近い仕組みの関与を疑うとしつつ、 AI の利用を直接示すログや痕跡は確認していないと明記している

脅威・攻撃キャンペーン不正アクセス・侵害続報が続いている日本の組織が当事者設計・実装上の不備既知の脆弱性の悪用
初報: 2026年10月9日（サイバーセキュリティクラウドのレポート公開） 最終更新: 2026年10月14日

攻撃が、応答を見て手を変えていました。

サイバーセキュリティクラウドは2026年10月9日、マクニカが2026年10月7日に公開した「重点的に確認するIPアドレス」2件を起点に、自社が観測した通信を分析した結果を公表しました（出典1）。観測期間は2026年9月18日から10月8日です（ただし保存ログの範囲は環境により異なり、9月18日〜28日は一部環境のデータに限られます）（出典1）。

観測された攻撃の流れは次のとおりです（出典1）。

  1. SQLインジェクションでログイン認証を回避できるか、情報を抜けるかを試す
  2. 回避できないと分かると、事前に作成していたとみられる正規アカウントでログインする
  3. ログイン後の画面や機能で、改めてSQLインジェクションを試す
  4. それも通らなければ、ポイント制度のあるサイトで他の利用者のポイントを窃取できないか探る
  5. 一通り試すと執拗には攻撃せず引き上げる（同じサイトへの再攻撃は確認されていない）

規模は、約40分間で326のIPアドレスを使い分け、1,200件を超えるアクセスを伴う攻撃が複数回確認された、というものです（出典1）。IPアドレスは異なるのに、リクエスト内で同一の識別子が使い回されていたため、同社は同一の攻撃者によるものと判断しています（出典1）。

使われた手段はサイトごとに異なり、SQLインジェクション自動検査ツール「sqlmap」、コマンドラインツール「curl」、スマートフォンアプリ開発言語 Dart の通信機能などが混在していました。User-Agent も Windows 上のブラウザ・Android 端末・スマートフォンアプリを装うものなど多岐にわたります（出典1）。

同社が AI エージェントの関与を疑う根拠は、「人手では難しい量でありながら、攻撃ツールに典型的な機械的規則性が無く、応答を見て次の手を選んでいるように見える」ことです（出典1）。

ただし同社は、AI の利用を直接示すログや痕跡は確認していないと明記しています。マクニカも同様に、AI の利用を示す痕跡は確認していないとしています（出典1）。本記録は、この留保を外して「AI による攻撃」と書くことはしません（本記録の方針）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公開 Web システムに対し、SQLインジェクションによる認証回避 → 事前に用意した正規アカウントでのログイン → ログイン後のSQLインジェクション → サイトの機能（ポイント）の悪用、と段階的に手を切り替える探索**（出典1）。 **約40分間に326のIPアドレスを使い分け、1,200件超のアクセスを行う**（出典1）。 **一通り試すと執拗には攻撃せず引き上げ、同じサイトへの再攻撃は 確認されていない**（出典1）。

  1. 1. 偵察確認済
    **複数の国内サイトに対して探索を行っている**（出典1）。 **サイトごとに sqlmap・curl・Dart の通信機能と手段を変え、 User-Agent も Windows ブラウザ・Android 端末・ スマートフォンアプリを装うものなど多岐にわたる**（出典1）。 **同社は「標的のサイトや API に合わせて手段を切り替えている可能性」を 示唆している**（出典1）。
    根拠: サイバーセキュリティクラウドの WAF 観測（2026年9月18日〜10月8日。出典1）
  2. 2. 初期侵入確認済
    **SQLインジェクションによってログイン認証を回避できないか、 情報を窃取できないかを試す**（出典1・2）。
    根拠: 観測されたリクエストの内容（出典1）
  3. 3. 認証情報アクセス確認済
    **認証回避に失敗すると、攻撃者が事前に作成していたとみられる 正規アカウントでログインする**（出典1・2）。 **アカウントの作り方（通常の会員登録か、乗っ取りか）は 公表されていない**〈未確定5〉。
    根拠: 観測された一連のリクエスト（出典1）
  4. 4. 内部探索確認済
    **ログイン後の画面や機能で、改めてSQLインジェクションを実行する**（出典1・2）。 **認証を通った先の機能・API を対象にしている**（出典1）。
    根拠: 観測されたリクエストの内容（出典1）
  5. 5. 影響（暗号化・破壊・改ざん）確認済
    **SQLインジェクションが通らない場合、 サイトの機能そのものに狙いを移し、 ポイント制度のあるサイトで他の利用者のポイントを 窃取できないかを探る**（出典1・2）。 **成否は公表されていない**〈未確定1〉。
    根拠: サイバーセキュリティクラウドの観測（出典1）

  • トレードオフ: **「AI の可能性」を掲げれば注目が集まり、 防御側に点検を促す力が強まる。** **一方で、留保が外れて伝わると 「国内で AI による攻撃が確認された」という事実誤認が広がる**（本記録の整理）。
  • トレードオフ: **全件を公開すれば照合の網は広がるが、 正規利用者の遮断や、攻撃者側への「どこまで見えているか」の 開示にもなる**（本記録の整理）。 **2件に絞れば誤遮断は減るが、見落としも増える。**

止められたら手を変える——この攻撃の特徴は規模ではなく「分岐」にあった原因・手口

326のIPアドレス、1,200件超のアクセス、約40分（出典1）。数字は目を引きますが、サイバーセキュリティクラウドが注目しているのはそこではありません（本記録の整理）。

同社が挙げる特徴は2つです（出典1）。

  • 人手による操作とは考えにくい量でありながら、攻撃ツールに典型的な「短時間大量アクセス」や機械的な規則性が見られない
  • 応答に応じて次の手を変えているように見える

手の変え方は具体的に記録されています（出典1）。①SQLインジェクションで認証を回避できるか試す → ②できないと分かると、事前に用意したとみられる正規アカウントでログインする → ③ログイン後の画面や機能で改めてSQLインジェクションを試す → ④それも通らなければ、ポイント制度のあるサイトで他の利用者のポイントを窃取できないか探る → ⑤一通り試すと引き上げる。

②が重要です（本記録の評価）。「認証を破る」ことを諦めて「認証を通る」に切り替えています。 このとき攻撃の舞台は、WAF が主に見ている未認証の入口から、ログイン後の画面と API に移ります。

④はさらに踏み込んでいます。 脆弱性を探すのをやめて、サイトの機能そのもの——ポイントの付与・移動——の設計の甘さを探しています（出典1）。これは脆弱性スキャンではなく、仕様の悪用です（本記録の整理）。

「AI エージェントの関与が疑われる」——両社とも、痕跡は確認していないと明記している帰属

サイバーセキュリティクラウドは、上記の特徴から「AI エージェント、またはそれに近い仕組みが使われている可能性」を指摘しています（出典1・2）。

同時に、次の留保を明記しています（出典1・2）。

「AI の利用を直接示すログや痕跡は確認されておらず、観測された振る舞いに基づく推測である」（出典2 の記述。出典1 にも同旨）

マクニカも、AI の利用を示すログや痕跡は確認していないとしています（出典1）。

本記録は、この留保を外しません（本記録の方針）。「AI による攻撃が国内で確認された」という要約は、両社が書いていないことを書くことになります（本記録の評価）。

では、この推測に意味が無いかというと、そうではありません（本記録の評価）。推測の根拠は「量と不規則性の両立」です。 従来、防御側は「人手＝量が少ないが柔軟」「ツール＝量が多いが規則的」という二分法で攻撃を見分けてきました。 本件の観測は、その二分法に当てはまらない事象が国内の観測網に現れたという報告です（本記録の整理）。これは、AI が使われたかどうかとは独立に、検知の設計を見直す理由になります。

IP 1個あたり平均3.7件——「アクセス数の多いIPを止める」では引っかからない対策・注意喚起

1,200件を326のIPアドレスで割ると、1個あたり平均3.7件です（本記録の算出）。

レートリミットやIPブロックの多くは、「単位時間あたりのアクセス数が閾値を超えたIP」を止める作りです。 1個あたり数件では、その閾値に届きません（本記録の評価）。

サイバーセキュリティクラウドが示す点検の観点は、この性質を踏まえたものになっています（出典1）。

観点 具体的に見るもの
HTTPレスポンスコードの偏り 4xx・5xx が普段より多い時間帯。429 を返したリクエストの内容
レスポンスサイズの違い 認証 API で成功・失敗時の定型サイズと異なる応答、通常ありえない大きさの応答

見るべき軸が「送信元」から「応答」へ移っていることに注目してください（本記録の評価）。送信元を分散されると送信元では捕まりません。一方、攻撃が探索である以上、応答の分布は必ず普段と変わります。

ただし同社は、公開した指標について「正規利用者と重なる可能性があるため、単独で被害を判断しないように」と注意しています（出典1）。指標の照合は出発点であって、前後のリクエストとレスポンスを併せて見る必要があります（出典1）。

ログイン後と、仕様の悪用——WAF の外側に出た攻撃をどう見るか評価・解釈

本件の攻撃が最後に試したのは、「他の利用者のポイントを窃取できないか」でした（出典1）。

これは、いわゆる脆弱性の悪用とは性質が違います（本記録の評価）。ポイントの移動機能が、リクエストに含まれる利用者IDをサーバー側で検証せずに受け入れていれば、それは実装どおりに動いた結果として他人のポイントが動きます。 入力値に不正な文字列は含まれないため、WAF のシグネチャには掛かりません。

サイバーセキュリティクラウド自身が、点検項目として「サーバー側の権限確認」「他利用者のデータを操作できないか」を挙げているのは、この性質によります（出典1）。WAF 事業者が、WAF では防げない範囲を点検項目に挙げている点は読み落とさないほうがよい（本記録の評価）。

攻撃者の側から見ると、この順序は合理的です（本記録の整理）。SQLインジェクション → 正規ログイン → ログイン後のSQLインジェクション →仕様の悪用、という流れは、「防御が厚いところから薄いところへ」降りていく動きです。 一般に、未認証の入口は WAF と脆弱性診断の両方で見られていますが、ログイン後の機能と API の認可は、どちらの網にも掛かりにくい（本記録の評価）。

    **本件の攻撃は、認証回避に失敗すると正規アカウントでログインし、 ログイン後の機能とポイント制度を狙っている**（出典1・2）。 **ポイントの不正操作は、不正な入力文字列を伴わないため WAF のシグネチャには掛からない**（本記録の評価）。 **WAF 事業者自身が点検項目に「サーバー側の権限確認」を 挙げている**（出典1）。

セキュリティ技術者への示唆
  • **検知の軸を「送信元」から「応答」へ足す。IP 1個あたり平均3.7件では止まらない**
    **1,200件 ÷ 326IP ≒ 3.7件**（本記録の算出）。 **レートリミットやIPブロックの閾値に届かない**（本記録の評価）。 **出典1 が推奨するのも、レスポンスコードとレスポンスサイズの 偏りを見ることである**（出典1）。
    取るべき行動 **①アクセスログにレスポンスコードとレスポンスサイズが 記録されているかを確認する（記録していなければログ形式を変える）。** **②直近30日の 4xx・5xx の時間帯別分布と、 認証 API のレスポンスサイズの分布を取り、平常時の形を把握する。** **③平常時からの乖離を検知する条件を、閾値ではなく分布の形で作る。**
  • **JA4 fingerprint をログに残す。IPアドレスより持続する識別子になる**
    **出典1 は、IPアドレス・User-Agent と並べて JA4 fingerprint を照合の指標に挙げている**（出典1）。 **本件では、IPアドレスが異なってもリクエスト内の識別子が 同一だったことから同一攻撃者と判断されている**（出典1）。 **送信元が分散されるほど、送信元以外の指紋の価値が上がる**（本記録の評価）。
    取るべき行動 **①ロードバランサ・WAF・リバースプロキシで JA3/JA4 fingerprint を取得・記録できるかを確認する。** **②記録できる場合、アクセスログに追加し、SIEM で集計できるようにする。** **③「同一 fingerprint が短時間に多数のIPアドレスから現れる」 という観点で集計する。**
  • **ログイン後の機能と非公開の管理機能を、脆弱性診断の対象に入れる**
    **本件の攻撃は、ログイン後の画面で改めてSQLインジェクションを 試している**（出典1・2）。 **出典1 は点検項目として「非公開の管理機能を含む脆弱性診断」を 明示している**（出典1）。 **未認証の入口だけを診断していると、この段階は見えない**（本記録の評価）。
    取るべき行動 **①直近の脆弱性診断の報告書で、診断対象に 認証後の画面・API・管理機能が含まれていたかを確認する。** **②含まれていなければ、次回の診断範囲に加える （診断用の会員アカウントを用意する必要がある）。** **③ポイント・残高など金銭的価値を扱う API については、 「他人のIDを指定したときに拒否されること」を 個別のテストケースとして明示する。**
  • **他利用者の資源を操作しようとした試みを、アプリケーション側の監査ログに残す**
    **ポイントの不正操作の試みは、不正な入力文字列を含まないため WAF には現れない**（本記録の評価）。 **アプリケーションが権限確認で拒否したとしても、 その拒否が記録されていなければ、攻撃の存在が分からない**（本記録の評価）。
    取るべき行動 **①認可チェックで拒否したリクエストを、 「誰が」「誰の資源に対して」「何をしようとしたか」の形で 監査ログに記録する。** **②そのログを SIEM に取り込み、 同一アカウント・同一 fingerprint からの拒否が 短時間に連続することを検知条件にする。** **③既存の実装で拒否が記録されていない箇所を洗い出す。**
  • **攻撃ツールの「規則性」を前提にした検知ルールを棚卸しする**
    **出典1 は、本件の攻撃に 「攻撃ツールに典型的な短時間大量アクセスや機械的な規則性が 見られなかった」と述べている**（出典1）。 **一方で、使われたツール自体は sqlmap・curl・Dart である**（出典1）。 **ツールの痕跡（User-Agent・リクエストの形）だけに依存した検知は、 装われれば外れる**（本記録の評価）。
    取るべき行動 **①既存の WAF ルール・検知ルールのうち、 User-Agent 文字列や固定の間隔に依存しているものを一覧にする。** **②それぞれについて「装われた場合に何が残るか」を書き出す。** **③残らないものについては、応答側（コード・サイズ）の 観点で代替の検知を用意する。**
