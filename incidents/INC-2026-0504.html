INC-2026-0504Docker Hub の PAT が他人名義へ転送

Docker は2026年10月12日、個人アカウントを組織（Organization）へ変換する機能が 個人用アクセストークン（PAT）の所有者レコードだけを書き換え、秘密値の再発行も 当人の同意確認も行わないまま「指名された新オーナー」へ付け替えていたと公表した （CVE-2026-105445）——攻撃者は自分で作ったアカウントの PAT を手元に残したまま 標的ユーザーをオーナーに指名するだけで、そのトークンでレジストリ上は標的本人として イメージの取得・push・削除を行えた。露出期間は2024年8月26日から2026年9月30日までの 2年1か月で、Docker は報告受領から約3時間30分で修正を本番投入し、転送された トークンによる約304,000件の push を調べて「悪用の証拠は見つからなかった」としている

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年10月12日（Docker のセキュリティアドバイザリ公表） 最終更新: 2026年10月14日

「自分のトークンが、いつの間にか他人のものになっていた」——この事案で起きたのは、その逆です。他人のトークンが自分のものになり、秘密値は元の持ち主が握ったままでした。

Docker は2026年10月12日、Docker Hub のセキュリティアドバイザリを公表しました（出典1）。個人アカウントを組織（Organization）へ変換する機能に不備があり、変換時に個人用アクセストークン（PAT）が「指名された新しいオーナー」へ付け替えられていました。CVE-2026-105445 として採番されています（出典1・2）。

成立の筋は4段です（出典1）。

段 内容
1 攻撃者がアカウントを作り、PAT を発行する（秘密値は攻撃者の手元）
2 そのアカウントを組織へ変換し、標的のユーザーをオーナーとして指名する
3 PAT の所有者レコードが標的ユーザーへ書き換わる。秘密値は変わらない
4 攻撃者は手元の秘密値で、レジストリに対し標的本人として認証できる

Docker の説明——「トークンのスコープの範囲内で、付け替えられた PAT はレジストリのレベルで標的ユーザーとして振る舞った。つまり攻撃者は標的のリポジトリ、および標的がアクセスできる組織において、イメージの pull・push・削除を行い得た」（出典1・2。原文英語。本記録の訳）。Docker はこれを「正規の名前でイメージを公開できることを含む」ためソフトウェアサプライチェーンのリスクとして扱い、重要度を critical と評価しました（出典2）。

できなかったことも、はっきり書かれています。 「この脆弱性は Docker Hub の Web インターフェースへのアクセスを与えず、標的のパスワード・メールアドレス・二要素設定の変更やアカウントの乗っ取りには使えなかった」（出典1。原文英語。本記録の訳）。

露出期間は2024年8月26日 20:33 UTC から、修正が本番投入された2026年9月30日 約19:10 UTC までです（出典1）。本記録の算出では765日——2年1か月にわたり、この経路は開いていました。

一方で、報告を受けてからの速度は際立っています（出典1）。9月30日 11:40（米国東部）に security@docker.com で報告を受け、約13:30 に社内で独立に再現、約15:10 に修正を本番投入。本記録の算出で、報告から修正まで約3時間30分です。

調査では、2024年8月26日以降のすべての変換を列挙し、レジストリの認証ログ・利用データ・IAM のトークン記録と突き合わせました（出典1）。転送されたトークンで行われた push 約304,000件を調べ、「この脆弱性が悪用された証拠は見つからなかった」としています（出典1）。

ただし Docker は、検知に頼らなかった理由を明示しています。 「レジストリのログはトークンが使われた時刻を示すが、トークンが存在することは示さない。したがって転送されたが一度も使われなかったトークンは痕跡を残さない」（出典1。原文英語。本記録の訳）。そのため「露出期間中に変換を通過したすべての PAT を、影響を受けた可能性があるものとして扱った」としています（出典1）。

本記録の評価——この事案の読みどころは脆弱性そのものではなく、「所有者が移る資格情報」という設計パターンの危うさです。 秘密値を変えずに所有者だけを書き換える処理は、監査上は「正当な権限委譲」として記録されます。 Docker は恒久対策として、他の「資格情報の所有者を変更するフロー」も同じパターンで点検中だと述べています（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない**（出典1）。 **以下は Docker のアドバイザリが記述する「成立し得た筋」であり、 被害事例の再構成ではない**（本記録の明示）。 **攻撃者は自分のアカウントで PAT を発行し、そのアカウントを組織へ変換して 標的ユーザーをオーナーに指名するだけで、 手元の秘密値のままレジストリ上は標的として認証できた**（出典1）。

  1. 1. 認証情報アクセス確認済
    **攻撃者が自分のアカウントで個人用アクセストークン（PAT）を発行する**（出典1）。 **この時点では、トークンは攻撃者自身の権限しか持たない。**
    根拠: Docker のアドバイザリによる成立条件の記述（出典1）
  2. 2. 権限昇格確認済
    **攻撃者が自分のアカウントを組織へ変換し、 標的のユーザーをその組織のオーナーとして指名する**（出典1）。 **変換処理は PAT の所有者レコードを標的ユーザーへ書き換えるが、 秘密値のローテーションも失効も行わない。 指名された当人への確認も通知も行わない**（出典1）。
    根拠: Docker のアドバイザリによる変換処理の記述（出典1）
  3. 3. 初期侵入確認済
    **攻撃者が手元の秘密値でレジストリへ認証する。 トークンは標的ユーザーのものとして扱われる**（出典1）。 **「トークンのスコープの範囲内で、付け替えられた PAT は レジストリのレベルで標的ユーザーとして振る舞った」** （出典1。原文英語。本記録の訳）。
    根拠: Docker のアドバイザリによる影響の記述（出典1）
  4. 4. 影響（暗号化・破壊・改ざん）確認済
    **トークンのスコープと標的の権限に応じて、 標的のリポジトリおよび標的がアクセスできる組織において イメージの pull・push・削除を行い得た**（出典1・2）。 **Web インターフェースへのアクセス、パスワード・メールアドレス・ 二要素設定の変更、アカウントの乗っ取りはできなかった**（出典1）。
    根拠: Docker のアドバイザリによる影響範囲の切り分け（出典1）

この事案で下された判断
  • トレードオフ: **公表を遅らせる間、同じ不備を自力で見つけた第三者が悪用する余地が残る。** **一方で、残存トークンを失効させる前に手口を公表すれば、 「どのトークンがまだ有効か」を攻撃者に教えることになる**（本記録の整理）。
  • トレードオフ: **一律失効は安全側だが、動いている CI/CD を壊す。** **除外を認めれば、理論上は「攻撃者が秘密値を握ったままのトークン」が 残り得る**（本記録の整理）。
  • トレードオフ: **限界を書けば「調べきれていない」と読まれる。** **書かなければ「約304,000件を調べて悪用は無かった」が 全量調査として誤読される**（本記録の整理）。

秘密値を変えずに所有者だけを書き換えた——監査ログには「正当な権限委譲」として残る原因・手口

不備は、アカウント→組織の変換処理そのものにありました（出典1）。

Docker の記述を段に分けます（出典1。原文英語。本記録の訳）。

処理 行われたこと 行われなかったこと
所有者の変更 PAT の所有者レコードを新オーナーへ書き換えた 秘密値のローテーション・失効
指名 任意のユーザーを組織オーナーとして指名できた 指名された当人への確認
通知 — 指名された当人への通知

この3つが揃うと、攻撃者は「自分が作ったトークン」を「標的が所有するトークン」に変えられます。秘密値は手元に残ったままです（出典1）。

本記録の評価——この形の怖さは、検知の側にあります。トークンの所有者が変わる操作は、プラットフォームから見れば正当な機能の実行です。レジストリの認証ログには「標的ユーザーとしての認証」が記録されますが、それは標的本人の操作と区別がつきません（出典1 の記述から。本記録の整理）。

Docker 自身がこの点を明文化しています—— 「レジストリのログはトークンが使われた時刻を示すが、トークンが存在することは示さない。したがって転送されたが一度も使われなかったトークンは痕跡を残さない。そのため我々は、誰が露出したかを決めるのに検知に頼らなかった」（出典1。原文英語。本記録の訳）。

影響範囲の決め方を「ログに出たもの」ではなく「構造上通過したもの」に置いた判断が、この事案の対応で最も評価できる部分です（本記録の評価）。

できたこととできなかったことが切り分けて書かれている——「乗っ取り」ではなく「名義の借用」だった被害規模・影響範囲

Docker は影響の境界を明示しました（出典1・2）。

できたこと——「トークンのスコープの範囲内で、付け替えられた PAT はレジストリのレベルで標的ユーザーとして振る舞った。つまり攻撃者は標的のリポジトリ、および標的がアクセスできる組織において、イメージの pull・push・削除を行い得た」（出典1・2。原文英語。本記録の訳）。

できなかったこと——「この脆弱性は Docker Hub のWeb インターフェースへのアクセスを与えず、標的のパスワード・メールアドレス・二要素設定の変更やアカウントの乗っ取りには使えなかった」（出典1。原文英語。本記録の訳）。

影響の重さの評価は、Docker 自身の言葉に拠ります。 「それは正規の名前でイメージを公開できることを含むため、我々はこれをソフトウェアサプライチェーンのリスクとして扱い、critical と評価した」（出典2。原文英語。本記録の訳）。

本記録の整理——「乗っ取り」ではなく「名義の借用」だったことは、被害の軽重とは別の問題を生みます。正規の名前で push されたイメージは、利用者側から見て正規のイメージです。署名やダイジェストの固定をしていない限り、docker pull の時点で区別する手立てはありません（本記録の評価）。

なお影響は「トークンのスコープの範囲内」です（出典1）。読み取り専用のトークンであれば push はできず、スコープを絞る運用がそのまま被害の上限になっていたことになります（出典1 の記述から。本記録の整理）。

アドバイザリには、分単位の時刻の列が載っています（出典1）。

本記録の評価——注目すべきは、速かった部分と時間がかかった部分の切れ目です。 「脆弱性を閉じる」は3時間半で終わりました。一方「すでに転送されてしまったトークンを消す」には8日かかっています（本記録の算出）。その8日の中身は、全変換の列挙・ログとの突き合わせ・約304,000件の push の精査・対象者への通知・保持希望の受付です（出典1）。

資格情報が絡む事案では、修正の投入は対応の始まりにすぎません。 「配ってしまった鍵をどう回収するか」の工程を事前に持っているかどうかが、収束までの時間を決めます（本記録の評価）。

恒久対策は「同意」「監査」「他のフローの点検」の3点——Docker は同じパターンを探しに行った再発防止

Docker が挙げた対策は次のとおりです（出典1）。

  1. 即座の修正——「変換からの PAT 転送を完全に取り除いた」（出典1。本記録の訳）。
  2. ドキュメントの更新——PAT は転送されず新オーナーが作り直す必要がある。自動化には組織用アクセストークンを推奨する（出典1）。
  3. 同意の導入——組織オーナーとして指名される前に当人の同意を要求し、指名されたときに通知する（出典1）。
  4. 監査の追加——「トークンの所有権変更のすべてについて監査可能な履歴を記録する」（出典1。本記録の訳）。
  5. 横展開の点検——「資格情報の所有権を変更する他のフローを同じパターンで見直している」（出典1。本記録の訳）。

本記録の評価——5点目が最も重要です。 この事案は「変換機能のバグ」ではなく「所有者が移る資格情報」という設計パターンの問題だからです。同じパターンは、退職者のトークン引き継ぎ、組織統合、プロジェクトの移管、サービスアカウントの担当変更など、多くの場所に現れます。自組織の点検も「Docker Hub を使っているか」ではなく「秘密値を変えずに所有者を書き換える処理を持っていないか」で始めるべきです（本記録の評価）。

利用者側に求められた行動は3つです（出典1）。①2026年10月2日のメールを受け取ったかを確認する（受け取っていなければ「このフローで転送された PAT は無い」）②Docker Hub の Account settings → Personal access tokens で、見覚えのないトークンや使っていないトークンを失効させる③組織の自動化には個人の PAT ではなく組織用アクセストークンを使う。

  • **「資格情報の所有者が移る処理」を、自社システムとSaaSの両方で棚卸しする**
    **本件の原因は、変換機能のバグというより 「秘密値を変えずに所有者を書き換える」という設計パターンである** （出典1。本記録の整理）。 **Docker 自身が恒久対策として 「資格情報の所有権を変更する他のフローを同じパターンで見直している」と 述べている**（出典1。本記録の訳）。 **同じパターンは、退職者のトークン引き継ぎ・組織統合・ プロジェクト移管・サービスアカウントの担当変更に現れる**（本記録の評価）。
    取るべき行動 **①自社の ID 管理・CI/CD・SaaS について 「所有者が変わり得る資格情報」を一覧にする （API キー・PAT・サービスアカウント・署名鍵）。** **②各々について「所有者が変わったとき秘密値は再発行されるか」を確認し、 されないものは手順に再発行を組み込む。** **③所有者変更の操作が監査ログに残るかを確認し、 残らないものは「変更できない」運用に寄せる。**
  • **「悪用の証拠が無い」という報告を受け取ったら、その証拠が取れる範囲を聞く**
    **Docker は約304,000件の push を調べて悪用の証拠を見つけなかったが、 同時に「転送されたが一度も使われなかったトークンは痕跡を残さない」と 述べている**（出典1。本記録の訳）。 **つまり「証拠が無い」は「使われなかった」と 「使われたが記録されなかった」の両方を含む**（本記録の評価）。 **ベンダーの報告を受けて自社の対応を決める立場では、 この差が「トークンを全部作り直すか否か」を分ける。**
    取るべき行動 **①ベンダーからの影響調査報告を受けたとき、 「どのログで何を確認したか」「その手段で検出できないケースは何か」の 2点を必ず質問する（質問テンプレートとして手順に入れる）。** **②回答が得られない場合は「影響があったものとして扱う」を既定にする。** **③その既定で何を作り直すことになるかを、事前に書き出しておく。**
  • **通知メールが唯一の判定材料になる事案がある。受信できる体制を先に作る**
    **Docker は「通知を受け取っていない利用者は、 影響を受けておらず対応は不要と考えてよい」としている**（出典1。本記録の訳）。 **つまり自組織が該当するかは、2026年10月2日のメールが届いたかどうかで決まる。** **開発者個人のアカウントに紐づくメールは、 退職・異動・迷惑メール振り分けで届かないことがある**（本記録の評価）。
    取るべき行動 **①開発基盤の SaaS について、 セキュリティ通知の宛先が「個人の受信箱」になっていないかを確認する （共有メールボックスかチケット系へ転送する）。** **②退職・異動時のアカウント処理手順に 「通知先メールアドレスの引き継ぎ」を入れる。** **③主要な SaaS のセキュリティアドバイザリ公開先（ブログ・RSS）を 巡回対象に登録し、メールが届かなくても気づける経路を二重化する。**
  • **サプライチェーンの脅威評価に「正規の名前で配られる改ざん物」を入れる**
    **Docker がこれを critical とした理由は 「正規の名前でイメージを公開できることを含む」ためである** （出典2。本記録の訳）。 **侵害の対象はレジストリではなく、そこから取得する全ての下流である。** **本記録の評価**——**依存関係の脅威評価は 「悪意あるパッケージを入れてしまうリスク」に偏りがちだが、 本件は「正しいパッケージの正しい名前が、中身だけ入れ替わる」形である。**
    取るべき行動 **①本番と CI で取得する外部イメージ・パッケージの一覧を作り、 タグ指定かダイジェスト指定かを棚卸しする。** **②重要なものからダイジェスト固定に切り替え、 更新は意図的な作業として記録する。** **③「取得元が侵害された場合に何が止まり、何を作り直すか」を 事業継続計画に1項目として置く。**
セキュリティ技術者への示唆
  • **Docker Hub の PAT を棚卸しし、見覚えのないトークンを失効させる**
    **Docker が利用者に求めた行動の中核がこれである**（出典1）。 **本件では、自分が所有者になっているが秘密値を他人が握っている トークンが存在し得た**（出典1）。 **トークンの一覧には、作成日と説明文が表示される**（出典1）。
    取るべき行動 **①Docker Hub の Account settings → Personal access tokens を開き、 説明文と作成日で全件を確認する。** **②自分が作った記憶が無いもの、用途が説明できないもの、 使っていないものを失効させる。** **③2026年10月2日の Docker からの通知メールを検索し、 対象トークンの列挙があればその全てを失効させる （保持を希望したものが残っている可能性がある）。**
  • **CI/CD の認証を、個人の PAT から組織用アクセストークンへ移す**
    **Docker は組織の自動化に組織用アクセストークンを推奨している**（出典1）。 **本記録の評価**——**個人に紐づく資格情報をパイプラインに使うと、 その個人の身分に起きた変化（本件のような所有者の付け替え、 退職によるアカウント削除、権限の変更）が そのままビルドの可否に波及する。**
    取るべき行動 **①CI/CD の環境変数・シークレットストアを grep して、 Docker Hub 認証に個人の PAT を使っている箇所を洗い出す。** **②組織用アクセストークンへ置き換え、スコープを 必要最小（読み取りのみで足りるものは読み取りのみ）にする。** **③トークンの有効期限を設定し、更新を定期作業として登録する。**
  • **イメージの取得をダイジェスト（sha256）で固定する**
    **本件で成立し得たのは「正規の名前での push」である**（出典1・2）。 **タグを指定して取得している限り、 中身が差し替わっても取得側は気づかない**（本記録の評価）。 **ダイジェストを固定していれば、内容が変わった時点で取得が失敗する。**
    取るべき行動 **①Dockerfile の `FROM`、Kubernetes のマニフェスト、 docker-compose の `image:` を棚卸しし、 タグ指定になっているものを列挙する。** **②基盤イメージと外部提供のサイドカーから順にダイジェスト固定へ移す。** **③更新は Renovate / Dependabot 等で差分として見える形にし、 「いつ、誰が、どのダイジェストに上げたか」を記録に残す。**
  • **自社サービスで「権限を与える操作」に、相手側の同意を要求する**
    **本件の成立条件は「他人を自分の組織のオーナーに指名できる」ことだった** （出典1）。 **Docker の恒久対策は、指名の前に当人の同意を求めることである**（出典1）。 **本記録の評価**——**招待・権限付与・所有権移転は 片側だけで完結させてはいけない操作である。** **同意が無い設計は、本件のように「与えた側が得をする」経路を作る。**
    取るべき行動 **①自社サービスの招待・権限付与・所有権移転の各フローを列挙し、 相手側の操作が1回以上要るかを確認する。** **②要らないものには受諾のステップを追加し、 少なくとも相手側へ通知を出す。** **③所有権が移る処理では、移転前の資格情報を無効化し新規発行させる （移転ではなく再発行にする）。**
  • **「ログに出たもの」で影響範囲を決めない。構造上通過したもので決める**
    **Docker はこの判断を明文化している** ——**「レジストリのログはトークンが使われた時刻を示すが、 トークンが存在することは示さない」「そのため我々は、 誰が露出したかを決めるのに検知に頼らなかった。 露出期間中に変換を通過したすべての PAT を 影響を受けた可能性があるものとして扱った」** （出典1。原文英語。本記録の訳）。
    取るべき行動 **①インシデント対応手順に「影響範囲の母数の決め方」の節を作り、 ログベースと構造ベースのどちらを既定にするかを書く。** **②構造ベースで数えるために必要な記録 （設定変更・権限変更・資格情報発行のイベント）が 実際に取れているかを確認する。** **③取れていない項目は、取得の追加を課題として登録する。**
