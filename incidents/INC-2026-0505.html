INC-2026-0505SAP Python SDK に CVSS10 欠陥

SAP は2026年10月13日のセキュリティパッチデーで、SAP Cloud SDK for Python に CVSS v3.1 基本値10.0 の OAuth2 サーバーサイドリクエストフォージェリ（SSRF）が あると公表した（CVE-2026-89111・SAP Note 3797111）——SAP Business Technology Platform 上のマルチテナントアプリケーションで、攻撃者が `tenant_subdomain` パラメータの値を制御できると OAuth2 のトークン要求が攻撃者のサーバーへ向き、 アプリケーションのクライアント資格情報がそのまま渡る。修正版 0.45.2 は この値を RFC 1123 の DNS ラベル規則で検証するようになった

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月13日（SAP セキュリティパッチデー・GitHub アドバイザリ公開） 最終更新: 2026年10月14日

CVSS 10.0 は、滅多に出ません。「認証不要・前提条件なし・影響がスコープの外へ及ぶ」の3つが同時に成立したときにだけ到達する値です。

SAP は2026年10月13日のセキュリティパッチデーで、SAP Cloud SDK for Python の脆弱性を公表しました（出典1・2・3）。CVE-2026-89111、SAP Note 3797111、GitHub セキュリティアドバイザリGHSA-4mv3-jxxm-9cx2。CVSS v3.1 基本値は10.0（Critical）で、評価ベクトルは CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N です（出典1・2）。この日の SAP の公表21件のうち、最も高い値です（出典3。本記録の整理）。

不備の中身は1文で書けます（出典1・2）。

攻撃者が tenant_subdomain パラメータを制御できる場合、OAuth2 のトークン要求を自分が支配するサーバーへ向けさせ、クライアント資格情報を持ち出せる（出典1・2。原文英語。本記録の訳）。

影響を受けるのは、SAP Business Technology Platform（BTP）上でこのSDKを使うマルチテナントアプリケーションです（出典1）。対象バージョンは 0.45.2 より前のすべて。修正版は 0.45.2 です（出典1）。

なぜ CVSS が10.0 になるのかを、ベクトルの各要素で見ます（出典1・2。本記録の整理）。

要素 値 意味
AV:N ネットワーク 遠隔から到達できる
AC:L 低 特殊な条件が要らない
PR:N 不要 権限が要らない
UI:N 不要 利用者の操作が要らない
S:C 変更あり 影響が脆弱な部品の外へ及ぶ
C:H / I:H 高 / 高 機密性・完全性への影響が高い

10.0 を押し上げているのは S:C（Scope: Changed）です（本記録の評価）。流出するのはアプリケーションのクライアント資格情報であり、それを握った攻撃者は「アプリケーションとして」BTP のサービスへ認証できます。 つまり被害は SDK の内部では終わらず、そのアプリケーションが権限を持つ範囲全体へ移ります（本記録の評価）。

マルチテナント構成であることが、この脆弱性の前提です。 tenant_subdomain は「どのテナント向けのトークンを取るか」を決める値で、マルチテナントアプリケーションではテナントごとに切り替わります（本記録の整理）。検証が無ければ、この値に外部由来のデータが入る経路がそのまま SSRF の入口になります。

悪用については何も公表されていません。 SAP のアドバイザリにも、実環境での悪用に関する記述はありません（出典1・2・3。本記録の確認）。CISA の KEV カタログへの登録も、本記録の作成時点で確認できていません〈未確定2〉。

本記録の評価——この事案で CISO が最初に確かめるべきは「自社に SAP BTP があるか」ではありません。 「Python の依存関係一覧に sap-cloud-sdk が入っているか」です。 SDK は PyPI から入る部品であり、SAP 製品の棚卸しでは見えない場所に紛れ込みます（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない**（出典1・2・3）。 **以下は GitHub セキュリティアドバイザリと CVE レコードが記述する 「成立し得た筋」であり、被害事例の再構成ではない**（本記録の明示）。 **攻撃者が `tenant_subdomain` の値を制御できると、 SDK が組み立てる OAuth2 トークン要求の宛先が攻撃者のサーバーになり、 要求に載るクライアント資格情報が渡る**（出典1・2）。

  1. 1. 偵察推定
    **攻撃者は、対象が BTP 上のマルチテナントアプリケーションであり テナントをサブドメインで識別していることを確認する** （出典1 の前提条件から。本記録の整理）。
    根拠: GitHub アドバイザリが示す影響構成の条件（出典1）
  2. 2. 初期侵入確認済
    **攻撃者が制御する値を `tenant_subdomain` へ到達させる。** **SDK はこの値を検証せずにトークン URL へ組み込む**（出典1・2）。
    根拠: GitHub アドバイザリの記述と、修正版 0.45.2 が追加した検証内容（出典1）
  3. 3. 認証情報アクセス確認済
    **SDK が OAuth2 のトークン要求を、攻撃者が支配するサーバーへ送る。** **要求にはアプリケーションのクライアント資格情報が載っているため、 攻撃者はそれを受け取る**（出典1・2）。 **アドバイザリの記述——「クライアント資格情報を持ち出せる （exfiltrate）」**（出典1。原文英語。本記録の訳）。
    根拠: GitHub アドバイザリと CVE レコードの影響記述（出典1・2）

外から与えられる値がトークン要求先の URL になっていた——欠けていたのは入力検証そのもの原因・手口

GitHub セキュリティアドバイザリの記述は簡潔です（出典1。本記録の訳）。

「SAP Cloud SDK for Python には、BTP のマルチテナントアプリケーションに影響する OAuth2 SSRF の脆弱性がある」

具体の経路は、tenant_subdomain という1つのパラメータです（出典1・2）。この値を制御できる攻撃者は、OAuth2 のトークン要求を自分のサーバーへ向けさせ、アプリケーションのクライアント資格情報を受け取れます（出典1・2。本記録の訳）。

分類は CWE-918（Server-Side Request Forgery）です（出典1）。

本記録の整理——この形は SSRF の典型ですが、普通の SSRF と重さが違います。通常の SSRF は「サーバーに任意の宛先へリクエストさせる」ことで内部ネットワークへの到達や情報の読み出しを狙います。本件では、そのリクエストに アプリケーションのクライアント資格情報が載っています。 宛先を差し替えるだけで、資格情報が攻撃者の手に渡ります（出典1。本記録の評価）。

修正の内容が、欠けていたものを明示しています（出典1。本記録の訳）。

「バージョン 0.45.2 は、tenant_subdomain の値をトークン URL に置く前に、RFC 1123 の DNS ラベル規則に照らして検証する」

つまり 0.45.2 より前は、この値がそのまま URL に組み込まれていました（出典1。本記録の整理）。

CVSS 10.0 の内訳——押し上げているのは「影響が部品の外へ及ぶ」という1点被害規模・影響範囲

評価ベクトルは CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N です（出典1・2）。

要素 値 本件での意味
AV（攻撃元区分） N（ネットワーク） 遠隔から到達できる
AC（攻撃条件の複雑さ） L（低） 特殊な前提が要らない
PR（必要な権限） N（不要） 認証が要らない
UI（利用者の関与） N（不要） 利用者の操作が要らない
S（スコープ） C（変更あり） 影響が脆弱な部品の外へ及ぶ
C（機密性） H（高） クライアント資格情報が渡る
I（完全性） H（高） 資格情報でアプリとして操作できる
A（可用性） N（なし） 直接の停止は生じない

本記録の評価——S:C が付く理由を言葉にすると、「漏れるのは SDK の中の情報ではなく、アプリケーション全体の身分証である」ということです。

OAuth2 のクライアント資格情報（client_id と client_secret）は、アプリケーションが BTP のサービスへ「自分である」と示すための鍵です。 これを握った攻撃者は、そのアプリケーションが持つ権限の範囲でdestination 管理・オブジェクトストレージ・監査ログなどSDK が扱う各サービスへ認証できます（出典5 の SDK 機能説明から。本記録の整理）。

可用性が N（なし）であることにも意味があります（本記録の評価）。この脆弱性でサービスは止まりません。 止まらないということは、気づく契機が無いということです。 資格情報が1回渡ったあと、攻撃者が正規の資格情報として使う限り、挙動は正常な通信と区別がつきません。

マルチテナントであることが前提——`tenant_subdomain` に外部由来の値が入る経路を数える評価・解釈

影響を受けるのは「BTP 上のマルチテナントアプリケーションでこのSDKを使っているもの」です（出典1）。

tenant_subdomain は、どのテナント向けのトークンを取得するかを決める値です。マルチテナントのアプリケーションでは、リクエストごとに切り替わります（本記録の整理）。

本記録の評価——判定の実務は「この値がどこから来るか」を追うことに尽きます。

値の出所 評価
設定ファイル・環境変数に固定 外部から制御できない（影響は限定的）
テナント登録時に検証済みの台帳から引く 台帳への登録経路次第
HTTP ヘッダ（Host・X-Forwarded-Host 等）から取る 外部から制御できる
リクエストのパス・クエリ・ボディから取る 外部から制御できる
JWT の claim から取る（署名検証あり） 発行元の信頼次第

ヘッダ由来の経路は見落としやすい——マルチテナントの振り分けをサブドメインで行う設計では、Host ヘッダからテナント名を取り出すのが自然な実装だからです（本記録の評価）。リバースプロキシが Host を書き換えずに通していれば、その値は利用者が自由に指定できます。

回避策としてアドバイザリが挙げているのは、許可リストによる検証です（出典1。本記録の訳）。

「SDK の呼び出しに渡す前に、tenant_subdomain を登録済みテナントサブドメインの既知の許可リストに照らして検証する」

本記録の整理——修正版 0.45.2 が行う検証は「DNS ラベルとして妥当か」であり、許可リストではありません（出典1）。つまり 0.45.2 に更新しても、「妥当な形式の、しかし自組織のものではないサブドメイン」が渡る余地は残ります。 アドバイザリが更新と併せて許可リストを示しているのは、この差を埋めるためと読めます（本記録の評価）。

    取るべき行動 **①`pip list | grep sap-cloud-sdk` と ロックファイルの検索で、全環境のバージョンを確認する。** **②0.45.2 以上へ更新し、テナント切り替えの経路を 結合テストで確認する（検証が追加されたため、 これまで通っていた異常な値は弾かれる）。** **③コンテナイメージ・ビルドキャッシュに 古いバージョンが残っていないかを確認する。**
  • **`tenant_subdomain` に渡る値の出所を、コードを追って1つずつ確認する**
    **本件の到達性は「攻撃者がこの値を制御できるか」で決まる**（出典1・2）。 **本記録の評価**——**マルチテナントの振り分けを サブドメインで行う設計では、`Host` ヘッダから テナント名を取り出す実装が自然であり、 リバースプロキシが書き換えていなければ外部から制御できる。**
    取るべき行動 **①`tenant_subdomain` を渡している呼び出し箇所を全て列挙する。** **②各箇所について値の出所を辿る （設定ファイル／環境変数／台帳／`Host` ヘッダ／ `X-Forwarded-Host`／クエリ／JWT の claim）。** **③ヘッダ・クエリ由来のものを、検証済みの台帳引きか 署名検証済みの claim へ置き換える。**
  • **更新と別に、許可リストによる検証を自分の側に入れる**
    **アドバイザリの回避策は 「SDK の呼び出しに渡す前に、登録済みテナントサブドメインの 既知の許可リストに照らして検証する」である**（出典1。本記録の訳）。 **本記録の評価**——**0.45.2 が行う検証は形式の妥当性のみで、 「妥当な形式の、しかし自組織のものではないサブドメイン」は通る。**
    取るべき行動 **①テナント登録時にサブドメインを台帳へ記録する （すでにあるなら参照できる形にする）。** **②SDK 呼び出しの直前に、台帳にあるかどうかを検査する 共通関数を1つ作り、全呼び出しをそこに通す。** **③検査に落ちた値をログに残す—— 攻撃の試行がそこに現れる。**
  • **アプリケーションの外向き通信を、宛先の許可リストで縛る**
    **SSRF は「サーバーに任意の宛先へ要求させる」攻撃であり、 出口を縛れば成立しない**（本記録の評価）。 **本件で差し替えられるのは OAuth2 のトークンエンドポイントで、 これは数が限られており列挙できる**（本記録の評価）。
    取るべき行動 **①アプリケーションが正当に接続する必要のある 外部ホストを列挙する（BTP の各サービス・IdP・ 外部 API）。** **②出口プロキシまたはネットワークポリシーで、 それ以外への接続を拒否する。** **③拒否されたリクエストをログに残し、 監視対象に含める——誤設定と攻撃の両方がここに出る。**
  • **OAuth2 クライアント資格情報のローテーション手順を書き、所要時間を測る**
    **本件で漏れるのはアプリケーションのクライアント資格情報である** （出典1・2）。 **本記録の評価**——**漏洩後に効く対策は再発行だけである。** **再発行の手順が無い、あるいは所要時間が分からない状態では、 「漏れたかもしれない」という段階で判断ができない。**
    取るべき行動 **①BTP のサービスバインディング・destination・ XSUAA のクライアント資格情報について、 再発行の手順を文書化する。** **②検証環境で実際に再発行し、 アプリケーションの再起動が要るか・停止時間がどれだけかを測る。** **③測った値を、インシデント対応の判断材料として 手順書に書き込む。**
