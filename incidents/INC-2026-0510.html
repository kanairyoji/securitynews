CVE-2026-96951（CVSS 8.8） ——Windows シェルのセキュリティ機能バイパスで、Mark of the Web（MotW）の防御を回避します。

MotW は、インターネットから入手したファイルに「これは外から来た」という印を付ける仕組みです。その印を見て、Defender SmartScreen や Office の保護ビューが自動実行を止めます。 印が付かなければ、下流の防御はすべて黙ります（本記録の整理）。

Microsoft の勧告はこう書いています（原文英語）。

「メールまたはインスタントメッセージによる攻撃の筋書きでは、攻撃者は、この脆弱性を悪用するよう細工したファイルを標的の利用者に送ることができる」

「いずれの場合も、攻撃者が利用者に攻撃者の制御下のコンテンツを閲覧させることを強制する手段はない。代わりに攻撃者は、利用者に操作を行わせるよう説得しなければならない」

報告者は3者です——富士通、Anthropic、そして独立研究者。 それぞれ独立に Microsoft へ報告しました。

CISA は同日、これを KEV カタログに登録し、連邦機関の期限を2026年10月16日——3日後——に設定しました。 同じ回で、Ivanti Connect Secure の認証回避CVE-2026-104935 も同じ期限で登録されています（本DB では INC-2026-0496）。

ただし、CISA と Microsoft で脆弱性の分類が一致していません。 KEV カタログ上の名称は「Microsoft Windows Command Injection Vulnerability」（コマンド注入）で、説明も「Microsoft Windows Shell にはコマンド注入の脆弱性がある」で始まります（本記録が2026年10月14日に確認）。Microsoft は「セキュリティ機能バイパス」、ZDI は「Windows Shell Security Feature Bypass Vulnerability」と記述しています。 読者が自社の資産に当てはめるとき、この2つは違う場所を探させます（本記録の評価）〈齟齬1〉。

Microsoft はこの件数に対応する枠組みも同日に出しました。 「リスクコホート（risk cohorts）」 ——「同様の顧客側の評価を必要とする CVE のグループ」です（原文英語。本記録が同社のブログを取得して確認）。1件ずつ読むのではなく、「自社環境についての同じ問いに答えれば済む CVE」をまとめます。

悪用された1件は、警告を出す仕組みそのものを黙らせる原因・手口

CVE-2026-96951（CVSS 8.8）は、Windows シェルのセキュリティ機能バイパスです。

回避される対象は Mark of the Web（MotW）です。

MotW は、インターネットから入手したファイルに「これは外から来た」という印を付ける仕組みです。 その印を見て、Defender SmartScreen や Office の保護ビューが自動実行を止めます。

印が付かなければ、下流の防御はすべて黙ります（本記録の整理）。これが本件の重さです ——攻撃者は SmartScreen を破る必要も、保護ビューを破る必要もありません。 印を落とすだけで、両方が動かなくなります。

Microsoft の勧告はこう書いています（原文英語）。

「メールまたはインスタントメッセージによる攻撃の筋書きでは、攻撃者は、この脆弱性を悪用するよう細工したファイルを標的の利用者に送ることができる」

「いずれの場合も、攻撃者が利用者に攻撃者の制御下のコンテンツを閲覧させることを強制する手段はない。代わりに攻撃者は、利用者に操作を行わせるよう説得しなければならない」

後半の文は、読み方に注意が必要です（本記録の評価）。「利用者の操作が必要」は、攻撃の難しさを意味しません。 MotW が回避されている状況では、利用者が見る画面から警告が消えています。 つまり、操作を求められた利用者には、止まる理由が表示されません。

ZDI の記述も引きます（出典5）。これは MotW 保護を回避する手法の一種であり、従来と違うのは SmartScreen ではなくシェルが対象になった点だとしています。 本記録はここを重く見ます ——同じ目的（印を落とす）に対して、新しい場所（シェル）が見つかったということです。 防御側が SmartScreen を監視していても、シェルの経路は見えません（本記録の評価）。

報告者は3者です——富士通、Anthropic、独立研究者。 それぞれが独立に Microsoft へ報告しました（Microsoft の謝辞）。本記録の読みとして、独立3件の到達は「見つけやすい種類の欠陥だった」ことを示唆します ——ただし裏づけとなる記述はどの資料にもありません（本記録の留保）。

なお、悪用の具体は一切公表されていません。 誰が、いつから、どの標的に対して、どのファイル形式で使ったのか——どれも分かりません。 「ゼロデイ攻撃について情報は共有されていない」（出典3）。

したがって読者が今できることは、コホートを待つことではありません（本記録の主張）。自社の環境についての問い——「インターネットから到達できる RDP ゲートウェイがあるか」「Office の文書をどの経路で受け取っているか」——を自分で書き出しておくことです。 その問いの一覧が、どのベンダーのどの枠組みが来ても使えます。

1,413 件の陰で、既定値が1つ変わった——止まるのは更新の適用ではなく Wi-Fi と VPN である対策・注意喚起

同じ2026年10月13日の更新には、CVE 番号の付かない変更が入っていました（出典7）。NTLMv1 由来の資格情報によるシングルサインオン（SSO）の遮断です。

変わったのは既定値です（出典7）。

  • 更新前——レジストリ値 BlockNtlmv1SSO が未設定なら監査モード。NTLMv1 由来の資格情報は使えて、警告イベント（ID 4024）が出るだけ
  • 更新後——未設定なら遮断モード。要求そのものが拒否され、エラーイベント（ID 4025）が記録される（出典7・8）

影響するのは、MS-CHAPv2 を使う認証です（出典7・8）。PEAP-MSCHAPv2・EAP-MSCHAPv2 による Wi-Fi・有線・VPN の自動接続が失敗しえます（出典7・8）。手動で資格情報を入力すれば接続できますが、その資格情報は保存できません（出典8）。Credential Guard が有効な端末は対象外です（出典7・8）。

ここで整理しておくべきことが3つあります（本記録の主張）。

①これは障害ではなく、予告された仕様変更です。 Microsoft は告知で「計画された変更であり、2026年10月のセキュリティ更新の既知の問題ではない」と明記しています（出典8。本記録の訳）。報道も「バグではなく設計どおり」としています（出典9。本記録の訳）。監査モードを提供した文書の公開（2025年8月29日）から既定の変更（2026年10月13日）までは410日あります（出典7。算出は本記録）。予告の長さは十分でした ——それでも移行が終わっていなければ接続は止まります（本記録の評価）。

②「更新を当てたら繋がらなくなった」の切り分けが変わります。 月例更新の件数が1,413 件もある月に接続の問題が起きると、どの修正が原因かを探しに行きがちです（本記録の評価）。しかし本件は CVE に紐づかない既定値の変更であり、セキュリティ更新の一覧を追っても見つかりません（本記録の主張）。見る場所は Microsoft-Windows-NTLM/Operational ログのイベント ID 4025 と、レジストリ値の設定状況です（出典7・8。整理は本記録）。

③一時的な差し戻しは「例外」として扱います。 BlockNtlmv1SSO に 0（監査モード）を設定すれば従来の動作に戻せますが、Microsoft は「遮断モードより保護が弱まるため、範囲を限定した一時的な例外としてのみ検討すべき」としています（出典7。本記録の訳）。期限は示されていません〈未確定7〉。恒久の対策は、証明書による認証（PEAP-TLS・EAP-TLS）への移行です（出典8）。

なお、報道はレジストリ値の名称を BlockNtlmSSO と書いています（出典9）。Microsoft の文書では BlockNtlmv1SSO です（出典7）〈齟齬6〉。設定名を1文字違いで入れた場合、例外の設定は効きません（本記録の注意）。

**公表されていない。** **本記録の評価として、この段階が本件の核心である** ——**単一の印（MotW）に複数の防御が依存しているため、 印が落ちた事実を見ている監視は普通は存在しない**（本記録の主張）。 **ダウンロードしたファイルの代替データストリーム （Zone.Identifier）の有無を点検していれば痕跡は残るが、 それを常時監視している組織は多くない**（本記録の評価）。
侵入を防げた　**Microsoft が修正を提供している**（出典3）。 **CISA は連邦機関に2026年10月16日を期限とした**（出典2） ——**3日である。**
影響を限定できた　**本記録の評価である。** **MotW は「外から来た」という事実を伝える1本の線であり、 そこに SmartScreen と保護ビューの両方がつながっている。** **線が切れたときに別の経路で止まる仕組みが必要である** （本記録の主張） ——**ただし本件と同じ月に WDAC の強制を回避する CVE-2026-108398 も公開されており （悪用は未確認）、 アプリケーション制御も単独では頼れない**（出典3・5）。
実行公表されていない
**公表されていない。** **本記録の評価として、実務上の監視点はここに移る** ——**印を落とされた事実は見えなくても、 文書を開いた直後の子プロセスの生成や 外向きの通信は端末側の記録に残る**（本記録の主張）。 **ただし本件の悪用後の挙動が公表されていないため、 何を探すべきかの指標（IoC）は存在しない。**
検知できた　**本記録の評価である。** **本件に固有の指標は公表されていないため、 手口に依存しない一般的な監視点を挙げた。** **「警告が出なかった」ことは記録に残らないが、 「文書が子プロセスを作った」ことは残る**（本記録の主張）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**Microsoft は、CVE-2026-96951 を「悪用されている」と評価して公表した一方、 悪用の具体（攻撃者・時期・標的・ファイル形式・後続の挙動）を 公表していない**（出典3）。 **CISA も、KEV への登録と期限のみを示し、 観測の内容に触れていない**（出典2。本記録が確認）。部分的に機能**本記録の作成者の評価である。** **「悪用されている」という事実を更新と同時に公表し、 CISA が同日 KEV へ登録して期限を3日に設定した点は機能している** ——**優先順位の信号としては十分に強い。** **一方で、指標（IoC）が1つも公表されていないため、 読者は「適用する」以外の行動を取れない**（本記録の主張）。 **とくに本件は MotW の回避であり、 既に開かれてしまったファイルを事後に探す必要があるのに、 何を探すかが示されていない。** **なお、理由が公表されていないため 「出せなかった」のか「出さない方針」なのかは判断できない** （本記録の留保）。
**Microsoft は、1回の更新で 1,413 件の CVE を提供し、 同日に「リスクコホート」という優先順位付けの枠組みを導入した** （出典1・3）。 **「リスクコホートは出発点であり、最終的な判断ではない」 「コホートに含まれることは、1つの更新・回避策・緩和策で グループ内のすべての CVE に対処できることを意味しない」** （出典1。原文英語）。部分的に機能**本記録の作成者の評価である。** **枠組みの発想は妥当だと考える** ——**「自社環境についての同じ問いに答えれば済む CVE をまとめる」は、 件数が4桁になった状況での正しい方向である。** **一方で、現時点では道具になっていない**（本記録の主張）。 **①セキュリティ更新ガイド（SUG）に表示されないため、 利用者が普段使う一覧から辿れない。** **②同社自身の文書で、本文と表の件数が一致していない （RDP は本文 64／表 65、Office は本文 119／表 135）**〈齟齬4〉。 **③「出発点であり最終判断ではない」という留保が、 作業をそのまま利用者側へ戻している。** **したがって読者が今できることは、コホートを待つことではなく、 自社環境についての問いを自分で書き出しておくことである** （本記録の評価）。
CISO・経営層への示唆
  • **月例更新の「件数」を経営指標にしない。 見るのは「悪用されているものがいくつあるか」である**
    **本事案では 1,413 件のうち、実環境で悪用されていたのは1件 （CVE-2026-96951）である** ——**0.07% である**（本記録の算出）。 **一方、件数は前年の通年を1か月で上回り、 2026年の累計は 4,000 件を超えた**（出典3）。 **件数が増え続ける前提で見ると、 「今月は何件だったか」は経営の判断材料にならない**（本記録の評価）。 **1,413 件は適用作業の量でもない** ——**1つの更新プログラムが複数の CVE を直すため、 作業量は配布する更新プログラムの数と再起動の回数で決まる。**
    取るべき行動 **①月例更新の報告様式を「件数」から 「悪用が確認されているもの」「KEV に登録されたもの」 「自社が使っている製品に該当するもの」の3つに変える。** **②適用の負荷は、更新プログラムの数と再起動の回数で測る** ——**CVE 件数で測らない。** **③KEV の期限（本事案では登録から3日）を 自社の適用目標に写すかを決めておく** ——**連邦機関向けの期限だが、 悪用の緊急度を示す外部指標として使える**（本記録の評価）。
  • **CISA の KEV とベンダーの分類がずれる前提で、 社内の期限管理と検知の設計を別々に根拠づける**
    **本事案では、同じ CVE-2026-96951 について CISA の KEV カタログが「コマンド注入」、 Microsoft と ZDI が「セキュリティ機能バイパス（MotW 回避）」と 記述している**（本記録が2026年10月14日に確認）〈齟齬1〉。 **「セキュリティ機能バイパス」と「コマンド注入」は、 防御側にとって探す場所が違う**（本記録の主張）。 **KEV の文面だけで検知ルールを書くとベンダーの分類とずれ、 ベンダーの分類だけを見ると KEV を根拠にした期限管理と対象がずれる。**
    取るべき行動 **①脆弱性管理の手順に、 「同じ CVE 番号でベンダー勧告と KEV の両方を引いて突き合わせる」を 明示的な工程として入れる。** **②期限管理の根拠（KEV）と検知の根拠（ベンダー勧告）を 別の記録として残す** ——**どちらかだけを根拠にすると、 後から「なぜこの対象にしたのか」を説明できない。** **③分類が食い違っている CVE を、 そのこと自体を理由に優先度を上げる** ——**どちらが正しいか分からない状態は、 対策範囲が確定していない状態である**（本記録の評価）。
  • **「利用者の操作が必要」を、リスクを下げる要素として読まない**
    **Microsoft の勧告は 「攻撃者が利用者に攻撃者の制御下のコンテンツを閲覧させることを 強制する手段はない。代わりに攻撃者は、 利用者に操作を行わせるよう説得しなければならない」と書いている** （原文英語。出典3）。 **しかし本件は MotW の回避である** ——**つまり、操作を求められた利用者の画面から 警告が消えている**（本記録の主張）。 **「利用者が操作する必要がある」ことと 「利用者が止まる機会がある」ことは別である**（本記録の評価）。
    取るべき行動 **①CVSS の UI（利用者の関与）が必要な脆弱性について、 「警告が出るか」を別の軸として評価する手順を作る。** **②利用者教育の前提を見直す** ——**「警告が出たら止まる」という訓練は、 警告が出ない攻撃には効かない。** **③本件については、 「警告が出なかったかもしれない」ことを前提に、 適用前の期間に開かれた外部由来のファイルを 事後に点検する方針を決める** ——**ただし本件に固有の指標は公表されていない**（本記録の留保）。
  • **ベンダーが出す優先順位付けの枠組みは、 自社の問いの一覧ができてから使う**
    **Microsoft は本事案と同日に「リスクコホート」を導入した** ——**「同様の顧客側の評価を必要とする CVE のグループ」である** （原文英語。出典1。本記録が確認）。 **発想は妥当だが、現時点では道具になっていない**（本記録の評価） ——**①セキュリティ更新ガイドに表示されない、 ②同社の文書で本文と表の件数が合っていない （RDP は本文 64／表 65、Office は本文 119／表 135）、 ③「出発点であり最終判断ではない」という留保が 作業を利用者側に戻している。** **一方で、コホートが問うていること （「インターネットから到達できる RD Gateway があるか」など）は、 どの枠組みが来ても自社で答える必要がある。**
    取るべき行動 **①自社環境についての問いを10〜20個の一覧として書き出す** （外部公開している管理経路・文書の受け取り経路・ バックアップの置き場所・DNS/DHCP の構成・ 特権境界をまたぐ経路）。 **②その一覧を、月例更新のたびに使い回す** ——**ベンダーの束ね方に依存しない。** **③ベンダーの枠組みを採り入れるときは、 「自社の問いの一覧にどれだけ対応しているか」で評価する。**
セキュリティ技術者への示唆
  • **MotW（Mark of the Web）の印に、何がどれだけ依存しているかを 棚卸しする**
    **MotW はインターネットから入手したファイルに印を付け、 Defender SmartScreen や Office 保護ビューといった セキュリティ機構に自動実行の制限を促す仕組みである**（出典3）。 **印が落ちれば、下流の防御はすべて黙る**（本記録の整理） ——**攻撃者は SmartScreen も保護ビューも破る必要がない。** **本件（CVE-2026-96951）は、その印を落とす新しい場所 ——Windows シェル——が見つかったという事案である。** **ZDI は、従来と違うのは SmartScreen ではなく シェルが対象になった点だと述べている**（出典5）。
    取るべき行動 **①MotW の印を前提にしている防御を列挙する** （SmartScreen・Office 保護ビュー・マクロの既定動作・ スクリプトホストの警告・アーカイブ展開時の挙動）。 **②そのうち、印が無くても止まるものがどれかを確認する** ——**止まらないものが、本件で無効化される範囲である。** **③ダウンロードされたファイルの代替データストリーム （Zone.Identifier）の有無を、 少数の代表的な端末で実際に確認する** ——**印が付く経路と付かない経路が、環境によって違う。**
  • **指標（IoC）が公表されない悪用済み脆弱性に備えて、 手口に依存しない監視点を持っておく**
    **本事案では「ゼロデイ攻撃について情報は共有されていない」** （出典3）。 **CISA の KEV カタログも登録と期限だけを示し、 観測の内容に触れていない**（出典2。本記録が確認）。 **ランサムウェアでの利用欄は `Unknown` である。** **つまり読者は「適用する」以外の行動を取る材料を持たない** （本記録の評価） ——**適用前の期間に既に踏まれていたかを確かめる手段が無い。**
    取るべき行動 **①文書アプリケーションからの子プロセス生成を記録・監視する** （本件に固有の指標は無いが、 MotW を回避した実行の後続はここに現れる）。 **②外部由来のファイルの到達から実行までを、 端末側の記録で追えるようにしておく** （保存期間を含めて確認する）。 **③「指標が出なかった脆弱性」の一覧を持ち、 後日 IoC が公表されたときに 過去のログへ遡って照合できる保存期間を確保する。**
  • **単一の防御層を回避する脆弱性が同じ月に複数出ている前提で、 層の独立性を確認する**
    **本事案の月には、MotW を回避する CVE-2026-96951（悪用済み）と、 Windows Defender Application Control（WDAC）の強制を回避する CVE-2026-108398（公開済み・悪用は未確認）が 同時に含まれている**（出典3・5）。 **MotW が落ちたときの受け皿としてアプリケーション制御を 期待していた場合、その受け皿にも穴が公開されている** （本記録の評価）。 **層を重ねること自体は正しいが、 層が同じ月に同時に抜けうることを前提に点検する必要がある。**
    取るべき行動 **①自社の防御の層を、 「どの層が抜けたときに、どの層が受けるか」の形で書き出す。** **②月例更新のたびに、 「今月の修正が、受け皿にしている層に当たっていないか」を確認する。** **③受け皿が同時に抜けている月は、 人の運用（配送経路での制限・適用の前倒し）で補う判断を その場でできるようにしておく。**
  • **月例更新の総量は Microsoft の件数だけでは測れない**
    **同じ火曜日に、Adobe が11件の告知で 174 件の CVE に対応している** （ZDI の集計。出典5） ——**SecurityWeek は「11 製品で 176 件」と記述しており、 2件の差がある**（出典3）。 **同日には SAP のセキュリティパッチデーもあり、 CVSS 10.0 の案件が含まれている**（本DB では INC-2026-0505）。 **運用側が同じ週に向き合う総量は、 Microsoft の 1,413 件だけではない**（本記録の評価）。
    取るべき行動 **①月例の作業計画を、Microsoft・Adobe・SAP・ 自社が使うその他のベンダーの公表日を並べた暦として持つ。** **②同じ週に重なるベンダーごとに、 「悪用済み」「KEV 登録」の有無だけを先に突き合わせる。** **③集計値がベンダーと第三者で食い違うことがある前提で、 社内の集計は「自社に該当するもの」だけを数える** ——**総件数を転記しない。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 利用者が外部から受け取った文書・圧縮ファイルを端末上で開く業務があり、その安全性の判断を Windows の警告表示（SmartScreen・Office 保護ビュー）に依存している
運用・監視□ 月例更新の社内報告を CVE の件数で行っており、「悪用が確認されているもの」を独立した数として出していない
運用・監視□ 脆弱性管理の期限を CISA の KEV だけ、または検知ルールをベンダー勧告だけを根拠に作っている
システム構成□ MotW が落ちた場合の受け皿としてアプリケーション制御（WDAC・AppLocker 等）を期待しているが、その受け皿の脆弱性を同じ頻度で追っていない
運用・監視□ 同じ火曜日に公表される他ベンダー（Adobe・SAP 等）の更新を、同じ作業計画の中で扱っていない
体制・契約□ 悪用済みの脆弱性について、指標（IoC）が公表されない場合に「適用する」以外の行動を決めていない
