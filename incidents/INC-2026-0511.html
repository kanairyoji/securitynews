守るための装置が2つ同時に、未認証で抜かれる原因・手口

Fortinet が2026年10月13日に Critical として公開した2件は、どちらもセキュリティ運用のための製品です（出典1・2）。

FortiSIEM は、組織内のログを集めて相関分析する SIEM 製品です。 CVE-2026-106173（FG-IR-26-180）は、その gRPC コンポーネントphQueryMaster にパストラバーサル（CWE-22）があり、細工したパケットによって未認証の攻撃者が任意のファイルを書き込める、という脆弱性です（出典1）。アドバイザリは影響を「不正なコードまたはコマンドの実行」と記しています（出典1）。

FortiSandbox は、検体を隔離環境で動かして挙動を見る製品です。 CVE-2026-107656（FG-IR-26-185）は、ウェブ管理インタフェースのアクセス制御とセッション管理の不備（CWE-288）により、細工した HTTP リクエストで GUI の認証を回避できる、という脆弱性です（出典2）。

ただし、本記録はこの2件が実際にそう使われたという材料を持っていません。 悪用の記載はアドバイザリにありません〈未確定2〉。

手口は7日後に全部出た——NUL バイトでパスを切り詰め、cron が動かす原因・手口

初報の時点では「技術的詳細は公表されていない」と記録しました（出典1）。2026年10月20日、Horizon3 の Zach Hanley が根本原因と悪用手順を公開し、あわせて GitHub に実証コードを置きました（出典8・9）。アドバイザリ公開から7日後です。

3段構えです（出典8）。

①未認証で到達できる理由。 phQueryMaster の中で grpcNotificationServer::run() が起動するgRPC サービスは、[::]:27918 を全インタフェースで待ち受けます。 SSL の設定でクライアント証明書の要求が既定値のまま置かれているため、証明書を持たないどの遠隔クライアントも接続できます。 「認証が無い」のではなく「認証を要求する設定を書いていない」形です（本記録の整理）。

②パスの外へ出る。 脆弱な RPC は grpcNotificationService.cpp の SendQueryResult です。 ハンドラは書き込み先を /query/result/ に攻撃者の与える query-id を検証せず連結して作るため、../ でディレクトリの外へ出られます。

③ファイル名を奪う。 サーバーは本来、result-<src>-<start>-<end>-<id>.dat という接尾部を自分で付けます。<id> はサーバーが生成するので攻撃者は指定できません。 ところがサーバーはヘッダ値を「クライアントが申告した長さ」のまま複製するため、query-id の中に NUL バイトを埋め込めます。 OS は NUL をパスの終端として扱い、サーバーが付けた接尾部を切り落とします。 結果、攻撃者は書き込み先を完全に指定でき、既存ファイルを所有者と権限を保ったまま上書きできます。

実行はここから間接的に起こります。 PoC が上書きするのは Redis のヘルスチェック用スクリプト/opt/charting/redishb.sh です。これは cron が60秒ごとに実行し、管理ユーザーの文脈で書き込み可能です（出典8）。攻撃者は書き込んだら待つだけで、コード実行は「盲目的」に、最大60秒後に起こります（出典8・9）。

〈本記録の評価〉 防御側にとって重いのは、この手口の「痕跡の残らなさ」です。 ①書き込みは既存ファイルの所有者と権限を保つため、権限やファイル一覧の差分では見つかりません。 ②実行は cron 経由なので、攻撃者のプロセスとしては現れません。 ③Horizon3 自身が「この脆弱性が悪用されたことを明示的に示すアプリケーションログは見つけられなかった」（原文英語）と記しています（出典8）。残るのはファイルの更新時刻だけです。

〈本記録の評価〉 一方で、60秒の遅延は防御側の猶予でもあります。 書き込みから実行までに最大60秒あるため、ファイル完全性監視が即時に発報する環境では、実行前に気づける可能性があります。 ただしこれは /opt/charting/redishb.sh を監視対象に入れている場合に限ります（本記録の留保。Fortinet はこのファイルについて何も案内していない）。

CVSS「9.4 と 9.8」の食い違いは報道の誤りではなく、Fortinet の2つの公表の差だった未確定事項

初報で〈齟齬1〉として記録したのは、「国内報道は 9.8 と伝えているが、Fortinet の PSIRT 本文は 9.4 である」という食い違いでした（出典1・4）。本記録はそこで一次資料の 9.4 を採り、報道値を齟齬として残しました。

2026年10月22日、NVD の API を直接引いて原因が分かりました（出典10）。

  • NVD に登録されている CVE-2026-106173 の CVSS 値は1件だけで、提出元は Fortinet 自身（psirt@fortinet.com）です
  • その値は基本値 9.8、ベクタはCVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H です
  • 一方 FG-IR-26-180 本文のベクタはAV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H/E:H/RL:O/RC:C です（出典1）

後半の3つが時間的指標です。 E:H（悪用コードの成熟度「高」）・RL:O（公式の修正あり）・RC:C（確認済み）を掛けると、9.8 は 9.4 に下がります。

つまり 9.8 は基本値、9.4 は現状値です。 同じ脆弱性の同じ評価で、どちらも Fortinet が出しています。 報道の誤りではありませんでした——本記録の初報の整理を訂正します（訂正に記録）。

〈本記録の評価〉 実務上は、どちらを採るかで判断は変わりません。 9.4 も 9.8 も Critical で、未認証・遠隔・影響は全面です。 変わるのは「スコアの出所を確かめずに食い違いを誤りと決めつけてはいけない」という教訓のほうです。

〈本記録の評価〉 むしろ注目すべきは E:H がアドバイザリ公開時点のベクタに含まれていたことです（出典1）。Fortinet は10月13日の時点で悪用コードの成熟度を「高」と評価していました。 ただし FG-IR-26-180 には改訂履歴が付いていないため、この値がいつ設定されたかは確認できません（本記録の留保）。同じ日に CISA（ADP）が NVD に入れた SSVC 判定は「悪用: PoC／自動化可能: はい／技術的影響: 全面」でした（出典10）。公開 PoC が出たのはその7日後です。

    取るべき行動 **①更新の前に、FortiSandbox の GUI アクセスログと FortiSIEM の 27918 への接続記録を外部へ退避する。** **②認証の記録が無いのに設定変更・ファイル作成が記録されている箇所を探す。** **③FortiSIEM 自身のログが信頼できない前提で、 前段のネットワーク機器・ファイアウォールのログも併せて確保する。**
  • **これらの製品に保存されている認証情報を棚卸しする**
    **SIEM はログ収集のために各機器への認証情報を保持することが多い** （本記録の整理。出典1・2 はこの点に触れていない）。 **未認証でのコード実行・認証回避が成立する脆弱性では、 その保持物が射程に入る**（本記録の評価）。
    取るべき行動 **①FortiSIEM に登録している収集用アカウント・API キー・ SNMP コミュニティ等を一覧にする。** **②各アカウントの権限が収集に必要な最小限かを確認する。** **③侵害の疑いがある場合に、どの順でどこまで入れ替えるかを決めておく （入れ替えの最中に監視が欠けることを含めて）。**
  • 攻撃の痕跡が「ファイルの更新時刻」だけなら、見るファイルを先に決めておく
    **Horizon3 は「この脆弱性が悪用されたことを明示的に示す アプリケーションログは見つけられなかった」（原文英語）と記している**（出典8）。 **手口がそれを説明している**——**書き込みは既存ファイルを 所有者と権限を保ったまま上書きし、実行は cron 経由で起こる**（出典8・9）。 **権限の差分にもプロセス一覧にも現れない。** **残るのはファイルの更新時刻だけである。** **一方で cron が60秒ごとであるため、書き込みから実行までに 最大60秒の猶予がある**——**即時に発報する仕組みがあれば、 実行前に気づける可能性がある**（本記録の評価）
    取るべき行動 ①**FortiSIEM の `/opt/charting/redishb.sh` と `/opt/phoenix/bin/phLicenseTool` をファイル完全性監視の対象に入れる** （出典8 が注目すべきファイルとして挙げた2つ。 **Fortinet はこれらについて何も案内していない**） ②**cron が実行するスクリプト類**を同様に棚卸しする—— 本件の本質は「定期実行されるスクリプトが書き込み可能だった」ことであり、 同じ形は他製品にもある（本記録の整理） ③すでに悪用された可能性を調べるときは、 **周囲のファイルと更新時刻が合わないものを探す**（出典8 の手段） ④**TCP 27918 への到達を、発信元を絞って制限する**（出典1 の回避策）—— **ノード間通信が同じポートを使うため、閉じるのではなく発信元で絞る**
