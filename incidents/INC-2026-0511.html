INC-2026-0511FortiSIEM/FortiSandbox に重大2件

Fortinet は2026年10月13日（米時間のパッチチューズデー）の PSIRT 公開で、 FortiSIEM の gRPC コンポーネント phQueryMaster に未認証で任意ファイル書き込みに至る パストラバーサル（CVE-2026-106173・CWE-22・CVSSv3 9.4・Critical・FG-IR-26-180）と、 FortiSandbox / FortiSandbox PaaS のウェブ管理インタフェースに未認証で認証を回避できる アクセス制御不備（CVE-2026-107656・CWE-288・CVSSv3 9.6・Critical・FG-IR-26-185）を 公表した——前者は FortiSIEM 7.5.0 のみが対象で TCP 27918 への到達を絞れば回避でき、 後者は FortiSandbox 5.0.0〜5.0.6 と 4.4.0〜4.4.9、PaaS 4.4 の全バージョンに影響する。 いずれも悪用は確認されていないと Fortinet は記載している

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月13日（Fortinet PSIRT の公開） 最終更新: 2026年10月14日

ログを集める装置と、マルウェアを調べる装置が、未認証で落ちます。

Fortinet は現地時間2026年10月13日（米国のパッチチューズデー）、PSIRT アドバイザリを一括公開しました（出典1・2・3）。本記録が Fortinet の PSIRT フィードを直接取得して数えたところ、2026年10月13日付のエントリは11件でした（出典3。計数は本記録）。そのうち2件が最高位の「Critical」です。

1件目は FortiSIEM の CVE-2026-106173（FG-IR-26-180）です（出典1）。gRPC の phQueryMaster コンポーネントにパストラバーサル（CWE-22）があり、細工したパケットによって未認証の攻撃者が任意のファイルを書き込み、不正なコードやコマンドの実行に至る可能性があります（出典1）。CVSSv3 は 9.4。影響を受けるのは FortiSIEM 7.5.0 のみで、7.5.1 以降へ更新すれば解消します。7.6 系と FortiSIEM Cloud は影響を受けません（出典1）。回避策として、TCP 27918 への到達を制限すれば本脆弱性は成立しません（出典1）。

2件目は FortiSandbox の CVE-2026-107656（FG-IR-26-185）です（出典2）。ウェブ管理インタフェースのアクセス制御とセッション管理に不備があり（CWE-288）、細工した HTTP リクエストで GUI の認証を回避できます（出典2）。CVSSv3 は 9.6。FortiSandbox 5.0.0〜5.0.6 は 5.0.7 以降へ、4.4.0〜4.4.9 は 4.4.10 以降へ更新します。FortiSandbox PaaS 5.0.0〜5.0.6 も同様で、PaaS 4.4 は全バージョンが対象で修正版への移行が必要です。5.2 系（PaaS 含む）は影響を受けません（出典2）。

本記録が、報道の要約には現れにくい点として記録しておくものが3つあります。

  • CVSS 値が報道と一次資料で食い違っている。 国内報道は両件とも「9.8」と伝えているが（出典4）、Fortinet の PSIRT 本文は 9.4（FortiSIEM）と9.6（FortiSandbox）である（出典1・2）〈齟齬1〉
  • FortiSIEM の脆弱性は、管理用の HTTPS ではなく TCP 27918 という固有ポートに効く。 「管理画面を閉じている」ことが対策になっていない（出典1。整理は本記録）
  • FortiSandbox PaaS、すなわちベンダーが運用する SaaS 形態も対象に含まれる。 PaaS 4.4 は「全バージョン」が影響を受ける（出典2）

2件とも「悪用の確認」は Fortinet のアドバイザリに記載がありません（出典1・2）。また本記録が2026年10月14日に確認した時点で、CVE-2026-107656 は NVD に登録されていません（出典5。確認は本記録）〈齟齬2〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**CVE-2026-106173 は、FortiSIEM 7.5.0 の gRPC phQueryMaster に対して 細工したパケットを送り、パストラバーサル（CWE-22）で任意のファイルを書き込み、 不正なコードまたはコマンドの実行に至らせる**（出典1）。 **CVE-2026-107656 は、FortiSandbox のウェブ管理インタフェースへ 細工した HTTP リクエストを送り、GUI の認証を回避する（CWE-288）**（出典2）。 **いずれも未認証・遠隔で成立する。具体的な手口は公表されていない**〈未確定3〉。

  1. 1. 初期侵入確認済
    **FortiSIEM 側では、攻撃者が TCP 27918（gRPC）に到達できる位置にいる必要がある** （出典1。整理は本記録）。 **FortiSandbox 側では、ウェブ管理インタフェースに HTTP で到達できればよい**（出典2）。 **どちらも認証は不要である**（出典1・2）。
    根拠: FG-IR-26-180 の回避策「TCP 27918 への到達制限」、 および両アドバイザリの「未認証の攻撃者」の記載（出典1・2）。
  2. 2. 実行確認済
    **CVE-2026-106173: パストラバーサルにより任意のファイルを書き込み、 不正なコードまたはコマンドの実行に至る**（出典1）。 **どのパスへ、どの権限で書き込めるかは公表されていない**〈未確定3〉。
    根拠: FG-IR-26-180（CWE-22・CVSSv3 9.4・影響「execute unauthorized code or commands」）（出典1）。
  3. 3. 権限昇格確認済
    **CVE-2026-107656: GUI の認証を回避し、 管理インタフェースの機能に未認証で到達する**（出典2）。 **回避後に何ができるかの具体はアドバイザリに記載が無い**（本記録の明示）。
    根拠: FG-IR-26-185（CWE-288・CVSSv3 9.6）（出典2）。
  4. 4. 収集推定
    **本記録の評価である。** **SIEM には各機器のログと、多くの場合は収集のための認証情報が集約される。 サンドボックスには検体と解析結果が置かれる。** **そのため、どちらの製品も掌握されれば調査の材料そのものが 攻撃者の手に入る位置にある**（本記録の評価）。 **実際にそうした持ち出しが起きたことを示す資料は無い**〈未確定2〉。

守るための装置が2つ同時に、未認証で抜かれる原因・手口

Fortinet が2026年10月13日に Critical として公開した2件は、どちらもセキュリティ運用のための製品です（出典1・2）。

FortiSIEM は、組織内のログを集めて相関分析する SIEM 製品です。 CVE-2026-106173（FG-IR-26-180）は、その gRPC コンポーネントphQueryMaster にパストラバーサル（CWE-22）があり、細工したパケットによって未認証の攻撃者が任意のファイルを書き込める、という脆弱性です（出典1）。アドバイザリは影響を「不正なコードまたはコマンドの実行」と記しています（出典1）。

FortiSandbox は、検体を隔離環境で動かして挙動を見る製品です。 CVE-2026-107656（FG-IR-26-185）は、ウェブ管理インタフェースのアクセス制御とセッション管理の不備（CWE-288）により、細工した HTTP リクエストで GUI の認証を回避できる、という脆弱性です（出典2）。

本記録が重く見るのは、2件が「守る側の装置」であることです（本記録の評価）。SIEM にはログが集まります。どのサーバがどの時刻に何をしたかの記録、そして多くの場合、各機器へ接続するための認証情報が入っています。 サンドボックスには検体、すなわち攻撃者が送り込んだものの実物が入ります。 どちらも、攻撃者から見れば「調査の結果が置いてある場所」です（本記録の評価）。

ただし、本記録はこの2件が実際にそう使われたという材料を持っていません。 悪用の記載はアドバイザリにありません〈未確定2〉。

「管理画面を閉じている」は、FortiSIEM の対策になっていない対策・注意喚起

CVE-2026-106173 の回避策として、Fortinet は「TCP 27918 への到達を制限すれば本脆弱性を防げる」と記しています（出典1）。

これは、脆弱な入口が HTTPS の管理画面ではないことを意味します（本記録の整理）。FortiSIEM の管理 GUI を社内からのみ到達可能にしていても、gRPC の 27918 が別のネットワークに開いていれば残ります。 逆に言えば、適用の猶予を作る手段としてこの回避策は有効です（出典1。評価は本記録）。

確認すべきことは2つです（本記録の整理）。①自組織の FortiSIEM が 7.5.0 かどうか。7.6 系と FortiSIEM Cloud は影響を受けません（出典1）。②TCP 27918 がどこから到達できるか。 FortiSIEM は collector / supervisor / worker といった複数ノードで構成されることがあり、ノード間通信の経路を絞りすぎると機能が止まる可能性があります（本記録の留保。出典1 はノード構成に触れていない）。回避策の適用前に、この影響を確認する必要があります。

FortiSandbox は PaaS も対象で、4.4 系は「全バージョン」被害規模・影響範囲

CVE-2026-107656 の影響範囲は、オンプレミス版と PaaS 版の両方に及びます（出典2）。

本記録が注目するのは PaaS 4.4 の行です（本記録の評価）。「全バージョンが影響を受け、修正版への移行が必要」とは、その系列に修正が出ないという意味です（出典2。読み方は本記録）。PaaS 形態は、ベンダーが基盤を運用します。 利用者は「自分でパッチを当てる」ことができません。 したがって利用者側の作業は、更新の実施状況をベンダーに確認し、完了までの期間を把握することになります（本記録の評価）。その実施主体と時期はアドバイザリに書かれていません〈未確定5〉。

CVSS の数字が、報道と一次資料で食い違っている未確定事項

本件では、国内報道と Fortinet の一次資料で CVSS 値が一致していません〈齟齬1〉。

出所 FortiSIEM（CVE-2026-106173） FortiSandbox（CVE-2026-107656）
Fortinet PSIRT（出典1・2） 9.4 9.6
Security NEXT（出典4） 9.8 9.8

本記録は、2026年10月14日に FG-IR-26-180 と FG-IR-26-185 の本文を直接取得し、9.4 と 9.6 を確認しました（出典1・2）。また第三者のまとめ記事では、本文に 9.4 と書きながら同じ記事の表に 9.8 と書くという矛盾が生じています（出典6）。

実務上の意味は限定的です（本記録の評価）。9.4 も 9.6 も 9.8 も Critical の帯に入り、「未認証でコード実行」「未認証で認証回避」という性質は変わりません。 ただし、CVSS を閾値にして対応優先度を自動判定している組織では、9.5 や 9.8 といった境界の設定次第で扱いが変わります（本記録の評価）。一次資料の値を取り込む経路を持っているかが、ここで効きます。

あわせて、本記録が2026年10月14日に NVD の API を引いた時点では、CVE-2026-107656 は結果0件でした（出典5）〈齟齬2〉。NVD を唯一の取り込み元にしている組織は、この時点で本件を認識できません（本記録の評価）。

CISO・経営層への示唆
  • **セキュリティ運用の基盤そのものを、脆弱性管理と事業継続計画の対象に入れる**
    **本件の Critical 2件は、SIEM とサンドボックス—— いずれも「守るための装置」である**（出典1・2）。 **こうした製品は社内の資料で「対策」として扱われ、 「管理すべき資産」の欄から落ちやすい**（本記録の評価）。 **さらに、更新作業そのものが監視や解析を一時的に止める**（本記録の評価）。
    取るべき行動 **①資産台帳に SIEM・サンドボックス・EDR 管理サーバ・ログ収集基盤が 個別の資産として登録されているかを確認する。** **②各基盤について「更新のため止めるとき、その間の監視を何で代替するか」を あらかじめ決めておく（代替の収集先・手動確認の範囲・容認する空白時間）。** **③「監視基盤が侵害された場合」の対応手順を、 通常のサーバ侵害とは別に作る（ログの信頼性が前提から崩れるため）。**
  • **PaaS・SaaS 形態で使っている製品は、「自社で適用できない」ことを前提に管理する**
    **CVE-2026-107656 は FortiSandbox PaaS にも影響し、 PaaS 4.4 は全バージョンが対象で修正済みリリースへの移行が必要である**（出典2）。 **PaaS の更新は利用者が実施できない。** **実施主体と完了時期はアドバイザリに書かれていない**〈未確定5〉。
    取るべき行動 **①ベンダー運用型（PaaS / SaaS / マネージド）で使っている セキュリティ製品を一覧にし、「誰がパッチを当てるか」を列として持つ。** **②契約書・SLA に、脆弱性修正の適用期限と利用者への通知義務が 書かれているかを確認する。** **③書かれていない場合、次の更新交渉の論点に加える。**
  • **脆弱性情報の取り込み経路を、NVD だけに依存させない**
    **本記録が2026年10月14日に照会した時点で、 CVE-2026-107656 は NVD に登録されていなかった**（出典5）〈齟齬2〉。 **CVSS 値も、ベンダーの一次資料と報道で食い違っていた**（出典1・2・4）〈齟齬1〉。
    取るべき行動 **①自組織の脆弱性情報の取り込み元を書き出し、 NVD／JVN／ベンダー PSIRT のどれを見ているかを明確にする。** **②主要ベンダーの PSIRT フィード（本件なら Fortinet の ir.xml）を 直接購読しているかを確認する。** **③CVSS を閾値にした自動判定を使っている場合、 値の出所がベンダーか NVD かで扱いが変わることを手順に明記する。**
  • **「Critical が同日に複数」という状況の優先順位を、事前に決めておく**
    **本件では2026年10月13日に11件が一括公開され、うち2件が Critical だった** （出典1・2・3。計数は本記録）。 **同じ日に Microsoft の月例更新も重なっている**（本記録の整理）。
    取るべき行動 **①「未認証・遠隔」「回避策の有無」「製品が持つ権限」の3点で 優先順位を決める社内ルールを作る。** **②パッチチューズデーの翌営業日に、 自組織が使う製品の Critical を棚卸しする時間を定例化する。** **③回避策が示されている脆弱性は「回避策を先に適用し、 更新は計画どおり」という選択を許すかどうかを決めておく。**
セキュリティ技術者への示唆
  • **FortiSIEM は、バージョンと TCP 27918 の到達範囲を同時に確認する**
    **影響を受けるのは FortiSIEM 7.5.0 のみで、 7.6 系と FortiSIEM Cloud は影響を受けない**（出典1）。 **回避策は「TCP 27918 への到達制限」であり、 脆弱な入口は管理用の HTTPS ではない**（出典1）。
    取るべき行動 **①稼働中の FortiSIEM のバージョンを確認する（7.5.0 かどうか）。** **②27918 がどのネットワークから到達できるかを、 実際にポートスキャンまたはファイアウォール設定の確認で調べる。** **③ノード構成（supervisor / worker / collector）を確認し、 到達制限がノード間通信を壊さない範囲を決めてから適用する。** **④7.5.1 以降へ更新する。**
  • **FortiSandbox は 5.2 系かどうかで対応が分かれる**
    **5.2 系（PaaS 含む）は影響を受けず、 5.0.0〜5.0.6 と 4.4.0〜4.4.9、PaaS 4.4 の全バージョンが対象である**（出典2）。
    取るべき行動 **①稼働中の FortiSandbox のバージョンと形態（オンプレ / PaaS）を確認する。** **②5.0 系は 5.0.7 以降、4.4 系は 4.4.10 以降へ更新する。** **③PaaS 4.4 は修正版が出ないため、移行先と期限を Fortinet に確認する。** **④更新前に、GUI へ到達できる発信元を記録しておく （事後に「誰が到達できたか」を確かめるため）。**
  • **更新前に、管理インタフェースへのアクセスログを退避する**
    **両アドバイザリに、侵害を判定する指標は示されていない**（出典1・2）〈未確定4〉。 **未認証で認証を回避できる脆弱性では、 「正規の認証記録が無いまま操作された痕跡」を探すことになる**（本記録の評価）。 **更新作業でログが切り替わると、その材料が失われうる**（本記録の評価）。
    取るべき行動 **①更新の前に、FortiSandbox の GUI アクセスログと FortiSIEM の 27918 への接続記録を外部へ退避する。** **②認証の記録が無いのに設定変更・ファイル作成が記録されている箇所を探す。** **③FortiSIEM 自身のログが信頼できない前提で、 前段のネットワーク機器・ファイアウォールのログも併せて確保する。**
  • **これらの製品に保存されている認証情報を棚卸しする**
    **SIEM はログ収集のために各機器への認証情報を保持することが多い** （本記録の整理。出典1・2 はこの点に触れていない）。 **未認証でのコード実行・認証回避が成立する脆弱性では、 その保持物が射程に入る**（本記録の評価）。
    取るべき行動 **①FortiSIEM に登録している収集用アカウント・API キー・ SNMP コミュニティ等を一覧にする。** **②各アカウントの権限が収集に必要な最小限かを確認する。** **③侵害の疑いがある場合に、どの順でどこまで入れ替えるかを決めておく （入れ替えの最中に監視が欠けることを含めて）。**
