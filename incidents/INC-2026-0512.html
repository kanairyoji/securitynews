INC-2026-0512HAProxy DPAPI にmTLS起因の認証外れ

HAProxy の設定管理 API「HAProxy Data Plane API」に、相互TLS（mTLS）を有効にすると HTTP と UNIX ドメインソケットの認証が丸ごと外れる脆弱性（CVE-2026-109575・CWE-306・ CVSSv3.1 9.8・Critical）が2026年10月12日に公表された——Server.ConfigureAPI() が tls_ca と数値の tls_port を検出するとベーシック認証をハンドラ全体で無効化し、 mTLS は HTTPS 経路でしか強制されないため、同時に待ち受けている HTTP と UNIX ソケットが「認証なしで開く」状態になる。未認証の攻撃者が API の管理権限を得て 設定を平文で読み、raw 設定エンドポイントで設定そのものを置き換えられる。 修正は2026年10月9日公開の 3.4.4 / 3.3.9 / 3.2.17 / 3.0.25 / 2.9.29

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月12日（CVE-2026-109575 の公表） 最終更新: 2026年10月14日

認証を強くしたら、認証が外れました。

2026年10月12日、HAProxy の設定管理 API である「HAProxy Data Plane API」の認証バイパス脆弱性 CVE-2026-109575 が公表されました（出典1）。CVSSv3.1 基本値は 9.8（Critical）、CWE-306（重要な機能に対する認証の欠如）、採番は MITRE です（出典1）。

本記録が重く見るのは、引き金が「設定の不備」ではなく「相互TLS認証（mTLS）を設定したこと」である点です（出典1。評価は本記録）。

CVE の記述によれば、TLS の CA（tls_ca）と数値の TLS ポート（tls_port）が設定されていると、HTTP・HTTPS・UNIX ドメインソケットの待ち受けが共有する1つのハンドラ上で、ベーシック認証が全体的に無効化されます（出典1）。ところが mTLS が強制されるのは HTTPS の経路だけです。 結果として、同時に動いている HTTP と UNIX ソケットの待ち受けが「認証なしで開く（fail open）」状態になります（出典1）。

成立すると、未認証の攻撃者が API の管理権限を完全に取得し、設定を平文で読み出し、raw 設定エンドポイントを使って設定そのものを置き換えられます（出典1）。HAProxy はロードバランサであり、その設定とは「どの通信をどこへ送るか」そのものです（本記録の評価）。

影響範囲は広いです（出典1）。コミュニティ版は 2.2.0 から 3.4.3 まで、Enterprise 版も対応する系列が対象です。 修正版は 3.4.4 / 3.3.9 / 3.2.17 / 3.0.25 / 2.9.29 で、現地時間2026年10月9日に公開されました（出典1・2・4）。

本記録が、報道の要約には現れにくい点として記録しておくものが3つあります。

  • GitHub のリリースノートには CVE 番号が書かれていない。 該当の修正は「BUG/MAJOR: adapters: enforce basic auth on non-mTLS listeners」（原文英語。日本語訳: mTLS でない待ち受けにベーシック認証を強制する）という1行で、5つのリリースに同日付で入っている（出典2）〈齟齬1〉
  • HAProxy 公式ドキュメントの変更履歴ページには、本記録の確認時点で修正版の記載が無かった（出典3）〈齟齬2〉
  • CVE レコードの影響範囲に、3.1 系の独立した修正版が無い。 「3.1-ee 〜 3.2.16-ee1 → 3.2.17-ee1」「3.1.0 〜 3.2.16 → 3.2.17」という記載であり、3.1 系の利用者は 3.2 系へ上がることになる（出典1。整理は本記録）

悪用については、CVE レコードに付随する CISA の評価が「Exploitation: none（悪用なし）／Automatable: yes（自動化可能）／Technical Impact: total（技術的影響は全面的）」となっています（出典1）。「自動化可能」と評価されている点に注意が要ります（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**tls_ca と数値の tls_port が設定された HAProxy Data Plane API に対し、 未認証の攻撃者が HTTP または UNIX ドメインソケットの管理エンドポイントへ到達し、 認証を通らずに API の管理権限を得る**（出典1）。 **その後、設定を平文で読み出し、raw 設定エンドポイントで設定を置き換えられる**（出典1）。 **実環境での悪用は観測されていないと CISA が評価している**（出典1）〈未確定4〉。

  1. 1. 偵察確認済
    **攻撃者は、HAProxy Data Plane API の HTTP 待ち受けを見つける必要がある** （出典1。整理は本記録）。 **CISA の SSVC 評価は Automatable: yes であり、 偵察から成立までを自動化できるとされている**（出典1）。
    根拠: CVSS ベクトルの AV:N / AC:L / PR:N / UI:N、 および CISA ADP の Automatable: yes（出典1）。
  2. 2. 初期侵入確認済
    **HTTP または UNIX ソケットの管理エンドポイントへアクセスする。** **tls_ca と数値の tls_port が設定されていると、 共有ハンドラ上でベーシック認証が全体的に無効化されているため、 認証を求められない（fail open）**（出典1）。
    根拠: CVE レコードの説明文——"Basic authentication is globally disabled on a handler shared by HTTP, HTTPS, and UNIX socket listeners. Mutual TLS is enforced only on the HTTPS path, so the other active listeners fail open." （原文英語。出典1）。
  3. 3. 内部探索確認済
    **API の管理権限で、HAProxy の設定を平文で読み出す （原文英語: "read cleartext configuration"）**（出典1）。
    根拠: CVE レコードの影響の記載（出典1）。
  4. 4. 影響（暗号化・破壊・改ざん）確認済
    **raw 設定エンドポイントを通じて設定そのものを置き換える （原文英語: "replace the configuration through the raw configuration endpoint"）**（出典1）。 **本記録の評価として、ロードバランサの設定の置換は 通信の宛先の書き換えに等しい**（本記録の評価）。 **実際にそうした操作が行われた事例は公表されていない**〈未確定4〉。
    根拠: CVE レコードの影響の記載、および CVSS の I:H / A:H（出典1）。

mTLS を設定したことが、HTTP と UNIX ソケットの認証を外す引き金になる原因・手口

HAProxy Data Plane API は、HAProxy の設定を API 経由で管理するためのコンポーネントです（出典4）。この API は複数のトランスポートで待ち受けることができます—— HTTP、HTTPS、そして UNIX ドメインソケットです（出典1）。

CVE の記述によれば、不備は Server.ConfigureAPI() の認証ロジックにあります （原文英語: "authentication logic in Server.ConfigureAPI() improperly drops security controls across multiple transport types"。日本語訳: Server.ConfigureAPI() の認証ロジックが、複数のトランスポート種別をまたいでセキュリティ制御を不適切に落としている）（出典1）。

成立の条件と結果を分けて書くと、次のようになります（出典1。整理は本記録）。

内容
前提 TLS の CA（tls_ca）と数値の TLS ポート（tls_port）が設定されている
起きること HTTP・HTTPS・UNIX ソケットが共有するハンドラ上で、ベーシック認証が全体的に無効化される
mTLS の効き方 HTTPS の経路でのみ強制される
残る穴 HTTP と UNIX ソケットの待ち受けが「認証なしで開く（fail open）」

ここが本件の肝です（本記録の評価）。mTLS の設定は、認証を弱めるためにやることではありません。 クライアント証明書による相互認証は、ベーシック認証より強い手段です。 ところが本件では、それを設定した事実が「ベーシック認証を無効にしてよい」という判断に使われ、しかし mTLS 自体は HTTPS でしか効かない、という組み合わせになっていました（出典1）。

強化策を適用した環境ほど穴が開く、という構造です（本記録の評価）。「設定を間違えた環境が危ない」のではなく、「設定を進めた環境が危ない」ことになります。

修正は、リクエストごとに TLS の接続状態を検証するモデルへの変更と記載されています（原文英語: "a per-request TLS connection-state validation model"）（出典1）。GitHub 側の表現は「mTLS でない待ち受けにベーシック認証を強制する」です（出典2）。

取れるのは「どの通信をどこへ送るか」そのもの被害規模・影響範囲

CVE の記述によれば、成立した場合に攻撃者ができることは3つです（出典1）。

  • API の管理権限を完全に取得する（原文英語: "gain full API administrative access"）
  • 設定を平文で読み出す（原文英語: "read cleartext configuration"）
  • raw 設定エンドポイントを通じて設定を置き換える（原文英語: "replace the configuration through the raw configuration endpoint"）

本記録の評価として、3つ目の重さを書いておきます。 HAProxy はロードバランサ・リバースプロキシであり、その設定は「どのホスト名のどの通信を、どのバックエンドへ送るか」の定義です（本記録の評価）。設定を置き換えられるということは、通信の宛先そのものを書き換えられるということです。

また2つ目——設定の平文読み出し——も軽くありません。 HAProxy の設定ファイルには、バックエンドの構成、ヘルスチェックの経路、場合によっては TLS の鍵のパスや認証に関わる値が含まれます（本記録の評価。出典1 は設定の内容に触れていない）。

CVSS ベクトルが C:H / I:H / A:H、すなわち機密性・完全性・可用性のすべてがHigh になっているのは、この3点に対応しています（出典1。整理は本記録）。

ただし、実際にそうした被害が起きたことを示す資料は無く、CISA の評価も Exploitation: none です（出典1）〈未確定4〉。

「自動化可能」という評価が付いている評価・解釈

CVE レコードには CISA の ADP（Vulnrichment）による SSVC 評価が付与されています（出典1）。

項目 評価
Exploitation（悪用の観測） none（観測されていない）
Automatable（自動化可能性） yes
Technical Impact（技術的影響） total（全面的）

本記録が注目するのは Automatable: yes です（本記録の評価）。SSVC におけるこの項目は、偵察から成立までを自動化できるか、すなわち標的を探して一括で攻撃できるかを示します（本記録の整理）。本件は未認証・ネットワーク経由・利用者の操作不要（AV:N / PR:N / UI:N）で、条件に合う待ち受けを見つければそのまま成立します（出典1）。

したがって、Exploitation: none（現時点で悪用の観測なし）とAutomatable: yes（自動化可能）の組み合わせは、「今は静かだが、動き出せば速い」という読み方になります（本記録の評価）。修正版は10月9日に出ており、CVE 番号が付いたのは10月12日です（出典1・2）。本記録の作成時点（10月14日）は、公表から2日目です。

  • **「強化策を適用した環境ほど穴が開く」型の脆弱性があることを、前提に置く**
    **本件の成立条件は、設定の不備ではなく mTLS の設定である**（出典1）。 **クライアント証明書による相互認証は、ベーシック認証より強い手段であり、 通常は「やるべきこと」として推奨される**（本記録の評価）。 **その適用が引き金になる構造だった。**
    取るべき行動 **①「対策を適用済み」の一覧を、そのまま安全の根拠として扱わない方針を明文化する。** **②強化策を適用した構成について、適用後の実際の挙動 （どの経路でどの認証が効いているか）を検証する工程を手順に入れる。** **③製品の脆弱性情報を読むとき、「影響を受ける条件」の欄を バージョンだけでなく設定の組み合わせまで読む運用にする。**

セキュリティ技術者への示唆
  • **tls_ca と tls_port の設定有無を、まず確認する**
    **本脆弱性は、TLS の CA（tls_ca）と数値の TLS ポート（tls_port）が 設定されているときに成立する**（出典1）。 **設定していなければ、ベーシック認証は無効化されない** （出典1。読み方は本記録）。
    取るべき行動 **①稼働中の Data Plane API の設定で tls_ca と tls_port を確認する。** **②両方が設定されている場合、HTTP の待ち受けと UNIX ドメインソケットの待ち受けが有効かを確認する。** **③有効なら、実際に認証なしで API を叩けるかを 自組織の管理下で検証する（検証は本番以外で行う）。** **④修正版（3.4.4 / 3.3.9 / 3.2.17 / 3.0.25 / 2.9.29）へ更新する。**
  • **UNIX ドメインソケットの待ち受けを、認証の対象として棚卸しする**
    **本件では HTTP と UNIX ソケットの両方が fail open する**（出典1）。 **UNIX ソケットは「ホスト内だから安全」と扱われやすいが、 同一ホスト上の他プロセス・他コンテナから到達できる** （本記録の評価。出典1 は到達経路に触れていない）。
    取るべき行動 **①Data Plane API が UNIX ソケットで待ち受けているパスを確認する。** **②そのソケットのファイル権限と、 同一ホスト上でどのプロセス・利用者が到達できるかを確認する。** **③コンテナで動かしている場合、ソケットがボリュームとして 他のコンテナへ共有されていないかを確認する。**
  • **設定の正本を、API の外側に持つ**
    **成立した場合、攻撃者は raw 設定エンドポイントで 設定を置き換えられる**（出典1）。 **本記録の評価として、ロードバランサの設定の置換は 通信の宛先の書き換えに等しい**（本記録の評価）。
    取るべき行動 **①HAProxy の設定を構成管理リポジトリで管理し、 稼働中の設定との差分を定期的に比較する。** **②差分が出たときに通知する仕組みを入れる。** **③比較の実行を Data Plane API 経由だけで行わない （掌握されていれば API の応答も信頼できない）。**
  • **更新前に、API のアクセスログを退避する**
    **侵害を判定する指標は公表されていない**（出典1・2）〈未確定5〉。 **認証を通らずに通る脆弱性では、 認証の失敗ログが残らない可能性がある**（本記録の評価）。 **したがって探すのは「認証の記録が無いのに行われた設定の読み出し・変更」になる** （本記録の整理）。
    取るべき行動 **①更新前に Data Plane API のアクセスログを外部へ退避する。** **②設定の読み出し・変更を行ったエンドポイントの呼び出し記録と、 認証の記録を突き合わせる。** **③Data Plane API 自身のログだけでなく、 前段のネットワーク機器・リバースプロキシのログも確保する。**
