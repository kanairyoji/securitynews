INC-2026-0513偽WatchGuard VPNサイトでMSP被害

Huntress は2026年10月13日、マネージドサービスプロバイダ（MSP）の管理者が Bing で「watchguard vpn sll download」と打ち間違えて検索し、8秒後に偽サイト www.watchguard-vpn[.]net を開いて VPN の接続情報（サーバ・ログイン・パスワード）を 入力しかけた事案を公表した——偽サイトは1回目の入力を必ず「入力内容が誤っています」と 赤字で拒否して2回打たせ、2回目の送信後に配るのは**WatchGuard 公式CDN の 正規の署名済みインストーラ**である。マルウェアを一切介さないため端点の防御に 掛からず、2026年10月8日時点で VirusTotal の検知は誘導ドメイン7ベンダー・ 収集ドメイン2ベンダーだけだった。Huntress は検知から21秒で警報を上げている

脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）
初報: 2026年10月13日（Huntress の公表） 最終更新: 2026年10月14日

マルウェアを配らないことが、この攻撃の技術です。

2026年10月13日、Huntress が自社 SOC の調査事例を公表しました（出典1）。2026年10月7日、あるマネージドサービスプロバイダ（MSP）の管理者が、Bing で「watchguard vpn sll download」と検索しました（出典1）。"ssl" の打ち間違いです。 その8秒後、管理者は検索結果からwww.watchguard-vpn[.]net（ページ題名「WatchGuard Firebox VPN Client」）を開いていました（出典1）。

偽サイトの振る舞いには、2つの仕掛けがあります（出典1）。

1つ目は、入力を2回させることです。 「WatchGuard SSL VPN をインストールするには、接続情報を入力してください」（原文英語）という小窓が開き、サーバ・ログイン・パスワードの3つを求めます（出典1）。正規の Mobile VPN with SSL クライアントも接続時にこの3つを聞くため、見た目に違和感がありません（出典1）。ところが約150行の平文の JavaScript（popup.js）は、1回目の送信を必ず拒否します——入力欄を空にし、見出しを赤字で「入力内容が誤っています。インストールを開始するにはもう一度入力してください」（原文英語）に差し替え、attempt を2に進めます（出典1）。Huntress の評価はこうです——打ち間違えた人はより丁寧に打ち直し、どのパスワードか迷っていた人は別のパスワードを試すので、攻撃者は検証用に2組目を得る（出典1）。

2つ目は、配るものが本物であることです。 2回目の送信後、小窓は緑色になって「VPN クライアントのインストールを開始しました」（原文英語）と表示し、隠しリンクを自動でクリックします（出典1）。その先は https://cdn.watchguard.com/SoftwareCenter/Files/MUVPN_SSL/12_11_5/WG-MVPN-SSL_12_11_5.exe ——WatchGuard の公式CDN です（出典1）。Huntress はこのファイルの Authenticode の SHA256 ダイジェストを再計算し、署名内のダイジェストと一致することを確認しています。すなわち WatchGuard が署名した後に改変されていません（出典1）。

本記録が重く見るのは、この2つ目です（本記録の評価）。トロイの木馬化したインストーラも悪性 DLL も存在しません。 検知すべき実行ファイルが無く、被害者は期待した成果物（本物のクライアント）を手に入れるため、後から見ても何も不自然に見えません（出典1。評価は本記録）。

実際、2026年10月8日時点の検知は薄いものでした（出典1）。誘導ドメインを悪性と判定していた VirusTotal のベンダーは7社、認証情報の収集先ドメインは2社。どちらの IP にも AbuseIPDB の報告はありませんでした（出典1）。

この事案で被害が広がらなかった理由は、端点の防御ではありません（本記録の評価）。Huntress Managed Defender が、悪性ドメインの読み込みから21秒後に警報を上げ、SOC が組織へ復旧手順を提示しています（出典1）。また調査対象の端末のブラウザ履歴には cdn.watchguard.com からのダウンロード記録が無く、2回目の送信まで完了していなかったとみられます——ただし1回目で認証情報を入力した可能性は残ります（出典1）。

背景には同じ系統の報告が2つあります（出典1・2）。2026年1月13日、WatchGuard の Secplicity（Red Cell）がVPN クライアントの偽ダウンロードサイト群を報告しており、watchguard-vpn[.]net はその時点から記録されています（出典1・2）。2026年3月には Microsoft Threat Intelligence が、watchguard-vpn[.]com に結びつく活動を、2025年5月から活動する金銭目的の攻撃者 Storm-2561 に帰属させています（出典1）。ただし、2026年10月の本事案を Storm-2561 に帰属させた記述はHuntress の報告には無く、本記録も帰属を述べません〈齟齬1〉。

1回目を必ず拒否する——これが認証情報を2組とる設計である原因・手口

偽サイトの認証情報収集は、popup.js という1つのファイルで完結しています（出典1）。Huntress は「約150行の、平文で難読化されていない JavaScript」と記しています（出典1）。

動きを順に追うと、次のようになります（出典1）。

段 起きること
1 利用者がダウンロードの選択肢をクリックすると小窓が開く
2 「WatchGuard SSL VPN をインストールするには、接続情報を入力してください」（原文英語）と表示し、サーバ・ログイン・パスワードの3つを求める

3つの入力項目のうち、Huntress が特に有用だと指摘するのは「サーバ」の欄です（出典1）。攻撃者は、認証先となる VPN サーバのアドレスをそこで得ます（出典1）。ログインとパスワードだけでは、どこへ使うかが分かりません。

本記録の評価として、ここに技術的な高度さはありません（本記録の評価）。難読化されていない150行の JavaScript です。 効いているのは、人が「入力を間違えた」と思ったときの行動の予測です。

被害が止まったのは「21秒」のほう組織の対応

この事案で被害が拡大しなかった要因は、端点のマルウェア検知ではありません（本記録の評価）。配られたのは正規の署名済みファイルであり、検知すべき実行ファイルが存在しないからです（出典1）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
機能した**本記録の評価**——**本事案では、手口を公表する判断が妥当である。** **マルウェアを介さない手口は端点の防御で止まらないため、 利用者が画面で見分けるしかなく、 「1回目は必ず拒否される」という具体を知らせることに価値がある**（本記録の評価）。 **また Huntress は、同一運用者かどうかを証拠で確定できないという 留保を明記しており、帰属を言い過ぎていない**（出典1。評価は本記録）。
評価材料なし**本記録の評価**——**通知の時期と、ドメインのオフライン化の因果が 報告に書かれていないため、通知の効果を評価できない**〈未確定4〉。 **また WatchGuard 側から2026年10月の活動についての公表を 本記録は確認できていない**〈齟齬2〉。
CISO・経営層への示唆
  • **「マルウェアを配らない攻撃」を、端点の防御の外側として扱う**
    **本事案で配られたのは、WatchGuard の公式CDNにある 正規の署名済みインストーラだった**（出典1）。 **トロイの木馬化したファイルも悪性 DLL も無い**（出典1）。 **実際、2026年10月8日時点で誘導ドメインを悪性と判定していた VirusTotal のベンダーは7社、収集先は2社だった**（出典1）。
    取るべき行動 **①自組織の防御のうち「悪性ファイルの検知」に依存している部分と、 「到達先のドメイン・通信を見る」部分を書き分ける。** **②認証情報をブラウザで入力させる攻撃に対して、 どの層が検知するのかを確認する（端点・プロキシ・DNS・SaaS 側のいずれか）。** **③「検知がゼロ件だった」という報告を、 攻撃が無かった証拠として扱わない方針を明文化する。**
  • **MFA を、認証情報が漏れる前提の最後の砦として位置づける**
    **本事案では、サーバ・ログイン・パスワードの3点が同時に求められている**（出典1）。 **Huntress は「サーバ欄は攻撃者にとってとくに有用で、 認証先となる VPN サーバのアドレスを与える」と述べている**（出典1）。 **パスワードを変えても、狙う先は攻撃者に知られたままになる**（本記録の評価）。
    取るべき行動 **①すべての VPN・リモートアクセス経路で MFA が強制されているかを確認する。** **②MFA が入っていない経路を一覧にし、期限を付けて潰す。** **③中間者型（AiTM）の手口に発展した場合に備え、 フィッシング耐性のある方式（FIDO2 等）への移行計画を持つ （本件では AiTM は観測されていない。本記録の留保）。**
  • **ソフトウェアの入手経路を、検索に任せない**
    **起点は「watchguard vpn sll download」という打ち間違いの検索であり、 その8秒後に偽サイトがクリックされている**（出典1）。 **8秒は検索結果を吟味する時間ではない**（本記録の評価）。 **Huntress も「公式の配布リンクを顧客向け文書に明記し、 ブックマークしておく」ことを挙げている**（出典1）。
    取るべき行動 **①業務で使うクライアントソフトの公式配布URLを一覧化し、 社内文書に固定する（検索させない）。** **②可能なものは社内の配布基盤に置き、 利用者が外部から落とす必要を無くす。** **③管理者が使うツールこそ対象に含める—— 本事案の被害者は MSP の管理者である**（出典1）。
  • **自社が MSP・受託運用を行っている場合、自社の管理者が標的であることを前提にする**
    **本事案の被害者は、MSP の管理者である**（出典1）。 **MSP の管理者の VPN 認証情報は、 顧客環境への到達手段になりうる**（本記録の評価。 出典1 は顧客への波及に触れていない）〈未確定1〉。
    取るべき行動 **①顧客環境へ到達できる自社アカウントを棚卸しし、 MFA と到達元の制限を確認する。** **②管理者のアカウントについて、 「認証情報が漏れた場合に何件の顧客環境へ届くか」を数える。** **③顧客との契約・手順書に、 自社側で認証情報の漏えいが疑われた場合の通知手順を書く。**
セキュリティ技術者への示唆
  • **収集先ドメインへの POST を見る検知を持つ**
    **認証情報はブラウザから watchguard-ssl[.]online へ JSON で POST される**（出典1）。 **この通信はネットワーク側で見える**（本記録の整理）。 **一方、2026年10月8日時点でこのドメインを悪性と判定していた VirusTotal のベンダーは2社だけだった**（出典1）。
    取るべき行動 **①プロキシ・DNS のログで、 業務と無関係な新規ドメインへの POST を抽出できるかを確認する。** **②VPN 製品名を含む類似ドメイン （vendor 名 + vpn / ssl 等の組み合わせ）への到達を監視対象に入れる。** **③ドメイン評価（レピュテーション）だけに依存した遮断の限界を 運用手順に書いておく——本件では7社・2社しか判定していない。**
  • **新規登録ドメインの遮断期間を見直す**
    **誘導ドメインの WHOIS 上の作成日は2026年8月22日で、 被害発生は2026年10月7日である**（出典1）。 **本記録が算出すると46日が経過している**（本記録の算出）。 **「新規登録ドメインを30日遮断する」型の運用では間に合わない** （本記録の評価。出典1 はこの種の対策に触れていない）。
    取るべき行動 **①自組織の新規登録ドメイン遮断の期間設定を確認する。** **②期間の延長が業務に与える影響（誤遮断の件数）を測ってから決める。** **③期間での遮断に加えて、 自社が使うベンダー名を含む類似ドメインの登録監視を検討する。**
  • **偽サイトの「1回目を必ず拒否する」挙動を、利用者への周知に入れる**
    **popup.js は1回目の送信を必ず拒否し、 赤字で「入力内容が誤っています」と表示して2回入力させる**（出典1）。 **Huntress の評価では、これにより攻撃者は 検証用に2組目の認証情報を得る**（出典1）。 **利用者側から見れば「自分が打ち間違えた」としか見えない**（本記録の評価）。
    取るべき行動 **①利用者向けの注意喚起に、 「インストーラのダウンロードで認証情報を求められること自体がおかしい」 「入力を1回拒否されてもう一度打たせる画面は疑う」という 2点を具体的に書く。** **②VPN クライアントの正しい入手手順（配布元・画面の流れ）を スクリーンショット付きで示す。** **③「入力してしまった」と申告しやすい窓口を用意する—— 本事案では申告の有無が被害の確定に関わっている**（出典1）〈未確定2〉。
  • **正規の署名済みファイルの取得を、文脈とともに見る**
    **本事案では、正規CDN からの正規インストーラのダウンロードが 攻撃連鎖の一部になっている**（出典1）。 **ファイル単体では悪性の判定が付かない**（本記録の評価）。 **Huntress は、調査対象の期間のブラウザ履歴に cdn.watchguard.com からのダウンロード記録が無かったことを 「2回の送信を完了していなかった」証拠として使っている**（出典1）。
    取るべき行動 **①ブラウザの履歴・プロキシのログを、 インシデント調査で参照できる形で保持する （本事案では「無いこと」が判断材料になっている）。** **②正規ファイルのダウンロードを、 その直前に到達したドメインと紐づけて見られるようにする。** **③端点の検知だけでなく、 「どこを経由して来たか」を調査で追える状態を確認する。**
