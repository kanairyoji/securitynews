INC-2026-0515rustc の生存期間検査に11年越しの穴

Rust コンパイラ（rustc）に、構造体の生存期間（ライフタイム）制約を 共変なフィールド代入で回り込める健全性（soundness）の穴があることが 2026年10月13日に GitHub で報告された——unsafe を1文字も書いていない 安全な Rust コードが生存期間検査を通過してコンパイルに成功し、 Drop 実装で参照を外へ退避させることで、有効範囲を抜けた スタック上のメモリを実行時に読み出せる。報告者は nightly と 安定版 1.85.0 以降で再現すると述べ、別の報告者は 2015年10月公開の 1.4.0 でも再現すると示した。Rust チームは I-unsound / P-high を付与したが、 本記録の確認時点で修正提案 PR #164277 は未マージであり、 修正版の番号も公開時期も公表されていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月13日（GitHub Issue 最終更新: 2026年10月14日

unsafe を書かなければメモリ安全、という前提そのものに穴がありました。

2026年10月13日、Rust コンパイラ（rustc）の GitHub リポジトリに、構造体の生存期間制約を共変なフィールド代入で回り込める問題が報告されました（Issue #164250）（出典1）。報告者は jsnell 氏で、Rust チームの lcnr 氏が「struct's lifetime requirements can be bypassed via covariant field assignment」（原文英語: 構造体の生存期間要件が共変なフィールド代入で回り込める）に改題しています（出典1）。

本記録が重く見るのは、これが unsafe ブロックを使わない「安全な Rust」の側で起きている点です（出典1。評価は本記録）。Rust の売りは、所有権と借用検査によってコンパイル時にメモリ安全性を保証することにあります。 設計上、生存期間の制約を満たさないコードはコンパイル段階で拒否されるはずで、unsafe を使わないコードは原則としてこの種の問題を生まないことになっています（出典3。整理は本記録）。

ところが報告された再現コードは、コンパイルを通ったうえで、実行するとスタック上の文字列をその有効範囲が終わった後に表示しました（出典1）。AddressSanitizer（メモリ検査ツール）を当てると「stack-use-after-scope」（有効範囲を抜けたスタックメモリの使用）で異常終了します（出典1）。つまりコンパイラが、本来許してはならない操作を止められていません。

成立の鍵は Drop 実装です（出典1）。別の報告者 theemathas 氏の再現コードは、Drop 実装の中で&'static String 型のフィールドへ 'static ではない &String を代入し、その参照をスレッドへ脱出させています（出典1）。lcnr 氏も 'static を使わない変種を示しており、いずれも Drop 実装に依存します（出典1）。

期間の長さも際立ちます。 報告者は「現在の nightly と、少なくとも 1.85.0 まで下った安定版で問題が起きる」（原文英語: "Issue on current nightly, and stables at least down to 1.85.0."）と述べました（出典1）。theemathas 氏は自分の変種が「1.18.0（2017年）以来ずっとコンパイルできている」（原文英語）と述べ、maxdexh 氏は別の変種が「1.4 以来、セグメンテーション違反を起こす／解放済みメモリを表示する」（原文英語）と報告しています（出典1）。Rust 1.4.0 は2015年10月の公開であり、約11年前にあたります（出典3）。lcnr 氏自身も「過去11年のあいだ見つからなかったこの種のバグが、実際にそう簡単に踏めるものであるはずがない」（原文英語: "A bug like this which has not been found during the last 11 years cannot actually be that easy to hit."）と書いています（出典1）。

一方で、慌てる種類の問題ではありません（出典1。評価は本記録）。lcnr 氏は「見た目は簡単に引ける（trigger できる）ように見えるが、これを悪用するには意図的に悪意のある Drop 実装が必要である」（原文英語: "While it looks easy to trigger, to exploit this you need an intentionally malicious Drop implementation."）と述べています（出典1）。また「この健全性の穴が偶然メモリ安全性の問題を引き起こしてきた可能性は非常に低い」（原文英語）とも書いています（出典1）。付与された優先度は I-unsound / P-high で、最上位の P-critical ではありません（出典1）。

ただし本記録は、これを「安心材料」とだけ読むべきではないと考えます（本記録の評価）。「意図的に悪意のある Drop 実装が要る」という条件は、言い換えれば「自分が書いていないコードを取り込む経路」では成立しうるということです（本記録の評価）。依存クレートの中身を読まずに使う運用、あるいは利用者が投稿したコードをコンパイル・実行する基盤では、条件の意味が変わります。

修正はまだ着地していません（出典2）。2026年10月13日に PR #164277「require MIR local types to be well-formed」（原文英語: MIR のローカル変数の型に整合性を要求する）が提出され、MIR 借用検査の段階で一時変数の型に整合性検査を課す変更が示されています（出典2）。しかし本記録の確認時点でレビュー待ち（S-waiting-on-review）であり、承認は付いておらず、レビュア側からは検査範囲についての質問が未回答のまま残っています（出典2）。修正版の番号と公開時期は公表されていません。

unsafe を書いていないコードが、有効範囲を抜けたスタックメモリを読む原因・手口

Rust は、所有権と借用検査によって、プログラムがデータを参照していられる期間をコンパイル時に制限します（出典3）。データが無効になった後に読まれることを防ぐ仕組みであり、生存期間の制約を満たさないコードはコンパイル段階で拒否されるのが設計上の建前です（出典3）。

報告された不備は、この拒否が働かない経路です（出典1）。構造体に生存期間の制約が付いていても、共変（covariant）なフィールドへの代入を経由すると、制約を満たさない短命な参照を格納できます（出典1）。原報告の例では、型引数に 'static（プログラムの実行期間ずっと有効）を要求しているにもかかわらず、局所的なブロックの中でしか有効でない文字列への参照をOption のフィールドへ入れることをコンパイラが許しました（出典1・3）。

ここで Drop 実装が効いてきます（出典1）。構造体の実体が破棄されるときに走る Drop の中で、その参照を別の場所へ退避させられます（出典1・3）。theemathas 氏の変種は、Drop 実装の中で&'static String 型のフィールドへ非 'static の &String を代入し、その参照をスレッドへ脱出させています（出典1）。結果として、元のデータが無効になった後も参照が生き残ります。

報告者の試験プログラムはコンパイルを通っただけでなく、実行すると他のデータで上書きされたメモリの内容を読み出しました（出典3）。AddressSanitizer を当てると「stack-use-after-scope」（有効範囲を抜けたスタックメモリの使用）で止まります（出典1）。つまり実際に、本来許してはならない操作がコンパイラを通っています。

修正提案が触っているのは、MIR（コンパイラの中間表現）の借用検査の型チェックです（出典2）。種別が LocalKind::Temp（一時変数）のローカル変数について、その型に整合性（WellFormed）の義務を課す変更であり、言い換えれば「一時変数の型が制約を満たしているかをこれまで確認していなかった」ということになります（出典2。整理は本記録）。

11年前の安定版でも再現する——「どの版なら安全か」を言える状態ではない被害規模・影響範囲

影響範囲の広さは、報告されている再現版の幅から読み取れます（出典1）。

報告者 jsnell 氏は「現在の nightly と、少なくとも 1.85.0 まで下った安定版で問題が起きる」（原文英語）と述べました（出典1）。theemathas 氏は自分の変種が「1.18.0（2017年）以来ずっとコンパイルできている」（原文英語）と述べ、maxdexh 氏は別の変種が「1.4 以来、セグメンテーション違反を起こす／解放済みメモリを表示する」（原文英語）と報告しています（出典1）。Rust 1.4.0 の公開は2015年10月です（出典3）。

本記録が重く見るのは、変種ごとに成立する最古の版が1.4 / 1.18.0 / 1.85.0 とばらついている点です（出典1。評価は本記録）。これは「この版から入った」と特定できていないことを意味します。 したがって利用者の側から見ると、「自分の使っている Rust の版は該当するか」を公表資料から判定する手立てが現時点ではありません（本記録の評価）。

一方で、影響の表れ方は限定的です（出典1）。lcnr 氏は「これを悪用するには意図的に悪意のある Drop 実装が必要である」（原文英語）と述べており、偶然のコードがこの穴を踏む可能性は低いという見立てです（出典1）。ただし「どれだけの既存コードが実際に踏んでいるか」を調べた結果は公表されていません（出典1・2・3）〈未確定2〉。

「意図的に悪意のある Drop 実装が要る」という条件は、依存関係では意味が変わる評価・解釈

Rust チームが P-critical ではなく P-high とした理由は、公開の議論から読み取れます（出典1）。

lcnr 氏は「このバグは P-high であり、実際に踏んだ人がいたかどうかに関わらず P-critical にはならなかっただろう」（原文英語）、「過去11年のあいだ見つからなかったこの種のバグが、実際にそう簡単に踏めるものであるはずがない」（原文英語）、「この健全性の穴が偶然メモリ安全性の問題を引き起こしてきた可能性は非常に低い」（原文英語）と述べています（出典1）。そして「見た目は簡単に引けるように見えるが、これを悪用するには意図的に悪意のある Drop 実装が必要である」（原文英語）としています（出典1）。実環境での悪用への言及は公開の議論に見当たりません（出典1・3）〈未確定4〉。

ここから先は本記録の評価です。 「意図的に悪意のある Drop 実装が要る」という条件は、自分が書いたコードだけを動かす前提では強い制約です。 しかし、その条件が満たされる経路は実際には存在します（本記録の評価）。

第一に、依存クレート（ライブラリ）です。 Rust の開発では、crates.io から多数のクレートを取り込むのが通常の作りです（本記録の評価）。取り込んだクレートの Drop 実装を読んで確認する運用は、一般には行われていません。 「unsafe が無いから安全」という審査基準を使っていた場合、本件はその基準をすり抜けます（本記録の評価）。

第二に、外部から受け取ったコードをコンパイル・実行する基盤です。 プレイグラウンド、課題の自動採点、CI 上での利用者提供コードのビルドなどが該当します（本記録の評価）。これらは「悪意のあるコードが前提」の環境であり、unsafe の禁止をサンドボックスの一部として使っている場合、その前提が本件で崩れます（本記録の評価）。

第三に、本記録は優先度の判断そのものには異論を置きません（本記録の評価）。偶然のメモリ破壊としては確かに踏みにくく、11年見つからなかったことがその裏付けです（出典1）。論点は優先度ではなく、「unsafe の有無」を安全性の判定基準として使っている運用の側にあります（本記録の評価）。
