INC-2026-0519Claude Code に SneakPeek

Anthropic の Claude Code Desktop アプリに、HTML のプレビュー枠から 開発者端末のローカルファイルを読み出せる脆弱性「SneakPeek」が見つかった。 256KB を境に描画方式が変わり、超えたファイルは file:// として読み込まれて コンテンツセキュリティポリシーの保護を外れる。公開リポジトリに仕込んだ HTML を開発者が Claude Code に点検させるだけで、追加の操作なしに スクリプトが実行され、AWS の認証情報・GitHub のシークレット・SSH 秘密鍵が 外部へ送られうる。Anthropic 評点の CVSS v4.0 は 8.7（High）。 2026年7月4日の報告から、初期パッチの回避を経て8月17日に修正が完了し、 10月14日に Noma Security が公表した

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月14日（Noma Security の公表および CSO Online の報道） 最終更新: 2026年10月14日

Anthropic の Claude Code Desktop アプリに、HTML のプレビュー枠を経由して開発者端末のローカルファイルを読み出せる脆弱性が見つかりました（出典1・2）。発見した Noma Security（Noma Labs）はこれを「SneakPeek」と名付けています（出典1）。

成立の筋は次のとおりです（出典2）。攻撃者が公開リポジトリに悪性の HTML ファイルを置いておき、開発者がそれを Claude Code に点検させる。 アプリがファイルを描画した時点で、追加の操作なしに埋め込まれた JavaScript が実行され、ローカルファイルを読んで外部のサーバへ送り出せます（出典2）。CSO Online は、送られうるものとして AWS の認証情報・GitHub のシークレット・SSH 秘密鍵を挙げています（出典2）。

評点は CVSS v4.0 で 8.7（High）、Anthropic が割り当てたものです（出典2）。CVE 番号は公表時点で未採番で、Anthropic は GitHub Security Advisory の準備と CVE の申請を行っているとされています（出典2）。

本記録が注目するのは、スクリプトが動いた場所です（本記録の評価）。実行されたのはプレビュー枠の描画プロセスの中であり、AI エージェントの行為としてではありません（出典2）。つまり、モデルやエージェントの振る舞いに対して用意した統制（どのコマンドを許すか、どのファイルに触れさせるか）は、この経路には及びません。 Noma の研究者の言葉では「保護は実在していた。ただ、すべての経路を覆っていなかった」（出典2。原文英語。本記録の訳）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は、Noma Security が公表した成立の筋道である**（出典1・2）。 **実環境での悪用の観測ではない**〈未確定2〉。 **攻撃者が公開リポジトリに悪性の HTML ファイルを置き、 開発者がそれを Claude Code Desktop に点検させると、 プレビュー枠がファイルを描画した時点で埋め込まれた JavaScript が 追加の操作なしに実行される**（出典2）。 **256KB を超えるファイルは file:// として読み込まれるため CSP の保護を外れ、 ローカルファイルシステムへ到達できるオリジンが与えられる**（出典1・2）。 **スクリプトはローカルファイルを読み、 AWS の認証情報・GitHub のシークレット・SSH 秘密鍵などを 遠隔のサーバへ送り出せる**（出典2）。

  1. 1. 初期侵入確認済
    **攻撃者が公開リポジトリに悪性の HTML ファイルを仕込み、 開発者がそれを Claude Code に点検させるのを待つ**（出典2）。 **ファイルは256KB を超えるサイズである必要がある** （出典1・2。この条件の整理は本記録）。
    根拠: CSO Online の記述「攻撃者は、公開リポジトリに悪性のファイルを置き、 開発者が Claude Code にそれを点検させるのを待つことで この不具合を悪用できる」（出典2。本記録の訳）。
  2. 2. 実行確認済
    **プレビュー枠がファイルを描画した時点で、 埋め込まれた JavaScript が追加の利用者操作なしに実行される**（出典2）。 **256KB を超えるファイルはディスクに書き出され file:// URL として 読み込まれるため、256KB 未満のファイルに適用されていた 厳格な CSP の保護を外れる**（出典2）。 **スクリプトが動くのは、AI エージェントの行為としてではなく プレビュー枠の描画プロセスの中である**（出典2）。
    根拠: CSO Online の記述「256KB 未満のファイルは、スクリプト実行を遮断する 厳格な CSP を伴う base64 符号化された data: URL に変換された。 そのしきい値を超えるファイルは代わりにディスクへ書き出され、 file:// URL として直接読み込まれ、 小さいファイルに適用される CSP の保護を回避した」 （出典2。本記録の訳）。
  3. 3. 内部探索確認済
    **file:// として読み込まれたことにより、 描画側はローカルファイルシステムへ到達できるオリジンを 与えられる**（出典1・2）。 **隔離された不透明なオリジンに閉じ込められていない**（出典2）。 **さらに、file:// へのアクセスを遮断するはずの要求フィルタが、 静的ファイルの描画時には動作していなかった**（出典2）。
    根拠: CSO Online の記述「より大きなファイルを file:// 経由で読み込むことは、 隔離された不透明なオリジンに閉じ込めるのではなく、 Chromium においてプレビューの描画側にローカルファイルシステムへの アクセスを与えた」および要求フィルタが 「静的ファイルの描画時には有効でなかった」（出典2。本記録の訳）。
  4. 4. 持ち出し確認済
    **読み出した機微なデータを遠隔のサーバへ送り出せる**（出典2）。 **挙げられているのは AWS の認証情報・GitHub のシークレット・ SSH 秘密鍵である**（出典2）。 **Black Duck の Ronald Lewis 氏は、 Kubernetes の構成と OAuth のセッショントークンも 開発機が持つ価値の高い秘密として挙げている**（出典2）。
    根拠: CSO Online の記述「アプリケーションがファイルを描画すると、 スクリプトはローカルファイルを読み、 AWS の認証情報・GitHub のシークレット・SSH 秘密鍵を含む 機微なデータを遠隔のサーバへ持ち出せた」（出典2。本記録の訳）。
  5. 5. 影響（暗号化・破壊・改ざん）推定
    **開発者端末から持ち出された認証情報が、 企業のクラウド基盤への到達に使われうる**（出典2）。 **Ronald Lewis 氏は「開発者のローカル作業環境の侵害は、 実質的に企業のクラウド基盤への直通路である」と警告している** （出典2。原文英語。本記録の訳）。 **Crystal Morin 氏も「エンドポイントは AI エージェントの出発点だが、 その影響範囲はクラウドまで広がる」としている**（出典2。本記録の訳）。 **実際にこの段階まで至った事例は公表されていない**〈未確定2〉。
    根拠: CSO Online が伝える外部論者の見解（出典2）。 **これは想定される影響であり、観測された被害ではない** （本記録の留保）。

被害組織の対応

この事案で下された判断
  • トレードオフ: **公表を遅らせれば、利用者が更新を適用する猶予ができる** （本記録の整理）。 **一方、公表が遅れるほど、同種の設計を持つ他の製品の開発者は 自製品を点検する機会を失う**（本記録の整理）。 **また、CVE 番号が無い状態での公表は、 組織の脆弱性管理の仕組みに乗せられない**（本記録の評価）。
  • トレードオフ: **症状の経路を塞ぐ修正は速く出せる（本件では5日）** （出典1。評価は本記録）。 **一方、他の文脈から同じ到達ができる場合、 塞いだ経路を列挙するやり方では問題が残る。** **構造を直す修正は時間がかかる（本件では報告から44日）が、 回避の余地を減らす**（本記録の整理）。

256KB を超えたHTMLだけが保護の外に出る設計だった——しきい値が信頼の境界になっていた原因・手口

Noma Security は、SneakPeek を3つの構造上の欠落が連なったものとして説明しています（出典1・2）。対象は、Claude Code Desktop のプレビュー機構です ——Claude が生成または変更した HTML を表示するために、Electron ベースの Chromium 描画パネルを使う部分です（出典2）。

第一の欠落は、ファイルサイズによる分岐です（出典2）。

  • 256KB 未満の HTML は、base64 で符号化された data: URL に変換され、スクリプトの実行を遮断する厳格な CSP の下で描画された
  • 256KB を超える HTML は、ディスクに書き出され、file:// URL として直接読み込まれ、CSP の保護を外れた

第二の欠落は、描画される内容に与えられたオリジンです（出典2）。file:// として読み込むことにより、隔離された不透明なオリジンに閉じ込めるのではなく、Chromium 上でローカルファイルシステムへ到達できるオリジンが与えられていました。

第三の欠落は、動いていなかったフィルタです（出典2）。file:// へのアクセスを遮断する仕組みは用意されていたものの、静的ファイルの描画時——開発者がローカルのコードのテストレポートを確認する場合などを含む——には動作していませんでした。

本記録の整理として、この3つは独立した不備ではなく、1つの考え方の帰結です。 「大きいファイルは data: URL に収まらないから、ディスク経由にする」という実装上の都合が、そのまま保護の有無の分岐になっています（本記録の評価）。Black Duck の Ronald Lewis 氏の言葉はこの点を突いています（出典2）。

「サイズのしきい値やクライアント側のフィルタをセキュリティ境界に使うことは、本質的に脆い」
（出典2。原文英語。本記録の訳）

仕込んで待つだけでよく、開発者が「点検して」と頼んだ時点で成立する被害規模・影響範囲

CSO Online は、成立の筋を次のように伝えています（出典2）。

  • 攻撃者が公開リポジトリに悪性のファイルを仕込む
  • 開発者が Claude Code にそのファイルを点検させるのを待つ
  • アプリがファイルを描画すると、スクリプトがローカルファイルを読み、機微なデータを遠隔のサーバへ送り出せる

「追加の利用者の操作なしに実行されうる」と明記されています（出典2）。

送られうるものとして挙げられているのは次のとおりです（出典2）。

  • AWS の認証情報
  • GitHub のシークレット
  • SSH 秘密鍵

Black Duck の Ronald Lewis 氏は、開発機が持つ資産をさらに広く挙げています（出典2）。

「開発機は価値の高い運用上の秘密を持っている——SSH 秘密鍵、AWS の認証情報、Kubernetes の構成、OAuth のセッショントークンだ」
（出典2。原文英語。本記録の訳）

同氏は、開発者のローカル作業環境の侵害は実質的に企業のクラウド基盤への直通路だと警告しています（出典2）。

本記録の評価として、ここで効いているのは「開発者が自分の意思でファイルを開かせた」という点です。 怪しいファイルを警戒する利用者教育は、「レビューしてほしいファイル」には働きません。 点検を頼むという行為自体が、攻撃の起動条件になっています。

スクリプトが動いたのは描画プロセスの中で、AIエージェントの行為としてではなかった評価・解釈

CSO Online は、本件の最も重要な性質を次のように整理しています（出典2）。

「悪性のスクリプトは、AI エージェント自身が行った動作としてではなく、プレビュー枠の描画プロセスの中で動いた。これは、モデル向けに意図されたセキュリティ統制がすべての AI ワークフローを保護しているという前提を打ち崩す」
（出典2。原文英語。本記録の訳）

Noma の Eli Ainhorn 氏の表現はさらに簡潔です（出典2）。

「保護は実在していた。ただ、すべての経路を覆っていなかった」
（出典2。原文英語。本記録の訳）

本記録の評価として、これは AI コーディングツールの統制を考えるうえでの枠組みの問題です。 「エージェントにどのコマンドを許すか」「どのファイルに触れさせるか」「どの操作に確認を求めるか」——こうした統制はすべてエージェントの行為を対象にしています。 本件のスクリプトは、エージェントの行為ではなくアプリの描画機能の中で動きました。 したがって、エージェント向けの許可設定をどれだけ厳しくしてもこの経路は閉じません。

AIツールの統制を「エージェントに何を許すか」だけで組むと、この型の経路は残る対策・注意喚起

本記録の評価として、本件は特定の製品の不具合にとどまりません。

AI コーディングツールは、次の3つの層を同時に持っています（本記録の整理）。

  • ①モデル／エージェントの層——何を指示し、何を許すか
  • ②アプリケーションの層——描画・プレビュー・ファイル操作などの機能
  • ③実行環境の層——開発者の端末と、そこにある認証情報

統制の議論は①に集まりがちです（本記録の評価）。どのコマンドを許すか、どのディレクトリに触れさせるか、どの操作に確認を求めるか。

本件で破れたのは②です（出典2）。そして被害が及ぶのは③です（出典2）。①の統制をどれだけ厳しくしても、②の経路は閉じません。

この構造から導かれる備えは、ツール固有ではありません（本記録の提案）。

  • ③の層を薄くする——開発機に長命の認証情報を置かない
  • ②の層を監視する——ファイル読み出しと外向き通信をランタイム層で見る
  • ①の層の統制を、②の経路の保護と混同しない

Sysdig の Crystal Morin 氏が指摘するとおり、エージェント層のログではこの実行は必ずしも捕捉されません（出典2）。AI ツールの監査ログを取っていることが、端末の挙動を見ていることの代わりにはなりません（本記録の評価）。

CISO・経営層への示唆
  • **AIコーディングツールの統制を「エージェントに何を許すか」だけで組むと、この型は残る**
    **本件のスクリプトは、AI エージェントの行為としてではなく、 プレビュー枠の描画プロセスの中で動いた**（出典2）。 **CSO Online は「モデル向けに意図されたセキュリティ統制が すべての AI ワークフローを保護しているという前提を打ち崩す」と 整理している**（出典2。本記録の訳）。 **エージェントの許可設定をどれだけ厳しくしても、 アプリケーションの機能側の経路は閉じない**（本記録の評価）。
    取るべき行動 **①自組織で使っている AI コーディングツールについて、 「エージェントの統制」「アプリの機能」「端末の実行環境」の 3層に分けてリスクを整理する。** **②ツールの承認プロセスに、 「エージェント以外の機能（プレビュー・レンダリング・ 外部コンテンツの取り込み）が何をするか」の確認項目を入れる。** **③AI ツールの監査ログを取っていることを、 端末の挙動監視の代替として扱わないことを方針に明記する。**
  • **開発者端末に長命の認証情報を置かないことが、この型の被害の上限を決める**
    **送られうるものとして挙げられたのは AWS の認証情報・ GitHub のシークレット・SSH 秘密鍵である**（出典2）。 **Noma の Eli Ainhorn 氏は 「開発機に長命の認証情報を置くのをやめ、 可能な場所では範囲を絞った短命のトークンを使う。 それだけでも、このエクスプロイトが取れるものは 限られていただろう」と述べている**（出典2。原文英語。本記録の訳）。 **脆弱性が何であれ、端末上に無いものは取られない** （本記録の評価）。
    取るべき行動 **①開発者端末上の認証情報を棚卸しする （~/.aws/credentials・~/.ssh/ 配下・各種CLIの設定・ 環境変数ファイル・IDE に保存された資格情報）。** **②長命のアクセスキーを、短命トークンを発行する仕組み （SSO・一時認証・ハードウェアキーに紐づく認証）へ移す 計画と期限を決める。** **③移行できないものを一覧にし、 その範囲（権限・対象リソース）を最小化する。**
  • **開発者の端末を、クラウド基盤の一部として扱う**
    **Black Duck の Ronald Lewis 氏は、 開発者のローカル作業環境の侵害は実質的に企業のクラウド基盤への 直通路だと警告している**（出典2。本記録の訳）。 **Sysdig の Crystal Morin 氏も 「エンドポイントは AI エージェントの出発点だが、 その影響範囲はクラウドまで広がる」としている**（出典2。本記録の訳）。 **端末を「社内の1台のPC」として扱う分類では、 この影響範囲が見えない**（本記録の評価）。
    取るべき行動 **①開発者端末の重要度区分を、 そこから到達できるクラウド環境の重要度に合わせて見直す。** **②開発者端末の監視（EDR・ファイルアクセス・外向き通信）の 水準を、サーバと同等に扱うかどうかを判断する。** **③端末からクラウドへの認証経路を一覧化し、 端末が奪われた場合の影響範囲を環境ごとに書き出す。**
  • **CVE 番号の無い脆弱性を管理する手順を用意する**
    **本件の CVE 番号は公表時点で未採番である**（出典2）。 **修正完了（2026年8月17日）から公表（10月14日）まで 58日経っている**（出典1。算出は本記録）。 **影響を受けるバージョンの範囲も修正版の番号も 公表されていない**〈未確定1・3〉。 **番号と版が無い脆弱性は、脆弱性管理の仕組みに乗らない** （本記録の評価）。
    取るべき行動 **①AI 開発ツールを資産台帳に登録し、 バージョンを定期的に収集する仕組みを作る （自動更新であっても、現在の版を把握する）。** **②CVE 番号が無い脆弱性情報を受け付ける経路を決める （ベンダーのアドバイザリ・研究者の公表・報道）。** **③識別子が無い案件を追跡するための社内の採番規則を定める。**
セキュリティ技術者への示唆
  • **「レビューしてほしいファイル」は、不審ファイルの警戒が働かない経路である**
    **本件の成立条件は、開発者が自分の意思で Claude Code にファイルの点検を依頼することである**（出典2）。 **描画された時点で、追加の操作なしにスクリプトが実行される**（出典2）。 **「怪しいファイルを開かない」という教育は、 点検を依頼する行為には適用されない**（本記録の評価）。
    取るべき行動 **①外部由来のコード・レポート・HTML を AI ツールに 点検させる作業を、隔離した環境（使い捨てのコンテナ・ 認証情報を持たない仮想マシン）で行う手順を用意する。** **②隔離環境に認証情報を持ち込まないことを、 手順の最初の確認項目にする。** **③本番の認証情報を持つ端末で外部由来のファイルを扱う場合の 例外手続きを決める。**
  • **ファイル読み出しと外向き通信をランタイム層で見る**
    **Sysdig の Crystal Morin 氏は、 エージェント層のログではこの実行が必ずしも捕捉されず、 ファイルの読み出しと外向きのネットワーク接続は ランタイム層で見えると指摘している**（出典2。本記録の訳）。 **AI ツール自身が外部APIと通信するため、 プロセス単位の異常判定は効きにくい**（本記録の評価）。 **区別できるのは「何を読んだ直後に、どこへ送ったか」である。**
    取るべき行動 **①開発者端末の EDR で、認証情報ファイル （~/.aws/credentials・~/.ssh/id_*・kubeconfig・ 各種CLIのトークンファイル）への読み出しを記録する。** **②読み出しの直後に未知の宛先へ外向き通信が発生した場合に 警報を上げる検知を作り、1か月の誤警報数を測る。** **③AI コーディングツールのプロセスからの通信先を一覧化し、 正規の宛先を把握する。**
  • **サイズや拡張子による分岐を、保護の有無の分岐にしない**
    **本件では、256KB を境に描画方式が変わり、 超えたファイルは CSP の保護を外れた**（出典1・2）。 **Ronald Lewis 氏は 「サイズのしきい値やクライアント側のフィルタを セキュリティ境界に使うことは本質的に脆い」と述べている** （出典2。原文英語。本記録の訳）。 **自社で作るアプリにも同じ型の分岐は入りうる**（本記録の評価）。
    取るべき行動 **①自社のアプリで、入力のサイズ・形式・拡張子によって 処理経路が分かれる箇所を洗い出す。** **②各経路について、適用される保護（CSP・サンドボックス・ オリジンの隔離）が同一かを確認する。** **③異なる場合は、弱い側に合わせるのではなく 強い側に揃える（または弱い経路を廃止する）。**
  • **「APIを塞ぐ修正」は、同じ到達ができる別の文脈を列挙し終えないと完了しない**
    **初期パッチは fetch() と XMLHttpRequest による file:// への アクセスを遮断した**（出典1）。 **Noma は、ファイル読み出しの処理を blob: URL から生成した Web Worker へ移すことで、この遮断を回避した**（出典1・2）。 **報告から初期パッチまで5日、 構造の修正完了まで44日かかっている**（出典1。算出は本記録）。
    取るべき行動 **①自社の修正で「特定のAPIを遮断する」方式を取る場合、 同じ機能に到達できる文脈（Worker・iframe・ ServiceWorker・WebAssembly など）を列挙して記録する。** **②列挙が困難な場合は、オリジンやサンドボックスの層で 制限する方式へ切り替える。** **③修正後の検証を、報告者自身に再テストしてもらう手順を 脆弱性対応のプロセスに入れる（本件ではこれが回避の発見に つながっている）。**
