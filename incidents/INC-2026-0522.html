INC-2026-0522Ghostscript に未認証RCE

PDF・PostScript の解釈エンジン Ghostscript に、細工した PDF で ヒープバッファオーバーフローを起こし未認証の遠隔コード実行に至る脆弱性 CVE-2026-39919 が見つかった。JPEG 2000 画像の成分ごとの間引き率を 食い違わせると、詰めて書く前提で確保した行バッファに1列あたり1バイトを 書き込んでしまい、ヒープの管理情報を壊す。発見したのは Wordfence の AI 探索基盤 Argus で、WordPress 7.1 の点検中に見つけた。 WordPress は PDF のサムネイル生成で Imagick → ImageMagick → Ghostscript と 辿るため、PDF をアップロードできるだけで入口になる。 影響は 9.21 から 10.07.1。修正版 10.08.0 は2026年9月8日に出たが、 更新するのは WordPress ではなく OS のパッケージである

PDF・PostScript の解釈エンジン Ghostscript に、細工した PDF でヒープバッファオーバーフローを起こし、未認証の遠隔コード実行に至る脆弱性が見つかりました（出典1・2）。CVE 番号は CVE-2026-39919、CVSS v3.1 で 9.8、v4.0 で 9.3（いずれも Critical）です（出典1・2・3）。

発見したのは Wordfence の AI 探索基盤 Argus で、WordPress 7.1 の点検中に見つけました（出典1）。CVE の謝辞に記されている発見者は Wordfence Argus の Alex Thomas 氏です（出典3）。

成立の筋は次のとおりです（出典3）。JPEG 2000 画像を含む PDF で、画像の成分ごとの間引き率を食い違わせておきます。 Ghostscript の JPEG 2000 出力アダプタ（base/sjpx_openjpeg.c のprocess_one_trunk）は、サブバイト深度の出力を「詰めて書く」前提で行バッファを確保しますが、実際の書き込みは1列あたり丸ごと1バイトを書いてしまいます。 ヒープの確保器の管理情報が壊れ、コード実行に至りえます。

本記録が注目するのは、WordPress 経路の入口の低さです（本記録の評価）。WordPress は PDF のサムネイルを生成するとき、PHP の Imagick 拡張を通して ImageMagick を呼び、ImageMagick が Ghostscript を起動します（出典1・2）。したがって、PDF をアップロードできる立場にあるだけで、この経路に到達します。 Wordfence は、専用に組んだ WordPress の試験サーバで-dSAFER を有効にした状態のまま、未認証の遠隔コード実行を実証しました（出典1）。

一方、Wordfence は「これは WordPress 固有の脆弱性ではない」と強調しています（出典1。原文英語。本記録の訳）。文書管理システム・印刷サービス・請求書処理・メールゲートウェイ・変換 API——信頼できない PDF を Ghostscript に渡すものはすべて対象になります（出典1・2。本記録の訳）。

影響を受けるのは Ghostscript 9.21 から 10.07.1 です（出典1・2）。修正版 10.08.0 は2026年9月8日にリリースされました（出典1・4）。ここに運用上の落とし穴があります（本記録の評価）——更新するのは WordPress のプラグインではなく、OS のパッケージまたはコンテナイメージです（出典1・2）。Wordfence は「更新すべき WordPress プラグインは存在しない」と書いています（出典1。原文英語。本記録の訳）。

Wordfence は、実環境での悪用を確認していないとしています（出典2）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は、Wordfence が公表した成立の筋道と実証結果である** （出典1・2）。 **実環境での悪用の観測ではない**〈未確定4〉。 **攻撃者は、成分ごとに食い違う間引き率を宣言した JPEG 2000 画像を含む PDF を細工し、 対象のアプリケーションへアップロードする**（出典2・3）。 **アプリケーションがプレビュー・サムネイルの生成のために その PDF を処理すると、Imagick → ImageMagick → Ghostscript と 辿って脆弱なデコード処理に到達する**（出典1・2）。 **詰めて書く前提で確保した行バッファに1列あたり1バイトを 書き込むため、ヒープの確保器の管理情報が壊れ、 コード実行に至りえる**（出典3）。 **Wordfence は専用に組んだ WordPress 試験サーバで、 `-dSAFER` 有効のまま未認証の遠隔コード実行を実証した**（出典1）。

  1. 1. 初期侵入確認済
    **攻撃者が、成分ごとに食い違う間引き率を宣言した JPEG 2000 画像を含む PDF を細工し、 対象のアプリケーションへアップロードする**（出典2・3）。 **WordPress 環境では、無認証または低権限のアカウント経由で アップロードできることが前提の1つ目になる**（出典2）。
    根拠: GitHub Security Advisory の記述「PDF には、成分ごとに 食い違う間引き率を宣言した JPEG 2000 画像が含まれる」 （出典3。原文英語。本記録の訳）。 Wordfence が挙げた前提「攻撃者が PDF をアップロードできる （無認証または低権限のアカウント経由）」（出典2。本記録の訳）。
  2. 2. 実行確認済
    **アプリケーションがプレビューまたはサムネイルの生成のために その PDF を処理する**（出典2）。 **WordPress では、PHP の Imagick 拡張を通して ImageMagick を呼び、ImageMagick が Ghostscript を起動する** （出典1・2）。 **処理の連鎖が Ghostscript に到達し、 ポリシー設定が PDF の描画を許していることが 前提の2つ目・3つ目になる**（出典2）。
    根拠: BleepingComputer の記述「PDF のサムネイルを生成するとき、 WordPress は PHP の Imagick 拡張を使って ImageMagick を呼び、 ImageMagick が Ghostscript を起動しうる」 （出典2。原文英語。本記録の訳）。
  3. 3. 影響（暗号化・破壊・改ざん）確認済
    **非 samescale のサブバイト深度の出力経路が、 詰めて書く想定で行バッファを確保しながら 1出力列あたり丸ごと1バイトを書き込む**（出典3）。 **ヒープの確保器のチャンク管理情報が壊れる**（出典3）。 **Wordfence の2つの PoC は、 256バイトのバッファへ1,024バイトを書き込ませた**（出典2）。
    根拠: GitHub Security Advisory の記述「非 samescale の サブバイト深度の出力経路は、詰めて出力する想定で 行バッファを確保するが、1出力列あたり丸ごと1バイトを 書き込む。このオーバーフローは確保器のチャンク管理情報を壊し、 コード実行に至りえる」（出典3。原文英語。本記録の訳）。 BleepingComputer の記述「Ghostscript に256バイトの バッファへ1,024バイトを書き込ませ、近傍のメモリを壊す」 （出典2。原文英語。本記録の訳）。
  4. 4. C2通信推定
    **コード実行に成功した場合、 Ghostscript を起動したプロセスの権限で サーバ上の操作が可能になる**（出典1・2）。 **Wordfence は「サーバの乗っ取り」に至りうるとしている** （出典1・2。本記録の訳）。 **これは成立した場合の想定であり、 実環境での観測ではない**〈未確定4〉。
    根拠: Wordfence が専用に組んだ WordPress 試験サーバで 未認証の遠隔コード実行を実証したこと（出典1）。 BleepingComputer の題名「Ghostscript の不具合により、 攻撃者は PDF のアップロード経由でサーバを乗っ取れる」 （出典2。本記録の訳）。

詰めて書く前提のバッファに1列1バイトを書き込む——間引き率を食い違わせた JPEG 2000 画像が引き金原因・手口

所在は Ghostscript の JPEG 2000 出力アダプタ、base/sjpx_openjpeg.c の process_one_trunk 関数です（出典3）。CWE は CWE-122（ヒープベースのバッファオーバーフロー）です（出典3）。

GitHub Security Advisory の記述は次のとおりです（出典3。原文英語。本記録の訳）。

「JPEG 2000 出力アダプタ（base/sjpx_openjpeg.c）におけるヒープベースのバッファオーバーフローにより、攻撃者は細工した PDF でメモリを破壊できる。PDF には、成分ごとに食い違う間引き率を宣言したJPEG 2000 画像が含まれる。非 samescale のサブバイト深度の出力経路は、詰めて（packed）出力する想定で行バッファを確保するが、1出力列あたり丸ごと1バイトを書き込む。このオーバーフローは確保器のチャンク管理情報を壊し、コード実行に至りえる。」

本記録の整理では、ここには2つの前提の食い違いがあります（本記録の評価）。

  • バッファを確保する側は「サブバイト深度なので詰めて書く」と想定している（たとえば1画素1ビットなら8画素で1バイト）
  • 書き込む側は「1列あたり1バイト」で書いている

つまり、列数ぶんだけ超過が積み上がります（本記録の整理）。Wordfence の実証では、256バイトのバッファに1,024バイトが書き込まれました（出典2）——4倍の超過です（本記録の算出）。

この食い違いが現れるのは、サブバイト深度で、かつ成分ごとの解像度が揃っていない場合に限られます（出典3。整理は本記録）。攻撃者が PDF の中で間引き率を食い違わせるのは、この条件を作るためです。

壊れるのはヒープの確保器の管理情報です（出典3）。BleepingComputer の表現では「近傍のメモリを壊し、未認証の遠隔コード実行に至る」（出典2。本記録の訳）。

なお、Ghostscript の役割を確認しておきます（出典2）。Ghostscript は PostScript と PDF の解釈エンジンで、PDF を画像として描画し、プレビュー用のサムネイルを生成し、埋め込み画像の圧縮や不要なフォントデータの除去でPDF を最適化します（出典2）。つまり、PDF を「読んで何かする」場面で広く使われています（本記録の整理）。

WordPress は PDF のサムネイル生成で Ghostscript を呼ぶ——アップロードできるだけで入口になる被害規模・影響範囲

WordPress 経路の筋は次のとおりです（出典1・2）。

WordPress は PDF のサムネイルを生成するとき、PHP の Imagick 拡張を通して ImageMagick を呼び、ImageMagick が Ghostscript を起動します（出典2）。

Wordfence は、専用に組んだ WordPress の試験サーバで、-dSAFER を有効にした状態のまま未認証の遠隔コード実行を実証しました（出典1）。-dSAFER は Ghostscript の安全側の実行モードで、ファイル操作などを制限するものです（本記録の補足）——それが有効でも成立した点が、この経路の深刻さを示しています（本記録の評価）。

WordPress 環境での成立には4つの前提が要ります（出典2。本記録の訳）。

  1. 攻撃者が PDF をアップロードできる（無認証または低権限のアカウント経由）
  2. サイトがその PDF をプレビューまたはサムネイルの生成のために処理する
  3. 処理の連鎖が Ghostscript に到達し、必要なソフトウェアとポリシー設定が PDF の描画を許している
  4. Ghostscript に未修正の脆弱なデコード処理が含まれている

Wordfence は「素の WordPress は無認証でのメディアライブラリへのアップロードを許していない」と注記しています（出典2。本記録の訳）。本記録はこの注記を重く見ます（本記録の評価）——つまり、WordPress 本体の既定設定のままなら1つめの前提が成立しません。 成立するのは、投稿フォーム・応募フォーム・問い合わせフォームなどのプラグインが PDF の添付を受け付けている場合、あるいは低権限の登録ユーザーを受け入れている場合です（本記録の整理。出典はこの列挙をしていない）。

一方、Wordfence は WordPress 固有ではないと強調しています（出典1・2。本記録の訳）。

「これは WordPress だけの脆弱性ではない。文書管理システム・印刷サービス・請求書処理・メールゲートウェイ・変換 API はいずれも、信頼できない PDF を Ghostscript へ渡しうる。」

より一般的には、攻撃者が与えた PDF を影響を受ける Ghostscript のコードで描画するアプリケーションはすべて露出しうるものであり、悪用に認証が要るかどうかはアプリケーションごとに異なります（出典2。本記録の訳）。

本記録はこの点を、読者が該当性を判定するうえでの要所と見ます（本記録の評価）——「WordPress を使っていないから該当しない」という判定は誤りです。 判定軸は「信頼できない PDF が Ghostscript に到達する経路があるか」です。

10,240回実行しても成立しなかった一方、専用に組んだ試験サーバでは成立した——悪用の難しさの読み方評価・解釈

Wordfence の実証結果には、2つの異なる側面があります（出典2）。

一方では、成立しませんでした（出典2。本記録の訳）。試験環境で Linux パッケージに対して PoC を10,240回実行しましたが、遠隔コード実行には至りませんでした。 Debian・Ubuntu・Fedora・Alpine・AlmaLinux を含む10のLinux 環境と、公式の WordPress Docker イメージのスナップショットを検査した結果、すべてに脆弱なコードは含まれていましたが、PoC が引き金を引けるかは環境に依存しました。

他方では、成立しました（出典2。本記録の訳）。専用に組んだ試験サーバでは、遠隔でコードを実行できました。 PDF のフォント・言語設定・フォント設定、および中核のシステムライブラリ1つを変更すると成立しましたが、安定はしませんでした。

Wordfence の PoC は、準備した対象のビルドでのみ動作しました（出典1。本記録の訳）。同社は、標的を定めた攻撃と、1つのビルドを共有する多数のサーバについてはなお注意を促しています（出典1。本記録の訳）。

本記録の読み方はこうです（本記録の評価）。

①無差別の大量悪用には向きません。 10,240回の失敗は、「とりあえず PDF を投げれば落ちる」型ではないことを示しています。

②標的型では成立します。 攻撃者が対象環境のビルドを把握できるなら、それに合わせた調整で成立します。 Wordfence が挙げた「1つのビルドを共有する多数のサーバ」は、共用ホスティングやコンテナイメージの配布を指すものと本記録は読みます（本記録の整理。出典は具体例を挙げていない）。

③ヒープの管理情報を壊す型であるため、「成立しなかった」が「安全」を意味しません（本記録の評価）。メモリ破壊が起きていること自体は10環境すべてで共通しており（出典2）、成立しなかったのはコード実行への橋渡しの部分です。 サービスの異常終了は起こりえます。

Wordfence は、実環境での悪用を確認していないとしています（出典2）〈未確定4〉。CISA KEV への収載も、本記録では確認できませんでした（本記録の確認）。

更新するのは WordPress ではなく OS のパッケージで、バージョン番号では該当性を判定できない対策・注意喚起

影響を受けるのは Ghostscript 9.21 から 10.07.1 です（出典1・2）——OpenJPEG デコーダが存在する版が対象です（出典1）。修正版 10.08.0 は2026年9月8日にリリースされました（出典1・4）。

ここで、本記録が最も実務に効くと考える点を示します（本記録の評価）。

Wordfence は「更新すべき WordPress プラグインは存在しない」と書いています（出典1。原文英語。本記録の訳）。Ghostscript は OS またはコンテナイメージから来るものであり、WordPress の管理画面からは更新できません（出典1）。

したがって、やることは次のようになります（出典1・2）。

  • WordPress の管理者は、ホスティング事業者を通してGhostscript が 10.08.0 以降に更新されているかを確認する必要がある（出典2。本記録の訳）
  • Docker を使っているなら、修正済みのベースイメージで再ビルドして再配備する（出典2。本記録の訳）

そして、もう1つの落とし穴があります（出典1・2）。

Linux ディストリビューションは修正をバックポートしうるため、gs --version の出力よりもパッケージの改訂番号のほうが重要になります（出典1・2。本記録の訳）。つまり、gs --version が 10.07.1 と返しても、ディストリビューションが修正をバックポートしていれば修正済みの可能性があります。 逆に、10.08.0 と返しても別の問題が残る可能性は否定できません。

本記録の整理では、判定の順序は次のようになります（本記録の整理）。

  1. 信頼できない PDF が Ghostscript に到達する経路があるかを確認する（これが無ければ該当しない）
  2. 経路があるなら、使っているディストリビューションのセキュリティ勧告で CVE-2026-39919 の修正状況を確認する
  3. パッケージの改訂番号で判定する（gs --version の出力では判定できない）

修正版へ更新できない場合の暫定の緩和策として、Wordfence は次を挙げています（出典1・2。本記録の訳）。

  • 信頼できない利用者からの PDF の受け入れをやめる／サーバへの PDF のアップロードを遮断する
  • ImageMagick のポリシー設定で PDF の読み込み・描画を無効にする
  • アップロードを制限する

Wordfence は「これらはリスクを下げるが、不具合そのものを直すわけではない」と注記しています（出典1。本記録の訳）。
