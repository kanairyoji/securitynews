INC-2026-0524XBOW が Chrome 完全連鎖を6日で構築

セキュリティ企業 XBOW が、公開されている OpenAI のモデル（GPT-5.6 Sol）に 指示する AI エージェントを用いて、当時未知だった Google Chrome の脆弱性3件を 連鎖させ、利用者がウェブページを開くだけで Windows 上でコードが走る 完全な攻撃連鎖を6日で構築した。 研究者4名が戦略と検証を担い、探索・検証・試作・初期の攻撃コードの草案を エージェントに任せた。計算資源の費用は約4万米ドル。 Google は3件すべてを確認して修正し、2026年の規定による初の 最高額25万米ドルの報奨金を支払った。 脆弱性の CVE 番号・部位・種別は、本記録の確認時点では公表されていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備公表されていない／不明
初報: 2026年10月13日（XBOW の公表） 最終更新: 2026年10月15日

米国のセキュリティ企業 XBOW が2026年10月13日、当時未知だった Google Chrome の脆弱性3件を連鎖させ、利用者がウェブページを読み込むだけで Windows 上でコードが走る完全な攻撃連鎖（full chain）を構築したと公表した（出典1）。

構築に使ったのは、公開されている OpenAI のモデルGPT-5.6 Sol とその前世代である（出典1）。XBOW は「我々が使ったモデルはすでに公開されている」と書いている（出典1。本記録の訳）。人とエージェントの分担は明示されている（出典1）——エージェントが Chrome のソースコードを探索し、仮説を試し、実証コードを組み、攻撃コードの初期の草案を書いた。人は戦略を決め、どこを見るかを選び、結果を検証し、方向を修正した。

要した期間は6日である（出典1・2）。報奨対象になった連鎖は、2026年8月2日（日）から8月7日（金）までのラスベガスでの作業で組み上がった（出典1）。計算資源の費用は約4万米ドルだった（出典1）。

Google は3件すべてを確認して修正し、25万米ドルの報奨金を支払った（出典1・2）。XBOW は、これが2026年の規定による最初の支払いであるとしている（出典1）。

脆弱性そのものの詳細は、本記録の確認時点では公表されていない〈未確定1〉。CVE 番号・影響する部位・脆弱性の種別・報告日・修正日・修正された Chrome の版はいずれも XBOW の公表に含まれていない（本記録の確認）。XBOW は技術的な詳細を別の記事に譲るとしているが、本記録はその記事に到達できなかった〈齟齬2〉。

本記録がこの事案を記録する理由は、脆弱性の内容ではなく、到達までの費用と時間の構造にある（本記録の整理）。完全連鎖の構築は、従来は少数の専門家が数か月をかける作業だった（本記録の評価。出典はこの比較をしていない）。本件で公表された数字は、6日・研究者4名・約4万米ドルである（出典1）。

人は戦略、エージェントは探索と試作——分担がそのまま公表されている原因・手口

XBOW は、人とエージェントの分担を明示しています（出典1）。

エージェントが担った作業（出典1。本記録の訳）

  • Chrome のソースコードの探索
  • 仮説の検証
  • 実証コード（PoC）の作成
  • 攻撃コードの初期の草案の執筆

人が担った作業（出典1。本記録の訳）

  • 戦略の決定
  • どこを見るかの選択
  • 結果の検証
  • 方向の修正

この分担の意味は2つあります（本記録の評価）。

第一に、置き換わったのは「探索の手数」です。 ブラウザのソースコードは膨大で、どこに不備がありそうかの見当をつけ、仮説を1件ずつ試す作業に時間がかかります。 ここが並列化できる作業になった、という主張です。

第二に、置き換わっていないのは「どこを見るか」です。 XBOW の記述では、戦略と探索範囲の選択は人が担っています（出典1）——つまり、本件の6日という数字は、熟練した研究者4名（うち1名は Chrome の脆弱性研究で知られる Willem Pinckaers 氏）の判断を前提にしています（本記録の評価）。

XBOW 自身は、この前提が外れる見込みを述べています（出典1。本記録の訳）——「1年のうちに、3件のいずれもエージェントが自力で見つけられるようになりうる」。 これは予測であり、実証ではありません（本記録の明示）。

組み方は「3つの独立した部品＋それぞれの予備」——失格を織り込んだ設計になっていた評価・解釈

連鎖の組み方について、XBOW は次のように書いています（出典1）。

①連鎖は3つの独立した部品として組んだ。 ②それぞれに予備を用意した。 ③理由は、提出した脆弱性が失格になったときに差し替えられるようにするためである。

③の背景は実際に起きています（出典1）——先に提出した別の連鎖は、含まれていた脆弱性の1件を Google が既に把握していたために失格になりました。

本記録はこの設計を重く見ます（本記録の評価）。

理由は、これが「脆弱性を1件見つける」話ではなく、「連鎖を成立させる在庫を持つ」話になっている点です。 部品ごとに予備を持てるということは、未知の脆弱性の発見が、一点狙いではなくある程度の歩留まりで出せる作業として扱われているということです（本記録の評価。出典はこの整理をしていない）。

ただし、XBOW が見つけた脆弱性の総数は公表されていません〈未確定2〉——在庫がどれだけ厚かったかは分かりません。 「3件×予備」という記述から、少なくとも4件以上は見つかっていたと読めますが、これは本記録の読みです（本記録の留保）。

CVE 番号が無いので、読者が自組織で判定する手段は「最新に保つ」しかない対策・注意喚起

本件について、読者が実務でできることは限られています（本記録の整理）。

これらが無いため、「自社の端末の Chrome の版は影響を受けるか」という問いに答える手段がありません（本記録の明示）。

XBOW の助言は2点です（出典1。本記録の訳）。

  • Chrome を最新に保ち、更新が出たら再起動する
  • 攻撃者より先に、自社のソフトウェアを検査する

前者について、本記録は補足します（本記録の整理）——Chrome の更新は、ダウンロードされても再起動するまで反映されません。 端末を長期間スリープで使い続ける運用では、更新済みの表示と実際に走っている版が食い違います。 組織で確認すべきは「配布した版」ではなく「実際に走っている版」です（本記録の評価）。

後者については、XBOW が同種の製品を開発中であることを明示しています（出典1）——助言には自社製品の売り込みが含まれます（本記録の明示）。

XBOW は、モデルへのアクセス制限という論点を明示的に否定しています（出典1。本記録の訳）——「我々が使ったモデルはすでに公開されているので、（制限すべきかという）問いの立て方が間違っていると考える」。

本記録は、この主張の当否を判定しません（本記録の留保）——モデルの提供側（OpenAI）の見解は公表されておらず〈未確定4〉、1件の事例から政策の是非は導けません。

本記録が読み取るのは、防御側の時間の見積りへの影響です（本記録の評価）。

従来、ブラウザの完全連鎖は「国家が支援する攻撃者か、商業的な攻撃ツール業者が、数か月をかけて作るもの」という前提で扱われてきました（本記録の整理。出典はこの比較をしていない）。この前提は、パッチ適用の猶予期間の見積りに使われています ——公開から悪用までに何日あるか、という見積りです。
