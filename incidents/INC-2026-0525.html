INC-2026-0525Hirudoが正規銀行アプリを改造版に入替

Android のバンキング型マルウェア「Hirudo」が、端末に入っている正規の バンキングアプリを一度アンインストールし、同じパッケージ名・同じ版で 「改造版」を入れ替えて導入する手口を使っていた。改造版はアプリの中で 署名の確認・アクセシビリティの検出・画面保護・鍵の証明・Play Integrity の 判定をすべて偽り、アプリ自身の防御機構をアプリの中から無効化する。 ThreatFabric が2026年10月14日に公表した。改造版が用意されていたのは インドネシアの7行・8本のアプリで、認証情報の窃取の対象として 中国・インド・メキシコ・モロッコ・タイも組み込まれていた。 被害者数は公表されていない

脅威・攻撃キャンペーン詐欺の手口初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備人を介した誘導（ビッシング・BEC）
初報: 2026年10月14日（ThreatFabric の公表） 最終更新: 2026年10月15日

オランダのモバイルセキュリティ企業 ThreatFabric が2026年10月14日、Android のバンキング型マルウェア「Hirudo」を公表した（出典1）。

手口の中心は、正規のバンキングアプリの「入れ替え」である（出典1・2・3）。Hirudo は、端末に入っている正規のバンキングアプリのアンインストールを起動し、改造版をダウンロードし、アクセシビリティ権限を使って導入する（出典1・2）。改造版は元のアプリのコードをほぼそのまま保ち、パッケージ名も版も同じで、公開されている Android のテスト鍵で署名されている（出典1）——正規の署名と異なるため、更新としては導入できない。だから先に消す（出典1。整理は本記録）。

改造版の中では、アプリの防御機構がアプリに向けて使われる（出典2。本記録の訳）。仕込まれているのは、元のアプリの Application クラスに1行を挿入して読み込ませるフック機構で、YAHFA（Java のメソッドのフック）と Dobby（ネイティブ関数のフック）を基礎にしている（出典1・2）。これが次の5つを偽る（出典1・2）——①署名の問い合わせに正規の証明書を返す②有効なアクセシビリティサービスの一覧を空で返す③画面保護（FLAG_SECURE）を外す④鍵の証明（key attestation）の証明書を、公開されて漏れているキーボックスで作り直す⑤Play Integrity の問い合わせを平文の HTTP で運用側のサーバへ中継し、返ってきた判定をアプリに受け取らせる。

入口は、正規に機能する「普通のアプリ」である（出典1・2）。買い物（Shopora）・成人向け動画（1V1 X）・短編ドラマ（ZoyaTV・KoiShort）が、約束どおりの機能を提供しながら、偽の「更新」通知で別の APK の導入とアクセシビリティ権限の付与を利用者に行わせる（出典1・2）。

できることは広い（出典1・2）——8言語に翻訳された偽の決済画面で支払用の PIN を取る（appPayPwd）、銀行ごとの画面でログインのパスワードを取る（appPwd）、偽のパターン画面とアクセシビリティ経由で端末のロック解除の秘密を読む、WebRTC で画面を実時間で配信する、前後のカメラを使う、SMS を集める（初回は90日分、以後は設定された銀行・ウォレットの送信元）。

一方、この回避には限界がある（出典1・2）。使われているキーボックスはすでに公開されて漏れたもので、うち2つの証明書は Google が侵害済みとして公表している（出典1・2）——したがって、サーバ側で失効を確認すれば偽造は見抜ける（出典2。本記録の訳）。

運用側の設備には穴がある（出典1）——APK を組み直す管理画面が認証を要さずに到達でき、保管領域と資格情報も露出していた。 ThreatFabric は、2026年8月時点の運用側のデータに「数千件」の資格情報の記録と、端末の記録・ロック画面の履歴・月収や危険度の項目を持つ金融の素性情報を確認したとしている（出典1）。

被害者数は公表されていない〈未確定1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は、ThreatFabric が公表した観測である**（出典1）。 **買い物・成人向け動画・短編ドラマのアプリが投下役となり、 偽の「更新」通知から Hirudo 本体（RAT）の導入と アクセシビリティ権限の付与を利用者に行わせる**（出典1・2）。 **Hirudo は、端末の正規のバンキングアプリのアンインストールを 起動し、改造版をダウンロードして アクセシビリティ権限で導入する**（出典1・2）。 **改造版はパッケージ名と版を保ち、公開されているテスト鍵で 署名され、`Application` クラスに挿入された1行から フック機構（YAHFA＋Dobby）を読み込む**（出典1）。 **フック機構は、署名の確認・アクセシビリティの検出・ 画面保護・鍵の証明・Play Integrity の判定を偽る**（出典1・2）。 **その上で、偽の決済画面・偽のパターン画面・画面配信・ カメラ・SMS の収集により、資格情報と資産に関わる情報を集める** （出典1・2）。

  1. 1. 初期侵入確認済
    **利用者が投下役のアプリを導入する**（出典1・2）。 **Shopora（買い物）・1V1 X（成人向け動画）・ ZoyaTV・KoiShort（短編ドラマ／カジノ経路）が確認されている** （出典1）。 **いずれも約束どおりの機能を提供する**（出典2）。 **配布は Amazon CloudFront 上で、 投下役の系統ごとに別の経路が用意されている**（出典1）。 **流入元の特定には OpenInstall と Meta Pixel の ID が 使われている**（出典1）。
    根拠: ThreatFabric が回収した投下役の標本4件（SHA-256 とパッケージ名）、 および配布経路のホスト（出典1）。
  2. 2. 実行確認済
    **投下役が偽の「更新」通知を表示し、 別の APK（Hirudo 本体・RAT）の導入と アクセシビリティ権限の付与へ誘導する**（出典1・2）。 **買い物系の投下役の1つは、導入中に IPv4 の通信を落とす 「ブラックホール VPN」を立てる**（出典1） ——**目的は公表されていない**（本記録の確認）。
    根拠: ThreatFabric が確認した投下役の動作と、 回収した Hirudo RAT の標本2件（2026年7月の版と v7.8.166） （出典1）。
  3. 3. 検知回避確認済
    **Hirudo が正規のバンキングアプリのアンインストールを起動し、 改造版をダウンロードして アクセシビリティ権限を使って導入する**（出典1・2）。 **改造版はパッケージ名と版を保ち、 公開されている Android のテスト鍵で署名されている**（出典1）。 **起動後、フック機構が ①署名の問い合わせに正規の証明書を返す ②有効なアクセシビリティサービスの一覧を空で返す ③`FLAG_SECURE` を外す ④鍵の証明の証明書を、公開されて漏れているキーボックスで 作り直す ⑤Play Integrity の問い合わせを平文の HTTP で 運用側のサーバへ中継する**（出典1・2）。
    根拠: ThreatFabric が解析した改造版の構成（`Application` クラスへの 1行の挿入・YAHFA＋Dobby・引き金のファイル）と、 Play Integrity の中継先 （`hxxp://43[.]225[.]157[.]157:8766/request_token`）（出典1）。
  4. 4. 認証情報アクセス確認済
    **改造版の中で、偽の決済画面（8言語）が支払用の PIN を `appPayPwd` として取り、 銀行ごとの画面がログインのパスワードを `appPwd` として取る**（出典1）。 **偽のパターン画面、および一部の版では アクセシビリティ経由で端末のロック解除の PIN・パスワード・パターンを読む**（出典1）。 **SMS は初回に過去90日分を走査し、 以後は設定された銀行・ウォレットの送信元を対象にする**（出典1）。 **偽の決済成功画面を見せて、窃取中であることを隠す**（出典2）。

    根拠: ThreatFabric が認証を要さずに到達できた運用側の管理画面と、 そこで確認したデータ（出典1）。

本件の手口の核は、入れ替えの工程にあります（出典1・2）。

  1. 利用者が、約束どおりに機能する買い物・動画・短編ドラマのアプリを導入する
  2. そのアプリが、偽の「更新」通知を表示する
  3. 通知から、別の APK（Hirudo 本体）の導入とアクセシビリティ権限の付与へ誘導される
  4. Hirudo が、端末に入っている正規のバンキングアプリのアンインストールを起動する
  5. 改造版をダウンロードし、アクセシビリティ権限を使って導入する

4が必要なのは、技術的な制約です（出典1。整理は本記録）——改造版は公開されている Android のテスト鍵で署名されており、正規の署名と異なります。 Android は署名が異なるアプリを「更新」としては導入しません。 だから先に消すしかありません。

改造版の中身は、元のアプリのほぼそのままです（出典1）。

  • パッケージ名は同じ
  • 版も同じ
  • 元のアプリのコードをほぼすべて保っている
  • Application クラスに1行だけ挿入されている
  • その1行が、フック機構を読み込む

フック機構は、YAHFA（Java のメソッドのフック）とDobby（ネイティブ関数のフック）という公開されている枠組みの上に作られています（出典1・2）。そして、マルウェアが書いた引き金のファイルが存在するときだけフックを有効にします（出典1）——解析のために単体で動かしても、本来の動きが出ない作りです（本記録の整理）。

ThreatFabric は、この工程を「危うい（delicate, risky）」としています（出典2。本記録の訳）——利用者が2か所で中断できるためです。 本記録はこれを、防御の手掛かりが技術ではなく利用者の画面の上にあるという意味に読みます（本記録の評価）。

偽るのは5つ——署名・アクセシビリティ・画面保護・鍵の証明・Play Integrity評価・解釈

改造版が起動したあとに行う回避は5つです（出典1・2）。

偽る対象 やり方
署名の確認 問い合わせに正規の証明書を返し、テスト鍵の署名を隠す
アクセシビリティの検出 有効なサービスの一覧を空で返し、操作している自分を隠す
画面保護 FLAG_SECURE を外し、画面の録画・遠隔の閲覧を可能にする
鍵の証明 公開されて漏れているキーボックスで証明書を作り直す
Play Integrity 問い合わせを平文の HTTP で運用側のサーバへ中継し、返ってきた判定を受け取らせる

ThreatFabric の表現はこうです（出典2。本記録の訳）——「フック機構がバンキングアプリ自身のプロセスの中で動いているため、アプリの防御がアプリに向けて使われる」。

本記録が重く見るのは、5つの共通点です（本記録の評価）。

いずれも、答えを作っているのが端末の中である点です。 署名の確認も、アクセシビリティの一覧も、鍵の証明の組み立ても、Play Integrity の問い合わせも、アプリのプロセスの中で結果が決まります。 同じプロセスの中にフックが入れば、答えは差し替えられます。

逆に言えば、答えを外で作れば崩れます（本記録の整理）。実際、本件の回避には穴があります（出典1・2）——使われているキーボックスは公開されて漏れたものであり、うち2つの証明書を Google は侵害済みとして失効の一覧に載せています。 サーバ側で失効を確認すれば偽造は見抜けます（出典2）。

つまり本件は、「アプリの中の検査を全部突破した話」ではなく、「アプリの中の検査しか見ていない相手には通る話」です（本記録の評価）。

入口は「ちゃんと動くアプリ」——買い物・成人向け動画・短編ドラマ発覚の端緒

投下役として確認されたのは4本です（出典1）。

  • Shopora（買い物・com.agbbh.kjdrttt）
  • 1V1 X（成人向け動画・com.onev.vip）
  • ZoyaTV（短編ドラマ・com.zoyatv.app）
  • KoiShort（短編ドラマ／カジノを題材にした経路・com.koishort.app）

いずれも、約束どおりの機能を提供します（出典2）——「入れてみたら動かない」という形で疑われることがありません。

配布と運用の作りも業務的です（出典1）。

  • APK は Amazon CloudFront に置かれている
  • 投下役の系統ごとに別の経路が用意されている
  • 改造版のバンキングアプリ8本には専用のホストがある
  • 流入元の特定に OpenInstall と Meta Pixel の ID を使っている
  • 買い物系の投下役の1つは、導入中にIPv4 の通信を落とす「ブラックホール VPN」を立てる（出典1）

最後の点について、ThreatFabric は目的を述べていません（本記録の確認）。本記録は、導入中の通信を遮ることで検査や告知が届かない状態を作る意図が考えられると見ますが、これは推測です（本記録の留保）。

運用側の設備には穴がありました（出典1）——APK を組み直す管理画面が認証を要さずに到達でき、保管領域と資格情報も露出していました。 ThreatFabric がこの構成と2026年8月時点のデータを確認できたのは、この穴があったからです（本記録の整理）。

「phished」と注記された記録と、月収・危険度の項目——集めた先に選別の工程がある被害規模・影響範囲

2026年8月時点の運用側のデータの中身は、次のように示されています（出典1）。

  • 「数千件」の資格情報の記録。短編ドラマ系と買い物系のcampaign group に分かれていた
  • 端末の記録
  • ロック画面の履歴
  • 月収（monthly income）と危険度（risk score）の項目を持つ金融の素性情報
  • 「phished」と注記された記録

ThreatFabric は、最後の注記について「窃取した情報を現金化する作業の流れがある」ことを示すものだとしています（出典1。本記録の訳）。

本記録が注目するのは、月収と危険度の項目です（本記録の評価）。これは、取った資格情報を一律に扱わず、「どの口座から取るか」を選別していることを示します ——ただし ThreatFabric は選別の運用そのものを記述していないため、本記録の読みです（本記録の留保）。

できることの一覧は次のとおりです（出典1・2）。

  • 8言語に翻訳された偽の決済画面で支払用の PIN を取る（appPayPwd）
  • 銀行ごとの画面でログインのパスワードを取る（appPwd）
  • 偽のパターン画面、および一部の版ではアクセシビリティ経由で端末のロック解除のPIN・パスワード・パターンを読む
  • WebRTC で画面を実時間で配信する
  • 前後のカメラを使う
  • SMS を集める（初回は過去90日分、以後は設定された銀行・ウォレットの送信元）
  • 偽の決済成功画面を見せて、窃取中であることを隠す（出典2）

SMS の90日分という設定は、感染より前の情報まで持ち出されることを意味します（本記録の整理）——認証コードの履歴・取引の通知が3か月さかのぼります。

守る側の結論は「端末の中の答えを信じない」——ただし行動分析の欠落も信号になる対策・注意喚起

ThreatFabric が銀行に向けて示した推奨は次のとおりです（出典1。本記録の訳）。

  • Play Integrity はサーバ側で検証し、セッションと保護すべき操作に結び付ける。あわせて鍵の証明の失効を確認する
  • 多層の防御を使い、行動分析を含める。行動のテレメトリが欠落していること自体が危険の信号になりうる
  • アクセシビリティと画面取得の信号は、判断を補強する材料として使い、単独で取引を止める条件にはしない
  • サーバ側の取引リスク管理を、ログイン・資格情報の回復・振込先の新規登録・支払いの承認の各段で維持する

3番目は、本件の性質から出てきた助言です（本記録の整理）——改造版はアクセシビリティの一覧を空で返すため、「アクセシビリティが有効なら止める」という条件はそもそも発火しません。 一方、正規の利用者が読み上げ機能を使っている場合には発火します。 つまり、この信号は単独で使うと「攻撃者は通り、障害のある利用者が止まる」形になります（本記録の評価）。

2番目の「欠落が信号になる」という発想は、本記録が本件から最も持ち帰るべきものだと見ます（本記録の評価）。改造版は信号を「偽る」より「消す」ことが多い ——署名は正規のものを返し、アクセシビリティは空を返し、画面保護は外れる。 したがって、「あるはずの信号が来ていない」ことを異常として扱う設計が要ります。

利用者向けの助言は3点です（出典2。本記録の訳）。

  • 端末を最新に保つ
  • 非公式のストアから入手した APK を導入しない
  • Play Protect の走査を定期的に実行する

ただし、Play Protect が本件の標本を検出するかは示されていません〈未確定5〉（本記録の明示）。
