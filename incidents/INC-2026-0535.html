INC-2026-0535PAN-OS 管理IFの RCE が悪用

Palo Alto Networks が2026年10月14日、ファイアウォール向け OS「PAN-OS」の 管理インタフェースにおけるコードインジェクションの脆弱性 CVE-2026-0322 （CVSS v4.0 基本値 8.6・CWE-94）を公表した。認証済みの利用者がネットワーク経由で root 権限により任意のコードを実行できるもので、同社は「管理インタフェースを狙う ごく限定的な悪用を観測した」としている。回避策は無く、同社は対応優先度を 最高（Highest）とした。CISA は同日 KEV に収載し、連邦民間機関の対処期限を 2026年10月17日に設定した

脆弱性脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）未知の脆弱性の悪用設計・実装上の不備
初報: 2026年10月14日（Palo Alto Networks のセキュリティアドバイザリ公開） 最終更新: 2026年10月15日

2026年10月14日、Palo Alto Networks は自社のファイアウォール向け OS「PAN-OS」の管理インタフェースにおける脆弱性 CVE-2026-0322 を公表しました（出典1）。認証済みの利用者がネットワーク経由で root 権限により任意のコードを実行できるコードインジェクションで、CVSS v4.0 の基本値は 8.6（High）です（出典1）。

同社は悪用を観測したと明記しています（出典1）。

「Palo Alto Networks の管理インタフェースを狙う、ごく限定的な悪用を観測した」（出典1。原文英語。本記録の訳）

影響を受けるのは PA シリーズ（物理）・VM シリーズ（仮想）のファイアウォールと、集中管理製品 Panorama（仮想および M シリーズ）です（出典1）。Cloud NGFW と Prisma Access は影響を受けません（出典1）。

本記録が重く見るのは、次の3点の組み合わせです（本記録の評価）。

  • 回避策が存在しない（出典1。「No known workarounds exist for this issue」）
  • 「影響を受けるために特別な設定は要らない」（出典1。すべての対象構成が該当する）
  • CISA が公表と同日に KEV へ収載し、対処期限を3日後の2026年10月17日に設定した（出典2）

一方で、悪用には既存の認証情報が必要です（出典1・3）。つまりこの脆弱性は「入口」ではなく、管理者認証情報が既に奪われている環境で被害が root 権限まで広がる経路です（本記録の評価）。日本の読者にとっては、境界機器の管理インタフェースをどこから到達可能にしているか、そしてその認証情報をどう守っているかを同時に点検する契機になります（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は単一組織の被害事案ではなく、悪用が確認された脆弱性の構造である** （本記録の整理）。 **攻撃者は既存の認証情報で PAN-OS の管理インタフェースへ到達し、 コードインジェクション（CWE-94）によって root 権限で任意のコードを 実行できる**（出典1）。 **以下の各段階は、アドバイザリの記述（出典1）と報道（出典3）を 本記録が段階に分けて並べたものであり、 出典が段階別に説明したものではない**（本記録の整理）。

  1. 1. 偵察推定
    **攻撃者が、到達可能な PAN-OS 管理インタフェースを探す** （本記録の整理）。 **アドバイザリは「影響を受けるために特別な設定は必要ない」としており、 構成による除外が成り立たない**（出典1）。 **同社は悪用元として3つの IP アドレスを公表している**（出典1・3）。
    根拠: アドバイザリの記述「No special configuration is required to be affected by this issue」および悪用元 IP の公表 （出典1。本記録の訳と整理）。
  2. 2. 認証情報アクセス確認済
    **攻撃者が、管理インタフェースへログインできる認証情報を あらかじめ保有している**（出典1・3）。 **CVSS の PR:H がこれを示す**（出典1）。 **BleepingComputer は「攻撃者は既存の認証情報を必要とする」と 記している**（出典3）。
    根拠: CVSS ベクタの PR:H（出典1）、 BleepingComputer の記述「To exploit the vulnerability, attackers need existing credentials and network access to the PAN-OS management interface」（出典3。本記録の訳）。
  3. 3. 実行確認済
    **管理インタフェースのコードインジェクション（CWE-94）により、 ネットワーク経由で root 権限により任意のコードを実行する**（出典1）。 **利用者の操作は不要**（出典1）。 **攻撃の自動化は不可とされている（AU:N）**（出典1）。
    根拠: アドバイザリの表題「Authenticated Remote Code Execution (RCE) in the Management Interface」および CWE-94 の記載（出典1）。
  4. 4. 影響（暗号化・破壊・改ざん）確認済
    **root 権限で機器上の任意のコードが実行される**（出典1）。 **CVSS の VC:H / VI:H / VA:H は、 機器自身の機密性・完全性・可用性のすべてが高い影響を受けることを 示している**（出典1）。 **一方 SC:N / SI:N / SA:N であり、 評点上は後続システムへの影響は数えられていない**（出典1。整理は本記録）。
    根拠: CVSS ベクタ VC:H/VI:H/VA:H/SC:N/SI:N/SA:N（出典1）、 アドバイザリの「execute arbitrary code as root」（出典1。本記録の訳）。

悪用には既存の認証情報が必要——この脆弱性は入口ではなく、被害の深さを決める段である評価・解釈

CVSS ベクタの PR:H は、悪用に高い権限が必要であることを示します（出典1）。BleepingComputer はこれを「攻撃者は既存の認証情報と、PAN-OS 管理インタフェースへのネットワーク到達を必要とする」と説明しています（出典3。本記録の訳）。Security NEXT も「悪用するには認証が必要」と伝えています（出典4）。

ここから読み取れることは2つあります（本記録の評価）。

第一に、この脆弱性だけでは侵入は成立しません。 管理者の認証情報が先に奪われている必要があります。 したがって「この CVE を塞いだから安全」という整理は成り立ちません（本記録の評価）。認証情報がどう守られているか——多要素認証の有無、管理者アカウントの共用の有無、認証情報の保管場所——が同時に問われます。

第二に、この脆弱性があることで、奪われた認証情報の価値が跳ね上がります（本記録の評価）。管理インタフェースへのログインができるだけなら、設定変更の監査ログに現れる可能性があります。 root 権限での任意コード実行ができるなら、機器そのものを足場にでき、ログを含む機器内部の制御も攻撃者の側に移ります。

実際に何が起きたのかは公表されていません〈未確定4〉。BleepingComputer は「攻撃者がファイアウォールを侵害したのか、それを使って内部ネットワークへアクセスしたのか」を同社に問い合わせています（出典3）が、回答は記事に掲載されていません。

本記録の評価として、どちらであっても、被害を受けた組織の調査範囲は機器の外へ広がります ——root を取られた境界機器を「設定を直して使い続ける」判断は、機器の完全性を検証できない限り成り立ちません（本記録の評価）。

CISA は公表と同日に KEV 収載、期限は3日後に設定された当局対応

CISA は2026年10月14日に CVE-2026-0322 をKnown Exploited Vulnerabilities カタログへ収載しました（出典2）。

  • ベンダー・製品: Palo Alto Networks, PAN-OS（出典2）
  • 収載日: 2026年10月14日（出典2）
  • 対処期限: 2026年10月17日（出典2）
  • ランサムウェアでの使用: Unknown（出典2）

収載から期限までは3日です（本記録の算出）。KEV の期限は収載から3週間程度が通例であり、3日という設定は短いと言えます（本記録の一般的整理）。ただし、CISA が期限を短くした理由は公表されていません〈未確定6〉。

この期限は米国の連邦民間行政機関への拘束であり、日本の組織に適用されるものではありません（本記録の明示）。それでも、期限の短さは「悪用が現に進行している」という当局の判断を示す材料として読めます（本記録の評価）。

緩和策は「保護の網」ではなく「到達できる者を減らす」ことに尽きる対策・注意喚起

アドバイザリが挙げる手段は次のとおりです（出典1）。

  • 回避策は存在しない（「No known workarounds exist for this issue」）
  • 管理インタフェースへの到達を、信頼できる内部 IP または踏み台（jump box）に限定するとリスクが下がる
  • Threat Prevention の Threat ID 510046・510047（Applications and Threats コンテンツ 9159-10287 以降）が限定的な保護を提供する。ただし SSL 復号が必要
  • 追加の緩和: 管理ポートの通信をデータプレーンのポート経由にする、受信側の管理証明書を差し替える、受信する管理通信を復号する、受信する管理通信に Threat Prevention を有効にする

Threat Prevention の限界は、同社自身が明示しています（出典1・3）。

「Threat Prevention の保護が限定的であるとは、既知の攻撃パターンは現在の Threat ID で識別できるが、現時点で検知できない変種が存在しうることを意味する」（出典1・3。原文英語。本記録の訳）

本記録の評価として、実務上の順序は次のようになります（本記録の評価）。

  1. 自機の枝に対応する修正版へ更新する（これが唯一の解決である）

  • **境界機器の管理インタフェースは「認証情報が奪われた後」を前提に設計する**

    取るべき行動 **①境界機器の管理アカウント一覧を出し、多要素認証の有無と 共用アカウントの有無を確認する。** **②管理インタフェースへ到達できる発信元の一覧を、 構成から（運用の記憶ではなく）取り出す。** **③「管理者認証情報が奪われた場合に何が起きるか」を 境界機器ごとに書き出し、取締役会へ報告するリスク一覧に入れる。**

  • **ベンダーが示す「限定的な保護」を、対策済みと報告しない**
    **同社は Threat Prevention の署名について 「既知の攻撃パターンは識別できるが、検知できない変種が存在しうる」と 自ら限界を述べている**（出典1・3）。 **さらに署名の適用には SSL 復号が必要である**（出典1）。 **これを「暫定対策済み」と報告すると、 更新の優先度が下がる**（本記録の評価）。
    取るべき行動 **①暫定措置の報告様式に「何を防げないか」の欄を設け、 ベンダーの限界の記述をそのまま引く。** **②署名の適用に前提条件（本件では SSL 復号）がある場合、 自組織でその前提が満たされているかを確認してから 「適用済み」と記録する。**
セキュリティ技術者への示唆
  • **「最新版へ上げる」では決まらない——自機の枝に対応する修正版を確認する**
    **修正版は系統ごとに複数の枝に分かれている**（出典1）。 **例えば 11.1 系では 11.1.4-h37 / 11.1.6-h39 / 11.1.7-h11 / 11.1.10-h35 / 11.1.13-h15 / 11.1.16-h3 のいずれか以降である**（出典1）。 **枝を誤ると、更新しても修正が入らない**（本記録の評価）。
    取るべき行動 **①各機器の現在の版（枝まで）を一覧化する。** **②アドバイザリの表と突き合わせ、機器ごとに目標版を決める。** **③サポート切れの版を使っている機器を別扱いにする ——サポート対象版への移行が必要で、作業量が違う**（出典1）。
  • **公表された悪用元 IP 3件は、照合の出発点にしかならない**
    **同社は 66.42.72[.]14 / 208.83.239[.]114 / 149.248.47[.]234 を 公表している**（出典1・3）。 **アドバイザリはこれらを「脅威活動および限定的な悪用の試行に 関連する」と位置づけている**（出典1。本記録の訳）。 **本記録はこれらの悪性を検証していない**（本記録の留保） ——**照合先のテレメトリを持たないため、検知に直接用いることは 推奨しない。** **また、3件に当たらないことは侵害されていないことを意味しない** （本記録の評価）。
    取るべき行動 **①管理インタフェースへの接続ログを保持期間の全体にわたって検索し、 この3件との通信を確認する。** **②当たらなかった場合も「確認できなかった」と記録し、 「侵害なし」と結論しない。** **③同時に、管理インタフェースへの接続元の一覧を出し、 想定外の発信元がないかを確認する（IP の照合より網が広い）。**
  • **管理通信の復号をしていない環境では、ベンダー署名は発動しない**
    **Threat ID 510046・510047 は SSL 復号を必要とする**（出典1）。 **アドバイザリは追加の緩和として、受信する管理証明書の差し替え、 受信する管理通信の復号、管理通信への Threat Prevention の有効化を 挙げている**（出典1）。 **これらは単独の設定ではなく、連続した手順である**（本記録の整理）。
    取るべき行動 **①自組織で管理通信の復号を行っているかを確認する。** **②行っていない場合、署名が「適用されているが機能していない」 状態になっていないかを点検する。** **③復号を導入する場合の影響（証明書の管理・運用者の接続）を 更新作業と分けて評価する。**
  • **境界機器のログは機器外へ出す——root を取られた機器のログは証拠にならない**
    **本件は root 権限での任意コード実行である**（出典1）。 **機器上のログは、機器を掌握した攻撃者が操作できる** （本記録の一般的整理）。 **本件で機器内に残る痕跡は公表されていない**（出典1）〈未確定5〉。 **調査は機器の外に残る記録に依存する**（本記録の評価）。
    取るべき行動 **①境界機器のログ（管理インタフェースへの認証・設定変更・ セッション）を外部の収集基盤へ転送しているかを確認する。** **②転送していない機器を一覧化し、優先順位を付けて対応する。** **③管理インタフェースへの到達を、ネットワーク側の記録 （ファイアウォール・プロキシ・踏み台のログ）でも追えるようにする。**
