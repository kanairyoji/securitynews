INC-2026-0536Nextcloud 同梱 Collabora で侵害

Nextcloud の任意アプリ「Collabora Online - Built-in CODE Server」 （richdocumentscode）の proxy.php に、認証不要の OS コマンドインジェクション CVE-2026-110447（CVSS v4.0 9.2・CWE-78）があり、自己運用の Nextcloud サーバーに PHP の Web シェルが設置された。最初の攻撃は2026年9月10日に記録され、 修正版 26.4.303 は翌9月11日に出たが、注意喚起と CVE の公表は 2026年10月14日まで行われなかった。攻撃者はパスワード管理ファイルと 暗号資産ウォレットを探索していた

Nextcloud の任意アプリ「Collabora Online - Built-in CODE Server」（アプリ ID: richdocumentscode）に、認証を必要としない OS コマンドインジェクションの脆弱性 CVE-2026-110447 がありました（出典1）。CVSS v4.0 の基本値は 9.2（Critical）、弱点の種別は CWE-78 です（出典1）。

自己運用の Nextcloud サーバーに PHP の Web シェルが設置されました（出典2・3）。Web シェルとは、ウェブ要求で送られた任意のコマンドを、ウェブサーバーの権限で実行する小さなファイルです（出典4）。

本記録が本件を重く見る理由は、脆弱性の内容ではなく時間の並びです（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃者は認証を経ずに `/apps/richdocumentscode/proxy.php?status` へ 細工した GET 要求を送り、OS コマンドを実行して PHP の Web シェルを 設置した**（出典1・2）。 **成立する条件は、同梱の CODE サーバーが停止中であること （コンテナの再起動・更新・異常終了の直後）**（出典1）。 **設置後、ウェブサーバー利用者の権限でパスワード管理ファイルと 暗号資産ウォレットが探索された**（出典2・5）。 **以下の段階分けは、勧告（出典1）・課題 #354（出典2）・ 報道（出典5）の記述を本記録が段階に割り当てたものである** （本記録の整理）。

  1. 1. 初期侵入確認済
    **攻撃者が `/apps/richdocumentscode/proxy.php?status` へ 細工した GET 要求を送った**（出典2）。 **パストラバーサル（`%2e%2e`）・コマンド置換（`$(...)`）・ `${IFS}` による空白の難読化・Base64 で符号化した命令列を `sh` へ渡す形が使われた**（出典2）。 **エスケープされていないパスの値が `Collabora_Online.AppImage` 起動時の `remote_font_config.url` 引数へ渡される経路とされる**（出典5）。 **認証も利用者の操作も不要（PR:N / UI:N）**（出典1）。
    根拠: 課題 #354 に残された要求の記録（出典2）、 勧告の記述「proxy.php エンドポイントを通じて脆弱であり、 細工した要求によりウェブサーバー利用者として OS コマンドが実行される」（出典1。本記録の訳）。
  2. 2. 実行確認済
    **注入された命令列が `sh` で実行された**（出典2）。 **成立する条件は、同梱の CODE サーバーが起動していないこと （コンテナの再起動・更新・異常終了の直後）**（出典1）。 **CVSS ベクタの AT:P がこの前提条件に対応する**（出典1。整理は本記録）。
    根拠: 勧告の記述「この攻撃は、同梱の CODE サーバーが起動していないときに のみ機能する。コンテナの再起動、更新、異常終了の後などである」 （出典1。本記録の訳）、 課題 #354 の `remote_font_config.url` に命令列が見えるという報告 （出典2）。
  3. 3. 永続化確認済
    **Base64 の命令列が PHP の Web シェルを設置した**（出典2・5）。 **ファイル名は `shx*.php` 形式 （shxa35d0.php・shxf4645.php・shx13a86.php）**（出典2）。 **報道は `shrf*.php` 形式も挙げている**（出典5）〈齟齬3〉。 **回収された Web シェルは `c` パラメータの値を `shell_exec` へ渡し、 ウェブサーバー利用者の権限で任意のコマンドを実行できる**（出典2）。
    根拠: 課題 #354 における Web シェルの名前と実装の記述（出典2）、 UlliDieckmann の報告「Nextcloud の整合性チェックが shx13a86.php を検出した」（出典2。本記録の訳）。
  4. 4. 内部探索確認済
    **攻撃者はウェブサーバー利用者の権限で、 パスワード管理ソフトと暗号資産ウォレットのファイルを探索した** （出典2）。 **報道は対象を具体に挙げている**——**`*.kdbx`・`wallet.dat`・ `keystore.json`・Bitwarden・1Password、 および Bitcoin・Monero・Ethereum のディレクトリ**（出典5）〈齟齬3〉。
    根拠: HeikoBw の報告「1つのシステムで、攻撃者はパスワード管理ソフトと 暗号資産ウォレットのファイルを狙う探索コマンドを実行した」 （出典2。本記録の訳）。
  5. 5. 持ち出し推定
    **持ち出しの成立は確認されていない**（出典2）〈未確定3〉。 **HeikoBw は、精査した要求の範囲では持ち出しの痕跡が 見えなかったとしつつ、ウェブサーバー利用者が参照できる 秘密情報は露出したものとして扱うべきだと述べている**（出典2）。 **報道は、システムの識別情報を webhook.site の URL へ送って 感染を確認していたとしている**（出典5）〈齟齬3〉。
    根拠: 課題 #354 における報告者の記述（出典2）、 侵害指標としての webhook.site への参照（出典2）。

アプリを無効化しても防げない——止める方法は更新か削除の二択だった対策・注意喚起

勧告の運用上もっとも重要な記述がここです（出典1）。

「アプリを無効化しても問題を防げない。利用者は 26.4.303 以降へ更新するか、アプリを削除する必要がある」（出典1。原文英語。本記録の訳）

課題 #354 でも、同じ現象が報告されています（出典2）。UlliDieckmann はアプリを無効化した状態でも要求が届き続けたことから、「無効化したアプリが要求を受け続けるのは正しいのか」と問いかけています（出典2）。

これは Nextcloud のアプリの作りに由来します（本記録の整理）。proxy.php はアプリのディレクトリに置かれた PHP ファイルであり、アプリが無効であってもウェブサーバーから到達できます（本記録の一般的整理）——勧告はこの理由を説明していません（本記録の明示）。

影響の有無は、構成で分かれます（出典1・3）。

攻撃が成立する条件もあります（出典1）。

「この攻撃は、同梱の CODE サーバーが起動していないときにのみ機能する。コンテナの再起動、更新、異常終了の後などである」（出典1。原文英語。本記録の訳）

CVSS ベクタの AT:P（攻撃の前提条件がある）がこれに対応します（出典1。整理は本記録）。本記録の評価として、この条件は防御には使えません ——コンテナの再起動は運用で日常的に起きる事象であり、更新作業そのものが条件を作り出します。

なお、勧告は Nextcloud 29 以前が保守終了であることにも触れ、該当する利用者は Nextcloud 本体を更新するかアプリを削除すべきだと述べています（出典1）。

手口は「停止中のサーバーを起動しようとする処理」へのコマンド注入だった原因・手口

課題 #354 に残された要求の形から、手口が分かります（出典2）。

攻撃は /apps/richdocumentscode/proxy.php?status への細工した GET 要求です（出典2）。使われた技法は次のとおりです（出典2）。

  • パストラバーサル（%2e%2e）
  • コマンド置換（$(...)）
  • ${IFS} による空白の難読化
  • Base64 で符号化した命令列を sh へ渡す

報道（出典5）はさらに具体的な経路を伝えています ——エスケープされていないパスの値が、Collabora_Online.AppImage の起動時にremote_font_config.url 引数へ渡され、そこでシェルの置換が働くという説明です（出典5）。この説明は、課題 #354 で UlliDieckmann が「プロセス一覧に remote_font_config.url の中に命令列が見える」と報告している内容と整合します（出典2。整理は本記録）。

設置された Web シェルは次の形です（出典2・5）。

  • ファイル名: shx*.php（例: shxa35d0.php・shxf4645.php・shx13a86.php）（出典2）
  • 報道は shrf*.php 形式も挙げている（出典5）
  • c パラメータの値を shell_exec へ渡す実装（出典2）
  • 権限はウェブサーバー利用者（出典2・4）

侵害後の行動も記録されています（出典2・5）。HeikoBw は、1つの環境で攻撃者がパスワード管理ソフトと暗号資産ウォレットのファイルを狙う探索コマンドを実行したと報告しています（出典2）。報道は対象をより具体的に挙げています（出典5）——*.kdbx・wallet.dat・keystore.json・Bitwarden・1Password、および Bitcoin・Monero・Ethereum のディレクトリ。 また、システムの識別情報を webhook.site の URL へ送って感染を確認していたとされています（出典5）。

持ち出しの成立は確認されていません（出典2）〈未確定3〉。HeikoBw は、精査した要求の範囲では持ち出しの痕跡が見えなかったとしつつ、ウェブサーバー利用者が参照できる秘密情報は露出したものとして扱うべきだと述べています（出典2）。本記録はこの姿勢を妥当と評価します（本記録の評価）——Web シェルは任意のコマンドを実行できるため、ログに残った要求だけで持ち出しの有無を否定できません。

検知の端緒が環境ごとに違う点も記録に値します（出典2。整理は本記録）。

  • HeikoBw: ログ上の不審な要求
  • UlliDieckmann: Nextcloud の整合性チェックによる Web シェルの検出
  • ahlund: sudo の失敗通知メール

いずれも専用の監視ではなく、既存の仕組みが偶然に拾ったものです（本記録の評価）。

同じ部品で10か月前にも類似の脆弱性が出ており、その修正では防げなかった背景・過去事例

勧告は、過去の CVE との関係を明記しています（出典1）。

「これは CVE-2025-66208 とは別のコード経路であり、あの CVE に対する修正では本件を防げない」（出典1。原文英語。本記録の訳）

CVE-2025-66208 の勧告（GHSA-j3q6-q5pc-v5wf、重要度 Moderate、「Configuration-Dependent RCE (OS Command Injection) in richdocumentscode proxy」）は2025年12月3日に公開されています（出典1）。

つまり、同じ richdocumentscode の proxy において、約10か月の間に2件の OS コマンドインジェクションが公表されたことになります（本記録の整理）。重要度は Moderate から Critical（9.2）へ上がっています（出典1）。

本記録の評価として、ここから読める点は2つです。

第一に、「前回のパッチを当てたから大丈夫」は成り立ちません。 勧告自身が、前回の修正では防げないと述べています（出典1）。

第二に、この部品は「開発・検証向けの同梱サーバー」です（出典2）。開発側（mmeeks）は2026年9月14日、影響は Development Edition に限られ、同梱 CODE サーバーがローカルの AppImage を取得する構成でのみ起きると述べています（出典2）。本記録の評価として、これは利用実態と食い違いうる説明です ——同梱版は「手軽に文書編集を使える構成」として本番環境でも選ばれます（本記録の評価）。実際に侵害を報告したのは、本番運用中の管理者です（出典2。評価は本記録）。

  • **「security fix と書かれていない更新」が安全に遅らせられるとは限らない**

    取るべき行動 **①自組織が依存するアプリ・プラグインについて、 版情報以外の情報源（課題管理システム・コミュニティ掲示板）を 監視対象に含めるかを判断する。** **②「security fix の記載が無い更新」をどう扱うかの方針を 明文化する（本件のような事例があることを前提にする）。** **③依存している小規模な部品の数を把握し、 監視できる数に収まっているかを確認する。**
  • **「使っていないから無効化してある」は、攻撃面の除去ではない**
    **勧告は「アプリを無効化しても問題を防げない」と明記している** （出典1）。 **課題 #354 でも、無効化した状態で要求が届き続けたことが 報告されている**（出典2）。 **本記録の評価として、これは Nextcloud 固有の話ではなく、 「無効化」という操作が何を止めるのかを確認していない運用の問題である。**
    取るべき行動 **①導入済みで使っていない拡張・プラグインの一覧を出し、 無効化ではなく削除する方針に切り替える。** **②「無効化」が何を止める操作なのかを、 基盤ごとにベンダー文書で確認する。** **③棚卸しの周期を決める（使わない部品は増え続ける）。**
  • **自己運用の基盤では、検知は「偶然に拾えるか」で決まっている**
    **本件で侵害に気づいた端緒は、ログ上の不審な要求（HeikoBw）、 Nextcloud の整合性チェック（UlliDieckmann）、 sudo の失敗通知メール（ahlund）である**（出典2）。 **いずれも専用の監視ではない**（本記録の評価）。 **ahlund が気づいたのは最初の攻撃から8日後である** （出典2。算出は本記録）。
    取るべき行動 **①自組織が自己運用している基盤について、 「侵害されたらどの仕組みが教えてくれるか」を1つ以上挙げられるか 確認する。挙げられないなら、それが現状である。** **②整合性チェックのような標準機能を、定期実行と結果確認まで 運用に組み込む。** **③自己運用の基盤に、認証情報や鍵素材を同居させていないか 点検する（本件の攻撃者はそれを探していた）**（出典2・5）。
  • **Web シェルを設置された環境は、更新だけでは回復しない**
    **開発側は、更新に加えて残存する `shx*.php` の削除を 助言している**（出典2）。 **報道も「更新は既存のバックドアを除去しない」と注意している** （出典5）。 **報告者は、ウェブサーバー利用者が参照できる秘密情報は 露出したものとして扱うべきだと述べている**（出典2）。
    取るべき行動 **①「脆弱性を塞ぐ」と「侵害を回復する」を別の作業として 手順に分ける。** **②ウェブサーバー利用者が参照できる認証情報・鍵・トークンの 一覧を作り、侵害時に再発行する対象として定義する。** **③再発行の所要時間を平時に測る（本件のような小規模環境では、 誰が何を再発行するのかが決まっていないことが多い）。**
セキュリティ技術者への示唆
  • **確認すべきは、richdocuments ではなく richdocumentscode の有無である**
    **影響を受けるのは同梱の CODE サーバー（richdocumentscode）であり、 スタンドアロンの Collabora Online は影響を受けない**（出典1）。 **外部の Collabora を参照する richdocuments のみの構成、 Docker や配布パッケージによる Collabora、 ホスティング版も影響を受けない**（出典3）。 **「Collabora を使っているか」では判定できない**（本記録の評価）。
    取るべき行動 **①`occ app:list` 等でアプリ一覧を取り、 richdocumentscode の有無と版を確認する。** **②26.4.303 未満なら 26.4.303 以降へ更新する。 使っていなければ削除する（無効化では足りない）**（出典1）。 **③Nextcloud 本体が 29 以前なら、本体の更新も必要である**（出典1）。
  • **更新後も、アプリのディレクトリに残った Web シェルを探す**
    **設置された Web シェルは `shx*.php` 形式 （shxa35d0.php・shxf4645.php・shx13a86.php）**（出典2）。 **報道は `shrf*.php` 形式も挙げている**（出典5）〈齟齬3〉。 **ファイル名は毎回異なるため、完全一致では探せない** （本記録の評価）。 **`c` パラメータの値を `shell_exec` へ渡す実装である**（出典2）。
    取るべき行動 **①`/apps/richdocumentscode/` 配下の PHP ファイルを列挙し、 配布物に含まれないものを洗い出す（名前の照合より確実である）。** **②Nextcloud の整合性チェックを実行する ——本件で実際に Web シェルを検出した手段である**（出典2）。 **③見つかった場合、削除で終わらせず、 そのファイルへのアクセスログを遡って調査範囲を決める。**
  • **ウェブサーバー利用者がシェルを起動したら、それ自体が異常である**
    **本件の実行段では、注入された命令列が `sh` で実行された** （出典2）。 **報道は侵害指標として「不審な www-data プロセス」を 挙げている**（出典5）。 **通常の運用で、ウェブサーバー利用者がシェルを起動することは ほとんど無い**（本記録の一般的整理）。
    取るべき行動 **①ウェブサーバー利用者によるシェル起動と外向き通信を 監視・警報の対象にできるか確認する。** **②できない場合、せめて更新・再起動の直後にログを確認する運用を 作る——本件の攻撃は CODE サーバーが停止中のときだけ成立し、 その条件は運用作業が作り出す**（出典1。評価は本記録）。 **③webhook.site のような正規サービスへの外向き通信を 把握しているか確認する**（出典2・5）。
  • **過去の同種 CVE の修正は、今回の経路を防がない**
    **勧告は「これは CVE-2025-66208 とは別のコード経路であり、 あの CVE に対する修正では本件を防げない」と明記している**（出典1）。 **CVE-2025-66208 の勧告は2025年12月3日に公開されている**（出典1）。 **同じ部品で約10か月の間に2件の OS コマンドインジェクションが 公表されたことになる**（本記録の整理）。
    取るべき行動 **①「前回のパッチを当てたから大丈夫」という判断を、 勧告の記述で必ず確認する。** **②同じ部品で同種の脆弱性が繰り返し出ている場合、 その部品を使い続けるかどうかを別途判断する （本件では、使っていなければ削除が選べる）**（出典1）。
