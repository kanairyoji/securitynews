INC-2026-0539Aoki が AI 支援の API キーを窃取

Symantec の Threat Hunter Team は2026年10月15日、情報窃取型マルウェア 「Aoki（Aokigahara）」の新しい版が AI コーディング支援の認証情報・セッション ファイルを窃取対象に加えたと報告した——`.claude.json`・Claude デスクトップの cookie・ChatGPT の cookie・OpenAI Codex の `config.toml` と `.env`・ Cursor のローカル状態データベースを狙い、GitHub Copilot・Cursor・Google Gemini・ JetBrains AI Assistant・Kiro のトークンと AWS の資格情報もあわせて持ち出す。 以前の版はブラウザ・暗号資産ウォレット・パスワード管理の情報だけを対象にしており、 AI 関連ファイルは狙っていなかった。窃取した API キーは正規利用者の身元と 利用枠のまま使えるため「LLMjacking」として直接換金でき、同時に連携先の リポジトリ・クラウド・CI/CD への入口にもなる。Symantec は背後の集団を 特定できておらず、既存のマルウェアファミリとの関連も示していない

情報窃取型マルウェアの窃取対象一覧に、AI コーディング支援の設定ファイルが入りました。

2026年10月15日、Symantec の Threat Hunter Team（Symantec and Carbon Black, Broadcom）は、情報窃取型マルウェア「Aoki」の新しい版が AI コーディング支援の認証情報・セッションファイルを狙うようになったと報告しました（出典1）。Aoki は2026年のうちに初めて観測された比較的新しいファミリで、公開された分析はほとんどありません（出典1・2）。

本記録が要点と見たのは、次の3点です。

  • 狙われているのはソースコードではなく「鍵」である。 窃取対象として挙げられているのは .claude.json、Claude デスクトップの cookie、ChatGPT の cookie、OpenAI Codex の config.toml と .env、そして GitHub Copilot・Cursor・Google Gemini・JetBrains AI Assistant・Kiro のトークンです（出典1・2）。例外は Cursor のローカル状態データベースで、ここには対話の文脈とコード断片が残ることがあります（出典1）。
  • 「鍵が盗まれた」で終わらない。 Symantec は、盗まれたキーが正規開発者の身元と API 利用枠のまま使われ、さらに連携先のリポジトリ・クラウドサービス・CI/CD パイプラインを露出させうると述べています（出典1・2）。キーの直接換金（転売・利用枠の食い潰し）は「LLMjacking」と呼ばれており、Symantec は決済カード情報と同じ価値になったと評価しています（出典1・2）。
  • 誰がやっているかは分かっていない。 Symantec は背後の集団を特定できておらず、既存のマルウェアファミリとの関連を示す兆候も無いとしています（出典1・2）。窃取対象の残りが暗号資産ウォレットと拡張機能に偏っていることから、金銭目的と見られるという評価だけが示されています（出典2）。

本記録は2026年10月16日に Symantec の報告本文（出典1）を直接取得して裏を取りました。 配布・感染の経路、被害の件数、対象地域・業種はいずれも公表されていません〈未確定1〜3〉。

  • トレードオフ: **分からないと書けば記事としての訴求は弱まる。** **一方で、後から誤りが判明して訂正する必要が生じない**（本記録の整理）。

盗まれるのはコードではなく「鍵の置き場」——ファイル名の水準まで公表された原因・手口

Symantec が挙げた窃取対象は、製品名ではなくファイルの名前で示されています（出典1）。

  • Claude: .claude.json、および Claude デスクトップの cookie
  • ChatGPT: cookie
  • OpenAI Codex: config.toml、.env
  • Cursor: ローカル状態データベース（対話の文脈やコード断片が残ることがある）
  • トークンを取る対象: GitHub Copilot、Cursor、Google Gemini、JetBrains AI Assistant、Kiro
  • あわせて: AWS の資格情報
  • Codeium も対象に挙げられているが、具体のファイル名は示されていない（出典1）

ここから読める性質は2つあります（本記録の整理）。

第一に、狙われているのは成果物ではなく資格情報です。 Symantec は「主に資格情報・トークン・セッションファイルを取り、ソースコードは取らない。Cursor のデータベースが例外である」と述べています（原文英語。出典1）。ソースコードの流出を心配する設計（DLP・リポジトリの監視）ではこの窃取は見えません（本記録の評価）。

第二に、置き場が利用者の端末上の平文ファイルであることが前提になっています。 .claude.json・config.toml・.env はいずれも開発者の作業端末のホームディレクトリやプロジェクト直下に置かれる設定ファイルです（本記録の整理）。窃取に特別な権限昇格や脆弱性は要らず、利用者の権限で読めれば足ります（本記録の評価。出典1 に権限昇格の記述は無い）。

なお Symantec の報告は、従来の窃取対象が縮んでいないことも示しています（出典1）。約50のブラウザ、数十の暗号資産ウォレット拡張とデスクトップウォレット、"mnemonic"・"wallet"・"keystore" を名前に含むファイル、Discord のトークン、Telegram のデータ、Steam・Roblox・Epic Games・Minecraft、レジストリ内の Outlook のパスワードと Thunderbird のプロファイル、FileZilla・WinSCP 等の FTP クライアント、OpenVPN・NordVPN・ProtonVPN 等の VPN クライアント、KeePass・Bitwarden・1Password・Dashlane 等のパスワード管理ソフト、そして導入済みのセキュリティ製品の記録——これらはそのままです（出典1）。AI 対応は「置き換え」ではなく「追加」である（本記録の整理）。

「正規利用者として使える」ことが被害の中身である——API キーの性質がそうさせる被害規模・影響範囲

Symantec が述べている影響は、キーの紛失そのものではありません（出典1・2）。

盗まれた API キーとトークンは、正規利用者の身元と API 利用枠のもとで攻撃者が活動を行うことを可能にし、要求が信頼された利用者から発せられていると仮定している安全装置を迂回させる（原文英語。出典1・2）

さらに、トークンは連携先を露出させます（出典1・2）。

トークンは、そのアカウントに紐づいたリポジトリ、クラウドサービス、および継続的インテグレーション／継続的デリバリ（CI/CD）のパイプラインも露出させうる（原文英語。出典1・2）

換金の筋道についても、報告は明示しています（出典1・2）。

カード情報と同じように、盗まれた AI キーは直接換金できる。転売するか、被害者のアカウントで利用を積み上げるかであり、後者は LLMjacking と呼ばれることがある。カード情報と違うのは、開発者のより広い環境への経路にもなりうる点である（原文英語。出典1・2）

本記録はここに2つの含みを見ます（本記録の評価）。

①被害の最初の兆候は、セキュリティ製品のアラートではなく請求書になりうる。 利用枠の食い潰しは「正規の鍵による正規の API 呼び出し」であり、マルウェアの痕跡としては現れません（本記録の評価）。逆に言えば、利用量の急増は検知の材料になります（本記録の提案。出典1 に記述は無い）。

②「AI の鍵」を資格情報の棚卸しに入れていない組織が多い。 人のアカウント（SSO・MFA）と、サービス間の認証（クラウドの IAM ロール）は管理の対象に入っていることが多い一方、開発者の端末に置かれた AI 支援のキーは、どちらの枠にも入っていないことがあります（本記録の評価）。Symantec が AWS の資格情報と AI のキーを同じ窃取対象の列に並べている点は、その意味で示唆的です（出典1。読み方は本記録）。

帰属は示されていない——「日本の地名」からも読み取らない評価・解釈

Symantec は帰属について、分からないと明示しています（出典1・2）。

我々は、どの脅威集団が Aoki 情報窃取型マルウェアの背後にいるのかを知らず、既存のいずれのマルウェアファミリとの繋がりを示す兆候も無い（原文英語。出典1・2）

示されているのは動機の推定までです（出典2）。「窃取対象一覧の残りが暗号資産関連のウォレットと拡張機能に偏っていることから、攻撃者は金銭目的であると示される」（原文英語。出典2）。

名前についても、報告は含みを持たせていません（出典1）。「Aokigahara」は復号処理のなかで使われる長い文字列で、これが日本の有名な森の名であることには触れつつ、開発者について何かを明らかにするものかは不明である**としています（原文英語。出典1）。

本記録はこれを帰属の材料として使いません（本記録の方針）。マルウェア内の文字列から出身地・言語圏を推定するのは、偽装が容易な指標に依拠することになります（本記録の評価）。記録に残すのは「名前の由来の説明がある」という事実だけです。

この報告で塞げる入口は示されていない——検知と棚卸しに寄せるしかない再発防止

本件の最大の欠落は、配布・感染の経路が書かれていないことです（出典1。本記録の整理）。

したがって「どの入口を塞ぐか」という形の対策は、この資料からは導けません（本記録の評価）。示されているのは次の2つだけです（出典1）。

  • Symantec のエンドポイント製品は Infostealer.Aoki として検知する（出典1）
  • C&C の3ドメインと /gate という送出先、17件の SHA-256 ハッシュ（出典1）

本記録は IoC の値を転記しません（本記録の方針）。照合先のテレメトリを持たないため検知に使えず、かつ悪性の検証を自前で行っていないからです。 必要な読者は出典1 の原典から取ってください。

代わりに、本記録が有効と見る対策は資格情報の側に寄ります（本記録の評価）。①AI 支援のキーを「棚卸しの対象」に入れる。②長期有効なキーを短命な資格情報に置き換える。③連携先（リポジトリ・クラウド・CI/CD）の権限を、AI 支援のキーが握れる範囲として評価する。④利用量の異常を検知の入口にする。 いずれも Symantec が述べたことではなく、本記録の提案です（本記録の明示）。

CISO・経営層への示唆
  • **「AI の鍵」は資格情報の台帳に載っているか——載っていないなら本件は未対応である**
    **人のアカウントとクラウドの IAM は管理対象に入っていても、 開発者の端末に置かれた AI 支援のキーはどちらの枠にも入らないことがある** （本記録の評価）。 **Symantec は AWS の資格情報と AI のキーを同じ窃取対象の列に並べている** （出典1）。
    取るべき行動 **①AI コーディング支援の利用実態を部門別に洗い出し、 誰がどのツールにどの鍵を持っているかを一覧にする。 ②その鍵の有効期限・権限範囲・連携先を記録する。 ③台帳に載らない「個人契約のまま業務で使っている鍵」を特定し、 組織の管理下に移すか禁止するかを決める。**
  • **被害の最初の兆候はアラートではなく請求書になりうる**
    **窃取されたキーの悪用は、正規の鍵による正規の API 呼び出しである** （出典1・2。整理は本記録）。 **Symantec は「被害者のアカウントで利用を積み上げる（LLMjacking）」を 換金手段として挙げている**（原文英語。出典1・2）。
    取るべき行動 **①AI API の利用量・課金額を部門別・鍵別に可視化し、 月次ではなく日次で見る経路を作る。 ②急増時に誰が一次対応するかを決めておく（経理ではなくセキュリティ側）。 ③「使っていない鍵」の失効を定期の作業に入れる。**
  • **連携先の権限が、そのまま被害の広さになる**
    **Symantec は、トークンがアカウントに紐づいた リポジトリ・クラウドサービス・CI/CD パイプラインを露出させうると 述べている**（原文英語。出典1・2）。
    取るべき行動 **①AI 支援が握っているリポジトリ・クラウド・CI/CD の権限を一覧にする。 ②書き込み・デプロイの権限が必要かを機能ごとに問い直す。 ③CI/CD への到達経路がある場合、 そこから本番に出る経路に人の承認を挟む。**
  • **配布経路が公表されていない脅威に、入口対策で応じようとしない**
    **Symantec の報告には配布・感染の経路が無い**（出典1）〈未確定2〉。 **入口が分からないまま入口を塞ぐ投資をすると、 外れたときに何も残らない**（本記録の評価）。
    取るべき行動 **①本件への対応は「鍵の管理」と「異常利用の検知」に寄せる。 ②入口対策は、情報窃取型マルウェア全般への既存の対策 （実行制御・ブラウザ拡張の管理・海賊版ソフトの排除）として扱い、 本件固有の投資にしない。 ③配布経路に関する追加報告が出た時点で見直す前提を決めておく。**
セキュリティ技術者への示唆
  • **自分の端末の `.claude.json`・`config.toml`・`.env` に何が入っているかを数える**
    **これらは Symantec が名指しした窃取対象である**（出典1）。 **設定ファイルは「一度書いたら忘れる」ため、 失効させていない古い鍵が残りやすい**（本記録の評価）。
    取るべき行動 **①ホームディレクトリとプロジェクト直下の設定ファイルを列挙し、 含まれている鍵を数える。 ②業務で使っていない鍵をその場で失効させる。 ③`.env` を誤ってコミットしていないかを履歴まで遡って確認する。**
  • **AI 支援のトークンに、必要以上のスコープを与えていないか確認する**
    **トークンがリポジトリ・クラウド・CI/CD を露出させうる**（出典1・2）。 **「とりあえず広く」で発行した鍵が、窃取時の被害範囲を決める** （本記録の評価）。
    取るべき行動 **①各トークンのスコープを発行元の管理画面で確認する。 ②読み取りで足りるものを読み取りに落とす。 ③組織のリポジトリに触れるトークンを個人アカウントで持っていないか確認する。**
  • **Cursor のローカル状態データベースは「対話の履歴」ではなく「漏れる資料」として扱う**
    **Symantec は、Cursor のローカル状態データベースが 対話の文脈とコード断片をキャッシュすることがあり、 窃取対象になっていると述べている**（出典1）。 **これは窃取対象のなかで唯一、資格情報ではなく内容そのものである** （出典1。整理は本記録）。
    取るべき行動 **①機微な識別子・接続文字列・顧客データを対話に貼らない運用にする。 ②貼らざるを得ない場合の代替（ダミー値・マスク）を決めておく。 ③端末の全ディスク暗号化と画面ロックを前提条件として確認する。**
  • **IoC の照合先を持っていないなら、ハッシュとドメインの転記で安心しない**
    **公表されているのは C&C ドメイン3件と SHA-256 17件である**（出典1）。 **照合するテレメトリが無ければ、一覧を手元に置いても何も起きない** （本記録の評価）。
    取るべき行動 **①自組織のどのログで通信先を照合できるかを先に確認する （プロキシ・DNS・EDR のいずれか）。 ②照合できる経路が無い場合は、その欠落を課題として記録する。 ③本記録は IoC の悪性を検証していないため、原典から取る。**
