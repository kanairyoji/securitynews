INC-2026-0540FortiManager 1台から500台超へ

Palo Alto Networks Unit 42 は2026年10月14日、通信事業者（他社のファイアウォールを 預かるマネージドサービス提供者）への多段侵入を調査結果として公表した—— 攻撃者は2024年9月に CVE-2024-47575（FortiJump）で中央の FortiManager 1台を 未認証で奪い、そこから500台を超える管理下 FortiGate の設定・暗号学的信頼情報・ データベースを一括で持ち出した。設定内に可逆な暗号文として入っていた管理者・ SSL-VPN の資格情報は復元可能で、Unit 42 自身が総当たりで復元を確認している。 その後 FortiOS の auto-script のパストラバーサル CVE-2025-61624 で root へ昇格し、 ディスクに残らず待ち受けポートも持たない ARM64 の常駐しない注入型マルウェア PEERSTITCH を miglogd と iked のメモリへ埋め込んだ。Apache mod_md の ACME 機構を 逆シェルに転用し、FortiManager になりすまして他の管理下機器から設定を抜いている。 クラスタ名は CL-STA-0954（別名 UNC5820）で、国家背景が疑われる侵入との重なりがある

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及初報のみ有名事象として記録（日本と直接の関係は薄い）未知の脆弱性の悪用認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備
初報: 2026年10月14日（Unit 42 の調査報告公開） 最終更新: 2026年10月16日（本記録の確認時点）

管理装置1台の陥落が、500台を超えるファイアウォールの鍵と設定の流出になりました。

2026年10月14日、Palo Alto Networks の Unit 42 は、通信事業のマネージドサービス提供者に対する多段侵入の調査結果を公表しました（出典1）。侵入は2024年9月に発生し、Unit 42 はこの活動をクラスタ CL-STA-0954（別名 UNC5820）として追跡しています（出典1）。侵入後の活動の一部は、国家背景が疑われる攻撃者による侵入と重なるとしています（出典1）。

本記録が要点と見たのは、次の4点です。

  • 起点は1台、影響は500台超。 攻撃者は中央の FortiManager に CVE-2024-47575（FortiJump）を使って未認証で侵入し、.tm という名の設定アーカイブを作って持ち出しました（出典1）。中身は、500台を超える管理下 FortiGate の完全な稼働設定、シリアル番号と公開 IP の一覧、集中管理のデータベース（global.db・revinfo.db）、内部ネットワークの構成図と経路表、可逆な暗号文の資格情報、そして公開証明書と秘密鍵を含む暗号学的信頼情報です（出典1）。これらのファイアウォールは、同社自身の基盤と顧客企業のネットワークを守っていました（出典1）。
  • 資格情報は「復元できる」ことが確認されている。 Unit 42 は、持ち出された設定ファイルから管理者と SSL-VPN のパスワードを総当たりで復元できることを確認したと述べています（出典1）。攻撃者はその正規の資格情報で、外部の踏み台から SSL-VPN の接続を張り直しています（出典1）。
  • ディスクに残らず、待ち受けもせず、自分から通信もしないマルウェア。 FortiOS の auto-script のパストラバーサル CVE-2025-61624 で root へ昇格した後、攻撃者は PEERSTITCH を /bin/miglogd と /bin/iked のメモリへ注入しました（出典1）。PEERSTITCH は永続的なバイナリをディスクに残さず、待ち受けポートを開かず、自分から外向きの接続も行いません（出典1）。正規プロセスが生成する通信のなかに目印（8550・169.254.0.1）を探し、見つけた識別子を /proc/<pid>/mem 経由でもう一方のデーモンへ直接書き込みます（出典1）。
  • 管理装置になりすませる。 FortiGate と FortiManager の通信（FGFM・TCP 541番）は、シリアル番号に対して検証される暗号学的信頼情報に依存します（出典1）。それが初期侵入で丸ごと持ち出されているため、攻撃者は FortiGateCloud という名の管理者アカウントで複数の管理下ファイアウォールから設定を取得しました（出典1）。被害組織は FortiManager Cloud のテナントを運用しておらず、そのようなアカウントは当該機器に作られていませんでした（出典1）。

本記録は2026年10月16日に、初期侵入に使われた CVE-2024-47575 のFortinet 勧告（出典2）と、権限昇格に使われた CVE-2025-61624 のFortinet 勧告（出典3）を直接取得して裏を取りました。 とくに前者の勧告には、Unit 42 が観測した不正登録機器のシリアル番号FMG-VMTM23017412、IP アドレス2件、/tmp/.tm というファイルが侵害指標として載っています（出典2。突き合わせは本記録）——本件が既知の FortiJump 悪用の波の一部であることを、製品ベンダー側の資料が裏付けています（本記録の整理）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃者は2024年9月、中央の FortiManager に CVE-2024-47575 を悪用して 未認証で侵入し、500台を超える管理下 FortiGate の設定・資格情報・ 暗号学的信頼情報を一括で持ち出した**（出典1）。 **設定内の可逆な暗号文から管理者・SSL-VPN の資格情報を復元して再侵入し、 FortiOS の auto-script のパストラバーサル CVE-2025-61624 で root へ昇格、 ディスクに残らない ARM64 の注入型マルウェア PEERSTITCH を `/bin/miglogd` と `/bin/iked` のメモリへ埋め込んだ**（出典1）。 **C2 は Apache `mod_md` の ACME 機構を転用した逆シェルで、 さらに FGFM 越しに FortiManager になりすまして 他の管理下機器から設定を取得した**（出典1）。 **クラスタ名は CL-STA-0954（別名 UNC5820）で、 侵入後の活動の一部は国家背景が疑われる侵入と重なる**（出典1）。

  1. 1. 初期侵入確認済
    **中央の FortiManager に対し CVE-2024-47575（FortiJump）を悪用し、 未認証で任意のコマンドを実行した**（出典1・2）。 **不正な仮想 FortiGate `localhost`（シリアル `FMG-VMTM23017412`）を 外部基盤（`45.32.41[.]202`、後に `198.199.122[.]22`）から登録した**（出典1）。
    根拠: Fortinet の勧告が侵害指標として同じシリアル番号と IP を挙げていること （出典2。突き合わせは本記録）
  2. 2. 持ち出し確認済
    **機器登録の直後に `.tm` という設定アーカイブを生成し、持ち出した**（出典1）。 **中身は、FortiManager 自身のシリアル番号と全登録機器との管理関係、 500台を超える管理下 FortiGate の完全な稼働設定、 集中管理データベース（`global.db`・`revinfo.db`）、 500台超のシリアル番号と公開 IP の平文一覧、 内部構成図・経路表・インタフェース設定、 可逆な暗号文の管理者・ローカル・SSL/VPN 資格情報、 公開証明書と秘密鍵を含む符号化された暗号学的信頼情報**（出典1）。
    根拠: 「500台を超える管理下 FortiGate ファイアウォールについての 稼働設定、暗号学的材料、およびデータベースファイルを含む アーカイブを持ち出した」（原文英語。出典1）
  3. 3. 内部探索確認済
    **長い潜伏期間の後、侵害した FortiManager から下流の管理下 FortiGate へ 不正なスニッファ設定を配布した**（出典1）。 **捕捉対象は暗号化されていない HTTP と TCP 3696〜3706番の11サービスで、 平文の資格情報の傍受・内部通信の捕捉・内部構成の把握・ 稼働ホストの発見・イベント列の監視が意図されている**（出典1）。 **後続の段階では境界ファイアウォールに対し UDP 69番（TFTP）、UDP 1812・1813番（RADIUS）、 TCP 389番（LDAP）を対象とする規則を追加した**（出典1）。
    根拠: Unit 42 がポート・サービス識別子・対象プロトコルの目的・ 想定された意図を表として示していること（出典1）
  4. 4. 認証情報アクセス確認済
    **持ち出した設定ファイル内の可逆な暗号文から、 管理者と SSL/VPN のパスワードを復元した**（出典1）。 **Unit 42 自身が総当たりで復元できることを確認している**（出典1）。
    根拠: 「我々は、持ち出された設定ファイルから管理者および SSL/VPN の パスワードを総当たりで復元することに成功し、 資格情報が復元可能であることを確認した」（原文英語。出典1）
  5. 5. 横展開確認済
    **復元した正規の資格情報で、既知の外部踏み台 （`23.240.77[.]233`・`47.18.167[.]159`）から 境界ファイアウォールへ SSL-VPN セッションを張った**（出典1）。 **これにより内部のネットワーク管理セグメントへ 認証済みで到達した**（出典1）。
    根拠: 「正規の資格情報を使い、攻撃者は既知の外部の staging 基盤から不正な FortiGate SSL/VPN セッションを確立した」 （原文英語。出典1）
  6. 6. 権限昇格確認済
    **CVE-2025-61624 を悪用し、FortiOS の管理権限から 基盤 OS の root へ昇格した**（出典1・3）。 **auto-script のオブジェクト名が無害化されていないため、 名前にトラバーサル列を含めるとスクリプト本体を 任意のファイルシステム上の位置へ置ける**（出典1）。 **`../../../../setup` を作成し、PEERSTITCH の初段ローダを設置した**（出典1）。
    根拠: Fortinet の勧告が「権限を持つ攻撃者が、細工したコマンド引数により 任意のファイルの書き込みまたは削除を達成しうる」としていること （原文英語。出典3）
  7. 7. 永続化確認済
    **PEERSTITCH を `/bin/miglogd` と `/bin/iked` のメモリへ注入した**（出典1）。 **`hxxp[:]//23.240.77[.]233:8085/` から5ファイルを `/data2/template/` へ取得し、 `ipssem.js` が `lldprx` を起動する**（出典1）。 **`ptrace(PTRACE_SEIZE)` で両プロセスに接続し、 動的に生成した ARM64 のブートストラップで 16,384バイトの RWX 領域を `mmap` し、1,344バイトのペイロードを `/proc/<pid>/mem` 経由で書き込む**（出典1）。 **永続的なバイナリをディスクに残さず、待ち受けポートを開かず、 自分から外向きの接続を開始しない**（出典1）。

1台の管理装置が落ちた時点で、500台分の鍵が攻撃者の手に渡っていた原因・手口

初期侵入は、中央の FortiManager 1台に対する未認証の遠隔コード実行でした（出典1・2）。

CVE-2024-47575（外部では FortiJump と呼ばれる）は、FMG-Access 管理チャネル（TCP 541番）への細工した要求により、未認証の遠隔攻撃者が任意のコマンドを実行できる脆弱性です（出典1）。Fortinet の勧告では、FortiManager の fgfmd デーモンにおける重要な機能の認証欠落（CWE-306）とされ、深刻度は Critical・CVSSv3 は 9.8 です（出典2）。

攻撃者がやったことは単純です（出典1）。外部の基盤（45.32.41[.]202、後に 198.199.122[.]22）から、localhost という名の不正な仮想 FortiGate（シリアル番号 FMG-VMTM23017412）を中央の FortiManager へ登録し、登録直後に .tm という設定アーカイブを生成して持ち出しました（出典1）。

持ち出された中身が本件の重さを決めています（出典1）。

  • FortiManager 自身のシリアル番号と、登録されている全機器との管理関係
  • 500台を超える管理下 FortiGate の完全な稼働設定ファイル（同社自身の基盤と顧客ネットワークの両方）
  • 集中管理の SQLite データベース——global.db（管理ドメイン・グローバルオブジェクト・ポリシーパッケージ）とrevinfo.db（機器の改訂メタデータ）
  • 500台を超える FortiGate のシリアル番号と、それぞれの公開 IP アドレスを並べた平文の一覧
  • 内部ネットワークの構成図、経路表、インタフェース設定
  • 管理者・ローカル・SSL/VPN の資格情報（可逆な暗号文として）

本記録はここを「設定の流出」と読みません（本記録の評価）。流出したのは、500台のファイアウォールに対する正規の支配権そのものです。 シリアル番号と公開 IP の一覧があれば宛先が分かり、暗号学的信頼情報があれば管理装置として振る舞え、可逆な暗号文の資格情報があれば管理者として入れます（本記録の整理）。

なお本記録は、Fortinet の勧告（出典2）がFMG-VMTM23017412・45.32.41.202・198.199.122.22・/tmp/.tm を侵害指標として挙げていることを確認しました（突き合わせは本記録）。出典1 はこの対応を明示していませんが、本件が2024年秋に広く観測された FortiJump 悪用の波の一部であることは、製品ベンダー側の資料から読み取れます（本記録の整理）。

「暗号文で保存されている」は「読めない」ではない——Unit 42 が自分で復元して確かめた原因・手口

持ち出された FortiGate の設定には、資格情報が可逆な暗号文として入っていました（出典1）。

我々は、持ち出された設定ファイルから管理者および SSL/VPN のパスワードを総当たりで復元することに成功し、資格情報が復元可能であることを確認した（原文英語。出典1）

これは調査側による実証です（本記録の整理）。「理論上は復元できる」ではなく「やってみたらできた」という記述であり、設定ファイルの持ち出しをそのまま資格情報の流出として扱わなければならない根拠になります（本記録の評価）。

攻撃者も同じことをしています（出典1）。復元した正規の資格情報で、既知の外部踏み台（23.240.77[.]233・47.18.167[.]159）から境界ファイアウォールへ SSL-VPN の接続を張り、内部のネットワーク管理セグメントへ認証済みで到達しました（出典1）。

本記録が実務上の含みと見るのは次の点です（本記録の評価）。①設定のバックアップは資格情報のバックアップである。 設定ファイルを運用上どこに置いているか（共有フォルダ・チケット添付・構成管理リポジトリ）をそのまま資格情報の所在として扱う必要があります。 ②「機器が侵害された」と「その機器の設定が流出した」は対応の範囲が違う。 後者では、機器が無事であっても資格情報と証明書の交換が要ります（本記録の評価）。

ディスクに残らず、待ち受けず、自分から通信もしない——PEERSTITCH の作り原因・手口

権限昇格は FortiOS の auto-script のパストラバーサルCVE-2025-61624 で行われました（出典1・3）。

FortiOS の管理者（super_admin を含む）は制限された管理コマンドラインのなかで動作し、シェルも、機器のファイルシステムや稼働プロセスへの直接の支配も持ちません（出典1）。一方、FortiOS を構成するデーモンはその下で root として動きます（出典1）。auto-script のオブジェクト名が無害化されていないため、名前にトラバーサル列を含めると、スクリプト本体を任意のファイルシステム上の位置へ置けます（出典1）。攻撃者は ../../../../setup を作り、PEERSTITCH の初段ローダを設置しました（出典1）。

Fortinet 側の記述は、より一般的な言い方です（出典3）。「FortiOS・FortiPAM・FortiProxy・FortiSwitchManager のコマンドラインインタプリタにおけるパストラバーサル（CWE-22）で、権限を持つ攻撃者が任意のファイルの書き込みまたは削除を達成しうる」（原文英語。出典3）。CVSSv3 は 6.0（Medium）、発見の経緯は「内部」、「Known Exploited: Yes」です（出典3）。Fortinet の勧告は auto-script という機構名には触れていません（出典3。本記録の確認）〈齟齬5〉。

PEERSTITCH 本体の性質は、検知の前提を崩しに来ています（出典1）。

  • 64ビット Linux ARM64 の実行可能ファイル。C で書かれ、glibc を静的リンク（出典1）
  • 一発限りのプロセスメモリ書き換え注入器——対象は/bin/miglogd（システムと通信のログを集めるデーモン）と/bin/iked（IKE/IPsec VPN の暗号ネゴシエーションを担うデーモン）（出典1）
  • 永続的なバイナリをディスクに残さない。待ち受けポートを開かない。自分から外向きの接続を開始しない（出典1）
  • 代わりに、感染ホスト上の正規プロセスが生成する通信のなかで通信する（出典1）

注入の手順は次のとおりです（出典1）。/proc/ を走査して /bin/miglogd と /bin/iked の PID を特定し、/proc/<pid>/maps でメモリ配置を把握し、ptrace(PTRACE_SEIZE) で両プロセスに接続して PTRACE_INTERRUPT で停止させ、PTRACE_GETREGSET で ARM64 の汎用レジスタ（X0〜X30）・SP・PC を保存します（出典1）。続いて ARM64 のブートストラップを動的に生成し、mmap（X8 = 0xDE）で 0x4000（16,384バイト）のPROT_READ | PROT_WRITE | PROT_EXEC（RWX）領域をMAP_PRIVATE | MAP_ANONYMOUS として確保し、1,344バイトの注入ペイロードを /proc/<pid>/mem 経由で書き込みます（出典1）。

通信の仕組みが本件の特徴です（出典1）。両デーモンの内部に入ったフックは、プロセスを通過している通信を流れを変えずに観察し、strstr() で2つの印を探します（出典1）。TCP ポートの印 8550（通信データのなかに埋め込まれた文字列であり、待ち受けポートではない）と、IP の印 169.254.0.1（照合のために使われるリンクローカルの識別子）です（出典1）。印が見つかると、紐づくセッショントークンまたは識別子（最大31バイト）を抽出してオフセット +0x0F0 の16スロットの環状バッファへ書き込み、オフセット +0x400 の転送表（相手側デーモンの PID とバッファの基底アドレスが入っている）を辿って、open()・lseek()・write() で/proc/<相手の pid>/mem へ直接書き込みます（出典1）。/bin/iked が以後の VPN セッションを処理するとき、フックは自分の注入バッファを調べ、対応する印があれば代替の戻り経路（ADRP）を取り、FortiOS の既定の安全性検証を迂回します（出典1）。

加えて、改竄検知と既定処理の抑止のために、3箇所（base + 0x106F7B8・base + 0x1072E20・base + 0x109A570）へ0xAA0003E0（MOV X0, X0）の NOP パッチを当て、base + 0x135102C へ20バイトのトランポリンを書いて実行を RWX のフックバッファへ逸らしています（出典1）。

C2 は証明書の自動更新に化けていた——Apache mod_md の ACME 機構の転用原因・手口

PEERSTITCH とは別に、攻撃者は FortiGate に載っているApache の mod_md（Managing Domains）モジュールを武器化しました（出典1）。このモジュールは ACME（証明書の自動管理）プロトコルを使います（出典1）。

段取りは次のとおりです（出典1）。

  1. auto-script で ../../tmp/apache2/conf/md-acme.conf を作成する。
  2. account.json（状態ファイル）が攻撃者の ACME サーバへの初回登録を示し、ACME のディレクトリ要求を外部基盤へ明示的に向ける。
  3. order.json が保留中の証明書注文を示し、認可と確定の URL を攻撃者のサーバへ直接対応付ける。
  4. MDChallengeDns01 を /bin/node に対応付ける。Apache が証明書の検証チャレンジを開始すると、遠隔の ACME サーバから取得した引数で Node.js が実行される。job.json のデバッグログから、攻撃者がチャレンジ要求のドメイン名欄へシェルコマンドを注入し、SSH による逆シェルを張っていたことが分かる。
  5. MDRenewMode を always にすることで、Apache のデーモンが悪性の更新チャレンジを継続的に発火させ、注入されたペイロードの再実行が続く。

本記録が注目するのは、この C2 が「正規の自動化の継続実行」に見える点です（本記録の評価）。証明書の自動更新は止まっていないことが望ましい処理であり、繰り返し動いていること自体は異常の根拠になりません（本記録の評価）。攻撃者は md-acme.conf を、このファイルによく現れる文字列（#0 certs managed by ACME）で上書きして痕跡を隠してもいます（出典1）。

管理装置になりすませる——持ち出した信頼情報は「交換するまで有効」波及・関係先

FortiGate と FortiManager の通信（FGFM）は TCP 541番で行われ、機器のシリアル番号に対して要求・検証される暗号学的信頼情報に依存します（出典1）。初期侵入で持ち出されたアーカイブには、この信頼情報と、全下流機器のシリアル番号・管理関係が含まれていました（出典1）。

観測されたのは次の事実です（出典1）。外部基盤からの TCP 541番の FGFM 通信に続いて、FortiGateCloud という名の管理者アカウントが、複数の管理下ファイアウォールから完全な稼働設定をダウンロードしました（出典1）。被害組織は FortiManager Cloud のテナントを運用しておらず、当該機器にそのようなアカウントは作られていませんでした（出典1）。

Unit 42 の評価は、確度を明示したうえで経路を特定していません（出典1）。

我々は、攻撃者が FGFM 越しに管理プラットフォームになりすましてこれらのコマンドを発行したと中程度の確度で評価する。彼らには2つの経路が利用可能であり、証拠はそれらを区別しない（原文英語。出典1）

2つの経路とは、CVE-2024-26009（FortiManager のシリアル番号を使ったFGFM 認証の迂回）の悪用と、持ち出した信頼情報を直接再利用して正規の FortiManager として認証することです（出典1）。管理の身元を主張するには正規の FortiManager のセッションを終了させる必要があり、CVE-2024-26008 を使って強制した可能性にも触れていますが、「利用可能なログは引き金となった通信を捉えていないため、機構は確認できなかった」としています（原文英語。出典1）。

また Unit 42 は、FortiGateCloud アカウントの悪用に関わる他の脆弱性（CVE-2025-59718・CVE-2025-59719、および FG-IR-26-060 のSSO 関連の問題）を、本件の範囲から明示的に除外しています（出典1）——いずれも機器が FortiGate Cloud／FortiCloud SSO に登録されていることを要するが、当該ファイアウォールはそのような登録を持っていなかったためです（出典1）。観測された活動はアカウント名だけを再利用しており、それらの問題に伴う悪用の痕跡は無かったとしています（出典1）。

結論部の指摘が、本件の最も重い含みです（出典1）。

管理プラットフォームの侵害は、それを所有する組織の境界では封じ込められない。その侵害は、プラットフォームにパッチが当たった時点でも終わらない。プラットフォームと各管理下機器の関係を支配する暗号学的信頼情報は攻撃者とともに去り、交換されるまで有効なままである（原文英語。出典1）

検知の話を「仕組みの話」として読む——痕跡を消す側も徹底している評価・解釈

攻撃者は痕跡の除去を広範に行っています（出典1）。

  • サービスの停止——悪性の auto-script の実行前にkillall -9 miglogd と killall -9 syslogd を実行し、ローカルと遠隔の syslog 生成を止める（出典1）
  • クラッシュログの消去——初回のメモリ注入で生じたセグメンテーション違反のログをdiagnose debug crashlog clear で消す（出典1）
  • 設定の巻き戻し——不正な管理者アカウント・不正な VPN グループ・auto-script オブジェクト（../../../../setup）を実行の直後に自動削除する（出典1）
  • おとりの作成——/tmp/apache2/conf/md-acme.conf をこのファイルに通常見られる文字列で上書きして逆シェルの設定ファイルを隠す（出典1）
  • 自己削除——lldprx は自分のバイナリをディスクから外し、/proc/ を走査して staging の setup プロセスを終了させてから終了する（出典1）
  • ログ送信の妨害——悪性活動の期間中、トンネル管理インタフェースでログ送信の断続的な欠落が見られた。Unit 42 は中程度の確度で、中央の管理コンソールへの実時間の送信を抑えるために意図的に劣化を誘発したと評価している（出典1）

Unit 42 は、PEERSTITCH が完全にメモリ内で動き、永続的なファイルも待ち受けポートも作らないため、検知には専門的な探索が要るとして、5つの観測面を示しています（出典1）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
機能した**本記録の評価**——**この但し書きが無ければ、 「500台超」という数字は被害台数として流通していた。** **露出（exposed）と実害（accessed）を分けて書いたことで、 読者は自組織に当てはめるときの判定条件を誤らずに済む**（本記録の評価）。 **本記録も figures の measure を exposed としている。**
機能した**本記録の評価**——**アカウント名の一致だけで 既知の SSO 脆弱性に結び付けるのは容易だが、 本報告はその誘惑を避けて除外条件を示している。** **「観測された活動はアカウント名だけを再利用しており、 それらの問題に伴う悪用の痕跡は無かった」という書き方は、 読者が自組織のログを見るときの判定基準になる**（出典1。評価は本記録）。
機能した**本記録の評価**——**この但し書きは、 本記録が出典1 と出典2 を突き合わせるときにも効いた。** **シリアル番号と IP の一致は「同じ波の活動である」ことの根拠になるが、 それ自体が個々の組織の侵害を意味しない**（本記録の整理）。 **指標を出す側が、指標の限界まで書いている例として記録する。**
CISO・経営層への示唆
  • **集中管理装置は「管理の便利な道具」ではなく、ネットワーク上で最も価値の高い標的である**
    **Unit 42 は結論で「他社のために基盤を管理する組織にとって、 管理プラットフォームはネットワーク上で最も価値の高い標的である」と 述べている**（原文英語。出典1）。 **1台の侵害が500台超の鍵と設定の流出になった**（出典1）。
    取るべき行動 **①管理装置（FortiManager・各種 EMS・構成管理サーバ）を列挙し、 それぞれが「何台分の鍵を持っているか」を数える。 ②その管理インタフェースがインターネットから到達可能かを確認し、 到達可能なものを閉じる計画を立てる。 ③管理装置の侵害を前提にした演習（鍵の一括交換）を手順として持つ。**
  • **「パッチを当てたら終わり」ではない——持ち出された鍵は交換するまで有効である**
    **「その侵害は、プラットフォームにパッチが当たった時点でも終わらない。 プラットフォームと各管理下機器の関係を支配する暗号学的信頼情報は 攻撃者とともに去り、交換されるまで有効なままである」** （原文英語。出典1）。 **Fortinet の勧告も資格情報の緊急の交換を勧めている**（出典2）。
    取るべき行動 **①管理装置の侵害が判明した場合に交換すべきものを一覧にする （管理者パスワード・SSL-VPN の資格情報・機器証明書・秘密鍵・ RADIUS／LDAP の共有秘密）。 ②交換に要する時間を台数から見積もり、 「交換が終わるまでは侵害が継続している」と扱う方針を決める。 ③顧客の機器を預かっている場合、 顧客側に交換を依頼する連絡経路と文面を先に用意する。**
  • **預かっている側の侵害は、預けている側の境界では止まらない**
    **「管理プラットフォームの侵害は、 それを所有する組織の境界では封じ込められない」**（原文英語。出典1）。 **本件では顧客ネットワークを守るファイアウォールの設定・資格情報・ 信頼情報が持ち出された**（出典1）。
    取るべき行動 **①自社のファイアウォール・VPN の管理を委託している場合、 委託先の管理装置が侵害されたときの通知条件を契約で確認する。 ②委託先が持っている自社機器の資格情報・証明書を一覧にする。 ③委託先起因での一括交換を自社側の手順として持つ （委託先の作業完了を待つ構成になっていないか確認する）。**
  • **設定ファイルのバックアップは、資格情報のバックアップである**
    **持ち出された設定内の資格情報は可逆な暗号文として保存されており、 Unit 42 は総当たりで復元できることを確認した**（出典1）。 **「暗号化されている」は「読めない」ではない**（本記録の整理）。
    取るべき行動 **①機器設定のバックアップの保管場所を洗い出す （共有フォルダ・チケットの添付・構成管理リポジトリ・担当者の端末）。 ②それらを資格情報と同じアクセス制御・保持期間の基準に合わせる。 ③過去に外部へ渡した設定ファイル（ベンダーへの障害解析依頼等）が あるかを確認し、該当する資格情報を交換の候補に入れる。**
  • **ネットワーク機器を「ログを送ってくる箱」として扱っている限り、本件は検知できない**
    **攻撃者は `killall -9 miglogd`・`killall -9 syslogd` で ログ生成そのものを止め、クラッシュログを消し、 設定オブジェクトを巻き戻している**（出典1）。 **Unit 42 が示した検知の観測面は、 機器のメモリとシステムコールに到達できることを前提としている** （出典1。整理は本記録）。
    取るべき行動 **①ファイアウォール・VPN 装置のログが「届かなくなったこと」を 検知する仕組みがあるかを確認する。 ②無い場合、死活ではなくログ到着の欠落を監視項目に加える。 ③機器の設定改訂履歴を機器の外に保持する （攻撃者が機器内のオブジェクトを削除しても残るようにする）。**
セキュリティ技術者への示唆
  • **`system.auto-script` のオブジェクト名に `../../` が無いかを設定改訂から探す**
    **Unit 42 は検知の観測面として、 FortiOS の設定改訂を調べ `../../` を含む `system.auto-script` オブジェクトを探すことを挙げている**（出典1）。 **攻撃者は `../../../../setup` と `../../tmp/apache2/conf/md-acme.conf` を作っている**（出典1）。
    取るべき行動 **①手元の FortiOS の設定改訂履歴を取り出し、 `auto-script` のオブジェクト名を全件列挙する。 ②`../` を含むものがあれば、作成時刻と作成アカウントを確認する。 ③履歴が機器内にしか無い場合、外部への保存を設定する （攻撃者は実行直後に削除している）。**
  • **`/bin/miglogd` と `/bin/iked` のメモリに 16,384バイトの RWX 無名領域が無いかを見る**
    **PEERSTITCH は `mmap` で 0x4000（16,384バイト）の `PROT_READ | PROT_WRITE | PROT_EXEC` 領域を `MAP_PRIVATE | MAP_ANONYMOUS` として確保する**（出典1）。 **Unit 42 は `/proc/<pid>/maps` で `rwxp` 権限の 16,384バイトの無名領域を探すよう示している**（出典1）。
    取るべき行動 **①該当機器でメモリマップを取得できる経路があるかを先に確認する （無ければ、それ自体が課題である）。 ②`base+0x106F7B8`・`base+0x1072E20`・`base+0x109A570` の テキスト領域の完全性（`0xAA0003E0` が無いこと）を検証する。 ③`diagnose debug crashlog read` で `miglogd`・`iked`・`syslogd` に 関わる Signal 11 を照会する（攻撃者が消していなければ残る）。**
  • **Apache `mod_md` の設定が ACME のチャレンジから `/bin/node` を起動していないか確認する**
    **攻撃者は `MDChallengeDns01` を `/bin/node` に対応付け、 チャレンジ要求のドメイン名欄へシェルコマンドを注入して SSH の逆シェルを張っている**（出典1）。 **`MDRenewMode always` により再実行が続く**（出典1）。 **この項目は Unit 42 の観測面一覧には含まれていない** （出典1。本記録の確認・追加）。
    取るべき行動 **①`/tmp/apache2/conf/md-acme.conf` の存在と内容を確認する （攻撃者はおとりの文字列で上書きするため、 ファイルの有無だけでは判断しない）。 ②`account.json`・`order.json` の ACME サーバの宛先が 正規の認証局を指しているかを確認する。 ③`MDChallengeDns01` に外部コマンドが対応付けられていないか確認する。**
  • **FGFM（TCP 541番）の通信元と、管理アカウント名の棚卸しを行う**
    **外部基盤からの FGFM 通信に続いて、 存在しないはずの `FortiGateCloud` アカウントが 設定をダウンロードしている**（出典1）。 **被害組織は FortiManager Cloud のテナントを運用していなかった**（出典1）。
    取るべき行動 **①各 FortiGate で FGFM の通信元として正当な IP を列挙し、 それ以外からの TCP 541番を遮断または警報の対象にする。 ②機器上の管理アカウントを全件列挙し、 運用台帳に無いものを特定する。 ③FortiGate Cloud／FortiCloud SSO への登録状況を確認する （登録が無いのに関連アカウントがあるのは異常である）。**
  • **持ち出された設定からの資格情報復元を「できる」前提で棚卸しする**
    **Unit 42 は総当たりで管理者と SSL/VPN のパスワードを 復元できることを確認している**（出典1）。 **可逆な暗号文であるため、設定が外に出た時点で資格情報は失われている** （出典1。整理は本記録）。
    取るべき行動 **①設定ファイルに平文または可逆な暗号文で入っている 資格情報・共有秘密（RADIUS・LDAP・IPsec の事前共有鍵）を列挙する。 ②外部参照で済むもの（証明書認証・外部 IdP）へ寄せられるかを検討する。 ③寄せられないものは「設定が出れば失われる資格情報」として 交換手順に紐づける。**
