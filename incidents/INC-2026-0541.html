INC-2026-0541Drupal Field UI に未認証 RCE

Drupal セキュリティチームは2026年10月14日、コアの Field UI モジュールに 遠隔コード実行の脆弱性 CVE-2026-108097 があるとして勧告 SA-CORE-2026-014 を公開し、 Drupal 11.4.10・11.3.19・10.6.19 をリリースした——独自の25点満点で19点、 5段階中2番目に高い「Critical」。コア単体では直接悪用できないとされる一方、 拡張モジュール（contributed modules）を介した深刻な悪用経路が複数存在し、 そのうち少なくとも1つは認証を必要としない。独自コードによって 脆弱な機能が露出することもあるとしており、勧告は該当モジュールを名指ししていない。 更新までの緩和策はコアの Field UI モジュールのアンインストールである。 同日には Link モジュールと Navigation モジュールの XSS 2件 （CVE-2026-108515・CVE-2026-108514）も公表され、 CERT-FR も10月15日に注意喚起を出した

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月14日（Drupal の勧告公開と修正版リリース） 最終更新: 2026年10月16日（本記録の確認時点）

コアの欠陥ですが、悪用できるかどうかはコア以外で決まります。

2026年10月14日、Drupal セキュリティチームは勧告 SA-CORE-2026-014 を公開し、コアの Field UI モジュール（field_ui）に遠隔コード実行の脆弱性CVE-2026-108097 があることを明らかにしました（出典1）。同時に Drupal 11.4.10・11.3.19・10.6.19 がリリースされています（出典1）。独自の危険度評価は25点満点で19点、5段階中2番目に高い「Critical」です（出典1・4）。

本記録が要点と見たのは、次の3点です。

  • 「コア単体では悪用できない」は安心の材料にならない。 勧告は、コア単体では脆弱性に直接到達できないとしつつ、拡張モジュールを使った深刻な悪用経路が複数存在すると述べています（出典1）。さらに、独自コードによって脆弱な機能が露出することもあるとしています（出典1）。そして少なくとも1つの既知の経路は認証を必要としません（出典1）。つまり「自分のサイトが該当するか」は、コアの版だけでは判定できません**（本記録の整理）。
  • 該当するモジュールが名指しされていない。 勧告は「拡張モジュール」「独自コード」と述べるだけで、具体のモジュール名を1つも挙げていません（出典1。本記録の確認）。更新を急ぐ以外に、利用者が取れる判定の手段がありません（本記録の評価）。
  • 緩和策は「機能を外す」ことである。 更新できるまでの緩和策として、コアの Field UI モジュールのアンインストールが示されています（出典1・4）。Drupal Steward の利用者は既知の攻撃経路の一部から保護されるが、すべてではないとも述べられています（出典1）。

本記録は2026年10月16日に、Drupal の勧告 SA-CORE-2026-014（出典1）および同日公表の SA-CORE-2026-015（出典2）・SA-CORE-2026-016（出典3）を直接取得して裏を取りました。 実環境での悪用を示す記載は、いずれの資料にもありません〈未確定2〉。

「コア単体では悪用できない」と「認証なしで悪用できる経路がある」が同じ勧告に書いてある原因・手口

勧告の核は、成立条件の置き方にあります（出典1）。

勧告は、コア単体では脆弱性に直接到達できないとしています（出典1）。その一方で、次の3つを続けて述べています（出典1）。

  • 拡張モジュール（contributed modules）を使った、深刻な悪用経路が複数存在する
  • 独自コードによっても、脆弱な機能が露出することがある
  • 少なくとも1つの既知の悪用経路は、認証を必要としない

この3つが同時に成り立つと、利用者側の判定はほぼ不可能になります（本記録の評価）。「コアの版が該当する」ことは確認できます。 しかし「悪用可能か」は、導入している拡張モジュールと独自コードの構成で決まり、勧告はその判定に必要なモジュール名を挙げていません（出典1。本記録の確認）。

危険度の内訳を読むと、評価側もこの構造を反映しています（出典1）。

  • AC:Basic——攻撃の複雑さは「基本」
  • A:None——必要な権限は「なし」
  • CI:All / II:All——機密性・完全性への影響はいずれも「すべて」
  • E:Theoretical——悪用の実績は「理論上」
  • TD:Default——対象は既定の設定で該当する

A:None（権限不要）と TD:Default（既定設定で該当）が並んでいる一方、E:Theoretical に留まっている（出典1）。本記録はこれを「経路は存在するが、実際の悪用はまだ観測されていない段階である」と読みます（本記録の整理）。ただし E:Theoretical は公開時点の評価であり、その後を保証するものではありません（本記録の注意）。

なお、Security NEXT の報道は「独自のリスク評価で『25点中19点』、重要度を5段階中、2番目に高い『クリティカル（Critical）』とした」と伝えています（出典4）。本記録が Drupal の勧告を確認した結果、点数と格付けはこの記述と一致します（出典1。突き合わせは本記録）。Drupal の5段階は上から Highly critical / Critical / Moderately critical / Less critical / Not critical であり、「2番目に高い」という表現も正確です（本記録の整理）。

緩和策は「機能を外す」——Field UI をアンインストールする対策・注意喚起

勧告が示す対応は2つです（出典1）。

第一に、修正版への更新です（出典1）。Drupal 11.4.10・11.3.19・10.6.19 がリリースされています（出典1）。

第二に、更新までの緩和策として、コアの Field UI モジュールのアンインストールが示されています（出典1・4）。勧告は「これによりサイトは更新できるようになるまで保護される」と述べています（原文英語。出典1）。

Drupal Steward（Drupal 側が提供する WAF 類似の保護サービス）については、勧告が明確に限界を書いています（出典1）。「Drupal Steward の利用者は、既知の攻撃経路の一部に対して保護されるが、すべてではない」（原文英語。出典1）。

本記録が実務上の含みと見るのは次の点です（本記録の評価）。

①Field UI のアンインストールは、運用に影響する。 Field UI はフィールドの定義・表示設定を管理画面から操作する機能です。 外すとコンテンツ構造の変更ができなくなるため、「更新までの一時的な措置」としてしか成立しません（本記録の評価）。

②「WAF で止める」という発想が、ここでは明示的に否定されている。 Drupal 側が自ら提供している保護サービスについて「一部にのみ有効」と書いているため、一般的な WAF に同等以上を期待する根拠はありません（本記録の整理）。

③判定できないなら、更新を前提にするしかない。 該当モジュールが名指しされていないため、「自分のサイトは経路を持たないから後回しでよい」という判断は根拠を持ちません（本記録の評価）。

  • **開発版（alpha・beta）を本番に置いている場合、勧告が対策を示さないことがある**
    **影響範囲に 12.0.0-alpha1 以上 12.0.0-beta2 未満が含まれているのに、 勧告の対策欄には 12.x の修正版が挙げられていない**（出典1）〈齟齬2〉。 **同日の XSS 2件も同じ書き方である**（出典2・3。本記録の確認）。
    取るべき行動 **①本番または公開環境で開発版の Drupal を使っていないか確認する。 ②使っている場合、どの版へ上げるべきかを開発元へ照会する経路を決める。 ③開発版の利用を続ける判断をするなら、 「勧告が対策を示さないことがある」ことを前提に 追加の確認手順を定める。**
セキュリティ技術者への示唆
  • **更新は3件まとめて1回で済む——11.4.10 / 11.3.19 / 10.6.19**
    **2026年10月14日公表のコアの勧告3件 （SA-CORE-2026-014 の RCE、015・016 の XSS）は、 いずれも同じ修正版で直る**（出典1・2・3）。
    取るべき行動 **①自サイトの系列に応じて 11.4.10・11.3.19・10.6.19 のいずれかへ上げる。 ②更新後、Field UI・Link・Navigation の各機能の動作を確認する。 ③`administer menu` 権限を持つ役割の一覧を確認する （SA-CORE-2026-016 の悪用の前提条件である）。**
  • **すぐに更新できないなら、Field UI をアンインストールする——ただし影響を把握してから**
    **勧告は、コアの Field UI モジュールのアンインストールにより 「サイトは更新できるようになるまで保護される」としている** （原文英語。出典1・4）。 **Field UI はフィールドの定義・表示設定を管理画面から操作する機能である** （本記録の整理）。
    取るべき行動 **①Field UI を外した状態でサイトの表示と既存の投稿機能が 動くことを検証環境で確認する。 ②コンテンツ構造の変更予定（新しいフィールドの追加等）が 期間内に無いことを確認する。 ③外した場合は、更新後に戻す手順と期限を記録する。**
  • **IoC は無い——「痕跡を探す」ではなく「版を数える」作業である**
    **実環境での悪用を示す記載が無く、 IoC も公表されていない**（出典1〜3）〈未確定2〉。 **欠陥の技術的な内容も非公開であるため、 痕跡の形が分からない**（本記録の整理）。
    取るべき行動 **①稼働している全 Drupal サイトの版を機械的に列挙する （手作業の一覧に依拠しない）。 ②8.9.0 以上の全系列が対象であることを前提に、 古い系列を使っているサイトを特に洗い出す。 ③開発環境・検証環境・放置されている旧サイトも対象に含める。**
  • **危険度の `E:Theoretical` を「悪用されていない」と読み替えない**
    **`E:Theoretical`（悪用の実績＝理論上）は 勧告公開時点の評価である**（出典1。整理は本記録）。 **同じ評価のなかで `A:None`（権限不要）・`TD:Default`（既定設定で該当）と されている**（出典1）。
    取るべき行動 **①`E` の値を更新の優先度から外し、 `A`（必要な権限）と `TD`（対象の範囲）で判断する。 ②勧告が改訂されたときに評価が変わることを前提に、 公開後も一定期間は勧告ページを再確認する。**
