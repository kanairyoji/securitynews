INC-2026-0542車検証閲覧アプリから API キー漏えい

JPCERT/CC は2026年10月15日、国土交通省が提供する「車検証閲覧アプリ」に 送信データへの機微な情報の挿入の脆弱性（CWE-201・CVE-2026-75559）があるとして JVN#94004488 を公開した——車検証を扱う事業者向けの API 連携機能の仕様に問題があり、 API 連携用のアクセス ID およびアクセスキーが漏えいする可能性があった。 対象は Android 版・iOS 版ともに ver.6.2.0 およびそれ以前。 危険度は IPA の評価で CVSS v4.0 基本値 6.9・CVSS v3.0 基本値 5.3 で、 いずれも機密性のみへの影響である。開発者は API 利用事業者に対して 新しいアクセス ID とアクセスキーを発行し、漏えいする可能性があるものを 無効化しており、JVN は「そのため、本脆弱性を悪用することはできません」としている。 報告は情報セキュリティ早期警戒パートナーシップに基づく井尻翔氏からのもの

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月15日（JVN#94004488 の公開。同日に関連文書を更新） 最終更新: 2026年10月16日（本記録の確認時点）

アプリが外へ送るデータのなかに、事業者向け API の鍵が入っていました。

2026年10月15日、JPCERT/CC は JVN#94004488 を公開し、国土交通省が提供する「車検証閲覧アプリ」に送信データへの機微な情報の挿入の脆弱性（CWE-201・CVE-2026-75559）があることを明らかにしました（出典1）。

本記録が要点と見たのは、次の3点です。

  • 漏えいしうるのは「車検証の情報」ではなく「事業者向け API の鍵」である。 JVN が挙げている想定影響は「API 連携用のアクセス ID およびアクセスキーが漏えいする可能性があります」で、車検証情報そのものの漏えいには触れていません（出典1・2）。車検証を扱う事業者向けに車検証情報を提供するための API 連携機能が実装されており、その仕様に問題があったとされています（出典1）。
  • 公表の時点で、鍵はすでに差し替えられている。 「開発者は API 利用事業者に対して新しいアクセス ID およびアクセスキーを発行するとともに、漏えいする可能性があるアクセス ID およびアクセスキーを無効化しています。そのため、本脆弱性を悪用することはできません」と明記されています（出典1）。利用者側の対応はアプリの最新版への更新です（出典1）。
  • 一方、開発者（国土交通省）自身の公表には到達できていない。 本記録は2026年10月16日に電子車検証特設サイトのお知らせ一覧を確認しましたが、本脆弱性・アクセス ID／キーの再発行・無効化に言及する告知は見当たりませんでした〈齟齬1〉。JVN の「ベンダ情報」欄に挙げられているリンク先も、Google Play ストアと App Store のアプリ配布ページだけです（出典1）。

本記録は2026年10月16日に、JVN#94004488（出典1）とJVN iPedia の JVNDB-2026-000151（出典2）を直接取得して裏を取りました。 危険度は IPA の評価で CVSS v4.0 基本値 6.9・CVSS v3.0 基本値 5.3 であり、いずれも機密性のみへの影響です（出典1・2）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**「車検証閲覧アプリ」の API 連携機能の仕様に、 送信データへ機微な情報を含めてしまう問題（CWE-201）があった**（出典1）。 **これにより、API 連携用のアクセス ID およびアクセスキーが 漏えいする可能性があった**（出典1・2）。 **技術的な内容（どの通信にどのような形で含まれていたか）は 公表されていない**〈未確定2〉。 **公表の時点で開発者は鍵の無効化と再発行を完了しており、 JVN は「本脆弱性を悪用することはできません」としている**（出典1）。

  1. 1. 認証情報アクセス確認済
    **アプリが送信するデータのなかに、 API 連携用のアクセス ID およびアクセスキーが含まれていた** （CWE-201。出典1・2）。 **これにより第三者がこれらを取得しうる状態だった**（出典1）。 **具体の経路・観測条件は公表されていない**〈未確定2〉。
    根拠: 「API 連携の仕様において、次の脆弱性が存在します—— 送信データへの機微な情報の挿入（CWE-201）」および 「API 連携用のアクセス ID およびアクセスキーが漏えいする 可能性があります」（出典1）
  2. 2. 影響（暗号化・破壊・改ざん）推定
    **漏えいした鍵で車検証閲覧 API を呼べる状態になりうる** （本記録の評価）。 **ただし JVN はこの段階について何も述べていない** （出典1・2。本記録の確認）。 **実際の漏えい・不正利用を示す記載も無い**〈未確定6〉。
    根拠: JVN の想定影響は「アクセス ID およびアクセスキーが 漏えいする可能性があります」までであり、 その先の影響には触れていない（出典1・2。本記録の確認）

漏えいしうるのは車検証の情報ではなく、事業者向け API の鍵である被害規模・影響範囲

JVN が示している想定影響は1行です（出典1・2）。

API 連携用のアクセス ID およびアクセスキーが漏えいする可能性があります（出典1）

車検証情報そのものの漏えいには触れていません（出典1・2。本記録の確認）。

構図を整理すると次のようになります（出典1。整理は本記録）。「車検証閲覧アプリ」には、車検証を扱う事業者向けに車検証情報を提供するための API 連携機能が実装されています（出典1）。この API を使う事業者には、国土交通省からアクセス ID とアクセスキーが発行されます（出典1）。脆弱性があったのは、この API 連携の「仕様」です（出典1）。分類は CWE-201——送信データへの機微な情報の挿入です（出典1・2）。

本記録が注意を促したいのは、CVSS の点数の読み方です（本記録の評価）。

IPA による評点は CVSS v4.0 で 6.9、CVSS v3.0 で 5.3 であり、いずれも「Medium」です（出典1・2）。内訳を見ると、AV:N（ネットワークから）・AC:L（容易）・PR:N（権限不要）・UI:N（利用者の関与不要）である一方、影響は機密性のみ、しかも「低」で、完全性・可用性および後続システムへの影響はいずれも「なし」です（出典1・2）。

点数は「漏れる情報の量が限定的である」ことで下がっています（本記録の整理）。しかし漏れる対象は、API への認証そのものを成立させる鍵です（出典1）。鍵が第三者の手に渡れば、その鍵で API を呼べる範囲の車検証情報に到達しうることになります（本記録の評価。出典1・2 はこの点に触れていない）。

したがって本記録は、評点を「対応の優先度を下げる根拠」として使わないことを勧めます（本記録の評価）。実際、開発者側は鍵の無効化と再発行という、評点の水準に比べれば重い対応を取っています（出典1。読み方は本記録）。

公表の時点で鍵は差し替えられていた——「悪用できません」と明記されている組織の対応

JVN の対策欄には、利用者向けと開発者側の対応が並んでいます（出典1）。

利用者向け——「開発者が提供する情報をもとに、アプリを最新版へアップデートしてください」（出典1）。

開発者側——次のように記述されています（出典1）。

なお、開発者は API 利用事業者に対して新しいアクセス ID およびアクセスキーを発行するとともに、漏えいする可能性があるアクセス ID およびアクセスキーを無効化しています。そのため、本脆弱性を悪用することはできません（出典1）

本記録はこれを、JVN の記述としては踏み込んだ書き方だと見ます（本記録の評価）。「対策を適用してください」で終わるのではなく、「無効化が済んでいるため悪用できない」という状態の宣言まで含まれています（出典1。整理は本記録）。

ただし、この宣言には書かれていないことがあります（本記録の整理）。

  • 無効化と再発行の実施日〈未確定4〉——公表より前であることしか分かりません。
  • 対象となった API 利用事業者の件数〈未確定1〉——「API 利用事業者に対して」という書き方から全事業者が対象と読めますが、明示はされていません。
  • 実際に漏えいが起きたか〈未確定6〉——「漏えいする可能性があります」という想定影響の記述に留まります。
  • 旧い鍵が無効化された時点で、事業者側の連携が止まったのではないか（本記録の疑問）——新しい鍵への切り替えが必要だったはずですが、その連絡と移行の経緯は公表されていません〈未確定4〉。

なお、JVN iPedia（出典2）の記述は JVN（出典1）と一致しており、本記録が突き合わせた範囲で齟齬はありませんでした（本記録の確認）。

    取るべき行動 **①自社側で残っている記録（API 呼び出しのログ・アクセス元）を 保持期間内に確保する。 ②提供元へ、実際の漏えいの有無と調査範囲を照会する経路を決める。 ③照会して回答が得られない場合の扱い （「不明」として記録を残す）を方針にする。**
セキュリティ技術者への示唆
  • **車検証閲覧アプリを業務で使っているなら、版を数えて更新する**
    **影響を受けるのは Android 版・iOS 版ともに ver.6.2.0 およびそれ以前である**（出典1・2）。 **対策はアプリの最新版へのアップデートである**（出典1）。
    取るべき行動 **①業務端末に導入されている車検証閲覧アプリの版を列挙する （個人端末での業務利用がある場合はそれも含める）。 ②ver.6.2.0 以前のものを更新する。 ③最新版の版番号が JVN と提供元のお知らせ一覧のいずれにも 明記されていないため、ストアの表示で確認する**〈齟齬2〉。
  • **アプリが外へ送るデータに認証情報が混ざっていないかを、自社のアプリでも確認する**
    **本件の類型は CWE-201（送信データへの機微な情報の挿入）であり、 API 連携の「仕様」の問題とされている**（出典1）。 **実装の誤りではなく仕様の段階で混入していた形である** （出典1。整理は本記録）。
    取るべき行動 **①自社のモバイルアプリが送信する通信を実機で観察し、 API キー・アクセス ID・トークンが含まれていないかを確認する （ヘッダ・クエリ・本文・ログ送信・クラッシュレポートを含む）。 ②アプリに埋め込まれた共有鍵を使う設計になっていないかを確認する （端末ごと・利用者ごとに分離されているか）。 ③混入していた場合、鍵の無効化と再発行を前提に対応計画を立てる （アプリの更新だけでは過去に漏れた鍵は止まらない）。**
  • **鍵の無効化は「アプリ更新だけでは足りない」ことの裏返しとして読む**
    **開発者はアプリの修正に加えて、 漏えいする可能性があるアクセス ID・アクセスキーを無効化している**（出典1）。 **JVN が「悪用することはできません」と書けているのは、 この無効化によるものである**（出典1。整理は本記録）。
    取るべき行動 **①自社で同種の事象が起きた場合の対応手順に、 「鍵の無効化と再発行」を必ず含める。 ②無効化によって止まる連携先を事前に一覧にしておく。 ③無効化から再発行・切り替え完了までの業務影響を見積もる。**
  • **API 側の呼び出し元・呼び出し量を見る経路を用意する**
    **漏えいした鍵による API 呼び出しは、 正規の鍵による正規の呼び出しとして現れる**（本記録の評価。 出典1・2 はこの点に触れていない）。 **JVN は検知の手がかりを何も示していない**〈未確定2〉。
    取るべき行動 **①自社が提供する API について、 鍵別の呼び出し元 IP・呼び出し量を記録しているか確認する。 ②記録していない場合、記録の追加を課題として登録する。 ③異常な呼び出し元・急増を検知したときの一次対応者を決める。**
