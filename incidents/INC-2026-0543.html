INC-2026-0543ゲオアプリに2件の脆弱性

スマートフォンアプリ「ゲオアプリ」に2件の脆弱性——アプリ内ブラウザの誘導で セッションIDが、端末内の平文保存でパスワードが窃取されうる（JVN#40460777）

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月15日 最終更新: 2026年10月16日（本記録の確認時点）

アプリ内ブラウザに任意のサイトを開かせられる問題と、端末の中にパスワードを平文で置いていた問題が、同じ日に2件まとめて公表されました。

2026年10月15日、JPCERT/CC は JVN#40460777 を公開し、株式会社ゲオが提供するスマートフォンアプリ「ゲオアプリ」に2件の脆弱性があることを明らかにしました（出典1）。対象は Android 版・iOS 版のいずれも Ver 11.8.6 およびそれ以前で、修正版は Ver 11.8.8 です（出典1・2）。

本記録が要点と見たのは、次の3点です。

  • 2件は性質がまったく違う。狙われる位置も、必要な前提も別である。 CVE-2026-96614 は Custom URL Scheme の処理におけるアクセス制限不備（CWE-939）で、「当該アプリ内のブラウザで任意のWebサイトにアクセスさせられ、結果としてフィッシング被害を受けたり、当該サービスのセッションIDが窃取されたりする」とされています（出典1）。CVE-2026-105271 は重要情報の平文保存（CWE-312）で、「攻撃者によって当該アプリのユーザーのパスワードが窃取される」とされています（出典1）。
  • CVSS の値は近いのに、攻撃の条件は正反対である。 前者は AV:N（ネットワーク）・PR:N（権限不要）だが UI:A／UI:R（利用者の操作が要る）、後者は AV:P（物理）・PR:L（権限が要る）だが UI:N（利用者の操作は不要）です（出典1・2）。CVSS v4.0 基本値はどちらも 5.1 で並びますが、前者は「利用者を踏ませる」経路、後者は「端末を手にする」経路であり、対策の考え方も変わります（評点は出典1・2、読み方は本記録）。
  • 報告者は別人であり、2件は別々に届け出られた。 CVE-2026-96614 は三井物産セキュアディレクション株式会社の金子 俊介 氏、CVE-2026-105271 は佐藤 壮 氏が IPA に報告しています（出典1）。1つの調査で2件が同時に出たのではなく、別々の報告が同じアプリで同じ日に公表された形です（出典1。読み方は本記録）。

本記録は2026年10月16日に JVN#40460777（出典1）を直接取得して裏を取りました。 一方、開発者である株式会社ゲオ自身がこの2件に言及した公表には到達できていません〈齟齬1〉。JVN の「ベンダ情報」欄に挙げられているリンク先も、Google Play ストアと App Store のアプリ配布ページだけです（出典1）。

攻撃者によって当該アプリのユーザーのパスワードが窃取される（出典1）

本記録が注意を促したいのは、CVSS のベクタの違いです（本記録の評価）。

CVE-2026-96614 は AV:N（ネットワークから）・AC:L（容易）・PR:N（権限不要）ですが、UI:A（v4.0）／UI:R（v3.0）——つまり利用者の操作を必要とします（出典1）。影響は機密性・完全性がともに「低」で、可用性は「なし」です（出典1）。典型的には、悪意のあるリンクを踏ませてアプリ内ブラウザを任意の URL へ誘導する経路が想定されます（本記録の整理。出典1 は具体的な手順に触れていない）。

CVE-2026-105271 はこの正反対です（本記録の整理）。AV:P（物理）・PR:L（限定的な権限が要る）・UI:N（利用者の操作は不要）で、機密性への影響は「高」、完全性・可用性は「なし」です（出典1）。攻撃者が端末そのものに到達できる状況が前提になりますが、到達できたときに取れるものはパスワードそのものです（出典1。読み方は本記録）。

CVSS v4.0 の基本値はどちらも 5.1 で並びます（出典1）。しかし「利用者を踏ませる」経路と「端末を手にする」経路は、自組織での当てはまり方も、打つべき手も違います（本記録の評価）。点数が同じだから同じ扱いでよい、とは読まないことを勧めます（本記録の評価）。

CISO・経営層への示唆
  • 自社アプリの脆弱性は、JVN に出たときが利用者への説明の始まりである。 公表と同時に出す文面を用意しておく。
    本件では JVN が2026年10月15日に公表しているが、 本記録は開発者自身の告知に到達できていない〈齟齬1〉。 利用者は「更新すればよいのか、パスワードも変えるべきか」を 自分で判断するしかない状態である（本記録の評価）。
    取るべき行動 自社アプリに脆弱性が公表される場合に備え、 ①対象バージョン ②更新方法 ③利用者が取るべき追加の行動（パスワード変更の要否） を書いた告知のひな型を、広報・開発・CSIRT の合意のうえで用意しておく。 JVN 調整案件では公表日が事前に分かるため、当日公開に間に合わせられる。
  • CVSS の点数で対応の優先度を決めると、本件のような2件を取り違える。
    CVE-2026-96614 と CVE-2026-105271 は CVSS v4.0 基本値がどちらも 5.1 で並ぶが、 前者は `AV:N`・`UI:A`、後者は `AV:P`・`VC:H` である（出典1）。 自組織にとっての重さは、点数ではなく前提条件で決まる（本記録の評価）。
    取るべき行動 脆弱性の受け入れ基準に点数だけを置かず、 「攻撃元区分（AV）」と「利用者操作（UI）」を見て 自社の運用で成立する前提かを判定する手順を入れる。 業務端末の紛失・下取りが日常的にある組織では `AV:P` を軽く扱わない。
  • 端末が人手を渡る事業では、平文保存は「物理」で済む問題ではない。
    CVE-2026-105271 の攻撃元区分は物理（AV:P）だが（出典1）、 中古端末の買取・下取り・修理・譲渡が日常的に起きる環境では、 端末が第三者の手に渡る機会そのものが業務に内在している（本記録の評価）。
    取るべき行動 自組織が端末を預かる・引き取る業務を持つなら、 引き取り時のデータ消去手順に「自社アプリの保存データ」を明示的に含める。 委託先が消去を担う場合は、消去の範囲と証跡の提出を契約に書く。
  • 脆弱性の受付経路（早期警戒パートナーシップ）は、外部の目を安く借りる仕組みである。
    本件の2件は、社外の2名が別々に IPA へ報告したものである（出典1）。 自社のテストでは出なかった問題が、外部から2件同時に届いた形になる（本記録の整理）。
    取るべき行動 自社の脆弱性報告の受け口（連絡先・対応方針・調整の窓口）を公開し、 IPA／JPCERT/CC からの調整連絡を受けたときに誰が動くかを決めておく。 社内に受け口がないと、調整の連絡が開発現場に届くまで日数を失う。
セキュリティ技術者への示唆
  • Custom URL Scheme は「アプリが外から呼ばれる入口」である。入口として検証する。
    CVE-2026-96614 は Custom URL Scheme の処理におけるアクセス制限不備（CWE-939）で、 アプリ内ブラウザに任意の Web サイトを開かせられるとされている（出典1）。
    取るべき行動 自社アプリが受け付けるスキームとパラメータを棚卸しし、 URL を受け取ってアプリ内ブラウザで開く箇所には 許可するホストの明示的な白名簿を置く。 正規表現の部分一致や「自社ドメインを含むか」での判定は避ける。
  • アプリ内ブラウザは、セッションを持ったまま任意のサイトを表示する装置になりうる。
    JVN は「フィッシング被害」と「当該サービスのセッションIDが窃取される」を 並べて挙げている（出典1）。 アプリ内ブラウザが認証状態を共有していると、 表示先の選択がそのままセッションの露出になる（本記録の評価。 出典1 は共有の有無に触れていない）。
    取るべき行動 アプリ内ブラウザに渡す URL の決定ロジックと、 Cookie・トークンの共有範囲を1枚の図にして確認する。 外部サイトを開くときは OS の既定ブラウザへ渡し、 アプリのセッションを持ち込ませない構成を既定にする。
  • 端末内のパスワードは、保存しない・保存するなら OS の保護領域を使う。
    CVE-2026-105271 は重要情報の平文保存（CWE-312）で、 機密性への影響は「高」と評価されている（出典1）。
    取るべき行動 自社アプリの保存データを実機で洗い出す （SharedPreferences・NSUserDefaults・SQLite・ログ・キャッシュ）。 資格情報は Keychain／Keystore に置き、 「再ログインの手間を省く」ための平文保存をコードレビューの禁止事項にする。
  • 修正版を出すだけでは、すでに書かれた値は消えない。
    JVN は修正版 Ver 11.8.8 を示すが、 更新時に既存の保存値をどう扱うかには触れていない〈齟齬2〉（出典1。本記録の確認）。
    取るべき行動 平文保存を修正するときは、更新時に旧データを削除する処理 （マイグレーション）を同じリリースに入れる。 削除したことをテストで確認し、リリースノートに明記する。
