INC-2026-0544TLS 13 実装で名前制約が食い違う

13 の TLS ライブラリと BoringSSL で X.509 の名前制約の扱いが食い違う—— 中間CAを封じ込めるはずの仕組みが、検証側によって効かなくなる（JVNVU#95474776／JVNVU#95613365）

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年10月14日（CERT/CC の公開日） 最終更新: 2026年10月16日（本記録の確認時点）

中間CAが発行できる名前の範囲を縛る仕組みが、検証するライブラリによって効き方が違います。

2026年10月14日、CERT/CC は2つの脆弱性ノートを公開しました（出典3・4）。VU#948176「Multiple TLS Libraries can Bypass Delegation Enforcement」（複数の TLS ライブラリで委任の強制を回避できる／原文英語）は13 のライブラリ個別の記録を束ねたもので、VU#410595「Google BoringSSL Name Constraints Bypass in SAN Validation Logic」（BoringSSL の SAN 検証ロジックにおける名前制約の回避／原文英語）はBoringSSL に絞った5件の記録です（出典3・4）。翌2026年10月15日、JPCERT/CC がそれぞれ JVNVU#95474776・JVNVU#95613365 として国内向けに公表しました（出典1・2）。

本記録が要点と見たのは、次の3点です。

  • これは1つのバグではなく、「同じ証明書を実装ごとに違って読む」という状態である。 CERT/CC は X.509 の名前制約が「下位の CA を許された名前空間の内側に留めるためのもの」（原文英語）だとしたうえで、実装ごとに適用が一貫しておらず、あるライブラリが受け入れる名前を別のライブラリは拒否する、と述べています（出典3）。
  • CERT/CC 自身が「検証器の不一致だけでは悪用ではない」と書いている。 「これらの記録が問題になるのは、攻撃者が選んだ証明書フィールドに対して信頼された署名を得られ、影響を受ける検証経路に到達でき、かつアプリケーションが受け入れた識別名を認可に使っている場合に限られる」「検証器の不一致それ自体は悪用ではない」（いずれも原文英語）と明記されています（出典3）。読む側が真っ先に確かめるべきは、評点ではなく自分の前提条件です（本記録の評価）。
  • 修正の進み方はライブラリごとにばらばらで、「修正済み」から「却下」まで並んでいる。 GnuTLS は CVE-2026-3833 を 3.8.13 で修正、pyca/cryptography は CVE-2026-34073 を46.0.6 で修正、wolfSSL は CVE-2026-3547 を 5.9.0 で修正しています（出典3・5・6）。一方で Apple Security.framework の3件は2026年3月16日に提出されたまま triage のまま、Mbed TLS は非クリティカルな名前制約を強制しない挙動を「機能要望」として扱い、BoringSSL の1件は2026年2月28日に「セキュリティの閾値に達しない」として却下されています（出典3・4）。

本記録は2026年10月16日に CERT/CC の2つのノート（出典3・4）を直接取得して裏を取りました。 GnuTLS の修正（GNUTLS-SA-2026-04-29-5・出典5）とpyca/cryptography の勧告（GHSA-m959-cc7f-wv43・出典6）も開発者側の資料として確認しています。 ただし JVN 側の2件は本文を持たず、CERT/CC のノートを参照するだけの体裁です（出典1・2）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

公表されているのは「照合の仕方がどう分かれているか」と 「どういう条件なら問題になるか」までで、実際の攻撃は観測として示されていない（出典3・4）。 以下は CERT/CC が示す3条件に沿って段階へ割り当てたものである（整理は本記録）。

  1. 1. 偵察推定
    標的の配備が名前制約を強制しているか、 どの実装のどの検証経路を通っているかを見極める （出典3・4 が示す前提条件の裏返し。整理は本記録。 CERT/CC はこの段階に言及していない）。
    根拠: 「これらの発見が問題になるのは、影響を受ける経路で名前制約が 強制されている場合に限られる」（出典4。原文英語）。
  2. 2. 初期侵入確認済
    名前制約で本来は許されないはずの名前を含む証明書を、 照合が緩い実装に提示して受け入れさせる （出典3 の「意図した名前空間の外側にある名前を受け入れてしまう場合がある」に基づく）。
    根拠: GnuTLS では大文字小文字の区別により、 除外されるべきドメイン名が受け入れられうるとされる（出典5）。 pyca/cryptography では要求されたピア名に対する照合が欠けていた（出典3・6）。
  3. 3. 影響（暗号化・破壊・改ざん）推定
    受け入れられた識別名を認可の判断に使っている場合、 本来の名前空間の外側にある主体として扱われる （出典3 の3条件の3つめ。実際の悪用は観測として示されていない〈未確定3〉）。
    根拠: 「アプリケーションが受け入れた識別名を認可に使っている場合に限られる」 （出典3。原文英語）。

この事案で下された判断
  • トレードオフ: 全実装の修正を待てば公表は無期限に延びる。 一方、公表により未修正の実装の存在が広く知られる（本記録の評価）。 CERT/CC は影響の3条件と「検証器の不一致だけでは悪用ではない」を 同じノートに置くことで、過剰反応と無視の両方を抑えようとしている （出典3。読み方は本記録）。
  • トレードオフ: 誤った版の範囲を出さないという意味では安全側だが、 読者が自社の版を照合できない（本記録の評価）。 BoringSSL については影響を受ける版の記載自体がない（出典4）。

問題は1つのバグではなく、同じ証明書を実装ごとに違って読むという状態である原因・手口

X.509 の名前制約（Name Constraints）は、中間CA が発行できる名前の範囲を縛るための拡張です（出典3）。CERT/CC の表現では「名前制約は下位の CA を許された名前空間の内側に留めるためのものである」（原文英語）となっています（出典3）。

VU#948176 が報告しているのは、この照合の仕方が実装ごとに分かれていることです（出典3）。内訳は大きく5つに分けられています（出典3。整理は本記録）。

  • DNS 名の大文字小文字とワイルドカード。 GnuTLS は一部の名前の比較を大文字小文字を区別して行っていました（CVE-2026-3833）（出典3・5）。pyca/cryptography は証明書の SAN に対しては制約を照合していたものの、要求されたピア名に対しては照合していませんでした（CVE-2026-34073）（出典3・6）。同種のワイルドカード・大文字小文字の差異は Go・LibreSSL・wolfSSL についても報告されています（出典3）。
  • IP アドレス。 一部の実装は、IPv4 と IPv4 射影 IPv6 の表現を制約の照合時に別のものとして扱います（出典3）。
  • URI。 URI の SAN からどのホストを取り出すかが実装ごとに違います。関連する報告は OpenSSL・Apple・NSS・wolfSSL（CVE-2026-3547）に及びます（出典3）。
  • Common Name へのフォールバック。 AWS-LC と s2n-tls は、リーフ証明書に SAN が無くワイルドカードの CN を使っている場合に、DNS 制約の適用が一貫しないと報告されています（出典3）。
  • 非クリティカルな制約。 報告された Mbed TLS の構成では、非クリティカルな名前制約が強制されません（出典3）。ベンダーは対応の追加を機能要望として扱い、報告者の懸念は disputed（見解が分かれている）とされています（出典3）。

BoringSSL を扱う VU#410595 は、これを5件に絞って並べています（出典4）。記録 .8（修正済み）はワイルドカード DNS 名が、明示的に除外されたホストを含むものとして扱われうる問題、.12（修正済み）は末尾ドットの DNS 名が旧い検証経路で常に正規化されていなかった問題です（出典4）。.9（受理）は「@」の前にコロンを含む URI で誤ったホストが URI 制約と照合されうる問題、.10 は rfc822Name の照合における最初の「@」でのドメイン抽出に関するものでdisputed、.11 は末尾ドットの rfc822Name で却下です（出典4）。.8・.9・.10・.12 は旧い crypto/x509 経路、.11 は新しい pki 経路に関わります（出典4）。

本記録が注意を促したいのは、ここに単一の「修正すべき版」が無いことです（本記録の評価）。読者が確かめるべきは「どの CVE か」ではなく「自社の配備がどの実装のどの検証経路を通っているか」になります（本記録の評価）。

CERT/CC 自身が「検証器の不一致だけでは悪用ではない」と書いている評価・解釈

CERT/CC は影響の条件を明示しています（出典3）。

これらの記録が問題になるのは、攻撃者が選んだ証明書フィールドに対して信頼された署名を得られ、影響を受ける検証経路に到達でき、かつアプリケーションが受け入れた識別名を認可に使っている場合に限られる（出典3。原文英語）

検証器の不一致それ自体は悪用ではない（出典3。原文英語）

効果は配備ごとに異なり、意図した名前空間の外側にある名前を受け入れてしまう場合がある、という記述です（出典3）。BoringSSL のノートも同趣旨で、「これらの発見が問題になるのは、影響を受ける経路で名前制約が強制されている場合に限られる」（原文英語）としています（出典4）。

本記録はこの但し書きを、評点の代わりに読むことを勧めます（本記録の評価）。両ノートに CVSS 評点は示されていません（出典3・4。本記録の確認）。代わりに置かれているのが上の3条件です（出典3）。したがって自組織での判定は、次の順で行うのが筋になります（本記録の評価）。

  1. 自社の PKI で、名前制約を付けた中間CA を実際に発行しているか（本記録の評価）。
  2. その制約を強制する側（検証する側）が、どの実装のどの経路を通っているか（本記録の評価）。
  3. 検証を通った識別名を、認可の判断（誰として扱うか）に使っているか（本記録の評価）。

3つめが「いいえ」であれば、不一致があっても認可の破れには至りません（本記録の評価。出典3 の条件の裏返し）。逆に、mTLS でクライアント証明書の SAN を使って「どのテナントか」「どのサービスか」を決めている構成は、3条件すべてに当たりうる形です（本記録の評価。出典3・4 はこの例を挙げていない）。

CERT/CC は緩和についても期待値を下げています（出典3・4）。「2つめの検証器を置くことが助けになるのは、同じ入力を使い、かつ安全側に閉じる（fail closed）場合に限られる」（原文英語）としています（出典3・4）。実装の差異そのものが問題なのだから、実装を増やしても差異は減らない——という読み方になります（本記録の整理）。

修正の進み方は実装ごとにばらばらで、「修正済み」から「却下」まで並んでいる対策・注意喚起

CERT/CC が示す解消済みの版は次のとおりです（出典3）。

  • GnuTLS — 3.8.13 で修正（CVE-2026-3833）（出典3・5）
  • pyca/cryptography — 46.0.6 で修正（CVE-2026-34073）（出典3・6）
  • wolfSSL — 5.9.0 で修正（CVE-2026-3547）。ワイルドカードの件は PR #9991（出典3）
  • OpenSSL — PR #30319 がマージされ、2026年9月10日時点で当時サポートされていた全バージョンに入っている（出典3）
  • AWS-LC — ワイルドカード CN の件は修正済み（版の記載なし）（出典3）

一方、結論が出ていない／出ない形になっているものがあります（出典3・4）。

  • Apple Security.framework — 3件が2026年3月16日に提出されたまま triage（出典3）
  • Go crypto/x509 — 2件が triage。IPv4 射影 IPv6 の件は「セキュリティの基準を満たさない」として受理されなかった（出典3）
  • Mozilla NSS — IP アドレスの件が調整中（出典3）
  • LibreSSL — ワイルドカードの件が調整中（出典3）
  • s2n-tls — triage（出典3）
  • Mbed TLS — 非クリティカルな名前制約を強制しない挙動は機能要望として扱われ、拡張をクリティカルに設定すればそうした連鎖が安全側に閉じる、という整理（出典3）
  • BoringSSL — .8 と .12 はコミット 5774eca（2026年3月4日）で修正、.9 は受理されて調整中、.10 は disputed、.11 は2026年2月28日に却下（出典4）

運用者向けの推奨として CERT/CC が挙げているのは次の点です（出典3・4）。自分たちが実際に動かしているライブラリが名前制約をどう扱うかを確かめること、リーフ証明書は明示的な SAN に留めること、「発行方針を第一の管理手段として扱う」（原文英語）こと、そしてベンダーの修正が出たら適用することです（出典3）。「更新が広く行き渡るまでは影響が続く」（原文英語）とも書かれています（出典3）。

本記録は、ここに1つ注意を足します（本記録の評価）。「発行方針を第一の管理手段とする」とは、検証側の修正を待つのではなく、そもそも攻撃者が選んだフィールドに署名を得られない体制を作れ、という意味に読めます（出典3 の記述に対する本記録の解釈）。自社 CA の発行手続き・審査・鍵の保護が、ライブラリの更新よりも先に来る項目になります（本記録の評価）。

JVN の2件は本文を持たず、CERT/CC のノートへの転送として公表されている未確定事項

JPCERT/CC が2026年10月15日に出した2件は、いずれも短いものです（出典1・2）。

JVNVU#95474776「複数のTLSライブラリにおける名前制約回避の問題」の本文は「CERT/CCから本件に関するアドバイザリが公表されました。CERT/CCのアドバイザリを参照してください」と、参照先として Vulnerability Note VU#948176 を挙げるだけです（出典1）。JVNVU#95613365「Google BoringSSL証明書検証における複数の名前制約回避の脆弱性」も同じ体裁で、参照先は VU#410595 です（出典2）。

したがって、国内の読者が得られる情報は CERT/CC のノートと同じ範囲に限られます（本記録の整理）。国内製品への影響、国内ベンダーの対応状況、JVN としての評点はいずれも示されていません〈未確定6〉。

finding_nameCERT/CC VU#948176「Multiple TLS Libraries can Bypass Delegation Enforcement」 および VU#410595「Google BoringSSL Name Constraints Bypass in SAN Validation Logic」。 国内では JVNVU#95474776・JVNVU#95613365（出典1・2・3・4）。 CVE が示されているのは CVE-2026-3833（GnuTLS）・CVE-2026-34073（pyca/cryptography）・ CVE-2026-3547（wolfSSL）の3件である（出典3）。

CISO・経営層への示唆
  • 「どの CVE を塞ぐか」では管理できない事案がある。本件は実装間の解釈の差異である。
    CERT/CC が CVE を示したのは3件だけで、 13 のライブラリ個別記録の多くに CVE は付いていない（出典3）。 CVE 一覧で管理していると、本件は「3件の Low／Moderate」に見える（本記録の評価）。
    取るべき行動 脆弱性管理の台帳に「CVE が付かない勧告」を登録できる欄を用意する。 CERT/CC の VU 番号・JVNVU 番号で追えるようにし、 四半期ごとに未決着の調整案件（triage 中のもの）を棚卸しする。
  • 検証側の修正を待つより、発行側の方針で縛るほうが早く効く。
    CERT/CC は推奨の中で「発行方針を第一の管理手段として扱う」（原文英語）としている（出典3）。 また「更新が広く行き渡るまでは影響が続く」とも書いている（出典3）。 実装の修正は Apple のように7か月以上動かないことがある（出典3）。
    取るべき行動 自社 CA から中間CA を発行している場合、 名前制約に頼った封じ込めを「唯一の壁」にしていないか確認する。 発行の審査・承認・鍵の保護を見直し、 外部へ委任している中間CA があればその棚卸しを行う。
  • mTLS の識別名を認可に使っている構成は、本件の3条件に当たりうる。
    CERT/CC は影響が出る条件の3つめに 「アプリケーションが受け入れた識別名を認可に使っている」ことを挙げている（出典3）。 逆にそうでなければ、不一致があっても認可の破れには至らない（本記録の評価）。
    取るべき行動 クライアント証明書の SAN／CN をテナント識別や権限判定に使っている箇所を アーキテクチャ図の上で特定する。 特定できた箇所については、証明書以外の要素と組み合わせる改修を計画に載せる。
  • 「検証器を二重にする」は、本件では期待どおりに効かない。
    CERT/CC は両ノートで 「2つめの検証器を置くことが助けになるのは、同じ入力を使い、 かつ安全側に閉じる場合に限られる」（原文英語）と述べている（出典3・4）。 実装の差異そのものが問題なので、実装を足せば差異も増える（本記録の整理）。
    取るべき行動 多層防御の設計を見直すとき、「別実装を足す」案を採る前に 「同じ入力を見ているか」「不一致のときに閉じるか」を条件として明記する。 条件を満たさない二重化は、安心の材料にしない。
セキュリティ技術者への示唆
  • 名前制約の照合は、SAN だけでなく「要求したピア名」に対しても行う必要がある。
    pyca/cryptography は証明書の SAN に対しては制約を照合していたが、 要求されたピア名に対しては照合していなかった（CVE-2026-34073）（出典3・6）。
    取るべき行動 自前で証明書検証の層を書いている場合、 制約の照合対象が「証明書に書かれた名前」だけになっていないか確認する。 接続先として要求した名前も照合対象に含める。
  • ドメイン名の比較は大文字小文字を区別しない。末尾ドットは正規化する。
    GnuTLS は一部の比較を大文字小文字を区別して行っており、 RFC 5280 7.2 節から逸脱していた（CVE-2026-3833）（出典3・5）。 BoringSSL では末尾ドットの DNS 名が旧い検証経路で 常に正規化されていなかった（VU#410595.12）（出典4）。
    取るべき行動 名前の照合を自分で書いている箇所について、 大文字小文字・末尾ドット・ワイルドカード・IPv4 射影 IPv6 の 4つを入力に含む試験を追加する。 通る／落ちるの期待値は RFC 5280 7.2 節に照らして決める。
  • SAN を持たないリーフの CN にフォールバックする経路は、制約の適用が崩れやすい。
    AWS-LC と s2n-tls は、リーフ証明書に SAN が無くワイルドカードの CN を 使っている場合に DNS 制約の適用が一貫しないと報告されている（出典3）。
    取るべき行動 自社が発行する証明書はすべて明示的な SAN を持たせ、 CN だけの証明書を発行・受け入れしない方針にする。 受け入れ側でも SAN が無い証明書を拒否する設定を既定にする。
  • 使っているライブラリと「検証経路」を特定しておく。同じライブラリでも経路で挙動が違う。
    BoringSSL では、.8・.9・.10・.12 が旧い crypto/x509 経路、 .11 が新しい pki 経路に関わるとされている（出典4）。 「BoringSSL を使っている」だけでは影響の有無が決まらない（本記録の整理）。
    取るべき行動 SBOM で TLS ライブラリを洗い出したうえで、 どの検証 API を呼んでいるかまで記録する。 間接依存の奥にある場合は、依存グラフを辿って呼び出し元を特定する。
  • 非クリティカルな拡張を強制しない実装があることを前提に、拡張の critical 指定を決める。
    報告された Mbed TLS の構成では非クリティカルな名前制約が強制されず、 CERT/CC は拡張をクリティカルに設定すればそうした連鎖が 安全側に閉じる（fail closed）と整理している（出典3）。
    取るべき行動 自社 CA が名前制約を付けるとき、拡張を critical として発行するか決める。 critical にすると理解しない検証器は接続を落とすため、 影響範囲の確認とあわせて判断する。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 自社 PKI で中間CA を発行し、名前制約（Name Constraints）で発行できる名前の範囲を縛っている
認証・認可□ TLS クライアント証明書の SAN や CN を、テナント識別・権限判定などの認可に使っている
委託・第三者部品□ 製品・サービスが OpenSSL／GnuTLS／wolfSSL／pyca cryptography／Go crypto-x509／NSS／LibreSSL／AWS-LC／s2n-tls／Mbed TLS／BoringSSL のいずれかに依存している
システム構成□ 同じ証明書を複数の実装で検証する構成（ゲートウェイとアプリ、プロキシと背後のサービス等）になっている
運用・監視□ 依存ライブラリの版を把握できておらず、修正版（GnuTLS 3.8.13・pyca cryptography 46.0.6・wolfSSL 5.9.0 等）への更新状況が分からない
体制・契約□ 外部の組織へ中間CA を委任している、または他社の CA を信頼ストアに入れている
