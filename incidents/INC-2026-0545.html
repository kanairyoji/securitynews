INC-2026-0545LiteLLM で管理権限を奪取できた

LLM ゲートウェイ LiteLLM に管理権限の奪取経路——アカウントを1つ持つだけで 設定を書き換えられ、クラウドストレージ上の Python が実行される（CVE-2026-35029・CVE-2026-59823）

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年4月3日（GitHub Advisory Database での CVE-2026-35029 公開） 最終更新: 2026年10月16日（本記録の確認時点）

AI ゲートウェイは、組織が使う全プロバイダの API キーを1か所に集めた箱です。その箱の設定を、一般利用者のアカウントで書き換えられました。

2026年10月13日、Check Point Research は「When LLM Gateways Go Wrong: Findings from LiteLLM」（LLM ゲートウェイが壊れるとき——LiteLLM からの発見／原文英語）を公開し、LiteLLM の2件の脆弱性を明らかにしました（出典1・4）。2026年10月15日には Infosecurity Magazine が報じています（出典4）。

本記録が要点と見たのは、次の3点です。

  • 必要なのは「アカウントを1つ持っていること」だけである。 CVE-2026-35029 は /config/update が管理者ロールを確認しておらず、認証済みの利用者であれば誰でもプロキシの設定と環境変数を変更できた、というものです（出典1・2）。Check Point は「要求は、実際のロール（Admin、Internal User など）に関係なく、有効な UI セッショントークンを持つすべての利用者に許可される」（原文英語）と書いています（出典1）。
  • 設定の書き換えは、そのままファイル読み出し・管理者乗っ取り・コード実行になる。 Check Point が示した経路は3つです。UI_LOGO_PATH を書き換えて検証のない /get_image から任意のファイルを読む（実証では /etc/passwd）、UI_USERNAME と UI_PASSWORD を書き換えて管理者として入り直す、そして general_settings.pass_through_endpoints の宛先を s3:// または gcs:// にしてダウンロードした Python を exec_module() で実行させる、です（出典1）。
  • もう1件は、ゲートウェイが持っているプロバイダの API キーを外へ運び出す。 CVE-2026-59823 は user_config 経由の SSRF で、攻撃者が api_base を自分のサーバに向けると、プロキシに設定されている API キーが既定ヘッダに載って送られます（出典1・3）。Check Point は、api_base と api_key を直接指定する経路を制限するconfigurable_clientside_auth_params が、この user_config 経路には適用されないと指摘しています（出典1）。

本記録は2026年10月16日に Check Point Research のブログ（出典1）とGitHub Advisory Database の2件（出典2・3）を直接取得して裏を取りました。 ただし「修正された版」の表記が資料の間で食い違っています〈齟齬1〉。GitHub の勧告は CVE-2026-35029 を「1.83.0 未満が対象・1.83.0 で修正」とする一方、Check Point と Infosecurity Magazine は「1.83.9 で修正」「1.83.9 より古い版が対象」としています（出典1・2・4）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

Check Point が実証した経路であり、実際の攻撃の観測ではない（出典1）。 前提は「脆弱な LiteLLM 配備に認証済みのアカウントを1つ持っていること」で、 管理者権限は不要である（出典1・2）。

  1. 1. 初期侵入確認済
    脆弱な配備で認証済みのアカウントを使い、UI セッショントークンを得る （出典1。CVSS では `PR:L`・出典2）。
    根拠: 「要求は、実際のロール（Admin、Internal User など）に関係なく、 有効な UI セッショントークンを持つすべての利用者に許可される」（出典1。原文英語）。
  2. 2. 権限昇格確認済
    `/config/update` でプロキシの設定と環境変数を変更し、 `UI_USERNAME` と `UI_PASSWORD` を書き換えて Proxy Admin として入り直す （CVE-2026-35029。出典1・2）。
    根拠: GitHub の勧告は「`UI_USERNAME` と `UI_PASSWORD` 環境変数を上書きすることで 特権アカウントを奪取できる」と記載している（出典2。原文英語）。
  3. 3. 認証情報アクセス確認済
    `UI_LOGO_PATH` を設定し、検証のない `/get_image` から任意のファイルを読む。 実証では `/etc/passwd` を読み出している（出典1）。 別経路として、`user_config` 経由の SSRF で `api_base` を攻撃者のサーバへ向け、 既定ヘッダに載るプロバイダの API キーを受け取る（CVE-2026-59823。出典1・3）。
    根拠: 「攻撃者は `environment_variables` を通じて `UI_LOGO_PATH` を設定する。 検証のない `/get_image` 端点がそのファイルを配信する」（出典1。原文英語）。 SSRF については「プロキシに設定された API キーが既定ヘッダで そのサーバへ送られる」（出典1。原文英語）。
  4. 4. 実行確認済
    `general_settings.pass_through_endpoints` の宛先を `s3://` または `gcs://` にして、 ダウンロードされた Python を `exec_module()` で実行させる（出典1）。
    根拠: 「ダウンロードされた Python ファイルのトップレベルのコードをすべて実行する」 （出典1。原文英語）。
  5. 5. 影響（暗号化・破壊・改ざん）推定
    ゲートウェイの完全な掌握。Check Point は ファイル読み出し・資格情報の窃取・リモートコード実行を挙げる（出典1・4）。 実際の被害の観測は公表されていない〈未確定3〉。
    根拠: 「実務的には、脆弱な LiteLLM 配備のアカウントを持つ者は誰でも ゲートウェイを乗っ取り、悪意ある目的に使えた」 （Mateo Rojas-Carulla 氏。出典4。原文英語）。

「アカウントを1つ持っている」だけで設定を書き換えられた——3つの実装が重なった原因・手口

Check Point は CVE-2026-35029 の成立を3段で説明しています（出典1）。

  1. ロールの確認が無い。 /invitation/new のような保護された端点は PROXY_ADMIN を明示的に要求するのに、/config/update は汎用の user_api_key_auth 依存だけに頼っており、利用者のロールを確認していませんでした（出典1）。
  2. UI のトークンがチーム ID で分類される。 UI からログインすると litellm-dashboard チームに割り当てられた鍵が発行され、common_checks はそのチームを持つトークンを——利用者のロールに関係なく——「ui」として扱います（出典1）。
  3. UI 経路の判定が緩い。 UI のトークンは、より厳格な API 経路の判定ではなく _is_ui_route() で照合されます。ui_routes の一覧には /config が含まれ、照合は startswith なので /config/update が通ります（出典1）。

結果として、Check Point はこう書いています（出典1）。

要求は、実際のロール（Admin、Internal User など）に関係なく、有効な UI セッショントークンを持つすべての利用者に許可される（出典1。原文英語）

GitHub の勧告も同じ内容を短く示しています（出典2）。分類は CWE-863（不適切な認可）、深刻度 High、CVSS v4.0 基本値 8.7（AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:L/SI:L/SA:N）です（出典2）。

本記録が注意を促したいのは、PR:L の読み方です（本記録の評価）。「低い権限が要る」は一見すると緩和要因に見えますが、ゲートウェイの性質上、組織内の開発者・利用者・CI の全員がアカウントを持ちます（本記録の評価）。Check Point の Mateo Rojas-Carulla 氏の言い方では「実務的には、脆弱な LiteLLM 配備のアカウントを持つ者は誰でもゲートウェイを乗っ取り、悪意ある目的に使えた」（原文英語）となります（出典4）。

設定の書き換えは、ファイル読み出し・管理者乗っ取り・コード実行の3つに化ける被害規模・影響範囲

Check Point は /config/update から先の経路を3つ示しています（出典1）。

  • 任意のファイル読み出し。 environment_variables を通じて UI_LOGO_PATH を設定すると、検証のない /get_image 端点がそのファイルを配信します（出典1）。実証では /etc/passwd を読んでいます（出典1）。
  • 管理者アカウントの乗っ取り。 UI_USERNAME と UI_PASSWORD を設定し、その資格情報でログインすると Proxy Admin の権限が得られます（出典1）。
  • リモートコード実行。 general_settings.pass_through_endpoints の宛先が s3:// または gcs:// で始まる場合、それがダウンロードされ exec_module() で実行されます（出典1）。Check Point はこれが「ダウンロードされた Python ファイルのトップレベルのコードをすべて実行する」（原文英語）と注記しています（出典1）。

GitHub の勧告はこれらを列挙したうえで、回避策について明記しています（出典2）。設定レベルの回避策は存在せず、示されている緩和は「API 鍵の配布を制限すること」だけです（出典2）。修正は該当端点に proxy_admin ロールを要求することです（出典2）。

本記録の整理では、ここで重要なのは「何が読めるか」ではなく「ゲートウェイが何を持っているか」です（本記録の評価）。Infosecurity Magazine はこの点を次のように整理しています（出典4）。LLM ゲートウェイは資格情報の管理・ログ・利用量の追跡を集約するために使われ、組織が使うすべての AI プロバイダの API キーを保管し、ロールと権限で利用者のアクセスを管理する責任を負っている——（出典4。原文英語）。つまり奪取の対価は、1つのサービスの権限ではなく「組織の AI 利用の束」になります（本記録の評価）。

もう1件は、ゲートウェイが持つプロバイダの鍵を外へ運び出す原因・手口

CVE-2026-59823 は SSRF です（出典1・3）。Check Point の説明は4段です（出典1）。

  1. /chat/completions その他の LLM 端点が user_config パラメータを受け付ける（出典1）。
  2. route_llm_request.py がそれをもとにlitellm.Router(**router_config) を——検証なしで——生成する（出典1）。
  3. 攻撃者は任意の api_base を含む model_list を与え、要求を攻撃者のサーバへ向ける（出典1）。
  4. そのとき、プロキシに設定されている API キーが既定ヘッダに載って送られる（出典1）。

Check Point は、api_base と api_key の直接指定を制限するconfigurable_clientside_auth_params が、この user_config 経路には適用されないと指摘しています（出典1）。GitHub の勧告では深刻度 Moderate、「LiteLLM Proxy に user_config 要求パラメータ経由のサーバサイドリクエストフォージェリ」として登録されています（出典3）。

Infosecurity Magazine は影響を「ゲートウェイの外向き要求を向け直し、AI プロバイダの API キーを露出させる」（原文英語）と要約しています（出典4）。

本記録の評価では、2件は組み合わせて読むべきものです（本記録の評価）。CVE-2026-35029 が「箱の中に入る」経路、CVE-2026-59823 が「箱の中身を外へ運ぶ」経路であり、どちらも必要なのは認証済みのアカウント1つです（出典1・3。整理は本記録）。検知の観点では、後者は外向きの通信先が増えるという痕跡を残しますが、ゲートウェイはもともと多数のプロバイダへ外向き通信する装置なので、通常の宛先と区別する材料が無ければ見分けられません（本記録の評価。出典1・3・4 は検知に触れていない）。

「どの版で直ったか」が資料の間で食い違っている未確定事項

修正版の表記が揃っていません〈齟齬1〉。

GitHub Advisory Database の GHSA-53mr-6c8q-9789 は、CVE-2026-35029 について「対象は 1.83.0 未満」「修正は 1.83.0」としています（出典2）。一方 Check Point は、2件とも「LiteLLM バージョン 1.83.9 の時点で解消されている」（原文英語）と書き、検証に使った版を v1.77.7 としています（出典1）。Infosecurity Magazine も「1.83.9 より古い版が影響を受ける」とし、「LiteLLM バージョン 1.83.9 とそれ以降のすべての版に修正が含まれる」と伝えています（出典4）。

本記録はこの食い違いを解消できていません〈齟齬1〉。読者に勧めるのは、安全側の 1.83.9 以降に揃えることです（本記録の評価）。1.83.0 から 1.83.8 の間に別の修正が入ったのか、それとも Check Point が2件をまとめて最新の修正版で案内しているのかは、本記録が確認した資料からは判断できません（本記録の整理）。

公表されていないことを並べておきます（出典1・2・3・4。整理は本記録）。報告日と修正版の公開日〈未確定1・齟齬2〉、脆弱性が存在していた期間〈未確定2〉、悪用の有無と影響を受けた配備〈未確定3〉、CVE-2026-59823 の CVSS 評点〈未確定4〉、流出しうる API キーの範囲〈未確定5〉、そして国内向けの公表の有無〈未確定6〉です。

なお Check Point のブログには推奨事項の節がありません（出典1。本記録の確認）。4項目の推奨として報じられているものは Infosecurity Magazine の記事に載っている形です（出典4）。アカウントの棚卸し、API キーの再発行、「設定された権限と実際に強制される権限の差」の検証、そして AI ツールをペネトレーションテストと脆弱性評価の対象に含めることです（出典4）。

CISO・経営層への示唆
  • AI ゲートウェイは「全プロバイダの鍵を1か所に集めた箱」である。重要度を認証基盤と同じ段に置く。
    Infosecurity Magazine は、LLM ゲートウェイが資格情報の管理・ログ・ 利用量の追跡を集約し、組織が使うすべての AI プロバイダの API キーを 保管していると整理している（出典4）。 Check Point の2件は、どちらもその箱の中身に到達する経路である（出典1）。
    取るべき行動 自組織の AI ゲートウェイを資産台帳に登録し、 重要度を ID 基盤・シークレット管理と同じ区分に上げる。 インターネットに面しているか、誰がアカウントを持っているかを今週のうちに確認する。
  • 「設定された権限」と「実際に強制される権限」は別物である。後者を測る手順を持つ。
    CVE-2026-35029 は、ロールが設定されていても UI セッショントークンの経路判定で確認が抜け落ちていた例である（出典1・2）。 Check Point の推奨にも「限定的なロールの利用者が実際に限定されているかを 確認せよ」が入っている（出典4）。
    取るべき行動 権限の検証を文書レビューで済ませず、 最小権限のアカウントを1つ用意して管理系の端点に実際に当てる手順を作る。 新しい SaaS・社内ツールの導入時の受け入れ条件に含める。
  • AI ツールは、ペネトレーションテストと脆弱性評価の対象範囲から外れやすい。
    Check Point の推奨は「Web アプリケーションやクラウド基盤と並べて AI ツールを対象に含めよ」と明示している（出典4）。 Black Duck の Christopher Jess 氏は 「AI の導入が加速するなかでセキュリティの基本が 二次的な関心事として扱われる傾向」（原文英語）と述べている（出典4）。
    取るべき行動 次回のペネトレーションテストの対象資産一覧に、 AI ゲートウェイ・ベクトルDB・エージェント実行環境を追記する。 対象外にする場合は、その理由を記録に残す。
  • オープンソースの脆弱性は「勧告の1行」と「技術詳細」の間に数か月の空白がある。
    CVE-2026-35029 の勧告公開は2026年4月3日、技術詳細の公開は2026年10月13日で、 約193日の差がある（出典1・2。日数は本記録の算出）。 その間、利用側が持っていた情報は勧告の記述だけである（本記録の評価）。
    取るべき行動 依存ライブラリの勧告を「詳細が出ていないから様子見」にしない運用にする。 深刻度 High 以上の勧告は、詳細の有無によらず更新の判断を行う。
セキュリティ技術者への示唆
  • 経路の権限判定を前方一致で書かない。`/config` の許可が `/config/update` を通す。
    Check Point は `ui_routes` に `/config` が含まれ、 照合が `startswith` であるため `/config/update` が通ると説明している（出典1）。
    取るべき行動 自前のルート許可リストを棚卸しし、前方一致の照合を完全一致または メソッド込みの明示的な列挙に置き換える。 許可リストの単体テストに「許可した経路の配下が通らないこと」を加える。
  • 認可の判定を「トークンの出自」で代用しない。ロールはロールとして確認する。
    UI ログインで発行された鍵が `litellm-dashboard` チームに割り当てられ、 `common_checks` がそれを——利用者のロールに関係なく——「ui」として 扱っていた（出典1）。 GitHub の分類は CWE-863（不適切な認可）である（出典2）。
    取るべき行動 管理系の端点に、依存注入の層でロール要求（例: `proxy_admin`）を 明示的に付ける。 「どの端点がどのロールを要求するか」を一覧にして、 要求が無い端点をレビューの対象にする。
  • 要求本体から渡された接続先（api_base 等）を、そのまま使う実装を作らない。
    CVE-2026-59823 では `user_config` から `litellm.Router(**router_config)` が 検証なしに生成され、任意の `api_base` へ要求が向けられた（出典1・3）。 `api_base`・`api_key` の直接指定を制限する設定は この経路に適用されなかった（出典1）。
    取るべき行動 外向きの接続先を要求本体から受け取る箇所を洗い出し、 許可するホストの白名簿で縛る。 既存の制限設定がある場合は、その設定が「すべての入力経路」に 掛かっているかを実際に試験する。
  • 外部から取得したコードを `exec_module()` に渡す設計は、設定1つで RCE になる。
    `general_settings.pass_through_endpoints` の宛先が `s3://` または `gcs://` の場合、 ダウンロードされて `exec_module()` で実行され、 「トップレベルのコードをすべて実行する」（原文英語）（出典1）。
    取るべき行動 動的にコードを読み込む機能を持つ場合、 取得元を固定のパスまたは署名付きの配布物に限定する。 設定から任意の URI を受け取る実装は、管理者ロールと変更監査の両方で囲う。
  • 秘密を既定ヘッダに載せる作りは、宛先が変わった瞬間に漏えいになる。
    Check Point は、SSRF で宛先を変えられたとき 「プロキシに設定された API キーが既定ヘッダで送られる」と書いている（出典1）。
    取るべき行動 外向き要求の既定ヘッダに資格情報を入れている箇所を洗い出し、 宛先ごとに鍵を解決する作りへ変える。 宛先が白名簿外のときは鍵を付けずに失敗させる。
