INC-2026-0551サンポー食品サイトで管理者権限奪取

サンポー食品が、自社ウェブサイトで使用している web システムの脆弱性を悪用され、第三者に管理者権限を取得されたうえウェブサイトを改ざんされた——2026年8月25日に不正アクセスを確認してサイトを停止し、制作会社・システム会社と調査した結果が9月28日に公表された。情報の持ち出しや不正利用の痕跡は確認されていないが、不正アクセス期間中にサイトのデータへアクセス可能な状態であった可能性は否定できないとしている。問い合わせフォームの送信内容はサイト側に保存していなかった

不正アクセス・侵害初報のみ日本の組織が当事者既知の脆弱性の悪用
初報: 2026年9月28日 最終更新: 2026年10月16日

サンポー食品株式会社（佐賀県三養基郡基山町。「焼豚ラーメン」などの即席麺メーカー）は2026年9月28日、同社ウェブサイトへの不正アクセスについて公表しました。

経過は同社の公表によれば次のとおりです。2026年8月25日、同社ウェブサイトに対する第三者からの不正アクセスを確認しました。同社は当該サイトを停止し、ウェブサイト制作会社およびシステム会社と連携して調査を実施しています。

原因について同社は、当該サイトで使用している web システムの脆弱性を悪用された可能性が高いと判断しています。調査の結果、第三者による管理者権限の取得やウェブサイトの改ざんが行われていたことが判明しました。

情報の扱いについては、対象情報の持ち出しや不正利用を示す痕跡は確認されていない一方、不正アクセス期間中にウェブサイトのデータへアクセス可能な状態であった可能性は否定できないとしています。また、ウェブサイト内の問い合わせフォームから送信された個人情報等については、ウェブサイトシステム内にデータを保存していないと明記しています。

再発防止として、OS やソフトウェア等の脆弱性管理とアップデートの徹底、さらなるセキュリティ対策の実施、従業員向けセキュリティ研修の徹底を挙げています。

本記録が注目するのは3点です。①「管理者権限を取られた」と明示して公表していること、②問い合わせフォームの送信内容を「サイト側に保存していない」と説明し、被害の上限を自ら示していること、③確認から公表まで34日を要し、その間、改ざんされたページを閲覧した人がいたかどうかは示されていないこと。一次資料は同社のお知らせで、評価・示唆は本記録の判断として分けて書きます。

「管理者権限を取られた」と書いた以上、痕跡の不在は無罪の証明にならない（本記録の評価）評価・解釈出典 [1]

ここからは本記録の作成者の評価である。

第一に、この公表の最大の価値は「管理者権限の取得」を書いたことである。日本の中小・中堅企業のサイト改ざんの公表は「不正アクセスを受け、一部ページが改ざんされました」で終わることが多い。同社は権限を取られたところまで書いた。読む側にとっては意味が全く違う。改ざんだけなら書き換えられたページの範囲で話が済むが、管理者権限があればサイトでできることは全部できたことになる。

第二に、だからこそ「痕跡が確認されていない」の読み方に注意が要る。同社は持ち出し・不正利用の痕跡が無いとしつつ、アクセス可能な状態だった可能性は否定していない。これは誠実な書き方である。ただし管理者権限を持つ者は、操作の記録そのものを消せる。「痕跡が無い」は「行われていない」ではなく「残っている記録の中には無い」である。同社が消去の可能性に触れていないのは惜しい。読者が自社の公表文を書くときは、痕跡の不在を述べる段落に、ログの保全範囲と解析の対象期間をセットで書くほうが信用される。

第三に、「保存していなかった」は最も安い対策である。同社は問い合わせフォームの送信内容をウェブサイトシステム内に保存していなかった。これが本件の被害の上限を決めた。公開サーバに置かれた個人情報は、暗号化しても、アクセス制御を掛けても、管理者権限を取られたら全部読める。対して、そもそも置いていなければ読めない。コーポレートサイトの問い合わせフォームは、送信内容を DB に保存せずメール送信だけにするか、外部のフォームサービスへ分離するかで、この層の被害をゼロにできる。費用はほぼかからない。日本の同種事案で漏えいに至っているものの多くは、ここが逆になっている。

第四に、再発防止策の3点のうち、本件に効くのは1つだけである。「脆弱性管理とアップデートの徹底」は原因に直接効く。「さらなるセキュリティ対策」は内容が無い。「従業員向けセキュリティ研修」は、本件の原因が web システムの脆弱性である以上、効き目が説明されていない。研修で防げる種類の侵入ではない。再発防止策は、原因の一つひとつに対応づけて書かないと、読者には「とりあえず並べた」ようにしか見えない（本記録の評価）。

第五に、34日という間隔をどう見るか。確認から公表まで34日は、調査を外部2社と行ったことを踏まえれば不自然に長くはない。問題は長さではなく、その間に閲覧者向けの速報が無かったことである。改ざんされたサイトを閲覧した人がいるかもしれない期間に、「サイトを停止しています」の一報すら外から確認できる形で出ていたかは不明である。調査結果を待つ公表と、利用者への即時の告知は、別の文書として分けてよい。

CISO・経営層への示唆
  • 公開サイトに個人情報を「置かない」ことが、最も安く確実な上限の設定である
    同社は問い合わせフォームの送信内容をウェブサイトシステム内に保存していなかった。 管理者権限を取得されてもなお、そこから抜かれる個人情報が存在しなかった
    取るべき行動 自社の公開サイトが保持している個人情報を棚卸しし、 「サイトに置く必然性」を1件ずつ問い直す。問い合わせフォームは 送信内容を DB に保存せずメール送信のみにするか、外部のフォームサービスへ分離する。 判断と移行の期限を決めて実行する
  • 「痕跡は確認されていない」は、ログの保全範囲とセットでなければ意味が伝わらない
    同社は管理者権限の取得を確認したうえで、持ち出しの痕跡は確認されていないとしている。 管理者権限を持つ者は記録そのものを消せるため、 どの範囲のログを見た結論なのかで確からしさが変わる
    取るべき行動 インシデント公表のテンプレートに「調査対象としたログの種類・保存期間・ 解析した期間」の欄を設ける。痕跡の不在を述べる段落には必ずこの3点を添える
  • 再発防止策は、原因の一つひとつに対応づけて書く
    同社の再発防止策3点のうち、本件の原因（web システムの脆弱性の悪用）に 直接対応するのは「脆弱性管理とアップデートの徹底」のみで、 従業員向け研修との対応関係は説明されていない
    取るべき行動 公表文の再発防止策を「原因 → 対策 → 実施時期・確認方法」の表形式にする。 原因に対応しない対策を書く場合は、何を狙った対策かを明示する
  • 調査結果の公表と、利用者への即時の告知は別の文書に分ける
    確認から公表まで34日あり、その間に改ざんされたページを閲覧した人への 告知があったかは外部から確認できない
    取るべき行動 「サイトを停止した」時点で出す一報の雛形を用意する。 内容は、停止の事実・停止の理由（調査中）・閲覧者が取るべき行動の有無・ 次の案内の目安時期の4つに限り、調査結果を待たずに出す
  • 制作会社に委託したサイトでも、更新責任の所在を契約で決めておく
    同社はウェブサイト制作会社とシステム会社の2社と連携して調査しており、 サイトの構築・運用に外部が関与していたことがうかがえる。 脆弱性の更新をどちらが行う取り決めだったかは公表されていない
    取るべき行動 外部に委託している公開サイトについて、CMS・プラグイン・サーバ OS の 更新実施者と頻度を契約書または覚書で特定する。 特定できないサイトを一覧にし、優先して契約を見直す
セキュリティ技術者への示唆
  • 管理画面へのログインと管理者アカウントの変更に、即時の通知を付ける
    本件では管理者権限の取得が確認されている。 管理者アカウントの追加・権限変更・管理画面へのログインは CMS の標準機能で記録でき、日常の発生件数も少ないため検知しやすい
    取るべき行動 管理画面のログインを IP 制限または多要素認証で絞る。 管理者アカウントの追加・権限変更・パスワード変更が起きたら 運用担当へ即時に通知する設定を入れる。 平常時の発生件数を測り、通知が埋もれない水準か確認する
  • 公開ページの差分監視を入れると、改ざんは当日に分かる
    改ざんをいつどのように把握したかは公表されていない。 確認が2026年8月25日であることだけが分かっている
    取るべき行動 公開ページの HTML と、公開ディレクトリのファイルのハッシュを 定期的に取得して比較する仕組みを入れる。 更新作業の予定表と突き合わせ、予定外の差分だけを通知する
  • 侵害されたサイトは、管理者権限が取られた前提で作り直す
    管理者権限を取得された環境では、記録の消去・改変・追加の仕掛けの設置が いずれも可能である。「痕跡が無い」は「行われていない」を意味しない
    取るべき行動 復旧時は、既存の管理者アカウントを全て無効化して作り直し、 全ての認証情報（管理画面・DB・FTP/SSH・API キー）を変更する。 コンテンツは侵害前のバックアップか版管理されたソースから戻す
  • 問い合わせフォームの送信内容を DB に書かない構成を既定にする
    同社はこの構成だったため、管理者権限を取られても問い合わせ内容が サイト側に残っていなかった
    取るべき行動 フォームの実装を確認し、送信内容を DB に保存している場合は 保存の必要性を問い直す。必要なら保存先を公開サーバの外へ移すか、 保持期間を短くして自動削除する
  • 調査のログ要件を、インシデントが起きる前に決めておく
    「痕跡は確認されていない」という結論の根拠となるログの保全範囲が 公表されていないため、確からしさを評価できない
    取るべき行動 公開サイトについて、Web アクセスログ・CMS の操作ログ・DB のクエリログ・ ファイルの変更記録の4種を、最低でも90日分、サイトとは別の場所に保存する。 保存されていることを四半期ごとに実際に取り出して確認する
