INC-2026-0552生豆本舗が SQLi 攻撃で応答不能に

コロンビア珈琲が運営する通販サイト「極上珈琲 生豆本舗」が、外部の自動攻撃ツールによる SQL インジェクションの試行を約1万件受け、商品検索に送り込まれた特殊な文字列でデータベースに極端に重い処理が発生してサイト全体が応答不能になった——2026年9月26日23時頃から翌27日13時15分頃までの障害。攻撃はいずれもシステムにより拒否または無効化され、顧客情報や注文情報の取得に至った形跡は確認されていない。対策としてデータベース側に60秒の処理時間上限を設け、Web サーバ側で攻撃文字列を遮断するようにした

システム障害脅威・攻撃キャンペーン初報のみ日本の組織が当事者容量・リソース枯渇設計・実装上の不備
初報: 2026年9月28日 最終更新: 2026年10月16日

コロンビア珈琲株式会社（兵庫県尼崎市）は 2026年9月28日、同社が運営するコーヒー生豆・焙煎豆の通販サイト「極上珈琲 生豆本舗」で発生したサイト障害について公表しました。

経過は同社の公表によれば次のとおりです。2026年9月25日から、外部の自動攻撃ツールによる不正アクセスの試行（SQL インジェクション）が集中的に行われ、件数は約1万件、国内の100以上の回線を経由していました。9月26日22時50分頃には、攻撃の一環として商品検索に特殊な文字列が送り込まれ、データベースで極端に重い処理が発生しました。これが他の処理を長時間待たせることとなり、サイト全体が応答できない状態になっています。

障害が続いたのは 9月26日23時頃から9月27日13時15分頃までで、この間「極上珈琲 生豆本舗」が正常に表示されませんでした。

同社がアクセス記録を調査した結果、攻撃はいずれもシステムにより拒否または無効化されており、顧客情報や注文情報などのデータ取得に至った形跡は確認されていないとしています。

対策として実施されたのは次の2つです。

  1. データベース側 — サイトからの処理に上限時間（60秒）を設け、異常に重い処理は自動的に打ち切る
  2. Web サーバ側 — 不正アクセスで使われる文字列を含むリクエストを、データベースに届く前に遮断する

本記録が注目するのは3点です。①データは抜かれていないのに、サービスは14時間止まったこと、②止めたのは「侵入」ではなく「重いクエリ1本」だったこと、③対策の第一がタイムアウトの設定であり、それまで上限が無かったと読めること。SQL インジェクションを「漏えいの手口」としてのみ構えていると、この止まり方は想定から落ちます。なお、本記録の作成者は同社による公表文そのものを発見できませんでした（後述）。事実関係は ScanNetSecurity の報道に依拠し、評価・示唆は本記録の判断として分けて書きます。

対策はデータベース側のタイムアウトと、Web サーバ側での事前遮断の2段である再発防止出典 [2]

同社が実施したとする対策は次の2つである。

1. データベース側

サイトからの処理に上限時間（60秒）を設け、異常に重い処理は自動的に打ち切り。

2. Web サーバ側

不正アクセスで使われる文字列を含むリクエストを、データベースに届く前に遮断。

この2つは役割が違う。1つ目は「重い処理が来てもサイト全体は巻き込まれない」ための被害の封じ込めであり、2つ目は「そもそも届かせない」ための入口の遮断である。順番としては1つ目が先に書かれており、サービスを落とさないことを優先した構成と読める。

一方、1つ目を「対策」として挙げているということは、事案の発生時点で処理時間の上限が設定されていなかったと読める。同社がそう明言したわけではないが、この読みが成り立つ（本記録の評価）。

2026年10月16日時点で、公表されていないのは次の点である。

  • 同社による公表文そのものの所在（本記録の作成者は発見できなかった。後述）

  • 障害期間中の注文・決済への影響と補償
  • 使用している EC システムの名称とバージョン

このうち2点目は、読者が自社の点検に使ううえで効く情報である。注入が無効化されながら処理が重くなったのであれば、「WAF や無害化を入れていても、検索の重さは止まらない」という教訓になる。文字列が示されていないため、本記録はこの区別を推定しない。

入力の無害化は「漏れない」ことを保証するが、「落ちない」ことは保証しない（本記録の評価）評価・解釈出典 [1] [2]

ここからは本記録の作成者の評価である。

第一に、これは SQL インジェクション対策が効いたうえで起きた障害である。同社の説明では、攻撃はいずれも拒否または無効化され、データ取得の形跡は無い。対策は機能した。それでもサイトは約14時間止まった。注入を無害化する仕組みは、クエリが重くなることまでは止めない。エスケープもプレースホルダも WAF も、「危険な意味を持たせない」ための道具であって、「安いコストで終わらせる」ための道具ではない。日本の事業者の多くは SQL インジェクションを漏えいの手口として構えているが、本件が示すのは可用性の手口としての顔である。

第二に、止まったのは検索が「重い処理」を許す窓口だったからである。商品検索は、EC サイトで最も自由入力を受け付ける場所であり、かつ全件走査になりやすい機能である。インデックスが効かない条件、ワイルドカードの前方一致、複数カラムへの LIKE——どれも1本で数分かかりうる。そこへ自動攻撃ツールが毎秒何本も投げれば、接続が埋まり、商品ページも決済も巻き込まれる。攻撃者が狙ってやったのか、偶然の副作用なのかは分からないが、結果は DoS と同じである。

第三に、対策の順序が実務的である。 同社は入口の遮断より先に、データベース側の処理時間の上限（60秒）を挙げている。これは正しい優先順位である。入口の遮断は知っている文字列しか止められないが、上限時間はまだ知らない重い処理にも効く。前者は攻撃の種類に依存し、後者は依存しない。読者が自社で1つだけやるなら、上限時間の設定が先である。ただし60秒という値は、EC サイトの利用者が待てる時間としては長い。利用者から見れば60秒待たされた時点でサイトは「止まっている」。本来は接続数の上限・1 IP あたりの要求速度の制限と組み合わせる必要がある（本記録の評価）。

第四に、日本の読者にとっての含意は「検索窓の負荷試験」である。脆弱性診断は「注入が通るか」を見るが、「重くできるか」は見ないことが多い。本件は、診断で指摘されない種類の弱点でサービスが止まった事例である。自社の検索機能に対し、最悪の入力（長い文字列・先頭ワイルドカード・複数条件の組み合わせ）を投げたときの実行時間を測っておくと、どこに上限を置くべきかが決まる。

第五に、「国内の100以上の回線」という記述が重い。これが踏み台にされた第三者の回線であれば、国内に侵害された機器が相当数あり、それが別の国内サイトへの攻撃に使われていることになる。送信元が国内であるため、国別の遮断は効かない。同社がこの点を調べて記載したこと自体は価値があるが、性質（踏み台か否か）が示されていないため、読者は対策に繋げられない。

第六に、記録として残っていないことの問題。本記録の作成者は、同社サイトのお知らせ一覧を全件たどっても2026年9月28日の公表を見つけられなかった。報道には残り、当事者のサイトには残っていない。公表は出した時点ではなく、後から探せる状態になって初めて機能する（本記録の評価）。

malfunction2026年9月26日23時頃から9月27日13時15分頃まで、サイトが正常に表示されなかった。 商品検索に送り込まれた特殊な文字列によりデータベースで極端に重い処理が発生し、 他の処理を長時間待たせたことで、サイト全体が応答できない状態になった。 特定のページではなくサイト全体が対象である
cause_statement「9月25日から外部の自動攻撃ツールによる不正アクセスの試行（SQL インジェクション）が 集中的に行われており、件数は約1万件、国内の100以上の回線を経由していた。 9月26日午後10時50分頃には、攻撃の一環として商品検索に特殊な文字列が送り込まれ、 データベースで極端に重い処理が発生したことで、他の処理を長時間待たせることとなり、 サイト全体が応答できない状態となった」（同社の説明。ScanNetSecurity の報道による）。 攻撃はいずれもシステムにより拒否または無効化されたとされ、 SQL インジェクションの成立による侵害は確認されていない
復旧状況2026年9月27日13時15分頃に障害は解消した。 覚知の時刻、復旧のために行った操作、約14時間を要した理由はいずれも公表されていない。 本記録の作成者が2026年10月16日に確認した時点で、サイトは正常に稼働していた

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
無効化された攻撃が、検索窓を通ってデータベースの待ち行列でサイト全体を止めた経路
layer 0 は攻撃者と、経由した国内100以上の回線。layer 1 は通ってきた入口（Web サーバと商品検索）。 layer 2 はデータベースで、ここで「注入としては無効化されたが、処理としては重かった」という 分岐が起きている。layer 3 は結果——サイト全体の応答不能と、到達されなかった顧客情報。 layer 4 は障害後に追加された2つの歯止め。 点線で示すべきは、無害化の仕組みが layer 2 の左側（注入）だけを止め、 右側（負荷）を素通りさせたという構造である。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
障害の事実だけでなく、攻撃の件数（約1万件）、経由した回線の数（国内100以上）、 引き金となった時刻（9月26日22時50分頃）、および実施した対策2点を具体的に公表した機能した本記録の作成者の評価である。この規模の事業者の障害告知としては具体性が高い。 とくに対策を「データベース側」「Web サーバ側」と層に分けて書いており、 読者が自社に移し替えられる形になっている。 一方、攻撃に使われた文字列の性質（なぜ無効化されたのに重かったのか）が 示されていないため、最も実用的な部分が欠けている
再発防止として、入口の遮断より先にデータベース側の処理時間の上限（60秒）を挙げた部分的に機能本記録の作成者の評価である。上限時間を先に置いた判断は、 攻撃の種類に依存しない分だけ筋が良い。 ただし60秒では利用者から見たサイトは既に「止まっている」状態であり、 接続数の上限や1送信元あたりの要求速度の制限と組み合わせる必要がある。 これらへの言及は無い
CISO・経営層への示唆
  • SQL インジェクション対策は「漏れない」ことを保証するが、「落ちない」ことは保証しない
    本件では攻撃がいずれも拒否または無効化され、データ取得の形跡も無かった。 それでもサイトは約14時間15分止まった
    取るべき行動 自社の公開サービスについて、情報漏えいのリスク評価とは別に 「可用性のリスク評価」を行う。攻撃の試行が成立しなくてもサービスが止まる経路 （重い検索・重い集計・大きいファイルの生成）を洗い出し、 それぞれに上限を設けているかを確認する
  • 「攻撃を防いだ」で終わらせず、「なぜ止まったのか」を説明に含める
    同社の公表は、攻撃が無効化されたことと重い処理が発生したことを並べているが、 両者の関係を説明していない。読者が最も学べる部分が欠けている
    取るべき行動 障害の公表文に「防げたこと」と「防げなかったこと」を別の見出しで書く様式にする。 攻撃を受けた事案では、攻撃の成否と障害の発生を分けて記述する
  • 公表は、後から探せる状態になって初めて機能する
    本記録の作成者は、同社サイトのお知らせ一覧を全件たどっても 2026年9月28日の当該公表を発見できなかった。報道にのみ残っている状態である
    取るべき行動 障害・インシデントの公表を、商品告知とは別の固定の場所（「お知らせ」ではなく 「重要なお知らせ」等）に掲出し、一覧から恒久的に辿れるようにする。 掲出期間を決める場合は、その方針を明示する
  • 小規模な EC ほど、1つの機能の停止が売上の全停止に直結する
    本件はサイトの一部ではなく全体が応答できない状態になり、 深夜から翌日の昼過ぎまで約14時間続いた
    取るべき行動 自社 EC の停止1時間あたりの機会損失を概算し、 許容できる停止時間を経営として決める。 その時間内に復旧できる体制（覚知の手段・連絡先・夜間の対応）があるかを確認する
セキュリティ技術者への示唆
  • データベースの処理時間に上限を設ける。これが攻撃の種類に依存しない唯一の対策である
    同社は対策の第一にデータベース側の上限時間（60秒）を挙げている。 入口の遮断は既知の文字列にしか効かないが、上限時間は未知の重い処理にも効く
    取るべき行動 データベースの文の実行時間に上限を設定する （PostgreSQL・MySQL とも、文単位の実行時間上限を設定する機能がある）。 値は平常時のクエリ実行時間の分布を測ってから決める。 アプリケーション側の接続にも同じ上限を入れ、二重にする
  • 検索窓に「最悪の入力」を投げて、実行時間を測っておく
    脆弱性診断は注入が通るかを見るが、処理を重くできるかは見ないことが多い。 本件は診断で指摘されない種類の弱点でサービスが止まった
    取るべき行動 自社の検索機能に対し、長い文字列・先頭ワイルドカード・複数条件の組み合わせ・ ヒット件数が極端に多い語を投げ、実行時間を測る。 最悪値が許容時間を超える条件を特定し、入力長や条件数の制限を設ける
  • 1送信元あたりの要求速度に上限を設ける。国内からの攻撃には国別遮断が効かない
    試行は約1万件、国内の100以上の回線を経由していた。 送信元が国内であるため、国・地域による遮断では止まらない
    取るべき行動 Web サーバまたはその前段で、1送信元あたりの要求速度に上限を設ける。 検索など負荷の高いエンドポイントには、より厳しい上限を個別に設定する。 閾値は平常時の実測から決め、正当な利用を阻害しない水準にする
  • データベースの接続数に上限を設け、1つの機能が全接続を占有しないようにする
    本件では重い処理が「他の処理を長時間待たせる」ことでサイト全体が応答不能になった。 重いクエリが接続を抱えたまま解放しなかった構図である
    取るべき行動 接続プールの上限を設定し、検索など重い処理の同時実行数を別枠で制限する。 上限に達したときに全体を止めず、その機能だけを縮退させる設計にする
  • 外形監視でサイトの応答を常時測り、夜間でも通知が届くようにする
    障害は深夜23時頃に始まり、復旧は翌日13時15分頃だった。 覚知の時刻は公表されていないが、約14時間という長さは 夜間の覚知が遅れた可能性を示唆する（本記録の評価）
    取るべき行動 外部からの定期的な応答確認（トップページと検索結果ページの両方）を設定し、 連続で失敗したら夜間でも担当者へ通知する。 通知の到達を月1回のテストで確認する
