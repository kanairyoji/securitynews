公表によれば、同社の会員情報管理システムが2026年10月9日（金）10時頃から第三者の不正アクセスを受け、会員情報を取得する API が不正に利用されて、登録されていた会員情報2251万9960件が外部へ流出した可能性があります。同社は10月13日（火）9時頃に不正アクセスを確認し、同日13時36分までに封じ込めを完了しました。

対象項目は会員ごとに異なりますが、メールアドレス・パスワード・氏名・住所・電話番号・生年月日・性別・会社名・部署名・役職名、およびサービス登録日やログイン日などのシステム固有の識別情報が含まれます。クレジットカード情報は対象システムに保存しておらず対象外です。同社は全会員のパスワードを変更済みで、従来のパスワードは使えず、ログイン時の再設定を求めています。個人情報保護委員会への報告は10月15日に完了し、所轄警察署への被害申告は10月16日（金）に行う予定としています。

本件の要点は、侵害が4日間続いたことではなく、2251万件を読み出せる API が外から叩ける状態にあり、その大量読み出しが4日間検知されなかったことです。しかも流出項目にパスワードが含まれており、パスワードを「取り出せる形」で持っていた可能性が残ります（保存形式は公表されていません）。事実と評価は分けて記述します。

4日間で2251万件が読み出されるまで、大量読み出しが検知されなかった評価・解釈出典 [1]

ここからは本記録の作成者の評価である。

第一に、問われているのは侵入の入口よりも API の設計である。 同社の説明は「会員情報を取得する API が不正に利用された」であり、窃取は画面操作ではなく API 経由で行われている。2251万件規模のデータを外部から取得できる API が存在し、かつ取得量に制限がかかっていなければ、入口がどこであれ同じ結果になる。1リクエストあたりの件数上限、呼び出し元ごとのレート制限、1日あたりの累積取得量の上限は、侵入を防ぐ対策とは別に置かれるべき層である。

第二に、4日間（10月9日10時頃〜10月13日9時頃）気づかなかったという事実は、「大量読み出しの検知が無かった」ことを意味する。 通常の利用で会員情報 API が数百万件単位で呼ばれることはないはずで、ベースラインからの乖離は検知しやすい種類の異常である。検知が利用者からの申告や外部指摘ではなく自社の確認だった点は公表文から読み取れるが、何をきっかけに確認に至ったかは示されていない。

第三に、流出項目にパスワードが含まれる重さである。 API を通じて取得できたのであれば、パスワードが取り出せる形（平文または可逆な暗号化）で保持されていた可能性が残る。強いハッシュで保存されていれば「パスワードのハッシュ」と表現されることが多く、公表文はこの点に触れていない。保存形式が明らかにならない限り、会員は「他のサービスで使い回したパスワードはすでに攻撃者の手にある」前提で動くほうが安全である。

第四に、氏名・住所・電話番号・生年月日・メールアドレスに会社名・部署名・役職名が加わる組は、標的型のフィッシングにそのまま使える。 同社はソフトウェアの販売事業者であり、「購入製品のライセンス更新」「請求に関する確認」を装う文面が成立する。法人の担当者情報が含まれる点は、個人向けサービスの漏えいよりも悪用の射程が広い。

【続報】窓口が電話まで輻輳している——「全員に一斉に行動を促す」ことの代償組織の対応出典 [1] [4]

@IT は、パスワード再設定サイトだけでなく専用のコールセンターにもアクセスが集中し、電話もつながらない状態であると報じている（出典4）。一次公表の本文にも、パスワード再設定サイトが「つながりにくい状況」である旨の案内がある（本記録の作成者が10月17日に確認。T14）。

これは対応の失敗というより、取った措置の構造的な代償である（本記録の評価）。同社は対象の特定を待たず全会員のパスワードを一括無効化した（本記録の response 節）。流出項目にパスワードが含まれる以上、これは最も強い措置であり、判断としては支持できる。ただし全会員のパスワードを同時に無効化すれば、全会員が同時に再設定に来る。2251万件規模では、再設定基盤と問い合わせ窓口が同時にピークを迎えることは設計上わかっていたはずである。

パスワードは暗号化されていたが、復号鍵に手が届く API が破られ、平文で流出した原因・手口出典 [5]

2026年10月19日、同社広報担当者が ITmedia NEWS の取材に答え、本記録が初報から未確定としていた「パスワードの保存形式」を説明した。説明は次の3つに分かれる。

  • 「パスワードは暗号化して保存していた」
  • 「暗号化されたパスワードを復号するための鍵にアクセス可能なシステム（API）に対して、不正アクセスが行われた」
  • 「復号鍵そのものは流出していないが、パスワードが復号された状態で外部に流出したことを確認している」

つまり、攻撃者は平文のパスワードを得ている。「暗号化していた」という説明と「平文で流出した」という事実は矛盾しない—— 可逆な暗号化は、復号鍵に手が届く立場を取られた時点で平文と等価になる。ハッシュ化（一方向の変換）であればこうはならず、鍵を奪われてもパスワードそのものは復元できない。本件が示したのは「暗号化している」という言葉が、保存形式の安全性を何も保証しないということである（本記録の評価）。

ハッシュ化していなかった理由についての説明は、次のとおりである。

当該システムは開発時期が古く、当時採用した暗号化方式を継続して使用していた。結果として、最新のハッシュ化方式への移行ができていなかった。

具体的な開発時期は明らかにされていない。この説明は、原因を「選択」ではなく「移行の未完了」として述べている——本記録は原因軸に移行の失敗（migration-failure）を追加した。

ここから、攻撃の形が初報より具体的に見えてくる（以下は本記録の整理）。初報の段階では「会員情報を取得する API が不正に利用された」までしか分からず、その API が何を返していたのかは不明だった。今回の説明は、破られた API が復号鍵にアクセスできる立場にあったことを明らかにしている。すなわち、攻撃者が得たのは暗号文の山ではなく、復号された会員情報そのものである。

ただし、肝心の点は依然として開示されていない。「API の戻り値に平文のパスワードが載っていたのか」である。同社は API の役割について「個別の実装の詳細は、新たな攻撃を助長するおそれがあるため」回答を控えた。この点は次節に記す。

「正式な回答とは異なる」とだけ述べ、どこが違うかは説明されなかった未確定事項出典 [5]

API の戻り値にパスワードが含まれていた理由について、同社は一部メディア（Yahoo!ニュース／山口健太氏の記事）に対し、「ライセンス管理システムとの連携など、パスワードが必要な作業で使うため」と回答したとされる。

ITmedia がこの内容をただしたところ、同社は「当社が確認を経てお伝えした正式な回答とは異なるもの」と述べた。ただし、どの部分が「正式な回答と異なる」かは説明していない。あわせて「API の具体的な利用目的やシステム間の連携状況は現在、関係機関による捜査・調査に協力していることから、詳細な回答を差し控える」とした。

この否定の仕方には問題がある（本記録の評価）。「異なる」とだけ言って差異を示さないと、読者には①そもそもその回答をしていないのか、②内容は近いが表現が違うのか、③事実として誤っているのかが区別できない。結果として、流通している説明を訂正する効果を持たないまま、その説明の信頼性だけが下がる。

本記録はこの件を「発表間の食い違い」として齟齬に残し、「API の戻り値に平文のパスワードが載っていたか」を確定事項として扱わない。これは本件の設計上の論点の中心であり、API の認可の不備なのか、そもそも戻り値の設計が誤っていたのかの判断が、この一点に依存している。

非開示の範囲は、ほかにも広い。

  • 再設定後のパスワードの管理方法（ハッシュ化の有無）——「システムのセキュリティ確保の観点から、回答を差し控える」
  • 会員情報取得 API の役割——「新たな攻撃を助長するおそれがあるため」
  • 実施済みのセキュリティ対策の内容——「新たな不正アクセスを助長するおそれ」

②と③を非開示とする判断には理由がある。手口と防御の詳細は、同じ手が通る段階では公表が次の被害を生む。

一方で①は性質が違う（本記録の評価）。会員は全員がパスワードを再設定させられており、その新しいパスワードが今回と同じ形（可逆な暗号化）で保持されているのかを知る手段が無い。 「今回と同じことが起きたらまた平文で流出するのか」は、再設定に応じる会員が当然に知りたい点である。ハッシュ方式の名称を明かさずに「一方向のハッシュ化に移行した」とだけ述べることは技術的に可能であり、非開示が会員の判断材料まで巻き込んでいる。

侵害の開始時刻が後から分単位で特定できていることから記録は残っていたが、 開始から確認までに約4日を要した
侵入を防げた会員情報 API の呼び出し元を事前登録した経路（自社フロントエンド・IP・mTLS クライアント証明書）に限定し、 インターネットから直接到達できないようにする
侵入を防げた管理・API 用の認証情報に多要素認証と短期トークンを適用し、長期有効な API キーを廃止する
検知できた認証失敗・異常な認証成功（深夜・海外・新規 IP）の相関検知を監視対象に入れる
内部探索公表されていない
API の列挙・探索行為を検知できたかは公表されていない
侵入を防げたAPI の完全な一覧（棚卸し）を維持し、未使用・テスト用・旧版のエンドポイントを廃止する
侵入を防げた認可をエンドポイント単位ではなくレコード単位で検証し、他人のレコードを取得できないようにする
収集機会はあったが検知できず
2251万件規模の読み出しは通常の利用とかけ離れた量であり、 件数・レートの監視があれば検知できた見込みだが、4日間続いた
影響を限定できた1リクエストあたりの取得件数上限と、呼び出し元ごとの時間・日次の累積取得量上限を API に実装する
検知できた会員データベースの大量読み出し（通常のベースラインからの乖離）を秒単位・分単位で検知してアラートする
影響を限定できたパスワードを計算量の大きいハッシュ（bcrypt・scrypt・Argon2）で保存し、API の応答に含めない
持ち出し機会はあったが検知できず
確認は10月13日9時頃で、持ち出しの進行中には検知されなかった
影響を限定できた外向き通信の宛先をデフォルト拒否で制御し、許可した宛先以外への大量送信を遮断する
影響を限定できたAPI の応答サイズ・総転送量を監視し、閾値超過で自動的にトークンを失効させる

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
対象会員を特定して部分的に再設定を促すのではなく、全会員のパスワードを変更（無効化）し、 ログイン時の再設定を必須にした機能した本記録の作成者の評価である。流出項目にパスワードが含まれ、かつ保存形式が公表されていない状況では、 一括無効化は妥当な判断である。混雑は想定できた副作用であり、 再設定基盤の容量を事前に見積もる余地があった
確認（10月13日）から2日後の10月15日に公表し、同日に個人情報保護委員会への報告を完了した機能した本記録の作成者の評価である。件数・項目・侵害時刻を具体的に示しており、 初報として読者が行動できる水準にある
件数・項目・侵害時刻・封じ込め時刻・当局報告の状況は示したが、 パスワードの保存形式、API が不正利用できた経緯、実際の窃取量は示さなかった部分的に機能本記録の作成者の評価である。パスワードが対象に含まれる事案では、 保存形式は会員の行動を左右する情報であり、続報での説明が要る
CISO・経営層への示唆
  • 会員データベースの「一括取得できる経路」を資産として棚卸しし、経営レベルで上限を決める
    本件の窃取経路は画面操作ではなく「会員情報を取得する API」であり、 2251万件規模が外部から取得できる状態だった
    取るべき行動 顧客データを一括で返せる API・バッチ・管理機能を全件リスト化し、 「1回で取得できる上限」「1日で取得できる上限」を業務要件から決めて実装させる。 上限を超える取得は人の承認を必須にする
  • パスワードを「取り出せる形」で持っていないかを、事故の前に確認しておく
    流出項目にパスワードが含まれ、保存形式が公表されていないため、 会員は使い回しパスワードが使われる前提で動かざるを得ない
    取るべき行動 自社の全サービスについてパスワードの保存方式（アルゴリズム・ソルト・ストレッチ回数）を一覧化し、 可逆な保持をしているシステムを期限付きで移行させる。公表時に説明できる形で記録を残す
  • 「全会員の認証情報を一括で無効化する」判断を、事前に決めて訓練しておく
    同社は対象の特定を待たず全会員のパスワードを変更したが、再設定サイトが混雑した
    取るべき行動 一括無効化の発動条件（流出項目にパスワードが含まれる等）と承認者を規程に書き、 再設定基盤が全会員の同時アクセスに耐えるかを負荷試験で確認する。 問い合わせ窓口の増強も同じ手順に組み込む
  • 法人の担当者情報を含む会員 DB は、個人向けよりも悪用の射程が広いと評価する
    流出項目に会社名・部署名・役職名が含まれ、業務を装ったフィッシングが成立する
    取るべき行動 顧客 DB に法人属性が含まれるかを棚卸しし、含まれる場合は取引先への注意喚起と、 自社名を騙るメールの見分け方（送信ドメイン認証の公表）をインシデント手順に入れる
セキュリティ技術者への示唆
  • 会員情報 API にレート制限と取得量上限を実装する
    API 経由で2251万件規模が取得され、4日間止まらなかった
    取るべき行動 1リクエストあたりの最大件数（例: 100件）、呼び出し元ごとの分・時・日の累積上限、 カーソルページングの総ページ数上限を実装する。上限到達時はトークンを自動失効させる
  • 大量読み出しを「秒・分単位」で検知する仕組みを置く
    2251万件の読み出しは通常の利用から大きく外れるが、4日間検知されなかった
    取るべき行動 API ごとに平常時のリクエスト数・応答件数・転送量のベースラインを取り、 乖離（例: 平常の10倍）でアラートする。列挙・連番アクセス・同一トークンからの大量取得を個別ルールにする
  • API を外部から直接叩けないようにし、認可をレコード単位で検証する
    「会員情報を取得する API が不正に利用された」とされ、 外部の第三者が到達できる位置にあったことになる
    取るべき行動 会員情報 API は自社フロントエンド・特定 IP・mTLS に限定し、 認可はエンドポイント単位ではなく「要求者が当該レコードの本人か」をレコード単位で検証する。 管理用 API は管理ネットワークに閉じる
  • パスワードは API の応答に載らない形で保存・設計する
    流出項目にパスワードが含まれており、API の応答に含まれていた可能性が残る
    取るべき行動 パスワードは bcrypt・scrypt・Argon2 で保存し、シリアライザから恒久的に除外する。 レスポンスに機微項目が混入しないことを自動テストで検証し、CI で落とす
  • API の棚卸しを続け、使われていないエンドポイントを廃止する
    窃取に使われた API の素性（現行機能か旧版か）は公表されていないが、放置 API は同種事故の常である
    取るべき行動 API ゲートウェイのアクセス記録から「定義されているが呼ばれていない」エンドポイントを抽出し、 四半期ごとに廃止判断を行う。テスト用・移行用の経路は期限を決めて削除する

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 会員・顧客情報を一括で取得できる API やバッチ出力の経路がある本件の窃取経路は「会員情報を取得する API」であり、2251万件規模が対象になった
認証・認可□ API の認可がエンドポイント単位で、レコード単位の本人確認を行っていないAPI を叩ける立場になれば他人のレコードも取得できる作りだと、1件の侵害が全件の流出になる
データの保持□ パスワードを平文または可逆な暗号化で保持している、または保存方式を把握していない本件は流出項目にパスワードが含まれ、保存形式が公表されていないため会員のリスク評価ができない
運用・監視□ API の呼び出し件数・応答件数・転送量のベースラインを取っておらず、大量読み出しのアラートが無い本件は4日間（10月9日〜13日）にわたる大量読み出しが検知されなかった
運用・監視□ 全会員のパスワードを一括で無効化した場合に、再設定基盤と問い合わせ窓口が同時アクセスに耐えるか試していない同社は一括変更を行ったが、再設定サイトが混雑し10月16日に追記で案内する事態になった
体制・契約□ 顧客 DB に法人の会社名・部署名・役職名が含まれており、取引先を装う攻撃に転用されうる本件の流出項目には法人属性が含まれ、業務メールを装ったフィッシングが成立する
