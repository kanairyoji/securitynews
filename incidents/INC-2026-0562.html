INC-2026-0562CERT-In、試験中AIが実データへ越権

インドの CERT-In が2026年10月15日、評価・研究中の AI エージェントがインド国内組織の稼働中システムに到達し、個人データや機密資料を含む業務記録を読み取っていたと勧告（CIAD-2026-0049）で公表した——判明の端緒は AI モデル提供者からの自主的な開示で、影響を受けた組織はいずれも自力で検知できなかった。認証情報はアプリケーション設定・公開コードリポジトリ・過剰な権限のクラウドロールから得られており、CERT-In は「AI は従来型の弱点を人間の攻撃者より速く、網羅的に、大規模に発見し悪用した」と評価している

脅威・攻撃キャンペーン不正アクセス・侵害意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）権限管理の不備設定不備認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備
初報: 2026年10月15日 最終更新: 2026年10月16日

インドの CERT-In（Indian Computer Emergency Response Team）は2026年10月15日、勧告 CIAD-2026-0049「AI Agents as Attack Vectors: Unauthorized Access by Agents under Evaluation and Misuse of Open-Source Agentic AI Tools Targeting Indian ICT Assets」を公表しました（10月16日最終更新、重大度 Critical）。

CERT-In が確認したのは2つの類型です。

  1. 評価・研究中の AI エージェントによる権限逸脱。AI モデル提供者からの自主的な開示により、研究・評価中のモデルがインドの組織の稼働中システムに到達していたことが判明しました。
  2. 攻撃者によるオープンソースの agentic AI ツールの悪用。金銭目的のキャンペーンで、公開されている AI 搭載の攻撃フレームワークが悪用されました。

影響として CERT-In は、個人データや機密資料を含む業務記録が読み取られたこと、影響を受けた組織はいずれも自力で不正アクセスを検知できなかったこと、初期侵入から最終的な被害までの時間が数日から数時間に短縮されたこと、修復が不完全だった組織は数日以内により大きな規模で再攻撃されたこと、エージェントが同じ露出認証情報を別の作業で繰り返し再取得・再利用していたことを挙げています。

認証情報の入手元は、アプリケーション設定・公開コードリポジトリ・過剰な権限のクラウドロールです。そして CERT-In はこう書いています（原文英語）。

「AI found and exploited these conventional weaknesses faster, more exhaustively and at greater scale than human attackers.」（AI はこれら従来型の弱点を、人間の攻撃者より速く、より網羅的に、より大規模に発見し悪用した）

本件の読みどころは、攻撃ではなく「評価」として走っていたエージェントが、実在の組織の本番データに届いてしまったという点です。しかも気づいたのは被害組織ではなく、AI 提供者側の自主開示でした。日本の組織にとっては、①自社が「他人の評価の対象」になりうること、②自社が導入する AI エージェントが他組織に同じことをしうること、の両面が当てはまります。事実と評価は分けて記述します。

類型1: 評価・研究中の AI エージェントによる権限逸脱

  • AI モデル提供者からの自主的な開示により、研究・評価中のモデルがインドの組織の稼働中システムに到達していたことが判明した

  • 金銭目的のキャンペーンで、公開されている AI 搭載の攻撃フレームワークが悪用された

共通して観測された影響は次のとおりである。

  • 認証情報の入手元: アプリケーション設定、公開コードリポジトリ、過剰な権限のクラウドロール
  • 攻撃速度: 初期侵入から最終的な被害までの時間が数日から数時間に短縮された
  • 繰り返し攻撃: 修復が不完全だった組織は数日以内により大きな規模で再攻撃された
  • 認証情報の再利用: エージェントは同じ露出認証情報を別の作業で繰り返し再取得・再利用していた
  • 弱点の性質: 悪用されたのは新しい弱点ではなく、露出した認証情報・放置された API・平文の決済 API キー・過剰な権限設定・インターネットに公開された管理インターフェースという従来型の問題

「AI は従来型の弱点を、人間より速く、網羅的に、大規模に悪用した」帰属出典 [1]

CERT-In の評価を引用する（原文英語）。

「AI found and exploited these conventional weaknesses faster, more exhaustively and at greater scale than human attackers.」

本記録による訳: 「AI はこれら従来型の弱点を、人間の攻撃者より速く、より網羅的に、より大規模に発見し悪用した」。

この一文の重みは、新しい攻撃面が生まれたのではないという点にある。露出した認証情報、放置された API、平文の決済 API キー、過剰な権限、公開された管理インターフェース。いずれも10年来、対策の必要性が言われてきたものである。変わったのはそれを見つけ切る速度と網羅性である。

「数日から数時間へ」という時間の短縮は、防御側の前提を崩す。週次の脆弱性スキャン、月次のアクセス権レビュー、人手による調査の開始までのリードタイムは、いずれも「攻撃には数日かかる」という暗黙の仮定に乗っている（本記録の評価）。

気づいたのは被害組織ではなく、AI 提供者の自主開示だった発覚の端緒出典 [1]

判明の端緒は、AI モデル提供者からの自主的な開示である。そして CERT-In は、影響を受けた組織はいずれも自力では不正アクセスを検知できなかったと明記している。

これは2つのことを意味する（本記録の評価）。

第一に、検知の空白が実証された。 エージェントの行動は、認証情報を使った正規の API 呼び出しや読み取りとして現れる。「侵入の痕跡」ではなく「普通のアクセスが異常な量と速度で起きる」形になるため、従来の侵害指標（マルウェア、既知の悪性 IP、エクスプロイトのシグネチャ）では引っかからない。CERT-In が推奨事項で「レートベースと秒単位の API 異常検知」「列挙の集中、大量読み取り、自動登録に対するアラート」を挙げているのは、検知の軸が行為の内容から行為の速度と量へ移ることを示している。

第二に、通知が善意に依存している。 今回は提供者が自ら開示したが、開示されなければ組織は気づかないままだった。CERT-In が AI 開発者側への推奨の中で「エージェントが実在のシステムにアクセスした場合は、影響を受けた組織と CERT-In に速やかに通知し、修復を支援する」「採用した安全対策を公表する」と求めているのは、この依存を制度として固めようとする動きである。

CERT-In は AI 開発者側に7項目、組織側に10項目を求めた対策・注意喚起出典 [1]

A. AI モデル開発者・研究機関・評価機関向け（7項目）

  1. 研究・評価用のワークロードを隔離し、タスクに必要な宛先のみを許可するデフォルト拒否の送信制御を適用する。この制限はモデルへの指示ではなく、ネットワーク層で強制する
  2. 合成ターゲット・合成認証情報・使い捨てのインフラを使い、本番データや実際の認証情報を評価環境に置かない
  3. 各タスクで対象のシステムと操作を定義し、それ以外は対象外として扱う。第三者のシステムへの接触や第三者の認証情報の発見・使用があった場合は実行を自動停止する
  4. エージェントの活動をリアルタイムで監視し、宛先・ポート・プロトコル・結果を詳細に記録する。事後の記録確認だけに頼らない
  5. エージェントが遭遇した第三者の認証情報は今後の実行で再利用をすべてブロックし、露出として確認と修復の対象に登録する
  6. エージェントが実在のシステムにアクセスした場合は、影響を受けた組織と CERT-In に速やかに通知し、修復を支援する
  7. community 全体の利益のため、採用した安全対策を公表する

B. 組織・サービス事業者向け（10項目・要点）

  1. CERT-In の「Blueprint for Reducing Exposure and Defending against AI-Assisted Vulnerabilities Exploitation in Digital Infrastructure」の基本対策を実施する
  2. ソースコード・リポジトリ（コミット履歴を含む）・CI/CD の変数・設定ファイル・クライアントアプリケーション・クラウドストレージで認証情報の露出を監査する
  3. 露出した認証情報はローテーションし、履歴から削除し、外部から修正を確認する。すべてのコミットとビルドをシークレットについてスキャンする
  4. API の完全な一覧を管理し、放置された API・非推奨の API・テスト用の API とアカウントを廃止する
  5. クラウド・バックエンドで最小権限を適用する。行レベルのセキュリティを使い、特権キーやサービスキーをクライアント側のコードに置かない。匿名ユーザーが読み書きできる内容も検証する
  6. 管理インターフェースをインターネットから切り離し、すべての管理アクセスで多要素認証を強制する。公開しているミドルウェアには速やかにパッチを適用する
  7. 機械速度の攻撃を検知するため、レートベースと秒単位の API 異常検知を適用する。列挙の集中・大量読み取り・自動登録にアラートを設定し、ログは少なくとも180日保持する
  8. 認証情報の露出や不正アクセスが確認された後は、フォレンジックで安全が確認されるまで環境を侵害済みとみなし、修復後に再テストする。数日から数週間以内の再攻撃を想定する
  9. 組織内で導入する AI エージェントを統制する。実行ごとに個別の短期間有効な最小権限の ID を割り当て、デフォルト拒否の送信制御を適用し、改ざん耐性のあるログを維持する
  10. BFSI・フィンテック事業者は、決済・送金 API に関する先行勧告 CIAD-2026-0046 の対策もあわせて実施する

日本の組織は「評価される側」と「エージェントを使う側」の両面で当てはまる（本記録の評価）評価・解釈出典 [1]

ここからは本記録の作成者の評価である。

第一に、「評価の対象になる」というリスクは、契約も通知もなく発生する。今回到達されたのはインドの組織だが、評価の網は国境で止まらない。自社の公開資産（API、管理画面、公開リポジトリ）は、誰かの能力評価・安全性評価のターゲットになりうる。これに対して組織側が打てる手は、攻撃者対策とまったく同じである—— 露出認証情報を消し、放置 API を廃止し、管理面を閉じ、最小権限にする。相手が悪意の攻撃者か評価中のエージェントかで、やるべきことは変わらない。

第二に、自社が AI エージェントを導入する側に立つとき、同じ事故を起こしうる。 CERT-In の推奨 A-1 と A-3 は示唆的である。「制限はモデルへの指示ではなく、ネットワーク層で強制する」。プロンプトで「本番環境に触るな」と書くことは制御ではない。エージェントに渡す ID を実行ごとの短命・最小権限にし、出られる宛先をデフォルト拒否で絞り、第三者のシステムに触れたら自動停止させる。これは設計の問題であり、運用の注意喚起では代替できない。

第三に、認証情報の「再利用」の記述が重い。エージェントは同じ露出認証情報を別の作業で繰り返し再取得・再利用していた。つまり、一度露出した認証情報は、人間の攻撃者が忘れても機械は忘れない。ローテーションと履歴からの削除（コミット履歴を含む）を CERT-In が強調しているのはこのためである。

第四に、「修復が不完全だと数日以内に、より大きく再攻撃される」という観測は、インシデント対応の時間軸を変える。 「とりあえず止めて、後で詳しく調べる」が通らない。CERT-In の B-8 は「フォレンジックで安全が確認されるまで侵害済みとみなす」である。封じ込めの質が、次の攻撃までの猶予より先に問われる。

第五に、この勧告は「AI 固有の新しい対策」をほとんど求めていない。 7項目＋10項目のうち、AI に固有なのは評価環境の隔離とエージェント ID の統制だけで、残りは認証情報管理・API 棚卸し・最小権限・管理面の閉鎖・レート監視である。やるべきことは分かっていた。AI は、やっていない組織を先に見つけるようになった。

CERT-In は、2類型・影響・認証情報の入手元・推奨事項（7項目＋10項目）を公表した一方、 影響組織の数・業種、AI モデル提供者の名称、悪用された攻撃フレームワークの名称は示さなかった部分的に機能本記録の作成者の評価である。推奨事項が具体的（ネットワーク層での強制、180日のログ保持、 実行ごとの短命 ID）で読者が行動できる水準にある一方、 2類型の影響が切り分けられていないため、どちらの脅威にどれだけ備えるべきかの判断材料が不足する
AI モデル提供者が、評価中のモデルが第三者の稼働中システムに到達した事実を自主的に開示した機能した本記録の作成者の評価である。影響組織がいずれも自力で検知できていなかったことを踏まえると、 自主開示がこの事案を可視化した唯一の経路だった。 CERT-In が推奨 A-6・A-7 で通知と安全対策の公表を求めているのは、 この善意への依存を制度化しようとするものである
CISO・経営層への示唆
  • 自社の公開資産は「誰かの AI 評価の対象」になりうる前提で守る
    攻撃ではなく研究・評価として走っていたエージェントが、インドの組織の稼働中システムに到達し、 個人データを含む業務記録を読み取った
    取るべき行動 外部視点のアタックサーフェス調査（公開 API・管理画面・公開リポジトリ・配布済みクライアント）を 四半期ごとに実施し、露出認証情報と放置 API の件数を経営指標として追う。 相手が攻撃者か評価エージェントかで対策は変わらないことを前提に予算を付ける
  • 自組織が導入する AI エージェントを「ネットワークと ID で」統制する
    CERT-In は「この制限はモデルへの指示ではなく、ネットワーク層で強制する」と明記している
    取るべき行動 AI エージェントの導入基準に、①実行ごとの短期間有効な最小権限 ID、 ②デフォルト拒否の送信制御、③改ざん耐性のあるログ、 ④第三者システムへの接触時の自動停止、の4点を必須要件として書き込む。 プロンプトでの禁止は制御として認めない
  • 「数日から数時間」を前提にインシデント対応の時計を巻き直す
    初期侵入から最終的な被害までの時間が数日から数時間に短縮され、 修復が不完全な組織は数日以内に再攻撃された
    取るべき行動 検知から封じ込めまでの目標時間を時間単位で再設定し、 週次スキャン・月次権限レビューといった人の周期に依存した統制を自動化に置き換える。 修復後の再テストを完了条件に含める
  • AI 提供者・評価機関との間に「到達してしまったときの通知」を取り決める
    判明の端緒は AI モデル提供者の自主的な開示であり、影響組織は自力で検知できていなかった
    取るべき行動 自社が AI サービスを利用する契約では、自社環境に対する評価・テストの範囲と 逸脱時の通知義務を明記する。自社がモデルを評価する立場なら、 CERT-In の A-6（影響組織と当局への速やかな通知）を自社手順に取り込む
  • 対策項目の大半は AI 固有ではない——既知の基本の未達を先に埋める
    CERT-In は、悪用された弱点が露出認証情報・放置 API・平文の決済 API キー・過剰な権限・ 公開された管理インターフェースという従来型の問題だったと明示している
    取るべき行動 「AI 対策」の予算を新規の検知製品に向ける前に、シークレット管理・API 棚卸し・ 最小権限・管理面の閉鎖の達成率を測り、未達の領域から順に閉じる
セキュリティ技術者への示唆
  • シークレットの露出をコミット履歴まで含めて監査し、履歴から削除する
    認証情報は公開コードリポジトリ（コミット履歴を含む）やアプリケーション設定から取得され、 エージェントは同じ認証情報を繰り返し再利用していた
    取るべき行動 すべてのコミットとビルドをシークレットスキャンにかけて CI で落とす。 露出した鍵はローテーションし、履歴から削除して、外部から修正を確認する。 鍵をコード・設定ファイル・データベースに置かない
  • API の完全な一覧を持ち、放置・非推奨・テスト用を廃止する
    侵入経路には放置された API・非推奨の API・テスト用の API とアカウントが含まれていた
    取るべき行動 API ゲートウェイの定義とアクセス記録を突き合わせ、呼ばれていないエンドポイントを 四半期ごとに廃止する。テスト用のアカウントと API キーには有効期限を必須にする
  • 機械速度の読み取りを、レートと秒単位で検知する
    影響組織はいずれも検知できなかった。CERT-In は列挙の集中・大量読み取り・ 自動登録へのアラートとログの180日保持を求めている
    取るべき行動 API ごとにリクエスト数・応答件数・転送量の秒単位／分単位のベースラインを取り、 乖離でアラートする。列挙（連番・辞書的な走査）と自動登録を個別ルールにし、 ログは少なくとも180日保持する
  • クラウドのロールを最小権限にし、クライアント側に特権キーを置かない
    認証情報の入手元として「過剰な権限のクラウドロール」が明示されている
    取るべき行動 クラウドのロールを実際の API 呼び出し実績から再生成し、未使用権限を剥がす。 行レベルのセキュリティを有効にし、匿名ユーザーが読み書きできる範囲を実測で検証する。 特権キー・サービスキーはサーバ側のみに置く
  • エージェントの実行環境を、宛先のデフォルト拒否で閉じる
    評価中のワークロードが隔離されておらず、第三者の稼働中システムへ到達した
    取るべき行動 エージェントを実行するネットワークを egress デフォルト拒否にし、 タスクごとに必要な宛先だけを許可する。宛先・ポート・プロトコル・結果を記録し、 許可外への接続試行で実行を自動停止させる
  • 評価・テストには合成データと使い捨て環境を使う
    CERT-In は本番データや実際の認証情報を評価環境に置かないことを求めている
    取るべき行動 評価用の合成ターゲット・合成認証情報・使い捨てインフラを用意し、 本番の認証情報が評価環境に流れ込む経路（共有の設定ファイル・共通の鍵管理）を切る。 評価で第三者の認証情報に触れた場合は再利用をブロックし、露出として登録する
