INC-2026-0563アエナ EC アプリで81.7万人分を不正閲覧

オフプライスストア「アエナ」を運営する株式会社アエナが2026年10月14日、EC アプリが第三者の不正アクセスを受け、会員のマイページが不正に閲覧されていたと公表した——システムログの解析により10月13日5時58分に判明し、対象は EC アプリ会員 最大81万7,215人。氏名・住所・電話番号・生年月日・性別・メールアドレス・職業に加え、登録済みクレジットカードの名義・番号下4桁・有効期限と、第三者宛を含むお届け先の氏名・住所・電話番号が閲覧された可能性がある。機械的な連続アクセスが確認されたが詳細な原因は調査中で、同社は EC サイトへのアクセスを遮断し、退会専用ページを開設、10月19日午後のサービス再開を予定している

化粧品・健康食品のオフプライスストアチェーン「アエナ」を運営する株式会社アエナは2026年10月14日、同社 EC アプリが第三者の不正アクセスを受け、会員のマイページが不正に閲覧されていたと公表した。発覚は 2026年10月13日（火）5時58分、システムログの解析による。

対象は EC アプリに個人情報を登録している会員 最大81万7,215人。閲覧された可能性があるのは、氏名・フリガナ・住所・電話番号・メールアドレス・生年月日・性別・職業、お届け先（第三者宛を含む）の氏名・住所・電話番号、お気に入り店舗・メール配信設定、そして登録済みクレジットカードの名義・番号下4桁・有効期限である。カード番号の全桁とセキュリティコードは同社が保持しておらず、ログインパスワードも対象外としている。

会員情報の改ざん、購入の決済、退会手続きといった不正操作は行われていないことを確認したとし、悪用や二次被害も確認されていないとする。同社は EC サイトへのアクセスを遮断し、原因の究明と改修を進めるとともに、10月16日に「EC アプリ会員 退会専用ページ」を開設、10月19日（月）午後のサービス再開を予定している。

手口の核心は公表されていない。ただし被害が「閲覧」に限られ書き込みが無いこと、「機械的な連続アクセス」が確認されたことは、他人のマイページへ順に到達できる経路があったことを示唆する（本記録の推定）。マイページには決済手段の一部が表示されるため、「カード番号を持っていない」ことは守りになったが、名義・下4桁・有効期限は本人確認を装う材料として揃っている。

第一に、被害は「閲覧」に限られている。 同社は会員情報の変更・退会手続き・購入の確定（決済）が行われていないことを確認したと明記した。つまり第三者はマイページを読めたが、書けなかったか、書く意図がなかった。

第二に、「機械的な連続アクセス」が確認されている。 これは1つのアカウントへの繰り返しログイン試行（パスワードリスト攻撃）とも読めるが、その場合は通常「一部の会員がログインされた」という形の公表になる。対象が EC アプリ会員のほぼ全数（最大81万7,215人）として示されたことは、会員を順に走査できたことを示す。

ここから本記録は、他人のマイページを識別子の付け替えだけで参照できる経路（認可の確認が欠けた API・画面）があった可能性が高いと推定する。一般にこの形は、ログイン後の画面が「要求された会員 ID のデータ」を「要求した本人のデータか」の確認なしに返すときに生じる。これは本記録の推定であり、同社は手口を公表していない。

もう一つの読み方として、窃取・使い回しの認証情報による大量ログイン（クレデンシャルスタッフィング）も排除できない。ただしその場合、成功率は通常1%未満にとどまり、対象人数が会員全数規模に達する説明がつきにくい（本記録の評価）。

いずれにせよ、判明の端緒がシステムログの解析だったことは重要である。進行中のアラートではなく、事後のログ点検で見つかっている。連続アクセスのレート監視が置かれていれば、進行中に止められた性質の事象である（本記録の評価）。

カード番号は持っていなかったが、名義・下4桁・有効期限は本人確認を装う材料として揃っている被害規模・影響範囲出典 [1]

閲覧対象の評価で最も重いのは、クレジットカード情報の一部が含まれていることである。

同社はカード番号の全桁とセキュリティコードを保持していないと明記した。これは決済代行へのトークン化が機能したことを意味し、そのままでは不正決済に使えない。設計上の最大の緩衝材である。

しかし残った3項目の組み合わせは軽くない。

  • カード名義（氏名のローマ字表記）
  • 番号の下4桁
  • 有効期限

下4桁と有効期限は、カード会社・加盟店が本人確認に使う情報そのものである。ここに氏名・住所・電話番号・生年月日が揃っているため、「お使いの ◯◯ カード（下4桁 xxxx）に不審な利用がありました」と名乗る電話や SMS が、受け手から見て検証可能な正しさを持ってしまう。同社自身も「住所やメールアドレスを悪用したフィッシングやなりすましの可能性」に言及し、「当社から、メール、SMS、電話でパスワードやクレジットカード情報をお伺いすることはございません」と明記している。想定されている悪用はこれである。

もう一つ、お届け先情報に「第三者宛を含む」と明記されている点は見落としやすい。贈答で他人の住所を登録していた場合、その第三者の氏名・住所・電話番号も閲覧対象である。その第三者は同社の会員ではないため、「対象となる可能性のある会員へ個別メール」という通知設計では届かない（本記録の整理）。

CISO・経営層への示唆
  • 「カード番号を持たない」は守りになるが、名義・下4桁・有効期限を画面に出していれば なりすましの材料は漏れる
    同社はカード番号の全桁とセキュリティコードを保持しておらず不正決済は防げたが、 マイページに表示される名義・下4桁・有効期限は閲覧対象になった。 下4桁と有効期限はカード会社・加盟店が本人確認に使う情報そのものである
    取るべき行動 自社サービスのマイページ・注文履歴・メール通知に表示している決済情報を棚卸しし、 下4桁・有効期限・名義の同時表示をやめる（「VISA ••••」のようにカード種別のみに絞る、 または再認証を経て初めて表示する）。 「持たない」の次に「出さない」を設計の基準にする
  • 閲覧だけで書き込みが無い事案は、認証の破れではなく認可の欠落を疑う
    本件は改ざん・決済・退会が行われておらず閲覧のみで、 対象が会員のほぼ全数規模に及び、機械的な連続アクセスが確認されている。 これは「他人のデータを識別子の付け替えで読める」形に特徴的である（本記録の推定）
    取るべき行動 自社の会員向け API・画面を対象に、 「要求された ID」と「認証済みセッションの ID」の一致をサーバ側で検証しているかを 全経路で棚卸しする。棚卸しの単位は画面ではなく**エンドポイント**にする。 認可の検査を共通層に寄せ、個別実装に任せない
  • サービスを止めるときは、止めている間の顧客の選択肢を同時に用意する
    同社は EC を遮断したうえで、10月16日に「EC アプリ会員 退会専用ページ」を別途開設した。 停止中は通常経路で退会できないため、不安を感じた会員が動けない状態になるのを避けている
    取るべき行動 インシデント対応計画に「サービス停止中に顧客が必要とする操作」の一覧 （退会、登録情報の削除、問い合わせ、カード登録の解除）を入れ、 本体と切り離して提供できる代替経路をあらかじめ用意しておく。 再開予定日は留保つきで具体的に示す方針を決める
  • 「最大 N 人」は登録者数の上限であり、実際に見られた人数ではない——公表時に両方を出す方針を決める
    一次公表の「最大817,215人」は EC アプリに個人情報を登録している会員数を上限として示した値で、 実際にマイページを閲覧された人数は公表されていない。読者は被害の深さを見積もれない
    取るべき行動 自社の公表文テンプレートに「対象となりうる母数（登録者数）」と 「実際にアクセスが確認された数」を分けて書く欄を設け、 後者が算出できない場合は「ログからは特定できていない」と理由を添える運用にする。 人・件・アカウントの単位も固定する
  • 「お届け先」に登録された第三者は、通知の経路を持たない被害者である
    公表はお届け先情報に「第三者宛を含む」と明記したが、 案内は「対象となる可能性のある会員へ個別メール」であり、会員でない第三者には届かない
    取るべき行動 贈答先・配送先として他人の個人情報を預かっているサービスでは、 事故時の通知経路を「会員経由の間接通知（会員に第三者への連絡を依頼する）」まで含めて設計し、 公表文にその方針を書く。あわせて、お届け先の保持期間に上限を設けて預かる量自体を減らす
セキュリティ技術者への示唆
  • 会員ごとのデータを返す経路は、すべてサーバ側で所有者の一致を検証する
    被害が閲覧のみで、対象が会員のほぼ全数規模に及び、機械的な連続アクセスが確認されている。 識別子の付け替えで他人のマイページに到達できた可能性が高い（本記録の推定）
    取るべき行動 `/api/members/{id}`・注文履歴・お届け先・登録カードなど、 パスやクエリに会員識別子を取るエンドポイントを全部列挙し、 セッションの会員 ID との一致検証をミドルウェア層で強制する。 検証漏れを検出する自動テスト（他人の ID を入れて 403 になることの確認）を CI に入れる
  • 連続アクセスのレート上限と列挙の検知を、会員向け画面に必ず置く
    80万件規模のマイページ参照が進行中に検知されず、 判明はシステムログの事後解析だった。レート制限があれば成立しない量である
    取るべき行動 送信元 IP・セッション・会員アカウントの3軸でマイページ参照のレート上限を設け、 上限到達でセッションを失効させる。 あわせて「同一送信元から短時間に多数の異なる会員 ID が参照される」事象を 検知ルールにして通知する。しきい値は平常時の分布から決め、月次で見直す
  • 会員識別子を推測・列挙できない値にする
    機械的な連続アクセスで会員全数規模に到達できたことは、 識別子が機械的に生成・走査できる形だった可能性を示す（本記録の推定）
    取るべき行動 外部に露出する会員識別子を UUIDv4 等の推測不能な値に置き換え、 連番の内部 ID は外に出さない。既存システムでは外部公開用の別識別子を割り当て、 移行期間中は両方で認可検証を行う
  • マイページの表示項目を「見られたら困るか」で絞り、既定では伏字にする
    閲覧された情報には住所・電話番号・生年月日・カードの名義と下4桁・有効期限が含まれ、 そのまま本人確認を装うフィッシングの材料になる
    取るべき行動 マイページの初期表示では住所・電話番号・生年月日・カード情報を伏字にし、 「表示する」操作でパスワード再入力または多要素認証を要求する。 画面と API の両方で伏字を適用する（API が平文を返していれば意味がない）
  • ログの保持期間を、侵害の開始時期を特定できる長さで確保する
    判明日時は分単位で特定されたのに、不正アクセスの開始時期は公表されていない。 遡及できる範囲に限りがあった可能性が残る（本記録の推定）
    取るべき行動 会員向けアプリケーションのアクセスログ（送信元・参照された会員 ID・応答件数）を 少なくとも180日、できれば13か月保持する。 保持期間を決める基準を「直近の事故の検知までに要した日数」ではなく 「業界の平均的な dwell time」に置く
  • 遮断の次に、認証情報とセッションの扱いを決めておく
    同社の対応は「EC サイトに対するアクセスの遮断」であり、 セッション・トークンの一括失効やパスワードの扱いには言及が無い
    取るべき行動 封じ込め手順に、全セッションの失効、API キー・アプリトークンの再発行、 当該期間に使われた認証情報の洗い出しを含める。 手口が未確定の段階では、パスワードが対象外とされていても 「再ログインを求める」までは行う判断基準をあらかじめ決めておく
