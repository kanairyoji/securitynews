Arch Linux のコミュニティ主導パッケージ索引 AUR（Arch User Repository）に2026年10月13日、marchos1as というアカウントが人気の AUR ヘルパー yay と paru を模したタイポスクワット・パッケージを一括投入した。

仕掛けの構造は、レビューをすり抜けるために作られている。

  • PKGBUILD は正規そのもの——上流 URL も、ソース tarball も、その sha256sum の検証も、本物の yay と同じものを使う
  • 悪性の1行は .install（pacman のインストールスクリプトレット）側にある
  • post_install と post_upgrade の関数は 中身を true に空けてある——スクリプトレットを流し読みすると無害に見える
  • 実際の処理はどの関数の外側、ファイルの最上位に置かれている。そのためインストールと更新のたびに、無条件に root 権限で実行される
  • その1行は、外部の linux.sh を取得してシェルに流す。取得先は gitflic.ru の個人プロジェクト hellscripter/install-scripts をWayback Machine でラップした URL で、スナップショットの時刻が固定されていないため配信される内容は後から差し替えられる。取得物は source=() に無く、チェックサムも無い

検知したのはパッケージ索引の側ではない。AUR を監視する第三者（Emiliano Gandini Outeda）の自作コンテナが、アップロードの7分後にアラートを上げている。15件を1つのキャンペーンとして束ね、3つのルール（H045・H052・G003）で計45件のアラートを出した。もう一人のメンテナ（Andreas Reichel）は自作の静的解析でyyay を「悪性・確度99%」と判定し、4件の critical 指摘を公開した。

報告を受けた AUR 側のメンテナは「これらのパッケージのインストールスクリプトに悪性のペイロードが含まれていることを確認した。アカウントを停止し、当該ユーザーのパッケージをすべて削除した」と応じた。

AUR は2026年に入ってから繰り返し標的になっている。6月11日には400件超（最終的に1,500件超とする報道もある）、7月末にはパッケージの引き継ぎ（adoption）を一時停止する事態が起きていた。

AUR は、第三者製・商用ソフト、ベータ版、公式経路から外れた旧版のビルドスクリプト（PKGBUILD）をホストするコミュニティ主導の索引である。投稿は審査を経ずに公開される。利用者が自分でレビューする前提の設計だが、その前提が効かない場所に悪性の1行が置かれていた。

レビューをすり抜ける3つの工夫——正規コードの流用、空の関数、関数の外側原因・手口出典 [1]

Andreas Reichel が公開した静的解析の出力が、構造をそのまま示している。

==> Validating source files with sha256sums...
    yyay-13.0.1.tar.gz ... Passed
  scanning yyay (5 files) ...
[ MAL! ] yyay (confidence 99%)
  4 critical findings and 1 warning indicate malicious behaviour; do not build.

注目すべきは1行目である。sha256sums の検証は通っている。 偽パッケージは本物の yay のソース tarball をそのまま使っているため、ソースの完全性の検証は何も教えてくれない。

critical 指摘は4件。順に、何が仕掛けだったかが分かる。

① 上流の配布元を装う・偽装したソース（PKGBUILD）

このパッケージは、正規の 'yay' AUR ヘルパーを素直に再パッケージしたものとして自らを提示している（同じ上流 URL、同じソース tarball）。しかしパッケージ名 'yyay' と悪性のインストールスクリプトレットは、これが本物のパッケージに溶け込むよう設計されたトロイの木馬化したなりすましであることを明らかにしている。（原文英語）

② インストールスクリプトレットが root としてライブシステムを変更する

このスクリプトレットは、pacman のインストール／更新の時点で、ダウンロードした任意のコードを稼働中のシステム上で root として実行する。'linux.sh' がその時点で配信しているものが何であれ——資格情報の窃取、バックドアの設置、ルートキットの展開——導入するマシン上で完全な root 権限で実行される。（原文英語）

③ スキャナ向けに書かれたパッケージの記述

post_install と post_upgrade の関数は、無害なスクリプトレットに見えるよう意図的に true に空けられている一方で、実際の悪性ペイロードはどの関数の外側、ファイルの最上位に置かれている——流し読みのレビュアーと自動スキャナを狙った構造的な欺瞞である。（原文英語）

④ 無関係なホストのスクリプトをシェルにパイプする

この行はスクリプトレットの最上位、どの関数の外側にあるため、インストールと更新のたびに無条件に root として実行される。URL は 'gitflic.ru' 上の個人プロジェクト（'hellscripter/install-scripts'）を指しており、yay/yyay もその上流（github.com/Jguer/yay）とも何の関係も無いホストである。web.archive.org のラッパーはスナップショットの時刻を固定していないため、配信される内容は固定されていない。取得されるスクリプトは source=() に無く、チェックサムも無い。（原文英語）

4つを合わせると、レビューの各段を1つずつ外しに来ていることが見える。

レビューの手段 外し方
上流 URL の確認 本物と同じ URL を使う
ソースのチェックサム検証 本物の tarball を使う（検証は通る）
スクリプトレットの関数を読む 関数は true に空けてある
自動スキャナ ペイロードを関数の外側に置く
取得物のチェックサム source=() に入れない
配信内容の事後確認 Wayback のスナップショットを固定しない

最後の1つは事後の検証可能性を奪うという点で重い。同じ URL が時期によって別の内容を返しうるため、「あのとき何が実行されたのか」を後から確定できない（本記録の評価）。

AUR の設計では、インストールスクリプトレットが root を取る——「自分でレビューする」前提の限界評価・解釈出典 [1] [2] [4]

ここからは本記録の作成者の評価である。

第一に、この事案は AUR の設計上の前提が破れた例である。 AUR は「投稿を審査しない代わりに、利用者が自分でレビューする」という交換で成り立っている。Arch Linux 自身も2026年6月12日の公式ニュースで「更新時にはすべての PKGBUILD とインストールスクリプトの変更を確認すること」を利用者に促している。

しかしインストールスクリプトレットは pacman のインストール・更新時に root 権限で実行される。つまりレビューを一度省けば、その時点で全権限を渡す。「レビューを前提にする」設計と「失敗したら root を失う」帰結の組み合わせは、利用者側の注意に負荷をかけすぎている。

さらに本件の構成は、レビューを「した」人も騙しに来ている。PKGBUILD を見れば正規と同じ、関数を見れば空、チェックサムは通る——どれも「見た」という事実は作れるが、気づけない。気づくには「関数の外側にある行」を読む必要があり、それはシェルスクリプトの構造を意識していなければ飛ばしやすい箇所である。

第二に、タイポスクワットは「名前を1〜2文字変える」だけで成立している。 yay に対する ya・ayy・yyay・yqy。AUR ヘルパー経由の検索と導入では、候補一覧から選ぶ操作が多く、1文字の差は視認しにくい。パッケージ名の近さを投稿時に検査して保留する仕組みがあれば、この波は索引側で止められた性質のものである（本記録の評価）。

第三に、2026年に入ってから波が繰り返されている。 6月11日に400件超（1,500件超とする報道もある）、7月末にはパッケージの引き継ぎを一時停止、そして10月13日の本件。対処は毎回「報告を受けてから削除」である。 6月の公式ニュースは「より恒久的な解決策を作る作業を進めている」としていたが、10月の本件でもアカウント停止とパッケージ削除が対処として報告されている。

第四に、gitflic.ru というホスト名が議論を国別の遮断へ逸らした。スレッドでは「当面ロシアのドメインを遮断する」という提案が出たが、別の参加者が「攻撃者は他国のドメインを使い他国から物理的に活動できる。自国内にも完全に敵対的な人間はいる」と反論している。この反論は正しい（本記録の評価）。本件で機能した防御は国別の遮断ではなく、「無関係なホストからスクリプトを取得してシェルに流す」という挙動の検知だった。見るべきは取得先の国籍ではなく、取得と実行の構造である。

数え方: AUR からパッケージを導入・更新するときは、PKGBUILD だけでなく インストールスクリプトレット（`.install`）を**関数の外側まで**読む　副作用: 毎回の更新でこれを行うのは現実的でない。 AUR ヘルパー経由の一括更新では差分の確認が省かれやすい。 運用としては自動化（下記）と組み合わせる必要がある
数え方: パッケージ名が人気パッケージと1〜2文字しか違わないものを警戒する （yay に対する ya・ayy・yyay・yqy 等）　副作用: 正規の短い名前のパッケージや、意図的に似せた互換パッケージ （`-git`・`-bin` 系など）も引っかかるため、名前だけでは判断できない

数え方: 疑わしいパッケージを導入してしまった場合は、 システムが侵害されたと想定して復旧措置を取る　副作用: 再インストールを含む重い対応になる。 ただしインストールスクリプトレットは root 権限で任意コードを実行しており、 かつ配信された内容を事後に確定できないため、 部分的な駆除では安全を確認できない（本記録の評価）

対応の評価

判断評価評価の根拠と留保
AUR 側のメンテナは、アカウント marchos1as を停止し、 当該ユーザーのパッケージをすべて削除した。 AUR 全体の停止や投稿の一時凍結は行っていない部分的に機能本記録の作成者の評価である。初動としては適切で速い（報告から1日以内）。 ただし2026年6月・7月に続いて3度目の波であり、 毎回「報告を受けてから削除」という同じ形で対処されている。 2026年6月12日の公式ニュースは 「より恒久的な解決策を作る作業を進めている」としていたが、 本件の対処報告には再発防止の言及が無い
メーリングリスト上で、静的解析の出力（4件の critical 指摘の全文）と 監視コンテナの通知ログ（15件のパッケージ名とルール ID）が公開された機能した本記録の作成者の評価である。 「関数を `true` に空けて最上位にペイロードを置く」という構造を 具体的な指摘として示したことは、 同じパターンを検査する側に直接使える情報になっている。 パッケージ名15件を列挙したことも、利用者が自分の導入履歴を照合できる形である
導入した利用者への個別通知は行われず、 メーリングリストと報道を通じた周知にとどまった不十分本記録の作成者の評価である。 構造上やむを得ないが、root 権限での任意コード実行という帰結の重さに対して 周知の経路が弱い。 AUR ヘルパー側が「削除されたパッケージを導入済みの場合に警告する」仕組みを 持てば、この穴は部分的に埋まる（本記録の提案）
CISO・経営層への示唆
  • コミュニティ主導のパッケージ索引は、導入の一度の誤りで root を渡す経路である
    AUR のインストールスクリプトレットは pacman のインストール・更新時に root 権限で実行される。 本件のペイロードは関数の外側に置かれ、 インストールと更新のたびに無条件に実行される構成だった。 AUR は投稿を審査しない代わりに「利用者が自分でレビューする」前提に立っている
    取るべき行動 開発者端末・ビルド環境で利用を許すパッケージ源を明文化し、 審査の無い索引（AUR・npm・PyPI の無名パッケージ等）からの導入を 申請制または隔離環境に限定する。 業務端末で AUR を使う必要がある場合は、 導入を許可するパッケージの一覧を維持し、それ以外は禁止する
  • 「レビューした」という事実は、気づけたことを意味しない——本件はレビュアーを欺く設計だった
    PKGBUILD は正規と同じ上流 URL とソース tarball を使い、 sha256sums の検証は通る。 インストールスクリプトレットの `post_install` と `post_upgrade` は `true` に空けられ、ペイロードはどの関数の外側に置かれていた。 静的解析はこれを「流し読みのレビュアーと自動スキャナを狙った構造的な欺瞞」と評した
    取るべき行動 サードパーティのパッケージ・依存のレビューを人の目視だけに頼らず、 自動の静的解析（インストールフックの検査、source に無い外部取得の検出、 シェルへのパイプの検出）を導入経路に組み込む。 レビューを「承認の儀式」にしないため、 何を見たかをチェックリストで記録する運用にする
  • 同じ索引が繰り返し標的になっているなら、次の波を前提に設計する
    AUR は2026年6月11日に400件超（1,500件超とする報道もある）、 7月末にはパッケージ引き継ぎの一時停止、 そして10月13日の本件と、同年に3度の波を受けている。 対処は毎回「報告を受けてから削除」である
    取るべき行動 依存している外部索引について、過去12か月の悪性パッケージ事案の回数を数え、 回数が多い索引は「いずれまた汚染される」前提で運用を設計する。 具体的には、導入を隔離環境に限定する、 ミラーを自社で持ってバージョンを固定する、 導入済みパッケージが上流で削除されたことを検知する、のいずれかを選ぶ
  • 「取得先の国籍」ではなく「取得と実行の構造」を見る
    ペイロードの置き場が `gitflic.ru`（ロシアのホスティング）だったことから、 スレッドでは国別の遮断が提案された。 別の参加者は「攻撃者は他国のドメインを使い他国から物理的に活動できる」と反論している。 実際に本件を捉えたのは、国籍ではなく 「無関係なホストからスクリプトを取得してシェルに流す」という挙動の検知だった
    取るべき行動 遮断ポリシーを地理的な属性で組まず、挙動と構造で組む。 ビルド・導入時の外向き通信を上流ホストの許可リストに限定し、 それ以外への接続を遮断する。 地理的な遮断を使う場合でも、挙動の検知を代替にしない
  • 配信内容が固定されていない取得 URL は、事後の説明責任を奪う
    取得 URL は `web.archive.org` のラッパーで、 スナップショットの時刻を固定していなかった。 静的解析はこれを critical 指摘として挙げている。 同じ URL が時期によって別の内容を返しうるため、 「あのとき何が実行されたのか」を後から確定できない
    取るべき行動 自社のビルド・導入で外部から取得するものは、 バージョンまたはコミットハッシュで固定し、チェックサムを検証する。 固定できない取得（最新版を取る、リダイレクタ経由）を禁止する方針を定め、 CI で検出する。 インシデント時に「何を取得したか」を再現できることを要件にする
セキュリティ技術者への示唆
  • PKGBUILD だけでなく `.install` を、関数の外側まで読む
    悪性の1行は `post_install` と `post_upgrade` の**外側**、 ファイルの最上位にあった。関数の中身は `true` に空けてある。 スクリプトレットを「関数単位で」読むと見落とす
    取るべき行動 AUR パッケージの導入・更新時は `.install` ファイルを全文読み、 関数定義の外側に実行文があれば止まる。 具体的には `cat *.install` して関数ブロックの外に `curl`・`wget`・`bash`・`sh` を含む行が無いかを確認する。 AUR ヘルパーの差分表示を必ず有効にする（`yay --editmenu` 等）
  • ソースのチェックサム検証は、パッケージが安全であることを示さない
    偽パッケージは本物の yay のソース tarball をそのまま使っており、 `sha256sums ... Passed` と出る。 悪性のコードはソースではなくインストールスクリプトレット側にあり、 そこから取得される `linux.sh` は `source=()` に無いためチェックサムの対象外である
    取るべき行動 `sha256sums` の検証が通ったことを安全の根拠にしない。 確認すべきは「`source=()` に列挙されていない外部取得が無いか」である。 PKGBUILD と `.install` を対象に、 `source=()` 外の URL 参照を検出する検査を自前で用意する
  • パッケージ名の編集距離を自分で検査する
    15件はすべて `yay` を1〜2文字変えた名前だった （ay・ayy・hay・tay・uay・ya・yaay・yat・yau・yayy・yqy・ysy・yya・yyay・yzy）。 AUR ヘルパーの候補一覧から選ぶ操作では、1文字の差は視認しにくい
    取るべき行動 導入前に、指定したパッケージ名と 既知の人気パッケージ名との編集距離を確認する手順を入れる。 簡単には、導入しようとしているパッケージの得票数（NumVotes）と 初回投稿日（FirstSubmitted）を AUR の API で確認する—— 正規の yay は得票2,650・2016年投稿であり、 投稿直後・得票ゼロのパッケージとは明確に区別できる（本記録の観測）

    インストールスクリプトレットは実行時点で既に root 権限であり、 実行を事後に検知しても手遅れである。 本件では取得先が何を返すかも固定されていなかった
    取るべき行動 AUR パッケージを、ネットワークを上流ホストに限定したコンテナまたは 使い捨ての仮想マシンで先にビルド・導入し、 導入中の外向き通信・新規プロセス・ファイル変更を観測する。 問題が無ければ本番の端末に入れる。 最低限、ビルド・導入時の外向き通信を許可リスト制にする

    AUR は導入者を把握しないため、個別通知は構造上できない。 本件では AUR 側がパッケージを削除したが、 既に導入した利用者は自分で気づく必要がある
