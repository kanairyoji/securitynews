INC-2026-0568Magento に CVSS 10.0 の RCE

Adobe が2026年10月13日に公開した APSB26-153 で、Adobe Commerce と Magento Open Source の メールテンプレートエンジンに CVSS 10.0・未認証で任意コード実行が可能な脆弱性 CVE-2026-103849 を修正した—— EC セキュリティ企業 Sansec はこれを「BlockStrap」と名付け、公開24時間以内に4つの攻撃経路を再現したうえで、 Adobe の優先度2（30日以内の適用）という評価は危険度に見合わないと指摘した。実店舗への悪用は10月17日時点で観測されていない

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月13日 最終更新: 2026年10月17日

Adobe は2026年10月13日、Adobe Commerce・Magento Open Source・Adobe Commerce B2B 向けのセキュリティ公報 APSB26-153 を公開し、メールテンプレートエンジンにおける特殊要素の不適切な無害化（CWE-1336）に起因する CVE-2026-103849 を修正した。深刻度は Critical、CVSS 基本値は 10.0（CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H）で、悪用に認証を要しない。

EC セキュリティ企業 Sansec は10月15日、この脆弱性を BlockStrap と名付けて分析を公開した。9月の StyleSmuggler（CVE-2026-75650）に対するホットフィックス VULN-39341 が残した隙を突くもので、子テンプレート内の攻撃者制御データが署名を受けたままルートレベルで再評価され、密輸された {{block}} ディレクティブが実行される、という二次パスのディレクティブ注入である。Sansec は公開から24時間以内に4つの攻撃経路を再現したと述べ、「攻撃経路は複雑だが、AI エージェントを持つ者なら比較的短時間でパッチをリバースエンジニアリングして動く攻撃コードにできる」として、Adobe の優先度2（30日以内の適用）という評価に疑問を呈した（原文英語）。

2026年10月17日時点で、Adobe は「本アップデートで対処した問題について、野外での悪用は把握していない」とし、Sansec も「実店舗への悪用は未観測」としている。ただし Sansec は、同種・同程度の複雑さだった StyleSmuggler が優先度1のホットフィックスから3日で大量悪用に至ったことを引き合いに、近いうちの悪用波を予告している。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は未認証で、メールテンプレートに取り込まれる経路から攻撃者制御のデータを送り込む。 9月のホットフィックスがそのデータにも署名を付けてしまうため、ルートレベルの再評価で 密輸された {{block}} ディレクティブが実行され、Magento のレンダリングの文脈で任意の PHP コードが動く。 以下は Sansec が公開した分析に基づく想定経路であり、実店舗での悪用は2026年10月17日時点で観測されていない。

  1. 1. 初期侵入disclosed[1] [2]
    未認証の攻撃者が、メールテンプレートの子テンプレートに取り込まれる経路から、 {{block}} ディレクティブを含むデータを送り込む。認証は不要（Adobe: Authentication required to exploit? No）
    根拠: Adobe APSB26-153（CVSS ベクタ AV:N/PR:N/UI:N）および Sansec の分析
  2. 2. 実行disclosed[2]
    9月のホットフィックスが攻撃者制御データにも署名を付けるため、ルートレベルでの再スキャン時に 密輸された {{block}} ディレクティブが有効なものとして評価され、任意の PHP コードが実行される
    根拠: Sansec の分析（second-pass template engine directive injection）
  3. 3. 影響（暗号化・破壊・改ざん）推定[2] [3] [4]
    先行する StyleSmuggler では、悪用に成功した店舗に Rust 製の Linux バックドアが設置され、 C2 が NTP サーバーを装っていたと報じられている（本事案ではなく先行事例の観測）
    根拠: StyleSmuggler（CVE-2026-75650）に関する2026年9月の報道

9月のホットフィックスが残した隙を突く「二次パスのディレクティブ注入」で、未認証の任意コード実行に至る原因・手口出典 [1] [2]

公開された情報から、起きていることは次のとおりである。

  • Adobe は2026年10月13日に APSB26-153 を公開し、CVE-2026-103849 を修正した
  • 分類はテンプレートエンジンにおける特殊要素の不適切な無害化（CWE-1336）で、影響は任意コード実行
  • 深刻度 Critical、CVSS 10.0（AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H）、認証は不要
  • 対象は Adobe Commerce 2.4.4〜2.4.9、Magento Open Source 2.4.6〜2.4.9、Adobe Commerce B2B 1.3.3〜1.5.3 の「2026-sep 以前」のビルド
  • Sansec によれば Mage-OS も 3.5.0 までが影響を受け、3.6.0 で修正されている

Sansec の説明する仕組みは次のとおりである。9月の StyleSmuggler 対策ホットフィックス VULN-39341 は、信頼されたディレクティブに署名を付けたうえで再スキャンする方式を採った。ところが、子のメールテンプレートに含まれる攻撃者制御のデータにも署名が付いてしまい、それがルートレベルでもう一度評価される。この二度目の評価で、密輸された {{block}} ディレクティブがMagento のレンダリング内で実行される。Adobe の10月のパッチは、この汎用的な再スキャンを登録済みプレースホルダー方式に置き換えることで塞いでいる。

つまり本件は、独立した新しい欠陥というより、先行する修正の設計が残した隙である。

Adobe は優先度2（30日以内）、Sansec は「それでは遅い」——評価が割れている評価・解釈出典 [1] [2] [3]

同じ脆弱性に対する2者の評価が、はっきり食い違っている。

Adobe（APSB26-153） Sansec（BlockStrap）
深刻度 Critical / CVSS 10.0 同じ（CVSS 10.0）
適用の緊急度 優先度2（30日以内） 優先度2 は危険度に見合わない
悪用の状況 野外での悪用は把握していない 実店舗への悪用は未観測。近く大量攻撃が来るとみる

Sansec の根拠は2つある。第一に、攻撃経路の複雑さはもはや時間稼ぎにならないという主張である。「攻撃経路は複雑だが、AI エージェントを持つ者なら比較的短時間でパッチをリバースエンジニアリングして動く攻撃コードにできる」（原文英語）。実際、同社自身が24時間以内に4つの攻撃経路を再現している。第二に、同じ複雑さだった StyleSmuggler が、優先度1のホットフィックスから3日で大量悪用に至ったという先行事例である。

ここからは本記録の評価である。「複雑だから優先度を下げる」という前提が、この事案では成立していない。パッチ差分から攻撃経路を導くのに要する時間は、攻撃経路の理論的な複雑さではなく、それを探索する者の道具立てで決まる。ベンダーの優先度は依然として適用計画の起点として有用だが、CVSS 10.0・認証不要・インターネット公開が前提の製品という3条件が揃ったときは、優先度の数字ではなくこの3条件で判断するのが安全側である。

なお、Sansec は自社製品（Sansec Shield）による HTTP 層での緩和を併せて勧めており、評価の厳しさに商業的な動機が混じりうる点は割り引いて読む必要がある（本記録の留保）。

Composer の通常更新では塞がらない——9月のホットフィックスと10月の修正は「両方」要る対策・注意喚起出典 [1] [2]

Sansec が強調しているのは、対処が1つではないという点である。

  • 素の Composer インストールでは不十分。Adobe の 2026-oct リリース、または Adobe が配布する分離パッチを適用する必要がある
  • BlockStrap と StyleSmuggler は別の修正である。9月の VULN-39341 ホットフィックスはそのまま残すこと
  • Adobe の公報自体も、本公報の更新に加えて CVE-2026-75650 のホットフィックスを適用するよう指示している
  • Magento Open Source 2.4.6 以前はライセンス上の都合で 2.4.7-p10 以降へのアップグレードが要る
  • 適用の確認は、Sansec が示す resolveDeferredDirectives の grep で行える
  • すぐにパッチできない場合、Sansec は HTTP 層でのブロック（自社製品）を挙げている

「更新したつもりで片方しか当たっていない」が最も起きやすい失敗である（本記録の評価）。パッチ適用後は、当たったことをコードで確認する手順まで運用に含める必要がある。

悪用はまだ観測されていない——ただし観測していないのは「Sansec のセンサーが」である未確定事項出典 [1] [2]

2026年10月17日時点で、次の点は確定していない。

  • 実際の悪用が始まったかどうか。Adobe は「野外での悪用は把握していない」、Sansec は「No exploitation observed yet.」としている。いずれも「観測していない」であって「起きていない」ではない（本記録の整理）
  • 影響を受ける公開インスタンスの数と、日本国内の分布
  • 報告者 vozec が報告した日付と、報告から修正までの経過
  • PoC・攻撃コードの公開状況

Sansec は、大量攻撃の波を検知した時点で更新すると述べている。本記録は status を updating とし、悪用の観測が報じられた時点で追記する。

判断評価評価の根拠と留保
Sansec は脆弱性の仕組みと影響バージョン、適用確認の手順を公開する一方、 再現した4つの攻撃経路の詳細と PoC は公開しなかった機能した本記録の評価である。パッチ適用の確認手段（grep）まで示しており、 防御側が行動するのに必要な情報は揃っている
Adobe は公報全体を優先度2（30日以内の適用）として公開した不十分本記録の評価である。Sansec の指摘（AI 支援でのパッチ差分解析、StyleSmuggler の3日という前例）に対し、 Adobe 側が優先度の根拠を示していない。評価は結果論になりうるため、悪用観測の有無で後日検証する
CISO・経営層への示唆
  • ベンダーの優先度は、CVSS・認証要否・公開面の3条件で上書きする運用にしておく
    Adobe は優先度2（30日以内）としたが、CVSS 10.0・認証不要・インターネット公開が前提の EC 製品である。 Sansec は同種の先行事例が3日で大量悪用に至ったと指摘している
    取るべき行動 脆弱性の適用 SLA を「ベンダー優先度」だけで決めず、 「CVSS 9.0 以上 かつ 認証不要 かつ 外部公開」の組み合わせに該当したら、 ベンダー優先度にかかわらず72時間以内の適用または緩和を要求する規程に改める
  • 「攻撃が複雑だから時間がある」という前提は、すでに成り立たない
    Sansec は「AI エージェントを持つ者ならパッチを比較的短時間で動く攻撃コードに変えられる」と述べ、 自ら24時間以内に4経路を再現した
    取るべき行動 リスク評価の様式から「攻撃難易度が高い」を単独の減点要素として外し、 「パッチが公開された＝差分から攻撃コードが導ける」を前提に猶予期間を設定し直す
  • EC 基盤は「止める判断」を平時に決めておく
    Magento の RCE は決済ページ改ざん（スキマー）に直結する。 先行事例では侵害店舗に Rust 製バックドアが設置されたと報じられている
    取るべき行動 自社 EC について「パッチ適用までの間、サイトを止めるか／機能を縮退させるか」の判断基準と 意思決定者を事前に決め、売上影響の試算と併せて経営会議で合意しておく
  • 修正が2本立ての脆弱性は、適用管理の失敗が起きる
    本件は10月の修正と9月のホットフィックス VULN-39341 の両方が要る。 素の Composer インストールでは不十分とされている
    取るべき行動 脆弱性管理台帳に「適用済み」のチェック欄だけでなく「何をもって適用済みと判定したか（検証方法）」の欄を設け、 ベンダーが示す検証手順の実施を完了条件にする
セキュリティ技術者への示唆
  • パッチが当たったことを、バージョン番号ではなくコードで確認する
    Composer の通常更新では塞がらず、分離パッチの適用が必要である。 Sansec は resolveDeferredDirectives の grep による確認手順を示している
    取るべき行動 本番・ステージングの両方で Sansec が示す grep を実行し、結果をチケットに貼る。 同じ確認をデプロイパイプラインのチェックに組み込み、再デプロイで巻き戻るのを防ぐ
  • 9月のホットフィックスを外さない
    BlockStrap と StyleSmuggler は別の修正であり、Sansec は VULN-39341 を残すよう明記している。 アップグレード作業でホットフィックスの差分が失われる事故が起きやすい
    取るべき行動 適用済みホットフィックスの一覧を構成管理に持ち、アップグレード後に各ホットフィックスの 適用状態を再判定するスクリプトを用意する
  • テンプレートエンジンに渡る入力を記録する
    本脆弱性はメールテンプレートの二次評価で発火する。 標準ではテンプレートへ渡る入力の記録は残らず、事後の追跡ができない
    取るべき行動 メールテンプレートの描画時に、テンプレート識別子と変数のキー（値ではなく）を記録し、 {{block}} / {{config}} 等のディレクティブ文字列が入力値に含まれた場合はアラートする
  • アプリケーション実行ユーザーの権限と書き込み可能領域を絞る
    任意の PHP 実行に至ると、Web ルートへのファイル書き込み（Web シェル・スキマー）が次の一手になる
    取るべき行動 コード領域を読み取り専用でマウントし、書き込みが要る領域を列挙して分離する。 Web ルート配下のファイル作成・変更を完全性監視で検知し、var/ や pub/media への実行権限を外す
  • パッチ適用後も、適用前に侵害されていなかったかを確認する
    先行事例（StyleSmuggler）では、ホットフィックスが既に侵害された店舗を浄化しないため、 スキャンと認証情報の入れ替えが必要だと指摘されていた
    取るべき行動 適用と同時に、管理者アカウント・API キー・暗号鍵の棚卸しと入れ替え、 cron・スケジュールタスク・管理者追加の差分確認、決済ページの改ざんスキャンを一度回す
