INC-2026-0569OpenAI 公式スキルの幻覚ドメインに本番トークン

OpenAI が公式に配布していた Render 向けスキル（render-deploy）が、実在しないドメイン render-internal.com をサービス間通信の宛先として案内しており、これに従って Codex 等が生成した本番アプリが 当該ドメインへトークンを送信していた——AIR Security が2026年10月14日に公開した調査によれば、 研究チームが未登録だったドメインを取得して受信専用のシンクホールを置いたところ、 実在する本番アプリからトークンと API 呼び出しが届いた。該当の記述は2026年1月27日の初回コミットから存在し、 Render が8月14日に参照を削除、OpenAI が8月26日に Render プラグインを公式リポジトリから削除した

委託先・再委託先起因で委託元多数に波及意図せぬ露出（設定不備等で外部から到達可能だった）続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因
初報: 2026年10月14日 最終更新: 2026年10月17日

OpenAI は、AI エージェントに各種プラットフォームの扱い方を教える「スキル」を公式の GitHub リポジトリで配布している。公式であること自体が暗黙の信頼として働く種類の部品である。

AIR Security の研究チームは、そのうち Render へのアプリ配備を教えるスキル（render-deploy）の参考ドキュメント references/service-types.md が、サービス間の内部通信の宛先として[service-name].render-internal.com を案内していることを見つけた。configuration-guide.md にも同じドメインを含むデータベース URL の例があった。このドメインは誰も登録していなかった。

研究チームが Codex にこのスキル経由で「内部通信する2つのサービス」の配備を依頼したところ、生成されたアプリのコードと設定にこのドメインが既定値として現れた。そこでチームはドメインを登録し、すべてのサブドメインとポートに応答して受信内容を記録するだけの受信専用シンクホールを置いた。すると、実在する本番アプリからトークンを含む通信と API 呼び出しが届いた。

該当の記述は 2026年1月27日の初回コミット（d6231b6c）から存在し、3月13日のコミット（6a8ab473）でopenai/plugins に同梱されていた。責任ある開示を受け、Render は8月14日にスキルからrender-internal.com の参照をすべて削除（5152e543）、OpenAI は8月26日に Render プラグインをopenai/plugins から削除した（33bd9529）。ドメインは Render の管理下へ移された。AIR Security は10月14日に技術的な記事を公開し、CSO Online が10月16日に報じた。

流出したトークンの件数、影響を受けたアプリの数、流出したデータの範囲はいずれも公表されていない。

公式スキルの参考ドキュメントが、誰も登録していないホスト名を「内部通信の宛先」として案内していた原因・手口出典 [1] [2]

AIR Security の記事によれば、起きていたことは次のとおりである。

  • OpenAI の公式リポジトリにある render-deploy スキルの references/service-types.md が、Render のプライベートサービスへの接続先として [service-name].render-internal.com を案内していた
  • configuration-guide.md にも、同じドメインを含むデータベース URL の例があった
  • このドメインは誰も登録していなかった（CSO Online は「unregistered domain」と表現している）
  • 研究チームが Codex に、このスキル経由で「内部通信する2つのサービス」の配備を依頼したところ、生成されたアプリのコードと設定に当該ドメインが既定値として現れた。実行時に別の宛先を指定しなければ、この値が使われる
  • 該当の記述は 2026年1月27日の初回コミット（d6231b6c）から存在し、3月13日のコミット（6a8ab473）で openai/plugins に同梱された

「幻覚」が一度ドキュメントに書かれると、それはもう幻覚ではなく仕様になるという点が、この事案の芯である。LLM が実行のたびに作り出す誤りであれば、出力ごとにばらつくので気づける。ところが、公式の参考ドキュメントに書かれた誤りは、毎回同じ値として、確定的に生成コードへ写される。

研究チームがドメインを登録してシンクホールを置くと、本番アプリからトークンが届いた発覚の端緒出典 [1] [2]

研究チームは、未登録だったドメインを自ら登録し、すべてのサブドメインとポートに応答して受信内容を記録するだけの受信専用シンクホールを設置した。

その結果、実在する本番アプリからトークンを含む通信と API 呼び出しが届いた。アプリ側は、自社の内部サービス宛に送っているつもりだった。

この手口は、攻撃者から見れば待っているだけでよいという性質を持つ。侵入も、フィッシングも、脆弱性の悪用も要らない。ドメイン1つを買うだけである。CSO Online は「研究者が先に見つけていなければ、誰も買わなかったドメインを使ってサプライチェーン攻撃を仕掛けられたかもしれない」と書いている。

なお、シンクホールが受信専用であったことは AIR Security 自身の説明であり、本記録の作成者が独立に検証したものではない。また、研究チームが登録するより前に第三者が同じことをしていなかったかは確認されていない。

修正は Render が8月14日、OpenAI が8月26日——存在していたのは約7か月間組織の対応出典 [1] [2]

ドメインを第三者に渡らないよう事業者側で保持するという最後の処置は、同種の事故に対する定石として妥当である（本記録の評価）。一方で、この期間に生成されたコードは、修正によって書き換わらない。スキルから参照を消しても、すでに本番で動いているアプリの設定ファイルにはドメインが残る。Render がドメインを保持しているため現在は安全側に倒れているが、「直ったのはスキルであって、生成物ではない」という点は読者が押さえておく必要がある。

公式であることは検証の代わりにならない——スキルは依存関係として扱うべきである（本記録の評価）評価・解釈出典 [1] [2]

ここからは本記録の作成者の評価である。

第一に、この事案の新しさは「誰も悪意を持っていない」ことにある。スキルを書いた側に悪意は無く、Codex にも悪意は無く、アプリを作った開発者にも落ち度らしい落ち度は無い。それでも本番のトークンが見知らぬドメインへ流れた。攻撃者が要るのはドメイン登録料だけで、以降は受信するだけである。パッケージのタイポスクワットと違い、開発者が名前を打ち間違える必要すらない。

第二に、「公式」という表示が、検証の省略を正当化してしまっている。 AIR Security の Niv Hoffman は「公式でベンダーが公開した AI スキルであっても、誤り、安全でない前提、依存関係、脆弱性を含みうる。スキルはソフトウェアサプライチェーンの他の部分と同じように検証・監視し、脆弱性が見つかったらパッチまたは失効ができるようにすべきだ」と述べている（原文英語）。この指摘はそのまま運用要件に翻訳できる——スキルに版を付け、依存関係として台帳に載せ、失効の手段を持つということである。

第三に、スキルの「参照先」こそが監視対象である。スキルの本文が安全かどうかだけを見ても足りない。スキルが指し示すドメイン・URL・リポジトリ・API が、(a) 実在するか、(b) 誰の持ち物か、(c) 持ち主が変わっていないか——が本当の検査項目になる。本件は (a) で落ちた例である。より危険なのは、かつて実在したが失効したドメインがスキルに残っている場合で、そちらは検査を「実在するか」だけで組むと通り抜ける。

第四に、これは生成 AI 特有の現象ではなく、生成 AI によって増幅された古い問題である。ドキュメントの例示に書かれたホスト名がそのままコピーされる事故は昔からあった。変わったのはコピーの速度と規模である。1つのスキルが166日間、エージェントを通じて不特定多数のアプリに同じ既定値を書き込み続けた。

CISO・経営層への示唆
  • AI エージェントのスキルを、ソフトウェア部品と同じ台帳に載せる
    公式に配布されたスキルが、約7か月にわたり実在しないドメインを既定値として下流アプリに書き込んでいた。 スキルは「設定」ではなく「依存関係」である
    取るべき行動 社内で使用している AI エージェントのスキル・プラグイン・MCP サーバーを棚卸しし、 名称・提供元・版・取得元 URL を資産台帳に登録する。 更新・失効の手段（どうやって配布を止めるか）を部品ごとに決めておく
  • 「公式」「ベンダー提供」は検証を省く理由にならない
    AIR Security の CTO は「公式でベンダーが公開した AI スキルであっても、誤り、安全でない前提、 依存関係、脆弱性を含みうる」と述べている（原文英語）。本件がその実例である
    取るべき行動 調達・利用の基準から「公式かどうか」を単独の可否条件として外し、 「参照先の実在と所有者を検査したか」「版を固定したか」「失効できるか」を可否条件に置き換える
  • 生成されたコードは、生成元を直しても直らない
    Render と OpenAI はスキルと配布を修正したが、その間に生成され本番で動いているアプリの設定には 当該ドメインが残る。ドメインを Render が保持しているため現在は安全側に倒れているだけである
    取るべき行動 AI 支援で生成したコードについて「いつ・どのスキル／モデルで生成したか」を記録に残す仕組みを作り、 上流の部品に問題が見つかったときに、影響を受けた生成物を逆引きできるようにする
  • 「エージェントが作ったものの中身を誰も読んでいない」状態を前提に統制を置く
    本件では、生成された設定の中の見慣れないホスト名が、本番に出るまで誰にも問われなかった
    取るべき行動 生成コードのレビュー要件に「外部へ出る宛先（ホスト名・URL・IP）を列挙し、 それぞれの正当性を1行で説明する」項目を加え、説明できない宛先がある変更はマージしない
セキュリティ技術者への示唆
  • アプリが参照する外部ホスト名の一覧を作り、所有者と実在を定期的に検査する
    本件の入口は、実在しないホスト名が設定の既定値になっていたことである。 より危険なのは、かつて実在して失効したドメインが残っている場合である
    取るべき行動 設定ファイル・環境変数・コードからホスト名を抽出し、 (1) 名前解決できるか (2) WHOIS の登録者が想定どおりか (3) 前回から変化していないか を定期ジョブで検査してアラートする。未登録ドメインへの参照は即時にチケット化する
  • 外向き通信をデフォルト拒否にする
    内部通信のつもりの宛先が外部へ解決され、トークンがそのまま出て行った。 宛先を許可制にしていれば、ドメインが誰のものであっても通信は成立しない
    取るべき行動 本番環境の外向き通信を既定で拒否し、必要な宛先だけを明示的に許可する。 許可一覧の変更はレビュー対象にする。到達できない宛先への接続試行はログに残して監視する
  • サービス間通信に mTLS を使い、相手が誰かを証明書で確かめる
    宛先のホスト名だけを信頼していたため、そのホスト名を取得した第三者に接続してしまう
    取るべき行動 内部サービス間の通信を mTLS 化し、自社 CA の証明書でなければ接続を打ち切る。 トークンは短命化し、用途と宛先を限定したスコープで発行する
  • 生成 AI に書かせた設定の既定値を、そのまま本番に出さない
    Codex はスキルの案内どおり当該ドメインを既定値として生成した。 モデルが誤ったのではなく、参照した資料が誤っていた
    取るべき行動 生成されたコードのうち、外部宛先・認証情報・エンドポイントに関わる既定値は 空値またはビルド時に解決必須の変数に置き換え、 設定が注入されなければ起動しない作りにする（fail-closed）
  • スキル・プラグインの版を固定し、差分をレビューする
    問題の記述は初回コミットから入っており、同梱によって配布範囲が広がった。 版を固定していなければ、上流の変更が無審査で手元に届く
    取るべき行動 スキルの取得をコミットハッシュで固定し、更新時は差分（特に参照先 URL・ドメインの追加）を レビュー対象にする。社内ミラーを置き、外部リポジトリから直接取得しない

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ AI エージェント（Codex・Claude Code 等）のスキル・プラグイン・MCP サーバーを開発に使っている本件は公式配布のスキルの記述が、そのまま本番アプリの既定値になった事案である
委託・第三者部品□ 使用中のスキル・プラグインの一覧と版を、資産台帳で把握していない上流に問題が見つかったとき、影響を受けた生成物を逆引きできない
システム構成□ 本番環境の外向き通信が既定で許可されている（宛先の許可制になっていない）宛先ドメインを誰が持っていても通信が成立してしまい、トークンがそのまま外へ出る
システム構成□ サービス間の内部通信をホスト名だけで信頼しており、mTLS などで相手を検証していないホスト名を取得した第三者に、アプリ側が自発的に接続して認証情報を渡す
認証・認可□ アプリが持つトークンが長命で、用途・宛先のスコープが限定されていない1回の誤送信で広い権限が渡る。本件で届いたのは本番アプリのトークンである
運用・監視□ コードや設定に現れる外部ホスト名の実在・所有者を定期的に検査していない未登録ドメイン・失効ドメインへの参照は、気づかないまま第三者に拾われる
