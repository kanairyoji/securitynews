MSP 向けバックアップサービス ConnectWise Cloud Backup（旧 SkyKick）の アプリケーション識別情報が攻撃者の手に渡り、同アプリが導入済みの顧客 Microsoft 365 テナントへ 2026年10月15日に次々とサインインされた——Huntress は10月16日19:00（UTC）時点で 162テナントでの不正サインインを確認し、報道では173テナントとされる。資格情報はベンダー自身の テナントに存在する client assertion であり、顧客側の設定や操作では生じえない。 ConnectWise は10月17日05:01（UTC）に Cloud Backup のアプリケーションアクセスを停止し、 パートナーとその顧客のバックアップが中断している。10月17日、Microsoft も本件を 公式に確認し「進行中のサプライチェーン攻撃」と位置づけた【続報・2026年10月19日】 **停止が3日目に入り、ConnectWise は復旧の時期をなお示していない。** 10月19日01:15（UTC）の更新では「封じ込めと調査は継続中」「対策後、監視対象の環境で 成功した脅威活動は確認していない」とし、次回更新を同日13:00（UTC）までに出すとした。 **攻撃元のIPアドレスは10月18日18:45（UTC）の更新で2つ増え、計3つになった** （144.172.64[.]128／144.172.64[.]99／144.172.64[.]60・いずれも同一の /24）。 Cloud Backup と Exchange・Teams・SharePoint Online および自社製品との統合は無効化され、 スケジュールバックアップ・アーカイブの参照・リストア・SaaS Security の監視と Cloud Management のユーザー/ライセンス管理が使えない状態が続く。 帰属については「現時点で脅威アクターの帰属について話すことはできない」とされた

掲載の5分間——全体管理者への自己昇格と、他アプリへの資格情報の植え付け原因・手口

Huntress の観測で最も重いのは、不正サインインの約2時間半前、1つの顧客テナントで起きた5分間である。

時刻（UTC） 出来事

03:44〜03:49 Python のスクリプト（User-Agent: Python-urllib/3.12）が、テナント内の別の2つのアプリ——MSP 管理アプリと Huntress Security Platform——に新しいクライアントシークレットを追加（9件の変更のうち6件成功・3件失敗）

失敗した3件のうち1件は証明書の追加で、Microsoft が thumbprint の不一致として拒否した。その後に追加されたクライアントシークレットは成功している。追加されたシークレットの有効期限は2028年に設定されていた。

ここが効く理由は、アプリに資格情報を足す操作の性質にある。クライアントシークレットと証明書は、アプリが Entra に自分を証明する2つの手段で、どちらを持っていても同じアクセスが得られる——そのアプリとして、どこからでもサインインできる。アプリのみのサインインには利用者も端末も介在せず、MFA の確認も出ない。シークレットを作った者はその値を作成時に見られるため、誰かが削除するまで、攻撃者は両アプリの有効な資格情報を保持し続ける。これは MITRE ATT&CK の T1098.001（Account Manipulation: Additional Cloud Credentials）である。

しかも資格情報を足された2つは、どちらも信頼され特権を持つ道具である。MSP 管理アプリへの資格情報追加は、そのアプリが MSP の顧客テナントに同意されていることが多いため、1テナントを超えて広がりうる。セキュリティ製品のアプリへの資格情報は、その製品に許された操作をそのまま与える。

なお Huntress は、この5分間と06:13以降の不正サインインを同一の実行者と結び付けていない。前段の操作には送信元IPが記録されず、User-Agent はConnectWise 自身のアプリが使う kiota-dotnet（ベンダーの自動処理を示す）だが、03:44 の操作に続く変更は Python の User-Agent であり、ベンダーのアプリとは異なっていた。

同じIPは2日前から試していた——法律事務所4テナントへのパスワードスプレー背景・過去事例

  • 10月13日〜14日: 法律事務所4テナントに対するパスワードスプレー。OAuth2 のトークン要求をスクリプト（User-Agent: curl/7.88.1）で投げる形で、2アカウントが Entra のスマートロックアウトで施錠された。Huntress の観測範囲では、このIPからの利用者サインインの成功は無かった
  • 同じ期間に、他のツールのクライアントアプリケーションIDを使ったサインイン試行も行われた

つまり攻撃者は、まず総当たり気味の試行をしてから、手元のベンダー資格情報を使う段階に移っている。User-Agent（curl/7.88.1・Python-urllib/3.12・kiota-dotnet）はどれもこの攻撃者固有のものではなく、Python と curl は通常の運用でも日常的に現れる。使えるのは「どのアプリが、どの操作を、どの User-Agent で行ったか」の組み合わせであって、User-Agent 単独ではない。

ConnectWise は2026年10月16日13:47（EDT）、Trust Center に「Cloud Backup (formerly known as SkyKick) Service Interruption」を掲載した（10月17日01:01 EDT に更新）。本記録の作成者が取得して確認した内容は次のとおりである。

  • 「ConnectWise Cloud Backup 環境内のアプリケーション識別情報への不正アクセスを確認した」（原文英語）
  • 保護措置として Cloud Backup のアプリケーションアクセスを停止した
  • その結果、パートナーとその顧客のバックアップサービスが中断している
  • 現時点で、パートナーのバックアップデータが侵害された兆候は無い
  • 既存のクラウドバックアップアーカイブは影響を受けておらず、サービス復旧後に参照できる
  • 監視のための情報として、Entra 管理センターでのサインインログの確認方法・アプリケーションID・不審なIPアドレス（144.172.64.128）を記載
  • 不審な活動は SecurityPartnerSupport@ConnectWise.com へ報告するよう求めている

告知で使われているのは「アプリケーション識別情報（application identities）」という語で、「資格情報（credential）」は使われていない。ベンダー側で何がどう奪われたか、侵害がいつ始まったかには触れていない。

顧客側が取れる手は「止める」であって「調べて判断する」ではない対策・注意喚起

Huntress の指示は、調査結果を待たずに止めるという形になっている。これは確認手段が無いことの裏返しである。

  1. Entra 管理センターの「エンタープライズ アプリケーション」でアプリケーションID 506e08f9-6e9a-4da4-942b-a099a03644ae（「SkyKick」「ConnectWise Cloud Backup」でも検索できる）を開き、プロパティの「ユーザーがサインインできるようにする」をいいえにする
  2. 削除はしない。 削除すると同意が外れ、復旧には再同意が必要になる
  3. テナント内の他の ConnectWise / SkyKick アプリを点検し、安全と確認できないものは同様に（削除せず）無効化する。古いテナントではCloud Management 系が「SkyKick Cloud Manager」として見えることがある
  4. ConnectWise / SkyKick のアプリがディレクトリロール（特に全体管理者・特権認証管理者）を持っていれば見直し、意図して付与していないロールはアプリ無効化後に削除する
  5. 全エンタープライズアプリケーションとアプリ登録の資格情報（クライアントシークレットと証明書）を点検し、10月13日以降に追加された心当たりの無いものを削除する。特に管理系・セキュリティ系の道具
  6. Entra の監査ログで、ConnectWise / SkyKick アプリがディレクトリロールに自らを追加していないか、他のアプリを変更していないかを確認する
  7. 条件付きアクセスの除外設定を見直す。このアプリを場所ベースのブロックから除外しているポリシーがあれば、攻撃者のインフラもそこでは止まらない
  8. サインインログは「サービスプリンシパルのサインイン」タブで見る。既定の「ユーザーのサインイン」タブには出ない

副作用は明確である。アプリを無効化すると、再有効化するまで自動バックアップが止まる。メール・ファイル・Teams・利用者のサインインは動き続け、ConnectWise が保持する既存のバックアップも削除されない。判断すべきは「復旧ポイントの空白が自社にとって許容できるか」である。

そしてログがきれいでも除外にはならない。 Huntress が「結果が白でもアプリは無効化せよ」と書いているのは、ディレクトリ読み取りが痕跡を残さないからである。

Microsoft が公式に確認した——そして「アプリを止めた」だけでは終わらない再発防止出典 [4] [5] [6]

10月17日、Microsoft がこの事案を公式に確認した。 Microsoft Threat Intelligence は「進行中のサプライチェーン攻撃を追跡している」とし（原文英語）、ConnectWise Cloud Backup の信頼された OAuth アプリが侵害されたこと、10月15日に 144.172.64[.]128 からのサービスプリンシパル認証の成功を広範に観測したことを述べた。認証の成功後にはバックドアによる足場の確保、Microsoft Graph API を使った偵察、サービスプリンシパルへの資格情報追加の試みが続いたとしている。攻撃者が悪用したのは顧客が以前に同意した権限で、Directory.ReadWrite.All を含む、というのが Microsoft の評価である。

これで、本件を観測した3者——Huntress・Microsoft・Todyl——がいずれも同じIPアドレス 144.172.64[.]128 を指している。ベンダー、プラットフォーム提供者、第三者の監視事業者が独立に同じ痕跡に到達しており、「起きたこと」自体はもう争点ではない。

注目すべきは、停止と失効のあいだに約12時間が空いていることだ。アプリを止めるのは「これ以上、新しいトークンを出さない」措置であり、証明書の失効は「攻撃者が持っている鍵を使えなくする」措置である。Todyl が指摘するとおり、アプリを無効化しても発行済みのトークンは期限切れまで有効で、利用者セッションの失効はアプリケーション単位のアクセスを止めない。ConnectWise 自身も「発行済みのアクセストークンは期限切れまで使える可能性がある」と注記している。つまりこの12時間は、止めたつもりで止まっていない時間でありうる。

そして、ベンダーが何をしても顧客テナントに植えられた資格情報は消えない。 Huntress が1テナントで観測した、アプリが自らを全体管理者に昇格させ、別のアプリに2028年期限のシークレットを足していった5分間の操作は、ConnectWise 側の停止や失効とは無関係に残り続ける。管理者が自分のテナントで、10月13日以降に追加されたシークレットと証明書を自分で探して消すしかない。これは「ベンダーが直したから終わり」と言えない型の事案である。

停止は3日目に入り、バックアップが取れない時間がそのまま復旧可能性の空白になっている復旧の経過出典 [7] [8]

ConnectWise が Cloud Backup のアプリケーションアクセスを停止したのは10月17日05:01（UTC）である。10月19日01:15（UTC）の更新時点でも、復旧の時期は示されていない。ここまでで約44時間（1日20時間14分）が経過している。

止まっているのは、次のとおりである。

  • スケジュールバックアップ（新しいバックアップが取られない）
  • アーカイブへのアクセス（過去のバックアップを参照できない）
  • リストア（復元できない）
  • SaaS Security の監視とアラート
  • Cloud Management のユーザー・ライセンス管理

バックアップ事業者の停止は、他のサービスの停止と性質が違う（本記録の評価）。業務システムが止まれば、その間の業務ができない——損失は停止中に発生する。バックアップが止まった場合、停止中は何も起きない。損失が現れるのは、この期間に作られたデータが失われたときである。つまり、停止が長引くほど「戻せない範囲」が静かに広がる。

しかも、今この瞬間に別のインシデント（ランサムウェア・誤削除・退職者の持ち出し）が起きた MSP の顧客は、復元もできない。 The Register が指摘するとおり、エンドユーザーはバックアップの取得も、アーカイブの参照も、データの復元もできない状態にある。

ConnectWise 側の説明は一貫している—— 「既存のアーカイブは暗号化・隔離された状態で保持されており、不正アクセスの証拠は無い」（security operations 担当 VP の Jason Ferguson によるReddit への投稿・原文英語）。つまり、停止はデータが壊れたからではなく、「安全に動かせる確信が持てないから」である。 10月19日の更新では「対策後、監視対象の環境で成功した脅威活動は確認していない」として、封じ込めが効いていることも示している。

判断そのものは妥当である（本記録の評価）。MSP 向けのバックアップ基盤が侵害された状態で動き続けることのほうが危険であり、止めるという選択は正しい。問題は期間の見通しが示されないことにある。MSP は顧客に対して「いつ戻るか」を説明できず、代替のバックアップ手段を手配すべきかどうかも判断できない。復旧時期が未定であること自体は事実として仕方がないが、「現時点では示せない」と「いつ示せるかも分からない」の間には差がある。 ConnectWise は次回更新の時刻（10月19日13:00 UTC まで）を明示しており、更新の頻度を約束する形で、この差を埋めようとしている。

ここから、実務上の注意が2つ出てくる（以下は本記録の整理）。

①IoC を「3つのIP」ではなく「/24」で見るほうがよい。同一レンジから3つ出ているということは、攻撃者がそのホスティング事業者の範囲を使っているということである。ハンティングの条件を個別のIPに固定すると、4つ目が出たときに引っかからない。サービスプリンシパルのサインインを調べるときは、レンジ単位、あるいは「Azure のプライベートIP空間以外からのConnectWise アプリのサインイン」という条件で引くほうが取りこぼしが少ない。

②IoC が後から増えることを前提に、記録を保全しておく。 ConnectWise はパートナーに対し、監査ログとサインインログをエクスポートして保全するよう求めている。これは「今の IoC で調べて終わり」ではなく、後から増える指標で何度でも引き直せる状態にしておけという意味である。Microsoft 365 の監査ログは保持期間に上限があるため、エクスポートしておかないと、新しい IoC が出た頃には調べる材料が消えている。

ConnectWise の告知は、これらの指標について「活動を確認するための材料であり、単独で侵害を証明するものではない」と明記している（原文英語）。ヒットしたからといって侵害とは限らず、ヒットしなかったからといって安全でもない——とくに、顧客テナントに植えられた資格情報は、攻撃元IPとは無関係に残り続ける。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
ConnectWise は、Cloud Backup のアプリケーションアクセスを停止した。 その結果、パートナーとその顧客のバックアップサービスが中断している機能した**本記録の評価である。**顧客側に予防手段が存在しなかった事案で、 ベンダー側の経路を断つ以外に全テナントを一度に守る方法は無い。 資格情報の個別リセットよりも確実で、速い。 ただし復旧の見通しが示されていないため、 空白がどこまで伸びるかをパートナーが見積もれない点は評価を留保する
ConnectWise の告知は「アプリケーション識別情報への不正アクセスを確認した」 という事実と、監視用のIOC（アプリケーションID・不審なIPアドレス）までを示し、 侵害の経路・時期・影響テナント数には触れていない部分的に機能**本記録の評価である。**IOC と確認手順を初報から出した点は、 パートナーが即座に動ける材料として機能している。 他方、影響範囲の数が外部のセキュリティ事業者（Huntress）からしか出ていない状態は、 **ベンダーの告知だけでは自社の立場が分からない**という構造を残している
CISO・経営層への示唆
  • SaaS の「同意」は、ベンダーのテナントに自社データへの鍵を1本置くことである
    本件で侵害されたのは顧客側の何かではなく、ベンダー自身のテナントに存在する client assertion 型の資格情報だった。顧客が取りうる予防手段は存在しなかった
    取るべき行動 自社テナントに同意済みのエンタープライズアプリケーションを棚卸しし、 **「このアプリの資格情報が奪われたら何が読めるか」を1行で書く。** 書けないアプリは権限が過大か、用途が不明である。 棚卸しは年1回ではなく、同意の追加時に必ず行う手順に組み込む
  • バックアップ製品は、権限の大きさで見れば「全データへの読み書き」である
    バックアップと復元の双方をこなすため、Cloud Backup は メールボックス・OneDrive / SharePoint・Teams・ディレクトリへの 広範な権限を全テナントで同意されていた。1つの資格情報の侵害が、 そのまま全テナントの読み書き権限になった
    取るべき行動 バックアップ・DLP・監査・移行ツールなど「全データに触る」系の SaaS を 別の格付けに置き、**ベンダー側侵害を前提にした停止手順**（止めたときの 業務影響・許容できる空白期間・代替手段）を事前に文書化しておく
  • 「痕跡が無い」は「被害が無い」ではない。影響を確定できない事案がある
    Microsoft Graph 経由のディレクトリ読み取りは監査記録を残さない。 Entra の監査ログは app-only の操作に送信元IPを記録せず、 追加された資格情報の詳細も記録しない。影響の確定が原理的にできない
    取るべき行動 **「影響が確定できない」場合の判断基準を平時に決めておく。** 通知するか、顧客へ何を伝えるか、何日待つか。 事案の最中に決めると、確定を待つ側に流れて何も言えないまま時間が過ぎる
  • MSP に運用を預けているなら、MSP のテナントは自社の攻撃面である
    MSP 管理アプリへの資格情報追加は、そのアプリが MSP の顧客テナントに 同意されていることが多いため、1テナントを超えて広がりうる。 本件では実際に、1つの顧客テナントで MSP 管理アプリへシークレットが追加された
    取るべき行動 MSP との契約に「MSP 側テナントでの侵害を認識した場合の通知義務（時間を明記）」と 「顧客側からの緊急無効化の権利」を入れる。 MSP が自社テナントで持つアプリとロールの一覧を、年1回以上提出させる
セキュリティ技術者への示唆
  • サービスプリンシパルのサインインを見ていなければ、この攻撃は見えない
    不正サインインは最初から Microsoft のサインインログに残っていた。 しかしアプリのみのサインインは Entra 管理センターの既定タブ （ユーザーのサインイン）に出ず、「サービスプリンシパルのサインイン」タブを 開かないと現れない
    取るべき行動 サービスプリンシパルのサインインログを SIEM に取り込み、 **アプリごとに正規の送信元IP範囲をベースラインとして持つ。** Cloud Backup の正規の送信元は Azure のプライベートIPv6 であり、 そこから外れたサインインは単独で警報に値する
  • アプリが自分にロールを付ける操作と、アプリへの資格情報追加は、単独で警報にする
    10月15日03:44〜03:49（UTC）の5分間で、アプリが自らを全体管理者に昇格させ、 他の2アプリにクライアントシークレットを追加した。 正常運用でまず起きない操作であり、量も少ないため警報の負担は小さい
    取るべき行動 Entra 監査ログで次の2つを即時警報にする。 ①サービスプリンシパルへの特権ロール（全体管理者・特権認証管理者・ アプリケーション管理者）の割り当て ②アプリ登録・エンタープライズ アプリケーションへのクライアントシークレット／証明書の追加。 正規の資格情報更新は年に数回であり、誤検知は運用で吸収できる
  • User-Agent 単独では判別できない。「どのアプリが・何を・どの UA で」の組み合わせで見る
    本件では curl/7.88.1（パスワードスプレー）・Python-urllib/3.12（アプリ変更）・ kiota-dotnet（ベンダーの正規自動処理）が現れたが、 Python と curl は通常の管理作業でも日常的に使われる
    取るべき行動 監査イベントの検知ルールを「操作の種類 × 実行主体（アプリ） × User-Agent」で組む。 ベンダーのアプリが使う UA（本件では kiota-dotnet）を把握しておき、 **同じアプリが別の UA で現れたこと**を異常として扱う
  • 条件付きアクセスの除外設定は、インシデント時にそのまま穴になる
    Huntress は「このアプリを場所ベースのブロックから除外しているポリシーがあれば、 攻撃者のインフラもそこでは止まらない」と指摘している
    取るべき行動 条件付きアクセスのアプリ単位・サービスプリンシパル単位の除外を一覧化し、 各除外に「なぜ必要か・いつ見直すか」を書く。 除外の棚卸しを四半期ごとに行い、**理由を書けない除外は外す**
  • アプリ資格情報の有効期限に上限を設けておく
    攻撃者が追加したクライアントシークレットの有効期限は2028年に設定されていた。 誰かが削除するまで、約2年にわたって有効な資格情報を持ち続けられる
    取るべき行動 アプリ資格情報の最大有効期限をポリシー（Entra のアプリ管理ポリシー）で 制限し、長期の資格情報を構成上作れないようにする。 あわせて、全アプリの資格情報の作成日・作成者・有効期限を定期に出力し、 説明できないものを削除する手順を持つ
