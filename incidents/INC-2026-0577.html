INC-2026-0577Power BI経由でScreenConnect導入

Huntress は2026年10月7日、**Microsoft Power BI の正規ドメイン上に 偽の「参照資料」ページを置き、そこから RMM ツール ScreenConnect を導入させる フィッシング**を公表した。 経路は **Outlook のメール → Power BI の正規ドメイン → 攻撃者のサイト → ScreenConnect のインストーラ**で、 **攻撃者のサイトは閲覧環境を調べて結果を Telegram のボットへ送り、 条件に合わなければ別のページへ飛ばしてから、 数秒後に隠しリンクを自動で押してインストーラを取得させる。** **導入後は2つ目のクライアントを入れて1つ目を消す**—— **防御側が見つけた1つを消しても、もう1つが残る形**である。 **2分ごとに動くスケジュールタスク `SCAutoRepairEvery2Min` と、 検知回避ツール `HideUL_x64.exe` も使われた。** **観測は「複数のエンドポイント」にとどまるが、 さかのぼり調査で同じクライアントと設定が 別のインシデントの22台でも見つかっている**

脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）
初報: 2026年10月7日 最終更新: 2026年10月18日

Huntress は2026年10月7日、Microsoft Power BI を悪用したフィッシングを公表した（著者: Sarah Reddish。事実）。同社は「9月10日から、このフィッシングキャンペーンを確認した」としている（年の明記は本文に無い。unknowns 参照）。

流れは4段である。

  1. Outlook で届くフィッシングメールのリンクを押すと、Microsoft Power BI の正規ドメイン上にある「参照資料」を装ったページへ飛ぶ。
  2. ページの「Download Reference」ボタンを押すと新しいタブが開き、攻撃者が用意したサイトへ移る。
  3. 攻撃者のサイトは閲覧環境を調べ、結果を Telegram のボットへ送る。条件に合わない相手は別のページへ飛ばす。
  4. 数秒の遅延のあと、スクリプトが隠しダウンロードリンクを自動で押し、ScreenConnect のインストーラ（ScreenConnect.ClientSetup.exe）を取得させる。

導入後の動きに本件の特徴がある（事実）。不正な ScreenConnect クライアントは2つ入る（2b302081e9e777d0 と 43773b3da4ccb17b）。1つ目が PowerShell スクリプト SCAutoFix.ps1 を実行して2つ目を入れ、そのうえで1つ目自身を削除する。 検知回避ツール HideUL_x64.exe が実行され、2分ごとにスクリプトを走らせるスケジュールタスクSCAutoRepairEvery2Min が作られた。

確認されたのは「複数のエンドポイント」だが、さかのぼり調査で同じ RMM のクライアントと設定が別のインシデントの22台でも見つかっている。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は Huntress の分析で示された動作である**（事実）。 **各段階の検知の機会について、同社は被害側の検知の成否を述べていない**ため、 **評価は本記録のものであることを明示する。** **本件の設計上の要点は3つ**—— ①**各段で「正規のもの」を使い、検知の根拠を1つずつ外している** （Power BI の正規ドメイン・正規の商用 RMM・正規の Windows の仕組み）、 ②**フィンガープリントで自動解析をふるい落としている**、 ③**クライアントを2つ入れて1つを消すため、 1つ見つけて消す対応では残る。**

  1. 1. 初期侵入[1]
    **Outlook で届くフィッシングメールのリンクから、 Microsoft Power BI の正規ドメイン上に置かれた 「参照資料」を装ったページへ誘導される。** **Huntress は「脅威アクターは正規の Power BI のドメインを悪用して 攻撃をもっともらしく見せ、このサービスを信頼する セキュリティ上の仕組みを回避している」としている**（原文英語）。 **ページには「Download Reference」ボタンが置かれている。**
  2. 2. 検知回避[1]
    **「Download Reference」を押すと新しいタブが開き、 攻撃者のサイトへ移る。** **サイトは閲覧者の環境をフィンガープリントし、 結果を Telegram のボットへ送る。** **条件に合わない相手は別のページへ転送される。** **条件に合う場合のみ、数秒の遅延のあとスクリプトが 隠しダウンロードリンクを自動で押す。**
  3. 3. 実行[1]
    **取得された `ScreenConnect.ClientSetup.exe` が実行され、 不正な ScreenConnect クライアントが導入される。** **攻撃者のテナントは `hamham27[.]screenconnect[.]com`、 中継は `instance-g01s1n-relay[.]screenconnect[.]com`、 ゲストトークンは `ILEAYEASAN`・`PERFECTO`・`PAPASUPE` など。** **導入されるのは正規の商用 RMM であり、 マルウェアとしての検知名を持たない。**
  4. 4. 永続化[1]
    **不正なクライアントは2つ導入される** （`2b302081e9e777d0` と `43773b3da4ccb17b`）。 **1つ目が PowerShell スクリプト `SCAutoFix.ps1` を実行して 2つ目を導入し、そのうえで1つ目自身を削除する**（Huntress の記述）。 **さらに検知回避ツール `HideUL_x64.exe` が実行され、 2分ごとにスクリプトを走らせるスケジュールタスク `SCAutoRepairEvery2Min` が作られる。**
  5. 5. C2通信[1] [2]
    **攻撃者は ScreenConnect を通じて被害端末へ遠隔アクセスする** （iThome の要約・Huntress の分析）。 **通信は `hamham27[.]screenconnect[.]com` および `instance-g01s1n-relay[.]screenconnect[.]com` を経由する。** **遠隔アクセス後に何が行われたか （持ち出し・横展開・暗号化の有無）は公表されていない。**

各段で「正規のもの」が並び、遮断する根拠が1つずつ外されている概観

本記録が本件の核心と見るのは、技術的な新しさではなく「止める理由が出てこない」ことのほうである（本記録の評価）。

経路の各段を並べると、こうなる（事実）。

段 使われるもの 正規かどうか
メール Outlook で届くリンク リンク先は正規
1段目の着地 Microsoft Power BI のドメイン 正規
2段目 攻撃者のサイト（.site ドメイン群） 不正
導入物 ScreenConnect（商用 RMM） 正規の製品
永続化 PowerShell・スケジュールタスク 正規の Windows の仕組み

不正だと機械的に言えるのは2段目だけである。 しかもその2段目は、閲覧環境をフィンガープリントして条件に合わない相手を別ページへ逃がす—— 自動のスキャンやサンドボックスからは「何も起きない」ように見える。

Huntress の記述はこうである（原文英語）——「脅威アクターは正規の Power BI のドメインを悪用することで、攻撃をよりもっともらしく見せ、このサービスを信頼するセキュリティ上の仕組みを回避している。」

ここから出る実務上の結論は1つである（本記録の評価）。「リンク先が Microsoft のドメインなら安全」という判断基準は、利用者教育においても自動の仕組みにおいても成立しない。 本件で判定に使える軸は、ドメインの評判ではなく「その資料を、その相手から、その経路で受け取るのが業務上自然か」という文脈のほうである。

クライアントを2つ入れて1つを消す——見つけて消す対応では終わらない原因・手口

本件でもっとも実務に効く発見である（本記録の評価）。

Huntress が記述した動作はこうである（事実）。

  • 不正な ScreenConnect クライアントが2つ導入される（2b302081e9e777d0 と 43773b3da4ccb17b）。
  • 1つ目が PowerShell スクリプト SCAutoFix.ps1 を実行し、2つ目を導入したうえで1つ目自身を削除する。
  • 検知回避ツール HideUL_x64.exe が実行される。
  • 2分ごとにスクリプトを走らせるスケジュールタスクSCAutoRepairEvery2Min が作られる。

この構成が防御側に何をするか（本記録の整理）—— 防御側が「不正な RMM が1つ入っている」ことを見つけて削除したとき、対応は完了したように見える。 しかし消したのは、攻撃者がすでに捨てたほうかもしれない。 残っているのは、防御側がまだ知らない2つ目である。

Huntress の推奨にも同じ趣旨の項目がある（原文英語）——「RMM のクライアントが複数入っているエンドポイントを調査する。」

本記録はこれを一般化して記録する（本記録の提言）。RMM の不正利用を見つけたときは、「1つ見つけた」で打ち切らずに、①その端末に他の RMM クライアントが無いか、②同じ設定（テナント・リレー）が他の端末に無いか、の2つを必ず確認する。 後者については、Huntress 自身がさかのぼり調査を行い、同じクライアントと設定を別のインシデントの22台で見つけている。

判定の軸は「製品が何か」ではなく「どのテナントにつないでいるか」対策・注意喚起

ScreenConnect は正規の商用 RMM であり、IT 部門が業務で使う道具でもある（事実）。したがって「ScreenConnect が入っている」だけでは異常と言えない。

Huntress の推奨は4つである（原文英語を要約）。

  1. 信頼されたクラウドサービス上のリンクに対するフィッシング対策と、利用者からの報告手順を見直す。
  2. 新規または想定外の ScreenConnect の導入、未承認インスタンスへの接続、スケジュールタスクやスクリプトの作成を監視する。
  3. リモート管理ソフトウェアを承認済みのインスタンスに限定する。
  4. RMM クライアントが複数入っているエンドポイントを調査する。

本記録が最も効くと見るのは3番目である（本記録の評価）。理由は、判定の根拠が「製品の正規性」から独立しているためである—— インストーラが差し替えられても、署名が有効でも、検知名が付かなくても、「承認していないテナントにつないでいる」ことは変わらない。

本件の該当テナントは hamham27[.]screenconnect[.]com、中継は instance-g01s1n-relay[.]screenconnect[.]com である（事実）。ただし指標は変わる—— 次の事案では別のテナント名になる。 したがって運用としては「このテナントを遮断する」ではなく「許可したテナント以外を遮断する」の形で作る必要がある（本記録の提言）。

自組織が RMM を1つも使っていない場合は、判定はさらに単純になる——RMM の導入そのものが検知の根拠になる。 「使っていないから関係ない」ではなく「使っていないからこそ強い検知規則が書ける」と読むべきである（本記録の評価）。

誰のアカウントで Power BI にページが置かれたかは公表されていない未確定事項

本件で公表されていないことのうち、読者の判断に影響するものを挙げる（事実と、その読み）。

  • 攻撃者がどうやって Power BI 上にページを用意したか。 新規に作った試用アカウントなのか、侵害された組織のテナントなのかは述べられていない。 Microsoft 側の対応（ページの削除・アカウントの停止）についても記述が無い。
  • 遠隔アクセス後に何が行われたか。 Huntress は導入と永続化までを記述し、持ち出し・横展開・暗号化の有無には触れていない。 本件が窃取目的なのか、ランサムウェアの前段としての初期アクセスなのかは分からない。
  • 本キャンペーンで直接確認されたエンドポイントの台数。 「複数のエンドポイント」とのみ。 22台は別のインシデントのものであり、本件の規模ではない。
  • 観測開始の「9月10日」の年。 本文に明記が無く、公開日（2026年10月7日）から推定している。

本記録は、これらを埋めずに残す（本記録の方針）。とくに「誰のアカウントか」は、自組織が加害の踏み台になりうるかという別の問いにつながるが、分からないものを分かったように書くとその問いの立て方自体が狂う。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「リンク先が Microsoft なら安全」という教え方をやめる
    **本件の1段目の着地は Microsoft Power BI の正規ドメインである**（事実）。 **Huntress は「正規の Power BI のドメインを悪用することで 攻撃をもっともらしく見せ、このサービスを信頼する セキュリティ上の仕組みを回避している」としている**（原文英語）。 **ドメインを見る訓練をしてきた組織ほど、 この手口は訓練どおりに通る**（本記録の評価）。
    取るべき行動 **フィッシング訓練と教育資料から 「URL が正規のクラウドサービスかどうかで判断する」という 判定基準を外し、 「その資料を、その相手から、その経路で受け取るのが業務上自然か」に 置き換える。** **あわせて、判断に迷ったときの報告先と、 報告しても咎められないことを明文化する。**
  • RMM を「使っているか」ではなく「どのテナントを承認しているか」で管理する
    **導入されたのは正規の商用 RMM（ScreenConnect）であり、 マルウェアとしての検知名を持たない**（事実）。 **Huntress の推奨の中核も 「リモート管理ソフトウェアを承認済みのインスタンスに限定する」である。** **製品の正規性では判定できないが、接続先では判定できる** （本記録の評価）。
    取るべき行動 **①自組織で承認している RMM 製品とテナント（サブドメイン）の一覧を作る。 ②一覧に無いテナントへの接続を遮断する。 ③委託先・保守業者が持ち込む RMM も一覧に載せる （載っていないものは使わせない）。** **RMM を一切使っていない組織は、その事実を明文化して 「RMM の存在＝異常」とする検知規則を書く。**
  • 「見つけて消した」で終わらせない対応手順にする
    **本件では不正なクライアントが2つ入り、 1つ目が2つ目を入れたうえで自身を削除する**（事実）。 **防御側が1つ見つけて消しても、 消したのは攻撃者がすでに捨てたほうかもしれない**（本記録の読み）。 **さらに2分間隔のスケジュールタスクが残る。**
    取るべき行動 **RMM・遠隔操作ツールの不正利用を確認したときの手順に、 「同一端末の他の RMM クライアントの全数確認」と 「同じテナント・リレー設定を持つ他端末の横断検索」を 必須の工程として入れる。** **スケジュールタスクとサービスの新規作成の棚卸しも同じ工程に含める。**
  • 他社の調査レポートは、要約ではなく原典に当たる体制を持つ
    **本記録がこの事案を把握した要約（iThome・2026年10月16日）は 経路とフィンガープリントまでを伝えているが、 2つのクライアントの入れ替え・`HideUL_x64.exe`・ `SCAutoRepairEvery2Min`・22台のさかのぼり調査には触れていない**（事実）。 **本記録が本件の中心と判断した「1つ消しても1つ残る」構造は、 原典に当たらないと出てこなかった**（本記録の評価）。
    取るべき行動 **自組織の対応を変える可能性がある事案については、 要約で止めず原典（ベンダーの分析本文と IoC）まで読む担当と時間を あらかじめ割り当てる。** **「読む価値がある原典」を選ぶ基準を （例: 自社が使っている製品が関わる／初期侵入の手口が新しい） 先に決めておく。**
セキュリティ技術者への示唆
  • 承認済み以外の RMM テナントへの通信を遮断する規則を書く
    **接続先は `hamham27[.]screenconnect[.]com` と `instance-g01s1n-relay[.]screenconnect[.]com` だった**（事実）。 **ドメインの評判では止まらない**——**ConnectWise の正規ドメインである。** **指標は次の事案で変わるため、 「このテナントを塞ぐ」ではなく 「許可したテナント以外を塞ぐ」で作る必要がある**（本記録の提言）。
    取るべき行動 **プロキシまたは DNS の層で、RMM ベンダーのドメインに対して 許可リスト方式（承認したサブドメインのみ許可）を設定する。** **テナント単位の可視性が無い経路については、 その経路自体を RMM 通信の対象外にできないかを検討する。**
  • 2分間隔のような不自然なスケジュールタスクを洗い出す
    **本件では `SCAutoRepairEvery2Min` という 2分ごとにスクリプトを実行するタスクが作られた**（事実）。 **業務用途で分単位の繰り返しタスクが作られることは多くない** （本記録の評価）。 **間隔そのものが手がかりになる。**
    取るべき行動 **全端末のスケジュールタスクを収集し、 「繰り返し間隔が10分未満」かつ 「PowerShell またはスクリプトを起動する」ものを一覧化する。** **一度棚卸しして正規のものを登録すれば、 以後は差分だけを見ればよい。**
  • 既知の指標で「過去に踏んだ者」を探す
    **攻撃者のサイトは閲覧環境をフィンガープリントし、 条件に合わない相手を別ページへ逃がす**（事実）。 **自動の URL 検査では原理的にすり抜ける**（本記録の評価）。 **したがって既知の指標は「次を防ぐ」より 「すでに踏んだ端末を見つける」ために使うほうが効く。**
    取るべき行動 **`dailylifeproject[.]site`・`burnsworth[.]site`・ `essaywritingservice[.]site`・`openpediatrics[.]site`・ `onthegotree[.]site` と `hamham27[.]screenconnect[.]com` を、 プロキシ・DNS・EDR の過去ログに対して遡及照合する。** **運用に組み込むときは Huntress の原典から IoC の全量を取ること** （本記録は一部しか確認していない）。
  • RMM の導入そのものをイベントとして記録できるようにする
    **本件の実行段で動いたのは正規のインストーラである**（事実）。 **Huntress の推奨にも 「新規または想定外の ScreenConnect の導入を監視する」とある。** **検知名に頼れない以上、 「入った」という事実自体を記録に残す必要がある**（本記録の評価）。
    取るべき行動 **主要な RMM 製品（ScreenConnect・AnyDesk・TeamViewer・ Atera・Splashtop 等）のインストールとサービス登録を EDR またはソフトウェア資産管理で検知対象に設定する。** **検知時に「承認済みテナントか」を即座に確認できるよう、 前述の承認一覧と突き合わせる手順まで用意しておく。**
