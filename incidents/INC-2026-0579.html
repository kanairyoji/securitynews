INC-2026-0579Next.js に未認証 RCE 2件

Next.js が定例外のセキュリティ更新で未認証リモートコード実行2件を修正—— 画像最適化 API の SVG 経路（CVE-2026-96889・CVSS v4.0 9.5・Next.js 10.0.0〜15.5.27 と 16.0.0〜16.4.0）と `use cache` が型付き配列を返す経路（GHSA-673q-mjm6-r5xr・同 9.5）。3件はいずれも上流依存（librsvg・React）に由来し、 2件は9月のリリースから上流調整の遅れで延期されていた

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月14日 最終更新: 2026年10月18日

フレームワークのパッチ適用が、依存ライブラリの解決結果の確認とセットになった事例です。

2026年10月14日、Next.js 開発チームは定例外（out-of-band）のセキュリティ更新v16.4.1（Active LTS）と v15.5.28（Maintenance LTS）を公開し、重大（Critical）2件・高（High）1件の脆弱性を修正しました（出典1）。重大2件はいずれも未認証でのリモートコード実行（RCE）で、CVSS v4.0 基本値は 9.5 です（出典2・3）。

本記録が要点と見たのは、次の3点です。

  • 影響する版の下限が古い。 CVE-2026-96889（画像最適化 API の SVG 経路）の対象はNext.js 10.0.0〜15.5.27 および 16.0.0〜16.4.0 で、2020年の世代まで遡ります（出典2）。一方で成立条件は限定的で、glibc ベースの Linux 上で動いている場合とされています（出典1・2）。さらに Next.js は既定では画像最適化 API で SVG を最適化しません——公式ドキュメントは「既定では Next.js は SVG 画像を最適化しない」と明記し、有効化には dangerouslyAllowSVG の設定が必要です（出典9）。
  • Next.js を上げるだけでは終わらない可能性がある。 勧告は回避策として「Next.js が使う sharp の版が 0.35.5 以降であることを確かめる」ことを挙げ、修正版への更新は「パッケージマネージャが修正済みの sharp を自動的に供給することを保証する」と書いています（出典1・2）。つまり実際に解決された sharp の版を見るという手順が、勧告自身によって示されています（本記録の整理）。
  • use cache の RCE には回避策が無い。 GHSA-673q-mjm6-r5xr は「影響を受けるアプリケーションに既知の回避策は無い。同種の関数が無いアプリケーションでも直ちに更新すべきだ」としています（原文英語・出典3）。対象は Next.js 16.0.0〜16.4.0 で、修正は 16.4.1 のみです（出典3）。

この更新は10月8日に予告されていました。 開発チームは「来週水曜、2026年10月14日に定例外のセキュリティ更新を公開する予定である。上流依存の3件——重大2件と高1件——に対処する。うち2件は上流との調整のため9月のセキュリティリリースから延期されたものである」と事前に告知しています（原文英語・出典4）。実際、9月30日の 15.5.27 / 16.3.8 のリリース記事にも「重大1件と高1件の修正が上流依存の遅れにより延期された」と記されていました（出典5）。悪用の観測については、3件の勧告・2本のリリース記事のいずれも言及していません〈未確定1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

以下は CVE-2026-96889（画像最適化 API の SVG 経路）について、公表された勧告の記述から 成立経路を整理したものである。実際の悪用は観測が公表されていない（〈未確定1〉）ため、想定経路である。 未認証の攻撃者が画像最適化 API に細工した SVG を処理させ、 下層ライブラリのメモリ関連の欠陥を踏ませることで、サーバー側でコードを実行する。 勧告が示す前提は「glibc ベースの Linux 上で動作していること」であり、 加えて Next.js は既定では画像最適化 API で SVG を扱わない（`dangerouslyAllowSVG` が必要）。

  1. 1. 偵察推定[2] [9]
    攻撃者は、対象サイトが Next.js の画像最適化 API を公開しているか、 SVG を最適化対象にしているかを外部から調べる。認証は不要で、 攻撃元の制約も公表されていない（CVSS ベクタ AV:N）
    根拠: GHSA-2464-fhr4-w9xw の CVSS ベクタ（AV:N/PR:N/UI:N）
  2. 2. 初期侵入disclosed[1] [2] [9]
    攻撃者は細工した SVG を画像最適化 API に処理させる。 勧告は成立条件として glibc ベースの Linux 上での動作を挙げている。 要求の具体的な形は公開されていない
    根拠: GHSA-2464-fhr4-w9xw および2026年10月14日付リリース記事の記述
  3. 3. 実行disclosed[1] [2]
    下層の画像処理ライブラリでメモリ関連の欠陥が踏まれ、サーバー側で任意のコードが実行されうる。 勧告の影響欄は「リモートコード実行に至りうる（can lead to possible remote code execution）」とする
    根拠: GHSA-2464-fhr4-w9xw の Impact 記述、CVSS v4.0 9.5（VC:H/VI:H/VA:H）
  4. 4. 影響（暗号化・破壊・改ざん）disclosed[2]
    CVSS v4.0 のベクタは、脆弱なシステム（VC:H/VI:H/VA:H）と後続システム（SC:H/SI:H/SA:H）の いずれについても機密性・完全性・可用性すべてに High の影響を示している。 実際の被害事例は公表されていない
    根拠: GHSA-2464-fhr4-w9xw の CVSS ベクタ

3件すべてが「上流依存の脆弱性」として公表され、2件は React の勧告と対になっている原因・手口出典 [1] [2] [3] [6] [7] [10]

公開された情報から、起きていることは次のとおりである。

  • Next.js は2026年10月14日に定例外のセキュリティ更新 v16.4.1（Active LTS）とv15.5.28（Maintenance LTS）を公開した
  • リリース記事の題は 「Next.js Security Update for Upstream Vulnerabilities」（上流脆弱性に対する Next.js のセキュリティ更新／原文英語）であり、3件すべてを上流依存の問題として位置づけている
  • CVE-2026-96889 / GHSA-2464-fhr4-w9xw（Critical・CVSS v4.0 9.5）——「画像最適化に使われる上流ライブラリのメモリ関連の脆弱性が、glibc ベースの Linux 上で Next.js が動作している場合にリモートコード実行に至りうる」（原文英語）
  • GHSA-673q-mjm6-r5xr（Critical・同 9.5・CVE 番号なし）—— App Router ＋ Cache Components を使うアプリケーションで、use cache 関数が複数の型付き配列を返す場合に未認証のリモートコード実行に至りうる。上流勧告は React の GHSA-xqc2-xf4c-x3h3
  • GHSA-p3m5-59mp-jv5r（High・同 8.2・CVE 番号なし）—— App Router で Server Action を1つ以上使うアプリケーションに細工した要求を送るとCPU を過剰に消費し、同一プロセス内の後続要求の処理が止まる。上流勧告は React の GHSA-h3gv-c5rc-p453

上流側の対応も同じ10月14日に出ている。React の2件の勧告はreact-server-dom-webpack / react-server-dom-parcel / react-server-dom-turbopack を対象とし、19.0.0〜19.0.8・19.1.0〜19.1.9・19.2.0〜19.2.8・19.3.0 が影響を受け、19.0.9 / 19.1.10 / 19.2.9 / 19.3.1 で修正されたとしている。React 側の RCE 勧告は成立条件を「応答が複数の型付き配列と攻撃者が制御する値を運ぶ、きわめて稀な場合」（原文英語）と説明しており、Next.js 側の記述よりも踏み込んでいる。

SVG 経路については、Next.js の勧告はライブラリ名を書いていない。名指ししているのは報道で、sharp がその下層で SVG を処理する librsvg にメモリ安全性の問題があったと説明している。ただし勧告が回避策として sharp 0.35.5 以降を指示していることから、sharp が経路に入っていること自体は一次資料から読み取れる。

影響する版の下限は 10.0.0（2020年の世代）まで遡る——ただし成立条件は限定的である被害規模・影響範囲出典 [1] [2] [3] [9]

SVG 経路の下限が 10.0.0 である点は、長期運用のサイトにとって重い。一方で、成立するには条件が重なる必要がある。

  • glibc ベースの Linux 上で動作していること（勧告の明示）
  • 画像最適化 API が SVG を処理する構成になっていること。Next.js の公式ドキュメントは「既定では Next.js は SVG 画像を最適化しない」と述べ、理由として「SVG はベクタ形式で無劣化に拡大縮小できる」「SVG は HTML/CSS と同等の機能を多く持ち、適切な CSP ヘッダが無いと脆弱性につながりうる」の2点を挙げている。有効化には dangerouslyAllowSVG: true の設定が必要で、ドキュメントはSVG が src に来る場合は unoptimized prop の使用を推奨している（.svg で終わる場合は自動適用）

つまり「対象の版である」ことと「悪用できる状態である」ことは別であり、自社の構成では dangerouslyAllowSVG の有無と実行基盤の libc が判定の分かれ目になる（本記録の整理）。

use cache の RCE は 16.x 限定だが、回避策が無い。勧告は「影響を受けるアプリケーションに既知の回避策は無い。同種の関数が無いアプリケーションでも直ちに更新すべきだ」（原文英語）と書いている。DoS は Pages Router のみ、または Server Actions を使っていないアプリケーションには影響しない。

勧告が「sharp の解決結果を確かめよ」と書いている——Next.js を上げただけで終わらせない対策・注意喚起出典 [1] [2] [3] [8]

SVG 経路の回避策として、勧告は次の2つを並べている（原文英語）。

  1. Next.js が使う sharp の版が 0.35.5 以降であることを確かめる。 新規インストールでは既に修正版が入る
  2. Next.js を修正版へ更新する。 そうすればパッケージマネージャが修正済みの sharp を自動的に供給する

ここからは本記録の評価である。この2つが並記されていること自体が運用上の情報である。 Next.js の更新で sharp が自動的に上がるのであれば、1番目は不要なはずである。それでも「確かめる」が先に書かれているのは、依存の解決結果が環境によって変わりうることを前提にしているからだと読める。npm / pnpm / yarn のロックファイルが既に古い sharp を固定している場合、next のバージョンだけを上げても sharp の解決が動かないことがある。sharp 0.35.5 のリリース自体は Next.js の修正より早く、9月27日付で公開されている。

したがって確認すべきは「next のバージョン」ではなく「実際に解決された sharp のバージョン」である。これはフレームワーク単体の版数管理では捉えられない層にあたる。

一方、use cache の RCE と Server Actions の DoS には回避策が存在しない。この2件については「更新する」以外の選択肢が公表されていない。

「上流調整のため9月から延期」を2度にわたって明示したことは、評価に値する——ただし14日の空白は残った評価・解釈出典 [1] [2] [3] [4] [5]

この更新の公表の仕方には、他のベンダーではあまり見ない要素が2つある。

第一に、延期の事実と理由を自ら2度書いている。 9月30日のリリース記事は冒頭で「重大1件と高1件の修正が上流依存の遅れにより延期された」と述べ、10月8日の予告は「うち2件は上流との調整のため9月のセキュリティリリースから延期されたものである」（原文英語）と繰り返している。修正が揃っていないことを伏せずに書いた形である。

第二に、公開の6日前に予告を出している。 予告は「10月14日に公開予定」「上流依存の3件（重大2件・高1件）」「公開と同時に影響・影響版・更新手順を含む完全な勧告を出す」「利用可能になり次第、修正版へ更新せよ」とだけ述べ、技術的な詳細には触れていない。

ここからは本記録の評価である。予告は利用者に「作業枠を押さえる時間」を与える一方、攻撃者には「何かが来る」という合図にもなる。本件では、重大2件が未修正のまま 9月30日から10月14日の14日間公開され続け、そのうち最後の6日間は「重大な未修正の脆弱性がある」という事実が公知になっていた。それでも本記録はこの運用を妥当と見る。理由は、延期の事実を伏せた場合、利用者は「9月のリリースを当てたから最新である」と誤認し、10月14日の更新を定例外の緊急対応として扱う根拠を持てないからである。

ただし、この判断が妥当だったかを事後に検証する材料は無い。悪用の観測について、勧告もリリース記事も一切触れていない〈未確定1〉。「悪用は確認されていない」という記述すら無いため、14日の空白に何が起きたかは本記録からは言えない。

  • フレームワークの版数管理と、その下にある依存の解決結果の管理は別の作業である
    勧告は回避策として「Next.js が使う sharp の版が 0.35.5 以降であることを確かめる」と 「Next.js を更新すればパッケージマネージャが修正版の sharp を供給する」を並記している。 両方が書かれているのは、依存の解決が環境によって動かないことがあるためと読める
    取るべき行動 脆弱性対応の完了判定を「フレームワークのバージョンを上げた」で終わらせず、 「ロックファイル上で該当依存が修正版に解決されていること」を確認項目として手順書に加える。 確認結果の記録（更新後の依存ツリーの出力）を対応記録に残す運用に改める
  • 「延期を公表するベンダー」は、むしろ運用しやすい相手だと評価しておく
    Next.js は9月30日に「重大1件・高1件の修正を上流の遅れにより延期した」と書き、 10月8日に定例外更新を予告した。延期が伏せられていれば、利用者は 「9月の更新を当てたから最新」と誤認し、10月の更新を緊急扱いする根拠を持てない
    取るべき行動 主要な OSS 依存について、セキュリティリリースの告知経路（ブログ・勧告・RSS）を監視対象に登録し、 「次回に延期された」「定例外を予告した」という情報が運用チームへ届く経路を作る。 ベンダー評価の観点に「延期・未修正を明示するか」を加える
  • CVE 番号が付かない重大脆弱性があることを、脆弱性管理の前提に入れる
    3件のうち CVE 番号があるのは CVE-2026-96889 のみで、CVSS 9.5 の `use cache` の RCE と 8.2 の DoS には CVE が付与されていない。 上流 React の2件も CVE 番号が無い
    取るべき行動 脆弱性管理の取り込み元を CVE / NVD だけに依存させず、 GitHub Security Advisory（GHSA）と主要依存の勧告を一次の取り込み元として追加する。 SLA の判定を CVE の有無ではなく深刻度と公開面で行うよう規程を直す
  • 「対象の版である」ことと「悪用できる状態である」ことを分けて判定する体制にしておく
    CVE-2026-96889 の対象は Next.js 10.0.0 以降という広い範囲だが、 成立には glibc ベースの Linux と、既定では無効な SVG 最適化の有効化が必要である。 範囲だけで判断すると、該当しない系まで緊急停止の対象になりうる
    取るべき行動 緊急パッチの優先順位付けの様式に「版の該当」と「構成・実行環境の該当」の2欄を設け、 後者を答えられる構成情報（実行基盤の libc、フレームワークの設定値）を 平時から資産管理に持たせる
セキュリティ技術者への示唆
  • 更新後に、実際に解決された sharp の版を見る
    勧告の回避策は sharp 0.35.5 以降を指す。`next` のバージョンを上げても、 ロックファイルが古い sharp を固定していれば解決が動かない可能性がある
    取るべき行動 更新後に `npm ls sharp`（pnpm / yarn の相当コマンド）で解決された版を確認し、 0.35.5 未満であればロックファイルを更新して再解決する。 CI に「主要な脆弱性対象依存の解決版を検査する」手順を1つ足す
  • 画像最適化 API で SVG を扱っているかどうかを、設定で確認する
    Next.js は既定では画像最適化 API で SVG を最適化せず、 有効化には `dangerouslyAllowSVG: true` が必要である。 公式ドキュメントは SVG が `src` に来る場合は `unoptimized` prop の使用を推奨している
    取るべき行動 `next.config.js` 内の `dangerouslyAllowSVG` を全プロジェクトで grep し、 有効になっている箇所について必要性を再評価する。 必要な場合は `contentSecurityPolicy` と `contentDispositionType: 'attachment'` を併設する
  • `use cache` と Server Actions の使用状況を、影響判定の前に洗い出しておく
    `use cache` の RCE は App Router ＋ Cache Components が前提、 DoS は Server Action が1つ以上あることが前提で、 Pages Router のみ・Server Actions 未使用のアプリケーションは DoS の影響を受けない
    取るべき行動 リポジトリ横断で `'use cache'` ディレクティブと Server Action の定義（`'use server'`）を検索し、 App Router / Pages Router の採用状況と併せて一覧にしておく。 次回の勧告が来たときに影響判定を即座に出せる状態にする
  • 上流（React）側のパッケージ版も独立に確認する
    2件は React Server Components 関連パッケージ （react-server-dom-webpack / -parcel / -turbopack）の欠陥で、 修正版は 19.0.9 / 19.1.10 / 19.2.9 / 19.3.1 である。 Next.js の修正版を入れても、固定している React の版が古ければ残りうる
    取るべき行動 更新後に React 関連パッケージの解決版を確認し、該当系統の修正版以降になっているかを確かめる。 React の版を明示的に固定している場合は固定値を見直す
  • 画像処理を本体のプロセスと同じ実行文脈で動かさない
    本件はネイティブの画像処理ライブラリのメモリ欠陥であり、 実行されるのは Next.js のサーバープロセスの中である。 この種の欠陥は今後も上流で発生しうる
    取るべき行動 外部由来の画像の最適化を CDN または独立したワーカー（権限最小・外向き通信を制限）へ切り出す構成を検討する。 切り出せない場合は、アプリケーション実行ユーザーの権限と書き込み可能領域を最小化する
