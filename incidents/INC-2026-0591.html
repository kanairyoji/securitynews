AI コーディングエージェント OpenCode の任意利用のホスティング版「OpenCode Console」で、 2026年10月16日の夜に**廃止作業中だった旧システム**へ不正アクセスがあり、 利用者がワークスペースに保存していた **OpenAI・Anthropic・Google の API キー**が 露出したおそれがあると同社が10月17日に公表した——影響は「Console 利用者の1.4%」とされ、 対象者にはメールで通知済み、メールが届かなかった利用者は対象外と説明された。 同社は本件を「大規模な蒸留（distillation）攻撃に関連するもの」と位置づけ、 OpenAI・Anthropic・Google と対応を進めているとした一方、 **「インシデントは進行中であり、これ以上の詳細は共有できない」として技術的な説明をしていない。** 一部の利用者は盗まれた鍵で従量課金の請求が発生したと申告しているが、 **同社はこれを確認していない。** なお**本記録の作成者は opencode.ai 上に本件の告知ページを発見できず、 公式の X 投稿も取得できなかった**（引用は複数の二次情報が同一文面で伝えているもの）

OpenCode は AI コーディングエージェントで、OpenCode Console はその任意利用のホスティング版です。The Hacker News の報道によれば、Console ではワークスペースごとに自前のOpenAI・Anthropic・Google の API キーを保存し、Console がそのキーを使ってプロバイダを呼び出すことで、チームのメンバーが個別にキーを持たずにモデルを使えるようになっています。

2026年10月17日、同社は10月16日の夜に第三者が廃止作業中だった旧システムへ不正アクセスし、利用者がワークスペースに保存していたプロバイダの API キーが露出したおそれがあると公表しました。影響は「OpenCode Console 利用者の1.4%」とされ、対象者には同日朝にメールで通知済み、メールが届かなかった利用者は対象外と説明されています。

同社は本件を「大規模な蒸留（distillation）攻撃に関連するもの」と位置づけ、OpenAI・Anthropic・Google の3社と対応を進めているとした一方、「インシデントは進行中であり、現時点でこれ以上の詳細は共有できない」として侵入経路・侵害期間・キーの保存形式を説明していません（いずれも原文英語）。

本件の要点は、漏えいした情報がデータではなく「計算資源へのアクセス権」であることです。従量課金のモデル API キーが盗まれると、二次被害は後日の名簿悪用ではなくその日の請求書として現れます。実際、複数の利用者が数百〜1,700ドル規模の不正請求を申告していますが、同社はこれを確認していません。

なお、本記録には裏取りの限界があります。本記録の作成者は opencode.ai 上に本件の告知ページを発見できず、公式の X 投稿も取得できませんでした。 引用として示す文面は、複数の二次情報が同一の文言で伝えているものです。事実と評価は分けて記述します。

この仕組みが、そのまま被害の形を決めている。利用者の鍵を1か所に集めて代理で呼び出すサービスは、集めた鍵の束が1回の侵害で全部出る構造を持つ。

漏れたのはデータではなく「計算資源へのアクセス権」で、二次被害が請求書として即日現れる評価・解釈出典 [1] [2] [3]

通常の個人情報漏えいでは、二次被害はフィッシングやなりすましという形で、数週間から数か月かけて現れる。本件は違う（以下は本記録の評価）。

従量課金のモデル API キーは、データではなく計算資源へのアクセス権である。盗んだ側は鍵を使って即座にモデルを呼び出せ、その呼び出しは鍵の持ち主の請求として記録される。 つまり二次被害は、後日の名簿悪用ではなくその月の請求書として出る。

実際、報じられている自己申告は次のとおりである（いずれも同社は確認していない）。

ここから、実務上の違いが3つ出てくる。

①検知の手がかりが請求額とレート制限にある。通常の漏えいでは「漏れたかどうか」を利用者側で確かめる術がないが、API キーの場合はプロバイダ側の利用履歴に異常が残る。逆に言えば、利用履歴とコスト上限を見ていない利用者は、請求が来るまで気づけない。

②「ローテーション」の意味が2つあり、片方は効かない。 Console の画面で鍵を差し替えるのは、仲介役が持っているコピーを入れ替えるだけである。盗まれた鍵はプロバイダ側で失効させない限り生き続ける。同社の案内が「各プロバイダのダッシュボードから失効させ、置き換えてください」とプロバイダ側での操作を指定しているのは、この区別を踏まえたものである。

③被害の上限を決めるのは、漏えい側ではなく鍵の持ち主である。プロバイダ側で支出上限（ハードリミット）を設定していれば、盗まれた鍵で積み上がる額はそこで止まる。預け先の安全性を検証する手段を持たない利用者にとって、上限設定は数少ない自衛手段である。

「1.4%」は母数が公表されておらず、規模を伝えていない被害規模・影響範囲出典 [1] [2] [3]

公表された影響範囲は「OpenCode Console 利用者の1.4%」である。割合だけで、実数は示されていない。

母数が分からないと、この数字は規模を伝えない。Console 利用者が1万人なら140アカウント、10万人なら1,400アカウント、1,000人なら14アカウントである。3桁の幅がある。露出した鍵の本数（1ワークスペースに複数プロバイダの鍵を置ける）も、プロバイダ別の内訳も示されていない。

「1.4%」という表現は小さく見える（本記録の評価）。分母を伴わない割合は、公表する側にとっては正確で、読む側にとっては規模の判断材料にならない。本記録が figures に持てたのも割合だけで、実数は算出できなかった。

一方で、影響範囲の切り分け方そのものは明快である。同社は対象者全員にメールで通知したとし、「メールが届かなかった方は対象ではない」と述べた。これは利用者が自分の状態を判断できる形であり、「調査中のため対象者を特定できていません」という段階より一歩進んでいる——ただし通知日が10月17日か10月18日朝かは情報源によって揺れている。

なお、この割合はConsole 利用者に対するものであり、OpenCode 全体の利用者に対するものではない。Console は任意利用のホスティング版なので、母数はさらに小さい。

ここには2つの事実が同時に入っている。

①そのシステムは廃止が決まっていた。つまり同社は、それが不要であると判断し、作業に入っていた。リスクを認識していなかったのではなく、手を付けている最中だった。

②それでも本番の鍵に到達できる状態だった。廃止作業中のシステムが侵害されたことで、利用者が保存していたプロバイダ API キーが露出したおそれがある、というのが公表の内容である。廃止予定であることと、本番データから切り離されていることは別である（本記録の評価）。

移行・廃止の作業には、たいてい「まだ使われているかもしれない」という不確かさがある。そのため、まず接続を切る（本番データ・認証基盤・ネットワークから切り離す）のではなく、まず使われないようにする（新規の導線を消す）順で進みやすい。前者をせずに後者だけ済んだ状態が長く続くと、「もう使っていないから監視も手当もしていないが、データには手が届く」システムが残る。

何がそのシステムであり、どう侵入されたのかは公表されていない。同社は「インシデントは進行中であり、現時点でこれ以上の詳細は共有できない」としている。理由が説明された非開示であり、沈黙ではない——本記録は未確定事項の理由を withheld とした。

「蒸留攻撃」という位置づけは動機の主張であり、根拠は示されていない帰属出典 [2] [3]

公式投稿は、本件を次のように位置づけている（原文英語）。

蒸留（distillation）とは、あるモデルの応答を使って別のモデルを学習させる手法である。この語を使うことで、同社は「鍵が盗まれた目的」まで述べている——盗んだ鍵で商用モデルを大量に呼び出し、その応答を学習データとして集める、という動機である。

位置づけとしては筋が通っている。盗まれた鍵が数百〜数千ドル分の呼び出しに使われたという利用者の申告は、鍵の転売や単発の悪用より、継続的な大量呼び出しと整合する。そして計算資源へのアクセス権という本件の漏えい対象の性質にも合う。

ただし、そう判断した根拠は示されていない（本記録の整理）。呼び出しのパターン、プロバイダから得た情報、攻撃者の属性——いずれも公表されていない。帰属も示されていない。本記録はこれを「同社による動機の主張」として扱い、確認された事実とはしない。

なお、この語の選択には副作用もある。「蒸留攻撃」と呼ぶと、問題がモデル業界の競争の話に見えてしまうが、利用者から見れば起きたことは単純で、預けた鍵が漏れ、自分の請求で誰かがモデルを使ったということである。

AI エージェントのホスティング版に鍵を預ける構造が、そのまま被害の形になっている評価・解釈出典 [1] [2] [3]

本件を日本の読者の実務に引き直すと、問題は OpenCode 固有ではない（以下は本記録の評価）。

AI コーディングエージェントやエージェント基盤をチームで使うとき、各メンバーが自分でモデルプロバイダの鍵を持つ形は管理しにくい。そこで多くのサービスが「組織の鍵を1か所に預け、サービスが代理で呼び出す」形を提供する。利便性の源泉は、鍵の集約である。

この形には、避けられない性質が3つある。

①鍵は復元可能な形で保持されている。代理で呼び出すには、サービスが鍵の平文を得られなければならない。ハッシュ化して持つことはできない。暗号化していても、呼び出しの瞬間には復号される。「ハッシュ化しているので安全です」という説明が成り立たない種類の秘密である。

②預けた側の対抗手段は失効しかない。パスワードと違って、利用者は預け先の保存方式を検証できない。漏れた後にできるのは、プロバイダ側で鍵を失効させることだけである。

③被害は従量課金の請求として即日出る。だからこそ、プロバイダ側の支出上限が実質的な被害上限になる。

これを踏まえると、自組織で AI エージェント基盤を導入するときの確認事項は、「どのモデルが使えるか」ではなく「鍵をどこに置くか」になる。鍵を預ける形を選ぶなら、①預け先専用の鍵を発行して用途を分離する②プロバイダ側で支出上限とレート制限を設定する③利用履歴を自社でも監視する④失効と再発行の手順を所有者が自分で実行できる状態にしておくの4点が、預け先の安全性に依存しない自衛になる。

なお、OpenCode のような OSS 由来のツールには、手元で鍵を持つ CLI 版と、鍵を預けるホスティング版が併存することが多い。本件の対象は後者である。「同じツールを使っている」ことと「同じリスクを負っている」ことは別であり、自組織がどちらの形で使っているかを把握しているかが、最初の分かれ目になる。
