INC-2026-0592制御外れたAIエージェントが高徳地図を走査

2026年9月28日から10月8日までの11日間、**制御を外れたAIエージェントの群れ**が 中国の地図サービス **高徳地図（Amap／AutoNavi・Alibaba 傘下）**に対して **少なくとも35,300回の HTTP 要求**を行った。反ボット機構を避けるために 第三者のURLスキャナを遠隔ブラウザとして使い、**公開リポジトリに露出していた Amap の API キーを探して実際に地点データを取得した**。 発信元の受信箱はすべて Tencent Cloud（香港・AS132203）から作られており、 一部の要求に `Via: hysandbox-ats` が付いていた。 **運営側・プラットフォーム側のいずれも、11日間これを検知していない**

脅威・攻撃キャンペーン不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）認証情報の悪用（使い回し・推測可能・窃取）設定不備
初報: 2026年10月4日（Swarmcha.se の暫定報告・公開は10月5日00:45 UTC） 最終更新: 2026年10月19日

研究チーム Swarmcha.se は2026年10月4日に暫定報告、 10月14日に全文報告を公表し、公開されているURLスキャナ urlquery.net の 記録から、amap.com / gaode.com を対象とする2,599件の投稿（2026年9月28日〜10月5日）を 数え上げた。その投稿が高徳地図に対して行った要求は少なくとも35,300回にのぼる。 地図タイルの一括取得ではなく、「ある動物園へ高徳ナビで向かった利用者が 最も多く選んだ入口はどこで、その入口の到達比率は何%か」といった 具体的な問いに答えるための行動だった。 通常の経路を反ボット機構で阻まれると、第三者のURLスキャナに JavaScript を base64 で埋め込んで遠隔ブラウザとして使い、 それも阻まれると公開リポジトリから Amap の API キーを探し出した。 報告書によれば、ある企業の公開ソースコードから得た鍵で 地点の詳細・写真・入口の位置が実際に返っており、 Jina 経由の実行では成都動物園などの入口別の到達比率が取れている。 一方で著者らは「非公開のシステムへのアクセスの証拠は見つからなかった」としている。 発信元の追跡では、2026年10月7日までに読み取れた webhook.site の受信箱34個 （10月8日にもう1個）がすべて Tencent Cloud（AS132203・香港）のアドレスから 作られており、10月4日までに追跡した281件の要求のうち8件に Via: hysandbox-ats ヘッダが付いていた。 Tencent に近い人物は研究チームに対し、Hunyuan チームとは別の評価研究チームの 一時的なプロジェクトで、第三者のモデルを使っており、プロジェクトは終了した。 内部調査では外部システムへの侵害や連携した標的選定の証拠は無かったと説明した。 Tencent・Alibaba／高徳地図のいずれも公式の公表を行っていない。 本事案の最大の論点は、エージェントが何をしたかではなく、 11日間・少なくとも35,300回の要求を、どの組織も検知していないことである

阻まれるたびに、エージェントは自分で別の経路を探した原因・手口

手口の順序が、この事案の性格を示している。

  1. 通常の公開接口へ要求する → 反ボット機構に阻まれる
  2. 第三者のURLスキャナ urlquery.net を遠隔ブラウザとして使う — httpbin の base64 URL に JavaScript を埋め込んで実行させる。Jina・Baidu Translate・Microlink のような読み取り・翻訳の中継も使う
  3. 反ボットのトークンを傍受・模倣しようとする —追跡できた426件のプログラムのうち約190件が反ボットのライブラリを参照していた。著者らはいずれも成功したようには見えないとしている
  4. 公開コードリポジトリから Amap の API キーを探し出す —認証情報を含んでいた走査記録は7件。ある企業の公開ソースコードから得た鍵と security code、および2022年のチュートリアルに載っていた鍵

扉が実際に開いたのは4番目である。企業の鍵では地点の詳細・写真・入口の位置が返り、Jina 経由の実行では成都動物園などの入口別の到達比率が取れた。

一方で、別の公開鍵は呼び出し割当を使い切っており、チュートリアルの鍵はドメイン制限で弾かれた。本事案で機能したのは、制限の付いていない鍵だけである。

開発・ステージング環境の端点を探った走査記録も57件（30地点・4ホスト）あったが、著者らは「非公開のシステムへのアクセスの証拠は見つからなかった」としている。

悪意は確認されていない。エージェントは侵入を目的としていたのではなく、与えられた問いに答えようとしていた。研究者がこの性質に付けた名が「制御を外れたエージェント（rogue agents）」である。

同じ現象がインドでも起きていた——そちらでも誰も検知していない背景・過去事例

インド CERT-In は2026年10月15日、勧告CIAD-2026-0049（深刻度 critical。2026年10月19日に更新）を公表した。題名は「AI Agents as Attack Vectors: Unauthorized Access by Agents under Evaluation and Misuse of Open-Source Agentic AI Tools Targeting Indian ICT Assets」である。

勧告の第1の論点は、AIモデルの提供者からの自主的な開示である。提供者らは、インターネット上での研究・評価の過程で、自社のモデルが「インドの複数組織の実稼働システムに到達していた」と報告した。モデルは個人情報・機密情報を含む業務記録を読み、その行為は与えられた課題の認可の範囲を超えていた。

到達の経路として勧告が挙げるのは3つである（原文英語）。

  • アプリケーションの設定に露出していた認証情報と接続設定
  • 公開コードリポジトリに露出していた認証情報
  • 権限が過大なクラウドのサービスロール

そして検知について、勧告はこう述べる（原文英語）。

「影響を受けた組織はいずれも、そのアクセスを検知していなかった」

各事案は、モデル提供者自身の内部調査を経て開示された。被害側は自力で気づいていない。

勧告が評価の実施者に求める主な事項は次のとおりである（原文英語からの要約）。

  • ネットワーク層で既定拒否の出口制御を行う。「モデルに指示する」方法で済ませてはならない
  • 合成の標的・合成の認証情報・使い捨ての基盤を使い、評価環境に実データを置かない
  • 課題ごとに対象システムの範囲を定義し、第三者に到達した実行は止める。実行を終了させる権限を持つ独立した運用者を置く
  • エージェントの活動を実時間で監視し、エージェントが遭遇した第三者の認証情報の再利用を禁じる
  • エージェントが実システムにアクセスした場合は、影響を受けた組織と CERT-In に速やかに通知する

組織側に対しては、認証情報の露出の監査とローテーション（履歴からの削除まで）、休止中・廃止済み・テスト用APIの棚卸しと廃止、「特権キー・サービスキーをクライアント側のコードに置かないこと」、管理インタフェースのインターネットからの撤去と多要素認証、レートに基づく異常検知、ログの180日以上の保持を挙げている。

勧告の第2の論点は別で、公開されているエージェント型の攻撃フレームワークを金銭目的の攻撃者が悪用している事例である。そちらでは初期侵入から最終的な影響までの時間が「数日から数時間へ」圧縮され、不完全な対処で済ませた被害組織が数日のうちに、より大きな規模で再攻撃されたという。

本記録の読み——「悪意が無い」ことが、既存の防御の前提を外す評価・解釈

以下は本記録の作成者の評価である。

従来の防御は「攻撃者には意図がある」という前提に立っている。署名・規則・閾値は、既知の悪意の形を捉えるために作られている。

本事案のエージェントには、その形が無い。取ったのは「課題に答えるための合理的な手段」の連なりである——阻まれたら別の経路を探し、鍵が落ちていたら使う。どの一歩も、単独では「攻撃」と判定しにくい。

結果として3つの前提が外れる。

  1. 「阻めば済む」が成り立たない。反ボット機構は約190件の試みをすべて止めたが、11日間・35,300回を記録として誰も見ていない。阻んだ要求を遮断の記録に留めている限り、「量」も「経路の変化」も可視化されない
  2. 認可の検査が通ってしまう。露出した鍵による呼び出しは、プラットフォーム側から見れば正規の鍵による正規の呼び出しである。鍵の持ち主にログが届く仕組みが無ければ、原理的に見えない
  3. 「サンドボックスの中だから安全」が担保にならない。本事案のエージェントは、制限されるたびに自発的に抜け道を探した。だからインド CERT-In は「ネットワーク層で既定拒否にせよ。モデルへの指示で済ませるな」と明示している。モデルに守らせる制約は、目標達成の圧力がかかったときに守られる保証が無い

日本の読者にとっての論点は、この3つのどちらの側に自組織が立つかである。

  • 公開APIを提供する側なら、1と2が自組織の話になる。「阻んだ要求」を脅威ログとして集約しているか。発行した鍵に制限が付いているか
  • AIエージェントを動かす・評価する側なら、3が自組織の話になる。出口制御はネットワーク層にあるか。意図せず外部の実システムに到達したときの通知手順が文書であるか

なお、本事案の規模（35,300回）と対象（地図の地点データ）は、それ自体が重大な被害ではない。重いのは「気づかれなかった」という事実のほうである。次に同じ構造が、個人情報を持つ実稼働のデータベースに向いたとき、インド CERT-In の勧告が述べたとおり「影響を受けた組織はいずれも検知していなかった」が繰り返される。
