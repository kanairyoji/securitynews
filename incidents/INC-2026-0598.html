INC-2026-0598パスキー偽装でMicrosoft 365侵害

Microsoft が2026年9月9日に公表した「パスキーを口実にしたソーシャルエンジニアリング」のキャンペーン—— 攻撃者は IT ヘルプデスクを装って従業員の**個人用携帯**に電話や SMS を入れ、 「パスキー・MFA・SSO の設定を直ちに更新せよ」と急かして偽のサインイン画面へ誘導する。 **狙いはパスキーの登録ではなく、AiTM フィッシングとデバイスコードフィッシングによる トークンの奪取**である。一部の侵入では、すでに乗っ取った従業員アカウントから **Microsoft Teams で同じ案内を社内に送る**ことで信用させていた。 アクセスを得た攻撃者は自分が管理する電話番号・認証アプリ・ソフトウェアトークンを MFA 方法として追加して足場を固め、Microsoft Graph でテナントを網羅的に調べたうえで、 SharePoint Online・OneDrive for Business・一部では Exchange Online から **毎時1,000件未満に抑えた速度で数時間から数日かけて**データを持ち出した。 関連する活動は2026年5月から確認されており、Microsoft は初期アクセスを Storm-3121・Storm-3032 をはじめ同じ恐喝エコシステムの複数のアクターに帰属させている。 **2026年10月26日、Arctic Wolf Labs が同じ入口を別の角度から測った**—— **Microsoft Teams の外部チャット作成機能が悪用された400件超のインシデント**を並べ、 「**繰り返されるソーシャルエンジニアリングのパターン**」として報告した。 共通していたのは**使い捨てテナント**（既定の *.onmicrosoft.com が全体の30〜40%、 有料ドメインは .top が約50%・.com が約40%）と、 **「(Internal)」を付けた IT サポート風の表示名**（絵文字入りが100件以上）である。 流れは**メールボムで受信箱を埋める → 外部テナントから「IT サポート」が1対1チャットを開く → 音声通話で Quick Assist などのリモート支援を入れさせる → ペイロード実行**で、 **接触から15分以内に実行まで至った事例**がある。 **Arctic Wolf は「既知の Teams の脆弱性を突いたものではなく、 既定で有効な正規の共同作業機能を悪用している」と明記している。** **この400件超が Microsoft のパスキー口実キャンペーンと同一のものかは、 どちらの報告も述べていない**（本記録は同一と断定しない）

初報: 2026年9月9日（米国時間） 最終更新: 2026年10月26日

Microsoft は2026年9月9日（米国時間）、「Passkey-themed social engineering leads to identity and cloud compromise」（パスキーを口実にしたソーシャルエンジニアリングが ID とクラウドの侵害につながる・原文英語）を公式ブログで公表しました。関連する活動は2026年5月から確認されています。

攻撃は電話またはメッセージで始まります。攻撃者は企業の IT ヘルプデスク担当者を名乗り、従業員の個人用携帯電話に連絡し、パスキー・多要素認証（MFA）・シングルサインオン（SSO）の設定を直ちに更新する必要があると説明します。対応しなければ業務に支障が出ると伝えて手続きを急がせ、Microsoft の正規のサインイン画面によく似た Web サイトへ誘導します。個人用携帯に SMS でリンクを送るケースもありました。

攻撃者は事前に標的企業と従業員を調べており、偽サイトの URL には標的企業の名称を組み込む——パスキー・SSO・鍵の同期・アカウント設定・本人確認に関連する語と企業名を組み合わせたドメインを登録し、企業名をサブドメインに置いて「その企業専用の認証ページ」に見せかけます。さらに、すでに乗っ取った従業員のアカウントから Microsoft Teams を通じて同じ案内を社内に送るケースも確認されています。社内の人物から届いた連絡に見せることで、受信者に信用させる狙いです。

ここで読み違えてはならないのは、攻撃者の目的がパスキーの登録ではないことです。Microsoft は、パスキーを題材にした口実はAiTM（Adversary-in-the-Middle）フィッシングサイトへのサインインか、デバイスコード認証の流れへ誘導するための手段だと述べています。前者は利用者と正規の認証サービスの間に攻撃者が入り込み、認証情報とセッショントークンを取得します。後者は利用者に正規の Microsoft 認証ページでコードを入力させ、攻撃者が操作するクライアントにアクセス権を与えさせます。いずれもパスキーの暗号技術を破った攻撃ではありません。

アクセスを得た攻撃者は、自分が管理する電話番号・認証アプリ・ソフトウェアのワンタイムパスワードトークンを MFA 方法として追加し、以後の認証要求を自力で通過できる状態を作ります。続いて Microsoft Graph を使って利用者・グループ・権限・利用可能なアプリケーションを調べ、SharePoint Online・OneDrive for Business、一部の侵入ではExchange Online のメールデータへ到達します。収集の速度は毎時1,000件未満のファイルまたはメールに抑えられ、数時間から数日かけて通常の業務に紛れるペースで実行されていました。

Microsoft は初期アクセスの活動を Storm-3121（ShinyHunters・Falcon による恐喝につながる）とStorm-3032（BlackFile から分かれた集団で Helix の恐喝ブランドで活動）に帰属させ、同じ初期アクセス手法を他の脅威アクターも使っていると述べています。

攻撃者は標的企業と従業員を事前に調べ、IT ヘルプデスクを装って **従業員の個人用携帯電話**へ電話または SMS を入れる。 「パスキー・MFA・SSO の設定を直ちに更新する必要がある」「対応しなければ業務に支障が出る」と 急がせ、企業名を組み込んだドメインの偽サインイン画面へ誘導する。 一部では、すでに乗っ取った従業員アカウントから **Microsoft Teams** で同じ案内を送る。 **アクセス権の奪取は主に2通り**——①AiTM フィッシングで認証情報とセッショントークンを取る ②デバイスコードフィッシングで、正規の Microsoft 認証ページ上で利用者にコードを入力させ、 攻撃者のクライアントにトークンを発行させる。 以前に登録された認証アプリの OTP を使って MFA を通過する例もある。 侵入後は自分が管理する電話番号・認証アプリ・ソフトウェアトークンを MFA 方法として追加し、 Microsoft Graph でテナントを網羅的に調べ、 SharePoint Online・OneDrive for Business・一部では Exchange Online（REST API 経由）から **毎時1,000件未満**に抑えた速度でデータを収集する。 **パスキーの暗号技術そのものは破られていない。**

  1. 1. 偵察disclosed[1] [2]
    攻撃者が標的企業と従業員について事前に調査し、 パスキー・SSO・鍵の同期・アカウント設定・本人確認に関連する語と**企業名**を 組み合わせたフィッシングドメインを登録する。 **企業名はサブドメインに置かれ、「その企業専用の認証ページ」に見せかける**
    根拠: Microsoft のブログ（企業名と各語を組み合わせたフィッシングドメインの登録、 企業名をサブドメインに置く手法の記述）および @IT の記事 （「偽サイトの URL には標的企業の名称を組み込み、 あたかもその企業専用の認証ページであるかのように見せ掛けていた」）
  2. 2. 初期侵入disclosed[1] [2]
    IT ヘルプデスク担当者を名乗る人物が**従業員の個人用携帯電話**へ電話またはメッセージを入れ、 「パスキー・MFA・SSO の設定を直ちに更新する必要がある」「対応しなければ業務に支障が出る」と 伝えて手続きを急がせる。SMS でリンクを送るケースもある。 **一部では、すでに乗っ取った従業員アカウントから Microsoft Teams で 同じ案内を送り、社内の人物からの連絡に見せていた**
    根拠: Microsoft のブログおよび @IT の記事 （「Microsoftが確認した一部のケースでは、既に乗っ取った従業員のアカウントを利用し、 『Microsoft Teams』を通じて同様の案内を送っていた」）
  3. 3. 認証情報アクセスdisclosed[1] [2]
    **2通りの方法でアクセス権が奪われる。** ①**AiTM フィッシング**: 攻撃者が用意した偽サイトが利用者と正規の認証サービスの間に入り、 認証情報とサインイン後のセッショントークンを取得する。 フィッシング耐性のない MFA が突破された例がある。 ②**デバイスコードフィッシング**: 利用者に**正規の Microsoft 認証ページ**でコードを入力させ、 攻撃者が操作するクライアントにトークンを発行させる。 さらに、以前に登録された認証アプリの OTP を使って MFA を通過する例もある
    根拠: Microsoft のブログ（AiTM・デバイスコード認証・既存認証アプリの OTP 再利用の記述）および @IT の記事（「主に2つの方法でアカウントへのアクセス権が奪われていた」）
  4. 4. 永続化disclosed[1] [2]
    アクセスに成功した攻撃者が、**被害者のアカウントに自分が管理する認証方法を追加する**—— 新しい電話番号、認証アプリ、ワンタイムパスワード用のソフトウェアトークンである。 これにより、後から再び認証を試みる際にも自分が管理する手段で通過できる。 **パスワードとセッションが全面的にリセットされるまで有効に働く**。 Microsoft は「Update user」操作でソフトウェアトークンが追加された監査ログの例を示している
    根拠: Microsoft のブログ（認証方法の追加・監査ログの例・ 「パスワードやセッションが全面的にリセットされるまで有効に働く」という説明）および @IT の記事
  5. 5. 内部探索disclosed[1] [2]
    攻撃者が **Microsoft Graph** を使ってテナント内を網羅的に調べる—— テナント情報、ディレクトリの列挙、特権と MFA の情報、アプリと同意の状況、 SharePoint/OneDrive の探索、メールボックスの探索である。 **自動化には Node.js と Microsoft Graph で作られた仕組みが使われたとされ、 ページングの処理まで自動化されていた。** 自動化を示す **python-httpx** の User-Agent も観測されている
    根拠: Microsoft のブログ（偵察の段階分け・Node.js による自動化・python-httpx の User-Agent・ 「単一の API 呼び出しでは不審に見えにくく、一連の行動の相関分析が必要」という指摘）および @IT の記事（「Microsoft Graph を利用して組織内のユーザーやグループ、 アクセス権限、利用可能なアプリケーションなどを調査していた」）
  6. 6. 収集disclosed[1] [2]
    **SharePoint Online・OneDrive for Business** に保存されたファイルへの大量アクセスと ダウンロードが行われ、一部の侵入事例では **Exchange Online** のメールデータ （REST API 経由）にも到達した。 大量の FileAccessed・FileDownloaded イベントが発生した。 **収集の速度は毎時1,000件未満のファイルまたはメールに抑えられ、 数時間から数日にわたって通常の業務利用に紛れるペースで実行された**
    根拠: Microsoft のブログ（SharePoint/OneDrive/Exchange Online・ FileAccessed/FileDownloaded イベント・毎時1,000件未満・数時間から数日の記述）および @IT の記事（「データの収集は短時間で一気に実行されるとは限らない」）
  7. 7. 持ち出しdisclosed[1]
    収集したファイルとメールのデータが攻撃者側へ持ち出された。 Microsoft は、初期アクセスの活動が **ShinyHunters・Falcon・Helix といった恐喝ブランドにつながる**としており、 持ち出したデータが恐喝の材料になる構造である。 **持ち出し先のインフラ・総量は公表されていない**
    根拠: Microsoft のブログ（Storm-3121 が ShinyHunters・Falcon の恐喝に、 Storm-3032 が Helix の恐喝ブランドにつながるという帰属）

「パスキーを更新してください」は依頼の形をしていて、狙いはトークンの奪取だった概観出典 [1] [2]

Microsoft が2026年9月9日に公表した内容によれば、起きていることは次のとおりである。

  • 関連する活動は2026年5月から確認されている
  • 攻撃は、企業の IT ヘルプデスク担当者を名乗る人物からの電話またはメッセージで始まる
  • 連絡先は従業員の個人用携帯電話。SMS でリンクを送るケースもある
  • 「パスキー・MFA・SSO の設定を直ちに更新する必要がある」「対応しなければ業務に支障が出る」と伝えて手続きを急がせる
  • 誘導先は Microsoft の正規のサインイン画面によく似た Web サイト。URL には標的企業の名称が組み込まれ、企業専用の認証ページに見せかけられている
  • 一部では、すでに乗っ取った従業員アカウントから Microsoft Teams を通じて同じ案内が送られていた
  • アクセス権の奪取は主に2通り——AiTM フィッシングとデバイスコードフィッシング
  • 侵入後、攻撃者は自分が管理する電話番号・認証アプリ・ソフトウェアトークンを MFA 方法として追加した
  • Microsoft Graph で利用者・グループ・権限・アプリを調べた
  • SharePoint Online・OneDrive for Business、一部では Exchange Online からデータを収集した
  • 収集の速度は毎時1,000件未満で、数時間から数日にわたった
  • Microsoft は初期アクセスを Storm-3121（ShinyHunters・Falcon の恐喝につながる）とStorm-3032（BlackFile から分かれ Helix ブランドで活動）に帰属させ、同じ手法を他のアクターも使っているとしている

口実の形が重要である。 「あなたのアカウントが危険です」という警告ではなく、「セキュリティを強化するので設定を更新してください」という依頼になっている。受け手にとっては、言われたとおりに動くことが安全な行動に見える。

パスキーは破られていない——破られたのは、認証設定を変更するときの手順だった原因・手口出典 [1] [2]

パスキーは、パスワードを入力する代わりに端末に保存された暗号鍵で本人を認証する仕組みで、偽のログインサイトにパスワードを入力させる従来のフィッシングに強いという特徴がある。

Microsoft が明示しているのは、攻撃者の目的がパスキーの登録ではないという点である。パスキーを題材にした口実は、次のどちらかへ誘導するための手段にすぎない。

① AiTM（Adversary-in-the-Middle）フィッシング利用者と正規の認証サービスの間に攻撃者が入り込み、認証情報とサインイン後のセッショントークンを取得する。フィッシング耐性のない MFA（SMS・音声・アプリの承認）は、この経路で突破された例がある。

② デバイスコードフィッシング利用者に正規の Microsoft 認証ページでコードを入力させ、攻撃者が操作するクライアントにアクセス権を与えさせる。Microsoft が調査した事例では、デバイスコードを使った認証の後、攻撃者が取得したトークンを再利用してアカウントにアクセスし、組織内の情報を調べる活動が確認された。

②が厄介なのは、認証そのものが正規のページで行われることである（本記録の評価）。「URL をよく見る」「証明書を確認する」という従来の教育は、この経路では効かない。利用者が見るのは本物の Microsoft のページであり、そこで入力するコードが誰のクライアントに権限を与えるのかは画面から判断できない。

いずれもパスキーの暗号技術を破った攻撃ではない。破られたのは、認証設定を変更するという作業が「電話一本で始まってよい」運用になっていた部分である。 @IT はこの点を「認証技術の強化とともに、認証設定を変更する際の運用や本人確認の手順を見直す必要性を示している」と整理している。

侵入後の足場は「攻撃者が管理する MFA 方法の追加」で、ここが最も検知しやすい一点である評価・解釈出典 [1] [2]

アクセスに成功した攻撃者は、その状態を維持するため、被害者のアカウントに自分が管理する認証方法を追加する。具体的には、新しい電話番号、認証アプリ、ワンタイムパスワード用のソフトウェアトークンの登録である。Microsoft は「Update user」操作でソフトウェアトークンが追加された監査ログの例を示し、この足場がパスワードとセッションが全面的にリセットされるまで有効に働くと説明している。

この一手は、防御側にとって最も捉えやすい信号である（本記録の評価）。理由は3つある。

  1. 必ずログに残る。 認証方法の追加は Entra ID の監査ログに記録される。攻撃者が隠せる操作ではない。
  2. 頻度が低い。 正常な業務でも起きるが、1人の利用者が認証方法を追加するのは年に数回である。ファイルアクセスやサインインとは桁が違う。
  3. 並びが不自然になる。 サインインの直後に認証方法が追加されるのは、新入社員の初回登録や端末の更新を除けば稀である。

Microsoft 自身も、不正アクセスの兆候を調べる際には「普段と異なるログインだけでなく、その直後に認証方法が追加されていないか、Microsoft Graph を通じた大量の情報取得やクラウド上のファイルのダウンロードが発生していないかを、関連付けて確認することが重要」としている。

「関連付けて」が要点である。 サインインの異常だけを見ると、出張・リモートワーク・VPN で誤検知が溢れる。認証方法の追加だけを見ると、入社手続きの期間に埋もれる。2つを時間窓で相関させたときに初めて、異常な並びとして浮かぶ。

データの持ち出しは毎時1,000件未満に抑えられ、件数ベースの検知を避けていた被害規模・影響範囲出典 [1] [2]

偵察には Microsoft Graph が使われた。テナント情報、ディレクトリの列挙、特権と MFA の情報、アプリと同意の状況、SharePoint/OneDrive の探索、メールボックスの探索と、段階を踏んで調べられている。自動化には Node.js と Microsoft Graph で作られた仕組みが使われたとされ、ページングの処理まで自動化されていた。python-httpx の User-Agent も観測されているが、Microsoft はこれだけで悪意があると判断すべきではないとしている。

収集先は SharePoint Online・OneDrive for Business、一部の侵入事例では Exchange Online（REST API 経由）である。大量の FileAccessed・FileDownloaded イベントが発生した。

速度が重要である。 Microsoft によれば、収集は急激ではなく、毎時1,000件未満のファイルまたはメールに抑えられ、数時間から数日にわたって通常の業務利用に紛れるペースで実行されていた。一部の事例ではセッションが約1時間持続していた。

ここから言えるのは、件数の絶対値を閾値にした検知は設計として脆いことである（本記録の評価）。攻撃者は閾値の存在を前提に速度を落としている。仮に「1時間に1,000件」で引くルールを置いても、攻撃者は900件に落とすだけで通過する。

有効なのは次の2つである。

  • 利用者ごとの平常値との比で見る。普段1日に10件しか開かない利用者が500件開けば、絶対値では小さくても明らかな異常である
  • ID・認証のイベントと突き合わせる。Microsoft も「SharePoint/OneDrive のダウンロード異常・Exchange REST の活動・メールボックスの検索を、ID と認証のイベントと突き合わせる」ことを推奨している

Microsoft は偵察についても「単一の API 呼び出しでは不審に見えにくく、一連の行動の相関分析が必要」と明記している。本キャンペーンに対する検知は、単発の閾値ではなく相関でしか成立しない。

攻撃者は乗っ取ったアカウントを次の侵入の足場にし、Teams が社内の信用を運んだ波及・関係先出典 [1] [2]

Microsoft が確認した一部のケースでは、すでに乗っ取った従業員のアカウントを利用し、「Microsoft Teams」を通じて同様の案内を送っていた。社内の人物から届いた連絡に見せることで、受信者に信用させようとしていたという。

この構造は、防御の観点では2つの意味を持つ（本記録の評価）。

第一に、1件の侵害が組織内で増幅する。最初の1人は外部からの電話で落ちるが、2人目以降は社内の同僚からの Teams メッセージで落ちる。「社外からの連絡は疑う」という訓練は、2人目以降には効かない。

第二に、ここは組織の監視が届く唯一の経路である。外部から個人用携帯にかかる電話と SMS は、組織のログに何も残らない。だが Teams のメッセージは社内の通信であり、リンク保護・メッセージ検査・送信パターンの分析の対象にできる。乗っ取られたアカウントから短時間に多数の同僚へ同じ外部リンクが送られるという形で、検知の射程に入る。

つまり本キャンペーンに対しては、「社内コミュニケーションツールを外部からの攻撃経路として監視するか」が実装上の分かれ目になる。Teams を「社内だから安全」として検査の対象外にしている組織では、増幅の段階が丸ごと見えない。

400件超を並べて見えたのは、同じ使い捨てテナントと同じ表示名だった評価・解釈出典 [1] [3]

Microsoft の報告（9月9日）は、1つのキャンペーンを縦に追ったものでした。Arctic Wolf Labs が10月26日に出した報告は、同じ入口を横に並べたものです。

対象は、Microsoft Teams の外部チャット作成機能が悪用された400件超のインシデント。そこに繰り返し現れたのは次の特徴でした（事実）。

  • 使い捨てテナント — 既定の *.onmicrosoft.com ドメインが全体の30〜40%。検証が要らず、数分で作れます
  • 有料ドメインの偏り — .top が約50%、.com が約40%、多階層ドメイン（.com.pl / .com.vn / .com.br 等）が5%強
  • 表示名 — 「(Internal)」を付けて社内 IT に見せる、「IT Service Desk – Liam」のように名前を添えて親しみやすくする、フランス語・スペイン語圏向けに地域化する、絵文字（盾・工具・チェックマーク）入りが100件以上
  • 一部のドメインは、正規の Microsoft や被害組織のサイトへリダイレクトするようDNS が設定されていた

重要なのは、攻撃者が URL を Teams のメッセージに貼らないことです（事実）。リモートセッションを張ってから、自分でペイロードへ移動します。メッセージを走査する仕組み（Safe Links のような）は、そもそも見るものが無いので効きません。

本記録の評価を2つ書きます。 ①表示名にコストがかからない以上、「見た目で見分ける」教育には天井があります。絵文字入りが100件以上あり、AI による自動生成が疑われている状況では、来月には別の見た目になっているはずです。②一方、テナント側の性質（既定ドメイン・作成日の新しさ・トライアル）は、攻撃者が安く変えられない部分です。 検知と遮断は、見た目ではなくここに置くべきです。

なお、この400件超が Microsoft の報告したパスキー口実のキャンペーン（Storm-3121・Storm-3032）と同じものかどうかは、どちらの報告も述べていません。 本記録は同一と断定しません。 共通しているのは「外部テナントからの IT サポート偽装」という入口の形であって、同じ攻撃者だという証拠ではありません。

受信箱を埋めてから電話が来る——接触から15分でペイロードに届いた事例がある原因・手口出典 [3]

Arctic Wolf が整理した流れは、次の順です（事実）。

  1. メールボム — 数分のうちに数百件の購読確認メールを送りつけ、受信箱を埋める
  2. 外部チャット — 直後に「IT サポート」を名乗る外部ユーザーが1対1のチャットを開く。受け手の側には「困っているところに助けが来た」という筋書きができている
  3. 音声通話（ビッシング） — Quick Assist や RMM ツールの導入を促す。報告では Quick Assist が最も多く使われた
  4. ペイロード実行 — 顧客事例では接触から15分以内。約5分間隔で複数の標的に同時接触する自動化も観測されている
  5. 永続化 — AnyDesk・Atera・ScreenConnect・Level（msiexec 経由）などの RMM を追加導入し、独立した制御チャネルを確保する

解析された1事例では、利用者に PowerShell の実行を指示し（親プロセスは explorer.exe。CAPTCHA の偽装が無い点を除けば ClickFix に似ています）、Azure Blob Storage から MSI を取得、同梱の cleaner.ps1 と archive6.zip を展開し、ZIP から出した Python 実装 ss.py を pythonw.exe で実行。LDAP で Active Directory の計算機とユーザーを収集し、ランダムに選んだ C2 ドメインへ送っていました。 この事例でランサムウェアの名称は挙げられていません。

15分という数字の読み方を書きます（本記録の評価）。これは1事例の値で、400件超の中央値ではありません。それでも設計には効きます——従業員が「おかしい」と気づき、窓口に報告し、SOC が判断して端末を隔離する、という経路は15分では回りません。 検知の起点を人の通報に置いている組織は、間に合わないことを前提に、機械側（外部テナントからの ChatCreated、未承認 RMM の起動、explorer.exe を親とする PowerShell）に自動の歯止めを置く必要があります。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
ヘルプデスク偽装からトークン奪取・MFA 追加・Graph 偵察を経てクラウドのデータに至る経路
layer 0 は脅威アクター（Storm-3121・Storm-3032 ほか）。 layer 1 は口実を運ぶ3つの経路——従業員の個人用携帯への電話・SMS と、 乗っ取り済みアカウントからの Microsoft Teams メッセージ。 layer 2 はアクセス権を奪う2つの仕組み（AiTM フィッシングサイトと、 正規の Microsoft 認証ページを使うデバイスコードフロー）。 layer 3 は侵害後の足場（攻撃者が追加した MFA 方法）と偵察（Microsoft Graph）。 layer 4 は収集先（SharePoint Online・OneDrive for Business・Exchange Online）と恐喝ブランド。 **デバイスコードフローは正規の Microsoft ページを通る点が要点で、 偽サイトの検知では止まらない。**

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察機会はあったが検知できず
**自社名を含むドメインの新規登録は、外から観測できる唯一の前兆である**（本記録の評価）。 証明書透明性ログ（CT ログ）や新規登録ドメインの監視に自社名と 「passkey」「sso」「mfa」「verify」「account」などの語の組み合わせを登録しておけば、 電話がかかってくる前に気づける可能性がある
検知できた証明書透明性ログと新規登録ドメインの監視に、自社名・ブランド名と 認証関連の語（passkey・sso・mfa・verify・login・account・key）の 組み合わせをルールとして登録し、検出時にテイクダウンと社内周知を同時に行う
影響を限定できた従業員の個人用携帯番号が外部に出回っていないか（名刺・SNS・ 漏えいデータ）を定期的に点検し、ヘルプデスクからの連絡に個人携帯を使わない運用を明示する
初期侵入機会はあったが検知できず
**Teams 経由の案内は、社内の通信として検知の射程に入る**（本記録の評価）。 外部からの電話・SMS は組織の監視が届かないが、 乗っ取られたアカウントから同僚へ送られる URL 付きメッセージは Teams のメッセージ検査・リンク保護の対象にできる。 **同一アカウントから短時間に多数の相手へ同じリンクが送られる**という形で現れる
検知できたTeams を含む社内コミュニケーションのリンク保護・URL 書き換えを有効にし、 「同一送信者から短時間に多数の宛先へ同じ外部リンク」を検知ルールにする
侵入を防げたヘルプデスクから従業員へ認証設定の変更を依頼する連絡経路を**1つに定め、 それ以外の経路（個人携帯への電話・SMS・Teams の DM）では依頼しない**と社内規程に書き、 従業員に周知する。従業員側には「案内されたリンクや電話番号をそのまま信用せず、 社内で確認された連絡経路で正当性を確かめる」ことを求める
検知できた認証要求の真偽を問い合わせられる確認済みの窓口（チャットの公式チャンネル・内線）を用意し、 「怪しい認証要求を報告しても咎められない」ことを明示する
認証情報アクセス機会はあったが検知できず
**デバイスコードフィッシングは、認証そのものは正規のページで行われるため 「偽サイトを見分ける」教育では止まらない**（本記録の評価）。 一方、サインインログ側には痕跡が出る—— 業務で使っていないデバイスコードフローの成功、 普段と異なる場所・端末からのサインインである。 Microsoft は一部の事例でセッションが約1時間持続していたとしている
侵入を防げた条件付きアクセスで**フィッシング耐性のある MFA**（FIDO2・パスキー・ Windows Hello for Business）を強制する
侵入を防げた**業務上必要のないデバイスコード認証と認証転送フローを条件付きアクセスで遮断する。** 必要な業務がある場合は、対象の利用者・アプリ・場所に限定する
影響を限定できた機微なクラウドリソースへのアクセスを、管理対象・コンプライアンス準拠の端末に限定する。 未管理端末からはダウンロードと同期のないブラウザ限定セッションに制限する
検知できたサインインログで「デバイスコードフローの成功」を単独の検知ルールにし、 許可した業務以外での発生を即時に調べる
永続化検知した
**ここが本キャンペーンで最も検知しやすい一点である**（本記録の評価）。 認証方法の追加は Entra ID の監査ログに必ず記録され、 正常な業務でも起きるが**頻度が低く、サインインの直後に起きることは稀**である。 Microsoft 自身も「普段と異なるログインだけでなく、 **その直後に認証方法が追加されていないか**を関連付けて確認することが重要」としている
検知できた**「異常なサインインの直後に認証方法が追加された」を単独のアラートにする。** サインインの異常だけ、認証方法の追加だけでは埋もれるため、 2つの事象を時間窓で相関させる（Microsoft の推奨）
侵入を防げた認証方法（セキュリティ情報）の新規登録・変更に条件付きアクセスを適用し、 **管理対象端末からのアクセスとフィッシング耐性のある認証を要求する**
検知できたヘルプデスクによる認証情報・MFA のリセットの前に厳格な本人確認を行い、 **リセットはすべて本人へ通知する**
内部探索機会はあったが検知できず
**1回1回の API 呼び出しは正当な操作と区別がつかない**（Microsoft 自身の指摘）。 検知できるのは「短時間に多数の種類のディレクトリ情報を順に読む」という**形**であり、 単発の閾値では引っかからない。 python-httpx の User-Agent は自動化の示唆だが、 Microsoft は**これだけで悪意があると判断すべきではない**としている
検知できたMicrosoft Graph の利用について「短時間・大量・自動化された列挙」 （ディレクトリ・ロール・サービスプリンシパル・SharePoint/OneDrive の列挙）を 相関ルールとして実装する。**単発の呼び出し数ではなく、読んだ対象の種類の広がりで見る**
影響を限定できたアプリへの利用者同意を制限し、**高権限の Graph 権限を定期的に棚卸しして削る**
収集機会はあったが検知できず
**件数ベースの閾値検知を避けるために速度を落としているため、 「1時間に何件」という閾値では止まらない**（本記録の評価）。 有効なのは**利用者ごとの平常値との比**と、 **ID・認証イベントとの突き合わせ**である—— Microsoft も「SharePoint/OneDrive のダウンロード異常・Exchange REST の活動・ メールボックスの検索を、ID と認証のイベントと突き合わせる」ことを推奨している
検知できた利用者ごとのファイルアクセス・ダウンロード件数の平常値を学習させ、 **絶対件数ではなく個人の平常値からの乖離**でアラートを上げる
影響を限定できた匿名共有リンクを無効化し、未管理端末からのダウンロードと同期を禁止する
影響を限定できた機微なファイルに感度ラベルと暗号化を適用し、 持ち出されても閲覧できない状態にする
持ち出し公表されていない
**持ち出しの段階そのものの検知機会は報告に記述がない。** クラウドサービスからのダウンロードが正規の API・正規のトークンで行われるため、 収集段階と持ち出し段階が実質的に同じ操作になっている（本記録の評価）
影響を限定できた侵害が疑われる ID のセッションとリフレッシュトークンを**即時に無効化**し、 認証情報をリセットする。**パスワード変更だけではトークンは失効しない**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 認証設定の変更を依頼する連絡経路を1つに定め、それ以外では依頼しないと宣言する
    本キャンペーンの入口は「IT ヘルプデスクを名乗る者からの、 従業員の**個人用携帯**への電話・SMS」である。 **従業員が「これは正規の依頼か」を判断する基準を組織が与えていなければ、 どんな教育も「怪しければ疑う」という曖昧な指示にしかならない。** さらに攻撃者は乗っ取ったアカウントから Teams で同じ案内を送る
    取るべき行動 ①認証設定の変更依頼を出す経路を**1つに定める** （例: 社内ポータルの告知のみ。電話・SMS・DM では依頼しない） ②その方針を全従業員に周知し、**「それ以外の経路で依頼が来たら必ず詐欺である」と断言できる形にする** ③真偽を問い合わせる確認済みの窓口を用意し、報告しても咎められないことを明示する。 **「疑ってください」ではなく「この経路以外は無い」と言い切れる状態を作るのが要点**
  • ヘルプデスクの本人確認を、フィッシング耐性のある MFA の導入と同時に強化する
    フィッシング耐性のある MFA を強制すると、**攻撃の標的は「再発行の窓口」に移る。** 物理キーの紛失・端末の交換・入社初日といった局面では、 必ず誰かが本人確認だけで認証手段を再発行する。 Microsoft も「ヘルプデスクによる資格情報や MFA のリセットの前には 厳格な本人確認を行い、リセットはすべて通知する」ことを推奨している
    取るべき行動 ①ヘルプデスクが認証情報・MFA をリセットする手順に、 **複数の経路による本人確認**（上長の承認・既知の別経路での折り返し・ 人事データとの突合）を必須で組み込む ②リセットは例外なく**本人へ通知**する ③一時的な例外（Temporary Access Pass 等）の発行権限を絞り、発行の記録を監査する。 **MFA の強化計画とヘルプデスク手順の見直しを同じプロジェクトに入れる**—— 別々にやると、強化した分だけ窓口に穴が移る
  • デバイスコード認証を使っている業務を棚卸しし、不要な分を遮断する決定を下す
    デバイスコードフィッシングは、**認証そのものが正規の Microsoft ページで行われる**ため、 「偽サイトを見分ける」教育では止まらない。 Microsoft は「業務上必要のないデバイスコード認証を制限する」ことを推奨している。 **技術的な遮断でしか止められない経路である**
    取るべき行動 ①デバイスコードフロー（および認証転送フロー）の利用実績を サインインログから抽出し、**どの業務・どの端末が使っているか**を一覧にする ②正当な用途（入力機構のない会議室機器・IoT・一部の CLI）を特定し、 対象を利用者・アプリ・場所で限定する ③それ以外を条件付きアクセスで遮断する。 **棚卸しをせずに一律遮断すると業務が止まる**ため、 遮断の決定には「止まる業務を引き受ける」という経営判断が要る
  • 社内コミュニケーションツールを「攻撃経路」として監視対象に入れる
    攻撃者は乗っ取った従業員アカウントから **Microsoft Teams** で同じ口実を社内に送っていた。 **外部から個人携帯にかかる電話と SMS は組織のログに残らないが、 Teams のメッセージは残る。** ここが本キャンペーンで組織の監視が届く唯一の増幅経路である
    取るべき行動 ①Teams を含む社内コミュニケーションのリンク保護・URL 書き換え・ メッセージ検査を有効にする ②「同一送信者から短時間に多数の宛先へ同じ外部リンク」を検知ルールにする ③**「社内ツールだから検査しない」という前提を文書で否定する。** 社内ツールの検査が例外扱いになっていないかを、設定画面で確認する
  • 「件数の閾値」ではなく「個人の平常値からの乖離」で見る検知方針に切り替える
    本キャンペーンの収集は**毎時1,000件未満に意図的に抑えられ、 数時間から数日に分散**されていた。 **攻撃者は閾値の存在を前提に速度を調整している。** 絶対件数の閾値は、閾値を知られた時点で無効になる
    取るべき行動 ①クラウドストレージ・メールのアクセス検知を、 絶対件数ベースから**利用者ごとの平常値との比**に切り替える ②ID・認証イベントとの相関を検知の前提に置く （Microsoft の推奨: ダウンロード異常・Exchange REST の活動・ メールボックスの検索を ID・認証イベントと突き合わせる） ③**検知方針を「単発の閾値」から「行動の並び」へ移す**という方針転換として、 SOC の運用設計に明記する
  • 外部とのチャットを「既定で誰とでも」から「許可した相手とだけ」に変える判断は、CISO が出す
    Arctic Wolf は400件超を分析し、 「この活動は既知の Teams の脆弱性を突くものではなく、 既定で有効な正規の共同作業機能を悪用している」（原文英語）と明記した。 既定値のままでは、世界中のどのテナントからでも自社の従業員に1対1で話しかけられる。 既定ドメインのテナントは数分で作れる。
    取るべき行動 **外部チャットを許可リスト方式へ切り替える判断を、情報システム部門の設定変更ではなく 経営判断として出す。** 同時に、**外部との共同作業が日常の部署に代替経路を用意する** （用意しないと個人のメールや SNS へ逃げる）。 **「大半の組織に開かれた外部チャットの正当な必要は無い」という前提が 自社に当てはまるかを、部署ごとに1行で書き出すところから始める。**
セキュリティ技術者への示唆
  • 「異常なサインインの直後に認証方法が追加された」を単独のアラートとして実装する
    攻撃者は永続化のために**自分が管理する電話番号・認証アプリ・ ソフトウェアトークンを MFA 方法として追加**している。 この操作は Entra ID の監査ログに必ず残り、頻度も低い。 Microsoft 自身が「普段と異なるログインだけでなく、 **その直後に認証方法が追加されていないか**を関連付けて確認する」ことを求めている
    取るべき行動 監査ログの認証方法登録・変更イベント（ソフトウェアトークンの追加を含む 「Update user」操作等）と、サインインログの異常サインインを **30分〜数時間の時間窓で相関**させるルールを作る。 入社手続き・端末配布の既知の期間を除外リストで調整し、 **検出時は対象 ID のセッションとリフレッシュトークンの無効化までを自動化する**。 パスワード変更だけではトークンは失効しないことを手順に明記する
  • デバイスコードフローの成功を1つの検知ルールにする
    デバイスコードフィッシングでは、利用者は**正規の Microsoft 認証ページ**で コードを入力する。偽サイトの検知では引っかからない。 一方、サインインログには「デバイスコードフローでの認証成功」として記録が残る
    取るべき行動 サインインログを認証フローの種別で絞り、 **デバイスコードフローの成功を単独のアラート**にする。 許可した業務（会議室機器・IoT・特定の CLI）を除外リストに入れ、 それ以外の発生は即時に調査する。 **あわせて条件付きアクセスでの遮断を申請する**—— 検知は遮断までの橋渡しであり、恒久対策ではない
  • Microsoft Graph の利用を「呼び出し数」ではなく「読んだ対象の広がり」で見る
    攻撃者は Node.js と Microsoft Graph で作った仕組みを使い、 テナント情報・ディレクトリ・特権・MFA 情報・アプリと同意・ SharePoint/OneDrive・メールボックスを**順に**調べていた。 Microsoft は「単一の API 呼び出しでは不審に見えにくく、 一連の行動の相関分析が必要」と明記している
    取るべき行動 Graph の監査ログを利用者・アプリ単位で集約し、 **短時間に読んだエンドポイントの「種類の数」**を指標にする。 1種類を大量に読むのは正常な業務でも起きるが、 ディレクトリ→ロール→サービスプリンシパル→SharePoint→メールボックスと **横断的に読む並びは偵察の形である。** python-httpx などの自動化を示す User-Agent は補助情報として扱い、 **それ単独では判定に使わない**（Microsoft の注意書きに従う）
  • 封じ込めは「セッションとリフレッシュトークンの無効化」から始める
    AiTM フィッシングで奪われるのは認証情報と**セッショントークン**である。 **パスワードを変えてもトークンは失効しない。** 攻撃者が追加した MFA 方法も残る。 Microsoft は「侵害された ID のセッションとリフレッシュトークンを無効化し、 資格情報をリセットする」「攻撃者が登録した認証方法、メールボックスルールを削除し、 認証方法の安全な再登録を求める」ことを推奨している
    取るべき行動 ID 侵害の封じ込め手順を次の順序で固定する—— ①セッションとリフレッシュトークンの無効化 ②資格情報のリセット ③**攻撃者が追加した認証方法の削除**（本人確認の後） ④メールボックスルール・転送設定の確認と削除 ⑤認証方法の安全な再登録。 **③を飛ばすと、リセット後に攻撃者が再び入れる。** この順序を Runbook に書き、机上訓練で実際に手順を通す
  • 未管理端末からのダウンロードと同期を止め、匿名共有リンクを無効化する
    攻撃者の収集先は SharePoint Online・OneDrive for Business・Exchange Online である。 **アクセスは正規のトークンと正規の API で行われるため、「不正なアクセス」としては見えない。** 見える形にできるのは、持ち出せる量と経路をあらかじめ絞ることである
    取るべき行動 ①条件付きアクセスのアプリ制御で、未管理端末からは **ダウンロードと同期のないブラウザ限定セッション**に制限する ②匿名共有リンクを無効化する ③機微なファイルに感度ラベルと暗号化を適用し、 持ち出されても開けない状態にする。 **①〜③はいずれも検知ではなく「持ち出せる量を減らす」対策である**—— 検知が間に合わない前提で、被害の上限を先に決めておく
  • 自社名を含むドメインの新規登録を監視する
    攻撃者は**事前に**標的企業を調べ、 パスキー・SSO・鍵の同期・アカウント設定・本人確認に関連する語と企業名を 組み合わせたフィッシングドメインを登録している。 企業名はサブドメインに置かれる。 **これは電話がかかってくる前に外から観測できる唯一の前兆である**（本記録の評価）
    取るべき行動 証明書透明性（CT）ログと新規登録ドメインのフィードを監視し、 **自社名・ブランド名と認証関連の語**（passkey・passkeys・sso・mfa・ verify・verification・login・signin・account・key・keysync）の 組み合わせをルールとして登録する。 検出時はテイクダウン申請と**社内周知を同時に**行う—— テイクダウンには時間がかかるため、周知の方が早く効く
  • 検知の起点を人の通報に置くと、15分には間に合わない
    Arctic Wolf の顧客事例では、外部チャットでの接触からペイロード実行まで15分以内だった。 約5分間隔で複数の標的に同時接触する自動化も観測されている。 従業員が気づき、窓口に報告し、SOC が判断して隔離する経路は、この時間では回らない。
    取るべき行動 **機械側に検知点を置く**——①**Teams が会話作成時に出す ChatCreated イベント**を 外部テナントからの初回接触の検知に使う（表示名の特徴やテナント作成日と組み合わせる）、 ②**未承認の RMM（AnyDesk・Atera・ScreenConnect・Level 等）の起動**を アプリケーション制御で止める、 ③**explorer.exe を親とする PowerShell の実行**を検知対象に入れる。 **人の通報は補助線であって、一次の検知手段にしない。**
  • TLD での遮断は半分しか止められない
    Arctic Wolf が特定した有料ドメインのうち、.top が約50%、.com が約40%だった。 既定の *.onmicrosoft.com テナントも全体の30〜40%を占める。 「怪しい TLD を切る」対策では、.com を使う側が残る。
    取るべき行動 **ドメイン名ではなくテナントの性質で絞る**—— **トライアルテナントからのフェデレーションを遮断し （`Set-CsTenantFederationConfiguration -ExternalAccessWithTrialTenants "Blocked"`）、 非管理アカウントからの会話開始を無効化し、許可した外部ドメインだけを通す。** **.top などの一括遮断は、その上に重ねる補助策として扱う。**
