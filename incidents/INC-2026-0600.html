INC-2026-0600FirstVDS侵害で顧客VPSの鍵が流出

ロシアのホスティング事業者 FirstVDS が2026年10月17日、 仮想化管理システム **VMmanager 6 の脆弱性**を悪用されて自社インフラの一部へ侵入され、 **一部の仮想化ノード上で情報窃取プログラムを実行された**—— そのプログラムは**顧客の仮想サーバーのディスクを「読み取り専用」でマウントして 中身を収集し、攻撃者が管理するサーバーへ送信**していた。 収集対象はパスワード・SSH 鍵・API 鍵・クラウドサービスのトークン・設定ファイル・ コマンド履歴・暗号資産ウォレットのデータ・利用者のファイルである。 **マルウェアは仮想マシンの内部では実行されず、ディスクを書き換えなかったため、 ゲスト OS 側には攻撃の痕跡が残らない可能性がある**とされた。 同社は仮想化管理システムへの外部アクセスを遮断し、攻撃者のサーバーのアドレスを 自社ネットワークでブロック。影響を受けたサーバーの所有者には電子メールと 会員ページで通知し、**通知を受け取った場合はサーバー上の全データが コピーされたものとして扱うよう**求めた。 報道（SecurityLab）によれば VMmanager 6 の開発元は ISPsystem で、 想定される不正アクセスの時間帯は10月17日12時27分から22時34分（モスクワ時間）の約10時間である

初報: 2026年10月18日 最終更新: 2026年10月19日

ロシアのホスティング事業者 FirstVDS は2026年10月17日、サイバー攻撃を受けて自社インフラの一部へ侵入されたことを公表しました。侵入経路は仮想化管理システム VMmanager 6 の脆弱性です。

本件の構造が特異なのは、顧客の仮想サーバーの中に入らずにデータを盗んだ点にあります。FirstVDS の説明によれば、攻撃者は一部の仮想化ノード（ハイパーバイザが動く物理サーバー）上で情報窃取プログラムを起動しました。そのプログラムは

  • 顧客の仮想サーバーのディスクを「読み取り専用」でマウントする
  • 中身を収集する
  • 攻撃者が管理するサーバーへ送信する

という動作をしていました。収集対象は、パスワード、SSH 鍵と API 鍵、クラウドサービスのトークン、設定ファイル、コマンド履歴、暗号資産ウォレットのデータ、利用者のファイルです。

重要なのは、マルウェアが仮想マシンの内部では実行されず、ディスクの内容を書き換えなかったことです。そのため仮想サーバーは平常どおり動き続け、ゲスト OS の内部には攻撃の痕跡が残らない可能性があると FirstVDS は述べています。顧客が自分のサーバーにログインして調べても、何も見つからないという状態です。

影響は FirstVDS の全インフラではなく、一部の仮想化ノードに限られたとされます。影響を受けたサーバーの所有者には電子メールと会員ページで通知が送られ、通知を受け取った場合は、そのサーバー上の全データが攻撃者にコピーされたものとして扱うべきとされました。

攻撃の発見後、FirstVDS は侵入の経路となった仮想化管理システムへの外部アクセスを遮断し、攻撃者のサーバーのアドレスを自社ネットワークでブロックしました。VMmanager 6 の開発元は中間パッチを公開し、最終的な修正に取り組んでいるとされ、問題が完全に解消されるまで管理システムへの外部アクセスは閉じたままとされています。2026年10月19日7時20分（モスクワ時間）の追記では、ベンダーの追加修正が適用されたと報告されました。

顧客への推奨は具体的です。①潜在的に侵害された暗号資産ウォレットから、クリーンな端末で新規に作成したウォレットへ資産を移す ②サーバーに保存していたパスワード・SSH 鍵・API 鍵・トークンをすべて変更し、古い鍵は「新しく発行する」だけでなく明示的に失効させる ③10月17日以降のログイン履歴を確認する④SSH の authorized_keys、新規ユーザー、cron のジョブ、systemd のサービスを点検する⑤顧客の個人データを保存していた場合は、ロスコムナゾール（Роскомнадзор）への届け出が必要かを弁護士に相談する。

調査は継続中で、完了後に詳細なインシデントレポートを公表する予定とされています。本記録は、日本の読者にとっては海外事案の記録ですが、IaaS・VPS・専用サーバーを利用する組織にそのまま当てはまる論点を含みます。事実（FirstVDS の公表と報道）と評価（本記録の判断）は分けて記述します。

    トレードオフ: 外部アクセスを閉じる代わりに、**自社の運用が管理網・踏み台経由に限られる。** ホスティング事業者の管理システムは、 顧客対応・障害対応・リソースの払い出しに日常的に使うものであり、 遠隔からの即時操作ができなくなれば**対応時間が伸びる。** 一方、ベンダーの修正を待って開け続ける選択は、 **同じ脆弱性が他の攻撃者にも使われる期間を延ばす**
  • 侵害の事実・侵入経路（VMmanager 6 の脆弱性）・窃取プログラムの動作・ 収集された情報の種類・ゲスト内に痕跡が残らない可能性・ 影響範囲が一部のノードに限られたこと・実施した措置・ 顧客が取るべき具体的な手順を公表した。 一方、**脆弱性の識別子・影響件数・持ち出された総量・発見の端緒は示していない**
    トレードオフ: 早く出す代わりに、**影響件数と脆弱性の識別子という2つの重要な情報が欠けた。** 前者が無いと事案の規模が分からず、 後者が無いと**同じ製品を使う他の事業者が自社の露出を判定できない。** 一方、脆弱性が完全に塞がっていない段階で識別子と詳細を出せば、 **同製品を使う他の事業者が一斉に標的になる**
  • 顧客に対し、サーバーに保存されていた**パスワード・SSH 鍵・API 鍵・トークンの 全面的な変更**を求め、**古い鍵は新規発行で済ませず明示的に失効させる**よう指示した。 **暗号資産についてはクリーンな端末で新規に作成したウォレットへ資産を移すよう求めた。** あわせて10月17日以降のログイン履歴の確認と、 SSH の `authorized_keys`・新規ユーザー・cron のジョブ・systemd のサービスの点検を推奨した
    トレードオフ: **実行の負担はすべて顧客側にある。** 鍵とトークンの全面的な失効と再発行は、 連携先のサービス・CI/CD・デプロイ鍵・外部 API の設定変更を伴い、 作業中にサービスが止まる場面もある。 **「古い鍵を失効させる」はとくに影響が大きい**—— どこで使っているかを把握していなければ、 失効させた瞬間に想定外の連携が壊れる。 一方、失効させなければ窃取された鍵は有効なまま残る

ハイパーバイザ側から顧客のディスクを読み取り専用でマウントし、中身だけを抜いていった概観出典 [1] [2] [3]

FirstVDS の公表によれば、起きたことは次のとおりである。

  • 2026年10月17日、攻撃者が仮想化管理システム VMmanager 6 の脆弱性を悪用し、同社インフラの一部へのアクセスを獲得した
  • 攻撃者は一部の仮想化ノード上で情報窃取プログラムを起動した
  • そのプログラムは顧客の仮想サーバーのディスクを「読み取り専用」でマウントし、情報を収集して攻撃者が管理するサーバーへ送信した
  • 収集対象はパスワード、SSH 鍵と API 鍵、クラウドサービスのトークン、設定ファイル、コマンド履歴、暗号資産ウォレットのデータ、利用者のファイル
  • マルウェアは仮想マシンの内部では実行されず、ディスク上の何も変更しなかった。そのためサーバーは平常どおり稼働し、ゲスト OS 内部に攻撃の痕跡が無かった可能性がある
  • 影響は全インフラではなく一部の仮想化ノードに限られた
  • 影響を受けたサーバーの所有者には電子メールと会員ページで通知した。通知が届いていない場合は、そのノードで痕跡が見つかっていないという扱い
  • 通知を受け取った場合は、サーバー上の全データがコピーされたものと考えるべき
  • 発見後、仮想化管理システムへの外部アクセスを遮断し、攻撃者のサーバーのアドレスを自社ネットワークでブロックした
  • ベンダーは中間パッチを公開し、最終的な修正に取り組んでいる。完全な解消まで管理システムへの外部アクセスは閉じたまま
  • 2026年10月19日7時20分（モスクワ時間）の追記で、ベンダーの追加修正が適用されたと報告された
  • 調査は継続中で、完了後に詳細なインシデントレポートを公表する予定

報道（SecurityLab）によれば、VMmanager 6 の開発元は ISPsystemで、同社は「Группа Астра」傘下である。想定される不正アクセスの時間帯は10月17日12時27分から22時34分（モスクワ時間）の約10時間7分とされるが、この時刻は一次資料で裏を取れていない。

顧客は自分のサーバーを調べても何も見つけられない——痕跡が残らないよう設計されていた原因・手口出典 [1] [3]

本件でもっとも重要なのは、攻撃の位置である。

窃取プログラムが動いたのは仮想化ノード（ハイパーバイザが動く物理サーバー）の上であり、顧客の仮想マシンの中ではない。顧客のディスクは、ハイパーバイザ側から読み取り専用でマウントされた。FirstVDS はこう述べている（原文ロシア語）。

マルウェアは仮想マシン自体の内部では起動せず、そのディスク上の何も変更しなかったため、サーバーは平常モードで稼働を続け、ゲストシステム内部に攻撃の痕跡が無かった可能性がある

3つの選択が重なっている（本記録の整理）。

  1. ゲスト内で実行しない → ゲストのプロセス一覧・監査ログ・EDR に現れない
  2. 読み取り専用でマウントする → ファイルのアクセス時刻（atime）も含め書き込みが発生しない
  3. ディスクを変更しない → 改ざん検知・ファイル整合性監視に引っかからない

結果として、顧客側に観測点が一つも残らない。顧客が自分のサーバーにログインしてログを調べ、EDR の結果を確認し、ファイルのハッシュを突き合わせても、何も出ないのが正常な結果である。「何も出なかったから無事だった」という推論が、本件では成立しない。

これは顧客側の対策の不備ではなく、IaaS・VPS という構造に内在する盲点である。仮想マシンのディスクは、最終的にハイパーバイザが読み書きできる形で存在している。ハイパーバイザが攻撃者の手に落ちれば、ゲスト OS がどれだけ堅牢でも、ディスクの中身は読める。

FirstVDS が「通知を受け取った場合は、サーバーの全データがハッカーによってコピーされたものと考えるべき」と書いているのは、この構造の裏返しである。顧客に確認の手段が無いため、事業者からの通知が唯一の情報源になる。「調べて判断してください」ではなく「侵害されたものとして動いてください」と指示するしかない。

窃取されたのは「サーバーの中身」ではなく「他のシステムへ入るための鍵」だった被害規模・影響範囲出典 [1] [2] [3]

FirstVDS が挙げた収集対象は次のとおりである。

  • パスワード
  • SSH 鍵と API 鍵
  • クラウドサービスのトークン
  • 設定ファイル
  • コマンド履歴
  • 暗号資産ウォレットのデータ
  • 利用者のファイル

報道（SecurityLab）は、より細かい対象として次を挙げている（こちらは報道値であり、一次資料で裏を取れていない）。

  • KeePass・GPG の内容、ブラウザの保存パスワードと Cookie
  • 環境変数ファイル、Docker の設定
  • PostgreSQL・MySQL・MongoDB・Redis の接続文字列
  • Restic・Borg のバックアップ用パスワード
  • 暗号資産ウォレットの秘密鍵・バリデータ鍵・シードフレーズ
  • AWS・Google Cloud・Azure・OpenStack の認証情報
  • Kubernetes と Terraform の設定
  • GitHub・GitLab・npm のトークン、各種の API キー

この一覧が示しているのは、被害が「VPS 1台」に留まらないことである（本記録の評価）。一覧に並ぶのはほとんどが他のシステムへ入るための資格情報である。

  • クラウドの認証情報 → 顧客の AWS・GCP・Azure 環境へ
  • GitHub・GitLab のトークン → ソースコードと CI/CD パイプラインへ
  • npm のトークン → 公開パッケージの改ざんへ（供給網への波及）
  • データベースの接続文字列 → 別のホストで動く本番データベースへ
  • バックアップ用パスワード → 復旧の最後の砦へ
  • ウォレットの秘密鍵・シードフレーズ → 直接の金銭的損失へ

1台の VPS の侵害が、その VPS に鍵が置かれていたすべての環境の侵害に広がる構造である。「踏み台として使っていた小さなサーバー」「開発用の検証機」が、実は組織の鍵束になっていることは珍しくない。

FirstVDS が暗号資産を最優先に挙げ、「クリーンな端末で新規に作成したウォレットへ移す」よう求めているのは、窃取された秘密鍵は失効させられないためである(本記録の補足)。パスワードと API キーは変更できるが、暗号資産の秘密鍵は「変える」のではなく「資産を別の鍵の下へ移す」しかない。

顧客への指示は「古い鍵を失効させる」まで書き切っている再発防止出典 [1] [3]

FirstVDS が顧客に求めた対応は次のとおりである。

  1. 潜在的に侵害された暗号資産ウォレットから、クリーンな端末で新規に作成したウォレットへ資産を移す
  2. サーバーに保存されていたすべてのパスワード・SSH 鍵・API 鍵・トークンを変更する。古い鍵は「新しく発行する」だけでなく、明示的に失効させる
  3. 2026年10月17日以降のログイン履歴を確認する
  4. 攻撃者が窃取したデータを既に使っている場合に備え、SSH の authorized_keys、新規ユーザー、cron のジョブ、systemd のサービスを点検する
  5. サーバーに顧客の個人データを保存していた場合は、ロスコムナゾールへの届け出が必要かを弁護士に相談する

2 の書き方が実務的である（本記録の評価）。「鍵を再生成してください」で終わる通知は多いが、新しい鍵を作っても古い鍵が有効なままなら、攻撃者は入れる。 SSH 鍵は authorized_keys から削除しなければ失効しない。API トークンは管理画面で revoke しなければ有効である。FirstVDS は「именно отозвать, а не просто выпустить новые」（まさに失効させるのであって、単に新しいものを発行するのではない・原文ロシア語）と、この区別を明示している。

4 は、窃取した鍵を使った再侵入と永続化を想定した点検項目である。挙げられている4つは、いずれも「鍵で入った攻撃者が居座るために使う場所」である。

点検先 攻撃者の使い方
SSH の authorized_keys 自分の公開鍵を追加して再入場
新規ユーザー 別のアカウントを作って温存
cron のジョブ 定期実行で接続を張り直す
systemd のサービス 再起動後も生き残る常駐

一方で、公表資料に見当たらないものがある（本記録の指摘）。影響を受けたサーバーの識別子の一覧、侵害されたノードの範囲、顧客の移行を助ける仕組み（スナップショットの提供・代替インスタンス）、窃取データの悪用を監視する仕組みである。顧客に求める作業は重く、事業者側の支援策は示されていない。

VMmanager 6 の脆弱性から仮想化ノードを経て、顧客 VPS のディスクの中身が持ち出された経路
layer 0 は攻撃者と、悪用された VMmanager 6 の脆弱性。 layer 1 は FirstVDS の仮想化管理システムと、侵害された一部の仮想化ノード。 layer 2 は顧客の仮想サーバーとそのディスク—— **ディスクは読み取り専用でマウントされ、ゲスト OS の内部では何も実行されず、 ディスクは書き換えられなかった（そのためゲスト側に痕跡が残らない）。** layer 3 は窃取された資格情報の種類と、それが通じる先（クラウド・リポジトリ・ データベース・暗号資産）。 layer 4 は攻撃者のサーバー（送信先）と、FirstVDS・ベンダー・顧客・監督機関。 **点線で示すべきは「顧客側の観測点が存在しない」ことであり、 顧客は事業者からの通知でしか侵害を知れない。**

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入公表されていない
**発見の端緒が公表されていないため、この段階で検知機会があったかは評価できない。** FirstVDS は「攻撃の発見後」の措置を述べるだけで、 何を見て気づいたかに触れていない（本記録の指摘）
侵入を防げた仮想化管理システム・ハイパーバイザ管理インターフェースを インターネットから到達できない位置に置き、 運用は踏み台・VPN・専用管理網からのみに限定する
影響を限定できた管理系ソフトウェアのベンダーのセキュリティ告知を購読し、 基盤に影響するものを48時間以内に評価・適用する運用にする。 **ただし本件ではベンダーの修正が侵害の後に出ているため、 これ単独では防げない**（本記録の留保）
実行機会はあったが検知できず
**ハイパーバイザ上で未知のプロセスが動き、ディスクをマウントし、 外部へ通信するという一連の動作は、基盤側では観測可能な振る舞いである**（本記録の評価）。 仮想化ノードは稼働するソフトウェアが限られているため、 変化の少ない環境としてプロセスとファイルの許可リストが作りやすい。 **検知されなかった事実は、基盤側の実行監視が及んでいなかったことを示す**
侵入を防げた仮想化ノードに実行監視（EDR または許可リスト方式の実行制御）を入れ、 **許可していないバイナリの実行を拒否する。** 仮想化ノードは稼働ソフトが限られるため許可リストの維持が現実的である
検知できた仮想化ノード上での新規プロセスの生成、 とくに**顧客ディスクのマウント操作**を監査対象にしてアラートを上げる
収集現実的な検知機会なし
**顧客（ゲスト OS）側に検知機会は無い**（本記録の評価）。 ディスクはハイパーバイザ側からマウントされており、 ゲスト OS のプロセス・ファイルアクセスログ・EDR のいずれにも現れない。 **「自分のサーバーを調べても何も出ない」のが正常な結果である。** これは顧客側の対策の不備ではなく、構造上の盲点である
侵入を防げた**仮想サーバーのディスク全体を暗号化し、鍵をディスク外に置く。** ディスクを読み取り専用でマウントされても中身が読めない状態にする。 ただし起動時の鍵の供給方法（ネットワーク経由・TPM・手動入力）の設計が要る
影響を限定できた秘密情報をサーバーのファイルシステムに置かず、 外部のシークレット管理（Vault・クラウドのシークレットマネージャ）から 実行時に取得する構成にする
侵入を防げた暗号資産の鍵・シードフレーズを**インターネットに接続したサーバーに置かない** （ハードウェアウォレット・オフライン端末で管理する）
検知回避現実的な検知機会なし
**これは攻撃者が検知回避のために選んだ設計である**（本記録の評価）。 読み取り専用でマウントし、書き込まず、ゲスト内で実行しない—— 3つの選択がいずれもゲスト側の観測を無効化している。 **顧客にとっての帰結は深刻である**: 侵害の有無を自力で判定できないため、 **事業者からの通知が唯一の情報源になる。** FirstVDS が「通知を受け取った場合は全データがコピーされたものとして扱え」と 書いているのは、顧客側で確認する手段が無いことの裏返しである
影響を限定できた**ゲスト側で検知できない前提で、鍵とトークンの定期的なローテーションを運用に組み込む。** 「侵害が確認されたら変える」ではなく「期限で必ず変わる」設計にする
復旧を早められたホスティング事業者との契約・SLA に **「基盤側の侵害が判明した場合の通知の義務と期限」**を含める
持ち出し機会はあったが検知できず
**仮想化ノードからの外向き通信は、基盤側で観測できる**（本記録の評価）。 仮想化ノード自身が外部へ大量にデータを送る必要は通常なく、 **「ホストからの未知の宛先への外向き通信」は検知の筋が良い信号である。** FirstVDS が事後にアドレスをブロックできたことは、通信記録が残っていたことを示す
侵入を防げた仮想化ノード自身の外向き通信を**許可リスト方式で制限する** （ベンダーの更新サーバー・自社の監視系・ライセンス確認先のみ）。 顧客 VM のトラフィックとは経路を分ける
検知できたハイパーバイザ・ホストからの外向き通信量と宛先の分布を監視し、 未知の宛先への通信でアラートを上げる

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
侵入の経路となった**仮想化管理システムへの外部アクセスを遮断**し、 **脆弱性が完全に解消されるまで閉じたままにする**と決めた機能した**「パッチが完全でないあいだは閉じる」という判断は、本件の構造に対して適切である** （本記録の評価）。 ベンダーの修正を待つあいだ、脆弱性は依然として悪用可能であり、 かつ**同じ製品を使う他のホスティング事業者も同じ状態に置かれる。** 自社の運用の不便を引き受けて露出を絶った判断は筋が通っている。 **ただし「閉じたまま」がいつまで続くかは公表されておらず、 恒久対策への移行計画は示されていない**
侵害の事実・侵入経路（VMmanager 6 の脆弱性）・窃取プログラムの動作・ 収集された情報の種類・ゲスト内に痕跡が残らない可能性・ 影響範囲が一部のノードに限られたこと・実施した措置・ 顧客が取るべき具体的な手順を公表した。 一方、**脆弱性の識別子・影響件数・持ち出された総量・発見の端緒は示していない**機能した**顧客が「いま何をすべきか」を判断できる水準には達している**（本記録の評価）。 とくに評価できるのは次の3点である。 ①**ゲスト OS 内に痕跡が残らない可能性を明記した**—— これを書かなければ、顧客は自分のサーバーを調べて「何も出ないから無事」と 誤って結論づける。 ②**「通知を受け取った場合は全データがコピーされたものとして扱え」**と、 判断の基準を顧客に委ねずに指示した。 ③**鍵を「新しく発行する」だけでなく「古いものを失効させる」よう明示した**—— この違いを書かない通知は多い。 **脆弱性の識別子を出さない判断も、修正が未完であることを踏まえれば妥当である**
顧客に対し、サーバーに保存されていた**パスワード・SSH 鍵・API 鍵・トークンの 全面的な変更**を求め、**古い鍵は新規発行で済ませず明示的に失効させる**よう指示した。 **暗号資産についてはクリーンな端末で新規に作成したウォレットへ資産を移すよう求めた。** あわせて10月17日以降のログイン履歴の確認と、 SSH の `authorized_keys`・新規ユーザー・cron のジョブ・systemd のサービスの点検を推奨した部分的に機能**指示の内容は正しく、具体性も高い**（本記録の評価）。 特に「失効させる（отозвать）」と「新しく発行する（выпустить новые）」を 明確に区別した点、暗号資産の移動先を「クリーンな端末で新規作成」と限定した点は実務的である。 **不十分なのは、事業者側が顧客を助ける手段を示していないこと**である—— VPS のスナップショット提供、侵害が疑われるノードの一覧、 影響を受けたサーバーの識別子、代替インスタンスの提供といった 支援策は公表資料に見当たらない。 **「あなたのサーバーは全部盗まれたと思って全部やり直してください」で終わっている**
CISO・経営層への示唆
  • 「借りているサーバーは、基盤が落ちれば中身が読まれる」を前提に置く
    本件の窃取は**ハイパーバイザ側から顧客ディスクを読み取り専用でマウント**して行われ、 **ゲスト OS 内部には痕跡が残らない可能性がある**とされた。 **ゲスト側をどれだけ堅牢にしても、この経路は塞げない。** 顧客は自分のサーバーを調べても何も見つけられず、 事業者からの通知が唯一の情報源になる
    取るべき行動 ①IaaS・VPS・専用サーバーに置いている資産を一覧にし、 **「基盤が侵害されたら読まれる前提で許容できるか」**で分類する ②許容できない資産（暗号資産の鍵、本番データベースの資格情報、 公開パッケージの発行トークン、長期有効の API キー）を **その環境から外へ出す**計画を立てる ③**リスク登録簿に「基盤事業者の侵害」を独立した項目として立てる。** 「クラウド事業者は信頼できる」で済ませず、 通知の遅れ・範囲の不確実性を含めて評価する
  • ホスティング事業者との契約に「基盤侵害時の通知」を明記する
    本件で FirstVDS は影響を受けたサーバーの所有者に通知し、 **「通知を受け取った場合は全データがコピーされたものと考えるべき」**と指示した。 **顧客に確認の手段が無いため、通知が届くかどうかで対応が決まる。** 通知の義務と期限が契約に無ければ、 **届かないことも、遅れることも、曖昧なまま終わることもある**（本記録の評価）
    取るべき行動 ①ホスティング・IaaS の契約と SLA に **「基盤側（ハイパーバイザ・管理システム）の侵害が判明した場合の 通知の義務・期限・通知先・含めるべき情報」**を含める ②既存契約で定めていない事業者を洗い出し、更新時に交渉する ③**通知を受け取る窓口を、営業担当ではなくセキュリティ部門に向ける。** 会員ページだけに掲載される形だと、気づくのが遅れる
  • 鍵とトークンを「侵害が確認されたら変える」から「期限で必ず変わる」へ移す
    本件のように**ゲスト側で検知できない侵害**では、 「侵害が確認されたら変える」という運用は起動しない。 さらに FirstVDS は顧客に**全パスワード・SSH 鍵・API 鍵・トークンの変更と、 古い鍵の明示的な失効**を求めたが、 **どこで使っているかを把握していなければ失効させた瞬間に連携が壊れる**（本記録の評価）
    取るべき行動 ①鍵・トークンの**一覧と有効期限**を持つ（どこで発行し、どこで使っているか） ②**定期ローテーションを運用に組み込み、期限切れで自動的に無効になる設計**に寄せる ③**緊急時に全部を失効させる手順と所要時間を測っておく。** 「全部の鍵をいま失効させてください」と言われたときに、 何時間かかり何が壊れるかを事前に知っておく
  • 「基盤の脆弱性で、自社のパッチ運用では防げない」場合の判断を決めておく
    本件の原因は自社の設定不備ではなく**調達した製品の脆弱性**であり、 **ベンダーの修正は侵害の後に出ている。** しかも公表時点でも**完全には塞がっておらず追加のパッチが準備中**とされた。 FirstVDS は「問題が完全に解消されるまで管理システムへの外部アクセスは閉じたまま」と 決めている——**修正を待つあいだ露出を絶つという判断である**
    取るべき行動 ①基盤の管理インターフェース（仮想化管理・ストレージ管理・ネットワーク機器・ バックアップ管理）を一覧にし、**それぞれの外部到達性**を記録する ②「ベンダーの修正が未完のあいだ、外部アクセスを閉じる」判断を **誰が・どの基準で下すか**を事前に決める。 閉じたときに**どの運用が止まるか**の対応表も作る ③訓練として、年1回**管理インターフェースを実際に閉じて運用してみる**
  • 1台の侵害が「鍵束の侵害」になっていないか、置き場を点検する
    窃取対象として挙げられたのは、 SSH 鍵・API 鍵・クラウドサービスのトークン・設定ファイル・コマンド履歴である。 報道はさらに AWS・GCP・Azure の認証情報、GitHub・GitLab・npm のトークン、 データベースの接続文字列、バックアップ用パスワードを挙げている。 **並んでいるのはほとんどが「他のシステムへ入るための鍵」**であり、 **VPS 1台の侵害が、その鍵が通じるすべての環境の侵害になる**（本記録の評価）
    取るべき行動 ①**最も管理が緩いサーバー**（検証機・踏み台・古い開発環境）から順に、 置かれている資格情報を実際に探す （環境変数ファイル・SSH 鍵・クラウド CLI の設定・シェル履歴） ②見つかったものを「そこに無くてよいもの」「そこに要るが期限を切れるもの」に分け、 前者を削除、後者を短命化する ③**npm・PyPI などの公開パッケージの発行トークンは、 個人のサーバーに置かせない**——供給網への波及につながる
セキュリティ技術者への示唆
  • ディスク暗号化の鍵をディスクの外に置く構成を検討する
    本件の窃取は、顧客ディスクを**読み取り専用でマウント**して中身を読むものだった。 **ディスク全体が暗号化され、復号鍵がディスク外にあれば、 マウントしても中身は読めない**（本記録の評価）。 攻撃者は稼働中の仮想マシンの中には入っていないため、 メモリ上の鍵には触れていない
    取るべき行動 重要なデータを置く仮想サーバーで LUKS 等のフルディスク暗号化を評価する。 **要点は鍵の供給方法**——鍵をディスク上のファイルに置けば意味がないため、 ①起動時にネットワーク経由で取得（Clevis/Tang 等） ②手動入力 ③基盤が提供する鍵管理（ただし基盤が侵害された場合は無力） のいずれかを選ぶ。 **「再起動時に自動で立ち上がらなくなる」副作用を受け入れられるかが判断の分かれ目**である
  • 秘密情報をファイルシステムに置かず、実行時に取得する構成へ移す
    窃取対象には**設定ファイル・コマンド履歴**が含まれ、 報道はさらに環境変数ファイル・Docker の設定・データベースの接続文字列を挙げている。 **これらはディスクを読むだけで取れる。** プロセスのメモリ上にしか存在しない秘密情報は、本件の手口では取れない
    取るべき行動 ①アプリケーションの秘密情報を環境変数ファイルから **外部のシークレット管理**（Vault・クラウドのシークレットマネージャ）へ移し、 起動時に取得する構成にする ②**シェル履歴に秘密情報が入らないようにする** （環境変数経由での受け渡し、履歴の無効化、`HISTIGNORE` の設定） ③`git` のクレデンシャルヘルパー・クラウド CLI の資格情報キャッシュの 保存先と内容を実際に確認する。 **「どこにも書いていないつもりのトークンが、どこかのキャッシュに平文である」ことが多い**
  • 鍵の「失効」と「再発行」を別の作業として手順に書く
    FirstVDS は顧客に、古い鍵を **「まさに失効させるのであって、単に新しいものを発行するのではない」**と明示した。 **SSH 鍵は `authorized_keys` から削除しなければ失効しない。 API トークンは管理画面で revoke しなければ有効である。** 新しい鍵を作っただけでは、窃取された鍵で入れる状態が続く
    取るべき行動 鍵・トークンの交換手順を**「①新規発行 → ②利用箇所の切り替え → ③旧鍵の失効 → ④失効の確認」**の4段階で書く。 とくに③と④を独立した手順にする。 **SSH は `authorized_keys` の実物を目で見て確認し**、 API トークンは発行側の管理画面で無効化されたことを確かめる。 机上ではなく実機で一度通して、所要時間を記録する
  • 侵害後の点検対象を「SSH 鍵・新規ユーザー・cron・systemd」の4点から始める
    FirstVDS は、攻撃者が窃取データを既に使っている場合に備えて点検すべき箇所として **SSH の `authorized_keys`、新規ユーザー、cron のジョブ、systemd のサービス**を挙げた。 **4つはいずれも「鍵で入った攻撃者が居座るために使う場所」である**（本記録の整理）
    取るべき行動 Linux サーバーの侵害時点検リストを作り、最低限この4点を入れる。 **平時に各項目の「正常な状態」を記録しておく**—— 侵害後に `authorized_keys` を見ても、 元から何行あったかを知らなければ増えたかどうか分からない。 構成管理（Ansible 等）で管理していれば差分で判定できる。 あわせて**10月17日以降のログイン履歴**にあたるもの （`last`・`lastb`・認証ログ）の保持期間を確認する
  • 暗号資産の鍵とシードフレーズを、インターネットに接続したサーバーに置かない
    FirstVDS が顧客への推奨の**第一に挙げた**のは、 潜在的に侵害されたウォレットから**クリーンな端末で新規に作成したウォレットへ 資産を移す**ことだった。 **秘密鍵は「変更」できない**——パスワードや API キーのように差し替えられず、 資産を別の鍵の下へ移すしかない。 報道は窃取対象にウォレットの秘密鍵・**バリデータ鍵**・ **シードフレーズ**が含まれるとしている
    取るべき行動 ①暗号資産の鍵・シードフレーズが VPS・クラウド上のサーバーに 置かれていないかを実際に探す（ウォレットのデータディレクトリ・ 設定ファイル・バックアップ・スナップショット） ②見つかったものは**ハードウェアウォレットまたはオフライン端末へ移す** ③サーバー上での署名が業務上必要な場合は、 **署名だけを行う分離された仕組み**（リモート署名・閾値署名）を検討する。 **「サーバーに秘密鍵を置いたまま守る」方法は本件の手口に対して存在しない**
  • 仮想化ノードからの外向き通信を許可リスト方式で制限する
    窃取プログラムは収集した情報を**攻撃者が管理するサーバーへ送信**していた。 FirstVDS は発見後に攻撃者のサーバーのアドレスを自社ネットワークでブロックしている。 **仮想化ノード自身が外部へ大量にデータを送る必要は通常なく、 「ホストからの未知の宛先への外向き通信」は検知の筋が良い信号である**（本記録の評価）。 自社で基盤を運用している組織に直接当てはまる
    取るべき行動 ①仮想化ノード（ハイパーバイザ）自身の外向き通信を **許可リスト方式で制限する**——ベンダーの更新サーバー・自社の監視系・ ライセンス確認先のみ。顧客 VM のトラフィックとは経路を分ける ②ホストからの外向き通信量と宛先の分布を監視し、未知の宛先でアラートを上げる ③あわせて**仮想化ノード上での顧客ディスクのマウント操作**を監査対象にする。 正規の運用（移行・バックアップ）でも起きるため、 **実行主体とスケジュールの照合**を前提に設計する

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ IaaS・VPS・専用サーバーなど、他社が運用する基盤の上で仮想サーバーを使っている本件の窃取は**ハイパーバイザ側から顧客ディスクを読み取り専用でマウント**して行われ、 **ゲスト OS 内部には痕跡が残らない可能性がある**とされた。 **ゲスト側の対策では塞げない経路であり、自力での侵害判定もできない**
データの保持□ 仮想サーバーのファイルシステムに、他のシステムへ入るための資格情報 （SSH 鍵・クラウドの認証情報・API トークン・データベース接続文字列・ バックアップ用パスワード・暗号資産の鍵）を平文で置いている窃取対象として挙げられたのはほとんどが**他のシステムへの鍵**である。 **1台の侵害が、その鍵が通じるすべての環境の侵害になる。** 暗号資産の秘密鍵・シードフレーズは**失効させられない**
運用・監視□ 鍵・トークンの一覧と有効期限を持っておらず、 「全部を失効させる」作業にどれだけかかり何が壊れるかを把握していないFirstVDS は顧客に**全パスワード・SSH 鍵・API 鍵・トークンの変更と、 古い鍵の明示的な失効**を求めた。 **どこで使っているかを把握していなければ、失効させた瞬間に想定外の連携が壊れる**
委託・第三者部品□ ホスティング事業者・IaaS 事業者との契約に、 **基盤側の侵害が判明した場合の通知の義務・期限**が定められていない顧客側に確認の手段が無いため、**事業者からの通知が唯一の情報源**になる。 FirstVDS は「通知を受け取った場合は全データがコピーされたものと考えるべき」としている
システム構成□ 自社で仮想化基盤を運用しており、 仮想化管理システム（VMmanager・vCenter・Proxmox・OpenStack 等）の 管理インターフェースが外部から到達可能である本件の侵入経路は**外部からアクセスできた仮想化管理システムの脆弱性**であり、 FirstVDS は対応として「外部アクセスを遮断した」と述べている。 **管理システムが落ちれば、その配下の全ゲストのディスクが読める**
運用・監視□ 仮想化ノード（ハイパーバイザ）上の実行監視・外向き通信の制限・ 顧客ディスクのマウント操作の監査を行っていない本件では**仮想化ノード上で未知のプログラムが起動し、ディスクをマウントし、 外部へ送信する**という一連の動作が検知されていない。 仮想化ノードは稼働ソフトが限られるため、許可リスト方式の制御が現実的である
体制・契約□ 基盤製品の脆弱性に対し、「ベンダーの修正が未完のあいだ外部アクセスを閉じる」判断を 誰がどの基準で下すかが決まっていない本件はベンダーの修正が**侵害の後**に出ており、公表時点でも完全には塞がっていない。 FirstVDS は「完全に解消されるまで閉じたまま」と決めている—— **自社の運用の不便を引き受ける判断が要る**
