INC-2026-0610Rank Math PRO 配布に混入

WordPress の SEO プラグイン「Rank Math PRO」の公式配布が侵害され、2026年10月15日20時02分（UTC）から16日07時12分（UTC）までの約11時間に rankmath.com からダウンロードまたは更新で配布された v3.0.123 にマルウェアが混入していた——有効化したサイトは侵害されたものとして扱うべきとされ、マルウェアはページが閲覧されるたびに隠しバックドアを再生成し、rank1cdn[.]com と通信してDB認証情報やAPIキーを露出させる

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因公表されていない／不明
初報: 2026年10月16日 最終更新: 2026年10月19日

WordPress の SEO プラグイン「Rank Math」の有料版 Rank Math PRO の公式配布が侵害された。提供元の通知によれば、2026年10月15日20時02分（UTC）から10月16日07時12分（UTC）までの間にrankmath.com からダウンロードされた、または更新として配布された v3.0.123 のファイルにマルウェアが混入していた。約11時間の窓である。同社は該当ファイルを直ちに削除し、クリーンな v3.0.124 を公開した。

この期間に導入して有効化したサイトは、侵害されたものとして扱うべきとされている。マルウェアは永続的なアクセスを確立し、ページが閲覧されるたびに隠しバックドアを再生成する。通信先は rank1cdn[.]com。Webサーバーから到達できるデータベース認証情報・APIキー・その他の秘密情報が露出するとされ、偽のコアファイル wp-includes/class-wp-cache-util.php の設置、.cache ファイルをPHPとして実行させる .htaccess の改変、cron の登録、wpsupport_ で始まる管理者アカウントの作成といった痕跡が示されている。

WordPress.org で配布されている無料版 Rank Math SEO は影響を受けていない（無料版は400万サイト以上で稼働している）。

本記録の読みどころは3点ある。第一に、「更新したら直った」が成立しないことである。同社は、侵害後にプラグインを無効化または更新しても脅威は除去されないと明記している。第二に、窓が11時間であり、自動更新を有効にしたサイトは「何もしていないのに」この窓に入り得る。第三に、復旧の手順が WordPress の外側まで及ぶ——SSHの authorized_keys、他ユーザーの crontab、Webサーバー利用者が書き込める場所まで確認対象に含まれている。

通知は、導入の状況によって対応を3つに分けている。

状況 示された扱い

重要なのは、有効化後にプラグインを無効化または更新しても脅威は除去されないと明記されている点である。マルウェアはプラグインの外側に痕跡を作るため、プラグインを新しくしても残る。

公表されたマルウェアの挙動は次のとおりである。

  • 永続的なアクセスを確立する
  • ページが閲覧されるたびに隠しバックドアを再生成する
  • rank1cdn[.]com と通信する
  • Webサーバーから到達できるデータベース認証情報・APIキー・その他の秘密情報を露出させる
  • 偽のコアファイル wp-includes/class-wp-cache-util.php を設置する
  • .cache ファイルをPHPとして実行させる .htaccess のルールを加える
  • cron／スケジュールされたタスクを登録する
  • 他のプラグインやテーマを改変し、別のファイルをアップロードする
  • WordPress の外側にも変更を加え得る

痕跡は固有の文字列として公表され、第三者の検体でも同じものが確認された原因・手口出典 [1] [2]

通知が示した痕跡（IoC）は次のとおりである。

  • base64_decode と XOR ループを組み合わせたPHPコード、XOR鍵 xmmqhn、proc_open、PHP-FPM ソケット関連のコード
  • wp_options の不正なエントリ — _uf6qdn2hmm、t8krdk990phb、_np5pvf754c
  • システムの crontab 内の目印 — #ms6v46
  • 不正な管理者アカウント — wpsupport_ で始まるユーザー名（後に乱数が続く）、または @wp-mail[.]net で終わるメールアドレス
  • 偽のコアファイル — wp-includes/class-wp-cache-util.php
  • C2ドメイン — rank1cdn[.]com（発信接続の遮断が推奨されている）

BleepingComputer は VirusTotal 上で cache-preloader-fff033 (1).php という PHP 検体を見つけ、上記のうち XOR鍵・_np5pvf754c・#ms6v46・wpsupport_ と @wp-mail.net を使う管理者アカウント作成という同じ痕跡を含んでいたと報告した。同検体は wp-includes/class-wp-cache-util.php のバックドアを作る第1段階の展開スクリプトとみられ、コマンドの実行、WordPress データベースの改変、AWS・Cloudflare・Google Cloud・Azure の認証情報、SSH鍵などの窃取の機能を含むとしている。ただし、同検体が侵害されたプラグインを通じて配布されたかは確認できなかったとされる。

本記録は、これらの痕跡が悪性であることを独自に検証していない。 提供元が公表したIoC と報道の内容をそのまま記録したものである。

  • すべてのパスワードと認証情報を変更する（復元した場合でも必須とされている）

選択肢2：手動でのクリーンアップ（段階は通知の区分に沿う）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
影響バージョンと期間（分単位・UTC）、無料版が対象外であること、導入状況別の扱い、IoC、 段階別のクリーンアップ手順と検証方法を1つの通知に載せた。侵入経路と影響サイト数は示さなかった部分的に機能本記録の作成者の評価である。影響期間を**分単位のUTCで示した**ことと、 IoC を固有の文字列（XOR鍵・DBエントリ名・cron の目印・管理者アカウントの命名規則）まで 下ろしたことは、利用者が自分のサイトを判定するうえで実用的である。 一方、**混入版のハッシュが無い**ため、更新時刻の記録が無い環境では判定の手段が限られる。 侵入経路が示されていない点も、同じ配布形態を取る他の提供元が学べない形になっている
「無効化または更新では脅威は除去されない」と明記し、有効化したサイトは 侵害されたものとして扱うよう求めた機能した本記録の作成者の評価である。供給元の事故では「最新版に上げてください」で済ませる案内が 起こりがちだが、本件は再生成する永続化を伴うため更新では足りない。 その点を最初に明示し、復旧をサーバー全体（SSH鍵・他ユーザーの crontab・プロセス）まで 広げた案内は、事象の性質に合っている
クリーンなバックアップから復元した場合でも、すべてのパスワード・DB認証情報・ wp-config.php のキーとソルト・APIキー・決済／SMTP情報・ホスティングと FTP/SFTP/SSH の 認証情報を変更することを必須とした機能した本記録の作成者の評価である。復元は「ファイルと中身を戻す」だけで、 窓の間に露出した秘密情報は戻らない。この区別を手順に書き込んでいる点は適切である
CISO・経営層への示唆
  • 「公式サイトからの更新」を無条件に信頼する前提を、台帳の上で見直す
    本件はマーケットプレイスでも第三者サイトでもなく、提供元の公式配布と更新経路で マルウェアが配られた。利用者側の操作に誤りは無い
    取るべき行動 公開サイトで使っているプラグイン・テーマ・ライブラリを台帳化し、 1件ごとに「更新の適用方法（自動／検証後）」「提供元のハッシュ・署名の有無」を記録する。 署名や照合手段が無い有料コンポーネントは、採用・継続の判断材料として扱う
  • 供給元の事故では「該当したか」を即座に答えられる記録を持つ
    本件の影響期間は11時間10分と短い。更新の適用時刻が残っていれば該当の有無は確定するが、 ハッシュは公表されていないため記録が無いと判定できない
    取るべき行動 更新作業（適用日時・バージョン・取得元・適用者）を自動で記録する仕組みを入れ、 供給元の事故公表時に照合する手順を決める。照合の責任者と期限（例: 公表から24時間）も決める
  • 公開サイトの侵害を「サイトの復旧」ではなく「サーバーの復旧」として設計する
    提供元の手順は、SSHの authorized_keys、他のシステム利用者の crontab、実行中のプロセス、 Webサーバー利用者が書き込めるすべての場所の確認まで求めている
    取るべき行動 公開サイトが侵害された場合の復旧手順に、サーバー・ホスティング・クラウドの認証情報の 変更と、OS側の永続化（SSH鍵・cron・サービス）の確認を含める。 復旧の完了判定を「サイトが表示される」ではなく「検証項目をすべて満たす」に置く
  • 公開サイトから到達できる秘密情報の棚卸しを、事故が起きる前に済ませる
    本件で露出し得るとされたのは、DB認証情報・APIキー・Webサーバーから到達できる秘密情報である。 第三者が発見した検体にはクラウドの認証情報とSSH鍵の窃取機能が含まれていたとされる
    取るべき行動 Webサーバーの実行利用者が読める秘密情報を一覧化し、長期の認証情報を短期の資格情報に 置き換える。決済・SMTP・クラウドのキーは影響範囲を限定した権限で発行し直す
セキュリティ技術者への示唆
  • 本番の自動更新を止め、検証環境を経た適用に変える
    混入の窓は11時間10分で、自動更新が有効なサイトは操作なしにこの窓へ入り得る
    取るべき行動 プラグイン・テーマの自動更新を本番で無効にし、検証環境で導入して差分と動作を確認してから 適用する流れにする。緊急の脆弱性修正だけは例外として扱う基準を決めておく
  • コアとプラグインのチェックサム検証を定期実行する
    本件の痕跡には偽のコアファイル `wp-includes/class-wp-cache-util.php` が含まれる。 `wp core verify-checksums` で検出できる種類の変化である
    取るべき行動 コアのチェックサム検証とファイル改ざん検知を日次で回し、差分を警告する。 有料プラグインでチェックサムが使えない場合は、導入時に取得した正規コピーを保管して比較できるようにする
  • Webサーバーの実行利用者に、コアとプラグイン配下への書き込み権限を与えない
    マルウェアは偽のコアファイルの設置、他プラグイン・テーマの改変、`.htaccess` の改変、 `uploads/` へのPHPファイルの設置を行うとされる
    取るべき行動 ファイル所有者と実行利用者を分離し、書き込みが必要な場所（uploads 等）を限定する。 uploads 配下と `.cache` のようなファイルでのPHP実行を禁止し、`.htaccess` の変更を監視する
  • Webサーバーからの発信通信を限定し、DNSと接続の記録を残す
    マルウェアは rank1cdn[.]com と通信し、提供元は同ドメインへの発信接続の遮断を推奨している
    取るべき行動 Webサーバーからの発信先を必要な宛先に限定し、未知の宛先への接続を遮断・記録する。 DNSの問い合わせ記録を保存し、公表された IoC と突き合わせられるようにする
  • 管理者アカウントの作成と cron の登録を、即時に気づける変化として監視する
    本件では `wpsupport_` で始まる管理者アカウントの作成と、`#ms6v46` を目印とする cron の登録が痕跡として示された
    取るべき行動 管理者権限のアカウント作成・権限変更を通知し、`wp user list --role=administrator` と `wp cron event list` の結果を定期的に取得して差分を確認する
