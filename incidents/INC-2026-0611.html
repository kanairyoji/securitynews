INC-2026-0611Zeabur 再侵入、環境変数321万件

台湾のデプロイ基盤 Zeabur が8月の侵害から約1か月半で**同じ種類の認証情報を使って再び侵入され**、 プラットフォームのデータベースから**環境変数 3,218,965 件・アカウント 321,810 件**を読み取られた—— 入口は2本で、一方は**2024年1月に作られ期限もローテーションも無かった共有クラスタの管理トークン**（設定リポジトリに平文）、 他方は**初期化設定に平文で置かれていた root パスワード**で GCP 専用サーバ 101 台（利用者92名）に root ログインされた。 2本は内部ネットワークで合流し、**読み取り専用アカウントでの37分間**にデータベース全体が読まれた。 8月の事案の対応で「内部の管理者キーはすべて無効化またはローテーション済み」としていたが、 **平文のクラスタ管理トークンと AWS キーはその対象から漏れており、 GCP の平文 root パスワードは9月3日に判明していたのに事件まで直されていなかった**。 最初の不正な認証情報の利用から調査開始まで**約36時間、警報は一度も鳴らず**、端緒は利用者からの報告だった。 同社は10月17日に**年末での営業終了**を公表し、12月1日から順次停止、12月31日に全停止する

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）設定不備権限管理の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）

Zeabur（台湾のアプリケーションデプロイ基盤）は2026年10月19日、2026年10月14日（UTC）に発生した侵害の予備調査報告を公表しました。読み取られたのは環境変数 3,218,965 件・アカウント 321,810 件で、2026年8月末の事案（[[INC-2026-0069]]）より範囲が広いと同社は述べています。

本件の記録として重いのは、件数ではなく同じ鍵が二度効いたことです（本記録の評価）。

  • 入口は2本あった。一方は共有クラスタの管理トークン——2024年1月に作られ、有効期限が無く、一度もローテーションされず、設定リポジトリに平文で置かれていた。管理インターフェースはインターネットから到達できた。他方はGCP 専用サーバの初期化設定に平文で入っていた root パスワードで、攻撃者はそれを読める旧 GCP キーを持っていた。
  • 2本は内部ネットワークで合流した。 1本目で得た内部ネットワークの管理認証情報を使い、侵害した GCP サーバから内部ネットワークへ入り、読み取り専用アカウントでプラットフォームのデータベースを読んだ。所要は37分（10月15日16時10分〜16時47分 UTC）。
  • 8月の是正は漏れていた。 8月の事案のあと同社は流出が確認された内部キーをローテーションし Legacy API Key を停止したが、設定リポジトリに平文で残っていたクラスタ管理トークンと AWS キーはその対象外だった。 GCP の平文 root パスワードは9月3日に判明していたが、事件まで直されていなかった。 今回使われたのは、まさにこれらの認証情報である。
  • 約36時間、警報は鳴らなかった。最初の不正な内部認証情報の使用（10月14日1時36分 UTC）から調査の開始（10月15日13時56分 UTC）まで約36時間。正規の経路と有効な認証情報を使っていたため検知されず、端緒は利用者からの報告だった。

同社は2026年10月17日、年末での営業終了を公表しました。一部サービスは12月1日から順次停止し、専用サーバと共有クラスタは12月31日までに全停止します。創業者の林沅霖（Yuanlin Lin）氏は終了の理由として、成長の壁・システムの複雑化に加えて「2026年下半期の2件のセキュリティインシデントでセキュリティと運用の不備が明らかになった」ことを挙げています。

読者にとっての含意は、侵害そのものより「鍵の棚卸しの完了をどう確認するか」にあります（本記録の評価）。8月の対応は「流出が確認された鍵」を対象にしており、「平文でどこかに置かれている鍵」の全量は対象になっていませんでした。この2つは別の集合です。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は手口が時刻単位で公表されている珍しい事案である**（本記録の整理）。 **以下、各段階の経緯は Zeabur の予備調査報告に基づく事実であり、 検知の機会と対策についての注記は本記録の評価である。**

  1. 1. 初期侵入[1] [2]
    **攻撃者は Zeabur 内部の AWS キー（10月14日1時36分 UTC が最初の使用）と 共有クラスタの管理トークン（1時40分）を使って外部から侵入した。** **管理トークンは2024年1月に作成され、有効期限が無く、 一度もローテーションされず、設定リポジトリに平文で保存されていた。** **共有クラスタの管理インターフェースは当時インターネットから到達可能で、 これにより9つのリージョンの共有クラスタへ外部から到達できた。** **並行して、攻撃者が持っていた旧 GCP キーで 専用サーバの初期化設定にある平文の root パスワードを読み取り、 10月14日13時40分に101台へ root でサインインした（利用者92名）。** **これらの認証情報を攻撃者が最初にどう入手したかは公表されていない。**
  2. 2. 権限昇格[1]
    **経路Aで、攻撃者は権限が過大だった別のキーを使って旧クラスタのバックアップを読み、 シークレット管理サービスへのアクセス能力を得た**（Zeabur の判断）。 **その結果、10月15日14時52分〜16時51分に本番環境のシークレット約53件を読み取った** ——**内部ネットワークの管理認証情報、プラットフォームデータベースのアカウント、 GitHub App の秘密鍵を含む。** **Zeabur は根本原因として「クラスタのバックアップに全シークレットが含まれ、 そのアクセスキーも同じ環境に置かれていた」「権限が過大だった （1つのバケットだけで足りる鍵が全バケットを読めた）」を挙げている。**
  3. 3. 横展開[1] [2]
    **2本の経路が合流した。** **10月15日15時30分、攻撃者は経路Aで得た内部ネットワークの管理認証情報を使い、 侵害した GCP 専用サーバから内部ネットワークへノードを追加した。** **Zeabur は根本原因として「内部のサービスと利用者のサービスが 同じクラスタで動いていた」ことを挙げている。** **あわせて専用サーバ50台に攻撃者自身の SSH 鍵が追加され（10月15日14時26分〜）、 仮想マシン5台が作成され、利用者サーバのディスク複製16枚が接続された。**
  4. 4. 持ち出し[1] [2] [5]
    **10月15日16時10分から16時47分（UTC）までの37分間、 攻撃者は内部の読み取り専用アカウントでプラットフォームのデータベースを読み取った。** **読み取られたのは——環境変数 3,218,965 件、アカウント 321,810 件 （メールアドレス・ユーザー名・電話番号など）、 zSend API キー 566 件（平文）、 プラットフォームのアクセストークン 11,536 件（ハッシュのみ保存）。** **これに先立ち、10月14日13時40分〜17時04分に 利用者のデータベースコンテナ865件でコマンドが実行されたが、 Zeabur は「出力内容の記録が無く、全体の流出量は確定できない」としている。**

**予備調査報告（10月19日）で、時刻単位の経緯・件数の確定値・ 根本原因6点・8月の対応の不完全さ・約36時間警報が鳴らなかったことを公表した。** **「認証情報のローテーションとセキュリティの改善を完全に実施できなかった責任は当社にある」 と明記した**（原文英語）。機能した**本記録の評価である。** **評価の根拠は3点。** ①**件数を概数ではなく確定値（3,218,965／321,810／11,536／566）で出している** ——**利用者が「自分が含まれるか」ではなく「全量を交換する」判断に進める形になっている。** ②**8月の報告の記述が不完全だったことを自ら訂正している** ——**先行報告の誤りを後から正す記録はまれである。** ③**「出力内容の記録が無く流出量を確定できない」という 測れなかった部分を測れなかったと書いている**（865件のデータベースサービス）。 **留保**——**攻撃者の初期侵入経路が未確定であり、 また事業終了が同時に決まっているため、 最終報告が出るかは本記録として保証できない**（status を updating とした理由）。
**2026年10月17日、年末での営業終了を決定・公表した。** **即時に専用サーバとドメインの新規購入を停止、 12月1日に専用サーバの更新停止と共有クラスタの稼働サービス一時停止、 12月31日に全停止。** **終了の理由の1つとして「2026年下半期の2件のセキュリティインシデントで セキュリティと運用の不備が明らかになった」ことを挙げた。** **残高の返金とインシデントによる損失の補償は別々の申請とし、 いずれもサポートを窓口とした。**部分的に機能**本記録の評価である。** **「直せないものを抱えて続けない」という判断自体は、 利用者の長期的な安全という観点では筋が通る**（本記録の考え）。 **部分的と評価する理由は、移行に必要な期限が告知の時点で 3つとも未確定だったことである。** **利用者は「インシデント対応としての全シークレット交換と GCP 専用サーバの再構築」と 「期限不明のままの全データ退避と移行先選定」を同時に負う。** **さらに両方の窓口が同じサポートであり、 告知自身が問い合わせ増による返信遅延を予告している。** **一般論として、事業終了を伴うインシデントでは 「いつまでに何ができなくなるか」を金額や原因の説明より先に 確定させる必要がある**（本記録の提言）。
CISO・経営層への示唆
  • インシデント後の鍵の是正は「流出が確認された鍵」ではなく「平文で置かれている鍵の全量」を対象にする
    **本件で使われた3つの認証情報は、いずれも8月の事案の是正対象から漏れていた**（事実）。 **8月の対応は「流出が確認された内部キーのローテーション」と 「Legacy API Key の停止」で、 設定リポジトリに平文で残っていたクラスタ管理トークンと AWS キーは対象外だった。** **Zeabur は8月の報告の「すべての内部管理者キーは無効化またはローテーション済み」 という記述が不完全だったと今回訂正している。** **2つの集合は別物である**（本記録の整理）—— **「流出が確認された鍵」は事案から導けるが、 「平文で置かれている鍵」は棚卸しからしか出てこない。**
    取るべき行動 **インシデント後の是正を終える条件に、 「設定リポジトリ・サーバの初期化設定・バックアップ・CI の変数に 平文で置かれているシークレットの全量走査を完了したこと」を入れる。** **走査の結果を件数で記録し、 「ローテーション済み」と公表・報告する前にその件数が0であることを確認する。** **走査していない領域がある場合は、 報告に「この領域は走査していない」と書く** ——**本件の訂正は、書かなかったことから起きている。**
  • 自分で見つけた不備に修理期限を付け、期限超過を経営の視界に上げる
    **GCP 専用サーバの初期化設定に root パスワードが平文で入っていることを、 Zeabur は2026年9月3日に把握していた**（事実）。 **しかし10月14日の事件まで修正されていない。** **攻撃者が101台に root ログインしたのは、まさにこの平文パスワードである。** **検知の失敗ではなく、把握から修理までの間に攻撃が来た事案である**（本記録の評価）。
    取るべき行動 **自社で発見した構成上の不備に、発見日と修理期限を付けて台帳に載せる。** **期限を超えたものは件数と最古の滞留日数を月次で経営に報告する** ——**「見つかっている未修理」は、脆弱性スキャンの結果と同じ重みで扱う。** **とくに「平文で置かれた認証情報」は、 発見から修理までの期間がそのまま侵害の窓になるため、 他の指摘より短い期限（例: 発見から7日）を設定する。**
  • 共通基盤を使う側は「基盤側の侵害は自社の監視では見えない」を前提に、鍵の交換手順を平時に用意する
    **本件で利用者に求められたのは、環境変数内の全シークレットの交換、 アクセストークンの再発行、共有クラスタ利用者はデータベース内のパスワード変更と n8n 暗号化キーの再生成、GCP 専用サーバ利用者はサーバの再構築である**（事実）。 **しかも865件のデータベースについては 「出力の記録が無く流出量を確定できない」ため、 読まれた前提で動くしかない**（事実）。 **基盤側が件数を確定値で出しても、 利用者側に「どの鍵をどこに置いたか」の一覧が無ければ交換は進まない**（本記録の評価）。
    取るべき行動 **外部基盤に預けている環境変数・シークレットの一覧を、 基盤ごとに作って維持する（どの鍵がどの第三者サービスのものか、 交換の手順と所要時間、交換時に止まる業務）。** **「基盤側から侵害の連絡が来た翌営業日までに全件交換を開始できるか」を 机上で確認し、できない部分（手作業での交換が必要なもの）を先に減らす。**
  • 事業終了を伴うインシデントでは、金額の説明より先に「いつまでに何ができなくなるか」を確定させる
    **Zeabur は10月17日の告知で、 データ削除日・最終エクスポート期限・サポート終了日の3つを いずれも未確定としたまま、12月1日からの段階停止と12月31日の全停止を示した**（事実）。 **利用者は、インシデント対応（全シークレット交換・サーバ再構築）と 期限不明のままのデータ退避を同時に負う**（本記録の評価）。 **返金と補償はいずれもサポート窓口であり、 告知自身が問い合わせ増による返信遅延を予告している**（事実）。
    取るべき行動 **自社がサービス提供者である場合、 事業終了・サービス廃止の告知の雛形に 「データの読み出しが止まる日」「削除される日」「問い合わせ窓口が閉じる日」の 3つを必須項目として入れる。** **自社が利用者である場合、 重要な外部基盤について「提供者が60日後に停止したら何が失われるか」を 年1回棚卸しし、エクスポート手順を実際に1回動かしておく。**
セキュリティ技術者への示唆
  • 管理者トークンの有効期限は棚卸しではなく発行時の制約で担保する
    **本件の共有クラスタ管理トークンは2024年1月に作成され、 有効期限が無く、一度もローテーションされず、 2026年10月まで有効だった**（事実）。 **8月の是正の棚卸しでは見落とされている**（事実）。 **棚卸しは人が行う作業であり、見落としが残る**（本記録の評価）。 **一方、期限が付いていれば見落としても時間が解決する。**
    取るべき行動 **管理者権限のトークン・鍵の発行経路を、 期限の設定を必須とする仕組み（発行 API の必須パラメータ、 IaC のバリデーション、ポリシーエンジン）に通す。** **既存の無期限トークンを棚卸しし、 「残っている無期限トークンの本数」をダッシュボードに出して0を目標にする。** **期限の更新が自動化できない経路は、その経路自体を廃止する候補として扱う。**
  • 管理面（クラスタ管理 API・コンソール）をインターネットから切り離す
    **Zeabur は根本原因として 「共有クラスタの管理インターフェースがインターネットから到達可能だった」ことを 自ら挙げている**（事実）。 **トークンが平文で漏れていても、 管理面に到達できなければ9つのリージョンの共有クラスタを 外部から操作することはできなかった**（本記録の評価）。 **認証情報の漏えいと到達可能性は独立した条件であり、 片方を潰せば侵害は成立しない。**
    取るべき行動 **クラスタ管理 API・管理コンソール・内部管理用のエンドポイントを 公網から外し、要塞ホスト・VPN・プライベートエンドポイント経由に限定する。** **「公網に出ている管理面」の一覧を外部スキャンで定期に取得し、 想定外のものが出ていないかを確認する** ——**自社の構成図ではなく外からの観測で確認する。**
  • バックアップをシークレットの集積として扱い、復号鍵を同じ環境に置かない
    **本件では、権限が過大な鍵で旧クラスタのバックアップを読んだことが シークレット管理サービスへの到達につながり、 本番シークレット約53件（内部網の管理認証情報・GitHub App の秘密鍵）が読まれた**（事実）。 **Zeabur は根本原因として 「クラスタのバックアップに全シークレットが含まれ、 そのアクセスキーも同じ環境に置かれていた」と述べている**（事実）。 **バックアップは可用性の道具として扱われやすく、 機密の集積としての監視が薄くなりがちである**（本記録の評価）。
    取るべき行動 **バックアップに含まれるシークレットを棚卸しし、 復号鍵・アクセスキーを被保護対象とは別の権限境界（別アカウント・別プロジェクト）に移す。** **バックアップ用ストレージへの読み取りアクセスを監査ログの監視対象に加え、 通常の取得頻度から外れた読み取りを警報にする。** **ストレージのアクセスキーの権限は、 対象バケット単位まで絞ったうえで定期に差分を検査する。**
  • 中核データベースの読み取りは「誰が」ではなく「どれだけ」で監視する
    **本件の最大の持ち出しは、権限昇格を伴わず、 内部の読み取り専用アカウントで37分間に行われた**（事実）。 **新規ユーザーの作成も、権限の変更も、設定の変更も起きていない。** **約36時間にわたり警報は一度も鳴らず、端緒は利用者からの報告だった**（事実）。 **有効な認証情報と正規の経路を使う相手には、 「誰が入ったか」を見る監視は効かない**（本記録の評価）。
    取るべき行動 **プラットフォームの中核データベース（利用者の環境変数・認証情報を保持するもの）への 読み取りについて、単位時間あたりの件数の正常範囲を実測して定義し、 超過を警報にする。読み取り専用アカウントも対象に含める。** **あわせて、利用者のコンテナ・データベースに対する 内部からのコマンド実行を出力まで含めて記録する** ——**本件では実行の記録はあったが出力が残っておらず、 流出量を確定できていない。**
  • 預かった環境変数を中核データベースから復号可能な形で読めないようにする
    **本件の被害の中心は環境変数 3,218,965 件であり、 これが1つのデータベースから読める構造だったことが爆発半径を決めた**（本記録の評価）。 **同じデータベース内で、zSend API キー566件は平文、 アクセストークン11,536件はハッシュ保存であり、 保存方式が揃っていなかった**（事実）。 **ハッシュであれば読まれても直ちには使えないが、 環境変数はデプロイ時に平文で必要なため同じ方式は取れない。** **だからこそ鍵の置き場所を分ける設計が要る。**
    取るべき行動 **利用者から預かるシークレットを、 基盤の業務データベースではなく専用のシークレットストアに置き、 復号はデプロイ時の限定された経路でのみ行う。** **業務データベースから復号可能な状態で読めないことを、 実際に「DB のダンプから鍵が復元できるか」を試して確認する。** **保存方式が項目ごとに揃っているかを一覧で点検する** ——**本件では平文とハッシュが同居していた。**
