INC-2026-0612OVHcloud 公式CLI に窃取型マルウェア

OVHcloud の公式コマンドラインツール（ovhcloud-cli）の**すでに公開済みだった5つのリリースの配布物が、 2026年10月19日の約25分間（12時47分〜13時12分 UTC）に窃取型マルウェアへ差し替えられた**—— 新しいタグもビルドも作られず、**GitHub の Releases API で既存リリースのファイルだけが上書きされ、 同じ場所にある `checksums.txt` も一緒に差し替えられた**ため、リリース内のハッシュ照合は無効化された。 **公式の `install.sh` はハッシュを検証していない。** 気づいたのは**CI に SHA-256 を直書きしていた利用者**で、ビルドが落ちたことから約1時間後に Issue が立ち、 差し替えファイルは**14時21分 UTC に削除**された（差し替え開始からの経過は94分）。 創業者 Octave Klaba 氏は**開発者の GitHub アカウントが使われた**と述べたが、 アカウントがどう侵害されたかは公表されていない。 **ソースリポジトリは改変されておらず**、`go install`・ソースからのビルド・公式 Docker イメージは影響を受けない。 第三者の調査では、**アップロードに使われたアカウントの個人リポジトリが2026年3月に侵害されていた**こと、 そこに置かれたローダーが**9,123 個の不可視 Unicode 文字**に隠され、 **次段の取得先を Solana ブロックチェーンの memo から読む**構造だったことが示されている

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備設計・実装上の不備

OVHcloud（フランスのクラウド事業者）の公式コマンドラインツール ovhcloud-cli で、すでに公開済みだったリリースの配布ファイルが窃取型マルウェアへ差し替えられました。創業者の Octave Klaba 氏が2026年10月19日に X で公表し、影響バージョンは v0.11.0 から v0.15.0 までの5本としています。

本件が通常のサプライチェーン攻撃と違うのは、何も「作られていない」点です（本記録の評価）。

  • 新しいバージョンもタグも作られていない。 GitHub Actions も走っていない。
  • ソースリポジトリは改変されていない。
  • 行われたのは、GitHub の Releases API を使った「既存リリースの添付ファイルの上書き」だけである。

差し替えの時間帯は約25分（2026年10月19日 12時47分〜13時12分 UTC）。対象は macOS（arm64／x86_64）・Linux（arm64／x86_64）・Windows x86_64 のバイナリと、同じリリースに置かれていた checksums.txt です。ハッシュの一覧がアーカイブと一緒に差し替えられたため、リリース内で突き合わせる検証は意味を失いました。 公式の install.sh は、そもそもハッシュを検証していません。

止めたのは、ハッシュをリリースの外に持っていた側でした（事実）。

  • CI に v0.15.0（Linux_arm64）の SHA-256 を直書きしていた利用者のビルドが落ち、約1時間後に Issue #300 が立った。この利用者はハッシュを機械的に更新せず、バイナリのビルド情報を確認した ——正規版は v0.15.0・vcs.modified=false なのに、差し替え版は v0.15.1-…+dirty・vcs.modified=true だった。
  • Homebrew の cask のハッシュは9月16日以降変更されておらず、差し替えアーカイブは brew 側で弾かれたはずである（第三者の調査による推測）。

差し替えファイルは 14時21分 UTC に削除され（差し替え開始からの経過は94分）、その後クリーンな v0.16.0 が公開されました。

攻撃の背景については、第三者の調査のほうが先に進んでいます（本記録の整理）。アップロードに使われた GitHub アカウントは2026年3月に侵害されていたとみられ、その個人リポジトリに残されたローダーは9,304 文字中 9,123 文字が不可視の Unicode 文字（variation selector）で、次段の取得先を Solana ブロックチェーンの memo 欄から読む構造でした。ただしこれらは独立した研究者の調査結果であり、OVHcloud は裏付けも否定もしていません。

読者が自組織に持ち帰るべき点は1つです（本記録の提言）—— ハッシュを、検証したい対象と同じ場所に置かない。本件で生き残ったのは、ハッシュを別の場所（自社の CI、別リポジトリの cask）に持っていた経路だけでした。

ハッシュの一覧が、検証したい対象と同じリリースに置かれていた原因・手口

本記録が本件の核心と見るのは、鍵でも権限でもなく、ハッシュの置き場所である（本記録の評価）。

攻撃者がしたことは、既存リリースの添付ファイルの上書きだけである（事実）。

  • 新しいバージョンもタグも作られていない
  • GitHub Actions も走っていない
  • ソースリポジトリは改変されていない
  • 使われたのは通常の GitHub Releases API

そして、同じリリースに置かれていた checksums.txt も一緒に差し替えられた（事実）。つまり「リリースページのハッシュと照合する」という手順は、本件では攻撃者が両方を書き換えられるため無効だった。

さらに公式の install.sh は、そもそもハッシュを検証していない（第三者が sha256・shasum・hash の該当が0であることを確認）。curl … | sh でインストールした利用者には、検証の機会が無かった。

止まった経路は2つだけである（事実）。

経路 ハッシュの置き場所 結果
利用者の CI（SHA-256 直書き） 自社のリポジトリ ビルドが落ちて検知
Homebrew cask ovh/homebrew-tap（別リポジトリ） 9月16日以降ハッシュ未変更＝弾かれたはず（第三者の推測）
install.sh 検証しない 通る
GitHub Releases から直接 同じリリースの checksums.txt 通る（両方差し替え済み）

一般論として言えることは短い（本記録の提言）—— 検証に使うハッシュは、検証したい対象と同じ場所に置いてはならない。 同じ場所にあるハッシュは「配布物が壊れていないこと」しか示さず、「配布物が差し替えられていないこと」は示さない。 この2つは別の性質である。

気づいたのは、ハッシュを機械的に更新しなかった利用者だった発覚の端緒

検知の経緯は、本件で最も学べる部分である（本記録の評価）。

CI に v0.15.0（Linux_arm64）の SHA-256 を直書きしていた利用者のビルドが、差し替えから約1時間後に落ちた（事実）。ハッシュは 5c2beb56… から 3833daff… に変わっていた。

ここで分岐がある（本記録の整理）。

  • ハッシュを新しい値に書き換えてビルドを通す —— これは実務でよく行われる。「公式が更新したのだろう」という解釈が自然だからである。 この選択をすれば、マルウェアは CI を通って本番環境に入る。
  • なぜ変わったのかを確認する —— この利用者が取ったのはこちらだった。

確認の結果、バイナリのビルド情報に差があった（事実）。

正規の v0.15.0 差し替え版
バージョン表記 v0.15.0 v0.15.1-…+dirty（疑似バージョン）
vcs.modified false true
ビルド元 タグのコミット（760fd72d） コミット 5ead8ef9b43d からのローカルビルドと疑われる

+dirty と vcs.modified=true は、未コミットの変更を含むローカルビルドであることを示す。 公式のリリースビルドにこれが出ることはない。

読者が持ち帰るべき点は2つである（本記録の提言）。

  • 固定したハッシュが変わったとき、それ自体を事象として扱う。 「更新されたから合わせる」ではなく、「なぜ公開済みのバージョンのハッシュが変わったのか」を先に問う。 公開済みリリースのハッシュは、本来変わらない。
  • Go で書かれたツールなら go version -m でビルド情報を読める。 vcs.modified と疑似バージョンの有無は、タグからの正規ビルドかどうかの手がかりになる（ただし不審なバイナリを実行せずに確認する手段を使うこと——第三者も同じ注意を添えている）。

Klaba 氏の説明は「攻撃者は開発者の1人の GitHub アカウントを使った」である（事実・報道経由）。どう侵害されたかは公表されていない。

第三者の調査が示したのは、権限の形である（第三者の調査）。

  • アップロードに使われたアカウントは、公開されている組織メンバーではなく、ovhcloud-cli へのコミット実績も無い。
  • それでもリリースへの書き込み権限を持っていた。
  • 第三者は CODEOWNERS 経由のチーム所属によるものと推測しているが、OVHcloud は経緯を説明していない。

本記録が指摘しておくのは、コミット権限とリリース権限の性質の違いである（本記録の評価）。

  • コミットはレビューを通る。 変更は履歴に残り、他人の目に触れる。
  • リリースアセットの上書きは、レビューを通らない。 本件では新しいタグも作られず、Actions も走らず、ソースにも何の変更も現れていない。 つまり、ふだんの開発の目には一切映らなかった。

したがって「誰がコミットできるか」の管理と「誰がリリースアセットを書き換えられるか」の管理は、別に行う必要がある（本記録の提言）。後者はコードレビューという安全網の外にある。

隠し場所は不可視の文字と公開台帳で、どちらも「見えないこと」に依存していた評価・解釈

以下は独立した研究者の調査結果であり、OVHcloud は裏付けも否定もしていない（本記録の留保）。また、ここで述べるローダーは「アップロードに使われたアカウントの個人リポジトリに仕込まれていたもの」であり、CLI のバイナリの機能として確認されたものではない（第三者2本がいずれも同じ区別をしている）。

ローダーの隠し方は2段構えだった（Habr の調査）。

  • 1段目は不可視の文字。 ファイルは 9,304 文字のうち 9,123 文字が不可視の variation selector（U+FE00〜U+FE0F、U+E0100〜U+E01EF）で、各文字が1バイトを表していた。 見た目は1行のデコーダと eval だけである。 第1段は AES-256-CBC で暗号化されていたが、鍵と IV は同じファイル内に平文で置かれていた ——暗号化の目的は秘匿ではなく、見た目を変えることだったと読める（本記録の評価）。
  • 2段目は公開台帳。 約4.4KB の第2段は、ロケール（ru_RU／ru-RU）とタイムゾーン（Europe/Moscow）を確認し、該当すると何もせずに終了する。 次段の取得先は公開の Solana RPC に問い合わせ、特定ウォレットの最新の memo から base64 で埋め込まれた URL を読む。

この隠し場所には、構造上の弱点があった（Habr の調査）。

  • ローダーは memo の送信者を検証しない。
  • 最初に見つかった memo をそのまま使う。
  • memo は誰でも少額で書き込める。

実際に2026年5月29日19時42分（UTC）、オペレーターとは別のウォレットからbase64 で「I know you」と読める memo が書き込まれ、1分後にオペレーターが正しいリンクを書き戻している（Habr の調査）。以後、memo の書き込みは止まっている。

本記録がこの節を置く理由は、防御側の教訓が1つあるからである（本記録の評価）。「ブロックチェーンに置けば止められない」はよく言われるが、本件の作りは逆の性質も持っていた ——公開台帳は誰でも読めて、誰でも書き込める。 止めることはできないが、観測することはできる。 実際に第三者は、ウォレットの取引履歴から参照先IPの分散（12のIP・最多が19件）と活動期間を復元している。

ただし本記録は、ここに挙がったIPやウォレットを検知の指標として使わない ——照合先のテレメトリを持たず、悪性を自分で検証していないためである。

    取るべき行動 **本番に入る外部バイナリについて、 検証に使うハッシュまたは署名公開鍵を自社の管理下 （自社リポジトリ・社内アーティファクトリポジトリ）に置き、 配布元から毎回取り直さない運用に変える。** **既存の調達経路を棚卸しし、 「配布元からハッシュも一緒に取っている」ものの一覧を作って順に移す。** **移せないもの（検証手段が提供されていないツール）は、 その旨をリスク台帳に載せる。**
  • 固定したハッシュが変わったら、合わせる前に理由を問う手順を決めておく
    **本件の検知は、CI のハッシュ不一致から始まっている**（事実）。 **分岐はそこにあった**（本記録の評価）—— **「公式が更新したのだろう」とハッシュを書き換えてビルドを通せば、 マルウェアは CI を通って本番に入る。** **この利用者はハッシュを機械的に更新せず、 バイナリのビルド情報を確認して差し替えを見つけた （正規版は `vcs.modified=false`、差し替え版は `+dirty`・`vcs.modified=true`）。** **公開済みのバージョンのハッシュは、本来変わらない。**
    取るべき行動 **CI の依存物のハッシュ不一致を「ビルド失敗」ではなく 「調査が必要な事象」として扱う手順を文書化する。** **最低限、①バージョンが上がっていないのにハッシュが変わった場合は 担当者の判断でハッシュを更新してはならない、 ②配布元の公開済みリリースの変更履歴を確認する、 ③確認できなければ取得を止める、の3点を決める。** **この手順を知らない担当者が1人いれば破れるため、 CI の設定側でハッシュの自動更新を禁止する。**
  • 「誰がコミットできるか」と「誰が配布物を書き換えられるか」を別に管理する
    **本件では新しいタグも作られず、GitHub Actions も走らず、 ソースリポジトリにも何の変更も現れていない**（事実）。 **行われたのは Releases API による既存アセットの上書きだけである。** **つまり、ふだんの開発の目（コードレビュー・差分の確認）には一切映らなかった** （本記録の評価）。 **さらに第三者の調査によれば、使われたアカウントは 当該リポジトリへのコミット実績が無いのにリリースへ書き込めた。**
    取るべき行動 **自社が配布する成果物について、 リリースアセットへの書き込み権限を持つ主体を一覧化し、 人のアカウントを外して署名されたビルドパイプラインに限定する。** **公開済みリリースのアセットの上書きを禁止する（不変リリース）。** **禁止できない環境では、 監査ログの「リリースアセットの更新」イベントを監視し、 パイプライン以外の主体による更新を警報にする。**
  • 配布物の差し替えを公表するときは、利用者が影響を判定できる材料を同時に出す
    **本件の公表（創業者の X 投稿・同日）は 影響バージョンと取るべき行動を含んでおり、速さと実用性の両方があった**（本記録の評価）。 **一方で、読み取られたパスも通信先も示されておらず、 「送信先はまだ分析中」とされている**（事実）。 **結果として利用者は、該当期間に取得したかどうかだけを基準に 端末の全シークレットを交換することになる。** **また、組織としての勧告・事後報告は10月20日時点で未公開であり、 X を見ていない利用者には届かない**（本記録の確認）。
    取るべき行動 **自社が供給者である場合、 配布物の汚染を公表する雛形に ①影響するバージョン・アセット・配布経路、 ②差し替わっていた正確な期間（開始と終了の時刻）、 ③影響の有無を利用者が自分で判定する手段 （ハッシュの一覧または確認された通信先）、 ④取るべき行動、の4点を必須項目として入れる。** **公表は組織の勧告ページに置き、SNS はその入口として使う。**
セキュリティ技術者への示唆
  • 取得したバイナリは、ハッシュだけでなく来歴（タグからの正規ビルドか）まで確認する
    **差し替え版は `v0.15.1-…+dirty` という疑似バージョンを持ち、 `vcs.modified=true`（未コミットの変更を含むローカルビルド）で、 バージョン情報の ldflag が欠けていた**（Issue #300 の報告）。 **正規版は `v0.15.0`・`vcs.modified=false` で、タグのコミットから作られていた。** **ハッシュは `checksums.txt` ごと差し替えられたが、 ビルド情報は差し替えようがなかった**（本記録の整理） ——**ローカルビルドである痕跡が残っていた。**
    取るべき行動 **Go 製ツールは `go version -m <binary>` でビルド情報を読み、 `vcs.modified=false` と、タグと一致するバージョン表記を確認する （不審なバイナリを実行せずに確認する）。** **可能なら `gh attestation verify` で来歴証明を検証し、 署名されたタグからのビルドであることを機械的に確かめる。** **この確認を CI の取得ステップに組み込み、人の目に依存させない。**
  • ツールの入手経路を、差し替えに弱い順に把握しておく
    **本件で影響を受けた経路と受けない経路は、はっきり分かれていた**（第三者の調査）。 **影響を受ける** —— `install.sh`、Homebrew（cask のハッシュで弾かれた可能性はある）、 GitHub Releases からの直接ダウンロード、リリース tarball を取得する CI・Dockerfile。 **影響を受けない** —— `go install`、ソースからのビルド、 `ovhcom/ovhcloud-cli` の Docker イメージ。 **差は「配布された成果物を信じるか、自分で作るか」である**（本記録の整理）。
    取るべき行動 **自社の CI・Dockerfile・開発端末のセットアップ手順で取得している外部ツールを 一覧化し、経路ごとに分類する （①配布バイナリ＋同梱ハッシュ、②配布バイナリ＋外部ハッシュ、 ③ソースからのビルド、④提供元の署名済みコンテナ）。** **①に該当するものを②以降へ移す。** **とくに `curl … | sh` 形式のインストールは、 スクリプトが検証しているかを実際に読んで確認する** ——**本件の `install.sh` は検証していなかった。**
  • 開発端末と CI のディスクに長期有効なシークレットを置かない
    **本件のマルウェアの役割は「ディスク上のシークレットを取得すること」とされている** （創業者の説明・報道経由）。 **交換を求められた対象は API キー・クラウドの認証情報・SSH キーである。** **窃取の範囲も通信先も公表されていないため、 影響を受けた端末では全交換しか選べない**（事実）。 **ディスクに無い鍵は取られず、短命な鍵は取られても有効期間が限られる** （本記録の評価）。
    取るべき行動 **クラウドの認証情報を長期の静的キーから、 短命な資格情報（OIDC によるワークロード単位の引き換え等）へ移す。** **開発端末のシークレットを OS の資格情報ストアまたは 短命なセッションに寄せ、平文ファイルの数を数えて減らす。** **CI は実行ごとに破棄される環境にし、 本番へ到達できる鍵を常設しない。**
  • 不可視文字を含むコードを検知できるようにする
    **第三者の調査によれば、 アップロードに使われたアカウントの個人リポジトリに残されたローダーは、 9,304 文字のうち 9,123 文字が不可視の variation selector （U+FE00〜U+FE0F、U+E0100〜U+E01EF）で、各文字が1バイトを表していた**（事実）。 **見た目は1行のデコーダと `eval` だけで、 コードレビューでは見落としやすい。** **なおこれは CLI のバイナリの機能として確認されたものではなく、 同じアカウントのリポジトリに仕込まれていた別の要素である**（本記録の留保）。
    取るべき行動 **自社リポジトリの CI に、 ソースファイル中の不可視 Unicode 文字（variation selector・ 双方向制御文字・ゼロ幅文字）を検出して失敗させる検査を入れる。** **あわせて `eval` と動的なコード読み込みの新規追加を レビュー必須の変更として扱う。** **依存パッケージの `preinstall`／`postinstall` スクリプトの有無を 一覧化し、新規に追加されたものを検知する。**
  • 公開台帳を使う通信先は、止められないが観測できる
    **第三者の調査によれば、ローダーは公開の Solana RPC に問い合わせ、 特定ウォレットの最新の memo から次段の URL を読む作りだった**（事実）。 **ローダーは memo の送信者を検証せず、最初に見つかった memo を使う。** **実際に2026年5月29日、オペレーターとは別のウォレットから 「I know you」と読める memo が書き込まれている。** **公開台帳は誰でも読めるため、 第三者はウォレットの取引履歴から活動期間（2025年11月〜2026年5月）と 参照先IPの分散（12のIP・最多19件）を復元できた**（本記録の整理）。
    取るべき行動 **ブロックチェーンを指令経路に使う脅威について、 「遮断」ではなく「観測」を前提に対応を設計する （公開台帳上の指標は、報告された時点では読める）。** **自社の端末・CI から公開ブロックチェーンの RPC エンドポイントへの 通信が必要かを確認し、不要なら出口で落とす。** **なお本記録が挙げたIP・ウォレットは悪性を自分で検証していないため、 そのまま検知の指標として投入しない** ——**まず自社に該当する通信があるかの確認に使う。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 外部バイナリを配布元から取得し、検証に使うハッシュも同じ配布元の同じ場所（リリースページ・同梱 checksums）から取っている本件では checksums.txt がアーカイブと一緒に差し替えられ、リリース内での照合は無効だった。止まったのはハッシュを外に持つ経路だけである
委託・第三者部品□ ツールの導入に `curl … | sh` 形式のスクリプトを使っており、そのスクリプトがハッシュや署名を検証しているかを確認していない本件の公式 install.sh はハッシュ検証を行っておらず、この経路の利用者には検知の機会が無かった
運用・監視□ CI で依存物のハッシュを固定しているが、不一致が出たときに担当者の判断でハッシュを更新できる本件の検知はハッシュ不一致から始まった。合わせて通せばマルウェアが CI を通過する分岐点だった
認証・認可□ 自社が配布する成果物のリリースアセットへの書き込み権限を持つ主体を一覧化しておらず、人のアカウントが含まれている本件はタグも Actions も伴わないアセットの上書きで、コードレビューの外側で完結した。使われたアカウントはコミット実績が無かった
システム構成□ 公開済みリリースのアセットを後から上書きできる状態で成果物を配布している公開済みリリースのハッシュは本来変わらない。上書きが可能な限り、利用者側の固定ハッシュによる検証が唯一の砦になる
データの保持□ 開発端末や CI のディスクに、長期有効なクラウド認証情報・API キー・SSH キーが平文で置かれている本件のマルウェアの役割はディスク上のシークレットの取得とされ、窃取範囲が不明なため影響端末では全交換しか選べない
体制・契約□ 自社が供給者として配布物の汚染を公表する雛形を持っておらず、影響期間と判定手段を書く欄が無い本件では分単位の差し替え時刻とアセット一覧を持っているのが第三者だけで、利用者は自分の影響を判定できない
