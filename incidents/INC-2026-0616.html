INC-2026-0616Studio 侵害、全登録顧客が対象

ノーコードWeb制作サービス Studio のクラウド環境が一部機能の脆弱性を悪用されて侵害され、 登録している全顧客のアカウント情報・デザイン/CMS の内容・フォーム送信内容と、 API 連携の外部サービスキーやパスワード保護ページのパスワードなど各種設定の認証情報が流出した可能性—— 暗号化保存分も復号鍵が同じ侵害で読み出され、10月20日時点で98組織が影響の可能性や調査を公表

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及意図せぬ露出（設定不備等で外部から到達可能だった）続報が続いている日本の組織が当事者既知の脆弱性の悪用設計・実装上の不備
初報: 2026年10月16日 最終更新: 2026年10月20日

暗号化していたのに守れなかった理由が、公表文に明記された事例です。

2026年10月16日、ノーコードの Web サイト制作サービス「Studio」を運営する Studio 株式会社は、同社が利用するクラウド環境への第三者による不正アクセスを公表しました（出典1）。確認されている不正アクセスの期間は2026年9月30日から10月1日（日本時間）で、10月13日に社内調査で発覚し、10月14日までに脆弱性の修正と経路の遮断を完了しています（出典1・4）。

本記録が要点と見たのは、次の3点です。

  • 対象は「登録している全顧客」である。 Studio は現時点の調査として、Studio に登録しているすべての顧客について、アカウント情報（ユーザー名・メールアドレス・ハッシュ化されたパスワード）、Studio 上で管理されるデータ（デザインエディタと CMS の内容・フォーム送信内容・Webhook 通知の URL）、ライブプレビューの URL、各種設定に含まれる認証情報が流出した可能性があるとしています（出典1・4）。
  • 暗号化が保護として働かなかった理由を明示している。 フォーム送信内容・外部サービスの API キー・Google スプレッドシート連携の認証情報などは暗号化して保存していたが、「復号に必要な鍵が同じ不正アクセスで読み出された」ため内容を知られた可能性があると公表しています（出典4）。鍵とデータが同じ侵害範囲に入っていたことを、当事者が自ら言語化した記述である（本記録の評価）。
  • 流出対象に「他社サービスの認証情報」が入っている。 API 連携に登録された外部サービスの API キーやトークン、パスワード保護ページのパスワード、カスタムプロキシのプロキシキーが対象です（出典1・4）。Studio 側で鍵を切り替えても外部サービスのキーは発行元の管理下にあるため、利用者自身が発行元で切り替えと失効を行う必要があるとされています（出典4）。

影響は Studio の顧客側に広がっています。 piyolog の集計では、10月20日時点で98組織（自治体17・上場企業5・その他の企業と団体57・個人事業主と小規模事業者19）が自組織のサイトへの影響の可能性または調査中であることを公表しました（出典6）。本記録が一次資料で確認できた件数は、ラクスル 6,412件（2024年6月3日〜2026年10月15日のフォーム送信情報・出典7）、TVer 1,801件（延べ件数・出典8）、埼玉県〈さいたま緑の森博物館〉162件（出典9）です。

個人情報保護委員会への報告の運用も動いています。 Studio は10月17日に利用者へ個別報告の保留を依頼し、10月20日、同委員会との協議の結果、利用者が個別に報告するか、Studio が取りまとめて連名で報告するかを選べることになったと公表しました（出典3）。連名報告を選んだ場合、本件に限り速報の目安期間の超過は報告遅延として扱われません（出典3）。

暗号化していたデータも、復号鍵が同じ侵害で読み出されたため保護として働かなかった原因・手口出典 [1] [4]

Studio の公表内容から、起きていることは次のとおりである（出典1・4）。

  • 第三者が Studio の一部機能の脆弱性を悪用して同社のクラウド環境に不正アクセスし、環境内のデータを外部から取得できる状態にしていた
  • 確認されている不正アクセスの期間は 2026年9月30日から10月1日（日本時間）
  • この状態は 10月14日に Studio が対処するまで続いていた
  • 実際に第三者に取得された事実は確認できていないが、Studio は取得されたものとみなして対応している

注目すべきは、暗号化が保護として機能しなかった理由を当事者が明記していることである。フォームの送信内容、外部サービスの API キーやトークン、Google スプレッドシート連携の認証情報、プロキシキー、reCAPTCHA v3 の設定情報、Webhook 通知の URL については、

暗号化して保存していたものも含め、復号に必要な鍵が同じ不正アクセスで読み出されたため、内容を知られた可能性がある

としている（出典4）。保存時の暗号化は、鍵が別の信頼境界にある場合にのみ侵害時の保護になる。本件は鍵とデータが同じ侵害範囲に入っていたことを示す記述であり、「暗号化しているから大丈夫」という説明が成り立たない条件を当事者が自ら言語化した例である（本記録の評価）。

パスワードについては扱いが分かれる。Studio のパスワードとパスワード保護ページのパスワードはハッシュ化して保存し平文では保存していないため、Studio は「元のパスワードを割り出すことは困難だが、可能性は完全には否定できない」としている（出典1・4）。

最後の区分が本件の性質を決めている。流出した可能性があるのは Studio 内の情報だけではなく、利用者が Studio に預けた「他社サービスへの鍵」でもある。 Studio 側で鍵を切り替えても、外部サービスの API キーやトークンは発行元の管理下にあるため、利用者自身が発行元で新しいキーへの切り替えと古いキーの失効を行う必要があるとされている（出典4）。カスタムプロキシのキーは Studio が新規発行済み、Google スプレッドシート連携の鍵は10月14日に更新済みである（出典1・4）。

フォームの送信内容については、対象と対象外が細かく示されている（出典4）。対象は Studio に保存されていた回答であり、ダッシュボードに届いた回答のほか、ゴミ箱に移した回答（「完全に削除」していないもの）、ライブプレビューでテスト送信した回答、プランの上限を超えてダッシュボードで表示できなかった回答も含まれる。一方、「フォームの結果を Studio に保存」を無効にしていた間の回答、9月30日より前に「完全に削除」した回答、Google フォームなど外部サービスの埋め込みフォームの回答は含まれない。添付ファイルはファイル名のみが対象で中身は含まれない。

このほか、2022年12月から2023年8月に AI によるサイト作成機能「Studio AI」（当初の名称は「Auto」）の先行利用を申し込んだ人のメールアドレス・ユーザー名・居住国（申込時の接続元 IP アドレスから Studio が判定）も流出した可能性があるとされ、Studio のアカウントを持たない人も含まれる（出典1・4）。

なお、データの改ざんや削除は確認されていない。第三者が取得した認証情報にはデータを書き換える権限も含まれていたが、Studio はこれを無効化し、操作の記録を調査して顧客データの書き換え・削除の記録が無いことを確認したとしている（出典1・4）。

時系列で見ると、Studio の対応は次の順序で進んでいる（出典1・3・4）。

  • 10月13日 社内の調査により不正アクセスを確認
  • 10月13日〜14日 脆弱性を修正し、不正アクセスに利用された経路を塞ぐ対応を完了
  • 10月14日 午前2時30分ごろ 安全のため、ログインしていたすべてのユーザーを一括ログアウト
  • 10月14日 Google スプレッドシート連携の接続に必要な鍵を更新
  • 10月16日 第一報を公開（公式Xでも10時11分に告知）、機能別の個別メールをプロジェクトのオーナーへ送付
  • 10月17日 フォーム送信内容や外部サービスの API キーなどを暗号化する鍵を新しい鍵に切り替え
  • 10月20日 個人情報保護委員会への報告方法（個別／連名の選択）を案内

発覚から第一報まで3日で、その間に経路の遮断・セッションの無効化・連携鍵の更新を終えている。一括ログアウトを深夜（午前2時30分ごろ）に実施しているのは、利用者の作業への影響を抑える判断と読める（本記録の推定）。

一方、切り替え前に保存されたデータの再暗号化は進行中であり、古い鍵は切り替え前のデータを読み出すためだけに残されている（出典4）。Studio は「鍵や認証情報を切り替えても、不正アクセスの時点で取得された可能性のある情報は守れない」と明記している（出典1・4）。

原因の詳しい調査は外部の専門機関に依頼すべく依頼先と調整中で、調査結果と再発防止策がまとまる時期は未定である（出典1・4）〈未確定5〉。二次被害（不正ログインや情報の悪用など）の有無は調査中、機能ごとの対象件数は精査中で確定次第公表するとしている（出典4）〈未確定3〉〈未確定4〉。

  • 10月17日 Studio は同委員会からの要請を受けたとして、これから報告する予定の利用者に個別の報告をいったん保留するよう依頼した。保留の依頼の対象は委員会への報告であり、サイト利用者（本人）への通知は含まない
  • 10月20日 同委員会と協議した結果、次のいずれかを選べることになったと公表した

連名報告を選んだ場合、本件に限り、速報の目安の期間を超過しても報告遅延として扱わないこととなった（出典3）。

実務上重要なのは、連名報告に含まれるのは委員会への報告だけだという点である。Studio は、サイト利用者本人への通知の要否・内容・方法は利用者自身が法令・ガイドラインに基づいて判断する必要があるとしている（出典4）。委託先であるプラットフォーム側が報告を取りまとめても、本人通知の責任は委託元である各サイト運営者に残るという切り分けである（本記録の整理）。

CISO・経営層への示唆
  • 保存時の暗号化は、鍵が別の信頼境界にある場合にしか侵害時の保護にならない
    Studio は「暗号化して保存していたものも含め、復号に必要な鍵が同じ不正アクセスで読み出されたため、 内容を知られた可能性がある」と明記している。 暗号化の有無ではなく、鍵の置き場が保護の成否を決めている
    取るべき行動 自社および委託先の「保存時の暗号化」について、鍵の保管場所と、 データに到達できる主体が鍵にも到達できるかを一覧にする。 同一環境に鍵があるものを洗い出し、鍵管理サービスまたは別アカウントへの分離を計画に載せる。 監査やセキュリティチェックシートの回答を「暗号化している」で止めず、鍵の置き場まで書く様式に改める
  • SaaS に預けた「他社サービスの鍵」は、SaaS の侵害時に自社の責任で回収しなければならない
    流出対象には API 連携に登録された外部サービスの API キーやトークン、 パスワード保護ページのパスワード、プロキシキーが含まれる。 Studio は、外部サービスのキーは発行元の管理下にあるため利用者自身が切り替えと失効を行う必要があるとしている
    取るべき行動 利用中の SaaS に登録してある外部サービスの資格情報（API キー・トークン・Webhook URL・連携鍵）の 一覧を作り、保管場所と発行元を記録する。 SaaS 侵害時の切り替え手順（誰が・どこで・どの順に失効させるか）を事前に書いておく
  • 委託先が当局報告を取りまとめても、本人通知の責任は自社に残る
    Studio は個人情報保護委員会との協議により連名報告の道を用意したが、 連名報告に含まれるのは委員会への報告のみで、 サイト利用者本人への通知の要否・内容・方法は利用者自身が判断する必要があるとしている
    取るべき行動 委託先起因の漏えいを想定した対応手順に、「当局報告」と「本人通知」を別の工程として書き分ける。 本人通知の判断基準（対象データの種類・件数のしきい値）と文面の雛形を平時に用意する
  • 問い合わせフォームの回答は、消したつもりのものまで露出の母数に入る
    対象にはゴミ箱に移した回答（「完全に削除」していないもの）、 ライブプレビューでのテスト送信、プランの上限超過で表示できなかった回答も含まれる。 対象外は「完全に削除」した回答と保存を無効にしていた間の回答だけである
    取るべき行動 フォームで取得した個人情報の保存期間を定め、期間経過後に「完全に削除」するところまでを運用手順に書く。 コーポレートサイトのフォームを対象に、現在の保存件数と最古の回答の日付を棚卸しする
  • 「実際に取得された事実は確認できていない」段階での対応方針を、あらかじめ決めておく
    Studio は取得の事実を確認できていないが、取得されたものとみなして対応している。 確認できないことを理由に対応を遅らせる選択もありえたが、取らなかった
    取るべき行動 インシデント対応規程に「持ち出しの有無が確定できない場合は流出したものとして扱う」という既定の方針を明記する。 この前提で必要になる通知・鍵の切り替え・公表の作業量を見積もり、体制を決めておく
セキュリティ技術者への示唆
  • Studio に登録した外部サービスの資格情報を、発行元で切り替えて古い方を失効させる
    Studio 側の鍵の切り替えでは外部サービスのキーは無効にならない。 Studio は利用者自身による新しいキーへの切り替えと古いキーの失効が必要だとしている
    取るべき行動 API 連携・Webhook・カスタムプロキシ・Google スプレッドシート連携の設定を洗い出し、 外部サービス側で新しいキー・トークンを発行して差し替えたうえで、古いものを失効させる。 失効まで行ったかをチェックリストで確認する（差し替えただけでは古いキーは有効なままである）
  • パスワード保護ページのパスワードと、Studio アカウントのパスワードを別に扱う
    どちらもハッシュ化されて平文保存はされていないが、Studio は 「元のパスワードを割り出すことは困難だが、可能性は完全には否定できない」としている。 他サービスで同じパスワードを使い回していれば影響はそこへ波及する
    取るべき行動 Studio アカウントのパスワードを変更し、同じパスワードを使っている他サービスも変更する。 パスワード保護ページのパスワードは別途変更し、ページの閲覧者への再周知の手順を決める
  • 発行済みのライブプレビュー URL を棚卸しして削除・再発行する
    公開前のページを確認するためのライブプレビュー URL が流出対象に含まれる。 Studio は発行済み URL が直接特定されたことは確認していないとしているが、 URL を知る者は公開前の内容を見られる
    取るべき行動 発行済みのライブプレビュー URL を一覧で確認し、不要なものを削除、必要なものを再発行する。 公開前の情報をプレビューで扱う運用そのものを見直し、URL を知っているだけで見られる経路を減らす
  • 暗号鍵の保管をアプリケーション実行環境から切り離す
    本件では復号鍵がデータと同じ不正アクセスの範囲にあった。 アプリケーションの侵害がそのまま復号能力の侵害になる構成だったと読める
    取るべき行動 自社サービスで保存時の暗号化を行っている箇所について、鍵の取得元を点検する。 設定ファイル・環境変数・同一環境のデータストアに鍵がある箇所を、鍵管理サービス経由に移す。 鍵の利用を監査ログに残し、量と時間帯の異常を検知対象にする
  • データの一括読み出しに対する量のしきい値監視を入れる
    9月30日から10月13日まで、外部からデータを取得できる状態が13日間続き、 発覚は社内調査によるものだった。リアルタイムの検知は働いていない
    取るべき行動 顧客データを返す API・データストアへのアクセスについて、 単位時間あたりの件数・バイト数のしきい値超過を通知する設定を入れる。 テナント横断の読み出しが発生しうる経路を洗い出し、優先して監視対象にする

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
データの保持□ 保存時の暗号化を行っているが、復号鍵がアプリケーションと同じ環境・アカウントに置かれている本件で暗号化が保護として働かなかった理由そのもの。鍵の置き場が侵害時の保護の成否を決める
認証・認可□ 自社サービスが、利用者から他社サービスの API キー・トークン・パスワードを預かって保存している流出対象に他社サービスの認証情報が含まれると、被害は自社の外へ広がり、回収も利用者に依存する
