INC-2026-0618Lenovo タブ27機種がテスト鍵使用

Lenovo 製タブレット27機種の Android Verified Boot が AOSP で公開されているテスト用の鍵をそのまま使用しており、 物理アクセスで細工したシステムイメージをインストールできる（CVE-2026-92777・CWE-1391/CWE-1394）—— JVN と Lenovo で深刻度の評価も成立条件（端末がロックされているか否か）の記述も食い違っており、 サポート終了済み製品には修正が提供されない

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年10月20日 最終更新: 2026年10月20日

「検証しているが、誰でも持っている鍵で検証していた」事例です。

2026年10月20日、JPCERT/CC は JVN#33436631「複数の Lenovo 製タブレットの Android Verified Boot 機能において既知のテスト用鍵がそのまま使用されている問題」を公表しました（出典1）。Lenovo が提供する複数のタブレットの AVB（Android Verified Boot）機能では、AOSP（Android Open Source Project）で公開されているテスト用の鍵がそのまま使用されており、当該デバイスへの物理的アクセスにより細工されたシステムイメージをインストールされる可能性があります（出典1）。

本記録が要点と見たのは、次の3点です。

  • 検証の仕組みは動いていたが、鍵が公開されていた。 Android Verified Boot は、起動時にシステムイメージの署名を検証して改ざんを拒む仕組みである。その検証鍵が AOSP に公開されているテスト用の鍵であったため、誰でも「正規」と判定されるイメージに署名できる状態だった（本記録の整理）。署名検証そのものが壊れていたのではなく、信頼の起点が公開物だったという形である。
  • JVN と Lenovo で成立条件の記述が食い違っている。 JVN は「当該デバイスへの物理的アクセスにより、細工されたシステムイメージをインストールされる可能性があります」とするのみで、端末のロック状態に言及していません（出典1）。一方、Lenovo の CVE レコードの説明文は 「ロックされていないタブレット（an unlocked tablet）への物理アクセスを持つ利用者」 を条件としています（原文英語・出典2）。JVN が参照する研究の題は 「ロックされた端末での Android Verified Boot の迂回」（原文英語・出典3）であり、どちらが成立条件なのかが資料間で合っていない〈齟齬2〉。
  • 深刻度の評価も食い違っている。 JVN は CVSS v4.0 基本値 7.0（AV:P/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N）・v3.0 6.6 とします（出典1）。Lenovo の CVE レコードは CVSS v4.0 5.4（AV:P/AC:L/AT:P/PR:N/UI:N/…）・v3.1 6.4（AV:P/AC:H/PR:N/…）です（出典2）。差は AT（攻撃前提条件）・PR（必要な権限）・AC（攻撃の複雑さ） の3項目に出ています〈齟齬1〉。

対象は27機種です（Lenovo の CVE レコードに列挙された製品の数・本記録の集計）。Idea Tab Pro / Tab K11 Gen 2 / Legion Tab / Tab M11 / Tab Extreme / Tab K11 Plus / Tab M10 5G / Tab K9 / Tab One / Tab P12 / Tab Plus / Tab with Clear Case / Yoga Tab / Yoga Tab Plus などで、機種ごとに修正版のビルド番号が異なります（出典2）。すでにサポートが終了している製品へは修正が提供されません（出典1）。

  • 対象機種の出荷台数と、国内で稼働している台数公表されていない
    JVN・CVE レコードのいずれも台数を示していない。 対象27エントリのうち日本国内で販売された機種がどれかも明示されていない（出典1・2）
  • すでにサポートが終了していて修正が提供されない機種はどれか公表されていない
    JVN は「すでにサポートが終了している製品へは修正が提供されない」と記すが、 対象機種のうちどれが該当するかは示していない（出典1）。 Lenovo の CVE レコードには27エントリすべてに修正ビルド番号が記載されており、 サポート終了機種の区別は読み取れない（出典2）〈齟齬5〉
  • 成立条件が「ロックされた端末」か「ロックされていない端末」か見解が分かれる
    JVN は端末のロック状態に言及せず「物理的アクセスにより」とする（出典1）。 Lenovo の CVE レコードは「ロックされていないタブレット」を条件とする（原文英語・出典2）。 JVN が参照する研究の題は「ロックされた端末での迂回」である（原文英語・出典1・3）。 三者で記述が異なり、本記録ではいずれかに決められない〈齟齬2〉
  • テスト用鍵が使われていた経緯（どの工程で差し替えが行われなかったか）公表されていない
    JVN は結果（テスト用の鍵をそのまま使用している）のみを記す（出典1）。 研究側はファームウェア供給網の脆弱性として位置づけているが（出典1・3）、 Lenovo・ODM・SoC ベンダーのどの工程で起きたかは公表されていない。 本記録の作成者は研究ページの本文を取得できていない〈齟齬4〉
  • 報告日と、調整および修正配信の経過公表されていない
    JVN は報告者（松原 正佳 氏）を記載するのみで、報告日も調整の期間も示していない（出典1）。 Lenovo の CVE レコードの公開日（2026年10月15日）と JVN の公開日（10月20日）に5日の差があるが、 理由は示されていない（出典1・2）
  • 同じテスト用鍵の問題が他ベンダーの端末にも及ぶか公表されていない
    研究の題が「AVBTestKeyInTheWild」（野に放たれた AVB テスト鍵）であることから Lenovo 以外の端末も調査対象に含まれる可能性があるが、 JVN が公表しているのは Lenovo 製タブレットについてのみである（出典1）。 本記録の作成者は研究ページの本文を取得できておらず、他ベンダーへの波及は確認していない〈齟齬4〉
  • アップデートできない場合のワークアラウンド公表されていない
    JVN が挙げる対策はアップデートと後続製品への乗り換えのみで、 暫定対策（設定変更等）は示されていない（出典1）。 物理アクセスが前提であるため端末の物理管理が緩和策になりうるが、 これは本記録の評価であり公表された対策ではない

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

以下は JVN と Lenovo の CVE レコードの記述から成立経路を整理したものである（出典1・2）。 実際の悪用は公表されていない〈未確定1〉ため、想定経路である。 攻撃者が対象タブレットに物理的にアクセスし、 AOSP で公開されているテスト用の鍵で署名した細工されたシステムイメージを書き込む。 AVB はこの鍵で署名を検証するため、改ざんされたイメージが正規のものとして受け入れられ、 デバイスの保護を迂回して任意のコードが実行される。 成立条件のうち端末のロック状態については資料間で記述が食い違っている〈齟齬2〉。

  1. 1. 初期侵入disclosed[1] [2]
    攻撃者が対象タブレットに物理的にアクセスする。 CVSS ベクタは AV:P（物理）で、JVN は AT:N（攻撃前提条件なし）・PR:L（低い権限が必要）、 Lenovo は AT:P（前提条件あり）・PR:N（権限不要）と評価している
    根拠: JVN#33436631 の想定される影響および両者の CVSS ベクタ
  2. 2. 検知回避disclosed[1]
    AVB（Android Verified Boot）が AOSP で公開されているテスト用の鍵で署名を検証するため、 攻撃者は同じ公開鍵に対応する秘密鍵でイメージに署名でき、 改ざんされたイメージが正規のものとして受け入れられる
    根拠: JVN#33436631「AOSP で公開されているテスト用の鍵をそのまま使用しています」
  3. 3. 永続化disclosed[1]
    細工されたシステムイメージがインストールされる。 システム領域に書き込まれるため、利用者による初期化や再起動では取り除けない（本記録の評価）
    根拠: JVN#33436631「細工されたシステムイメージをインストールされる可能性があります」
  4. 4. 実行disclosed[1] [2]
    Lenovo の CVE レコードは、デバイスの保護を迂回して任意のコードを実行しうるとしている （原文英語「bypass device protections and execute arbitrary code」）
    根拠: CVE-2026-92777 のレコードの説明文

被害組織の対応

この事案で下された判断
  • JVN は脆弱性の性質（AOSP の公開テスト用鍵をそのまま使用）・CWE 分類・CVSS・想定される影響・ 対策（最新版へのアップデート／サポート終了製品は後続製品への乗り換え）を公表し、 影響を受ける機種の一覧は示さずベンダ情報の参照を求めた。 Lenovo は CVE レコードで27エントリの製品名と機種別の修正ビルド番号を公開した
    理由は公表されていない
    トレードオフ: JVN が機種一覧を抱えないことで、機種と版数の情報源を開発者側に一元化できる。 一方、読者は JVN だけでは自社の端末が対象かを判断できず、Lenovo の勧告まで辿る必要がある。 その勧告ページ（LEN-221035）は自動取得の経路では参照できない
  • すでにサポートが終了している製品へは修正を提供せず、後続製品への乗り換えを求めた
    トレードオフ: 提供しない方針を明示すれば利用者は代替手段の検討に移れる。 一方、本件はワークアラウンドが示されておらず、 サポート終了機種の利用者には物理的な管理を強めるか端末を入れ替えるしか残らない

署名検証は動いていたが、検証に使う鍵が AOSP に公開されたテスト用の鍵だった原因・手口出典 [1] [2] [3]

JVN の記述は次のとおりである（出典1）。

Lenovo が提供する複数のタブレットの AVB（Android Verified Boot）機能では、AOSP（Android Open Source Project）で公開されているテスト用の鍵をそのまま使用しています。

Android Verified Boot は、起動時にシステムイメージの署名を検証し、改ざんされたイメージでの起動を拒む仕組みである。検証そのものは設計どおり働くが、検証鍵が公開物であれば、誰でも「正規」と判定されるイメージに署名できる（本記録の整理）。壊れていたのは検証の処理ではなく、信頼の起点である。

JVN は CWE-1391（脆弱な認証情報の使用）として分類し、Lenovo の CVE レコードは CWE-1394: Use of Default Cryptographic Key（既定の暗号鍵の使用） としている（出典1・2）。どちらも「出荷前に製品固有の鍵へ差し替える工程が行われていなかった」ことを指している（本記録の整理）。

JVN が参考情報として挙げる研究の題は、この性質をより直接に示している。

AVBTestKeyInTheWild: Bypassing Android Verified Boot Using A Firmware Supply Chain Vulnerability on Locked Devices（野に放たれた AVB テスト鍵——ファームウェア供給網の脆弱性を用いた、ロックされた端末での Android Verified Boot の迂回／原文英語）

つまり研究側は、これをファームウェアの供給網の問題として位置づけている（出典1・3）。ただし本記録の作成者は当該研究ページの本文を取得できていない〈齟齬4〉。

成立条件が「ロックされた端末」なのか「ロックされていない端末」なのかが資料間で合っていない未確定事項出典 [1] [2] [3]

本件で最も扱いに注意が要るのは、成立条件の記述が資料間で食い違っている点である。

資料 成立条件の記述
JVN#33436631（出典1） 「当該デバイスへの物理的アクセスにより、細工されたシステムイメージをインストールされる可能性があります」。ロック状態への言及なし
Lenovo の CVE レコード（出典2） 「a user with physical access to an unlocked tablet」（ロックされていないタブレットへの物理アクセスを持つ利用者／原文英語）
研究の題（出典1・3） 「on Locked Devices」（ロックされた端末で／原文英語）

Lenovo の記述に従えば、端末がロックされていることが防御として働く。研究の題に従えば、ロックされた端末でも迂回できることが主張の中身である。JVN はこの点を書き分けていない〈齟齬2〉。

深刻度の評価もこれに連動している（出典1・2）。

資料 CVSS ベクタ
JVN v4.0 7.0 / v3.0 6.6 AV:P/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/…
Lenovo（CNA） v4.0 5.4 / v3.1 6.4 v4.0 AV:P/AC:L/AT:P/PR:N/UI:N/… ／ v3.1 AV:P/AC:H/PR:N/…

差が出ているのは AT（攻撃前提条件）・PR（必要な権限）・AC（攻撃の複雑さ） である。JVN は AT:N（前提条件なし）・PR:L（低い権限が必要）、Lenovo は AT:P（前提条件あり）・PR:N（権限不要）で、v3.1 では AC:H（攻撃が困難）とする。「前提条件は要るが権限は不要」（Lenovo）と「前提条件は不要だが権限は要る」（JVN） という、ほぼ反転した評価になっている（本記録の整理）。

本記録はいずれかを採らず、両方を記録する。実務上は、より厳しい側（ロックされた端末でも成立しうる・前提条件なし）を前提に置くのが安全である（本記録の評価）。Lenovo の勧告 LEN-221035 の本文を確認すれば整理できる可能性があるが、同ページは自動取得の経路では HTTP 403 を返し、本記録の作成者は直接取得できていない〈齟齬3〉。

対象は27機種で修正版のビルド番号は機種ごとに異なり、サポート終了製品には修正が出ない対策・注意喚起出典 [1] [2]

JVN は「影響を受ける製品は多岐に渡ります。詳細については『ベンダ情報』を参照してください」と記すのみで、機種の一覧を載せていない（出典1）。Lenovo の CVE レコードには 27エントリの製品が列挙されており、機種ごとに修正ビルド番号が異なる（出典2）。主なものを挙げる。

  • 現行製品の利用を停止し、後続製品に乗り換える「開発者によると、すでにサポートが終了している製品へは修正が提供されない」ため

事案の詳細

直接原因Lenovo が提供する複数のタブレットの AVB 機能では、 AOSP（Android Open Source Project）で公開されているテスト用の鍵をそのまま使用している（出典1）。 AVB は起動時にシステムイメージの署名を検証して改ざんを拒む仕組みだが、 検証に用いる鍵が公開物であるため、誰でも「正規」と判定されるイメージに署名できる（本記録の整理）。 JVN は CWE-1391（脆弱な認証情報の使用）、 Lenovo の CVE レコードは CWE-1394（Use of Default Cryptographic Key／既定の暗号鍵の使用）として 分類している〈齟齬1〉。
impact_mechanismJVN は「当該デバイスへの物理的アクセスにより、細工されたシステムイメージをインストールされる 可能性があります」としている（出典1）。 Lenovo の CVE レコードの説明文は 「A potential vulnerability was reported in some Lenovo Tablets that could allow a user with physical access to an unlocked tablet to bypass device protections and execute arbitrary code.」 （原文英語。ロックされていないタブレットへの物理アクセスを持つ利用者が、 デバイスの保護を迂回して任意のコードを実行しうる／出典2）としており、 端末のロック状態についての記述が JVN と食い違っている〈齟齬2〉。

  • 発表・報道間の食い違いJVN と Lenovo で CVSS の評価と CWE の分類が食い違っている
    JVN は CWE-1391（脆弱な認証情報の使用）、CVSS v4.0 7.0 （CVSS:4.0/AV:P/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N）、 CVSS v3.0 6.6（CVSS:3.0/AV:P/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H）とする（出典1）。 Lenovo（CNA）の CVE レコードは CWE-1394（Use of Default Cryptographic Key）、 CVSS v4.0 5.4（CVSS:4.0/AV:P/AC:L/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N）、 CVSS v3.1 6.4（CVSS:3.1/AV:P/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H）とする（出典2）。 差は AT（JVN は N・Lenovo は P）・PR（JVN は L・Lenovo は N）・ AC（v3 系で JVN は L・Lenovo は H）の3項目に出ており、 「前提条件は要るが権限は不要」と「前提条件は不要だが権限は要る」でほぼ反転している。 いずれの資料もこの差の理由を説明していない。 本記録は両方を記録し、detail.cvss には JVN の値を主として置いた
  • 発表・報道間の食い違い成立条件が「ロックされた端末」か「ロックされていない端末」かが三者で異なる
    JVN は「当該デバイスへの物理的アクセスにより、細工されたシステムイメージを インストールされる可能性があります」とするのみで、ロック状態に言及していない（出典1）。 Lenovo の CVE レコードの説明文は「a user with physical access to an unlocked tablet」 （ロックされていないタブレットへの物理アクセスを持つ利用者／原文英語・出典2）とする。 JVN が参考情報として挙げる研究の題は 「Bypassing Android Verified Boot Using A Firmware Supply Chain Vulnerability on Locked Devices」 （ロックされた端末での Android Verified Boot の迂回／原文英語・出典1・3）である。 ロック状態が防御として働くのかどうかが資料間で合っておらず、本記録では決められない。 実務上はより厳しい側を前提に置くことを本記録の評価として示した
  • 裏取りできていないLenovo の勧告 LEN-221035 を本記録の作成者は直接取得できていない
    CVE レコードが参照先として示す https://support.lenovo.com/us/en/product_security/LEN-221035 は、 本記録の作成者が2026年10月21日に取得を試みたところ HTTP 403 を返した （WebFetch と UA を指定した取得の両方で同じ結果）。 このため勧告本文の記述（成立条件の説明・サポート終了機種の扱い・ ワークアラウンドの有無）は確認できていない。 Lenovo 側の情報としては CVE レコード（Lenovo が CNA として登録した内容）に依拠している
  • 裏取りできていない研究（AVBTestKeyInTheWild）の本文を本記録の作成者は取得できていない
    JVN が参考情報として挙げる Android-Device-Security.Org の研究について、 本記録の作成者は刊行物一覧ページ（https://www.android-device-security.org/publications/）の リンクまでは確認したが、当該研究の本文は取得できていない。 このため、ロックされた端末での迂回の具体的な手順、 テスト用鍵が製品に残った工程、Lenovo 以外の端末への波及はいずれも裏取りしていない。 本記録が研究について記しているのは、JVN に掲載された題のみである
  • 発表・報道間の食い違いサポート終了機種が示されていない一方、CVE レコードは全27エントリに修正版を記載している
    JVN は「開発者によると、すでにサポートが終了している製品へは修正が提供されないとのことです。 後続製品への乗り換え等を検討してください」と記す（出典1）。 一方、Lenovo の CVE レコードは27エントリすべてに修正ビルド番号を記載しており、 修正が提供されない機種の区別は読み取れない（出典2）。 JVN が言うサポート終了製品が CVE レコードの27エントリに含まれるのか、 それとも CVE レコードに載っていない別の機種を指すのかは、いずれの資料からも判断できない

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
AOSP の公開テスト用鍵で AVB を通し、細工したシステムイメージを導入する経路
layer 0 は攻撃者と、AOSP に公開されているテスト用の鍵。 layer 1 は対象タブレットへの物理アクセスという前提条件。 layer 2 は AVB（Android Verified Boot）の署名検証と、そこで受け入れられてしまう細工されたイメージ。 layer 3 は結果（デバイスの保護の迂回・任意のコード実行）と、端末の利用者・導入組織。 layer 4 は対策（型番ごとの修正ビルドへの更新／サポート終了製品は後続製品への乗り換え）。 成立条件のうち端末のロック状態については JVN・Lenovo・研究の題で記述が食い違っている。 実際の悪用は公表されていない。

判断評価評価の根拠と留保

CISO・経営層への示唆
  • 「署名を検証している」は、鍵が誰のものかを確認しないと保証にならない
    AVB は設計どおり署名を検証していたが、検証鍵が AOSP に公開されたテスト用の鍵だった。 検証の仕組みの有無ではなく、信頼の起点が誰だけのものかが保証を決める
    取るべき行動 セキュアブート・コード署名・ファームウェア検証を要件に挙げている調達・設計の文書を見直し、 「鍵が製品固有か」「鍵の生成・保管の責任主体は誰か」を確認項目として追加する。 ベンダーへの質問票に、出荷時の鍵差し替えの実施を問う項目を入れる
  • 資料間で深刻度と成立条件が食い違う脆弱性は、厳しい側を前提に置く
    JVN は CVSS v4.0 7.0・AT:N・PR:L、Lenovo は 5.4・AT:P・PR:N と評価し、 成立条件も「ロックされた端末」か「ロックされていない端末」かで記述が分かれている。 評価を低い側に合わせると、実際には成立する条件を見落としうる
    取るべき行動 脆弱性の緊急度判定の手順に「一次資料が複数あり評価が食い違う場合は厳しい側を採る」という規則を明記する。 食い違いの事実そのものを対応記録に残し、後から経営に説明できる状態にする
  • 端末の物理アクセスを前提とする脆弱性は、貸与・中古・紛失の運用で効いてくる
    本件は物理アクセスが前提（AV:P）であり、ネットワーク越しの攻撃ではない。 逆に言えば、端末が手元を離れる場面（貸与返却・修理・中古購入・紛失）がそのまま成立条件になる
    取るべき行動 業務で使うタブレットについて、貸出・返却・修理・廃棄の各段階の手続きを見直す。 返却時と中古調達時にファームウェア版数を確認する工程を入れ、 紛失端末を回収した場合は再利用せず初期化ではなく交換する方針を決める
  • サポート終了済み端末の業務利用を、脆弱性が出てから判断しないようにする
    JVN は「すでにサポートが終了している製品へは修正が提供されない」としつつ、 どの機種が該当するかを示していない。 終了後に脆弱性が出た時点では、選択肢は端末の入れ替えしか残らない
    取るべき行動 業務で使うモバイル端末の機種ごとにサポート終了時期を台帳に記録し、 終了の半年前に更新または業務利用の停止を決める運用にする。 私物端末の業務利用を認めている場合は、対象機種の条件に版数とサポート状況を含める
セキュリティ技術者への示唆
  • 機種名ではなく型番で対象を判定し、型番ごとの修正ビルド番号に上げる
    同じ Tab K11 Gen 2 でも TB336FU は 17.5.10.193、TB336ZU は 17.5.10.210、 TB336FU/TB336ZU の組は 17.5.10.213 と修正版が3通りに分かれている。 機種名だけでは上げるべき版が決まらない
    取るべき行動 管理下のタブレットについて型番（TB3xxxx 形式）と現在のビルド番号を収集し、 Lenovo の勧告に記載された修正ビルド番号と突き合わせる。 MDM で型番とビルド番号を必須の収集項目にする
  • 端末の完全性を、端末自身の表示に頼らず外側から確認する
    本件では改ざんされたイメージが AVB の検証を通る。 端末が「正規に起動した」と表示しても、それが正しいとは限らない
    取るべき行動 MDM の構成証明（attestation）やネットワーク側の端末検査を併用し、 ビルド番号・パッチ版数・ブート状態を外部から収集して照合する。 想定外のビルド番号を持つ端末を業務ネットワークから隔離する条件を設定する
  • 端末内に業務データと長期有効な資格情報を置かない
    CVSS の機密性・完全性・可用性はいずれも High で、 Lenovo は「デバイスの保護を迂回して任意のコードを実行しうる」としている。 端末が侵害された場合、端末内のものはすべて射程に入る
    取るべき行動 業務データは管理された領域に置き、端末側はリモート参照を基本にする。 端末に配布する証明書・トークンの有効期間を短くし、 端末の侵害が疑われた時点で失効させる手順を用意する
  • 中古・貸与で入ってきた端末を、受け入れ時に検査する工程を作る
    本件は物理アクセスで細工したイメージを入れられる脆弱性である。 来歴の分からない端末は、受け入れた時点で既に改ざんされている可能性がある
    取るべき行動 中古調達・貸与返却の受け入れ手順に、ビルド番号の確認と修正版への更新を組み込む。 更新できない機種（サポート終了）は業務利用の対象から外す
  • 自社製品にセキュアブートを実装している場合、鍵の由来を点検する
    本件は「公開されているテスト用の鍵を出荷時にもそのまま使っていた」ことによる。 開発中のテスト鍵が製品に残るのは、組込み製品で起こりうる事故である（本記録の評価）
    取るべき行動 自社製品の署名鍵について、開発用と製品用が分かれているか、 製品用の鍵が外部に出ていないか、出荷前の差し替えが工程として存在するかを確認する。 確認を出荷前チェックリストの項目として固定する
