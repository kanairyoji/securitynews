INC-2026-0624Bullhornが人材基盤を全面停止

人材派遣・採用業務基盤を1万社以上に提供する米 Bullhorn は、2026年10月16日の求人投稿の不具合を端緒に 17日にプラットフォーム全体の障害となり、同日「サイバーインシデントを検知した」として 自らシステムへのアクセスを全面停止した——19日から段階的に復旧したが、10月20日時点でも SSO・パスワードリセット・カスタマイズに不具合が残り、**顧客データが持ち出されたかどうかは 「まだ判明していない」**とされ、SSO を使わない全利用者のパスワード強制変更と API 認証情報のローテーションが要求された

不正アクセス・侵害システム障害続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年10月19日 最終更新: 2026年10月20日

米国の人材派遣・採用業務ソフトウェア企業 Bullhorn（自社公表で1万社超の顧客）は、2026年10月、サイバーインシデントの封じ込めのため自らプラットフォームへのアクセスを全面停止した。

発端は10月16日（金）で、顧客が Bullhorn アプリケーションからの求人投稿（Indeed への掲載）に不具合を訴え始めた。翌17日（土）朝には「Bullhorn プラットフォーム全体に影響するシステム全体の障害」となり、同社は同日「Bullhorn プラットフォーム上でサイバーインシデントを検知した。さらに調査するため、活動を封じ込める目的で一時的に当社システムへのアクセスを無効化した」（原文英語）と公表した。調査には CrowdStrike の専門家が入った。

影響は ATS/CRM・自動化・バックオフィス・Talent Platform・サンドボックス環境に及び、採用代理店は候補者レコード・応募・配属、そして場合によっては人に支払うための仕組みへのアクセスを失った。サービスは10月19日（月）から戻り始め、20日（火）時点で米国・英国・豪州の全リージョンがオンラインになったが、SSO・パスワードリセット・カスタマイズには不具合が残り、自動化ツール・Talent Platform・Onboarding365・Time & Expense では性能劣化が続いていた。

最も重要な未確定事項は持ち出しの有無である。 Bullhorn は FAQ でフォレンジック調査を開始したとしつつ「顧客データが持ち出されたかどうかはまだ判明していない」（原文英語）とし、確認されれば影響を受けた個人に直接通知すると約束した。復旧にあたってはSSO を使わない全利用者に次回ログイン時のパスワード変更を要求し、連携を守るため API パスワードのローテーションを指示した（クライアントシークレットの変更は後続。Bullhorn がホストするインスタンスでは自動で実施）。

Bullhorn はまた、混乱に便乗する詐欺への警告を出している——「攻撃者がメール・SMS・電話で Bullhorn の担当者を装い、本インシデントを口実に認証情報や機微情報を要求してくる可能性がある」（原文英語）。同社の従業員がパスワード・多要素認証コード・検証トークンの開示を求めることは決して無いと強調した。

  • API 連携を使う顧客は、連携を守るため API パスワードをローテーションする

採用基盤が扱うデータの性質を踏まえると、この未確定は重い（本記録の評価）。Bullhorn の基盤は候補者の氏名・連絡先・職歴に加え、オンボーディングと給与計算を含むため報酬・勤務記録にも及ぶ。持ち出しが確定した場合の通知対象は、顧客企業ではなく求職者・派遣スタッフ本人になる。

そして通知の判断は顧客企業側にも降りてくる。多くの国の規制では、個人データの管理者（controller）は顧客企業であり、Bullhorn は処理者（processor）の位置にある。「Bullhorn が調査中」である間、顧客企業は自社の通知義務の判断を保留せざるを得ない。 Bullhorn の当局報告の有無・時期も公表されていない。

ここに運用上の矛盾がある（本記録の指摘）。Bullhorn はSSO を使わない全利用者にパスワード強制変更を要求した一方で、パスワードリセット機能そのものに不具合が残っていた。ステータスページの10月20日17時24分 EDT の更新では「ATS 管理者が利用者を編集し手動でパスワードを設定できるようになった」ことが復旧項目として挙げられている——つまりそれまでは管理者による代替手段も使えなかった。

認証情報の緊急交換は、交換の手段が動いていることを前提にしている。侵害対応で認証情報を一斉に無効化する計画を持つ組織は、その計画が「無効化の手段自体が障害下にある」状況で成立するかを確認しておく必要がある。

本記録はこれを評価すべき対応として記録する。大規模なサービス停止の最中は、利用者が「復旧のための手続き」を受け入れやすくなる。しかも本件では実際に全利用者のパスワード変更と API 認証情報のローテーションが要求されているため、正当な依頼と偽の依頼が見分けにくい。警告が被害の報告を待たずに出されたことは、この構造を踏まえた先回りである。

第一に、人材・採用の業務が SaaS 1社に集中していることである。本件で止まったのは求人投稿から候補者管理、オンボーディング、そして給与計算・勤務記録までである。自社の人材 SaaS が止まったとき、どこまで止まるのかを棚卸ししている組織は少ない。

第四に、処理者の調査が終わらない間、管理者としての通知判断が保留されることである。日本の個人情報保護法でも、委託先での漏えいは委託元の報告義務に関わる。「委託先が調査中」という状態がどれだけ続きうるかを、契約の段階で詰めておく必要がある（本件は検知から4日目でも持ち出しの有無が未判明である）。

事案の構造を図にしたものです。数値は公表値に基づきます。
1社の採用 SaaS の停止が、1万社超の採用業務と「人への支払い」まで止めるまで
layer 0 は攻撃側——実体・手口・侵入経路のいずれも非公表で、 ランサムウェアの関与も確認されていない。 layer 1 は基盤——Bullhorn プラットフォーム（2026年10月17日に同社が自らアクセスを全面停止）と、 調査に入った CrowdStrike。 layer 2 は製品群——大規模障害となった ATS/CRM・自動化・バックオフィス・ Talent Platform・サンドボックスと、性能劣化した Onboarding365・Time & Expense ほか、 そして稼働を維持した Adapt・eEmpACT・StaffSuite の3製品。 layer 3 は波及先——1万社超の採用代理店が候補者レコード・応募・配属を失い、 さらに給与計算・勤務記録が止まった。 layer 4 は個人——求職者・派遣スタッフ。**持ち出しが確認された場合に直接通知される対象**だが、 10月20日時点で持ち出しの有無は判明していない。 併せて、Bullhorn 担当者を装う便乗詐欺への警告が顧客向けに出されている。 **影響を受けた社数・利用者数・日本の顧客の有無はいずれも公表されていない。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**サイバーインシデントの検知と同日に、プラットフォームへのアクセスを全面停止した** （1万社超の顧客すべてが対象）。復旧は10月19日から段階的に行い、 20日に米国・英国・豪州の全リージョンがオンラインに戻った機能した**本記録の作成者の評価である。** Bullhorn は停止の理由を「活動を封じ込めるため」と明示しており、 **侵害範囲が分からない段階で業務継続より封じ込めを選んだ**ことになる。 基盤提供者の判断として妥当である。 とくに**給与計算まで止まる基盤**でこの判断を下すのは容易ではない。 一方で**未投稿の勤務記録の再処理・サービスクレジットの SLA 照合**という後始末を 同時に提示しており、停止の代償を顧客に丸投げしていない点も評価できる。 **ただし「いつ全面復旧するか」の見通しが示されていない**ことは、 顧客側の事業継続計画を立てにくくしている
**SSO を使わない全利用者に次回ログイン時のパスワード変更を要求**し、 **連携を守るため API パスワードのローテーション**を指示した。 クライアントシークレットの変更は後続とし、 Bullhorn がホストするインスタンスでは自動で実施するとした部分的に機能**本記録の作成者の評価である。** 持ち出しの有無が未確定な段階で**予防的に全交換へ踏み込んだのは適切**である。 また「Bullhorn がホストするインスタンスでは自動で実施する」という切り分けは、 顧客の作業量を減らす方向に働いている。 一方で**クライアントシークレットの変更が「後続」とされている**点は、 交換の完了が段階的であること——つまり**一定期間、未交換の認証情報が 残り続けること**を意味する。 さらに10月20日時点で**パスワードリセット機能自体に不具合が残っている**と 報じられており、**強制変更を要求しながらその手段が不安定**という状態になっている
**障害の発生・サイバーインシデントであること・CrowdStrike の起用・ 製品別の復旧状況・必要な認証情報の交換・なりすまし詐欺への警告は公表した**一方、 **侵入経路・攻撃者・ランサムウェアの関与・検知の経緯・持ち出しの有無は示さなかった**部分的に機能**本記録の作成者の評価である。** 評価できる点は**速さと具体性**にある——検知と同日に「サイバーインシデント」と 言い切り、製品別の状態をステータスページで細かく示し、 顧客が取るべき行動（パスワード変更・API 認証情報のローテーション・ データエクスポートの依頼・なりすまし詐欺への注意）を明示している。 とくに**なりすまし詐欺への先回りの警告**は、過去の大規模インシデントで 繰り返し起きた二次被害を踏まえた実務的な対応である。 一方で**「顧客データが持ち出されたかどうかはまだ判明していない」以上の情報が無い**ため、 顧客は**本人通知が必要になるかどうかを判断できない。** 採用基盤は候補者の氏名・連絡先・職歴を扱うため、 **判断の遅れがそのまま個人の備えの遅れになる**（本記録の指摘）
停止中の顧客に対し、**サポート経由でのデータエクスポート要求**を受け付け、 **未投稿の勤務記録は復旧後に再処理**し、**サービスクレジットは インシデント解決後に SLA に照らして検討する**とした部分的に機能**本記録の作成者の評価である。** 勤務記録の再処理とサービスクレジットの明示は、 **顧客の損失を自社の課題として引き受ける姿勢**を示している。 一方で**データエクスポートは「サポートへの依頼」という形**であり、 1万社超が同時に依頼した場合に処理できる仕組みなのかは示されていない。 **平時からエクスポートを取っていた顧客と、停止中に初めて依頼する顧客で 業務継続の成否が分かれる**（本記録の評価）
CISO・経営層への示唆
  • 人材 SaaS の停止は「採用が止まる」ではなく「人への支払いが止まる」である
    Bullhorn の基盤は応募者追跡・CRM・オンボーディング・**給与計算（バックオフィス）・ 勤務記録（Time & Expense）**を含む。 The Register は停止の影響を「候補者レコード・応募・配属、 **そして場合によっては人に支払うための仕組み**へのアクセスを失うこと」（原文英語）と 書いている。 **業務影響度評価（BIA）で人材 SaaS を「採用業務」に分類していると、 実際の影響——派遣スタッフへの支払い遅延——を見落とす**
    取るべき行動 ①人材・労務系 SaaS について、**停止したときに止まる業務を給与・勤務記録まで含めて列挙**する ②そのうち**法定期限があるもの（給与支払日・社会保険の手続き）を特定**し、 手作業での代替手順と所要工数を出させる ③BIA の分類を「採用」ではなく**「人への支払いを含む基幹業務」**に見直す
  • 委託先が調査中である間、自社の本人通知の判断は止まる
    Bullhorn は検知から4日目でも「顧客データが持ち出されたかどうかはまだ判明していない」 としている。**多くの規制で個人データの管理者は顧客企業**であり、 **委託先の調査が終わらない限り、自社の通知義務の判断ができない。** Bullhorn の当局報告の有無・時期も公表されていない
    取るべき行動 ①重要な SaaS との契約に**「インシデント発生時の報告期限」と 「調査中であっても一定期間ごとに状況を報告する義務」**を入れる （「判明次第」だけでは本件のような長期の未確定に対応できない） ②自社が各 SaaS に預けている**個人データの項目と件数を平時から一覧化**する （持ち出しが確定してから調べ始めると通知判断が遅れる） ③**「委託先が調査中」という状態で自社がどこまで動くか**を、 法務と事前に合意しておく（監督当局への先行報告の可否を含む）
  • 認証情報の緊急交換は、交換の手段が動いている前提で設計されていないか確認する
    Bullhorn は**SSO を使わない全利用者にパスワード強制変更を要求**した一方で、 10月20日時点で**パスワードリセット機能自体に不具合が残っていた。** 管理者による手動パスワード設定が「復旧した項目」として報告されているため、 **それまでは代替手段も使えなかった。** 自組織の侵害対応計画にも同じ構造の前提が潜んでいる
    取るべき行動 ①侵害対応計画の「認証情報の一斉無効化」手順について、 **その手順に使うシステム（IdP・パスワード管理・管理コンソール）が 停止している場合の代替**を書き出す ②**SSO に寄せる**ことの価値を再評価する——本件の強制変更対象は 「SSO を使わない利用者」であり、SSO 利用者は対象外だった ③年に1回、**「IdP が使えない状態での認証情報交換」を机上演習**に入れる
  • 大規模停止の最中は、正当な依頼と便乗詐欺が見分けられなくなる
    本件では**実際に全利用者のパスワード変更と API 認証情報のローテーションが 要求されている。** その状況で Bullhorn は 「攻撃者が Bullhorn の担当者を装い、本インシデントを口実に 認証情報や機微情報を要求してくる可能性がある」（原文英語）と警告した。 **正当な依頼が飛び交っているときほど、偽の依頼が通る**
    取るべき行動 ①重要な SaaS について、**インシデント時の正式な連絡経路** （ステータスページ・特定のドメインからのメール・担当者）を平時に確認し、 **利用者へ周知しておく** ②「**当社からパスワード・MFA コード・トークンを尋ねることは無い**」という 自社版の文言を用意し、自社がインシデントを公表する際に同時に出す ③停止中の問い合わせ窓口を1本化し、**そこ以外からの指示に従わない**ことを社内規則にする
セキュリティ技術者への示唆
  • SaaS 連携用のクレデンシャルを「全交換できる状態」で持つ
    本件では顧客側の作業として**API パスワードのローテーション**が要求された （クライアントシークレットの変更は後続）。 **「どのシステムが、どの認証情報で、何本つながっているか」の一覧が無ければ、 交換の指示を受けても何を交換すればよいか分からない。** また Bullhorn がホストするインスタンスでは自動交換されるため、 **自社側だけが取り残される可能性がある**
    取るべき行動 ①主要 SaaS ごとに**API キー・OAuth クライアントシークレット・ サービスアカウントの一覧**（所在・用途・最終交換日・交換手順）を作る ②**交換を1回試す**（手順書があっても動くとは限らない）。 所要時間と停止する業務を記録する ③シークレットをコード・設定ファイルに直書きしている箇所を洗い出し、 **交換の際に再デプロイが必要な箇所**を明示する
  • 業務データの自社側へのエクスポートを、平時から定期的に取得しておく
    Bullhorn は停止中の顧客に**サポート経由でのデータエクスポート要求**を受け付けたが、 **1万社超が同時に依頼した場合の処理能力は示されていない。** 停止してから初めて依頼する組織と、平時から取得していた組織で業務継続の成否が分かれる
    取るべき行動 ①主要 SaaS の**エクスポート API／機能**を確認し、 **定期取得を自動化**する（候補者データ・配属・勤務記録など業務再開に必要な範囲） ②取得したデータから**実際に業務を回せるか**を1回試す （形式だけ取れても使えないことがある） ③エクスポートしたデータの**保管場所の保護**（暗号化・アクセス制限・保持期限）を決める—— **バックアップのつもりの抜き出しが次の漏えい元になる**
  • ステータスページを「製品単位」で読み、自社の業務にどう効くかを対応づける
    Bullhorn のステータスページは製品・クラスタ単位で状態を示しており、 **同じ「障害中」でも ATS/CRM と Time & Expense では止まる業務が違う。** 本件では**Adapt・eEmpACT・StaffSuite の3製品だけが稼働を維持**していた
    取るべき行動 ①自社が使っている SaaS の**製品／モジュール名を正確に把握**し、 ステータスページの表記と対応づけた一覧を作る ②ステータスページの**購読（RSS・メール・Webhook）を設定**し、 担当者個人ではなくチームの窓口に届くようにする ③「この製品が止まったら、どの業務が止まり、誰に連絡するか」を一覧に併記する
  • 「判明していない」と「無かった」を、社内報告で混ぜない
    Bullhorn の表現は「**顧客データが持ち出されたかどうかはまだ判明していない**」である。 これを社内で「漏えいは確認されていない」と要約すると、 **「調査が終わって無かった」と読まれる。** 本件は検知から4日目でも調査中であり、**持ち出しが否定されたわけではない**
    取るべき行動 ①インシデント報告の様式に**「調査中／確認されず／否定された」の3段階**を設け、 混用しないようにする ②SaaS 由来のインシデントでは**ベンダーの原文表現をそのまま引用**し、 要約で確度を変えない ③「調査中」の案件について**次回の状況確認日を必ず設定**し、 放置されないようにする

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ **人材・採用・労務の業務を単一の SaaS に集約している** （応募者管理だけでなくオンボーディング・給与計算・勤務記録を同じ基盤で扱っている）本件では**候補者レコード・応募・配属に加え、 人に支払うための仕組みまで同時に止まった。** 業務影響度評価で「採用業務」として扱っていると、 **派遣スタッフへの支払い遅延という実際の影響を見落とす**
認証・認可□ **SaaS 連携用の API キー・クライアントシークレットの一覧を持っておらず、 一斉交換を試したことがない**本件では顧客側の作業として API パスワードのローテーションが要求された。 一覧が無ければ**何を交換すればよいかが分からず**、 ベンダー側が自動交換した場合に**自社の連携だけが切れたまま残る**
認証・認可□ **SSO を使わない利用者が残っており**、 かつ認証情報の緊急交換手順が「パスワードリセット機能が動く」前提で書かれている本件の強制パスワード変更の対象は「**SSO を使わない利用者**」であり、 しかも**パスワードリセット機能自体に不具合が残っていた。** 交換の手段が障害下にあるという状況は、計画段階で想定されていないことが多い
データの保持□ **SaaS に預けている個人データの項目と件数を平時に一覧化していない**Bullhorn は検知から4日目でも持ち出しの有無を判明させていない。 **管理者としての本人通知・当局報告の判断は自社に残る**ため、 確定後に調べ始めると判断が遅れる
体制・契約□ SaaS 契約に**「調査中であっても一定期間ごとに状況を報告する義務」**が無く、 報告義務が「判明次第」になっている本件は検知から4日目でも「まだ判明していない」状態であり、 **「判明次第」では顧客企業が自らの義務を履行する計画を立てられない**
運用・監視□ 業務データの**自社側へのエクスポートを定期取得しておらず**、 エクスポートしたデータで業務を回せるか試したことがないBullhorn はサポート経由のエクスポート依頼を受け付けたが、 **1万社超が同時に依頼した場合の処理能力は示されていない。** 停止してから初めて依頼する組織は、受付と処理を待つ間業務が止まる
