INC-2026-0628opencode の重大RCEがCVE無しで修正

AI コーディングエージェント opencode に CVSS 9.8 相当の遠隔コード実行の欠陥—— 悪意ある MCP サーバが OAuth 発見文書の authorization_endpoint に仕込んだ文字列が Windows で PowerShell に解釈され、開発者の端末でコードが動く。 修正は2026年9月28日の 1.18.33 で入ったが CVE も勧告も発行されず、 脆弱性スキャナからは見えない

脆弱性委託先・再委託先起因で委託元多数に波及初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年10月4日（Pillar Security の報告書公開） 最終更新: 2026年10月20日

直した。しかし、直ったことを誰にも知らせなかった、という形の事案です。

2026年10月、セキュリティ企業 Pillar Security の研究責任者 Eilon Cohen が、AI コーディングエージェント opencode の遠隔コード実行（RCE）の欠陥を公表しました（出典1）。影響を受けるのは 1.0.137 から 1.18.32 までのバージョンで、Windows と WSL のみです（macOS・Linux は影響を受けません）。悪意あるリモート MCP サーバを設定に加えた開発者が OAuth 認証の手順を踏むだけで、追加の操作も同意も無くコードが実行されます（出典1・2）。

本記録が要点と見たのは、次の3点です。

  • 仕込まれる場所は「ブラウザで開く URL」だった。 MCP の OAuth 発見文書にはauthorization_endpoint という項目があり、値はサーバ側が自由に決められる。この文字列が MCP SDK → opencode の OAuth プロバイダ → ブラウザ起動処理を通り、スキームの検査も発行元の照合もされないまま open パッケージの open() に渡っていた（出典1）。Windows 上の open@10.1.2 は対象をエスケープせず base64 化してpowershell -EncodedCommand に渡すため、PowerShell が二重引用符内の $(...) を展開してコードを実行する。ブラウザの起動自体は失敗するが、コードはすでに動いている。
  • URL のスキーム検査では止まらない。 払い出される文字列はhttps://evil.test/$(...) のように正しい形の https URL として成立する（出典1）。opencode は 1.18.33 でスキーム検査を追加したが、Pillar Security は「決定的な修正は依存パッケージを URL を正しく引用符で囲む版へ更新することだった」としている。
  • CVE も勧告も発行されなかった。 Pillar Security は2026年8月29日にGitHub Security Advisory 経由で再現手順を添えて非公開で報告した（出典1）。約1か月後の9月25日、opencode を開発する Anomaly は報告の受領を認めつつ「悪意ある MCP サーバは自社の脅威モデルの外」と回答した（出典2）。修正（PR #51414）は同じ日にリファクタリングとして取り込まれ、9月28日に 1.18.33 として npm へ公開された。CVE の取得も勧告の公開も行われていない（出典1）。Pillar Security は「通常の脆弱性スキャナや依存関係の警告では該当するインストールを特定できず、企業は更新が必要であることに気づかないままになりうる」と警告している（出典2。原文英語）。

深刻度は報告者の評価であり、ベンダーの評価ではありません。 Pillar Security はCVSS v3.1 で 9.8（Critical） を提案し、CWE-78（OS コマンドインジェクション）に分類しています（出典1）。ベンダー側の深刻度評価は存在しません〈未確定1〉。なお、本件は同時期に報じられた opencode の Console（API 資格情報の共有基盤）への侵害とは無関係で、2026年1月に公開された CVE-2026-22812（認証なし HTTP サーバの RCE）とも別の欠陥です（出典2・本記録の確認）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

以下は Pillar Security の報告書に書かれた成立経路を段階ごとに並べたものである（出典1）。 **実際の攻撃が観測された事例の記述は無く、段階は研究者が示した成立条件である**〈未確定4〉。 攻撃者が用意したリモート MCP サーバの OAuth 発見文書に細工した `authorization_endpoint` を置き、 開発者がそのサーバを設定に加えて OAuth の手順を踏むと、 値がスキーム検査も発行元照合もされないまま `open()` へ渡り、 Windows 上で `powershell -EncodedCommand` 経由でコードが実行される。

  1. 1. 初期侵入third_party_research[1]
    攻撃者が用意したリモート MCP サーバが、OAuth 発見文書の `authorization_endpoint` に 細工した文字列を返す。 文字列は `https://evil.test/$(...)` のように**正しい形の https URL** として成立するため、 スキームの検査では弾けない
    根拠: Pillar Security 報告書「A remote MCP server's OAuth discovery document includes an `authorization_endpoint` field. The server controls this free-form string.」（原文英語）
  2. 2. 実行third_party_research[1]
    値が MCP SDK → opencode の OAuth プロバイダ → ブラウザ起動処理を経て、 スキーム検査も発行元照合もされないまま `open` パッケージの `open()` 呼び出しへ渡る。 Windows 上の `open@10.1.2` は対象をエスケープせず base64 化して `powershell -EncodedCommand` に渡すため、 PowerShell が二重引用符内の `$(...)` を展開してコードを実行する。 ブラウザの起動自体はその後失敗するが、コードはすでに動いている
    根拠: 同報告書「On Windows, `open@10.1.2` does not escape the target. It base64-encodes the command and runs it through `powershell -EncodedCommand`」（原文英語）
  3. 3. 影響（暗号化・破壊・改ざん）third_party_research[1] [2]
    開発者の端末上で、opencode を実行している利用者の権限で任意のコードが動く。 追加の操作も同意も必要としない
    根拠: 同報告書および Infosecurity Magazine「execute arbitrary code on a developer's machine during an MCP OAuth authentication process, without additional user interaction or consent」（原文英語）

仕込まれるのは「ブラウザで開く URL」で、PowerShell が引用符の中を展開してしまう原因・手口出典 [1] [2]

Pillar Security が示した経路は次の4段である（出典1）。

段 起きること
1 リモート MCP サーバの OAuth 発見文書に authorization_endpoint が含まれる。値はサーバ側が自由に決められる文字列である
2 その値が MCP SDK → opencode の OAuth プロバイダ → ブラウザ起動処理を経て、スキーム検査も発行元の照合もされないまま open パッケージの open() へ渡る
3 Windows 上の open@10.1.2 は対象をエスケープせず、base64 化して powershell -EncodedCommand に渡す
4 PowerShell は二重引用符で囲まれた文字列の中の $(...) を展開するため、https://evil.test/$(...) のような URL でコードが動く。ブラウザの起動自体はその後失敗するが、コードはすでに実行されている

要点は、払い出される文字列が「正しい形の https URL」として成立することである（出典1）。したがって URL のスキームを検査しても止まらない。opencode は 1.18.33 でスキーム検査を追加したが、Pillar Security は「決定的な修正は、URL を正しく引用符で囲む版へ依存パッケージを更新することだった」としている（出典1・2）。

影響範囲が Windows と WSL に限られるのは、open の実装が OS ごとに違うためである（出典1）。macOS・Linux では PowerShell を経由しないため成立しない。同じソースコードを使っていても、動く OS によって脆弱かどうかが変わる（本記録の整理）——社内の開発端末が Windows 中心であるか否かで該当性が分かれる。

攻撃者の位置は「リモート MCP サーバ」である（出典1・2）。Eilon Cohen は同時期に報じられた Console への侵害との違いを次のように説明している（出典2。日本語訳は本記録・原文英語）。

「侵害はホスト型の鍵プロキシの背後にある旧システムに当たり、利用者がそこに保管していた事業者の鍵を露出させた。我々が報告した脆弱性は向きが逆で、悪意あるリモート MCP サーバがOAuth のハンドシェイクの最中に開発者自身の端末でコードを実行する。標的も攻撃者の位置も異なる」

ベンダーは「脅威モデルの外」と答えた日に修正を取り込み、CVE も勧告も出さなかった再発防止出典 [1] [2]

公開された時系列は次のとおりである（出典1）。

  • 2026年8月29日 — Pillar Security が GitHub Security Advisory 経由で、完全な再現手順を添えて非公開報告
  • 2026年9月25日 — Anomaly が受領を認め、悪意ある MCP サーバは自社の脅威モデルの外と回答。同じ日に修正（PR #51414）がリファクタリングとして取り込まれる
  • 2026年9月28日 — 1.18.33 が npm へ公開される
  • 2026年10月4日 — Pillar Security が報告書を CVE 無しで公開

「脅威モデルの外」という回答と、同日の修正取り込みが並んでいる点が本件の特徴である（本記録の評価）。Pillar Security の表現を借りれば、修正はリファクタリングとして静かに入った。結果として、利用者から見ると「何のための更新か」が分からない。

Pillar Security の警告は次のとおりである（出典2。日本語訳は本記録・原文英語）。

「結果として、通常の脆弱性スキャナや依存関係の警告は、影響を受けるインストールを特定しない。企業は自分たちが更新する必要があることに気づかないままになりうる」

CVE は「直ったかどうか」ではなく「自分が該当するかを知る手段」である（本記録の整理）——資産管理台帳と SBOM、依存関係スキャナは CVE を鍵にして照合する作りになっているため、番号が無い欠陥は、修正が公開されていても組織の点検作業には現れない。

なお、本記録は Anomaly 側の見解を同社の公表資料で直接確認していない〈齟齬2〉。「脅威モデルの外」という回答は Pillar Security の報告書と Infosecurity Magazine の記事が伝えるもので、ベンダーの公開文書として確認したものではない。

推奨されたのは更新だけではない——「リモート由来の文字列をシェルに渡さない」という実装の作法対策・注意喚起出典 [1]

Pillar Security が挙げた対処は、利用者向けと実装者向けに分かれる（出典1）。

利用者向け

  • opencode を 1.18.33 以降へ更新する
  • Windows・WSL で更新できない場合は、検証していないリモート MCP サーバを設定から外す
  • セキュリティ部門は、opencode の導入状況を直接棚卸しする ——CVE が無いためスキャナと依存関係の警告では検出されない

実装者向け

  • open にリモート由来の文字列を渡さない。 open 11.x への更新は助けになるが、報告者はこれを完全な修正ではなく安全網として扱っている
  • スキーム検査は有用だが、それだけでは不十分である
  • URL は引数ベクタとして渡し、リモート入力からシェルコマンドを組み立てない
  • OAuth の発見処理を、設定済みサーバの発行元（origin）に束縛する
  • サーバが返すすべての項目を信頼できない入力として扱う

最後の2項目が、MCP を使う実装全体に効く作法である（本記録の評価）。OAuth の発見文書は本来、サーバが自分の設定を宣言するための仕組みであり、宣言された値を照合せずに使うと、サーバが自分の身元を自称したまま通る。発行元に束縛すれば、authorization_endpoint が設定済みサーバと別のホストを指す時点で弾ける。

「引数ベクタとして渡す」は、言語とプラットフォームを越えて同じ教訓である（本記録の整理）——文字列を組み立ててシェルに渡す設計は、エスケープの責任を呼び出し側に置く。本件では open@10.1.2 がその責任を果たしておらず、opencode 側は「URL なら安全だろう」と見なしていた。

事案の詳細

affected_component①opencode（npm パッケージ `opencode-ai`）1.0.137〜1.18.32 の、 MCP の OAuth 発見文書を処理してブラウザを起動する経路、 ②依存パッケージ `open@10.1.2` の Windows 向け実装（出典1）。 **影響を受けるのは Windows および WSL のみで、macOS・Linux は影響を受けない。**
直接原因リモート MCP サーバが自由に決められる OAuth 発見文書の `authorization_endpoint` の値が、 MCP SDK → opencode の OAuth プロバイダ → ブラウザ起動処理を経て、 **スキームの検査も発行元の照合もされないまま** `open` パッケージの `open()` 呼び出しへ渡っていた（出典1）。 Windows 上の `open@10.1.2` は対象文字列をエスケープせず、 base64 化して `powershell -EncodedCommand` に渡すため、 PowerShell が二重引用符内の `$(...)` を展開してコードを実行する。
impact_mechanism開発者の端末上で任意のコードが、opencode を実行している利用者の権限で動く（出典1）。 **追加の操作も同意も不要で、ブラウザの起動自体は失敗するがコードはすでに実行されている。** **実際の悪用が観測されたという記述は無い**〈未確定4〉。

  • CVE が無い欠陥は、いまの資産管理の仕組みでは原理的に見つからない

セキュリティ技術者への示唆
  • 外部から来た文字列は、URL の形をしていてもシェルに渡さない
    本件の払い出しは `https://evil.test/$(...)` という**正しい形の https URL** である（出典1）。 **スキーム検査を通過し、ホスト名も正常で、それでも PowerShell が中身を展開する**
    取るべき行動 外部入力を使ってブラウザ・エディタ・外部プログラムを起動している箇所を洗い出し、 引数ベクタとしてプロセスを起動する形に書き換える （シェル経由の文字列結合をやめる）。 洗い出しの手がかりとして、`open`・`exec`・`system`・`shell` を含む呼び出しを検索する
  • OAuth の発見文書は「サーバの自称」である——発行元に束縛して照合する
    `authorization_endpoint` はサーバが自由に決められる自由記述の文字列である（出典1）。 **照合しなければ、設定済みサーバとは別のホストを指す値がそのまま通る**
    取るべき行動 OAuth の発見処理で、取得した各エンドポイントのホストが設定済みサーバの発行元と一致するかを検証し、 一致しない場合は接続を中止する。 **サーバが返すすべての項目を信頼できない入力として扱う**方針をコードレビューの観点に加える
  • 同じコードでも、動く OS によって脆弱かどうかが変わる
    本件は Windows と WSL のみが影響を受け、macOS・Linux は影響を受けない（出典1）。 **原因は `open` パッケージの OS 別の実装の違いである**
    取るべき行動 依存パッケージが OS ごとに別の実装を持つ箇所（プロセス起動・ファイル関連付け・ シェル呼び出し）を特定し、最も危険な OS を基準に検査する。 **CI の検査環境が Linux だけの場合、Windows 固有の経路は検査されない**ことを前提に、 Windows 向けの検査を追加する
  • 開発端末の検知条件に「Node.js 系プロセスを親とする PowerShell の起動」を入れる
    実行経路は `powershell -EncodedCommand` であり、 **エンコードされたコマンドを伴う PowerShell の起動は端末側の記録に残る形である**（本記録の評価）。 ただし開発端末では PowerShell の起動自体が日常的に起きるため、親プロセスとの組み合わせで見る必要がある
    取るべき行動 開発端末の EDR・端末ログで、Node.js・opencode を親プロセスとする `powershell -EncodedCommand` の実行を検知条件として設定する。 あわせて、base64 デコード後の内容を記録する設定（スクリプトブロックログ）を有効にする
  • AI エージェントを、資格情報を持たない隔離環境で動かす
    本件で動くコードは opencode を実行している利用者の権限を持つ（出典1）。 **エージェントが利用者の権限で端末上で動く構成そのものが、影響範囲を決めている**（本記録の評価）
    取るべき行動 AI コーディングエージェントの実行環境をコンテナまたは専用 VM に分離し、 長期の資格情報・SSH 鍵・クラウドの認証情報を置かない。 必要な権限は短命なトークンとして都度払い出す
