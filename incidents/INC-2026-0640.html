修正が出てから、3つのことが起きました。

1つめは、悪用の観測が始まったことです。 watchTowr は「パッチが着地したのとほぼ同じ時刻に、最初の実環境での悪用試行がセンサーに到達した」としています（出典18）。成功した試行はまだ観測していないとしつつ、脅威インテリジェンス責任者のJake Knott は「いまのところ誰も成功していないが、それが長く続くとは思っていない」と述べています（原文英語）。Hadrian は修正の公開の数時間前に「php2shell が実環境で大規模に悪用されているのを確認している。観測する攻撃の多くは PHP のセッションアップロード進捗の経路を悪用しており、修正の出荷の前後にさらに多くの攻撃経路が現れると予想する」と報告しました（原文英語・出典18）。Patchstack と Cloudflare も同日のより早い時間帯に試行を観測し、Vega は公開された実証コードを使う試行を観測しています。

ただし、見立ては一致していません〈齟齬9〉。PHP セキュリティチームは、漏洩後に公開された実証コードを検査したものの、リリース時点で機能するものを特定できていなかったとしています（出典14）。CISA はアドバイザリの公開時点で悪用を観測していないとしました（出典15）。「大規模に悪用されている」「機能する実証コードは無かった」「悪用は観測していない」が同じ日に並んでいます。

2つめは、PHP Foundation が事後検証を公表したことです（出典14）。ここで調整開示がどう壊れたかの全容が示されました（すべて UTC）。

  • 10月20日 約15:00：2つの CVE 番号がフォーラムと SNS に出現した—— 誤ったリリース時刻と、誤った CVSS 10.0（実際は9.2）が付いていた。技術的詳細は漏れていない
  • 10月20日 19:30：事前告知を前倒しし、リリースを10月22日14:00 から10月21日14:00 へ1日繰り上げた（時刻は維持）
  • 10月20日 約20:00：Calif がエクスプロイトが複数の標的に対して動作する様子を映した動画を誤って公開した。削除後もコピーが拡散し、限定的な追加の詳細を露出させ、公開 PoC の開発を加速させた
  • 10月20日 約23:00：一部の重要インフラ事業者と共有した緩和策の案内も漏洩した可能性がある
  • 10月21日 07:41：Chainguard が、調整公開の6時間以上前に、修正を含むビルド済みイメージを公開した

PHP Foundation は Chainguard の行為を「一方的にエンバーゴを破った」と書きました（出典14・19）。「攻撃者は、他のすべての PHP 利用者がまだリリースを待っているあいだに、修正をバイナリの形で研究できるようになった。これは多くの関係者が調整開示に向けて費やした数週間の作業を無視するものだった」（原文英語）。Chainguard の CEO である Dan Lorenc はこれを擁護しています（出典19）—— 「実環境でエクスプロイトが出たときに、早く出す判断をした」。他の研究者とビデオ会議で話した後に出荷を決め、即座に調整グループへ通知したとし、自社のテストハーネスとフロンティア AI モデルで独自に脆弱性を発見し、修正のテストも手伝ったと述べています。

3つめは、2024年に兆候を把握していたことが明かされたことです（出典14・21）。CVE-2026-109618 の根本原因は、Sovereign Tech Agency が資金を出しOSTIF が組織した2024年の Quarkslab 監査の指摘を直す過程で、PHP のコア開発者が最初の兆候に気づいたものでした。当時は悪用が理論上のもので、具体的な攻撃経路が特定されておらず、影響がより明確な別の問題が優先されました。提案された修正はいずれも互換性の破壊・新たな DoS リスク・サードパーティ拡張全体にわたる変更の要求といったコストを伴い、セキュリティチームの合意形成はアプローチを決めきれず、作業は何か月も停滞と再開を繰り返しました。

PHP Foundation はこれを言い切りました。 「我々は否定しない。この遅延は構造的な失敗であり、セキュリティチームの意思決定プロセスと、その資源の不足の両方が原因である」（原文英語・出典14）。対策として、合意形成から多数決への移行を始め、トレードオフの難しい重大な脆弱性は早期に財団の指導層へ上げることにしました。

そして、見つけたのは AI でした。 OpenAI は、Calif が GPT-5.6 Sol モデルを使って重大な欠陥を特定したとしており、Wiz は独立に2件とも発見して報告しています（出典18・20）。Calif の説明では、最初の OOM の不具合は2020年に見つかり、2024年の監査で再発見されたが、悪用が実証されなかったため修正されなかった——フロンティア AI モデルのおかげで OOM の弱点をより深く分析でき、最終的に RCE に変えられた（出典19）。Wiz は「これらの発見は PHP において、そしておそらくソフトウェアの歴史においても、最も深刻な脆弱性のひとつに位置づけられる。根底にある欠陥は数十年にわたり存在していたが、その悪用可能性を実証するには、人間の研究者が実際に達成できる限界に近い、極めて複雑な一連の手順を要した」と述べています（原文英語・出典18）。

国内では、脆弱性がサービスの廃止を直接引き起こしました。 旅行ゲーム「ワールドクエスト」は2026年10月21日をもって即日サービスを終了し、「サーバで使っている PHP 自体に深刻な脆弱性が見つかったとの発表があったが、ゲームが古い仕組みの上で動いているため十分な対策をとれない」「利用者の情報を守ることを第一に考えた」と説明しました（出典23）。翌10月22日には、ゲーム「僕の魔界を救って！」も終了を発表しています—— 「サービス開始から10年以上が経ち、OS や PHP を含めて古い環境で稼働していたため、安全な対応や新環境への移行は現実的でない」（出典24）。

「PHP 5以降が影響」の出どころは、攻撃ツールのバナーだった被害規模・影響範囲

影響を受けるバージョンについて、一次公表には記載がありません（出典1）。PHP セキュリティチームは「影響を受けるバージョンと修正バージョンはリリースと同時に公表する」としています（出典1）。

一方で、報道と注意喚起には3種類の記載が出回っています（本記録の整理）。

  • 「PHP 5以降」 — CERT-EU の注意喚起（出典3）。IPA もこれを引いている（出典2）
  • 「PHP 5.4以降」 — Sansec（出典5）。ただし同社は、これがリークされた攻撃ツール「PHP2Shell」のバナーの主張であることを明記し、"claims"（主張）として扱っている
  • 「5・6・7・8 が影響するとの報道があるが、修正はサポート中の PHP 8 系のみになると見る研究者もいる」 — Huntress（出典4）

本記録が注目するのは、Sansec の書き方です（本記録の評価）。「PHP 5.4以降」という具体的な数字の出どころが攻撃者側のツールの表示だと明記しているため、読者はその数字の重みを自分で判断できます。 出どころを書かずに「PHP 5.4以降が影響」とだけ書けば、検証された事実のように読めてしまいます。

IPA も同じ配慮をしています（出典2）。「CERT-EU は、複数の情報源に基づき、CVE 識別子をCVE-2026-109618 および CVE-2026-109619 とする注意喚起を公表しています。また、同注意喚起では、PHP 5以降が影響を受けるとされています」（出典2）。「CERT-EU の注意喚起では」という限定が入っています。

読者が取るべき姿勢は、次のとおりです（本記録の評価）。リリース前の段階で影響バージョンを絞り込もうとしない。 「PHP 8.4 だから大丈夫」「PHP 7 は対象外」という判断は、どの情報源にも裏付けがありません。 棚卸しは、バージョンで切らずに全部を数えます。

流通している CVE 番号は、公式の記録にまだ存在しない評価・解釈

本記録が2026年10月21日08:09 UTC に照会した結果です（本記録の確認）。

  • NVD（米国の脆弱性データベース） — CVE-2026-109618 の登録は無し（照会結果0件）
  • CVE Program の公式記録 — 存在しない（CVE_RECORD_DNE）
  • PHP セキュリティチームの予告（出典1） — CVE 番号の記載なし

つまり、報道と注意喚起が使っている CVE-2026-109618 / CVE-2026-109619 という番号は、本記録の確認時点では公式の記録に裏付けがありません（本記録の確認）〈齟齬1〉。

これは「番号が間違っている」という指摘ではありません（本記録の整理）。採番の予約と公開は別の工程であり、リリースと同時に公開されることは普通にあります。 IPA が「CERT-EU は、複数の情報源に基づき……CVE 識別子を……とする注意喚起を公表しています」と書き方を分けているのは、この段階を正確に反映しています（出典2）。

実務上の意味は2つあります（本記録の評価）。

1つ目。脆弱性管理の仕組みが CVE 番号で動いている組織では、この段階では何も検知できません。 スキャナも、SBOM の照合も、資産管理の脆弱性アラートも、CVE が公開されていなければ反応しません。 「ツールが何も言わない」は「影響が無い」ではありません。

2つ目。社内の連絡に CVE 番号を使うと、受け手が確認できません。 「CVE-2026-109618 に対応してください」と伝えても、受け手が NVD を見れば「そんな CVE は無い」と返ってきます。 この段階では、CVE 番号ではなく「10月21日23時（日本時間）に公開される PHP のセキュリティリリース」という呼び方で伝えるほうが確実です（本記録の評価）。

対策はサーバ側にしかなく、WAF もアプリ側の緩和も間に合わない可能性がある対策・注意喚起

Sansec は、対策がインフラ側にしかないことを明記しています（出典5）。

「サーバ上の PHP 本体を更新する必要があり、ストアのコード側では対処できない」（出典5。要約）。自分で Web サーバ環境を管理していない場合は、ホスティング事業者に「いまから待機し、リリース後すぐ適用する」よう依頼するよう勧めています（出典5）。

さらに踏み込んだ記述があります（出典5）。同社は自社製品（Sansec Shield）のアプリケーション層の緩和策を「可能であれば」提供する予定としつつ、攻撃はストアのコードや Shield より前に実行されるためルールの提供を待つべきではないと警告しています（出典5）。

これは、自社製品で解決できると言わない書き方です（本記録の評価）。PHP のコアで実行が起きるなら、PHP の上で動く緩和策は後ろにいます。

CERT-EU は別の角度の緩和策を挙げています（出典3）。即時のパッチ適用の準備を勧め、すぐに適用できない場合はインターネットに公開しているアプリケーションの隔離を検討するよう求めています（出典3）。

Huntress は「パッチが出るまでにできること」を挙げています（出典4）。

  • すべての PHP の棚卸し——Web サーバから始め、見えにくい場所（php.exe / php-cgi.exe を同梱するベンダー機器や Windows ソフト、cPanel・Plesk などの管理用パネル、WordPress・Drupal・Joomla・Magento）を探す
  • 適用の作業枠を10月21日の東部時間10時（日本時間23時）に確保し、インターネットに面したものから先に直す
  • サポート終了（EOL）の PHP 環境を特定する——PHP 5・7・8.0／8.1 では修正が出ない可能性がある。更新するか、インターネットから外すか、VPN や WAF の後ろに置く
  • PHP が何を起動するかを見る——PHP のワーカープロセス（php-fpm・php-cgi・httpd・apache2）がシェル（sh・bash・cmd.exe・powershell.exe）、インタプリタ（python・perl）、ダウンロードツール（curl・wget・nc・certutil.exe）を起動したら警報を上げる
  • 何か見つかったらサーバを隔離し、Web サーバと PHP のログを保全する——Web ルートの新規ファイル、新しい cron・タスク・アカウントを確認する

本記録が付け加える評価は1つです（本記録の評価）。「PHP のワーカーがシェルを起動したら警報」という検知は、本件のためだけの検知ではありません。 Huntress 自身、「ほぼすべての PHP 侵入事案で見るパターン」と述べています（出典4）。本件を機に入れておけば、本件が空振りでも別の侵入で効きます。

「PHP がどこで動いているか」を利用者が把握できない層がある被害規模・影響範囲

IPA の注意喚起には、他の資料に無い指摘があります（出典2）。

「PHP は、ウェブアプリケーションだけでなく、ソフトウェア製品やネットワーク機器などの内部でも使用されている場合があります。製品や機器の内部でのPHPの利用状況は、利用者側では把握できない場合があります」（出典2）。

そのうえで IPA は、現実的な線を引いています（出典2）。「現時点で、利用しているすべての製品について、内部でのPHPの利用有無を個別に確認することをお願いするものではありません」（出典2）。まずは製品のマニュアルや開発元・提供元のセキュリティ情報を確認し、PHP の利用が把握できている製品について今後の情報を注視するよう求めています（出典2）。

この書き方は実務的です（本記録の評価）。「全製品の内部を調べろ」は実行できない指示であり、実行できない指示は無視されます。 「把握できているものから」という線を引いたことで、手が動きます。

Huntress も同じ問題を別の表現で挙げています（出典4）。「PHP は、PHP で動いていると表に出ていないかなりの量のソフトウェアを静かに支えている。アプリではなく PHP そのものに重大なバグが入ると、脆弱なバージョンを探しに行かなければならない場所の数が、あっという間に非常に多くなる」（出典4。要約・原文英語）。

本記録が読者に残したい問いは次のとおりです（本記録の評価）。「自社の資産台帳で、PHP のバージョンを答えられる資産は何%か。」 この問いに答えられないことは、本件に限った弱点ではありません。 同じことは OpenSSL でも、Java でも、ネットワーク機器の内蔵 Web UI でも起きます。

悪用はまだ確認されていないが、「15分」という予測の重さは別に測る未確定事項

  • watchTowr と Huntress のいずれも、実環境での悪用を観測していない（出典6）

  • IPA も「現時点でIPAが悪用した攻撃を確認しているわけではない」と明記（出典2）

本記録はこの15分という数字を、公表された予測として記録しますが、検証された所要時間としては扱いません（本記録の方針）。理由は、本記録が出典5 を直接取得して確認したところ、算出の根拠が記事に書かれていなかったためです（本記録の確認）〈齟齬5〉。同社が背景として挙げているのは、攻撃ツールの画面が漏れたことと、詳細が事前に漏洩したことです（出典5）。

それでも、この予測が示している構造は確かです（本記録の評価）。修正が公開されると、差分（パッチの中身）から脆弱性の場所が分かります。 本件は詳細が事前に漏れており、watchTowr はすでに1件の再現に成功したと述べています（出典6）。つまり、攻撃者側に残っている作業は少ない状態です。

実務の帰結は1つです（本記録の評価）。「リリースを見てから計画を立てる」では遅い可能性があります。 棚卸しと作業枠の確保は、リリース前に終わっていなければなりません——本件の注意喚起がどれも「事前準備」を主題にしているのは、これが理由です（出典2・4・5）。

これは記録する価値があります。PHP セキュリティチームは予告の時点で、「詳細が公になった場合、または実環境での悪用の証拠が現れた場合には前倒しする権利を留保する」と書いていました（出典1）。

それでも時刻は動きませんでした（本記録の照合）。

Apache の `mod_php` では「アプリのコードが動く前」に攻撃が成立する——防げるのはアプリ側ではない原因・手口

修正の公開で、2件の正体が明らかになりました。

識別子 題名 内容
CVE-2026-109618 RCE via OOM corruption メモリ不足（OOM）時の longjmp() による早期終了が適切に扱われず、メモリが不正な状態のまま残る。リクエスト終了処理がその不正状態を読む
CVE-2026-109619 RCE via stale global state リクエストが所有する内部状態が、その基になるメモリの解放後も残り、次のリクエストが通常の初期化より前にその古い状態を使う

双方に CWE-416（use-after-free）を含む5つの CWEが割り当てられ、CVSS v4.0 のベクトルはAV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H です（出典11・12）。ネットワークから・権限不要・利用者の操作不要で、攻撃複雑性は「高」・攻撃要件は「あり」。

実務上もっとも重いのは、SAPI ごとの差です（出典11）。

  • mod_php（Apache） — 最もリスクが高い。 デフォルトの PHP 入力・メモリ制限と複数ワーカーの prefork 構成で、HTTP 経由の完全な RCE が実証されている。 攻撃は「アプリケーションのコードより前」に発生する
  • PHP-FPM — 起動失敗時に子プロセスを終了するため不正状態の利用は防がれる。ソース解析上は影響を受けると考えられるが、完全な悪用コードは実証されていない
  • FrankenPHP — ソース解析上 mod_php と同様に終了処理を無条件に呼ぶため攻撃を受けやすいと考えられるが未検証
  • LSAPI — FPM と同様のモデル。アプリ固有の悪用は可能性が高いが未検証

「アプリケーションのコードより前」という一句が、この事案の核心です（本記録の評価）。

PHP の脆弱性と聞いたとき、多くの組織はまず「自分のアプリに該当する書き方があるか」を探します。本件ではそれが意味を持ちません。入力の検証を厚くしても、WAF のルールを足しても、フレームワークを最新にしても—— 攻撃が成立するのはアプリのコードが動く前です。

Sansec が「対策はサーバ上の PHP の更新であり、アプリ側では対処できない」と書いていたのは、この意味でした（出典5）。初報の時点ではベンダーの主張でしたが、一次資料で裏付けられました（本記録の照合）。

なお、「未検証」は「安全」ではありません。アドバイザリは双方とも、更新だけが確実な対策であると明記しています。

以下は本記録の整理である。 この食い違いは、矛盾というより観測点の違いである。

  • 「試行」と「成功」は違う。 watchTowr は試行の到達を報告しつつ、成功した試行は観測していないとしている。Hadrian の「大規模に悪用されている」が試行の量を指しているなら、両者は両立する
  • 「機能する PoC が無い」と「悪用試行がある」は両立する。 攻撃者は機能しないコードでも投げる。PHP セキュリティチームが検査したのは公開されていた PoC であり、非公開のコードについては何も言っていない
  • CISA の「観測していない」は、CISA 自身の観測範囲の話である。 民間ベンダーのセンサー網とは見える範囲が違う

読者（日本の CISO）が判断に使うべき数字はどれか。 本記録の評価では、どれも使えない。

使えるのは「試行は始まっている」という事実だけである。 件数も成功率も、この時点の公開資料からは定まらない。「大規模に悪用されている」を根拠に緊急対応を発令するのも、「悪用は観測されていない」を根拠に様子を見るのも、どちらも同じ日の資料から引ける。

したがって判断は観測数ではなく、脆弱性の性質で行うべきである（本記録の評価）——未認証・リモート・CVSS 9.2・mod_php で実証済み・PHP を使うサイトが全体の約70%・Unit 42 が2,260万超の露出インスタンスを特定。 この条件が揃っているときに、観測件数の多寡は対応の優先度を変えない。

なお、実環境での侵害の成立（データの流出・サイトの改ざん・シェルの獲得）は、本記録作成時点でどの資料も報告していない。 Sansec の「公開から15分で大量攻撃」という予測の当否も、確定していない〈齟齬9〉。

  • 2024年：Sovereign Tech Agency が資金を出し OSTIF が組織した Quarkslab による外部監査の指摘を修正する過程で、PHP のコア開発者が OOM 問題の最初の兆候に気づいた
  • 当時、悪用は理論上のものにとどまり、具体的な攻撃経路は特定されていなかった。影響がより明確な別の脆弱性への対応が優先された
  • 提案された修正はいずれも深刻なコストを伴った——互換性の破壊・新たな DoS リスク・サードパーティ拡張全体にわたる変更の要求

  • 2026年8月11日：Calif が無条件の RCE を報告し、OpenAI が独立に同じ根本原因を報告。以降これが最優先事項になった

そして PHP Foundation はこう書いた（原文英語・出典14・19）。

我々は否定しない。この遅延は構造的な失敗であり、セキュリティチームの意思決定プロセスと、その資源の不足の両方が原因である。

以下は本記録の評価である。 この文は、オープンソースの基盤ソフトウェアの脆弱性対応について、実務家が普段言語化しにくいことを当事者が自ら書いている点で価値がある。

「悪用が実証されていないから直さない」は、合理的な判断として成立する。 修正に互換性の破壊と DoS リスクと拡張全体の変更が伴うなら、理論上の脆弱性のために払うコストとして正当化しにくい。本件で起きたのは、その判断が「2年後に AI が悪用可能性を実証する」という変化によって覆されたことである。

PHP Foundation が示した対策は2つである（出典14・19）。

  • トレードオフの難しい重大な脆弱性は、より早く財団の指導層へ上げることにした

読者（日本の CISO）への含意はこうである。 自社のシステムが依存している基盤ソフトウェアの脆弱性対応能力は、自社の対応能力の一部である。 本件は、「理論上の脆弱性を2年間抱えた」状態が、依存する側には一切見えないまま続いていたことを示している。 依存先の体制・資金・人員の厚みは、自社のリスク評価に入れるべき変数である——ただし、それを外部から測る手段は乏しい（本記録の留保）。

Wiz の評価（原文英語・出典18）：

これらの発見は PHP において、そしておそらくソフトウェアの歴史においても、最も深刻な脆弱性のひとつに位置づけられる。根底にある欠陥は数十年にわたり存在していたが、その悪用可能性を実証するには、人間の研究者が実際に達成できる限界に近い、極めて複雑な一連の手順を要した。

以下は本記録の評価である。 この一文が本件の性格を決めている。

欠陥は新しくない。 PHP 5.4 以降に存在し、2020年に兆候が見え、2024年の監査で再発見されている。変わったのは「悪用できると証明する能力」である。

これは、脆弱性管理の前提を1つ崩す。 「悪用が実証されていない脆弱性は優先度が低い」という判断は、悪用の実証が人間の能力で律速されていることを暗黙に前提にしていた。 その前提が外れると、過去に「理論上」と判定して据え置いた脆弱性の在庫が、まとめて再評価の対象になる。

PHP Foundation 自身が、この変化を数字で示している（出典14・18）——AI が従来より多くの PHP 脆弱性を表面化させており、2026年7月1日以降に15件の CVE を公開した一方、100件超の無効・重複・再現不能な報告も処理している。 報告は増え、そのうち本物の割合は下がり、修正はエンジニアの人数で律速される。

Wiz はもう1つ重要なことを示している（出典18）。2件の CVE は PHP の4つのメモリ安全性の問題をまとめたものであり、すべての変種を覆っているわけではない。追跡されている変種と、おそらく追跡されていない変種の両方が存在する。 つまり「この2件を直せば終わり」ではない（本記録の評価）。

読者（技術者）への含意はこうである。 自社の脆弱性管理台帳で「悪用困難」「理論上のみ」として据え置いた項目を、もう一度見直す価値がある。 とくにメモリ安全性に関わる問題で、修正に互換性破壊や性能劣化が伴うために保留したものは、本件と同じ構図にある。

CISA は「オフラインにせよ」と書き、IPA は「廃止も検討せよ」と書いた当局対応出典 [15] [16] [20] [22] [25]

公的機関の注意喚起が、通常の「速やかに更新してください」を越えた。

CISA のアラート「Critical Vulnerabilities in PHP Require Immediate Patching」（2026年10月21日・出典15）

  • 組織内で稼働するすべての PHP を特定して棚卸しする——他のソフトウェアの構成要素として組み込まれている場合もあり、見えにくい可能性がある
  • インターネットに公開されたシステムを優先して、直ちにパッチを適用する
  • すぐに更新できない場合、または PHP 8.1 以前のサポート終了版を使い続けている場合は、パッチ適用または更新までシステムをオフラインにする
  • 更新までの間、WAF である程度防御できる可能性がある
  • PHP のワーカープロセスがシェルを起動する、またはツールをダウンロードする挙動を監視する
  • アドバイザリ公開時点で悪用は観測していない

NSA・FBI も同趣旨の警告を出し（出典20・22）、英 NCSC も更新・緩和ができない場合のオフライン化の検討を助言した（出典25）。欧州では、実際に一部の政府サイトがオフラインにされた（出典20）。

IPA の続報（2026年10月22日・出典16）は、さらに踏み込んでいる。「修正対応が難しい場合について」として6段の判断手順を示した。

  1. 利用中の PHP のサポート状況を確認する（8.1 以前は EOL。修正が出ないバージョンを使っているなら、サポート中の PHP への更新や対策済み製品・サービスへの移行を検討する）
  2. 更新・移行までの暫定対策を講じる（有効な暫定対策が難しい場合は、攻撃を受けた際の被害と業務への影響を踏まえ、外部からのアクセス遮断やサービスの一時停止が必要か判断する）
  3. システムの状況と更新・移行の難易度を把握する（アプリの改修・動作確認の必要、開発時の資料やノウハウの不足、担当者の不在、保守契約の終了により対策が難しくなっている場合がある）
  4. 組織として対応の実現性を検討する（システム管理担当者だけでなく、事業責任者や経営層も含め、更新・移行とその後の継続的な維持管理に必要な人員・予算・保守体制を確保できるか検討する）
  5. 今後の対応方針を決める——「体制を確保する見通しが立たない場合は、現行システムの継続を前提とせず、保守を受けられる製品・サービスへの移行、提供機能の縮小、公開の終了やシステムの廃止も含めて検討してください」
  6. 利用者や業務への影響を考慮して実施する（必要なデータの移行・保存、代替手段の案内を計画する）

以下は本記録の評価である。 注意喚起が「廃止」を選択肢として正面から書くのは異例である。

通常の脆弱性対応の文書は「更新してください」で終わる。更新できない組織をどうするかは、暗黙に「がんばって更新する」か「リスクを受容する」のどちらかに委ねられていた。IPA の6段は、第3の道を明示した——更新できない、暫定対策も効かない、体制も作れないなら、そのシステムは閉じるという道である。

そして、国内で実際にそれが起きた（次節）。

CISA と IPA の書き方の違いも記録しておく価値がある。 CISA は「オフラインにせよ」と技術的な措置を指示した。IPA は「経営層を含めて実現性を検討し、廃止も含めて方針を決めよ」と意思決定の手順を示した。 後者は、更新できない理由が技術ではなく組織（人員・予算・保守体制・担当者の不在）にあることを前提にしている（本記録の読み）。

国内では脆弱性がサービスを2つ終わらせた——「古い仕組みのため対策がとれない」業務・事業への影響出典 [16] [23] [24]

初報の時点で本記録が記録したのは、国内の著名サービスが緊急メンテナンスに入ったことだった。続報では、それが廃止に至った例が出た。

旅行ゲーム「ワールドクエスト」（2026年10月21日・即日終了・出典23・24）

  • 運営は同日をもってサービスを終了すると発表した
  • 「サーバで使っているプログラミング言語 PHP 自体に深刻な脆弱性が見つかったとの発表があったが、ゲームが古い仕組みの上で動いているため十分な対策をとれない」
  • 「利用者の情報を守ることを第一に考えた」
  • 公式サイトの告知では「突然のお知らせとなり、ご迷惑をおかけしますことを心よりお詫び申し上げます」と謝罪した
  • 同作は2011年に GREE で公開され、モバゲー・ワクプラにも展開した後、2019年5月に一度終了。2020年5月に「コロナ禍で海外旅行に行けない人たちがゲームの中で海外旅行を楽しめるように」として復活し、中身をほぼ変えないまま運営されていた

ゲーム「僕の魔界を救って！」（2026年10月22日に発表・出典24）

  • 「サーバーで使う PHP に深刻な脆弱性が確認された」
  • 「サービス開始から10年以上が経ち、OS や PHP を含めて古い環境で稼働していたため、安全な対応や新環境への移行は現実的でない」
  • 「利用者の情報を危険にさらしたまま運営は続けられないと判断した」

以下は本記録の評価である。 2件の説明は、ほとんど同じ構造をしている。

  1. PHP 自体の脆弱性である——アプリ側のコードを直しても防げない
  2. 稼働環境が古い——PHP のバージョンが修正対象の4ブランチに入っていないか、OS ごと古い
  3. 移行が現実的でない——10年以上前の仕組みの上で動いており、新環境への移行は作り直しに近い
  4. したがって、利用者の情報を守るには止めるしかない

これは IPA の6段の第5段がそのまま実行された形である（本記録の整理）——「体制を確保する見通しが立たない場合は、現行システムの継続を前提とせず（中略）公開の終了やシステムの廃止も含めて検討してください」。

本記録が注目するのは、判断の速さである。 ワールドクエストは、修正の公開（日本時間10月21日23時ごろ）と同じ日に終了を発表している。 脆弱性の公表から廃止の決定までが1〜2日である。これは「検討した結果できなかった」のではなく、「できないことが最初から分かっていた」ことを示す（本記録の推定）。

ワールドクエストには、もう1つ読むべき点がある。 2019年5月に一度終了したサービスが、2020年5月に「中身をほぼ変えないまま」復活していた。 復活の判断は利用者の声に応えるものだったが、その時点で技術的な更新は行われていない。 「動いているから続ける」という運用が、6年後に脆弱性1件で終わる形になった（本記録の評価）。

読者（日本の CISO）への含意はこうである。 自社が抱える「古いが動いているシステム」の一覧は、廃止の判断を迫られたときの候補リストである。 本件のように基盤ソフトウェアに未認証 RCE が出たとき、更新できないシステムに残る選択肢は「止める」しかない。 その判断を当日に下せるよう、何を止めるとどの利用者がどう困るかを事前に把握しておく必要がある。

なお、本記録は国内の全サービスを網羅的に調べていない。 2件は本記録が確認できた範囲であり、同じ事情を抱えるサービスは他にもあると考えられるが、数は推定しない（figures 参照）。

  • **自社サービスの土台（言語処理系・ミドルウェア）のバージョンを答えられる状態にする**
    **本件は PHP そのものの脆弱性であり、 アプリケーションの脆弱性ではない**（出典4）。 **PHP は WordPress・Drupal・Joomla・Magento の基盤であり、 共用ホスティング、管理用パネル、 さらに「PHP で動いていると表に出ていない」製品でも 使われている**（出典4）。 **IPA は、製品・ネットワーク機器の内部での利用は 利用者側では把握できない場合があると指摘している**（出典2）。
    取るべき行動 **①資産台帳に「言語処理系とそのバージョン」の欄があるかを確認し、 無ければ追加する（PHP・Java・Python・Node.js・OpenSSL）。** **②答えられない資産の割合を数え、経営に出す—— これが本件に限らない恒久的な弱点の大きさである。** **③ベンダー製品については、調達と更新の契約に 「内蔵する第三者コンポーネントの脆弱性情報を通知する」条項が あるかを確認する。**
  • **「15分で悪用が始まる」という予測を、根拠とセットで経営に伝える**
    **Sansec は修正の公開から15分以内に大量攻撃が始まると 予測している**（出典5・6）。 **本記録が出典5 を直接取得して確認したところ、 この数字の算出根拠は記事に書かれていなかった**（本記録の確認） 〈齟齬5〉。 **一方、watchTowr と Huntress は実環境での悪用を 観測していないとしている**（出典4・6）。 **予測と観測を混ぜて伝えると、判断の前提が崩れる**（本記録の評価）。
    取るべき行動 **①経営に上げる資料で「観測された事実」と「ベンダーの予測」を 別の欄に分ける。** **②予測を使う場合は出所と根拠の有無を併記する （「Sansec の予測。根拠は記事に示されていない」）。** **③予測が外れた場合も対応が無駄にならない施策を選ぶ （棚卸し・監視の追加は、本件が空振りでも残る）。**
  • 「更新できない」の次に用意しておく選択肢は「止める」である。 本件では国内で2件、サービスが実際に終わった
    **CISA は「すぐに更新できない場合、または PHP 8.1 以前の サポート終了版を使い続けている場合は、 パッチ適用または更新までシステムをオフラインにする」ことを求めた** （出典15）。 **IPA は「体制を確保する見通しが立たない場合は、 現行システムの継続を前提とせず（中略）公開の終了やシステムの廃止も含めて 検討してください」と書いた**（出典16）——**注意喚起が廃止を 選択肢として明記するのは異例である。** **そして実際に、旅行ゲーム「ワールドクエスト」が2026年10月21日付で 即日終了し、「僕の魔界を救って！」が10月22日に終了を発表した** （出典23・24）。**いずれも「古い環境のため十分な対策がとれない」 ことを理由としている。**
    取るべき行動 **自社が抱える「古いが動いているシステム」の一覧を作り、 各システムについて①更新できるか②暫定対策が効くか ③移行に要する期間と費用④止めたときに困る利用者と業務——の 4点を平時に埋めておく。** **基盤ソフトウェアに未認証 RCE が出たとき、 ③が長く①②が不可なら残る選択肢は停止・廃止だけである。** **その判断を当日に下せるよう、承認者と告知文の雛形も用意する**
  • 「悪用が実証されていない」を据え置きの根拠にできる時代は終わりに近い。 台帳の保留案件を見直す
    **本件の根本原因は2020年に見つかり、2024年の監査で再発見されたが、 悪用が実証されなかったため修正されなかった**（出典19）。 **Calif は、フロンティア AI モデルのおかげで OOM の弱点をより深く 分析でき、最終的に RCE に変えられたと説明している。** **Wiz は「根底にある欠陥は数十年にわたり存在していたが、 その悪用可能性を実証するには、人間の研究者が実際に達成できる限界に 近い、極めて複雑な一連の手順を要した」と述べた**（原文英語・出典18）。 **変わったのは欠陥ではなく、悪用を証明する能力である**（本記録の評価）。
    取るべき行動 **自社の脆弱性管理台帳で「悪用困難」「理論上のみ」「PoC なし」を 理由に据え置いた項目を抽出し、再評価する。** **とくにメモリ安全性に関わる問題で、修正に互換性破壊や性能劣化が 伴うために保留したものを優先する。** **据え置きの判断には「いつ再評価するか」の期限を必ず付け、 期限の無い保留を台帳から無くす**
  • 依存している基盤ソフトウェアの「修正能力」は、自社のリスク変数である。 本件は2年間、依存する側に見えなかった
    **PHP Foundation は「この遅延は構造的な失敗であり、 セキュリティチームの意思決定プロセスと、その資源の不足の両方が原因である」 と認めた**（原文英語・出典14）。 **提案された修正はいずれも互換性の破壊・新たな DoS リスク・ サードパーティ拡張全体にわたる変更の要求を伴い、 合意形成はアプローチを決めきれず、 エンジン深部の知識を持つ開発者は少数だった。** **2026年7月1日以降に15件の CVE を公開し、 あわせて100件超の無効・重複・再現不能な報告も処理している。** **この状態は、PHP に依存する組織からは一切見えなかった。**
    取るべき行動 **自社の重要システムが依存する基盤ソフトウェア（言語処理系・ Web サーバ・ミドルウェア・主要ライブラリ）を列挙し、 それぞれについて①維持組織の形態（財団・企業・個人） ②資金源 ③セキュリティ対応の公表実績——を1ページで記録する。** **測れない部分が多いことは前提として、 「誰も維持していない」ものを見つけることが目的である。** **PHP Foundation が資金提供を求めていることも、 依存する側の選択肢として検討する**
セキュリティ技術者への示唆
  • **影響バージョンが未公表の段階では、バージョンで絞り込まずに全数を数える**
    **一次公表に影響バージョンの記載が無い**（出典1）〈未確定2〉。 **流通している記載は「PHP 5以降」（CERT-EU。出典2・3）、 「PHP 5.4以降」（リークされた攻撃ツールのバナーの主張。出典5）、 「修正はサポート中の PHP 8 系のみになると見る研究者もいる」 （Huntress。出典4）と分かれている。** **どれも一次情報ではない**（本記録の整理）。
    取るべき行動 **①`php -v` を全サーバで走らせ、 バージョンとインストール経路（OS パッケージ・ ソースビルド・コンテナイメージ・同梱）を一覧にする。** **②Web サーバ以外も探す——コンテナイメージ、 CI のビルド環境、管理用パネル（cPanel・Plesk）、 ベンダー機器や Windows ソフトに同梱された php.exe / php-cgi.exe（出典4）。** **③「対象外」と判断した資産には、 その判断の根拠（どの情報源のどの記載か）を書き添える—— 根拠が後で崩れたときに再点検できるようにする。**
  • **PHP のワーカープロセスが何を起動するかを監視する（本件の有無にかかわらず残る）**
    **Huntress は、exploitation は PHP から起動される 不審な子プロセスとして現れる可能性が高いとし、 これが「ほぼすべての PHP 侵入事案で見るパターン」だと 述べている**（出典4）。 **具体的には、php-fpm・php-cgi・httpd・apache2 が シェル・インタプリタ・ダウンロードツールを起動するパターンである** （出典4）。
    取るべき行動 **①PHP のワーカープロセスを親とするプロセス起動を記録し、 シェル（sh・bash・cmd.exe・powershell.exe）、 インタプリタ（python・perl）、 ダウンロードツール（curl・wget・nc・certutil.exe）を 子に持つ場合に警報を上げる。** **②リバースシェルの痕跡（/dev/tcp/・fsockopen・mkfifo）と、 Web サーバから直接実行される偵察コマンド （whoami・id・uname -a・ipconfig）をコマンドラインで探す。** **③導入の前に平常時の挙動を記録する—— 画像変換や PDF 生成で外部コマンドを呼ぶ環境では誤検知が出る。**
  • **適用の順序を「インターネットに面したものから」で固定する**
    **Huntress は作業枠を2026年10月21日の東部時間10時 （日本時間23時）に確保し、インターネットに面したものから 先に適用するよう勧めている**（出典4）。 **Sansec は、公開から15分以内に大量攻撃が始まると 予測している**（出典5）〈齟齬5〉。 **全数を同時に直せない以上、順序が結果を決める**（本記録の評価）。
    取るべき行動 **①棚卸しの一覧に「インターネットから到達可能か」の列を付け、 適用の順序をその列で決める。** **②Linux ディストリビューションとホスティング事業者の バックポート版の提供状況を、適用の前に確認する（出典4）。** **③自分で環境を管理していない場合は、 事業者に「リリース後すぐ適用する」よう依頼し、 依頼した記録を残す（出典5）。**
  • **EOL の PHP を「直せないもの」として台帳に明示する**
    **Sansec は PHP 8.1以前がサポート外であり、 公式の修正が出ないと指摘している**（出典5）。 **Huntress も PHP 5・7・8.0／8.1 では修正が出ない可能性が あるとしている**（出典4）。 **IPA は「サポート終了の古いPHPを利用し続けている ウェブサイト・ウェブサービスも見受けられる」と述べている**（出典2）。
    取るべき行動 **①EOL の PHP で動いている資産を特定し、 「修正が出ない」ことを台帳に明示する （「未適用」ではなく「適用できない」として扱う）。** **②それぞれについて、インターネットからの切り離し・ VPN や WAF の後ろへの配置・ホスティング事業者への バックポート依頼のどれを取るかを決める（出典4・5）。** **③サポート対象版への移行計画と期限を、 本件の対応とは別に立てる——本件が終わっても 次の PHP の脆弱性で同じことが起きる。**
  • **WAF やアプリ層の緩和に寄りかからない**
    **Sansec は、自社製品（Sansec Shield）の アプリケーション層の緩和策を「可能であれば」提供する予定としつつ、 攻撃はストアのコードや Shield より前に実行されるため ルールの提供を待つべきではないと警告している**（出典5）。 **PHP のコアで実行が起きるなら、 PHP の上で動く緩和策は後ろにいる**（本記録の整理）。
    取るべき行動 **①「WAF があるから後回しにできる」という判断を、 本件では採らない（技術的詳細が未公表であり、 WAF で止められるかを評価できない）。** **②WAF を使う場合は、暫定の遅延策として位置づけ、 適用の期限は変えない。** **③自社の防御スタックについて 「これは PHP の前にいるのか、後ろにいるのか」を 平時に整理しておく。**
  • 悪用の「観測件数」で対応の優先度を変えない。 同じ日に「大規模に悪用」「悪用は観測せず」が並んだ
    **修正公開の前後で、Hadrian は「大規模に悪用されている」と報告し、 watchTowr は「試行は到達したが成功例は未観測」とし、 PHP セキュリティチームは「機能する公開 PoC を特定できていなかった」とし、 CISA は「悪用を観測していない」とした**（出典14・15・18・19）〈齟齬9〉。 **どれを引いても、緊急対応の発令も様子見も正当化できてしまう** （本記録の評価）。
    取るべき行動 **対応の優先度を、観測件数ではなく脆弱性の属性で決める判断表を 用意する。** **「未認証か」「リモートか」「インターネットから到達するか」 「実証済みか」「自社の露出数」の5項目で足切りし、 すべて満たすものは観測件数に関わらず最優先にする。** **外部の「大規模に悪用」という表現は、 試行か成功かを確認するまで数として扱わない**
  • PHP のワーカープロセスがシェルを起動したら、それは異常である。 CISA が名指しした2つの挙動を検知に落とす
    **CISA は監視すべき挙動として 「PHP のワーカープロセスがシェルを起動する」 「PHP のワーカープロセスがツールをダウンロードする」の2つを 名指しした**（出典15・22）。 **本件は PHP のプロセス内で任意コードが実行される脆弱性であり、 攻撃の成立後に最初に現れるのがこの挙動である**（本記録の整理）。 **アプリ側のログには残らない。**
    取るべき行動 **`php-fpm` / `httpd`（`mod_php`）/ `php-cgi` / `frankenphp` を親プロセスとする子プロセスの生成を EDR で検知し、 `sh` / `bash` / `curl` / `wget` / `python` の起動を警報にする。** **併せて、PHP が動くホストからの外向き通信を宛先ホワイトリストに 限定する。** **本件のように修正が間に合わない時間帯があっても、 成立後の検知と遮断は残せる**
  • 「この2件を直せば終わり」ではない。Wiz は追跡されていない変種の存在を示した
    **Wiz は、2件の CVE が PHP の4つのメモリ安全性の問題をまとめたもので あり、すべての変種を覆っているわけではないこと、 追跡されている変種と、おそらく追跡されていない変種の両方が存在することを 示している**（出典18）。 **PHP 自身のアドバイザリも GitHub Security Advisory も、 変種の存在に触れていない**（出典10・11・12）〈齟齬13〉。 **また PHP 8.2 は2026年12月31日に EOL を迎えるため、 今回 8.2.35 へ上げた環境は2か月後に再び判断を迫られる。**
    取るべき行動 **今回の更新を「対応完了」として台帳を閉じない。** **①PHP の更新を四半期単位の定常作業として組み込む ②8.2 系を使っている環境に、2026年12月31日を期限とする 移行タスクをいま立てる ③同じ根本原因からの追加 CVE が出たときに即座に適用できるよう、 今回の更新手順を手順書として残す**
  • 更新の前に「どこで PHP が動いているか」を数えられるようにする。 CISA も Unit 42 もそこを突いた
    **CISA は「組織内で稼働するすべての PHP を特定して棚卸しする。 他のソフトウェアの構成要素として組み込まれている場合もあり、 見えにくい可能性がある」ことを第一の行動として挙げた**（出典15）。 **Unit 42 は2,260万超のインターネット露出インスタンスを特定し、 Trey Darley は「攻撃者は、叩き始める前に何が脆弱かを知る必要がない。 一方で防御側は、パッチと保護が必要なものを信頼できる形で数えられない」 と指摘した**（原文英語・出典20）。 **SimSpace の Lee Rossey も 「パッチが公開される前に、チームは PHP がどこで動いているか、 緊急の変更を誰が承認できるか、更新が効いたことをどう確認するかを、 すでに知っているべきだ」と述べている**（原文英語・出典18）。
    取るべき行動 **平時に、PHP の所在を3経路で突き合わせる仕組みを作る。** **①構成管理（CMDB・IaC）からの一覧 ②ホスト上での実測（インストール済みパッケージ・プロセス・ コンテナイメージの SBOM） ③外部からの観測（自社の公開レンジに対するバナー取得）。** **3つが一致しない箇所が、更新の漏れが出る場所である。** **併せて「更新が効いたことをどう確認するか」の手順も先に決める**
