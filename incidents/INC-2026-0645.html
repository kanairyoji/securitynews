2026年10月21日、LiteLLM の v1.107.0 が、資格情報を窃取するマルウェアを同梱した状態で PyPI と Docker レジストリに配布されました（出典1）。

LiteLLM は、企業のアプリケーションと OpenAI・Anthropic など各社の大規模言語モデルを1つの interface につなぐ AI ゲートウェイです（出典3）。週あたり約2,300万回ダウンロードされています（出典2）。性質上、プロバイダーの API キー・クラウドの権限・データベースの接続文字列と同じ場所で動きます（出典2。整理は本記録）。

侵害されたのは、パッケージではなくリリースパイプラインです（出典1）。GitHub 上の公式 v1.107.0 ソースタグ自体に悪意あるファイルはありません（出典1）。成果物は、正規の BerriAI/litellm とハイフン1つだけ違う攻撃者側のリポジトリ Berri-AI/litellm からビルドされていました（出典1・2）。

同社の公表は、経路を秒単位で示しています（出典1。すべて2026年10月21日 UTC）。

  • 10:08:29 — 不正なリリースワークフロー変更が、ブランチ保護により拒否された
  • 10:08:34 — その5秒後、特権を持つ開発者アカウントの認証情報で保護が覆された
  • 11:11:18 — 2人目の開発者アカウントの認証情報で、本番承認ゲートを通過
  • 11:39:51〜11:40:13 — 悪意ある wheel 7個が PyPI へアップロード
  • 11:53:49〜11:54:01 — 3人目の開発者アカウントで、ワークフロー記録を削除
  • 13:23 — PyPI から litellm==1.107.0 を削除

攻撃者は3組の開発者の GitHub CLI 認証情報を入手していました（出典1）。ブランチ保護も、本番の承認ゲートも、機能はしていました—— ただし、それを通せる資格情報が奪われていました（本記録の評価）。

マルウェアの入り方には、注意が要ります。 cook.pth と sitecustomize.py という Python の起動フックとして入るため、アプリケーションが LiteLLM を import しなくても、その環境で python や pip を起動するだけで実行されます（出典1・2）。つまり「調べよう・直そうとして pip を叩く」行為が、再実行になります（出典1 が警告）。

窃取の対象は、プロバイダーの API キーに留まりません（出典2）。AWS・Azure・Google Cloud・Kubernetes・Vault・Terraform、SSH／GPG／TLS の秘密鍵、ブラウザのログイン情報とクッキー、そして Claude・Codex・Gemini・Cursor といった AI 開発ツールの認証ファイルに及びます。 さらに LiteLLM プロキシの DB を狙う専用モジュールがあり、保存されたプロバイダーキーとモデル設定を直接問い合わせます（出典2）。

LiteLLM を import しなくても、その環境で pip を叩くだけで実行される被害規模・影響範囲

本事案で運用上もっとも注意を要するのは、起動の仕組みです（本記録の評価）。

wheel は litellm/ 本体の外に、3つのファイルを置きます（出典1・2）。

litellm-1.107.0.data/purelib/cook.pth
litellm-1.107.0.data/purelib/cook.py
litellm-1.107.0.data/purelib/sitecustomize.py

wheel のインストール形式により、これらは環境の Python ライブラリディレクトリに置かれます（出典2）。そして Python は通常の起動時に、実行可能な .pth 行を処理し、続いて sitecustomize の import を試みます（出典2）。

cook.pth の中身は、1行だけです（出典2）。

import cook

この1行が資格情報の収集を起動します（出典2）。sitecustomize.py は、背後のローダー用の2つ目の起動点を提供します（出典2）。

帰結は明確です（出典1・2。整理は本記録）〈重要〉。アプリケーションが LiteLLM を import しなくても、その環境で python を起動するだけで実行されます。 そして同社が明示的に警告しているのは、次の点です（出典1）。

「pip を先に実行しないでください。影響を受けた環境で Python を起動すると、マルウェアが再実行されます」（出典1 の要旨）

つまり「調べよう・直そうとして pip を叩く」行為が、再実行になります（本記録の整理）。出典2 も同じ点を挙げています—— 「影響を受けた環境で Python や pip を起動してインストールを検査したり修復しようとすると、ペイロードが再実行されうる」（出典2）。一方で、「wheel をダウンロードしたり、その ZIP の中身をデータとして検査するだけでは、これらのフックは実行されない」（出典2）。

残存の判定は難しく、同社も断定を避けています（出典1・2）。判定に使える痕跡は次のとおりです（出典1）。
