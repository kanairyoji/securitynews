    **本件の起点はこれである**（出典4）〈重要〉。 **2026年5月27日、Agent Platform のマスターキーを含む `opencode.json` が 公開リポジトリへコミットされた**（出典4）。 **対応は行われている——コミットは強制プッシュで上書きされた**（出典4）。 **しかし「マスターキーの失効は行われなかった」**（出典4。原文英語）。 **鍵は136日後に使われ、組織オーナーの GitHub トークンの取得に至った** （出典4。算出は本記録）。 **一般化するとこうである**（本記録の評価）—— **履歴の書き換えは「見えなくする」措置であり、 「使えなくする」措置ではない。** **そして、見えなくなった分だけ、 対応したという記憶だけが残って失効の有無は確認されない。**
    取るべき行動 **①資格情報の誤公開に関する手順書の完了条件を 「当該資格情報の失効の確認」に置く。 履歴の書き換え・リポジトリの非公開化・ファイルの削除は、 いずれも完了条件にしない。** **②失効が技術的に難しい資格情報（長命なマスターキー・ 共有トークン）を棚卸しし、失効可能な形へ置き換える。 失効できないものは、誤公開時に事故が解消できない。** **③過去に「履歴を書き換えて対応済み」とした事案を洗い直し、 当該資格情報が現在も有効でないかを確認する。 本件の136日は、その確認が行われなかった期間である。**
  • **実験的なプロジェクトに、組織オーナーの権限を持つ絞られていないトークンを置かない**
    **Agent Platform は同社の説明で 「自己ホスト型のクラウドエージェントが GitHub リポジトリへ プルリクエストを出すための実験的プロジェクト」である**（出典4。原文英語）。 **その GitHub トークンは 「サービスアカウントに紐づいておらず、権限が絞られていなかった」うえ、 組織オーナーのものだった**（出典4。原文英語）〈重要〉。 **さらに、その基盤の API が 預かっているトークンを応答として返す作りだった**（出典4）—— **`GET /api/v1/managed_agents/agents?limit=100` の応答が オーナーの GitHub CLI トークンを返している。** **結果として、実験の失敗の上限が組織全体になっていた**（本記録の評価）。 **AI エージェントに作業権限を預ける構成では、 この形が繰り返されやすい**（本記録の評価）—— **エージェントに「人と同じことをさせる」ために、 人の資格情報をそのまま渡す誘因が働く。**
    取るべき行動 **①エージェント・自動化に渡す資格情報を、 専用のサービスアカウントに紐づけ、 対象リポジトリと操作の種類で権限を絞る。 個人（とくに組織オーナー）の資格情報を渡さない。** **②エージェント基盤が預かる資格情報を、 API の応答として読み出せない設計にする—— 読み出せるなら、その API の認証は資格情報そのものと等価である。** **③実験的なプロジェクトについて、 「失敗したときに失うものの上限」を着手前に定める。 本件では、その上限が設定されていなかった。**
  • **「複数人の承認」を統制として数えるなら、承認者の資格情報が別経路で守られているか確認する**
    **本件では、ブランチ保護と本番承認ゲートの両方が機能していた**（出典1）—— **10:08:29（UTC）に保護が不正な変更を拒否している。** **しかし攻撃者は3組の開発者の GitHub CLI 認証情報を入手しており**（出典1）、 **10:08:34 に1人目で保護を覆し、11:11:18 に2人目で本番承認ゲートを通過し、 11:53:49〜11:54:01 に3人目でワークフロー記録を削除した**（出典1）。 **複数人の承認を求める統制は、 複数人の資格情報が同じ経路で奪われた時点で機能しない**（本記録の評価）〈重要〉。 **統制の図は「2人の承認」と書けるが、 実態は「同じ種類の資格情報が2つ」である。**
    取るべき行動 **①リリース・本番配備の承認に使う資格情報を、 通常の開発作業で使うものと分離する（別のアカウント・ハードウェアキー必須）。** **②「承認者が N 人」ではなく「承認の経路が何種類あるか」で統制を評価する—— 同じ経路の N 人は1つの経路である。** **③リリース権限の一時的な拡大に、期限と自動の失効を必ず付ける。 本件では事案前の月曜日に2人へ権限を一時拡大していたことが 背景要因として挙げられており**（出典1）、 **拡大の期限・解除の有無は公表されていない**〈未確定4〉。

    **同社は事後に、社内 LiteLLM デプロイに 公開インターネットから到達可能な、目立たない名前のユーザーアカウントが 見つかったと述べている**（出典1）。 **攻撃者はここからログ経由でトークンを得たとみられているが、 侵入経路は未確認である**（出典1）〈未確定1〉。 **重要なのは、それが見つかったのが事案の後だったことである**（本記録の評価）〈重要〉。 **自社製品のドッグフーディング環境は、 「開発のための環境」として扱われ、 本番と同じ厳しさの棚卸しの対象から外れやすい**（本記録の評価）—— **しかしそこに本番の資格情報が置かれていれば、 攻撃者にとっては本番への入口である。**
    取るべき行動 **①自社が運用する内部ツール・検証環境について、 公開インターネットからの到達性を外部スキャンで確認する （台帳ではなく外からの観測で）。** **②それらの環境の利用者アカウントを棚卸しし、 用途の説明が付かないものを削除する。** **③内部ツールのログに資格情報が混入しうる経路を洗う。 本件では「Claude Code が GitHub CLI の OAuth トークンを 応答本文に埋め込む場合があり、応答がログに記録されると トークンがログに残る可能性がある」と同社が述べている**（出典1）〈齟齬5〉—— **一般化すれば、「ツールの出力をログに残す運用」と 「そのツールが資格情報を扱うこと」が同時に成り立つと、 ログが資格情報の保管場所になる**（本記録の評価）。
  • **AI ゲートウェイは資格情報が集まる場所である。そこで動くプロセスの侵害を、単一障害点として扱う**
    **LiteLLM は、企業のアプリケーションと各社のモデルを 1つの interface につなぐ AI ゲートウェイである**（出典3）。 **統一された入口であるため、設計上、 各プロバイダーの実際の API キーがそこに預けられる**（出典3。整理は本記録）。 **本件のマルウェアには LiteLLM 専用のモジュールがあり、 `DATABASE_URL` が設定されているデプロイに対して `LiteLLM_CredentialsTable` と `LiteLLM_ProxyModelTable` を 直接問い合わせる**（出典2）〈重要〉。 **同社がローテーションを求めた範囲は、 プロキシ DB 内のすべてのプロバイダーキー、 マスターキーとバーチャルキー、`DATABASE_URL` のパスワードに及ぶ**（出典1）。 **つまり1つのコンポーネントの侵害で、 契約している全プロバイダーの資格情報が同時に失われる**（本記録の評価）。
    取るべき行動 **①AI ゲートウェイに預けるプロバイダーキーを、 ゲートウェイの DB から読めても使えない形にする （外部の鍵管理サービス・短命の資格情報・ 発行元での IP 制限や利用上限）。** **②ゲートウェイの侵害を前提にした復旧計画を持つ—— 全プロバイダーキーを同時にローテーションする手順と所要時間を あらかじめ測っておく（本件の指示はまさにそれである）。** **③ゲートウェイが動くホストに、 他の用途の秘密情報を環境変数で置かない。 本件のローテーション範囲には 「ホスト上のいずれかのプロセスの環境変数にあった秘密情報」が 含まれている**（出典1）—— **同じホストに同居させた別の秘密まで巻き込まれる。**
  • **自社の成果物が汚染されたことを第三者から知らされる前提で、外部からの通報を受ける経路を用意する**
    **本件でマルウェアを最初に検出したのは Socket であり、 PyPI 公開から6分39秒後であった**（出典2。算出は本記録）。 **提供元でも PyPI でもない**（本記録の整理）〈重要〉。 **そして検出から PyPI での削除までは約96分かかっている**（本記録の算出）—— **検出の速さと、配布を止める速さは別である。** **さらに、3つの配布経路のうち Docker Hub が最後まで残り、 停止までに約153分を要した**（出典1。算出は本記録）。 **これは供給側の話だが、利用側にも同じ構図が当てはまる**（本記録の評価）—— **自社が使っているパッケージの汚染も、第三者から知らされる。**
    取るべき行動 **①依存パッケージの汚染を知らせてくる経路（スキャナ・ ベンダーの告知・公開のアドバイザリ）を決め、 営業時間外も含めて誰が受けるかを決める。** **②自社が成果物を配布している場合は、 外部からの通報を受ける窓口（security.txt・専用アドレス）を公開し、 配布経路ごとの停止手順と所要時間を測っておく—— 本件では経路が3つあり、最後の1つまでに153分かかった。** **③「検出」と「配布停止」を別の指標として測る。**

  • **ビルド来歴（provenance）の source リポジトリが前回リリースと一致することを、公開前に機械的に検証する**

    取るべき行動 **①自社のリリースパイプラインで、 成果物の来歴の `source_owner` / `vcs:source` を 定数（許可リスト）と照合し、一致しなければ公開を止める。** **②前回リリースの来歴と差分を取り、 source が変わった場合は人の確認を必須にする。** **③ワークフローが参照できるソースリポジトリを 入力で切り替えられない形（定数）に固定する—— 本件は `source_owner` を入力で指定できたことが前提である**（出典2）。 **④留保を持っておく。来歴は「記録された入力の証拠」であって 「入力が信頼できたことの証明」ではない**（出典2 が明示）—— **ワークフローを書き換えられる攻撃者なら来歴も偽りうる。**

  • **資格情報窃取型の侵害では、調査のために python や pip を起動しない**

  • **AI 開発ツールの認証ファイルを、クラウド資格情報と同じ重さで棚卸しの対象にする**
    **本件の収集対象には、AI 開発ツールの認証ファイルが 明示的に含まれている**（出典2）〈重要〉—— **Codex の `~/.codex/auth.json`、 Claude の `~/.claude/.credentials.json`、 Gemini の `~/.gemini/oauth_creds.json`、 Cursor の `~/.cursor/mcp.json`、 ほか Copilot・Windsurf・Kiro・Zed・Continue・OpenCode・Hugging Face の設定。** **これらは開発者の作業端末のホームディレクトリにあり、 「本番の秘密」として管理されていないことが多い**（本記録の評価）。 **従来のクラウド資格情報の棚卸し（IAM・Vault・CI の秘密）の 対象に入っていない可能性がある。** **なお `~/.cursor/mcp.json` のような MCP の設定ファイルは、 他サービスのトークンを含みうる**（本記録の評価）—— **1つのファイルが複数のサービスへの入口になる。**

  • **本番コンテナからの外向き通信を宛先の許可リストで限定する。製品名を含むドメインを信頼しない**
    **本件の送信先は `hxxp://www[.]litellm[.]dev/healthcheck` である**（出典2）。 **URL は健全性確認を装っているが、本体は暗号化された収集結果である**（出典2）。 **ここが検知の観点で重要である**（本記録の評価）〈重要〉—— **送信先が製品名を含むドメインであるため、 宛先ドメインの一致だけで外向き通信を許可している環境では 「LiteLLM が litellm.dev と通信している」は正常に見える。** **収集が成功しても、送信できなければ流出しない**（本記録の整理）。 **AI ゲートウェイは外向き通信が業務の中心であるため 「外に出る通信を全部止める」ことはできないが、 宛先を列挙することはできる**（本記録の評価）。
