2026年10月2日（金）09時35分、乗っ取られた Tor の出口リレー333台が協調して SSH 接続の傍受を始めました（出典1）。

Tor 全体の出口リレーは約3,000台で、その約10%が攻撃者の管理下にありました（出典1）。

出口リレーは、Tor 回線の最後の中継点です（出典2）。通信はここから Tor の外へ出て宛先へ向かいます—— つまり出口リレーは、暗号化されていない通信をそのまま見られる位置にいます（本記録の整理）。

攻撃者の狙いは2つでした（出典1）。

  1. 暗号化されていないメール通信を大量に収集する — 特定ポートを塞ぎ、出口リレーが平文のメール通信だけを扱うようにしていた
  2. SSH 接続の中間者攻撃（MITM） — 22番ポートの接続を12台の傍受サーバへリダイレクトした

暗号化された Web 通信は通常どおり転送されました（出典1）—— だから利用者からは、何も起きていないように見えます（本記録の評価）。

気づける点は、1つだけです（出典1）。SSH の接続先が入れ替わっているため、「ホスト鍵が変わった」という警告が出ます。 その警告を無視してログインすると、次のことが起きました（出典1）。

  • 攻撃者がパスワードを盗む
  • 別の接続でコマンドを監視する
  • さらに別の接続で、そのサーバを Ebury に感染させる

逆に言えば、鍵認証を使っていれば被害は生じません（出典1。整理は本記録）〈重要〉。盗まれうるのはパスワード認証の資格情報だけです。

攻撃は、始まる2か月前から準備されていました（出典1）。攻撃者は8月にサーバへ侵入し、OpenSSH のバックドア兼認証情報窃取ツールEbury 1.8.3 を静かに配備していました。

発見と排除の経過は速いものでした（出典1）。発見者（kaba）は exitmap を使い、出口リレーを固定してサーバAからサーバBへ SSH 接続するスクリプトを書き、約3,000台すべてをスキャンしました。 約12台が偽のフィンガープリントを返し、300台超が傍受サーバへリダイレクトしていました。 10月2日夕方に Tor Project のネットワークヘルスチームへ通報し、10月4日に該当リレーが BadExit として印を付けられ、10月5日には感染サーバがすべて停止しました。

分かっていないことが2つ残っています（出典1）。攻撃者がどうやって多数のサーバへ侵入したのか、そして攻撃者が誰なのか。 発見者はどちらも「推測にすぎない」と明記しています。

出口リレーは、Tor 回線の最後の中継点です（出典2）。通信はここから Tor の外へ出て宛先へ向かいます。 つまり出口リレーは、構造上、暗号化されていない通信をそのまま見られる位置にいます（本記録の整理）〈重要〉。これは Tor の欠陥ではなく設計です—— Tor が与えるのは匿名性であって、通信相手に対する機密性ではありません（本記録の評価）。

  1. 暗号化されていないメール通信の大量収集 — 特定ポートを塞ぎ、出口リレーが平文のメール通信だけを扱うようにしていた
  2. SSH 接続の中間者攻撃 — 22番ポートの接続を12台の傍受サーバへリダイレクトした

ここで重要なのは、選択的だったことです（本記録の評価）〈重要〉。暗号化された Web 通信は通常どおり転送されました（出典1）。つまり Tor で Web を見ている利用者からは、何も異常が見えません。 差し替えられたのは22番ポート、すなわち SSH だけです。

12台という数が、この攻撃の性質を示しています（本記録の評価）。333台のリレーが、12台の傍受サーバを共有していました（出典1）。個々のリレー運営者がそれぞれ設定を誤ったのなら、リダイレクト先が共通になる理由はありません（本記録の整理）—— 一元的に操作されていたことの根拠です。 発見者も「協調して」という表現を使っています（出典1）。

なお、侵害されたのは Tor Project の設備ではありません（本記録の整理）〈重要〉。第三者の運営者が持つリレーのサーバです。 Tor の暗号化が破られた事案でもありません。

逆に言えば、鍵認証を使っていれば被害は生じません（本記録の整理）〈重要〉。

理由は単純です（本記録の評価）。傍受サーバは、本来の宛先サーバの秘密鍵を持っていません。 鍵認証では、クライアントが送るのは署名であって秘密そのものではなく、しかもホスト鍵の検証が先に失敗します。 パスワード認証の場合だけ、「警告を無視する」という人間の操作を経て、パスワードという共有秘密が相手に渡ります。

報道もこの点を押さえています（出典2）。The Hacker News は「2026年10月1日から5日のあいだにTor 経由で SSH サーバへパスワードでログインした場合のみ」が影響を受けたとしています（出典2）。

警告を無視した場合、何が起きたか（出典1）。

  • さらに別の接続で、そのサーバを Ebury に感染させる

つまり、防御は機能していました（本記録の評価）〈重要〉。本事案で傍受が成立したのは、その警告を無視してログインした場合だけです（出典1）。

ここに、本DBが繰り返し見てきた形が現れています（本記録の評価）。仕組みは正しく動き、正しく警告を出した。破れたのは運用です。

なぜ無視されるのかは、実務の事情で説明が付きます（本記録の評価。発見者はこの点を述べていない）。

  • ホスト鍵の変更は、正当な理由でも起こる（サーバの再構築・移設・鍵の更新）
  • そのため「また出た」として慣れてしまう
  • 警告を回避する手順（既知ホストの該当行を消す）が広く知られており、手が速い

対策は2方向あります（本記録の評価）。

第一は、警告を無視できない事象にすることです。 既知ホストの鍵を配布・固定して管理すれば、「変わった」は例外として扱えます（本記録の提言）。

第二は、そもそもパスワードを渡さないことです。 これが発見者の結論でもあります（出典1）—— 「パスワード認証をやめ、SSH 鍵認証を使うこと。著者はハードウェアキーの導入も検討している」。

鍵認証であれば、警告を無視しても資格情報は渡りません（本記録の整理）。つまり人間の判断に依存しない防御になります（本記録の評価）〈重要〉—— 警告に気づけるかどうかを運用に委ねるより、盗まれるものを無くすほうが堅牢です。

もう1つ、経路の設計についての論点があります（本記録の評価）。本事案の前提は、SSH 接続が Tor の出口リレーを通ったことです。 Tor が与えるのは匿名性であって、通信相手に対する機密性ではありません（本記録の整理）。出口リレーは設計上、通信が平文に戻る位置にいます。 匿名性が必要な通信と、サーバ管理のための SSH を同じ経路に載せるべきかは、設計の判断です（本記録の評価）。

匿名化ネットワークの出口は、構造上「平文に戻る場所」である背景・過去事例

本事案を一般化すると、次のことが言えます（本記録の評価）。

Tor の出口リレーは、設計上、通信が平文に戻る位置にいます（本記録の整理）。Tor は回線の中では多重に暗号化しますが、出口から先は利用者が使っているプロトコル自身の暗号化しかありません。

したがって、本事案の成立条件はこうなります（本記録の整理）。

通信 出口リレーから見えるもの 本事案での扱い
暗号化された Web 通信 内容は見えない 通常どおり転送された（出典1）
暗号化されていないメール通信 内容が見える 収集の対象（出典1）
SSH 内容は見えないが、宛先を差し替えられる 12台の傍受サーバへリダイレクト（出典1）

3行目が本事案の核心です（本記録の評価）。SSH は暗号化されているため、出口リレーは中身を読めません。 しかし出口リレーは「どこへつなぐか」を決める位置にいるため、宛先そのものを自分の用意したサーバへ差し替えられます。 そこで初めて、中間者攻撃が成立します。

そして SSH は、まさにこれを検出するための仕組みを持っています（本記録の整理）——ホスト鍵の検証です。 本事案では、その仕組みが正しく警告を出していました（出典1）。

ここから導ける一般的な判断は2つです（本記録の評価）。

第一に、匿名化ネットワークを「安全な回線」として扱わないことです。 Tor が与えるのは匿名性であって、通信相手に対する機密性ではありません。 出口の運営者は誰でもなれます（本記録の整理）—— 本事案は333台が乗っ取られた例ですが、最初から悪意のある運営者が出口を立てることも構造上は可能です。

第二に、「経路を信頼しない」前提で認証を選ぶことです（本記録の評価）。経路上の誰かが宛先を差し替えうるなら、共有秘密（パスワード）を送る認証方式は危険です。 鍵認証であれば、相手が偽物のとき認証そのものが成立せず、秘密も渡りません。

なお、同種の事象には先例があります（本記録の背景整理）。Tor の出口リレーによる中間者攻撃は、過去にも研究者によって報告されてきた類型です。 ただし本記録は過去事例の具体的な件数・時期を一次資料で確認していないため、個別の比較は行いません（本記録の明示）—— 本記録が記録するのは、本事案の規模（約10%・333台）が台数ベースで大きいことだけです（出典1）。
