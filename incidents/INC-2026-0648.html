INC-2026-0648LazarusがINISAFEを入口に韓国3組織侵害

Lazarus の新作戦「Operation FlashHole」——韓国で必須の金融セキュリティソフト INISAFE CrossWeb EX を入口に、ソフトウェア・建設・有線通信機器製造の 3組織以上が侵害された。AI で作った架空の経歴書サイトを標的ごとに用意し、 LPEClient は後量子暗号 ML-KEM-1024 で通信を守っていた（Kaspersky GReAT・2026年10月21日）

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因設計・実装上の不備人を介した誘導（ビッシング・BEC）公表されていない／不明
初報: 2026年10月21日（Kaspersky GReAT が公表） 最終更新: 2026年10月22日（本記録の作成）

「国が入れさせるソフト」が、2年おきに同じ攻撃者の入口になっている。 2026年10月21日、Kaspersky GReAT は Lazarus Group の新しい作戦 「Operation FlashHole」を公表した（出典1）。同社は2026年1月に韓国で この攻撃への対応にあたり、韓国で広く使われる金融セキュリティソフト 「INISAFE CrossWeb EX V3」（バージョン 3.4.1.2・2023年リリース）が 侵害の経路に使われていたことを確認した。このソフトは オンラインバンキングと政府サイトの利用に必要で、ブラウザと対話するため 常時背後で動いている。前作戦 Operation SyncHole では同系統の Cross EX が 使われており、Lazarus は2021年・2022年・2023年にも同じベンダーの製品を悪用している（出典1）。確認された被害は韓国のソフトウェア・建設・有線通信機器製造の3組織以上。 作戦の最も古い痕跡は2025年7月にさかのぼり、SyncHole の終了直後に 準備が始まっていたとみられる（出典1）。 誘い込みには、AI で作ったとみられる架空の経歴書サイトが使われた—— GitHub Pages 上に置かれた「ネットワーク機器の上級開発者」の経歴書で、 写真には EXIF が無く質感が不自然、氏名は韓国語版の「John Doe」に似た名前だった。 このサイトは1月にインテリアデザインの展示に差し替えられており、 Kaspersky は前者が有線通信機器製造の、後者が建設業の標的に対応するとみている（出典1）。技術面での更新は3つある。 ①C2 に非公開の GitHub リポジトリ （Personal Access Token 経由）と Dropbox API を使う。 ②LPEClient が後量子暗号 ML-KEM-1024 で鍵共有を行う（GOST/Magma も併用）。 ③同じ LPEClient が、jscript9.dll の関数を使って MD4Update のメモリ保護を変更し、 システムコールのスタブを書き込んで、ユーザーモードの監視フックを外す（出典1）。 帰属は SyncHole と同一アクターとして中〜高の確度で示されている。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**入口は「入れないわけにいかないソフト」、通り道は「正規のサービス」である**（本記録の整理）。 標的ごとに作り替えた経歴書サイト（GitHub Pages）へスピアフィッシングで誘い込み、 埋め込まれた外部 JavaScript から **CrossWeb EX を経由して メモリ上だけで動くチェーンを起動する。** 永続化の後は、 **C2 も非公開の GitHub リポジトリと Dropbox API、侵害された韓国の正規サイト**という **通信先で弾けない構成**になっている（出典1）。 **最も注目すべきは LPEClient の2点**——**後量子暗号 ML-KEM-1024 による鍵共有**と、 **ユーザーモードの監視フックを外す実装**である。

  1. 1. 偵察disclosed[1] [2]
    **標的ごとに誘い込みサイトを作り替えた。** 2025年9月に作られた GitHub アカウント （C2 にも使われた同一アカウント）の GitHub Pages に、 当初は「ネットワーク機器の上級開発者」の経歴書を、 2026年1月にはインテリアデザインの展示を置いた。 **Kaspersky は前者を有線通信機器製造、後者を建設業の標的に対応づけている。** **経歴書の写真は AI 生成とみられる**（EXIF が無く質感が不自然）、 **氏名は韓国語版の「John Doe」に似た名前**で、ポートフォリオは 意味のない細部とランダムな会社名で埋められていた。 **生成したサイトを標的ごとに手で仕立て直している**（出典1）
    根拠: Kaspersky GReAT「Operation FlashHole: Lazarus breaks security, defies control」 （2026年10月21日）。**本記録の作成者が記事を取得して確認した**
  2. 2. 初期侵入推定[1]
    **スピアフィッシングのリンクから、GitHub Pages のサイトを経て感染が始まった。** サイトには script タグで外部 JavaScript が読み込まれていた—— 経歴書サイトは `hxxps://javadevhouse.co[.]kr/ajax/libs/jquery/1.7.3/jquery.min.js`、 インテリアデザインのサイトは `hxxps://pythonapischool[.]com/api/detach`。 **Kaspersky は「標的が GitHub Pages 上の悪性サイトへのリンクを含む フィッシングメールを受け取った」ことを中〜高の確度で評価し、 サイトの閲覧が CrossWeb EX を伴う感染を開始させた可能性が高いとする**（出典1）
    根拠: 同記事。埋め込まれた2つの外部 JavaScript の URL を確認した
  3. 3. 実行disclosed[1]
    **CrossWeb EX のプロセス配下で、正規の Windows バイナリ `fsquirt.exe` が 実行され、悪性 DLL（TechHub）を含むシェルコードが注入された。** **生成されたプロセスは高い整合性レベル（high integrity level）で動いていた。** 親プロセスは `INISAFECrossWebEXSvc.exe`（INISAFE CrossWeb EX V3 3.4.1.2 の インストールバンドル由来）。**初期侵入の段階では、この実行チェーンは メモリ上にのみ存在する**（出典1）
    根拠: 同記事。プロセスの親子関係と整合性レベルの記述を確認した
  4. 4. 永続化disclosed[1]
    **TouchHub と TouchShift の対で永続化した。** TechHub が TouchHub を配置し、TouchHub は **正規の `printfilterpipelinesvc.exe` を `ImeBroker.exe` としてコピーし、 svchost の netsvcs 系の名前を使ったサービスとして登録する。** さらに **TouchShift を置き、ファイルの MAC タイムスタンプを改ざんする。** TouchShift は `mscoree.dll` の名前で **DLL サイドローディング**により読み込まれ、 `LockClrVersion` を使って **XOR と AES-CBC-128** で次段を復号し、 **2つ目の TechHub をメモリ上で実行する。** その TechHub は Cubridge を直接動かさず、**ClientHub と LPEClient の対を配置する**。 **ディスクに残る痕跡は最小限で、残りはメモリ上だけに存在する**（出典1）
    根拠: 同記事。サービス名の偽装・サイドローディング・MAC 改ざんの記述を確認した
  5. 5. 検知回避disclosed[1]
    **検知回避は4層にわたる。** ①**初期段階はメモリ上のみ**で、 ディスクの痕跡が少ない。②**TouchHub がファイルの MAC タイムスタンプを 周囲に合わせ、フォレンジック分析を妨げる。** ③**ClientHub は Chromium 系ブラウザの `Sec-CH-UA` などのヘッダーを付けて 正規の通信を装い、設定を SNOW 1.0 で暗号化する。** ④**LPEClient は `jscript9.dll` の `HeapPageAllocator::ProtectPages` を使って `MD4Update` のメモリ保護を変更し、そこにシステムコールのスタブを書き込んで、 ユーザーモードのシステムコール監視フックを無効化する**（出典1）
    根拠: 同記事。4点それぞれの実装の記述を確認した
  6. 6. 認証情報アクセスdisclosed[1] [2]
    **Cubridge が認証情報の窃取を担う。** Cubridge は本チェーンの **中核のオーケストレータ**で、プラグイン・ツール・モジュールを読み込み、 ファイル操作・プロセス操作・**認証情報の窃取**・ネットワーク情報の取得を行う。 **Cubridge は初期侵入の段階ではメモリ上にしか存在しないため、 Kaspersky は「永続化を獲得した後に意図的に再配置するための 間接的な多段チェーンを設計した」とみている**（出典1）。 あわせて **LPEClient が、インストールされているセキュリティ製品・ Windows の防御機能・その他のシステム特性を収集し、圧縮・暗号化して送る**（出典2）

AI で作った架空の経歴書サイトを、標的の業種に合わせて差し替えていた原因・手口

C2 は GitHub と Dropbox、鍵交換は ML-KEM-1024——「後から解く」道が塞がれている原因・手口

本作戦のマルウェアは6系統（出典1）。 TechHub（チェーンの起点のダウンローダ。Mandiant の CLOUDBURST・ ESET の NickelLoader の高度版）、TouchHub（新規。インストーラ）、 TouchShift（ローダ）、ClientHub（新規。CookiePlus の高度版と 中〜高の確度で評価）、LPEClient（2019年から既知。大幅な更新版）、 Cubridge（中核のオーケストレータ）。C2 の作りが本作戦の特徴である。 TechHub は非公開の GitHub リポジトリに Personal Access Token で接続する （主要3＋フォールバック1。アカウントは乗っ取られたメールで作成）。 ハンドシェイクは GitHub の issue で行う——過去の通信が残っていれば消し、 1[ID] という題名で本文 hel の issue を作って open にし、 リポジトリから 2[ID] を名前に含む RSA 公開鍵を取り、 16バイトのランダムな XOR 鍵を RSA で暗号化して戻す。 以後のファイル名は [1|2][ID][random-16-byte-key]。 ID は 0x1000〜0xFFFF の4バイト16進値で、侵害ホストを区別するためのものである。 Cubridge と ClientHub は侵害された韓国のメディアやインテリア関連の正規サイトを、 ClientHub の一部の検体は Dropbox API を C2 に使う（出典1）。LPEClient の更新が最も重い。 この道具は自分の C2 アドレスを持たず、 ClientHub と共有バッファで通信する。 インストールされているセキュリティ製品・Windows の防御機能・ その他のシステム特性を収集し、圧縮・暗号化して送る（出典2）。 そして ML-KEM-1024 ——NIST が標準化した後量子鍵カプセル化方式 （CRYSTALS-Kyber 由来）——の公開鍵を C2 から受け取り、共有鍵を生成する。 通信には GOST（Magma）も使われる（出典1）。これが意味するのは「記録しておいて後から解く」道が塞がることである （本記録の評価）。通信を保存しておけば将来の鍵の入手や計算力の向上で 読めるかもしれない、という前提が成り立たない。 Kaspersky の Sojun Ryu 氏は、この種の暗号が少なくとも2024年9月から 使われていたとし、「公表の1年以上前からマルウェアの通信の保護に 使っていたことになる」と述べている（出典2・齟齬2）。さらに LPEClient は、jscript9.dll の HeapPageAllocator::ProtectPages を 使って MD4Update のメモリ保護を変更し、そこにシステムコールのスタブを 書き込んで、ユーザーモードのシステムコール監視フックを無効化する（出典1）。 ユーザーモードのフックに依存する防御製品は、この時点で目を潰される （本記録の評価）。

「国が入れさせるソフト」は、その普及率がそのまま国の攻撃面になる評価・解釈

本記録の評価を1つに絞る。本件の教訓は Lazarus の技術ではなく、 入口の性質にある。 CrossWeb EX は、利用者が選んだソフトではない。 オンラインバンキングと政府サイトを使うために入れさせられ、 ブラウザと対話するために常時動き、高い整合性レベルのプロセスを持つ（出典1）。 この3つが揃うと、1つの製品の問題が国民規模の攻撃面になる。 Lazarus は2021年・2022年・2023年、そして今回と、 同じベンダーの製品を繰り返し入口にしている（出典1）。日本にも同じ構図がある（本記録の評価）。 金融機関や公的手続のために、電子証明書の管理ソフトや 常駐型の補助ソフトを利用者に入れさせる仕組みは残っている。 「推奨」や「必須」として配られるソフトは、利用者の判断で外せない。 外せないソフトの脆弱性は、利用者側の対策では閉じられない ——Kaspersky の助言（「不要な構成要素を無効化する」）が、 この領域では構造的に効かないのはそのためである（本記録の指摘）。取るべき向きは2つある。 ①配る側（金融機関・官公庁・ベンダー）が、常駐ソフトの攻撃面を 自分の責任範囲として管理すること。 韓国政府が必須インストールの 段階的廃止に動いたのは、この認識の表れである（出典1）。 ②使う側（企業）が、業務で入れさせられている常駐ソフトを棚卸しし、 そのプロセスが何の子プロセスを生むかを監視に入れること ——本件で最も現実的に検知できた段階は、 金融セキュリティソフトのサービスが fsquirt.exe を起動したところである （本記録の評価。attack.chain の execution 段階）。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
必須の金融セキュリティソフトを入口に、正規サービスを C2 として多段で永続化する構造
**layer 0 は誘い込み**（標的ごとに作り替えた GitHub Pages のサイトと そこから読まれる外部 JavaScript）。**layer 1 が入口**—— 韓国で必須の金融セキュリティソフト INISAFE CrossWeb EX V3 と、 その配下で注入される正規バイナリ `fsquirt.exe`。 **layer 2 が多段のマルウェア**（TechHub → TouchHub/TouchShift → 2つ目の TechHub → ClientHub + LPEClient、そして中核の Cubridge）。 **layer 3 が C2 とデータの行き先**（非公開 GitHub リポジトリ・Dropbox API・ 侵害された韓国の正規サイト）。 **太い流れは2つ**——①閲覧から CrossWeb EX 経由でメモリ上の実行へ、 ②永続化の後に Cubridge を再配置して認証情報を集める。 **LPEClient は自分の C2 を持たず ClientHub と共有バッファで通信し、 ML-KEM-1024 で鍵共有する**（出典1）。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
偵察現実的な検知機会なし

検知できた**プロキシログで「jQuery 等の著名ライブラリを、公式 CDN 以外から取得した」 通信を定期的に洗い出す**（本記録の推奨）
実行機会はあったが検知できず
**ここは現実的に検知できた段階である**（本記録の評価）—— **金融セキュリティソフトのサービスが `fsquirt.exe`（Bluetooth ファイル転送ウィザード）を起動することに、業務上の説明がつかない。** **親子関係の異常として書けるルールである**

**サービスの新規登録と、正規バイナリの別名コピーは記録に残る**（本記録の指摘）。 **`printfilterpipelinesvc.exe` が `ImeBroker.exe` という別名で置かれることは 正常な運用では起こらない。** **MAC タイムスタンプの改ざんは フォレンジックを妨げるが、サービス登録イベント自体は消えない**
検知できた**サービスの新規作成（イベント ID 7045 等）を全台で収集し、 既知のサービス名の一覧と突き合わせる**（本記録の推奨）

**④は、ユーザーモードのフックに依存する製品の前提を壊す手口である** （本記録の評価）。**「EDR が入っているのに何も出ない」という状態が 正常に見えてしまう。** **カーネル側のテレメトリ（ETW・カーネルコールバック）や ネットワーク側の観測を併せ持たない構成では、 この段階以降の活動が構造的に見えない**（本記録の指摘）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • **「業務上入れざるを得ない常駐ソフト」の一覧を、自社のリスク台帳に載せる**
    本件の入口は、オンラインバンキングと政府サイトの利用に必要で **利用者の判断では外せないソフトだった**（出典1）。 **外せないソフトの攻撃面は、利用者側の対策では閉じられない**（本記録の評価）。 **日本でも電子証明書の管理ソフトや常駐型の補助ソフトは同じ性質を持つ**
    取るべき行動 **取引先・官公庁から入れるよう求められている常駐ソフトを棚卸しし、 ①導入台数 ②常駐プロセス名 ③実行権限 ④更新の経路を台帳にする。** **「外せない」ものは、外す代わりに監視でカバーする対象として明記する**
  • **同じアクターが同じ入口を繰り返すことを前提に、過去事例を自社の点検項目に変える**
    Lazarus は **2021年（Racket ダウンローダ）・2022年・2023年、 そして今回と、同じベンダーの金融セキュリティソフトを入口にしている**（出典1）。 **前作戦 SyncHole の直後（2025年7月）から次の準備を始めていた**
    取るべき行動 **自社の業種・利用製品に関係する過去の侵害公表を、 「次も同じ入口が来る」前提で点検項目に落とす。** **四半期に1回、過去2年の同型事案を見直し、 当時の検知ルールが今も有効かを確認する**
  • **「EDR が入っているのに何も出ない」を正常と読まない仕組みを作る**
    LPEClient は **ユーザーモードのシステムコール監視フックを無効化する**（出典1）。 **防御製品の目を潰す実装であり、検知が静かになることが むしろ侵害の兆候になりうる**（本記録の評価）
    取るべき行動 **監視の生存確認を運用に組み込む。** 合成イベントを定期的に流して 検知されるかを試し、**検知件数が不自然に落ちた端末群を調査対象にする。** **ユーザーモードのフックに依存しないテレメトリ（ETW・カーネル側）の 有無をベンダーに確認する**
  • **通信の中身を「後から解く」前提を捨てる**
    LPEClient は **後量子暗号 ML-KEM-1024 で鍵共有を行う**（出典1）。 Kaspersky は**少なくとも2024年9月から使われていたとする**（出典2）。 **記録しておいて将来復号する道は塞がれている**（本記録の評価）
    取るべき行動 **調査の設計を「通信の中身」から「通信の事実とプロセスの対応」へ寄せる。** どのプロセスが・どの資格情報で・どこへ出たかを残すことに投資する。 **全パケット保存の費用対効果を再評価する**
  • **ベンダー1社による帰属を、そのまま自社の意思決定の前提にしない**
    帰属は **Kaspersky が中〜高の確度で示したもの**で、 **同じ活動群を韓国政府の共同勧告や AhnLab は別の粒度で切っている**（出典1）。 **「Lazarus」という名前が指す範囲は資料ごとに違う**（本記録の指摘）
    取るべき行動 **脅威情報を取り込むとき、帰属の確度と出所を必ず添えて社内に流す。** **対策の優先順位は「誰がやったか」ではなく 「どの入口が自社にあるか」で決める**
セキュリティ技術者への示唆
  • **常駐セキュリティソフトのサービスプロセスが生む子プロセスを監視する**
    本件で最も現実的に検知できた段階は、 **`INISAFECrossWebEXSvc.exe` の配下で `fsquirt.exe` （Bluetooth ファイル転送ウィザード）が実行された**ところである（出典1）。 **金融セキュリティソフトがこれを起動する業務上の説明はつかない**（本記録の評価）
    取るべき行動 **常駐ソフトのサービスプロセスごとに「正常な子プロセスの一覧」を作り、 外れたものを警報にする。** あわせて **`fsquirt.exe` のような 業務で使わない正規バイナリの実行を許可リストで止める**
  • **正規バイナリの「別名での配置」とサービスの新規登録を全台で拾う**
    TouchHub は **正規の `printfilterpipelinesvc.exe` を `ImeBroker.exe` として コピーし、svchost の netsvcs 系の名前でサービス登録する。** さらに **MAC タイムスタンプを改ざんする**（出典1）。 **タイムスタンプは消せても、サービス登録イベントは残る**
    取るべき行動 **サービス作成イベント（7045 等）を全台から集め、既知のサービス名と突き合わせる。** **署名付きバイナリのハッシュとファイル名の対応が崩れた端末を洗い出す** （`mscoree.dll` 名での DLL サイドローディングも同じ観点で拾える）
  • **GitHub・Dropbox への API 通信を「プロセス単位」で見る**
    TechHub は **Personal Access Token で非公開 GitHub リポジトリと issue 経由のハンドシェイクを行い**、ClientHub の一部は **Dropbox API** を C2 にする（出典1）。**宛先ドメインでは弾けない**
    取るべき行動 **組織の GitHub / Dropbox テナント以外への API 通信を区別して記録する。** **業務アプリ以外のプロセスが SaaS の API を叩く通信を警報にする。** **`[1|2][ID][16バイト鍵]` 形式のファイル名や `1[ID]`/本文 `hel` の issue 作成という具体の痕跡は、自社テナントの監査ログで探せる**
  • **著名ライブラリを公式 CDN 以外から取得している通信を洗い出す**
    誘い込みサイトは **jQuery の配布パスを模した URL （`javadevhouse.co[.]kr/ajax/libs/jquery/1.7.3/jquery.min.js`）**から 外部スクリプトを読み込んでいた（出典1）。 **文字列の見た目だけでは正当に見える**
    取るべき行動 **プロキシログで「jquery.min.js などの著名ファイル名を、 公式 CDN 以外のドメインから取得した」通信を定期的に抽出する。** **外部スクリプトの読み込み先をドメイン単位で制限する**
  • **ユーザーモードのフック無効化を前提に、カーネル側とネットワーク側で裏を取る**
    LPEClient は **`jscript9.dll` の `HeapPageAllocator::ProtectPages` で `MD4Update` のメモリ保護を変え、システムコールのスタブを書き込んで 監視フックを外す**（出典1）。**端末側の可視性が落ちる**
    取るべき行動 **ETW・カーネルコールバック・ネットワーク側の観測を併用し、 端末エージェントの検知が無いことを「異常なし」と読まない。** **`jscript9.dll` を本来読み込まないプロセスがこれを読む挙動を検知対象にする**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ **取引先・官公庁・金融機関から求められて導入している常駐ソフト （電子証明書の管理ソフト・ブラウザ連携の補助ソフト等）があるか。 その数と導入台数を把握しているか**本件の入口は**利用者の判断では外せない必須ソフト**だった（出典1）。 **「外せない」ことが攻撃面の本質である**（本記録の読み）
運用・監視□ **常駐ソフトのサービスプロセスが生成する子プロセスを監視しているか。 正常な子プロセスの一覧を持っているか**本件で最も現実的に検知できた段階がここである （`INISAFECrossWebEXSvc.exe` → `fsquirt.exe`・出典1）
システム構成□ **GitHub・Dropbox などの SaaS への通信を、プロセスとテナントの単位で 区別して記録しているか**C2 が**非公開 GitHub リポジトリ・Dropbox API・侵害された正規サイト**で 構成されており、**宛先ドメインでは弾けない**（出典1）
運用・監視□ **端末の検知がユーザーモードのフックに依存していないか。 監視の生存確認（合成イベントの投入）を定期的に行っているか**LPEClient は**ユーザーモードのシステムコール監視フックを無効化する**（出典1）。 **検知が静かになることが兆候になりうる**（本記録の評価）
認証・認可□ **特権アカウントの利用が場所と時間で縛られているか。 侵害端末から横展開できる範囲を把握しているか**Cubridge が**認証情報の窃取とネットワーク情報の取得**を担う（出典1）。 **高い整合性レベルのプロセスから始まるため、初動の権限が高い**
体制・契約□ **採用・調達の窓口に届く外部リンクの扱いを決めているか （判断を代わりにする報告先があるか）**誘い込みは**標的の専門に合わせて作り替えた経歴書・ポートフォリオ**であり、 **業務上開く理由がある**（出典1）。 **「開くな」という教育だけでは実務が回らない**（本記録の評価）
