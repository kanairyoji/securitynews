INC-2026-0649IIJがLinux版Noodle RATを分析

IIJ が Linux 版 Noodle RAT と専用ローダを分析——ローダのアンチウイルス検知率は 記事執筆時点で0%。攻撃者は日本の IP アドレスから同一アカウントで VirusTotal に検体を上げ、検知回避性能を試していたとみられる（2026年10月21日）

脅威・攻撃キャンペーン初報のみ日本に波及した海外事案設計・実装上の不備公表されていない／不明
初報: 2026年10月21日（IIJ Security Diary が公表） 最終更新: 2026年10月22日（本記録の作成）

「検知されないこと」を攻撃者が先に測っている。 2026年10月21日、IIJ（Internet Initiative Japan）の Security Diary は、 2026年9月に VirusTotal へアップロードされた複数の Linux 版 Noodle RAT と そのローダを分析した結果を公表した（出典1）。 Noodle RAT は中国語圏の複数の攻撃者グループが使うマルウェアで、 過去にサイバーエスピオナージ目的の攻撃と金銭目的の攻撃で観測されている（出典1・2）。検体は同時期に同一のユーザによって API 経由でアップロードされており、 ファイル名は vt-submit-x64.bin や vt2-packed-x64 だった。 IIJ は「攻撃者がマルウェアの検知回避性能を検証する目的で VirusTotal にアップロードした可能性が高い」と評価している。 アップロード元は日本の IP アドレスで、VirusTotal の Submitter ID は 1f915147。 そして記事執筆時点で、ローダのアンチウイルス製品による検知率は0%である（出典1）。ローダの作りはこうである。 実行されるとまず自分自身 （/proc/self/exe）の末尾60バイトを読む。 そこには マジック値 NLKA01\x00\x01 から始まる、本体のサイズと復号パラメータが入っている。 続いてオフセット 0x5B88 以降の ChaCha20 で暗号化された Noodle RAT 本体を 読み出して復号し、memfd_create で kworker という名前の無名ファイルを作って そこへ書き込み、execve で実行する（出典1）。 memfd_create が失敗した場合、または環境変数 STUB_MODE に file が 設定されていた場合は /tmp/.0000e444 に書いて実行する。 環境変数 STUB_ARGV0 が設定されていれば argv を書き換えてプロセス名を偽装する。 IIJ は「このローダは Noodle RAT 以外のマルウェアを実行する時にも 使用される可能性がある」と指摘している。 設定情報の鍵は付け替えられていた——RC4 鍵が r0st@#$ から mBCHk?u に 変わっている。 ところが偽装先プロセス名を復号するコードは古い鍵を使うままで、 この機能は正常に動作しない。IIJ は「マルウェア開発者のミスだと考えられる」としている（出典1）。 復号できた設定は、偽装先プロセス名が /usr/bin/sshd、 C2 サーバが 127.0.0.1:9000 と 192.0.2.9:443、稼働時間 00-24、 稼働曜日は全曜日、通信間隔 5 だった。 C2 がループバックアドレスと例示用アドレス（RFC 5737 の TEST-NET-1）である点から、 IIJ はこの検体が実攻撃用ではないとみている（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件で分析されたのは「本体」ではなく「運び方」である**（本記録の整理）。 **ローダは自分の末尾に本体を抱え、ChaCha20 で復号して `memfd_create` の無名ファイルから直接実行する。** **ディスクに Noodle RAT の実体が現れないため、ファイルを走査する防御は空振りする** ——**記事執筆時点の検知率0%はその結果である**（出典1）。 **プロセス名の偽装（`kworker`・`/usr/bin/sshd`）が重なると、 プロセス一覧を見ても異常が分からない。**

  1. 1. 検知回避third_party[1]
    **ローダは自分自身を読んで本体を取り出す。** 実行されると **`/proc/self/exe`（ローダ自身）の末尾60バイトを読み取る。** この領域は **`NLKA01\x00\x01` というマジック値で始まり、 Noodle RAT 本体のサイズと復号パラメータを含む。** 続いて**オフセット `0x5B88` 以降にある ChaCha20 で暗号化された本体を読み出し、 末尾から得たパラメータで復号する**（出典1）。 **外部からペイロードを取りに行かないため、通信の観測にも引っかからない** （本記録の評価）
    根拠: IIJ Security Diary「FUD ローダによって実行される Linux 版の Noodle RAT」 （2026年10月21日）。**本記録の作成者が記事全文で確認した**〈齟齬1〉
  2. 2. 実行third_party[1]
    **復号した本体を、ディスクに置かずに実行する。** **`memfd_create` システムコールで `kworker` という名前の無名ファイルを作成し、 そこへ ChaCha20 復号した Noodle RAT 本体を書き込んで `execve` で実行する。** **`memfd_create` が失敗した場合、または環境変数 `STUB_MODE` に `file` が 設定されていた場合は `/tmp/.0000e444` に書き込んで実行する。** さらに**環境変数 `STUB_ARGV0` に値が設定されていれば、コマンドライン引数 （`argv`）を書き換えてプロセス名を偽装する。** **Noodle RAT 本体にも同様の偽装機能が実装されているため、 IIJ は「このローダは Noodle RAT 以外のマルウェアを実行する時にも 使用される可能性がある」と指摘している**（出典1）
    根拠: 同記事。`memfd_create`・`execve`・環境変数の挙動の記述を確認した

    **設定情報は RC4 で暗号化されており、鍵は付け替えられていた**—— **過去に観測された Noodle RAT では `r0st@#$`、今回の検体では `mBCHk?u`。** **ただし偽装先プロセス名を復号するコードは古い鍵を使うままで、 この機能は正常に動作しない。IIJ は「マルウェア開発者のミスだと考えられる」とする** （設定情報側の復号は正しく実装されている）。 **復号できた設定は、偽装先プロセス名 `/usr/bin/sshd`、 C2 サーバ `127.0.0.1:9000` と `192.0.2.9:443`、稼働時間 `00-24`、 稼働曜日 `1;1;1;1;1;1;1;`（全曜日）、通信間隔 `5`**（出典1）

攻撃者が自分で VirusTotal に上げて、検知されないことを確かめていた発覚の端緒

2026年9月、IIJ は VirusTotal にアップロードされた複数の Linux 版 Noodle RAT とローダを観測した（出典1）。気づきの手がかりは、上げ方そのものだった。 検体は同時期に同一のユーザによって API 経由でアップロードされており、 ファイル名が vt-submit-x64.bin・vt2-packed-x64 だった。 IIJ は「攻撃者がマルウェアの検知回避性能を検証する目的で VirusTotal にアップロードした可能性が高い」と評価している。 アップロード元は日本の IP アドレスで、Submitter ID は 1f915147 である。 そして記事執筆時点で、ローダのアンチウイルス製品による検知率は0%だった（出典1）。 記事の題名にある「FUD」は Fully UnDetectable の略で、 攻撃者側が「どの製品にも検知されない」状態を指して使う言葉である（本記録の補足）。 つまり攻撃者は、FUD であることを確認するために VirusTotal を使った ——検知率は防御側の指標だが、同じ数字を攻撃側も読んでいる（本記録の評価）。ただし IP アドレスが日本であることを過大に読まないこと（本記録の留保）。 VPN・クラウド・踏み台のいずれでも日本の IP は得られる。 IIJ も攻撃者の所在については何も述べていない（unknowns 1）。

ローダは自分の末尾に本体を抱え、無名ファイルから直接実行する原因・手口

ローダの動きは4段階である（出典1）。①自分自身を読む。 実行されると /proc/self/exe（ローダ自身）の 末尾60バイトを読み取る。 この領域は NLKA01\x00\x01 というマジック値から始まり、 Noodle RAT 本体のサイズや復号処理で使用するパラメータを含む。 ②本体を復号する。 オフセット 0x5B88 以降に存在する ChaCha20 で暗号化された Noodle RAT 本体を読み取り、 末尾から取得したパラメータを使って復号する。 ③ディスクに置かずに実行する。 memfd_create システムコールで kworker という名前の無名ファイルを作成し、そこへ復号した本体を書き込んで execve で実行する。 kworker は Linux のカーネルワーカースレッドの名前であり、 プロセス一覧の中で最も目立たない名前のひとつである（本記録の補足）。④失敗したときの逃げ道を持つ。 memfd_create が失敗した場合、 または環境変数 STUB_MODE に file が設定されていた場合は /tmp/.0000e444 に本体を書き込んで実行する。 さらに環境変数 STUB_ARGV0 に値が設定されていれば、 コマンドライン引数（argv）を書き換えてプロセス名を偽装する。 ここから2つのことが言える（本記録の評価）。 1つは、ファイルを走査する防御が構造的に空振りすること。 ディスクに現れるのはローダだけで、Noodle RAT 本体の実体はメモリ上にしか無い。 検知率0%はこの作りの結果である。 もう1つは、このローダが Noodle RAT 専用ではないこと。 IIJ も「このローダは Noodle RAT 以外のマルウェアを実行する時にも 使用される可能性がある」と指摘している—— 本体を差し替えれば同じ運び方が使える。

RC4 鍵の付け替えに失敗していて、プロセス名の偽装は動かない原因・手口

設定情報の暗号鍵は変わっていた（出典1）。 過去に観測された Noodle RAT では、偽装先プロセス名と設定情報が RC4 鍵 r0st@#$ で暗号化されていた。今回の検体ではこれが mBCHk?u になっている。 ところが付け替えは徹底されていなかった。 偽装先プロセス名を復号するコードは古い鍵 r0st@#$ を使うままで、 この機能は正常に動作しない。 設定情報の方の復号は正しく実装されている。 IIJ は「これはマルウェア開発者のミスだと考えられる」としている（出典1）。復号できた設定はこうだった（検体 packed-x64・SHA256 5cc6aad1… のもの。 設定は検体ごとに異なる）。
- 偽装先プロセス名: /usr/bin/sshd - C2 サーバ1: 127.0.0.1:9000（ループバックアドレス） - C2 サーバ2: 192.0.2.9:443（RFC 5737 の例示用アドレス） - 稼働時間: 00-24（0時〜24時） - 稼働曜日: 1;1;1;1;1;1;1;（日曜日〜土曜日） - 通信間隔: 5（単位の明示は無い・齟齬2）実装ミスの発見には実務上の意味がある（本記録の評価）。 偽装先プロセス名の復号が壊れているなら、この検体は /usr/bin/sshd を名乗らない。 逆に言えば、実攻撃の検体で このバグが直っていれば、プロセス名を見た調査は確実に騙される。 分析記事のこの種の指摘は、検体ごとの差を読む手がかりになる。

C2 がループバックと例示用アドレス——これは実攻撃の検体ではない被害規模・影響範囲

C2 の設定が、この検体の性格を決めている（出典1）。127.0.0.1（ループバック）と 192.0.2.9（RFC 5737 の TEST-NET-1。 文書で例示に使うために予約されたアドレス）は、 どちらも実際の通信先になりえない。 IIJ は「C2 サーバとしてループバックアドレスおよび例示用アドレスが 指定されていることから、記事冒頭にも記述した通り、この Noodle RAT は 実際の攻撃で使用するためのものではなく、主にローダの検知回避性能を テストする目的でアップロードされた可能性が高いといえる」と結論している。 本記録はこの区別を重く扱う（本記録の整理）。 本件は「侵害事案」ではない。被害組織も、持ち出された情報も無い。 観測されたのは、攻撃の準備段階——道具の仕上がりを攻撃者が確認する作業である。 それでも記録する理由は2つある。 ①IIJ 自身が「2026年においても Noodle RAT（ローダ）の開発は続いていて、 攻撃でも使用される可能性が高いため、今後も警戒が必要」と述べている（出典1）。 ②検知の手がかり（NLKA01 のマジック値・memfd_create からの実行・ /tmp/.0000e444・kworker を名乗る無名ファイル）が、 実攻撃の検体でもそのまま使える（本記録の評価）。 道具の構造は、C2 を書き換えても変わらない。

Linux サーバの「見えなさ」が、そのまま検知率0%になっている評価・解釈

本記録の評価を1つに絞る。この0%は、ローダの出来の良さだけで説明できない。 memfd_create による無名ファイルの実行は、Linux の正規の仕組みである （本記録の整理）。ディスクに実体を作らずにプログラムを動かせる。 ファイルを走査する前提の防御——つまり多くのアンチウイルス製品——は、 この経路では何も見るものが無い。 攻撃者がやったのは、既にある仕組みを使ってファイルを消しただけである。 日本の組織に当てはめると、問題は製品ではなく配備の側にある（本記録の評価）。 Windows 端末にはプロセス実行のテレメトリ（EDR）が入っているのに、 Linux サーバには入っていない組織が多い。 Noodle RAT の標的は後者である。 検知の設計としては、見る場所を変えるしかない（本記録の推奨。lessons へ続く）。 ①プロセスの実体を /proc/<pid>/exe で確認する ——ps の表示は argv の書き換えで偽装される。 ②memfd_create 由来のファイルからの execve を異常として扱う。 ③外向き通信を既定で拒否する。 ①〜③はいずれも製品の検知率に依存しない。 「検知率0%」のマルウェアに対して、組織側に残っている手はこの3つである。

  • **ELF の末尾にマジック値 `NLKA01` を持つファイルを探す**
    **ローダは自分の末尾60バイトに `NLKA01\x00\x01` から始まるメタデータを 持ち、オフセット `0x5B88` 以降に ChaCha20 暗号化された本体を抱える**（出典1）。 **これはハッシュと違い、再ビルドでも残る特徴である**（本記録の評価）
    取るべき行動 **YARA ルールを書いて、サーバ上の ELF と受信ファイルを走査する。** **末尾のマジック値と、ファイルサイズが `0x5B88` を大きく超える ELF という組み合わせで絞る**
  • **`/tmp` の隠しファイルと `noexec` を見直す**
    **`memfd_create` が失敗したとき、または `STUB_MODE=file` のときは `/tmp/.0000e444` に書き込んで実行する**（出典1）。 **ドット始まりの名前で `ls` の既定表示から消える**
    取るべき行動 **`/tmp`・`/var/tmp`・`/dev/shm` を `noexec` でマウントする （迂回されるが段階を1つ増やせる）。** **これらの配下のドット始まりファイルの作成を監視する**
  • **サーバの外向き通信を既定で拒否する**
    **設定情報は稼働時間・稼働曜日・通信間隔の項目を持つ**（出典1）。 **実攻撃の検体は、時間帯を絞った定期的なビーコンを打つ作りである** （本記録の読み。本件の C2 はループバックと例示用アドレスで実在しない）
    取るべき行動 **サーバからの egress を既定拒否にし、必要な宛先だけ許可する。** **許可できない環境では、宛先と時刻を記録して 「一定間隔で同じ宛先に出ている通信」を定期的に抽出する**
