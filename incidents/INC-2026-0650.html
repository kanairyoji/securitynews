INC-2026-0650Broadcom WPS に未修正RCE・CVE無し

独立研究者 Quentin Kaiser は2026年10月16日、Hexacon（パリ）で Broadcom の 独自 WPS 実装にある未修正のメモリ破壊脆弱性「WPSplinter」を公開した—— 断片化した WPS の EAP メッセージを再結合する際に宛先バッファの大きさで 制限していないため、**電波の届く範囲にいる攻撃者が Wi-Fi のパスワードも WPS の登録手続きも要らずに任意コードを実行できる**。影響は eCos 系 （BCM3380・BCM3383・BCM33834）と Linux 系（BCM3390・BCM63xx・BCM65xx・ BCM68xx）に及び、研究者の一覧は19社・約70機種を挙げる（網羅ではない）。 **Broadcom は「サポート期間外の旧ソフトウェア」として CVE の登録を拒み**、 CERT/CC も Broadcom 自身が CNA であることを理由に同日で受付を閉じた。 2018年に不完全な修正が静かに入っていたが、研究者が確認した機種は 2026年10月15日時点でどれも未修正だった。台湾では Zyxel が 2機種の該当を認めて Broadcom と協議中、Netgear の代理店は該当2機種が 台湾未導入と回答した

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備脆弱性の放置委託先・供給元起因

電波が届く距離にいる他人が、パスワード無しでルータの中でコードを動かせます。そして、直す経路がありません。

2026年10月16日、独立研究者の Quentin Kaiser は、パリで開かれたHexacon で Broadcom の Wi-Fi 実装にある未修正の脆弱性を公開しました（出典1・2）。研究者が付けた名前は「WPSplinter」で、CVE 番号はありません（出典2）。

成立の条件は、次の3つだけです（出典1・2）。

  • 攻撃者が Wi-Fi の電波の届く範囲にいること
  • Wi-Fi のパスワード（PSK）は要らないこと
  • WPS の登録手続き（enrollment）を完了させる必要もないこと——脆弱なパーサは、正常な登録が終わる前の段階で到達できる

結果として得られるのは、制御された情報漏えいと任意コードの実行です（出典2）。研究者は、ベルギーの主要 ISP 4社のうち3社が配っているゲートウェイで実際に動かしており、Orange Belgium の ASKEY TCG3000 では未認証のリモートコード実行に加えて、シェルコードで PSK（Wi-Fi の鍵）を802.11 経由で持ち出すところまで実証しています（出典1）。

本事案の核心は、脆弱性そのものよりも「直す経路が無い」ことです。

止まらなかったのは「断片を再結合するときに、宛先の大きさを見ていない」1点である原因・手口出典 [1] [2]

公表されている技術的な原因は1行で書ける（出典1・2）。

Broadcom の legacy WPS Monitor は、再結合した EAP-WPS の断片を宛先バッファの大きさで正しく制限していない（出典2。原文英語を本記録が訳した）

WPS（Wi-Fi Protected Setup）の手続きは EAP の上で動き、長いメッセージは断片に分けて送られる。受け手はそれを繋ぎ直す。その繋ぎ直しの際に、入れ物の大きさを見ていない（出典1・2。整理は本記録）。

成立の前提が極端に軽いのが本件の性質である（出典1・2）。

「forever day（永久に直らない日）」は zero-day の対義的な言い方で、修正が出ないまま残り続ける欠陥を指す（本記録の補足）。

CVE が無いのは偶然ではなく、CNA が自分で登録しないと決めたからである評価・解釈出典 [1] [2]

本件に CVE 番号が無い経緯は、研究者の開示記録に時系列で残っている（出典1）。

拒否の理由として公表されているのは「当該ソフトウェアは旧式であり、サポート期間の外である」である（出典2）。

ここから先は本記録の評価である。

CVE が無いと、次の3つが同時に成り立たなくなる。

  1. スキャナ・SBOM 照合・依存関係の警告はすべて CVE 番号を鍵に動く。番号が無い欠陥は、どの自動点検にも現れない——「赤くならない」ことが安全の根拠にならない
  2. OEM・ISP への問い合わせに共通の識別子が使えない。「WPSplinter」は研究者が付けた名前で、ベンダーの受付窓口がそれで検索できる保証は無い
  3. 「対応済みか」を組織として記録・監査する欄が作れない。脆弱性管理台帳は CVE 単位で作られているため、本件は台帳に乗らない

出典1 の著者は、Broadcom が公表も登録もしなかったことが、多くの OEM が修正を取り込まなかった理由かもしれないと述べている（出典1）。2018年の不完全な修正が「静かに」入ったという記述も同じ構図である（出典1。整理は本記録）—— 修正が存在しても、それが脆弱性への対処だと誰も知らなければ適用されない。

第一に、最初に打てた手は機能の無効化だけだった。 修正ファームウェアの配布には Broadcom → OEM → ISP → 利用者という4段の連鎖が必要で、先頭の Broadcom が公表も CVE 登録もしていない（出典1。整理は本記録）。ISP が自力で決められるのは、自分の管理下にある設定だけである。

第二に、その無効化が効くかどうかに留保が付いている。 出典2 は「WPS の設定の切り替えが、脆弱なパーサを取り除く、あるいは完全に無効化するとは限らない」と明記している（出典2）—— つまり ISP の対応は「おそらく効く緩和」であって、「検証された修正」ではない（本記録の評価）。

第三に、対応の差が出たのは研究者と連絡が付いたかどうかに対応している（本記録の評価）。Proximus は7月29日に CVD フォーム経由で全文の報告を受け取り、8月25日に PSIRT のアナリストが追加の通話を行っている（出典1）—— 最も具体的な対応（WPS 無効化＋修正計画）を公表したのはこの ISP である。 一方 Orange Belgium は、8月18日に CISO が研究者を LinkedIn でフォローしたという記述しか無く、正式な返答は無かったとされる（出典1）。受付窓口（CVD の受け口）が機能していたかどうかが、3か月後の対応の差になっている（本記録の評価）。

「悪用は確認されていない」と「悪用されても分からない」は両立している未確定事項出典 [1] [2]

実環境での攻撃が観測されたという公表は、本記録の確認時点で無い（本記録の確認）。公開されたのは研究者による実機での実証であり、実証コードは出ていない（出典1）。一部の報道は見出しに「Active Exploitation Alert（活発な悪用の警告）」を掲げているが、本記録が確認した一次資料に実環境での悪用の記述は無い（本記録の確認）〈齟齬5〉。

ただし、本件では「確認されていない」という言葉の重みが普段より軽い（本記録の評価）。

  • 攻撃は電波の届く範囲から行われる。 ネットワークのログには外部からの接続として現れない
  • 攻撃対象は ISP 貸与のゲートウェイや家庭用ルータである。エンドポイント検知は入っておらず、802.11 の管理フレームやEAP のやり取りを記録している機器はまず存在しない
  • 侵害判定の指標（IoC）は公表されていない（本記録の確認）

したがって、利用者側には「攻撃されたか」を事後に判定する手段が無い（本記録の評価）。公開されている YARA ルールとフィンガープリント用スクリプトは、いずれも「脆弱か」を調べる道具であって「攻撃されたか」を調べる道具ではない（出典1・2。整理は本記録）。

この構図は、CVE が無いこととあわせて効く（本記録の指摘）—— 脆弱性管理台帳に乗らず、スキャナにも映らず、攻撃の痕跡も残らない。組織として「この件は大丈夫だった」と言える材料が、どの方向からも手に入らない。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Broadcom は、パッチは提供可能としながら、 CVE の登録と OEM への通知内容の共有をいずれも拒否した（2026年7月29日）。 対外的な公表も行っていない不十分**本記録の評価である。** 「サポート期間外」という線引きは、 供給元の製品ライフサイクルの話であって、 **現に稼働している機器の台数とは無関係である**—— 研究者の概算ではベルギーの3社だけで約156万台が該当しうる（出典1）。 **判断の帰結は「直す経路が無い」状態の固定であり、 利用者側に残った手は機能の無効化と機器の交換だけになった。**
Proximus は BBOX 群の WPS を全面的に無効化し、 数週間のうちに全面的な修正を行う計画を公表した（2026年10月20日時点）部分的に機能**本記録の評価である。** 無効化は、ISP が自力で全台に適用できる 唯一の手段であり、打つ手として妥当である。 **ただし出典2 が「WPS の設定の切り替えが、脆弱なパーサを取り除く、 あるいは完全に無効化するとは限らない」と明記しているため、 effective とは書けない**—— **これは「おそらく効く緩和」であって「検証された修正」ではない。**
CISO・経営層への示唆
  • 「CVE が無い」は「危険が無い」ではなく、「管理の仕組みに乗らない」である
    脆弱性管理の実務は CVE 番号を鍵に動いている——スキャナの照合、 SBOM の突き合わせ、ベンダー勧告の購読、台帳への記載、監査への報告のすべてである。 **本件は CNA（Broadcom 自身）が登録を拒んだため、 これらのどこにも現れない**（出典1・2）。 **CERT/CC も「その CNA が登録しないから」という理由で同日に受付を閉じた**（出典1）
    取るべき行動 **CVE 番号を持たない脆弱性情報を受け取る経路を1本持つ。** 具体的には、①自社が使う主要な SoC・組込みベンダーについて、 研究者の公開（カンファレンス発表・個人ブログ）を追う担当と頻度を決める、 ②脆弱性管理台帳に「CVE 無し」の行を作れるようにする （番号欄を必須にしているとそもそも登録できない）、 ③「スキャナが赤くならない」ことを安全の根拠にしないと明文化する。 **本件を台帳に載せるなら、鍵は「WPSplinter／Broadcom legacy WPS Monitor」である**
  • 供給元が「サポート期間外」と言った時点で、リスクは自社に移る
    **Broadcom の拒否理由は「当該ソフトウェアは旧式でサポート期間外」である**（出典2）。 **しかし稼働している機器はその判断とは無関係に動き続けている**—— 研究者の概算ではベルギーの ISP 3社だけで約156万台が該当しうる（出典1）。 **eCos 系の機種は「決定的な forever day」とされ、修正の経路が無い**（出典1）
    取るべき行動 **ネットワーク機器・組込み機器の資産台帳に「供給元のサポート終了日」と 「修正経路の有無」の2列を足す。** サポート終了済みで修正経路が無い機器を抽出し、 ①交換の予算と時期を決める、②交換までの間に受け入れるリスクを 文書化して承認を取る、のどちらかに必ず振り分ける。 **「いつか替える」のまま放置された機器が、本件のような 直せない脆弱性の受け皿になる**
  • 受付窓口（CVD の受け口）が機能しているかどうかが、3か月後の対応の差になる
    **Proximus は7月29日に CVD フォーム経由で全文の報告を受け取り、 8月25日に PSIRT のアナリストが追加の通話を行い、 10月20日時点で最も具体的な対応（WPS の全面無効化＋修正計画）を公表している**（出典1）。 **一方 Orange Belgium については、8月18日に CISO が研究者を LinkedIn でフォローしたという記述しか無く、正式な返答は無かったとされる**（出典1）。 **同じ情報が同じ時期に届いていながら、3か月後の状態が違う**（本記録の整理）
    取るべき行動 **自社の脆弱性受付窓口を、外部の研究者の立場から実際に試す。** ①公開ページから窓口（CVD フォーム・security.txt・連絡先メール）に 到達できるか、②送った報告に何日で人間の返信が来るか、 ③受け取った報告が PSIRT 相当の判断者まで届くか、を年1回測る。 **窓口が無い／返信が来ない組織には、研究者は公開で知らせることになる**
  • 「悪用は確認されていない」が安心の材料にならない事案がある
    **本件の攻撃は電波の届く範囲から行われ、対象は ISP 貸与ゲートウェイや 家庭用ルータである**（出典1・2）。 **これらにエンドポイント検知は無く、802.11 のやり取りを記録する仕組みも 無く、IoC も公表されていない**（本記録の評価）—— **つまり悪用の有無を事後に判定する手段がそもそも無い**
    取るべき行動 **「検知できない資産」の一覧を作り、報告の文面を変える。** ログもエージェントも無い機器については、 「侵害は確認されていない」ではなく 「侵害の有無を確認する手段が無い」と書く。 そのうえで、①その機器が侵害された場合にどこまで到達されるかを図にする、 ②到達範囲を狭める統制（セグメント分離・端点間の暗号化・ 管理面への到達禁止）を機器を直せない前提で置く
セキュリティ技術者への示唆
  • 攻撃者の位置が「電波の届く範囲」だと、境界の統制はすべて経路の外にある
    **成立条件は、電波の届く範囲にいること・PSK 不要・WPS 登録の完了も不要である** （出典1・2）。 **ファイアウォール、VPN、WAF、IDS はいずれも 802.11 の EAP のやり取りの経路上に存在しない**（本記録の整理）。 **実証では、シェルコードが PSK を 802.11 経由で持ち出している**（出典1）—— **持ち出しも上流のネットワークを通らない**
    取るべき行動 **執務室・店舗・工場の Wi-Fi が建物の外にどこまで届くかを実測する。** そのうえで、①無線網を業務ネットワークから分離する、 ②無線側から機器の管理面（管理画面・SSH・SNMP）に到達できないようにする、 ③無線網の内側でも端点間の暗号化を前提にする。 **出力を下げるのは到達距離を縮めるだけで成立そのものは防げない** （研究者は長距離でも動くと述べている）
  • WPS の無効化は緩和であって修正ではない——「対処済み」と記録すると誤った安心が残る
    **出典2 は「WPS の設定の切り替えが、脆弱なパーサを取り除く、 あるいは完全に無効化するとは限らない」と明記している**（出典2）。 **ISP が打った手（Proximus の BBOX 群での WPS 無効化）も、 この留保の下にある**（出典1。整理は本記録）
    取るべき行動 **脆弱性管理台帳で「緩和（mitigation）」と「修正（fix）」の欄を分ける。** WPS 無効化は緩和の欄に入れ、修正の欄は 「OEM／ISP の修正ファームウェア適用」のまま未了にしておく。 **あわせて、無効化が実際に効いているかを 研究者のフィンガープリント用スクリプトで確認する （自組織の管理下の機器に対してのみ）**
  • 型番の照合では該当可否が決まらない——SoC と実装を聞くしかない
    **出典2 は2つのことを同時に明記している**（出典2）—— **①「SoC が一致することだけでは、そのファームウェアが脆弱であることの 確認にはならない」、②「一覧に載っていない機器が安全とは限らない」。** **影響する SDK のバージョン範囲は公表されていない**〈未確定2〉—— **バージョンでも型番でも判定できない**
    取るべき行動 **ベンダー／ISP への問い合わせ文面を、CVE 番号ではなく技術の記述で作る。** 含める要素は、①対象機器の型番とファームウェア版、 ②「Broadcom の legacy WPS Monitor を使っているか」、 ③「WPS の EAP 断片の再結合に関する2026年の問題（研究者名 WPSplinter）に 対処済みか」、④「hostapd ベースの実装へ移行済みか」。 **「CVE はありますか」と聞くと「該当 CVE なし」と返ってくる**
  • 検出の道具は「脆弱か」を調べるもので、「攻撃されたか」は分からない
    **公開されているのは、抽出済みファームウェアに当てる YARA ルールと、 稼働中のアクセスポイントの電波から判定するスクリプトである**（出典1・2）。 **研究者自身が「triage の補助であって確認ではない」としている**（出典2）。 **侵害判定の指標（IoC）は公表されていない**（本記録の確認）
    取るべき行動 **棚卸しと侵害調査を別の作業として計画する。** 棚卸しは公開ツールで進められるが、侵害調査は現状できない—— **できないことを「調査中」と書かず「判定手段が無い」と記録する。** そのうえで、機器が侵害された前提で影響を限定する設計 （セグメント分離・管理面の分離・端点間暗号化）を優先する

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。

システム構成□ Broadcom の SoC（BCM3380・BCM3383・BCM33834・BCM3390・BCM63xx・ BCM65xx・BCM68xx）を使う Wi-Fi 機器を、自社の拠点・店舗・工場、 または従業員の在宅勤務環境で使っている本件の影響範囲そのもの。 **ただし出典2 は「SoC の一致だけでは確認にならない」と明記しており、 該当の判定はベンダーへの問い合わせでしか行えない**

委託・第三者部品□ 自社製品に Broadcom の Wi-Fi SDK（legacy WPS Monitor を含む版）を 組み込んで出荷しており、hostapd ベースの実装へ移行していない**供給元は CVE を登録せず、OEM への通知内容も共有していない**（出典1）—— **自社製品が該当するかを、供給元の告知を待っていても分からない。** eCos 系を使っている場合、修正には SDK の移行が必要になる

運用・監視□ Wi-Fi 機器にエンドポイント検知もログ収集も無く、 802.11 の管理フレーム・EAP のやり取りを記録していない**攻撃は電波経由で行われ、上流のネットワークには現れない**（出典1・2）。 **IoC も公表されていないため、悪用の有無を事後に判定できない**—— 「侵害は確認されていない」と報告できる根拠が無い
