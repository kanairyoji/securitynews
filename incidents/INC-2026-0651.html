INC-2026-0651MCP 横断のSSRF・Google に CVE 発行

独立研究者 Syed Anas Mohiuddin は、複数の組織の MCP（Model Context Protocol） サーバに同型のサーバサイドリクエストフォージェリ（SSRF）があることを公表した—— Google の「MCP Toolbox for Databases」の汎用 HTTP ソース／ツールにある CVE-2026-14540（CWE-918・CVSS v4.0 基本値8.0・High）は、HTTP クライアントが リダイレクト方針を制限せず宛先 IP も検証しないため、細工した path パラメータで 内部エンドポイントへ要求を出させられる。**同じ思い込み（「信頼の確認は どこか別の場所で済んでいる」）が Google・JPMorgan Chase・Weaviate・ フランス DINUM・インドネシア タンゲラン市の5組織で独立に修正された。** 研究者は、MCP の出力に仕込んだ指示が A2A の委任を通って別のエージェントの 権限で実行される攻撃類型を「Protocol Pivoting」と名付けている。 Google は v1.5.0（2026年6月18日）で SSRFGuard を入れて修正済みだが、 日本のデジタル庁の MCP サーバについては別種の指摘（認証が無い）が 未解決のまま残っている

脆弱性委託先・再委託先起因で委託元多数に波及続報が続いている日本に波及した海外事案設計・実装上の不備委託先・供給元起因
初報: 2026年7月31日（CVE-2026-14540 の公開） 最終更新: 2026年10月21日

5つの組織が、連絡を取り合わずに同じ欠陥を直しました。

独立研究者の Syed Anas Mohiuddin は、複数の組織の MCP（Model Context Protocol）サーバに同型のサーバサイドリクエストフォージェリ（SSRF）があることを公表しました（出典1・2・3）。このうち Google の「MCP Toolbox for Databases」のものにはCVE 番号が発行されています（出典1）。

原因は2つの欠落です（出典1）。

  • HTTP クライアントが、リダイレクトを安全に制限する方針を持たずに初期化されていた（internal/sources/http/http.go）
  • 宛先 IP アドレスの検証が無かった

結果として、細工した path パラメータでリダイレクトを起こすと、Toolbox が内部または外部のエンドポイントへ許可されていない要求を出します（出典1）。勧告は「悪意あるデータ駆動のプロンプトからも発火しうる」と付記しています（出典1）。

本事案の論点は、CVE 1件の深刻度ではありません。 研究者が示したのは、同じ思い込みが別々の組織で独立に成立していたという事実です（出典2・3）。

研究者はこれを「同じ悪い前提（one bad assumption）」と呼んでいます（出典2）—— 「URL が信頼境界を越えたのに、その境界で誰も検査しなかった」。

さらに研究者は、MCP 単体では閉じない攻撃類型を「Protocol Pivoting」と名付けています（出典2・3）。仕組みは4段です（出典3）。

  1. 攻撃者が、MCP ツールの返す内容に A2A のタスク指示の形をした文を仕込む
  2. 統括エージェントがその出力を読み、通常の委任として子エージェントへ指示を渡す
  3. 子エージェントは統括エージェントを信頼して指示を実行する
  4. その子エージェントの MCP サーバに SSRF があれば、要求は信頼境界の内側から、子エージェントのネットワーク位置と権限で出る

どの部品も古典的な意味では「侵害」されていません（出典3）—— それぞれが設計どおりに動いた結果です。

なお、Google の修正は2026年6月18日、CVE の公開は7月31日であり、本記録の起点となった報道（2026年10月21日）はこれらより3〜4か月後です（本記録の整理）〈齟齬3〉—— 「新しく見つかった脆弱性」ではなく、「既に修正された一連の指摘が、研究者の整理によってまとめて報じられたもの」です。

「Protocol Pivoting」は、どの部品も侵害せずに信頼境界を越える評価・解釈出典 [3] [5]

研究者が名付けた攻撃類型「Protocol Pivoting」の定義はこうである（出典3）。

複数のプロトコルを使うエージェント基盤（ツール用の MCP、エージェント間委任の A2A、発見用の ANP など）において、1つのノードを制御する攻撃者が、委任を利用して信頼境界を越える攻撃類型（出典3。原文英語を本記録が訳した）

手順は4段である（出典3）。

  1. 攻撃者が、MCP ツールの返す内容に、A2A のタスク指示の形をした文を仕込む
  2. 統括エージェントがその出力を読み、通常の委任として子エージェントへ渡す
  3. 子エージェントは統括エージェントを信頼して指示を実行する
  4. その子エージェントの MCP サーバに SSRF があれば、要求は信頼境界の内側から、子エージェントのネットワーク位置と権限で出る

研究者が強調しているのは、次の2点である（出典3）。

  • どの部品も古典的な意味では侵害されていない。 それぞれが設計どおりに動く
  • この攻撃は SSRF に依存しない。 SSRF は、特権のある外向き要求を得る具体的な一手段にすぎない

報道も同じ点を伝えている（出典5）—— 「攻撃者は AI エージェントが読む外部の内容に悪意ある指示を植え込める。エージェントが作業を別のエージェントへ渡すとき、悪意ある指示も一緒に渡されうる。受け取ったエージェントがその操作が認可されているかを確認しなければ、本来は制限されていた操作を指示どおりに実行してしまう」（出典5）。

ここから先は本記録の評価である。

防御の観点で厄介なのは、各段が「正常」だということである。

段 見た目 検知の手がかり
ツール出力に指示が混ざる 正規のツール呼び出しの戻り値 内容の検査が必要。形式では区別できない
統括→子への委任 正規の A2A の委任 委任自体は日常的に起きる
子が実行する 正規のツール実行 実行主体の権限で動くので、権限違反としては映らない
SSRF で内部へ要求 正規サービスからの HTTP 要求 外部からの不審な接続としては映らない

つまり、どの層で見ても「異常な通信」としては現れない（本記録の評価）。残る手は、①ツール出力を指示として解釈させない設計、②委任のたびに認可を確認する仕組み、③エージェントの外向き・内向き通信を宛先で絞ることの3つである（本記録の整理。mitigations 参照）。

ここで押さえておくべき設計上の要点を、本記録の評価として書く。

第一に、「URL の検査」では足りず「IP の検査」が必要だという点である。 DNS リバインディングは、同じホスト名が検査の時点と接続の時点で違う IP を返す攻撃である（本記録の補足）—— したがって、名前解決の結果を接続の直前に検査しなければ意味がない。 研究者がタンゲラン市の件を「ホスト名の解決結果を一度も検査していない」と整理しているのは、まさにこの点である（出典3）。

第二に、リダイレクトを追うたびに検査が必要だという点である。 1回目の宛先が許可された IP でも、リダイレクト先が内部の IP なら SSRF は成立する（本記録の整理）—— これが CVE-2026-14540 の原因そのものだった。

第三に、既定値が安全側であることと、利用者が設定を書いていることは別だという点である（本記録の評価）。allowPrivateNetworks のような項目は、社内 API を参照する正規の設定を動かすために有効化されやすい——そこで広く許可してしまえば、修正の効果は失われる。

内部探索機会はあったが検知できず
**本記録の評価である。** 要求は実際にネットワークを流れるため、 外向き・内向きの宛先を記録していれば見える。 **ただし SSRF は正規のサービスが自分の権限で出した要求として現れ、 外部からの不審な接続としては映らない**—— **エージェント基盤の通信記録を取っていない組織では 事後の判定もできない**
影響を限定できた私設ネットワークへの到達を既定で遮断し、許可する範囲を明示的に設定する　**v1.5.0 で追加された設定項目 （`allowPrivateNetworks`・`allowedIpRanges`・`customBlockedIpRanges`）が これに当たる**（出典4）—— **ただし社内 API を参照する正規の設定のために広く許可すると 効果が失われる**（本記録の注意）
影響を限定できたエージェント実行環境を専用ネットワークに置き、メタデータサービスと管理面を遮断する　**本記録の評価。** 製品側の修正とは独立に、 利用側で置ける統制である—— **修正が出ていない MCP サーバを使う場合、ここだけが残る手になる**
横展開現実的な検知機会なし
**本記録の評価である。** 委任は日常的に起きる正規の動作であり、 実行は子エージェント自身の権限で行われるため、 権限違反としても異常通信としても現れない。 **各段が設計どおりに動いた結果なので、 「どこかが壊れた」という形の検知が成立しない**
侵入を防げたエージェントが機微データへのアクセスや高権限の操作を行う前に、認可の有無を確認する　出典5 が企業向けの対処として整理している点。 **ただし確認の判断自体をモデルに任せると、 同じプロンプトインジェクションの影響下に置かれる**（本記録の注意）
検知できた委任で渡される指示の出所を記録し、ツール出力由来のものを区別する　**本記録の評価。** 「この指示は人間から来たのか、 ツールの戻り値から来たのか」を追跡できる基盤設計が無いと、 事後の調査もできない

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Google は修正を先に公開（2026年6月18日・v1.5.0）し、 CVE-2026-14540 は43日後の7月31日に公開した。 PR の題名は `fix(source/http): implement SSRF guard` で、 リリースノートの分類は「Bug Fixes」だった部分的に機能**本記録の評価である。** 修正そのものの速度と内容 （`SSRFGuard`・二層の検証・設定項目の追加）は十分である。 **評価を partial にしたのは、 「直ったことが利用者に届く経路」が整っていないためである**—— **勧告の構造化欄（パッケージ名・影響バージョン・修正バージョン）が Unknown のままでは、影響範囲が説明文の中にしか存在せず、 依存関係の自動警告も SBOM 照合も働かない。** **これは Google 固有の問題ではなく、 MCP サーバの多くがパッケージとして配布されていない構造の問題でもある** （本記録の整理）。
研究者は、組織ごとに異なる経路で報告した—— Google は GitHub 経由で CVE 発行まで至り、 Weaviate は HackerOne、タンゲラン市は GitHub の勧告、 Anthropic と Microsoft は Full Disclosure での公開、 デジタル庁は JPCERT/CC への報告である評価材料なし**評価できる材料がない**（本記録の判断）。 **各組織の受付窓口がどう応答したか、 研究者がどの時点でどの経路を選んだかは公表されていない。** **本記録が確認できるのは結果（経路と修正状況の一覧）だけである**（出典3）。
CISO・経営層への示唆
  • MCP サーバは「自前で書いて動かす部品」であり、組織の規模と実装の質が相関しない
    **同型の SSRF を独立に修正した5組織には、 大手クラウド事業者（Google）、金融機関（JPMorgan Chase）、 国の行政機関（フランス DINUM）、自治体（インドネシア タンゲラン市）が 並んでいる**（出典3）。 **研究者は16件の GitHub 勧告で謝辞に挙げられており、 指摘は特定のベンダーに限られていない**（出典3）。 **自治体が SIEM（Wazuh）の MCP サーバを自前で公開していた例もある**（出典3）
    取るべき行動 **自組織が「使っている」「公開している」MCP サーバの一覧を作る。** ①社内のエージェント基盤に組み込んだ MCP サーバ（製品・OSS・自作）、 ②外部へ公開している MCP サーバ（自組織のデータを提供するもの）、 ③従業員が個人の判断で設定に加えたもの、の3区分で数える。 **③は端末管理の仕組みから設定ファイルを集めないと見えない**
  • 「修正が出ている」ことと「利用者が気づける」ことは別である
    **Google の修正は2026年6月18日に v1.5.0 として公開されたが、 CVE-2026-14540 の公開は43日後の7月31日である**（出典1・4）。 **PR の題名は `fix(source/http): implement SSRF guard`、 リリースノートの分類は「Bug Fixes」だった**（出典4）。 **さらに CVE 公開後も、勧告の構造化欄（パッケージ名・影響バージョン・ 修正バージョン）はいずれも記載なし／Unknown のままである**（出典1）—— **依存関係の自動警告も SBOM 照合も働かない**
    取るべき行動 **AI エージェント基盤の部品について、 自動検査とは別の追跡経路を置く。** ①使っている MCP サーバ・SDK の一覧を作り、 各リポジトリのリリースノートと勧告を追う担当と頻度を決める、 ②「脆弱性の修正」と明記されていない更新も適用対象に含める運用にする、 ③脆弱性管理台帳に CVE 番号の無い行を作れるようにする。 **「スキャナが赤くならない」ことを安全の根拠にしない**
  • エージェントの権限は「できること」ではなく「どこへ到達できるか」で見る
    **SSRF の影響は、MCP サーバがネットワーク上のどこに届くかで決まる** （出典1・5）。 **Protocol Pivoting では、要求は子エージェントの ネットワーク位置と権限で、信頼境界の内側から出る**（出典3）—— **アカウントの権限を絞っても、ネットワークの到達範囲が広ければ 被害は変わらない**（本記録の評価）
    取るべき行動 **エージェント実行環境ごとに「到達可能なネットワーク範囲」を図にして 承認対象にする。** ①外向きは許可した宛先のみ、 ②内部向けはメタデータサービス（169.254.169.254 等）・ 管理面・他システムの管理 API を遮断、 ③エージェントを専用のセグメントに置く。 **この3つは、使っている MCP サーバに修正が出ていなくても 利用側だけで置ける統制である**
  • 委任を前提にした基盤では、「どの部品も壊れていない侵害」が起きる
    **研究者は Protocol Pivoting について 「どの部品も古典的な意味では侵害されていない。 それぞれが設計どおりに動いた結果である」と明記している**（出典3）。 **統括エージェントがツール出力を読み、委任として子エージェントへ渡し、 子エージェントが統括を信頼して実行する—— 各段はすべて正規の動作である**（出典3）
    取るべき行動 **インシデント対応の想定に「権限違反が1件も出ない侵害」を加える。** ①エージェント間で渡される指示の出所（人間／ツール出力／別エージェント）を 記録する基盤設計を要件に入れる、 ②高権限の操作と機微データへのアクセスの前に認可を確認する段を置く、 ③その確認の判断をモデル自身に委ねない （同じプロンプトインジェクションの影響下に入るため）
セキュリティ技術者への示唆
  • URL の検査では止まらない——検査すべきは接続の直前の IP である
    **CVE-2026-14540 の原因は、リダイレクト方針の欠落と 宛先 IP の検証の欠落である**（出典1）。 **v1.5.0 の `SSRFGuard` は DNS リバインディング（TOCTOU）への対処として 追加されており、自動レビューの要約は 「接続時とリダイレクト時の両方で IP を検証する」と述べている**（出典4）。 **タンゲラン市の件は「ホスト名の解決結果を一度も検査していない」と 整理されている**（出典3）
    取るべき行動 **自組織の HTTP クライアント実装を、次の4点で点検する。** ①リダイレクトを追う前に、毎回、宛先 IP を検証しているか、 ②検証は名前解決の結果に対して、接続の直前に行っているか （検査と接続の間に再解決が入ると意味がない）、 ③私設アドレス範囲・リンクローカル（169.254.0.0/16）・ ループバックを既定で遮断しているか、 ④許可範囲を設定で広げたときに、それが記録に残るか
  • 「ある欄は固めたが、別の欄を見落とす」が最も再発しやすい形である
    **Weaviate は `baseURL` 欄の検証を2026年3月に追加したが、 `apiEndpoint`・`region`・`location` が残っており、 9月まで3段階（PR #10878 → #11683 → #12961）かかっている**（出典2・3）。 **JPMorgan Chase の件は「兄弟ツールには許可一覧があったのに、 取得ツールには無かった」という形である**（出典3）
    取るべき行動 **「外部から来た文字列が HTTP 要求の宛先になる箇所」を 欄単位で網羅的に列挙する。** 設定項目・ツール引数・取得した文書の中の URL・ リダイレクトの Location ヘッダのすべてを対象にし、 ツールごとに「この欄に検証が入っているか」の表を作る。 **1つのツールで直したら、同じリポジトリの他のツールも必ず見る**
  • 走査ツールでは見つからない——手でソースを読む工程が要る
    **研究者は走査ツール `mcp-safeguard` を公開しているが、 自身で「この類型の多くを見逃す」「いくつかの発見は 手でソースを読む必要があった」と述べている**（出典3）。 **MCP サーバはツール面（外から呼べる関数）だけを見ても、 内部で何に接続するかが分からない**（本記録の整理）
    取るべき行動 **MCP サーバのレビュー観点を1枚にして、コードレビューの必須項目にする。** 含める項目は、①外部由来の文字列が宛先になる経路、 ②リダイレクトの扱い、③名前解決の時点と接続の時点のずれ、 ④ツール出力が次の行動の入力になる箇所、 ⑤認証・認可の有無。 **走査ツールは「全部見た」の根拠にしない**
  • SSRF の痕跡は「正規サービスが出した要求」として現れる——記録が無ければ事後に分からない
    **SSRF は、MCP サーバが自分の権限で出した HTTP 要求として現れる** （本記録の評価）。 **外部からの不審な接続としては映らず、 権限違反としても記録されない。** **本記録の確認時点で侵害判定の指標（IoC）は公表されておらず、 攻撃に使われる URL は環境ごとに異なるため値としての IoC が 成立しにくい**（本記録の評価）
    取るべき行動 **エージェント基盤の通信記録を、宛先単位で取る。** ①MCP サーバと AI エージェント実行環境からの外向き・内向き HTTP 要求の宛先、②リダイレクトの最初の宛先と最終の宛先の両方、 ③内部ネットワーク側で「エージェント基盤から来た要求」を受けた記録。 **③を取っておくと、製品側の修正が無い状況でも 「内部へ向いた要求があったか」を後から言える**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ Google の MCP Toolbox for Databases を 0.3.0〜1.4.0 の版で使っており、 汎用 HTTP ソース／ツールを有効にしているCVE-2026-14540 の影響範囲そのもの。 **修正は v1.5.0（2026年6月18日）**。 **勧告の構造化欄が Unknown のため、依存関係の自動警告では気づけない**
システム構成□ AI エージェントの実行環境が、社内ネットワークやクラウドの メタデータサービス（169.254.169.254 等）に到達できる位置にあるSSRF の被害は「MCP サーバがどこへ届くか」で決まる。 **製品側の修正が無い場合、到達範囲の制限が利用側に残る唯一の統制である**
認証・認可□ エージェント間の委任（A2A 等）を使っており、 子エージェントが統括エージェントの指示を認可の確認なしに実行するProtocol Pivoting の成立の鍵はこの段である（出典3）。 **どの部品も侵害されないため、権限違反としても異常通信としても現れない**
データの保持□ エージェントが読む外部の内容（取得した文書・ツールの戻り値・ 提供者が渡す URL）を、指示として解釈しうる形でモデルに渡している勧告は「悪意あるデータ駆動のプロンプトからも発火しうる」と付記している （出典1）。 **攻撃者は MCP サーバへ直接アクセスする必要が無い**
運用・監視□ MCP サーバ・AI エージェント基盤の脆弱性管理が、 CVE 番号を鍵にした自動検査（スキャナ・SBOM・依存関係警告）に依存している**研究者の一連の指摘のうち CVE が発行されたのは2件だけで、 残りは PR・コミット・GitHub 勧告・Full Disclosure の投稿として散っている** （出典2・3）。 **CVE-2026-14540 も構造化欄が Unknown のため自動検査に現れない**
体制・契約□ 自組織が外部へ MCP サーバを公開している（自組織のデータ・API を提供している）**本件の一覧には国の行政機関・自治体・金融機関が並んでいる**（出典3）。 **公開している側は、研究者からの指摘を受け取る窓口と、 修正を反映する経路（PR の受け入れ体制）を持っている必要がある**—— **デジタル庁の件は公開 PR が未マージのまま残っている**
