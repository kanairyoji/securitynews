INC-2026-0652Plex の4件がKEV収載・Plex2Shell

米 CISA は2026年10月20日、Plex Media Server の4件（CVE-2026-96652・96654・ 96655・96656）を悪用確認済み脆弱性リスト（KEV）へ収載した——4件を連鎖させると **未認証のリモート攻撃者が Plex Media Server プロセスの権限で コードを実行できる**。連鎖は研究者 Zach Main が「Plex2Shell」と名付けて 2026年10月16日に実証コードごと公開し、翌17日にはハニーポットで悪用が観測され、 Plex は10月19日に自社の勧告へ「活発かつ広範に悪用されている」と追記した。 **侵害された機器では暗号資産のマイナーとプロキシソフトが動かされている。** 修正は2026年8月に出た 1.43.3.10861 以降で、Plex は 「1.43.3.10861 より古く、インターネットから到達できるサーバは 侵害された可能性があるものとして扱え」と求めている—— **更新だけでは Codecs フォルダに置かれた実体も漏れた管理トークンも消えない。** 同日の KEV 追加は6件で、国産WAF SiteGuard Server Edition と Siemens Software Center の各1件を含む

侵害された機器では、暗号資産のマイナーとプロキシソフトが動かされています（出典1・3・4）。

Plex が挙げている侵害の痕跡は次の4つです（出典1）。

  • Plex Media Server が起動した見慣れないプロセス——とくに myawesomeproxy・mylovelyminer・x12345 という名前のもの
  • Plex の Codecs フォルダにある見慣れない .so または .dll ファイル
  • proxystream.st への外向きの接続
  • 何も再生していないのに CPU 使用率が高い状態が続く

そして、更新だけでは終わりません（出典1・3）。

1.43.3.10861 より古く、インターネットから到達できるサーバは、侵害された可能性があるものとして扱ってください（出典1。原文英語を本記録が訳した）

Plex は、痕跡が見つかった場合、あるいは侵害を否定できない場合は、古い Plex のデータディレクトリを使い回さずにクリーンインストールから作り直すよう求めています（出典1）—— 最低でも Codecs フォルダの中身を削除し、Preferences.xml に自分が設定していないトランスコーダの項目が無いか確認すること、Plex アカウントの全デバイスからサインアウトしてパスワードを変更すること、Plex のサービスアカウントが到達できたもの（マウントした共有・保存した資格情報）はすべて露出した可能性があるものとして扱うことを挙げています（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

以下は Plex の勧告と第三者の分析が示した連鎖を段階ごとに並べたものである （出典1・3）。 **本件は実環境での悪用が確認されており、段階は成立条件ではなく 実際に使われている経路である**（出典1・2・4）。 未認証の要求が `/player/timeline` に届き、サーバが攻撃者の代わりに要求を出す。 細工した値でループバック経由の内部エージェントへ向けさせると、 Plex は所有者の管理トークンを添付する。 そのトークンでトランスコーダの設定を変え、Codecs ディレクトリへ 共有オブジェクトを書き、Plex がそれを署名検査なしで読み込む。

  1. 1. 初期侵入disclosed[1] [3] [4]
    未認証の要求が `/player/timeline` 端点に届き、 Plex Media Server が攻撃者の代わりに外向きの要求を出す（SSRF）。 認証の検査は「X-Plex-Token が存在するか」だけで、 値が有効かは見ていなかった
    根拠: Plex の勧告の記述「CVE-2026-96652: プレイヤーのタイムライン端点における 未認証のサーバサイドリクエストフォージェリ」（原文英語を本記録が訳した）。 出典3・4 は、検査がトークンの有効性ではなく存在だけを見ていたと整理している
  2. 2. 認証情報アクセスdisclosed[1] [3]
    細工した `searchOne` の値で、ループバック経由の内部エージェント機能へ 要求を向けさせる。Plex はその要求に所有者の管理トークンを添付するため、 トークンが攻撃者に渡る
    根拠: Plex の勧告の記述「CVE-2026-96654: ループバックインタフェース経由での 内部エージェント機能へのアクセス」「CVE-2026-96655: サーバ所有者の 管理トークンの漏えい」（原文英語を本記録が訳した）。 出典3 の整理「細工した `searchOne` の値が、ループバック経由で内部エージェントへの 要求を強制し、Plex はそれに所有者の管理トークンを添付する」
  3. 3. 実行disclosed[1] [3]
    得た管理トークンで x264 トランスコーダの設定を変更し、 細工した動画のトランスコード時に Codecs ディレクトリへ 共有オブジェクトが書かれるようにする。 Plex はその共有オブジェクトを署名検査なしで読み込み、 サーバを動かしているアカウントの権限でコードが実行される
    根拠: Plex の勧告の記述「CVE-2026-96656: トランスコーダの設定を通じた Codecs ディレクトリへの任意ファイル書き込み」 「これらを連鎖させると、未認証のリモート攻撃者が Plex Media Server プロセスの権限でコードを実行できる」 （原文英語を本記録が訳した）。 出典3 は「Plex は署名検査なしでその共有オブジェクトを読み込む」と整理している
  4. 4. 影響（暗号化・破壊・改ざん）disclosed[1] [3] [4]
    侵害された機器で暗号資産のマイナー（XMRig）とプロキシソフトが実行される。 観測された例では `myawesomeproxy`・`mylovelyminer`・`x12345` という名前の プロセスが動き、`proxystream.st` への外向き接続が発生した
    根拠: Plex の勧告の記述「侵害されたサーバは暗号資産のマイナーと プロキシソフトを動かすために使われている」および痕跡の列挙（出典1。原文英語）。 出典4 はペイロードの配布元（217.60.194.116）と XMRig の使用を記録している

Censys が整理した連鎖の段取りは次のとおりである（出典3）。

  1. 未認証の要求が /player/timeline に届き、サーバが攻撃者の代わりに要求を出す
  2. 細工した searchOne の値で、ループバック経由の内部エージェントへ要求を向けさせる。Plex はその要求に所有者の管理トークンを添付する
  3. 管理トークンを得た攻撃者が、x264 トランスコーダの設定を変え、細工した動画のトランスコード時に Codecs ディレクトリへ共有オブジェクトが書かれるようにする

Plex 自身の表現は「これらを連鎖させると、未認証のリモート攻撃者が Plex Media Server プロセスの権限でコードを実行できる」である（出典1）。

ここから先は本記録の評価である。

第一に、1段目の認証の甘さが連鎖全体の入口になっている。 複数の情報源は、/player/timeline の検査が「トークンが有効か」ではなく「トークンが存在するか」だけを見ていたと整理している（出典3・4）—— 任意の X-Plex-Token の値で通る。

第二に、2段目で「内側から来た要求」として扱われることが効いている。 ループバック経由の要求に管理トークンが添付されるのは、「自分自身からの要求は信頼できる」という前提である（本記録の整理）—— SSRF がその前提を壊す。

第三に、4段目の「署名検査なしの読み込み」がファイル書き込みをコード実行に変えている（出典3）。書き込み（CVE-2026-96656）だけなら管理者権限を要する操作であり、単体の深刻度は高くない—— Censys は「管理者アクセスを要するが、連鎖の前段がそれを提供する」と整理している（出典3）。

つまり本件は、1件ずつ評点を付けて優先順位を決める運用では見落とされる形をしている（本記録の指摘）—— 実際に公開されている個別の CVSS は 4.3〜8.6 に散っており、情報源によっても食い違っている〈齟齬1〉。

侵害の痕跡として Plex が挙げているのは4つである（出典1）。

ここから先は本記録の評価である。

この指標の並びは、痕跡として強いものと弱いものが混ざっている。

  • 強いのはファイルと通信である。 Codecs フォルダに共有オブジェクトが置かれるのは連鎖の構造上必要な段であり、通信先はペイロードの配布と関係する
  • 弱いのはプロセス名である。 myawesomeproxy のような名前は観測された攻撃で使われたものにすぎず、変えられれば当たらない
  • 負荷は副作用である。 マイナーが動いていれば現れるが、プロキシだけなら現れない

  • 単体の評点で優先順位を決める運用では、連鎖する脆弱性は後回しになる
    **4件の個別 CVSS は情報源によって 4.3〜8.6 に散っており、 3件は 7.0 未満の値で流通している**（出典3・4）〈齟齬1〉。 **Plex の勧告には評点の記載が無い**（出典1）。 **一方で、連鎖させた結果は「未認証のリモートコード実行」である**（出典1）—— **この情報は、ベンダーの勧告の文章を読まないと得られない**
    取るべき行動 **優先順位の判断材料に「KEV への収載」と「ベンダー勧告の文面」を 評点より上に置く。** ①KEV（悪用確認済み脆弱性リスト）を毎営業日確認する担当を決める、 ②同一製品の複数 CVE が同時に出たときは、 個別の評点ではなく「連鎖の帰結」をベンダー勧告から読む、 ③評点が 7.0 未満でも KEV に載っていれば最優先に上げる運用にする
  • 「更新した」は「安全になった」ではない——更新で消えないものを先に決めておく
    **Plex は「1.43.3.10861 より古く、インターネットから到達できるサーバは 侵害された可能性があるものとして扱え」と求めている**（出典1）。 **Censys は「更新しても Codecs に置かれた実体は取り除かれず、 漏えいした管理トークンも無効化されない」と明記している**（出典3）。 **侵害は修正の77日前から始まりうる状態にあり、 実証コードの公開の翌日から実際に悪用された**（出典4）
    取るべき行動 **脆弱性対応の手順に「更新後に残るもの」の確認段を加える。** ①書き込まれた実体（プラグイン・共有ライブラリ・設定ファイル）、 ②漏えいした可能性のある資格情報・トークン、 ③そのサービスアカウントが到達できた範囲、の3つを 製品ごとにあらかじめ書いておく。 **「更新完了」で台帳を閉じられる製品と、 侵害調査を必ず伴う製品を区別する**
  • 自動更新が効かない設置形態（NAS・Docker・Linux）が、適用の空白を作る
    **自動更新が効くのは Windows と macOS（有効にしている場合）だけで、 Linux・NAS・Docker の導入環境は手で更新する必要がある**（出典3）。 **修正は2026年8月に出ていたが、 CISA の KEV 収載（10月20日）まで77日かかった**（本記録の算出）—— **その間に実証コードが公開され、翌日から悪用が始まった**（出典4）
    取るべき行動 **資産台帳に「更新が自動で届くか」の列を足す。** 届かない機器（NAS・コンテナ・組込み・貸与機器）を抽出し、 ①更新の確認を定期作業として割り当てる、 ②その機器がインターネットから到達できるかを併記する、 ③到達できるものから先に手当てする。 **「設置したら触らない」運用の機器が、適用の空白になる**
  • 従業員が自宅・事務所に置いた1台が、組織の加害の経路になりうる
    **侵害された機器では暗号資産のマイナーとプロキシソフトが 動かされている**（出典1・3・4）。 **プロキシ化された機器は、第三者の通信を中継する踏み台になる** （本記録の評価）—— **ある情報源は「あなたのインターネット通信を外部で利用する」と 称するバナーを持つツールが使われていたと記述している**（出典3）。 **Plex は「サービスアカウントが到達できたもの （マウントした共有・保存した資格情報）はすべて露出した可能性がある ものとして扱え」と求めている**（出典1）
    取るべき行動 **在宅勤務・持ち出し端末の規程に、 「自宅ネットワークに公開サービスを置かない」という項目を入れる。** あわせて、①業務ファイルを個人の NAS に置かせない、 ②在宅環境から社内へ入る経路を端末単位で限定する、 ③家庭用機器の侵害が業務に波及する経路を一覧にして 従業員向けの説明に使う。 **本件は「個人の趣味のソフト」が入口になる形である**
セキュリティ技術者への示唆
  • SSRF があると「内側から来た要求」という性質が保証にならない
    **連鎖の2段目は、ループバック経由の要求に Plex が所有者の管理トークンを添付することで成立している**（出典1・3）。 **「自分自身からの要求は信頼できる」という前提が、 1段目の SSRF で壊される**（本記録の整理）。 **CVE-2026-96654 は「ループバックインタフェース経由での 内部エージェント機能へのアクセス」である**（出典1）
    取るべき行動 **自組織の実装で「要求元がループバック／内部ネットワークだから信頼する」 判定をしている箇所を洗い出す。** ①その判定を、要求元のアドレスではなく 呼び出し主体の認証に置き換える、 ②内部向けの要求に特権トークンを自動で添付する処理を探し、 添付の範囲を必要最小にする、 ③同じプロセス内で外部入力を受ける経路（SSRF になりうる箇所）と 内部信頼の境界が重なっていないか図にする
  • ファイル書き込みをコード実行に変えるのは「署名検査のない読み込み」である
    **連鎖の4段目は、Plex が Codecs ディレクトリの共有オブジェクトを 署名検査なしで読み込むことで成立する**（出典3）。 **書き込み（CVE-2026-96656）だけなら管理者権限を要する操作であり、 単体の深刻度は高くない**—— **連鎖の前段がその管理者権限を提供している**（出典3）
    取るべき行動 **動的に読み込む部品（共有ライブラリ・プラグイン・コーデック・ スクリプト）の読み込み経路を列挙し、 それぞれに署名検査があるかを確認する。** 無い場合は、①読み込み元のディレクトリを書き込み不可にする、 ②書き込みと読み込みの主体を分離する、 ③最低限、ディレクトリの変更を監視して差分を検知する
  • 侵害判定の指標は、強いものと弱いものを区別して使う
    **Plex が挙げた痕跡は4つある**（出典1）—— **プロセス名（`myawesomeproxy`・`mylovelyminer`・`x12345`）、 Codecs フォルダの `.so`／`.dll`、 `proxystream.st` への外向き接続、継続的な高 CPU 使用率。** **プロセス名は観測された攻撃で使われたものにすぎず、 変えられれば当たらない**（本記録の評価）—— **一方、Codecs へのファイル配置は連鎖の構造上必要な段である**
    取るべき行動 **侵害判定の手順を「構造上必要な痕跡」から書く。** ①Codecs ディレクトリの中身と更新日時、 ②`Preferences.xml` のトランスコーダ関連の設定の差分、 ③サーバプロセスの子プロセスの一覧——の順で確認し、 プロセス名の一致は補助的な手がかりとして扱う。 **「公表された名前のプロセスが無かった」で調査を終わらせない**
  • 到達性の制限は、修正が間に合わないときに残る唯一の統制である
    **Plex は対処として「リモートアクセスが不要なら無効にする」 「必要がない限りポート 32400 を直接転送しない」を挙げている**（出典1）。 **Censys はインターネットに面した Plex Media Server を 約32万4,000台観測し、そのうち約30%が脆弱な版だとしている**（出典3）—— **攻撃者はこの一覧を同じ方法で作れる**（本記録の評価）
    取るべき行動 **自組織・自拠点から外向きに公開しているポートを実測する。** ①外部の走査サービスから見た自分の IP の開放ポートを確認する、 ②必要のない転送設定を外す、 ③必要なものは VPN 越しに変える、 ④残すものは「修正が出たらすぐ当てる対象」として 名前を付けて台帳に載せる

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Plex Media Server を 1.43.3.10861 より前の版で動かしており、 インターネットから到達できる（ポート 32400 の転送、 またはリモートアクセスが有効）本件の影響範囲そのもの。 **Plex は「1.43.3.10861 より古く、インターネットから到達できるサーバは 侵害された可能性があるものとして扱え」と求めている**（出典1）—— **更新だけでは侵害は解消しない**
運用・監視□ 自動更新が効かない設置形態（Linux・NAS・Docker）で ソフトウェアを運用しており、更新の確認が定期作業になっていない**修正は2026年8月に出ていたが、実証コードの公開（10月16日）の翌日から 悪用が始まった**（出典3・4）。 **「設置したら触らない」機器が適用の空白になる**
認証・認可□ ループバックまたは内部ネットワークから来た要求を、 要求元のアドレスだけで信頼し、特権トークンを自動で添付している連鎖の2段目はこの前提の上に成立している（出典1・3）。 **SSRF があると「内側から来た」という性質は保証にならない**
システム構成□ 動的に読み込む部品（共有ライブラリ・プラグイン・コーデック）の 読み込み元ディレクトリが、アプリケーションから書き込み可能である**ファイル書き込みをコード実行に変えているのは 「署名検査のない読み込み」である**（出典3）。 **書き込みと読み込みの主体が分離されていれば、 連鎖は最後の段で止まる**
