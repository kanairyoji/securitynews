Oracle の Critical Patch Update は四半期ごとの定例であり、今回はのべ1,295件・1,209件の CVE・33の製品群に及んだ（出典3・4）。

出典4 が示している適用の順序は、この欠点への実務的な答えである（出典4）。

本記録はこの考え方を支持する（本記録の評価）。理由は、今回の内訳そのものが示している—— CVSS 10.0 の6件のうち4件は HTTP 経由で、対象は他システムと繋ぐための機能（認証エンジン・アダプタ・Orchestrator・Workflow）である（出典4）。これらは、攻撃者が最初に探す場所でもある。

ただし、優先順位を付けることは「後回しにしたものを未適用のまま運用する」という決定でもある（本記録の指摘）。その決定を記録に残さないと、次の四半期には1,000件規模の未適用が積み上がり、どれが「判断して後回しにしたもの」でどれが「忘れたもの」かが区別できなくなる。

CISO・経営層への示唆
  • 四半期に1,000件規模が来る前提で、「後回しにした決定」を記録に残す
    **今回はのべ1,295件・1,209件の CVE・33の製品群である**（出典3・4）。 **これを3か月ごとに全件適用できる体制を持つ組織は限られる** （本記録の評価）—— **優先順位を付けることは、同時に 「後回しにしたものを未適用のまま運用する」決定でもある。** **記録に残さないと、次の四半期には 「判断して後回しにしたもの」と「忘れたもの」が区別できなくなる**
    取るべき行動 **四半期ごとの適用計画に「当てないものの一覧」を必ず作る。** ①対象（製品・CVE・件数）、②当てない理由 （業務停止枠が取れない／互換性の懸念／到達性が低い）、 ③代替の緩和策（到達性の制限・監視の追加）、 ④次に見直す時期、の4項目を書き、承認者を記録する。 **「全部当てた」か「当てられなかった」の二択にしない**

    **CVSS 10.0 の6件のうち4件は HTTP 経由で、 対象は他システムと繋ぐための機能 （認証エンジン・アダプタ・Orchestrator・Workflow）である**（出典4）。 **一方 Java SE は「クリティカル」が0件だが、 55件のうち49件が認証なしのリモートから悪用できる**（出典4）—— **深刻度の分布と到達性の分布は一致しない**
    取るべき行動 **資産台帳に「インターネットから到達できるか」の列を作り、 パッチ適用の順序をその列で決める。** ①外から到達できる Oracle 製品を先に当てる、 ②当てられない場合は到達性を切る （T3・IIOP の遮断、管理コンソールの非公開化）、 ③内部システムは次の保守枠に回す。 **深刻度（CVSS）は、同じ到達性の中での順序付けに使う**
