Kaspersky GReAT は2026年10月22日、中央アジア（タジキスタン・ウズベキスタン・ トルクメニスタン）の外交機関を標的とした UEFI ブートキット「BlackX」の分析を公表した—— **2023年に ESET が実在を確認した犯罪者向けブートキット BlackLotus の実装を APT 側が作り直したもので、Kaspersky は中程度の確度で APT41 に帰属させている。** **侵入の成立した理由は「パッチを当てていなかった」ではない**—— **標的の端末は完全にパッチ済みであり、Secure Boot 回避の脆弱性 Baton Drop（CVE-2022-21894）の修正が、 更新の適用では有効にならず管理者の手動操作を要する設計だったためである。** Microsoft が予定していた自動的な強制フェーズは公表時点で未実施で、 対象証明書「Windows Production PCA 2011」は2026年10月19日に有効期限を迎えたが、 失効登録されない限り脆弱なバイナリは読み込まれ続ける

当てていなかったのではありません。当てても有効にならなかったのです。

Kaspersky GReAT は2026年10月22日、中央アジアの外交機関を標的としたUEFI ブートキット「BlackX」の分析を公表しました（出典1）。標的は タジキスタン・ウズベキスタン・トルクメニスタンの外交機関で、発見は2026年初頭です。

BlackX は、2023年に ESET が実在を確認した犯罪者向けブートキットBlackLotus によく似ています（出典1）。Secure Boot を回避する脆弱性 Baton Drop（CVE-2022-21894） を突く実装がBlackLotus と著しく似ている一方で、差異もあります。BlackLotus のソースコードは公開されたことがないため、攻撃者は逆解析したか、犯罪者から購入したと考えられます（出典1）—— APT が犯罪者の成果物を取り込む例は稀です。

Kaspersky は本件を中程度の確度で APT41 に帰属させています（出典1）。根拠は、ESET が2026年6月に報じた FishMonger の攻撃に現れたPDB パス C:\Users\xdd\Desktop の識別子「xdd」がBlackX のペイロード内に繰り返し現れること、正規実行ファイルによる DLL サイドローディングと暗号化ファイルの組み合わせ、中国語話者のアクターに多い難読化器 OLLVM の使用です。

しかし本件の中心は、ブートキットそのものではありません（本記録の評価）。Kaspersky は当初「標的が更新を当てていなかった」と考えましたが、調査の結果それは誤りでした——標的の端末は完全にパッチ済みでした（出典1）。Baton Drop の修正は、脆弱な UEFI コンポーネントの署名証明書「Windows Production PCA 2011」を失効させる設計ですが、この失効は更新の適用では自動的に起きません。 利用者が手動で発動させる必要があり、その手順は Microsoft のサイトの奥深くに置かれています（出典1）。

Microsoft が予定していた「強制フェーズ」（自動的に証明書を失効させる段階）は、公表時点で未実施です（出典1）。当該証明書は2026年10月19日に有効期限を迎えましたが、失効登録されない限り脆弱なバイナリは読み込まれ続けます。

犯罪者のブートキットを、国家側が作り直して使った概観

Kaspersky GReAT の報告（出典1）が示している経緯は次のとおりである。

  • 2022年10月 — Kaspersky は犯罪者フォーラムで、Secure Boot を回避できるUEFI ブートキット BlackLotus が 5,000ドルで売られている広告を観測した。強力な能力に対して価格が安すぎるため、当時のコミュニティは広告を疑っていた（検体が見つからず検証できなかった）。

  • 2023年3月 — ESET が広告が本物であったことを確認した。検体を特定し、Baton Drop（CVE-2022-21894） を通じて Secure Boot を回避できることを確認した。なお悪用可能であったため、Microsoft は複数の更新を公開した。

  • それ以降 — BlackLotus を用いた公知の攻撃は確認されなくなった。

  • 2026年初頭 — Kaspersky が、タジキスタン・ウズベキスタン・トルクメニスタンの外交機関を標的とした攻撃を特定した。用いられていた UEFI ブートキットは BlackLotus に類似しており、Kaspersky はこれを BlackX と命名した。

BlackLotus のソースコードは公開されたことがない（出典1）。 Baton Drop の悪用の連鎖は BlackLotus と著しく似ている一方で差異もあることから、 Kaspersky は 「攻撃者は BlackLotus を逆解析したか、 犯罪者からソースコードを購入したかのいずれかである」 と評価している。 そして「APT アクターが犯罪者のアイデアやコードを借用する例を 我々が見ることは稀である」と付記している（原文英語を本記録が訳した）。

ここから先は本記録の評価である。 この「稀」という観察は、防御側の前提に関わる。 犯罪者向けの道具と国家支援型の道具を別の棚に置き、 前者を「量で来るもの」、後者を「狙われたときに来るもの」として 扱う整理は広く使われている。 本件はその境界を越えた例である—— 犯罪市場で5,000ドルで売られた能力が、 3年後に外交機関を標的とする作戦の永続化手段として現れた。 価格が安かったのは能力が低かったからではなく、 市場がその能力を正しく値付けできていなかったからだと読める（本記録の評価）。

当てても有効にならない修正——侵入が成立した本当の理由原因・手口

ここが本件の中心である（本記録の評価）。

Kaspersky は報告の中で、自らの当初の見立てが誤っていたことを明示している（出典1）。

  • 当初の見立ては 「標的組織の怠慢（negligence）で設置が成立した」。Baton Drop は2023年に公表され修正もされていたため、感染した端末には該当する更新が入っていないのだろうと考えた。

  • 調査はこれを否定した —— 「標的となった端末は完全にパッチされていた（the targeted machines were fully patched）」（原文英語を本記録が訳した）。

  • 問題は修正そのものにあった。 Baton Drop の修正は、脆弱な UEFIコンポーネントの署名に使われた証明書 「Windows Production PCA 2011」を失効させる設計である。しかしこの失効は、更新のインストールによって自動的には起こらない——利用者が手動で発動させる必要がある。

  • 手動の手順は2段である。①HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Secureboot 配下にレジストリフラグを設定する、②Secure-Boot-Update という名称のスケジュールタスクを作成する。

  • Microsoft がこの設計を選んだ理由も示されている ——自動適用すると、「Windows Production PCA 2011」証明書に依存して起動しているデュアルブート構成が壊れうるためである。

Kaspersky はこの配布方式が生む問題を次のように述べている（原文英語を本記録が訳した）。 「更新のインストール後にシステム管理者が追加の手順を踏むことは、 きわめて異例である。通常、管理者はインストールの失敗が起きない限り、 パッチ適用に際して追加の操作を行わない。」 さらに、この有効化の手順は「Microsoft のウェブサイトの奥深くに埋もれており、 平均的な IT 管理者が気づくのはかなり難しい」と評価している。

Kaspersky は、攻撃者がこの状況を計算に入れたと評価している（出典1）—— 「Baton Drop のパッチを手動で有効化することの重要性を理解した組織が 少ないことを脅威アクターが考慮し、BlackLotus の仕組みを理解して その模倣品を作ることに時間を投じると決めたのだろう」（原文英語を本記録が訳した）。

ここから先は本記録の評価である。 これは「パッチ管理の失敗」ではなく「パッチ管理の指標の失敗」である。 多くの組織が持っている指標は「更新の適用率」であり、 それは今回 100% だったはずである。 測れていなかったのは「適用した修正が有効になっているか」である—— この2つを区別する指標を持っていた組織だけが、 自分が脆弱なままだと知ることができた。

強制フェーズは未実施で、証明書は期限切れでも読み込まれ続ける未確定事項

Kaspersky は本件の構造が現在も解消していないことを2点で示している（出典1）。

  • Microsoft の Baton Drop パッチ展開計画には、利用者の操作なしに「Windows Production PCA 2011」を自動的に失効させる「強制フェーズ（Enforcement Phase）」が記載されている。公表時点でこの段階は実施されていない。

  • 2026年10月19日、当該証明書は有効期限を迎えた。しかしこれは脆弱なバイナリの読み込みを阻止しない——証明書が失効登録（blocklist）されない限り読み込まれ続ける。

ここから先は本記録の評価である。 「期限切れ」と「失効」を同じものとして読むと、 ここで判断を誤る。 Secure Boot の検証は、署名の有効期限ではなく 署名者が失効リストに載っているかで判断する部分がある—— 期限切れの証明書で署名された古いブートローダは、 失効登録されていなければ今も起動できる。 「2026年10月19日に期限が切れたから終わった話」ではない。

本記録として明示しておく（本記録の判断）—— 強制フェーズがいつ実施されるかは公表されていない〈未確定3〉。 したがって、各組織が手動の有効化を行ったかどうかが、 いまのところ唯一の分かれ目である。

ブートキットから降りてくるもの——署名済みドライバ、セキュリティ製品の無効化、クラウドC2原因・手口

Kaspersky が記述している BlackX の構成は次のとおりである（出典1）。

①設置。 攻撃者はネットワークを侵害し管理者権限を取得したあとに BlackX を設置する。投下されるファイルは2つである—— inst.exe（インストーラ）と PVMDIJGKAX2（拡張子の無い RC4 暗号化ファイル。 設置に必要なファイルと文字列を含む）。 起動の指令行は C:\ProgramData\Intel\inst.exe PVMDIJGKAX2 Q46F6MDLI3RX2KV1 で、 最後の引数が復号用の RC4 鍵である。 inst.exe 自体には悪性の文字列も埋め込みデータも含まれない—— 必要なものはすべて PVMDIJGKAX2 の中にあり、 これがインシデント対応側がブートキットの部品を回収することを難しくしている（出典1）。

②Secure Boot の回避。 インストーラはシステムパーティションと UEFI パーティションの両方にファイルを投下し、Baton Drop を悪用する。 目的は BlackLotus と同じく、独自の Machine Owner Key（MOK）を 登録して任意の EFI ファイルを読み込めるようにすることである。

③カーネルドライバの注入。 UEFI ペイロードの役目は、悪性ドライバを Windows カーネルに注入することである。 このドライバは BlackLotus が投下するものとは異なり、 温江区明宇网络技术服务工作室（Wenjiang District Mingyu Network Technology Service Studio）名義の証明書で署名されている （シリアル番号 0bcdf5e0da32d68900b8b7638459d072。公表時点で失効済み）。 ドライバの機能は3つである—— (a) セキュリティ製品に関わるプロセス・スレッド・レジストリのコールバックを 無効化する、(b) ETW プロバイダに干渉してセキュリティ製品が出力を取れなくする、 (c) ブートキットのファイルを保護する（これらのファイルを開く カーネル要求を横取りし、悪性ファイルのハンドルではなく calc.exe のハンドルを返す）。 なお改竄処理の一部は Kaspersky または Avast の製品が入っている場合にのみ 動くよう作られているが、動的解析の結果、 Kaspersky 製品に対しては何の干渉もできていない（出典1）。

④ユーザーモードの第2段。 2種が観測されている。

  • クラウドストレージを C2 に使う RAT。 後続の .NET ペイロードを読み込める。観測された版は Google Drive・OneDrive・Yandex.Disk を用いる。接続後、ストレージ上のファイルを列挙し、接尾辞（0X01〜0X06・SSSR）で処理を切り替える（0X01 は .NET ファイルを解析して TEST.Class1.RunCMD を実行、0X03/0X05 はファイルのアップロード・ダウンロード、SSSR は初期のシステム情報の送出）。

  • OxiDLLRunner。 OLLVM で難読化された悪性 DLL で、正規ファイル googleupdate.exe（本来の名称 jcef_helper.exe、MD5 AF8A983B9ADA07EAE1259BF2953ABD40）によって読み込まれる（この正規ファイルもブートキットが投下する）。DLL は同じフォルダにある v8_context_snapshot.bin を復号し、先頭へジャンプする。復号結果はシェルコードに続いて PE ファイル（Rust 製のペイロード）で、www[.]archivetj[.]com の C2 と通信する。通信では create_plugin をエクスポートする DLL を受け取り、別スレッドで実行する。

本記録として注記する（本記録の明示）—— ここに挙げた指標（IoC）は Kaspersky の報告の記述であり、 本記録の作成者が悪性を検証したものではない。 照合先のテレメトリを持たないため、検知に用いる場合は 自組織で評価してから使うこと。

帰属は中程度の確度——根拠は識別子・サイドローディングの型・難読化器帰属

Kaspersky は本件を「中程度の確度（medium confidence）」で APT41 に帰属させている（出典1）。 確度の表現は原文のままであり、本記録はこれを強めない。

根拠として示されているのは3点である（出典1）。

  • ①識別子「xdd」の一致。 2026年6月に ESET が公表した FishMonger（コミュニティで APT41 と関連するとみられている）の攻撃に関するブログは、PDB パスが C:\Users\xdd\Desktop で始まるカーネルインプラントを記述し、CVE-2023-24932 を悪用しうる不特定の UEFI ブートキットコンポーネントの使用可能性にも言及していた。 Kaspersky は BlackX のペイロード内に「xdd」が繰り返し現れることを確認し、「BlackX が ESET のブログで言及された UEFI ブートキットである」と評価している。

  • ②手口の型。 BlackX が投下するペイロードは、正規実行ファイルを悪用した DLL サイドローディングと暗号化ファイルの組み合わせで読み込まれる。この型は中国語話者のアクターに共通する。

  • ③難読化器。 OxiDLLRunner は OLLVM で難読化されている。これも中国語話者のアクターが多く用いる難読化器である。

ここから先は本記録の評価である。 この3点の性質は同じではない。 ①は本件と既知の報告を結ぶ具体的な痕跡（開発者の作業環境に由来する識別子）で、 帰属の重みを担っている。 ②と③は「中国語話者のアクターに多い」という傾向の記述であり、 それ自体で特定のアクターを指すものではない（本記録の整理）—— DLL サイドローディングも OLLVM も広く共有される手法である。 Kaspersky が「中程度」に留めたのは、 この重みの差を踏まえた判断と読める（本記録の読み）。

読者が本記録から持ち帰るべきは、アクター名ではない（本記録の評価）—— 「完全にパッチされた端末で Secure Boot が回避された」という事実は、 帰属が誰であっても変わらない。
