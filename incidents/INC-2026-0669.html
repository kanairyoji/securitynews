INC-2026-0669LIFF SDK に DOM 型 XSS

LINEヤフーの LIFF SDK に DOM ベースのクロスサイトスクリプティング—— 細工した URL を外部ブラウザで開かせると LIFF アプリのオリジンで任意の JavaScript が動く（CVE-2026-112148／JVNVU#91023667）

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月22日（JVN 公開日） 最終更新: 2026年10月23日（本記録の確認時点）

LINE 上で動くウェブアプリの土台である LIFF SDK に、DOM ベースのクロスサイトスクリプティングが見つかりました。修正版はすでに出ていますが、直すのは SDK を組み込んだ各アプリの側です。

2026年10月22日、JPCERT/CC は JVNVU#91023667 を公開し、LINEヤフー株式会社が提供する LIFF SDK に DOM ベースのクロスサイトスクリプティング（CWE-79）の脆弱性があることを明らかにしました（出典1）。対象は LIFF SDK 2.20.0 から 2.31.0 まで、修正版は 2.31.1 です（出典1・2・3）。CVE 番号は CVE-2026-112148、CVSS v4.0 基本値は 5.1、CVSS v3.1 基本値は 6.1 です（出典1）。

本記録が要点と見たのは、次の3点です。

  • 成立の条件は「外部ブラウザで細工された URL を開くこと」である。 LY Corporation のアドバイザリは「攻撃者が細工した URL を利用者が外部ブラウザで開くと、影響を受ける LIFF アプリのエンドポイントのオリジンで任意の JavaScript を実行されるおそれがある」と説明しています（出典2・3。原文英語）。CVSS の UI:A（利用者の操作が要る）はこの前提を指しています（出典1）。
  • 被害が出る場所は SDK ではなく、SDK を組み込んだ各アプリのオリジンである。 GitHub Security Advisory は、アプリの状態や実装によって認証トークンなど JavaScript から参照可能な機密データの読み取り、localStorage や Cookie の読み取り（HttpOnly 属性の Cookie は直接読み取れない）、利用者のセッションを使った不正操作、表示内容の改変やフィッシングページへのリダイレクトがありうるとしています（出典3。原文英語）。SC:L/SI:L（影響範囲が変わる先への低影響）も同じ構図を示しています（出典1）。
  • 「SDK を更新すれば終わり」にはならない。配布の経路によって作業が違う。 出典2・3 は、CDN の edge URL を使うアプリは自動配信されるが実際に修正版が読み込まれているか確認すること、固定バージョンの CDN URL を使うアプリは URL を変えること、npm（@line/liff）を使うアプリは依存関係と lockfile を更新して再ビルド・再デプロイすること、SDK を自前で配信している場合は差し替えること、アプリ側のキャッシュに古い SDK やバンドルが残っている場合は併せて更新することを挙げています（出典2・3。原文英語）。

本記録は2026年10月23日に JVN（出典1）・LY Corporation のアドバイザリ（出典2）・GitHub Security Advisory（出典3）を直接取得して裏を取りました。 技術的な詳細は「アプリ開発者が更新できるようにするため」非公開とされており、どの API のどの引数が起点なのかは公表されていません〈未確定1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

公表されているのは「どう作られていたか」と「何が起こりうるか」までで、 実際の攻撃の観測は示されていない（出典1・2・3）。 以下は出典2・3 が述べる想定される影響を段階に割り当てたものである（整理は本記録）。

  1. 1. 初期侵入確認済
    攻撃者が細工した URL を用意し、利用者にそれを外部ブラウザで開かせる （出典2・3 の記述に基づく。誘導の手段そのものは公表されていない）。
    根拠: 「攻撃者が細工した URL を利用者が外部ブラウザで開くと」（出典2・3。原文英語）。 CVSS で `UI:A`／`UI:R` とされており、利用者の操作が前提である（出典1）。
  2. 2. 実行確認済
    DOM ベースのクロスサイトスクリプティング（CWE-79）により、 影響を受ける LIFF アプリのエンドポイントのオリジンで 任意の JavaScript が実行される（出典1・2・3）。
    根拠: 「影響を受ける LIFF アプリのエンドポイントのオリジンで 任意の JavaScript を実行されるおそれがある」（出典2・3。原文英語）。 CVSS v3.1 の `S:C`、v4.0 の `SC:L/SI:L` がスコープの変化を示す（出典1）。
  3. 3. 認証情報アクセス確認済
    注入されたスクリプトが、オリジンの JavaScript から参照できる認証トークンや localStorage・Cookie を読み取る（出典3。原文英語）。 HttpOnly 属性の Cookie は直接読み取れないとされる（出典3）。
    根拠: 「認証トークンなど、オリジンの JavaScript から参照可能な機密データの読み取り」 「localStorage や Cookie の読み取り（HttpOnly 属性の Cookie は直接読み取れない）」 （出典3。原文英語）。
  4. 4. 影響（暗号化・破壊・改ざん）確認済
    利用者のセッションを使った、アプリの認可制御に従う範囲での不正操作、 および表示内容の改変・フィッシングページへのリダイレクトが起こりうる （出典3。原文英語）。実際の被害事例は公表されていない〈未確定4〉。
    根拠: 「利用者のセッションを使った、アプリの認可制御に従う範囲での不正操作」 「表示内容の改変やフィッシングページへのリダイレクト」（出典3。原文英語）。

壊れていたのは SDK だが、スクリプトが動くのは SDK を組み込んだアプリのオリジンである原因・手口出典 [1] [2] [3]

JVN は本脆弱性を次のように示しています（出典1）。

LINEヤフー株式会社が提供する LIFF SDK には、DOMベースのクロスサイトスクリプティング（CWE-79）の脆弱性が存在します（出典1）

当該製品を使用しているサイトにアクセスしたユーザのウェブブラウザ上で、任意のスクリプトを実行される可能性があります（出典1）

LY Corporation 自身のアドバイザリは、成立の条件をもう一段具体的に書いています。 「攻撃者が細工した URL を利用者が外部ブラウザで開くと、影響を受ける LIFF アプリのエンドポイントのオリジンで任意の JavaScript を実行されるおそれがある」とされています（出典2・3。原文英語。訳は本記録）。

ここで押さえるべきは「どこで動くか」です（本記録の評価）。任意のスクリプトが動くのは LIFF SDK の中ではなく、その SDK を読み込んでいる各アプリのエンドポイントのオリジンです（出典2・3）。つまり、同じ SDK の同じ欠陥から受ける被害の大きさは、アプリごとに違います（本記録の評価）。

GitHub Security Advisory は、アプリの状態や実装によって次のことが起こりうるとしています（出典3。原文英語。訳は本記録）。

  • 認証トークンなど、オリジンの JavaScript から参照可能な機密データの読み取り
  • localStorage や Cookie の読み取り（HttpOnly 属性の Cookie は直接読み取れない）
  • 利用者のセッションを使った、アプリの認可制御に従う範囲での不正操作
  • 表示内容の改変やフィッシングページへのリダイレクト

同アドバイザリは「トークンが漏えいするかどうかは、トークンが存在し、注入されたスクリプトから参照できるかに依存する」とも明記しています（出典3。原文英語）。自分のアプリがアクセストークンを JavaScript から読める場所に置いているかどうかが、そのまま影響の大きさになります（本記録の評価）。

CVSS のベクタが示しているのは「利用者を踏ませる経路」と「別オリジンへの波及」である評価・解釈出典 [1] [2] [3]

評点は CVSS v4.0 で 5.1、v3.1 で 6.1 です（出典1）。数字そのものより、ベクタの各要素が条件を語っています（本記録の評価）。

v4.0 のベクタはAV:N/AC:L/AT:N/PR:N/UI:A/VC:N/VI:N/VA:N/SC:L/SI:L/SA:N です（出典1・2・3）。

  • AV:N・PR:N——ネットワーク越しで、権限は要りません（出典1）。
  • UI:A——利用者側の能動的な操作が要ります。「細工された URL を外部ブラウザで開く」がこれに当たります（出典2・3 に照らす。対応づけは本記録）。
  • VC:N/VI:N/VA:N に対して SC:L/SI:L——脆弱な部品（SDK）そのものへの影響は無しとされ、影響は後続のシステム、つまり SDK を読み込んだアプリのオリジン側に出ます（出典1。読み方は本記録）。v3.1 の S:C（スコープ変更）も同じことを別の記法で言っています（出典1）。

この構図は、脆弱性の管理台帳を「自社が使っている製品」の単位で持っている組織に読みにくさを与えます（本記録の評価）。影響を受けるのは @line/liff という依存パッケージですが、被害が出るのは自社サービスのオリジンだからです（出典2・3 に照らす）。

直すべき対象は4通りに分かれ、「更新したつもり」が最も危ない対策・注意喚起出典 [1] [2] [3]

JVN の対策は「開発者が提供する情報をもとに、最新版へアップデートしてください」であり、修正版は LIFF SDK 2.31.1 です（出典1）。LY Corporation と GitHub Security Advisory は、配布の経路ごとに具体的な作業を挙げています（出典2・3。原文英語。訳は本記録）。

  • CDN の edge URL（https://static.line-scdn.net/liff/edge/2/sdk.js）を使っているアプリ——修正版が自動で配信されるが、実際に修正版が読み込まれているかを確認すること（出典2・3）。
  • 固定バージョンの CDN URL を使っているアプリ——URL を修正版に変更すること（出典2・3）。
  • npm の @line/liff を使っているアプリ——依存関係と lockfile を更新し、再ビルドして再デプロイすること（出典2・3）。
  • SDK のコピーを自前で配信している場合——修正版に差し替えること（出典2・3）。
  • アプリ側のキャッシュに古い SDK やバンドルが残っている場合——デプロイ時に併せて更新すること（出典2・3）。

本記録が危ういと見るのは1番目です（本記録の評価）。自動配信の経路を使っている組織は「何もしなくても直る」と理解しがちですが、アドバイザリ自身が「実際に修正版が読み込まれているか確認せよ」と書いています（出典2・3）。CDN・CloudFront 等の中間キャッシュ、Service Worker、アプリ内に同梱したバンドルのどこかに旧版が残っていれば、自動配信は届きません（本記録の評価。出典2・3 はキャッシュへの言及にとどまる）。

なお、出典2・3 のいずれにも独立した「Workarounds（回避策）」の節はありません（本記録の確認）。更新せずに緩和する手段は示されていない、と読むべきです（本記録の評価）。

技術的詳細は意図的に伏せられており、自社アプリが踏むかどうかは自力では判定できない未確定事項出典 [1] [2] [3]

GitHub Security Advisory は、技術的詳細を「アプリ開発者が更新できるようにするため」非公開としています（出典3。原文英語）。どの API のどの引数に細工した値が渡ると発火するのか、どの URL スキームが起点になるのかは、3資料のいずれにも書かれていません〈未確定1〉（出典1・2・3。本記録の確認）。

この非公開には利点と代償があります（本記録の評価）。利点は、更新が行き渡る前に実証コードが出回るのを遅らせられることです。 代償は、「自社のアプリの作りなら影響を受けない」という判定を防御側が自分でできないことです。

したがって、対象バージョンを使っているなら、影響の有無を見積もらずに更新する以外の選択肢は実務上ありません（本記録の評価）。逆に、更新を遅らせる判断をする場合は、その間に何が起こりうるかを評価する材料が無いという事実も同時に記録しておくべきです（本記録の評価）。

CISO・経営層への示唆
  • 依存ライブラリの脆弱性は「自社の脆弱性」として扱う。影響が出るのは自社のオリジンである。
    本件で壊れていたのは LIFF SDK だが、任意スクリプトが動くのは SDK を読み込んだ各アプリのエンドポイントのオリジンであり、 失われうるのは自社アプリのトークンとセッションである（出典2・3）。 SDK 提供者が直しても、自社が配信を更新しなければ何も変わらない（本記録の評価）。
    取るべき行動 外部 SDK・JavaScript ライブラリについて「誰が更新の責任を負うか」を サービス単位で決め、台帳に記載する。 CDN 自動配信を使っているサービスも「自動で直る」扱いにせず、 更新確認の担当を置く。
  • CVSS 5.1 は「後回し」の理由にならない。ベクタの `SC:L/SI:L` が示す波及先を見る。
    v4.0 基本値 5.1・v3.1 基本値 6.1 は中程度の評点だが、 脆弱な部品自身への影響が無い（`VC:N/VI:N/VA:N`）一方で 後続システムに影響が出る（`SC:L/SI:L`）という形である（出典1）。 評点は部品に対して付いており、自社サービスにとっての重さではない（本記録の評価）。
    取るべき行動 脆弱性の受け入れ基準に点数だけを置かず、 「スコープ変更の有無」「自社でトークンをどこに置いているか」を 加点要素として判定表に明記する。
  • 技術的詳細が伏せられた脆弱性では、「自社は該当しない」という判断は成立しない。
    出典3 は、アプリ開発者が更新できるようにするため技術的詳細を非公開としている （原文英語）。発火条件が分からない以上、自社アプリの実装を根拠に 影響なしと結論づける材料は存在しない（本記録の評価）。
    取るべき行動 非公開詳細つきのアドバイザリに対しては、影響調査を待たずに 「対象バージョンを使っているか」だけで更新を決める運用に切り替える。 影響調査は更新後に行う。
  • 修正版のリリースとアドバイザリの公開には時間差がある。更新の検知を告知に依存しない。
    修正版 2.31.1 の告知 URL は2026年9月30日の日付を持ち、 アドバイザリの公開は10月20日、JVN は10月22日である（出典1・2・3・4）。 告知を待っていた組織は、3週間ぶんの露出を知らないまま過ごしたことになる （本記録の評価）。
    取るべき行動 主要な依存パッケージについて、アドバイザリではなく リリース通知（npm・GitHub Releases 等）を監視対象に加える。 パッチ版の無言リリースを拾える経路を1つ持つ。
セキュリティ技術者への示唆
  • 更新作業は4経路に分かれる。自分のアプリがどれかを先に確定させる。
    出典2・3 は、CDN edge URL・固定バージョン CDN URL・npm・自前配信の 4通りを分けて手順を示している（原文英語）。 経路を取り違えると「更新したつもり」で旧版が残る（本記録の評価）。
    取るべき行動 配信しているページのネットワークログで、実際に読み込まれている `sdk.js` の URL とバージョンを確認する。 複数サービスを持つ場合は、サービス単位で経路を一覧にする。
  • CDN 自動配信でも、中間キャッシュとバンドルに旧版が残る。読み込まれている版を実測する。
    出典2・3 は、edge URL なら自動配信されるとしつつ 「実際に修正版が読み込まれているか確認すること」 「アプリ側のキャッシュに古い SDK やバンドルが残っている場合は デプロイ時に更新すること」と明記している（原文英語）。
    取るべき行動 本番で読み込まれる SDK のバージョンを外形監視に入れる。 Service Worker・CDN キャッシュ・ビルド成果物に同梱したコピーの3か所を 個別に確認する。
  • アクセストークンを JavaScript から読める場所に置いているなら、XSS 1件でそれが全部出る。
    出典3 は「トークンが漏えいするかどうかは、トークンが存在し、 注入されたスクリプトから参照できるかに依存する」としている（原文英語）。 HttpOnly Cookie は直接読み取れないとも明記されている（出典3）。
    取るべき行動 自社アプリで ID トークン・アクセストークンをどこに保持しているかを棚卸しし、 localStorage に置いているものを HttpOnly Cookie か短命のメモリ保持へ移す計画を立てる。 移せないものは有効期限を短くする。
  • 「アプリの認可制御に従う範囲」が被害の上限になる。サーバ側の検証を薄くしない。
    出典3 は、不正操作の範囲をアプリの認可制御に従う範囲としている（原文英語）。 クライアント側のスクリプトが乗っ取られても、 サーバ側が操作ごとに権限と文脈を検証していれば被害は限定される（本記録の評価）。
    取るべき行動 金銭・個人情報・権限変更に関わる操作について、 クライアントからの要求だけで完了しないよう再認証または サーバ側の追加検証を入れる。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 自社または委託先のウェブアプリが LIFF SDK（`@line/liff`）2.20.0〜2.31.0 を読み込んでいる
システム構成□ SDK を CDN の自動配信経路（edge URL）で読み込んでおり、読み込まれている版を実測していない
認証・認可□ アプリのオリジンで、JavaScript から参照できる場所（localStorage 等）に認証トークンを保持している
データの保持□ そのアプリのオリジンで、個人情報や決済に関わる画面・API を扱っている
運用・監視□ 依存パッケージのパッチ版リリースを、アドバイザリ公表とは別経路で検知できていない
体制・契約□ 外部 SDK を含むフロントエンド資産について、更新責任者とサービス単位の台帳が無い
