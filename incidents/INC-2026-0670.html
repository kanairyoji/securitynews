INC-2026-0670M365 トークン再生で79組織侵害

盗んだセッショントークンを「スプレー」して Microsoft 365 に入り続けた10週間—— 79組織でサインインが成立し、48台の偽デバイス登録と MFA 方式の入れ替えで 居座られた（Huntress 公表）

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）人を介した誘導（ビッシング・BEC）
初報: 2026年10月22日（Huntress 公表日） 最終更新: 2026年10月28日（二次報道の統合時点）

パスワードは一度も破られていません。攻撃者が使ったのは、MFA を通過した後に発行された「ログイン済みの証明」そのものでした。

2026年10月22日、Huntress は Microsoft 365 を狙ったトークン再生キャンペーンを公表しました（出典1。著者は Andrea Hatcher・Susannah Matt・Matt Poto・Andrew Schwartz）。同社は2026年7月14日から9月22日までの約10週間に、79の被害組織にまたがる497件の Microsoft 365 サインインイベントを検知し、同じキャンペーンに由来する20万件超のログイン失敗をドイツのホスティング事業者 1337 Services GmbH（AS210558）の193.26.115[.]0/24 にさかのぼったとしています（出典1）。

本記録が要点と見たのは、次の3点です。

  • 「トークンスプレー」である。パスワードスプレーの、当て推量をやめた版である。 攻撃者は AiTM リレーの背後に置いた偽サインインページ、デバイスコードフィッシング、正規ログイン中の誘導という複数の経路でトークンを集め、それを多数の組織に対して大量に再生しました（出典1）。Huntress はこれを、推測したパスワードの代わりに盗んだトークンを使う「token spraying」と呼んでいます（出典1。原文英語）。
  • 居座りの手段はトークンではなく、アカウントに残る設定だった。 攻撃者は被害組織のディレクトリに少なくとも48台の偽コンピュータを登録し（出典1）、19の組織では最初のサインインから3時間以内に、利用者の既存 MFA 方式を消去して新しい方式を登録しています（出典1）。Huntress は「盗んだセッショントークンはいずれ失効するか取り消されるが、MFA 方式はアカウントに残る」「パスワードリセットをしても、誰かが MFA 方式を点検して不正なものを削除しない限り、そのアクセスは生き残る」と書いています（出典1。原文英語。訳は本記録）。
  • 条件付きアクセスは効いた。ただし、効いた組織だけで効いた。 第3波（9月11日〜・193.26.115[.]72）では、同じ送信元から1,052件のサインインがブロックされていますが、そのブロックはすべて4組織から出たものでした（出典1）。同じ期間に29の組織では何も止まっていません（出典1）。

本記録は2026年10月23日に Huntress の公表（出典1）を直接取得して裏を取りました。 同社が攻撃者を特定の集団に帰属させた記述は無く、Microsoft からの独立した公表も本記録は確認していません〈未確定1・齟齬2〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

パスワードを一度も使わずに Microsoft 365 のアカウントを奪う連鎖である。 捕捉（AiTM リレー・デバイスコードフィッシング）と再生（1337 Services の /24）を 別のインフラに分け、入った後はディレクトリとアカウント設定に足場を残した（出典1）。

  1. 1. 初期侵入確認済
    利用者を偽サインインページ（AiTM リレー）へ誘導する、 またはデバイスコードを Microsoft の正規サインインページに入力させる。 後者では利用者が攻撃者のセッションを知らずに認可することになる（出典1）。
    根拠: 「偽サインインページの背後の AiTM リレー、デバイスコードフィッシング、 正規ログイン手続き中のソーシャルエンジニアリング」（出典1。原文英語）。 第2波では `193.26.115[.]16` から Microsoft Office のデバイスコードフロー経由の サインインが記録されている（出典1）。
  2. 2. 認証情報アクセス確認済
    リレーが MFA 通過後に Microsoft が発行したセッショントークンを保持する。 MFA の後に発行されるため、以後の再認証を必要としない（出典1）。
    根拠: 「そのトークンは MFA の後に発行されるため、それを持つ者はもう一度 MFA を通る必要がない」（出典1。原文英語）。
  3. 3. 検知回避確認済
    盗んだトークンを 1337 Services GmbH の `193.26.115[.]0/24` 上のホストから 自動的に再生する。Build A は `node` の User-Agent で `OAuth2:Token` を要求し、 Build B は Chrome／Edge を装って OfficeHome のセッションを再生する（出典1）。
    根拠: 6つのアドレスが順に使われ、期間中20万件超のログイン失敗と497件の サインインイベントが観測された（出典1）。 Microsoft Entra ID Protection も4つのアドレスを検知している（出典1）。
  4. 4. 永続化確認済
    被害組織のディレクトリに `DESKTOP-` ＋16進数8文字の名前で偽デバイスを登録する （少なくとも48台）。また、利用者の既存 MFA 方式を消去して 攻撃者自身の認証アプリを登録する（19組織で初回サインインから3時間以内）（出典1）。
    根拠: 7月21日の事例では MFA 通過の約50分後に「iPhone 13」という認証アプリが 登録されている（出典1）。第1波の終わり（8月3日）までに37組織で 37台の不正デバイスが登録された（出典1）。
  5. 5. 収集確認済
    受信トレイルールを作成し、特定の相手や語句（payroll・direct deposit・bank・bonus）に かかるメールを既読化・移動・削除して被害者の目から隠す（出典1）。
    根拠: 第1波では `sss` という名前のルールで全受信メールを既読にして削除、 第3波では `s`・`d` の2つのルールで会計事務所からの返信を 会話履歴フォルダへ移していた（出典1）。
  6. 6. 影響（暗号化・破壊・改ざん）確認済
    侵害したメールボックスを使って、数百の外部宛先へのスパム送信、 および外部の会計事務所への給与関連メールの送信が行われた（出典1）。 送金の成否は公表されていない〈未確定4〉。
    根拠: スパム送信については Microsoft Entra ID Protection がアカウントを 高リスクと判定し、Huntress がルールを無効化している（出典1）。

パスワードを当てるのをやめ、MFA 通過後のトークンを大量に再生した原因・手口出典 [1]

Huntress は手口をこう説明しています（出典1。原文英語。訳は本記録）。

攻撃者はパスワードを推測するのではなく、被害者から盗んだサインイントークンを再生した（出典1）

トークンの出どころは3つ挙げられています——偽サインインページの背後に置いたAiTM（adversary-in-the-middle）リレー、デバイスコードフィッシング、そして正規のログイン手続きの最中に行われるソーシャルエンジニアリングです（出典1）。

AiTM の仕組みについて、記事は次のように書いています（出典1。原文英語。訳は本記録）。

被害者は、自分と Microsoft の間に入ったリレーを通してサインインする。リレーは本物のログインページと MFA のプロンプトをそのまま被害者に渡し、被害者がサインインを終えたときに Microsoft が発行する「ログイン済みの証明」であるトークンを手元に残す。そのトークンは MFA の後に発行されるため、それを持つ者はもう一度 MFA を通る必要がない（出典1）

そのうえで、盗んだトークンを自分たちのマシンから自動的に大量再生する動きを、同社は「token spraying」と呼んでいます——推測したパスワードの代わりに盗んだトークンを使う、パスワードスプレーと同じ型です（出典1。原文英語）。

期間中、20万件超のログイン失敗が 193.26.115[.]0/24 にさかのぼれた一方、成功したサインインイベントは497件でした（出典1）。この比は、手作業の侵入ではなく、使えるトークンを探す総当たりに近い運用だったことを示しています（本記録の評価）。

再生側は1つの /24 に居座り、6つのアドレスを順に使い替えていた原因・手口出典 [1]

再生に使われたのは、ドイツ・ハンブルクのホスティング事業者1337 Services GmbH（AS210558）の 193.26.115[.]0/24 です（出典1）。Huntress は、この事業者が正規の IP ホスティングを提供しているとしたうえで、攻撃者がこの種の事業者を使って悪性トラフィックを置く手口を「bring your own IP（BYOIP）」として説明しています（出典1。原文英語）。

同社はこの /24 の中の6つのアドレスが順番に使われたとしています（出典1）。アドレスを替えた理由は分からないとしつつ、効果についてはこう書いています（出典1。原文英語。訳は本記録）。

1つのアドレス向けに書かれたブロック・アラート・条件付きアクセスのルールは、次のアドレスには何もしない（出典1）

実際、Microsoft Entra ID Protection も193.26.115[.]221・.72・.16・.21 を個別の IP として検知しており、レンジとしては扱っていません（出典1）。Huntress は「どれか1つのアドレスをブロックしても、止められたのはせいぜい1つのフェーズだった。/24 をブロックしていれば主要な再生ホスト6つすべてを覆えた（ただしこの範囲の外にも 1337 Services のアドレスがいくつか使われている）」と述べています（出典1。原文英語。訳は本記録）。

さらに、捕捉側と再生側は別の事業者に分かれていました（出典1）。AiTM リレーは別のホスティング（第4波では Evoxt Sdn. Bhd.）に置かれ、受信トレイルールの作成はいずれも 1337 Services のネットワークからではなく、その都度別のレンタルサーバや VPN のアドレスから行われています（出典1）。Huntress の整理はこうです——「1337 のレンジをブロックしても認証情報の捕捉は止まらないし、リレーをブロックしても、すでに盗まれたトークンの再生は止まらない」（出典1。原文英語。訳は本記録）。

/24 の外で使われた 1337 Services のアドレスとして124.198.132[.]33・45.83.31[.]44・192.159.99[.]172 が、第4波の Evoxt のリレーとして 185.238.2[.]195 とIPv6 の 2400:8d60:2::1:841d:5dd が挙げられています（出典1）。再生の主範囲だけを遮断対象にすると、これらは残ります（本記録の評価）。

道具立ては2種類あり、片方は自動化された台本、もう片方は人のブラウザに見える原因・手口出典 [1]

Huntress は再生ホストで動いていた道具立てを Build A・Build B の2つに分けています（出典1）。

Build A はスクリプトによるトークン再生です（出典1）。

  • User-Agent は node（または素の Mozilla/5.0）（出典1）
  • 要求の種類は OAuth2:Token——トークンを別のトークンに交換する動き（出典1）
  • クライアントアプリは Microsoft Office および Microsoft Authentication Broker（出典1）
  • 対象は Microsoft Graph・Exchange Online・SharePoint Online・Device Registration Service（出典1）
  • DESKTOP- ＋16進数8文字の名前を持つ不正な Entra 参加デバイスを伴う（出典1）

Build B はブラウザセッションの再生です（出典1）。

  • User-Agent は Windows 上の現行の Chrome／Edge（出典1）
  • クライアントアプリは OfficeHome、対象は OfficeHome と Exchange Online（出典1）
  • デバイス登録は伴わない（出典1）

Huntress は、Build A が登録したデバイス名について「DESKTOP- に大文字16進数ちょうど8文字」という形が48台で共通しており、これは Windows の出荷時既定である DESKTOP- ＋英数字7文字とは一致しない、と指摘しています（出典1）。防御側にとっては、ここが数少ない「機械的に見分けがつく印」です（本記録の評価）。

逆に Build B は、それ単体では通常のブラウジングに見えます（出典1 の IoC 表のUser-Agent 欄の記述）。User-Agent での選別は Build A には効き、Build B には効きません（本記録の評価）。

居座りを支えたのはトークンではなく、アカウントに残る MFA 方式とデバイス登録だった原因・手口出典 [1]

7月21日の1件では、MFA 通過から約50分後に「iPhone 13」と名付けられた新しい認証アプリがアカウントに登録されています（17:18:20 捕捉／18:08:50 登録。出典1）。

Huntress はこの行為の意味をこう説明しています（出典1。原文英語。訳は本記録）。

自分の認証アプリを登録しておけば、攻撃者はいつでも新しいサインインの MFA を完了できる。そしてそのアクセスは、誰かがアカウントの MFA 方式を点検して不正なものを削除しない限り、パスワードリセットを行っても生き残る（出典1）

19の組織では、最初のサインインから3時間以内に、被害者の既存の MFA 方式が消去され、新しい方式が登録されました（出典1）。第2波以降は、Microsoft のセキュリティ情報登録サービスを通じてMFA 方式を消してから、数分後に新しい認証アプリを登録する、という一貫した型が観測されています（出典1）。

デバイス登録も同じ役割を果たしています（出典1）。少なくとも48台の偽コンピュータが被害組織のディレクトリに登録され、Huntress は「登録済みのデバイスは、盗んだセッション単体よりも持続的にトークンを要求する手段を攻撃者に与える。そしてそれは、誰かが削除するまでディレクトリに残り続ける」としています（出典1。原文英語。訳は本記録）。

つまり、この事案で「封じ込め」を名乗るには、パスワードリセットでもセッション失効でも足りません（本記録の評価）。MFA 方式の棚卸しと、ディレクトリに残ったデバイスの削除まで行って初めて、攻撃者の足場が消えます（出典1 の記述に基づく本記録の評価）。

条件付きアクセスは実際に止めていたが、止まったのは4組織だけだった対策・注意喚起出典 [1] [2]

第3波（193.26.115[.]72・9月11日〜15日）の数字が、この事案で最も示唆的です（本記録の評価）。

同じ送信元から、29の組織では303件のサインインが成立し、一方で1,052件がブロックされています（出典1）。そしてそのブロックは、すべて4つの組織から出たものでした（出典1）。Huntress の言い方はこうです——「入れた29組織では、何も立ちはだからなかった」（出典1。原文英語。訳は本記録）。

同社が挙げている対策は次のとおりです（出典1。原文英語。訳は本記録）。

  • 条件付きアクセス——すべての利用者・すべてのクラウドアプリ・すべてのクライアント種別に対して、無条件に MFA を要求する（またはブロックする）
  • 優先順位——スプレーの量ではなく、認証情報が有効かどうかで対応の優先度を決める
  • セッションの失効——パスワードリセットだけでは足りない。セッションを取り消す。アクセストークンは約90分有効なままの場合がある
  • デバイスの点検——DESKTOP- 等の名前でホスティング IP から登録されたデバイスを確認する（削除の前に確認する）
  • MFA の点検——短時間で消去・再登録された方式や、利用者が身に覚えのない認証アプリを削除する
  • 受信トレイルールの確認——名前が1〜3文字や記号だけのルール、RSS フィードや会話履歴フォルダへ移動するルール、給与・銀行関連の語句で動くルールを探す
  • AADSTS53003 の扱い——これは認証が成功した後のブロックである。「防げた」ではなく「有効な認証情報が存在する」兆候として扱う
  • デバイスコードフローの制限——認証フローに対する条件付きアクセスで絞る
  • ハンティング——ホスティング基盤から、Office／Authentication Broker クライアントでnode や素の Mozilla/5.0 の User-Agent を使って行われる OAuth2:Token のサインインを探す
  • 新規アプリの監視と同意の制限——新しいエンタープライズアプリを確認し、一般利用者によるアプリ同意を無効にして申請制にする

このうち、本記録が運用上もっとも効きが大きいと見るのは「AADSTS53003 を防御の成功として数えない」という点です（本記録の評価）。ブロックのログが積み上がっている組織は、一見すると守れているように見えますが、実際には「有効なトークンがすでに相手の手にある」状態だからです（出典1 の記述に基づく本記録の評価）。

二次報道もこの点を正面から書いています——「一部の組織は条件付きアクセスのポリシーで攻撃者のサインインを遮断できたが、他の組織では成功サインインが生じた。したがって企業は、遮断されたサインインの回数だけで被害の程度を判断してはならない」（出典2。原文中国語。訳は本記録）。

メールボックスの使われ方は、スパムの踏み台から給与の詐取まで幅があった業務・事業への影響出典 [1]

侵害後の使われ方は、フェーズによって違います（出典1）。

第1波では、特定の語句を含むメールを削除するか、RSS フィードのような目立たないフォルダへ移すルールが作られました（出典1）。あるメールボックスでは、sss という名前のルールで受信メールをすべて既読にしたうえで削除する設定が作られ、そのメールボックスから数百の外部宛先へスパムが送信されています（出典1）。Microsoft Entra ID Protection がアカウントを高リスクと判定し、Huntress がルールを無効化した、と記されています（出典1）。

第3波では、より狙いの定まった使われ方が観測されています（出典1）。攻撃者は s という名前の受信トレイルールを変更して、payroll（給与）・direct deposit（口座振込）・bank（銀行）・bonus（賞与）のいずれかを含むメールを捕まえるようにしました（出典1）。その5分後、同じ Interserver のアドレス（167.148.41[.]96）からd という2つ目のルールを作り、外部の会計事務所（CPA）のアドレスから届くメールを既読にして会話履歴フォルダへ移すようにしています（出典1）。そのうえで、侵害したメールボックスから当の会計事務所へ給与関連のメールを送っています（出典1）。

返信を被害者から隠したうえで外部とやり取りする—— BEC（ビジネスメール詐欺）の典型的な組み立てです（本記録の評価）。送金が実行されたかどうかは公表されていません〈未確定4〉。

なお、受信トレイルールはいずれも 1337 Services のネットワークからではなく、別のレンタルサーバや VPN のアドレスから作られています（出典1）。再生ホストの IP だけを探していると、メールボックス側の操作は見落とします（本記録の評価）。

CISO・経営層への示唆
  • 「MFA を入れた」は、この手口に対する答えになっていない。奪われたのは MFA 通過後の証明である。
    攻撃者はパスワードを一度も破っていない（出典1）。 AiTM リレーは本物の MFA プロンプトを素通しし、完了後に発行されたトークンを 手元に残している（出典1。原文英語）。 MFA の導入率を統制の指標にしている組織は、この事案を「対象外」と誤読する （本記録の評価）。
    取るべき行動 認証に関する経営報告の指標を「MFA 導入率」から 「フィッシング耐性のある認証方式（FIDO2／証明書ベース）の比率」と 「トークン保護・条件付きアクセスの適用範囲」に差し替える。
  • 封じ込めの定義を改める。パスワードリセットは、この事案では封じ込めではない。
    Huntress は、攻撃者自身の認証アプリが登録されていれば 「パスワードリセットを行ってもアクセスは生き残る」と明記している（出典1。原文英語）。 アクセストークンは約90分有効なままの場合があるとも述べている（出典1）。
    取るべき行動 アカウント侵害時の対応手順に、①セッションの明示的な失効 ②MFA 方式の棚卸しと不正な方式の削除 ③登録デバイスの確認と削除 ④受信トレイルールの確認、の4つを必須項目として書き込む。 1つでも欠けた状態を「封じ込め完了」と呼ばない。
  • ブロックのログが増えていることを、守れている証拠として読まない。
    Huntress は `AADSTS53003` について「認証が成功した後のブロックであり、 有効な認証情報が存在する兆候として扱うべきだ」としている（出典1。原文英語）。 第3波の1,052件のブロックは4組織に集中しており、 その4組織は「狙われていた組織」でもある（出典1）。
    取るべき行動 条件付きアクセスのブロック件数を、月次のセキュリティ報告で 「阻止した攻撃」ではなく「有効な資格情報が外部にある可能性」の指標として扱い、 該当利用者のトークン失効と MFA 点検をセットで回す運用に変える。
  • 被害の出口はメールである。BEC を想定した業務側の統制を、技術対策と別に持つ。
    攻撃者は受信トレイルールで返信を隠したうえで、外部の会計事務所へ 給与関連のメールを送っている（出典1）。 メールアカウントの奪取そのものより、その後の送金指示が損害になる （本記録の評価。送金の成否は公表されていない〈未確定4〉）。
    取るべき行動 振込先の変更・給与の支払先変更について、メール以外の経路での 確認（登録済みの電話番号への折り返し等）を必須とする規程を作り、 例外を認めない。取引先にも同じ運用を求める。
セキュリティ技術者への示唆
  • `OAuth2:Token` ＋ホスティング事業者の IP ＋`node` という組み合わせが、最も機械的な目印である。
    Build A は User-Agent が `node`（または素の `Mozilla/5.0`）、要求種別が `OAuth2:Token`、クライアントが Microsoft Office／Authentication Broker、 対象が Graph・Exchange Online・SharePoint Online・Device Registration Service という組み合わせだった（出典1）。
    取るべき行動 サインインログに対し、「ホスティング／データセンター由来の IP」 ×「`OAuth2:Token`」×「`node` または素の `Mozilla/5.0`」で継続的なハンティングを 仕掛ける。Device Registration Service へのサインインは特に優先して確認する。
  • デバイス名の命名規則は、既定値との差で機械的に抽出できる。
    不正登録された48台はいずれも `DESKTOP-` ＋大文字16進数ちょうど8文字で、 Windows の出荷時既定（`DESKTOP-` ＋英数字7文字）とは一致しない（出典1）。
    取るべき行動 Entra ID の登録デバイス一覧を正規表現 （`^DESKTOP-[0-9A-F]{8}$` に相当する条件）で突き合わせる定期ジョブを作る。 合致したデバイスは、削除の前に登録元 IP・登録日時・紐づく利用者を記録する。
  • IP 単位のブロックは、この相手には効かない。レンジと「種別」で考える。
    6つのアドレスが順に使われ、Microsoft の検知も個別 IP 単位だった（出典1）。 Huntress は「`/24` をブロックしていれば主要な再生ホスト6つすべてを覆えた」 としつつ、範囲外のアドレスも使われたと留保している（出典1。原文英語）。
    取るべき行動 ブロックの単位を IP から ASN・レンジ・「ホスティング事業者由来かどうか」へ上げる。 条件付きアクセスのネットワーク条件に、従業員が使うはずのない データセンター由来のトラフィックを含める。
  • メールボックス側の操作は、侵入に使われた IP とは別のところから来る。
    受信トレイルールはいずれも 1337 Services のネットワークからではなく、 その都度別のレンタルサーバや VPN のアドレスから作られていた（出典1）。 第3波のルール作成元は Interserver の `167.148.41[.]96` である（出典1）。
    取るべき行動 インシデント調査で「既知の悪性 IP からの操作」だけを追わない。 侵害期間中に作成・変更されたすべての受信トレイルールを、 作成元 IP を問わず列挙して確認する手順にする。
  • 捕捉から再生までは4分だった。人の目視確認を前提にした対応手順は間に合わない。
    9月22日の事例では、被害者が MFA を完了してから4分後に 別のホストからセッションが再生されている（出典1）。 7月21日でも12分である（出典1）。
    取るべき行動 「普段と違う場所・デバイスからのサインイン」に対する対応を自動化する （リスクベースのサインイン条件でセッションを自動失効させる、 デバイス登録イベントを即時にアラート化する）。 手動トリアージを待つ設計は、この時間軸では機能しない。
