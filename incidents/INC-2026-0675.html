2026年10月21日、Node.js は10件の脆弱性をまとめて修正するセキュリティリリースを公開しました（出典1）。そのうち最も重いのが CVE-2026-111497——同梱する Brotli デコーダの境界外書き込みで、リモートコード実行を許すもので、深刻度は High です（出典1）。対象は 22.x・24.x・26.x の3系列、修正版は 22.23.4・24.22.1・26.12.1 で、Node.js 20 以前には修正が提供されません（出典1）。

2026年10月22日、Imperva の脅威リサーチが「Node2Shell」としてこの脆弱性の実証を公開しました（出典2）。本記録が要点と見たのは、次の3点です。

  • 実証は「公式ビルドのまま」行われた。 Imperva は公式の Node.js 24.22.0 Linux arm64 イメージを使い、新しいコンテナ上で実行したとしており、「デバッガも計測用のバイナリも必要なかった」と明記しています（出典2。原文英語）。メモリサニタイザは不具合そのものを調べるために別途使ったもので、コード実行の実証には使っていないとしています（出典2）。これまで公開されていた実証コードは、標準ビルドに対してはクラッシュとプロセスメモリの限定的な読み出しまでで、コード実行には至っていませんでした（出典2）。
  • 入口は2つある。「受け取る側」と「送られる側」の両方である。 ①Node.js 組み込みの fetch() が圧縮された応答を復号するとき（＝自分が外へ取りに行った先から返ってくるデータ）。②受信したリクエストボディを Express 5.0.0〜5.3.0 またはbody-parser 2.0.0〜2.3.0 が展開するとき（出典2）。素の Node.js の HTTP サーバは、Brotli のボディを受け取っただけでは展開しないとされています（出典2）—— 脆弱なコードは Node.js にあり、ミドルウェアは「そこへ到達する経路」を作る側です。
  • 確実には動かない。「成立しうる」と「いつでも成立する」は別である。 Imperva は「我々の環境では実行に複数回の試行を要した」「実証はすべての試行で成功したわけではない」と書いています（出典2。原文英語）。検証したのは Linux arm64 のそのビルドとアプリ構成であり、22.x・26.x や他のアーキテクチャは試していないとしています（出典2）。修正版 24.22.1 では同じ入力が拒否され、コードは動きませんでした（出典2）。

「公式ビルドのまま」成立したことが、この実証の意味である評価・解釈

脆弱性の実証には、しばしば前提が付きます（本記録の整理）。デバッガを当てる、計測用に作り直したバイナリを使う、ASLR を切る、特定のヒープ配置を先に作る——どれも「研究室では動くが現場では動かない」と読む理由になります。

Imperva の実証には、その前提がありません（出典2）。

  • 使ったのは公式の Node.js 24.22.0 Linux arm64 イメージである（出典2）
  • 新しいコンテナ上で実行した（出典2）
  • 「デバッガも計測用のバイナリも必要なかった」（出典2。原文英語）
  • メモリサニタイザは不具合そのものを調べるために別途使ったもので、コード実行の実証には使っていない（出典2）

これまで公開されていた実証は、ここまで届いていませんでした（出典2）。最初の公開された実証コードの作者は、標準ビルドに対してはクラッシュとプロセスメモリの限定的な読み出しを報告しており、コード実行ではありませんでした（出典2）。

「クラッシュする」と「コードが動く」の間には、実務上まったく違う対応が入ります（本記録の評価）。前者なら可用性の問題として段階的に直せますが、後者は「そのプロセスの権限で何でもできる」ことを意味します。

ただし、同じレポートに留保が書かれています（出典2）。

  • 「我々の環境では実行に複数回の試行を要した」（原文英語）
  • 「実証はすべての試行で成功したわけではない」（原文英語）
  • 検証したのは Linux arm64 のそのビルドとアプリ構成であり、すべての Node.js のビルドやアプリ、中間ミドルウェアのすべてのリリースを試したわけではない

この2つは矛盾しません（本記録の評価）。「毎回確実に動く攻撃」ではないが、「公式ビルドに対して条件を揃えれば動く攻撃」ではある、という状態です。 防御側の判断に使えるのは後者のほうです。

入口は「受け取る側」と「送られる側」の両方にある——素の HTTP サーバだけは別原因・手口

Brotli は圧縮形式であり、Node.js がそれを展開する場面は一つではありません（本記録の整理）。Imperva は2つの経路を試しています（出典2）。

①自分が取りに行った先から返ってくるデータ

Node.js 組み込みの fetch() が、圧縮された応答を復号するときです（出典2）。これは「攻撃者がこちらのサーバへ送ってくる」構図ではありません（本記録の評価）—— こちらから外部 API・外部サイトへ取りに行き、その応答に細工が入っている構図です。 外向きの通信を WAF で見ていない組織では、ここは監視の外にあります。

②受信したリクエストボディ

Express 5.0.0〜5.3.0、または body-parser 2.0.0〜2.3.0 がボディを展開するときです（出典2）。Imperva が版を固定して試したのは、Express 5.0.0＋body-parser 2.0.1、Express 5.3.0＋body-parser 2.3.0、body-parser 2.0.0 単体の3つで、raw() と json() の両方のパーサを使っています（出典2）。

ここで区別が要ります（出典2）。

素の Node.js の HTTP サーバは、Brotli のボディを受け取っただけでは展開しません（出典2）。脆弱なコードは Node.js にあり、ミドルウェアは「そこへ到達する経路」を作る側です（出典2 の記述に基づく整理）。

したがって、これは Express の脆弱性でも body-parser の脆弱性でもありません（本記録の明示）。Express を外しても Node.js を更新しなければ①の経路は残り、Node.js を更新すれば①も②も閉じます。 直すべきものは Node.js です。

同梱されているから、更新は「パッケージ一覧」では見つからない対策・注意喚起

欠陥があるのは Node.js 自身のコードではなく、Node.js が同梱する Brotli ライブラリです（出典1・2）。この構図が、更新作業の形を決めます（本記録の評価）。

Node.js のリリースは2つの場合を挙げています（出典1）。

  • Node.js が同梱する brotli 依存部が脆弱である
  • システム側の brotli をリンクしているビルドでも、上流（google/brotli）の修正（コミット 0ed4268）より古ければ影響を受ける

Imperva の対策の案内も、この点を中心に置いています（出典2）。

  • 修正版（22.23.4／24.22.1／26.12.1 以降）へ更新する。Node のバイナリを同梱しているコンテナイメージやその他の成果物も含める
  • 保守対象外の系列で動いているアプリは、支援されている版へ移す
  • 信頼できない Brotli データが処理系へ届く場所を洗い出す（取り込んだ応答と、ミドルウェアが展開するリクエストボディの両方）
  • 配備済みのイメージやホストの中で Node.js の版を確認する——パッケージの棚卸しは同梱された処理系を見落とすことがある
  • 実務上可能な範囲で、影響のある経路について信頼できない Brotli の通信を一時的に制限する（通常の通信で試験してから）

最後の項目が、この事案でいちばん実務に効きます（本記録の評価）。「npm ls に出てこないものが脆弱である」という形だからです。 依存関係の一覧には Brotli は現れません。 現れるのは「Node.js のバージョン」だけで、それはコンテナイメージの中・ビルド基盤の中・商用製品に同梱された処理系の中にあります。

痕跡は残りにくい——「落ちていないから大丈夫」は言えない未確定事項

侵害を確かめる手がかりについて、Imperva は慎重に書いています（出典2）。

「予期しないプロセスの終了やデコーダのエラーは、調査の手がかりとしてのみ扱うこと」「いずれも単独では悪用の確かな証拠にならない」（出典2。原文英語）

これは両方向に効きます（本記録の評価）。

  • エラーが出ていても、悪用されたとは言えない
  • エラーが出ていなくても、悪用されていないとは言えない

実証が「複数回の試行を要した」ものである以上、失敗した試行がプロセスを落とす形で記録に残ることは期待できます（本記録の推測）。しかし成功した試行がどう記録に残るかは、公表されていません〈未確定6〉。

  • CISA の KEV にも収載されていない（出典5。2026年10月23日時点）

それでも実務上の意味は大きい。 「公開ツールをそのまま投げる」段階に入ったということは、攻撃の実行に必要な技術が攻撃者側に要らなくなったということである（本記録の評価）。Imperva の実証が公式ビルドで複数回の試行を要したこと（本記録の第1回）と合わせると、成功率は低くとも母数を増やせば当たる、という形の攻撃に向く。

露出の広さは「Brotli が入っているか」ではなく「攻撃者が送ったデータを解凍するか」で決まる評価・解釈出典 [23] [24]

同じ10月29日に、露出の規模をめぐる数字と、その数字の読み方を限定する分析が並んで出た。

Wiz はクラウド環境の91%に脆弱なシステムがあり、82%では Node.js サーバがインターネットに露出していると述べている（出典23）。一方 Sysdig は、影響を受けるのは攻撃者が送った Brotli 圧縮データを処理するサービスに限られると説明する。ただし Node.js のウェブフレームワーク Express 5 の既定のJSON 処理を使うサービスは、相当数がそこに含まれる（出典23）。Rapid7 も、アプリケーションが攻撃者由来の圧縮データを node:zlib で解凍するとメモリ破壊が起こりうるとし、デコーダが存在することはそれ自体では露出を意味しないと述べている（出典24）。

この3つは矛盾していない。 91%は「同梱されている環境」の割合であり、Sysdig と Rapid7 が述べているのは「成立の条件」である。本記録が第2回で書いた「入口は受け取る側と送られる側の両方にある」という整理を、数字の側から裏返した形になる（本記録の整理）。

したがって自組織の点検は2段で足りる（本記録の評価）。①インターネットに面した Node.js・Bun・.NET・Python のサービスのうち、要求本文や上流からの応答を Brotli で解凍する経路を持つものを挙げる（Express 5 の既定のJSON 処理、リバースプロキシ、HTTP クライアント）。②それらを 22.23.4／24.22.1／26.12.1 以降（Node.js の場合）へ上げる。Akamai によれば回避策は無く、更新以外に手段がない。保守が終わった系列（20.x・23.x・25.x）には修正が出ないため、系列の移行そのものが対策になる（出典23・24）。

「91%」を見て全数を止める判断は過剰であり、「限られたサービスだけ」を見て後回しにする判断は危ない——分ける基準は解凍の経路であって、同梱の有無ではない（本記録の評価）。

    取るべき行動 **Node.js プロセスの異常終了とデコーダのエラーを、 単発では警報にせず「短時間に繰り返す」ことを条件に監視する。** **ただし Imperva の留保どおり、これだけを悪用の判定に使わない。**
  • **同じ更新で3つの性質の違う問題が閉じる。更新の理由を1つに絞らない。**
    **2026年10月21日のリリースには、Brotli の RCE、 TLS 証明書ホスト名検証の回避2件（CVE-2026-105483・CVE-2026-106069）、 DNS 名の切り詰め（CVE-2026-105482）、 そして eMudhra 中間CA の危殆化への対応（同梱 CA 証明書の更新）が入っている** （出典1）。
    取るべき行動 **更新の起票理由に CVE を1件だけ書かない。** **とくに eMudhra 対応は、Node.js を更新しない限り 危殆化した中間CA を信頼し続ける**（出典1・INC-2026-0633）—— **TLS の信頼の問題として別途追跡する。**
