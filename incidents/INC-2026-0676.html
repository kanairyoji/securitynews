INC-2026-0676プリザンター LDAP 認証不備

国内のノーコード業務アプリ基盤「プリザンター」の LDAP 認証に認証不備—— **有効なログインIDを知っていれば、パスワード無しでログインできた**（CVE-2026-113438／ JVN#82312317）。対象は 1.1.0.0〜1.5.9.0、**修正版 1.5.9.1 は公表と同日**に出た。 Linux 版と Docker 版は既定の構成がそのまま該当する

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月23日（JVN 公開日・開発者のお知らせ公開日） 最終更新: 2026年10月23日（本記録の確認時点）

「パスワードが違う」と判定する手順が、特定の形のリクエストでは実行されませんでした。

2026年10月23日、JPCERT/CC は JVN#82312317 を公開し、株式会社インプリムが提供するプリザンターの LDAP 認証に認証不備の脆弱性（CWE-304・CVE-2026-113438）があることを明らかにしました（出典1）。同日、開発者も「【重要】プリザンターのLDAP認証における認証回避の脆弱性」を公開し、修正版 1.5.9.1 をリリースしています（出典2）。

影響は次のとおりです（出典1）。

「有効なログインIDを知る第三者によって、パスワードなしで当該製品にログインされる可能性があります。その結果、ログインしたユーザの権限で当該製品に登録されている情報を閲覧、改ざん、削除される可能性があります」（出典1）

本記録が要点と見たのは、次の3点です。

  • Linux 版と Docker 版は、既定の構成がそのまま該当する。 開発者が示した組み合わせの表では、Linux 環境（Docker 版を含む）は接続先が Active Directory、または匿名バインドを許可しているOpenLDAP・389 Directory Server などであれば「該当」です（出典2）。Windows 環境は DsProvider に "Novell" を指定している場合のみ該当し、既定値（null）であれば対象外です（出典2）。つまり「特別な設定をした組織だけが危ない」のではなく、Linux で動かしていること自体が条件になります（本記録の評価）。
  • 対象バージョンの幅が 1.1.0.0 から 1.5.9.0 までと広い。 Community Edition と Enterprise Edition の両方が対象です（出典2）。さらに、2026年10月13日にリリースされた 1.5.9.0 にはこの修正が含まれていません（出典2）—— 「10日前に上げたばかり」の組織も、もう一度上げる必要があります。
  • 前提条件は「ログイン画面に到達できること」だけである。 開発者は「ログイン画面にアクセスできる第三者であれば、特別な権限や準備がなくても悪用できます」と明記しています（出典2）。CVSS v4.0 の基本値は 6.9、ベクタはAV:N/AC:L/AT:N/PR:N/UI:N/VC:L/VI:L/VA:N/SC:N/SI:N/SA:N です（出典1）—— 権限も利用者の操作も要りません。

本記録は2026年10月23日に JVN（出典1）と開発者のお知らせ（出典2）を直接取得して裏を取りました。 悪用の観測は、どちらの資料も述べていません〈未確定1〉。一方、JVN は「開発者はワークアラウンドの適用を推奨しています」と書いていますが、開発者のページにはアップグレード以外の回避策が載っていません〈齟齬1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。
  1. 1. 偵察
    **有効なログインIDを把握する**（出典1 の「有効なログインIDを知る第三者」 という前提から整理した。本記録の整理）。 **ログインIDの入手経路は公表資料には書かれていない**—— **メールアドレスや社員番号をIDに使っている構成、 公開情報や過去の流出データから分かる場合がありうる**（本記録の推測）。
  2. 2. 初期侵入
    **「通常の操作では送信されない形に細工したリクエスト」を認証処理へ送る**（出典2）。 **サーバー側のリクエスト検証が不十分なため、 接続先 LDAP サーバーの設定によっては認証成功と判定される**（出典2）。 **パスワードは検証されない**（出典2）。 **具体的なリクエストの形は公表されていない**〈未確定2 相当。本記録の確認〉。
  3. 3. 影響（暗号化・破壊・改ざん）
    **ログインしたユーザの権限で、 製品に登録されている情報を閲覧・改ざん・削除される可能性がある**（出典1）。 **実際の被害の範囲は、そのユーザに与えられた権限で決まる**（本記録の整理）—— **管理者のIDであれば影響は大きくなる**（本記録の評価）。 **実際に悪用された事例は公表されていない**〈未確定1〉。

「特別な設定をした組織だけ」ではない——Linux と Docker は既定で該当する被害規模・影響範囲

脆弱性の該当条件を読むとき、いちばん先に知りたいのは「自分は該当するか」です（本記録の整理）。本件は、開発者が構成の組み合わせを表で示しています（出典2）。

プリザンターの構成 Active Directory OpenLDAP 等（匿名バインド許可） OpenLDAP 等（匿名バインド拒否）
Linux（Docker 版を含む） 該当 該当 対象外
Windows ＋ DsProvider="Novell" 該当 該当 対象外
Windows ＋ DsProvider 既定値（null） 対象外 対象外 対象外

この表の意味は、次のように読めます（本記録の評価）。

  • Linux 環境（Docker 版を含む）は、DsProvider の指定にかかわらず該当する
  • Windows 環境は、DsProvider に "Novell" を明示的に指定した場合のみ該当する
  • 接続先が Active Directory なら、匿名バインドの可否を問わず該当する
  • 接続先が OpenLDAP・389 Directory Server などの場合、匿名バインドを拒否していれば対象外

つまり「変わった設定をした組織だけが危ない」構図ではありません（本記録の評価）。Docker で立てて Active Directory につないでいる——おそらく最も普通の構成が、そのまま該当します。

対象となる認証方式も開発者が明示しています（出典2）。

  • 該当 — Authentication.json の Provider が "LDAP" または "LDAP+Local"（後者では LDAP 認証でログインするユーザのみ）
  • 対象外 — ローカル認証、SAML 認証、パスキー認証、二段階認証（メール・TOTP）、統合Windows認証

JVN の記載は、この表のうち「該当」の行を要約したものです（出典1）。判定には開発者のページの表を使うほうが確実です（本記録の評価）。

前提は「ログイン画面に到達できること」だけ——権限も利用者の操作も要らない原因・手口

開発者の説明は、成立の前提をはっきり書いています（出典2）。

「ログイン画面にアクセスできる第三者であれば、特別な権限や準備がなくても悪用できます」（出典2）

起きることは次の形です（出典2）。

  • 通常のログイン操作では発生しない
  • 「通常の操作では送信されない形に細工したリクエスト」が認証処理に送られた場合に起きる
  • サーバー側のリクエスト検証が不十分で、接続先 LDAP サーバーの設定によっては認証成功と判定される

結果として、「パスワードを正しく検証しないままログインを許可してしまう」（出典2）。

CVSS のベクタがこの前提をそのまま表しています（出典1）。

  • AV:N — ネットワーク経由
  • AC:L — 攻撃の難易度は低い
  • AT:N — 攻撃の前提条件が無い
  • PR:N — 権限は不要
  • UI:N — 利用者の操作は不要

必要なのは、有効なログインIDを1つ知っていることだけです（出典1）。

ここが本件の重さを決めています（本記録の評価）。ログインIDは秘密情報として扱われていないことが多いからです。 メールアドレスをそのまま使っている、社員番号を使っている、社内の名簿から分かる、過去の流出データに載っている——どれもありうる状態です。 「IDは知られているがパスワードは知られていない」という前提で組まれている防御が、本件では全部無効になります。

CWE-304（認証処理内の重要な手順の欠落）という分類が、正確にこの状態を指しています（出典1）。壊れたのは暗号でもセッション管理でもなく、「パスワードを検証する」という手順そのものです。

10日前に最新版へ上げた組織も、もう一度上げる必要がある再発防止

修正版は 1.5.9.1 で、2026年10月23日のリリースです（出典1・2）。開発者は、そのうえでこう書いています（出典2）。

「1.5.9.0（2026年10月13日リリース）には本脆弱性の修正が含まれていません」（出典2）

この一文が必要だった理由は明らかです（本記録の評価）。1.5.9.0 と 1.5.9.1 はパッチ版の違いでしかなく、「1.5.9 系にしたから対応済み」と読まれる危険があります。 1.5.9.0 のリリースから10日後に、同じ系列の次のパッチ版が脆弱性修正として出た形です。

更新以外の選択肢について、2つの資料の記述が食い違っています〈齟齬1〉。

  • JVN — 「最新版へのアップデートが難しい場合、開発者はワークアラウンドの適用を推奨しています。詳細は開発者にお問い合わせください」（出典1）
  • 開発者のお知らせ — アップグレード以外の回避策は掲載されていない。「バージョンアップが難しい場合は下記の連絡先までご相談ください」として問い合わせフォームを案内している（出典2）

したがって、回避策の具体は公開情報からは分かりません（本記録の確認）。即時に更新できない組織は、開発者へ問い合わせる経路しかありません。

該当条件から逆算すれば、条件を外す方向に働く設定変更はあります（本記録の推測）。

  • 接続先の OpenLDAP・389 Directory Server で匿名バインドを拒否する
  • Windows 環境で DsProvider を既定値（null）に戻す

ただしこれは本記録の推測であり、開発者が推奨するものとして示されたわけではありません（本記録の明示）。接続先が Active Directory の場合、匿名バインドの可否にかかわらず該当するとされているため、前者は効きません（出典2）。

自社が運用する環境については、開発者が明示しています（出典2）。プライベートクラウドと Pleasanter.net は LDAP 認証が未設定のため対象外で、利用者側の対応は不要とされています。

認証の回避は2回目だが、壊れた場所が違う——今回は自製品の実装である背景・過去事例

プリザンターにとって、外部の認証基盤と連携する部分での認証回避はこれが初めてではありません（本記録の整理）。

2023年11月、SAML 認証を使っている場合に認証を回避されうる脆弱性（CVE-2023-41890）が公表されています（出典3）。対象は 1.3.46.1 およびそれ以前で SAML 認証を使用している場合、Community Edition と Enterprise Edition の両方でした（出典3）。

ただし、原因の所在が違います（本記録の評価）。

  • 2023年の SAML の件 — 原因は製品が利用していたSAML ライブラリ Sustainsys.Saml2 にあり、応答処理時に IdP の発行者の検証が不十分だった（出典3）。壊れていたのは外部のライブラリである。
  • 2026年の LDAP の件 — 開発者は「サーバー側のリクエスト検証が不十分」と説明している（出典2）。壊れていたのは製品自身の認証処理である。

この違いは、組織の側の対応の仕方を変えます（本記録の評価）。ライブラリ起因なら、SBOM と依存関係の監視で拾えます。 製品自身の実装なら、製品のアドバイザリを見る以外に拾う経路がありません。

本記録が共通点として記録するのは、別のことです（本記録の評価）。どちらも「外部の認証基盤に認証を委ねている構成」で起きています。 認証をアプリ本体から切り出して IdP や LDAP に寄せることは正しい設計ですが、委ねた先との境界——応答の検証、リクエストの検証——が新しい攻撃面になります。 本件では、その境界で「パスワードを検証する」手順が抜けました。

成立しても「ログイン成功」として記録される——失敗の痕跡が残らない未確定事項

侵害の有無をどう確かめるかについて、JVN にも開発者のお知らせにも記述がありません（出典1・2。本記録の確認）〈未確定7〉。

本記録は、記録の残り方について次のように評価します（本記録の評価・推測）。

成立する場合、パスワードの検証という手順が実行されないまま認証成功と判定されます（出典2）。つまりアプリケーションの記録には、「有効なログインIDでログインに成功した」として残ることになります。

これは、よくある侵入の痕跡とは形が違います（本記録の評価）。

  • パスワードリスト型攻撃 — 大量の認証失敗が残る
  • ブルートフォース — 同一IDへの連続失敗が残る
  • 本件 — 失敗が残らない。 1回のリクエストで成功する

したがって「認証失敗の急増を監視している」仕組みでは本件は検知できません（本記録の評価）。見るべきは、ログイン元のIPアドレス・時刻・普段使っていない利用者のID・ログイン後の操作（情報の閲覧・改ざん・削除）のほうです。

ただしこれは本記録の推測です（本記録の明示）。プリザンターがどのような認証記録を残すか、細工されたリクエストが通常のログインと区別できる形で残るかは、公表資料からは分かりません〈未確定7〉。確認するには開発者へ問い合わせる必要があります。

なお、悪用の観測はどの資料も述べていません（出典1・2）。CISA の KEV にも収載されていません（出典4。2026年10月23日時点）。「観測されていない」ことと「起きていない」ことは別です—— 本件は、痕跡が正常なログインと同じ形になる種類の脆弱性です。

  • **国内製品の脆弱性は、海外のカタログや脅威情報には出てこない。**
    **本記録が2026年10月23日に確認した時点で、 CVE-2026-113438 は CISA の KEV に収載されていない**（出典4）。 **国内製品であり、今後も収載されない可能性が高い**（本記録の評価）。 **KEV や海外ベンダの脅威情報を優先度の入口にしている運用では、 国内製品の重大な脆弱性が下位に沈む。**
    取るべき行動 **JVN・IPA・製品ベンダのお知らせを、 海外の脅威情報と同等の優先度で受け取る経路を確保する。** **国内製品については、ベンダのお知らせページを RSS やメール通知で直接購読する。**
  • **外部の認証基盤に委ねている境界を、攻撃面として棚卸しする。**
    **同じ製品で、2023年に SAML 認証の回避（CVE-2023-41890）、 2026年に LDAP 認証の認証不備が公表されている**（出典2・3）。 **原因の所在は異なるが（前者は外部ライブラリ、後者は自製品の実装）、 どちらも「外部の認証基盤との境界」で起きている**（本記録の評価）。 **認証を切り出すこと自体は正しい設計だが、境界は新しい攻撃面になる。**
    取るべき行動 **自社システムについて「認証をどこに委ねているか」の一覧を作る （AD・LDAP・SAML IdP・OIDC・パスキー）。** **委ねている先ごとに、過去の認証回避の脆弱性の有無を確認し、 二要素認証や IP 制限で多層化できているかを点検する。**
セキュリティ技術者への示唆
  • **まず `Authentication.json` の `Provider` と `DsProvider` を見る。該当判定はそこで決まる。**
    **開発者は、該当するのを `Provider` が `"LDAP"` または `"LDAP+Local"` の場合とし、 Windows 環境では `DsProvider` に `"Novell"` を指定している場合のみとしている** （出典2）。 **`DsProvider` は 1.3.41.0 以降で追加された設定項目で、 未指定なら既定値（null）である**（出典2）。
    取るべき行動 **稼働中の全インスタンスの `Authentication.json` を集め、 `Provider` と `DsProvider` の値を一覧にする。** **`"LDAP+Local"` の環境では、LDAP 認証でログインするユーザが 対象になることを忘れない。**
  • **Linux と Docker は `DsProvider` を問わず該当する。「設定していないから大丈夫」は成り立たない。**
    **開発者の構成表では、Linux 環境（Docker 版を含む）は 接続先が Active Directory または匿名バインドを許可している OpenLDAP 等であれば該当するとされている**（出典2）。 **`DsProvider` による分岐は Windows 環境の行にしかない**（出典2）。
    取るべき行動 **Docker で立てたインスタンス（開発環境・検証環境を含む）を 棚卸しの対象から外さない。** **インターネットに出ている検証環境があれば、本番より先に止めるか更新する。**
  • **接続先が Active Directory なら、LDAP 側の設定では条件を外せない。**
    **構成表では、接続先が Active Directory の場合は 匿名バインドの可否にかかわらず該当するとされている**（出典2）。 **匿名バインドの拒否で対象外になるのは OpenLDAP・389 Directory Server などの場合である**（出典2）。
    取るべき行動 **接続先が AD の環境は、更新以外に条件を外す手が無いものとして 優先的に 1.5.9.1 へ上げる。** **即時に上げられない場合は、ログイン画面への到達経路を ネットワーク側で絞る。**
  • **認証失敗の監視では検知できない。見るのはログイン成功のほうである。**
    **パスワードの検証という手順が実行されないまま 認証成功と判定される形である**（出典2）。 **したがって失敗の記録が残らない**（本記録の推測）〈未確定7〉。 **公表資料には侵害調査の着眼点が示されていない**（出典1・2）。
    取るべき行動 **プリザンターのログイン成功記録について、 ログイン元IP・時刻・利用者IDの組み合わせを 普段の分布と比べられる形で保持する。** **残る記録の形が分からないため、開発者へ問い合わせて確認する。**
  • **1.3.41.0 より前の版は、構成表だけでは判定できない。**
    **`DsProvider` は 1.3.41.0 以降で追加された設定項目である**（出典2）。 **対象バージョンの下限は 1.1.0.0 であるため、 1.1.0.0〜1.3.40.x の Windows 環境には `DsProvider` の分岐が存在しない** （本記録の整理）〈未確定4〉。 **その範囲の扱いは公表されていない。**
    取るべき行動 **1.3.41.0 より前の版が残っている環境は、 該当・非該当を自分で判定せず、更新対象として扱う。** **判定が必要なら開発者へ問い合わせる。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ プリザンターの `Authentication.json` で `Provider` が `"LDAP"` または `"LDAP+Local"` に設定されている
システム構成□ プリザンターを Linux 環境（Docker 版を含む）で動かしている、 または Windows 環境で `DsProvider` に `"Novell"` を指定している
認証・認可□ 接続先の LDAP サーバーが Active Directory である、 または匿名バインドを許可している OpenLDAP・389 Directory Server などである
運用・監視□ バージョンが 1.1.0.0 以上 1.5.9.0 以下である （1.5.9.0 も対象。2026年10月13日のリリースに修正は入っていない）
認証・認可□ ログインIDにメールアドレス・社員番号など、外部から推測・入手できる値を使っている
システム構成□ プリザンターのログイン画面がインターネットから直接到達できる
運用・監視□ 国内製品の脆弱性情報を、海外の脅威情報と別の優先度で扱っている
