INC-2026-0680Arista VCO にゼロデイ悪用

Arista の VeloCloud Orchestrator（オンプレミス版）に悪用中のゼロデイ—— 最下位のテナント権限「Enterprise Read Only」でログインできれば SQL インジェクションで superuser operator になりすませる（CVE-2026-114625・CVSS v3.1 9.9）

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）未知の脆弱性の悪用設計・実装上の不備
初報: 2026年10月22日（Arista のセキュリティアドバイザリ 0199 の公開日） 最終更新: 2026年10月24日（CISA KEV への収載〈2026年10月23日〉と是正期限2026年10月26日を反映）

Arista Networks は2026年10月22日、SD-WAN の集中管理基盤 VeloCloud Orchestrator（VCO）のオンプレミス版に、 既に悪用されているゼロデイ脆弱性があることを公表した（出典1）。 CVE-2026-114625、CWE-89（SQL インジェクション）、CVSS v3.1 で 9.9、 CVSS v4.0 で 9.4。 攻撃に必要な権限は、組み込みテナントロールの最下位にあたる 「Enterprise Read Only」で足りる。 認証済みであれば誰でもオペレーター権限を取得し、 ローカルの「superuser operator」になりすませる—— 本来は内部用途に限られ、リモートから到達することを想定していない機能にまで届く。 Arista は攻撃中に観測された2つの送信元 IP アドレス （74[.]82.197.86 と 38[.]54.50.151）の遮断を求めている。 影響を受けるのは 5.2.3.18 未満、6.1.3.10 未満、6.4.2.12 未満のオンプレミス版で、 ホスト型（Dedicated を含む）は既にパッチ適用済みである。 被害組織・被害件数は公表されていない。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表されているのは、脆弱性の性質と悪用の事実、観測された送信元 IP までである。** ①認証済みであれば最下位の読み取り専用ロールでも成立する、 ②SQL インジェクション（CWE-89）により superuser operator になりすませる、 ③内部用途に限られリモートから到達することを想定していない機能に届く、 ④VCO ホストに影響が及びうる——以上である（出典1）。 **悪用の開始時期、被害組織、攻撃者、起点となるエンドポイントは いずれも公表されていない**〈未確定〉。

    根拠: 「攻撃に必要な最小権限は Enterprise Read Only（組み込みテナントロールの最下位）」 （出典1。原文英語）。 「低い権限、VCO ウェブインタフェースへのアクセス、 有効な認証済みセッションを持つ攻撃者」（出典2。原文英語）。

    根拠: 「影響を受けるシステムでは、認証済みの任意のユーザーがオペレーター権限を取得し、 ローカルの superuser operator ユーザーになりすますことができる」（出典1。原文英語）。 CVSS v3.1 の `S:C`（スコープ変更）がこの性質を示す。

    根拠: 「これには、内部用途にのみ意図され、リモートから到達することを 想定していない機能へのアクセスが含まれる」（出典1。原文英語）。

最下位の読み取り専用ロールが、そのまま最上位のオペレーターになる原因・手口出典 [1] [2]

Arista の説明は次のとおりである（出典1。原文英語・訳は本記録）。

VeloCloud Orchestrator（VCO）のオンプレミス版に、リモートの攻撃者が特権的な内部機能にアクセスし、VCO ホストに影響を与えうる問題がある。悪用に成功すると、オーケストレーターおよびオーケストレーターが管理するデータの機密性・完全性・可用性が損なわれる可能性がある。

影響を受けるシステムでは、認証済みの任意のユーザーがオペレーター権限を取得し、ローカルの「superuser operator」ユーザーになりすますことができる。これには、内部用途にのみ意図され、リモートから到達することを想定していない機能へのアクセスが含まれる。

技術的には CWE-89、SQL インジェクションである（出典1）。BleepingComputer は「低い権限・VCO ウェブインタフェースへのアクセス・有効な認証済みセッションを持つ攻撃者が、利用者の操作を必要としない低複雑度の SQL インジェクションによって権限を昇格できる」と説明している（出典2。原文英語）。

決定的なのは、必要な権限の低さである（出典1）。攻撃に必要な最小権限は「Enterprise Read Only」——組み込みテナントロールの最下位、読み取り専用のアカウントである。

ここが本件の構造の核心である（本記録の評価）。VCO はマルチテナントの管理基盤であり、テナント（顧客企業）の担当者に読み取り専用アカウントを配るのはごく普通の運用である。監視画面だけ見せる、レポートだけ出させる—— 権限を絞ったつもりで配ったアカウントが、そのままオーケストレーター全体の最上位権限への入口になる。

CVSS v3.1 のベクタに S:C（スコープ変更）が付いているのは、この性質を表している（出典1）。脆弱な部品の権限境界を越えて影響が及ぶ。1テナントの読み取り専用アカウントから、オーケストレーターが管理する全体へ届く。

Arista は悪用を認め、送信元 IP の遮断とログの保全を求めている対策・注意喚起出典 [1] [2]

アドバイザリは本脆弱性を「既に実際に悪用されている」と明記している（出典1。原文英語）。ベンダー自身が検出した悪用であり、公表と同時に修正版が提供されている。

観測された送信元 IP アドレス（出典1・2）

  • 74[.]82.197.86
  • 38[.]54.50.151

これらは攻撃中に観測されたものとして遮断が求められている。本記録はこの2件の悪性を独自に検証していない（本記録の確認）。また、観測された送信元であって攻撃インフラの全体ではない（本記録の評価）。遮断は有効な初動だが、これで塞がったとみなすべきではない。

ログの確認観点も具体的に示されている（出典1）。VCO のウェブアクセスログについて、通常と異なる URL 風のパス要素、エンコードされた文字、ローカルまたは内部サービスへの参照、高頻度のリクエストを探すよう求めている。

侵害が疑われる場合は、是正の前にログを保全する（出典1。原文英語）。

侵害が疑われる場合、運用上可能な範囲で、是正を行う前にVCO のウェブアクセスログ、バックエンドのアプリケーションログ、システムログ、データベースログ、および関連するファイルシステムのタイムスタンプを保全すること。

「是正の前に保全」という順序が明示されている点は実務上重要である（本記録の評価）。パッチ適用や再起動でログが失われたり、タイムスタンプが上書きされたりすると、侵害の有無と範囲を後から判定できなくなる。

それでも日本の組織にとって意味があるのは、2点です（本記録の評価）。

第一に、悪用の確認がベンダー1社の記載から当局の判断に移りました。 10月22日の時点で「悪用されている」と述べていたのは Arista だけでした（出典1）。KEV は、CISA が悪用の証拠を得たと判断した脆弱性だけを載せる一覧です ——社内で「ベンダーの言い分だけでは止められない」と言われる場面で、判断の後押しになります。

第二に、forensicTriage: Yes が付いています（出典4）。これは「直す前に、証跡を取れ」という趣旨の指定です（本記録の整理）。Arista のアドバイザリも、是正の前にウェブアクセスログ・アプリケーションログ・システムログ・データベースログを保全するよう求めています（出典1）。順序を逆にすると、侵害を受けていた場合に「やられていたかどうか」が永久に分からなくなります（本記録の評価）。

なお、Arista のアドバイザリは本記録の確認時点でも Revision 1.0 のままで、KEV 収載に触れていません（出典1。本記録の確認）——ベンダーのページだけを見ていると、この変化は見えません。

ホスト型は先に直り、オンプレミスは利用者が直す——同じ製品で時間差が生まれる評価・解釈出典 [1] [2]

本記録の評価である。

アドバイザリは、ホスト型（Dedicated を含む）VCO について「既にパッチが適用されている」と述べている（出典1）。BleepingComputer も、5.2.3.18 以降・6.1.3.10 以降・6.4.2.12 以降を実行しているホスト型配備は対応済みだと伝えている（出典2）。

つまり、同じ脆弱性に対して、配備形態で露出時間が大きく変わる（本記録の評価）。ホスト型を使っている組織は、公表を読んだ時点で既に守られている。オンプレミス版を使っている組織は、これから計画して、検証して、適用することになる。

悪用が既に起きている状況では、この時間差が決定的になる（本記録の評価）。公表は攻撃者にとっても情報であり、公表後は「まだ直していない環境」を探す動きが増えるのが通例である。オンプレミス版の運用者にとって、本件は「計画的に適用する更新」ではなく「今夜のうちに塞ぐ対象」に近い。

緩和策の筆頭が「ウェブインタフェースへのアクセスを信頼できる管理ネットワークに限定する」である理由も、ここにある（本記録の評価）。パッチ適用に時間がかかるなら、先に到達経路を絞るほうが速い。 VCO の管理画面がインターネットから到達できる状態にあるなら、それ自体を先に是正する——認証済みユーザーが前提の脆弱性であっても、到達できる範囲が狭いほど、認証情報を持つ攻撃者の母数も減る。

もう一点、本件は「管理基盤そのものが標的になる」傾向の一例である（本記録の評価）。VCO は SD-WAN とエッジ機器の設定・監視・管理を行う中央管理ポータルであり（出典2）、掌握されれば配下のネットワーク全体の設定に届きうる。 BleepingComputer は、Arista が2026年に本件を含めて4件の悪用済みゼロデイ（EOS およびオンプレミス版 VCO）を修正したと伝えている（出典2）。ネットワーク機器とその管理基盤が、継続的に狙われているという文脈のなかで読むべき事案である。

読み取り専用アカウントの棚卸しが、そのまま被害想定の作業になる再発防止出典 [1]

本記録の評価である。

本件で「攻撃に使われうるアカウント」は、普段リスクが低いと見なされているものである（出典1。評価は本記録）。Enterprise Read Only——読み取り専用、組み込みロールの最下位。

VCO を運用する組織が最初にやるべきは、パッチ適用と並行した、このロールの棚卸しである（本記録の評価）。

  • 誰に配っているか。 テナント側の担当者、監視を委託している事業者、過去のプロジェクトで作って消し忘れたアカウント。
  • 外部に配っているものはあるか。 顧客企業や保守ベンダーに渡した読み取り専用アカウントは、自社の管理外のどこかに保存されている。
  • パスワードは使い回されていないか。 読み取り専用だからと簡易なパスワードを設定していないか。
  • 多要素認証はかかっているか。 権限が低いからと除外していないか。

この棚卸しの結果が、そのまま「侵害されたとしたら誰の経路か」の候補リストになる（本記録の評価）。Arista が求めているログの確認——異常なパス、エンコードされた文字、高頻度のリクエスト——と突き合わせるとき、どのアカウントのセッションから来ているかが見られる。

あわせて、Arista が挙げた「管理者の最近の操作に不審な変更が無いか」の確認も具体化できる（出典1）。superuser operator になりすませる脆弱性である以上、確認すべきは「オペレーター権限で行われた設定変更」である。ポリシーの変更、エッジ機器の設定配信、ユーザーの追加——身に覚えのないものが無いかを、悪用の時期が不明である以上さかのぼれる限りさかのぼって見る必要がある（本記録の評価）。

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • **権限を絞ったアカウントほど、配った先の管理が緩い。それが入口になる。**
    本件の悪用に必要な最小権限は「Enterprise Read Only」—— 組み込みテナントロールの最下位である（出典1）。 **読み取り専用は「渡しても大丈夫」と判断されがちで、 多要素認証の対象外にされたり、委託先に共有されたりしやすい**（本記録の評価）。
    取るべき行動 **自社が外部（顧客・委託先・保守ベンダー）に配っている 読み取り専用アカウントの一覧を作らせる。** 各アカウントについて、多要素認証の有無・最終利用日・保管場所を確認し、 使われていないものを停止する。
  • **同じ製品でも、ホスト型と自社運用では露出時間が違う。その差を把握しておく。**
    本件ではホスト型（Dedicated 含む）VCO は Arista 側で適用済みだが、 **オンプレミス版は利用組織が適用する**（出典1）。 **悪用が既に起きている状況では、この時間差がそのままリスクになる**（本記録の評価）。
    取るべき行動 自社の重要システムについて、**「ベンダーが直すもの」と 「自社が直すもの」を台帳で区別する。** 後者には**緊急時の適用目標時間**を決めておく （「悪用中のゼロデイなら何時間以内」という形で）。
  • **ネットワークの管理基盤は、配下全体への到達点として狙われている。**
    VCO は SD-WAN とエッジ機器の設定・監視・管理を行う中央管理ポータルである（出典2）。 **BleepingComputer は、Arista が2026年に本件を含めて4件の 悪用済みゼロデイを修正したと伝えている**（出典2。本記録は一次資料で未確認）。
    取るべき行動 ネットワーク管理基盤（SD-WAN オーケストレーター、SIEM、構成管理、 監視サーバ）を**「サーバ1台」ではなく「全体への到達点」として リスク評価の別枠に置く。** 到達経路の制限と、管理者操作の記録を他のサーバより厚くする。
  • **「是正の前にログを保全する」を、手順として事前に決めておく。**
    Arista は、侵害が疑われる場合は**是正を行う前に**各種ログと ファイルシステムのタイムスタンプを保全するよう求めている（出典1）。 **急いでパッチを当てると、侵害の有無を判定する材料が消えうる**（本記録の評価）。
    取るべき行動 緊急パッチ適用の手順書に、**「適用前のログ退避」を必須ステップとして 追記する。** どのログを、どこへ、誰が退避するかまで書く。 急いでいるときに判断させない。
セキュリティ技術者への示唆
  • **まず該当バージョンを確認し、同時に管理画面の到達範囲を絞る。**
    影響を受けるのは 5.2.3.18 未満、6.1.3.10 未満、6.4.2.12 未満の オンプレミス版である（出典1）。 **更新に時間がかかるなら、到達経路を絞るほうが速い**（本記録の評価）。
    取るべき行動 VCO のバージョンを確認する。該当するなら、 **①ウェブインタフェースへのアクセスを管理ネットワークに限定する、 ②観測された送信元 IP（`74[.]82.197.86`・`38[.]54.50.151`）を遮断する** を先に行い、その上で修正版へ更新する（出典1）。 **サポート終了版なら TAC に連絡する。**
  • **探すログの特徴が具体的に示されている。そのまま検索条件にできる。**
    Arista は VCO のウェブアクセスログについて、 **通常と異なる URL 風のパス要素、エンコードされた文字、 ローカルまたは内部サービスへの参照、高頻度のリクエスト**を 探すよう求めている（出典1）。
    取るべき行動 ウェブアクセスログに対し、**URL エンコード文字（`%2e`・`%2f`・`%27` 等）を 含むリクエスト、`localhost`／`127.0.0.1`／内部ホスト名への参照、 同一セッションからの短時間の大量リクエスト**を検索する。 **悪用の開始時期が不明なので、保存している全期間を対象にする。**
  • **SQL インジェクションでも、確認すべきはホスト側の痕跡まで及ぶ。**
    Arista は緩和策として**バックドア用デーモンやウェブシェルの兆候の監視**と、 **VCO ホストからの想定外のアウトバウンド通信の監視**を挙げている（出典1）。 **アドバイザリ自身が「VCO ホストに影響を与えうる」と述べている。**
    取るべき行動 VCO ホストについて、**常駐プロセス・起動設定・ウェブ配信ディレクトリの ファイル一覧**を取得し、構築時の状態と突き合わせる。 あわせて**外向き通信を既定で遮断し、許可外の宛先への接続試行を アラートにする。**
  • **権限昇格が起きたなら、確認すべきは「オペレーター権限で行われた設定変更」である。**
    本件は superuser operator になりすませる脆弱性である（出典1）。 **昇格後の操作は正規のオペレーターの操作として記録される**（本記録の評価）。
    取るべき行動 **ポリシーの変更、エッジ機器への設定配信、ユーザー・ロールの追加や変更**について、 さかのぼれる限りの履歴を確認する。 身に覚えのない変更が無いかを、変更者ではなく**変更内容**で見る。
  • **読み取り専用アカウントを多要素認証の除外対象にしない。**
    本件の入口は Enterprise Read Only である（出典1）。 **「権限が低いから」という理由での除外が、 そのまま攻撃の前提条件を満たしてしまう**（本記録の評価）。
    取るべき行動 VCO に限らず、**管理系システムの全ロールについて 多要素認証の適用状況を確認する。** 除外しているアカウントがあれば、除外した理由を記録に残し、 残せないものは除外をやめる。
