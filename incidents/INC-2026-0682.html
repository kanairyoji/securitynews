INC-2026-0682Pillow の EPS 引数インジェクション

Python の画像ライブラリ Pillow に引数インジェクション—— **EPS を Ghostscript に渡すとき、ファイル名を絶対パスにしないまま `-f` の後ろに置いていた**ため、 `-` で始まる名前がオプションとして解釈される（CVE-2026-112900・CWE-78）。 2.6.0 から 12.3.0 までが対象で 13.0.0 で修正。 **コマンド実行まで到達するには `@` で始まる名前と、参照先ファイルの内容の両方を握る必要がある**

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備
初報: 2026年10月17日（GitHub セキュリティアドバイザリの公開日） 最終更新: 2026年10月24日（本記録の確認時点）

外部のプログラムを呼ぶとき、渡す値が「引数」になるか「オプション」になるかは、先頭の1文字で決まることがあります。

2026年10月17日、Pillow プロジェクトは GitHub セキュリティアドバイザリGHSA-w889-685w-c8fh「Argument Injection in Ghostscript call, potentially leading into RCE」を公開しました（出典1）。CVE-2026-112900 が割り当てられ、NVD には2026年10月19日に収載されています（出典2）。修正は 13.0.0 に入っており、同版は2026年10月16日にリリースされています（出典1・4）。

NVD が収載している説明は次のとおりです（出典2。原文英語）。

「Pillow は Python の画像ライブラリである。2.6.0 から 13.0.0 の手前まで、Pillow は EPS 入力に対して Ghostscript を呼び出す際の引数インジェクションに脆弱である。EpsImagePlugin.Ghostscript は、呼び出し元が制御する入力ファイル名を安全な絶対パスへ変換しないまま -f の後ろに渡すため、ハイフンで始まる名前が Ghostscript のオプションとして解釈されうる。ファイル名を制御できる攻撃者は Ghostscript の引数を注入できる。任意のコマンド実行には、具体的には先頭が @ の引数ファイル名と、追加の Ghostscript 引数を含む参照先テキストファイルの制御が必要である。報告された連鎖は、既定の -dSAFER 付きの呼び出しで再現する。この問題はバージョン 13.0.0 で修正されている」

本記録が要点と見たのは、次の3点です。

  • 成立の入口は「画像の中身」ではなく「ファイル名」。 アドバイザリは「無害な EPS ファイルで注入が成立する」と述べています（出典1）—— つまり、EPS の中身を検査しても防げません（本記録の整理）。狙われるのは、アップロードされた名前をそのまま保存名に使う作りです（出典1）。
  • コマンド実行までの条件は、見出しより重い。 引数の注入だけならファイル名を握れば成立しますが、任意コマンドの実行には @ で始まる名前に加えて、その参照先テキストファイルの中身まで握る必要があります（出典1・2）—— The Hacker News の見出しは「Critical Flaw ... Allows Code Execution via a Crafted Image」ですが、実際に要るのは細工した画像ではなく細工したファイル名です（出典3。本記録の整理）〈齟齬1〉。
  • -dSAFER は効かない。 報告された連鎖は、Ghostscript の既定の安全モード -dSAFER 付きで再現します（出典1・2）—— 「安全モードで呼んでいるから大丈夫」という前提が通りません（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。
  1. 1. 偵察
    **アプリケーションが EPS を受け付けるか、 アップロードしたファイルの名前がどう保存されるかを確かめる** （出典1 の前提条件から整理した。本記録の整理）。 **GHSA は成立の前提を「`Image.open()` に渡るファイル名を 攻撃者が左右できること」としている**（出典1）。 **具体的な探索手法は公表されていない**〈未確定2〉。
  2. 2. 初期侵入
    **`-` で始まるファイル名、あるいは `@` で始まるファイル名を アプリケーションに保存させ、それを `Image.open()` に渡させる**（出典1・2）。 **Pillow は EPS と判断すると Ghostscript を起動し、 その名前を `-f` の後ろに渡す**（出典2）。 **名前が `-` で始まっていれば Ghostscript はそれをオプションとして読む**（出典2）。 **EPS の中身は無害でよい**（出典1）—— **「a benign EPS file is enough to trigger the injection」 （無害な EPS ファイルで注入は成立する／原文英語）。**
  3. 3. 実行
    **任意コマンドの実行へ到達するには、 先頭が `@` のファイル名に加えて、 その参照先テキストファイル（追加の Ghostscript 引数が書かれたもの）の 中身を攻撃者が制御している必要がある**（出典1・2）。 **報告された連鎖は、既定の `-dSAFER` 付きの呼び出しで再現する**（出典1・2）—— **Ghostscript の安全モードは、起動時の引数には効かない**（本記録の整理）。 **引数だけの注入にとどまる場合でも、 Ghostscript の挙動（出力先・読み込み先など）を変えられる**（本記録の評価）。
  4. 4. 影響（暗号化・破壊・改ざん）
    **CVSS v4.0 の評価では、機密性・完全性・可用性への影響がいずれも 「高」（`VC:H/VI:H/VA:H`）である**（出典2）。 **サーバー上で、アプリケーションの実行権限でOSコマンドが実行されうる** （出典1・2・3）。 **実際の被害事例は公表されていない**〈未確定1〉。

守るべき値は画像の中身ではなくファイル名だった——`-` で始まればオプションになる原因・手口

Pillow は EPS（Encapsulated PostScript）を開くとき、自分で描画せずGhostscript という別のプログラムを呼び出します（出典1・2・3）。そのとき、開くファイルの名前を -f オプションの後ろに渡します（出典2）。

問題は、この名前を絶対パスへ変換していなかったことです（出典2）。

「EpsImagePlugin.Ghostscript passes a caller-controlled input filename after -f without converting it to a safe absolute path, so a name beginning with a hyphen can be interpreted as a Ghostscript option」

（EpsImagePlugin.Ghostscript は、呼び出し元が制御する入力ファイル名を安全な絶対パスへ変換しないまま -f の後ろに渡すため、ハイフンで始まる名前が Ghostscript のオプションとして解釈されうる／原文英語）（出典2）

ここで起きていることを分解すると、次のようになります（本記録の整理）。

  • Ghostscript は、コマンドラインで - で始まる語をオプションとして読む
  • ファイル名が - で始まっていれば、それはファイル名ではなくオプションになる
  • Pillow は名前を絶対パスにしていなかったので、- が先頭のまま渡っていた

修正はこの1点です（出典4）。

「Transform EPS file name to an absolute path before invoking Ghostscript」

（Ghostscript を呼ぶ前に EPS のファイル名を絶対パスへ変換する／原文英語）

絶対パスにすれば必ず / で始まるので、オプションには見えなくなります（本記録の整理）。

CWE は CWE-78（OSコマンドで使われる特殊要素の不適切な無害化）です（出典2）。

重要なのは、EPS ファイルの中身は関係しないことです（出典1）。GHSA は「無害な EPS ファイルで注入が成立するため、この欠陥は悪意ある PostScript の内容に依存しない」と述べています（出典1。原文英語）—— したがって、EPS の中身を検査するだけでは防げません（本記録の評価）。

コマンド実行までは2段ある——名前だけでは引数注入、実行には参照先ファイルも要る被害規模・影響範囲

「コード実行」という見出しだけを読むと、画像を1つアップロードすればサーバーが乗っ取られるように見えます。 一次公表はもう少し細かく書いています（出典1・2）。

到達点 攻撃者が握る必要があるもの
Ghostscript への引数注入 ファイル名だけ
任意コマンドの実行 ①先頭が @ のファイル名 ＋ ②その参照先テキストファイルの中身

NVD の記述はこうです（出典2。原文英語）。

「Arbitrary command execution specifically requires a leading @ argument-file filename and control of the referenced text file containing additional Ghostscript arguments」

（任意のコマンド実行には、具体的には先頭が @ の引数ファイル名と、追加の Ghostscript 引数を含む参照先テキストファイルの制御が必要である）

@ で始まる引数を渡すと、Ghostscript はその名前のファイルを開いて中身を引数として読み込みます（出典1・2 の記述に基づく整理）—— つまり攻撃者は「引数が書かれたファイル」をサーバー上のどこかに置けなければなりません。

これは実務上、次のような構成で満たされやすい条件です（本記録の評価）。

  • アップロードされた複数のファイルが、同じディレクトリに保存される
  • ファイル名を利用者の入力からそのまま、あるいは一部を引き継いで決めている
  • 保存先のパスが推測できる、または攻撃者が指定できる

GHSA が現実的な例として挙げているのは、「保存名を利用者の入力そのまま、あるいはそこから導出するファイルアップロードの受け口」です（出典1。原文英語）。

CVSS v4.0 のベクタにもこの前提が表れています（出典2）。

CVSS:4.0/AV:N/AC:L/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N（9.2）

AT:P（Attack Requirements: Present）が付いている点が本件の要です（本記録の整理）—— 「攻撃者の制御下にない前提条件が要る」という評価であり、それでも 9.2 と高く出ています。

なお本記録は、The Hacker News の見出し「Allows Code Execution via a Crafted Image」（細工した画像によるコード実行）が誤解を招きうると評価します（出典3。本記録の評価）〈齟齬1〉—— 要るのは細工した画像ではなく、細工したファイル名です。

`-dSAFER` は防波堤にならない——「安全モードで呼んでいる」は根拠にならない評価・解釈

Ghostscript には -dSAFER という安全モードがあります。 PostScript の中からファイル操作やコマンド実行を行わせないための仕組みで、Pillow も既定でこれを付けて呼び出しています（出典1・2 の記述に基づく整理）。

本件は、その -dSAFER 付きで再現します（出典1・2）。

「the reported chain reproduces with the default -dSAFER invocation」

（報告された連鎖は、既定の -dSAFER 付きの呼び出しで再現する／原文英語）（出典2）

理由は、攻撃の入口が PostScript の中身ではなくコマンドラインだからです（本記録の整理）。-dSAFER が制限するのは「PostScript プログラムが何をできるか」であって、「Ghostscript 自身がどんなオプションで起動されたか」ではありません。

ここから引ける一般則は、本記録の評価として次のようになります。

  • サンドボックス・安全モードは、想定された入口に対してしか効かない
  • 外部プログラムに渡す値のうち、「中身」と「起動時の引数」は別の経路である
  • 前者を厳しく検査していても、後者が素通りなら意味がない

過去の Pillow 経由の Ghostscript 問題（CVE-2017-8291 など）はPostScript の中身を使うものでしたが、本件は性質が違います（本記録の評価）—— ただし本記録は過去事例の一次資料を確認していません〈齟齬4〉。

13.0.0 のリリースノートに CVE 番号が無い——「更新済み」の判定がずれる再発防止

一方で、本記録が 13.0.0 のリリースノートを確認したところ、CVE 番号の記載がありませんでした（出典4。本記録の確認）〈齟齬2〉。該当する項目はこう書かれています。

  • 「Do not allow Ghostscript to render beyond decompression bomb limit」

後者は別の脆弱性（GHSA-vx6w-vv9f-6gvg、深刻度 Low）に対応するものです（本記録の整理）—— 本記録はこちらの一次資料を直接確認していません〈齟齬4〉。

実務上の影響は、更新の判定にあります（本記録の評価）。

  • リリースノートだけを見ている運用では、13.0.0 がセキュリティ修正を含むと分からない
  • 一方、13.0.0 はメジャーバージョンの更新であり、互換性の確認が要るため後回しにされやすい

CISO・経営層への示唆
  • **「ライブラリの脆弱性」ではなく「自社のアップロード設計の脆弱性」として扱う。**
    **成立の前提は、`Image.open()` に渡るファイル名を 攻撃者が左右できることである**（出典1）。 **GHSA は現実的な例として「保存名を利用者の入力そのまま、 あるいはそこから導出するファイルアップロードの受け口」を挙げている**（出典1）—— **つまり、同じ Pillow を使っていても、 保存名をサーバー側で生成している組織は該当しない**（本記録の評価）。 **該当するかどうかはライブラリの版だけでは決まらない。**
    取るべき行動 **ファイルアップロードを受け付けるシステムの一覧に対して、 「保存名をどう決めているか」を書き出させる。** **利用者の入力を保存名に使っているものを、 Pillow の版とは別の軸で洗い出し、優先度を付ける。**
  • **リリースノートに CVE 番号が無い修正は、脆弱性管理の網から落ちる。**
    **本記録が Pillow 13.0.0 のリリースノートを確認したところ、 CVE-2026-112900 という番号の記載は無く、 「Transform EPS file name to an absolute path before invoking Ghostscript」という技術的な説明だけだった**（出典4。本記録の確認）〈齟齬2〉。 **修正は10月16日、アドバイザリは10月17日、 NVD 収載は10月19日である**（出典1・2・4）—— **更新する動機がリリースノートからは読み取れない期間があった。**
    取るべき行動 **依存ライブラリの脆弱性検知を、リリースノートの購読ではなく アドバイザリデータベース（GitHub Advisory / OSV / NVD）への 自動照合で行う運用に揃える。** **SCA ツールを入れているなら、 GHSA を取り込んでいるかどうかを確認する。**
  • **OS パッケージで入れたライブラリは、上流が直っても自社は直っていない。**
    **本記録が2026年10月24日に Debian のセキュリティトラッカーを確認した時点で、 bookworm・trixie・forky はいずれも vulnerable のままだった** （出典5。本記録の確認）。 **上流（Pillow 13.0.0）のリリースから8日が経っている**（本記録の算出）。 **「最新のセキュリティ更新を当てている」運用は、 ディストリビューションがバックポートするまで待つことになる**（本記録の評価）。
    取るべき行動 **重要な依存について、導入経路（pip / OS パッケージ / コンテナ基礎イメージ）を 資産台帳に記録する。** **OS パッケージ経由のものは、上流の修正日とディストリビューションの 反映日を別々に追う。反映が遅い場合の回避策を事前に決めておく。**
  • **深刻度のラベルが資料によって割れている。片方だけを見て判断しない。**
    **GHSA のページ表示は Moderate だが、 NVD が収載する CVSS v4.0（GitHub 提供・Secondary）は 9.2 Critical である** （出典1・2。本記録の確認）〈齟齬5〉。 **さらに NVD 自身の一次評点はまだ付いておらず、 ステータスは「解析中」である**（出典2）。 **報道の見出しは「Critical Flaw」である**（出典3）。 **どのラベルを採るかで、社内の対応優先度が変わってしまう**（本記録の評価）。
    取るべき行動 **脆弱性の優先度を評点のラベルだけで決めず、 「自社の構成で成立条件を満たすか」で判定する手順を併用する。** **本件なら「アップロード名を保存名に使っているか」が判定軸になる。**
セキュリティ技術者への示唆
  • **外部プログラムを呼ぶとき、値が「引数」か「オプション」かは先頭文字で決まる。**
    **本件の原因は、ファイル名を絶対パスへ変換しないまま `-f` の後ろに渡していたことである**（出典2）。 **`-` で始まる名前は、Ghostscript にとってオプションである**（出典1・2）。 **修正はこの1点で、絶対パスにすれば必ず `/` で始まるため オプションには見えなくなる**（出典4。本記録の整理）。 **同じ構図は、`subprocess` で外部コマンドを呼ぶあらゆる箇所に存在する** （本記録の評価）。
    取るべき行動 **自社コードで外部コマンドにパスを渡している箇所を `subprocess`・`os.system`・`Popen` などで検索し、 渡す前に絶対パス化（`os.path.abspath`）しているかを確認する。** **あるいは、引数の終わりを示す `--` を使えるコマンドなら明示する。** **シェル経由（`shell=True`）の有無とは別の問題である点に注意する。**
  • **サンドボックス（`-dSAFER`）は、想定された入口にしか効かない。**
    **報告された連鎖は、Ghostscript の既定の安全モード `-dSAFER` 付きで再現する**（出典1・2）。 **`-dSAFER` が制限するのは PostScript プログラムの挙動であって、 Ghostscript 自身がどんなオプションで起動されたかではない**（本記録の整理）。 **「安全モードで呼んでいるから大丈夫」という前提が通らない。**
    取るべき行動 **外部プログラムをサンドボックス付きで呼んでいる箇所について、 「サンドボックスが制限しているのは何か」をドキュメントで確認する。** **入力の中身に対する制限と、起動時の引数に対する制限は 別物として扱う。**
  • **EPS の中身を検査しても防げない。無害な EPS で成立する。**
    **GHSA は「無害な EPS ファイルで注入が成立するため、 この欠陥は悪意ある PostScript の内容に依存しない」としている** （出典1。原文英語）。 **マジックバイト検査・PostScript の構文検査・ アンチウイルスでのスキャンは、いずれも本件には効かない**（本記録の評価）。
    取るべき行動 **アップロードされたファイルの検査項目に、 「中身」だけでなく「名前」が含まれているかを確認する。** **最も確実なのは名前を使わないこと—— 保存名をサーバー側で生成し、元の名前は表示用のメタデータとしてのみ保持する。**
  • **コマンド実行の条件は「名前」＋「参照先ファイルの中身」の2つ。保存先の設計が効く。**
    **任意コマンドの実行には、先頭が `@` の引数ファイル名に加えて、 追加の Ghostscript 引数を含む参照先テキストファイルの制御が要る** （出典1・2）。 **複数のアップロードが同じディレクトリに溜まり、 そのパスが推測できる作りほど、2つ目の条件を満たしやすい**（本記録の評価）。
    取るべき行動 **アップロードされたファイルの保存先を、 利用者ごと・リクエストごとに分離し、 他の利用者のファイルを相対パスで指せない構成にする。** **画像処理が読み出すディレクトリと、 任意のファイルが置かれるディレクトリを分ける。**
