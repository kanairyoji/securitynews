KSMBD の脆弱性は何か——ディスパッチの取り違えで SMB1 が SMB2 として読まれる原因・手口

本記録が ZDI-CAN-33774 の報告本文で確認した技術的な説明は、次のとおりです（出典1。本記録の確認）。

  • 接続ごとのディスパッチハンドラが、キューへの投入時に選ばれ、キューからの取り出し時に使われる
  • このずれにより、SMB1 のバッファが SMB2 のヘッダとして解析されうる
  • 結果として、範囲外読み出しのメモリが攻撃者に漏れうる
  • SMB2 の set-info 経路を介した範囲外書き込みの可能性にも触れている
  • 成立には、レースに勝つことと、ゲストが到達できる共有が要る

評点とベクタは次のとおりです（出典1）。

CVSS 9.0 ／ AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H

記号 値 意味
AV:N Network ネットワーク越しに届く
AC:H High レースに勝つ必要がある
PR:N None 権限不要
UI:N None 利用者の操作不要
S:C Changed 影響が部品の外へ出る

AC:H が付いているのはレースコンディションだからです（本記録の整理）—— 一発で決まる攻撃ではなく、タイミングを当てる必要があります。 一方で、認証は要りません（PR:N）。

報道の間で、成立条件の書き方に幅があります〈齟齬3〉。

  • The Hacker News — 「ネットワーク認証の前に発動させられる」（出典6）
  • ZDI の報告本文 — 「レースに勝つことと、ゲストが到達できる共有が要る」（出典1）

本記録は一次資料（出典1）の記述を採ります（本記録の明示）—— 認証は不要だが、ゲストで到達できる共有が存在する必要がある、というのが報告本文の記述です。

もう1件の KSMBD の脆弱性 ZDI-CAN-33549 については、本記録は報告本文を確認していません〈齟齬3〉。報道によれば、SMB Direct における整数アンダーフロー由来の遠隔コード実行で、CVSS 9.0、SMB Direct トランスポートとRDMA 対応ネットワークを要するとされています（出典5・6）。

  1. 私有でないページ由来のパケットデータに SKBFL_SHARED_FRAG の印を付ける
  2. ESP は復号の前にその印を確認し、印があれば私有の複製を作ってから復号する

skb_zerocopy() は、同じページを新しいバッファへ渡しますが、この印を引き継ぎません（出典7・8）。印が無いので防御は発動せず、ESP はその場で復号し、攻撃者が読むだけのファイルのページキャッシュに書き込みが及びます（出典7）。

結果として、非特権の利用者が「読むことしかできないファイルのメモリ上の内容を書き換えられる」（出典9。原文英語）。

Sysdig はこれを「修正をすり抜けた7番目の経路」と数えています（出典8）—— 先行する6つの内訳は本記録では確認していません（本記録の明示）。

原因となった変更は、コミット af2806f8f90a にあり、カーネル 3.14 で導入されたとされます（出典7）。2014年の実装です（本記録の整理）。

実務上、重いのは次の一点です（本記録の評価）—— AlmaLinux 8〜10 は Dirty Frag の修正を適用した状態でもroot を取られています（出典7）。「先の脆弱性に対応したから大丈夫」が成り立ちません。

本記録が本件を「手順の事故」として記録してきたことと、これは別の話ではありません（本記録の整理）—— 印を引き継ぐかどうかという一行の見落としが、公開リストに PoC 付きで置かれたことで、修正が間に合う前に実証されました。

緩和策はどれも未検証で、Ubuntu の既定の防御は迂回された対策・注意喚起出典 [7] [8]

修正が無いあいだ、何をするか。挙げられている候補は3つですが、いずれにも留保が付いています（出典7・8）。

①非特権ユーザ名前空間の無効化（user.max_user_namespaces = 0、Debian では kernel.unprivileged_userns_clone=0）— 公開 PoC を止める見込みとされますが、TuxCare は「社内では PoC に対して未検証である」と明記しています（出典7。原文英語）。加えて、rootless コンテナはこの機能に依存するため、必要のないホストに限る必要があります（出典8）。

②nlmon・act_pedit の modprobe 遮断 — これも未検証で、PoC の経路がすべて塞がるとは限らないとされています（出典7）。

③Ubuntu の apparmor_restrict_unprivileged_userns — 既定で有効ですが、PoC がこれを迂回しました（出典7）—— TuxCare は「緩和策に数えるべきでない」としています。

ここが本節の要点です（本記録の評価）—— 既定で入っている防御があることは、その防御が今回の攻撃に効くことを意味しません。 Ubuntu 24.04・26.04 の2構成は、その防御が有効な状態で root を取られました（出典7）。

KSMBD の2件については、条件を外す手が明確です（出典8）。

  • 使っていないホストでは ksmbd モジュールをアンロードし、読み込みを遮断する
  • 残す必要があるなら、445/tcp を信頼できるネットワークに限定する

VMware ゲストでは、vmwgfx（ZDI-CAN-34068・CVSS 8.8）のパッチを待つよう勧められています（出典8）—— 本記録の確認時点でパッチはありません（出典8）。

ライブパッチという道もありますが、揃っていません（出典7）。

    取るべき行動 **ksmbd を読み込んでいるホストを `lsmod | grep ksmbd` で洗い出し、 不要なホストではアンロードと読み込み遮断を行う。 残すホストでは 445/tcp を信頼できるネットワークに限定する。** **ZDI-CAN-33367 については、修正済みカーネルが出るまでのあいだ、 非特権ユーザ名前空間を必要としないホストでのみ `user.max_user_namespaces=0`（Debian では `kernel.unprivileged_userns_clone=0`）を検討する**—— **ただし公開 PoC に対する有効性は未検証であり、 rootless コンテナを壊すため、ステージングで確認してから入れる**（出典7・8）。 **VMware ゲストでは vmwgfx のパッチを待つ対象として台帳に載せる。**
  • **「先の脆弱性に対応済み」を安全の根拠にしない。修正が届かない経路が残る。**
    **ZDI-CAN-33367 は、Dirty Frag（CVE-2026-43284）の修正が 取りこぼした経路である**（出典7・8）—— **修正は共有ページに印を付けて復号前に複製する仕組みだが、 `skb_zerocopy()` はその印を引き継がない**（出典7）。 **結果として、AlmaLinux 8〜10 は Dirty Frag の修正を含んだ状態でも root を取られている**（出典7）。 **原因の実装はコミット `af2806f8f90a`（カーネル 3.14・2014年）に遡る**（出典7）。
    取るべき行動 **過去に対応した重い脆弱性について、 「同じ原因で別の経路が残っていないか」を上流の議論で追う対象に入れる。** **具体的には、対応済みの CVE を台帳から消さず、 同一原因の後続報告（same root cause / incomplete fix）が出たときに 再評価できる形で残す。** **本件のように CVE 番号が付かない段階の報告は自動検査に現れないため、 人が読む情報源（カーネルの ML・ディストリの security feed）を 最低1つ確保する。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
