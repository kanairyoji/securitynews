INC-2026-0689Popcorn Time 分派の更新機構でRCE

放棄された動画視聴アプリ **Time4Popcorn**（Popcorn Time の分派）の自動更新機構に、 **更新をHTTPで取得し、実行ファイルの署名を検証せずに最高権限で実行する不備** （**CVE-2026-30612**）があった。 **更新サーバーのドメイン `popcorntimeupd.xyz` は失効して誰でも登録できる状態にあり**、 これを取得した者は **Windows では SYSTEM、macOS では root として 任意のコードを実行できた**。 オランダの Eye Security が調査のためにこのドメインを登録したところ、 **6か月間で380万を超える端末識別子（hid）からの接続を観測した**—— 同社の見直し後の推定で **Windows 約250万〜300万台・macOS 約25万〜35万台**である。 **接続元には一般の ISP だけでなく、企業・政府・軍のネットワークが含まれていた**。 **利用者はほぼ誰もアプリを使っておらず、インストールしたまま忘れられていた**とみられる。 同社は **2025年11月から2026年3月にかけて、この脆弱な更新機構そのものを使って 「更新機構を停止・無効化する」コードを配信する是正作戦（Operation IXIM）を実施した**。 **配信したコードは端末情報の収集もファイルの削除も行っていない**。 **200万件を超える更新を配信し、2026年3月1日時点で更新要求は98%減少した**。 **同社は登録した15のドメインを2026年3月下旬に The Shadowserver Foundation へ移管した**。 **ただし危険は消えていない**—— **Android は更新に利用者の操作が必要で遠隔から無効化できず、 アプリ自体が2014年当時の Chrome エンジンをサンドボックス無効で同梱している**。 **同社の結論は「アンインストールすること」である。**

放棄されたソフトウェアは、消えるのではなく「乗っ取り可能な設備」として残る。本件がそれを数字で示した。

Popcorn Time は、Netflix 風の画面で BitTorrent の動画を再生するアプリとして広まり、法的な理由で開発が止まった。その分派である Time4Popcorn は「Popcorn Time」の名で配布され、数百万台に入ったまま放置された。問題は本体ではなく自動更新機構にある。更新情報を HTTP で取り、示された実行ファイルを署名検証なしに最高権限で実行する（CVE-2026-30612）。そして更新サーバーのドメインは失効していた。

オランダの Eye Security は調査の過程でこのドメイン popcorntimeupd.xyz を登録した。流れ込んできたのは 毎秒約50件の更新要求で、6か月で380万を超える端末識別子だった。見直し後の推定は Windows 約250万〜300万台・macOS 約25万〜35万台。接続元には企業・政府・軍のネットワークが含まれ、しかもほとんどの利用者はアプリを使っていなかった——入れたまま忘れられた常駐プロセスが、最高権限で未署名のコードを待ち続けていた。

ここで問われるのは「誰がドメインを先に取るか」だけである（本記録の評価）。同社は 2025年11月から2026年3月にかけて、この脆弱な更新機構を使って更新機構自身を停止・無効化するコードを配信した（Operation IXIM）。端末情報の収集もファイルの削除も行わず、200万件を超える更新を配信し、2026年3月1日時点で更新要求は98%減った。登録した15のドメインはThe Shadowserver Foundation へ移管された。

日本の読者にとっての論点は、自組織の端末に同じ構造のものが残っていないかである（本記録の評価）。本件の接続元には企業ネットワークが含まれていた。「使っていないから無害」は成り立たない——使っていなくても更新サービスは動き、最高権限で外部の指示を待っている。

放棄されたアプリの更新先ドメインが失効しており、取った者が最高権限を得られた原因・手口

本件の核心は脆弱性の種類ではなく、その前提が消えていたことである。

Time4Popcorn の更新機構は、暗号化されていない HTTP で更新情報を取得し、JSON で示された実行ファイルをダウンロードして実行する。コード署名の検証はない（出典1）。動く権限は、Windows では Updater.exe が NT AUTHORITY\SYSTEM、macOS では /Library/PrivilegedHelperTools/ 配下の PT.updd が root である（出典1）。

この設計は、更新サーバーが信頼できる限りは辛うじて成り立つ。その前提が消えていた。 更新サーバーのドメイン popcorntimeupd.xyz は登録が失効しており、誰でも取得できた（出典1）。

この構造には「攻撃」と呼ぶべき技術的な工程がほとんど無い（本記録の評価）〈重要〉。通信を傍受する必要も、脆弱性の実証コードを書く必要も、権限を昇格させる必要もない。ドメインの登録料を払うだけで、数百万台の最高権限プロセスが自分の指示を待つ状態になる。

権限昇格が要らない点が重要である（本記録の評価）。更新機構は設計上すでに最高権限で動いている。攻撃者がするのは権限を上げることではなく、すでに最高権限を持つプロセスに仕事を渡すことだけである。

研究者が同じ経路で「更新機構を止める更新」を配信し、要求は98%減った組織の対応

Eye Security は、この脆弱な経路を是正のために使う判断をした（出典1）。

配信した内容は、更新機構そのものの停止である。 Windows ではサービス制御マネージャ経由で「Update service」を停止し無効化、macOS では launchctl unload -w /Library/LaunchDaemons/PT.updd.plist を実行するシェルスクリプトを配信した（出典1）。

やらなかったことが明示されている（出典1・3）—— 端末情報の収集も遠隔測定も行わず、利用者のファイルを削除していない。

安全策も段階的である（出典1）。初期はすでに観測した hid 値にのみ、1識別子につき1回だけ配信し、可能な場合は HTTPS へ誘導した（数週間後に緩和）。事前に広範な試験と小規模な先行配信を行い、対象を細かく絞る仕組みを用意していた。

結果は次のとおりである（出典1・3）。2025年12月までに100万台を超える端末に到達し、数週間で要求は約90%減少。2026年3月1日には1日約5,000件まで減り、98%の減少となった。累計の配信は200万件を超える。その後、登録した15のドメインを The Shadowserver Foundation へ移管した。

ただし「98%減った」が意味するのは、要求が止まったことだけである（本記録の評価）〈重要〉。更新機構が無効化されただけで、アプリ本体は端末に残っている。

善意の配信は11のベンダーにマルウェアと判定され、回避のためにコードを書き換えている評価・解釈

本記録がこの一節を独立させるのは、ここに防御側の本質的な難題があるためである（本記録の明示）。

是正コードが VirusTotal に提出された後、約1週間で11のベンダーがこれをマルウェアと判定した（出典1）。判定の理由として挙げられていたのは「Windows のサービスを無効化する」ことである（出典1）。

同社は、誤検知の申告が処理されるまで数週間かかると判断し、シグネチャを回避するようコードを改変した。最終版の検知は1ベンダーのみとなった（出典1）。

判定は誤っていなかった（本記録の評価）〈重要〉。「最高権限のプロセスが、HTTP で取得した未署名の実行ファイルを走らせ、それがサービスを無効化する」——これは挙動として攻撃と区別できない。区別できるのは意図だけであり、意図は実行ファイルに書かれていない。

ここから2つのことが言える（本記録の評価）。①端末側の検知規則は機能していた。 本件で実証されたのは、この挙動が検知しうるということである。②善意の是正は、検知回避と同じ技術を使うことになる。同社はシグネチャを回避している（出典1）。第三者による是正を手段として認めるなら、「検知を回避する是正コード」が流通することも認めることになる。

本記録はこの手段の是非を判定しない（本記録の方針）。記録するのは、この手段が成立するために何が必要だったかである——失効ドメインの取得、検知の回避、法務の検討、そして修正できる提供元の不在。

更新機構を止めても危険は残る。2014年のChromeエンジンとAndroid、そして他者が持つドメイン対策・注意喚起

同社の結論は「アンインストールすること」である（出典1・2）。是正作戦が成功した後でもこの結論が変わらないのは、残る危険が3つあるためである。

①Android は是正できていない（出典1・2）。更新機構がアプリ本体に組み込まれており、個別に無効化できない。また Android では更新のインストールに利用者の操作が必要なため、遠隔からの是正配信が成立しない。

②アプリ本体が2014年当時の Chrome エンジンを、サンドボックス無効で同梱している（出典1）〈重要〉。これは更新機構の不備とは独立した危険である（本記録の整理）—— 2014年以降に公表された多数のブラウザ脆弱性が当てはまりうる。さらにアプリは放棄されたドメインから JavaScript を読み込む（出典1）。同社はそのドメインの一部を登録した上で、JavaScript から calc.exe を起動する実証コードを作成している（実際の配信は行っていない／出典1）。

③同社が登録できなかったドメインは、第三者の保有のまま残っている（出典1）〈重要〉。数も保有者も公表されていない〈未確定5〉。更新機構が止まっていない端末が、それらを参照し続けている可能性がある（本記録の評価）。

自組織での確認事項は次のとおりである（本記録の評価）。Windows では「Update service」というサービス名、macOS では /Library/LaunchDaemons/PT.updd.plist と/Library/PrivilegedHelperTools/PT.updd の存在を確認する（出典1・2）。ただし本質的な確認は個別のファイル名ではない—— 「業務端末に、提供元が消えたソフトウェアが最高権限の常駐サービスを残していないか」である。

**実行の瞬間は端末側の防御製品で観測できる**（本記録の評価）。 **実際に観測された**（出典1）〈重要〉—— **同社の是正コードは VirusTotal 提出から約1週間で11ベンダーに マルウェアと判定され、理由は「Windows のサービスを無効化する」ことだった**（出典1）。 **つまり「最高権限のプロセスが未署名の実行ファイルを落として走らせる」挙動は 検知しうる**——**本件で検知されたのが是正コードの側だったのは皮肉である**（本記録の評価）。 **同社はこの検知を回避するようコードを改変し、最終版は1ベンダーのみの検知となった**（出典1）。
侵入を防げた最高権限で動く更新プロセスが落としてきた実行ファイルの署名検証を、端末側の制御で強制する（WDAC・Gatekeeper 等）　**アプリ側に署名検証が無いなら、OS 側で止めるしかない**（本記録の評価）。 **実行の許可をアプリの実装に委ねている限り、 放棄されたアプリの実装は永久に直らない。**
検知できた「SYSTEM/root で動くサービスが外部から取得したバイナリを実行した」事象を警報として扱う　**本件では、善意の配信がこの規則で検知された**（出典1）〈重要〉—— **規則自体は機能することが実証されている**（本記録の評価）。
影響（暗号化・破壊・改ざん）公表されていない
**悪用された記録が公表されていないため、 影響段階で何が検知されたかを論じる材料がない**〈未確定3〉。
侵入を防げた業務端末における業務外ソフトウェアの実行制御（許可リスト方式）　**本件の最大の論点は、 企業・政府・軍のネットワークに 放棄された動画視聴アプリが残っていたことである**（本記録の評価）〈重要〉—— **脆弱性そのものより、そこに存在したこと自体が問題である。**
影響を限定できた業務端末の権限分離（常駐サービスが最高権限を必要としない設計の要求）　**更新のためだけに SYSTEM/root の常駐サービスを置く設計が、 被害の上限を決めている**（本記録の評価）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
機能した**結果として機能した**（本記録の評価）—— **更新要求は98%減り、報告された障害は公表資料に現れていない。** **本記録が「機能した」と評価する根拠は、 配信内容を更新機構の停止に限定し、 収集も削除も行わなかったという制約の明示である**（出典1）。 **ただし本記録はこの手段の適法性・妥当性を一般化しない**（本記録の方針）〈重要〉—— **成功したことは、同じ手段が常に正しいことを意味しない。** **また、提供元が存在する脆弱性に同じ手段を使う理由は無い。**
部分的に機能**部分的に機能した**（本記録の評価）。 **穴を塞ぐ時間は得られた**——**公表時点で要求は98%減り、 ドメインは非営利組織へ移管済みだった**（出典1）。 **一方、Android の利用者は是正の対象外であり、 その利用者が自分で対処できたのは勧告が出た2026年6月以降である**（本記録の評価）〈重要〉。 **また、2014年世代の Chrome エンジンという別の危険も、 同じ時期まで利用者には知らされていない。**
機能した**機能した**（本記録の評価）—— **シンクホール運用を継続的に行う非営利組織へ渡したことで、 同じ穴が再び誰かに取られる事態を避けている。** **ただし、同社が登録できなかったドメインは第三者保有のまま残る**（出典1）〈未確定5〉—— **この部分は解決していない。**
CISO・経営層への示唆
  • **「使っていないソフトウェア」を棚卸しの対象外にしない。本件の端末はほぼ全てが未使用だった**
    **本件の接続元には企業・政府・軍のネットワークが含まれていた**（出典1）。 **しかも、ほとんどの利用者はアプリを実際には使っていなかった**（出典3）—— **「インストールされたまま忘れられていた」**（出典3）。 **つまり危険は利用から生じていない**（本記録の評価）〈重要〉—— **危険は、最高権限で動く常駐サービスが外部の指示を待ち続けていたことから生じている。** **利用実績に基づく棚卸しは、この構造を取りこぼす**—— **使われていないものほど、誰も気づかないまま残る。**
    取るべき行動 **①端末の棚卸しを「インストール済みアプリの一覧」ではなく 「自動起動するサービスとその実行権限」の単位で行う。 SYSTEM/root で動く常駐サービスの一覧を作り、 それぞれの提供元が現在も存在するかを確認する。** **②業務端末における業務外ソフトウェアの実行制御（許可リスト方式）を適用する。 本件の論点は脆弱性より前にあり、 放棄された動画視聴アプリが業務ネットワークに存在したこと自体である。** **③退職者・機種更新・部門異動で引き継がれた端末を重点的に見る—— 「誰が入れたか分からないもの」が残りやすい。**
  • **提供元が消えたソフトウェアを「パッチ待ち」に分類せず、「削除以外に手がない既知リスク」として台帳に載せる**
    **本件の脆弱性には修正版が存在しない**（出典1・2）〈重要〉—— **プロジェクトは法的な理由で放棄され、提供元は到達できず、 更新用ドメインの管理さえ失われていた。** **通常の脆弱性管理は「提供元が修正を出す→適用する」を前提に組まれている**（本記録の評価）。 **提供元が存在しない脆弱性は、この流れに乗らないまま 「対応待ち」の欄に残り続ける**——**永久に閉じない項目になる。** **本件では、閉じるために第三者がドメインを取得して 是正コードを配信するという異例の手段が必要だった**（出典1）。
    取るべき行動 **①脆弱性管理の台帳に「提供元の生存」の列を持つ。 提供元が存在しないものは「修正待ち」から外し、 「削除・置換の計画」として別に管理する。** **②自社が使っているソフトウェアの提供元について、 更新の最終日・ドメインの登録期限・公開されている連絡先の生存を定期的に確認する。** **③委託先・子会社の端末にも同じ基準を適用する—— 本件のような放置は、管理の目が届きにくい場所から生じる。**
  • **自社が使うソフトウェアが参照する外部ドメインの「失効」を、脅威として台帳に持つ**
    **本件の決定的な条件は脆弱性の種類ではなく、 更新先ドメインの登録が失効していたことである**（出典1）〈重要〉。 **失効したドメインは誰でも取得できる**—— **本件で先に取ったのが研究者だったのは偶然である**（本記録の評価）。 **同社が登録できなかったドメインは、いまも第三者の保有のまま残っている**（出典1）〈未確定5〉。 **この構造は Popcorn Time 固有ではない**（本記録の評価）—— **更新先・ライセンス確認先・テレメトリ送信先・ JavaScript の読み込み元など、 ソフトウェアが前提にしている外部ドメインはどれも同じ危険を持つ。**
    取るべき行動 **①端末・サーバーが参照する外部ドメインを通信ログから抽出し、 登録者と有効期限を確認する。 期限が近く、かつ自社が制御できないものを危険として挙げる。** **②自社が提供するソフトウェア・サービスについて、 それが参照するドメインを棚卸しし、 廃止時にも登録を維持するか、安全に失効させる手順を定める—— 加害者の側に立たないために必要である。** **③買収・事業譲渡・サービス終了の際に、 ドメインの扱いを引き継ぎ事項として明文化する。**
  • **第三者による是正を「ありがたい話」として終わらせず、自組織が同じ立場に立つ可能性を考える**
    **本件では、研究者が他者の端末上でコードを実行した**（出典1）。 **同社は法務部門の助言を得たとしているが、助言の結論は公表されていない**（出典1）〈未確定4〉。 **本記録は適法性を判断しない**（本記録の方針）—— **他者の端末でコードを実行する行為の評価は法域によって異なる。** **CISO にとっての論点は是非ではなく、 自組織の端末が「善意の是正」の対象になりうることである**（本記録の評価）〈重要〉。 **本件の是正コードは、11のベンダーにマルウェアと判定され、 同社はシグネチャを回避するようコードを改変している**（出典1）—— **自組織の端末防御は、善意の是正と攻撃を区別できない。**
    取るべき行動 **①自組織の端末に「外部から未署名のコードが届いて実行される」経路が 残っていないかを確認する。残っているなら、 それは攻撃者にも是正者にも開かれている。** **②端末防御が「SYSTEM/root の常駐サービスが外部取得のバイナリを実行した」 事象を警報として扱う設定になっているか確認する—— 本件はこの規則が機能することを実証している。** **③供給元が消えた製品について、第三者による是正を待つのではなく、 自組織の計画として削除・置換の期限を決める。**
セキュリティ技術者への示唆
  • **更新機構の安全性は「通信の暗号化」ではなく「成果物の署名検証」で決まる**
    **本件の更新機構は HTTP を使っていたが、 決定的な欠陥は署名検証の不在である**（本記録の評価）〈重要〉。 **HTTPS に変えても、更新先ドメインを取得した者は 正規のサーバーとして振る舞えるため、攻撃は成立する**（本記録の評価）—— **TLS が守るのは経路であり、成果物の出所ではない。** **署名検証があれば、ドメインを取得しただけでは 実行させられない**（本記録の評価）。 **本件の更新機構は、JSON で示された実行ファイルを そのまま最高権限で実行していた**（出典1）。
    取るべき行動 **①自社が実装する更新機構について、 成果物の署名検証を必須にする。検証鍵はソフトウェアに同梱し、 更新サーバーから取得しない。** **②更新を適用するプロセスの権限を見直す—— 最高権限が必要なのは「配置」だけであり、 「取得」と「検証」を同じ権限で行う必要はない。** **③更新先のドメインを変更可能な設定値にしない。 設定で差し替えられるなら、それは攻撃面である。**
  • **常駐する自動更新サービスは、アプリ本体とは別の資産として扱う**
    **本件で危険だったのはアプリ本体ではなく、 別プロセスとして常駐する更新サービスである**（出典1）。 **Windows では `Updater.exe` が SYSTEM、 macOS では `PT.updd` が root として動き、 アプリを起動していなくても動作していた**（出典1）〈重要〉。 **利用者はアプリを使っていなかったが、更新サービスは動き続けていた**（出典3）。 **また、Android では更新機構がアプリ本体に組み込まれているため 個別に無効化できず、是正ができなかった**（出典1・2）—— **分離されていないことが、別の形の弱点になっている**（本記録の評価）。
    取るべき行動 **①端末上で `SYSTEM`／`root` 権限で常駐しているサービスを列挙し、 それぞれが「何のために最高権限を必要とするか」を説明できるようにする。 説明できないものを削除する。** **②Windows では `sc.exe` でサービスの一覧と起動種別を取得し、 macOS では `/Library/LaunchDaemons/` と `/Library/PrivilegedHelperTools/` の中身を確認する（出典1・2）。 本件では「Update service」「PT.updd」が該当する。** **③自社が実装する場合、更新サービスを本体から分離し、 利用者が個別に停止できる形にする—— Android の是正が成立しなかったのはこれが理由である。**
  • **古いブラウザエンジンを同梱するアプリは、同梱した時点の脆弱性をすべて抱え続ける**
    **本件のアプリは2014年当時の Chrome エンジンを、 サンドボックス無効で同梱している**（出典1）〈重要〉。 **これは更新機構の不備とは独立した危険である**（本記録の整理）—— **更新機構を止めても解消しない。** **さらにアプリは平文 HTTP でコンテンツを読み込み、 放棄されたドメインから JavaScript を読み込む**（出典1）。 **同社は該当ドメインの一部を登録した上で、 JavaScript から `calc.exe` を起動する実証コードを作っている** （実配信はしていない／出典1）—— **つまり更新機構とは別の経路でも、コード実行が成立する。**
    取るべき行動 **①自社の製品・内部ツールが同梱するブラウザエンジン・ランタイムの バージョンと更新経路を棚卸しする。 同梱したものは、同梱した時点で自社の責任になる。** **②サンドボックスを無効化している設定があれば、 その理由を文書化し、代替の分離手段を用意する。** **③アプリが読み込む外部リソース（JavaScript・設定・画像）の 取得元ドメインを列挙し、自社が制御していないものを洗い出す。**
  • **「最高権限のプロセスが外部取得のバイナリを実行した」事象は検知できる。本件がそれを実証した**
    **同社の是正コードは、VirusTotal 提出後の約1週間で 11のベンダーにマルウェアと判定された**（出典1）。 **判定の理由は「Windows のサービスを無効化する」ことだった**（出典1）。 **判定は誤っていなかった**（本記録の評価）〈重要〉—— **挙動として、善意の是正と攻撃は区別できない。** **区別できるのは意図だけであり、意図は実行ファイルに書かれていない。** **同社はシグネチャを回避するようコードを改変し、 最終版の検知は1ベンダーのみとなっている**（出典1）—— **検知規則は機能したが、回避もされた**（本記録の整理）。
    取るべき行動 **①「SYSTEM/root の常駐プロセスが、外部から取得した未署名のバイナリを 実行した」事象を警報として扱う規則が有効か確認する。** **②HTTP で実行ファイルを取得する通信を、宛先の許可リストで限定する （既定は拒否）。本件の更新機構は平文 HTTP を使っていた（出典1）。** **③サービスの停止・無効化という操作そのものを監視対象に含める—— 本件では11ベンダーがこの挙動を検知の根拠にしていた（出典1）。**
