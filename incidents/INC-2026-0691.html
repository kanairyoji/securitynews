INC-2026-0691Signal の通話後もマイクが稼働

Signal が音声・ビデオ通話に使う自社ライブラリ **RingRTC** に、 **通話を終了したはずなのにマイクとカメラが動き続ける**脆弱性 （**CVE-2026-113380**・CVSS v4.0 **9.3**／CWE-754）があった。 RingRTC は通話に関わる事象を**有限状態機械（FSM）のキュー**で処理するが、 **通話相手がこのキューを要求で埋め尽くすと、キューが溢れて新しい事象が 適時に処理されなくなる**。 **その結果、「通話を切る」要求がキューに滞留して実行されず、 利用者は通話が終わったと思っているのに、 音声・映像の経路が開いたままになる**。 **攻撃者は、被害者の端末の周囲の音を聞き続け、 カメラの映像を受け取り続けられる可能性がある**。 **影響は 2.72.0 より前のすべてのバージョンに及ぶ**。 **修正は2026年9月4日のタグ `v2.72.0` で出ており**、 **通話の終了要求を FSM の主キューとは独立に処理する方式へ変更し、 処理の滞留が終了を無期限に妨げないようタイムアウトを設けた**。 **ところが CVE が公開されたのは2026年10月20日で、修正から46日後である**。 **Signal Desktop は2026年9月に 2.72.0 を取り込んだが、 Android 版・iOS 版に修正済みライブラリがいつ入ったかは明らかでない**。 **発見者は Python の実証コードを公開している**。 **Signal 自身によるセキュリティ勧告は、本記録の確認時点で公開されていない**。

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月20日（CVE-2026-113380 および GitHub Advisory の公開） 最終更新: 2026年10月24日（本記録の作成）

「切った」という操作が、実際に切れていなかった。

Signal が音声・ビデオ通話に使う自社ライブラリ RingRTC は、通話に関わる事象を有限状態機械（FSM）のキューで順に処理する。通話相手がこのキューを要求で埋め尽くすと、キューが溢れ、新しい事象が適時に処理されなくなる（出典3）。このとき「通話を切る」要求もキューに滞留して実行されない。

結果として起きることが、この脆弱性の重さを決めている（出典2・3）。利用者の画面では通話は終わっている。しかし音声・映像の経路は開いたままである。 攻撃者は被害者の端末の周囲の音を聞き続け、カメラの映像を受け取り続けられる可能性がある。

CVE-2026-113380・CVSS v4.0 で 9.3（Critical）・CWE-754（出典2）。影響は 2.72.0 より前のすべてのバージョンに及ぶ（出典2・3）。

修正は2026年9月4日のタグ v2.72.0 で出ている（出典1）。変更点は2つ——通話の終了要求を FSM の主キューとは独立に処理する方式へ変え、処理の滞留が終了を無期限に妨げないようタイムアウトを設けた（出典3）。つまり直したのは個別の不具合ではなく、「終了処理が他の処理の健全性に依存していた」という構造である（本記録の整理）。

本記録が重く見るのは、修正と公表のあいだの46日である（本記録の評価）〈重要〉。CVE が公開されたのは2026年10月20日（出典2）。その間、Signal Desktop は2026年9月に 2.72.0 を取り込んだが、Android 版・iOS 版に修正済みライブラリがいつ入ったかは明らかでない（出典3）。Signal 自身によるセキュリティ勧告は、本記録の確認時点で公開されていない（本記録の確認）〈齟齬1〉。

日本の読者にとっての論点は、終了処理の設計である（本記録の評価）。「停止」「切断」「取消」「失効」を、他の処理と同じ待ち行列に並べていないか——本件はその設計が、プライバシーの約束そのものを破る形で現れた例である。

「通話を切る」要求を他の事象と同じ待ち行列に並べていたことが原因だった原因・手口

RingRTC は Signal が自社で開発した通話用ライブラリで、WebRTC の上に構築されている（出典3）。中核にあるのが有限状態機械（FSM）で、そのキューが通話に関わる事象を順に処理する（出典3）。

脆弱性の仕組みは単純である（出典3）。通話の相手がこのキューを要求で埋め尽くすと、キューが溢れ、新しい事象が適時に処理されなくなる。 そして「通話を切る」要求もキューに滞留し、実行されない。

問題の本質は、終了処理が他の処理の健全性に依存していたことである（本記録の評価）〈重要〉。終了は、最も確実に実行されなければならない操作である。それを他の事象と同じ待ち行列に並べれば、待ち行列が詰まれば終了も詰まる。

割り当てられた CWE はこの読み方と整合する—— CWE-754（異常・例外状態の不適切な確認）（出典2）。

修正の内容が、原因の所在を裏付けている（本記録の評価）。RingRTC 2.72.0 での変更は2点である（出典3）。①通話の終了要求を、FSM の主キューとは独立に処理する方式へ変更した。 ②処理の滞留が通話の終了を無期限に妨げないよう、タイムアウトを設けた。

つまり直したのは個別の不具合ではなく、依存関係そのものである（本記録の整理）。終了処理に独立した経路と時間的な上限を与えた——この2つは、停止・取消・失効のような「必ず完了すべき処理」に共通して必要な設計である（本記録の評価）。

この配点の読み方が、本件の性質を示している（本記録の整理）〈重要〉。

可用性への影響は「なし」（VA:N）である。「通話を切れなくする」という現象は、一見すると可用性の問題に見える。しかし評価は機密性・完全性を「高」（VC:H／VI:H）とし、さらに後続システムの機密性も「高」（SC:H）としている（出典2）。

  • **終了・解放の経路を、通常の事象キューから分離する**
    **本件では、通話の終了要求が FSM の主キューに並んでいた**（出典3）。 **相手がキューを埋め尽くすと、終了要求も滞留して実行されない**（出典3）〈重要〉。 **修正は、終了要求を主キューとは独立に処理する方式への変更だった**（出典3）。 **一般化すればこうである**（本記録の評価）—— **資源の解放・接続の切断・権限の失効は、 それを引き起こした系の健全性に依存してはならない。** **依存していれば、系を壊すだけで解放を止められる。**
    取るべき行動 **①終了・解放の処理に、通常の処理とは別の経路 （専用のフラグ・別スレッド・別チャネル）を与える。** **②終了処理の各段が失敗しても後続の段を続行する構造にする—— 最初の失敗で止まると、解放が中途で終わる。** **③終了待ちに必ずタイムアウトを置く。 本件の修正はこの2点（独立した経路とタイムアウト）である（出典3）。**
  • **「通話相手」「対向ノード」は信頼できない入力源である。キューの長さは攻撃面になる**
    **本件の攻撃者は侵入者ではなく、通話相手という正規の立場にいる** （出典2。整理は本記録）〈重要〉。 **CVSS に `PR:N`（特権不要）と `UI:P`（受動的な利用者操作）が 付いているのはこのためである**（出典2）。 **必要なのは、被害者が通話に応じることだけである**（本記録の整理）。 **そして攻撃の手段は、事象を大量に送ってキューを溢れさせることだけである**（出典3）。 **つまり、対向ノードが送る事象の量が内部状態の処理能力に 直結していた**（本記録の評価）。
    取るべき行動 **①対向ノード由来の事象について、 流量の制限（レート制限）と、キューに積む量の上限を設ける。** **②キューが上限に達したときの振る舞いを明示的に設計する—— 「新しい事象を捨てる」のか「古いものを捨てる」のか、 そして制御系の事象（終了）は常に通るのか。** **③プロトコル実装の試験に「対向が異常な量を送ってくる」場合を入れる。 正常系と故障系の間にある「悪意ある対向」の試験が欠けやすい。**
