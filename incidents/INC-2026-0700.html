INC-2026-0700Tailscale SSH 転送に権限昇格

Tailscale SSH の転送機能に権限昇格——Erica Windisch（Cyberdione Labs）が2026年10月25日に 「Tailworm」として Tailscale 1.104.2 と headscale 0.29.5 の11件の発見を公開した。 SSH の転送処理が root 権限の tailscaled 内で行われ、ログインしたアカウントの権限で 制限されていないため、許可された1台を押さえた攻撃者が他のサーバの管理者権限と デバイス追加用の認証鍵に到達できたとされる。 Tailscale は報告を受けて調査中で修正は未公開、CVE もセキュリティ公告も発行されていない。 開示は調整されておらず、研究者と同社の推奨策も食い違っている。

2026年10月25日、Erica Windisch（Cyberdione Labs Corporation）は「Tailworm」と題した評価レポートを公開し、Tailscale 1.104.2 と headscale 0.29.5 に11件の発見があるとしました。中核は Tailscale SSH の転送（port forwarding）機能による権限昇格です。レポートによれば、Tailscale SSH は利用者単位の認証を行わずデバイスIDでポリシーを評価するため、ポリシー上ログインを許可された1台を押さえた攻撃者は、セッション中の転送機能を使える。そして転送の処理は root 権限で動く tailscaled の内部で行われ、パスの検証と実際の操作のあいだに競合（TOCTOU）があるため、ログインしたアカウントの権限では触れない root 所有の Unix ソケットに到達でき、既存のソケットを置き換えることもできたとされます。研究室内の検証では、Docker の管理ソケット経由でホストの root 権限に到達し、保護されたシステムファイルを読み出したほか、Tailnet Lock を有効にしていない環境でデバイス追加用の認証鍵（authkey）を通信中から取得し、攻撃者の管理する機器を同じ private network に参加させたと報告されています。Tailscale は報告を受けて調査中であり、修正は本記録の確認時点で未公開、CVE もセキュリティ公告（最新は TS-2026-013）も発行されていません。エンジニアリング担当副社長の Mike Shaver は10月25日、問題は「SSH 接続が認可された後」に生じるもので、外部の攻撃者が未認可のまま任意のサーバにログインできるというものではないとの初期評価を示し、全利用者に一律で Tailscale SSH を無効化することは勧めないとしました。一方で研究者は Tailscale SSH と App Connectors の無効化を勧めており、推奨策そのものが食い違っています。開示は調整されておらず（研究者は「報告はしたが調整はしていない」と述べています）、修正前の詳細公開を無責任とする批判も出ています。

指摘の核は「許可リストはセキュリティ境界ではない」という点にある原因・手口出典 [1] [2]

レポートの中核は、Tailscale SSH の認可の単位と、転送処理が動く権限のずれです。
認可の単位 デバイスID（利用者単位の認証を行わない）
転送処理が動く場所 root 権限で動く tailscaled の内部
指摘されたずれ 一部の転送操作がログインしたアカウントの権限で制限されていない
加えて パスの検証と実際の操作のあいだに競合（TOCTOU）がある

研究者はこれを 「the allowlist is not a security boundary」（許可リストはセキュリティ境界ではない／原文英語）と表現しています。

具体的に報告された挙動は次の形です。ポリシー上ログインを許可された1台を押さえた攻撃者が、ssh -L / ssh -R で root 所有の Unix ソケットに到達でき、既存のソケットを置き換えることもできた。 SSH の転送はもともと、リモート接続を通して相手側のサービスへ到達するための機能です。ところが本件では、一般のアカウントでは操作する権限が無いシステムの機能にも届いたとされます。

研究室内の検証では、Docker の管理ソケットに転送で接続して高権限のコマンドを実行し、保護されたシステムファイルを読み出したと報告されています。Docker のソケットは「触れれば root 相当」として知られる資産であり、到達できてしまえば昇格の工程は要らない（本記録の注記）。

もうひとつの経路がデバイス追加用の認証鍵（authkey）です。ソケットの乗っ取りによって localapi 経由の authkey を通信中に取得したとされ、Tailnet Lock を有効にしていない検証環境では、その鍵で攻撃者の管理する機器を同じ private network に参加させられたと報告されています。ただし、新たに参加した機器がすべてのサーバに接続できるわけではなく、実際に到達できる範囲は Tailscale 側の既存の権限設定で制限されます。

Tailnet Lock が有効な場合についてもレポートは触れており、「the TKA disable-secret and signer-key material were captured in transit」（TKA の無効化シークレットと署名鍵の素材を通信中に取得した／原文英語）としながら、実際の無効化は実行していないと明記しています。

研究者と Tailscale で、推奨する対処が食い違っている対策・注意喚起出典 [1] [2]

緩和策の中身が、研究者とベンダーで異なります。 読者はまずこのずれを把握してから判断する必要があります（本記録の評価）。

Tailscale（管理者向けの案内）

  • SSH のアクセス規則を点検し、必要な人員と機器だけにログインを許す
  • 転送が不要なら転送機能を無効化する（通常の Tailscale SSH ログインには影響しない）
  • SSH の再認証モード（check mode）を有効にすると防護を一段増やせるが、権限昇格そのものは解決しない
  • 全利用者に一律で Tailscale SSH を無効化することは勧めない

研究者（レポート）

  • SSH 規則は利用者単位・タグ単位の広い付与を避け、送信元と宛先の1対1の付与（per-pair grants）にする
  • SaaS では転送フラグを個別に拒否できる。headscale 0.29.5 では転送を無効化できないため、headscale の SSH 付与はすべて root 相当として扱う
  • ノードキーに有効期限を設定し、TPM や Secure Enclave を使う
  • App Connector は権限を制限し、宛先を許可リストにし、Kubernetes ではegress を default-deny にする
  • インシデント対応では再イメージ化だけでは不十分で、コントロールプレーン側でデバイスを削除する必要がある
  • Tailscale SSH と App Connectors の無効化

最後の1点が正面から衝突しています。 研究者は Tailscale SSH の無効化を勧め、Tailscale は一律の無効化を勧めないとしています。

両者が食い違うのは、評価の前提が違うためです（本記録の読み取り）。Shaver の初期評価は「問題は主に SSH 接続が認可された後に生じるもので、外部の攻撃者が未認可のまま任意のサーバにログインできるというものではない」というものです。つまり攻撃の起点として「すでに許可された1台の掌握」を要するという整理です。研究者の側は、その1台の掌握が成立する前提では被害が他のホストへ広がる、という点を重く見ています。

判断の分かれ目は、自組織で「許可されたデバイス1台の掌握」をどれだけありうることとして扱うかにあります（本記録の評価）。開発者の手元の端末やCIのランナーが tailnet に入っている構成では、その1台は日常的に外部のコードを実行しています。

開示は調整されていない——「報告はしたが調整はしていない」評価・解釈出典 [1] [2] [3]

本件は、調整開示（coordinated disclosure）の枠組みの外で公開されています。

研究者は、公開に先立ってレポートと PoC を Tailscale のセキュリティ窓口へ送ったとしつつ、その過程を 「It was reported but not coordinated.」（報告はしたが調整はしていない／原文英語）と述べています。送付の日付は示されていません。

Hacker News では、研究者が「Tailworm」という名の意図——侵害された1台から他の許可済みホストへ広がりうるというワーム的な懸念——を説明した投稿が通報され、非表示になりました。 また、従来の意味でのワーム化は考えにくいとするコメントも出ています。修正の提供前に詳細を公開したことを無責任とする批判に対し、研究者は、脆弱性はベンダーに通報済みであり、双方で公開時期を調整していなかったと応答しました。

読者にとっての実務上の意味は、「待てば情報が整う」という前提が崩れることです（本記録の評価）。調整開示であれば、公開の時点で CVE 番号・影響範囲・修正版が揃います。本件はその逆で、手口の方向性だけが先に公開され、影響範囲と修正はあとから来ます。

この順序は、攻撃側と防御側で使える情報の非対称を生みます。 攻撃側はレポートの記述（root 所有の Unix ソケットへの転送、Docker 管理ソケット、localapi 経由の authkey）から試行の方向を決められますが、防御側は「自社が影響を受けるか」を公式の情報で確認できません。PoC が非公開であることは試行の難度を上げますが、方向が示されている以上、難度の問題は時間の問題でもあります（本記録の評価）。

なお、本記録はこの開示の作法そのものを評価しません。 評価すべき材料——報告の日付、ベンダーの応答の経過、両者のやりとりの内容——が公表されていないためです。

日本の読者にとっては「保守経路に入れた1台」の問題として読める評価・解釈出典 [1] [5]

Tailscale は、拠点間の接続、開発環境へのアクセス、保守経路の構築といった用途で国内でも使われており、本件については日本語の注意喚起記事も出ています。

本記録として、日本の読者に向けた論点を1つに絞ります。本件の起点は「ポリシー上ログインを許可された1台の掌握」です。これは脆弱性の悪用ではなく、日常的に起きうる事象です——開発者の端末がマルウェアに当たる、CI のランナーが外部の依存を実行する、委託先の作業端末が持ち込まれる。

そのうえで本件が示したのは、その1台から他のサーバの root に届きうるという主張です。つまり、tailnet に入れたデバイスの一覧が、そのまま「root を取れる候補の一覧」になりうるという読み方です（本記録の評価。研究者の主張に依拠しており、再現は未確認）。

この読み方が正しければ、対策の軸は製品の修正を待つことではなく、「許可の粒度」に移ります。 研究者の推奨の中心が送信元と宛先の1対1の付与（per-pair grants）にあるのは、この理由です。タグ単位や利用者単位で広く付与していると、1台の掌握がその付与の範囲全体に効きます。

もう1つ、インシデント対応の手順に関わる指摘があります。研究者は、侵害されたノードの再イメージ化だけでは不十分で、コントロールプレーン側でデバイスを削除する必要があるとしています。ノードキーが有効なまま残れば、再イメージ化した端末とは別に、鍵を持ち出した側が tailnet に残ります。これは本件の成否にかかわらず成り立つ運用上の論点です（本記録の評価）。

CISO・経営層への示唆
  • 「許可されたデバイス1台の掌握」を、ありうる前提として扱う
    本件の起点は脆弱性の悪用ではなく、**ポリシー上ログインを許可された1台を 押さえること**である。開発者の端末、CI のランナー、委託先の作業端末は 日常的に外部のコードを実行している。 **その1台が押さえられたときに何が起きるかを設計の前提に入れていないと、 本件のような指摘が出たときに影響範囲を自力で判断できない。**
    取るべき行動 **tailnet（あるいは同等の mesh VPN）に参加しているデバイスの一覧を出し、 「この1台が攻撃者の手に落ちたとき、どこまで届くか」を機器ごとに1行書く。** 書けない機器があれば、それが付与の粒度が粗い箇所である。 **一覧が「root を取れる候補の一覧」になっていないかで判断する。**
  • ベンダーと研究者で推奨策が食い違う局面の決め方を、あらかじめ持つ
    本件では**研究者が Tailscale SSH の無効化を勧め、Tailscale は一律の 無効化を勧めないとしている。** CVE も修正も再現も無い状態で、 現場はどちらかに従う判断を迫られる。 **その場で合議を始めると、判断そのものが遅れる。**
    取るべき行動 **「ベンダーの評価と第三者の指摘が食い違ったときの決定者と判断軸」を 規程に1行で持つ。** 判断軸は自組織の構成に基づくものにする—— 本件なら「転送機能を実際に使っている経路があるか」。 **使っていなければベンダーの案内（転送の無効化）を副作用なく実行でき、 食い違いに巻き込まれない。**
  • 調整されていない開示を前提に、情報が揃わないまま動く手順を持つ
    本件は**調整開示の枠組みの外**で公開された。研究者は 「報告はしたが調整はしていない」と述べている。 **公開の時点で CVE 番号・影響範囲・修正版が揃うという前提が崩れる。** 手口の方向だけが先に出て、影響範囲と修正はあとから来る。
    取るべき行動 **脆弱性対応の手順に「CVE が無い・修正が無い・再現が無い」状態の 分岐を足す。** 最低限、①自組織が当該の機能を使っているかの確認手順、 ②使っている場合に止められるか／止めたら何が止まるかの評価、 ③ベンダーの公告一覧を定点観測する担当。 **「CVE が出てから」で始まる手順しか無い組織は、この種の公開に対応できない。**

    取るべき行動 **保守・リモートアクセスに使っている製品について、 「認可の単位は人か機器か」「認可された後の操作はどの権限で動くか」を ベンダーの文書で確認し、記録に残す。** 文書に書かれていなければ問い合わせる。 **この2つが分かっていれば、同種の指摘が出たときに自力で影響を切れる。**
セキュリティ技術者への示唆
  • Tailscale SSH の転送を実際に使っている経路を棚卸しする
    Tailscale の案内にある「転送が不要なら無効化する」は、 **使っていなければ副作用なく実行できる最も安い対策**である。 逆に、使っている経路を把握せずに無効化すると業務が止まる。 **棚卸しが対策の前提になる。**
    取るべき行動 **SSH のアクセス規則を出力し、転送を許可している付与を列挙する。** そのうえで、**実際に転送を使っている接続があるかを接続のログで確認する。** 使っていない付与から順に転送フラグを落とす。 **headscale 0.29.5 では転送の無効化ができないとされるため、 headscale 運用の環境は付与の削減のほうで対応する。**
  • SSH の付与を「送信元と宛先の1対1」に寄せる
    研究者の推奨の中心がこれである。**タグ単位・利用者単位の広い付与は、 1台の掌握がその範囲の全体に効く。** 本件の成否が確定していなくても、付与の粒度を細かくすることは 他の侵害でも効く（本記録の評価）。
    取るべき行動 **広い付与（タグ→タグ、利用者→タグ）を洗い出し、 実際に発生している接続の組み合わせに置き換える。** 接続ログから「実際に使われた組み合わせ」を出し、 それだけを許可する形に寄せる。**使われていない付与は消す。**
  • root 相当のソケットを、転送で到達できる場所に置かない
    研究室内の検証では **Docker の管理ソケット経由でホストの root に到達した** と報告されている。**Docker のソケットは触れれば root 相当であり、 到達できてしまえば昇格の工程は要らない。** これは Tailscale に限らない構成上の論点である。
    取るべき行動 **SSH でログインできるホストの上で、root 所有の Unix ソケットを列挙する** （`ss -xlp` 等）。Docker の管理ソケットがあれば、 **その到達をホスト内のアクセス制御（ファイル権限・名前空間・ rootless モード）でも絞る。** 「ネットワーク側で絞っているから大丈夫」という前提を外して確認する。
  • ノードキーの失効を、ホストの再構築とは別の操作として手順に書く
    研究者は、**侵害されたノードの再イメージ化だけでは不十分で、 コントロールプレーン側でデバイスを削除する必要がある**としている。 **ノードキーが有効なまま残れば、再構築した端末とは別に、 鍵を持ち出した側が tailnet に残る。** これは本件の成否にかかわらず成り立つ（本記録の評価）。
    取るべき行動 **インシデント対応手順の「端末の初期化」の節に、 コントロールプレーン側でのデバイス削除を独立した手順として足す。** あわせて、**ノードキーに有効期限を設定しているかを確認する**—— 無期限であれば、失効は手動の削除だけが唯一の手段になる。
  • 「防護を一段増やす」設定を、対策として数えない
    Tailscale は **SSH の再認証モード（check mode）**で防護を一段増やせるとしつつ、 **権限昇格そのものは解決しない**と明言している。 **解決しない設定を対策表に「対応済み」と書くと、 残っているリスクが見えなくなる。**
    取るべき行動 **対策表の各行に「これで止まるのは何か／止まらないのは何か」を併記する。** 本件なら check mode は「認可の段階を厚くする」もので、 「認可された後の昇格」には効かない。 **効かない範囲が書かれていない対策表は、効果を過大に見積もる。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ mesh VPN のアクセス制御が、利用者単位ではなくデバイス単位で付与されている本件の指摘の核がここにある。 認可の単位が機器であれば、1台の掌握がその付与の範囲全体に効く。
認証・認可□ SSH の付与がタグ単位・利用者単位で広く、送信元と宛先の1対1になっていない研究者の推奨の中心が per-pair grants である。 広い付与は、1台の掌握をそのまま横展開に変える。
システム構成□ SSH でログインできるホスト上に、root 所有の Unix ソケット（Docker 管理ソケット等）がある研究室内の検証では Docker 管理ソケット経由でホストの root に到達したとされる。 到達できてしまえば昇格の工程は要らない。
運用・監視□ Tailscale SSH の転送機能を使っている経路を把握していない「転送が不要なら無効化する」はもっとも安い対策だが、 使っている経路を知らずに実行すると業務が止まる。把握が対策の前提になる。
運用・監視□ 侵害端末の対応手順が「再イメージ化」で終わり、コントロールプレーン側のデバイス削除を含まないノードキーが有効なまま残れば、鍵を持ち出した側が tailnet に残る。 本件の成否にかかわらず成り立つ論点である。
体制・契約□ 脆弱性対応の手順が「CVE が発行されてから」で始まる本件は CVE も公告も修正も無い状態で詳細が公開された。 CVE を起点にする手順しか無いと、この種の公開に対応できない。
