INC-2026-0702Gheist、秘密情報をログに吐かせる

**盗んだ GitHub のトークンで、リポジトリの秘密情報を GitHub 自身のログに 吐き出させる**自動化キャンペーンが続いている。 Wiz Research が **Gheist** と名づけて2026年9月15日から追跡しており、 **850超のアカウント**から**13,500超の仕込まれたブランチ**を回収した。 手口は、盗んだトークンで到達できる全リポジトリに `ci-sync-` ＋6文字のブランチを作り、`.github/workflows/sync-check.yml` を コミットする——**走り出したワークフローが、環境変数と `secrets` コンテキストを base32 で符号化して自分のログに印字する**。 **GitHub が秘密情報を隠すのは「そのままの文字列」が出たときだけなので、 符号化された値はそのまま出る**。 **攻撃者は API でログを取得し、数秒後に実行記録を消す**。 **外部へ出ていく通信が無いので、遮断すべき攻撃者のドメインも存在しない。** **2026年7月28日から GitHub は公開リポジトリで疑わしいワークフローの実行を 承認待ちで止めており、Wiz が調べた公開リポジトリの実行はすべて `action_required` のまま動かなかった**。 **一方、この保護は非公開リポジトリと GitHub Enterprise Server には及ばず、 そこでは成功している**——監査ログには `ci-sync-*` ブランチでの実行完了と `gheist` の利用者エージェントによる削除が残り、 AWS CloudTrail には同じブランチでの AWS ロール引き受けが記録されていた。 **ブランチや実行記録を消しても露出は戻らない。 当該リポジトリが読めた秘密情報はすべて更新が必要である。**

外へ送信しないのに、情報は出ていきます。出口は GitHub 自身のログです。

2026年10月25日、Wiz Research が Gheist と名づけたキャンペーンを公表しました（出典1）。名前の由来は、攻撃に使われている道具が GitHub の API へ送る利用者エージェント gheist です（出典1）。Wiz は2026年9月15日から追跡しており、850を超えるアカウントから13,500を超える仕込まれたブランチを回収しました（出典1）。

手口は次のとおりです（出典1）。

  1. 盗んだトークンで、そのトークンが到達できる全リポジトリを対象にする。
  2. 各リポジトリに ci-sync- ＋6文字のブランチを作り、.github/workflows/sync-check.yml を ci: sync config というメッセージでコミットする（署名は無く、作成者はトークンの持ち主として記録される）。
  3. push で走り出したワークフローが、環境変数と secrets コンテキストをbase32 で符号化して自分のログに印字する。
  4. 道具が GitHub の API でそのログを取得する。
  5. 数秒後に実行記録を消す。

本記録が要点と見たのは、次の3点です。

  • 出口が基盤の内側にあるので、止める先が無い。 Wiz は「データが GitHub 自身の API を通って出ていくため、攻撃者のドメインも外向きの接続も存在しない」としています（出典1。原文英語。訳は本記録）。送信先を遮断する、という防御の形がそもそも当てはまりません（本記録の評価）。
  • 秘密情報を隠す仕組みは、符号化すると効かない。 GitHub がログで秘密情報を隠すのは「そのままの文字列」が現れたときだけで、base32 で符号化された値は全部そのまま出ます（出典1）。さらに、ジョブの permissions: {} が制限するのは GITHUB_TOKEN であって、secrets コンテキストではありません（出典1）。どちらも設定の誤りではなく、仕様どおりの挙動です（本記録の評価）。
  • 公開リポジトリでは止まり、非公開と Enterprise Server では止まらなかった。 2026年7月28日から、GitHub は公開リポジトリで疑わしいワークフローの実行を共同作業者の承認まで保留しています（出典1）。Wiz が調べた公開リポジトリの実行はすべて action_required のままで、「この対策は機能し、悪性のペイロードは一度も走らなかった」とされています（出典1。原文英語。訳は本記録）。一方、この保留は非公開リポジトリと GitHub Enterprise Server には及びません（出典1）。そこでは、監査ログに ci-sync-* ブランチでの実行完了とgheist による削除が残っていました（出典1）。

出口が GitHub の内側にあるので、遮断する先が存在しない原因・手口

Wiz は手口を次の5段で説明している（出典1）。

# 動作 使われるもの
1 盗んだトークンで到達できる全リポジトリを対象にする 正規のトークン
2 ci-sync-＋6文字のブランチに .github/workflows/sync-check.yml をコミット 正規の push
3 走り出したワークフローが環境変数と secrets を base32 で符号化して印字 正規の Actions
4 道具が GitHub の API でログを取得 正規の API
5 数秒後に実行記録を削除 正規の API

全段が正規の機能である（本記録の評価）。だから Wiz はこう書いている。

「データが GitHub 自身の API を通って出ていくため、攻撃者のドメインも外向きの接続も存在しない」（出典1。原文英語。訳は本記録）

この1文が、本件で最も重い（本記録の判断）。秘密情報の持ち出しに対する防御は、たいてい「どこへ送られたか」を押さえる形で作られている——外向き通信の監視、DNS の遮断、プロキシでの制御、C2 ドメインのブロックリスト。本件はそのどれにも当たらない。

秘密情報を隠す仕組みが効かない理由も、同じ性質である（出典1）。

「GitHub が秘密情報を隠すのは、それがそのままの形で現れたときだけなので、符号化された値は全部印字される。ジョブの permissions: {} が制限するのはGITHUB_TOKEN だけで、secrets コンテキストではない」（出典1。原文英語。訳は本記録）

permissions: {} は、見た目には最も厳しい設定である。それでも secrets は読める。設定を間違えたのではなく、仕様どおりの挙動が組み合わさっている（本記録の評価）。

公開リポジトリでは止まり、非公開と Enterprise Server では止まらなかった被害規模・影響範囲

2026年7月28日から、GitHub は公開リポジトリで疑わしいワークフローの実行を共同作業者の承認まで保留している（出典1）。

Wiz が調べた公開リポジトリの実行は、変種を問わずすべてaction_required のままだった（出典1）。Wiz の言い方はこうである。

「対策は機能し、悪性のペイロードは一度も走らなかった」（出典1。原文英語。訳は本記録）

ところが、この保留は非公開リポジトリと GitHub Enterprise Server には及ばない（出典1）。

場所 承認保留 結果（出典1）
github.com の公開リポジトリ 及ぶ 実行されなかった（action_required のまま）
github.com の非公開リポジトリ 及ばない 実行された（完了後に削除）
GitHub Enterprise Server 及ばない 実行された

成功の証拠として挙げられているのは2つである（出典1）。①GitHub の監査ログに、ci-sync-* ブランチでの実行完了と、その後の gheist による削除が残っていた。②AWS CloudTrail に、組織自身のワークフローがこれらのブランチで動き、AWS のロールを引き受けた記録が残っていた—— 承認なしに Actions が実行されたことを示す。

本記録が重く見るのは、この非対称である（本記録の評価）。公開リポジトリは、不特定多数に見られる代わりに基盤側の保護が厚い。非公開リポジトリは、見られない代わりに保護が薄い。 「非公開だから安全」という直感と、実際の保護の厚みが逆を向いている。

そして企業が機密を置くのは非公開リポジトリの側である（本記録の評価）。Wiz が記述している企業環境での動きは、複数の利用者と自動化アカウントのトークンを数分で巡回し、ワークフローを仕込む前に非公開リポジトリを複製し、数時間後に同じ組織のクラウド資格情報で AWS Secrets Manager を列挙した ——というものである（出典1）。

消しても戻らない——「ブランチを削除して対応完了」にしてはいけない再発防止

Wiz の対応の指針で最初に来るのはこれである（出典1）。

「影響を受けたリポジトリが読めたリポジトリ・組織・環境のすべての秘密情報を更新せよ。実行やブランチを削除しても露出は元に戻らない」（出典1。原文英語。訳は本記録）

仕込まれたブランチを見つけたとき、最も手軽に見える対応は「ブランチを消す」である（本記録の評価）。しかし秘密情報はすでにログへ印字され、API で取得されている。 残っている痕跡を消すことは、露出を取り消すことではない。

攻撃者側も、実行記録を数秒後に消している（出典1）。つまり「痕跡が無い」は「何も起きなかった」の証拠にならない（本記録の評価）。

対応として挙げられているのは次である（出典1）。

  • 当該リポジトリから読めた秘密情報を、リポジトリ・組織・環境の全スコープで更新する
  • コミットを push したトークンを無効化し、持ち主の端末をインフォスティーラーの観点で確認する
  • ci-sync ブランチが self-hosted ランナーで走った場合は、そのホストとインスタンスのロールを侵害済みとして扱う
  • 保留されている sync-check の実行を承認しない。ci-sync ブランチのコードを実行しない

探索（hunt）で本記録が有用と見たのは、最後の1つである（出典1）。

「クラウド事業者と OIDC を使っているなら、主体（subject）に ci-sync- を含むロールの引き受けやトークン交換をクラウドの監査ログで確認せよ。これは GitHub のログが無くてもこの活動を検知できる」（出典1。原文英語。訳は本記録）

GitHub 側のログは攻撃者が消しうる。クラウド側のログは消せない（本記録の評価）。自組織に残っている記録のうち、相手の手が届かないものはどれか——という問いの立て方が、本件では効く。

事案の詳細

露出の仕組み**秘密情報は、GitHub Actions の実行ログを出口にして出ていく**（出典1）。 **①ワークフローが環境変数と `secrets` コンテキストを base32 で符号化して印字する。 ②GitHub が秘密情報を隠すのは「そのままの文字列」が現れたときだけなので、 符号化された値は全部そのまま出る。 ③攻撃者の道具が GitHub の API でログを取得する。 ④数秒後に実行記録を消す。** **外部への接続が無いため、遮断すべき攻撃者のドメインが存在しない**（出典1）。
露出経路**ジョブの `permissions: {}` が制限するのは `GITHUB_TOKEN` であって、 `secrets` コンテキストではない**（出典1）。 **デプロイ環境（environment）を持つリポジトリでは、 ジョブのマトリクスを使って環境ごとの秘密情報も印字される**（出典1）。
露出した項目**リポジトリ・組織・環境の各スコープの秘密情報、および環境変数**（出典1）。 **`self-hosted` ランナーで走った場合は、さらにホスト・プロセス・コンテナ・ クラウドのメタデータ・ランナー・Kubernetes の資格情報**（出典1） ——**ただしこのジョブには不具合があり、GCP・Azure のトークンなど 取り逃がしがあるとされる**（出典1）。
緩和策
手順: **当該リポジトリから読めた秘密情報を、リポジトリ・組織・環境の全スコープで更新する** （出典1）。　副作用: **本番の認証情報を一斉に差し替える作業であり、 更新漏れがそのまま障害になる**（本記録の評価）。 **出典1 自身が「実行やブランチを消しても露出は戻らない」と述べているため、 作業を避ける選択肢が無い。**
手順: **コミットを push したトークンを無効化し、 その持ち主の端末をインフォスティーラーの観点で確認する**（出典1）。　副作用: **自動化アカウントのトークンを無効化すると、 そのトークンに依存する CI が止まる**（本記録の評価）。 **企業の環境では複数の利用者と自動化アカウントのトークンが 数分のあいだに使われていた**（出典1）ため、**対象が1本では済まない。**
手順: **`ci-sync` ブランチが self-hosted ランナーで走った場合は、 そのホストとインスタンスのロールを侵害済みとして扱う**（出典1）。　副作用: **ビルド基盤そのものの再構築になり、開発が止まる**（本記録の評価）。
手順: **保留されている `sync-check` の実行を承認しない。 `ci-sync` ブランチのコードを実行しない**（出典1）。　副作用: **承認待ちの実行が溜まり、正規の実行の承認作業に紛れる**（本記録の評価） ——**判別の手順を先に決めておかないと、取り違えが起きうる。**
手順: **本番の秘密情報を持つ環境にレビュー担当者を必須にし、 OIDC の信頼方針を保護されたブランチ・環境に限定する**（出典1）。　副作用: **デプロイのたびに人の承認が入り、リリースの速度が落ちる**（本記録の評価）。
手順: **個人アクセストークン（PAT）ではなく GitHub App または 短命の細粒度トークンを使う**（出典1）。　副作用: **既存の自動化の作り替えが必要になり、移行期間は両方の経路が並存する** （本記録の評価）。
手順: **self-hosted ランナーを使い捨てのホストとして運用し、 Docker ソケットや無制限のメタデータへのアクセスを与えない**（出典1）。　副作用: **ビルドのキャッシュが効かなくなり、実行時間とコストが増える**（本記録の評価）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「非公開リポジトリだから安全」という前提を外す。保護の厚みは公開設定と逆を向いている。
    **2026年7月28日以降の承認保留は github.com の公開リポジトリにのみ及び、 非公開リポジトリと GitHub Enterprise Server には及ばない**（出典1）。 **Wiz が調べた公開リポジトリの実行はすべて止まり、 非公開側では実行されている**（出典1）。 **企業が機密を置くのは非公開側である**（本記録の評価）。
    取るべき行動 **自組織のリポジトリを公開設定と基盤の種別（github.com／Enterprise Server）で 分類し、基盤側の保護が及ぶ範囲を明示した表を作る。** **及ばない範囲については、承認を要する環境の設定・OIDC の信頼範囲の限定・ 監査ログの外部保持で埋める**（出典1 の推奨に基づく）。
  • 秘密情報の持ち出しを「外向き通信」で捉える設計は、本件には当たらない。
    **「データが GitHub 自身の API を通って出ていくため、 攻撃者のドメインも外向きの接続も存在しない」**（出典1。原文英語。訳は本記録）。 **外向き通信の監視・DNS の遮断・プロキシの制御・C2 のブロックリストは いずれも当たらない**（本記録の評価）。
    取るべき行動 **情報持ち出しの検知の棚卸しを、「出口の種類」で行う。** 外向き通信以外の出口——SaaS の API、基盤のログ、共有機能、 正規の同期機能——について、それぞれ何で気づけるかを書き出す。 **埋まらない欄が、本件と同じ形の穴である。**
  • 個人アクセストークンの到達範囲が、そのまま被害範囲になる。
    **手口は「盗んだトークンが到達できる全リポジトリ」を対象にする**（出典1）。 **企業の環境では、複数の利用者と自動化アカウントのトークンを 数分のあいだに巡回していた**（出典1）。 **トークン1本の到達範囲が広ければ、1本の漏えいで全部が露出する**（本記録の評価）。
    取るべき行動 **PAT の棚卸しを、本数ではなく「1本あたりの到達範囲」で行う。** GitHub App または短命の細粒度トークンへの移行計画を、 到達範囲の広い順に作る（出典1 の堅牢化の推奨に基づく）。 **自動化アカウントのトークンを所有者不明のまま残さない。**
  • 先行キャンペーンの被害者だったことは、次のキャンペーンの前提になる。
    **Gheist の第1段階に現れた57アカウントは、 2026年5月に Megalodon の被害者でもあった**（出典1）。 **トークンの出所には2026年3月の Trivy 侵害も挙げられている**（出典1）。 **盗まれた資格情報は使い回され、別の運用者の手に渡る**（本記録の評価）。
    取るべき行動 **過去に自組織が関係した供給網侵害・インフォスティーラー感染について、 そのとき露出しえた資格情報が「いま無効になっているか」を遡って確認する。** **当時の対応記録に「更新した」とあるだけでは足りない—— 現在の有効性を確認する。**
  • 「痕跡を消した」は対応ではない。露出は戻らない。
    **「実行やブランチを削除しても露出は元に戻らない」** （出典1。原文英語。訳は本記録）。 **攻撃者側も実行記録を数秒後に消している**（出典1） ——**痕跡が無いことは、何も起きなかった証拠にならない**（本記録の評価）。
    取るべき行動 **CI/CD の秘密情報が露出しえた事象について、 「秘密情報の全スコープ更新」を完了条件とする手順を先に用意する。** リポジトリ・組織・環境の各スコープの一覧と、更新の順序、 更新漏れによる障害の戻し方を決めておく（出典1 の対応指針に基づく）。
セキュリティ技術者への示唆
  • `permissions: {}` は `secrets` を守らない。
    **「ジョブの `permissions: {}` が制限するのは `GITHUB_TOKEN` だけで、 `secrets` コンテキストではない」**（出典1。原文英語。訳は本記録）。 **さらに GitHub が秘密情報をログで隠すのは 「そのままの文字列」が現れたときだけで、base32 で符号化すると隠されない**（出典1）。
    取るべき行動 **ワークフローの審査項目に「`secrets` コンテキスト全体を参照する記述の有無」を 入れる**（`toJSON(secrets)` のような全体参照）。 **秘密情報は必要なものだけを個別に `env` へ渡し、 コンテキスト全体を触らせない。**
  • 検知は「完了から約1分以内に削除された実行」という時間差で成立する。
    **攻撃者はログを取得してから数秒で実行記録を消す**（出典1）。 **Wiz は「`ci-sync-*` ブランチでの実行が完了して約1分以内に 削除されたもの」を監査ログで探すよう推奨している**（出典1）。 **Wiz Defend の規則名も 「New Workflow Completed And Deleted In Short Time Span」である**（出典1）。
    取るべき行動 **GitHub の監査ログを外部へ保持し、 「実行の完了」と「実行の削除」の時間差が短い組を検出する問い合わせを置く。** **基盤側のログだけに頼ると、消えたあとに再構成できない**（本記録の評価）。
  • GitHub のログが無くても、クラウドの監査ログで気づける。
    **AWS CloudTrail には、組織自身のワークフローが `ci-sync-` ブランチで動き AWS のロールを引き受けた記録が残っていた**（出典1）。 **Wiz は「これは GitHub のログが無くてもこの活動を検知できる」としている** （出典1。原文英語。訳は本記録）。
    取るべき行動 **OIDC を使っているなら、クラウドの監査ログで 主体（subject）に `ci-sync-` を含むロール引き受け・トークン交換を探す。** **併せて OIDC の信頼方針を、保護されたブランチ・環境に限定する**（出典1） ——**攻撃者が作ったブランチからロールを引き受けられる状態をやめる。**
  • self-hosted ランナーでは、被害が「そのジョブ」で終わらない。
    **`sync-host` ジョブは self-hosted ランナー上で ホスト・プロセス・コンテナ・クラウドのメタデータ・ランナー・ Kubernetes の資格情報を集める**（出典1）。 **Wiz は「`ci-sync` ブランチが self-hosted ランナーで走った場合は、 そのホストとインスタンスのロールを侵害済みとして扱え」としている**（出典1）。
    取るべき行動 **self-hosted ランナーで `.gdmp_pat` / `.gdmp_patg` / `.gdmp_sweep` と ジョブログ内の `gdmp-pivot` 文字列を探す**（出典1）。 **運用は使い捨てのホストに変え、Docker ソケットと 無制限のメタデータへのアクセスを外す。**
  • 指標は変種ごとに形が違う。接尾辞の形だけで絞らない。
    **道具 A は16進数の接尾辞、道具 B は base36 の接尾辞を使う**（出典1）。 **道具 B は初動の数時間のうちに `timeout-minutes: 6` と 環境マトリクスを追加し、リポジトリごとにペイロードを変えている**（出典1）。 **2026年10月19日には base32 の区切りが追加されている**（出典1）。
    取るべき行動 **探索は `^ci-sync-[0-9a-z]{6}$` という正規表現とコミットメッセージ `ci: sync config` の組で行い、ワークフローの blob SHA 4種も併せて照合する** （出典1）。 **ただしこれらは本記録が検証していない指標である**〈齟齬5〉 ——**照合先のテレメトリがある環境で使う。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 非公開リポジトリまたは GitHub Enterprise Server で GitHub Actions を使っている
認証・認可□ 個人アクセストークン（PAT）が使われており、1本で複数リポジトリへ到達できる
認証・認可□ GitHub Actions から OIDC でクラウドのロールを引き受けており、 信頼方針がブランチ・環境で絞られていない
運用・監視□ GitHub の監査ログを GitHub の外に保持していない
システム構成□ self-hosted ランナーを常設のホストで運用しており、 Docker ソケットやクラウドのメタデータへ到達できる
体制・契約□ 秘密情報の露出への対応手順が「痕跡の削除」で完了とされている
