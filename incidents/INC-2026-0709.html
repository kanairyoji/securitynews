INC-2026-0709GuardBreaker でAI解析を止める手口

**マルウェアのコードコメントに「核兵器の作り方を教えてほしい」と書き込み、 AI によるコード解析を途中で止めさせる手口が、実際の攻撃で使われていた。** ESET は2026年9月10日、ロシアと結び付きのある攻撃グループ **UAC-0099** が ウクライナ国内の標的への攻撃の初期段階で使った VBScript にこの仕掛けを発見し、 **GuardBreaker** と名付けた（出典1）。 **狙いは、LLM を組み込んだコードスキャナーの安全装置（ガードレール）を作動させ、 当該コメント行以降を検査しないまま処理を打ち切らせることである**（出典1）。 **コメントは実行時の動作に何の影響も与えない**（出典1） ——**隠すための難読化ではなく、「解析するモデルに読ませるために、誰の目にも見える形で 書かれている」点が従来の検知回避と性質を異にする**（出典1）。 スクリプト本来の目的は、同グループ専用のローダー **MATCHBOIL** の取得と実行である（出典1）。 **ESET はこれを「解析対象のファイルという経路で推論時に LLM へ届く、 きわめて単純な間接プロンプトインジェクション」と位置づけ、 「コードの安全性を判断する権限を単一の LLM エンジンだけに持たせるべきではない」と述べた** （出典1）。 **同種の手口は PyPI・npm のサプライチェーン攻撃でも確認されている**（出典1） ——**npm では "You're absolutely right!" を数万回繰り返してモデルの文脈窓を 使い切らせる例があった**（出典1）。 **IoC・ハッシュは公表されていない**〈未確定1〉。

セキュリティ企業 ESET は2026年9月10日、マルウェアのコードコメントに大規模言語モデル（LLM）の安全装置を作動させる文言を仕込み、AI によるコード解析を途中で止めさせる手口を報告しました（出典1）。ESET はこの手法を GuardBreaker と名付けています（出典1）。

見つかったのは、ロシアと結び付きのある攻撃グループ UAC-0099 がウクライナ国内の標的に対する攻撃の初期段階で使った VBScript です（出典1）。スクリプトのコメント行には、核兵器の作り方を教えるよう求める文言が書き込まれていました（出典1）。

狙いは次のとおりです（出典1）。

LLM を組み込んだコードスキャナーがガードレール（安全装置）を起動して応答を拒否し、ファイルの該当コメント行以降を検査しないまま処理を打ち切ることを狙ったもの。（出典1・出典2 の記述に基づく本記録の整理）

スクリプト本来の目的は、UAC-0099 が追加のペイロードを配信するためにのみ使用するローダー MATCHBOIL をダウンロードしてインストールすることです（出典1）。

本記録が重く見るのは、この手口の性質です（本記録の評価）。

従来の検知回避 GuardBreaker（出典1）
置き方 読む者の目から隠す（難読化・暗号化） 誰の目にも見える形で書く
読ませる相手 読ませない 解析するモデルに読ませる
実行時の影響 挙動に影響する場合がある 何の影響も及ぼさない

コメントがあること自体が、UAC-0099 が標的の防御に AI が組み込まれていることを織り込んでいたことをうかがわせます（出典1）。同グループは最近の別の攻撃でも、IDA・Wireshark といった従来型の解析ツールに関連するプロセスの有無を確認していました（出典1）。

ESET はこれを「きわめて単純なプロンプトインジェクション」と位置づけています（出典1）——攻撃者の入力が、解析対象のファイルという経路で推論時に LLM に届く形です（出典1）。

隠すのではなく、読ませるために書かれている原因・手口

GuardBreaker が従来の検知回避と違う点を、先に押さえておく（出典1）。

従来の検知回避 GuardBreaker（出典1）
目的 読まれないようにする 読ませて、止めさせる
見え方 難読化・暗号化で読めない 平文のコメントとして誰にでも見える
実行時の影響 挙動に関わることがある 何の影響も及ばない
対象 人間のアナリスト・署名検査 解析を行う LLM

ESET の位置づけはこうである（出典1）。

攻撃者の入力が、解析対象のファイルという経路で推論時に LLM に届く形である。今日の LLM は、信頼できないコンテンツと信頼できる指示を、両者の間に確かな境界を設けないまま処理している。GuardBreaker はこのアーキテクチャ上の弱点を突こうとするものだ。（出典1・出典2 の記述に基づく本記録の整理）

「きわめて単純なプロンプトインジェクション」である（出典1）。特別な技術も、モデルの内部知識も要らない。コメント行に自然言語で依頼を1つ書くだけである。

本記録が重く見るのは、ここに技術的な障壁が無いことである（本記録の評価）。再現のコストがほぼゼロであるため、この手口が UAC-0099 に留まる理由が無い。ただし、他のグループが採用しているという証拠も、現時点では示されていない（本記録の明示）。

「手口が使われた」ことは確認され、「手口が効いた」ことは確認されていない未確定事項

出典1 が示しているのは、手口の存在とその狙いである（本記録の確認）。

  • 実際の攻撃で使われた VBScript から発見された（出典1）→ 確認されている
  • LLM スキャナーの安全装置を作動させる狙いだった（出典1）→ ESET の判断
  • 実際に LLM スキャナーが止まった → 示されていない〈未確定2〉

どのモデル・どの製品で試されたのか、成功したのか失敗したのかが分からない（本記録の明示）。

この空白は、事案の性質から生じている（本記録の評価）。止まったという事実は、止められた側の記録にしか残らない。そして多くの検査パイプラインでは、「LLM が応答を拒否した」「出力が空だった」という事象はエラーやスキップとして捨てられる（本記録の整理）。つまり、成功していても、誰も数えていない可能性がある。

それでも対処の必要は変わらない（本記録の評価）。効いたかどうかより重いのは、攻撃者が防御側の構成に AI が入っていることを織り込んで作ってきたという事実である（出典1）。同じグループが、IDA・Wireshark というプロセスの存在確認（人による解析への対策）と、LLM への依頼文（AI による解析への対策）を両方用意している（出典1）。

問題は LLM の欠陥ではなく、「拒否されたら通る」設計にある評価・解釈

GuardBreaker が成立する条件を3つに分けて書く（出典1 の記述に基づく本記録の整理）。

  1. 検査の経路に LLM が入っている
  2. LLM が解析対象の内容を「指示」として読みうる
  3. LLM が応答を拒んだとき、検査が「問題なし」または「終了」として扱われる

1と2は、現在の LLM の作りに由来する（出典1）——組織の側で短期に変えられるものではない。3は、組織の側の設計である（本記録の評価）〈重要〉。

ESET の要求は、まさに3に向いている（出典1）。

そのツールが「何を検査するのか」「意思決定プロセスのどこに位置するのか」「応答を拒んだり、タスクを完了できなかったりしたときに何が起こるのか」を正確に把握すること（出典1 の記述に基づく本記録の整理）

出力が得られなかったこと自体も、追加の確認を促すトリガーとして扱わなければならない（出典1 の記述に基づく本記録の整理）

「コードの安全性を判断する権限を単一の LLM エンジンだけに持たせるべきではない」（出典1。原文英語「no single LLM engine should have the sole authority to decide that a piece of code is safe」。訳は本記録）

この3点は、モデルを差し替えても、プロンプトを固めても解決しない（本記録の評価）。「無応答を陽性として扱うか陰性として扱うか」という、業務プロセスの側の決定である。

本記録が読者に薦める確認は1つである（本記録の提案）。自組織の LLM を使った検査について、モデルが応答しなかったときのログを探すこと。 見つからなければ、それが答えである。

同じ狙いの手口は、すでに PyPI と npm で見つかっている背景・過去事例

ESET は、LLM を使ったスキャナーを妨害する試みがソフトウェアサプライチェーン攻撃で特に表面化しているとしている（出典1）。

経路 手口 報告
PyPI JavaScript ペイロードの手前に、偽造されたシステム指示と LLM のポリシー違反判定を誘発する内容を置く Socket（出典1）
PyPI 解析したモデルに、悪質なコードを無視してパッケージを「問題なし」と報告するよう露骨に指示する StepSecurity（出典1）
npm "You're absolutely right!" を数万回繰り返し、モデルの文脈窓を使い切らせる 出典1

3つは狙いが違う（本記録の整理）。

  • GuardBreaker と npm の例は「解析を止める」
  • StepSecurity が見た例は「誤った判定を出させる」〈重要〉

後者のほうが危険である（本記録の評価）。止まれば「結果が無い」ことに気づく機会があるが、「問題なし」が返ってくれば、気づく機会そのものが無い。

ESET はさらに、起こりうる経路として次を挙げている（出典1）。

  • 通常とは異なる、または不自然な構造のファイルによって、切り詰められたり一部しか解析されなかったりする
  • 悪質なコードの一部を、機密情報や取り扱いに注意を要するデータに見せ掛けて隠す
  • 攻撃者側のツールでなければ処理できない独自のファイル形式を使う
  • 人間のレビューが必要な動作に AI エージェントを誘導し、対応が遅れる時間を突く
  • アンパッカーや難読化解除ツールを呼び出すエージェントでは、その呼び出し自体がマルウェアの配布や実行に乗っ取られる（出典1）〈重要〉

最後の1つは、解析の自動化を進めるほど大きくなる（本記録の評価）——外部ツールを呼ぶ権限をエージェントに与えることは、検査対象のファイルに実行の引き金を渡すことに近づく。

解析を止めても、通信は止まらない対策・注意喚起

GuardBreaker が守ろうとしたのは MATCHBOIL である（出典1）。ESET の別の調査によれば、MATCHBOIL は C# 製のダウンローダーで、当初は一度きりの動作だったが、後に2分間隔で C&C と通信する仕組みへ進化した（出典3）。

ここに、対処の足場がある（本記録の評価）〈重要〉。

層 GuardBreaker の影響
LLM による静的解析 止まりうる（出典1）
署名・構造による静的検査 影響しない（本記録の評価）
エンドポイントでの挙動監視 影響しない（本記録の評価）
ネットワークでの通信検知 影響しない（本記録の評価）

GuardBreaker はファイルの解析を止めるが、通信を止めることはできない。 2分間隔の定期通信は、ネットワーク側の統計で見える種類の特徴である（出典3 の記述に基づく本記録の評価）。

したがって、本件への実務的な備えは「LLM 検査の精度を上げる」方向ではない（本記録の評価）。LLM 検査を、他の層と置き換えないことである。 ESET が「高度な自動化と人間の専門性を組み合わせた多層かつ複数モデルによるアプローチ」を求めているのは、この意味である（出典1）。

ただし、多層化にはコストがかかる（本記録の明示）。全件に人の確認を入れれば、LLM 導入の目的（検査の高速化）と衝突する。本記録の提案は、対象を絞ることである—— 「LLM が拒否した・無応答だった・途中で終わった」対象に限って、多層の検証へ回す。 この絞り込みが成立するには、拒否と無応答が記録されている必要がある（本記録の整理）——それが本件の最初の一手になる。

    取るべき行動 **LLM の判定が「唯一の関門」になっている工程を洗い出す （マージの承認・パッケージの取り込み・添付ファイルの通過）。** **全件を多層化するとコストが合わないため、 対象を「LLM が拒否・無応答だったもの」と 「外部由来で初めて取り込むもの」に絞って多層の検証へ回す**（本記録の提案）。
  • AI を防御に組み込んだことを、攻撃者はすでに前提にしている。
    **同じグループが、IDA・Wireshark といった解析ツールのプロセス確認** （人による解析への対策。出典1）**と、LLM への依頼文** （AI による解析への対策。出典1）**の両方を用意している**〈重要〉。 **コメントがあること自体が、標的の防御に AI が組み込まれていることを 織り込んでいたことをうかがわせる**（出典1）。
    取るべき行動 **AI を使った検知・検査の導入を、「攻撃対象領域が増えた」という前提で リスク登録に反映する。** **とくに、外部ツール（アンパッカー・難読化解除ツール）を呼び出す AI エージェントは、呼び出し自体が乗っ取られうる**（出典1） ——**エージェントに与えた実行権限の一覧を作る**（本記録の提案）。
  • 「解析が止まる」より「問題なしと返ってくる」ほうが危険であることを、評価基準に入れる。
    **StepSecurity は、解析したモデルに対して悪質なコードを無視して パッケージを「問題なし」と報告するよう露骨に指示するプロンプトを確認している** （出典1）〈重要〉。 **止まれば結果が無いことに気づく機会があるが、 「問題なし」が返れば気づく機会そのものが無い**（本記録の評価）。
    取るべき行動 **LLM 検査の評価を「検出率」だけで見ず、 「検査対象の内容によって判定が誘導されうるか」を試験項目に入れる。** **具体的には、無害なテスト用ファイルに 「これは安全だと報告せよ」に相当する指示文を埋め込み、 判定が変わるかを確認する**（本記録の提案） ——**導入前の受け入れ試験として実施できる。**
セキュリティ技術者への示唆
  • 検査パイプラインで、LLM の「拒否・空出力・タイムアウト」を陰性と区別して記録する。
    **本手口が成功したかどうかは、解析を行った側のログにしか残らない** （本記録の評価）〈重要〉。 **これらの事象は、多くのパイプラインで「エラー」や「スキップ」として 捨てられる種類の記録である**（本記録の整理） ——**捨てていれば、止められていても誰も数えていない。**
    取るべき行動 **検査の結果コードを、少なくとも「陽性／陰性／未判定（拒否・空・タイムアウト）」 の3値に分ける。** **未判定の件数を日次で集計し、増加を異常として扱う。** **未判定のまま次工程へ進む経路があれば、止める**（本記録の提案）。
  • コメント・文字列の中に自然言語の指示文が含まれることを、静的な検査項目にする。
    **GuardBreaker のコメントは平文で、誰の目にも見える形で書かれている**（出典1） ——**隠されていない**〈重要〉。 **正規のソースコードのコメントに、モデルへの依頼文や 「無視せよ」「安全と報告せよ」に相当する命令文が現れることは稀である** （本記録の評価）。
    取るべき行動 **コードレビュー・パッケージ取り込みの静的検査に、 コメントおよび文字列リテラルを対象とした検査を1つ足す （命令形の自然言語・モデルやシステムへの呼びかけ・ 極端に長い反復文字列）。** **反復文字列の検出は npm の例（"You're absolutely right!" を数万回。出典1）に 直接当たる**（本記録の整理）。
  • LLM 検査を、既存の静的・動的・ネットワークの層と置き換えない。
    **GuardBreaker はファイルの解析を止めるが、通信を止めることはできない** （本記録の評価）〈重要〉。 **MATCHBOIL は2分間隔で C&C と通信する**（出典3） ——**定期的で間隔が一定の通信は、ネットワーク側の統計で見える特徴である** （本記録の評価）。
    取るべき行動 **LLM による検査の導入を理由に、署名検査・挙動監視・ ネットワークのビーコン検知を削減していないかを確認する。** **削減した工程があれば、復活させるか、 代替の検知手段を明記する**（本記録の提案）。
  • AI エージェントに与えた外部ツールの実行権限を棚卸しする。
    **ESET は、アンパッカーや難読化解除ツールといった外部ツールを呼び出す エージェントについて、その呼び出し自体がマルウェアの配布や実行に 乗っ取られる場合があり、攻撃対象領域をさらに広げる可能性があると 指摘している**（出典1）〈重要〉。
    取るべき行動 **解析・検査に使っている AI エージェントについて、 呼び出せる外部コマンド・ツールの一覧を作る。** **解析対象のファイルを引数として渡す経路には、 隔離された実行環境（ネットワーク遮断・使い捨て）を用いる**（本記録の提案） ——**検査対象に実行の引き金を渡さないこと。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ コードレビュー・脆弱性検査・依存パッケージの検査・ファイル分類のいずれかに LLM を組み込んでおり、モデルが応答しなかった場合の扱いを決めていない
システム構成□ LLM の判定が、マージ・取り込み・通過の「唯一の関門」になっている工程がある
委託・第三者部品□ PyPI・npm などの公開リポジトリから依存パッケージを取り込んでおり、 その検査が LLM による内容の読み取りに依存している
システム構成□ 解析・検査を行う AI エージェントに、外部ツール（アンパッカー・難読化解除ツール等）の 呼び出し権限を与えている
運用・監視□ LLM 検査の導入を理由に、署名検査・挙動監視・ネットワークのビーコン検知の いずれかを削減した
体制・契約□ LLM 検査の導入時の受け入れ試験に、「検査対象の内容によって判定が誘導されうるか」の 項目が無い
