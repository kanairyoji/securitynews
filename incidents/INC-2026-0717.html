INC-2026-0717Cloudflare Workers AI でKV混入

Cloudflare Workers AI の GLM-5.3 で、681,280トークンを超える長いプロンプトへの 応答155件に他の顧客の推論データが混入していた—— KVキャッシュプールの容量と公称コンテキスト長の不一致と、 SGLang の「拒否したはずのリクエストが生き残る」不具合が重なった

意図せぬ露出（設定不備等で外部から到達可能だった）脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設定不備設計・実装上の不備
初報: 2026年10月26日（Cloudflare による公表日） 最終更新: 2026年10月27日（本記録の作成時点）

Cloudflare は2026年10月26日、Workers AI で提供する GLM-5.3（@cf/zai-org/glm-5.3）にテナント分離の不具合があり、2026年8月27日から9月9日までの間、一部の応答に「直前に同じモデルへ送られた他の顧客のリクエストのデータ」が含まれていたと公表した（出典1）。影響を受けた応答は155件で、いずれも 681,280トークンを超える長さのプロンプトに対するものだった（出典1）。

この事案が読む価値を持つのは、原因が「攻撃」ではないからである（本記録の評価）。侵入も認証の突破も起きていない。起きたのは、GPU メモリ上の KVキャッシュのページが、前のリクエストの内容を保持したまま次のリクエストの注意（attention）に読まれたことである（出典1）。推論エンジンは性能のためにページをゼロ化しない—— その前提の上で、ページの所有権を追う責任はエンジン側にある（出典1）。

公表は、外部研究者の報告から47日後に、上流の SGLang と協調して行われた（出典1）。封じ込め自体は速い。インシデント宣言から40分以内にモデルを非公開にし、同日中に復旧している（出典1）。一方で、影響を受けた顧客への個別通知の有無、混入したデータの内容、影響を受けた顧客の数は、いずれも公表文に書かれていない〈未確定1〉〈未確定2〉〈未確定4〉。

攻撃は無い。正規のリクエストが、他人のメモリを読んだ原因・手口

この事案には侵入者がいない（本記録の整理）。起きたことは、推論基盤の内部でメモリのページの持ち主が入れ替わったことである。

前提を2つ押さえる（出典1）。

  1. KVキャッシュは固定サイズのページを持つ共有プールである。リクエストは受付時にページを割り当てられ、終了時に解放する。ページは解放時にゼロ化されない——次に使うリクエストが上書きするだけである。これは性能のために推論エンジンで一般的な設計であり、その代わりにページの所有権と寿命を追う責任がエンジン側に生じる。
  2. 分離（disaggregated）構成では、プリフィル用 GPU とデコード用 GPU が分かれている。プリフィルがプロンプトから KVキャッシュを作り、Mooncake 経由の RDMA でデコードへ渡す。このときページの所有権は、ノードをまたいで共有される。

ここに2つの不備が重なった（出典1）。

内容 単独では
設定 プール 681,280トークン ＜ 公称コンテキスト長 1,048,576トークン 超過分はエラーで返るはずだった
エンジン 拒否されたリクエストが受付キューを通過する 有効なリクエストは拒否されないので到達しない

成立の経路はこうである（出典1。表は本記録の整理）。

段階 起きたこと
ブートストラップ ルータがデコードへプロンプト長を伝え、デコードが8ページを予約
プリフィル受付 req.finished() が False なので、拒否済みのリクエストが受け付けられる
プリフィル実行 プロンプトは既に1トークンのプレースホルダに差し替わっており、自明な順伝播が走る
KV転送 1ページ分の KV だけを送り、「転送完了」を通知する
デコード受付 同じ finished() 判定なので、受け渡しを受理する
デコードの注意 予約済みの8ページすべてを読む。P0 以外は前のリクエストの中身
応答 HTTP 400 ではなく HTTP 200。prompt_tokens は長いプロンプトと一致し、文章は自然

最後の行が、この事案のいちばん重い部分である（本記録の評価）〈重要〉。応答は「壊れた出力」として現れなかった。 HTTP は 200 で、トークン数は整合し、文章は読める形をしていた。違っていたのは中身の持ち主だけである。

Cloudflare は、プールの大きさが設定値ではないことも明記している（出典1）。

「SGLang はこのプールの大きさを、モデルの重みを読み込んだ後に残った GPU メモリから起動時に決める。モデルの公称コンテキスト長は別の設定値である。両者を一致させる仕組みは無く、一致を確認するのは我々の仕事である」（出典1。原文英語。訳は本記録）

「一致させる仕組みが無い」ことが、この構成の既定の状態である（本記録の評価）——同じエンジンを同じ構成で使う配備は、同じ前提の上にある。

検証は通っていた——HTTP 200 とトークン数の整合を見ていたため発覚の端緒

公開前の検証について、Cloudflare は次のように書いている（出典1）。

「公開前の試験では、長文のベンチマークにおいて成功を示す HTTP ステータスコードと、エラーフレームを含まないストリーミング本体を観測した。エンジンが、KVキャッシュのプールと要求されたコンテキスト窓の差を、ストリーミングか何らかの仕組みで穏当に処理できるものと想定した」（出典1。原文英語。訳は本記録）

この想定は、観測によって裏付けられていた（本記録の整理）。不一致は認識されていた。長文の試験は成功していた。したがって「エンジンが何とかしている」と読むことに矛盾は無かった。

矛盾が無かった理由は、検証項目の選び方にある（出典1）。

  • 見ていた: HTTP のステータスコード、エンジンの性能（スループット・遅延）
  • 見ていなかった: モデルの出力内容とその一貫性

本件の不具合は、見ていた項目すべてで「正常」を返す（本記録の評価）〈重要〉。ステータスは 200、prompt_tokens は長いプロンプトと一致、しかも8ページ分のプリフィルにかかるはずの時間よりも応答が速い（出典1）——速いことは、性能の指標としては「良い」と読める。

対策として Cloudflare が挙げているのは、検証の追加ではなく検証の対象の変更である（出典1）。

「いまは、稼働中のエンジンから KVプールの大きさを取得し、コンテキスト長と直接突き合わせている。応答コードから推測することはしない」（出典1。原文英語。訳は本記録）

ここが、自前で推論基盤を運用する国内の読者にそのまま移せる部分である（本記録の評価）。「エラーが返らないこと」を正常の根拠に使うと、本件のように『正常に見える誤り』は検証を通過する。

155件は特定できている。それでも、通知のことは書かれていない未確定事項

公表文には、顧客への通知に関する記述が無い（本記録の確認）〈未確定1〉。

これを「書き忘れ」として読み流せない理由がある（本記録の評価）。

  • 155件という確定値が出ている（出典1）——どのリクエストが影響を受けたかを特定できているという意味である。
  • しきい値（681,280トークン）も出ている ——影響範囲の判定基準が明示されている。
  • 自社の検証分と研究者の分を除外した後の数である（出典1）——個々のリクエストの属性まで見分けられている。

事案の詳細

影響を受けたサービス**Cloudflare Workers AI 上の GLM-5.3（`@cf/zai-org/glm-5.3`）のみ**（出典1）。 **「We have confirmed that no other model hosted on Workers AI was affected.」 （Workers AI で提供する他のモデルに影響が無いことを確認した）** （出典1。原文英語。訳は本記録）。 構成は SGLang の分離（disaggregated）配備で、 **プリフィル用 GPU 群がプロンプトを処理して KVキャッシュを作り、 それを Mooncake 経由の RDMA でデコード用 GPU 群へ引き渡す**（出典1）。
直接原因**2つの不備の重なりである**（出典1）。 ①**設定**: プリフィル側の KVプールが 681,280トークン、公称コンテキスト長が 1,048,576トークンで一致していなかった。 ②**エンジン**: プールに収まらないプロンプトを SGLang のスケジューラは拒否し、 `Req.set_finish_with_abort` でクライアントへ返すエラーを記録したうえで プロンプトを1トークンのプレースホルダに差し替える。 **ところが拒否は `to_finish` に入り `finished_reason` には入らないため、 `finished()` は False を返し続けた**（出典1） ——**プリフィルとデコードの受付キューはいずれも `finished()` しか見ていなかったので、 拒否されたリクエストが「生きている」として受け付けられた。** 結果、**プリフィルは1トークン分の KV だけを作って「転送完了」を通知し、 デコードは予約済みの8ページすべてを読んで応答を生成した**（出典1） ——**P0 以外のページには、前のリクエストの内容が残っていた。** **単一ノード構成ではプレースホルダがそのまま流れてクライアントにエラーが返るため、 この不具合は分離構成でのみ顕在化した**（出典1）。

緩和策
数え方: **KVプールの容量を公称コンテキスト長の約2倍（約204万トークン）に拡大し、 有効なリクエストが拒否の経路に入らないようにする**（出典1）。　副作用: **GPU メモリをプールに寄せるため、他の用途に使える余地が減る**（本記録の評価）。 **Cloudflare は GLM-5.2 と同じ設定に合わせることで余裕を作ったとしており**（出典1）、 **設定の自由度を下げることで安全側に寄せた形である。** **「これだけで不具合は踏まれなくなる」と書く一方、 「プールの大きさだけに頼るのは脆い」とも書いている**（出典1。訳は本記録）。
数え方: **拒否を抱えたリクエストを、ブートストラップ・割り当て・KV転送の前に 受付キューで退場させる（本来のエラーを付けて返す）**（出典1。上流 #38704／#38935／#36988）。　副作用: **受付の判定が1段増えるため、受付経路に手が入る**（本記録の評価）。 **Cloudflare が上流へ提案した #38704 では、 デコード側が「転送されたトークン数が予約した数と一致するか」も検証する**（出典1） ——**検証を増やせば、その分だけ正常系の処理も増える。**
数え方: **転送ごとの KVチェックサム（`--disaggregation-enable-kv-checksum`）と KVカナリア（`--kv-canary`）で、汚染を検知・記録する**（出典1）。　副作用: **いずれも既定では有効にならない設定であり、 KVカナリアの対応はすべてのモデル構造に及んでいない**（出典1）〈重要〉。 **検知の仕組みが「オプション」である限り、 同じ事故は設定を入れていない配備で再発しうる**（本記録の評価）。 **ページを解放時にゼロ化する案（#46435）は、 性能への影響のため本公表の時点でまだ下書きである**（出典1） ——**根本的な対策ほど性能と衝突する。**
数え方: **配備の変更を出す前に、稼働中のエンジンから KVプールの大きさを取得し、 コンテキスト長と直接突き合わせる**（出典1）。　副作用: **確認の工程が増え、配備の速度は落ちる**（本記録の評価）。 **ただし本件で欠けていたのはまさにこの工程である** ——**「HTTPのステータスコードと長文時の性能しか検証しておらず、 モデルの出力と一貫性を検証していなかった」と Cloudflare は書いている** （出典1。訳は本記録）〈重要〉。
