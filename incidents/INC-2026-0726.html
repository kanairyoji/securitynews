2026年10月27日、JPCERT/CC が国産Wikiシステム GROWI の脆弱性3件をJVN#51223238 として公表しました（出典1）。3件とも「認可処理の回避」です。ログインできる人が、見てはいけないページの中身を読めたり、見るだけの人が中身を書き換えられたりします。 修正は v8.0.7 です（出典1・2）。

1件目・CVE-2026-105272（CWE-639／CVSS v4.0 2.3・v3.0 4.2）。 影響は v3.2.10 から v8.0.6 まで。 「当該製品にログイン可能な攻撃者によって、閲覧権限のないページの本文およびコメントが取得される」（出典1。原文日本語を引用）。仕組みは、自分が見られるページのIDと、見られないページのリビジョンIDを組み合わせて渡すことです（出典3。原文英語を訳出）。

2件目・CVE-2026-109848（CWE-639／CVSS v4.0 2.3・v3.0 4.2）。 影響は v4.5.5 から v8.0.6 まで。 「閲覧権限のないページの本文が取得され、自身が編集可能なページに保存される」（出典1。原文日本語を引用）。対象は POST /_api/tags.update と PUT /_api/v3/page です（出典4。原文英語を訳出）。

3件目・CVE-2026-115624（CWE-862／CVSS v4.0 6.9・v3.0 5.3）。 影響は v7.0.0 から v8.0.6 まで。 「閲覧のみ許可されているユーザ（またはゲストユーザ）、および承認待ち・停止中・招待中のユーザにより、ページの下書きが書き換えられる」（出典1。原文日本語を引用）。

本記録が要点と見たのは、次の4点です。

  • 3件に共通する間違いが、ひとつの文で言える。 「そのページを見てよいか」は確かめているのに、「一緒に渡されたリビジョンが、そのページのものか」を確かめていない（出典3・4。整理は本記録）。3件目は、認可の条件が「閲覧できるか」だけで、「編集してよいか」が入っていなかった（出典5。整理は本記録）。別々の機能に出た3件ではなく、同じ考え違いが3か所に出たものである（本記録の評価）。
  • 改ざんの痕跡が、改ざんしていない人の名前で残る。 ゲストは保存APIで弾かれるので自分では版を作れないが、書き込んだ内容は「編集中の下書き」として残り続ける（出典5。原文英語を訳出）。あとで正規の利用者が保存すると、その内容がその利用者の名前でページ履歴に入る（出典5）。履歴を見ても誰が入れたのか分からない形になる（本記録の評価）。
  • CVSS の 2.3 を「小さい」と読むと、社内Wikiでは判断を誤る。 1件目・2件目の CVSS v4.0 は 2.3、v3.0 でも 4.2 である（出典1）。低い理由は AT:P（攻撃前提条件が要る＝リビジョンIDを知っている必要がある）とPR:L（ログインが要る）である（出典1。整理は本記録）。ただし GitHub 側の勧告は「MongoDB の ObjectId は設計上そもそも秘密ではない」と明記している（出典3・4。原文英語を訳出）—— AT:P の前提は、見た目ほど高くない（本記録の評価）。
  • 同じ3件が、英語と日本語で別の名前を持っている。 GitHub 側の勧告3本（GHSA-m72c-xgjf-56ww／GHSA-pqx5-gx68-83h4／GHSA-3v2v-8q3r-mhm4）はいずれも「No known CVE」と表示しており、JVN が付けた CVE 番号が載っていない（出典3・4・5。本記録の確認）〈齟齬1〉。どの GHSA がどの CVE かは、影響バージョン範囲と記述の一致から本記録が対応づけた（出典1・3・4・5）〈齟齬2〉。

CWE-639 の2件はこうである——リクエストは「ページID」と「リビジョンID」の2つを受け取る。実装はページIDへのアクセス権だけを確認し、渡されたリビジョンがそのページのものかを確認していなかった（出典3・4。原文英語を訳出）。だから「自分が見られるページのID」＋「見られないページのリビジョンID」という組み合わせが通ってしまう。

CWE-862 の1件は、確認する項目そのものが足りていなかった——同時編集の接続は「そのページを閲覧できるか」を確認していたが、「編集してよいか」を確認していなかった（出典5。原文英語を訳出）。

言い換えると、2件は「権限を確認する対象を間違えた」、1件は「確認する権限の種類を間違えた」（本記録の整理）。どちらも、認可の判定がリソースの単位と一致していないという同じ形をしている（本記録の評価）。

修正の内容もこれに対応している。「リビジョンは、提供されるページに属する場合にのみ使用される」「ページ更新APIと同じ認可（ログイン済み・アクティブ・閲覧専用でない）を既存の閲覧権限の確認に加える」（出典3・5。原文英語を訳出）。

改ざんの痕跡が、改ざんしていない利用者の名前で残る被害規模・影響範囲

3件のうち CVSS v4.0 が最も高いのは CVE-2026-115624（6.9）である（出典1）。だが本記録が重く見たのは点数ではなく、帰結の形である（本記録の評価）。

GitHub 勧告はこう説明している（出典5。原文英語を訳出）。

ゲストは版を直接保存できない。ページ更新APIが拒否するためである。しかし、投入された内容はページの編集中の下書きとして残る。あとで正規の利用者が保存すると、その内容はその利用者の名前でページ履歴に確定する。

つまり攻撃者は「保存」という最後の一歩を、正規の利用者に踏ませる（本記録の整理）。履歴に残る作成者は、何もしていない人の名前である。

これは社内Wikiでは具体的な困りごとになる（本記録の評価）。

  • 事後に「誰が入れたか」を履歴から追えない。 作成者欄が別人を指している。
  • 指された人は、自分が書いていないことを証明しにくい。下書きの書き換えはサーバ側の同時編集セッション上の出来事であり、利用者の手元には痕跡が無い。
  • 手順書・設定値・連絡先を置いているWikiでは、内容の改変が業務に直結する。「Wikiの記述が間違っていた」事故として処理され、脆弱性の悪用だと気づかれない可能性がある。

ゲストアクセスを「拒否」にすれば未ログインのゲストは止まる（出典2・5）。止まらないのは、ログイン済みの閲覧専用ユーザと、承認待ち・停止中・招待中のユーザである（出典5。原文英語を訳出）—— 後者は「もう使えないようにしたつもりの人」である（本記録の評価）。停止したアカウントが、閲覧権限が残っている限り下書きを書き換えられる。

「ユーザ登録を無効にしても緩和されない」とも明記されている（出典5。原文英語を訳出）。

CVSS 2.3 の2件を「小さい」と読むと、社内Wikiでは判断を誤る評価・解釈

CVE-2026-105272 と CVE-2026-109848 の CVSS v4.0 基本値は 2.3 である（出典1）。v3.0 でも 4.2 で、脆弱性管理のダッシュボード上では「低」に入る値である。

CVSS:4.0/AV:N/AC:L/AT:P/PR:L/UI:N/VC:L/VI:L/VA:N/SC:N/SI:N/SA:N

値を押し下げているのは AT:P と PR:L である（整理は本記録）。

  • PR:L — ログインできるアカウントが要る。
  • AT:P — 攻撃に前提条件が要る。この前提とは「対象のリビジョンIDを知っていること」である。

ところが GitHub 勧告は、その前提についてこう書いている（出典3・4。原文英語を訳出）。

MongoDB の ObjectId は設計上そもそも秘密ではないため、見た目より推測しやすいことがある。同じプロセスが近い時刻に生成したIDは、さらに推測が容易になりうる。

ObjectId は時刻・機器識別子・カウンタから作られる構造を持つ（技術的背景。本記録の整理）。ランダムな秘密値ではない。

そして PR:L の「ログインできる人」とは、社内Wikiにおいては社員全員である（本記録の評価）。閲覧権限で区切っているページ——人事・法務・経営会議・特定プロジェクト——は、「社員には見せない」ために区切ってある。 その壁を越えられる脆弱性に対して、「ログインが要るから低リスク」という評価軸はうまく働かない（本記録の評価）。

さらに、読み取り側（CVE-2026-105272）は痕跡を残さない（出典3。原文英語を訳出）。スコアが低く、検知もできない組み合わせである。

本記録の整理はこうである—— CVSS は「製品の脆弱性の一般的な深刻度」を測る尺度であり、「自組織でその情報が漏れたときの重さ」は測らない。 後者は、そのWikiに何を置いているかで決まる。

暫定回避策は「ゲストアクセスの拒否」だが、止まるのは3つの経路のうち1つだけである対策・注意喚起

株式会社GROWI の告知は、すぐに更新できない場合の措置として次を挙げている（出典2）。

  • 管理画面 /admin/security でゲストアクセスを「拒否」にする
  • ゲストが閲覧できるページの下書きは、保存前に内容を確認する

ここで取り違えやすいのは、「拒否」が何を止めるかである（本記録の注意）。

GitHub 勧告は CVE-2026-115624 に到達できる3つの経路を書き分けている（出典5。原文英語を訳出）。

経路 ゲストアクセスを「拒否」にすると
未ログインのゲスト（閲覧可能なページ） 止まる
ログイン済みの閲覧専用ユーザ（閲覧できるページすべて） 止まらない
ログイン済みの非アクティブユーザ（承認待ち・停止中・招待中） 止まらない

勧告自身が「部分的にしか助けにならない」と書いている（出典5。原文英語を訳出）。残る2経路に対する措置として挙げられているのは、ゲスト・閲覧専用ユーザ・非アクティブユーザが閲覧できるページを絞ることである（出典5）。

本記録の評価では、これは暫定措置としても使いにくい—— 閲覧範囲を絞ることは、Wikiを使う目的そのものと衝突する。 実務上は「更新するまでの数日を凌ぐ」以上のことはできない。

そして、更新そのものには障害が少ない（本記録の評価）—— 修正版 v8.0.7 の番号は一次資料3経路すべてに明記されており（出典1・2・3・4・5）、どの版が安全かを利用者が判断できる。 やるべきことは更新であって、回避策の精査ではない。

報告したのは開発者自身で、JPCERT/CC は周知の場として使われている発覚の端緒

JVN の末尾にはこう書かれている（出典1。原文日本語を引用）。

この脆弱性情報は、製品利用者への周知を目的に、開発者がJPCERT/CCに報告し、JPCERT/CCが開発者との調整を行いました。

外部の研究者が報告したのではなく、開発者自身が報告している（本記録の整理）。GitHub 勧告3本の公開者も開発元の人物であり、Credits 欄に第三者の記載は無い（出典3・4・5。本記録の確認）。

発見の経緯は書かれていない〈未確定4〉——自社のコード監査で見つけたのか、利用者からの指摘があったのかは分からない。

同じ製品では2026年8月28日にも認可の不備2件が公表されている（JVN#42348352・CVE-2026-53620／CVE-2026-68951・修正 v8.0.1・出典6）。対象はブックマーク関連APIで、今回とは別の機能である（本記録の確認）。ただし原因の系統は同じ（認可処理の不備）であり、2か月のあいだに同系統の脆弱性が5件公表されたことになる（出典1・6。整理は本記録）。

本記録はこれを「製品が危ない」とは読まない（本記録の判断）—— 認可の不備を自分で探して公表している状態と、探していないから出てこない状態は、外から見分けられない。 判断材料になるのは、同じ箇所の再発があるかどうかである ——今回の3件は、8月の2件とは別の機能である。

同じ3件が、英語と日本語で別の名前を持っている評価・解釈

本記録が GitHub の勧告一覧を確認した時点（2026年10月27日）で、3本の勧告はいずれも 「No known CVE」 と表示されていた（出典3・4・5。本記録の確認）〈齟齬1〉。

一方、JVN と株式会社GROWI の告知は3つの CVE 番号を示している（出典1・2）。

つまり同じ3件の脆弱性が、経路によって別の識別子で流れている（本記録の整理）。

  • JVN・自社告知 → CVE-2026-105272／CVE-2026-109848／CVE-2026-115624
  • GitHub 勧告 → GHSA-m72c-xgjf-56ww／GHSA-pqx5-gx68-83h4／GHSA-3v2v-8q3r-mhm4（CVE なし）

どの GHSA がどの CVE に当たるかは、資料に書かれていない〈齟齬2〉。本記録は影響バージョン範囲（v3.2.10／v4.5.5／v7.0.0）と影響の記述の一致から対応づけたが、これは推定である（本記録の明示）。

これが実務で効くのは、脆弱性管理の突合のしかたによる（本記録の評価）。

  • CVE を鍵にして検索する運用（SBOM・脆弱性スキャナの CVE 照合、JVN/NVD の購読）からは、JVN 経由で3件が見える。
  • GitHub の Dependabot・GHSA を見ている運用からは3件が見えるが、CVE 番号では引けない。
  • 両方を見ていない運用（提供元のサイトだけを見る）では、自社告知に載っているので見える（出典2）。

本記録の整理では、今回は3経路すべてに情報が出ているため「どこを見ても気づける」状態である（本記録の評価）。問題は、同じ事象を2つの識別子体系で数えると、自組織の脆弱性台帳の上で件数が合わなくなることである。 なお GHSA への CVE 付与は後から行われることがあり、これは2026年10月27日時点の状態の記録である（本記録の留保）。

悪用されたかどうかは、公表されていないうえに確認もできない未確定事項

JVN・自社告知・GitHub 勧告3本のいずれも、悪用の観測に触れていない（出典1〜5。本記録の確認）〈未確定1〉。「悪用されていない」と書かれているわけでもない。

そして CVE-2026-105272 については、確認する手段そのものが無い（本記録の評価）。GitHub 勧告は「読み取りは痕跡を残さない」と明記している（出典3。原文英語を訳出）。

運用者が自組織について言えるのは、せいぜい次の範囲である（本記録の整理）。

  • 書き込み側（CVE-2026-109848）——覚えのない内容が増えた版がページ履歴に残る。Slack 通知の差分にも流れる（出典4）。過去の履歴を見れば、痕跡が残っている可能性はある。
  • 同時編集（CVE-2026-115624）——確定した版の作成者は正規の利用者の名前である（出典5）。「その人が書いた覚えのない内容」としてしか現れない。
  • 読み取り側（CVE-2026-105272）—— 確認できない。

したがって、更新後に「影響があったか」を調べる作業は、3件のうち1件半ぶんしか成立しない（本記録の評価）。これは GROWI に限った話ではなく、読み取りの監査ログを持たないアプリケーション全般に当てはまる。

緩和策
手順: **GROWI を v8.0.7 以降へ更新する**（出典1・2・3・4・5）。　副作用: **社内Wikiは業務時間中ほぼ常時使われるため、 更新のための停止窓を取りづらい**（本記録の評価。出典1〜5 は運用影響に触れていない）。 **オンプレミス運用では、更新の判断と実施が同じ組織の中にある ——つまり誰も代わりにやってくれない**（本記録の評価）。
手順: **すぐに更新できない場合、管理画面 `/admin/security` で ゲストアクセスを「拒否」にする**（出典2・5）。　副作用: **止まるのは未ログインのゲストだけである**（出典5。原文英語を訳出）—— **ログイン済みの閲覧専用ユーザと非アクティブユーザ （承認待ち・停止中・招待中）は、設定が「拒否」でも下書きを書き換えられる** （出典5）。 **また、社外や未ログイン利用者への公開を前提にしている GROWI では、 「拒否」にすると公開そのものが止まる**（本記録の評価）。
手順: **ゲスト・閲覧専用ユーザ・非アクティブユーザが閲覧できるページを絞る** （出典5。原文英語を訳出）。　副作用: **閲覧範囲を絞ることは、Wikiの目的（情報を共有すること）と 正面からぶつかる**（本記録の評価）。 **暫定措置として許容できるかは、そのWikiが何のためにあるかで変わる。**
手順: **公開されているページの編集中の下書きを、保存する前に内容を確認する** （出典2・5）。　副作用: **保存のたびに人が目で見る運用は長くは続かない**（本記録の評価）。 **これは更新までの時間を稼ぐための措置であり、対策ではない。**
手順: **承認待ち・停止中・招待中のユーザを棚卸しし、不要なものを削除する** （本記録の提案。出典5 の前提条件からの導出）。　副作用: **招待の取り消しは、導入途中の利用者の手続きをやり直させることになる** （本記録の評価）。

CISO・経営層への示唆
  • CVSS が低い脆弱性でも、「自社のWikiに何が置いてあるか」で重さは変わる。
    **CVE-2026-105272・CVE-2026-109848 の CVSS v4.0 は 2.3（v3.0 で 4.2）である** （出典1）。 **値を押し下げているのは「ログインが要る」（PR:L）と 「リビジョンIDを知っている必要がある」（AT:P）だが、 社内Wikiにおいて「ログインできる人」は社員全員である**（本記録の評価）。 **閲覧権限で区切っているのは、まさに社員に見せないためである。**
    取るべき行動 **自組織のWiki・ナレッジ基盤で「閲覧権限だけで守っている情報」を棚卸しする。** 人事・法務・経営会議・特定プロジェクトの資料が、 同じシステムの中で権限だけで区切られているなら、 認可回避の脆弱性は CVSS の値と無関係に重い。 **CVSS の閾値（例: 7.0 以上を対応する）で切る運用に、 「認可回避」を例外として入れるかを決める。**
  • 「停止したアカウント」は、閲覧権限が残っている限り攻撃経路として残る。
    **CVE-2026-115624 に到達できるのは、未ログインのゲストだけではない**（出典5）。 **ログイン済みの閲覧専用ユーザ、および承認待ち・停止中・招待中の 非アクティブユーザも、閲覧権限があれば下書きを書き換えられる** （出典5。原文英語を訳出）。 **ゲストアクセスを「拒否」にしても、この2経路は止まらない**（出典5）。
    取るべき行動 **アカウントの「停止」が何を止めているのかを、システムごとに確認する。** ログインを止めているのか、権限を剥がしているのか、 招待の途中で止まっている状態がどう扱われるのか。 **退職・異動・契約終了の手続きに「招待中・承認待ちの取り消し」を入れる。** **停止と削除の違いを、運用の規程に書き分ける。**
  • 読み取りの監査ログを持たないシステムでは、「影響があったか」を事後に答えられない。
    **GitHub 勧告は CVE-2026-105272 について「読み取りは痕跡を残さない」と 明記している**（出典3。原文英語を訳出）。 **更新したあとに「漏れたか」を調べようとしても、材料が無い**（本記録の評価）。 **公表資料に悪用の記載が無いことは、悪用が無かったことを意味しない**〈未確定1〉。
    取るべき行動 **社内の主要なアプリケーションについて、 「読み取りが記録されているか」を一覧にする。** 記録されていないシステムで機密情報を扱っているなら、 脆弱性が出たあとに言えることは「分からない」だけになると、先に経営に伝えておく。 **事後に答えが出ないことを、脆弱性対応の優先順位に反映させる。**
  • 同じ脆弱性が、CVE と GHSA という2つの名前で流れることがある。
    **GitHub 勧告3本はいずれも「No known CVE」と表示されており、 JVN が付けた3つの CVE 番号が載っていない** （出典3・4・5。本記録の確認・2026年10月27日時点）〈齟齬1〉。 **CVE を鍵にした突合では、GitHub 側の記述（機序・前提条件・ 回避策の効く範囲）に辿り着けない**（本記録の評価）。
    取るべき行動 **自組織の脆弱性情報の入口を数える。** JVN・NVD・提供元サイト・GitHub（Dependabot／GHSA）のうち、 どれを見ているか。オープンソース製品を自組織で運用しているなら、 **GHSA 側も入口に加える。** **同じ事象が2つの識別子で入ってくるため、台帳で重複排除の規則を決めておく。**
セキュリティ技術者への示唆
  • 認可の判定は、リソースの単位と一致させる——「親が見えるか」で子を返してはいけない。
    **CWE-639 の2件は、ページIDへのアクセス権だけを確認し、 一緒に渡されたリビジョンIDがそのページに属するかを確認していなかった** （出典3・4。原文英語を訳出）。 **修正は「リビジョンは、提供されるページに属する場合にのみ使用される」である** （出典3）。 **これは GROWI 固有の問題ではなく、 親子関係を持つリソースを扱う API に共通する形である**（本記録の評価）。
    取るべき行動 **自組織のアプリで、リクエストが2つ以上のIDを受け取る箇所を洗い出す。** `pageId` と `revisionId`、`orderId` と `lineItemId`、 `projectId` と `taskId` のような組み合わせである。 **それぞれについて「後者が前者に属することを検証しているか」をコードで確認する。** **検証がテストで守られているかも確認する（属さないIDを渡して 403 になるテスト）。**
  • WebSocket・同時編集・リアルタイム同期の経路は、REST とは別に認可が必要である。
    **CVE-2026-115624 は、Yjs の同時編集接続が 「閲覧できるか」だけを確認し「編集してよいか」を確認していなかったもの** （出典5。原文英語を訳出）。 **ページ更新API では弾かれる利用者が、同時編集では通っていた**（出典5）。 **修正は、同時編集接続にページ更新APIと同じ認可を適用することである**（出典5）。
    取るべき行動 **REST API 以外の経路（WebSocket・SSE・GraphQL subscription・ 同時編集のセッション確立）について、認可の条件が REST と同じかを突き合わせる。** **認可の判定を1か所にまとめ、各経路がそれを呼ぶ形にする。** **経路ごとに条件を書いていると、片方だけ直る。**
  • 「保存できないから安全」とは限らない——下書きのような中間状態も攻撃面である。
    **ゲストはページ更新APIで弾かれ、自分では版を保存できない**（出典5）。 **それでも投入した内容は編集中の下書きとして残り、 あとで正規の利用者が保存した時点でその利用者の名前で履歴に確定する** （出典5。原文英語を訳出）。 **最後の一歩を正規の利用者に踏ませる形である**（本記録の整理）。
    取るべき行動 **下書き・一時保存・プレビュー・インポート待ちのキューなど、 「まだ確定していないデータ」の書き込み権限を確認する。** 確定前のデータに書けるなら、確定操作を通じて永続化されうると考える。 **確定の操作を行う利用者に、何を確定しようとしているかが見える形にする （差分の表示・直前の変更者の表示）。**
  • 識別子を「推測しにくいから秘密」として扱わない。
    **GitHub 勧告は「MongoDB の ObjectId は設計上そもそも秘密ではない」 「同じプロセスが近い時刻に生成したIDはさらに推測が容易になりうる」と 明記している**（出典3・4。原文英語を訳出）。 **CVSS の AT:P（前提条件が要る）は、この前提の強さを反映していない** （本記録の評価）。
    取るべき行動 **自組織のアプリで、IDを知っていることを前提にした防御がないかを確認する。** 連番・ObjectId・UUIDv1 は秘密値ではない。 **秘密にしたい値には、暗号論的に安全な乱数を使う。** **ただし「推測しにくいIDにする」ことは認可の代わりにならない ——認可の検証を入れることが本来の対策である。**
  • 更新のための停止窓を、脆弱性が出てから探さない。
    **3件すべてが v8.0.7 で修正され、修正版の番号は3経路すべてに明記されている** （出典1・2・3・4・5）——**判断に必要な材料は揃っている**（本記録の評価）。 **残るのは「いつ止めるか」だけである。** **社内Wikiは業務時間中ほぼ常時使われるため、 停止窓の調整が対応の律速になりやすい**（本記録の評価）。
    取るべき行動 **自組織で運用しているオープンソース製品について、 「緊急更新のための停止窓」を平常時に決めておく。** 誰が承認し、どのチャネルで利用者に告知し、何分まで止めてよいか。 **暫定回避策の精査に時間を使うより、更新を実行したほうが早いことが多い** ——今回はとくに、回避策が3経路のうち1経路しか止めない（出典5）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 社内Wiki・ナレッジ基盤で、機密度の違う情報を同一システムに置き、 閲覧権限（ページごとのACL・グループ）だけで区切っている

システム構成□ WebSocket・同時編集・リアルタイム同期の経路を持つアプリケーションを 運用または開発している

体制・契約□ オープンソース製品を自組織で運用しており、脆弱性情報の入口が JVN／NVD（CVE 起点）に限られている
