INC-2026-0731Sleipnir Mobile 偽アドレスバー

**JPCERT/CC と IPA は2026年10月27日、フェンリル株式会社の Android 向けブラウザ 「Sleipnir Mobile for Android」に、偽のアドレスバーなどを表示される脆弱性 （CVE-2026-109434・CWE-451）があることを JVN#90463048 として公表した。 3.9.0 より前のバージョンが対象で、細工されたWebページを開くとフィッシングの被害に あう可能性がある。修正版 3.9.0 は2026年10月15日にリリースされている。**

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年10月15日（フェンリルによる修正版 3.9.0 のリリース告知） 最終更新: 2026年10月28日（本記録の作成時点）

フェンリル株式会社が提供する Android 向けタブブラウザ 「Sleipnir Mobile for Android」に、 ユーザーインターフェースにおいて偽のアドレスバーなどを表示される脆弱性が 存在する（出典2）。 対象は 3.9.0 より前のバージョンで、CVE 番号は CVE-2026-109434、 CWE は CWE-451、CVSS v4.0 基本値 5.1／CVSS v3.0 基本値 4.3 である（出典2）。 当該アプリ上で細工されたWebページにアクセスすると、 フィッシングの被害にあう可能性がある（出典2）。 ベンダーは2026年10月15日に修正版 3.9.0 をリリースしており、 全画面表示に切り替わった際にアクセス中のドメインと全画面の終了方法を表示する 仕様に変更した（出典1）。 JVN での公表はその12日後の2026年10月27日である（出典2。本記録の算出）。 報告者は Fanda Dwi Aprilianto 氏で、製品開発者へ直接報告され、 調整を経て公表に至っている（出典2）。

時点は2つ公表されている。修正版 3.9.0 のリリースが2026年10月15日（出典1）、JVN#90463048 の公表が2026年10月27日（出典2）で、間隔は12日である（本記録の算出。figures 参照）。

この順序は、脆弱性情報の公表としては望ましい形である（本記録の評価）—— JVN を読んだ利用者は、その時点で対策（アップデート）を実行できる。手口の詳細が公表されていないこと〈未確定1〉も、修正前に悪用される余地を狭める方向に働く。

ベンダー側の告知も、変更点に CVE 番号を併記している（出典1）。リリースノートに CVE を書く例は多くない（本記録の整理）——利用者が「この更新は何を直したのか」を外部の情報と突き合わせられる。

偽のアドレスバーは、利用者が見て判断する仕組みでしか防げていない原因・手口出典 [1]

ベンダーの説明は次のとおりである（出典1）。

「全画面表示に切り替わった際、アクセス中のドメインおよび全画面の終了方法を表示するように改善 (CVE-2026-109434)」

直したのは、全画面表示中に表示元のドメインを利用者へ示す仕組みである（本記録の整理）。つまり修正後も、偽装された表示を見分けるのは利用者である（本記録の評価）〈重要〉——アプリ側が偽のアドレスバーの描画そのものを止めるのではなく、本物のドメインを併記して気づきやすくする設計である。

これは Web ブラウザの UI 偽装（UI Spoofing）に共通する限界で、ページ側の描画内容を制限できない以上、ブラウザが取れる手は「本物の情報を、ページが描けない場所に出す」ことに限られる（本記録の評価）。だからこそ、フィッシング対策を利用者の目視に依存させない層（フィッシング耐性のある認証、ドメインに紐づく資格情報）が必要になる。

「フィッシングの被害にあう可能性」は、悪用が観測されたという意味ではない未確定事項出典 [1] [2]

出典2 が述べているのは「当該アプリ上で細工されたWebページにアクセスすると、フィッシングの被害にあう可能性があります」である（出典2）。

これは想定される影響であり、実際の攻撃が観測されたという記述ではない（本記録の明示）〈重要〉。出典1・2 のいずれにも、悪用の観測・被害報告・標的型の攻撃に関する記載は無い〈未確定2〉。

本DBがこの区別を明示するのは、CVSS の数値（v4.0 で 5.1）と「フィッシングの可能性」という語が並ぶと、進行中の攻撃として読まれることがあるためである（本記録の整理）。本件で確認できるのは、脆弱性の存在と修正版の提供までである。

報告は国外の研究者から直接ベンダーへ届き、調整を経て公表された背景・過去事例出典 [1] [2]

出典2 は公表の経緯を次のように記している（出典2）。

「この脆弱性情報は、下記の方が製品開発者に直接報告し、製品開発者との調整を経て、製品利用者への周知を目的にJVNでの公表に至りました。報告者：Fanda Dwi Aprilianto 氏」

ベンダー側の告知でも、全画面表示機能に潜在していた UI Spoofing の脆弱性の報告者として同氏に謝意が示されている（出典1）。

報告日は公表されていない〈未確定4〉ため、受付から修正までの時間は測れない。測れるのは修正版リリースから JVN 公表までの12日だけである（本記録の算出）。受け付けから修正・公表までが滞りなく進んだ事案として読めるが、その期間の長さを本記録は評価できない（本記録の留保）。

CISO・経営層への示唆
  • UI 偽装の脆弱性は、CVSS が中程度でも、実害は「利用者が偽の画面に入力する」 形で出る。数値だけで優先度を決めると取り落とす。
    **本件の CVSS は v4.0 で 5.1、v3.0 で 4.3 であり、 機密性への影響は無しと評価されている**（出典2）〈重要〉—— **一方で想定される影響は「フィッシングの被害にあう可能性」である**（出典2）。 **フィッシングの成立は、認証情報の窃取や口座の被害に直結する** （本記録の評価）。
    取るべき行動 **脆弱性の優先度付けに「利用者が直接操作する画面に関わるか」の観点を加える。** **CVSS が中程度でも、ブラウザ・メールクライアント・認証画面に関わるものは 配布端末の更新を急ぐ対象に入れる。**
  • 目視で見分けさせる対策には上限がある。フィッシング対策の本体は、 利用者の判断に依存しない認証側に置く。
    **修正は「全画面表示に切り替わった際にドメインと終了方法を表示する」ことである** （出典1）——**見分けるのは利用者である**（本記録の評価）〈重要〉。 **ページ側の描画を制限できないブラウザでは、 これ以上の対策が構造的に難しい**（本記録の評価）。
    取るべき行動 **業務アカウントの認証を、ドメインに紐づく方式（パスキー・FIDO2）に寄せる。** **偽のアドレスバーに騙されても資格情報が別ドメインへ渡らない構成にする。**
  • 私用アプリを業務端末で許容しているなら、ブラウザの版は資産管理の対象になる。
    **対象は「3.9.0 より前のバージョン」であり、下限は示されていない**（出典2） ——**自動更新が無効な端末にどれだけ残るかは公表されていない**〈未確定3〉。 **国産のタブブラウザであり、業務端末に私物の選択で入っていることがある** （本記録の評価）。
    取るべき行動 **業務端末にインストールされているブラウザを棚卸しし、 標準ブラウザ以外の版も把握できる状態にする。** **把握できないなら、業務用の認証はその端末で行わせない。**
  • 自社製品の脆弱性をリリースノートで CVE 付きで示すベンダーは、 利用者の点検コストを下げる。調達の評価項目に入れる価値がある。

  • WebView やフルスクリーンAPIを使う自社アプリは、 全画面時に「どのドメインを表示しているか」を利用者に示せているか確認する。
    **本件の修正は、まさにこの表示を追加するものだった**（出典1）〈重要〉—— **全画面表示中にドメインが見えないと、ページ側が描いた偽の UI と区別できない** （本記録の整理）。

  • UI 偽装は、ページ側が描ける領域とアプリが保証する領域の境界の問題である。 境界を「ページが描けない場所」に持つ。

  • アプリの更新は「配布した」ではなく「適用された」で確認する。
