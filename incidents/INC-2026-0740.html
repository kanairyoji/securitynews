INC-2026-0740Authenticator窃取とDefender無力化

Microsoft 製品の「守る仕組み」そのものを無力化する2件の不備について、 2026年10月下旬に実証の情報が出そろった。 **1件目は Microsoft Authenticator（Android 版）の CVE-2026-80097（CWE-287・不適切な認証／Microsoft 評価 CVSS v3.1 8.6）である**—— **権限をひとつも要求しない悪性アプリが Teams などの正規アプリに成り代わり、 業務アカウントのアクセストークンを受け取れた**〈重要〉。 **原因は、外部から起動できる画面（`AccountChooserActivity`）が 呼び出し元の申告をそのまま信じていたことである**—— **署名の検証は存在したが、装う相手が端末に入っていれば必ず通る作りだった**。 **研究者（Enclave の Ofek Levin）が得たトークンには、 メールの読み書き・送信、ファイル・SharePoint・予定表への到達、 Teams のチャット送信、さらに認証方式とパスキーの登録・削除の権限が含まれていた**。 **修正は Authenticator for Android 6.2606.4246 で、CVE の公開は2026年9月8日。 実証の公表は2026年10月23日である**。 **2件目は Microsoft Defender の CVE-2026-45498 で、 一般権限のまま定義ファイルの更新を妨げて Defender を止められる**—— **2026年5月に修正済みで、同年5月20日に CISA の悪用確認済み脆弱性目録（KEV）に 収載されている**。 **2026年10月下旬、これを突く実証コード「UnDefend」の公開が国内で報じられた**〈重要〉—— **Huntress は2026年4月16日、実際の侵害の中で同ツールの実行を観測している**。

守る仕組みが、守る対象より弱い前提の上に立っていた。

2026年10月下旬、Microsoft の2つの保護機構について、実証の情報が出そろった（出典2・6）。どちらも修正済みの不備だが、どちらも「公開されている情報」が「ベンダーの記録」を追い越している（本記録の評価）〈重要〉。

1件目は Microsoft Authenticator（Android 版）の CVE-2026-80097 である（出典1）。

権限をひとつも要求しない悪性アプリが、Teams などの正規アプリに成り代わって、業務アカウントのアクセストークンを受け取れた（出典2）。

仕組みは単純である（出典2）。Authenticator は AccountChooserActivity という画面を外部から起動できる形で公開していた。 唯一の門は「呼び出し元が存在すること」だけで、呼び出し元の UID・パッケージ名・クライアント ID・リダイレクト URI・要求する権限範囲は、すべて攻撃者が申告した値だった。 署名の検証は存在した——しかしそれは、申告されたパッケージの署名から導いた URI と申告された URI を比べるものだった。 装う相手（Teams）が端末に入っていれば、本物の署名から本物の URI が導かれ、検査は必ず通る（出典2）。

Authenticator は本当の呼び出し元を知っていた（出典2）〈重要〉—— ただしそれは並行要求の管理に使われるだけで、信頼の判断には使われていなかった。

研究者（Enclave の Ofek Levin）が得たトークンの権限が、本件の重さを決めている（出典2）—— メールの読み書きと送信、ファイルと SharePoint と予定表への到達、Teams のチャット送信。さらに Authenticator 自身のクライアントとしては、利用者の認証方式の読み書きと、パスキーの作成・削除。

修正は Authenticator for Android 6.2606.4246 である（出典1・2）。CVE の公開は2026年9月8日、実証の公表は2026年10月23日である（出典1・2）。Microsoft は悪用を確認しておらず、「悪用の可能性は低い」と評価している（出典1）。

ただし利用者操作の必要性について、2つの資料は食い違っている〈齟齬1〉〈重要〉—— Microsoft は「利用者に Authenticator 上で認証の手続きを完了させる必要がある」とし、評価ベクタにも利用者操作あり（UI:R）を含める（出典1）。研究者は「業務アカウントで署名済みの状態にあること以外、利用者操作は不要だった」と述べている（出典2）。

2件目は Microsoft Defender の CVE-2026-45498 である（出典3・6）。

一般権限のまま、更新処理が作るファイルにロックを掛けて更新を妨げると、Defender の動作が停止する（出典6）。修正は2026年5月分の更新で出ており、CISA の悪用確認済み脆弱性目録（KEV）には2026年5月20日に収載されている（出典3・4）。

2026年10月下旬、これを突く実証コード「UnDefend」の公開が国内で報じられた（出典6）。Huntress は2026年4月16日、実際の侵害の中で同ツールの実行を観測している（出典5）〈重要〉—— ただしその報告は CVE-2026-45498 に言及していない〈齟齬3〉。

Defender の方は、止めるのではなく「更新させない」手口だった原因・手口

したがって監視すべきものが決まる（本記録の整理）。「Defender が動いているか」ではなく「Defender の定義が更新されているか」。 そして更新が止まっていた期間を特定し、その期間に何が実行されたかを突き合わせる。

    取るべき行動 **①マルウェア対策の定義の最終更新日時を端末ごとに集計し、 一定期間更新されていない端末を洗い出す指標にする。 監視対象は「動いているか」ではなく「更新されているか」。** **②更新が止まっていた期間を特定できるようにし、 その期間の他の記録（プロセスの実行・通信）を 突き合わせる手順を用意する。** **③マルウェア対策の異常を単独の事象として閉じず、 同時期の他の事象と併せて見る運用にする。**
  • **トークンを前提にした被害想定と、トークンの失効手順を持つ**
    **CVE-2026-80097 で得られるのはアクセストークンと リフレッシュトークンである**（出典2）〈重要〉。 **パスワードの変更では失効しない**（本記録の評価）。 **さらに、研究者が得た権限には 利用者の認証方式の読み書きと、パスキーの作成・削除が含まれていた**（出典2）—— **認証方式を操作されれば、 トークンの寿命を越えて入り直せる足場を作られうる**（本記録の評価）。 **本記録はこれを推定として明示する**——**出典2 はこの用途を述べていない。** **また、必要だった権限はゼロである**（出典2）〈重要〉—— **「怪しい権限を求めるアプリを入れない」という利用者教育は、 本件に効かない。**
    取るべき行動 **①トークンの一括失効（サインアウト・リフレッシュトークンの無効化）の 手順を用意し、実行にかかる時間と業務への影響を事前に測る。** **②利用者の認証方式とパスキーの登録・削除を監査の対象にし、 棚卸しの周期を決める。** **③被害想定を「パスワードが漏れた場合」で止めず、 「有効なトークンを持たれた場合」で作る。**
  • **提供元の記録と研究者の公表の両方を読む。食い違う箇所が判断の分かれ目になる**
    **CVE-2026-80097 では、利用者操作の必要性について 2つの資料が食い違っている**（出典1・2）〈齟齬1〉〈重要〉。 **Microsoft は「利用者に Authenticator 上で認証の手続きを 完了させるよう仕向ける」ことが必要とし、 評価ベクタにも利用者操作あり（`UI:R`）を含める**（出典1）。 **研究者は「業務アカウントで署名済みの状態にあること以外、 利用者操作は不要だった」と述べている**（出典2）。 **この差は打てる手を変える**（本記録の評価）—— **必要なら周知が緩和策になる。不要なら更新以外に手が無い。** **さらに、提供元の記録は本記録の確認時点でも 「公表済みか: いいえ」のままである**（出典1）〈齟齬4〉—— **実証は2026年10月23日に公表されている（出典2）。**
    取るべき行動 **①脆弱性の評価に、提供元の記録と 研究者・ベンダーの公表の両方を材料として入れる規則にする。** **②食い違いが見つかったときは、 緩和策の無い側を前提に扱う—— 誤りの代償が非対称である（効かない緩和策を信じるか、 不要な更新を急ぐか）。** **③自動化された取り込みが 提供元の「公表済みか」「悪用されたか」を 優先度の引き下げに使っていないか確認する。**
セキュリティ技術者への示唆
  • **呼び出し元の身元は、呼び出し元が選べない情報から取る**
    **CVE-2026-80097 の検証は、 「申告されたパッケージの署名から導いた期待値」と 「申告された値」を比べる作りだった**（出典2）〈重要〉—— **装う相手が端末に入っていれば必ず通る。** **そして Authenticator は、本当の呼び出し元を `getCallingActivity().getPackageName()` で知っていた**（出典2）—— **その値は並行要求の管理にしか使われず、 信頼の判断には使われていなかった。** **一般化するとこうである**（本記録の評価）—— **攻撃者が選べる値を、攻撃者が選べる値で検証しても検証にならない。 身元は OS・基盤が与える値（呼び出し元の UID・ 相互 TLS の証明書・署名付きの要求元）から取らなければならない。**
    取るべき行動 **①外部から呼べる入口について、 「身元をどこから取っているか」を1つずつ確認する。 要求の中身から取っているものがあれば、それが本件と同じ位置にある。** **②OS が与える呼び出し元の情報（Android なら呼び出し元の UID・ パッケージ名）を、信頼の判断に使う。** **③検証の関数が「必ず通る」経路を持たないか、 入力を攻撃者が選べる前提で読み直す。**
  • **外部に公開する画面・入口を最小にし、公開する理由を1つずつ説明できる状態にする**
    **本件の入口は `android:exported="true"` で公開された画面であり、 端末上のどのアプリからも起動できた**（出典2）〈重要〉。 **唯一の門は「呼び出し元が存在すること」だった**（出典2）—— **これは門ではない**（本記録の評価）。 **公開が必要な入口はありうる**（本記録の整理）—— **broker は他のアプリから呼ばれるための仕組みである。 問題は、公開することと、呼び出し元を信頼することを 分けていなかったことである。**
    取るべき行動 **①公開している入口（Android の exported な部品・ 公開 API・IPC の端点）を列挙し、 それぞれについて「誰が呼べるべきか」を書き出す。** **②「誰でも呼べる」ものには、 呼び出し元の検証を基盤の値で行う経路を付ける。** **③機微な応答（トークン・資格情報）を返す入口は、 公開の必要性を再検討する—— 本件では broker の応答が平文で呼び出し元に返されていた（出典2）。**
  • **保護機構が作るファイル・使うファイルは、保護対象の利用者から触れない場所に置く**
    **CVE-2026-45498 は、更新処理が作成するファイルに 一般権限でロックを掛けられる不備である**（出典6）〈重要〉。 **Huntress が観測したツールは、 定義ファイルの更新先ディレクトリを監視し、 新規・更新されたファイルを Defender が使う前に開いてロックしていた**（出典5）。 **さらに、予備の定義ファイルもロックし、 サービスの停止を待って再起動時の読み込みを妨げていた**（出典5）。 **一般化するとこうである**（本記録の評価）—— **保護を提供する仕組みが使う資源（ファイル・ソケット・ 共有メモリ）に、保護される側が干渉できてはならない。 干渉できれば、保護は止められる。**
    取るべき行動 **①自社の常駐サービス・保護機構が使うファイルの 置き場と権限を確認し、 一般利用者が開ける・ロックできる場所にないかを見る。** **②処理の途中の状態（一時ファイル・作業領域）も対象にする—— 本件で狙われたのは更新処理が作るファイルである。** **③重要な処理が「ファイルを開けなかった」とき、 黙って停止するのではなく異常として記録する作りにする。**
  • **「失敗したら止まる」処理に、記録と復帰の経路を付ける**
    **本件の手口が有効なのは、 更新が妨げられたときに Defender が停止するためである**（出典6）〈重要〉。 **さらに、ロックは開いたハンドルで保持されるため、 プロセスが終了すれば解放され Defender は復帰する**（出典5）—— **すなわち、調べたときには正常に戻っている**（本記録の評価）。 **残るのは「定義の更新が一定期間行われていない」という記録だけである。** **設計の観点では2つの欠落がある**（本記録の整理）—— **①更新の失敗が、停止という結果だけで現れていた。 ②失敗の記録が、外から読める形で残っていない （本記録はこの点を確認していない）。**
    取るべき行動 **①重要な処理の失敗を、状態の変化（停止）ではなく 記録として残す。停止は結果であり、原因ではない。** **②「最後に成功した時刻」を外部から読めるようにする—— これが本件で唯一残る痕跡である。** **③失敗が続いたときに自動で復帰を試みる経路と、 それが失敗したときに人へ届く経路を分けて用意する。**
