**本件に侵害事案は存在しない**（本記録の明示）〈重要〉—— **公表されたのは脆弱性であり、被害の報告ではない**（出典1・6・7）。 **CISA は「これらの脆弱性を直接狙う公開された悪用は、 現時点で CISA へ報告されていない」と述べている**（出典1。原文英語を訳出）。 **以下は、公表された内容が攻撃のどの段階に当たるかを整理したものである** （整理は本記録。出典1・6・7 は攻撃の実例を示していない）。

EPICS Base 側の時間の並びは、公開された記録から追える。

RSRV（Channel Access のサーバー実装）のメッセージ検証を加える変更は2026年7月19日に提案され、2026年7月23日に 7.0 ブランチへ取り込まれた（出典3）。提案には 「非公開の脆弱性報告への対応であり、類似の非公開でない報告があったため早めに公開した」 と記載されている（出典3。原文英語を訳出）。pvDataCPP 側の逆シリアライズ検査は2026年8月10日に取り込まれた（出典5）。

リリース 7.0.11 が公開されたのは2026年10月27日である（出典2）。取り込みからリリースまで96日である（本記録の算出。figures 参照）。同じ日に CISA の勧告 ICSA-26-300-01 が出て、CVE 4件と CVSS v3.1 9.8 が明らかになった（出典1）。

本記録がこの並びを問題として記録するのは、「コードが直っている」ことと「利用者が直せる」ことが別だからである（本記録の評価）〈重要〉。修正は公開リポジトリにあり、差分は誰でも読める。一方で、利用者が入手できるリリースには含まれていなかった。

さらに、リリース 7.0.11 の告知には security fix である旨もCVE 番号も書かれていない（出典2。本記録の確認）〈齟齬4〉。更新すべき理由を知る手段は、勧告（出典1）側にしか無い。 これは INC-2026-0536（Collabora Online の CVE-2026-110447）と同じ型である（本記録の評価）——あちらは修正が攻撃の翌日に出たが security fix と告知されず、その間に悪用が続いた。本件に悪用の報告は無い（出典1）—— だが「告知しない」という選択の構造は共通している。

CISA が緩和策に挙げた3つの参照先のうち1つは、コードの修正ではない評価・解釈

出典1 は、4件すべてに同じ緩和策を並べている。7.0.11 への更新と、3つのリポジトリ変更への参照（epics-base の #934・#937、pvDataCPP の #109）である（出典1）。

本記録が3つを確認したところ、#937 は「SECURITY.md ファイルの追加」であり、コードの修正ではなかった（出典4。本記録の確認）〈齟齬3〉。SECURITY.md は脆弱性の報告先・受付方針を記した文書である。プロジェクトが報告の受け口を整えたこと自体は前進である（本記録の評価）—— しかし「緩和策」の一覧に並ぶと、読んだ運用者は「当てるべき修正が3つある」と受け取る。

もう一つ、対応関係が書かれていない点がある（本記録の整理）。pvDataCPP の変更（出典5）は別のリポジトリで、master ブランチへ取り込まれている（出典5。本記録の確認）。EPICS Base 7.0.11 に更新すればこの変更も入るのかは、出典1 にも出典2 にも書かれていない〈未確定3〉。

運用者にとっての含意は具体的である（本記録の評価）〈重要〉—— 「7.0.11 にした」で4件すべてが解消するのかを、公表資料だけでは確認できない。 確認するには EPICS Controls のサポート窓口に問い合わせる必要がある（出典1 が案内する経路）。

生産終了品には修正が出ない（出典6・7）。OnCell G3150A-LTE Series は全ファームウェアが対象で、示されているのは緩和策のみである（出典7・9）—— CVE-2026-111460（固定鍵）の緩和は「機器を初期化して証明書と暗号鍵素材を再生成する」ことであり、更新ではなく現地作業である（出典7）〈重要〉。NPort W2150A／W2250A Series は後継機への置き換えが案内されている（出典6）。

緊急度の表現も勧告の間で違う（本記録の確認）。MPSA-269510 は「利用者は直ちに解決策を適用すべきである」と述べ（出典7）、MPSA-261250 は中（5.3）と評価して「環境を評価し、次回の保守・更新の機会に更新を計画すること」を勧めている（出典6。いずれも原文英語を訳出）。一方 CERT-FR は、勧告1本の「リスク」欄に任意のコード実行・遠隔からのサービス拒否・機密性の侵害などをまとめて並べている（出典8）〈重要〉—— これは4件を合わせた一覧であり、個々の CVE に1対1で対応しない（本記録の読み方）。社内で優先度を決めるときは、供給元の CVE 単位の評価に戻る必要がある（本記録の評価）。

「公開された悪用の報告は無い」は「悪用が無い」ではない未確定事項

CISA は勧告に「これらの脆弱性を直接狙う公開された悪用は、現時点で CISA へ報告されていない」と書いている（出典1。原文英語を訳出）。

これは「悪用が無い」という確認ではない（本記録の読み方）〈重要〉—— 「報告されていない」という記述である。 Moxa の勧告2本は、悪用について何も述べていない（出典6・7。本記録の確認）。

本件で注意すべき点が1つある（本記録の評価）。修正は2026年7月23日以降、公開リポジトリに存在した（出典3）—— 差分を読める者には、どこが弱かったかの手がかりが3か月あった。 これは悪用があったという主張ではない（本記録の明示）——公表資料にその裏付けは無い〈未確定9〉。記録するのは、「修正が公開されてからリリースされるまでの期間」がリスクの観点を持つという事実である（本記録の評価）。

EPICS Base の利用施設・設置台数も公表されていない〈未確定2〉。CISA の記載は「全世界」「重要製造業」のみである（出典1）——自組織に当たるかどうかは、各組織が資産台帳で判断するしかない。

CISO・経営層への示唆
  • 「修正が公開リポジトリにある」ことを、対策済みと読み替えてはならない。 利用者が入手できるリリースに入るまでの期間が、本件では96日あった。
    **修正は2026年7月23日に取り込まれ、リリース 7.0.11 は2026年10月27日である** （出典2・3。本記録の算出）〈重要〉。 **そのうえで、リリース告知には security fix である旨も CVE 番号も書かれていない**（出典2）〈齟齬4〉—— **更新の理由を社内に説明する材料が、勧告が出るまで存在しなかった。**
    取るべき行動 **オープンソースを組み込んでいる製品・基盤について、 「リリース告知」だけでなく「勧告・CVE」の両方を受け取る経路を持つ。** **CISA の ICS 勧告・JVN・供給元のセキュリティ告知を、 資産台帳の品目に紐づけて購読する。** **変更管理の手続きに「告知に security の語が無い更新」でも 緊急適用できる経路を用意しておく**（本記録の提言）。
  • 「更新する」という選択肢が存在しない機器を、事前に台帳で切り出しておく。 本件の Moxa 4件のうち2件は、修正ファームが出ない生産終了品が対象だった。
    **OnCell G3150A-LTE Series は全ファームウェアが対象で、 示されたのは緩和策のみである**（出典7・9。figures 参照）。 **緩和は「機器を初期化して鍵を再生成する」ことであり、 現地作業と設定の消失を伴う**（出典7）〈重要〉。 **NPort W2150A／W2250A Series は後継機への置き換え案内である**（出典6）。
    取るべき行動 **資産台帳に「供給元の保守終了日」の列を持ち、 終了した機器を網の分離・機能の無効化で守る対象として別管理にする。** **置き換えの予算を、脆弱性が出てからではなく保守終了の時点で確保する** （本記録の提言）。
  • 修正の入手に供給元への連絡が要る機器は、資産台帳の精度がそのまま 対応の速さになる。公開ダウンロードを前提にした手順では動かない。
    **Moxa は NPort W2150A-W4／W2250A-W4（v1.5.9）と MRC Client の v4.2.0 以前について、 「サポート窓口に連絡してセキュリティパッチを入手せよ」と案内している** （出典6・7。原文英語を訳出）〈重要〉—— **何台分・どの型番・どのファーム版を請求するかが決まらないと、 問い合わせ自体ができない。**
    取るべき行動 **OT 機器の台帳に型番・ファーム版・設置場所・保守契約の有無を揃える。** **供給元のサポート窓口の連絡経路と応答の実績（過去の所要日数）を 記録しておき、適用計画の前提に使う**（本記録の提言）。
  • 当局の勧告は「見落とさないための通知」であり、対象範囲の判定には使えない。 本件では、片方の当局の勧告を見ただけでは製品が1つ抜け落ちた。
    **カナダの勧告には NPort 無線デバイスサーバー（CVE-2026-111548）が 載っていない**（出典9）〈齟齬2〉。 **CERT-FR と供給元では Remote Connect Suite の版の切り方が違い、 v4.2.1 の扱いが決まらない**（出典7・8）〈齟齬1〉。
    取るべき行動 **「対象かどうか」の最終判定は供給元の勧告で行う規則を手順に書く。** **当局の勧告は検知の入口として使い、 版の範囲・修正の入手条件は供給元の文書に戻って確認する**（本記録の提言）。
  • 制御系の停止を「設備の不調」として処理していると、攻撃と区別できない。 本件の Moxa の症状は「管理画面だけが落ちて通信は続く」である。
    **「サービスの復旧には当該機器の電源の入れ直しが必要となる一方、 機器のそれ以外の機能は動作し続ける」**（出典6。原文英語を訳出）〈重要〉—— **運転は続くため、現場では「管理画面が固まった」としか見えない。** **出典1・6・7 は検知について何も述べていない**（本記録の確認）。
    取るべき行動 **制御網の通信記録（接続元・プロトコル・時刻）を保存し、 機器の異常停止の際に突き合わせる手順を作る。** **「電源の入れ直しで直った」事象を記録として残し、 再発の頻度を見る**（本記録の提言）。
セキュリティ技術者への示唆
  • ネットワークから届く長さ・要素数・型は、相互に検査しないと意味がない。 本件の修正は、個々の値の検査ではなく値の間の整合の検査だった。
    **取り込まれた変更は、`msgsize`・`dtype`・`count` の相互検査、 `m_count` のチャネル要素数に対する境界検査、 DBR データ長の受信ペイロード長に対する検査である** （出典3。原文英語を訳出）〈重要〉。 **CWE-130（長さパラメータの不整合の扱いの不備）と CWE-843（型混同）が割り当てられている**（出典1）—— **「長さは正の数か」だけでは防げない型の不備である。**
    取るべき行動 **自作のプロトコル実装・パーサについて、 宣言された長さと実際のペイロード長、宣言された型とデータの大きさを 突き合わせる検査を入れる。** **確保の大きさを計算する箇所で整数の桁あふれを検査する （乗算の前に上限を確認する）**（本記録の提言）。
  • EPICS の4件は AV:N／PR:N／UI:N である。到達性を切ることが、 更新を待つ間に効く唯一の手段になる。
    **4件すべてのベクタが AV:N／AC:L／PR:N／UI:N である**（出典1）〈重要〉—— **認証も利用者の操作も要らない。** **CISA の緩和策の第一も「インターネットから到達できないようにし、 ファイアウォールの背後に置き、業務網から分離する」ことである**（出典1）。
    取るべき行動 **Channel Access／PV Access の待ち受けポートが 制御網の外から到達できるかを実測で確認する （設定ではなく、外側からの到達性で確認する）。** **到達できる経路が見つかった場合は、更新の前に経路を閉じる** （本記録の提言）。
  • 「遠隔接続は VPN で」という助言は、VPN クライアントが サーバーの証明書を検証している前提に立っている。
    **CISA は遠隔接続に VPN を勧める一方で、 「VPN にも脆弱性があり得る」「VPN の安全性は接続される機器の 安全性どまりである」と留保している**（出典1。原文英語を訳出）。 **本件の CVE-2026-111459 は、まさに遠隔接続基盤のクライアントが サーバーから与えられた OpenVPN 設定を認証していなかった事例である** （出典7）〈重要〉—— **経路上の攻撃者が信頼されたサーバーに成り代わりうる。**
    取るべき行動 **遠隔保守に使っている基盤のクライアント版を把握し、 証明書・設定の検証に関する勧告を購読する。** **保守経路の機器も「更新対象の資産」として台帳に載せる**（本記録の提言）。
  • 既定で無効な機能は、有効にした時点で攻撃面になる。 有効化の記録を残していないと、影響の判定ができない。
    **CVE-2026-111461 は「SMS 管理機能が有効なとき」に成立し、 供給元は「この機能は既定で無効である」と述べている**（出典7）〈重要〉。 **緩和策は「運用上必要でない限り無効のままにする」ことである**（出典7）。
    取るべき行動 **既定値から変更した設定の一覧を機器ごとに持つ。** **「既定で無効」を根拠に影響なしと判断する前に、 実機の設定を確認する**（本記録の提言）。
  • 勧告が挙げる「緩和策の参照先」は中身を読む。本件では3つのうち1つが 報告方針の文書で、コードの修正ではなかった。
    **出典1 は epics-base の #934・#937 と pvDataCPP の #109 を 緩和策として並べている**（出典1）。 **本記録が確認した #937 は「Add a SECURITY.md file」であり、 脆弱性の受付方針の文書である**（出典4。本記録の確認）〈齟齬3〉。 **また pvDataCPP の変更が 7.0.11 に含まれるかは書かれていない**〈未確定3〉。
    取るべき行動 **勧告の参照先（コミット・PR・リリース）を実際に開き、 自組織が入れる版にその変更が含まれるかを確認する。** **確認できないときは、供給元・プロジェクトの窓口に問い合わせ、 回答を記録に残す**（本記録の提言）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 加速器・大型実験設備・望遠鏡・試験設備などの制御に EPICS を使っており、 EPICS Base の版が 7.0.10 以前である。

体制・契約□ オープンソースの構成要素について、リリース告知のみを購読しており、 CVE・当局勧告を資産台帳の品目に紐づけて受け取る経路が無い。
