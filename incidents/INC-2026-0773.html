2026年10月28日、米国土安全保障省（DHS）の職員・契約職員の内部名簿データが、透明性を掲げる非営利組織Distributed Denial of Secrets（DDoSecrets）のリークサイトで公開されました。件数は「4万件超」（TechCrunch）／「41,000件超」（CyberScoop）と報道で食い違っています〈齟齬に記録〉。

含まれるのは氏名・職名・業務用メール・携帯番号・勤務地に加えて、Active Directory の利用者グループ所属—— その職員がどの内部ツール・第三者サービスに到達できるかの一覧です。内訳は CBP 約21,000件、ICE と HSI 約10,000件、CISA 1,000件弱で、DHS の職員数約22万人の約5分の1に相当します。

「Department of Peace」と称するハクティビストは、DHS が使う Okta のシングルサインオンから入手したと主張しました。 Okta はこれを否定しています。 DHS は報道後に「侵害の可能性を認識しており、迅速かつ効果的に対処するべく積極的に取り組んでいる」と述べましたが、本記録が2026年10月29日に dhs.gov の報道発表を確認した時点で、同省による公表は存在しません〈齟齬に記録〉。

本記録が本件で最も重いと見るのは、流出した件数ではなく中身の構造です。 職員名簿と「権限の地図」が同じ器に入っていたため、個人の特定と、組織がどの道具を使っているかの把握が1つのデータセットで同時に成立しています。

**公開は組織の外で行われており、 組織側に検知や阻止の機会はない。** **本記録が「現実的な機会がない」と判定したのは この構造によるもので、公表された判断ではない**
影響を限定できた職員の業務用連絡先が公開された場合に備え、なりすましを前提とした本人確認の手順（内部からの連絡であっても別経路で確認する）を定めておく
影響を限定できた現場職員・捜査担当の個人の安全に関わる脅威評価を、情報流出の種類に応じて行う体制を持つ

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**DHS は、報道機関の記事が公開された後に 「侵害の可能性を認識しており、状況に迅速かつ効果的に対処するべく 積極的に取り組んでいる。職員と職員に対するあらゆる脅威を 真剣に受け止め、全員が適切に保護されるよう取り組む。 より多くの情報が得られ次第、公衆に情報を更新する」 と述べるにとどめた。** **本記録が2026年10月29日に確認した時点で、 同省の報道発表としての公表は存在しない**不十分**本記録の評価である。** **判断の根拠は3点。** **①データは既に公開済みであり、 非開示によって被害を抑える余地がほぼ無い。** **②流出した項目（氏名・業務用メール・携帯番号・勤務地）は、 本人が取れる自衛行動（不審な連絡への警戒・別経路での本人確認）が 明確に存在する種類のものである。** **③同省は「より多くの情報が得られ次第更新する」と 述べており、公表しないという方針ではない。** **留保** ——**本記録は同省の内部の通知（職員向けの連絡）の有無を 確認できていない。** **対外的な公表が無いことと、 職員に伝えていないことは別である**（本記録の留保）
**DDoSecrets と maia arson crimew は、データセット全体を公開し、 さらに検索用の道具を作成した。** **公開の理由として、組織構造の可視化、 報道・議会の調査・法的な異議申し立て・情報自由法にもとづく請求への 寄与を挙げている**評価材料なし**本記録は評価しない。** **公開の是非は、組織の防御の巧拙とは別の軸にある。** **本記録が記録するのは「公開されたという事実」と 「公開側が理由を明示したという事実」である**
CISO・経営層への示唆
  • ID 基盤に同期されたディレクトリは、職員名簿ではなく「権限の地図」として守る対象である
    本件で出たのは連絡先だけではない。Active Directory の利用者グループ所属 ——どの内部ツール・第三者サービスに到達できるかの一覧——が含まれており、 監視技術・顔認識・生成AIの利用者の規模と部署の分布が同時に読める状態になった
    取るべき行動 自組織のディレクトリと ID 基盤に入っている情報を**実際に書き出して読む** （設計書ではなく現物）。 **「この一覧が外に出たら何が分かるか」を3つ挙げる**演習を行う。 グループ名に外部サービス名をそのまま使う命名規則を見直し、 **業務上不要な項目（個人の携帯番号・自宅に近い勤務地の詳細）の保持を減らす。** ディレクトリの分類を「社内情報」から「機密」に上げるかを判断する
  • ID 基盤の提供者の「当社は安全です」は、自組織の利用者情報が出ていないことを意味しない
    攻撃者は Okta のシングルサインオンから取得したと主張し、 Okta は「Okta は安全であり、当社のデータまたはシステムが 侵害された証拠はない」と否定した。この2つは、 提供者の側ではなく利用組織の側の資格情報が使われた場合には両立する
    取るべき行動 ID 基盤の侵害を想定した問いを**提供者向けと自組織向けに分けて**持つ。 提供者向けは「あなたのシステムは侵害されたか」、 自組織向けは**「当社のテナントから、当社の利用者情報が 大量に読み出された記録は無いか」**である。 後者を自組織で確認できる手段（管理 API の利用記録・ 一括取得の記録）を持っているかを点検する。 **持っていなければ、提供者の否定で代替するしかなくなる**
  • 契約が終わったサービスの利用者グループが残っていることは、流出すると外から見える
    「Headspace_users」に約4,500名が所属していたが、 同社は2023年に契約が終了して以降サービスを提供していないと述べている。 データは数年分に遡り、退職した幹部や2023年の内部会合に言及する グループ名も含まれていた
    取るべき行動 利用者グループの棚卸しを**契約の終了と連動させる** （調達・契約の終了処理に「関連する権限グループの削除」を項目として入れる）。 棚卸しの頻度ではなく**契機**で設計する—— 契約終了・退職・組織改編の各時点で走る形にする。 **「残っているが権限は無効」という状態を正常として扱わない** ——外から見れば区別できない
  • 当事者が公表しないと、職員は自分の情報が出たかを流出サイト側の道具で確かめることになる
    本件では流出データの検索用の道具が公開側によって作られ、 DHS からの対外的な公表は本記録が確認した時点で存在しない。 同省の発言は報道機関への「侵害の可能性を認識している」のみである
    取るべき行動 大量の職員情報が外部に公開された場合に、 **職員本人向けの連絡を「調査の結論を待たずに」出す基準**を平時に決める。 初報に書くべきことを定型にする—— **①何が出た可能性があるか ②本人が取るべき行動 ③組織からの連絡の本物を見分ける方法 ④次に知らせる時期。** **「確定していないから言わない」が既定になる体制を避ける**
  • 業務用の連絡先が出た後は、内部からの連絡を装った働きかけを前提にする
    出たのは氏名・職名・業務用メール・携帯電話番号・勤務地の組み合わせであり、 さらに誰がどの部署で何を担っているかが読める。 これは組織内の人物を装った連絡を作るのに十分な材料である
    取るべき行動 **「内部からの連絡であっても別経路で確認する」手順**を、 金銭・権限・データの移動を伴う依頼について必須にする。 連絡先が公開された前提で、 窓口（人事・情報システム・経費）への依頼の受け付け方を見直す。 **職員への注意喚起を、流出の事実の確定を待たずに出せるようにする**
セキュリティ技術者への示唆
  • ディレクトリの一括取得が記録されていなければ、出たこと自体を後から確認できない
    本件では、持ち出しとみられる時期（2026年8月中旬）は 報道機関がデータのタイムスタンプから読み取った推定であり、 DHS が確認した日付ではない。取得が記録されていたかも公表されていない
    取るべき行動 ID 基盤・ディレクトリに対する**一括取得（利用者一覧・グループ一覧の 大量の読み出し）を、件数の閾値で警報にする。** 管理 API の利用記録を外部に保持し、保持期間を **「発覚が数か月後になる」前提**で決める （本件は持ち出しから公開まで約2か月半ある）。 **記録が無い経路を1つずつ潰す**——どの経路から一括取得できるかを 先に列挙する
  • 利用者グループの命名が、そのまま外部への情報開示になる
    本件では「Headspace_users」「Penlink PLX」に言及するグループ名から、 組織が使っている監視技術・サービスと、その利用者の規模・部署が読めた。 ChatGPT への到達、Salt Typhoon・Volt Typhoon の調査に 関連するグループも含まれていた
    取るべき行動 グループ名・ロール名の命名規則を見直し、 **外部サービス名・作戦名・調査対象名をそのまま使わない**方針を検討する。 既存のグループ名を書き出して、 **「名前だけで何が分かるか」を点検する。** 識別子と表示名を分け、意味のある名前は管理側だけが見る構造にできるかを検討する
  • ディレクトリに持つ項目は、業務に必要な最小限まで削れる
    出たのは氏名・職名・業務用メールに加えて、 携帯電話番号と勤務地である。これらが組み合わさることで、 個人の特定と接触の経路が同時に成立している
    取るべき行動 ディレクトリの項目を1つずつ「どの業務がこれを参照しているか」で棚卸しする。 **参照元を特定できない項目は削除の候補にする。** 個人の携帯番号のように、流出時の影響が大きく かつ代替経路（組織の連絡網）がある項目を優先して見直す。 **全職員が全職員の連絡先を引ける設計になっていないかを確認する**
  • 「グループは残っているが権限は無効」という状態は、外からも内からも区別できない
    Headspace は2023年以降サービスを提供していないと述べているが、 約4,500名のグループは残っていた。 グループの存在と実効的な権限が一致しているかを、 流出後に外部が判定することはできない
    取るべき行動 グループと実際に紐づく権限の対応を**定期に突き合わせて検証する** （グループ定義の棚卸しだけでは不十分で、 紐づく先のサービス側の設定と照合する）。 **権限が無効になったグループは削除する** ——残すなら、残す理由を記録に残す

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ ID 基盤（SSO・ディレクトリ）に、利用者の属性と「到達できるサービスの一覧」が同じ器に入っている
認証・認可□ 自組織のテナントから利用者情報が大量に読み出された記録を、提供者に頼らず自分で確認できる
運用・監視□ 利用者グループの棚卸しが、契約の終了・退職・組織改編という契機と連動している
データの保持□ ディレクトリに保持する項目が、業務上の参照元を特定できる範囲に絞られている
体制・契約□ 大量の職員情報が外部に公開された場合に、調査の結論を待たずに職員本人へ連絡を出す基準を持っている
体制・契約□ 業務用の連絡先が公開された前提で、内部からの連絡を別経路で確認する手順がある
