INC-2026-0776検索横取り拡張319本を Socket が特定

Chrome ウェブストアに非公開登録された検索横取り拡張319本・約1,344万ユーザーを Socket が特定——権限を一切要求せず既定検索をプロキシ経由に置き換え、転送先はリクエストごとにサーバー側が決めていた

脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年10月29日 最終更新: 2026年10月29日

2026年10月29日、サプライチェーンセキュリティ企業 Socket が、ブラウザの既定検索エンジンを横取りすることだけを目的とした Chrome 拡張機能319本（インストール数の合計 約1,344万ユーザー）を特定したと公表しました。うち264本は今回新たに見つかったもので、約870万ユーザー分が加算されています。最も古いものは2016年に公開されており、同じ手口が10年にわたって継続していたことになります。これらの拡張は、マニフェストの chrome_settings_overrides で既定検索プロバイダを運営者のプロキシサーバーへ差し替えるだけで、権限要求もバックグラウンド処理もコンテンツスクリプトもUIも持ちません。検索語はまずプロキシを通り、そこから Yahoo や Bing へパートナーID付きで転送されて広告収益の分配を受けます。Socket は、転送先がリクエストごとにサーバー側で決まっており、同一の検索を6回送ると4か所に分かれた例（Predator Search）を示しました。多くは Chrome ウェブストアで「非公開（unlisted）」に設定され、検索やインデクサーから見えない状態で、広告のポップオーバー・ポップアンダー経由でインストールされています。ここでは、Socket のレポート（一次資料）から確認できた範囲を、観測事実と本記録の評価を分けて整理します。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

運営者は Chrome ウェブストアに「非公開」で拡張を登録し、広告のポップオーバー／ ポップアンダーでインストールへ誘導する。拡張はマニフェストの chrome_settings_overrides で既定検索プロバイダを運営者のプロキシへ差し替えるだけで、 権限・バックグラウンド処理・コンテンツスクリプト・UIを持たない。利用者の検索語は すべてプロキシを通り、そこからリクエストごとにサーバー側が決めた先 （Yahoo／Bing のパートナータグ付き結果、ランディングページ、中継ドメイン等）へ 転送される。収益はYahoo／Bing の検索シンジケーションのパートナー分配。

  1. 1. 初期侵入公表・報道に基づく[1]
    「manual finder」「safe search」「PDF converter」「AI search」などを謳う ポップオーバー／ポップアンダー広告を、小規模な収益化ブログやコンテンツファームに 出す。数クリックで Chrome ウェブストアの拡張ページへ至り、インストールされる。 共通のランディングページで転換を計測している例が多い。
    根拠: Socket のレポート（広告経路・ランディングページの共用・ジャンク広告枠の説明）
  2. 2. 検知回避公表・報道に基づく[1]
    拡張を Chrome ウェブストアで「非公開（unlisted）」に設定し、ストア内検索と 外部インデクサーから見えないようにする。拡張ごとに独自ドメインと admin@ の メールボックスを用意し、独立した小規模パブリッシャーに見せる（Intango は 約111本で約279ドメイン）。拡張が削除されてもドメインは生き続け、 新しい拡張とランディングページがすぐに現れる。
    根拠: Socket のレポート（unlisted の利用、ドメインとメールボックスの使い分け、削除後のドメイン残存）
  3. 3. 実行確認済[1]
    マニフェストの chrome_settings_overrides.search_provider に is_default: true と 運営者側の search_url／suggest_url を書き、既定検索プロバイダを差し替える。 これは拡張機能の枠組みに用意された設定であり、コードの実行を伴わない。 権限要求・サービスワーカー・コンテンツスクリプト・UIを持たない拡張が存在する。
    根拠: Socket が全文を掲載した「Safe Game Search」のマニフェスト（アイコン3枚とこのマニフェストだけで拡張が成立している）
  4. 4. 収集公表・報道に基づく[1]
    利用者の検索語はすべて運営者のプロキシサーバーへ送られる。Socket は、 プロキシ運営者が完全な検索履歴を、多くの場合は一意の識別子に紐づけて 見られる立場にあると指摘している。地域別の切り分けや特定IPへの紐づけも 可能で、トレンドデータ・センチメントデータとして収益化しうるとしている （実際の保存・売却は確認されていない）。
    根拠: Socket のレポート（プロキシを置く理由の分析。検索の捕捉地点としての機能）
  5. 5. C2通信確認済[1]
    転送先はすべてサーバー側でリクエストごとに決まる。Socket の実測では、 Predator Search のプロキシへ同一の検索を6回送ると行き先が4か所に分かれた （Yahoo へ直行・searchlio.net のランディングページ・searchtosearch.com → mcftink.com → Yahoo・Cloudflare のエラーページ）。繰り返した検索が パートナータグ無しで Google のホームページへ転送された一方、別の検索は Bing へ行き続けた例もあり、転送が検索語そのものによって選ばれている。 Socket は、これが Traffic Distribution System に似た仕組みであり、 将来フィッシングや偽の検索結果、マルウェア誘導へ切り替える余地があるとするが、 「仮定にすぎない」と明記している。
    根拠: Socket が実施した Predator Search プロキシへの6回の同一検索の実測

権限もコードも持たない拡張が、既定検索の差し替えだけで検索履歴の全量を手に入れていた原因・手口出典 [1]

Socket が示した典型例は、マニフェストとアイコン3つだけで成り立っている拡張である。マニフェストの chrome_settings_overrides.search_provider に"is_default": true と運営者側の search_url を書き、既定の検索プロバイダを差し替える。これは拡張機能の枠組みに最初から用意された設定で、コードの実行すら伴わない。

その結果、こうした拡張には次のものが存在しない。

  • permissions（要求する権限）
  • バックグラウンドのサービスワーカー（拡張の処理の中心）
  • コンテンツスクリプト（ページへ注入されるJavaScript）
  • UI（ツールバーのポップアップや設定画面）

Socket が強調するのは、ここで「権限を要求していないからリスクはない」と判断するのが誤りだという点である。既定検索の差し替えはインストール時に利用者への確認を促すが、検索がどこへ行くのかは明示されない。そして検索プロバイダを差し替えるだけで、運営者は利用者の検索の全量を手に入れる。

本記録の評価として、ここで効いているのは拡張機能の権限モデルの外側にある挙動である。権限の粒度や審査が権限宣言を中心に組み立てられているほど、「権限ゼロで価値のあるデータを取る」設定項目は検査の網にかからない。

検索は Yahoo や Bing へ直接行かず、運営者のプロキシを通る——転送先はリクエストごとに決まる評価・解釈出典 [1]

Yahoo と Microsoft は、検索トラフィックを持ち込んだパートナーに広告収益を分配するシンジケーションプログラムを運営しており、パートナーには追跡用のIDが割り当てられる。Yahoo では hspart=／hsimp=、Bing では PC=（パートナーコード）とPTAG=（サブID）である。収益だけが目的なら、拡張の検索プロバイダ設定にパートナータグを直接書けば足りる。

しかし実際の流れは、検索語がまず運営者のプロキシサーバーへ行き、そこから検索エンジンへ転送される形になっている。Socket はその理由を3つ挙げる。①紹介実績の記録（パートナーからの支払いと突き合わせる）、②検索の全量を捕捉する地点（トレンドやセンチメントのデータとして収益化しうる。地域別の切り分けや特定IPへの紐づけも可能）、③プログラム可能な転送（これが「searchjacking」の核心で、転送先はすべてサーバー側でリクエストごとに決められる）。

Socket が示した実測はこうだ。Predator Search（拡張ID odkcfoohjiicbelloepgcomekdknchjh、約5万ユーザー）のプロキシへ同一の検索を6回送ると、行き先は4か所に分かれた——パートナータグ付きで Yahoo へ直行（hspart=sz&hsimp=yhs-026）、searchlio.net のランディングページ、searchtosearch.com を経由して別の結果ドメインmcftink.com を通ってから Yahoo、そして Cloudflare のエラーページ。拡張そのものは一度も変わっていない。検索が届いたそのときに、プロキシが行き先を選んでいる。

さらに、繰り返した検索がパートナータグ無しで Google のホームページへ転送された一方、別の検索は Bing へ行き続けた例も確認されている。転送が検索語そのものによって選ばれているということである。

本記録の評価として、ここが「不要なだけの拡張（PUP）」と区別すべき点である。収益の仕組みは watering hole として安定した収入になり、その間プロキシ運営者はデータが蓄積され標的が浮かび上がるのを待てる。実際に悪性の転送が行われた証拠は無い（Socket 自身が「仮定にすぎない」と明記している）が、転送を切り替える能力は運営者の手元に常にある。

ウェブストアの「非公開（unlisted）」設定と広告経由の配布で、見つからないまま1,344万インストールに達した波及・関係先出典 [1]

Chrome ウェブストアには、拡張をストア内検索と外部インデクサーの両方から見えないようにする「非公開（unlisted）」の設定がある。ページ自体は誰でも閲覧できるが、正確な拡張IDを知っているか、別のページからリンクされている必要がある。Socket が見つけた検索横取り拡張の大半は、この非公開設定になっていた。

では、1,344万インストールはどこから来たのか。Socket によれば、これらは広告ネットワーク経由で配布されている。多くは「ポップオーバー」「ポップアンダー」として表示される、最も安価で転換率の低い「ジャンク」品質の広告枠である。ページ読み込み時の短い入札で表示先が決まり、小規模な収益化ブログやコンテンツファームのようなシグナルの乏しい場所に出る。そこで「PDFを検索」「マニュアルを探す」といったポップオーバーが出て、数クリックで拡張が入り、そのまま忘れられる。

Socket は、Intango が拡張ごとに独自ドメインと admin@ のメールボックスを用意し、それぞれの登録が独立した小規模パブリッシャーに見えるようにしていたと述べている。複数のドメインが同じ拡張へ誘導することもあり（newtabsearch.net と newtabhub.net）、拡張が削除された後もドメインは生き続けることが多い。Tightrope Interactive は307ドメインにわたって約20万件の Google 広告を出していたとされる。

規模感について Socket は、これらを1本の拡張として数えれば1,300万ユーザーは現在の Chrome 拡張の人気上位25位に入ると書いている。

2016年から同じ手口が続いている——削除しても新しいドメインと誘導がすぐ現れる背景・過去事例出典 [1]

Socket が追跡した拡張は2016年にまで遡る。

  • 「Yandex search」（2016年公開）: ロシア語の MV2 拡張で、現在も稼働中のextension-search.online 経由で Yandex を既定検索に強制した。削除前に20万ユーザー。
  • HermesTab（2017年公開）: Yahoo 向けの新規タブ横取りで、2本合計40万ユーザー。
  • Intango LTD（2018年以降）: 約111本・約218万インストール・約279ドメイン。大半は Yahoo（hspart=iba）へ、15本は Bing（PC=INES*）へ送る。12件のIDがウェブストアから削除されている。

Socket は、拡張が削除されても新しいドメインと誘導がすぐに現れ、この手口が10年にわたって継続的に稼働している証拠があると述べている。また、Intango の認証済み Google Ads アカウントに載っている広告は2026年10月時点で16件しかなく、大半が "Search Direct" 向けであるため、インストールの多くは別の経路から来ていると指摘している。

Socket はレポートの中で、広告が増え拡張が増えることで Google 自身も利益を得られる立場にあるため、この活動を広く取り締まる緊急の理由が無いかもしれない、とも述べている。これは Socket の推測であり、Google の方針を示す事実ではない。

「権限を要求していない」は安全の根拠にならない——審査の軸が宣言型の権限に寄っている評価・解釈出典 [1]

本記録の作成者がレポートを整理した限りでは、この事案の教訓は二段ある。

第一に、拡張機能のリスク評価が「要求する権限」を中心に組み立てられていることの穴である。検索プロバイダの差し替えは権限ではなく設定であり、コード実行を伴わない。しかし得られるのは、利用者が入力した検索語の全量という、権限で守られている多くのデータより価値の高いものである。Socket が「検索を横取りするだけで、索引から意図的に隠され、価値の低い広告枠で宣伝され、追加の価値を何も提供しない拡張は、定義上悪意あるものとみなすべきだ」と書いているのは、この非対称に対する主張である。

第二に、転送がサーバー側で決まることの意味である。拡張の中身を静的に解析しても、マニフェストに書かれた1本のURLしか見えない。実際の挙動はプロキシの判断次第で、しかもリクエストごとに変わる。Socket が示した「同じ検索6回で4か所」という実測は、配布物の検査だけでは挙動を把握できないことを示している。企業が拡張を許可リストで管理する場合も、審査時点の挙動が継続する前提は置けない。

日本の読者にとっての論点は、このデータが検索語であることだ。業務端末で従業員が何を検索するかは、進行中の案件・障害・取引先・採用・買収の検討を映す。権限ゼロの拡張が1本入っているだけで、その全量が外部のプロキシを通る。Socket はインストールの国別内訳を示していないため、日本国内の規模は分からない。

広告経由で入った権限ゼロの拡張が、検索語をプロキシへ集めて転送先をサーバー側で選ぶ経路
運営者（layer 0）が Chrome ウェブストアへ拡張を「非公開」で登録し（layer 1）、 広告のポップオーバー／ポップアンダー（layer 1）で利用者（layer 2）にインストールさせる。 拡張（layer 2）はマニフェストの chrome_settings_overrides で既定検索を運営者の プロキシ（layer 3）へ差し替える。利用者の検索語はすべてプロキシを通り、 そこからリクエストごとにサーバー側が決めた先——Yahoo／Bing のパートナータグ付き結果、 ランディングページ、中継ドメイン（layer 4）——へ転送される。パートナーIDに応じた 検索紹介の収益が運営者へ戻る（点線）。対象は拡張319本・インストール合計約1,344万。 悪性の転送は Socket の調査では確認されていない。

CISO・経営層への示唆
  • ブラウザ拡張のリスク評価を「要求する権限」で代表させない——権限ゼロで検索語の全量が出ていく
    対象拡張の多くは permissions も背景処理もコンテンツスクリプトもUIも持たず、 マニフェストに既定検索プロバイダを書くだけで成立している。それでも運営者は 利用者の検索の全量を受け取る立場に立つ。権限宣言を軸にした審査では網にかからない。
    取るべき行動 社内の拡張審査基準に「権限以外の設定による挙動」（既定検索プロバイダ・ 新規タブ・プロキシ設定・検索候補の送信先）を明示的な審査項目として加える。 「権限なし＝低リスク」で通す運用になっていないかを基準の文面で確認する。
  • 業務端末の検索語は、案件・障害・取引先・採用・買収の検討をそのまま映す情報資産である
    検索履歴は一意の識別子に紐づけて蓄積されうる。拡張1本で全量が外部の プロキシを通る構造になっており、しかも転送先は運営者が随時変えられる。
    取るべき行動 情報分類の規程で「従業員の検索クエリ」を保護対象の情報として扱うかを決め、 扱うなら既定検索の固定と拡張の許可リスト化を必須統制に位置づける。 秘匿性の高いプロジェクトに関わる端末から先に適用する。
  • 配布基盤の審査は当てにできない——10年続いた手口が、非公開設定と広告配布で1,344万インストールに達した
    対象拡張の大半は Chrome ウェブストアで非公開に設定され、ストア内検索から 見えない状態だった。削除されても新しいドメインと誘導がすぐ現れ、 2016年から同じ手口が継続している。
    取るべき行動 ストア掲載を信頼の根拠として扱う運用（「公式ストアにあるから可」）を見直し、 自組織側で許可リストと棚卸しを持つ。基盤側の削除を待たずに止められる状態にする。
  • 審査時点の挙動が続く前提を置かない——転送先はサーバー側でリクエストごとに変わる
    Socket の実測では、同一の検索を6回送ると行き先が4か所に分かれた。 拡張は一度も更新されていない。静的解析でも挙動は把握できず、 収益目的の転送が後から悪性の転送に変わりうる余地が運営者の手元に残る。
    取るべき行動 許可した拡張の定期再評価（最低でも年1回、および拡張の所有者変更時）を 運用手順に入れる。拡張の所有者・公開者の変更を検知する仕組みがないなら、 棚卸しの頻度でその不足を埋める。
  • 「悪性の確証はない」段階での方針を事前に決めておく
    Socket は悪性の転送を確認しておらず、「仮定にすぎない」と明記している。 一方で、検索を横取りするだけで価値を何も提供しない拡張は定義上悪意あるものと みなすべきだと主張している。確証を待つと、待っている間の検索は全量が外へ出る。
    取るべき行動 「確定した悪性」ではなく「正当な機能的理由の不在」を遮断の根拠にできるよう、 社内の判断基準と承認権限を決めておく。判断を技術的な確証待ちにしない。
セキュリティ技術者への示唆
  • 既定検索の差し替えはコード実行を伴わないため、実行監視では見えない——設定値を見るしかない
    対象拡張はマニフェストの chrome_settings_overrides だけで成立し、 サービスワーカーもコンテンツスクリプトも持たない。端末側に現れるのは 「既定検索が変わった」という設定の変化だけである。
    取るべき行動 端末の既定検索プロバイダのURL とインストール済み拡張の一覧を 資産管理・MDM で定期収集し、既知の検索エンジン以外のURL を検出する ルールを作る。EDR のプロセス監視だけで拡張リスクを見ている状態をやめる。
  • プロキシ経由であることは、ネットワーク側に必ず痕跡を残す
    検索語は運営者のプロキシへHTTPS で送られてから検索エンジンへ転送される。 つまり検索のたびに、既知の検索エンジンではないホストへ検索クエリ形式の 要求が出ている。
    取るべき行動 DNS／Web プロキシのログに対し、検索クエリ形式のパス・パラメータを持つ 要求のうち宛先が既知の検索エンジンでないものを抽出するクエリを用意する。 継続的に出ている端末を洗い出す。検索語を扱うため、調査の権限と保持期間を先に定める。
  • 拡張の静的解析は「何が書かれているか」しか見ない——挙動はサーバー側にある
    マニフェストに見えるのは search_url／suggest_url の1本ずつである。 Socket が同一検索6回で4か所への転送を観測したのは、実際にプロキシへ 送って追跡したからであって、配布物の解析では分からない。
    取るべき行動 拡張を審査するときは、配布物の解析に加えて実際に検索を複数回通して 到達先を記録する（リダイレクトチェーンを最終到達先まで追う）。 一度の検証で判断せず、回数・間隔・検索語を変えて確認する。
  • ドメインは拡張より長生きする——削除済みの拡張の痕跡がログに残り続ける
    Socket は、拡張が削除されてもドメインは稼働し続けることが多いと指摘している。 2016年の拡張が使った extension-search.online は現在も稼働中とされる。
    取るべき行動 過去ログに対して遡及検索を行い、現在は削除された拡張の経路が残っていないかを 確認する。ドメインの稼働状況をもって「もう使われていない」と判断しない。 ただしレポート記載のドメインは悪性が検証されていないため、検知ルールの 材料ではなく調査の出発点として扱う。

観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ 業務端末でブラウザ拡張の新規インストールを利用者が自由に行える（許可リスト方式になっていない）本事案の拡張は広告のポップオーバー経由で数クリックで入り、そのまま忘れられる。 権限要求が無いため利用者にも不審に映りにくい。インストールを止める統制が 無ければ、検出は事後の棚卸しに依存する。

データの保持□ 従業員の検索クエリを保護対象の情報として分類しておらず、外部へ出ることの影響を評価していない検索語は進行中の案件・障害・取引先・採用・買収の検討を映す。本事案では 運営者が完全な検索履歴を一意の識別子に紐づけて見られる立場に立っていた。
