INC-2026-0784GitHubのissue経由でCI/CD侵害

**Radware の研究者は、GitHub の issue・プルリクエスト・コメントに HTML コメントとして隠した命令で CI/CD ワークフローを実行させる攻撃が、 61の公開リポジトリに対して少なくとも83件行われていたことを明らかにした** （出典1。The Register の独占取材。**本記録は Radware のレポート原文を 取得できていない**〈齟齬1〉）。 **対象には google/langextract・aquasecurity/trivy・brave/brave-browser・ mlflow/mlflow・cilium/cilium・Homebrew/homebrew-cask・github/docs など、 数万のスターを持つ広く使われたプロジェクトが含まれる。** **悪性のものと確認された投稿83件のうち77件は2026年9月1日の43分間に、 残る6件はその2分以内に投稿されており、 74個の GitHub アカウントが使われた**（多くは正当な開発履歴を持つため、 侵害されたアカウントとみられる）。 **研究者は単独の人物による協調した活動と評価している。** **本記録がこの事案で重いと見るのはここである**（本記録の評価）〈重要〉—— **攻撃者はリポジトリへの書き込み権限を必要としない。** **GitHub のアカウントさえあれば誰でも issue を立てられ、 それがワークフローの起動条件になっていれば、 隠した命令が1秒以内に自動実行される。** **しかも HTML コメントは描画されたページに表示されないため、 維持者が気づく手がかりが画面上に残らない。** **実行の痕跡が確認できたのは2件で、 認証情報の窃取やコードの改ざんに至ったかは確認できていない** 〈未確定1〉〈未確定2〉。

脅威・攻撃キャンペーン委託先・再委託先起因で委託元多数に波及初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年10月29日（The Register の独占報道） 最終更新: 2026年10月30日

Radware の研究者 Gabi Nakibly と Zvika Babo は、GitHub の prompt injection を調べる過程で、公開リポジトリの CI/CD を狙う一連の投稿を見つけた（出典1。事実）。2026年10月13日時点で、悪性の内容が確認された GitHub 上の投稿は83件、対象となったリポジトリは61である。

手口はこうである（出典1）。

  1. 攻撃者が issue・プルリクエスト・コメントを投稿する。命令は HTML コメントの中に隠されているため、描画されたページには表示されない。
  2. リポジトリがその種類のイベントでワークフローを起動する設定になっていれば、投稿から1秒以内にワークフローが自動で動く——攻撃者はこの時点以降、何もしなくてよい。
  3. ワークフローが投稿の内容をシェルのソースコードへそのまま展開すると、隠された命令が実行される。
  4. 命令は環境変数を収集し、攻撃者の管理するサーバーへ送ろうとする。

「ワークフローは1秒以内に自動で起動し、そのワークフローに脆弱性があれば攻撃は成功する」（Nakibly の説明。出典1。原文英語。本記録の訳）。

規模と時間の集中が、この活動を単発の試行から区別している（出典1）。83件のうち77件は2026年9月1日の43分間に投稿され、残る6件はその2分以内に続いた。 使われた GitHub アカウントは74個あり、多くは正当な開発履歴を持つため侵害されたものとみられる。 「同じ種類のペイロードを、同じ日に、狭い時間帯に、同じ基盤へ向けて、数十のアカウントが投稿したことを踏まえれば、協調した活動であったと評価するのが妥当である」（研究チームの記述。出典1。原文英語。本記録の訳）。

一方で、確認できていないことがはっきりしている（出典1。事実）。研究者は実際の実行ログを調べ、悪性の命令が自動化環境の中で走った証拠を2件で見つけた。 しかし、攻撃者がリポジトリへの書き込み権限を得たか、ソースコードを改変したか、下流のソフトウェアを侵害したかは断定できないとしている。

本記録がこの事案を記録する理由は、攻撃の前提の低さである（本記録の評価）。「攻撃者はリポジトリを侵害する必要も、コードベースへのアクセスも要らない。基本的に、GitHub のアカウントを持つ誰でもこの攻撃を試せる——始めるのがとても簡単だ」（Babo の説明。出典1。原文英語。本記録の訳）。

    取るべき行動 **ワークフローの実装を1本ずつ直すのは時間がかかるため、 先に権限の側を絞る——外部イベントで起動するジョブから 秘密情報を外し、昇格権限を持つジョブと分離する。** **この2つは設定の変更で済み、 実装の修正を待たずに損害の上限を下げられる。**
セキュリティ技術者への示唆
  • 外部由来の内容をシェルのソースコードへ埋め込まない
    **本件の技術的な中心はここである**（出典1。事実）—— **ワークフローが攻撃者の制御する内容を シェルのソースコードへ直接取り込み、 シェルが隠された命令を実行した。** **HTML コメントとして書かれているため、 描画されたページには表示されない**（本記録の整理）。
    取るべき行動 **issue のタイトル・本文・コメント・ブランチ名・ プルリクエストのタイトルを、 シェルの中で文字列として展開している箇所を全て洗い出す。** **それらを環境変数または引数として受け渡す形に書き換え、 引用符で囲む。** **外部入力を含む変数を直接展開しているワークフローを 検出する検査を、CI に入れる。**
  • 外部イベントで起動するジョブに、秘密情報を渡さない
    **実行された命令は環境変数を収集し、 外部へ送ろうとしている**（出典1。事実）。 **ジョブから見える秘密情報が無ければ、 実行されても持ち出せるものが無い**（本記録の評価）。
    取るべき行動 **外部イベント（issue・コメント・外部からのプルリクエスト）で 起動するワークフローと、 秘密情報を使うワークフロー（配布・署名・デプロイ）を 別のファイル・別の起動条件に分ける。** **前者に与えるトークンの権限を読み取りだけに縮める。** **分離の前後で、どのジョブがどの秘密情報を見られるかの一覧を作る。**
  • 投稿の生の本文を見る。描画結果だけを見ない
    **命令は HTML コメントの中に隠されており、 描画されたページには表示されない**（出典1。事実）。 **維持者が issue を目で見て気づく手がかりが画面上に無い** （本記録の評価）。
    取るべき行動 **外部から投稿された内容を扱う自動化では、 生の文字列として検査する工程を入れる （HTML コメント・制御文字・不可視文字の検出）。** **検出した投稿は自動実行の対象から外し、 人の確認を要求する。**
  • 自動化環境の実行ログを、自分で見る運用にする
    **研究者は実際の実行ログを調べ、 悪性の命令が自動化環境で走った証拠を2件で確認した**（出典1。事実）。 **外部の研究者が見られた記録であれば、維持者も見られたはずである** （本記録の評価）——**見ていなかった。**
    取るべき行動 **ワークフローの実行ログについて、 ①外部イベントで起動した実行を一覧できるようにする、 ②想定しているコマンド以外が走った実行を抽出する、 ③保持期間を侵害の調査に足る長さにする。** **公開リポジトリでは実行ログも公開されうることを前提に、 ログに秘密情報が出ない作りにする。**
  • 自動化環境からの外部通信を、宛先で絞る
    **収集された環境変数は、 攻撃者の管理するサーバーへ送られようとした**（出典1。事実）。 **送信が成功したかは示されていない**〈未確定1〉。
    取るべき行動 **自動化環境からの外部通信を、 必要な宛先（パッケージ配布元・自社の基盤）に限定する。** **限定が難しい場合は、通信先を記録して 想定外の宛先への接続を事後に抽出できるようにする。**
