予測市場プラットフォーム Polymarket は2026年10月29日、国際版 Polymarket.com の取引を一時停止し、「当社の第三者提供事業者の1社が侵害された」と公表しました（出典1。原文英語を本記録が訳しました）。同社は法執行機関に照会し、「影響を受けた方には全額補償する」としています。

侵害されたのはウェブ性能監視サービス DebugBear です。 同社の RUM（実利用者監視）用 JavaScript の配信基盤cdn.debugbear[.]com から、暗号資産を抜き取るスクリプトが配られていたとHudson Rock が特定しました（出典3）。DebugBear 自身も X で「進行中のセキュリティインシデントの影響を受けている。RUM 製品を使っている場合は埋め込みコードをサイトから外してほしい」と述べています（出典2）。

このスクリプトの作りが、本件の核心です（出典3 の解析）。

  • 利用者が Polymarket にログイン済みかを確認する
  • ログイン済みなら、その取引セッションとプラットフォームの取引機能をそのまま使って不正な取引を行う
  • 残高とポジションの価値を調べ、認証の方式に応じて手口を変える—— ある利用者にはポジションを自動で売却し、別の利用者にはトークンを攻撃者のウォレットへ直接移す
  • 暗号資産の保有も、移転できる資産に変換して運び出す
  • 指令の受け取りと情報の持ち出しは data.debugbear.com 経由

つまり攻撃者は、利用者の鍵も認証情報も盗んでいません（本記録の整理）。利用者自身の正規のセッションを、利用者のブラウザの中で使っています。 資産の移動は、プラットフォームから見れば「本人の操作」です。

時間の経過は速いものでした（出典1・3）。攻撃者のウォレットが Polymarket のトークン契約と大量の取引を行ったのは13:50〜13:56（米東部時間）で、Polymarket が取引所を「キャンセルのみ」モードにしたのは14:05、修正の公表は14:37、全面再開は15:05——停止から再開までちょうど1時間でした。 攻撃者のウォレットには約219万ドル相当があり、約2,860万 POL（約257万ドル相当）が3つのウォレットへ移されたと報じられています（出典3）。

本件を Polymarket の事故として読むと、学びが半分になります（本記録の評価）—— 悪性のスクリプトが配られていたのは DebugBear の CDN であり、同社の RUM を埋め込んでいた組織はすべて同じ状態に置かれていました。 国内のサイトに埋め込まれていたかどうかは公表されていません〈未確定4〉。

    **Polymarket の最初の措置は全面停止ではなく、 取引所を「キャンセルのみ」モードにし、 リレイヤーの動作を一時停止するものだった**（出典1）—— **新規の約定を止めつつ、利用者が持っているポジションを 閉じる手段は残している。** **この粒度は事故の最中に思いつけるものではない**（本記録の評価）—— **平時に設計し、実装し、試しておく必要がある。** **停止から全面再開までは1時間だった**（出典1）。
    取るべき行動 **自社のサービスについて「止め方」を3段階で定義する。** ①一部の機能だけを止める（新規の受付停止・書き込み停止等）、 ②利用者が自分の資産・データを引き出す経路だけを残す、 ③全面停止。 **各段階について、誰が判断し、どの操作で実行し、 何分で効くかを文書にする。** **年に1度は実際に試す**—— **試していない停止手順は、事故のときに動かない。**
  • 供給元の名前を公表するかどうかの方針を、事前に決めておく
    **Polymarket は「第三者提供事業者の1社が侵害された」と述べ、 事業者の名前は出していない**（出典1）。 **名前が明らかになったのは、Hudson Rock の特定と DebugBear 自身の X 投稿による**（出典2・3）。 **供給網の事案では、被害を受けた側が供給元の名前を出すかどうかが、 同じ供給元を使う他の組織の初動を左右する**（本記録の評価）—— **本件では供給元自身が呼びかけたため結果として伝わったが、 供給元が黙る場合もある。** **一方で、捜査上の理由や契約上の制約で出せないこともある** （本記録の補足。Polymarket は理由を述べていない）。
    取るべき行動 **自社が被害を受けた場合の公表方針に、供給元の扱いを明記する。** ①供給元の名前を出す条件（供給元自身が公表済み・ 他の利用組織に危険が及ぶ・当局の了解がある等）、 ②出せない場合に代わりに出す情報（製品の種類・影響の性質）、 ③供給元へ「公表してほしい」と求める手順と、 それを契約に書いておくこと。 **逆に、自社が供給元の側に立つ場合の方針も同時に決める。**
セキュリティ技術者への示唆
  • 自社サイトが読み込む外部ホストの一覧を自動で取得し、変化を検知する
    **本件の悪性スクリプトは、許可済みのホスト （`cdn.debugbear[.]com`）から配られていた**（出典3）—— **ホスト名は変わっていない。** **変わったのは配られる内容である。** **したがってホストの許可リスト（Content Security Policy）だけでは 止まらない**（本記録の整理）—— **効くのは「読み込まれるファイルの一覧と、 その内容が変わったこと」を継続して見ることである。** **ただし RUM のような随時更新されるスクリプトでは 内容の変化そのものは正常であり、 「変わったこと」だけでは異常を判定できない**（本記録の注意）。
    取るべき行動 **本番サイトの外部スクリプトを定期的に走査する仕組みを作る。** ①主要なページを自動で開き、読み込まれた外部ホストとファイルを記録する、 ②台帳に無いホスト・ファイルが現れたら警報を出す、 ③各ファイルの内容のハッシュを記録し、変化の頻度を基準線として持つ、 ④普段は週1回しか変わらないファイルが日に何度も変わるなど、 頻度の異常を見る。 **②は確実に効く。③④は補助である。**
  • 外部スクリプトを、認証済みセッションに触れられない場所に隔離する
    **本件のスクリプトは、利用者が Polymarket にログイン済みかを確認し、 その取引セッションをそのまま使って資産を動かした**（出典3）—— **同一オリジンのページ内で実行されていたため、 セッションにも取引機能にも届いた。** **別オリジンの iframe に閉じ込めれば、 親ページのセッションには触れられない**（本記録の整理）—— **ブラウザの同一オリジンポリシーが境界になる。** **代償は計測の精度である**—— **RUM のように親ページの描画を測る仕組みは、 隔離すると本来の目的を果たせない場合がある**（本記録の注意）。
    取るべき行動 **外部スクリプトを目的で分類し、隔離の可否を判断する。** ①親ページの DOM に触れる必要が無いもの（エラー収集・ 一部の解析・チャット窓口）は別オリジンの iframe へ、 ②触れる必要があるもの（RUM・A/B テスト）は、 そのページで扱う情報の重みと引き換えに可否を判断する、 ③①②のどちらでもないなら外す。 **「外せない」と結論する前に、 その計測で何を決めているかを確認する。**
  • 利用者の操作を「個々の正常さ」ではなく「集団の形」で監視する
    **本件の各取引は、個々に見れば正常である**（本記録の整理）—— **ログイン済みの利用者が、自分のポジションを売り、 自分の資産を移している。** **異常なのは、多数の利用者が同じ時刻帯に同じ順序の操作を 行っていることである**（本記録の評価）—— **配信されたスクリプトによる自動実行なので、 訪問した利用者から順に同じ動作が走る。** **1人ずつ見ると見えないが、全体の形で見ると立つ。** **ただし Polymarket が何を見ていたかは公表されていない**〈未確定5〉。
    取るべき行動 **利用者の行動の監視に「集団の軸」を足す。** ①同一時間窓で同じ型の操作（照会→売却→移転）を行った利用者の数、 ②同じ宛先アドレスへ複数の利用者から移転が集まっていないか、 ③操作の間隔（人の操作としてありえない短さ）、 ④これらの平常時の値を測り、基準線を持つ。 **②は本件に直接効く**—— **複数の利用者の資産が同じ新規アドレスへ集まるのは、 平常の業務では起きない。**
  • 供給元が参照不能になる事態を前提に、必要な情報を自分の側に保全する
    **DebugBear のサイトは参照できない状態になり、 本記録が2026年10月30日に到達を試みた際も HTTP 530 が返った** （本記録の観測。出典3 も同様の状況を報じている）—— **つまり同社の顧客は、いま同社から説明を読むことができない。** **供給元が落ちると、①侵害の範囲の説明、 ②対処の指示、③自社が使っていたファイルの内容、 のいずれも取れなくなる**（本記録の評価）。
    取るべき行動 **外部から読み込むスクリプトについて、自分の側に記録を残す。** ①配信されていたファイルの内容を定期的に取得して保存する （事後に「いつから内容が変わったか」を調べられる）、 ②供給元の告知ページ・ステータスページを定期的に保存する、 ③供給元の連絡先（メール・担当者）を、 その供給元のサイト以外の場所に記録しておく。 **①は本件のような事案で、自社が影響を受けた期間を 特定する唯一の手がかりになりうる。**

自組織に当てはまるか
