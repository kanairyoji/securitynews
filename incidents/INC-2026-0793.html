INC-2026-0793Cisco ASA/FTDのVPNに悪用中のDoS

2026年10月28日、Cisco が Secure Firewall ASA/FTD のリモートアクセス SSL VPN にある サービス拒否の脆弱性（CVE-2026-76418・CVSS 8.6）を公表し、 **「2026年10月、Cisco PSIRT は本脆弱性の活発な悪用を認知した」**と記載した。 未認証の遠隔攻撃者が SSL VPN のログイン処理へ細工した要求を送るだけで **装置が予期せず再起動し、防火壁そのものが落ちる。** 成立条件は ①いずれかのインターフェイスで `webvpn` が有効 ②いずれかのトンネルグループ（既定の DefaultWEBVPNGroup を含む）に `secondary-authentication-server-group` が設定されていること、の2つで、 **VPN ログインの成功は要らない。** **回避策は無い**と Cisco は明記しており、提示された緩和策は **「セカンダリ認証を無効にする」——つまり VPN の2要素目を外すこと**である。 翌29日、CISA が CVE を KEV へ収載し、米連邦機関の是正期限を **2026年11月1日（3日）**に設定した

緩和策が「2要素目を外せ」になっている脆弱性です。

2026年10月28日（19時15分 GMT）、Cisco は Secure Firewall ASA Software とSecure FTD Software のリモートアクセス SSL VPN にあるサービス拒否の脆弱性CVE-2026-76418 を公表しました。CVSS 基本値は 8.6（CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:N/I:N/A:H）、Security Impact Rating は High、Cisco Bug ID は CSCwx26625 です（出典1）。

未認証の遠隔攻撃者が SSL VPN のログイン処理へ細工した要求を送ると、装置が予期せず再起動してサービス拒否になります。 Cisco は「成功した VPN ログインは要らない」と明記しています（原文英語。本記録の訳）。落ちるのは VPN だけではありません——落ちるのは防火壁そのものです。装置が再起動すれば、その装置を通る通信がすべて止まります（本記録の整理）。

そして、この事案の読みどころは悪用の記述です。 Cisco のアドバイザリには「2026年10月、Cisco PSIRT は本脆弱性の活発な悪用を認知した」とあります（原文英語。本記録の訳）。公表の時点で、すでに攻撃が観測されていたということです。翌10月29日、CISA はこの CVE を KEV（悪用が確認された脆弱性の一覧）へ収載し、米連邦機関の是正期限を 2026年11月1日——収載から3日に設定しました（出典2）。

実務でいちばん重いのは、緩和策の中身です。 Cisco は「この脆弱性に対処する回避策（workaround）は無い」と明記しています。提示されている緩和策は、トンネルグループまたは既定グループのセカンダリ認証を無効にすること——VPN の2要素目を外すことです。脆弱性を避けるために認証を弱める選択肢しか用意されていない構図で、これは「どちらのリスクを取るか」の判断を利用組織に押し付けています（本記録の評価）。取るべき道は1つです。緩和ではなく修正版への更新を最優先にすること。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本記録が書けるのは、Cisco が公表した成立条件と結果だけである。** **実際の悪用は Cisco PSIRT が認知しているが、手口・攻撃者・観測の内容は 公表されていない**〈未確定1〉。 **以下の段は、アドバイザリの記述から読み取れる成立経路の骨格と、 検知・防御の観点（本記録の評価）である。** **侵害（情報の持ち出し・侵入の足場）は本件の結果ではない** ——**CVSS の C:N/I:N が示すとおり、起きるのは可用性の喪失だけである。**

  1. 1. 偵察推定[1]
    **外部から到達できる SSL VPN のログイン処理を見つける段階。** **成立条件の片方（いずれかのインターフェイスで `webvpn` が有効）は、 インターネットから SSL VPN のログイン画面が応答することと対応する** （出典1 の条件記述）。 **もう片方（トンネルグループへのセカンダリ認証の設定）は設定内容であり、 外部からは分からない**（本記録の整理）。 **Cisco は攻撃者の偵察について何も述べていない** ——**この段は条件記述から本記録が立てたものである。**
    根拠: Cisco アドバイザリの「脆弱な設定の判定手順」（`show running-config | include webvpn` 相当の確認手順）
  2. 2. 実行disclosed[1]
    **未認証の遠隔攻撃者が、リモートアクセス SSL VPN への接続時に 細工した要求を送る。** **Cisco の記述**——**「攻撃者は、SSL リモートアクセス VPN へ接続する際に 細工した要求を送ることで、この脆弱性を悪用しうる」** （原文英語。本記録の訳。出典1）。 **トンネルグループにセカンダリ認証が設定されているときの論理誤りにより、 チェックされない戻り値が NULL ポインタ参照に至る（CWE-690）。** **Cisco は「成功した VPN ログインは要らない」と明記している** ——**資格情報も証明書も不要である。**
    根拠: Cisco セキュリティアドバイザリ cisco-sa-asaftd-tunnel-dos-s6mgkb75（2026年10月28日・版1.0）
  3. 3. 影響（暗号化・破壊・改ざん）disclosed[1]
    **装置が予期せず再起動し、サービス拒否（DoS）状態になる。** **Cisco の記述**——**「悪用に成功した攻撃者は、 装置を予期せず再起動させ、サービス拒否（DoS）状態を引き起こしうる」** （原文英語。本記録の訳。出典1）。 **CVSS の A:H / S:C は、落ちるのが VPN 機能だけでなく、 その装置を通る通信全体であることと整合する**（本記録の整理）。 **情報の持ち出しや設定の改ざんは記述されていない（C:N/I:N）。** **再起動が繰り返し引き起こせるかどうかについて Cisco は述べていない。**
    根拠: Cisco セキュリティアドバイザリの「Details」節と CVSS ベクタ（A:H・S:C）

  • DefaultWEBVPNGroup がセカンダリ認証を使わない場合: no tunnel-group-list enable
  • DefaultWEBVPNGroup がセカンダリ認証を使う場合: no secondary-authentication-server-group

どちらも、やっていることは「セカンダリ認証を外す」です。セカンダリ認証は、ID/パスワードの後段に別の認証サーバ（RADIUS 等）を挿す設定で、多要素認証をこの形で実装している組織は珍しくありません（本記録の整理）。

つまり構図はこうなっています—— 本件の条件を満たすのは「VPN に2要素目を入れている組織」であり、ベンダーが示す緩和策は「その2要素目を外すこと」です。 対策をしている組織のほうが該当し、回避するには対策を戻せ、という向きになっています（本記録の評価）。

Cisco 自身も留保を付けています—— 「緩和策はセキュリティ態勢や機能を低下させる可能性があるため、自環境での適用性と影響を事前に評価すること」（原文英語。本記録の訳）。そして修正版への更新を強く推奨しています。

本記録の結論は明快です。取るべき道は緩和ではなく更新です。緩和策を使うのは「更新までの数時間を凌ぐ」場合に限り、外した期間を台帳に記録して必ず戻すこと。夜間に現場判断で外すと、戻し忘れが恒久化します——可用性の脆弱性を避けるために認証強度を永久に下げる、という最悪の帰結はこの経路で起きます（本記録の評価）。

公表されているのは、この1文だけです（原文英語。本記録の訳。出典1）。

「2026年10月、Cisco PSIRT は本脆弱性の活発な悪用を認知した。」

ここから先が何もありません。攻撃者、観測件数、標的の地域や業種、認知の端緒（顧客からの報告か自社の観測か）、観測の開始時期——いずれも書かれていません。

CISA 側も同じです。本記録が KEV の JSON 原本を取得して確認したところ、CVE-2026-76418 のエントリの notes に置かれているのはCisco のアドバイザリ URL と BOD 26-04 の案内だけで、悪用の内容に関する記述はありません（出典2。T5）。forensicTriage は "No" ——フォレンジック証跡の提出も求められていません。

実務上の意味は重いです（本記録の指摘）。「自組織が狙われたか」を事後に確かめる材料が、どこにも無い。攻撃元の IP も、要求の特徴も、ログに残る文字列も公表されていないため、IoC が出るのを待って照合する運用は、本件では永久に始まりません。

さらに、本件は認証前の要求で装置が再起動します。再起動すれば装置上の揮発したログは失われ、残るのは「落ちた」という事実だけです（本記録の評価）。外部の収集基盤へ syslog を転送していない組織は、攻撃で落ちたのか障害で落ちたのかを区別できません。

したがって、本件で防御側が持てる材料は「平時に自分で取っていたログ」しかありません。これは本件に限った話ではなく、境界装置の脆弱性が悪用される局面では繰り返し成立する条件です（本記録の整理）。

情報は漏れないが防火壁が落ちる——「可用性だけ」を軽い脆弱性として扱う優先順位付けは本件を取りこぼす評価・解釈出典 [1] [2]

CVSS のベクタを読みます—— CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:N/I:N/A:H（出典1）。

C:N/I:N ——機密性への影響なし、完全性への影響なし。情報は漏れず、設定も改ざんされません。それでも基本値が 8.6 になるのは、AV:N（遠隔）・AC:L（容易）・PR:N（権限不要）・UI:N（利用者の操作不要）・S:C（スコープ変更あり）・A:H（可用性への影響が高い）が揃っているからです。

注目すべきは S:C です。これは「脆弱な部品の権限境界を越えて影響が及ぶ」ことを意味します。本件で落ちるのは SSL VPN の機能だけではありません—— 落ちるのは ASA/FTD という装置そのもので、再起動すればその装置を通る通信が全部止まります（本記録の整理）。リモートアクセスだけでなく、拠点間通信も、その装置が境界にある区画の出入りも止まります。

ここが優先順位付けの落とし穴です（本記録の評価）。多くの組織の脆弱性対応基準は、情報漏えいの可能性を軸に組まれています。「情報は漏れない DoS」は、その軸では自動的に後回しになります。ところが本件は、すでに悪用されており、CISA が3日の期限を付けた脆弱性です。

本記録の整理では、境界装置・認証基盤・ネットワーク機器については、優先順位の軸に「落ちたときに止まる業務の範囲」を足す必要があります。情報漏えいの有無ではなく、止まる範囲で緊急度を決める軸です。本件のように、漏えいゼロでも全社が止まる事象はこの軸でしか拾えません。

条件は2つの積で、ASA/FTD のすべてが脆弱なわけではない——ただし確認手順を間違えると「該当なし」と誤判定する被害規模・影響範囲出典 [1] [4]

本件が成立するのは、次の2条件を両方満たす構成だけです（出典1）。

  1. いずれかのインターフェイスで webvpn が有効（SSL VPN が外部から到達できる）
  2. セカンダリ認証が設定されている

台湾の iThome もこの限定を明示して報じています—— 「この弱点は ASA や FTD の防火壁すべてに risk があるのではなく、SSL VPN サービスが外部から接続でき、かつトンネルグループの範囲内にセカンダリ認証が設定されている場合に限り、攻撃者が引き金を引ける」（原文中国語（繁体）。本記録の訳。出典4）。

ただし、2つめの確認手順には分岐があります（出典1）。

  • tunnel-group-list enable が有効な場合: 既定の DefaultWEBVPNGroup を含むすべてのトンネルグループについてsecondary-authentication-server-group の設定を確認する
  • tunnel-group-list enable が無い（または削除されている）場合: DefaultWEBVPNGroup の secondary-authentication-server-group を確認する

この分岐を読み飛ばすと誤判定します（本記録の指摘）。たとえば「利用者向けのトンネルグループにはセカンダリ認証を入れていない」ことだけを確認して該当なしと判定すると、既定グループ（DefaultWEBVPNGroup）の設定を見落とします。既定グループは明示的に使っていなくても設定が残っていることがあります。

また、Cisco は「成功した VPN ログインは要らない」と明記しています。 資格情報の正しさも、証明書も、接続の成立も前提ではありません ——ログイン処理に要求が届くだけで足ります（本記録の整理）。

なお、影響を受けないと Cisco が確認したのはCisco Secure FMC Software・Cisco Secure Firewall Access（CSA）・クラウド提供の Firewall（CDFW）・cdFMC の4つです。 記載の無い製品が安全であることを意味しません（本記録の注記）。

    本件で落ちるのは防火壁そのもので、その装置を通る通信が全部止まる。 冗長化していても、同じ版の2台は同じ要求で同じように落ちる。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Cisco Secure Firewall ASA または Secure FTD を、インターネットに面したリモートアクセス SSL VPN の終端として使っている本件の成立条件の片方は「いずれかのインターフェイスで `webvpn` が有効」である。 SSL VPN を終端していない ASA/FTD は、この脆弱性の引き金を引けない。 まずここで対象を絞れる。
認証・認可□ トンネルグループ（または既定の DefaultWEBVPNGroup）に `secondary-authentication-server-group` を設定しているもう片方の条件がこれである。多要素認証を第2認証として挿している構成ほど 条件を満たしやすく、「対策をしている組織のほうが該当する」向きになっている。 設定内容なので外部からは分からず、自分で確認するしかない。
運用・監視□ 境界装置の syslog を外部の収集基盤へ転送しておらず、再起動の前後のログが装置内にしか無い本件は未認証の要求で再起動が起きるため、装置内のログは失われうる。 転送していなければ、悪用が確認された脆弱性に対して 「自組織が狙われたか」を事後に確かめる手段が無い。
運用・監視□ VPN 終端が1台（または同一版・同一設定の2台）に集約されており、落ちたときの代替手順が無い同じ版・同じ設定の装置は同じ要求で同じように落ちる。 冗長化していても本件のような脆弱性では同時に落ちるため、 冗長化を可用性の担保として数えていると判断を誤る。
体制・契約□ 「統制を一時的に外す」緩和策を適用する際の承認者・期限・戻す確認方法が決まっていない本件の緩和策はセカンダリ認証の無効化である。 手順が無いまま夜間に適用すると、更新後に戻すことを忘れて VPN の2要素目が恒久的に外れたままになる。
運用・監視□ 緊急パッチの基準が「CISA KEV に収載されたら」になっている本件はベンダー公表の翌日に収載され、是正期限は3日だった。 KEV を起点にする運用では、動き出した時点で猶予がほぼ無い。 「ベンダーが悪用を認知したと書いた時点」で動く基準に前倒しする必要がある。
