開発者の端末が、更新を受け取っただけでバックドアを抱えた事案です。

2026年10月29日、AI コードエディタ Cursor の拡張機能マーケットプレイスで、Anthropic の公式拡張 Claude Code を装った改ざん版が配布されました。Cursor のセキュリティ通知によれば、配布されていたのは太平洋時間の午前2時27分ごろから午後1時35分まで——約11時間です（出典1）。対象バージョンは Windows 版・macOS 版の 2.1.312 と 2.1.313（10月30日の通知更新で明確化されました）。影響は最大約5,000利用者と報じられています（出典3・4）。

Cursor は、拡張の挙動をこう書いています（原文英語。本記録の訳）。

「この拡張は、永続的な SSH バックドアを設置しようとする悪性コードを実行する。」

悪性コードの置き場所が、この事案の読みどころです。第三者の解析によれば、攻撃者は正規の extension.js の先頭に小さな自己完結型の JavaScript ローダーを挿し込んだだけで、残りの正規コードには手を付けていません（出典4・5）。ローダーは VS Code の API を使わず素の Node.js で動くため、拡張が読み込まれた瞬間に実行されます—— Claude Code を使わなくても、会話を1回もしなくても走ります。

実行されると、攻撃者の SSH 公開鍵（コメント svc-telemetry）がauthorized_keys に書き込まれ、OS ごとの永続化（macOS は LaunchAgent com.apple.sysmond、Windows はタスク SysMon、Linux は cron の @reboot）が仕掛けられ、攻撃者サーバ134.209.82.225 へリバース SSH トンネルが張られます（出典1・5）。同時に、利用者名・ホスト名・公開 IP・Git のメールアドレスと、KEY TOKEN SECRET PASS AWS GCP を含む環境変数の「名前」がポート 8099 の平文 HTTP で送られます（出典5）。値そのものは盗んでいません——どの認証情報がその端末にあるかを先に調べ、トンネルで入ってから手で取る段取りだったと読めます（出典3）。

救いは、攻撃者の実装が雑だったことです。 Phorion の解析では、SSH を有効化する処理に誤りがあり、macOS では権限不足で systemsetup -getremotelogin が状態を返さず、Windows では PowerShell を /bin/sh 経由で呼ぼうとして失敗しました（出典3）。もともと SSH が動いていた端末以外では、トンネルは接続先として機能しません。 ただし、鍵の設置・永続化・偵察情報の送信は成功します—— 「入られなかった」ことと「何も起きなかった」ことは別です（本記録の評価）。

Cursor の対応は速く、そして踏み込んでいます。悪性版を削除して配布を止めたうえで、念のためマーケットプレイス全体を停止し、鍵をローテーションしてマーケットプレイスを再構築してから再開しました。ホスティング事業者と協力して攻撃者サーバも停止させています（出典1）。一方で、最も知りたいことが分かっていません—— 攻撃者がどうやって Anthropic の発行者名で公開できたのかです〈未確定1〉。拡張のアンインストールだけでは永続化は消えません（出典1・5）。本記録の結論は1つです。配布窓の間に更新した端末は、アンインストールではなく「調査と再構築」の対象として扱うこと。

重要なのは、このローダーが VS Code の API を使わないことです。素の Node.js として書かれており、拡張モジュールが読み込まれた時点で実行されます（出典5）。BleepingComputer の記述を引きます（原文英語。本記録の訳。出典3）。

「悪性コードは拡張の読み込み時に実行され、利用者が Claude Code と対話することを必要としない。」

つまり「AI 機能を使っていないから関係ない」という切り分けが成り立ちません（本記録の整理）。Cursor を起動し、該当版の拡張が入っていれば、それだけで走ります。会話を1回もしていなくても、同じです。

実行されると、順にこうなります（出典1・5）。

  1. 攻撃者の SSH 公開鍵（コメント svc-telemetry）を~/.ssh/authorized_keys に追加する
  2. OS ごとの永続化を仕掛ける（macOS は LaunchAgent com.apple.sysmond、Windows はタスク SysMon とスタートアップの sysmon.cmd、Linux は cron の @reboot）
  3. 攻撃者サーバ 134.209.82.225 へリバース SSH トンネルを張る（ssh -N -R '*:0:localhost:22' と autossh -M 0）

永続化の名前の付け方にも注意が要ります。 macOS の com.apple.sysmond、Windows の SysMon は、いずれもOS やマイクロソフト純正の道具を思わせる名前です。置き場（利用者の LaunchAgents ディレクトリ・利用者のスタートアップ）を見れば純正でないと分かりますが、名前だけを一覧で眺めると見逃します（本記録の評価）。

盗まれたのは資格情報の「値」ではなく「目録」だった——トンネルで入ってから手で取る段取り被害規模・影響範囲出典 [1] [3] [5]

つまり、この段階で攻撃者が得たのは「目録」です（本記録の整理）—— その端末に GitHub のトークンがあるか、AWS の鍵があるか、どのクラウドを使っているか。 Git のメールアドレスが入っているのは、端末の持ち主がどの組織の開発者かを特定するためと読めます（本記録の評価）。

5,000という数字の扱いには注意が要ります。これは Cursor の X 投稿を引く報道と第三者解析による「最大約5,000利用者」であり、Cursor のセキュリティ通知の本文には人数の記載がありません（出典1・3・5）〈齟齬1〉。意味は「配布窓の間に該当版を取得しうる状態にあった利用者の上限」であり、実際に導入した数でも、バックドアが機能した数でもありません（本記録の整理）。

実際に何が起きたかは、ほとんど分かっていません〈未確定2〉。導入した端末数、トンネルが接続に至った数、攻撃者が実際に入った数、認証情報が悪用された件数—— いずれも公表されていません。そして攻撃者サーバは停止されたので（出典1）、今から通信を観測して確かめることもできません。 各組織が自分のログで自分の分を確かめるしかない構造です（本記録の評価）—— だからこそ、IoC が同日に公表されたことの意味は大きいのです。

攻撃者の実装が雑で、多くの端末では入られずに済んだ——ただし鍵と偵察は成功している評価・解釈出典 [3] [5]

この事案が「数千台が乗っ取られた」にならなかったのは、防御が効いたからではありません。攻撃者の実装が雑だったからです。

Phorion の解析によれば、SSH を有効化する処理に誤りがありました（出典3。本記録の訳を含む）。

  • macOS: Remote Login が有効かをsystemsetup -getremotelogin で確かめようとするが、権限昇格なしで実行するため、SSH サービスの状態ではなく管理者権限のエラーが返る。マルウェアは出力に "Off" が含まれるときだけ有効化を試みるので、有効化の手順が丸ごと飛ばされる。
  • Windows: OpenSSH サーバの導入と起動を PowerShell で行おうとするが、標準の Windows に存在しない /bin/sh 経由で呼ぶため失敗する。

結果として、もともと SSH サーバが動いていなかった端末では、トンネルがアクセス経路として成立しません（出典3）。

ここで切り分けを間違えないことが重要です（本記録の評価）。成功していることが3つあります（出典3）。

  1. 攻撃者の SSH 鍵は設置されている ——後から SSH が有効化されれば、そのとき入れる状態になっている
  2. 永続化は仕掛けられている——拡張を消しても残る
  3. 偵察情報は送信されている ——どの認証情報がその端末にあるかは、既に攻撃者に渡っている

「入られなかった」ことと「何も起きなかった」ことは別です。鍵が残っている端末は、将来 SSH を有効化した瞬間に開く（本記録の指摘）。開発端末で遠隔ログインを後から入れることは、珍しくありません。

そして、次が同じように雑である保証はありません（本記録の評価）。本件の攻撃者は、配布経路を破るという難しい部分を成功させたうえで、コマンドの呼び方という易しい部分で失敗しました。 この2つは独立です—— 配布経路を破る手口が再び使えるなら、次の攻撃者は実装を直してくるだけです。

Cursor は1件を消すのではなく配布経路全体を止めた——侵入経路が分からない段階での範囲の取り方として正しい組織の対応出典 [1] [3] [5]

Cursor の対応で評価すべきは、封じ込めの「範囲」です（本記録の評価）。

「我々は悪性版をマーケットプレイスから直ちに削除し、さらなる配布を遮断した。」 「念のため、マーケットプレイスの全面停止を続けて行った。」 「我々は鍵をローテーションし、マーケットプレイスを再構築し、オンラインに戻した。」

1件を消して終わりにしていません。報道によれば、全面停止は他の拡張を監査し、すべてのアクセス鍵をローテーションするためでした（出典3）。さらにホスティング事業者と協力して攻撃者サーバを停止させ、リバース SSH 接続と偵察データの送信の双方を断っています（出典1）。

侵入経路が分からない段階では、これが唯一筋の通る範囲の取り方です（本記録の評価）。発行者権限がどう破られたか分からないなら、同じ経路で別の拡張が差し替えられている可能性を否定できません。鍵のローテーションまで行ったのは、発行者権限の悪用を前提に置いた動きとして整合します（本記録の整理）。

公表の内容も実務に使える形です。 IoC（鍵のフィンガープリント・C2 の IP とポート・永続化の置き場・確認コマンド）と削除スクリプトを出し、「拡張のアンインストールだけでは不十分」と明記しました（出典1）。この一文が無ければ、ほとんどの利用者は拡張を消して終わりにします（本記録の評価）——永続化は拡張の外に残るのに。

一方で、注意点を2つ記録します。

第一に、対象バージョンの明確化が翌日にずれました。通知は当初 2.1.313 を示し、10月30日11時30分 PT の更新で「2.1.312 および 2.1.313」になりました（出典1）。見出しは 2.1.313 のままです。初報を読んで確認を始めた組織は、2.1.312 を対象から外していました〈齟齬2〉。

第二に、削除スクリプトを先に走らせると証跡が消えます。第三者の解析は「証拠を保全したうえで永続化を削除する」順序を明示しています（出典5）。先に消すと、トンネルが接続に至ったかを後から判定できません（本記録の指摘）—— 復旧手順の先頭にベンダー提供のスクリプトを置かないこと。

  • 開発端末を「本番ではないから軽い」と扱わない——そこには本番へ入る鍵が揃っている

セキュリティ技術者への示唆
  • 拡張の悪性コードは「使わなければ安全」ではない——読み込みだけで走る
    本件のローダーは VS Code の API を使わず素の Node.js で動き、 拡張の読み込み時点で実行された。 Claude Code との対話もパッケージマネージャのフックも不要だった。 「AI 機能を使っていないから無関係」という切り分けは成り立たない。
    取るべき行動 導入済みの拡張を「使っているか」ではなく「入っているか」で棚卸しする。 使っていない拡張は無効化ではなく削除する。 エディタのプロセスから ssh・autossh・cmd・powershell が起動する挙動を EDR で単独のアラートにする。
  • authorized_keys は資産として管理する——台帳外の鍵を機械的に検出できるようにする
    本件の感染判定は、コメント `svc-telemetry` の鍵が `~/.ssh/authorized_keys` にあるかどうかで行える。 逆に言えば、許可した鍵の台帳が無い組織は、 自分の端末の鍵が増えていても気づけない。
    取るべき行動 開発端末とサーバの authorized_keys をファイル完全性監視の対象に入れ、 台帳と差分が出たら通知する仕組みを作る。 Windows では administrators_authorized_keys も対象に含める。
  • 永続化は拡張の外に残る——アンインストールを復旧手順の完了条件にしない
    本件では macOS の LaunchAgent `com.apple.sysmond`、 Windows のタスク `SysMon` とスタートアップの `sysmon.cmd`、 Linux の cron の `@reboot` が仕掛けられ、 いずれも拡張を消しても残る。名前は OS 純正を騙っている。
    取るべき行動 LaunchAgent・スケジュールタスク・cron の新規作成を監視し、 OS 純正らしい名前がユーザー領域に作られる動きを疑う検知を入れる。 復旧手順の完了条件を「永続化の不在を確認した」に書き換える。
  • 証跡を消す前に保全する——削除スクリプトは調査の後に走らせる
    Cursor は削除スクリプトを配布し、第三者の解析は 「証拠を保全したうえで永続化を削除する」順序を明示している。 先に消すと、トンネルが接続に至ったか、 いつから感染していたかを後から判定できなくなる。
    取るべき行動 侵害端末の手順書に「保全 → 調査 → 除去」の順序を明記する。 保全の対象を具体化する（authorized_keys、永続化の定義ファイル、 プロセス一覧、シェル履歴、認証ログ、egress のログ）。 ベンダー提供のスクリプトを無条件に先頭へ置かない。
  • 認証情報を環境変数に置く運用そのものが、偵察の対象になっている
    攻撃者が送信したのは値ではなく、 `KEY` `TOKEN` `SECRET` `PASS` `AWS` `GCP` を含む環境変数の名前だった。 これは「どの認証情報がこの端末にあるか」の目録であり、 トンネルで入った後に何を取るかを決めるために使われる。
    取るべき行動 長命の静的トークンを環境変数から外し、 OIDC 等で短命の資格情報を払い出す方式へ寄せる。 残さざるを得ないものは、権限の範囲と有効期限を棚卸しし、 端末が侵害されたときに無効化できる経路を用意する。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 開発端末で Cursor を使っており、拡張の導入・更新を Cursor のマーケットプレイス経由で行っている本件の配布経路はこれである。 2026年10月29日の約2時27分〜13時35分（太平洋時間。日本時間では 10月29日18時27分〜10月30日5時35分）に `anthropic.claude-code` を導入・更新した端末が対象になる。 日本時間では夜間にあたるため、自動更新の端末が静かに取り込んだ可能性がある。
運用・監視□ 開発端末の拡張の導入・更新のテレメトリを収集しておらず、誰がいつどの版を入れたかを後から照合できない本件では、配布窓と対象バージョンが明確に公表された。 テレメトリがあれば「自組織に該当端末があるか」を数分で判定できる。 無ければ、全端末を手で確認するか、該当の有無を結論できないまま終わる。
認証・認可□ 開発端末の ~/.ssh/authorized_keys に許可した鍵の台帳が無く、台帳外の鍵を検出する仕組みも無い本件の感染判定は、コメント `svc-telemetry` の鍵の有無で行える。 台帳と検出の仕組みが無い組織は、IoC が公表された事案でさえ 自分で確かめる手段を持たない。
運用・監視□ 開発端末から外部への 22/tcp と未知の宛先への平文 HTTP が許可されており、egress のログを90日以上保持していない本件のリバース SSH は TCP 22、ビーコンは TCP 8099 の平文 HTTP だった。 egress を絞っていれば成立せず、ログがあれば事後に照合できる。 攻撃者サーバは既に停止しているため、確かめられるのは過去ログだけである。
データの保持□ GitHub・CI/CD・クラウドの長命トークンを開発端末の環境変数やファイルに置いている攻撃者が最初に収集したのは、そうした認証情報を示す環境変数の名前だった。 端末が侵害された時点で、そこに置かれた長命トークンは すべてローテーション対象になる。 短命トークン方式に寄せていれば、影響の範囲と作業量が大きく変わる。
体制・契約□ 開発端末が EDR の除外対象になっている、または開発環境の設定変更が開発者の裁量に委ねられている本件の execution・persistence の段は、EDR で観測できる種類の挙動だった。 開発端末が除外されていると、検知の機会があっても見えない。 除外の有無とその理由が記録されていない組織は、 事後に「なぜ見えなかったか」を説明できない。
