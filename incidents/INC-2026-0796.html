2026年10月29日、AI コードエディタ Cursor の拡張機能マーケットプレイスで、Anthropic の公式拡張 Claude Code を装った改ざん版が配布されました。Cursor のセキュリティ通知によれば、配布されていたのは太平洋時間の午前2時27分ごろから午後1時35分まで——約11時間です（出典1）。対象バージョンは Windows 版・macOS 版の 2.1.312 と 2.1.313（10月30日の通知更新で明確化されました）。影響は最大約5,000利用者と報じられています（出典3・4）。

Cursor は、拡張の挙動をこう書いています（原文英語。本記録の訳）。

「この拡張は、永続的な SSH バックドアを設置しようとする悪性コードを実行する。」

悪性コードの置き場所が、この事案の読みどころです。第三者の解析によれば、攻撃者は正規の extension.js の先頭に小さな自己完結型の JavaScript ローダーを挿し込んだだけで、残りの正規コードには手を付けていません（出典4・5）。ローダーは VS Code の API を使わず素の Node.js で動くため、拡張が読み込まれた瞬間に実行されます—— Claude Code を使わなくても、会話を1回もしなくても走ります。

実行されると、攻撃者の SSH 公開鍵（コメント svc-telemetry）がauthorized_keys に書き込まれ、OS ごとの永続化（macOS は LaunchAgent com.apple.sysmond、Windows はタスク SysMon、Linux は cron の @reboot）が仕掛けられ、攻撃者サーバ134.209.82.225 へリバース SSH トンネルが張られます（出典1・5）。同時に、利用者名・ホスト名・公開 IP・Git のメールアドレスと、KEY TOKEN SECRET PASS AWS GCP を含む環境変数の「名前」がポート 8099 の平文 HTTP で送られます（出典5）。値そのものは盗んでいません——どの認証情報がその端末にあるかを先に調べ、トンネルで入ってから手で取る段取りだったと読めます（出典3）。

救いは、攻撃者の実装が雑だったことです。 Phorion の解析では、SSH を有効化する処理に誤りがあり、macOS では権限不足で systemsetup -getremotelogin が状態を返さず、Windows では PowerShell を /bin/sh 経由で呼ぼうとして失敗しました（出典3）。もともと SSH が動いていた端末以外では、トンネルは接続先として機能しません。 ただし、鍵の設置・永続化・偵察情報の送信は成功します—— 「入られなかった」ことと「何も起きなかった」ことは別です（本記録の評価）。

Cursor の対応は速く、そして踏み込んでいます。悪性版を削除して配布を止めたうえで、念のためマーケットプレイス全体を停止し、鍵をローテーションしてマーケットプレイスを再構築してから再開しました。ホスティング事業者と協力して攻撃者サーバも停止させています（出典1）。一方で、最も知りたいことが分かっていません—— 攻撃者がどうやって Anthropic の発行者名で公開できたのかです〈未確定1〉。拡張のアンインストールだけでは永続化は消えません（出典1・5）。本記録の結論は1つです。配布窓の間に更新した端末は、アンインストールではなく「調査と再構築」の対象として扱うこと。

Microsoft の解析で、鍵が2本あることと、拡張を消しても残る置き場が確定した原因・手口

2026年10月30日、Microsoft Threat Intelligence が挿し込まれた JavaScript の解析を公開しました（出典6）。Cursor の通知（出典1）で分かっていたことと重なる部分も多いのですが、運用で効く差が3つあります。

1つめ。SSH の鍵は2本あり、役割が違います。

鍵 置かれる場所 役割
公開鍵（コメント svc-telemetry） 利用者の ~/.ssh/authorized_keys 攻撃者が端末へ入るための「入口の許可」
秘密鍵（埋め込み） 隠し一時ファイル .stk_＋16進10桁 端末から攻撃者サーバへ外向きに繋ぐための「身分証」

.stk_ の後ろの10桁は、ホスト名とホームディレクトリから導かれます（出典6）。つまり端末ごとに名前が変わるので、ファイル名の完全一致では探せません。Microsoft が IoC として挙げているのも.stk_[0-9a-f]{10} というパターンです（出典6）。

2つめ。永続化は拡張のディレクトリの外に書かれます。

  • macOS: ~/Library/LaunchAgents/com.apple.sysmond.plist＋ ~/.config/.smt・~/.config/.smtk
  • Linux: 利用者 crontab の @reboot ＋ 同じ2ファイル
  • Windows: SYSTEM 実行を要求するタスク SysMon ＋%USERPROFILE%\.config\smt.cmd・smtk、失敗時はスタートアップの sysmon.cmd

Unix 系の .smt は、起動するたびに .smtk（鍵）を作り直してから自分の再試行ループを始めます（出典6）。鍵のファイルだけを消しても戻ってくる作りです。 拡張をアンインストールしても消えません（出典1）。

3つめ。送られたのは「名前」です。

ローダーはホスト名・利用者名・OS・アーキテクチャ・ホームディレクトリ・作業ディレクトリ・Git のグローバル設定のメールアドレスを集め、さらにKEY・TOKEN・SECRET・PASS・AWS・GCP を含む環境変数の名前を最大40件まで保持します（出典6）。Microsoft の記述を引きます（原文英語。本記録の訳。出典6）。

「コールバックが送るのは一致した環境変数の名前であり、値ではない。これは機微な設定の種類を明らかにするが、それらの変数に格納された秘密が盗まれたことを示すものではない。」

この区別は、影響評価の結論を変えます（本記録の整理）。盗まれたのは目録であって中身ではない。ただし目録を持った攻撃者は、トンネルで入れた端末から何を狙えばよいかを知っている。だから「鍵が置かれただけ」の端末でも、そこに長命トークンを置いていたなら交換の対象になります。

再試行の間隔も実務に関わります。 SSH が終了してから60秒待って再試行します（出典6）。Unix 系では autossh を優先し、無ければ ssh、Windows では隠した PowerShell のループです。egress のログを見るとき、1分間隔で 22/tcp へ出ていく試行が並んでいれば、これです。

C2通信機会はあったが検知できず
**機会はあった**（本記録の評価）—— **端末から外部へ向かう 22/tcp の常時接続と、 約1分ごとの再試行は、通信ログに明確な周期として残る。** **攻撃者サーバは既に停止しているため、 今から通信を観測することはできない**（T5）—— **過去ログを遡れる組織だけが確かめられる。**
侵入を防げた端末から外部への 22/tcp を既定で遮断し、SSH は踏み台経由に限定する
検知できた通信ログを90日以上保持し、IoC が後から出たときに遡って照合できるようにする

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。

CISO・経営層への示唆
  • 開発端末を「本番ではないから軽い」と扱わない——そこには本番へ入る鍵が揃っている
    本件で狙われたのは本番環境ではなく開発者の手元の端末である。 攻撃者が最初に取ったのは、どの認証情報がその端末にあるかという情報 （GitHub・CI/CD・AWS・GCP のトークンを示す環境変数の名前）だった。 開発端末は、本番への到達経路が最も短い場所である。
    取るべき行動 開発端末を資産台帳で本番系と同じ区分に置き、 EDR の適用・egress の管理・ログ保持を本番サーバと同じ水準に揃える。 「開発端末は除外」になっている設定を棚卸しし、 除外の理由と期限を記録する運用に変える。
  • 拡張・プラグインの自動更新は、検証していない第三者コードの自動実行である
    本件の利用者は、正規の発行者名と正規の拡張名を見て更新を受け取った。 判断の機会は無く、署名や発行者名の確認では区別できなかった。 配布経路が破れた場合、自動更新は被害を11時間で数千台へ広げる仕組みになる。
    取るべき行動 開発環境の拡張について、組織が検証した版だけを配る内部カタログを用意するか、 少なくとも自動更新を遅延させる（数日の猶予を置く）設定を既定にする。 対象の拡張一覧と版を資産として把握し、 IoC が出たときに「誰が・いつ・どの版を入れたか」を即答できる状態にする。
  • 侵入経路が公表されない事案では、「再発の確率」を自分で見積もる前提で判断する
    Cursor は配布窓・IoC・復旧手順を出したが、 攻撃者がどうやって発行者名で公開できたかは公表していない。 経路が分からないまま基盤が再開されたため、 同じことが再び起きるかを利用組織は評価できない。
    取るべき行動 AI 開発ツールの採用判断に「インシデント時に侵入経路まで公表するか」を 評価項目として入れる。経路が不明な事案が起きた基盤については、 自動更新の停止・配布の内部化・egress の制限のいずれかを 恒久的な補償統制として残す。
  • 「上限5,000」のような数値を被害件数として報告に載せない
    本件で公表された人数は Cursor の X 投稿由来の「最大約5,000」であり、 セキュリティ通知の本文には記載が無い。 実際に導入した数、トンネルが機能した数、二次被害の件数はいずれも不明である。 上限値を被害件数として扱うと、経営への報告が事実から離れる。
    取るべき行動 外部事案の報告様式に「値の出所（一次公表／報道／第三者）」と 「測っている対象（露出／導入／被害）」の欄を設ける。 自組織の該当台数は、上限値ではなく自社のテレメトリから出す。
  • 【続報】AI エージェントの実行ログ（トレース・プロンプト）を、認証情報を含む資産として扱う
    本件の起点は、2025年のコーディングエージェントのトレースを 第三者の推論基盤と共有していたバケットだった。 そのトレースの一部に伏字処理されていない API 認証情報が残っており、 攻撃者はそこから Cursor の内部システムへ到達し、 最終的に配布基盤へ書ける資格情報を得た。 露出した割合は Privacy Mode 未使用者の 0.05% 未満でしかないが、 その中の数件が1年後の供給網攻撃の入口になっている。 エージェントのログは、設計上「端末で起きたことの全部」が入る場所である。
    取るべき行動 自組織で使っている AI コーディング支援・エージェントについて、 ①トレースやプロンプトが外部へ送られる設定か（Privacy Mode 相当が 既定で有効か）、②その保存期間と保存先、 ③第三者（モデル提供者・推論基盤）との共有の有無、 ④保存前の伏字処理の有無を、契約と設定の両面で確認して記録する。 既定が「送る」になっている製品は、組織の方針として既定を反転させる。 過去に送ったぶんの削除請求ができるかも契約で確かめる。
  • 【続報】取引先へ渡した鍵は、取引先の事故で自組織の事故になる——「渡した先のインシデント公表」を監視対象に入れる
    本件で露出したのは Cursor が Fireworks AI に渡した鍵であり、 露出した場所は Cursor の管理外である。 Fireworks AI は2026年10月に複数の侵害を公表しており、 同じ事故で Notion も AI チャットの記録が露出したと公表している。 渡した鍵は、渡した時点で自組織の管理の外に出る。
    取るべき行動 第三者へ発行した資格情報の台帳を作り、 発行先・権限・有効期限・到達できるデータの範囲を記載する。 発行先のセキュリティ公表（ステータスページ・ブログ・通知）を 購読対象に入れ、公表があったら台帳から影響範囲を即座に引けるようにする。 台帳に「この鍵が漏れたら何が読めるか」を書いておくと、 公表から対処までの判断が早くなる。
  • **【続報】AI 基盤に渡した鍵の「置かれ方」を契約と設計の両方で確認する—— 評価・学習ジョブの環境変数は最も読まれやすい置き場である。**
    **Fireworks AI の説明では、不正な第三者が到達したのは 「限られた数の顧客アカウントの評価ジョブで使われる環境変数」であり、 そこにはシークレットとして保存された API キーやトークンが 含まれていた**（出典11）〈重要〉—— **Fireworks 自身も対応として「評価ジョブへのシークレットの 渡し方を見直している」と書いている**（出典11）。 **顧客側から見ると、鍵を渡した先で「どう保持されるか」は 契約書にも管理画面にも出てこない**（本記録の評価）。
    取るべき行動 **AI 基盤・推論 API・エージェント基盤に発行している鍵を一覧にし、 各事業者に①シークレットの保持方式（環境変数か秘密管理サービスか）、 ②評価・学習・バッチジョブへの渡し方、③社内からの読み取り権限の範囲、 を書面で確認する。** **回答が得られない場合は、鍵の権限を読み取り専用・ 特定リソース限定に絞り、有効期限を90日以内にする。** **あわせて「Fireworks 上のシークレットを削除しただけでは 元の認証情報は無効にならない」（出典11）という点を運用手順に書く—— 基盤から消すことと、発行元で失効させることは別の作業である。**
  • **【続報】上流の「もう不正アクセスはない」という表明を、 自社の「止まった」と読み替えない。**
    **Fireworks AI は「10月25日時点で、顧客が利用する Fireworks プラットフォームへの成功した不正アクセスの追加の証拠は 確認されていない」としている**（出典12）。 **一方 Cursor 側では、10月29日に改ざん版の拡張が置かれ、 攻撃者の活動が最後に観測されたのは11月1日である**（出典9）〈重要〉—— **矛盾ではない。既に持ち出された鍵と認証情報で動けるため、 露出元が止まっても下流は止まらない**（本記録の整理）。
    取るべき行動 **委託先・基盤事業者から「不正アクセスは止まった」という連絡を受けたら、 自社側で別に確認する項目を決めておく—— ①その事業者に渡していた鍵・トークンの失効と再発行が完了したか、 ②その鍵で到達できた自社資産（バケット・ログ・トレース）に 伏字処理されていない認証情報が残っていないか、 ③残っていた認証情報の先にある SaaS のアクセス記録に 想定外の成功ログインがないか。** **①〜③が終わるまで「収束」と社内外に伝えない。**
  • **【続報】影響の大きさが確定する前に切り離せるかを、 平時に決めておく——Notion は半日で接続を断ち、製品機能を止めた。**
    **Notion が Fireworks から受けた最初の通知（11月2日夕方）の内容は 「少量のデータに不正アクセスがあった」であり、 顧客データへの影響が伝えられたのはその4日後の11月6日である**（出典13）〈重要〉。 **Notion は最初の通知から半日程度で、接続の切断・ Fireworks 側の全データ削除の確認・通信の停止を終え、 Insights 機能という製品機能を無効化した**（出典13。本記録の算出）。 **影響が確定してから切る運用では、その間に露出が続く**（本記録の評価）。
    取るべき行動 **外部 AI 基盤・SaaS ごとに「切り離した場合に止まる自社の機能」を 事前に対応づけ、切り離しの判断権限（誰が、何時間以内に判断するか）を 規程に書く。** **切り離しの手順には、①接続の遮断、②先方に残るデータの削除要求と 完了確認、③通信の停止、の3点を入れる—— ②を省くと、切ったつもりで露出が続く。** **年1回、主要な外部基盤を切り離す机上演習を行い、 止まる機能と代替手段を確認する。**
セキュリティ技術者への示唆
  • 拡張の悪性コードは「使わなければ安全」ではない——読み込みだけで走る
    本件のローダーは VS Code の API を使わず素の Node.js で動き、 拡張の読み込み時点で実行された。 Claude Code との対話もパッケージマネージャのフックも不要だった。 「AI 機能を使っていないから無関係」という切り分けは成り立たない。
    取るべき行動 導入済みの拡張を「使っているか」ではなく「入っているか」で棚卸しする。 使っていない拡張は無効化ではなく削除する。 エディタのプロセスから ssh・autossh・cmd・powershell が起動する挙動を EDR で単独のアラートにする。
  • authorized_keys は資産として管理する——台帳外の鍵を機械的に検出できるようにする
    本件の感染判定は、コメント `svc-telemetry` の鍵が `~/.ssh/authorized_keys` にあるかどうかで行える。 逆に言えば、許可した鍵の台帳が無い組織は、 自分の端末の鍵が増えていても気づけない。
    取るべき行動 開発端末とサーバの authorized_keys をファイル完全性監視の対象に入れ、 台帳と差分が出たら通知する仕組みを作る。 Windows では administrators_authorized_keys も対象に含める。
  • 永続化は拡張の外に残る——アンインストールを復旧手順の完了条件にしない
    本件では macOS の LaunchAgent `com.apple.sysmond`、 Windows のタスク `SysMon` とスタートアップの `sysmon.cmd`、 Linux の cron の `@reboot` が仕掛けられ、 いずれも拡張を消しても残る。名前は OS 純正を騙っている。
    取るべき行動 LaunchAgent・スケジュールタスク・cron の新規作成を監視し、 OS 純正らしい名前がユーザー領域に作られる動きを疑う検知を入れる。 復旧手順の完了条件を「永続化の不在を確認した」に書き換える。
  • 証跡を消す前に保全する——削除スクリプトは調査の後に走らせる
    Cursor は削除スクリプトを配布し、第三者の解析は 「証拠を保全したうえで永続化を削除する」順序を明示している。 先に消すと、トンネルが接続に至ったか、 いつから感染していたかを後から判定できなくなる。
    取るべき行動 侵害端末の手順書に「保全 → 調査 → 除去」の順序を明記する。 保全の対象を具体化する（authorized_keys、永続化の定義ファイル、 プロセス一覧、シェル履歴、認証ログ、egress のログ）。 ベンダー提供のスクリプトを無条件に先頭へ置かない。
  • 認証情報を環境変数に置く運用そのものが、偵察の対象になっている
    攻撃者が送信したのは値ではなく、 `KEY` `TOKEN` `SECRET` `PASS` `AWS` `GCP` を含む環境変数の名前だった。 これは「どの認証情報がこの端末にあるか」の目録であり、 トンネルで入った後に何を取るかを決めるために使われる。
    取るべき行動 長命の静的トークンを環境変数から外し、 OIDC 等で短命の資格情報を払い出す方式へ寄せる。 残さざるを得ないものは、権限の範囲と有効期限を棚卸しし、 端末が侵害されたときに無効化できる経路を用意する。
  • 証拠を保全する前に消さない——「鍵を消して終わり」にすると、入られたかどうかが分からなくなる
    Microsoft と Cursor の手順はいずれも、削除の前に 拡張パッケージ・改ざんされた authorized_keys・生成された鍵と スクリプト・起動設定の保全を求めている（出典1・6）。 攻撃者サーバは既に停止しており、後から確かめられるのは 端末に残った痕跡と自組織のログだけである。 先に消すと「鍵は置かれたが入られていない」のか 「入られた後に使われた」のかを区別できなくなる。
    取るべき行動 該当端末では、①拡張パッケージと authorized_keys・ `~/.config/.smt`・`.smtk`・`.stk_` 系の一時ファイル・ LaunchAgent／タスク／cron の設定を先に採取し、 ②鍵のフィンガープリントを照合してから該当行だけを消し、 ③22/tcp と 8099/tcp の通信ログ、ローカル SSH の認証ログ、 プロセス生成ログを同じ時間帯で突き合わせる、の順で進める。 Windows は `%USERPROFILE%\.ssh\authorized_keys` と `C:\ProgramData\ssh\administrators_authorized_keys` の両方を見る。
  • 【続報】サポート窓口に顧客から送られてきた認証情報を溜め込まない
    Cursor が露出範囲として挙げたものの中に 「顧客が過去に Cursor のサポートチームへ共有した認証情報」がある。 これは攻撃でも脆弱性でもなく、運用の積み重ねで生まれた資産である。 チケットシステムやメールに残った認証情報は、 侵害されたときに「顧客側の環境への鍵束」になる。
    取るべき行動 サポート窓口の運用に、①認証情報を求めない、 ②送られてきた場合は検証後すぐ失効を依頼して本文を削除する、 ③チケット本文とメールに対して認証情報のパターン検出を常時かける、 の3つを入れる。 既存のチケット・メールアーカイブを一度スキャンし、 見つかったものは顧客へ失効を依頼する。
  • 【続報】シークレットスキャンの対象を「コードリポジトリ」で止めない
    本件で漏れた認証情報はリポジトリではなく、 エージェントのトレースとサポートのやり取りに残っていた。 Cursor 自身、対応として 「全コードリポジトリにシークレットスキャンを追加し、 他の内部データソースにも拡大した」と述べている。 スキャンの対象がリポジトリだけなら、本件の漏えいは見つからない。
    取るべき行動 スキャン対象に、ログ基盤・チケットシステム・社内 Wiki・ チャットの履歴・データウェアハウス・オブジェクトストレージ （特に第三者と共有しているバケット）を加える。 対象の一覧を資産台帳として持ち、 「スキャンしていない保存先」を明示的に残さない。 新しいデータ保存先を作るときの手続きに、 スキャン対象への追加を含める。
  • **【続報】AI に渡したもの（プロンプト・チャット記録・エージェントのトレース）を 「認証情報を含みうるデータ」として扱う。**
    **Cursor ではエージェントのトレースに伏字処理されていない API 認証情報が残り、そこから次の侵害が起きた**（出典9。既記）。 **Notion では Notion AI のチャット記録が流出し、 「インシデント期間中に Notion AI へパスワード・API キー・ その他の認証情報や機密情報を貼り付けた場合は、 それらをローテーションする」ことが求められている**（出典13）〈重要〉—— **形は違うが、同じ性質の露出である**（本記録の評価）。
    取るべき行動 **①自社が AI 基盤へ送るデータ（プロンプト・ログ・トレース）に対して、 送信前に認証情報のパターン（AWS キー・Bearer トークン・ 秘密鍵のヘッダ・`password=` など）を検出して伏字にする処理を入れる。** **②保存するトレース・会話ログに同じ検出を掛け、 保持期間を定めて自動削除する。** **③開発者向けに「AI へ認証情報を貼らない」ではなく 「貼ってしまったら何を変更するか」の手順を用意する—— 禁止だけでは実際の運用で守られない。**
  • **【続報】供給の鎖を「契約先」ではなく「データと鍵が通る先」で数える。**
    **本件の鎖は、第三者クラウド事業者（10月23日に侵害）→ Fireworks AI （10月24日に開発マシンへ到達される）→ Cursor（預けた鍵が露出）→ Cursor のマーケットプレイス（改ざん版の配布）→ 開発者の端末 の5層である**（出典9・12。本記録の算出）〈重要〉—— **読者の組織が契約しているのは4層目だけで、 1層目とは契約関係が無い。それでも1層目の侵害は5層目まで届いた** （本記録の評価）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 開発端末で Cursor を使っており、拡張の導入・更新を Cursor のマーケットプレイス経由で行っている本件の配布経路はこれである。 2026年10月29日の約2時27分〜13時35分（太平洋時間。日本時間では 10月29日18時27分〜10月30日5時35分）に `anthropic.claude-code` を導入・更新した端末が対象になる。 日本時間では夜間にあたるため、自動更新の端末が静かに取り込んだ可能性がある。
運用・監視□ 開発端末の拡張の導入・更新のテレメトリを収集しておらず、誰がいつどの版を入れたかを後から照合できない本件では、配布窓と対象バージョンが明確に公表された。 テレメトリがあれば「自組織に該当端末があるか」を数分で判定できる。 無ければ、全端末を手で確認するか、該当の有無を結論できないまま終わる。
認証・認可□ 開発端末の ~/.ssh/authorized_keys に許可した鍵の台帳が無く、台帳外の鍵を検出する仕組みも無い本件の感染判定は、コメント `svc-telemetry` の鍵の有無で行える。 台帳と検出の仕組みが無い組織は、IoC が公表された事案でさえ 自分で確かめる手段を持たない。
運用・監視□ 開発端末から外部への 22/tcp と未知の宛先への平文 HTTP が許可されており、egress のログを90日以上保持していない本件のリバース SSH は TCP 22、ビーコンは TCP 8099 の平文 HTTP だった。 egress を絞っていれば成立せず、ログがあれば事後に照合できる。 攻撃者サーバは既に停止しているため、確かめられるのは過去ログだけである。
データの保持□ GitHub・CI/CD・クラウドの長命トークンを開発端末の環境変数やファイルに置いている攻撃者が最初に収集したのは、そうした認証情報を示す環境変数の名前だった。 端末が侵害された時点で、そこに置かれた長命トークンは すべてローテーション対象になる。 短命トークン方式に寄せていれば、影響の範囲と作業量が大きく変わる。
体制・契約□ 開発端末が EDR の除外対象になっている、または開発環境の設定変更が開発者の裁量に委ねられている本件の execution・persistence の段は、EDR で観測できる種類の挙動だった。 開発端末が除外されていると、検知の機会があっても見えない。 除外の有無とその理由が記録されていない組織は、 事後に「なぜ見えなかったか」を説明できない。
データの保持□ AI コーディング支援・エージェントの実行ログ（トレース・プロンプト）が外部へ送られる設定のまま使われており、保存前の認証情報の伏字処理と保存期間が確認できていない【続報で追加した判定条件である。 本件の起点は、2025年のコーディングエージェントのトレースを 第三者の推論基盤と共有していたバケットだった。 そのトレースの一部に伏字処理されていない API 認証情報が残っており、 攻撃者はそこから内部システムへ到達した。 露出したのは Privacy Mode を有効にしていない利用者のぶんであり、 「既定のまま使っていたか」が当てはまるかどうかを決める。
委託・第三者部品□ 第三者（モデル提供者・推論基盤・データ基盤）へ発行した資格情報の台帳が無く、その鍵で到達できるデータの範囲を即座に引けない【続報で追加した判定条件である。 本件で露出したのは Cursor が Fireworks AI へ渡した鍵であり、 露出した場所は Cursor の管理外である。 渡した鍵が漏れたときに何が読めるのかを台帳で引けなければ、 発行先のインシデント公表を見ても影響範囲を判断できない。
運用・監視□ シークレットスキャンの対象がコードリポジトリに限られており、ログ基盤・チケットシステム・第三者と共有しているストレージが対象外になっている【続報で追加した判定条件である。 本件で漏れた認証情報はリポジトリではなく、 エージェントのトレースとサポートのやり取りに残っていた。 Cursor 自身が対応として対象の拡大を挙げている。 対象がリポジトリだけの組織では、同種の漏えいは検出できない。
委託・第三者部品□ **【続報】自社が使う開発者向け基盤（IDE・拡張マーケットプレイス・ AI コーディング支援）が、推論・学習を外部の AI 基盤事業者に委ねており、 その基盤事業者がどこでホストされているかを把握していない。** **本件の鎖は、第三者クラウド事業者 → Fireworks AI → Cursor → Cursor のマーケットプレイス → 開発者の端末 の5層である** （出典9・12。本記録の算出）〈重要〉—— **読者の組織が契約しているのは4層目だけで、1層目と契約関係は無い。 それでも1層目の侵害は5層目まで届いた**（本記録の評価）。 **第三者クラウド事業者の名称は公表されていないため、 同じ事業者を使う他の組織は自分にも同じ経路があるかを確認できない**〈未確定14〉。
認証・認可□ **【続報】外部の AI 基盤・推論 API へ発行した鍵について、 その鍵が先方でどう保持されるか（環境変数か秘密管理サービスか、 評価・学習ジョブへどう渡されるか）を確認していない。** **Fireworks AI の説明では、不正な第三者が到達したのは 「限られた数の顧客アカウントの評価ジョブで使われる環境変数」であり、 そこにシークレットとして保存された API キーやトークンが含まれていた** （出典11）〈重要〉—— **Fireworks 自身も「評価ジョブへのシークレットの渡し方を見直している」と 書いている**（出典11）。 **鍵を渡した先での置かれ方は、契約書にも管理画面にも出てこない** （本記録の評価）。
データの保持□ **【続報】AI 基盤へ送るデータ（プロンプト・会話記録・ エージェントのトレース）や、自社で保存するそのログに対して、 認証情報の検出・伏字処理を行っていない。** **Cursor ではエージェントのトレースに伏字処理されていない API 認証情報が残り、そこから次の侵害が起きた**（出典9。既記）。 **Notion では Notion AI のチャット記録が流出し、 そこへ貼り付けられた認証情報の変更が利用者に求められている**（出典13）〈重要〉—— **同じ上流の1つの侵害が、下流では「トレース」と「チャット記録」という 別の形の露出になった**（本記録の整理）。
運用・監視□ **【続報】外部基盤から侵害の通知を受けたとき、 影響の大きさが確定する前に接続を切り離す判断の権限と手順 （接続遮断・先方に残るデータの削除要求と完了確認・通信停止）が 定まっていない。** **Notion は最初の通知（11月2日夕方・「少量のデータに不正アクセス」）から 半日程度で接続を断ち、Fireworks 側の全データ削除を確認し、 通信を停止した。顧客データへの影響が伝えられたのは その4日後である**（出典13。本記録の算出）〈重要〉—— **影響が確定してから切る運用では、その間に露出が続く**（本記録の評価）。
