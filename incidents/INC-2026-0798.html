② CVE-2026-109822 — 保存された機微な情報に対するアクセス権設定の不備（CWE-922）

「CONFIG ファイルのエクスポート機能で生成された CONFIG ファイルが、未認証で読み取られる可能性があります。」（出典1）

  • CVSS v4.0: 7.1（UI:P）
  • CVSS v3.1: 6.5（UI:R）

UI:R / UI:P が付いているのが①との違いです（本記録の整理）—— エクスポート機能で CONFIG ファイルが生成された状態が前提になると読めます。

②の重さは、スコアより中身にあります（本記録の評価）。CONFIG ファイルには、接続先・認証情報・フィルタの構成が含まれうる。 読み取られること自体が、次の攻撃の材料になります。しかも読み取りに気づける仕組みが無ければ、後から起きた不正アクセスを本件と結びつけることもできません。

ヤマハが示す想定される影響は、両件を合わせて4つです（出典2）—— 不正なコードの実行、設定の変更、サービス運用妨害（DoS）、設定情報の漏えい。

「設定の変更」を軽く見ないでください（本記録の指摘）。NWR100 は拠点や店舗の境界に置かれる機器です（出典4）。設定を変えられれば、通信の経路そのものが攻撃者の手に入ります。

ここで、CVSS の枠組みと実務のずれに触れます（本記録の整理）。本件のベクタは v4.0 で SC:N / SI:N / SA:N、v3.1 で S:U です（出典1）——後続システムへの影響は評価の対象になっていません。 しかし境界機器が乗っ取られたとき、実務上の影響はその機器の中に収まりません。 スコアだけで優先度を決めると、ここが落ちます。

なお、どの機能のどの入力が該当するかは公表されていません〈未確定1〉。本記録はこれを欠陥とは扱いません—— 未更新の機器を狙う攻撃者に手がかりを与えない利点があり、代わりに実行可能な回避策が示されています（本記録の評価）。記録しておくのは、この粒度では「どの機能を止めれば凌げるか」が判断できないことです。

方向は正しいです（本記録の評価）。本件の CVSS は AV:N であり、成立の前提は Web GUI への到達です。到達できなければ、脆弱性は残っていても引き金が引けません。

ただし、実行すると分かることがあります（本記録の判断）。

「どの接続元から Web GUI に入れる設定になっているか」を確認する作業は、そのまま「WAN 側から入れる設定になっていないか」の確認です。

本件の実害の分かれ目はそこにあります。 LAN 側からしか入れない機器と、WAN 側から管理画面が見えている機器では、緊急度が桁で違います。そして、インターネットに露出している台数は公表されていません〈未確定3〉——自分で確認するしかありません。

確認の順序を提案します（本記録の判断）。

  1. 全台の型番とファームウェア版を出す ——出せなければ、まずそこが課題です
  2. WAN 側から Web GUI へ到達できる設定の台を特定する
  3. 到達できる台は、更新を待たずに接続元を絞る
  4. 並行して Rev.26.00.08 以降へ更新する

4 を「3 が終わったら」にしないこと（本記録の判断）。回避策は脆弱性を残します。許可した接続元の端末が侵害されれば、そこから成立します。

「回避策を適用したので更新しない」は、本件では選んではいけません。修正版はすでに4か月前から存在し、取得の障壁がありません。回避策を使うのは、更新作業の段取りがつくまでの数日を凌ぐ場合に限ること。 外した期間・絞った内容を記録し、更新後に戻すかどうかを決めておくこと。

更新の副作用も確認してください（出典3）。Rev.26.00.08 には、運用に効く仕様変更が含まれます。

  • Wi-Fi の認証フレーム送信時のログ<10102>がDEBUG から INFO に変わり、ステータスコードが追加される ——ログ量が増えます。監視の閾値とストレージを見積もってください。
  • CLI のログインが3回失敗して制限されている間は、ユーザー名の入力プロンプトを表示しなくなる
  • 別筐体への CONFIG インポート後に、ネットボランチDNS の設定が引き継がれなくなる ——機器の交換・移設の手順を持っている組織は改訂が要ります。

更新は再起動を伴うため、拠点の通信が一時断になります（本記録の整理）。そして再起動は、機器内のログを失わせます—— 「狙われたか」を後から確かめたいなら、作業前にログと設定を保全してください。

実務への帰結は2つあります。

第一に、優先度の判定に使えません。「悪用情報が無いから後回し」という判定は、「悪用されていないと確認された」という情報があって初めて成り立ちます。本件にはそれがありません。使えるのは CVSS（v3.1 で 9.8）と、自組織の露出状況だけです（本記録の判断）。

第二に、事後の確認手段がありません。 IoC——攻撃元の IP、要求の特徴、ログに残る文字列——は何も示されていません〈未確定4〉。自組織が狙われたかを確かめられるのは、自分で取っていた Web GUI のアクセスログだけです。

そして、こうした機器ではそのログが残っていないことが多い（本記録の評価）。機器内のログは容量が小さく、再起動で失われます。 更新のための再起動そのものが、証跡を消す作業になります。

いま取れる行動は2つです（本記録の判断）。

①更新作業の前に、ログと設定を保全する。 ②境界機器の SYSLOG を外部の収集基盤へ転送する運用を、この機会に入れる。

②は本件のためではありません—— 次に IoC が公表されない脆弱性が出たときのためです。 IoC を待つ運用は、IoC が出ない事案では永久に始まりません。

CISO・経営層への示唆
  • 境界機器のファームウェア更新を「機能が要るかどうか」で判断させない
    本件の修正版 Rev.26.00.08 は、2026年7月1日に 「拠点間接続VPN機能に対応」した機能追加版として配られた。 脆弱性の修正であることが分かったのは、119日後の10月28日である。 「拠点間VPN は使わないから更新は見送る」という当時の合理的な判断が、 結果として CVSS 9.8 の放置になっていた。
    取るべき行動 境界機器・ネットワーク機器のファームウェアについて、 「最新を維持する」を既定の方針とし、見送る場合に理由と期限の記録を要求する。 見送りの判断を現場の裁量に委ねず、四半期ごとに棚卸しする。 機能追加のリリースも、更新対象として同じ扱いにする。
  • CVSS の版の違いで優先度が変わることを、社内基準の問題として整理する
    本件の CVE-2026-109822 は、CVSS v3.1 で 6.5、v4.0 で 7.1 である。 多くの組織の基準では、これは「中」と「高」に分かれる。 JVN は両方を出しているため、どちらを採るかで対応の期限が変わる。 基準を決めていない組織では、担当者ごとに判定が揺れる。
    取るべき行動 社内の脆弱性管理基準に、どの CVSS 版を用いるかを明記する。 両方が示されている場合の扱い（高いほうを採る等）も決める。 境界機器については、スコアだけでなく 「落ちたとき・乗っ取られたときに止まる業務の範囲」を軸に加える。
  • 中小拠点・店舗に置いた機器を、資産台帳の外に置かない
    NWR100 は中小法人向けのルーターで、拠点や店舗の境界に置かれる。 こうした機器は、導入が現地や施工業者に任されやすく、 台数・設置場所・ファームウェア版が本社で把握されていないことがある。 把握していなければ、公表の翌日に「自社に何台あるか」に答えられない。
    取るべき行動 拠点・店舗のネットワーク機器を資産台帳の対象に含め、 型番・ファームウェア版・設置場所・管理責任者を記録する。 遠隔から版を取得できる仕組みを用意し、 脆弱性公表の当日に該当台数を出せる状態を目標にする。
  • 「悪用の情報が無い」ことを安全の根拠に使わない
    本件では、悪用に関する記述がどの資料にも無い。 これは「悪用されていない」と公表されたのではなく、 悪用について何も言われていない状態である。 IoC も示されていないため、自組織が狙われたかを確かめる手段もない。
    取るべき行動 脆弱性の優先度判定に「悪用情報の有無」を使う場合、 「情報が無い」と「悪用されていないと確認された」を 別の値として扱う基準に直す。 境界機器については、悪用情報の有無にかかわらず CVSS と露出状況で期限を決める。
セキュリティ技術者への示唆
  • リリースノートの「バグ修正」は、後から脆弱性修正だったと分かることがある
    Rev.26.00.08 のリリースノートは、公開時点では 機能追加1件・仕様変更4件・バグ修正33件を並べていた。 2026年10月の更新で「Web GUI に関する脆弱性」として CVE-2026-97854・CVE-2026-109822 への対応が追記された。 調整中の脆弱性の修正は、こうして機能追加やバグ修正に混ざって出る。
    取るべき行動 機器のファームウェアについて、リリースノートの内容で 更新の可否を判断する運用をやめる。 すでに適用を見送った版について、 後から脆弱性対応が追記されていないかを定期的に確認する （ベンダーの更新履歴を見る）。
  • AV:N の機器脆弱性は、まず「WAN 側から管理画面に入れるか」を確認する
    本件の CVSS はいずれも AV:N で、CVE-2026-97854 は PR:N / UI:N である。 ヤマハの回避策も Web GUI への接続元の制限である。 実害の分かれ目は、管理画面が外から到達できるかどうかにある。 台数も露出状況も公表されていないため、自分で確認するしかない。

  • CONFIG ファイルを機器上に置いたままにしない
    CVE-2026-109822 は、エクスポート機能で生成された CONFIG ファイルが 未認証で読み取られるというものである。 CVSS の UI:R / UI:P は、利用者側の関与が条件に入ることを示す。 CONFIG には接続先・認証情報・フィルタの構成が含まれうるため、 読み取られること自体が次の攻撃の材料になる。
    取るべき行動 設定のバックアップは機器上に残さず、取得後は外部の保管先へ移す。 設定に含まれる認証情報を一覧化し、 機器の侵害を前提に変更できる状態にしておく。
  • 機器のログを外へ出していないと、「狙われたか」に答えられない

    取るべき行動 境界機器の SYSLOG を外部の収集基盤へ常時転送し、保持期間を90日以上確保する。 設定を定期的に取得して差分を確認し、承認のない変更を検出する。 更新作業の手順に「作業前のログと設定の保全」を入れる。
  • 更新の副作用を、ログと手順の両面で確認する
    Rev.26.00.08 では、Wi-Fi の認証フレーム送信時のログ<10102>が DEBUG から INFO に変わりステータスコードが追加される。 また、別筐体への CONFIG インポート時に ネットボランチDNS の設定が引き継がれなくなる。 更新は脆弱性を塞ぐが、監視の閾値と機器交換の手順に影響する。
    取るべき行動 更新前にリリースノートの仕様変更を読み、 ログ量の増加が監視の閾値やストレージに与える影響を見積もる。 機器交換・移設の手順書を持っている場合は、 CONFIG インポートの挙動変更に合わせて改訂する。
