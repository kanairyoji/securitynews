CISO・経営層への示唆
  • 境界機器のファームウェア更新を「機能が要るかどうか」で判断させない
    本件の修正版 Rev.26.00.08 は、2026年7月1日に 「拠点間接続VPN機能に対応」した機能追加版として配られた。 脆弱性の修正であることが分かったのは、119日後の10月28日である。 「拠点間VPN は使わないから更新は見送る」という当時の合理的な判断が、 結果として CVSS 9.8 の放置になっていた。
    取るべき行動 境界機器・ネットワーク機器のファームウェアについて、 「最新を維持する」を既定の方針とし、見送る場合に理由と期限の記録を要求する。 見送りの判断を現場の裁量に委ねず、四半期ごとに棚卸しする。 機能追加のリリースも、更新対象として同じ扱いにする。
  • CVSS の版の違いで優先度が変わることを、社内基準の問題として整理する
    本件の CVE-2026-109822 は、CVSS v3.1 で 6.5、v4.0 で 7.1 である。 多くの組織の基準では、これは「中」と「高」に分かれる。 JVN は両方を出しているため、どちらを採るかで対応の期限が変わる。 基準を決めていない組織では、担当者ごとに判定が揺れる。
    取るべき行動 社内の脆弱性管理基準に、どの CVSS 版を用いるかを明記する。 両方が示されている場合の扱い（高いほうを採る等）も決める。 境界機器については、スコアだけでなく 「落ちたとき・乗っ取られたときに止まる業務の範囲」を軸に加える。
  • 中小拠点・店舗に置いた機器を、資産台帳の外に置かない
    NWR100 は中小法人向けのルーターで、拠点や店舗の境界に置かれる。 こうした機器は、導入が現地や施工業者に任されやすく、 台数・設置場所・ファームウェア版が本社で把握されていないことがある。 把握していなければ、公表の翌日に「自社に何台あるか」に答えられない。
    取るべき行動 拠点・店舗のネットワーク機器を資産台帳の対象に含め、 型番・ファームウェア版・設置場所・管理責任者を記録する。 遠隔から版を取得できる仕組みを用意し、 脆弱性公表の当日に該当台数を出せる状態を目標にする。
  • 「悪用の情報が無い」ことを安全の根拠に使わない
    本件では、悪用に関する記述がどの資料にも無い。 これは「悪用されていない」と公表されたのではなく、 悪用について何も言われていない状態である。 IoC も示されていないため、自組織が狙われたかを確かめる手段もない。
    取るべき行動 脆弱性の優先度判定に「悪用情報の有無」を使う場合、 「情報が無い」と「悪用されていないと確認された」を 別の値として扱う基準に直す。 境界機器については、悪用情報の有無にかかわらず CVSS と露出状況で期限を決める。
セキュリティ技術者への示唆
  • リリースノートの「バグ修正」は、後から脆弱性修正だったと分かることがある
    Rev.26.00.08 のリリースノートは、公開時点では 機能追加1件・仕様変更4件・バグ修正33件を並べていた。 2026年10月の更新で「Web GUI に関する脆弱性」として CVE-2026-97854・CVE-2026-109822 への対応が追記された。 調整中の脆弱性の修正は、こうして機能追加やバグ修正に混ざって出る。
    取るべき行動 機器のファームウェアについて、リリースノートの内容で 更新の可否を判断する運用をやめる。 すでに適用を見送った版について、 後から脆弱性対応が追記されていないかを定期的に確認する （ベンダーの更新履歴を見る）。
  • AV:N の機器脆弱性は、まず「WAN 側から管理画面に入れるか」を確認する
    本件の CVSS はいずれも AV:N で、CVE-2026-97854 は PR:N / UI:N である。 ヤマハの回避策も Web GUI への接続元の制限である。 実害の分かれ目は、管理画面が外から到達できるかどうかにある。 台数も露出状況も公表されていないため、自分で確認するしかない。
    取るべき行動 全台について、WAN 側から Web GUI へ到達できる設定になっていないかを確認する。 到達できるものは、更新を待たずに IP フィルターで接続元を絞る。 絞った内容と期限を記録し、更新後に設定を戻すかどうかを決めておく。
  • CONFIG ファイルを機器上に置いたままにしない
    CVE-2026-109822 は、エクスポート機能で生成された CONFIG ファイルが 未認証で読み取られるというものである。 CVSS の UI:R / UI:P は、利用者側の関与が条件に入ることを示す。 CONFIG には接続先・認証情報・フィルタの構成が含まれうるため、 読み取られること自体が次の攻撃の材料になる。
    取るべき行動 設定のバックアップは機器上に残さず、取得後は外部の保管先へ移す。 設定に含まれる認証情報を一覧化し、 機器の侵害を前提に変更できる状態にしておく。
  • 機器のログを外へ出していないと、「狙われたか」に答えられない
    本件では IoC が示されていない。 自組織が狙われたかを確かめられるのは、自分で取っていたログだけである。 機器内のログは容量が小さく、再起動で失われうる。 更新のための再起動そのものが、証跡を消す作業になる。
    取るべき行動 境界機器の SYSLOG を外部の収集基盤へ常時転送し、保持期間を90日以上確保する。 設定を定期的に取得して差分を確認し、承認のない変更を検出する。 更新作業の手順に「作業前のログと設定の保全」を入れる。
  • 更新の副作用を、ログと手順の両面で確認する
    Rev.26.00.08 では、Wi-Fi の認証フレーム送信時のログ<10102>が DEBUG から INFO に変わりステータスコードが追加される。 また、別筐体への CONFIG インポート時に ネットボランチDNS の設定が引き継がれなくなる。 更新は脆弱性を塞ぐが、監視の閾値と機器交換の手順に影響する。
    取るべき行動 更新前にリリースノートの仕様変更を読み、 ログ量の増加が監視の閾値やストレージに与える影響を見積もる。 機器交換・移設の手順書を持っている場合は、 CONFIG インポートの挙動変更に合わせて改訂する。
