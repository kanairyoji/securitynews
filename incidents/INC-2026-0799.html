INC-2026-0799Drupal Commerce に悪用中の脆弱性

2026年10月28日、Drupal セキュリティチームは EC 構築モジュール **Commerce Core** のアクセス制御回避の脆弱性 **CVE-2026-118539** を **「Highly critical」（リスク評点 21/25）**として公表し、 **「この脆弱性は実際に悪用されています」**と明記した。 **「モジュールは特定のルートとエンティティフィールドを十分に保護しておらず、 アクセス制御の回避に至り、販売者に金銭的な被害が及ぶおそれがある」**。 未認証の攻撃者が設定に関係なく悪用でき、対象は 2.41 未満および 3.0.0 以上 3.3.13 未満。**42,000 を超えるサイトが利用している。** 公表された対処は更新に加えて**「注文データに不整合がないか監査すること」**で、 **手口・攻撃者・標的サイト数・ゼロデイだったかはいずれも公表されていない。** 本記録の確認時点で CISA の KEV には収載されていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年10月28日（Drupal セキュリティアドバイザリ SA-CONTRIB-2026-254） 最終更新: 2026年10月31日

「注文データに不整合がないか監査してください」という指示が付いた脆弱性です。

2026年10月28日、Drupal セキュリティチームは EC 構築モジュールCommerce Core のアクセス制御回避の脆弱性CVE-2026-118539 を公表しました（出典1）。区分は「Highly critical」、リスク評点は21点満点中21——25点満点中21です（出典1・3）。

アドバイザリの記述を引きます（原文英語。本記録の訳。出典1）。

「このモジュールは、included shopping cart と checkout form、あるいは API 経由の分離型アプリケーションを通じて、顧客に商品やサービスを販売することを可能にします。」 「モジュールは特定のルートとエンティティフィールドを十分に保護しておらず、アクセス制御の回避に至り、販売者に金銭的な被害が及ぶおそれがあります。この脆弱性は実際に悪用されています。」

影響範囲は広いです。対象は 2.41 未満、および 3.0.0 以上 3.3.13 未満（出典1）。Drupal の統計では、42,000 を超えるサイトがこのモジュールを使っています（出典2・3）。報道は、利用者に Fortune 500 企業や研究大学が含まれるとしています（出典2）。

対処は2つです（出典1）。①3.x 系は Commerce Core 3.3.13 へ、それ以前は 8.x-2.41 へ更新する。 ②注文データに不整合がないか監査する。

②が、この事案の性格を示しています（本記録の評価）。更新だけでは終わらないということです。被害が「販売者に金銭的な被害が及ぶ」形で現れるなら、すでに通された注文が記録として残っています。 塞いだあとに、通ってしまった分を自分で探す必要があります。

ただし、探すための材料がほとんど出ていません（本記録の指摘）。Drupal は悪用の事実は認めた一方、どう悪用されているのか、誰がやっているのか、何サイトが狙われたのか、修正の提供前から悪用されていた（ゼロデイだった）のかをいずれも公表していません（出典3）〈未確定1・2・3〉。「不整合」が具体的に何を指すのか——価格か、数量か、支払い状態か、配送か——も書かれていません〈未確定4〉。

もう1つ、同日の文脈を押さえておく必要があります。 10月28日に Drupal が公表したアドバイザリは、SA-CONTRIB-2026-254 から 292 までの39件です（出典5。本記録が確認）。21のコントリビュートプロジェクトが対象で、うち10件以上が「Critical」（出典3）。その中には、Stripe 経由の Commerce の注文が支払いなしで「支払い済み」と記録されうる不具合も含まれます（出典3）。本件1件だけを見て終わる局面ではありません（本記録の判断）。

なお、本記録の確認時点（2026年10月31日）で、CVE-2026-118539 は CISA の KEV に収載されていません（カタログ版 2026.10.30・収載総数1,766件。本記録が JSON 原本で確認）〈齟齬3〉——ベンダーが「悪用されている」と書いた脆弱性がKEV に入っていない状態です。 KEV を起点に動く運用では、本件はまだ動き出していません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本記録が書けるのは、Drupal が公表した脆弱性の性質と結果だけである** （出典1）。 **悪用は Drupal が確認しているが、手口・攻撃者・観測の内容は 公表されていない**〈未確定1〉。 **以下の段は、アドバイザリの記述とリスク評点から読み取れる 経路の骨格と、検知・防御の観点（本記録の評価）であり、 実際の攻撃手順の記述ではない。** **本記録は手口を推定して具体化しない。**

  1. 1. 偵察推定[1] [3]
    **Commerce Core を使っている Drupal サイトを見つける段階。** **Drupal のサイトはモジュール構成が外部から推測可能な場合があり、 チェックアウトの経路や静的ファイルの配置から Commerce の利用が分かることがある**（本記録の整理）。 **Drupal も報道も偵察について何も述べていない** ——**この段は本記録が立てたものである。** **リスク評点が「未認証の攻撃者が設定にかかわらず悪用できる」ことを 示しているため、標的の選別は「Commerce を使っているか」だけで足りる** （出典3。本記録の評価）。
    根拠: Drupal のリスク評点の内訳（攻撃の複雑さが低い・認証不要）
  2. 2. 初期侵入disclosed[1] [3] [4]
    **未認証の攻撃者が、十分に保護されていない「特定のルート」へ 要求を送り、アクセス制御を回避する。** **Drupal の記述**——**「モジュールは特定のルートと エンティティフィールドを十分に保護しておらず、 アクセス制御の回避に至り、販売者に金銭的な被害が及ぶおそれがある」** （原文英語。本記録の訳。出典1）。 **The Hacker News は「missing authorization（認可の欠落）の事例」と 整理している**（出典4）。 **リスク評点によれば、認証は不要で、攻撃の複雑さは低く、 モジュールの設定方法にかかわらず成立する**（出典1・3）。 **どのルートかは公表されていない**〈未確定2〉。
    根拠: SA-CONTRIB-2026-254（CVE-2026-118539・Highly critical・21/25）
  3. 3. 影響（暗号化・破壊・改ざん）disclosed[1] [3]
    **アクセス制御の回避により、販売者に金銭的な被害が及ぶおそれがある** （出典1）。 **Drupal のリスク評点は「機密データの漏えいと一部データの改ざんの おそれ」を示している**（出典1）—— **読み取りだけでなく、書き込みも含まれる。** **「エンティティフィールド」が保護されていないという記述から、 注文などのデータ項目が操作されうると読める**（本記録の整理）。 **公表された対処に「注文データに不整合がないか監査すること」が 含まれているのは、すでに通された操作が記録として残っていることを 前提にしている**（本記録の評価）。 **ただし「不整合」の具体的な内容は公表されていない**〈未確定4〉。

対処に「注文データの監査」が入っている——更新だけでは終わらない種類の脆弱性対策・注意喚起出典 [1]

アドバイザリの対処欄に、見慣れない行が入っています。

公表された対処は2つです（出典1）。

  1. 3.x 系を使っている場合は Commerce Core 3.3.13 へアップグレードする。それ以前のバージョンを使っている場合は 8.x-2.41 へアップグレードする。
  2. 「サイトは注文データに不整合がないか監査すべきである。この脆弱性は実際に悪用されているため」（原文英語。本記録の訳）

②が入っている理由は、脆弱性の性質にあります（本記録の整理）。

アクセス制御の回避は、アプリケーションから見れば「成功した正当な要求」です。例外も出ません。エラーログにも残りません。残るのは、その結果として作られた・変更されたデータだけです。

だから、更新で経路を塞いだあとに、通ってしまった分を自分で探す必要があります。 Drupal はそれを対処として明記しました—— 本記録はこの点を機能していると評価します（本記録の評価）。「更新して終わり」にさせなかったことが、この事案で最も実務的な部分です。

ただし、探すための手がかりがありません（本記録の指摘）。「不整合」が何を指すのか、書かれていないのです〈未確定4〉。価格でしょうか。数量でしょうか。支払い状態でしょうか。適用された割引でしょうか。配送先でしょうか。「販売者に金銭的な被害が及ぶおそれがある」という記述から金額に関わる項目が中心と読めますが、これは本記録の推測です。

待っていても出ない可能性があります。 本記録が提案する起点を挙げます（本記録の判断。Drupal が示したものではありません）。

  • ①注文明細の合計額と、決済代行から得た実際の入金額の差分
  • ②支払い状態が「支払い済み」に遷移したが、決済通知が無い注文

CISO・経営層への示唆
  • 「更新して終わり」にならない脆弱性がある——認可の回避は通った分を自分で探す必要がある
    本件のアドバイザリは、更新に加えて 「注文データに不整合がないか監査すること」を求めている。 アクセス制御の回避は、アプリケーションにとって 「成功した正当な要求」として記録されるため、エラーログに残らない。 残るのは、その結果として作られた・変更されたデータだけである。
    取るべき行動 脆弱性対応の手順に「塞いだ後に、通った分を探す必要があるか」の 判定を入れる。認可・認証の回避、権限昇格、 データ改ざんを伴う種類については、 業務データの突き合わせを対応項目として必須にする。 対象期間の決め方（最古の脆弱な版の導入時期まで遡る）を事前に決める。
  • CVSS と KEV を前提にした優先度判定では、本件のような脆弱性が拾えない
    本件には CVSS 基本値が付与されていない（報道は「N/A」と記している）。 また、本記録の確認時点で CISA の KEV にも収載されていない。 それでも Drupal は「Highly critical・21/25」とし、 「実際に悪用されている」と明記している。 スコアと KEV だけを入口にしている運用では、本件は検知されない。
    取るべき行動 脆弱性管理の入口に「利用しているソフトウェアのベンダー／ コミュニティのアドバイザリ」を一次の経路として登録する。 CVSS が無い場合の代替基準（ベンダー独自の区分、悪用の記述の有無）を 社内基準に明記する。 緊急パッチの起点を「KEV 収載」ではなく 「ベンダーが悪用を記述した時点」に前倒しする。
  • EC の金銭的な整合性を日次で確認する仕組みが、脆弱性対応の前提になる
    本件の被害は「販売者に金銭的な被害が及ぶ」形で現れる。 注文明細の合計額と実際の入金額の突き合わせを日常的に行っている組織は、 監査の指示にすぐ応じられる。 行っていない組織は、何をどう突き合わせるかを決める作業から始める。 この差は、脆弱性が公表された日に現れる。
    取るべき行動 注文明細の合計額と決済代行から得た入金額の日次照合を、 業務プロセスとして持つ（セキュリティの仕組みとしてではなく、経理の統制として）。 支払い状態の遷移を監査ログに残し、 決済通知を伴わない遷移をアラート化する。
  • コントリビュート部品の一括公開日を、仕分けの日として運用に組み込む
    本件は、2026年10月28日に公開された39件のアドバイザリのうちの1件である。 対象は21のコントリビュートプロジェクトで、うち10件以上が Critical。 同じ日に Stripe 経由の注文が支払いなしで「支払い済み」と 記録されうる不具合も出ている。 全件を同列に見ていると、悪用されている1件が埋もれる。
    取るべき行動 利用している CMS・フレームワークのアドバイザリ公開日を把握し、 その日に「悪用の記述があるものを先に抜く」仕分けを行う担当と手順を決める。 自社が使っているモジュールの一覧を機械可読で持ち、 アドバイザリと機械的に突き合わせられるようにする。
セキュリティ技術者への示唆
  • 使っているコントリビュートモジュールと版を、機械可読な一覧として持つ
    本件の対象は「2.41 未満、および 3.0.0 以上 3.3.13 未満」である。 39件のアドバイザリが同日に出た状況で、 自サイトが該当するかを即断するには、 モジュール名と版の一覧が機械可読であることが要る。 手で確認する運用では、仕分けだけで1日が溶ける。
    取るべき行動 Composer の lock ファイル等から、導入済みモジュールと版を 定期的に出力して保管する。 アドバイザリの対象版と機械的に突き合わせる仕組みを用意する （一覧の形式を揃えるだけでも効果がある）。
  • 認可の回避はエラーログに残らない——残るのはアクセスログとデータの変化だけ
    本件は、保護されていないルートとエンティティフィールドへの アクセス制御の回避である。 アプリケーションから見れば成功した要求であり、 例外もエラーも発生しない。 公表された対処が「注文データの監査」なのは、この性質の裏返しである。
    取るべき行動 ウェブサーバのアクセスログを90日以上保持し、 経路（URL）単位で集計できる状態にする。 注文・商品・価格のエンティティに対する変更履歴を保持し、 誰が・いつ・どのフィールドを変えたかを遡れるようにする。
  • 「不整合」の定義を、ベンダーの指示を待たずに自分で決める
    アドバイザリは「注文データに不整合がないか監査せよ」と求めるが、 不整合が何を指すかは書かれていない。 価格か、数量か、支払い状態か、割引か——手がかりが無い。 待っていても出ない可能性がある。
