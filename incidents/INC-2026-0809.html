INC-2026-0809現代イージーウェル会員情報が流出

2026年10月29日21時ごろ、韓国の福利厚生プラットフォーム事業者 **現代イージーウェル（현대이지웰）** が、**会員情報照会 API への外部からの 異常なアクセス**を検知した。同社は攻撃元 IP を遮断し、当該システムへの 外部からのアクセスを全面停止したうえで、**金融監督院（FSS）と 韓国インターネット振興院（KISA）へ届け出た**。翌10月30日、 **朴鍾善（박종선）代表取締役名義の謝罪文**をホームページに掲載し、 **氏名・生年月日・性別・携帯電話番号・メールアドレス**の流出を認めた。 同社は**公共機関・企業の「選択的福利制度」を受託運営**する事業者で、 **顧客約2,700社・利用従業員約340万人**を抱える。 **流出規模は本記録の作成時点でも公表されていない。** **二次被害は確認されていないとされる。**

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）
初報: 2026年10月30日（現代イージーウェルの謝罪文掲載・同日の報道） 最終更新: 2026年10月31日

狙われたのは、会員情報を「照会する」ための API でした。

2026年10月29日21時ごろ、現代イージーウェルは会員情報照会 API に外部からの異常なアクセスがあることを検知しました（出典1・2）。同社は、検知した直後に攻撃元の IP を遮断し、当該システムへの外部からのアクセスを全面的に停止しています（出典1・2）。

翌30日、同社は朴鍾善（박종선）代表取締役名義の謝罪文をホームページに掲載しました（出典2）。流出が確認された項目は、氏名・生年月日・性別・携帯電話番号・メールアドレスです（出典1・2）。謝罪文は「お客様に心配と不安を与えた点を深くお詫びする」とし、「今回の事故を機に、全社の保安システムと脆弱性を原点から全面的に再点検する」としています（出典2・原文韓国語）。

この事案が日本の読者に関係するのは、会社の立ち位置です。 現代イージーウェルは、公共機関・企業の「選択的福利制度」（福利厚生ポイント制度）を受託運営する専門事業者で、顧客約2,700社・利用従業員約340万人を抱えています（出典3）。つまり、1社の API が破られると、2,700社の従業員の個人情報がまとめて露出し得る構造です（本記録の整理）。日本でも福利厚生・健康管理・社宅・慶弔のサービスは外部委託が一般的で、同じ形の集中が起きています（本記録の評価）。

肝心の規模は、まだ出ていません。 「正確な流出規模は現在把握中」というのが、本記録の作成時点での公表内容です（出典1・2）〈未確定1〉。340万人という数字は利用者の母数であって、流出した人数ではありません（本記録の整理）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表されているのは「会員情報照会 API に外部からの異常なアクセスがあった」という 一文だけである**（出典1・2）。 **以下の各段階は、その記述と対応の内容（攻撃元 IP の遮断・当該システムの外部アクセス停止）から 整理したもので、同社が公表した攻撃の解析結果ではない**（本記録の整理）。 **確かなのは、①狙われたのが会員情報を照会する API であること、 ②同社が「異常」として検知できる形の通信だったこと、 ③遮断の単位が IP だったこと、の3点である**（出典1・2）。

  1. 1. 偵察推定
    **会員情報照会 API の所在と呼び出し方を把握する段階。** **公表された記述はない**（出典1・2）。 **本記録の整理では、福利厚生ポイントのショッピングモールという業態上、 会員向けのウェブ・モバイルアプリから同じ API が呼ばれているため、 正規の利用者として観察すれば呼び出し方は分かる位置にある。**
    根拠: 公表された記述はない（業態からの整理）
  2. 2. 初期侵入確認済[1] [2]

    根拠: 同社の公表（회원정보 조회 API에 외부의 비정상적인 접근이 발생）

破られたのは画面ではなく、会員情報を照会するための API だった原因・手口出典 [1] [2] [3]

現代イージーウェルが公表したのは、次の一文です（出典1・2・原文韓国語）。

「会員情報照会 API に外部からの異常なアクセスが行われ、調査の過程で個人情報の流出が確認された」

この一文から読み取れることと、読み取れないことを分けておきます（本記録の整理）。

読み取れること。 攻撃の対象が会員情報を「照会する」API だったこと。その API が外部から到達できる位置にあったこと。そして、同社が「異常」として見分けられる形の通信だったことです（出典1・2）。

読み取れないこと。 認可の不備なのか、正規の資格情報が悪用されたのか、レート制限が無かったのか、パラメータを改変されたのか——どれなのかは示されていません〈未確定3〉。報道の一部は「API の脆弱性」という語を使っていますが、これは同種事案を並べた文脈の中の表現で、当事者の説明ではありません（出典3）〈差異2〉。

この区別が出てこないかぎり、同じ構造を持つ他社は自組織を点検できません（本記録の評価）。「会員情報を返す API がある」だけでは、確認すべき箇所が決まらないためです。

本記録が評価するのは、遮断の単位です（本記録の評価）。同社は攻撃元 IP の遮断で止めず、当該システムへの外部アクセスを全面的に停止しています（出典1・2）。IP 単位の遮断だけなら、発信元を変えて再試行されれば効きません。システム単位で切ったことで、その経路を同時に塞いでいます。

公表の速さも妥当だと考えます（本記録の評価）。流出項目が氏名・生年月日・性別・携帯電話番号・メールアドレスである以上、悪用はスミッシングとフィッシングの形で来ます。注意喚起は規模の確定を待つより早いほうが効きます。

ただし、謝罪文の「全社の保安システムと脆弱性を原点から全面的に再点検する」という表明は、範囲も期限も実施主体も示していません（出典2）。委託元が自社の対応を決める材料にはなりません（本記録の評価）。

340万人は母数であって、流出した人数ではない被害規模・影響範囲出典 [1] [2] [3]

本件でもっとも誤読されやすいのが数字です（本記録の整理）。

公表されている数値は、会社の規模だけです（出典3）。

  • 利用従業員 約340万人 — サービスの利用者の母数
  • 顧客 約2,700社 — 選択的福利制度を委託している組織の数
  • 市場の約50% — 同社が占める割合（算定基準は示されていない）

流出した人数は「把握中」です（出典1・2）〈未確定1〉。340万人を流出人数として読むと、実態より大きく見積まれる可能性があります。逆に、照会が自動化されていれば母数に近づく可能性も否定できません——どちらとも言えないのが現状です（本記録の整理）。

流出項目についても、報道の間で食い違いがあります。 謝罪文を直接引用している報道は5項目（氏名・生年月日・性別・携帯電話番号・メールアドレス）を挙げていますが、보안뉴스は住所を加えた6項目として報じています（出典1・2・3）〈差異2〉。住所が含まれるかどうかは、郵送型の詐欺が成立するかを変えるため、本人通知の文面にも影響します（本記録の評価）。

なお、同社サイトに掲載された謝罪文そのものは、本記録から取得できていません〈差異1〉。上記はすべて、謝罪文を引用した韓国の報道を経由した内容です。

委託元2,700社は、自社が対象かを自力では判断できない波及・関係先出典 [1] [2] [3]

この事案の構造上の要点は、被害者の位置です（本記録の整理）。

現代イージーウェルは、公共機関・企業の「選択的福利制度」を受託運営する事業者です（出典3）。流出した会員情報は、同社自身の顧客の情報ではなく、委託元である約2,700社の従業員の情報です。

ところが、どの組織の従業員が対象かは公表されていません〈未確定2〉。被害が無いと確認された組織の扱いも示されていません（本記録の確認）。委託元の側から見ると、次の状態になります。

  • 自社の従業員が対象か分からない
  • 分からないまま、従業員への説明を求められる
  • 受託事業者からの個別連絡を待つしかない

보안뉴스は、韓国でこの形の事案が続いていることを指摘しています（出典3）—— ソニーネットワークコミュニケーションズ、学習管理システム（LMS）の受託運営事業者、学会サイトの構築・保守の受託運営事業者が、いずれも同じ経路で破られています。

日本でも同じ集中が起きています（本記録の評価）。福利厚生・健康管理・社宅・慶弔・EAP は外部委託が一般的で、委託先には従業員名簿の写しが置かれています。 自社のシステムをいくら固めても、この経路は残ります。

本人通知の母数は、照会 API のログ設計で先に決まっている評価・解釈出典 [1] [2]

「規模が把握中」という状態が何を意味するかを考えると、技術的な論点が1つ浮かびます（本記録の評価）。

侵害の規模を確定するには、「どの会員の、どの項目が照会されたか」をログから再構成する必要があります。 同社が攻撃元 IP を特定できていることから、呼び出し元を識別できる記録は存在したと整理できます（出典1・2・本記録の判断）。一方、規模の確定に時間がかかっている事実は、対象の会員を単位とした復元に手間がかかっていることを示します（本記録の整理）。

ここは設計で決まる部分です。 個人情報を返す API のログに「呼び出し元」「対象の会員 ID」「返した項目」の3つが揃っていれば、規模の確定は照会の集計で終わります。揃っていなければ、通知の母数そのものが確定しません（本記録の評価）。

本記録が技術者に薦める確認は、侵害の後ではなく今できるものです。

  1. 個人情報を返す API について、認可を「対象の会員」単位で検証しているかをコードで確認する
  2. 資格情報単位・時間単位の照会件数に上限を設け、上限到達を即時に通知する
  3. アクセスログに対象の会員 ID と返した項目が残る設計かを確認し、保存期間を決める

3番目は、侵害を防ぐ対策ではありません。 侵害が起きたときに「誰に通知すべきか」を答えられるようにする対策です（本記録の判断）。
