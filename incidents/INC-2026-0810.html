INC-2026-0810Applebee's アプリにDBパスワード

2026年10月、英国の研究者 **Robert Wiggins**（What Security）が、 米レストランチェーン **Applebee's** の Android アプリの中に **社内データベースの資格情報が埋め込まれている**（ハードコード）ことを発見した。 **アプリを入手した者は誰でも、登録顧客の個人情報を含むデータベースへ 正規の利用者として接続できる状態だった。** 露出していた項目は**氏名・メールアドレス（確認済みか否かを含む）・生年月日・ 電話番号・郵便番号・退役軍人資格・ログイン回数・アカウント作成日時・ 直近ログイン時の IP アドレス**で、**研究者によれば書き換えも可能**だった。 研究者は Applebee's と親会社 **Dine Brands** に通報する手段が見つからず、 TechCrunch を介して連絡した。**2026年10月29日に修正が確認された。** Dine Brands は**「現時点で不正アクセスの証拠は見つかっていない」**とする一方、 **確認に使えるサーバログを保有しているかという問いには答えなかった。** **影響を受けた顧客数は公表されていない。**

意図せぬ露出（設定不備等で外部から到達可能だった）脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備
初報: 2026年10月30日（TechCrunch の報道） 最終更新: 2026年10月31日

アプリを配布することは、アプリの中身を配布することです。

2026年10月、英国の研究者 Robert Wiggins（What Security）が、Applebee's の Android アプリのソースコードの中に、社内データベースの資格情報が埋め込まれているのを見つけました（出典1）。Google Play での配信数は100万件を超えています（出典1）。つまり、100万回以上ダウンロードされたファイルの中に、顧客データベースへの鍵が入っていたことになります（本記録の整理）。

TechCrunch は自分で検証しました（出典1）。同誌はアプリをダウンロードして逆コンパイルし、資格情報の存在を確認したうえで、ダミーのデータでアカウントを作成しています。そのダミーの情報を研究者がデータベースから取り出せたことで、経路が実際に通ることが確かめられました。

露出していた項目は、思っていたより多いはずです（出典1）。

氏名、メールアドレス（確認済みか否かの別を含む）、生年月日、電話番号、郵便番号、退役軍人資格、ログイン回数、アカウント作成日時、直近ログイン時の IP アドレス

最後の IP アドレスは、その人のおおよその所在地を示します（出典1）。さらに研究者は、この資格情報があれば顧客データの書き換えも可能だったとしています（出典1）。

本記録が重く見るのは、通報経路が無かったことです。 Wiggins は Applebee's にも親会社の Dine Brands にもセキュリティ上の問題を報告する手段を見つけられず、TechCrunch に仲介を頼みました（出典1）。見つけた人が報告できない会社は、見つけてもらえない会社と同じです（本記録の評価）。

そして、不正アクセスの有無は分からないままです。 Dine Brands の広報担当者（氏名は示されていない）は2026年10月30日、TechCrunch にこう述べました（出典1・原文英語）。

「TechCrunch とセキュリティ研究者が本件を我々の注意に向けてくれたことに感謝する。当社のセキュリティチームは速やかに調査を開始し、現時点で不正アクセスの証拠は見つかっていない」

しかし TechCrunch が「誰かがデータベースにアクセスしたかを調べられるサーバログを持っているのか、そもそもログはあるのか」と尋ねたところ、同社は答えませんでした（出典1）〈未確定2〉。「証拠が見つかっていない」が、「調べた結果、無かった」なのか「調べる記録が無い」なのかは区別できません（本記録の評価）。

100万回ダウンロードされたアプリの中に、データベースの鍵が入っていた原因・手口出典 [1]

本件の構造は単純です（出典1）。

  1. Applebee's の Android アプリに、社内データベースの資格情報が埋め込まれていた
  2. アプリは Google Play で100万件以上ダウンロードされている
  3. 逆コンパイルすれば、誰でもその資格情報を読み出せる
  4. その資格情報で、顧客データベースへ正規の利用者として接続できた

TechCrunch はこの種の不備をこう説明しています（出典1・原文英語）。

「ソフトウェアにパスワードや秘密鍵を保存すること（資格情報のハードコード）は、もっとも深刻な種類のセキュリティ脆弱性の一つである。アプリを持つ者が誰でも鍵を抽出し、認可された利用者であるかのように遠隔システムへログインできてしまうためだ」

本記録が強調したいのは、この不備の「取り返しのつかなさ」です（本記録の評価）。サーバ側の設定不備なら、設定を直せば露出は終わります。しかし配布物に入った秘密は、配布した時点で外に出ています。 100万台以上の端末に、鍵を含むファイルが既に届いているという状態です。

そして、この経路は防御側のログに何も残しません（本記録の判断）。逆コンパイルは攻撃者の手元で完結するためです。 残るのは、資格情報を使って接続してきた記録だけ——しかもそれは正規の資格情報による接続として記録されます。

発見者は通報先を見つけられず、報道機関に仲介を頼んだ発覚の端緒出典 [1]

発見したのは英国の研究者 Robert Wiggins（What Security）です（出典1）。2026年10月の初めに見つけ、数千行のソースコードの中から資格情報を探し出すのに AI を使ったとしています（出典1）。

ところが、報告する先がありませんでした（出典1）。

Wiggins は Applebee's にも親会社の Dine Brands にも通知できなかった——いずれもセキュリティ上の問題を報告する手段を持っていなかったためである（原文英語）

そこで、TechCrunch に開示の仲介を依頼しています（出典1）。TechCrunch は受け取った内容を自分で検証しました—— アプリをダウンロードして逆コンパイルし、資格情報の存在を確認。さらにダミーのデータで Applebee's のアカウントを作成し、その情報を Wiggins がデータベースから取り出せることを確かめています（出典1）。経路が実際に通ることを、第三者が独立に実証した形です。

TechCrunch は、不具合の修正が確認されるまで記事の公開を見送りました（出典1）。修正の確認は2026年10月29日（木）、記事の公開は翌30日（金）です（出典1）。

本記録が評価するのは、この一連が「仕組み」ではなく「個人の善意と報道機関の協力」で成り立っていることです（本記録の評価）。窓口が無い会社は、通報される確率そのものが下がります。 同じ資格情報を見つけた別の者が、同じ選択をする保証はありません。

人数は分かりません（出典1）〈未確定1〉。Applebee's は影響を受けた顧客数の提示を拒みました。前年時点で報酬プログラムには少なくとも850万人が登録していましたが、これは母数です（出典1・本記録の整理）。

研究者が数えなかった理由は、記録しておく価値があります（出典1）。

データベース内の顧客数を把握するには、AI モデルに不必要にほぼ全ての顧客レコードへアクセスさせることになるため、数えなかった（原文英語）

規模を知る手段はありましたが、意図的に行使されていません。 攻撃者が同じ自制をする理由はありません（本記録の評価）。

「証拠は見つかっていない」と言いながら、ログの有無には答えなかった未確定事項出典 [1]

Dine Brands の声明は、2026年10月30日に TechCrunch へ電子メールで送られたものです（出典1・原文英語）。

「TechCrunch とセキュリティ研究者が本件を我々の注意に向けてくれたことに感謝する。当社のセキュリティチームは速やかに調査を開始し、現時点で不正アクセスの証拠は見つかっていない」 「調査は継続中であり、所見に基づいて適切な措置を取る」

問題は、TechCrunch が続けて尋ねたことに答えていない点です（出典1）。

  • 誰かがデータベースにアクセスしたかを判断できるサーバログを持っているのか — 無回答〈未確定2〉
  • そもそもログはあるのか — 無回答〈未確定2〉
  • 資格情報がアプリに入っていた期間はどれだけか — 無回答〈未確定3〉
  • 顧客や米国の規制当局へ通知するのか — 無回答〈未確定4〉
  • 上場企業として SEC へ開示するのか — 無回答〈未確定4〉

本記録は、この声明を「悪用が無かった」ことの根拠として扱いません（本記録の評価）。理由は明確です。ハードコードされた資格情報による接続は、正規の資格情報による接続と見分けがつきません。 接続元・頻度・取得量を記録していなければ、悪用の有無は原理的に判定できないのです（本記録の判断）。

つまり「証拠が見つかっていない」は、「調べたが無かった」とも「調べる記録が無い」とも読めます。 ログがあるかどうかは、調査の途中でも答えられる事実です。それに答えないことが、本件でもっとも実務的な欠落です（本記録の評価）。

なお、本記録の作成時点で、Applebee's・Dine Brands のいずれも自社サイトに本件の公表を掲載していません〈差異1〉。当事者の見解は、報道に引用された声明としてしか存在しません。

修正の内容が示されないため、過去版のアプリから到達できるかも分からない対策・注意喚起出典 [1]

修正は2026年10月29日に確認されています（出典1）。しかし、何をしたのかは公表されていません〈未確定5〉。

考えられる対処は、少なくとも3つあります（本記録の整理）。

  1. 資格情報を失効させた — 過去版のアプリからも到達できなくなる
  2. アプリを更新して資格情報を取り除いた — 更新しない端末には資格情報が残る
  3. データベースへの経路（ネットワーク・認可）を遮断した — 失効と同等の効果

2番だけだった場合、問題は解消していません（本記録の評価）。既に配布済みの版を使い続けている端末からは、同じ資格情報が抽出できます。 どの対処を取ったかが示されないため、利用者側が「アプリを更新すべきか」を判断する材料もありません。

本記録が読者に薦める確認は、Applebee's の話ではなく自社の話です（本記録の判断）。

  1. 自社が配布しているアプリを手元で逆コンパイルし、資格情報・秘密鍵が含まれていないかを確認する。結果を記録に残す
  2. アプリから直接データベースへ接続している経路が無いかを確認し、あればサーバ側の API 経由に寄せる
  3. アプリ・外部連携が使う資格情報の権限を棚卸しし、更新・削除の権限を読み取り専用に分離する
  4. 自社サイトに脆弱性の報告先（security.txt または専用の連絡先）を置く

4番目は技術的な対策ではありませんが、本件で最初に失敗した箇所です（本記録の評価）。発見者が報告できなければ、修正は始まりません。

CISO・経営層への示唆
  • 配布したアプリは、取り戻せない公開物である
    **資格情報は、Google Play で100万件以上配信されたアプリの中にあった**（出典1）。 **逆コンパイルすれば誰でも抽出できる状態で、 防御側のログには何も残らない**（出典1・本記録の評価）。 **サーバ側の設定不備なら閉じれば終わるが、 配布物に入った秘密は配布した時点で失われている**（本記録の評価）。
    取るべき行動 **自社が配布しているモバイルアプリ・デスクトップアプリ・ 社外に渡すスクリプトについて、 「配布物に秘密情報が入っていないこと」を確認する責任者と確認方法を決める。 確認は自社で逆コンパイルして行い、結果を記録に残す。**
  • 脆弱性の通報窓口が無い会社は、通報されない会社である
    **発見者は Applebee's にも Dine Brands にも報告手段を見つけられず、 報道機関に仲介を頼んだ**（出典1）。 **本件では善意の研究者が報道機関を選んだが、 同じ発見をした別の者が同じ選択をする保証は無い**（本記録の評価）。
    取るべき行動 **自社のウェブサイトに脆弱性の報告先（`security.txt` または専用の連絡先）を置き、 受理から一次回答までの目安を明記する。 窓口に届いた報告を誰が読み、誰が判断するかも併せて決める。**
  • 「不正アクセスの証拠は見つかっていない」は、ログの有無を確かめてから読む
    **Dine Brands はこの表現を使いつつ、 確認に使えるサーバログを保有しているかという問いには答えなかった**（出典1）〈未確定2〉。 **正規の資格情報による接続は、 接続元・頻度・取得量を記録していなければ悪用と区別できない**（本記録の判断）。
    取るべき行動 **自社または委託先から「不正アクセスの痕跡なし」という報告を受けたとき、 ①どのログを ②どの期間について ③何を条件に調べたかの3点を確認する質問を定型化する。 自社のデータベースについては、この3点に答えられる状態かを先に点検する。**
  • 開示の判断は、規模が分からないままでも求められる
    **影響を受けた顧客数は公表されておらず、 Applebee's は人数の提示を拒んでいる**（出典1）〈未確定1〉。 **一方、Dine Brands Global は上場企業であり、 重要なサイバーセキュリティ事案の開示義務がかかる**（出典1）。 **TechCrunch の問いにも答えていない**（出典1）〈未確定4〉。
    取るべき行動 **「影響範囲が確定しない段階での開示・通知の基準」を事前に決めておく。 規模が不明という事実そのものを開示の要素として扱うか、 確定を待つかを、法務と合わせて文書化する。**
セキュリティ技術者への示唆
  • 秘密情報のスキャンを、リリースを止める条件として CI に入れる
    **資格情報は数千行のソースコードの中に埋め込まれていた**（出典1）。 **人のレビューで見つけるのは現実的でない**—— **発見者は AI を使って見つけ出したとしている**（出典1）。
    取るべき行動 **モバイルアプリのビルドパイプラインに秘密情報スキャンを組み込み、 検出時にリリースを失敗させる。 既に公開済みの版についても、手元で逆コンパイルして同じスキャンをかける。**
  • アプリから直接データベースへ接続させない
    **アプリに資格情報を持たせる設計は、 その資格情報が配布物の中に存在することを意味する**（出典1・本記録の整理）。 **抽出されれば、アプリの画面で課していた制約はすべて迂回される。**
    取るべき行動 **アプリからの経路をサーバ側の API に限定し、 データベースの資格情報はサーバ側だけが持つ構成にする。 既存のアプリにデータベースの資格情報が渡っていないかを、 ネットワーク監視または逆コンパイルで確認する。**
  • アプリ経由の権限は読み取り専用に分ける
    **研究者は、この資格情報があれば顧客データの書き換えも可能だったとしている**（出典1）。 **本記録の評価では、読み取りの露出より書き換えの可能性のほうが重い**—— **連絡先を書き換えられれば、本人確認の迂回やアカウント乗っ取りに使える** （本記録の判断）。
    取るべき行動 **アプリ・外部連携が使う資格情報の権限を棚卸しし、 更新・削除の権限が付いているものを読み取り専用に分離する。 更新が必要な処理は、別の権限を持つサーバ側の経路に限定する。**
  • データベースへの接続ログを、接続元と取得量で見られるようにする
    **本件では、悪用の有無を判定できるかどうかがログの有無に依存している**（出典1）〈未確定2〉。 **研究者は全レコードへのアクセスを避けて件数を数えなかったが、 攻撃者が同じ自制をする理由は無い**（出典1・本記録の評価）。
    取るべき行動 **顧客データを保持するデータベースについて、 接続元・問い合わせの件数・返したレコード数を記録し、 「通常の業務では起こらない取得量」を検知条件として常設する。 保存期間を、侵害の調査に必要な期間から逆算して決める。**
