Airoha 製 Bluetooth オーディオ SoC の社内用コマンドプロトコル **RACE** が、 ペアリングも認証も要さずに電波で到達できる状態で出荷されていた—— ドイツの **ERNW** の研究者2人（Dennis Heinze・Frieder Steinmetz）が 2025年3月25日に Airoha へ報告し、6月26日に技術詳細なしで部分公開、 **12月27日の 39C3 で全面公開した。** **CVE-2025-20700（BLE GATT の認証欠如）・CVE-2025-20701（Bluetooth Classic の 認証欠如）・CVE-2025-20702（RACE が持つ危険な機能）の3件**で、 **電波の届く範囲にいる第三者がヘッドホンのフラッシュを読み出し、 「スマートフォンとヘッドホンのリンクキー」を平文で取り出せる。** **取り出した鍵でヘッドホンを名乗り直すと、利用者の端末は何も尋ねずに接続を受け入れる**—— 研究者はそこからハンズフリー通話プロファイル（HFP）で電話番号を聞き出し、 **WhatsApp の電話認証の着信を端末が鳴る前に自動応答して読み上げコードを奪い、 アカウントを引き継ぐところまで実証した**（同じ番号で Amazon のログインも成立）。 **対象として列挙されたのは Sony・Bose・JBL・Jabra・Marshall・Beyerdynamic・Teufel ほか 10社29機種**だが、研究者は「**これは影響を受ける機器の完全な一覧ではない**」と明記している。 **Airoha は2025年6月4日に緩和を含む SDK を各社へ渡したが、 配布状況は社ごとに揃わず、研究者は「現在の修正状況の全体像は無い」と書いている。** **本記録は2026年10月31日のロシア語媒体の解説記事を起点に、 研究者側の全面公開の原文と GitHub Advisory Database を取得して作成した**

壊れていたのは暗号ではありません。「誰が話しかけてよいか」の判定が無かっただけです。

ドイツの ERNW（ERNW Enno Rey Netzwerke GmbH）の研究者Dennis Heinze と Frieder Steinmetz は、Bluetooth Auracast の調査の過程で、台湾 Airoha Technology Corp. の Bluetooth オーディオ SoC がRACE という社内用のコマンドプロトコルを外部に向けて開けたままにしていることを見つけました。

RACE はもともと製造時の試験とファームウェア更新のためのもので、USB HID（レポート ID 0x06／0x07）で使う前提の面です。ところがこれが Bluetooth LE の GATT と Bluetooth Classic の RFCOMM（多くは channel 21）からも到達でき、どちらもペアリングを要しませんでした。割り当てられた CVE は3件です。

CVE 内容（研究者の記述）
CVE-2025-20700 BLE の GATT サービスに認証が無い（Missing Authentication for GATT Services）
CVE-2025-20701 Bluetooth Classic（BR/EDR）に認証が無い
CVE-2025-20702 RACE プロトコルが危険な機能を外に出している

RACE で使えるコマンドには、ビルド版の取得（0x1E08）・フラッシュの読み出し（0x0403）・RAM の読み書き（0x1680／0x1681）・Bluetooth アドレスの取得（0x0CD5）が含まれます。つまり、話しかけるだけで他人のヘッドホンのメモリが読めます。

本当に取られるのは音ではありません。フラッシュの中の設定領域（NVDM）には接続テーブルがあり、そこにペアリング済みのスマートフォンの Bluetooth アドレスとリンクキーが平文で入っています。リンクキーは、スマートフォンが「このヘッドホンは信用してよい」と判断する根拠です。

攻撃者はこれを取り出し、アドレスを書き換えられる Bluetooth アダプタに鍵を読み込ませてヘッドホンを名乗り直します。利用者の端末は何も尋ねずに接続を受け入れます。あとはハンズフリー通話プロファイル（HFP）の仕事です。AT+CNUM で加入者番号（電話番号）を聞き出し、AT+BVRA で音声アシスタントを起こし、通話を乗っ取り、マイクを聞くことができます。

研究者はここから先も実証しました。聞き出した電話番号を自分の端末の WhatsApp に入れ、認証方法として「電話で知らせる」を選ぶ。WhatsApp からの自動音声の着信を、利用者の端末が鳴る前に HFP 経由で自動応答させる。読み上げられたコードを入れてアカウントを引き継ぐ—— 39C3（2025年12月27日）で全面公開された内容です。 同じ電話番号で Amazon のログインも成立したと報告されています。

対象として列挙されたのは10社29機種です。Beyerdynamic・Bose・EarisMax・Jabra・JBL・Jlab・Marshall・MoerLabs・Sony・Teufel。ただし研究者は「これは影響を受ける機器の完全な一覧ではない」と明記しています。

そして、直し方は利用者の手の中にありません。 Airoha は報告から約2か月後（2025年6月4日）に緩和を含む SDK を各社へ渡しました。しかし、そこから先の「ブランドがファームウェアを作ってエンドユーザへ届ける」部分が揃いませんでした。 Jabra は3件の CVE を公表して5機種以上に配布し、Beyerdynamic と Marshall は更新を出しましたが、Teufel は CVE に触れない無言の修正、Sony は当初回答が無く、研究者は「現在の修正状況の全体像は無い」と書いています。

日本の読者にとっての論点は「ヘッドホンが危ない」ではありません。 ①社内向けの試験用インターフェースを、出荷する製品の外向きの経路に残していないか。②買った製品の中にある他社製のチップのファームウェアを、誰が更新するのか。③電話番号を本人確認に使っているアカウントが、社内にいくつあるか——この3つです。

ERNW の2人の研究者が調べたのは Bluetooth Auracast でした。仕様の細かな粗を拾うつもりの作業の中で見つかったのが、Airoha の Bluetooth オーディオ SoC にある RACE というコマンドプロトコルです。

RACE は製造時の試験とファームウェア更新のためのもので、本来は USB HID（レポート ID 0x06 がホスト→機器、0x07 が機器→ホスト）で使います。ところが同じ面が、

  • Bluetooth Classic の RFCOMM（多くは channel 21・ベンダー固有の UUID）
  • Bluetooth LE の GATT（TX キャラクタリスティックへ送り、RX から受ける）

からも到達でき、どちらもペアリングを要しませんでした。研究者の記述は「ペアリングは必要なかった」（原文英語）です。

使えるコマンドには次のものが含まれます。

コマンド 内容
0x1E08 ビルド版の取得（機種の特定に使える）
0x0403 フラッシュの読み出し
0x1680 / 0x1681 RAM の読み書き（メモリマップド I/O を含む）
0x0CD5 Bluetooth アドレス（BD_ADDR）の取得

書き込みはファームウェア更新用の領域に限られますが、読み出しには制限がありません。 0x0CD5 で固定の Classic アドレスが取れることは、BLE のアドレスランダム化を無意味にします——つまり同じヘッドホンを着けている人を、場所をまたいで追跡できます。

盗まれるのは音ではなく「スマートフォンがヘッドホンを信じる根拠」原因・手口

フラッシュを読めることの意味は、音の盗聴ではありません。

Airoha の機器のフラッシュには NVDM という設定領域があり、そこに接続テーブルが置かれています。テーブルには、ペアリング済みの端末の Bluetooth アドレスとリンクキーが平文で入っています。

リンクキーは、スマートフォンが「このヘッドホンは以前ペアリングした、信用してよい相手だ」と判断する根拠です。これを取り出せば、攻撃者はヘッドホンそのものになれます。

研究者が示した手順は4段落です。

  1. 接続 — 近接する攻撃者が BLE か Classic で接続する（CVE-2025-20700／20701）。再生は止まりません。
  2. 持ち出し — RACE（CVE-2025-20702）でフラッシュを部分的にダンプする
  3. 抽出 — ダンプから接続テーブルを見つけ、端末のアドレスとリンクキーを取り出す
  4. なりすまし — アドレスを書き換えられるアダプタに鍵を読み込ませ、利用者の端末へ接続する。端末は何も尋ねません。

ここまでで、攻撃者は「利用者のスマートフォンに信用されたオーディオ機器」になります。あとはハンズフリー通話プロファイル（HFP）の標準的なコマンドです。

  • AT+CNUM — 加入者番号（電話番号）を取得する。研究者によれば、多くの端末は追加の許可を求めずに返します
  • AT+BVRA — 音声アシスタントを起動する
  • 通話の乗っ取りと、攻撃者の番号への発信による盗聴

破られたのは暗号ではありません。 「鍵を預けた先が、誰にでも鍵を見せる金庫だった」という話です（本記録の整理）。

電話番号が本人確認である限り、鎖の最後の輪はアカウントになる評価・解釈

39C3 で示されたのは、ここから先です。

  1. ヘッドホンから電話番号を聞き出す
  2. 攻撃者が自分の端末の WhatsApp にその番号を入れる
  3. 認証方法として「電話で知らせる」を選ぶ
  4. WhatsApp からの自動音声の着信を、利用者の端末が音を鳴らす前に HFP 経由で自動応答させる
  5. 読み上げられたコードを入れ、アカウントを引き継ぐ

同じ番号で Amazon のログインも成立したと報告されています。

ここが本件の重心です。失われたのはヘッドホンの制御権ではなく、電話番号を本人確認に使うすべてのアカウントです。 そして電話番号は、変えられません。

本記録の評価を2点書きます。

①「電話に出られる」ことは「本人である」ことの証明にならない、という前提が崩れた形ではありません。むしろ前から崩れていたものが、新しい経路で踏まれただけです。 SIM スワップも、音声通話の転送も、同じ前提を突いてきました。本件が加えたのは「被害者の端末に触らなくてよい」という条件です。

②この攻撃には「近くにいる」ことが必要です。電波の届く範囲に攻撃者がいなければ成立しません。だから不特定多数への大量攻撃には向かず、狙い撃ちに向きます。カフェ・空港・コワーキングスペースで長時間ヘッドホンを着けている人、という条件は、出張の多い役員や研究者にそのまま当てはまります。

CISO・経営層への示唆
  • 自社製品に載っている他社製チップのファームウェアを、誰が利用者へ届けるのかを決めておく
    **本件では、欠陥のある Airoha が報告から71日で SDK を修正したのに、 エンドユーザへの配布は10社以上に分かれ、揃わなかった。** **研究者は「現在の修正状況のまとまった全体像は存在しない」と書いている。** **製品を売った会社が窓口であり、チップ供給元の修正は売った会社が 配らなければ利用者に届かない。**
    取るべき行動 **自社が販売するハードウェア製品について、 ①使っている主要な SoC・無線モジュール・ファームウェアの供給元の一覧、 ②供給元から脆弱性情報を受け取る窓口と連絡先、 ③修正を受け取ってから自社ファームウェアとして配布するまでの標準日数、 ④配布の到達率をどう測るか、を文書で決める。** **とくに④を決めていない組織が多い**—— **「アプリ経由の更新」は、アプリを入れていない利用者には届かない。** 年1回、販売中の全機種で「最新版を使っている利用者の割合」を出す。
  • 「修正版の版数が公表されていない」欠陥は、資産台帳では管理できないと認める
    **本件の CVE-2025-20700 は、GitHub Advisory Database において 影響を受ける版・修正された版がいずれも「Unknown」と記載されている。** **突き合わせる相手が無いため、台帳に CVE 番号を載せても 「対処済みか」を判定できない。** **脆弱性管理を「台帳×版数の突き合わせ」で回している組織は、 この型の案件を静かに取りこぼす。**
    取るべき行動 **脆弱性台帳に「版数で判定できない案件」の置き場を作り、 判定方法（実機での検査・供給元への問い合わせ・代替策の適用）を 案件ごとに書けるようにする。** **判定できないまま放置された案件の件数を、月次で経営へ出す。** **件数がゼロなら、それは取りこぼしている疑いがある。**
  • 電話番号を本人確認に使っているアカウントの数を把握し、重要な口から外す
    **本件の最終段は、電話番号を聞き出し、着信を代わりに取ることで成立している。** **攻撃者は被害者の端末に一度も触っていない。** **電話番号は変更できず、SIM スワップや通話転送でも同じ前提が狙われてきた。** **「電話に出られる＝本人」という前提を使っている口が、 自社にいくつ残っているかが被害の上限を決める。**
    取るべき行動 **①役員・管理者・経理・広報の業務アカウントについて、 SMS と音声通話を二要素認証および復旧手段から外す。 ②外せないサービス（サービス側が電話番号の復旧経路を残しているもの）を 一覧にして、残存リスクとして記録する。 ③個人の WhatsApp・メッセージアプリが業務連絡に使われていないかを確認する** ——**本件で奪われたのは、まず個人のアカウントである。**
  • 「近くにいないと成立しない攻撃」を、だから安全とは読まない
    **本件は電波の届く範囲に攻撃者がいることを要する。** **大量攻撃には向かないが、狙い撃ちには向く。** **カフェ・空港・コワーキングスペース・ホテルのラウンジで 長時間ヘッドホンを着けている人、という条件は、 出張の多い役員や研究者にそのまま当てはまる。**
    取るべき行動 **渡航・重要会議の前後に適用する携行機器の規則を作る。** **最低限は「業務端末とペアリングしたオーディオ機器を、 渡航中は使わないか、ペアリングを解除する」。** **併せて、狙われうる立場の人（役員・M&A 担当・研究者・広報）を 個人単位で把握し、その人の端末だけ別の基準で扱う。** **全社一律にすると守れないので、対象を絞ることが要点である。**
セキュリティ技術者への示唆
  • 製造・試験用のインターフェースが、出荷時に外向きの経路から外れているかを確認する
    **RACE は製造時の試験とファームウェア更新のためのコマンド面で、 本来は USB HID で使うものだった。** **これが BLE の GATT と Bluetooth Classic の RFCOMM からも到達でき、 認証も無かった。** **「機能を増やしすぎた」のではなく、 「社内向けの面を外向きの経路に出したまま認証を付けなかった」のが欠陥である。** **同じ形は、組み込み機器の UART・JTAG・デバッグ用 HTTP・ 製造用の MQTT トピックなどに広く存在する。**
    取るべき行動 **自社製品の出荷ファームウェアについて、 「製造・修理・試験のために存在するコマンド面」を列挙し、 それぞれが①どの物理／論理経路から到達できるか、 ②認証があるか、③出荷ビルドで無効化されているかを表にする。** **表の空欄をゼロにすることが目標ではない**—— **「出荷後も有効で認証が無い」行が1つでもあれば、 それが本件と同じ形である。**
  • 長期の鍵を平文で持つ領域を、読み出し経路から切り離す
    **本件で致命的だったのは、フラッシュが読めたことそのものではなく、 設定領域 NVDM の接続テーブルに ペアリング済み端末のアドレスとリンクキーが平文で入っていたことである。** **リンクキーは「相手がこちらを信用する根拠」であり、 漏れた瞬間に機器のなりすましが成立する。** **鍵が平文で置かれていれば、読み出しの穴1つが認証の破綻になる。**
    取るべき行動 **自社製品が保持する長期の秘密（ペアリング鍵・デバイス証明書の秘密鍵・ API トークン・プロビジョニング鍵）を列挙し、 ①保存場所、②暗号化の有無と鍵の置き場、 ③汎用の読み出しコマンドの射程に入っているかを確認する。** **セキュアエレメントが無い SoC では、 少なくとも「汎用の flash read で読める場所に平文で置かない」ことを 設計の受け入れ条件にする。**
  • ハンズフリー通話プロファイル（HFP）で何が取れるかを、自組織の端末で実際に確かめる
    **攻撃の後半は、特殊な技術ではなく HFP の標準コマンドで成り立っている。** **`AT+CNUM` で加入者番号が返り、`AT+BVRA` で音声アシスタントが起動し、 着信を自動応答できる。** **研究者は「多くの端末は追加の許可を求めずに電話番号を返す」としている。** **つまり「ペアリング済みのオーディオ機器」は、 多くの組織が想定しているよりも強い権限を持っている。**
    取るべき行動 **業務で使っている端末（iOS／Android／MDM の構成ごと）で、 ①ロック中に音声アシスタントが起動できるか、 ②ロック中に着信の自動応答が成立するか、 ③ペアリング済み機器に電話番号が返るか、を実機で確認する。** **確認の結果を、端末の標準構成の設定値として固定する。** **「Bluetooth を許可する」という1行の設定が、 実際に何を許可しているのかを文書に落とすのが目的である。**
  • 無線機器の棚卸しを「ペアリング済みの相手」の単位で行う
    **本件の攻撃は、機器そのものではなく 「機器とスマートフォンの間に残っている信頼関係」を資産として使っている。** **ペアリングの記録が残っていなければ、抜かれる鍵も無い。** **一方、端末側のペアリング一覧は長年掃除されないことが多く、 もう使っていない機器の鍵が残り続ける。**
    取るべき行動 **業務端末のペアリング一覧を定期的に棚卸しし、 使っていない機器のペアリングを削除する手順を標準作業に入れる。** **MDM で一覧を取得できる場合は、 「ペアリング済み機器が5件以上ある端末」を抽出して確認する。** **退職者から回収した端末・貸出機は、再貸出の前に必ずペアリングを消す。**
  • 公開された検査ツールを、使う前に「誰の機器に使うか」を決める
    **ERNW は全面公開と同時に RACE Toolkit を公開しており、 自分の機器が脆弱かを確認できる。** **ただしこの種の道具は、他人の機器にも同じように動く。** **社内検査の名目で、来客や隣席の私物機器に試せば、 それ自体が不正アクセスになりうる。**
    取るべき行動 **無線の検査を行う前に、①対象機器の所有者からの同意、 ②実施場所（電波が外に漏れない場所か）、③記録の残し方を文書で決める。** **「自社が購入した検査用の機器だけを対象にする」と決めるのが もっとも単純で安全である。**

観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 自社が販売するハードウェア製品に、他社製の SoC・無線モジュール・SDK が入っている本件の欠陥は Airoha の中にあり、修正を届ける責任は10社以上に分かれた。 **チップ側が71日で直っても、配布が揃わなければ利用者は守られない。** 供給元の修正を受け取る窓口と、自社ファームウェアとして配る工程が 決まっていなければ、同じことが起きる。
システム構成□ 出荷する機器に、製造・試験・修理のためのコマンド面やデバッグ経路が残っているRACE は本来 USB で使う社内向けの面だった。 **出荷後も Bluetooth から到達でき、認証が無かったことが欠陥の中身である。** UART・JTAG・デバッグ用 HTTP・製造用トピックなど、同じ形は広く存在する。
データの保持□ 機器が長期の鍵（ペアリング鍵・証明書の秘密鍵・トークン）を平文で保持している本件で抜かれたのはリンクキーであり、 **これは「相手がこちらを信用する根拠」そのものである。** 汎用の読み出しコマンドの射程に平文の鍵があると、 読み出しの穴1つが認証の破綻になる。
認証・認可□ 役員・管理者の業務アカウントで、電話番号（SMS・音声）が二要素認証や復旧手段に使われている本件の最終段は、電話番号を聞き出して着信を代わりに取ることで成立した。 **攻撃者は被害者の端末に触っていない。** 電話番号は変更できないため、一度この経路が成立すると長く残る。
運用・監視□ 脆弱性管理を「資産台帳の版数と CVE の影響版の突き合わせ」で回しているCVE-2025-20700 は、公開情報に影響版も修正版も「Unknown」と記載されている。 **突き合わせる相手が無い案件は、台帳では判定できない。** 判定できないまま滞留する案件の置き場が無いと、静かに取りこぼす。
運用・監視□ 社員が業務端末とペアリングした私物のオーディオ機器を、社外で長時間使っている成立には攻撃者が電波の届く範囲にいることが要る。 **大量攻撃には向かないが、狙い撃ちには向く。** カフェ・空港・ホテルのラウンジという条件は、出張の多い立場の人に当てはまる。
体制・契約□ 業務で使うオーディオ機器・周辺機器が資産台帳に載っていない本件の対象は「ヘッドホン」である。 **資産として管理していなければ、該当の有無も更新の到達も確認できない。** ブランドが SoC の供給元を公表しないことも多く、台帳に書く情報が手に入らない場合がある。
