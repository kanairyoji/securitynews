INC-2026-0822Android「SMS of Death」PoC 公開

研究者 Mark B（@sourone）は2026年10月29日、Android の WAP Push 処理 （`WapPushOverSms.decodeWapPdu()`）に、ヘッダ長の値を範囲検査なしに 符号付き32ビット整数へ変換して配列長に使う不備があり、 細工した SMS を1通送るだけで通話中の回線ごと `com.android.phone` を 落とせることを「SMS of Death」として公表し、実証コードを GitHub で公開した—— 受信箱に届く前に処理されるため利用者には何が起きたか見えず、 緊急通報を含む通話が切断される。Google は2026年6月15日に独自の修正 （commit 735d967）を作成し2026年10月の更新で Android 14〜17 に配布したが、 研究者の検証では Android 12 から再現し、更新対象外の Android 12・13 は 修正を受け取れない。報道は CVE-2026-58882 を採番として示しているが、 研究者自身の公表には CVE の記載が無く、NVD にも登録されていない

8バイトの SMS が1通届くと、通話が切れます。利用者の操作は要りません。

研究者 Mark B（@sourone）は2026年10月29日、Android の WAP Push 処理にある整数の扱いの不備を「SMS of Death」として公表し、実証コード（PoC）をGitHub で Apache 2.0 のもとに公開しました（出典1・2）。

仕組みは単純です（出典1）。WAP Push のポート（2948）宛のデータ SMS として細工したメッセージを送ると、WapPushOverSms.decodeWapPdu() が WSP のヘッダ長を long で読み、範囲検査をせずに int へ変換します。 5バイトの uintvar が 0x80000000 にデコードされ、符号付き32ビット整数としては -2147483648 になります。 この長さで配列を確保しようとして NegativeArraySizeException が発生し、主スレッドで捕まらないまま com.android.phone が死にます。

com.android.phone は携帯網の機能を担うプロセスです（出典3）。落ちれば通話が切れ、圏外になります。 研究者の検証では、通話は DisconnectCause CS_DEATH で切断され、1通あたり1〜2秒の無サービス状態が生じます（出典1）。緊急通報中であっても同じです（出典1・3）。

そして利用者には、何が起きたか見えません。 Android はこのメッセージを受信箱に入れる前に処理するため、通知も痕跡も残りません（出典3）。

研究者が報告した検証結果のうち、実務上重いのは次の3点です（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**細工した WAP Push メッセージを1通、相手の電話番号へ データ SMS として送るだけで、 携帯網の機能を担う `com.android.phone` プロセスを落とせる**（出典1）。 **利用者の操作は不要（ゼロクリック）で、 メッセージは受信箱に入る前に処理されるため痕跡が見えない**（出典1・3）。 **本記録の明示**——**実環境での悪用を示す資料は無い**〈未確定6〉。 **以下は研究者が実証した経路であり、 観測された攻撃の記述ではない**（本記録の整理）。

  1. 1. 実行確認済
    **細工した WAP Push メッセージがポート 2948 宛の データ SMS として届く。** **Android は受信箱へ入れる前にこれを処理する**（出典1・3）。
    根拠: 研究者による実証と解説（出典1）
  2. 2. 影響（暗号化・破壊・改ざん）確認済
    **`WapPushOverSms.decodeWapPdu()` が WSP のヘッダ長を `long` として読み、範囲検査をせずに `int` へキャストして 配列の長さに用いる。** **5バイトの uintvar は 0x80000000 にデコードされ、 符号付き32ビット整数としては -2147483648 になる。** **この長さでの配列確保が `NegativeArraySizeException` を投げ、 主スレッドで捕まらないまま `com.android.phone` が死ぬ**（出典1）。
    根拠: 研究者による実証と解説（出典1）。報道も同じ機構を記述している（出典3）
  3. 3. 影響（暗号化・破壊・改ざん）確認済
    **影響の継続。** **約20通で端末が長時間にわたり使用不能になり、 Android 12 では約90秒ごとの再起動ループに陥って 利用者が初期化の案内に行き着く**（出典1）。 **さらに、通信事業者による再配信のため、 研究者の検証では1通で最長1週間にわたり 断続的な障害が続いた**（出典1）。
    根拠: 研究者による検証結果（出典1）

攻撃者（相手の電話番号を知っているだけ） → 細工した WAP Push メッセージを ポート 2948 宛のデータ SMS として送信 → Android が受信箱に入れる前に処理 → `WapPushOverSms.decodeWapPdu()` が WSP ヘッダ長を範囲検査なしに `int` へ変換 （0x80000000 → -2147483648） → その長さで配列確保 → `NegativeArraySizeException` が主スレッドで未捕捉 → `com.android.phone` が死亡 → 通話が `DisconnectCause CS_DEATH` で切断・1〜2秒の圏外 → 端末に残ったメッセージの再処理と通信事業者の再配信で反復 （約20通で長時間使用不能／Android 12 では約90秒ごとの再起動ループ／ 1通で最長1週間の断続障害） → 復旧は ADB による削除か初期化
研究者 Mark B（@sourone）の解説（2026年10月29日・出典1）にもとづく。 **実環境での悪用を示す資料は無い**〈未確定6〉 ——**これは研究者が実証した経路であり、観測された攻撃ではない** （本記録の明示）。 **破線で示した修正（2026年10月の更新）は Android 14〜17 にしか届かず、 Android 12・13 では経路が塞がれない**（出典1・3）。 **利用者側に見える痕跡は無い**——**メッセージは受信箱に入る前に 処理される**（出典3）。 **本記録はトリガーとなるバイト列と ADB の手順を記載しない** （本記録の方針）。

CISO・経営層への示唆
  • **「更新を適用する」で閉じない資産を把握しておく。修正が届かない端末がある**
    **本件の修正は Android 14〜17 にしか配布されていない**（出典1・3）。 **研究者の検証では Android 12 から再現し、 再起動ループという最も重い影響が出たのもこのバージョンである**（出典1）。 **すなわち「パッチ適用率」という指標では、 この事案のリスクは1%も動かない**（本記録の評価）。 **指標が改善しないまま、守れない端末が残る形である。**
    取るべき行動 **①業務で使う Android 端末の OS メジャーバージョンを棚卸しし、 「セキュリティ更新の提供が終わっている端末」を別の台帳に分ける。** **②その台帳の台数と、業務上の役割（通話に使うか・ 緊急連絡の経路に入っているか）を経営報告の項目に加える。** **③更新が終わった端末の置き換え時期を予算計画に載せる ——本件はその必要性を示す具体例として使える（本記録の推奨）。**
  • **CVE 番号を前提にした脆弱性管理は、番号が付かない事案を取りこぼす**
    **報道は CVE-2026-58882 としているが、 研究者自身の公表には CVE の記載が無く、 本記録が NVD で照会しても登録が無い**（出典1・3・4。本記録の確認）〈齟齬1〉。 **また、2026年10月の Android セキュリティ公報にも 記載されていないと報じられている**（出典3）。 **CVE で検索する運用では、動作する実証コードが公開され、 未修正のバージョンが残っているこの事案に行き当たらない** （本記録の主張）。
    取るべき行動 **①脆弱性情報の取り込み経路に、 「CVE が付いていないが実証コードが公開されたもの」の 受け口を1つ用意する（研究者の公表・ベンダーの commit を見る経路）。** **②取り込んだものを台帳に登録する際、 識別子として CVE 以外の手がかり （本件なら commit 735d967・関数名 decodeWapPdu）を 記録できる欄を持たせる。** **③「公報に載っていない」ことを「修正されていない」とも 「問題がない」とも読まない運用を明文化する。**
  • **端末が圏外のまま落ち続ける事象を、事業継続の想定に入れる**
    **本件では `com.android.phone` が落ちるため、 通話が切れ圏外になる**（出典1・3）。 **Android 12 では約90秒ごとの再起動ループ**（出典1）。 **この状態の端末には、遠隔の MDM から何も届かない ——電波が無いためである**（本記録の評価）。 **復旧には PC と ADB、または初期化が要る**（出典1・3）。
    取るべき行動 **①現場・出張者・当直など「通話が業務の前提になっている役割」を 特定し、端末が使えない場合の代替連絡経路を決める。** **②端末を物理的に回収して処置する手順と、 その所要時間（回収・初期化・再設定）を測る。** **③緊急通報が切れる事象であることを、 安全管理の担当部門と共有する（本記録の推奨）。**
  • **「修正は速かったが届かなかった」という形を、委託先・供給元の評価軸に加える**
    **本件では、報告から修正の作成まで41日、 そこから配布まで約3か月半である**（出典1。本記録の算出）。 **技術的な修正の速さと、利用者に届くまでの速さは別物だった** （本記録の評価）。 **さらに、届く範囲はバージョンの線引きで決まっていた**（出典1・3）。
    取るべき行動 **①OS・組込み機器・アプライアンスの供給元について、 「修正の提供が終了するバージョン」と 「その終了時期」を契約・調達の確認項目に入れる。** **②既に終了している製品について、 「修正が出ても届かない」ことをリスク登録簿に明記する。** **③評価では「修正を出す速さ」ではなく 「自社の資産に届くか」を見る（本記録の主張）。**
セキュリティ技術者への示唆
  • **長さ・個数を外部入力から取る箇所は、符号と上限の両方を検査する**
    **本件の不備は、WSP ヘッダ長を `long` で読み、 範囲検査なしに `int` へキャストして配列長に使っていたことである** （出典1）。 **細工した5バイトの uintvar が 0x80000000 にデコードされ、 符号付き整数としては -2147483648 になる**（出典1）。 **型の幅を縮める変換が、検査の抜け道になっている**（本記録の整理）。
    取るべき行動 **①プロトコル解析のコードで、 外部入力から得た長さ・個数を配列確保やループ回数に使う箇所を 洗い出す。** **②各箇所に「0 以上であること」と 「許容される上限以下であること」の2つの検査を置く （片方では足りない）。** **③型の幅を縮める変換（`long` → `int` 等）の前後に 検査があるかを、静的解析の規則として追加する。**
  • **例外の捕捉は「落ちなくする」だけで、原因を消さない**
    **Google の修正は、例外の捕捉範囲を `RuntimeException` まで 広げるものだった**（出典1）。 **研究者が提出した範囲検査の案は採られていない**（出典1）。 **負の長さが作られること自体は残っており、 同じ値が別の経路で使われた場合には守られない** （本記録の評価）。
    取るべき行動 **①不正な入力に対する対処として例外の捕捉を入れる場合、 「入力を弾く検査」を別に置くかどうかを設計判断として記録する。** **②捕捉だけで済ませた箇所を一覧にし、 同じ値が流れる他の経路を確認する。** **③捕捉の範囲を広げる変更は、 想定外の例外まで飲み込む副作用を伴うため、 記録（ログ・計測）を併せて入れる。**
  • **「一度届いた不正な入力」が永続化される経路を確認する**
    **本件では、端末に保存されたメッセージが処理されるたびに 再び落ちる**（出典1）。 **さらに通信事業者の再配信により、 研究者の検証では1通で最長1週間、断続的な障害が続いた**（出典1）。 **Google の修正に「原因となったメッセージを削除する」処理が 含まれているのは、この性質への対処である**（出典1。本記録の整理）。
    取るべき行動 **①受信したデータを永続化してから処理する経路で、 「処理が失敗したデータが残り続けるか」を確認する。** **②残り続ける場合、失敗したデータを隔離・削除する処理を置く。** **③再試行の仕組み（網側の再配信・内部のリトライ）が 被害を伸ばしうることを、設計時の検討項目に加える。**
  • **復旧に PC が要る障害を、端末運用の手順に書いておく**
    **再起動ループに陥った端末の復旧手段は、 ADB による該当行の削除（@sakisdog が issue #2 で提供）または 初期化である**（出典1・2）。 **初期化では SMS/MMS と APN 設定が失われる**（出典1）。 **端末は圏外のため、遠隔からの操作は届かない**（本記録の評価）。
    取るべき行動 **①業務端末について、ADB を使った処置が 組織の方針上許されるかを事前に確認する （開発者オプションの扱い・MDM の制限）。** **②許されない場合、初期化と再設定の手順と所要時間を測る。** **③端末を物理的に回収する経路（拠点・配送・代替機）を 手順に含める。**
