INC-2026-0824用友 BIP の0day疑いで15万ファイル暗号化

中国のインシデント対応チームが2026年10月28日、ある企業の用友 BIP 高級版の 主サーバで `/servlet/~uapfw/sprmonitorservlet` の Java ネイティブ デシリアライゼーションの不備が3度突かれ、 2026年10月18日20時36分に暗号化され150,411個のファイルが `.rox` 拡張子に 変えられて業務が止まったことを公表した—— 前2回の WebShell 設置（10月17日05時03分・10月18日08時15分）と 3回目の暗号化では C2 基盤が別で、 チームは「打点する者と暗号化する者が別で、 脆弱性の詳細か掌握した権限が人の間を流れた可能性が上がった」としつつ、 これは推測であり取引の事実は認定できないと明記した。 現場には防御製品もミドルウェアのアクセスログも無く、 リクエストの原本は復元できていない

暗号化は1分で終わりました。そこに至る24時間が、3回に分かれていました。

2026年10月28日、中国のインシデント対応チームが阿里云先知（Aliyun Xianzhi）に、ある企業の用友 BIP 高級版（Yonyou BIP。中国の大手 ERP 製品）の主サーバがrox ランサムウェアで暗号化された事案の追跡結果を公表しました（出典1）。被害組織の名前は、チームの方針により公表されていません（出典1）。

入口は /servlet/~uapfw/sprmonitorservlet でした（出典1）。このエンドポイントはリクエストボディをそのまま Java ネイティブのデシリアライゼーションにかけ、その過程で JtaTransactionManager.readObject がJNDI 参照を発火させ、応答として返る javax.el.ELProcessor を使ってコード実行に到ります（出典1）。チームは「これは fastjson のデシリアライゼーション経路ではなく、Java ネイティブのシリアライズ流である」と明確に区別しています（出典1）。

時系列が、この事案の核心です（出典1。以下の時刻はすべて北京時間）。

3回目は違いました（出典1）。脆弱性の入口と利用チェーンは同じですが、JNDI の回連先がrmi://192.151.233.247:1099/x に変わり、PowerShell の形態も難読化されたものに変わっています（出典1）。難読化は、整数を1バイトずつ129 減算して IEX で始まる内容を復元する組と、23 減算して System.Management.Automation.ScriptBlock を復元しScriptBlock.Create でメモリ上に実行する組の2系統で、コメントには Update service mesh routing table、変数名には $Timestamp・$LogFile・$ConfigPath という運用で使われがちな名前が使われていました（出典1）。

ここでチームが出した読みが、本事案を記録する理由です（出典1）。「前期の人員が脆弱性で一斉に打点して対象の可用性を検証し、その後に脆弱性の詳細か掌握済みの権限が流れ、ランサム実行者が同じ入口を再利用して暗号化を完了した」という筋です。

そしてチームは、その直後に歯止めをかけています（出典1）。「可疑性が上がったことは取引の事実の成立とは違う。同一チームが自ら基盤を切り替えた、攻撃ツールを共用した、工程ごとに C2 を臨時に変えた、でも一部の現象は説明できる。現時点で双方の通信・資金の往来・検体の同源性の証拠は無く、これをもって脆弱性の取引があったと認定することはできない。まして IP の地理的位置だけで攻撃者の国籍を判断することはできない」。

この留保の付け方自体が、本DBが記録に値すると考える点です（本記録の評価）。

現場には何も残っていませんでした（出典1）。防御製品の配備なし、ミドルウェアのアクセスログなし、アプリケーションログは異常スタックのみでリクエスト URI・送信元 IP・POST ボディを記録しない—— チームはリクエストの原本を復元できず、アプリケーションログの異常発生時刻を起点に、Windows PowerShell イベントログ・ファイル時刻・システム痕跡を1件ずつ突き合わせて経過を再構成しています（出典1）。脆弱性の存在は、顧客の授権のもとで載荷の RMI 先を自チームが制御する DNSLOG のドメインに差し替えた無害化検証（悪性コードを実行せず、対象にファイルも書かない）で確認されました（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**インターネットに露出した用友 BIP 高級版の `/servlet/~uapfw/sprmonitorservlet` を Java ネイティブの デシリアライゼーションで突き、JNDI 経由でコード実行を得て WebShell を置き、最後に同じ入口から暗号化器を落として実行する**（出典1）。 **3回の利用のうち前2回が WebShell の設置、3回目が暗号化である**（出典1）。 **前2回と3回目で攻撃基盤が異なり、 「打点する者と暗号化する者が別である可能性」が論点になっている** （出典1）〈未確定6〉。 **以下の chain は、対応チームが異常スタック・PowerShell イベントログ・ ファイル時刻・AppCompatCache を突き合わせて再構成したものである**（出典1） ——**リクエストの原本は復元されていない。**

  1. 1. 偵察確認済[1]
    **2026年10月17日05時02分59秒、`fw-log.log` に `####sprmonitorServlet Exception` が初めて記録された。 例外の型は `java.io.EOFException` で、 呼び出し位置は `ObjectInputStream` がシリアライズ流のヘッダを読む段階である** （出典1）。 **チームの判断——不完全あるいは予期しないシリアライズデータを 受け取ったことを示し、38秒後に完全な利用の例外が現れることから、 正式な利用の前の試探の特徴に合致する**（出典1）。
    根拠: アプリケーションログ `fw-log.log` の異常スタック（出典1）
  2. 2. 初期侵入確認済[1]
    **2026年10月17日05時03分37秒、`####requestEntry Exception` が出現。 スタックは `Hashtable` のネイティブデシリアライゼーション中に `JtaTransactionManager.readObject` が発火し、 `rmi://8.130.77.216:1099/x` へ JNDI 参照を行い、 対向が `javax.el.ELProcessor` オブジェクトを返したことを示す**（出典1）。 **この3つ——`JtaTransactionManager.readObject`、 `JNDI location [rmi://`、`javax.el.ELProcessor`——が、 本件の攻撃を識別する鍵の特徴であるとチームは述べている**（出典1）。 **同じ経路が10月18日08時15分34秒（同一 C2）と 10月18日20時34分59秒（`rmi://192.151.233.247:1099/x`）にも使われた**（出典1）。
    根拠: アプリケーションログの異常スタック（JNDI 回連先と返却オブジェクトを含む。出典1）／DNSLOG による無害化検証（出典1）

  • **自環境の脆弱性確認は、載荷を撃たず外部参照の宛先だけを差し替える**
    **対応チームは、顧客の授権のもとで、 載荷中の RMI アドレスを自チームが制御する DNSLOG のドメインに 差し替えるだけの無害化検証を行った**（出典1）。 **悪性コードを実行せず、対象にファイルも書かない設計である。** **結果、DNSLOG が対象サーバの出口からの解決記録を受け取り、 同時にアプリケーションログに同型の `JtaTransactionManager.readObject` の例外が追加され、 2つが相互に裏づけた**（出典1）。
    取るべき行動 **①自組織で脆弱性の有無を実機で確かめる必要があるとき、 「外部参照の宛先を自分の観測点に差し替える」形で設計する （コード実行やファイル書き込みを伴わせない）。** **②実施の前に、授権の範囲・実施時刻・観測点・ 想定される副作用を文書にして承認を取る。** **③検証の成否の判定を、観測点側の記録とサーバ側のログの 2系統で裏づける（1系統だけでは「届かなかった」のか 「発火しなかった」のかを区別できない）。**
