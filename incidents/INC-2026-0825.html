INC-2026-0825LXD に CVSS 10.0 の認証バイパス

Canonical は2026年10月28日、LXD と MicroCloud の相互 TLS 認証に 「クライアントが送ってきた証明書チェーンの全ピア証明書を信頼ストアと照合する」 不備（CVE-2026-112816）があり、 署名鍵の所有を証明できるのはリーフ証明書だけであるため、 攻撃者は信頼済みの公開証明書を中間証明書としてチェーンに挿入するだけで 別の身元として認証できると公表した—— 公開証明書は秘密ではないので秘密鍵は要らず、 なりすました相手の権限によってはホストの root を取れる。 Canonical は CVE 採番機関として CVSS 4.0 で 10.0 を付けたが、 Ubuntu の CVE ページの優先度は Medium であり、 Canonical 自身の告知には CVSS の記載が無い

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年10月28日17時50分（Canonical による Ubuntu Discourse 上の告知） 最終更新: 2026年11月3日（本記録の作成。Canonical の告知と Ubuntu の CVE ページを直接確認）

公開証明書は、秘密ではありません。この脆弱性は、それを認証に使ってしまいます。

Canonical は2026年10月28日、LXD と MicroCloud に重大な脆弱性（CVE-2026-112816）があると公表しました（出典1）。LXD の HTTPS API に到達できる攻撃者は、信頼済みクライアントの公開証明書を持っているだけで、そのクライアントとして認証されます（出典1）。秘密鍵は要りません。

仕組みは一文で説明できます（出典1。原文英語）。「相互 TLS 認証において、我々はクライアントが提示したすべてのピア証明書を信頼ストアと照合していた。しかし署名鍵の所有を証明できるのはリーフ証明書だけである。攻撃者は、自分が信頼されている公開証明書を中間証明書としてチェーンに挿入し、別の身元として認証できる」。

つまり、検証の対象を1枚に絞っていなかったことが不備です（本記録の整理）。TLS が鍵の所有を証明するのはリーフ証明書についてだけで、チェーンの中間に何を入れるかはクライアント側が自由に決められます。 そこを信頼の判定に使えば、「公開されている証明書を知っているか」が認証になってしまいます。

影響の範囲は、なりすました相手の権限で決まります（出典1・3）。Canonical は「侵害されたアカウントの権限によっては、ホストの root アクセスを得られる可能性がある」としています（出典1）。CVE の記録は「認証されていない攻撃者が信頼済みクライアントとして認証され、クラスタと管理対象の仮想マシンへ完全にアクセスできる可能性がある」と記しています（出典2）。

MicroCloud には固有の条件があります（出典1）。クラスタメンバーが MicroCloud に参加している最中に、そのメンバーの公開 TLS 証明書を攻撃者が傍受できる場合、後にその証明書を使ってそのメンバーとして認証できる、というものです。

修正は全サポート系列に出ています（出典1）。LXD 6.10.1（6/stable）・5.21.9（5.21/stable）・5.0.11（5.0/stable）・4.0.15（4.0/stable）、MicroCloud 2.1.5（2/stable）・3.4.1（3/stable）。Canonical はすべての利用者に直ちに各チャネルの最新版へ更新することを求めています（sudo snap refresh lxd / sudo snap refresh microcloud）。 修正版は candidate から stable へ段階的に配信中とされています（出典1）。

一方で、深刻度の表示が資料の間で揃っていません（本記録の確認）〈齟齬1〉。Canonical は CVE の採番機関として CVSS 4.0 で 10.0（Critical）を付け、報道もその数字を見出しに使っています（出典3・4）。しかし Ubuntu の CVE ページの優先度は Medium です（出典2）。そして Canonical 自身の告知には CVSS の記載がありません（出典1。本記録の確認）。本記録は、この不一致自体を記録に残します。

報告は Incus プロジェクトから持ち込まれました（出典1）。Canonical は、Incus で見つかった問題が LXD にも影響することを確認したとし、謝辞で stgraber の継続的な協力に触れています。

不備の説明は、Canonical の告知の一文に尽きている（出典1。原文英語）。

相互 TLS 認証において、我々はクライアントが提示したすべてのピア証明書を信頼ストアと照合していた。しかし署名鍵の所有を証明できるのはリーフ証明書だけである。攻撃者は、自分が信頼されている公開証明書を中間証明書としてチェーンに挿入し、別の身元として認証できる。

ここで前提を分けておく（本記録の整理）。

要素 攻撃者が持っている必要があるか
信頼済みクライアントの公開証明書 必要（ただし公開情報である）
信頼済みクライアントの秘密鍵 不要
HTTPS API へのネットワーク到達 必要
認証情報（パスワード・トークン） 不要

「公開証明書を持っていること」は、本来なにも証明しない（本記録の評価）。TLS のクライアント認証が身元の証明になるのは、クライアントがリーフ証明書に対応する秘密鍵で署名できるからである。 チェーンの中間に何を入れるかは、クライアントが自由に決められる。 そこを信頼の判定に使えば、認証の条件が「秘密鍵を持っているか」から「公開証明書を知っているか」へ下がる。

影響の範囲は、なりすました相手の権限で決まる（出典1・2）。Canonical は「侵害されたアカウントの権限によっては、ホストの root アクセスを得られる可能性がある」とする（出典1）。Ubuntu の CVE ページは「認証されていない攻撃者が信頼済みクライアントとして認証され、クラスタと管理対象の仮想マシンへ完全にアクセスできる可能性がある」とする（出典2）。

MicroCloud には固有の条件が付く（出典1）。クラスタメンバーが MicroCloud に参加している最中に、そのメンバーの公開 TLS 証明書を攻撃者が傍受できる場合、後にその証明書を使ってそのメンバーとして認証できる。 本記録の整理——参加（join）の瞬間に証明書が流れるため、そのときにネットワーク上にいられるかが条件になる。

ただし、読み方は整理できる（本記録の評価）。CVSS は「成功したときの影響と、成功までの容易さ」を測る。本件は認証不要・ネットワーク越し・影響は管理面の完全掌握であり、その軸では上限に近い。 一方、Ubuntu の優先度は、Ubuntu のパッケージとしての実際のリスクを踏まえた運用上の指標である。LXD は snap で配布され、Ubuntu の各リリースは「Not in release」または「Not affected」と記録されている（出典2）——ディストリビューションのパッケージとしては影響が無いことが、優先度の低さに反映されているとみられる（本記録の推定）。

さらに別の軸の数字もある（出典3）。EPSS（30日）は 0.3% で、CISA の KEV カタログには収載されていない。 これは「30日以内に悪用が観測される確率の予測」であり、CVSS とは測っているものが違う（本記録の明示）。

本記録の評価——読者にとっての実務上の結論は、どの数字を採るかではない（本記録の判断）。①自組織に LXD / MicroCloud があるか、②その HTTPS API にどこから到達できるか、③信頼ストアに何が登録されているか。 この3点が決まれば、スコアの議論は要らない（本記録の評価）。

CISO・経営層への示唆
  • **「公開情報だから秘密にしなくてよい」ものが、認証に使われていないか問い直す**
    **本件の攻撃条件は、信頼済みクライアントの公開証明書を持っていることだけである** （出典1）。 **公開証明書は秘密ではない** ——**構成管理リポジトリ、手順書、チケット、 バックアップ、クラスタ参加時の通信など、 秘密として扱われていない場所に置かれている可能性が高い**（本記録の評価）。 **本件は、製品側がその前提を崩したために、 「公開情報の管理」が突然認証の強度になった例である。**
    取るべき行動 **①自組織で「公開情報だから管理不要」と整理している資産 （公開鍵・公開証明書・エンドポイントの一覧・内部ドメイン名）を棚卸しし、 それが認証や認可の判断に使われていないかを確認する。** **②クラスタ参加や機器登録の手順で、 証明書・公開鍵が平文で流れる区間を洗い出す。** **③基盤製品の信頼ストアに何が登録されているかを定期的に見直し、 不要な登録を外す運用を作る。**
  • **深刻度の数字が資料間で揃わないことを前提に、判断の軸を自組織側に置く**
    **本件は、Canonical の告知に CVSS の記載が無く**（出典1）、 **Ubuntu の CVE ページの優先度は Medium**（出典2）、 **第三者と報道は CVSS 4.0 の 10.0 を伝える**（出典3・4）、 **EPSS（30日）は 0.3%**（出典3）—— **という状態である**〈齟齬1〉。 **どの数字を採るかを議論しても、自組織の露出は決まらない**（本記録の評価）。
    取るべき行動 **①脆弱性の優先度判断の社内基準を、 外部スコア単独ではなく「自組織での到達可能性」と 「侵害されたときに取られる権限」の2軸で書く。** **②ベンダーの告知・ディストリビューションの CVE ページ・ 第三者の解説で数値が食い違う場合の扱い（どれを採るか、誰が決めるか）を あらかじめ決めておく。** **③EPSS と CVSS が測っているものの違いを、 経営向け資料の定型注記として持つ。**
  • **仮想化・コンテナの管理 API は、侵害されたときに取られるものが段違いである**
    **本件でなりすまされた先の権限によっては、 クラスタと管理対象の仮想マシンへの完全なアクセス、 さらにホストの root アクセスまで到る**（出典1・2）。 **管理面（コントロールプレーン）は、 その配下の全ワークロードを一度にまとめて失う経路である**（本記録の評価）。

    **本件は Incus プロジェクトから持ち込まれ、 Canonical が LXD にも影響することを確認した**（出典1）。 **相互 TLS の検証処理という、 フォーク前から存在していたとみられる箇所の不備である**（本記録の推定）。 **自組織が LXD だけを使っていても、 Incus 側の告知が先に出る構図になりうる。**

セキュリティ技術者への示唆
  • **クライアント証明書の検証は、リーフ1枚だけを信頼ストアと照合する**
    **本件の不備は、クライアントが提示したすべてのピア証明書を 信頼ストアと照合していたことである**（出典1）。 **署名鍵の所有を証明できるのはリーフ証明書だけであり、 チェーンの中間に何を入れるかはクライアント側が自由に決められる**（出典1）。 **CVE の記録は細工された証明書チェーンが利用されるとしている**（出典2）。
    取るべき行動 **①自社で相互 TLS を実装している箇所について、 信頼の判定に使っている証明書がリーフ1枚に限定されているかを コードで確認する（`PeerCertificates` の全要素を走査していないか）。** **②「証明書をピン留めしている」実装では、 ピン留めの比較対象がリーフであることを確認する。** **③中間証明書を複数入れたチェーン、 信頼済み証明書を中間位置に入れたチェーンを試験項目に加える。**
  • **段階配信（candidate → stable）があるため、`snap refresh` の結果を確認する**
    **Canonical は修正版が candidate から stable へ 段階的に配信されているとしている**（出典1・3）。 **つまり `sudo snap refresh lxd` を実行しても、 その時点で stable に修正版が届いていなければ更新されない**（本記録の整理）。
    取るべき行動 **①更新後に `snap list lxd` / `snap list microcloud` で 実際のバージョンを確認する（LXD は 6.10.1 / 5.21.9 / 5.0.11 / 4.0.15、 MicroCloud は 2.1.5 / 3.4.1 以上）。** **②まだ届いていない場合の扱い（待つか、 candidate を明示的に指定するか）を決めてから作業する。** **③複数ノードのクラスタでは、全ノードのバージョンを確認する ——1台残るとその1台がなりすましの経路になる。**
  • **信頼ストアの棚卸しを、更新とセットで行う**
    **本件では、信頼ストアに登録されている証明書の公開部分を 知っているだけで、その身元になりすませた**（出典1）。 **第三者の解説も、更新に加えて 「API の露出を制限し、信頼ストアを監査する」ことを挙げている**（出典3） ——**ただしこれは Canonical の推奨ではない**（本記録の明示）。
    取るべき行動 **①`lxc config trust list` 相当の操作で 信頼済みクライアント証明書の一覧を取り、 用途が説明できないものを削除する。** **②削除した場合の影響（自動化・CI・監視からの接続断）を 事前に洗い出す。** **③今後、証明書の追加を申請と記録を伴う手順に変える。**
  • **MicroCloud では「参加の瞬間」が条件になる。参加作業の経路を分ける**
    **Canonical は、クラスタメンバーが MicroCloud に参加している最中に そのメンバーの公開 TLS 証明書を攻撃者が傍受できる場合、 後にその証明書を使ってそのメンバーとして認証できるとしている**（出典1）。 **つまり攻撃の窓は、恒常的ではなく参加作業の最中にある**（本記録の整理）。
    取るべき行動 **①MicroCloud のクラスタ参加作業を、 業務ネットワークではなく管理専用の経路で行う。** **②参加作業の時刻を記録し、 その時間帯の管理ネットワーク上の通信を後から確認できるようにする。** **③過去に参加作業を業務ネットワーク上で行っていた場合は、 更新後に当該メンバーの証明書を入れ替えることを検討する ——更新だけでは、既に傍受された証明書が信頼ストアに残る。**
