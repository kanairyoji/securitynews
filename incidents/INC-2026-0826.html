Google Threat Intelligence Group（GTIG）と Mandiant は2026年10月30日、インシデント対応の現場で、オープンソースのエージェント型ペンテストフレームワークが実際の侵入に使われていることを確認したと公表しました（出典1）。確認されたのは ARTEX・PentAGI・CAIRN・Hexstrike、および独自のエージェント基盤とみられるものです（出典1）。観測は2026年8月下旬以降です。

GTIG 自身の言葉で、何が変わったかがはっきり書かれています（出典1。原文英語）。「侵害された認証情報を使うこと、未修正のシステムを狙うことといった侵入の仕組みは変わらないままである。変わったのは、フレームワークがこうした既知の弱点を突く速度と規模である。」

その速度は、ログに人のものではない形で残ります（出典1）。①個々の実行は2〜25秒の圧縮された塊（バースト）で走る。一方で工程の間には長い停止がある。 ②あるオペレーションでは、23秒の実動時間に27イベントが記録され、複数のセキュリティグループをまたいで AWS の権限を高速に探っていた。 ③持ち出し用スクリプトの準備中、「スクリプトが大きすぎる」というエラーを自力で解釈してスクリプトを削り、再実行して約10秒で17スナップショットのインスタンスを展開した。

そして、痕跡が多いのです（出典1）。GTIG の評価は「熟練した人間の攻撃者と比べて、ARTEX はきわめてフォレンジック上騒がしい形でコード実行に到った。高速で反復的な試行錯誤に依存するためである」です。

その騒がしさが具体的に現れた例が、Weaver OA への侵入です（出典1）。正規の認証情報を与えられた ARTEX は、外部公開の Linux 上の Weaver OA の Web サーバに到達し、公開された API 呼び出しを通じて SQL コマンドを実行しました。 技術的な困難に当たりながらも部分的なコマンド実行を達成してさらなる探索を行いましたが、この過程で240件のログイベントを生み、複数のサブエージェントが同じ目的を追って互いを上書きしたとみられるエラーも出ています（出典1）。

データベースの文脈からシステムの文脈へ移る試みは、MySQL のログ汚染でした（出典1）。SET GLOBAL general_log_file = '<webshell のパス>' の後にSET GLOBAL general_log = 1; を実行し、以降の SQL が指定したパスに書かれるようにする。そのうえで SELECT '<% [webshell の内容] %>' という形のSELECT 文を走らせる—— Java のサーブレットが JSP を扱う仕組み上、<% %> の中の Java コードが解析・コンパイルされてプロセスのメモリ空間に入り、実行の手段になります。

ここに ARTEX の学習の痕跡が残りました（出典1）。ログには上記の手順の反復が記録されており、WebShell の候補ごとに cl1217.jsp・f1219a.jsp・z1219.jsp という短命で半ば連番のファイル名が付けられ、それぞれが別のコマンドを実行していました。 WebShell の実行時のエラー（「変数 t は既に定義されている」など）が失敗を招き、ARTEX はおそらく手法を練り直して、目的の異なる複数の WebShell を書き、一部は前の誤りを訂正し、最終的に .jsp の WebShell が正常に実行され有効なコマンド出力を ARTEX に返すまで続きました（出典1）。

GTIG の見通しは、両面を含んでいます（出典1）。「ARTEX のようなフレームワークは攻撃速度を機械の速さまで引き上げる一方、ステルス性を犠牲にしている。自律実行はフォレンジックな痕跡、識別しやすい識別子、コードレベルの痕跡を残す。」 そのうえで「サイバー犯罪者は自律型攻撃ツールを使い続ける」と高い確信度で評価しています ——キャンペーンの到達範囲の拡大が成功率の低下を補うためです（出典1）。逆に、ステルス性を重視し長期の滞留を狙うアクターが公開版のツールを使う可能性は低いとされています（出典1）。

そして、防御の提言は長年の定石に戻ります（出典1）。GTIG 自身が「提案する防御戦略——コントロールプレーンの分離、短命な認証情報、最小権限、セグメント化、挙動ベースの検知——はいずれも長年のセキュリティのベストプラクティスである」と書いています。 本記録がこの事案を記録する理由はここにあります（本記録の評価）——新しい攻撃基盤に対して、新しい対策が提示されていない。

MySQL のログに JSP を書かせてコード実行に到る——学習の痕跡がファイル名に残った原因・手口出典 [1]

データベースの実行文脈から、システムの実行文脈へ移る試みである（出典1）。

手順（出典1）。①SET GLOBAL general_log_file = '<webshell のパス>' を実行し、一般クエリログの出力先を Web からアクセスできる場所に変える。 ②SET GLOBAL general_log = 1; を実行し、ログ出力を有効にする。 ③SELECT '<% [webshell の内容] %>' という形の SELECT 文を実行する。以降の SQL コマンドが general_log_file で指定したパスに書き込まれる。 ④Java の Web サーブレットが JSP ファイルを扱う仕組み上、<% %> の中の Java コードが解析・コンパイルされてプロセスのメモリ空間に入り、実行の手段になる。

使われた API は、正規に公開されているアプリケーション固有のSQL API であり、与えられた利用者の認証情報でアクセスできるものだった（出典1）。つまり脆弱性の悪用ではなく、正規機能の悪用である（本記録の整理）。

ここに ARTEX の試行錯誤が残った（出典1）。ログには上記の手順の反復が記録されており、WebShell の候補ごとに短命で半ば連番のファイル名（cl1217.jsp・f1219a.jsp・z1219.jsp）が付き、それぞれが別のコマンドを実行していた。 WebShell の実行時のエラー（「変数 t は既に定義されている」など）が失敗を招き、ARTEX はおそらく手法を練り直して、目的の異なる複数の WebShell を書き、一部は前の誤りを訂正し、最終的に .jsp の WebShell が正常に実行され有効なコマンド出力を ARTEX に返すまで続いた（出典1）。

別の事例では、アクセスの探索の過程でartex-probe-* というファイル名（* は5桁の半ば連番の数字）でさまざまな拡張子のファイルが生成された（出典1）。GTIG は「これらの数字の正確な意味や増え方については、我々の可視性からは言及が難しい」としつつ、ARTEX が設置ファイル名・作成したアカウント名にも同様の連番の目印を使っていたと観測している（出典1）。

本記録の評価——この連番の目印は、検知の資産である（本記録の判断）。手口自体（MySQL ログ汚染による JSP 書き込み）は古くからあるが、「短時間に半ば連番の名前のファイルが複数作られ、それぞれ別のコマンドを実行し、エラーを経て成功に至る」という一連の形は、自律エージェントの固有の痕跡である（本記録の評価）。ただし名前の規則（artex-probe- 等）は変えられるため、名前そのものではなく「短時間での連番生成と反復的な失敗」で引く必要がある（本記録の判断）。

PentAGI は Kali のサンドボックスで公開ツールを回す——偵察で止まる例が多い背景・過去事例出典 [1]

ARTEX とは性格が違う（出典1）。

PentAGI（VXControl が開発）の作り（出典1）——①利用者は対象と目的を記述するだけでよい。②専門エージェントのチームがタスクを「Flow」に分解して実行し、報告する。③ツールは既定でホストではなく Kali Linux のサンドボックス内で動作する。④使用するツールは metasploit・nmap・SQLmap などの公開ツールである。

観測された使い方（出典1）——①大半は WHOIS によるアセットマッピングと脆弱性スキャンにとどまっている。②一部は侵入と、複数組織での永続化まで進んでいた。③アジアのシステムインテグレーターと大手通信企業を対象に、カスタマイズされた基盤が少なくとも2026年8月下旬から10月上旬に使われた形跡がある。④プロキシサービスと組み合わせ、航空宇宙セクターを狙った事例もある。

Hexstrike と CAIRN については、記事に詳細な機能の説明が無い（出典1。本記録の確認）〈未確定6〉——インシデント対応案件で悪用が確認されたエージェント型ペンテストフレームワークとして名前が挙がるだけである。

ARTEX の作りは別である（出典1）。「Go で書かれ、Next.js の Web コンソールを組み込んだ、自律型・多エージェントの LLM 駆動のペンテストおよび攻撃用コマンド＆コントロール（C2）プラットフォーム」であり、攻撃ライフサイクルを6つの専門サブエージェントに抽象化する（個々の名称と役割は記事に無い）〈未確定5〉。GTIG が観測した機能には、Active Directory の自動偵察、権限昇格、標的のクラウド基盤のプロファイリング（Azure のストレージキーの収集など）、独自の WebShell の合成と展開が含まれる（出典1）。

本記録の整理——同じ「エージェント型」でも、既定でサンドボックスに閉じるもの（PentAGI）とC2 の機能を内蔵するもの（ARTEX）がある（本記録の評価）。防御側にとっての差は、後者が侵害後の全工程を1つの基盤で回せることである。

速度と規模のために、ステルス性が捨てられている——それでも使われ続ける評価・解釈出典 [1]

GTIG の見通しは、利点と欠点の両方を書いている（出典1）。

欠点（攻撃者側から見た）（出典1）——①ARTEX のようなフレームワークは攻撃速度を機械の速さまで引き上げる一方、ステルス性を犠牲にしている。②自律実行はフォレンジックな痕跡、識別しやすい識別子、コードレベルの痕跡を残す。③そのため、検知されるコストが低いシナリオに向いている。

それでも使われ続ける、という評価（出典1）——GTIG は高い確信度で、サイバー犯罪者が自律型攻撃ツールを使い続けると評価している。キャンペーンの到達範囲の拡大が、成功率の低下を補うためである。

逆に使われにくい層（出典1）——ステルス性を重視し長期の滞留を狙うアクターが公開版のツールを使う可能性は低いとされている。

そして、検知と妨害を分ける指摘がある（出典1）。「検知と、対応・妨害は別の機能である。攻撃を早期に検知しても、目的の達成を阻止するには不十分である。」

本記録の評価——この一文が、本事案の実務上の核心である（本記録の判断）。攻撃が2〜25秒のバーストで走り、最短15分で深いシステムアクセスに到るなら（出典1）、「検知してから人が判断して遮断する」工程は間に合わない。 必要なのは、検知の精度を上げることではなく、検知から遮断までを自動で閉じることである（本記録の評価）。

記事の結びも同じ方向を指している（出典1）。「LLM 支援のツールは新しい技術を生むのではなく、既存の手法を組み合わせる時間を大幅に短縮する。単一の ID・認証情報・ワークロードが侵害されても被害が限定されるよう設計することが最も重要である。」

Mandiant Consulting の提言は5層——いずれも長年の定石である対策・注意喚起出典 [1]

記事末尾の提言は5層に整理されている（出典1）。

層 概要
1 コントロールプレーンの保護（管理 API・コンソール・CI/CD を信頼ネットワークに限定）
2 ID とキーの制限（短命なワークロード認証情報へ移行し、シークレットを排除）
3 設定の強化と攻撃経路の削減（アプリ・インフラの継続的な脆弱性スキャン）
4 アプリケーション保護（正規機能の悪用を防止）
5 挙動・ボリューム変化の検知（ID の速度、API バースト、ボリューム異常の監視）

第2層の具体策が最も細かい（出典1）。AWS は静的アクセスキーから IAM ロールの一時認証情報へ移行する。Azure はサービスプリンシパルのクライアントシークレットをManaged Identity に置き換え、Azure Storage の共有キー認証を無効化して Entra ID とConditional Access を使う。Google Cloud は Workload Identity Federation を使い、長期のサービスアカウントキーを避ける。GitHub は classic PAT から fine-grained PAT や OIDC へ移行する。AWS の iam:PassRole を特定のロール・サービスに制限する。パスワード保管庫やシークレット基盤へのアクセスを制限し、一括取得を監視する。パスワードリセットやアカウント作成の急増を監視する。リポジトリ・イメージ・パイプラインのシークレットを継続的にスキャンし、露出した認証情報は即ローテーションする。

第3層には横展開の封じ込めが入る（出典1）。DMZ から内部への Kerberos・NTLM・LDAP・SMB・RDP・SSH・DB 接続を制限する。DB の実行アカウントに OS コマンド実行やファイル書き込みの権限を与えない。外部利用者に詳細なエラーやスタックトレースを返さない。AD CS では ENROLLEE_SUPPLIES_SUBJECT を避け、登録権限を絞る。Credential Guard・Protected Users を有効にし、SMB・LDAP の署名と channel binding を有効化して NTLM を減らす。

第4層は本件の特徴に直接対応している（出典1）。高影響 API（メール・通知・ユーザー作成・アクセス変更など）に受信者数やレート制限を設ける。RCE・デプロイ・一括メッセージなどの管理機能を事前に棚卸しする。内部アプリに SAST/DAST を実施し、LLM を使った脆弱性発見も検討する。

本記録の評価——第4層の「受信者数とレート制限」は、本件の観測（1,300超の社内ユーザーへのテスト通知、500回超の Web リクエスト、491個の webhook.site URL）にそのまま対応する（出典1。本記録の判断）。「正規機能に上限を付ける」ことが、自律エージェントに対する実効のある制約になる。

Google SecOps の検知ルールとして4件が挙げられている（出典1）——Suspicious Webhook.Site Interaction（webhook.site との疑わしい通信）、Suspicious Curl Invocation（疑わしい curl の起動）、Cmd Launching Curl（cmd が curl を起動）、AWS Cloud Accounts Getcalleridentity（AWS の呼び出し元 ID の取得）——いずれも Mandiant Frontline Threats / Mandiant Hunting Rules パックに含まれる（原文英語の規則名）。

**量そのものが検知の条件になる**（本記録の評価）。 **110,000を超えるオブジェクトの列挙、 500回を超える Web リクエストは、 人の操作では到達しない規模である**（出典1。本記録の判断）。 **Mandiant Consulting の提言の第5層が 「ID の速度、API バースト、ボリュームの異常を監視する」であり、 この段階を直接指している**（出典1）。
検知できた管理 API の急増・権限テスト・資格情報の取得を監視し、認証元（ネットワーク・ASN・リージョン・ホスティング事業者）の変化を追跡する　**Mandiant Consulting の提言の第5層**（出典1）。
影響を限定できたAD の列挙を抑える（Credential Guard・Protected Users の有効化、SMB・LDAP の署名と channel binding、NTLM の削減、AD CS で `ENROLLEE_SUPPLIES_SUBJECT` を避ける）　**Mandiant Consulting の提言の第3層**（出典1）。
認証情報アクセス検知した
**権限の探索は、短時間の高密度な API 呼び出しとして現れる** （出典1。本記録の評価）。 **Google SecOps の検知ルールに 「AWS Cloud Accounts Getcalleridentity」（AWS の呼び出し元 ID の取得）が 含まれているのは、この段階に対応するものである**（出典1）。
影響を限定できた静的な長期キーを廃し、短命な認証情報へ移行する（AWS は IAM ロールの一時認証情報、Azure は Managed Identity、Google Cloud は Workload Identity Federation、GitHub は fine-grained PAT や OIDC）　**Mandiant Consulting の提言の第2層**（出典1）。 **本記録の評価——侵害済み認証情報が入口であるため、 認証情報の寿命を短くすることが最も直接に効く**（本記録の判断）。
侵入を防げたパスワード保管庫・シークレット基盤へのアクセスを制限し、一括取得を監視する。リポジトリ・イメージ・パイプラインのシークレットを継続的にスキャンし、露出した認証情報は即ローテーションする　**Mandiant Consulting の提言の第2層**（出典1）。
実行検知した
**痕跡が多い**（出典1。本記録の評価）。 **①Weaver OA の事例では240件のログイベントが生成された。 ②WebShell の候補ごとに短命で半ば連番のファイル名 （`cl1217.jsp`・`f1219a.jsp`・`z1219.jsp`）が作られた。 ③実行時のエラー（「変数 `t` は既に定義されている」）を経て 反復的に書き直されている**（出典1）。 **本記録の評価——名前の規則は変えられるため、 名前ではなく「短時間での連番生成と反復的な失敗」で引く必要がある** （本記録の判断）。
侵入を防げたDB の実行アカウントに OS コマンド実行やファイル書き込みの権限を与えない　**Mandiant Consulting の提言の第3層**（出典1）。 **本記録の評価——本件の手口は `SET GLOBAL general_log_file` で任意のパスにログを書かせることに 依存している**（出典1） ——**書き込み先を制限すれば成立しない**（本記録の判断）。
侵入を防げた管理機能（RCE・デプロイ・一括メッセージなど）と高影響 API を事前に棚卸しし、正規機能の悪用を前提に保護する　**Mandiant Consulting の提言の第4層**（出典1）。 **本記録の明示——本件で使われたのは正規に公開された アプリケーション固有の SQL API であり、脆弱性ではない**（出典1）。
影響を限定できた外部利用者に詳細なエラーやスタックトレースを返さない　**Mandiant Consulting の提言の第3層**（出典1）。 **本記録の評価——本件では ARTEX が 「スクリプトが大きすぎる」「変数 `t` は既に定義されている」という エラーメッセージを読んで自力で修正している**（出典1） ——**エラーの詳細が自律エージェントの入力になっている**（本記録の判断）。
横展開検知した
**検知はできる。しかし間に合うかは別である**（本記録の評価）。 **GTIG 自身が「検知と、対応・妨害は別の機能である。 攻撃を早期に検知しても、目的の達成を阻止するには不十分である」と 明記している**（出典1）。 **最短15分という速度に対して、 人が判断して遮断する工程は間に合わない**（本記録の判断）。
影響を限定できたDMZ から内部への Kerberos・NTLM・LDAP・SMB・RDP・SSH・DB 接続を制限し、侵害されたワークロードが届く範囲を最小化する　**Mandiant Consulting の提言の第3層**（出典1）。
検知できた認証・権限探索・ストレージ列挙・大量ダウンロード・未知の外部サービスへの接続を、一連のシーケンスとして相関させる　**Mandiant Consulting の提言の第5層**（出典1）。 **本記録の評価——単発の事象では引けないが、 この順序が短時間に並ぶことは人の操作では起きにくい**（本記録の判断）。
影響を限定できた検知から遮断（セッション無効化・キーのローテーション・ネットワーク隔離）までを自動で閉じる　**本記録の評価。** **GTIG の「検知と妨害は別の機能」という指摘と、 最短15分という観測から導かれる**（出典1。本記録の判断）。 **これは記事の提言には明示されていない。**
C2通信検知した
**正規サービスを C2 に使うため、 ドメイン単位の遮断は業務影響を伴う**（本記録の評価）。 **Google SecOps の検知ルールに 「Suspicious Webhook.Site Interaction」 （webhook.site との疑わしい通信）が含まれている**（出典1）。 **491個という数は、 「同一ホストから短時間に多数の異なる使い捨て URL へ出ていく」という 形で引ける**（本記録の判断）。
検知できたサーバの egress を制限し、Webhook・OAST・トンネリング・ファイル共有・外部 AI プラットフォームへの未知の宛先を監視する　**Mandiant Consulting の提言の第5層**（出典1）。 **本記録の評価——「外部 AI プラットフォーム」が 監視対象に挙げられている点が本件固有である**（本記録の判断） ——**エージェントは推論のために外部 API を呼ぶため、 その通信自体が痕跡になる。**
検知できた必要なテレメトリ（ID・コントロールプレーン・データプレーン・DNS・プロキシ・ネットワーク・エンドポイント）を収集・集約する　**Mandiant Consulting の提言の第5層**（出典1）。
持ち出し検知した
**ボリュームの作成・ディスクの拡張・スナップショットの展開は、 クラウドのコントロールプレーンに記録される事象である** （本記録の評価）。 **Mandiant Consulting の提言の第5層が 「ストレージのデータプレーンで列挙、書き込み・読み取り・削除の連続、 大量ダウンロードを検知する」としている**（出典1）。
検知できたストレージのデータプレーンで、列挙・書き込み／読み取り／削除の連続・大量ダウンロードを検知する　**Mandiant Consulting の提言の第5層**（出典1）。
影響を限定できた高影響 API（メール・通知・ユーザー作成・アクセス変更など）に受信者数やレート制限を設ける　**Mandiant Consulting の提言の第4層**（出典1）。 **本記録の評価——本件の観測（1,300超の社内ユーザーへのテスト通知、 500回超の Web リクエスト、491個の webhook.site URL）は いずれも「正規機能を上限なく回した」結果である**（出典1。本記録の判断） ——**上限を付けることが、自律エージェントに対する実効のある制約になる。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • **「検知できるか」ではなく「検知から遮断までが自動で閉じるか」を問う**
    **GTIG 自身が「検知と、対応・妨害は別の機能である。 攻撃を早期に検知しても、目的の達成を阻止するには不十分である」と 明記している**（出典1）。 **Wiz の観測では、最初の侵害アカウントから深いシステムアクセスまで 通常約4時間、ある事例では15分であった**（出典1）〈齟齬1〉。 **ARTEX の個々の実行は2〜25秒のバーストで走る**（出典1）。 **この速度に対して、「警報が上がる→担当者が見る→判断する→遮断する」という 工程は間に合わない**（本記録の評価）。
    取るべき行動 **①現在の自組織の「検知から遮断まで」の実測値を出す （警報の発生から、セッション無効化・キーのローテーション・ ネットワーク隔離が完了するまでの時間を、訓練で計る）。** **②その値が1時間を超える経路について、 自動遮断（条件付きアクセスによるセッション失効、 キーの自動ローテーション、 異常な ID の自動隔離）の導入を検討する。** **③自動遮断の誤作動が業務を止める範囲を事前に評価し、 「止めてよい範囲」を経営として決めておく ——この判断を現場に委ねると自動化は入らない。**
  • **新しい攻撃基盤に、新しい対策は提示されていない。定石の「隙間」を潰す**
    **GTIG 自身が 「提案する防御戦略——コントロールプレーンの分離、 短命な認証情報、最小権限、セグメント化、挙動ベースの検知——は いずれも長年のセキュリティのベストプラクティスである」と書いている** （出典1）。 **原因も新しくない** ——**「侵害された認証情報を使うこと、未修正のシステムを狙うことといった 侵入の仕組みは変わらないままである」**（出典1）。 **変わったのは速度と規模だけである**（出典1）。
    取るべき行動 **①5層（コントロールプレーンの保護／ID とキーの制限／ 設定の強化と攻撃経路の削減／アプリケーション保護／ 挙動とボリュームの検知）について、 自組織の実施状況を「導入済み・部分・未」で棚卸しする。** **②「部分」のものについて、 どこに隙間が残っているか（どの環境・どのアカウント種別・ どのネットワーク区間が外れているか）を具体に落とす。** **③AI エージェントを理由とした新規の製品導入より、 既存対策の網羅率を上げる方を優先する—— 報告自体がその順序を示している。**
  • **正規機能に上限が無い箇所を棚卸しする。エージェントはそこを上限なく回す**
    **本件の観測の多くは、正規機能を上限なく回した結果である**（出典1） ——**AD で110,000超のオブジェクト列挙、 500回超の Web リクエスト、 テスト通知で1,300超の社内ユーザーへの送信、 491個の webhook.site URL。** **Weaver OA の事例では、 正規に公開されたアプリケーション固有の SQL API が使われており、 脆弱性の悪用ではない**（出典1）。 **Mandiant Consulting の提言の第4層が 「高影響 API に受信者数やレート制限を設ける」である**（出典1）。
    取るべき行動 **①社内アプリと SaaS について、 「管理者が使う高影響の機能」（一括メール・通知・ユーザー作成・ アクセス変更・デプロイ・任意コード実行）を棚卸しする。** **②それぞれに受信者数・実行回数・時間あたりの上限があるかを確認し、 無いものに上限を付ける。** **③上限に当たったときの警報の宛先を決める ——上限は検知の仕組みにもなる。**
  • **「アジア」という地域記述を日本と読み替えない。日本への言及は無い**
    **記事に日本への言及は無い**（出典1。本記録の確認）〈未確定1〉。 **示されているのは、米国・欧州（エンタープライズソフトウェア・ 産業オートメーション・半導体・通信）、 米国（政府・テクノロジー・化学材料・製造）、 アジア（金融セクターを狙ったとする公開報告、 システムインテグレーターと大手通信企業、航空宇宙）である**（出典1）。 **ただし ARTEX はフォークを通じて世界的に拡散しており、 地域化された派生版（ScopeWeaver）や商用版（ARTEX PRO）が 存在するとされる**（出典1）。
    取るべき行動 **①外部の脅威情報を社内に伝えるとき、 「日本が対象として名指しされているか」を区別して書く。** **②名指しが無い場合は、 自組織が該当する業種・構成（本件ではソフトウェアベンダー、 産業オートメーション、半導体、通信、政府、SI）で当てはめる。** **③フォークによる拡散が示されているツールについては、 「報告された地域の外でも使われうる」ことを前提に置く。**
セキュリティ技術者への示唆
  • **「長い停止＋2〜25秒の高密度バースト」という時間の形を検知条件に書く**
    **GTIG はログとタイムスタンプから 「人間の攻撃者にとってはきわめて不規則な活動の塊」を特定した**（出典1）。 **いずれの侵入も工程中に長い停止を示したが、 個々の実行シーケンスは2〜25秒の圧縮されたバーストで走った**（出典1）。 **1つのオペレーションでは23秒の実動時間に27イベントが記録された**（出典1）。 **Azure では一時 Blob の書き込み・削除が330〜400ミリ秒、 ARM の validate sweep が8秒で11リソースタイプである**（出典1）。
    取るべき行動 **①クラウドの監査ログ（AWS CloudTrail・Azure Activity Log・ Google Cloud Audit Logs）に対し、 「同一の ID が N 秒以内に M 件以上の API を呼ぶ」という 速度の条件を書く（本件の観測なら23秒で27件が目安になる）。** **②条件を「件数」だけでなく 「異なる API 種別の数」でも書く ——権限の探索は種類が多い。** **③長い停止を挟む点に注意し、 相関の時間窓を工程単位（数十秒）と侵入単位（数時間）の 2段で持つ。**
  • **MySQL の `general_log` による JSP 書き込みを塞ぐ——DB アカウントに書き込み権限を与えない**
    **本件の手口は `SET GLOBAL general_log_file = '<webshell のパス>'` → `SET GLOBAL general_log = 1;` → `SELECT '<% [webshell の内容] %>'` という順序で成立する**（出典1）。 **Java のサーブレットが JSP を扱う仕組み上、 `<% %>` の中のコードが解析・コンパイルされて プロセスのメモリ空間に入る**（出典1）。 **使われた API は正規に公開されたアプリケーション固有の SQL API であり、 脆弱性ではない**（出典1）。 **Mandiant Consulting の提言の第3層が 「DB の実行アカウントに OS コマンド実行やファイル書き込みの権限を 与えない」である**（出典1）。
    取るべき行動 **①アプリケーションが使う DB アカウントから `SUPER`／`SYSTEM_VARIABLES_ADMIN` 相当の権限と ファイル書き込み権限（`FILE` 等）を外す。** **②`general_log_file`・`secure_file_priv` の設定を確認し、 Web から到達できるパスへ書けない状態にする。** **③`SET GLOBAL general_log` の変更を監査ログの警報にする ——正常な運用でこの値が動くことは稀である。** **④アプリケーションが公開している SQL 実行系の API を棚卸しし、 利用者の認証情報で到達できる範囲を確認する。**
  • **短時間に半ば連番の名前のファイルが複数作られる形を検知する（名前そのものではなく）**
    **本件では、WebShell の候補ごとに短命で半ば連番のファイル名 （`cl1217.jsp`・`f1219a.jsp`・`z1219.jsp`）が付き、 それぞれ別のコマンドを実行していた**（出典1）。 **別の事例では `artex-probe-*`（`*` は5桁の半ば連番の数字）という ファイル名でさまざまな拡張子のファイルが生成された**（出典1）。 **GTIG は、ARTEX が設置ファイル名・作成したアカウント名にも 同様の連番の目印を使っていたと観測している**（出典1）。 **ただし名前の規則は変更できる**（本記録の評価）。
    取るべき行動 **①Web 公開ディレクトリのファイル完全性監視で、 「短時間に複数の新規ファイルが作られる」ことを警報にする （1件ごとではなく、頻度で引く）。** **②作成されたアカウント名について、 短時間に複数・名前が半ば連番という形を検知条件に入れる。** **③`artex-probe` のような既知の文字列も条件に入れてよいが、 それだけに依存しない——フォークと派生版が拡散している。**
  • **外部 AI プラットフォームへの通信と、使い捨て Webhook サービスを監視対象に入れる**
    **ARTEX はフロンティアおよびオープンソースのモデルの API を 活用して高レベルの目標を機械命令に翻訳する**（出典1） ——**推論のための外部通信が発生する。** **C2 としては491個の使い捨て webhook.site URL が使われた**（出典1）。 **Mandiant Consulting の提言の第5層は 「サーバの egress を制限し、Webhook・OAST・トンネリング・ ファイル共有・外部 AI プラットフォームへの未知の宛先を監視する」である** （出典1）。 **Google SecOps の検知ルールにも 「Suspicious Webhook.Site Interaction」が含まれている**（出典1）。
    取るべき行動 **①業務サーバからの egress を白名簿化し、 外部 AI プラットフォームの API エンドポイントへの通信を 既定で遮断または警報にする（業務で使う場合は経路を明示的に分ける）。** **②webhook.site・OAST 系サービス・トンネリングサービスへの通信を 検知条件にする。** **③「同一ホストから短時間に多数の異なる使い捨て URL へ出ていく」という 形で引く——個々の URL は遮断しても意味が薄い。**
  • **詳細なエラーを外部に返さない。それが自律エージェントの入力になっている**
    **本件では ARTEX が 「スクリプトが大きすぎる」というエラーを引用して自力で修正し、 約10秒で17スナップショットのインスタンスを展開した**（出典1）。 **WebShell の実行時のエラー （「変数 `t` は既に定義されている」）を経て、 目的の異なる複数の WebShell を書き、 一部は前の誤りを訂正して最終的に成功させた**（出典1）。 **Mandiant Consulting の提言の第3層に 「外部利用者に詳細なエラーやスタックトレースを返さない」が含まれている** （出典1）。 **本記録の評価——従来この項目は情報漏えいの観点で語られてきたが、 自律エージェントに対しては「学習の入力を断つ」意味を持つ** （本記録の判断）。
    取るべき行動 **①外部公開のアプリケーションとAPI について、 エラー応答に実装の詳細（スタックトレース・SQL の内容・ 内部パス・変数名）が含まれていないかを確認する。** **②エラーは一般化したメッセージと相関用の ID のみを返し、 詳細はサーバ側のログに残す。** **③同一の ID・送信元から短時間に多数のエラーが発生することを 警報にする——反復的な試行錯誤はエラーの山として現れる。**
