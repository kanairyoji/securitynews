攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃の中心は、正規の署名済み部品に「何を読み込むか」を 設定ファイルで指示することである**（出典1）。 **攻撃者が持ち込んだのは `.config` 2本と `.resx` 1本で、 実行可能ファイルは1つも無い。** **以下は出典1が示した筋道を段階に整理したものである**（本記録の整理）。

  1. 1. 偵察[1]
    **攻撃は、アジアの政府機関だけが使う Windows 10 の カスタムビルドに合わせて作られている**（出典1）。 **根拠は痕跡の消し方である**—— **`.NET 1 Loader` が抜き取るのは `%WINDIR%\Logs\CmitUpdateAgent\` のログのうち `GetExtendedUpdateInfoHandler` を含む行に限定されており、 この更新エージェントは当該専用ビルド固有の部品である**（出典1）。 **攻撃者が標的環境の中身を事前に調べていたことを示す** （本記録の整理）。 **どのように調べたかは公表されていない**〈未確定1〉。
  2. 2. 初期侵入[1]
    **悪性の CAB 書庫が `C:\Windows\SoftwareDistribution\Download\` に置かれ、 中身7ファイルが `...\Download\Install\` へ展開された**（出典1）。 **7ファイルの大半は Patch My PC の正規コンポーネントで、 Kaspersky が悪性コードを含むとしたのは `Resources.resx` のみである** ——**ただし改変された `PatchMyPC-ScriptRunner.exe.config` と `fabric.config` も実行の筋道の要である**（本記録の整理）。 **CAB がどのようにして端末に届いたかは観測されていない** （出典1が明記）〈未確定1〉。
  3. 3. 実行[1]
    **正規の `PatchMyPC-ScriptRunner.exe` が `-updatepackage` とアプリケーション ID を引数に起動され、 同名の `.config` が AppDomainManager として Microsoft 署名済みの `Microsoft.HostIntegration.Connectors.dll` 内の `Microsoft.ApplicationServer.Caching.DataCacheFactoryConfiguration` を 読み込ませた**（出典1）。 **同クラスは `fabric.config` を読み、 そこで指定された `System.Resources.ResXResourceSet` に `Resources.resx` を渡す。** **`Resources.resx` には `BinaryFormatter` で直列化された オブジェクトが Base64 で入っており、 その復元の過程で TypeConfuseDelegate が成立して `XamlReader.Parse()` が呼ばれ、埋め込みの XAML-1 が実行された。**
  4. 4. 検知回避[1] [2]
    **XAML-2-1 が AMSI を無力化した**（出典1）—— **`Console.Clear()` の先頭バイトをメモリ上で `41 C7 00 01 00 00 00 33 C0 C3` に書き換え、 AMSI の COM オブジェクト（CLSID `fdb00e52-a214-4aa1-8fba-4357bb0072ec`。 文字列を分割して組み立てる）の仮想関数表の オフセット `0x18` を差し替えて、 `CAmsiAntimalware::Scan` がつねに「問題なし」（0）を返すようにした。** **続いて `.NET 1 Loader` が CAB の展開物・CLR の使用ログ・Prefetch を削除し、 `CmitUpdateAgent` のログから該当行を抜き、 `HKLM\SOFTWARE\Classes\appid\` 配下の GUID キー9個を削除し、 `COMPlus_ETWEnabled=0` を設定して .NET のイベントトレーシングを止めた**（出典1）。
  5. 5. 永続化[1] [2]
    **`.NET 1 Loader` は、RPC で公開された COM オブジェクト （CLSID `ab8902b4-09ca-4bb6-b78d-a8f59079a8d5`）を使って XAML-3 を新しい `dllhost.exe` の中へ読み込ませ、 元のプロセスの親子関係から切り離した**（出典1）。 **`.NET 2 Plugin` はレジストリの GUID サブキー12個を削除した後、 `{ff259bcd-2f0a-44de-b34a-0092fec1d8a2}` を作り `DllSurrogate` を設定し、 `CoLockObjectExternal` で `dllhost.exe` の寿命を保った**（出典1）。 **さらに自身が `dllhost.exe` の中にいるかを確認し、 約28時間（100,801秒）のタイマーで自ら終了する。**
  6. 6. C2通信[1]
    **`.NET 2 Plugin` は20〜40分待ってから `openaigpt4v[.]com` へ初回接触した**（出典1）。 **応答があれば次は5〜6分後、 応答が無ければ22〜28時間後（10分ごとに時刻を確認）に再接触する。** **プロキシを WinHTTP・`explorer.exe` の権限借用・ `DefaultWebProxy` の3通りで探し、 SSL 証明書は無検査（`tp` = `*`）、 Host ヘッダは `rh` の値で上書きする。** **通信は AES-128-CBC ＋ HMAC-SHA256（Encrypt-then-MAC）で、 鍵は共通鍵 `ec` から HMAC（種 0〜3）で導出し、 形式は IV(16バイト) ｜ 本体 ｜ HMAC(32バイト) を Base64 にして URL のクエリ文字列へ載せる。** **受け取った XAML は乱数 GUID を名前にした隔離 AppDomain で実行し、 終了後に破棄する。**

ここから読める実務上の含みは2つである（本記録の評価）。

第一に、実行ファイルの署名検査では止まらない。 起点のプロセスも、コードを読み込んだ DLL も、どちらも正規の署名済みファイルである。 攻撃者の持ち込み物は .config 2本と .resx 1本——いずれも「実行されるもの」とは見なされにくい拡張子である。

第二に、.config は「設定」ではなく「実行の指示書」である。 AppDomainManager の差し替えは、アプリケーションの起動時に任意のアセンブリ・任意の型を最初に読み込ませる機構である（本記録の補足）。実行ファイルの隣に同名の .config を置けるなら、その実行ファイルが何を読み込むかは置いた側が決められる。

置かれた場所が Windows 更新の作業ディレクトリだったこと自体が、この攻撃の設計である原因・手口

CAB 書庫が置かれたのはC:\Windows\SoftwareDistribution\Download\ で、展開先は ...\Download\Install\ である（出典1。事実）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Kaspersky は、読み込み機構の内部構造・AMSI の無力化の手順・ 痕跡の消去の対象・指令通信の仕様と痕跡情報を詳細に公表した一方で、 被害組織の国名・組織名と、標的となった Windows 10 カスタムビルドの 正式名称は公表しなかった（出典1）部分的に機能**本記録の評価。** **技術的な部分の開示は十分であり、 防御側が自分の環境で確認すべき点 （更新ディレクトリの `.config`、`dllhost.exe` の外向き通信、 `COMPlus_ETWEnabled=0` の設定）まで導ける**（出典1・2）。 **一方で、標的の特定を避けた結果、 「この攻撃が自組織に関係するか」を読者が判定できない** ——**本記録は applicability を 「専用ビルドを使っているか」ではなく 「同じ構造を持つか」の軸で立てることにした**（本記録の方針）。
CISO・経営層への示唆
  • 「署名されていない実行ファイルを止める」型の防御では止まらない攻撃がある、という前提を置き直す
    **本件で攻撃者が持ち込んだのは `.config` 2本と `.resx` 1本だけで、 実行可能ファイルは1つも無い**（出典1。事実）。 **コードを読み込んだのは Microsoft が署名した DLL であり、 起点のプロセスも第三者製パッチ配布ツールの正規実行ファイルである。** **許可リスト・署名検査・未署名バイナリの遮断—— いずれもこの経路には何も映らない**（本記録の評価）。
    取るべき行動 **自組織の端末防御について、 「実行ファイルの出自」以外にどの観点で判断しているかを 担当部門に説明させる。** **具体的には——①プロセスが読み込んだアセンブリ・DLL の 組み合わせを記録しているか、 ②`.config` などの設定ファイルの作成・改変を記録しているか、 ③記録は端末の外へ転送されているか、の3点を確認する。** **「EDR を入れている」という答えで止めず、 本件の3つの着眼点（更新ディレクトリの `.config`・ `dllhost.exe` の外向き通信・`COMPlus_ETWEnabled=0`）で 検索できるかを実際に試させる。**
  • 「閉じたネットワークだから外に出られない」を防御として数えない
    **本件のプラグインは、プロキシを WinHTTP・`explorer.exe` の権限借用・`DefaultWebProxy` の 3通りで探す**（出典1。事実）〈重要〉。 **これは直接インターネットに出られない環境を 前提に作られているという意味である**（本記録の評価） ——**攻撃者は「閉じている」ことを障害ではなく条件として扱っている。** **標的が政府機関である点と整合する。**
    取るべき行動 **閉域・準閉域と称しているネットワークについて、 外部への到達経路を実際に列挙させる （業務用プロキシ・管理用経路・更新用の中継・ 利用者端末のブラウザ設定を含む）。** **そのうえで、許可した経路以外からの到達試行が 記録・遮断されるかを試験する。** **「出られないはず」と「出られないことを確認した」を 区別して報告させる。**
  • 更新・配布の仕組みを「信用している経路」として棚卸しの対象に含める
    **CAB が置かれたのは Windows 更新の作業ディレクトリで、 起点になったのは第三者製パッチ配布ツールの正規実行ファイルである** （出典1。事実）。 **更新の仕組みは、ファイルが入れ替わり未知の実行が起きることが 正常な唯一の経路であり、 そのために監視の除外に入りやすい**（本記録の評価）。
    取るべき行動 **①端末防御・ログ収集の除外設定の一覧を提出させ、 除外した理由と、除外した範囲で何が起きても気づかないかを明記させる。** **②パッチ配布・ソフトウェア配布に使っている製品を一覧にし、 その製品が端末上でどの権限でどのディレクトリに書き込むかを 把握しているかを確認する。** **③供給元が侵害された場合の話と、 供給元の正規ファイルが流用された場合の話を分けて検討させる** ——**本件は後者であり、供給元への問い合わせでは解決しない。**
  • ベンダーの調査で公表された事案について、自組織が対象かを判定する手順を持つ
    **本件は被害組織の公表ではなく、 Kaspersky のテレメトリ1件から明らかになった事案である** （出典1。事実）。 **標的の国名・専用ビルド名は公表されていない**〈未確定2〉—— **「自社は対象か」を公表資料から判定できない**（本記録の評価）。 **同種の侵害が他組織で起きていても、 その組織が同社の製品を使っていなければこの報告には現れない。**
    取るべき行動 **ベンダーレポートを受け取ったときの判定手順を文書化する** ——**①公表された痕跡情報（ハッシュ・ドメイン・パス）を 自社のログに当てる、 ②痕跡が無くても手口の構造（本件なら 「設定ファイルで署名済み部品に読み込みを指示する」）が 自社環境で成立するかを机上で確認する、 ③成立するなら検知規則を1つ作る、の3段。** **「自社は該当なし」という結論を出すときは、 ①だけで出していないかを確認する。**
セキュリティ技術者への示唆
  • 更新の作業ディレクトリで、実行ファイルの隣に現れた `.config` を検知対象にする
    **本件の実行は `C:\Windows\SoftwareDistribution\Download\Install\ PatchMyPC-ScriptRunner.exe.config` から始まっている** （出典1。事実）。 **`.config` は「設定」ではなく、 .NET が起動時に何を読み込むかを決める指示書である** （本記録の補足）—— **AppDomainManager の指定はアプリケーション起動時に 任意のアセンブリ・任意の型を最初に読み込ませる。**
    取るべき行動 **①`C:\Windows\SoftwareDistribution\Download\` 配下の ファイル作成イベントを収集する（除外していたら外す）。** **②`.config` ファイルの内容に `appDomainManagerAssembly` / `appDomainManagerType` が 現れるものを抽出する。** **③`.resx` ファイルの中に直列化オブジェクト （Base64 の長い文字列・`BinaryFormatter` の痕跡）を 含むものを抽出する。** **④出典1 のファイルパス3件をそのまま検索式にする。**
  • `dllhost.exe` の外向き通信と .NET の読み込みを、単独で異常として扱う
    **最終段は RPC 経由の COM で 別プロセスの `dllhost.exe` に読み込まれ、 親子関係から切り離されている**（出典1。事実）。 **`dllhost.exe` は COM オブジェクトの代理ホストであり、 自分でインターネットへ出る業務は通常存在しない** （本記録の評価）—— **プロセスの系譜では起点まで戻れないが、 この1点だけでも抽出できる。**
    取るべき行動 **①`dllhost.exe` からの外向き TCP/443 を抽出する規則を作る （正当な例があるなら事前に洗い出して除外一覧にする）。** **②`dllhost.exe` 内での CLR の読み込み・ .NET アセンブリの読み込みを抽出する。** **③`HKLM\SOFTWARE\Classes\appid\` 配下の `DllSurrogate` の新設・変更を記録する （本件は12個を削除して1個を作っている）。**
  • ログを消す行為そのものを検知対象にする——とくに「行だけ抜く」改変
    **`.NET 1 Loader` は、ログを丸ごと消すのではなく `%WINDIR%\Logs\CmitUpdateAgent\` から `GetExtendedUpdateInfoHandler` を含む行だけを抜いている** （出典1。事実）〈重要〉。 **ファイルは存在し、サイズも大きく変わらない**（本記録の整理） ——**「ログが消えた」という検知には引っかからない。** **同時に Prefetch・CLR 使用ログの削除、 `COMPlus_ETWEnabled=0` の設定も行っている。**
    取るべき行動 **①`COMPlus_ETWEnabled` を 0 に設定したプロセスを 検知対象にする（正常な業務では起きない）。** **②Prefetch（`C:\Windows\Prefetch\`）と CLR 使用ログの削除イベントを記録する。** **③更新・配布系のログを端末の外へ転送し、 端末上の控えとの差分（行の欠落）を定期的に突き合わせる。** **行単位の欠落は、端末外の控えが無いと検出できない。**
  • AMSI の無力化は「`amsi.dll` の改変」だけではない——COM の呼び出し表を見る
    **本件は `amsi.dll` のコードを改変していない**（出典1。事実）。 **変えたのは AMSI の COM オブジェクト （CLSID `fdb00e52-a214-4aa1-8fba-4357bb0072ec`）の 仮想関数表のオフセット `0x18` で、 `CAmsiAntimalware::Scan` の呼び出し先を差し替えている** ——**走査要求に対してつねに 0（問題なし）が返る。** **モジュールの完全性検査では見つからない**（本記録の評価）。
    取るべき行動 **①AMSI に依存した検知の有効性を、 実際に無効化された状態で確認する試験を1回行う （AMSI が返す結果を信用した判定が、どこで何件あるかを把握する）。** **②AMSI の結果に依存しない層 （プロセス系譜・読み込みアセンブリ・外向き通信・ レジストリの変更）で同じ攻撃が見えるかを検証する。** **③AMSI が「つねに問題なし」を返している状態を 検知できるかを確認する。**
  • 痕跡情報は検証せずに検知へ流さない——とくに CDN の共有 IP
    **出典1 の痕跡情報には `104.18.14[.]219` が含まれるが、これは Cloudflare の CDN の アドレスである**（出典1。事実）。 **指令サーバーのドメイン `openaigpt4v[.]com` は Cloudflare の背後にある**—— **IP を遮断すると、同じ CDN を使う無関係なサービスを巻き込む** （本記録の評価）。
    取るべき行動 **①公開された痕跡情報を、遮断ではなく まず「過去ログの検索」に使う。** **②IP の遮断は、それが共有基盤のアドレスかを確認してから決める （本件の IP は共有である）。** **③ドメインは遮断の対象にしてよいが、 `openaigpt4v[.]com` のように正規サービスに似せた名前は 誤って許可一覧に入っていないかを先に確認する。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 端末防御・ログ収集の除外設定に、Windows 更新や ソフトウェア配布の作業ディレクトリが含まれている本件の CAB と `.config` はまさにその場所に置かれた。 除外した範囲で何が起きても気づかない

体制・契約□ ベンダーの調査レポートを受け取ったときに、 痕跡情報の照合だけで「該当なし」と判定している本件は被害1件・標的国も専用ビルド名も非公表で、 痕跡の照合では自組織が対象かを判定できない。 手口の構造が自社で成立するかの机上確認が要る
