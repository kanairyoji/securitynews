INC-2026-0832PingCAP 侵害で TiDB Cloud 情報流出

TiDB の開発元 PingCAP の社内システムが、不正取得された**サービスアカウントの 認証情報**で2026年9月9日〜10月7日（米国時間）に侵入され、データが複製された。 **TiDB Cloud のアカウント情報・取引情報・API キーの一部・ソースコード**が 持ち出され、**日本国内で最大約5万件**の個人情報が漏えいしたとされる。

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている日本に波及した海外事案認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年10月19日（英語版の報告公開） 最終更新: 2026年11月3日

データベース基盤の提供元が侵害され、顧客側に鍵の入れ替えを要求した事案です。分散 SQL データベース TiDB を開発する PingCAP は、不正に取得されたアカウントの認証情報を使って社内システムに侵入され、データが複製されたことを公表しました（出典1・2）。

期間は2026年9月9日から10月7日（米国時間）。同社が認識したのは10月7日で、同日のうちに影響を受けた認証情報の無効化を開始しています（出典1・2）。侵入から検知まで28日間（本記録の算出）。

持ち出された範囲は3〜4種に分かれます（出典1・2）。①TiDB Cloud のアカウント情報（ユーザー名・メールアドレス・組織とプロジェクトの関連付け・SQL エディタの実行履歴とエラー情報・問い合わせ情報）②取引関連情報（氏名・メールアドレス・企業名・電話番号・契約条件・注文内容・支払条件・請求設定）③認証情報（TiDB Cloud API キーの Public Key 部分）。英語版の報告はこれに加えてソースコードの取得にも触れています〈差異1〉（出典2）。

日本法人の公表は「日本国内で最大約5万件の個人情報が漏洩したことが判明」としています（出典1）。国内でこの事案を測る数値はこれ1つです。

顧客側の作業が明示されている点が、この事案の実務上の要点です（出典1）。アクセスログの確認・組織メンバーとロールの見直し・TiDB Cloud で発行した API キーのローテーション——つまり「提供元が侵害されたので、利用側で鍵を入れ替えてほしい」という依頼です（本記録の整理）。

一方で、TiDB に保存された顧客データ自体への影響は「確認されていない」とされています（出典1・2）。本記録はこれを「影響が無かった」とは読みません ——調査は継続中であり、同社自身が「データ流出の範囲を否定するものではない」と留保しています（出典2）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**入口は認証情報、影響の広がりは権限である**（出典1・2。本記録の整理）。 **不正取得されたサービスアカウントの認証情報で社内システムに入られ、 28日間にわたってデータが複製された**（出典1・2）。 **同社が対応として「クラウドプロジェクト間の過剰な権限の削除」を挙げている点から、 1つのアカウントから複数のプロジェクトへ到達できる状態だったと読める** （本記録の評価）。 **本番システムでは、攻撃者がコマンドを実行した形跡や永続的なアクセスの痕跡は 確認されていないとされるが、同社自身が 「これはデータ流出の範囲を否定するものではない」と留保している**（出典2）。

    **第三者が不正取得したアカウント（サービスアカウント）の認証情報を使って 社内システムにアクセスした**（出典1・2）。 **認証情報が盗まれた経路は公表されていない**〈未確定1〉。
    根拠: PingCAP の報告（「不正取得したアカウントの認証情報を使用して社内システムにアクセス」）
  2. 2. 内部探索推定[2]
    **社内システム内で、顧客のアカウント情報・取引情報・ API キーを含むテーブル・ソースコードへ到達した**（出典1・2）。 **同社は10月10日に「クラウドプロジェクト間の過剰な権限」を削除しており、 プロジェクトをまたぐ到達が可能だったと読める**（出典2。本記録の評価）。
    根拠: PingCAP の報告（持ち出された情報の分類、過剰な権限の削除）
  3. 3. 収集確認済[1] [2]
    **①TiDB Cloud のアカウント情報**（ユーザー名・メールアドレス・ 組織とプロジェクトの関連付け・SQL エディタの実行履歴とエラー情報・ 組織/プロジェクト/クラスタ ID・問い合わせ情報） **②取引関連情報**（氏名・メールアドレス・企業名・電話番号・ 契約条件・注文内容・支払条件・請求設定） **③TiDB Cloud API キーの Public Key 部分**（出典1）。 **英語版はこれに加えてソースコードの入手にも触れる**〈差異1〉（出典2）。 **SQL エディタの実行履歴が含まれる点は、 クエリ本文にテーブル名・カラム名・条件値が現れるため、 顧客のスキーマや業務の形が読める材料になる**（本記録の評価）。

失われたのはデータベースの中身ではなく、データベースへ入るための名簿である被害規模・影響範囲出典 [1] [2]

この事案で持ち出されたのは、顧客が TiDB に保存しているデータではありません（出典1・2）。

持ち出されたのは、TiDB Cloud を使うための周辺情報です（出典1）。

  • アカウント情報 — ユーザー名、メールアドレス、組織・プロジェクトの関連付け、SQL エディタの実行履歴とエラー情報（組織・プロジェクト・クラスタ ID を含む）、問い合わせ情報（サポートチケット）
  • 取引関連情報 — 氏名、メールアドレス、企業名、電話番号、契約条件（注文内容・支払い条件・請求設定）
  • 認証情報 — TiDB Cloud API キーの Public Key 部分

英語版の報告はこれに加えて、攻撃者がソースコードを入手したとしています〈差異1〉（出典2）。

「組織・プロジェクトの関連付け」と「SQL エディタの実行履歴」は、一見すると軽い情報です（本記録の評価）。しかし前者は、どの会社がどの規模のクラスタを持っているかの名簿になり、後者はテーブル名・カラム名・条件値を通じて業務の形を見せます。 攻撃者が次に狙う先を選ぶための材料として質が高い（本記録の判断）。

TiDB Cloud への不正アクセスとクレジットカード情報の流出は確認されていないとされています（出典1）。ただし英語版は、本番システムで痕跡が見つからないことを示したうえで「これはデータ流出の範囲を否定するものではない」と明記しています（出典2）。

28日間気づかれず、検知後7日で遮断を完了している組織の対応出典 [1] [2]

時間の並びは、検知の前と後で対照的です（出典1・2）。

  • 2026年9月9日（米国時間） 不正取得された認証情報で社内システムへ侵入
  • 10月7日 認識。同日中に影響を受けた認証情報の無効化を開始
  • 10月10日 追加の認証情報を削除。クラウドプロジェクト間の過剰な権限を削除。影響を受けたプロジェクトでクラウドストレージのアクセスログを追加で有効化
  • 10月12〜13日 外部機関が4件の脆弱性を報告
  • 10月14日 4件を修正し、外部機関が再検証。特定された流出認証情報はすべて無効化、不正アクセス経路も遮断
  • 10月19日 Trust Hub でセキュリティ更新を公開（認識から12日）
  • 10月21日13時05分 日本語の報告に追記（問い合わせ情報を対象に追加）

侵入から検知まで28日、検知から遮断完了まで7日です（本記録の算出）。

28日の側に出ている論点は2つあります（本記録の評価）。第一に、10月10日に「クラウドストレージのアクセスログを追加で有効化」しているため、侵害当時は記録が無い領域がありました（出典2）。第二に、継続中の作業として「異常アクセスや大量エクスポートの通知強化」が挙げられています（出典2）——データの複製が28日間続いても通知が上がらない状態だったということです。

鍵を入れ替えるのは、侵害された側ではなく使っている側である対策・注意喚起出典 [1] [2]

公表が顧客に求めている作業は4つです（出典1）。

  1. TiDB Cloud と関連クラウドアカウントのアクセスログを確認する（不審な IP アドレス・身に覚えのない操作）
  2. 組織メンバーとロールを見直し、不要なアカウントを削除する
  3. TiDB Cloud で発行した API キーをローテーションする
  4. PingCAP を装う不審なメールに注意する（同社がパスワードやアクセスキーをメールで尋ねることはない）

3番目が実務の核です（本記録の判断）。日本語の報告は「Public Key 部分のみが流出し、Private Key 部分は流出していないため、Public Key だけでは TiDB Cloud を操作できない」としています（出典1）。それでもローテーションを依頼しているのは、「他に使用可能な認証情報が流出したかは未確認」という状態だからです（出典2）。

本記録の補足として、交換対象は API キーだけではありません（本記録の判断）。漏えい対象に問い合わせ情報（サポートチケット）が含まれるため、過去にサポートへ貼り付けた接続文字列・一時パスワード・デバッグ用の認証情報も交換の対象になります。

自社で確認すべきことは1つです—— API キーを無停止で差し替えられるか。 設定ファイルに直書きしている構成では、ベンダーから依頼が来ても即日では動けません（本記録の判断）。

どちらかが誤りだと断定する材料はありません（本記録の明示）。Public Key 部分という説明と「暗号化された値を含むテーブル」という説明は、同じ実装を別の粒度で述べている可能性があります。

実務上の結論は変わりません（本記録の判断）。どちらを読んでも、やることは API キーのローテーションです。 ただし、海外ベンダーの侵害を日本語の案内だけで判断すると、ソースコードの持ち出しのような論点を見落とします（本記録の評価）。

  • サービスアカウントの権限は、プロジェクトをまたがせない
    **同社は対応として「クラウドプロジェクト間の過剰な権限を削除」 「アカウント権限とネットワーク管理の見直し」を挙げている**（出典1・2）。 **1つの認証情報から到達できる範囲が、影響範囲を決めている**（本記録の評価）。
    取るべき行動 **自社のクラウドでも、サービスアカウントの権限を プロジェクト・環境（本番/検証）ごとに分割し、 横断する権限を棚卸しして期限を切る。**
  • オブジェクトストレージのアクセスログを既定で有効にする
    **同社は侵害後の2026年10月10日に 「影響を受けたプロジェクトでクラウドストレージのアクセスログを 追加で有効化した」としている**（出典2） ——**侵害当時は記録が無い領域があった**（本記録の評価）。
    取るべき行動 **全プロジェクトのオブジェクトストレージでアクセスログを既定有効にし、 保持期間を90日以上にする。 有効化されていないバケットを検出するポリシーを置く。**
  • 大量エクスポートの検知を、侵入検知より優先して置く
    **28日間にわたってデータの複製が行われたが検知されていない** （出典1・2。本記録の算出）。 **同社も継続中の作業として大量エクスポートの通知強化を挙げている**（出典2）。
    取るべき行動 **顧客メタデータ・課金情報・認証情報を持つストアについて、 取得件数と転送量の基準を決め、閾値超過を即時通知にする。**
