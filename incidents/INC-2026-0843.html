INC-2026-0843Alpine Linux が GitLab を再構築

Alpine Linux が2026年10月28日、自前の GitLab（gitlab.alpinelinux.org）に対して **CVSS 10.0 の CVE-2026-97229 の悪用が試みられた**と公表した—— **修正版の公開から1週間後**、新規登録アカウントが細工した CI 設定を投げ、 **GitLab のワーカーを8回クラッシュさせ、うち4回は悪用の途中まで到達**していた。 **10月13日に修正版 19.3.5 ではなく 19.3.4 を誤って入れ**、 10月22日の 19.3.6 への更新も**修正が GitLab のコードではなく 同社が自社パッケージにのみ適用する Ruby へのパッチだったため効かなかった**。 **コード実行の証拠は見つからなかったが、必要なログが既に失われており否定できない**ため、 **侵害されたものとして扱い GitLab をゼロから作り直した**

「製品のバージョンを上げた」が、脆弱性の修正を適用したことにならない事例です。

2026年10月28日、Alpine Linux は自前の GitLab（gitlab.alpinelinux.org）に対してCVE-2026-97229（CVSS 10.0）の悪用が試みられたことを公表しました（出典1）。10月30日には復旧後の利用者向け手順を別記事として公表しています（出典2）。

攻撃の経緯（出典1。すべて同プロジェクトの公表内容）。

  • 10月20日、新規登録されたアカウントがアカウントを作って探りを始めた。
  • 10月20日〜21日、細工した CI 設定を投げ、GitLab のワーカープロセスを8回クラッシュさせた。そのうち4回は、攻撃者が悪用の途中まで到達し、次の段階で失敗している。10月21日が主たる攻撃で、クラッシュ・502 エラー・CI ジョブの失敗として表に出た。
  • 攻撃者は Alpine の GitLab コンテナイメージもダウンロードしており、自分たちの正確なビルドに合わせて攻撃を調整していたことを示唆するとされています。
  • 10月23日、攻撃者のアカウントをブロック。10月25日〜26日に攻撃者が戻って再試行したが失敗。

脆弱な状態が続いた理由（出典1）。

  • 10月12日、GitLab が修正版を公開。 しかし10月13日、Alpine は修正の入った 19.3.5 ではなく誤って 19.3.4 を入れた（原文英語: "by mistake"）。
  • 10月22日に 19.3.6 へ上げたが、これでも直らなかった。 「修正は GitLab 自身のコードではなく、GitLab が自社の公式パッケージにのみ適用するRuby へのパッチである。我々のイメージは標準の Ruby を使っていたため、パッチを受け取らなかった」（原文英語）。
  • 10月26日、更新後もまだ脆弱であることを発見。
  • 上流の Ruby が修正を出したのは10月23日（Ruby 3.3.13・3.4.12・4.0.9）。

判断と対応（出典1・2）。

  • 10月27日、開発者とビルドサーバを除く全員に対して GitLab を閉鎖し、再構築を開始。
  • 10月28日、再構築が完了。全パスワードをリセットし、GitLab の秘密鍵を交換。
  • 10月29日、19.3.7 に上げて再開。10月30日に利用者向けの手順を公表。
  • 判断の理由は明示されています—— 「コード実行を否定できず、それを確認するために必要な証拠はもう存在しないため、我々は困難な道を選び、GitLab インスタンスをゼロから作り直した」（原文英語）。

本記録が要点と見たのは、次の4点です。

  • 「バージョンを上げた」が修正の適用を意味しなかった。 修正の実体は Ruby へのパッチで、GitLab は自社の公式パッケージとコンテナイメージにのみそれを適用していました（出典1）。自前のイメージ・ソースからの構築で GitLab を運用している組織は、GitLab を最新版にしても直っていません。 Alpine は「GitLab を自分の Ruby で動かしている場合、GitLab を上げるだけでは足りない。Ruby 3.3.13・3.4.12・4.0.9 以降も必要だ」と明記しています（出典1）。これは本件で最も再現性の高い学びです（本記録の評価）。
  • 「否定できない」を理由に、否定できる形へ作り直した。 改ざんの痕跡は見つかっていません（aports・パッケージ・10月21日のリリースはいずれもGitLab の外の記録と突き合わせて検証済み）。署名鍵も GitLab サーバには一度も置いていない。 それでも「成功した悪用はクラッシュも Web ログの痕跡も残さない」「攻撃当日のログの一部が既に失われている」「外向き通信の記録を取っておらず、ホスティング事業者も保持していない」という3点を理由に、侵害されたものとして扱いました（出典1）。本記録はこの判断を、本DBに収めた事案のなかで最も明晰なものと評価します（本記録の評価）。
  • 「もし成功していたら何が露出したか」を列挙して公表した。利用者全員のメールアドレス・氏名・IPアドレス、パスワードハッシュ、2FA の秘密・CI/CD 変数・Runner トークン、Webhook・連携・プッシュミラーの認証情報、パーソナルアクセストークン（ハッシュ）、非公開リポジトリと非公開の課題・マージリクエスト（出典1）。確認されたわけではない情報を「もしも」の形で先に出しておくことで、利用者が自分で判断して動けるようになっています（本記録の評価）。
  • 攻撃者は防御側のビルドをダウンロードして攻撃を合わせてきた。 公開されているコンテナイメージの取得自体は正常な行為であり、それ単体では不審に見えません（本記録の評価）。自分が公開している成果物が、自分への攻撃の調整材料になるという構造は、OSS プロジェクトに限らず、公開イメージや公開ビルドを持つすべての組織に当てはまります。

    **公表に外部の調査機関・セキュリティ企業の関与についての記述は無い**（出典1）。 **10月30日の記事に「インシデントの調査とサーバの再構築を手伝ってくれた すべての人に感謝する」という謝辞があるのみで、 それがプロジェクト内のボランティアか外部の専門家かは区別できない**（出典2）。 **結果として、「コード実行の証拠は無い」という認定の客観性を 外部から検証する材料は無い**（本記録の評価）。 **ただし Alpine は寄付とボランティアで運営されるプロジェクトであり、 外部調査の費用を前提にできる体制ではないことに留意が必要である**（本記録の留保）。
  • CI 実行系とリポジトリ・認証情報の保持系の分離について公表されていない

    **Alpine は「コード実行の証拠は見つからなかったが、否定することはできない」と 明記している**（出典1）。 **否定できない理由として3点が挙げられている**—— **①成功した悪用は、クラッシュも Web ログの痕跡も残さない。 ②攻撃当日のログの一部が既に失われている （バックグラウンドジョブのログ、旧コンテナのファイルシステム）。 ③外向きのネットワーク接続の記録を取っておらず、 ホスティング事業者も保持していない。** **これは「調べていない」ではなく「確認に必要な証拠が存在しない」状態である**（本記録の整理）。 **本記録は、この項目が今後も確定しないと判断している**—— **失われたログは戻らない。**

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

以下は Alpine Linux の公表2本に書かれた事実関係を段階ごとに並べたものである。 **本件は悪用の試みであり、成功は確認されていない**（出典1）。 **攻撃の各段階は具体的に公表されている**—— 新規アカウントの登録と探り、公開コンテナイメージの取得による攻撃の調整、 細工した CI 設定の投入、8回のワーカークラッシュ（うち4回は途中まで到達）、 アカウントのブロック後の再試行。 **一方、コード実行・持ち出しの段階は「否定できない」という形でしか書けていない**—— **成功した悪用は痕跡を残さず、必要なログが既に失われていたためである**（出典1）。

    根拠: Alpine Linux の公表「What we found」および「Why we can't be sure」
  4. 4. 認証情報アクセスdisclosed[1]
    **もし悪用が成功していた場合に露出しえた情報として、 Alpine は次を列挙している**（出典1）—— **全利用者のメールアドレス・氏名・IPアドレス、パスワードハッシュ、 2FA の秘密・CI/CD 変数・Runner トークン、 Webhook・連携・プッシュミラーの認証情報、 パーソナルアクセストークン（ハッシュとして保存）、 非公開リポジトリおよび非公開の課題とマージリクエスト。** **いずれについても露出は確認されていない。** **一方、Alpine のパッケージとリリースに署名する鍵は、 GitLab サーバに置かれていないし、これまで一度も置かれたことがない。**
    根拠: Alpine Linux の公表「What could have been exposed if the attack succeeded」
  5. 5. 永続化disclosed[1]
    **2026年10月23日に攻撃者のアカウントがブロックされた後、 10月25日〜26日に攻撃者が戻って再び侵入を試みたが失敗した**（出典1）。 **この時点で Alpine のインスタンスはまだ脆弱であった** ——**19.3.6 への更新後もまだ脆弱であることが分かったのは10月26日である**（本記録の整理）。 **また、想定外のファイル・鍵・フック・プロセスは見つかっておらず、 足場が残された証拠は無い。**
    根拠: Alpine Linux の公表タイムラインおよび「What we found」

    トレードオフ: **再構築は、足場が残っている可能性を一括して消せる唯一の手段である。** **「調べて見つからなかった」で済ませる場合、 見つからなかったのは無いからなのか、見る手段が無いからなのかを区別できない** ——**本件はまさに後者の状態にあった**（本記録の評価）。 **代償は大きい。** 2日間の閉鎖、全パスワード・2FA・トークンのリセット、 **CI/CD 変数の値の全損**、連携設定の再入力、SSH ホスト鍵の変更による 全利用者への警告、そして再構築に要した人手である（出典1・2）。 **プロジェクトの貢献者全員に作業を発生させる判断でもある。**

    トレードオフ: **交換しなければ、露出していた場合に攻撃者が後から使える。** **交換すれば、全利用者と全プロジェクト管理者に再設定作業が発生する。** **本件は「失効させるもの」と「保持するもの」を区別している**（本記録の整理）—— **SSH 鍵と GPG 鍵は利用者が持つ公開鍵であり、 サーバ側の秘密が漏れても危険にならないため保持できる。** **逆に CI/CD 変数の値は、サーバ側に平文相当で保持される秘密なので捨てるしかない。**
  • **「見つかったこと」「確信が持てない理由」「もし成功していたら露出しえた情報」を 分けて公表した。** **あわせて、日付ごとのインシデントタイムライン、FAQ、再発防止策4点を掲載した。** **外向き通信の記録を取っていなかったこと、 攻撃当日のログの一部が失われていたことも明記した**（出典1）。
    理由は公表されていない
    トレードオフ: **自分たちの運用の欠落（ログの不足・バージョンの取り違え）を書くことは、 プロジェクトの信頼を一時的に損なう。** **一方、書かなければ利用者は「確認されていない」の確度を判断できず、 自分のアクセストークンや CI/CD 変数を差し替えるべきかも決められない**（本記録の評価）。 **「もし成功していたら」の列挙は、不要な不安を与える可能性と、 利用者が自分で判断できるようになる利益を引き換えにしている。**
  • **2026年10月28日（再構築完了と同日）に経緯と調査結果を公表し、 10月30日（再開の翌日）に利用者向けの再設定手順を別記事として公表した。** **10月28日の記事には後から「10月30日更新」として再開の告知が追記された**（出典1・2）。
    理由は公表されていない
    トレードオフ: **10月21日の障害（502 エラー・CI ジョブの失敗）は利用者から見えていたため、 公表までの7日間は「GitLab が不調」という状態が説明されないまま続いたことになる** （本記録の評価。Alpine はこの点に触れていない）。 **一方、調査結果と対応をまとめて出すことで、 利用者は「何を再設定すべきか」を1度に受け取れる。** **2本に分けたことで、インシデントの説明と作業手順が混ざらずに読める**（本記録の評価）。

「GitLab を上げた」が修正の適用にならなかった——修正は製品の外の Ruby にあった原因・手口出典 [1]

本件の技術的な中核は、修正がどこにあったかである。

Alpine の公表は次のように述べている（出典1。原文英語・訳は本記録）。

CVE-2026-97229 は、GitLab が CI 設定の正規表現を評価する方法にある重大な（CVSS 10.0）脆弱性である。根本のバグは、Ruby に組み込まれた正規表現エンジン Onigmo にある。 GitLab は10月12日に修正版をリリースしたが、修正そのものは、GitLab が自社のパッケージとコンテナイメージに同梱している Ruby へのパッチの集合である。 上流の Ruby が修正を出荷したのは10月23日で、Ruby 3.3.13・3.4.12・4.0.9 に含まれる。

19.3.6 への更新（10月22日）では脆弱性は直らなかった。修正は GitLab 自身のコードではなく Ruby へのパッチにあり、GitLab はそれを自社の公式パッケージにのみ適用している。我々のイメージは標準の Ruby を使っていたため、パッチを受け取らなかった。

GitLab を（ソースから、あるいは自分のコンテナイメージで）自前の Ruby で動かしている場合、GitLab を上げるだけでは足りない。Ruby 3.3.13・3.4.12・4.0.9 以降も必要である。

ここから読み取れることを整理する（本記録の整理）。

  • 「製品のバージョンを上げた」という行為が、脆弱性の修正を適用したことを意味しない場合がある。 脆弱性は製品にあるのではなく、製品が同梱している言語処理系にあった。製品ベンダーは自社のパッケージ経路でそれを塞いだが、その経路を使っていない運用者には届かない。
  • 時間差も効いている。 GitLab の修正版は10月12日、上流 Ruby の修正は10月23日である。その間の11日間、自前の Ruby で GitLab を動かしていた運用者には、適用できる上流の修正が存在しなかった—— GitLab の公式パッケージ・公式イメージに乗り換えるか、GitLab のパッチを自分で Ruby に当てるかしかなかったことになる（本記録の評価）。
  • 「19.3.4 を誤って入れた」の方は、人のミスである。 Alpine は 2026年10月13日に、修正の入った 19.3.5 ではなく 19.3.4 を入れたと自ら明記している（原文英語: "by mistake"）。1つ違いのバージョン番号は取り違えやすい。 なお本DBの INC-2026-0476 は、CVE-2026-97229 の修正版について報道と2つの政府系 CERT が「19.3.4」と記載し GitLab 自身の記載（19.3.5）と食い違っていたことを記録している。 Alpine はその食い違いを取り違えの理由として挙げていないため、本記録は両者を結び付けない〈差異1〉。

影響はコンテナイメージの利用者にも及んでいる（出典1）。alpinelinux/gitlab イメージを使っている場合は、alpinelinux/gitlab:19.3.6 を改めて取得する必要がある——10月27日に公開されたイメージが Ruby 3.3.13 を含み、CVE-2026-97229 に対処している。10月27日より前に取得した 19.3.6 イメージ、および古いすべてのタグは脆弱である。

攻撃は8回のクラッシュとして表に出た——うち4回は悪用の途中まで到達していた発覚の端緒出典 [1]

本件が検知された経路は、可視的な障害である（本記録の整理）。

Alpine の公表によれば（出典1。原文英語・訳は本記録）、

10月20日と21日、新規登録されたアカウントが細工した CI 設定を我々の GitLab インスタンスへ送った。インスタンスはまだ 19.3.4 を実行しており、10月12日の修正を持っていなかった。これにより GitLab のワーカープロセスが8回クラッシュした。そのうち4回のクラッシュでは、攻撃者は悪用の途中まで進み、次の段階で失敗した。 攻撃者は我々の GitLab コンテナイメージもダウンロードしており、我々の正確なビルドに合わせて攻撃を調整していたことを示唆する。攻撃者がサーバ上でコードを実行した証拠は見つかっていないが、否定することはできない。

公表されたタイムラインでは、10月21日が「主たる攻撃」とされ、「GitLab のクラッシュ・502 エラー・CI ジョブの失敗」が併記されている（出典1）。

ここに2つの含意がある（本記録の評価）。

  • 攻撃が失敗したからこそ気づけた。 8回のクラッシュと502エラーと CI の失敗は、利用者から見れば「GitLab が不調」である。 攻撃者が悪用に成功していれば、これらは発生しなかった—— Alpine 自身が「成功した悪用はクラッシュも Web ログの痕跡も残さない」と明記している（出典1）。つまり本件の検知は、攻撃の不出来に依存している。
  • 攻撃者は防御側の正確なビルドを手に入れて調整していた。 Alpine が公開している GitLab コンテナイメージのダウンロードは、それ自体まったく正常な行為である（本記録の評価）。公開イメージ・公開ビルドを持つ組織は、自分の成果物が自分への攻撃の調整材料になるという構造を抱えている—— これは OSS プロジェクトに限らない。

検知の端緒が「誰が最初に気づいたか」という形では公表されていない（本記録の確認）〈未確定4〉。502 エラーと CI の失敗が利用者から報告されたのか、自分たちの監視で気づいたのかは示されていない。

「否定できない」を理由に、否定できる形へ作り直した組織の対応出典 [1] [2]

Alpine が公表した判断の理由は、本DBに収めた事案のなかで最も明晰である（本記録の評価）。

公表の FAQ は次のとおりである（出典1。原文英語・訳は本記録）。

攻撃を緩和できたのに、なぜ GitLab を再構築したのか。 コード実行を否定できず、それを確認するために必要な証拠はもう存在しないため、我々は困難な道を選び、GitLab インスタンスをゼロから作り直した。これにより、成功しえた悪用が残したかもしれない足場を取り除く。

判断を支える3つの事実が、分けて示されている（出典1）。

（A）見つかったこと

  • Alpine のリリースとパッケージは改変されていない。 10月21日の安定版リリース（3.21.9・3.22.7・3.23.7・3.24.3。ISO イメージと公式 alpine Docker イメージのもとになる minirootfs tarball を含む）、および10月20日から24日に構築された全パッケージは、GitLab の外の記録と突き合わせて検証した aports のコミットから来ている。
  • 署名鍵は露出していない。 Alpine のパッケージとリリースに署名する鍵は、GitLab サーバに置かれていないし、これまで一度も置かれたことがない。
  • 攻撃者のコードが動いた証拠は無い。 タイミングの探査では遅延が見られず、想定外のファイル・鍵・フック・プロセスも見つからなかった。
  • Web や API のリクエストを通じて非公開データが攻撃者へ返された形跡は、我々が見られる範囲では無い。

（B）確信が持てない理由

  • 成功した悪用は、クラッシュも Web ログの痕跡も残さない。
  • 攻撃当日のログの一部が既に失われている（バックグラウンドジョブのログ、旧コンテナのファイルシステム）。
  • 外向きのネットワーク接続の記録を取っておらず、ホスティング事業者も保持していない。

（C）もし成功していたら露出しえた情報

  • 全利用者のメールアドレス・氏名・IPアドレス
  • パスワードハッシュ
  • 2FA の秘密・CI/CD 変数・Runner トークン
  • Webhook・連携・プッシュミラーの認証情報
  • パーソナルアクセストークン（ハッシュとして保存）
  • 非公開リポジトリ、および非公開の課題とマージリクエスト

本記録がこの構成を評価する理由は3点ある（本記録の評価）。

  • 「何を調べて、何が分かったか」と「調べられなかった理由」を分けている。 「痕跡なし」で終わる公表は、調べた範囲を示さないため読者が確度を判断できない。 本件は「成功した悪用なら痕跡が残らない」という調査手法の限界そのものを書いている。
  • ログが無いことを隠していない。 外向き通信の記録を取っていなかったこと、ホスティング事業者も保持していないことを明記し、それを再発防止策（外向き接続とデータベース接続の記録・保持期間の延長）に直結させている。
  • 確認されていない情報の露出可能性を、先に列挙している。 「確認されていないので何も言わない」のではなく、「もし成功していたらこれが出た」という形で利用者に判断材料を渡している—— 結果として、利用者は CI/CD 変数の値を新しい認証情報に差し替えるという具体的な行動を取れる（出典2）。

なお、外部の調査機関を入れたかどうかは公表されていない（本記録の確認）〈未確定5〉。謝辞として「インシデントの調査とサーバの再構築を手伝ってくれたすべての人に感謝する」と述べられているのみである（出典2）。

改ざんの検証は「GitLab の外の記録」と突き合わせて行われた被害規模・影響範囲出典 [1]

本件で最も再現可能な手続きは、改ざんの有無を侵害された系の外側から検証した方法である（本記録の評価）。

Alpine の公表は次のとおりである（出典1。原文英語・訳は本記録）。

10月20日から22日に追加された aports の全コミットは、既知の開発者による記録されたプッシュを経て届いている。 我々はこれを、攻撃者が到達できない記録と突き合わせて確認した——ある開発者のクローンと、45台すべてのビルダである。 10月20日から24日に全アーキテクチャで構築された全パッケージは、git.alpinelinux.org に公開されたとおりのコミットから来ている。 10月21日のリリース（3.21.9・3.22.7・3.23.7・3.24.3）は、それと同じ検証済みのコミットから構築された。我々はこれらの検査を10月24日に実施し、10月20日から22日のコミットと10月24日までに構築されたパッケージを対象とした。我々の GitLab は10月27日に閉じるまで脆弱なままだったので、同じ検査をその日まで拡張している。

この手続きの性質を整理する（本記録の整理）。

  • 検証の基準を、侵害された可能性のある系の外側に置いている。 GitLab 上の記録だけで「改ざんされていない」と言っても、その記録自体が書き換えられた可能性を排除できない。 開発者の手元のクローンと、45台のビルダがそれぞれ持つ記録は、攻撃者が GitLab を取ったとしても到達できない。
  • 検証の対象期間と、検証を行った日を分けて書いている。 10月24日に検査し、対象はコミットが10月22日まで、パッケージが10月24日まで。その後も脆弱だった10月27日までへ検査を拡張している。 「いつまでを検証したか」が明示されているため、読者は残った不確かさの範囲を判断できる。
  • 署名鍵が系の外にあったことが、独立した安心の根拠になっている。 「Alpine のパッケージとリリースに署名する鍵は、GitLab サーバに置かれていないし、これまで一度も置かれたことがない」（出典1）。これは本件の対応ではなく、事前の設計判断である（本記録の評価）。

再発防止策のひとつに「署名付きリリースタグ——GitLab から独立してリリースを検証できるようにする」が挙げられている（出典1）。本件の検証は人手で記録を突き合わせる形だったが、それを仕組みに移す方向である（本記録の整理）。

再開時に何を捨てたか——秘密鍵を交換したことの波及復旧の経過出典 [1] [2]

10月28日に再構築が完了し、全パスワードがリセットされ、GitLab の秘密鍵が交換された（出典1）。10月30日の記事は、その結果として利用者側で何が効かなくなるかを列挙している（出典2）。

全員が行うこと

  • 新しいパスワードの設定。 全パスワードがリセットされたため、サインインページの「Forgot your password?」から設定する。GitHub・GitLab.com・postmarketOS でのサインインは引き続き使える。
  • 2FA の再設定。 認証アプリ・セキュリティキーの双方がリセットされ、古いリカバリコードは無効。 認証アプリから古い gitlab.alpinelinux.org の項目を削除する。
  • 新しい SSH ホスト鍵の受け入れ。 サーバの SSH ホスト鍵が新しくなったため、初回の git pull/push で警告が出る。 ssh-keygen -R gitlab.alpinelinux.org で古い鍵を削除し、公表された3種の SHA256 指紋（ED25519・ECDSA・RSA）と照合する。利用者側の SSH 鍵と GPG 鍵は保持されており、再登録は不要。
  • パーソナルアクセストークンの再作成。 以前作成したものは無効。
  • フィード URL とメールアドレスの更新。 RSS・カレンダーフィードの URL に含まれるトークン、課題作成やメール返信に使う非公開メールアドレスがリセットされた。

プロジェクト管理者が行うこと

  • CI/CD 変数の値の再入力。 値はすべて失われている（変数自体は名前と設定とともに残っているが値は空）。パイプラインスケジュールの変数も同様。「古い値は露出した可能性があるものとして扱うこと。可能な場合は、古いものではなく新しい認証情報を使うこと」と明記されている。
  • 連携・Webhook・ミラーの確認。 連携設定は動作しなくなっているためトークンとパスワードを再入力する。Webhook とプッシュミラーは新サーバへ移されて動作するが、秘密トークンとパスワードが露出した可能性があるため新しいものに差し替える。OAuth アプリケーションを持っている場合はその秘密も更新する。

運用の変更

  • メールアドレスとパスワードで新規登録したアカウントは、使用開始前に管理者の承認が必要になった（出典2）。本件の攻撃者は10月20日に新規登録したアカウントから攻撃を始めている（出典1）ため、これは攻撃の前提条件そのものへの対処である（本記録の整理）。
  • 他サイトから漏えいしたパスワードを用いた自動ログイン試行を観測しているとして、同じパスワードを他で使っている場合はそちらも変更するよう呼びかけている（出典1・2）。

ここに現れているのは、「秘密鍵を交換する」という1つの決定が利用者側の再設定作業へ広く波及するという構造である（本記録の評価）。Alpine はその波及をすべて列挙し、何が保持され何が失われたかを区別して示した。 再構築を選べるかどうかは、この一覧を事前に書けるかどうかに依存する（本記録の評価）。

Alpine が公表した再発防止策は次の4つである（出典1。原文英語・訳は本記録）。

この出来事に対して我々が変えること
- 修正済みの Ruby：再構築したインスタンスは修正の入った Ruby（3.3.13 以降）で動く。
- より速いパッチ適用：GitLab の重大なセキュリティリリースを1日以内に適用し、各リリースについて、我々自身のビルドが適用しなければならないRuby やその他のコンポーネントのパッチが含まれていないかを確認する。
- より良いログ：GitLab ホストからの外向き接続とデータベース接続を記録し、ログを14日より長く保持する。
- 署名付きリリースタグ：GitLab から独立してリリースを検証できるようにする。

4つはいずれも、本件で機能しなかった点に1対1で対応している（本記録の整理）。

経過

2026年10月12日注意喚起**GitLab が CVE-2026-97229 の修正版をリリースした**（出典1）。 **修正の実体は、GitLab が自社のパッケージに同梱する Ruby へのパッチの集合である** （原文英語: "the fix itself is a set of patches to the Ruby that GitLab bundles in its own packages and container images"）。 **GitLab は、特定の条件下で細工した正規表現を CI/CD パイプライン設定に投入することで 攻撃者が本脆弱性を発火させうると警告した**（出典3）。

CISO・経営層への示唆
  • **「最新版に上げた」を是正の完了として報告させない。 修正がどこにあるかを確認させる**
    本件では、**GitLab を 19.3.6 へ上げても脆弱性は閉じなかった**（出典1）。 **修正の実体は GitLab のコードではなく、 GitLab が自社の公式パッケージとコンテナイメージにのみ適用する Ruby へのパッチだったためである。** **自前のイメージやソースからの構築で運用していた Alpine は、 「上げた」のに4日間無防備だった**（本記録の算出）。 **脆弱性管理の報告が「対象製品のバージョン」で完結する運用では、 この種の見落としは報告上「完了」として通る**（本記録の評価）。
    取るべき行動 脆弱性対応の完了基準を**「版を上げた」から「該当の脆弱性が閉じたことを確認した」に変える。** **緊急度の高い CVE については、是正報告に ①適用した版、②修正の実体がどこにあるか（製品のコードか、同梱コンポーネントか）、 ③自組織の配布経路でそれが適用されるか、④閉じたことをどう確認したか**の4項目を書かせる。 **とくに「自前でビルドしている」「公式パッケージを使っていない」構成を 資産台帳で識別し、別扱いにする。**
  • **「侵害を否定できるか」は、事後の調査能力ではなく事前のログ設計で決まる**
    本件で Alpine が再構築を選んだ理由は**「コード実行を否定できず、 それを確認するために必要な証拠はもう存在しない」**ことである（出典1）。 **欠けていたのは3点**—— **①成功した悪用は痕跡を残さない（原理的な制約）、 ②攻撃当日のログの一部が既に失われていた（保持期間14日）、 ③外向きのネットワーク接続の記録を取っておらず、ホスティング事業者も保持していない。** **②③は事前の設計で用意できた記録である**（本記録の評価）。
    取るべき行動 重要な系について、**「侵害が否定できない」と判断するコストを試算しておく**—— **再構築に要する停止時間・認証情報の全差し替え・利用者への波及作業。** **そのコストと、それを避けるために必要なログ（外向き通信・データベース接続・ バックグラウンドジョブ・保持期間）の費用を並べて比較する。** **本件はログの不足が「2日間の停止＋全利用者の再設定」という形で請求された事例である。**
  • **署名鍵・リリース鍵を、侵害されうる系の外に置く。これは事後にはできない**
    本件で最も効いたのは**「Alpine のパッケージとリリースに署名する鍵は、 GitLab サーバに置かれていないし、これまで一度も置かれたことがない」**という 事前の設計である（出典1）。 **GitLab が侵害されたものとして扱われても、 配布物の署名の信頼は損なわれなかった。** **逆に、署名鍵が同じ系にあれば、再構築しても 「過去に配ったものが本物か」は答えられない**（本記録の評価）。
    取るべき行動 **自組織の署名鍵・リリース鍵・コード署名証明書の秘密鍵がどこにあるかを確認する。** **アプリケーションサーバ・CI の環境変数・リポジトリの秘密に置かれているものは、 オフラインまたは HSM・専用の署名サービスへ移す。** **移せない場合は、「その系が侵害されたら配布物の信頼が失われる」ことを リスクとして明示的に記録する**（移さない判断自体は経営の選択でよい）。
  • **「確認されていない」と「起きていない」を公表文で混ぜない。 もし起きていたら何が出たかを先に列挙する**
    本件の公表は**「見つかったこと」「確信が持てない理由」 「もし成功していたら露出しえた情報」を分けて書いている**（出典1）。 **結果として、利用者は CI/CD 変数の値を新しい認証情報に差し替えるという 具体的な行動を取れた**（出典2）。 **「確認されていません」で止める公表は、 読者に「では何もしなくてよいのか」を判断させない**（本記録の評価）。
    取るべき行動 自組織の侵害公表の雛形に**「もし成功していた場合に影響しえた情報」の欄を作る。** **書く内容は、①その系が保持している情報の種類、 ②それが露出した場合に読者が取るべき行動**の2つでよい。 **「確認されていない」と書くときは、同じ段落に 「確認の方法」と「その方法で確認できない範囲」を添える** ——本件の「成功した悪用はクラッシュも Web ログの痕跡も残さない」がその例である。
  • **自分が公開している成果物が、自分への攻撃の調整材料になることを前提に置く**
    本件の攻撃者は**Alpine の GitLab コンテナイメージをダウンロードしており、 Alpine の正確なビルドに合わせて攻撃を調整していたことを示唆するとされている**（出典1）。 **公開イメージの取得はまったく正常な行為であり、検知の手がかりにはならない**（本記録の評価）。 **この構造は OSS プロジェクトに限らない**—— **公開している Docker イメージ・SDK・オンプレ版の配布物・ 求人票に書いた技術スタックはいずれも同じ役割を果たす。**
    取るべき行動 **自組織が外部から確認できる構成情報を棚卸しする** （公開コンテナイメージ・公開リポジトリ・配布するオンプレ版・ 技術ブログ・求人票・バナー情報）。 **本番で稼働する構成を、公開している構成と一致させない** （版・パス・設定の差分を作る）。 **公開物に本番の構成がそのまま現れる場合は、 その系の脆弱性対応を他より速い基準で運用する。**
セキュリティ技術者への示唆
  • **同梱コンポーネント（言語処理系・ライブラリ）にある脆弱性は、 製品を上げても直らないことがある**
    CVE-2026-97229 の**根本のバグは Ruby に組み込まれた正規表現エンジン Onigmo にあり、 GitLab の修正は「GitLab が自社のパッケージとコンテナイメージに同梱している Ruby へのパッチの集合」だった**（出典1）。 **Alpine の自前イメージは標準の Ruby を使っていたため、 GitLab を 19.3.6 に上げてもパッチを受け取らなかった。** **上流 Ruby が修正を出したのは GitLab の11日後（10月23日）である。**
    取るべき行動 **自前でビルド・コンテナ化している製品について、 「製品のソース」と「同梱コンポーネント」のどちらがベンダーのパッチの対象かを、 セキュリティリリースごとに読む。** **ベンダーのリリースノートが『当社のパッケージでは修正済み』と書いている場合は、 自分のビルドに同じパッチが入るかを確認する。** **本件の Alpine の再発防止策がまさにこれである**—— **「各リリースについて、我々自身のビルドが適用しなければならない Ruby やその他のコンポーネントのパッチが含まれていないかを確認する」。** **確認が難しい製品は、ベンダーの公式パッケージ・公式イメージへ寄せることを検討する。**
  • **パッチ適用の後に、脆弱性が実際に閉じたことを検証する手順を持つ**
    本件では**10月22日に 19.3.6 へ上げてから10月26日まで4日間、 「対処済み」という認識のまま脆弱であった**（出典1。本記録の算出）。 **その間の10月25日〜26日に攻撃者が戻って再試行している。** **版番号の確認だけでは、本件のように修正が別のコンポーネントにある場合に 誤った安心が残る**（本記録の評価）。
    取るべき行動 重大な CVE については、**適用後に「閉じたこと」を確認する手順を1つ用意する**—— **①同梱コンポーネントの版を実際に問い合わせる** （本件なら稼働中のコンテナで `ruby -v` を確認し 3.3.13 以降かを見る）、 **②ベンダーが示す検出方法・検証スクリプトがあれば実行する、 ③検証環境で概念実証を試す（可能な場合）。** **「適用した」と「閉じた」を別のチェック項目として記録に残す。**
  • **外向き通信の記録を取る。これが無いと「持ち出されたか」に答えられない**
    本件で Alpine が侵害を否定できなかった理由のひとつは **「外向きのネットワーク接続の記録を取っておらず、 ホスティング事業者も保持していない」**ことである（出典1）。 **「Web や API のリクエストを通じて非公開データが返された形跡は無い」ことは 確認できたが、悪用に成功した場合はそれらの経路を通らない**（本記録の整理）。 **再発防止策には「GitLab ホストからの外向き接続とデータベース接続を記録し、 ログを14日より長く保持する」が挙げられている。**
    取るべき行動 重要なアプリケーションホストについて、**外向き接続を既定で拒否し、 許可した宛先への接続のみを記録付きで通す。** **データベースへの接続と大量の読み出しも記録する。** **ログは本体とは別の保存先へ転送する** ——**本件では旧コンテナのファイルシステムとともにバックグラウンドジョブのログが失われている。** **保持期間は「侵害に気づくまでの想定日数」から逆算する**（14日では足りないことが本件で示された）。
  • **配布物の改ざんは、侵害された系の外側の記録と突き合わせて検証する**
    Alpine は**10月20日から22日に追加された aports の全コミットを、 「攻撃者が到達できない記録——ある開発者のクローンと、45台すべてのビルダ」と 突き合わせて確認した**（出典1）。 **GitLab 上の記録だけで「改ざんされていない」と言っても、 その記録自体が書き換えられた可能性を排除できない**（本記録の評価）。 **また検証の対象期間（コミットは10月22日まで・パッケージは10月24日まで）と 検証した日（10月24日）を分けて示し、脆弱だった10月27日まで検査を拡張している。**
    取るべき行動 **自組織のビルド成果物について、「ソースの真正性を系の外側から確認する方法」を1つ用意する** ——**開発者の手元のクローン、別の系に置いたミラー、 ビルダ側に残るコミットハッシュの記録のいずれでもよい。** **さらに署名付きのリリースタグを導入し、 リポジトリ基盤から独立してリリースを検証できるようにする** （Alpine の再発防止策のひとつ）。 **検証を行うときは、対象期間と実施日を分けて記録する。**
  • **CI 設定の評価は信頼されていない入力の処理である。 実行系とリポジトリ・認証情報の保持系を分ける**
    本件の攻撃経路は**新規登録アカウントから投入された CI 設定の正規表現の評価**である（出典1）。 **そこから「もし成功していたら露出しえた情報」の一覧は、 利用者全員のメールアドレス・パスワードハッシュ・2FA の秘密・ CI/CD 変数・Runner トークン・非公開リポジトリまで広がっている。** **CI 設定を評価する処理が、これらを保持する系と同じ特権で動いていたことになる** （本記録の評価）。 **なお Alpine の再発防止策には、この分離への言及が無い**〈未確定6〉。
    取るべき行動 **CI 設定の構文解析・正規表現の評価といった「外部からの入力を処理する部分」を、 リポジトリ本体と認証情報を保持する系から分離する** （別プロセス・別コンテナ・最小権限・読み取り専用のファイルシステム）。 **自己登録したアカウントからの CI 設定の投入を、 承認済みのマージリクエスト経由に限る。** **CI/CD 変数・Runner トークンは外部の秘密管理に置き、 アプリケーションのデータベースに値を持たせない。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ GitLab・その他の製品を、ベンダーの公式パッケージ・公式コンテナイメージではなく 自前のビルドや自前のコンテナイメージで運用している**本件の中核はここである**（出典1）。 **CVE-2026-97229 の修正は GitLab が自社パッケージにのみ適用する Ruby へのパッチであり、 自前の Ruby を使う構成では GitLab を上げても直らなかった。** **「最新版にした」が是正にならない構成である**（本記録の評価）。
運用・監視□ 重大な CVE への対応が「対象製品のバージョンを上げた」で完了扱いになっており、 該当の脆弱性が実際に閉じたことを確認する手順が無い本件では**10月22日の更新から10月26日まで4日間、 「対処済み」という認識のまま脆弱だった**（本記録の算出）。 **誤った安心は、無防備よりも検知を遅らせる**（本記録の評価）。
運用・監視□ 重要なアプリケーションホストからの外向きネットワーク接続を記録しておらず、 ホスティング事業者・クラウド事業者側にも記録が無い**本件で「コード実行を否定できない」状態を作った3点のうちの1点である**（出典1）。 **持ち出しの有無に答えられないと、再構築と全認証情報の差し替えしか選択肢が残らない。**
運用・監視□ アプリケーションのログをコンテナやホストの内部にのみ保持しており、 保持期間が「侵害に気づくまでの想定日数」に足りていない本件では**攻撃当日のバックグラウンドジョブのログと旧コンテナのファイルシステムが 既に失われていた**（出典1）。 **事案当時の保持期間は14日で、再発防止策としてこれを延ばすとされている。**
認証・認可□ 開発基盤・課題管理基盤で新規アカウントの自己登録が可能で、 登録直後から CI 設定の投入やパイプラインの実行ができる本件の攻撃者は**10月20日に新規登録したアカウントから攻撃を始めている**（出典1）。 **再開後は管理者承認が必須になっており、攻撃の前提条件そのものへの対処である**（出典2）。
システム構成□ パッケージ・リリースの署名鍵、コード署名証明書の秘密鍵が、 アプリケーションサーバ・CI の環境変数・リポジトリの秘密のいずれかに置かれている**本件で最も効いたのは「署名鍵を GitLab サーバに置かない」という事前の設計である**（出典1）。 **同じ系にあれば、再構築しても「過去に配ったものが本物か」に答えられない**（本記録の評価）。
システム構成□ 自組織が公開しているコンテナイメージ・配布物・技術情報が、 本番で稼働している構成とほぼ一致している本件の攻撃者は**Alpine の GitLab コンテナイメージを取得して 攻撃を正確なビルドに合わせていた**とされる（出典1）。 **公開物の取得は正常な行為であり、検知の手がかりにならない**（本記録の評価）。
