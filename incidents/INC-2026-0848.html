INC-2026-0848Node-REDのCVSS10悪用でOT機器にボット

OT/ICS の現場で広く使われるフロー型プログラミングツール Node-RED の CVSS 10.0 の脆弱性（CVE-2026-58115）が 実際に悪用され始めた——Siemens SIMATIC IoT2050 Advanced では Node-RED の HTTP インターフェースに認証が無く、 未認証の攻撃者が inject ノードと exec ノードをつないだフローを投げるだけで任意のコマンドが走る。 VulnCheck のカナリアは2026年10月30日、単一の POST /flows でエクスプロイトとドロッパーをまとめて送り込み、 別のサーバから Linux 向けボット（bot-linux-amd64）を取得させる攻撃を捕捉した。 Siemens は2026年8月11日に SSA-834709 を公表して V4.3.4.1 以降への更新を求めていた

脆弱性脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備既知の脆弱性の悪用
初報: 2026年11月2日 最終更新: 2026年11月3日

VulnCheck は2026年11月2日、Node-RED を標的とした実際の悪用を観測したと公表しました。Node-RED はフロー型のプログラミングツールで、ICS（産業制御システム）・OT（制御技術）環境のワークフロー自動化に広く使われ、Siemens SIMATIC IoT2050 のような商用製品にも組み込まれています。

悪用されたのは CVE-2026-58115。Siemens が2026年8月11日に SSA-834709 として公表した脆弱性で、CVSS v3.1 で 10.0（Critical）、分類は CWE-306（重要な機能に対する認証の欠如）です。対象機器では Node-RED の HTTP インターフェースに認証が強制されておらず、未認証の攻撃者がシステムコマンドを実行できるプログラミング用のノードに到達できます。

VulnCheck の研究者 Patrick Garrity は、2つの組み込みノードの組み合わせで「武器化が自明になる」と説明しています。inject ノード（スケジュールまたは起動時にメッセージを発火する）と exec ノード（シェルコマンドを実行する）を配線するだけで、デプロイした瞬間に追加の操作なしでコマンドが走る（原文英語）。

観測は 2026年10月30日、同社のカナリアによるものです。「単にスキャンしただけではない。エクスプロイトとフロー、ドロッパーを、1回の POST /flows にまとめて送ってきた」（原文英語）。ドロッパーが取得しようとしたのは bot-linux-amd64（保存先 /dev/shm/.b）で、ファイル名から Linux／AMD64 を狙うマルウェアと推定され、他のビルドが存在する可能性も示唆されます。検体そのものは取得できておらず、動作は分かっていません。

送信元は単一の IP 4.201.105[.]116（Microsoft の AS8075、位置情報はブラジル）。10月30日から11月1日までに同じ脆弱性へ16回、より広いカナリア網では8件の CVE に対して125回のヒットを記録しました。ダウンロード元は別のサーバ（85.215.73[.]250）で、VulnCheck は「探索して感染させる（scan-and-infect）分業の構成」と見ています。古い脆弱性（7年前の Apache Solr の CVE-2019-17558 など）と新しい脆弱性が無関係な製品にまたがって混在する点から、同社は「標的型ではなく日和見的な大量スキャン」と評価しています。

本脆弱性は VulnCheck の KEV には収載された一方、報道時点で CISA の KEV には載っていません（出典3）。本記録は、Siemens のアドバイザリと VulnCheck の分析を一次資料として取得し、日付・CVSS・対象バージョン・IP・ファイル名を逐語で確認しています。被害組織・被害台数は公表されていません。評価・示唆は本記録の判断として分けて書きます。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**形は「インターネット越しの大量スキャン → 未認証の POST /flows で悪性フローを投入 → デプロイと同時にシェルコマンドが走る → 別サーバからボットを取得して実行」である**（出典2・3）〈重要〉—— **段階への割り当ては本記録による。** **この形で注目すべきなのは、攻撃者が脆弱性を「突く」というより 製品の正規機能を「使っている」点である**（本記録の評価）〈重要〉—— **inject ノードと exec ノードは Node-RED の組み込み機能であり、 欠陥は「それらに未認証で到達できること」の側にある。** **したがってエクスプロイトコードは不要で、 デプロイ用の API に正しい形のフローを1回 POST するだけで成立する。**

  1. 1. 偵察確認済[2] [3]
    **単一の送信元 IP 4.201.105[.]116（AS8075／Microsoft、位置情報はブラジル）が、 古い脆弱性と新しい脆弱性を無関係な製品にまたがって試す大量スキャンを行った**（出典2・3）—— **2026年10月30日から11月1日までに、8件の CVE に対して125回のヒットを記録した。** **Node-RED への試行では少なくとも5種類の User-Agent が使われた**（出典2）。
    根拠: **「The mix of old and new bugs across unrelated products indicates 'opportunistic mass scanning rather than a targeted attack'」**（出典3。原文英語）。 **対象には7年前の Apache Solr の CVE-2019-17558 も含まれ、 Camunda・Gitea・MLflow・Traefik・Joomla に影響する**（出典3）。
  2. 2. 初期侵入確認済[1] [2] [3]
    **未認証のまま `POST /flows` に、悪性フローとドロッパーを一度に送り込んだ**（出典2・3）〈重要〉—— **「単にスキャンしただけではない。エクスプロイトとフロー、ドロッパーを、 1回の POST /flows にまとめて送ってきた」**（出典2。原文英語を本記録が訳した）。
    根拠: **「It didn't just scan us. It sent the complete exploit, flow and dropper, in a single POST /flows」**（出典2・3。Patrick Garrity。原文英語）。 **CVE-2026-58115 は CWE-306（重要な機能に対する認証の欠如）で、 対象機器では Node-RED の HTTP インターフェースに認証が無い**（出典1）。
  3. 3. 実行確認済[2] [3]
    **inject ノードと exec ノードを配線したフローにより、 デプロイした瞬間に追加の操作なしでシェルコマンドが実行された**（出典2・3）〈重要〉—— **inject ノードはスケジュールまたは起動時にメッセージを発火し、exec ノードはシェルコマンドを実行する。**
    根拠: **「Wire one to the other and the flow executes a command as soon as it is deployed, with no further interaction」**（出典2・3。Patrick Garrity。原文英語を本記録が訳した）—— **Garrity は、この2つの組み込みノードが本脆弱性の「武器化を自明にする」としている。** **VulnCheck は、`http in` エンドポイント（例: `/cmd` やランダムなパス）を介した 任意コマンド実行（ウェブシェル）の形も確認している**（出典2）。
  4. 4. C2通信確認済[2] [3]
    **別のサーバからボットのドロッパーを取得させた**（出典2・3）〈重要〉—— **`http://85.215.73[.]250:8080/bot-linux-amd64` を `/dev/shm/.b` へ、 `http://85.215.73[.]250:8080/wget.sh` を `/tmp/.s` へ保存する形。** **別の観測では第2のペイロードサーバ 45.194.90.57（ポート38472）から `/.sys_update` を `/tmp/.kworker` として保存し `nohup` で実行していた**（出典2。T5）。
    根拠: **「Because the download host is a different machine from the one that sent the exploit, the likely setup is a scan-and-infect arrangement: the hosts that find and exploit vulnerable instances pull the implant from a separate, dedicated server」** （出典2・3。原文英語を本記録が訳した）。 **保存先の `/dev/shm`（共有メモリ上のファイルシステム）と 先頭にドットを付けたファイル名、`kworker`（Linux のカーネルワーカーを装う名称）は、 いずれも痕跡を目立たせない選択である**（本記録の整理）。
  5. 5. 影響（暗号化・破壊・改ざん）推定[2] [3]
    **取得された `bot-linux-amd64` が何をするかは分かっていない**（出典2・3）〈重要〉—— **VulnCheck は検体を取得しておらず、段階的なスクリプトも入手していない。** **ファイル名から Linux／AMD64 プロセッサ上で動くことが推定され、 他のビルドが存在する可能性も示唆される。**
    根拠: **「We did not fetch the binary, so we can't say what it does once running」** （出典2・3。Patrick Garrity。原文英語を本記録が訳した）〈重要〉—— **本記録はここに推測を書かない**（本記録の方針）。

この事案で下された判断
  • **VulnCheck は、検体を取得していないことを明示したうえで公表した**（出典2・3。T6）〈重要〉—— **「検体を取得していないため、動き出した後に何をするかは言えない」**（原文英語を本記録が訳した）。
    理由は公表されていない
    トレードオフ: **分からないまま出せば、読者は「何が起きるのか」を知らずに対処を迫られる**（本記録の評価）。 **一方、検体の解析を待てば、その間に悪用が広がる**—— **本件は CVSS 10.0・未認証・エクスプロイト不要という条件がそろっており、 待つ側の損失が大きい。**

認証の無い管理 API に、正規機能を配線したフローを1回投げるだけで成立する原因・手口出典 [1] [2] [3]

CVE-2026-58115 の正体は CWE-306（重要な機能に対する認証の欠如）である。Siemens のアドバイザリ SSA-834709（2026年8月11日）によれば、対象機器ではNode-RED の HTTP インターフェースに認証が強制されておらず、未認証の攻撃者がシステムコマンドを実行できるプログラミング用のノードに到達できる。

  • 対象: SIMATIC IoT2050 Advanced（6ES7647-0BA00-1YA2）で、Industrial OS 上に Node-RED がインストールされている V4.3.4.1 未満の構成
  • CVSS v3.1: 10.0（CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H）。S:C（スコープ変更あり）が付いており、影響は脆弱なコンポーネントの外側に及ぶ
  • 対策: V4.3.4.1 以降への更新
  • 回避策: Node-RED の User Guide に従った堅牢化、または Node-RED のアンインストール

武器化の容易さについて、VulnCheck の Patrick Garrity は Node-RED の2つの組み込みノードを挙げている。inject ノードはスケジュールまたは起動時にメッセージを発火し、exec ノードはシェルコマンドを実行する。

一方を他方に配線すれば、デプロイした瞬間に、追加の操作なしでコマンドが実行される。（原文英語）

つまりエクスプロイトコードは要らない。必要なのは、正しい形のフローを管理 API に1回 POST することだけである。

カナリアが捕らえたのはスキャンではなく、1回の POST に詰め込まれた完成品だった発覚の端緒出典 [2] [3]

VulnCheck は2026年11月2日、自社のカナリア（おとり）での観測を公表した。

2026年10月30日、当社のカナリアの1つが CVE-2026-58115 を悪用する攻撃者を捕らえた。（原文英語）

単にスキャンしただけではない。エクスプロイトとフロー、ドロッパーを、1回の POST /flows にまとめて送ってきた。（原文英語）

観測された内容は次のとおりである。

  • 送信元: 単一の IP 4.201.105[.]116（Microsoft の AS8075、位置情報はブラジル）
  • 頻度: 2026年10月30日〜11月1日に、同じ Node-RED の脆弱性へ16回。より広いカナリア網では8件の CVE に対して125回のヒット
  • ペイロード: http://85.215.73[.]250:8080/bot-linux-amd64 を /dev/shm/.b へ、http://85.215.73[.]250:8080/wget.sh を /tmp/.s へ。別の観測では 45.194.90.57:38472 の /.sys_update を /tmp/.kworker として保存し nohup で実行
  • User-Agent: Node-RED への試行で少なくとも5種類
  • ウェブシェル: http in エンドポイント（例: /cmd やランダムなパス）経由の任意コマンド実行も確認

ダウンロード元がエクスプロイトの送信元と別のマシンであることから、VulnCheck は「探索して感染させる（scan-and-infect）分業の構成——脆弱なインスタンスを見つけて悪用するホストが、専用の別サーバからインプラントを取得する」と見ている（原文英語）。

なお VulnCheck は悪用の3日前（2026年10月27日）に検知用アーティファクト（Suricata／Snort／YARA 等）を提供していた。見分ける材料が先に出ていたことになる。

狙われた理由は業種でも重要度でもなく、到達できたことだった帰属出典 [2] [3]

同じ IP が狙った対象には、7年前の Apache Solr の脆弱性 CVE-2019-17558 が含まれていた（Camunda・Gitea・MLflow・Traefik・Joomla に影響する）。古い脆弱性と新しい脆弱性が、まったく無関係な製品にまたがって混在している。

VulnCheck はこれを「標的型の攻撃ではなく、日和見的な大量スキャン」と評価している（原文英語）。帰属（国家背景か犯罪グループか）に関する記述は無い。

The Register は背景として、犯罪者がインターネットに露出した OT/ICS 機器を狙う傾向が強まっており、物理世界への影響と現実の被害を生み得ることを指摘している。例として、欧州各地で続く冷蔵制御装置への侵害と、夏にかけて米国の少なくとも12州の水道システムで起きた攻撃を挙げている。

Garrity は LinkedIn の投稿で、次のように呼びかけている。

Node-RED をどこかで動かしているなら——OT 環境の内側も含めて——今日、外部から到達可能かを確認し、入手できる更新を適用し、悪用のリスクを下げる検知を実装してほしい。（原文英語）

VulnCheck の KEV には載ったが、CISA の KEV にはまだ載っていない対策・注意喚起出典 [1] [2] [3]

本脆弱性は VulnCheck の KEV（Known Exploited Vulnerabilities）カタログに収載された一方、The Register の報道時点（2026年11月2日）では CISA の KEV には載っていない。

これは運用上の意味を持つ（本記録の評価）。「CISA KEV に載ったら緊急対応」という手順を持つ組織では、本件は緊急にならない。一方、実際の悪用はすでに観測されている。

読者が打てる手は、優先順に次のとおりである（出典1・2の推奨と本記録の整理）。

  1. Node-RED が外部から到達可能かを今日確認する（最優先。到達できなければ本件は成立しない）
  2. V4.3.4.1 以降へ更新する（Siemens の正規の対策）
  3. 更新できない場合は adminAuth を設定して堅牢化する、または Node-RED をアンインストールする
  4. デプロイ済みのフローに、意図していない exec ノードや HTTP エンドポイントが無いか点検する
  5. OT セグメントからの外向き通信を宛先の許可制にする（ボットの取得段階で止まる）
  6. VulnCheck が提供する検知アーティファクト（Suricata／Snort／YARA 等）を適用する

なお IOC の IP は Microsoft の AS8075 上にある。IP 単位の遮断は正当な通信を巻き込みうる。また本記録は、これらの IOC の悪性を独自に検証していない（照合先のテレメトリを持たない）。

ここからは本記録の作成者の評価である。

第一に、本件の中心にいるのは「自社が Node-RED を動かしていると認識していない機器」である。 Node-RED は ICS/OT のワークフロー自動化で広く使われ、Siemens SIMATIC IoT2050 のような商用製品に組み込まれて出荷される。調達したのは「IoT ゲートウェイ」であって「Node-RED」ではない。ソフトウェア資産台帳が製品名で作られていれば、「Node-RED の脆弱性」というニュースは検索にかからない。SBOM が必要とされる理由は、まさにこの一点にある。

第二に、「脆弱性を突く」というより「正規機能を使う」形である。 inject ノードと exec ノードは Node-RED の組み込み機能で、脆弱性は「それらに未認証で到達できること」の側にある。つまり攻撃者はエクスプロイトを書く必要がなく、製品のドキュメントどおりの使い方をしている。この型は、ローコード／自動化基盤に共通して現れる。読者が自分の環境で探すべきなのは「任意コマンド実行に相当する部品」と「それに到達できる経路の認証」である。

第三に、攻撃者が残すのはバイナリではなくフローの定義である。ファイル改ざん検知やマルウェア対策の視界に入らない。フローは「設定」に見えるため、構成管理や変更検知の対象から落ちやすい。だが実際には実行されるコードである。VulnCheck の推奨事項に「デプロイ済みのフローに、意図していない exec ノードが無いか確認する」が入っているのはこのためだろう。これを人手の点検として置くと必ず抜ける——差分を機械的に見る形にしなければ続かない。

第四に、猶予は80日だった。 CVSS 10.0 のアドバイザリ（2026年8月11日）から実際の悪用の観測（10月30日）まで80日。OT の計画停止が四半期〜年単位で回る現場では、「次の停止機会に更新する」という判断と噛み合わない。更新できるまでの繋ぎ——到達経路の遮断、管理インターフェースの無効化、egress の制限——を、どの権限で何時間以内に打てるかを平時に決めておく必要がある。本件については、更新を待たずに打てる最も効く手は「外から到達できないようにする」ことである。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
エクスプロイトを書かずに済む経路——認証の無い管理 API に、正規機能を配線したフローを1回投げる
攻撃者（layer 0）は単一の IP 4.201.105[.]116 から、古い脆弱性と新しい脆弱性を 無関係な製品にまたがって試す大量スキャンを行った（8件の CVE に125回のヒット）。 Node-RED に当たると、認証が強制されていない HTTP 管理インターフェース（layer 1）へ 未認証で POST /flows を1回送る。送られたのは、inject ノードと exec ノードを配線した 悪性フロー（layer 2）で、どちらも Node-RED の組み込み機能である。 デプロイと同時に exec ノードがシェルコマンドを実行し（layer 3）、 別のペイロードサーバ 85.215.73[.]250:8080 から bot-linux-amd64 を /dev/shm/.b へ取得する（layer 4）。 探索と感染を別ホストに分けた scan-and-infect の構成である。 取得されたボットが何をするかは、検体が取得できていないため分かっていない（layer 5）。 対象機器は Siemens SIMATIC IoT2050 Advanced（V4.3.4.1 未満）で、 Siemens は2026年8月11日に SSA-834709 を公表していた。

    **Node-RED は Siemens SIMATIC IoT2050 のような商用製品に組み込まれて出荷される**（出典2・3）〈重要〉—— **調達したのは「IoT ゲートウェイ」であって「Node-RED」ではない。** **ソフトウェア資産台帳が製品名で作られていると、本件は検索にかからない。**
    取るべき行動 **OT/IoT 機器の台帳に「機器名」ではなく「機器の中で動いているソフトウェアと管理インターフェース」の欄を持つ。** **少なくとも ①待ち受けポートと到達範囲、②管理 UI/API の有無と認証の設定、 ③組み込まれている OSS の名称を、機器ごとに1行で埋める。** **ベンダーに SBOM を求める場合も、最初に必要なのはこの3つである。**
  • CVSS 10.0 のアドバイザリに対して、現場が持つ猶予は80日程度と見積もる
    **Siemens のアドバイザリ（2026年8月11日）から実際の悪用の観測（10月30日）までは80日だった** （出典1・2。本記録の算出）〈重要〉—— **一方、OT の計画停止は四半期〜年単位で回る現場もある。** **「次の停止機会に更新する」という判断は、この80日と噛み合わない。**
    取るべき行動 **未認証で遠隔から任意コード実行が可能な脆弱性については、 「更新までの繋ぎ」を決める手順を別に持つ。** **具体的には、到達経路の遮断（許可元 IP の限定・VPN 経由化）、 管理インターフェースの無効化、egress の制限のうち、 どれをどの権限で何時間以内に実施できるかを平時に決めておく。**
  • CISA KEV への収載を更新判断の起点にすると、取りこぼす
    **本件は VulnCheck の KEV に収載された一方、報道時点で CISA の KEV には載っていなかった**（出典3）〈重要〉—— **「KEV に載ったら緊急対応」という運用では、本件は緊急にならない。**
    取るべき行動 **悪用情報の入力源を複数持ち、どの情報源で何が起きたら社内の緊急手順が動くかを明文化する。** **少なくとも、製品ベンダーのアドバイザリ、CISA KEV、商用の悪用情報（VulnCheck 等）の3系統を並べ、 「1つでも悪用を報告したら動く」側に寄せる。**
  • 日和見的な大量スキャンは、業種や重要度で自組織を除外できない
    **同一の IP が、Apache Solr（7年前）から Node-RED（新規）まで、 無関係な製品にまたがって125回のヒットを記録している**（出典2・3）〈重要〉—— **VulnCheck は「標的型ではなく日和見的な大量スキャン」と評価している。** **狙われた理由は「到達できたから」であって、業種でも重要度でもない。**
    取るべき行動 **「うちは狙われるほどの組織ではない」という前提で露出を許容している箇所を洗い出す。** **判定の軸は「狙う価値があるか」ではなく「インターネットから到達できるか」にする。** **外部からの到達可能性の棚卸しを四半期ごとの定例にする。**
セキュリティ技術者への示唆
  • エクスプロイトコードは不要——正規機能の組み合わせがそのまま武器になる
    **inject ノード（起動時にメッセージを発火）と exec ノード（シェルコマンドを実行）は Node-RED の組み込み機能である**（出典2・3）〈重要〉—— **「配線すれば、デプロイした瞬間に追加の操作なしでコマンドが走る」**（Garrity。原文英語）。 **欠陥は機能の側ではなく「未認証で到達できること」の側にある**（出典1）。
    取るべき行動 **自動化・ローコードの基盤では、「任意コマンド実行に相当する部品」を列挙し、 それに到達できる経路（管理 API・デプロイ API・Webhook）を認証必須にする。** **部品単位で無効化できるなら、使っていないものは無効化する。** **Node-RED であれば `adminAuth` の設定状況を機器ごとに確認する。**
  • フローは「設定」に見えるが、実行されるコードである。変更検知の対象に入れる
    **VulnCheck の推奨事項に「デプロイ済みのフローに、意図していない exec ノードや HTTP エンドポイントが無いか確認する」がある**（出典2）〈重要〉—— **攻撃者が残したのはバイナリではなくフローの定義であり、 ファイル改ざん検知やマルウェア対策の視界に入らない**（本記録の評価）。
    取るべき行動 **フローの定義（flows.json 相当）をバージョン管理に置き、 ベースラインとの差分を機械的に検出する。** **とくに exec ノードと `http in` ノードの増減を監視対象にする。** **人手の目視点検にしない——続かないので必ず抜ける。**
  • 制御機器が任意のインターネットホストから実行ファイルを落とせる状態が、本件の前提になっている
    **ドロッパーは別サーバ（85.215.73[.]250:8080）からボットを取得する構成で、 VulnCheck は「探索して感染させる分業」と見ている**（出典2・3）〈重要〉—— **エクスプロイトが成功しても、egress が閉じていれば取得の段階で止まる**（本記録の評価）。
    取るべき行動 **OT セグメントからの外向き通信を、宛先と宛先ポートの許可制（既定は拒否）にする。** **とくに 80/8080/443 の任意ホストへの到達を既定で許している箇所を探す。** **`/dev/shm` や `/tmp` への新規実行ファイルの出現、`nohup` による常駐、 `kworker` のような正規プロセスを装う名称を検知ルールに入れる。**
  • 「検体が取れていない」という公表は、対処できる段階が限られることを意味する
    **VulnCheck は bot-linux-amd64 の検体を取得しておらず、挙動は分かっていない**（出典2・3）〈重要〉—— **したがって「このマルウェアを検知する」という形の対策は組めない。**
    取るべき行動 **挙動が不明なペイロードに対しては、検知ではなく経路で止める。** **使えるのは ①到達経路の遮断、②フローの差分検出、③egress の制限、 ④VulnCheck が2026年10月27日に提供した検知アーティファクト（Suricata／Snort／YARA）である。** **IOC の IP は Microsoft の AS8075 にあるため、IP 単位の遮断は正当な通信を巻き込みうる点に注意する。**
