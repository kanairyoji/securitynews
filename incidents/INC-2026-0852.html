INC-2026-0852Trigger.dev で環境変数に不正アクセス

AI ワークフロー基盤 Trigger.dev が2026年11月1日、 **攻撃者が一部の利用組織の環境変数に不正アクセスした**と公表した。 **悪用された欠陥は遮断済みとするが、影響組織数・環境変数の中身・侵入経路は いずれも公表されておらず、公表文は5文で終わっている**。

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年11月1日22:33（UTC・Trigger.dev のインシデント報告） 最終更新: 2026年11月3日

公表文が5文しかない、という事実そのものが本件の特徴です。 Trigger.dev は2026年11月1日22:33（UTC）、CTO の Eric Allam 名義で「Security Disclosure: Sunday November 1st」を公開し、攻撃者が一部の利用組織の環境変数に不正アクセスしたと公表しました（出典1）。

公表された事実はこれだけです（出典1・原文英語）。

  • 「Trigger.dev でセキュリティインシデントが発生した」
  • 「この攻撃で使われた exploit は遮断したが、調査により一部の組織にまたがる露出を特定した」
  • 「攻撃者はこれらの組織の環境変数に不正アクセスした」
  • 「影響を受けたアカウント所有者全員に、緩和手順を記したメールを送った」
  • 「更新はステータスページに掲載する」

Trigger.dev は、TypeScript で AI エージェントや長時間ジョブを動かす「durable execution」基盤です（出典1・3）。2026年10月26日には Slack・Stripe・GitHub 等からの Webhook 受信機能を追加しており（出典2）、利用組織の環境変数には、連携先サービスの API キーが入っているのが通常の使い方です（出典3。本記録の整理）。The Register は「環境変数に機微な認証情報が含まれていれば、攻撃者は事実上『王国の鍵』を得て、連携先のサービスや基盤に到達し得る」と書いています（出典3・原文英語）。

読み方として重要なのは、被害の範囲が利用側にしか分からない構造です（本記録の評価）。Trigger.dev は影響組織を公表しておらず、環境変数の中身も当然公表しません。自分の環境変数に何を入れていたかを知っているのは利用組織だけです。 つまり、影響の大きさを判定できるのは提供側ではなく利用側であり、棚卸しができていない組織は「自社がどれだけ危ないか」を判断できません。

  • 悪用された欠陥の内容公表されていない
    **「この攻撃で使われた exploit は遮断した」とあるのみで、 何の欠陥だったのか、ホスティング版固有か OSS 版にも及ぶのかは示されていない**（出典1）。 **同社の OSS 版では2026年10月に環境変数・シークレットに関する勧告が複数出ており （CVE-2026-114069 等）**（出典4）、 **自前運用している組織は自分のバージョンを確認する必要があるが、 本事案との関係は誰も述べていない**（本記録の明示）。
  • 攻撃の期間と検知の契機公表されていない
    **攻撃がいつ始まり、いつ検知され、どれだけ続いたのかは公表されていない**（出典1・2）。 **このため、侵入から検知まで（dwell）・検知から公表まで（disclosure）を 算出できない**（本記録の確認）。
  • 環境変数が実際に悪用されたかどうか公表されていない
    **公表は「環境変数に不正アクセスした」までで、 そこに含まれていた認証情報が連携先で使われたかどうかに触れていない**（出典1）。 **「悪用は確認していない」という定型の記述もない**（本記録の確認）。 **本記録はこれを「悪用が無かった」とは読まない**（本記録の明示）。
  • 利用組織に求めた「緩和手順」の内容公表されていない
    **「影響を受けたアカウント所有者全員に、緩和手順を記したメールを送った」と あるが、その手順は公開されていない**（出典1）。 **影響を受けていない組織や、自前運用している組織が 同じ手順を参考にすることができない**（本記録の評価）。
  • 予告された「完全なインシデント報告」の公開時期公表されていない
    **The Register の取材に対し、広報は「完全なインシデント報告を待ってほしい」と 述べたとされるが、公開時期は示されていない**（出典3）。 **11月3日時点で公開は確認できていない**（本記録の確認）。

Trigger.dev は、TypeScript で AI エージェントや長時間ジョブを動かし、再試行・キュー・スケーリングを基盤側が受け持つ実行基盤です（出典2・3）。この使い方では、環境変数に次のようなものが入ります（本記録の整理）。

  • 連携先 SaaS の API キー（決済・通知・ストレージ等）
  • データベースの接続情報
  • モデル提供者の API キー
  • Webhook の署名検証鍵（2026年10月26日に Webhook 受信機能が追加・出典2）

The Register は「環境変数に機微な認証情報が含まれていれば、攻撃者は事実上『王国の鍵』を得て、連携先のサービスやデジタル基盤に到達し得る」と書いています（出典3・原文英語）。

本記録の評価としては、この構造は通知の受け手に判断を押し返します。 「影響を受けた」というメールを受け取った組織が最初にやることは、自分が何を預けていたかを調べることです。棚卸しが無ければ、そこから始めることになります。

発生当日の公表は速い。足りないのは、影響外の組織に向けた情報である組織の対応出典 [1] [2] [3]

発生（11月1日）と公表（同日22:33 UTC）が同じ日です（出典1）。環境変数の露出は、時間がそのまま被害に変わる種類の事案なので、速さを優先した判断には合理性があります（本記録の評価）。本記録は公表の時期を「機能した」と評価します。

一方、公表の範囲は「不十分」と評価します（本記録の評価）。理由は3つです。

  • 影響の有無を、利用組織はメールが来たかどうかだけで知る形になっている（出典1）
  • 緩和手順が公開されていないため、影響外の組織が予防に使えない〈未確定5〉
  • Trigger.dev は OSS として自前運用もできるが、悪用された欠陥の所在が示されていないため、自前運用側は自分の危険度を判定できない（出典2・3）〈未確定2〉

通知先が「アカウント所有者（account owners）」である点も、本記録は留保をつけます（出典1）。SaaS のアカウント所有者が請求担当や管理者になっている組織では、実際に鍵を回す技術担当に届かないことがあります（本記録の判断）。

一方、Trigger.dev の OSS 版には、環境変数とシークレットに関する勧告が2026年10月に複数出ています（出典4）。

本記録は、この勧告と本事案の関係を主張しません〈差異4〉。Trigger.dev の公表はホスティング版で悪用された欠陥に触れておらず、勧告側もクラウド版への影響に言及していないためです（出典1・4）。

ただし、自前運用している組織にとって、やるべきことは変わりません（本記録の判断）。自分のバージョンを確認し、上流の勧告を購読することです。「SaaS 側で遮断済み」という公表は、自前運用の安全を意味しません。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
基盤1か所の欠陥が、利用組織ごとの「鍵束」に届いた
攻撃者（layer 0）が Trigger.dev の基盤側の欠陥を突いて不正アクセスし（layer 1）、 一部の利用組織の環境変数（layer 2）に到達した構造を示す。 環境変数は連携先サービスの認証情報を含むのが通常の使い方であり（layer 3）、 そこから各サービスへ到達し得る（layer 4）。 ただし環境変数の中身と影響組織は公表されていないため、layer 2 以降の広がりは 「この基盤の一般的な使い方」に基づく整理であって、確認された被害ではない。 右下に、提供側の結論を待たずに利用側が実行できる対策を置いた。

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入公表されていない

侵入を防げたマルチテナント基盤で、テナント間の境界をまたぐ参照をリクエスト単位で検査する（認可の試験をテナント越えの観点で書く）
侵入を防げたシークレットを平文で返し得る API 経路に、権限の粒度（読み取り鍵でルート鍵を取れない）を強制する
認証情報アクセス公表されていない

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**インシデント発生と同じ2026年11月1日（日）に、CTO 名義で公表した** （出典1。公表は22:33 UTC）。 **ステータスページのインシデントも同日22:50 UTC に記録されている**（出典2）。 機能した
**公表は5文に留め、影響組織数・悪用された欠陥・緩和手順を含めなかった**（出典1）。 **The Register の取材には追加情報の提供を断り、 「完全なインシデント報告を待ってほしい」と回答した**（出典3）。 不十分
**影響を受けたアカウント所有者全員にメールを送り、 緩和手順を案内したとした**（出典1）。 **手順の内容は公開していない**（出典1）〈未確定5〉。 部分的に機能
CISO・経営層への示唆
  • 実行基盤に預けたシークレットは、その基盤の侵害でまとめて失われる
    **本件では、基盤側の欠陥1つで一部組織の環境変数が まとめて不正アクセスされた**（出典1）。 **環境変数は「アプリが動くために必要な鍵の集合」であり、 1か所の侵害が連携先すべてに広がる構造になっている**（出典3。本記録の評価）。
    取るべき行動 **「どの SaaS に、どのサービスの鍵を、どの権限で預けているか」の 一覧を作る。棚卸しの単位はサービスではなく鍵にする。 鍵ごとに、盗まれたときに何ができてしまうかを1行で書く。**
  • 影響範囲を判定できるのは提供側ではなく自社である
    **Trigger.dev は影響組織を公表せず、環境変数の中身も公表しない**（出典1・3）。 **自社が何を預けていたかを知っているのは自社だけである**（本記録の評価）。
    取るべき行動 **インシデント通知を受けたときに「自社の影響度」を即答できるよう、 主要 SaaS ごとの預けた鍵の一覧を、通知の受領窓口と同じ場所に置く。**
  • 「アカウント所有者宛のメール」は、鍵を管理している人に届かないことがある
    **本件の通知先は account owners（アカウント所有者）である**（出典1）。 **請求担当や管理者が所有者になっている SaaS では、 実際に鍵を回す技術担当に届かない**（本記録の判断）。
    取るべき行動 **主要 SaaS の「アカウント所有者」と「セキュリティ連絡先」を棚卸しし、 セキュリティ通知の宛先をチーム用アドレス（配布リスト）に変更する。**
  • OSS 版を自前運用している場合、提供側の公表は自社の安全を保証しない
    **本件の公表は「exploit は遮断した」とするが、 それはホスティング版の話である**（出典1）。 **Trigger.dev は OSS として自前運用でき、 OSS 版では2026年10月に環境変数・シークレットに関する勧告が出ている** （出典2・3・4）。
    取るべき行動 **自前運用している基盤を一覧にし、それぞれの ①現在のバージョン ②上流の勧告の購読先 ③更新の責任者を明記する。 「SaaS 版が直った」という報道で安心しない。**
セキュリティ技術者への示唆
  • 長期有効の API キーを預けるのをやめる
    **環境変数に長期有効の鍵が入っていると、 露出した時点から更新までの全期間が危険期間になる**（本記録の判断）。 **本件では攻撃の期間も検知時刻も公表されていないため、 危険期間の長さを利用側は推定できない**（出典1）〈未確定3〉。
    取るべき行動 **預け先が対応している範囲で、短命トークン（OIDC 連携・STS・ 期限付きトークン）へ置き換える。置き換えられない鍵は 権限を最小化し、利用元を IP・テナントで縛る。**
  • 鍵の更新を「30分で終わる作業」にしておく
    **環境変数の露出に対する唯一確実な対策は更新であり、 それは利用側だけで実行できる**（本記録の判断）。 **本件では緩和手順が公開されていないため、 手順を持っていない組織は手探りになる**（出典1）〈未確定5〉。
    取るべき行動 **基盤に預けたシークレットの更新手順を書き、 年1回は実際に回して所要時間を測る。 更新で壊れる連携（Webhook の署名鍵・DB 接続）を先に洗い出す。**
  • 連携先側のログで「鍵が誰に使われたか」を見られるようにする
    **提供側が悪用の有無を公表しない場合**（出典1）、 **判定材料は連携先サービスのアクセスログしかない**（本記録の判断）。
    取るべき行動 **預けた鍵ごとに、連携先サービスの監査ログで 利用元・時刻・操作を引ける状態にしておく。 Stripe・Slack・クラウドの API キーは、鍵単位で絞り込める設定にする。**
  • Webhook の追加は、影響範囲の拡大として扱う
    **Trigger.dev は2026年10月26日に Slack・Stripe・GitHub 等の Webhook 受信機能を追加している**（出典2）。 **The Register も、Webhook の追加によって 影響し得る連携の範囲が広がった可能性を指摘している**（出典3）。
    取るべき行動 **基盤に新しい連携を足すたびに、預ける鍵の一覧を更新し、 「この基盤が侵害されたとき何が失われるか」を書き直す。 連携の追加を変更管理の対象にする。**

自組織に当てはまるか

観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ AI エージェント・バッチ処理をクラウド型の実行基盤（durable execution・ワークフロー SaaS）で動かしている**本件は基盤側の欠陥1つで、複数の利用組織の環境変数が まとめて不正アクセスされた構造である**（出典1）。 **アプリの処理を外に出すと、アプリが使う鍵も一緒に外に出る**（本記録の評価）。
