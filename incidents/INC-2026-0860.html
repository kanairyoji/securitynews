INC-2026-0860露ウの公共警報アプリ乗っ取り

ウクライナの空襲警報アプリ「Повітряна тривога」（開発元 Ajax Systems・利用者約660万人）が2026年11月1日夜に乗っ取られ、放射線・化学・核攻撃・市街戦の偽警報が配信された。数時間後の11月2日未明にはロシア非常事態省（МЧС России）の公式アプリが管理パネルを攻撃され、約02:45（モスクワ時間）に「核弾頭が発射された」とする偽警報が33の連邦構成主体へ送られた。ウクライナ側の乗っ取りは Hitcore Corp、ロシア側は DC8044 が名乗り、DC8044 は API 経由で侵入したと主張。ゼレンスキー大統領は11月3日、ロシア側への攻撃がウクライナのハッカーによる報復であることを認めた

不正アクセス・侵害偽情報・影響工作続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年11月2日 最終更新: 2026年11月3日

2026年11月1日の夜（現地時間）、ウクライナの空襲警報アプリ「Повітряна тривога」（空襲警報。開発元 Ajax Systems） が乗っ取られ、キーウの利用者に放射線の危険・化学の脅威・核攻撃・市街戦を警告する偽の通知が配信されました。通知にはアプリの聞き慣れた案内音声がそのまま使われ、ロシア語の通知は核弾頭を搭載しうる弾道ミサイル「オレシニク」の攻撃可能性を警告していました。ウクライナ空軍は Telegram で「おそらくアプリ『Повітряна тривога』が敵の影響を受けた。放射線の脅威は無い。落ち着いて当チャンネルの更新を確認してほしい」（原文ウクライナ語）と呼びかけました。

数時間後、同じことがロシア側で起きました。 11月2日未明、ロシア非常事態省（МЧС России）の公式モバイルアプリが攻撃され、約02:45（モスクワ時間）に「核弾頭が発射された」とする偽の通知が33の連邦構成主体の利用者へ送られました。同省は Telegram で「モバイルアプリが大規模なサイバー攻撃を受け、虚偽の情報が拡散された」「モバイルアプリの侵害は住民警報システムの動作に影響を与えておらず、与えることもできない」（いずれも原文ロシア語）と発表し、翌朝には「11月2日、モバイルアプリ『МЧС России』の管理パネルに対してサイバー攻撃が行われた」と攻撃された面を明示しました。

名乗り手が双方に現れています。 ウクライナ側の偽通知には、乗っ取りを自称する無名の組織 Hitcore Corp の Telegram チャンネルへのリンクが貼られていました。ロシア側は DC8044 が「非常事態省のアプリを API 経由で突破した」と主張し、Telegram に技術的な詳細を掲載したと報じられています。ウクライナ戦略コミュニケーションセンター（SPRAVDI）は自国アプリの乗っ取りをロシアの仕業だとし、ゼレンスキー大統領は11月3日、ロシア側のアプリへの攻撃がウクライナのハッカーによる報復であることを認めました（「我々はたった今、攻撃に対して応じた」）。

狙われたのは、避難の判断を人に促すための経路そのものです。ウクライナ空軍はアプリが軍の指揮システムとは接続していないと述べ、ロシア非常事態省も警報はサイレン・拡声器・SMS・テレビ・ラジオで継続しておりアプリは補助手段だと説明しました。警報の根幹は動いていたということです。それでも、660万人が使うアプリから「放射線の危険」が流れたという事実は残ります。

ロシア非常事態省が公表したのは、攻撃された面が「モバイルアプリの管理パネル」だったという一点である（原文ロシア語）。名乗り手の DC8044 はAPI 経由だと主張している。ウクライナ側は、開発元が「外部の者がアプリの動作に介入した」と説明したと報じられているにとどまる。

どちらも、侵害されたのは利用者の端末ではない。端末のアプリは正規のまま動き、正規の案内音声で、正規の配信経路から偽の内容を受け取った。だから利用者には見分けようがなかった（本記録の評価）。

警報配信の仕組みは、構造上「1人が押せば全員に届く」面を必ず持つ。緊急時に秒単位で全国へ届けることが目的だからである。その面は、アプリの中ではなく運用者側の管理画面や API にあり、アプリの審査やストアの保護はここには及ばない（本記録の整理）。

侵入の経路はどちらも公表されていない〈未確定1・2〉。認証情報の窃取か、認証のない API か、露出した管理画面か—— 区別できなければ、同じ構成の警報アプリを運用する他の組織は自組織の同じ面を点検できない。

  • ウクライナ空軍は自らの Telegram チャンネルを代替の情報源として提示した

警報アプリの価値は「鳴ること」ではなく「鳴ったら本物だと信じられること」にある（本記録の評価）評価・解釈出典 [1] [2] [4] [5]

ここからは本記録の作成者の評価である。

第一に、この攻撃が奪ったのは可用性ではなく信頼性である。アプリは止まらなかった。正規の経路で、正規の音声で、正規の形式の通知が届いた。止まるより悪い——止まれば利用者は別の経路を探すが、動いているアプリから嘘が流れると、利用者は次に本物が鳴ったときにも疑う。ウクライナ空軍が「アプリの通知を無視してほしい」と告知した瞬間、660万人が使う警報経路は一時的に無価値になった。

第二に、「補助手段だから影響は無い」という説明は、半分しか当たっていない。ロシア非常事態省の「住民警報システムの動作に影響を与えておらず、与えることもできない」という説明は、システムの可用性については正しい。だが、住民の側から見れば、省の名前で届いた「核弾頭が発射された」は省の警報である。 サイレンが鳴っていなくても、アプリが鳴れば人は動く。経路の分離は冗長性を担保するが、信頼の毀損は分離できない。

第三に、公共警報は「国家が運用する通信」でありながら、実装は民間のアプリと配信基盤に依存している。ウクライナの「Повітряна тривога」は民間企業（Ajax Systems）の開発で、省庁が支援した。配信にはモバイル OS のプッシュ通知基盤が介在する。守る対象は「アプリ」ではなく、「配信を起動できる人・鍵・画面」の集合である——そこに国家の警報の権威が宿っている。

第四に、相互の報復が数時間で成立したことが、この領域の敷居の低さを示している。ゼレンスキー大統領が報復であることを認めるまで2日かかっていない。警報システムは、軍事目標としての価値は低いが、心理的効果は大きく、対抗措置も同じ形で返せる。 相互にエスカレートしやすい領域である。

日本への当てはめ。 日本の公共警報は J-ALERT から緊急速報メール・自治体アプリ・放送へ分岐しており、自治体や事業者が独自に運用する防災アプリも多い。本件が問うのは「誰が通知を押せるか」「その面はどこに露出しているか」である。1つの管理画面の認証が破られたときに、全住民へ任意の文面が送れる構成になっていないか——これは日本の自治体・事業者にもそのまま当てはまる問いである。

判断評価評価の根拠と留保
Ajax Systems がプッシュ通知を停止し、アプリのサービスを一時停止した （報道による。本記録は開発元の公表を確認できていない）機能した**本記録の作成者の評価である。** 偽の警報が正規の経路・正規の音声で届いており、 利用者には見分ける手段が無かった。**内容を信じられない配信経路を 動かし続けるより、止めて代替経路（空軍 Telegram・サイレン）へ誘導するほうが 合理的である。** 翌未明には基本機能を復旧させており、停止は短期で終わっている。 ただし**停止・復旧の時刻が公表されていないため、判断の速さは評価できない。**
ロシア非常事態省が、攻撃された面（管理パネル）・時刻（約02:45 モスクワ時間）・ 範囲（33の連邦構成主体）を公表した一方、到達経路と誰の仕業かは述べなかった部分的に機能**本記録の作成者の評価である。** 時刻と範囲を数値で示した点は、 住民が自分の受信を照合できる形になっており有用である。 **一方で「管理パネル」までしか示さなかったため、同じ構成で警報アプリを 運用する他国・他組織は自組織の同じ面を点検できない**〈未確定2〉。 **また「警報システムへの影響は無い」という説明は可用性の話であり、 住民が受け取った偽の警報そのものへの言及にはなっていない。**
両国とも、アプリ以外の経路（ウクライナ空軍 Telegram・ロシア非常事態省 Telegram・ サイレン・拡声器・SMS・テレビ・ラジオ）を代替として提示した機能した**本記録の作成者の評価である。** 偽情報への対処でもっとも重要なのは 「正しい情報がどこにあるか」を示すことであり、両国ともそれを行っている。 **ただし代替経路の告知が届くのは Telegram やニュースを見ている人に限られる** （本記録の留保）。
CISO・経営層への示唆
  • 住民・顧客へ一斉配信できる経路は、「情報システム」ではなく 「組織の発言権」として扱う
    正規のアプリ・正規の音声で「核弾頭が発射された」が届いた。 侵害されたのはシステムの可用性ではなく、組織の名前で語る権威である
    取るべき行動 プッシュ通知・緊急メール・公式 SNS・緊急放送の各経路について、 「誰が押せるか」「どの画面・API から押せるか」「文面は誰が検証するか」を 一覧にし、経営が承認する管理対象として登録する。管理者の数を数え、 四半期ごとに棚卸しする
  • 「別経路があるから影響は無い」という説明は、可用性の話であって 信頼の話ではないと理解する
    ロシア非常事態省は「アプリの侵害は住民警報システムに影響を与えない」と 説明したが、住民が受け取った偽警報そのものは残る
    取るべき行動 インシデント時の広報文の雛形に、①システムの可用性 ②受信者が受け取った 誤った内容 ③今すぐ取るべき行動 の3点を分けて書く欄を設ける。 ②を省いた文面を承認しない
  • 緊急連絡の代替経路を、平時から利用者に周知しておく
    アプリを止めたあと、住民は空軍の Telegram やサイレンに頼る必要があったが、 その案内が届くのは Telegram やニュースを見ている人に限られた
    取るべき行動 「公式アプリ・公式サイトが使えないときの連絡経路」を、 平時の案内（アプリ内・契約書・自治体広報）に明記し、年1回は実際に その経路でテスト配信して到達を確認する
  • 配信機能を外部の開発元・配信事業者に委ねている場合、 その管理面の統制を契約で縛る
    ウクライナの空襲警報アプリは民間企業（Ajax Systems）が開発・運用しており、 省庁は支援する立場だった。侵害経路も開発元側にある可能性が高い
    取るべき行動 委託契約に「配信を起動できるアカウントの一覧提出」「多要素認証の必須化」 「管理画面の到達元制限」「侵害時の時間内通報」を具体的な数値で書き込み、 年次で証跡を受領する
セキュリティ技術者への示唆
  • 配信を起動する管理画面と API を、インターネット全体から到達できない面にする
    ロシア非常事態省は「モバイルアプリの管理パネルに対するサイバー攻撃」と 公表し、DC8044 は API 経由だと主張した
    取るべき行動 管理画面・管理 API を VPN か固定 IP の背後に置き、デバイス証明書を要求する。 公開が必要な API は認証トークンに加えて送信元 IP の許可リストを適用し、 外部からの到達性を実際にスキャンして確認する
  • 緊急配信の文面を自由文にせず、テンプレートと重大度の階層で縛る
    「放射線の危険」「核弾頭が発射された」という、通常の空襲警報には現れない 内容が、そのまま全国の端末へ配信された
    取るべき行動 配信 API の受け付ける文面をあらかじめ登録したテンプレートの ID と 差し込みパラメータだけに制限する。最上位の重大度（核・放射線・化学）には 別経路の第二承認者を必須にし、承認なしの呼び出しは API 側で拒否する
  • 配信の直後に自組織の端末で内容を照合する「打ち返し監視」を置く
    偽警報は正規の経路・正規の案内音声で届いたため、利用者側には 見分ける手段が無く、組織側も飛んだ後に気づいた
    取るべき行動 自組織が保有する受信用端末（複数地域）で配信を受信し、 配信台帳と内容を自動照合する。台帳に無い配信を検知したら 即座に訂正通知を打つ手順を演習しておく
  • 配信ログを「誰が・どの面から・どの文面を・どの範囲へ」の4点で残す
    ロシア非常事態省は時刻（約02:45 モスクワ時間）と範囲（33の連邦構成主体）を 特定して公表できた一方、到達経路の説明は無かった
    取るべき行動 配信ログに操作者 ID・認証方式・送信元 IP・API エンドポイント・ テンプレート ID・対象範囲を必ず含め、改ざんできない保存先へ転送する。 インシデント時に「誰が押したか」を1時間以内に答えられるか演習で測る
  • 「アプリは正常に動いている」状態での誤情報配信を、インシデント訓練の シナリオに入れる
    障害ではなく「正常に動くアプリが嘘を配る」形の事案だった。 可用性監視では一切検知できない
    取るべき行動 机上演習に「自社アプリから偽の緊急通知が全利用者へ飛んだ」シナリオを追加し、 停止の判断・代替経路の案内・訂正通知の文面を30分以内に出せるか測る

観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 自組織のアプリ・サービスから、利用者全員（または広域）へ一斉にプッシュ通知・ SMS・メールを送れる機能がある本件で侵害されたのは端末でもアプリ本体でもなく、一斉配信を起動する面だった

体制・契約□ 公式アプリ・公式サイトが使えないときの代替連絡経路を、 平時から利用者へ周知していないアプリの通知を無視するよう告知した結果、代替経路を知らない利用者は 情報源を失った
