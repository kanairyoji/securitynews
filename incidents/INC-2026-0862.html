INC-2026-0862新ボットネット VeilDHT

中国の国家インターネット応急センター（CNCERT）が2026年11月3日ごろ、新型ボットネット VeilDHT の大規模な拡散について風険提示を公表した。主に Linux サーバと IoT 機器を感染させ、2026年10月16日から26日の間に中国国内で累計40,467台が感染、日次の最大上線数は15,805台。拡散は ASUS ルータの CVE-2024-3912 と Realtek Jungle SDK の CVE-2021-35394 という2つのコマンドインジェクションの悪用が主。制御端のアドレスは偽装 DNS 応答と公開 P2P（DHT）網の2経路で取得し、通信は Ed25519・X25519・SHA-512・XChaCha20-Poly1305 で保護される。20種の DDoS・任意コマンド実行・対話型リバースシェル・リバースプロキシを備える。検体解析には緑盟科技（NSFOCUS）伏影実験室が寄与した

中国の 国家インターネット応急センター（CNCERT／国家互联网应急中心） が、新型ボットネット VeilDHT の大規模な拡散について風険提示（リスク警告）を公表しました。検体解析には 緑盟科技（NSFOCUS）伏影実験室が寄与しています。

規模は中国国内で累計40,467台です。 2026年10月16日から26日の観測で、日次の最大上線数（その日に活動が確認された感染端末の数）は15,805台、累計の感染は約40,467台でした。感染先は主に Linux サーバと IoT 機器です。

名前の DHT は、隠れ場所から来ています。 CNCERT は「DHT は、公開の分散ネットワークに身を隠す予備の制御チャネルから取った」と命名の由来を説明しています（原文中国語）。実際の制御端のアドレスは、①暗号化・符号化された DNS 応答と②公開 P2P ネットワーク（DHT）の2経路で取得され、どちらも真の制御端アドレスを偽装しています。 そのため制御面が固定のドメインや IP に依存せず、検知・遮断・追跡が難しくなります。

CNCERT の評価は「攻撃能力より隠蔽性に工学を注いだ」というものです。「多くのボットネットが工学的な投入を攻撃能力に集中させるのと異なり、VeilDHT は主たる精力を隠蔽性に置いており、機能もより全面的である」「その開発者は専業の暗号工学の素養を備えている」（いずれも原文中国語）。通信は Ed25519・X25519・SHA-512・XChaCha20-Poly1305 を用い、上線時には内蔵の検証用公開鍵で制御端の署名を検証してからセッションを確立します。 CNCERT は「鍵交換の段階で通信を完全に掌握していなければ、事後に傍受した通信データを復号できる可能性はない」と述べています。

機能は揃っています。 UDP・TCP・GRE などにまたがる 20種の DDoS 攻撃、任意コマンド実行、対話型リバースシェル、リバースプロキシ。感染したホストは、攻撃元であると同時に隠蔽された踏み台となり、長期にわたって制御可能な資源になります。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**VeilDHT は、攻撃能力ではなく隠蔽性に工学を注いだボットネットである** （CNCERT の評価。出典1）。 **拡散は既知の脆弱性2件（CVE-2024-3912・CVE-2021-35394）の悪用が主で、 感染後は偽装 DNS 応答と公開 DHT 網の2経路で制御端アドレスを取得し、 認証付き暗号で通信する。** **心拍は周期・内容とも無作為化され、設定は順序を乱した暗号文で保存される。** **以下の各段階は CNCERT の風険提示の記述に基づく。**

  1. 1. 初期侵入確認済[1]
    **拡散は漏洞利用（脆弱性の悪用）が主で、標的は Linux サーバと 各種 IoT 機器である**（出典1）。 **現時点で観測された悪用は2件——CVE-2024-3912（ASUS ルータの コマンドインジェクション）と CVE-2021-35394（Realtek Jungle SDK の コマンドインジェクション）。** **どちらも既知の脆弱性であり、ゼロデイではない**（本記録の整理）。 **Realtek Jungle SDK は多数の機器ベンダーの製品に組み込まれているため、 影響を受ける機種の範囲は本記録では特定できない。**
    根拠: CNCERT の監視と、緑盟科技 伏影実験室による検体解析
  2. 2. C2通信確認済[1]
    **この家族のもっとも際立った特徴である**（出典1）。 **木馬は2つの経路で真の制御端アドレスを取得する—— ①暗号化・符号化された DNS 応答、②公開 P2P（DHT）ネットワーク。 両経路とも真の制御端アドレスを偽装しており、互いに予備となる。** **制御面が固定のドメインや IP に依存しないため、 制御端が長期にわたって隠れることができ、検知・封禁・追跡の難度が高い。** **通信保護は握手・認証・指令伝送の全過程に及び、Ed25519・X25519・ SHA-512・XChaCha20-Poly1305 を使う。上線時に内蔵の検証用公開鍵で 制御端の署名を検証してからセッションを確立する。** **CNCERT は「鍵交換の段階で通信を完全に掌握していなければ、 事後に傍受した通信データを復号できる可能性はない」と述べている。**
    根拠: 緑盟科技 伏影実験室による検体解析
  3. 3. 検知回避確認済[1]
    **通信・心拍・設定の保存・プロセスの動作のすべてに隠蔽処理が施され、 版のローリング更新にも対応している**（出典1）。 **通信**——全過程が暗号化され、途中で傍受されても復元が難しい。 **心拍**——**周期と内容がいずれも無作為**で、 固定の規律に基づく通信検知を回避する。 **設定の保存**——**暗号文で、かつ保存の順序を乱している**ため、 静的解析では完全な設定内容を順に復元できない。 **版のローリング更新**——被害ホスト上で自動的に昇級を完了でき、 制御端は新しい版を押し出して受控節点を長期に掌握できる。
    根拠: 緑盟科技 伏影実験室による検体解析
  4. 4. 影響（暗号化・破壊・改ざん）確認済[1]
    **20種の DDoS 攻撃（UDP・TCP・GRE 等）・任意コマンド実行・ 対話型リバースシェル・リバースプロキシを備える**（出典1）。 **制御端は主機情報の照会、ホストの再起動、木馬の自己削除も指示できる。** **情報収集ではアーキテクチャ・ホスト名・メモリ・プロセス数を送信し、 CNCERT は「後続の横展開や、より的を絞った攻撃のための情報の基礎を 提供する」としている。** **CNCERT の結論——「一旦感染すれば、被害ホストは攻撃元であると同時に 隠蔽された踏み台となり、長期にわたって制御可能な資源になる」。** **実際に DDoS 攻撃が行われたかは公表されていない**〈未確定4〉。
    根拠: 緑盟科技 伏影実験室による検体解析

CNCERT の評価の核心は、工学の投入先が普通と逆だという点にある。

「多くのボットネットが工学的な投入を攻撃能力に集中させるのと異なり、VeilDHT は主たる精力を隠蔽性に置いており、機能もより全面的である。設定は順序を乱した暗号文で保存され、通信は認証付き暗号を採用し、心拍は完全に無作為化されており、発見・遮断・復号・駆除の難度はいずれも明らかに上がっている」（原文中国語）

そして運営者の性格について、こう述べている。

「この家族は現段階では伝播拡張期にあり、その開発者は専業能力を備えた運営団伙で、長期にわたって在線し、隠蔽的で持続的な資源プールを構築する意図がある」（原文中国語）

制御端のアドレスを「偽装 DNS」と「公開 P2P 網」の二重取得にする設計原因・手口出典 [1]

CNCERT が「この家族のもっとも際立った特徴」と呼ぶのは、C&C の寻址（アドレス発見）の仕組みである。

  • 木馬は2つの経路で真の制御端アドレスを取得する
  • ①暗号化・符号化された DNS 応答
  • ②公開 P2P ネットワーク（DHT）
  • 2つの経路はどちらも真の制御端アドレスを偽装しており、互いに予備となる
  • その結果、制御面が固定のドメインや IP に依存しなくなる
  • 「制御端が長期にわたって隠れることを可能にし、検知・封禁・追跡の難度が高い」（原文中国語）

これが IoC の扱いに直接効いてくる。 CNCERT は防範建議の第5項でこう書いている——「掲載したドメインの現在の解決結果は偽装 IP であり、真の制御端は以下の IP による」（原文中国語）。つまり、掲載されたドメインを名前解決して出てきた IP を遮断対象にしてはいけない（本記録の注記）。

通信保護は握手・認証・指令伝送の全過程に及ぶ。

  • 使われる暗号は Ed25519・X25519・SHA-512・XChaCha20-Poly1305
  • 上線時、木馬は内蔵の検証用公開鍵で制御端の署名を検証し、確認できて初めてセッションを確立する
  • その後の主機情報・心拍・指令はすべて暗号化された通路で伝送される
  • 「この体系は現代の暗号工学の規範に厳格に従っており、ボットネットによくある軽量な難読化を遥かに超えている」（原文中国語）
  • 「鍵交換の段階で通信を完全に掌握していなければ、事後に傍受した通信データを復号できる可能性はない」（原文中国語）

検知回避は通信だけではない。

  • 心拍——周期も内容も無作為で、固定の規律に基づく通信検知を回避する
  • 設定の保存——暗号文で、かつ保存の順序を乱しているため、静的解析では完全な設定内容を順に復元できない
  • 版のローリング更新——被害ホスト上で自動的に昇級を完了でき、制御端は新しい版を継続的に押し出して受控節点を長期に掌握できる

拡散に使われているのは2021年と2024年の既知の脆弱性である原因・手口出典 [1]

CNCERT が「当前観測到」（現時点で観測された）として挙げた脆弱性は2件だけである。

識別子 内容

どちらも新しくない。 識別子の年から見て、Realtek のものは2021年、ASUS のものは2024年である。CNCERT の防範建議の第1項が「資産一覧の棚卸しと、歴史漏洞（過去の脆弱性）と最新に露出した脆弱性を含むシステム脆弱性の修復、IoT 機器のファームウェアの同期更新」であることは、未更新の機器が残っていることを前提にした書き方である（本記録の整理）。

とくに Realtek Jungle SDK の脆弱性は影響の範囲が読みにくい。 SDK は多数の機器ベンダーの製品に組み込まれるため、「Realtek 製の機器」を探しても見つからない。自組織のルータ・カメラ・NAS のどれが Jungle SDK を使っているかは、ベンダーの告知を辿らないと分からない（本記録の評価）。

「観測された」という限定にも注意が要る。 CNCERT はこの2件が悪用の全てだとは書いていない〈未確定5〉。あわせて、防範建議の第2項はパスワード強度（16桁以上・機器ごとに別のパスワード・定期変更）に充てられているが、弱いパスワードによる感染が実際に観測されたのかは判別できない〈齟齬1〉。

感染した機器は「攻撃元」「踏み台」「長期の資源」を同時に兼ねる被害規模・影響範囲出典 [1]

VeilDHT の機能は、DDoS 専用のボットネットより広い。

  • 情報収集——被害ホストのアーキテクチャ・ホスト名・メモリ・プロセス数などを収集して送信する。CNCERT は「後続の横展開や、より的を絞った攻撃のための情報の基礎を提供する」と述べている
  • コマンド実行——任意のシステムコマンドを実行でき、ホストの再起動と木馬の自己削除も可能
  • リバースシェル——対話型のリバースシェル通路を確立し、被害ホストを完全に制御する。さらなる攻撃の足場になる
  • リバースプロキシ——ネットワークトラフィックを転送し、被害ホストを攻撃の踏み台として使い、攻撃者の真の出所を隠す
  • DDoS 攻撃——20種の方式、複数プロトコル（UDP・TCP・GRE 等）に対応。攻撃指令は動的に配信でき、指定した標的への精確な打撃を行う

CNCERT の結論はこうである——「一旦感染すれば、被害ホストは攻撃元であると同時に隠蔽された踏み台となり、長期にわたって制御可能な資源になる」（原文中国語）。

実際に DDoS 攻撃が行われたかは公表されていない〈未確定4〉。本記録が読み取れたのは能力の記述までである。

「隠れること」に投資したボットネットは、IoC での防御を前提から崩す（本記録の評価）評価・解釈出典 [1]

ここからは本記録の作成者の評価である。

第一に、この設計は「指標で止める」という防御の前提を崩しにきている。ドメインを遮断すれば止まる、IP を遮断すれば止まる——ボットネット対策の基本はこれだった。VeilDHT は制御端アドレスの取得を偽装 DNS 応答と公開 DHT 網の二重化にし、掲載されたドメインの解決結果すら偽装 IP である。CNCERT がわざわざ「ドメインの解決結果ではなく掲載の IP を見よ」と書いているのは、この罠に防御側が落ちるからである。

第二に、「事後の復号ができない」という性質が、調査の手を縛る。 CNCERT は「鍵交換の段階で通信を完全に掌握していなければ、事後に傍受した通信データを復号できる可能性はない」と明記している。つまり、通信を記録していても、鍵交換を押さえていなければ「何が盗まれたか」「何を指示されたか」は永久に分からない。 インシデント対応で「ログは取ってある」が答えにならない事例である。

第三に、心拍の無作為化は検知のコストを非対称にする。固定周期の通信は、量が少なくても周期性で見つかる。周期も内容も無作為なら、ビーコン検知の特徴量が効かない。防御側は通信の振る舞いではなく通信先で見るしかなくなるが、その通信先が偽装されている——第一の点と噛み合っている。

第四に、日本の読者にとっての実務上の論点は「資産の棚卸し」に尽きる。悪用されているのは2021年と2024年の既知の脆弱性で、とくに Realtek Jungle SDK は多数のベンダー製品に組み込まれている。 「Realtek の機器を探す」では見つからない。自組織のルータ・カメラ・NAS・産業用ゲートウェイについて、ベンダーの告知を辿って Jungle SDK の採用有無とファームウェアの更新状況を確認する——これが具体的な行動である。

第五に、感染した機器が「攻撃元」であると同時に「踏み台」になることを忘れないこと。 自組織の IoT 機器が感染した場合、被害は自組織の情報漏えいではなく、自組織の回線から他者への攻撃が出ていくことである。 リバースプロキシの機能がある以上、自組織の IP アドレスが他者の侵害の出所として記録される。 これは法的・契約的な責任の問題になりうる（本記録の評価）。

CNCERT が、感染規模（累計40,467台・日次最大上線15,805台）・ 悪用された CVE 2件・通信機構・暗号アルゴリズム・機能・対抗設計・ IoC 25点・防範建議6項を公表した一方、**活動の開始時期・国外の感染状況・ 運営者の帰属・実際の攻撃の有無は示さなかった**機能した**本記録の作成者の評価である。** **技術記述の水準は高い**——暗号アルゴリズム名まで挙げ、 **「掲載ドメインの解決結果は偽装 IP だから掲載の IP を見よ」という 但し書きまで付けている。** 防御側が誤った遮断をしないための配慮であり、 指標を出すだけの警告より実用的である。 **一方、活動の開始時期が無いため「11日で4万台」なのか 「長期に積み上がった4万台」なのかが読者に判断できない**〈未確定2〉。 **また国外の感染状況が無いため、日本を含む他国の読者は 自国の状況を推し量れない**〈未確定1〉。

CISO・経営層への示唆
  • IoT 機器・ネットワーク機器の資産一覧を、「台数」ではなく 「機種・ファームウェア版・サポート期限」で持つ
    悪用されているのは2021年と2024年の既知の脆弱性で、 ファームウェアを更新していれば塞がる性質のものだった
    取るべき行動 ルータ・カメラ・NAS・産業用ゲートウェイについて、 **機種・ファームウェア版・サポート終了日**を台帳化する。 **サポート終了機器を「交換対象」として予算計画に乗せる** ——棚卸しだけして予算を付けないと一覧が放置される
  • 自組織の機器が「踏み台」になるリスクを、情報漏えいとは別の項目として リスク評価に入れる
    VeilDHT はリバースプロキシの機能を持ち、 CNCERT は「被害ホストは攻撃元であると同時に隠蔽された踏み台になる」と 述べている。**自組織の IP アドレスが他者の侵害の出所として記録される**
    取るべき行動 リスク登録簿に「自組織の回線・IP アドレスが他者への攻撃に使われる」 という項目を立て、**自組織の IP が攻撃元として外部から報告された場合の 受付窓口と初動手順**を定める。契約・約款上の責任範囲も法務と確認する
  • 「ログは取ってある」が答えにならない攻撃があることを前提に、 調査能力への期待値を下げる
    CNCERT は「鍵交換の段階で通信を完全に掌握していなければ、 事後に傍受した通信データを復号できる可能性はない」と明記している
    取るべき行動 インシデント対応計画で、**「通信内容が復元できない場合に、 何をもって影響範囲を判断するか」**をあらかじめ決める。 通信の中身ではなく、接続先・データ量・時刻・機器の挙動から 判断する手順を書いておく
  • サプライチェーンの脆弱性は「製品名」ではなく「組み込み部品」で追う
    CVE-2021-35394 は Realtek Jungle SDK の脆弱性であり、 同 SDK は多数の機器ベンダーの製品に組み込まれている。 **「Realtek の機器」を探しても見つからない**
    取るべき行動 調達の要件に「組み込みチップセット・SDK の開示」を加え、 既存機器についてはベンダーの告知を辿って該当の有無を確認する手順を作る。 **確認できない機器は「不明」として台帳に残す**
セキュリティ技術者への示唆
  • IoT 機器・サーバの外向き通信を、宛先とポートの許可リストで限定する
    制御端アドレスは偽装 DNS 応答と公開 DHT 網の2経路で取得され、 固定のドメインや IP に依存しない。**宛先ベースの遮断が効きにくい**
    取るべき行動 **IoT 機器は通信先が少ないため、許可リストが現実的である。** 機器ごとに必要な宛先（ベンダーの更新サーバ・NTP・自組織の収集基盤）を 洗い出し、それ以外の外向き通信を遮断する。 **業務上不要なら P2P（BitTorrent DHT 等）の通信を既定で落とす**
  • 外向き DNS を自組織のリゾルバに強制し、機器からの直接の DNS を禁止する
    C&C アドレスの取得経路の一つが「暗号化・符号化された DNS 応答」である。 機器が外部の DNS を直接引けると、問い合わせ自体が見えない
    取るべき行動 機器セグメントから 53/udp・53/tcp の外向きを遮断し、 自組織のリゾルバ経由に強制する。**DoH/DoT も遮断対象に含める。** リゾルバのログで掲載ドメインへの問い合わせを検知する
  • IoC のドメインは「名前解決の結果」ではなく「ドメイン名そのもの」で扱う
    CNCERT は「掲載したドメインの現在の解決結果は偽装 IP であり、 真の制御端は掲載の IP による」と明記している。 **解決結果を遮断対象にすると無関係の宛先を止めかねない**
    取るべき行動 脅威情報の取り込み手順で、**ドメインは DNS フィルタに（名前のまま）、 IP は通信遮断に、と経路を分ける。** **ドメインを自動で名前解決して IP ブロックリストへ流し込む実装を 使っている場合は、本件で誤遮断が起きないか確認する**
  • ビーコン検知（固定周期の通信の検出）に依存した監視を見直す
    VeilDHT の心拍は周期も内容も無作為化されており、 固定の規律に基づく通信検知を回避する設計である
    取るべき行動 周期性以外の特徴（宛先の新規性・機器の役割に合わない通信・ 通信量の分布）でも検知できるようにする。 **「ビーコンが出ないから感染していない」という判断を手順書から外す**
  • 感染機器の駆除より先に証拠保全を挟む手順を書く
    木馬は自己削除の機能を持ち、設定は順序を乱した暗号文で保存されている。 **駆除を急ぐと侵入経路の特定に要る証跡が失われる**
    取るべき行動 IoT 機器・サーバの感染を疑った時点で、**まずネットワークから隔離 （電源は切らない）**し、メモリと通信記録を保全してから駆除する手順を 定める。**ファームウェアの再書き込みは証跡を消す**ことを明記する
