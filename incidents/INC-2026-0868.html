INC-2026-0868cPGuard 更新配信が乗っ取られ偽更新を配布

Linux サーバ向けセキュリティ製品 cPGuard の開発元 OPSSHIELD が2026年11月3日、 **自社の課金・ライセンスサーバを侵害され、盗まれた公開用キーで 偽の cPGuard 更新を配信された**と公表した。 **偽更新は約70分間配られ、約2,950台の顧客サーバで root 権限で実行されて /etc/shadow・root の SSH 秘密鍵・MySQL root パスワード・root のシェル履歴を 攻撃者のサーバへ送った**。課金ポータルの約7,900件の顧客レコードも複製された。 **侵入は攻撃者自身が無料試用を申し込んだ顧客アカウントから始まっている。**

初報: 2026年11月3日（OPSSHIELD のセキュリティインシデント開示） 最終更新: 2026年11月4日

自社製品の更新チャネルが、そのまま root 権限の実行経路になりました。 Linux サーバ向けのセキュリティ製品 cPGuard を開発する OPSSHIELD は2026年11月3日、課金・ライセンスサーバを侵害され、盗まれたキーで偽の cPGuard 更新を顧客サーバへ配信されたと公表しました（出典1・原文英語）。

配信された時間は約70分です（2026年11月2日 02:08〜03:20 UTC。出典1）。その間に更新を受け取った約2,950台の顧客サーバで、スクリプトが root 権限で動き、以下を攻撃者のサーバへ送りました（出典1）。

  • /etc/shadow と /etc/passwd（ローカルのパスワードハッシュ）
  • /root/.ssh（root の SSH 秘密鍵・authorized_keys・known_hosts）
  • /root/.my.cnf（MySQL の root パスワード）
  • root のシェル履歴（打ち込んだパスワードやトークンが残っていることが多い）
  • /root/.s3cfg（一部のサーバでクラウドストレージのキー）

この一覧が意味するのは、該当サーバの root 権限の秘密が全部もう相手の手にある、ということです（本記録の評価）。OPSSHIELD 自身も「11月2日 02:08〜03:20 UTC に cPGuard が稼働していたなら、そのサーバの root レベルの秘密は攻撃者に知られていると考えてください」と書いています（出典1・原文英語）。

侵入の始まりは、攻撃者自身が申し込んだ無料試用です（出典1）。11月1日15:38 に課金ポータルを探り始め、16:34 に偽名で顧客登録して試用を申し込み、21:17 に自分のサーバへ入れて挙動を調べ、22:58 に課金サーバでコマンド実行に到達、翌02:04 に偽更新を公開用ストレージへ上げています（出典1）。興味深いのは、その途中（11月1日 21:40〜21:51）に cPGuard 自身が攻撃者を2回ブロックしている点です（出典1）。製品は気づいていたが、一時 BAN が nftables のファイアウォールでは強制されていなかったため、止まらなかった——OPSSHIELD は是正項目としてこの点を挙げています（出典1）。

課金ポータル側でも約7,900件の顧客レコード（氏名・会社名・住所・メールアドレス・ハッシュ化されたパスワード）が複製されました（出典1）。パスワードは bcrypt ハッシュで平文ではないとしています（出典1）。

**一次公表が段階ごとの時刻つきで経過を開示しているため、 以下は公表されたタイムラインの整理である**（出典1）。 **要点は「製品の顧客として正面から入り、課金アプリの欠陥で実行権限を取り、 更新配信のキーを盗んで、製品の正規の更新経路で root 実行を得た」という 4手である**（本記録の整理）。

70分の配信で、約2,950台の root 権限の秘密が相手の手に渡った被害規模・影響範囲出典 [1] [2]

影響の重さは、持ち出されたファイルの一覧を見れば分かります（出典1）。

  • /etc/shadow・/etc/passwd — ローカルユーザーのパスワードハッシュ
  • /root/.ssh — root の SSH 秘密鍵・authorized_keys・known_hosts
  • /root/.my.cnf — MySQL の root パスワード
  • root のシェル履歴 — 打ち込んだパスワードやトークンが残っていることが多い
  • /root/.s3cfg — 一部のサーバでクラウドストレージのキー

OPSSHIELD 自身の言葉はこうです。 「2026年11月2日 02:08〜03:20 UTC の間に cPGuard が導入されオンラインだったサーバについては、その root レベルの秘密は攻撃者に知られていると考えてください」（出典1・原文英語）。

該当は約2,950台（出典1。BleepingComputer への回答では2,946台〈差異1〉）。配信が実行されていた時間は約72分です（02:08〜03:20。本記録の算出）。

加えて、OPSSHIELD 側の課金ポータルの顧客レコード約7,900件（氏名・会社名・郵送先住所・メールアドレス・パスワードハッシュ）が複製されました（出典1）。パスワードは bcrypt ハッシュで平文ではないとしています（出典1）。

本記録として強調したいのは、/root/.ssh の流出が「そのサーバ1台の問題」で終わらないことです（本記録の評価）。秘密鍵と known_hosts と authorized_keys が同時に出ているため、攻撃者には「どの鍵でどこへ行けるか」の地図が渡っています。一次公表も「このサーバから SSH で到達できる他のサーバも、鍵を差し替えるまで露出扱いにせよ」と書いています（出典1）。

この表の4行目が、本件で最も実務的な教訓です（本記録の評価）。自社製品が攻撃者を検知し、2回ブロックしていました。それでも攻撃は止まりませんでした。理由は OPSSHIELD が是正項目として自ら書いています—— 「一時 BAN が nftables のファイアウォールで強制されるよう cPGuard を修正する」（出典1）。検知は鳴っていた。遮断が効いていなかった（本記録の整理）。

そして、悪用された欠陥そのものは特定できていません〈未確定1〉。「当社のログは、攻撃者にアクセスを与えた正確な要求を記録していない。そのため該当コードを見直し、見つかった2つの侵入口候補に修正を当て、関連するベンダー製コンポーネントを1行ずつ検証している」（出典1・原文英語）。SSH・コントロールパネル・FTP・API トークンの経路は除外されています（出典1）。

課金サーバの実行権限が、更新配信の鍵に届いていた評価・解釈出典 [1]

本件の構造的な問題は1つです。 課金・ライセンスサーバでコマンドを実行できた攻撃者が、そのまま「更新を公開するために使っているキー」を持ち出せたことです（出典1）。

更新を配る権限は、顧客環境における root 実行の権利と同じです（本記録の評価）。cPGuard のエージェントは root で動き、取得した更新を検証せずに実行しました。つまり、課金アプリ1つの欠陥が、約2,950台の root に直結しました。

この連鎖を切る場所は2つあります（本記録の判断）。

  1. 配信側 — 署名・公開に使う鍵を、課金や顧客管理の系から到達できない別のアカウント・別ネットワークに置く。成果物の公開に二人承認とハッシュの事前登録を要求する。
  2. 受信側 — エージェントが、配信経路とは独立した署名を検証してから実行する。検証に失敗した成果物は実行しない。

受信側の対策は、顧客が自分で選べないことが多い点に注意が要ります（本記録の評価）。自動更新を持つエージェントを root で動かすという決定は、「このベンダーの鍵の管理を信用する」という決定と同じです。調達時にベンダーへ確認すべきは、更新成果物の署名の有無と、署名鍵の分離の方法です。

対応は速く、開示は厚い——自社に不利な事実まで出した組織の対応出典 [1] [2]

封じ込めは同日中です（出典1）。偽更新の実行は約72分で止まり、盗まれた更新用キーを失効、クラウドの API トークンとアクセスキーを全て失効、攻撃者の SSH 鍵・複製サーバ・スナップショットを削除、自社サーバの SSH 鍵とパスワードを全て差し替え、cPGuard のライセンス鍵の再発行を開始、課金ポータルの全セッションをリセット——と並んでいます（出典1）。

公表の厚みは、この種の事案では例外的です（本記録の評価）。分単位のタイムライン、影響件数の表、顧客が取るべき7手順、そして IoC（操作元 IP・偽更新スクリプト4点の SHA-256・残存ファイルのパス・Web シェルの名前） までを1ページに置いています（出典1）。

  • ログに侵入要求が残っていない（侵入口が特定できていない）

CISO・経営層への示唆
  • 自社製品の更新チャネルは、顧客環境における root 実行の権利である
    **本件では約2,950台の顧客サーバで、正規の更新経路を通じて スクリプトが root 権限で実行された**（出典1）。 **更新を配る権限は、顧客環境の最高権限とほぼ等価である**（本記録の評価）。
    取るべき行動 **自社が顧客環境へ配信している更新・エージェント・スクリプトを棚卸しし、 それぞれの実行権限を書き出す。root 相当のものは、 配信に二人承認と署名検証を要求する対象として経営レベルで管理する。**
  • 更新の署名鍵を、顧客管理・課金の系から到達できる場所に置かない
    **攻撃者は課金・ライセンスサーバで実行権限を取り、 そこから更新公開用のキーを持ち出した**（出典1）。 **1つのアプリの欠陥が、顧客全台の root に直結した**（本記録の評価）。
    取るべき行動 **署名・公開に使う鍵を別アカウント・別ネットワークへ分離し、 HSM または短命の発行手続きに寄せる。 「課金サーバが落ちたら顧客全台が危ないか」を自社で図に書いて確認する。**
  • 検知が鳴っても、遮断が効いていなければ意味がない
    **cPGuard は攻撃者を2回 BAN したが、一時 BAN が nftables 環境で 強制されていなかった**（出典1）。 **「検知できている」という報告は、遮断の実効性を保証しない**（本記録の評価）。
    取るべき行動 **ブロック機能について、本番で使われている全ての実装・構成で 実際に通信が止まるかを定期試験の項目にする。 自社製品であれば、顧客環境の構成差分ごとに検証する。**
  • 不利な事実を自分から書くことが、顧客の行動を引き出す
    **本件の公表は、ログに侵入要求が残っていないこと・自社内部サーバにも インプラントが残っていたこと・影響件数を自ら開示した**（出典1）。 **そのうえで「所要はサーバあたり1時間未満」「無償で手伝う」と 実行の障壁を下げている**（出典1）。
    取るべき行動 **公表文の様式に「分かっていないこと」の欄と「所要時間の見積もり」 「支援窓口」の欄を置く。顧客に作業を求める公表では、 手順・所要・支援の3点を必ず揃える。**
セキュリティ技術者への示唆
  • 更新の取得と実行を分け、署名検証に失敗したら実行しない
    **顧客側では、正規のチャネルから来た正規製品の更新であり、 内容の悪性を見分ける手掛かりがほとんど無かった**（本記録の評価）。 **配信経路の信頼だけに依存する作りだと、鍵を盗まれた瞬間に全台が落ちる** （本記録の判断）。
    取るべき行動 **エージェントの更新処理に、配信元とは独立した署名の検証を入れる。 検証に失敗した成果物は実行せず、警告を上げて停止する実装にする。**
  • サーバからの外向き通信を既定で拒否にする
    **窃取は、収集したファイルを攻撃者のサーバへ送ることで成立した**（出典1）。 **egress を白名簿にしていれば、スクリプトは読めても送れない**（本記録の判断）。
    取るべき行動 **本番サーバの外向き通信を既定拒否にし、 更新・監視・バックアップの宛先だけを許可する。 許可リストの作成は、いま出ている通信先の記録から始める。**
  • root の秘密をサーバ上の平文ファイルに置かない
    **持ち出されたのは /root/.ssh の秘密鍵・/root/.my.cnf の MySQL root パスワード・ root のシェル履歴・/root/.s3cfg のクラウドキーである**（出典1）。 **いずれもサーバ上に平文で置かれるのが「普通」とされてきたファイルである** （本記録の評価）。
    取るべき行動 **①root の SSH 秘密鍵をサーバに置かず、踏み台と証明書ベースの短命認証に移す ②MySQL はソケット認証または秘密情報管理から注入する ③シェル履歴に秘密が残らないよう、対話でのパスワード入力をやめる ④クラウドキーはインスタンスロール等の動的な資格情報に置き換える。**
  • known_hosts と authorized_keys の流出は、横展開の地図の流出である
    **一次公表は「このサーバから SSH で到達できる他のサーバも、 鍵を差し替えるまで露出扱いにせよ」と明記している**（出典1）。 **鍵と到達先の一覧が同時に出ているため、次の標的が分かる状態である** （本記録の評価）。
    取るべき行動 **侵害されたサーバを起点に、その鍵を信頼している全サーバを機械的に 列挙する手順（authorized_keys の横断検索）を用意し、 鍵の差し替えを一括で実行できるようにしておく。**
  • /var/tmp の setuid バイナリと /etc/cron.d の新規ファイルを即時アラートにする
    **顧客サーバに残されたのは、/var/tmp/.cpg91511_sh（setuid root のシェル）・ /var/tmp/.i93677/・/etc/cron.d/i93677 である**（出典1）。 **いずれも一般的な完全性監視の対象にできる**（本記録の判断）。
    取るべき行動 **setuid ビットの新規付与、/etc/cron.d・/etc/profile.d 配下の変更、 /var/tmp 配下の実行可能ファイルの出現を監視対象に加え、 検知時は即時にアラートを上げる。**
