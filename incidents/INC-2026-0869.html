INC-2026-0869mSecure が全利用者に鍵の作り直しを要請

パスワード管理アプリ mSecure の開発元 mSeven Software が2026年11月3日、 利用者へ**「mSecure に関連する不審な活動を認知した」とだけ伝えるメールを送り、 保管している全ての機密情報の保護措置——パスワードの変更・2要素認証の再設定・ パスキーの削除——を直ちに取るよう求めた**。 **何が起きたのか、いつか、顧客データに到達されたのかは一切示されておらず、 公式サイトにも告知ページが存在しない**。 **利用者は、数百件の資格情報を全部やり直すべきかを判断できない状態に置かれている。**

不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年11月3日（The Register の報道。mSeven から利用者へのメールは同日） 最終更新: 2026年11月4日

これは「何が起きたか分からないまま、利用者に最も重い作業を求めた」事案です。パスワード管理アプリ mSecure を開発する米 mSeven Software は2026年11月3日、利用者へメールを送りました（出典1・原文英語）。

「mSeven Software は最近、mSecure パスワード管理アプリケーションに関連する不審な活動を認知しました。これを受けて mSeven は速やかに調査を開始し、問題を緩和する措置を取り、支援のため外部のサイバーセキュリティ専門家を起用しました」（出典1・原文英語）。

「潜在的なセキュリティ上の影響を踏まえ、mSeven は、mSecure パスワード管理アプリケーション内に保管されている全ての機密情報を保護する措置を直ちに取ることを推奨します。これにはパスワードの変更、2要素認証の方式の再設定または再登録、既存のパスキーの削除が含まれ得ます」（出典1・原文英語）。

求められている作業の量を具体的に考えると、この公表の問題が見えます（本記録の評価）。The Register が伝えた利用者の声には、「mSecure に800件以上のパスワードが入っている。このメールは全部変えろと言っているのか」というものがあります（出典1）。500件以上を保管している別の利用者は、警告が保管している全てのアカウントの2要素認証とパスキーを指すのか、それとも mSecure 自身へのログインだけを指すのかを尋ねています（出典1）。

どちらなのかは、公表に書かれていません〈未確定2〉。

そして、公表は「何が起きたか」に触れていません（出典1・2）。不審な活動の内容・発生時期・顧客情報に到達されたかどうか・影響した利用者数——いずれも示されていません（本記録の確認）。本記録の作成時点で、mSeven の公式サイトにも告知ページは見つかりません〈差異1〉（本記録の確認）。

パスワード管理は、事業の中身が「他人の秘密を預かること」です（本記録の評価）。その事業者が、何が起きたかを言わずに「中身を全部作り直してください」と言う形になっており、利用者はどの資格情報が危ないのかを判定できません。

「全部やり直してください」の作業量を、公表は見積もっていない被害規模・影響範囲出典 [1]

この公表の実務的な問題は、求められた作業の量です（本記録の評価）。

The Register が引用した利用者の投稿（出典1・原文英語）。

  • 「私は mSecure に800件以上のパスワードを入れている。このメールは、それを全部変えろと言っているのか」

  • 「『措置を取ってください』という曖昧な助言は受け入れられない。どの対処が必要で、どのデータが侵害されたのかを明示してほしい」

範囲が決まらないと、作業量は数十分から数十時間まで変わります（本記録の評価）。そして、何が危ないのか分からないため、利用者は優先順位も付けられません。

本記録の判断として、利用者が現実的に取れる順序は次のとおりです。

  1. メールアドレスと携帯電話番号 — 他の資格情報の再発行の起点になる
  2. 金融・決済・暗号資産 — 金銭に直結する
  3. 管理者権限を持つ業務アカウント — 組織へ波及する
  4. 残り

全件を一度にやり直すのは現実的ではないため、波及の大きい順に進めるのが安全です（本記録の判断）。

「設計上は我々も見られない」は、事故時の回答にならない評価・解釈出典 [1] [3]

mSecure はサポート資料で、平時の設計をこう説明しています（出典3・原文英語）。データは端末側で暗号化されてからサーバへ同期され、仮にシステムが利用者の情報にアクセスできる作りであればそれ自体が弱点になる、という趣旨です。 サインインのたびに利用者へメール通知が届く仕組みも説明されています（出典3）。

しかし本件のメールは、その設計が今回も有効だったかに触れていません（本記録の確認）。金庫のデータに到達されたのか、金庫を守る鍵に到達されたのか、それとも別の構成要素（アカウント基盤・配信・社内系）だったのか——どれも示されていません〈未確定4〉。

本記録の評価として、ここが預かり型サービスの難しさです。 平時の「我々も中身は見られません」という説明は、設計の説明であって、事故の説明ではありません。 事故時に必要なのは「設計上どこまでは影響が及ばないと言えて、どこからが調査中なのか」という切り分けです。

その切り分けを事故後に書き始めると、曖昧になります（本記録の判断）。あらかじめ、自社が預かっているものについて「どの系が侵害されたら何が危ないか」を文章にしておく必要があります。

公式サイトに告知が無いことは、それ自体が危険である組織の対応出典 [1]

メールだけで通知し、公式サイトに同じ文面を置かない形は、パスワード管理の事業者としては危険です（本記録の評価）。

理由は単純です。 「資格情報を作り直してください」という文面は、フィッシングに最も転用しやすい形だからです。利用者が受け取ったメールの真正性を確かめようとしても、公式サイトに同じ告知が無ければ、確かめる先がありません〈差異1〉。

The Register は、利用者が通知の写しを Reddit で共有し、何が起きたのかを互いに尋ね合っている状況を伝えています（出典1）。この状態は、本物の通知を装う偽メールが紛れ込む余地を作ります（本記録の評価）。

対策は、費用のかからない1点です（本記録の判断）。利用者へ送る注意喚起と同じ文面を、自社サイトの固定 URL に置き、メール本文からその URL を参照させる。 本件では、それが行われていません。
