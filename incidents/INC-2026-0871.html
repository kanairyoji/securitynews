INC-2026-0871Hugging Face で偽Qwen2 31件

セキュリティ企業 Pluto Security は2026年10月29日、 **AI モデル共有プラットフォーム Hugging Face 上で、小さな Qwen2 の検証用モデinsertを装った 悪性リポジトリ31件（7アカウント）が、暗号資産マイニングプログラムと裏口を配布していた**と公表した。 **悪用されたのはモデルの重みではなく、`config.json` の `auto_map` が指す Python コードであり、 利用者が `trust_remote_code=True` を指定すると、重みの読み込み前に 呼び出し側の権限でそのコードが実行される**（出典1）。 **第1波（2026年9月21日〜10月12日・12リポジトリ）を Pluto が Hugging Face と ModelScope に通報し、 アカウントは削除されたが、数日のうちに5つの新アカウントで第2波（19リポジトリ）が展開された**（出典1）。 **第2波はハードコードされた SSH 鍵をリバースシェルに替え、 コンテナから権限のあるホストへ出るスクリプトを加えている**（出典1）。 **ダウンロードはキャンペーン合計29,818回、関連モデルを含めて32,376回（いずれも2026年10月28日時点）**だが、 **これは配布の広さであって感染台数ではない**（出典1。整理は本記録）。 **狙われたのは自己ホスト型の推論基盤——とくに Xinference と GPUStack を使う GPU ホスト、 レンタル GPU、共有の研究用ノートブック、検証用の小さなモデルを取得する CI ジョブである**（出典1）。 **被害組織・感染台数・攻撃主体はいずれも公表されていない。** **Hugging Face と ModelScope 自身の公表は、本記録の探索では見つかっていない。**

セキュリティ企業 Pluto Security は2026年10月29日、Hugging Face 上で小さな Qwen2 検証用モデルを装った悪性リポジトリ31件（7アカウント）が、暗号資産マイニングプログラムと裏口を配布していたと公表しました（出典1）。台湾の iThome が2026年11月3日にこれを報じています（出典2）。

手口の中心は、脆弱性ではなく1つのフラグです（出典1）。一部の AI モデルは読み込みにリポジトリ内の自前の Python コードを要し、利用者が trust_remote_code=True を指定すると、config.json の auto_map が指すモジュールが読み込まれ、Transformers の get_class_in_module() がその最上位コードを実行します。 実行は呼び出し側の権限で行われ、モデルの重みが読み込まれる前に起きます—— 重みを汚す必要も、直列化形式の脆弱性を突く必要もありません。

Pluto の通報を受けて Hugging Face と ModelScope は第1波のアカウントを削除しましたが、数日のうちに5つの新アカウントで第2波（19リポジトリ）が立ち上がりました（出典1）。第2波は、ハードコードされた SSH 鍵をリバースシェルに替え、第2段階のペイロードを送信元 IP で制限し、コンテナから権限のあるホストへ出るスクリプトを加えています（出典1）。

本件で読者が持ち帰るべき点は、金額ではありません（本記録の評価）。第1波のマイニング収益は約5,000ドル相当にとどまります（出典1）—— それでも成り立つのは、計算資源が他人の財布で動いているからです。 ①「公式のプラットフォームから取った」は安全の根拠になりません—— 走査は既知のマルウェアと危険な直列化形式を見るもので、Python コードが何をするかは見ません（出典1）。②削除は対策になりません—— 同じ攻撃者が数日で新しいアカウントに戻ってきています。 ③読むべき対象は auto_map が指すファイル1つです—— これは機械にやらせる前に、人が1回読める量です（本記録の評価）。

被害組織・感染台数・攻撃主体はいずれも公表されていません。Hugging Face と ModelScope 自身の公表も、本記録の探索では見つかっていません〈未確定1・4〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件の攻撃は、脆弱性の悪用ではなく「仕様どおりの実行」から始まる**（出典1）—— **`trust_remote_code=True` を指定した利用者が悪性リポジトリを読み込むと、 `auto_map` が指す Python コードが呼び出し側の権限で実行される。** **以下の各段階は Pluto の報告に基づく。** **被害組織側のログに基づく経路は公表されていないため、 ここに書くのは配布側の手口である**（本記録の明示）。

  1. 1. 初期侵入確認済[1]
    **小さな Qwen2 検証用モデルを装った悪性リポジトリを、 Hugging Face（7アカウント）と ModelScope（1アカウント）に公開した**（出典1）。 **標的は自己ホスト型の推論基盤（Xinference・GPUStack）、 レンタル GPU、共有の研究用ノートブック、 検証用の小さなモデルを取得する CI ジョブである**（出典1）。
    根拠: Pluto Security の報告（31リポジトリ・7アカウント・2026年9月21日〜）
  2. 2. 実行確認済[1]
    **`config.json` の `auto_map` が指すモジュールが読み込まれ、 Transformers の `get_class_in_module()` がその最上位コードを実行した**（出典1）。 **実行は呼び出し側の権限で、モデルの重みの読み込み前に起きる**（出典1）—— **重みの汚染も直列化形式の脆弱性も使われていない。**
    根拠: Pluto の報告（`auto_map` → `get_class_in_module()` の経路の記述）
  3. 3. 永続化確認済[1]
    **第1波はハードコードされた SSH 鍵を置いた**（出典1）。 **Pluto は、永続化の除去対象としてシェル起動ファイル・cron・ `authorized_keys`・モデル登録を挙げている**（出典1）。
    根拠: Pluto の報告（第1波の SSH 鍵、除去手順の記述）
  4. 4. C2通信確認済[1]
    **第2波は SSH 鍵に代えてリバースシェルを使った**（出典1）—— **攻撃者側から入るのではなく、侵害したホストから外へ接続させる形である。**
    根拠: Pluto の報告（第2波の変化の記述）
  5. 5. 検知回避確認済[1]
    **第2段階のペイロードの配布を送信元 IP で制限し、 許可されていないアクセスには 403 と「static ip.」を返した**（出典1。2026年10月21日時点）。 **通報による削除後も、新しいアカウントで同じ内容を再公開している**（出典1）。
    根拠: Pluto の報告（403 と「static ip.」の記述、第2波の再展開）
  6. 6. 権限昇格確認済[1] [2]
    **第2波はコンテナから権限のあるホストへ脱出するスクリプトを備えた （`MENXIANGYU/qa-whl-1021`）**（出典1）—— **GPUStack の `/var/lib/gpustack` を狙う。** **iThome も「容器逃逸程式」として同じ点を報じている**（出典2）。
    根拠: Pluto の報告（コンテナ脱出スクリプトとその標的パス）

    根拠: オンチェーンのウォレット記録と、マイニングプールへの接続の観測

重みは汚染されていない——走ったのは `config.json` が指した Python コードだった原因・手口出典 [1]

本件の成立に、モデルの重みの汚染も直列化形式の脆弱性も要らない（出典1）。

仕組みは Pluto の報告に沿うと次の順で動く（出典1。整理は本記録）。①利用者が trust_remote_code=True を指定してモデルを読み込む。 ②config.json の auto_map が、リポジトリ内のモジュールとクラスを指す。 ③Transformers の get_class_in_module() がそのモジュールを読み込み、最上位のコードを実行する。 ④実行は呼び出し側の権限で、モデルの重みが読み込まれる前に起きる。

つまり攻撃者が用意したのは「悪いモデル」ではなく「悪いローダー」である（本記録の整理）—— モデルの中身を検査する道具は、ここを見ない。 Pluto は、Hugging Face の走査と提携スキャナが既知のマルウェアと危険なモデル形式を対象としており、Python コードの挙動は対象でないことを指摘し、ローダーのファイルが各スキャナで「クリーン」と判定されたことを示している（出典1）。

Hugging Face のセキュリティ方針自身が、このフラグを使うときはモデリングファイルの内容を必ず確認するよう求めている（出典1）—— 仕様は「読んでから使え」と言っており、運用がそれを省いたという構図である（本記録の評価）。

31リポジトリ・29,818ダウンロード——数字が示すのは配布の広さで、感染台数ではない被害規模・影響範囲出典 [1] [2]

公表されている数値は次のとおりである（出典1。2026年10月28日時点）。

①悪性リポジトリ31件（第1波12件・第2波19件）。 ②Hugging Face の7アカウント（第1波2・第2波5）、加えて ModelScope の1アカウント（wssb123e）。 ③ダウンロードはキャンペーン合計29,818回（第1波728回・第2波29,090回）、関連モデル13件を含めて32,376回。

Pluto は「ダウンロード数は感染台数でも固有の被害者数でもない」と明記している（出典1。本記録が訳した）—— 本記録はこの但し書きを重く扱う。 同じ人が複数回取得することも、CI が自動で取得することもあり、逆に1回の取得が共有ホストで複数の利用者に影響することもある（本記録の整理）。

被害組織は1件も公表されていない〈未確定1〉—— したがって「どの業種が・どの国で・何台」は本記録には書けない。 代わりに書けるのは標的の性質である（出典1）—— 自己ホスト型の推論基盤（とくに Xinference と GPUStack）、レンタル GPU、共有の研究用ノートブック、検証用の小さなモデルを取得する CI ジョブ。 いずれも「GPU があり、外部からモデルを取る」環境である（本記録の整理）。

削除は対策にならなかった——通報の数日後に、5つの新アカウントで19リポジトリが戻った組織の対応出典 [1] [2]

第1波の通報後、Hugging Face と ModelScope は関連アカウントを削除した（出典1）。しかし数日のうちに、5つの新アカウントで19リポジトリの第2波が展開された（出典1・2）。さらに第2波の一部は、通報から8日が経った2026年10月28日時点でも公開されたままだった（出典1）。

ここから読み取れるのは、プラットフォーム側の削除が防御の中心に置けないという構造である（本記録の評価）—— アカウントの作成に費用がかからない場所では、削除は攻撃者にとって「やり直し」でしかない。 一方で利用者側の防御（auto_map の先のコードを読む・リビジョンを固定する・権限と秘密情報を与えない）は、アカウントが何個増えても効き続ける（本記録の評価）。

Hugging Face と ModelScope 自身の公表は、本記録の探索では見つかっていない〈未確定4・齟齬3〉—— 削除の事実も、削除までに要した時間も、再発を防ぐ措置の有無も、プラットフォーム側からは語られていない。

第2波は SSH 鍵をリバースシェルに替え、コンテナからホストへ出る道を足した原因・手口出典 [1] [2]

第1波と第2波の差は、攻撃者が何を学んだかを示している（出典1。整理は本記録）。

①永続化の手段を替えた。 第1波はハードコードされた SSH 鍵を置いていたが、第2波はリバースシェルを使う（出典1）—— 鍵の文字列は侵害指標として共有されやすく、第2波はそれを捨てている（本記録の評価）。

②第2段階を隠した。 ペイロードの配布を送信元 IP で制限し、許可されていないアクセスには 403 と「static ip.」を返す（出典1。2026年10月21日時点）—— 解析側が同じ URL を叩いても中身が取れない。

③ホストへ出る道を加えた。 コンテナから権限のあるホストへ脱出するスクリプトが置かれ（MENXIANGYU/qa-whl-1021）、GPUStack の /var/lib/gpustack を狙う（出典1）。iThome も「新增容器逃逸程式」として同じ点を報じている（出典2）。

コンテナで隔離したつもりの環境が、特権付きで動いていれば隔離になっていないという、AI 推論基盤に限らない論点である（本記録の評価）。

稼いだのは約5,000ドル——割に合わない額が、他人の計算資源では成り立つ評価・解釈出典 [1] [2]

第1波のマイニングウォレットに入ったのは約2,276 PRL、当時の換算で約5,000ドル相当である（出典1・2）。調査時点で稼働していた2台のワーカーの直近30日ぶんの報酬は約1,008 PRL（約2,237ドル）（出典1）。

この額は、A100 クラスの GPU を自前で借りて同じ計算を回す費用に遠く及ばない（本記録の評価）—— 成り立つのは、費用を払っているのが被害者側だからである。 被害者から見た損失は、盗まれた暗号資産ではなく①クラウド・GPU の請求 ②研究や CI の処理能力 ③裏口が残った端末である（本記録の整理）。

そして裏口が残るという点で、本件はマイニングで終わらない（本記録の評価）—— 第2波はリバースシェルとコンテナ脱出を備えており、Pluto は「このフラグを有効にしてこれらのモデルを読み込んだなら、その機器は侵害されたものとして扱い、到達できる資格情報をローテーションせよ」と勧めている（出典1。本記録が訳した）。マイニングは、到達できたことの副産物として見るべきものである。

対策はコードを読むことに戻る——`auto_map` の先の1ファイルと、固定したリビジョン対策・注意喚起出典 [1]

Pluto が示した手順は、新しい道具を要しない（出典1。本記録が訳して整理した）。

①確認する。 侵害指標は /tmp/.cch/、svc.py プロセス、[kworker/u20:1]。②隔離し、消す前に証拠を保全する（プロセス・接続・ログ・キャッシュ・起動設定）。③永続化を除去する（シェル起動ファイル・cron・authorized_keys・モデル登録）—— 判断がつかなければ信頼できるイメージから再構築する。 ④侵害された可能性のある資格情報（トークン・クラウド資格情報・SSH 鍵）を、クリーンな端末からローテーションする。 ⑤Xinference API に認証をかけ、到達範囲を絞る。 ⑥カスタムのモデルコードを確認し、レビュー済みのリビジョンを固定する。 ⑦信頼できないコードは権限とネットワークを制限して実行し、本番の秘密情報を与えない。

本記録が強調するのは⑥である（本記録の評価）—— auto_map が指すファイルは1つで、人が1回読める量である。 そして読んだあとにリビジョンを固定しなければ、次に取得したときには別のコードが入っている可能性がある ——第2波が同じ名前で戻ってきた事実が、それを示している。

本記録が裏取りできたのは Pluto の報告までで、プラットフォーム側の公表は無い未確定事項出典 [1] [2]

一方で、本DBが中核に置く「当事者の一次公表」はこの事案には存在しない（本記録の明示）—— ①被害組織が公表されていないため、被害側の公表はそもそも無い〈未確定1〉。②プラットフォーム（Hugging Face・ModelScope）の公表は本記録の探索では見つかっていない〈未確定4・齟齬3〉。③攻撃主体の帰属は、報告自体が行っていない〈未確定5〉。

対応の評価

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • **「公式プラットフォームから取ったモデル」は、審査を通ったソフトウェアではない。** **走査の対象は既知のマルウェアと危険なモデル形式で、 同梱の Python コードが何をするかは見ていない**（出典1）
    **本件の31リポジトリは、各スキャナで「クリーン」と判定されていた**（出典1）—— **「プラットフォームが走査している」ことを根拠に 社内の受け入れ審査を省くと、審査が誰も行っていない状態になる**（本記録の評価）
    取るべき行動 **外部モデルの受け入れ基準を、ソフトウェア調達と同じ扱いで文書化する。** **最低限、①取得元と固定リビジョンの記録 ②同梱コードのレビュー記録 ③実行環境の権限の明示を、承認の要件にする**
  • **削除を待つ防御は成り立たない。** **通報で消えたアカウントは数日で5つに増えて戻り、 一部は8日後も残っていた**（出典1）
    **アカウントの作成に費用がかからない場所では、 削除は攻撃者の「やり直し」でしかない**（本記録の評価）—— **一方で取得側の固定リビジョン運用は、相手が何個アカウントを作っても効く**
    取るべき行動 **「通報・削除」を対策表から外し、 取得側で止める統制（内部レジストリ・固定リビジョン・権限分離）に予算を付ける**
  • **被害が出るのは暗号資産ではなく、計算資源の請求と裏口である。** **攻撃者の収益は約5,000ドル相当にとどまる**（出典1・2）
    **攻撃が割に合うのは、計算の費用を被害者が払っているからである**（本記録の評価）—— **収益の小ささを根拠に「被害は小さい」と読むと、 残された裏口（第2波はリバースシェルとコンテナ脱出を備える）を見落とす**
    取るべき行動 **GPU・クラウドの請求に上限と警告を設定し、 請求の異常を「コストの問題」ではなくセキュリティ事象として扱う経路を作る**
  • **研究部門と CI は、本番と同じ注意を払われていないことが多い。** **本件の標的は共有の研究用ノートブックと検証用モデルを取得する CI ジョブである**（出典1）
    **これらの環境は「本番ではない」という理由で統制が緩められがちだが、 GPU と資格情報を持っている**（本記録の評価）—— **攻撃者が欲しいのは本番の権限ではなく計算資源である**
    取るべき行動 **GPU を持つ環境の棚卸しを行い、本番以外の環境にも 「本番の秘密情報を置かない」「外向き通信を絞る」の2点を適用する**
セキュリティ技術者への示唆
  • **`trust_remote_code=True` は、任意コード実行の許可である。** **`config.json` の `auto_map` が指すモジュールの最上位コードが、 重みの読み込み前に呼び出し側の権限で走る**（出典1）
    **多くの手順書とサンプルに書かれているため、 「動かすために付けた」状態がそのまま残りやすい**（本記録の評価）
    取るべき行動 **コードベース・ノートブック・手順書を `trust_remote_code` で検索し、 使用箇所を一覧にする。** **残すものは `auto_map` が指すファイルを読み、リビジョンを固定する**
  • **確認すべき痕跡は公表されている。** **`/tmp/.cch/`、`svc.py` プロセス、`[kworker/u20:1]` という名前のプロセス**（出典1）
    **第2段階の配布は送信元 IP で制限されており、 URL からの検証ができない**（出典1）—— **ホスト上の痕跡のほうが確実に使える**（本記録の評価）
    取るべき行動 **GPU ホストで上記3点を確認する。** **1つでも当たれば、消す前にプロセス・接続・ログ・キャッシュ・起動設定を保全する**
  • **当たっていた場合、作業は「消す」ではなく「資格情報を替える」から始まる。** **Pluto は、到達できる資格情報（トークン・クラウド資格情報・SSH 鍵）の ローテーションを、クリーンな端末から行うよう勧めている**（出典1）
    **侵害されたホストから鍵を替えても、 攻撃者が見ている端末で新しい鍵を作ることになる**（本記録の評価）
    取るべき行動 **侵害が疑われるホストを隔離したうえで、別の端末から トークン・鍵・クラウド資格情報を失効・再発行する。** **永続化（シェル起動ファイル・cron・`authorized_keys`・モデル登録）を除去し、 判断がつかなければ信頼できるイメージから再構築する**
  • **コンテナは、特権付きで動いていれば隔離になっていない。** **第2波はコンテナからホストへ出るスクリプトを備え、 GPUStack の `/var/lib/gpustack` を狙う**（出典1）
    **推論基盤は GPU を使うために特権やホストのマウントを与えられることが多い** （本記録の評価）—— **その構成では、コンテナ内の任意コード実行がホストの侵害に直結する**
    取るべき行動 **推論コンテナの特権設定とマウントを棚卸しし、 ホストのディレクトリをマウントしない構成に寄せる。** **外せない場合は、そのホストで未検証のモデルを読み込まない運用にする**

    **認証のかかっていない推論 API と、 到達範囲が絞られていないホストが標的として挙げられている**（出典1）
    取るべき行動 **推論 API の認証を有効にし、到達できる範囲を 社内ネットワークと必要な呼び出し元に限定する。** **外部から到達できる推論エンドポイントを棚卸しする**
