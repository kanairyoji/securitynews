INC-2026-0872LLMjacking で累計100万ドル

Google Threat Intelligence Group（GTIG）と Mandiant は2026年11月3日、 **企業の大規模言語モデル（LLM）アクセスを乗っ取って転売する「LLMjacking」の実害**を公表した。 **単一のインシデントで1日あたり10万ドルを超える不正請求が観測され、 一部の組織ではアクセスを取り消すまでの累計が100万ドルに達した**（出典1）。 **攻撃は分業している**——**①公開された LLM の接続先を探す／保護されていない機器から 有効な API キーを盗む「初期アクセス」の集団と、 ②盗んだキーを集約してプロキシ経由で再販売する「LLM mixer」の集団**（出典1・2）。 **初期アクセスの主経路は、露出・窃取されたクラウドの識別情報である** （IAM 資格情報・サービスアカウントキー・GitHub の個人アクセストークン・ 有効なセッショントークン。出典1）。 **攻撃者は盗んだキーの有効性を、出力長を1に絞った最小のリクエストで確かめ、 量的な異常検知を避ける**（出典1）。 **転売網の例として、月60ドルで「無制限プラン」を売る jet-night.com が挙げられ、 ある攻撃者は8時間未満で50万回を超える LLM API 呼び出しを実行した**（出典1）—— **Jet Night はトークン費用としてほぼ100万ドルを被害組織に負担させた。** **Google は、キーを集約して配分する UNC6993 を脅威クラスタとして追跡しており、 同クラスタは誤設定のサービスアカウントキーでクラウドを侵害し、 追加の API キーを生成してサービスを有効化し、請求を10万ドル超に積み上げた**（出典1）。 **LLM ゲートウェイ自体も狙われており、LiteLLM の CVE-2026-40217 （鍵の再生成の端点で利用者 ID が再束縛される不備）を悪用して 通常の仮想キーを管理者権限へ昇格させた事例が示されている**（出典1）。 **被害組織の名前・業種・国・被害総額はいずれも公表されていない。**

Google Threat Intelligence Group（GTIG）と Mandiant は2026年11月3日、企業の LLM アクセスを乗っ取って転売する「LLMjacking」の実害を公表しました（出典1）。単一のインシデントで1日あたり10万ドルを超える不正請求が観測され、一部の組織ではアクセスを取り消すまでの累計が100万ドルに達しています（出典1・2・3・4）。

特徴は、攻撃が分業していることです（出典1・2）。①公開された接続先を探す集団と、保護されていない機器から有効な API キーを盗む集団が初期アクセスを作ります。 ②その access は「LLM mixer」と呼ばれる転売網へ渡され、プロキシ経由で購読者のプロンプトを被害組織のキーで中継します。 サービス提供者の側からは正当な消費として記録され、請求は被害組織に立ちます。

例として挙げられた jet-night.com は、月60ドルで「無制限プラン」を売っていました（出典1）—— 同種のサービスの相場は月100〜250ドルで、Google はこの安さを「盗んだ鍵に依存している証拠」と評価しています。 ある攻撃者は8時間未満で50万回を超える API 呼び出しを実行し、Jet Night はトークン費用としてほぼ100万ドルを被害組織に負担させました（出典1）。

本件で読者が持ち帰るべき点は3つです（本記録の評価）。①検知は「量」では間に合いません。 攻撃者は出力長を1に絞った最小のリクエストで鍵の有効性を確かめ、量的な異常検知を避けています（出典1）。②盗まれる資産は従来どおりです。 公開リポジトリに置き忘れた鍵、端末に残ったサービスアカウントキー、有効なセッショントークン（出典1）—— 新しいのは、それが「計算の請求」に変換される速さだけです。 ③LLM ゲートウェイ自身が標的です。 LiteLLM の CVE-2026-40217 を悪用して、通常の仮想キーを管理者権限へ昇格させた事例が示されています（出典1）。

被害組織の名前・業種・国・被害総額はいずれも公表されていません〈未確定1・2〉。本記録が裏取りできたのは Google の報告本文までであり、報道が加えた「毎秒1,000リクエストを超えるスパイク」は報告本文には対応する記述がありません〈齟齬1〉。

攻撃は分業していた——盗む集団と、売る集団がいる原因・手口出典 [1] [2]

報告の中心は、金額ではなく構造である（出典1。整理は本記録）。

GTIG はひとつの調査で、2つの運用クラスタが連携して企業の LLM 基盤を侵害・収益化している様子を観測した（出典1）。①初期アクセスを作る側。 公開された LLM の接続先を探す集団と、保護されていない機器から有効な API キーを盗む集団がいる（出典1・2）。②収益化する側。 「LLM mixer」と呼ばれ、不正なアクセスをプロキシ・集約・再販売して地下市場の購読者に提供する（出典1）。

具体例として、初期侵入の担い手から事前に有効性を確認した仮想キーを受け取った後続のクラスタが、LiteLLM ゲートウェイを攻撃している（出典1）—— 「盗んだ鍵の検証済みリスト」が受け渡される市場が成立している。

この分業が意味するのは、被害組織から見た攻撃者が「侵入してきた相手」ではないということである（本記録の評価）—— 請求を発生させているのは、鍵を買った購読者の利用である。 サービス提供者の側からは正当な消費として記録され、課金は被害組織に立つ（出典1・2）。

入口は新しくない——IAM 資格情報、サービスアカウントキー、GitHub のトークン原因・手口出典 [1] [2]

報告は「初期アクセスの支配的な経路は、露出または窃取されたクラウドの識別情報である」と述べる（出典1。本記録が訳した。原文英語）。

挙げられているのは次のものである（出典1）。①IAM 資格情報。侵害された社員の資格情報を使い、クラウドのフェデレーショントークンで新しいアクセスキーを生成して多要素認証を回避した事例がある。 ②サービスアカウントキー（誤設定のもの）。 ③GitHub の個人アクセストークン。 ④有効なセッショントークン。 ⑤公開 GitHub リポジトリに残された企業の LLM API キー。

UNC6993 の事例では、アプリの入口を装ったセッション奪取のページを用意し、利用者に有効なアクセストークンを含む生のデータを貼り付けさせることで、パスワードと多要素認証の両方を回避している（出典1）—— 「鍵を盗む」のではなく「有効な切符を提出させる」形である（本記録の整理）。

ここで確認しておくべきは、この一覧に「AI 固有の脆弱性」が1つも無いことである（本記録の評価）—— 変わったのは入口ではなく、入ったあとに換金される速さである。

検知は「量」では間に合わない——出力長1の最小リクエストで鍵は試される発覚の端緒出典 [1]

攻撃者は、盗んだ鍵の有効性を確かめる段階で量的な監視を避けている（出典1）。

公開リポジトリから集めた LLM API キーに対し、出力長を1に絞った最小のリクエストを送って有効性を検証する（出典1）—— 報告はこれが EDR や SIEM の量的な異常検知を回避するためだと述べる。

一方で、請求が跳ねる段階はきわめて速い（出典1）。報告は「暗号資産マイニングのような緩やかなリソース消費とは異なり、数時間で不正請求が急増しうる」と記している（本記録が訳した）—— 8時間未満で50万回超という例が、その速さを示す。

つまり検知の窓は2つあり、性質が正反対である（本記録の評価）。①鍵が試される瞬間は「静かすぎて」見えない。 ②消費が始まる瞬間は「速すぎて」間に合わない。 報告が勧める監視が、出力長1・温度0のような低量リクエストの検出と、モデル別の利用枠・予算警告の両方である理由はここにある（出典1。整理は本記録）。

LLM ゲートウェイ自体が標的だった——CVE-2026-40217 で仮想キーが管理者になる原因・手口出典 [1] [2]

報告が示したもう1つの経路は、鍵を束ねている装置そのものへの攻撃である（出典1）。

LiteLLM の CVE-2026-40217 は、鍵の再生成を行う端点で利用者 ID が再束縛される不備である（出典1）—— これを悪用すると、通常の仮想キーを管理者権限（PROXY_ADMIN）へ昇格させられ、環境を継続的に支配できる。

報告はさらに、オープンソースの AI ゲートウェイ（One API・New API 等）の不備が利用者から鍵を盗むために日常的に悪用されていると述べ、侵害されたゲートウェイがデータベースの資格情報を集めて内部のクラウド環境へ横移動する足場になりうると警告している（出典1）。

実務上の含意は単純である（本記録の評価）—— LLM のプロキシ・ルーティングゲートウェイを、ミドルウェアとして脆弱性管理の対象に入れる。 この種の装置は「AI の実験」として部門主導で立ち上がることが多く、資産台帳に載っていないことが被害の前提になっている。

他人のクラウドで、攻撃者のサービスが動いていた被害規模・影響範囲出典 [1] [2]

被害は請求だけではない（出典1）。報告は、攻撃者が被害組織のクラウド基盤を使って未承認のプロキシ端点とエージェント型の処理を動かした事例を挙げている（出典1・2）。

ある攻撃者はエージェントを有効化し、公開到達可能なリバースプロキシを展開し、独自の Node.js プロキシ束を使って複数の先端 LLM と互換の端点を公開した（出典1・2）—— これは D1337-KAIROS という名で売られていた。 Manus というエージェント基盤を使ったコンテナ型の裏口、SearXNG、agent-infra/sandbox の利用、GPU インスタンスの確保、API 経由での利用枠引き上げ要求も観測されている（出典1）。

newapi[.]pro は、正規ホストに似せたドメインに独自の中継を置き、被害組織の利用枠を吸い上げていた（出典1）。

ここまで来ると、被害組織の環境は「資源を盗まれた場所」ではなく「攻撃者の商用基盤」になっている（本記録の評価）—— 請求を止めても、立ち上げられたサービス・エージェント・裏口アカウントの棚卸しが残る。 報道も、攻撃者が環境内の資格情報・ログ・データベース・秘密管理基盤を探索し、裏口アカウントの作成や SSH 鍵の注入で居座りを図ると伝えている（出典2）。

本記録が裏取りできたのは報告本文までで、「毎秒1,000リクエスト」は確認できなかった未確定事項出典 [1] [2] [3] [4]

本記録は、2026年11月4日収集分の報道3本（出典2・3・4）を起点に、Google の報告本文（出典1）を取得して突き合わせた（本記録の明示）。

一致した項目—— 1日10万ドル超／累計100万ドル／8時間未満で50万回超／Jet Night の月60ドル／newapi[.]pro／D1337-KAIROS／UNC6993／CVE-2026-40217（LiteLLM）／初期アクセスの資格情報の種類。

一致しなかった項目（本記録の確認）—— ①BleepingComputer は「リクエスト量が突然跳ね、毎秒1,000リクエストを超えることもある」と書くが、報告本文に毎秒あたりの数値の記述は無い〈齟齬1〉。②報告は「累計100万ドルに達した組織がある」と「Jet Night がほぼ100万ドルを負担させた」を別の箇所で述べており、同一事案かどうかは判断できない〈齟齬2〉。③The Hacker News の本文は取得できず、冒頭部分のみを確認した（出典3）。

対策は請求の話ではなく、鍵の寿命と権限の分割の話である対策・注意喚起出典 [1] [2]

報告が挙げた対策を、本記録が実施の順に並べ替えた（出典1。並べ替えは本記録）。

①鍵を短命にする。 集中型の秘密管理基盤で鍵を管理・交換し、自動化によって漏えいした資格情報の寿命を短くする（出典1）。②鍵を分割する。 モデル・環境（開発／本番）・利用上限ごとに API キーを分け、安価なモデル用の鍵で高性能モデルを呼べないようにする（出典1）—— これは被害額の上限を設計で決める措置である（本記録の評価）。③必要のない権限を明示的に拒否する（クラウドの LLM サービスへのアクセスを含む）（出典1）。④フィッシング耐性のある多要素認証を、クラウドの ID 基盤・管理コンソール・開発者プラットフォームに適用する（出典1）。⑤コードの秘密走査を自動化する（GitHub・GitLab 等）（出典1）。⑥上限と警告を置く。 WAF での速度制限、モデルごとの利用枠、予算警告（出典1）。⑦検証の走査を監視する。 出力長1・温度0のような低量リクエストを見る（出典1）。⑧ゲートウェイをパッチ管理の対象に入れる（LiteLLM 等）（出典1）。⑨モデルの取得を承認済みの内部レジストリに限る（出典1）。⑩未有効化だった LLM サービスの有効化を「重大なセキュリティ事象」として扱う（出典1）—— 報告は、未使用だった Bedrock・Gemini API 等が不正に有効化された事例が多いと述べている。

本記録が実務上もっとも効くと評価するのは②と⑩である（本記録の評価）—— ②は被害額の天井を事前に決め、⑩は「気づく経路」を監視の設計ではなく台帳の差分に置き換える。

  • **被害額の天井は、事故の後ではなく鍵の設計で決まる。** **1日10万ドル超・累計100万ドルという請求は、 1つの鍵で高価なモデルを無制限に呼べる構成の帰結である**（出典1）
