INC-2026-0893台湾EC受託事業者の連鎖侵害

台湾の EC 技術サービス事業者で、2026年10月中旬の 91APP 侵害のあと **1shop・Cyberbiz・meepShop・そして EC 向けクラウド ERP の莫筆克科技（Mallbic）が 相次いで資安事件を公表／ブランド側から示唆された**—— **1shop は第三者メール配信（Mailgun）の API 鍵が取得され 「注文確定通知メール」の内容が読まれた可能性を公表、 莫筆克科技は品牌公式サイトの入口から侵入され 他の EC プラットフォームから取り込んだ取引データまで影響範囲に入ると説明した。** **並行して上場企業3社（中天生技の子会社・棉花田／王品の子会社・萬鮮／毛寶）が 重大訊息で「委託先の購物サイトで異常なデータアクセス」等を開示した**

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害脅威・攻撃キャンペーン続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年10月30日（1shop の公告。本記録が束ねる最初の当事者公表） 最終更新: 2026年11月5日（本記録の作成時点。1shop の公告を取得して確認した）

EC の裏側には、ブランドの名前では出てこない事業者が積み重なっている。 開店プラットフォーム、EC システム、受注出荷管理のクラウド ERP、メール配信サービス。 台湾で2026年10月から11月にかけて起きたのは、その層が次々に破れる事態である（本記録の整理）。

起点は2026年10月中旬の 91APP の侵害公表である（出典1）。そのあと、①1shop が10月30日に「注文確定通知メール」の内容が取得された可能性を公表し（出典1・2）、②11月に入ってから Cyberbiz と meepShop を使う複数のブランドが「注文データの異常な読み取り」「不正取得の可能性」を相次いで告知し（出典1）、③EC 向けクラウド ERP の莫筆克科技（Mallbic 雲端小幫手）がホストで未認可の悪性コマンド実行を受けたと説明し、Shopline が連携用の API トークンを全面更換した（出典4）。

並行して、台湾の上場・上櫃企業3社が公開資訊觀測站で重大訊息を開示した（出典3・5・6）—— 中天生技（4128）の子会社・棉花田生機園地、王品（2727）の子会社・萬鮮、そして毛寶（1732）である。 前2社はいずれも「委外購物網站服務廠商」のシステムで異常なデータアクセスが見つかったという形であり、廠商が先にアクセスを遮断したと述べている（出典3・5）。

本件の読みどころは2つある（本記録の整理）。

第一に、1shop の事案が示した「漏れた場所」の特殊さである（本記録の評価）。漏れたのは注文データベースではなく、第三者メール配信サービスに7日間保存されていた「注文確定通知メール」そのものだった可能性が高いとされる（出典2）。1shop がそう判断した根拠は、詐欺メールに書かれた「初回注文日」が実際の注文成立時刻ではなく、数秒遅れた通知メールの送信時刻だったことである（出典1・2）。データの出どころが、タイムスタンプのずれで特定された（本記録の読み）。

第二に、責任の線が契約の線と一致していないことである（本記録の評価）。Shopline は、商家が選んだ ERP 事業者と自社の間に直接の契約関係は無く、技術的には API 連携の仕組みを提供しているだけだと説明している（出典4）。それでも、Shopline 上の取引記録が影響範囲に入ったブランドが出ている（出典4）。契約が無い相手のデータ処理が、自社プラットフォームの顧客データに届いていた（本記録の整理）。

漏れたのは注文データベースではなく、メール配信サービスに7日間残っていた通知メールだった原因・手口

1shop の事案は、漏えいの場所を特定した過程が記録に値する（本記録の評価）。

詐欺メールは、消費者の氏名・購入商品・金額を実際の注文とおおむね一致させていた（出典1・2）。普通ならここで「注文データベースが漏れた」と考える。 1shop が違う結論に至った根拠は、日付のずれである（出典1・2）。

詐欺メールに示された「初回注文日」は、実際の注文成立時刻ではなく、それより数秒遅い「注文確定通知メール」の送信時刻だった（出典1・2。要旨）

加えて、商品項目の書き方も通知メールの書式に似ていた（出典1）。この2点から、相手が持っているのは注文レコードではなく通知メールそのものだと判断された（出典1・2）。

では、通知メールはどこにあったのか。 1shop は、長年使い続けていた第三者メール配信サービス Mailgun の送信用 API 鍵が他者に取得されれば通知メールの内容を読み取れる状態であり、これが現時点の証拠に最も合う推論だとしている（出典2）。通知メールは Mailgun 側に7日間保存される設定だった（出典1・2）。

ここが本件の要点である（本記録の評価）〈重要〉。露出面は、自社のデータベースではなく「外部サービスに置いた送信済みメールの保存」だった。 データ保護の棚卸しは、たいていデータベースとファイルサーバを対象にする。 メール配信サービスの送信ログに本文が7日間残っていることは、台帳に載らない（本記録の評価）。

1shop が打った手も、この構造に対応している（出典2）。

ERP が「合流点」になる——他のプラットフォームから取り込んだデータまで影響範囲に入った波及・関係先

莫筆克科技（Mallbic 雲端小幫手）の説明は、EC の受託構造の中で ERP が持つ位置を言い当てている（本記録の整理）。

攻撃者は品牌公式サイトのサービス入口からシステムに入ったが、影響を受けうるデータは品牌公式サイトのものに限らず、商家が他の EC プラットフォームから同システムへ取り込んだ消費者および取引のデータも含まれうる（出典4。要旨）

ERP は、受注と出荷を1か所で扱うために作られている（本記録の整理）。商家が自社公式サイト・Shopline・その他のモールで売っていれば、その全部の注文が ERP に集まる。 侵入口がひとつのサイトの入口でも、読める範囲は商家が取り込んだ全チャネルに及ぶ（本記録の評価）。

果果能量と彼蛋白の公告は、さらに踏み込んだ内容を伝えている（出典4）—— 莫筆克科技の書面説明として、未認可の悪性コマンド実行に加え、データベースへの照会と外部への持ち出しの試みが確認されたとされる。 「照会された」「持ち出しを試みた」は、「影響を受けうる」よりも一段強い記述である（本記録の読み）。

ここで契約の線を見る（本記録の整理）。Shopline の説明は明快である（出典4）。

  • 商家が選んだ ERP 事業者と Shopline の間に直接の契約関係は無い
  • 商家が自ら ERP 事業者と契約し、データ処理を行っている
  • 技術面では、Shopline は API 連携の仕組みを提供しているだけである
  • 事件は莫筆克科技のシステム側で発生し、Shopline プラットフォーム自体は侵入されていない

それでも、Shopline 上の取引記録は影響範囲に入った（出典4）。Shopline は連携用の API トークンを全面的に更換し、公式サイト側の関連データの棚卸しを行い、影響を受けたブランドへの情報提供を続けるとしている（出典4）。

これが本件で最も移植可能な論点である（本記録の評価）〈重要〉。契約関係が無い相手が、API を通じて自社の顧客データを持ち出せる状態は、「商家の自己責任」で説明できても「自社の顧客データは守られている」の根拠にはならない。 API 連携の仕組みを提供する側は、連携先の侵害が自社データの侵害になることを前提にトークンの寿命・権限の粒度・取得量の上限を設計するほかない（本記録の評価）。

  • **異常なアクセスを見つけた時点で遮断する手順を、 調査の前に用意しておく。**
    **中天生技（棉花田）と王品（萬鮮）の開示によれば、 委外廠商は異常なデータアクセスを発見して 当該アクセスを「先に遮断」している**（出典3・5）〈重要〉—— **調査を待たずに止める動きが実際にあった。** **その結果、両社は購物サイトのサービスを止めずに済んでいる** （出典3・5・本記録の読み）。
    取るべき行動 **顧客データを扱う API・データベースについて、 ①単位時間あたりの取得件数の上限、 ②上限超過時の自動遮断、 ③特定のアクセス元を即時に遮断する手順——を用意する。** **「調査が終わってから止める」ではなく 「止めてから調べる」を既定にするかを、事前に決めておく。**
  • **正規の通知メールに、顧客が真偽を判定できる要素を常に入れる。**
    **1shop の事案では、詐欺メールの消費者の氏名・購入商品・金額が 実際の注文とおおむね一致していた**（出典1・2）—— **内容の一致だけでは真偽を判定できない。** **1shop は商家に対し、 公式サイトと公式 LINE で唯一の公式サポートアカウントを告知し、 顧客が見分けられるようにすることを勧めている**（出典2）。
    取るべき行動 **注文確認・配送通知の定型文に、 ①公式サポートの唯一の窓口、 ②「当社から LINE 登録やリンククリックでの解約を求めることはない」 という否定形の明示——を常に含める。** **否定形は、攻撃者が使える手口を事前に塞ぐ （「この形の連絡は来ない」と約束しておく）。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ **自社の EC・会員サービスの裏側に、 開店プラットフォーム・EC システム・受注出荷管理（ERP/OMS）・ メール配信・決済・物流の受託事業者が何層あるかを図で言えるか。 各層が持つ顧客データの項目と保持期間を把握しているか。****本件では、ブランドの名前では出てこない4社（1shop・Cyberbiz・ meepShop・莫筆克科技）でそれぞれ事案が起き、 下流のブランドに顧客データの被害が出た**（出典1・4）—— **層の存在を把握していなければ、通知が来るまで気づけない**（本記録の評価）。
データの保持□ **第三者サービス側に自社の顧客データが「保存」されていないか （メール配信サービスの送信済み本文・SMS のログ・帳票の生成物）。 保存期間の既定値を確認したことがあるか。****1shop の露出面は、注文データベースではなく メール配信サービスに7日間保存されていた通知メールだった**（出典1・2）—— **データベース中心の棚卸しでは見つからない**（本記録の評価）。
認証・認可□ **第三者サービスの API 鍵に有効期限が設定され、 定期的に更換されているか。利用元 IP が許可リストで縛られているか。 「長年使い続けている鍵」が残っていないか。****1shop は、長年使い続けていた送信用鍵が取得された可能性を 最も証拠に合う推論としている**（出典2）—— **期限の無い鍵は、漏れた時点から発見されるまで有効である**（本記録の評価）。
システム構成□ **複数チャネルの受注データを1つのシステムに集約しているか。 集約先が侵害された場合に出るデータの範囲を、 チャネル横断で把握しているか。****莫筆克科技は、侵入口が品牌公式サイトのサービス入口である一方、 影響範囲は商家が他の EC プラットフォームから取り込んだ 消費者および取引データにも及びうるとした**（出典4）—— **一元管理が被害範囲の広さになる**（本記録の評価）。
体制・契約□ **委託契約に、事案発生時の「書面による説明」の提供義務 （影響データ項目・対象期間・件数・調査結果の提供期限）が書かれているか。 口頭やチャットでの通知だけで自社の顧客へ告知する運用になっていないか。****本件では、受託事業者3社の当事者公表が確認できず〈未確定4〉、 事案の輪郭が下流ブランドの告知の寄せ集めで作られている**（本記録の評価）。 **果果能量・彼蛋白は書面の説明を得て公告している**（出典4）。
運用・監視□ **外部からの不正利用の指摘（顧客・取引先からの通報）を受け付ける窓口が 公開され、到着が監視されているか。 通報から調査着手までの時間を測っているか。****1shop が事案を把握した端緒は、商家および消費者からの通報であり、 同社は通報を受けた当夜に調査を開始している**（出典1・2）—— **自社側の検知は働いていなかった**（本記録の評価）。
