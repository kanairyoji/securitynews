INC-2026-0897Rails 8.1.4.1で21件修正・最大9.8

Ruby on Rails が2026年11月4日に 8.1.4.1 / 8.0.5.2 を公開し、21件の脆弱性を修正した—— 深刻度 Critical は Active Storage の画像解析に関する1件（GHSA-f3w6-w445-fwh9・CVSS 9.8）で、 ImageMagick のコーダ選択を制限していなかったため、 細工したファイルを「添付するだけ」でサーバ上の任意ファイル書き込みに至り、 Disk サービス併用時は secret_key_base などの読み取りからコード実行・横展開に進みうる。 国内報道が示した CVE-2026-122006 という番号は、Rails のアドバイザリ側では確認できない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月4日（Rails 公式ブログおよび GHSA の公開） 最終更新: 2026年11月6日（本記録の作成。Rails ブログと GHSA を取得して裏を取った時点）

Ruby on Rails の開発チームは2026年11月4日、セキュリティリリース「Rails 8.1.4.1」「Rails 8.0.5.2」を公開し、21件の脆弱性を修正しました（出典1）。深刻度の内訳はCritical 1件・High 4件・Medium 13件・Low 3件です（出典1・3）。

Critical の1件は GHSA-f3w6-w445-fwh9、「Active Storage の画像解析における任意ファイル書き込みおよび読み取りの可能性」です（出典2。原文英語）。CVSS 3.0 のベーススコアは 9.8（CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H）、弱点分類は CWE-1188（出典2）。

仕組みはこうです。 ImageMagick は入力ファイルの内容からコーダを選び、一部のコーダは画像の中に書かれた別のファイル名に対して動作します。Active Storage はそれらのコーダを制限していませんでした（出典2）。そして ImageMagick の解析処理は「ファイルを添付した時点」で走ります——アドバイザリは「アップロードを添付するだけで足りる。variant・preview・analyze の呼び出しは要らない」と明記しています（出典2。原文英語）〈重要〉。

影響は、認証されていない攻撃者によるサーバ上の任意ファイル書き込みです。さらに Disk サービスを使っている場合は、アプリのプロセスが読めるファイル—— secret_key_base や外部サービスの資格情報——の読み取りにも至り、そこからコード実行や横展開に進みうるとされています（出典2）〈重要〉。

該当するのは、次の3条件がすべて成り立つアプリです（出典2）。①config.active_storage.variant_processor = :mini_magick（load_defaults 6.1 以前の既定値）、②該当コーダを拒否していない ImageMagick のポリシーで動いている（Debian と Ubuntu の既定ポリシーは拒否していない）、③信頼できない利用者からのファイルアップロードを受け付けている。

加えて期限の問題があります。 Rails 8.0 系のセキュリティサポートは2026年11月7日に終了します（出典1）〈重要〉——今回の 8.0.5.2 は 8.0 系に対する最後のセキュリティ修正にあたります。

なお、国内報道はこの Critical の脆弱性に CVE-2026-122006 という番号とCVSS 9.8 を与えていますが（出典3）、本記録が2026年11月6日に取得した GHSA-f3w6-w445-fwh9 の本文ではCVE 番号は「None known（判明している CVE は無い）」と記載されています（出典2）〈齟齬1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**アップロード受付 → ImageMagick のコーダ選択 → 任意ファイル書き込み（および読み取り）→ 資格情報の奪取 → コード実行・横展開、という経路である**（出典2）〈重要〉—— **実際の攻撃の観測ではなく、アドバイザリが述べる成立条件と影響を段階に並べたものである** （本記録の明示）〈未確定2〉。 **各段階の「検知の機会」と「効きえた対策」は本記録の評価である。**

    根拠: GHSA の「影響を受けるアプリケーション」の3条件（出典2）
  2. 2. 初期侵入確認済[2]

  3. 3. 実行確認済[2]

    **認証されていない攻撃者がサーバ上の任意ファイルを書き込める**（出典2）〈重要〉。 **Disk サービスを使う構成では、アプリのプロセスが読めるファイル—— `secret_key_base` や外部サービスの資格情報——の読み取りにも至る**（出典2）。 **そこからリモートコード実行や横展開に進みうる**（出典2）—— **Dark Reading も「攻撃者を横展開の位置に置きうる」と伝えている**（出典4。原文英語）。

参照・持ち出された情報

    「添付するだけ」で成立する——サムネイルを作っていないアプリも対象になる原因・手口

    この脆弱性でもっとも重要な一文は、成立条件の軽さです（本記録の評価）〈重要〉。

    アップロードを添付するだけで足りる。variant・preview・analyze の呼び出しは要らない。（出典2。原文英語）

    Active Storage は、ファイルが添付された時点で画像解析（analyzer）を動かします（出典2）。つまり「画像変換を使っていないから関係ない」「サムネイルは作っていない」という前提は成り立ちません。

    仕組みは ImageMagick のコーダ選択にあります（出典2）。ImageMagick は入力ファイルの内容から処理すべき形式（コーダ）を選びます。拡張子ではなく中身で決まるため、.png という名前のファイルが別の形式として扱われます。そして一部のコーダは、画像の中に書かれた別のファイル名に対して動作します——読み取り、削除、遠隔・ローカル参照の取得、画面表示です（出典2）。

    Active Storage はこれらのコーダを制限していませんでした（出典2）。弱点分類が CWE-1188「安全でない既定値での初期化」なのは、この構造を指しています。

    修正の中身も、裏返しに読むと理解が早いです（出典2）。修正版は policy.xml を同梱し、MiniMagick.cli_env 経由で MAGICK_CONFIGURE_PATH を設定して、次を拒否します——MSL スクリプトコーダ、他ファイルを読み取り・削除するコーダ、遠隔・ローカル参照を取得するコーダ、画面表示を行うコーダ、Ghostscript 系のコーダとgs デリゲート、@filename 形式の間接参照。「画像処理器が持っていたファイル操作能力を閉じる」という修正です（本記録の整理）。

    該当するかどうかは3条件で決まる——Debian・Ubuntu の既定ポリシーは拒否していない被害規模・影響範囲

    アドバイザリは、影響を受けるアプリの条件を3つ挙げ、そのすべてが成り立つ場合だとしています（出典2）〈重要〉。

    # 条件 確認のしかた（本記録の整理）
    ① config.active_storage.variant_processor = :mini_magick load_defaults 6.1 以前が既定で該当。設定ファイルと load_defaults の値を見る
    ② 該当コーダを拒否していない ImageMagick のポリシーで動いている Debian と Ubuntu の既定ポリシーは拒否していない（出典2）
    ③ 信頼できない利用者からのファイルアップロードを受け付けている 会員登録・応募フォーム・問い合わせ添付など

    ②が重いところです（本記録の評価）〈重要〉—— Debian と Ubuntu は国内の本番環境でも広く使われており、「OS 既定のままなら拒否されていない」とアドバイザリが明示しています（出典2）。つまり自分で ImageMagick のポリシーを書いた記憶がない組織は、②に該当します。

    ①は年季の問題です（本記録の評価）。load_defaults 6.1 以前という条件は、長く運用してきたアプリのほうが該当しやすいことを意味します——新規に作ったアプリよりも、何度もアップグレードを重ねてきたアプリのほうが危ないという向きです。

    影響を受けるバージョンは、8.1 系が 8.1.4.1 未満、それ以外が 8.0.5.2 未満です（出典2）。

    Disk サービスを使っていると、書き込みだけでなく secret_key_base の読み取りに届く評価・解釈

    影響の記述は2段になっています（出典2）〈重要〉。

    1段目は任意ファイルの書き込みです。 認証されていない攻撃者が、サーバ上の任意のファイルを書き込める可能性があります（出典2）。

    2段目は読み取りです。 Disk サービス（添付をアプリのファイルシステムに置く構成）を使っている場合、アプリのプロセスが読めるファイルも読み取られ得ます——アドバイザリが例示しているのは secret_key_base と外部サービスの資格情報です（出典2）。

    なぜこれが決定的か（本記録の評価）〈重要〉。secret_key_base は Rails のセッション・署名付き URL・暗号化属性の根です。これを取られた攻撃者は、正規の署名を自分で作れます——つまり「任意のファイルを読めた」で終わらず、アプリの信頼の土台を握ることになります。アドバイザリがコード実行と横展開に言及し、Dark Reading が「横展開の位置に置きうる」と伝えているのはこの意味です（出典2・4）。

    だからアドバイザリの推奨に「資格情報のローテーション」が入っています（出典2）〈重要〉—— パッチを当てただけでは、すでに読まれていた場合の後始末が済まないためです（本記録の整理）。ただし実際に読まれた事実が確認されたという記載はありません（出典2）〈未確定2〉。

    国内報道の CVE-2026-122006 は、Rails のアドバイザリ側では確認できない未確定事項

    番号の扱いに食い違いがあります（本記録の確認）〈重要〉〈齟齬1〉。

    • GHSA-f3w6-w445-fwh9（2026年11月6日に本記録が取得）の CVE 欄は「None known（判明している CVE は無い）」です（出典2）。

    本記録は、CVE-2026-122006 が GHSA-f3w6-w445-fwh9 に対応することを一次資料では確認できていません（本記録の明示）〈未確定1〉。GHSA の公開に遅れて CVE が採番され、GHSA 側の表示が追いついていないという説明はありえますが、それも本記録は検証していません（本記録の推定）。

    事案の詳細

    影響を受けたシステム
    名称: Active Storage（activestorage gem）　ベンダー: Ruby on Rails　CVE番号: GHSA-f3w6-w445-fwh9　バージョン: **8.1 系は 8.1.4.1 未満、それ以外は 8.0.5.2 未満が影響を受ける**（出典2）〈重要〉—— **修正版は 8.1.4.1 と 8.0.5.2 である**（出典1・2）。　概要: **Rails 標準の添付ファイル機構。画像解析（analyzer）はファイルの添付時に動作する** （出典2）〈重要〉—— **variant（変換）や preview（プレビュー）、`analyze` の明示的な呼び出しは不要であり、 「サムネイルを作っていないから安全」という前提は成り立たない**（本記録の整理）。　症状: **細工されたファイルがアップロードされると、ImageMagick が内容からコーダを選び、 画像内に書かれたファイル名に対して動作する**（出典2）〈重要〉—— **結果として、認証されていない攻撃者がサーバ上の任意のファイルを書き込める。 Disk サービスを使う構成ではアプリのプロセスが読めるファイル （`secret_key_base` や外部サービスの資格情報）の読み取りにも至り、 コード実行や横展開に進みうる**（出典2）。
    名称: ImageMagick（システム側のポリシー設定）　ベンダー: ImageMagick　バージョン: **バージョンではなくポリシー設定が条件である**（出典2）〈重要〉—— **該当コーダを拒否していないポリシーで動いている場合に影響を受ける。 Debian と Ubuntu の既定ポリシーは拒否していないと明記されている**（出典2）。　概要: **ImageMagick はファイルの内容からコーダを選ぶ。 一部のコーダは画像内に書かれたファイル名に対して読み取り・削除・外部参照・画面表示を行う** （出典2）。　症状: **Rails 側が制限していなかったため、アップロードされたファイルが これらのコーダに到達できた**（出典2）。
    緩和策
    手順: **修正版（8.1.4.1 または 8.0.5.2）へのアップグレード**（出典1・2）。　副作用: **8.0 系のセキュリティサポートは2026年11月7日に終了するため、 8.0.5.2 への更新は3日後に再び期限を迎える**（出典1。本記録の算出）〈重要〉—— **実質的には 8.1 系への移行が必要になる**（本記録の評価）。
    手順: **同梱された `policy.xml` の規則をシステムのポリシー （例: `/etc/ImageMagick-7/policy.xml`）に写す**（出典2）〈重要〉—— **最低限、MSL コーダ・Ghostscript 系のコーダ・`gs` デリゲートを拒否する**（出典2）。　副作用: **PostScript や PDF を ImageMagick 経由で描画しているアプリでは機能が壊れる** （出典2）〈重要〉—— **アドバイザリ自身が、必要な場合は `gs` と該当コーダを再許可するよう述べている** （出典2）。
    手順: **mini_magick 5.1 以降を使う**（出典2）。　副作用: **それより古い mini_magick は起動時に例外を投げる**（出典2）〈重要〉—— **パッチ適用がそのまま依存関係の更新を強制する**（本記録の整理）。
    手順: **Disk サービスで添付を扱っている場合は、`secret_key_base` と プロセスが読める資格情報をすべてローテーションする**（出典2）〈重要〉。　副作用: **セッション・署名付き URL・暗号化属性が一斉に無効になりうる**（本記録の評価）—— **利用者の再ログインや連携先の鍵差し替えが必要になるため、 計画された停止時間が要る**（本記録の評価。アドバイザリに手順の記載は無い）。

    初期侵入公表されていない

    CISO・経営層への示唆
    • **脆弱性管理の台帳を CVE 番号だけで回していないか点検する。**
      **今回の21件はすべて GHSA ID で公表され、Rails のブログは CVE 番号を示していない** （出典1）〈重要〉—— **Critical の1件も GHSA 本文では「CVE は判明していない」と記載されている**（出典2）〈齟齬1〉。 **CVE 到着を待つ運用では、最も重い1件が台帳に載らないまま数日が過ぎる**（本記録の評価）。
      取るべき行動 **①脆弱性情報の取り込み経路に、GitHub Security Advisory（GHSA）と 言語エコシステムの公式アドバイザリを加える。 ②台帳の識別子欄を CVE 以外の ID でも起票できる形にする。 ③「CVE 無しで深刻度 Critical」の起票を、月次で件数として可視化する。**
    • **フレームワークのサポート期限を、パッチ適用とは別のリスクとして管理する。**
      **8.0 系のセキュリティサポートは今回のリリースから3日後の2026年11月7日に終了する** （出典1。本記録の算出）〈重要〉—— **8.0.5.2 を当てても、3日後には「修正が出ない枝」に立つことになる**（本記録の評価）。
      取るべき行動 **①主要フレームワーク・言語処理系のサポート終了日を一覧にし、 残り日数を四半期ごとに経営へ出す。 ②残り180日を切った枝について、移行の工数と予算を先に確保する。 ③未サポート枝で動くアプリを「代替対策で凌いでいる状態」として明示し、 対策の内容（本件なら ImageMagick ポリシー）を記録する。**
    • **「侵害されていた場合に何が読めたか」を平時に棚卸ししておく。**
      **本件のアドバイザリは、パッチ適用に加えて `secret_key_base` と プロセスが読める資格情報のローテーションを求めている**（出典2）〈重要〉—— **読めたものが分からなければ、何を回すべきかも決まらない**（本記録の評価）。
      取るべき行動 **①アプリのプロセスが読める秘密情報の一覧を作る（環境変数・設定ファイル・鍵ファイル）。 ②各秘密情報のローテーション手順と所要時間、影響（再ログインの発生など）を文書化する。 ③年1回、実際に回して手順が動くことを確認する。**
    • **「うちは画像変換を使っていない」という安心の仕方を禁じる。**
      **本件はファイルを添付した時点で解析が走り、 variant・preview・`analyze` の呼び出しは不要である**（出典2）〈重要〉—— **機能を使っていないことは、コードが動かないことを意味しない**（本記録の評価）。
      取るべき行動 **①影響条件は「機能を使っているか」ではなく「設定値・ライブラリ・入力経路」で判定する という原則を、脆弱性トリアージの手順に書く。 ②判定を開発チームの自己申告に任せず、設定値の実測（grep と設定ダンプ）で確認する。**
    セキュリティ技術者への示唆
    • **ImageMagick のポリシーを「自分で書いたもの」にする。**
      **アドバイザリは Debian と Ubuntu の既定ポリシーが該当コーダを拒否していないと 明記している**（出典2）〈重要〉—— **OS 既定のままなら影響条件②を満たす**（本記録の整理）。
      取るべき行動 **①`/etc/ImageMagick-*/policy.xml` の現状を確認する。 ②修正版 Rails が同梱する `policy.xml` の規則を写す—— 最低限 MSL コーダ・Ghostscript 系コーダ・`gs` デリゲートを拒否する。 ③PDF・PostScript を扱うアプリでは、必要なコーダだけを明示的に再許可して動作確認する。**
    • **添付ファイルの解析を、アプリ本体と同じ権限で動かさない。**
      **本件の影響は「アプリのプロセスが読めるファイル」の範囲で決まる**（出典2）〈重要〉—— **解析処理が `secret_key_base` を読める位置にいることが、 ファイル書き込みをコード実行に変えている**（本記録の評価）。
      取るべき行動 **①画像・動画の解析と変換を、別プロセス・別コンテナに切り出す。 ②その実行環境に秘密情報を置かず、読み取り専用のファイルシステムで動かす。 ③外部コマンド（`gs` 等）の起動を禁止し、起動されたら警報にする。**
    • **Disk サービスの採用を、本番では見直す。**
      **任意ファイル書き込みが「`secret_key_base` の読み取り」に昇格する条件が Disk サービスである**（出典2）〈重要〉—— **添付がアプリのファイルシステム上にあることが、読み取りの足場になっている** （本記録の整理）。
      取るべき行動 **①本番の Active Storage サービス設定を確認し、Disk を使っている箇所を洗い出す。 ②オブジェクトストレージへ移すか、少なくとも別ボリューム・別権限に分ける。 ③移行できない場合は、プロセスが読める秘密情報を外部の金庫経由に変える。**
    • **パッチ適用が依存関係の更新を強制する場合に備える。**
      **修正版は mini_magick 5.1 以降を要求し、 それより古いと起動時に例外を投げる**（出典2）〈重要〉—— **「Rails だけ上げる」ができない**（本記録の整理）。
      取るべき行動 **①セキュリティリリースの適用前に、依存 gem の制約差分を確認する手順を持つ。 ②`bundle update` の範囲を限定する運用（`--conservative` 等）を試し、 起動確認までを CI に入れる。 ③緊急適用の演習を、年1回は本番相当の環境で行う。**
    • **アップロード経路を棚卸しし、「信頼できない入力」の定義を更新する。**
      **影響条件③は「信頼できない利用者からのファイルアップロードを受け付けている」である** （出典2）—— **ログイン後の機能も、会員登録が誰でもできるなら信頼できない入力である**（本記録の評価）。
      取るべき行動 **①ファイルを受け付ける全経路（フォーム・API・メール取り込み）を一覧にする。 ②各経路の認証要件と、登録の敷居（誰でも会員になれるか）を併記する。 ③受け付ける形式を絞り、サーバ側で内容を検査してから保存する。**
