INC-2026-0898APTに検証後差し替えの脆弱性

Debian と Ubuntu のパッケージ管理ツール APT に、 検証を通ったパッケージを事後に差し替えられる脆弱性（CVE-2026-109518・CVSS 4.0 で 7.7）が見つかり、 2026年11月4日に修正版が公開された—— HTTP リダイレクトで2つのダウンロードが同じ URI になると両者が統合され、 ダウンロードの再開時のファイル扱いの不備でハードリンク越しに中身を上書きできる。 成立にはリトライ設定（Acquire::Retries が0以外）が要り、 これは Debian 12・Ubuntu 22.04 LTS 以降の既定値である

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月4日（Debian DSA-6607-1・Ubuntu USN-8996-1・APT 開発者告知の公開） 最終更新: 2026年11月6日（本記録の作成。Debian・Ubuntu の一次公表を取得して裏を取った時点）

Debian と Ubuntu は2026年11月4日、パッケージ管理ツール APT の脆弱性CVE-2026-109518 に対する修正版を公開しました（出典1・2）。発見者はセキュリティ研究者 Max Justiczです（出典1・2・3）。

何が起きるか。 通信経路上に位置する攻撃者（中間者）が、署名検証を通ったパッケージを、検証の後に自分のものへ差し替えられます（出典1）。Debian のパッケージは root 権限でインストールされるため、差し替えが成功すれば root としての任意コード実行になります（出典1・4）。Ubuntu は「悪意あるミラーも同じ立場を取れる」と述べています（出典3）。

仕組みは2つの機能の組み合わせです（出典1・4）。①HTTP リダイレクトによって、2つの異なるパッケージのダウンロードが同じ URI になると、APT は両者を統合してしまう。②ダウンロードを再開（リトライ）するときのファイル扱いが適切でないため、既存のハードリンク越しに中身を上書きできる。Ubuntu は原因を端的に「ハードリンクの再利用」と書いています（出典2）。

成立条件は「リトライが有効であること」です（出典2・3・4）〈重要〉。Acquire::Retries が0なら悪用できません（出典3）。この設定が0以外（既定値は3）になっているのは、APT 2.3.2 以降、すなわち Debian 12（Bookworm）と Ubuntu 22.04 LTS（Jammy）以降です（出典2・4）。それより古いリリースは既定では影響を受けませんが、スクリプト等でリトライを有効にしていれば影響を受けます（出典4）。

修正版は、Debian 13（Trixie）が apt 3.0.4、Debian 12（Bookworm）が 2.6.2、Ubuntu は 22.04 LTS が 2.4.15ubuntu0.1、24.04 LTS が 2.8.4ubuntu0.1、26.04 LTS が 3.2.1ubuntu0.1、26.10 が 3.3.3ubuntu0.1 です（出典1・2）。深刻度は Ubuntu の評価で High、CVSS 4.0 のベーススコアは 7.7 です（出典2）。

緩和策として Ubuntu が挙げているのは2つです（出典3）〈重要〉—— ①APT のソースを http:// から https:// に変える（HTTPS は本件の悪用を防ぐ）。②更新作業の間だけ Acquire::Retries を0にする（sudo apt update && sudo apt upgrade -o Acquire::Retries=0）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**経路上の位置取り → リダイレクトと一時エラーによるリトライの誘発 → ハードリンク越しの上書きによる検証後の差し替え → root としてのコード実行、という経路である** （出典1・2・4）〈重要〉—— **実際の攻撃の観測ではなく、各公表が述べる成立条件と影響を段階に並べたものである** （本記録の明示）〈未確定2〉。 **各段階の「検知の機会」と「効きえた対策」は本記録の評価である。**

  1. 1. 偵察確認済[2] [3]
    **攻撃者は、APT クライアントとアーカイブサーバの間の HTTP 通信を 操作できる位置を取る必要がある**（出典2）〈重要〉。 **Ubuntu は「悪意あるミラーやプロキシ」がその位置を与えうると例示している**（出典2・3）—— **どの経路が現実的かという分析は公表されていない**〈未確定1〉。
    根拠: Ubuntu のセキュリティ情報とブログの前提条件（出典2・3）
  2. 2. 初期侵入確認済[1] [2] [4]
    **攻撃者はリダイレクトと一時的な HTTP サーバエラーを使って、 APT にダウンロードのリトライを行わせる**（出典4）〈重要〉。 **リダイレクトによって2つの異なるパッケージのダウンロードが同じ URI になると、 APT は両者を統合してしまう**（出典1）。 **この経路は `Acquire::Retries` が0以外であることを要する**（出典2・3・4）—— **既定値3は Debian 12・Ubuntu 22.04 LTS 以降に適用される**（出典2）。
    根拠: DSA-6607-1 の説明（出典1）／APT 開発者の告知（出典4）
  3. 3. 実行確認済[1] [2] [4] [6]
    **ダウンロードの再開時のファイル扱いが適切でないため、 APT は既存のハードリンクを攻撃者が選んだ中身で上書きしてしまう**（出典1・4）〈重要〉。 **これにより、署名検証を通った後のパッケージが差し替わる**（出典1）—— **Ubuntu は「署名検証に失敗したパッケージでもインストールさせられる」と述べている** （出典3）。 **修正は、ダウンロード先のファイルを排他で開き、 部分ダウンロード分を書き写す前に既存ファイルを unlink する変更である**（出典6）〈齟齬2〉。
    根拠: Ubuntu のセキュリティ情報（原因はハードリンクの再利用）（出典2）／APT 開発者の告知（出典4）
  4. 4. 影響（暗号化・破壊・改ざん）確認済[1] [2] [3] [6]
    **Debian のパッケージは root 権限でインストールされるため、 差し替えが成功すれば root としての任意コード実行になる**（出典1・4）〈重要〉。 **Ubuntu も「root 権限でのリモートコード実行に至る可能性がある」と述べている**（出典2）。 **影響は APT ライブラリの HTTP バックエンドにあるため、 apt・apt-get・aptitude・グラフィカルツールのいずれを使っていても対象になる**（出典3）。
    根拠: DSA-6607-1（出典1）／USN-8996-1（出典2）／Ubuntu のブログ（出典3）
参照・持ち出された情報

    「検証は通った」という記録が残る——差し替わるのは検証の後だった原因・手口

    この脆弱性の本質は、検証の前後関係です（本記録の評価）〈重要〉。

    Debian の DSA-6607-1 はこう書いています（出典1。原文英語）。

    APT は、HTTP リダイレクトによって2つの別個のパッケージのダウンロードが同じ URI になったとき、それらを統合してしまう。HTTP ダウンロードの再開時のファイル扱いが適切でないため、中間者攻撃者が検証の後にパッケージを差し替えることができ、root としての任意コード実行に至りうる。

    「検証の後に」が決定的です（本記録の整理）。APT の署名検証そのものは破られていません。検証を通ったファイルの中身が、別の経路の書き込みで入れ替わるのです。

    どう入れ替わるか。 Ubuntu は原因を端的に「ハードリンクの再利用」と書いています（出典2）。APT 開発者の説明では、リダイレクトと一時的な HTTP サーバエラーがダウンロードのリトライを引き起こし、その結果 APT が既存のハードリンクを選んだペイロードで上書きしてしまう（出典4。原文英語）。

    修正の方向も同じ場所を指しています。 CSO Online の報道によれば、2026年10月12日付のコミットで、ダウンロード先のファイルを排他で開き、部分ダウンロード分を書き写す前に既存ファイルを unlink するように変えられました（出典6）〈齟齬2〉——つまり「既存のハードリンク越しに書かせない」という修正です。

    そして Debian のパッケージは root 権限でインストールされます（出典1・4）。差し替えが成功すれば、それは root としてのコード実行です。

    成立条件は設定1つ——リトライが0なら悪用できず、既定で3になったのは Debian 12 以降被害規模・影響範囲

    影響の有無は Acquire::Retries の値で決まります（出典2・3・4）〈重要〉。

    条件 状態
    Acquire::Retries が0 悪用できない（出典3）
    Acquire::Retries が0以外（既定値3） 影響を受ける
    既定が0以外になった時期 APT 2.3.2 以降（出典4）＝ Debian 12（Bookworm）・Ubuntu 22.04 LTS（Jammy）以降（出典2）
    それより古いリリース 既定では影響を受けない。ただしスクリプト等でリトライを有効にしていれば影響を受ける（出典4）

    ここに運用上のねじれがあります（本記録の評価）〈重要〉。新しいリリースのほうが既定で影響を受け、古いリリースは既定では受けない——通常の「古いほど危ない」という感覚と逆向きです。そして Ubuntu は 14.04 LTS まで遡って修正版を出しています（出典2）—— 既定では影響しないはずの古いリリースにも修正を出すのは、リトライを有効にしている運用が実在するという前提に立っているからだと読めます（本記録の評価）。

    対象の広さも押さえておきます。 Ubuntu は、脆弱性が APT ライブラリのHTTP バックエンドにあるため、apt・apt-get・aptitude・Ubuntu のグラフィカルツールなどAPT を使うフロントエンド全般が影響を受けると述べています（出典3）。一方で snap パッケージは影響を受けず、FTP 等の他のトランスポートも影響を受けません（出典3）。

    緩和策は HTTPS 化とリトライの一時停止——更新作業そのものが脆弱な経路を通る対策・注意喚起

    Canonical のブログが示す手順は、順序に意味があります（出典3。本記録の整理）〈重要〉。

    ①リトライを止めて更新する。

    sudo apt update && sudo apt upgrade -o Acquire::Retries=0

    全体を更新できない場合は APT だけを対象にできます（出典3）。

    sudo apt update && sudo apt install -o Acquire::Retries=0 --only-upgrade '?source-package(^apt$)'

    なぜ -o Acquire::Retries=0 を付けるのか。 更新作業そのものが、まだ脆弱な APT で行われるからです（本記録の整理）〈重要〉—— パッチを取りに行く通信が攻撃の対象になりうるため、その間だけ成立条件を外しておくという考え方です。

    ②ソースを HTTPS に変える。 Ubuntu は http:// を https:// に置換する手順を示しています（出典3）。HTTPS は本件の悪用を防ぎます（出典3）。ただし注意が2つあります——一部のコミュニティミラーは HTTPS に対応していません。そして Ubuntu 自身が「パッチ適用後は TLS は主に予防措置であり、アーカイブの署名方式のほうが強い保護である」と述べています（出典3。原文英語）。

    ③バージョンを確認する。

    apt list --installed '?source-package(^apt$)'

    ④自動更新に任せる場合。 Ubuntu 16.04 以降は unattended-upgrades が既定で有効で、24時間以内にパッチが当たるはずとされています（出典3）。その24時間はそのまま露出時間です（本記録の評価）。

    そして忘れやすいのが払い出し用イメージです。 CSO Online は、企業のセキュリティチームにとっての優先事項として「脆弱な導入の特定・リトライ設定の確認・本番システムと払い出しに使う Linux イメージへのパッチ適用」を挙げています（出典6）〈重要〉—— 自動更新はイメージの中には届きません（本記録の整理）。

    影響を受けたシステム
    名称: APT（Debian）　ベンダー: Debian プロジェクト　CVE番号: CVE-2026-109518　バージョン: **Trixie（13・安定版）は 3.0.3 以前が影響を受け 3.0.4 で修正 （DSA-6607-1）。Bookworm（12）は 2.6.1 以前が影響を受け 2.6.2 で修正（DLA-4880-1）。 Forky/sid は 3.3.6 で修正**（出典1・5）〈重要〉。　概要: **Debian のパッケージ管理ツール。パッケージは root 権限でインストールされる** （出典1・4）。　症状: **HTTP リダイレクトで2つの異なるパッケージのダウンロードが同じ URI になると統合され、 ダウンロード再開時のファイル扱いの不備により、 中間者が検証後にパッケージを差し替えられる**（出典1）〈重要〉—— **結果は root としての任意コード実行である**（出典1・4）。
    名称: APT（Ubuntu）　ベンダー: Canonical　CVE番号: CVE-2026-109518　バージョン: **修正版は 26.10 が 3.3.3ubuntu0.1、26.04 LTS が 3.2.1ubuntu0.1、 24.04 LTS が 2.8.4ubuntu0.1、22.04 LTS が 2.4.15ubuntu0.1、 20.04 LTS が 2.0.12+esm1（Ubuntu Pro）、18.04 LTS が 1.6.19+esm1（Ubuntu Pro）、 16.04 LTS が 1.2.36+esm1、14.04 LTS が 1.0.1ubuntu2.24+esm4 （いずれも Legacy Support アドオン）**（出典2）〈重要〉。　概要: **APT ライブラリの HTTP バックエンドの問題であるため、 apt・apt-get・aptitude・Ubuntu のグラフィカルツールなど APT を使うフロントエンド全般が影響を受ける**（出典3）〈重要〉—— **snap パッケージは影響を受けず、FTP 等の他のトランスポートも影響を受けない**（出典3）。　症状: **経路上の攻撃者が、検証されていないパッケージを APT にインストールさせ、 root 権限でのリモートコード実行に至りうる**（出典2）—— **署名検証に失敗したパッケージでもインストールさせられる**（出典3）〈重要〉。
    名称: Acquire::Retries（APT の設定項目）　ベンダー: Debian プロジェクト　バージョン: **設定値が0以外であることが成立条件である**（出典2・3・4）〈重要〉—— **既定で0以外になったのは APT 2.3.2 以降、 すなわち Debian 12・Ubuntu 22.04 LTS 以降である**（出典2・4）。　概要: **ダウンロードが失敗したときの再試行回数。既定値は3**（出典2）。　症状: **0であれば本件は悪用できない**（出典3）〈重要〉—— **それより古いリリースでも、スクリプト等でリトライを有効にしていれば影響を受ける** （出典4）。
    緩和策
    手順: **修正版の APT へ更新する**（出典1・2・3）〈重要〉—— **Ubuntu は `sudo apt update && sudo apt upgrade -o Acquire::Retries=0`、 全体を更新できない場合は `sudo apt update && sudo apt install -o Acquire::Retries=0 --only-upgrade '?source-package(^apt$)'` を示している**（出典3）。　副作用: **更新そのものが脆弱な経路を通るため、リトライを止めた状態で実施する必要がある** （出典3。本記録の整理）〈重要〉—— **古い LTS（20.04 以前）は Ubuntu Pro または Legacy Support の契約が要る**（出典2）。
    手順: **APT のソースを `http://` から `https://` に変える**（出典3）〈重要〉—— **Ubuntu のブログは Ubuntu アーカイブ向けの置換コマンドを示し、 その後 `sudo apt update` を実行するよう述べている**（出典3）。　副作用: **一部のコミュニティミラーは HTTPS に対応していない**（出典3）〈重要〉—— **また Ubuntu は「パッチ適用後は TLS は主に予防措置であり、 アーカイブの署名方式のほうが強い保護である」と述べている**（出典3。原文英語）。
    手順: **更新作業の間、`Acquire::Retries` を0にする**（出典3）〈重要〉—— **経路上の攻撃者と悪意あるミラーの双方に対して緩和になる**（出典3）。　副作用: **ネットワークが不安定な環境では、一時的な失敗でダウンロードが完遂しなくなる** （本記録の評価。Ubuntu は副作用に言及していない）—— **恒久設定にすると、通常運用の自動更新が失敗しやすくなる**（本記録の評価）。
    手順: **自動更新（unattended-upgrades）に任せる**（出典3）—— **Ubuntu 16.04 以降は既定で有効で、24時間以内にパッチが当たるはずとされている** （出典3）。　副作用: **24時間の猶予がそのまま露出時間になる**（本記録の評価）〈重要〉—— **払い出し用の Linux イメージには自動更新が及ばないため別途の対応が要る** （出典6。本記録の整理）。

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    リダイレクトとリトライでハードリンクを上書きし、検証後のパッケージを差し替える経路
    **DSA-6607-1（出典1）・USN-8996-1（出典2）・APT 開発者の告知（出典4）の説明に 対応させた経路図である。** **破線は成立条件（リトライが0以外）が満たされる場合にのみ通る段を示す**（本記録の整理）。 **実際の悪用の観測ではない**〈未確定2〉。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    偵察公表されていない
    **検知について公表された記載は無い**（本記録の確認）〈未確定4〉。 **平文 HTTP でパッケージを取りに行く通信は、 出口の通信記録に残るため棚卸しは可能である**（本記録の評価）〈重要〉—— **「どのサーバがどのミラーへ平文で取りに行っているか」は平時に把握できる。**
    侵入を防げたAPT のソースを HTTPS に揃え、平文 HTTP のミラー参照を禁止する
    影響を限定できたパッケージ取得を社内の信頼できるミラー・プロキシ1か所に集約し、経路を短くする
    検知できた出口通信の記録から、平文でアーカイブへ出ているホストを洗い出す
    初期侵入公表されていない
    **リトライと 3xx・5xx の連発は、プロキシやミラー側の記録に現れうる** （本記録の評価）〈重要〉—— **ただし一時的な障害でも同じ形になるため、単独では異常と断定できない**。 **公表に検知の指針は無い**〈未確定4〉。
    侵入を防げた更新作業中は Acquire::Retries を0にする
    検知できた社内ミラーのアクセス記録で、同一クライアントのリトライ急増を監視する
    実行現実的な検知機会なし
    **検証を通った後に差し替わるため、APT 自身の検証結果からは異常が見えない** （本記録の評価）〈重要〉—— **「検証に成功した」という記録が残るのが、この脆弱性の厄介さである。**
    侵入を防げた修正版の APT へ更新する（Debian 3.0.4 / 2.6.2、Ubuntu は各リリースの指定版）
    検知できたインストール後のパッケージの整合性を独立に検証する（debsums 等による事後確認）
    影響（暗号化・破壊・改ざん）公表されていない
    **侵害後の痕跡についての指針は公表されていない**（本記録の確認）〈未確定4〉。 **実務的には、パッケージ更新を行ったホストの一覧と更新時刻を押さえ、 平文 HTTP を使っていたホストから優先して確認するのが現実的である** （本記録の判断）〈重要〉。
    侵入を防げた払い出し用の Linux イメージにも修正版を取り込む（イメージは自動更新が及ばない）
    復旧を早められたパッケージ更新の実行ホスト・時刻・経路を記録し、事後の絞り込みに使えるようにする

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • **「パッケージ管理は安全」という前提を、根拠まで降りて確認する。**
      **本件は署名検証そのものを破っていない。検証を通った後に差し替わる**（出典1）〈重要〉—— **つまり「署名を検証しているから安全」という説明が成り立たない場合がある** （本記録の評価）。 **しかもパッケージは root 権限でインストールされるため、 差し替えはそのまま最高権限のコード実行になる**（出典1・4）。
      取るべき行動 **①自組織のサーバ・コンテナ・CI がパッケージをどこから取っているかを一覧にする。 ②平文 HTTP で取りに行っている経路を洗い出し、HTTPS か社内ミラーへ寄せる。 ③「パッケージ取得の経路」をサプライチェーンのリスク項目として台帳に載せる。**
    • **払い出し用のイメージ（ゴールデンイメージ）をパッチ管理の対象に入れる。**
      **自動更新はイメージの中には届かない**（本記録の整理）〈重要〉—— **CSO Online も企業の優先事項として 「本番システムと払い出しに使う Linux イメージへのパッチ適用」を挙げている**（出典6）。 **古いイメージから新しいホストが生まれ続ける構造では、脆弱性が再生産される** （本記録の評価）。
      取るべき行動 **①イメージの一覧と、それぞれの最終更新日を出す。 ②重大な脆弱性の対応手順に「イメージの再作成」を明記する。 ③イメージから起動したホストが初回起動時に更新を取る設計になっているか確認する。**
    • **「新しいリリースのほうが既定で危ない」場合があることを前提に判断する。**
      **本件の成立条件であるリトライの既定有効化は、 Debian 12・Ubuntu 22.04 LTS 以降という比較的新しい側である**（出典2・4）〈重要〉—— **古い LTS は既定では影響を受けない（ただし設定していれば受ける）**（出典4）。 **「更新しているほうが安全」という一般則だけでは判断を誤る**（本記録の評価）。
      取るべき行動 **①脆弱性のトリアージで、影響条件を「バージョンの新旧」ではなく 「設定値の状態」で判定する手順にする。 ②本件については `Acquire::Retries` の実値を全ホストで確認する。 ③確認結果を資産台帳に記録し、次回同種の脆弱性で再利用できる形にする。**
    • **緩和策の副作用を、適用前に見積もる。**
      **HTTPS 化は一部のコミュニティミラーで使えず、 リトライの無効化はネットワークが不安定な環境で更新の失敗を増やす** （出典3。本記録の評価）〈重要〉—— **「とりあえず緩和策を全台に入れる」と運用が壊れる**（本記録の評価）。
      取るべき行動 **①緩和策ごとに影響を受ける運用（自動更新・CI・オフライン環境）を列挙する。 ②恒久設定にするもの（HTTPS 化）と一時措置にするもの（リトライ0）を分けて決める。 ③決めた内容を手順書に書き、作業後に戻し忘れがないか確認する項目を設ける。**
    セキュリティ技術者への示唆
    • **APT のソースを HTTPS に揃え、平文 HTTP の参照を残さない。**
      **Ubuntu は HTTPS が本件の悪用を防ぐと明記している**（出典3）〈重要〉—— **経路上の攻撃者が HTTP 通信を操作できることが前提条件であるため、 経路を暗号化すれば成立しない**（出典2・3）。
      取るべき行動 **①`/etc/apt/sources.list` と `/etc/apt/sources.list.d/` 配下、 およびコンテナイメージの Dockerfile を対象に `http://` を検索する。 ②HTTPS に対応しているミラーへ寄せる（対応していないミラーは変更先を決める）。 ③変更後に `apt update` が通ることを確認する。**
    • **更新作業中はリトライを0にして実行する。**
      **更新作業そのものが、まだ脆弱な APT で行われる**（本記録の整理）〈重要〉—— **Ubuntu は `sudo apt update && sudo apt upgrade -o Acquire::Retries=0` を示している** （出典3）。
      取るべき行動 **①`apt list --installed '?source-package(^apt$)'` で現在のバージョンを確認する。 ②`-o Acquire::Retries=0` を付けて更新する（全体更新ができない場合は APT のみ）。 ③Debian は 3.0.4（Trixie）/ 2.6.2（Bookworm）、 Ubuntu は各リリースの指定版に達していることを確認する。**
    • **パッケージ取得の経路を1か所に集約する。**
      **中間者の位置を与えるのは、悪意あるミラーやプロキシである**（出典2・3）〈重要〉—— **各ホストが好きなミラーへ直接出ていく構成は、守る面が広くなる**（本記録の評価）。
      取るべき行動 **①社内ミラー（または認証付きプロキシ）を1か所に決め、全ホストをそこへ向ける。 ②ミラーのアクセス記録を残し、同一クライアントのリトライ急増を監視する。 ③出口のファイアウォールで、ホストから外部アーカイブへの直接通信を止める。**
    • **インストール済みパッケージの整合性を、APT とは独立に確認できるようにする。**
      **本件では「検証に成功した」という記録が残る**（本記録の評価）〈重要〉—— **APT 自身の検証結果からは差し替えが見えないため、 事後の確認は別の道具で行う必要がある**（本記録の評価。公表に検知指針は無い）〈未確定4〉。
      取るべき行動 **①`debsums` 等でファイルのハッシュを事後確認する手順を用意する。 ②パッケージ更新の実行ホスト・時刻・取得経路を記録に残す。 ③平文 HTTP を使っていた期間に更新を行ったホストを、確認の優先対象にする。**

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ **Debian 12（Bookworm）以降、または Ubuntu 22.04 LTS（Jammy）以降を運用しているか。****これらは `Acquire::Retries` の既定値が3であり、既定の状態で成立条件を満たす** （出典2・4）〈重要〉—— **「設定を変えていない」ことが、この脆弱性では安全を意味しない**（本記録の整理）。
    運用・監視□ **それより古いリリースで、スクリプトや設定ファイルで APT のリトライを有効にしていないか。****APT 開発者は「古いリリースでも多くの利用者スクリプトがリトライを使っていた可能性がある」と 述べている**（出典4）〈重要〉—— **Ubuntu が 14.04 LTS まで修正版を出しているのは、この層が実在するからだと読める** （出典2。本記録の評価）。
    委託・第三者部品□ **APT のソースに平文 HTTP の参照が残っていないか（コンテナイメージの定義ファイルも含む）。****成立には経路上で HTTP 通信を操作できることが要り、HTTPS は悪用を防ぐ**（出典2・3）〈重要〉—— **コンテナのビルド時に平文で取りに行く定義は見落とされやすい**（本記録の評価）。
    委託・第三者部品□ **社外のミラーやプロキシを経由してパッケージを取得していないか。****Ubuntu は「悪意あるミラーやプロキシ」が攻撃位置を与えうると例示している**（出典2・3）—— **悪意あるミラーの場合は、経路の暗号化だけでは防げない**（本記録の評価）〈未確定1〉。
    運用・監視□ **払い出し用の Linux イメージ（仮想マシンテンプレート・コンテナのベースイメージ）に 修正版を取り込む手順を持っているか。****自動更新はイメージの中には届かず、古いイメージから新しいホストが生まれ続ける** （本記録の評価）〈重要〉—— **CSO Online も優先事項としてイメージへのパッチ適用を挙げている**（出典6）。
    体制・契約□ **パッケージ更新の実行ホスト・時刻・取得経路が記録として残っているか。****本件は検証成功の記録が残るため、APT の記録だけでは差し替えを判定できない** （本記録の評価）〈重要〉—— **事後に「どのホストを優先して確認するか」を決める材料が必要になる**（本記録の判断）。
