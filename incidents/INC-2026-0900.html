INC-2026-0900Linux カーネルIPv4にUAF

Linux カーネルのIPv4処理に、認証なしでネットワーク越しに踏める解放後使用（UAF）が公表された （CVE-2026-98432・CVSS 3.1 で 9.8）—— TCP接続要求の再送やソケットマイグレーションと並行して ソケットオプションが解放され、まだ読んでいる処理が解放済みメモリを参照する。 Red Hat は2026年10月30日に専用の速報（RHSB-2026-016）を立てて 「修正の提供を急いでいる」とし、暫定策として IPオプション付きのIPv4 TCPパケットを nftables で落とす規則を示した。 WatchGuard も11月3日に WGSA-2026-0033 を出し、Dimension・Fireware OS・ WatchGuard AP が対象だと公表した

脆弱性続報が続いている日本に波及した海外事案設計・実装上の不備
初報: 2026年10月30日（Red Hat 速報 RHSB-2026-016 の公開） 最終更新: 2026年11月6日（本記録の作成。Red Hat・WatchGuard の一次公表を取得して裏を取った時点）

Red Hat は2026年10月30日16時03分（協定世界時）、Linux カーネルのIPv4ネットワーク処理に解放後使用の脆弱性があるとして、専用の速報 RHSB-2026-016 を公開しました（出典2）。CVE-2026-98432。Red Hat の評価は CVSS 3.1 で 9.8（Critical）、ベクターは AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H です（出典1）〈重要〉。cve.org の値も 9.8 で一致し、NVD は「N/A」です（出典1）。

何が起きるか。 Red Hat の記述では、inbound な接続要求に結び付いたソケットオプションが、並行する処理がまだそれを読んでいる最中に解放されうる（出典2。原文英語）。競合が起こるのは、接続要求が再送されたとき、またはソケットマイグレーションのときです（出典2）。結果として、遠隔の認証されていない攻撃者が「リモートコード実行を達成しうる（possibly achieve remote code execution）」（出典2。原文英語）。悪用には精密なタイミングが要るが、権限も利用者の操作も要りません（出典2）。

どこまで及ぶか。 Red Hat の速報が挙げるのはRHEL 8・9・10、OpenShift Container Platform 4（ノードが RHEL CoreOS で動く）、および RHEL カーネルの上に作られた製品（Red Hat OpenStack Platform・Red Hat Virtualization）です（出典2）。国内報道は、これに加えて OpenShift Container Platform 5 の openshift/ose-rhel-coreos-9、RHEL for NVIDIA 26 のカーネル、RHEL 9 の kernel-rt を挙げ、RHEL 7 は脆弱なコードが存在しないため影響を受けないと伝えています（出典4）。

暫定策は「IPオプション付きのIPv4 TCPパケットを落とす」ことです（出典2）〈重要〉—— nftables で ip protocol tcp ip hdrlength > 5 counter drop を入力フックに置く規則が速報に載っています（出典2）。ただしこれは修正ではなくフィルタで、再起動をまたいで残りません（出典2）。Red Hat は一部のワークロードを壊しうるので先に試験せよと述べています（出典2）。MPTCP は前提条件ではないので、MPTCP の無効化では防げません（出典2）。

機器ベンダーへの波及が始まっています。 WatchGuard は2026年11月3日、WGSA-2026-0033「Linux Kernel IPv4 Use-After-Free Vulnerability」をCritical として公開し、対象を Dimension 2.0 以降・Fireware OS 2025.1 および 12.0 以降・WatchGuard AP 1.0 以降としました（出典3）〈重要〉。報道によれば、Fireware OS と WatchGuard AP は脆弱なカーネルを含むがこの脆弱性が開くリモートコード実行の連鎖の影響は受けず、Dimension は脆弱な Ubuntu で動いていて修正はまだ提供されていない、とWatchGuard は説明しています（出典5。原文英語）。

悪用の報告はありません（出典1・2・3・5）〈未確定1〉—— 報道は「Cisco も WatchGuard も、いずれの脆弱性も実際に悪用されているとは把握していない」と伝えています（出典5。原文英語）。

参照・持ち出された情報

    競合状態が、認証も操作も要らない遠隔の攻撃面になっていた原因・手口

    Red Hat の速報の技術記述はこうです（出典2。原文英語。本記録の訳）〈重要〉—— inbound な接続要求に結び付いたソケットオプションが、並行する処理がまだそれを読んでいる最中に解放されうる。競合は、接続要求が再送されたとき、またはソケットマイグレーションのときに起こりうる。

    国内報道はこれを「TCP接続要求の再送やソケットマイグレーション（ソケットの移行）などを並行して処理する際に発生する競合状態」と整理し、「接続要求に関連付けられたソケットオプションの所有権が子ソケットに移される一方、別の処理が同じメモリ領域を参照する可能性がある」と説明しています（出典4）。

    CVSS のベクターが意味するところは明快です。 AV:N（ネットワーク）・AC:L（複雑さ低）・PR:N（権限不要）・UI:N（操作不要）（出典1）〈重要〉—— つまり、外部からTCP接続を受け付けているだけで条件が揃います。 Red Hat は Critical 評価の理由として、ネットワーク上の前提条件が無いことと、深刻な不安定化の可能性を挙げています（出典1）。

    ただし「複雑さ低」と「精密なタイミングが要る」は矛盾していません。 Red Hat 自身が「悪用には精密なタイミングが要るが、権限も利用者の操作も要らない」と書いています（出典2。原文英語）—— 競合状態は何度も試せるため、CVSS の AC は低く付きます（本記録の評価）。DoS は比較的容易に、コード実行は精密なヒープ制御を要する、という段差があります（出典4）〈未確定2〉。

    弱点の分類には表現の揺れがあります。 Red Hat の CVE ページは CWE-825（期限切れポインタの参照）、WatchGuard の勧告の題名と国内報道は「解放後使用（use-after-free）」です（出典1・3・4）〈齟齬2〉—— 指している現象は同じで、分類の粒度が違うだけです（本記録の整理）。

    暫定策は「IPオプション付きのパケットを落とす」——ただし再起動で消える対策・注意喚起

    Red Hat の速報は、修正の提供を急ぐと述べる一方で、nftables による暫定策を具体的な規則の形で載せています（出典2）〈重要〉。入力フックに ip protocol tcp ip hdrlength > 5 counter drop を置き、IPオプションを含むIPv4 TCPパケットを落とすものです（出典2）。

    この規則には3つの注意書きが付いています（出典2。原文英語）〈重要〉—— ①これはフィルタであって修正ではない。②再起動をまたいで残らない。③一部のワークロードを壊しうるので先に試験せよ。

    ②が実務では一番危ういところです（本記録の評価）〈重要〉。カーネル更新そのものが再起動を要する作業である一方、暫定策は再起動で消えます。 「更新できないから暫定策を入れた」環境で予定外の再起動が起きると、守られているつもりで無防備な状態に戻ります（本記録の判断）—— 入れるなら永続化の仕組み（systemd ユニット・構成管理）まで含めて入れるべきです。

    MPTCP の無効化は効きません（出典2）〈重要〉。Red Hat は「MPTCP は前提条件ではないため、その無効化は完全な緩和ではない」と明記し、「RHEL は MPTCP を既定で無効にしているが、それでも影響を受ける」と述べています（出典2。原文英語）—— 近年の TCP 系の競合状態の脆弱性では MPTCP が条件になったものがあり、同じ対処を当てはめると外します（本記録の評価）。

    OpenShift には別の手順があります（出典2）。Red Hat は OpenShift 向けの暫定指針（solution 7149635）を用意し、マネージド OpenShift サービスには別の手順を示しています（出典2）—— ノード単位の nftables 規則では Pod 間の通信が守られないと明記されています（出典2）〈重要〉。コンテナ基盤では「ノードに入れたから終わり」が成立しません（本記録の整理）。

    一つ、守りに転用できる点があります（本記録の判断）〈重要〉。速報の規則は counter drop です。 IPオプション付きのIPv4 TCPパケットは平常時にほとんど来ないため、このカウンタが伸びること自体が「誰かが試している」指標になります。 規則を入れるなら、カウンタを監視に載せるべきです（公表に記載は無い。本記録の判断）。

    4日でアプライアンスへ波及した——棚卸しが「OS」止まりだと見えない波及・関係先

    Red Hat の速報は2026年10月30日、WatchGuard の勧告は11月3日です（出典2・3）〈重要〉—— 4日の差で、Linux ディストリビューションの問題がネットワーク機器の問題になりました（本記録の算出）。

    WGSA-2026-0033「Linux Kernel IPv4 Use-After-Free Vulnerability」は Critical で、対象は Dimension 2.0 以降・Fireware OS 2025.1 および 12.0 以降・WatchGuard AP 1.0 以降です（出典3）。報道によれば WatchGuard は、Fireware OS と WatchGuard AP は脆弱なカーネルを含むがこの脆弱性が開くリモートコード実行の連鎖の影響は受けず、Dimension は脆弱な Ubuntu で動いていて修正はまだ提供されていない、と説明しています（出典5。原文英語）〈重要〉〈未確定3〉。

    「脆弱なコードは入っているが、連鎖は成立しない」という説明の扱いが難しいところです（本記録の評価）〈重要〉—— これはベンダー側の内部構成の知識に依存する判断で、利用者側では検証できません。 一方で WatchGuard は、その Fireware OS と AP を勧告の対象として明示してもいます（出典3）。実務的には「対象として挙がった以上、ベンダーの修正提供を追う」のが素直です（本記録の判断）。

    ここから引ける一般則があります（本記録の評価）〈重要〉。自組織の脆弱性管理が「OS のパッチ適用」までで止まっていると、中で Linux が動いているアプライアンス（ファイアウォール・無線 AP・管理サーバ・ストレージ・ロードバランサ・監視装置）が抜けます。 本件では、管理プラットフォーム（Dimension）と無線 AP が対象に入りました（出典3）—— どちらも「サーバ」として管理台帳に載っていないことが多い機器です。

    手順: **修正済みカーネルへ更新する**（出典2・4）〈重要〉—— **RHEL 10 は RHSA-2026:93413、RHEL 9 は 93412、 RHEL 8 のカーネルは 93414、kernel-rt は 93415**（出典4）。　副作用: **カーネル更新は再起動を要する**（本記録の整理）〈重要〉—— **無停止が前提のシステムでは、更新の実施そのものが計画作業になり、 その間は暫定策で凌ぐことになる**（本記録の評価）。 **OpenShift のノード更新はローリング再起動となり、 Pod の退避とディスラプションバジェットの確認が要る**（本記録の評価）。

    手順: **アプライアンス・仮想基盤の棚卸しを、OS だけでなく 「中で Linux が動いている製品」まで広げる**（本記録の判断。公表に記載は無い）〈重要〉—— **本件では WatchGuard の Dimension・Fireware OS・AP が対象に入った**（出典3）。　副作用: **棚卸しの対象が広がり、ベンダーへの問い合わせ件数が増える**（本記録の評価）—— **一方で、ベンダーが「影響なし」と明記しない限り 利用者側では判断できないため、この作業は省けない**（本記録の判断）。
