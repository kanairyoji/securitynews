INC-2026-0902cwpdoor——CWPを差し替える後門

サーバ管理パネル Control Web Panel の Web サーバ本体（cwpsrv）を 「更新」の名目で差し替える受動型の後門 cwpdoor が公表された（奇安信 XLab・2026年11月5日）—— 独立したマルウェアではなく cwpsrv のソースに悪性コードを入れて再コンパイルしたもので、 3つの HTTP ヘッダ（X-Ngx-Integrity-Time / -Data / -Sig）で検証が通ったときだけ コマンドを実行し、同時にその要求のログ記録を抑止する。 VirusTotal での検出率は0、インターネットに露出した CWP は34万超

脅威・攻撃キャンペーン初報のみ有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年11月5日（奇安信 XLab による公表） 最終更新: 2026年11月6日（本記録の作成。XLab の中国語版・英語版を取得して裏を取った時点）

奇安信 XLab は2026年11月5日、サーバ管理パネル Control Web Panel（CWP）のWeb サーバ本体を差し替える受動型の後門を公表しました（出典1・2）〈重要〉。同社はこれを cwpdoor と名付けました（出典1・2）。

発見の端緒は2026年6月29日です（出典1・2）。XLab の大網威脅感知システム（CTIA）がcwpsrv_update.sh という名前の怪しいスクリプトを捕捉しました（出典1・2）。このスクリプトは、136.0.141.71 から cwpsrv というファイルを取ってきて、システム上の同名ファイルを置き換えるものでした（出典1・2）。

cwpdoor は独立したマルウェアではありません（出典1・2）〈重要〉—— 攻撃者が cwpsrv のソースコードに悪性コードを入れ、再コンパイルしたものです。 cwpsrv は、CWP 自身の管理パネル画面と内蔵アプリを動かすための専用 Web サーバで、実体は CWP が Nginx を基に作ったカスタム版です（出典1・2）。

受動型であることが本件の核です（出典1・2）〈重要〉。通常動作では悪性の挙動を見せず、正規の cwpsrv とまったく同じように振る舞います。 攻撃者が細工した特定の要求を受け取ったときにだけ、後門の論理が起動します（出典1・2）。そして起動と同時に、その要求のログ記録を抑止します（出典1・2）—— アクセスログにやりとりの痕跡が残りません。

起動の鍵は3つの HTTP ヘッダです（出典1・2）〈重要〉—— X-Ngx-Integrity-Time（タイムスタンプ。±300秒の窓で検証）、X-Ngx-Integrity-Data（Base64 の中身は先頭16バイトが IV、残りが AES-256-CBC の暗号文）、X-Ngx-Integrity-Sig（Base64 の RSA 署名）。 署名の対象は <Time の値>:<Data の値> を連結したもので、内蔵の RSA 公開鍵で検証されます（出典1・2）。どれかが通らなければ、要求は普通のトラフィックとして処理され、後門は起動しません（出典1・2）。AES の鍵は、内蔵 RSA 公開鍵の文字列の SHA-256 ダイジェストから導出されます（出典1・2）。公開鍵自体は各バイトを 0x55 と XOR して隠されています（出典1・2）。

実行は helper 子プロセスが担います（出典1・2）。検証を通ると、主プロセスが命令を復号し、Unix ドメインソケット ngx_http_integrity_helper 経由で helper へ渡します（出典1・2）。実行結果は AES で暗号化され、application/octet-stream の HTTP 200 応答として攻撃者へ返ります（出典1・2）。

検出率は0でした（出典1・2）〈重要〉。2026年9月30日、ブラジルから evidencia.tgz が VirusTotal へ上げられました（出典1・2）。中身は2つの悪性ファイル——libkeyutils.so.1.5.2 と cwpsrv.suspeito です。 前者はほとんどのベンダーが Ebury 後門として正しく判定しましたが、後者の検出率は0でした——そのファイルが cwpdoor です（出典1・2）。XLab はこれを「この攻撃活動が実験的なものではなく、在野に実際の被害者が存在することを示す」と述べています（出典1・2）。

露出面は大きいです。 奇安信の網絡空間測絘（Hunter）プラットフォームのデータでは、直近1か月でインターネットに露出していた CWP のインスタンスは34万を超えており、そのすべてが cwpdoor の潜在的な感染対象です（出典1・2）〈重要〉。

伝播の経路は分かっていません（出典1・2）〈重要〉〈未確定2〉—— XLab は「どの脆弱性を通じて伝播しているか分からない」「Ebury と cwpdoor に関連があるかも分からない」として、同業他社と読者に情報提供を呼びかけています（出典1・2）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**XLab が公表した投下と起動の流れを段階に並べたものである**（出典1・2）〈重要〉。 **初期侵入の経路は公表されていない**〈未確定2〉—— **分かっているのは、投下スクリプトが root 権限で動く必要があることだけであり、 その時点で攻撃者はすでに root を持っていた**（出典1・2。本記録の整理）。 **各段階の「検知の機会」は公表されている検査方法を本記録が整理したものであり、 「効きえた対策」は本記録の評価である。**

  1. 1. 初期侵入推定[1] [2]
    **公表されていない**（出典1・2）〈重要〉〈未確定2〉—— **XLab は「cwpdoor がどの脆弱性を通じて伝播しているか分かっていない」と明記している** （出典1・2）。 **分かっているのは、投下スクリプトが root 権限で動く必要があることだけである**（出典1・2）—— **つまりこの段が終わった時点で攻撃者は root を持っている**（本記録の整理）。 **同じアーカイブに Ebury（libkeyutils.so.1.5.2）が同梱されていたが、 XLab は「関係は不明で、同じサーバに別々の攻撃者が植えた可能性もある」としている** （出典1・2）〈未確定3〉—— **Ebury を初期侵入の経路と断定してはならない**（本記録の明示）。
    根拠: XLab の記述（出典1・2）
  2. 2. 永続化確認済[1] [2]
    **攻撃者は `cwpsrv_update.sh` を root で実行し、 正規の `/usr/local/cwpsrv/bin/cwpsrv` を後門入りのバイナリで上書きする**（出典1・2）〈重要〉。 **手順は慎重である**（出典1・2）—— **①ローカルのバージョンを調べ、②対応するバイナリを 136.0.141.71 から取得して バージョン一致を確認し、③元のファイルを `cwpsrv.prev-YYYYMMDD-HHMMSS` で退避し、 ④サービスを停止し、⑤上書きし、⑥起動して master/worker/helper の生存を確認し、 ⑦失敗すれば自動で巻き戻し、成功すれば一時ファイルと退避ファイルを削除する。** **永続化の実体は「正規のサービスそのもの」である**（本記録の整理）〈重要〉—— **cron も systemd ユニットも新しいプロセスも追加されない。 OS が起動するたびに正規の手順で cwpsrv が立ち上がり、その中に後門がいる。**
    根拠: XLab によるスクリプト解析（出典1・2）
  3. 3. C2通信確認済[1] [2]
    **後門は受動型である**（出典1・2）〈重要〉—— **自分から外へ繋がず、攻撃者からの HTTP/HTTPS 要求を待つ。** **起動は3つのヘッダで制御される**（出典1・2）—— **`X-Ngx-Integrity-Time`（タイムスタンプ。±300秒の窓で検証）、 `X-Ngx-Integrity-Data`（Base64。先頭16バイトが IV、残りが AES-256-CBC の暗号文）、 `X-Ngx-Integrity-Sig`（Base64 の RSA 署名）。** **署名の対象は `<Time の値>:<Data の値>` の連結で、内蔵の RSA 公開鍵で検証される** （出典1・2）—— **3つが束ねられ、±300秒の窓と併せてリプレイ防止と認可の制御を担う**（出典1・2）。 **公開鍵は各バイトを 0x55 と XOR して隠されており、 AES の鍵はその公開鍵文字列の SHA-256 ダイジェストから導出される**（出典1・2）。 **検証のどれかが通らなければ、要求は普通のトラフィックとして処理され、 後門は起動しない**（出典1・2）〈重要〉。 **実装は2つの関数である**（出典1・2）—— **`ngx_http_integrity_init`（設定解析 `ngx_http_block` の終盤で呼ばれ、 `ngx_modules` を走査してログモジュールの索引を控え、 残存 helper を掃除し、Unix ドメインソケット `ngx_http_integrity_helper` を作って束ね、 helper 子プロセスを生む）と `ngx_http_integrity_check`（`ngx_http_process_request` の入口で呼ばれ、 外部からの起動点になる）。**
    根拠: XLab による逆解析（出典1・2）
  4. 4. 実行確認済[1] [2]
    **検証を通ると、主プロセスが命令を復号し、 Unix ドメインソケット `ngx_http_integrity_helper` 経由で helper 子プロセスへ渡して実行させる**（出典1・2）〈重要〉。 **実行結果は AES で暗号化され、 `application/octet-stream` の HTTP 200 応答として攻撃者へ返る**（出典1・2）—— **これにより双方向の暗号化された隠密な指令チャネルが成立する**（出典1・2）。 **実行される内容は「攻撃者が下した任意のコマンド」であり、 cwpsrv が root で動く構成であればその権限で動く**（出典1・2。本記録の整理）—— **XLab は「後門は任意コマンドを実行できるため、 関連する資格情報は漏洩したものとみなすべきである」と述べている**（出典1・2）。 **実際に何に使われたかは公表されていない**〈未確定6〉。
    根拠: XLab による逆解析（出典1・2）
  5. 5. 検知回避確認済[1] [2]
    **回避は3段構えである**（出典1・2）〈重要〉。 **①正規バイナリの差し替え——独立したマルウェアのファイルが置かれないため、 VirusTotal での検出率は0だった**（出典1・2）。 **②受動的な起動——通常動作では悪性の挙動を見せず、正規の cwpsrv と同じに振る舞う** （出典1・2）。 **③ログ抑止——起動要求に当たると、その要求のモジュール文脈配列を複製して改竄し、 ログモジュールに対応する文脈ポインタを差し替える。 これにより、この要求は正常にログへ書かれず、追跡の鎖が切れる**（出典1・2）〈重要〉。 **投下の段でも痕跡が消されている**（出典1・2）—— **バイナリの atime/mtime と親ディレクトリのタイムスタンプが元の値に戻され、 `history -d` で当該セッションのコマンド履歴が削除される。** **XLab はこの組み合わせを「『直接正常な cwpsrv バイナリを置き換える』に 『受動的な起動』を合わせ、さらに『ログ抑止』を重ねた技術の組み合わせが cwpdoor の隠蔽性を極めて高めている」と評している**（出典1・2。本記録の訳）。

    独立したマルウェアではなく、正規の Web サーバそのものが後門だった原因・手口

    cwpdoor は、ディスクに置かれる新しい悪性ファイルではありません（出典1・2）〈重要〉。攻撃者は cwpsrv のソースコードに悪性コードを入れ、再コンパイルしました（出典1・2）。cwpsrv は、CWP 自身の管理パネル画面と内蔵アプリを動かす専用 Web サーバで、実体は CWP が Nginx を基に作ったカスタム版です（出典1・2）。

    この選択が3つの帰結を生みます（本記録の整理）〈重要〉。

    第一に、検出されません。 2026年9月30日にブラジルから VirusTotal へ上がった evidencia.tgz には2つの悪性ファイルが入っていました（出典1・2）—— libkeyutils.so.1.5.2 はほとんどのベンダーが Ebury 後門として正しく判定しましたが、cwpsrv.suspeito の検出率は0でした。後者が cwpdoor です（出典1・2）〈重要〉。ファイル全体としては正規のサーバプログラムに見えるためです（本記録の評価）。

    第二に、永続化の仕掛けが要りません（本記録の評価）〈重要〉。cron のエントリも、新しい systemd ユニットも、常駐する別プロセスも追加されません。OS が起動するたびに、正規の手順で cwpsrv が立ち上がり、その中に後門がいます。 「見慣れないプロセスを探す」という点検が空振りします。

    第三に、プロセスの構成も正規のままです（出典1・2）。投下スクリプトは差し替え後に master / worker / helper の各プロセスが生きているかを確認し、失敗すれば自動で巻き戻します（出典1・2）〈重要〉—— 攻撃者がサービスの健全性をここまで気にしているのは、壊れて管理者に気づかれることを避けたいからです（本記録の評価）。

    なお XLab は、サンプルが strip されているにもかかわらず関数名などの記号が多く残っており、逆解析の敷居は低いと述べています（出典1・2）—— 隠密性に労力を割いた一方で、バイナリの難読化には手をかけていないという非対称があります（本記録の評価）。

    3つのヘッダが揃ったときだけ起動し、その要求だけログに残らない原因・手口

    後門は受動型です（出典1・2）〈重要〉—— 自分から外へ繋がず、攻撃者からの HTTP/HTTPS 要求を待ちます。

    起動の鍵は3つのヘッダです（出典1・2）〈重要〉。X-Ngx-Integrity-Time にタイムスタンプ、X-Ngx-Integrity-Data に AES で暗号化した命令、X-Ngx-Integrity-Sig に RSA 署名を載せます。 主プロセスが要求の入口で割り込み、タイムスタンプを検証し、内蔵の公開鍵で署名を検証します（出典1・2）。どれかが通らなければ、要求は普通のトラフィックとして処理され、後門は起動しません（出典1・2）。

    仕掛けは丁寧に作られています（出典1・2）。署名の対象は <Time の値>:<Data の値> を連結したものです—— だからタイムスタンプだけ、あるいは暗号文だけを書き換えると署名が無効になります。 3つが束ねられていることと ±300秒の時間窓が、リプレイ防止と認可の制御を同時に担っています（出典1・2）〈重要〉。公開鍵は各バイトを 0x55 と XOR して隠されており、AES-256-CBC の鍵はその公開鍵文字列の SHA-256 ダイジェストから導出されます（出典1・2）。X-Ngx-Integrity-Data の Base64 を解くと、先頭16バイトが IV、残りが暗号文です（出典1・2）。

    これが防御側に何を意味するか（本記録の評価）〈重要〉。①宛先ベースの検知が効きません——自分から外へ繋がないので、C2 の IP やドメインの照合では捕まりません。 ②捕捉した要求を再送しても起動しません——時間窓と署名があるため、防御側が「本当に後門なのか」を能動的に確かめることもできません。 ③通信は正規の管理パネルへの HTTPS 要求と同じ形です——ヘッダ名を知らなければ区別できません。

    実行の経路はこうです（出典1・2）。検証を通ると、主プロセスが命令を復号し、Unix ドメインソケット ngx_http_integrity_helper 経由で helper 子プロセスへ渡します。実行結果は AES で暗号化され、application/octet-stream の HTTP 200 応答として返ります（出典1・2）。

    そして、その要求はログに残りません（出典1・2）〈重要〉。実装の仕掛けまで公表されています—— 起動用の関数 ngx_http_integrity_init は、設定解析 ngx_http_block の終盤で呼ばれ、最初に ngx_modules を走査してログモジュールの索引を控えます（後のログ抑止のため）。起動要求に当たったとき、その要求のモジュール文脈配列を複製して改竄し、ログモジュールに対応する文脈ポインタを差し替えます（出典1・2）。「これによりこの要求は正常にログへ書かれず、追跡の鎖がそこで切れる」（出典1・2。本記録の訳）。

    ls と stat で「変わっていない」と読める——点検の前提そのものが潰されている評価・解釈

    投下スクリプトが消す痕跡を並べます（出典1・2）〈重要〉。①新しいバイナリの atime と mtime を、元のファイルの古い時刻に戻す。②親ディレクトリのタイムスタンプも元に戻す。③history -d で当該セッションのコマンド履歴を削除する。④成功すれば一時ファイルと退避ファイルを削除する。 これは成功時だけでなく失敗時にも行われます（出典1・2）。

    公表の表現はこうです——「その結果、ls や stat といった通常の点検では置き換えられたファイルが『一度も変更されていない』ように見える」（出典1・2。本記録の訳）〈重要〉。

    ここに、本件から引ける一番広い教訓があります（本記録の評価）〈重要〉。root を取られた後のホストでは、ホスト上の記録を信じる点検がすべて成立しません。 ファイルの更新時刻は戻され、アクセスログは抑止され、コマンド履歴は消され、マルウェア検出は検出率0です。

    残っているものは2種類だけです（出典1・2 の検査方法。本記録の整理）〈重要〉—— ①時刻に依存しない「内容」の比較（ハッシュ）。②プロセスとソケットの構造。

    XLab が示した検査方法は、まさにこの2種類です（出典1・2）。ss -axp | grep integrity（Unix ドメインソケット ngx_http_integrity_helper の有無）。ps aux | grep cwpsrv（不審な helper 子プロセスの有無）。strings /usr/local/cwpsrv/bin/cwpsrv | grep X-Ngx-Integrity（バイナリ内の文字列）。

    ただし、どれも亜種には当たりません（本記録の評価）〈重要〉—— ソケット名もヘッダ名も、このサンプル固有の値です。攻撃者が名前を変えれば空振りします。 また、正規の cwpsrv も master / worker / helper の構成を持つため（投下スクリプトがその3つの生存を確認している事実がそれを示します）、「helper があること」自体は異常ではありません（出典1・2。本記録の整理）。

    したがって、恒久的に有効なのは一つだけです（本記録の判断）〈重要〉—— 重要バイナリのハッシュ基準値を「ホストの外」に保管し、そこと比較すること。 ホスト上の情報は全部疑わしい、という前提に立つしかありません。

    復旧手順には、退避ファイルが消えている場合の空白がある復旧の経過

    XLab が示した復旧手順は3段です（出典1・2）〈重要〉—— ①/usr/local/cwpsrv/bin の中にある攻撃者が退避した正規ファイル（cwpsrv.prev-YYYYMMDD-HHMMSS 形式）を探し、悪性の cwpsrv と差し替える。②最新版へ更新し、ss -axp | grep integrity がもう当たらないことを確認する。③パネルの資格情報をすべて直ちに更新し、後門が任意コマンドを実行できることから関連する資格情報は漏洩したものとみなし、ホストが失陥した前提で同じサーバ上の他の脅威も点検する。

    ①には注意が要ります（本記録の評価）〈重要〉。同じ公表のスクリプト解析によれば、投下が成功した場合、スクリプトは一時ファイルと退避ファイルを削除します（出典1・2）—— つまり退避ファイルが残っているのは、投下が途中で失敗した場合や複数回の投下が行われた場合に限られる可能性があります（本記録の整理）。退避ファイルが無い場合にどうするかは、公表に記載がありません（本記録の確認）—— 実務的には、正規の配布物から取り直すことになります（本記録の判断）。

    ③の範囲が重い作業です（本記録の評価）〈重要〉。CWP が管理するのはウェブサイト・DNS・メールです（出典1・2）—— 資格情報をすべて更新するということは、パネルで管理している全サイト・全ドメイン・全メールアカウントが対象になります。 共用ホスティングであれば、同じサーバに載っている他の顧客環境にも調査と再設定が及びます（本記録の評価）—— この範囲の広さ自体が復旧を遅らせます。

    そして、伝播の経路が分かっていないことが②を不安定にします（出典1・2）〈重要〉〈未確定2〉。XLab は「cwpdoor がどの脆弱性を通じて伝播しているか分かっていない」と明記しています。 CVE 番号も付いていません（本記録の確認）—— つまり「パッチを当てれば防げる」という形の対処が存在しません。 最新版へ更新するのは「正規のバイナリに戻す」という意味であって、再び差し替えられないことの保証にはなりません（本記録の整理）。

    したがって本記録は、公表に無い対策を一つ加えます（本記録の判断）〈重要〉—— 管理パネルの画面を、インターネット全体から到達できない場所に置くことです。 後門の起動は HTTP/HTTPS の要求を通じて行われるため、要求が届かなければ起動しません（出典1・2。本記録の整理）。ただしこれは、管理パネルが「SSH のコマンド操作を代替する」ために導入されるものであることと正面からぶつかります（出典1・2）—— 利便性を削る判断になります。

    段階検知の機会効きえた対策
    初期侵入公表されていない
    **この段についての検知の指針は公表されていない**（本記録の確認）〈重要〉〈未確定2〉。 **CVE 番号が付いていないため「パッチを当てれば防げる」という形にならない** （本記録の評価）〈重要〉—— **対処は、パネル画面の到達範囲を絞ること、 root を取られる経路（パネルの資格情報・SSH・同居する他のソフトウェア）を 一般論として潰すことに向かう。**
    影響を限定できた管理パネルの画面をインターネット全体から到達できない場所に置く（VPN・許可元IP）
    侵入を防げたパネルの管理者資格情報を強固にし、多要素認証を要求する
    影響を限定できた同じホストに同居する他のソフトウェア（SSH・メール・DNS）の更新を維持する
    永続化機会はあったが検知できず
    **差し替えの瞬間には痕跡が出る**（本記録の評価）〈重要〉—— **サービスの停止と起動、バイナリの書き換え、 外部（136.0.141.71）への HTTP 取得と結果報告。** **しかしスクリプトは、成功・失敗のいずれでも 新しいバイナリの atime/mtime と親ディレクトリのタイムスタンプを元に戻し、 `history -d` でコマンド履歴を消す**（出典1・2）〈重要〉—— **「その結果、`ls` や `stat` といった通常の点検では 一度も変更されていないように見える」**（出典1・2。本記録の訳）。 **したがって、時刻に依存しない完全性検査（ハッシュの比較）を 事前に用意していなければ、この段は見えない**（本記録の判断）。
    検知できた重要バイナリのハッシュを外部に保管した基準値と定期比較する（時刻ではなく内容で見る）
    検知できたファイル完全性監視（FIM）を /usr/local/cwpsrv/bin に適用し、変更イベントを即時転送する
    検知できたサービスの予期しない再起動を監視対象に載せる
    侵入を防げた外向き通信を許可リスト方式にし、未知のIPへの HTTP 取得を遮断する
    C2通信現実的な検知機会なし
    **通信の側からの検知は難しい**（本記録の評価）〈重要〉—— **要求は正規の管理パネルへの HTTPS 要求と同じ形をしており、 ヘッダ名を知らなければ区別できない。** **自分から外へ繋がないため、宛先ベースの検知（C2 の IP・ドメインの照合）も効かない** （本記録の整理）。 **捕捉した要求を再送しても、±300秒の窓と署名のため起動しない**（出典1・2）—— **つまり防御側が「本当に後門なのか」を能動的に確かめることもできない**（本記録の評価）。 **検知できるのはホスト側である**（出典1・2 の検査方法）〈重要〉—— **ソケット名・helper プロセス・バイナリ内の文字列。**
    検知できたss -axp で ngx_http_integrity_helper ソケットの有無を点検する
    検知できた管理パネルへの HTTPS 要求のヘッダを記録し、未知の X- ヘッダを検知する（TLS 終端が手元にある場合）
    侵入を防げた管理パネルの画面をインターネット全体から到達できない場所に置く（要求自体を届かせない）
    実行機会はあったが検知できず
    **helper 子プロセスが生むプロセスは、ホスト側の記録に残りうる**（本記録の評価）〈重要〉—— **Web サーバの子プロセスからシェルやネットワークツールが起動すれば、 それは異常な親子関係である。** **公表はプロセスの検査（`ps aux | grep cwpsrv`）を挙げているが、 実行された命令の内容を追う手段は示していない**（出典1・2。本記録の確認）。 **auditd や eBPF による実行記録があれば追えるが、 それを前提にできる環境は限られる**（本記録の評価）。
    検知できたWeb サーバプロセスからの子プロセス生成（シェル・curl・コンパイラ）を検知する
    検知できたauditd / eBPF で execve の記録を取り、ホスト外へ転送する
    影響を限定できたcwpsrv を root 以外の最小権限で動かす（可能な構成であれば）
    検知回避現実的な検知機会なし
    **設計された回避に対して、通常の点検には現実的な機会が無い**（本記録の評価）〈重要〉—— **ファイルの更新時刻を見る点検は無効（時刻が戻されている）、 アクセスログを見る点検は無効（抑止されている）、 コマンド履歴を見る点検は無効（削除されている）、 マルウェア検出は無効（検出率0）。** **残っているのは、時刻に依存しない内容の比較（ハッシュ）と、 プロセス・ソケットの構造である**（出典1・2 の検査方法。本記録の判断）〈重要〉。 **これが本件の最大の教訓である**（本記録の評価）—— **「ホスト上の記録を信じる点検」は、root を取られた後には成立しない。**
    検知できた重要バイナリのハッシュ基準値を「ホストの外」に保管し、そこと比較する
    検知できたアクセスログをホスト外へ即時転送し、ホスト上のログだけに依存しない
    検知できたss / ps によるソケット・プロセス構造の点検を定期化する

    CISO・経営層への示唆
    • **「root を取られた後は、ホスト上の記録を点検の根拠にできない」を 前提として明文化する。**
      **本件では、ファイルの更新時刻が元に戻され、親ディレクトリのタイムスタンプも戻され、 コマンド履歴が `history -d` で消され、起動要求のアクセスログが抑止され、 VirusTotal の検出率は0だった**（出典1・2）〈重要〉—— **「`ls` や `stat` といった通常の点検では一度も変更されていないように見える」** （出典1・2。本記録の訳）。 **ホスト上の情報を信じる点検は、すべて空振りする**（本記録の評価）。
      取るべき行動 **①重要なサーバの重要バイナリ（Web サーバ・SSH・管理パネル）のハッシュ基準値を 「ホストの外」に保管する仕組みがあるか確認する。 ②無ければ、対象を絞って（例: 外部公開しているホストの10ファイル）作る。 ③アクセスログ・認証ログをホスト外へ即時転送しているかを確認する—— ホスト上のログだけに依存している箇所を洗い出す。**
    • **「中で何が動いているか分からない無料の管理パネル」を 資産台帳とリスク評価の対象に入れる。**
      **対象は CentOS 等向けの無料のオープンソース管理パネルで、 直近1か月でインターネットに露出していたインスタンスは34万超である**（出典1・2）〈重要〉。 **安価なレンタルサーバ・VPS・小規模ホスティングで使われる類の製品であり、 正式な調達プロセスを通らずに「立てた人」の判断で入ることがある**（本記録の評価）—— **台帳に無いものは、本件のような公表が出ても誰も照合しない。**
      取るべき行動 **①自組織（および子会社・部門）で使っているサーバ管理パネルを棚卸しする （CWP・cPanel・Plesk・Webmin 等）。 ②それぞれの画面がインターネット全体から到達可能かを確認する。 ③外部委託先・ホスティング事業者に対し、同種のパネルの使用有無を照会する。**
    • **CVE 番号が付いていない脅威への対応手順を持つ。**
      **本件は脆弱性の公表ではなく、在野で稼働している後門の発見である**（出典1・2）〈重要〉—— **XLab は「どの脆弱性を通じて伝播しているか分かっていない」と明記し、 CVE 番号も付いていない**〈未確定2〉。 **脆弱性管理の仕組みが CVE 番号を起点に動く組織では、 この種の情報が業務プロセスに乗らない**（本記録の評価）。
      取るべき行動 **①脅威情報の受け口が「CVE 番号があるもの」に限定されていないか確認する。 ②番号の無い脅威（マルウェア・手口の公表）を受けたときに 誰が影響判定をするかを決めておく。 ③本件のような IoC（ハッシュ・IP・ソケット名・ヘッダ名）を 自環境で照合する手順を用意する。**
