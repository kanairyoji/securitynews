INC-2026-0903EDK II のPXEに起動前RCE

UEFI の参照実装 EDK II の PXE ネットワーク起動ドライバに、 Secure Boot と計測起動の検証が終わる前に ring 0 でコードを実行させうる 境界外書き込みが公表された（CVE-2026-97631・TianoCore GHSA-99cj-7hg9-mp4m・ CVSS 4.0 で 9.5）——ICMP エラー報文の複製ループが固定504バイトの Mode.IcmpError を越えて書き、しかも宛先ポインタを分割ごとではなく 累積長で進める。公表は2027年1月の予定だったが、 修正コードを含む公開のプルリクエストが先に出たため10月22日へ繰り上がった

TianoCore は2026年10月22日、UEFI の参照実装 EDK II のPXE ネットワーク起動ドライバに境界外書き込みがあるとして、勧告 GHSA-99cj-7hg9-mp4m を公開しました（出典1）〈重要〉。題名は「Pre-boot RCE in EDK II PXE driver」、CVE-2026-97631。深刻度は Critical、CVSS 4.0 のスコアは 9.5、ベクターは AV:N/AC:L/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H です（出典1）。

どこにあるか。 部品は NetworkPkg、場所は PXE Base Code ドライバNetworkPkg/UefiPxeBcDxe です（出典1）。壊れている関数は2つ——IPv4 の PxeBcIcmpErrorDpcHandle とIPv6 の PxeBcIcmp6ErrorDpcHandle です（出典1）〈重要〉。書き込み先はドライバの私有コンテキスト構造体の中にあるMode.IcmpError フィールドで、固定504バイトです（出典1）。

何が間違っているか。 勧告の原文は「複製ループの境界処理が IPv4 と IPv6 の両方のハンドラで誤っている」です（出典1。原文英語。本記録の訳）〈重要〉。誤りは2つ重なっています（出典1・3）—— ①報文の長さが504バイトを超えても複製を続ける、②宛先ポインタを各分割の長さではなく累積長で進める。 結果として、超長の報文が攻撃者の制御するデータをフィールドの外の隣接メモリへ書き込みます（出典1）。受信経路のどこにも、事前に報文長を制限する箇所がありません（出典3）。

何が起きるか。 勧告は影響を2つに分けています（出典1）〈重要〉。(a) ドライバの私有データが決定的に破壊され、次の ICMP エラーで DXE コアが CPU 例外を起こし、起動が止まる。(b) 対象のファームウェアのビルドを知っている攻撃者は「偽造したイベントを仕込み」、CoreSignalEvent() に攻撃者が与えたバイト列を DXE フェーズで実行させうる（出典1。原文英語。本記録の訳）。

ここが本件の重さです（出典1。本記録の評価）〈重要〉。DXE フェーズは、Secure Boot と計測起動が検証を終える前の段階です。 つまり、それらの機構が立ち上がる前にコードが走り終わります。

修正はまだ入っていません（出典1）〈重要〉。勧告の「Patched versions」欄は本記録の取得時点で「Not patched currently」のままで、修正はプルリクエスト #13302 として参照されています（出典1）。Red Hat の CVE ページは本件を Critical とし、CVSS 3.1 では 8.8、ベクターは AV:A（隣接ネットワーク）です（出典2）〈重要〉—— TianoCore の CVSS 4.0 が AV:N（ネットワーク）であるのと食い違います〈齟齬1〉。Red Hat は「露出はネットワーク起動のシーケンスに限られ、ローカルストレージから起動する仮想マシンや、起動後に通常動作している仮想マシンは露出しない」と述べています（出典2。原文英語。本記録の訳）。

    504バイトのフィールドを越える複製と、分割ごとではなく累積長で進む宛先ポインタ原因・手口

    場所は PXE Base Code ドライバ NetworkPkg/UefiPxeBcDxe です（出典1）〈重要〉。PXE ネットワーク起動のあいだ、このドライバはICMP 差錯報文——ルータが「この包は届かない」と知らせる類のもの——を受け取るための受信要求を掛けています（出典1・3）。報文を受け取るたびに、ドライバはそれを私有コンテキスト構造体のMode.IcmpError フィールドへ複製します。このフィールドは固定504バイトです（出典1）。

    誤りは複製ループの境界処理にあります（出典1）〈重要〉。勧告の原文は「複製ループの境界処理が IPv4 と IPv6 の両方のハンドラで誤っている」です（出典1。原文英語。本記録の訳）。壊れている関数は IPv4 の PxeBcIcmpErrorDpcHandle とIPv6 の PxeBcIcmp6ErrorDpcHandle の2つです（出典1）。

    具体的には2つの誤りが重なっています（出典1・3）〈重要〉—— ①報文の長さが504バイトを超えても、ループは複製を続ける。②宛先ポインタを「各分割の長さ」ではなく「累積長」で進める。 結果として、超長の報文が攻撃者の制御するデータをフィールドの外の隣接メモリへ書き込みます（出典1）。そして、受信経路のどこにも事前に報文長を制限する箇所がありません（出典3）。

    弱点の分類は3つ挙げられています（出典1）—— CWE-120（サイズ未検査のバッファ複製）・CWE-131（バッファサイズの誤計算）・CWE-787（境界外書き込み）。 Red Hat の CVE ページは CWE-787 のみを挙げています（出典2）。

    「両方のハンドラ」であることが実務に効きます（本記録の評価）〈重要〉—— IPv6 を無効にすれば済む、という対処が成立しません。IPv4 側も同じく脆弱です。

    悪用の条件は、聞くと単純です（出典3）。「任意のネットワーク位置から対象機器のIPアドレスへ単播の報文を1つ送るだけ。パスワードも、既存のアクセス権限も要らない。要求されるのは1つだけ——対象が PXE ネットワーク起動を使っていること」（出典3。本記録の訳）〈重要〉。ただしコード実行まで持っていくには、対象のファームウェアの具体的なビルドを知っている必要があります（出典1）〈未確定6〉。

    Secure Boot も TPM も、この層には届かない評価・解釈

    勧告が記述する影響の重い側はこうです（出典1。原文英語。本記録の訳）〈重要〉—— 「対象のファームウェアのビルドを知っている攻撃者は、偽造したイベントを仕込み、CoreSignalEvent() に攻撃者が与えたバイト列を DXE フェーズで実行させうる」。

    DXE フェーズは、Secure Boot と計測起動が検証を終える前の段階です（出典1）〈重要〉。つまり、それらの機構が立ち上がる前にコードが走り終わります。 実行は CPU の ring 0 ——OS カーネルよりさらに下です（出典3）。

    この位置で何が崩れるか（出典3。本記録の整理）〈重要〉。全ディスク暗号化の信頼の根は TPM にあり、TPM の信頼の根は起動チェーンにあり、起動チェーンの最初の環はファームウェアです。 ファームウェアが取られれば、その下にあるすべての保証が仮定に変わります。

    報道は Dragos の最高研究責任者（Metasploit の作者）HD Moore の発言としてこう伝えています（出典3。本記録の訳）〈齟齬3〉—— 「攻撃者はこのバグで、起動過程がまだ TPM のような機微な部品にアクセスできる時点でプログラムフローを奪える」「攻撃者が短期のネットワークアクセスを持つ状況で、これはディスク暗号化を破るために使われうる（機器が盗まれた場面ならさらに容易）」。 本記録はこの発言を一次資料で確認していません（本記録の明示）。

    遠隔証明（attestation）についても同じ問題があります（出典3）〈重要〉。「遠隔証明の機構の役目は『このハードウェアは綺麗だ』とサーバに証明することで、検証するのは起動チェーンの計測値である。このチェーンが上流で汚染されていれば、証明は依然として通る」（出典3。本記録の訳）。

    したがって、社内説明の整理を変える必要があります（本記録の判断）〈重要〉—— 「Secure Boot と TPM を入れ、ディスクも暗号化しているのでサーバが盗まれてもデータは読めない」という説明は、本件が該当する機器については成り立ちません。 これらの機構を無効にするという意味ではありません（本記録の明示）—— 有効にすべきものは有効にする。ただし、これを盾として使ってはいけない、という整理です（出典3の趣旨）。

    軽い側の影響も、現場では無視できません（出典1・3）。ドライバの私有データが決定的に破壊され、次の ICMP エラーで DXE コアが CPU 例外を起こし、起動が止まります（出典1）—— 報道は「無人の機械室にとって、1台が PXE 段階で止まって再起動を繰り返すと運用担当は夜中に出向くことになる」と書いています（出典3。本記録の訳）。

    CVSS が 9.5 と 8.8 で、攻撃経路の判定も N と A で食い違っている評価・解釈

    2つの一次公表が、本件に異なる評価を付けています（出典1・2）〈重要〉。

    TianoCore の勧告は、深刻度 Critical、CVSS 4.0 で 9.5、ベクターは AV:N/AC:L/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H です（出典1）。AV:N はネットワーク、AT:P は「攻撃前提条件あり」で、後続システムへの影響（SC/SI/SA）もすべて高い。

    Red Hat の CVE ページは、深刻度 Critical、CVSS 3.1 で 8.8、ベクターは AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H です（出典2）〈重要〉。AV:A は隣接ネットワークです。

    食い違いは2か所あります（本記録の整理）〈重要〉〈齟齬1〉。①攻撃経路が N（ネットワーク）か A（隣接ネットワーク）か。②数値が 9.5 か 8.8 か（ただし CVSS 4.0 と 3.1 でそもそも計算式が違います）。

    ①の実務上の差は大きいです（本記録の評価）〈重要〉。AV:A なら攻撃者は同じ L2 セグメントに居る必要があり、AV:N なら任意のネットワーク位置から届きます。 報道の記述は「任意のネットワーク位置から対象機器のIPアドレスへ単播の報文を1つ送る」であり、AV:N 側の読みに沿っています（出典3）—— ただし実際には、PXE 起動中の機器がルーティング可能なIPを持っていて外部からの ICMP が届く構成であるかどうかに依存します（本記録の評価）。

    Red Hat は自分の評価を「preliminary（暫定）で見直しの対象」と明記しています（出典2）〈重要〉—— また CVSS 3.1 の 8.8 は通常の区分では High に当たるのにRed Hat 自身の深刻度評価は Critical であり、数値と区分が噛み合っていません（出典2。本記録の整理）。NVD と cve.org はいずれも「N/A」です（出典2）。

    実務的な扱い方を1つ示します（本記録の判断）〈重要〉—— スコアで優先順位を決めるのではなく、「自組織に PXE 起動している機器があるか」で決めるべきです。 無ければスコアがいくつでも該当せず、あれば攻撃経路が N でも A でも、起動用ネットワークを隔離するという同じ対処に行き着きます。

    修正が行き渡るまでの時間と、「forever bug」という見立て対策・注意喚起

    勧告の「Patched versions」欄は、本記録の取得時点で「Not patched currently」のままです（出典1。本記録の確認）〈重要〉。修正はプルリクエスト #13302 として参照されています（出典1）。

    報道は、修正が行き渡るまでの道筋をこう整理しています（出典3。本記録の訳）〈重要〉—— 「TianoCore が上流を修正する（10月15日）→ 各 IBV が統合する（数週間から数か月）→ OEM が BIOS 更新を出す（数か月）→ 企業が順次適用する（数か月から1年）→ サポートの切れた機器は永遠に適用されない」。 報道は理由も挙げています（出典3）—— 「ファームウェアコードのテストは敷居が高い（実機が要り、書き込めること、文鎮になったら救えること）。ファームウェアベンダーの開発プロセスの成熟度はアプリケーションソフトウェアベンダーに遅れている。問題が出たときの修正周期は四半期単位で、OEM・認証・顧客検証を通す必要があるため」。

    HD Moore の見立てとして報道が伝えるのは「この脆弱性の普遍性を考えると、これは『forever』bug になる可能性が高い——サポートの終わった機器の中に永遠に生き続ける」です（出典3。本記録の訳）〈重要〉〈齟齬3〉。

    報道は PixieFail（2024年初）との比較も置いています（出典3）〈重要〉—— あれも EDK2 の PXE 起動の問題で、一連の脆弱性でファームウェア生態系が半年揺れました。その後、業界は複数回のファジングを行い、OSS-Fuzz に edk2 のプロジェクトがあり、NDSS にも専門の論文がある。それでもこの16年の古い穴は、それらのファジングで見つからなかった。

    したがって、実務の結論は「待たない」ことです（出典3。本記録の判断）〈重要〉。報道は「ベンダーのファームウェア更新が行き渡る前に、まず PXE の範囲を縮めること。『今日のうちに終わり、費用はほぼゼロ、効果は即座に見える』処置のごく少数の一つである」と書いています（出典3。本記録の訳）。イタリア ACN の CSIRT が2026年10月28日の警報で示した助言も同じ内容です（出典3）〈齟齬3〉—— 本記録はこの警報そのものを取得できていません。

    本記録が加える注意を1つ（本記録の判断）〈重要〉—— PXE は既定で有効です（出典3）。「使っていないから無効になっているはず」という前提では点検になりません。1台ずつ設定を確認する必要があります。

    **公表に検知の指針は無い**（本記録の確認）〈未確定1〉。 **実務的には、どの機器が PXE 起動を使っているかを 把握しているかどうかが分かれ目になる**（本記録の評価）〈重要〉—— **報道は「PXE の管理は平時に誰も見ておらず、 アプリにもネットワークにも属さず『装置を組み立てる流れ』に属するため、 事が起きてから『どの機械が PXE を有効にしているか』を 誰も説明できないと分かる」と書いている**（出典3。本記録の訳）。 **また、攻撃の時機が「起動の数秒」に限られるため、 常時監視の網には掛かりにくい**（本記録の評価）。
    侵入を防げたPXE を使っている機器を資産台帳に明示し、使っていない機器では無効化する
    侵入を防げたPXE を必要とする機器を、導入サーバのみが到達できる隔離 VLAN に閉じ込める
    影響を限定できた起動用ネットワークへの ICMP の流入を、導入サーバ以外から遮断する
    実行現実的な検知機会なし
    **この段での検知には現実的な機会が無い**（本記録の評価）〈重要〉—— **OS が立ち上がる前のファームウェア環境であり、 ホスト側の監視も EDR も存在しない。** **検知できる可能性があるのはネットワーク側である**（本記録の判断）—— **起動用ネットワークに504バイトを超える ICMP 差錯報文が流れることは 平常時には無いため、そこを見れば異常として捉えうる。** **ただし、起動用ネットワークに監視を置いている組織は少ない**（本記録の評価）。
    検知できた起動用ネットワークで ICMP のサイズ・発生元を監視し、異常な報文を検知する
    侵入を防げた起動用ネットワークを導入サーバのみに限定し、報文が届かないようにする
    侵入を防げたPXE を無効化する（受信要求そのものが掛からない）
    影響（暗号化・破壊・改ざん）現実的な検知機会なし
    **(a) は観測しやすい**（本記録の評価）〈重要〉—— **PXE 段階で起動が止まり、再起動を繰り返す形で表に出る。** **ただし原因の切り分けは難しい**（本記録の判断）—— **ネットワーク起動の失敗は日常的に起きるため、 「またか」で片付けられる可能性がある。** **(b) は現実的な検知機会が無い**（本記録の判断）〈重要〉—— **計測起動の値が汚染されていても遠隔証明は通ってしまう。** **報道は「遠隔証明の機構の役目は『このハードウェアは綺麗だ』と サーバに証明することで、検証するのは起動チェーンの計測値である。 このチェーンが上流で汚染されていれば、証明は依然として通る」と書いている** （出典3。本記録の訳）〈重要〉。
    検知できたPXE 段階で停止・再起動を繰り返す機器を、障害として記録し原因を追う運用にする
    検知できた起動の計測値（TPM の PCR）の基準値を外部に保管し、変化を検知する
    効果は期待できないSecure Boot・計測起動・TPM・ディスク暗号化を本件の対策として数えない（判断の誤りを避ける）

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    対応の巧拙を評価できる材料が公表資料から得られていません。
    CISO・経営層への示唆
    • **「どの機器が PXE でネットワーク起動しているか」を、 今日答えられる状態にする。**
      **本件の該当条件は「ファームウェアが EDK2 ベースで PXE が有効であり、 ローカルネットワークから起動していること」であり、 PXE は既定で有効である**（出典3）〈重要〉。 **ローカルディスクからのみ起動する機器は影響を受けない**（出典2・3）—— **つまり、該当範囲の判定は PXE の棚卸しで決まる。** **報道は「PXE の管理は平時に誰も見ておらず、 アプリにもネットワークにも属さず『装置を組み立てる流れ』に属するため、 事が起きてから誰も説明できないと分かる」と指摘している**（出典3。本記録の訳）。
      取るべき行動 **①PXE を有効にしている機器の一覧を作る責任者を1人決める（運用の自動化担当が妥当）。 ②高確率の場面から当たる——仮想化クラスタ、ベアメタルの自動導入、 ディスクレスワークステーション、HPC ノード、一部のストレージアレイ。 ③一覧を資産台帳の正式な項目として追加し、以後の新規導入時に記入させる。**
    • **BIOS/UEFI のバージョンを脆弱性管理の対象に入れる。**
      **報道は「多くの企業の脆弱性スキャンは OS・ミドルウェア・アプリを覆っているが、 BIOS/UEFI のバージョンだけが無く、 ベンダーのファームウェア公告も脆弱性データベースに入らない」と指摘している** （出典3。本記録の訳）〈重要〉。 **本件は OS 側のパッチでは塞げず、各 OEM の BIOS/UEFI 更新を待つことになる** （本記録の評価）—— **ファームウェアのバージョンが台帳に無ければ、 更新が出たことにも気づけない。**
      取るべき行動 **①主要機種のファームウェアバージョンの取得方法を調べ、自動収集を作る。 ②CMDB にファームウェアバージョンの項目を追加する。 ③サーバベンダーのファームウェア公告の購読先を登録し、 受信したときの影響判定の担当を決める。**
    • **「Secure Boot と TPM とディスク暗号化があるから大丈夫」という説明を撤回する。**
      **コードが走るのは Secure Boot と計測起動が検証を終える前の DXE フェーズであり、 CPU の ring 0 である**（出典1・3）〈重要〉。 **全ディスク暗号化の信頼の根は TPM にあり、TPM の信頼の根は起動チェーンにあり、 その最初の環がファームウェアである**（出典3。本記録の整理）。 **さらに、計測起動の値が上流で汚染されていても遠隔証明は通る**（出典3）。 **これらの機構を無効にすべきという意味ではないが、 本件の盾としては数えられない**（本記録の明示）。
      取るべき行動 **①「サーバが盗まれてもデータは読めない」という社内・顧客向けの説明文を見直す。 ②本件が該当する機器について、risk 受容の説明を作り直す。 ③遠隔証明に依存している業務（ゼロトラストの機器健全性判定等）があれば、 その前提が本件で崩れうることを記録する。**
    • **「ベンダーの回答が無い機器」を経営報告の対象にする。**
      **EDK II は参照実装であり、各社の実際の統合状況が異なるため、 利用者は自分の機種とファームウェアのバージョンでベンダーへ照会するしかない** （出典3）〈重要〉。 **報道の時点で AMD・Phoenix・AMI・Microsoft・Amazon は回答していない** （出典3）〈齟齬3〉—— **Intel も「OEM のボードメーカーやシステムインテグレータが 統合している可能性がある」と留保を置いている**（出典3）。 **回答が無い状態を「対象外」と読むと、該当機器が全部抜ける**（本記録の評価）。
      取るべき行動 **①CVE-2026-97631 を添えて各サーバベンダーへ照会し、 回答を「影響なしの明記」「潜在的に影響」「未回答」の3区分で記録する。 ②未回答が一定期間（例: 14日）を超えた機器を経営報告に載せる。 ③未回答の機器については、PXE 無効化または隔離を先に実施する。**
    • **ファームウェアの修正が「年単位」で行き渡ることを前提に、 機器のライフサイクル計画へ織り込む。**
      **報道が示す道筋は「上流の修正 → 各 IBV の統合（数週間から数か月） → OEM の BIOS 更新（数か月）→ 企業の適用（数か月から1年） → サポート切れ機器には永遠に適用されない」である**（出典3。本記録の訳）〈重要〉。 **HD Moore の見立てとして「forever bug になる可能性が高い」が伝えられている** （出典3）〈齟齬3〉—— **つまり、サポートの切れた機器を持ち続ける判断そのものが risk になる。**
      取るべき行動 **①サポート期間の切れたサーバ・ストレージの一覧を出す。 ②そのうち PXE を使っているものを特定し、置換か PXE 無効化かを決める。 ③今後の機器調達時に「ファームウェア更新の提供期間」を評価項目に加える。**
    セキュリティ技術者への示唆
    • **PXE を1台ずつ確認する（既定で有効なので「使っていないから無効」は成立しない）。**
      **報道は「PXE は既定で有効」と明記している**（出典3）〈重要〉—— **使っていない機器でも有効なまま放置されている可能性がある。** **一方、ローカルディスクからのみ起動する機器は影響を受けない**（出典2・3）—— **つまり「起動順序でネットワークが入っているか」が判定の分かれ目である**（本記録の整理）。
      取るべき行動 **①BMC / iDRAC / iLO 等の管理インタフェース経由で 起動順序と PXE の有効・無効を一括取得できるか調べる。 ②取得できるなら全台を走査し、できないなら機種別に手順を作る。 ③使っていない機器の PXE を無効化する（起動順序からネットワークを外す）。**
    • **必須の PXE は、導入サーバのみが到達できる隔離 VLAN に閉じ込める。**
      **攻撃面は PXE 起動シーケンスの最中の数秒だけで、 必要なのは対象機器のIPへ単播の報文を1つ届けることである**（出典1・3）〈重要〉。 **したがって、報文が届かなければ成立しない**（本記録の整理）。 **報道が伝えるイタリア ACN の CSIRT の助言も 「必須なら信頼された隔離されたネットワークに限定せよ」である**（出典3）〈齟齬3〉。
      取るべき行動 **①導入用ネットワークを専用 VLAN に分け、導入サーバ以外からの到達を禁じる。 ②その VLAN への ICMP の流入を、導入サーバ以外から遮断する。 ③切り戻しの手順を用意してから適用する（導入自動化が止まると業務影響が出る）。**
    • **IPv6 の無効化を緩和策として数えない。**
      **境界処理の誤りは IPv4 の `PxeBcIcmpErrorDpcHandle` と IPv6 の `PxeBcIcmp6ErrorDpcHandle` の両方にある**（出典1）〈重要〉—— **勧告の原文が「両方のハンドラで誤っている」と明記している。** **したがって、どちらか一方を無効にしても攻撃面が残る**（本記録の整理）。
      取るべき行動 **①緩和策の手順書から「IPv6 無効化」を本件の対策として削る。 ②代わりに PXE の無効化または隔離 VLAN を記載する。 ③「片方を止めた」ことを対策として報告させない。**
    • **PXE 段階での停止・再起動ループを、障害として記録する運用にする。**
      **勧告の影響 (a) は「ドライバの私有データが決定的に破壊され、 次の ICMP エラーで DXE コアが CPU 例外を起こし、起動が止まる」である** （出典1。原文英語。本記録の訳）〈重要〉。 **これは観測しやすい側だが、ネットワーク起動の失敗は日常的に起きるため 「またか」で片付けられやすい**（本記録の評価）。 **報道も「無人の機械室にとって、1台が PXE 段階で止まって 再起動を繰り返すと運用担当は夜中に出向くことになる」と現場の帰結を書いている** （出典3。本記録の訳）。
      取るべき行動 **①PXE 起動の失敗・再起動ループを、記録に残る障害として扱う運用にする。 ②同じ機器で繰り返す場合、起動用ネットワーク側のパケット取得を試みる。 ③504バイトを超える ICMP 差錯報文が流れていないかを確認する （平常時には無い形である）。**
    • **起動用ネットワークでの ICMP を監視対象にする。**
      **攻撃はファームウェア環境で成立するため、ホスト側の監視も EDR も無い** （本記録の評価）〈重要〉—— **検知できる可能性があるのはネットワーク側だけである。** **504バイトを超える ICMP 差錯報文は平常時には流れない**（出典1。本記録の整理）。
      取るべき行動 **①導入用 VLAN にパケット取得の仕組みを置く（スイッチのミラーポート等）。 ②ICMP のサイズと発生元を記録し、異常なものをアラート化する。 ③導入サーバ以外からの ICMP をそもそも遮断したうえで、 遮断ログを監視対象にする。**
    • **TPM の計測値（PCR）の基準値を外部に保管し、変化を検知する。**
      **影響 (b) が成立した場合、ring 0 でのコード実行になり、 起動チェーンの計測値が汚染されても遠隔証明は通る**（出典1・3）〈重要〉—— **報道の表現では「このチェーンが上流で汚染されていれば、証明は依然として通る」** （出典3。本記録の訳）。 **自組織で基準値を持っていなければ、変化そのものに気づけない**（本記録の判断）。
      取るべき行動 **①該当機器の TPM の PCR 値を正常時に取得し、ホスト外に保管する。 ②定期的に取得して比較し、変化があれば調査する。 ③遠隔証明の結果を単独の判断材料にしない設計にする。**

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    システム構成□ **ローカルネットワークから起動している（PXE ネットワーク起動を使っている） サーバ・ストレージ機器があるか**（出典2・3）。**これが該当判定の中心である**（出典1・2・3）〈重要〉—— **ローカルディスク・SSD からのみ起動する機器は影響を受けない**（出典2・3）。 **高確率の場面は、仮想化クラスタ・ベアメタルの自動導入・ ディスクレスワークステーション・HPC ノード・一部のストレージアレイである**（出典3）。
    システム構成□ **PXE を使っていない機器でも PXE が有効なまま放置されていないか （PXE は既定で有効）**（出典3）。**「使っていないから無効になっているはず」という前提では点検にならない** （出典3。本記録の整理）〈重要〉—— **1台ずつ起動順序と設定を確認する必要がある。**
    運用・監視□ **BIOS/UEFI のバージョンを資産台帳（CMDB）に持ち、 サーバベンダーのファームウェア公告を受け取る経路があるか**（出典3）。**本件は OS 側のパッチでは塞げず、各 OEM の BIOS/UEFI 更新を待つことになる** （本記録の評価）〈重要〉—— **ファームウェアバージョンが台帳に無ければ、更新が出たことにも気づけない**（出典3）。
    運用・監視□ **導入用ネットワークが専用 VLAN に分かれており、 導入サーバ以外からの到達を禁じられるか**（出典1・3）。**攻撃面は PXE 起動シーケンスの最中の数秒で、 必要なのは対象機器のIPへ単播の報文を1つ届けることである**（出典1・3）〈重要〉—— **報文が届かなければ成立しない**（本記録の整理）。
    体制・契約□ **「ベンダーからの影響なしの明記が取れるまで対象とみなす」判定規則があるか**（出典3）。**EDK II は参照実装であり、各社の統合状況が異なる**（出典3）〈重要〉—— **報道の時点で AMD・Phoenix・AMI・Microsoft・Amazon は回答しておらず、 Intel も OEM による統合の可能性に留保を置いている**（出典3）〈齟齬3〉。 **回答が無い状態を「対象外」と読むと、該当機器が全部抜ける**（本記録の評価）。
    体制・契約□ **「Secure Boot と TPM とディスク暗号化があるから盗難時もデータは守られる」という 説明を、社内・顧客向けに行っていないか**（出典1・3）。**コードが走るのは Secure Boot と計測起動が検証を終える前の DXE フェーズである** （出典1）〈重要〉—— **これらの機構は本件の盾として数えられない**（出典3。本記録の整理）。 **該当機器について risk 受容の説明を作り直す必要がある**（本記録の判断）。
