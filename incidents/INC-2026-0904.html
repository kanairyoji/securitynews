INC-2026-0904Crawl4AI 0.8.0未満に未認証RCE

LLM 向けクローラ Crawl4AI の 0.8.0 未満に未認証のリモートコード実行 （CVE-2026-26216・GHSA-5882-5rx9-xgxp・CVSS v4.0 で 10.0）—— 公式 Docker 配備が 11235 番ポートに JWT 認証なしで API を出し、 `POST /crawl` の `hooks` パラメータで渡した Python コードが `exec()` で動く作りだった。 手書きの builtins 白名簿に `__import__` が残っていたため、サンドボックスは成立していなかった。 修正は2026年1月12日の 0.8.0 で、hooks は既定で無効（opt-in）になった

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年1月16日（GHSA-5882-5rx9-xgxp の公開） 最終更新: 2026年11月6日（本記録の作成。GHSA と CHANGELOG を取得して裏を取った時点）

LLM 向けのクローラ・本文抽出フレームワーク Crawl4AI の 0.8.0 未満に、認証不要のリモートコード実行の脆弱性があります（出典1）。CVE-2026-26216 / GHSA-5882-5rx9-xgxp、CVSS v4.0 のベーススコアは 10.0（Critical）、ベクタは CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H、弱点分類は CWE-94 です（出典1）〈重要〉。

成立の筋はこうです。 公式 Docker 配備は API を 11235 番ポートに出し、POST /crawl エンドポイントは既定で JWT 認証が無効です（出典3）。このエンドポイントは hooks パラメータを受け取り、クロールの各段階で動く Python コードを呼び出し側から注入できます。コードは exec() で実行され、外側には手書きの builtins 白名簿がかぶせてありました（出典1・3）。

その白名簿に __import__ が残っていました（出典1・3）〈重要〉。__import__ は import 文の下地になる関数です。これが使えれば__import__('os')・__import__('subprocess') と書けますし、__import__('builtins').__dict__['open'] とすれば、作者が意図して外した open も取り戻せます（出典3）。つまり白名簿は、一行の見落としで役目を果たしていませんでした。

影響は、認証を持たない攻撃者による任意コマンド実行です（出典1）。公式イメージはコンテナ内で root として動くため、コンテナに置かれた上流 API キー・モデルの資格情報・DB 接続文字列がそのまま読める位置に攻撃者が立ちます（出典1・3）〈重要〉。

修正は 0.8.0 です。 公式 CHANGELOG は 0.8.0 を2026年1月12日のリリースとし、Security 節で「hooks の許可 builtins から __import__ を削除した」こと、および「hooks は既定で無効になり、環境変数 CRAWL4AI_HOOKS_ENABLED を設定したときだけ有効になる」ことを挙げています（出典2）〈重要〉—— 報告者は ProjectDiscovery の Neo と記載されています（出典2）。

GHSA の公開は2026年1月16日、NVD での公開は2026年2月12日です（出典1）。本記録が起点にした技術解説記事（阿里云先知）は2026年11月2日の公開で、GHSA 公開から290日が経っています（出典3。本記録の算出）〈重要〉—— 記事自体には「1月に修正済みの脆弱性である」という時間の説明がありません〈齟齬3〉。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**11235 番ポートの発見 → 認証なしの `POST /crawl` → `hooks` 経由の `exec()` → 白名簿の `__import__` で任意モジュール → コンテナ内 root でのコマンド実行 → 資格情報の奪取・横展開、という経路である**（出典1・3）〈重要〉—— **実際の攻撃の観測ではなく、アドバイザリの成立条件と 技術解説記事の再現手順を段階に並べたものである**（本記録の明示）〈未確定1〉。 **各段階の「検知の機会」と「効きえた対策」は本記録の評価である。**

  1. 1. 偵察推定[3]
    **攻撃者は 11235 番ポートが開いているホストを探す**（出典3）。 **記事は「11235 は特徴の明確なポートで、`/health` の応答 （`{"status":"ok","version":"..."}`）から版数を指紋判定でき、 影響範囲に入るかを直接判断できる」と述べている**（出典3。原文中国語）〈重要〉。

  2. 2. 初期侵入確認済[1] [3]
    **認証を持たない攻撃者が `POST /crawl` に JSON を投げる**（出典1・3）〈重要〉。 **`hooks.code.<イベント名>` に Python の非同期関数を入れるだけで、 クロールのライフサイクル上で実行される**（出典3）—— **資格情報は要らない（CVSS ベクタは PR:N / UI:N）**（出典1）。

  3. 3. 実行確認済[1] [3]
    **渡されたコードは `exec(compile(code, f"<hook:{event}>", "exec"), sandbox_globals, sandbox_locals)` で実行される。`sandbox_globals` に入っているのが手書きの白名簿 `ALLOWED_BUILTINS` である** （出典3）〈重要〉。 **白名簿には `len`・`range`・`str`・`int`・`dict`・`list`・`sorted`・`min`・`max` や 3種の例外クラスが並び、`open`・`eval`・`exec`・`compile`・`__builtins__` は 意図して外されていた——にもかかわらず `__import__` が残っていた**（出典3）。 **`__import__('builtins').__dict__['open']` と書けば、 外したはずの `open` も取り戻せる**（出典3）—— **一つの鍵で2つの防御線が同時に抜けている**（出典3。本記録の整理）。
    根拠: 出典3の `hook_manager.py` 該当行の提示（59行目・94行目）／GHSA の CWE-94（出典1）

参照・持ち出された情報

    白名簿に残った一行が、2つの防御線を同時に抜いた原因・手口

    この脆弱性の核は「exec() を使ったこと」ではなく、exec() の周りに手で書いた白名簿を安全の根拠にしたことです（本記録の評価）〈重要〉。

    白名簿の構成を見ると、作者の意図は明確です（出典3）。残されていたのは len・range・str・int・dict・list・sorted・min・max というデータ処理の道具と、Exception・ValueError・KeyError の3種の例外です。外されていたのは open・eval・exec・compile・__builtins__——つまり作者は何が危ないかを分かっていました。

    それでも __import__ が残っていました（出典1・3）。しかも並び順は KeyError の直後で、特別な印は何もありません（出典3）。

    __import__ が一つあるだけで、2つの防御線が同時に抜けます（出典3。本記録の整理）〈重要〉。

    抜けた防御線 抜け方
    モジュール読み込みの制限 __import__('os')・__import__('subprocess')・__import__('socket') で標準ライブラリ全体に届く
    危険な builtins の排除 __import__('builtins').__dict__['open'] で、外したはずの open を取り戻せる

    弱点分類が CWE-94「コード生成の不適切な制御」なのは、この構造を指しています（出典1）。

    修正の中身も、裏返しに読むと早いです（出典2）。0.8.0 は①白名簿から __import__ を削り、②hooks そのものを既定で無効にして CRAWL4AI_HOOKS_ENABLED による opt-in に変えました。「白名簿を直す」だけで終わらせず、「既定で機能を閉じる」ほうへ寄せたのが要点です（本記録の評価）〈重要〉—— 白名簿方式は、一行の見落としで全体が無効になることを、この事例が示しています。

    既定で認証なし・既定で root・固定ポートの3点が、利用の難度を押し下げた被害規模・影響範囲

    CVSS v4.0 で 10.0（上限値）が付いた理由は、脆弱性そのものより配備の既定値にあります（本記録の評価）〈重要〉。

    ベクタは CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H です（出典1）。権限不要（PR:N）・利用者の操作不要（UI:N）に加え、後続システム側の機密性・完全性・可用性もすべて High（SC:H/SI:H/SA:H）——これは「踏まれた先の被害まで織り込んだ」評価です（本記録の整理）。

    増幅要因は3つです（出典3）。

    # 既定値 効いているところ
    ① POST /crawl の JWT 認証が無効 「資格情報が要らない」
    ② コンテナが root で動く 「取れた後に何でもできる」
    ③ 11235 番ポートが直接公開されがち 「到達できる相手が増える」

    ②が軽く見られがちです（本記録の評価）〈重要〉—— LLM アプリの前段に置くクローラのコンテナには、上流 API キー・モデルの資格情報・DB 接続文字列が揃っていることが多い。 到達された時点で、攻撃者はそれらが読める位置に立ちます（出典1・3）。

    ③は指紋の問題でもあります（出典3）。11235 は特徴の明確なポートで、/health の応答から版数まで読めるため、攻撃側は「影響範囲に入るか」を走査の段階で判定できます（出典3）。

    どれか一つを崩せば難度は上がります（本記録の評価）—— 逆に言えば、公式イメージを何も触らずに立てた構成は3つすべてに当たります。

    したがって、記事の uid=0(root) の応答は「公式イメージが root で動く」ことの直接の証拠にはなりません（本記録の整理）—— 記事は別の箇所で「既定イメージは root で動く」と述べていますが、これは再現結果ではなく記事の記述です（出典3）。

    本記録は、成立条件そのものは一次アドバイザリ（出典1）で裏付けています—— 認証不要・hooks 経由・0.8.0 未満・CWE-94・CVSS v4.0 で 10.0（出典1）。公式イメージ上での再現は本記録では行っていません〈未確定5〉—— 再現の検証が目的ではなく、一次資料が同じ条件を述べているため足りると判断しました（本記録の判断）。

    もう一つ、記事の中に小さな食い違いがあります〈齟齬1〉。記事は「0.8.0 は ALLOWED_BUILTINS から import・eval・exec・open・compile を削除した」と書いていますが、同じ記事の別の箇所では「open・eval・exec・compile は元から白名簿に入っていなかった」と書いています（出典3）。公式 CHANGELOG が挙げているのは __import__ の削除と hooks の既定無効化だけです（出典2）—— 本記録は CHANGELOG の記述を採ります（本記録の判断）。

    対策は版の更新だけで終わらない——既定無効化が Breaking Change である対策・注意喚起

    0.8.0 への更新には、機能の停止が同梱されています（出典2）〈重要〉。

    hooks は既定で無効になり、CRAWL4AI_HOOKS_ENABLED を設定したときだけ有効になります（出典2）。CHANGELOG はこれを Security 節と Breaking Changes（Docker API の変更）の両方に挙げています（出典2）—— つまり hooks に依存した処理を持つ利用者は、更新した時点で動かなくなります。

    ここが分かれ目です（本記録の評価）〈重要〉。「CRAWL4AI_HOOKS_ENABLED=true を足して元に戻す」という最短の復旧をすると、__import__ の削除は効いているものの、「利用者のコードを exec() で動かす経路」自体は開いたままになります。 白名簿方式の限界（一行の見落ちで全体が無効になる）は構造として残ります（本記録の判断）。

    出典3が挙げる防御は4つです（出典3）。①0.8.0 以上へ更新、②更新できないなら逆プロキシ層で /crawl を遮断するか JWT を強制、③コンテナを非 root で動かす（--user 1000:1000）、④11235 番ポートを公衆網に出さない。

    本記録はこれに1つ足します（本記録の評価）〈重要〉—— 到達されていた可能性が否定できない期間がある場合、そのコンテナから読めた資格情報（上流 API キー・モデルの資格情報・DB 接続文字列）をローテーションすることです。 アドバイザリにはローテーションの要請は書かれていません（本記録の確認）—— しかし影響に「環境変数や API キーなどの情報漏えい」が挙がっている以上、パッチ適用だけでは後始末が済まない（本記録の判断）。

      取るべき行動 **①`pip show crawl4ai` / `requirements.txt` / `Dockerfile` のタグを確認する。 ②公式イメージを使っている場合、`:latest` 固定の有無と実際のダイジェストを確認する。 ③`/health` の応答で稼働中の版数を突き合わせる（出典3が指紋判定に使えると述べている経路）。**
    • **更新時に hooks が既定無効になることを前提に、依存の有無を先に調べる。**
      **0.8.0 で hooks は opt-in（`CRAWL4AI_HOOKS_ENABLED`）になり、 CHANGELOG が Breaking Change として挙げている**（出典2）〈重要〉—— **更新して壊れたときに環境変数で戻すと、 「利用者コードを `exec()` する経路」が開いたままになる**（本記録の評価）。
      取るべき行動 **①自組織のコードが `hooks` を使っているかを grep で確認する。 ②使っている場合、その処理を hooks の外（取得後の自前の後処理）へ移せるか検討する。 ③どうしても有効化が必要なら、そのインスタンスを内部網限定にし、別権限で動かす。**
    • **`exec()` の周りの白名簿を、安全の根拠として受け入れない。**
      **本件は `open`・`eval`・`exec`・`compile` を外しておきながら `__import__` を残したことで、両方の防御線が同時に抜けた**（出典1・3）〈重要〉—— **`__import__('builtins').__dict__['open']` で、外した `open` が戻る**（出典3）。
      取るべき行動 **①自前のコードに「白名簿つき `exec`／`eval`」がある箇所を洗い出す。 ②`__import__`・`__class__`・`__subclasses__`・`__globals__` 等の 間接参照の経路を確認する（白名簿では閉じきれないことを前提にする）。 ③隔離が必要なら、プロセス・コンテナ・seccomp の層で行う。**
    • **コンテナを root で動かすのをやめ、外向き通信を宛先で絞る。**
      **出典3の再現では `uid=0(root)` が返っており、 アドバイザリは横展開と情報漏えいを影響に挙げている**（出典1・3）〈重要〉—— **root であることが「取れた後の自由度」を決めている**（本記録の整理）。
      取るべき行動 **①`--user 1000:1000` 等で非 root 実行に変え、検証環境で Playwright の起動を確認する。 ②コンテナからの外向き通信を、クロール対象の経路と必要な API に限定する。 ③コンテナ内のプロセス起動を監視し、クローラから `sh`・`curl` 等が起動したら警報にする。**
    • **逆プロキシ層で、要求本体に `hooks` キーを含む呼び出しを見える形にする。**
      **攻撃の入口は `POST /crawl` の本体に入った `hooks.code.<イベント名>` である**（出典3）〈重要〉—— **本体をログに残していない構成では、到達の痕跡が残らない**（本記録の評価）。
      取るべき行動 **①`/crawl` への要求を逆プロキシ経由に限定し、JWT を強制する。 ②本体に `hooks` キーを含む要求を遮断し、件数を記録する。 ③遮断ログを「誰が到達を試みたか」の資料として保全する。**
