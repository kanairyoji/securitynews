INC-2026-0906ChatGPTのLockdown Mode回避

ChatGPT の Lockdown Mode を回避できる脆弱性——HTML プレビューのサンドボックス iframe に `allow-popups` と `allow-popups-to-escape-sandbox` が残っていたため、 入れ子の iframe の `contentWindow.open` でポップアップを開けば サンドボックスの外で任意の HTML が動き、チャット履歴の黙った持ち出し・ 更新を装ったマルウェア配布・強制サインアウトからの資格情報窃取に至った。 Electron 製の ChatGPT Classic では利用者の操作なしで成立した。 OpenAI は2026年9月18日に2つのトークンを削除して修正した

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月5日（Check Point Research の公表） 最終更新: 2026年11月6日（本記録の作成。研究者の記事を取得して確認した時点）

Check Point Research（研究者 Alexey Bukhteyev）は2026年11月5日、ChatGPT の Lockdown Mode を回避できる脆弱性を公表しました（出典1）。

Lockdown Mode は、ログイン済み利用者向けの任意の高度なセキュリティ設定です（出典1）。プロンプトインジェクションによって会話の外へデータが出ていく経路を断つことを狙い、有効にすると次を制限します（出典1）—— ①ライブのウェブアクセスをキャッシュ済みコンテンツに限定、②インターネット上の画像の読み込みと表示を遮断、③Canvas が生成したコードからのネットワーク要求を無効化、④Deep Research・Agent Mode・ライブコネクタ・ファイルのダウンロードを停止。

回避の筋はこうです。 2026年2月、OpenAI は ChatGPT のコードブロックにHTML ページのプレビュー機能を追加しました（出典1）。利用者の作った HTML を JavaScript ごと ChatGPT の画面の中で描くため、実装には何重もの隔離が置かれていました—— 描画先は2段の入れ子 iframe で、親文書・ChatGPT の UI 状態・chatgpt.com の Cookie や localStorage には届きません（出典1）。外部への送信、遠隔画像・スクリプト・リンクの読み込み、任意 URL の開封は、すべて傍受されて警告として表示されます（出典1）。

ところが、ポップアップだけは扱いが違いました（出典1）〈重要〉。iframe の sandbox 属性には allow-popups とallow-popups-to-escape-sandbox が許可として入ったままで、抑止はサンドボックス側のスクリプトが window.open を差し替えることで行われていました（出典1）。

したがって、本物の window.open に手が届けば抜けます（出典1）。サンドボックスの中でさらに iframe を1つ作り、その contentWindow.open を呼ぶと、ポップアップが開きます（出典1）〈重要〉。allow-popups-to-escape-sandbox があるため、開いた窓の中の HTML はもうサンドボックスの中では動きません（出典1）。

ここから広い攻撃面が開きます（出典1）。チャット履歴とアップロードしたファイルの黙った持ち出し、更新を装ったマルウェアの配布（窓は ChatGPT のアイコンを保ち、題名は攻撃者が決める）、本物のアプリの文脈だと錯覚させるフィッシング、利用者を強制的にサインアウトさせて攻撃者のページで再認証させる資格情報窃取です（出典1）〈重要〉。経路は、悪意あるプロンプト・悪意ある GPT・共有されたチャットの3つです（出典1）—— 共有チャット経由のマルウェア配布では、被害者はアカウントを持っている必要さえありません（出典1）。

Electron 製の ChatGPT Classic ではゼロクリックで成立しました（出典1）〈重要〉—— 同アプリでは window.open が利用者の操作（ジェスチャー）なしでも動くため、会話をしているだけで持ち出しが起きうる状態でした（出典1）。

OpenAI は2026年9月18日、HTML プレビューの外側のサンドボックス iframe からallow-popups と allow-popups-to-escape-sandbox を削除する修正を展開したと研究者に連絡しました（出典1）。研究者は再検証し、記事に書かれた手法が通らなくなったことを確認しています（出典1）。CVE 番号の記載はありません（出典1。本記録の確認）〈未確定2〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**悪意あるプロンプト／悪意ある GPT／共有チャットのいずれかで HTML プレビューを描かせる → サンドボックス内で入れ子の iframe を作る → その `contentWindow.open` で ポップアップを開く → `allow-popups-to-escape-sandbox` によりサンドボックス外で 任意の HTML が動く → チャット履歴の持ち出し・マルウェア配布・ 強制サインアウトからの資格情報窃取、という経路である**（出典1）〈重要〉—— **研究者の実証に基づく。実際の攻撃の観測ではない**（本記録の明示）〈未確定1〉。 **各段階の「検知の機会」と「効きえた対策」は本記録の評価である。**

  1. 1. 初期侵入確認済[1]
    **攻撃者は3つの経路のいずれかで、HTML プレビューを利用者の画面に描かせる**（出典1）〈重要〉—— **①悪意あるプロンプト、②悪意ある GPT、③共有されたチャット。** **③では、被害者はアカウントを持っている必要さえない**（出典1）。 **記事は「攻撃者が生成ページの内容を制御できるため、 説得力のある誘いを作るのは容易だ」としている**（出典1。原文英語）。
    根拠: 記事の「The attack could be carried out in several ways」節（出典1）
  2. 2. 検知回避確認済[1]
    **サンドボックスの中でさらに iframe を1つ作り、その `contentWindow.open` を呼ぶ** （出典1）〈重要〉。 **`window.open("about:blank")` は差し替えられた実装に捕まって `null` を返すが、 `document.createElement('iframe')` で作った iframe の `contentWindow.open("about:blank")` は通る**（出典1）。 **iframe の sandbox 属性に `allow-popups` が入っているため、 ポップアップそのものは禁じられていない**（出典1）—— **抑止は「属性による宣言」ではなく「スクリプトによる上書き」に依存していた** （本記録の整理）。
    根拠: 記事の技術詳細節（差し替えられた `window.open` の実装と回避コード）（出典1）
  3. 3. 実行確認済[1]
    **開いたポップアップの中に任意の HTML を置くと、 `allow-popups-to-escape-sandbox` があるためサンドボックスの外で実行される** （出典1）〈重要〉。 **ブラウザの既定設定では JavaScript からのポップアップは通常止まるため、 ブラウザ版ではプレビューへのクリックを誘う必要がある**（出典1）—— **一方、Electron 製の ChatGPT Classic では `window.open` が利用者の操作なしでも動くため、クリックが要らない**（出典1）。
    根拠: 記事の「Zero-Click Exploitation in ChatGPT Classic」節（出典1）
  4. 4. 持ち出し確認済[1]
    **サンドボックス外で動くコードから、チャット履歴全体と アップロードしたファイルを攻撃者のサーバへ送れる**（出典1）〈重要〉—— **記事の実証（動画1）では、悪意ある GPT がチャットのメッセージを 攻撃者の管理するサーバへ黙って漏らしている**（出典1）。 **Lockdown Mode は本来この種の外向き経路を断つための設定だが、 この経路は Lockdown Mode を越えた**（出典1）。
    根拠: 記事の冒頭要旨と動画1の説明（出典1）
  5. 5. 影響（暗号化・破壊・改ざん）確認済[1]
    **攻撃面は持ち出しに留まらない**（出典1）〈重要〉。 **①更新を装ったマルウェア配布——ポップアップは ChatGPT アプリのアイコンを保ち、 題名は攻撃者が決めるため、利用者は本物のアプリの文脈にいると錯覚する （ChatGPT Classic では自動ダウンロードが止まるためクリックが要るが、 ブラウザ版では止まらない）。 ②フィッシング——ChatGPT Classic の画面に任意の内容のポップアップを出せる。 ③資格情報窃取——主画面の再読み込みや、利用者を強制的にサインアウトさせる操作ができ、 攻撃者のページで再認証させられる**（出典1）。
    根拠: 記事の「Attack surface」節および動画2〜4の説明（出典1）
参照・持ち出された情報

    抑止をスクリプトの上書きに置いたため、本物の window.open に届けば抜けた原因・手口

    本件の構造は、隔離の「層の数」ではなく「どこで止めていたか」の問題です（本記録の評価）〈重要〉。

    置かれていた隔離は厚いものでした（出典1）。描画は2段の入れ子 iframe の中で、親文書・ChatGPT の UI 状態・chatgpt.com の Cookie や localStorage には届きません。 外部への送信、遠隔画像・スクリプト・リンクの読み込み、任意 URL の開封は、すべて傍受されて承認ダイアログや警告として表示されます（出典1）。

    ところがポップアップは、別のやり方で止めていました（出典1）〈重要〉。iframe の sandbox 属性には allow-popups とallow-popups-to-escape-sandbox が許可として入ったままで、実際の抑止はサンドボックス側のスクリプトが window.open を差し替えることで行っていました。 記事が引用している差し替え後の実装は、承認を要求し、その場では null を返すものです。空 URL や about:blank を渡した場合は、通知さえ出ません（出典1）。

    ここが分かれ目です（本記録の整理）。「属性による宣言」で禁じていれば、どの経路から呼んでも効きます。 「スクリプトによる上書き」で止めていると、上書きされていない別の参照に手が届けば抜けます。

    回避コードは短いものでした（出典1）。

    window.open("about:blank");            // 止まる
var f = document.createElement('iframe');
document.body.appendChild(f);
f.contentWindow.open("about:blank");   // 通る

    サンドボックスの中で新しく作った iframe の contentWindow は、差し替えられていない本物の window.open を持っています（出典1）。そして allow-popups-to-escape-sandbox があるため、開いた窓の中の HTML はもうサンドボックスの中では動きません（出典1）〈重要〉。

    修正も同じ場所を直しています（出典1）—— 外側のサンドボックス iframe から allow-popups とallow-popups-to-escape-sandbox を削除する、という内容です。 「スクリプトでの上書きをやめ、属性で禁じる」側へ寄せた修正です（本記録の整理）。

    ChatGPT Classic ではクリックが要らなかった——会話しているだけで成立した被害規模・影響範囲

    同じ脆弱性でも、どこで使っているかで成立の重さが変わります（出典1）〈重要〉。

    環境 成立の条件 ダウンロード
    ブラウザ版 プレビューへのクリックを誘う必要がある（既定設定では JS からのポップアップが止まる） 自動ダウンロードは止まらない
    ChatGPT Classic（Electron 製） 利用者の操作なしで window.open が動くため、クリックが要らない 自動ダウンロードは止まるので、取得にはクリックが要る

    ChatGPT Classic 側の記述が本件で最も重い部分です（本記録の評価）〈重要〉。記事は「会話をしているだけで攻撃が引き起こされる」としており、実証（動画1）では悪意ある GPT がチャットのメッセージを攻撃者のサーバへ黙って漏らしています（出典1）。

    さらに、同アプリでは主画面に対する操作もできました（出典1）—— 主画面の再読み込み、および利用者を強制的にサインアウトさせることです。 サインアウトさせたうえで攻撃者のページに再認証を誘えば、資格情報が取れます（出典1）。

    ポップアップの見え方も効いています（出典1）〈重要〉。開いた窓は ChatGPT アプリのアイコンを保ち、題名は攻撃者が決めます—— 利用者には「まだ ChatGPT を使っている」ように見えます（出典1）。これが「更新を装ったマルウェア配布」の説得力を作っています。

    共有チャット経由では、被害者がアカウントを持っている必要さえありません（出典1）〈重要〉—— 記事は「共有チャット内のコンテンツへのクリックはいずれも危険になりうる」と結んでいます。

    本件を「よくある XSS まわりの一件」として読むと要点を落とします（本記録の評価）〈重要〉。

    Lockdown Mode は、プロンプトインジェクションが残り続けるリスクであることを前提に、データが会話の外へ出ていく経路そのものを断つ設計です（出典1）。記事はその考え方を、OpenAI 自身の URL 安全性の解説を引きながら説明しています—— 攻撃者が AI を騙してattacker.example/collect?data=<private data> のようなリンクを読み込ませると、チャット上には何も怪しいものが出ないまま、機微なデータが攻撃者のサーバのログに残る（出典1）。

    だから Lockdown Mode は機能を削ります（出典1）—— ライブのウェブアクセスをキャッシュに限り、外部画像を止め、Canvas 生成コードのネットワーク要求を無効にし、Deep Research・Agent Mode・ライブコネクタ・ファイルのダウンロードを停止する。

    これを有効にするのは、便利さを捨てる判断です（本記録の評価）〈重要〉—— つまり Lockdown Mode を有効にしている利用者は、機微な内容を ChatGPT で扱っていた可能性が高い。 本件はその利用者を対象に、Lockdown Mode を越えてチャット履歴の全体を黙って持ち出せる経路でした（出典1）。

    一般化できる教訓はこうです（本記録の判断）〈重要〉。「出口を塞ぐ」設計は、塞ぎ忘れた出口が1つあれば全体が無効になります。 本件の塞ぎ忘れは allow-popups 系のトークン2つでした（出典1）。そして、残っていたのは「禁止の宣言」ではなく「実装による上書き」という弱い形の抑止でした（本記録の整理）。自組織の設計でも、「機能を無効にした」と言うときに、それが属性・ポリシーによる宣言か、コードによる上書きかを区別して記録しておく価値があります。

      取るべき行動 **①業務で使う GPT・カスタムアシスタントの一覧を作り、作成者を記録する。 ②外部作成のものは審査を通したものだけに限る。 ③共有チャットのリンクを業務で回す運用を見直し、 「中の生成物はクリックしない」を周知する。**
    • **SaaS 側の脆弱性を、自組織の台帳に記録する仕組みを持つ。**
      **本件には CVE が無く、利用者側の作業も無い**（出典1）〈重要〉—— **したがって何も記録せずに過ぎてしまうが、 「いつ、どの機能で、何が可能だった期間があったか」は 後の調査（あの時期の会話は漏れていないか）に必要になる**（本記録の評価）。
      取るべき行動 **①利用中の SaaS について、公表された脆弱性と修正日を自組織の台帳に残す。 ②影響期間（機能追加から修正までと読める期間）を併記する。 ③機微な業務でその SaaS を使っていた期間と突き合わせられる形にする。**
    • **デスクトップアプリ（Electron 製）とブラウザ版のリスク差を把握する。**
      **同じ脆弱性が、ブラウザ版ではクリックを要し、 ChatGPT Classic ではゼロクリックで成立した**（出典1）〈重要〉—— **デスクトップアプリは「信頼済みアプリの文脈」を提供するため、 偽装窓の説得力も上がる**（出典1）。
      取るべき行動 **①業務で使う AI サービスを、ブラウザ版に寄せるかデスクトップ版を使うかを方針として決める。 ②デスクトップ版を使う場合、更新の経路と、 「アプリが更新ファイルの取得を促してきた」を報告対象にすることを定める。 ③端末側で実行ファイルの取得・実行を制限する。**
    セキュリティ技術者への示唆
    • **「機能を無効にした」と言うとき、宣言か上書きかを区別して記録する。**
      **本件のポップアップ抑止は、sandbox 属性（宣言）ではなく スクリプトによる `window.open` の差し替え（上書き）で行われていた**（出典1）〈重要〉—— **上書きは、上書きされていない別の参照に手が届けば抜ける**（本記録の整理）。
      取るべき行動 **①自組織のコードで「危険な API を無効化した」箇所を洗い出す。 ②その実現方法を、属性・CSP・ポリシーによる宣言か、 プロトタイプ・グローバルの書き換えかで分類する。 ③後者は防御として数えず、宣言側で重ねて禁じる。**
    • **iframe の sandbox 属性は、許可トークンの最小集合で書く。**
      **削除されたのは `allow-popups` と `allow-popups-to-escape-sandbox` の2つだけである** （出典1）〈重要〉—— **後者は「開いた窓の中身をサンドボックスの外で動かす」許可であり、 前者と揃うことで回避が成立していた**（本記録の整理）。
      取るべき行動 **①自組織で利用者コンテンツを描画している iframe の sandbox 属性を列挙する。 ②各トークンについて「なぜ要るか」を書けないものを外す。 ③特に `allow-popups-to-escape-sandbox`・`allow-same-origin`・ `allow-top-navigation` の有無を重点的に確認する。**
    • **入れ子の iframe から `contentWindow` 経由で素の API に届く経路を想定する。**
      **回避は `document.createElement('iframe')` で作った iframe の `contentWindow.open` を呼ぶだけで成立した**（出典1）〈重要〉—— **新しく作った閲覧文脈は、差し替えられていない API を持つ**（本記録の整理）。
      取るべき行動 **①利用者コンテンツの実行環境で、iframe の生成を許しているかを確認する。 ②許す必要がなければ CSP（`frame-src 'none'` 等）で禁じる。 ③禁じられない場合、抑止を親側の上書きに頼らず sandbox 属性で行う。**
    • **AI サービスを使う端末からの外向き通信を記録する。**
      **持ち出しは「通知なしに」行われ、ChatGPT の画面に痕跡は残らない**（出典1）〈重要〉—— **組織として見える材料は、端末からの外向き通信だけである**（本記録の判断）。
      取るべき行動 **①業務端末の外向き通信（宛先ドメイン）を記録する仕組みを確認する。 ②AI サービスを使う端末で、未知のドメインへの POST を可視化する。 ③記録の保存期間を、公表された脆弱性の影響期間を遡れる長さにする。**
    • **AI サービスの認証を、フィッシング耐性のある方式に寄せる。**
      **本件では主画面の再読み込みと強制サインアウトが可能で、 攻撃者のページで再認証させる資格情報窃取のシナリオが示されている**（出典1）〈重要〉。
      取るべき行動 **①ChatGPT を含む AI サービスの認証を SSO 配下に置き、パスキー等に寄せる。 ②「突然サインアウトした直後の再ログイン」を注意すべき場面として周知する。 ③サインイン元の記録（IP・端末）を定期確認できる状態にする。**
