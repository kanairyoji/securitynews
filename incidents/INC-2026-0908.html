Layer3 Intel が検出したのは、大統領府が登録する自律システム AS2650 のアドレスから、住宅用プロキシの出口ノードが外へ向かって通信していることである（出典1）。観測は2026年10月5日から11月3日までの30日間、出口として記録されたのは236回、使われたアドレスは6つ、記録があったのは30日のうち26日である（出典1）。

どこで止められたか

段階検知の機会効きえた対策
初期侵入機会はあったが検知できず
**本記録の評価である**〈重要〉。 **根拠は観測の持続性にある**——**出口は30日のうち26日で記録され** （出典1）、**Layer3・Spur・Synthient の3社が公開の検索ページで 同じアドレスを出口と判定していた**（出典3）。 **つまり外部からは30日間可視であり、 同じ判定は組織側からも照会できた**（本記録の評価）。 **組織側が検知していたかは公表されていない**〈未確定6〉—— **本記録は「検知の機会はあった」と評価し、 「検知できなかった」の断定は避ける。**
侵入を防げた端末に導入されるアプリケーションの許可制と、 同梱 SDK の確認を調達・利用の条件に含めること　**本記録の評価である。** **プロキシ SDK は端末側では正規アプリの一部として動くため、 マルウェア検知では止まりにくい**（本記録の評価）〈重要〉—— **止める位置は導入の可否そのものになる。** **ただし SDK の同梱はアプリの説明に明記されないことが多く**（出典2）、 **確認の実効性には限界がある**（本記録の留保）。
C2通信機会はあったが検知できず
**本記録の評価である**〈重要〉—— **この段階は、組織側の外向き通信の監視で最も捉えやすい。** **出口ノードは要求を受けるために常時接続を保つ必要があり、 宛先は住宅用プロキシ事業者のインフラである**（本記録の整理）。 **業務端末が、業務と無関係の事業者へ夜間も常時接続していれば、 宛先の評判情報を使わずとも通信の形だけで浮く**（本記録の評価）。 **組織側の監視状況は公表されていない**〈未確定6〉。
侵入を防げた外向き通信の既定拒否と、許可したプロキシ経由への限定　**本記録の評価である**〈重要〉—— **出口ノードは外部からの接続を待つのではなく、 自ら事業者のインフラへ出ていく形で成立する。** **したがって受信側の遮断（ファイアウォールの着信規則）では止まらず、 止まる位置は送信側である**（本記録の整理）。 **副作用（把握されていなかった正規通信の遮断）は detail.mitigations に記載した。**
検知できた住宅用プロキシ事業者のインフラ宛て通信の検知と、 自組織アドレスの出口判定の定期照会　**本記録の評価である。** **本件では Layer3・Spur・Synthient の公開検索ページで 当該アドレスが出口と判定されていた**（出典3）〈重要〉—— **同じ照会は組織側からも可能であり、 30日間そのままだったことは照会が行われていなかったことを示唆する** （本記録の推定。組織側の運用は公表されていない〈未確定6〉）。
影響（暗号化・破壊・改ざん）現実的な検知機会なし
**大統領府の側からは現実的に検知できない段階である** （本記録の評価）〈重要〉—— **第三者が出口を使った記録は、 プロキシ事業者と宛先サイトの側にしか残らない。** **組織側に見えるのは、自前の端末が事業者インフラへ 接続していること（前段）までである**（本記録の整理）。 **本記録がこの段階を「現実的な検知機会がない」と置くのは 「検知が不要」という意味ではなく、 「止める位置は前段しかない」という意味である。**
影響を限定できた送信元 IP の許可リストを、本人性の証拠として使わないこと （相互 TLS・署名付き要求・スコープ付きの資格情報へ置き換える）　**本記録の評価であり、宛先側（守られる側）の対策である**〈重要〉。 **本件が示したのは「信頼されたネットワークのアドレスが 数ドルで借りられる」という状態である**（出典2）—— **Synthient の Ben Brundage は「1ドル未満で、 最も機密で信頼されたネットワークのいくつかへ 入り込める」と述べている**（原文英語。本記録の訳。出典2）。 **IP を信頼の根拠にしている統制は、 その前提が崩れたことを認識する必要がある**（本記録の評価）。
影響を限定できたSDK の脆弱性を前提とした端末の隔離 （プロキシ SDK が入った端末を内部ネットワークの到達範囲から外す）　**本記録の評価である。** **Layer3 の報告は、安全性の低いプロキシ SDK が 内部ネットワークへの到達や横展開を許しうると述べている**（出典1）〈重要〉—— **実例として、2025年末にプロキシ事業者側の脆弱性を突いて 各出口端末の LAN を探索しマルウェアを感染させる大量悪用が 見つかり、2026年1月に多数の事業者が修正を行っている**（出典2）。 **つまり SDK が入った端末は、貸し出す側であると同時に 外部から内部へ入る足場にもなる**（本記録の整理）。

CISO・経営層への示唆
  • **「自組織の IP が信頼される」という前提を、資産として棚卸しする**
    **本件で失われたのは、データではなくアドレスの信頼である** （本記録の評価）〈重要〉—— **大統領府のシステムが侵害された報告は無い**（出典1）。 **それでも、28の住宅用プロキシサービスから数ドルで借りられる 出口として30日のうち26日にわたって成立していた**（出典1・2）。 **Synthient の Ben Brundage は「1ドル未満で、最も機密で 信頼されたネットワークのいくつかへ入り込める」と述べている** （原文英語。本記録の訳。出典2）。 **自組織のアドレスを信頼の根拠にしている相手は、 自組織の外にいる**（本記録の整理）。
    取るべき行動 **自組織が保有・割当を受けているグローバル IP の一覧を作り、 「このアドレスを信頼している外部の相手」を書き出す （取引先の許可リスト、API の送信元制限、監督官庁への提出系）。** **そのうえで、各アドレスが住宅用プロキシの出口として 判定されていないかを外部の判定サービスで照会する。** **照会は1社では足りない**—— **本件では Layer3・Spur・Synthient の3社が同じ判定を出していた**（出典3）。
  • **「外から見えていたのに30日気づかなかった」という失敗の型を想定する**
    **本件の露出は、特殊な調査でなく公開の検索ページで判定できた** （出典3）〈重要〉—— **Layer3 は「選んで狙ったのではなく偶然捉えた」と述べている**（出典2）。 **つまり自組織の外形的な異常は、 自組織より先に第三者のデータベースに載る**（本記録の評価）。 **Infoblox は、顧客基盤の65%が住宅用プロキシ関連ドメインを 照会していたと述べている**（出典2）—— **これは「うちは無いだろう」が成り立たない水準の普及率である。**
    取るべき行動 **自組織について「外から無料または安価に確認できる情報」を列挙し、 その定期確認を運用の手順に組み込む （IP の出口判定、公開ポートの一覧、証明書の失効、 漏えい資格情報の掲載、リークサイトへの掲載）。** **確認の結果は「異常なし」ではなく 「いつ・どの事業者のデータで・何を見たか」で記録する** ——**事業者ごとに判定が異なるため、 記録が無いと見落としの範囲が分からない。**
  • **私物・持ち込み端末の方針を、「情報を持ち出す risk」だけで設計しない**
    **本件の端末は、情報を外へ出す経路ではなく 外から内へ入る入口として機能しうる**（本記録の評価）〈重要〉—— **Layer3 の報告は、安全性の低いプロキシ SDK が 内部ネットワークへの到達や横展開を許しうると述べ**（出典1）、 **2025年末には実際に、プロキシ事業者側の脆弱性を突いて 出口端末の LAN を探索しマルウェアを感染させる大量悪用が 見つかっている**（出典2）。 **活動が夕方17時から深夜0時に偏っていたことは、 業務時間外にネットワークに残る端末の存在を示唆する**（出典1・3）。
    取るべき行動 **持ち込み端末・私物端末が接続できるネットワークから、 内部システムへの到達経路を外す（ゲスト網の分離を 「インターネットだけ通る」まで徹底する）。** **方針文書の risk 欄に「端末が外部に貸し出される」 「端末経由で内部を探索される」の2項目を明記する。** **業務時間外も接続を保つ端末の一覧を取り、 その必要性を部署ごとに確認する。**
  • **当事者が沈黙する事案から、自組織の説明責任の形を逆算する**
    **本件には当事者の公表が1件も無い**〈齟齬2〉〈重要〉（本記録の確認）—— **ホワイトハウスはコメントの求めに即答せず**（出典2）、 **報告の公表当日夕方にも活動は記録されていた**（出典3）。 **結果として、読者は「侵害されたのか」「解消したのか」を 判断できない状態に置かれている**（本記録の評価）。 **第三者の観測で自組織が名指しされる事態は、 住宅用プロキシに限らず増えている** ——**約300の政府ネットワークで同じ状態が確認されている**（出典2）。
    取るべき行動 **「第三者の観測レポートで自組織が名指しされた場合」の 対応手順を作る（照会への一次回答の期限、 事実確認の責任部署、確認できるまでに言えることの範囲）。** **肝は「調査中」を言える体制である** ——**沈黙と否定のどちらも、確認が終わる前には使えない。**
セキュリティ技術者への示唆
  • **プロキシ SDK は端末側では止めにくい。止める位置は外向き通信である**
    **SDK は正規アプリの一部として動作する**（出典2）〈重要〉—— **マルウェアとしての特徴を持たず、 アプリ開発者が収益化のために自ら埋め込んでいる。** **一方で出口ノードは、要求を受けるために 事業者インフラへ常時接続を保つ必要がある**（本記録の整理） ——**この通信は外向きであり、形が目立つ。** **本件では活動が30日のうち26日で記録されていた**（出典1）。
    取るべき行動 **外向き通信を既定拒否にし、許可したプロキシ経由に限定する。** **既定拒否が難しい場合は、まず 「長時間維持される外向きのセッション」を宛先別に集計し、 業務上の説明が付かない宛先を洗い出す。** **住宅用プロキシ事業者のドメイン・ASN への通信を 個別に検知対象へ加える** ——**Infoblox の観測では顧客基盤の65%が 関連ドメインを照会していた**（出典2）。
  • **送信元 IP の許可リストを、本人性の証拠として使わない**
    **本件は「信頼されたアドレスから通信できる」ことが 数ドルで買える商品になっていた事案である**（出典2）〈重要〉。 **宛先サイトから見れば、通信は プロキシ利用者ではなく貸し出し元のアドレスから来たように見える**（出典2）。 **許可リストは「この経路を通った」ことしか示さず、 「この組織である」ことを示さない**（本記録の整理）。
    取るべき行動 **IP 許可リストに依存している統制を列挙し、 相互 TLS・署名付き要求（nonce とタイムスタンプ）・ エンドポイント単位にスコープを絞った資格情報へ置き換える。** **置き換えが間に合わない経路では、 許可リストを「1つ目の条件」に格下げし、 2つ目の条件（資格情報・署名）を必ず併置する。**
  • **自組織アドレスの外形を、定期的に外から観測する**
    **本件の判定は公開の検索ページで可能だった**（出典3）〈重要〉—— **Layer3 は Spur と Synthient の公開ページで 当該アドレスが出口と判定されていることを確認している。** **つまり30日間、誰でも確認できる状態が続いていた**（本記録の評価）。
    取るべき行動 **自組織の IP 範囲（割当・クラウド上の固定 IP・ VPN 出口・拠点回線）を一覧にし、 住宅用プロキシ出口判定・スキャナ判定・ブロックリスト掲載を 定期照会する仕組みを作る。** **照会は複数事業者で行い、結果を時系列で保存する** ——**判定が付いた日が分かれば、露出の始点を推定できる。** **本件では観測開始日しか分からず、始点が不明である**〈未確定3〉。
  • **NAT の背後では、アドレス数から端末数を推定しない**
    **本件で観測されたのは6つのアドレスである**（出典1・3）〈重要〉—— **これは端末の台数ではない**（本記録の区別）。 **NAT の背後では複数端末が同一アドレスから出るため、 1アドレスが1端末を意味しない。** **Layer3 自身が「我々のデータが示すのは出口であって、 その背後の端末や人物ではない」と明記している**（出典1）。
    取るべき行動 **外部から「自組織のアドレスで異常がある」と指摘されたときに、 アドレスから内部端末へ遡れる記録（NAT の変換ログ・ DHCP の払い出し記録・プロキシのアクセスログ）が どの期間ぶん残っているかを確認する。** **残っていなければ、指摘を受けても端末を特定できない** ——**本件で端末が特定されていないのは、 外部観測者の位置ではそこまで見えないためである。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ 自組織のグローバル IP アドレス（割当・クラウドの固定 IP・ VPN 出口・拠点回線）の一覧が、 最新の状態で1か所にまとまっていない。
システム構成□ 外向き通信が既定で許可されており、 端末から任意の外部宛先へ恒常的な接続を張れる。
認証・認可□ 外部の取引先・API・監督官庁向けの経路で、 送信元 IP の許可リストを認証または本人性の根拠として使っている。
運用・監視□ 私物端末・持ち込み端末が接続できるネットワークから、 内部システムへ到達できる経路が残っている。
体制・契約□ 従業員の私物端末・自宅回線について、 導入されるアプリの同梱 SDK を確認する手段と、 確認を求める根拠（規程・契約）が無い。
運用・監視□ 第三者の観測レポートで自組織が名指しされた場合の 一次対応（照会への回答期限・事実確認の責任部署・ 確認できるまでに言える範囲）が決まっていない。
