攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**形は「インターネットに露出した非本番環境へ侵入 → 共有された資格情報・トークン・ネットワーク経路で本番へ移動 → アプリのコードベースを解析して専用のエクスプロイトと改変パッケージを作成 → 信頼された第三者の IP プールを経由して許可リストを通過し API を呼ぶ → クラウド管理機能とサーバーレスでコマンド実行と不正ファイル配置 → 1ルピーのテスト送金で経路を検証 → 高額送金・暗号資産の持ち出し」である** （出典1・2。段階への割り当ては本記録）〈重要〉。 **この形の特徴は、各段階で「組織が自分で信頼を与えていたもの」を 使っている点である**（本記録の評価）—— **非本番環境、環境間で共有した鍵、自社の正規クライアントアプリ、 許可リストに入れた第三者サービス、クラウドの管理機能。** **侵入のための新しい技術はほとんど要らない。** **AI が変えたのは速さと量である**（出典1・2）—— **攻撃の全工程を自律実行し、機能が同じで細部だけ異なる スクリプトを大量に即席で作って相手の応答に応じて改良する。**

  1. 1. 偵察公表・報道に基づく
    **AI を用いて標的を調査し、公開直後の脆弱性を即座に突ける体制で 待ち構える**（出典1・2）〈重要〉。 **攻撃インフラの IP は数時間から数日単位で変わる**（出典1）。 **攻撃の時期は休日・週末・その他の監視が手薄な時間帯に 寄せられており、検知と対応を遅らせる狙いとされる**（出典2）。
    根拠: **「Attacks were typically observed during holiday periods, on weekends and "other low-monitoring windows" to delay detection and response」** （出典2）——**（攻撃は典型的に、休日・週末・その他の監視が手薄な 時間帯に観測され、検知と対応を遅らせるものだった。 原文英語。本記録の訳）。** **勧告は対策として「休日・週末・監視が薄い時期に 24時間体制の監視を維持し、人員を増やし、警告の閾値を下げる」ことを 求めている**（出典1・2）。
  2. 2. 初期侵入公表・報道に基づく
    **インターネットに露出した非本番環境 （UAT・ステージング・テスト）から初期侵入する**（出典1・2）〈重要〉。 **また公開直後の脆弱性を即座に突き、 ファイルアップロードと逆シリアル化の不備を連鎖させて PHP・Node.js アプリに Web シェルを設置する**（出典1・2）。
    根拠: **「Typically, Crafty Falcon gains initial access through internet-exposed non-production environments, such as user acceptance testing (UAT), staging and testing environments」**（出典2）—— **（典型的に Crafty Falcon は、ユーザー受入テスト（UAT）・ ステージング・テスト環境といった、インターネットに露出した 非本番環境を通じて初期アクセスを得る。原文英語。本記録の訳）。**
  3. 3. 横展開公表・報道に基づく
    **非本番環境から本番環境へ移動する。 経路は、両環境で共有された認証情報・認証トークン・ ネットワーク経路である**（出典1・2）〈重要〉。
    根拠: **「Once inside, the threat actor moves from non-production environments into production systems by exploiting shared credentials, authentication tokens or network paths between the environments」** （出典2）——**（内部に入ると、脅威アクターは環境間で共有された 認証情報・認証トークン・ネットワーク経路を悪用して、 非本番環境から本番システムへ移動する。原文英語。本記録の訳）。**
  4. 4. 検知回避公表・報道に基づく
    **2つの手口で統制を回避する**（出典1・2）〈重要〉。 **①改変または変更されたアプリパッケージから不正な API 呼び出しを行い、 「正規のクライアントアプリだけが API と通信する」という前提に 立った統制を回避する**（出典1・2）—— **そのためにアプリのコードベースを解析（リバースエンジニアリング）して 専用のエクスプロイトを作る。** **②コンテンツ配信やアプリストアの審査に使われる 第三者の取得サービス（fetcher）の IP プールを経由して通信し、 送信元 IP の許可リストを通過する**（出典1・2）—— **これらのサービスは誰でも任意の URL を取得させられるため、 組織が既に信頼している IP から通信が始まる。**
    根拠: **「The actor also bypasses IP allow-listing restrictions by routing traffic through whitelisted third-party fetcher IP pools, such as content-acceleration services and app-store review fetchers. These shared services can be instructed by any internet user to fetch arbitrary URLs, allowing the actor to originate traffic from IP addresses already trusted by the organization」**（出典2）—— **（行為者はまた、コンテンツ加速サービスやアプリストアの審査用 フェッチャといった、許可リストに入った第三者フェッチャの IP プールを 通じて通信を回すことで、IP 許可リストの制限を回避する。 これらの共用サービスは、インターネット上の誰からでも 任意の URL の取得を指示できるため、行為者は組織が既に信頼している IP アドレスから通信を発生させられる。原文英語。本記録の訳）。**
  5. 5. 実行公表・報道に基づく
    **クラウドの管理機能とサーバーレスを使ってコマンドを実行し、 不正なファイルを配置する**（出典1・2）〈重要〉—— **勧告は AWS Systems Manager と Lambda を名指ししている。** **正規のクラウド管理操作に紛れるため検知が難しくなるとされる**（出典1・2）。 **またアプリ配備ディレクトリに PHP・Node.js の Web シェルを置く**（出典1・2）。
    根拠: **「Cloud management services, such as AWS Systems Manager and Lambda, are abused to execute commands and deploy malicious files, allowing malicious activity to blend into legitimate cloud management operations」**（出典2）—— **（AWS Systems Manager や Lambda といったクラウド管理サービスが 悪用され、コマンドの実行と不正ファイルの配置が行われる。 これにより悪性の活動が正規のクラウド管理操作に紛れ込む。 原文英語。本記録の訳）。**
  6. 6. 影響（暗号化・破壊・改ざん）公表・報道に基づく
    **資金を抜く段階である**（出典1・2）〈重要〉。 **①高額送金の前に1ルピー程度の少額テスト送金を行い、 不正な資金の流れが成立することを検証する**（出典1・2）。 **②決済アグリゲーターの加盟店精算（merchant settlement）API を 悪用または不正利用して資金を移す**（出典1・2）。 **③暗号資産取引所および VASP を標的に、 ウォレット鍵を盗んでウォレットから資産を抜き取る**（出典1・2）。
    根拠: **「Before executing large-value transfers, the actor performs micro-value test transactions, such as transactions of Rs. 1, to validate that unauthorized fund flows are possible」**（出典2）—— **（高額の送金を実行する前に、行為者は1ルピーの取引のような 極小額のテスト取引を行い、不正な資金の流れが可能であることを 検証する。原文英語。本記録の訳）。**

入口は非本番環境、本番への鍵は環境間の使い回しだった原因・手口

攻撃ライフサイクルの前半は、2つの文で言い切れる（出典1・2）。

「典型的に Crafty Falcon は、ユーザー受入テスト（UAT）・ステージング・テスト環境といった、インターネットに露出した非本番環境を通じて初期アクセスを得る」（原文英語。本記録の訳。出典2）。

「内部に入ると、脅威アクターは環境間で共有された認証情報・認証トークン・ネットワーク経路を悪用して、非本番環境から本番システムへ移動する」（原文英語。本記録の訳。出典2）〈重要〉。

本記録の整理——この2段は、組織の側から見ると別の失敗である。 ①非本番環境がインターネットに面していた（境界の問題）。 ②非本番環境から本番へ入れる鍵が置かれていた（分離の問題）。 ②が無ければ、①は初期侵入で止まっていた。

勧告が求めている対策も、この2つに対応している（出典1）—— 「UAT・ステージング・テスト環境を本番から分離し、認証情報・トークン・API キー・データベース・直接のネットワーク経路を共有しない。公開している場合は本番並みに堅牢化して監視する。非本番から本番へのアクセスは監視・調査する」。

続く段階も、組織が自分で与えた信頼を使っている（本記録の評価）〈重要〉。③アプリのコードベースを解析して専用のエクスプロイトを作り、改変したアプリパッケージから不正な API 呼び出しを行う（出典1・2）—— 「正規のクライアントアプリだけが API と通信する」という前提の統制が破れる。 ④クラウド管理サービス（AWS Systems Manager・Lambda）でコマンドを実行し不正ファイルを配置する（出典1・2）—— 正規のクラウド管理操作に紛れる。 ⑤公開直後の脆弱性を即座に突き、ファイルアップロードと逆シリアル化の不備を連鎖させてPHP・Node.js アプリに Web シェルを置く（出典1・2）。

本記録の整理——どの段階にも、組織が「安全だと決めたもの」がある。 非本番環境、環境間で共有した鍵、自社の正規アプリ、許可リストに入れた第三者サービス、クラウドの管理機能。

許可リストに入れた第三者フェッチャが、信頼の抜け道になった原因・手口

この手口は、日本の事業者がそのまま点検できる形をしている（本記録の評価）〈重要〉。

勧告の記述を引く（原文英語。本記録の訳。出典2）—— 「行為者はまた、コンテンツ加速サービスやアプリストアの審査用フェッチャといった、許可リストに入った第三者フェッチャの IP プールを通じて通信を回すことで、IP 許可リストの制限を回避する。これらの共用サービスは、インターネット上の誰からでも任意の URL の取得を指示できるため、行為者は組織が既に信頼しているIP アドレスから通信を発生させられる」。

成立の理屈は単純である（本記録の整理）。CDN・画像プロキシ・リンクプレビュー・URL スキャナ・アプリストアの審査用フェッチャは、「指定された URL を取りに行く」ことを仕事にしている。 その指示は、誰からでも出せる。 したがってこれらのサービスの IP を許可リストに入れた時点で、その IP は実質的にインターネット全体と等価になる〈重要〉。

勧告の対策はここに正面から答えている（出典1）—— 「第三者の取得サービスへの IP 許可リストを、相互 TLS・署名付き要求・専用エンドポイントへのスコープ付きAPI キーなど ID 基盤の方式に置き換える」。

本記録の補足——置き換えは相手側の実装に依存するため、自組織だけでは完了しない（本記録の評価）。現実的な第一歩は、許可リストの全エントリについて「その IP の背後にいるのは誰か」を書き出すことである。 背後が「不特定のインターネット利用者」になるエントリが見つかれば、そのエントリは本人性の根拠として使えない。

1ルピーの送金が、最後の防波堤を教えている対策・注意喚起

本キャンペーンの最終段階には、守る側に有利な性質がある（本記録の評価）〈重要〉。

勧告の記述（原文英語。本記録の訳。出典2）—— 「高額の送金を実行する前に、行為者は1ルピーの取引のような極小額のテスト取引を行い、不正な資金の流れが可能であることを検証する」。

これは攻撃者の弱点である（本記録の整理）。攻撃者は、高額送金が失敗して警戒を招く risk を避けたい。 だから先に少額で試す。 この手順は省けない——つまり観測可能な痕跡を必ず残す〈重要〉。

勧告の対策はこの性質を使っている（出典1）—— 「新規受取人への少額テスト送金の後に高額送金が続くパターンを不正送金の強い前兆とみなし、保留や審査を行う。送金速度の制限、新規受取人への待機期間、金額帯の異常検知を導入する」。

副作用もはっきりしている（本記録の評価）—— 「少額で試してから本番の送金をする」行為は、正規の利用者が新しい振込先を登録するときの自然な手順でもある。 保留の件数と待機期間は、そのまま顧客体験と運用の人手の負担になる。

本記録はそれでもこの対策を最優先に置く〈重要〉。理由は位置である——侵害が成立していても、資金が出る前に止まる。 本キャンペーンの前半（非本番環境・環境分離・API 検証）は構成の見直しに時間がかかるが、送金パターンの監視は既存の不正検知の設定変更で始められる（本記録の評価）。

併せて勧告が挙げている対策（出典1）—— 「加盟店精算の指示は、サーバ側検証・メーカーチェッカー承認・照合を経て処理する」「暗号資産のウォレット鍵は HSM またはコールドストレージで保管し、出金には複数署名を求める」。 いずれも「1つの経路の侵害では資金が動かない」形にする設計である（本記録の整理）。

AI が変えたのは速さと量で、入口の種類は変わっていない評価・解釈

本記録の主張は1つである。 この勧告を「AI 攻撃への備え」として読むと、対策の優先順位を誤る（本記録の評価）〈重要〉。

勧告が記述する AI の使われ方は2つである（出典1・2）。①公開されている AI 攻撃ツールを組み合わせ、攻撃の全工程を機械の速さで自律実行する。 挙げられたのは ARTEX（PentAGI を基礎とする自律型マルチエージェント基盤で LLM を接続できる）、侵入テスト基盤 CyberStrikeAI、攻撃検索エンジン Cairn である（出典1・2）。CERT-In はこれらが「攻撃チェーン全体を機械の速さで自律実行し、多数の専用攻撃スクリプトを立て続けに生成・改良し、標的の応答に応じてペイロードを適応させる」ことを可能にすると書いている（原文英語。本記録の訳。出典2）。②機能が同じで細部だけ異なるスクリプトを大量に即席で作り、立て続けに改良する（出典1・2）—— CERT-In はこのパターンを「AI が生成したコードおよびAI 支援による反復開発と整合する」としている（原文英語。本記録の訳。出典2）。

一方、勧告が挙げる対策の一覧を見ると、大半は AI 固有ではない（出典1）〈重要〉—— 環境の分離、資格情報の非共有、サーバ側の取引検証、最小権限、パッチ適用期限、クラウド権限の限定、送金パターンの監視、ゼロトラストとマイクロセグメンテーション。

AI 固有の項目は3つに絞られる（本記録の整理）。①公開されている AI 型攻撃ツールの持ち込み・実行を禁止し、権限確認を無効化した AI コーディングエージェントの稼働を監視する。 ②サーバなど非開発ホストからの LLM API 利用を監視・管理する ——勧告は「サーバや非開発ホストから発生する LLM API 通信は、攻撃インフラまたは仕込まれた操作コンソールを示しうる」としている（出典2）。③SIEM の相関を、機械の速さ・複数手法の併用・並列の攻撃スレッド・適応的なペイロード変更・営業時間外の継続活動に合わせ直す。

本記録の結論——変わったのは攻撃の速さと量であって、入口の種類ではない〈重要〉。非本番環境の露出、環境間での資格情報の共有、クライアント同一性への依存、IP 許可リストへの依存は、AI が無くても成立していた弱点である（本記録の評価）。AI が変えたのは、それらを見つけて繋げるまでの時間である。 したがって対策の優先順位は、「AI 対策製品」ではなく「従来の統制の抜けを埋める速さ」に置かれる。

指標は配布網の中にしか無い。届かない組織には手口だけが残る未確定事項

この勧告には侵害指標が1つも載っていない（出典1）〈重要〉。

CERT-In は、侵害指標・インフラの特徴・検知ルールを含む詳細版を、BFSI 事業者へ適切な TLP レベルを付して共有しているとしている（出典1）。公開されているのは手口と対策である。

本記録はこの判断を妥当と評価する（本記録の評価。response.decisions 参照）〈重要〉—— 攻撃インフラの IP は数時間から数日単位で変わるとされ（出典1）、指標の寿命が短い。 勧告自身が「指標は変わりやすく手法は残りやすい」として、指標のブロックだけに頼らないよう求めている（出典1）。

ただし帰結は明確である（本記録の明示）—— 配布網に入っていない組織には、照合できる材料が届かない。 日本の金融事業者にとって、インドの CSIRT-Fin の配布網は自動的に届くものではない。

他に公表されていないもの（本記録の整理）。①被害事業者の名称と件数〈未確定1〉〈未確定2〉—— 業態（NBFC・デジタルレンディング・フィンテック・決済アグリゲーター・決済サービス事業者・暗号資産取引所と VASP）のみが示されている。 ②不正送金の件数と金額、暗号資産の流出額〈未確定2〉。③帰属〈未確定3〉—— 勧告は述べていない。 報道は「これらのツールが使われた過去のキャンペーンの多くは中国を拠点とする行為者に結び付けられてきた」と書いているが（出典2）、本記録はこれを帰属の根拠として扱わない〈齟齬5〉—— 公開ツールの使用は、使った者を特定しない。 ④先行勧告 CIAD-2026-0046 の本文〈未確定4〉—— 限定配布であり、何を求めていたかが読めない。

本記録の評価——④が読めないことが、本件で最も痛い〈重要〉。「対策したのに再び入られた」という事実から学べることの多くは、「どの対策を求めていたか」と「どこが足りなかったか」の差分にある。 その差分が非公開である限り、読者にできるのは自組織の対応の完了判定を自分で疑うことだけである。

侵入を防げた新規受取人への少額テスト送金に続く高額送金を保留・審査に回し、 送金速度の制限・新規受取人への待機期間・金額帯の異常検知を導入する　**勧告が求めている対策である**（出典1）〈重要〉。 **本記録の評価**——**本キャンペーンに対する 最後の防波堤であり、かつ最も実装しやすい対策である。** **侵害の有無に関わらず、送金の時点で止まる**（本記録の整理）。 **副作用（正当な取引も止まる）は detail.mitigations に記載した。**
侵入を防げた加盟店精算の指示をサーバ側検証・メーカーチェッカー承認・ 照合を経て処理する／暗号資産のウォレット鍵を HSM または コールドストレージに保管し、出金に複数署名を求める　**勧告が求めている対策である**（出典1）〈重要〉。 **本記録の整理**——**どちらも「1つの経路の侵害では 資金が動かない」形にする対策である。** **本キャンペーンがシステムへの侵入に成功しても、 人の承認または別の署名鍵が要るなら、資金は出ない。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
機能した**本記録はこの判断を機能したものと評価する**〈重要〉（本記録の評価）。 **理由は2つある。** **①IoC の寿命が短い。** **攻撃インフラの IP は 数時間から数日単位で変わるとされる**（出典1）—— **公開しても照合に使える期間が短く、 攻撃側に「どこまで見えているか」を教える不利益のほうが大きい。** **②公開したのは寿命の長いほうである。** **勧告自身が「指標は変わりやすく手法は残りやすい」として 指標のブロックだけに頼らないよう求めており**（出典1）、 **公開された手口と対策は、照合ではなく構成の見直しに使える。** **留保**——**この判断は、TLP 配布の受け手に入っていない組織 （BFSI 以外の業態・国外の事業者）には何も届かないことを意味する** （本記録の明示）。
部分的に機能**本記録の評価である**〈重要〉。 **結果が示したこと**——**限定配布と修復の組み合わせは、 この相手には足りなかった**（出典1・2）。 **配布を受けて修復した事業者が再び攻撃され、 CERT-In は「不完全な修復」と指摘している。** **本記録は CERT-In の判断そのものを責めない**（本記録の明示）—— **限定配布は国家 CERT の標準的な手順であり、 公開すれば攻撃側にも警戒が伝わる。** **partial と置いた理由は結果にある**—— **約1か月で公開に切り替えざるを得なかったこと自体が、 最初の配布範囲と内容では止まらなかったことの記録である**（本記録の評価）。
CISO・経営層への示唆
  • **「対策した」を状態ではなく、検証の対象として扱う**
    **本件の中心は AI ではなく、2度目に入られたことである** （本記録の評価）〈重要〉—— **先行勧告を受けて修復した事業者が再び攻撃され、 CERT-In は「incomplete remediation」（不完全な修復）と指摘した** （原文英語。本記録の訳。出典1・2）。 **修復を終えた報告と、攻撃が通らない状態は別物である**（本記録の整理）。 **勧告は「インシデント後は侵害の残存を前提に、 フォレンジックによる完全な除去と定期的な脅威ハンティングを行う」ことを 求めている**（出典1）。
    取るべき行動 **過去6か月から1年のインシデント・勧告対応について、 「完了」の判定根拠を1件ずつ確認する （何をもって完了としたか・誰が確認したか・ 攻撃者の残存を確かめたか）。** **判定根拠が「担当部署からの完了報告」だけの案件を洗い出し、 同じ経路が今も通るかを外部からの検証で確かめる。** **1件ずつ確かめる時間が無い場合は、 初期侵入点に関わる対応（境界の露出・資格情報の共有）から始める。**
  • **監視が薄くなる時期を、攻撃側が先に把握していると前提する**
    **攻撃は休日・週末・その他の監視が手薄な時間帯に 寄せられていた**（出典2）〈重要〉—— **目的は検知と対応を遅らせることである。** **本記録の整理**——**これは技術の問題ではなく体制の問題である。** **攻撃側が狙うのは脆弱なシステムではなく、 薄い人員配置のほうである。** **勧告は、こうした時期に24時間体制の監視を維持し、 人員を増やし、警告の閾値を下げることを第一の対策に挙げている**（出典1・2）。
    取るべき行動 **自組織の年間カレンダーで、監視と対応が薄くなる期間を書き出す （年末年始・連休・決算期の繁忙・システム更改の直後）。** **その各期間について、警告の受け手・一次判断の権限者・ 資金移動を止められる人の連絡経路を名前で決める。** **「当番がいる」ではなく「送金を止める判断を誰がするか」まで 決めること**——**本件の最終段階は資金の移動である**（出典1・2）。
  • **AI を使った攻撃への対策予算を、AI 固有の製品に寄せない**
    **勧告が挙げた対策の大半は AI 固有ではない**（出典1）〈重要〉—— **環境の分離、資格情報の非共有、サーバ側の取引検証、 最小権限、パッチ適用期限、送金パターンの監視。** **AI 固有の項目は限られる**（本記録の整理）—— **①公開の AI 攻撃ツールの持ち込みを禁止し 権限確認を無効化した AI エージェントの稼働を監視すること、 ②非開発ホストからの LLM API 利用を監視すること、 ③SIEM の相関を機械の速さ・並列の攻撃スレッド・ 営業時間外の継続活動に合わせ直すこと。** **変わったのは速さと量であって、入口の種類ではない**（本記録の評価）。
    取るべき行動 **「AI 攻撃対策」として検討している投資を、 勧告の対策一覧（環境分離・資格情報・サーバ側検証・ クラウド権限・送金監視）に対応付けて並べ替える。** **対応しない投資があれば、 それが何の攻撃段階を止めるのかを説明させる。** **AI 固有の投資は、検知ルールの作り直し （機械の速さ・並列・営業時間外の継続活動）に優先して充てる。**
  • **自社の IoC 入手経路が、どの配布網に属しているかを確認する**
    **本件の侵害指標は公開されていない**（出典1）〈重要〉—— **CERT-In は詳細版を BFSI 事業者へ TLP レベルを付して 別途共有している。** **本記録はこの判断を妥当と評価するが**（response.decisions 参照）、 **結果として、配布網に入っていない組織には何も届かない** （本記録の明示）。 **日本の金融事業者にとって、インドの CSIRT-Fin の配布網は 自動的に届くものではない。**
    取るべき行動 **自組織が属している情報共有の枠組み（金融 ISAC・業界団体・ 監督官庁・ベンダーの脅威情報）を列挙し、 各枠組みから過去1年に受け取った TLP 付き情報の件数を数える。** **数えられない（受け取った記録が無い）枠組みは、 加入しているだけで届いていない可能性がある。** **海外当局の勧告について、公開版だけでも 定期的に確認する担当を決める。**
セキュリティ技術者への示唆
  • **「環境を分けた」と「鍵を分けた」を別に点検する**
    **本キャンペーンの本番侵入経路は、 環境間で共有された認証情報・認証トークン・ネットワーク経路である** （出典1・2）〈重要〉。 **初期侵入はインターネットに露出した UAT・ステージング・ テスト環境だが、そこで止まらなかった理由がここにある**（本記録の整理）。 **勧告は「認証情報・トークン・API キー・データベース・ 直接のネットワーク経路を共有しない」ことを求めている**（出典1）。
    取るべき行動 **ステージング・テスト環境の設定ファイル・環境変数・ シークレットストアを取り出し、本番の資格情報と突き合わせる。** **確認する問いは1つ**——**「ステージングの資格情報で 本番の API・データベースに接続できるか」。** **実際に試して、接続できたら記録する。** **併せて、非本番から本番へ向かうネットワーク経路 （セキュリティグループ・ルーティング・VPC ピアリング）を 洗い出して閉じる。**
  • **IP 許可リストに「誰でも任意の URL を取らせられるサービス」を入れない**
    **本キャンペーンは、コンテンツ配信やアプリストアの審査に使われる 第三者フェッチャの IP プールを経由して許可リストを通過した** （出典1・2）〈重要〉—— **これらのサービスは、インターネット上の誰からでも 任意の URL の取得を指示できる。** **つまりその IP を信頼した時点で、 実質的にインターネット全体を信頼したことになる**（本記録の整理）。
    取るべき行動 **IP 許可リストの全エントリについて、 「その IP の背後にいるのは誰か」を1件ずつ書き出す。** **CDN・画像プロキシ・リンクプレビュー・アプリストア審査・ URL スキャナ・翻訳プロキシが入っていたら、 そのエントリは信頼の根拠として使えない。** **置き換え先は、相互 TLS・署名付き要求（nonce とタイムスタンプ）・ エンドポイント単位にスコープを絞った API キーである**（出典1）。
  • **クライアントアプリを信頼しない。取引はサーバ側で1件ずつ検証する**
    **本キャンペーンは、アプリのコードベースを解析して 改変したパッケージから不正な API 呼び出しを行い、 「正規のクライアントアプリだけが API と通信する」という 前提の統制を回避した**（出典1・2）〈重要〉。 **アプリが利用者の端末にある限り、この前提は成立しない** （本記録の評価）——**解析でき、改変でき、再配布できる。**
    取るべき行動 **自社の API について、「このアプリから来た」ことを 何で判定しているかを確認する （User-Agent・独自ヘッダ・ビルド時に埋め込んだキー・ 証明書ピンニングのみ、はいずれも改変で越えられる）。** **取引系の API には、要求の署名（nonce とタイムスタンプ付き）と サーバ側の金額・受取人・権限の検証を入れる。** **アプリの正当性確認（app attestation）は補助として使い、 それ単独を根拠にしない。**
  • **クラウドの管理機能とサーバーレスを、攻撃の実行経路として監視する**
    **本キャンペーンは AWS Systems Manager と Lambda を悪用して コマンドを実行し不正ファイルを配置した**（出典1・2）〈重要〉—— **正規のクラウド管理操作に紛れるためである。** **本記録の整理**——**この経路の良い点は、 監査ログに必ず残ることである。** **検知できていないとすれば、 ログを集約していないかルールを書いていないかのどちらかである。**
    取るべき行動 **クラウド監査ログをリアルタイムで集約し、 リモートコマンド実行・サーバーレス関数のコード更新・ ロールやユーザーやアクセスキーの作成を警告対象にする**（出典1）。 **併せて、これらの操作を実行できる主体を列挙し、 承認済みのアカウントに限定する。** **サーバーレス関数には、インスタンスメタデータ保護・ 最小権限ロール・既定で外部通信を拒否する構成を適用する**（出典1）。
  • **AI が大量に作るスクリプトの「量と相似」を検知条件に変える**
    **本キャンペーンは、機能が同じで細部だけ異なるスクリプトを 大量に即席で作り、相手の応答に応じて改良していた**（出典1・2）〈重要〉—— **CERT-In はこのパターンを「AI が生成したコードおよび AI 支援による反復開発と整合する」としている** （原文英語。本記録の訳。出典2）。 **これは従来のマルウェア検知（既知の検体との一致）では映らない形である** （本記録の整理）—— **1つ1つは新規で、特徴は「似たものが急に増える」ことのほうにある。**
    取るべき行動 **Web ルート・一時ディレクトリ・ステージング領域で、 スクリプトファイルの増加数と相似度を監視する**（出典1）。 **SIEM の相関ルールを、機械の速さ・複数手法の併用・ 並列の攻撃スレッド・適応的なペイロード変更・ 営業時間外の継続活動に合わせて調整する**（出典1）。 **人の操作を前提にした閾値（1分あたりの試行回数など）は、 機械の速さに合わせて見直す。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ UAT・ステージング・テストなどの非本番環境が、 インターネットから到達可能な状態にある （ホスト名に uat / stg / test / dev を含むものが外部に面している）。
認証・認可□ 非本番環境と本番環境で、 認証情報・認証トークン・API キー・データベース・ 直接のネットワーク経路のいずれかを共有している。
認証・認可□ 送信元 IP の許可リストに、 CDN・画像プロキシ・リンクプレビュー・アプリストア審査・ URL スキャナなど「第三者が任意の URL を取得させられるサービス」が 含まれている。
システム構成□ 取引系 API の呼び出し元を、 「正規のクライアントアプリだけが呼ぶ」という前提で統制しており、 要求ごとのサーバ側検証（署名・nonce・金額と受取人の検証）が無い。
運用・監視□ クラウドの管理サービス（Systems Manager 相当）と サーバーレス関数について、 実行できる主体の限定と監査ログの集約・警告設定を行っていない。
運用・監視□ 資金移動の監視に、 「新規受取人への少額送金に続く高額送金」の検知が入っていない、 または休日・夜間に送金を保留できる体制が無い。
