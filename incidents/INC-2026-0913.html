INC-2026-0913OWNLY から参加者情報14,034件

スマートシェアが提供する SNS キャンペーンツール「OWNLY」のファイルアップロード機能の不備を突いた不正アクセスで、モスフードサービスの3キャンペーンの参加者情報14,034件が閲覧・ダウンロードされた——2026年10月16日未明に監視システムが検知したが通知設定の不備で開発担当者の把握が遅れ、同日中に侵入経路を遮断。漏えいしたのは X・LINE のユーザー名とユーザーID・エントリー日時・抽選やクーポンの取得状況で、氏名・住所・電話番号・メールアドレスは収集していなかった

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及初報のみ日本の組織が当事者設計・実装上の不備設定不備
初報: 2026年10月27日 最終更新: 2026年11月6日

スマートシェア株式会社は2026年10月27日、同社が提供する SNS キャンペーンツール「OWNLY」への不正アクセスを公表しました。同日、キャンペーンを実施していた株式会社モスフードサービスも「第三者の不正アクセスに伴うキャンペーン参加者情報漏洩に関するお知らせ」を公表しています。

2026年10月16日未明、OWNLY のファイルアップロード機能の不備を侵入経路とした不正アクセスを監視システムが検知しました。ところが通知設定の不備により、同社開発担当者による把握が検知から遅れました。同日中に侵入経路は遮断されています。

漏えいしたのは、モスフードサービスの3キャンペーンの参加者情報合計14,034件です。内訳は「モスのレシートチャレンジ」（2026/8/3〜8/31・LINE）2,995件、「モスでハロウィン プレゼントキャンペーン」（2026/10/15〜10/17・X）11,001件、「VALX×モスバーガーコラボ！レシートキャンペーン」（2026/10/1〜10/21・X）38件。項目はX または LINE の「ユーザー名」「ユーザーID」・エントリー日時・抽選やクーポンの取得状況で、氏名・住所・電話番号・メールアドレス・クレジットカード情報・SNS のパスワードは、対象キャンペーンでそもそも収集していません。

この事案で読み取るべき点は2つあります。1つは、集めなかったデータは漏れないこと。レシート応募型のキャンペーンで個人の連絡先を集めない設計にしていたため、14,034件という規模でも漏えい項目は SNS 上の識別子に収まりました。もう1つは、検知できていたのに人に届かなかったこと。監視は作動していましたが、通知設定の不備が「検知から対応開始まで」の時間を伸ばしました。スマートシェアは連絡先を保有していないため、公表の掲載をもって個人情報保護法に基づく本人通知に代えるとしています。評価・示唆は本記録の判断として分けて書きます。

漏えいしたのは SNS 上の識別子だけ——氏名・住所・連絡先は「そもそも集めていなかった」被害規模・影響範囲出典 [1] [2]

漏えいした項目は、X または LINE の「ユーザー名」「ユーザーID」、エントリー日時、抽選・クーポンの取得状況等である。

両社は、対象キャンペーンにおいて氏名・住所・電話番号・メールアドレス・クレジットカード情報・SNS のパスワード等の情報は収集しておらず、漏えいした情報には含まれていないと明記している。

14,034件という規模に対して漏えい項目が限定されているのは、偶然ではなくキャンペーンの設計の結果である（本記録の評価）。レシート応募型・SNS 参加型のキャンペーンは、当選連絡を SNS のダイレクトメッセージで行えば住所や連絡先を集めずに成立する。集めていないデータは、侵入されても漏れない。

ただし、SNS のユーザー名とユーザーID は本人を特定できる識別子であり、「どのキャンペーンにいつ参加し、当選したか」という行動の記録と結びついている。両社が当選連絡を装うフィッシングへの注意を呼びかけているのは、この組み合わせが「当選しました」という文面の説得力を高めるためである。スマートシェアは参加者の連絡先を保有していないため、個別の通知はできず、公表の掲載をもって個人情報保護法に基づく本人への通知に代えるとしている。

監視は作動していたが、通知設定の不備で人に届かなかった発覚の端緒出典 [1]

この事案の経緯で最も具体的に書かれているのは、検知から対応までの間に起きたことである。

  • 2026年10月16日未明、監視システムが不正アクセスを検知した
  • しかし通知設定の不備により、同社開発担当者による把握が検知から遅れた
  • それでも同日中に侵入経路を遮断した

検知の仕組みは動いていた。欠けていたのは、検知を人に届ける経路である。遅れの長さ（何時間か）は公表されていないため、11,001件を記録した「ハロウィン キャンペーン」の参加が続く時間帯に把握が遅れた影響を測ることはできない。

スマートシェアは再発防止として「監視システムが異常を検知した際の通知設定の見直し」を挙げている。自社の監視について、検知の有無ではなく通知の到達を確かめた事業者は多くない（本記録の評価）。この事案は、その欠落が公表文に残った稀な例である。

遮断・修正・点検・利用企業への依頼まで実施し、外部調査の要否は年内に検討とされた再発防止出典 [1] [2]

スマートシェアが実施したとする対策は次のとおりである。

  • ファイルアップロード機能の修正（受け付けるファイル形式の限定等）
  • OWNLY における類似の不備の有無の社内点検（現時点で未検出）
  • 全ての OWNLY アカウントへの不正アクセス有無の点検（現時点で未検出）
  • OWNLY を利用する全ての企業へ、アカウント管理画面のログインパスワードの変更、多要素認証・IP アドレス制限等の設定依頼の通知
  • 監視システムが異常を検知した際の通知設定の見直し

さらに、年内に実施の要否と対応方針を検討する項目として次を挙げている。

  • アカウント管理画面へのログインに係るセキュリティ向上策の追加（多要素認証の種類の追加等）
  • 参加者情報のダウンロード手順の見直し
  • 外部調査機関を起用した OWNLY の不備の総点検の要否・実行

モスフードサービスは、他社サービスの利用を含めた全社的な情報管理・セキュリティ体制の強化を図るとしている。

注目すべきは、多要素認証と IP 制限が「利用企業への設定依頼」になっている点である（本記録の評価）。これらが既定で有効ではなく、利用企業が設定する前提であったことを意味する。SaaS 事業者が安全側の既定値を持たない場合、利用企業の設定の差がそのまま被害の差になる。

遅れの長さ・不備の内容・保持期間の定めは公表されていない未確定事項出典 [1] [2]

2026年11月6日時点で、次の点は公表されていない。

  • 検知から開発担当者が把握するまでの遅れの長さ
  • ファイルアップロード機能の不備の技術的な内容
  • 侵入から遮断までの間に攻撃者が到達できた範囲（管理画面の権限取得の有無）
  • モスフードサービス以外の利用企業における点検の方法・対象期間と利用企業数
  • 終了したキャンペーンの参加者情報を保持し続けていた理由と保持期間の定め
  • 漏えいデータの外部での公開・売買の有無
  • 外部調査機関による総点検を行うかの結論（年内に検討とされている）

「集めない」設計が被害を小さくし、「通知が届かない」運用が対応を遅らせた（本記録の評価）評価・解釈出典 [1] [2]

ここからは本記録の作成者の評価である。

第一に、この事案は「データ最小化が効いた事例」として読める。 14,034件が漏れても、漏えい項目は SNS の識別子と参加履歴にとどまった。氏名・住所・電話番号・メールアドレスを集めていれば、同じ侵入で本人への通知義務・なりすまし被害・二次的なフィッシングの規模がまったく違っていた。キャンペーンの設計段階で「当選連絡を SNS の DM で行う」という選択をしていたことが、事故の重さを決めている。集めたデータの量は、侵害されたときに初めて請求書として現れる。

第二に、検知と通知を別の問題として点検する必要がある。 監視システムは作動したが、通知設定の不備で開発担当者に届かなかった。監視の導入は「入れたかどうか」で確認されやすいが、通知の到達は定期的に試さないと静かに壊れる（宛先の担当者が異動する、連携先の設定が変わる、通知先のチャネルが廃止される）。訓練で「意図的に異常を起こして、誰の手元に何分で届くか」を測るべきである。

第三に、SaaS の既定値が利用企業のリスクを決める。 事故後の対策として、利用企業へパスワード変更・多要素認証・IP 制限の設定が依頼された。これは裏返せば、事故の時点でそれらが既定で有効ではなかったということである。キャンペーンツールのような「本業の片隅で使う SaaS」では、利用企業側に設定を詰める体制がないことが多い。安全側の既定値（多要素認証を既定で必須にする）を事業者が選ぶかどうかが、利用企業全体の水準を決める。

第四に、終了したキャンペーンのデータが被害を積み増している。 8月末に終わったレシートチャレンジの2,995件は、10月の侵入時点でサーバ上に残っていた。抽選と発送が終わったあとも参加者情報を保持する必要は薄い。保持期間を決めて削除していれば、漏えい件数は減っていた。

第五に、委託元の公表が「参照先を示す」形で成立している点は参考になる。モスフードサービスは自社の公表文でスマートシェアの発表文を参照先として掲げ、窓口もスマートシェアの専用フォームに集約した。利用企業が独自に説明を作ると食い違いが生まれるため、一次情報を提供者側に置き、委託元は自社キャンペーンの範囲を明示するという分担は合理的である。

外部調査機関を起用した OWNLY の不備の総点検は、年内に実施の要否と対応方針を検討するとした不十分本記録の作成者の評価である。侵入経路となった機能と同種の不備の有無は、 侵入を受けた当事者による社内点検だけでは説得力が弱い。 実施済みの対策が具体的である一方、この項目が「要否の検討」にとどまる点は釣り合っていない

  • キャンペーンの設計段階で収集項目を削る——集めなかったデータは漏れない
    14,034件が漏えいしたが、項目は SNS のユーザー名・ユーザーID・エントリー日時・抽選状況にとどまった。 対象キャンペーンでは氏名・住所・電話番号・メールアドレスを収集していなかった
    取るべき行動 販促・キャンペーンの企画書に「収集項目と、その項目が無いと成立しない理由」の記載を必須にし、 当選連絡を SNS の DM・店頭引換で済ませられる設計を既定の選択肢にする
  • 監視の「検知」ではなく「通知の到達」を定期的に確かめる
    監視システムは2026年10月16日未明に検知していたが、通知設定の不備で開発担当者の把握が遅れた
    取るべき行動 四半期ごとに意図的な試験警報を発生させ、「誰の手元に何分で届いたか」を記録する。 担当者の異動・連携先の変更のたびに通知先の棚卸しを行う運用を規程に書く
  • 業務の片隅で使う SaaS も、委託先として同じ基準で点検する
    侵害されたのは販促で使うキャンペーンツールで、モスフードサービス自身のシステムは侵害されていない
    取るべき行動 部門が個別に契約している SaaS を棚卸しし、預けているデータの項目・件数・保持期間と、 多要素認証・IP 制限の設定状況を一覧にして、未設定のものから是正する
  • 本人への連絡先を持たない漏えいの通知方法を、事前に決めておく
    スマートシェアは参加者の連絡先を保有しておらず、公表の掲載をもって本人への通知に代えた
    取るべき行動 連絡先を持たないデータ（SNS 識別子・端末 ID 等）の漏えいを想定し、公表による通知の掲載場所・ 窓口の受付期間・対象確認の方法をあらかじめ手順化する
  • 自社の運用上の欠落を公表文に書く判断を、評判リスクだけで却下しない
    「通知設定の不備で把握が遅れた」という記述が公表文に残ったため、他社が同じ欠落を点検できる
    取るべき行動 公表文の作成基準に「原因・検知・対応の遅れを事実として書く」を明記し、 表現の調整は法務・広報と行うが事実の削除は行わない運用にする
セキュリティ技術者への示唆
  • ファイルアップロードは受け付ける形式・内容を検証し、保存先を実行できない領域に分離する
    侵入経路は OWNLY のファイルアップロード機能の不備で、修正は受け付ける形式の限定等であった
    取るべき行動 拡張子ではなく内容でファイル種別を判定し、許可した形式以外を拒否する。保存先を オブジェクトストレージ等の実行権限の無い領域に置き、Web から直接実行できない構成にする
  • 監視の通知経路を監視する（通知が届かないことを検知する）
    検知は成立していたが、通知設定の不備で人に届かなかった
    取るべき行動 警報の送信結果（配信成功・既読・エスカレーション）を記録し、一定時間内に誰も応答しなければ 次の宛先へ自動で上げる。定期的なハートビート警報で経路の生存を確認する
  • 終了したキャンペーンの参加者情報に保持期限を設けて自動削除する
    8月末に終了したキャンペーンの2,995件が、10月の侵入時点でサーバ上に残っていた
    取るべき行動 キャンペーン単位で保持期限（例: 抽選・発送完了後30日）を設定し、期限到来で参加者情報を削除する バッチを用意する。削除の実行結果を記録して利用企業に示せるようにする
  • 利用企業ごとにデータを分離し、横断的な参照・一括取得を制限する
    OWNLY のサーバ上に複数企業・複数キャンペーンの参加者情報が保存されており、3キャンペーン分が取得された
    取るべき行動 テナント単位・キャンペーン単位でデータを分離し、一括ダウンロードは承認制にする。 一定件数を超える取得は速度制限と管理者通知の対象にする
  • 多要素認証と接続元制限を既定で有効にし、利用企業の設定に依存させない
    事故後の対策として、利用企業へ多要素認証・IP アドレス制限等の設定依頼が行われた
    取るべき行動 管理画面の多要素認証を既定で必須にし、解除は申請制にする。既存テナントについては 有効化の期限を定めて移行し、未設定テナントの一覧を定期的に確認する
