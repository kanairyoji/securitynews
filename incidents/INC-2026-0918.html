INC-2026-0918OpenSSH にパスワード認証回避の脆弱性

2026年11月5日、OpenSSH が緊急リリース 10.6p2 を公開した。 **Linux 上で musl libc を使い PAM を無効にしてビルドした sshd では、 パスワード欄が「*」のアカウントに257〜1024バイトの長いパスワードで ログインできた**（CVE-2026-123158・通称「*sshole」）。 **正しいパスワードは要らない。** **OpenSSH は「根本原因は sshd の外にあるが sshd 経由で悪用でき、 sshd 側で回避できる」として迂回策を入れ、 把握の翌日に長い非公開期間を置かずリリースした**—— **理由として「AI エージェントによる数時間単位の再発見」を挙げている。**

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月5日（OpenSSH 10.6p2 のリリースと Alpine Linux のアドバイザリ） 最終更新: 2026年11月6日（本記録の作成。一次公表を取得して裏を取った時点）

これは「長いパスワードを送るだけで、パスワードを持たないアカウントに入れてしまう」脆弱性です（出典1・3・4）〈重要〉。

2026年11月5日、OpenSSH は緊急リリース 10.6p2 を公開しました（出典1・2）。対象は、Linux 上で musl libc を使い、PAM を無効にしてビルド・実行している sshd です（出典1・4）。この構成では、/etc/shadow のパスワード欄が「*」のアカウント——鍵認証だけで使うユーザー、ディレクトリサービス由来のユーザー、Alpine の基礎イメージの root など——に対し、257〜1024バイトの長いパスワードを送るとログインが成功しました（出典3・5）。正しいパスワードは要りません。要るのはアカウント名と、SSH ポートへの到達です（出典4・5）。

仕組みは2つの古い判断の噛み合わせです（出典5。本記録の整理）。muslのcrypt()は、鍵が256バイトを超えると失敗し、失敗の印として文字列「*」を返します（2012年の変更。出典5）。一方 OpenSSH は2016年、利用者名の列挙を防ぐために、使えるハッシュを持たないアカウントでもハッシュ化の処理を走らせるようにしました（CVE-2016-6210 対策。出典5・7）。「」は、パスワード欄の「」と同じ文字列です。照合が一致します（出典1・3・5）。

成立条件は狭く、同時に現実的です（本記録の評価）。Alpine は、①PAM 無しの openssh-server、②PasswordAuthentication が有効、③パスワード欄が「*」のアカウントがある、④salt を借りられる $5$／$6$ のハッシュを持つローカルアカウントが1つ以上ある、の4点を挙げています（出典3）〈重要〉—— ④が要るのは、保存値「*」が短く salt を含まないため、sshd が別のアカウントの salt を借りる作りになっているからです（出典5）。Alpine は「パスワードを持つ利用者が1人いれば、パスワードを持たない全アカウントが露出する」と述べています（出典3・原文英語）。

本記録がもっとも注目するのは、公開の速さとその理由です（本記録の判断）〈重要〉。OpenSSH は「問題を知ったのは昨日」と書き、「可能な限り速く」出しています（出典2・原文英語）。理由として挙げているのが「AI エージェントによる急速なバグ再発見——ときに数時間のうちに起きる」事例の複数の確認で、「長い非公開期間は、主に攻撃者を利する危険な慣行だと考える」としています（出典2・原文英語）。発見そのものも AI エージェント群によるもので、発見者は約17,600回の異常なログイン試行を行ったと述べています（出典5）。脆弱性の発見と公開の両側で AI が前提になりつつある、という形が記録されています（本記録の評価）。

影響しないケースも明記されています（出典2・3）—— 非 Linux、Linux/glibc（Debian・Ubuntu・Fedora 等）、パスワード認証に PAM を使う構成、PasswordAuthentication no の構成、パスワード欄が「!」でロックされたアカウント、salt を借りられるアカウントが1つも無い構成。 CISA の SSVC は exploitation を poc（実証コードあり・悪用の観測なし）、automatable を no、technical impact を total と評価しています（出典4）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**アカウント名の取得 → SSH ポートへの到達 → 257〜1024バイトのパスワードで パスワード認証を試行 → muslのcrypt()が「*」を返す → 保存値「*」と一致して認証成功 → （構成によっては）doas 等で root 権限、という経路である**（出典1・3・5）〈重要〉—— **実際の攻撃の観測ではなく、アドバイザリの成立条件と発見者の説明を 段階に並べたものである**（本記録の明示）〈未確定1〉。 **各段階の「検知の機会」と「効きえた対策」は本記録の評価である。**

  1. 1. 偵察推定[3] [6]
    **攻撃者は SSH ポートが開いているホストと、有効なアカウント名を集める** （出典3・5。本記録の整理）。 **Alpine の tiny-cloud イメージの `alpine`、基礎イメージの `root`、 鍵だけで使う運用上のユーザー名は、推測しやすい側に寄っている**（出典3）〈重要〉。 **遠隔から確かめられるのは SSH バナーの版数とパスワード認証の受付可否だけで、 musl か・PAM があるか・該当アカウントがあるかは分からない**（出典3・6）—— **攻撃側も「試してみる」以外に判定手段を持たない**（本記録の読み）。
    根拠: Alpine アドバイザリの成立条件（出典3）／遠隔からの可観測性についての整理（出典6）
  2. 2. 初期侵入確認済[1] [3] [5] [6]
    **攻撃者は、アカウント名と257〜1024バイトの長いパスワードで パスワード認証を試す**（出典3・5）〈重要〉。 **sshd は保存値が「*」で salt を含まないため、 `$5$` または `$6$` のハッシュを持つ別のアカウントの salt を借りて 試行パスワードを crypt() に渡す**（出典3・5）。 **muslのcrypt()は256バイトを超えた鍵で失敗し、「*」を返す。 それが保存値の「*」と一致し、認証が成功する**（出典1・3・5）。 **1回の接続で成立し、再試行は要らない**（出典6）。
    根拠: OpenSSH リリースノートの記述（出典1）／Alpine アドバイザリの成立条件（出典3）／発見者の解説（出典5）
  3. 3. 権限昇格確認済[3] [6] [7]
    **到達したアカウントが root になれる構成であれば、root 権限まで至る**（出典3）〈重要〉。 **Alpine の公式 tiny-cloud イメージ（3.18.11〜3.24.3）の alpine ユーザーは、 パスワード欄が「*」で、パスワード不要の doas を持つ**（出典3・7）。 **root 自身は既定の PermitRootLogin prohibit-password で守られており、 PermitRootLogin yes にしている場合だけ直接到達できる**（出典3・6）。
    根拠: Alpine アドバイザリの tiny-cloud に関する記述（出典3）／報道（出典7）
  4. 4. 影響（暗号化・破壊・改ざん）推定[3]
    **公表されているのは「認証なしでログインできる」ところまでで、 その先に何が起きたかの観測は示されていない**（出典1・3・5。本記録の確認）〈未確定1〉。 **Alpine が点検対象として挙げているのは、 doas の使用・最近作られたユーザーとファイル・authorized_keys である**（出典3）—— **これは「永続化と横展開を疑え」という形の指示である**（本記録の読み）。
    根拠: Alpine アドバイザリの侵害指標（出典3）

    1つ目は musl 側です（出典5・6）。2012年8月9日、muslはcrypt()の失敗時の戻り値を、NULL から「何にも一致しないはずのハッシュ」である文字列「*」へ変えました。 理由は、呼び出し側が NULL を検査しないことが多いからです（出典5）—— NULL を返して相手が検査を忘れれば、そこで落ちるか、もっと悪いことが起きます。「絶対に一致しない値」を返すほうが安全だ、という判断です。 同月29日、sha256／sha512 の crypt が追加され、鍵の上限が256バイトになりました（出典5）。ここで「257バイト以上を渡すと『*』が返る」が完成します（本記録の整理）。

    2つ目は OpenSSH 側です（出典5・6）。2016年7月15日、利用者名の列挙（CVE-2016-6210）への対策として、「Determine appropriate salt for invalid users.」がコミットされました。 応答時間の差から有効な利用者名を見分けられないよう、使えるハッシュを持たないアカウントでもハッシュ化の処理を走らせる、という変更です（出典7）。保存値「*」には salt が無いので、sshd は別のアカウントの salt を借りて計算します（出典3・5）。

    噛み合わせの結果はこうです（出典1・3・5）〈重要〉—— 攻撃者が257バイト以上のパスワードを送る。sshd は他人の salt を借りて crypt() を呼ぶ。muslのcrypt()は長すぎる鍵で失敗し「」を返す。sshd はその「」を保存値「*」と比べる。一致する。

    「何にも一致しないはずの値」が、/etc/shadow の慣習で「パスワードを無効にする印」として使われていた値と、同じ文字列でした（本記録の整理）。どちらのプロジェクトも、相手の前提を知らずに正しく振る舞っています（本記録の評価）。

    責任の所在については、現在も見解が分かれています〈差異2〉—— OpenSSH は「根本原因は sshd の外にあると考えるが、sshd 経由で悪用でき、sshd 側で回避できる」としました（出典1・原文英語）。musl 側は「musl のバグではなく呼び出し側の誤用」との立場と報じられています（出典6）。本記録はどちらが正しいとは書きません。 記録するのは、境界をまたいだ前提のずれが10年見つからなかったという事実です（本記録の判断）。

    把握から1日で公開した——理由として「AI による数時間単位の再発見」を挙げている組織の対応

    本記録がこの事案から最も持ち帰るべきと考えるのは、技術ではなく公開の判断です（本記録の判断）〈重要〉。

    OpenSSH は2026年11月4日に問題を把握し、翌5日に 10.6p2 を公開しました（出典2。本記録の算出）。メーリングリストの投稿は「問題を知ったのは昨日」であり、「可能な限り速く」出していると書いています（出典2・原文英語）。

    なぜ待たなかったのか。投稿はその理由を明示しています（出典2・原文英語）〈重要〉—— 「AI エージェントによる急速なバグ再発見の事例を複数——ときに数時間のうちに——確認しており、長い非公開期間は、主に攻撃者を利する危険な慣行だと考える」。

    これは、調整型開示（coordinated disclosure）の前提が変わったという主張です（本記録の評価）。従来、非公開期間は「配布元が修正を用意し、利用者が適用する時間」を作るためにありました。 その前提は、攻撃側が同じバグを独立に見つけるまでに時間がかかる、というものです。 OpenSSH はその前提が崩れたと言っています。

    発見の側も同じ方向を向いています（出典5）〈重要〉—— 発見者は、glibc／musl・PAM の有無・shadow の有無を組み合わせて sshd をビルドし、AI エージェント群に約17,600回の異常なログインを投げさせました。 すべての構成がすべてのログインで一致したのに対し、musl かつ PAM 無しの構成だけが、通してはならないログインを通しました（出典5）。人が10年見つけなかった噛み合わせを、網羅的な組み合わせ試験が見つけた形です（本記録の読み）。

    読者が引き取るべきは、速さの側の帰結です（本記録の判断）〈重要〉—— 非公開期間が短くなるほど、「公開された時点で、まだ誰も適用していない」状態の時間が長くなります。 配布元の修正が出る前に情報が出ることも増えます。 本件では Alpine が同日に9ブランチ分の修正パッケージを出せましたが（出典3）、自前でビルドしている組織・組み込み機器を出荷している組織では、同じ日に出せるとは限りません（本記録の評価）。「アドバイザリが出てから動く」運用は、この速さに追いつきません。

    版番号では修正済みと見分けられない——スキャナーに任せきれない形の脆弱性対策・注意喚起

    この脆弱性は、道具で判定しにくい形をしています（本記録の評価）〈重要〉。理由は3つあります。

    1つ目。遠隔から成立条件が確かめられません（出典3・6）。ネットワーク越しに見えるのは、SSH バナーの OpenSSH の版と、パスワード認証を受け付けるかどうかだけです（出典6）。musl か glibc か、PAM があるか、パスワード欄が「*」のアカウントがあるか、salt を借りられるアカウントがあるかは、すべてホスト上でしか分かりません（出典3）。

    2つ目。Alpine の修正版は版番号が古いままです（出典3・6）〈重要〉—— 3.24 の修正は 10.3_p1-r2、3.21 の修正は 9.9_p2-r1 です。 「10.6p2 より前なら影響」という判定規則を資産台帳の版数に当てると、修正済みのホストが全部ひっかかります。 見るべきはパッケージのリビジョン（-r2・-r1）のほうです。

    3つ目。CVE 割当のタイミングがずれました（出典3・4・6）。Alpine のアドバイザリは「執筆時点で CVE 番号は未割当」と書いています（出典3・原文英語）〈差異1〉。CVE-2026-123158 が割り当てられ NVD が公開したのは同日ですが（出典4）、CVE に基づいて動くスキャナーが11月5日時点で検出しない可能性が指摘されています（出典6）。

    したがって作業はホスト上の確認に落ちます（本記録の判断）—— Alpine は設定後の実効値を sshd -T | grep -i passwordauthentication で確かめる手順を示しています（出典3）。そしてもう1点、更新したあと rc-service sshd restart を忘れないことです（出典3）〈重要〉—— アドバイザリ自身が「更新は稼働中の sshd を再起動しない」と明記しています（出典3・原文英語）。更新済みの台帳と、実際に穴が塞がったホストは、別物になりえます（本記録の評価）。

    「悪用の報告は確認していない」——SSVC は poc、KEV は未登録未確定事項

    悪用されたかどうかは、本記録の作成時点で分かりません（本記録の確認）〈未確定1〉〈重要〉。

    分かっているのは、各機関の評価です（出典4・6）—— CISA の SSVC は exploitation を poc、automatable を no、technical impact を total と付けています（出典4）。poc は実証コードの存在を示す値で、実際の悪用の観測を示す値ではありません（本記録の整理）。automatable: no は、大量自動化の難度が高いという評価です——前提条件（musl・PAM 無し・該当アカウント・salt を借りられるアカウント）がホストごとに揃っている必要があり、外形から判定できないことに対応すると読めます（本記録の読み）。technical impact: total は、成立したときの影響が全面的だという評価です。

    piyolog は「現在のところ公的機関等の報告は確認していない」とし、KEV が未登録であること、Detectify が11月5日15時30分（CET）時点で公開された悪用の報告を把握していないとしていることを伝えています（出典6）。OpenSSH・Alpine・発見者のいずれも、悪用の観測には触れていません（出典1・2・3・5。本記録の確認）。

    NVD の状態も記録しておきます（出典4）〈重要〉—— 本記録が API を照会した2026年11月6日時点で vulnStatus は Received で、NVD 自身の分析は終わっていません。 CVSS 8.1 は CNA（MITRE）が付けた Secondary の値です。 一方 OpenSSH はリリースノートの冒頭でこれを「critical」と呼んでいます（出典1・原文英語）〈差異4〉—— 8.1（HIGH）と「critical」は食い違って見えますが、CVSS の AC:H（攻撃条件の複雑さが High）は前提条件の多さを反映した値であり、条件が揃ったホストにとっての深刻さを表していません（本記録の読み）。スコアで優先順位を決めている組織は、ここで取りこぼします（本記録の評価）。

    もう一つの空白は規模です〈未確定2〉—— musl かつ PAM 無しの sshd をネットワークに出している台数を示す資料はありません。 本記録も走査を行っていません。 「どれだけ残っているか」は、本記録では語れません。

    緩和策
    手順: **OpenSSH 10.6p2、または配布元の修正パッケージへ更新し、sshd を再起動する** （出典1・3）〈重要〉—— **Alpine では `apk upgrade -U -a` のあと `rc-service sshd restart`**（出典3）。　副作用: **パッケージの更新だけでは稼働中の sshd は入れ替わらない**（出典3）〈重要〉—— **アドバイザリ自身が「更新は稼働中の sshd を再起動しない」と明記している** （出典3・原文英語）。 **再起動を忘れると、更新したつもりで穴が開いたままになる**（本記録の評価）。 **また Alpine の修正版は版番号が古いままなので、 資産管理台帳の版数照合では「修正済み」と判定できない**（出典3・6）。
    手順: **更新できないときは `PasswordAuthentication no` を設定して sshd を再起動する** （出典2・3）—— **Alpine は `/etc/ssh/sshd_config.d/00-no-passwords.conf` を作り、 `sshd -t && rc-service sshd restart`、確認は `sshd -T | grep -i passwordauthentication` という手順を示している**（出典3）。　副作用: **パスワードでログインしている利用者・自動処理がすべて止まる**（本記録の評価）〈重要〉—— **Alpine は「事前に鍵でのログインが通ることを確かめ、 現在のセッションは新規ログインの確認が済むまで閉じないこと」としている**（出典3）。 **更新と `PasswordAuthentication no` は、どちらか一方で穴が塞がる**（出典2・3・6）。
    手順: **更新前に公開状態だったホストは、悪用の痕跡を調べる**（出典3）—— **`/var/log/messages` で、パスワードを持たないアカウント（alpine・root・ 鍵だけで使うユーザー）に対する `Accepted password for` の行を探す。 あわせて doas の使用・最近作られたユーザーとファイル・authorized_keys を点検する**（出典3）。　副作用: **ログを残していない、またはすでに巻き取られたホストでは何も分からない** （本記録の評価）〈重要〉—— **Alpine は「ログインを否定できない場合は、侵害されたものとして扱う」としている** （出典3・原文英語）。 **「否定できないから侵害扱い」は作業量が大きく、 コンテナ群に対して機械的に適用すると再構築の範囲が広がる**（本記録の評価）。
    手順: **スキャナーの結果を鵜呑みにしない（本記録の注意）**—— **CVE 割当前の11月5日時点では CVE に基づくスキャナーが検出しない可能性があり、 遠隔から確かめられるのは版数とパスワード認証の受付可否だけである**（出典3・6）。　副作用: **ホスト上の確認（musl か・PAM があるか・該当アカウントがあるか）が 人手の作業として残る**（本記録の評価）〈重要〉—— **Alpine は設定後の値を `sshd -T` で確認する手順を示している**（出典3）。

    システム構成□ **Linux 上で musl libc を使う環境（Alpine・OpenWrt・Buildroot・Yocto 等）で sshd を動かしているか。****これが影響範囲の最初の条件である**（出典1・4・5）〈重要〉—— **glibc を使う Debian・Ubuntu・Fedora 等は影響を受けない**（出典2・7）。
    認証・認可□ **その sshd は PAM 無しでビルド・実行されているか （Alpine の openssh-server は既定で PAM 無し）。****PAM でパスワード認証を行う構成は影響を受けない**（出典2・3）〈重要〉—— **openssh-server-pam を UsePAM yes で使っているかどうかで分かれる**（出典3）。
    認証・認可□ **`PasswordAuthentication` が有効のままか（OpenSSH の既定は yes）。****これを no にすれば、更新しなくても穴は塞がる**（出典2・3・6）〈重要〉—— **逆に、鍵認証に移行済みのつもりで設定が yes のまま残っている構成は影響する** （本記録の評価）。
    データの保持□ **`/etc/shadow` にパスワード欄が「*」のアカウントがあり、 かつ `$5$`／`$6$` のハッシュを持つローカルアカウントが1つ以上あるか。****両方が揃ってはじめて成立する**（出典3・5）〈重要〉—— **「*」は鍵専用ユーザー・ディレクトリサービス由来のユーザー・ 基礎イメージの root に付きやすく、意図して付けたものではないことが多い**（出典3）。
    運用・監視□ **SSH ポートをネットワーク（特に公衆網）から到達可能にしているか。****攻撃に要るのはアカウント名とポートへの到達だけである**（出典4・5）〈重要〉—— **到達経路を踏み台・VPN に限定していれば、成立条件が揃っていても悪用の難度は上がる** （本記録の評価）。
    運用・監視□ **ホストの認証ログを外部に集約しており、インスタンスが消えた後も参照できるか。****唯一の侵害指標が `/var/log/messages` の1行である**（出典3）〈重要〉—— **集約していなければ「侵害を否定できない」状態から抜けられず、 Alpine の指示どおりなら侵害扱いになる**（出典3。本記録の評価）。
