INC-2026-0930Claude Code の承認記録に秘密情報

コーディング支援エージェント Claude Code が「次回から確認しない」の選択時に承認したコマンド本文を プロジェクト内の個人設定ファイルへ逐語保存する既定動作により、公開 GitHub 上の同ファイル 104,185 本のうち 1,122 本（約1.1%）に認証情報が含まれていたと Apiiro が2026年11月5日に公表した

意図せぬ露出（設定不備等で外部から到達可能だった）脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備作業ミス・誤操作設定不備
初報: 2026年11月5日（Apiiro の調査公表） 最終更新: 2026年11月7日（本記録の作成。Anthropic の設定ドキュメントを直接確認）

「秘密が漏れた」ではなく「秘密が公開の場に置かれている」事案です。

2026年11月5日、イスラエルのアプリケーションセキュリティ企業 Apiiro が、 公開 GitHub 上にある Claude Code の個人設定ファイル 104,185 本を調べ、 そのうち 1,122 本（約1.1%）に認証情報が含まれていたと公表しました（出典2・3・4）。 これらのファイルに含まれていた異なる秘密の値は 1,379 件で、 git の履歴・共有設定ファイル・エージェントの会話記録まで広げた調査では 1,994 リポジトリにまたがる 2,539 件に達したとされます（出典4）。 収集は2026年11月1日から3日にかけて公開 GitHub から行われました（出典4）。

仕組みは Anthropic 自身のドキュメントに書かれています。 コマンドの実行許可を求められた利用者が「はい、次回以降は確認しない」を選ぶと、 Claude Code はそのコマンドを許可規則として .claude/settings.local.json に保存します（出典1）。 コマンド本文に秘密が書かれていれば、秘密もそのまま保存されます。 同じドキュメントは、このファイルを git リポジトリ内で初めて書いたときに 利用者の全体除外ファイルへ追記する、とも記しています（出典1）。 保護は存在しますが、端末ごとであり、手で作った既存ファイルや すでに追跡下にあるファイルには効きません（出典1。本記録の整理）。

被害は確認されていません。 Apiiro は見つけた認証情報を試しておらず、いまも有効かどうかを検証していません（出典4）。 例外は1件あり、通知を受けた企業のうち1社が「露出していた鍵は有効だった」と確認したと 報じられています（出典4）。悪用の観測は、どの資料にも示されていません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃は観測されていない**（出典2・3・4。本記録の確認）。 **以下は、露出した認証情報が悪用される場合に通る経路を、 本記録が公開情報から整理したものである**—— **実際に起きた段階ではない。** **段階ごとの確度をすべて「とみられる」にしているのはそのためである。**

  1. 1. 偵察推定[4]
    **公開 GitHub を検索すれば、該当ファイルを持つリポジトリを機械的に列挙できる** （本記録の整理）。 **Apiiro が 104,185 本を数えられたこと自体が、列挙が容易であることの証拠である**（出典4）。 **絞り込みの手がかりはもう1つある**—— 追跡できた 1,105 リポジトリのうち 539 で、設定ファイルの変更に Claude の共同署名コミットが含まれていた（出典4）。 **コミットの署名は公開情報なので、外部から絞り込める。**
    根拠: 公開 GitHub 上で該当ファイル 104,185 本を列挙した調査（出典4）
  2. 2. 認証情報アクセス推定[1] [4]
    **ファイルを読むだけで認証情報が得られる**（出典2・4）。 **承認したコマンドが本文のまま許可規則として保存されるため、 接続文字列・認証ヘッダ・ログイン情報がそのまま読める形で残る**（出典1）。 **1,122 本のファイルに 1,379 件の異なる秘密があったとされる**（出典4）。 **復号も権限昇格も要らない段階である。**
    根拠: 承認コマンドが許可規則として保存される旨の提供元ドキュメントの記載（出典1）と、 1,122 本・1,379 件という調査結果（出典4）
  3. 3. 初期侵入推定[4]
    **読み取った認証情報で、本来の対象（クラウド・レジストリ・データベース・ 社内の仕組み）へ正規の認証として入れる**（本記録の整理）。 **この段階が起きたことを示す資料は無い**〈未確定2〉。 **確認できるのは、通知を受けた1社が「露出していた鍵は有効だった」と 認めたことまでである**（出典4）。 **有効であることと、使われたことは別である。**
    根拠: 有効性が確認された1件（出典4）。悪用の観測を示す資料は無い（出典2・3・4）

承認の記録が、そのまま秘密の保管場所になっていた原因・手口出典 [1] [4]

この事案の中心は、便利さと秘密の保全が同じ1行で衝突している点にある（本記録の評価）。

Anthropic のドキュメントは、動作を隠していない（出典1）。 コマンドの実行許可を求められた利用者が「はい、次回以降は確認しない」を選ぶと、 Claude Code はその承認を許可規則としてプロジェクト内の個人設定ファイルへ保存する。 承認の単位がコマンド本文であるため、本文に秘密が書かれていれば秘密も保存される。

| 要素 | ドキュメントの記載（出典1） | 本記録の読み | | --- | --- | --- | | 保存場所 | プロジェクト内の .claude/settings.local.json | リポジトリの中。つまり git の射程 | | 保存の契機 | 「はい、次回以降は確認しない」の選択 | 利用者がいちばん押したい選択肢 | | 保存される内容 | 承認したコマンドの許可規則 | コマンド本文に秘密があれば秘密も残る | | 既定の保護 | git リポジトリ内で初回書き込み時に全体除外ファイルへ追記 | 端末ごと。手で作った既存ファイルは対象外 | | 共有の想定 | チーム共有は別ファイル（.claude/settings.json）側 | 個人ファイルは共有しない前提の設計 |

保護は確かに存在する。 同ドキュメントは、git リポジトリ内でこのファイルを 初めて書いたときに、利用者の全体除外ファイルへ **/.claude/settings.local.json を 追記すると記している（出典1）。 しかし「初めて書いたとき」であり、かつ「利用者の端末の全体設定」である。 ドキュメント自身が「手で作った場合は自分で除外設定に入れること」と明記している（出典1）。 この条件を満たさない経路——先に手で作った、別の端末で作られた、 すでに git の追跡下にある——が、1,122 本の実体である（本記録の整理）。

数値は3組あり、母数が違う。見出しの数字だけを引くと規模を読み違える被害規模・影響範囲出典 [3] [4]

報道の見出しと本文で数字が食い違っている（本記録の確認）〈齟齬1〉。 本記録は3組を分けて持つ。

読み方の注意は3つある（本記録の整理）。

①約1.1%という比率が、この事案の性格を表している。 10万本のうち1,122本。「エージェントを使えば秘密が出る」ではなく、 「ごく一部の使い方で出る」。対策の設計も、全面禁止より検出と除外に向く。

②ファイル・リポジトリ・組織は別の単位である。 1,994 はリポジトリの数で、組織数ではない。 1組織が複数リポジトリを持つのが普通なので、影響組織数はこれより少ない。 逆に、1リポジトリの露出で複数の環境の鍵が出ることもあるため、 件数の大小がそのまま被害の大小にはならない。

③「露出」と「漏えい」は違う。 Apiiro は見つけた認証情報を試していない（出典4）。 有効性が確認されたのは、通知を受けた1社が認めた1件だけである。 本記録が数値の測定対象を「露出していた範囲」としているのは、 この区別を集計のうえでも保つためである。

git 履歴に残るため、「ファイルを消した」では終わらない再発防止出典 [1] [4]

対応の順序を間違えると、作業が無駄になる（本記録の評価）。

Apiiro の調査が git の履歴まで見ていること自体が、対応の順序を示している（出典4）。 ファイルを削除してコミットしても、過去のコミットには残る。 公開リポジトリでは、履歴は誰でも読める。 さらに、追跡できた 1,105 リポジトリのうち 539 で、 設定ファイルの変更に Claude の共同署名コミットが含まれていたとされる（出典4）。 外部から「このリポジトリはエージェントがそのファイルを触った」と絞り込める という意味でもある（本記録の整理）。

本記録が示す順序は次のとおり（本記録の判断。出典1・4 を踏まえる）。

  1. 先に無効化する。 露出した鍵・トークン・パスワードを失効させ、新しい値に差し替える。ファイルを消す作業より先に行う——消しても履歴に残るため、時間を稼げない。
  2. 次に追跡から外す。 個人設定ファイルを git の追跡から外し、リポジトリの除外設定に明示的に入れる。利用者の端末の全体除外設定に頼らない——端末が変われば効かない（出典1）。
  3. そのうえで履歴を見る。 現在のファイルが無くても、過去のコミットに残っていないかを確認する。 4. 最後に、承認の作法を変える。 秘密を含むコマンドを承認対象にしない（値を環境変数や秘密管理の仕組みから読む形に書き換える）。

この論点は、留保を付けて読む必要がある（本記録の評価）。

本記録は、この結論を2点で割り引く。

①文書の比較は、実装の比較ではない。 文書に書いていない動作は比較表に現れない。 「他の製品は安全だった」ではなく「他の製品の文書には同じ記載が無かった」が 確認できたことである（本記録の整理）。

②調査主体はセキュリティ製品を販売している。 報道自身がこの点を注記している（出典4）。 利害があるから間違いというわけではない——数値の母数と手法が示されている点は評価できる。 ただし「他製品との比較」は、最も利害の影響を受けやすい部分である。

自組織で効く確かめ方は、文書を読むことではない（本記録の判断）。 使っているエージェントに、秘密を含むコマンドを一度わざと承認させ、 どのファイルに何が書かれたかを自分で見ることである。 1回の作業で、製品名に依存しない答えが出る。

セキュリティ技術者への示唆
  • **鍵の失効を、ファイルの削除と履歴の整理より先に行う**
    **公開リポジトリでは git の履歴が誰でも読める**（本記録の整理）。 **調査が git の履歴まで見ていることが、その前提を示している**（出典4）。 **ファイルを消してコミットしても、過去のコミットに秘密は残る。** **履歴の書き換えは時間がかかり、その間も鍵は生きている。**
    取るべき行動 **①露出した鍵・トークン・パスワードを失効させ、新しい値に差し替える（最優先）。** **②失効で止まる自動処理を事前に把握しておく**—— 把握していないと、失効の判断自体が遅れる。 **③そのうえでファイルを追跡から外し、履歴を確認する。**
  • **除外設定は、利用者の端末の全体設定ではなくリポジトリ側に書く**
    **提供元のドキュメントは、既定の保護が 「git リポジトリ内でそのファイルを初めて書いたとき」に 「利用者の全体除外ファイル」へ追記する形だと明記している**（出典1）。 **端末ごとの保護であり、別の端末・別の利用者・手で作った既存ファイルには効かない。** **1,122 本の実体は、この条件から外れた経路である**（本記録の整理）。
    取るべき行動 **①リポジトリの除外設定にエージェントの個人設定ファイルを明示的に書く。** **②すでに追跡下にあるものは追跡から外す（除外設定だけでは止まらない）。** **③テンプレートリポジトリと新規作成の雛形に最初から入れる**—— 個人の端末設定に依存しない形にする。
  • **秘密を直書きしたコマンドを承認しない。保存先を直しても残る場所が複数ある**
    **コマンド本文に秘密がある限り、許可規則だけでなく エージェントの会話記録・シェルの履歴・端末のスクロールバッファにも残る**（本記録の整理）。 **調査が会話記録まで対象に含めていることが、その裏付けである**（出典4。 広い集計 2,539 件は git 履歴・共有設定・会話記録を含む）。
    取るべき行動 **①秘密を環境変数または秘密管理の仕組みから読む形にコマンドを書き換える。** **②エージェントに読ませないファイルを拒否規則で指定する （認証情報を置いたファイルを対象に含める）。** **③承認済みの許可規則を定期的に目で見て、秘密が混じったものを削除する。**
  • **自組織のリポジトリを、攻撃者と同じ方法で自分で列挙する**
    **外部から 104,185 本を機械的に数えられている**（出典4）。 **絞り込みの手がかりも公開されている**—— 追跡できた 1,105 リポジトリのうち 539 で、設定ファイルの変更に エージェントの共同署名コミットが含まれていた（出典4）。 **同じ列挙は自組織でもできる**（本記録の整理）。
    取るべき行動 **①組織配下の全リポジトリでエージェントの設定ファイルを検索する （公開・非公開の両方）。** **②現在のファイルが無いリポジトリでも git 履歴を検索する。** **③検査を一度で終わらせず、push 前の検査とサーバ側の保護で継続的に止める。**
法務・コンプライアンスへの示唆
  • **委託先・再委託先の開発者が使うエージェントの保存動作を、契約と点検の対象に入れる**
    **露出は開発者の端末とリポジトリで起きる**（出典1・4）。 **自組織の鍵が、委託先のリポジトリから公開される経路がある**（本記録の整理）。 **本事案の母数 1,994 リポジトリに個人・小規模の開発者が含まれていることは、 リポジトリ数と組織数の差から読み取れる**（出典4）。
    取るべき行動 **①委託契約に「自組織の認証情報を外部の版管理に置かない」旨を明記する。** **②委託先に発行する鍵は有効期限と権限範囲を絞り、委託終了時に失効させる。** **③委託先の公開リポジトリに自組織の名称・ドメインが現れないかを定期的に検査する。**
