INC-2026-0931ARTEX を使う Storm-3358 が金融を標的

金銭目的の攻撃集団 Storm-3358 が2026年10月から攻撃用エージェント型AIフレームワーク ARTEX を 金融機関への攻撃に使い始め、公開資産の走査からファイルアップロードの不備と SSRF の悪用、 オープンソースの遠隔操作ツールの設置までを機械速度で行っていると Microsoft が2026年11月6日に公表した

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）既知の脆弱性の悪用設定不備認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年11月6日（Microsoft Security Blog の公表） 最終更新: 2026年11月7日（本記録の作成。Microsoft の公表内容を直接確認）

「AIが新しい穴を開けた」事案ではありません。既知の穴を、機械の速さで一通り試す運用が始まった、という報告です。

2026年11月6日、Microsoft Threat Intelligence は、金銭目的の攻撃集団 Storm-3358 が 2026年10月から金融機関への攻撃に攻撃用エージェント型AIフレームワーク ARTEX を 使い始めたと公表しました（出典1）。 Microsoft は Storm-3358 をカンボジアを拠点とする侵入クラスタと位置づけ、 主に東南アジアの金融機関を、加えて少数ながら世界の大手金融機関を狙うとしています（出典1。原文英語）。

観測された流れは次のとおりです（出典1）。 ①公開資産の走査——ARTEX と従来型の自動化ツールを併用し、インターネットに接している システムを走査する。 ②侵入——匿名のファイルアップロードと SSRF を含む不備を悪用する。 ③足場の確保——netcat や curl でオープンソースの遠隔操作ツールを落とす。 使われたのは WISP・vshell・AdaptixC2 の3種で、永続化と横展開に用いられたとされます。 ④持ち出し——Web シェルを残し、公開情報と侵害端末から認証情報を集め、 侵害したクラウド上の識別情報でデータを持ち出す。

被害の規模は公表されていません。 被害組織名・件数・金額・持ち出されたデータ量は、いずれも示されていません〈未確定1〉〈未確定2〉。 公表されているのは手口と、8件の IP アドレスからなる痕跡の指標です（出典1）。 その指標には、同じ文書の中で値が食い違っている箇所が1つあります〈齟齬1〉。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は Microsoft が観測したとして公表した段階である**（出典1）。 **ただし「どの段階がどの被害組織で起きたか」は示されていない**—— 複数の攻撃から抽出した手口の集合として読む必要がある（本記録の留保）。 **各段階の検知機会について、Microsoft は個別の被害組織での成否を公表していない**ため、 本記録は「公表されていない」と「現実的な機会がない」を区別して記す。

使われた不備は既知の類型ばかりで、新しいのは試行の速さと幅である原因・手口出典 [1]

この公表の価値は、手口の新しさではなく「同じ手口が別の速度で来る」ことの提示にある（本記録の評価）。

Microsoft が挙げた侵入の面は2つで、どちらも古い類型である（出典1）。 匿名のファイルアップロード（認証なしでファイルを置けてしまう設定の不備）と、 SSRF（サーバに任意の宛先へ通信させる実装の不備）。 どちらも対策の教科書に載っている。

変わったのは運用である。 Microsoft は、エージェント型AIの枠組みが標的を走査するとき、 短時間に多種類の要求を送り、同じ手口の変形を試し、 あるいは機械速度で次の段階の行動へ移ると記している（出典1）。 さらにARTEX のエージェントは、認証情報を使った横展開・権限昇格・ データ持ち出しを機械速度で行えるとされる（出典1）。

| 観点 | 従来型の攻撃 | 本公表が示すもの（出典1） | | --- | --- | --- | | 走査 | 道具を順に回す | 多種類の要求を短時間に送り、変形を試す | | 侵入 | 人が結果を見て判断 | 失敗したら次の手口へ機械速度で移る | | 足場 | 用意した道具を置く | netcat・curl で既製の遠隔操作ツールを落とす | | 横展開 | 人の作業速度 | 認証情報を使って機械速度で移動・昇格・持ち出し |

防御側への含意は、対策の内容ではなく時間設計である（本記録の判断）。 「翌営業日に見る」運用では間に合わない面がある—— 走査から持ち出しまでが人の判断を挟まずに進むため、 検知してから人が動くまでの時間が、そのまま被害の幅になる。

公表された痕跡は IP アドレス8件のみで、しかも1件は文書内で値が食い違っている帰属出典 [1]

痕跡の指標として使うには、2つの限界を理解しておく必要がある（本記録の評価）。

公表された指標は IP アドレス8件だけである（出典1）。 内訳は、遠隔操作ツール WISP の指令通信の中継点が3件（199.19.95[.]66・ 199.19.95[.]67・199.19.95[.]68）、ARTEX のサーバが4件 （91.92.240[.]238・85.11.168[.]45・178.16.54[.]129・31.77.229[.]35）、 指令通信のサーバが1件（85.11.167[.]52）である。 ドメイン・ファイルのハッシュ値・証明書は公表されていない〈未確定5〉。

限界①——Microsoft 自身が、IP の照合に多くを期待していない。 公表は、攻撃者が通信元の IP を変えるために代理サーバや VPN を日常的に使い、 静的な検知を回避すると述べたうえで、それでも防御側の検知の助けになるよう 指標を提供する、としている（出典1。原文英語）。 つまり「当たれば確実、当たらなくても当然」という性質の指標である（本記録の整理）。

限界②——同じ文書の中で値が食い違っている〈齟齬1〉。 痕跡の一覧には 178.16.54[.]129、 Microsoft Sentinel 向けの捜索クエリには 178.15.54.129 とある（出典1。本記録の確認）。 第3オクテットが 16 と 15 で違う。 実務上は両方を監視対象に入れるのが安全だが、 片方は無関係の第三者の可能性があるため、遮断ではなく検知に留めるべきである （本記録の判断）。

なお本記録は、これらの指標の悪性を検証していない（本記録の明示）。 照合先のテレメトリを持たないため、検知の根拠には使えない。

Microsoft が「おとり」を前面に出したのは、相手が自動で判断するからである対策・注意喚起出典 [1]

対策の章立てに、この公表の読みどころがある（本記録の評価）。

Microsoft は、防御側の対策として「おとり」を明示的に挙げている（出典1）。 ハニーポット・おとりの資産・タールピット（通信を引き延ばして時間と資源を消費させる仕組み）・ 偽の成功の4つである。 説明はこうなっている（出典1。原文英語）。 「防御側のハニーポット、おとり、タールピット、偽の成功は、 自律的なAIによる攻撃を正規の標的から引き離せる」。 「偽の成功は、エージェントの目的が達成されたという説得力のある証拠を示し、 誤った成功判定でエージェントを止めうる」。 自社の検証では、これらの対策が実資産に届く攻撃通信を減らし、 帰属に使える高確度の信号を生んだとされる（出典1。原文英語）。

なぜ「おとり」が前に出るのかは、相手の性質から説明できる（本記録の判断）。 人が操作する攻撃では、おとりは数分で見抜かれる。 自動で判断する攻撃では、見抜く判断そのものが自動化の対象になる—— 偽の成功を信じて停止する、タールピットに資源を吸われる、 という形で攻撃側の計算資源と時間を消費させられる。

本記録は、この対策を「有望だが実装の負担が重い」と評価する（本記録の判断）。 おとりの資産は、作れば運用が付いてくる—— 本物と区別が付く管理が要り、誤って業務系に繋がれば逆にリスクになる。 検証結果が公表されているのは自社製品を含む環境での結果であり、 一般の環境での再現性は示されていない（本記録の留保）。 先に手を付けるべきは、下の段階別の対策に挙げた、面の縮小と認証の強化である。

既定の道具立てが分かっているため、通信の特徴から気づける余地がある対策・注意喚起出典 [1]

検知の手がかりとして、指標より使えるものが公表されている（本記録の評価）。

Microsoft は、ARTEX が既定で使う道具を列挙している（出典1）—— Nmap・curl・wget・Python の HTTP クライアント・Norma SDK の取得機能・ Playwright 経由のヘッドレス Chromium など。 これらの通信には、既定の利用者エージェント文字列のような 特徴が出ることがあるとされる（出典1）。

ただし公表は、同じ段落で期待値を下げている（出典1。原文英語）—— 「こうした特徴を持つ通信を遮断してもAIエージェントの攻撃は止まらない。 エージェントはすぐに特徴を変える。だが特徴を見つけることで、 防御側が活動に気づくことはできる」。

本記録の整理では、使い方は2段階になる（本記録の判断）。 ①遮断には使わない——変えられるため、遮断は誤検知の負担だけが残る。 ②気づきの入口に使う——同一の発信元から、短時間に多種類の要求が来て、 手口の変形が連続する、という挙動の組み合わせを検知条件にする。 単一の特徴ではなく、速度と幅を条件に入れるのが要点である。

公表された捜索クエリは2件（出典1）。 ①Microsoft Defender XDR 向け——過去1週間に curl で新しく ダウンロードされたファイルを、平常時と比べて探す （curl には正当な用途があると注記されている）。 ②Microsoft Sentinel 向け——公表された IP の指標を過去30日の ネットワークセッションと照合する。 ②は前節の食い違い〈齟齬1〉を含む側のクエリである（本記録の確認）。

    取るべき行動 **①自組織と連結子会社の公開資産のうち、東南アジアで運用されているものを特定する。** **②現地の運用・委託先が持つ管理権限と、本体のシステムへの経路を洗い出す。** **③現地拠点の警報が本体の監視に届いているかを確認する**—— 届いていない拠点が、この種の攻撃の入口になる。
  • **公開資産の面を減らすことを、年次の棚卸しから継続的な作業へ移す**
    **悪用された不備は匿名のファイルアップロードと SSRF であり、 どちらも「公開されていなければ当たらない」類型である**（出典1）。 **一方、走査は機械速度で広く行われる**—— 「見つかりにくい」は防御として成立しない（本記録の評価）。
    取るべき行動 **①外部から見える資産の一覧を継続的に更新する仕組みを入れる （年1回の棚卸しでは、検証環境と旧システムが残る）。** **②匿名で書き込める経路を洗い出し、認証付きの受付へ寄せる （採用応募・資料提出・問い合わせの添付を先に代替する）。** **③廃止の判断権限を現場に下ろす**—— 承認待ちで残り続ける公開資産がいちばん危ない。

    **本公表では、痕跡の一覧の IP アドレス1件と、 同じ文書内の捜索クエリの値が食い違っている**（出典1。本記録の確認）〈齟齬1〉。 **大手ベンダーの公表でも起きる**（本記録の評価）。 **指標をそのまま遮断設定へ流し込む運用では、 無関係の第三者を遮断する事故になりうる。**
    取るべき行動 **①外部から受け取った指標を、遮断ではなく検知から始める運用にする。** **②指標の取り込み時に、同一資料内の整合（表と本文・表とクエリ）を確認する。** **③指標の出所と取り込み日を記録に残し、後から取り消せるようにする。**
セキュリティ技術者への示唆
  • **指標の照合より先に、挙動の検知条件を作る。IP は変えられる**
    **公表自身が、攻撃者は代理サーバや VPN で通信元の IP を変えて 静的な検知を回避すると述べている**（出典1。原文英語）。 **さらに、既定の利用者エージェント文字列などの特徴についても 「遮断しても攻撃は止まらない。エージェントはすぐ特徴を変える。 だが気づくことはできる」と明記している**（出典1。原文英語）。 **つまり単一の特徴は、検知の入口にはなるが防御にはならない。**
    取るべき行動 **①同一発信元からの短時間・多種類の要求、手口の変形の連続を 検知条件に組み込む（速度と幅を条件に入れる）。** **②公表された捜索クエリ2件を自環境に合わせて入れる**—— curl による新規ファイルのダウンロードを平常時と比較するもの、 および公表 IP を過去30日のネットワークセッションと照合するもの（出典1）。 **③照合の結果は遮断せず、まず件数を見る**—— 誤検知の量が分かる前に遮断を入れない。
  • **SSRF 対策とクラウド識別情報の管理を、同じ1本の経路として塞ぐ**
    **公表では、SSRF の悪用（侵入）と、 侵害したクラウド識別情報による永続化・データ持ち出しが どちらも挙げられている**（出典1）。 **SSRF からクラウドのメタデータ端点に到達すれば、 その場で識別情報が取れる**（本記録の整理）—— 2つの段階は実装上ひと続きである。
    取るべき行動 **①アプリケーションからの外向き通信を許可制にし、 クラウドのメタデータ端点への到達を遮断する。** **②インスタンスに付与する権限を、そのアプリが使う操作だけに絞る。** **③クラウドの識別情報の新規作成・権限付与・資格情報の追加を 変更管理と突き合わせて監視する。**
  • **Web サーバの実行アカウントから、外部ダウンロードと書き込み領域での実行を落とす**
    **ARTEX のエージェントは netcat や curl で遠隔操作ツールを落としている**（出典1）。 **Microsoft の検知名にも 「書き込み可能なディレクトリから起動された疑わしいプロセス」 「PHP アプリケーションからの疑わしいシェル実行」が並んでいる**（出典1）。 **この経路を落とせば、侵入が成功しても足場の確保で止まる**（本記録の判断）。
    取るべき行動 **①Web サーバの実行アカウントの外向き通信を許可制にする。** **②アップロード先と一時領域を実行不可でマウントする。** **③シェルの起動を Web アプリケーションの実行主体に対して監視する （正当な用途があるため、遮断より検知から始める）。**
  • **パスワードスプレーをアカウント単位のしきい値で探さない**
    **ARTEX のエージェントは、総当たりに加えてパスワードスプレーと API の列挙・悪用を実行できるとされる**（出典1）。 **パスワードスプレーは、少数の試行を多数のアカウントへ散らす手口である**—— **アカウントごとの失敗回数のしきい値では引っかからない**（本記録の整理）。
    取るべき行動 **①アカウントをまたいだ認証失敗の集計で検知条件を作る （同一発信元・同一時間帯での横断的な失敗）。** **②API の列挙に対して、識別子の連続アクセスと 存在しない識別子への大量要求を検知する。** **③機械向け認証情報に有効期限と発信元の制限を付ける。**

  • **海外拠点・現地委託先での侵害を想定し、報告義務と連絡経路を事前に整理する**
    **標的は主に東南アジアの金融機関とされる**（出典1）。 **日本の金融機関の現地拠点・現地委託先で侵害が起きた場合、 現地の規制当局への報告と日本側の報告が併走する**（本記録の整理）。 **機械速度で段階が進む攻撃では、報告期限の起算点（検知の時点）が 短時間で過ぎる。**
