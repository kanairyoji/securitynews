INC-2026-0935偽セキュリティツールで2千台超が侵害

GitHub 上の「セキュリティツール」を装った不正なリポジトリでセキュリティ技術者が標的にされ、 2,000台超の Windows 機が AsyncRAT・クリッパー・情報窃取に侵害された（Doctor Web の報告）

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年11月5日（Doctor Web の公表） 最終更新: 2026年11月8日（本記録の作成。Doctor Web の報告本文を直接取得して確認）

「道具を作る側が、道具を装って狙われている」という報告です。 2026年11月5日、ロシアのアンチウイルス企業 Doctor Web が、 GitHub 上の不正なリポジトリによる侵害の調査結果を公表した（出典1）。 侵害された Windows 機は2,000台を超える（出典1・2）。 キャンペーンは約2年前から続いており、当初は暗号資産の利用者・ ブロックチェーンゲームの利用者・ゲームの bot やチートの利用者が標的だったが、 最近になって「スキャンの自動化」「セキュリティ検証」「ログ解析」を うたうリポジトリが公開され、標的がセキュリティ技術者へ移った（出典1・2）。実務として押さえるべき点は3つです。 ①不正なコードが置かれているのは、読まれにくい場所である（出典1）—— Visual Studio のプロジェクトファイル（.csproj のビルド前イベント）、 .suo ファイル、そして Python と Go のソースの「長い空白の先」。 ②最終段は AsyncRAT のバックドアと、 クリップボードの暗号資産アドレスを差し替えるクリッパー、情報窃取である（出典1・2）。 窃取対象には FileZilla・MobaXterm・Total Commander の FTP 設定、 VPN 設定、ブラウザのデータ、Discord のトークンが含まれる（出典1）—— 技術者の手元にある「他の環境への鍵」が狙われている。 ③ローダーは ESET・McAfee・Malwarebytes の削除を試み、 hosts ファイルを書き換えてアンチウイルスのドメインを遮断する（出典1）。なお本記録は、Doctor Web の報告（出典1）の本文を直接取得して確認しました。 報告はリポジトリ名を挙げていません〈差異1〉—— したがって「どのリポジトリか」を名指しで確認する手段は、本記録にはありません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は Doctor Web が観測したとして公表した段階である**（出典1）。 **「どの段階がどの被害者で起きたか」は示されていない**—— **公表は2,000台超の侵害を横断してまとめた記述である**（本記録の整理）。 **各段階の確度は、公表が明示している手口については confirmed、 本記録が補った解釈には presumed を付した。**

  1. 1. 初期侵入確認済[1] [2]

    根拠: Doctor Web の調査（出典1）。検出名 PowerShell.Packed.270
  2. 2. 実行確認済[1]
    **初段の PowerShell スクリプトが `t.ps1` または `L.ps1` としてパブリックの画像フォルダに保存され、実行される** （出典1）。 **攻撃者のサーバに加えて YouTube・Telegram・Google Docs・GitCode・Pastebin へ 問い合わせ、暗号化された文字列を復号して `Quixo.7z` の URL を得る**（出典1）。 **展開先は `C:\ProgramData\Windows.Microsoft.Photos`**（出典1）。
    根拠: Doctor Web の調査（出典1）。検出名 PowerShell.Packed.270

不正なコードは「読まれない場所」に置かれており、ソースレビューでは見つからない原因・手口出典 [1] [2]

本件の核は、手口の新しさではなく置き場所の選び方である（本記録の評価）。

Doctor Web が挙げた隠し場所は3つある（出典1）。

| 置き場所 | いつ動くか | なぜ見つけにくいか | | --- | --- | --- | | .csproj のビルド前イベント | コンパイルの前 | コードを実行していないつもりでも、ビルドしただけで動く | | .suo（利用者別の設定ファイル） | Visual Studio がプロジェクトを開いたとき | 普段レビュー対象にならない。バイナリ形式で文字列検査も通りにくい | | .go／.py のソース（大量の空白の先） | スクリプトの実行時 | 横スクロールしない限り画面に現れない |

「ビルドしただけで動く」が本件で最も実務に効く点である（本記録の判断）。 外部の道具を評価するとき、 「コードを読んでから実行する」という順序を守っていても、 読むためにプロジェクトを開き、動作を確かめるためにビルドした時点で終わっている。

空白による隠蔽について、出典2 は 「古い手法だが、いまも有効であることが証明されている」と書いている （出典2。原文英語）。 本記録も同じ評価である—— 差分レビューの画面は、長い行を折り返さずに切ることが多い。

狙われているのは技術者の情報ではなく、技術者が持つ他の環境への鍵である被害規模・影響範囲出典 [1] [2]

窃取対象の一覧を読むと、標的を切り替えた理由が見える（本記録の評価）。

Doctor Web が挙げた窃取対象は次のとおりである（出典1）。 ブラウザのデータ、FileZilla の XML、MobaXterm.ini、 Total Commander の wcx_ftp.ini、VPN 設定、メッセンジャーのファイル、 ゲームとゲーム基盤のアカウント情報、Discord のトークン。

前半3つが決定的である（本記録の判断）。 FileZilla・MobaXterm・Total Commander はいずれも 接続先のホスト・利用者名・保存されたパスワードを設定ファイルに持つ。 VPN 設定も同じ性質である。 つまり、1台の端末から出ていくのは個人のデータではなく、 その人が日常的に接続している環境の資格情報である。

本記録の整理では、ここに2段の波及がある。 ①技術者の端末 → その人が管理する本番・顧客環境。 ②その環境 → さらにその先の利用者。 当初の標的が暗号資産の利用者だったのに対し（出典1・2）、 セキュリティ技術者へ移した判断は、 1台あたりの「到達範囲」を上げる方向の変更である（本記録の評価）—— 公表はこの意図までは述べていないため、これは本記録の解釈である。

あわせて、クリッパー（暗号資産アドレスの差し替え）と AsyncRAT の2本構成が残っていることにも触れておく（出典1）。 AsyncRAT が2本・別ポートで動くのは 「2人の運用者が1台を操作できるようにするため」と説明されている （出典1。原文英語）—— 金銭の直接的な回収と、環境への足場の確保が、同じ侵害の上で並走している。

ローダーは検知の土台を外すが、設定変更の痕跡は残る評価・解釈出典 [1] [2]

防御側が使える信号はどこに残るか、を分けて考える必要がある（本記録の判断）。

ローダー（Doctor Web の検出名 Trojan.Loader.3261）の既定モード Mode3 は、 次の回避手法を用いる（出典1・2）。 親プロセスの偽装（explorer.exe を親に見せる）、 レジストリ値の変更による Smart App Control の迂回、 ディスクから元の ntdll.dll を復元してセキュリティ製品のフックを外す、 Halo's Gate 方式による直接システムコール、 ETW（EtwEventWrite）のパッチ、AMSI（AmsiScanBuffer）のパッチ。 注入先は RegAsm.exe・dwwin.exe・dwm.exe である（出典1）。

これらはいずれも「ユーザーモードでの可視性」を削る手法である （本記録の整理）—— プロセス実行の記録、スクリプトの内容検査、API フックに依存した検知は、 この段階より後ろでは効きにくくなる。

一方で、外せない痕跡が残る（本記録の判断）。

| 残る痕跡 | 性質 | | --- | --- | | Defender の除外の追加（regasm.exe・dwm.exe 等） | 設定変更。製品の管理側に記録が残る | | hosts ファイルの書き換え（アンチウイルス事業者のドメインの遮断） | ファイル変更。drivers\etc の一部削除も伴う | | VSS・システムの復元の無効化 | 設定変更。バックアップの前提が崩れる | | ESET・McAfee・Malwarebytes の削除の試み | 管理サーバ側で「エージェントの応答が止まった端末」として見える | | パブリックの画像フォルダでの .ps1（t.ps1／L.ps1）の実行 | 置き場所が明確に異常である |

本記録の判断として一点強調する。 アンチウイルスが削除される構成では、 端末側の検知に頼ると「止められた瞬間」が見えない。 管理サーバ側で応答の途絶を異常として扱う仕組みが要る。

なお、Mode3 の回避手法の数について、 出典2 は6つと数え、出典1 の記述では ETW と AMSI のパッチを まとめて読める形になっている（本記録の確認）—— 数え方の違いであり、内容の食い違いではないと本記録は判断する。

配布に正規サービスを使うため、通信先のドメインで善悪を判定できない対策・注意喚起出典 [1] [2]

本件は「怪しいドメインを遮断する」方式が効かない構成である （本記録の評価）。

初段の PowerShell スクリプトは、攻撃者のサーバに加えて YouTube・Telegram・Google Docs・GitCode・Pastebin に問い合わせ、 暗号化された文字列を復号して配布元の URL を得る（出典1）。 窃取データの送信先も Telegram の bot である（出典1）。 ローダーからの報告も Telegram 経由である（出典1）。

本記録の整理では、ここから出る実務の結論は次のとおりである。

①宛先ドメインによる判定は使えない。 YouTube・Google Docs を遮断する運用は、ほとんどの組織で成り立たない。

②効くのは「誰が」の側である。 PowerShell のプロセスが Telegram の API へ接続する、 ビルドの過程で外部へ接続する、といった 「プロセスと宛先の組み合わせ」を条件にする必要がある。

③痕跡の指標（IP・ドメイン）に依存した検知は、 本件では特に寿命が短い（本記録の判断）—— 配布の中継が正規サービスである以上、 攻撃者は中継先の投稿を差し替えるだけで経路を変えられる。 なお、出典2 は指標の完全な一覧が共有されたと記しているが、 本記録はその一覧を取得していない〈未確定6〉。

影響を限定できた外部リポジトリのビルドと実行を、資格情報・VPN 設定・ FTP クライアントの設定を持たない使い捨て環境に限定する　**本記録の評価。** **「防げた」ではなく「限定できた」とする理由は、 情報窃取側がサンドボックスと仮想機械を検査するため**（出典1）—— **分離環境では動かないことがあり、悪性の確認には使えない。** **目的は観察ではなく、鍵をその環境に置かないことである。**
実行機会はあったが検知できず
**本記録の判断では、この段階も検知できる**—— **パブリックの画像フォルダに置かれた `.ps1` の実行は、 正規の運用ではまず起きない。** **一方で、通信先による判定は効かない**（出典1。本記録の整理）—— **中継が正規サービスであるため、 宛先ドメインの善悪では区別できない。** **効くのは「PowerShell が Telegram の API へ接続する」のような プロセスと宛先の組み合わせである。**
検知できたパブリックフォルダ・一時フォルダからのスクリプト実行を 検知条件に入れる（遮断ではなく気づきの入口として使う）
検知できたプロセスと宛先の組み合わせを条件にする （開発ツール・スクリプト実行系から外部メッセージング API への接続）　**本記録の評価。** **正規サービスを中継に使う構成では、 宛先だけの条件は作れない**（出典1）。
検知回避機会はあったが検知できず
**ETW と AMSI をパッチされた後では、 ユーザーモードの可視性に依存した検知は効きにくい**（出典1。本記録の整理）。 **ただし設定変更の痕跡は残る**（本記録の判断）—— **Defender の除外の追加、hosts の書き換え、VSS の無効化、 アンチウイルスのエージェントの応答の途絶。** **これらは端末側ではなく管理サーバ側で見える信号である。**
検知できたDefender の除外の追加・hosts ファイルの変更・VSS とシステムの復元の 無効化を、設定変更の監査として検知する　**本記録の評価。** **いずれも正規の運用でも起きるため、 遮断ではなく気づきの入口として使う。**
検知できたアンチウイルス・EDR のエージェントの応答が止まった端末を、 管理サーバ側で異常として扱う　**本記録の評価。** **製品の削除が試みられる構成では**（出典1）、 **端末側の検知に頼ると止められた瞬間が見えない。**
影響を限定できた端末での管理者権限の常用をやめ、 セキュリティ機能の無効化に管理者の承認を要する構成にする
永続化公表されていない
**公表は、被害者側で永続化が検知されたかどうかに触れていない**（出典1）。 **本記録の判断では、`C:\ProgramData\Windows.Microsoft.Photos` という置き場所は検知条件にしやすい**—— **正規の Windows のコンポーネント名に似せているが、 その場所に実行可能ファイルが置かれること自体が異常である。**
検知できたProgramData 配下の実行可能ファイルの新規作成と、 そこからの実行を検知条件に入れる
検知できた自動起動の経路（タスク・レジストリの Run キー・サービス）の 変更を定期的に差分で確認する
認証情報アクセス公表されていない
**公表は被害者側の検知に触れていない**（出典1）。 **本記録の判断では、この段階は検知しうる**—— **FTP クライアント・ターミナルソフトの設定ファイルへの 別プロセスからの読み取りは、正規の運用ではまず起きない。** **ただし ETW と AMSI がパッチされた後の段であるため**（出典1）、 **ファイルアクセスの監視がカーネル側に根を持つ製品でなければ見えない。**
検知できたFileZilla・MobaXterm・Total Commander・VPN クライアントの 設定ファイルへの読み取りを、正規プロセス以外から行われた場合に検知する
侵入を防げたこれらのクライアントに資格情報を保存する運用をやめ、 踏み台経由・短期の資格情報・鍵管理の仕組みへ寄せる　**本記録の評価。** **窃取されても使えない形にするのが唯一の確実な手である** ——**ただし代替の仕組みを用意せずに禁止すると、 各自が別の場所へ逃がすため効果が出ない。**
C2通信公表されていない
**公表は被害者側の検知に触れていない**（出典1）。 **本記録の判断では、Telegram の bot API への定常的な通信は 検知条件になる**—— **ただし Telegram を業務で使う組織では分けられないため、 「どのプロセスが接続したか」を条件に含める必要がある。**
検知できたメッセージング基盤の API への接続を、 接続元プロセスとあわせて検知条件に入れる
影響を限定できた技術者の端末を業務ネットワークの中で分離し、 本番環境への直接の到達を踏み台経由に限定する　**本記録の評価。** **窃取された資格情報が使われる段を遅らせる。**
影響（暗号化・破壊・改ざん）現実的な検知機会なし
**クリップボードの差し替えは、利用者側で気づく機会がほとんど無い** （本記録の評価）—— **送金先を目で確認する習慣が無ければ、差し替えは成立する。** **技術的な検知も、クリップボードの読み書き自体が正常な操作であるため難しい。** **本記録が「現実的な検知機会がなかった」とするのは、 「この段階に至ってからの検知」を前提にした場合である**—— **前段で止めるしかない。**
侵入を防げた暗号資産の送金を伴う業務がある場合、 送金先アドレスの検証を別の経路（別端末・別チャネル）で行う　**本記録の評価。** **クリッパーに対する確実な対策は、 差し替えを検知することではなく、別経路での確認である。**
影響を限定できた窃取された資格情報の悪用に備え、 FTP・SSH・VPN の接続元 IP の限定と、異常なログインの検知を置く

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • **セキュリティ部門の端末を、社内で最も守られていない端末のまま放置していないか確認する**
    **本件の標的はセキュリティ技術者であり、 窃取対象には FTP クライアント・ターミナルソフト・VPN の設定が含まれる**（出典1）。 **これらは「他の環境への鍵」である**（本記録の判断）—— **1台の侵害が、その人が管理する本番環境・顧客環境へ広がる。** **一方で、調査・検証を行う端末は 「仕事上必要だから」という理由で例外運用になりやすい**（本記録の評価）。
    取るべき行動 **①セキュリティ・開発部門の端末に適用されている例外（管理者権限の常用、 製品の除外設定、ネットワークの自由な到達）を一覧にする。** **②各例外について、業務上の必要性と代替手段を見直す期日を決める。** **③例外を残す端末については、分離（本番環境への直接到達を禁止し踏み台経由にする）を 代償として要求する。**
  • **外部の道具を取り込む経路を、業務プロセスとして可視化する**
    **本キャンペーンは約2年続き、2,000台超が侵害された**（出典1）。 **侵入の起点は、利用者自身がリポジトリを取り込む行為である**（出典1・2）—— **脆弱性の悪用ではない。** **公表はリポジトリ名を挙げていないため、 名前の遮断リストでは対処できない**（出典1）〈差異1〉。
    取るべき行動 **①外部の道具（GitHub のリポジトリ・スクリプト・ビルド済みバイナリ）を 業務で使う際の経路を文書化する（誰が・どこで・何を確認して取り込むか）。** **②取り込みの検査と、分離環境での実行を手順に組み込む。** **③手順が現場の速度を落とす点を認め、 「検査済みの道具の共有置き場」を用意して迂回の動機を減らす。**
  • **アンチウイルス製品の削除・無効化を、検知の対象として設計に入れる**
    **ローダーは ESET・McAfee・Malwarebytes の削除を試み、 hosts ファイルでアンチウイルス事業者のドメインを遮断する**（出典1）。 **さらに Defender・UAC・通知・システムの復元・VSS を無効化する**（出典1）。 **製品が削除された後では、その製品自身が異常を報告できない**（本記録の判断）。
    取るべき行動 **①管理サーバ側で「エージェントの応答が止まった端末」を 異常として扱う仕組みを確認する（止まっただけで警報が出るか）。** **②VSS・システムの復元の無効化を検知条件に入れる （ランサムウェアの前段としても同じ操作が行われる）。** **③バックアップが端末の VSS に依存していないかを確認する。**
  • **「2年続いた」という事実から、自組織の過去を遡って確認する判断をする**
    **キャンペーンの開始は約2年前であり、 標的がセキュリティ技術者へ移った時期は公表されていない**（出典1）〈未確定2〉。 **つまり、自組織の技術者が過去に取り込んだ道具が 対象に含まれていた可能性を、現時点の検査では否定できない**（本記録の判断）。
    取るべき行動 **①技術者の端末について、過去に取り込んだ外部リポジトリの一覧を 可能な範囲で洗い出す（ローカルのクローン先・ビルド履歴）。** **②`C:\ProgramData\Windows.Microsoft.Photos` の存在、 パブリックの画像フォルダの `.ps1`、Defender の除外設定、 hosts ファイルの内容を点検する。** **③見つからないことを「侵害なし」の結論にしない—— ログの保持期間を確認し、確認できた範囲を明記して報告させる。**
セキュリティ技術者への示唆
  • **「コードを読んでから実行する」では足りない。ビルドしただけで動く場所がある**
    **不正なコードは `.csproj` のビルド前イベント（PreBuildEvent）に置かれ、 コンパイルの前に実行される**（出典1）。 **`.suo`（利用者別の設定ファイル）には PowerShell のコマンドが入る**（出典1）—— **Visual Studio がプロジェクトを開いた時点の経路である。** **`.go`／`.py` では、大量の空白の先に本体が置かれている**（出典1）。
    取るべき行動 **①クローン直後に、ビルド前後イベント（`PreBuildEvent`／`PostBuildEvent`）の 有無を機械的に検査する。** **②`.suo` などの利用者別設定ファイルが同梱されているリポジトリを拒否する （本来は `.gitignore` の対象であり、入っていること自体が異常である）。** **③極端に長い空白を含む行を検出する検査を入れる （行の長さの閾値と、空白の連続の長さの両方で見る）。** **④検査は、プロジェクトを IDE で開く前に行う。**
  • **分離環境は「観察のため」ではなく「鍵を置かないため」に使う**
    **情報窃取はサンドボックスと仮想機械を検査する**（出典1）—— **分離環境では動かないため、「動かして様子を見る」方式では悪性を確認できない。** **一方、窃取対象は FileZilla の XML、MobaXterm.ini、 Total Commander の wcx_ftp.ini、VPN 設定である**（出典1）—— **これらが環境に無ければ、動いても取るものが無い**（本記録の判断）。
    取るべき行動 **①外部の道具を試す環境から、FTP クライアント・ターミナルソフト・ VPN クライアントの設定と保存された資格情報を排除する。** **②その環境のブラウザに業務のセッションを持たせない。** **③「分離環境で動いたから安全」という判断をしない—— 検査を回避している可能性があることを前提にする。**
  • **検知は、プロセスの実行ではなく設定変更の側に置く**
    **ローダーは ETW（EtwEventWrite）と AMSI（AmsiScanBuffer）をパッチし、 ディスクから `ntdll.dll` を復元してフックを外し、 Halo's Gate 方式で直接システムコールを行う**（出典1・2）—— **ユーザーモードの可視性に依存した検知は後段で効きにくい。** **一方で、Defender の除外の追加、hosts ファイルの書き換え、 VSS とシステムの復元の無効化、`regasm.exe`／`dwm.exe`／`dwwin.exe` への注入は 痕跡として残る**（出典1。本記録の整理）。
    取るべき行動 **①Defender の除外設定の変更、hosts ファイルの変更、 VSS・システムの復元の無効化を監査の対象にする。** **②`RegAsm.exe`・`dwm.exe`・`dwwin.exe` が ネットワーク通信を行う、または異常な親子関係で起動する事象を条件にする。** **③`C:\ProgramData` 配下の実行可能ファイルの新規作成と実行、 パブリックの画像フォルダでの `.ps1` の実行を条件にする。** **④遮断ではなく気づきの入口として導入し、 誤検知の量を見ながら条件を詰める。**
  • **通信先のドメインで判定しない。正規サービスが中継に使われている**
    **初段のスクリプトは YouTube・Telegram・Google Docs・GitCode・Pastebin へ 問い合わせ、暗号化された文字列を復号して配布元の URL を得る**（出典1）。 **窃取データとローダーの報告も Telegram の bot 経由である**（出典1）。 **これらを遮断する運用はほとんどの組織で成り立たない**（本記録の判断）。
    取るべき行動 **①「プロセスと宛先の組み合わせ」を条件にする （PowerShell・開発ツールからメッセージング API への接続など）。** **②痕跡の指標（IP・ドメイン）に依存した検知を主軸にしない—— 中継先の投稿を差し替えるだけで経路が変わる。** **③Pastebin・GitCode のような貼り付け系サービスへの スクリプト実行系からの接続を、個別に条件化する。**
  • **資格情報を「クライアントに保存する」運用から降りる**
    **窃取対象の中心は、FTP クライアント・ターミナルソフトの設定ファイルと VPN 設定である**（出典1）。 **これらには接続先・利用者名・保存されたパスワードが入る。** **窃取されても使えない形にするのが唯一の確実な手である**（本記録の判断）。
    取るべき行動 **①FileZilla・MobaXterm・Total Commander への資格情報の保存を禁止し、 踏み台経由・短期の資格情報・鍵管理の仕組みへ寄せる。** **②禁止の前に代替手段を用意する—— 用意せずに禁止すると、各自がテキストファイルへ逃がす。** **③FTP・SSH・VPN の接続元 IP を限定し、 保存された資格情報が外部から使われても通らない状態を作る。**
法務・コンプライアンスへの示唆
  • **技術者の端末が侵害された場合に、顧客環境への到達が生じうることを契約側で想定する**
    **窃取対象に FTP クライアント・ターミナルソフト・VPN の設定が含まれる**（出典1）—— **受託業務で顧客環境へ接続している技術者の端末が侵害されると、 顧客環境への到達が生じうる**（本記録の判断）。 **この場合、通知の義務と主体は委託契約の内容に依存する。**
    取るべき行動 **①受託業務の契約に、自社端末の侵害時の通知義務・期限・ 窓口が書かれているかを確認する。** **②顧客環境への接続に使っている資格情報の一覧を、 契約単位で把握できる状態にする（侵害時に影響範囲を即座に示すため）。** **③侵害時に顧客側で必要になる作業（資格情報の失効・接続元の遮断）を 事前に合意しておく。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ 技術者・開発者が、GitHub 等の外部リポジトリを業務端末で直接クローンし、 ビルドまたは実行している（取り込み前の検査の段が無い）
システム構成□ 技術者の端末に、FileZilla・MobaXterm・Total Commander・VPN クライアントの 設定と保存された資格情報が置かれており、そこから本番・顧客環境へ直接到達できる
運用・監視□ 端末のセキュリティ製品の除外設定・無効化が利用者の権限で行え、 管理サーバ側で「エージェントの応答が止まった端末」を異常として扱っていない
運用・監視□ 検知の条件が、痕跡の指標（IP・ドメイン・ハッシュ値）の照合に依存しており、 挙動・設定変更の側の条件を持っていない
システム構成□ バックアップが端末の VSS（ボリュームシャドウコピー）に依存している
体制・契約□ 受託業務で顧客環境へ接続しており、 自社端末の侵害時の通知義務・影響範囲の提示方法が契約・手順で決まっていない
