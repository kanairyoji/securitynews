攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**2つの経路が同じ IP アドレスに収束している**（出典1・2）。 **経路A（Microsoft）** ——**ARTEX で GitHub を検索して OAuth アプリの秘密を見つけ、 サービスプリンシパルとして Entra ID にサインインし、 Azure を列挙して Key Vault の秘密・ストレージキー・ SharePoint と OneDrive のファイル・Azure DevOps 内の秘密へ到達する**（出典1）。 **経路B（VulnCheck）** ——**露出した Langflow の CVE-2025-3248 を突いて `/api/v1/validate/code` に Python を送り、 環境変数・`.env`・`langflow.db`・ログを掃き、 Fernet で暗号化された変数を Langflow 自身の鍵導出で復号する**（出典2）。 **どちらも終着点は同じである**（出典2）—— **「どちらの経路も同じ場所に行き着く。 AI サービスの資格情報と、その背後のクラウド資源である」**（出典2。訳は本記録）。

  1. 1. 偵察disclosed[1] [2]
    **ARTEX が GitHub を大量に検索して秘密を探した**（出典1）—— **2026年8月以降の観測で、問い合わせには標的組織の名前・ 秘密に関する語・クラウドサービス名・他の AI サービス提供者名が 組み合わされていた**（出典1）。 **ARTEX は「人の操作者より速く複数の GitHub リポジトリを走査し、 エージェントが結果を分析して後続の攻撃を走らせる」**（出典1。訳は本記録）。 **別に、199.19.77.84 は2026年11月2日にスウェーデンとブラジルのカナリアへ PHP の露出確認（CVE-2026-109618／CVE-2026-109619 の前段）を送っている**（出典2）—— **「ここでの内容は無害なので、これは悪用ではなく露出の確認だった」**（出典2。訳は本記録）。 **157.22.126.128 は Azure AI サービス上の AI ワークロードの偵察に使われた**（出典1）。
    根拠: Microsoft Threat Intelligence のブログ（出典1）および VulnCheck のカナリア記録（出典2）。
  2. 2. 初期侵入disclosed[1] [2]
    **経路A: 2026年10月28日以降、漏えい・窃取されたアプリケーション資格情報で サービスプリンシパルとして Entra ID にサインインした**（出典1）—— **「複数のテナントにまたがる数十のアプリケーション」が対象で、 一部はベンダー保有のマルチテナントアプリの資格情報であり、 下流のテナントへのアクセスに使われた**（出典1）。 **サインイン元は 199.19.77.84 と 199.19.77.18（Tor の出口ノード）である**（出典1）。 **65.87.223.26 は、User-Agent に埋め込んだシェルコマンドによる悪用の可能性と、 App Service の認証トークンの取得試行に使われた**（出典1）。 **経路B: 2026年11月7日00時02分、199.19.77.84 が英国のカナリアの Langflow に CVE-2025-3248 のペイロード（第1段）を送った**（出典2）。

    根拠: VulnCheck が公開した第2段のペイロード全文（出典2）、Microsoft の観測（出典1）。

この事案で下された判断
  • **Microsoft は、脅威アクター名を付けずに「threat actors」として公表した**（出典1）。
    トレードオフ: **本記録の整理。** **名前が無いぶん、防御側は「どの集団を警戒すればよいか」を言えなくなる。** **経営への報告や取引先への注意喚起では、 「ARTEX という道具を使う何者か」としか書けず、 脅威の輪郭が伝わりにくい**（本記録の評価）—— **Microsoft は正確さを取り、伝わりやすさを捨てた。**
  • **VulnCheck は、Microsoft の公表（11月5日）の3日後、 自社の観測（11月7日）の翌日に公表した**（出典2）。
    トレードオフ: **本記録の整理。** **おとり装置の中身（11段階のペイロード全文・検知の手がかり）を 公開したことで、攻撃者側も「どこを見られているか」を知った**（本記録の評価）—— **VulnCheck 自身が「セッションごとに生成されるため文字列は持続しないだろう」 としているとおり、公開した指紋の寿命は短くなる。** **防御側の速さを取り、指標の持続性を捨てた形である。**

三つめの扉は MSP だった——1つのアプリ資格情報が15の顧客テナントを10秒周期で掃いた波及・関係先出典 [5] [6]

本記録は当初、侵入口を「GitHub の漏えい秘密」（Microsoft）と「露出した Langflow」（VulnCheck）の2つで整理していた。 2026年11月9日に Todyl の原典（出典5）を取得して読むと、実務上もっとも広がりの大きい経路は3つめ——MSP 経由だった（本記録の整理）〈重要〉。

持ち出されたファイルの中身が、この事案の重さを決めている（本記録の評価）。「パスワード一覧・秘密鍵・VPN プロファイル・MFA と RMM の API キー・バックアップ保管先の資格情報・ファイアウォールと RDP の設定・Azure 環境の目録・サービスアカウントの対応表」（出典5。訳は本記録）〈重要〉。Todyl は「これらは Microsoft 365 の外（VPN・MFA サービス・RMM と監視基盤・バックアップ保管先・ネットワーク機器）へ移るために必要なものであり、その露出は Microsoft 365 のログからは見えない」と書いている（出典5。訳は本記録）—— つまり、観測できた範囲が被害の範囲ではない（本記録の読み）。

セキュリティ製品の連携用アプリも悪用された側に入っている。 「セキュリティ道具の連携用の資格情報——2つの MSP テナントにおけるTodyl 自身の連携アプリを含む——が悪用されたものの中にあった。いずれかのベンダーのプラットフォームが侵害された兆候は無い」（出典5。原文英語・訳は本記録）〈重要〉—— 報告者が自社の名前を被害側に書いている点を、本記録は記録に値する誠実さとして残す（本記録の評価）。

恒常化（永続化）は観測されていない（出典5）—— 新しい同意・資格情報・ロール・利用者の追加はいずれも無い。 代わりに攻撃者は、無効化・ローテーション済みのアプリに対しても約11秒周期で再試行を続け、利用者のリフレッシュトークンの再生に移った（出典5）〈重要〉—— 「資格情報のローテーションだけでは足りない」というのが Todyl の結論である（出典5。訳は本記録）。11月3日に観測されたトークン再生は、条件付きアクセスがすべて遮断している（出典5）。

「種」はどこから来たのか——Microsoft は GitHub、Todyl はファイル保管庫か稼働中のバックエンドと見ている原因・手口出典 [1] [5]

初期侵入の説明が、2つの報告で食い違っている（本記録の整理）〈重要〉〈差異6〉。

Microsoft は GitHub だとする。 「2026年8月以降、Microsoft は攻撃者が自律型の AI オフェンシブフレームワークを使って秘密を求める大量の問い合わせを GitHub に送るのを観測した」（出典1。訳は本記録）。

Todyl は、少なくとも自社が見た「種」については別の見方を示す。 「それがどのようにしてこれらの資格情報を最初に手に入れたのかは、いまも不明である。いくつかの種となったシークレットは、職員の端末と社内ネットワークからしか使われたことが無く、一部は『現行のものと期限切れのもの』の対で届いていた。これは、インターネットから巡回して集めた設定ファイルではなく、ファイル保管庫か稼働中のバックエンドを指し示す」（出典5。原文英語・訳は本記録）〈重要〉。

一方で、11月6日の更新では Todyl 自身が「自律型の資格情報クローラ」という見方に寄せている（出典5）—— ①AbuseIPDB に最初のサインインの数日前から同 IP による資格情報の走査が記録されている、②初期アクセスより前のクラウド・端末の侵害の直接の証拠が無い、③影響を受けたアプリの多くが自社開発である、という3点を根拠に挙げ、「公開リポジトリや Web アプリに露出した資格情報が出所として最もありそうだ」としている（出典5。訳は本記録）。

本記録は、この2つの記述を矛盾ではなく「観測範囲の違い」として扱う（本記録の判断）。Microsoft が見たのはクラウド全体のテレメトリ、Todyl が見たのは自社にログを送る MSP とその顧客のサインインログである。 「種」の供給源が1つである必要は無い（本記録の評価）—— ただし「GitHub に秘密を置いていなければ関係ない」という読み方は、Todyl の記述によって成り立たなくなる。

Todyl は、確定していない関連可能性を3つ明示している（出典5）〈差異7〉。

  • Storm-0940 による ConnectWise Cloud Backup（旧 SkyKick）の侵害（2026年10月。Microsoft は中国国家に連なると評価）—— アプリ身元でのサインイン・MSP の道具を狙う点・スクリプトの速さ・Key Vault への関心は似るが、単一のベンダーアプリではなく被害者自身のアプリ資格情報が狙われている点、インフラが異なる点、恒常化が無い点、SkyKick の影響テナントとの重なりが無い点が違う—— Todyl は本件を SkyKick 侵害とは無関係と評価している（出典5）〈重要〉。
  • Cursor のマーケットプレイスで配られた改ざんされた Claude Code 拡張（2026年10月29日。改ざん版 2.1.312／2.1.313 が約11時間公開され、SSH 鍵の設置と 134.209.82.225 への逆トンネルを行った。Cursor は最大5,000利用者が影響と見積もり、公式の Visual Studio Marketplace と npm の配布は影響を受けず、Anthropic は自社システムの侵害は無いと表明）—— 「時期（最初の観測の3日前）と標的（アプリの秘密・PAT・Azure DevOps のセッションを持つ開発者の端末）から、資格情報の供給源としてはあり得るが、影響組織を導入に結びつけてはいないし、ここでその基盤を見てもいない」（出典5。訳は本記録）。
  • 許可のない AI モデル利用の急増—— 「関連している確度は中、仕組みについては低」と Todyl 自身が格付けしている（出典5）。

本記録はこの3点を、Todyl の仮説として記録し、いずれも事実として扱わない（本記録の方針）〈差異7〉。

同じ IP が、GitHub の漏えい秘密とは別の扉から来ていた原因・手口

Microsoft の報告と VulnCheck の報告は、同じ IP アドレスについて違う経路を記述している（出典1・2）。

Microsoft 側の経路（出典1）—— ARTEX が GitHub を検索して OAuth アプリケーションの秘密を見つけ、その資格情報でサービスプリンシパルとして Entra ID にサインインする。 サインインの観測は2026年10月28日以降で、「複数のテナントにまたがる数十のアプリケーション」が対象だった。

VulnCheck 側の経路（出典2）—— Langflow の /api/v1/validate/code に Python を送り込み（CVE-2025-3248）、箱の中に保管された資格情報を直接取りに来る。

「漏えいした GitHub の秘密ではなく、Langflow を悪用して資格情報を機械から直接引き出していた」（出典2。原文英語・訳は本記録）

VulnCheck はこの差を明示している（出典2）——

「Microsoft も Todyl も Huntress も、この IP が脆弱性を悪用したとは記述していない。そこが我々のデータの出番である」（出典2。原文英語・訳は本記録）

本記録がこの節を最初に置くのは、「侵入口の棚卸し」が報告書ごとに欠けうることを示すためである（本記録の評価）〈重要〉。ベンダーの報告は、自社のテレメトリが見える範囲でしか書けない。 クラウド側のログを持つ Microsoft には Entra ID のサインインが見え、おとり装置を持つ VulnCheck にはアプリケーション層の悪用が見えた。 どちらの報告も間違っていないが、どちらも全体ではない。

持ち出しの経路が「応答の中」だった——外向きの通信が無い原因・手口

VulnCheck が記録した11段階には、攻撃者側への通信が1つも無い（出典2）〈重要〉。

仕掛けはこうである（出典2）。各段階は、集めた結果を |RAISE| という印を付けた例外に詰める。 脆弱な端点は例外のテキストを HTTP 応答に返すので、要求への返答そのものがデータを運ぶ。

「盗まれたデータは別の経路では出て行かない。各段階は結果を |RAISE| の印を付けた例外に入れ、脆弱な端点は例外のテキストを HTTP 応答に返すので、各要求への返答がそのデータを運ぶ。ペイロードはどれも攻撃者のインフラへ呼び返さず、何もダウンロードせず、ファイルも書かない」（出典2。原文英語・訳は本記録）

ペイロードの形は全段階で同じである（出典2）——

import os
@exec('\nimport os, json\ndef _gather():\n ...')
def _lf_probe():
    pass

デコレータは関数定義の時点で走るため、Langflow が「検証のために」コンパイルした瞬間に実行される（出典2）。

この構造は、よく置かれている検知の網をすり抜ける（本記録の評価）〈重要〉。外向きのビーコン・ファイルの書き込み・ダウンロードを見る検知には何も映らない。 VulnCheck が「警報を出す価値がある通信」として挙げたのは2つだけである（出典2）—— ①クラウドのメタデータサービス 169.254.169.254 への問い合わせ、②Docker ソケットとの通信。

VulnCheck の防御側への助言も、この構造を前提にしている（出典2）——

「IP だけでなく挙動で狩れ。大きな本文を伴う POST /api/v1/validate/code の連続、JSON の塊を運ぶエラー応答、@exec( を含む要求を見よ」（出典2。訳は本記録）

保管された資格情報の復号まで試し、4手目で成功していた被害規模・影響範囲

第5局面（00時36分〜00時38分）が、この事案でもっとも重い部分である（本記録の評価）。

Langflow は保管された変数を Fernet で暗号化している（出典2）。攻撃者は4つの手を順に試した（出典2）——

  1. Langflow 自身の decrypt ヘルパーを呼ぶ。
  2. パッケージ全体に grep -rn "def decrypt" をかける。
  3. 自分が先に行った2回の環境変数の吐き出しにしか現れない候補の秘密（LANGFLOW_SECRET_KEY）を、7通りの鍵導出にかける。
  4. Langflow 自身の ensure_valid_key() にその実際の秘密を食わせる。

「最後の段階は variable テーブルの全行を、その所有者のユーザー名と結合して復号する。Langflow 自身の鍵導出をおとりの鍵で使っているので、これが動く手口である」（出典2。原文英語・訳は本記録）。

VulnCheck は、ここが実機との分かれ目だと書いている（出典2）——

「実際のインスタンスに対しては、ここで各種の提供者の鍵が出てくる。我々のカナリアに対しては、取れたのはおとりのデータだけだった」（出典2。訳は本記録）

そして段階3が、本記録が「自律的な動き」として読む根拠である（本記録の読み）〈重要〉—— 候補の秘密は、同じセッションの前半で自分が吐き出させた環境変数にしか現れない。 固定の攻撃キットなら、どの標的にも同じペイロードを送る。

AI エージェントが操作していたかは、証明されていない帰属

VulnCheck は断定を避けている（出典2）〈重要〉——

「ネットワークの通信だけから、AI エージェントがこのセッションを走らせたと証明することはできない。とはいえ、これは Microsoft が記述する内容と符合する」（出典2。原文英語・訳は本記録）

挙げられた根拠は5つである（出典2）。

  1. 段階が前の段階に依存している。 後の段階に出てくるパス・テーブル名・鍵導出の推測は、前の段階が返した内容から来ている。
  2. 機械の速さで再試行している。 復号の試行は初回からおよそ80秒で動く手口に到達し、失敗のたびに新しい変種が続いた—— Microsoft が報告した28〜80秒の ARM 再試行と符合する。
  3. ペイロードに説明的なコメントが付いている。 # try langflow decrypt on any encrypted-looking values、# leftover scripts of other actors: grep など。
  4. Python の HTTP クライアントのヘッダ順。 第1段と PHP への探索はpython-requests の順、第2〜11段は urllib の順である—— Microsoft は ARTEX の既定の道具に Python の HTTP クライアントを挙げている。
  5. AI の鍵を狙っている。 ペイロードに現れる鍵のパターンと端点はすべて LLM の提供者かクラウドの AI サービスを指している。

本記録は、この5点を「符合する観測」として記録し、「AI エージェントが操作していた」とは書かない（本記録の方針）〈未確定3〉。理由は2つある（本記録の評価）。①VulnCheck 自身が証明できないと明記している。 ②自動化の度合いは防御の手当てをほとんど変えない—— 速さが前提になることだけが実務上の差であり、「人か AI か」を決めなくても対策は同じである。

同じ週、別の攻撃者も同じ扉を叩いていた背景・過去事例

VulnCheck は、199.19.77.84 が唯一ではなかったと書いている（出典2）。

2026年11月2日、.84 がブラジルとスウェーデンのカナリアに PHP の探索を送る約5時間前に、179.43.191.82（Private Layer・スイス）がブラジルの Langflow カナリアに対して CVE-2025-3248 経由の対話的なセッションを走らせていた（出典2）。

その手順は .84 とよく似ている（出典2）—— ①Langflow の秘密（/app/data/.cache/langflow/secret_key・/proc/1/environ の読み取り、langflow.log から sk-・api_key・openai・anthropic・aiza・gsk_・hf_・vertex の探索）、②エージェントの記憶（.mem0 と .composio の一覧と読み取り）、③他の侵入者の残骸、④コンテナ（Docker と containerd のソケットの確認・コンテナネットワークのポート走査）、⑤Azure の識別情報（management.azure.com 向けのマネージド ID トークンの取得試行・インスタンスメタデータ端点への問い合わせ・環境変数の IDENTITY|MSI|AZURE の探索・168.63.129.16 の WireServer への到達確認）。

8時間後、同じ IP は HKUDS AutoAgent（CVE-2026-86124）に対し、AWS の IMDSv1/v2 のロール資格情報・user-data・OCI と GCP のメタデータを集めるスクリプトを送った（出典2）。

VulnCheck はこの IP を .84 と同一視していない（出典2）。だが、意味はそこではないとしている（出典2）——

「標的の収束こそが要点である。露出した AI ツールはクラウドの識別情報への正面玄関になり、複数の攻撃者が同じチェックリストでそこを通っている」（出典2。原文英語・訳は本記録）

なお Microsoft は11月6日に、カンボジアを拠点とする Storm-3358 がARTEX を使って金融機関を標的にしていると別途公表している（出典4）〈差異3〉—— 本記録は、ARTEX という道具の共通性を攻撃者の同一性と読み替えない（本記録の方針）。

CVE-2025-3248 の経過を並べると、次のようになる（本記録の整理）。

「AI の基盤は急いで配置され、しばしば露出し、周りのすべての鍵を抱えている。いま違うのは速さである。エージェントが最初の要求から動く復号手口まで30分ほどで進めるとき、週単位で測るパッチの窓は持ちこたえない」（出典2。原文英語・訳は本記録）

判断評価評価の根拠と留保
**Microsoft は、脅威アクター名を付けずに「threat actors」として公表した**（出典1）。機能した**本記録の評価。** **名前を付けなかったことは、読者の誤読を防いでいる。** **ARTEX は道具であり、複数の無関係な攻撃者が使っている**（出典1・4）—— **ここで名前を付けると「ARTEX を使う1つの集団」という像が立ち、 Storm-0940（中国国家に連なる）や Storm-3358（カンボジア拠点の金銭目的）と 混同される**（本記録の評価）。
**VulnCheck は、Microsoft の公表（11月5日）の3日後、 自社の観測（11月7日）の翌日に公表した**（出典2）。機能した**本記録の評価。** **①侵入口が1つ増えた。** **Microsoft の報告だけを読んだ防御側は、 「GitHub に秘密を置いていなければ関係ない」と判断しうる。** **VulnCheck の公表は、露出した Langflow も同じ攻撃者の入口であることを示した。** **②公表後も活動が続いていることが分かった。** **指標を公開しても止まらない相手である、という情報は防御の前提を変える。**
CISO・経営層への示唆
  • 委託先・MSP が自社テナントに持っている「アプリとしての入り口」を棚卸しし、 その数と権限を把握する
    **Todyl の観測では、約18組織の45のアプリ登録が狙われ、33件以上が認証を通り、 そこから27組織へ到達している**（出典5）。 **「1つの侵害された MSP のアプリは、その MSP が管理するすべての顧客を露出させる。 ある事例では、単一のマルチテナントアプリが約10秒の繰り返しで 15の顧客テナントを掃いた」**（出典5。訳は本記録）〈重要〉。 **自社が何も漏らしていなくても、委託先のアプリ資格情報が漏れれば中に入られる** （本記録の評価）—— **到達の手段はマルチテナントアプリ・委任管理（GDAP）・Partner Center のトークンである**（出典5）
    取るべき行動 自社テナントの**同意済みサードパーティアプリと委任管理の関係を一覧にし、 「誰が・どのアプリで・どの権限で入れるか」を台帳にする**。 **アプリ単位で「利用者の操作を伴わないサインイン（アプリのみの権限）」が 許されている範囲を見直す。** 委託契約に**①資格情報の保管場所と保管方法、 ②侵害時の通知の期限、③ローテーションの責任分担**を書く。 MSP に委託している場合は、**自社テナントに対する GDAP の関係を 必要最小の役割・期間に絞る**
  • セキュリティ製品の連携用アプリも「入り口」である——ベンダーが侵害されていなくても悪用される
    **「セキュリティ道具の連携用の資格情報——2つの MSP テナントにおける Todyl 自身の連携アプリを含む——が悪用されたものの中にあった。 いずれかのベンダーのプラットフォームが侵害された兆候は無い」** （出典5。原文英語・訳は本記録）〈重要〉。 **ベンダー側が無事でも、自社テナントに置いた連携用の資格情報が漏れれば その経路は使われる**（本記録の評価）—— **セキュリティ製品の連携アプリは、調査のために広い読み取り権限を持つことが多い。**
    取るべき行動 **セキュリティ製品・バックアップ・RMM・監視の連携アプリを「特権アプリ」として扱い、 一般の業務アプリと別の台帳で管理する。** 各連携アプリの**権限の一覧・資格情報の有効期限・ローテーションの実績**を記録し、 期限切れを待たずに定期で入れ替える。 連携用の資格情報を**managed identity（マネージド ID）や証明書に置き換えられるか**を ベンダーに確認する
  • 「ログが届いている範囲」が被害の範囲ではない——報告された数字はいずれも下限である
    **Todyl は「これらの数は、Todyl にログを送っている組織しか含まないため下限である」と 明示している**（出典5。訳は本記録）〈重要〉。 **さらに持ち出されたファイル（VPN プロファイル・MFA と RMM の API キー・ バックアップ保管先の資格情報・ネットワーク機器の設定）について 「その露出は Microsoft 365 のログからは見えない」としている**（出典5。訳は本記録）。 **観測の窓の外で何が起きたかは、報告書には書けない**（本記録の評価）
    取るべき行動 自社の監視が**どのログ源を見ていないか**を一覧にする （クラウド側のサービスプリンシパルサインイン、Key Vault の監査、 Partner Center の操作、VPN・MFA・RMM・バックアップ保管先の認証ログ）。 **侵害の通知を受けたときは、「ベンダーが見えた範囲」と 「自社が見える範囲」を重ねて、見えない区間を明示的に列挙する。** 見えない区間については、**資格情報の総入れ替えを前提に対応計画を作る**
  • **「AI 開発基盤」を、脆弱性管理の台帳に載っている資産として扱えているかを確かめる。 載っていなければ、KEV に載った穴でもパッチの対象にならない。**
    **本件で入口になった Langflow の CVE-2025-3248 は、 2025年5月5日に CISA の KEV に収載され、 是正期限は2025年5月26日だった**（出典3）。 **VulnCheck が悪用を観測したのは551日後の2026年11月7日である**（出典2・本記録の算出）。 **Langflow のような道具は、情報システム部門の調達を通らずに 開発者や事業部門が自分で立てることが多い**（本記録の評価）—— **台帳に無い資産にはパッチ適用の工程が回らない。**
    取るべき行動 **①直近90日間に社内で立てられた、インターネットに面したサービスの一覧を ネットワーク側（ファイアウォールの許可・DNS の登録・証明書の発行）から作り直す ——申請ベースの台帳と突き合わせ、差分を数える。** **②その中から AI 関連の基盤（LLM のワークフロー・エージェント・ ベクトルデータベース・モデルのゲートウェイ）を抜き出し、 各1台について「誰が持ち主か」「中に何の鍵が入っているか」を書き出させる。** **③差分の件数を次回の経営報告に数字で出す。**
  • **自組織が何も漏らしていなくても、使っている SaaS ベンダーのアプリ資格情報が 漏れれば自社テナントに入られる。委託先管理の軸に「ベンダーのアプリが 自社テナントに持つ権限」を加える。**
    **「一部の事例では、ベンダーが保有するマルチテナントアプリケーションの 侵害された資格情報が、下流のテナントへのアクセスに使われた」** （出典1。訳は本記録）〈重要〉。 **Microsoft が示した封じ込め手順の第1項（条件付きアクセスでの IP 遮断）は 「自テナント内の単一テナントアプリのみ」が対象であり、 この経路には効かない**（出典1・本記録の評価）。
    取るべき行動 **①自社の Entra ID テナントに同意済みのサードパーティアプリを一覧し、 各アプリが持つ API 権限（特に Mail.Read・Files.Read.All・ Directory.Read.All のような広い読み取り）を書き出す。** **②権限の広いアプリについて、ベンダーに 「アプリのシークレットをどう保管しているか」「侵害時に何時間で通報するか」を 文書で確認する。** **③不要なアプリの同意を取り消す—— 棚卸しの結果として取り消した件数を記録に残す。**
  • **指標（IP・文字列）の遮断を対策の中心に置かない。 公表の2日後に、同じインフラで同じ活動が続いていた。**
    **Microsoft の公表は2026年11月5日、 VulnCheck がカナリアで同じ IP の活動を記録したのは11月7日である**（出典1・2）〈重要〉。 **Microsoft 自身が「既定の道具の指紋を遮断するだけでは エージェントは止まらない——エージェントはそれを素早く変えられる」と書いている** （出典1。訳は本記録）。 **VulnCheck も文字列の指紋の確度を「中（retro-hunt 向け）」にとどめ、 「挙動で狩れ」としている**（出典2）。
    取るべき行動 **①自組織の検知規則のうち、IP・ドメイン・ハッシュに依存するものの割合を数える。** **②挙動に基づく規則を少なくとも3つ足す ——「1つのアドレスが3つ以上のサービスプリンシパルに成否混じりの認証をしている」 「1つのアプリが短時間に ARM・Key Vault・Storage・Graph のトークンを要求している」 （いずれも出典1）、 「大きな本文を伴う `POST /api/v1/validate/code` の連続」（出典2）。** **③指標の公開から自社での遮断までの所要時間を測り、 それが数日かかるなら指標依存の対策は前提として成立しないと経営に伝える。**
  • **おとり（カナリア・デコイ）を、検知の手段として予算に載せる。 本件で侵入口が1つ増えたのは、おとりがあったからである。**
    **Microsoft は「おとり・デコイ・タールピットを検討せよ。 これらは実資産に届く攻撃通信を減らし、確度の高いシグナルを生んだ」と書いている** （出典1。訳は本記録）。 **本件はその実例である**（本記録の読み）〈重要〉—— **VulnCheck のカナリアが36分のセッションを引き受けたことで、 Microsoft の報告に無かった Langflow 経由の侵入口が分かった**（出典2）。 **「我々のおとりに対する36分のセッションにこのエージェントを引き込んだ。 攻撃者の動き方を理解するのに役立つ類の欺瞞である。 走らせた全段階が我々にその手口の情報を与え、 そのどれも実際の顧客には触れていない」**（出典2。訳は本記録）。
    取るべき行動 **①自組織でもっとも狙われる種類の資産（本件なら AI 開発基盤）を1つ選び、 同じ構成のおとりを1台立てる——中には必ず偽の鍵だけを置く。** **②おとりへの到達を、通常の警報とは別の経路（即時通知）に接続する。** **③3か月後に、おとりが拾った事象の件数と、 そのうち実資産の検知に無かったものの件数を数える。**
セキュリティ技術者への示唆
  • 調査の開始日を他社の初見に合わせない——Microsoft は10月28日、Todyl は11月1日を初見としている
    **Todyl の初見は11月1日08時45分（UTC）だが、 Microsoft は同じ IP アドレスからのサービスプリンシパルサインインの成功を その4日前の10月28日から観測している**（出典1・5）〈重要〉。 **Todyl は「11月1日から調査範囲を取っていたなら、10月28日まで遡れ」と書いている** （出典5。訳は本記録）—— **報告書の「初見」は、その報告者の観測の窓の始まりでしかない**（本記録の評価）
    取るべき行動 **ハンティングの範囲は、公表された最も早い日付に合わせる** （本件なら2026年10月28日。データ保持の上限まで遡る）。 **サービスプリンシパルおよび非対話サインインのログを対象に、 `AADSTS7000215`（無効なシークレット）／`AADSTS7000222`（期限切れのシークレット）に 続く成功を探す**——**失敗に続く成功は緊急である**（出典1・5）。 **1つの送信元アドレスが24時間内に無関係な複数組織のサービスプリンシパルとして 認証していないかを横断で見る**（出典5）
  • 資格情報のローテーションだけでは止まらない——リフレッシュトークンの再生に移る
    **攻撃者は無効化・ローテーション済みのアプリに対しても約11秒周期で再試行を続け、 利用者のリフレッシュトークンの再生に移った**（出典5）〈重要〉。 **「資格情報のローテーションだけでは足りない」とされ、 11月3日に観測されたトークン再生は条件付きアクセスがすべて遮断している**（出典5。訳は本記録）。 **恒常化（新しい同意・資格情報・ロール・利用者の追加）は観測されていない**（出典5）—— **つまり止めるのは「次に入ってくる経路」側である**（本記録の読み）
    取るべき行動 **条件付きアクセスのポリシーが、スクリプトのクライアントとホスティング事業者からの サインインを対象にしているかを確認する** （準拠端末またはハイブリッド参加端末の要求、信頼できる場所への限定）。 **ワークロード ID（アプリ）を対象にしたポリシーを別に作る**—— **利用者を対象にしたポリシーではアプリのサインインは止まらない**（出典5）。 **悪用されたアプリは「完全に掃除する」**—— シークレット・証明書・連携資格情報を外し、そのアプリが読めた Key Vault の中身を すべて入れ替える（出典5）
  • 「ARM トークン → Key Vault トークン → 直後に未使用のアプリが認証」という並びを検知の形にする
    **「ほぼすべての資格情報について、まず Azure Resource Manager のトークンを要求し、 次に Key Vault のトークンを要求し、しばしば数秒内に Graph・Storage・ Cognitive Services のトークンが続く。数分内に、それまで使われたことの無いアプリが 認証を始める」**（出典5。原文英語・訳は本記録）〈重要〉。 **Todyl は「Key Vault の読み取りが新しい資材の供給源の1つとみられるが、 確認には Key Vault の監査ログが要る」としている**（出典5。訳は本記録）—— **つまり既定のままでは因果を確認できない**（本記録の評価）
    取るべき行動 **Key Vault の監査ログを有効にして自社の保存先へ転送する**（既定では不足する）。 **「同一アプリの ARM トークン取得 → Key Vault トークン取得」の並びを検知規則にし、 その後の数分で新規のアプリが認証したかを続けて見る。** **SharePoint のアプリのみの権限によるダウンロードが Microsoft 以外のアドレスから毎秒1件程度で続く挙動**、および **ワイルドカード1文字（`*`）の Graph 検索**を検知の対象に加える（出典5）
  • **AI 開発基盤に保管する資格情報を、その基盤の暗号化機能に預けない。 本件では Langflow 自身の鍵導出が復号に使われた。**
    **Langflow は保管された変数を Fernet で暗号化している**（出典2）。 **攻撃者は4手を試し、4手目で成功した**（出典2）〈重要〉—— **「Langflow 自身の `ensure_valid_key()` にその実際の秘密を食わせた。 Langflow 自身の鍵導出をおとりの鍵で使っているので、これが動く手口である」** （出典2。訳は本記録）。 **つまり、同じホスト上でコード実行を得た相手に対して、 アプリケーション層の暗号化は保護にならない**（本記録の評価）—— **鍵も同じホストの環境変数にあるためである。**
    取るべき行動 **①Langflow・n8n・Dify などの基盤に保管している資格情報を一覧し、 マネージド ID または外部の秘密管理（Key Vault 参照・環境ごとの注入）へ出す。** **②出せないものについては、その鍵が「ホスト侵害時に失われる」前提で 影響範囲を書き、利用量上限と呼び出し元制限を設定する。** **③`langflow.db` の `variable` テーブル相当の中身を実際に数え、 何本の鍵が1台に集まっているかを把握する。**
  • **外向きの通信を前提にした持ち出し検知を見直す。 本件の持ち出し経路は「要求への応答」であり、外向きの通信が1つも無い。**
    **「盗まれたデータは別の経路では出て行かない。 各段階は結果を `|RAISE|` の印を付けた例外に入れ、 脆弱な端点は例外のテキストを HTTP 応答に返す。 ペイロードはどれも攻撃者のインフラへ呼び返さず、 何もダウンロードせず、ファイルも書かない」**（出典2。原文英語・訳は本記録）〈重要〉。 **VulnCheck が「警報に値する」としたのは、 メタデータサービス `169.254.169.254` への問い合わせと Docker ソケットとの通信の2つだけである**（出典2）。
    取るべき行動 **①Web アプリケーションのログに、応答の大きさとエラー応答の本文の有無を記録させる ——「JSON の塊を運ぶエラー応答」が手がかりになる（出典2）。** **②例外の内容を利用者への応答に返す設定（デバッグ表示・詳細エラー）が 本番で有効になっていないかを全アプリで確認する。** **③アプリのコンテナから `169.254.169.254` への到達を遮断し、 遮断された試行をログに残す。**
  • **サービスプリンシパルの「失敗したサインイン」を監視対象に入れる。 成功の前に、資格情報の保有が分かる。**
    **「エラー AADSTS7000215（無効なシークレット）と AADSTS7000222（期限切れのシークレット）は、 誰かがそのアプリの資格情報を持っていることを示す。 失敗に続いて成功があれば緊急である」**（出典1。原文英語・訳は本記録）〈重要〉。 **本件では2026年10月28日からサインインが始まっており、 それ以前の失敗を見ていれば気づける余地があった**（出典1・本記録の読み）。
    取るべき行動 **①`EntraIdSpnSignInEvents` で AADSTS7000215／7000222 の発生を検索し、 過去90日分について該当アプリを洗い出す。** **②該当があれば、そのアプリのシークレットをローテーションし、 公開リポジトリへの流出を疑って検索する。** **③以後、この2つのエラーコードの発生を警報にする ——件数ではなく「同一アプリに対する失敗の後の成功」を条件にする。**
  • **コンテナからの出口（docker.sock・メタデータ端点）を、アプリ単位で閉じる。 コード実行を得た相手は、そこからクラウドの識別情報に手を伸ばす。**

自組織に当てはまるか
