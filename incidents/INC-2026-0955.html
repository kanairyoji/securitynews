INC-2026-0955Airbyte の RCE 脆弱性に悪用確認

**データ連携基盤 Airbyte** の **Connector Builder / Manifest Server** に、 **マニフェストが参照できる Python クラスを制限していなかったことに起因する 任意コード実行の脆弱性**が明らかになった（出典1・2）〈重要〉。 **Airbyte は2026年10月17日に GitHub Security Advisory「GHSA-g35w-6r6v-h4r7」を 重大度 Critical・CVSS 3.1 基本値 9.9 で公開**し、**2.2.0 より前のすべてのバージョンが 影響を受ける**とした（出典1）。 **JPCERT/CC は11月4日に JVN#12040144 を深刻度「緊急」で公表し、 「本脆弱性の悪用が確認されています」と明記した**（出典2）〈重要〉。 **CVE 番号は割り当てられていない**（出典1 が "No known CVE" と記載）〈未確定1〉。 **2.x では Workspace Reader / Organization Reader 以上の権限を持つ認証済み利用者が Manifest Server コンテナ内でコマンドを実行できる**が、 **旧 Helm Chart で導入した 1.x では Connector Builder サービスが認証設定を継承しないため、 ネットワーク到達性があれば認証なしに悪用できる**（出典1）〈重要〉。 **修正は 2.2.0（`airbyte/manifest-server` 7.23.7 を同梱）で、1.x に修正は提供されない** （出典1）〈重要〉。 **`AIRBYTE_ENABLE_UNSAFE_CODE` が無効でも成立する**点が advisory の題名に入っている（出典1）。

脆弱性続報が続いている日本に波及した海外事案設計・実装上の不備設定不備
初報: 2026年10月17日 最終更新: 2026年11月9日

データベースやクラウドサービス間のデータ連携を自動化するプラットフォーム Airbyte に、任意のコードを実行できる脆弱性が明らかになりました。すでに悪用が確認されています。

問題があるのは、外部サービスとのデータ接続用コネクタをノーコードで作るConnector Builder と、その背後でマニフェストを処理する Manifest Server です。接続設定（マニフェスト）に含まれる Python クラスの読み込み処理が、読み込めるクラスを制限していませんでした。細工した設定データを投入すると、Manifest Server コンテナ内で想定外のプログラムが呼び出される——つまり任意のコマンドが実行されます。advisory の題名にあるとおり、安全でないコードの実行を許可する設定（AIRBYTE_ENABLE_UNSAFE_CODE）を無効にしていても成立します。

深刻さは導入形態で変わります。Airbyte 2.x（2.2.0 より前）では、Workspace Reader または Organization Reader 以上の権限を持つ認証済みの利用者が悪用できます。閲覧権限で足りるという点が重要です。一方で、旧 Helm Chart でデプロイした Airbyte 1.x では、Connector Builder サービスが認証設定（global.auth.enabled）を継承しません。この場合、ネットワーク経由で到達できるクライアントなら認証なしに悪用できます。

Airbyte は2026年10月17日に GitHub Security Advisory GHSA-g35w-6r6v-h4r7 を公開し、重大度 Critical・CVSS 3.1 基本値 9.9 としました。修正は 2.2.0（airbyte/manifest-server 7.23.7 を同梱）で、1.x 系に修正は提供されません。回避策として、Connector Builder / Manifest Server へのネットワークアクセスをAirbyte サーバーのみに限定すること、Workspace Reader と Organization Reader の権限を信頼できる利用者に限ることが挙げられています。

JPCERT/CC は2026年11月4日、JVN#12040144 を深刻度「緊急」で公表し、「本脆弱性の悪用が確認されています」と明記しました。 JVN が示す影響範囲は「Airbyte 1.7.0 から 2.1.0 までのバージョン」で、GitHub advisory の「2.2.0 より前のすべて」とは幅が異なります。CVSS 値も JVN は v3.0 で 8.8、v4.0 で 8.7 と、GitHub の 9.9 とは一致しません。CVE 番号は割り当てられていません（advisory は "No known CVE" と記載）。

Airbyte はデータウェアハウス・SaaS・データベースへの接続情報を集約して保持する基盤です。コンテナ内でのコード実行が成立すれば、そこに置かれた認証情報が射程に入ります。評価・示唆は本記録の判断として分けて書きます。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

マニフェストが読み込める Python クラスを制限していなかったため、コンテナ内で任意のコマンドが実行できる概観出典 [1]

GitHub Security Advisory「GHSA-g35w-6r6v-h4r7」（2026年10月17日公開）の記載は次のとおりである（出典1）。

Summary——2.2.0 より前の Airbyte では、Connector Builder と Manifest Server が、マニフェストがカスタムコンポーネントとして参照できる Python クラスを制限していなかった（原文英語: "the Connector Builder and Manifest Server did not restrict which Python classes"）。その結果、コンテナ内で任意のコマンドが実行される可能性がある。AIRBYTE_ENABLE_UNSAFE_CODE が無効でも発生する——これが advisory の題名「Remote code execution via Connector Builder custom components when unsafe code is disabled」の意味である。

Impact——導入形態で前提条件が変わる。

系統 悪用の前提
Airbyte 2.x（2.2.0 より前） Workspace Reader または Organization Reader 以上の権限を持つ認証済み利用者が「Manifest Server コンテナ内でコマンドを実行できる」（原文英語: "could execute commands in the Manifest Server container"）
Airbyte 1.x（旧 Helm Chart） Connector Builder サービスが global.auth.enabled の設定を継承しないため、ネットワーク到達性がある任意のクライアントが認証なしに悪用できる

Patches——2.2.0 で修正（airbyte/manifest-server 7.23.7 を同梱）。Airbyte 1.x には修正を提供しない（原文英語: "Airbyte 1.x will not receive a fix"）。

Workarounds—— ①Connector Builder / Manifest Server へのネットワークアクセスを Airbyte サーバーのみに制限する、②Workspace Reader と Organization Reader の権限を信頼できる利用者に限る。

  • CISA KEV への収載は本記録の確認範囲では見つかっていない〈未確定5〉—— CVE 番号が無いため、CVE を鍵にする KEV には載りにくい構造である（本記録の評価）

したがって、「どれくらい急ぐべきか」を外部の観測から判断する材料が無い。本記録は、判断の根拠を次の2点に置くことを推奨する（本記録の判断）。①自組織の Connector Builder / Manifest Server がネットワークのどこから到達できるか、②旧 Helm Chart の 1.x を使っていないか。1.x で旧 Helm Chart なら、悪用の観測の有無に関わらず無認証 RCE である。

公表されていないことをもう1つ記録しておく。影響を受けうる公開インスタンスの数が、どの資料にも示されていない。 Airbyte は自社運用（self-hosted）とクラウドの両方で提供されており、自社運用の総数も、そのうちインターネットから到達できる数も分からない〈未確定4〉。

「閲覧権限だけで足りる」ことと「接続情報が集まっている基盤である」ことが重なる評価・解釈出典 [1] [2] [3]

以下は本記録の判断である（公表資料に基づく事実ではない）。

①2.x の前提条件「Workspace Reader / Organization Reader 以上」は、実務上かなり低い。 Reader は閲覧の権限であり、データ基盤チーム以外の利用者——アナリスト、監査担当、業務部門の閲覧者——にも配られやすい役割である。「認証済みユーザーが必要」と書かれていると内部犯行の文脈で読んでしまいがちだが、フィッシングで Reader 1人のアカウントを取れば RCE に到達するという読み方のほうが実態に近い。つまり 2.x でも「外部からの攻撃で成立する経路」がある。

②Airbyte は認証情報の集積点である。この基盤の役割は、データベース・SaaS・データウェアハウスへ接続してデータを動かすことである。したがってソース側とデスティネーション側の接続情報（DB の資格情報・API キー・OAuth のトークン）が構造的に集まっている。コンテナ内でのコード実行が成立すれば、環境変数・設定ファイル・シークレットのマウント先が射程に入る。被害は「Airbyte が乗っ取られた」で終わらず、Airbyte がつながっている先に及ぶ。この性質は、2026年に相次いだデータ連携・メール配信などの「基盤を1つ抜くと契約企業の全部に及ぶ」事案と同じ構造である（本記録の評価）。

③1.x に修正が出ないことの意味を、期限として扱うべきである。 advisory は "Airbyte 1.x will not receive a fix" と明記している。これは「パッチ適用」という選択肢が存在しないという宣言であり、1.x の利用組織に残る手段は 2.2.0 以降への移行か、ネットワーク到達性の遮断しかない。JVN の「最新バージョンへアップデートする」という対策は、1.x ユーザーにとってはメジャーバージョンアップの要求である。「脆弱性対応」ではなく「移行プロジェクト」として計画しなければ期限に間に合わない。

④CVE 番号が無い脆弱性は、既存の運用から漏れる。本件の識別子は GHSA-g35w-6r6v-h4r7 と JVN#12040144 だけである。CVE を鍵にして動く仕組み——脆弱性スキャナの照合、SBOM の突合、KEV の監視、社内の脆弱性管理台帳——はいずれも本件を拾えない可能性がある。 OSS のデータ基盤を自社運用している組織は、GHSA（GitHub Advisory Database）を CVE とは別の入力として監視する必要がある（本記録の提言）。

CISO・経営層への示唆
  • データ連携基盤は「認証情報の金庫」として扱い、業務システムと同じ監視水準に置く
    Airbyte の役割はデータベース・SaaS・データウェアハウスへ接続してデータを動かすことであり、 接続情報が構造的に集まっている。コンテナ内でのコード実行が成立すれば、 被害は Airbyte の内側で終わらず接続先に及ぶ（本記録の評価）
    取るべき行動 社内のデータ連携基盤（Airbyte・Fivetran・Airflow 等）を資産台帳で「重要システム」に格上げし、 保持している接続情報の一覧と、侵害時に失効・再発行すべき資格情報のリストを作る。 棚卸しは四半期ごとに更新する
  • CVE 番号が無い脆弱性を拾う経路を、CVE とは別に用意する
    本件の識別子は GHSA-g35w-6r6v-h4r7 と JVN#12040144 だけで、 advisory は "No known CVE" と記している。 CVE を鍵にするスキャナ・SBOM 突合・KEV 監視・脆弱性管理台帳は本件を拾えない
    取るべき行動 自社が使う OSS について、GitHub Advisory Database と JVN を CVE とは独立した入力として監視対象に加える。 脆弱性管理台帳の識別子欄を CVE 固定にせず、GHSA・JVN 番号で登録できるようにする
  • 「修正が出ないバージョン」を見つけたら、脆弱性対応ではなく移行計画として扱う
    advisory は Airbyte 1.x に修正を提供しないと明記している （原文英語: "Airbyte 1.x will not receive a fix"）。 パッチ適用という選択肢が存在せず、2.2.0 以降への移行かネットワーク遮断しか残らない
    取るべき行動 自社が使う OSS・製品について「現在の版に修正が出るか」を資産台帳の属性として持ち、 出ないものはメジャーバージョンアップの予算と期限を事業計画に載せる。 移行が間に合わない期間の暫定措置（ネットワーク遮断）を先に決めておく
  • 「閲覧権限が必要」という前提条件を、安全の根拠として読まない
    2.x の悪用には Workspace Reader / Organization Reader 以上の認証が必要だが、 Reader はアナリストや監査担当にも広く配られる役割であり、 アカウント1つを奪えば RCE に到達する（本記録の評価）
    取るべき行動 基盤系ツールの Reader 権限の付与状況を棚卸しし、 人数と部署を経営に報告できる形にする。Reader にも多要素認証を必須とし、 退職・異動時の権限回収を自動化する
  • ベンダーと国内 CSIRT の記載が食い違ったときは、範囲の広いほうを前提に動く
    GitHub advisory は「2.2.0 より前のすべて」、JVN は「1.7.0 から 2.1.0」としている。 CVSS も 9.9 と 8.8 で一致しない。JVN だけを読むと 1.7.0 より前の利用者が対象外と誤読しうる
    取るべき行動 脆弱性トリアージの手順に「一次資料（ベンダー advisory）の影響範囲を必ず確認する」を入れ、 国内公表のみを根拠に対象外と判定しない。 食い違いがあった場合は広いほうを採る規定にする
セキュリティ技術者への示唆
  • Connector Builder / Manifest Server のネットワーク到達性を、いま確認する
    advisory の回避策の第一がこれである。 旧 Helm Chart の 1.x では Connector Builder サービスが `global.auth.enabled` を 継承しないため、到達できれば認証なしに RCE が成立する
    取るべき行動 Airbyte の各コンポーネントについて、どのネットワークから到達できるかを実際に接続して確かめる。 Connector Builder / Manifest Server への到達元を Airbyte サーバーのみに制限し、 Kubernetes では NetworkPolicy で明示する

    取るべき行動 更新後に稼働中のコンテナイメージのタグを列挙し、 `airbyte/manifest-server` が 7.23.7 以降であることを確認する。 イメージのピン止めやキャッシュで古い版が残っていないかを点検する
  • Manifest Server コンテナを最小権限で動かし、プロセス生成を観測点にする
    脆弱性の影響は「コンテナ内での任意のコード実行」である。 実行そのものを前提にした封じ込めと検知が、パッチと並行して必要になる（本記録の判断）
    取るべき行動 Manifest Server / Connector Builder のコンテナを非 root・読み取り専用ルートファイルシステム・ 不要なケーパビリティ削除で動かす。コンテナ内での shell 起動と 予期しない外向き通信をランタイム監視で検知するルールを入れる
  • 侵害を想定して、Airbyte が保持する接続情報の失効・再発行を手順にしておく
    悪用が確認されている一方で、被害の内容は公表されていない。 自組織で悪用された場合に最初に失われるのは、 ソース・デスティネーションの接続情報である（本記録の評価）
    取るべき行動 Airbyte に登録されている全コネクションの資格情報を列挙し、 一括で失効・再発行する手順を文書化して年1回実行する。 接続情報を外部のシークレット管理に預け、コンテナ内に常駐させない構成へ移す

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Airbyte を自社運用（self-hosted）しており、Connector Builder または Manifest Server がアプリケーションネットワークから到達できる位置にあるadvisory の回避策の第一がネットワークアクセスの Airbyte サーバーへの限定である。 到達できること自体が前提条件になる
システム構成□ Airbyte 1.x を旧 Helm Chart でデプロイしているこの構成では Connector Builder サービスが `global.auth.enabled` を継承せず、 ネットワーク到達性のある任意のクライアントが認証なしに悪用できる。 さらに 1.x には修正が提供されない
認証・認可□ Airbyte の Workspace Reader / Organization Reader 権限を、 データ基盤チーム以外（アナリスト・監査・業務部門）にも配っている2.x ではこの閲覧権限以上の認証済み利用者が Manifest Server コンテナ内でコマンドを実行できる。 アカウント1つの奪取が RCE に直結する（本記録の評価）
データの保持□ データベース・SaaS・データウェアハウスへの接続情報を Airbyte 側に保持しており、 外部のシークレット管理に分離していないコンテナ内でのコード実行が成立すれば、環境変数・設定ファイル・ マウントされたシークレットが射程に入り、被害が接続先に及ぶ（本記録の評価）
運用・監視□ 脆弱性管理の台帳・スキャナ・SBOM 突合が CVE 番号を前提に組まれており、 GHSA や JVN 番号だけの脆弱性を登録・照合できない本件には CVE が割り当てられていない（advisory は "No known CVE" と記載）。 CVE を鍵にする仕組みは本件を拾えない
体制・契約□ 使用している OSS について「現在の版に修正が出るか」を把握しておらず、 メジャーバージョンアップの予算と期限が計画に入っていないAirbyte 1.x には修正が提供されない。 恒久対策は 2.2.0 以降への移行であり、脆弱性対応の工数では収まらない
