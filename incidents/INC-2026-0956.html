ドイツ・ノルトライン＝ヴェストファーレン州のホスティング事業者Mittwald CM Service が、顧客プロジェクト56件を侵害されたと公表しました。侵入口は、顧客が自分の AI アシスタントを管理基盤 mStudio に接続するために同社が提供していた MCP（Model Context Protocol）サーバです。

同社の時系列はこうです。攻撃者は10月21日夜に MCP サーバの欠陥を最初に試し、10月23日には一般の利用者として振る舞って（テストアカウントの作成、拡張機能の利用、単純なインジェクションの試行）プラットフォームを調べました。10月27日14時58分に新しいアカウントを登録し、その5分後の15時03分にMCP サーバの欠陥を狙って悪用しました。 同社が異常な挙動に気づいたのは11月4日午前で、悪用から検知までの滞留は約8日間です。

同社は 「10月27日以降のすべてのデータを侵害されたものとして扱う」 と表明しました。11月4日11時11分に攻撃者の最初のアカウントを停止、12時53分にステータスページを「調査中」に切り替え、11月5日に攻撃の痕跡があったプロジェクトを停止し、mStudio のログインと SSH アクセスを遮断、新規アカウント登録を一時停止しました。同じ日に外部のフォレンジック専門家を投入し、関係当局に通知しています。11月6日に56件の侵害プロジェクトと MCP サーバを分析し、繰り返しのスキャンでも追加の侵害は見つからなかったとして、11月7日に mStudio と SSH を再開しました。ただし侵害の疑いで停止した Web サイトは当面停止のままです。カスタマーセンターとそこで管理される Web サイトは影響を受けていないとしています。

公表されていないことが2つあります。ひとつは 欠陥の所在 です。同社の自前コードにあったのか、オープンソースの MCP ライブラリにあったのかは示されていません。もうひとつは AI 利用の根拠 です。同社の社長は「ログは、攻撃者が極めて速くシステムを進んだことを示している」「人間の攻撃者であれば相当な時間がかかる手順の間に、数秒しか経っていない場合もある」と述べていますが、それ以外の証拠は示されていません。報道は、AI ツールの検知と、人間より速く動ける従来型スクリプトの区別について同社に問い合わせたが回答が無かったと記しています。同社は「詳細な経緯を来週公表する」と予告しています。

Mittwald CM Service のブログ記事「Sicherheitsvorfall am MCP-Server」（2026年11月7日・社長 Robert Meyer 名義）の記載は次のとおりである（出典1）。

侵入口は MCP サーバである。 「MCP サーバを侵入口と特定し、停止しました」（原文ドイツ語: "Wir können den MCP-Server als Einfallstor identifizieren und schalten ihn ab."）。

この MCP サーバが何であったかは報道側が説明している（出典2）—— 「顧客が自分の AI アシスタントを mStudio（Web サイトとホスティングサービスを管理するプラットフォーム）に接続できるようにするために使われていた」（原文英語: "used to allow customers to connect their AI assistants to mStudio, a platform for managing websites and hosting services"）。

つまり顧客の代理として基盤を操作する権限を、外部の AI クライアントに渡すための口がそのまま攻撃経路になった（本記録の整理）。ホスティング基盤の MCP サーバは、定義上「顧客プロジェクトを操作できる」ことを目的に作られる。権限の境界が破れたときの到達範囲は、設計時点で決まっている。

欠陥の所在は公表されていない（出典2）—— 「その欠陥が同社の自前コードにあったのか、オープンソースの MCP ソフトウェアライブラリにあったのかは不明である」（原文英語: "It is unclear whether the flaw was in the company's own code or in the open-source MCP software libraries."）。脆弱性の種類・CVE 番号・技術的な詳細・攻撃経路はいずれも一次公表に無い〈未確定1〉。

10月21日の試行から11月4日の検知まで、ログには2週間ぶんの痕跡が残っていた発覚の端緒

一次公表は分単位の時系列を示している（出典1）。

報道も滞留期間を明示している（出典2）—— 「同社のシステム上で8日間、検知されずにいたのち、顧客プロジェクト56件を侵害した」（原文英語: "compromised 56 customer projects after going undetected on its systems for eight days"）。

最初の試行（10月21日夜）を起点にすると約14日である（本記録の算出）。新規アカウント登録から5分後に欠陥を悪用する——という連続は、事後には明瞭なパターンに見える。それが事前に拾えなかった理由は公表されていない。

「10月27日以降のすべてのデータを侵害扱いとする」という宣言が、調査の限界を示している被害規模・影響範囲

侵害の範囲について、一次公表は2つの記述を置いている（出典1）。

確定したもの——侵害された顧客プロジェクトは56件である。11月6日に同社はこの56件とMCP サーバを分析し、繰り返しのスキャンでも追加の侵害は見つからなかったとした。「現時点では、当社システム上での攻撃者の活動は確認できていません」（原文ドイツ語: "Wir können gegenwärtig keine Aktivitäten eines Angreifers auf unseren Systemen nachweisen."）。

影響を受けなかったもの—— 「カスタマーセンターとその中で管理されている Web サイトは、いかなる時点でもこのセキュリティインシデントの影響を受けていません」（原文ドイツ語: "Das Kundencenter und die darin verwalteten Websites waren zu keiner Zeit von dem Sicherheitsvorfall betroffen."）。

そして範囲を特定できていないもの—— 「10月27日以降のすべてのデータを、侵害されたものとして扱っています」（原文ドイツ語: "Wir behandeln alle Daten ab dem 27.10. als kompromittiert."）〈重要〉。

この一文は、対応方針としては正しく、同時に調査の限界を示している（本記録の評価）。「何が見られたか」をログから確定できないため、時点で切って全部を侵害扱いにした。56件という数は「痕跡が見つかったプロジェクト」であり、「データが持ち出されたと確認されたプロジェクト」ではない。侵害されたデータの種類・量・持ち出しの有無はいずれも公表されていない〈未確定2〉。

なお56は「件（プロジェクト）」であり、顧客数ではない（本記録の指摘）。1顧客が複数プロジェクトを持ちうるため、影響を受けた顧客の数は分からない。

AI 利用の根拠はログの速度だけで、従来型スクリプトとの区別は示されていないか帰属

本件が「AI を使った攻撃」として報じられた根拠は、同社社長の発言である（出典2）。

「ログは、彼が極めて速く我々のシステムを進んでいったことを示している」「人間の攻撃者であれば相当に長い時間がかかる手順の間に、数秒しか経っていない場合もある」（原文英語: logs "show that he worked his way through our system extremely quickly"・"in some cases, only seconds passed between steps that would take significantly longer for a human attacker"）。

報道はこれを明確に留保付きで扱っている（出典2）〈差異1〉—— 「Mittwald は AI の関与について他の証拠を示さなかった。同社は、AI ツールの検知と、支援を受けない人間の操作者より速く動けるようにする従来型のスクリプトとを、どう区別したのかを尋ねられたが、直ちには回答しなかった」（原文英語: "Mittwald provided no other evidence of AI involvement. The company did not immediately respond when asked to distinguish between the detection of AI tools and conventional scripts that also allow hackers to move faster than an unaided human operator."）。

本記録は「AI を使ったか」を本件の論点の中心に置かない（本記録の判断）〈重要〉。理由は2つある。第一に、示された根拠（手順間が数秒）は、自動化スクリプトでも成立する。速度は自動化の証拠にはなるが、どの自動化かを区別しない。第二に、防御側の打ち手が変わらない。侵入口は MCP サーバの欠陥であり、滞留は8日である。攻撃者が LLM を使っていたかどうかで、権限設計も検知設計も変わらない。

ただし「速度」自体は実務的な示唆を持つ（本記録の評価）。手順間が数秒という進行は、人手の運用監視では追随できない。滞留8日という結果は、速さの問題というより、速い進行に反応する仕組みが無かったことの問題である。

なお同社は 「まず PHP2Shell の脆弱性、そして今回の当社システムへの攻撃。AI による攻撃は今後さらに増えるだろう」 と述べ、「我々はこれについて透明でありたい。したがって、分析と復旧が完了次第、来週に詳細な経緯を公表する」 と予告している（出典2 の引用）。

検知から半日で告知し、2日後に管理系を遮断し、3日後に経緯を公表した組織の対応

対応の経過は次のとおりである（出典1）。

即日（11月4日）——午前に検知、11時11分に攻撃者の最初のアカウントを停止、12時53分に規模を把握してステータスページを「調査中」に設定。同日夜に mStudio がオンラインに復帰した（Web プロジェクトは終始利用可能）。

翌日（11月5日深夜以降）——攻撃の痕跡があったプロジェクトを停止。新規アカウント登録を一時停止。mStudio ログインと SSH アクセスを遮断。 MCP サーバを侵入口と特定して停止。外部 IT フォレンジック事業者が参加し、関係当局に通知。

11月6日——56件の侵害プロジェクトと MCP サーバを分析。追加の侵害は確認されず。

11月7日——mStudio ログインと SSH を再開。侵害の疑いで停止した Web サイトは当面停止のまま。同日ブログで経緯を公表。

本記録の評価として、検知後の順序は妥当である。アカウント停止（即時）→ 外部告知（半日未満）→ 侵入口の切断と管理系の遮断（翌日）→ フォレンジック投入と当局通知（翌日）→ 分析完了後に再開（3日後）。ただし「MCP サーバの停止が11月5日である」点は留保が要る（本記録の指摘）——検知は11月4日午前であり、侵入口を特定して閉じるまでに1日以上かかっている。その間の判断理由は公表されていない。

パスワードリセットや顧客への強制的な認証情報変更の要求は、一次公表に記載が無い〈未確定3〉。同社はパスキー（Passkey）の設定が可能になったことを案内しているが、これが本件の対応として行われたのかは示されていない。

MCP サーバは「権限を外部のクライアントに渡す口」であり、境界の設計が先に要る評価・解釈

以下は本記録の作成者の評価である（公表資料に基づく事実は前節までに分けた）。

第一に、本件の構造は「AI の攻撃」ではなく「権限委譲の口の脆弱性」である。 MCP サーバの役目は、外部のクライアント（AI アシスタント）に対して、顧客の代理で基盤を操作する能力を提供することである。機能として「できること」を広く取るほど、欠陥が破れたときの到達範囲が広がる。 56件という被害は、MCP サーバがそれだけのプロジェクトに到達できる設計だったことの帰結でもある（本記録の読み。同社は到達範囲の設計を説明していない）。

第二に、MCP サーバを「新しい API」として扱う必要がある。ホスティング事業者が顧客向けに提供する API には、通常、認証・認可・レート制限・監査ログ・異常検知が整備される。MCP サーバは機能としては API だが、「AI 連携機能」という枠で導入されると、これらの整備が後回しになりやすい（本記録の評価）。本件で侵入口になったのが MCP サーバであったこと、そして欠陥の所在が自前かライブラリかすら整理されていないことは、この経路の作り込みと棚卸しが API と同水準になっていなかった可能性を示す。

第三に、滞留8日の意味である。ログは十分に残っていた。アカウント登録から5分後の悪用、手順間が数秒という進行—— 事後には明瞭な異常が、事前には拾われなかった。速い自動化に対しては、人手のレビューを前提にした監視は原理的に間に合わない。検知のルール（短時間での大量操作・新規アカウントによる特権機能の即時利用）をMCP 経路にも適用しておく必要がある。

第四に、同社の情報公開の姿勢は評価できる（本記録の判断）。分単位の時系列、56件という具体的な数、「10月27日以降を侵害扱い」という保守的な方針、影響を受けなかった範囲の明示——いずれも実務の役に立つ記述である。一方で、AI 利用について証拠を示さずに「AI による攻撃」と性格づけた点は、読者の注意を本質から逸らす（本記録の指摘）。報道が留保を付けたのは適切な扱いである。

CISO・経営層への示唆
  • MCP サーバを「AI 連携機能」ではなく「顧客向け API」として扱い、同じ審査を通す
    本件の侵入口は、顧客が AI アシスタントを管理基盤に接続するための MCP サーバだった。 機能としては顧客向け API と同じく、外部から基盤の操作を受け付ける口である。 それが「AI 連携」という新しい枠で導入されると、 認証・認可・レート制限・監査ログ・ペネトレーションテストといった API に当然適用される審査が抜けやすい（本記録の評価）
    取るべき行動 自社が提供・導入している MCP サーバを資産台帳に API として登録し、 既存の API セキュリティ基準（認証方式・権限スコープ・レート制限・監査ログ・ リリース前のセキュリティレビュー）の適用状況を1件ずつ確認する。 未適用のものは提供停止か限定公開に戻す期限を決める
  • 「AI が使われたか」を事案の性格づけに使わず、権限と検知の設計で判断する
    本件で示された AI 利用の根拠は「手順の間隔が数秒」というログの速度のみで、 報道は従来型スクリプトとの区別について同社が回答しなかったと記している。 攻撃者が LLM を使っていたかどうかで、必要な打ち手（権限の最小化・滞留の短縮）は 変わらない。性格づけを誤ると、対策の優先順位が逸れる（本記録の判断）
    取るべき行動 インシデント報告の様式に「攻撃の自動化の程度」を速度・操作間隔の実測値で書く欄を設け、 「AI による攻撃」という定性的なラベルを根拠なしに使わない運用にする。 経営報告でも、滞留日数・到達範囲・検知の端緒を主要指標に据える
  • 影響範囲を確定できない前提で、「時点で切って侵害扱いにする」方針を事前に決めておく
    本件で同社は「10月27日以降のすべてのデータを侵害されたものとして扱う」と表明した。 ログから「何が見られたか」を確定できない状況で、顧客が対応を決められる形を 先に出した判断である（本記録の評価）。 この方針を事案発生後に議論すると、公表が遅れるか範囲が曖昧になる
    取るべき行動 インシデント対応計画に「侵害範囲を特定できない場合の既定方針」を書き込む—— 起点日時の決め方、侵害扱いとするデータの範囲、顧客への伝え方、 影響外と断定できる範囲の切り出し方。年1回の机上演習でこの判断を試す
  • 顧客に委譲する権限の到達範囲を、提供開始時点で数えておく
    被害が顧客プロジェクト56件に及んだのは、MCP サーバがそれだけの範囲に 到達できる設計だったことの帰結でもある（本記録の読み。到達範囲の設計は公表されていない）。 権限委譲の口を作るときに「破れたら何件に届くか」を数えていなければ、 侵害時の規模は設計者にも分からない
    取るべき行動 外部クライアントに権限を渡す機能（MCP サーバ・OAuth アプリ・API キー）ごとに 「最大到達テナント数」「操作できる種類」を一覧化し、 到達範囲が全テナントに及ぶものはテナント境界での分割を設計課題として起票する
セキュリティ技術者への示唆
  • 自組織の MCP サーバ実装について、自前コードと利用ライブラリの境界を把握しておく
    本件では、欠陥が同社の自前コードにあったのかオープンソースの MCP ライブラリに あったのかが公表されていない。 同種の実装を使う他組織は、この区別が示されない限り自分が影響を受けるかを判定できない 〈未確定1〉。自組織側でも同じ区別ができていなければ、 将来この種の公表が出たときに影響判定ができない（本記録の指摘）
    取るべき行動 MCP サーバの依存関係（SDK・トランスポート実装・認可ミドルウェア）を バージョン付きで SBOM に載せ、自前実装部分（ツール定義・権限チェック・入力検証）の コード範囲を文書化する。GitHub Advisory Database を CVE とは独立に監視対象に加える
  • MCP サーバのツールに渡す権限を、呼び出し元の権限で評価し直す
    MCP サーバはモデル／クライアントの代理で基盤を操作する。 サーバ側のプロセス権限で操作を実行すると、呼び出し元が本来持たない権限まで 届いてしまう。顧客向け MCP サーバでは、テナント境界を越える到達が そのまま多数テナントへの波及になる（本記録の評価）
    取るべき行動 MCP サーバの各ツールについて「どの主体の権限で実行されるか」を列挙し、 呼び出し元のトークンに紐づくテナント・スコープで認可を再評価する実装になっているかを コードレビューで確認する。サーバの共有資格情報で操作している箇所を洗い出して置き換える
  • 「新規アカウント登録から短時間での特権機能利用」を検知ルールにする
    本件では10月27日14時58分のアカウント登録から5分後の15時03分に MCP サーバの欠陥が悪用されている。 この連続は事後にはログから明瞭に読めるが、当時は検知されず8日間の滞留になった （本記録の指摘）
    取るべき行動 アカウント作成から一定時間内（例: 24時間）の MCP・API・管理機能の利用を 相関ルールで検知対象にし、レート制限と追加の監査ログ出力を適用する。 既存のログに対してこのルールを過去分で試し、誤検知率を測ってから適用する
  • 操作の時間間隔（秒単位の連続実行）を自動化検知の指標として監視に入れる
    同社が異常と認識したのは「人間なら相当な時間がかかる手順の間に数秒しか 経っていない」という進行の速さだった。 これは AI の証拠にはならないが、自動化の指標としては使える（本記録の評価）。 人手のレビューを前提にした監視は、この速度には原理的に間に合わない
    取るべき行動 セッション単位の操作間隔の中央値・最小値をメトリクスとして出し、 閾値を下回るセッションを自動で隔離・追加認証の対象にする。 正規の自動化（CI・顧客のスクリプト）を事前に許可リスト化してから有効化する
  • 侵入口を特定したら、検知と同日に閉じられる手順を用意する
    本件では検知が11月4日午前、MCP サーバの停止が11月5日深夜以降で、 侵入口を閉じるまでに1日以上かかっている（理由は公表されていない）。 攻撃者アカウントの停止は検知から数時間で行われており、 個別の停止と機能全体の停止の間に判断の時間差がある（本記録の指摘）
    取るべき行動 MCP サーバ・API・外部連携機能ごとに「機能単位で即時停止する手順」を Runbook に書き、停止の判断権者と顧客告知の文面を事前に用意する。 停止による業務影響を事前に評価しておき、判断の時間を短くする
