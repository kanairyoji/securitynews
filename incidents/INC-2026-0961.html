INC-2026-0961NEC WinShareに9.8が2件

日本電気のリモート操作製品「WebSAM WinShare」に3件の脆弱性が公表された （JVN#89009783・NV26-006・2026年11月9日）—— 深刻なのは認証を要さずネットワークから踏める2件で、 細工したパケットを送るだけでリモート操作対象のPC上で SYSTEM 権限の 任意コマンド実行（CVE-2026-113363・CWE-749）と任意コード実行 （CVE-2026-113364・CWE-122）に至る。いずれも CVSS 3.0 で 9.8。 残る1件はインストール時のフォルダ権限設定の不備で、 一般ユーザから SYSTEM へ昇格する（CVE-2026-113362・CVSS 3.0 で 7.8）。 対処は修正モジュールの適用

脆弱性初報のみ日本の組織が当事者設計・実装上の不備権限管理の不備
初報: 2026年11月9日（JVN#89009783 の公開および NV26-006 の掲載） 最終更新: 2026年11月10日（本記録の作成。JVN と日本電気の告知を取得して裏を取った時点）

2026年11月9日、日本電気株式会社が提供するリモート操作製品「WebSAM WinShare」の脆弱性3件が公表された（出典1・2）〈重要〉—— JVN#89009783 と、日本電気のセキュリティ情報 NV26-006 である。

深刻なのは、認証も利用者の操作も要さない2件である（出典1・2）〈重要〉。

  • CVE-2026-113363（CWE-749「危険なメソッドや機能の意図しない公開」）——細工されたパケットを送信されると、SYSTEM 権限で任意のコマンドを実行される。CVSS 4.0 で 8.5 ではなく 9.3、CVSS 3.0 で 9.8（出典1）
  • CVE-2026-113364（CWE-122「ヒープベースのバッファオーバーフロー」）——細工されたパケットを送信されると、SYSTEM 権限で任意のコードを実行される。CVSS 4.0 で 9.3、CVSS 3.0 で 9.8（出典1）

残る1件は端末にログインできる利用者を前提とする権限昇格である（出典1・2）。

  • CVE-2026-113362（CWE-276「プログラムフォルダにおけるインストール時の不適切なファイルアクセス権設定」）——一般ユーザ権限でログインしている攻撃者によって SYSTEM 権限を取得される。CVSS 4.0 で 8.5、CVSS 3.0 で 7.8（出典1）

影響を受けるのは「当該製品のリモート操作対象（リモートPC）」である（出典1）〈重要〉—— 操作する側ではなく、操作される側の端末が奪われる。

対処は修正モジュールの適用である（出典2）〈重要〉—— 日本電気は Ver7.6 用と Ver7.7 用の2つの修正モジュールを示し、「上記はいずれも 7.5.0 以下の下位バージョンにも適用が可能」としている。入手には同社サポートポータルへのログインが必要である（出典2）。一方 JVN の対策欄は「開発者が提供する情報をもとに、最新版へアップデートしてください」と書いており、修正済みバージョンの番号は示されていない（出典1）〈差異1〉。

本記録の確認時点で、悪用されたという記載は JVN にも日本電気の告知にも無い（出典1・2）〈未確定1〉。導入組織数・導入台数、待ち受けに使うポート番号、修正モジュールの公開日も公表されていない〈未確定2〉〈未確定4〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本記録は、公表された3件の脆弱性を段階に並べ替えたものである**（本記録の整理）〈重要〉—— **実際の攻撃の観測ではない**〈未確定1〉。 **2件（CVE-2026-113363・CVE-2026-113364）は、 ネットワークから細工されたパケットを送るだけで リモート操作対象の端末上に SYSTEM 権限の実行を得る**（出典1・2）。 **初期侵入と権限獲得が1手で同時に成立する形であり、 段階を分けて止める余地が小さい**（本記録の評価）〈重要〉。 **残る1件（CVE-2026-113362）は、 すでに端末にログインできる者が SYSTEM へ昇格する経路である**（出典1・2）。

  1. 1. 初期侵入確認済[1] [2]
    **リモート操作対象（リモートPC）に対し、細工されたパケットを送信する** （出典1・2）〈重要〉—— **CVSS ベクターが AV:N/AC:L/PR:N/UI:N であることから、 ネットワークから到達できれば、認証も利用者の操作も要らない**（出典1）。 **どの口へ送るのかは公表されていない**〈未確定3〉。
    根拠: JVN の想定される影響（出典1）——「細工されたパケットを送信されると」／CVSS ベクター AV:N/PR:N/UI:N（出典1）。
  2. 2. 実行確認済[1] [2]
    **送られたパケットの処理の不備により、SYSTEM 権限で任意のコマンドまたは 任意のコードが実行される**（出典1・2）〈重要〉—— **CVE-2026-113363 は通信パケットの処理不備による任意コマンド実行、 CVE-2026-113364 はデータ受信処理のバッファオーバーフローによる任意コード実行である** （出典2）。 **いずれも CVSS 3.0 で 9.8。**
    根拠: JVN の想定される影響（出典1）／NV26-006 の概要（出典2）。
  3. 3. 権限昇格確認済[1] [2]
    **別経路として、端末にログインできる一般利用者が プログラムフォルダの緩い権限を使って SYSTEM 権限を取得する**（出典1・2）〈重要〉—— **CVE-2026-113362。インストール時に設定されるフォルダのアクセス権が 適切でないことによる（CWE-276）。 CVSS 3.0 で 7.8（AV:L/PR:L）。** **ネットワークからは踏めない。**
    根拠: JVN の想定される影響（出典1）——「一般ユーザ権限でログインしている攻撃者によって SYSTEM 権限を取得される」／NV26-006 の概要（出典2）。
  4. 4. 影響（暗号化・破壊・改ざん）確認済[1] [2]
    **リモート操作の対象となっていた端末が SYSTEM 権限で奪われる**（出典1・2）〈重要〉—— **本記録の評価では、ここから先が本件の重さである。 リモート操作製品は保守・ヘルプデスク・装置管理のために 多数の端末へ横並びに入る。 1台ぶんの到達点ではなく、導入台数ぶんの到達点になる。** **横展開・持ち出し・暗号化のいずれにつながるかは、攻撃者の目的による。**
    根拠: JVN の対象が「当該製品のリモート操作対象（リモートPC）」であること（出典1）。横展開の観測は公表されていない。
参照・持ち出された情報

    深刻な2件は、認証も利用者の操作も要らずパケット1発で SYSTEM に届く原因・手口

    CVE-2026-113363 と CVE-2026-113364 のベクターは、どちらもAV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H である（出典1）〈重要〉—— ネットワークから到達でき、攻撃条件が低く、権限も利用者の操作も要らない。CVSS 3.0 で 9.8、CVSS 4.0 で 9.3。

    中身は別である（出典1・2）。

    • CVE-2026-113363 は「危険なメソッドや機能の意図しない公開」（CWE-749）。日本電気の表現では「通信パケットの処理不備による任意コマンド実行」。つまり、外から呼ばれるべきでない機能が、パケットを通じて呼べる状態になっていた（出典1・2）
    • CVE-2026-113364 は「ヒープベースのバッファオーバーフロー」（CWE-122）。日本電気の表現では「データ受信処理におけるバッファオーバーフローによる任意コード実行」。受け取ったデータの長さの扱いの問題である（出典1・2）

    本記録の評価として、この2件は段階を分けて止める余地が小さい（本記録の評価）〈重要〉—— 初期侵入と権限獲得が1手で同時に成立している。「侵入されても権限昇格で止める」「横展開で気づく」という多層の考え方のうち、最初の2層が無い。 残るのは、到達させないことと、実行後に気づくことだけである。

    奪われるのは「操作する側」ではなく「操作される側」の端末である被害規模・影響範囲

    JVN の想定される影響は、「当該製品のリモート操作対象（リモートPC）が次のような影響を受ける可能性があります」と書き出されている（出典1）〈重要〉。

    これは本件の広さを決める一文である（本記録の評価）〈重要〉—— リモート操作の製品は、保守・ヘルプデスク・工場の装置管理のために、操作される側の端末へ横並びに入れられる。操作卓は1台でも、操作対象は数十台から数千台になる。待ち受けの口を開けたまま常駐するのが前提の製品である。

    したがって本件は、1つの製品の脆弱性ではなく、その製品が入っている端末の台数ぶんの到達点として読むべきである（本記録の評価）。

    導入組織数・導入台数は公表されていない（本記録の確認）〈未確定4〉—— 影響の広さを外から測る材料は無い。

    3件目の CVE-2026-113362 は性質が違う（出典1）〈重要〉—— AV:L/PR:L で、端末にログインできる一般利用者が前提である。ネットワークからは踏めない。効きが大きいのは、多人数が入る共用端末や、一般利用者の権限で使われている端末である（本記録の評価）。

    対処は修正モジュールの適用で、修正済みバージョンの番号は示されていない対策・注意喚起

    日本電気の NV26-006 は、対処方法として修正モジュール2件を示している（出典2）〈重要〉。

    • WinShare Ver7.6 用の修正モジュール
    • WinShare Ver7.7 用の修正モジュール
    • 「※NECサポートポータルへのログインが必要となります。」
    • 「上記はいずれも 7.5.0 以下の下位バージョンにも適用が可能です。」

    一方、JVN の対策欄は「開発者が提供する情報をもとに、最新版へアップデートしてください」である（出典1）〈差異1〉—— 最新版の番号は書かれていない。

    本記録の評価として、この差が運用に効く（本記録の評価）〈重要〉—— バージョン番号で判定できないため、資産管理台帳に並んだ版数を見ても「対処済みか」が分からない。修正モジュールを当てた記録を、端末ごとに別で持つ必要がある。 修正モジュールの公開日も記載が無いため、「公表の何日前から入手できたのか」も分からない〈未確定2〉。

    さらに、入手にサポートポータルのログインが必要である（出典2）〈重要〉—— 運用を委託している場合、委託先が自力で入手できる契約・アカウントを持っているかを確かめておく必要がある（本記録の評価）。

    踏まれる口が公表されていないため、到達を絞る緩和策を自社で設計しなければならない評価・解釈

    JVN と NV26-006 のどちらも、「細工されたパケットを送信されると」という書き方にとどまり、待ち受けのポート番号・プロトコルを書いていない（出典1・2。本記録の確認）〈未確定3〉〈重要〉。

    公表を控えるのは悪用を助けないための判断とも読めるが、理由は説明されていない（本記録の確認）。

    その結果、利用者側の緩和策は次の順になる（本記録の評価）〈重要〉。

    1. 修正モジュールを当てる。これが唯一の確実な対処である（出典2）
    2. 当て終わるまでの間、到達範囲を絞る。ただし絞る対象は自社で実測して特定する必要がある（本記録の評価）
    3. 使っていない端末から製品を外す。台数を減らすのが効く（本記録の評価）

    ここで注意が要るのは、修正モジュールの配布そのものがリモート操作の経路を使う場合である（本記録の評価）〈重要〉—— 直す手段と、危険な経路が同じものになる。台数が多い環境では、適用が終わるまでの期間が長くなり、その間ずっと認証なしで踏める状態が残る。適用の順番は、外部に面している端末・多人数が入る端末から決めるべきである。

    報告は国内の枠組みを通っており、同業他社の研究者が他社製品の穴を届けている背景・過去事例

    本件の公表は、情報セキュリティ早期警戒パートナーシップに基づき、報告者が IPA へ届け、JPCERT/CC が開発者との調整を行った結果である（出典1）。

    CISO・経営層への示唆
    • **リモート操作・遠隔保守の製品を、「入っている台数」で資産管理の対象にする。**
      **本件で影響を受けるのは「リモート操作対象（リモートPC）」である**（出典1）〈重要〉—— **操作卓は1台でも、操作される端末は数十台から数千台になる。 製品単位で1行の台帳では、影響の広さが見えない**（本記録の評価）。
      取るべき行動 **遠隔保守に使っている製品ごとに、導入されている端末の台数と設置場所を 台帳で持つ。棚卸しの単位を「製品」ではなく「製品が入っている端末」にする。 委託先が入れた分も同じ台帳に載せる。**
    • **修正の適用経路が、危険な経路そのものである場合の手順を決めておく。**
      **修正モジュールを多数の端末へ配るのに、 同じリモート操作の仕組みを使うことがある**（本記録の評価）〈重要〉—— **適用が終わるまで、認証なしで踏める状態が残る。 台数が多いほどその期間は長い。**
      取るべき行動 **適用の優先順位を事前に決めておく （外部に面している端末・多人数が入る共用端末・ 業務が止められない端末の順など）。 適用が終わるまでの間に到達範囲を絞る暫定措置を、 同じ手順書の中に併記する。**
    • **修正手段がバージョン番号で表されない場合に備え、適用記録を別で持つ。**
      **本件の対処は修正モジュールの適用であり、 修正済みバージョンの番号は示されていない**（出典1・2）〈差異1〉〈重要〉—— **資産管理台帳の版数だけでは、対処済みかを判定できない**（本記録の評価）。
      取るべき行動 **修正モジュールの適用を、端末ごとに適用日と識別子つきで記録する仕組みを持つ。 版数の棚卸しとは別の列にする。 四半期ごとに、未適用の端末を一覧で出せる状態にしておく。**
    • **委託先が修正手段を自力で入手できるかを、契約の段階で確かめる。**
      **修正モジュールの入手には開発元のサポートポータルへのログインが必要である** （出典2）〈重要〉—— **運用を委託している場合、委託先がアカウントを持たなければ適用が止まる** （本記録の評価）。
      取るべき行動 **遠隔保守製品の運用委託契約に、脆弱性公表時の修正手段の入手責任と 入手手段（誰のアカウントで取るか）を明記する。 既存の契約については、委託先に入手可否を照会して記録する。**

    • **同一製品が入った端末群を1つの区画として扱い、端末間の直接通信を止める。**
      **同じ製品が多数の端末に入っているため、 1つのパケットで成立する攻撃は横並びに効く**（本記録の評価）〈重要〉—— **1台を踏まれたあと、同じ手で隣の端末へ届くのを止める必要がある。**
      取るべき行動 **端末間の直接通信を既定で止める設定にし、 保守の通信は管理系からの一方向だけに限る。 止めた通信の記録を集約し、端末間の接続試行を検知材料にする。**

      取るべき行動 **CVE ごとに対象バージョンの条件を分けて台帳に書き、 除外（7.3.3）と上限の違いを残す。 影響判定を CVE 単位で行い、製品単位でまとめない。**
