INC-2026-0962OpenAMにCVSS10.0の認証回避

ID管理・シングルサインオン基盤「OpenAM」に、認証を要さずに 他人のセッショントークンを読み出せる脆弱性が公表された （CVE-2026-123551・CVSS 4.0 と CVSS 3.1 のいずれも最高値の 10.0）—— セッションの開始・終了を通知する通信路に、 旧 Liberty ID-FF の端点を経由した内部転送で認証チェックを回さずに接続でき、 管理者を含む利用者のセッションを乗っ取れる。 修正版 OpenAM 16.1.4 は2026年10月22日に公開済みで、 同じ版で18件の勧告（うち最高深刻度が3件）が修正された

脆弱性初報のみ日本に波及した海外事案設計・実装上の不備権限管理の不備
初報: 2026年10月22日（OpenAM 16.1.4 と18件の勧告の公開。CVE-2026-123551 の公開は2026年11月8日） 最終更新: 2026年11月10日（本記録の作成。勧告・リリース・CVE の記録を取得して裏を取った時点）

ID管理・シングルサインオン基盤「OpenAM」に、認証を要さずに他人のセッショントークンを読み出せる脆弱性が公表された（出典1・3）〈重要〉。

CVE-2026-123551。CVSS 4.0 の基本値も CVSS 3.1 の基本値も、いずれも最高値の 10.0 である（出典3）〈重要〉—— 採番したのは VulnCheck で、公開は2026年11月8日。CVSS 4.0 のベクターは AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H、CVSS 3.1 は AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H である（出典3）。

手口は2つの不備の重ね合わせである（出典1）〈重要〉。

  • OpenAM はセッションの事象をエージェント向けの通知として配信する。この通知が有効（既定）のとき、セッションの作成・ログアウト・タイムアウト・属性変更で完全なセッション識別子が流れる。セッション識別子は、それだけで認証を通す持参型の資格情報である（出典1）
  • その通知の通信路の認証チェックが、旧 Liberty ID-FF の端点に対する検証されていない内部転送で回避できる。接続した側は内部向けを含む任意の購読先を指定できる（出典1）

CVE の記述はこうである——「OpenAM 14.0.0 以降 16.1.4 より前には情報漏えいの脆弱性があり、認証されていない攻撃者が通知の通信路から有効なセッショントークンを読み取れる。攻撃者はエージェント限定のチェックを旧 Liberty ID-FF の端点に対する検証されていない内部転送で回避し、iPlanetDirectoryPro トークンを集めて利用者および管理者のセッションを乗っ取れる」（出典3。原文英語）〈重要〉。

影響は「あらゆる利用者（管理者を含む）のセッション乗っ取り」と「サーバ上でのコマンド実行への発展の可能性」とされている（出典1）〈重要〉—— 開発元は技術的な詳細と実証コードを、運用者が更新できるようになるまで公開しないとしている（出典1）。

修正版 OpenAM 16.1.4 は2026年10月22日に公開済みである（出典1・2）〈重要〉—— 同じ版で18件の勧告が修正され、GitHub 上の深刻度では最高位が3件ある（本件のほか、SAML v2.0 のサービスプロバイダが署名のないアサーションを受け入れる問題、自己登録が許可属性の一覧を強制せず匿名の利用者が管理者を作れる問題）（出典2・4）。これに加えて、依存部品の更新で36件の CVE が解消されている（出典2）。

公表から CVE 番号の付与までに17日あった（本記録の算出）〈重要〉—— その間、勧告は GitHub の識別子だけで流通しており、CVE 番号を鍵にした資産管理の仕組みには載らなかった。 本記録の確認時点でも、GitHub 上の各勧告は「既知の CVE は無い」と表示したままである（出典1・4・5）〈差異1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本記録は、公表された勧告と CVE の記述を段階に並べ替えたものである**（本記録の整理）〈重要〉—— **実際の攻撃の観測ではない**〈未確定1〉。 **技術的詳細と実証コードは開発元が意図的に非開示にしているため、 段階の粒度も勧告の記述に限られる**（出典1）〈未確定3〉。 **公表されている筋道は、 ①認証を要さず通知の通信路へ接続する、 ②内部向けを含む購読先を指定する、 ③流れてくるセッション識別子を集める、 ④それを持参型の資格情報として使い、管理者を含む誰かになる、である**（出典1・3）。

  1. 1. 初期侵入確認済[1] [3]
    **認証を要さずに、セッション事象の通知の通信路へ接続する**（出典1・3）〈重要〉—— **本来はエージェントだけが接続できるはずの検査が、 旧 Liberty ID-FF の端点に対する検証されていない内部転送によって回避される。 CVSS のベクターは AV:N/AC:L/PR:N/UI:N で、 ネットワークから到達できれば権限も利用者の操作も要らない**（出典1・3）。
    根拠: 開発元の勧告（出典1）／CVE の記述（出典3）——「エージェント限定のチェックを旧 Liberty ID-FF の端点に対する検証されていない内部転送で回避する」（原文英語）。
  2. 2. 内部探索確認済[1]
    **接続した側が、内部向けのものを含む任意の購読先を指定する**（出典1）〈重要〉—— **本来は購読できる範囲が限られているべきところで、 範囲の制限が効いていない。**
    根拠: 開発元の勧告（出典1）——「接続した側は、内部向けのものを含め任意の購読先を指定できる」（原文英語）。
  3. 3. 認証情報アクセス確認済[1] [3]
    **セッションの作成・ログアウト・タイムアウト・属性変更の各事象とともに、 完全なセッション識別子が流れてくるのを集める**（出典1・3）〈重要〉—— **勧告は「セッション識別子は持参型の資格情報である」と明記している。 CVE の記述では、攻撃者が iPlanetDirectoryPro トークンを集めるとされている**（出典1・3）。 **エージェント向け通知が有効であることが前提で、これが既定である**（出典1）。
    根拠: 開発元の勧告（出典1）——「エージェント向け通知が有効（既定）のとき、OpenAM はセッションの作成・ログアウト・タイムアウト・属性変更の各事象で完全なセッション識別子を配信する」（原文英語）。
  4. 4. 横展開確認済[1] [3]
    **集めたセッション識別子を提示して、 その識別子の持ち主としてふるまう**（出典1・3）〈重要〉—— **対象は管理者を含むあらゆる利用者である。 シングルサインオンの基盤であるため、 影響はその基盤で認証しているすべてのアプリに及ぶ。** **勧告は加えて「サーバ上でのコマンド実行への発展の可能性」を挙げているが、 その経路は非開示である**（出典1）〈未確定6〉。
    根拠: 開発元の勧告（出典1）——「影響には、管理者を含むあらゆる利用者のセッション乗っ取りと、サーバ上でのコマンド実行への発展の可能性が含まれる」（原文英語）。
参照・持ち出された情報

    セッション識別子が「通知」として流れていたことが、本件の核心である原因・手口

    勧告は、2つの弱点が重なって成立すると書いている（出典1）〈重要〉。

    1つ目は配信の設計である（出典1）。OpenAM はセッションの事象をポリシーエージェント向けに配信する。エージェント向け通知が有効（これが既定）のとき、セッションの作成・ログアウト・タイムアウト・属性変更の各事象で、完全なセッション識別子が流れる。 勧告はここに一文を添えている——「セッション識別子は持参型の資格情報である」（出典1。原文英語）〈重要〉。

    2つ目は到達の設計である（出典1）。通知の通信路の認証チェックは、旧 Liberty ID-FF の端点に対する検証されていない内部転送によって回避できる。そして接続した側は、内部向けのものを含め任意の購読先を指定できる。

    本記録の評価として、この組み合わせの性質が重要である（本記録の評価）〈重要〉—— 攻撃者は何かを送り込むわけではない。正規に配信されているものを、受け取る資格がないのに受け取るだけである。そのため「不審な入力」「異常な操作」として現れる余地が小さい。異常として見分けられるのは、接続と購読の指定という最初の一手だけになる。

    加えて、同じ勧告は旧 Liberty ID-FF の端点について、検証されていない宛先へ利用者を転送することがあり、URL の書き換えが有効な構成ではその宛先に利用者のセッショントークンが付加されうるとしている（出典1）〈重要〉—— 同じ資格情報が、別の経路でも外に出る。

    CVSS は新旧どちらの版でも 10.0 で、影響が基盤の外へ出ることが理由である被害規模・影響範囲

    CVE-2026-123551 のスコアは、CVSS 4.0 で 10.0、CVSS 3.1 でも 10.0 である（出典1・3）〈重要〉—— 採番したのは VulnCheck、公開は2026年11月8日である（出典3）。

    **勧告は検知の方法を示していない**（本記録の確認）〈重要〉—— **本記録の評価としては、 通知の経路への接続元が「エージェントとして登録された発信元の一覧」と 一致するかを突き合わせることが、唯一の現実的な手掛かりになる。 回避に使われる旧世代の端点へのアクセスそのものも、 使っていない構成であれば異常として見分けられる。**
    侵入を防げた通知の経路への接続を、エージェントとして登録した発信元の一覧に限り、一覧外からの接続を落として記録する
    侵入を防げた旧世代の連携の端点を遮断し、遮断した要求を記録して探索の兆候として扱う
    内部探索公表されていない
    **勧告に記載が無い**（本記録の確認）—— **本記録の評価としては、 内部向けの購読先が外部からの接続に対して指定されたことは、 通信の内容を記録していれば残る類の事象である。 ただし通知の経路の記録が既定で取られているかは公表されていない。**
    検知できた通知の経路で指定された購読先を記録し、内部向けの購読先が外部由来の接続から指定された場合に警報にする
    認証情報アクセス現実的な検知機会なし
    **本記録の評価として、この段階に現実的な検知の機会は無い**（本記録の評価）〈重要〉—— **正規の通知の配信そのものを読んでいるだけであり、 攻撃者側は何も送らず受け取るだけになる。 異常として現れるのは1つ前の段階（接続と購読の指定）だけである。**
    侵入を防げたセッション識別子を通知の本文に含めない構成を選ぶ（エージェント向け通知の無効化を含む）
    影響を限定できたセッション識別子の提示元を、発行時の接続元や端末の特性と突き合わせて検証する構成にする
    横展開公表されていない
    **勧告に記載が無い**（本記録の確認）〈重要〉—— **本記録の評価としては、 同一のセッション識別子が複数の接続元から提示されたこと、 管理者のセッションが通常と異なる発信元から使われたことが 残り得る手掛かりである。 ただし、乗っ取られた側の正規の操作と見分けがつきにくい。**
    検知できた管理者のセッションについて、発信元と操作内容の逸脱を警報にし、重要操作に再認証を要求する
    影響を限定できた同一のセッション識別子が異なる接続元から提示された場合にセッションを失効させる

    CISO・経営層への示唆
    • **認証基盤の脆弱性は、業務系の脆弱性と同じ尺度で優先順位を決めない。**
      **本件の影響は「その基盤でシングルサインオンしているすべてのアプリ」に及ぶ** （出典1・4）〈重要〉—— **CVSS で 10.0 になるのは、影響が脆弱な部品の外へ出るためである**（出典3）。 **業務系1つの 9.8 と認証基盤の 10.0 は、同じ尺度上の隣の数字ではない**（本記録の評価）。
      取るべき行動 **資産の台帳に「この資産が落ちたとき同時に落ちる業務系の数」の列を持つ。 認証・認可・鍵管理・端末管理の基盤については、 その数を使って脆弱性対応の優先順位を上げる規則を文書化する。**
    • **CVE 番号の到着を待つ脆弱性管理は、修正版より遅れると前提する。**
      **本件では修正版の公開から CVE 番号の公開まで17日あった**（本記録の算出）〈重要〉—— **その間、勧告は GitHub の識別子だけで流通しており、 CVE 番号を鍵にした台帳・スキャナ・情報配信には載らなかった**（本記録の評価）。 **本記録の確認時点でも、勧告側は「既知の CVE は無い」と表示したままである** （出典1・4・5）〈差異1〉。
      取るべき行動 **自社が使っているオープンソース基盤の一覧を作り、 開発元のリリースと勧告の配信を直接受け取る経路を設定する。 脆弱性管理の入口を CVE 番号だけにしない。 四半期ごとに、台帳の各基盤について「監視経路が生きているか」を確認する。**
    • **止めにくい基盤について、計画的な停止の枠を先に確保しておく。**
      **シングルサインオンの基盤の更新は、 その基盤で認証しているすべての業務系の停止を伴う**（本記録の評価）〈重要〉—— **調整に要する期間が、そのまま危険な期間になる。 修正版は2026年10月22日に出ていた**（出典2）。
      取るべき行動 **認証基盤の緊急更新のための停止枠を、年間の計画に定期で確保する （使わなければ返す形でよい）。 連携している業務系の一覧と、各系の停止可否・連絡先を台帳で持ち、 緊急時に調整の起点にする。**
    • **既定値のまま運用されている前提を、導入から年数が経った基盤こそ点検する。**
      **本件では、導入時から存在する利用者の初期パスワードが すべての環境で同一かつ公開されており、 アカウントのロックアウトも既定で無効だった**（出典5）〈重要〉—— **これは攻撃ではなく、既定値の設計の問題である**（本記録の評価）。
      取るべき行動 **長く使っている基盤について、導入時から存在する利用者・サービス用の定義の 棚卸しを行い、使っていないものを削除する。 既定のパスワード・既定で無効になっている保護機能を一覧化し、 点検の結果を記録に残す。**
    セキュリティ技術者への示唆
    • **更新前の暫定措置として、旧世代の連携の端点を先に遮断する。**
      **認証チェックの回避は、 旧 Liberty ID-FF の端点に対する検証されていない内部転送で成立する**（出典1）〈重要〉—— **使っていない構成では業務への影響が無く、 回避の経路そのものを閉じられる**（本記録の評価）。
      取るべき行動 **旧世代の連携の端点への要求が実際に来ているかを記録で確かめ、 来ていなければ経路の手前で遮断する。 遮断した要求を記録し、探索の兆候として監視に回す。**
    • **通知の経路への接続を、登録済みの発信元の一覧に限る。**
      **攻撃者は何も送り込まず、正規に配信されるものを受け取るだけである** （出典1）〈重要〉—— **そのため異常として現れるのは、接続と購読の指定という最初の一手だけになる** （本記録の評価）。
      取るべき行動 **通知の経路への接続元を、エージェントとして登録した発信元の一覧に限り、 一覧外からの接続を落として記録する。 指定された購読先も記録し、内部向けの購読先が 外部由来の接続から指定された場合に警報にする。**
    • **セッション識別子を、持参型の資格情報として扱い直す。**
      **勧告は「セッション識別子は持参型の資格情報である」と明記している**（出典1）〈重要〉—— **本件では、それが通知の本文として配信されていた。 資格情報が通信の内容に載る設計は、 その通信路の認証が破れた瞬間に全部が出る**（本記録の評価）。
      取るべき行動 **自社の構成で、セッション識別子や同等の資格情報が 通知・ログ・連携の本文に含まれていないかを洗い出す。 含まれている場合は、識別子そのものではなく参照用の値を渡す形に変える。**
    • **同一のセッション識別子が別の接続元から提示されたときに失効させる。**
      **本件の到達点は、集めた識別子を提示して他人になることである**（出典1・3）〈重要〉—— **乗っ取られた側の正規の操作と見分けがつきにくいため、 識別子の提示元の変化が数少ない手掛かりになる**（本記録の評価）。
      取るべき行動 **セッション識別子に発行時の接続元や端末の特性を結びつけ、 提示元が変わった場合に失効させる設定を検討する。 管理者のセッションについては、重要操作の前に再認証を要求する。**
    • **深刻度が最高位の3件を、別々の暫定措置で塞ぐ必要があると理解する。**
      **3件はいずれも「認証を通らずに他人になれる」が、経路が違う** （出典1・4）〈重要〉—— **通知の通信路、SAML のアサーション検証、自己登録の属性制限の3つである。 1つを潰す暫定措置では足りない**（本記録の評価）。
      取るべき行動 **更新までの暫定措置を経路ごとに用意する。 SAML については、署名されたアサーションを要求する設定が 自社のメタデータで有効になっているかを確認する。 自己登録については、機能を使っていなければ無効にする。**
