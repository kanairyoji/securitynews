INC-2026-0975SHOGUN BURGER アプリ基盤に不正アクセス

和牛バーガー専門店「SHOGUN BURGER」を展開する株式会社ガネーシャが2026年10月30日、同店の公式アプリで利用しているシステムへの不正アクセスと一部顧客の個人情報の漏えいを公表した——侵害を受けたのは**同アプリの基盤である株式会社DIRIGIO のモバイルオーダーサービス「PICKS」**で、DIRIGIO の公表によれば**第三者が同社の API を経由してシステムに侵入し顧客情報を外部に持ち出した**。**2026年10月27日12時30分頃に不正アクセスの可能性を確認し、同日15時に PICKS の全サービスを停止**、**対象は注文9,992件・顧客8,312人（重複を除く／会員登録をしていない注文者を含む）**。漏えい項目は氏名・メールアドレスで、一部の利用者では電話番号・生年月日・性別・会員ID・住所・注文内容・注文メモを含む。**クレジットカード番号は保持しておらず漏えいなし**、ログインパスワードの漏えいと二次被害は未確認。DIRIGIO は脆弱性を修正し全顧客をログアウトさせたうえ**10月29日10時から PICKS を順次再開した一方、ガネーシャは SHOGUN BURGER 公式アプリのモバイルオーダーを停止したまま再開を未定とした**

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている日本の組織が当事者設計・実装上の不備
初報: 2026年10月30日 17時10分（日本時間） 最終更新: 2026年11月10日

ハンバーガー店のアプリで起きた事案だが、侵害されたのはハンバーガー店のシステムではない。

株式会社ガネーシャ（富山市）は2026年10月30日17時10分、同社が展開する和牛バーガー専門店「SHOGUN BURGER」の公式アプリで利用しているシステムに第三者による不正アクセスがあり、一部顧客の個人情報が外部に漏えいしたと公表した。公表文は漏えいした可能性のある項目（氏名・メールアドレス・電話番号・生年月日・性別・注文内容）を挙げ、システム運営会社である株式会社DIRIGIO が原因調査とセキュリティ診断を進めていると記している。

同じ日の午前11時過ぎ、その DIRIGIO が事案の中身を公表していた。侵害されたのは飲食店向けモバイルオーダープラットフォーム「PICKS」の顧客情報を管理するシステムで、第三者が DIRIGIO の API を経由して侵入し顧客情報を外部に持ち出していた。対象は注文9,992件・顧客8,312人。SHOGUN BURGER 公式アプリは、この PICKS の上に自社ブランド名義で載っている導入店舗の1つである。

本記録が読者に渡したい論点は2つある。

1つは時間の速さだ。10月27日12時30分頃に不正アクセスの可能性を確認し、同日15時に全サービスを停止、10月29日10時から順次再開、10月30日に公表。確認から停止まで約2時間30分、確認から公表まで3日である。

もう1つは基盤と導入店舗で判断が分かれたことだ。DIRIGIO は安全性を確認したとして10月29日に PICKS を再開したが、ガネーシャは翌30日の公表文で「現在、SHOGUN BURGER公式アプリによるモバイルオーダーサービスを一時停止しております」「サービスの再開につきましては、これらの調査・診断結果を踏まえ、安全性を確認したうえで判断いたします」と書いている。 基盤が再開した後も、導入店舗の側は自ブランドのサービスを止め続ける選択をした。共通基盤に乗る事業者が、基盤提供者の「安全確認済み」をそのまま自社の再開判断に使わなかった例である（本記録の整理）。

これは批判ではない。共通基盤に乗る以上、技術的な点検は基盤側しかできないのが構造である。問題は、その構造を前提にしたときに導入店が平時に何を握っておくべきかである（本記録の問い）。

  • 自由記述欄（注文メモ）に何が入っているかを棚卸しする——項目名からは機微さが読めない
    漏えい項目の最後に「**注文メモ**」がある（一部利用者）。 項目名は無害に見えるが、モバイルオーダーの備考欄にはアレルギー、 受け渡し場所の指示、同席者への配慮、勤務先への配達指定などが入りうる。 **自由記述欄は「どの種類の個人情報が入っているか」を事業者側も 把握していないことがある**（本記録の指摘）
    取るべき行動 **自社の自由記述欄を列挙し、実データを標本抽出して何が書かれているかを見る。** 要配慮個人情報が入りうる欄は、①選択肢に置き換える、 ②保存期間を短くする、③漏えい時の項目一覧に必ず載せる、のいずれかを決める。 **侵害時の項目列挙で自由記述欄を落とさないこと**
  • 「脆弱性の修正」だけでは他社の点検に使えない——書ける範囲で種別を書く
    DIRIGIO の公表は「API を経由して」「脆弱性の修正」までで、 **種別（認可の不備・認証の回避・パラメータ操作・レート制限の不在）を 区別していない。** 再発防止策も「システムの脆弱性対策と不正アクセスの 監視体制の強化」までである。**修正済みで再開もしている段階であり、 種別を書けない理由としては弱い**（本記録の評価）
    取るべき行動 **自社が公表する側になったときに書ける粒度を事前に決めておく。** 「認可の検証漏れ」「レート制限の不在」程度の種別は、 エンドポイント名やパラメータを出さなくても書ける。 **同種の構成を持つ他社が自社の点検項目を導けるかを基準にする**
  • 全顧客のログアウトを実施したら、同時に「パスワードを尋ねない」を明示する
    本件は全顧客をログアウトさせ、再開後に再ログインを求めた。 **再ログインを求める状況は、パスワード入力を促す偽メール・偽SMS が 成立しやすい文脈をそのまま作る**（本記録の評価）。 DIRIGIO は「当社がメールや電話でお客様のパスワードをお尋ねすることは ございません」の一文でこれに対処している
    取るべき行動 **強制ログアウト・パスワードリセットを行う手順書に、 「同時に出す注意喚起の文面」を組み込む。** 文面には①自社が求めないこと、②正規の通知の送信元、 ③アプリ内から操作する経路（メールのリンクを踏ませない）を入れる
