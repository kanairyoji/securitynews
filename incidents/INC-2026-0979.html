INC-2026-0979N-able N-central に33件の脆弱性

RMM製品「N-able N-central」に33件の重大な脆弱性と4本の攻撃連鎖（Able2Shell）が非協調で公開され、N-able は翌日に全世界のホスト型 N-central を停止しオンプレミス顧客にもサーバー停止を求めた——N-able は公開の2日後に7件の CVE を明示したホットフィックス（N-central 2026.4 HF2）を出したが、33件との対応関係は示していない。公開の当日夜から watchTowr・Defused Cyber・Previdian のハニーポットで悪用試行が観測され、Beazley Security は未認証の SOAP 要求という具体的な試行の形と2件の送信元IPを公表した。ホスト型環境は更新を終えて復旧したと同社が報道に述べた一方、研究者 Sean Bales は「自分は N-able に一つも報告していない。『無視された』という主張は古い README に由来するもので、すでに書き換えた」と認めた——第1回の続報まで本記録が「一方当事者の主張」として扱っていた非協調公開の理由は、研究者本人の訂正によって形が変わった。そして11月12日、同研究者が HF2 に対して成立するとする新たな2本（4EverAble2Shell・Agent2Shell）の実証コードを公開し、その数時間後に悪用が始まった——Huntback は12時50分 UTC 時点で21台の本番 N-central サーバーが XMRig で採掘していることを確認し、うち19台は11月10日の最新ホットフィックス適用済みだった

N-able（MSP・社内IT 向けの遠隔監視管理＝RMM 製品「N-central」の提供元）は2026年11月9日、ホスト型 N-central 環境を全世界で停止し、オンプレミスで N-central サーバーを運用する顧客に対しても当面サーバーを停止するよう求めました。

きっかけは前日の2026年11月8日深夜（米国時間・日曜）、独立研究者が33件の重大な脆弱性とその実証コードを GitHub（Oracle-Security/CVEs の「0-Days/N-Central N-Able」配下。公開名「Able2Shell」）へ事前通知なしで公開したことです。Huntress の整理によれば、公開された内容は4本の攻撃連鎖にまとまり、うち3本がリモートコード実行、1本が root への権限昇格に至ります。検証対象は N-central Appliance 2026.4.0.31（製品版前のビルド）で、研究者は「ほとんど、あるいはすべてが以前のバージョンにも当てはまる」としています。

N-able は BleepingComputer への声明で「独立研究者による N-central の重大な脆弱性の非責任ある伝達に対応している」「予防措置としてホスト型環境を停止し、オンプレミス顧客には一時的なサーバー停止の指針を示した」と述べ、2026年11月9日 15:15 UTC 時点で実際の悪用は確認していないとしています。その後の状況更新でも「悪用や不正なデータアクセスの証拠は無い」とし、修正プログラム（ホットフィックス）は開発・検証中、復旧時期は示さず4時間ごとの更新を予告しました。N-central classic が止まっている間もN-able Login 経由の Ecoverse サービスは稼働を続けているとしています。

本記録が注目するのは2点です。第一に、被害が確認されないまま「全世界の管理基盤を止める」判断が取られたこと。RMM は管理対象の端末すべてにコードを流せる位置にあるため、未修正の未認証 RCE が公開された状態では、稼働を続ける選択肢が実質的に無くなります。第二に、公開が非協調だった理由として研究者が挙げたのは、同社の脆弱性受付の運用だったことです。33件に CVE は割り当てられておらず、どれが有効かも N-able は確認を示していません。一次資料は N-able のステータスダッシュボード（イベント 202561）ですが、本記録の作成者は同ページを機械的に取得できず（JavaScript 描画）、同社の文言は報道が引用した声明で確認しています。

【第3回続報・2026年11月12日】ここまで「悪用の試行」にとどまっていた状況が、実際の侵害に変わりました。同研究者は11月12日、新たな2本の攻撃連鎖「4EverAble2Shell」と「Agent2Shell」の実証コードを公開しました。検証対象は N-central Appliance 2026.4.1.26 HF2 ——N-able が11月10日に出した修正そのものです（出典12）。4EverAble2Shell は未認証の攻撃者が root としてコマンドを実行できるとされ、同梱の Apache Axis コンポーネントの欠陥と N-central 側の権限昇格の弱点を組み合わせます。成立には Legacy API の有効化が前提です（出典12・13）。

公開の数時間後に悪用が始まりました。 Previdian は公開ページで、脆弱性の公開を11月12日 06時12分 UTC、GitHub の実証コードの作成を 07時13分、自社センサーでの試行の初観測を 08時24分、IoC の記録を 09時38分、自社 KEV への追加を 09時45分 と記しています（出典13）。Huntback は 09時16分 UTC に完全な連鎖の実行試行を初観測したとされ、12時50分 UTC 時点で採掘を続けるサーバーを 21台確認しました——うち19台は11月10日の最新ホットフィックス（2026.4.1.26）適用済みでした（出典12）〈重要〉。投入されたのは XMRig（Monero の採掘）で、検知されにくいよう CPU コアの約半分に抑えて動かしていたとされます。

N-able は11月12日の advisory で、追加の保護として「一部の N-central の機能と連携の制限」を実施したとしています（出典12 が引用）。予防措置として Intune 連携を無効化し、オンプレミス顧客にはLegacy API のアクセスが無効であること（既定で無効）の確認を求めています。同社は新たな欠陥による侵害の兆候は見ていないとしており、研究者側が報告する本番サーバーでの侵害とは食い違っています〈齟齬〉。本記録は N-able の advisory 本文を今回も取得できていません ——参照先（uptime.n-able.com のイベント 202609）は JavaScript 描画で、status.n-able.com の Security Notices にも11月12日付の掲示は見当たりませんでした（本記録の確認）。

ここからは本記録の判断である。

多くの組織の脆弱性対応は、CVE 番号を起点に組み立てられている。脆弱性情報の取り込み、資産との突き合わせ、優先度付け、適用期限の管理——どれも「番号」を鍵にして回る。本件にはその鍵が無い。あるのは「製品名」「製品版前のビルド番号」「研究者の見立て」だけである。

この形は今後増えると本記録は見る。理由は2つある。ひとつは、発見が AI 支援で加速していること。本件の研究者は発見が AI 支援だったと認めており、1人が1製品から33件を取り出した。番号の割り当てと提供元の検証は、この速度に追いつかない。もうひとつは、非協調公開の動機が構造的であること。報告が滞留し、報奨も払われず、応答も無い——という当事者の主張が事実であれば、同じ選択をする研究者は他にも出る。

実務では、次の3点が分かれ目になる。①資産台帳が「製品とバージョン」で引けるか。CVE が無くても該当性を判断できる。②提供元の停止要請に即応できるか。本件は公開から停止要請まで1日である。管理基盤を落とす判断を、夜間・休日に誰が下せるかが決まっていなければ間に合わない。③管理基盤が止まった時の代替手順があるか。RMM が無い状態で監視とパッチ適用をどう続けるかは、止まってから考えることではない。

さらに本件は、監査ログの改ざんが脆弱性一覧に含まれている点を軽く見るべきではない。「悪用の証拠が無い」という表明の意味は、改ざん可能なログの上では弱まる。提供元の表明を受け取る側は、自分の環境のログで独立に確認する必要がある。Huntress が11月8日以降のログイン・認証記録の点検を勧めているのは、そのためである。

RMM の事故で手順が長くなるのは、管理基盤が持っている資格情報の種類が多いためである。人のアカウントだけを変えても、Agent 登録トークンやエコシステムのキーが残っていれば、配下の端末に戻る道が残る。しかも監査ログの改ざんが公開された脆弱性一覧に含まれているので、「ログに何も無い」は弱い根拠になる。だからこそ順序が効く——保全してから、更新する。逆の順序でやると、侵害の有無を後から判断する材料が消える。

最後の1つが本件固有の難所である（本記録の評価）〈重要〉。公開された攻撃連鎖には監査ログの改ざんが含まれる〔既記〕—— つまり N-central 自身のログを見て「何も無い」ことは、無事の根拠にならない。

実務上必要になるのは、N-central の内部ログとは独立した記録である（本記録の判断）—— ①境界機器・プロキシのアクセスログ（/dms2/services2/ServerMMS2 への未認証要求が来ていたか）、②認証基盤側の記録（管理者アカウントの作成・パスワードリセットがN-central の外からも見えるか）、③SIEM へ転送済みのログ（転送先では改ざんできない）。

この3つを持っていない組織は、「探査されたかどうか」を事後に判定できない（本記録の評価）。そして本件では、判定できないまま復旧させるという選択を取らざるを得ない組織が出る。

Beazley Security が示した復旧の手順も、この構造を前提にしている（出典9）—— 本番・テスト・ステージング・DR を含むすべてのオンプレミスN-central サーバーを洗い出して停止を確認し、停止できないものはインターネットからの露出を除去して信頼できる管理ネットワークからのみ到達できるよう制限し、「リスクがあるもの」として扱う。 兆候が見つかった場合は、そのサーバーが管理する顧客ネットワークまで調査範囲を広げる。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
悪用が確認されていない段階で、ホスト型 N-central を全地域で停止し、 オンプレミス顧客にもサーバー停止を求めた機能した本記録の作成者の評価である。RMM は管理対象すべてにコードを流せる位置にあり、 公開された内容に監査ログの改ざんが含まれるため「監視しながら運用を続ける」判断の 前提が弱い。被害が確認されていない段階で止めた決定は、材料に照らして妥当と考える

  • 「提供元が全世界で基盤を止める」事態を事業継続計画の想定に入れる
    本件は被害が確認されないまま、公開の翌日にホスト型環境が全地域で停止し、 オンプレミス顧客にも停止が求められた。復旧時期は示されていない

  • 休日・夜間に「基盤を落とす」判断ができる権限者を決めておく
    公開は日曜深夜（米国時間）、停止要請は翌日である。判断の猶予は実質1日だった
    取るべき行動 管理基盤の緊急停止について、判断権者・代理者・連絡経路を名前で決めた一枚紙を用意する。 「誰が決めるか」が空いていると、技術的に正しい対応が時間切れになる
  • 脆弱性管理の前提を「CVE 番号がある」から外す
    今回の33件に CVE 番号は無く、N-able もどれが有効かを示していない。 資産との突き合わせは製品名とバージョンだけで行うことになる
    取るべき行動 資産台帳を「製品名・バージョン・公開面の有無・管理対象の範囲」で引ける状態にする。 番号が無い脆弱性情報を受け取ったときの判断手順（誰が該当性を見て、誰が止めるか）を 脆弱性管理規程に足す

    **本件では、非協調公開の理由として研究者が挙げた説明 （別製品で報告した脆弱性が放置された、連絡に応答が無かった）の前提を、 研究者本人が2日後に取り下げた**（出典11・T18）〈重要〉—— **「N-able が自分を無視したという主張は、古くなった README に由来するもので、 それ以降書き換えた」と述べ、N-able の説明が正確であることを認めた。** **公開直後の経緯の説明は、事実ではなく当事者の立場である**（本記録の評価）。 **一方、事前通知が無かったこと・修正が2日で出たこと・ 公開当日の夜から試行が観測されたことは、説明が変わっても動かない**（出典9・10・11）。
    取るべき行動 **①脆弱性の報告が外部で公開されたとき、 経営への第一報では「誰が悪いか」を書かない。** **書くのは「自社に影響があるか」「何を止めるか」「いつまでに戻すか」に限る。** **②ベンダーと研究者の言い分は、どちらも一方当事者の主張として記録し、 数日後に見直す前提で扱う。** **③自社が報告を受ける側である場合、 報告の受付記録（誰が・いつ・どの経路で）を監査可能な形で残す**—— **「報告を受けていない」を証明できるのは記録だけである。**
  • 自社の脆弱性受付の運用を、攻撃面として点検する
    研究者は「先行報告が5〜6か月放置され、追加連絡にも応答が無かった」として 事前通知なしの公開を選んだと述べている。N-able はこの主張に答えていない
    取るべき行動 外部からの脆弱性報告の受付窓口・一次応答の期限・滞留の可視化・報奨の支払実績を 棚卸しする。応答しない運用は、非協調公開という形で製品と顧客に跳ね返りうる （本記録の評価）
セキュリティ技術者への示唆
  • 管理基盤の監査ログを、管理基盤の外へ即時転送する

    最も重大とされる連鎖は、未認証の状態からパスワード再設定と 既定管理者アカウントの作成に到達する。いずれも監査ログに残る種類の操作である
    取るべき行動 管理基盤の管理者アカウント一覧を台帳と定期照合し、新規作成・権限付与・ パスワード再設定を検知ルールにする。2026年11月8日以降の記録については さかのぼって点検する

    取るべき行動 **①管理基盤の監査ログを、基盤の外（SIEM・ログ集約）へ即時転送する** 〔既記の項目と対になる〕。 **②境界機器・プロキシのアクセスログで `/dms2/services2/ServerMMS2` のような管理用端点への 未認証要求を遡って確認できるようにする（2026年11月8日以降）。** **③管理者アカウントの作成・有効化（"Default Administrator" を含む）と パスワード再設定を、管理基盤の外の認証記録でも見えるようにする。** **④「ログの欠落そのもの」を検知条件に入れる**—— **一定時間ログが来ないことを警報にする。**
  • **【第2回続報】停止の棚卸しに、テスト・ステージング・DR を必ず含める**

    取るべき行動 **①管理基盤の台数を、構成管理台帳ではなく ライセンス・証明書・DNS・外部からの走査の4つで突き合わせて数える。** **②停止できない台は、インターネットからの露出を除去し、 信頼できる管理ネットワークからのみ到達できるよう制限したうえで 「リスクがあるもの」として扱う**（出典9）。 **③検証環境が本番の管理対象に繋がっていないことを、 配下側のエージェント登録先の一覧で確認する。**
  • 復旧は「修正適用」で終わらせず、ビルド番号と資格情報まで確認する
    N-able は再起動を伴わない適用でバージョン番号を上げないことがあり、 番号だけでは適用済みかを判断できない場合がある。既定管理者アカウントの作成も 連鎖に含まれている

観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ RMM・特権管理・監視のいずれかを、インターネットに面した管理コンソールで運用している起点は未認証の XXE で、到達できることが成立条件になっている
