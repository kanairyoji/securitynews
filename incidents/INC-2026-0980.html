INC-2026-0980Qubole 経由で顧客AWSへ横断侵入

データレイク基盤 Qubole の AWS アカウントに属する IAM 認証情報が悪用され、顧客が残していた信頼ポリシー経由で2026年10月14〜26日に顧客の AWS 環境へ横断的に侵入——Lambda・Secrets Manager・SSM から秘密情報を抜き、TruffleHog で有効性を確かめ、S3 からバケットごと持ち出した。Qubole の利用をやめた後も信頼を残していた組織ほど被害が深く、Qubole と親会社 Idera の公表は確認できていない

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年11月9日 最終更新: 2026年11月10日

Qubole（Idera 傘下のデータレイク基盤。顧客の AWS 環境で計算資源を動かしストレージへ到達するために、クロスアカウントの IAM ロールを使う）のAWS アカウントに属する IAM 認証情報が悪用され、2026年10月14日から26日まで、複数の顧客の AWS 環境が横断的に侵入されました。Wiz と Sentra が2026年11月9日にそれぞれ分析を公開しています。

攻撃者は Qubole の AWS アカウント 805246085872 の IAM 利用者としてsts:AssumeRole を呼び、顧客側が作成した連携用ロールを引き受けました。観測された引受要求はすべて External ID を伴い、すべて成功しています。環境に入った後は、計算・ストレージ・データベース・鍵と ID の棚卸しを行い、Lambda の環境変数・Secrets Manager・SSM パラメータストアから秘密情報を集め、TruffleHog で AWS キーの有効性を確かめ、見つけた資格情報でMicrosoft Entra ID のサービスプリンシパルとしてのサインインやOkta のクライアント資格情報による OAuth トークンの取得まで試しています。S3 からはバケットを丸ごと持ち出した例があり、書き込み操作は1件もありませんでした。

発見の端緒は Sentra でした。同社が複数の顧客環境で異常を認めて Wiz に連絡し、Wiz の対応チームが Google の Mandiant とともに調査しています。規模について Wiz は件数を明かさず「広範で機会便乗型の供給網キャンペーン」と表現し、Sentra は「十数組織以上」（導入部では「数十の Qubole 顧客」）と記しています。帰属は示されておらず、Wiz は国家背景の優先順位とは合わない機会便乗型と評価しています。

本記録が注目するのは、被害の深さを決めたのが「解約後に残した信頼」だった点です。Wiz によれば、攻撃者が引き受けたロールの多くはほかに使われていないロールでした。Qubole を使うのをやめても信頼ポリシーを消していなかったため、「もう使っていない連携」が広い読み取り権限を持ったまま生きていたのです。Wiz は「本件で観測したすべての引受は、送信元IPの条件だけで防げた」と明記しています。Qubole と親会社 Idera の公表は、本記録の作成者が確認した範囲では存在しません。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

侵入は提供元の AWS アカウントに属する IAM 認証情報の悪用から始まり、 顧客側が作った連携ロールの引受という正規の経路を通った。 脆弱性の悪用は無く、すべての段階が正規の API 呼び出しで構成されている。

  1. 1. 初期侵入disclosed[1] [2]
    提供元の IAM 利用者として `sts:AssumeRole` を呼び、顧客の連携ロールの一時認証情報を得た。 観測されたすべての要求に External ID が含まれ、すべて成功した。 セッション名には `quiam-enum`・`quiam-scope-full` が使われた
    根拠: CloudTrail の記録（Wiz CIRT の分析）
  2. 2. 内部探索disclosed[1]
    引き受けたロールの権限で、ストレージとデータ（バケット・オブジェクト・ データベースとテーブル・クラスタ）、計算（インスタンス・イメージ・ セキュリティグループ・仮想網）、データベース（インスタンス・スナップショット）、 鍵と ID（ロール・鍵・鍵の方針）を一覧した
    根拠: CloudTrail の記録（Wiz CIRT の分析）
  3. 3. 認証情報アクセスdisclosed[1] [2]
    Lambda の関数設定（環境変数が返る）・Secrets Manager の値・ SSM パラメータストアの値・EC2 のユーザーデータから、ソース管理・ID 基盤・ 継続的統合・データベースの資格情報、提供元のトークン、External ID を収集した。 Sentra の例では3か所の保管場所から7分間で約100件が読み出された
    根拠: CloudTrail の記録（Wiz CIRT・Sentra の分析）
  4. 4. 検知回避disclosed[1]
    送信元を Mullvad VPN とホスティング上の仮想サーバーの間で切り替え、 2人目の IAM 利用者（正規の基盤通信にも現れるもの）を使い始めた。 これにより利用者IDだけでは正規と攻撃を切り分けられなくなった
    根拠: 送信元IPと IAM 利用者の使い分け（Wiz CIRT の分析）
  5. 5. 横展開disclosed[1]
    収集した資格情報の有効性を確認した。AWS のキーは TruffleHog の利用者文字列を伴う 呼び出しで検証し、Entra ID ではサービスプリンシパルとしてサインインし、 Okta ではクライアント資格情報で OAuth トークンを取得した。 確認された資格情報はいずれも被害組織のもので、提供元のものではなかった
    根拠: CloudTrail と Entra ID・Okta のサインイン記録（Wiz CIRT の分析）
  6. 6. 持ち出しdisclosed[1] [2]
    引き受けたロールで到達できる S3 のバケットを一覧し、オブジェクトのヘッダを確かめてから 取得した。1回のセッションでバケットを丸ごと落とした例がある。 Sentra の例では、顧客プロファイルのファイル、資格情報を含むファイル、 本番データベースのバックアップが対象になり、1社では数百万件の取得が記録に残っていた
    根拠: CloudTrail とアクセス記録（Wiz CIRT・Sentra の分析）

    環境内での行動は次の順序だった。

    1. 引受——sts:AssumeRole で顧客の連携ロールの一時認証情報を得る（セッション名は quiam-enum・quiam-scope-full 等）
    2. 棚卸し——ストレージとデータ（バケット・オブジェクト・データベースとテーブル・クラスタ）、計算（インスタンス・イメージ・セキュリティグループ・仮想網）、データベース（インスタンス・スナップショット）、鍵と ID（ロール・鍵・鍵の方針）を一覧する
    3. 秘密情報の収集——Lambda の関数設定（環境変数が返る）、Secrets Manager の値、SSM パラメータストアの値、EC2 のユーザーデータ
    4. 有効性の確認——TruffleHog の利用者文字列を伴う呼び出しで AWS キーを検証し、見つけたクライアントシークレットで Entra ID のサービスプリンシパルとしてサインインし、Okta のクライアント資格情報で OAuth トークンを取得する
    5. 持ち出し——S3 を一覧し、ヘッダを確かめて取得する。バケットを丸ごと落とした例がある

    書き込み操作は1件も無い。 削除も改ざんも行われていない。有効性を確認された資格情報は、いずれも被害組織のものであって提供元のものではなかった。

    被害の深さを決めたのは「解約後に残した信頼」だった原因・手口出典 [1] [2]

    この事案で最も重要な事実は、攻撃者が何も破っていないことである。

    • 引受要求にはすべて External ID が付いていた。そしてすべて成功した
    • Wiz は「多くの環境では、10月中に提供元アカウントから引受が行われたのは攻撃者の要求だけだった」と記している
    • つまり攻撃者が引き受けたロールの多くは、ほかに使われていないロールだった

    Sentra の記述はさらに踏み込んでいる。悪用されたロールの多くは2026年春以降使われていなかった。同社は攻撃の前に、ある Qubole 用ロールを「数か月使われていないのに機微なデータへ到達できる」として指摘していた。同社の結論は一文である——使われていない特権的な外部ロールは、監視するのではなく消すもの。

    External ID についても整理が要る。これは AWS が推奨する確認の仕組みだが、CloudTrail に平文で記録される。したがって秘密ではない。Wiz の評価は明快で、「本件で観測したすべての引受は、送信元IPの条件だけで防げた」。Sentra も「Qubole の公表アドレスへの絞り込みだけで、観測されたすべてのログインを止められた」と書いている。両社が同じ結論に達している。

    一方で、Qubole 側の認証情報がどう盗まれたかは公表されていない。起点が分からないため、同種の事故が他の提供元で起きるかを判断する材料が無い。

    検知の端緒は「流出資料の中身」だった——出所から信頼関係をたどった発覚の端緒出典 [1] [2]

    発見の経路は、この事案の実務的な示唆の半分を占める。

    Sentra の説明では、同社はまず流出した資料の中身（ファイル名ではなく内容）を、自社が走査済みのデータと突き合わせた。これで出所が数個の S3 バケットに絞られた。次に、そのバケットを読める外部の主体を列挙した。候補のうち、直近の活動（時刻・頻度・送信元IP・操作）を各主体の履歴と比べて平常と違っていたのは Qubole だけだった。同社は Qubole 連携のある自社顧客を約1時間で点検し、同じ活動を確認して Wiz へ連絡した。

    ここから読み取れることが2つある。

    第一に、「誰が読めるか」の一覧が引けることが前提になっている。外部アカウントを信頼しているロールと、そのロールが到達できるデータの対応表が無ければ、出所から提供元へさかのぼれない。第二に、提供元ごとの平常の挙動を持っていたことが決め手になっている。引受そのものは正規の操作なので、「正規かどうか」では切り分けられない。切り分けられるのは「この提供元のいつもと違うか」である。

    なお Wiz は、S3 のデータイベントやアクセスログが有効でない環境ではどのオブジェクトが読まれたかを特定できなかったと明記している。引受は管理イベントに残るが、読まれた中身はデータイベントが無いと分からない。

    「使っていない連携」は資産ではなく負債である（本記録の評価）評価・解釈出典 [1] [2]

    ここからは本記録の判断である。

    SaaS との連携は、契約の終了とともに消えない。消えるのは請求だけである。残るのは、①顧客側に作った IAM ロール、②その信頼ポリシー、③その権限、④連携のために保管した資格情報、である。本件で深く入られたのは、まさにこの4つを片付けていなかった組織だった。

    ここには、通常の委託先管理が取りこぼす構造がある。委託先の棚卸しは契約を単位に行われる。契約が終われば一覧から消える。しかし権限は契約ではなくクラウドの設定として残る。台帳の側では「もう委託していない」のに、環境の側では「いまも読める」という食い違いが生じる。この食い違いは、契約の棚卸しでは見えない。見えるのは、クラウド側で「外部を信頼しているロール」を引いたときだけである。

    もうひとつ、本件は一時認証情報の性質を突いている。資格情報を取り替えても、すでに発行された一時セッションは終わらない。Wiz がこれを明記しているのは、取り替えだけで対応を終えた組織が「もう安全」と誤解するからである。必要なのはロールのセッション無効化まで含めた手順である。

    最後に、本件を「Qubole の事故」として読むと学びを失う。同じ構図を持つのは、データ基盤・監視・バックアップ・費用管理・セキュリティ製品——顧客の AWS 環境に引受権限を持つすべての SaaS である。自組織で引けるべき問いは「Qubole を使っているか」ではなく、「いま外部アカウントを信頼しているロールは何本あり、それぞれ最後に引き受けられたのはいつか」である。

    緩和策
    数え方: 外部アカウントを信頼している IAM ロールを棚卸しし、使っていない連携は削除する　副作用: 稼働中の連携を誤って消すと基盤の処理が止まる。削除の前に、 直近の引受実績（どのアカウントがいつ引き受けたか）で使用中かを確かめる必要がある
    数え方: 信頼する主体をアカウント全体ではなく個別の主体に絞り、送信元IPの条件を付ける　副作用: 提供元が送信元の範囲を公表していない場合は条件を書けない。 提供元の基盤移転で通信が止まるため、範囲の変更を追う運用が要る
    数え方: External ID を秘密として扱わず、事故後は提供元と取り替える　副作用: 取り替えは提供元側の設定変更を伴うため、連携の一時停止が発生しうる
    数え方: 連携ロールの権限を最小化する（関数設定・秘密情報・パラメータ・広い S3 読み取りを外す）　副作用: 権限を削ると提供元の機能の一部が動かなくなる。何を落とすかの判断に 提供元の仕様確認が必要になる
    数え方: 読まれた可能性のある秘密・パラメータ・関数の環境変数をすべて取り替え、セッションを無効化する　副作用: 資格情報の一斉取り替えは広い停止を伴う。すでに発行済みの一時セッションは 資格情報の取り替えだけでは終わらないため、ロールのセッション無効化も必要になる

    波及の構造

    事案の構造を図にしたものです。数値は公表値に基づきます。
    提供元の認証情報から、顧客が残していた信頼ポリシーを通って顧客環境へ届いた経路
    layer 0 は攻撃者と、悪用された提供元アカウントの認証情報。 layer 1 は引受の仕組み（信頼ポリシーと External ID）。 layer 2 は顧客環境の中で触られた場所。layer 3 は持ち出されたものと、 そこから到達した外部の ID 基盤。矢印はすべて正規の API 呼び出しである。

    どこで止められたか

    段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
    段階検知の機会効きえた対策
    初期侵入機会はあったが検知できず
    引受は正規の操作として記録されるため、操作名では異常にならない。 多くの環境では10月中の引受が攻撃者の要求だけであり、 「提供元の平常の挙動」と比べていれば浮かんだ（本記録の評価）

    侵入を防げた使っていない連携ロールを削除する（提供元を信頼ポリシーから外す）
    検知できた提供元がこれまで使っていない通信元（VPN・ホスティング）からの引受を警報にする
    内部探索機会はあったが検知できず
    短時間に多種の一覧 API が連続する形は、提供元の通常の処理とは異なる。 引受セッション単位で後続の操作を追えば異常として見える（本記録の評価）

    影響を限定できた連携ロールの権限を提供元の機能に必要な範囲へ最小化する
    認証情報アクセス機会はあったが検知できず

    検知回避機会はあったが検知できず
    共用の VPN 出口は単独では決め手にならないと Wiz も記している。 切り分けの鍵は「提供元が使っていない通信元か」である
    侵入を防げた提供元が公表する通信元の範囲を信頼ポリシーの条件に書き、範囲外を落とす

    検知できた機微なバケットで S3 のデータイベントまたはアクセスログを有効にする
    検知できた組織全体の CloudTrail を1本用意し、記録の欠けを作らない
    影響を限定できた連携ロールの S3 読み取りを必要なバケット・接頭辞に限定する

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    判断評価評価の根拠と留保
    調査にあたった Wiz と Sentra が、提供元の公表を待たずに2026年11月9日に分析を公開し、 提供元の AWS アカウントID・IAM 利用者ID・送信元IP・調査手順を示した機能した本記録の作成者の評価である。アカウントID・IAM 利用者ID・送信元IP・ 見るべき API（引受・秘密情報の取得・S3 の取得）まで示されているため、 利用組織は自力で点検できる。「広範で機会便乗型」としつつ件数を明かさない点は、 被害組織の保護と読者の判断材料の間の妥当な線引きだと考える
    Qubole と親会社 Idera は、本記録の作成者が確認した範囲では公表を行っておらず、 報道の問い合わせにも応答していない不十分本記録の作成者の評価である。起点は提供元のアカウントの認証情報であり、 顧客が自分で調べるには提供元の協力（影響範囲・期間・取り替えるべき External ID）が要る。 進行中の可能性があるため、後続で公表が出れば評価は変わる
    CISO・経営層への示唆
    • 委託先の棚卸しを「契約」ではなく「クラウドの権限」から引く
      契約が終わっても、顧客側に作った連携ロールと信頼ポリシーは残る。 本件で深く入られたのは、利用をやめた後も信頼を残していた組織だった
      取るべき行動 四半期ごとに「外部アカウントを信頼している IAM ロール」を一覧し、 ①最後に引き受けられた日 ②到達できるデータ ③対応する契約の有無を並べた表を作る。 契約が無いものは監視対象ではなく削除対象として扱う
    • 提供元が公表しない前提で、自社が動ける手順を用意する
      起点は提供元の認証情報だったが、Qubole・Idera の公表は確認できていない。 顧客は第三者の分析に載った識別子で自分の記録を調べる形になった
      取るべき行動 主要な SaaS 連携について「提供元から説明が無いまま侵害が報じられた場合」の手順を作る。 調べる記録の種類（クラウドの監査記録・ID 基盤のサインイン）、 取り替える資格情報の一覧、連携を止める判断権者を事前に決めておく
    • 「確認の仕組みがある」を「防げる」と読み替えない
      引受要求はすべて External ID を伴い、すべて成功した。 External ID はクラウドの監査記録に平文で残るため、秘密として機能しない
      取るべき行動 連携の設計レビューで「この条件は秘密に依存していないか」を確認項目にする。 提供元との契約・設定の見直し時に、送信元の範囲（公表アドレス）を条件に 書けるかを必ず聞く
    • データの持ち出しは「読まれたことを特定できるか」で被害が決まる
      S3 のデータイベントやアクセスログが有効でない環境では、 どのオブジェクトが読まれたかを特定できなかった
      取るべき行動 機微なデータを置くバケット・ストレージについて、データ読み取りの記録を有効にする。 費用を理由に全体で無効にするのではなく、分類に応じて有効にする範囲を決める。 記録が無い範囲は「事故時に説明できない範囲」として経営リスクの一覧に載せる
    セキュリティ技術者への示唆
    • 信頼ポリシーの主体を絞り、送信元の条件を付ける
      Wiz は「送信元IPの条件だけで、観測されたすべての引受を防げた」と明記している。 信頼する主体がアカウント全体のままでは、提供元のどの資格情報でも通る
      取るべき行動 外部連携のロールについて、信頼ポリシーの主体をアカウント全体から個別の主体へ変更し、 提供元が公表する送信元の範囲（IPまたは仮想網の端点）を条件に加える。 提供元が範囲を公表していない場合は、公表を求めるか連携方式の見直しを検討する
    • 連携ロールから秘密情報の読み取り権限を外す
      攻撃者は Lambda の関数設定・秘密情報の保管サービス・パラメータストア・ EC2 のユーザーデータから資格情報を集め、ID 基盤の資格情報まで到達した
      取るべき行動 連携ロールの権限を点検し、関数設定の取得・秘密情報の値の取得・ パラメータの値の取得・広い S3 読み取りを、提供元の機能に不要なら削除する。 必要な場合は対象を名前・接頭辞で限定する
    • 資格情報の取り替えだけで終わらせず、セッションを無効化する
      資格情報を取り替えても、すでに発行された一時セッションは終わらない。 Wiz はこの点を明記している
      取るべき行動 対応手順に①読まれた可能性のある秘密・パラメータ・環境変数の取り替え ②該当ロールの有効セッションの無効化 ③External ID の取り替え（提供元と調整）を入れる。 ①だけで完了にしない
    • 提供元ごとの「平常」を記録しておく
      引受は正規の操作なので、操作名では異常にならない。 Sentra は提供元ごとの時刻・頻度・送信元IP・操作の履歴と比べて1社を切り出した
      取るべき行動 外部ロールの引受について、提供元ごとの時間帯・頻度・送信元・後続操作の傾向を ダッシュボードに出す。これまで使われていない通信元からの引受、 長く使われていないロールの引受を警報にする
    • 引受セッション単位で後続の操作を追えるようにする
      Wiz の調査手順は「見つけたセッションごとに、その後の操作を全部見る」ことだった。 特に秘密情報・パラメータ・関数・ストレージへの操作が対象になる
      取るべき行動 組織全体の監査記録を1本にまとめ、セッション名・主体でひも付けて検索できる状態にする。 調査の起点となる問い（提供元アカウントからの引受のうち、クラウド外の通信元のもの）を あらかじめ保存したクエリにしておく

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    委託・第三者部品□ 顧客側の IAM ロールを外部の SaaS に引き受けさせる連携（クロスアカウント方式）を 1つ以上使っている本件は提供元の認証情報が悪用され、この正規の経路がそのまま通られた
    認証・認可□ 信頼ポリシーの主体がアカウント全体のままで、送信元の条件が付いていないWiz は送信元IPの条件だけで観測されたすべての引受を防げたとしている
    体制・契約□ SaaS の解約・停止の手順に「顧客側に作った連携ロールと信頼ポリシーの削除」が入っていない攻撃者が引き受けたロールの多くは、ほかに使われていないロールだった
    認証・認可□ 連携ロールに、関数設定の取得・秘密情報の値の取得・パラメータの取得・ 広い S3 読み取りの権限が付いている攻撃者はこの4か所から資格情報を集め、ID 基盤の資格情報まで到達した
    運用・監視□ 機微なデータのストレージでデータ読み取りの記録を有効にしていない記録が無い環境では、どのオブジェクトが読まれたかを特定できなかった
    運用・監視□ 外部ロールの引受について、提供元ごとの平常の挙動を記録・可視化していない引受は正規の操作であり、平常との差分でしか切り分けられない
