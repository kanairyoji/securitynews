INC-2026-0982自動車2社のアプリ不備で遠隔解錠

自動車2社のコネクテッドアプリの背後にある ForgeRock の ID 基盤に、WAF をすり抜ける経路の取り違えと既定・検証用の資格情報が残っており、研究者が本番の顧客ディレクトリを管理者として操作して任意の所有者アカウントを乗っ取り、遠隔での解錠・エンジン始動まで到達した——2社は匿名を希望し、報告から約2時間で修正。社名は公表されていないが Toyota・Lexus だとの観測が流れ、同社は肯定も否定もしていない

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備設定不備認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年11月7日 最終更新: 2026年11月10日

研究者 Sam Curry と Shubham Shah（Assetnote 共同創業者）は2026年11月7日、自動車2社のコネクテッドアプリの背後にある ForgeRock の ID 基盤を攻撃し、本番の顧客ディレクトリを管理者として操作して任意の所有者アカウントを乗っ取り、遠隔での解錠・エンジン始動まで到達したことを、それぞれの記事として公開しました。2社は匿名を希望しており、記事では「Automaker #1」「Automaker #2」と表記されています。

オーストラリア向けの経路（Shah）はこうです。Android アプリを逆コンパイルしてAPI の所在を調べ、副ドメインに置かれた管理用の検証ツールを見つけます。その JavaScript には固定の API キーが埋め込まれており、メールアドレスからの契約者検索や、ナンバープレート → 車台番号（VIN）→ 契約者の識別子というたどり方ができました。さらに提供元の JavaScript にForgeRock の ID 管理（OpenIDM）の管理者資格情報が入っており、これは検証環境向けのものでしたが本番でも通りました。WAF は管理用の経路を塞いでいましたが、経路の取り違え（パストラバーサル）で回避でき、管理者として任意の利用者のパスワードを上書きできました。そこから多要素認証を経ない認証方式でアプリ用のトークンを取り、遠隔操作の API を呼べる状態になっています。

米国向けの経路（Curry）はより手がかかっています。符号化された経路の扱いが WAF・サーブレットコンテナ・アプリで食い違う経路の取り違えを突いて、隠れていた Apache Felix の管理コンソールに到達し、出荷時の資格情報で入ります。設定機能から Groovy を実行する停止状態の定期処理を作り、コマンド受け口を公開する部品を組み込んでID サーバー上でコマンドを実行。プロセスの環境変数から取った資格情報で、公開側では WAF が塞いでいた顧客ディレクトリの管理 API に内部経由で到達し、試験用の所有者のメールアドレスとパスワードを変更して通常のアプリログイン（メールで届く確認コードも自分で受領）を完了、公式アプリ用の OAuth トークンに交換して車庫と車台番号を取得しました。得られた操作は所有者のアプリと同等で、位置情報と走行データ・アカウントと車両情報・施錠解錠・遠隔のエンジン始動と停止が含まれます。

本記録が注目するのは2点です。第一に、車の鍵の話が ID 基盤の運用の話だったこと。使われたのはゼロデイではなく、検証用資格情報の本番流用・出荷時資格情報・WAF をすり抜ける経路の取り違えです。第二に、修正が約2時間だったこと。2社は報告から約2時間で修正し、実証用の仕込みは撤去され、該当する資格情報は入れ替えられました。当事者の公表は存在せず、本記録の事実関係は研究者2名の記事に基づきます。

    ここにWAF の役割の誤解が重なる。両地域で、管理用の経路は公開側では WAF が塞いでいた。しかしオーストラリアでは経路の取り違えで回り込まれ、米国ではサーバー内部（自分自身への接続）から到達されている。つまり管理 API 側には、到達した相手を認証・制限する仕組みが足りていなかった。WAF は「外から来た要求を選別する装置」であって、「管理機能の認可」ではない。

    もうひとつ、オーストラリア側で効いたのは多要素認証を経ない認証方式である。管理者としてパスワードを上書きできても、通常のログインには追加の確認が入る。ところが利用者アプリ向けに、利用者名とパスワードだけでトークンを得られる方式が有効になっていたため、追加の確認を通らずにアプリと同じトークンが手に入った。米国側では、Curry はメールで届く確認コードを自分の受信先で受け取ることで通常のログインを完了させている（メールアドレスを書き換えられたため）。

    Curry は地域差にも触れている。米国向けは「はるかに多くの手間を要した」のであり、対象の自動車メーカーは米国・カナダ・欧州の ID 管理環境の防御により多くの時間を費やしていた。同じ会社でも、地域ごとに守りの厚みが違っていたことになる。

    ここからは本記録の判断である。

    この連鎖のどこにも、車載装置の話は出てこない。通信方式の解析も、鍵の暗号の解読も、車両ネットワークへの侵入も無い。あるのは、会員 ID 基盤の管理画面・管理 API・トークン発行である。車は、正規の API に正規のトークンで来た命令に従っただけである。

    ここから引き出せる論点は3つある。

    第一に、コネクテッドの安全性は ID 基盤の運用品質に等しい。所有者アカウントを乗っ取れれば、車の設計がどれだけ堅牢でも解錠される。自動車に限らず、スマートロック・宅配ボックス・住宅設備・決済—— 物理的な動作を伴うサービスはすべて同じ構図を持つ。

    第二に、「公開側で塞いだ」は到達の制御ではない。本件では2地域とも、WAF で管理経路を塞いだうえで突破されている。片方は経路の取り違えで、もう片方はサーバー自身の内部からの接続で。必要なのは「誰が来ても管理機能には認証と到達元の制限がかかる」状態である。ここは設計の問題であり、装置の追加では埋まらない。

    第三に、検証環境の資格情報は本番の資格情報である——本番で通るなら。「これは検証用だから」という前提は、流用を止める技術的な裏付けを伴わない限り、ただの期待である。公開資材（アプリ・JavaScript）に埋め込まれた鍵は必ず読み出されると考えるべきで、読み出されても本番に届かないことが要件になる。

    日本の組織が自組織で引ける問いは3つである。①基盤製品に同梱される管理画面（本件の Apache Felix に相当するもの）の存在を把握し、出荷時の資格情報を変えてあるか。②会員 ID 基盤の管理 API は、公開側の遮断に加えて自前の認証と到達元制限を持っているか。③利用者アプリ向けに、多要素認証の段を飛ばせる認証方式が有効になっていないか。
