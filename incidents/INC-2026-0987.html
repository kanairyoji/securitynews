観点 従来の漏えい LLMJacking
取られるもの データそのもの モデルを呼び出す権利（API キー・トークン）

報道によれば、GTIG と Mandiant は1週間前に、LLMjacking により侵害された組織のクラウド AI 利用料が最大100万ドルに達していると報告した（出典3）〈重要〉—— 本記録はこの報告そのものを取得しておらず、数値は報道を通じた確認である〈齟齬4〉。

  2. 自社のキーが、他社の環境変数に入っていないかを数える。 Fireworks は第1の侵害で、評価ジョブの環境変数に置かれていた secrets が取得された可能性を認めている（出典2）—— そこには第三者サービスの認証情報も含まれており、Fireworks は「発行元で個別にローテーションする必要がある」と書いている。 預けた先が侵害されたとき、自社が回す必要があるキーの一覧を持っているかが問われる。

理由は3つある。

第一に、これは「監視をしていなかった」という話ではない。データが置かれていたのは外部の無管理な場所ではなく、Uber のクラウドセキュリティチームが自ら作り、自ら管理していた環境である（出典18）。アラートも設定されていた。それでも発火は0件である。監視の有無と監視の有効性は別の軸であり、「委託先にデータを預けるが、環境は自社で管理する」という設計は、この経路に対しては防御になっていなかった。

第二に、認証情報が正規である限り、認証を見る監視には何も映らない。委託先（Fireworks AI）の内部の認証情報が盗まれ、それが Uber のアカウントへのアクセスに使われた（出典10・18）。Uber から見れば、入ってきたのは正しい鍵を持った正規の委託先である。失敗したログイン、未知の認証方式、総当たりといった「認証の異常」は発生しない。映りうるのは認証の後——送信元、時間帯、取得する量、取得するデータの種類——だけである。Uber がそれらを見ていたかは公表されていない（〈未確定23〉）。

第三に、「他のシステムには届かなかった」ことが成果として語られている。 Uber は「当該委託先の侵害された認証情報は Uber の他のシステムへのアクセスを与えなかった」としている（出典18）。これは分離が効いたという意味で確かに成果だが、預けたデータそのものは全量が到達範囲にあった。本件で持ち出されたのは運転免許証の画像を含む本人確認の材料であり（出典18）、横展開が無かったことは被害の小ささを意味しない。

本記録の読みはこうである——委託先にデータを渡した時点で、自社の監視が見られるのは「渡した先の鍵が正しく使われているか」ではなく「渡した先の鍵がどれだけのデータに触れたか」である。前者は認証の問題であり、後者は量とふるまいの問題である。本件は、前者だけを見ていた環境で何が起きるかを当事者の言葉で示している。

CISO・経営層への示唆
  • 「監視を置いた」ではなく「盗まれた正規の鍵で入られたときに何が映るか」で監視を評価する
    **Uber は、当該データが自社のクラウドセキュリティチームが作成・管理する環境にあり、 アラートも有効だったが、攻撃者が正規の認証情報を使ったため 1件も発火しなかったと説明している**（出典18。事実）〈重要〉。 **環境を自社で管理していたことも、アラートを設定していたことも、 この経路に対しては防御にならなかった**（本記録の整理）。
    取るべき行動 **委託先に渡しているデータ基盤ごとに、「委託先の正規の認証情報が盗まれた」 という前提で机上演習を1回行う。認証の失敗ではなく、 ①送信元の変化、②時間帯、③取得したデータの量と種類、④通常との差分 のどれを見ているかを書き出し、1つも無い基盤を特定する。 そのうえで「アラートが発火する条件」を文書にして、年次で検証する。**
  • 研究・開発環境を外部の基盤に置くなら、その事業者のインシデントが自社の事案になることを前提に契約を読む
    **本件の第2の侵害は、Fireworks の R&D マシンをホストしていた 第三者クラウドプロバイダのインシデント（10月23日）から始まり、 翌日に Fireworks の顧客データへの影響に至っている**（出典1。事実）。 **起点は Fireworks の統制の外であり、 Fireworks が検知できたのは自社の開発マシンに入られてからである** （本記録の整理）。
    取るべき行動 **自社の研究・開発環境を外部に置いている箇所を一覧にし、 各契約について①事業者側のインシデントを自社へ通報する義務と時限、 ②連絡先と連絡手段、③自社が調査のために取れるログの範囲を 確認する。書かれていない項目は更新交渉の論点として記録する。**
  • 「データを持たない」判断が効く範囲と、効かない範囲を分けて棚卸しする
    **本件では、推論トラフィック（プロンプトと出力）は ゼロデータ保持（ZDR）で影響が検出されず、 カード番号は保存していないため影響が無かった**（出典1。事実）。 **一方で、請求情報・データセット・不完全なモデルの重みは 影響を受けている**（出典1）—— **これらは業務上そこに置く必要があるものである**（本記録の評価）。
    取るべき行動 **自社が AI 基盤へ預けているものを「持たないことにできるもの」と 「業務上預けざるを得ないもの」に分け、後者について 基盤側の保護（テナント分離・暗号化・アクセス記録）を 契約と技術文書で確認する。確認できない項目は残存リスクとして 経営に上げる。**
  • AI 基盤の API キーを、データではなく「課金される資産」として管理対象に入れる
    **第1の侵害で Fireworks は、LLM への不正アクセスから得た トークンを不正な中継ゲートウェイへ売ることを狙う 金銭目的の集団とのつながりを示す証拠があると述べた （LLMJacking）**（出典3。事実）。 **報道によれば GTIG と Mandiant は、 この型の攻撃で侵害された組織のクラウド AI 利用料が 最大100万ドルに達していると報告している**（出典3）〈齟齬4〉。 **この被害は本人への二次被害ではなく、請求額として現れる** （本記録の整理）。
    取るべき行動 **AI 基盤ごとに発行している API キーの一覧（発行元・用途・保持場所・ 失効手順・課金の上限）を作り、利用量と請求額の異常を 週単位で見る担当を決める。上限を設定できる基盤では上限を入れる。**
  • 続報で範囲が増える前提の通知設計を、公表文の中に書く
    **本件は第1の侵害の時点で「顧客のモデル・データセット・学習データへの 不正アクセスは確認されていない」とされていたが**（出典2）、 **17日後に始まった第2の侵害では、限定的なアカウント群について データセットと不完全なモデルの重みが影響を受けている**（出典1。事実）。 **影響顧客には個別通知するとされている一方、 調査は継続中であり対象は確定していない**（出典1）—— **通知を受けていない組織は「対象外」と読んでしまう** （本記録の評価）。
    取るべき行動 **自社の事案公表の雛形に、①その時点で特定できた範囲であることの 明示、②範囲が増えた場合の追加通知の方法と窓口、 ③調査の節目（次に何がいつ分かるか）の3項目を入れる。**
  • AI ベンダーへ「渡したデータ」とは別に、「渡した鍵」が自社のどこを開けるかを台帳にする
    **Cursor の事案で攻撃者が入手したのは、Cursor が Fireworks に 発行していたアクセスキーである**（出典15。事実）—— **そのキーが開けたのは Fireworks の保存先ではなく、 Cursor 自身の読み取り専用ストレージバケットだった。** **基盤側の侵害の影響は「基盤に置いたデータの範囲」では収まらず、 渡した鍵の到達範囲で決まった**（本記録の整理）〈重要〉。
    取るべき行動 **AI ベンダー・SaaS へ発行した鍵を一覧にし、各鍵について ①何を開けるか（保存先・API・権限）、②読み取り専用かどうか、 ③送信元の制限がかかっているか、④失効の手順と所要時間を記録する。 「読み取り専用だから軽い」と評価していた鍵を洗い出し、 中身が全部複製された場合の影響を見積もる。 共有用の保存先は、その鍵でしか開かない専用のものに分ける。**
  • 「伏せている」「持たない」「消している」は、測った記録が無ければ対策として数えない
    **本事案では、同じ形の食い違いが2社で起きている**（本記録の評価） 〈重要〉—— **①Notion は「Fireworks のエンドポイントからデータが 保持されていたことが分かった」と書いた（出典4）。 Fireworks はゼロデータ保持を契約で約束していた**〈齟齬7〉。 **②Cursor は学習用トレースに「伏字化されていなかった認証情報」が 含まれていたと書いた（出典15）。** **いずれも、実装が意図どおりでないことの発見は侵害の調査の中で起きた。**
    取るべき行動 **自社が「持たない・消す・伏せる」で守っていると説明している項目を 一覧にし、各項目について「最後に実測したのはいつか、 誰が、どの手順で確かめたか」を書き込む。 空欄の項目は、対策ではなく未検証の前提として残存リスクに移す。 ベンダーの約束に依っている項目は、 自社で検証できる形（出力の抜き取り検査・保持期間の実測）を 契約に書き込む。**
セキュリティ技術者への示唆
  • 委託先へ発行した認証情報には、量と範囲の上限を付ける
    **本件では、委託先の認証情報で Uber が当該委託先と共有していたデータへ 到達された**（出典10・18。事実）。 **Uber は「当該委託先の侵害された認証情報は Uber の他のシステムへの アクセスを与えなかった」としており、横展開は止まっている**（出典18）—— **しかし、渡したデータそのものは全量が到達範囲にあった**（本記録の読み）。
    取るべき行動 **委託先に発行するアクセス資格について、①到達できるデータの範囲を 資源単位で明示する、②単位時間あたりの取得件数に上限を設ける、 ③送信元を事前に登録したアドレスに限る、④有効期限を付けて自動失効させる、 の4点を既定にする。上限に当たったこと自体を警報にする。**
  • 評価・学習ジョブに secrets を環境変数で渡す設計をやめる
    **第1の侵害で取られた可能性があるのは、 一部の顧客アカウントの評価ジョブの環境変数に置かれていた API キーやトークンである**（出典2。事実）。 **Fireworks 自身が「評価ジョブへの secrets の提供方法を 見直している」と書いている**（出典2）—— **見直しの内容は公表されていない**（本記録の確認）。
    取るべき行動 **自社の学習・評価・バッチのジョブ定義を grep して、 環境変数・ジョブ設定・YAML に静的な API キーが 埋まっている箇所を数える。見つかった分は、実行時に短期の資格情報を 発行する方式（OIDC 連携・秘密管理サービスからの動的取得）へ 置き換える計画を作る。**
  • 開発・研究環境から本番の顧客データ保存先に届く経路と権限を、実測で確認する
    **本件では、クラウド事業者経由で到達された先は Fireworks の「開発マシン」であり、 そこから顧客データへの影響が生じている**（出典1。事実）。 **Fireworks は対応として「不要な昇格権限を削除した」 「不正なネットワーク経路を制限した」と書いており**（出典1）、 **侵害の時点でそれらが存在していたことを当事者の文書が示している** （本記録の整理。 **それらが今回の到達に使われたとは書かれていない**）。
    取るべき行動 **開発・研究環境のワークロードに付与されているロール／ サービスアカウントを列挙し、各々が本番のデータ保存先・ 分析基盤に到達できるかを実際に試して確認する。 到達できた経路は、必要性を1件ずつ判断して削る。**
  • 預けた先が侵害されたときに自分で回すべきキーの一覧を、事前に持つ
    **Fireworks は、第三者サービスの認証情報について 「発行元で個別にローテーションする必要がある」と記し、 それらを使った呼び出しの範囲は確認中としている**（出典2。事実） 〈重要〉—— **基盤側が失効できるのは基盤自身のキーだけであり、 顧客が基盤に預けた他社のキーは顧客が回すしかない** （本記録の整理）。
    取るべき行動 **AI 基盤・CI・SaaS に預けている第三者キーを、 「どのサービスのキーを、どこに、何のために置いたか」の表にする。 各行に失効と再発行の手順を書き、 預け先の侵害時にその表だけで作業が完了する状態にする。**
  • 承認されていないワークロードの起動を記録し、逸脱で鳴らす
    **第2の侵害で実行されたのは「不正なワークロード」であり、 Fireworks はこれを同日中に検知している**（出典1。事実）。 **検知の手段は公表されていない**〈未確定8〉—— **ただし対応として「ログと監視の強化」が挙げられている**（出典1）。
    取るべき行動 **研究・開発用の計算環境で、ジョブの起動（誰が・どのイメージで・ どの権限で）を記録しているかを確認する。記録していない環境を洗い出し、 平常の起動パターン（起動元・時間帯・イメージ）からの逸脱を 警報する条件を1つ以上入れる。**
  • 【続報】ゼロデータ保持は契約の文言ではなく、実装の挙動として確かめる
    **Notion は「私たちが使っていた Fireworks の エンドポイントからデータが保持されていたことが分かった」と 書いている**（出典4・原文英語。事実）〈重要〉—— **Fireworks はゼロデータ保持を契約で約束していた。** **一方、Fireworks の速報は 「Inference・Training SDK・Nexus はいずれも既定で ゼロデータ保持」と記している**（出典1）〈齟齬7〉。 **検証したのは基盤側ではなく顧客側で、 契機は侵害だった**（本記録の整理）。
    取るべき行動 **ゼロデータ保持を前提にしている AI 基盤について、 ①既定なのか明示的な設定なのか、 ②どのエンドポイント・どの API 経路に適用されるのか、 ③保持されていないことを自社が確認する手段（削除の証跡・ 保持期間の設定値・監査レポート）があるかを問い合わせる。 確認手段が無い基盤は「保持されている前提」で 預けるデータを決める。**
  • Cursor の VS Code 拡張マーケットプレースから Claude Code 拡張を入れた端末を、いま洗い出す
    **2026年10月29日の太平洋時間2時27分から13時35分まで（11時間8分）、 Cursor のマーケットプレースの配信キャッシュから Anthropic.claude-code 2.1.312／2.1.313（Windows・macOS）の 改ざん版が配信された**（出典15・16。事実）〈重要〉—— **受け取った可能性があるのは最大5,000ユーザーで、 国別の内訳は公表されていない**〈未確定17〉。 **悪性コードは拡張の読み込み時に動き、攻撃者の SSH 公開鍵を `authorized_keys` に追加して永続化を設置する**（出典16）。
    取るべき行動 **①該当する時間帯に当該拡張を導入・更新した端末を、 拡張の導入記録・EDR のテレメトリ・ネットワークログから洗い出す。 ②各端末で `~/.ssh/authorized_keys` に名札 `svc-telemetry` の鍵が あるかを確認する（Cursor が出典16 で公表した手順）。 ③見つかった端末は隔離し、攻撃者の SSH 鍵・永続化（macOS の LaunchAgent／Windows のスケジュールタスク）・動いている トンネルのプロセスを除去する——拡張のアンインストールだけでは 足りない。④その端末から到達できた認証情報とセッションを、 信頼できる別の端末からローテーションする。**
  • エージェントの実行記録（トレース）を外部へ出す経路に、シークレット走査を置く
    **Cursor が Fireworks と共有していたバケットには、 Privacy Mode でないセッションのコーディングエージェントの トレースが入っており、少数に伏字化されていない認証情報が 含まれていた**（出典15。事実）—— **API 認証情報が露出した顧客は 0.01% 未満だが、 攻撃者はそこを起点に SaaS ツール群・アーカイブ済みの ソースコードリポジトリ・そしてマーケットプレースの配信キャッシュへ 到達している**（本記録の整理）〈重要〉。 **件数の小ささと、1件あたりの到達の深さは別の軸である** （本記録の評価）。
    取るべき行動 **①自社からベンダーへ出ているログ・トレース・会話履歴の経路を すべて洗い出す。②その経路の出口でシークレット走査をかけ、 検出数と取りこぼし（既知のキー形式を仕込んだ試験）を 定期に測って記録に残す。③エージェントの実行記録を保存する時点で、 環境変数・コマンド引数・貼り付けられた文字列を既定で伏せる。 ④「学習に使う許諾」と「認証情報が入っていないこと」は 別の確認であることを、ベンダーへの提出手順に明記する。**
