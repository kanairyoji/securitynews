INC-2026-0989Hinemos に権限割り当ての不備

国産の統合運用管理ソフト **Hinemos** に、**一般ユーザが管理者ユーザのパスワードを変更できる**不適切な権限の割り当ての脆弱性（CVE-2026-109849・CVSS v4 7.1）——**全ユーザが所属する ALL_USERS ロールに「アカウント－変更権限」が初期状態で付与されていた**ことが原因で、提供元の NTTデータ先端技術は2026年11月4日に累積パッチと修正版を公開したが、**保守サポート終了済みの ver.6.x には修正が提供されず回避策のみ**、かつ**修正版を適用しても既存環境の権限設定は自動では変わらない**

脆弱性初報のみ日本の組織が当事者権限管理の不備設計・実装上の不備
初報: 2026年11月4日 最終更新: 2026年11月11日

独立行政法人情報処理推進機構（IPA）と一般社団法人JPCERT コーディネーションセンター（JPCERT/CC） は2026年11月4日、統合運用管理ソフトウェアHinemos の脆弱性を JVN#46901199 として公表しました。提供元の株式会社NTTデータ先端技術も同日、お知らせと修正を公開しています。

脆弱性は CVE-2026-109849、分類は CWE-266（不適切な権限の割り当て）、深刻度は CVSS v4.0 基本値 7.1（CVSS v3.0 では 6.5）です。JVN の記述は次のとおりです。

一般ユーザに割り当て可能な特定の権限でパスワード変更 API にアクセス可能な攻撃者によって、管理者ユーザのパスワードを変更される可能性があります。

提供元のお知らせは、その「特定の権限」が何かまで書いています。システム権限「アカウント－変更権限」を持つロールに所属する一般ユーザが、管理者ユーザのパスワードも変更できる仕様であり、全ユーザが所属する ALL_USERS ロールには、この権限が初期状態で付与されていました。 つまり既定の構成では、一般ユーザの誰でも管理者のパスワードを書き換えて管理者権限を取得できたことになります。

影響を受ける版は ver.7.2.0／7.1.0〜7.1.2／7.0.0〜7.0.4 と、通常保守サポートが終了済みの 6.2.0〜6.2.2／6.1.0〜6.1.2／6.0.0〜6.0.3 です。提供元は「これより前の、保守サポートが終了したバージョンも影響を受ける可能性がある」としています。

対処には2つの落とし穴があります。① ver.6.x には累積パッチも修正版パッケージも提供されません（回避策としての権限設定の見直しのみ）。② 修正版を適用しても、既存環境の権限設定は自動では変わりません。提供元は「既存環境の権限設定は自動的には変更されません」と明記しており、ALL_USERS ロールの初期権限が「リポジトリ－参照」のみになるのは修正版パッケージで新規導入した場合だけです。

JVN の記述は「一般ユーザに割り当て可能な特定の権限でパスワード変更 API にアクセス可能な攻撃者」という書き方になっています。この「特定の権限」が何かは JVN には書かれていませんが、提供元のお知らせを読むと分かります。

システム権限「アカウント－変更権限」を持つロールに所属する一般ユーザが、管理者ユーザのパスワードも変更できました。ALL_USERS ロールにはこの権限が初期状態で付与されていました。

ALL_USERS は、その名の通り全ユーザが所属するロールです。つまり既定の構成では、Hinemos にログインできる一般ユーザの誰でも、管理者ユーザのパスワードを書き換えて管理者権限を取得できたことになります。

CVSS v4.0 のベクタ PR:L（低い権限が必要）は、この構図を正しく表しています。事前に Hinemos のアカウントが1つあればよく、その権限は特別なものでなくてよい。

修正後は ADMINISTRATORS ロールへの所属が要る原因・手口出典 [1]

提供元のお知らせによる修正後の仕様は、次のとおりです。

  • 他の管理者ユーザのパスワードを変更するには、操作するユーザがADMINISTRATORS ロールに所属している必要がある
  • 「アカウント－変更権限」を持つだけの一般ユーザは、管理者ユーザのパスワードを変更できなくなる
  • 一般ユーザのパスワード変更、および本人による自身のパスワード変更は従来どおり

つまり修正は「権限の種類」ではなく「変更対象が管理者かどうか」で判定を追加したものです。CWE-266（不適切な権限の割り当て）という分類は、元の設計が「アカウント－変更権限」という1つの権限に、一般ユーザの変更と管理者の変更という重さの違う2つの操作をまとめていたことを指しています。

あわせて提供元は、ALL_USERS ロールの初期権限そのものを変更しました。修正版パッケージで新規導入した場合、ALL_USERS ロールの権限は「リポジトリ－参照」のみになります。運用に必要な権限は、利用者の役割に応じて個別に付与する設計に変わりました。

対処には2つの落とし穴がある——6.x に修正は来ず、既存環境の権限は自動では直らない再発防止出典 [1]

1つ目。保守サポート終了済みの ver.6.x には修正が提供されません。

提供元のお知らせには、ver.7.2／7.1／7.0 向けの累積パッチ名とOSS 版パッケージ名が具体的に並んでいますが、ver.6.x にはその記載がなく、通常保守サポート終了版には提供しないと明記されています。 ver.6.2／6.1／6.0 の3系列、さらに「それより前の版も影響を受ける可能性がある」とされる範囲が、修正の及ばない領域として残ります。該当する環境では、回避策（権限設定の見直し）が唯一の手段です。

2つ目。修正版を適用しても、既存環境の権限設定は自動では変わりません。

提供元の原文はこうです。

既存環境の権限設定は自動的には変更されません。

ALL_USERS ロールの初期権限が「リポジトリ－参照」のみになるのは、修正版パッケージで新規導入した場合だけです。既存環境でパッチを当てた場合、ALL_USERS ロールには「アカウント－変更権限」が付いたまま残ります。

ただしパッチを適用済みであれば、管理者ユーザのパスワード変更はADMINISTRATORS ロールへの所属を要するようになるため、本脆弱性そのものは解消します。提供元も「パッチを適用済みであれば、この追加対応は不要」としています。それでも権限の見直しが推奨されるのは、「アカウント－変更権限」がアカウントパースペクティブ全般の変更権限にあたるためで、一般ユーザに残しておく理由は通常ありません。

回避策の手順として提供元が示しているのは次の3つです。

  1. 「アカウント－変更権限」を、業務上必要なユーザだけに付与されるよう見直す
  2. ALL_USERS ロールを含む各ロールについて、同権限の付与状況と所属ユーザを確認する
  3. ロールの権限やユーザの所属ロールを変更する（変更前に、現在の運用への影響を確認する）

参照先として Ver.7.x は基本機能マニュアル 4.3.3／4.3.5、Ver.6.x はユーザマニュアル 12.2／12.6 が案内されています。

運用管理ソフトの管理者権限は、監視対象のすべてに届く評価・解釈出典 [1] [2]

以下は本記録の作成者の評価です。

CVSS v4.0 の 7.1 は「緊急」ではありません。機密性（VC）と可用性（VA）への影響は N（なし）、完全性（VI）のみ H（高い）という評定です。評点だけ見れば、当月の他の脆弱性に埋もれる水準です。

しかし Hinemos は統合運用管理ソフトウェアです。サーバー・ネットワーク機器の監視を行い、ジョブを実行します。その管理者権限が取れるということは、Hinemos が管理している対象すべてに対して、Hinemos を経由して何かを実行できる立場に立てることを意味します。CVSS の評定は Hinemos というソフトウェア単体への影響を測るもので、運用管理ソフトが持つ「他のシステムへの到達」は評点に入りません。

前提条件は「Hinemos のアカウントを1つ持っていること」です。これは外部の攻撃者にとっては障壁ですが、内部の利用者、あるいは一般ユーザのアカウントを1つ奪った攻撃者には障壁になりません。 運用管理ソフトには、オペレータ・開発者・監視要員といった形で多数の一般ユーザがアカウントを持っているのが通常です。

読み方としては、「評点7.1の脆弱性」ではなく「運用管理基盤における権限分離の不成立」として扱うのが妥当だと考えます。そして、この観点から見ると最も重い事実は脆弱性そのものではなく、修正版を適用しても既存環境の権限設計は変わらないという点です。パッチ適用で本脆弱性は閉じますが、「ALL_USERS に広い権限が付いている」という設計上の状態は残ります。

CISO・経営層への示唆
  • 運用管理ソフトの脆弱性は、評点ではなく「そこから到達できる範囲」で測る
    本件の CVSS v4.0 は 7.1 で、機密性と可用性への影響は「なし」と 評定されている。評点だけなら当月の他の脆弱性に埋もれる。 **しかし Hinemos は監視とジョブ実行を担う基盤であり、 その管理者権限は管理対象のすべてに届きうる。** CVSS はソフトウェア単体への影響を測る尺度で、 「その先への到達」は入らない
    取るべき行動 資産台帳に「このシステムを乗っ取られたら、そこから到達できる システムの範囲」の欄を設け、運用管理・監視・構成管理・CI の基盤には 評点に関係なく最優先の扱いを与える。 脆弱性対応の優先順位を評点だけで決める運用をやめる
  • 「パッチを当てた」で終わらせない——既存環境の設定が自動で直るかを 報告に含めさせる
    提供元は ALL_USERS ロールの初期権限を変更したが、 **既存環境には適用されない。** 「既存環境の権限設定は 自動的には変更されません」と明記されている。 パッチ適用の完了報告だけを受け取っていると、 **権限設計が古いまま残っている事実が見えない**
    取るべき行動 脆弱性対応の報告様式に「**提供元が推奨する設定変更の有無**」と 「それを実施したか」の2欄を追加する。 設定変更が必要な案件は、パッチ適用とは別のタスクとして 完了を追跡する
  • 保守サポートが切れた運用基盤を、「回避策で守っている資産」として明示的に管理する
    本件では ver.6.2／6.1／6.0 の3系列に修正が提供されず、 「それより前も影響する可能性がある」とされている。 **回避策（権限設定の見直し）は修正ではなく、 設定が時間とともに崩れれば元に戻る**
    取るべき行動 保守切れの運用基盤を一覧にし、各々について 「回避策の内容」「その設定が崩れていないかを確認する頻度」 「移行計画の有無と期限」を記録する。 確認の頻度を決めていない資産は、受容のリスクを決裁者の名前で残す
  • 国産製品の脆弱性情報は JVN だけでなく提供元のお知らせまで読む体制にする
    本件では、JVN の記述は「一般ユーザに割り当て可能な特定の権限」で 止まっており、**原因の権限名（「アカウント－変更権限」）と ALL_USERS ロールの初期値は提供元のお知らせにしか書かれていない。** 報道も JVN の表現を踏襲している。 JVN や報道だけを情報源にすると、何を見直すべきか分からない

  • ALL_USERS のような「全員が入るロール」の権限を書き出して確認する
    本件の原因は、全ユーザが所属する ALL_USERS ロールに 「アカウント－変更権限」が**初期状態で**付与されていたことである。 **既定値だったため、誰も意図して付けていない。** 同じ構図は、全員が入るグループやロールを持つあらゆる製品にありうる
    取るべき行動 Hinemos では ALL_USERS ロールを含む各ロールの権限一覧と 所属ユーザを書き出す（Ver.7.x は基本機能マニュアル 4.3.3／4.3.5、 Ver.6.x はユーザマニュアル 12.2／12.6）。 他の製品でも「全員が所属する既定のロール・グループ」を探し、 その権限を同じ方法で確認する

  • 管理者ユーザのパスワード変更を、監視・通知の対象にする
    本脆弱性は**正規の API 呼び出し**で成立するため、 不正な通信としては現れない。一方で結果は 「管理者のパスワードが変わる」という観測しやすい事象である。 **検知の指標は公表されていないが、これは自組織で作れる** （本記録の評価）
    取るべき行動 Hinemos に限らず、運用管理・認証基盤の**管理者アカウントの パスワード変更・権限変更**を通知の対象にする。 変更管理の申請と突合し、申請のない変更は調査に回す手順を決める
  • 修正が提供されない ver.6.x は、回避策を「設定の監視対象」にする
    ver.6.x には修正が来ない。回避策は権限設定の見直しだが、 **設定は運用のなかで変わる。** 誰かが業務の都合で 「アカウント－変更権限」を付け直せば、脆弱性は戻る
    取るべき行動 ver.6.x の環境では、ロールの権限一覧を定期的に取得して 差分を確認する手順を作る（手作業でも四半期ごとに記録を残す）。 あわせて 7.0 以降への移行計画の期限を決める
  • Hinemos マネージャの停止が業務に与える影響を、適用前に確認する
    Hinemos は監視とジョブ実行を担う。 **マネージャを止めると、その間は監視が止まり、 スケジュールされたジョブが走らない。** 緊急パッチだからといって即時に止められるものではない
    取るべき行動 適用前に、停止時間に重なるジョブの一覧と、監視が止まることを 許容できる時間帯を洗い出す。 停止調整に時間がかかる場合は、**先に回避策（権限の見直し）だけを 入れて脆弱性を閉じ、パッチ適用は計画的に行う**
