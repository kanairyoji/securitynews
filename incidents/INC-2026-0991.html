INC-2026-0991Turla が Exchange 自体を C2 化

ロシアの FSB に結びつけられる **Turla（Snake／Secret Blizzard）** が、未公表の道具立て **Cereal** でカザフスタンとルーマニアの政府機関の **Microsoft Exchange サーバーを侵害**——**外部の指令サーバーを一切使わず、侵害した Exchange そのものを唯一の操作拠点**にし、`EdgeTransport.exe` に注入した **CerealBox** が既存のトランスポートエージェントの処理を memory 上で乗っ取って、**NATO・EU 宛の文書添付メールだけを選んで収集**していた。ESET が2026年11月10日に公表。**初期侵入の経路は特定できていない**。2026年11月11日、**ルーマニア情報局（SRI）が自国の政府機関が標的だったことを公式に確認**——国家 Cyberint センターが2025年12月に検知して止め、「機微なデータの流出は確認されず、影響を受けたメールの業務は復旧した」とした。ただし**機関名も悪用された脆弱性の識別子も示していない**

脅威・攻撃キャンペーン不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年11月10日 最終更新: 2026年11月13日

ESET（スロバキア）は2026年11月10日、これまで記録されていなかったサイバー諜報の道具立て Cereal の分析を公表しました。使っていたのは Turla（Snake、Secret Blizzard、Waterbug、Venomous Bear とも呼ばれる）で、ロシア連邦保安庁（FSB）の一部と広く評価されている集団です。ESET は Turla への帰属を高い確度としており、根拠は「Turla に公に結びつけられている別の部品が同時に使われていたこと」と「過去の Turla のマルウェアとの概念上の類似」です。

侵害が確認されたのは政府機関2組織です。

本件の際立った点は、外部の指令サーバー（C2）をまったく使っていないことです。ESET の記述を ESET の言葉で引くと、次のようになります（原文英語）。

Cereal の道具立ては、長期にわたる隠密な諜報のために注意深く組み立てられた道具である。ディスク上にほとんど何も残さず、発見されて遮断されうる外部のインフラを避け、正規の Exchange のプロセスの中に自らを隠す。

メールの収集を担う CerealBox は、Exchange のメール処理を担うEdgeTransport.exe に注入され、すでに memory 上に読み込まれているトランスポートエージェントの処理を包み込みます。新しいエージェントを登録しないため、Exchange の構成を見ても追加された要素がありません。 ESET は、この手法が他のマルウェアファミリでは記録されたことがないと述べています。

初期侵入の経路は特定できていません。 ESET は、攻撃者の接続元 IP アドレス、カザフスタンでの正確な侵害日、確認された2組織以外に被害があったかどうかも判断できないとしています。

本件の中心にあるのは、外部の指令サーバーを持たないという設計です。通常のマルウェアは外部のサーバーへ通信を出して指令を受け取るため、その通信先が検知と遮断の手がかりになります。Cereal にはそれがありません。

代わりに使われるのが、侵害した Exchange サーバーそのものです。裏口の CerealNeuron は自ら通信を出さず、OWA・Autodiscover・ActiveSync に似せた経路で入ってくるHTTPS の要求を待ち受けます。暗号化された要求が整合性の検査を通ればそれを復号して実行し、検査を通らない要求には、正常に見える Exchange のエラー画面を返します。外から探っても、不審なものは何も見えません。

ESET はこう述べています（原文英語）。

侵害された Exchange サーバーを中心の操作拠点として悪用するのは珍しい手口で、ごく一部の APT 集団しか使っていない。 Turla は過去にもこの手法の変種を使ったことがある。

さらに予備の経路として CerealHermit があります。これは CerealNeuron から通信の機能を取り除いた変種で、ディスク上の暗号化された指令ファイルを読んで、結果を書き戻します。 HTTPS の経路が使えなくなった場合の代替とみられますが、攻撃者がその指令ファイルをどうサーバーに置き、結果をどう回収するのかは ESET も説明していません。

新しいエージェントを登録せず、memory 上で既存の処理を包む原因・手口出典 [1] [2]

メールの収集を担うのが CerealBox です。

Exchange には「トランスポートエージェント」という仕組みがあり、メールの流れの中に処理を割り込ませられます。Turla は過去にもこの仕組みを悪用したことがあります（2019年に ESET が公表した LightNeuron）。

しかし CerealBox は新しいエージェントを登録しません。メール処理を担う EdgeTransport.exe に注入され、すでに memory 上に読み込まれているエージェントの処理を包み込みます。その結果、Exchange の構成を見ても追加された要素がありません。通常のメール配送も中断されません。

ESET は、この手法が他のマルウェアファミリでは記録されたことがなく、攻撃者が Microsoft のメール基盤を細部まで理解していることを示すと述べています。

収集の条件は細かく設定されていました。

  • .doc／.docx／.pdf の添付を持つメール
  • かつ、組み込みの送信者・受信者・件名・添付名の一覧に合致するもの
  • 合致したものを圧縮・暗号化してディスク上に待機させる

ルーマニアの被害組織では、この条件がNATO および EU の機関のアドレスとのやり取りに向けられていました。

隠れ方のもう1つの軸は .NET のネイティブイメージキャッシュの悪用です。CerealLoader（ディスク上で唯一、暗号化されていない .NET のファイル）は、Microsoft.Exchange.Search.Mdb.ni.dll のような名前でキャッシュに置かれ、実行環境が本物の代わりに読み込みます。ある標本は、親プロセスが Exchange の検索サービスのときだけ動き出しました。ほかに System32\wbem 配下の ncobjapi.dll・wbemcomn.dll の乗っ取り、Vtable Fixups、マネージドでないエントリポイントの利用も観測されています。

実行の部品は「1つの作業ごとに1つの実行ファイル」だった原因・手口出典 [1] [2]

実行の中核は CerealRunner です。暗号化された .NET のプログラムとその引数を内部に持ち、memory 上で展開して実行し、結果を CerealNeuron 経由で返します。

観測された作業は次のとおりです。

  • Exchange Web Services によるメールボックスの取得
  • Active Directory への問い合わせ（利用者・グループ・DNS の記録）
  • WMI への問い合わせ
  • LSA Secret の抽出（端末に保存された認証情報）
  • ボリュームの複製の一覧表示
  • ファイルの操作（待機させたメールの束の管理を含む）

注目すべきは、作業ごとに別の実行ファイルが用意されていたことです。ESET はこう述べています（原文英語）。

ほぼ同一の実行ファイルが大量にあり、それぞれが特定の作業のためにコンパイルされていることは、運用者が内部に、指令のコンパイルと梱包を自動化する枠組みを持っていることを強く示している。

相互に差し替え可能なモジュール部品を中心に組まれたコードベースと合わせると、受ける印象は成熟した、よく設計された基盤であり、寄せ集めのスクリプト群ではない。

つまり使い捨ての実行ファイルを、指令のたびに自動で作って送り込む運用です。これは検体のハッシュ値による検知が効きにくいことを意味します。1つの指令に1つの実行ファイルなら、同じハッシュ値は二度と現れません。

以下は本記録の作成者の評価です。

本件の標的像は明確で、日本の組織は入っていません。ESET は2022年以降に Turla が標的とした国の約70%が旧ソビエト連邦構成国か、ソビエト連邦と歴史的に結びつきの深い欧州諸国だったと述べています。カザフスタンとルーマニアはいずれもこの区分に入ります。「日本が狙われている」と読む根拠はありません。

それでも読む価値があるのは、検知の前提が崩される部分です。オンプレミスで Exchange を運用している組織の多くは、次のような検知に頼っています。

  • サーバーからの外向き通信の宛先を、脅威情報と照合する
  • Exchange の構成（トランスポートエージェント等）の差分を取る
  • 検体のハッシュ値を照合する

本件には、この3つがいずれも効きません。

通常の検知 本件での状況
外向き通信の宛先の照合 外部の指令サーバーが無い
構成の差分 新しいエージェントを登録しない（memory 上で既存の処理を包む）
ハッシュ値の照合 1指令1実行ファイルで自動生成されるため同じ値が現れない

残るのは、端末側で何が起きているかを見る検知です。具体的には、EdgeTransport.exe へのプロセス注入、.NET のネイティブイメージキャッシュへの想定外のアセンブリの配置、System32\wbem 配下の DLL の乗っ取り。いずれも普段の運用点検の範囲外にあります。

そして指令そのものは、OWA・Autodiscover・ActiveSync に似せた経路へのHTTPS の要求として届きます。Exchange のアクセス記録には、正規の利用と同じ見た目で並びます。検査を通らない要求には正常なエラー画面が返るため、外部からの走査でも見つかりません。

本記録としての読み方は1つです。「侵害されたときに自組織で何が残るか」を、手口ごとに確かめておく。 本件の構図では、外向き通信の記録を何年保存していても手がかりになりません。必要なのは、Exchange サーバー上のプロセスとアセンブリの読み込みの記録であり、それを取っているかどうかは今日確認できます。

    **ESET は外部の指令インフラを一切観測していない。** 指令は OWA・Autodiscover・ActiveSync に似せた経路への 入ってくる HTTPS の要求として届き、 結果はその応答として返る。**外向きの異常な通信は発生しない。** 検査を通らない要求には正常に見える Exchange のエラー画面が返るため、 外部からの走査でも見つからない

    取るべき行動 ESET が公開した侵害指標（IoC）で照合するのは当然として、 **振る舞いに基づく検知**（memory 上での .NET アセンブリの読み込み、 プロセス注入、LSA Secret へのアクセス）を併用する。 ハッシュ値の照合で「該当なし」だったことを安全の根拠にしない

    取るべき行動 Exchange サーバーで LSA の保護機能を有効にする。 あわせてサーバー上に保存されている認証情報を棚卸しし、 必要最小限の権限しか持たないアカウントに置き換える
