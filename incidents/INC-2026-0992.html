**Recorded Future（Insikt Group）は2026年11月10日、 VMware ESXi を狙う未文書化の侵入後フレームワーク「GhostFrame」を公表した**（出典1）。 **脆弱性を突くものではなく、すでに root を取った ESXi ホストに置く実装で、 ホスト1台の上で動く複数の仮想マシンへ横から入り、 スナップショットや仮想ディスクから認証情報を抜き、 SOCKS5 で奥へ中継する**（出典1）。 **Insikt Group はこれを TAG-218 のインフラ監視の過程で見つけており、 同グループの活動は Settra ランサムウェアと重なるとしている**（出典1） ——**ただし本フレームワークが Settra 専用であると立証はされていない**（出典1）。 **本記録がこの事案の中心と見るのは、攻撃の作業場が 「仮想マシンの中」から「仮想マシンの下」へ移っていることである**（本記録の評価）—— **ESXi ホストに置かれた実装は、ゲスト OS に入れた EDR から見えない層にあり、 ホスト1台の掌握が、その上の全ゲストとそのデータへの到達を同時に意味する**（出典1）。 **もう1つは、この実装が検知回避を「設定の書き換え」ではなく 「約5秒ごとの書き戻し」で維持していることである**（出典1）—— **ファイアウォールと execInstalledOnly を手で戻しても、 永続化の本体（/opt/vmhostd-core と /etc/rc.local.d/local.sh）を消さなければ 数秒で元に戻る**（出典1）。 **初期侵入は米国と欧州の VPN 機器（SonicWall・Palo Alto Networks・Fortinet が中心）で、 標的のうち4組織が後に Settra のリークサイトへ掲載されている**（出典1）。

Recorded Future の Insikt Group は2026年11月10日、VMware ESXi 環境を標的とする、これまで文書化されていなかった侵入後フレームワーク「GhostFrame」を公表しました（出典1）。

GhostFrame は、攻撃者が ESXi ホストの root 権限を得たあとに置く実装です（出典1）。公表文は「実装の配置と実行には、ESXi ホストの root 権限をすでに取得している必要がある」と述べており、実装そのものは脆弱性を突きません（原文英語。出典1）。置かれると、1つの操作画面からハイパーバイザ上の仮想マシンへ到達し、認証情報を収集し、コマンドを実行し、被害組織のネットワークの奥へ中継できるとされています（出典1）。

Insikt Group は、TAG-218 という脅威活動グループのインフラを監視する過程でGhostFrame を見つけたとしています（出典1）。TAG-218 の活動は Settra ランサムウェアと重なるとされますが、公表文は「入手できた証跡は、本フレームワークが Settra 専用であることを立証していない」としています（原文英語。出典1）。

日本の CISO・技術者にとっての読みどころは2つあります。

1つは、攻撃の作業場が仮想マシンの「中」から「下」へ移っていることです（本記録の評価）。ゲスト OS に入れた EDR は、ESXi ホスト上で動くプロセスを見ません。 一方で、ホスト1台の掌握は、その上で動く全ゲストと、そのゲストが抱えるデータへの到達を同時に意味します（出典1）——公表文も「単一の侵害された ESXi ホストが、複数の仮想マシンとそれらが含むシステム・データへのアクセスを与えうる」と書いています（原文英語。出典1）。

もう1つは、検知回避の維持のしかたです（出典1）。この実装は ESXi のファイアウォールと execInstalledOnly（署名済み実行ファイルのみを許す制御）を、およそ5秒ごとに無効へ書き戻します（出典1）——設定を手で戻すだけの対処では、数秒で元に戻ります（本記録の評価）。公表文も「設定を再有効化するだけでなく、永続化の仕組みそのものを調査せよ」と勧めています（原文英語。出典1）。

攻撃の作業場が、仮想マシンの「中」から「下」へ移っている原因・手口

GhostFrame が置かれるのは ESXi ホストである（出典1。事実）。

公表文は「単一の侵害された ESXi ホストが、複数の仮想マシンと、 それらが含むシステム・データへのアクセスを与えうる」と述べ、 「仮想マシンを個別に侵害することなく、 被害環境全体へアクセスを広げうる」としている（原文英語。出典1）。

本記録の評価では、ここに2つの含意がある。

①見えない。 ゲスト OS に入れた EDR は、 ESXi ホスト上で動くプロセスを見ない。 実装はメモリ上でシェルコードを読み込んで動き、 プロセス名を vmhostd に変えて VMware の vmware-hostd に似せる （出典1） ——ホスト側を見る仕組みを別に持たない限り、 この層の観測点は0である。

②1台が全部になる。 VMkatz は仮想マシンのスナップショットと ディスクから NTDS.dit のデータまで取り出すとされる（出典1） ——ドメインコントローラにログインしなくても、 その中身が手に入る形である。

したがって、ハイパーバイザは「仮想マシンを載せる台」ではなく、 その上の全資産と同じ重みを持つ資産として扱う必要がある （本記録の評価）。

脆弱性ではなく、root を取られた後の「居座り方」が中核である評価・解釈

公表文は「実装の配置と実行には、ESXi ホストの root 権限を すでに取得している必要がある」と明記し、 実装は脆弱性を突かないとしている（原文英語。出典1。事実）。

本記録の評価では、この性質が対策の形を決める。

CVE の番号で管理する運用では、この脅威は拾えない。 影響を受けるバージョンが無く、適用すべきパッチも無い。 代わりに問うべきは「ESXi ホストの root に、 誰がどの経路で到達できるか」である（本記録の評価）。

居座り方の具体は3点に集約されている（出典1。事実）—— ①/opt/vmhostd-core への複製と /etc/rc.local.d/local.sh の書き換え。 ②/sbin/auto-backup.sh の実行による、再起動をまたいだ保持。 ③ファイアウォールと execInstalledOnly を、 およそ5秒ごとに無効へ書き戻すこと。

③が運用に対して持つ意味は大きい（本記録の評価） ——設定が無効になっていることに気づいて手で戻しても、 数秒で元に戻る。 「直したのに直らない」という形で現場の時間が溶け、 原因（永続化の本体）は残る。 公表文が「設定を再有効化するだけでなく、 永続化の仕組みそのものを調査せよ」と勧めているのは、 この構造への警告である（原文英語。出典1）。

C2 の「同一宛先へ6ポート同時」は、正規の通信にほぼ現れない形である対策・注意喚起

実装は 53・2222・3389・4444・8443・9443 の6ポートへ 同時に TCP 接続を試み、最初に成功した接続を C2 に使い、 残りを閉じる（出典1。事実）。 30秒のうちにどれもつながらない場合は、 5〜12秒のランダムな間隔を置いて再試行する（出典1）。 結果として、1つの宛先 IP へ6本の SYN がほぼ同時に出る（出典1）。

本記録の評価では、これは条件が具体的で誤検知が少ない検知規則になる。 業務の通信で、1台のホストが同一の宛先に対して 53（DNS）・2222・3389（RDP）・4444・8443・9443 を 同時に叩くことはほぼ無い。

ただし前提がある（本記録の評価） ——ESXi ホストの外向き通信がフローログに載っていなければ、 この形は誰にも観測されない。 「ESXi の通信を記録しているか」を先に確かめる必要がある。

間隔がランダム（5〜12秒）である点も踏まえておきたい（出典1） ——ビーコンの周期性だけを見る検知では拾いにくい。 拾えるのは周期ではなく、ポートの組み合わせの形である （本記録の評価）。
