INC-2026-1003Movable Type に PHP コード実行

**シックス・アパートは2026年11月11日、CMS「Movable Type」のダイナミックパブリッシング機能に コードインジェクションの脆弱性（CVE-2026-117687・CWE-94）があったことを公表し、 同時に修正版 8.8.7 / 8.0.14（Premium 2.19）を提供した。** **細工されたリクエストで、製品が動作するサーバ上で任意の PHP コードが実行される可能性がある** （JVN#11786640）。 **対象は 8.8.6 以前・8.0.13 以前・Premium 2.18 以前で、サポートが終了した 8.4.x 系と Movable Type 7 も影響を受ける。Movable Type 9 は影響を受けない。** **設定ディレクティブ DynamicTemplateAllowPHP を 0 にしている環境では、 修正前の時点でこの実行は起きていなかった**（ベンダーのリリースノート）。

脆弱性初報のみ日本の組織が当事者設計・実装上の不備
初報: 2026年11月11日（シックス・アパートの告知および JVN#11786640 の公表。同日） 最終更新: 2026年11月11日（本記録の作成時点）

シックス・アパート株式会社の CMS 「Movable Type」のダイナミックパブリッシング機能に、 コードインジェクションの脆弱性（CWE-94）が存在する（出典2）。 CVE 番号は CVE-2026-117687、CVSS v4.0 基本値 6.9 （CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:L/VI:L/VA:L/SC:N/SI:N/SA:N）、 CVSS v3.0 基本値 7.3（CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L）である（出典2）。 「ダイナミックパブリッシング機能において、攻撃者に細工されたリクエストを送信されると、 当該製品が動作するサーバ上で任意の PHP コードが実行される可能性があります」（出典2。原文日本語を引用）。 対象は 8.8.6 およびそれ以前（8.8.x 系・Advanced を含む）／8.0.13 およびそれ以前（8.0.x 系）／ Movable Type Premium 2.18 およびそれ以前（2.x 系・Advanced Edition を含む）で、 サポート終了済みの Movable Type（Advanced）8.4.x 系および Movable Type 7 も影響を受ける（出典2）。 Movable Type 9 は影響を受けない（出典2）。 修正版は 8.8.7 / 8.0.14 / Premium 2.19（出典1・2・3）で、 JVN は回避策として「DynamicTemplateAllowPHP に 0 を設定することが開発者により推奨されている」と 記載している（出典2）。 実際の悪用が観測されたという記述は、出典1〜3 のいずれにも無い（本記録の確認）。

修正版の提供と JVN 公表が同日で、読んだ時点で手当てができる対策・注意喚起出典 [1] [2] [3]

公表は同じ日に揃っている。シックス・アパートの告知が2026年11月11日11:00（出典1）、JVN#11786640 の公表も同日（出典2）、リリースノートの掲載も同日である（出典3）。間隔は0日である（本記録の算出。figures 参照）。

この順序は、利用者が情報を読んだ時点で対策を実行できる形である（本記録の評価）。再現手順が公表されていないこと〈未確定3〉も、公表から適用までの間に悪用される余地を狭める方向に働く。

ただし、適用そのものに副作用が明示されている点が本件の注意点である（本記録の評価）。出典1・3 はいずれも「ダイナミックパブリッシングの表示や動作が変わる可能性がある」と述べている（出典1・3）。修正の内容が「テンプレート処理結果の PHP を実行しない」ことである以上、その実行に依存していたサイトでは出力が変わる（本記録の整理）。急いで当てる対象だが、確認なしで本番へ当てる対象ではない。

直されたのは「処理結果を PHP として評価していた」設計である原因・手口出典 [2] [3]

リリースノートの記述は次のとおりである（出典3。原文英語を訳出）。

「設定ディレクティブ DynamicTemplateAllowPHP が 1 に設定されている場合に、以下の MT タグ・修飾子・エラー表示処理において、テンプレート処理結果に含まれる PHP コードが実行される問題を修正した（CVE-2026-117687, MTC-31851）」

対象は MTInclude・MTIncludeBlock・MTWidgetSet・MTWidgetManager・MTFileTemplate・MTUserSessionCookieDomain・MTUserSessionCookiePath の7タグ、mteval 修飾子、そしてダイナミックパブリッシングのエラーテンプレート（404 など）である（出典3）。

1つの関数の入力検証漏れではなく、テンプレートの読み込み・展開・エラー表示という複数の経路が横並びで影響している（本記録の評価）〈重要〉。これは「どこで値を検証するか」の問題ではなく、処理結果を PHP として評価する経路が広く存在していたことを示す（本記録の整理）。CWE-94（コード生成の制御不備）という分類もこれに対応する（出典2）。

自組織のテンプレート処理基盤に同じ型の問題がないかは、「ユーザー入力が最終的に評価系（eval・インクルード・テンプレートの二次展開）へ届くか」で点検できる（本記録の推奨）。

DynamicTemplateAllowPHP は「0 なら安全」ではなく、修正後に意味が変わる対策・注意喚起出典 [2] [3]

設定の扱いは2つの資料で説明が分かれているので、順に並べる。

JVN は回避策として「DynamicTemplateAllowPHP に 0 を設定することが開発者により推奨されています」と記載している（出典2）。リリースノートは、修正前の挙動について「DynamicTemplateAllowPHP が 0 に設定されていた場合、テンプレート処理結果に含まれる PHP コードは、この修正の前は実行されていなかった」と述べている（出典3。原文英語を訳出）。この2つは整合する（本記録の整理）——0 にすれば、修正前でも当該実行は起きない。

問題は修正後である。出典3 は続けて、修正適用後は、例外条件に該当すると 0 の設定でもPHP コードが実行されるようになると注意している（出典3）。例外条件は、①サイトのインクルード方式が PHP で MTInclude／MTIncludeBlock にssi="1" が指定されている場合、②読み込み先テンプレートの Server Side Includes 設定（include_with_ssi）が有効な場合（MTWidgetSet・MTWidgetManager では各ウィジェットの設定）である（出典3）。

つまり、設定値の意味がバージョンの前後で変わる（本記録の評価）〈重要〉。「0 にしてあるから影響なし」で止めると、更新後に挙動が変わったことに気づけない。回避策は修正版を当てるまでの時間稼ぎとして使い、更新後は SSI 関連の設定とあわせて動作を確認するのが筋である（本記録の推奨）。

サポートが終了した系列も影響を受けるが、修正版は示されていない被害規模・影響範囲出典 [1] [2]

JVN の影響範囲には、サポート対象の3系列に加えてサポート終了済みの Movable Type（Advanced）8.4.x 系および Movable Type 7 が挙げられている（出典2）。一方、修正版として示されているのは 8.8.7 / 8.0.14 / Premium 2.19 の3つである（出典1・2・3）。

終了済み系列の利用者に提示されている手段は、JVN の回避策と移行だけである（本記録の整理）〈未確定4〉。ベンダーの告知（出典1）は終了済み系列に言及していない（本記録の確認）。

なお、Movable Type 8.0 系は2026年11月5日に EOL を迎えているが、本件については修正版 8.0.14 が提供されている（出典1）。EOL の直後に修正が出た形で、同じ「サポート終了」という語でも扱いが違う（本記録の整理）。自組織の資産台帳では、製品の版だけでなくその版が修正の提供対象かどうかを持つ必要がある（本記録の推奨）。

「任意のコード実行」と CVSS の影響評価（いずれも低）が同時に並ぶ評価・解釈出典 [2]

JVN が示す想定影響は「当該製品が動作するサーバ上で任意の PHP コードが実行される可能性」である（出典2）。一方、CVSS の評価は v4.0 で VC:L／VI:L／VA:L、v3.0 で C:L／I:L／A:L、基本値は 6.9／7.3 である（出典2）。

サーバ上での任意コード実行という影響と、機密性・完全性・可用性がいずれも「低」という評価が同じページに並んでいる（本記録の整理）〈重要〉。この評価の根拠は公表されていない（本記録の確認）。

社内の優先度判定を CVSS の数値だけで回している組織では、本件は「7点台の案件」として他の多数の脆弱性に埋もれる余地がある（本記録の評価）。判定には「認証が要るか（PR:N）」「利用者の操作が要るか（UI:N）」「公開サーバで動いているか」を別軸で見る必要がある（本記録の推奨）——本件はいずれも攻撃側に有利な側に振れている。

CISO・経営層への示唆
  • 「認証不要・操作不要でサーバ上のコード実行」は、CVSS の影響評価が低でも 公開サーバでは最優先に扱う。
    **本件は PR:N・UI:N でネットワーク経由（AV:N）であり、 想定影響はサーバ上での任意 PHP コード実行である**（出典2）〈重要〉—— **一方 CVSS の機密性・完全性・可用性の評価はいずれも「低」で、 基本値は 6.9／7.3 にとどまる**（出典2）。 **数値だけで並べると、公開 CMS の前提条件の悪さが消える**（本記録の評価）。
    取るべき行動 **脆弱性の優先度判定に「インターネットから到達できる資産か」 「認証・利用者操作が前提に要るか」を CVSS とは別の軸で入れる。** **公開 CMS は、中程度の評点でも即日適用の候補として扱う。**
  • 修正の適用に「表示が変わる」副作用があると明記された更新は、 適用の意思決定を技術部門だけに任せられない。
    **出典1・3 はいずれも、ダイナミックパブリッシングの表示や動作が変わる可能性を 明記している**（出典1・3）〈重要〉—— **公開サイトの見た目が変わる判断は、広報・事業側の合意が要る**（本記録の評価）。 **合意の調整に日数がかかると、その間は脆弱なまま残る。**
    取るべき行動 **「公開サイトの表示が変わりうる緊急更新」の承認経路を、平時に決めておく。** **検証環境での確認・暫定の回避策・適用の期限をセットで判断する運用にする。**
  • サポート終了済みの版が影響範囲に含まれる脆弱性は、資産台帳の精度がそのまま 残存リスクになる。
    **本件は 8.4.x 系と Movable Type 7 も影響を受けるが、これらの修正版は示されていない** （出典2）〈未確定4〉—— **8.0 系は2026年11月5日に EOL を迎えた直後に修正版が提供されており、 同じ「終了」でも扱いが違う**（出典1）。 **台帳に「版が修正提供の対象か」が無いと、どれが残るのか判断できない**（本記録の評価）。
    取るべき行動 **CMS・業務システムの資産台帳に、版だけでなく 「サポート期限」「修正提供の対象か」の2項目を持たせる。** **期限切れの版については、移行計画の有無を経営の報告項目にする。**
  • 自社サイトの構築・運用を外部に委託している場合、脆弱性情報は委託先経由でしか届かない。 到達の確認は委託元の責任として残る。
    **本件の公表は JVN とベンダーの告知ページである**（出典1・2）—— **サイトの運用を制作会社に委ねている組織では、 この情報を受け取る窓口が社内に無いことがある**（本記録の評価）。 **クラウド版は提供側でアップデート済みだが、 ソフトウェア版・AMI 版は利用者側の作業である**（出典1）。
    取るべき行動 **委託契約に「利用製品の脆弱性公表時の通知と適用の責任分担」を明記する。** **自社サイトがクラウド版かソフトウェア版かを把握し、 後者なら適用状況の報告を受け取る。**
セキュリティ技術者への示唆
  • テンプレートエンジンの「処理結果」を再評価する経路を洗い出す。 本件はそこに不備があった。
    **修正の対象は、インクルード系4タグ・ファイルテンプレート・ セッションCookie関連2タグ・mteval 修飾子・エラーテンプレートに広がっている**（出典3）〈重要〉—— **1か所の検証漏れではなく、処理結果を PHP として評価する経路が複数あったことを示す** （本記録の整理）。
    取るべき行動 **自社のテンプレート処理で、①展開結果を再度テンプレート／コードとして評価する箇所、 ②エラーページの生成経路、③インクルード先の読み込み経路 を列挙する。** **利用者が内容に影響を与えられる値が、これらに到達するかを確認する。**
  • 更新後は DynamicTemplateAllowPHP と SSI 設定の組み合わせを実機で確認する。 設定値の意味が版の前後で変わる。
    **出典3 は、修正適用後は 0 の設定でも例外条件に該当すると PHP コードが実行されるようになると注意している**（出典3）〈重要〉—— **例外条件は、PHP インクルード方式＋`ssi="1"` の指定、 または読み込み先テンプレートの `include_with_ssi` 有効である**（出典3）。
    取るべき行動 **更新前に、サイトのインクルード方式・`ssi="1"` の指定箇所・ ウィジェットごとの `include_with_ssi` 設定を棚卸しする。** **更新後に、該当するテンプレートの出力を実機で比較する。**
  • ダイナミックパブリッシングが必要なければ、機能自体を止めるのが一番確実である。
    **本件の前提はダイナミックパブリッシング機能の利用である**（出典2・3）—— **静的公開のみで足りるサイトでは、攻撃面を持たずに済む**（本記録の評価）。 **回避策（DynamicTemplateAllowPHP に 0）も、機能を使わない構成では判断が単純になる。**
    取るべき行動 **ダイナミックパブリッシングを使っているテンプレート・アーカイブを特定し、 不要な箇所は静的公開へ戻す。** **使う必要がある箇所だけを残し、到達経路を WAF・アクセス制限で絞る。**
  • 公開 CMS の更新は「適用した」ではなく「稼働中の版が修正版か」で確認する。
    **対策はアップデートである**（出典2）—— **ソフトウェア版は別ディレクトリへのインストールが案内されており、 切り替えが済むまで旧版が動いたままになりうる**（出典1。本記録の整理）。 **クラウド版は提供側で完了している**（出典1）。
    取るべき行動 **稼働中のドキュメントルートと mt-config.cgi の参照先を確認し、 管理画面のバージョン表記で修正版であることを確かめる。** **旧ディレクトリを残す場合は、外部から到達できない状態にする。**
