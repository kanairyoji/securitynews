公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表されている範囲は次のとおりである**（出典2・3）。 攻撃者が細工されたメッセージファイルを送り、利用者がそれを影響を受ける版の Outlook で開く。 Outlook は通常表示される外部コンテンツの警告を出さずに、 攻撃者の管理するネットワーク位置へ接続する。 その接続の過程で利用者の NTLMv2 ハッシュが攻撃者に渡り、 攻撃者はそれを使って当該利用者として認証できる。 **プレビューウィンドウは攻撃経路にならない**（出典2）。 **実際に観測された攻撃の内容（攻撃者・標的・時期）は公表されていない**〈未確定1〉。

1,342 件のうち急ぐのは1件で、その1件は評点では目立たない評価・解釈出典 [1] [2] [3] [4]

数の構造はこうである（出典1。集計は本記録）。

  • 収載 CVE: 1,342 件
  • うち Microsoft の影響分類を持つもの: 1,095 件
  • うち第三者（Chromium 等）の再掲: 247 件
  • 深刻度: Critical 68・Important 1,117・Moderate 110・Low 47
  • 実環境での悪用が記録されているもの: 1 件（CVE-2026-124194）
  • 修正前に公開されていたもの: 0 件

悪用された1件の CVSS 基本値は 6.5、深刻度は Moderate である（出典2）。Critical 68 件より低い評点であり、深刻度順に並べた一覧では68件より後ろに来る（本記録の整理）〈重要〉。

一方で CISA は同日この1件を KEV に収載し、2026年11月24日の期限を付けた（出典4）。JPCERT/CC も注意喚起で名指ししている（出典3）。「評点」と「いま攻撃に使われているか」は別の軸であり、月例更新の着手順を決めるのは後者である（本記録の評価）。

社内の判断に使うなら、月例の一覧から最初に抜くべきは「Exploited:Yes」と「KEV 収載」の2つのフラグである（本記録の推奨）。

警告が出ないことが本体で、利用者側には気づく手がかりがない原因・手口出典 [2] [3]

Microsoft の説明は次のとおりである（出典2。原文英語を訳出）。

「認証されていない攻撃者が細工されたメッセージファイルを送り、影響を受ける版の Microsoft Outlook で開かせる可能性がある。ファイルを開くと、Outlook が通常表示される外部コンテンツの警告を出さずに攻撃者の管理するネットワーク位置へ接続し、利用者になりすますのに使える認証情報が漏えいするおそれがある。悪用にはネットワーク接続と利用者の操作が要る」

JPCERT/CC はこれを CWE-356（安全でない操作をユーザーに警告しない）と記している（出典3）。

つまり、不備は「外部へ接続する前に出るはずの警告が出ない」ことにある（本記録の整理）〈重要〉。利用者教育の観点では、ここが難所である—— 警告が出ないのだから、利用者が「怪しい」と判断する材料は画面に現れない（本記録の評価）。唯一の手がかりは、添付ファイルそのものの出自である。

残る防御は端末の外側にある。外向きの SMB／WebDAV を遮断していれば、接続自体が成立しない（本記録の整理。なおこの推奨は Microsoft の勧告には記載されていない）。この型（開くと外部へ認証を取りに行く）は過去にも繰り返し現れており、境界での遮断は個別の CVE に依存しない対策になる（本記録の評価）。

悪用の中身は公表されていない——「検知された」以外は分からない未確定事項出典 [1] [2] [3] [4]

公表されているのは、CVRF の Exploit Status が「Publicly Disclosed:No / Exploited:Yes」であり、最新の状態が「Exploitation Detected」であることだけである（出典1・2）。

攻撃者の帰属・標的の業種や地域・観測の開始時期・被害の件数は、いずれも示されていない〈未確定1〉。CISA KEV の「ランサムウェアキャンペーンでの使用」も "Unknown" である（出典4）。JPCERT/CC の注意喚起も「悪用されていることを公表しています」と伝えるに留まる（出典3）。

本DBがこの区別を明示するのは、「悪用が確認された」という語が「広く攻撃が観測されている」と読まれることがあるためである（本記録の整理）〈重要〉。本件で確認できるのは、Microsoft が悪用を検知し、CISA が2週間の期限を付けた、という2点である。

この材料で判断できることは限られる。標的が絞られているのか広いのかが分からないため、「自社が標的か」ではなく「当てていないなら当てる」で動かすしかない（本記録の評価）。

報道の件数は一致しない——数える範囲が違う評価・解釈出典 [1] [5] [6]

今月の件数として報じられた値は次のように分かれている。

  • 本記録の集計（CVRF 文書）: 1,342 件（出典1）
  • SecurityWeek: 1,094 件（出典5）
  • BleepingComputer: 1,235 件（出典6）

本記録が CVRF を分解した結果、影響分類を持つ CVE は 1,095 件、持たない（Chromium 等の再掲）CVE は 247 件だった（出典1。集計は本記録）。SecurityWeek の 1,094 件は前者とほぼ一致する（差は1件）（本記録の整理）。BleepingComputer は「当日公開分のみを数え、月内に先行して公開された108 件（Entra Device Registration 1・Mariner 82・Microsoft Edge 25）を除く」と明記している（出典6）——1,342 件から 108 件を引くと 1,234 件になる（本記録の算出）。

どの数字も誤りではなく、数える範囲が違う（本記録の評価）〈重要〉。運用上の意味もそれぞれ異なる——第三者 CVE の再掲を含む 1,342 件は「今月この文書で扱われた総量」、1,095 件は「Microsoft 製品として分類された数」、1,235 件は「当日の配信で向き合う数」である（本記録の整理）。

社内の報告に件数を使うなら、出所と数え方を併記する必要がある（本記録の推奨）。件数そのものは作業量の目安にもならない——1つの更新プログラムが複数の CVE を直すためである（本記録の注記）。

ベンダーの謝辞に、発見に用いた生成AIの名が入っている（出典2）〈重要〉。SecurityWeek も「Sevens への謝辞は Anthropic の Claude AI モデルの使用に言及している」と報じている（出典5）。

件数の増加が発見手法の変化によるものだとすると、受け手側の運用（毎月の選別と適用）の設計を変える必要がある（本記録の評価）—— 1,000 件規模を毎月「全件検討する」前提は維持できない。選別の基準を悪用・KEV・外部露出の3点に固定し、残りは定常の更新サイクルに流すのが現実的である（本記録の推奨）。

事案の詳細

影響を受けたシステム
名称: Microsoft Outlook（Microsoft 365 Apps for Enterprise / Office LTSC 2021 / Office LTSC 2024）　ベンダー: Microsoft Corporation　CVE番号: CVE-2026-124194　バージョン: **影響: Microsoft 365 Apps for Enterprise（32ビット・64ビット）、 Microsoft Office LTSC 2021（32ビット・64ビット）、 Microsoft Office LTSC 2024（32ビット・64ビット）**（出典2）。 **修正: 2026年11月10日の月例更新**（出典1・2）。 **チャネル別のビルド番号は本記録では整理していない**〈未確定3〉。　概要: **危険な操作の前に利用者へ警告しない不備（Microsoft の分類は "Product ui does not warn user of unsafe actions"、 JPCERT/CC は CWE-356 と記載）による、ネットワーク経由のなりすまし**（出典2・3）。　症状: **「認証されていない攻撃者が細工されたメッセージファイルを送り、 影響を受ける版の Outlook で開かせると、通常表示される外部コンテンツの警告なしに 攻撃者の管理するネットワーク位置へ接続し、 利用者になりすますのに使える認証情報が漏えいする可能性がある」**（出典2。原文英語を訳出）〈重要〉—— **Microsoft は機密性への影響が High である理由を 「利用者の NTLMv2 ハッシュを攻撃者に開示し、攻撃者はこれを使って 当該利用者として認証できる」と説明している**（出典2。原文英語を訳出）。　手法: **公表されているのは、細工されたメッセージファイルを開かせる経路までである**（出典2）。 **プレビューウィンドウは攻撃経路にならない**（出典2）〈重要〉—— **成立には利用者がファイルを開く操作が要る（CVSS の UI:R）**（出典2）。 **攻撃者が用意するネットワーク位置の形（SMB・WebDAV 等）は公表されていない** （本記録の確認）〈未確定1〉。　内容: **攻撃者が得るのは利用者の NTLMv2 ハッシュである**（出典2）—— **これを使って当該利用者として認証できる（リレー）、 あるいはオフラインで解析してパスワードを得る経路がある**（本記録の整理。 後者の手順は公表されていない）。 **CVSS では完全性・可用性への影響は無しと評価されている（I:N／A:N）**（出典2）。　preconditions: **影響を受ける版の Outlook で、送られたメッセージファイルを利用者が開くこと**（出典2）。 **悪用にはネットワーク接続と利用者の操作が要る**（出典2）—— **外部への SMB／認証の送出が許されている環境であること**（本記録の整理。 Microsoft の勧告にこの前提の記述は無い）。
緩和策
手順: **2026年11月の月例更新を適用する**（出典1・3）—— **JPCERT/CC は Microsoft Update／Windows Update による適用を案内している**（出典3）。　副作用: **1,342 件という規模の更新は、適用のための再起動と検証の負荷を伴う**（本記録の評価）—— **全件を同時に当てる前提では着手が遅れるため、 悪用1件を含む Office／Outlook 系を先に出す判断が要る**（本記録の推奨）。
手順: **境界で外向きの SMB（445/tcp 等）と認証の送出を止める**（本記録の推奨）。　副作用: **外部のファイル共有・一部のクラウドストレージ連携が使えなくなる場合がある** （本記録の評価）—— **NTLM ハッシュの漏えい型の脆弱性は過去にも繰り返し現れており、 境界での遮断は個別の CVE に依存しない対策になる**（本記録の整理。 Microsoft の勧告にこの推奨は記載されていない）。
手順: **NTLM への依存を減らす（Kerberos／最新の認証方式への移行、 NTLM の送出制限ポリシーの適用）**（本記録の推奨）。　副作用: **古い業務システム・NAS との互換性が崩れる余地があり、 棚卸しと段階的な移行が要る**（本記録の評価）—— **短期の手当てにはならない。**

CISO・経営層への示唆
  • 月例更新の着手順は CVSS ではなく「悪用されているか」で決める。 本件の悪用1件は評点では68件の Critical より下に来る。
    **悪用が記録されているのは1,342 件中1件（CVE-2026-124194）で、 その CVSS は 6.5・深刻度 Moderate である**（出典1・2）〈重要〉—— **一方 CISA は同日 KEV に収載し、2週間（2026年11月24日）の期限を付けた**（出典4）。 **評点順の一覧では、急ぐべき1件が埋もれる**（本記録の評価）。
    取るべき行動 **月例の脆弱性一覧から「悪用あり」「KEV 収載」の2フラグで最初の処理対象を抜く運用にする。** **残りは定常の更新サイクルに流し、全件を個別に検討する前提を捨てる。**
  • 件数を社内報告に使うなら、出所と数え方を必ず添える。 同じ月で 1,094・1,235・1,342 の3つの数字が流通している。
    **本記録の CVRF 集計は 1,342 件、SecurityWeek は 1,094 件、 BleepingComputer は 1,235 件である**（出典1・5・6）〈齟齬1〉—— **第三者 CVE の再掲を含むか、当日公開分のみかで差が出る**（本記録の整理）。 **件数は作業量の指標にもならない（1つの更新が複数の CVE を直す）**（本記録の注記）。
    取るべき行動 **経営報告の指標を「件数」から「悪用あり・KEV 収載の件数と適用状況」へ置き換える。** **件数を載せる場合は、数え方の定義を脚注に固定する。**
  • 認証情報が外部へ流れる型の脆弱性は、端末の更新だけでなく 境界での遮断とNTLM依存の削減をセットで判断する。
    **本件で攻撃者が得るのは利用者の NTLMv2 ハッシュであり、 これで当該利用者として認証できる**（出典2）〈重要〉—— **同じ型（開くと外部へ認証を取りに行く）は過去にも繰り返し現れている** （本記録の評価）。 **更新だけを対策にすると、次の同型の脆弱性でまた同じ作業をすることになる。**
    取るべき行動 **外向きの SMB（445/tcp）・WebDAV を境界で遮断し、例外の一覧を持つ。** **NTLM の送出制限と Kerberos・フィッシング耐性認証への移行を、 個別の CVE とは別の恒久施策として予算化する。**
  • 「悪用が確認された」だけでは自社が標的かを判断できない。 判断を待つのではなく、当てる前提で動かす。
    **Microsoft の勧告には観測された攻撃の内容が記載されていない**（出典2）〈未確定1〉—— **攻撃者・標的・時期・件数はいずれも非公表で、 CISA KEV のランサムウェア使用も "Unknown" である**（出典4）。 **標的が絞られているかどうかが分からない**（本記録の評価）。
    取るべき行動 **KEV 収載かつ自社で稼働している製品については、 標的情報の有無を判断材料にしない運用にする（期限内の適用を既定とする）。** **情報が出たら対応を見直す、という順序にしない。**
セキュリティ技術者への示唆
  • Outlook の更新は「配信した」ではなく、チャネルごとのビルドで確認する。
    **影響製品は Microsoft 365 Apps for Enterprise（32/64）・ Office LTSC 2021・Office LTSC 2024 である**（出典2）—— **更新チャネルによって配信の時期とビルドが異なる**（本記録の整理。 チャネル別のビルド番号は本記録では整理していない）〈未確定3〉。
    取るべき行動 **M365 Apps の更新チャネル（Current／Monthly Enterprise／Semi-Annual）ごとに、 対象ビルド以上であることを端末台帳で集計する。** **LTSC 版は別の更新経路になるため、分けて確認する。**
  • 警告が出ない脆弱性は端末側で検知できない。見るのは外向きの通信ログである。
    **本件は「通常表示される外部コンテンツの警告が出ない」ことが本体である**（出典2）〈重要〉—— **利用者にも端末にも異常は現れず、現れるのは外部ホストへの接続だけである** （本記録の評価）。 **プレビューウィンドウは攻撃経路にならないため、閲覧だけでは成立しない**（出典2）。
    取るべき行動 **プロキシ・ファイアウォールで、外部宛の SMB／WebDAV／認証を伴う接続のログを 保持し、メール受信後の短時間に発生する外部接続を探せる状態にする。** **過去ログに対する遡及調査（7〜30日）を1回実施する。**
  • メッセージファイル形式の添付（.msg 等）は、ゲートウェイでの扱いを決めておく。
    **成立の前提は「細工されたメッセージファイルを利用者が開くこと」である**（出典2）—— **攻撃者が送るのはメールそのものではなくファイルであり、 本文の検査だけでは判定できない**（本記録の整理）。
    取るべき行動 **メールゲートウェイで、メッセージファイル形式の添付を隔離または無害化する方針を決める。** **業務上必要な経路（転送されたメールの保全等）を洗い出し、例外を明示する。**
  • 毎月1,000件規模の一覧を処理する前提で、自動の選別を作る。
    **今月の収載は 1,342 件、うち Microsoft 分類が 1,095 件である**（出典1。本記録の算出）—— **前月（2026年10月）は 1,413 件だった**（関連記録 INC-2026-0510）。 **人手で全件を読む運用は維持できない**（本記録の評価）。
    取るべき行動 **MSRC の CVRF／API を取得し、「Exploited:Yes」「Publicly Disclosed:Yes」 「自社で稼働している製品」で自動抽出する仕組みを作る。** **抽出結果だけを人が読む運用にする。**
