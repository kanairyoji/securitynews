機密コンピューティングは、そのなかで動くソフトウェアの脆弱性からは守らない原因・手口出典 [1] [2]

本件の構造はこうである（出典1）。

攻撃者が悪用したのは、推論基盤で使っているオープンソースの推論エンジン SGLang のリモートコード実行の脆弱性である。狙われたのはエンクレーブの外側の弱点ではなく、エンクレーブの中で動いているソフトウェアそのものである（本記録の整理）〈重要〉。

NEAR AI は、機密コンピューティングがオペレーターやホストからデータを守る仕組みであり、その環境で動くソフトウェアの脆弱性からは守らない、という趣旨を報告に記している（出典1。同趣旨は出典2 も報告の内容として伝える）。

結果として、2026年11月8日に当該サーバ上で処理中だったリクエスト（機密モードで送られたものを含む）を攻撃者が見られた可能性がある（出典1）。TEE を使っていることは、この可能性を消さなかった。

読み替えると、「機密モードで処理します」という保証の射程は、推論スタックの脆弱性管理の品質以上にはならない（本記録の評価）。自組織が同種のサービスを提供する側・利用する側のいずれであっても、確認すべきは TEE の採用そのものではなく、エンクレーブ内で動くソフトウェアの更新体制である（本記録の推奨）。

NEAR AI 自身も、今後は推論ソフトウェアとエンクレーブ周辺のサービスにエンクレーブ本体と同水準の分析を適用するとしている（出典1）。

提供を終了した機能の背後に、生きた内部システムが残っていた被害規模・影響範囲出典 [1] [2]

侵害の広がり方で目を引くのはここである（本記録の評価）。

攻撃者は推論サーバ1台でコードを実行し、そこから社内インフラへ到達した。到達先として報告に明示されているのが、「提供を終了していた Private Chat の背後にある内部システム」である（出典1）。約100ユーザーのアカウント情報がダウンロードされたのは、この経路である（出典1・2）。

さらに、アクセスされた18エージェントは旧 NEAR AI Agents の環境で動いており、機密コンピューティング環境では動いていなかった（出典1）〈重要〉。

つまり被害の中心は、現役の主力機能ではなく「過去の構成」「旧環境」に残っていたものである（本記録の整理）。廃止・移行の際に基盤とデータを落としきれていないと、新しい設計の保証が及ばない領域が残り続ける。

なお、保存済みの Private Chat の会話とアップロードされたファイルについては、アクセスされた形跡は確認されていないとしている（出典1）—— この点は、停止した機能のデータが残っていた事実と合わせて読む必要がある（本記録の整理）。残っていたが、読まれた形跡は無かった、という状態である。

API キーがログに書かれていた——攻撃の巧拙ではなく平時の設計の問題原因・手口出典 [1]

露出の経路として報告に書かれているのは次の一点である（出典1）。

NEAR AI Cloud の顧客2件の API キーが、ログ内に露出した（すでに失効させた）

これは攻撃手法の高度さの話ではない（本記録の評価）〈重要〉。サーバ上でコードを実行できた攻撃者が、そこにあるログファイルを読んだだけで顧客の鍵が手に入った、という構造である。

平時に見つけられる種類の問題でもある（本記録の整理）。ログ出力のレビュー、秘密検出（secret scanning）の仕組み、マスキングの標準化は、侵害を前提にしなくても実施できる。

侵害時に「ログに何が書かれていたか」を調べ直す作業は、対応のなかでも時間がかかるほうである（本記録の評価）——どのログに何が出ていたかを把握していなければ、交換すべき秘密の一覧を作れない。

本件で NEAR AI が残る認証情報のローテーションまで実施したと記しているのは（出典1）、この不確かさに対する妥当な線引きである（本記録の評価）。

悪用の翌日に、影響を5段階に書き分けて公表した組織の対応出典 [1]

公表の形は、本DBが扱ってきた事案のなかでも区別が明確である（本記録の評価）。

報告は影響を次のように書き分けている（出典1）。

  1. ダウンロードされた: 約100ユーザーのアカウント情報（メールアドレス・氏名、一部はプランと残高）
  2. アクセスされた: 旧環境の18エージェントのチャット履歴・設定・ログ
  3. ログ内に露出した: クラウド顧客2件の API キー（失効済み）
  4. 見られた可能性がある: 2026年11月8日に当該サーバで処理中だったリクエスト（機密モードを含む）
  5. アクセスされた形跡は確認されていない: 保存済みの Private Chat の会話とアップロードされたファイル

「取得された」「触れられた」「可能性がある」「形跡が無い」を混ぜていない（本記録の評価）〈重要〉。読者は自分がどの区分に当たるかを判断できる。

公表は悪用のあった日の翌日である（本記録の算出。figures 参照）。ただし、検知の日時が公表されていないため、対応の速さそのものは検証できない（本記録の留保）〈未確定2〉——測れるのは「11月8日の出来事が11月9日に公表された」ことだけである。

悪用された脆弱性の識別子が公表されていない未確定事項出典 [1] [2] [3] [4]

報告が示しているのは「SGLang のリモートコード実行の脆弱性」という記述までである（出典1）。

CVE 番号・影響していた版・修正が公開された日のいずれも公表されていない〈未確定1〉。報道も同様である（出典2・3・4）。

この欠落には実務上の意味がある（本記録の評価）〈重要〉。

  • 同じ SGLang を使っている組織が、自環境が該当するかを判定できない
  • 「未パッチの脆弱性」と記されているが（出典1）、修正の公開からどれだけ経っていたのかが分からないため、放置の長さを評価できない
  • 本DBとしても、過去に公表された SGLang の脆弱性と本件を結びつけられない（推定しない）

NEAR AI は脆弱性を SGLang プロジェクトへ報告したとしている（出典1）—— この記述は、悪用された不備が報告時点で未修正だった可能性を示すが、断定できる材料は無い（本記録の留保）。

AI 推論スタックを運用する組織に対して本件から言えるのは、「使っている推論エンジンの脆弱性情報をどこで受け取るか」をあらかじめ決めておく必要があるということである（本記録の推奨）。

    取るべき行動 **AI サービスの調達時に、TEE の採用の有無ではなく 「エンクレーブ内で動くソフトウェアの脆弱性管理（更新頻度・報告経路・SLA）」を確認する。** **自社が提供側なら、同じ内容を利用者向けの説明に書く。**
  • 提供を終了した機能は、基盤とデータまで落とさないと攻撃面として残る。
    **攻撃者が到達したのは「提供を終了していた Private Chat の背後にある内部システム」で、 約100ユーザーのアカウント情報はそこから取得された**（出典1）〈重要〉—— **アクセスされた18エージェントも、機密コンピューティング環境の外で動く旧環境にあった** （出典1）。 **被害の中心が現役の構成ではなく過去の構成に残っていたものだった**（本記録の整理）。
    取るべき行動 **機能・サービスの廃止手順に「基盤の停止」「データの削除または隔離」「到達経路の遮断」を 含め、完了を確認する担当を決める。** **廃止済み機能の一覧と、その基盤がまだ稼働しているかの棚卸しを定期で行う。**
  • 影響の公表は「取得された／触れられた／可能性がある／形跡が無い」を書き分ける。 読者が自分の立場を判断できる。
    **本件の報告は影響を5段階に書き分けている**（出典1）〈重要〉—— **自社の売りである機密モードの処理についても「見られた可能性がある」と 隠さずに記載している**（出典1）。 **混ぜて書くと、読者は過大にも過小にも受け取る**（本記録の評価）。
    取るべき行動 **インシデント公表のひな形に、確定した取得・アクセスの有無・可能性・ 形跡が確認されなかった範囲を分けて書く欄を設ける。** **「可能性がある」と書く場合は、その判断の根拠（ログの有無）も併記する。**
  • 秘密の交換範囲は「露出が確認された分」ではなく 「その環境が保持していた分」で決める。
    **本件では API キーがログ内に露出していた**（出典1）—— **サーバ上でコードを実行できた攻撃者が読めた範囲を、 ログの設計を把握していない状態で特定することは難しい**（本記録の評価）。 **NEAR AI は全セッション・管理者認証情報・エージェントトークンに加え、 残る認証情報のローテーションまで行ったとしている**（出典1）。
    取るべき行動 **侵害時に交換すべき秘密の一覧（どのシステムが何を保持しているか）を平時に作る。** **交換に他社の作業が要る秘密（顧客の API キー等）を区別し、連絡手順を決めておく。**
セキュリティ技術者への示唆
  • 推論エンジン（SGLang・vLLM 等）を、OS やミドルウェアと同じ更新管理の対象にする。
    **本件の侵入口は推論エンジンのリモートコード実行の脆弱性である**（出典1）〈重要〉—— **NEAR AI のブログ一覧は「未パッチの SGLang 脆弱性」と記している**（出典1）。 **AI 基盤のソフトウェアは更新が速く、 研究用の構成がそのまま本番に残りやすい**（本記録の評価）。
    取るべき行動 **推論エンジンとその依存関係を SBOM に載せ、脆弱性情報の受領経路 （GitHub の security advisory・リリース通知）を購読する。** **本番で動いている版を定期的に棚卸しする。**
  • 推論サーバから社内システムへの到達を絞る。本件はそこから内部システムへ届いた。
    **攻撃者は推論サーバ1台から社内インフラへ到達し、 提供終了済み機能の背後の内部システムにアクセスした**（出典1）〈重要〉—— **到達の手段は公表されていない**〈未確定2〉。 **推論サーバは外部からの入力を受ける位置にあり、 侵害された場合の起点になりやすい**（本記録の評価）。
    取るべき行動 **推論サーバを独立したセグメントに置き、社内システムへの通信を 必要な宛先・ポートに限定する。** **推論サーバから出る通信を既定で遮断し、例外を明示する。**
  • ログに秘密を書かない。本件の API キーの露出はログ経由だった。
    **クラウド顧客2件の API キーがログ内に露出した**（出典1）〈重要〉—— **これは攻撃の高度さではなく、平時の出力設計の問題である**（本記録の評価）。 **ログは閲覧権限が広く、保存期間も長い**（本記録の整理）。
    取るべき行動 **ログ出力のレビュー基準に「資格情報・トークン・鍵を出さない」を明記し、 秘密検出の自動検査を CI に入れる。** **既存のログについても、秘密が含まれていないかを走査する。**
  • エージェント基盤では、トークンを一括で再発行できる仕組みを事前に作る。
    **本件の対応には「全エージェントトークンの再発行」が含まれている**（出典1）—— **18エージェントのチャット履歴・設定・ログにアクセスされており、 設定に含まれる資格情報が危険にさらされた可能性がある**（本記録の整理）。 **一括再発行ができないと、対応が長期化する**（本記録の評価）。
    取るべき行動 **エージェント・連携用のトークンに有効期限と失効 API を用意し、 一括失効・再発行を手順として持つ。** **再発行時に利用者側で必要な作業を文書化しておく。**
  • 機密モードの処理を行うサーバでは、監視をどう設計するかを先に決める。
    **サーバ上でコードを実行できる攻撃者が、処理中のデータを読むことは記録に残らない** （本記録の評価）〈重要〉—— **本件では「見られた可能性がある」までしか判定できていない**（出典1）〈未確定5〉。 **一方、内部の可観測性を上げることは、機密性の設計と衝突しうる**（本記録の整理）。
    取るべき行動 **機密処理を行う基盤について、 ①プロセス起動・外向き通信などデータの中身を見ない指標での監視、 ②侵害時に「何が処理中だったか」を後から示せる最小限の記録 を設計する。** **機密モードと非機密モードの処理をサーバ単位で分けることを検討する。**
