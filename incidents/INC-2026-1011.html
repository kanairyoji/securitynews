INC-2026-1011Git に6脆弱性・再帰クローンでRCE

Git に6件の脆弱性が同時公表され、うち CVE-2026-111760 は 悪性リポジトリを再帰クローンするだけで攻撃者のコードが動く（CVSS 3.1 基本値 8.0）—— index 処理の整数切り詰めにより、極端に長いパスが検証を通ったあと短い名前で書き込まれ、 サブモジュールの `.git` ファイルを攻撃者の設定・フックを置いたディレクトリへの シンボリックリンクに置き換えられる。 修正は Git 2.56.1、および 2.55.1 / 2.54.1 / 2.53.1 / 2.52.1 / 2.51.3 / 2.50.2 へ バックポートされた。GitHub は github.com と GitHub Enterprise Cloud に修正を適用済みで、 GitHub Enterprise Server は 3.19.15 / 3.20.11 / 3.21.9 / 3.22.4 で修正された。 悪用の観測は公表に記載が無い。

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備脆弱性の放置
初報: 2026年11月10日 最終更新: 2026年11月12日

Git プロジェクトは2026年11月10日、6件の脆弱性を修正した版を同時に公開しました（出典1）。

最も重いのは、悪性リポジトリを再帰クローンするだけでコードが動くものです（出典1・2）〈重要〉。

  • CVE-2026-111760 — 再帰クローン中のコード実行（CVSS 3.1 基本値 8.0・GitHub の評価は high。出典2）。Git は作業ツリーへファイルを書く前にパスを検証し、自身のリポジトリメタデータを上書きするパスを拒否する。しかしindex 処理の整数切り詰めにより、極端に長いパスが「ある名前」で検証を通ったあと「短い名前」で書き込まれる（出典1）。これを使うとサブモジュールの .git ファイルを、攻撃者の設定ファイルやフックを置いたディレクトリへのシンボリックリンクに置き換えられる（出典1）。Git が後でそのディレクトリを使った時点で、再帰クローンの最中に攻撃者のコードが実行される（出典1）。
  • CVE-2026-113408 — サーバが広告する HEAD を経由したパストラバーサル（出典1）。プロトコル v2 で空リポジトリをクローンするとき、サーバはまだコミットの無いブランチ（unborn branch）を指す HEAD symref を広告できる。Git はその参照先を検証せずに保存していたため、悪性サーバがパストラバーサルを含む名前を返すと、files 参照バックエンドでは後続のブランチ更新が参照ディレクトリの外へ書き込みうる。
  • CVE-2026-114467 — 署名除去時のスタック破壊（出典1）。GPG 署名をメッセージから取り除くとき、Git は署名が最大2つまでしか無いと仮定していた。3つ以上の署名を含む細工されたメッセージで固定長スタック配列の外に書き込みが起きる。署名が3つ以上付いたタグをマージすると発火するため、利用者の代わりにマージを行うホスティングサービスも影響を受ける（出典1）。
  • CVE-2026-114469 — バイナリパッチ適用時の境界外読み取り（出典1）。Git は約1GiB を超えるパッチを拒否するが、検査していたのは「渡された時点の大きさ」だけで、バイナリパッチは圧縮・符号化されているため、小さなパッチが展開後に上限を超えられる。
  • CVE-2026-105437 — 大きなマージでのヒープ破壊（CVSS 3.1 基本値 7.5・high。出典3）。マージ結果の必要メモリ量の計算がオーバーフローしうる（大量の衝突と大きな conflict-marker-size 属性の組み合わせなど）。小さすぎるバッファを確保してその外へ書き込む。GitHub のアドバイザリはこれを「三方マージのコード（xdiff）のヒープバッファオーバーフロー」と説明している（出典3）。信頼できない内容をマージするアプリケーションとホスティングサービス、およびローカルのマージが対象である（出典1）。
  • CVE-2026-114466 — fast-import ストリーム経由のファイルシステムアクセス（出典1）。git fast-import の3つの機能に、信頼できない入力ストリームに対する保護が無かった。rewrite-submodules-from と rewrite-submodules-to は任意のファイルを読み、その内容をエラーメッセージ経由で露出しうる。export-pack-edges はファイルを作成し、既存ファイルに追記しうる（出典1）。以後これらは --allow-unsafe-features を明示しない限り入力ストリームからは拒否される。

修正版は Git 2.56.1 で、2.55.1 / 2.54.1 / 2.53.1 / 2.52.1 / 2.51.3 / 2.50.2 へバックポートされました（出典1）。GitHub は github.com・GitHub Enterprise Cloud・データレジデンシー版のGitHub Enterprise Cloud に修正を適用済みで、GitHub Enterprise Server は 3.19.15 / 3.20.11 / 3.21.9 / 3.22.4 で修正されました（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃者が用意するのはリポジトリかサーバで、引き金を引くのは被害者の側の日常操作である** （出典1。本記録の整理）〈重要〉—— **CVE-2026-111760 は「再帰クローン」、CVE-2026-113408 は「空リポジトリのクローン」、 CVE-2026-114467 と CVE-2026-105437 は「マージ」、 CVE-2026-114469 は「バイナリパッチの適用」、 CVE-2026-114466 は「fast-import ストリームの処理」で発火する。**

  1. 1. 初期侵入確認済[1]
    **攻撃者が、極端に長いパスの index エントリと、 サブモジュールを含む構成を仕込んだリポジトリを用意する**（出典1）。 **被害者がそれを再帰クローンする。**
    根拠: **出典1の CVE-2026-111760 の説明に基づく**（出典1）。
  2. 2. 実行確認済[1]
    **index 処理の整数切り詰めにより、 極端に長いパスが「ある名前」で検証を通ったあと「短い名前」で書き込まれる**（出典1）。 **この食い違いを使って、サブモジュールの `.git` ファイルを、 攻撃者の設定ファイルやフックを置いたディレクトリへの シンボリックリンクに置き換える。 Git が後でそのディレクトリを使った時点で、 再帰クローンの最中に攻撃者のコードが実行される**（出典1）。
    根拠: **出典1の記述による**（出典1）—— **「Git checks paths before writing files into a working tree, including rejecting paths that would overwrite its own repository metadata. However, an integer truncation in Git's index handling can cause an extremely long path to pass validation under one name and then be written using a shorter name.」（原文英語。 訳: Git は作業ツリーへファイルを書く前にパスを検証し、 自身のリポジトリメタデータを上書きするパスを拒否する。 しかし index 処理における整数の切り詰めにより、 極端に長いパスが、ある名前では検証を通り、 短い名前で書き込まれることが起こりうる）。**
  3. 3. 初期侵入確認済[1]
    **別経路——悪性サーバがプロトコル v2 で、 まだコミットの無いブランチを指す HEAD symref を広告する**（出典1）。 **Git はその参照先を検証せずに保存していたため、 パストラバーサルを含む名前を受け入れる。 files 参照バックエンドでは、 後続のブランチ更新が参照ディレクトリの外へ書き込みうる**（CVE-2026-113408。出典1）。
    根拠: **出典1の記述による**（出典1）。
  4. 4. 影響（暗号化・破壊・改ざん）確認済[1] [3]
    **マージ経路の2件は、メモリ破壊に至る**（出典1）。 **CVE-2026-114467 は、署名が3つ以上付いたタグをマージすると 固定長スタック配列の外へ書き込む。 CVE-2026-105437 は、大量の衝突と大きな `conflict-marker-size` 属性の 組み合わせなどでマージ結果のサイズ計算がオーバーフローし、 小さすぎるバッファの外へ書き込んでヒープを壊す**（出典1）。 **出典1は、どちらについても 「利用者の代わりにマージを行うホスティングサービスも影響を受ける」と明記している。**
    根拠: **出典1の記述、および出典3のアドバイザリ （「三方マージのコード（xdiff）のヒープバッファオーバーフロー」）による**（出典1・3）。
  5. 5. 収集確認済[1]
    **fast-import 経路では、ファイルの読み出しと書き込みが起きる**（CVE-2026-114466。出典1）。 **`rewrite-submodules-from` と `rewrite-submodules-to` は任意のファイルを読み、 その内容をエラーメッセージ経由で露出しうる。 `export-pack-edges` はファイルを作成し、既存ファイルに追記しうる**（出典1）。
    根拠: **出典1の記述による**（出典1）。

再帰クローンという日常操作が、コード実行の引き金になる原因・手口出典 [1] [2]

CVE-2026-111760 の仕組みは、検証と書き込みで「違う名前」が使われることにあります（出典1）〈重要〉。

Git は作業ツリーへファイルを書く前にパスを検証し、自身のリポジトリメタデータ（.git 配下）を上書きするようなパスは拒否します（出典1）。この防御自体は以前から入っているものです。しかし index 処理に整数の切り詰めがあり、極端に長いパスが「ある名前」で検証を通ったあと、「短い名前」で書き込まれる（出典1）。検証した対象と書き込んだ対象がずれるので、防御をすり抜けます。

このずれを使って攻撃者は、サブモジュールの .git ファイルを、攻撃者の設定ファイルやフックを置いたディレクトリへのシンボリックリンクに置き換えます（出典1）。Git が後でそのディレクトリを使った時点で、再帰クローンの最中に攻撃者が置いたコードが実行されます（出典1）。修正は、長さが切り詰められる前に、極端に長い index エントリのパスを拒否するものです（出典1）。

引き金が「再帰クローン」であることが、この脆弱性の実務上の重さを決めています（本記録の評価）〈重要〉。git clone --recursive は、OSS を取り込むとき、フォークをビルドするとき、依存を更新して検証するとき、外部からのプルリクエストを CI で確かめるときに走ります。人が意識して「危険な操作」と認識する場面ではありません。 CVSS 3.1 のベクタは UI:R（利用者の操作が要る）で減点されていますが（出典2）、ここで要求される「操作」はクローン1回です。

GitHub は同時に「追加の堅牢化」も入れました（出典1）。チェックアウトとツリー処理における index エントリの確保にオーバーフロー検査を加え、パスをメモリへ複写する前に確保サイズが切り詰められたりオーバーフローしたりしないようにしたとしています（出典1）。これには CVE が振られていません。

6件を1本の記事で読むと同じ重さに見えますが、刺さる相手が違います（本記録の整理）〈重要〉。

パッチやストリームを食わせる処理に当たるもの（出典1）。

  • CVE-2026-114469 — バイナリパッチ適用時の境界外読み取り。Git は約1GiB を超えるパッチを拒否しますが、検査していたのは「渡された時点の大きさ」だけでした。バイナリパッチは圧縮・符号化されているため、小さなパッチが展開後に上限を超えられます。修正は、処理前に宣言された非圧縮サイズも検査します。
  • CVE-2026-114466 — fast-import ストリーム経由のファイルシステムアクセス。git fast-import は、リポジトリ外のファイルに触れるコマンドを信頼できない入力ストリームでは既に制限していましたが、3つの機能にその保護が無かった。rewrite-submodules-from と rewrite-submodules-to は任意のファイルを読み、内容をエラーメッセージ経由で露出しうる。export-pack-edges はファイルを作成し既存ファイルに追記しうる。

自組織がどれに当たるかは、「Git を何に使っているか」で決まります（本記録の評価）。クローンだけなら前2件、コードレビュー基盤やマージの自動化を持つなら中2件、リポジトリの移行・変換の仕組みを持つなら後2件が効きます。

OS の更新では直らない Git が、どれだけ残っているかが問題になる対策・注意喚起出典 [1]

出典1が繰り返しているのは「同梱版も更新せよ」です（出典1）〈重要〉。

修正版は Git 2.56.1 で、2.55.1 / 2.54.1 / 2.53.1 / 2.52.1 / 2.51.3 / 2.50.2 の6系列にバックポートされました（出典1）。7系列に戻していること自体が、長期サポート版を固定している環境が多いという前提の表明です（本記録の評価）。

出典1の更新の指示は3段です（出典1）。

  1. OS または Git 配布元から修正版を入れる。
  2. 自前の Git を同梱するアプリケーションを更新する。
  3. 管理者は、利用者の代わりにリポジトリを処理する自動化やサービスで使われている Git も更新する。

実務の難所は2と3です（本記録の評価）〈重要〉。IDE、コンテナイメージ、CI ランナーのベースイメージ、コードスキャンの実行環境、AI コーディング基盤のサンドボックス——これらはそれぞれが自分の Git を抱えており、ホスト OS の apt upgrade では動きません。棚卸しの手がかりとしては、稼働中のイメージで git --version を取るのが確実です（本記録の判断）。

GitHub 自身の対応状況（出典1）。

  • github.com・GitHub Enterprise Cloud・データレジデンシー版のGitHub Enterprise Cloud — 修正を適用済み。
  • GitHub Enterprise Server — 3.19.15 / 3.20.11 / 3.21.9 / 3.22.4 で修正。「可能な限り速やかに更新すること」。
  • GitHub Desktop・GitHub Copilot アプリ — 修正版 Git を含むリリースを「調整中」。日付も版番号も示されていません〈未確定5〉。
  • GitHub Codespaces・GitHub Actions — 修正版 Git が「配られる」。こちらも時期が示されていません〈未確定5〉。

暫定措置には副作用があります（本記録の評価）。出典1は、すぐ更新できない場合に「信頼できるサーバからのみクローンする、信頼できないリポジトリの再帰クローンを避ける、信頼できない内容やタグをマージしない、信頼できない出所のバイナリパッチと fast-import ストリームを処理しない」を挙げ、同時に「これらの予防措置は修正の適用に代わるものではない」と明記しています（出典1）。外部貢献を受け入れているプロジェクトでは「信頼できない内容をマージしない」は成立しません。暫定措置は時間稼ぎであって、運用方針ではありません。

    取るべき行動 **自社の脆弱性管理が、CVSS や影響版が欠けた入力を どう扱うかを確認する。 「スコア無しは後回し」という既定になっていないかを点検し、 欠損時は人が読んで判断する経路を用意する。**

    **出典1の暫定措置は 「信頼できないリポジトリの再帰クローンを避ける」「信頼できない内容をマージしない」で、 外部貢献を受け入れる組織では事業の制約になる**（出典1）—— **出典1自身が「これらは修正の適用に代わるものではない」と明記している。** **制約が長引くと、現場は制約を回避する方向に動く。**
    取るべき行動 **暫定措置を入れるときは、解除条件（修正版の配布完了）と期限を同時に記録し、 期限を越えたら報告が上がる仕組みにする。**
セキュリティ技術者への示唆
  • **`--recursive` を使うクローンの場所を全部挙げられるようにする** （本記録の評価）〈重要〉。
    **CVE-2026-111760 の引き金は再帰クローンである**（出典1）—— **サブモジュールの `.git` ファイルがシンボリックリンクに置き換わり、 攻撃者の設定・フックが実行される。 `git clone --recursive`、`git submodule update --init --recursive`、 CI の checkout アクションの `submodules: recursive` 相当の設定が対象になる。**
    取るべき行動 **リポジトリと CI の定義を横断して `recursive`・`submodules` の指定を検索し、 そのうち「外部由来の URL をクローンするもの」を洗い出す。 外部由来のものは、修正版が行き渡るまで隔離された使い捨て環境で走らせる。**
  • **稼働中のイメージの `git --version` を取るのが、 台帳より確実である**（本記録の判断）。
    **同梱版は OS のパッケージ更新で動かない**（出典1）—— **台帳には「Git 2.5x」と書いてあっても、 ベースイメージの固定・レイヤキャッシュ・ベンダー同梱で 実際に動いている版は違いうる。**
    取るべき行動 **CI の各ジョブの先頭に `git --version` を出す行を一時的に入れ、 ログから実測を集める。 2.56.1 / 2.55.1 / 2.54.1 / 2.53.1 / 2.52.1 / 2.51.3 / 2.50.2 の いずれにも達していないものを更新対象として並べる。**
  • **自社がマージを「代行」しているなら、 影響する CVE が変わる**（本記録の評価）〈重要〉。
    **CVE-2026-114467（署名3つ以上のタグのマージでスタック破壊）と CVE-2026-105437（大きなマージでヒープ破壊・CVSS 7.5）について、 出典1は「利用者の代わりにマージを行うホスティングサービスも影響を受ける」と 明記している**（出典1・3）—— **自前のコードレビュー基盤、マージキュー、 プルリクエストの自動マージ、リリース自動化が該当する。**
    取るべき行動 **「外部から来た内容を自社の基盤でマージする処理」を列挙する。 該当する処理の Git を最優先で更新し、 更新までは隔離された実行環境で走らせる。 マージを行うプロセスの異常終了を監視対象に入れる。**
  • **CVE-2026-114466 の修正は、既存の移行スクリプトを止めうる** （本記録の評価）。
    **`rewrite-submodules-from`・`rewrite-submodules-to`・`export-pack-edges` は 以後 `--allow-unsafe-features` 無しでは入力ストリームから拒否される**（出典1）—— **リポジトリの変換・移行でこれらを使っている自動化は、 更新した時点で失敗する。**
    取るべき行動 **`fast-import` を使っている処理を検索し、 上記3機能の使用を確認する。 使っている場合は、ストリームの生成元が自社管理であることを確かめた上で `--allow-unsafe-features` を明示する （出典1は「ストリームを生成するプログラムを信頼できるときにのみ 有効にすること」としている）。**
  • **バイナリパッチのサイズ上限は「渡された大きさ」では測れない** （本記録の評価）。
    **CVE-2026-114469 は、約1GiB の上限検査が 「供給された時点のパッチの大きさ」しか見ていなかったことによる**（出典1）—— **バイナリパッチは圧縮・符号化されているため、 小さな入力が展開後に上限を超える。 修正は宣言された非圧縮サイズも検査する。**
    取るべき行動 **自社の処理系で「圧縮された入力のサイズで上限を判断している箇所」が 他にないかを点検する （アーカイブの展開、添付の検査、ログの取り込み）。 同じ型の誤りが入りやすい。**
