INC-2026-1014Grok製アプリ35,578件が無認証で公開

Grok Build で作られたアプリ 35,578 件が、サインインなしで誰でも開ける状態だった—— セキュリティ企業 Claroc が grok.me 配下の 43,551 のアドレスを調べ、 稼働していた 37,571 件のうち約94.7%が無認証で到達できたと2026年11月10日に公表。 公開の設定欄は「リンクを知っている人は誰でも」があらかじめ選ばれており、 アプリのホスト名はランダムな語から成るため passive DNS に記録されて見つけられる。 露出した中身には病院の患者記録、平文パスワードを含む勤務表、 米連邦機関向けの提案資料、SpaceXSI と X の従業員が作った24件が含まれる。 24件は削除されたが、残る3万件超は本稿作成時点で未解消。

意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）設定不備設計・実装上の不備ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）
初報: 2026年11月10日 最終更新: 2026年11月12日

セキュリティ企業 Claroc は2026年11月10日、Grok Build で作られたアプリの大半がサインインなしで誰でも開ける状態だったと公表しました（出典2・3・4・5）〈重要〉。

数字はこうです（出典2。出典4・5もほぼ同じ数値を示します）。

  • 調べたアドレス — grok.me ドメイン配下の 43,551（別の報道は 43,601 とする〈齟齬2〉）。
  • 稼働していたアプリ — 37,571 件（検証の期間は2026年11月8日〜10日）。
  • サインインなしで開けたもの — 35,578 件。約94.7%。
  • SpaceXSI と X の従業員が作ったもの — 24 件（出典3・4）。
  • 機微な内容を含むとみられるもの — 650〜800 件と見積もられています（出典2）。出典4は「公開されていたアプリの多くはゲーム・ランディングページ・電卓だったが、およそ10件に1件は社内の業務情報を含んでいた」と報じています。

出典2はこの状態を「漏えいというより既定の設定である」と表現しています。

露出していた中身の例（出典2・3）。

  • 病院職員の名簿と、機微な患者記録（出典2）。
  • 平文でパスワードが書かれた従業員の勤務表（出典2）。
  • 米連邦機関向けに用意された営業テリトリーの地図と導入資料（出典2）。
  • ペルーの建設会社の産業保健ダッシュボード——労働者の健康診断 3,784 件の記録（出典3）。
  • 米海軍の物流契約を支える船舶エンジニアリングの委託先に紐づく、108 名の人員名簿（出典3）。
  • Tesla の整備拠点の評価表——技術者22名とその賞与の状況（出典3）。
  • ある医療関連企業の約 3,565 名の従業員名簿（出典3）。
  • SpaceXSI・X の従業員が作った24件には、営業の導入計画、594 件の取引先を含む営業テリトリーの地図、社内システムのアドレス、広告の提案が含まれていました（出典3）。
  • さらに30の組織のデータが紐づいており、うち26 は従業員1,000名超、6 は Fortune 500 の企業です（出典2）。

原因は、公開の既定と、アドレスの見つけやすさの組み合わせです（出典2・3）〈重要〉。Grok Build のリンク共有は、各アプリに grok.me 配下のランダムな識別子を与えます。リンクを知っている者は、ログインせずに開けます（出典2）。Claroc の共同創業者兼CTO Asaf Aprozper の検証では、共有の設定欄で「Anyone with the link」（リンクを知っている人は誰でも）があらかじめ選ばれていました（出典3）。そして「リンクを知らなければ到達できない」という前提が成り立ちません——アプリのホスト名にはランダムな語が置かれ、それが passive DNS のデータベースに記録されるため、そこから列挙できます（出典3）。

Claroc が中核の弱点としているのは「組織単位のアクセス管理が無いこと」です（出典2）。

公表後の経過（出典2・3）。Claroc は2026年11月8日に SpaceXSI へ通知を始め、11月10日に報告を公表しました。公表時点で SpaceXSI からの直接の返答は無かったとされます（出典3）。SpaceXSI・X の従業員が作った24件は削除され、リンクは「App not found」を返すようになりました（出典3）。一方、残る3万件超の利用者・組織のアプリは、報告の時点で手当てされておらず、Claroc 自身が所有者への連絡を進めているとされます（出典2・3）〈重要〉。

提供側の説明は、Claroc の指摘と一致していません（出典3）〈齟齬1〉。Cursor（SpaceXSI が買収）の担当者は「Grok Build のアプリは既定では非公開であり、作成者が共有したときにのみ公開になる」と述べ、ChatGPT・Lovable・Bolt も同様の共有リンクを提供しているとしています。 Aprozper 側は「我々は衝撃を受けた」とし、Lovable・Bolt・Replit も DNS から発見できるアドレスを生成するが、Grok が露出させた情報は圧倒的に機微だったと述べています（出典3）。

ランダムなホスト名による秘匿は、passive DNS に記録されて破られる原因・手口出典 [2] [3]

本件の構造は2段です（出典2・3）〈重要〉。

第1段は、公開の既定設定です。 Grok Build のリンク共有は、各アプリに grok.me 配下のランダムな識別子を与えます。リンクを知っている者は、ログインせずに開けます（出典2）。Claroc の共同創業者兼CTO Asaf Aprozper の検証では、共有の設定欄で「Anyone with the link」（リンクを知っている人は誰でも）があらかじめ選ばれていました（出典3）。

第2段は、アドレスの発見可能性です。 これが本件を「3万件超」の規模にしています（本記録の評価）〈重要〉。出典3は、Grok Build の URL がホスト名にランダムな語を置き、passive DNS のデータベースがそれを記録する、としています。 つまり「リンクを知らなければ到達できない」という前提が成り立ちません。

ここには一般化できる教訓があります（本記録の評価）。ランダムな文字列を「パス」に置くか「サブドメイン」に置くかで、秘匿の強さが変わります。

  • example.com/<ランダム> — パスは DNS に出ません。第三者が列挙するには当て推量が要ります。
  • <ランダム>.example.com — サブドメインは DNS の問い合わせに現れ、passive DNS のデータベースに記録されます。 列挙できます。

Grok Build は後者でした（出典3）。さらに、列挙はアプリに接続せずに行えるため、所有者側に痕跡が残りません（本記録の評価）—— 所有者が「調べられている」ことに気づく機会が構造的にありません。

Claroc が中核の弱点としているのは、別の点です（出典2）〈重要〉。「組織単位のアクセス管理が無いこと」です。個人が作り、個人が共有する作りのため、組織として「誰が何を公開しているか」を把握・制御する手段がありません。 これは設定の問題ではなく、製品の作りの問題です（本記録の整理）—— 設定を直せと言っても、組織には直す対象の一覧が見えません。

提供側の説明は、この指摘と一致していません（出典3）〈齟齬1〉。Cursor（SpaceXSI が買収）の担当者は「Grok Build のアプリは既定では非公開であり、作成者が共有したときにのみ公開になる」と述べ、ChatGPT・Lovable・Bolt も同様の共有リンクを提供しているとしています。

本記録の読みでは、両者は「既定」の指す対象が違う可能性があります（本記録の推測。どちらも検証できていません）—— 作成直後のアプリは非公開だが、共有の操作に入った時点で「リンクを知っている人は誰でも」が選ばれている、という読みが成り立ちます。 いずれにせよ、この説明は論点に答えていません（本記録の評価）〈重要〉—— 「作成者が共有したときにのみ公開になる」は、共有した作成者が「リンクを知る人だけ」と理解していたのに実際には列挙可能だった、という問題に触れていません。 他社も同様という指摘についても、Aprozper 側が「Lovable・Bolt・Replit もDNS から発見できるアドレスを生成する」と認めており、争点になっていません（出典3）——争点は露出した情報の機微さのほうです。

この事案を自組織に移すとき、問いは「設定を直せ」ではありません（本記録の評価）〈重要〉。「そもそも何件あるのかを数えられるか」です。

棚卸しの手がかりは、どれも穴があります（本記録の判断）。

  • grok.me への通信ログ — 社内の端末・ネットワークから作られたものは映りますが、自宅や個人端末から作られたものは映りません。

  • 従業員への照会 — 最も網羅的ですが、「申告したら使用禁止になる」と思われると出てきません〈重要〉。棚卸しは「責任追及ではなく露出の確認である」ことを先に明示する必要があります。

禁止だけでは解決しません（本記録の評価）。業務部門が Grok Build を使ったのは、手元のデータを見やすくしたかったからです。代替手段を用意せずに削除させれば、別の同種サービスへ移って同じ状態が再現します。 Aprozper 自身が「Lovable・Bolt・Replit も DNS から発見できるアドレスを生成する」と述べています（出典3）—— 移った先も同じ構造です。

調達の判定条件に入れるべき点があります（出典2の指摘に基づく。本記録の判断）。

  • 組織単位のアクセス管理があるか（管理者が、所属メンバーの作ったものを一覧でき、公開を制限できるか）。
  • 共有の既定が非公開か。
  • アプリのアドレスがサブドメインか、パスか（サブドメインなら passive DNS から列挙されます）。
  • 所有者にアクセスログが提供されるか〈重要〉—— 露出が起きた後に通知の要否を判断できるかが、ここで決まります。

組織単位の管理を備えた基盤は有償・上位プランになりやすく、個人が無償で使える道具へ流れる圧力は残ります（本記録の評価）。したがって現実的な落とし所は、「個人データと認証情報を含むものは、認証のある基盤に限る」という線引きを明示し、それ以外は許容する形です（本記録の判断）—— 全面禁止は守られず、全面許容は本件の再現になります。

最後に、本件の悪用の有無について（本記録の明示）〈重要〉〈未確定1〉。第三者による実際のアクセス・持ち出し・悪用は公表されていません。 測られているのは「到達可能だった範囲」のみです。 そして「誰でも開ける」状態では、悪意ある参照と偶然の参照を区別する痕跡がそもそも残りにくい（本記録の評価）—— 「悪用は確認されていない」が「悪用は無かった」を意味しない型の事案です。
