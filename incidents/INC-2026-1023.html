INC-2026-1023ScreenConnect悪用でMSP経由に侵害

クラウド版 ScreenConnect の管理パネルを握った攻撃者が Run Command で 管理対象エンドポイントへ不正な ScreenConnect クライアントと独自ツールキット「SCKit」を 一斉配布し、2026年11月11日 17:47 UTC から約90分で288台・48組織に及んだ ——ConnectWise はパートナーアカウントへの不正アクセスを認め、 関連が疑われる5つのサードパーティ拡張機能を約400のパートナー環境で無効化したが、 初期侵入の経路はまだ特定されていない

脅威・攻撃キャンペーン不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている有名事象として記録（日本と直接の関係は薄い）公表されていない／不明
初報: 2026年11月11日（Huntress・ConnectWise・Sophos の同日公表） 最終更新: 2026年11月12日（本記録の作成。ConnectWise の advisory と Huntress・Sophos の分析を取得して確認）

侵害されたのは1社ではなく、「他社の端末にコマンドを流す権限」そのものでした。

2026年11月11日17時47分（UTC）ごろ、 クラウドホスト型の ScreenConnect 環境を狙う活動が始まりました（出典1・4）。 攻撃者は複数の ScreenConnect 管理パネルにアクセスし、 ScreenConnect の Run Command 機能を使って 管理対象のエンドポイントへ一斉にコマンドを送りました（出典1）。 コマンドは SYSTEM 権限で実行され、 攻撃者が管理する ScreenConnect クライアント（sc.msi）が サイレントインストールされました（出典1） ——正規の MSP の ScreenConnect 環境の外から、 その端末に入れる経路ができたことになります（出典4）。

Huntress は、同社の監視下で288台のエンドポイント・48組織が 影響を受けたとしています（出典1）。 288台のうち約3分の1は最初の10分で侵害され、全体は約90分で進みました（出典1）〈重要〉。 BleepingComputer は Huntress の初期の投稿を引いて 「MSP 6社、286台以上、47組織」と報じており、数値に食い違いがあります（出典4）〈齟齬1〉。

配布されたのは16ファイルからなる独自ツールキット「SCKit」です（出典1）。 機能は、①正規クライアントの接続枠を乗っ取る RelayTrap、 ②SYSTEM 権限で定期実行される TrapWatch スケジュールタスク、 ③Microsoft Defender の除外設定の追加、 ④SRP／AppLocker ルールによる 「ScreenConnect の一時フォルダから送られたファイルの実行」の阻止 ——の4つが挙げられています（出典1）〈重要〉。 ④は、正規の管理者が同じ経路で対処することを妨げる向きに働きます（本記録の評価）。

ConnectWise は同日のセキュリティ advisory で、 ScreenConnect のパートナーアカウントへの不正アクセスと、 顧客環境への未承認のリモートアクセスソフトウェアの導入を確認したとしました（出典2）。 関連が疑われる5つのサードパーティ拡張機能 （Labtech Plus／RMM Plus／RMM+／RMM Plus Password Link／RMM+ Password Link）を 約400のパートナー環境で予防的に無効化しています（出典2・4）。 同社は「無効化は予防的な封じ込めであり、 すでにデバイス上にある未承認のソフトウェア・永続化の仕組み・ アクセスが除去されたことを意味しない」と明記しています（出典2。原文英語。訳は本記録）〈重要〉。

本記録が最も重いと見るのは、調査の手段そのものが汚染されている点です（本記録の評価）。 Huntress は「ScreenConnect 経由で感染が疑われるホストに接続しないこと」を 明記しています（出典1。原文英語。訳は本記録）。 ConnectWise も、技術者が対話型の ScreenConnect セッションを 開始しないよう求め、別のセキュリティツールで調査するよう勧めています（出典2）。 設計上、SCKit は技術者の .aspxauth セッション Cookie を盗み、 Shared Toolbox 経由で到達できるセッションへペイロードを配布するとされますが、 Huntress はその成功を確認していないと明記しています（出典1）〈齟齬2〉。

初期侵入の経路は、本記録の確認時点でまだ特定されていません（出典1・2・4）〈未確定1〉。

Huntress が示した時間が、本件の性格を決めている（出典1）〈重要〉。

| 経過 | 状態 | | --- | --- | | 2026年11月11日 17:47 UTC ごろ | 活動開始（Huntress SOC が対応を開始） | | 開始から約10分 | 288台のうち約3分の1が侵害 | | 開始から約90分 | 全体の進行が完了 | | 同日の夜 | ConnectWise が advisory を公表 |

なぜ速いのか。 Run Command は、 管理対象の端末群に対して同時にコマンドを流す機能である（本記録の整理）。 したがって、端末の台数は配布の所要時間をほとんど増やさない。 攻撃者の作業量は「パネルの数」で決まり、「端末の数」では決まらない。

読者にとっての含意は、検知の目標を変えることである（本記録の評価）〈重要〉。 「配布を検知して止める」は、90分の窓では現実的でない。 成立しうるのは、①パネルへの不審なサインイン・管理者アカウントの追加を 検知すること（配布の前）、 ②配布後の不正クライアントの常設を検知して駆除すること（配布の後）——である。 ConnectWise が advisory で求めている 「認証・拡張機能のインストール・管理操作・Run Command・Toolbox の 各記録の保全と調査」は①と②の両方に効く（出典2。本記録の整理）。

なお、Huntress の288台・48組織は同社の監視下の数値である（出典1）。 同社は、攻撃者が割り当てたタグが連番であることから、 以前に侵害された MSP が他にもあると示唆している（出典4）〈重要〉 ——「アラートを受けていなくても Run Command の履歴を確認すべきだ」 というのがその帰結である（出典4）。

SCKit は、駆除の経路を先に塞ぐ設計になっている原因・手口出典 [1] [2] [4]

Huntress が SCKit と名付けた16ファイルのツールキットの機能は、 永続化と「対処の妨害」に向いている（出典1。本記録の整理）〈重要〉。

| 機能 | 内容 | 本記録の読み | | --- | --- | --- | | RelayTrap | 正規クライアントの接続枠を乗っ取る | 正規の遠隔管理と同じ枠を占める | | TrapWatch スケジュールタスク | SYSTEM 権限で定期実行 | 削除しても戻る | | Microsoft Defender の除外設定の追加 | 検知の対象から外す | 既存のエンドポイント保護を無効化せずに回避する | | SRP／AppLocker ルール | ScreenConnect の一時フォルダから送られたファイルの実行をブロック | 正規の管理者が同じ経路で対処することを妨げる |

4つ目が本記録の着目点である（本記録の評価）〈重要〉。 攻撃者は、自分が使った経路（ScreenConnect の一時フォルダ経由の ファイル配布と実行）を、あとから閉じている。 これは正規の管理者が同じ経路で駆除ツールを送り込むことを 妨げる向きに働く（本記録の読み。 ただし Huntress はこの意図を明言していない）。

Huntress の推奨対応は、この構造に対応している（出典1）。

  • ScreenConnect 経由で感染が疑われるホストに接続しない。EDR のライブレスポンス、WinRM など帯域外の手段を使う
  • 感染が疑われるホストは隔離する。ただし隔離だけでは永続化は除去されず、隔離解除後の再感染が観測されている
  • 不正クライアントのサービス、TrapWatch タスク、C:\ProgramData\RelayTrap\、%TEMP% 内の関連ファイル、RelayTrapLiteAlert の Run キーを削除する
  • 正規の ScreenConnect Web セッションを終了し、認証情報をローテーションする。盗まれたブラウザや IdP のセッションも無効化する
  • 再感染の確認が完了するまで、ホストを業務に戻さない

ConnectWise も同じ向きの注意を出している（出典2）〈重要〉—— 「拡張機能の無効化は予防的な封じ込めであり、 すでにデバイス上にある未承認のソフトウェア・永続化の仕組み・ アクセスが除去されたことを意味しない」 （原文英語。訳は本記録）。

検知の根拠についての注記も重要である（本記録の整理）。 Huntress は「ハッシュはスクリプトごとに再生成されるため、 検知の根拠としては弱い」としている（出典1） ——16ファイルに RelayTrap.cs というソース形式が含まれ、 一部は被害者の端末上でその場でコンパイルされる（出典1・4）。 したがって、ハッシュのブロックリストでは追えない（本記録の評価）。

技術者の端末を狙う設計は確認されたが、成立は確認されていない未確定事項出典 [1] [2] [4]

ここは、出典の間で確度が分かれている箇所である （本記録の整理）〈重要〉〈齟齬2〉。

| 出典 | 述べていること | | --- | --- | | Huntress（出典1） | 設計上は技術者の .aspxauth セッション Cookie を盗み、Shared Toolbox 経由で到達できるセッションへペイロードを配布する。ただし、エンドポイントから技術者端末への感染、技術者端末から他のエンドポイントへの感染が成功したことは確認していない。 回収できたログではコンソール乗っ取りの試みは失敗していた | | ConnectWise（出典4） | 対話型 ScreenConnect セッション中に技術者ワークステーションが侵害されたという報告を受けているが、これらの報告は確認中である | | BleepingComputer（出典4） | Huntress が「より危険な手法」として警告したと伝える一方、感染したエンドポイントから技術者ワークステーションへ広がる正確な仕組みは公表されていないとする |

本記録は、設計の存在と成立の確認を分けて記述する（本記録の明示）〈重要〉。 確認されているのは、SCKit にその機能が実装されていることである。 確認されていないのは、それが実際に働いたかである。

それでも、対応は「成立する前提」で取られている （本記録の整理）。 Huntress は「ScreenConnect 経由で感染が疑われるホストに接続しないこと」を 明記し、ConnectWise も技術者に対話型セッションを開始しないよう求めている （出典1・2）。 これは、確認を待たずに最悪の想定で動く判断である（本記録の評価） ——本記録はこの判断を妥当と評価する。 根拠は、仮に成立していた場合の影響が 「技術者の端末 → その技術者が触れる全セッション」へ広がることであり、 確認を待つ費用が高すぎることである。

読者にとっての含意は、調査の手段を事前に分けておくことである （本記録の評価）〈重要〉。 本件では、遠隔管理の基盤が侵害されたため、 その基盤を使って調査すること自体が危険になった。 EDR のライブレスポンス・WinRM・物理アクセスのいずれかを 平時から使える状態にしていない組織は、 調査に入る手段を失う（本記録の整理）。

拡張機能マーケットプレイスが、遠隔管理基盤の攻撃面になった評価・解釈出典 [2] [4]

ConnectWise が無効化した5つは、いずれも ScreenConnect の管理画面に組み込まれた拡張機能マーケットプレイス経由で 導入されるものである（出典2・4。本記録の整理）〈重要〉。

Labtech Plus／RMM Plus／RMM+／RMM Plus Password Link／RMM+ Password Link。

名称から読めることがある（本記録の読み）—— 「RMM Plus」「Password Link」はいずれも MSP の日常業務（遠隔管理の補助・認証情報の受け渡し）を 便利にする種類の名前である。 したがって、入れる動機がはっきりしており、 パートナーが自分の判断で入れたと考えられる（本記録の整理。 ただし ConnectWise は導入の経緯を説明していない）。

ConnectWise の説明の慎重さに注目する価値がある（本記録の評価）。

  • 「初期の評価では、攻撃者がパートナーが自環境に追加した独立したサードパーティ拡張機能を通じて追加のリモートアクセスソフトウェアを配布したと疑っている」（出典4。原文英語）
  • 「これらの拡張機能が入っていることは、ネットワークが侵害されたことを必ずしも意味しない」（出典2。原文英語）
  • 「拡張機能を導入していないパートナーが本件の影響を受けていると考える理由は無い」（出典4。原文英語）

3つ目は条件付きの安心の提示である（本記録の読み）〈重要〉—— 一方で同社は全パートナーに警戒を求めており、 初期侵入の経路は特定されていない〈未確定1〉。 つまり「拡張機能が無ければ安全」とは言い切られていない。

本記録が読む一般的な示唆は、基盤の拡張機構の棚卸しである （本記録の評価）〈重要〉。 遠隔管理基盤・SaaS 管理コンソール・CI/CD の多くは、 サードパーティの拡張を入れる仕組みを持つ。 拡張は基盤と同じ権限で動くことが多く、 基盤の権限が「他社の端末へのコマンド実行」である場合、 拡張の信頼性はその権限に等しい（本記録の整理）。 本件では、クラウド版は提供元がまとめて無効化できたが、 オンプレミス版はパートナー自身が無効化する必要があった（出典2） ——同じ事象でも、運用形態によって対処の主体が変わる。

日本の読者にとっての位置——MSP・SI 経由の遠隔管理は同じ構造を持つ評価・解釈出典 [1] [2] [3]

本件で日本の組織が影響を受けたという公表は確認していない （出典1・2・3・4。本記録の確認）〈未確定5〉。 本記録は、本件を日本と直接の関係が薄い事象として記録している。

それでも読む価値があるのは、構造が同じだからである（本記録の評価）〈重要〉。 日本でも、保守事業者・SI・社内IT部門が 遠隔管理ツールで端末へ到達する運用は広く行われている（本記録の整理）。 本件の構造を一般化すると次の3条件になる。

| 条件 | 本件での現れ方 | | --- | --- | | 外部の事業者が、自組織の端末へ SYSTEM 権限でコマンドを流せる | MSP の ScreenConnect の Run Command | | その権限の入口が、インターネットからアクセスできる管理画面である | クラウドホスト型 ScreenConnect のパネル | | 自組織側に、その権限の行使を記録・検知する仕組みが無い | Run Command の履歴は ScreenConnect 側にある |

3つ目が、自組織が取れる対策の所在を示す（本記録の評価）〈重要〉。 本件では、Run Command の履歴・Toolbox の記録・ インスタンスの監査ログはいずれも ScreenConnect 側にある（出典1・2）。 自組織の EDR や端末のログから見えるのは、結果だけである ——curl.exe が外部からインストーラを取得し、 msiexec.exe がサイレントインストールする動き（出典3）。

Sophos が示している検知の着眼点は、この結果の側にある（出典3）〈重要〉。

  • ScreenConnect のコマンド履歴に、想定外のクライアント配布や遠隔コマンドが無いかを確認する
  • curl や PowerShell が Windows の Temp からScreenConnect のインストーラやスクリプトを取得し、続いて msiexec.exe がインストールする動きを調査する

自組織で確認できることは3つある（本記録の判断）。 ①自組織の端末に常設されている遠隔管理エージェントを数え、 それぞれの提供元と、コマンドを流せる主体を書き出す。 ②そのエージェントが「想定外のインストーラを取得して実行する」動きを 自組織の EDR で検知できるかを確認する。 ③保守事業者に対し、その管理基盤への管理者サインインに MFA が強制されているかを確認する ——本件で ConnectWise が求めている措置の1つである（出典2）。

手順: **ConnectWise が、関連が疑われる5つのサードパーティ拡張機能を 約400のパートナー環境で予防的に無効化した**（出典2・4）。　副作用: **無効化は駆除ではない**（本記録の整理）〈重要〉—— **ConnectWise 自身が「拡張機能の無効化は予防的な封じ込めであり、 すでにデバイス上にある未承認のソフトウェア・永続化の仕組み・ アクセスが除去されたことを意味しない」と明記している** （出典2。原文英語。訳は本記録）。 **また、クラウド版は同社が一括で無効化できたが、 オンプレミス版はパートナー自身が行う必要がある**（出典2） ——**同じ事象でも、運用形態によって対処の主体と速度が変わる。** **さらに、無効化はパートナーが業務で使っていた機能を止めるため、 その機能に依存していた運用が止まる**（本記録の読み。 ただし ConnectWise は業務影響に言及していない）。

  • **外部の事業者が自組織の端末へ SYSTEM 権限でコマンドを流せる経路を数える**
    **本件で侵害されたのは1社ではなく、 「他社の端末にコマンドを流す権限」そのものである**（出典1・4。本記録の整理）〈重要〉。 **攻撃者は ScreenConnect の管理パネルを握り、 Run Command で管理対象エンドポイントへ SYSTEM 権限のコマンドを 一斉に送った**（出典1）。 **脆弱性は使われていない** ——**Huntress は「正規の機能の悪用に見える」としている**（出典4）。 **したがって、パッチでは防げない種類の事案である**（本記録の評価）。
    取るべき行動 **①自組織の端末に常設されている遠隔管理エージェントを数え、 それぞれについて「誰がコマンドを流せるか」を書き出す （保守事業者・SI・社内IT部門・製品ベンダー）。** **②そのうち SYSTEM 権限で任意のコマンドを実行できるものを特定する。** **③その権限の入口（管理コンソール）がインターネットから アクセスできるかを確認する。** **④契約上、その権限の行使の記録を自組織が参照できるかを確認する ——本件では Run Command の履歴は基盤側にある**（出典1・2）。
  • **配布が90分で終わる前提で、検知の目標を「配布前」と「配布後」に置き直す**
    **本件では、288台のうち約3分の1が最初の10分で侵害され、 全体は約90分で進行した**（出典1）〈重要〉。 **ConnectWise の advisory 公表は配布が終わった後である**（出典2。本記録の整理）。 **Run Command は端末群へ同時にコマンドを流す機能であるため、 攻撃者の作業量は「パネルの数」で決まり「端末の数」では決まらない** （本記録の整理） ——**台数が増えても配布時間は増えない。**
    取るべき行動 **①「配布を検知して止める」を目標から外す ——90分の窓では人の判断が間に合わない。** **②配布前の信号に投資する ——管理コンソールへの不審なサインイン、 想定外の管理者アカウントの追加（ConnectWise が advisory で 全パートナーに求めている確認項目である。出典2）。** **③配布後の駆除を手順にする ——不正クライアント・スケジュールタスク・Run キー・ 残存ファイルの除去と、再感染の確認**（出典1）。 **④保守事業者に、①②の記録を自組織へ提供できるかを確認する。**
  • **遠隔管理基盤が侵害されたときに使う「調査の手段」を、平時に1つ確保しておく**
    **本件では、Huntress・ConnectWise の双方が 「ScreenConnect 経由で感染が疑われるホストに接続しない」ことを 求めている**（出典1・2）〈重要〉。 **設計上、SCKit は技術者のセッション Cookie を盗み Shared Toolbox 経由でペイロードを配布するとされるためである**（出典1） ——**成立は確認されていないが、対応は成立する前提で取られている**〈齟齬2〉。 **代替として挙げられているのは EDR のライブレスポンス・WinRM など 帯域外の手段である**（出典1）。
    取るべき行動 **①主たる遠隔管理経路が使えないときに端末へ到達する手段を 1つ決め、平時に動作を確認しておく （EDR のライブレスポンス・別系統の管理ツール・物理アクセス）。** **②その手段が主たる経路と認証基盤を共有していないか確認する ——共有していると同時に失う。** **③保守事業者との契約に、 「主経路が使えない場合の調査手段」を明記する。** **④「隔離だけでは永続化は残る」ことを手順に書く ——Huntress は隔離解除後の再感染を観測している**（出典1）。
  • **基盤の拡張機構を棚卸しし、拡張の信頼性を基盤の権限と同じ重さで扱う**
    **ConnectWise が無効化した5つは、いずれも ScreenConnect の管理画面の拡張機能マーケットプレイス経由で 導入されるものである**（出典2・4）〈重要〉。 **名称（RMM Plus・Password Link 等）から、 MSP の日常業務を補助する種類のものと読める**（本記録の読み） ——**入れる動機がはっきりしている。** **基盤の権限が「他社の端末へのコマンド実行」である場合、 その拡張の信頼性はその権限に等しい**（本記録の整理）。 **ただし ConnectWise は、拡張機能が配布の経路であると 確認したわけではない**（出典2）〈未確定6〉。
    取るべき行動 **①自組織（または保守事業者）が使う管理基盤について、 導入されている拡張・プラグイン・連携アプリを一覧にする。** **②それぞれの提供元と、基盤上で持つ権限を書き出す。** **③「入れた理由」が説明できないものを外す。** **④クラウド版とオンプレミス版で対処の主体が変わることを確認する ——本件ではクラウド版は提供元が無効化できたが、 オンプレミス版はパートナー自身が行う必要があった**（出典2）。
  • **「侵害の確認が無い」を「影響が無い」と読み替えない運用にする**
    **本件では、確度の異なる表現が並んでいる**（本記録の整理）〈重要〉。 **①ConnectWise「拡張機能が入っていることは、 ネットワークが侵害されたことを必ずしも意味しない」**（出典2）。 **②同社「拡張機能を導入していないパートナーが 影響を受けていると考える理由は無い」**（出典4）。 **③Huntress「連番の攻撃者タグから、 以前に侵害された MSP が他にもあると示唆される。 アラートを受けていなくても Run Command の履歴を確認すべきだ」**（出典4）。 **②と③は向きが逆である**（本記録の読み） ——**②は条件付きの安心、③は未検知の存在の示唆である。**
    取るべき行動 **①ベンダーの「影響を受けていると考える理由は無い」を 自組織の確認の省略の根拠にしない。** **②自組織で確認できる項目（本件では Run Command の履歴、 不正クライアントの存在、スケジュールタスク、 Defender の除外設定の変更）を列挙し、実際に確認する。** **③確認の結果を記録に残す ——後続の公表で範囲が広がったときに、 どこまで確認済みかが分かる。**

    **顧客組織側の端末から見える唯一の材料がこれである** （本記録の整理）〈重要〉—— **Run Command の履歴は基盤側にしかない**（出典1・2）。 **Sophos が示している着眼点は、 「Windows Temp から ScreenConnect のインストーラやスクリプトを取得する `curl` と PowerShell の動き、および続く `msiexec.exe` のインストール」である** （出典3）。 **本件では `curl.exe` が `185[.]99[.]255[.]28` から `ScreenConnect.ClientSetup.msi` を `C:\Windows\TEMP\sc.msi` へ取得し、 ScreenConnect が生成したコマンドファイルが `msiexec.exe` を起動している**（出典3）。
    取るべき行動 **①自組織に常設されている遠隔管理エージェントの実行ファイル名を調べ、 その子プロセスとして `curl`／`powershell`／`msiexec`／ `cmd` が起動する事象を検知するルールを作る。** **②正規の運用でも起きる組み合わせを除外リストにして、 通知の量を実用的な水準に落とす ——除外リストそのものを変更記録として残す。** **③`%TEMP%` や `C:\Windows\TEMP` への `.msi`／`.ps1`／`.bat` の 作成と、その直後の実行を監視する。**
  • **端末上の遠隔管理クライアントの一覧を正として持ち、差分を取る**
    **本件では、正規の ScreenConnect クライアントとは別のIDを持つ クライアント（`2588ef5c15954b10`・`ed630cc2c873b091`）が 追加されている**（出典1・3）〈重要〉。 **Sophos はさらに、起点となった侵害インスタンスID 3件を挙げている**（出典3）。 **一方、`RelayTrap` は正規クライアントの接続枠を乗っ取るため、 単純な一覧では見えない部分がある**（出典1。本記録の読み）。
    取るべき行動 **①自組織の端末に入っている遠隔管理クライアントの インスタンスID／接続先を一覧にし、正として保存する。** **②定期的に差分を取り、知らないIDや接続先を洗い出す。** **③接続先ホスト名・リレー先も一覧に含める ——本件のリレーは `185.99.255[.]28`（ホスト名 screen）である**（出典1）。 **④ハッシュによる検知に頼らない ——Huntress は「ハッシュはスクリプトごとに再生成されるため 検知の根拠としては弱い」としている**（出典1）。
  • **エンドポイント保護の除外設定と SRP／AppLocker ルールの変更を、中央で記録する**
    **本件では、攻撃者が Microsoft Defender の除外設定を追加し、 さらに SRP／AppLocker ルールで 「ScreenConnect の一時フォルダから送られたファイルの実行」を ブロックしている**（出典1）〈重要〉。 **後者は、正規の管理者が同じ経路で対処することを妨げる向きに働く** （本記録の評価） ——**防御の道具が、駆除を妨げる道具として使われている。** **いずれも SYSTEM 権限で実行されるため、 端末上の権限では止められない**（出典1。本記録の読み）。
    取るべき行動 **①Defender の除外設定の一覧を中央に集め、 変更を通知する（頻度が低い操作なので通知が実用的である）。** **②SRP／AppLocker のルール集合を正として保存し、差分を取る。** **③除外設定とルールが端末ごとに異なっている状態を解消する ——差分の検出は、正が1つに決まっていて初めて成立する。**
  • **管理コンソールにアクセスする端末と、顧客端末へ対話接続する端末を分ける**
    **本件の設計が狙っているのは、 「顧客端末に接続した技術者の端末」である**（出典1）〈重要〉〈齟齬2〉。 **設計上は技術者の `.aspxauth` セッション Cookie を盗み、 Shared Toolbox 経由で到達できるセッションへ配布するとされる**（出典1）。 **成立は確認されていないが、 ConnectWise は対話型セッションを開始しないよう求め、 接続した技術者のワークステーションを調査対象に含めるよう求めている** （出典2・4）。 **接続の端末とコンソールの端末が同じなら、 1台の侵害で全セッションに届く**（本記録の整理）。
    取るべき行動 **①管理コンソールへのアクセスを、 専用の端末または専用のブラウザプロファイルに限る。** **②その端末から、顧客端末への対話接続を行わない。** **③セッション Cookie の有効期間を短くし、 IdP 側でセッションを即時に無効化できる手段を確認する ——ConnectWise は信頼できるデバイスからの セッション取り消しを求めている**（出典2）。 **④MFA を管理者サインインに強制する ——ただしセッションが盗まれる形では迂回されるため、 ③と組み合わせる**（本記録の整理）。
  • **駆除の手順を、永続化の痕跡の名前つきで書いておく**
    **本件では、隔離だけでは永続化が除去されず、 Huntress は隔離解除後の再感染を観測したとしている**（出典1）〈重要〉。 **除去の対象として挙げられているのは、 不正クライアントのサービス、`TrapWatch` タスク、 `C:\ProgramData\RelayTrap\`、`%TEMP%` 内の関連ファイル、 `RelayTrapLiteAlert` の Run キーである**（出典1）。 **同社は「再感染の確認が完了するまで ホストを業務に戻さない」ことを求めている**（出典1）。
    取るべき行動 **①侵害対応の手順を「隔離」「永続化の除去」「再感染の確認」 「業務復帰」の4段階に分け、それぞれの完了条件を書く。** **②永続化の捜索対象を種類で列挙する （サービス・スケジュールタスク・Run キー・ WMI サブスクリプション・常設ディレクトリ） ——名前は変えられるが、種類は変わらない。** **③再感染の確認期間を決める ——本件では隔離解除後の再感染が観測されている。** **④復旧の判断を、作業者ではなく別の人が行う形にする。**
