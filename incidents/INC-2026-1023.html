INC-2026-1023ScreenConnect悪用でMSP経由に侵害

クラウド版 ScreenConnect の管理パネルを握った攻撃者が Run Command で 管理対象エンドポイントへ不正な ScreenConnect クライアントと独自ツールキット「SCKit」を 一斉配布し、2026年11月11日 17:47 UTC から約90分で288台・48組織に及んだ ——ConnectWise はパートナーアカウントへの不正アクセスを認め、 関連が疑われる5つのサードパーティ拡張機能を約400のパートナー環境で無効化したが、 初期侵入の経路はまだ特定されていない ——Microsoft Threat Intelligence は2026年11月13日に SCKit の解析を公表し、 RelayTrap が技術者の `.ASPXAUTH` Cookie を Chrome／Edge／Opera から DPAPI で復号して奪い、Shared Toolbox 経由でペイロードを配る設計であること、 Defender の除外設定を書き込んで駆除の経路を塞ぐことを示した ——初期侵入の方法は Microsoft の公表でも「調査中」のままである。 一方 Huntress は11月14日、仮想通貨取引所の名を冠した偽の Access セッションが 118台のサーバー・109アカウントに2,223件登録されていたと公表した ——SCKit の公表済み指標との重なりは見つかっていない ——さらに Huntress は2026年11月16日、CVE-2026-84869 そのものの悪用を公表した ——2026年10月20日から11月16日までに42台の MSP の ScreenConnect サーバーへ 29の送信元IPから688,000回の「ファイル実行」要求が送られており、 11月12日には1社の技術者のワークステーションが9秒で侵害されている ——ただし Huntress は、この散布の運用者を SCKit とは別のものとして扱い、 SCKit 自身は CVE-2026-84869 を直接悪用していないと述べている。 SCKit の感染は11月13日の第2波（41組織・205台）を加えて計493台になった

侵害されたのは1社ではなく、「他社の端末にコマンドを流す権限」そのものでした。

2026年11月11日17時47分（UTC）ごろ、 クラウドホスト型の ScreenConnect 環境を狙う活動が始まりました（出典1・4）。 攻撃者は複数の ScreenConnect 管理パネルにアクセスし、 ScreenConnect の Run Command 機能を使って 管理対象のエンドポイントへ一斉にコマンドを送りました（出典1）。 コマンドは SYSTEM 権限で実行され、 攻撃者が管理する ScreenConnect クライアント（sc.msi）が サイレントインストールされました（出典1） ——正規の MSP の ScreenConnect 環境の外から、 その端末に入れる経路ができたことになります（出典4）。

Huntress は、同社の監視下で288台のエンドポイント・48組織が 影響を受けたとしています（出典1）。 288台のうち約3分の1は最初の10分で侵害され、全体は約90分で進みました（出典1）〈重要〉。 BleepingComputer は Huntress の初期の投稿を引いて 「MSP 6社、286台以上、47組織」と報じており、数値に食い違いがあります（出典4）〈齟齬1〉。

配布されたのは16ファイルからなる独自ツールキット「SCKit」です（出典1）。 機能は、①正規クライアントの接続枠を乗っ取る RelayTrap、 ②SYSTEM 権限で定期実行される TrapWatch スケジュールタスク、 ③Microsoft Defender の除外設定の追加、 ④SRP／AppLocker ルールによる 「ScreenConnect の一時フォルダから送られたファイルの実行」の阻止 ——の4つが挙げられています（出典1）〈重要〉。 ④は、正規の管理者が同じ経路で対処することを妨げる向きに働きます（本記録の評価）。

ConnectWise は同日のセキュリティ advisory で、 ScreenConnect のパートナーアカウントへの不正アクセスと、 顧客環境への未承認のリモートアクセスソフトウェアの導入を確認したとしました（出典2）。 関連が疑われる5つのサードパーティ拡張機能 （Labtech Plus／RMM Plus／RMM+／RMM Plus Password Link／RMM+ Password Link）を 約400のパートナー環境で予防的に無効化しています（出典2・4）。 同社は「無効化は予防的な封じ込めであり、 すでにデバイス上にある未承認のソフトウェア・永続化の仕組み・ アクセスが除去されたことを意味しない」と明記しています（出典2。原文英語。訳は本記録）〈重要〉。

本記録が最も重いと見るのは、調査の手段そのものが汚染されている点です（本記録の評価）。 Huntress は「ScreenConnect 経由で感染が疑われるホストに接続しないこと」を 明記しています（出典1。原文英語。訳は本記録）。 ConnectWise も、技術者が対話型の ScreenConnect セッションを 開始しないよう求め、別のセキュリティツールで調査するよう勧めています（出典2）。 設計上、SCKit は技術者の .aspxauth セッション Cookie を盗み、 Shared Toolbox 経由で到達できるセッションへペイロードを配布するとされますが、 Huntress はその成功を確認していないと明記しています（出典1）〈齟齬2〉。

初期侵入の経路は、本記録の確認時点でまだ特定されていません（出典1・2・4）〈未確定1〉。

Huntress が SCKit と名付けた16ファイルのツールキットの機能は、永続化と「対処の妨害」に向いている（出典1。本記録の整理）〈重要〉。

ConnectWise が無効化した5つは、いずれも ScreenConnect の管理画面に組み込まれた拡張機能マーケットプレイス経由で 導入されるものである（出典2・4。本記録の整理）〈重要〉。

名称から読めることがある（本記録の読み）—— 「RMM Plus」「Password Link」はいずれも MSP の日常業務（遠隔管理の補助・認証情報の受け渡し）を 便利にする種類の名前である。 したがって、入れる動機がはっきりしており、 パートナーが自分の判断で入れたと考えられる（本記録の整理。 ただし ConnectWise は導入の経緯を説明していない）。

ConnectWise の説明の慎重さに注目する価値がある（本記録の評価）。

  • 「初期の評価では、攻撃者がパートナーが自環境に追加した独立したサードパーティ拡張機能を通じて追加のリモートアクセスソフトウェアを配布したと疑っている」（出典4。原文英語）

本記録が読む一般的な示唆は、基盤の拡張機構の棚卸しである （本記録の評価）〈重要〉。 遠隔管理基盤・SaaS 管理コンソール・CI/CD の多くは、 サードパーティの拡張を入れる仕組みを持つ。 拡張は基盤と同じ権限で動くことが多く、 基盤の権限が「他社の端末へのコマンド実行」である場合、 拡張の信頼性はその権限に等しい（本記録の整理）。 本件では、クラウド版は提供元がまとめて無効化できたが、 オンプレミス版はパートナー自身が無効化する必要があった（出典2） ——同じ事象でも、運用形態によって対処の主体が変わる。

日本の読者にとっての位置——MSP・SI 経由の遠隔管理は同じ構造を持つ評価・解釈出典 [1] [2] [3]

それでも読む価値があるのは、構造が同じだからである（本記録の評価）〈重要〉。日本でも、保守事業者・SI・社内IT部門が遠隔管理ツールで端末へ到達する運用は広く行われている（本記録の整理）。本件の構造を一般化すると次の3条件になる。

  • curl や PowerShell が Windows の Temp からScreenConnect のインストーラやスクリプトを取得し、続いて msiexec.exe がインストールする動きを調査する

自組織で確認できることは3つある（本記録の判断）。①自組織の端末に常設されている遠隔管理エージェントを数え、それぞれの提供元と、コマンドを流せる主体を書き出す。 ②そのエージェントが「想定外のインストーラを取得して実行する」動きを自組織の EDR で検知できるかを確認する。 ③保守事業者に対し、その管理基盤への管理者サインインにMFA が強制されているかを確認する——本件で ConnectWise が求めている措置の1つである（出典2）。

管理面に足された拡張が、MFA の外側に遠隔コマンドの入口を作っていた原因・手口出典 [2] [7] [8]

第1回の続報で、疑いは「拡張の認証」に絞られた（出典2・7・8。事実）。

公表された形は次のとおりである。

  • RMM+ は ScreenConnect の外部から遠隔セッションを自動操作するための拡張で、遠隔コマンドを実行できる API を提供する（出典2）。
  • その API の認証は、ScreenConnect の利用者アカウント・ロール・MFA を使わず、導入時にパートナーが設定する共有のアクセスキー（パスフレーズ）で行われる（出典2・8）。
  • 1.0.31 と 1.0.32 では、管理者がキーを設定していない場合に空の値が認証検査を通った（出典7・8）。
  • Huntress が観測した活動は「ログイン活動を伴わないコマンド実行」で、ログはそのコマンドを RMM+ に結び付けていた（出典7・8）。
  • ConnectWise が確認した導入数は約400のパートナー環境で、同社は「存在するだけでは侵害は確定しない」と明記している（出典2）。

本記録はこの構図を、拡張固有の不具合としてではなく「管理面の認証の外に、もう一つの入口ができる」問題として読む（本記録の評価）〈重要〉。理由は、欠陥の中身（空のキーが通る）よりも、その API が最初から MFA の外側に置かれていたことのほうが再発しやすいからである。 MFA を強制していても、それを経由しない API が同じ権限を持っていれば、強制の効き目はその分だけ減る。 ConnectWise 自身の導入数の数え方（「少なくとも1つ入っている環境」）も、管理面に何が足されているかが提供元からも見えにくいことを示している（本記録の読み）。

自組織で確認できることは3つある（本記録の判断）——

  • 保守事業者の管理基盤に、どの拡張・連携・API キーが足されているかを一覧で出させる。 「MFA を強制しているか」ではなく「MFA を通らない経路があるか」を聞く。
  • その経路の認証が共有の鍵（パスフレーズ・アクセスキー）であれば、誰が持っているか・未設定のまま動いていないかを確認する。
  • 案件のために一時的に入れた拡張・連携が残っていないかを棚卸しする——本件で Huntress は、観測した RMM+ の導入の大半が「案件のために入れて、そのまま残されていた」正規のものだったと述べている（出典8）。

Microsoft の解析で分かったこと——RelayTrap は技術者の Cookie を取り、駆除の経路に先に除外設定を敷く原因・手口出典 [1] [2] [9]

2026年11月13日、Microsoft Threat Intelligence が SCKit の解析を公表した （出典9）〈重要〉—— 「ConnectWise が報告した活動を確認した」と明記しており、 基盤提供元の報告に第三者の裏付けが付いた形である（出典9。原文英語。訳は本記録）。

本記録が重いと見るのは3点である（本記録の評価）。

①永続化は3重で、どれも「クライアントを消す」では消えない（出典9）〈重要〉—— スクリプトは C:\ProgramData\RelayTrap に置かれ、 マシン全体の CurrentVersion\Run に RelayTrapLiteAlert が書かれ、 10秒間隔でポーリングする監視タスクがスケジュールされる。 監視役は ScreenConnect のクライアントサービスを列挙し、 そのクライアントのライブラリを使って RelayTrap の実行ファイルを 端末ごとに組み立てる（出典9）。 Microsoft は「未承認のクライアントを削除しただけでは、 ツールキットの永続化は除去されず、露出したウェブセッションも無効化されない」と 明記している（出典9。原文英語。訳は本記録）〈重要〉。

②Defender の除外設定を書き込み、ScreenConnect サービスを自動起動に変える（出典9）—— 第1報の時点で Huntress が挙げていた「SRP／AppLocker で ScreenConnect の一時フォルダからの実行を阻止する」設計（出典1）と合わせて読むと、 このツールキットは駆除の経路を先に塞ぐ向きに作られている（本記録の評価）〈重要〉。 防御側の道具と、防御側の配布経路の両方に手が入っている。

③窃取の対象は認証情報ではなくセッションそのものである（出典9）〈重要〉—— Chrome・Edge・Opera・Opera GX のプロファイルから .ASPXAUTH Cookie を探し、 ロックされたデータベースはボリュームシャドウコピーで回避し、 Chromium のマスターキーと Windows DPAPI で復号する。 さらにブラウザのネットワークサービスプロセスのメモリも走査する（出典9）。 得た Cookie に必要なトークンを足して到達可能なセッションを列挙し、 Shared Toolbox 経由でペイロードを配り、投入物を削除する（出典9）。 パスワードを変えても、MFA を足しても、 有効なセッション Cookie が手元にある間は止まらない（本記録の評価）—— だから ConnectWise も Microsoft も、 「ScreenConnect と IdP の有効セッションを無効化する」ことを対応に挙げている （出典2・9）。

一方で、初期侵入は Microsoft の公表でも埋まらなかった（本記録の確認）〈未確定1〉—— 「報告されたキャンペーンの侵入方法は調査中のままである」と記されている （出典9。原文英語。訳は本記録）。 ConnectWise が11月13日の更新でサードパーティ拡張に CVE-2026-127063 を採番したことも確認したが（出典2）、 同社は研究者の指摘を「評価中」としており、欠陥を確認したとは述べていない。 本記録は原因の軸に「不明」を残す（本記録の判断）。

ハッシュで追えない点も記しておく（本記録の明示）〈重要〉—— RelayTrap は各端末上で局所的にコンパイルされるため、 Microsoft 自身が「ハッシュは個々のファイルしか特定しない。 他のビルドを見つけるには挙動の指標を使うこと」と書いている （出典9。原文英語。訳は本記録）。 IOC の配布を受け取って終わりにすると、この攻撃は見つからない。

同じ製品に、別の何かが2,223件座っていた——仮想通貨取引所名の偽セッションと、SCKit との距離未確定事項出典 [10]

まず、これは SCKit と同じ活動だと断定されていない（本記録の明示）〈未確定10〉—— Huntress は「公表済みの SCKit 指標との重なりは見つかっていない」と 明記している（出典10。原文英語。訳は本記録）。 本記録は両者を同一視しない。 同じ製品が舞台であることと、同じ攻撃者であることは別である（本記録の整理）。

入口になったのは、認証なしで配られるインストーラである（出典10）〈重要〉—— ゲストクライアントが登録するにはサーバーのリレーアドレスが要り、 それはそのサーバーの Access インストーラに埋め込まれている。 最初に調べたサーバーではインストーラが公開状態で、 10月中旬にオンラインのファイル検査サービスがそれを取得していた（出典10）。 ScreenConnect は設計上、これらのインストーラを認証なしで配布する（出典10）。 つまり「インストーラの URL が外に出ている」ことが、 そのまま「他人が自分のコンソールに端末を並べられる」ことを意味する（本記録の評価）〈重要〉。

サーバー自体は侵害されていなかった（出典10）—— ウェブシェル・不審な子プロセス・新規アカウントのいずれも見つかっていない。 偽セッションはデータベース上の実在する登録であり、 攻撃者は約151秒ごとに同じ順でサーバーを巡回して接続を維持し、 1回の接続は約64分、再接続は約55分間隔だった（出典10）。 サンドボックスの検体実行による雑音だという見方について、 Huntress は——鍵を送らない・7種類のスクリーンショットを使い回す・ ハードウェアとOSの情報を無作為化する・10日間同じ順で巡回する——という点から エミュレータの特徴であり意図があると判断している（出典10）〈重要〉。

では何のためか。 Huntress の最有力の仮説は「餌」である（出典10）—— 技術者が接続してきたときに、 2026年9月8日に公表された CVE-2026-84869（ホストクライアント側の ファイル転送の権限不備）を突く機会を作る。 ただし同社は「そのように使われているのを観測していない」と明記している （出典10）〈未確定11〉。 1件だけ、技術者が長く留まって「テキスト送信」機能で遠隔側へ2回打ち込んだ例があり、 ScreenConnect は送信テキストを保持しないため、 Huntress は認証情報の露出の可能性として当該 MSP に連絡している（出典10）〈重要〉。

日本の読者にとっての含意は、SCKit の話より手前にある（本記録の評価）—— 自社の遠隔管理コンソールに、自社が入れていない端末が並んでいないかを 見たことがあるか、という問いである。 見分ける材料は公表されている（出典10）—— 会社名・サイト欄が空、ゲストのクライアント版が 25.3.4.9288、 ゲストの公開鍵が空、取引画面風のサムネイル、 単一の外部IPから短時間に多数の新規 Access ゲストが登録される。 消す前に App_Data\Session.db とその WAL ファイルを保全すること、 という手順も併せて示されている（出典10）—— 消してしまうと、技術者が接続したかどうかが分からなくなる。

緩和策
手順: **ConnectWise が、関連が疑われる5つのサードパーティ拡張機能を 約400のパートナー環境で予防的に無効化した**（出典2・4）。　副作用: **無効化は駆除ではない**（本記録の整理）〈重要〉—— **ConnectWise 自身が「拡張機能の無効化は予防的な封じ込めであり、 すでにデバイス上にある未承認のソフトウェア・永続化の仕組み・ アクセスが除去されたことを意味しない」と明記している** （出典2。原文英語。訳は本記録）。 **また、クラウド版は同社が一括で無効化できたが、 オンプレミス版はパートナー自身が行う必要がある**（出典2） ——**同じ事象でも、運用形態によって対処の主体と速度が変わる。** **さらに、無効化はパートナーが業務で使っていた機能を止めるため、 その機能に依存していた運用が止まる**（本記録の読み。 ただし ConnectWise は業務影響に言及していない）。
手順: **「ScreenConnect 経由で感染が疑われるホストに接続しない」ことを Huntress・ConnectWise の双方が求めた**（出典1・2）。　副作用: **調査と復旧の手段が1つ減る**（本記録の整理）〈重要〉—— **MSP の技術者にとって ScreenConnect は 顧客端末へ到達する主たる経路である。** **代替として挙げられているのは EDR のライブレスポンス・WinRM など 帯域外の手段である**（出典1） ——**これらを平時から使える状態にしていない組織は、 調査に入る手段を持たない**（本記録の評価）。
手順: **感染が疑われるホストを隔離する**（出典1）。　副作用: **隔離だけでは永続化が除去されず、 Huntress は隔離解除後の再感染を観測したとしている**（出典1）〈重要〉。 **したがって隔離は時間を稼ぐ措置であり、 その間に `TrapWatch` タスク・`C:\ProgramData\RelayTrap\`・ `%TEMP%` の関連ファイル・`RelayTrapLiteAlert` の Run キーの 除去を行う必要がある**（出典1。本記録の整理）。 **また、隔離は顧客組織の業務端末を止めるため、 Huntress は「再感染の確認が完了するまでホストを業務に戻さない」ことを 求めている**（出典1） ——**復帰の判断を早めると、再感染の形で戻る。**
手順: **正規の ScreenConnect Web セッションを終了し、 認証情報をローテーションする。 盗まれたブラウザや IdP のセッションも無効化する**（出典1・2）。　副作用: **初期侵入の経路が特定されていないため、 ローテーションが入口を閉じたかを確認できない**（本記録の評価）〈重要〉〈未確定1〉。 **Huntress の見立ては「侵害された認証情報、または 乗っ取られたオペレータのセッション」だが（出典4）、 確認されたものではない。** **ConnectWise は、信頼できるデバイスからこの作業を行い、 MFA を強制するよう求めている**（出典2） ——**侵害された技術者端末から行うと、新しい認証情報も盗まれる。**
手順: **認証・拡張機能のインストール・管理操作・Run Command・Toolbox の 各記録を保全し、不審なアカウント・権限変更・コマンドを調査する**（出典1・2）。　副作用: **記録は ScreenConnect 側にあるため、 顧客組織が自力で確認できない**（本記録の整理）〈重要〉。 **顧客組織の EDR から見えるのは結果だけである** ——**`curl.exe` によるインストーラの取得と `msiexec.exe` のサイレントインストール**（出典3）。 **Huntress は「アラートを受けていなくても Run Command の履歴を確認すべきだ」としており（出典4）、 これは MSP 側の作業である。**

    取るべき行動 **①自組織（または保守事業者）が使う管理基盤について、 導入されている拡張・プラグイン・連携アプリを一覧にする。** **②それぞれの提供元と、基盤上で持つ権限を書き出す。** **③「入れた理由」が説明できないものを外す。** **④クラウド版とオンプレミス版で対処の主体が変わることを確認する ——本件ではクラウド版は提供元が無効化できたが、 オンプレミス版はパートナー自身が行う必要があった**（出典2）。
  • **「侵害の確認が無い」を「影響が無い」と読み替えない運用にする**
    **本件では、確度の異なる表現が並んでいる**（本記録の整理）〈重要〉。 **①ConnectWise「拡張機能が入っていることは、 ネットワークが侵害されたことを必ずしも意味しない」**（出典2）。 **②同社「拡張機能を導入していないパートナーが 影響を受けていると考える理由は無い」**（出典4）。 **③Huntress「連番の攻撃者タグから、 以前に侵害された MSP が他にもあると示唆される。 アラートを受けていなくても Run Command の履歴を確認すべきだ」**（出典4）。 **②と③は向きが逆である**（本記録の読み） ——**②は条件付きの安心、③は未検知の存在の示唆である。**
    取るべき行動 **①ベンダーの「影響を受けていると考える理由は無い」を 自組織の確認の省略の根拠にしない。** **②自組織で確認できる項目（本件では Run Command の履歴、 不正クライアントの存在、スケジュールタスク、 Defender の除外設定の変更）を列挙し、実際に確認する。** **③確認の結果を記録に残す ——後続の公表で範囲が広がったときに、 どこまで確認済みかが分かる。**
セキュリティ技術者への示唆
  • **遠隔管理エージェントの子プロセスを、EDR の検知対象として明示的に作る**
    **顧客組織側の端末から見える唯一の材料がこれである** （本記録の整理）〈重要〉—— **Run Command の履歴は基盤側にしかない**（出典1・2）。 **Sophos が示している着眼点は、 「Windows Temp から ScreenConnect のインストーラやスクリプトを取得する `curl` と PowerShell の動き、および続く `msiexec.exe` のインストール」である** （出典3）。 **本件では `curl.exe` が `185[.]99[.]255[.]28` から `ScreenConnect.ClientSetup.msi` を `C:\Windows\TEMP\sc.msi` へ取得し、 ScreenConnect が生成したコマンドファイルが `msiexec.exe` を起動している**（出典3）。
    取るべき行動 **①自組織に常設されている遠隔管理エージェントの実行ファイル名を調べ、 その子プロセスとして `curl`／`powershell`／`msiexec`／ `cmd` が起動する事象を検知するルールを作る。** **②正規の運用でも起きる組み合わせを除外リストにして、 通知の量を実用的な水準に落とす ——除外リストそのものを変更記録として残す。** **③`%TEMP%` や `C:\Windows\TEMP` への `.msi`／`.ps1`／`.bat` の 作成と、その直後の実行を監視する。**
  • **端末上の遠隔管理クライアントの一覧を正として持ち、差分を取る**
    **本件では、正規の ScreenConnect クライアントとは別のIDを持つ クライアント（`2588ef5c15954b10`・`ed630cc2c873b091`）が 追加されている**（出典1・3）〈重要〉。 **Sophos はさらに、起点となった侵害インスタンスID 3件を挙げている**（出典3）。 **一方、`RelayTrap` は正規クライアントの接続枠を乗っ取るため、 単純な一覧では見えない部分がある**（出典1。本記録の読み）。
    取るべき行動 **①自組織の端末に入っている遠隔管理クライアントの インスタンスID／接続先を一覧にし、正として保存する。** **②定期的に差分を取り、知らないIDや接続先を洗い出す。** **③接続先ホスト名・リレー先も一覧に含める ——本件のリレーは `185.99.255[.]28`（ホスト名 screen）である**（出典1）。 **④ハッシュによる検知に頼らない ——Huntress は「ハッシュはスクリプトごとに再生成されるため 検知の根拠としては弱い」としている**（出典1）。
  • **エンドポイント保護の除外設定と SRP／AppLocker ルールの変更を、中央で記録する**
    **本件では、攻撃者が Microsoft Defender の除外設定を追加し、 さらに SRP／AppLocker ルールで 「ScreenConnect の一時フォルダから送られたファイルの実行」を ブロックしている**（出典1）〈重要〉。 **後者は、正規の管理者が同じ経路で対処することを妨げる向きに働く** （本記録の評価） ——**防御の道具が、駆除を妨げる道具として使われている。** **いずれも SYSTEM 権限で実行されるため、 端末上の権限では止められない**（出典1。本記録の読み）。
    取るべき行動 **①Defender の除外設定の一覧を中央に集め、 変更を通知する（頻度が低い操作なので通知が実用的である）。** **②SRP／AppLocker のルール集合を正として保存し、差分を取る。** **③除外設定とルールが端末ごとに異なっている状態を解消する ——差分の検出は、正が1つに決まっていて初めて成立する。**
  • **管理コンソールにアクセスする端末と、顧客端末へ対話接続する端末を分ける**
    **本件の設計が狙っているのは、 「顧客端末に接続した技術者の端末」である**（出典1）〈重要〉〈齟齬2〉。 **設計上は技術者の `.aspxauth` セッション Cookie を盗み、 Shared Toolbox 経由で到達できるセッションへ配布するとされる**（出典1）。 **成立は確認されていないが、 ConnectWise は対話型セッションを開始しないよう求め、 接続した技術者のワークステーションを調査対象に含めるよう求めている** （出典2・4）。 **接続の端末とコンソールの端末が同じなら、 1台の侵害で全セッションに届く**（本記録の整理）。
    取るべき行動 **①管理コンソールへのアクセスを、 専用の端末または専用のブラウザプロファイルに限る。** **②その端末から、顧客端末への対話接続を行わない。** **③セッション Cookie の有効期間を短くし、 IdP 側でセッションを即時に無効化できる手段を確認する ——ConnectWise は信頼できるデバイスからの セッション取り消しを求めている**（出典2）。 **④MFA を管理者サインインに強制する ——ただしセッションが盗まれる形では迂回されるため、 ③と組み合わせる**（本記録の整理）。
  • **駆除の手順を、永続化の痕跡の名前つきで書いておく**
    **本件では、隔離だけでは永続化が除去されず、 Huntress は隔離解除後の再感染を観測したとしている**（出典1）〈重要〉。 **除去の対象として挙げられているのは、 不正クライアントのサービス、`TrapWatch` タスク、 `C:\ProgramData\RelayTrap\`、`%TEMP%` 内の関連ファイル、 `RelayTrapLiteAlert` の Run キーである**（出典1）。 **同社は「再感染の確認が完了するまで ホストを業務に戻さない」ことを求めている**（出典1）。
    取るべき行動 **①侵害対応の手順を「隔離」「永続化の除去」「再感染の確認」 「業務復帰」の4段階に分け、それぞれの完了条件を書く。** **②永続化の捜索対象を種類で列挙する （サービス・スケジュールタスク・Run キー・ WMI サブスクリプション・常設ディレクトリ） ——名前は変えられるが、種類は変わらない。** **③再感染の確認期間を決める ——本件では隔離解除後の再感染が観測されている。** **④復旧の判断を、作業者ではなく別の人が行う形にする。**
