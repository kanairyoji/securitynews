INC-2026-1024AntiFox 悪用でAWS本番秘密に到達

中国語のオープンソース・エージェント型ペネトレーションテスト基盤「AntiFox」を Alibaba Cloud 上に自前で立てた攻撃者が、インターネット公開の IIS アプリに ASPX Web シェルを置いて web.config の接続文字列を読み出し、 有効な AWS の IAM ユーザーと EC2 のロールで約30分に数百のAPI呼び出しを行って 本番のシークレット取得と S3 オブジェクトの削除に至った ——Arctic Wolf Labs は「拒否が大半だったことを理由に攻撃が失敗したとは言えない」と警告している

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）公表されていない／不明
初報: 2026年11月10日（Arctic Wolf Labs の alert の日付） 最終更新: 2026年11月12日（本記録の作成。Arctic Wolf Labs の alert 原文を取得して確認）

攻撃の道具が「人が張りつく必要のないもの」になったときに、 防御側の読み方が1つ変わります。

Arctic Wolf Labs は2026年11月10日、 自前でホストするエージェント型ペネトレーションテスト基盤が パブリッククラウドから使われる動きを追跡していると公表しました（出典1）。 対象の1つが「AntiFox」です。 中国語のインターフェースを持つオープンソースの基盤で、 AI エージェントを配置して偵察・脆弱性の探索といった ペネトレーションテストの作業を自動化します（出典1・2）。 ARTEX 0.1.1 のフォークとして作られたとされます（出典2）。

Arctic Wolf は「最近観測された複数の侵入において、 AntiFox のインターフェースをホストする Alibaba Cloud のシステムが、 インターネット公開の Web サービスおよび関連する AWS 環境に対する 確認された悪性の行動に関連していた」としています （出典1・2・3。原文英語。訳は本記録）〈重要〉。

IIS 側の流れは次のとおりです（出典1・3）。 IIS のワーカープロセス w3wp.exe が ASPX の Web シェルを作り、 OS コマンドで実行コンテキストを確認（whoami）、 アプリのディレクトリを列挙、icacls で権限を確認、 Web ルートへの書き込み可否を試す。 続いて PowerShell で web.config の接続文字列とアプリ設定を解析し、 デバッグ・エラーログのディレクトリも列挙する。 抽出した認証情報で内部の本番データベースへの接続を試み、 最後に設定ファイルとログを Web から見えるアップロード用ディレクトリへコピーする。

AWS 側は速い（出典1・3）〈重要〉。 有効な IAM ユーザー、一部では EC2 の assumed role で GetCallerIdentity・GetUser・ListUsers・ListRoles・ListPolicies・ ListKeys といった ID と権限の探索を行い、 ECR の GetAuthorizationToken も試しています。 ある侵入では、複数の AWS の ID を切り替えながら 約30分で数百のAPI呼び出しを行いました（出典1・2・3）。 列挙の対象は IAM・EC2・S3・Lambda・Secrets Manager・KMS・RDS・ECS・EKS・ Redshift・Athena・Glue・Systems Manager・API Gateway・CloudWatch・ CloudFormation・DynamoDB・Amazon Bedrock に及びます（出典1・3）。

大半は AccessDenied で返りました。しかし一部は通りました（出典1・2・3）〈重要〉。 ListSecrets → GetSecretValue の連鎖が本番のシークレットの取得に成功した例があり、 別の侵入では有効な AWS の ID で S3 オブジェクトの 読み出し・コピー・削除が行われています（出典1・2・3）。

本記録が最も重いと見るのは、Arctic Wolf が付した警告の一文です（本記録の評価）。 「大半が拒否された一連の要求は、攻撃が失敗したことを意味しない」 （出典3が引用した同社の警告。原文英語。訳は本記録）〈重要〉。 自動化された基盤は、拒否を気にせず次を試します。 したがって拒否の山は、ノイズではなく探索の痕跡として読む必要があります。

AntiFox は本記録の確認時点で GitHub 上で入手でき、 バージョン2.0に更新されているとされます（出典2）。 公開者は実システムへの使用・現実のペネトレーションテストや演習での使用・ 破壊的または違法な活動を禁じていますが、 それを技術的に強制する仕組みは示されていません（出典2）。

「拒否が大半だった」は攻撃が失敗した証拠にならない——Arctic Wolf の警告がここにある評価・解釈出典 [1] [3]

本件で最も実務に効く一文は、Arctic Wolf の警告である（本記録の評価）〈重要〉。

「大半が拒否された一連の要求は、攻撃が失敗したことを意味しない」 （出典3が引用した同社の警告。原文英語。訳は本記録）。

同社の観測を並べると、この警告の根拠が見える（出典1・3）。

| 観測された事実 | 本記録の読み | | --- | --- | | 認可の失敗の後も、活動は他のサービスへ続き、到達できたリソースに集中した | 拒否は停止の合図ではなく、探索の結果として扱われている | | 大半の要求は AccessDenied だったが、一部は通った | 成功は拒否の山の中に埋まる | | ListSecrets → GetSecretValue の連鎖が本番シークレットの取得に成功した例がある | 埋まった成功が、最も重い結果を出した | | 約30分で数百のAPI呼び出し、複数の ID を切り替え | 人が張りつかない速度・量である |

自動化された基盤を使う攻撃者に、拒否の費用はほとんどない （本記録の整理）〈重要〉。 人が手で試すなら、拒否が続けば諦める。 エージェントは諦めない。 Security Affairs はこの性質を 「誰もその種の執拗さのために夜起きている必要はない。 それがこの道具の全体の要点である」と表現している （出典3。原文英語。訳は本記録）。

したがって、防御側の読み方を2つ変える必要がある（本記録の評価）〈重要〉。

①拒否の山を、ノイズではなく探索の痕跡として扱う。 Arctic Wolf のハンティングガイダンスは 「成功した呼び出しを、拒否のバーストの中で確認する」ことと、 「大半が拒否されたことを理由に無害と判断しない」ことを挙げている（出典1・3）。

②判定の単位を「1つの呼び出し」から「短時間の連なり」へ移す。 同社が挙げている着眼点は、 1つの送信元IPが短時間に複数のアクセスキー・IAM ユーザー・ assumed role を使っていないか、 複数サービスにまたがる List／Get／Describe の連続が無いか、 である（出典1） ——いずれも個別の呼び出しでは正常に見える。

入口は2つ——どちらも「どうやって入ったか」が特定されていない原因・手口出典 [1] [3]

Arctic Wolf は、観測された侵入の入口を2系統に分けている （出典1・3。本記録の整理）〈重要〉。

| 入口 | 公表されている内容 | 特定の状況 | | --- | --- | --- | | ① インターネット公開の IIS アプリケーションの侵害（Web シェル経由） | ASPX の Web シェルが w3wp.exe によって作成された | 悪用された脆弱性は特定できていない〈未確定1〉 | | ② 有効な AWS 認証情報 | IAM ユーザーと、一部では EC2 の assumed role | 入手の手段は分かっていない〈未確定4〉 |

①について、本記録は入口の示唆を1つだけ読む（本記録の読み）。 Arctic Wolf の IoC には、upload ディレクトリ配下のファイルパターンとして *.aspx・pwn*.aspx・cfg*.txt・wc*.txt・el*.txt が並び、 防御上の考慮では 「ファイル変換・アップロード・文書処理などユーザー入力を受けるサービスを 優先してパッチ・テスト・WAF 対応する」ことが挙げられている（出典1）〈重要〉。 アップロード機構が入口の候補として扱われていることは読めるが、 同社は本件の入口がそれだったとは述べていない（本記録の明示）。

②について、同社のハンティングガイダンスが示唆を含んでいる（本記録の読み）。 「1つの送信元IPが短時間に複数のアクセスキー・IAM ユーザー・ assumed role を使っていないか確認する ——収集した認証情報の自動検証の兆候である」（出典1）〈重要〉。 つまり、どこかで集めた認証情報の束を機械的に試している可能性である ——入手経路（インフォスティーラー・公開リポジトリへの流出・ フィッシング・購入）は公表されていない〈未確定4〉。

本記録が原因を credential-abuse と unknown の併記にしたのは、 この2系統に対応する（本記録の明示）。 ②の認証情報の悪用は確認されている。 ①の脆弱性は特定されていないため unknown である。

読者にとっての含意は、パッチで閉じる話ではないことである （本記録の評価）〈重要〉。 本件に「適用すべきCVE」は示されていない。 示されているのは、公開アプリの棚卸しと優先付け、 設定ファイル内の認証情報のローテーション、 アプリケーションの ID への最小権限の適用である（出典1） ——いずれも設計と運用の作業である。

web.config が、Web シェルから本番 DB と AWS の両方への鍵になった原因・手口出典 [1] [3]

IIS 側の手順は、設定ファイルの読み出しに向かって一直線である （出典1・3。本記録の整理）〈重要〉。

| 段階 | 観測された行動 | | --- | --- | | 1 | w3wp.exe が ASPX の Web シェルを作成 | | 2 | 実行コンテキストの確認（whoami）、アプリディレクトリの列挙 | | 3 | icacls による権限確認、Web ルートへの書き込み可否のテスト | | 4 | PowerShell で web.config の接続文字列とアプリ設定を解析 | | 5 | デバッグ・エラーログのディレクトリの列挙 | | 6 | 抽出した認証情報で内部の本番データベースへの接続を試行 | | 7 | 設定ファイルとログを Web から見えるアップロード用ディレクトリへコピー |

4が本件の転換点である（本記録の評価）〈重要〉。 Arctic Wolf が PowerShell 内の探索対象として挙げているのは WebConfigurationManager・WebConfigurationFileMap・ VirtualDirectoryMapping・ConnectionStrings・ AppSettings.Settings・[IO.File]::ReadAllText である（出典1） ——.NET の設定クラスを使って設定を読む、正規の作法である。

7が持ち出しの形である（本記録の整理）。 設定とログを「Web から見えるディレクトリ」へコピーしておけば、 Web シェルを経由せずに HTTP で取り出せる（本記録の読み）。 IoC に cfg*.txt・wc*.txt・el*.txt が並ぶのはこれに対応する（出典1） ——Arctic Wolf は 「設定やログを .txt や画像拡張子などで Web 公開ディレクトリに コピーした痕跡も疑う」としている。

本記録が重いと見るのは、6と AWS 側の接続の両方が 同じ設定ファイルから始まっている点である（本記録の評価）〈重要〉。 同社の防御上の考慮では、ローテーションの対象として 「web.config・アプリ設定・デプロイ成果物・デバッグログ・ 環境変数・バックアップ設定に含まれる認証情報 （DB資格情報・AWS アクセスキー・API トークン・暗号鍵・ アプリのシークレットを含む）」が列挙されている（出典1）。 つまり、1つのファイルから内部 DB とクラウドの両方へ届く構成が 前提になっている。

ただし、Arctic Wolf はこの構成を原因として述べていない（本記録の明示） ——.NET アプリの標準的な作りであり、 本記録もこれを「原因」ではなく「増幅の条件」として扱う。 読者が確認できるのは、 「自社の公開アプリの設定ファイルから、 どこまで到達できるか」を書き出すことである（本記録の判断）。

AWS 側では、18のサービスを順に叩いて開いている扉だけを押した被害規模・影響範囲出典 [1] [2] [3]

AWS 側の手順は、ID の確認 → 権限の棚卸し → 広域の列挙 → 通ったところへの集中、という順である（出典1・3。本記録の整理）〈重要〉。

| 段階 | 観測された呼び出し | | --- | --- | | 1 | GetCallerIdentity・GetUser（自分は誰か） | | 2 | ListUsers・ListRoles・ListPolicies・ListKeys（何があるか） | | 3 | ECR の GetAuthorizationToken（コンテナレジストリの資格） | | 4 | 18のサービスを List／Get／Describe で広域に列挙 | | 5 | 認可の失敗の後も続け、アクセスできたリソースに集中 | | 6 | ListSecrets → GetSecretValue（本番シークレットの取得に成功した例がある） | | 7 | S3 の列挙 → GetObject・CopyObject・DeleteObject |

4で並んでいるサービスが、本記録の着眼点である（本記録の評価）〈重要〉。 IAM・EC2・S3・Lambda・Secrets Manager・KMS・RDS・ECS・EKS・ Redshift・Athena・Glue・Systems Manager・API Gateway・CloudWatch・ CloudFormation・DynamoDB・Amazon Bedrock（出典1・3）。 本記録が数えて18である（本記録の算出） ——Arctic Wolf の原文は「含む」としており、全部とは述べていない。

互いに無関係なサービスが並んでいることが信号になる（本記録の評価）。 用途の決まったアプリケーションの ID が、 Redshift と Athena と Bedrock を順に叩くことは 正常な運用では起きにくい（本記録の整理）。 Arctic Wolf のハンティングガイダンスが 「複数サービスにまたがる List／Get／Describe の連続を探す。 新規ホスティング ASN や Boto3／Botocore などのスクリプト系 SDK と 組み合わさると確度が上がる」としているのはこれに対応する（出典1）〈重要〉。 IoC に User-Agent として Boto3/1.43.125・Botocore/1.43.125 が挙げられている（出典1）。

6と7が結果である（本記録の整理）。 本番シークレットの取得に成功した例があり、 別の侵入では S3 オブジェクトの読み出し・コピー・削除が行われた （出典1・2・3）〈重要〉。 削除の件数、バージョニングや Object Lock の設定状況、 復元の可否は公表されていない〈未確定7〉。

3つ目に自組織で確認できる余地がある（本記録の判断）〈重要〉。 Arctic Wolf の防御上の考慮から、自組織で確認できる項目を抜き出すと 次のようになる（出典1。本記録の整理）。

    **本件で使われたのは、公開されているオープンソースの基盤である** （出典1・2）〈重要〉。 **AntiFox は本記録の確認時点で GitHub 上で入手でき、 バージョン2.0に更新されているとされる**（出典2）。 **Arctic Wolf は「この種のフレームワークは、 攻撃者にとってペネトレーションテストの手法を扱いやすくし、 実際の攻撃を速く一貫して実行できるようにする」としている** （出典1・3。原文英語。訳は本記録）。 **新しい技術が生まれたという話ではなく、 既知の手法が速く・一貫して・安く実行されるようになったという話である** （本記録の読み） ——**技能の必要量が道具に吸収されると、 対象の選び方は「価値があるか」より「届くか」に寄る**（本記録の評価）。
    取るべき行動 **①自組織のリスク評価で「攻撃者の技能」を前提にしている箇所を洗い出し、 その前提を外して再評価する。** **②対象の選び方が「届くか」に寄ることを前提に、 インターネットから到達できる資産の数を優先的な指標にする。** **③攻撃の速度を見積もりに入れる ——本件では約30分で数百のAPI呼び出しが行われている**（出典1）。 **④「自社は狙われるほどの価値がない」という説明を 経営への報告から外す。**
  • **「拒否が大半だった」を安心の根拠にしない運用にする**
    **Arctic Wolf は「大半が拒否された一連の要求は、 攻撃が失敗したことを意味しない」と明記している** （出典1・3。原文英語。訳は本記録）〈重要〉。 **本件では、認可の失敗の後も活動が他のサービスへ続き、 アクセスできたリソースに集中した**（出典1）。 **その結果、`ListSecrets` → `GetSecretValue` の連鎖が 本番シークレットの取得に成功している**（出典1・3）。 **自動化された基盤を使う攻撃者に、拒否の費用はほとんどない** （本記録の整理） ——**人なら諦めるところで、機械は次を試す。**
    取るべき行動 **①セキュリティ運用の報告で 「アクセス拒否が大量に発生したが被害は無い」という結論を そのまま受け取らない。** **②拒否のバーストが起きた場合に 「その中で成功したものは何か」を必ず確認する手順にする。** **③その確認ができるログ（CloudTrail の管理イベント）が 取られているかを先に確認する。** **④確認の結果を記録に残す ——同じ送信元が後日戻ってきたときに比較できる。**
  • **公開アプリの設定ファイルから、どこまで到達できるかを棚卸しする**
    **本件では `web.config` の接続文字列とアプリ設定が 転換点になっている**（出典1・3）〈重要〉。 **抽出した認証情報で内部の本番データベースへの接続が試みられ、 AWS 側の活動もこの段階の後に始まっている**（出典1・3）。 **Arctic Wolf がローテーションの対象として挙げているのは `web.config`・アプリ設定・デプロイ成果物・デバッグログ・ 環境変数・バックアップ設定に含まれる DB資格情報・AWS アクセスキー・API トークン・暗号鍵・ アプリのシークレットである**（出典1） ——**1つのファイルから内部とクラウドの両方へ届く構成が前提にある。**
    取るべき行動 **①インターネットに公開しているアプリケーションごとに、 その設定ファイル・環境変数・デプロイ成果物に 何の認証情報が入っているかを書き出す。** **②それぞれの認証情報で到達できる先（データベース・ クラウドAPI・外部サービス）を書き出す。** **③「1つ露出したら何が巻き込まれるか」を一覧にする ——侵害時のローテーションの範囲がそれで決まる。** **④ローテーションの手順と所要時間を事前に測る ——相互に依存する認証情報は、順序を誤るとアプリが止まる。**
  • **アプリケーションの ID の権限を、「何ができるか」ではなく「何が見えるか」で点検する**
    **本件で観測されたのは、18のサービスに対する `List`／`Get`／`Describe` の連続である**（出典1・3）〈重要〉。 **IAM・EC2・S3・Lambda・Secrets Manager・KMS・RDS・ECS・EKS・ Redshift・Athena・Glue・Systems Manager・API Gateway・CloudWatch・ CloudFormation・DynamoDB・Amazon Bedrock**（本記録が数えて18）。 **列挙の多くは拒否されたが、一部は通った**（出典1）。 **Arctic Wolf は防御上の考慮で 「アプリケーションの ID に最小権限を適用し、 アカウント全体にわたる広範な一覧権限を持たせない」ことを 挙げている**（出典1）。
    取るべき行動 **①アプリケーションが使う ID（IAM ユーザー・ロール）について、 「書き込み・変更の権限」とは別に 「一覧・参照の権限」を洗い出す ——後者は害が無いと見られて残りやすい。** **②その ID で現在どのサービスを列挙できるかを実際に試す （自組織の環境での確認作業として）。** **③アカウント全体にわたる一覧権限を外す。** **④EC2 のインスタンスロールが必要な場合は IMDSv2 を強制し、 メタデータ応答のホップ数制限を厳しくする**（出典1の推奨） ——**古い SDK やスクリプトが動かなくなる余地があるため、 事前の確認が要る**（本記録の注記）。
  • **IoC のうち IP とハッシュに依存した対策を作らない**
    **Arctic Wolf 自身が 「IoC は網羅的ではなく、パブリッククラウドのIPは 別のテナントに再割り当てされる可能性がある」と注記している** （出典1）〈重要〉。 **本件の送信元IPは Alibaba Cloud の2件であり、 同じアドレスが後に無関係のテナントに割り当てられうる**（本記録の整理） ——**遮断リストに入れたままにすると、 正規の通信を止める副作用が生じる。** **一方、挙動に基づく IoC（親子関係・API のシーケンス・ PowerShell の参照）は変わりにくい**（本記録の評価）。
    取るべき行動 **①IoC を受け取ったら、 「値そのもの（IP・ドメイン・ハッシュ）」と 「挙動（プロセスの親子関係・API の順序）」に分ける。** **②前者には期限を付け、期限が来たら見直す。** **③後者を検知ルールの中心にする。** **④本記録に記載した IoC の悪性は、 本記録も独自に検証していない ——照合先のテレメトリが無いため検知には使わない。**
セキュリティ技術者への示唆
  • **IIS のワーカープロセスの子プロセスを検知する。本件で最も安く作れる**
    **Arctic Wolf が IoC として挙げた親子関係は `w3wp.exe → cmd.exe`・`w3wp.exe → powershell.exe`・ `w3wp.exe → where.exe`・`cmd.exe → whoami.exe`・ `cmd.exe → icacls.exe` である**（出典1）〈重要〉。 **IIS のワーカープロセスがシェルやインタプリタを起動することは、 正常な運用では少ない**（本記録の整理）。 **同社は防御上の考慮で 「IIS ワーカープロセスが想定外のシェルやインタプリタを起動したら、 そのサーバを直ちに隔離する」ことを挙げている**（出典1・3）。
    取るべき行動 **①まず正常時の棚卸しを行う ——自組織の IIS で `w3wp.exe` が子プロセスを起こす構成 （デプロイ時のフック・外部コマンドの呼び出し）を洗い出す。** **②それ以外の子プロセスを検知するルールを作る。** **③検知時の手順を書く （隔離 → Web ルート・IIS ログ・エンドポイントテレメトリ・ メモリの保全 → 再イメージ化）**（出典1の推奨）。 **④自動隔離を入れるのは①が済んだ後にする ——誤検知で公開アプリが止まる。**
  • **PowerShell のスクリプトブロックログを有効にし、設定クラスへの参照を探す**
    **本件では PowerShell で `web.config` の接続文字列と アプリ設定が解析されている**（出典1・3）〈重要〉。 **Arctic Wolf がハンティングガイダンスに挙げた参照先は `WebConfigurationManager`・`WebConfigurationFileMap`・ `VirtualDirectoryMapping`・`ConnectionStrings`・ `AppSettings.Settings`・`[IO.File]::ReadAllText` である**（出典1） ——**.NET の設定クラスを使う正規の作法であり、 難読化されていれば見えないが、 平文であれば文字列として残る**（本記録の整理）。
    取るべき行動 **①Windows Server の PowerShell の スクリプトブロックログを有効にする （取っていなければ、この検知も事後の捜索も成立しない）。** **②上記の文字列を含む実行を検索するクエリを作り、 過去のログに対して1回実行する。** **③以後は通知にする ——正規の運用でこれらを参照するスクリプトがあれば除外する。** **④保存期間を、侵害の判明から遡れる長さにする。**
  • **AWS の判定単位を「1つの呼び出し」から「短時間の連なり」へ移す**
    **本件の呼び出しは、個別には正常に見える**（本記録の整理）〈重要〉—— **`GetCallerIdentity`・`ListUsers`・`ListBuckets` は いずれも正規の運用で呼ばれる。** **異常なのは連なりである**（出典1）。 **Arctic Wolf が挙げた着眼点は、 ①対象の ID にとって初めてのホスティング事業者／AS からの呼び出し、 ②1つの送信元IPが短時間に複数のアクセスキー・IAM ユーザー・ assumed role を使う兆候（収集した認証情報の自動検証の兆候）、 ③複数サービスにまたがる `List`／`Get`／`Describe` の連続 （Boto3／Botocore などのスクリプト系 SDK との組み合わせで 確度が上がる）——である**（出典1）。
    取るべき行動 **①CloudTrail の管理イベントを有効にし、 呼び出し元の IP・ASN・User-Agent を保持する。** **②「同一送信元IPが15分以内に3つ以上の異なる ID を使った」 という条件で検知を作る（しきい値は自組織の運用から決める）。** **③「同一 ID が15分以内に5つ以上の異なるサービスへ `List`／`Describe` を行った」という条件を加える。** **④IoC の API シーケンス （`ListSecrets` → `GetSecretValue`、 `GetCallerIdentity` → `ListBuckets`、 `ListBuckets` → `ListObjects`、 `ListObjects` → `HeadObject`、 `ListObjects` → `GetObject`）を検知の形にする**（出典1）。
  • **シークレットの読み出しを、ID だけでなく呼び出し元のネットワークで絞る**
    **本件では、有効な ID で外部のホスティング事業者 （Alibaba Cloud）から `GetSecretValue` が成功している** （出典1・2・3）〈重要〉。 **ID が有効であることと、 その ID が本来の場所から使われていることは別である**（本記録の整理）。 **Arctic Wolf が挙げているのは最小権限と通知だが、 呼び出し元のネットワークを条件に入れる統制は明示していない** （本記録の明示） ——**本記録はこれを有効な補強として挙げる。**
    取るべき行動 **①シークレットを読み出す ID を列挙し、 それぞれが正常時にどこから呼ばれるかを把握する。** **②VPC エンドポイント経由のみを許可する条件、 または送信元の条件を IAM ポリシーに加えられるか検討する。** **③加えられない場合は、 成功した `GetSecretValue` を呼び出し元とともに通知する （とくに広範な列挙や拒否の後に続く場合）**（出典1の推奨）。 **④「新規インフラ」の判定には過去の呼び出し元の履歴が要る ——履歴を蓄積する仕組みを先に作る。**
  • **S3 の削除権限を、アプリケーションの ID から外せるか検討する**
    **本件では、有効な AWS の ID で S3 オブジェクトの読み出し・コピー・削除が行われている** （出典1・2）〈重要〉。 **Arctic Wolf はバージョニングと Object Lock を推奨しているが、 これは影響の限定であり削除そのものは防げない**（出典1・3。本記録の整理）。 **読み出しが必要なアプリケーションに 削除権限が付いている構成は珍しくない**（本記録の評価） ——**削除をライフサイクルポリシーに任せれば、 アプリの ID に削除権限は要らない。**
    取るべき行動 **①バケットごとに、どの ID が `DeleteObject` を持つかを洗い出す。** **②アプリケーションの運用上、削除が本当に必要かを確認する （ライフサイクルポリシーで代替できないか）。** **③重要バケットにバージョニングを有効にし、 必要に応じて Object Lock を設定する ——保持期間の設計が要る（正規の削除も妨げる）**（出典1の推奨）。 **④重要バケットの S3 データイベントを有効にして、 オブジェクト単位の操作を記録する ——量と費用が増えるため対象を絞る。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ インターネットに公開した IIS／.NET アプリケーションがあり、 その背後に AWS 環境がある
データの保持□ 公開アプリの設定ファイル（web.config 等）・環境変数・ デプロイ成果物に、本番データベースやクラウドの認証情報が置かれており、 「1つ露出したら何に届くか」を一覧にしていない
認証・認可□ アプリケーションが使う AWS の ID に、 アカウント全体にわたる広範な一覧（List／Describe）権限が付いている
認証・認可□ シークレットやオブジェクトの読み出しを ID だけで許可しており、 呼び出し元のネットワークを条件に入れていない
運用・監視□ CloudTrail の管理イベントを有効にしていない、 または有効だが「拒否のバーストの中の成功」を確認する手順が無い
運用・監視□ IIS のワーカープロセスが cmd／powershell 等を起動する事象を 検知できない、または正常時にその親子関係が出る構成を棚卸ししていない
運用・監視□ 重要な S3 バケットにバージョニングが無く、 アプリケーションの ID に DeleteObject 権限が付いている
