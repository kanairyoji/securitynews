INC-2026-1031Apache mod_http2 に無認証RCE

Apache HTTP Server の開発チームが2026年11月11日に 2.4.71 を公開し、 mod_http2 の `assign_headers()` におけるスレッド安全性の欠陥（CVE-2026-119618）に **自身の最上位ラベル「critical」**を付けた。 共有資源の同期不備（複数スレッドが同じメモリを書き換える）によりヒープが壊れ、 **無認証の遠隔攻撃者が任意コードを実行しうる**という評価で、 影響は 2.4.55〜2.4.70（GitHub 版 mod_h2 は 2.0.8〜2.0.42）。 Red Hat は CVSS 3.1 で 9.8（`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`）を付け、 **`Protocols` ディレクティブで HTTP/2（h2 / h2c）を有効にしているサーバだけが対象**で 「HTTP/1.1 のみを提供する構成は脆弱ではない」と明記した。 同じ Red Hat の同じページが、全体としては Critical、 **RHEL 9 と RHEL 10 については「Critical ではなく Important」**という二重のラベルを示している

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月11日 最終更新: 2026年11月12日

2026年11月11日に公開された Apache HTTP Server 2.4.71 は、3件の CVE に対処した。内訳は critical 1件・important 1件・low 1件で、critical は mod_http2 の CVE-2026-119618である（出典1）。

欠陥は assign_headers() にある。 Apache の記述は「共有資源を用いた並行実行の同期不備」であり、Red Hat はこれを「あるスレッドが別のスレッドの持つメモリを書き換え、サーバのメモリを壊す」と言い換えている（原文英語。出典1・2）。結果として、無認証の遠隔攻撃者が任意のコマンドを実行しうるという評価である（出典2）。Red Hat の CVSS 3.1 基本値は 9.8、ベクタはCVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H—— 権限も利用者の操作も要らない。

ただし成立には構成の条件が付く。 Red Hat は「Protocols ディレクティブを通じて HTTP/2（h2 または h2c）を有効にしているサーバだけが影響を受ける」「HTTP/1.1 のみを提供するよう構成されたサーバは脆弱ではない」と明記した（原文英語。出典2）。影響範囲は 2.4.55〜2.4.70で、2.4.54 以前と、RHEL 8 以前の Red Hat 製品は対象外とされている（出典1・2）。

本記録が注目するのは、ラベルの付き方が前回と逆転したことである。 2026年10月1日の 2.4.69 では、CVE レコードの CVSS が 9.8 に達していたのにApache 自身のラベルは「中（moderate）」止まりで、critical・important は1件も付いていなかった（本DB INC-2026-0320）。今回は Apache 自身が critical を付けている。一方で Red Hat は、全体としては Critical としながらRHEL 9・RHEL 10 については「Critical ではなく Important」と書いている（出典2）。「どのラベルを見るか」で対応期限が変わる構図は、前回と同じまま残っている。

前回は「クリティカル無し」で済んだが、今回は Apache 自身が critical を付けた概観

2.4.71 が対処したのは3件。 Apache 自身のラベルは critical 1件・important 1件・low 1件で、critical は mod_http2 の CVE-2026-119618 である（出典1）。

  • CVE-2026-119618（critical / mod_http2） — assign_headers() におけるヒープ破壊と RCE
  • CVE-2026-106023（important / mod_md） — NULL ポインタ参照により子プロセスがクラッシュ
  • CVE-2026-109163（low / mod_vhost_alias） — 1バイトのスタック上書き（CVE-2026-63292 の後に判明）

これは前回と比べて意味のある変化である。 2026年10月1日の 2.4.69 では、CVE レコードの CVSS が 9.8（mod_http2 の CVE-2026-57941）に達していたのに、Apache 自身のラベルは「中（moderate）」が最高で、critical・important は1件も無かった（本DB INC-2026-0320）。ラベルだけを対応の起動条件にしている組織は、前回を見送って今回は動くことになる。

ただし今回も、見るラベルによって答えが変わる構図は残っている。 Red Hat Product Security の総合評価は Critical だが、同じページが「RHEL 9 と RHEL 10 については Critical ではなく Important」と書いている（出典2）。RHEL を使っている組織が自社のラベルだけを見ると、Important として扱うことになる。

成立条件は「HTTP/2 を有効にしているか」の一点に集約される原因・手口

欠陥の中身は、共有資源に対する同期の不備である。 Apache の記述は "Concurrent Execution using Shared Resource with Improper Synchronization vulnerability in Apache HTTP Server's mod_http2 in assign_headers() can lead to RCE."（「Apache HTTP Server の mod_http2 のassign_headers() における、共有資源を用いた並行実行の同期不備の脆弱性がリモートコード実行に至りうる」。原文英語。出典1）。

Red Hat の言い換えのほうが、運用者には分かりやすい。「これはスレッド安全性のバグである。あるスレッドが別のスレッドの持つメモリを書き換えることができ、サーバのメモリを壊す。遠隔の、認証されていない攻撃者が任意のコマンドを実行しうる」（原文英語。出典2）。

判定の条件は2つだけである（出典1・2。事実）。

  1. バージョンが 2.4.55〜2.4.70 であること。 2.4.54 以前は対象外。GitHub 配布版の mod_h2 を単体で入れている場合は 2.0.8〜2.0.42。
  2. Protocols ディレクティブで HTTP/2（h2 または h2c）を有効にしていること。 Red Hat は「HTTP/1.1 のみを提供するよう構成されたサーバは脆弱ではない」と明記した。

この2条件のどちらかが外れていれば該当しない。逆に、両方に当たる公開サーバは PR:N/UI:N——権限も利用者の操作も要らずにインターネット側から届く（出典2）。

実務上の難所は、2 の把握である（本記録の評価）。HTTP/2 は性能のために有効化されることが多く、リバースプロキシやロードバランサの前段で入れた担当者と、httpd のバージョンを管理している担当者が別になっている組織では、「自社は該当するのか」の即答ができない。

競合状態であることは、安心の材料にはならない評価・解釈

以下は本記録の評価である（公表資料は悪用について何も述べていない）。

競合状態（race condition）を突く欠陥は、タイミングに依存するため、安定して動く実証コードを作るのが難しい側面がある。単発のリクエストで確実に発火する種類の欠陥とは、悪用までの距離が違う。

しかしそれを根拠に優先度を下げるのは筋が悪い（本記録の評価）。理由は3つある。

  • HTTP/2 は多重化が前提のプロトコルである。 1本の接続で多数のストリームを並行に流せるため、攻撃者がタイミングを試す回数を稼ぎやすい。「競合状態だから起こりにくい」という直感は、HTTP/2 の文脈では弱まる。
  • 成功しなくても害が出る。 ヒープ破壊が失敗すれば子プロセスが落ちる。任意コード実行に至らないまま、可用性だけが削られる状態はありうる。
  • Apache 自身が critical を付けた。 前回 9.8 の CVSS に対して moderate で済ませたプロジェクトが、今回は最上位を付けている（出典1・本DB INC-2026-0320）。ラベルを保守的に運用してきた主体の判断が変わったことには、重みがある。

「悪用の報告が無い」は、安全の証明ではなく情報の不在である〈未確定1〉。

更新が止まる環境では、HTTP/2 の停止が一時措置になりうる対策・注意喚起

公表された対策は 2.4.71 への更新だけである（出典1。事実）。本記録が取得した範囲では、Apache も Red Hat も回避策を示していない〈未確定2〉。

ただし、成立条件の記述から一時措置は読み取れる（本記録の読み）。Red Hat が「HTTP/1.1 のみを提供するよう構成されたサーバは脆弱ではない」と書いている以上（出典2）、Protocols から h2 / h2c を外せば成立条件を外せる。

代償は明示しておく必要がある（本記録の評価）。

  • 性能が落ちる。 多重化・ヘッダ圧縮・サーバプッシュを捨てることになり、リソースの多いページでは体感に出る。
  • gRPC が止まる可能性がある。 h2c を前提にした内部通信をhttpd で中継している構成では、止めた瞬間に業務が壊れる。
  • 恒久策ではない。 更新できるまでの時間を買う措置である。

順序は、①該当台の洗い出し → ②更新できる台は更新 → ③更新できない台（同梱版・アプライアンス）だけ HTTP/2 を落とす、になる（本記録の整理）。②と③を同時に判断しようとすると止まる。

CISO・経営層への示唆
  • ベンダーのラベルは年単位で動く前提で、対応の起動条件をラベル単独に置かない
    **同じプロジェクトが、10月には CVSS 9.8 の欠陥に moderate を付け、 11月には critical を付けている**（出典1・本DB INC-2026-0320）。 **さらに Red Hat は同じページで、総合 Critical と RHEL 9/10 の Important を併記している**（出典2）。 **ラベルを起動条件にしている組織の対応速度は、ベンダーの運用の揺れに従属する。**
    取るべき行動 脆弱性管理の規程で、**期限の起動条件に「CVSS ベクタの `PR` と `UI` が ともに不要」という機械的な条件を1本入れる。** ラベルは補助に落とし、**ベンダーが複数のラベルを出した場合は厳しい側を採る**と明記する。
  • 「どの製品のラベルを見るか」が決まっていない組織は、同じ脆弱性に二つの期限を持つ
    **本件では、上流（Apache）が critical、Red Hat 総合が Critical、 RHEL 9/10 が Important である**（出典1・2）。 **自社が RHEL を使っていれば Important、ソースビルドなら critical** になり、 **同一組織内でサーバごとに期限が割れる。**
    取るべき行動 **「上流の評価と配布元の評価が食い違ったときにどちらを採るか」を規程に1行書く。** 併せて、**httpd がソースビルドか配布パッケージか同梱版かを、 台ごとに台帳に持たせる**（期限の根拠が台ごとに違うため）。
  • 構成情報を持っていない組織では、公表から該当判定までの時間がそのまま露出時間になる
    **本件の成立条件は「HTTP/2 を有効にしているか」の一点である**（出典2）。 **条件は単純なのに、即答できる組織は多くない**（本記録の評価）。 HTTP/2 は性能のために入れられ、入れた担当とバージョンを見る担当が分かれやすい。
    取るべき行動 **`httpd -M` の出力と `Protocols` の設定値を構成管理に取り込み、 脆弱性公表時に突き合わせられる状態にする。** **アプライアンス・業務パッケージ同梱の httpd を含めて棚卸しする** （自分で更新できない台こそ先に把握が要る）。
  • 「悪用の報告が無い」「競合状態だから難しい」を優先度を下げる根拠に使わない
    **Apache も Red Hat も悪用について沈黙している**（出典1・2）〈未確定1〉。 **沈黙は安全ではなく情報の不在である。** **HTTP/2 は多重化が前提のプロトコルであり、 タイミングを試す回数を稼ぎやすい**（本記録の評価）—— 競合状態であることは成立しないことの保証にならない。
    取るべき行動 **脆弱性台帳で「悪用情報なし」を理由に延期した案件を洗い出し、 ベクタが `PR:N/UI:N` のものを例外として前に出す。** **KEV 収載を待つ運用になっていないかを点検する。**
セキュリティ技術者への示唆
  • 判定は「バージョン」と「Protocols の値」の2条件で機械的に切れる
    **影響は 2.4.55〜2.4.70 で、かつ `Protocols` に `h2` / `h2c` がある構成に限られる** （出典1・2。事実）。**2.4.54 以前と HTTP/1.1 のみの構成は対象外である。** **GitHub 配布版の mod_h2 を単体で入れている環境は 2.0.8〜2.0.42 が対象**で、 本体バージョンだけでは判定できない。
    取るべき行動 **全台で `httpd -v` と、`Protocols` を書いている箇所の grep （`httpd -S` と設定ファイル全体）を取り、2条件の AND で該当表を作る。** **mod_h2 を単体導入している台は別建てで数える。**
  • 更新できない台には、HTTP/2 の停止という一時措置がある（代償つき）
    **Red Hat は「HTTP/1.1 のみを提供する構成は脆弱ではない」と明記している**（出典2）。 **更新と違って再起動の調整が軽く、即日打てる**（本記録の評価）—— **ただし h2c を前提にした gRPC 等の内部通信は止まる**（本記録の評価）。
    取るべき行動 **同梱版・アプライアンスなど更新を自組織で完結できない台を先に特定し、 その台だけ `Protocols` から `h2` / `h2c` を外す。** **外す前に、当該台を経由する gRPC・h2c の通信が無いかを アクセスログのプロトコル欄で確認する**（止めてから気づくと業務が壊れる）。
  • 侵害確認の入口は、HTTP/2 を有効にした台の子プロセス異常終了である
    **IoC もログの見方も公表されていない**（出典1・2）〈未確定3〉。 **ヒープ破壊は、成功時にアクセスログに痕跡を残さないことがあり、 失敗時には子プロセスのクラッシュとして現れる可能性がある**（本記録の評価）。
    取るべき行動 **HTTP/2 を有効にしている台で、エラーログの `child pid ... exit signal Segmentation fault` 等の 異常終了の件数を更新前後で比べる。** **`CoreDumpDirectory` を設定していない台では証跡が残らない**ので、 重要な台だけでも有効化を検討する。
  • HTTP/2 を「性能のために入れたもの」として棚卸し対象から落としていないか見る
    **本件の成立条件は、機能としての HTTP/2 の有効化そのものである**（出典2）。 **性能設定として入れられた項目は、セキュリティの構成管理の対象から 漏れやすい**（本記録の評価）。
    取るべき行動 **構成管理の点検項目に `Protocols` を加える。** **使っていない台では平時から HTTP/2 を落としておく** （攻撃面を減らす。本件に限らず mod_http2 は過去にも繰り返し CVE が出ている。 本DB INC-2026-0320 の CVE-2026-57941 も mod_http2 である）。
