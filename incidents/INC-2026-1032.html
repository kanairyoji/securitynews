フィリピン証券取引委員会（SEC）が2026年11月9日、デジタルプラットフォームへの不正アクセスを認めた（出典1）。発端は当局の検知ではない。 11月5日に民間のサイバーセキュリティ団体Deep Web Konek が、ハッカーフォーラムに「約48万7千行の SEC データ」を売りに出す投稿が現れたことを指摘し、SEC が事象を検知したと述べるのはその翌日の11月6日である（出典3・4）。

SEC が否定したのは3点だった。 初期調査では法人登記記録は影響を受けておらず、パスワードの流出はなく、データの改変・改ざんもない（出典1）。一方、売り手が公開した標本を BNC が数えた値には、氏名・利用者名487,318件、メール487,294件、携帯番号482,424件、生年月日486,512件、住所362,625件、税籍番号（TIN）414,696件が並んでいる（出典2）。否定された項目と露出した項目が噛み合っていない。

原因の説明は2方向に割れている。 SEC は公表声明では原因に触れず、利用者への通知メールにだけ「プラットフォームにアクセスするために用いられた端末のマルウェア感染、または第三者の脅威アクターによる不正アクセスを通じて漏えいした可能性がある」と書いた（原文英語。出典3）。これが「被害者に責任を転嫁している」として批判を受けた（出典3）。売り手を称する人物は端末側の説明を明確に否定し、「自分たちの Web アプリが脆弱で、MC28 クライアント API のエンドポイントがサニタイズされていない」「マルウェアは使っていない」と主張している（出典2）。どちらも検証されていない〈齟齬1〉。

検知から3日で、公表・当局報告（NPC）・利用者通知が揃っている（本記録の算出）。措置の列挙も厚い（全システム監査・フォレンジック・IoC 確認・ログ分析・アクセス制御の強化・監視ルールの追加）。それでも本記録は対応を評価できない——原因が公表されていないため、列挙された措置が原因に対応しているかを判定する足場が無い。

外部の指摘が先に出て、当局の検知はその翌日だった発覚の端緒

SEC が独自の監視で気づいたのか、公開された指摘を受けて把握したのかは公表されていない〈未確定4〉。ただし11月7日の文言が「オンライン上の報道を認識している」である点は、外部由来を示唆する（本記録の読み）。

原因の説明が、当事者と攻撃者で正面から食い違っている原因・手口

SEC は2つの異なる場所で、異なる量の説明をした（出典1・3。事実）。

①利用者への通知メールでは、原因を端末側に置いた。アカウント情報が「プラットフォームにアクセスするために用いられた端末のマルウェア感染、または第三者の脅威アクターによる不正アクセスを通じて漏えいした可能性がある」（原文英語。出典3）。

②公表した声明では、原因に触れなかった。述べたのは「露出した可能性がある個人データの区分には個人のプロファイル情報が含まれる」「影響を受けた記録の出所・範囲・正当性を検証中」であり、初期調査では法人登記記録は無影響・パスワードは非流出・データの改変なしとした（出典1）。

③売り手を称する人物は、①を明確に否定した。「自分たちの Web アプリが脆弱で、MC28 クライアント API のエンドポイントがサニタイズされていないという事実を受け入れろ」（原文英語）、マルウェアは使っていない（出典2）。

本記録はどちらも採らない〈齟齬1〉。根拠は非対称である。 ①は当事者の説明だが公表声明からは外されており、③は攻撃者の自称で、手口を誤認させる動機を持ちうる（本記録の評価）。検証可能な材料はどちらにも付いていない。

収集した二次報道（iThome）は、売り手が「以前の攻撃で SEC デジタルプラットフォームの利用者端末の認証情報を入手した」と述べたと伝えているが（出典6）、一次に近い BNC の記事では売り手はその説明を否定している（出典2）〈齟齬1〉。二次報道の時点で、攻撃者の主張と当事者の主張が入れ替わっている。

「パスワードは漏れていない」が答えになっていない項目がある評価・解釈

以下は本記録の評価である。

SEC が否定したのは3点である（出典1。事実）——法人登記記録への影響、パスワードの流出、データの改変。いずれも「システムの健全性」と「認証の秘密」に関する否定である。

一方、報道が数えた標本に並んでいるのは別の種類のデータである（出典2）。

  • 氏名・利用者名 487,318件
  • メールアドレス 487,294件
  • 携帯電話番号 482,424件
  • 生年月日 486,512件
  • 住所 362,625件
  • 税籍番号（TIN） 414,696件

TIN は、フィリピンで銀行口座開設や就職の本人確認に使われる識別子である（本記録の背景説明）。氏名・生年月日・住所・TIN が揃った組は、パスワードを必要としない種類のなりすまし——電話口・窓口での本人確認の通過——の材料になる（本記録の評価）。「パスワードは漏れていない」はその risk に対する答えになっていない。

批判はこの点に向いた。 サイバーセキュリティ専門家の Justin David Pineda は、パスワードの強調が氏名・連絡先・住所・TIN の露出を軽く見せていると述べ、原因を利用者の端末に置く説明を「自らの不備・過失・あるいは無能をデータ主体に転嫁している」と批判した（出典3）。

本記録の評価では、問題は言っている内容の真偽ではなく、否定した項目と露出した項目が噛み合っていないことである。 否定の対象を自分で選べる局面では、「何を否定しなかったか」が実質の開示になる。

対応の中身は厚いが、原因を公表していないため評価ができない組織の対応

SEC が公表した措置は多岐にわたる（出典1。事実）。

  • 全システムのセキュリティ監査の実施
  • セキュリティスキャン・デジタルフォレンジック調査・侵害指標（IoC）の確認・システムログの分析
  • アクセス制御の強化と認証情報の更新
  • 監視ルールと技術的保護措置の追加、不審なアカウント活動の監視強化
  • アカウント関連の要求に対する確認手順の追加
  • 11月9日、国家プライバシー委員会（NPC）への義務的報告
  • 利用者への通知（使い回しパスワードの変更・多要素認証の有効化・認証情報や OTP・メール認証リンクを共有しないこと・端末のマルウェア検査）

検知から3日で公表・当局報告・利用者通知が揃っている（本記録の算出）。フォレンジックと IoC 確認に言及している点も、形式的な「調査中」より踏み込んでいる。

それでも本記録は対応を評価できない（本記録の評価）。原因が公表されていないため、列挙された措置が原因に対応しているかを判定する足場が無い〈未確定2〉。「アクセス制御の強化」が端末側の原因に対するものなのか、API のサニタイズ不備に対するものなのかで、意味が正反対になる。

措置の列挙は、原因の説明の代わりにはならない。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**公表した声明では疑われる原因に触れず、 利用者への通知メールにのみ「端末のマルウェア感染または第三者による不正アクセス」 という原因の説明を書いた**（出典1・3。事実）。不十分
**11月7日に「オンライン上の報道を認識している」とする注意喚起を先に出し、 事実関係の確認を待って11月9日に侵害を認めた**（出典1・4。事実）。部分的に機能
**アクセス制御を強化し、認証情報を更新したと公表した**（出典1。事実）。 **併せて利用者に、使い回しているパスワードの変更と多要素認証の有効化を呼びかけた** （出典1）。評価材料なし
CISO・経営層への示唆
  • 否定する項目と露出した項目が噛み合っているかを、公表前に突き合わせる
    **SEC が否定したのは、法人登記記録への影響・パスワードの流出・データの改変である** （出典1。事実）。 **一方、報道が数えた標本に並んでいるのは氏名・メール・携帯番号・生年月日・住所・TIN である** （出典2）。 **否定は「システムの健全性」と「認証の秘密」に向いており、 露出したのは「本人確認を通過させる材料」である**（本記録の評価）—— **噛み合っていない。** 実際に「パスワードの強調が他の露出を軽く見せている」と 批判を受けた（出典3）。
    取るべき行動 **公表文の草案段階で、「露出した項目」と「否定した項目」を2列に並べて突き合わせる。** **否定した項目でカバーされない露出項目があれば、 その項目について何が言えるかを必ず1行書く**（「調査中」でもよい。 **触れないという選択は、触れなかった事実として読まれる**）。
  • 原因が確定していない局面で、原因の帰属を通知文に書かない
    **SEC は公表声明では原因に触れず、利用者への通知メールにのみ 「端末のマルウェア感染または第三者による不正アクセス」と書いた**（出典1・3。事実）。 **「可能性がある」という留保を付けても、受け手には責任の所在として読まれる** （本記録の評価）——**結果として victim-blaming の批判を招き、 攻撃者側が「Web アプリが脆弱だ」と反論する余地を作った**（出典2・3）。 **原因の論争の主導権を、検証が終わる前に手放したことになる。**
    取るべき行動 **通知文の雛形から「推定原因」の欄を外し、 「現在検証中である」「確定し次第お知らせする」の2行に固定する。** **利用者に求める行動（パスワード変更・MFA）は、 原因の帰属と切り離して書けることを確認する** （行動は原因が何であれ有効だが、原因を添えると帰属の主張になる）。
  • 外部の指摘が自組織の検知より先行する前提で、通報の受け口を用意する
    **本件は、民間団体 Deep Web Konek の公開の指摘（11月5日）が SEC の検知（11月6日）に先行した**（出典3・4。事実）。 **公開の場に出てから気づく構図では、公表の主導権も最初から外にある** （本記録の評価）。 **指摘が公開ではなく直接届いていれば、1日早く動けた可能性がある** ——**本件で直接の通報があったかは確認できていない**〈未確定5〉。
    取るべき行動 **security.txt または脆弱性報告窓口を公開し、 第三者からの指摘が社内の担当に直接届く経路を作る。** **併せて、自組織名・ドメイン・識別子をフォーラム／リークサイトの 出品監視の対象に入れる**（本件では「SEC」という名称での出品だった）。
  • 同時期に同業・同セクターで多発しているときは、単独事案として処理しない
    **2026年11月5〜9日に名指しされたフィリピンの組織は23（うち政府関連16）と 報じられている**（出典6）〈未確定7〉。 **BIR も別途34万件の主張を調査中であり、NPC は複数機関から報告を受けている** （出典4・5）。 **共通の調達・共通の実装慣行・共通の基盤を疑うべき局面では、 機関ごとの個別対応が同じ穴を残す**（本記録の評価）。
    取るべき行動 **自組織と同じ基盤・同じベンダー・同じ時期に導入した仕組みを持つ 同業他社の事案が出たら、自組織の該当箇所を能動的に点検する運用を決めておく。** **グループ会社・関連法人を含めて、共通コンポーネントの一覧を持つ。**
セキュリティ技術者への示唆
  • 個人情報を返す API に、1セッションあたりの取得件数とレートの上限を置く
    **標本の項目ごとの件数が48万台で揃っていることは、 個別アカウントの逐次参照ではなく一括取得を示唆する**（本記録の評価。 公表された事実ではない。出典2）。 **48万件規模の読み出しは、件数・応答量・所要時間のいずれでも平常の利用から外れる** （本記録の評価）——**上限さえ設けてあれば、 「異常な振る舞い」を定義できていなくても量だけで引っかかる。** **SEC が事後に「監視ルールと技術的保護措置を追加した」と述べていることは、 それ以前に当該の監視が無かったことと整合する**（本記録の読み。出典1）。
    取るべき行動 **個人情報を返すエンドポイントを棚卸しし、 1セッション・1アカウント・1IP あたりの件数上限とレート上限を設定する。** **超過をブロックするのが難しければ、まず通知だけでも入れる** （止められなくても、気づけるかどうかが公表の起点になる）。
  • 一覧・検索の応答に識別子（TIN・マイナンバー等）を既定で含めない
    **露出したとされる項目のうち、なりすましに最も効くのは TIN（414,696件）と氏名・生年月日・住所の組である**（本記録の評価。出典2）。 **パスワードと違って、識別子は変更できない。** **応答の既定に含まれていれば、同じ侵害でも持ち出せる中身が増える** （本記録の評価）。
    取るべき行動 **一覧・検索 API の応答スキーマから、変更不能な識別子を既定で外す。** **必要な画面では、明示的なパラメータと別の認可チェックを経て個別に取得させる。** **既存の応答に含まれている箇所を、スキーマ定義の grep で洗い出す。**
  • 「端末が侵害された」で説明できる被害範囲かを、認可の粒度から逆算して確かめる
    **SEC の説明は、利用者の端末のマルウェア感染または不正アクセスである**（出典3）。 **仮にそれが正しいとして、1利用者の端末が侵害されたことで48万件が引けるなら、 認可の粒度が利用者の権限と釣り合っていない**（本記録の評価） ——**48万件が1アカウント経由で取得されたことは公表されていない**〈未確定2〉が、 **この逆算は自組織の点検には使える。**
    取るべき行動 **「最も権限の低い利用者アカウント1つが完全に奪われたとき、 何件のレコードに到達できるか」を実測する**（テナント境界・水平権限のテスト）。 **到達件数が利用者の業務上の必要を超えていれば、 原因が端末側であろうとサーバ側であろうと被害は同じ大きさになる。**
  • 入力検証と認可の網羅テストを、API ごとに工程として持つ
    **売り手は「Web アプリに脆弱性があり、MC28 クライアント API の エンドポイントがサニタイズされていない」と主張している**（出典2）〈未確定8〉。 **主張の真偽は検証されていない**が、**この種の主張が成立しうる状態かどうかは 自組織では検査できる**（本記録の評価）。
    取るべき行動 **CI に DAST または API スキーマ検証を組み込み、 エンドポイント単位で入力検証と認可の網羅テストを回す。** **特に、画面を経由せず呼ばれる「クライアント向け API」は、 画面側のバリデーションに守られていない前提で検査する。**
