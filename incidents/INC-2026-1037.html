INC-2026-1037三菱電機CNCのDoS、C80も対策版

三菱電機が2026年11月12日、数値制御装置（CNC）のサービス拒否の脆弱性 CVE-2025-2399 のアドバイザリ（2025-022）を改訂し、**C80 シリーズの対策版 （BL 版以降）を追記した**——TCP 683 番ポートへ不正なパケットを送ると 領域外のメモリ読み出しが起きて**該当製品が非常停止し、復旧にはシステムの リセットが必要になる**（CVSS 3.1 基本値 5.9・CWE-1285）。 **初報は2026年3月10日で、最後に残っていた C80 シリーズの対策版が 出るまで247日かかった**（本記録の算出）—— **その間、C80 の利用者に提供されていたのは緩和策だけだった**〈重要〉。 **JVN は同日に［影響を受けるシステム］を更新し（JVNVU#95523788）、 C80 の記載が「BK 版以前」に変わった**—— **一方 CISA の ICS 勧告 ICSA-26-078-05 は本記録の確認時点（2026年11月13日）で 2026年8月27日の改訂4のままで、C80 の対策版は「None listed」と表示される**〈差異1〉

脆弱性そのものの内容は2026年3月10日の初報から変わっていない（出典1・2・3）。TCP 683 番ポートへ不正なパケットを送信されると領域外のメモリ読み出しが起き、該当製品がサービス停止（DoS）状態に陥る。 開発元は「該当製品がサービス停止(DoS)状態に陥ると、システムが非常停止します。なお、復旧にはシステムのリセットが必要になります」と書いている（出典1）〈重要〉。CVSS 3.1 の基本値は 5.9（AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:H）で、影響は可用性のみ・攻撃条件の複雑さは「高」である（出典1・3）。

読み取れるのは、OT の脆弱性対応が「公表の日」では終わらないということである（本記録の評価）。本件のアドバイザリは3月10日の初報のあと、3月12日（JVN の誤植修正）・3月24日（JVN に ICS 勧告のリンク追加）・8月27日（M700V/M70V/E70 の対策版追記と影響対象からのソフトウェアツール削除）・11月12日（C80 の対策版追記）と改訂されてきた（出典1・2）。シリーズごとに対策版の提供時期が違い、最後の C80 までは初報から247日である（本記録の算出）。「公表されたら対応する」という運用では、同一 CVE を4回読み直すことになる。

    トレードオフ: **捨てたのは「一律の個別通知で漏れなく伝える」ことである**（本記録の整理）。 **利用者が自力で判定できる形にした分、 該当する組織を開発元が把握して名指しで知らせる仕組みにはなっていない。** **自社で判定を実施しない組織は、該当していても気づかないまま残る** （本記録の評価）—— **該当台数が公表されていないのは、この構造の裏返しでもある**〈未確定5〉。

本記録がこの改訂を1件として立てる理由は、対策版の有無で利用者の取るべき行動が入れ替わるからである（本記録の判断）〈重要〉—— 3月から11月11日までの C80 の利用者に提供されていたのは緩和策だけで、「アップデートする」という選択肢が無かった。 11月12日以降は、緩和策の恒久化をやめて更新計画に移すべき状態になっている。

止まるのは情報システムではなく生産設備で、復旧にはシステムのリセットが要る原因・手口

脆弱性の構造は単純である（出典1・2）。

  1. 攻撃者が TCP 683 番ポートへ不正なパケットを送信する。
  2. 入力で指定されたインデックス・位置・オフセットの検証が不適切なため（CWE-1285）、領域外のメモリ読み出しが発生する。
  3. 該当製品がサービス停止（DoS）状態に陥る。

重いのは3の中身である（本記録の評価）〈重要〉。開発元はこう書いている。

「該当製品がサービス停止(DoS)状態に陥ると、システムが非常停止します。なお、復旧にはシステムのリセットが必要になります」（出典1）

非常停止（EMG）は工作機械にとって通常の停止ではない。 加工中の刃物とワークの位置関係が崩れ、仕掛品の廃棄・刃具の点検・原点復帰と再段取りが要る。 「可用性だけ」という CVSS の読み方（C:N/I:N/A:H）と、現場の損失は一致しない（本記録の評価）。

CVSS 3.1 の基本値 5.9 は、攻撃条件の複雑さが「高」（AC:H）であることで押し下げられている（出典1・3）—— 認証も利用者の操作も要らない（PR:N/UI:N）一方で、成立に何らかの条件が要るということである。 その条件の中身は公表されていない。

本記録は「CVSS が中程度だから後回しでよい」とは読まない（本記録の判断）。判断材料は点数ではなく「その装置に到達できる経路があるか」である—— 緩和策がすべて到達範囲の制限に向けられているのは、そこが分かれ目だからである（出典1）。

本件のアドバイザリは8か月で4回改訂された（出典1・2。本記録の整理）。

  • 2026年3月12日 — JVN が［影響を受けるシステム］の誤植を修正（出典2）
  • 2026年3月24日 — JVN が［参考情報］に CISA 勧告のリンクを追加（出典2）
  • 2026年8月27日 — 三菱電機が M700V/M70V/E70 の対策版を追記し、影響対象から「ソフトウェアツール」を削除（出典1）／CISA は改訂4（出典3）
  • 2026年11月12日 — 三菱電機が C80 の対策版を追記（出典1）／JVN も更新（出典2）

改訂の向きは一方向ではない（本記録の整理）〈重要〉—— 8月27日の改訂には「影響を受ける製品を削除しました（ソフトウェアツール）」が含まれている（出典1）。つまり初報の時点で対象外のものが対象に入っていた。 3月12日の「誤植の修正」も［影響を受けるシステム］の箇所である（出典2）。

ここから導かれる実務上の帰結は2つある（本記録の評価）。

①初報の判定を保存しておかないと、改訂のたびにやり直せない。 「自社の装置はどのシリーズの何版か」を台帳に持っていない組織は、改訂が来るたびに現場へ確認を出すことになる。 本件は幸い、利用者側で判定できる—— 表示ユニットの「診断」画面からソフトウェア構成画面を開き、NCMAIN1 のシステム番号を読めばよい（出典1に画面図つきで記載）。

②緩和策は「対策版が出るまでの繋ぎ」として期限を持たせないと恒久化する。 C80 の利用者にとって、緩和策だけで過ごす期間は247日あった（本記録の算出）。緩和策（到達範囲の制限）は正しい手当てだが、「対策版が出たら更新する」という宿題が台帳に残っていなければ、改訂は誰にも読まれない。

CISA の勧告は11月12日の改訂を反映しておらず、C80 の修正版が「無し」と表示される未確定事項

対策版が出た以上、緩和策の恒久化から更新計画へ切り替える段階にある対策・注意喚起

開発元が示している手当ては2つに分かれる（出典1）。

①対策版が提供されている製品を使っている場合 → 対策済みバージョンを適用する。適用方法は最寄りの三菱電機窓口へ相談する（出典1）。11月12日以降は、4シリーズすべてがこちらに該当する（出典1。本記録の整理）。

②対策版が提供されていない製品を使っている場合 → 緩和策・回避策で対応する（出典1）。挙げられている緩和策は次のとおりである（出典1の原文を要約）。

  • インターネットに接続する場合はファイアウォール・VPN 等で不正アクセスを防止する
  • LAN 内で使用し、信頼できないネットワーク・ホストからのアクセスをファイアウォールでブロックする
  • IP アドレスフィルタ機能を使って信頼できないホストからのアクセスをブロックする（この機能は M800V/M80V シリーズと M800/M80/E80 シリーズのみ対応。C80 と M700V/M70V/E70 では使えない）〈重要〉
  • 装置および装置へ接続可能なパソコン・ネットワーク機器への物理的アクセスを制限する
  • 装置へアクセス可能なパソコンにウイルス対策ソフトを搭載する

本記録が注目するのは、IP アドレスフィルタ機能の対応範囲である（本記録の評価）〈重要〉—— 装置自身で発信元を絞れるのは2シリーズだけで、C80 と M700V/M70V/E70 では上位のネットワーク機器側で絞るしかない。 「装置の手前に何があるか」で守りの強さが変わるため、緩和策の実効性はシリーズごとに違う。

本記録の評価としての優先順位は次のとおりである（本記録の判断）。

  1. TCP 683 番へ到達できる経路を実測で棚卸しする（設計図ではなく実際の到達性を測る）
  2. 対策版の適用を、装置の停止計画に載せる（適用には窓口経由の調整が要るため、計画の起点は保全部門ではなく調達・保全の合議になる）
  3. 緩和策は適用完了まで維持し、台帳に「対策版あり・未適用」として残す

  • OT の脆弱性は「公表された日」ではなく「自社のシリーズに対策版が出た日」で管理する
    **本件は同一 CVE が8か月で4回改訂され、 シリーズごとに対策版の記載日が違った**（出典1・2）—— **C80 の利用者にとっては、初報から247日間「対策版が無い製品」だった** （本記録の算出）。 **CVE 単位で「対応済み／未対応」を管理していると、 自社の機種に対策版が出たことに誰も気づかない。**
    取るべき行動 **脆弱性台帳に「機種・シリーズ・現行版」の欄と 「対策版の有無」の欄を分けて持ち、 対策版が未提供の案件には再確認の期日を入れる。** **OT の案件は、ベンダーのアドバイザリ URL を台帳に記録し、 四半期ごとに更新履歴を読み直す運用にする。**
  • 緩和策には期限を付ける。付けないと恒久化し、対策版が出ても誰も動かない
    **対策版が無い間の正しい手当ては到達範囲の制限である**（出典1）—— **これは一度設定すれば日々の運用で意識されなくなる。** **本件のように8か月後に対策版が追記されても、 「緩和策済み」として台帳が閉じていれば読み直されない**（本記録の評価）。
    取るべき行動 **緩和策で対応した案件を「完了」にしない。** **「暫定対応中・対策版待ち」という状態を台帳に設け、 再確認の期日（例: 90日ごと）と確認先の URL を必ず書く。**
  • 生産設備の停止は、CVSS の「可用性のみ」が示す重さとは一致しない
    **本件の CVSS 3.1 基本値は 5.9 で、影響は可用性のみ（C:N/I:N/A:H）である** （出典1・3）—— **一方で開発元は「システムが非常停止します。復旧にはシステムのリセットが 必要になります」と書いている**（出典1）。 **非常停止は仕掛品の廃棄・刃具点検・原点復帰と再段取りを伴う**（本記録の評価）。 **CVSS の点数で優先順位を決める運用では、この重さが落ちる。**
    取るべき行動 **OT の脆弱性の優先順位付けに、CVSS とは別の軸を1つ入れる**—— **「成立したら生産が止まるか」「止まったら復旧に人手と停止時間が要るか」。** **止まる系の案件は、点数に関わらず保全部門との合議にかける。**
  • 情報源を1つに決めず、日本のベンダー製品は開発元の PSIRT を一次で見る
    **本記録の確認時点で、CISA の勧告は2026年8月27日の改訂4のままで、 C80 の修正版は「None listed」と表示される**（出典3）〈差異1〉—— **開発元のアドバイザリと JVN は11月12日の改訂を反映している**（出典1・2）。 **どの資料も間違っていないが、見る場所で結論が変わる。**
    取るべき行動 **OT の脆弱性情報の参照先を台帳に明記し、 国内ベンダーの製品は「開発元 PSIRT を一次・JVN を二次・CISA を参考」の順に定める。** **逆に海外ベンダー製品では順序が入れ替わることも明記しておく。**
セキュリティ技術者への示唆
  • 自組織の該当判定を、ベンダー連絡待ちにせず現場で実施できる手順にする
    **本件は利用者側で判定できる**（出典1）—— **表示ユニットの「診断」画面からソフトウェア構成画面を開き、 NCMAIN1 に表示されるシステム番号を読めばよい（画面図つきで記載されている）。** **これができれば、改訂のたびにベンダーへ照会する必要がない**（本記録の評価）。
    取るべき行動 **装置ごとのシステム番号（例: BND-2036W000-BK）を台帳に記録し、 棚卸しの頻度を決める。** **記録は保全の点検票に組み込み、情報システム部門が読める場所に置く。**
  • TCP 683 番への到達性は、設計図ではなく実測で確かめる
    **公表されている唯一の攻撃面は TCP 683 番ポートである**（出典1・2・3）。 **683 番で何が待ち受けているかは公表されておらず、 止められるのかどうかも分からない**〈未確定2〉—— **できるのは到達範囲を絞ることだけである。** **ネットワーク構成図は現実と乖離しやすい**（本記録の評価）。
    取るべき行動 **生産系セグメントの装置に対し、保全用の区画以外から 683 番へ 到達できるかを実際に試して確かめる。** **到達できた経路はすべて記録し、遮断するか許可リストに載せるかを決める。**
  • 装置側で発信元を絞れるかはシリーズで違う。緩和策の実効性を機種ごとに評価する
    **IP アドレスフィルタ機能は M800V/M80V シリーズと M800/M80/E80 シリーズのみ対応である**（出典1）〈重要〉—— **C80 と M700V/M70V/E70 では装置側で絞れず、 上位のネットワーク機器に依存する。** **「緩和策を実施した」と一括で記録すると、守りの差が見えなくなる。**
    取るべき行動 **緩和策の実施記録を機種単位にし、 「装置側で絞っている／上位機器だけで絞っている」を区別して書く。** **後者の装置は、上位機器の設定変更時に影響を受ける対象として台帳に残す。**
  • 原因不明の非常停止を、設備故障だけで処理しない経路を作る
    **本脆弱性が成立したときに現場で見えるのは「非常停止」である**（出典1）—— **装置側に異常パケットの記録が残るかは公表されていない**〈未確定2〉。 **攻撃と故障を区別する材料が無ければ、 同じことが繰り返されても設備側の問題として閉じてしまう**（本記録の評価）。
    取るべき行動 **非常停止の発生記録に「同時刻のネットワーク機器のログを確認したか」の 欄を作る。** **原因不明の非常停止が短期間に繰り返された場合に セキュリティ側へ上げる基準（回数・間隔）を決めておく。**
