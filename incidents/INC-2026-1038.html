INC-2026-1038KUSANAGI にヘッダ挿入の脆弱性

GMOプライム・ストラテジーが2026年11月9日、WordPress 向け高速化基盤 KUSANAGI に HTTP ヘッダーインジェクションの脆弱性（CVE-2026-117477・CWE-113）が あると自社から JPCERT/CC へ報告し、JVNVU#92635551 として公表された—— **原因は製品が同梱する「WordPress 向け Nginx の設定ファイルに含まれる リダイレクトルール」で、細工された URL にアクセスさせることで HTTP レスポンスに任意のヘッダーを挿入できる**（CVSS 4.0 基本値 5.1・ CVSS 3.1 基本値 6.1。**Apache httpd を使っている場合は対象外**）〈重要〉。 **2026年11月12日に JVN が［影響を受けるシステム］を更新し、 KUSANAGI 7 は「すべてのバージョン」、KUSANAGI 8 は 「Free / Business / Premium Edition のすべてのバージョン」に変わった**—— **サポートが終了した2つのメジャー版には修正版が出ず、 提供されるのは緩和策だけである**（当事者の公表）〈重要〉。 **悪用の有無についての記述は、どの資料にも無い**

GMOプライム・ストラテジー株式会社は2026年11月9日、自社製品 KUSANAGI の脆弱性（CVE-2026-117477）への対応を公表した（出典1）。同日、JPCERT/CC と IPA が JVNVU#92635551 として公表している（出典2）—— 「この脆弱性情報は、製品利用者への周知を目的に、GMOプライム・ストラテジー株式会社がJPCERT/CC に報告し、JPCERT/CC が GMOプライム・ストラテジー株式会社との調整を行いました」（出典2）。

本記録が重く見るのは、影響範囲が「メジャー版3つにまたがる」ことである（本記録の評価）〈重要〉。2026年11月12日に JVN が［影響を受けるシステム］を更新した結果、対象は次のようになった（出典2）。

不備があったのは利用者の設定ではなく、製品が同梱していた Nginx の設定ファイルである概観

JVN が示す原因箇所は具体的である（出典2）。

「GMOプライム・ストラテジー株式会社が提供する KUSANAGI には、WordPress 向け Nginx の設定ファイルに含まれるリダイレクトルールに次の脆弱性が存在します——HTTP ヘッダにおける CRLF 文字の不適切な無害化（CWE-113）」（出典2）

ここが本件を読むうえでの要点である（本記録の評価）〈重要〉。

  • 壊れていたのは WordPress 本体でもプラグインでもない。
  • 利用者が書いた設定でもない。
  • 製品が「WordPress を速く動かすための既定の構成」として配っていた設定ファイルの中のリダイレクトルールである。

したがって「自社では特別な設定をしていない」ことは安全の根拠にならない（本記録の評価）—— 既定のまま使っていた組織がそのまま該当する。

判定条件は3つに整理できる（出典2・3。本記録の整理）。

  1. KUSANAGI のメジャー版と版数（7／8／9 と、9 なら 10.7.2-1 もしくは 9.12.2-1 以前か）
  2. エディション（Security/Enterprise か Free/Business/Premium か）
  3. Web サーバが Nginx か Apache httpd か——Apache httpd なら対象外（出典3）〈重要〉

3 が効く理由は、不備があったのが Nginx 向けの設定ファイルだからである（本記録の解釈）。KUSANAGI は Web サーバを切り替えて使える製品であり、同じ製品・同じ版でも構成によって該当が変わる。

細工された URL にアクセスさせるとレスポンスに任意のヘッダーが入る。利用者の操作が要る原因・手口

成立の流れは次のとおりである（出典2・3）。

  1. 攻撃者が、CRLF（改行）を含むよう細工した URL を用意する。
  2. その URL へ利用者（被害サイトの訪問者）がアクセスする。
  3. KUSANAGI 同梱の Nginx 設定のリダイレクトルールがURL 中の値を無害化せずにレスポンスヘッダーへ反映する。
  4. HTTP レスポンスに任意のヘッダーが挿入される。

CVSS のベクターがこの構造をよく表している（出典2）〈重要〉。

版 ベクター 基本値 読み方
CVSS 4.0 AV:N/AC:L/AT:N/PR:N/UI:A/VC:N/VI:N/VA:N/SC:N/SI:L/SA:N 5.1 ネットワークから・容易・権限不要だが利用者の操作が要る。影響は後続システムの完全性（SI:L）のみ
CVSS 3.1 AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N 6.1 同じく利用者の操作が要る（UI:R）。スコープ変更あり（S:C）

重要なのは2点である（本記録の評価）。

①「利用者の操作が要る」ため、サーバを直接奪われる類の脆弱性ではない。 攻撃者は、細工した URL を踏ませる手段（フィッシングのメール・SNS の投稿・広告・他サイトからの誘導）を別に用意する必要がある。 それでも標的型の攻撃では十分に成立する〈重要〉—— リンク先のドメインは正規のサイトのものになるため、URL の見た目で見分ける防御が効きにくい。

②影響が「スコープの外」へ出る（S:C／SI:L）。 挿入されたヘッダーを解釈するのはブラウザ側である。 CVSS の評価が可用性（A:N／VA:N）をゼロとし、機密性・完全性を「低」に置いているのは、サーバ上のデータが直接漏れたり壊れたりする経路ではないためである（本記録の解釈）。

本記録は、この脆弱性で何ができるかを具体的に列挙しない（本記録の判断）〈重要〉—— 当事者も JVN も「HTTP レスポンスに任意のヘッダーが挿入される可能性があります」までしか書いていない。 想定される悪用の形を本記録が書き足せば、公表の範囲を超えた推測になる。

  • 該当判定に Web サーバの種類を入れる。同じ製品・同じ版でも構成で結論が変わる
    **本件は Nginx 向けの設定ファイルの問題であり、 Apache httpd を使っている場合は対象外である**（出典3）〈重要〉。 **KUSANAGI は Web サーバを切り替えて使える製品のため、 版数だけでは該当の有無が決まらない**（本記録の評価）。

    取るべき行動 **重要な公開サイトについて、応答ヘッダーを含む記録を取る構成が可能かを確認する。** **容量と個人情報の扱いが問題になるため、 対象サイトと保存期間を限って設計する。** **取らない判断をする場合は「成立の有無を後から判定できない」ことを インシデント対応の前提として明記しておく。**
  • 緩和策を当てる前に、既存のリダイレクト動作への影響を確認する
    **原因箇所は WordPress 向け Nginx 設定ファイルのリダイレクトルールである** （出典2）〈重要〉—— **その無害化を直す緩和策は、既存の URL 正規化・リダイレクトの挙動に 影響しうる**（本記録の評価）。 **緩和策の具体的な内容は本記録が未確認である**〈未確定2〉。
    取るべき行動 **緩和策は検証環境で先に適用し、 正規の URL のリダイレクト（末尾スラッシュ・HTTPS 強制・ 旧 URL からの転送など）が壊れていないかを確認してから本番へ入れる。**
