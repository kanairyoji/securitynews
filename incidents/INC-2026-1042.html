INC-2026-1042Apify 社内システム侵害

**ウェブスクレイピング・ブラウザ自動化基盤を提供するチェコの Apify は、 2026年11月9日から10日にかけて第三者が社内システムの一部へ不正アクセスしたことを 11月11日 12:13 UTC に検知した。同社は「侵害された1つの認証情報を使って 複数のアカウント認証情報を入手し、関連する Apify アカウントへアクセスした」と 説明している。対応として社内の重要シークレットの輪番、顧客の API トークンと Apify Proxy パスワードの輪番、GitHub を含む OAuth 連携の取り消し、 全有効セッションの無効化を行い、一部顧客には2要素認証コードが露出した可能性が あるとして再設定を求めた。個人情報または保存データへのアクセスが確認された顧客への 個別通知は11月12日に始まった。**

    取るべき行動 **自社が発行する API トークンを、発行時に一度だけ表示し、 保存はハッシュのみにする（照合はハッシュで行う）。** **既存のトークンが復号可能な形で保存されているなら、 移行計画を立てる（移行時に全トークンの再発行が必要になるため、 事故後ではなく平時に行う）。** **プロキシのパスワードなど「送信に平文が必要」なものは、 用途ごとに分離して影響範囲を区切る。**
  • 2要素認証のシークレット（TOTP の種）を、アプリケーションから 一括で読み出せる場所に置かない。
    **一部顧客には「2要素認証コードが露出した可能性がある」として Apify Console での再設定を求める通知が送られている** （出典2）〈重要〉—— **本記録は、これを2要素認証のシークレットが 到達可能な場所にあったことの表れと読む** （本記録の評価・推測。出典2 に保持形式の記述は無い）。 **TOTP の種が漏れれば、2要素認証は突破される （コードを生成できるため）**（本記録の評価）。
    取るべき行動 **TOTP のシークレットを、パスワードや他の認証情報とは 別の保管（HSM・専用の鍵管理サービス）に置き、 アプリケーションからの一括読み出しを不可能にする。** **可能であれば TOTP ではなくパスキー（WebAuthn）へ移行する （サーバ側に秘密が残らない）。** **利用者に再設定を求める手順と、復旧コードを紛失した 利用者の救済手順を、事故前に用意しておく。**
  • 1つの認証情報で複数のアカウント認証情報に到達できる構成を残さない。 管理系の操作には別の認証を要求する。
    **出典1 は「侵害された1つの認証情報を使って 複数のアカウント認証情報を入手し」と述べている** （原文英語を訳出）〈重要〉—— **1件の侵害が複数件の侵害に増幅する構成だった** （本記録の整理）。 **どのシステムだったかは公表されていない**〈未確定4〉。
    取るべき行動 **「1つのアカウントが奪われたとき、そこから何件の認証情報に 到達できるか」を権限の棚卸しの指標にする。** **シークレット管理・トークン発行系・顧客データベースへの 横断的な参照は、承認付き・時限付きの手続（Break-glass）に 限定し、常時の権限から外す。** **併せて、これらの系への読み出しに件数・時間当たりの上限を設け、 閾値超過を遮断・警報の対象にする。**
  • トークンの一斉輪番は「できる状態」にしておく。 事故の最中に作る仕組みではない。
    **Apify は検知の当日から顧客の API トークンの輪番と 全有効セッションの無効化を実施している**（出典1・出典2）〈重要〉 ——**本記録は、これをトークンの発行と失効が一元的に 管理されていたことの表れと読む**（本記録の評価・推測）。 **分散して管理されていれば、当日の一斉輪番はできない** （本記録の評価）。
    取るべき行動 **自社が発行する認証情報（API トークン・セッション・ 連携の OAuth トークン）について、 「特定の顧客のぶんだけ」「全件」を切り替えられる操作を 平時に用意し、年に1回は実際に実行して所要時間を測る。** **併せて、輪番時に顧客へ送る通知の文面と、 顧客が新しいトークンを取得する手順を事前に用意する （輪番の仕組みがあっても、通知と手順が無ければ顧客は復旧できない）。**
