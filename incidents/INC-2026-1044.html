    初段 `dllhost.exe`（UPX 圧縮・Go 製）が `hxxp://site.vietnam852[.]com:88/ip.php` へ HTTP GET を送り標的 IP を受け取る。 これをハードコードされた /16 に展開し、 組み込みの Naabu（v2）の `Runner.RunEnumeration()` で 範囲内のランダムなアドレスに対し TCP 1433 の開放を調べ、 成立したものを `%temp%\Result.txt` に「{IP} 1433 Open」の形で記録する。 1範囲の走査が終わると次の範囲を C2 に要求して繰り返す（出典1）

脆弱性は使われていない——成立の条件は「露出」と「弱いパスワード」の2つだけ原因・手口出典 [1] [2]

本活動で悪用された CVE は、一次公表にも報道にも示されていない（出典1・2。本記録の確認）。成立に要るのは次の2つだけである（出典1。整理は本記録）。

  • Microsoft SQL Server の TCP 1433 がインターネットから到達可能であること
  • 認証情報が辞書（2,700件超）と既定の利用者名（sa・admin 等）で当たること

つまり、パッチ適用では止まらない（本記録の評価）〈重要〉。止まるのは、到達経路を閉じるか、認証情報を推測不能にしたときである。

CSO Online が載せた Keeper Security の CISO Shane Barney のコメントは、この構図を次のように言っている（出典2。原文英語を訳出）。

「インターネットに面したデータベースは、技術的負債や設定不備の意図しない結果であることがある。しかし、その露出を深刻な脆弱性へ変えているのは、静的で常時有効な認証情報に依存していることである。管理者ログインが総当たりできるなら、攻撃者は複雑な悪用を1つも要さずに即座に無制限の制御を得て、マルウェアを展開できる」

「脆弱性管理」の枠では検出されない種類の露出である（本記録の整理）——資産管理と設定監査の側で見る必要がある。

データベースのログインが、そのまま OS のコード実行になる評価・解釈出典 [1] [2]

この活動の要点は T-SQL の使い方にある（出典1）。

dwm.exe は総当たりに成功したインスタンスへ接続し、2018.sql のバッチをGO 区切りで実行する。バッチが行うことは次のとおりである（出典1）。

  1. xp_cmdshell を有効化する
  2. HTTP/FTP サーバから、または @DATA 変数に埋め込まれたバイナリから実行ファイルを C:\Users\Public へ展開する
  3. それを起動する

xp_cmdshell は、データベース管理者が Windows のコマンドシェル操作を実行できる SQL Server の機能である（出典2）。これが有効化できる権限でログインできた時点で、「DB の侵害」は「サーバの侵害」と同じ意味になる（本記録の整理）〈重要〉。

CSO Online が載せた Sectigo の Jason Soroko のコメントも同じ点を突いている（出典2。原文英語を訳出）。

「組織は SQL Server への直接のインターネット接続を取り除き、接続を承認済みのシステムに限定し、強固で一意な認証情報を強制すべきである。管理者アクセスは、それを要する account に限るべきである」「xp_cmdshell は必要でなければ無効のままにし、有効化の試行を監視することを推奨する」

防御の設計上、xp_cmdshell の有効化は「権限昇格の一歩」として扱うべきである（本記録の推奨）——構成変更として記録でき、警報化できる。

標的は選ばれていない——1つの IP を /16 に広げて総当たりしている被害規模・影響範囲出典 [1]

走査の仕組みはこうである（出典1）。

初段 dllhost.exe は C2（hxxp://site.vietnam852[.]com:88/ip.php）へHTTP GET を送り、標的 IP アドレスを1つ受け取る。これをハードコードされた 0x10（= /16）でCIDR に展開し、範囲内のアドレスをランダムに生成しながら TCP 1433 を調べる。1範囲を終えると次の範囲を要求して繰り返す。

/16 は最大 65,536 アドレスである（本記録の算出）。したがって本活動における「標的」は、業種でも国でもなく IP の範囲である（本記録の評価）〈重要〉。

読み方としては、次の2つを分ける必要がある。

  • 自社が狙われたか — この問いは本活動には当てはまらない。攻撃者が選んでいるのはアドレス範囲であり、組織ではない。
  • 自社が範囲に入っていたか — これは「1433 が外から開いていたか」で決まる。

被害組織の件数・業種・国はいずれも公表されていない〈未確定2〉。Fortinet の記述は「Impacted Users: Microsoft SQL Server」までである（出典1）。日本国内で侵害が確認されたという情報も無い（本記録の確認）。

マイナーで止めると RAT が残る——最終段は2種で、永続化は5系統ある評価・解釈出典 [1] [2]

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「脆弱性管理」の枠では本件は映らない。資産の露出と認証情報の強度を 別の指標として経営報告に載せる。
    **本活動は CVE を一つも使っていない**（出典1・2。本記録の確認）〈重要〉—— **成立の条件は「1433 が外から開いている」と「辞書で当たるパスワード」だけである。** **パッチ適用率が100%でも、この2つが残っていれば侵害される**（本記録の評価）。
    取るべき行動 **「インターネットに露出している管理系ポート（1433・3389・22 等）の数」と 「既定アカウントが有効なままの件数」を、パッチ適用率と並ぶ指標として毎月出す。** **外部からの走査（自組織のIP範囲に対する実測）を四半期ごとに実施する。**
  • マイニングの検知を「掃除して終わり」にしない運用を決めておく。 同じ侵入で遠隔操作ツールが入っている。
    **最終段は Monero マイナーと Gh0st RAT 変種の2種で、 永続化は合わせて5系統ある**（出典1・2）〈重要〉—— **CPU 使用率で気づけるのはマイナー側だけである**（本記録の整理）。 **CSO Online は「マイニングは長期の永続化を確立するための目くらましになりうる」との 識者コメントを載せている**（出典2。原文英語を訳出）。
    取るべき行動 **「暗号資産採掘の検知」をインシデント対応手順の起点として定義し、 プロセス停止で閉じることを禁止する。** **最低でも、永続化（タスク・サービス・Run キー）の棚卸しと、 当該サーバで扱った認証情報の無効化までを必須手順にする。**
  • データベースの管理者ログインは「OS のコード実行権限」として リスク登録簿に書き換える。
    **`xp_cmdshell` を有効化できる権限でログインできた時点で、 DB の侵害は OS の侵害と同義になる**（出典1・2。整理は本記録）〈重要〉—— **本活動はこの変換を T-SQL のバッチ1本で行っている**（出典1）。
    取るべき行動 **DB の管理者アカウントを「特権アクセス管理（PAM）の対象」に含め、 常時有効な静的認証情報を廃止する（都度払い出し・多要素）。** **`xp_cmdshell` の構成値を構成管理のベースラインに固定し、 逸脱を自動検知する。**
  • サーバのログを当該サーバだけに置かない。消去機能を持つ RAT が 入った時点で、そこでの調査は成立しない。
    **Gh0st RAT 変種は `ClearEventLogA()` によるイベントログ消去を 制御コマンド（Cmd# 4）として備えている**（出典1）〈重要〉—— **消されたあとでは、侵入時期も持ち出しの有無も確認できない**（本記録の評価）。
    取るべき行動 **DB サーバを含む全サーバのイベントログを、改変できない外部のログ基盤へ 即時転送する構成にする。** **ログ消去イベント（Windows 1102 等）を警報の対象に加える。**
セキュリティ技術者への示唆
  • 最初に確認するのは構成の5点である。IoC 照合より先にこれを済ませる。
    **IoC（ドメイン・ハッシュ）は攻撃者が変えれば無効になるが、 構成の側は変わらない**（本記録の整理）〈重要〉—— **本活動の経路は、走査→総当たり→`xp_cmdshell`→`C:\Users\Public`→ Edge 更新を装うタスク、で固定されている**（出典1）。
    取るべき行動 **①1433 の外部到達性 ②`sa` の有効/無効と認証方式 ③`xp_cmdshell` の構成値 ④`C:\Users\Public` 配下の実行ファイル ⑤`MicrosoftEdgeUpdateTask*` を名乗るタスクの実行パス——この5点を全 SQL Server で確認する。** **③は `sp_configure 'xp_cmdshell'` の `run_value` を集計する。**
  • スケジュールタスクは名前で判定しない。実行ファイルのパスで判定する。
    **本活動のタスク名は `MicrosoftEdgeUpdateTaskMachineUA{CEC15D9B-...}`・ `MicrosoftEdgeUpdateTaskMachineCore{4C33CE3F-...}` で、 正規の Edge 更新タスクと同じ命名規則・GUID 形式である**（出典1）〈重要〉—— **一覧を目で見て区別することはできない**（本記録の評価）。 **区別できるのは実行パス（`E:\dllhost.exe`・`C:\Users\Public\Secs.exe`）である。**
    取るべき行動 **タスクの棚卸しを「名前」ではなく「実行ファイルのパスと署名」で行うクエリに変える。** **`C:\Users\Public`・リムーバブル／データドライブ直下を実行元とするタスクを 全台で抽出する。**
  • DB サーバからの外向き通信を既定拒否にする。平文 HTTP と FTP が この連鎖の全段で使われている。
    **標的範囲の取得（HTTP/88）・ファイル配布（HTTP/88）・最終段の取得（FTP）・ ホスト登録（HTTP POST）・マイニング開始通知（HTTP GET）・C2（8000）が すべてサーバからの外向き通信である**（出典1）〈重要〉—— **DB サーバが外部へ出る必要のある宛先は、通常ごく少数である**（本記録の評価）。
    取るべき行動 **DB サーバの外向き通信を既定拒否に変え、更新・監視・バックアップの宛先のみ許可する。** **非標準ポート（88・8000）とFTPを明示的に遮断し、 許可した宛先以外への接続試行をログに残す。**
  • 失敗ログインを数えていなければ、総当たりは「無音」で成功する。
    **総当たりは `sa`・`admin` 等の利用者名と 2,700件超の辞書で行われる** （出典1・2）—— **成功するまでの失敗は認証ログに残るが、 露出したインスタンスでは監視対象外になっていることが多い**（本記録の評価）。 **Fortinet も IPS 署名での検知を前提にしている**（出典1）。
    取るべき行動 **SQL Server の失敗ログイン監査を有効にし、 単位時間あたりの失敗数と接続元 IP の分散をしきい値監視する。** **過去ログに対して、1433 への外部からの失敗ログインを遡及確認する（30日）。**
  • マイニングの兆候は運用監視の既存データに既にある。基準線を持つ。
    **マイナーは侵害されたサーバの CPU を使って Monero を採掘する**（出典1）〈重要〉—— **DB サーバの CPU 使用率は容量計画のために常時計測されていることが多く、 新しい計測を要しない**（本記録の整理）。
    取るべき行動 **DB サーバの CPU 使用率の基準線（曜日・時刻別）を持ち、 業務負荷で説明できない恒常的な上昇を警報化する。** **警報の対応手順に「永続化の棚卸し」を含める（マイナー単体で閉じない）。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Microsoft SQL Server の TCP 1433 が、インターネットから直接到達できる状態にある （クラウド上のVMのセキュリティグループ・オンプレの境界を含む）。
認証・認可□ SQL 認証（混在モード）を使っており、`sa` が有効、 または管理者権限のログインが辞書に載りうるパスワードを使っている。
運用・監視□ `xp_cmdshell` の構成値を構成管理のベースラインで固定しておらず、 有効化の構成変更を検知していない。
運用・監視□ データベースサーバからの外向き通信が既定許可になっており、 FTP・非標準ポート（88・8000）が遮断されていない。
運用・監視□ サーバのイベントログを外部のログ基盤へ転送しておらず、 当該サーバ上のログだけが記録になっている。
体制・契約□ 暗号資産採掘の検知を「不要プロセスの停止」で閉じる運用になっており、 同一侵入による永続化・RAT の調査を手順に含めていない。
