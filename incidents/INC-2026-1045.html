**MongoDB は2026年11月10日、MongoDB Server のレプリケーション処理に 認証前に到達できる Use After Free（CVE-2026-118383）を公表し、修正版を提供した** （ベンダーの表題は「Pre-authentication use-after-free in MongoDB Server replica set primary catch-up」）。 **レプリカセットで新たに選出されたプライマリが最新状態へ追い付く キャッチアップ処理の完了時に不具合が生じる**（Security NEXT）。 **CVSS は 9.5（ベンダーの掲載値）で、重要度は最上位のクリティカル。 修正は 9.0.7／8.3.16／8.0.37／7.0.48／6.0.30／5.0.35／4.4.32。** **公表時点で悪用は確認されていない**（Security NEXT）。 **ただし任意コード実行まで至るかは資料で評価が分かれている。**

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表されている範囲は次のとおりである**（出典1・2・3・4）。 MongoDB Server のレプリケーション処理に Use After Free があり、 認証を経ずに到達できる。 成立の場面は、レプリカセットで新たに選出されたプライマリが 最新状態へ追い付く（キャッチアップ）処理である。 細工されたリクエストによってサーバプロセスが予期せず終了する。 **任意コード実行まで至るかは資料で評価が分かれている**〈齟齬3〉—— **Security NEXT は「条件次第でサーバプロセスの権限で任意のコードを実行される 可能性がある」とし、The Hacker News は「クラッシュを引き起こす」としている** （出典3・4）。 **実環境での悪用は公表時点で確認されていない**（出典3）。 **攻撃の具体的な手順・前提となるネットワーク到達性の条件は公表されていない** 〈未確定2〉。

可用性のために組んだレプリカセットが、そのまま攻撃面になっている原因・手口出典 [1] [2] [3] [4]

成立の場面は、レプリカセットのフェイルオーバーである（出典1・2・3）。

ベンダーが付けた表題は次のとおりである（出典1。原文英語を訳出）。

「MongoDB Server のレプリカセットのプライマリ追い付き処理における認証前の Use After Free」

MongoDB 自身の修正項目は次である（出典2。原文英語）。

「SERVER-138175 Fix use-after-free in CatchupState::abort() reentrancy via _catchupState」

CatchupState は、ノードがプライマリになる前の「追い付き」処理を担うレプリケーションの構成要素である。Security NEXT の説明は「新たに選出されたプライマリが最新の状態へ追い付くキャッチアップ処理の完了時に不具合が生じるおそれがある」である（出典3）。

ここが本件の読みどころである（本記録の評価）〈重要〉。レプリカセットは MongoDB の標準的な冗長構成であり、単一障害点を避けるために組むものである。その冗長化のための処理に、認証を経ずに到達できる不備があった——つまり可用性のための仕組みが可用性を損なう経路になっている。

The Hacker News の説明はこの条件性をより具体に述べている（出典4。原文英語を訳出）。

「クラッシュが起きるのは、そのサーバが最近の変更の一部を欠いたまま、後にメインのサーバを引き継ぐよう選出された場合のみである」

つまり「遅れているメンバーが昇格する」という、障害時にまさに起こる状況が条件になっている（本記録の整理）。平常時に試しても再現しない種類の不備である。

確認すべきは「いま何を動かしているか」である（本記録の推奨）。マネージドサービス（MongoDB Atlas 等）か自前運用かで作業が分かれ、自前運用の場合はレプリカセットのメンバーごとに版が異なることもある。メンバー単位で版を集計する必要がある（本記録の整理）—— 1台でも古ければ、その1台が昇格したときに条件が揃う。

なお、マネージドサービス側の適用状況について本記録は資料を確認していない〈未確定4〉。

追加リリース 9.0.8・8.0.38 は本脆弱性の修正ではない再発防止出典 [2] [3]

Security NEXT は「また追加リリースとして『同9.0.8』『同8.3.17』『同8.0.38』が提供されている」と記している（出典3）。

本記録がリリースノートを確認したところ、9.0.8 および 8.0.38 に記載されている項目は「SERVER-138547 Use target architecture in cross-compiled archive directory names」のみで、CVE-2026-118383 への言及は無い（出典2。原文英語。本記録の確認）〈重要〉。

一方、9.0.7 のリリースノートには次の注記がある（出典2）。

RedHat/CentOS 8.3 の s390x および RedHat/CentOS 9 の s390x 向けのバイナリは 9.0.7 では提供されない。これらの利用者は 8.0.38 のバイナリを使うこと（原文英語を訳出）

つまり 9.0.8・8.0.38 は、本脆弱性の追加修正ではなくビルド成果物に関するリリースとみられる（本記録の推定）。実務上の意味は「9.0.8 へ上げれば本件が直る」のではなく「9.0.7 以上であれば直っている」である（本記録の整理）。

8.3.17 のリリースノートは本記録が確認していない〈未確定5〉—— 8.3 系の確認は 8.3.16 以上であることを基準にすればよい（本記録の推奨）。

「クラッシュ」か「任意コード実行」か——資料で評価が分かれている未確定事項出典 [1] [2] [3] [4]

影響の上限について、2つの資料が異なる書き方をしている。

  • Security NEXT（出典3。原文日本語）——「細工されたリクエストによってサーバが予期せず終了したり、条件次第ではサーバプロセスの権限で任意のコードを実行される可能性がある」
  • The Hacker News（出典4。原文英語を訳出）——「認証されていない攻撃者が2つのリクエストを送ることでデータベースサーバのクラッシュを引き起こせる」。任意コード実行に触れていない

本記録はベンダー自身の説明文の全文を取得できていない（本記録の明示）〈齟齬2〉—— MongoDB の一覧ページに掲載されている説明は「A use-after-free in the replication component of MongoDB Server can occur when a newly ele…」で途切れており、続きは別ページにある。参照先として示されている課題（SERVER-138119）は認証を要するため参照できなかった。

判断に使える材料として確実なのは次である（本記録の整理）〈重要〉。

  • 不備の種別は Use After Free（出典1・2）
  • 認証前に到達できる（出典1「Pre-authentication」・出典3）
  • ベンダー掲載の CVSS は 9.5（出典1）—— サービス拒否だけでこの評点にはなりにくい（本記録の評価）
  • 公表時点で悪用は確認されていない（出典3）

運用の判断としては、任意コード実行の可否を待つ意味はない（本記録の推奨）。どちらであっても対処は同じ（修正版への更新と到達経路の制限）であり、評点 9.5 と「認証不要」の2点で優先度は決まる。

緩和策は示されていない——更新以外の手は「到達させない」だけである対策・注意喚起出典 [1] [2] [3] [4]

本記録が取得した資料に、構成変更による回避策（ワークアラウンド）の記述は無い（出典1・2・3・4。本記録の確認）〈未確定3〉。

したがって取れる手は2つである（本記録の整理）。

  1. 修正版へ更新する — 各系列の 9.0.7／8.3.16／8.0.37／7.0.48／6.0.30／5.0.35／4.4.32 以上。レプリカセットのローリング更新は、更新中に意図的なフェイルオーバーを起こす作業である（本記録の注記）〈重要〉——本脆弱性の成立条件がフェイルオーバーであることを踏まえ、外部からの到達を止めた状態で行うのが安全である（本記録の推奨）。
  2. 到達経路を制限する — データベースをインターネットから到達不能にし、接続元を承認済みのシステムに限る。レプリカセットのメンバー間通信を専用のネットワークに分ける。

2は本脆弱性に限らず効く（本記録の評価）。認証前に到達できる不備は、認証の強度では防げない——防げるのはネットワーク層の到達性だけである。

国内の注意喚起（JPCERT/CC 等）が出ているかは本記録では確認していない（本記録の明示）。

  • 「認証前」の脆弱性は、認証の強化では防げない。 到達性の管理を別の統制として持つ。

    取るべき行動 **データベース・メッセージキュー等のミドルウェアについて、 「インターネットから到達可能か」を資産台帳の必須項目にし、四半期ごとに外部から実測する。** **「認証前（pre-auth）」の表記がある勧告を、適用判断の最優先区分として運用規程に書く。**
  • 冗長構成そのものが攻撃面になりうる。 可用性設計のレビューにセキュリティの観点を入れる。

    取るべき行動 **フェイルオーバー時のプロセス異常終了を、更新の適用状況と突き合わせる手順にする （未更新のメンバーで起きた場合は調査に回す）。** **クラッシュダンプとログを外部に保全し、事後に切り分けられる状態にする。**
  • データベースプロセスの権限と外向き通信を、いまのうちに絞る。
    **Security NEXT は「条件次第ではサーバプロセスの権限で任意のコードを 実行される可能性がある」としている**（出典3）〈重要〉—— **成立した場合の影響の上限は、プロセスの権限で決まる**（本記録の整理）。 **本脆弱性に限らず、次の同種の不備にも効く**（本記録の評価）。
    取るべき行動 **MongoDB を専用の非特権アカウントで動かし、 データディレクトリ以外への書き込みを制限する。** **データベースサーバからの外向き通信を既定拒否にする。**
