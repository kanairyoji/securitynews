INC-2026-1059Windows CLFS に SignDrop 公開

Microsoft が2025年10月に CLFS のメモリ破壊対策として入れたログ認証機構そのものを踏み台にし、 Windows Defender に SYSTEM 権限で認証ファイル（.cnpf）を作らせてパスを差し替え、 標準ユーザーから SYSTEM へ昇格する実証コード「SignDrop」が2026年11月10日に 事前連絡なしで公開された——CVE 番号も修正も無く、Microsoft は本記録の作成時点で 見解を示していない。作者は「アンチマルウェア自身のプロセスからの要求に見えるため、 どの製品の自己防衛も回避できる」と主張している

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備未知の脆弱性の悪用
初報: 2026年11月10日（研究者による実証コードの公開） 最終更新: 2026年11月13日

2026年11月10日、研究者 Abdelhamid Naceri（別名 Nightmare Eclipse／GitHub では MSNightmare）が、Windows の Common Log File System（CLFS）ドライバを使った権限昇格の実証コードを「SignDrop」の名で公開した（出典1・2・3）。標準ユーザーから NT AUTHORITY\SYSTEM への昇格である。

踏み台にされたのは、Microsoft が2025年10月28日に正規の配信経路で導入したCLFS のログ認証機構そのものである（出典1）。CLFS ドライバのメモリ破壊脆弱性がランサムウェアに繰り返し悪用されたため、Microsoft はログファイルに HMAC を付ける対策を入れた。その対策が新しい脆弱性を作ったというのが作者の主張である（出典2・3）。

仕組みはパスの差し替えである（出典1・2）。CLFS は新しいログを作るとき、対になる認証ファイル（拡張子 .cnpf）を作る。最初のアクセス検査は正しく行われるが、その後に別の特権プロセスがそのログを開くと、認証ファイルは特権プロセスの文脈で作られる（出典1・3）。実証コードは Windows Defender の署名更新 RPC を呼んで Defender にログを開かせ、オブジェクトマネージャのシンボリックリンクで .cnpf の作成先をC:\Program Files\Common Files\microsoft shared\ink\hid.dll へ向ける。clfs.sys が SYSTEM として、攻撃者の指定した場所にファイルを作る（出典2）。

作者が「この脆弱性は唯一無二だ」と書いた理由は、権限昇格そのものではない（出典3）。ファイル作成の要求がアンチマルウェア自身の正規プロセスから出ているように見えるため、その製品のカーネルドライバから見ると検査を通る——つまり自己防衛（改ざん防止）を回避して任意の AV／EDR を止められるという主張である。本記録はこの主張の裏取りを確認していない〈未確定3〉。

本記録が構造上の中心と見るのは2点である（本記録の判断）。①緩和策が攻撃面になった。 対策の無効化は選べない——作者自身が「無効にすると CLFS のメモリ破壊脆弱性に晒される」と書いており（出典1）、退避先が無い。 ②影響範囲を利用者が自分で測れる形で示されていない。作者は「世界の Windows 導入の80%」と述べるが（出典1）、検証されたのは Windows 11 26H2 と Windows Server 2025 の試験ビルドだけである（出典1）。唯一の判定手段は実証コードを走らせるか、レジストリの値を読むことだとされている（出典1・2）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**メモリ破壊を一切使わない連鎖である**（出典2が明記）。 使われるのは正規のサブシステム（CLFS・オブジェクトマネージャ・ Defender の RPC・AppInfo／consent.exe）だけで、 **攻撃者が持ち込むのは「どの順でどこを指させるか」という段取りである** （本記録の整理）〈重要〉。 **骨格は3手に要約できる**（出典1・2）。 ①標準ユーザーの権限で CLFS ログとシンボリックリンクを用意する。 ②Defender に署名更新をさせてログを開かせ、 SYSTEM 権限で `.cnpf` を作る瞬間にリンクの指す先を差し替える。 ③こうして任意の場所に作られたファイルを DLL に上書きし、 SYSTEM で動く consent.exe に読ませる。 **以下の各段階は出典2の再現報告に基づく**（本記録が整理した。 作者の README（出典1）はここまで細かく書いていない）。

  1. 1. 実行disclosed[1] [2]
    実証コードが osk.exe（スクリーンキーボード）を隠して起動し直し、 %TEMP% 配下に作業用ディレクトリを作る。 `\CLFS` のデバイス接頭辞を通じて CLFS ログを作成し、 `\BaseNamedObjects\Restricted\` の下にオブジェクトマネージャの シンボリックリンクを2本置く（出典2）。 次に DeviceIoControl（IOCTL 0x8007A808）で CLFS コンテナと 署名ファイル（.cnpf）を作らせる。 **ここで .cnpf が現れなければ、その環境では CLFS 認証が 有効になっていないと判定できる**（出典2）
    根拠: Cyderes（Howler Cell）の再現報告（出典2）。 README の記述（出典1）とは「CLFS のログ作成時に .cnpf が作られる」点で整合する
  2. 2. 権限昇格disclosed[1] [2] [3]
    偽の MpEngine.dll を置いて oplock を張り、作業スレッドから Defender の署名更新 RPC（Proc42_ServerMpUpdateEngineSignature）を呼ぶ。 oplock が破れた時点で偽ファイルを削除し、 `\BaseNamedObjects\Restricted` 配下のシンボリックリンクを張り替える—— `mpasbase.vdm` という名のリンクを CLFS ログに向け、 `.cnpf` のリンクを `C:\Program Files\Common Files\microsoft shared\ink\hid.dll` に向ける。 **SYSTEM として動く clfs.sys が、このリンクを通じて .cnpf を作る結果、 ink ディレクトリに hid.dll が作られる**（出典2）。 **最初のアクセス検査は正しく行われるが、 後から別の特権プロセスがログを開くとロジックが悪用できる**という 作者の説明と一致する（出典1・3）
    根拠: Cyderes の再現報告（出典2）。作者の README の説明（出典1）および 作者の発言「すべては Microsoft によって正しく行われているが、 ロジックが悪用を許している」（出典3。原文英語を訳出）と整合する
  3. 3. 検知回避推定[2] [3]
    植え付けたファイルを CREATE_ALWAYS で開き、 実証コードのリソース（IDR_DLL1）の中身で上書きする。 次に conhost.exe に対して ShellExecute の "runas" を呼ぶ。 AppInfo サービスが consent.exe を SYSTEM として起動し、 consent.exe が ink ディレクトリの hid.dll を読み込む。 **読み込まれたコードは WinSta0\Default に切り替えて SYSTEM の conhost.exe を起こし、consent.exe を終了させる**（出典2）。 **その後、植え付けた hid.dll はトランザクション削除で消される**〈重要〉—— **ディスク上の痕跡が残らない**（本記録の読み）。 作者はあわせて、**ファイル作成の要求が アンチマルウェア自身の正規プロセスから出ているように見えるため、 どの製品の自己防衛（改ざん防止）も回避できる**と主張している（出典3）

直すべき対象が、去年入れた対策そのものである原因・手口

CLFS は、ランサムウェアの権限昇格に繰り返し使われてきた部品である（出典3）。Microsoft は2025年10月28日、ログファイルに HMAC を付ける認証機構を正規の配信経路で導入した（出典1）。メモリ破壊を使った悪用を止めるための対策である。作者は「この緩和策のあと CLFS 脆弱性の悪用は急減した」と認めた上で、緩和策そのものが新しい脆弱性を作ったと述べている（出典3）。

仕組みは認証ファイルの作成順序にある（出典1・3）。

  • CLFS が新しいログを作ると、対になる認証ファイル（.cnpf）が作られる
  • 最初のアクセス検査は正しく行われる（作者自身がそう書いている）
  • しかし、その後に別の特権プロセスが同じログを開くと、認証ファイルはその特権プロセスの文脈で作られる
  • 作られるファイルは、元のファイルのアクセス権を引き継ぐ（出典3）

Windows Defender のような特権プロセスは、外から強制的にログを開かせられる（出典1・3）。そこへオブジェクトマネージャのシンボリックリンクを噛ませれば、SYSTEM が、攻撃者の選んだ場所にファイルを作る。

作者の言い方はこうである——「正しく連鎖させれば、おかしなことに、この正規のセキュリティ緩和策は自分自身に対して使えて、権限昇格を許してしまう。ここで Microsoft はすべてを正しく行っているが、ロジックが悪用を許している」（出典3。原文英語を訳出）。

この構図が、退避先の無さをそのまま説明している（本記録の整理）〈重要〉。緩和策を外せば、緩和策が防いでいたメモリ破壊の系統に戻る—— 作者自身と、再現を報告した Cyderes の双方が、無効化を推奨しないと書いている（出典1・2）。選べるのは「待つ」だけであり、待つ間に何をするかが実務の全部になる。

    **作者と出典2の双方が無効化を推奨しないと書いている**（出典1・2）〈重要〉—— **CLFS のメモリ破壊脆弱性の系統に晒されるためである**（出典3。 この系統は実際にランサムウェアに悪用されてきた）。 **現場では「設定を戻せば直る」が最初に出る案になりやすい**（本記録の評価）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Windows クライアントまたは Windows Server を運用しており、 `HKLM\SYSTEM\CurrentControlSet\Services\CLFS\Authentication\Mode` の値が 0（強制モード）または 1（学習モード）になっている端末がある。
運用・監視□ ローカルで標準ユーザー権限のコード実行を許している環境がある （共用端末・仮想デスクトップ・開発端末・ターミナルサーバー・ 利用者が任意の実行ファイルを持ち込める端末）。
運用・監視□ EDR／監査ログの採取対象に、ファイル作成イベントと イメージ読み込み（DLL 読み込み）イベントが含まれていない、 または保持期間が数日しかない。
認証・認可□ EDR・アンチマルウェアの稼働確認を、そのエージェント自身の報告だけに 依存しており、別系統（資産管理・サーバー側の最終通信時刻・ ネットワーク側の到達確認）で二重化していない。
体制・契約□ 脆弱性管理が CVE 番号を鍵にして回っており、 CVE の無い案件（実証コードは公開済み・ベンダー勧告は無し）を 登録・追跡する欄と担当が決まっていない。
体制・契約□ セキュリティ機能・緩和策を無効化する判断の様式に、 「無効化によって晒される脅威」を併記する欄が無い。
