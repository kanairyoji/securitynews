INC-2026-1062Check Point GW 経由で ESXi 破壊

Check Point が2026年11月12日、自社 Security Gateway の Mobile Access ポータルを 経路とする侵害を公表した——PHP の PHP2Shell（CVE-2026-109618／109619）で 侵入し、**未公表だった Gaia OS のローカル権限昇格 CVE-2026-123039（CVSS 7.8・ 悪用あり）で root を取り**、TSGA／TSProxy を仕込んだうえで、 ゲートウェイから VMware ESXi へ横展開してワイパー destroy_v6 を実行した。 修正は10月23日に出ており、**悪用はその約1週間後に始まった**

2026年11月12日、Check Point Software Technologies が自社のSecurity Gateway を標的とする侵害活動を公表した（出典1・2）。侵害の経路は Mobile Access ポータルであり、起点は PHP 自体の脆弱性である。

使われたのは3つの脆弱性を連ねた経路である（出典1・2）〈重要〉。まず PHP2Shell（CVE-2026-109618・CVE-2026-109619／CVSS 9.2）で、インターネットに面した Mobile Access ポータルに到達する。 PHP2Shell は PHP 5 以降のすべての版に影響する遠隔コード実行の2件で、2026年10月21日に PHP 側で修正された（出典5）。次に、公表されていなかった Gaia OS のローカル権限昇格CVE-2026-123039（CVSS 7.8）で、ポータルのサービスアカウントから root へ昇格する（出典1・2）。この CVE は本件の調査で初めて世に出たもので、Check Point 自身が「悪用あり」と記している（出典2・3）〈重要〉。

CVE-2026-123039 の中身は、認証していないソケットである（出典4）〈重要〉—— root で動く DynamicCLI デーモンが、誰でも書き込める /tmp/dynamic_socket を待ち受けており、接続元のプロセスを確かめていなかった。 ローカルの認証済み利用者がコマンドを送るだけで root として実行された。

root を取った後の動きは、情報窃取では終わっていない（出典1）〈重要〉。攻撃者は ポータルがログイン画面を組み立てるディレクトリに PHP ウェブシェル（zz*.tpl）を置き、TSGA バックドア（/tmp/CPconfigdaemon として起動しslot_CPconfigdaemon へ移動）と TSProxy（/lib/libcpfwcommon.so） を仕込んだ。TSGA はファイアウォールのログ改変まで備えている（出典1）。そこから gogo スキャナで内部を探り、vpxuser アカウントで SSH によりVMware ESXi ホストへ移り、ワイパー destroy_v6 を実行した（出典1）。

ワイパーは身代金を要求していない（出典1）〈重要〉。処理した各ディレクトリに DREAM_ANNEXATION.txt という書き置きを残すが、内容は政治的なもので、ヘブライ語でイスラエル・パレスチナ情勢に言及し、身代金の交渉を明示的に拒んでいる（出典1）—— 金銭目的の恐喝ではなく、破壊それ自体が目的に見える形である。

波は2つあり、性格が違う（出典1）。第1波は2026年10月30日で、イスラエルの組織を標的とし、一部で破壊に至った。 第2波は11月2日で、複数の国・業種に広がったが、破壊の痕跡は観測されていない（出典1）。どちらの波も業種の偏りが無く、Check Point は「業種を狙った標的化ではなく、機会主義的な初期侵入の試行」と見ている（出典1。原文英語を訳出）。

帰属は確定していない（出典1）〈重要〉。TSGA と TSProxy は、Ivanti 製品への攻撃で見つかった PhiliKit の改変版であり、ESET は PhiliKit を中国関連の UNC5221 に結び付けている（出典1）—— TSProxy は PhiliKit の構成部品 libdssafe.so と、運用者の認証情報・通信の秘密・TLS 証明書と秘密鍵まで一致する。 しかし破壊の実行・イスラエルへの集中・ヘブライ語の書き置きはUNC5221 の既知の目的と合わない（出典1）。Check Point は「証拠は、この作戦の本当の性質を高い確度で評定することを許さない」と結論し、4つの筋書きを並べたまま残している（出典1。原文英語を訳出）。

侵害された規模は限定的である（出典2）。Check Point は「単一の地域で、修正されていないシステムが20数台（a couple of dozen）だけが、観測された事案で侵害された」としており、該当する顧客には実時間で通知したと述べている（出典2。原文英語を訳出）。

**3つの脆弱性を連ねて root を取り、そこから別の層へ移って破壊している** （出典1・2）〈重要〉。 **段階は、PHP2Shell による Mobile Access ポータルへの到達 → CVE-2026-123039 による root への昇格 → ウェブシェルと TSGA／TSProxy による永続化と検知回避 → gogo による内部探索 → vpxuser での SSH による ESXi への横展開 → destroy_v6 による破壊、である**（出典1）。 **本記録が構造上の中心と見るのは、 「境界機器の侵害が、境界機器の被害では終わらなかった」点である**（本記録の評価）〈重要〉—— **ゲートウェイ上で失われたのは制御であり、 実際に壊されたのは ESXi 上の仮想環境だった。** **ESXi 側の脆弱性は1つも使われていない**（出典1。本記録の確認）—— **使われたのは正規の管理経路と正規のサービスアカウントである。** **第2波では破壊に至っていない**（出典1）〈未確定2〉—— **同じ経路で入って破壊しなかった理由は公表されていない。**

  1. 1. 偵察[1] [2] [4]
    **130.94.19[.]204 から脆弱な Mobile Access ポータルを探すスキャンが 行われた**（出典1・4）。 **スキャンは 00:00〜09:00 UTC に集中している**（出典1）。 **発信元は LightNode VPS 上にあった**（出典1）。 **第1波（10月30日）はイスラエルの組織に、 第2波（11月2日）は複数国に向けられた**（出典1）。 **どちらも業種の偏りが無く、Check Point は機会主義的な試行と見ている**（出典1）。
  2. 2. 初期侵入[1] [2] [4]
    **PHP2Shell（CVE-2026-109618・CVE-2026-109619／CVSS 9.2）を悪用して Mobile Access ポータルでコードを実行した**（出典1・2）。 **痕跡は2つある**（出典1・4）〈重要〉—— **/opt/CPcvpn-R81.20/tmp/ 配下に upload_progress_pwn という印を含む PHP セッションファイルが残り、 ポータルの Apache／PHP ワーカーが数百回にわたって異常終了した （悪用の試行の繰り返しを示す）。** **この時点で得られるのはポータルのサービスアカウントの権限である**（出典1）。
  3. 3. 権限昇格[1] [2] [4]
    **CVE-2026-123039 を悪用し、ポータルのサービスアカウントから root へ 昇格した**（出典1・2・4）〈重要〉。 **root で動く Gaia OS の DynamicCLI デーモン（dynamic_server）が、 誰でも書き込める局所ソケット /tmp/dynamic_socket を待ち受けており、 接続してきたプロセスを認証していなかった**（出典4。原文英語を訳出）—— **認証済みのローカル利用者がソケットにコマンドを送れば root で実行された。** **この脆弱性は本件の調査で初めて公表された**（出典1・2）。
  4. 4. 永続化[1] [2] [4]
    **2段構えで永続化している**（出典1・4）〈重要〉。 **第1段はウェブシェルである**—— **ポータルがログイン画面を組み立てるテンプレートディレクトリに zz で始まり .tpl で終わる Base64 符号化されたファイルを置いた。** **当初は単純なコマンド実行用だったが、後に固定鍵 zz2026 を要求し、 OS コマンド・PHP の評価・ファイルのアップロードに対応する版へ 置き換えられた**（出典1・4）—— **アップロードは /tmp/.up.tpl に保存され、 challenge_render.tpl の名でポータルのディレクトリへ複写された。** **第2段は TSGA バックドアである**—— **/tmp/CPconfigdaemon として起動し、自身を移動して 起動の永続化ディレクトリ内で slot_CPconfigdaemon の名で動き直した**（出典1・4）。 **TSGA はバックアップとスナップショットを介した永続化も備える**（出典1）〈重要〉—— **機器の復元で消えない形である。**
  5. 5. 検知回避[1] [2] [4]
    **TSProxy を /lib/libcpfwcommon.so として書き込み、 機器上のプロセスへ注入した**（出典1・4）〈重要〉。 **TSProxy はネットワーク呼び出しを横取りし、 攻撃者が使う接続だけを処理して通常の通信はそのまま通す**（出典1・4）—— **通信の異常として表に出にくい。** **加えて TSGA は、バイナリ形式のファイアウォールログを改変する機能を持つ** （出典1・4）〈重要〉。 **Check Point が解析した PhiliKit の版は待ち受けをループバックに 限っていたが、TSGA は IPv4 の全インターフェースで待ち受ける**（出典1）。
  6. 6. 内部探索[1] [4]
    **侵害したゲートウェイ上で公開ツール gogo を実行し、 内部ネットワークの資産を把握した**（出典1・4）〈重要〉—— **境界機器は、内部に対して到達性の高い位置にある**（本記録の整理）。 **gogo は中国関連の攻撃者による Ivanti 製品の悪用でも 報告されており、帰属の根拠の1つに挙げられている**（出典1）。
  7. 7. 横展開[1] [4]
    **ゲートウェイから VMware ESXi ホストへ、vpxuser アカウントで SSH により移動した**（出典1・4）〈重要〉。 **vpxuser は vCenter が ESXi を管理するために使うサービスアカウントである** （本記録の補足）。 **ESXi 側の脆弱性は使われていない**（出典1。本記録の確認）〈重要〉—— **使われたのは正規の管理経路と正規のアカウントである。** **攻撃者がこの認証情報をどこで得たかは公表されていない**〈未確定3〉。
  8. 8. 影響（暗号化・破壊・改ざん）[1] [4]
    **ESXi ホスト上でワイパー destroy_v6 を /tmp 配下に置いて実行した** （出典1・4）〈重要〉。 **指定したディレクトリを再帰的に処理し、拡張子を問わず削除する。** **既定ではゼロで上書きしてから削除し、高速モードでは上書きを省く** （出典1・4）——**除外するディレクトリを指定できる。** **処理した各ディレクトリに DREAM_ANNEXATION.txt を残す**（出典1）。 **書き置きは政治的な内容で、時刻を含み、ヘブライ語で イスラエル・パレスチナ情勢に言及し、身代金の交渉を明示的に拒んでいる** （出典1・4）〈重要〉——**恐喝型ではない。** **書き置きは Dream Security のブランドを使っている**（出典1）。 **破壊に至ったのは第1波（イスラエルの組織）の一部のみで、 第2波では破壊の痕跡が観測されていない**（出典1）〈未確定2〉。

境界機器の侵害が、境界機器の被害では終わらなかった原因・手口

本件の経路は、6つの段階を通って別の層へ抜けている（出典1）。

段階 手段 前提
初期侵入 PHP2Shell（CVE-2026-109618／109619・9.2） 10月23日の修正が未適用
権限昇格 CVE-2026-123039（7.8・当時未公表） ローカルの認証済み利用者

検知回避 TSProxy（/lib/libcpfwcommon.so）・ログ改変 root

横展開 vpxuser で SSH → ESXi 管理経路が通っていた

ここで重要なのは、最後の2段に脆弱性が1つも無いことである（出典1。本記録の確認）〈重要〉。

ESXi 側の脆弱性は使われていない—— 使われたのは gogo（公開ツール）と、vpxuser（正規のサービスアカウント）と、SSH（正規の管理経路）である。 つまり脆弱性の管理で止められたのは前半3段までで、実際に被害が出た後半は、構成と権限の問題だった（本記録の評価）。

ゲートウェイ上で失われたのは制御であり、壊されたのは ESXi 上の仮想環境である。 したがって「Check Point を使っているか」という問いは、本件の当てはめとして不十分である（本記録の評価）〈重要〉—— 問うべきは「境界機器から仮想化基盤へ管理経路が通っているか」である。

修正は出ていた。足りなかったのは7日である評価・解釈

Check Point は、侵害されたのが未適用の機器のみだったと明示している（出典2。原文英語を訳出）〈重要〉—— 「単一の地域で、修正されていないシステムが20数台だけが、観測された事案で侵害された」。

これは「ゼロデイに備えよ」という話ではない（本記録の評価）。初期侵入に使われたのは、修正が出ていた既知の脆弱性である。 未公表だったのは権限昇格の1件だけで、それ単体では外からは踏めない（出典2。本記録の読み）。

したがって本件で問われるのは、適用の速度である。 全台を対象にした適用計画で7日を守れる組織は多くない（本記録の評価）—— ベンダー自身が「インターネットに面した Mobile Access の構成を優先せよ」と順序を示しているのは、全台を7日で処理できないことが前提になっている（出典2。本記録の読み）。

面している資産を独立した一覧として持つかどうかが、この7日を使えるかどうかを決める（本記録の評価）〈重要〉。

権限昇格の CVSS は 7.8 で、優先順位の網から落ちる形だった評価・解釈

CVE-2026-123039 の CVSS は 7.8（High）である（出典2）。PHP2Shell の 9.2（Critical）より低い。

評点だけで適用順序を決める運用では、この1件は後回しになる（本記録の評価）〈重要〉。理由は評点の付け方として正しい—— ローカルの権限昇格は、単体では外から踏めないため値が上がらない。

しかし本件では、この1件が経路の要になっている（出典1・2）。PHP2Shell で得られるのはポータルのサービスアカウントの権限までで、ウェブシェルの設置・TSGA の投入・ログの改変・ESXi への横展開はいずれも root を要する（出典1。本記録の読み）。

つまり評点の低い1件が、評点の高い1件の価値を決めていた。

本記録はここから、評点ではなく「連鎖の可能性」で見る必要があると評価する〈重要〉—— 同じ機器の上に、外から踏める脆弱性と、ローカルの権限昇格が同時にあるかどうかを問う形である。 本件では両方が同じ Jumbo Hotfix で直る（出典2）—— したがって実務上の結論は「分けずに当てる」になる。

探索の手がかりに「記録の不在」が入っている対策・注意喚起

Check Point の勧告が挙げた探索の手がかりは6つある（出典2）。

  • スキャンの発信元 130.94.19[.]204 ／ 130.94.19[.]168
  • upload_progress_pwn を含む PHP セッションファイル
  • CPconfigdaemon を装うプロセス
  • /tmp または /temp 配下のスキャナ・ワイパー
  • 「Dream Annexation」に言及する身代金風の書き置き
  • ファイアウォールの通信ログの説明のつかない欠落（とくにログデーモンの異常終了後）

最後の1つが、他の5つと性質が違う（本記録の評価）〈重要〉。

他の5つは「あるもの」を探す。最後の1つは「ないもの」を探す。 TSGA がバイナリ形式のファイアウォールログを改変する機能を持つためである（出典1）。

通常の監視は、記録された事象に対して条件を書く作りになっている。 「ログが来ないこと」に警報を出す仕組みを別に持っていないと、この手がかりは誰も見ない（本記録の評価）。

加えて BleepingComputer は、ベンダーが示した別の見分け方を伝えている（出典4）〈重要〉—— 「system() のシンクの使用（正規の通信では稀か存在しない）」と「既定の Clish ラッパーを経由しないコマンド（ソケット経由で root として実行されたことを示す）」。

後者は、本記録が本件で最も価値の高い検知条件と評価するものである〈重要〉—— 脆弱性の個別の知識を要しない。 未公表の権限昇格であっても、「root 実行が正規の経路を通っていない」という形は変わらない。

なお勧告は「一致が無いことは侵害を排除しない」と明記している（出典2。原文英語を訳出）—— IoC 照合は「侵害なし」の根拠にならない。

  • 境界機器の資産一覧を「全台」ではなく「インターネットに面しているもの」で 独立に持ち、ベンダーの修正が出た時点でこの一覧だけを先に処理する体制にする。
    **修正の提供（2026年10月23日）から悪用開始（10月30日）までは7日である** （出典1・2。算定は本記録）〈重要〉。 **侵害されたのは未適用の機器のみだった**（出典2。Check Point が明示）—— **つまりこの7日が使えれば防げた。** **全台を対象にした適用計画で7日を守れる組織は多くない** （本記録の評価）—— **ベンダー自身が「インターネットに面した Mobile Access の構成を優先せよ」と 順序を示しているのは、全台を7日で処理できないことが前提である**（出典2）。
    取るべき行動 **境界機器（VPN・リバースプロキシ・認証の前段・Mobile Access 型の ポータル）について、インターネットに面している機器だけの一覧を 資産台帳とは別に維持する。** **この一覧に対しては、ベンダーの修正公開から7日以内の適用を 約束された期限として設定し、守れない場合は 到達元の制限または機能の停止を代替として用意しておく。** **一覧の正しさを四半期ごとに外側からの到達性で検証する （構成情報ではなく実際の到達で確かめる）。**
  • 境界機器の侵害を「その機器が止まる」事象として見積もるのをやめ、 そこから到達できる基盤の被害として見積もる。
    **本件でゲートウェイ上で失われたのは制御であり、 実際に壊されたのは VMware ESXi 上の仮想環境である**（出典1）〈重要〉。 **ESXi 側の脆弱性は1つも使われていない**（出典1。本記録の確認）—— **使われたのは公開ツール（gogo）と正規のサービスアカウント（vpxuser）と 正規の管理経路（SSH）である。** **したがって「Check Point を使っているか」という当てはめでは 本件の被害の形を捉えられない**（本記録の評価）—— **問いは「境界機器から仮想化基盤へ管理経路が通っているか」である。**
    取るべき行動 **境界機器ごとに「そこから到達できる管理面」を書き出し、 仮想化基盤・バックアップ基盤・ディレクトリサービスが含まれるかを判定する。** **含まれる経路について、業務上必要かを個別に決裁し、 不要なものを閉じる。** **必要なものについては、使う認証情報を境界機器と共有しない （サービスアカウントの対話的利用を禁じる）形にする。** **リスク登録簿の記述を「境界機器の侵害」から 「境界機器を経由した仮想化基盤の喪失」に書き換える。**
  • 復旧計画が「バックアップから戻す」で閉じていないかを確認する。 本件のバックドアは、バックアップとスナップショットを介して永続化する。
    **TSGA は、バックアップとスナップショットを介した永続化を 機能として備えている**（出典1）〈重要〉。 **つまり侵害後に取得したバックアップからの復元は、 バックドアを呼び戻す**（本記録の読み）。 **さらに破壊側では、ワイパーが除外ディレクトリを指定できる仕様であり、 指定しなければ拡張子を問わず処理する**（出典1）—— **ESXi の datastore 上にバックアップを置く構成では一緒に失われる** （本記録の評価）〈未確定2〉。
    取るべき行動 **仮想化基盤のバックアップについて、 ①保管先が仮想化基盤の管理権限から到達できないこと、 ②認証情報が仮想化基盤と独立していること、 ③復元前に既知良好な状態と照合する手順があること、の3点を確認する。** **満たさない場合、復旧の所要時間の見積りを 「バックアップが使えない前提」で作り直す。** **侵害時点の判定（いつから汚染されているか）が 復旧の前提になることを、事業部門と事前に合意しておく。**
  • 脆弱性の優先順位を CVSS の値だけで決めている運用を見直す。 本件の要になったのは 7.8 の1件である。
    **PHP2Shell は 9.2（Critical）だが、 権限昇格の CVE-2026-123039 は 7.8（High）である**（出典2）〈重要〉。 **評点の付け方としては正しい**—— **ローカルの権限昇格は単体では外から踏めない。** **しかし本件では、PHP2Shell で得られるのはサービスアカウントの権限までで、 ウェブシェルの設置・TSGA の投入・ログの改変・ESXi への横展開は いずれも root を要する**（出典1。本記録の読み）—— **評点の低い1件が、評点の高い1件の価値を決めていた。**
    取るべき行動 **境界機器について、「外から踏める脆弱性」と 「同じ機器上のローカル権限昇格」が同時に未修正でないかを 判定する項目を追加する。** **同時にある場合は、評点に関わらず最優先として扱う。** **本件では両方が同じ Jumbo Hotfix で直るため、 実務上の結論は「分けずに当てる」になる**（出典2）—— **ベンダーの一括修正を CVE 単位に分解しない運用を既定にする。**
  • ベンダーが「悪用の有無」と「自社の該当」を別に伝えてくることを前提に、 勧告の読み方を定めておく。本件では「一致が無いことは侵害を排除しない」と ベンダー自身が明記している。
    **Check Point は IoC と探索の手がかりを示したうえで、 「一致が無いことは侵害を排除しない」と明記した**（出典2。原文英語を訳出）〈重要〉。 **理由は本件の構造にある**（本記録の読み）—— **TSGA はファイアウォールログを改変する機能を持ち、 勧告は「ログの説明のつかない欠落」自体を手がかりに挙げている**（出典1・2）。 **つまり痕跡が無いことは、痕跡が消されたことと区別できない。** **IoC 照合の結果を「侵害なし」の報告に使うと、 経営は実態より安全だと判断する**（本記録の評価）。
    取るべき行動 **IoC 照合の結果を経営に上げる書式を、 「一致なし」ではなく「一致なし（照合の限界を併記）」に変える。** **併記する限界は、①対象機器のログが機器内のみに残っていたか、 ②攻撃者がログを改変できる権限に至った可能性があるか、の2点とする。** **本件のように提供元が自ら限界を明記した場合は、 その文言を報告にそのまま引く。**
セキュリティ技術者への示唆
  • 「root での実行が正規のラッパー（Clish）を経由していない」ことを 検知条件として実装する。脆弱性の個別の知識を要しない。
    **Check Point が示した見分け方である**（出典4）〈重要〉—— **「既定の Clish ラッパーを使わないコマンドは、 ソケット経由で root として実行されたことを示し、追加調査を要する」。** **本記録はこれを本件で最も価値の高い検知条件と評価する**（本記録の判断）—— **CVE-2026-123039 は悪用時点で未公表だったが、 この条件は脆弱性の番号を知らなくても成立する。** **併せて「system() のシンクの使用（正規の通信では稀か存在しない）」も 挙げられている**（出典4）。
    取るべき行動 **Gaia 上のコマンド実行の記録を、Clish 経由か否かで分類し、 非経由の root 実行を調査対象のキューに入れる。** **同様の考え方を他の機器にも広げる—— 管理 CLI を持つアプライアンスについて、 「正規の管理インターフェースを経由しない特権実行」を 検知条件として1本持つ。** **この記録を機器の外へ転送する（機器内のログは改変されうる）。**
  • 境界機器のログを機器の外へ転送し、「受信が途切れたこと」そのものに 警報を出す。本件の攻撃者はログを改変できる権限に至っている。
    **TSGA はバイナリ形式のファイアウォールログを改変する機能を持つ** （出典1）〈重要〉。 **勧告は「ファイアウォールの通信ログの説明のつかない欠落、 とくにログデーモンの異常終了後」を探索の手がかりに挙げている**（出典2）—— **検知の対象が、記録された事象ではなく記録の不在である。** **通常の監視は記録された事象に条件を書く作りであり、 「来ないこと」に警報を出す仕組みを別に持っていないと誰も見ない** （本記録の評価）。
    取るべき行動 **境界機器・ESXi・vCenter のログを遠隔 syslog で外部のログ基盤へ転送する （ESXi のログは再起動で消える領域に置かれる）。** **ログ基盤側に「機器ごとの受信の連続性」の監視を作り、 受信量の急減と一定時間の無受信に警報を出す。** **しきい値は機器の平常時の流量から決め、 ログデーモンの異常終了イベントと相関させる。**
  • 境界機器を発信元とする内部向け通信の「広がり」に警報を出す。 これは機器の中に手を入れずに成立する。
    **攻撃者はゲートウェイ上で gogo スキャナを実行し、 内部資産を把握した**（出典1・4）〈重要〉。 **境界機器は内部に対して到達性が高い位置にある**（本記録の整理）。 **本記録はこの段階を、本件で最も見落としが惜しいところと評価する**—— **破壊の前に、横展開の準備が通信として現れている。** **アプライアンスには汎用のエージェントを入れられないが、 「境界機器が内部の多数の宛先を順に叩いている」という通信は 内部側のネットワーク監視で見える**（本記録の評価）。
    取るべき行動 **境界機器の IP を発信元とする内部向けフローについて、 単位時間あたりの宛先数・ポート数のしきい値で警報を作る。** **正常な運用の流量を先に測ってベースラインにする （境界機器が内部の多数を叩く正当な動作がある場合は除外条件に書く）。** **併せて、境界機器から到達できる内部の宛先とポートを 業務上必要なものに限定する。**
  • ESXi の execInstalledOnly を有効に保ち、SSH を常時無効にして、 有効化の操作そのものを警報にする。
    **本件のワイパー destroy_v6 は /tmp 配下に置かれて実行された** （出典1・4）〈重要〉。 **execInstalledOnly は、持ち込まれた実行ファイル全般に効く** （本記録の整理）——**ワイパーの個別の知識を要しない。** **横展開は vpxuser アカウントでの SSH によるものだった**（出典1）—— **SSH が有効でなければこの経路は成立しない。** **ただし本件で SSH が元から有効だったのか攻撃者が有効化したのかは 公表されていない**〈未確定3〉。
    取るべき行動 **ESXi の execInstalledOnly の設定値を全ホストで棚卸しし、 無効になっているホストを有効化する（設定の弱化を警報条件にする）。** **SSH／ESXi Shell を常時無効にし、有効化の操作を 承認された作業窓と突き合わせて警報を出す。** **vpxuser のようなサービスアカウントの対話的な SSH ログインを 禁止し、記録された時点で調査する。**
  • 境界機器のテンプレート・ウェブ公開ディレクトリについて、 ファイルが「増えたこと」を見る。名前の規則で探すと次に効かない。
    **本件のウェブシェルは zz で始まり .tpl で終わる名で、 ポータルがログイン画面を組み立てる正規のテンプレート群に 混ざって置かれた**（出典1・4）〈重要〉。 **アップロードされたファイルは /tmp/.up.tpl に保存され、 challenge_render.tpl の名で複写された**（出典1）—— **正規のファイル名に見える形である。** **名前で探す方式は、次の攻撃で名前が変わると効かない**（本記録の評価）。
    取るべき行動 **境界機器のテンプレート・ウェブ公開ディレクトリのファイル一覧を 定期に取得し、構成管理上の変更と突き合わせて差分を審査する。** **同様に /lib 配下の共有ライブラリの新規追加 （本件では /lib/libcpfwcommon.so）と、 起動の永続化ディレクトリ内のプロセス名の追加 （本件では slot_CPconfigdaemon）を差分の対象に含める。** **照合の基準は「既知のファイル一覧」であり、 既知の悪性ファイル名の一覧ではない。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ インターネットに面した Mobile Access ポータルを構成した Check Point Security Gateway を運用しており、 2026年10月23日提供の PHP2Shell 修正、 または11月の Jumbo Hotfix を適用していない。
システム構成□ 境界機器（VPN・リバースプロキシ・Mobile Access 型ポータル）から 仮想化基盤の管理面（vCenter・ESXi）へ、SSH または管理プロトコルで 到達できる経路がある。
認証・認可□ vpxuser のような仮想化基盤のサービスアカウントで、 境界機器や一般の管理端末から対話的に SSH ログインできる状態にある。
運用・監視□ 境界機器のログ（コマンド実行・プロセスの異常終了・通信ログ）が 機器の中にのみ残り、外部のログ基盤へ転送されていない。
運用・監視□ 仮想化基盤のバックアップが、仮想化基盤の管理権限から到達できる場所 （ESXi の datastore を含む）に置かれている、 または仮想化基盤と同じ認証情報で操作できる。
体制・契約□ 脆弱性の適用順序を CVSS の値だけで決めており、 「外から踏める脆弱性」と「同じ機器上のローカル権限昇格」が 同時に未修正かどうかを判定していない。
