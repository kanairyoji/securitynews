INC-2026-1064ESXi 4台が10日で破壊される

Kaspersky の緊急対応チーム（GERT）が2026年11月13日、仮想化基盤が10日間で 破壊された事案を公表した——ESXi 4台・そこで動く全仮想マシン・vCenter Server Appliance 2台・接続された全バックアップ基盤が失われ、身代金要求は BlackNevas を 名乗った。**仮想化層の脆弱性は1つも悪用されていない**——ESXi に対する操作は すべて正規の VMware 管理インターフェース経由で実行された

初報: 2026年11月13日（Kaspersky（Securelist）の調査報告） 最終更新: 2026年11月14日

2026年11月13日、Kaspersky の Global Emergency Response Team（GERT）が、ある組織の仮想化環境が10日間で破壊された事案の調査結果を公表した（出典1）。

失われた範囲は、仮想化基盤のほぼ全体である（出典1）〈重要〉—— ESXi ホスト4台、そこで動いていたすべての仮想マシン、vCenter Server Appliance 2台、および接続されていたすべてのバックアップ基盤。 身代金要求の書き置きは、攻撃者を BlackNevas と名乗っていた（出典1）——2024年11月に初めて観測された群である。

この事案の核心は、何が使われなかったかにある（出典1）〈重要〉。Kaspersky は明示している—— 「仮想化層の脆弱性は悪用されていない。ゲストからホストへの脱出も、ハイパーバイザのメモリ破壊も無い。ESXi に対して取られたすべての行動は、正規の VMware 管理インターフェースを通じて実行された」（原文英語を訳出）。

到達経路は認証情報である（出典1）。vCenter Server Appliance へは、境界内の仮想化基盤以外のシステムから得られた認証情報で到達した。 さらにバックアップ基盤で管理者権限の実行を得たあと、そこに保存されていた認証情報を取り出している（出典1）〈重要〉—— バックアップが認証情報の橋渡しになった。

管理面での居座りの作り方が具体的である（出典1）〈重要〉。災害復旧用の VCSA に root で SSH ログインし、その約43秒後にシェルスクリプト経由で MeshAgent を展開した（SSH セッションの長さは2分26秒）。 約4時間後に MeshAgent 経由で戻り、Ligolo-ng の逆方向トンネルをvmware-vdma.service という名の systemd サービスとして設置した—— VMware のサービスを装い、Restart=always を設定し、C2 のドメインは cloudflare.com に似せた名前だった。

ESXi への SSH は、vCenter の Host Profiles で有効化された（出典1）〈重要〉—— 設定の投入が T+10分18秒、サービスが RUNNING に達したのが T+10分51秒。 その後の ESXi ホストへの直接 SSH は、vCenter の IP から来ている。 つまり踏み台は vCenter であり、ホストへの接続は「管理元から来た正当な接続」の形を取った（本記録の整理）。

起爆は準備されていた（出典1）。暗号化・破壊を行う実行体 esx64 は、Bitvise の FlowSsh ライブラリに由来するクライアント識別子を使って SFTP で持ち込まれた。 攻撃者は chmod +x を実行し、約16秒の /selftest を走らせている—— これは起爆の約3時間前である〈重要〉。起爆のコマンドは./tmp/esx64 /p /vmfs/ /depth 5 /wipe /allsys /detach /-showvolumes で、/detach により SSH セッションの終了後もプロセスが継続した（出典1）。

結果は速い（出典1）〈重要〉—— 災害復旧用ホストでは、23秒以内にすべての仮想マシンが停止し、vmksummary.log の稼働中仮想マシン数はゼロになった。 仮想ディスクファイルは先頭の約2KB が上書きされている—— 初期のブート構造は損なわれるが、GPT のバックアップヘッダが残っていれば復旧の余地はある（出典1）。

順序が重要である（出典1）〈重要〉—— ESXi の起爆より前に、バックアップサービスが停止され、復旧基盤が暗号化され、管理アクセスが妨害されていた。 さらにバックアップのセキュリティ制御は、主たる攻撃の数日前に無効化されていた。 つまり「壊す」より前に「戻せなくする」が終わっていた（本記録の読み）。

被害組織は公表されていない（出典1）〈未確定2〉—— Kaspersky の緊急対応の事案としての報告であり、組織名・業種・国・失われた仮想マシン数は示されていない。

**本事案の特徴は、脆弱性を使っていないことである**（出典1）〈重要〉。 **Kaspersky の明示**—— **「仮想化層の脆弱性は悪用されていない。 ゲストからホストへの脱出も、ハイパーバイザのメモリ破壊も無い。 ESXi に対して取られたすべての行動は、 正規の VMware 管理インターフェースを通じて実行された」（原文英語を訳出）。** **段階は、認証情報による管理面への到達 → VCSA での永続化 → vCenter の Host Profiles による ESXi の SSH 有効化 → SFTP での実行体の持ち込みと動作確認 → バックアップと復旧基盤の潰し → ESXi の起爆、である**（出典1）。 **本記録が構造上の中心と見るのは、順序である**（本記録の評価）〈重要〉—— **破壊より前に、戻せなくすることが終わっていた。** **バックアップのセキュリティ制御は主たる攻撃の数日前に無効化され、 ESXi の起爆より前にバックアップサービスが停止し、 復旧基盤が暗号化され、管理アクセスが妨害されている**（出典1）。 **初期侵入の経路は特定されていない**（出典1）〈未確定1〉。

  2. 2. 永続化[1]
    **災害復旧を担う VCSA に root で SSH ログインし、 約43秒後にシェルスクリプト経由で MeshAgent を展開した** （出典1）〈重要〉—— **この SSH セッションの長さは2分26秒である。** **約4時間後に MeshAgent 経由で戻り、 Ligolo-ng の逆方向トンネルを vmware-vdma.service という名の systemd サービスとして設置した**（出典1）—— **VMware のサービスを装い、Restart=always を設定し、 C2 のドメインは cloudflare.com に似せた名前だった。**
  3. 3. 権限昇格[1]
    **vCenter の Host Profiles を用いて、 ESXi ホストの TSM-SSH を有効化した**（出典1）〈重要〉。 **設定の投入が T+10分18秒、 サービスが RUNNING に達したのが T+10分51秒である**（出典1）—— **差は33秒（本記録の算定）。** **その後の ESXi ホストへの直接 SSH は vCenter の IP から 来ている**（出典1）—— **発信元としては「管理元からの正当な接続」に見える**（本記録の整理）。 **これは脆弱性ではなく、管理機能の正規の利用である**（出典1）〈重要〉。
  4. 4. 実行[1]
    **実行体 esx64 が、Bitvise の FlowSsh ライブラリに由来する クライアント識別子を使って SFTP で持ち込まれた**（出典1）〈重要〉。 **攻撃者は chmod +x を実行し、約16秒の /selftest を走らせた** （出典1）—— **これは起爆の約3時間前である**〈重要〉。

    **順序が2段ある**（出典1）〈重要〉。 **第1段はバックアップと復旧の潰しである**—— **バックアップのセキュリティ制御が主たる攻撃の数日前に 無効化され、ESXi の起爆より前に バックアップサービスが停止され、復旧基盤が暗号化され、 管理アクセスが妨害された。** **第2段が ESXi の起爆である**—— **`./tmp/esx64 /p /vmfs/ /depth 5 /wipe /allsys /detach /-showvolumes` が実行され、/detach により SSH セッションの終了後もプロセスが継続した。** **災害復旧用ホストでは23秒以内にすべての仮想マシンが停止し、 vmksummary.log の稼働中仮想マシン数はゼロになった**（出典1）。 **仮想ディスクファイルは先頭の約2KB が上書きされた**—— **初期のブート構造は損なわれるが、 GPT のバックアップヘッダが残っていれば復旧の余地はある**（出典1）。

時間の余裕は3時間あった。起爆は23秒で終わった評価・解釈

本報告の価値は、秒単位の時刻である（本記録の評価）〈重要〉。

防御側が使えるのは「どこに時間があったか」という情報である。

実行体の /selftest → 起爆 約3時間 ある

読み取れることは2つある（本記録の評価）。

第1に、個々の操作は速すぎて、警報から判断して行動する運用では間に合わない〈重要〉。43秒・33秒・23秒という時間尺は、人が画面を見て判断する時間ではない。

第2に、例外が1つある〈重要〉—— 実行体の設置から起爆までの約3時間。

ここで起きたことは具体的である（出典1）—— esx64 が SFTP で持ち込まれ（Bitvise の FlowSsh ライブラリに由来するクライアント識別子）、chmod +x が実行され、/selftest が約16秒動作した。

本記録はここを、本事案で最も惜しい見落としと評価する（本記録の判断）〈重要〉。

そして最も効く予防策もここにある—— execInstalledOnly を有効に保つことである（出典1。Kaspersky の推奨）。これは持ち込まれた実行ファイル全般に効き、実行体の個別の知識を要しない（本記録の評価）。

Kaspersky は検知の推奨として「execInstalledOnly の弱化」と「/tmp に置かれた実行ファイル」の両方を挙げている（出典1）。

ゲストの EDR からは見えない層で起きている評価・解釈

これが「ハイパーバイザ層」という表題の意味である（出典1）。

Kaspersky の整理は3段である（出典1。原文英語を訳出）〈重要〉。

第1に、ESXi には市販のセキュリティ製品を入れられない。 Broadcom は、汎用 OS 向けに設計された市販のセキュリティ製品は回避策なしには ESXi 上で動作せず、ESXi および VCSA への第三者エージェント・ウイルス対策の直接の導入はサポートされないとしている。

第2に、ゲスト内の EDR は上の層を観測できない。 「ESXi 側のプロセスが仮想マシンのディスク（VMDK）やデータストアのファイルを変更した場合、ゲスト内の EDR エージェントはその操作を行っているハイパーバイザのプロセスを直接観測も帰属もできない。」 ゲストのテレメトリに残るのは結果だけである—— I/O の失敗や突然の停止。

第3に、仮想化は制御点を減らし、1点の侵害の影響を広げる。 非仮想化環境では1つのゲストの侵害は通常1つの OS に影響するが、管理面の侵害は多数のハイパーバイザへのアクセスを与え、データストアへの直接の影響は多数のゲストを一度に利用不能にしうる。

帰結は、監視を置く場所である（本記録の評価）〈重要〉—— ホスト内蔵の記録と管理面のテレメトリ、および ESXi ホストの外からのテレメトリ収集に依存することになる。

そしてここに制約がもう1つある（出典1）〈重要〉—— 「ESXi のログはラムディスク上にあり再起動で消えるため、遠隔 syslog または永続的なスクラッチ領域が必要である。」

つまり破壊の後に機器を再起動すれば、経路の再構成の材料そのものが失われる（本記録の読み）。

Kaspersky が初動の推奨に「再起動の前に ESXi と VCSA のログを収集せよ」を置いているのはこのためである（出典1）—— これは、サービスを早く戻したい事業側の要求と正面から衝突する指示である（本記録の注意）。

バックアップは守る対象であり、同時に経路だった原因・手口

Kaspersky は、仮想化基盤へ至る4つの経路を整理している（出典1）—— 脆弱性の悪用、Windows 環境からの認証情報の再利用、Active Directory 連携の悪用、そして「認証情報の橋としてのバックアップ基盤」。

本事案に該当したのは、後ろ2つのうち2つである（出典1）〈重要〉。

第1に、境界内の仮想化基盤以外のシステムから得られた認証情報で VCSA へ到達した。

第2に、バックアップ基盤で管理者権限の実行を得たあと、そこに保存されていた認証情報を取り出した。

2つ目が本節の論点である（本記録の整理）〈重要〉。

バックアップ基盤は、構造上2つの性質を併せ持つ。

  • 守る対象 —— 破壊された場合に復旧できなくなる
  • 認証情報の集積場所 —— 守る対象へ到達するための鍵を保持する

後者が攻撃者に先に使われた（出典1）。

そしてバックアップは2回潰されている（出典1）—— セキュリティ制御の無効化（主たる攻撃の数日前）と、サービスの停止・復旧基盤の暗号化（ESXi の起爆より前）。

Kaspersky の推奨はこうである（出典1。原文英語を訳出）〈重要〉—— 「バックアップを独立したセキュリティ境界として設計し、独立した認証情報を用いよ。」

本記録はこれに1つ足す（本記録の提案）〈重要〉—— バックアップ側に他系統の管理者認証情報を置かないこと。 「独立した認証情報を用いる」は、バックアップへのアクセスの話である。 本事案で起きたのは逆方向で、バックアップの中に他システムの鍵が入っていた。

なお Kaspersky は設計上の教訓をこう書いている（出典1）〈重要〉—— 「ドメインの侵害が、攻撃者に自動的にハイパーバイザの管理権限を与えるべきではない。」

書き置きが BlackNevas を名乗った。それが帰属の根拠である帰属

Kaspersky の記述はこうである（出典1。原文英語を訳出）—— 「身代金要求の書き置きが、攻撃者を BlackNevas グループと特定した。2024年11月に初めて観測された群である。」

根拠は書き置きの自称である（本記録の整理）〈重要〉—— つまり攻撃者側の主張である。

Kaspersky は系統の比較も行っている（出典1）—— SentinelOne の調査にもとづき BlackNevas を Trigona の派生と説明し、コマンドラインの様式が Trigona に似ていると記している。

そのうえで留保を付けている（出典1。原文英語を訳出）〈重要〉—— 「この比較は、バイナリのハッシュ一致に代わるものではない。」

道具の系統から攻撃者を一意に定められない理由も報告が説明している（出典1）〈重要〉。

2021年9月に Babuk ランサムウェアのソースコードがESXi 版を含めて流出した。 これにより、比較的技術力の低い犯罪者にもESXi 向けランサムウェアが手に入るようになった。 少なくとも10の後続のランサムウェア系統がこの流出コードを利用しており、ESXi 対応のロッカーを自前で開発する専門性を持たない集団も含まれる（出典1）。流出した LockBit の Windows 版とBabuk 由来の ESXi ロッカーを併用する運用者も複数観測されている（出典1）。

    **本事案では、バックアップ基盤で管理者権限の実行を得た攻撃者が、 そこに保存されていた認証情報を取り出している**（出典1）〈重要〉—— **バックアップが認証情報の橋渡しになった。** **そしてバックアップは2回潰されている**（出典1）—— **セキュリティ制御の無効化（主たる攻撃の数日前）と、 サービスの停止・復旧基盤の暗号化（ESXi の起爆より前）。** **Kaspersky は「バックアップを独立したセキュリティ境界として設計し、 独立した認証情報を用いよ」としている**（出典1）—— **本記録はこれに「バックアップ側に他系統の鍵を置かない」を 足す**（本記録の提案）〈重要〉。 **前者はバックアップへのアクセスの話だが、 本事案で起きたのは逆方向である。**
    取るべき行動 **バックアップ基盤に保存されている認証情報を棚卸しし、 仮想化基盤・ドメイン・業務システムの管理者認証情報が 含まれていないかを確認する。** **含まれる場合は、取り出しに別の要素を要する形に変える （保管庫への分離・期限付きの払い出し）。** **併せて、バックアップを独立したセキュリティ境界として設計し （別のネットワーク・別の認証情報）、 バックアップのセキュリティ制御の無効化そのものを 警報条件にする**〈重要〉—— **本事案ではこれが主たる攻撃の数日前に起きており、 最も早く鳴りえた警報である**（本記録の提案）。
  • 復旧計画を「バックアップから戻す」前提で作っている場合、 バックアップも同時に失われる想定の手順を別に用意する。
    **本事案では、接続されていたすべてのバックアップ基盤が 失われている**（出典1）〈重要〉—— **ESXi ホスト4台・全仮想マシン・vCenter Server Appliance 2台と 併せて。** **順序も重要である**（出典1）—— **ESXi の起爆より前に、バックアップサービスが停止され、 復旧基盤が暗号化され、管理アクセスが妨害されている。** **つまり被害組織が「払うか払わないか」を考える時点で、 戻す手段は既に無い**（本記録の読み）〈重要〉。 **本事案で実際に復旧できたかは公表されていない**〈未確定4〉—— **報告は「仮想ディスクファイルの先頭およそ2KB が上書きされ、 GPT のバックアップヘッダが残っていれば復旧の余地はある」と 述べるにとどまる**（出典1）。
    取るべき行動 **事業継続計画に「仮想化基盤とバックアップが同時に失われた場合」の 章を追加し、復旧の所要時間を再見積もりする。** **見積もりの前提として、①最後に仮想化の信頼境界の外に出した 複製がいつのものか、②それから業務を再構築するのに要する期間、 の2点を具体的な日数で出す。** **その数字を事業部門と共有し、許容できない場合は 仮想化の信頼境界の外への複製の頻度を上げる決裁を取る。** **あわせて vCenter が2台とも失われた場合の ESXi への接続手順を文書化する**（本事案では2台とも失われている）。
  • 初動で「再起動の前にログを収集する」という制約を、 事業側と事前に合意しておく。
    **Kaspersky の初動の推奨には明確な順序がある**（出典1）〈重要〉—— **vCenter へのアクセスを隔離し、 vCenter の Events・Tasks を書き出し、 **いかなる再起動よりも前に** ESXi と VCSA のログを収集し、 疑わしいバイナリとユニットを削除する前に保全する。** **理由は技術的である**（出典1）—— **「ESXi のログはラムディスク上にあり再起動で消えるため、 遠隔 syslog または永続的なスクラッチ領域が必要である。」** **この指示は、サービスを早く戻したい事業側の要求と 正面から衝突する**（本記録の注意）〈重要〉—— **侵害の最中にこの交渉をすると、 復旧を優先して経路が永久に分からなくなる。**
    取るべき行動 **インシデント対応手順に「再起動の前に収集するログ」の 一覧を具体的に書く （auth.log・shell.log・vpxa.log・vobd.log・vCenter の Events と Tasks・ VCSA の systemd ユニットとファイルシステムを第1優先とする）。** **この順序を事業部門と事前に合意し、 収集に要する時間を復旧目標時間の中に織り込む。** **根本的には、遠隔 syslog を平時から構成して この制約自体を消す**〈重要〉—— **副作用が小さく、本記録はこれを最優先の対策と評価する。**
セキュリティ技術者への示唆
  • ESXi の execInstalledOnly を有効に保ち、設定の弱化そのものを 警報条件にする。本事案で最も効く予防策である。
    **本事案の実行体 esx64 は /tmp 配下に置かれて実行された** （出典1。起爆コマンドの path から）〈重要〉。 **Kaspersky は堅牢化の項で 「execInstalledOnly が有効なままであることを確かにせよ」とし、 検知の項で「execInstalledOnly の弱化」を警報条件に挙げている** （出典1）。 **本記録がこれを最も効く予防策と評価する理由は、 持ち込まれた実行ファイル全般に効き、 実行体の個別の知識を要しないことである**（本記録の判断）—— **Babuk の流出コードに由来する系統が少なくとも10あり**（出典1）**、 個別のハッシュを追うやり方は追いつかない。**
    取るべき行動 **全 ESXi ホストの execInstalledOnly の設定値を棚卸しし、 無効になっているホストを有効化する。** **設定値の変更（弱化）を警報条件として実装する （Host Profiles 経由の変更も対象に含める）。** **正規の保守で持ち込む診断用の実行ファイルがある場合は、 手順を事前に見直す（副作用として動かなくなる）。** **併せて /tmp 配下への実行ファイルの設置と chmod +x の実行を警報条件にする**—— **本事案ではここから起爆まで約3時間あった**（出典1）〈重要〉。
  • Host Profiles による TSM-SSH の有効化を、 「設定が投入された時点」で検知する。開いてから気づいても遅い。
    **本事案では、設定の投入が T+10分18秒、 サービスが RUNNING に達したのが T+10分51秒である**（出典1）〈重要〉—— **差は33秒（本記録の算定）。** **つまり「SSH が開いた」ことを検知条件にすると、 気づいた時点で既に開いている**（本記録の読み）。 **さらにその後の ESXi への直接 SSH は vCenter の IP から 来ている**（出典1）—— **発信元としては「管理元からの正当な接続」に見えるため 疑われにくい**（本記録の評価）。 **Kaspersky は検知の推奨として 「承認された作業窓の外で TSM-SSH を有効化する Host Profiles の変更」と「vCenter からの直接の SSH」の 両方を挙げている**（出典1）。
    取るべき行動 **vCenter の Events・Tasks と hostprofiletrace.log を取り込み、 TSM-SSH を有効化する Host Profiles の変更を 承認された作業窓と突き合わせて警報を出す。** **警報を「設定の投入」に置く（サービスの起動ではなく）。** **併せて、ESXi ホストへの SSH 接続のうち vCenter の IP を発信元とするものを警報条件にする**—— **vCenter が ESXi へ対話的に SSH する必要は 通常の運用では無い**（本記録の整理）。 **前提として、承認された作業窓を管理する運用が要る （管理していないと誤報が多くなる）。**
  • ESXi と VCSA のログを遠隔 syslog で外へ出す。 ESXi のログはラムディスク上にあり再起動で消える。
    **Kaspersky の明示である**（出典1。原文英語を訳出）〈重要〉—— **「ESXi はラムディスク上にログを書くため再起動で消える。 遠隔 syslog または永続的なスクラッチ領域が必要である。」** **加えて ESXi には市販のセキュリティ製品を導入できない** （出典1。Broadcom の見解）—— **防御側は内蔵の記録と管理面のテレメトリ、 およびホストの外からのテレメトリ収集に依存することになる。** **本記録はこれを、本事案で最も移植しやすい技術的要点と評価する** （本記録の判断）—— **副作用が小さく、効果が確実である。**
    取るべき行動 **全 ESXi ホストと VCSA について遠隔 syslog を構成し、 仮想化の信頼領域の外のログ基盤へ転送する** （出典1 は「仮想化の信頼領域の外の基盤へログを転送せよ」としている）。 **転送するログに、第1優先（auth.log・shell.log・vpxa.log・vobd.log）と 第2優先（vmkernel.log・vmkwarning.log・vmksummary.log・ esxupdate.log・仮想マシンごとの vmware.log・hostprofiletrace.log）を 含める。** **vCenter の Events・Tasks も定期に書き出す。** **転送が途切れたこと自体に警報を出す （受信の連続性を監視する）。**
  • VCSA の systemd ユニットの一覧を定期に取得し、差分を審査する。 名前では見分けられない。
    **本事案で設置された Ligolo-ng の逆方向トンネルは、 vmware-vdma.service という名の systemd サービスだった** （出典1）〈重要〉—— **VMware のサービスを装い、Restart=always が設定され、 C2 のドメインは cloudflare.com に似せた名前だった。** **つまりサービス名とドメイン名の両方で正当なものを装っている** （本記録の整理）—— **名前の規則では見分けられない。** **Kaspersky が第1優先のログ源に 「VCSA の systemd ユニットおよびファイルシステム」を 挙げているのは、ここが再構成の鍵だったためである** （出典1。本記録の読み）。
    取るべき行動 **VCSA の systemd ユニットの一覧（および有効化の状態・ Restart 設定・実行ファイルの path）を定期に取得し、 構成管理上の既知の一覧との差分を審査する。** **照合の基準を「既知のユニットの一覧」とする （既知の悪性な名前の一覧ではない）。** **併せて VCSA からの外向き通信を 業務上必要な宛先に限定する（許可リスト方式）**—— **C2 ドメインが正当なサービスに似せた名前を使うため、 拒否リスト方式では通る**（本記録の評価）。 **VCSA への root での SSH ログインも警報条件にする。**
  • ゲスト内の EDR では仮想化層の操作が見えないことを前提に、 監視の設計を管理面のテレメトリへ移す。
    **Kaspersky の整理である**（出典1。原文英語を訳出）〈重要〉—— **「ESXi 側のプロセスが仮想マシンのディスク（VMDK）や データストアのファイルを変更した場合、 ゲスト内の EDR エージェントはその操作を行っている ハイパーバイザのプロセスを直接観測も帰属もできない。」** **ゲストのテレメトリに残るのは結果だけである**—— **I/O の失敗や突然の停止。** **本事案の時系列の再構成が ホスト内蔵のログと管理面のテレメトリを中心に行われたのは このためである**（出典1）。 **さらに ESXi・VCSA への第三者エージェントの直接の導入は サポートされない**（出典1。Broadcom の見解）—— **エージェントで補えない。**
    取るべき行動 **監視の設計書に「仮想化層の操作はゲストの EDR では見えない」ことを 明記し、代替の観測点を列挙する （vCenter の Events・Tasks、ESXi のホスト内蔵ログ、 エージェントレスの連携、ホスト外からのネットワーク観測）。** **ゲストの大量の I/O 失敗・突然の停止を 「ハイパーバイザ層の事象の可能性」として扱う相関規則を作る。** **仮想マシンの大量停止（稼働中仮想マシン数の急減）を 警報条件にする**（出典1 の推奨）—— **ただしこれは抑止ではなく把握を早める条件である** （本事案では23秒以内に全停止している）〈重要〉。
