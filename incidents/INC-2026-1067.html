INC-2026-1067Arra Ghouls が露白18組織侵害

2026年11月9日、Kaspersky が新興グループ Arra Ghouls（別名 Mimbrob）の 調査を公表した——**2026年4月初めに個人狙いの窃取型から組織攻撃へ切り替え、 ロシア・ベラルーシの18組織を侵害した。**正規の Chromium と Notepad++ を 踏み台にした DLL 読み込みで Go 製の Arra RAT を入れ、 そこから Havoc・Chisel・Rust 製キーロガーへ広げている

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）設計・実装上の不備
初報: 2026年11月9日（Kaspersky Securelist の公表） 最終更新: 2026年11月14日

2026年11月9日、Kaspersky が Arra Ghouls（別名 Mimbrob）の調査結果をSecurelist に公表した（出典1）。2026年11月12日、ロシアの Xakep が報じた（出典2）。

本件の中心は、攻撃対象の切り替えである（本記録の判断）〈重要〉—— このグループは当初、窃取型マルウェアと バンキング型トロイの木馬 で個人利用者を狙っていた。 それが2026年4月初めから、組織への攻撃に切り替わった（出典1・2）。Kaspersky が確認した被害は、ロシアとベラルーシの18組織である—— 通信・製造（医薬品を含む）・IT・卸売・金融（コンサルティング）の各分野にまたがる（出典1・2）。

手口は、道具を自分で全部作るのではなく、正規の道具と公開の道具を組み合わせる形である（出典1。本記録の整理）〈重要〉。①フィッシングメールの RAR 書庫に、正規の Chromium 実行ファイルと悪性の DLL を同居させる。②利用者が Chromium を起動すると DLL が読み込まれ、ドロッパーが動く。③schtasks.exe で予定タスクを作って居座る（タスク名は「YandexUpdate」「CDBurnerXP Update」「DiskManager」）。④主な負荷は Go で書かれたモジュール型の Arra RAT。⑤そこから Havoc の エージェント・RootRat・Metasploit のリバースシェル・Chisel・Rust 製のキーロガーへ広げる（出典1・2）。

Arra RAT の成長が速い（出典1・2）〈重要〉—— 2026年4月初めに見つかった最初の版は、C2 との基本的な通信とわずかな命令しか持たなかった。 5〜6月には、ファイルの授受・データの窃取・TCP トンネルの構築ができるようになった。 Kaspersky は Arra RAT を「インフラへの入口にすぎない」と記し、主な操作は Havoc で行われたとしている（出典1。原文ロシア語を訳出）。

日本の組織への直接の関係は薄い（本記録の評価）〈重要〉—— ドロッパーはロシア・ウクライナ・ベラルーシ・カザフスタン・その他の CIS 諸国とモルドバのロケール識別子を確認しており、Kaspersky は標的が CIS 諸国とモルドバであると結論している（出典1）。本記録が日本の読者に向けて取り出すのは、相手ではなく手口の形である—— 正規の実行ファイルを踏み台にした DLL 読み込みと、更新処理を装った予定タスクは、ロケールを問わず成立する。

CISO・経営層への示唆
  • 「正規ソフトを踏み台にする」手口を前提に、検知の軸を 固有のファイルから「起動元の場所」へ移す。
    **本件で実行に使われたのは、正規の署名つき Chromium と Notepad++ 8.5.4 である**（出典1・2）〈重要〉—— **悪性なのは同じディレクトリに置かれた DLL のほうで、 起動されるファイル自体は正規のものである。** **Kaspersky の検知規則が「疑わしいフォルダからの実行」を 見ていることが、この手口に効く軸を示している**（出典1）。 **固有のハッシュ・ファイル名を探す検知では、 踏み台を別の正規ソフトに替えられるだけで外れる**（本記録の評価）。
    取るべき行動 **EDR・アプリケーション制御の方針を見直し、 「利用者の書き込み可能な場所（ダウンロード・一時・%APPDATA%）からの 実行ファイルの起動」を許可制にする対象範囲を決める。** **まず特権端末・管理端末から適用し、適用範囲と例外を記録に残す。** **例外（業務上そこから起動する正規のソフト）を洗い出す工数を 先に見積もる——この洗い出しが済まないと展開できない。**
  • 予定タスクの棚卸しを、名前ではなく「実行元の場所」と「実行間隔」で行う。
    **本件のタスク名は「YandexUpdate」「CDBurnerXP Update」「DiskManager」で、 いずれも正規の更新処理を装っている**（出典1）〈重要〉。 **名前で見分けることはできない。** **一方で、実行元が `%APPDATA%\Yandex Soft` 配下であることと、 2つのタスクが1分ごとに動くことは、 正規の更新処理としては説明しにくい**（出典1。本記録の評価）—— **正規の更新は通常、分単位では走らない。**
    取るべき行動 **全端末の予定タスクを収集し、 ①実行元が利用者の書き込み可能な場所にあるもの、 ②実行間隔が1時間未満のもの、の2条件で抽出する運用を作る。** **抽出結果を「既知の正規タスク」の一覧と突き合わせ、 差分だけを人が見る形にする。** **タスク名に現れるソフトが実際に端末に導入されているかも確認する。**
  • 取引先・公的機関を装うメールの件名の種類（裁判・検査）を、 訓練と運用の両方に織り込む。
    **本件の件名は「Судебное разбирательство」（裁判手続）や 「Poverka2026」（検査2026）である**（出典1・2）〈重要〉—— **担当者が無視できない種類に寄せてある。** **差出人は実在組織に似せた新規ドメインで、 侵害されたメールサーバーも使われた**（出典1）—— **つまり差出人の見た目では判定できない場合がある**〈未確定2〉。 **18組織で侵入が成立している**（出典1）。
    取るべき行動 **訓練メールの題材に「裁判・監査・検査・行政からの照会」を加える （請求書・配送通知だけに偏らせない）。** **法務・監査・総務の窓口に届く外部メールについて、 添付を開く前に発信元へ別経路で確認する手順を決める。** **確認の連絡先（電話番号）を、メール本文ではなく 自社が持つ台帳から引く運用にする。**
  • 「新興グループ」を能力が低いと読まない——2か月で能力が変わる前提で 脅威の前提を置く。
    **Arra RAT は2026年4月初めの初版では基本的な通信とわずかな命令しか 持たなかったが、5〜6月には TCP トンネル・窃取・文字列暗号化を備えた** （出典1・2。期間の算出は本記録）〈重要〉。 **Kaspersky の結論は「新しい担い手がどれほど速く技術的な能力を高め、 大量のデータ窃取から組織への攻撃へ移れるかを示している」である** （出典2 が引用。原文ロシア語を訳出）。 **同時に、このグループは個人狙いから組織狙いへ標的を切り替えている**—— **窃取型の運用で得た基盤が組織攻撃に転用された形である**（本記録の読み）。
    取るべき行動 **脅威の一覧を「国家系か犯罪者か」ではなく 「自組織の統制のどこを通れるか」で並べ替える。** **新興グループの報告を受けたときに、 能力の現在値ではなく手口の形（本件なら DLL 読み込みと予定タスク）を 点検項目に落とす運用にする。**
セキュリティ技術者への示唆
  • 署名つき正規実行ファイルが、同じディレクトリの署名の無い DLL を 読み込む事象を検知の対象にする。
    **本件の実行はこの形そのものである**（出典1・2）〈重要〉—— **名前を変えた正規 Chromium が `browser_elf.dll` を読み込み、 Notepad++ 8.5.4 が `MSASN1.dll` を読み込む。** **Kaspersky は Notepad++ の事例について 「新しい版の Windows ではこの脆弱性は再現しない」と記している** （原文ロシア語を訳出）—— **Windows 11 では DLL がシステムディレクトリから読み込まれる。** **Chromium の事例に同じことが言えるかは記事から読み取れない**〈未確定5〉。
    取るべき行動 **Sysmon のイベント ID 7（イメージの読み込み）を収集し、 「署名つきの親プロセス」×「署名の無い DLL」× 「読み込み元が利用者の書き込み可能な場所」の3条件で抽出する。** **収集量が問題になる場合、対象を ブラウザ・エディタ・圧縮ソフトなど踏み台にされやすいものに絞る。** **端末の OS 版を棚卸しし、Windows 10 が残っている範囲を把握する。**
  • 外向きの非標準ポート（本件では 444・4444・6969・8080）の発信を 既定で止め、例外を台帳にする。
    **本件の C2 は、Havoc が 109.205.212.241 のポート 444 と 4444、 Metasploit のリバースシェルが 194.87.37[.]14:8080、 Arra RAT の初期版が 6969 を使う**（出典1）〈重要〉。 **通信は暗号化された TCP トンネルで行われるため、 中身からの検知は期待しにくい**（出典1。本記録の読み）—— **残る手がかりは宛先とポート、そして接続の継続時間である。**
    取るべき行動 **端末セグメントからの外向き通信を、 業務上必要なポート（443・80・DNS 等）に絞る。** **例外が必要な業務（開発・運用ツール）を台帳にし、 送信元を限定する。** **絞れない環境では、まず「長時間続く単一の外向き接続」を 抽出する検知を用意する（宛先の既知悪性リストに頼らない）。**
  • 予定タスクの作成（イベント ID 4698 等）を収集し、 実行元と間隔で警報を出す。
    **本件の永続化は `schtasks.exe` による予定タスクで、 実行元は `%APPDATA%\Yandex Soft` 配下、 間隔は2つが1分ごとである**（出典1）〈重要〉。 **Kaspersky の KEDR 規則にも「予定タスクの作成」と 「予定タスク経由の疑わしいフォルダからの実行」が挙がっている** （出典1）——**この段階は検知できる段階である。**
    取るべき行動 **予定タスクの作成イベントを収集しているか確認する （監査方針が無効だと記録されない）。** **実行元が `%APPDATA%`・`%TEMP%`・`%PUBLIC%` 配下のタスク作成を 即時の警報にする。** **既存タスクの定期の棚卸し（差分検出）を自動化する。**
  • クリップボードとキー入力が取られる前提で、 認証の方式と貼り付けの運用を見直す。
    **本件では Rust 製のキーロガーがキー入力とクリップボードの内容を 取っている**（出典1・2）〈重要〉—— **`/api/handshake` で登録し、`/api/poll` で命令を取り、 `/api/submit` で送る。** **窃取された認証情報がその後どう使われたかは公表されていない** 〈未確定1〉——**以下は本記録の評価である。** **パスワードと一時コードはどちらもキー入力かクリップボードを通る。**
    取るべき行動 **特権アカウント・管理コンソールへの認証を、 フィッシング耐性のある方式（FIDO2・証明書）に移す対象から決める。** **パスワード管理ソフトの利用を、 クリップボード経由の貼り付けから自動入力に切り替える。** **クリップボードの保持時間を短くする設定があれば有効にする。**
