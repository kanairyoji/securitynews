INC-2026-1069Teams 予約装いのデバイスコード詐取

2026年11月12日、Huntress が Microsoft Teams の会議予約を装った デバイスコード・フィッシングを公表した——**「予約番号（Booking Reference）」として 見せていたのはデバイスコードで、利用者はそれを Microsoft の本物の デバイスログインページに入れて攻撃者のサインインを承認した。** 仕上げに Calendly の実在する予約ページへ飛ばし、気づかせない

脅威・攻撃キャンペーン不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）人を介した誘導（ビッシング・BEC）認証情報の悪用（使い回し・推測可能・窃取）設定不備
初報: 2026年11月12日（Huntress の公表） 最終更新: 2026年11月14日

2026年11月12日、Huntress が、Microsoft Teams の会議予約の流れを装ったデバイスコード・フィッシングの事例を公表した（出典1）。Huntress の SOC が観測したのは2026年10月中旬で、被害者は建設業の企業の従業員である（出典1）。

攻撃の形はこうである（出典1）〈重要〉。①建設業の別企業を模した打ち間違いドメインから、その企業の実在する上級副社長を名乗る標的型メールが届く。②リンクは Microsoft の Safe Links に包まれ、Google の短縮リンク（share[.]google）を経て、打ち間違いドメインの誘導ページへ飛ぶ—— この3段の転送はすべてサーバー側で同時に起きる。 ③ページは Microsoft Teams の会議予約画面として表示され、利用者は日時と所要時間を選ぶ。④「続ける」を押した時点で、背後では Microsoft のデバイスコードサインインが開始され、コード（user_code）が発行される。⑤次の画面は「予約を確定してください」で、そこに「予約番号（Booking Reference）」として表示されるのがデバイスコードである。 ⑥「コピー」または「会議を確定」を押すとコードがクリップボードに入り、Microsoft の本物のデバイスログインページがポップアップで開く。⑦利用者がコードを入力すると、攻撃者の待機中のサインインが承認される。

仕上げが本件の性格を示している（本記録の評価）〈重要〉—— 成功すると、ページはポップアップを閉じ「確認が完了しました」と表示し、最上位のウィンドウを Calendly の実在する30分枠の予約ページへ転送する（出典1）。「本物の予約ページに着いた」という体験で終わるため、利用者に疑う理由が残らない。

従来のデバイスコード・フィッシングとの違いは、口実の作り込みである（出典1。本記録の整理）〈重要〉—— Huntress が過去に多く見た型は「合意書の確認」などの PDF を見せ、「確認コード」を Microsoft のデバイスログインに入れさせるものだった。 本件は、コードを日常の業務（会議予約）の一部に埋め込んでいる。

侵害されたアカウントには多要素認証が登録されておらず、使われた端末は準拠していない非管理端末だった（出典1）〈重要〉。デバイスコードの認証は住宅用回線のコールバックプロキシを経由しており、Huntress は記録上のアドレスがニューオーリンズの一般家庭のインターネットアドレスを指すとしている。

Huntress の SOC は速やかに検知し封じ込め、攻撃がそれ以上進むのを止めた（出典1）—— 検知から封じ込めまでの所要は示されていない〈未確定3〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件の攻撃は、認証そのものを破っていない**（出典1。本記録の整理）〈重要〉—— **破ったのは、利用者がコードの意味を判断する場面である。** **流れは、①実在役員を装う標的型メール、 ②3段のサーバー側転送（Safe Links → share.google → 打ち間違いドメイン）、 ③Teams 風の会議予約画面、 ④「続ける」で背後がデバイスコードのサインインを開始、 ⑤「予約番号」としてコードを提示し、クリップボードへコピー、 ⑥Microsoft の本物のデバイスログインページをポップアップで開く、 ⑦利用者の入力で攻撃者のサインインが承認される、 ⑧Authentication Broker 向けトークンを取得し、 住宅用プロキシ経由でセッションを再生、である**（出典1）。 **フィッシングキットは AES-256-GCM で暗号化して置かれ、 ブラウザ内で復号される**（出典1）—— **JavaScript を実行しない検査には、暗号化された塊にしか見えない。**

Huntress の整理はこうである（出典1。原文英語を訳出）—— 「利用者の側からは手順が日常的に見える。コードを入れ、求められれば多要素認証を済ませ、要求を承認する。しかしそうすることで、彼らは攻撃者のセッションを認可し、攻撃者が価値あるアクセストークンを得ることを許している。」

検査をすり抜けた理由は1つ——本文に書かれていたのが Google のリンクだった発覚の端緒

転送は3段で、すべてサーバー側で同時に起きた（出典1）〈重要〉。

  1. Microsoft の Safe Links（nam12.safelinks.protection.outlook[.]com）
  2. Google の短縮リンク（share[.]google/?q=UltJkMsVWI5V9GJM1）
  3. www.google[.]com/share[.]google?q=UltJkMsVWI5V9GJM1
  4. → 打ち間違いドメインの誘導ページ

Huntress の説明はこうである（出典1。原文英語を訳出）〈重要〉—— 「メール本文に、打ち間違いドメインではなく share.google のリンクが含まれていたため、メールセキュリティの URL 評価の検査を回避できた。」

つまり回避はこの1点に依存している（本記録の読み）。URL の評価は本文に書かれたドメインを見るため、転送を展開しなければ最終到達先を判定できない。

誘導ページ側にも検査対策が入っている（出典1）〈重要〉—— ページは小さな読み込み器にすぎず、本体のキットは AES-256-GCM の暗号文として置かれている（鍵と初期化ベクトルは同じページの隣）。 ブラウザが WebCrypto API で復号してページに書き込む。 Huntress は「JavaScript を実行しないメールスキャナやクローラにとって、誘導ページは暗号化された塊にすぎない」と記している（原文英語を訳出）。

したがって静的な検査は2か所で外れる（本記録の整理）—— ①本文のリンクのドメイン評価、②誘導ページの内容検査。 残る手がかりは、差出人ドメインが8日前に登録された新規ドメインであること（出典1）と、サインインの記録である（本記録の評価）。

多要素認証が無かったのは事実だが、あっても止まらない設計である評価・解釈

事実から確認する（出典1）〈重要〉—— ATT&CK の対応表（T1078.004）に「多要素認証が登録されていなかった侵害された Microsoft 365アカウントを、準拠していない非管理端末から使用した」と明記されている（原文英語を訳出）。

ここで「多要素認証を入れていれば防げた」と読むと間取りを誤る（本記録の評価）〈重要〉。

キットには、多要素認証が要求された場合の代替手順があらかじめ組み込まれている（出典1）—— Microsoft が AADSTS50076 または interaction_required を返すと、利用者には「セキュリティのため、アカウントを再度確認してください。新しい確認コードを準備しています」と表示される。 背後では POST /api/device/start を送って新しいデバイスコードのセッションを開始し、多要素認証の流れをやり直す。

デバイスコード認証では、多要素認証は利用者が「攻撃者のサインインを承認する」過程の一部として消費される（本記録の読み）〈重要〉—— 利用者は自分の端末で正規の多要素認証を済ませるが、それが通すのは攻撃者のセッションである。

Huntress の推奨が「フィッシング耐性のある多要素認証」である理由がここにある（出典1。本記録の読み）—— 一時コードや承認の押下では足りない。

根元で止める統制は1つしかない（本記録の判断）〈重要〉—— デバイスコード認証を条件付きアクセスで既定拒否にすること。 Huntress も「必要でないところでは制限または監視せよ」と条件を付けている（出典1）—— 入力手段の乏しい機器など正規の用途があるため、例外の棚卸しが先に要る。

住宅用プロキシは IP の評価で捕まらない——検知は「変化」で行う対策・注意喚起

Huntress の記述が、この問題を正面から書いている（出典1。原文英語を訳出）〈重要〉—— 「記録上のアドレスは、プロキシとして悪用されている以外に悪性の活動が結び付いていない、ニューオーリンズの一般家庭のインターネットアドレスを指す。」

したがって既知悪性 IP の一覧は役に立たない（本記録の評価）。

代わりに使える特徴が2つある（出典1。整理は本記録）〈重要〉。

①利用者エージェント。 python-requests と node が痕跡として挙げられている。 Huntress は「対話型と非対話型の両方のサインイン記録に現れる。プログラムからの利用者エージェントは、非対話型の記録にしか現れないことも多い」と注意を添えている（原文英語を訳出）—— 非対話型の記録も検査の対象に含める必要がある。

②同一セッション内での変化。 ATT&CK の T1550.004 の記述に「取得したセッションは攻撃者の基盤から再生された。同一のセッション ID のまま ASN と地域が変わった」とある（原文英語を訳出）〈重要〉—— これは静的な属性ではなく、セッションの中の変化である。

加えて Cmsi:Cmsi というデバイスコード認証の成功を示す印が記録に残る（出典1）—— デバイスコード認証を使わない運用なら、この印の出現そのものが警報になる（本記録の評価）。

    **本件では偽サイトの見分けが役に立たない**（出典1）〈重要〉—— **コードを入力するのは Microsoft の本物のページである。** **終わり方も本物の Calendly の予約ページへの転送で、 利用者に疑う理由が残らない**（出典1）。 **Huntress の結論はこうである**（原文英語を訳出）—— **「日常の作業が、誰かにコードをコピーさせ、入力させ、 承認させるとき、防御側は、その人が誰のセッションを 認可しているのかを正確に理解できるようにしなければならない。」**
    取るべき行動 **教育の内容を1文に絞る—— 「画面に出たコードを別のサイトに入力するよう求められたら、 それは誰かのサインインを承認する操作である」。** **求められたときの確認手順を決める—— 依頼元へ、メールの本文ではなく自社の台帳にある連絡先で確認する。** **コードを入力してしまった場合の連絡先を周知し、 申告者を責めない方針を明示する。**
  • なりすまされる側の備えを持つ——自社名に似たドメインの登録監視と、 取引先への注意喚起の経路。
    **本件では、なりすまされたのも建設業の実在企業とその上級副社長である** （出典1）〈重要〉—— **顔写真・氏名・ミドルネームの頭文字・肩書まで使われた。** **打ち間違いドメインは侵害の8日前に登録されている**（出典1）。 **Huntress は当該企業に偽ドメインの存在を通知したとしている** （出典1）——**つまり企業自身は気づいていなかった**（本記録の読み）。 **8日という短さを考えると、監視の頻度が週単位では間に合わない** （本記録の評価）。
    取るべき行動 **自社名・ブランド・主要役員名に似たドメインの新規登録を 日次で監視する手段を用意する（商用サービスまたは 証明書透明性ログの監視）。** **検出したときに取引先へ注意喚起する経路（宛先一覧・文面）を 先に作る。** **役員の顔写真・肩書を公開範囲とともに棚卸しする—— 公開をやめる判断ではなく、悪用されうる前提で監視する。**
  • 侵害が疑われたときの手順に、パスワード変更ではなく トークンとセッションの無効化を置く。
    **本件で奪われたのはパスワードではない**（出典1）〈重要〉—— **Microsoft Authentication Broker 向けのアクセストークンと セッションである。** **セッションは攻撃者の基盤から再生され、 同一のセッション ID のまま ASN と地域が変わった**（出典1）。 **パスワードを変えてもトークンは生き続ける**（本記録の評価）。 **Huntress は侵害確認後の確認項目として、 不正な多要素認証の方式・見覚えのない登録端末・ 許可されていないアプリの同意・疑わしいメールボックスの規則・ 疑わしい外向きメールを挙げている**（出典1）。
    取るべき行動 **アカウント侵害の手順書に、 ①リフレッシュトークン・セッションの無効化、 ②登録端末の確認と削除、③多要素認証の方式の確認、 ④アプリの同意の確認、⑤メールボックス規則の確認、 ⑥外向きメールの確認、の6項目を明記する。** **各項目の実施者と、実施にかかる時間を事前に測る。** **パスワード変更だけで完了とする運用になっていないか点検する。**
セキュリティ技術者への示唆
  • サインイン記録からデバイスコード認証の成功（`Cmsi:Cmsi`）を 抽出する検知を作る。
    **Huntress は `Cmsi:Cmsi` を 「本件で観測されたデバイスコード認証の成功を示す」痕跡として 挙げている**（出典1。原文英語を訳出）〈重要〉。 **本件は正規の流れを使うため、 悪性のドメイン・ファイルによる検知が効かない**（本記録の評価）—— **残るのは認証の記録である。**
    取るべき行動 **Entra ID のサインイン記録で、 デバイスコード認証（`Cmsi:Cmsi`／Microsoft Authentication Broker）の 成功を抽出する検索を用意する。** **デバイスコード認証を使わない運用なら、 出現そのものを警報にする。** **使う運用なら、例外の利用者・機器との差分を警報にする。**
  • 利用者エージェントの検査を、非対話型のサインイン記録にも広げる。
    **痕跡として `python-requests` と `node` が挙げられている** （出典1）〈重要〉。 **Huntress は「自動化された基盤を示す。 対話型と非対話型の両方のサインイン記録に現れる。 プログラムからの利用者エージェントは、 非対話型の記録にしか現れないことも多い」と注意を添えている** （原文英語を訳出）—— **対話型の記録だけを見ていると取りこぼす。**
    取るべき行動 **サインイン記録の検索対象に非対話型（NonInteractiveUserSignInLogs）を 含める。** **利用者エージェントが `python-requests`・`node`・ その他のプログラム的な値であるサインインを抽出する。** **正規の自動処理（監視・連携）の利用者エージェントを 先に台帳にして除外する——除外一覧が無いと警報が埋もれる。**
  • 同一セッション内での ASN・地域の変化を検知する （既知悪性 IP の一覧に頼らない）。
    **本件の認証は住宅用回線のコールバックプロキシを経由しており、 該当アドレスには「プロキシとして悪用されている以外に 悪性の活動が結び付いていない」**（出典1。原文英語を訳出）〈重要〉—— **IP の評価では捕まらない。** **一方、取得されたセッションは攻撃者の基盤から再生され、 同一のセッション ID のまま ASN と地域が変わった** （出典1。T1550.004）——**変化は記録に残る。**
    取るべき行動 **サインイン記録をセッション ID で束ね、 同一セッション内で ASN または国が変わった事象を抽出する。** **正規の変化（モバイル回線の切り替え・VPN）を 先に把握して閾値を決める。** **住宅用プロキシの判定を試みるより、変化の検知を優先する—— 住宅用アドレスは一覧化できない。**
  • メールの URL 検査を「本文のドメイン評価」から 「転送を展開した最終到達先の評価」に変える。
    **本件の回避は1点に依存している**（出典1）〈重要〉—— **「メール本文に、打ち間違いドメインではなく share.google のリンクが含まれていたため、 URL 評価の検査を回避できた」**（原文英語を訳出）。 **転送は3段で、すべてサーバー側で同時に起きる**（出典1）。 **誘導ページ側も AES-256-GCM で暗号化されており、 JavaScript を実行しない検査には暗号化された塊にしか見えない** （出典1）。
    取るべき行動 **メールセキュリティでリンクを展開して 最終到達先を評価する設定を確認する（既定で無効の製品がある）。** **短縮リンク・リンク共有サービス（share.google 等）を含むメールを 警告・隔離の対象にする。** **URL の検査を JavaScript を実行する形 （ブラウザでの隔離表示・サンドボックス）に寄せる対象を決める。**
  • 差出人ドメインの登録からの日数を判定に加える——本件は8日である。
    **ATT&CK の対応表に 「脅威アクターは侵害の8日前に悪性の打ち間違いドメインを 登録した」と明記されている**（出典1。原文英語を訳出）〈重要〉。 **8日という短さは、新規登録ドメインによる判定が 有効に働きうることを示す**（本記録の評価）。 **ただし本件の口実は「新規の取引の打診」であり、 正規の新規取引先も同じ判定に当たる**（本記録の評価）—— **隔離後の確認手順が無いと業務が止まる。**
    取るべき行動 **メールセキュリティで、差出人ドメインの登録からの日数 （30日未満等）を判定条件に加える。** **隔離ではなく「警告の付与」から始め、 誤検知の量を測ってから隔離に移す。** **隔離する場合、確認の担当者と目標時間（営業時間内に○時間）を 先に決める。**
