INC-2026-1073CyberStrikeAI が AWS 4口座を渡る

**2026年11月13日、Elastic Security Labs は、2026年9月30日から10月16日までの 16日間に、CyberStrikeAI を動かしていた1台のサーバ（43[.]240[.]29[.]11）が 盗まれた AWS の資格情報を使って4つのアカウント・8つの ID を渡り歩いた記録を 公表した**（出典1。本記録が内容を確認した）。 **CloudTrail に残った呼び出しは、どれも正規のロールが日常的に行うものだった** ——**ID の有効性確認（GetCallerIdentity）、Secrets Manager からの秘密情報の 読み出し（GetSecretValue）、EC2 の起動スクリプトの取得 （DescribeInstanceAttribute の userData）、SSM パラメータの復号付き読み出し、 遠隔コマンドの送信（SendCommand）**（出典1）。 **この期間に鳴った警報は78件で、すべて中または低の深刻度だった**（出典1）。 **機械の速度が現れたのは2026年9月30日である**—— **EC2 のインスタンスロール（記事中の別名 app-role）が、 56件の起動スクリプト取得要求を141ミリ秒で投げた （1件あたり約2.5ミリ秒）**（出典1）。 **2026年10月2日には、別のロールが暗号化された SSM パラメータを復号して読み、 その29秒後に SSM の SendCommand を発行した**（出典1）。 **送られたコマンドの内容と成否は監査ログに残っていない**（出典1）〈未確定1〉。 **そして14日間沈黙し、2026年10月16日に戻ってきて、 それまで現れていなかった4つめのアカウントの ID を含めて 資格情報の生存確認をした**（出典1）。 **Elastic はこの14日の空白を、141ミリ秒の集中よりも重いと書いた**—— **「その空白のほうが集中より害が大きかった。 固定された相関の窓は2週間を跨げないからである」** （出典1・原文英語。本記録が訳した）〈重要〉。 **帰属について Elastic は「道具の帰属とログに残った機械の速度を根拠に AI 支援（AI-assisted）と呼ぶ。LLM のエージェントが判断していたことは 証明できず、攻撃者がどのように資格情報を得たかも分からない」と 明記している**（出典1・原文英語。本記録が訳した）。 **本記録がこの事案で重いと見るのはここである**（本記録の評価）〈重要〉—— **78件の警報は鳴っていた。** **それが意味を持ったのは、送信元 IP で束ねたあとだけである**（出典1）。 **「検知できなかった事案」ではなく「相関させなかった事案」である。**

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は CloudTrail に残った呼び出しの並びである**（出典1。整理は本記録） 〈重要〉—— **特徴は、どの段階にも「悪性の道具」が現れないことである。** **使われたのは AWS の標準 API だけで、 GetCallerIdentity・GetSessionToken・GetSecretValue・ DescribeInstanceAttribute・GetParameter・SendCommand の6種である** （出典1）。 **Elastic の表現では「どれも正規のロールが毎日呼ぶものである。 その時点では CloudTrail の中に急を要するものは何も無かった」** （出典1・原文英語。本記録が訳した）。

  1. 1. 認証情報アクセス確認済[1]
    **盗まれた資格情報の生存確認。2026年9月30日の51分間に、 3つのアカウントの4つの IAM ユーザに対して GetCallerIdentity が 呼ばれた。うち3件は同一の秒に、3つの別アカウントで発生している。 1つのユーザについては GetSessionToken が2回呼ばれ、 一時的な資格情報を要求している**（出典1）。 **2026年10月1日と10月16日にも同じ確認が繰り返された**（出典1）。
    根拠: Elastic の検知規則「AWS STS GetCallerIdentity API Called for the First Time」11件（中）、「AWS STS GetSessionToken Usage」3件（低） （出典1）
  2. 2. 認証情報アクセス確認済[1]
    **秘密情報の収穫。2026年9月30日、EC2 のインスタンスロール （app-role）が Secrets Manager から秘密情報を読み出し （このロールによる初回）、約3時間18分後に EC2 の起動スクリプト（userData 属性）の取得を1件試し、 約6時間10分後に56件の取得要求を141ミリ秒で投げた**（出典1）。 **翌10月1日には app-role が追加の秘密情報を読み、 別のロール（nonprod-role）が本番以外の環境から 約3分の間を置いて2回、秘密情報を読み出した**（出典1）。
    根拠: 検知規則「AWS EC2 User Data Retrieval for EC2 Instance」58件（中）、 「First Time Seen AWS Secret Value Accessed in Secrets Manager」 4件（中）（出典1）
  3. 3. 実行確認済[1]
    **2026年10月2日、3つめのロール（container-role）が 暗号化された SSM の SecureString パラメータを 復号フラグ付きで読み出し、その29秒後に SSM の SendCommand を発行した**（出典1）〈重要〉—— **Elastic は「データの中で最も危険度が高い活動」と評した。** **送られたコマンドの内容と成否は監査ログに残っていない**〈未確定1〉。
    根拠: 検知規則「AWS Systems Manager SecureString Parameter Request with Decryption Flag」1件（中）、 「AWS SSM SendCommand Execution by Rare User」1件（低）（出典1）
  4. 4. 内部探索確認済[1]
    **2026年10月16日、14日の沈黙のあとに戻ってきて、 それまで現れていなかった4つめのアカウント（D）の ID で GetSessionToken を呼び、約1時間57分後と約3時間7分後に 別の2アカウント（C・B）で資格情報の生存確認をした**（出典1）。 **Elastic は「空白のあとも access が生きているかの確認と 一致する。意図的な冷却期間とも、 別の標的の作業から戻ってきたとも読める。 データはこれらを切り分けない」と記した** （出典1・原文英語。本記録が訳した）。
    根拠: 検知規則 GetSessionToken・GetCallerIdentity による3件の警報（出典1）

    トレードオフ: **遮断リストとして配るほうが受け手は速く動ける** （本記録の評価）—— **一方で、既に別の用途に転用されている可能性がある IP を 遮断すると誤遮断が起きる。** **Elastic は速さより誤りの回避を選んだ。**

78件の警報は鳴っていた——足りなかったのは束ねることだった評価・解釈出典 [1]

この事案は「検知できなかった事案」ではありません（本記録の評価） 〈重要〉。 16日間で78件の警報が出ています（出典1）。 6つの検知規則が、4つの段階すべてを覆っていました。 問題は、78件すべてが中または低の深刻度で、 Elastic の言葉では「送信元 IP で相関させてはじめて意味を持った」 ことです（出典1・原文英語。本記録が訳した）。

なぜ深刻度が上がらなかったのかは、呼び出しの一覧を見れば分かります （本記録の整理）。 使われたのは GetCallerIdentity・GetSessionToken・GetSecretValue・ DescribeInstanceAttribute・GetParameter・SendCommand の6種だけで、 どれも正規のロールが日常的に呼ぶものです（出典1）。 悪性の道具は1つも現れません。 1件ずつ見れば、どれも正常です。

ここから出てくる宿題は、検知規則を増やすことではありません （本記録の判断）。 「低深刻度の警報を、何を軸に束ねるか」を決めることです。 本件で効いた軸は送信元 IP でした（出典1）。 ただしこれは攻撃側が1台のサーバを使い続けたからで、 住宅用プロキシを経由されれば効きません。 より壊れにくい軸は、使われた資格情報 （アクセスキーID・ロールセッション名）です（本記録の評価）—— 本件では3つのロールセッション名が EC2 のインスタンスIDになっており、 これが「インスタンスプロファイルから持ち出された資格情報」という 判断の決め手にもなっています（出典1）。

14日の空白が、141ミリ秒の集中より重い——窓では跨げない評価・解釈出典 [1]

Elastic は記事の冒頭をこう書き始めています—— 「1台のサーバが56件の EC2 起動スクリプトを141ミリ秒で読んだ。 それから14日間沈黙し、戻ってきた。 その空白のほうが集中より害が大きかった。 固定された相関の窓は2週間を跨げないからである」 （出典1・原文英語。本記録が訳した）〈重要〉。

この指摘が実務的なのは、復帰時に起きたことを見ると分かります （本記録の評価）。 2026年10月16日に戻ってきたサーバは、 それまで現れていなかった4つめのアカウント（D）の ID で GetSessionToken を呼んでいます（出典1）。 つまり14日の空白を跨いで見落とすのは、 「過去の活動の再掲」ではなく「侵害範囲の拡大」です。

24時間や7日の窓で警報を束ねている運用では、 10月16日の3件は「新しい、単独の、低深刻度の警報」に見えます （本記録の整理）。 9月30日の65件とは結び付きません。 対策は、相関を「窓」で持つのをやめて「台帳」で持つことです （本記録の提案）—— 侵害指標（送信元 IP・アクセスキーID・ロールセッション名）を 登録し、少なくとも90日はその指標での検索を定期実行する。 併せて、警報の調査を終了するときに 「送信元 IP」「使われた資格情報」を終了記録に残し、 次に同じ値が出たら再開できる形にしておくことです。

送られたコマンドは分からない——SSM の実行ログを入れていなかった未確定事項出典 [1]

2026年10月2日の29秒間が、この記録の中で最も危険度が高い部分です （出典1。Elastic の評価）。 3つめのロールが暗号化された SSM パラメータを復号して読み、 その29秒後に SSM の SendCommand を発行しました（出典1）。

何が実行されたかは、分かりません〈未確定1〉〈重要〉。 Elastic は「監査ログには、コマンドが何だったか、 成功したかどうかが記録されていない。 記録されているのは、コマンドが送られたことである」と書いています （出典1・原文英語。本記録が訳した）。

これは AWS の監査ログの設計上の区別です（本記録の整理）。 SendCommand という API を呼んだ事実は CloudTrail に残りますが、 送信された文書の中身と実行結果は、 SSM の Run Command の出力保存（S3 または CloudWatch Logs）を 別途有効にしていないと残りません。 本件の環境では有効になっていなかったと読めます。

したがってこの事案の被害範囲は、永久に確定しません （本記録の判断）。 読者が自組織で確認すべきことは1つです—— SSM の Run Command の実行ログ保存が有効になっているか。 無効なら、同じことが起きたときに 「遠隔実行があったか」すら答えられません。

「AI の攻撃」と呼ぶ根拠は道具の帰属であって、判断の証明ではない帰属出典 [1] [2]

Elastic は帰属について、2つを分けて書いています（出典1）。

道具の帰属は「確定」です〈重要〉—— ①2026年9月29日の走査データが、送信元 IP のポート8080 に CyberStrikeAI の Web 画面と、CN が CyberStrikeAI の 自己署名証明書を記録している（最初の警報の1日前）。 ②同じ証明書を他の2台も出しており、3台が結び付く。 ③ポート8080 は同基盤の既定の画面用ポート。 ④香港のホスティングは、同基盤のサーバの多くが 中国・シンガポール・香港にあったという先行報告と一致する（出典1）。

一方で、LLM が判断していたことは証明されていません （出典1）〈未確定5〉。 Elastic の言葉では 「AI 支援（AI-assisted）と呼ぶのは、 道具の帰属とログに残った機械の速度を根拠にしてのことである。 LLM のエージェントが判断していたことは証明できず、 攻撃者がどのように資格情報を得たかも分からない」 （原文英語。本記録が訳した）。

本記録はこの区別をそのまま引き継ぎます（本記録の方針）。 141ミリ秒で56件、同一の秒に3アカウントで ID 確認、 29秒で復号から遠隔実行——これらは自動化の証拠です。 自動化は LLM の専売ではありません。 スクリプトでも同じ密度は出ます。 「AI の攻撃」という語を使うときに、 何が確定していて何が推定なのかを分けておかないと、 対策の設計を誤ります（本記録の評価）—— 本件で効く対策は、相関と権限と秘密情報の置き場であって、 「AI 対策」という別の何かではありません。

承認を求めない設計が既定になっている——基盤の側の性質背景・過去事例出典 [2]

CyberStrikeAI は、Elastic が同じ週に公表した比較分析で 5つのエージェント型攻撃基盤の1つとして扱われています（出典2）。 その記述によれば、CyberStrikeAI は 「承認モードを切った状態で出荷される（ships with approval mode off）」 完結した操作卓であり、自前の implant を作り、 C2 の待ち受けと Web シェルの管理機能を持ち、 Telegram・Slack・Discord・DingTalk といったチャット基盤に 接続する（出典2・原文英語。本記録が訳した）〈重要〉。

Elastic は5つの基盤について 「いずれもコードの上で権限（authorization）を強制していない。 3つはプロンプトでモデルに権限があると告げている。 既定で有効な標的制限は、政府と教育機関のドメインの 拒否リストだけである」と記しています （出典2・原文英語。本記録が訳した）。

本記録がこれを背景として置くのは、 本件の速度の説明になるからです（本記録の評価）。 56件を141ミリ秒で投げる動きは、 人が1件ずつ承認していれば起きません。 承認を求めない設計が既定であることが、 ログに残った密度の前提条件になっています。 なお同じ週に公表された ARTEX の FBI 勧告については 本DB の別記録で扱います（本記録の注記）。
