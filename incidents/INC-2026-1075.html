INC-2026-1075AMD SEV-SNP に Mior と Skyfall

**2026年11月10日、AMD が2件のセキュリティ情報を公開し、 SEV-SNP（Secure Encrypted Virtualization - Secure Nested Paging）の 保護を破る攻撃が2つ、協調的な開示を経て公表された** （出典1・3。本記録が両方の原文を取得して確認した）。 **1つは Mior（AMD-SB-3059・CVE-2026-0462・CVSS 4.0 基本値 5.9）**—— **「悪意あるハイパーバイザが Memory Mapped I/O（MMIO）の経路を 操作し、一部の AMD プロセッサで SEV-SNP の完全性を 損ないうる」**（出典1・原文英語。本記録が訳した）。 **もう1つは Skyfall（AMD-SB-3061・CVE-2026-40671・CVSS 4.0 基本値 4.9）**—— **「VMRUN のエラー処理における不完全な後始末が、 Transient Scheduler Attacks（TSA）のサイドチャネル経由で SEV-SNP ゲストのレジスタ状態を特権を持つ攻撃者に 露出させうる」**（出典3・原文英語。本記録が訳した）。 **SEV-SNP は、サーバの運用者（ホスト側）を信頼の外に置くための仕組みである** ——**つまり破られているのは「クラウド事業者を信頼しなくても 仮想マシンの中身は守られる」という前提そのものである**（本記録の整理）〈重要〉。 **Mior はさらに2つのことをする**（出典2）—— **ゲストのメモリを書き換えること、および 「どのソフトウェアを起動したか」を証明する署名付きのレポート （attestation report）を偽造すること。** **研究者らは、良性のゲストの暗号化された起動測定値を 悪意あるゲストのメタデータに写し込むことで、 PSP（Platform Security Processor）に 良性の測定値を含むレポートを署名させたと記している**（出典2）。 **Mior の前提条件は重い**（出典2。本記録の確認）—— **ハイパーバイザの制御、BIOS の改変（Data Fabric の設定レジスタを 施錠されていない状態にする）、および攻撃者が用意した PCIe デバイス （GPU など）。** **修正の時期が分かれていることが、本記録が読者に最も伝えたい点である** （本記録の評価）〈重要〉—— **SEV ファームウェアとマイクロコードは2026年8月12日付で既に出ているが、 利用者が実際に当てる BIOS の元になる Platform Initialization（PI） ファームウェアは、Skyfall が2026年11月予定、Mior が2026年12月予定、 組込み向け（EPYC Embedded）は2027年1月〜4月予定である**（出典1・3）。 **AMD は「製品固有の BIOS 更新については OEM に問い合わせること」と 記している**（出典1・3）—— **つまり当てられるかどうかはサーバの製造元に依る。**

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は研究者の公開ページ（出典2・4）に記された仕組みである** （本記録の整理）〈重要〉—— **実環境の侵害事案ではなく、研究室内の実証である**〈未確定1〉。 **2件は独立した攻撃で、仕組みも前提も違う。** **共通しているのは攻撃者の立ち位置だけである**—— **SEV-SNP の脅威モデルでは、ハイパーバイザ・BIOS／UEFI・ 周辺デバイスはいずれも信頼されない**（出典2）。 **つまり「ホスト側が敵である」という前提は SEV-SNP が自ら置いているもので、 本件はその前提の下で保護が破れたという話である。**

  1. 1. 検知回避確認済[1] [2]
    **【Mior】PSP が自身のメモリ地図を検証する際に、 複数のファブリック構成要素から読んだ経路レジスタの ビットごとの論理和を取る。 悪意ある MMIO の範囲をその論理和の結果の中に隠すことで、 PSP はそれを DRAM として受け入れる**（出典2）。
    根拠: Mior の研究ページ「Hiding the redirect」の記述（出典2）
  2. 2. 影響（暗号化・破壊・改ざん）確認済[2]
    **【Mior】経路を変えられた PSP の書き込みが、 攻撃者のデバイス（GPU など）に向かう。 デバイスは値を保持して返すので、PSP の読み返しの検証も通る。 その結果、DRAM 上の Reverse Map Table（RMP）には 書き込みが届かない。 攻撃者は RMP 自身を保護する RMP の項目を未初期化のまま残し、 ハイパーバイザが RMP の残りを書き換えられる状態にする**（出典2）。
    根拠: Mior の研究ページ「Device-as-Memory」の記述（出典2）
  3. 3. 認証情報アクセス確認済[1] [2]
    **【Mior】暗号化されたゲストのメタデータを壊すことで、 本番の機密VM に対して PSP のデバッグコマンドを有効にし、 ハイパーバイザがゲストのメモリを読み書きできるようにする** （出典2）。
    根拠: Mior の研究ページ「Memory read/write」の記述（出典2）
  4. 4. 検知回避確認済[1] [2]
    **【Mior】良性のゲストの暗号化された起動測定値を 悪意あるゲストのメタデータに写し込む。 PSP は、実際には別のイメージを起動したにもかかわらず、 良性の測定値を含む構成証明レポートに署名する**（出典2）。
    根拠: Mior の研究ページ「Attestation forgery」の記述（出典2）
  5. 5. 認証情報アクセス確認済[3] [4]
    **【Skyfall】VMRUN のエラー処理における不完全な後始末により、 SEV-SNP ゲストのレジスタ状態が L1 キャッシュに残る。 研究側は、キャッシュの経路予測器における 「物理↔仮想」のマイクロタグ（µtag）の別名衝突と、 TSA（Transient Scheduler Attacks）の緩和策の穴を 組み合わせて取り出すと説明している**（出典3・4）。
    根拠: AMD-SB-3061 の CVE 説明と Skyfall の研究ページ（出典3・4）
  6. 6. 収集確認済[4]
    **【Skyfall】研究側が実験で取り出したもの**（出典4）〈重要〉—— **①VMSA からの SEV-SNP ゲストのレジスタ状態、 および改変したゲストカーネルを用いた実証での AES-XTS のディスク暗号化鍵。 ②選んだページ内の3つの固定されたキャッシュライン境界の位置に ある ゲストメモリ（全バイトではない）。 ③試験した3台すべてで、復号されたマイクロコードパッチの内容。 ④EPYC 7313 でのみ、EntrySign の緩和策より前に使われていた CMAC 鍵。 ⑤SMM の State Save Area の項目（SMBASE・CR3・R13）を 精度100%で。**
    根拠: Skyfall の研究ページの実験結果の記述（出典4）

破られたのは「クラウド事業者を信頼しなくてよい」という前提である評価・解釈出典 [1] [2] [3] [4]

SEV-SNP は、サーバの運用者を信頼の外に置くための仕組みです （本記録の整理）。 Mior の研究ページも 「AMD の SEV-SNP の脅威モデルでは、 ハイパーバイザ・BIOS／UEFI・周辺デバイスは信頼されない」と 前提を明記しています（出典2・原文英語。本記録が訳した）。 この前提があるから、機密コンピューティングは 規制産業や個人情報の処理で「基盤を信頼せずに使える」 選択肢として採用されてきました。

今回破られたのは、その前提の下での保護です〈重要〉。 Mior は、ゲストのメモリの読み書きに加えて、 「どのソフトウェアを起動したか」を証明する署名付きレポートの 偽造まで成立させます（出典2）。 Skyfall は、実験で SEV-SNP ゲストのレジスタ状態と、 改変したゲストカーネルを用いた実証では AES-XTS のディスク暗号化鍵を取り出しています（出典4）。

一方で、前提条件は軽くありません（本記録の整理）。 Mior はハイパーバイザの制御に加えて、 BIOS を改変して Data Fabric の設定レジスタを 施錠されていない状態にすること、 および攻撃者が用意した PCIe デバイス（GPU など）を要します （出典2）。 Skyfall は AMD の表現で「特権を持つ攻撃者」です（出典3）。 どちらもテナント側からは実行できません—— Mior の研究ページは「普通の VM は対象ではない。 既にハイパーバイザを信頼しているため」と書いています（出典2）。

したがって読み方はこうなります（本記録の判断）。 「クラウドの他のテナントから中身を覗かれる」話ではありません。 「基盤を握った相手に対して、SEV-SNP が条件付きで無力になる」 話です。 機密VM を選んだ理由が「事業者を信頼しなくてよいから」であった場合、 その理由の強度が下がったことになります。

修正は8月に出ていた——当てられるのは12月以降、組込みは2027年である再発防止出典 [1] [3]

本記録が読者に最も伝えたいのは、修正の時期が3層に分かれている ことです（本記録の評価）〈重要〉。

第1層——AMD が直した日。 Mior の SEV ファームウェア（1.3A.03／1.3A.4／1.3A.0A）と Skyfall のマイクロコードは、いずれも2026年8月12日付です （出典1・3）。 公開の約3か月前です。 AMD Instinct MI300A 向けの Skyfall 修正は2026年9月21日付です （出典3）。

第2層——OEM に渡る日。 Platform Initialization（PI）ファームウェアの提供予定は、 Skyfall が2026年11月、Mior が2026年12月です（出典1・3）。

第3層——利用者が当てられる日。 AMD は「製品固有の BIOS 更新については OEM に 問い合わせること」と記しています（出典1・3）。 PI ファームウェアが OEM に渡ったあと、 各社が BIOS を作って配布する工程が入ります。 その時期は AMD の情報には書かれていません〈未確定2〉。

組込み向け（EPYC Embedded）はさらに遠い〈重要〉。 Skyfall が2027年1月（7003）・2月（9005）・4月（8004・9004）、 Mior が2027年2月（全系統）の予定で、 版はいずれも「未定（TBD）」です（出典1・3）。 2026年8月12日から数えると、最も遠いものは約8か月後です （本記録の算出）。

実務上の意味は1つです（本記録の判断）。 「AMD が修正を出した」という報道を見て 対応済みと判断してはいけません。 確認すべきは、自社のサーバの OEM が AMD-SB-3059 と AMD-SB-3061 に対応した BIOS を いつ出すか、です。 クラウド上の機密VM を使っている場合は、 自分では当てられないので事業者に聞くしかありません。

評点 4.9 でディスク暗号化鍵が出ている——CVSS で優先順位を決めない評価・解釈出典 [3] [4]

Skyfall の CVSS 4.0 基本値は 4.9 です（出典3）。 ベクタの機密性への影響は VC:L（低）です。

一方で研究側が実験で取り出したものは、次の通りです （出典4）〈重要〉—— ①VMSA からの SEV-SNP ゲストのレジスタ状態、 および改変したゲストカーネルを用いた実証での AES-XTS のディスク暗号化鍵。 ②選んだページ内の3つの固定されたキャッシュライン境界の位置に あるゲストメモリ。 ③試験した3台すべてで、復号されたマイクロコードパッチの内容。 ④EPYC 7313 でのみ、EntrySign の緩和策より前に使われていた CMAC 鍵。 ⑤SMM の State Save Area の項目（SMBASE・CR3・R13）を精度100%で。

評点とこの一覧は、同じものを測っていません （本記録の評価）。 CVSS は「どれだけ容易に、どの範囲に影響するか」を測りますが、 ここでの前提は PR:H（高い権限が必要）です。 ホスト側を握っていることが前提なら、 評点は上がりにくい——しかし、その前提が満たされた世界では ディスク暗号化鍵まで届きます。

読者が取るべき行動はこうです（本記録の提案）。 機密VM を「基盤を信頼しなくてよい」根拠として使っている場合、 この2件は評点にかかわらず対応の対象です。 逆に、機密VM を性能や可用性の都合で選んでいて 脅威モデルにホスト側を含めていない場合、 優先順位は下がります。 分かれ目は評点ではなく、何のために機密VM を使っているかです。

なお数値の読み方にも注意が要ります（本記録の注意）。 「精度100%」は SMM の3項目に掛かる値で、 ゲストメモリ全体ではありません。 ゲストメモリは「選んだページ内の3つの固定された位置」に 限られると研究ページが明記しています（出典4）。 ディスク暗号化鍵の回収も 「改変したゲストカーネルを用いた実証」という条件付きです。

検知の最後の砦が同じ攻撃で無効化される——構成証明の偽造評価・解釈出典 [1] [2]

機密VM で異常に気づくための経路は、構成証明（attestation）です （本記録の整理）。 「自分が起動したのは、意図したイメージか」 「ホストはデバッグモードを有効にしていないか」を、 署名付きのレポートで確認します。

Mior は、この経路を壊します〈重要〉。 研究ページによれば、良性のゲストの暗号化された起動測定値を 悪意あるゲストのメタデータに写し込むことで、 PSP は実際には別のイメージを起動したにもかかわらず、 良性の測定値を含むレポートに署名します（出典2）。 同じ攻撃で、本番の機密VM に対して PSP のデバッグコマンドを有効にし、 ハイパーバイザがゲストのメモリを読み書きできる状態も 作られます（出典2）。

つまり、デバッグモードが有効になったことを 構成証明で確かめようとしても、 その構成証明が偽造されている、という構図です （本記録の整理）。

残る手掛かりは TCB の値です（本記録の読み）。 AMD-SB-3059 には、製品ごとの 「SNP の構成証明のための TCB 値」と緩和ビットが 掲載されています（出典1）—— 例えば EPYC 9005 シリーズは TCB[SNP]=0x8、緩和ビット=12。 検証側が更新後の TCB 値を要求すれば、 修正前のファームウェアで起動したことは分かるはずです。

ただし、これが実運用の検証経路で実際にどこまで効くかは、 研究側も示していません〈未確定5〉〈重要〉。 本記録は推測を書きません。 読者が確認すべきことは具体的です—— 自社の構成証明の検証が、起動測定値だけを見ているのか、 TCB 値も見ているのか。 測定値だけなら、この偽造は通ります。

AMD の情報に「Mior」「Skyfall」の名前は無い——対応表が要る評価・解釈出典 [1] [3] [5]

AMD-SB-3059 と AMD-SB-3061 には、 「Mior」「Skyfall」という名前が一度も現れません （出典1・3。本記録の確認）〈重要〉。 記載されているのは情報番号、CVE 番号、CWE、評点、 対象製品、修正版、謝辞です。

本記録は、名前と CVE の対応を 研究者の業績一覧（出典5）で確定しました（本記録の作業）。 そこには 「Mior: Breaking AMD SEV-SNP with Device-as-Memory」 （Christoph Wech・Philipp Giersfeld・Benedict Schlüter・ Shweta Shinde、ACM CCS 2026）に対して AMD-SB-3059 と CVE-2026-0462 が、 「Skyfall: Microarchitectural Data Sampling on AMD」 （Benedict Schlüter・Alessandro Vezzù・Daniel Moghimi・ Shweta Shinde、IEEE S&P 2027）に対して AMD-SB-3061・AMD-SB-7072 と CVE-2026-40671・CVE-2026-18448 が並記されています（出典5）。

謝辞の内容も対応を裏付けます（本記録の確認）。 AMD-SB-3059 の謝辞は ETH Zurich の4名（Mior の著者と一致）、 AMD-SB-3061 の謝辞は ETH Zurich の3名と Google の Daniel Moghimi（Skyfall の著者と一致）です （出典1・3）。

    **Mior は、良性のゲストの暗号化された起動測定値を 悪意あるゲストのメタデータに写し込み、 PSP に良性の測定値を含むレポートを署名させる** （出典2）〈重要〉。 **AMD-SB-3059 には製品ごとの 「SNP の構成証明のための TCB 値」と緩和ビットが 掲載されている**（出典1）—— **検証側で更新の有無を見分ける材料である。** **ただし実運用の検証経路でどこまで効くかは 研究側も示していない**〈未確定5〉。
    取るべき行動 **自社の構成証明の検証コードを読み、 照合している項目を列挙する。** **起動測定値のみなら、TCB 値（ファームウェアの版）の 照合を追加する。** **追加する際は、ファームウェア更新と検証側の設定変更を 同期させる手順を先に決める—— 同期を怠ると正常な機密VM が拒否される。**
  • 自社の EPYC 世代と SEV-SNP の利用有無を、 台帳で即答できる状態にする。
    **対象は EPYC 7003／8004／8005／9004／9005、 Instinct MI300A（Skyfall のみ）、 EPYC Embedded 7003／8004／9004／9005 である** （出典1・3）〈重要〉。 **Mior については SEV と SEV-ES は影響なしで、 SEV-SNP のみが対象である**（出典1）—— **つまり「EPYC を使っているか」ではなく 「SEV-SNP で機密VM を動かしているか」が分かれ目になる。**
    取るべき行動 **資産台帳に、EPYC の型番（世代が分かる形）と SEV／SEV-ES／SEV-SNP の利用状況を持たせる。** **持っていない場合、まず対象機の洗い出しに どれだけ時間がかかるかを測る—— 次回の同種の公表のときにも同じ時間がかかる。**
  • 機密VM の中だけに秘密を置く設計をやめ、鍵の生存期間を短くする。
    **Skyfall の実験では、改変したゲストカーネルを用いた実証で AES-XTS のディスク暗号化鍵が取り出されている** （出典4）〈重要〉。 **Mior では、デバッグコマンドの有効化によって ハイパーバイザがゲストのメモリを読み書きできる状態が 作られる**（出典2）。 **「機密VM の中なら安全」を唯一の防御層にしていると、 破られた時点で全部が出る**（本記録の評価）。
    取るべき行動 **機密VM 内に常駐させている長期の鍵を洗い出し、 生存期間を短くする（定期交換・セッション単位の派生）。** **鍵の解放を構成証明の結果に条件付ける設計になっているか 併せて確認する。**
  • 「精度100%」「鍵が取れた」の掛かる範囲を、研究ページで確認する。
    **Skyfall の研究ページは、精度100%が SMM の State Save Area の3項目（SMBASE・CR3・R13）に 掛かる値であること、 ゲストメモリは「選んだページ内の3つの固定された キャッシュライン境界の位置」に限られること、 ディスク暗号化鍵の回収は 「改変したゲストカーネルを用いた実証」であることを 明記している**（出典4）〈重要〉。 **報道の見出しだけでは、この条件が落ちる** （本記録の注意）。
    取るべき行動 **ハードウェアの脆弱性の報道を受けて対応を判断するとき、 研究側の公開ページの実験結果の節を必ず読む。** **「何が、どの条件で、どこまで取れたか」を 1行に書き出してから判断する。**
