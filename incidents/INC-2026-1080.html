    **本事案の突破は「認証番号を反復入力して認証を通過した」 ものである**（出典2）〈重要〉。 **回数制限を IP アドレス単位で数える実装では、 攻撃者が接続元を分散させれば上限に当たらない** （本記録の判断）。 **同社の措置には攻撃に使われた IP アドレスの 即時遮断が含まれるが**（出典2）、 **これは事後の封じ込めであり、 予防としては回数制限のほうが効く**（本記録の整理）。
    取るべき行動 **パスワード再設定の認証番号について、 アカウント単位の試行回数上限を実装する。** 上限超過時は、コードを無効化し（再送も一定時間拒否）、 アカウントを一時ロックして本人へ通知する。 あわせて、認証番号を使い捨てにし （同一コードでの再試行を許さない）、 有効期限を短く取る。 実装後は、意図的に総当たりを試して遮断されることを確認する。
  • API 鍵に有効期限と権限範囲が無いと、1本の流出で基盤全体に到達される
    **本事案では Open API の脆弱性で一部の API 鍵が流出し、 その鍵を用いた API 呼び出しが確認されている** （出典2）〈重要〉。 **提供事業者は流出鍵を特定できず、 全量廃棄に踏み切った**（出典1・2）—— **鍵に有効期限と権限の範囲があれば、 流出時の影響を絞り、 全量廃棄という選択を避けられた可能性がある** （本記録の判断）。 **とくに Admin API の鍵は、 通常のサービス API と同列に扱うと影響が大きい。**
    取るべき行動 **発行する API 鍵に有効期限（最長でも1年）と 権限の範囲（読み取り専用・対象プロジェクト限定）を必須にする。** 管理者用 API の鍵は通常の鍵と分離し、 接続元を限定した経路からのみ使えるようにする。 あわせて、鍵ごとの最終利用日時を記録し、 使われていない鍵を自動失効させる。
  • API 鍵による呼び出しに「正常の基準」が無いと、異常を異常として識別できない
    **本事案では、提供事業者が 「API 鍵を利用した異常な呼び出し」を識別できている** （出典3）〈重要〉—— **これは、呼び出しの量・頻度・接続元についての 基準を持っていたことを示す**（本記録の評価）。 **検知が発生と同じ夜のうちに成立し**（出典1・2）、 **滞留が数時間の範囲に収まっている**（本記録の整理）。
    取るべき行動 **API 鍵ごとに、平常時の呼び出し頻度・接続元 IP・ 参照範囲のベースラインを取る。** 逸脱時は、警報を出すだけでなく、 自動で当該鍵を失効させる経路を用意する （人の判断を待つと夜間に数時間が失われる）。 ベースラインが取れていない鍵を、 棚卸しの優先対象にする。
  • 「可能性のある項目」と「実際の項目」を分けて通知できるかは、監査ログの粒度で決まる
    **本事案では、告知で流出の可能性がある項目を列挙し、 実際の流出項目は情報主体ごとに個別通知メールで 伝える設計が採られている**（出典2）〈重要〉—— **これは、情報主体単位で実際の流出を切り分けられる記録が なければ成立しない**（本記録の見立て。資料に明示は無い）。 **粒度が足りない組織は 「全員に全項目が漏れた可能性がある」としか言えず、 通知の範囲が過大になる**（本記録の評価）。
    取るべき行動 **API 経由の参照についても、 「どの鍵が」「いつ」「どのリソースを」「どの範囲まで」 取得したかを記録する。** 画面操作のログだけでなく、 API のアクセスログを同じ粒度で保全する （保全期間は最低1年）。 設計の検証は、実際に1アカウント分の参照履歴から 流出項目を再構成できるかを試して行う。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ 自社サービス（または自社が使う SaaS）のパスワード再設定で、認証番号の試行回数の上限が無い、または上限を IP アドレス単位で数えている**本事案の突破経路がこれである**（出典2）〈重要〉—— **「認証番号を反復入力して認証を通過した」とされている。** **再設定の経路に制限が効かなければ、 パスワードの強度もログイン時の二要素認証も迂回される** （本記録の判断）。 **IP 単位で数える実装は、接続元の分散で回避される。**
認証・認可□ 発行している API 鍵に有効期限が無い、または権限の範囲（読み取り専用・対象限定）を設けていない。管理者用 API の鍵を通常の鍵と同列に扱っている**本事案では一部の API 鍵が流出し、 提供事業者は流出鍵を特定できず全量廃棄に踏み切った** （出典1・2）〈重要〉。 **鍵に期限と範囲があれば影響を絞れた可能性がある** （本記録の判断）—— **Admin API の鍵は、通常の鍵と同列だと影響が大きい。**
運用・監視□ API 鍵ごとの平常時の呼び出し頻度・接続元・参照範囲のベースラインを取っておらず、逸脱時に自動で鍵を失効させる経路が無い**本事案では提供事業者が 「API 鍵を利用した異常な呼び出し」を識別し、 発生と同じ夜のうちに検知している**（出典1・2・3）〈重要〉。 **基準が無ければ、正規の鍵による正規の呼び出しは 異常として浮かび上がらない**（本記録の評価）。
委託・第三者部品□ 外部 SaaS との API 連携を棚卸ししておらず、「鍵が今日無効になったら何が止まるか」を把握していない**本事案では、提供事業者の正しい判断の結果として API 鍵が予告なく全量無効化され、 顧客企業の外部システム連携と自動化機能が止まった** （出典1）〈重要〉。 **これは提供事業者の過失を問う話ではなく、 利用側の備えの話である**（本記録の判断）。
データの保持□ 協業ツール（プロジェクト・ドライブ・メッセンジャー・カレンダー）に置いてよい情報の区分を定めておらず、人事・M&A・訴訟の議論や認証情報が混在している**本事案で流出の可能性があるとされたのは これらの領域の業務関連資料である**（出典2）〈重要〉。 **個別ファイルの機密性ではなく、 組織の意思決定の文脈がまとまって出ていくことが 影響の本体になる**（本記録の評価）。 **列挙には「等」が付き、メールの扱いは示されていない**〈未確定4〉。
体制・契約□ 自社が多数の組織にサービスを提供する立場で、侵害時に「被害なしと確認された利用組織」への伝え方を決めていない**本事案は「一部顧客企業」で流出があったとされるが、 影響を受けていない顧客企業への伝え方に触れていない** （出典2）〈未確定5〉〈重要〉。 **通知が来なければ対象外という設計だとみられるが明示が無く、 「まだ通知が来ていない」と「対象外である」を 外から区別できない**（本記録の評価）。
