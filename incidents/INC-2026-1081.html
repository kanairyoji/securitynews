**Telegram が2026年11月9日に Bot API 10.4 で「対話の中で動く HTML ウィジェット」を 全ボットへ開放した直後、その隔離の内側で動く JavaScript エンジンの メモリ安全性の不備が相次いで修正された。Telegram 自身のウィジェットサンドボックスの 変更履歴（GitHub）は、v0.6.1（11月6日）の RegExp 削除の不備について 「これが報告された RCE である」と明記し、v0.6.4（11月10日）の `await using` の不備を 「ウィジェットのスクリプトからのネイティブコード実行として報告された」 「素のウィジェット JS から到達可能な use-after-return」と記述している。 後者は、11月9日に公開された QuickJS-ng の第三者セキュリティ監査（27件の指摘・ issue #1902）の指摘3（深刻度 High）に対応する。問題のコードは2026年5月16日に 上流の QuickJS-ng の main へ入っており、修正までの期間は178日である。 11月11日、研究者グループ V12 が Android 上で電卓アプリが自動的に開く実演動画 「Telegram Widgets RCE」を公開した——ただし `await using` の修正は その前日（11月10日）に Android 版 13.2.2（ビルド7303）で出ており、 同じ版でウィジェットの実行は Telegram のファイルにもネットワークにも 触れない独立プロセスへ移された。デスクトップ版は11月11日の 7.4.2 に 当該修正が入っておらず、入ったのは11月13日深夜（モスクワ時間）の 7.4.3 である。 その11月13日、Pavel Durov 氏は「問題は存在しない」と投稿した—— **自社の技術変更履歴が「報告された RCE」と書いているものを、 経営トップが存在しないと述べる形になっている。** CVE 番号は割り当てられていない。**

2026年11月9日、Telegram は Bot API 10.4 を公開し、ボットがメッセージの中に 対話型の HTML ウィジェットを埋め込めるようにした（出典1）。 Mini Apps と違い、別アプリを開かずに対話の中でそのまま動く（出典1）。 デスクトップ版では一足早く、11月5日の 7.4.0 で 「HTML widgets in bots」として入っていた（出典7）。 公式ドキュメントは隔離の仕組みを具体的に書いている（出典2）—— 「ウィジェットの JavaScript は QuickJS という小さな JavaScript エンジンで動き、 WebView やブラウザのコンテキストでは決して動かない」（訳。原文英語）、 HTML は32KB（圧縮4KB）まで、ネットワークは設計上無効で fetch や WebSocket は NetworkDisabledError を投げ、 外部のスクリプト・スタイルシート・フォント・画像は一切読み込まれない。 外へ出られる経路はボットへの最大64バイトの要求だけで、 本番環境ではボットとの1対1の対話でしか動かず、転送もできない（出典1・2）。その隔離の内側で、エンジンのメモリ安全性の不備が相次いで修正された。 Telegram 自身が公開しているウィジェットサンドボックスの変更履歴（GitHub）が 一次資料である（出典3）〈重要〉—— v0.6.1（2026年11月6日）は RegExp 削除の高速経路 （replace(re, "") / replaceAll(re, "") が lastIndex の変換前に コンパイル済みバイトコードを読む）の修正について 「これが報告された RCE である」（訳。原文英語）と明記し、 v0.6.4（2026年11月10日）は await using の不備を 「ウィジェットのスクリプトからのネイティブコード実行として報告された」 「素のウィジェット JS から到達可能な use-after-return」（いずれも訳。原文英語）と 記述している。 v0.6.4 はこのほかに5件の use-after-free / 領域外アクセスの修正を含み、 いずれも「サンドボックスより下、素のウィジェット JS から到達可能」とされる（出典3）。await using の不備は、2026年11月9日に公開された QuickJS-ng の 第三者セキュリティ監査（GitHub issue #1902・指摘27件）の指摘3に対応する（出典4）—— 深刻度 High、「for (await using ...) が非 async 関数でも受け入れられ、 その結果 OP_await が通常のフレームで走り、死んだ C スタックへの var_refs がぶら下がったまま残る」（訳。原文英語）。 問題のコードは2026年5月16日に上流の QuickJS-ng の main へ入っており、 修正までは178日である（出典8。本記録の算出）。2026年11月11日、研究者グループ V12 が実演動画「Telegram Widgets RCE」を公開した （出典6・7）——Android の利用者がボットを起動すると、 カウントダウンのメッセージのあとに端末の電卓アプリが自動的に開く（出典6）。 ただし await using の修正は前日（11月10日）に Android 版 13.2.2（ビルド7303）で出ており、 同じ版でウィジェットの実行は「Telegram のファイルにもネットワークにも 触れない独立した隔離プロセス」へ移され、 ウィジェットのプロセスからの新規プログラム起動も封じられた（出典7）。2026年11月13日、Pavel Durov 氏は自身のチャンネルで 「問題は存在しない」（原文英語: "The issue doesn't exist."）と投稿し、 「メッセージを受け取っただけでハックされうる者はいなかった」 「まず利用者が自分で第三者のサービスを起動する必要があった」 「それも含めてサーバ側で完全に修正済みである」と述べ、 「そう思わないなら私のアカウントをハックしてみろ」と書いた（出典5）。 CVE 番号は割り当てられていない〈未確定1〉。 実際に悪用された事例は報告されていない〈未確定2〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本記録が公表資料（出典1〜8）から整理した経路である。** **Telegram のウィジェットサンドボックス変更履歴（出典3）と QuickJS-ng の監査（出典4）が技術的な所在を記述しており、 実演動画（出典6）が外から見える結果を示している。** 経路は「**ボットの起動 → ウィジェットを含むメッセージの受信 → サンドボックス検査を通過した素のウィジェット JS → エンジン（QuickJS-ng の fork）のメモリ安全性の不備 → サンドボックスより下での動作 → 端末でのプログラム起動**」である。 **データの持ち出し・永続化・C2 は確認されていない**〈未確定9〉。 **本記録は、再現につながる技術的な詳細を採録しない**（本記録の判断）。

  1. 1. 初期侵入[1] [2] [5] [6]
    **利用者が当該ボットを自分で起動する**（出典5。Durov 氏が 「まず利用者が自分で第三者のサービスを起動する必要があった」と明記）。 **実演では利用者がボットを起動している**（出典6）。 **本番環境ではウィジェットはボットとの1対1の対話でしか動かず、 転送もできない**（出典1・2）ため、 **ボットの起動が唯一の入口である**（本記録の整理）。 **どのように当該ボットへ誘導するかは公表資料の対象外である。**
  2. 2. 実行[2] [3] [6] [7]
    **ボットが HTML ウィジェットを含むメッセージを送り、 クライアントがそれを処理する**（出典1・2）。 **実演ではカウントダウンのメッセージとして現れる**（出典6）。 **仕様上、ウィジェットの JavaScript は QuickJS（QuickJS-ng の fork）で動き、 WebView やブラウザのコンテキストでは動かない**（出典2）。 **この段階で動くのは「素のウィジェット JavaScript」であり、 特別な権限は要らない**（出典3。本記録の整理）。
  3. 3. 検知回避[3] [4]
    **サンドボックスの検査を迂回するのではなく、その下で成立する**（出典3）〈重要〉—— **Telegram は「パーサのメモリ安全性の不備は、 あらゆるサンドボックスの検査より下にあるエンジンの射程に入る」と書いている** （出典3。訳）。 **到達可能とされた不備は、RegExp 削除の高速経路（v0.6.1・ 「これが報告された RCE である」）と、 `await using` の use-after-return（v0.6.4・ 「ウィジェットのスクリプトからのネイティブコード実行として報告された」）、 および v0.6.4 の5件の use-after-free / 領域外アクセスである**（出典3。訳）。 **`await using` の技術的な所在は監査の指摘3（深刻度 High）に記述がある**（出典4）。
  4. 4. 影響（暗号化・破壊・改ざん）[3] [6] [7]
    **Android 上で電卓アプリが自動的に開いた**（出典6）—— **これが公開実演で外から確認できる影響の全部である**（本記録の明示）。 **Telegram の変更履歴は不備の到達性を書くが、 到達後に何ができたかは書いていない**（出典3。本記録の確認）。 **データの読み出し・持ち出し・永続化・C2 通信はいずれも 確認されていない**〈未確定9〉。 **なお、修正版では「ウィジェットのプロセスからの新規プログラム起動」が 封じられている**（出典7）—— **実演で起きたのはまさにこの動作である**（本記録の照合）。

本記録の評価として、ここから2つのことが言える。

①Telegram の対応そのものは速い。 到達可能な不備を把握してから数日で塞ぎ、到達可能な RCE と単なる hardening を変更履歴で区別して書いている（出典3）。公開実演の時点では、該当する不備はすでに修正済みであった可能性が高い。

②しかし、機能の全面開放の時点でエンジンの点検は終わっていなかった。開放の当日（11月9日）に27件の監査指摘が公開され（出典4）、その翌日に「サンドボックスより下、素のウィジェット JS から到達可能」な不備が6件まとめて修正されている（出典3）。順序が逆である（本記録の評価）〈重要〉—— 届く場所に置いてから、届く範囲を点検している。

サンドボックスの検査は、その下で動くエンジンが壊れる場合には効かない原因・手口

Telegram のウィジェットの隔離は薄くない。公式ドキュメント（出典2）が書く仕様は次のとおりである。

  • 実行エンジン: 「ウィジェットの JavaScript は QuickJS という小さなJavaScript エンジンで動き、WebView やブラウザのコンテキストでは決して動かない」（訳。原文英語）
  • 大きさ: HTML は32KB まで、圧縮後4KB まで
  • 描画: クライアントはウィジェットがページに加える変更を1つずつ「ウィジェットプロファイル」に照合し、通ったものだけを描く
  • ネットワーク: 設計上オフライン。fetch や WebSocket はNetworkDisabledError を投げ、外部のスクリプト・スタイルシート・フォント・画像は一切読み込まれない
  • 外向きの経路: ボットへの最大64バイトの要求だけ（5秒に5回まで）
  • 移動と対話: 画面遷移できない。alert / confirm / prompt はダイアログを出さない
  • 資源: CPU・メモリ・DOM ノード数・タイマーに上限があり、超えたウィジェットは停止される
  • 範囲: 「現在、本番環境ではウィジェットはボットとの1対1の対話でのみ動く」（訳。原文英語）

それでも破れた理由を、Telegram 自身が一文で書いている（出典3）〈重要〉。

「パーサのメモリ安全性の不備は、あらゆるサンドボックスの検査より下にあるエンジンの射程に入る」（訳。原文英語。v0.6.2 の記述）

これが本件の構造上の要点である（本記録の整理）。上に並んだ制約はすべてエンジンが正しく動いている前提で効く。エンジンのメモリが壊れれば、その制約を課している側のコードが壊れる。 v0.6.1 も v0.6.4 も、不備を「素のウィジェット JavaScript から到達可能」（訳。原文英語）と記述している（出典3）—— 特殊な権限も、仕様の穴も要らない。

不備の中身は2系統である（出典3）。

  • RegExp 削除（v0.6.1・11月6日）: replace(re, "") / replaceAll(re, "") の高速経路が、lastIndex の変換前にコンパイル済みバイトコードを読む。「これが報告された RCE である」（訳。原文英語）。なお Telegram は「fork の RegExp パターンキャッシュが最近コンパイルしたバイトコードを生かし続けるため、素朴な発火方法では解放されない」とも書いている（出典3。訳）。
  • await using（v0.6.4・11月10日）: 「ウィジェットのスクリプトからのネイティブコード実行として報告された」「素のウィジェット JS から到達可能な use-after-return」（訳。原文英語）。

後者は上流に由来する。第三者監査の指摘3（深刻度 High）が同じ不備を記述している（出典4）——「for (await using ...) が非 async 関数でも受け入れられ、その結果 OP_await が通常のフレームで走り、死んだ C スタックへの var_refs がぶら下がったまま残る」（訳。原文英語）。問題のコードは2026年5月16日に、明示的資源管理の対応と一緒に上流 QuickJS-ng の main へ入っている（出典8）。

不備は半年前からあり、それを届く場所に置いた機能が後から来た（本記録の整理）〈重要〉—— 部品を選んだ時点で、その部品の未発見の不備も一緒に引き受けている。

AI を使った第三者のコード監査が、機能の全面開放と同じ日に27件を公開した発覚の端緒

本件の発覚の経路には、記録しておく価値のある形がある（本記録の整理）。

2026年11月9日、Andreas Rösdahl 氏が GitHub issue #1902「Security audit of QuickJS-ng」を公開した（出典4）。コミット d4187c7 を対象に、本体エンジン・libc・libregexp を読み、27件の指摘を深刻度別（Critical〜Info）に並べている。

手法が明記されている点が重要である（本記録の評価）〈重要〉。

「依頼により、検証コードや発火コードは一切書かず、実行もしていない」「指摘は『再現した』のではなく『コードを読んで確認した』ものである」（いずれも訳。原文英語）

さらに「Claude Fable 5.1 モデルを用いた」と述べている（出典4）。

本記録は、この事実を評価の対象ではなく条件として扱う（本記録の明示）。読むべきは次の3点である。

①再現していない指摘が、実在する到達可能な不備を含んでいた。指摘3（深刻度 High）は、翌日 Telegram の v0.6.4 で「ウィジェットのスクリプトからのネイティブコード実行として報告された」不備として修正されている（出典3・4。本記録の照合）。PoC を書かない監査でも、当たりは出る。

②同時に、誤検知の可能性も議論されている。 11月11日、connorshea 氏が issue 上で相互参照を書き込み、指摘1 は #1900、指摘4 は #1865、指摘9 は閉じた PR #1482 と重なると指摘し、指摘6 が誤検知ではないかと問うている（出典4）。27件という数字を「27個の脆弱性」と読んではいけない（本記録の明示）。

本記録の評価として、ここに供給網の非対称がある。 指摘は上流に出され、修正は下流の fork で先に動いた。同じエンジンを使う他の製品は、issue を自分で読んでいなければ気づけない。小規模なオープンソース部品に、修正を配る仕組みが備わっていない場合、「修正されたかどうか」は組み込んだ側ごとにばらばらになる（本記録の評価）。

  • Desktop 7.4.2: 11月11日。await using の修正は入っていない。別のメモリ修正5件のみ。

差は3日である（本記録の算出。figures 参照）〈重要〉。デスクトップ版のウィジェットは11月5日の 7.4.0 から入っていた（出典7）ため、デスクトップの利用者は、Android が直った後も3日間、同じ不備を抱えていた。

そして、それを知る手段が無かった（本記録の評価）。7.4.2 と 7.4.3 のリリース説明はいずれも「バグ修正とその他の小さな改善」である（出典7。訳）。どちらにセキュリティ修正が入っているかは、説明文からは判別できない。

判別できる場所は1つだけ存在した—— ウィジェットサンドボックスの変更履歴（GitHub）である（出典3）。ここには到達可能な RCE と hardening の区別まで書かれている。つまり情報は公開されていたが、利用者が見る場所には無かった（本記録の評価）〈重要〉—— アプリの更新画面に出るのは「小さな改善」の側である。

実務上の含意はこうなる（本記録の評価）。マルチプラットフォームの製品では、「修正済み」は製品単位ではなくプラットフォーム単位・版単位で確認する必要がある。本件で「Telegram は直した」は正しいが、「自分の Telegram は直った」は、11月11日のデスクトップ利用者には当てはまらなかった。

自社の技術変更履歴が「報告された RCE」と書くものを、経営トップが存在しないと述べた組織の対応

2026年11月13日、Pavel Durov 氏は自身のチャンネルに次のように書いた（出典5。本記録の作成者が直接取得。訳。原文英語）。

「問題は存在しない。」「メッセージを受け取っただけでハックされうる者はいなかった。」「まず利用者が自分で第三者のサービスを起動する必要があった。」「それも含めてサーバ側で完全に修正済みである。」「そう思わないなら私のアカウントをハックしてみろ: t.me/monk」

正しい部分を先に置く（本記録の整理）。

前提条件の指摘は、公表仕様と整合する。本番環境でウィジェットはボットとの1対1の対話でしか動かず、送信されたウィジェットは自動的に protected content となり転送できない（出典1・2）。「メッセージを受け取っただけで」無関係な利用者が巻き込まれる経路は、公表仕様の上では存在しない。 この点について Durov 氏の記述は正しい。報道の見出しが「どんなメッセージも RCE になる」に寄っていたのに対し、訂正としては妥当な中身である（本記録の評価）。

しかし「問題は存在しない」は、自社の技術変更履歴と矛盾する（本記録の評価）〈重要〉。

Telegram のウィジェットサンドボックスの変更履歴（出典3）は、同じ週に次のように書いている。

  • v0.6.1（11月6日）: RegExp 削除の修正について「これが報告された RCE である」
  • v0.6.4（11月10日）: await using について「ウィジェットのスクリプトからのネイティブコード実行として報告された」、「素のウィジェット JS から到達可能な use-after-return」
  • v0.6.4: 他の5件について「5件の use-after-free と領域外アクセスの修正。いずれもサンドボックスより下、素のウィジェット JS から到達可能」

（いずれも訳。原文英語。）

同じ組織が、エンジニアの文書では「到達可能な RCE」と書き、経営トップの発信では「存在しない」と書いている。しかも同じ投稿で「サーバ側で完全に修正済み」とも述べている—— 存在しないものは修正できない（本記録の明示）。

言いたかったのが「報じられたような形では存在しない」であるなら、その区別は投稿には書かれていない（本記録の確認）。

「私のアカウントをハックしてみろ」についても一言置く（本記録の評価）。これは脆弱性の有無を決める材料にならない。特定のアカウントを落とせないことは、実装の不備が存在しないことの証明ではない。報奨金の額も条件も示されていない（本記録の確認）。

実務上の帰結はひとつである〈重要〉。利用者と組織は、更新すべきかどうかを提供元の広報からは判断できない。判断に使える一次情報は、GitHub のサンドボックス変更履歴（出典3）だけであった。本記録が2026年11月15日に確認した時点で、Bot API の変更履歴にウィジェットのセキュリティ修正に触れた記載は無く（出典1）、ウィジェットのドキュメントに「セキュリティ」の節は無い（出典2）。

対話の中にコード実行の面が増えたこと自体が、組織の判断材料になる評価・解釈

以下は本記録の評価である。

本件で塞がれた不備は複数だが、変わったのは不備ではなく構成である。

これまでメッセージングアプリで任意のコードが動く場所は、概ね「別アプリ」「別画面」として分離されていた（Mini Apps 等）。Bot API 10.4 以降、Telegram ではそれが対話の中に入った（出典1）。利用者の視点では、画面の中にあるのはメッセージである。「怪しいリンクを開かない」「アプリを入れない」という従来の指導は、この面に対しては空振りする——開くリンクもインストールもない。

残る前提条件は1つだけである。利用者がそのボットを起動すること（出典5）。これはアプリのインストールよりはるかに軽い動作である（本記録の評価）〈重要〉——検索して /start を押すだけで終わる。軽い動作の先にネイティブコード実行の面があるという非対称が、本件の構成上の要点である。

組織にとっての問いは「今回の不備は直ったか」ではない。前者は版を上げれば終わる。問うべきは「対話の中でコードが動く面を、自組織の端末で許すか」である。

同じ問いは Telegram に限らない。メッセージングやコラボレーションの製品が、対話の内側にスクリプトの実行面（カード・ウィジェット・埋め込みアプリ・AI の道具呼び出し）を増やす流れは続いている。判断の材料は「隔離が堅いか」ではなく「その面を無効化できるか」「無効化したとき業務が止まるか」である（本記録の評価）——本件のウィジェットについて、利用者側で切る設定は公表されていない〈未確定9〉。

なお、2026年11月13日に対話内のウィジェットが動かなくなったとの報告がある（出典7）。Telegram は停止の有無・範囲・復帰時期を公表していない〈未確定5〉—— 機能そのものが一時的に引っ込められた可能性があるが、確認できない。 これも組織の側から見れば「頼れない」という同じ判断材料になる（本記録の評価）。

侵入を防げた業務端末で利用を許可するボットを列挙し、それ以外の起動を運用で禁じる　**本記録の評価による。** 本件の前提条件は利用者のボット起動である（出典5）。 **技術的に強制する手段は公表されていないため運用と教育に頼る** ——**その分、確実性は低い**（本記録の明示）。

実行現実的な検知機会なし
**本記録の評価である。** 利用者から見えるのはメッセージである。 **ウィジェットの内容は32KB 以内の HTML で、 外部リソースを一切読み込まない設計のため**（出典2）、 **外向き通信としても観測できない。** **端末に EDR を入れていても、アプリ内のスクリプト実行は 通常の検知対象にならない。**
影響を限定できた組み込みスクリプトエンジンの実行を、別プロセス＋権限分離の内側に置く　**本記録の評価による。** Telegram は修正でまさにこれを行っている—— **Android 13.2.2 でウィジェットの実行を 「Telegram のファイルにもネットワークにも触れない独立した隔離プロセス」へ移し、 新規プログラム起動を封じた**（出典7）〈重要〉。 **これは提供元側の対策であり、利用組織が取れる策ではない**（本記録の明示） ——**製品を選ぶときの確認項目として持つ意味がある。**
検知回避公表されていない
**公表されていない。** Telegram は検知の経緯を述べていない。 **変更履歴は「報告された」と書くが報告者名も報告日も示していない** （出典3）〈未確定3〉—— **誰がいつ見つけたのかが分からないため、 発見から修正までの期間も測れない**（本記録の確認）。
影響を限定できた隔離は破られる前提で、破られた後の到達範囲を設計で絞る　**本記録の評価による。** ネットワークを切り DOM を代理 API に置き 描画をプロファイルで濾しても、**エンジンが壊れればその制約も壊れる** （出典3 の記述）。 **プロセスの権限・ファイルへの到達・OS の API 呼び出しを 個別に落としておくことが、実効のある層になる**
検知できた同梱した上流部品の監査・issue を追跡する経路を持つ　**本記録の評価による。** `await using` の不備は **上流 QuickJS-ng の公開 issue として2026年11月9日に出ていた**（出典4）。 **上流に修正を配る仕組みが無い部品では、 追跡していない組み込み側は気づけない**（本記録の評価）
影響（暗号化・破壊・改ざん）検知した
**本件では利用者の目に見える形で起きた**（本記録の評価）—— **電卓アプリが自分で開けば利用者は気づく。** **ただしこれは実演の演出である**（本記録の明示）〈重要〉—— **実際の攻撃者が、利用者に見える動作を選ぶ理由は無い。** **見えない動作（データの読み出し・待機）を選べば、 検知の機会は「現実的に無い」側へ戻る。**
影響を限定できた業務領域と私用領域を端末上で分離する（作業プロファイル・管理対象アプリ）　**本記録の評価による。** Android の作業プロファイルで分ければ、 私用側の Telegram から業務側のアプリ・データへ到達できない。 **本件が私用の Telegram で起きても業務データに届かない構成になる**
復旧を早められたアプリの版を資産台帳に持ち、プラットフォームごとに修正の到達を確認する　**本記録の評価による。** 本件の対策は更新のみで、 **CVE 番号が無いため脆弱性スキャンには載らない**〈未確定1〉〈重要〉。 **判定は版番号（Android 13.2.2 以降／Desktop 7.4.3 以降）で行う必要があり、 しかもリリース説明は「小さな改善」としか書かれていない**（出典7）

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**技術変更履歴（GitHub）では到達可能な RCE と hardening を区別して詳細に書く一方、 経営トップは公式チャンネルで「問題は存在しない」と述べた**（出典3・5）。 **利用者向けのリリース説明は「バグ修正とその他の小さな改善」であった**（出典7）。部分的に機能**本記録の作成者の評価である。** **技術水準の開示は、同種の事案の中ではむしろ厚い**（本記録の評価）〈重要〉—— **自社のサンドボックス変更履歴で「これが報告された RCE である」と 書く提供元は多くない**（出典3）。 **問題は、その内容と広報が噛み合っていないことである。** **「問題は存在しない」と「サーバ側で完全に修正済み」が同じ投稿に並び**（出典5）、 **変更履歴は「到達可能な RCE」と書いている**（出典3）。 **前提条件の指摘自体は公表仕様と整合しており正しい**（出典1・2）が、 **「報じられたような形では存在しない」という区別が書かれていないため、 利用者は更新すべきかを判断できない**（本記録の評価）。
**到達可能な不備を把握してから数日で修正を出した** （v0.6.1 は11月6日、v0.6.4 は11月10日。出典3）—— **ただしプラットフォーム間で到達が3日ずれ**（出典7）、 **セキュリティ修正であることを示す告知は行っていない**（本記録の確認）。部分的に機能**本記録の作成者の評価である。** **修正の速さは評価できる**—— **「報告された RCE」は機能の全面開放より3日前に塞がれており**（出典1・3）、 **V12 の公開実演の前日には `await using` も修正されている**（出典3・7）。 **評価を partial にとどめた理由は2つである**〈重要〉。 **①プラットフォーム間の3日のずれ**（出典7）—— **「全プラットフォームが影響を受けた」としながら**（出典8）、 **デスクトップ版の修正は Android の3日後である。** **②機能の全面開放（11月9日）の当日に27件の監査指摘が公開され、 翌日に到達可能な不備6件が修正されている**（出典3・4）—— **点検が終わる前に届く場所へ置いた順序は、修正の速さでは埋められない。**
CISO・経営層への示唆
  • 業務連絡に使うメッセージングが「対話の中でコードが動く面」を持ったとき、 問うべきは不備が直ったかではなく、その面を自組織で許すかである。
    **Bot API 10.4 以降、Telegram ではネイティブコード実行に至りうる面が 対話の内側に入った**（出典1・3）〈重要〉—— **利用者から見えるのは「ただのメッセージ」である。** **「怪しいリンクを開かない」「アプリを入れない」という従来の指導は、 この面に対しては空振りする**——開くリンクもインストールも無い。 **残る前提条件は利用者がボットを起動することだけで**（出典5）、 **これはアプリのインストールよりはるかに軽い動作である。**
    取るべき行動 業務で使用を認めているメッセージング・コラボレーション製品について、 **①対話の内側でスクリプトが動く機能があるか、 ②管理者が無効化できるか、 ③無効化したとき止まる業務があるか**の3点を棚卸しする。 **無効化できない製品は、業務データに到達できない領域 （作業プロファイル・管理対象アプリ）へ隔離する前提で方針を決める。**
  • 提供元の広報と技術変更履歴が食い違う場合、更新判断は技術変更履歴の側に合わせる。
    **本件では経営トップが「問題は存在しない」と述べた一方**（出典5）、 **自社のウィジェットサンドボックス変更履歴は 「これが報告された RCE である」（v0.6.1）、 「ウィジェットのスクリプトからのネイティブコード実行として報告された」 「素のウィジェット JS から到達可能な use-after-return」（v0.6.4）と 書いている**（出典3。訳）〈重要〉。 **利用者向けのリリース説明は「バグ修正とその他の小さな改善」であった**（出典7）。
    取るべき行動 **重要な業務に使う製品については、広報チャネルだけでなく 変更履歴・コミット・公開 issue を見る経路を1本持つ。** **広報と技術文書が食い違ったときは、修正が出ている側に合わせて更新する** ——説明は後から変わるが、出た修正は撤回されない。
  • マルチプラットフォーム製品では「修正済み」を製品単位で受け取らない。 プラットフォーム単位・版単位で確認する。
    **Telegram は「この fork をビルドしている全プラットフォームが影響を受けた」と している**（出典8）が、**修正の到達は Android が11月10日、 デスクトップが11月13日で3日ずれている**（出典7）〈重要〉—— **間の 7.4.2（11月11日）には当該修正が入っていない。** **本件で「Telegram は直した」は正しいが、 「自分の Telegram は直った」は11月11日のデスクトップ利用者には 当てはまらなかった**（本記録の評価）。
    取るべき行動 **資産台帳をアプリ単位ではなく「アプリ×プラットフォーム×版」で持つ。** **脆弱性対応の完了判定を、ベンダーの「修正済み」告知ではなく 自組織の版の分布で行う。** **配布経路が複数ある製品（ストア版・直配布版）は、経路ごとに把握する。**
  • CVE 番号が割り当てられない不備は、既存の脆弱性管理の仕組みに乗らない。
    **本件には CVE 番号も CVSS も無い**〈未確定1〉—— **脆弱性スキャン・パッチ台帳・SBOM による照合は、 いずれも識別子を鍵に動く仕組みである**（本記録の評価）。 **番号が無い不備は「対応済み／未対応」の集計に現れない。** **本件で判断に使える一次情報は GitHub の変更履歴だけであった**（出典3）。
    取るべき行動 **CVE の有無に関わらず「最新版かどうか」で判定できる経路を1本用意する。** スマートフォンのアプリは特に抜けやすい—— **MDM で版を取得できる範囲と、私用端末で取得できない範囲を把握しておく。** **重要部品については、上流リポジトリの変更履歴・issue を 人が読む運用を割り当てる。**
  • オープンソース部品の監査結果は、上流が応答しなくても下流に影響する。 自社が「下流」である自覚を持つ。
    **QuickJS-ng の監査 issue #1902 には、2026年11月15日時点で 保守者からの応答が無い**（出典4。本記録の観測）〈重要〉—— **応答したのは利用者側（Telegram の開発者）であり、 修正コミットも fork 側のものである**（出典4）。 **小規模なオープンソース部品には、修正を配る仕組みが備わっていないことがある** （本記録の評価）—— **その場合「修正されたか」は組み込んだ製品ごとにばらばらになる。**
    取るべき行動 **自社製品・自社が使う製品の重要部品について、 上流に「修正を配る仕組み」があるかを確認する** （セキュリティ連絡先・勧告の発行・リリース方針）。 **無い部品については、自社が上流の issue を追う責任を負うと決めて 担当を割り当てる。** 「上流が直してくれる」を前提に置かない。
セキュリティ技術者への示唆
  • サンドボックスの検査は、その下で動くエンジンのメモリ安全性が前提である。 エンジンが壊れれば検査も壊れる。
    **Telegram 自身がこう書いている**（出典3。訳）〈重要〉—— **「パーサのメモリ安全性の不備は、あらゆるサンドボックスの検査より下にある エンジンの射程に入る」。** **到達可能とされた不備は、いずれも「素のウィジェット JavaScript から到達可能」 とされており**（出典3）、**特別な権限も仕様の穴も要らない。** **ネットワーク無効・画面遷移不可・描画のプロファイル照合・資源上限という 多層の制約があっても**（出典2）、**それらを課す側のコードが壊れる。**
    取るべき行動 **自社製品に組み込みスクリプトの実行面を持つなら、 「エンジンが破られた場合、そのプロセスから何に到達できるか」を数える。** ファイル・ネットワーク・OS の API・親プロセスのメモリを個別に列挙する。 **言語水準の制約を、OS 水準の隔離（別プロセス・権限分離・syscall 制限）で 裏打ちする**——**Telegram の修正はまさにこれである**（出典7）。
  • 組み込みの JavaScript / スクリプトエンジンは依存部品として版管理する。 同梱すると SBOM に載らず、上流の修正が自動で届かない。
    **`await using` の不備のもとになったコードは2026年5月16日に 上流 QuickJS-ng の main へ、明示的資源管理の対応と一緒に入った**（出典8） 〈重要〉——**修正までは178日である**（本記録の算出）。 **不備は、それを到達可能にする機能（ウィジェット・11月5日）より 半年早く置かれていた。** **QuickJS のような小規模エンジンは、パッケージマネージャ経由ではなく ソースを同梱・fork する形で取り込まれることが多く、 依存関係の一覧に現れにくい**（本記録の評価）。
    取るべき行動 **自社製品に同梱しているスクリプトエンジン・パーサ・正規表現エンジン・ 画像/フォントのデコーダを列挙し、上流の版と取り込んだ版を記録する。** **fork した時点で版が凍結されるため、追随の責任がどこにあるかを決める。** **新機能で既存の同梱部品を「外部入力に触れる位置」へ動かすときは、 その部品の点検を機能の前提条件に入れる。**
  • 新しい実行面を公開する前に、その面の下にある部品の点検を終える。 修正の速さでは順序の誤りを埋められない。
    **本件の順序はこうである**（出典1・3・4）〈重要〉。 **11月6日に「報告された RCE」を修正 → 11月9日に全ボットへ開放 → 同日に27件の監査指摘が公開 → 11月10日に 「サンドボックスより下、素のウィジェット JS から到達可能」な不備6件を修正。** **対応は速いが、点検が終わる前に届く場所へ置いている**（本記録の評価）。
    取るべき行動 **新しい入力経路・実行面を開く前に、その経路が触る部品の ①公開 issue、②既知の監査、③上流の最近の変更を確認する。** **段階的な開放（テスト環境 → 限定公開 → 全面開放）を使い、 全面開放の判断条件に「部品の点検完了」を明文で入れる。** **緊急停止（フィーチャーフラグ・サーバ側での無効化）を機能と同じ回で用意する** ——**本件でも Durov 氏は「サーバ側で完全に修正済み」としている**（出典5）。
  • 対話の内側で動く実行面は、ネットワーク監視からも EDR からも見えない。 検知に期待せず、到達範囲の設計で抑える。
    **ウィジェットは外部リソースを一切読み込まない設計であり、 外向き通信としても観測できない**（出典2）〈重要〉。 **Telegram の通信は暗号化されており、 組織のネットワーク監視から見えるのは「Telegram を使っている」ところまでである** （本記録の評価）。 **アプリ内のスクリプト実行は、端末側 EDR の通常の検知対象でもない。**
    取るべき行動 **検知ではなく分離で対処する。** Android の作業プロファイルや iOS の管理対象アプリで業務領域と私用領域を分け、 **私用側のメッセージングから業務側のアプリ・データへ到達できない構成にする。** **「本件が私用の Telegram で起きても業務データに届かない」状態を作る。**
  • 実演や PoC の派手さで深刻度を判断せず、到達できた範囲で評価する。
    **実演では電卓アプリが自動的に開く**（出典6）——**利用者が気づく形である。** **しかし実際の攻撃者が、利用者に見える動作を選ぶ理由は無い** （本記録の評価）〈重要〉—— **見えない動作（データの読み出し・待機・後続の取得）を選べば、 利用者も監視も気づかない。** **修正版で封じられたのが「ウィジェットのプロセスからの新規プログラム起動」 である点にも注意が要る**（出典7）—— **実演で起きたのはまさにその動作であり、 それ以外の到達範囲は公表されていない**〈未確定9〉。
    取るべき行動 **評価の軸を「到達できた範囲」（プロセスの権限・触れるファイル・使える API）に置く。** **到達範囲が公表されていない場合は、最大だった前提で分離を設計する。** **PoC が無い監査指摘（本件の指摘3 がそれである）も、 実在する到達可能な不備を含みうるため、PoC の有無で優先度を決めない**（出典4）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 自社の製品・サービスが、外部から受け取ったコンテンツを 組み込みのスクリプトエンジン（QuickJS・QuickJS-ng・Duktape・JerryScript・Lua 等） や独自のパーサで処理している。
委託・第三者部品□ 自社製品に、パッケージマネージャを経ずソースを同梱または fork する形で スクリプトエンジン・パーサ・デコーダを取り込んでいる。
委託・第三者部品□ 業務で使うメッセージング・コラボレーション製品が、 対話やチャネルの内側でスクリプトを実行する機能 （ウィジェット・カード・埋め込みアプリ・AI の道具呼び出し）を持っている。
運用・監視□ 業務端末のアプリについて「アプリ名」までは把握しているが、 プラットフォーム別・版別の分布を集計できない。
運用・監視□ 従業員の私用端末・私用アカウントでのメッセージング利用を業務に使っており、 業務領域と私用領域が端末上で分離されていない。
体制・契約□ 利用している製品の脆弱性情報を、提供元の公式告知・広報のみを経路として 受け取っている。
