INC-2026-1083UnrealIRCd の欠陥が悪用・KEV 収載

UnrealIRCd の labeled-response モジュールが IRCv3 の label タグを エスケープせず応答に差し込んでいた——**サーバが2台以上つながった網では、 特権を持たない一般利用者が改行を注入してサーバ間コマンドを送り込み、 サーバ権限で実行できた**（CVE-2026-114713・CVSS 8.6・CWE-140）。 開発者は2026年11月7日に 6.2.7.1 と無停止のホットパッチを出し、 **CISA は11月13日に KEV へ収載した（期限11月16日）**

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備既知の脆弱性の悪用
初報: 2026年11月7日（UnrealIRCd 6.2.7.1 の公開と告知） 最終更新: 2026年11月15日

2026年11月7日、UnrealIRCd の開発者 Bram Matthys（Syzop）が6.2.7.1 と無停止のホットパッチを公開した（出典2・3）。直した脆弱性は9件で、そのうち1件が CRITICAL とされた（出典2・3）。それが CVE-2026-114713 である。

欠陥は IRCv3 の「label」メッセージタグの扱いにあった（出典1・2）〈重要〉。labeled-response モジュールは、クライアントが付けた label タグを応答に反映する作りだが、その値をエスケープしていなかった（出典1）—— 利用者が label に改行を混ぜると、サーバ間通信（server-to-server）に任意の行を差し込める。 差し込まれた行はサーバの権限で解釈されるため、KILL や GLINE といった運用者向けのコマンドが通る（出典2）。

成立の条件は「サーバが2台以上つながっていること」だけである（出典1）〈重要〉—— 攻撃する側に運用者権限は要らない。普通に接続した一般利用者でよい。 CVSS 3.1 は 8.6（HIGH）で、ベクタはAV:N/AC:L/PR:N/UI:N/S:C/C:N/I:H/A:N——完全性への影響が高く、スコープが変化する（S:C）という形である（出典1）。開発者自身は「この15年の UnrealIRCd で最も重大な問題」と書いている（出典2）。

影響は 6.0.0 以降 6.2.7.1 未満の全て（出典1）。既に保守が終わっている UnrealIRCd 5 も、この CRITICAL の件については影響を受ける（出典2）—— 5 系の保守終了は2023年7月1日である。 3.2.x・4 は開発者が確認しておらず、「いくつかの不具合は 3.2.x まで遡ると思われる」としている（出典2）。

そして2026年11月13日、CISA がこれを KEV（Known Exploited Vulnerabilities）カタログへ収載した（出典4）〈重要〉—— FCEB 機関の期限は11月16日、収載から3日である。 同日に Check Point の CVE-2026-123039 も同じ期限で収載されている（出典4・6）〈関連: INC-2026-1062〉。

本記録として、この事案の読みどころは2つある（本記録の判断）。第1に、これは「境界に置いた機器」の話ではなく「社内に立てたチャットサーバ」の話である—— IRC は古い技術だが、研究所・OSS コミュニティ・一部の運用現場でいまも動いている。 第2に、修正のための無停止ホットパッチと、パッチを当てられない場合の回避策（モジュールの無効化・SPAMFILTER）が開発者から同時に出されている（出典1・2）〈重要〉—— 「落とせないから当てられない」を理由にできない形で提示されている。

**公表されている「悪用の経路」は1段で完結する**（出典1・2）〈重要〉—— **網に接続した一般利用者が、IRCv3 の label タグに改行を含む値を入れて コマンドを送る。サーバがその値をエスケープせずに応答へ反映し、 結果としてサーバ間通信に任意の行が差し込まれる。 差し込まれた行はサーバの権限で解釈される。** **本記録は、実際の攻撃の観測記録を持っていない**（本記録の明示）〈未確定1〉—— **以下は「開発者と CVE レコードが示した悪用の形」であり、 特定の被害事案の再構成ではない。**

  1. 1. 実行[1] [2]
    **クライアントが IRCv3 の「label」メッセージタグに 改行などの区切り文字を含む値を付けてコマンドを送る**（出典1）。 **labeled-response モジュールは、応答にこの label を反映する際に 値をエスケープしない**（出典1。原文英語を訳出）—— **その結果、サーバが組み立てる応答の中に、 利用者が決めた改行から先の行が混ざる。**

    **差し込まれた行は、サーバ間（server-to-server）の通信として 解釈される**（出典1・2）〈重要〉—— **したがって、特権を持たない利用者の操作が 「サーバ権限」で実行される。** **開発者は、実行できるものの例として KILL（利用者の強制切断）と GLINE（ネットワークからの追放）を 挙げている**（出典2）。 **CVSS のベクタで S:C（スコープの変化）・I:H（完全性への高い影響）と されているのはこの性質を指す**（出典1。本記録の整理）。

権限の要らない注入が、サーバの権限に化けた原因・手口出典 [1] [2] [4]

欠陥の形は、言葉にすると単純です（出典1・2）。

IRCv3 には「label」というメッセージタグがあります。 クライアントが要求に札を付け、サーバが応答にその札を返すことで、どの応答がどの要求に対するものかを紐づける仕組みです。 labeled-response モジュールがこれを担っています。

問題は、サーバが札の中身を検査せずに応答へ書き戻していたことでした（出典1・原文英語を訳出）—— 「labeled-response モジュールは、IRCv3 の label メッセージタグを応答に反映する際にエスケープしない」。

IRC のプロトコルは行で区切られます。 したがって札に改行を混ぜれば、そこから先は別の行になります（出典1・2）。そして、その行が流れる先がサーバ間（server-to-server）の通信でした—— サーバ間通信で流れるコマンドは、サーバの権限で解釈されます。

成立条件は「サーバが2台以上つながっていること」だけです（出典1）〈重要〉。攻撃する側に必要なのは運用者権限ではなく、その網に接続できる一般利用者の立場です。 開発者は、実行できるものの例としてKILL（利用者の強制切断）と GLINE（ネットワークからの追放）を挙げています（出典2）。

CVSS 3.1 は 8.6（HIGH）、ベクタはAV:N/AC:L/PR:N/UI:N/S:C/C:N/I:H/A:N（出典1）。S:C（スコープの変化）が付いているのは、「利用者の権限で行ったことがサーバの権限になる」というこの性質そのものを指します（本記録の整理）。CWE は CWE-140——区切り文字の不適切な無害化です（出典1・4）。

本記録として強調したいのは、これが「入力検査の漏れ」ではなく「出力時のエスケープの欠落」だという点です（本記録の評価）〈重要〉。受け取った値そのものは不正ではありません。 不正になるのは、それを別の文法（サーバ間プロトコル）の文にそのまま埋め込んだ瞬間です。 同じ構造は SQL でも、シェルでも、ログでも起きます。 「値を受け取る側」ではなく「文を組み立てる側」の責務です。

日本の組織に BOD の義務はありません（本記録の明示）。それでも、この6日と3日という数字は目安として使えます（本記録の評価）。本件では、無停止で当てる手段が修正公開の時点で揃っていました（出典2・3）—— 「当てる手段が無かった」は本件では成り立ちません。

本記録として、もう1つ指摘しておきます（本記録の判断）〈重要〉。KEV に入ったのは CVE が付いた1件だけです。 同じ 6.2.7.1 には、CVE の無い8件が入っています（出典2・3）—— そのうち2件は、利用者の IP を暴く欠陥です（出典2）。「KEV に入った1件を当てる」ための更新が、結果として8件も直している。 逆に言えば、KEV を入口に動く運用では、何を直したのかを自分で確かめないと分かりません。

恒久対策は2つです（出典2）。

  • ホットパッチ: 全サーバで ./unrealircd hot-patch bundle-20261107 を実行する。再起動は不要
  • 更新: *NIX では ./unrealircd upgrade のあと再起動。または 6.2.7.1 を unrealircd.org から取得する

適用の確認は./unrealircd module-status | grep labeled-response です（出典2）。5.0-hot-patch-bundle-20261107 が出ればホットパッチ済み、6.2.7.1 が出れば修正版で動いており、5.0 だけなら未適用です（出典2）。

逃げ道は2つ（出典1・2）。

1つめは SPAMFILTER です（出典2）。運用者（IRCOp）として、不正な label タグに一致する正規表現を設定します。 ただし開発者は、はっきりこう書いています（出典2・原文英語を訳出）—— 「この回避策がネットワークを CRITICAL の件から守るのは、全てのサーバが 6.0.4 以降で動いている場合のみである。」

2つめはモジュールの無効化です（出典1・2）。各サーバの設定に blacklist-module "labeled-response"; を書きます。 UnrealIRCd 5 では、全サーバに書いたうえでrehash ではなく restart が必要です（出典2）。

影響を限定できたリンクする網の構成を把握し、 全サーバの版を揃える（最も古い1台を残さない）　**本記録の評価**〈重要〉—— **成立条件が「サーバが2台以上」であり、 回避策の有効性が「全サーバが 6.0.4 以降」であることから**（出典1・2）、 **網の版の不揃いが、そのまま攻撃面と対策の穴になる。**

CISO・経営層への示唆
  • CVE 番号を入口にする脆弱性管理では、同じ更新に入っている修正の大半が見えない
    **6.2.7.1 は9件の脆弱性を直しているが、 CVE が付いたのは1件だけである**（出典2・3）〈重要〉。 **CVE の無い8件には、利用者の IP を暴く2件が含まれる**（出典2）。 **cloak（ホスト名の隠蔽）を前提に運用している網では、 これは匿名性の破れそのものである**（本記録の評価）。
    取るべき行動 **自組織の脆弱性管理の入口を書き出し、 「CVE の購読」だけで回っている資産を特定する。** **OSS を使っている資産については、 CVE ではなくプロジェクトの告知（リリースノート・ メーリングリスト）を購読先に加える。** **「CVE が無いから対象外」という判定を、運用規程から外す。**
  • 保守が終わった版は、修正が出ないという一行で済む話ではない
    **UnrealIRCd 5 はこの CRITICAL の件の影響を受けるが、 保守終了は2023年7月1日で修正版は出ない**（出典2）。 **選べるのはモジュールの無効化か、6 系への移行だけである** （出典2。本記録の整理）。 **3.2.x・4 は開発者が影響を確認しておらず、 「影響の有無が分からない」状態に置かれている**（出典2）。
    取るべき行動 **保守終了済みのソフトウェアの一覧に、 「重大な欠陥が出たときに選べる手段」の欄を足す。** **移行計画が無い資産については、 「無効化できる機能はどれか」を事前に調べておく。** **調べていない場合、緊急時の判断材料がゼロになる。**
  • 期限は「当てる期限」ではなく「調べる期限」でもある
    **CISA の KEV は、緩和策の適用に加えて BOD 26-04 とフォレンジック・トリアージ要件への適合を求めている** （出典4）〈重要〉。 **本件は「利用者の操作がサーバ権限で実行される」欠陥であり、 当てる前に通られていた場合、 痕跡は「正規の運用コマンドの記録」の中にある**（本記録の評価）。
    取るべき行動 **重大な脆弱性への対応手順に、 「適用」と並んで「適用前の期間に悪用された痕跡を探す」工程を置く。** **本件で探す対象は、発行元の運用者が説明できない KILL・GLINE・ban の記録である。** **探せるかどうかは、その記録を機器の外に出しているかで決まる。**
  • 社内で動いている「古いが現役」の通信基盤を、資産台帳の外に置いていないか
    **IRC は古い技術だが、研究所・OSS コミュニティ・ 一部の運用現場でいまも動いている**（本記録の評価）。 **本件の成立条件は「サーバを2台以上リンクしていること」であり、 攻撃には一般利用者の立場しか要らない**（出典1・2）。
    取るべき行動 **チャット・通知・ボット連携など、 「業務システム」の枠に入っていない常時稼働の通信基盤を棚卸しする。** **それぞれについて、運用者・版・リンク先・更新の経路を記録する。** **担当者が1人しかいない基盤は、その人の不在時の手順まで決める。**
セキュリティ技術者への示唆
  • エスケープは「入力を受け取るとき」ではなく「文を組み立てるとき」に行う
    **本件は、受け取った label タグの値をそのまま サーバ間プロトコルの文に埋め込んだことで成立した**（出典1）〈重要〉。 **値そのものは不正ではない—— 不正になるのは、別の文法の文に埋め込んだ瞬間である**（本記録の整理）。 **CWE-140（区切り文字の不適切な無害化）はこの型である**（出典1・4）。
    取るべき行動 **自分のコードで、利用者由来の文字列を 「行区切りのプロトコル」「ログ」「シェル」「SQL」に 組み立てている箇所を列挙する。** **組み立てる関数の側でエスケープを行う実装になっているかを確認し、 呼び出し側の作法に依存している箇所を直す。** **とくに「反射して返すだけ」の値を安全と見なしていないか確認する。**
  • 無停止で当てる手段があるかどうかを、平時に確かめておく
    **本件のホットパッチは再起動を要さない**（出典2・3）〈重要〉。 **開発者は公開の3日前に事前告知を出し、 「いまのうちにホットパッチの試験を回しておくこと」を勧めている**（出典3）。 **常時接続の利用者を抱える基盤では、 「落とせない」が当てない理由になりやすい**（本記録の評価）。
    取るべき行動 **担当している常時稼働のソフトウェアについて、 無停止の修正手段（ホットパッチ・ローリング更新）があるかを調べ、 平時に1回実際に試す。** **試した結果（所要・影響・失敗時の戻し方）を手順書に残す。** **本件の確認コマンドにあたるもの—— 「当たったかどうかを確かめる1行」——も手順に含める。**
  • 回避策の有効範囲は、網の中で最も古い1台が決める
    **SPAMFILTER による回避策は、 「全てのサーバが 6.0.4 以降で動いている場合のみ」有効と 開発者が明記している**（出典2・原文英語を訳出）〈重要〉。 **攻撃の成立条件も「サーバが2台以上リンクしていること」である**（出典1）。
    取るべき行動 **リンク・クラスタを組んでいる基盤について、 ノードごとの版の一覧を取る（製品名と最新版だけでは足りない）。** **回避策を適用するときは、 その前提条件を満たさないノードが無いかを先に確認する。** **満たさないノードがある場合、回避策が効いていないものとして扱う。**
  • サーバ権限で実行された操作の記録を、そのサーバの外に出す
    **本件の帰結は「サーバ権限での正規の操作」である**（出典1・2）。 **操作自体は機能として正しいため、 異常として見えるのは「誰が出したか説明できない」という点だけになる** （本記録の評価）。
    取るべき行動 **運用者権限・サーバ権限で実行される操作の記録を、 機器の外のログ基盤へ転送する。** **発行元（どの運用者のセッションか）を記録に含める。** **「発行元が特定できない特権操作」を検知の対象として定義する。**

自組織に当てはまるか

委託・第三者部品□ 保守終了済みの OSS を本番で使っており、重大な欠陥が出たときの選択肢を事前に調べていない**UnrealIRCd 5 は影響を受けるが修正版は出ない**（出典2）。 **選べるのはモジュールの無効化か移行だけであり、 どちらも事前の調査が要る**（出典2。本記録の整理）。
