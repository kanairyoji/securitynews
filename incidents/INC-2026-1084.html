INC-2026-1084PostgreSQL が52件修正・14 終了

PostgreSQL が2026年11月12日、**52件の脆弱性**を一度に修正した—— 中核は型の取り違え CVE-2026-6460（CVSS 8.8）で、 **オブジェクトを作成できる利用者が `ALTER ... SET DATA TYPE` を使い、 データベースを動かす OS 利用者の権限で任意コードを実行できた**。 **完全な保護には C 言語拡張の再ビルドが要り、一部は原本の修正も要る**。 同時に PostgreSQL 14 が保守終了となった

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月12日（PostgreSQL Global Development Group の公開告知） 最終更新: 2026年11月15日

2026年11月12日、PostgreSQL Global Development Group が18.7・17.12・16.16・15.20・14.25 と 19 RC 2 を公開した（出典1）。直した脆弱性は52件、不具合は140件以上である（出典1）〈重要〉。

中核は CVE-2026-6460（CVSS 3.0 で 8.8）である（出典2）。型の取り違え（type confusion）であり、主な経路は ALTER ... SET DATA TYPE——オブジェクトを作成できる利用者が、データベースを動かしている OS 利用者の権限で任意のコードを実行できる（出典2。原文英語を訳出）。ベクタは AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H で、必要な権限は「低」（PR:L）である（出典2）。

この1件には、当てるだけでは終わらない条件が付いている（出典3）〈重要〉。18.7 のリリースノートはこう書いている（原文英語を訳出）—— 「完全な保護のためには、この変更は C 言語拡張の再ビルドを必要とし、また原本（ソースコード）の修正を要する拡張もいくつか存在する。」 検査を無効化する新しいサーバパラメータ composite_type_mismatch も用意されたが、リリースノートは「そうすることはセキュリティ上のリスクを伴う」と明記している（出典3）。

もう1つ、この更新には期限の意味がある（出典1）〈重要〉。14.25 は PostgreSQL 14 の最後のリリースである—— 以後、14 系はセキュリティ修正も不具合修正も受けない。 告知は「本番で使っている利用者は、サポートされている版への更新を計画すべきである」と記す（出典1）。

52件という数は、それ自体が読みどころである（本記録の評価）。CVSS 8.8（遠隔・低権限で任意コード実行に至る形）が32件、8.0 以上が35件ある（出典1。計数は本記録）。そして CVE-2026-6460 の謝辞には、個人の研究者に加えて OpenAI Security Research Team・Anthropic の OSS プログラム・Claude・Ada Logics が並んでいる（出典3）—— ただし「どの CVE が、どの取り組みから出たのか」は公表されていない〈未確定2〉。

報道は本件を「22年前の不具合」と見出しにしている（出典4）〈差異1〉。一次資料にその年数の記載は無い（出典1・2・3。本記録の確認）—— リリースノートの表現は「我々は長らく検査を持っていた」である（出典3）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**公表されているのは「悪用の形」であり、 観測された攻撃の記録ではない**（本記録の明示）〈重要〉〈未確定1〉。 **セキュリティ頁とリリースノートが示す形はこうである**（出典2・3）—— **オブジェクトを作成できる利用者が `ALTER ... SET DATA TYPE` （または `ALTER TABLE ... ADD COLUMN; ROLLBACK; ALTER TABLE ... ADD COLUMN` のような手順）を実行する。 古い行の配置のタプルや、データ辞書・PL/pgSQL の変数に残った古い値が、 新しい型の記述子で解釈される。 その取り違えを使って、データベースを動かしている OS 利用者の権限で 任意のコードが実行される。**

  1. 1. 実行[2] [3]
    **オブジェクトを作成できる利用者が、型を変える操作を行う**（出典2・3）。 **主な経路は `ALTER ... SET DATA TYPE`**（出典2）。 **リリースノートは、危険の本体を 「`ALTER TABLE ... ALTER COLUMN TYPE` のような操作は、 古い行の配置のタプルがシステム内に残り得るため危険である」と説明し、 従来の検査が「複合型が、それを使う問い合わせと同時に 変更される場合をまったく検出できていなかった」と記す** （出典3。原文英語を訳出）〈重要〉。 **古い値はデータ辞書の項目・PL/pgSQL の変数などに残る**（出典2）。
  2. 2. 権限昇格[2]
    **型の取り違えを使い、データベースを動かしている OS 利用者の権限で任意のコードが実行される**（出典2。原文英語を訳出）〈重要〉—— **「この方法で実行されたコードは、 データベースを動かしているオペレーティングシステム利用者の 権限を持つ。」** **つまり帰結はデータベースの中に留まらない**（本記録の整理）—— **典型的な構成では postgres 利用者であり、 データディレクトリの全体と、その利用者で到達できる資産が範囲になる。**

必要なのは管理者権限ではなく「表を作れること」だった原因・手口出典 [2] [3]

CVE-2026-6460 の要点は、必要な権限の低さです（出典2）。

セキュリティ頁はこう書いています（原文英語を訳出）—— 「PostgreSQL の中核サーバにおける型の取り違えの欠陥により、オブジェクトの作成者が、データベースを動かしているオペレーティングシステム利用者として任意のコードを実行できる。主な経路は ALTER ... SET DATA TYPE である。」

CVSS 3.0 は 8.8、ベクタはAV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H です（出典2）。PR:L——低い権限で足ります。 要るのは「オブジェクトを作成できる利用者」であって、スーパーユーザーではありません。

原因は型の追跡の作りそのものです（出典2・3）。セキュリティ頁は「型付きの値の追跡が不十分であり、値が自己識別的でなかった」と記します（出典2・原文英語を訳出）。リリースノートはより踏み込んでいます（出典3・原文英語を訳出）—— 「ALTER TABLE ... ALTER COLUMN TYPE のような操作は、古い行の配置のタプルがシステム内に残り得るため危険である。我々は長らくこれを防ぐための検査をいくつか持っていたが、それらは完全なものでは決してなく、複合型が、それを使う問い合わせと同時に変更される場合をまったく検出できていなかった。」

主な経路のほかに、こうした手順も挙げられています（出典2）—— ALTER TABLE ... ADD COLUMN; ROLLBACK; ALTER TABLE ... ADD COLUMN。 古い値が、データ辞書の項目や PL/pgSQL の変数に残り続けることで、取り違えが悪用可能になります（出典2）。

本記録として強調したいのは、帰結がデータベースの外に出ることです（本記録の整理）〈重要〉。「この方法で実行されたコードは、データベースを動かしているオペレーティングシステム利用者の権限を持つ」（出典2・原文英語を訳出）。典型的な構成では postgres 利用者です。 したがって、当てはめの問いは「データベースに何が入っているか」ではなく「postgres 利用者で何に手が届くか」になります。

当てても「完全な保護」にならない——拡張の再ビルドが要る再発防止出典 [1] [3]

この更新には、当てた後の作業が付いています（出典1・3）〈重要〉。

CVE-2026-6460 の修正は、タプル記述子と合わない複合データを検出するための版管理の仕組みを導入するものです（出典3）。そしてリリースノートはこう続けます（原文英語を訳出）—— 「完全な保護のためには、この変更は C 言語拡張の再ビルドを必要とし、また原本の修正を要する拡張もいくつか存在する。」

逃げ道も用意されていますが、警告付きです（出典3・原文英語を訳出）—— 「必要であれば、新しい composite_type_mismatch サーバパラメータを使ってこれらの検査を無効化できるが、そうすることはセキュリティ上のリスクを伴う。」 本記録はこれを「回避策」ではなく「一時的な退避」と読みます（本記録の整理）—— 修正そのものを止める操作です。

さらに、互換性の変更があります（出典3）。ALTER COLUMN TYPE の依存関係の規則が厳しくなり、これまで通っていた文が拒否されることがあります。

不具合修正の側にも、作業を要するものが並んでいます（出典1）。

  • GIN インデックス — 破損が疑われる場合は REINDEX INDEX
  • pg_trgm — gist_trgm_ops を使う GiST インデックスは再作成
  • missing chunk number が出る表 — REINDEX TABLE（TOAST 表も併せて再作成される）
  • 増分バックアップ — 新しい完全バックアップを取り直し、以後の増分の基礎にする
  • パーティション表 — NOT NULL NO INHERIT 制約を pg_constraint で確認し、不要なものを削除する
  • bpchar の B-tree インデックス — 長さ指定の無い列のものは再作成（char(n) は対象外）

本記録として、ここが本件の実務上の中心だと見ます（本記録の判断）〈重要〉。小規模更新は累積的で、ダンプ・再読み込み・pg_upgrade は不要です（出典1）—— 「止めてバイナリを置き換えて再起動」で済みます。 しかしこの更新に限っては、そこで終わると①拡張経由の経路が残り、②インデックスの破損が残り、③増分バックアップが使えないままになります。

さらに、更新を飛ばしていた場合は「飛ばした分のリリースノートに追加の作業が書かれている」とされています（出典1）—— 溜めた分だけ作業が増える構造です。

14.25 が PostgreSQL 14 の最後のリリースになった対策・注意喚起出典 [1]

この更新には、もう1つの意味があります（出典1）〈重要〉。

「これは PostgreSQL 14 の最後のリリースである。以後、セキュリティ修正も不具合修正も受けない。本番で使っている利用者は、サポートされている版への更新を計画すべきである」（出典1・原文英語を訳出）。

つまり 14.25 を当てた時点で、その系は終点に達します（本記録の整理）。次に 14 系の脆弱性が出ても、修正は出ません。 次回以降、保守中の系は 18・17・16・15 の4つになります（本記録の整理）。

そして今回、その「次の脆弱性」がどれだけ出るかの目安があります（本記録の評価）〈重要〉。1回の更新で52件です（出典1）。CVSS 8.8（遠隔・低権限で任意コード実行に至る形）が32件、8.0 以上が35件、7.0 以上が38件、5.0 未満は9件でした（本記録の計数）。

14 系を本番で使い続ける判断をする場合、比較すべきはこの数字です（本記録の判断）—— 「いま困っていないか」ではなく「次の52件を当てられないまま運用するか」です。

なお PostgreSQL 19 の正式公開は2026年11月19日が予定されています（出典1）—— 「遅延や追加の候補版が必要にならない限り」。 19 RC 2 には、この更新のうち 19 に該当する修正が含まれています（出典1）。19 へ移行する場合、全文検索・pg_trgm・fuzzystrmatch を使ったインデックスがあると再インデックスが必要になる可能性があると案内されています（出典1）。

「22年前」は一次資料に無い——謝辞に並ぶ名前のほうが読みどころか未確定事項出典 [1] [2] [3] [4]

    取るべき行動 **主要なデータベースについて 「稼働している OS 利用者で何に手が届くか」を書き出させる。** **バックアップの書き込み先の認証情報、 他サーバへの SSH 鍵、クラウドのキーがその利用者から読めるなら、 分離の計画を立てる。** **この一覧は、脆弱性が出る前に作る。**
  • 「オブジェクトを作成できる利用者」を数えていない組織は、影響範囲を答えられない
    **悪用に必要な権限は CREATE であり、管理者権限ではない**（出典2）。 **CVSS のベクタも PR:L である**（出典2）。 **受託開発・分析用途・一時的な検証のために CREATE を広く与えている系では、前提が満たされている**（本記録の評価）。
    取るべき行動 **本番のデータベースごとに、 CREATE 権限を持つロールと利用者の一覧を出させる。** **「アプリケーションの接続ロールが CREATE を持っているか」を 個別に確認する（持っている構成は珍しくない）。** **一覧が出てこない系は、それ自体を課題として扱う。**
  • 保守終了は「当てた日」が終点になる——数字で判断する
    **14.25 は PostgreSQL 14 の最後のリリースであり、 以後は修正が出ない**（出典1）〈重要〉。 **その「次に出るであろう脆弱性」の量は今回の数字で見える—— 1回の更新で52件、CVSS 8.8 が32件である**（出典1。計数は本記録）。
    取るべき行動 **保守終了が近い基盤ソフトウェアの一覧に、 「直近の更新で何件の脆弱性が直ったか」の欄を足す。** **延命の判断は「いま困っていないか」ではなく 「その件数を当てられないまま運用するか」で行う。** **移行の予算要求にも、この数字をそのまま使う。**
  • 更新作業の見積もりに「当てた後の作業」を入れていないと、対応が中途で止まる
    **本件は「バイナリを置き換えて再起動」で終わらない**（出典1・3）〈重要〉。 **C 言語拡張の再ビルド（一部は原本の修正も要る）、 複数種類の再インデックス、増分バックアップの取り直しが 公表された必要作業に含まれる**（出典1・3）。
    取るべき行動 **緊急更新の手順書に「当てた後の作業」の欄を設け、 リリースノートの該当箇所を貼り付ける運用にする。** **拡張を使っている系については、 拡張の提供元への確認を誰が行うかを決めておく。** **「当て終わった」の定義を、再起動ではなく この欄が埋まったことにする。**
セキュリティ技術者への示唆
  • アプリケーションの接続ロールから CREATE 権限を外す
    **悪用の前提は「オブジェクトを作成できる利用者」である**（出典2）〈重要〉。 **権限が分離されていれば、 この脆弱性の前提そのものが満たされない**（本記録の評価）。 **移行（マイグレーション）のために CREATE を与えたまま 運用しているアプリケーションは多い**（本記録の評価）。
    取るべき行動 **アプリケーションの接続ロールの権限を確認し、 CREATE を持っていれば外す。** **スキーマの変更は、別のロール・別の実行経路 （移行専用のジョブ）に限定する。** **外せない場合は、その理由と代替の歯止めを記録に残す。**
  • C 言語拡張の棚卸しを、更新の前提作業として持つ
    **「完全な保護のためには C 言語拡張の再ビルドが必要で、 一部は原本の修正も要る」とリリースノートが明記している**（出典3）〈重要〉。 **どの拡張が原本の修正を要するかは公表されていない**〈未確定4〉。
    取るべき行動 **各データベースに導入されている拡張を `\dx` などで一覧化し、C 言語で書かれたものを特定する。** **それぞれの提供元・版・入手経路・ビルド手順を記録する。** **この一覧が無いと、今回のような修正のときに 「当てたが保護されていない」状態を自分で検出できない。**
  • データベースのプロセスからの子プロセス生成と外向き通信を観測点にする
    **帰結が OS 利用者の権限での任意コード実行である**（出典2）。 **`ALTER ... SET DATA TYPE` 自体は正規の DDL であり、 実行の記録だけでは悪性を判定できない**（本記録の評価）〈重要〉—— **判定の手がかりは「誰が実行したか」であって「何を実行したか」ではない。**
    取るべき行動 **データベースの稼働利用者からの子プロセス生成を記録・警報の対象にする （通常は発生しない構成であれば実装しやすい）。** **データベースサーバからの外向き通信を既定拒否にし、 必要な宛先だけを許可する。** **DDL の実行記録に、実行したロールを必ず含める。**
  • 検査を無効化するパラメータは「退避」として扱い、期限と記録を付ける
    **`composite_type_mismatch` で検査を無効化できるが、 リリースノートは「セキュリティ上のリスクを伴う」と明記している** （出典3）〈重要〉。 **無効化した状態でどこまで悪用可能なのかは公表されていない** 〈未確定5〉。
    取るべき行動 **やむを得ず無効化する場合は、 設定した日・理由・解除の期限・承認者を記録に残す。** **拡張の再ビルドが完了したら必ず戻す。** **「設定したまま忘れる」を防ぐため、 構成の点検項目にこのパラメータを加える。**
  • 他人が作ったダンプを復元する手順を見直す
    **CVE-2026-116314（CVSS 8.8）は 「pg_restore が非プレーン形式の書庫の検証を欠き任意コードを実行する」 ものである**（出典1）〈重要〉。 **移行・検証・障害復旧の場面では、 自分が作ったのではない書庫を扱うことがある**（本記録の評価）。
    取るべき行動 **ダンプの復元を行う手順を洗い出し、 「書庫の出所」が確認されているかを点検する。** **信頼できない書庫を扱う必要がある場合は、 使い捨ての環境で復元する手順に変える。** **復元を行う利用者の権限も、あわせて最小化する。**
