韓国の中小ベンチャー企業部（중소벤처기업부。以下「中企部」）が主管する創業支援事業「第2次 모두의 창업（みんなの創業）」で、参加企業の1社から個人情報が流出したと、同部が2026年11月13日午後5時8分に公表しました（出典1。文書は本記録では確認できていません〈差異1〉）。

流出が起きたのは、第2次事業に参加する AI ソリューション企業「아미쿠스렉스」（Amicus Rex。AI による法律文書作成サービス「로폼」を運営）が独自に運営するシステムです。報道によれば、

  • 同社が保有していた個人情報 20,028名分が流出した
  • そのうち818名が第2次「모두의 창업」の参加者だった
  • 流出した項目は、氏名・電話番号・メールアドレスの3つ
  • 中企部の説明では、参加者の創業アイデアは流出していない

とされています（出典2・3・4）。

手口は、管理者ページに対する SQL インジェクション攻撃です。同社の流出届出書には「管理者ページから SQL インジェクション攻撃による一部情報の窃取の試みが確認され、措置として脆弱な API コードの削除を行った」と記載されていたと報じられています（出典2・3。原文韓国語・訳は本記録）。

本事案が韓国で問題になっているのは、同じ事業で2度目であるためです。 2026年6月に第1次事業の公式プラットフォームから約5,000名の情報が流出し、中企部と창업진흥원（創業振興院）は「サーバ API のセキュリティ不備により、ウェブクローリングと特定の API 呼び出しを通じて挑戦者プロフィールや審査評などが流出した」と診断していました（出典2）。同部はシステムの全面補完と厳格な企業選抜を約束し、2026年10月には AI・ソフトウェアの専門家で評価委員会を構成し、技術力と安全性を精査して50社のソリューション企業を選抜したと強調していました（出典2・3）。その選抜から約1か月で、選ばれた企業の1社から同種の経路（脆弱な API）で流出が起きたことになります。

もうひとつの論点は、公表までの時間です。届出書上の発生時刻は11月11日午前5時38分、同社の認知が同日午前8時30分、KISA（韓国インターネット振興院）への届出が同日午後3時45分。一方、中企部が公式に発表したのは11月13日午後5時8分で、発生から約60時間、KISA の届出受付から49時間が経っていました（出典2・3）。中企部は「今回侵害が起きたのは民間企業が独自に運営するシステムであり、事業の公式プラットフォームとは別個である」「事故企業から12日午後6時10分ごろに事故の事実を通報された。現在、正確な経緯の把握と追加被害の遮断のための後続措置を進めている」と説明しています（出典2。原文韓国語・訳は本記録）。

CISO・経営層への示唆
  • 公的事業・共同事業に参加すると、自社が「他人の個人情報を預かる側」になる
    本事案で流出した20,028名のうち818名は、同社の顧客ではなく **政府事業の参加者**である（出典3・4）。 **事業に参加する側は、自社サービスの利用者だけを見ていると 預かっている情報の範囲を見誤る**（本記録の評価）
    取るべき行動 参加している公的事業・共同事業・コンソーシアムを棚卸しし、 **それぞれで自社システムに入ってくる「他組織の参加者情報」の項目・件数・ 保持期間を一覧にする。** 事業ごとに、事故時の報告先（当局とは別に 事業の事務局）と報告期限を契約・要領から抜き出して書き留める
  • 当局への法定届出は、事業の主管官庁や取引先には回らない
    本事案では KISA への届出（11月11日15時45分）から事業の主管官庁への通報 （11月12日18時10分ごろ）まで**約26時間**あった（本記録の算出）〈重要〉。 **法定の届出を期限内に済ませても、事業側は知らない状態が続く**
    取るべき行動 事故時の連絡先リストを「当局」「取引先・委託元」「事業の事務局」「本人」に 分けて作り、**それぞれの期限を別々に決める。** インシデント対応手順の中に「当局届出と同時に委託元へ通報する」工程を 明示的に置く（届出の完了をもって報告済みと扱わない）

セキュリティ技術者への示唆
  • 管理画面は、インターネットから到達できる前提をやめる
    本事案の侵入点は**管理者ページ**である（出典2・3）。 **管理画面は権限が強く、持ち出せるデータの範囲が広い** （本記録の評価）——**そこが外から到達できる状態は、 SQL インジェクション1つで全件に届く構成を意味する**
    取るべき行動 管理画面・管理系 API の到達範囲を実測する（外部の回線から URL を叩く）。 **社内ネットワーク・VPN・許可 IP に限定し、 限定できないものは一覧にして理由を残す。** 併せて管理画面に多要素認証を要求する
  • SQL インジェクションは「残っていないこと」を検査で示す

    取るべき行動 事故で見つかった脆弱性について、**「同じ書き方をしている箇所」を コード全体から探す工程を復旧手順に組み込む。** 見つかった件数を記録し、修正済み・未修正・意図的に残すものを分けて管理する
  • 管理画面から引ける個人情報の件数に上限をかけ、大量読み出しを検知する
    本事案では20,028名分が流出している（出典3・4）。 **管理画面が全件を一度に引ける設計なら、 侵入が1回成功するだけで全件が出る**（本記録の評価）
    取るべき行動 管理画面・管理 API の1回あたりの取得件数に上限を設け、 **上限を超える読み出しをログに残して警報を出す。** エクスポート機能は操作者・件数・条件を監査ログに記録する
  • 事故の発生時刻を分単位で言えるだけのログを持つ
    同社は届出書に**発生時刻を11月11日午前5時38分と分単位で記載できた** （出典2・3）〈重要〉。 **これは評価できる点である**（本記録の評価）—— 発生時点が特定できなければ、流出範囲も絞れない
