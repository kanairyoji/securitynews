INC-2026-1098ArcticRAT・AI で資産を選別

**Android マルウェア「ArcticRAT」が、暗号資産アプリ利用者向けのスパイウェアから 129 コマンドを備えた遠隔操作型（RAT）へ拡大した**（Zimperium zLabs が2026年11月12日に公表）。 **窃取した SMS と導入済みアプリの一覧を xAI の Grok API へ送り、 ワンタイムコード・残高変動・送金通知を抜き出させ、 標的の「資産の厚み」を推定させる**（出典1）〈重要〉。 **端末には画面を真っ黒にしたまま遠隔操作する隠し VNC があり、 Android 11 以降の「ワイヤレスデバッグ」を悪用して特権シェルを取り、 画面ロックの消去・再設定まで行う**（出典1）。 **被害件数・標的地域・攻撃者の帰属はいずれも公表されていない**〈未確定1〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**Zimperium の記述から整理した経路である**（出典1。整理は本記録）。 悪性広告・SMS・第三者フォーラムから Google Play を模した偽ページへ誘導し、 ドロッパーを導入させる。 ドロッパーは VPN 権限を取って通信を宛先なしに落とし、 Google Play Protect の遠隔測定を目隠しした状態でペイロードを導入する。 ペイロードはアクセシビリティ権限を足場にし、 さらに Android 11 以降のワイヤレスデバッグを悪用して特権シェルを得る。 そのシェルで自らアクセシビリティを有効化し、画面ロックを消去・再設定できる。 収集した SMS と導入済みアプリの一覧は xAI の Grok API へ送られ、 ワンタイムコードや残高の抽出と「資産の厚み」の推定が行われる。 最終段では、黒い覆いで画面を隠したまま隠し VNC で端末を操作する。 **観測された被害の規模・標的・攻撃者の帰属は公表されていない**〈未確定1・2〉。

窃取情報の選別を外部の生成AIに委ねたため、攻撃者側に解析の実装が要らなくなった評価・解釈出典 [1]

ArcticRAT は、集めた情報を自分で解析しない。

C2 が <xAI_API> 指示と API キーを端末へ送ると、マルウェアはapi.x.ai/v1/chat/completions を呼び、モデル grok-4.20-0309-non-reasoning に2種の仕事をさせる（出典1）。

  • 導入済みアプリの一覧を読ませ、銀行・暗号資産・証券のアプリを選り出させる
  • 受信した SMS を読ませ、広告を捨て、ワンタイムコード・残高の変動・送金の通知を抜き出させ、さらに標的の資産状況を推定させて JSON で返させる

結果は端末内の /storage/emulated/0/config/AI_DATA/ に蓄え、<Get_AI_ANA_Data> で回収する（出典1）。

この作りの要点は、攻撃者が解析の実装を持たないことである（本記録の評価）〈重要〉。従来、盗んだ SMS の山から使えるコードを抜き、「この端末の持ち主に資産があるか」を見立てる作業は人手か自作の規則だった。それを API 呼び出し1本に置き換えている。

防御側から見ると、痕跡が薄くなる（本記録の評価）。端末に残るのは api.x.ai への通常の HTTPS 通信であり、悪性ドメインの名簿には載らない宛先である。マルウェア固有の文字列も、プロンプトの中にしか現れない。

運用に落とすなら、業務端末から生成AI の API 宛へ出る通信を「どのアプリが出しているか」まで把握しておくことが、本件に限らない検知の足場になる（本記録の推奨）。

端末の完全制御は脆弱性ではなく、正規の権限と開発者向け機能の積み上げで成立している原因・手口出典 [1]

ArcticRAT が端末を握るまでの道筋に、OS の脆弱性は出てこない（出典1。本記録の確認）。

  1. 偽の Google Play ページからドロッパーを導入させる（利用者の操作）
  2. ドロッパーが VPN 権限を取り、通信を宛先なしに落としてPlay Protect の遠隔測定を目隠しする（利用者の許可）
  3. ペイロードがアクセシビリティ権限を得る（利用者の許可）
  4. ワイヤレスデバッグ（Android 11 以降の開発者向け機能）を悪用し、mDNS 探索と6桁コードの TLS ペアリングで特権シェルを取る
  5. そのシェルから enable_accessibility_services を実行し、以降は利用者の操作なしに権限を付け外しできる
  6. locksettings で画面ロックを検証・消去・再設定し、所有者を締め出す

3 から 5 の転換が本件の肝である（本記録の評価）〈重要〉。一度シェルを取れば、以後の権限付与は「利用者に許可を求める」経路を通らない。利用者教育で止められるのは 1 から 3 までで、そこを越えられると端末側に止める手段が残らない。

したがって対策は MDM の構成側に寄る（本記録の推奨）——提供元不明のアプリの導入禁止、開発者向けオプション／ワイヤレスデバッグの禁止、アクセシビリティを使うアプリの許可制。いずれも「後から入れた端末」には効かないため、業務で使う端末を管理下に置けているかが前提になる。

なお Zimperium のレポートは自社製品（MTD 等）の推奨で閉じており、構成プロファイルによる封じ方には触れていない（本記録の注記）。

画面が真っ黒な間に操作されるため、利用者が気づく手がかりは端末の外にしか残らない評価・解釈出典 [1]

隠し VNC の作りはこうである（出典1）。

<screen_runrun> が MediaProjection と VirtualDisplay でメモリ上の仮想ディスプレイを作り、<START_CAPTURE> で取り込みを始め、JPEG のフレームを[Header]|[Timestamp]|[JPEG Size]|[Width]|[Height] のヘッダ付きで 8888/tcp に流す。同時に解除できない黒い覆いを画面に重ね、輝度を 0 にする。

Zimperium は、この状態の端末が利用者には「ロック中または電源が切れているように見える」と記している（出典1。原文英語を訳出）。

つまり、不正な操作が行われている最中、端末の画面は何も語らない（本記録の評価）〈重要〉。偽のロック画面（<Phsing>）も本物と見分けがつかず、端末内のログは攻撃者の管理下にある。

気づく手がかりは端末の外にしか残らない（本記録の整理）——口座側の取引の異常、普段と違う認証の成功、送金先の変化。本件のような型に対して、端末側の「不審な挙動に気づく」教育は効かない。

組織としての備えは、端末の外に置く検知と、被害が成立するまでの時間差（送金の上限・時間差・追加確認）になる（本記録の推奨）。

被害の規模と攻撃者は示されていない——「129 コマンド」は能力の記述であって被害の記述ではない未確定事項出典 [1] [3]

Zimperium が公表したのは、試料と能力の分析である（出典1）。

示されている数は、試料 78 件（ドロッパー 42・ペイロード 36）、コマンド 129 件、C2 の IP 21 件、当初狙われた暗号資産アプリ 11 件である（出典1）。

示されていないのは、感染端末数・被害額・標的の国や地域・攻撃者の帰属である〈未確定1・2〉。

C2 の所在はおよそ3分の2が香港、20% がドイツとされるが（出典1）、これは借りた基盤の所在であり、攻撃者の所在の根拠にはならない（本記録の留保）〈重要〉。Dark Reading は見出しで "Cybercrime Gang" としているが、集団の特定には踏み込んでいない（出典3）。

本DBがここを分けて書くのは、「129 コマンドを持つ」が「129 の被害が出た」と読まれうるためである（本記録の整理）。能力の棚卸しは、何が起こりうるかを示す。何が起きたかは示さない。

日本の利用者が標的に含まれるかも公表されていない（本記録の確認）。したがって本記録は、本件を「日本への脅威」として評価しない ——有名事象として記録するに留める。

AI が攻撃側に入った意味は「新しい手口」ではなく「手口の単価が下がったこと」にある評価・解釈出典 [1]

ここは本記録の解釈である（確度: presumed）。

ArcticRAT が生成AI でやっていることは、新しい攻撃ではない。SMS からワンタイムコードを抜く、資産のありそうな標的を選ぶ——どちらも以前から行われてきた作業である（本記録の整理）。

変わったのはその作業に必要な作り込みの量である（本記録の評価）〈重要〉。自作の正規表現や辞書を言語ごとに整備する代わりに、API キーを端末へ配り、プロンプトを2本書けば済む。攻撃者側の実装負担が下がると、同じ品質の攻撃がより多く出てくる。

Zimperium は AI 連携を備えた試料を2026年7月中旬ごろから確認しており（出典1）、v6.3 から v6.5.2 への更新が続いている。実装が軽いことは、改訂の速さとしても現れる（本記録の推定）。

防御側の含意は2つある（本記録の推奨）。

  • SMS によるワンタイムコードを前提にした認証は、「読まれない」前提をもう置けない。フィッシング耐性のある方式へ移す動機になる。
  • 「標的を選ぶ」工程が自動化されるため、「自社は小さいから狙われない」という想定が崩れる。選別は攻撃者の手間ではなくなった。

緩和策
手順: **業務端末で「提供元不明のアプリの導入」と「開発者向けオプション／ ワイヤレスデバッグ」を MDM の構成プロファイルで禁止する**（本記録の推奨。 Zimperium のレポートにこの具体の推奨は無い）。　副作用: **業務アプリの社内配布（サイドロード）を使っている組織では配布経路の作り直しが要る** （本記録の評価）—— **開発・検証用の端末は例外扱いの台帳が必要になり、 その例外がそのまま穴になりやすい**（本記録の評価）〈重要〉。
手順: **アクセシビリティサービスを有効にしているアプリを棚卸しし、 業務上許可するものを明示の許可制にする**（本記録の推奨）。　副作用: **実際に支援技術を必要とする利用者の利便を損なう余地がある**（本記録の評価）—— **「アクセシビリティを一律に禁止する」運用は取れないため、 許可制の維持に継続的な手間がかかる。**
手順: **暗号資産・銀行・証券アプリを業務端末と同一端末で使わせない方針を明示する** （本記録の推奨）。　副作用: **私物端末の利用（BYOD）を前提にしている組織では強制できず、 方針の宣言に留まる**（本記録の評価）—— **端末を分けても、SMS を受ける回線が同じなら ワンタイムコードの窃取は成立する**（本記録の注記）〈重要〉。
手順: **ワンタイムコードを SMS で受ける方式から、 フィッシング耐性のある方式（FIDO2／パスキー）へ移す**（本記録の推奨）。　副作用: **対応していない取引先サービスが残り、二重運用になる**（本記録の評価）—— **移行の判断は業務側と合わせる必要があり、短期では終わらない。**
手順: **Zimperium が公開した IoC（出典2）を自組織の通信ログと突き合わせる**（出典2）。　副作用: **IoC は借りた基盤の IP とハッシュであり、入れ替われば当たらなくなる** （本記録の評価）〈重要〉—— **本DBの方針として、抽出された IoC は悪性を自前で検証しておらず、 照合先のテレメトリが無いため検知の根拠には使わない。**

CISO・経営層への示唆
  • SMS で受けるワンタイムコードを「読まれない」前提で使うのをやめる判断の材料になる。 本件は端末上の SMS を生成AI に読ませてコードだけを抜き出している。
    **ArcticRAT は受信した SMS を xAI の API へ送り、 広告を捨ててワンタイムコード・残高変動・送金通知を抜き出させている**（出典1）〈重要〉。 **抽出の実装を攻撃者が持たなくてよくなったため、 言語や書式の違いが障壁にならない**（本記録の評価）。
    取るべき行動 **重要な業務システムの二要素認証を SMS からフィッシング耐性のある方式 （FIDO2／パスキー）へ移す計画を立て、移せない取引先サービスを一覧にする。** **移行が終わるまでの間は、送金・権限変更の操作に別経路の確認を挟む。**
  • 「自社は小さいから狙われない」という想定を置き直す。 標的の選別が攻撃者の手間ではなくなっている。
    **本件は導入済みアプリの一覧と SMS を生成AI に読ませ、 銀行・暗号資産・証券アプリの利用者を抽出し、 標的の資産状況まで推定させている**（出典1）〈重要〉。 **選別が自動化されると、母数を広く取って後から絞る攻撃が成立しやすくなる** （本記録の評価）。
    取るべき行動 **「狙われるほどの規模か」を前提にしたリスク評価の記述を見直し、 従業員個人の端末・口座が入口になる経路を評価の対象に加える。**
  • 業務で使うモバイル端末が MDM の管理下にあるかを、台数で把握する。 本件の有効な対策はほぼ構成プロファイル側にある。
    **侵入から特権取得までの経路に OS の脆弱性は無く、 提供元不明のアプリの導入・VPN 権限・アクセシビリティ権限・ ワイヤレスデバッグという正規の機能の積み上げで成立している**（出典1）〈重要〉—— **これらは MDM で禁止できるが、管理外の端末には効かない**（本記録の評価）。
    取るべき行動 **業務データに触れるモバイル端末の台数と、うち MDM 管理下の台数を出す。** **差が出た分について、業務アクセスを止めるか管理下に入れるかを期限付きで決める。**
  • 端末の画面が攻撃者の管理下に入る型では、検知を端末の外に置くしかない。
    **隠し VNC は解除できない黒い覆いと輝度 0 を併用し、 「ロック中または電源が切れているように見える」状態で操作する**（出典1。 原文英語を訳出）〈重要〉。 **偽のロック画面も本物と見分けがつかない**（出典1）—— **利用者の「不審に気づく」能力に頼る設計は成立しない**（本記録の評価）。
    取るべき行動 **不正操作の検知を、端末ではなく業務システム側（認証の異常・操作の異常）に置く。** **送金・出金・権限変更に上限と時間差を設け、被害が成立するまでの猶予を作る。**
セキュリティ技術者への示唆
  • 業務端末から生成AI の API 宛へ出る通信を、アプリ単位で把握できるようにする。 本件の持ち出しは api.x.ai への通常の HTTPS 通信として現れる。
    **C2 が API キーを配り、端末が api.x.ai/v1/chat/completions を直接呼ぶ**（出典1）〈重要〉。 **宛先は正規のサービスであり、悪性ドメインの名簿では当たらない**（本記録の評価）—— **一方で「どのアプリが生成AI の API を叩いているか」を見ていれば、 アプリでもブラウザでもない呼び出しとして見える**（本記録の整理）。
    取るべき行動 **業務端末の外向き通信で生成AI 系 API の宛先を許可制にし、 呼び出し元のアプリとともに記録する。** **併せて 9999/tcp・8888/tcp など生 TCP の外向き通信を遮断する。**
  • MDM の構成遵守チェックに「開発者向けオプション／ワイヤレスデバッグが有効」を 違反として入れる。
    **ArcticRAT は Android 11 以降のワイヤレスデバッグを悪用し、 mDNS 探索と6桁コードの TLS ペアリングで特権シェルを取る**（出典1）。 **シェルを取った後は enable_accessibility_services をシェルから実行し、 利用者の操作なしに権限を付けられる**（出典1）〈重要〉—— **この転換を越えられると端末側に止める手段が無い**（本記録の評価）。
    取るべき行動 **MDM で開発者向けオプションとワイヤレスデバッグを禁止し、 有効化を違反として検知して業務アクセスを止める構成にする。** **開発・検証用の例外端末は台帳に載せ、期限を切る。**
  • アクセシビリティサービスを有効にしているアプリの棚卸しを行う。
    **本件はアクセシビリティ経由で資格情報と二要素コードを収集し、 偽のロック画面を重ね、画面の覆いを制御する**（出典1）〈重要〉。 **アクセシビリティは画面の読み取りと操作の両方を許す権限であり、 1つ許すと端末の操作全体が見える**（本記録の整理）。
    取るべき行動 **業務端末でアクセシビリティを使うアプリを許可制にし、 許可した理由と見直し時期を記録する。** **支援技術を必要とする利用者向けには、例外を個別に承認する経路を用意する。**
  • アプリの導入中に VPN の許可を求める挙動を、検知の着眼点として覚えておく。
    **ドロッパーは VPN 権限を取り、0.0.0.0/0 と ::/0 を宛先なしに落として 「導入の段階で Google Play Protect の遠隔測定を事実上目隠しする」** （出典1。原文英語を訳出）〈重要〉—— **利用者に見えるのは VPN の許可画面だけである**（本記録の整理）。
    取るべき行動 **MDM で業務外アプリによる VPN プロファイルの作成を禁止・監査する。** **利用者向けの注意喚起には「アプリの導入中に VPN の許可を求められたら中断する」を 具体の挙動として入れる。**
  • 公開された IoC は突き合わせに使うが、検知の根拠にはしない。
    **出典2 の IoC は借りた基盤の IP とハッシュであり、入れ替われば当たらない** （本記録の評価）。 **C2 の IP はレポート内で 21 件と 17 件が併存しており、 数そのものも確定していない**（出典1）〈齟齬1〉—— **本DBの方針として、抽出された IoC は悪性を自前で検証しておらず 照合先のテレメトリも無いため検知には使わない。**
    取るべき行動 **IoC は過去ログの遡り照合（既に通信していなかったかの確認）に使い、 遮断名簿への恒久登録はしない。** **検知は挙動側（ADB 有効化・アクセシビリティ付与・生 TCP の外向き通信）に寄せる。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ 業務データに触れる Android 端末があり、MDM で 「提供元不明のアプリの導入」と「開発者向けオプション／ワイヤレスデバッグ」を 禁止していない。
認証・認可□ 重要な業務システムの二要素認証を SMS のワンタイムコードで行っている。
システム構成□ 私物端末（BYOD）から業務システムへ接続でき、端末の構成を組織が把握していない。
運用・監視□ 端末から外へ出る通信を宛先別に記録しておらず、 生成AI の API 宛の通信を呼び出し元アプリとともに把握していない。
体制・契約□ 不正操作の検知を端末側の「利用者が不審に気づく」ことに依存した設計になっている。
