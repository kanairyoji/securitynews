INC-2026-1100Coway 空清が平文HTTPで根証明書

**空気清浄機 Coway Airmega IconS は、信頼の起点となるルート証明書を 平文の HTTP で毎回取りに行き、ファームウェアにルート証明書を1枚も持っていない** （研究者 Scott J. Goldman が2026年11月11日に自身のブログで公表）。 **置き換えた証明書を機器がそのまま信頼するため、 HTTPS 通信の中身が見え、MQTT（8883/tcp）の指令も読める状態だった**（出典1）〈重要〉。 **さらに Bluetooth の設定パケットに「証明書サーバの URL」が入っているため、 設定を行える者は機器の信頼の起点そのものを差し替えられる**（出典1）。 **Coway による公表・修正の告知は確認できなかった**〈齟齬1〉—— **攻撃には通信路上の位置または設定モード中の近接が要り、遠隔からの悪用ではない** （本記録の評価）。

トラストアンカーを持たない機器は、起動のたびに「誰を信じるか」を外から教わる原因・手口出典 [1] [3]

本件で最も重いのは、通信が平文だったことではない。

機器のファームウェアにルート証明書が1枚も入っていないことである（出典1。原文英語を訳出）〈重要〉。

そのため機器は、信頼の起点となる Amazon のルート CA 証明書を平文の HTTP（S3 上の rootca-fs.iocareus.com）で毎回取りに行く（出典1）。著者はこのファイルを自前の CA 証明書に差し替えただけで、以降の HTTPS 通信の中身を読めるようになった。「最初からずっと中間者攻撃が可能だった」（出典1。原文英語を訳出）。

ここで区別が要る（本記録の評価）。Hacker News では、最も多く支持された反論が「HTTP で証明書を配ること自体は問題ではない。問題は検証していない証明書を暗黙に信頼することである」だった（出典3。原文英語を訳出）。公開鍵基盤では、証明書チェーンを HTTP で配ること（AIA）は通常の作りである。

本記録もこの整理に同意する（本記録の評価）。HTTPS にしても、取得した証明書を検証しないままなら同じことが起こる。逆に、ファームウェアにトラストアンカーを持ち、取得したものの署名を確かめていれば、経路が HTTP でも成立しない。

一方で、HTTPS に意味が無いわけでもない。議論では「署名検証に不備があったときの層になる」「観測者に見える情報が減る」という指摘も出ている（出典3）。多層としての HTTPS は有効だが、それは本件の代替にはならない（本記録の整理）。

組込み機器でこの形が採られる事情についても推測が挙がっている——組み込んだ証明書が期限切れになって出荷済みの機器が動かなくなるのを避けたかった、第三者 SDK が TLS を要求する一方で長期の更新を許さない契約だった、など（出典3）。いずれも確認されていない。Coway の説明は無い〈未確定2〉。

設定を行える者が信頼の起点を決める——暗号は盗聴を防ぐが、相手を確かめていない評価・解釈出典 [1] [2]

より射程の長い指摘は、Bluetooth の初期設定のほうにある（出典1。本記録の評価）。

著者が解析した手順はこうである（出典1）。

  1. キャラクタリスティック FFA0 から機器の識別情報（MAC アドレスを含む）を読む
  2. ランダムな20文字の鍵を含む "P001" を FFA2 へ書き込む
  3. その鍵と、12文字の大文字の MAC アドレスを組み合わせて AES 鍵を導く
  4. "P002" を FFA2 へ送る——protobuf で包み、PKCS#7 でパディングし、AES で暗号化した Wi-Fi 設定

設定パケットの中身には、Wi-Fi の SSID・パスワード・BSSID・MAC・CA の URL・証明書サーバの URL・登録トークン・製造番号が入っている（出典1）〈重要〉。

つまり設定を行う側が、機器の信頼の起点を指定できる。著者は「自前のサーバを立てて、扇風機の設定時にその URL を入れてやればよい」と書き、実際にそうした（出典1・2）。中間者の位置を取る必要すらない。

暗号の役割も見ておく（本記録の整理）。AES 鍵の材料の片方（MAC アドレス）は、手順1 で平文で読める値である。秘密は「その場で生成される20文字の鍵」だけで、これは設定する側が決める。したがってこの暗号は、傍受に対する保護であって、「正しい設定者かどうか」の確認にはなっていない（本記録の評価）〈重要〉。

現実の脅威の形は限られる（本記録の評価）。設定には機器を設定モードにする操作（本体のボタン長押し）とBluetooth の到達距離が要るため、遠隔からの一斉悪用には向かない。問題になるのは、家庭内・事務所内に入れる者、そして中古品・貸与品・退去後の機器である。機器を初期化しても、第三者が仕込んだ URL が消えるかは分からない——リポジトリも「アドレスやポートを変えると各機器の再設定が必要」と記すだけで、第三者の設定を消す手順には触れていない（出典2。本記録の確認）。

発見は脆弱性調査の副産物だった——クラウドが壊れることが動機だった背景・過去事例出典 [1] [4]

著者の目的は、脆弱性の指摘ではない（出典1・4）。

Coway の IoCare クラウドは年に1〜2回壊れていた—— Home Assistant 向けの連携が遮断され、アプリが変わり、一度は著者のアカウントが数週間止められた（出典1・4）。直したかったのは「Apple Home の『おやすみ』で空気清浄機がホワイトノイズとして動く」ことである（出典1・4）。

その過程で、信頼の起点が平文 HTTP で配られていることに行き当たった。著者は当初、2026年10月の eMudhra のルート CA の問題を使うことを考えたが、不要だと分かったと書いている（出典1）。

この経緯には2つの含意がある（本記録の評価）。

第一に、クラウド依存の家電は、利用者に機器を分解する動機を与える〈重要〉。サービスが壊れるほど、手元で動かそうとする人が増え、結果として設計が公開の場で検証される。ベンダーにとっては、サービスの安定性がそのまま「設計が調べられるかどうか」に効いている（本記録の整理）。

第二に、解析の費用が下がっている。著者は mitmproxy が見せる生の MQTT の流れから指令の意味を割り出す作業について、生成AI を使い、本来数日かかったはずのものを約20分で終えたと書いている（出典1）。この見立ては著者の主観であり本記録は検証できない（本記録の留保）—— ただし、同じ作業が「数日」から「夕食後」の規模になれば、やろうとする人の数が変わる（本記録の評価）。

著者は、ある AI 補助が Raspberry Pi のプロキシ構築をサイバー関連の分類で断り、別のものが手伝ったとも書いている（出典1）—— その当否について著者は立場を取っておらず、本記録も取らない。

本件の機器は空気清浄機である。業務システムではないし、漏れるのは空気質の測定値と稼働履歴だろう（著者はデータの範囲を整理していない。本記録の確認）。それでも読む価値があるのは、確認すべき項目が明確に1つ示されたからである（本記録の評価）。

「この機器は、信頼の起点をどこから得るか」〈重要〉。

  • ファームウェアにトラストアンカーを組み込んでいるか
  • 外部から取得する場合、取得したものの署名を検証しているか
  • その取得先（URL）は、誰が決めるのか

本件は3つすべてで不備があった（出典1）——組み込みは無し、検証は無し、取得先は設定パケットで外から与えられる。

家庭向けの機器ではメーカーが設計情報を出さないため、調達の場でこれを確認できないことが多い（本記録の評価）。その場合に取れるのは、置き場所で対処する判断である（本記録の推奨）—— IoT 機器を業務用の内部ネットワークと同じセグメントに置かない、出口の通信先を記録する、中古・貸与・退去時の初期化と再設定を手順に定める。

更新期間についても、本件は見方を示している。Coway の表記は「最低5年」である（出典5）。「最低」の保証では終了日が決まらず、機器の更新計画に落とせない（本記録の評価）〈重要〉——調達時に終了日を文書で確認するところまでやらないと、「いつ入れ替えるか」が決まらない。

侵入を防げた設定時の相手を機器側で確認する仕組みを設ける（設計変更）
影響を限定できた中古・貸与・退去時の初期化と再設定を手順に定める

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • IoT 機器・クラウド接続型の設備を、業務用の内部ネットワークと 同じセグメントに置かない方針を文書にする。
    **本件の機器は、信頼の起点を検証せずに外から取得しており、 通信路上に位置を取れる者に中身を読まれる状態だった**（出典1）〈重要〉。 **機器側に検証の仕組みが無いため、利用者側で設定を直す余地が無い** （本記録の評価）—— **残る手は「どこに置くか」だけである。**
    取るべき行動 **オフィス・工場・店舗にある通信する設備（空調・空気清浄機・ カメラ・入退室・掲示端末）を一覧にし、接続先のセグメントを確認する。** **業務用セグメントにあるものを IoT 用へ移す計画を期限付きで立てる。**
  • 調達の審査項目に「信頼の起点（トラストアンカー）をどこから得るか」を入れる。 答えられないベンダーがいることも含めて判断材料になる。
    **本件は3点すべてで不備があった**（出典1。本記録の整理）〈重要〉—— **①ファームウェアにルート証明書を組み込んでいない、 ②取得した証明書を検証していない、 ③取得先の URL が設定パケットで外から与えられる。** **「HTTPS で取っているか」だけを聞いても本件は見つからない**（本記録の評価）。
    取るべき行動 **機器調達の質問票に3項目を加える——トラストアンカーの組み込みの有無、 取得する場合の署名検証の有無、取得先の指定方法。** **回答できない場合は「分からない」として記録し、置き場所の制約で扱う。**
  • セキュリティ更新の提供期間を「終了日」で確認する。「最低N年」では計画に落ちない。
    **Coway は「製品の正式発売日から最低5年間」と表明しているが、 終了日は明記されていない**（出典5。原文英語を訳出）〈重要〉—— **さらに一覧には本件の機器が載っておらず、 対象かどうかも分からない**〈未確定4〉。 **終了日が決まらないと、機器の入れ替え時期を決められない**（本記録の評価）。
    取るべき行動 **通信する設備の調達契約・仕様書に、セキュリティ更新の終了日を 年月で記載させる。** **既設の設備については、現時点で分かる終了日を台帳に入れ、 不明なものを「不明」として残す。**
  • 中古・貸与・退去時の機器の扱いを手順に定める。設定した者が信頼の起点を決める型がある。
    **本件は Bluetooth の設定パケットに CA の URL と証明書サーバの URL が 含まれており、設定を行える者が機器の信頼先を決められる**（出典1）〈重要〉—— **機器を初期化しても第三者の設定が消えるかは分からない**（本記録の評価。 出典2 にも手順の記述は無い）。
    取るべき行動 **オフィスの移転・退去、什器の中古導入・貸与の手順に 「通信する設備の初期化と再設定」を入れる。** **初期化で何が消えるかベンダーに確認できないものは、 業務用セグメントに戻さない運用にする。**
セキュリティ技術者への示唆
  • 「HTTPS かどうか」ではなく「取得したトラストアンカーを検証しているか」を見る。
    **本件で最も支持された技術的な整理は 「HTTP で証明書を配ること自体は問題ではない。 問題は検証していない証明書を暗黙に信頼することである」である** （出典3。原文英語を訳出）〈重要〉—— **HTTPS にしても、取得したものを検証しないままなら同じことが起こる** （本記録の評価）。 **逆にトラストアンカーを組み込んで署名を確かめていれば、 経路が HTTP でも成立しない。**
    取るべき行動 **自社が作る機器・エージェントについて、 トラストアンカーの入手経路と検証の実装を確認する。** **「証明書を取ってくる」実装を見つけたら、 それが何によって正しさを保証されているかを辿る。**
  • 初期設定（プロビジョニング）のパケットに「信頼の起点の所在」を 入れていないかを確認する。
    **本件の設定パケットには CA の URL と証明書サーバの URL が入っていた** （出典1）〈重要〉—— **これにより、中間者の位置を取らずに信頼の起点を向け直せる**（本記録の整理）。 **鍵の導出材料の片方（MAC アドレス）は設定手順の最初に平文で読めるため、 暗号は盗聴への保護にしかなっていない**（出典1。本記録の整理）。
    取るべき行動 **自社のプロビジョニング設計を見直し、 トラストアンカーの所在を設定入力から与える作りになっていないか確認する。** **なっている場合は、機器側に出荷時の検証材料（組み込みの公開鍵等）を 持たせて照合する設計へ変える。**
  • IoT 機器の通信先を出口で記録する。機器側には痕跡が残らない。
    **機器側に検証の仕組みが無いため、差し替えを拒む動作もログも無い** （本記録の評価）〈重要〉—— **「信頼の起点が入れ替わった」ことを機器自身が知る手段が無い。** **残る観測点は、機器の外（どこへ繋いだか）だけである**（本記録の整理）。
    取るべき行動 **IoT 用セグメントの出口で、機器ごとの通信先ホストと通信量を記録する。** **想定外のホスト（手元のサーバを含む）への接続を検知する条件を作る。**
  • 機器の秘密鍵を「サーバからダウンロードする」設計になっていないか確認する。
    **本件では、機器自身の証明書と秘密鍵の取得先 （icert-fs.iocareus.com）が通信から見えた**（出典1）〈重要〉—— **これは「その機器としてクラウドに繋ぐ資格」であり、 中間者の位置から取得できる経路が存在したことを意味する**（本記録の整理）。
    取るべき行動 **自社の機器では秘密鍵を機器内で生成し、外に出さない設計にする （CSR のみを送る）。** **既存の設計で鍵を配っている場合は、 クラウド側で同一証明書の重複接続・接続元の逸脱を検知する仕組みを足す。**
  • プロトコル解析の費用が下がっていることを、脅威の前提に織り込む。
    **著者は MQTT の指令の対応付けを生成AI にさせ、 本来数日かかったはずのものを約20分で終えたと書いている**（出典1）。 **本記録はこの見立てを検証できない（著者の主観である）**（本記録の留保）—— **ただし同じ作業が「数日」から「夕食後」の規模になれば、 やろうとする人の数が変わる**（本記録の評価）〈重要〉。
    取るべき行動 **「独自プロトコルだから解析されない」ことを前提にした設計を洗い出す。** **難読化ではなく、認証と検証で成立する設計に置き換える。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ オフィス・工場・店舗にクラウド接続型の設備（空調・空気清浄機・カメラ・ 掲示端末等）があり、業務用の内部ネットワークと同じセグメントに置いている。
