INC-2026-1101Expedia、委託データ基盤経由の侵害を認める

2026年11月12日、オンライン旅行会社 Expedia Group が、 **第三者のデータプラットフォーム事業者が侵害され、その信頼されたアクセスを 経由して自社のシステムへ到達された**ことを認めた。 同社は旅行業界メディア Skift に対し、**「複数の企業にも影響した サプライチェーン型のサイバー攻撃」**であると説明した。 一方、恐喝グループ **n0n** は、**ロイヤルティ記録 8億3,000万件超・ 旅行者プロファイル 5,800万件・消費者アカウントと認証情報 3億3,300万件超**を 含む「10億件近く」の窃取を主張している。 **Expedia はこの数値を確認しておらず、侵害されたベンダー名も 漏えいしたデータの種類も公表していない。** **研究者（Wiz・Sentra）は、クラウドデータ基盤 Qubole に与えられた クロスアカウントの信頼が悪用された一連の攻撃を2026年10月14日〜26日に 観測しており、Skift はこれを Expedia の旧ベンダーとして結びつけているが、 Expedia 自身は関連を認めていない**

自社が止めた取引の痕跡が、1年後の侵入口として残っていた事案です。

2026年11月12日、オンライン旅行会社 Expedia Group が、第三者のデータプラットフォーム事業者が侵害され、その事業者に与えられていた信頼されたアクセスを経由して自社のシステムへ到達されたことを認めました（出典1）。同社は旅行業界メディア Skift に対し、これを「複数の企業にも影響したサプライチェーン型のサイバー攻撃」と説明しています（出典1）。Expedia は、侵害されたベンダーの名前を挙げておらず、どのデータが露出した可能性があるのかも公表していません（出典1・5）。

公表のきっかけは、攻撃者側の主張でした。 2026年9月中旬に現れたロシア語圏の恐喝グループ n0n が、Expedia から 10億件近くの旅行者記録を盗んだと主張し、複数のセキュリティ系サイトがこれを報じたのを受けて、Expedia が確認に応じた形です（出典1・5）。n0n の主張の内訳は、ロイヤルティプログラム記録 8億3,000万件超（35のプログラム分）、旅行者プロファイル 5,800万件、消費者アカウントと認証情報の記録 3億3,300万件超、ハッシュ化されたメールアドレスに紐づくクレジットカード利用記録約250万件、消費者の照合記録 7,200万件、宿泊詳細を含む宿泊者記録50万件です（出典5）。Expedia はこの数値を確認していません〈齟齬2〉。

技術的な経路を示したのは、当事者ではなく研究者でした。セキュリティ企業 Wiz と Sentra は、クラウドデータ基盤Qubole に与えられたクロスアカウントの信頼が悪用された一連の攻撃を、2026年10月14日から26日にかけて観測しています（出典3・4）。攻撃者は Qubole 関連の AWS アカウントの IAM ユーザーを使い、顧客環境側の統合用 IAM ロールを AssumeRole で引き受けました。各ロールには ExternalId の確認が設定されていましたが、攻撃者は正しい値を毎回提示しており、AWS から見れば攻撃者は Qubole として振る舞っていました（出典3・4）。Skift は Qubole を Expedia の旧ベンダーとして結びつけていますが、Expedia 自身は関連を認めていません〈齟齬1〉。

本記録が中心に置くのは、この事案の「侵入口が自社の設定の中にあった」という性質です（本記録の評価）。脆弱性は使われていません。Wiz は AWS 側の不備も見つけていません（出典3）。使われたのは、顧客自身が過去に書いた信頼ポリシー——「このベンダーのアカウントを信頼する」という1行です。 取引が終わってもその1行は消えず、ベンダー側で鍵が漏れた日に侵入口として起動しました。

**本件の経路は「ベンダーのクラウドアカウント → 顧客の統合用 IAM ロール → 顧客のデータ」である**（出典3・4）。 **脆弱性は使われていない。Wiz は AWS 側の不備も見つけていない**（出典3）。 **使われたのは、顧客自身が過去に書いた信頼ポリシー （「このベンダーのアカウントを信頼する」）と、 そのベンダー側で漏れた資格情報の組み合わせである**（本記録の整理）。 **以下の各段は、Expedia に対する攻撃として公表されたものではなく、 Wiz と Sentra が一連のキャンペーンとして観測した手口である** 〈齟齬1〉——**Expedia は技術的な経路を公表していない**〈未確定1〉。

  • 「第三者経由だった」という公表は、原因の説明ではない——委託先の事故を自社の事故として扱う
    Expedia が公表したのは「第三者のデータプラットフォーム事業者が 侵害され、その信頼されたアクセスを経由して到達された」までである。 ベンダー名も漏えいの範囲も示されていない。 一方、利用者から見れば自分のデータが露出した可能性のある事案であり、 「委託先の問題」では済まない。 自社が同じ立場になったとき、同じ説明で説明責任を果たせるかを 先に考えておく必要がある。
    取るべき行動 委託先起因のインシデントを想定した公表の雛形を用意し、 ①自社が確認した事実、②まだ確認できていないこと、 ③利用者が今取るべき行動、の3つを必ず書く構成にする。 「委託先の名前を出すか」の判断基準を平時に決めておく （契約上の守秘義務との関係を法務と整理する）。
  • 攻撃者の主張する件数を、そのまま被害規模として扱わない——「件（行）」と「人」は別である
    n0n は「10億件近く」を主張し、報道はその内訳を伝えているが、 Expedia はいずれも確認していない。 報道自身が「行数と影響を受けた人数は同じではない」と注意している。 恐喝グループの主張は支払いを促す圧力の手段でもある。 これを被害規模として社内に報告すると、 その後の訂正で信頼を失う。
    取るべき行動 外部事案の社内報告様式に「値の出所（当事者／当局／報道／攻撃者の主張）」 と「測っている対象（件・行・人・アカウント）」の欄を設ける。 攻撃者の主張は、確認されるまで「主張」として括って記載する運用に 統一する。
  • 破壊を伴わない窃取は、業務影響としては見えない——検知の指標を可用性から読み取り量へ移す
    Sentra は本件の特徴を「0 write actions。変更も削除もされず、 ただ盗まれただけで、それが気づきにくくしていた」としている。 ランサムウェアのような可用性の異常は起きないため、 業務側からの申告もない。 気づいたのは被害組織ではなく、外部の研究者だった。
    取るべき行動 インシデント検知の指標に「読み取り量の異常」を明示的に加える。 とくに、ベンダー用の権限で読まれたデータ量を 月次でレビューする仕組みを作る。 「業務影響がないので事案ではない」という判断が働かないよう、 窃取のみの事案を想定した報告基準を文書化する。
セキュリティ技術者への示唆
  • 外部アカウントを信頼する IAM ロールの一覧を、資産として持つ
    本件の侵入口は、顧客自身が過去に書いた信頼ポリシーである。 Wiz は対応の第一歩として「外部アカウントを信頼する IAM ロールをすべて洗い出す」ことを挙げている。 多くの組織はこの一覧を持っておらず、 ベンダーの事故が公表されても影響範囲を即座に引けない。
    取るべき行動 全 AWS アカウントの IAM ロールの信頼ポリシーを機械的に収集し、 「信頼している外部アカウント ID」「最後に引き受けられた日時」 「到達できるデータの範囲」を列にした一覧を作る。 定期的に再生成し、新しい外部信頼が増えたら差分で検知する。 同じことを Entra ID・Okta・GCP・SaaS の OAuth 連携でも行う。
  • ExternalId を秘密として扱わない——これは認証ではなく識別である
    本件では各ロールに ExternalId の確認が設定されていたが、 攻撃者は正しい値を毎回提示して全て成功させた。 Wiz は、ExternalId が CloudTrail に平文で記録されるため 秘密情報として扱うべきではないと指摘している。 ExternalId は「混乱した代理」問題を防ぐ識別子であり、 漏えいを前提にしていない。
    取るべき行動 ExternalId に依存した防御を、接続元の制限 （`aws:SourceIp` / `aws:SourceVpce`）と プリンシパルの限定（`:root` を使わない）へ置き換える。 ベンダーと調整して ExternalId をローテーションし、 可能ならロールごとに別の値を使う。 ExternalId を秘密管理の対象から外し、 「漏れている前提」で設計を見直す。
  • 組織全体の CloudTrail と S3 のデータイベントを有効にする——無いと「何が読まれたか」が永久に分からない
    研究者が読み取り件数を特定できたのは、 被害組織側に S3 のデータイベントが記録されていたためである。 管理イベント（`AssumeRole` など）だけでは、 引き受けた後に何を読んだのかが残らない。 本件は書き込みを伴わないため、 データイベントが無ければ「入られたが何も分からない」で終わる。
    取るべき行動 組織全体の証跡（organization trail）を有効にし、 個人情報・認証情報・バックアップを置くバケットで データイベント（読み取り）を記録する。 保持期間を、ベンダーのインシデント公表が遅れる前提で 最低1年に設定する。 記録していないバケットの一覧を作り、 「記録しない理由」を明示的に残す。
  • 秘密情報の保管場所を、ベンダー用ロールの到達範囲から外す
    本件では、Lambda の環境変数・Secrets Manager・ SSM パラメータストア・EC2 の user data から 約7分間に約100件の認証情報が読み取られた。 含まれていたのはソースコード管理・IdP・CI・データベースの 認証情報、監視エージェントのキー、 さらに Qubole 自身のトークンと ExternalId である。 1つのロールから秘密情報の保管場所全部に手が届いていた。
    取るべき行動 ベンダー用ロールのポリシーから `secretsmanager:GetSecretValue`・`ssm:GetParameter(s)`（復号付き）・ `lambda:GetFunctionConfiguration`・`ec2:DescribeInstanceAttribute` を外す。 外せない場合は、リソース条件で連携に必要なものだけに絞る。 秘密情報の取得 API の呼び出し頻度に閾値を設け、 短時間の大量取得を警報にする。
  • 認証情報のローテーションだけでは終わらない——発行済みの一時セッションを取り消す
    Wiz は「認証情報のローテーションだけでは、 既に発行された一時セッションは終了しない」と注意している。 `AssumeRole` で得られた一時資格情報は、 元の IAM ユーザーのキーを無効にしても有効期限まで生き続ける。 ローテーションで安心すると、その窓の間は侵入が続く。
    取るべき行動 侵害が疑われるロールについて、 ①信頼ポリシーからベンダーを外す（またはロールを削除する）、 ②`AWSRevokeOlderSessions` 相当のインラインポリシーで 発行済みセッションを失効させる、 ③ロールが読み取れた秘密情報をすべてローテーションする、 の順で実施する手順書を用意する。 手順書に「順序を変えてはいけない理由」を書き添える。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ データ分析・データ基盤・BI などの外部サービスに、自社のクラウド環境へのクロスアカウントの信頼（IAM ロール等）を与えている本件の侵入口はこれである。 ベンダー側で資格情報が漏れた時点で、 顧客側の設定は何も変わっていないのに侵入口になる。 自社の脆弱性管理・パッチ適用の状態とは無関係に成立する。
体制・契約□ ベンダーの解約・契約終了の手続きに、クラウド上の権限削除の確認が含まれていない本件で悪用されたロールの多くは休眠しており、 Sentra は「取引関係の終了後も侵入経路が残っていた」と報告している。 契約書の終了手続きに権限削除が無い組織では、 過去に止めたすべてのベンダーが同じ状態にある可能性がある。 棚卸しの出発点は、技術ではなく契約の一覧である。
認証・認可□ 外部アカウントを信頼する IAM ロールの信頼ポリシーが `:root` 指定のままで、接続元（SourceIp / SourceVpce）の条件が付いていないWiz は「送信元 IP の条件だけで、観測されたすべての `AssumeRole` を阻止できた」としている。 つまり本件は、設定1つで防げた側の事案である。 自社の信頼ポリシーがこの状態なら、 同じベンダーでなくても同じ形で侵入されうる。
運用・監視□ 組織全体の CloudTrail が有効でない、または個人情報・認証情報を置くバケットで S3 のデータイベントを記録していない本件は書き込みを伴わない窃取であり、 可用性の異常としては現れない。 管理イベントだけでは「引き受けた」ことしか残らず、 「何を読まれたか」は確定できない。 ログが無い組織は、ベンダーの公表を受けても 自社の被害範囲を結論できない。
データの保持□ 秘密情報（Secrets Manager / SSM / Lambda の環境変数 / EC2 の user data）が、ベンダー用ロールの到達範囲に入っている本件では約7分間に約100件の認証情報が読み取られ、 そこには IdP・CI・データベースの認証情報が含まれていた。 1つのベンダー用ロールから秘密情報の保管場所全部に 手が届く構成なら、1回の侵入が横展開の起点になる。
システム構成□ 本番データベースのバックアップや、複数ブランド・複数サービスで共有しているデータのプールが、同じアカウント・同じロールの到達範囲にあるSentra は、最後に本番データベースのバックアップが 取得されたことを報告している。 また報道は、Expedia・Hotels.com・Vrbo のアカウントが 同じデータのプールを参照している可能性を指摘している。 共有のプールは、1回の侵入で露出する範囲を ブランド数ぶん広げる。
