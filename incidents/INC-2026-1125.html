INC-2026-1125よーじや会員APIを悪用され13万名流出

株式会社よーじやは2026年11月9日、同社が利用する会員情報管理システムに対し 外部の第三者が「会員情報を取得するためのシステム連携機能（API）」を不正に利用したアクセスがあり、 会員の個人情報が取得されたことを公表した—— 確認済み131,557名・潜在的な最大134,344名で、 項目は氏名・フリガナ・住所・電話番号・生年月日・性別・メールアドレス・会員番号等の会員情報と購買統計情報。 同社は不正利用された可能性のある API 認証キーを無効化して再発行し、 発信元IPを遮断、API に条件付きのアクセス制限を追加したが、 認証キーが流出した経路は特定できておらず調査が続いている

不正アクセス・侵害続報が続いている日本の組織が当事者認証情報の悪用（使い回し・推測可能・窃取）設計・実装上の不備
初報: 2026年11月9日 最終更新: 2026年11月17日

2026年11月9日、株式会社よーじやは「【重要】当社システムへの不正アクセスによる個人情報流出に関するお詫びとお知らせ（第一報）」を公式サイトに掲載し、同社が利用する会員情報管理システムに対し、外部の第三者から「会員情報を取得するためのシステム連携機能（API）」を不正に利用したアクセスがあり、会員の個人情報の一部が取得された事実が判明したと公表した（出典1）。

件数は2段で示されている——確認済み131,557名、潜在的な最大134,344名（出典1）。対象は、2026年11月7日時点で同社の会員サービス（店舗・オンラインショップ・アプリ）に登録していた一部の顧客で、退会済みの一部も含まれる（出典1）。項目は、氏名、フリガナ、住所、電話番号、生年月日、性別、メールアドレス、会員番号等の会員情報と、購買統計情報である（出典1）。クレジットカード情報・決済情報・ログインパスワードは同社が保持していないため流出のおそれはないとされている（出典1）。

経緯として公表されているのは1点だけである—— 2026年11月7日未明に、会員情報取得 API に対する外部からの不正アクセスを確認し、緊急調査を開始して応急処置の検討・実施に着手した（出典1）。不正アクセスがいつ始まり、どれだけ続いたかは示されていない〈未確定1〉。

実施した対策は3つである（出典1）—— ①不正アクセスに利用された可能性のある API 認証キーを無効化し、新たな認証キーを発行、②正常なシステム通信への影響がないことを確認したうえで、不正アクセスの発信元となった IP アドレスからの通信を完全に遮断、③不正アクセスの対象となった API について、一定の条件に該当するアクセスを制限する機能を追加し不審なアクセスを遮断。

本記録が本事案で重く見るのは、漏えいした項目と自社の運用が重なっていた点である（本記録の評価）〈重要〉—— 同社は対応のひとつとして、店舗でのポイント利用を「会員番号と電話番号の口頭申告だけでは行わず、アプリの会員証提示などで本人確認を徹底する」運用に切り替えている（出典1）。漏えいした会員番号と電話番号は、そのまま店頭での成りすましの材料になる。 データが出た先の被害は、攻撃者の次の手ではなく、自社の本人確認の作りが決めている。

公表されていないのは、不正アクセスの期間〈未確定1〉、API 認証キーの流出経路〈未確定2〉、会員情報管理システムの提供元〈未確定3〉、検知の端緒〈未確定4〉、取得に要したリクエスト数と時間〈未確定5〉、「確認済み131,557名」と「最大134,344名」の差の理由〈未確定6〉、購買統計情報の粒度〈未確定7〉である。

侵害されたのは「会員情報を取得するための API」そのものだった概観出典 [1]

よーじやが2026年11月9日に出した第一報は、原因をこう書いている。

同社が利用する会員情報管理システムに対し、外部の第三者から会員情報を取得するためのシステム連携機能（API）を不正に利用したアクセスがあり、同社会員の個人情報の一部が取得された事実が判明した

ここで起きているのは、システムの破壊でも脆弱性の悪用でもない。会員情報を取り出すために用意された正規の機能が、正規の手順で呼ばれた。違っていたのは呼んだ主体だけである。

件数は2段で示された。確認済み131,557名、潜在的な最大134,344名。対象は2026年11月7日時点で会員サービス（店舗・オンラインショップ・アプリ）に登録していた一部の顧客で、退会済みの一部も含まれる。

項目は、氏名、フリガナ、住所、電話番号、生年月日、性別、メールアドレス、会員番号等の会員情報、購買統計情報。クレジットカード情報・決済情報・ログインパスワードは同社が保持していないため流出のおそれはない、と書かれている。

「保持していないから漏れない」は、本件で最も強い防御だった（本記録の評価）——持っていないデータは、API がいくら呼ばれても出ていかない。

対策の3つのうち、2つは「この攻撃者」を止め、1つは「この手口」を止めた再発防止出典 [1]

第一報が番号付きで挙げる対策は3つである。

  1. 不正アクセスに利用された可能性のある API 認証キーを無効化し、新たな認証キーを発行。
  2. 正常なシステム通信への影響がないことを確認した上で、不正アクセスの発信元となったIP アドレスからの通信を完全に遮断。
  3. 不正アクセスの対象となった API について、一定の条件に該当するアクセスを制限する機能を追加し、不審なアクセスを遮断する対策を実施。

性質が違う（本記録の整理）。①と②は、いま侵入している相手を止める対策である。キーを無効化すれば同じキーは使えず、発信元を遮断すればその経路は閉じる。しかしキーの流出経路が分かっていない以上、別のキーが同じ道で漏れれば同じことが起きる。第一報自身が「API 認証キー流出の具体的な経路特定に向けた調査を進めている」と書いている（〈未確定2〉）。

③だけが手口に対する対策である。 「一定の条件に該当するアクセスを制限する機能を追加」——事後に追加したということは、侵害の時点では、認証キーさえあれば会員情報を制限なく引き出せたと読める（本記録の整理）。13万名分が取り出せたのは、キーが漏れたからであり、かつキーが漏れたときに件数で止まる仕組みが無かったからである。

②に付いている「正常なシステム通信への影響がないことを確認した上で」という一句にも注目しておく（本記録の読み）。遮断はそれ自体が障害を生む操作であり、止める前に業務影響を確かめる手順が踏まれている。

漏えいした会員番号と電話番号が、店頭の本人確認の要素と同じだった対策・注意喚起出典 [1]

本記録が本事案で最も実務的だと考えるのは、技術対策ではなく店頭の運用変更である（本記録の評価）〈重要〉。

同社は顧客への案内として、店舗でのポイント利用を、会員番号と電話番号の口頭申告だけでは行わず、アプリの会員証提示などで本人確認を徹底するとしている（出典1）。あわせて、アプリにセキュリティ強化版への強制アップデートの案内が表示される場合があるとも書かれている。

漏えいした項目を思い出すと、そこには 会員番号 と 電話番号 が並んでいる。つまり、流出したデータの組み合わせが、そのまま店頭での成りすましの入力値になる。攻撃者が次に何かをしなくても、自社の受付手順が二次被害の経路として開いていた。

だから同社は、データを取り戻せない代わりに受付の条件を変えた。口頭申告を認めるかどうかは自社だけで決められる。ここは、漏えいの事後対応として「相手の行動を止める」のではなく「自分の鍵穴を変える」ことができた箇所である（本記録の評価）。

読者が自組織に当てはめるときの問いはこうなる—— 「もし会員DBの内容が全部出たら、自社の窓口・コールセンター・店頭はその情報だけで本人として扱ってしまうか」。 答えが「扱ってしまう」なら、漏えいの被害はデータの外に出たあとではなく、自社の受付で確定する。

認証キーの流出経路は特定できていない——提供元か自社かも示されていない未確定事項出典 [1]

第一報は、調査が続いている箇所を自ら明示している。

システム提供元および外部セキュリティ調査機関と連携し、API 認証キー流出の具体的な経路特定に向けた調査を進めている

ここから読めることと、読めないことを分ける（本記録の整理）。読めるのは、侵害されたのが外部から提供を受けた会員基盤であることである。「同社が利用する会員情報管理システム」「システム提供元」という表現がそれを示す。読めないのは、キーがどこから漏れたかである（〈未確定2〉）。よーじや側の管理（設定ファイル・運用端末・委託先）か、提供元側か、あるいは別の経路かは示されていない。提供元の名称も公表されていない（〈未確定3〉）。

この区別は、同じ基盤を使う他の事業者にとって重要である（本記録の評価）。提供元側で漏れたのであれば、他の利用事業者にも同じ危険が及ぶ。自社側で漏れたのであれば、本件は1社の運用の問題に収まる。第一報はどちらとも言っていない。

なお、第一報には アプリのセキュリティ強化版への強制アップデート の案内がある。本記録はここから「認証キーがアプリ側に配布されていたのではないか」という読み方が成り立ち得ることを記録しておくが、これは本記録の推定であって、同社の公表にその記述は無い（〈齟齬1〉）。一般に、モバイルアプリに埋め込まれた鍵は端末の持ち主が取り出せるため秘密にならない——この一般論が本件に当てはまるかどうかは、公表された材料では決まらない。

評価——「正規の機能が正規に呼ばれた」事案は、侵入の検知に映らない評価・解釈出典 [1]

本件に不正な通信は無い（本記録の評価）。API は想定どおりに動き、認証は成功し、会員情報は仕様どおりに返された。侵入検知の視点で見れば、異常は何も起きていない。

映るとすれば、量と相手である。13万名分を取り出すには、通常の業務で起きない回数・件数の呼び出しが必要になる（本記録の推定。実際のリクエスト数は公表されていない。〈未確定5〉）。そして呼び出し元のIPアドレスは、同社が事後に「完全に遮断」できる程度には特定可能だった（出典1）。

つまり本件の検知線は、認証の成否ではなく、呼び出しのふるまいにある（本記録の読み）—— ①1つの認証キーが単位時間に返した件数、②呼び出し元のIPアドレスの分布（普段と違う場所から来ていないか）、③全件取得に近い条件のクエリが来ていないか。

同社が事後に追加したのが「一定の条件に該当するアクセスを制限する機能」であることは、ここを押さえる対策が侵害前には無かったことを示す（出典1。本記録の整理）。

もうひとつの読みを添えておく。よーじやはカード情報・決済情報・ログインパスワードを保持していなかった（出典1）。この事案が13万名の氏名・住所・電話番号・購買統計情報の流出で止まり、金銭被害やアカウント乗っ取りに広がっていないのは、持っていなかったことの直接の結果である（本記録の評価）〈重要〉—— 「取られて困るものを、そもそも手元に置かない」という設計が、侵害のあとに効いた唯一の構造的な防御だった。

不正アクセスに利用された可能性のある API 認証キーを無効化し、新たな認証キーを発行した。 あわせて不正アクセスの発信元となったIPアドレスからの通信を、 正常なシステム通信への影響がないことを確認したうえで完全に遮断した機能した**本記録の評価——妥当である。** **キーが漏れた疑いがある時点で、キーの無効化と再発行以外に止める手段は無い** （本記録の読み）。 **「正常なシステム通信への影響がないことを確認した上で」遮断したという記述は、 封じ込めが業務影響の確認とセットで行われたことを示す**（出典1）〈重要〉—— **遮断は障害を生む操作であり、この一句があることは手順の成熟を示す。** **留保——キーの流出経路が特定されていないため、 新しいキーが同じ経路で漏れない保証は無い**〈未確定2〉。
店舗・オンラインショップ・アプリのサービスは停止せず継続した。 代わりに店舗でのポイント利用について、会員番号と電話番号の口頭申告のみでは行わず、 アプリの会員証提示などで本人確認を徹底する運用に変更した機能した**本記録の評価——この判断が本事案で最も学べる箇所である**〈重要〉。 **漏えいした項目（会員番号・電話番号）が店頭の本人確認要素と 同じであることを認識し、受付の条件そのものを変えている**（出典1）—— **データは取り戻せないが、鍵穴は変えられる**（本記録の読み）。 **サービス停止を選ばず運用変更で対処したことは、 侵害された API を閉じたうえで顧客接点を維持する選択として整合している。** **留保——口頭申告を認めない運用がいつまで続くのか、 恒久の方針なのかは公表されていない。**
件数を「確認済み131,557名」と「潜在的な最大134,344名」の2段で公表し、 漏えい項目・実施済みの対策3件・調査が続いている箇所（認証キーの流出経路）を明示した。 一方、システム提供元の名称・不正アクセスの期間・検知の端緒は示さなかった部分的に機能**本記録の評価——件数の2段提示と「経路は特定できていない」という明示は良い** （本記録の読み）—— **「最大」だけを出す公表や、原因を断定する公表より誠実である。** **留保——侵害されたのは外部から提供を受けた会員基盤であり、 キーの流出が提供元側で起きた場合は他の利用事業者にも同じ危険が及ぶ**〈未確定2〉〈未確定3〉。 **提供元の名称と「自社側か提供元側か」の区別が示されていないため、 第三者はその判断ができない。**
CISO・経営層への示唆
  • 「全件を取り出せる API」は、鍵が1つ漏れた日に全件が出ていく経路である
    本件で侵害されたのは脆弱性ではなく、会員情報を取得するために用意された正規の機能である。 認証キーが第三者に渡った結果、13万名分が仕様どおりに返された。 よーじやは事後に「一定の条件に該当するアクセスを制限する機能」を追加しており、 侵害時点では件数の上限が無かったと読める
    取るべき行動 個人情報を返す API を一覧にし、それぞれについて「1つの鍵が1日に取得できる件数の上限」を 決めて実装する。上限の決め方は業務の実測値（平常時の最大）＋余裕とし、 上限に達したら遮断して警報する設計を既定にする
  • 漏えいしたデータが、自社の本人確認の答えになっていないか確かめる
    漏えい項目には会員番号と電話番号が含まれ、よーじやはこの2つの口頭申告だけで 店舗のポイント利用を認めていた。同社は本人確認を厳格化したが、 これは「データが出たあとの被害が、自社の受付手順で確定する」ことを示している
    取るべき行動 店頭・コールセンター・Web の本人確認で使っている要素を全部列挙し、 会員DBに入っている項目と突き合わせる。DB に載っている項目だけで本人と認める手順は 廃止し、所持（アプリ・カード）や知識（その場で発行するコード）を1つ足す
  • 持っていないデータは漏れない——保持しない設計が侵害後に効く
    よーじやはクレジットカード情報・決済情報・ログインパスワードを保持していなかった。 13万名の会員情報が出た事案が金銭被害やアカウント乗っ取りに広がっていないのは、 対策が効いたからではなく、そこにデータが無かったからである
    取るべき行動 自社が保持している個人データについて「事業上なくても回るもの」を洗い出し、 決済・認証情報は外部のトークン化・委託に寄せる。 保持をやめた項目は、公表文で「保持していないため流出のおそれはない」と書ける資産になる
  • 外部提供の会員基盤では、「どちらで漏れたか」を言えるかが説明責任を分ける
    侵害されたのは同社が利用する会員情報管理システムであり、 同社はシステム提供元と連携して認証キーの流出経路を調査している。 だが第一報は提供元の名称も、流出が自社側か提供元側かも示していない。 提供元側であれば同じ基盤を使う他の事業者にも危険が及ぶ
    取るべき行動 外部提供の基盤を使う契約に、①侵害時の原因切り分けの責任分担、 ②鍵の管理主体と保管場所の明示、③他の利用顧客への影響の通知義務を明記する。 既存契約は棚卸しして、切り分けの手順が書かれていないものから順に改訂する
  • 件数は「確認済み」と「最大」の2段で出すほうが、読者にも自社にも誠実である
    よーじやは131,557名（確認済み）と134,344名（最大）を並べて示した。 差は2,787名・全体の2.1%で、記録でどこまで追えたかが読み取れる。 上限だけを示す公表は、対象者を過大に見積もらせ、窓口の負荷と不安を生む
    取るべき行動 公表文の雛形に「確認された範囲」と「可能性を否定できない範囲」の2欄を設け、 差が出る理由（記録の粒度・保全期間）を1行で説明する欄を付ける
セキュリティ技術者への示唆
  • API 認証キーに「接続元・件数・項目・有効期限」を結び付ける
    本件のキーは、漏れた時点で会員情報を制限なく取得できるものだったと読める。 キーが単に「通る／通らない」の2値でしか機能していないと、 漏えいの影響はその鍵が触れる全データになる
    取るべき行動 鍵ごとに許可する呼び出し先・返却項目・件数上限・接続元IP範囲・有効期限を 設定として持たせる。長期有効な恒久キーは廃止し、 自動ローテーションを運用に組み込む（まずは最も広い権限を持つ1本から）
  • 鍵の保管場所を棚卸しする——配布物の中に鍵を置かない
    キーの流出経路は特定されていない。 一般に、設定ファイル・ソースコード・配布するモバイルアプリ・運用端末・ 委託先の環境のどこかに鍵があれば、そこが経路になる。 鍵の置き場所を一覧にできない組織は、漏れた経路の特定もできない
    取るべき行動 鍵・トークンの保管場所を1枚の表にする（システム／保管先／権限／有効期限／最終更新）。 ソースコードと配布物に対する秘密情報の走査を CI に入れ、検出で失敗させる
  • 認証成功の監視では足りない——「1つの鍵が返した件数」を見る
    本件のアクセスは認証を正規に通っている。認証の成否だけを見ていれば異常は映らない。 映るのは、1つの鍵が単位時間に返した件数と、呼び出し元の分布である
    取るべき行動 API ゲートウェイまたはアプリケーション層で、鍵単位の呼び出し回数・返却件数・ 接続元IPを時系列で記録し、平常時の最大を基準にした警報を1本作る。 未明・休日の逸脱は当番へ通知する
  • 遮断の前に「正常な通信への影響がないこと」を確認する手順を用意しておく
    よーじやは発信元IPの遮断を「正常なシステム通信への影響がないことを確認した上で」 実施したと述べている。遮断や鍵の無効化はそれ自体が障害を起こす操作であり、 緊急時に影響範囲を把握できないと、止めること自体が二次障害になる
    取るべき行動 主要な連携ごとに「誰が、どの鍵で、どのIPから呼んでいるか」の対応表を平時に作る。 鍵の無効化とIP遮断については、影響確認のチェックリストと切り戻し手順を 運用手順書に入れ、年1回訓練する
  • 返す項目を用途ごとに絞る——ポイント照会に住所と生年月日は要らない
    漏えいした項目は、氏名・フリガナ・住所・電話番号・生年月日・性別・メールアドレス・ 会員番号等・購買統計情報と広い。会員情報取得 API が 用途を問わず同じ項目群を返す作りであれば、どの用途の鍵が漏れても全項目が出る
    取るべき行動 API の応答を用途別のビューに分け（ポイント照会・配送・マーケティング）、 鍵ごとに返す項目を制限する。既存の汎用エンドポイントは 用途別に置き換えてから廃止する

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 会員情報・顧客情報を返す API があり、1回の呼び出しで返せる件数や 単位時間あたりの呼び出し回数に上限が設けられていない本件は脆弱性ではなく正規機能の不正利用で13万名分が出た。 よーじやは事後に条件付きのアクセス制限を追加している。 上限が無い API は、鍵が1つ漏れた日に、その鍵が触れる全データが出ていく経路になる。 上限は侵害を防ぐ対策ではなく、侵害の規模を桁で変える対策である。
認証・認可□ API 認証キーが長期有効で、鍵ごとに接続元IP・返却項目・件数上限が結び付けられていない本件のキーは漏えい後そのまま使えた。 鍵が「通る／通らない」の2値でしか機能していないと、 漏えいの影響はその鍵が触れる全範囲になる。 鍵に条件が結び付いていれば、同じ鍵が漏れても使える場所と量が限られる。
データの保持□ 本人確認（店頭・コールセンター・Web）で使っている要素が、 自社の顧客データベースに入っている項目だけで構成されている本件では会員番号と電話番号が漏れ、同社はその2つの口頭申告で店舗のポイント利用を 認めていたため、本人確認の運用そのものを変更した。 DB に載っている項目だけで本人と認める手順は、 その DB が漏れた日に成りすましの入力値へ変わる。
委託・第三者部品□ 会員基盤を外部から提供を受けており、侵害時に「鍵がどちらで漏れたか」を 切り分ける責任分担と手順が契約・運用に定まっていない本件で侵害されたのは同社が利用する会員情報管理システムであり、 キーの流出経路は提供元と調査中である。 切り分けの手順が無ければ、原因の特定が遅れるだけでなく、 同じ基盤を使う他の事業者への影響も誰も判断できない。
運用・監視□ API の監視が認証の成否とエラー率に留まり、鍵単位の返却件数・接続元の分布を見ていない本件のアクセスは認証を正規に通っており、侵入検知の視点では異常が無い。 映るのは量と相手だけである。 認証成功を正常として扱う監視しか無い組織は、同じ事案を検知できない。
データの保持□ 決済情報・パスワードなど「漏れたときに金銭被害・乗っ取りへ直結するデータ」を 自社で保持している本件が13万名の会員情報の流出で止まったのは、 よーじやがカード情報・決済情報・ログインパスワードを保持していなかったからである。 保持していれば同じ API の不正利用で金銭被害とアカウント乗っ取りに広がっていた。 保持しない設計は、侵害後にはじめて価値が分かる投資である。
