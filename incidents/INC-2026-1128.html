    **GoWebクラウドは、本人確認書類の画像は「不正アクセスがなかったことを 確認した」、クレジットカード情報は「保有していない」と 書き分けている**（出典1）〈重要〉—— **前者には調査の確度という留保が付き、後者には付かない**（本記録の整理）—— **「含まれません」とだけ書けば、この差は読者に伝わらない。**
    取るべき行動 **自組織の公表の雛形で、対象外の情報を2つの欄に分ける**〈重要〉—— **①保有しているが影響がないと確認したもの（確認の根拠を添える） ②そもそも保有していないもの。** **前者には「現時点の調査では」という時点を必ず付ける。**
  • 対象者への通知を利用会社に委ねるなら、通知の期限と文面の最低条件を 提供元が示す。委ねた先の体制差がそのまま被害者への到達差になる。
    **対象者への連絡は「各ご利用会社様と連携のうえ、順次」とされ、 開始日・完了日は公表されていない**（出典1・3）〈重要〉—— **利用会社の数も公表されておらず、 通知がどこまで進んだかを外から測る手段がない**（本記録の確認）〈未確定2〉。
    取るべき行動 **自社がサービス提供者の側なら、利用会社向けの通知手順に 「何日以内に」「最低限どの項目を書くか」を明記した雛形を添えて配る**〈重要〉—— **自社が利用会社の側なら、提供元との契約に 事案発生時の情報提供の期限（把握から何時間以内に一次連絡か）を入れる。** **通知の進度を提供元へ報告する約束も、あわせて決めておく。**
  • 預かっている個人情報の中に「本人が登録を知らない第三者」がいる場合、 その人への通知手段を事前に設計しておく。
    **対象情報には緊急連絡先の氏名・生年月日・住所・電話番号が含まれる** （出典1）〈重要〉—— **緊急連絡先として書かれた人は、自分の情報がどの会社のシステムに あるかを知らない可能性がある**（本記録の整理）—— **通知は利用会社から行われるが、利用会社と契約関係にあるのは 申込者であって緊急連絡先ではない**（本記録の評価）。
    取るべき行動 **自組織の申込書・保証人欄・緊急連絡先欄・推薦者欄を洗い出し、 「本人以外の情報を取得している欄」を一覧にする**〈重要〉—— **それぞれについて、漏えい時に本人へ到達する経路（直接連絡か、 申込者経由か）を決めておく。** **取得の時点で第三者本人への利用目的の通知が必要かも、 法務とあわせて確認する。**
セキュリティ技術者への示唆
  • SQL インジェクションは2026年でも現役の侵入口である。 フレームワーク任せにせず、文字列連結で SQL を組む箇所を規約で禁じる。
    **本件の侵入口は「プログラムの脆弱性を突いた SQL インジェクション」と 明示されている**（出典1）〈重要〉—— **認証を突破したのではなく、アプリケーションの実装の不備が そのまま通り道になっている**（本記録の整理）。
    取るべき行動 **自社のコードベースを検索し、SQL を文字列連結・文字列補間で 組み立てている箇所を全部挙げる**〈重要〉—— **プレースホルダ（パラメータ化クエリ）へ置き換え、 置き換えられない箇所（動的なテーブル名・ORDER BY 等）は 許可値の白名簿で囲う。** **静的解析を CI に入れ、新しい文字列連結を落とす。**
  • 複数の利用会社が同じ基盤を使うなら、分離をアプリケーションの条件だけに 依存させない。1つの脆弱性で全社分に届く作りを避ける。
    **1つの脆弱性が「複数のご利用会社様の利用環境」に及んでいる** （出典1）〈重要〉—— **テナント分離の作りは公表されていないため断定はできないが、 SQL インジェクションが成立した時点でアプリケーションの 条件分岐は迂回されている**（本記録の読み）。
    取るべき行動 **テナントごとに接続ユーザを分け、データベース側の権限 （スキーマ分離・行レベルセキュリティ）でも境界を作る**〈重要〉—— **1つの接続で全テナントの行が見える構成になっていないかを、 実際に検証用の環境で試して確かめる。** **「アプリが WHERE 句を付けているから大丈夫」を根拠にしない。**
  • 機微な資産（本人確認書類の画像）は、申込情報の本体と別の保管領域・ 別の権限に置く。本件ではそれが被害の範囲を切っている。
    **本人確認書類の画像ファイルには不正アクセスがなかったことが 確認されている**（出典1）〈重要〉—— **データベースへの SQL インジェクションが成立しても 画像まで届かなかったのは、保管の場所と到達経路が 別だったからと読める**（本記録の読み。公表に基づく判定ではありません）。
    取るべき行動 **自社が預かる本人確認書類・契約書・診断書などの画像・文書を、 業務データベースとは別のストレージに置き、 署名付き URL など短命な権限でのみ取り出す形にする**〈重要〉—— **業務データベースの侵害だけでは画像へ届かないことを、 実際に権限を落とした環境で確認する。**
  • データベースの監査ログを、アプリケーションのログとは別に残す。 「持ち出されたか」を後から言い切れるかはここで決まる。
    **持ち出しの有無は公表から3週間たっても調査中である**（出典1・3）〈重要〉—— **一方でアクセス記録の保全・解析は行われており、 追える記録は存在する**（出典1）—— **記録が不足しているのか解析が途上なのかは外から判定できないが、 断定に時間を要していることは事実である**（本記録の評価）。
    取るべき行動 **データベース側の監査ログを有効にし、アプリケーションから 改変できない場所へ送る**〈重要〉—— **1回の問い合わせが返した行数を記録に残す （件数が分からないと「何人分が見られたか」が言えない）。** **保存期間を、想定する侵入期間より長く取る。**
  • 利用会社アカウントの認証情報が対象に入った時点で、 強制失効を既定の動作にする。
    **対象情報に「サービスを利用している仲介会社のアカウント情報」が 含まれている**（出典1）〈重要〉—— **パスワードの保存形式、強制リセットの実施、 不正ログインの有無はいずれも公表されていない**（本記録の確認）。
    取るべき行動 **アカウント情報が対象に入る事案では、全利用会社のパスワードと API トークン・セッションを一律で失効させる手順を用意しておく**〈重要〉—— **「悪用が確認されていないから据え置く」を既定にしない。** **失効後の一定期間、ログイン試行の失敗率と地域の偏りを監視する。**
