セキュリティ技術者への示唆
  • script-src を具体的な配信元に絞る。'strict-dynamic' と 'unsafe-eval' は、この攻撃を通しうる。
    **評価された256組織のうち、攻撃コードの実行自体を 遮断できたのは24組織（15%）で、 CSP なしが68、CSP があっても実行と送信の両方を許したのが50だった** （出典1）〈重要〉—— **Helme は 'strict-dynamic' と 'unsafe-eval' が 攻撃を通しうると指摘している**（出典1）—— **攻撃コードの変種には、外部の読み込みが遮断された場合に 埋め込んだ複製を eval で実行するものがあった**（出典1・2）。
    取るべき行動 **自社の CSP を取り出し、script-src に 'unsafe-eval' が入っていないかを確認する**〈重要〉—— **入っている場合は、それを必要としているコードを特定して外す。** **'strict-dynamic' を使っている場合は、 信頼したスクリプトがさらに外部を読み込める状態に なっていないかを検証する。** **検証は Report-Only ではなく実際に遮断する設定で、 検証環境で行う。**
  • connect-src を絞る。実行を防げなくても、データの送信は止まる。 ただしページ内で完結する改ざんは止まらない。
    **17組織では、攻撃コードの実行は通ったが connect-src がデータ送信を遮断した**（出典1）〈重要〉—— **一方で Helme は、connect-src は暗号資産アドレスの 差し替えを止められないと指摘している**（出典1）—— **差し替えはページの中で完結し、外部通信を要しないためである。**
    取るべき行動 **connect-src を自社と既知の通信先に絞る**〈重要〉—— **絞った結果として壊れる機能を洗い出し、 必要な送信先だけを明示的に許可する。** **同時に「ページ内で完結する改ざんは CSP では止まらない」ことを 前提に、表示する値（送金先アドレス・金額）の 正しさを別の経路で確認できるかを検討する。**
  • 基盤側の「顧客が任意のコードを書ける欄」は、 権限管理と変更通知を最優先で設計する対象である。
    **攻撃者は Optimizely Web の「Project JavaScript」の欄に コードを書き込み、それが顧客サイトの全ページで実行された** （出典1）〈重要〉—— **この欄は本来、顧客が自分で変更する場所であるため、 「変更が行われたこと」自体は異常ではない**（本記録の整理）—— **誰がいつ何を変更したかの記録と変更時の通知が無ければ、 正当な変更と攻撃の区別が付かない**（本記録の評価）。
    取るべき行動 **自社が同様の機能（顧客が書いたコードを自社が配信する）を 提供している場合、変更操作に多要素認証を必須にし、 変更のたびに顧客の管理者へ通知する**〈重要〉—— **変更の履歴を顧客自身が参照できる形にする。** **自社が利用組織の側なら、基盤が設定変更の記録を API で取得できるかを確認し、取得できるなら 定期的に差分を監視する。**
  • 固定のハッシュ・固定の文字列による検知に頼らない。 本件の攻撃コードは1日で26回作り直されている。
    **攻撃コードは協定世界時11月16日のうちに26回作り直された** （出典1）〈重要〉—— **読み込みの形も3種あり、URL の直接記述・ Base64 と atob() による隠蔽・埋め込んだ複製の eval 実行が 混在していた**（出典1・2）。
    取るべき行動 **検知を「既知の悪性ハッシュ」ではなく 「想定外の配信元からの読み込み」という構造で行う**〈重要〉—— **CSP の違反報告と、読み込まれたスクリプトの一覧の 差分監視を基本にする。** **文字列で探す場合は、ドメイン（本件では 1688360.cc）に加えて atob( の出現と、自社が書いていないコードの有無を見る （出典1 の推奨）。**
  • 第三者基盤の事案では、認証情報とトークンの失効を 「悪用が確認されたら」ではなく既定の手順にする。
    **攻撃者が178組織分のプロジェクトへ書き込めた経路は 公表されていない**（出典1・2）〈重要〉—— **Helme は利用組織への推奨として、 アクセス用の認証情報（利用者・API トークン・連携）の 見直しと更新を挙げている**（出典1）—— **経路が分からないまま汚染されたコードだけを消した場合、 同じ経路で再び書き込まれても外から分からない**（本記録の評価）。
    取るべき行動 **自社が使う基盤について、API トークン・連携用の 認証情報・利用者アカウントの一覧を取り出し、 事案の報告を受けたら一律で失効・再発行する手順を用意する**〈重要〉—— **失効によって止まる処理を事前に把握しておく。** **失効後の一定期間、設定変更とログイン試行を重点的に監視する。**
