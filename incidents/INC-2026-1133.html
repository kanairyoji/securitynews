攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**exploit_agent の作りは、修正の公表を入力にして エクスプロイトを出力する流れ作業である**（出典1。本記録の整理）〈重要〉。 **①広く使われている Web ソフトウェアのコードを、 修正の公表前後で継続的に差分解析する、 ②差分が何を明かしているかを推論して脆弱性の候補を特定する、 ③エクスプロイトを書く、 ④自動で実行する**（出典1）—— **複数のフロンティアモデルとローカルの LLM が組み合わされている**（出典1）。 **侵入後のためのスクリプトも同じサーバにあった—— 内部偵察、総当たり、ウェブシェルの設置、 そして他の攻撃者のウェブシェルの除去である**（出典1・2）〈重要〉。 **GTIG はこれを「脅威アクターが LLM の基盤を使って 脆弱性の発見と悪用を人の介在なしに完全に自動化したことを 初めて確認した」と述べている**（出典1。原文英語）。 **一方で、手口そのものは新しくない**（出典3。本記録の評価）〈重要〉—— **これらの基盤が依存しているのは、 盗まれた資格情報と未修正のソフトウェアである**（出典3）—— **変わったのは、複数の段を止まらずに連ねられることと、 結果に応じて手を変えられることである**（出典3）。

  1. 1. 偵察third_party_research[1]
    **広く使われている Web アプリケーションのソフトウェアについて、 修正の公表前後のコードを継続的に差分解析する**（出典1）〈重要〉—— **差分を解析して脆弱性の候補を特定する**（出典1）—— **報告が挙げる例は、WordPress プラグイン Spectra（Ultimate Addons for Gutenberg）2.19.25 の アクセス制御である**（出典1）—— **つまり偵察の対象は標的の組織ではなく、 標的が使っているソフトウェアのソースコードである**（本記録の評価）。
    根拠: GTIG 報告の「continuous differential analysis of popular web application software, comparing code before and after patch announcements」の記述（出典1）
  2. 2. 実行third_party_research[1] [2] [3]
    **差分から推論した脆弱性に対してエクスプロイトを書き、 自動で実行する**（出典1）〈重要〉—— **複数のフロンティアモデルとローカルで動かす LLM が 統合されている**（出典1）—— **GTIG はこの基盤が「人の介入なしに」 エクスプロイトを実行するように設計されていると述べている** （出典1。原文英語）—— **どの脆弱性が実際に悪用されたかは示されていない**〈未確定1〉。
    根拠: GTIG 報告の「drafts exploits, and automatically executes them」「without human intervention」の記述（出典1・2）
  3. 3. 内部探索third_party_research[1] [2] [3]
    **ステージングサーバには内部偵察のためのスクリプトが 置かれていた**（出典1・2）〈重要〉—— **侵入後の探索も自動化の対象に入っている**（本記録の評価）—— **CAIRN は OODA ループと共有の「黒板」を使い、 複数のエージェントが情報を共有しながら動く作りである**（出典1・3）。
    根拠: GTIG 報告の「scripts for internal reconnaissance, brute-forcing, installing webshells」の記述（出典1・2）
  4. 4. 認証情報アクセスthird_party_research[1] [2] [3]
    **総当たりのためのスクリプトがステージングサーバにあった**（出典1・2）〈重要〉—— **また、報告全体を通じて、 これらの基盤が盗まれた資格情報に依存していることが 繰り返し述べられている**（出典3）—— **LLMJacking では、公開された GitHub リポジトリに残された資格情報と、 セッショントークンを収穫する偽サイトが入口だった**（出典3）。
    根拠: GTIG 報告の「brute-forcing」のスクリプトの記述、および「These tools still rely on stolen credentials and systems that have not been patched」（出典1・3）
  5. 5. 永続化third_party_research[1] [2]
    **ウェブシェルを設置するスクリプトが置かれていた**（出典1・2）〈重要〉—— **同時に、他の攻撃者のウェブシェルを消すスクリプトもあった**（出典1・2）—— **これは、同じ標的を複数の攻撃者が争っている状況を示す** （本記録の評価）〈重要〉—— **つまり「自分が最初に入った」という前提では動いていない。**
    根拠: GTIG 報告の「installing webshells, and removing other attackers' webshells」の記述（出典1・2）
  6. 6. 影響（暗号化・破壊・改ざん）third_party_research[3]
    **LLMJacking では、盗んだ資格情報と計算資源が そのまま金銭化されている**（出典3）〈重要〉—— **Mandiant が対応した事案では1日で10万ドルを超える 不正な課金が発生し、片付けまでに最悪で100万ドルに達した**（出典3）—— **盗まれたアクセスは「LLM ミキサー」と呼ばれる店を通して売られ、 買い手の通信は盗まれた資格情報と計算インスタンスの束を 経由させられる**（出典3）—— **これにより安定したアクセスを提供しつつ、 問い合わせの量を複数の被害環境に分散させて 検知される可能性を下げている**（出典3。原文英語）。
    根拠: GTIG 報告の LLMJacking の章および「LLM Mixers」に関する記述（出典3 を通じて引用）

複数のフロンティアモデルとローカルで動かす LLM を統合している（出典1）。GTIG は「脅威アクターが LLM の基盤を使って、脆弱性の発見と悪用を人の介在なしに完全に自動化したことを初めて確認した」と述べている（出典1。原文英語）。

報告が示す「速さ」は3つの層で現れている（出典2・3。本記録の整理）。いずれも本記録は原資料を確認していない〈齟齬3〉。

① 脆弱性の武器化。 PaperCut の2件は2026年8月下旬にゼロデイとして悪用され、Huntress ほかの研究者は24時間以内に動作するエクスプロイトを作った（出典3）。GreyNoise は公表から4日後に攻撃の作戦を検知した。ある事例では、侵入からドメイン管理者権限の取得までが数分だった。

③ 金銭化の速さ（LLMJacking）。 Mandiant が対応した事案では1日で10万ドルを超える不正な課金が発生し、片付けまでに最悪で100万ドルに達した（出典3）。入口は、公開された GitHub リポジトリに残された資格情報と、セッショントークンを収穫する偽サイトである。ある攻撃者は CVE-2026-40217（LiteLLM のサンドボックス脱出）で限定されたキーを管理者の資格情報に変えた。短命のサービスアカウントを作って消して流量制限を回避した例、ボットネットが約24時間で数百万回の API 呼び出しを行った例もある。

盗まれたアクセスは「LLM ミキサー」と呼ばれる店で売られる（出典3）。買い手の通信を盗まれた資格情報と計算インスタンスの束に通すことで安定したアクセスを提供し、同時に問い合わせの量を複数の被害環境に分散させて検知される可能性を下げる（出典3。原文英語）〈重要〉。つまり1環境あたりの異常は小さく見える——使用量のしきい値を低く置かなければ気づけない（本記録の評価）。

価格はロシア語・中国語の市場で100万トークンあたり0.10〜25ドル。APIMart は10万トークンを超えると5倍にし、JetNight は月額の購読を売っている（出典3）。

痕跡は減っていない。見えないのではなく、人の承認が追いつかない評価・解釈出典 [1] [3]

GTIG の評価には、防御側にとって重要な留保がついている（出典1・3）—— 現在の基盤は「速さのために隠密さを捨てている」。

自律的に走る基盤は、通信・識別可能な指標・実行されるコードに痕跡を残す（出典3）。だから隠密さを重んじる諜報目的のアクターは、狙いを定めた環境でこの種の騒がしい道具を使いにくい。到達範囲を優先する犯罪目的のアクターの採用が進むとみられている（出典1・3）。

つまり見えない攻撃ではない（本記録の評価）。むしろ自動化によって、単位時間あたりの痕跡は増えている。しきい値型の検知にとっては有利な条件ですらある。

では何が問題か。見てから人が判断する速さである（本記録の評価）。PaperCut の事例では侵入からドメイン管理者権限まで数分だった（出典3）。警報が上がっても、分析して承認して遮断するまでに数分では終わらない組織が多い。

ここから本記録が引く結論は2つである（本記録の評価）。

第一に、検知を速くする競争には限界がある。併せて記録した Barracuda の事案（INC-2026-1132）で仕組みが攻撃者を止めたのは、管理者識別情報の作成が事前のポリシーで拒否されたところだった。当日の判断ではなく、事前の構成が効いている。

第二に、検知規則を基盤の名前に紐づけすぎない。 Security Affairs は、侵害されたシステムで見つかる ARTEX の「指標」の多くが LLM やその道具が生成したもので、基盤に組み込まれた固定の文字列ではないと指摘している（出典3）〈重要〉。モデルやプロンプトが変われば、文字列は変わる。振る舞い——短時間での列挙の集中、未使用の鍵の再使用、拒否された権限昇格——で見る側に重みを置く必要がある（本記録の評価）。

本件は特定組織の侵害ではなく、日本の組織が当事者でもない。それでも運用に直結する論点が3つある（本記録の評価）。

1. 修正の公表日を、攻撃の開始日として扱う。 exploit_agent の入力は修正の差分である（出典1）。月次の定期サイクルで適用している資産のうち、インターネットに面していて認証なしで到達できるものだけを別の経路に出す必要がある（本記録の評価）。全部を緊急にすると変更管理が壊れるので、線引きが要る。

2. 自社が使っている公開のソフトウェア部品の在庫を持つ。報告が差分解析の例に挙げたのは、WordPress プラグインSpectra（Ultimate Addons for Gutenberg）2.19.25 である（出典1）。狙われるのは自社が書いたコードではなく、自社が入れたことを忘れている部品である（本記録の評価）。

3. LLM の API 資格情報を、クラウドの資格情報と同じ台帳に載せる。 LLMJacking の入口は、公開 GitHub リポジトリに残された資格情報と偽サイトでのセッショントークンの収穫である（出典3）。1日で10万ドルという速さは、月次の請求の確認では間に合わない。使用量のしきい値つきの警報と自動停止が要る（本記録の評価）。

なお、公開されたエクスプロイトの主張については別の判断が要る（本記録の評価）。PHP の2件では数日で数百件の主張が現れ、多くは動作しなかった（出典2・3）。動作確認を待つと対処が遅れ、待たないと空騒ぎに時間を使う。「検証できていないが対処する」という判断の基準を、平時に決めておくほかない。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**GTIG は、基盤の設計・ロシア語の注記の文面・ 差分解析の対象となったプラグインの版まで公開した一方、 被害組織・件数・実際に悪用された脆弱性は公開していない**（出典1）〈重要〉—— **帰属についても、集団名も国家も挙げなかった**（出典2）。部分的に機能
**報告の公表と同時に、 Google SecOps は ARTEX の検知規則群を提供し、 Mandiant は堅牢化の手引きを公表した**（出典1・3）〈重要〉。機能した
CISO・経営層への示唆
  • 修正の公表日を「適用の開始日」ではなく「攻撃の開始日」として扱う。
    **exploit_agent の入力は、修正の公表前後のコードの差分である**（出典1）〈重要〉—— **修正は、何が壊れていたかを最も正確に教える資料であり、 その解析から実行までに人の時間が要らなくなった**（出典1。本記録の評価）—— **PaperCut の事例では、研究者が24時間以内に動作する エクスプロイトを作り、公表から4日後に攻撃の作戦が 検知されている**（出典3）—— **つまり「次の定期サイクルで適用する」という前提が、 インターネットに面した資産については成立しなくなっている** （本記録の評価）。
    取るべき行動 **資産を「インターネットに面している・認証なしで到達できる」で 絞り込み、その集合だけを定期サイクルの外で処理する経路を作る。** **その経路の所要時間（公表から適用まで）を測り、 実績値として経営に報告する。** **適用が間に合わない場合に備え、 仮想パッチ（WAF の規則）や機能の無効化で埋める手を 事前に決めておく。**
  • 速さで競うのをやめ、「速く動いても越えられない壁」を事前に置く。
    **GTIG は、現在の基盤が速さのために隠密さを捨てており、 痕跡を残すとしている**（出典1・3）〈重要〉—— **つまり問題は見えないことではなく、 見てから人が判断する速さが追いつかないことである**（本記録の評価）—— **PaperCut の事例では侵入からドメイン管理者権限までが 数分だった**（出典3）—— **併せて記録した Barracuda の事案（INC-2026-1132）で 仕組みが攻撃者を止めたのは、 管理者クラウド識別情報の作成が事前のポリシーで 拒否されたところだった**（本記録の評価）〈重要〉。
    取るべき行動 **「攻撃者が速く動いても越えられない壁」を列挙する—— 管理者権限の作成の既定拒否、 特権コンテナ・ホストのマウントの禁止、 鍵の有効期限、系ごとに独立した資格情報、 公開ディレクトリの読み取り専用化。** **検知から封じ込めまでのうち、 人の承認を要する範囲と自動で止める範囲を事前に線引きする。** **拒否が発生したこと自体を最優先の警報として人に届ける。**
  • LLM の API 資格情報と計算資源を、金銭的な攻撃対象として扱う。
    **LLMJacking では、Mandiant が対応した事案で 1日に10万ドルを超える不正な課金が発生し、 片付けまでに最悪で100万ドルに達した**（出典3）〈重要〉—— **入口は、公開された GitHub リポジトリに残された資格情報と、 セッショントークンを収穫する偽サイトである**（出典3）—— **盗まれたアクセスは「LLM ミキサー」で売られ、 問い合わせの量が複数の被害環境に分散されるため、 1環境あたりの異常は小さく見える**（出典3）〈重要〉—— **月次の請求の確認では、1日10万ドルの速さに間に合わない** （本記録の評価）。
    取るべき行動 **LLM・GPU の利用に予算のしきい値と自動停止を設定する （時間単位で効くものにする）。** **LLM の API 資格情報を、クラウドの資格情報と同じ台帳に載せ、 有効期限と棚卸しの対象にする。** **公開リポジトリへの秘密情報の混入を、 コミット時と定期の走査の両方で検出する。** **短命のサービスアカウントの作成と削除の繰り返しを警報にする。**
  • 「検証できていないエクスプロイトの主張」への判断基準を、平時に決めておく。
    **PHP の2件（CVE-2026-109618・CVE-2026-109619）が 2026年10月21日に修正されると、 数日で数百件のエクスプロイトの主張が現れ、 多くは動作しなかった**（出典2・3）〈重要〉—— **AI によって生成されたものとみられる**（出典2）—— **結果として防御側は、どの報告が本物かを 確かめる作業に時間を割くことになった**（出典3）〈重要〉—— **これは攻撃の副作用として生じた防御側のコストである**（本記録の評価）—— **検証を待てば対処が遅れ、待たなければ空騒ぎに時間を使う。**
    取るべき行動 **「PoC の動作確認を待たずに対処する」条件を文書にする （例: CVSS・インターネット露出・認証の要否の組み合わせ）。** **エクスプロイトの主張の数を、危険度の指標として使わない （数百件のうち多くが動かない）。** **一次の情報源（製品ベンダーの勧告・CISA KEV）を 優先順位の決定の軸に据える。**
セキュリティ技術者への示唆
  • 自社が使っている公開のソフトウェア部品の在庫を作り、使っていないものを外す。
    **exploit_agent が差分解析の対象としていた例は、 WordPress プラグイン Spectra（Ultimate Addons for Gutenberg）2.19.25 の アクセス制御である**（出典1）〈重要〉—— **対象は「広く使われている Web アプリケーションのソフトウェア」で、 自社が書いたコードではない**（出典1）—— **つまり狙われるのは、入れたことを忘れやすい部品のほうである** （本記録の評価）—— **在庫が無ければ、修正が出たときに 自社が該当するかどうかを判断できない。**
    取るべき行動 **CMS のプラグイン・テーマ、ライブラリ、 公開されている管理インタフェースの在庫を作る （版まで記録する）。** **使われていないものを外し、 外せないものには「なぜ要るか」を記録する。** **在庫を脆弱性情報の照合に使える形（SBOM 等）にする。**
  • Web の公開ディレクトリを読み取り専用にする。
    **exploit_agent のステージングサーバには、 ウェブシェルを設置するスクリプトと、 他の攻撃者のウェブシェルを除去するスクリプトが置かれていた**（出典1・2）〈重要〉—— **後者は、同じ標的を複数の攻撃者が争っている状況を示す** （本記録の評価）—— **ウェブシェルの設置は、公開ディレクトリへのファイルの 書き込みとして現れる**（本記録の評価）—— **書き込めなければ、設置そのものが成立しない。**
    取るべき行動 **Web の公開ディレクトリを読み取り専用でマウントし、 配備は別の経路（CI からの入れ替え・コンテナの作り直し）に限る。** **公開ディレクトリのファイルの追加・変更を 完全性の監視で検出する。** **アップロードを受け付ける必要がある場合は、 実行されない別の領域に置く。**
  • 検知を「基盤の名前」ではなく「振る舞い」で書く。
    **Security Affairs は、侵害されたシステムで見つかる ARTEX の「指標」の多くが LLM やその道具によって生成されたもので、 基盤に組み込まれた固定の文字列ではないと指摘している**（出典3）〈重要〉—— **したがって、単一の文字列や署名を探すより 攻撃者の振る舞いを見るほうが有用である**（出典3）—— **モデルやプロンプトが変われば、文字列は変わる**（本記録の評価）—— **一方、自律的に走る基盤は速さのために痕跡を残すので、 振る舞いの側は見えやすい**（出典1・3）。
    取るべき行動 **Google SecOps が提供する ARTEX の検知規則群のような 基盤ごとの規則は導入するが、それだけに依存しない。** **振る舞いの検知を併せて書く—— 識別情報あたりの列挙 API の短時間での集中、 認証失敗の急増、未使用の鍵の再使用、 拒否された権限昇格、公開ディレクトリへの書き込み。** **自社で意図的にこれらを発生させ、警報が届くかを確認する。**
  • LLM の利用量を時間単位で監視し、しきい値を低く置く。
    **LLM ミキサーは、買い手の通信を盗まれた資格情報と 計算インスタンスの束に通すことで安定したアクセスを提供しつつ、 問い合わせの量を複数の被害環境に分散させて 検知される可能性を下げている**（出典3。原文英語）〈重要〉—— **つまり1環境あたりの異常は小さく見える**（本記録の評価）—— **一方で、Mandiant が対応した事案では 1日で10万ドルを超える課金が発生しており、 分散しても金額は積み上がる**（出典3）—— **ボットネットが約24時間で数百万回の API 呼び出しを行った例もある**（出典3）。
    取るべき行動 **LLM の API の呼び出し回数とトークン量を時間単位で記録し、 前時間比・前日比の急増を警報にする。** **しきい値を「月額の予算」ではなく 「通常時の時間あたりの量」から決める。** **GPU インスタンスの起動を警報の対象にし、 起動できる識別情報を限定する。** **CVE-2026-40217（LiteLLM のサンドボックス脱出）のような AI 基盤自体の脆弱性を、修正の対象に含める。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ インターネットに面した Web アプリケーション・機器の修正を、 月次などの定期サイクルでのみ適用しており、 「公表から適用まで」の実績日数を測っていない。
システム構成□ CMS のプラグイン・公開ライブラリ・公開された管理インタフェースの 在庫（版まで）を持っておらず、修正が出たときに 自社が該当するかを即答できない。
運用・監視□ 検知から封じ込めまでの全てが人の承認を要する作り（自動で止める範囲を 事前に線引きしていない）。
認証・認可□ LLM・生成AI の API 資格情報を、クラウドの資格情報と同じ台帳・ 同じ期限管理の対象にしていない。
体制・契約□ 公開されたエクスプロイトの主張（PoC・報告）を、 動作確認なしに優先順位の決定に使っている。
委託・第三者部品□ AI 基盤（LLM のゲートウェイ・推論の proxy・エージェント実行環境）を 自社で運用しており、それ自体の脆弱性を修正の対象に 含めていない。
