INC-2026-1140エコめがねが侵害、ポイント不正交換

NTT スマイルエナジーの太陽光発電遠隔監視サービス「エコめがね」が2026年10月28日に不正アクセスを受け、 同社は Web サーバでの検知から約6時間30分でクラウド環境の全サーバの通信を遮断した—— 第3報（11月13日）で原因は「ソフトウェアの脆弱性を悪用した不正アクセス」と確認され、 ポイント還元サービス「スマイルeポイント」では約14,000件・約800万ポイントがデジタルギフトコードへ不正交換された。 施主・パートナー企業の氏名・住所・電話番号・メールアドレスとログイン ID・パスワードが流出した可能性があるが、 第3報は「個人情報の外部流出の痕跡は現時点では確認されていない」としており、件数は精査中。 サービスは停止したままで、再開の目安は12月上旬頃

不正アクセス・侵害不正送金・資金詐取（主損害が金銭）続報が続いている日本の組織が当事者既知の脆弱性の悪用
初報: 2026年10月29日（0時10分・公式サイトの第一報） 最終更新: 2026年11月17日

NTT スマイルエナジー（大阪市）は2026年10月30日から11月13日にかけて、太陽光発電遠隔監視サービス「エコめがね」への不正アクセスについて3回の公表を行いました。

同社によれば、2026年10月28日20時20分に Web サーバで不審なアクセスの形跡を検知し、同日22時30分に Web サイトのサービス画面を緊急停止、10月29日2時50分にクラウド環境上の全サーバの通信を遮断して顧客情報を管理するデータベースサーバを緊急停止しました。外部専門機関とのログ解析でデータベースサーバへの攻撃の形跡が確認され、施主・パートナー企業の氏名または企業名・住所・電話番号・メールアドレス、およびサービスログイン用の ID とパスワードが流出した可能性があると判断されています（出典1）。

被害が金銭として現れたのはポイント還元サービス側です。「スマイルeポイント」で約14,000件・約800万ポイントが、換金目的とみられる第三者によってデジタルギフトコードへ不正に交換されました（10月30日 約1,500件・約100万ポイント、10月31日 約12,500件・約700万ポイント）。異常な交換急増を検知してポイント交換を止めたのは提携会社で、10月31日のことです（出典2）。

原因は第3報（11月13日）で「ソフトウェアの脆弱性を悪用した不正アクセス」と確認されました。同じ第3報は「個人情報の外部流出の痕跡は現時点では確認されていない」とも述べており、第1報の「流出した可能性がある」という判断との間に表現の幅があります〈齟齬1〉。本記録は、停止によって利用者が ID・パスワードを変更できない状態が続いたことと、ポイントの不正交換を自社では検知できなかったことを、評価の中心に置きます。評価・示唆は本記録の判断として分けて書きます。

    ここからは本記録の作成者の評価である。

    第一に、遠隔監視サービスの停止は「業務停止」として軽く見えて、実際には安全の監視が消える。発電・売電は続くのに、異常を知らせるアラートメールが届かない。つまり設備は動き続け、異常だけが見えなくなる。太陽光発電設備の異常はパワーコンディショナの停止や発電量の低下として現れるが、発火・地絡のような安全側の事象も含まれる。監視を前提に人手の巡回を減らしていた事業者は、停止期間のあいだ無監視で運転していたことになる。SaaS の停止影響を「売上が止まるか」でしか評価していない組織は、この型を見落とす。

    第二に、認証情報が漏れた疑いがあるときに、認証情報を変えられない停止の設計は痛い。環境全体を遮断する判断は封じ込めとしては速く、適切だった（本記録の評価）。しかしその結果、ログイン ID とパスワードの流出可能性を公表しながら、利用者にパスワード変更の手段を提供できない状態が1か月以上続いている。封じ込めの計画には「停止中も認証情報の無効化・リセットだけは行える経路」を別に用意しておく必要がある。一斉失効（全ユーザーのパスワードを無効化し、再開時に再設定させる）はサービスを止めたままでも実行できる手段であり、公表文からはその採否が読み取れない。

    第三に、金銭に換わる仕組みは、本体の停止とは別に止めなければならない。「エコめがね」の Web サイトは10月28日に止まったが、ポイント交換は10月31日まで動いていた。不正交換の約9割（約700万ポイント）は、本体を止めた後の10月31日に起きている。しかも急増を検知したのは提携会社である。ポイント・ギフトコード・クーポンのような換金性のある機能は、多くの場合、別の事業者の API の向こう側にある。侵害時の手順書に「提携先へ換金系機能の停止を要請する」という一行があるかどうかが、被害額の桁を決める。

    第四に、ポイントは「おまけ」ではなく現金等価物である。本事案で流出の確認が取れていないのは個人情報のほうで、実害として確定しているのはポイントの不正交換である。攻撃者から見れば、顧客情報の転売より、ギフトコードへの交換のほうが短時間で現金化できる。ポイント基盤を持つ事業者は、ポイント残高を決済システムと同じ監視水準で扱うべきである——交換の件数・金額の急増に対する閾値監視、1日あたりの交換上限、同一の宛先・短時間での連続交換の検知は、決済の不正検知では当たり前の仕掛けである。

    Web サイトのサービス画面を検知の約2時間後に停止し、約6時間30分後にクラウド環境上の 全サーバの通信を遮断してデータベースサーバを緊急停止した部分的に機能本記録の作成者の評価である。封じ込めの速さ（検知から約6時間30分で環境全体を遮断）は評価できる。 一方、ログイン ID とパスワードの流出可能性を公表しながら、本人がパスワードを変更できない状態が 1か月以上続いている。停止中も認証情報の一斉失効・再設定だけは行える経路を別に用意しておくべきだった
    検知から約3時間50分後（翌日0時10分）に公式サイトで第一報を掲載し、以後3回にわたり続報を出した機能した本記録の作成者の評価である。検知当日のうちに第一報を出し、検知時刻・停止時刻を分単位で示した点は 読者が経緯を検証できる形になっている。件数が精査中であることも明示されている

    発電・売電への影響がないことを明示したうえで、機能ごとに段階的な再開を計画した （発電状況とアラート履歴の確認を一部主要機能として先行再開する準備）部分的に機能本記録の作成者の評価である。利用者にとって最も価値が高い機能（発電状況とアラート履歴の確認）を 先行再開の対象に選んだ判断は妥当だが、停止から1か月近く経ってから「11月下旬に対象と時期を公表予定」 という段取りで、無監視期間の長さは変わらない
    CISO・経営層への示唆
    • 認証情報の流出が疑われるときに、停止したままでは本人が変えられないという詰みを想定しておく
      流出した可能性のある項目にログイン ID とパスワードが含まれているのに、 サービス停止によって利用者はパスワードを変更できない状態が1か月以上続いている
      取るべき行動 インシデント対応計画に「サービス停止中でも全ユーザーのパスワード・セッション・API キーを 一斉失効できる経路」を独立した手順として書き、年1回、停止状態を模した訓練で実行できるか確かめる。 再開時に強制再設定を求める方針もあらかじめ決めておく
    • 換金性のある機能は、本体の停止とは別の判断で止める
      「エコめがね」本体は10月28日に停止したが、ポイント交換は10月31日まで動き、 不正交換約14,000件・約800万ポイントのうち約9割が10月31日に起きた
      取るべき行動 ポイント・ギフトコード・クーポン・払い出しなど現金等価の機能を一覧にし、 各機能について「誰に連絡すれば止まるか」（自社／提携先）と連絡先・所要時間を手順書に書く。 侵害の初動チェックリストに「換金系機能の停止要請」を独立した項目として入れる
    • 遠隔監視サービスの停止影響を「売上が止まるか」で測らない
      発電・売電は継続したが、発電設備の異常を知らせるアラートメールが届かなくなり、 監視を前提に運用していた事業者は無監視で運転する期間が生じた
      取るべき行動 自社が提供・利用している監視サービスについて、停止時に「見えなくなるもの」を列挙し、 人手の巡回・代替の通知経路・判断の遅れの許容時間を含む代替運用手順を文書化して委託先と共有する
    • 提携先が先に気づく構造を前提に、相互通報の取り決めを作る
      ポイント交換の異常急増を検知してポイント交換を止めたのは提携会社で、 自社が件数を把握したのは提携会社からの回答を受けた11月4日だった
      取るべき行動 ポイント・決済・ギフトの提携契約に、異常検知時の相互通報の義務・連絡経路・ 回答期限（例: 24時間以内の一次回答）を明記し、連絡先リストを半年ごとに更新する
    • 公表では「件数が分からない」ことと「原因の種別」を分けて出し、点検に使える形まで寄せる
      第1報は検知・停止の時刻を分単位で示した一方、第3報の原因は「ソフトウェアの脆弱性を悪用」の一語で、 対象製品や既知／未知の区別が示されていない
      取るべき行動 公表テンプレートに「時刻（検知・停止・通知）」「対象項目」「件数の確定状況」「原因の種別」 「読者が自社で行える点検」の欄を用意し、確定していない欄は空欄ではなく 「精査中」「公表しない理由」として埋める運用にする
    セキュリティ技術者への示唆
    • ポイント残高を決済と同じ監視水準で扱う
      不正交換は2日間で約14,000件・約800万ポイントに達し、約9割が2日目に集中した
      取るべき行動 ポイント交換の件数・金額・宛先の分布に対する閾値監視（平常値比・時間あたり件数）を入れ、 閾値超過で交換 API を自動停止する。1 アカウント・1日あたりの交換上限と、 同一宛先への連続交換の検知も併せて設定する

      不正に読み取られたのは「管理番号・交換用 URL・ポイント数」で、交換はその後に実行された
      取るべき行動 交換用 URL を一度だけ使える短命トークン（発行から数十分で失効）にし、 利用時に本人の再認証を求める。既発行のトークンを一括失効できる管理機能を用意する
    • Web 層からデータベース層への到達を前提に、高価値テーブルの読み出しを監視する

    • パスワードは「漏れても使えない」保存形式にし、それを公表できる状態にしておく
      ログイン ID とパスワードが流出した可能性があると公表されたが、保存形式は示されておらず、 利用者は他サービスでの使い回しの危険度を判断できない
      取るべき行動 パスワードを計算コストの高いハッシュ（bcrypt・Argon2 等）＋ソルトで保存し、 平文・可逆暗号・単純ハッシュの残存を棚卸しで洗い出す。 公表文のテンプレートに「保存形式」の欄を設け、事案時に即答できるようにする
    • 外部公開のソフトウェア構成を台帳化し、脆弱性の公開から適用までを期限で管理する
      原因は「ソフトウェアの脆弱性を悪用した不正アクセス」と確認された
      取るべき行動 公開サーバの製品・版・プラグイン・ライブラリを SBOM 相当の台帳で持ち、 深刻度ごとの適用期限（例: 緊急は72時間以内）を定める。 期限内に適用できない場合は WAF の仮想パッチ等の代替策を記録に残す
