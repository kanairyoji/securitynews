INC-2026-1143NoisyTCP: Linux に11年の遠隔DoS

Linux カーネルの TCP ソケット検索に11年ぶんの競合状態が残っていた—— 研究者 Hyunwoo Kim が2026年11月15日に公開した「NoisyTCP」（CVE-2026-99288）は、 ロックフリーの established ハッシュ検索と SLAB_TYPESAFE_BY_RCU によるメモリ再利用が重なり、 SYN cookie 由来の request socket が同じ番地に作り直されると NULL ポインタ参照でカーネルパニックに至る。 認証も特別な設定も不要で、既定構成の Nginx・Apache・SSH が対象。 QEMU/KVM の仮想マシンでは5秒〜2分で落ち、コンテナ内の Web サーバを狙うとホストごと落ちる。 一方、RX キュー8本の物理サーバでは環境に合わせた PoC でも約14時間を要した。 原因コミットは2015年10月3日（Linux 4.4）、修正は2026年11月3日。確認された影響はリモートの DoS

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月15日（研究者による詳細の公開） 最終更新: 2026年11月17日

2026年11月15日、セキュリティ研究者 Hyunwoo Kim（@v4bel） が、Linux カーネルの TCP 実装の脆弱性「NoisyTCP」（CVE-2026-99288） の詳細を公開しました（embargo 解除にともなう公開・出典1）。

認証も特別な設定も要りません。 攻撃者に必要なのは、開いた TCP ポートと、その系が複数の受信キュー（RX キュー）または RPS で複数 CPU に振り分けてパケットを処理していることだけです。既定構成の Nginx・Apache・SSH がそのまま対象になります（出典1）。

仕組みは ABA 競合です。TCP の established ハッシュ（ehash）の検索はロックを取らずに行われ、ソケットのキャッシュは SLAB_TYPESAFE_BY_RCU でメモリを再利用します。ある処理が古くなったエントリを掴んでいる間に、別の処理が同じ番地に SYN cookie 由来の新しい request socket を作ってしまうと、タプルの照合は通るのにその新オブジェクトは listening socket への参照を持ちません。以後の NULL 参照でカーネルパニック——リモートからの DoS です（出典1・2）。

落ちる速さは環境で大きく変わります。QEMU/KVM の仮想マシンでは5秒〜2分。一方、RX キュー8本の静かな物理サーバでは、環境に合わせた PoC でも約14時間を要しました（出典1）。コンテナ内の Web サーバを狙った場合でも、落ちるのはホスト全体です。

原因コミットは 2015年10月3日（079096f103fa・Linux 4.4 以降）、修正は 2026年11月3日（4e2b3ef19e0e）。11年ぶんの潜伏です。Red Hat は深刻度を Important、CVSS v3.1 7.5（暫定）と評価しています（出典3）。研究者は第2の経路（本物の子ソケットでの use-after-free）にも触れていますが、確認されている影響はリモートの DoSで、汎用的な RCE は実証されていません。本記録は、評価・示唆を本記録の判断として分けて書きます。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

研究者 Hyunwoo Kim が2026年11月15日に公開した NoisyTCP（CVE-2026-99288）の要点は次のとおりである（出典1）。

  • 認証は不要。攻撃者が必要とするのは開いた TCP ポートだけ
  • 対象の系が2本以上の RX キュー、または RPS によって複数 CPU で受信処理を分けていること
  • アプリケーション側の特別な設定は不要で、既定構成の Nginx・Apache・SSH が対象
  • 成立するとカーネルパニック——系全体が落ちる（リモート DoS）
  • コンテナ内の Web サーバを狙っても、落ちるのはホスト全体

Red Hat は深刻度を Important、CVSS v3.1 基本スコアを 7.5（暫定）と評価している（出典3）。ベクタは CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H である。ここには読者が注意すべき食い違いがある〈齟齬1〉——研究者と報道は認証不要としているのに、ベクタは PR:L（低い権限を要する）になっている。

ロックを取らない検索と、番地を使い回す slab が重なったときの ABA 競合原因・手口出典 [1] [2]

技術的な中身は次のとおりである（出典1・2）。

TCP の established ハッシュ（ehash）の検索はロックを取らない（ロックフリー）。一方、ソケットのキャッシュは SLAB_TYPESAFE_BY_RCU を使っており、解放されたメモリが同じ型の新しいオブジェクトに再利用される。従来のコードは、検索でタプル（接続の4つ組）が一致して参照を取得した後に、そのオブジェクトがまだハッシュに繋がっているか（unhashed でないか）を確認していなかった（出典2）。

攻撃者はここに2つの経路を見つけている（出典1）。

①request_sock 再利用の ABA 競合（確認された経路）ある受信処理が古い参照をたどって解放済みの request socket を見つけている間に、別の受信処理が SYN cookie 経由で同じ slab 番地に新しい request を割り当てる。接続パラメータの照合は通るが、新しいオブジェクトには listening socket への参照が無い。続く NULL ポインタ参照でカーネルパニック——リモート DoS である。

②本物の子ソケットでの ABA 競合（困難な経路）こちらは use-after-free に至り得るが、入れ子になった複数の競合が必要で、研究者自身が「一般には困難」としている。

競合を起こすには異なる受信コンテキストでの並行処理が要る。研究者が使ったのは、IPv4 フラグメントと通常の TCP パケットが異なる受信キューに振り分けられる性質である。このため、2本以上の RX キューまたは RPS 有効が前提になる（出典1）。

修正（2026年11月3日・4e2b3ef19e0e）は、参照を取得した後に unhashed かどうかを確認し、該当する場合やタプルが一致しない場合は参照を解放して検索をやり直す形に変えた。SYN cookie・Fast Open・request migration の各経路では、失敗時に reqsk_put() で参照を解放するようになった（出典2）。

仮想マシンでは5秒で落ちるが、物理サーバでは14時間かかった被害規模・影響範囲出典 [1] [5]

再現の難しさは環境で大きく変わる（出典1）。

環境 対象 所要
QEMU/KVM 仮想マシン（既定設定） Nginx・Apache・SSH 5秒〜2分
「静かな」物理サーバ（RX キュー8本・既定設定） Nginx 約14時間（環境に合わせて調整した PoC）

差の理由は競合の窓の広さである（出典1・5）。成立にはソケットのパラメータ照合と参照カウントの加算の間の、きわめて狭い時間差に入る必要がある。仮想マシンでは仮想 CPU の切り替えがこの窓を広げるため、はるかに当たりやすい。

ここから読み取れる実務上の含意がある（本記録の評価）。クラウドの仮想インスタンスとコンテナのホストが、最も危険な置き場である。しかもコンテナ内の Web サーバを狙っても落ちるのはホストなので、1つのテナントのアプリケーションを狙う攻撃が、同じホストに載った他の全ワークロードを巻き込む。一方、トラフィックの多い本番の物理サーバでは、14時間という数字がそのまま当てはまるとは限らない——研究者の14時間は「静かな」環境での値であり、本番の負荷が競合の成立にどう影響するかは示されていない（本記録の明示）。

当てるのが本線、当てられないなら SYN cookie を切るか RX キューを1本にする対策・注意喚起出典 [1] [2] [3] [4]

対策の優先順位は明快である（出典1・3）。

Habr は Linux CVE チームの通知として 6.12.117・6.18.63・7.3.4 を挙げているが、本記録の作成者は通知そのものを取得していない〈未確定3〉。自分のディストリビューションが修正済みカーネルを出しているかを個別に確認する必要がある（出典4）。

一時策①: SYN cookie を無効化する。

sudo sysctl -w net.ipv4.tcp_syncookies=0

確認された経路（request_sock の再作成）を塞ぐ。ただし代償が2つある（出典1・3）。

  • SYN flood への防御が弱まる
  • 設定はネットワーク名前空間ごとに効くため、独自の netns を持つコンテナには個別に適用しなければならない

一時策②: RX キューを1本に制限し、RPS と RFS を無効化する。競合の前提である「異なる受信コンテキストでの並行処理」を取り除く。代償はネットワーク性能で、低下の程度は示されていない〈未確定6〉。

いずれも恒久策ではない。研究者もディストリビュータも、一時的な措置として位置づけている。

悪用の実例・RCE の可否・修正版の全体像は確認できていない未確定事項出典 [1] [2] [3]

2026年11月17日時点で、次の点は確認できていない。

  • 実環境での悪用の有無（研究者・ディストリビュータ・報道のいずれも事例を示していない）
  • RCE の実現可能性（第2経路は use-after-free に至り得るが「一般には困難」。公開されているのは仮想マシン向けの限定的な検証用 exploit のみ）
  • 修正が反映されたカーネル版の全体像（本記録が確認できたのは Debian の修正版のみ）
  • Red Hat のベクタにおける PR:L の根拠と、DoS のみの影響に C:H/I:H が付く理由〈齟齬1〉
  • IPv6 のみの環境での成立条件
  • 緩和策を適用した場合の性能低下の程度

「カーネルの脆弱性はコンテナ分離を素通りする」が、この一件の要点（本記録の評価）評価・解釈出典 [1] [2] [3] [4] [5]

ここからは本記録の作成者の評価である。

第一に、コンテナの分離はカーネルの脆弱性に対して何の壁にもならない。本件の最も重い性質は、コンテナ内の Web サーバを狙うとホストごと落ちるという点である。名前空間と cgroup はカーネルを共有したまま資源と視界を分けているだけで、カーネルが panic すれば同じホストの全コンテナが同時に消える。マルチテナントのコンテナ基盤では、1つのテナントの公開ポートが、そのノードに載った全テナントの可用性の単一障害点になる。「アプリケーションは隔離してある」という説明は、カーネルの脆弱性には適用できない。

第二に、クラウドの仮想インスタンスが最も当たりやすいという逆転が起きている。一般に、攻撃の再現は本番の物理機より実験環境のほうが難しいと考えがちだが、本件では仮想 CPU の切り替えが競合の窓を広げるため、仮想マシンのほうが桁違いに落としやすい（5秒〜2分 対 約14時間）。クラウド上の VM が主たる本番環境である組織は、「研究環境でしか再現しない脆弱性」として扱うと判断を誤る。

第三に、緩和策の代償が「別の攻撃に弱くなる」形をしている。 SYN cookie の無効化は、SYN flood に対する防御を外すことと等価である。つまりカーネルパニックの経路を塞ぐ代わりに、古典的な DoS に戻る。しかも netns ごとの設定であるため、コンテナを数えて漏れなく適用する作業が要る。RX キューを1本にする側は性能を失う。どちらも「一時策」と呼ばれるが、実際には更新までの日数ぶんだけ、別のリスクを引き受ける選択である。緩和策を選ぶ判断には、更新完了までの見込み日数を先に決めておく必要がある。

第四に、CVSS のベクタを読まずにスコアだけで優先順位を決めると取り違える。 Red Hat の 7.5 は暫定値であり、ベクタには PR:L（権限を要する）が含まれている。一方、研究者と報道は認証不要としている。また、確認された影響はリモートの DoS なのに、ベクタには C:H/I:H が入っている。スコアの数字だけを見て「7.5 なら中程度」と扱うと、「認証不要でホストを落とせる」という本質を見落とす。脆弱性管理では、ベクタの各項目と、発見者の記述の両方を読む必要がある。

第五に、11年という潜伏期間は「古いコードは枯れている」という前提を揺らす。原因コミットは2015年、Linux 4.4 である。この間、ehash の検索はおそらく地球上で最も実行回数の多いコード経路の一つだった。それでも気づかれなかったのは、成立に必要な時間差が極端に狭く、偶然では起きない性質だったからである。ロックフリーのデータ構造と slab の型安全な再利用の組み合わせは、性能のために採られた設計であり、その副作用は実行回数では洗い出せない（本記録の評価）。同種の問題は他のサブシステムにも残っている可能性がある。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
IPv4 フラグメントで受信処理を分け、SYN cookie で同じ番地に request を作らせるまでの経路
layer 0 は攻撃者。layer 1 は送り込むパケット（IPv4 フラグメントと通常の TCP パケット）。 layer 2 は複数の RX キュー／RPS による別々の受信コンテキスト。 layer 3 はロックフリーの ehash 検索と SLAB_TYPESAFE_BY_RCU による slab 番地の再利用。 layer 4 は listening socket への参照を持たない新しい request socket と、 それを参照した結果のカーネルパニック。layer 5 は落ちる範囲——ホストと、その上の全コンテナ。 確認された影響はリモートの DoS で、汎用的な RCE は実証されていない。

対応の評価

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • コンテナの分離をカーネル脆弱性に対する防御として数えない
    コンテナ内の Web サーバを狙った攻撃でも、カーネルパニックによって落ちるのはホスト全体であり、 同じホスト上の他のワークロードも巻き込まれる
    取るべき行動 マルチテナントのコンテナ基盤について、「1ノードのカーネルが落ちたとき何が止まるか」を テナント単位で整理する。外部からの通信を受けるワークロードと、 重要度の高い内部ワークロードを別ノード・別ノードプールに分ける方針を決める
  • 仮想マシンが最も当たりやすいという逆転を、優先順位に反映する
    QEMU/KVM の仮想マシンでは5秒〜2分でカーネルパニックに至った一方、 RX キュー8本の物理サーバでは調整した PoC でも約14時間を要した
    取るべき行動 カーネルの更新計画で、クラウド・仮想化基盤上のインスタンスを物理サーバより先に扱う。 「検証環境でしか再現しない」という理由で優先度を下げる判断を、ベクタと発見者の実測で見直す
  • 一時策の採用は「別のリスクを引き受ける期間」を決めてから行う
    SYN cookie の無効化は SYN flood への防御を弱め、RX キューを1本にする策はネットワーク性能を損なう。 いずれも一時的な措置として位置づけられている
    取るべき行動 緩和策を適用する際は、適用の決裁に「本修正の適用予定日」を必ず含め、 その日までに更新できない場合の再評価を予定に入れる。緩和策を適用した資産の一覧を別に管理し、 更新後に元の設定へ戻す作業を完了まで追跡する
  • CVSS のスコアだけでなくベクタと発見者の記述を読んで判断する
    Red Hat の CVSS v3.1 スコアは 7.5（暫定）だが、ベクタには PR:L（権限を要する）が含まれ、 研究者・報道は認証不要としている。確認された影響は DoS なのにベクタは C:H/I:H を含む
    取るべき行動 脆弱性管理の基準に「スコアの単独使用を禁じ、ベクタの AV/PR/UI と発見者・ベンダーの記述を 併せて確認する」ことを明記する。スコアが暫定の段階では、再評価の時点を記録して追跡する
  • カーネル更新に伴う再起動の段取りを、平時に整えておく
    本線の対策は修正を含むカーネルへの更新であり、ライブパッチを使わない場合は再起動が必要になる
    取るべき行動 システムごとに「無停止で再起動できるか」を棚卸しし、できない系には ローリング再起動の手順かライブパッチの契約を用意する。 カーネル更新に要する調整期間を把握し、緊急時の目標時間を定める
セキュリティ技術者への示唆
  • 修正コミットと自分のカーネル版の対応を自力で突き合わせる
    原因コミットは 079096f103fa（2015年10月3日・Linux 4.4 以降）、修正は 4e2b3ef19e0e（2026年11月3日）で、 実際に脆弱かはディストリビューションのビルドと修正の取り込み状況で決まる
    取るべき行動 稼働中のカーネル版（uname -r）と、ディストリビューションのセキュリティ勧告 （Debian なら DLA-4906-1・DSA-6628-1）を突き合わせる。 自前ビルドのカーネルを使っている系は、修正コミットが含まれているかを直接確認する
  • SYN cookie の設定はネットワーク名前空間ごとに適用する
    net.ipv4.tcp_syncookies はネットワーク名前空間ごとに管理されるため、 独自の netns を持つコンテナには個別に適用しなければならない
    取るべき行動 緩和策として SYN cookie を無効化する場合は、ホストだけでなく独自 netns を持つ全コンテナを列挙し、 適用漏れを確認する手順を作る。設定が意図どおりか、各 netns で sysctl を読んで検証する
  • 外部に開いた TCP ポートを減らし、管理用ポートを直接公開しない
    攻撃に必要なのは開いた TCP ポートだけで、既定構成の SSH も対象になる
    取るべき行動 外部公開のポートを棚卸しし、SSH をはじめとする管理用ポートは VPN・踏み台・ ゼロトラストのプロキシの背後に移す。残した公開ポートは接続元を制限する
  • カーネルパニックを記録できる状態を保つ
    影響はカーネルパニックによる系全体の停止であり、Debian の記録には NULL ポインタ参照の クラッシュ例が示されている
    取るべき行動 kdump（またはクラウドのシリアルコンソールログ）を有効にし、クラッシュダンプの保存先と 容量を確保する。再起動後にダンプを回収して原因を特定できる手順を用意する
  • 受信処理の分散設定（RX キュー・RPS/RFS）を把握しておく
    攻撃の前提は、受信処理が2本以上の RX キューまたは RPS によって複数の受信コンテキストに分かれていることである
    取るべき行動 ethtool -l でインターフェースの RX キュー数を、/sys/class/net/*/queues/rx-*/rps_cpus で RPS の設定を確認し、構成を資産情報に記録する。緩和策②を検討する系では、 変更前の性能値を測っておき、戻す際の判断材料にする
  • ロックフリーの設計と型安全な slab 再利用の組み合わせを、自前のコードでも疑う
    原因はロックフリーの ehash 検索と SLAB_TYPESAFE_BY_RCU によるメモリ再利用が重なった ABA 競合で、 参照取得後にオブジェクトがまだ有効かを確認していなかった
    取るべき行動 自社でロックフリーのデータ構造やオブジェクトプールを実装している場合、 参照を取得した後に「そのオブジェクトがまだ目的のものか」を再検証する手順が入っているかを確認する。 競合の検出には実行回数ではなく、意図的な遅延の挿入やサニタイザ（KASAN 相当）を使う

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Linux カーネル 4.4 以降のサーバがインターネットから直接 TCP パケットを受けている （Nginx・Apache・SSH を含む）攻撃には開いた TCP ポートだけが必要で、認証もアプリケーション側の特別な設定も不要
システム構成□ 本番の主要な系が QEMU/KVM などの仮想マシン上にある仮想マシンでは仮想 CPU の切り替えが競合の窓を広げ、5秒〜2分で落ちた （物理サーバでは調整した PoC でも約14時間）
システム構成□ 1つのホスト上で複数テナント・複数ワークロードのコンテナを動かしており、 そのうち1つでも外部からの通信を受けているコンテナ内の Web サーバを狙った攻撃でもホスト全体が落ち、同居するワークロードを巻き込む
運用・監視□ 受信処理が2本以上の RX キュー、または RPS/RFS によって複数 CPU に分散しているこの並行処理が競合の成立条件であり、単一キューでは成立しない
運用・監視□ カーネル更新のために再起動を調整できる手順（ローリング再起動・ライブパッチ）が無い本線の対策は修正を含むカーネルへの更新であり、一時策はいずれも別のリスクを伴う
体制・契約□ 脆弱性の優先順位づけを CVSS のスコアのみで行っており、ベクタや発見者の記述を参照していない本件のスコアは暫定の 7.5 で、ベクタの PR:L は研究者の「認証不要」という記述と整合しない
