攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**経路は、既存の感染を足場に正規の遠隔管理ツールを設置し、 そこから3点組（正規実行ファイル＋悪性ローダ＋暗号化本体）を置き、 クラウドサービスを C2 にする裏口を記憶上で動かし、 必要な能力をシェルコードで取り寄せる流れである** （出典1。本記録の整理）〈重要〉。 **初期侵入の入口は特定されていない**（出典1）〈未確定2〉—— **台湾の組織では MeshCentral Agent の2つの実体が見つかり、 固定の C2（wss://27.102.66[.]162:443/agent.ashx）へ接続していた**（出典1）。 **そのエージェント経由で、 ①横読み用の正規の実行ファイル、②悪性ローダ DLL、 ③暗号化された本体ファイル（config.ini）が置かれた**（出典1）。 **ローダは本体を復号して現在のプロセスの記憶上に注入する**（出典1）—— **復号された本体は既に記憶上の配置済み形式になっており、 MZ ヘッダへ飛ぶと起動用コードが再配置と取り込みの解決を行う**（出典1）。 **裏口は C2 をクラウドサービスの背後に隠す**（出典1）〈重要〉—— **GitDoor は GitHub の issue とリポジトリ内のファイルで 命令・データ・生存信号をやり取りし、 GraphDoor は Microsoft SharePoint を使う（詳細は第2部）。** **追加能力は、要求に応じたプラグインの取得と、 多くが COFF 形式のシェルコードの記憶上注入で足される**（出典1）。

  2. 2. 実行third_party_research[1]
    **攻撃者は MeshCentral Agent の C2 セッション経由で 3点組を端末に置いた**（出典1）〈重要〉—— **①DLL 横読み用の正規の実行ファイル、 ②復号と実行を担う悪性ローダ DLL、 ③暗号化された本体（config.ini）。** **1組目は C:\windows\system32\ に Sandboxie の start.exe・SbieDll.dll・config.ini、 2組目は C:\Windows\system32\dts\pc\apo4x\ に Python の実行ファイル・python39.dll・config.ini である**（出典1）。 **ほかに OpenJDK の javaw.exe ← jli.dll、 Sysinternals の zoomit.exe（Windows サービスとして起動）、 WINMM.dll・libcef.dll の組み合わせが確認されている**（出典1）。

  3. 3. 検知回避third_party_research[1]
    **ローダは2系統あり、いずれも本体を復号して 現在のプロセスの記憶上に注入する**（出典1）〈重要〉—— **Type 1 は独自文字集合の Base64 → RC4（標本ごとの16バイト鍵） → XOR（標本ごとの16バイト鍵）の多層で、 さらに RtlEthernetAddressToStringA と RtlEthernetStringToAddressA を悪用して バイト列を MAC アドレス文字列に変換して戻すという 回避の工作を挟む**（出典1）—— **API 名の解決は CRC32（別標本では FNV-1）のハッシュで行い、 ライブラリ名と API 名は固定の7バイト鍵で XOR されている**（出典1）。 **Type 2（SbieDll_st.dll）は実行前に関門を置く**（出典1）〈重要〉—— **KERNEL32.DLL と KernelBase.dll に特定のバイト列を探し、 見つかればベクタ例外ハンドラを設置して CONTEXT.DR7 をゼロにし（ハードウェアブレークポイントの無効化）、 現在のプロセス名が固定値と一致するかを検証する**（出典1）—— **Windows 8 以降では NtAllocateVirtualMemory・RtlMoveMemory・ NtCreateThreadEx の native API を使い、 それ以前では標準 API に退避する**（出典1）。 **裏口自身も制御フローの平坦化と多層の間接呼び出しを持つ**（出典1）。
    根拠: Securelist 第1部の「Loaders」節（Type 1／Type 2 の復号手順・API ハッシュ・DR7 のゼロ化・プロセス名検証）および「Backdoors」節の難読化の記述（出典1）

本件の中心は、マルウェアの精巧さではなく C2 の置き場所である（出典1）。

GitDoor は GitHub を使う。手順はこうである（出典1）。

  1. 攻撃者の口座 LatonyCharnleyaW の2リポジトリを使い分ける—— Havo が命令と追加モジュールの置き場、Trix が窃取データと実行結果の受け皿
  2. 感染端末ごとに GitHub の issue を立て、本文に個体識別の符号を置く
  3. 窃取データと結果は AES で暗号化し、さらにファイル名で XOR を掛けてリポジトリ内のファイルとして置く
  4. issue に付ける 「bug」ラベルの入切を生存信号にする
  5. リポジトリを定期に見て、新しい命令を取る

補助経路として、固定の権限符号で rest.ably.io に接続し、チャネル経由でもデータを送る。失敗すると第2のチャネルで再試行する（出典1）。

ここで効かなくなるのは、宛先の評価に基づく検知である（本記録の評価）。新規に登録された領域、無名の領域、評判の悪い IP——こうした指標はすべて空振りする。github.com への HTTPS 通信は、開発部門を持つ組織では恒久的に許可されていることが多い。

残る足場は「どのプロセスがそこへ出ているか」である（本記録の評価）。本件では、横読みの覆いに使われたのはSandboxie の start.exe、Python の実行ファイル、OpenJDK のjavaw.exe、Sysinternals の zoomit.exe である（出典1）。これらが GitHub の API を定期に叩き続ける形は、正規の利用とは筋が違う。

足場は正規の遠隔管理ツールで、入口は分からないままである発覚の端緒出典 [1]

調査の端緒は、台湾の組織の内部で動いていた MeshCentral Agent の2つの実体だった（出典1。MD5: 74b025084026d8d9a64661bf995d835b）。MeshCentral は遠隔デスクトップ操作・コマンド行アクセス・ファイル管理を提供する正規の Web ベースの道具である。

エージェントは wss://27.102.66[.]162:443/agent.ashx へ接続するよう固定で書かれていた。C2 セッションが確立すると、攻撃者はこのエージェント経由で3点組を置いた（出典1）。

  • DLL 横読み用の正規の実行ファイル
  • 復号と実行を担う悪性ローダ DLL
  • 暗号化された本体（config.ini）

実際の配置は次の2組である（出典1）。

組 正規実行ファイル 悪性ローダ 暗号化本体

ディスクに残るのは config.ini だけで、本体は記憶上にしかない原因・手口出典 [1]

ローダは2系統ある。いずれも本体を復号し、現在のプロセスの記憶上に注入する（出典1）。ディスクに残るのは暗号化された config.ini だけで、名前と拡張子だけ見れば設定ファイルである。

Type 1（jli.dll 等）は多層である（出典1）。

  1. 独自の文字集合による Base64 復号
  2. RC4（16バイト鍵・標本ごとに異なる）
  3. XOR（16バイト鍵・標本ごとに異なる）
  4. RtlEthernetAddressToStringA でバイト列を MAC アドレス文字列に変換し、RtlEthernetStringToAddressA で戻して AllocADsMem で確保した記憶に書く（防御回避のための工作）
  5. VirtualProtect で PAGE_EXECUTE_READWRITE にし、MZ ヘッダへ飛ぶ

API 名の解決は CRC32（別の標本では FNV-1）のハッシュで行い、ライブラリ名と API 名は固定の7バイト鍵で XOR されている（出典1）。

Type 2（SbieDll_st.dll）は実行前に関門を置く（出典1）。

  • KERNEL32.DLL と KernelBase.dll に特定のバイト列を探す
  • 見つかればベクタ例外ハンドラを設置し、CONTEXT.DR7 をゼロにしてハードウェアブレークポイントを消す
  • 現在のプロセス名が固定値と一致するかを検証する
  • Windows 8 以降では NtAllocateVirtualMemory・RtlMoveMemory・NtCreateThreadEx を使い、それ以前は標準 API に退避する

関門は、解析環境と「想定外の場所での実行」を弾くためのものである（本記録の評価）。つまり検体を取って動かす調査も妨げられる。

防御側の含意は単純である（本記録の評価）。ファイルの中身で見つけようとしない。 着目すべきは前段（正規実行ファイルがどこから DLL を読んだか）と後段（どのプロセスがどこへ出ているか）である。

解析を妨げる作り込みの一方で、スレッド名が機能を露呈していた評価・解釈出典 [1]

GitDoor と GraphDoor は、解析を妨げる作りを多層に持つ（出典1）。

  • 制御フローの平坦化 —— 本来の実行の流れを隠す
  • 間接呼び出しの多用 —— 処理を何層もの補助関数で包み、順に呼び合わせる。中核の処理は入れ子の奥にあり、解析者は各層を辿らざるを得ない
  • スレッドへの分割 —— 実行は複数のスレッド部品に分かれ、各スレッドは C++ の ably 名前空間の Client クラスの実体である

ところが、ここに攻撃者側の落ち度がある（本記録の評価）。Kaspersky は、クラス名と名前空間が壊れた（mangled）C++ のスレッド関数名から判明したと記し、さらに「付随するラムダ名が各スレッドの実装する悪性機能を正確に露呈していた」と述べている（出典1。原文英語）。

つまり、実行の流れを隠す労力は払われている一方で、記号名の処理が甘く、機能が名前から読めてしまっている。

加えて、名前空間が ably であることは設計の出自を示している（本記録の評価）。両裏口が Ably のメッセージングを共通の部品として持っていることと整合する。
