INC-2026-1147Telegram ウィジェットで WebRAT 配布か

**Telegram は2026年11月10日、 メッセージの吹き出しの中で HTML のウィジェットを動かす機能を Bot API 10.4 として公開し、 Pavel Durov は「Telegram のどのメッセージも アプリになりうる」と述べた**（出典1・2）〈重要〉。 **翌11日、研究者集団 V12 が 「Telegram のどのメッセージも RCE になりうる」という題で ボットとの対話から Android 端末の電卓アプリが起動する動画を公開した** （出典4・5）—— **Telegram は同日「問題は前日に修正し、 修正は本日すべての利用者へ展開した」と応じた**（出典5。原文英語）。 **その後 V12 は、修正後の Windows 版でも別の RCE が成立すると主張する 2本目の動画を公開した**（出典4・5）〈重要〉—— **研究者らは、メッセージの中で JavaScript エンジン QuickJS を 砂箱なしで動かせること自体が攻撃面として大きすぎると述べている**（出典4・5）。 **11月13日未明、Kaspersky は 「この脆弱性に関係すると推定される」悪性活動を確認したと公表した** （出典3・4・6）〈重要〉—— **一部のチャネルを訪れると利用者に気づかれずに PowerShell スクリプトが 起動し、Rust 製の WebRAT（別名 Salat Stealer）を取得・実行する。** **同日 Durov は「問題は存在しない。 メッセージを受け取るだけで誰かが侵害されることはなかった」と反論した**（出典2）—— **ウィジェットと WebRAT の配布の関係は推定にとどまる**（出典4）。

Telegram は2026年11月10日、Bot API 10.4 として 「Widget Revolution」と題した機能を公開した（出典1）〈重要〉—— 公式の案内は「HTML のウィジェットが、 メッセージの吹き出しの中に独自の動的な画面を持ち込む—— ボットと AI エージェントに、対話的な道具・ゲーム・業務の流れのための 新しい画布を与える」としている（出典1。原文英語）—— 同日 Pavel Durov は自身のチャネルで 「Telegram のどのメッセージもアプリになりうる。 瞬時にダウンロード（わずか4KB）、対話的でネイティブに描画、 支払いと拡散の仕掛けを内蔵」と述べた（出典2。原文英語）。 翌11月11日、研究者集団 V12 が 「Telegram のどのメッセージも RCE になりうる」という題で動画を公開した （出典4・5）〈重要〉—— ボットとの対話が Android 端末の電卓アプリの起動に至る内容だった。 Telegram は同日、 「この問題は前日に修正し、修正は本日すべての利用者へ展開した」と応じた （出典5。原文英語）。 しかし V12 は2本目の動画を公開し、 修正後の Windows 版クライアントでも別の RCE が成立すると主張した（出典4・5）〈重要〉—— 研究者らの主張の核は、 メッセージの中で JavaScript エンジン QuickJS を砂箱なしで動かせること 自体が攻撃面として大きすぎるという点である（出典4・5）。 2026年11月13日未明、Kaspersky は自社のロシア語チャネルで、 この脆弱性に関係すると推定される悪性活動を確認したと公表した （出典3・4・6）〈重要〉—— 一部のチャネルを訪れると、利用者に気づかれずに PowerShell スクリプトが 起動し、既知のマルウェアを取得・実行する—— それが Rust 製の WebRAT（別名 Salat Stealer）で、 遠隔操作に加えて暗号通貨の財布と Telegram の口座の情報を盗む。 同じ11月13日、Durov は 「新しい TG の Android／Windows のウィジェットにおける いわゆる RCE について——問題は存在しない。 メッセージを受け取るだけで誰かが侵害されることはなかった。 利用者が自ら第三者のサービスを起動する必要があった。 それも server 側で完全に修正済みである」と反論した（出典2。原文英語）〈重要〉—— Kaspersky は、修正が出るまでウィジェットを起動しないよう 勧告している（出典3・4）。 本記録が重く見るのは、この3日間の構図である（本記録の評価）〈重要〉—— 機能の公開（10日）→ 実証の公開（11日）→ 悪用の疑いの観測（13日）が 連続しており、かつ当事者と研究者・ベンダーの見解が いまも一致していない。

公表から悪用の疑いの観測まで3日である（本記録が算出）。

この速さ自体が本件の要点である（本記録の評価）。メッセージの吹き出しの中で HTML と JavaScript を動かす機能は、公開の翌日に実証を呼び、3日後には悪性活動と結び付けられた。

ただし結び付けは推定にとどまる（出典3・4）。Kaspersky 自身が「предположительно связанную（関係すると推定される）」と書いており、Xakep も「関係はいまのところ推定にとどまる」と明記している（出典4）。

「修正した」と「問題は存在しない」が同じ主体から出ている評価・解釈出典 [2] [5]

本件でもっとも扱いに注意が要るのは、Telegram 側の説明である（本記録の評価）。

11月11日、V12 の Android 版の実証に対して、Telegram はこう応じた（出典5。原文英語）。

この問題は前日に修正され、修正は本日すべての利用者へ展開された

11月13日、Durov は自身のチャネルでこう述べた（出典2。原文英語。本記録が2026年11月18日に公開のチャネルの表示から直接確認）。

新しい TG の Android／Windows のウィジェットにおけるいわゆる RCE について——問題は存在しない。メッセージを受け取るだけで誰かが侵害されることはなかった。利用者が自ら第三者のサービスを起動する必要があった。それも server 側で完全に修正済みである。そう思わないなら私の口座を破ってみてほしい

2つは整合しにくい（本記録の評価）。「修正した」ことと「問題は存在しない」ことは両立しづらい。 後者の文中でも「それも server 側で完全に修正済みである」と述べており、何かを修正したことは認めている。

読み方としては、「メッセージの受信だけで成立する攻撃（ゼロクリック）は存在しない」という限定の主張として理解するのがもっとも整合的である（本記録の推定）。実際、Durov は「利用者が自ら第三者のサービスを起動する必要があった」と条件を述べている。

だがこの限定は、Kaspersky の記述と噛み合わない（本記録の評価）。Kaspersky が示した経路は「一部のチャネルを訪れると、利用者に気づかれずに PowerShell スクリプトが起動する」である（出典3・4・6）。「気づかれずに」と「自ら起動する必要があった」の差は、本件のもっとも重要な食い違いである〈齟齬1〉。

そして技術的な詳細がどちらからも出ていないため、外部からはどちらが実態か判断できない〈未確定4〉。

指摘されているのは個別の欠陥ではなく、機能の範囲である原因・手口出典 [4] [5]

V12 の主張は、特定のバグの指摘にとどまらない（出典4・5）。

研究者らの核心は、メッセージの中で JavaScript エンジン QuickJS を砂箱（sandbox）なしで動かせること自体が、全体として攻撃面を大きくし過ぎているという点である（出典4・5）。

この指摘の形は重要である（本記録の評価）。個別の欠陥であれば修正すれば終わる。だが「機能の範囲の決め方」への指摘であれば、1つ直しても次が出る。実際、Telegram が Android 版を修正したと述べた後に、V12 は Windows 版での別の RCE を主張している（出典4・5）。

Durov 側の公表の文面も、設計の意図を示している（出典2。原文英語）。

Telegram のどのメッセージもアプリになりうる。瞬時にダウンロード（わずか 4KB）、対話的でネイティブに描画、支払いと拡散の仕掛けを内蔵

「わずか4KB」で「どのメッセージにも載る」ことが売りである。軽さと普遍性は、そのまま攻撃面の広さに対応する（本記録の評価）。

公式の Bot API 10.4 の案内も同じ方向を示す（出典1。原文英語）——ウィジェットは「問い合わせを送って回答を受け取れ」、「ボットはウィジェットをその場で更新できる」、「共有されたウィジェットは複数のメッセージで同じ画面を再利用でき、中央の設定から即座に更新できる」。

つまり、攻撃者がボットを用意すれば、相手の画面の中で動く対話的なコードを後から差し替えられる（本記録の評価）。これは機能の説明をそのまま読んだ帰結である。

配られたのは暗号資産と Telegram 口座を狙う Rust 製の RAT だった被害規模・影響範囲出典 [3] [4] [6]

Kaspersky が観測した活動の中身は、次のとおりである（出典3・4・6）。

  • 一部のチャネルを訪れると、利用者に気づかれずに PowerShell スクリプトが起動する
  • スクリプトが既知のマルウェアを取得・実行する
  • それが WebRAT（別名 Salat Stealer）である

WebRAT の性質（出典4）。

項目 内容
実装 Rust 製
能力 運用者による感染系の遠隔操作
窃取 暗号通貨の財布のデータ、Telegram の口座のデータ

PowerShell が使われることから、対象は Windows 環境とみられる（本記録の推定）。ただし Kaspersky は OS も版も公表していない〈未確定1〉。

狙いの性質には注意が要る（本記録の評価）。盗まれるのは暗号資産と Telegram の口座であり、一見すると個人の被害である。だが Telegram の口座が取られれば、その利用者が業務で参加しているチャネルと対話も掌握される。 業務連絡に Telegram を使っている組織では、個人の被害として閉じない。

なお Kaspersky は、自社の対策製品が WebRAT を既に検知すると述べている（出典4）。

PowerShell の起動元を見れば、この経路は検知できる対策・注意喚起出典 [3] [4] [6]

本件の技術的詳細は公表されていないが、観測された挙動のうち1点は防御側で使える（本記録の評価）。

メッセンジャーのクライアントが PowerShell を起こす形は、正規の動作ではまず起きない。

Kaspersky の記述では「利用者に気づかれずに PowerShell スクリプトが起動し、マルウェアを取得・実行する」とある（出典3・4・6）。この形は、親プロセスと子プロセスの組み合わせとして明瞭である。

したがって次の手当てが効く（本記録の評価。出典の勧告ではない）。

  1. 親子関係での検知 —— メッセンジャーのクライアント（Telegram に限らず）を親とする powershell.exe ／ cmd.exe の起動を警報にする
  2. PowerShell の方針 —— スクリプトの署名要求、制約言語モード（Constrained Language Mode）、スクリプトブロックの記録を適用する
  3. Telegram 側の設定 —— 二段階認証（追加のパスワード）を有効にし、接続中の端末の一覧を定期に確認する（口座を取られた場合の検知と復旧のため）

一方、Kaspersky の勧告「修正が出るまでウィジェットを起動しない」には限界がある（本記録の評価）。同社自身が示した経路は「チャネルを訪れると」であり、利用者が明示的に起動していない可能性がある〈齟齬1〉。その場合、この勧告では防げない。

また「起動しない」という対策は利用者の判断に依存し、組織として強制する手段が無い。

    **Telegram は Android 版の問題を2026年11月10日に修正し、 翌11日に全利用者へ展開したとしている**（出典4・5）〈重要〉—— **一方 V12 は、修正後の Windows 版でも 別の RCE が成立すると主張している**（出典4・5）—— **影響を受ける版・修正された版は公表されていない**〈未確定1〉—— **したがって更新は必要だが、十分とは言えない**（本記録の評価）。
    取るべき行動 **業務で使う端末の Telegram クライアントの版を 一覧できる状態にする（管理コンソール・資産管理）。** **最新版への更新を促す経路を持つ。** **同時に、「更新したから安全」とは記録せず、 未解決の主張（Windows 版での別の RCE）が あることを台帳に残す。**
  • 口座の乗っ取りを前提に、接続中のセッションを定期に確認する。
    **WebRAT は Telegram の口座のデータを盗む**（出典4）〈重要〉—— **端末の駆除だけでは、 すでに持ち去られた口座への接続は切れない**（本記録の評価）—— **Telegram では接続中の端末の一覧を利用者自身が確認でき、 不要なセッションを切断できる**（本記録の整理）。
    取るべき行動 **業務連絡に使う口座について、 接続中の端末・セッションの一覧の確認手順を配る。** **二段階認証（追加のパスワード）の有効化を確認する。** **端末の感染が疑われた場合の手順に 「全セッションの切断とパスワードの変更」を含める。**
  • 「推定」と「確認」を分けて記録する。本件は関係が確認されていない。
    **Kaspersky は WebRAT の配布とウィジェットの脆弱性の関係を 「推定」としている**（出典3・4・6）〈重要〉—— **Xakep も「関係はいまのところ推定にとどまる」と明記している**（出典4）—— **SecurityWeek も「Kaspersky が観測した活動と V12 の実証が 同じ欠陥に関わるかをこの記事は確認していない」と記している** （出典5。原文英語）—— **一方、報道の見出しは因果を含む形になりやすい**（本記録の評価）。
    取るべき行動 **自組織の脆弱性・脅威の台帳に、 「悪用が確認された」「悪用が推定される」「実証のみ」の 3段階を区別する欄を設ける。** **本件は「実証あり・悪用は推定・ベンダーは存在を否定」として 記録する。** **対応の優先度は、段階と自組織の利用状況の 掛け合わせで決める。**
