**OpenJDK の Base64 デコード処理に、認証なしで遠隔からコード実行に至りうる ヒープバッファオーバーフローの脆弱性（CVE-2026-114938・通称「Java4Shell」）が 2026年11月17日に公表された。** Oracle は同日、臨時の Critical Security Patch Update （655件・うち Java SE 11件）で修正を出し、CISA とカナダ・サイバーセンターは 即時のパッチ適用を強く求める注意喚起を出した。**ただし2026年11月18日時点で、 成立した悪用（in-the-wild exploitation）はいずれの機関も確認していない。** 成立には x86-64 かつ AVX-512 VBMI 対応 CPU という条件と、 アプリごとに作り込んだ配送経路の両方が必要である。

OpenJDK の Base64 デコード処理に、認証なしで遠隔から情報漏えいまたはコード実行に 至りうる脆弱性が見つかった。 CVE-2026-114938、発見者による通称は「Java4Shell」である （出典1・4）。2026年11月17日に公表され、Oracle は同日、四半期の定例とは別の 臨時 Critical Security Patch Update（CSPU）で修正を出した（出典2）。 CISA は「即時のパッチ適用が必要」とする注意喚起を出し（出典3）、 カナダ・サイバーセンターも同日に警報を出している（出典5）。 JPCERT/CC と IPA は翌18日に JVNVU#99608534 を公表した（出典7）。 本記録が最初に書いておくべきことは、悪用の状況である。 CISA の注意喚起に実際の悪用を確認したという記述は無く、KEV カタログへの追加も 述べられていない（出典3。本記録が全文を確認）。 カナダ・サイバーセンターは「現時点で活発な悪用は把握していない」と明記（出典5）、 Cisco Talos も「実環境での悪用は未確認」と述べている（出典4）。 GreyNoise のダッシュボードでは、2026年11月17日00:00 UTC 以降に 「Java4Shell の形に合う Base64」を送信した IP が2件、 新規に観測された攻撃基盤が7件あるが、「成立した悪用は未確認」で 侵入成功数は0である（出典8。本記録が内容を確認）。 観測されているのは探りの通信であり、成立した攻撃ではない（本記録の整理）。 そして成立の条件が狭い。 脆弱な処理が動くのは x86-64 かつ AVX-512 VBMI 対応の CPU に限られ、ARM 系は影響を受けない（出典1・4・5・6）。 さらに汎用の実証コードは存在せず、アプリごとに「細工した Base64 を 脆弱なデコーダまで届ける経路」を見つける必要がある（出典1・9）。 それでも軽視できない理由は、Calif が既定設定のまま認証前のコード実行を実証した アプリの顔ぶれにある——Keycloak、Atlassian Jira、Atlassian Confluence、 JFrog Artifactory、Jenkins、PingFederate（出典1・9）。

この脆弱性は「Java を使っていれば危険」という形ではない（本記録の整理）。成立には3つの条件が重なる必要がある。

① ハードウェア: x86-64 かつ AVX-512 VBMI 対応の CPU

脆弱なコードは、HotSpot JVM が Base64 デコードを高速化するために使うAVX-512 版の組み込み関数の中にある（出典4・6）。VulnCheck は Ice Lake 世代で再現し、「AVX-512 VBMI（および BW）命令を提供する CPU でのみ脆弱なコードが動く。これらを持たない CPU は欠陥を含まない別のデコード経路に落ちるため、脆弱な命令が実行されない」と確認している（出典6。原文英語）。

該当する CPU 世代は次のとおりである（出典6）。

  • 該当: Intel Ice Lake／Sapphire Rapids 世代の Xeon、AMD Zen 4／Zen 5 世代（EPYC Genoa／Turin、Ryzen 7000／9000）、Intel の2019〜2021年のクライアント向け（Ice Lake／Tiger Lake／Rocket Lake）
  • 非該当: より古い Intel サーバ向けチップ、Intel の第12世代「Alder Lake」以降のクライアント向け（AVX-512 が無効化されている。現行の Core Ultra／Arrow Lake を含む）、ARM 系（Amazon Graviton・Ampere 等）

確認方法は示されている。 カナダ・サイバーセンターは Linux でlscpu | grep avx512 を使うよう案内している（出典5）。

ただし「サーバ側はほぼ該当する」という見方もある。研究者の指摘として、「このCPU要件に当てはまるのは……(メモを確認)…… Azure のすべての CPU だ。AWS/GCP のかなりの部分もそうだ」という投稿がある（出典11。原文英語）〈未確定5〉——これは個人の見立てであり、本記録は裏付けを取れていない。 ただし、クラウド上の現行世代のインスタンスが広く該当する方向であることは、VulnCheck が挙げた世代の一覧とも整合する（本記録の評価）。

② ソフトウェア: OpenJDK 17.0.6 以降

Calif は「OpenJDK 17.0.6 以降に影響する」としている（出典1・9）。影響は OpenJDK 本体にとどまらない—— Amazon Corretto、Eclipse Temurin、Microsoft Build of OpenJDK、Azul Zulu、BellSoft Liberica、SAP SapMachine、Red Hat OpenJDK、Oracle Java SE、Oracle GraalVM for JDK が挙げられている（出典6・9）。

Java 8 系も一部が対象である。 Oracle の一覧にはOracle Java SE 8u511b33-perf が含まれる（出典2・5・7）。末尾の「-perf」が付いた性能重視の構成だけが挙がっており、通常の 8u511b33 は本脆弱性の対象一覧に入っていない（本記録の確認）—— 「Java 17 以降だけを調べる」と取り落とす（本記録の評価）。

③ 到達性: 細工した Base64 を脆弱なデコーダまで届ける経路

Calif は「Java4Shell には汎用の実証コードが存在せず、攻撃者はアプリに依存した方法で悪性の Base64 データを脆弱なデコーダに届ける必要がある」と述べている（出典9。原文英語）。これが GreyNoise の「大量悪用は難しい」という見立ての根拠でもある（出典10）。

3つの条件のうち、組織が短期間に動かせるのは③だけである（本記録の評価）。①は調達の問題、②はパッチの問題であり、③は「外部から Base64 を受け取る経路に認証と入力制限を入れる」という当日に手を付けられる対策になる（出典3の代替策と整合）。

既定設定のまま認証前のコード実行が実証されたのは、企業の内側で使われる定番ばかりである被害規模・影響範囲出典 [1] [4] [6] [9]

悪用が未確認でありながら各国の当局が急いだ理由は、実証された対象の顔ぶれにある（本記録の評価）。Calif は既定設定のまま以下を実証している（出典1・9）。

認証前のコード実行（unauthenticated RCE）

  • Keycloak（認証基盤）
  • Atlassian Jira／Atlassian Confluence（課題管理・社内ドキュメント）
  • JFrog Artifactory（成果物リポジトリ）
  • Jenkins（CI/CD）
  • PingFederate（認証基盤）

認証後のコード実行（authenticated RCE）

  • Apache Kafka Broker／Apache Solr／Elasticsearch／Gerrit／Spinnaker

加えて Apache Struts と Spring Boot で構築した見本アプリでも実証された（出典1・9）。

この一覧の性質を見ておく（本記録の評価）。認証基盤（Keycloak・PingFederate）、CI/CD と成果物の保管（Jenkins・Artifactory）、社内の知識（Confluence・Jira）——いずれも、そこを取られると他の多くのものが連鎖的に取られる位置にある。認証基盤なら発行されるトークン全体、CI/CD なら本番への配布経路、成果物リポジトリなら配られるバイナリである。

「既定設定で」という条件も重要である（本記録の評価）。特殊な構成や珍しい拡張を入れている必要がない。

一方で、この一覧は網羅ではない〈未確定6〉。Cisco Talos は「すでに一連の Java アプリで試験され成功しているが、対象がさらに試験・確認されるにつれ攻撃面はもっと広い可能性が高い」と述べている（出典4。原文英語）。つまり「自社が使っているものが一覧に無いから安全」とは読めない（本記録の評価）。

なお Calif は、製品ごとに武器化した実証コードを公開していない（「全員が更新する時間を確保するため」。出典1・9）。公開されている実証コードはメモリ破壊を引き起こすところまでである（出典6）。ただし VulnCheck は2026年11月17日18時（米国東部時間）から、コード実行まで至る実証コードを自社顧客へ提供している（出典6）—— 非公開であることと、存在しないことは別である（本記録の評価）。

CVSS が 9.2 と 8.1 に割れており、社内の優先度規則をどちらで動かすかが分かれる評価・解釈出典 [1] [2] [6]

同じ脆弱性に2つの評点が付いている（本記録の整理）〈齟齬3〉。

評価主体 版 基本値 区分
Calif.io CVSS 4.0 9.2 Critical
Oracle CVSS 3.1 8.1 High

Oracle のリスクマトリクスの内訳はこうである（出典2。本記録が確認）—— Attack Vector: Network／Attack Complexity: High／Privileges Required: None／User Interaction: None／Scope: Unchanged／機密性・完全性・可用性: いずれも High。「認証なしの遠隔からの悪用が可能（Remote Exploit without Auth: Yes）」とも分類されている。

差を生んでいるのは Attack Complexity を High と見た点である（本記録の評価）。これは実測とも整合する。VulnCheck は、サービス妨害（JVM のクラッシュ）は「容易で、特別な悪用機構・実証コードの開発・ヒープの整地を要しない」が、コード実行には「ヒープの整地と、アドレスを漏えいさせて ASLR を回避する対象固有の経路」が必要だと評価している（出典6。原文英語）。

実務上の意味はこうである（本記録の評価）。社内の脆弱性対応規則が「CVSS 9.0 以上は48時間以内」のように数値で書かれている場合、どちらの数値を採るかで初動の期限が変わる。 CVSS 4.0 の 9.2 を採れば最上位の扱い、Oracle の 8.1 を採れば一段下の扱いになる。

本記録の立場を書いておく。 数値のどちらが正しいかを決める材料は無い。代わりに、本件の優先度は次の3つで判断するのが実態に合う（本記録の評価）。

  1. 対象のアプリが「認証前のコード実行を実証された顔ぶれ」に入っているか（出典1・9）
  2. そのアプリがインターネットから到達できるか（出典3・5がいずれも優先条件に挙げている）
  3. 動いている CPU が AVX-512 VBMI に対応しているか（出典5・6）

3つすべてが当てはまるものから手を付ける。 これは CVSS の数値より自組織の構成に即しており、CISA とカナダ・サイバーセンターの指示（インターネット公開系を優先）とも一致する（本記録の整理）。

VulnCheck はさらに踏み込んだ見方を示している（出典6）—— 「PHP2Shell と同様、容易に広く悪用されるとは見ていないが、攻撃者が特定のアプリで狭いが機能する経路を見つける可能性は高い」。 また「研究者が OpenJDK に AI を向けて、脆弱性を引き起こすがASLR を破れない公開実証コードを大量に出すだろう」とも予測している。後者が起きると、探りの通信は増えるが成立した悪用は増えないという状態が続く（本記録の評価）——GreyNoise の観測を読むときに、この区別が要る。

最大の難所はパッチではなく棚卸しである——JDK はソフトウェア一覧に別項目として現れない対策・注意喚起出典 [1] [2] [3] [4] [5] [6] [7] [9]

CISA の注意喚起で、本記録が最も実務的だと考えるのは次の注記である（出典3。原文英語）。

「影響を受ける Java 環境を特定する。ソフトウェア棚卸しで JDK や Java 実行環境を確認する。サードパーティ製アプリ、コンテナイメージ、アプライアンスに同梱されたものも対象。注: JDK や Java 実行環境は、棚卸しで別項目として現れない場合がある。」

これが本件の難所である（本記録の評価）。パッチ自体は Oracle が公表当日に出している（出典2）。問題は、どこに Java があるかが分からないことである。

Java が「見えない」場所は複数ある（本記録の整理）。

  • アプライアンス・装置の内部（監視機器、ストレージ管理画面、ネットワーク機器の Web UI）
  • コンテナイメージの基底層（アプリのベースイメージに同梱された JRE）
  • 商用ソフトウェアの同梱 Java（インストーラが自前の JRE を置くもの）
  • ビルド環境（CI の実行ノード、ビルドコンテナ）

カナダ・サイバーセンターはより具体的に指示している（出典5）—— 「すべてのアプリケーションを監査して、提供元と完全なビルド版を含めて稼働中の Java 実行環境を特定する」「Java コンポーネントを含むサードパーティ製品・アプライアンス・コンテナを特定する」「Java を同梱するアプライアンス・アプリ・サービスについて、提供元のセキュリティ更新を継続的に監視し、遅滞なく適用する」（原文英語）。

「完全なビルド版」まで要るのが本件の厄介な点である（本記録の評価）。影響する版は 17.0.21.0.3、21.0.13.0.3 のように4桁の構成で示されており（出典2・7）、「Java 17」という粒度では該当するかどうか判定できない。さらに Java 8 系では -perf 付きの構成だけが対象である（出典2・5・7）。

緩和策の副作用も見ておく（本記録の整理）。

  • -XX:-UseBASE64Intrinsics: ハードウェア加速が外れるため、Base64 を多用する処理（認証トークンの検証、ファイルアップロード）の性能が落ちる。低下幅は公表されていない（本記録の確認）。
  • -XX:UseAVX=2: x86-64 でのみ有効で、ARM 系の OpenJDK ではフラグを認識せず起動に失敗する可能性が高い（出典4・9）〈重要〉—— 混在環境で一律に配ると ARM 側が起動しなくなる。 AVX-512 を使う他の処理の性能も同時に落ちる。
  • アプリ境界での Base64 入力の制限（出典3）: 正常な大きい入力（添付ファイル、画像のデータ URI、証明書）が同時に拒否されうる。

どの緩和策も恒久対策ではない（出典1・9がいずれも明記）。Calif も VulnCheck も、最終的には実行環境の更新を求めている。

発見から動く実証まで3時間・費用200ドル未満だったことが、この種の脆弱性の供給量を変える評価・解釈出典 [1] [6] [9]

本件には、脆弱性そのものとは別の論点がある（本記録の整理）。Calif は発見の経緯を公表している（出典1・9）。

  • 研究者 Quang Luong が、OpenAI の Codex（コーディング支援）を使ってOpenJDK の内部を監査する中で発見した
  • 発見に約1時間、最初の動く実証コードの開発にさらに約2時間
  • 「The total token cost was less than $200.」（トークン費用の合計は200ドル未満だった。原文英語）
  • 後半の実証コードの連鎖は、ほぼ AI が自律的に構築した
  • 実証の改良を Jenish Rakholiya が行った

この数値が意味するのは、難易度ではなく供給量である（本記録の評価）。OpenJDK の HotSpot の組み込み関数は、従来であれば読める人が限られる領域である。3時間と200ドルで、既に広く使われている実行環境の中核に認証前のコード実行に至る不備が1件見つかったということは、同じ手法が他の成熟したコードベースにも向けられることを意味する。

VulnCheck も同じ方向を予測している（出典6。原文英語）—— 「必然的に、大勢の研究者が OpenJDK に AI を向けて、脆弱性を引き起こすが ASLR を破れない公開実証コードを大量に出すだろう」。

ここで本記録の評価を2つ書く。

第一に、防御側の時間の取り方が変わる。本件は embargo（事前の非公開調整）が効いた例である—— Oracle のパッチ、CISA とカナダ・サイバーセンターの注意喚起、Cisco Talos の検知ルール（Snort SID 1:67502〜1:67513）が、いずれも公表当日に揃っている（出典2・3・4・5）。Calif が製品ごとに武器化した実証コードを「全員が更新する時間を確保するため」非公開としたことも、この設計の一部である（出典1・9）。AI によって発見の側が速くなるなら、この調整の枠組みがどれだけ維持できるかが問われる（本記録の評価）。

第二に、VulnCheck が指摘する「市場との距離」も無視できない（出典6）。同社は本件の公表を「事前に予告される、話題性が高く悪用性の低い脆弱性の公開は、リスクに基づく誠実な分析よりマーケティングの演習に見えることが多い」と批判的に評している（原文英語）。一方で同社自身は、公表当日の18時からコード実行まで至る実証コードを自社の有料顧客に提供している（出典6）。本記録は、どちらの立場も評価しない。 ただし読者が知っておくべきこととして、「公開されている実証コードはメモリ破壊までだが、コード実行まで至るものは商業的に流通している」という状態を記録しておく（本記録の整理）。

先に打てる手が1つある（本記録の評価）。AVX-512 を無効にして JVM を起動すれば、棚卸しが終わる前でも脆弱な経路そのものが動かなくなる（出典14 が伝える Cisco の助言）。棚卸しとパッチ適用の間を埋める措置として、外部公開中の Java アプリケーションから順に検討する価値がある ——ただし性能への影響は自組織で測る必要がある（本記録の留保）。

名称: OpenJDK（HotSpot JVM の Base64 デコード組み込み関数）　ベンダー: OpenJDK コミュニティ／Oracle　CVE番号: CVE-2026-114938　バージョン: **Calif: 「Java4Shell affects OpenJDK from version 17.0.6 or newer.」 （Java4Shell は OpenJDK 17.0.6 以降に影響する。原文英語）**（出典1・9）。 **VulnCheck: 公式アドバイザリによれば OpenJDK 17・21・25・27 が影響する**（出典6）。 **JVN が示す影響を受ける OpenJDK の版は、27.0.1.0.3 およびそれ以前、 25.0.5.0.3 およびそれ以前、21.0.13.0.3 およびそれ以前、 17.0.21.0.3 およびそれ以前**（出典7）。　概要: **ヒープベースのバッファオーバーフロー（CWE-122）**（出典7）。 **Base64 デコード処理を高速化するための最適化処理（HotSpot の AVX-512 版 組み込み関数 generate_base64_decodeBlock。java.util.Base64.Decoder 経由で到達）に 整数のアンダーフローがあり、ヒープ領域の範囲外書き込みに至る**（出典6）。　症状: **「Base64デコード処理に細工したデータを入力されると、機微な情報が窃取されたり 任意のコードが実行されたりする可能性があります」**（出典7。原文日本語を引用）。 **実測では、JVM をクラッシュさせるサービス妨害は容易である**（出典6）—— **既定設定のサーバは1回の要求では落ちないが（JVM のスレッドローカル割り当てバッファが オーバーフローを吸収するため）、要求を連続して送ると確実にサービスが停止した**（出典6）。　手法: **パディング処理がデコード後サイズのカウンタを下限なく減算するため、 細工した入力でカウンタが負に回り込み、書き込み先ポインタと格納マスクが壊れる**（出典6）。 **その結果、デコード先バッファを約62バイト越えて書き込まれる**（出典6）。 **トリガとなる入力の記述は資料間で一致していない**〈未確定4〉。　内容: **攻撃者が得られるのは、メモリ内容の漏えいまたは任意のコード実行である**（出典1・7）。 **ただしコード実行の難易度は高い**——**ヒープの整地と、 対象固有のメモリ内容漏えい経路による ASLR 回避の両方が必要**（出典6）。　preconditions: **条件は3つ重なる必要がある**（本記録の整理）。 ①**ハードウェア**: x86-64 かつ AVX-512 VBMI（および BW）対応の CPU。 **対応しない CPU では別のデコード経路に落ちるため、脆弱な命令が実行されない**（出典6）。 **ARM 系（Amazon Graviton・Ampere 等）は影響を受けない**（出典1・5・6）。 ②**ソフトウェア**: OpenJDK 17.0.6 以降（または派生ディストリビューション）。 ③**到達性**: 攻撃者が細工した Base64 を、脆弱なデコーダまで届けられる経路。 **汎用の実証コードは存在せず、アプリごとに配送方法を見つける必要がある**（出典1・9）。

緩和策
手順: **Oracle および各ディストリビューション提供元のパッチを適用する**（出典2・3・5・7）。 **インターネットに公開されたシステムを優先する**（出典3・5）。　副作用: **Oracle の臨時 CSPU は655件の修正を含むため、 Oracle 製品を広く使う組織では適用の検証範囲が大きくなる**（出典2。本記録の評価）。 **Java の更新は、その Java の上で動くすべてのアプリの再起動を伴う**—— **共通の実行環境を複数のアプリが共有している構成では、 停止の調整が最大の作業になる**（本記録の評価）。
手順: **即時のパッチが難しい場合、JVM を `-XX:-UseBASE64Intrinsics` で起動して ハードウェア加速の Base64 処理を無効化する**（出典1・9）。 **VulnCheck の検証では `-XX:+UnlockDiagnosticVMOptions -XX:-UseBASE64Intrinsics` の 組み合わせで、OpenJDK 17・21・25 のいずれでもオーバーフローが止まった**（出典6）。　副作用: **Base64 のデコードがハードウェア加速なしの経路に落ちるため、 Base64 を多用する処理（認証トークンの検証、ファイルアップロード、 メッセージング）の性能が落ちる**（本記録の評価）。 **低下幅は公表されていない**（本記録の確認）—— **本番適用の前に、自組織の負荷で測る必要がある。**
手順: **`-XX:UseAVX=2` で AVX-512 命令を無効化する**（出典1・4・5・6・9）。 **カナダ・サイバーセンターと Cisco Talos がいずれも挙げている緩和策である。**　副作用: **x86-64 システムでのみ有効であり、ARM 系の OpenJDK では このフラグを認識せず起動に失敗する可能性が高い**（出典4・9）〈重要〉—— **混在環境で一律に配ると、ARM 側のアプリが起動しなくなる**（本記録の評価）。 **また AVX-512 を使う他の処理（数値計算・暗号・圧縮）の性能も同時に落ちる** （本記録の評価）。
手順: **アプリケーション境界で Base64 入力を制限・検証し、入力サイズの上限を設け、 未認証アクセスを制限する**（出典3。CISA が示した代替策）。　副作用: **正常な大きい入力（添付ファイル・画像のデータ URI・証明書）が 同時に拒否されうる**（本記録の評価）。 **上限値を業務の実態より狭く取ると、機能の障害として現れる**—— 障害の原因が緩和策であることを運用側が把握していないと切り分けが長引く（本記録の評価）。
手順: **パッチ適用が困難な場合、インターネットに公開されたアプリを 公衆網から隔離する**（出典5。カナダ・サイバーセンターが示した措置）。　副作用: **外部向けサービスの提供を止めることになる**（本記録の評価）—— **本件は成立した悪用が未確認の段階であるため、 この措置を取るかどうかは「対象アプリが認証前のコード実行を実証された 顔ぶれに入っているか」で判断するのが現実的である**（本記録の評価）。
手順: **不審な活動を監視する**（出典3）。 **具体的には、見慣れない Java 実行環境、予期しない JVM のクラッシュ、 不審な Java プロセスを見る**（出典3）。 **検知ルールとして Snort2 1:67502〜1:67513／Snort3 1:301754 が提供されている**（出典4）。　副作用: **Snort のルールは「特定の HTTP 要求フィールドに含まれる不正な Base64 データ」を 見るものであり、Talos 自身が「本脆弱性は実装固有である」と注意している**（出典4）—— **ルールが見ていないフィールドや経路での配送は検知できない**（本記録の評価）。 **「予期しない JVM のクラッシュ」の監視は有効だが、 サービス妨害は容易である一方コード実行は難しいという実測（出典6）を踏まえると、 クラッシュの大半は探りや失敗した試行である可能性がある**（本記録の評価）。

CISO・経営層への示唆
  • 「緊急注意喚起が出た」は「悪用が始まった」ではない。両者を分けて社内に伝えないと、 次に本当に悪用が始まったときに同じ強さでしか伝えられなくなる。
    **CISA は「即時のパッチ適用が必要」としながら、実際の悪用を確認したという記述を 置いていない**（出典3。本記録が全文を確認）〈重要〉。 **カナダ・サイバーセンター「現時点で活発な悪用は把握していない」**（出典5）、 **Cisco Talos「実環境での悪用はまだ観測していない」**（出典4）、 **GreyNoise「成立した悪用は未確認」・侵入成功数0**（出典8）。 **観測されているのは「形に合う Base64 を送った IP が2件」という探りの通信である** （出典8）。
    取るべき行動 **社内の脆弱性連絡の雛形に「悪用の状況」を独立した欄として設け、 ①未確認 ②探りの通信を観測 ③成立した悪用を観測 ④自組織で観測 の4段階で書く。** **段階が変わったときだけ再通知する運用にする**（本記録の推奨）—— **毎回「緊急」で出すと、④のときに動かせる余力が残らない。**
  • 対応の優先度を CVSS の数値だけで決めていると、本件のように評点が割れた脆弱性で 初動の期限が変わってしまう。構成の条件で順位を付ける規則を併記する。
    **同じ脆弱性に Calif の CVSS 4.0 で 9.2（Critical）と、 Oracle の CVSS 3.1 で 8.1（High）という2つの評点がある**（出典1・2）〈重要〉。 **差を生んでいるのは Attack Complexity を High と見た点であり、 これは「コード実行にはヒープの整地と対象固有のメモリ漏えい経路が必要」という 実測と整合する**（出典6）。 **「CVSS 9.0 以上は48時間以内」のような数値だけの規則では、 どちらを採るかで期限が変わる**（本記録の評価）。
    取るべき行動 **脆弱性対応規則に、数値とは別の優先条件を書く。** 本件に当てはめるなら **①認証前のコード実行が実証された製品を使っているか ②それがインターネットから到達できるか ③動いている CPU が条件に当てはまるか**の3つで、 すべて該当するものを最優先にする（出典1・3・5・6を踏まえた本記録の推奨）。 **数値は「下限」として使い、順位付けには構成を使う。**
  • 実行環境（ランタイム）の棚卸しは、アプリの棚卸しとは別の作業である。 本件では「どこに Java があるか」が最大の難所になる。
    **CISA は「JDK や Java 実行環境は、ソフトウェア棚卸しで別項目として 現れない場合がある」と明記している**（出典3。原文英語）〈重要〉。 **カナダ・サイバーセンターは「提供元と完全なビルド版を含めて」特定するよう求め、 さらに「Java コンポーネントを含むサードパーティ製品・アプライアンス・ コンテナ」も対象に挙げている**（出典5）。 **影響する版は 17.0.21.0.3 のように4桁で示されているため、 「Java 17」という粒度では判定できない**（出典2・7。本記録の評価）。
    取るべき行動 **ソフトウェア資産の台帳に「同梱されている実行環境」の欄を設け、 アプライアンス・商用ソフト・コンテナイメージ・CI 実行ノードについて 提供元とビルド版まで記録する。** **今回の対応の中で作った一覧を、次回のために台帳として残す**（本記録の推奨）—— **同じ作業は Java 以外（OpenSSL・glibc・Log4j 系）でも必ず再発する。**
  • AI 支援による脆弱性の発見が、3時間・200ドル未満で成熟したコードベースの中核に 届いた。防御側の前提を「年に数回の大物」から「供給量が増える」へ更新する。
    **Calif は、研究者が OpenAI の Codex を使って約1時間で発見し、 さらに約2時間で最初の動く実証コードを作り、トークン費用は200ドル未満だったと 公表している**（出典1・9）〈重要〉。 **後半の実証コードの連鎖はほぼ AI が自律的に構築したとされている**（出典1）。 **VulnCheck も「大勢の研究者が OpenJDK に AI を向けて、 脆弱性を引き起こすが ASLR を破れない公開実証コードを大量に出すだろう」と 予測している**（出典6。原文英語）。
    取るべき行動 **脆弱性対応の体制を「件数が増える」前提で見直す。** 具体的には**①棚卸しの自動化（台帳を人が維持する方式から、 実機を走査して作る方式へ）②緩和策の事前検証（本件の `-XX:UseAVX=2` のように、 配ったら動かなくなる環境がないかを平時に確かめる） ③適用の自動化の範囲を広げる**の3点を計画に入れる（本記録の推奨）。 **人手で1件ずつ追う方式は、供給量が増えた時点で先に破れる**（本記録の評価）。
セキュリティ技術者への示唆
  • 対象の絞り込みは CPU から始めるのが速い。AVX-512 VBMI 非対応の CPU と ARM 系は、この脆弱性の影響を受けない。
    **VulnCheck は「脆弱なコードは AVX-512 VBMI（および BW）命令を提供する CPU でのみ動く。 これらを持たない CPU は欠陥を含まない別のデコード経路に落ちるため、 脆弱な命令が実行されない」と再現により確認している**（出典6。原文英語）〈重要〉。 **ARM 系（Amazon Graviton・Ampere 等）は影響を受けない**（出典1・5・6）。 **該当・非該当の CPU 世代も具体的に示されている**（出典6）。
    取るべき行動 **Linux では `lscpu | grep avx512` で確認する**（出典5が示した手順）。 **クラウドではインスタンスの機種系列から当たりを付け、 実機で同じコマンドを流して確かめる。** **「非該当」と判定できた範囲を先に除外し、残りにパッチ適用の工数を寄せる** （本記録の推奨）——**全台を同じ優先度で追うと、 台数の多い環境では期限内に終わらない。**
  • Java 8 系も一部が対象である。Oracle の一覧には `-perf` 付きの構成だけが 挙がっており、「17 以降だけを見る」と取り落とす。
    **Oracle の対象一覧に Oracle Java SE 8u511b33-perf が含まれている** （出典2・5・7）〈重要〉——**通常の 8u511b33 は本脆弱性の対象一覧に入っていない** （本記録の確認）。 **一方 Calif は「OpenJDK 17.0.6 以降」としており、 資料だけを見ると Java 8 は無関係に見える**（出典1）。 **末尾の構成名まで照合しないと判定を誤る**（本記録の評価）。
    取るべき行動 **稼働中の Java のビルド版を、末尾の構成名（`-perf` 等）まで含めて取得する。** **`java -version` の出力をそのまま台帳に記録し、 出典2・出典7の対象一覧と文字列で照合する**（本記録の推奨）。 **メジャー版だけで判定する手順書があれば、今回の対応で直す。**
  • 緩和策の `-XX:UseAVX=2` は ARM 系で起動に失敗しうる。混在環境で一律に配らない。
    **Cisco Talos は「これは x86-64 システムでのみ該当する。 ARM 系のプロセッサはこのコマンドを認識せず、おそらく起動に失敗する」と 注意している**（出典4。原文英語）〈重要〉。 **Calif も、x86-64 システムで Java を動かしている管理者向けの選択肢として 提示している**（出典1・9）。 **本件の緩和策は、適用対象を間違えると障害になる種類のものである**（本記録の評価）。
    取るべき行動 **緩和策を配る前に、対象ホストのアーキテクチャで条件分岐させる。** **性能面の副作用も見積もる**—— `-XX:-UseBASE64Intrinsics` は Base64 処理の高速化が外れるため、 認証トークンの検証やファイルアップロードが多い系で影響が出る （低下幅は公表されていない。本記録の確認）。 **検証環境で自組織の負荷をかけて測ってから本番へ入れる**（本記録の推奨）。
  • 予期しない JVM のクラッシュを監視対象に入れる。サービス妨害は容易で、 コード実行は難しいという実測から、クラッシュが最初に見える兆候になる。
    **VulnCheck の実測では、JVM をクラッシュさせるサービス妨害は 「容易で、特別な悪用機構・実証コードの開発・ヒープの整地を要しない」** （出典6。原文英語）〈重要〉—— **「既定設定のサーバは1回の要求では落ちない（JVM のスレッドローカル 割り当てバッファがオーバーフローを吸収するため）が、 要求を連続して送ると確実にサービスが停止した」。** **一方コード実行にはヒープの整地と対象固有のメモリ漏えい経路が必要である**（出典6）。 **CISA も監視対象に「予期しない JVM のクラッシュ」を挙げている**（出典3）。
    取るべき行動 **JVM の異常終了（OOM ではないクラッシュ、hs_err_pid ファイルの生成）を 監視の対象にし、発生時に警報を出す。** **あわせて Snort のルール（Snort2: 1:67502〜1:67513／Snort3: 1:301754）を 導入する**（出典4。コミュニティルールセットでも利用できる）。 **ただしルールは特定の HTTP 要求フィールドの不正な Base64 を見るものであり、 Talos 自身が「本脆弱性は実装固有」と注意している**（出典4）—— **ルールだけに依存せず、クラッシュの監視と併用する**（本記録の推奨）。
  • 外部から Base64 を受け取る経路を洗い出す。この脆弱性で組織が当日に動かせるのは 「到達性」の条件だけである。
    **Calif は「Java4Shell には汎用の実証コードが存在せず、 攻撃者はアプリに依存した方法で悪性の Base64 データを 脆弱なデコーダに届ける必要がある」と述べている**（出典9。原文英語）〈重要〉。 **CISA の代替策も「アプリケーション境界で Base64 入力を制限・検証し、 入力サイズの上限を設け、未認証アクセスを制限する」である**（出典3）。 **成立の3条件のうち、ハードウェアは調達、ソフトウェアはパッチの問題であり、 到達性だけが当日に手を付けられる**（本記録の評価）。
    取るべき行動 **自社のアプリで Base64 を受け取る入口を列挙する**—— 認証ヘッダ（Basic 認証・JWT・SAML アサーション）、 ファイルアップロードのデータ URI、Cookie、API のバイナリ項目。 **各々について①未認証で到達できるか②入力長の上限があるかを確認し、 未認証かつ上限なしの経路から塞ぐ**（本記録の推奨）。 **上限値は業務の実態から決める**—— 狭く取ると正常な添付や証明書が拒否され、機能障害として現れる（本記録の評価）。
