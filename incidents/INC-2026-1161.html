INC-2026-1161MS agent-framework 2版が汚染

**Microsoft の AI エージェント開発基盤「Microsoft Agent Framework」の PyPI 版 `agent-framework` が2026年11月17日に改ざんされ、2つの版（1.26.1・1.26.2）に 資格情報を窃取するコードが仕込まれた。** 悪性コードは Python の起動フック（`.pth`）として 仕掛けられており、**パッケージを import しなくても、インタプリタが起動するたびに実行される。** 環境変数・他プロセスの環境・資格情報ファイルを収集するだけでなく、 **Azure のマネージドID と GitHub Actions の OIDC トークンを能動的に発行要求し**、 webhook.site の受け口へ送信していた。 **PyPI 上の露出は約55分で、両版は同日に隔離された。**

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている日本に波及した海外事案公表されていない／不明設計・実装上の不備
初報: 2026年11月17日（Socket.dev および Wiz による公表） 最終更新: 2026年11月18日（本記録の作成時点）

Microsoft の AI エージェント開発基盤の PyPI パッケージ agent-framework に、 資格情報を窃取するコードが仕込まれた2つの版が公開された。 1.26.1 と 1.26.2 である（出典1）。 本記録が最も重く見るのは、仕掛けられた場所である。 悪性コードは Python の起動フック（.pth ファイル）として置かれていた—— site 処理によってインタプリタの起動時に実行されるため、 パッケージを import しなくても動く（出典1）。 依存関係に入れただけ、ビルドしただけ、イメージに焼いただけでも実行される。 収集される対象も、既にある秘密を写し取るだけではない。 攻撃者のコードは Azure のマネージドIDエンドポイントと GitHub Actions の OIDC に対して 新しいトークンの発行を能動的に要求していた（出典1）〈重要〉—— 「漏れた資格情報を無効化する」では済まず、信頼関係（フェデレーション資格情報）の 見直しまで必要になる（本記録の評価）。 露出時間は短い。 Wiz の記録では 1.26.1 が2026年11月17日20:35 UTC、 1.26.2 が約21:08 UTC に公開され、21:30 UTC には両版が PyPI から利用できなくなっていた ——約55分間（出典2）。 本記録の作成者が2026年11月18日に PyPI のプロジェクトページを確認したところ、 1.26.1 と 1.26.2 はいずれも「Release quarantined」（2026年11月17日に隔離）と表示され、 最新の健全な版は 1.26.0（2026年11月12日公開）のままである（出典3）。 一方で、Microsoft 自身の公表は確認できなかった（本記録の確認）〈齟齬1〉—— 侵害経路も、実際に何件インストールされたかも、公表されていない。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

公開経路を掌握した第三者が、`agent-framework` の2つの版（1.26.1・1.26.2）に 資格情報窃取のコードを仕込んで PyPI へ公開した。 **悪性コードは Python の起動フック（`.pth`）として置かれ、 `site` 処理によってインタプリタの起動時に実行される——パッケージを import しなくても動く。** 環境変数・他プロセスの環境・資格情報ファイルを収集するだけでなく、 **Azure のマネージドIDと GitHub Actions の OIDC に対して新しいトークンの発行を 能動的に要求し**、zlib で圧縮して Base64 符号化したうえで webhook.site の受け口へ POST していた（出典1）。**露出は約55分**（出典2）。

    **第三者が `agent-framework` の PyPI 公開経路を掌握し、 2026年11月17日20:35 UTC に 1.26.1 を公開した**（出典2）。 **GitHub の main ブランチには悪性コードが含まれておらず、 対応するタグ・リリースも存在しない**（出典2）—— **汚染されたのは配布物だけである。** **掌握の手口は確認されていない。**

  2. 2. 実行disclosed[1]

  3. 3. 検知回避disclosed[1]
    **1.26.2 では、ペイロードをトップレベルのモジュールへ移設し、 正規のパッケージ初期化ファイル（`agent_framework_meta/__init__.py`）を バイト単位で復元した**（出典1）〈重要〉—— **「`agent_framework_meta/__init__.py` だけを検査する」方法では この版を見逃す**（出典1が明記）。 **送信先のURLは Base64 で符号化して埋め込まれていた** （`_ENC = "aHR0cHM6Ly93ZWJob29rLnNpdGUv..."`）。 **収集結果も zlib で圧縮し Base64 で符号化してから送信するが、 出典1は「符号化は HTTPS を超える秘匿性を与えない」と述べている**（原文英語）。

import しなくても動く——仕掛けられた場所がこの事案の本質である原因・手口出典 [1]

通常のパッケージ汚染であれば、「そのパッケージを import したときに動く」。本件は違う（出典1）。

「Python の起動時に、.pth ファイルが、背景のプロセスまたはスレッドで収集を開始するモジュールを import する」（原文英語）

.pth ファイルは、Python の site 処理によってインタプリタの起動時に読み込まれる仕組みである（出典1）。したがって、パッケージを import していなくても実行される。

これが実務上どう効くか（本記録の評価）。

  • 依存関係に入れただけで動く（直接使っていなくても、推移的な依存でも同じ）
  • pip install 後に Python を起動した時点で動く（ビルドの検証、テストの実行、別の無関係なスクリプトでも）
  • コンテナイメージに焼いた場合、そのイメージが起動するたびに動く
  • 「このライブラリは評価中で本番では使っていない」が免責にならない

経路は2つの版で違う（出典1）。

1.26.1: agent_framework_meta.pth → agent_framework_meta/__init__.py → agent_framework_meta/_telemetry.py。初期化ファイルには「軽量な実行時診断フック」というコメントが添えられ、例外を握りつぶす形で呼び出されていた。

1.26.2: af_runtime_diag.pth → トップレベルの af_runtime_diag.py。こちらは正規のパッケージ初期化ファイルをバイト単位で復元している（出典1）〈重要〉。出典1はこの意味を明示している—— 「agent_framework_meta/__init__.py だけを検査すると、この版を見逃す」（原文英語）。

つまり検知の設計が問われる（本記録の評価）。既知の悪性ファイルのハッシュを照合する方式では、復元された正規ファイルは一致してしまう。 見つけるには「正規版のファイル一覧に無いファイルが増えていないか」という差分の見方が要る——トップレベルに af_runtime_diag.py と af_runtime_diag.pth が現れている（出典1）。

実行の仕方にも配慮がある（出典1）。Unix では fork してセッションを切り離し、fork が無い環境ではデーモンスレッドを使う。起動ガードは環境変数 _AF_TEL で行われ、子プロセスに継承される——同じプロセスツリーでは二重に走らない。しかし「ディスク上に実行済みの印を持たないため、新しいプロセスツリーでは再び収集が起きうる」（出典1。原文英語）。パッケージが入ったままなら、Python を起動するたびに走る（本記録の整理）。

① 環境変数（部分一致での照合）

照合に使われた文字列は TOKEN・SECRET・KEY・AZURE・AWS・GITHUB・OPENAI・HF_・FOUNDRY・TENANT・CLIENT・MANAGED で、1.26.2 では ACTIONS・OIDC・RUNNER・ARM_ が追加された（出典1）。「固定の許可リストではなく部分一致である」点が重要である（出典1が明記）—— 自社固有の名前を付けた秘密も、これらの語を含めば対象になる（本記録の評価）。

② 他プロセスの環境変数

封じ込めの速さは評価できる（本記録の評価）。しかし3つの理由で、短さを安心の根拠にできない。

第一に、CI は秒単位で依存を取得する（本記録の評価）。55分は、人の作業時間としては短いが、自動化されたビルドが何回も走る時間である。版を固定していない（agent-framework のように上限を切らずに指定している）環境では、この窓に入ったビルドがそのまま悪性版を取る。

第二に、隔離は上流を閉じるだけである。 .pth は Python の起動ごとに実行されるため、この55分間に取得した環境では、隔離後も収集が続く（出典1・2）〈重要〉。出典2も「.pth は Python 起動のたびに実行されるため、インストールされた環境では公開停止後も影響が続く」と明記している。

第三に、誰が取得したかを配布側が把握していない。 PyPI の取得は匿名である（本記録の整理）。したがって「2026年11月17日20:35〜21:30 UTC に取得した組織」を特定して通知する手段が存在しない。 周知は、第三者ベンダーの公表と PyPI 上の隔離表示だけで行われた（出典1・2・3）。

攻撃者側の速さも記録しておく（本記録の評価）。約33分で版を差し替え、その差し替えでは①ペイロードをトップレベルのモジュールへ移設②正規の初期化ファイルをバイト単位で復元③GitHub Actions の OIDC を収集対象に追加 を行っている（出典1）。検知されることを織り込んで改良する動きである。

逸脱はもう一つある（出典2）。正規のリリースは wheel と sdist を同時に公開するが、1.26.1 は wheel のみだった。 さらに GitHub の microsoft/agent-framework に python-1.26.1 のタグもリリースも存在せず、main ブランチに悪性コードは含まれていない。ここから Wiz は、「プロジェクトの通常のリリース過程の外で作られ、PyPI へ直接アップロードされた可能性がある」と推測している（原文英語）。

つまり、この版は「正規の公開手順の指紋」を持っていなかった（本記録の整理）。出所証明が無い、sdist が無い、対応するタグが無い——3つとも揃っている。

一方で、版番号の増え方は自然だった（本記録の評価）〈重要〉。1.26.0 の公開は11月12日で、その前は 1.25.0（11月7日）、1.24.0（10月30日）、1.23.0（10月22日）と、週次に近い頻度で更新されてきた系列である（出典3の履歴）。5日後にパッチ版 1.26.1 が出ることは、更新の周期として何も不自然ではない。 版番号だけを見る運用では見分けられない。

読者が取れる対策は3段階ある（本記録の整理）。

  1. 取得の時点: provenance の存在を必須条件にする。版を固定し、ハッシュまで照合する（pip --require-hashes、ロックファイルの厳格運用）
  2. 実行の時点: site-packages 内の .pth の一覧を既知の状態と比較する。ビルド環境からの外向き通信を許可リスト方式にする
  3. 権限の設計: CI に与える権限を既定で最小にする（GitHub Actions の id-token: write を必要なジョブだけに限定し、フェデレーション資格情報の対象をリポジトリ・ブランチ・環境まで絞る）

3番目が最も効く（本記録の評価）。1と2は「悪性版を取らない・動かさない」ための対策だが、3は「取ってしまっても出せる秘密を減らす」対策である。 本件では新しいトークンが能動的に発行要求されているため、発行できる権限が最初から無ければ、収集されるものが減る。
