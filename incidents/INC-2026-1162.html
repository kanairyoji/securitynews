INC-2026-1162Puppet の RCE 脆弱性が KEV 収載

**Perforce の構成管理製品「Puppet Enterprise」のレポート処理に、 CA が署名したエージェント証明書を持つクライアントから Puppet Server 上で任意のコードを実行できる脆弱性（CVE-2026-115731・CVSS 4.0 で 9.4）があり、 CISA は2026年11月17日にこれを KEV カタログへ収載した。** **収載は「悪用が確認された」ことを意味するが、誰がどこをどう攻撃したかは公表されていない。** 修正は2026年11月3日に出ており、米連邦行政機関の対応期限は2026年12月1日である。

Perforce が提供する構成管理製品「Puppet Enterprise」に、 Puppet Server 上で任意のコードを実行できる脆弱性 CVE-2026-115731 がある。 Perforce 自身の題名は「Report Deserialization Code Execution」（出典1）。 CVE レコードは2026年11月3日20時40分（UTC）に公表され、 CVSS 4.0 の基本値は 9.4（Critical）である（出典1。本記録が直接確認）。 NVD は別途 CVSS 3.1 で 9.9（Critical）を付けている（出典2。本記録が直接確認）〈齟齬2〉。 本記録が最初に書いておくべきことは、悪用の位置づけである。 CISA は2026年11月17日、本脆弱性を KEV（悪用が確認された脆弱性カタログ）へ収載した （出典3。本記録がカタログの JSON を直接確認）。 KEV はその定義上「悪用が確認された」ものだけを載せる目録であり、 収載そのものが CISA による悪用確認の表明である（本記録の整理）。 ただし、誰が・どの組織を・いつ攻撃したかは公表されていない（本記録の確認）〈未確定1〉—— 攻撃者、被害組織、観測件数、侵害の痕跡（IoC）はいずれもカタログにも Perforce の資料にも示されていない。 また「ランサムウェアキャンペーンでの使用」は Unknown（不明）とされ、 フォレンジック・トリアージの要求対象（forensicTriage）は No である（出典3）。 対応期限は2026年12月1日（出典3）—— 収載から14日であり、米連邦行政機関に対する BOD 26-04 に基づく要求である。 日本の組織に対する強制力は無いが、Puppet Enterprise は サーバ群の設定を一斉に配る位置にあるため、侵害されたときの射程が広い（本記録の評価）〈重要〉。 修正版は Puppet Enterprise 2023.8.13／2025.12.1／2026.0.1、 同梱される puppet-agent は 8.22.2／9.1.3 である（出典1）。

KEV 収載は「悪用が確認された」ことを意味するが、その中身は何も公表されていない帰属

本件で最初に押さえるべきは、悪用の位置づけである。

CISA は2026年11月17日17時53分（UTC）、KEV カタログの版 2026.11.17 でCVE-2026-115731 を収載した（出典3。本記録がカタログの JSON を直接確認）。KEV は「悪用が確認された脆弱性」の目録であり、収載そのものがCISA による悪用確認の表明である（本記録の整理）。前日まで「悪用の確認なし」だった脆弱性が、この日に段階を1つ上げた。

ところが、その中身は何も公表されていない（本記録の確認）。カタログのエントリに含まれるのは次のフィールドだけである（出典3）。

フィールド 本件の値
dateAdded 2026-11-17
dueDate 2026-12-01
knownRansomwareCampaignUse Unknown（不明）
forensicTriage No
cwes CWE-502, CWE-94
notes Perforce アドバイザリ・BOD 26-04 の2文書・NVD の URL

攻撃者、被害組織、観測の時期、観測件数、侵害の痕跡（IoC）を記す欄はそもそも存在しない。 したがって本記録も「悪用が確認された」以上のことは言えない〈未確定1〉。

ここで2つ、読み間違えやすい点がある（本記録の評価）。

第一に、knownRansomwareCampaignUse: Unknown は「使われていない」ではない。「分かっていない」である。ランサムウェアでの使用が確認された脆弱性を優先する運用をしている組織は、この値で優先度を下げてしまう。

第二に、forensicTriage: No は「侵害の可能性が低い」ではない。これは BOD 26-04 の枠組みで、CISA が連邦機関に対して侵害調査（フォレンジック・トリアージ）の実施まで要求するかどうかの指定である（出典3。読みは本記録の整理）。要求されていないことは、自組織で痕跡を調べなくてよいという判断の根拠にはならない。

なお、この日に KEV へ追加されたのは本件1件のみである（出典3。本記録が全1,782件の dateAdded を走査して確認）〈重要〉。複数件をまとめた定期更新の一部ではなく、単独の追加だった。

悪用の前提は「インターネット公開」ではなく「エージェント1台の掌握」である原因・手口

技術的な条件を、一次資料の記述のまま置く（出典1・2・3）。

「Puppet のレポート処理コードにおける信頼できないデータのデシリアライズにより、CA が署名した任意のエージェント証明書を持つクライアントは、細工した rich-data 型を含むレポートを PUT 要求で送ることによって、Puppet Server 上でそのサービス実行ユーザとして任意のコードを実行できる。認証局が強い検証なしに署名要求を自動署名している場合は、認証を持たないネットワーク上の攻撃者が有効な証明書を取得して悪用できる。」（原文英語。本記録が訳した）

読むべき点は3つある（本記録の整理）。

① 経路が正規の API である。 Puppet のエージェントは適用結果をレポートとして Puppet Server へ PUT で送る。攻撃者は脆弱な入口を探す必要がなく、エージェントが毎回使っている経路に危険な型を混ぜるだけでよい。通信の見かけは正規のレポート送信と変わらない。

② 必要なのは「CA 署名済み証明書」である。 CVSS 4.0 のベクタが PR:L（低い権限が必要）になっているのはこの前提である（出典1）。正規のエージェント1台が侵害されれば、条件は満たされる（本記録の評価）。末端のサーバ1台の侵害が、構成管理基盤の掌握に接続する。

③ 自動署名の構成では、前提が「ネットワーク到達性のみ」に落ちる。認証局が署名要求を強い検証なしに自動署名していると、攻撃者は自分で証明書を取得できる（出典1・2・3）。自動署名はクラウド環境でノードを自動増設するために広く使われる設定であり、「便利だから入れてある設定」が、必要権限を LOW から NONE へ落とす（本記録の評価）〈重要〉。

だから「Puppet Server をインターネットに公開していないから対象外」という読み方は成立しない（本記録の評価）。本脆弱性は、社内に入った攻撃者が横展開の一手として使う形に向いている。CISA が要求行動で「資産ごとのインターネット露出を評価する責任」に触れているのはBOD 26-04 の優先順位付けの枠組みであって（出典3）、露出していなければ対象外という意味ではない（読みは本記録の整理）。

構成管理基盤の侵害は「1台の侵害」では終わらない評価・解釈

本脆弱性の深刻さは、CVSS の数値よりも侵害される対象の位置にある（本記録の評価）。

Puppet Enterprise は、配下のサーバ群に対して次のものを中央から配る位置にいる。

  • OS とミドルウェアの構成・パッケージ
  • 設定ファイル（認証・ネットワーク・ログ出力の設定を含む）
  • 秘密情報（Hiera／eyaml 経由の資格情報、SSH 鍵、API トークン）
  • 実行されるスクリプト（exec リソース）

Puppet Server を掌握した攻撃者は、配下ノードへ「正規の構成変更」として任意の処理を配布できる（本記録の評価）〈重要〉。エージェント側のログには、通常の構成適用として記録される。

実行権限について、一次資料は「サービス実行ユーザとして」と書いており、root とは明記していない（出典1。本記録の確認）。しかし権限の高低より、その役割が問題である（本記録の評価）——サービス実行ユーザは、配布すべき構成と秘密情報に読み取りで届く。

検知の観点でも不利である（本記録の評価）。構成管理は「サーバの設定が勝手に変わる」ことを正常な動作として持つ仕組みであり、設定変更の検知だけでは異常として浮かばない。浮かび上がるのは、配布された内容を誰が承認したかを突き合わせたときだけである。コードとして管理している構成（Git のコミット）と、実際に Puppet Server から配られた構成の差分を取る仕組みを持っていない組織では、この突き合わせができない。

同じ欠陥に 9.4 と 9.9 の2つの評点がある評価・解釈

本脆弱性には、公的な評点が2つある（本記録が両方を直接確認）。

評価主体 尺度 基本値 ベクタ
Perforce（CNA） CVSS 4.0 9.4（Critical） AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H
NVD（NIST） CVSS 3.1 9.9（Critical） AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H

これは評価の対立ではなく、尺度の違いである（本記録の整理）〈齟齬2〉—— CVSS 4.0 と 3.1 は計算式が違い、同じ条件でも数値が一致しない。NVD が Scope を Changed（S:C）と見ていることが 9.9 を押し上げている。

実務上の問題は、社内規則が数値だけで期限を決めている場合である（本記録の評価）。「CVSS 9.5 以上は48時間以内、9.0〜9.5 は7日以内」のような規則では、どちらの数値を採るかで初動の期限が変わる。そして本件はすでに KEV に載っている（出典3）——評点で揉めるより、「悪用が確認されたか」を先に見る規則のほうが本件では速い（本記録の評価）。

なお日本語で報じた Security NEXT は CVSS 4.0 の 9.4 を採っており、一次資料（Perforce の CVE レコード）と一致している（出典1・4。本記録が突き合わせて確認）。

    **本件の値は Unknown（不明）である**（出典3。本記録が JSON を直接確認）〈重要〉。 **「使われていない」ではなく「分かっていない」である。** **ランサムウェアでの使用が確認された脆弱性を優先する運用は合理的だが、 Unknown を「否」として扱うと、収載直後の脆弱性は構造的に後回しになる** （本記録の評価）——**悪用が広がるのはまさにその時期である。**
    取るべき行動 **社内の判定表で `Unknown` を独立した第3の値として扱い、 「否」と同じ扱いにしない**（本記録の推奨）。 **併せて `forensicTriage` の値も「侵害調査が要るか」の判断根拠にしない**—— **これは CISA が米連邦機関に要求するかどうかの指定であって、 自組織のリスク評価ではない**（出典3。読みは本記録の整理）。
  • 構成管理基盤・CI/CD・資産管理のような「全サーバへ届く仕組み」を、 通常のサーバと同じ優先度の枠で管理していると、1台の侵害が全体に接続する。
    **Puppet Server は配下ノードの構成・設定・秘密情報・実行スクリプトを 中央から配る位置にある**（本記録の評価）〈重要〉。 **掌握した攻撃者は「正規の構成変更」として任意の処理を配布でき、 エージェント側のログには通常の適用として記録される。** **本脆弱性の前提は「CA 署名済み証明書を持つクライアントからの到達」であり、 末端サーバ1台の侵害が条件を満たす**（出典1・2・3）。
    取るべき行動 **資産台帳に「射程（この機器を掌握したら何台に届くか）」の欄を設け、 射程が一定数を超える機器を別の管理区分に移す**（本記録の推奨）。 **別区分に対しては、①パッチ適用の期限を短くする、 ②ネットワーク上の到達元を明示的に限定する、 ③配布された内容と承認記録（Git のコミット等）の差分を定期に突き合わせる、 の3点を標準とする。**
  • 「更新したか」しか追っていない運用では、本件のように再起動が必要な修正で 「対応済みだが脆弱なまま」の状態が生まれる。
    **Perforce は解決策に「修正コードが読み込まれるように puppet server を 再起動せよ」と明示している**（出典1。原文英語。本記録が訳した）〈重要〉。 **構成管理基盤は停止の調整が要る位置にあるため、 更新と再起動の間に時間が空きやすい**（本記録の評価）。 **パッチ管理台帳が版番号だけを見ていると、この空白が見えない。**
    取るべき行動 **パッチ適用の完了条件を「版が上がったこと」ではなく 「修正が有効になったこと」と定義し直す**（本記録の推奨）—— **再起動・サービス再読込・設定反映が必要な製品を一覧にし、 台帳にその欄を持たせる。** **確認は版番号の照会ではなく、プロセスの起動時刻で行う。**
セキュリティ技術者への示唆
  • 認証局の自動署名（autosign）を有効にしているかどうかが、本件の必要権限を 「証明書の保有」から「ネットワーク到達性のみ」へ変える。まずここを確認する。
    **一次資料は「認証局が強い検証なしに署名要求を自動署名している場合は、 認証を持たないネットワーク上の攻撃者が有効な証明書を取得して悪用できる」と 明記している**（出典1・2・3。原文英語。本記録が訳した）〈重要〉。 **自動署名はクラウド環境でノードを自動増設するために広く使われる設定であり、 「便利だから入れてある」ものが前提条件を一段下げる**（本記録の評価）。
    取るべき行動 **Puppet Server の `autosign` 設定（`puppet.conf` の autosign エントリ、 `autosign.conf`、autosign スクリプト）を確認し、 ①無条件の自動署名になっていないか、②検証に事前共有の課題文 （challengePassword）やホスト名の照合を使っているかを確かめる**（本記録の推奨）。 **無条件なら、更新までの間は自動署名を止める。 止めるとノードの増設が手作業になるため、増設予定を先に把握しておく。**
  • 更新対象の判定をメジャー版だけで行うと取り落とす。影響版は3つの系列に分かれており、 明示的に非影響とされているのは3つの版だけである。
    **影響範囲は 2023.8.0〜2023.8.13未満／2025.0.0〜2025.12.1未満／ 2026.0.0〜2026.0.1未満の3系列である**（出典1。本記録が affected を直接確認）。 **CVE レコードの `defaultStatus` は `affected` であり、 列挙外の版は「影響する」側に寄せられている**（出典1。読みは本記録の整理）〈重要〉—— **古い系列を「対象外」と読むのは誤りである。**
    取るべき行動 **稼働中の Puppet Enterprise と、同梱される puppet-agent の版 （8.22.2／9.1.3 が修正版）の両方を採取する**（本記録の推奨）。 **採取は Puppet 自身の fact（`puppetversion`・`aio_agent_version`）で 全ノードから集められる。** **非影響と明示されているのは 2023.8.13／2025.12.1／2026.0.1 の3つだけである、 という前提で突き合わせる。**
  • レポート送信の経路は正規の API なので、通信の形では異常に見えない。 見るべきはレポート処理のプロセスから生まれた子プロセスである。
    **攻撃は、エージェントが日常的に使う PUT によるレポート送信に 細工した rich-data 型を混ぜる形をとる**（出典1・2・3）〈重要〉。 **通信の宛先・メソッド・証明書はすべて正規である**（本記録の整理）—— **ネットワーク側の特徴量では区別できない。** **一方、成立したときに起きるのは「Puppet Server のサービス実行ユーザによる 任意のコード実行」であり、これはプロセスの系統として現れる**（本記録の評価）。
    取るべき行動 **Puppet Server の JVM プロセスを親とする子プロセスの生成を監視対象に加える** （本記録の推奨）—— **シェル・インタプリタ（sh/bash/python/ruby）・ネットワーク系コマンド （curl/wget/nc）の起動を検知する。** **構成管理は「設定が勝手に変わる」ことを正常動作として持つため、 設定変更の検知だけでは浮かばない。**
  • エージェント証明書は「発行したら終わり」になりやすい。任意の CA 署名済み証明書で 成立する脆弱性なので、退役済み・用途不明の証明書を残しておく代価が上がった。
    **成立条件は「CA が署名した任意のエージェント証明書」である**（出典1・2・3）〈重要〉。 **退役したノード、検証用に発行したまま忘れた証明書、外部委託先に渡した証明書が 残っていれば、それぞれが攻撃の足場になる**（本記録の評価）。
    取るべき行動 **`puppetserver ca list --all` で発行済み証明書を棚卸しし、 ①稼働中のノードに対応しないもの、②最終通信から一定期間が経ったものを 失効させる**（本記録の推奨）。 **失効の判断を誤ると稼働中のノードが構成管理から外れ、 古い設定のまま静かに残るため、失効前に最終通信時刻で突き合わせる。**
  • 配られた構成と承認した構成の差分を取る仕組みが無いと、 基盤が侵害されたときに「正規の構成変更」として処理が通ってしまう。
    **Puppet Server を掌握した攻撃者は、配下ノードへ任意の処理を 構成変更の形で配布できる**（本記録の評価）〈重要〉。 **エージェント側から見れば正規の適用であり、ログも正常として残る。** **気づける場所は、コードとして管理している構成（Git のコミット）と 実際に配られた構成の差である**（本記録の整理）。
    取るべき行動 **Puppet Server が配布したカタログ・マニフェストの出所を、 Git のコミット（承認済み）と突き合わせる定期ジョブを置く**（本記録の推奨）。 **突き合わせの単位はファイルのハッシュにする—— 「Git にあるはずのない内容が配られた」ことを検出できる形にする。**
