技術的な脆弱性は使われていない（本記録の評価）〈重要〉。使われたのは、設計どおりに動くアカウント回復の仕組みである。

ここに本件の構造上の要点がある（本記録の整理）。

ドメインは「連絡先」としてだけでなく「身元の証明」として使われている。だからドメインの保有権の移動が、そのままアカウントの保有権の移動になる。

さらに悪いのは、検知の経路も同時に失われることである（本記録の評価）〈重要〉。パスワード再設定は、本来なら所有者に通知が届く操作である。ところが通知の宛先は、乗っ取られたドメインのアドレスである。所有者には届かない。回復手段と通知手段が同一の資産に依存していると、その資産を奪われた時点で両方が失われる。

なお、DONATE.md に連絡先を書くことは寄付を受け取るための正当な用途である（本記録が内容を直接確認）。攻撃のための情報が書かれていたわけではない。皮肉なのは、同じリポジトリのモデルカードに「root ドメインに kokoro を含むウェブサイトは本モデルおよび作者と無関係である」というなりすまし注意が置かれていることである（出典2。本記録が直接確認）—— 他人のなりすましには注意を促していたが、自分の連絡先ドメインの失効は防げていない。

重みだけを87秒で書き換えると、走査にも目にも映らない評価・解釈

アカウントを乗っ取った者が何をするか。報道は一般的な答えを示している—— 「供給網攻撃における配布経路として使い、データ窃取やコード実行につながりうる」（出典1）。

基盤側は所有権を検証しておらず、報告にも応答していない対策・注意喚起

研究者の指摘を、原文に即して置く（出典1。原文英語。訳は本記録）。

「Hugging Face は公開者を審査しない。アカウントが元の正当な所有者の手にあるのか、先週ひそかに乗っ取った誰かの手にあるのかを検証しない。それらのアカウントがアップロードするモデルやデータセットも審査しない。」

そしてHertz は Hugging Face に報告したが、応答は得られなかった（出典1）。BleepingComputer も取材したが回答を得ていない。2026年11月18日時点で、同社の公表は確認できていない（本記録の確認）〈未確定2〉。

さらに、所有権検証が導入されても本件の類型は消えない（本記録の整理）。Hertz はこうも述べている（出典1）。

これは失効ドメインの有無と無関係な問題である。正当な所有者が、ある日悪意ある更新を出す場合——所有権検証はすべて通る。

したがって利用側の対策は、公開者を信頼するかどうかではなく、「取り込む版を固定し、変化を検出する」形にしかならない（本記録の評価）。これは OSS の依存管理で既に標準になっている考え方であり、公開モデルにまだ適用されていないだけである。

  • AI モデルの供給網リスクを「悪意あるコードが混ざるか」で見ていると、 本件の形（重みだけの改変）を1つも捉えられない。審査の観点を変える。
    **研究チームが示したのは、アプリ側のコードを一行も触らず 重みだけを87秒で書き換えて発話内容を差し替える形である**（出典1）〈重要〉。 **「重みだけが変わるため、マルウェア走査が検出できる悪意あるコードも 署名も存在しない」**（出典1。原文英語。本記録が訳した）。 **公開者・配送経路・形式・構成・ファイルサイズも正規のリリースと 区別できず、別アカウントからの試験で基盤側は何も警告しなかったとされる**（出典1）。
    取るべき行動 **AI モデルの受け入れ基準に、コード走査とは別の2項目を加える** （本記録の推奨）—— **①取り込む版を改訂の識別子（コミットハッシュ）で固定していること、 ②重みファイルのハッシュを記録して取得のたびに照合していること。** **併せて、出力の内容を検証する試験（音声合成なら入力文と合成結果の突き合わせ）を 導入時と更新時に回す仕組みを、モデルごとに1つ決める。** **「ウイルス検査に通った」をモデルの安全性の根拠にしない。**
  • 基盤事業者（Hugging Face）の改善を前提に計画を立てると止まる。 本件では報告にも取材にも応答が無い。
    **Hertz は Hugging Face に報告したが応答は得られず、 BleepingComputer の取材にも回答していない**（出典1）〈重要〉。 **2026年11月18日時点で同社の公表は確認できていない**（本記録の確認）〈未確定2〉。 **さらに、所有権検証を導入しても本件の類型は消えない**（本記録の整理）—— **「乗っ取られていないアカウントでも、 一定期間もっともらしい姿を作っておいて悪意ある更新を押し込める」**（出典1）。
    取るべき行動 **AI モデルの取り込みに関する統制を、基盤側の機能に依存しない形で設計する** （本記録の推奨）—— **①取得経路を1か所に集約し、②自組織側に写しを持ち、 ③本番に入っている版を常に答えられる状態にする。** **基盤の改善が入ったら統制を緩める、という順序にする**—— **緩める前提で待つのではなく、緩められる条件を先に決めておく。**
  • 自組織が OSS やモデルの公開者である場合、公開文書に書いたドメインが 身元の証明として使われている。個人ドメインに依存していないか確認する。
    **乗っ取りの入口は、公開リポジトリの DONATE.md に記載された 連絡先ドメインだった**（出典1。本記録が記載を直接確認）〈重要〉。 **ドメインが失効すると、取り直した者がパスワード再設定で アカウントを掌握できる**（出典1）。 **しかも再設定の通知先が同じドメインであるため、 所有者には通知が届かない**（本記録の整理）—— **回復手段と検知手段が同一の資産に乗っている。**
    取るべき行動 **自組織が公開しているリポジトリ・パッケージ・モデルについて、 ①公開文書に記載した連絡先ドメイン、 ②アカウント回復に使えるメールアドレス、 ③多要素認証の設定状況 の3点を棚卸しする**（本記録の推奨）。 **個人所有のドメインが使われている場合は、 組織が保有し続けるドメインに寄せる。** **寄せる際には、担当者の異動・退職時の引き継ぎ手続きを同時に作る**—— **手続きが無いと「誰も入れないアカウント」になる。**
  • 「保守が止まっている依存先」の一覧を持っていないと、 気づかれない期間がそのまま乗っ取りの機会になる。本件は約1年7か月あった。
    **Hexgrad の更新は2025年4月以降止まり、 GitHub と PyPI も同時期に沈黙していた**（出典1。 本記録もモデルカードの「2025年4月時点」という注記で裏を取った）〈重要〉。 **その間、Hugging Face での月間ダウンロードは約1,300万回あった**（出典1）。 **更新停止から公開者アカウント掌握まで約1年7か月である**（本記録が算出）—— **ドメインの失効に気づく役割の人が、活動を止めていた。**
    取るべき行動 **依存している公開モデル・OSS の「保守状況」を四半期ごとに確認し、 止まっているものを一覧にする**（本記録の推奨）。 **確認の観点を3つに固定する**—— **①最終更新日、②関連する GitHub・パッケージレジストリの活動、 ③公開文書に記載された連絡先ドメインが生きているか（whois の登録日で、 取り直された直後かどうかが分かる）。** **一覧は「やめる判断」ではなく「固定と監視を強める判断」に使う**—— **保守が止まっていても使い続ける合理性はある。**
セキュリティ技術者への示唆
  • Hugging Face からモデルを取り込むとき、revision を指定していないと 公開者が差し替えた重みが自動で入る。コミットハッシュで固定する。
    **乗っ取ったアカウントから出される更新は、 公開者・配送経路・形式・構成が正規のリリースと同じで、 ファイルサイズも似ている**（出典1）〈重要〉。 **「更新を自動で取得するシステムへ、 改変された重みが日常的な更新として配られる供給網リスクは大きい」** （出典1。研究者の指摘。原文英語。本記録が訳した）。 **本件では配布は行われていないが、 配布されれば取り込み側に区別する手段が無い**（本記録の整理）。
    取るべき行動 **モデルの読み込みで revision を必ず指定し、 値にはコミットハッシュを使う**（本記録の推奨）—— **main などのブランチ名やタグは、公開者側で付け替えられる。** **指定箇所を洗い出す対象は、アプリのコード、 コンテナイメージのビルド手順、CI の設定、 推論サーバの設定ファイルの4か所である。** **併せて、取得した重みを自組織の保管場所へ写し、 本番はそこから読む形にする**——**上流が消えても動く。**
  • 重みファイルのハッシュを記録していないと、改変されても比べる相手が無い。 固定と照合は対にして入れる。
    **マルウェア走査では検出できず、 公開者・経路・形式・大きさでも区別できない**（出典1）〈重要〉。 **現実的に残る機械的な手がかりは、重みのハッシュの変化だけである** （本記録の評価）。 **ただし版を固定していなければ、 「正規の更新で変わった」と「改変された」を区別できない**（本記録の整理）。
    取るべき行動 **取り込んだ重みファイルのハッシュ（SHA-256）を、 モデル名・revision と一緒に台帳へ記録する**（本記録の推奨）。 **取得のたびに照合し、不一致なら本番への投入を止める。** **不一致が出たときの手順を併せて決める**—— **①公開者の更新の告知を確認、②revision の差分を確認、 ③出力の内容を検証、の順で判断する。** **照合だけを入れると警報が鳴り続けて無視されるため、 判断手順まで作る。**
  • 出力の内容を検証する経路を持っていないと、重みの改変は最後まで映らない。 入力と出力の一致を自動で試験する。
    **改変されたモデルは、同じ入力文に対して違う音声を出した**（出典1）〈重要〉。 **つまり異常は、ファイルでもプロセスでも通信でもなく、 出力の内容にしか現れない**（本記録の整理）。 **「同じ入力文、同じ音声ファイル、同じ設定、同じ推論コード」で 結果だけが変わる**（出典1。研究者の発言）。
    取るべき行動 **モデルの導入時と更新時に、出力の内容を検証する試験を自動で回す** （本記録の推奨）—— **音声合成なら、既知の入力文を合成し、 その音声を音声認識にかけて入力文と突き合わせる。** **試験文は固定し、固有名詞・数値・否定表現を含めておく**—— **改変は意味を変える方向に効くため、 数値や否定が入る文のほうが差が出やすい**（本記録の評価）。 **音声認識の誤りによる偽の警報が出るため、 閾値は実測して決める。**
  • ミラーや変換版（量子化版・ONNX 版）から取っていると、 元が直っても自分のところは直らない。取得元を一次に寄せる。
    **研究者の指摘（原文英語。本記録が訳した）**: **「同じ未審査の重みとデータセットが、ミラーや変換版、GitHub のリリース、 パッケージレジストリ、導入手順、直接ダウンロードを通じて、 公開モデルの生態系全体に流れていく」**（出典1）〈重要〉。 **Kokoro には第三者による複製・変換版が多数存在する**（本記録の確認）—— **変換版の作成者が元の改変に気づく保証は無い。**
    取るべき行動 **本番で使う公開モデルの取得元を棚卸しし、 一次の公開者以外から取っているものを洗い出す**（本記録の推奨）。 **変換版（量子化・ONNX 等）を使う必要がある場合は、 ①誰が作ったか、②元のどの revision から変換したか、 ③変換の手順が再現できるかを記録する。** **③が満たせるなら、自組織で変換して一次から辿れる形にする。**
  • 自分が公開者側のとき、アカウント回復の通知先と回復手段を 別の資産に分けておかないと、奪われた瞬間に気づく手段も失う。
    **パスワード再設定は本来なら所有者に通知が届く操作だが、 通知の宛先が乗っ取られたドメインのアドレスである**（本記録の整理）〈重要〉。 **したがって所有者には届かない**—— **回復手段と検知手段が同一の資産に乗っている。** **Hexgrad 本人が気づいたかは公表されていない**（本記録の確認）〈未確定1〉。
    取るべき行動 **自分が管理する公開者アカウントについて、 ①多要素認証を有効にする（メールの到達だけでは再設定が完了しない状態にする）、 ②回復用の予備コードをドメインに依存しない場所に保管する、 ③通知先に、回復に使うアドレスとは別ドメインのアドレスを追加する、 の3点を行う**（本記録の推奨）。 **③は、回復手段を奪われても通知だけは届く形にするためである。** **併せて、公開文書に書いたドメインの自動更新と 支払い手段の有効期限を確認する。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
委託・第三者部品□ 本番で使う公開モデル・データセットを、改訂の識別子（コミットハッシュ）で 固定せずに取り込んでいる（revision 未指定、または main などのブランチ名・ タグを指定している）。
委託・第三者部品□ 公開モデルをミラー・変換版（量子化版・ONNX 版）から取得しており、 元のどの改訂から変換されたかを記録していない。
運用・監視□ 取り込んだ重みファイルのハッシュを記録しておらず、 取得のたびに照合する仕組みが無い。
運用・監視□ モデルの出力の内容を検証する試験（入力と出力の一致確認）を 導入時・更新時に回していない。
認証・認可□ 自組織が公開者（OSS・モデル・パッケージ）であり、 公開文書に記載した連絡先や回復用アドレスが個人所有のドメインに依存している。 または公開者アカウントに多要素認証を設定していない。
体制・契約□ 依存している公開モデル・OSS の「保守が止まっているか」を定期に確認する運用が無く、 止まっている依存先の一覧を持っていない。
