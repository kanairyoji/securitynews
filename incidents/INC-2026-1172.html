INC-2026-1172GeoVisionのNVRにXMRig（13組織）

**インターネットに露出した GeoVision（奇偶科技）の映像監視ソフト 「GV-VMS」の WebCam Server 機能を突いて、 2026年11月8日から10日にかけて13組織の端末に XMRig の採掘プログラムが 設置された（Huntress が11月13日に公表）。** **起点は SYSTEM 権限で動く GeoStartupAgentService.exe であり、 攻撃者は正規署名を持つ脆弱ドライバ（kvckiller.sys ＝ wsftprm.sys）を 持ち込んで防御製品を妨害し、IFEO で Defender の3プロセスを systray.exe へそらしてから Go 製ローダを常駐させていた。** **ローダは BitTorrent の DHT から C2 の宛先を引くため、 ドメインを登録せずに基盤を移せる。** **GeoVision は11月11日に注意喚起を出し、未認証RCEの3件 （CVE-2026-7372・CVE-2026-42369・CVE-2026-42370）への更新を求めた ——修正版は2026年4月末に出ていた。**

C2 の宛先を BitTorrent の DHT から引くので、ドメインを潰しても止まらない評価・解釈

本件のローダ update.exe は Go で書かれており、次の2つを内蔵している（出典1）。

  • BitTorrent Mainline DHT のクライアント
  • PKARR リゾルバ

Huntress の記述はこうである（出典1。本記録が訳した）—— 「公開鍵を使って DHT 上から C2 の現在のアドレスを見つけるため、ドメインを登録せずにインフラを移動できる」。

これが何を意味するか（本記録の整理）〈重要〉。

通常、C2 の宛先はドメインかIPで固定される。だから防御側には手がある——ドメインの停止要請、IPの遮断、宛先の評判に基づく検知。

本件の設計では、そのどれも決定打にならない。観測された宛先（cctv-update[.]top / 156.246.94[.]183）を潰しても、ローダは DHT から次の宛先を引く。DHT は BitTorrent の分散ハッシュテーブルであり、特定の管理者がいない——停止要請を出す相手がいない〈重要〉。

したがって、検知の軸を変える必要がある（本記録の評価）。Huntress が追加の検知ポイントとして挙げているのは、いずれも「宛先」ではなく「どのプロセスが、どういう形で出ているか」である（出典1。本記録が訳した）。

  1. 「システム DNS クライアント以外のプロセスによる8.8.8.8、8.8.4.4、1.1.1.1 への DNS クエリ」
  2. WebCamServer.exe などの GeoVision プロセスからのUDP 6881 など DHT 関連のアウトバウンド通信
  3. update.exe が起動する schtasks /Create コマンド

2つめが本件に固有で、かつ強い（本記録の評価）〈重要〉—— カメラ管理ソフトが BitTorrent の DHT を使う正当な理由は無い。業務で BitTorrent を使う環境でも、プロセスを GeoVision のものに限定すれば誤検知は小さい。ただし DHT のポートは可変であるため、ポート番号だけに頼る検知は回避されうる（本記録の評価）。

1つめは本件に限らず使える（本記録の評価）。マルウェアが社内の DNS サーバを避けて公開 DNS を直接引く形は一般的である。自組織の正常な通信を棚卸しすれば、この指標は常設できる。

本記録の立場として付言する。 Huntress が示した痕跡（ハッシュ3件・IP 3件・ドメイン1件）は、本記録が悪性を検証したものではない〈齟齬4〉。遡及検索の条件としては使えるが、遮断の主軸にはしない—— DHT で宛先が移る設計では、IP とドメインの遮断は時間稼ぎにしかならない。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。

偵察現実的な検知機会なし
**外部からの探索自体は、組織の側では検知しにくい** （本記録の評価）〈重要〉—— **ただし、この段階は「防御側が先に自分を探す」ことで 手を打てる唯一の段階である**—— **Shodan・Censys で自組織のIP範囲を検索すれば、 攻撃者が見ているものと同じものが見える。**

初期侵入機会はあったが検知できず
**検知機会はあったが、活かされていない**（本記録の評価）〈重要〉—— **修正版は2026年4月末に出ており、CVE 公表から観測開始までは 188日ある（本記録が算出）。** **この期間に更新していれば、そもそも刺さらなかった。** **また露出を塞いでいれば、到達できなかった**（出典1・2）。 **本記録の評価では、ここでの「検知」は侵入の検知ではなく 「自組織が露出していて未更新であることの検知」である** ——**脆弱性管理の側の話になる。**
侵入を防げたGV-VMS を3件の CVE の累積修正を含む最新版（17.4.8.58 以降）へ更新する
侵入を防げた機器と管理インターフェースをインターネットから切り離す（VPN の背後に置くか、信頼できるIPに制限する）
影響を限定できたASLR 無しでコンパイルされた製品が自組織にあるかを調達時の確認項目に入れる（WebCam Server のウェブサーバは ASLR 無しとされる）
実行検知した
**ここが実際に検知された段階である**（出典1）〈重要〉—— **Huntress が観測したのは、 「カメラ管理ソフトのサービスがコマンドシェルと PowerShell を起動し、 外部IPからスクリプトを取る」という形である。** **本記録の評価では、これは極めて素性の悪い組み合わせである** ——**映像監視のサービスがスクリプトを外部から取ってくる 正当な理由は無い。** **権限昇格が不要だった点も重要である**（本記録の評価）—— **サービスが最初から SYSTEM で動いていたため、 攻撃者は昇格の段階を踏まずに最高権限を得た。**
検知できたGeoVision のサービスプロセスから起動されたコマンドシェル・PowerShell を警報にする（Huntress の推奨）
検知できたPowerShell のスクリプトブロックログを有効にし、外部IPからの取得（IWR/DownloadString）を警報にする
影響を限定できた業務用アプライアンス的なソフトウェアのサービスを SYSTEM より低い権限で動かせるかを調達・導入時に確認する
検知回避検知した
**この段階にも検知の足場がある**（本記録の評価）〈重要〉—— **①脆弱ドライバの読み込みは、 Microsoft の脆弱ドライバ遮断リスト（HVCI／WDAC）で止められる類である。 ②IFEO のレジストリキーへの書き込みは、 正規のソフトウェアがほとんど触らない場所である** ——**特に Defender のプロセス名に対する Debugger の設定は、 正当な理由がまず無い。** **ただし本件では、どちらも実行された後に検知されている** （出典1。本記録の読み）——**予防として働いてはいない。**
侵入を防げたMicrosoft の脆弱ドライバ遮断リスト（HVCI／WDAC）を有効にし、署名が有効でも既知の脆弱ドライバの読み込みを拒否する
検知できたIFEO（Image File Execution Options）配下の Debugger 値への書き込みを警報にする。特に防御製品のプロセス名に対するものは即時に扱う
検知できた防御製品のプロセスが起動していない状態を「異常」として別経路で監視する（製品自身の死活監視に依存しない）
永続化検知した
**スケジュールタスクの作成は記録に残る**（本記録の評価）〈重要〉—— **ただし「update.exe」「PackageUpdater」という名前は 正規の更新プログラムと紛れやすい**—— **効くのは名前ではなく、親プロセスの素性 （どこから起動された実行ファイルがタスクを作ったか）である。** **本記録の評価では、15分間隔という設定自体が 除去作業への対抗になっている**—— **プロセスを1回止めただけでは15分後に復活する。**
検知できたschtasks /Create の実行を親プロセスの素性つきで記録し、業務上の更新プログラム以外からの作成を警報にする
復旧を早められた除去の手順で、スケジュールタスクの削除をプロセスの停止より先に行う（15分間隔での再実行を止めてから作業する）
C2通信機会はあったが検知できず
**宛先による検知が働かない設計である**（本記録の評価）〈重要〉—— **`cctv-update[.]top` というドメインは停止要請の対象になりうるが、 ローダは DHT から次の宛先を引けるため、 ドメインを潰しても通信は続く。** **IP の遮断も同様である。** **効くのは「どのプロセスがどこへ出ているか」である** ——**Huntress が検知ポイントに 「GeoVision のプロセスからの DHT 関連の外向き通信（UDP 6881 など）」と 「システム DNS クライアント以外のプロセスによる 8.8.8.8・8.8.4.4・1.1.1.1 への DNS 問い合わせ」を挙げているのは この筋である**（出典1）。 **カメラ管理ソフトが BitTorrent の DHT を使う正当な理由は無い** （本記録の評価）。
検知できたGeoVision のプロセスからの DHT 関連の外向き通信（UDP 6881 など）を警報にする（Huntress の推奨）
検知できたシステム DNS クライアント以外のプロセスによる公開 DNS（8.8.8.8・8.8.4.4・1.1.1.1）への問い合わせを警報にする（Huntress の推奨）
検知できた痕跡の IP・ドメインは遡及検索の条件として使い、遮断の主軸にはしない（DHT で宛先が移るため）
影響（暗号化・破壊・改ざん）検知した
**採掘は CPU 使用率と外向き通信に現れるため、 影響の段階としては見つけやすい**（本記録の評価）〈重要〉—— **ただし本件の被害端末は映像監視システムであり、 映像の処理で常時 CPU 負荷が高い。** **採掘の負荷が平常の負荷に埋もれやすい**（本記録の評価）。 **また XMRig が `ApplyUpdate.exe` という 正規の更新プログラムらしい名前で動いていることも、 目視での発見を妨げる。**
検知できた映像監視サーバの CPU 使用率・消費電力の基準線を取り、恒常的な上振れを警報にする（採掘は負荷が平常化するため、瞬間値ではなく基準線との差で見る）
検知できた採掘プールへの通信（Stratum プロトコル・既知のプールのドメイン）を警報にする

GeoVision は Huntress の公表（11月13日）より前の11月11日に 自ら注意喚起を出した（出典1・2）機能した**本記録は effective と評価する**〈重要〉—— **根拠は2つである。①第三者の公表より2日早く、 自社の利用者に向けた具体的な手順つきで出した（出典1・2）。 ②「3件の累積的な修正を含む最新版への更新が必要」と明示し、 部分的な対応では足りないことを伝えた（出典2）。** **留保**: **本記録は注意喚起の原文を取得できていない**〈齟齬2〉—— **評価は iThome の報道（出典2）が伝える内容に基づく。** **また、2026年4月末の時点で「インターネットに露出させるな」という 構成上の注意が十分に伝わっていたかは分からない**（本記録の明示）。
CISO・経営層への示唆
  • 映像監視・入退管理・設備制御のソフトウェアを情報システムの資産台帳に載せる
    **本件の被害端末は映像監視ソフト（GV-VMS）であり、 Huntress は結びで「カメラ管理ソフトウェアも企業の 攻撃対象領域に含めて扱うべきだ」と述べている**（出典1・3）〈重要〉—— **本記録の評価では、映像監視は「設備」として扱われ、 情報システムの棚卸しから外れていることが多い。** **外れていれば、脆弱性管理の対象にも、 露出の点検の対象にも、監視の対象にもならない。** **本件では修正版が2026年4月末に出ていたのに、 被害端末は11月まで 17.4.8.0 で動いていた**（出典2・3）。
    取るべき行動 映像監視・入退管理・設備制御・環境監視のソフトウェアと機器を 棚卸しし、情報システムの資産台帳に登録する。 各資産について「所管部署」「バージョン」「インターネットへの露出」 「更新の責任者」の4列を埋める。 設備・警備の担当が導入したものを漏らさないため、 購買記録と現場の確認を併用する。 埋められない資産は、その事実を記録して所管の確定を依頼する。
  • 自組織のIP範囲を Shodan・Censys で定期的に検索し、攻撃者と同じものを見る
    **Huntress は Shodan で被害端末の外部IPを照合し、 公開された GeoVision 機器または管理インターフェースに 対応していたことを確認した**（出典1）〈重要〉—— **つまり、防御側が Shodan で見つけられるものを、 攻撃者も同じように見つけられる状態だった**（本記録の整理）。 **本記録の評価では、これは「探索の段階」で 防御側が先に手を打てる唯一の機会である。**
    取るべき行動 自組織が保有するIP範囲（クラウドの割り当て分を含む）を一覧化し、 Shodan・Censys で月次に検索する運用を作る。 見つかった機器・管理インターフェースについて、 公開が意図的か否かを所管部署に確認する。 意図的でないものは遮断し、意図的なものは 認証・更新状況・監視の3点を点検する。 外部に委託している場合は、委託先のIP範囲も対象に含めるか確認する。
  • 「更新できない前提」で露出を塞ぐ計画を先に立てる
    **修正版は2026年4月末に提供され、 CVE 公表から観測開始までは188日あった**（出典2・3。本記録が算出）〈重要〉—— **それでも被害端末は更新されていなかった。** **本記録の評価では、映像監視システムには構造的な事情がある** ——**①更新は録画の中断を伴う、②所管が情報システム部門でないことが多い、 ③「動いているから触らない」が成立しやすい。** **これらは脆弱性の評点では動かない。**
    取るべき行動 更新の窓を取りにくい資産（24時間稼働・設備系・所管が分散）を 一覧化し、各資産について「更新できないあいだに何で補うか」を書く。 補い方の第一は、インターネットからの切り離し （VPN の背後・信頼できるIPへの制限）である。 切り離しによって失われる運用（委託先の遠隔監視等）を 事前に洗い出し、代替手段を決める。 更新の計画は別に立て、年次の停止調整の議題にする。
  • 「採掘だけだった」事案を軽微として処理しない基準を決めておく
    **本件でデータの持ち出し・暗号化・恐喝は観測されていない** （出典1）〈重要〉—— **しかし攻撃者は SYSTEM 権限、正規署名の脆弱ドライバによる ウイルス対策の妨害、IFEO による Defender 3プロセスの起動阻害、 起動時と15分ごとの自動実行、ドメインに依存しない C2 を 揃えている**（出典1）。 **本記録の評価では、これは採掘には過剰な道具立てであり、 同じ足場から別のことをするのに必要なものはすべて揃っている。** **被害端末がカメラ映像と接続機器の認証情報に 到達できる位置にあることも効く**（出典5）。
    取るべき行動 インシデントの重大度判定の基準に、 「被害の種類」ではなく「攻撃者が得た状態」の欄を設ける。 具体的には、①最高権限の取得、②防御製品の無効化、 ③再起動をまたぐ永続化、④外部との継続的な通信路の4つを チェック項目にする。 採掘・アドウェアのような「被害が軽い」事案でも、 この4つが揃っていれば侵害調査（フォレンジック）の対象とする。
セキュリティ技術者への示唆
  • 外部から到達できるソフトウェアのサービスが、どの権限で動いているかを確かめる
    **本件の攻撃チェーンには権限昇格の段階が無い** （本記録の整理）〈重要〉—— **起点となった `GeoStartupAgentService.exe` が 多くの端末で `NT AUTHORITY\SYSTEM` 権限で動いていたため、 攻撃者は未認証RCEで入った瞬間に端末の最高権限を持っていた**（出典1）。 **GeoVision 自身も「侵入した後、Windows の SYSTEM 権限で PowerShell を実行し」と説明している**（出典2）。 **本記録の評価では、外部から到達できるサービスが SYSTEM で動くとき、 脆弱性1件の価値が「端末の完全な掌握」になる。**
    取るべき行動 外部から到達できるソフトウェア（管理インターフェース・ ウェブサーバ機能・API）のサービスについて、 実行アカウントを一覧化する。 SYSTEM・root で動いているものは、 製品が低い権限での動作に対応しているかをベンダーに確認する。 対応していない場合は、その事実をリスク登録簿に記載し、 露出させない運用で補う。 新規の調達では、サービスの実行権限を確認項目に入れる。
  • 脆弱ドライバの遮断リスト（HVCI／WDAC）を有効にし、署名の有効性だけで判断しない
    **攻撃者は `kvckiller.sys` を持ち込んだが、 これは VirusTotal 上で既知の `wsftprm.sys` と同一であり、 過去に BYOVD 手法でウイルス対策製品の防護機構を 妨害する目的で悪用されたものである**（出典1）〈重要〉—— **つまり「既知の脆弱ドライバ」である。** **本記録の評価では、署名が有効であることは 安全であることを意味しない**—— **脆弱なドライバは正規に署名されている。**
    取るべき行動 Windows 端末で Microsoft の脆弱ドライバ遮断リストを有効にする （メモリ整合性／HVCI、または WDAC のポリシー）。 有効化できない端末（互換性の問題がある業務系）を一覧化し、 その端末で読み込まれているカーネルドライバの一覧を取得して 定期的に差分を確認する。 新規に読み込まれたドライバを警報にする。
  • IFEO 配下の Debugger 値への書き込みを警報にする
    **攻撃者は Defender 関連の3プロセス（`MsMpEng.exe`・ `SecurityHealthService.exe`・`SecurityHealthSystray.exe`）に IFEO（Image File Execution Options）の Debugger を設定し、 起動時に `systray.exe` へリダイレクトした**（出典1）〈重要〉—— **これらのセキュリティコンポーネントの起動を妨げる狙いと見られる。** **本記録の評価では、IFEO は正規のソフトウェアが ほとんど触らないレジストリの場所である**—— **特に防御製品のプロセス名に対する Debugger の設定は、 正当な理由がまず無い。**
    取るべき行動 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options` 配下の `Debugger` 値への書き込みを監視し、警報にする。 防御製品のプロセス名に対するものは、 調査を待たずに即時の対応対象とする。 併せて、防御製品のプロセスが起動していない状態を 別経路（EDR の管理コンソール・資産管理ツール）で監視する ——製品自身の死活監視に依存しない。
  • 業務用ソフトウェアのプロセスからの異常な外向き通信を、宛先ではなくプロセスの素性で絞る
    **ローダは BitTorrent Mainline DHT と PKARR で C2 の現在の宛先を引くため、ドメインを登録せずに インフラを移動できる**（出典1）〈重要〉—— **観測された宛先（`cctv-update[.]top` / 156.246.94[.]183）を潰しても、 次の宛先が引かれる。DHT には停止要請を出す相手がいない。** **Huntress が挙げる検知ポイントは、いずれも 「どのプロセスが、どういう形で出ているか」である**（出典1）—— **カメラ管理ソフトが BitTorrent の DHT を使う正当な理由は無い。**
    取るべき行動 業務用ソフトウェア（映像監視・設備制御・業務アプリ）のプロセスについて、 正常な外向き通信先を棚卸しし、それ以外への通信を警報にする。 特に次の3つを指標として常設する。 ①システム DNS クライアント以外のプロセスによる 公開 DNS（8.8.8.8・8.8.4.4・1.1.1.1）への問い合わせ、 ②業務用ソフトウェアのプロセスからの DHT 関連通信（UDP 6881 など。 ポートは可変であるためプロセス側で絞る）、 ③`schtasks /Create` の実行（親プロセスの素性つきで記録する）。
  • 痕跡の IP・ドメインは遡及検索に使い、遮断の主軸にしない
    **Huntress が示した痕跡は、ハッシュ3件・IP 3件 （2.59.133[.]151・45.32.117[.]34・156.246.94[.]183）・ ドメイン1件（`cctv-update[.]top`）である**（出典1）〈重要〉—— **本記録はこれらの悪性を独自に検証していない**〈齟齬4〉。 **本記録の評価では、DHT で宛先が移る設計では IP とドメインの遮断は時間稼ぎにしかならない**—— **一方、過去のログに対する遡及検索の条件としては有効である。**
    取るべき行動 痕跡を遡及検索の条件として過去のログ（プロキシ・DNS・EDR）に 当てて、自組織に該当がないかを確認する。 遮断に使う場合は、その IP が共用の基盤（VPS・CDN）でないかを 先に確認し、業務影響を評価する。 遮断を主軸にせず、前項のプロセス単位の指標を常設の防御とする。
  • 除去の手順で、スケジュールタスクの削除をプロセスの停止より先に行う
    **一部の端末では、15分ごとに `update.exe` を実行する スケジュールタスク `PackageUpdater` と、 起動時に SYSTEM 権限で実行する `PackageUpdater_Startup` が 作成された**（出典1）〈重要〉—— **本記録の評価では、プロセスを1回止めただけでは15分後に復活する。** **一方、Huntress は「ファイルの削除や設定変更の前に 対象ホストを隔離し証拠を保全せよ」と推奨している**（出典1）—— **IFEO の設定・スケジュールタスク・ドライバの読み込み履歴は、 消してしまえば何が起きたかが分からなくなる。**
    取るべき行動 永続化を伴うマルウェアの除去手順を、 ①ネットワークからの隔離、②証拠の保全（メモリ・レジストリ・ スケジュールタスク・ドライバの一覧の取得）、 ③永続化の削除（スケジュールタスク・IFEO・サービス）、 ④プロセスの停止とファイルの削除、の順に定める。 手順書に「順序を入れ替えない理由」を併記する （作業中の再感染と、痕跡の消失を防ぐため）。
法務・コンプライアンスへの示唆
  • 被害が「採掘のみ」でも、個人データに到達できる位置の侵害は通知義務の検討対象にする
    **本件でデータの持ち出しは観測されていない**（出典1）〈重要〉—— **しかし被害端末は複数の監視カメラの映像を集約するソフトウェアであり、 SYSTEM 権限を得た攻撃者は映像・録画・設置場所に 到達できる位置にいた**（出典5。本記録の評価）。 **映像は個人を識別しうるデータであり、 日本の個人情報保護法でも個人情報に該当しうる**（本記録の整理）。 **「持ち出しが観測されていない」ことは 「到達されていない」ことを意味しない**〈未確定5〉。
    取るべき行動 インシデント対応の判断フローに、 「侵害された機器から到達できた個人データ」を 被害の種類とは別に評価する欄を設ける。 到達できた範囲が特定できない場合（ログが無い等）の扱いを 事前に決めておく（保守的に通知を検討するか、 到達の証跡が無いことを根拠に通知しないか）。 判断の根拠と判断者を記録に残す。 映像監視・入退管理のデータについては、 所管部署と個人情報の管理台帳の記載を確認する。

システム構成□ 映像監視・入退管理・設備制御のソフトウェアがインターネットから到達できる位置にあり、管理インターフェースやウェブサーバ機能が公開されているHuntress は Shodan で被害端末の外部IPを照合し、公開された GeoVision 機器または管理インターフェースに対応していたことを確認した

運用・監視□ 設備系・24時間稼働の資産が情報システムの資産台帳に載っておらず、バージョンと更新の責任者が把握されていない修正版は2026年4月末に出ており CVE 公表から188日あったが、被害端末は GV-VMS 17.4.8.0 で動いていた

体制・契約□ インシデントの重大度判定が「被害の種類」に基づいており、「攻撃者が得た状態」（最高権限・防御の無効化・永続化・継続的な通信路）を見ていない本件は採掘という軽い被害に見えるが、攻撃者は SYSTEM 権限・防御製品の二重の無効化・起動時の永続化・移動可能な C2 を揃えていた
