INC-2026-1173nginxのHTTP/2に未認証RCE（PoC公開）

**nginx の HTTP/2 の流量制御に整数アンダーフローの脆弱性 CVE-2026-123007（CWE-191・CVSS 4.0 で 9.2）があり、 認証を持たない遠隔の攻撃者がワーカープロセスの権限で コードを実行しうる。** **F5 と Rapid7 が2026年11月18日に同時開示し、 Rapid7 は nginx 1.31.8 の Docker 版に対する未認証RCEの実証を公開した。** **CERT-FR は公開された実証コードの存在を把握したとして警報を出し、 HTTP/2 の無効化を推奨している。** **影響は2015年の 1.9.5 以降の全系列に及び、修正は 1.31.9／1.30.7 である。** **悪用には約128GBの HTTP/2 データ送信が要るため、 回線速度と接続の寿命が実際の障壁になる。**

脆弱性続報が続いている日本に波及した海外事案設計・実装上の不備
初報: 2026年11月18日（F5・Rapid7・Wiz・Xint の同時開示、および CERT-FR の警報） 最終更新: 2026年11月19日（第1回続報。IPA・JPCERT/CC の注意喚起、Censys の再現、KEV 未収載の確認）

2026年11月18日、F5 と Rapid7 は nginx の HTTP/2 に 整数アンダーフローの脆弱性 CVE-2026-123007 があることを同時に開示した （出典1・5）〈重要〉。 CWE-191（整数アンダーフロー）、CVSS 4.0 の基本値は 9.2（Critical）、 ベクタは CVSS:4.0/AV:N/AC:H/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N である （出典5。本記録が NVD の API で直接確認）。 F5 の説明は次のとおりである（出典5。原文英語。本記録が訳した）〈重要〉—— 「この問題は HTTP/2 を使う NGINX Plus または NGINX Open Source の 構成に影響する。NGINX が未開示のトラフィックを処理するとき、 流量制御ウィンドウが許容されたしきい値を超えることがあり、 ヒープバッファオーバーフローを、通常は NGINX ワーカーの セグメンテーション違反を伴って引き起こしうる。 加えて、アドレス空間配置のランダム化（ASLR）が無効化されているシステム、 または攻撃者が ASLR を回避できる場合には、 攻撃者はコードを実行できる」。 「制御プレーンへの露出は無く、これはデータプレーンのみの問題である」（出典5）。 Rapid7 は、nginx 1.31.8 の linux/amd64 の Docker イメージに対して 未認証のリモートコード実行を実証した（出典1）〈重要〉—— 対象の構成は http2 on かつ TLS 有効である。 発見者は Rapid7 の Stephen Fewer（Senior Principal Security Researcher）である（出典1）。 本記録が最初に書いておくべきことは、悪用の現実性である。 悪用には約128GBの HTTP/2 データの送信が必要で、 10Gbit/s の回線で約2分、1Gbit/s で約17分かかる（出典1）〈重要〉—— nginx の既定の接続寿命は1時間であるため、 おおよそ 300Mbit/s より遅い回線では接続の上限を超えてしまい成功しない（出典1）。 また HTTP/2 接続がプロキシされている場合、 攻撃者が制御する正確なフレームが悪用を満たす形で再送されない見込みが高い（出典1）。 さらに Rapid7 の実証は、実行時に選ばれる x86-64 glibc の EVEX/YMM 版 memcpy 実装（avx512f と avx512vl の CPU 機能に依存）に 依拠している（出典1）。 一方、CERT-FR は2026年11月18日に警報 CERTFR-2026-ALE-017 を出し、 CVE-2026-123007 について「公開された実証コードの存在を把握している」として HTTP/2 の無効化を推奨した（出典2）〈重要〉。 Wiz は公式ビルドの nginx 1.31.7 および 1.31.8 に対して ASLR の回避を伴う RCE を確認したとしつつ、実証コードは公開しないとした（出典4）—— つまり「ASLR が有効なら安全」とは読めない（本記録の整理）。 本件は Xint が「NGINX2Root」と総称した5件の一部であり、 Xint は各脆弱性を Linux カーネルの SCTP の脆弱性と連鎖させれば ホスト上で root 権限を取得できる（nginx が Docker コンテナで 動いている場合も含む）としている（出典3）〈重要〉。 影響は2015年の nginx 1.9.5 以降の全系列に及び、 修正は 1.31.9（mainline）と 1.30.7（stable）である（出典4・6）。

送信枠を符号なし整数で持ち、戻すときに上限を検査していなかった原因・手口

技術的な要点を、一次資料の記述に沿って置く（出典1）。

① 型が違う。 nginx は HTTP/2 の送信枠を2つ持っている（出典1）。

// src/http/v2/ngx_http_v2.h
#define NGX_HTTP_V2_MAX_WINDOW  ((1U << 31) - 1)

struct ngx_http_v2_connection_s {
    size_t   send_window;   // 接続単位（符号なし）
};
struct ngx_http_v2_stream_s {
    ssize_t  send_window;   // ストリーム単位（符号つき）
};

ストリーム側が ssize_t（符号つき）なのは意図的である（出典1）—— SETTINGS_INITIAL_WINDOW_SIZE の引き下げで枠が一時的に負になることを許すためである。一方、接続側は size_t（符号なし）であり、64ビットビルドでは 0 から 2^64-1 を保持できる〈重要〉。HTTP/2 の上限 2^31-1 は型では守られておらず、nginx 自身のロジックで強制する必要があった。

② 戻すときに検査が無い。 nginx は DATA フレームをキューに入れる時点で、接続とストリームの枠からフレーム長を引いて予約する（出典1）。その要求が閉じると、クリーンアップ処理が未開始の DATA を取り除き、予約していた枠を戻す——

// ngx_http_v2_filter_cleanup()
window += frame->length;      // 取り除いたフレームの長さを合計
...
h2c->send_window += window;   // ← 上限を超えないかを検査していない

この加算が、本脆弱性の最初の不正状態である（出典1）〈重要〉。Rapid7 の例では、枠が 2,147,483,647（0x7FFFFFFF）に達した後に1,393 バイトを戻すと 2,147,485,040（0x80000570） になる—— HTTP/2 としては不正だが、64ビットの size_t には収まる。まだ桁あふれは起きていない。

③ 接続が生き残る実装になっていた。攻撃者は、枠を過剰にした状態の接続を使い続ける必要がある。そのために SETTINGS_INITIAL_WINDOW_SIZE を上げて、対象ストリームの枠が上限を超える状態を作る（出典1）。RFC 9113 はこの条件で、接続を FLOW_CONTROL_ERROR で終わらせることを求めている〈重要〉。ところが nginx は ngx_http_v2_terminate_stream() を呼び、RST_STREAM で該当ストリームだけを終わらせて、接続は使える状態に残す（出典1）。

④ 過大な枠が負の応答長として解釈される。次の接続 WINDOW_UPDATE の検査で符号なし減算がアンダーフローし、以後 WINDOW_UPDATE を繰り返すことでカウンタを64ビットの上位半分へ押し上げられる（出典1）。64ビットビルドでは、nginx はその過大なカウンタを負の応答長（符号つき off_t） として解釈して不正なバッファを作り、バッファされた TLS 出力が巨大な符号なしバイト数を memcpy に渡す——境界外の読み書きが起きる。

本記録の評価として整理する〈重要〉。悪用の成立には2つの実装上の選択が重なる必要があった——「上限を検査しない加算」と「仕様違反で接続を残す処理」である。どちらか片方だけでは、攻撃者は毎回やり直しになる。だから原因を「整数アンダーフロー」の一語で済ませると、本件から学べるものが減る—— 防御的な実装では、不変条件（接続枠は MAX を超えない）を1か所で強制し、違反したら接続を落とす。

「約128GB送る必要がある」ことが、この脆弱性の実務上の中心である評価・解釈

CVSS 4.0 の 9.2（Critical）という数字だけでは、どの構成が実際に危ないかが分からない（本記録の評価）。Rapid7 は自ら制約を明示している（出典1）—— 本記録はこれを本件の最も実務的な情報と見る〈重要〉。

制約 内容
データ量 約128GBの HTTP/2 データの送信が必要
10Gbit/s 約2分
1Gbit/s 約17分
下限 nginx の既定の接続寿命は1時間。おおよそ 300Mbit/s より遅い回線では成功しない

Rapid7 の実証そのものは、2分30秒で完了している（動画は8倍速。出典1）。

CVSS のベクタがこれと整合している（本記録の整理）〈重要〉。CVSS:4.0/AV:N/**AC:H**/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N——認証不要（PR:N）、利用者の操作不要（UI:N）、ネットワーク経由（AV:N）で3要素すべてに High の影響がありながら、攻撃の複雑度が High に置かれている（出典5）。

ここから読み取るべきこと（本記録の評価）。

第一に、「回線が遅いから安全」ではない。 300Mbit/s というのは攻撃者側の回線速度である。守る側の回線ではない。そして攻撃者がクラウドから攻撃すれば、10Gbit/s は容易に出る。

第二に、接続寿命は設定で変えられる。 1時間という下限は nginx の既定値に基づく—— 長く設定している構成では、必要な回線速度の下限が下がる〈重要〉。逆に、短く設定すれば緩和になる（本記録の評価。ただしこれは各社が推奨策として挙げたものではない）。

第三に、CDN・WAF の背後は相対的に安全だが、前提がある。 Rapid7 と Wiz はいずれもプロキシ下での成立しにくさに触れている（出典1・4）。ただし守られるのは「終端している経路」だけである（本記録の評価）——オリジンへの直接アクセスが可能な構成、内部から HTTP/2 で到達できる構成では効かない。そして前段の製品自体が nginx を内包している場合もある。

第四に、サービス妨害にはこれらの制約が同じ形で効くとは限らない（本記録の読み）〈未確定3〉。F5 の説明は「クラッシュ、メモリ破壊、またはコード実行」であり（出典5）、ワーカーのクラッシュに128GBが必要かどうかは明示されていない。本記録はこれを未確定として記録する—— RCE の条件で DoS のリスクを測るのは危険である。

「ASLR が有効だから安全」とは読めない評価・解釈

F5 の説明には条件が付いている（出典5。本記録が訳した）。

「加えて、アドレス空間配置のランダム化（ASLR）が無効化されているシステム、または攻撃者が ASLR を回避できる場合には、攻撃者はコードを実行できる」

Sophos X-Ops も「F5 によれば、コード実行には ASLR が無効化されているか回避されることが必要だ」と伝えている（出典3）。

この条件を「ASLR が有効なら安全」と読むのは誤りである（本記録の整理）〈重要〉——理由は2つある。

第一に、Wiz が公式ビルドで ASLR 回避を伴う RCE を確認している。 Wiz の記述はこうである（出典4。本記録が訳した）—— 「公式の NGINX 1.31.7 および 1.31.8 のビルドで、ASLR のバイパスを伴う RCE を確認した」、「ASLR のような一般的な保護は、攻撃者が先にメモリを読めるため、これらの問題を止めない」。

後半が本質である（本記録の評価）。本脆弱性は境界外の読み取りと書き込みの両方を引き起こす（出典1）。読み取りができるということは、アドレスを漏らせるということである。 ASLR はアドレスを推測させないための防御であり、アドレスを読める攻撃者には効かない。

第二に、Rapid7 は Docker イメージで実証している。 Rapid7 の実証対象は、nginx 1.31.8 の公式 linux/amd64 Docker イメージである（出典1）——特別に ASLR を無効化した環境ではない。

ただし、悪用は容易ではない（出典4）。Wiz は「悪用は難しく、メモリの開示・ヒープの整地・版と構成に固有の作業を要する」としており、実証コードは公開しないと決めている（出典4）。

ここで本記録が重要と見る対比がある〈重要〉。同じ2026年11月18日の収集分には、GeoVision の WebCam Server の脆弱性（INC-2026-1172）がある。そちらでは Cisco Talos が「このウェブサーバは ASLR 無しでコンパイルされているため、悪用がはるかに容易かつ現実的になる」と記している。

nginx では「ASLR を回避できる場合」という条件が付くが、GeoVision ではその条件がそもそも無い。条件が1つ減っているぶん、悪用のしやすさが違う——そして実際に、GeoVision のほうは実際の侵害が観測されている。本件は、まだ実証の段階である。

HTTP/2 を無効化しても、同じ更新で直る9件は塞がらない対策・注意喚起

CERT-FR は暫定の回避策として HTTP/2 の無効化を推奨し、設定を具体的に示している（出典2）。

  • 1.25.0 以前: listen 443 ssl; http2 off;
  • 1.25.1 以降: listen 443 ssl;（listen から http2 を外す）
  • 確認: nginx -t とリロードの後、openssl s_client -connect HOST:443 -servername HOST -alpn h2 の出力に ALPN protocol: h2 が現れないことを確かめる

確認コマンドが警報に載っていること自体が示唆的である（本記録の読み）〈重要〉——設定の書き方が版によって違うため、複数の server ブロック・複数の listen がある構成では一部だけ残ることが起きやすい。

しかし本記録が強調したいのは、無効化の射程である（本記録の評価）〈重要〉。

nginx.org のセキュリティアドバイザリ一覧を数えると、1.31.9／1.30.7 で修正された脆弱性は10件ある（出典6。本記録が数えた）。

そして更新には、本件固有の落とし穴がある〈重要〉。Xint の注記である（出典3。本記録が訳した）——

「nginx -s reload では新しいバイナリが読み込まれないため、更新後に NGINX を再起動するか、そのバイナリをアップグレードする必要がある」

これは「パッケージを更新した」と「新しいコードが動いている」がずれる形である（本記録の評価）。設定変更の反映に nginx -s reload を使う運用は一般的であり、そのまま脆弱性の修正にも使ってしまうと、パッチ適用の記録上は対応済みでも、古いバイナリのプロセスが動き続ける。

本記録が示す対応の順序はこうである（本記録の評価）。

  1. 更新して、再起動またはバイナリのアップグレードを行う。 ALPN の確認とは別に、動いているプロセスの版を確かめる。
  2. 直ちに更新できない範囲で HTTP/2 を無効化し、ALPN で h2 が返らないことを確認する。 これを①の代わりにしない。
  3. nginx を内包する製品・アプライアンス・コンテナイメージを棚卸しし、各提供元の対応を確認する。

「nginx ワーカーの権限」で止まるのか、ホストの root まで行くのか評価・解釈

影響の見積もりは、どこまで到達するかで変わる（本記録の整理）。

F5 の評価は、nginx ワーカープロセスの権限でのコード実行までである（出典1・5）。CVSS 4.0 のベクタも SC:N/SI:N/SA:N—— 後続システムへの影響なしとしている（出典5）。

Xint の主張は、これより先へ行く（出典3。本記録が訳した）〈重要〉——

「各脆弱性は、別個の Linux カーネルの SCTP の脆弱性と連鎖させることで、ホスト上で root 権限を取得できる。NGINX が Docker コンテナで動いている場合も含む」

そして命名が「NGINX2Root」である—— nginx2root.com の見出しは「nginx の訪問者から、サーバホストの root へ」と説明されている（出典3）。

この主張が正しければ、2つの前提が崩れる（本記録の評価）〈重要〉。

第一に、「ワーカー権限だから影響は限定的」が崩れる。 nginx のワーカーは通常 nginx や www-data のような低い権限で動く——だから「コード実行されてもホストは取られない」と見積もりがちである。

第二に、「コンテナに入れてあるから隔離されている」が崩れる。 Xint は Docker コンテナの場合も含むと明記している。カーネルはホストと共有されているため、カーネルの脆弱性はコンテナの境界を越える——これはコンテナの設計上の性質であり、本件に固有の弱点ではない。

ただし、本記録はこの主張を検証できていない（本記録の明示）〈齟齬2〉〈重要〉。

  • nginx2root.com は概要のみである。 5件の CVE 番号、Xint と Wiz への帰属、SCTP 脆弱性との連鎖という記述は確認できたが、CVE ごとの詳細・影響版・緩和策・開示日は Xint のブログにあるとされ、そちらを本記録は取得できていない。
  • 連鎖に使われる SCTP の脆弱性が特定できていない〈未確定4〉。CVE 番号も、影響するカーネルの版も分からない。したがって本記録は「Linux を更新せよ」以上の具体を書けない。

本節の確度を presumed とした理由はここにある。

それでも、対応の判断には影響する（本記録の評価）〈重要〉。「ワーカー権限で止まる」前提で優先度を下げるのは、この主張が否定されるまでは危うい。本記録が示せる具体は2つである—— Linux カーネルを更新すること、そして SCTP が不要ならモジュールを読み込まないことである。 SCTP は多くのサーバで使われていない。

nginx を内包する製品の棚卸しが、この種の脆弱性で毎回の課題になる再発防止

本記録が付記したい論点がある（本記録の評価）〈重要〉。

Sophos X-Ops は自社の記事の末尾でこう述べている（出典3。本記録が訳した）—— 「自社の製品またはサービスが影響を受けるかを判断するため、内部調査も進行中である」。

セキュリティ製品のベンダー自身が、自社製品に nginx が入っているかを調べている。これが本件（および nginx の脆弱性全般）の実務上の難しさを示している（本記録の評価）。

nginx は、次のような形で組織の中に入っている（本記録の整理）。

  • リバースプロキシ・ロードバランサとして明示的に導入したもの（これは棚卸しされている）
  • アプライアンス・仮想アプライアンスの内部（WAF・API ゲートウェイ・ADC・VPN 製品）
  • コンテナイメージのベースレイヤ（nginx:alpine を FROM にしているアプリ、Kubernetes の Ingress コントローラ）
  • SaaS・PaaS の基盤（提供元の責任範囲）
  • 開発用に起動されたまま残っているもの

1つめ以外は、脆弱性管理の一覧に載っていないことが多い（本記録の評価）〈重要〉。そして Xint は「nginx が Docker コンテナで動いている場合も含めてホストの root を取得できる」としている（出典3）—— コンテナに入っていることは緩和にならない。

本記録が勧める手順はこうである（本記録の評価。これは各社の推奨策ではない）。

  1. 外から見える範囲を先に確定する。公開エンドポイントについて ALPN で h2 が返るかを一覧化する（CERT-FR の確認コマンドがそのまま使える。出典2）。これは「自組織が攻撃者に見えている姿」である。
  2. コンテナイメージを走査する。イメージの一覧に対して nginx の版を抽出する（ベースイメージの更新が必要なものを洗い出す）。
  3. アプライアンス・SaaS は提供元に問い合わせる。問い合わせの記録を残し、回答が来るまでのあいだ前段での緩和（HTTP/2 の終端）を検討する。
  4. 動いているプロセスの版を確かめる。 nginx -s reload では新しいバイナリが読み込まれないため（出典3）、パッケージの版ではなくプロセスの版を見る。

本節の確度を presumed としたのは、上記が本記録の作成者による整理であり、各社の推奨策に含まれていないためである（本記録の明示）〈齟齬6〉。

    **本件には2つの落とし穴が重なっている**〈重要〉—— **①Xint は「`nginx -s reload` では新しいバイナリが 読み込まれないため、更新後に再起動するか バイナリをアップグレードする必要がある」と注記している**（出典3）。 **②HTTP/2 の無効化で塞がるのは2件だけで、 同じ更新で直る他の8件（うち major が2件）は塞がらない**（出典6）。 **本記録の評価では、どちらも「対応済み」と記録されたまま 脆弱なまま残る形である。**
    取るべき行動 脆弱性管理の台帳に、「緩和策の適用」と「修正版の稼働」を 別の列として持つ。 修正版の稼働は、パッケージの版ではなく 動いているプロセスの版で確認する運用にする。 緩和策で閉じたチケットには、本来の修正の期限を別に設定する。 本件については、HTTP/2 の無効化で閉じたものを洗い出し、 更新の予定を入れる。
  • nginx のような広く内包されるソフトウェアについて、「自組織のどこに入っているか」を平常時に把握する
    **セキュリティ製品のベンダーである Sophos 自身が、 自社製品・サービスが影響を受けるかの内部調査を進めているとしている** （出典3）〈重要〉—— **本記録の評価では、これが本件の実務上の難しさを示している。** **nginx は明示的に導入したもの以外に、 アプライアンスの内部・コンテナイメージのベースレイヤ・ SaaS の基盤として組織の中に入っている。** **Xint は「Docker コンテナで動いている場合も含めて ホストの root を取得できる」としており、 コンテナ化は緩和にならない**（出典3）。
    取るべき行動 広く内包されるソフトウェア（nginx・OpenSSL・glibc・ Log4j のような基盤部品）について、 自組織のどこに入っているかを平常時に把握する仕組みを作る。 具体的には、①コンテナイメージの一覧に対する構成要素の走査、 ②アプライアンス・SaaS の提供元への問い合わせ窓口の事前把握、 ③公開エンドポイントの外部からの観測（本件では ALPN で h2 が 返るかの一覧化）の3つを用意する。 緊急時に「どこに入っているか」から調べ始める状態を避ける。
  • 外部の実証が「条件つき」のとき、条件が自組織に当てはまるかを判定する責任を明確にする
    **Rapid7 は悪用の制約を自ら明示している**（出典1）〈重要〉—— **約128GBの送信が必要、おおよそ 300Mbit/s より遅い回線では成功しない、 プロキシ下では成立しにくい、特定の glibc memcpy 実装に依拠する。** **本記録の評価では、これは「安全」の根拠ではなく 「どの構成が危ないか」を判定する材料である。** **一方、F5 の「ASLR が無効化または回避できる場合」という条件は、 Wiz が公式ビルドで ASLR 回避を伴う RCE を確認したことで 実質的に満たされている**（出典3・4）—— **条件つきの記述を「条件が揃わないから安全」と読むのは危険である。**
    取るべき行動 脆弱性の初動の判断に、「公表された悪用条件が自組織の構成に 当てはまるか」を評価する欄を設け、評価の責任者を決める。 評価の結果は根拠つきで記録する （例: 「CDN が HTTP/2 を終端しているため該当しない」と判断した場合、 オリジンへの直接到達が不可能であることの確認結果を添える）。 条件が「ASLR の回避」のように攻撃者の能力に依存するものは、 満たされる前提で扱う方針を明記する。
セキュリティ技術者への示唆
  • nginx を更新したら、再起動またはバイナリのアップグレードを行い、プロセスの版を確認する
    **Xint は「`nginx -s reload` では新しいバイナリが 読み込まれないため、更新後に NGINX を再起動するか、 そのバイナリをアップグレードする必要がある」と注記している** （出典3。本記録が訳した）〈重要〉—— **設定変更の反映に `nginx -s reload` を使う運用は一般的であり、 そのまま脆弱性の修正にも使うと、 パッチ適用の記録上は対応済みでも古いバイナリのプロセスが動き続ける** （本記録の評価）。
    取るべき行動 nginx Open Source を 1.31.9（mainline）または 1.30.7（stable）へ、 NGINX Plus を該当の修正版へ更新する。 更新後に nginx を再起動するか、無停止で切り替えるなら nginx のバイナリアップグレード手順（USR2／WINCH／QUIT シグナル）を使う。 完了の確認は、パッケージの版ではなく動いているプロセスの版で行う。 構成管理で配布している場合は、再起動の手順を同じ変更に含める。
  • 更新が直ちにできない範囲では HTTP/2 を無効化し、ALPN で h2 が返らないことを確認する
    **CERT-FR は暫定の回避策として HTTP/2 の無効化を推奨し、 設定と確認コマンドを示している**（出典2）〈重要〉—— **設定の書き方が版によって違う（1.25.0 以前は `http2 off;`、 1.25.1 以降は `listen` から `http2` を外す）ため、 複数の server ブロック・複数の listen がある構成では 一部だけ残ることが起きやすい**（本記録の評価）。 **確認コマンドが警報に載っていること自体が、この難しさを示している。**
    取るべき行動 影響する listen ディレクティブで HTTP/2 を無効化する （1.25.1 以降は `listen 443 ssl;`、1.25.0 以前は `listen 443 ssl; http2 off;`）。 `nginx -t` で構文を確認してリロードした後、 `openssl s_client -connect HOST:443 -servername HOST -alpn h2` の 出力に `ALPN protocol: h2` が現れないことを確かめる。 公開しているホスト名ごとに確認する（SNI で server ブロックが分かれるため）。 確認の結果を記録に残す。
  • HTTP/2 の無効化を「対応完了」として記録しない
    **nginx.org の一覧では、1.31.9／1.30.7 で修正された脆弱性は 10件ある**（出典6。本記録が数えた）〈重要〉—— **HTTP/2 の無効化で塞がるのは CVE-2026-123007 と CVE-2026-123633 の2件だけである。** **残る8件のうち、CVE-2026-118899（TLS 1.3 でのボディ読み取り時の 無限ループ）と CVE-2026-113425（メールプロキシの use-after-free）は nginx.org の分類で major である**（出典6）。 **メールプロキシ・HTTP/3・resolver・alias/try_files・stream の 脆弱性は、HTTP/2 を切っても残る。**
    取るべき行動 自組織の nginx の構成について、HTTP/2 以外の機能の使用状況を確認する （mail プロキシ、HTTP/3、SSI・mirror ディレクティブと 変数を含むプロキシ先のサーバ名、alias と try_files の併用、 stream モジュールの ssl_preread・クライアント証明書検証、 PROXY protocol v2）。 使用しているものがあれば、該当する CVE を個別に確認する。 F5 の個別の回避策（SSI/mirror と変数を含むサーバ名を避ける、 メールプロキシの待ち受けを信頼できるネットワークに限定する）も 該当すれば適用する。
  • 1接続あたりの受信データ量と接続の寿命を記録し、異常な量を警報にする
    **悪用には約128GBの HTTP/2 データの送信が必要である** （出典1）〈重要〉—— **したがって「1接続で異常に大量のデータを受け取っている」という形が 必ず現れる。** **Wiz も検知の手がかりに 「大量のデータを送る長寿命の HTTP/2 接続 （WINDOW_UPDATE フレームの大量送出の表れでありうる）」を挙げている** （出典4）。 **一方、アクセスログは「要求と応答」を記録するが、 1接続が何バイト受け取ったかは通常記録されない**（本記録の評価）。 **検知の窓は短い——10Gbit/s の回線なら約2分で完了する**（出典1）。
    取るべき行動 nginx のログ形式に接続単位の指標を追加する （`$connection`・`$connection_requests`・`$bytes_sent` を使い、 接続ごとの集計をログ処理側で行う）。 単一接続で数GBを超える応答データを送出したものを警報にする。 併せて HTTP/2 の接続寿命（`keepalive_time`・`keepalive_timeout`）を 既定の1時間より短く設定し、必要な送信時間を確保させない。 設定変更が長時間接続を使う業務（SSE・gRPC ストリーミング）に 影響しないか先に確認する。
  • nginx ワーカーの予期しない終了を件数の推移として監視する
    **F5 の説明では、ヒープバッファオーバーフローは 「通常は NGINX ワーカーのセグメンテーション違反を伴う」** （出典5。本記録が訳した）〈重要〉—— **つまり悪用の試行は、成功しなくても痕跡を残す**（本記録の読み）。 **Wiz も検知の手がかりの第一にワーカーの予期しないクラッシュを 挙げているが、「一般的な警戒の徴候であり、 確認された痕跡ではない」とも注記している**（出典4）。 **本記録の評価では、単発のクラッシュでは判断できないため、 件数の推移を平常時と比べる形にする必要がある。**
    取るべき行動 nginx のエラーログから `worker process ... exited on signal` の件数を日次で集計し、平常時の基準線を取る。 基準線からの上振れを警報にする。 併せて、nginx のプロセスから起動された子プロセス （シェル・コマンド）を EDR で警報にする ——ウェブサーバが子プロセスを起動する形は正常な運用ではまず現れない。
  • 不変条件を「検査する場所」を1か所に集め、違反したら接続を落とす実装にする
    **本件の悪用には2つの実装上の選択が重なる必要があった** （本記録の整理）〈重要〉—— **①接続枠を戻す加算（`h2c->send_window += window;`）が 上限（2^31-1）を超えないかを検査していない（出典1）。 ②RFC 9113 が接続を FLOW_CONTROL_ERROR で終わらせることを求める条件で、 nginx はストリームだけを終わらせて接続を使える状態に残す（出典1）。** **どちらか片方だけでは、攻撃者は毎回やり直しになる**（本記録の評価）。
    取るべき行動 自分が書くプロトコル実装・状態機械について、 不変条件（「この値は常にこの範囲にある」）を列挙し、 検査を1か所に集める（値を変更する全経路がそこを通るようにする）。 違反を検知したときの動作を「その要求だけ失敗」ではなく 「接続を落とす」側に寄せる ——壊れた状態の接続を使い続けさせないことが要点である。 符号なし整数で上限のある値を持つ場合は、 減算と加算の両方に検査を置く。
法務・コンプライアンスへの示唆
  • 「公開された実証コードが存在する」段階での対応の遅れを、説明できる形で記録する
    **CERT-FR は開示の当日に「公開された実証コードの存在を 把握している」と明記した**（出典2）〈重要〉—— **本記録の評価では、これは「悪用が始まる前に対応する機会が あった」ことの公的な記録になる。** **仮に後に侵害が起きた場合、 「いつ知って、いつ何をしたか」の記録が 過失の評価に直接関わる**（本記録の整理）。 **一方、本件は約128GBの送信が必要などの条件があり、 自組織が該当しないと判断した場合はその根拠が要る**（出典1）。
