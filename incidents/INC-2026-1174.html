製品に埋め込まれた共通の暗号鍵が、認証そのものを迂回させた原因・手口

技術的な要点を、一次資料の記述に沿って置く（出典1・2）。

① 鍵が全導入先で共通である。 CVE-2026-126551 の CWE は CWE-321（ハードコードされた暗号鍵の使用）で、NVD の記述は 「Session Credential Falsification through Forging」—— セッション資格情報を偽造できる、である（出典2）。 鍵が製品に埋め込まれている以上、ある1つの導入先から鍵を取り出せば、 同じ版を使う全ての導入先に対して同じ偽造が成立する。 利用者側でパスワードを強くしても、証明書を入れ替えても、 この性質は変わらない（本記録の評価）。

② 到達先が「管理対象ホスト」である。 アドバイザリは影響を 「管理対象の System Agent ホスト上での未認証リモートコード実行」と 書いている（出典1。原文英語）。 WCC サーバ1台の侵害ではなく、その WCC が面倒を見ている サーバ群での実行である。本記録の評価では、ここが本件の重さの中心で、 CVSS の 9.3 という数字は「WCC が何台を管理しているか」を含んでいない。

③ 残り2件は旧版のエンドポイントである。 CVE-2026-126552（認証なしの設定エンドポイント）と CVE-2026-126553（デシリアライズ）は 24.0.01 までの版に該当し、 24.1.00 のプラットフォーム移行でエンドポイント自体が取り除かれた （出典1）。Broadcom はこれを「セキュリティ修正ではない」と明記している。

深刻な3件はすべて WCC にあり、Web 画面の到達性が実務上の分かれ目になる評価・解釈

11件の内訳を見ると、CVSS 9.3 の3件・8.7 の1件・8.6 の1件・7.8 の1件は いずれも WCC（Web 管理画面）側である（出典1）。 AE ネイティブクライアント側は 5.1 と 4.8 の2件で、 しかもどちらもローカルの利用者を前提にしている。

本記録の評価では、ここから実務上の優先順位が決まる。 まず WCC がどこから到達できるかを実測し、次に版を上げる、である。 理由は2つある。①9.3 の3件はいずれも「認証を持たない遠隔の攻撃者」を 前提にしており、到達性を切れば前提が崩れる。 ②ジョブ管理基盤の更新は停止窓の調整に時間がかかるため、 更新だけを待つと無防備な期間が数週間から数か月に伸びる。

ただし到達性の制限は解決ではない。ハードコードされた鍵は 内部ネットワークからの攻撃に対しては引き続き有効であり、 運用委託先の端末や、同じセグメントに置かれた別システムの侵害が そのまま入口になる（本記録の評価）。

修正版は 24.2.01 だが、11件のうち1件には修正版が存在しない対策・注意喚起

Broadcom が示す対応は、整理すると3層になっている（出典1）。

① 24.2.01 以降へ更新する。 WCC 側の CVE はこれで解消する。 アドバイザリは「WCC 24.2.01 以降はここに挙げた WCC の CVE の いずれにも該当しない」と述べている。

② 24.1.00 でも2件は外れる。 CVE-2026-126552 と 126553 は 24.1.00 以降では該当しない。ただしこれは脆弱なエンドポイントが プラットフォーム移行で消えた結果で、セキュリティ修正ではない（出典1）。 最悪の1件（CVE-2026-126551、9.3）は 24.2.00 まで影響するため、 24.1.00 で止めると残る。

③ CVE-2026-126556 には修正版が無い。 AE ネイティブクライアントの -pw／-pwx オプションは、与えたパスワードを同一ホストの他の利用者に 見せてしまう。アドバイザリは「このオプションを取り除いた版は無い。 24.2.01 で非推奨にしたが削除時期は未定（TBD）」とし、 24.2.01 で導入された環境変数 ASPASSWORD への移行と、 共有ホストでの procfs hidepid の設定を示している（出典1）。 本記録の評価では、これは「更新すれば終わり」にならない1件で、 ジョブ定義とシェルスクリプトの棚卸しが必要になる。

1人の研究者の調査で11件が同時に出たことを、どう読むか評価・解釈

アドバイザリの謝辞は1行だけで、「All findings - David Carliez (DC CyberSecurity)」である（出典1。原文英語。本記録が訳した）。 11件すべてが1人の調査から出ている。

本記録の評価では、これは2つのことを示す。 ①この製品の攻撃面が、これまで外部から十分に見られていなかった。 見られていれば、ハードコードされた鍵のような基礎的な問題が 2026年まで残らない。 ②したがって、11件で打ち止めになる見込みは薄い。 同じ系列の製品（AE 側、エージェント側）に対する調査が続けば、 追加の開示がありうる（これは本記録の推定であり、 Broadcom も発見者もそのような予告はしていない）。

運用上の含意は、「今回の11件を塞ぐ」だけでなく、 この製品の版追従を定常の運用に組み込むことである。 ジョブ管理基盤は一度構築すると数年触らないことが多く、 12.1 系が 2026年時点でまだ影響範囲に入っていること自体が、 その実情を示している（出典1の影響版の下限が 12.1 であること）。

悪用の有無について、ベンダーは何も述べていない未確定事項

アドバイザリには、実際の攻撃による悪用に関する記述が無い（出典1の確認）。 NVD の3件も、本記録の確認時点では状態が「Received」で、 悪用に関する情報は付いていない（出典2）。

本記録はこれを「悪用されていない」とは読まない（本記録の明示）。 ベンダーのアドバイザリは、悪用を把握していれば書くことが多いが、 書いていないことは「把握していない」までしか意味しない。

防御側の判断としては、CVSS の 9.3 と「未認証」「管理対象ホストでの実行」 という性質だけで、悪用の確認を待たずに動かすのが妥当である （本記録の評価）。本件は認証を要しないため、 悪用が始まれば観測から対応までの余裕が小さい。

    **ジョブ管理製品は正規の機能としてシェルやスクリプトを起動するため、 プロセス起動そのものでは攻撃と運用を区別できない** （本記録の評価）〈重要〉—— **区別できるのは「登録されていないジョブが走ったか」である。** **CVE-2026-126551 の到達先が管理対象ホストであることから、 痕跡はそこに出る（出典1）。**
    取るべき行動 登録済みジョブ定義の一覧を日次で取得し、 実行履歴と突き合わせて定義に無い起動を抽出する。 同一コマンドが短時間に多数のホストで走った場合も抽出する （運用の一斉実行は許可リストで除外する）。
  • アプリケーションログに資格情報とセッション識別子が 書かれていないかを、実際に grep して確かめる
    **CVE-2026-126549 は失敗したログインの資格情報を復元可能な形で、 CVE-2026-126550 は有効なセッション識別子をログに書き出す** （出典1）〈重要〉—— **本記録の評価では、これらは更新後も 「過去に出力されたログ」として残り続ける。** **ログ閲覧権限が運用委託先まで広く配られている現場では、 更新だけでは露出が止まらない。**
    取るべき行動 WCC のアプリケーションログを対象に、 資格情報とセッション識別子の出力実績を確認する。 見つかった場合は該当セッションを無効化し、 ログの閲覧権限と保管期間を見直す。 削除より先に権限の縮小を行う（障害調査の材料を失わないため）。
  • AE ネイティブクライアントの `-pw`／`-pwx` の使用箇所を棚卸しし、 環境変数へ移す
    **CVE-2026-126556 には修正版が存在しない** （出典1。オプションは 24.2.01 で非推奨、削除時期は未定）〈重要〉—— **同一ホストの他の利用者にパスワードが見えるため、 共有ホスト・踏み台での運用が危ない。** **本記録の評価では、これは11件のうち最も長く残る1件である。**
    取るべき行動 ジョブ定義・シェルスクリプト・運用手順書を対象に `-pw` と `-pwx` を検索し、該当箇所を 24.2.01 で導入された 環境変数 ASPASSWORD に置き換える。 共有ホストでは procfs の hidepid を設定する。
法務・コンプライアンスへの示唆
  • 修正版が存在しない脆弱性を抱えたまま運用する判断を、 説明できる形で記録する
    **CVE-2026-126556 はベンダーが「修正版は無い」と明言している** （出典1）〈重要〉—— **本記録の評価では、この状態で運用を続けること自体は 不合理ではないが、事故が起きたときに 「認識していたか」「何をしたか」を問われる。**
    取るべき行動 修正版が存在しない脆弱性について、 「認識日時」「影響範囲の判定根拠」「採った緩和策と日時」 「残存リスクを受け入れた責任者」の4点を記録する様式を用意する。 委託先が運用する基盤についても、同じ記録を求める契約条項を確認する。
