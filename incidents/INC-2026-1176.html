攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**推定中国系の APT が、正規のプログラムに悪性 DLL を読み込ませて メモリ上でフレームワークを動かし、 ファイル共有経由で横に広がり、 相互 TLS で保護した通信で操作する**（出典1）〈重要〉—— **初報の公表後、暗号と通信方式を作り替えたが、 上記の方法そのものは変えなかった。** **新たに加わったのは、Active Directory の探索、 powershell.exe を起動しないメモリ上の PowerShell、 そして外へ呼びかけずに TCP 5060 で待ち受ける受動型である。** **初期侵入の経路は公表されていない。**

公表の12日後に作り替えが始まり、2週間ごとに暗号が入れ替わった原因・手口

続報が示した日付を、一次資料に沿って並べる（出典1）。

2025年9月17日 初報の公表。 9月29日（12日後）構成情報の保護方式を変えた EggStremeFuel のビルドが現れる。暗号はファイル名を鍵にした RC4 から、 難読化して埋め込んだ鍵による AES-256-CBC へ。 10月13日（さらに14日後）新しい形式のローダー。 文字列の保護は XOR から RC5-32 の CBC へ。翌日には実環境で観測。 10月28日 独自の暗号「variant A」。 3つのビルドが約95分のあいだに作られている。 12月中旬 「variant B」に置き換わる （ビルドは2025年12月16日と2026年5月14日）。

Bitdefender はこの近さを、自社の報告が引き金になった可能性が高いことの 根拠として挙げている（出典1）。 同時に、これらの差し替えは実際の保護をほとんど増していない一方、 古い暗号に合わせて作られた検知は無効にできた、とも評価している。

本記録の評価では、ここから読むべきことは 「相手の対応速度」である。公表から12日で最初の変更が出ている。 自組織が脅威情報を受け取ってから検知に反映するまでの時間が これより長ければ、反映した時点で対象はすでに別のものになっている。

変わらなかったのは4つの振る舞いで、検知の寿命はそこにしかない評価・解釈

続報の本文は、作り替えを通じて変わらなかった振る舞いを4つ挙げている （出典1・4）。 ①システムのライブラリ名を装った DLL サイドローディング、 ②ファイル共有経由の横展開、 ③メモリ上での実行、 ④相互 TLS（双方が証明書を提示する）。 続報の「Constants」の節では、鍵スケジュールを伴う CBC と PKCS#7 の除去、および EggStremeFuel の C2 における 実行ごとの RC4 鍵を加えて6つに拡張している（出典1）。

Bitdefender の総括は「道具の水準では支出したが、方法は保ったままだった」 である（出典3。原文英語。本記録が訳した）。

本記録の評価では、これは検知の設計に直接効く観察である。 自組織の検知ルールを「何に依存しているか」で分類すると、 ハッシュ・ドメイン・文字列に依存した分は12日から2週間で失効し、 振る舞いに依存した分は1年以上生き残ったことになる。 本件は、その比率を測るための実例として使える。

ただし、振る舞いの検知には誤検知の負担がある。 正規のアプリケーションも自身のディレクトリから DLL を読み、 管理者も日常的にドメイン情報を列挙する。 Bitdefender の推奨が「ライブラリ名と読み込み位置の組み合わせ」 という具体の形で書かれているのは、そこを絞るためである（出典1）。

外へ呼びかけない受動型が加わり、出口側の監視では映らなくなった原因・手口

続報が示した最も実務的な変化は、受動型のバックドアである（出典1）。

動き方。 2つのビルドは、C2 へ呼びかけない。 TCP 5060 で待ち受け、運用者からの接続を待つ。 接続時の手順には RC4 を使う。 待ち受けのために、ホストのファイアウォールへ受信許可を追加し、 その規則名は「Core Networking - SIP」である。

意味。 出口側の通信を見る監視——プロキシのログ、 DNS の問い合わせ、既知の C2 ドメインとの照合——では、 この型は一切映らない。呼びかけが無いからである。

代わりに残る手がかり。 本記録の評価では2つある。 ①ホストのファイアウォール規則の変更（受信許可の追加）。 ②ワークステーションでの新しい受信待ち受けの出現。 どちらも Bitdefender が推奨に挙げている（出典1）。 業務端末が SIP の既定ポートを待ち受ける構成は通常ないため、 誤検知の少ない検知になる。

あわせて、EggStremeAgent は gRPC をやめて 相互 TLS 付きの生 TCP に移り、AES-256-CBC の層を重ねた（出典1）。 相互 TLS は、クライアント側も有効な証明書を提示しないと つながらないことを意味する。防御側から見れば、 C2 サーバに接続して応答を確かめる調査が成立しにくくなる （本記録の評価）。

標的は高確度でフィリピン政府機関、台湾は「手がかり」にとどまる帰属

確度の表現を、一次資料のまま記録する（出典1）。

高確度（high confidence）—— この作戦が複数のフィリピン政府機関を標的にしたこと。 初報（2025年9月）の対象はフィリピンの軍関連企業であり（出典2）、 続報では政府機関へと対象の記述が変わっている。

帰属についての新たな主張は無い。 続報は「推定中国系の APT」という初報の位置づけを変えず、 いかなる政府の関与についての主張でもないと述べている（出典1）。 既知の名前付き集団への結びつけも行われていない。

    **本件では、公表から12日後に最初の作り替えビルドが現れ、 その後も2週間ごとに暗号が差し替わっている**（出典1）〈重要〉—— **本記録の評価では、脅威情報の取り込みに1か月かかる組織では、 反映した時点で指標はすでに失効している。** **これは体制の問題であり、担当者の努力では縮まらない。**
    取るべき行動 直近に取り込んだ脅威情報について、 「公表日」「自組織が受領した日」「検知に反映した日」の3点を記録し、 受領から反映までの日数の中央値を出す。 2週間を超えている場合は、指標に依存した検知の比率を下げる方針に切り替える。
  • 検知の投資を、指標（ハッシュ・ドメイン）から振る舞いへ寄せる判断を 明示的に行う
    **本件では、暗号と形式は1年のあいだに4回以上入れ替わったが、 DLL サイドローディング・共有経由の横展開・メモリ上での実行・ 相互 TLS の4つは変わらなかった**（出典1・4）〈重要〉—— **Bitdefender の総括は「道具の水準では支出したが、方法は保った」である （出典3。原文英語。本記録が訳した）。** **本記録の評価では、指標に依存した検知は本件に対して 2週間ごとに無効化されていた。**
    取るべき行動 検知ルールの一覧を「依存している要素」で分類し （ハッシュ／ドメイン／文字列／振る舞い）、 振る舞い側の比率を出す。 低い場合は、次の投資（人・製品・ルール開発）を 振る舞い側に割り当てる判断を記録する。
  • 「外へ呼びかけない侵入」を前提に、監視の構成を点検する
    **本件の受動型は C2 へ呼びかけず、TCP 5060 で待ち受ける** （出典1）〈重要〉—— **本記録の評価では、出口側の通信監視に投資が偏っている組織では、 この型は原理的に映らない。** **必要なのはホスト側（ファイアウォール規則・受信待ち受け）の 記録であり、これは多くの環境で取られていない。**
    取るべき行動 自組織の監視を「出口側」「ホスト側」に分け、 ホストのファイアウォール規則の変更と 受信待ち受けの出現が記録されているかを確認する。 取れていない場合は、その2点に限って収集を始める （全ログの収集を待たない）。
  • 脅威情報の確度の表現を、社内の報告で潰さない
    **Bitdefender はフィリピン政府機関を「高確度」、 台湾を「低〜中確度の手がかり」と書き分け、 後者は確立した事実ではないと明記している**（出典1）〈重要〉—— **本記録の評価では、これを「フィリピンと台湾を狙う」と 1行にまとめると、区別が消える。** **「自組織が標的に含まれるか」の判断は、 この区別が残っているかで質が変わる。**
    取るべき行動 社内の脅威情報の報告様式に、 「評価の確度」と「その評価を出した主体」を記す欄を設ける。 地域・業種の記載を自組織の該当性に読み替えるときは、 確度を添えたまま行う。
セキュリティ技術者への示唆
  • ホストのファイアウォールの受信許可の追加を記録して警報にする
    **受動型は待ち受けのために受信許可を追加し、 その規則名は「Core Networking - SIP」である**（出典1）〈重要〉—— **本記録の評価では、規則名そのものは今後変わりうるが、 「ワークステーションに受信許可が追加される」という事象自体が 通常は起きない。** **名前ではなく事象で検知を作るべきである。**
    取るべき行動 Windows のファイアウォール規則の変更イベントを収集し、 ワークステーションでの受信許可の追加を警報にする。 既存の正規の追加（運用ツールによるもの）を許可リストに入れてから 運用に乗せる。
  • ワークステーションの受信待ち受けポートを定期的に棚卸しする
    **受動型は TCP 5060 で待ち受ける**（出典1）〈重要〉—— **本記録の評価では、業務端末が SIP の既定ポートを 待ち受ける構成は通常なく、誤検知の少ない検知になる。** **出口側の通信監視ではこの型は映らない。**
    取るべき行動 管理下のワークステーションで待ち受けポートの一覧を定期取得し、 前回との差分を出す。 新しい待ち受けが現れた端末を調査対象にする。 最低でも TCP 5060 を明示的な検知対象に加える。
  • PowerShell のスクリプトブロックログを有効にして転送する
    **新しいビルドは powershell.exe を起動せず、 ホストされたランスペースで PowerShell を動かす（コマンド84〜85）** （出典1）〈重要〉—— **本記録の評価では、プロセス起動の監視だけではこの実行は映らない。** **Bitdefender もプロセス内の PowerShell と CLR の読み込みの検知、 およびスクリプトブロックログの有効化を推奨している（出典1）。**
    取るべき行動 スクリプトブロックログを有効にし、 ログを端末外へ転送して保管する。 あわせて、通常 .NET を読み込まないプロセスでの CLR の読み込みを検知対象にする。
  • DLL の読み込みを「ライブラリ名と読み込み位置の組み合わせ」で監視する
    **DLL サイドローディングは、作り替えを通じて変わらなかった 4つの振る舞いの1つである**（出典1・4）〈重要〉—— **装うのはシステムのライブラリ名である。** **本記録の評価では、この観点は相手が再コンパイルしても 無効化されないため、検知の寿命が長い。**
    取るべき行動 システムのライブラリ名と同じ名前の DLL が システムディレクトリ以外から読み込まれた場合に警報を出す。 正規のアプリケーションによる読み込みを許可リストに整理してから 運用に乗せる。
  • ワークステーション間の SMB 接続と、管理外機器の到達範囲を絞る
    **横展開はファイル共有経由である**（出典1）〈重要〉—— **Bitdefender は、ワークステーションに到達できる 管理外の機器の棚卸しと、 SMB 経由で起動されたスクリプトの監視を推奨している（出典1）。** **本記録の評価では、管理外機器が残る環境では そこが監視の空白になり、横展開の起点として使われても記録が残らない。**
    取るべき行動 ワークステーション間の SMB 接続を既定で拒否する （ファイルサーバへの接続のみ許可する）。 あわせて、ワークステーションに到達できる管理外機器を棚卸しし、 管理下に入れるか経路を切る。
