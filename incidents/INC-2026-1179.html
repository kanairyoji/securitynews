INC-2026-1179Cisco Expressway 初の悪用、露企業

2026年11月18日、ロシアのセキュリティ企業 **F6** が、 **Cisco Expressway の重大脆弱性 CVE-2026-76466（CVSS 9.8）の 「最初の悪用事例」を調査した**と公表した。被害に遭ったのは**ロシアの企業**（名称・業種非公表）。 **公開の実証コード（PoC）が現れた直後**に、攻撃者は **Cisco Expressway X15.5.3** の機器を侵害し、**root 権限での遠隔コマンド実行**を得た。 経路は **インターネットから到達できる2台を侵害 → そのうち1台を踏み台に 社内ネットワーク側のクラスタ2ノードへ**という形である。 root を取った後、攻撃者は**自作の Python スクリプト**で ネットワーク走査・SMB 共有の探索・SQL Server と WinRM への接続・ **GitLab リポジトリの調査（認証情報などの持ち出しを目的とする）**の準備を始めた。 **F6 は、スクリプトが攻撃の最中に手直しされており、 ソースコードに残ったコメントと修正の説明から 「AI アシスタントの使用を示している」と判断している。** 検知の手掛かりとして、**Expressway の `erlang.log` に `nodeup,'wombat@127.0.0.1'` が現れること**を挙げた。 **一方、Cisco の勧告（2026年10月21日・版1.0・Final）は 「Cisco PSIRT は本勧告に記載の脆弱性の公表や悪用を把握していない」としたまま 改訂されていない**〈重要〉—— **悪用の第一報が、ベンダーではなく被害国の調査会社から出ている形である**（本記録の整理）。 **CISA の KEV には、2026年11月18日19時17分（UTC）版（1,786件）の時点で未収載だったが、 2026年11月20日、CISA は CVE-2026-76466 を KEV に収載した** （カタログ版 2026.11.20・収載1,790件・是正期限 2026年11月23日・ フォレンジック・トリアージ対象。本記録による確認）。 **カナダのサイバーセキュリティセンターも同日、勧告 AV26-1073 を改訂して収載を伝えた。** **それでも Cisco の勧告は2026年11月22日時点でなお版1.0 のままで、 「PSIRT は悪用を把握していない」という記述が残っている**（本記録による確認）〈重要〉。 **実際にデータが持ち出されたかどうかは公表されていない。**

公開の PoC が出た直後に、ロシアの企業の Cisco Expressway が root を取られ、クラスタ内部へ広げられた。 F6 はこれを CVE-2026-76466 の最初の悪用事例として公表した。

この記録が扱う論点は4つである。

  • 横展開の形。 侵害はインターネットに面した2台から始まり、そのうち1台を経由して社内ネットワーク側のクラスタ2ノードへ届いた。クラスタのメンバである以上、外側の1台が落ちれば内側も同じ信頼圏にある。
  • 攻撃者の道具の作り方。 root 取得後に用意されたのは、ネットワーク走査・SMB 探索・SQL Server と WinRM への接続・GitLab リポジトリからの認証情報の持ち出しを狙う自作の Python スクリプトで、攻撃の最中に手直しされていた。F6 はコード中のコメントと修正の説明から AI アシスタントの使用を読み取っている。
  • ベンダーの勧告が追いついていない。 Cisco の勧告は2026年10月21日の版1.0 のままで、「PSIRT は公表も悪用も把握していない」と書かれている。悪用の第一報は、ベンダーではなく被害国の調査会社から出た。 2026年11月20日に CISA が KEV へ収載し（是正期限 11月23日）、カナダのサイバーセキュリティセンターも同日に勧告を改訂したが、Cisco の勧告は11月22日時点でも版1.0 のままである（本記録の確認）。つまり当局側が先に「悪用されている」と宣言し、ベンダーの記述が後ろに残った形である。
  • 検知の手掛かりが1行ある。 erlang.log のnodeup,'wombat@127.0.0.1' は、既知の悪用機構に対応する Erlang ノード識別子である。F6 はこれを見つけたら他のログと痕跡も確認せよとしている。

本記録が最も重く見たのは「回避策が無い」ことである（本記録の評価）—— Cisco は「この脆弱性に対処する回避策は存在しない（原文英語）」と明記している。F6 が示した TCP/4371〜4372 の制限はベンダーの回避策ではなく調査会社による緩和の提案であり、更新までの時間を買うものにすぎない。

外側の2台から、クラスタの信頼関係をたどって社内の2ノードへ届いた原因・手口出典 [1] [3]

F6 が記した経過は次の順である（出典1）。

  1. インターネットから到達できる Cisco Expressway 2台を侵害した
  2. そのうち1台を経由して、社内ネットワークに置かれたクラスタの別の2ノードへアクセスを得た
  3. root 権限での遠隔コマンド実行を獲得した
  4. インフラ内をさらに進むための道具の準備に着手した

対象の版は X15.5.3 である。Cisco の勧告（出典3）によれば、X15.5.3 以前が影響を受け、修正は X15.5.20 で入っている。

なぜ外側から内側へ届いたのか。 Cisco は影響の条件を「脆弱性のある版を実行し、かつ機器がクラスタとして構成されている場合」と明記している（原文英語。本記録が訳した）。本件の脆弱性は CWE-798（ハードコードされた認証情報）に分類されており、クラスタのデータベースサービスに関わる。クラスタのメンバは互いを同じ信頼圏の相手として扱うため、外側の1台で root を取られた時点で、内側のノードは「正当なクラスタピアからの接続」として扱われる位置にあった（本記録の整理）。

ここに運用上の含意がある（本記録の評価）—— Expressway-E（外側）と Expressway-C（内側）を DMZ と社内に分けて置く構成は設計どおりであり、クラスタの境界はネットワークの境界と一致しない。「外側は落ちても内側は守られる」という前提は、クラスタのメンバである限り成り立たない。

root 取得後に用意されたのは、攻撃の最中に書き換えられていた自作の Python スクリプトだった原因・手口出典 [1]

F6 によれば、root を取った攻撃者は横展開のための道具を用意し始めた。スクリプトの機能は次のとおりである（出典1）。

  • ネットワークの走査
  • 利用可能な SMB 共有の探索
  • SQL Server および WinRM との接続
  • GitLab リポジトリの調査——目的は認証情報その他の機密情報の持ち出しとされている

注目すべきなのは、でき合いの攻撃ツールではなく自作（самописные）であり、しかも攻撃の進行中に手直しされていた点である。F6 は「攻撃者が Python スクリプトを攻撃の過程でそのまま改良していたことを突き止めた」と書いている。

F6 はここから AI アシスタントの関与を読み取っている（原文ロシア語。本記録が訳した）。

「ソースコードには、AI アシスタントの使用を示す特徴的なコメントと修正内容の説明が見つかった。」

本記録はこれを F6 の判断として記録し、事実として断定しない（本記録の明示）—— コメントの実例・どのアシスタントか・判断の基準はいずれも示されていない〈齟齬3〉。コード中のコメントの書きぶりは、AI 以外の要因（テンプレート・チーム内の作法・他人のコードの流用）でも似た形になりうる。

ただし、判断の当否とは別に、観測された事実だけでも含意がある（本記録の評価）—— 攻撃の最中に道具が書き換えられるという形は、静的な IoC（ハッシュ・ファイル名）での検知が効きにくいことを意味する。F6 が挙げた指標のうち、ファイルのパス/mnt/harddisk/i{0-9}{4}[a-zA-Z]?/*.py は正規表現の形になっている。

是正要求は BOD 26-04（リスクに基づく更新の優先順位付け）に沿った対処で、「緩和策が無い場合は製品の使用を中止すること」「資産ごとにインターネット露出を評価すること」が明記されている（原文英語）。同日に収載された4件（Apache Roller・VMware vCenter・SAP NetWeaver・Cisco Expressway）はいずれも期限が11月23日である。

翌 11月20日19時33分 UTC、カナダのサイバーセキュリティセンターが勧告 AV26-1073 を「Update 1」として改訂し、KEV 収載を伝えた（出典6）。

一方、本記録が11月22日に Cisco の勧告を同一 URL で再取得したところ、なお版1.0・Final のままで、「Cisco PSIRT は本勧告に記載の脆弱性について、公表や悪用を把握していない」という記述が残っていた（本記録による確認）〈齟齬1〉。

ここで並び順が逆になっていることに意味がある（本記録の評価）——通常は「ベンダーが悪用を認める → 当局が KEV に載せる」と流れるが、本件は ①被害国の調査会社（11月18日）→ ②米国の当局（11月20日）→ ③カナダの当局（11月20日） と進み、製品の供給元だけが11月22日時点でも動いていない。

読者への含意は2つある（本記録の評価）。

  • ベンダー勧告の「悪用の有無」欄は、優先度付けの最後の砦にならない。本件では、その欄が「把握していない」のままでも、当局は是正期限3日を設定していた。
  • 期限3日に対して、Cisco は回避策を示していない。つまり期限内に取れる手は「X15.5.20 以降への更新」か「インターネットからの切り離し」のどちらかに限られる。TCP/4371〜4372 の制限は F6 による緩和の提案であり、ベンダーの回避策ではない。

なお KEV の期限が及ぶのは米国の連邦民間行政機関（FCEB）であり、日本の組織に法的拘束力は無い。日本の読者にとっての意味は、「当局が3日と見積もる種類の脆弱性である」という緊急度の目安として読むことにある（本記録の整理）。

ただし、CISA が収載の根拠とした悪用が F6 の事案と同一かどうかは分からない—— CISA は観測の中身を示さず、F6 の報告も参照していない。同一なら悪用は1件、別なら複数の組織に及んでいることになるため、本記録は両者を同一の事案として扱わない（本記録の方針）。

検知の手掛かりは erlang.log の1行——ただし IoC の照合先は被害1件分しかない対策・注意喚起出典 [1] [3]

F6 が示した悪用の兆候は次のとおりである（出典1）。

  • erlang.log（Expressway 上の Erlang システムログ）にnodeup,'wombat@127.0.0.1' という記録が現れること —— F6 は「この記録は、識別子が CVE-2026-76466 の既知の悪用機構に対応する Erlang ノードとの接続が確立されたことを示す」としている。これを見つけたら、他のログと痕跡も確認して侵害の事実を裏付ける必要があるとも書いている（つまり単独では確定の根拠にならない）
  • IP アドレス: 66.179.31[.]32、18.130.47[.]116
  • ファイルの配置パス: /mnt/harddisk/i{0-9}{4}[a-zA-Z]?/*.py

F6 が示した推奨事項は次の4点である（出典1）。

  1. CVE-2026-76466 の修正を含む版へ緊急に更新する
  2. 更新が一時的に不可能な場合、ファイアウォールで TCP/4371〜4372 への接続を制限し、信頼できるクラスタノードの IP からのみ許可する
  3. 外部境界の監視を実施する（問題のある資産が悪用される前に把握する。脆弱な資産の侵害評価を加えることで、修正後であっても悪用が間に合っていたかどうかを確認できる）
  4. 24時間体制の監視とインシデント対応を確保する（早期に気づくだけでなく、隔離・範囲の特定・経路の遮断まで速く行う）

2点目は Cisco の回避策ではない（本記録の明示）—— Cisco は「回避策は存在しない」としている。F6 の TCP/4371〜4372 の制限は調査会社による緩和の提案であり、更新までの時間を買うものと理解すべきである。

IoC の限界も明示しておく（本記録の評価）—— IP 2件とパスの正規表現は、被害1件の調査から出た指標である。同じ脆弱性を他の攻撃者が別のインフラから悪用していれば、この照合は空振りする。erlang.log の nodeup のほうが、攻撃者のインフラに依存しないため寿命が長い。

F6 のリリースに書かれていないことを列挙する。

  • データが実際に持ち出されたか。書かれているのは、スクリプトが「認証情報その他の機密情報の持ち出しを目的として GitLab リポジトリを調査する」構成だったことまでである。「持ち出しを目的とする準備が確認された」と「持ち出された」は別である（本記録の区別）

  • PoC の公開日・公開者・公開場所
  • 攻撃者の帰属
  • 「AI アシスタントの使用」の具体的な根拠（コメントの実例・アシスタント名）

本記録はこれらを推測で埋めない。とくに「AI を使った攻撃」という見出しになりやすい事案だが、公表されているのはコード中のコメントと修正の説明から F6 がそう判断したという一段階の推論までである（本記録の評価）。

    取るべき行動 DMZ 側と社内側の機器を同一クラスタに入れている基盤 （Expressway に限らず、プロキシ・メールゲートウェイ・ADFS 等）を棚卸しし、 **「外側が落ちたとき内側はどの信頼関係で守られるか」を1台ずつ書き出す。** 書けない箇所は設計の見直し対象とする
  • 「回避策が無い」脆弱性に対する更新の猶予を、あらかじめ決めておく
    Cisco は「この脆弱性に対処する回避策は存在しない」と明記した。 F6 が示した TCP/4371〜4372 の制限はベンダーの回避策ではなく、 調査会社による緩和の提案である。 **CISA が設定した是正期限は収載から3日（2026年11月20日 → 11月23日）で、 回避策が無い以上、期限内に取れる手は更新か切り離しのどちらかに限られる**
    取るべき行動 緊急パッチ手順に「**ベンダーが回避策を示していない無認証 RCE**」の分類を設け、 **保守停止の窓を待たずに更新できる承認経路**（事後報告での停止）を あらかじめ定めておく。承認待ちで日数を失う構造を先に壊す
  • ベンダー勧告の「悪用の有無」欄を、優先度付けの唯一の入力にしない
    F6 が最初の悪用事例を公表した翌日も、 Cisco の勧告は版1.0 のまま「PSIRT は悪用を把握していない」と記していた。 **その後 CISA が2026年11月20日に KEV へ収載し（是正期限11月23日）、 カナダのサイバーセキュリティセンターも同日に勧告を改訂したが、 Cisco の勧告は11月22日時点でも版1.0 のままである**—— ベンダーの悪用欄は、第三者の観測だけでなく**当局の認定よりも遅れうる**
    取るべき行動 脆弱性管理の優先度判定に、ベンダー勧告のほかに **①CISA KEV、②各国 CERT（カナダ Cyber Centre・JPCERT/CC 等）の勧告改訂、 ③第三者の調査会社による悪用報告**の3つを独立した入力として足し、 **どれか1つが「悪用あり」と言えば緊急扱いに上がる**判定にする。 自社の主要製品について、**非英語圏を含む**調査会社の公表を 週次で確認する担当を決める
  • 攻撃者の道具が攻撃中に書き換わる前提で、検知の置き場所を選ぶ
    F6 は、自作の Python スクリプトが攻撃の最中に手直しされていたことを 突き止めている（F6 は AI アシスタントの使用を示すと判断しているが、 その根拠の詳細は公表されていない）
    取るべき行動 検知の投資配分を見直し、**ハッシュ・ファイル名などの可変な指標より、 ①悪用機構に由来するログの痕跡、②本来あり得ない振る舞い （アプライアンスからの SMB・WinRM 接続）に重みを置く。** 既存の検知ルールのうち可変な指標だけに頼っているものを洗い出す
セキュリティ技術者への示唆
  • Expressway の `erlang.log` の `nodeup` を監視対象に入れる
    F6 は、悪用成功の主要な兆候として `erlang.log` に `nodeup,'wombat@127.0.0.1'` が現れることを挙げた。 この識別子は既知の悪用機構に対応する
    取るべき行動 `erlang.log` を SIEM へ取り込み、 **`nodeup` のうちノード識別子が自クラスタのメンバに一致しないもの**を アラート化する。`wombat@127.0.0.1` の完全一致だけに頼らない （識別子は攻撃側が変えうる）。 **検出時は F6 の指示どおり、他のログと痕跡で裏付けを取るまで確定扱いにしない**
  • クラスタ間通信ポートを、クラスタメンバの IP に限定する
    F6 は、更新が一時的に不可能な場合の緩和策として TCP/4371〜4372 への接続を信頼できるクラスタノードの IP に限ることを挙げた
    取るべき行動 ファイアウォールで TCP/4371〜4372 の送信元を クラスタメンバの IP のみに制限する。 **これは更新までの時間を買う措置であり、Cisco の回避策ではない**ことを 変更記録に明記し、X15.5.20 以降への更新を別件として残す
  • アプライアンス上の想定外のファイル書き込みを検知する
    攻撃者は Expressway 上に Python スクリプトを置いた。 F6 が示した配置パスは `/mnt/harddisk/i{0-9}{4}[a-zA-Z]?/*.py` である
    取るべき行動 Expressway のようなアプライアンスでは、 **業務上書き込まれるはずのないパスへのファイル生成**を異常として扱う。 ログ取得やサポート機能でファイルシステムの変更を見られる範囲を確認し、 見られないなら**ネットワーク側の振る舞い検知で代替する** （次項）
  • 協働サービスのゲートウェイから SMB・SQL Server・WinRM への接続を異常扱いにする
    攻撃者のスクリプトは、ネットワーク走査・SMB 共有の探索・ SQL Server と WinRM への接続・GitLab リポジトリの調査を行う構成だった
    取るべき行動 Expressway のセグメントからの発信通信について、 **SMB(445)・SQL Server(1433)・WinRM(5985/5986) 宛てを デフォルト拒否にし、検知のアラートを立てる。** ビデオ会議のゲートウェイがこれらに接続する業務上の理由は通常無い
  • GitLab 側で、認証情報の持ち出しを前提にした備えを置く
    攻撃者のスクリプトは、GitLab リポジトリを **認証情報その他の機密情報の持ち出しを目的として**調査する構成だった （実際に持ち出されたかは公表されていない）
    取るべき行動 GitLab のリポジトリとコミット履歴・CI/CD 変数に対して シークレットスキャンを全件かけ、検出分をローテーションする。 あわせて**リポジトリの大量クローン・探索的な参照**にアラートを設定し、 サービスアカウントの権限を最小化する

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Cisco Expressway-C / Expressway-E を**クラスタ構成**で運用しており、 版が X15.5.20 より前である（X14 以前を含む）Cisco は影響の条件を「脆弱性のある版を実行し、かつクラスタとして 構成されている場合」としている。本件の被害機器は X15.5.3 だった
システム構成□ インターネットに面した機器（Expressway-E 等）と社内側の機器が 同一クラスタに属しており、クラスタ間通信ポートが絞られていない外側の1台で root を取られた後、クラスタの信頼関係を通じて 社内側の2ノードへ到達された
認証・認可□ 社内の GitLab・コードリポジトリ・CI/CD 変数に認証情報が残っており、 シークレットスキャンを全件に掛けていない攻撃者のスクリプトは GitLab からの認証情報の持ち出しを目的としていた
運用・監視□ アプライアンス機器の `erlang.log` などのシステムログを SIEM へ取り込んでおらず、機器内に留めているF6 が示した悪用成功の主要な兆候は `erlang.log` の1行である
運用・監視□ 協働サービスのゲートウェイが置かれたセグメントからの発信通信に デフォルト拒否がかかっていない（SMB・SQL Server・WinRM 宛てが通る）横展開の準備として、まさにこれらへの接続を行うスクリプトが用意されていた
体制・契約□ 脆弱性の優先度付けが、**ベンダー勧告の「悪用の有無」欄だけ**を入力にしている （KEV や各国 CERT の勧告改訂を別系統で見ていない）本件では、CISA が KEV に収載して是正期限まで設定し（2026年11月20日・期限11月23日）、 カナダのサイバーセキュリティセンターが同日に勧告を改訂した後も、 **Cisco の勧告は11月22日時点で版1.0・「悪用を把握していない」のままだった**
体制・契約□ CISA KEV の収載を監視していない、または **収載から是正期限までが数日しかない**前提で緊急更新の段取りを組んでいない本件の是正期限は収載から3日であり、 **Cisco が回避策を示していないため、期限内に取れる手は更新か切り離しに限られる** （期限自体は米国 FCEB 向けで、日本の組織に法的拘束力は無い）
体制・契約□ ベンダーが回避策を示していない脆弱性について、 保守停止の窓を待たずに更新する承認経路が定められていないCisco は「この脆弱性に対処する回避策は存在しない」と明記している
