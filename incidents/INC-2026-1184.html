決済の中核——カード番号・有効期限・CVV、および authorization / settlement / 元帳の各系統——はn0n 自身が主張していない（出典3が明示）。「Visa が侵害された」という見出しから想像される姿と、掲載の中身は別物である（本記録の評価）。

実体はカード会員向けのマーケティング・キャンペーン管理の層である。この層は、ふつう決済基盤と同じ管理下に無い—— キャンペーン配信・反応分析・予約特典の手配は外部のプラットフォームとベンダーに出ている（本記録の評価）。Visa が「第三者サービス提供者」と言ったのは、まさにその層のことである。

Visa の声明は「否定」ではなく「場所の訂正」である——自社システムは無事、事案は第三者にある帰属出典 [1] [2] [3]

Visa の2026年11月17日の声明は、2つの文からなる（出典2・3。報道経由。原文英語）。

  • 「当社のシステムは関与しておらず、影響も受けていない」（原文: "Visa's systems were not involved and were not impacted"）
  • 「カード番号などの決済データが影響を受けた兆候はない」（原文: "no indication that payment data such as card numbers has been affected"）

そのうえで、事案がアジア太平洋地域の第三者サービス提供者に由来することを認めている（出典1・2・3）。

これは侵害の否定ではなく、侵害の場所の訂正である（本記録の評価）〈重要〉—— 「うちではない、うちの委託先だ」。読者が注意すべきは、この言い方が本人のリスクを下げないことである。氏名・個人メール・携帯番号・プレミアム会員のホテルとレストランの予約履歴がどこから出たとしても、出た先にいる人にとっては同じである（本記録の評価）。

そして Visa は提供者名を明かしていない（出典1が明示）〈未確定1〉。同じ提供者を使っている他の発行会社・提携先・航空・ホテルは、自社が同じ露出を抱えているかを点検できない（本記録の指摘）—— これが本件でいちばん実務的に困る点である。

Eli Lilly も「第三者ベンダーが侵害されたことによる波及」と説明しており（出典1）、Expedia も2026年11月12日に第三者データプラットフォームの侵害を公表している（出典2）。3者の説明の形が揃っている（本記録の整理）—— だが「同じプラットフォームである」と述べた当事者は一人もいない〈齟齬1〉。形の一致を起点の一致と読まないこと。

同じ日に Chase が落ちた——偶然の同時性が、否定の言葉を弱くする関係が否定された事象出典 [1] [2] [3] [13]

n0n が59組織を掲載した2026年11月16日、JPMorgan Chase のネットおよびモバイルアプリのサービスに異常が発生した（出典1・2）。

同社の説明は、障害が「オンプレミスのハードウェア系のソフトウェア不具合による一時的な問題」であり、サイバー攻撃との関連を示す証拠はない、というものである（原文英語: "temporary issue related to a software bug in on-premise hardware systems"、"no evidence it is cyber-related"。出典3。ロイターに対する説明）。

本記録は、この説明を否定する材料を持っていない（本記録の明示）。同時に、否定を裏付ける材料も公開されていない——障害の原因究明の結果、影響範囲、復旧の経緯はいずれも公表されていない。

ここから読むべきは、技術的な結論ではなく広報の構造である（本記録の評価）〈重要〉—— 恐喝グループにとって、掲載の日に相手の障害が重なることは最大の追い風である。 「無関係です」という説明は、事実であっても、同時性の前では弱い。 逆に言えば、平常時から障害の原因と経過を一定の粒度で説明する習慣がある組織は、こうした偶然に対して強い（本記録の評価）—— 説明が普段から出ている組織の「無関係です」は信用されやすい。

2026年11月22日の更新で、障害の広がりが1行にとどまらなかったことが分かった（出典13）〈重要〉—— AP は、11月16日（月）に Bank of America・Chase・J.P. Morgan・U.S. Bank・Wells Fargo・Zelle の利用者が口座へのアクセスに支障を訴えたと伝えている。 同社広報 Joe Evangelisti の説明は「オンプレミスのハードウェア系のソフトウェア不具合による一時的な問題で、サイバーに起因するものではない」であり、ロイターへの説明と同じ内容である（出典13。原文英語。本記録が訳した）。さらに同じ週に Microsoft・FAA・NSA・Apple でも技術的な問題が起きていたと報じられている（出典13）。

これは「否定の言葉が弱くなる」構造を強める材料である（本記録の評価）〈重要〉—— 同時性が1社の偶然ではなく「その週はどこも落ちていた」という背景に広がると、読者は個々の説明を検証せずに束ねて疑う。 本記録はこれらの障害と本事案を結びつける材料を持っていない（本記録の明示）—— 各障害の原因は本記録が確認しておらず、JPMorgan Chase 以外の銀行の説明も確認していない。

48時間という期限は、交渉のための道具である——起点がずれて期限も1日ずれる評価・解釈出典 [1] [2] [3]

n0n は掲載にあたり、48時間以内に交渉が成立しなければデータを公開すると脅した（出典1・3）。

ところが期限の起点が資料によってずれている（本記録の整理）〈齟齬2〉——

  • 出典3 は、掲載（2026年11月16日）から48時間と読んで11月18日ごろを期限とする
  • 出典2 は、カウントダウンの開始が11月17日であるとし、期限は11月19日ごろになる

本記録はどちらとも断定しない。 重要なのは期限の正確な日付ではなく、48時間という短さの意図である（本記録の評価）。

48時間では、侵害の有無を調査して結論を出すことはできない（本記録の評価）〈重要〉——フォレンジックの着手、ログの保全、委託先への照会、法務の判断。どれも間に合わない。つまり48時間は「調査のための時間」ではなく「調査させないための時間」である。決める材料が無いうちに決めさせる、という設計になっている。

対になる備えは、交渉の可否ではなく「48時間で何を言えるか」を事前に決めておくことである（本記録の評価）。①掲載された主張の内容を記録する、②自社の該当システムと委託先を特定する、③カード番号など最も重い項目の有無を切り分ける、④現時点で言えることだけを出す。 Visa が11月17日に「自社システムではない／決済データの兆候はない」という2点だけを述べたのは、この形である（本記録の評価）—— 全部が分かる前に、切り分けた一部を出している。

件数の大きさは実害の大きさではない——Walmart の商品レビュー120万件が並ぶ掲載の読み方評価・解釈出典 [1] [3]

掲載には、Walmart の商品レビュー120万件と取引先26万社のスコアカードが並んでいる（出典1）。

商品レビューは、その多くが元々サイト上で公開されている情報である（本記録の評価）。これを「120万件」として並べれば掲載は大きく見えるが、漏えいとしての重さは、同じ桁の住民登録番号や口座番号とは比較にならない（本記録の評価）〈重要〉。

一方で、同じ Walmart の掲載に含まれる「SSO 構成」は性質が違う（本記録の評価）—— 認証連携の構成情報は、それ自体が次の侵入の設計図になりうる。 件数は小さく、桁では目立たない。

恐喝グループの掲載は、交渉を有利にするために「大きく見える数」を前に出す（本記録の評価）。読む側がやるべきは、桁で驚くことではなく、項目の性質で並べ替えることである—— ①次の侵入に使える情報（SSO 構成・アクセス鍵・内部ディレクトリ）、②なりすましに使える個人情報（氏名・連絡先・予約履歴・処方記録）、③既に公開されている情報（商品レビュー）。①と②だけが対応の対象であり、③は量が多くても対応不要である（本記録の評価）。

    Walmart の掲載には商品レビュー120万件が含まれる（出典1）。 **その多くは元々公開されている情報であり、漏えいとしての重さは小さい。** 一方、同じ掲載の「SSO 構成」は件数では目立たないが、 **次の侵入の設計図になりうる**（本記録の評価）。 **桁の大きさに引っ張られると、対応の優先順位が逆転する**
    取るべき行動 掲載された主張を受け取ったら、項目を3区分に振り分ける表を作る—— **①次の侵入に使える情報**（認証構成・鍵・内部ディレクトリ）、 **②なりすましに使える個人情報**（氏名・連絡先・行動履歴・医療情報）、 **③既に公開されている情報**。 **①を当日、②を翌日、③は対応不要とする順序を事前に合意しておく**
セキュリティ技術者への示唆
  • 第三者連携のために作った IAM ロールの信頼ポリシーに、送信元の条件が入っているかを数える
    **本件の経路の候補として示された Qubole のキャンペーンでは、 攻撃者は製品の脆弱性ではなく「顧客が自分で作った信頼関係」を通っている**（出典6）。 **要求には External ID が付いており、すべて成功した。** **Wiz は「送信元 IP の条件だけでも、我々が観測したすべてのロール引き受けを 止められた」と書いている**（原文英語の訳。出典6）〈重要〉—— **これは本記録の評価ではなく調査側の記述である。** **さらに「攻撃者が引き受けたロールの多くは、ほかでは使われていなかった」とある**—— **連携を止めたときに API キーは消しても、ロールの信頼は残りやすい**（本記録の評価）。
    取るべき行動 第三者連携用の IAM ロールを一覧し、3つの数を出す—— **①信頼ポリシーに `aws:SourceIp` / `aws:SourceVpce` の条件が無いロールの数、 ②過去90日に一度も引き受けられていないロールの数、 ③External ID だけを根拠に「安全」と整理していたロールの数。** **②は信頼そのものを削除する。③は「External ID は CloudTrail に平文で出る 非秘密である」という前提に文書を書き換える**（出典6）。 **①は条件を足す。今週できるのは一覧と数え上げまでで十分である。**
  • 重要なバケットの「読み出し」が記録に残る設定になっているかを確かめる
    **Wiz は「管理イベントではオブジェクトの読み出しは見えない」として、 重要なバケットで S3 のデータイベントまたはサーバアクセスログを 有効にするよう勧めている**（出典6）〈重要〉。 **本件の候補経路では、S3 が読まれ、 1セッションでバケット全体が取得された例もある**（出典6）。 **既定のままなら、持ち出しの事実も量も後から再現できない**（本記録の評価）—— **「何が出たか」を答えられない状態は、本人通知の範囲を決められない状態である。**
    取るべき行動 個人データを置いているバケットを列挙し、データイベントの有効・無効を表にする。 **全部を有効にすると費用が増えるため、 「料金を払って記録を取るバケット」の基準を先に決める**—— 例: 個人データを含む／第三者連携のロールから読める／本人通知の対象になりうる。 **あわせて、ロールが読める秘密情報（Secrets Manager・SSM・Lambda の環境変数）の 範囲を棚卸しする**（出典6）。
  • リークサイトの監視対象に、自社名だけでなく主要委託先名とブランド名を入れる
    本件の掲載は2026年11月9日に46件の「番号だけの枠」として先に現れ、 11月16日に組織名で埋まった（出典2）。 **自社名で監視していても番号枠は引っかからない**（本記録の整理）。 **また本件のように委託先が侵害された場合、 掲載されるのは委託元のブランド名である**
    取るべき行動 監視のキーワードを3系統で持つ—— **①自社の法人名・略称・英文名、②主要委託先の社名、③自社ブランド・サービス名。** **②は委託先台帳から自動生成する。** 掲載数の日次推移も取り、急増を検知対象にする（番号枠のような予告を拾うため）
  • 攻撃者が「主張していない項目」を、安全の証拠として扱わない
    n0n はカード番号・有効期限・CVV・決済の各系統を主張していない（出典3）。 **これは「無い」ことの確認ではなく、攻撃者が言っていないだけである**（本記録の評価）。 Visa が述べた「カード番号の兆候なし」は当事者の確認だが、 他の項目については当事者の確認が無い
    取るべき行動 掲載の内容を整理する表に、**項目ごとに「根拠の種類」の列を設ける**—— 「攻撃者の主張」「当事者が確認」「当事者が否定」「誰も触れていない」の4値。 **『誰も触れていない』に入った項目を、対応検討の対象から外さない**
  • 委託先に預けるデータから、行動履歴を分離できるかを設計で確認する
    本件で主張されているのは、氏名・連絡先に加えて **プレミアム会員のホテル・レストランの予約記録**である（出典1・3）。 **氏名とメールだけなら、なりすましの材料としては弱い。** **本人しか知らないはずの予約の事実が付くと、標的型の連絡が成立する**（本記録の評価）
    取るべき行動 キャンペーン管理に渡しているデータ項目を実際に1件ダンプして目で見る。 **予約・購買・来店の実体が入っていたら、 ①本当に効果測定に必要か、②IDへの置き換えで足りるかを設計者に確認する。** 必要なら、委託先には集計値と匿名IDだけを渡す経路に切り替える
  • 自社の障害の説明を、平常時から一定の粒度で出す習慣を作る
    JPMorgan Chase の障害は n0n の掲載と同じ日に起きた（出典1・2）。 **同社は「ソフトウェア不具合」と説明したが、 同時性の前では、正しい説明であっても弱く見える**（本記録の評価）。 **平常時から原因と経過を説明している組織の『無関係です』は信用されやすい**
    取るべき行動 障害のステータスページに、復旧報告だけでなく **原因の区分（設定変更／ハードウェア／外部要因／不明・調査中）を1行で載せる運用にする。** **恐喝の掲載と障害が重なった日のために、 「同日に別の事象が起きている」ことを明示する文面も雛形に加える**
