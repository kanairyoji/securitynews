INC-2026-1188ARTEX侵害の対応経過をEye Securityが公表

AIエージェント型の攻撃フレームワーク ARTEX による企業侵害の対応経過が公表された—— 自社開発のPHPファイルアップロード機能の不備からWebシェルを置かれ、環境変数からAPIキーを奪われ、 発見から数分で悪用が始まり、約15分後には大量収集のコードが書かれ、レート制限が効き始めると 約3分でヘッダーのクライアントIPを差し替えて毎分9,000件超に達し、遮断後は17,000以上の 住宅用プロキシIPへ切り替えた。技術者アカウントからGitリポジトリに入り既存のCI/CDで Kubernetesに悪性Podを配備、削除しても1秒で再作成され、盗んだCIアプリのキーで セルフホストRunnerを8分ごとに再登録。復旧から1時間弱で再侵入され、最終的に環境を全面隔離した。 防御側も読み取り専用のAIエージェントを並列で走らせ30分ごとにEDRテレメトリを解析した

不正アクセス・侵害初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備
初報: 2026年11月12日（Eye Security の公表） 最終更新: 2026年11月19日

Eye Security（オランダのセキュリティ事業者）は2026年11月12日、AIエージェント型の攻撃フレームワーク「ARTEX」による企業侵害のインシデント対応の経過を公表しました（出典1。著者は Bas van den Berg）。ARTEX の攻撃活動そのものは複数のベンダーが報告していますが、第一線の対応チームが何を見て何を判断したかを時系列で示した資料は少ない—— 本記録はその点を理由にこの1件を記録します（本記録の判断）。

被害組織の名前・業種・国は公表されていません〈未確定3〉。

侵入の入口は被害企業が自社で開発したPHPファイルアップロード機能の不備で、ここにPHP Webシェルを置かれました（出典1）。攻撃者は環境変数からAPIキーなどの機密情報を取得し、あるプラットフォームのAPIキーを得てから数分でリクエストを送り始め、約15分後には大量のデータを収集するコードを書き上げました（出典1）。APIのレート制限が効き始めると、約3分でリクエストヘッダーのクライアントIP情報を差し替える改修を行い、攻撃トラフィックは毎分9,000件超に達しました。 防御側がこの経路を遮断すると、17,000以上の住宅用プロキシIPへ切り替えて継続しました（出典1）。

さらに盗んだ認証情報でクラウドの機密情報ストアに到達して認証情報を増やし、GitHub から取得した Neo-reGeorg を数分で改修して、異なるロードバランサ経由でも維持できる内部トンネルを張りました（出典1）。技術者アカウントを奪ってGitリポジトリのコードを書き換え、既存の自動デプロイ機構を使ってKubernetes に悪性Podを配備しています。自社アプリに管理者のバックドアアカウントを作り、ギフトカードコードのような換金できるデータを探していたため、Eye Security はランサムウェアの配備ではなく換金目的と判断しています（出典1）。

対応の転機は「復旧した1時間弱後の再侵入」です（出典1）。約1日の対応でEDRの新規アラートが止まり、判明していた盗難認証情報の更新も終えたと判断してサービスを再開したところ、攻撃者はGitサービスへのアクセス権を保持したままで、再びコードを書き換えて高権限の悪性Podを作り直し、nsenter でコンテナからホストへ到達しました。 悪性Podを削除しても自動デプロイ機構が1秒以内に作り直し、盗んだCIアプリのキーでセルフホストRunnerを8分ごとに再登録していました。チームは環境の全面隔離と、サービス復旧の先送りを決めています。

防御側もAIエージェントを使っています（出典1）。共有の非公開Gitリポジトリで複数のエージェントに調査資料とログを分析させ、Pull Request で引き継ぎを行い、環境へのアクセスは読み取り専用に限定して設定変更・機密情報の読み出し・トークンの漏えいを防ぐ安全検査を置きました。EDRテレメトリは30分ごとに解析させ、ランサムウェア疑いやセンサー改ざんのアラートが出たときはプロセスツリーとログを追わせて、Windows Update の再起動や WSL の活動かを切り分けています。

入口は自社実装のアップロード機能で、新しい脆弱性は使われていない原因・手口

初期侵入は、被害企業が自社で開発したPHPファイルアップロード機能の不備である（出典1）。ここにPHP Webシェルを置かれ、システムへのアクセス権を取られた。公開されているPHPライブラリの脆弱性ではないと一次公表は明示している。

この事案で新しいのは脆弱性ではなく速度である——これは本記録の解釈ではなく、一次公表自身がそう書いている（出典1）。使われた技術はWebシェル・環境変数からの機密情報の読み出し・リバースプロキシのトンネル（Neo-reGeorg）・Kubernetes の権限付きPod・nsenter によるホストへの到達——どれも既知の手口である。 変わったのは、これらを繋ぐのに要る時間と、阻まれたときに別の手を打つまでの時間である（本記録の整理）。

環境変数に機密情報が置かれていたことが、被害を一段広げた（本記録の評価）。Webシェルを置かれた時点で読み出せるため、アプリケーションの侵害がそのままAPIキーの侵害になる。 なぜ環境変数に置かれていたか、どのプラットフォームのキーだったかは公表されていない〈未確定1〉。

認証情報を取ってから使うまでの時間が消え、防御の1手ごとに3分で適応された評価・解釈

一次公表が最初に挙げる特徴は、認証情報の発見から利用までの時間差がほぼ消えたことである（出典1）。

  • APIキーの取得から最初のリクエスト送出まで「数分」
  • 約15分後には、APIを一括で収集するコードが書き上がっていた
  • レート制限が効き始めると、約3分でリクエストヘッダーのクライアントIP情報を差し替える改修が入り、毎分9,000件超に達した
  • 防御側がこの経路を遮断すると、17,000以上の住宅用プロキシIPへ切り替えた

この並びは、防御側の「1手」の価値を測る尺度になる（本記録の評価）。レート制限は機能していた——約3分で回避された。 IP遮断も機能していた——17,000以上のIPで無効化された。 つまり個々の対策が無駄だったのではなく、「対策を打つ → 攻撃側が適応する」の回転が人手の運用速度を超えたということである。

ただし一次公表は、速いことと静かなことを分けている（出典1）。ARTEX は痕跡を大量に残すので、監視能力があれば気づける余地はあるとされている—— 毎分9,000件のAPIリクエストは、むしろ見つけやすい挙動である（本記録の読み）。したがって本事案から引き出すべき結論は「検知は無意味になった」ではない（本記録の評価）。引き出すべきは「検知してから人が判断して手を打つまでの経路が遅すぎる」である。

正規のCI/CDが攻撃者の配備経路になり、Podを消しても1秒で戻った原因・手口

本事案で最も再現性のある学びはここである（本記録の評価）。

攻撃者は技術者アカウントのアクセス権を奪い、Gitリポジトリのコードを書き換え、既存の自動デプロイ機構を使って Kubernetes 環境に悪性Podを配備した（出典1）。攻撃者が自分で配備したのではなく、被害企業の正規の仕組みが配備した。

結果として、対応側が悪性Podを削除しても自動デプロイ機構が1秒以内に作り直した（出典1）。さらに盗んだCIアプリのキーでセルフホストRunnerを登録し、8分ごとに再登録していた——後続のデプロイ処理からさらに機密情報を取ることが目的とされている。nsenter で権限付きコンテナからホストノードへも到達している。

「マルウェアを消す」という作業の前提が崩れている（本記録の整理）。消す対象が、消した瞬間に正規の経路から再供給される。 止めるには、Git への書き込み権・デプロイのトリガー・Runner の登録権という「供給の源」を止めるしかない。対応チームが最終的に環境の全面隔離を選んだのはこのためである（出典1）。

技術者アカウントがどう乗っ取られたかは公表されていない〈未確定2〉—— 攻撃の最も重い分岐点なのに、再現できる形では書かれていない（本記録の明示）。

「新規アラートが止まった」で復旧を決め、1時間弱で再侵入された復旧の経過

約1日の対応の後、チームは次の2つを根拠にサービス再開を決めた（出典1）。

  1. EDRの新規アラートと攻撃の痕跡が見られなくなった
  2. 判明していた盗難認証情報の更新を完了したと判断した

再開から1時間もたたないうちに、攻撃者は戻ってきた（出典1）。攻撃者はGitサービスへのアクセス権を保持したままだった。

この失敗の構造は、本記録の読者がそのまま持ち帰れる（本記録の評価）。①は「攻撃者が活動していない」の証拠にしかならず、「アクセス経路が残っていない」の証拠にはならない—— 攻撃者が静かにしていれば、①は満たされる。 ②の「判明していた」が核心である—— 洗い出せていない認証情報は更新の対象に入らない。 本事案では、Gitサービスへのアクセスがその漏れだった。

復旧の判定条件は「アラートが止まったか」ではなく「攻撃者が持ち得るアクセス経路を列挙し、その全てを無効化したか」である（本記録の評価）。列挙できていないなら、復旧の可否を判断する材料が足りていないということである。

その後チームは環境の全面隔離に切り替え、被害範囲の評価と更新が必要な認証情報・機密情報の洗い出しに時間を割き、数日かけて段階的にサービスを再開した（出典1）。以後、攻撃者の侵入の成功は観測されていない。

防御側もAIエージェントを並列で走らせたが、読み取り専用に縛っている組織の対応

一次公表のもう一つの焦点は、防御側のAIエージェント運用である（出典1）。

仕組み：共有の非公開Gitリポジトリを作り、複数のAIエージェントに調査資料の分析・システムログの集約・調査結果の共有をさせ、Pull Request の仕組みで作業を引き継いだ。

制約：環境へのアクセスは読み取り専用に限定し、設定の変更・機密情報の読み出し・アクセストークンの漏えいを防ぐ安全検査を置いた。各ハントは記録を残す。

具体例：EDRテレメトリを30分ごとに解析させ、ランサムウェア疑いやEDRセンサーの改ざんのアラートが出たときは、プロセスツリーとシステムログを追わせて、Windows Update による再起動や WSL の活動が原因かを切り分けさせた。これが数分で終わるため、担当者がアラートを1件ずつ追う負担が軽くなったとされる。

一次公表は、後続の対応行動の決定は人が行うとしている（出典1）。本記録はこの線引きを評価する（本記録の判断）—— 読み取り専用・記録必須・判断は人という3点は、調査にAIを入れるときの最小構成として他組織でも使える。 逆に、書き込み権限を持つエージェントを調査に入れると、証跡の破壊と二次被害の切り分けが不可能になる（本記録の評価）。

事案の構造を図にしたものです。数値は公表値に基づきます。
自社実装のアップロード不備から、正規のCI/CDが攻撃者の配備経路になるまで

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
約1日の対応で新規アラートが止まり、判明していた盗難認証情報の更新を終えたと判断して サービスを再開した不十分**1時間もたたないうちに再侵入され、攻撃者はGitサービスへのアクセス権を保持していた** （出典1）。 **「新規アラートが無い」は攻撃者が活動していない証拠にしかならず、 アクセス経路が残っていない証拠にはならない**（本記録の評価）—— **攻撃者が静かにしていれば、この条件は満たされてしまう。** **「判明していた」認証情報を更新したという表現がそのまま限界を示している**—— **洗い出せていない経路は更新の対象に入らない。** **ただし本記録はこの判断を責める立場を取らない**（本記録の判断）—— **一次公表がこの失敗を明示して書いたことに、資料としての価値がある。**
再侵入を受けて、マルウェアの除去だけでは攻撃が止まらないと判断し、 影響を受けた環境を全面隔離してサービス復旧を先送りした機能した**本記録はこの切り替えを妥当と評価する**（本記録の判断）。 **正規の自動デプロイ機構が悪性Podを1秒以内に再作成する状況では、 個別の除去作業は原理的に追いつかない**（出典1）。 **隔離して時間を作り、被害範囲の評価と更新対象の洗い出しを先に終えるのが 唯一の収束経路である。** **実際にこの後は数日で段階的な再開に至り、攻撃者の侵入の成功は観測されていない**（出典1）
調査にAIエージェントを並列で投入したうえで、環境へのアクセスを読み取り専用に限定し、 設定変更・機密情報の読み出し・トークンの漏えいを防ぐ安全検査を置き、 後続の対応行動の決定は人が行う運用にした部分的に機能**本記録はこの3点（読み取り専用・記録必須・判断は人）を、 調査にAIを入れるときの最小構成として評価する**（本記録の判断）。 **書き込み権限を持つエージェントを調査に入れると、 証跡の破壊と二次被害の切り分けが不可能になる**（本記録の評価）。 **partial としたのは、効果の定量（調査時間がどれだけ短縮されたか）が 公表されていないためである**—— **「数分で終わる」「負担が軽くなった」という定性的な記述にとどまる**（出典1。本記録の明示）
CISO・経営層への示唆
  • 復旧の判定条件を「アラートが止まったか」から「アクセス経路を全部列挙して無効化したか」に変える
    約1日の対応で新規アラートが止まり、判明していた盗難認証情報の更新を終えたと判断して サービスを再開したところ、1時間もたたないうちに再侵入された。 攻撃者はGitサービスへのアクセス権を保持していた（出典1）
    取るべき行動 インシデント対応手順の「サービス再開の判定」に、**アクセス経路の棚卸し表の完成**を 必須条件として書き込む。表の行は「アカウント」「APIキー・トークン」「SSH鍵」 「CIアプリのキー・Runner登録」「Gitの書き込み権」「クラウドの機密情報ストア」 「自社アプリの管理者アカウント」とし、各行に「無効化した日時」「無効化を確認した方法」を埋める。 **埋まっていない行が1つでもあれば再開しない**という線を引く。 併せて「新規アラートが無いこと」は再開の条件から外す
  • 攻撃側の適応が3分なら、防御側の「1手」を人の承認なしで打てる範囲を決めておく
    APIのレート制限が効き始めると約3分でヘッダーのクライアントIPを差し替えて回避され、 経路を遮断すると17,000以上の住宅用プロキシIPへ切り替えられた（出典1）
    取るべき行動 「人の承認を待たずに自動実行してよい封じ込め操作」の一覧を事前に作り、経営として承認しておく （例: APIキーの自動失効、異常な取得量での自動スロットリング、 特定サービスアカウントの自動停止）。各操作に「誤作動したときの業務影響」と 「元に戻す手順」を併記する。**平時に承認しておかないと、夜間のインシデントで 承認待ちの数十分が攻撃側の数十手になる**
  • CI/CDとGitを「本番を変更できる経路」として、本番と同じ重みで守る対象に格上げする
    技術者アカウントからGitリポジトリに入られ、既存の自動デプロイ機構が悪性Podを Kubernetes に配備した。削除しても1秒以内に再作成され、 盗んだCIアプリのキーでセルフホストRunnerが8分ごとに再登録されていた（出典1）
    取るべき行動 資産台帳で Git・CI/CD・Runner を「本番と同等」の区分に移し、 フィッシング耐性のある多要素認証・保護ブランチ・レビュー必須・ Runner登録の監査を必須要件にする。 インシデント対応手順に「デプロイの停止」を封じ込めの第一手として入れる
  • 調査にAIを入れるなら「読み取り専用・記録必須・判断は人」を規程に書く
    Eye Security は防御側のAIエージェントを読み取り専用に限定し、設定変更・機密情報の読み出し・ トークンの漏えいを防ぐ安全検査を置き、各ハントの記録を残し、 後続の対応行動の決定は人が行う運用にした（出典1）
    取るべき行動 インシデント対応規程に「調査支援AIの権限は読み取り専用」「操作は全件記録」 「封じ込め・復旧の決定は人が行う」の3点を明記する。 併せて、調査対象の環境に対してAIが実行できるコマンドの許可一覧を作る。 **書き込み権限を渡すと、証跡の破壊と二次被害の切り分けができなくなる**（本記録の評価）
セキュリティ技術者への示唆
  • アップロード先でのスクリプト実行を拒否する（入口はここだった）
    初期侵入は被害企業が自社開発したPHPファイルアップロード機能の不備で、 PHP Webシェルを置かれた。公開ライブラリの脆弱性ではない（出典1）
    取るべき行動 アップロードの保存先をドキュメントルート外に置き、Webサーバ設定でPHP等のハンドラを 無効化する（`php_admin_flag engine off` や nginx の location での拒否）。 保存名は受け取った名前を使わず付け替える。 **自社開発のアップロード機能を grep で洗い出し、検査を共通実装1か所に寄せる**
  • 認証情報を環境変数から短命トークンへ移す
    攻撃者はWebシェルから環境変数を読んでAPIキーなどの機密情報を取得し、 数分で別の攻撃経路へ転用した（出典1）
    取るべき行動 クラウドのワークロード単位の認証（Workload Identity・IRSA 等）に移し、 長命キーを環境変数から外す。移せないものは一覧にし、 「どのワークロードがどのキーを使うか」の対応表を作る。 **この表が無いと侵害後に更新対象を列挙できず、本件のような再侵入につながる**
  • レート制限の鍵に「リクエストヘッダーのクライアントIP」を使わない
    APIのレート制限が効き始めると、攻撃者は約3分でヘッダーのクライアントIP情報を 差し替える改修を行い、毎分9,000件超に達した（出典1）
    取るべき行動 制限の単位を認証済みのAPIキー・テナント・アカウントに変える。 プロキシ経由の実IPを使う必要がある場合は、信頼できるプロキシからの ヘッダーのみを採用する設定（trusted proxies）に限定する。 **併せてAPIキーごとの1日の取得上限と乖離アラートを置き、超過時は自動失効させる**
  • Kubernetes で特権Pod・ホスト名前空間の使用を入り口で禁止する
    攻撃者は高権限の悪性Podを配備し、nsenter でコンテナからホストノードへ到達した（出典1）
    取るべき行動 Pod Security Admission を `restricted` で適用し、`privileged`・`hostPID`・`hostNetwork`・ `hostPath` を禁止する。例外が必要な名前空間は一覧にして個別に承認する。 **悪性Podを「削除する」運用では止まらないため、作成を拒否する側に置く**
  • セルフホストRunnerの登録と反復をアラートにする
    攻撃者は盗んだCIアプリのキーでセルフホストRunnerを登録し、8分ごとに再登録していた。 目的は後続のデプロイ処理からさらに機密情報を取ることとされている（出典1）
    取るべき行動 Runnerの登録・解除のイベントを監査ログに集め、「新規登録」と 「短い間隔での再登録の反復」をアラートにする。 Runnerは使い捨て（ephemeral）にし、特定のラベル・リポジトリに固定する。 **8分ごとという反復は気づける挙動である**（本記録の評価）

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Gitリポジトリへの書き込みが、レビューや承認を経ずに本番環境のデプロイを起動する構成になっている本件では技術者アカウントからGitに入られ、既存の自動デプロイ機構が悪性Podを Kubernetes に配備した。削除しても1秒以内に再作成された（出典1）

認証・認可□ 侵害時に「更新が必要な認証情報・トークン・鍵」を列挙できる台帳が無い本件の再侵入は、更新が「判明していた」範囲にとどまりGitサービスへのアクセスが 残ったことから起きている（出典1）
運用・監視□ APIのレート制限やアクセス遮断が、リクエストヘッダーのIPや単一のIP一覧に依存している本件はヘッダーのクライアントIPの差し替えで約3分で回避され、 遮断後は17,000以上の住宅用プロキシIPへ切り替えられた（出典1）

体制・契約□ インシデント対応手順の「サービス再開」の判定条件が、アラートの有無で書かれている本件は新規アラートが止まったことを根拠に再開し、1時間弱で再侵入された（出典1）
