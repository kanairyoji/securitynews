修正版が出ない Apache Axis が4件のうち最も重い評価・解釈

4件を同じ重さで扱うべきではない（本記録の評価）。

Apache Axis 1 は EOL である。 Apache は 「この問題を修正する Axis 1.x のリリースを作る見込みはない」と明記し、別の SOAP エンジン（Axis2/Java 等）への移行、またはパッチコミット 41f3b4e8d04e310ca81f86b92630ab2c11d608bd を適用したビルドの利用を推奨している（出典3。原文英語）。CISA の収載本文も「対象製品は EOL／EOS の可能性があり、利用者は使用の中止または対応版への移行を推奨される」としている（出典1。原文英語）。

脆弱性の仕組みは「エラー応答を読む」ところにある（出典3）。SOAP の <Fault> に含まれる <detail><exceptionName> で指定されたクラスが読み込まれ、<data> 要素もあるとそのクラスの String コンストラクタでインスタンス化される。 クラスを読み込むだけで static initializer が実行されるため、適切なクラスがクラスパス上にあればリモートコード実行につながる。 さらに Fault はサービス解決の段階で処理されるため、サービスに設定した認証ハンドラーでは防げない（出典3）—— 「認証をかけているから大丈夫」が成り立たない（本記録の明示）。

問題は Axis を使っている側に出る（本記録の整理）。Atlassian Confluence Data Center は「Remote API (XML-RPC & SOAP)」が有効な場合に1.x〜9.x が影響を受ける。この設定は3.0以降の新規インストールでは既定で無効で、10.x 以降では機能が削除されており、Atlassian Cloud は影響を受けない。修正版は 9.2.28（出典4）。N-able N-central は「Legacy API」が有効な場合に影響を受ける。既定では無効とされており、2026.4 Hotfix 3（2026.4.1.39）で機能が無効化された（出典4）。

どちらも「既定では無効な古い API を有効にしていた環境」が狙われている（本記録の評価）—— これは『長年オンのままになっている互換機能』を棚卸しする話であり、パッチ適用の話ではない。

公表から攻撃まで7日、PoC 公開から攻撃まで1日である（本記録の算出）。修正版が出ない脆弱性では、PoC の公開が事実上の攻撃開始の合図になる（本記録の評価）—— 「パッチが出てから適用する」という手順が成立しない。

Rapid7 が観測した攻撃後の挙動も、EOL 由来の侵入がどこまで広がるかを示している（出典4）。Confluence の Java プロセスがサービスアカウントとして bash と curl を起動し、一時的なトンネルドメインから取得した16進エンコードのコマンドやスクリプトが数百件実行された。 ホスト・ネットワーク・設定・暗号鍵・データベース設定が列挙され、Confluence のデータベース認証情報で MySQL に接続してページ本文・アプリケーションリンク・添付ファイルが調べられた。 添付ファイルのディレクトリを探索して Office 文書を解析し認証情報を探し、Luhn チェックでクレジットカード番号を探した。 Crowd API でユーザーとグループを取得し AS-REP ロースティングを試みたが失敗した。 最初のエクスプロイト要求から約4時間後にサービスアカウントの認証情報を取得してクラウドのデータウェアハウスに照会し、約12時間後にはレガシー認証を使って192.238.253[.]176 から Microsoft 365 にサインインした（出典4）。

「社内 Wiki が1台やられた」で終わらない（本記録の評価）—— Confluence は認証情報と添付ファイルの集積地であり、そこから SaaS の認証へ繋がっている。

期限の長短ではなく、フォレンジック要件の有無で優先順位が分かれている対策・注意喚起

CISA が課した要件には、期限とは別の軸がある（本記録の整理。出典1）。

期限: Synology DSM・Apache Axis・REDCap は2026年11月21日（収載から3日）。LiteLLM は2026年12月2日（14日）。

BOD 26-04 に基づくフォレンジックのトリアージ要件: Synology DSM・Apache Axis・REDCap の3件に課され、LiteLLM には課されていない（本記録の作成者がカタログの記載で確認した）。

この2軸の意味を分けて読む必要がある（本記録の評価）。トリアージ要件は「すでに侵害されていないか調べよ」という指示である—— 修正を当てるだけでは足りないという判断を表している。 期限が14日で長い LiteLLM にこの要件が無く、期限3日の3件に要件が付いている。 したがって「期限が遠いから後回し」という読み方をすると、調査が必要な3件の優先度を落とすことになる。

4件に共通する要求事項は同じ文面である（出典1）—— 「ベンダーの指示に従って緩和策を適用し、CISA の BOD 26-04『リスクに基づくセキュリティ更新の優先順位付け』と『フォレンジックトリアージ要件』に従うこと。クラウドサービスについてはBOD 26-04 の該当指針に従い、緩和策が無い場合は製品の使用を中止すること。各資産のインターネットへの露出を評価し、BOD 26-04 の適用指針を守る責任は利害関係者にある」（原文英語の要旨）。

「緩和策が無い場合は製品の使用を中止する」という選択肢が明記されている点が、Apache Axis にとっては現実的な指示である（本記録の読み）。

Synology は勧告から743日後に悪用が確認された背景・過去事例

CVE-2024-10441 の KEV 収載は、修正版が出てから2年以上あとである（本記録の整理）。

Synology の勧告 SA-24:20 は2024年11月5日付（最終更新 2025年3月28日）で、状態は「Resolved」、重要度は Critical（出典2。本記録の作成者がページを取得して確認した）。CVE-2024-10441 は CVSS 9.8（AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H）で、system plugin daemon の出力のエンコード・エスケープの不備により、遠隔の攻撃者が任意のコードを実行しうる。 対象は BSM 1.1-65374 より前、および DSM の 7.2-64570-4 / 7.2.1-69057-6 / 7.2.2-72806-1 より前。修正版は DSM 7.2.2-72806-1 / 7.2.1-69057-6 / 7.2-64570-4 / 7.1.1-42962-7 / 6.2.4-25556-8 以上である（出典2）。

KEV 収載は2026年11月18日（出典1）——勧告から743日後である（本記録の算出）。

これは NAS という機器の性質を示している（本記録の評価）。NAS は「置いたら動き続ける」装置で、更新の担当者がいないままインターネットに公開されていることが多い。 修正版が2年前に出ていても、適用されていない台数が攻撃者にとって十分に残る。 サーバーの脆弱性管理の対象台帳に NAS・ルーター・カメラのような「機器」が入っていない組織では、この743日はそのまま露出期間になる。

なお、2026年10月末に Synology が C3RB3R ランサムウェアの攻撃を警告したと報じられ、CVE-2024-10441 がその1つとされている〈齟齬2〉。本記録はこの帰属を確認できていない—— Synology の勧告ページには C3RB3R への言及が無く（本記録の作成者がページを取得して確認した）、どの CVE が悪用されたかを Synology が明示したかは不明である〈未確定3〉。

LiteLLM は「APIキーを保持する位置」にあることが意味を持つ評価・解釈

CVE-2026-40217 は、4件のうち悪用の内容が最も分からない（本記録の明示）。

CISA の記載は「/guardrails/test_custom_code URI でのバイトコードの書き換えにより、遠隔の攻撃者が任意のコードを実行しうる、保護されていない代替チャネル（CWE-420）の脆弱性」である（出典1。原文英語）。期限は2026年12月2日で、フォレンジックのトリアージ要件は課されていない。 本記録の作成者は、実際の悪用を示す一次資料を見つけられなかった〈齟齬4〉〈未確定4〉。

それでも、この1件は日本の読者にとって意味がある（本記録の評価）。LiteLLM は各種 LLM プロバイダへのプロキシであり、構造上、複数のプロバイダのAPIキーを集積して保持する位置にある。 そこで任意のコードが実行できるなら、保持されている鍵が全部出る。

外部公開された LLM 基盤に保存されたAPIキーを狙う活動は、同日の別の記録（INC-2026-1188 の ARTEX の事案）でも論点になっている（本記録の整理）—— ただし本 CVE との結びつきを本記録は確認していない〈未確定4〉。「AIの基盤を自前で立てると、鍵の集積地が1つ増える」という見方は、本 CVE の内容からは独立して成り立つ（本記録の評価）。

実務上の最初の確認は1つである（本記録の評価）—— 自社の LiteLLM が外部から到達できる位置にあるか。 /guardrails/test_custom_code が外部に開いている必要は、通常の運用では無い。

REDCap は「公開アンケート」という到達面を持つ評価・解釈

CVE-2026-90817 の構造は、REDCap の用途そのものに関わる（本記録の整理）。

CISA の記載は「認証されていない攻撃者がサーバー上で任意のコードを実行しうるコードインジェクションの脆弱性。細工した HTTP 要求により、公開アンケートの文脈から想定外のコントローラーのルートに到達させ、データ取り込みの処理で細工したファイルパスまたはストリームのパラメータを与える。悪用には有効な公開アンケートのハッシュの知識が必要」である（出典1。原文英語。CWE-73・CWE-94）。

「公開アンケートのハッシュを知っている必要がある」という条件は、防御として弱い（本記録の評価）—— 公開アンケートは、まさに外部の回答者に URL を配るものである。 配布した URL がそのまま悪用の前提条件を満たす。

REDCap の利用者は研究機関・医療機関・大学である（本記録の整理）。日本でも研究データ収集の基盤として使われており、扱うデータは被験者の個人情報・健康情報である。 攻撃者の目的が採掘ソフトの設置だったとしても（報じられている内容。本記録は一次資料を確認していない〈齟齬3〉）、任意コード実行はデータへの到達も意味する（本記録の評価）。

期限は11月21日（収載から3日）で、フォレンジックのトリアージ要件も課されている（出典1）—— 「修正して終わり」ではなく「すでに入られていないか調べる」対象である。

CISO・経営層への示唆
  • 脆弱性管理の対象台帳に「サーバー以外の機器」と「同梱されている部品」を入れる
    Synology DSM は勧告から743日後に悪用が確認された（出典1・出典2）。 Apache Axis 1.x は EOL のまま Confluence Data Center と N-able N-central に 同梱され、そこで攻撃を受けている（出典4）
    取るべき行動 資産台帳に NAS・ルーター・カメラ・UPS のような「機器」の行を作り、 ファームウェアの版と最終更新日を記録する。 併せて主要な製品について、同梱されているサードパーティ部品の一覧（SBOM）を ベンダーに要求する。**取れない製品は「調べられない資産」として別に数える**—— Axis のような EOL 部品は、製品名で検索しても出てこない
  • EOL 部品の脆弱性には「パッチを待つ」という選択肢が無いことを前提に判断する
    Apache は Axis 1.x の修正版を作る見込みはないと明記し（出典3）、 CISA も「緩和策が無い場合は製品の使用を中止する」ことを選択肢として示している（出典1）。 実際に PoC 公開の翌日に攻撃が来ている（出典4）
    取るべき行動 「修正版が出ない脆弱性」が見つかったときの判断手順を事前に決める—— ①機能の無効化で回避できるか ②製品の移行にどれだけかかるか ③その間の代替の防御（到達制限・WAF・監視）は何か ④使用を中止する判断は誰がするか。 **この4問に答える場がないと、「パッチ待ち」のまま時間が過ぎる**
  • KEV は「期限」だけでなく「フォレンジック要件の有無」で優先順位を読む
    4件のうち Synology・Apache Axis・REDCap の3件には BOD 26-04 に基づく フォレンジックのトリアージ要件が課され、期限が最も遠い LiteLLM には課されていない （出典1。本記録の作成者がカタログの記載で確認した）
    取るべき行動 KEV を参照する運用で、各項目について「修正だけで足りるのか、 侵害の有無の調査まで求められているのか」を区別して記録する。 **調査が必要な項目は、修正担当とは別に調査担当を割り当てる**—— 更新作業で手一杯になると調査が落ちる
  • 「既定で無効な古い API を有効にしている環境」を棚卸しの単位にする
    Confluence Data Center は「Remote API (XML-RPC & SOAP)」が有効な場合に、 N-able N-central は「Legacy API」が有効な場合に影響を受ける。 どちらも既定では無効とされている（出典4）
    取るべき行動 主要な業務システムについて「既定と違う設定になっている項目」の一覧を作り、 各項目に「なぜ有効にしたか」「いま誰が使っているか」を記録する。 **記録が無い項目は無効化の候補にする。** 既定で無効な機能は、攻撃者にとって「有効にしている少数」を狙う的になる
  • 自前で立てたAI基盤を「認証情報の集積地」として資産に登録する
    LiteLLM は複数の LLM プロバイダへのプロキシであり、構造上それらのAPIキーを 保持する位置にある。その CVE-2026-40217 が KEV に収載された（出典1）
    取るべき行動 社内で稼働している LLM プロキシ・ゲートウェイ・エージェント基盤を洗い出し、 それぞれが保持している外部サービスのAPIキーの一覧を作る。 外部からの到達可否を確認し、**到達できるものは「認証情報の集積地が インターネットに面している」状態として扱う**
セキュリティ技術者への示唆
  • Confluence の Remote API 設定と N-central の Legacy API を今日確認する
    CVE-2026-90436 は PoC 公開の翌日（2026年11月13日）に実際の攻撃が観測されており、 影響条件はこの2つの設定である（出典4）
    取るべき行動 Confluence は「General Configuration」の「Further Configuration」で Remote API の設定を確認し、使っていなければ無効化する。 更新は 9.2.28 または 10.x へ。 N-central は Legacy API の有効・無効を確認し、2026.4 Hotfix 3（2026.4.1.39）へ更新する。 **どちらも既定では無効なので、有効なら理由を調べてから止める**
  • SOAP を受ける経路で「認証をかけているから安全」という前提を外す
    Apache の説明によれば、SOAP の Fault はサービス解決の段階で処理されるため、 サービスに設定した認証ハンドラーでは防げない（出典3）
    取るべき行動 Axis 1.x を使っている箇所を特定し、認証の前段で Fault を処理する経路が 外部から到達できるかを確認する。 到達できる場合はネットワーク側で遮断するか、 パッチコミット 41f3b4e8 を適用したビルドに差し替える。 **アプリ層の認証設定を確認するだけでは判断できない**
  • Confluence が侵害されたときの被害範囲を、添付ファイルと認証情報で見積もる
    Rapid7 の観測では、攻撃者は Confluence のデータベース認証情報で MySQL に接続して ページ本文・アプリケーションリンク・添付ファイルを調べ、添付の Office 文書を 解析して認証情報を探し、Luhn チェックでカード番号を探し、 最初の要求から約4時間後にサービスアカウントの認証情報を取得、 約12時間後にレガシー認証で Microsoft 365 にサインインした（出典4）
    取るべき行動 Confluence の添付ファイルに認証情報・鍵・カード番号が含まれていないかを 検索して洗い出す（手順書に平文のパスワードが書かれていることが多い）。 アプリケーションリンクで接続している先を一覧化し、 Microsoft 365 等のレガシー認証を無効化する。 **Wiki は「認証情報の二次的な保管庫」になっている**
  • NAS のファームウェア更新を「機器の点検」として定期の作業にする
    CVE-2024-10441 の修正版は2024年に出ていたが（勧告の状態は Resolved）、 2026年11月に実際の悪用が確認され KEV に収載された——743日の差がある（出典1・出典2）
    取るべき行動 社内の NAS を列挙し、DSM／BSM の版を記録して 7.2.2-72806-1 / 7.2.1-69057-6 / 7.2-64570-4 / 7.1.1-42962-7 / 6.2.4-25556-8 以上 （系列に応じて）へ更新する。 **併せてインターネットからの到達可否を確認し、管理画面を外部に出さない。** 更新の点検を四半期の定期作業として担当者を決める
  • LiteLLM の到達範囲を絞り、`/guardrails/test_custom_code` を外部に出さない
    CVE-2026-40217 は `/guardrails/test_custom_code` URI でのバイトコードの書き換えにより 任意のコードを実行しうるもので、KEV に収載された（出典1）
    取るべき行動 自社の LiteLLM が外部から到達できるかを確認し、 到達できる場合は VPN・リバースプロキシの認証・IP 制限のいずれかで絞る。 `/guardrails/*` のエンドポイントは管理用ネットワークからのみ到達できるようにする。 **併せて LiteLLM が保持している各プロバイダのAPIキーを棚卸しし、 侵害時に失効させる手順を用意する**
  • REDCap の公開アンケートの一覧と、サーバー上の異常なプロセスを確認する
    CVE-2026-90817 は公開アンケートの文脈から想定外のコントローラーに到達させるもので、 悪用には有効な公開アンケートのハッシュの知識が必要とされる（出典1）。 CISA はこの CVE にフォレンジックのトリアージ要件を課している
    取るべき行動 稼働中の公開アンケートを一覧化し、ベンダーの指示に従って REDCap を更新する。 **併せて Web プロセスがシェルやインタプリタを起動していないか、 見慣れないプロセス（採掘ソフトを含む）が動いていないかを確認する**—— 公開アンケートの URL は外部に配布済みであるため、 「ハッシュを知る必要がある」は防御として弱い
