守る機能は動かし続け、管理機能だけを落とした組織の対応

メール防御の基盤が侵害されたとき、全部止めるとメールが届かなくなります。

N-able が取った切り方は、すべての更新で一貫しています（出典1）。

  • 動かし続けたもの——メールの送受信（mail flow）とスパムフィルタ。「事案を通じて動作を続けた」とされています
  • 止めたもの——管理画面（UI）・API・隔離（quarantine）・ログ・メールボックス同期。管理画面と API は予防的に無効化したと明記されています

利用者から見た影響も具体的に書かれています（出典1。11月18日11時44分の更新）。顧客は管理画面にログインできず、隔離されたメールの確認や解放ができず、ログを参照できず、ドメインの追加や削除といった設定変更ができない状態です。

本記録の評価——切り方が構造に沿っています。データ面（メールを通す機能）と制御面（それを設定・確認する機能）を分け、制御面だけを落としています。メール防御の基盤では、守る機能が止まることが最大の被害です。

一方で、残る問題があります（本記録の指摘）〈重要〉。隔離が止まっている間、誤判定で止まった正当なメールは解放されません。フィルタは動き続けているので、判定は行われ、隔離にメールは溜まります。しかし利用者はそれを取り出せません。

起票（11月17日3時00分）から本記録の作成時点（11月19日19時55分）までは約65時間です（本記録の算出）。この間の代替手順は公表されていません（本記録の確認）。復旧の時期も示されていません〈未確定3〉。

「顧客データ侵害の証拠は無い」が、侵害されたサーバの役割は示されていない未確定事項

N-able のデータについての記述は、範囲を名指しで限定しています（出典1。原文英語）。

調査は継続中だが、現時点で顧客データが侵害された証拠は無い。これはテナントのメールボックスへのアクセスを含む。

「テナントのメールボックスへのアクセスを含む」という一句は、利用者が最初に心配する点を名指しで否定しています（本記録の評価）。多テナント基盤の事案では、「他のテナントのデータに届いたのか」が最大の問いです。

しかし、2つの留保があります（本記録の整理）〈重要〉。

1つは、「証拠が無い」は「侵害されていない」ではないことです。 The Hacker News も、公開されている事案の更新では認証情報の露出が確認されておらず、影響を受けたパスワード・API キー・トークンも特定されていないと整理しています（出典2）。確認されていないことと、無いことは別です。

もう1つは、侵害されたサーバの役割が公表されていないことです〈未確定2〉。同社は「サーバのうち1台（one of the servers）」と述べるだけです（出典1）。

Mail Assure・SpamExperts は、メールの中身を通過させる基盤です（本記録の整理）。そして隔離（quarantine）とログを保持します——つまりメールの内容が一定期間とどまる場所があります。侵害されたサーバがその役割を担っていたのか、管理画面を提供するサーバだったのか、公表資料からは判断できません。

これが利用者の行動を決めます（本記録の指摘）。メール処理に関わるサーバだったなら、自テナントのメールの扱いを確認する必要があります。管理面だけなら、確認すべきは設定の改変です。

さらに、調査期間中は利用者が自テナントのログを参照できません（出典1）〈重要〉。利用者が自分への影響を独自に確認する手段が、この期間は無い状態です（本記録の指摘）。

本記録を作ったとき（2026年11月19日）、公表されていたのは「サーバのうち1台への権限のないアクセス」までだった。その後の4日で、外から見える材料が3つ増えた。

  • 11月22日19時10分、N-able が CNA として CVE-2026-134624 を公表した（出典3）
  • 11月23日、CISA がこれを KEV カタログに収載した（出典5）

脆弱性の中身はこうである（出典3。原文英語を訳出）。

N-able MailAssure (SpamExperts) の 20261121.1943 より前の版は、リレーを設定したときに行われる LDAP 同期の接続確認の宛先を制限していない。認証済みの API 利用者は、サーバを任意の内部ホスト・ポートへ接続させ、どれが到達可能かを判定し、内部サービスへ細工したデータを送ることができる

「接続できるか試す」機能が、宛先を限っていなかった（本記録の整理）。LDAP 同期の設定画面で「つながるか確認」を押す動作が、そのまま内部ネットワークの走査に使える。CVSS 4.0 の基本値は 9.3（CRITICAL）で、前提は PR:H—— 高い権限の API アクセスを必要とする（出典3）。

ここが本事案の読みどころである（本記録の評価）〈重要〉。N-able はこの脆弱性が侵入経路だったとは言っていない（出典3・6）。The Hacker News も「侵害を調査する中で見つけた」と書くに留めている。一方 CISA は、公表の翌日に KEV へ収載し、SSVC の評価を Exploitation: active（悪用が現に起きている）とした（出典3・5）。

「当事者は原因と言っていないが、当局は悪用されていると判定した」という状態が成立している。本記録はこの2つを混ぜない——原因の分類は「公表されていない」のままである〈未確定6〉。だが読者の作業は、どちらであっても同じになる（本記録の評価）—— 版 20261121.1943 以降であることを確認する。

順序にも意味がある（本記録の整理）。CVE が出て翌日に KEV、NVD の分析はこの時点でまだ Received（未了）である（出典3）。NVD の掲載内容が揃うのを待って棚卸しを始める運用では、是正期限（KEV 登録の3日後）に間に合わない。本件で最初に動ける材料は、ベンダーの勧告と CVE レコードだけだった。

メール防御サービスの内部から内部を叩く形だった原因・手口出典 [1] [3]

CVE-2026-134624 はサーバサイドリクエストフォージェリ（SSRF）である。CVSS 4.0 のベクタを分解すると、どこに被害が出る想定かが読める（出典3）。

  • VC:H / VI:H — 脆弱なサービス自身の機密性・完全性への影響が高い
  • SC:H / SI:H — 後続のシステムへの機密性・完全性の影響も高い
  • PR:H — 実行には高い権限の API アクセスが要る
  • VA:N / SA:N — 可用性への影響は想定されていない

SC/SI が立っているのが SSRF の性質である（本記録の整理）〈重要〉。壊されるのは踏み台にされたサーバではなく、その内側にあるものである。マルチテナントのクラウドでは、その内側に他のテナントの構成・認証情報・管理面が並んでいる。

本事案で実際に停止したのも、メール配送そのものではなく管理画面・API・隔離・ログ・メールボックス同期だった（出典1）。止まった範囲と、脆弱性が到達できる範囲が、どちらも「管理面」である（本記録の評価）—— ただし両者を結ぶ説明は当事者から出ていない〈未確定6〉。

PR:H（高い権限が必要）という前提は、利用者の立場からは二通りに読める（本記録の評価）。

  1. 自社の API 利用者の資格情報が盗まれていなければ悪用されない
  2. 提供者側の管理アクセスが奪われていれば、前提は満たされている

本事案は提供者のサーバ1台への権限のないアクセスから始まっている（出典1）。したがって 2 の読み方を排除できない—— SaaS 側の権限前提は、SaaS 側が侵害された時点で前提として機能しない（本記録の評価）。これは利用者が自社で検証できない領域であり、だからこそ提供者からの個別連絡（11月18日に送付済みとされる）の内容が重要になる（出典1）〈未確定4〉。

    取るべき行動 ベンダーの「証拠は無い」という表明を受けたときに、 自組織で確認すべき項目（管理画面の設定変更履歴、API キーの利用記録、 テナント管理者の認証記録）を列挙しておく。 ベンダー側のログが参照できない期間について、 復旧後に提供を求める旨を事前に取り決める。

セキュリティ技術者への示唆
  • 「接続できるか確認する」機能を持つ設定画面を、 宛先の制限込みで点検する。
    **本件の脆弱性は、リレーを設定したときに走る LDAP 同期の接続確認が宛先を制限していなかったものである** （出典3。原文英語を訳出）〈重要〉—— **認証済みの API 利用者が、サーバを任意の内部ホスト・ポートへ 接続させ、到達可能なものを判定し、 内部サービスへ細工したデータを送れた。** **CVSS 4.0 で SC:H/SI:H（後続システムへの影響が高い）が立っており、 被害は踏み台にされたサーバではなくその内側に出る**（出典3）。 **この形の機能は自社の製品・社内ツールにも広く存在する** （本記録の評価）—— **疎通確認・Webhook の試験送信・URL のプレビュー・ インポート元の指定が同じ構造を持つ。**
    取るべき行動 **自組織の製品・社内ツールで「宛先を利用者が指定し、 サーバ側が接続する」機能を列挙する。** **各機能について、①許可する宛先を名簿で限っているか、 ②内部アドレス帯（リンクローカル・メタデータ endpoint を含む）を 拒否しているか、③リダイレクトの追跡を止めているか、 ④応答の差異（到達可否・所要時間）を利用者へ返していないかを確認する。** **権限が要る機能（本件は高い権限の API アクセスが前提）でも、 その権限を持つ側が侵害された場合を想定して宛先制限を入れる。**
  • 多テナント基盤の制御面とデータ面を、別の到達範囲に置く
    **本件では N-able が管理画面（UI）と API だけを予防的に無効化し、 メールの送受信とスパムフィルタを動かし続けた**（出典1）〈重要〉—— **この切り方ができたのは、両者が分けて止められる構成だったためである** （本記録の読み。構成自体は非公表）。 **メール防御の基盤では、守る機能が止まることが最大の被害になる**（本記録の評価）。
    取るべき行動 自組織が多テナント基盤を運用している場合、 管理面（管理画面・管理用 API）とデータ面（本来のサービス処理）を 別々に無効化できるかを確認する。 できない場合は、管理面を落としてもデータ面が動き続ける構成へ分離する。
  • 設定の変更履歴を、誰がいつ変えたかまで残す
    **N-able は障害の原因を「プラットフォームの設定とサービス依存関係の組み合わせ」と 説明したうえで、翌日にセキュリティ事案へ訂正した**（出典1）〈訂正1〉〈重要〉—— **設定の不整合を見つけたときに「誰がいつ変えたか」が記録から分かれば、 侵害を早く疑える**（本記録の評価）。 **本件で切り分けに要した時間（11月16日の障害認識から11月18日の判断まで2日）の 内訳は公表されていない**〈未確定1〉。
    取るべき行動 基盤の設定（構成管理・環境変数・権限・依存サービスの接続先）の変更を、 変更者・時刻・変更前後の値つきで記録に残す。 障害の切り分け手順で、この記録を最初に見る段を作る。
  • ベンダーのステータスページを、更新履歴が残る形で記録する
    **本件の経過は、N-able が過去の更新を書き換えず 11回の更新をすべて残したことで外部から追える**（出典1。本記録の確認）〈重要〉—— **「設定の問題」から「セキュリティ事案」への入れ替わりは、 更新履歴が残っていなければ見えない**（本記録の評価）。 **逆に、ベンダーが過去の更新を書き換える場合、 利用者側で記録していなければ経過が失われる。**
    取るべき行動 依存しているクラウドサービスのステータスページを定期に取得して保存する （多くのステータスページは JSON の API を持つ。 本記録は uptime.n-able.com の公開 API から取得した）。 事案が起きたら、更新のたびに取得して時系列を自組織の記録に残す。
  • 隔離（quarantine）が使えない期間、重要な送信元を素通しできる経路を用意する
    **本件では隔離とログが停止し、 顧客は隔離されたメールの確認・解放ができない状態である**（出典1）〈重要〉—— **フィルタは動き続けているため判定は行われ、 誤判定で止まった正当なメールは溜まり続ける**（本記録の指摘）。 **約65時間が経過し、復旧時期は示されていない**（本記録の算出）〈未確定3〉。
    取るべき行動 メール防御サービスの許可一覧（送信元ドメイン・IP）を、 サービス側の管理画面に依存しない形（自社のメールサーバ側の設定等）でも 持てるか確認する。 持てない場合は、重要な取引先に対して電話・別経路での連絡手段を周知しておく。
