INC-2026-1201CISAのICS勧告3件、OpenPLCに競合状態

CISA が2026年11月19日に ICS 勧告3件（ICSA-26-323-01／-02／-03）を同時公表した—— OpenPLC Runtime では「最初の管理者を作る」処理に競合状態があり、 同時に複数のリクエストを投げると存在チェックを全部が通り抜けて 未認証の管理者アカウントが複数作られる（CVE-2026-126088・CVSS v4.0 9.2）。 Elecbrakes のトレーラー用電動ブレーキ制御装置では、BLE の電波が届く範囲にいるだけで 認証もペアリングもなくブレーキに書き込める（CVE-2026-96805・CVSS v3.1 9.6）。 MQTT クライアントライブラリ libumqtt の整数アンダーフロー（CVE-2026-125132）は、 リポジトリの所有者が CISA の調整要請に応じなかったため修正が無い

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備委託先・供給元起因
初報: 2026年11月19日 最終更新: 2026年11月20日

CISA（米国サイバーセキュリティ・インフラストラクチャセキュリティ庁）は2026年11月19日、産業制御システム（ICS）向けの勧告を3件、同時に公表しました。いずれも実際の悪用は報告されていない段階の公表です。

  • ICSA-26-323-01: Autonomy Logic OpenPLC Runtime（4.2.4 以前）の競合状態。CVE-2026-126088、CWE-362、CVSS v3.1 8.1（High）／v4.0 9.2（Critical）。未認証の管理者アカウントが複数作られる。修正は 4.3.0 以降
  • ICSA-26-323-02: Elecbrakes EB2／VM1／ELBC2000（トレーラー用の電動ブレーキ制御装置）の3件の脆弱性。最大 CVSS v3.1 9.6（Critical）。BLE の電波が届く範囲にいる機器が、認証もペアリングもなくブレーキに書き込める。ELBC2000 には修正が無い
  • ICSA-26-323-03: libumqtt（1.1.1 以前）の整数アンダーフロー。CVE-2026-125132、CWE-191、CVSS v3.1 8.6（High）／v4.0 8.8（High）。修正は提供されていない——リポジトリの所有者が CISA の調整要請に応じなかった

3件のうち最も読みどころがあるのは OpenPLC Runtime です。欠陥は「パスワードが弱い」ではなく、「ユーザーがまだ存在しないこと」を確認してから登録するまでの間に別のリクエストが割り込めるという時間の穴にあります。CISA の記述は次のとおりです。

OpenPLC Runtime のバージョン 4.2.4 以前では、競合状態により、いずれのユーザーもコミットされる前に複数の同時リクエストが存在チェックを通過してしまい、結果として未認証の管理者アカウントが複数作られる。（原文英語）

初期セットアップ用の画面は「一度しか使われない」前提で作られることが多く、その前提が同時アクセスで崩れるという形です（本記録の整理）。

Elecbrakes の3件は、無線制御の設計がそのまま安全機能に効いてしまう例です。CISA は、悪用が成功した場合にトレーラーのブレーキの制御を奪い、ファームウェアを改変し、ブレーキランプを消し、ブレーキの条件を変え、その他の重要な安全機能を無効化できるとしています。

libumqtt は、本記録がとくに記録に残したい1件です。欠陥そのものより、「調整に応じる相手がいない」という事実のほうが運用に効きます（本記録の評価）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない**（出典1・2・3）〈重要〉—— **以下は、勧告が「悪用が成功した場合に何ができるか」として述べた内容を、 本記録が段階に並べ直したものである**（本記録の整理）。 **観測された事実ではない。** **3件の経路はまったく別で、OpenPLC と libumqtt はインターネット越し（AV:N）、 Elecbrakes は BLE の電波が届く範囲（AV:A）である。**

  1. 1. 初期侵入推定[1]
    **OpenPLC Runtime（4.2.4 以前）に対し、ユーザー登録の存在チェックを複数の同時リクエストで通過させる**（出典1）〈重要〉—— **CISA の記述は「いずれのユーザーもコミットされる前に複数の同時リクエストが存在チェックを通過してしまい、 結果として未認証の管理者アカウントが複数作られる」である**（原文英語を本記録が訳した）。 **CWE-362（共有資源の不適切な同期を伴う並行実行＝競合状態）。**
    根拠: **「In Autonomy Logic OpenPLC Runtime versions 4.2.4 and prior, a race condition allows multiple concurrent requests to pass the existence check before any user is committed, resulting in several unauthenticated admin accounts being created」**（出典1。原文英語）。 **CVSS v3.1 8.1（AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H）、v4.0 9.2。** **AC:H／AT:P は、タイミングを合わせる必要があることの反映である**（本記録の整理）。
  2. 2. 権限昇格推定[1]
    **作られるのは「管理者」アカウントである**（出典1）〈重要〉—— **CISA の表現は "several unauthenticated admin accounts"（未認証の管理者アカウントが複数）で、 権限の制約は記載されていない。** **CVSS の C:H/I:H/A:H は、機密性・完全性・可用性のすべてに高い影響があることを示す**（出典1）。
    根拠: **CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H**（出典1）。 **S:U（スコープ変更なし）であり、影響は OpenPLC Runtime の内側に留まる評価になっている**（本記録の整理）—— **ただし OpenPLC Runtime は PLC の論理を実行するソフトウェアであり、 「内側」が制御そのものであることには注意が要る**（本記録の評価）。
  3. 3. 影響（暗号化・破壊・改ざん）推定[2] [3]
    **Elecbrakes の3件については、CISA が影響を具体的に列挙している**（出典2）〈重要〉—— **「トレーラーのブレーキの制御を奪い、ファームウェアを改変し、ブレーキランプを無効化し、 ブレーキの条件を変更し、その他の重要な安全機能を無効化できる」**（原文英語を本記録が訳した）。 **libumqtt については「サービス運用妨害、メモリ破壊、情報漏えい」**（出典3）。
    根拠: **Elecbrakes の CVE-2026-125273（CWE-294）は 「リプレイ防止もコマンドの完全性保護も無い。コマンドにシーケンス番号・ノンス・セッショントークンが無く、 捕捉したコマンドは再送でき、最後のコマンドはセッションをまたいで残り続ける」** （出典2。原文英語を本記録が訳した）〈重要〉—— **「最後のコマンドが残り続ける」は、電源を切っても状態が戻らないことを意味する**（本記録の整理）。 **CVE-2026-124281（CWE-749）は「保護されていないファームウェア更新経路」である**（出典2）。

ここで注目すべきなのは、認証の実装にもパスワードの強度にも問題が無いことである（本記録の整理）。壊れたのは時間である。「ユーザーが存在しないことを確認する」処理と「ユーザーを登録する」処理の間に隙間があり、その隙間に同時のリクエストが入る。初期セットアップ用の画面は「一度しか使われない」前提で書かれやすく、その前提が同時アクセスで崩れるという形である。

PR:N（権限不要）と AV:N（ネットワーク越し）が付いている点が重要である。つまり認証を1つも持たない攻撃者が、インターネット越しに管理者になれる。AC:H／AT:P は「タイミングを合わせる必要がある」ことの反映だが、同時リクエストを投げ続けるだけで試行回数は稼げる（本記録の評価）。

本記録がこの1件を残したい理由は、欠陥の内容ではなく、この一文にある（本記録の評価）〈重要〉。

第一に、ベクターが AV:N/AC:L/PR:N である。インターネット越しに、特別な条件なしに、認証なしで到達できる。それでいて修正が存在しない。CISA の定型推奨（隔離・ファイアウォール・VPN）だけが残る。

第二に、これは「直せない」ではなく「直す相手に連絡がつかない」である。コードは公開されているのだから、技術的には修正できる。できないのは上流に反映させることで、組み込んだ側の製品ベンダーが各自でパッチを当てるか、依存を外すかしかない。

第三に、利用者は自分が影響を受けるかを判断できない。 libumqtt はライブラリである。CISA は配備地域を「全世界」とし5つの重要インフラ分野を挙げるが、どの製品に組み込まれているかは示していない。製品名で作られた資産台帳では、この勧告は検索にかからない。

ここからは本記録の作成者の評価である。

第一に、3件を並べて見えるのは「修正なし」が2種類あることである。 Elecbrakes ELBC2000 は「販売終了機で、ベンダーが対応方法を検討中」。libumqtt は「リポジトリの所有者が CISA の調整要請に応じなかった」。どちらも台帳上は同じ「修正なし」だが、前者は待てば出る可能性があり、後者は待っても出ない。多くの脆弱性管理の仕組みは、この2つを区別する欄を持っていない。結果として「修正待ち」の列に積まれ、いつまでも動かない項目として風景になる。区別が必要なのは、打ち手が変わるからである——待つのか、機器を交換するのか、用途を限定するのか、到達経路を物理的に塞ぐのか。

第二に、CISA の推奨が3件で同じ定型文であることは、読む側で補わなければならない。 3件すべてに「制御システム機器をインターネットから到達できないようにする」「ファイアウォールの背後に置いて業務ネットワークから分離する」「遠隔アクセスには VPN 等を使う」が付いている。だが Elecbrakes は AV:A（BLE の電波が届く範囲）であり、インターネットの隔離では攻撃面が減らない。勧告は読者の環境を知らないので定型になるしかない—— だから読む側が AV を見て、効く統制に翻訳してから社内に配る必要がある。定型文をそのまま転記する運用では、「隔離したので対応済み」という記録だけが残る。

第三に、OpenPLC の競合状態は、自組織の実装を見直す教材として直接使える。「ユーザーが0人のときだけ管理者を作れる」という形の初期化処理は、内部ツールでも SaaS でも珍しくない。アプリ層で存在を確認してから登録するという書き方は自然で、逐次の試験では何も起きない。同時リクエストを投げたときだけ破れる。直し方は確立していて、確認と登録を1トランザクションにまとめるか、データベースの一意制約で二重登録を弾く。問題は、試験の側が並列リクエストを投げていないことである。本件を読んだ技術者が自組織で確認すべきなのは、コードよりも試験の作りのほうだと考える。

第四に、libumqtt が示したのは「保守主体の生存」が運用リスクであることである。依存ライブラリの選定でコードの品質を見る習慣はあるが、「脆弱性が見つかったとき、直してもらえるか」を見る習慣は薄い。本件では、CISA という国家機関の調整要請に応答が無い。あわせて OpenPLC の従来の公開リポジトリも2026年4月4日にアーカイブされ、読み取り専用になっている。直近のコミット、未解決 issue の滞留、セキュリティ連絡窓口の記載、過去の CVE 対応実績——採用時に見られる指標はあり、見ていれば「窓口が無い依存」を抱える前に気づける。すでに組み込んでいるものについては、まず一覧を作るところからしかない。SBOM が必要とされる理由は、本件のように「自分が使っていることを知らない」状態にある。

CISO・経営層への示唆
  • 「修正が無い」には理由の種類があり、理由によって打ち手が変わる
    **本件では2つの「修正なし」が並んでいる**（出典2・3）〈重要〉—— **Elecbrakes ELBC2000 は「販売終了機でベンダーが対応方法を検討中」、 libumqtt は「リポジトリの所有者が CISA の調整要請に応じなかった」。** **前者は待てば出る可能性があり、後者は待っても出ない。**
    取るべき行動 **脆弱性管理の台帳に「修正の状態」を3値ではなく4値で持つ （適用済み／提供済み未適用／提供予定／提供見込みなし）。** **「提供見込みなし」に落ちた項目は、更新を待つ対象から外して 補償的統制（到達経路の遮断・機器の交換・用途の限定）の検討に移す。** **移す判断を誰がいつ行うかを、平時に決めておく。**
  • CVSS は v3.1 と v4.0 で深刻度の帯が入れ替わる。どちらで台帳を作るかを決める
    **OpenPLC の CVE-2026-126088 は v3.1 で 8.1（High）、v4.0 で 9.2（Critical）**（出典1）〈重要〉。 **逆に Elecbrakes の2件は v3.1 で 9.6（Critical）、v4.0 で 8.5（High）**（出典2）。 **同じ脆弱性が、版の選び方で緊急対応の対象から外れる。**
    取るべき行動 **社内の優先度判定にどの版の CVSS を使うかを明文化し、両方が示されている場合の扱いを決める （例: 高いほうを採る、または v4.0 を正とする）。** **決めていない場合、勧告の記載順や台帳ツールの既定値によって判定が揺れる。** **あわせて、CVSS だけでなく攻撃ベクター（AV）を優先度に反映させる。**
  • 「インターネットから隔離せよ」という定型推奨が効かない事案がある
    **Elecbrakes の3件は AV:A（隣接ネットワーク）で、BLE の電波が届く範囲の機器から成立する**（出典2）〈重要〉—— **CISA は3件すべてに同じ「インターネットから隔離する」推奨を付けているが、 本件では攻撃面が減らない**（本記録の評価）。
    取るべき行動 **勧告の推奨をそのまま社内指示に転記しない。** **AV（N／A／L／P）を見て、自組織で実際に効く統制に翻訳してから配る。** **無線（BLE・Wi-Fi・独自無線）を使う機器については、 「ネットワーク分離」とは別の軸（物理的な接近管理・ファームウェアの鮮度）で管理台帳を持つ。**
  • 安全機能に関わる更新を「利用者がアプリを開く」ことに依存させると、適用率は測れない
    **Elecbrakes の更新は「アプリを開いてファームウェア更新を適用する」形で配布される**（出典2）〈重要〉—— **ブレーキの制御に関わる修正が、利用者の任意の操作に委ねられている。** **組織として車両・トレーラーを運用している場合、適用状況を誰も把握していない状態になりうる**（本記録の評価）。
    取るべき行動 **組織で運用する無線制御機器について、ファームウェア版数の棚卸しを点検項目に入れる。** **「アプリ経由で更新」型の機器は、点検のたびに版数を記録し、 未適用の台数を数えられる形にする。** **車検・定期点検のような既存の周期行事に相乗りさせると続く。**
セキュリティ技術者への示唆
  • 初期セットアップ用のエンドポイントは「一度しか使われない」前提で書かれ、同時アクセスで崩れる
    **CVE-2026-126088 は、ユーザーの存在チェックから登録のコミットまでの間に 別のリクエストが割り込める競合状態である**（出典1）〈重要〉—— **CISA の記述は「いずれのユーザーもコミットされる前に複数の同時リクエストが存在チェックを通過してしまい、 結果として未認証の管理者アカウントが複数作られる」。** **CWE-362。パスワードの強度でも認証の実装でもなく、時間の穴である。**
    取るべき行動 **自組織の製品・内部ツールで「ユーザーが0人のときだけ管理者を作れる」形の初期化処理を探す。** **確認と登録を1つのトランザクションにまとめるか、 データベース側の一意制約（UNIQUE）で二重登録を弾く形に直す。** **アプリ層の存在チェックだけで守っている箇所は、同時リクエストで必ず抜ける。** **検証は並列リクエストを投げる試験で行う（逐次の試験では再現しない）。**
  • リプレイ防止の無いコマンド経路では、「最後のコマンドが残り続ける」ことまで考える
    **CVE-2026-125273 の記述は「コマンドにシーケンス番号・ノンス・セッショントークンが無く、 捕捉したコマンドは再送でき、最後のコマンドはセッションをまたいで残り続ける」である** （出典2。原文英語を本記録が訳した）〈重要〉—— **つまり一度注入した状態が、接続を切っても元に戻らない。**
    取るべき行動 **自組織の無線・シリアル制御経路について、 ①コマンドに単調増加のシーケンス番号かノンスがあるか、 ②セッションが切れたときに安全側の状態へ戻るか（フェイルセーフ）、 の2点を設計レビューの必須項目にする。** **②が無い機器は、攻撃だけでなく通信断でも危険側に残る。**
  • 組み込んだ OSS ライブラリの「保守主体に連絡がつくか」を、採用時の判断材料に入れる
    **CISA は libumqtt について「リポジトリの所有者は、CISA の調整要請に応じなかった」と明記している**（出典3）〈重要〉—— **あわせて OpenPLC の従来の公開リポジトリは2026年4月4日にアーカイブされ、読み取り専用になっている**（出典4）。 **コードの品質とは別に、「直してもらえるか」が運用のリスクになる。**
    取るべき行動 **依存ライブラリの採用・継続判断で、保守の生存指標を見る （直近のコミット・リリース、未解決 issue の滞留、セキュリティ連絡窓口の記載、過去の CVE 対応実績）。** **窓口が無いライブラリは、自前で修正を当てられる体制があるかを確認してから採用する。** **既に組み込んでいるものについては、まず一覧を作る——SBOM が無ければそこから始める。**
  • CVSS の AC:H／AT:P は「成功しにくい」の意味であって「安全」ではない
    **CVE-2026-126088 のベクターは AC:H（攻撃条件の複雑さが高い）／AT:P（攻撃要件あり）で、 競合状態であることの反映である**（出典1。本記録の整理）〈重要〉—— **タイミングを合わせる必要があるが、同時リクエストを投げ続けるだけで試行回数は稼げる。** **それでいて v4.0 の深刻度は Critical（9.2）である。**
    取るべき行動 **競合状態・タイミング依存の脆弱性を「AC:H だから後回し」と判定する運用になっていないか見直す。** **判定の軸は「1回で成功するか」ではなく「何回でも試せるか」にする。** **到達経路に試行回数の制限（レート制限）があるかを、あわせて確認する。**
