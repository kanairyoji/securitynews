この11月19日の更新で加わったのが SSA-272816「Java4Shell Vulnerability in Industrial Edge」（Siemens が2026年11月18日に公表）です。

  • CVE-2026-114938、CWE-122（ヒープベースのバッファオーバーフロー）
  • CVSS v3.1 8.1（CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H）
  • 影響: Industrial Edge Management Pro V1／Pro V2／Virtual の全バージョン
  • 修正: 未提供（Siemens は「修正を準備中」とする）
  • 回避策: 修正が出て適用できるまで、IEM Pro と IEM Virtual へのインターネットからの直接アクセスを遮断する—— インスタンスを停止するか、インターネット接続を無効にする

Java4Shell は、Java の Base64 デコーダに関する脆弱性です。Siemens は影響の条件として、次の4つがすべて揃うことを挙げています。

  1. 影響を受ける JVM（製品に同梱されたランタイムを含む）
  2. AVX-512 VBMI 命令に対応した Intel または AMD の x86-64 CPU
  3. 信頼できない入力が Base64.getDecoded() または getUrlDecoded() に到達する
  4. デコーダが JIT コンパイルされている

CPU の命令セットが条件に入る脆弱性です（本記録の強調）。同じソフトウェアでも、動いているハードウェアによって影響するかが変わります。

27件の一覧を眺めると、「○○2Shell」という名前が繰り返し現れます。Node2Shell が4件、PHP2Shell が3件、Broccoli2Shell が1件、そして Java4Shell が1件。これらは Siemens の製品名ではなく、上流の言語ランタイムや同梱 OSS の欠陥の名前です。1件の CVE が、Siemens の製品群に分岐して現れる構図になっています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない**（本記録の確認）〈重要〉—— **以下は、アドバイザリが述べた成立条件と影響を、本記録が段階に並べ直したものである**（本記録の整理）。 **観測された手口ではない。** **Java4Shell と Node2Shell で共通しているのは、 「外から入ってくるデータの展開・復号処理」が入口になっていることである**（本記録の評価）—— **Java4Shell は Base64 のデコード、Node2Shell は Brotli の展開。** **どちらも「中身を見る前に、形を整える」段階であり、認証の前に通過する。**

  1. 1. 初期侵入推定[3]
    **Node2Shell では、Brotli 圧縮された HTTP リクエストを送ることで、 同梱された Brotli デコーダに境界外書き込みを起こす**（出典3）〈重要〉—— **Siemens の記述は「Node.js に同梱された Brotli デコーダにおける境界外書き込みで、 遠隔の攻撃者がメモリを破壊し、任意コードを実行しうる」である**（原文英語を本記録が訳した）。 **CVSS は AV:N/AC:L/PR:N/UI:N——遠隔・条件なし・認証不要・利用者の操作不要。**
    根拠: **CVE-2026-111497、CWE-787（境界外書き込み）、CVSS v3.1 9.8／v4.0 9.2**（出典3）。 **回避策として Siemens は「TIA Administrator と UMC については、 IIS マネージャーのリクエストフィルタリング規則で Content-Encoding ヘッダ内の `br` 文字列を拒否する」ことを示している**（出典3）〈重要〉—— **入口が HTTP の Content-Encoding であることの裏付けになる**（本記録の整理）。
  2. 2. 実行推定[2]
    **Java4Shell では、JIT コンパイルされた Base64 デコーダに 信頼できない入力が到達したときに、ヒープベースのバッファオーバーフローが起きる**（出典2）〈重要〉—— **Siemens は「Industrial Edge への影響を現在も評価中である」とし、 成立には4つの条件がすべて揃う必要があるとしている。** **CVE の記述は「悪用は難しいが、認証を要さずネットワークアクセスのみで成立し、 Oracle Java SE・GraalVM for JDK・GraalVM Enterprise Edition に影響する」**（原文英語を本記録が訳した）。
    根拠: **CVE-2026-114938、CWE-122（ヒープベースのバッファオーバーフロー）、 CVSS v3.1 8.1（AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H）**（出典2）。 **成立条件に「AVX-512 VBMI 命令に対応した Intel または AMD の x86-64 CPU」が入る**〈重要〉—— **ソフトウェアの版だけでは影響の有無が決まらない**（本記録の整理）。 **「JIT コンパイルされたデコーダ」という条件は、 同じコードが解釈実行の段では安全で、最適化された後で危険になることを意味する。**
  3. 3. 影響（暗号化・破壊・改ざん）推定[2] [3]
    **いずれも任意コード実行に至りうる**（出典2・3）〈重要〉—— **Node2Shell の CVSS は C:H/I:H/A:H（機密性・完全性・可用性すべてに高い影響）、 Java4Shell も C:H/I:H/A:H である。** **対象が SCADA（WinCC）・バッチ制御（BRAUMAT／SISTAR）・ エンジニアリング基盤（TIA Administrator）・利用者管理（UMC）・ エッジ管理（Industrial Edge Management）であることが、影響の重さを決める**（本記録の整理）。
    根拠: **SSA-242944 の影響製品には SIMATIC WinCC V7/V8、WinCC Unified PC Runtime、 WinCC Runtime Professional、User Management Component（UMC）、 TIA Administrator が含まれる**（出典3）〈重要〉—— **UMC は利用者管理の部品であり、ここが落ちると 他の製品の認証基盤に影響が及びうる**（本記録の評価。Siemens は明言していない）。

Siemens はアドバイザリの中で、Java4Shell が Industrial Edge に与える影響を現在も評価中とし、成立には次の4条件がすべて揃う必要があるとしている。

ここからは本記録の作成者の評価である。

第一に、この月例群の構図は「上流1件 → 製品群へ分岐 → 分岐の先で修正が止まる」である。 Node2Shell は上流（Node.js）では1件の欠陥だが、Siemens 側では4件のアドバイザリに分かれ、その先に15製品が並び、うち12製品で修正が止まっている。Java4Shell も Java の Base64 デコーダという1点から、Industrial Edge の3製品に及んでいる。情報は上流で1つ、対処は下流で何十にも分かれるという非対称がある。上流の修正が出た時点で「直った」と読むと、下流で止まっていることが見えない——本件ではその差が30日になっている。

第二に、「名前が付く」ことの効果が上流と下流で逆に働いている。 Log4Shell 以来、○○2Shell／○○4Shell という命名は上流で広く知られるための装置として機能してきた。実際、Node2Shell・PHP2Shell・Broccoli2Shell・Java4Shell と名前が並ぶ。だが製品側のアドバイザリでは、それが「月例27件のうちの1行」になる。読者が受け取るのは「SSA-272816」という番号と英語の題名である。名前は上流の注目を集めるが、下流の優先順位付けには寄与していない（本記録の評価）。この落差を埋めるのは、ベンダーではなく利用者側の仕分けの手順しかない。

第三に、Java4Shell の成立条件は、脆弱性管理の前提を1つ崩している。「影響する版かどうか」で判定する仕組みは、ソフトウェアの版数が影響を決めることを前提にしている。だが本件の条件には CPU の AVX-512 VBMI 対応と JIT コンパイルされていることが入る。同じ版の同じ製品が、動いているハードウェアによって影響する／しないに分かれる。しかも Siemens は該当する型番を示していないので、利用者は条件を知らされても判定できない〈差異5〉。仮想環境ではホスト側の CPU と命令セットの公開設定にも依存するため、「影響しない」という判定は移設やホスト更新で無効になる。台帳に CPU の欄を持ち、判定に日付と根拠を残す——地味だが、これ以外の方法が見当たらない。

第四に、回避策の文面は検知ルールの素材として使える。 Siemens は Node2Shell の回避策として「Content-Encoding ヘッダ内の br 文字列を拒否する」ことを示した。これは言い換えれば、ベンダー自身が「この条件が来たら危ない」と教えているのと同じである。修正が無い12製品では、拒否できない経路でも「来ていること」をログに残すことはできる。回避策を読んだら「拒否する条件」を「記録する条件」に置き換えて1本ルールを作る——修正を待つ間に打てる手としては、これが最も安い。

第五に、影響製品の一覧に共通部品が混ざっているときは、見積もりの単位を変える必要がある。 SSA-242944 の対象には User Management Component（UMC）と TIA Administrator が入っている。UMC は複数の Siemens 製品が利用者管理に使う部品で、Siemens が回避策を TIA Administrator と UMC でまとめて示していることからも、単独製品ではないことが読める。認証・利用者管理・ライセンス管理・ログ基盤のような共通部品が影響対象に入っていたら、1製品の問題として扱わない。どの製品がどの共通部品に依存しているかを構成図として持っていなければ、この判断は毎回ゼロから考えることになる。

セキュリティ技術者への示唆
  • 「中身を見る前に形を整える」処理——復号・展開・デコードが、認証の前に通過する入口になる
    **Java4Shell は Base64 のデコード（`Base64.getDecoded()`／`getUrlDecoded()`）、 Node2Shell は Brotli の展開で起きる**（出典2・3）〈重要〉—— **どちらも「データの中身を検査する前に、形式を戻す」段階である。** **認証・認可の判定より前に走るため、PR:N（権限不要）になる。**
    取るべき行動 **自組織のアプリケーションで、認証前に実行される デコード・展開・復号・パースの処理を列挙する （Base64、gzip／Brotli／zstd の展開、JSON/XML のパース、画像のデコード、JWT の復号）。** **その処理に入力の大きさの上限と、失敗時の挙動（例外を飲まずに接続を切る）を入れる。** **使っていない圧縮方式は、受け付ける一覧から外す。**
  • 回避策の条件は、そのまま検知の条件として使える
    **Siemens は Node2Shell の回避策として「IIS マネージャーのリクエストフィルタリング規則で Content-Encoding ヘッダ内の `br` 文字列を拒否する」ことを示している**（出典3）〈重要〉—— **これは「`Content-Encoding: br` が来たら危ない」という条件を ベンダー自身が示しているのと同じである**（本記録の整理）。
    取るべき行動 **ベンダーの回避策を読んだら、「拒否する条件」を「記録する条件」に置き換えて 検知ルールを1本作る。** **本件なら、業務上 Brotli を受け取る必要がない経路での `Content-Encoding: br` の出現をログに残す。** **回避策を適用できない製品でも、来ていることだけは分かるようになる。**
  • ソフトウェアの版だけでは影響の有無が決まらない——CPU の命令セットが条件に入る脆弱性がある
    **Java4Shell の成立条件には「AVX-512 VBMI 命令に対応した Intel または AMD の x86-64 CPU」と 「デコーダが JIT コンパイルされていること」が含まれる**（出典2）〈重要〉—— **同じコードが、解釈実行の段では安全で、最適化された後に危険になる。** **同じ製品でも、動いているハードウェアによって影響するかが変わる。**
    取るべき行動 **資産台帳に、OS とソフトウェア版数のほかに CPU の型番（または仮想環境のホスト CPU と公開している命令セット）の欄を持つ。** **仮想・コンテナ環境では、移設やホスト更新で条件が変わりうるため、 「影響しない」という判定は有効期限付きの値として扱う。** **判定した日付と根拠を残しておけば、再判定の起点になる。**
  • 利用者管理の部品（UMC）が影響対象に入っているときは、影響の及ぶ範囲を1製品で見積もらない
    **SSA-242944 の影響製品には User Management Component（UMC）と TIA Administrator が含まれ、 いずれも修正は無い**（出典3）〈重要〉—— **UMC は複数の Siemens 製品が利用者管理に使う共通の部品である**（本記録の整理）。 **Siemens は波及の範囲を明言していないが、 共通部品であることは回避策が TIA Administrator と UMC で まとめて示されていることからも読める。**
    取るべき行動 **影響製品の一覧に共通部品（認証・利用者管理・ライセンス管理・ログ基盤）が 含まれていないかを先に確認する。** **含まれていた場合は、その部品を使っている製品を自組織の構成から洗い出し、 1製品の問題として扱わない。** **どの製品がどの共通部品に依存しているかを、構成図として持っておく。**
