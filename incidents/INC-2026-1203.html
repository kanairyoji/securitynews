INC-2026-1203Ruijie無線製品にOSコマンド注入

Ruijie Networks の無線アクセスポイント7機種に OS コマンドインジェクションの脆弱性 （CVE-2026-113347・CWE-78）があり、JPCERT/CC が開発者と調整して2026年11月19日に JVN#28897261 として公表した——Web 管理画面にログインできる攻撃者が CLI 経由で 任意の OS コマンドを実行できる。CVSS v4.0 8.6（PR:H）／v3.0 7.2。 報告は株式会社FFRIセキュリティの黒田浩平氏から IPA へ、 情報セキュリティ早期警戒パートナーシップに基づいて行われた。 Ruijie 側の公表（PSIRT-2026-092802）は2026年11月12日で、 修正ファームウェアのビルド名に「jp」が入る日本市場向けの機種が対象である

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**実際の攻撃は観測されていない（公表されていない）**（出典1・2）〈重要〉—— **以下は、両者の公表が述べた成立条件と影響を、本記録が段階に並べ直したものである**（本記録の整理）。 **観測された手口ではない。** **形は「Web 管理画面に管理者としてログインする → CLI 経由で OS コマンドを注入する → 機器の OS で任意コマンドが走る」である**（出典1・2）。 **本記録が注目するのは、この経路に権限の段差が無いことである**（本記録の評価）〈重要〉—— **Web 管理者は機器の設定を変える権限であって、機器 OS で任意コードを実行する権限ではない。** **その2つが分かれていない。**

Ruijie 側の公告（PSIRT-2026-092802・2026年11月12日）の説明はこうである。

一部の Ruijie 無線製品にコマンド実行の脆弱性がある。Web 管理画面へのログインアクセスを既に持つ攻撃者が、CLI を通じて OS コマンドを注入できる。（原文英語）

本脆弱性は認証を破るものではない（本記録の強調）。PR:H（高い権限が必要）であり、成立には管理者として Web 管理画面にログインできることが前提になる。

それでいて CVSS v4.0 は 8.6、影響は VC:H/VI:H/VA:H（機密性・完全性・可用性すべてに高い影響）である。「管理者でなければ使えないが、使えれば機器を取れる」という形になる（本記録の整理）。

ここで本記録が問題だと考えるのは、権限の段差が無いことである（本記録の評価）〈重要〉。Web 管理者は「機器の設定を変える権限」であって、「機器の OS で任意のコードを実行する権限」ではない。本来は分かれているべき2つが、本件では地続きになっている。

組み込み機器の管理 CLI は、内部でシェルコマンドを組み立てて実行する実装が多い。ping・traceroute・nslookup・tcpdump・ファームウェア更新・ログ取得といった機能である。引数に利用者の入力をそのまま連結すると、CWE-78 が成立する（本記録の整理。一般論）。ただし本件の具体的な注入箇所は公表されていない〈未確定2〉。

第一に、本件は「PR:H だから後回し」という判定に引っかかりやすい形をしている。 CVSS v3.0 では 7.2（High）で、v4.0 でも 8.6 は Critical の帯に入らない。脆弱性管理のツールが自動で付ける優先度は、おそらく「中〜高」に落ちる。だが実際に起きることは機器の OS での任意コマンド実行であり、対象は利用者の通信が通る無線アクセスポイントである。判定の軸に「その権限を持つ者が、本来できないことができるようになるか」を1つ加えるべきだと考える。 Web 管理者は設定を変える権限であって、OS でコードを走らせる権限ではない——その段差が無いことが本件の中身である。

第二に、Ruijie の回避策の内容そのものが、防壁の薄さを教えている。示されたのは「12文字以上・文字種3種類以上のパスワード」と「管理アクセスの許可 IP 一覧」の2点だけである。ベンダー自身が、認証と到達制御以外に打てる手を示していない。ここから読み取るべきなのは、面的に設置された機器の管理パスワードが全台共通になっていないかという問いである（本記録の評価。本件の公表には無い一般論）。アクセスポイントは1組織に数十〜数百台が入る。共通パスワードは、1台から漏れた時点で全台が落ちる。長さを12文字に伸ばしても、この性質は変わらない。本件に対して最も安く最も効くのは、許可 IP 一覧で管理画面への到達を絞ることである。しかも副産物として、一覧の外からの試行が拒否として記録に残る——注入箇所が非公開である以上、「何が来たら危ないか」では検知が作れない。「そこに来られること自体が異常」という形なら作れる。

第三に、本件は「JVN とベンダー公告を両方読まないと情報が揃わない」実例である。 JVN には CVSS v4.0 と報告者と報告の枠組みがあり、機種名が無い。Ruijie には 7機種と影響版と修正ビルド名と回避策があり、報告者と v4.0 が無い。日本語で読める JVN だけを見た読者は、「自社の機器が該当するか」を判断できない。これは JPCERT/CC の不備ではなく役割分担の結果だが、実務としては「JVN を見たらベンダー公告も開く」を手順に1行として入れるしかない。

第四に、修正ビルド名に jp が入っていたことは、記録として残す価値があると考える。 [xiyuan-jp-ma2610]、[xiyuan-jp-ap180v4]、ダウンロード先は www.ruijie.co.jp。海外ベンダーの製品でも、日本市場向けに別系統のファームウェアが供給されていることがある。これが意味するのは、海外のニュースで「このベンダーの製品が直った」と読んでも、自社に入っている国内向けの版が同じ時期に直っているとは限らないということである（本記録の評価）。本記録はこの推定を明言された事実としては扱わない〈差異3〉—— Ruijie も JVN も、対象が日本市場向けであることを述べていない。ただし、国内向けの版の系統を把握しているかという問いは、海外製ネットワーク機器を使う組織すべてに当てはまる。

波及の構造

事案の構造を図にしたものです。数値は公表値に基づきます。
認証を破る脆弱性ではない——Web 管理者という設計上の権限が、そのまま機器 OS の任意コマンド実行まで通る
CVE-2026-113347 の経路である。攻撃者（layer 0）は、まず Ruijie 無線アクセスポイントの Web 管理画面（layer 1）に管理者としてログインする必要がある（PR:H）。 本脆弱性は認証を破るものではなく、Ruijie が示した回避策2点 （12文字以上・文字種3種類以上のパスワード／管理アクセスの許可 IP 一覧）が示すとおり、 実務上の防壁はこの認証と到達制御だけである。 ログインできた攻撃者は、管理機能の CLI 経由で OS コマンドを注入できる（layer 2・CWE-78）。 どの入力箇所かは公表されていない。 結果として機器の OS 上で任意のコマンドが実行され（layer 3）、 CVSS は機密性・完全性・可用性のすべてに高い影響があると評価している （v4.0 8.6／v3.0 7.2）。 対象は無線アクセスポイント7機種（RG-MA2610-AC／-PE、RG-MA2810、 RG-AP180-AC V4／-PE V4、RG-MA3511-AC／-PE）で、修正ビルドが3系統に分かれている。 公表はベンダー（2026年11月12日・PSIRT-2026-092802）が先で、 JPCERT/CC の JVN#28897261（11月19日）が7日後である。 報告は株式会社FFRIセキュリティの黒田浩平氏から IPA へ行われ、JPCERT/CC が調整した。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**JVN は機種名を載せず「影響を受ける製品は多岐に渡ります。 詳細については『ベンダ情報』を参照してください」とした**（出典1。T2）〈重要〉—— **一方 Ruijie の公表には7機種と各ファームウェア版、修正ビルド名が列挙されている**（出典2）。部分的に機能
CISO・経営層への示唆
  • 「管理者権限が必要」は深刻度を下げる理由にならない——Web 管理者から機器 OS まで段差が無い
    **本件は PR:H（高い権限が必要）でありながら、CVSS v4.0 は 8.6、 VC:H/VI:H/VA:H（機密性・完全性・可用性すべてに高い影響）である**（出典1）〈重要〉—— **JVN の表現は「管理者権限を有する攻撃者によって、任意の OS コマンドを実行される可能性があります」。** **Web 管理者は「設定を変える権限」であって「機器 OS で任意コードを実行する権限」ではない—— その2つが分かれていないのが本件である**（本記録の評価）。
    取るべき行動 **脆弱性の優先度判定で「PR:H だから後回し」という運用になっていないか見直す。** **判定の軸に「その権限を持つ者が、本来できないことができるようになるか」を1つ加える。** **ネットワーク機器・複合機・監視カメラ・UPS のような「管理画面を持つ箱」については、 管理画面への到達経路を資産として台帳に持つ（誰がどこから到達できるか）。**
  • ベンダーの公表と日本語の周知の間には日数差がある。ベンダー側を直接購読する
    **Ruijie の公表は2026年11月12日、JVN の公表は11月19日で、差は7日である**（出典1・2。本記録の算出）〈重要〉—— **本件は PR:H なので7日の遅れが即座に被害に結びつく性質ではないが、 同じ経路で未認証の脆弱性が出たときには、この7日が効く**（本記録の評価）。
    取るべき行動 **自組織が使っているネットワーク機器のベンダーについて、 セキュリティ告知の配信（RSS・メール）を機器の調達時に登録する運用にする。** **登録先を機器台帳の欄として持ち、機器を導入した担当が登録する—— セキュリティ部門が後から探すと必ず漏れる。** **JVN・JPCERT/CC は「見落としを拾う二重化」として位置づけ、一次の入力源にしない。**
  • 回避策が「パスワードを長くする」であるときは、防壁が1枚しかないと読む
    **Ruijie が示した回避策は「12文字以上・文字種3種類以上のパスワード」と 「管理アクセスの許可 IP 一覧」の2点である**（出典2）〈重要〉—— **ベンダー自身が、認証と到達制御以外に打てる手を示していない。** **多数のアクセスポイントで管理パスワードが共通になっている環境では、 1台から漏れた時点で全台が落ちる**（本記録の評価。本件の公表には無い一般論）。
    取るべき行動 **面的に設置する機器（アクセスポイント・スイッチ・カメラ）について、 管理用の認証情報が全台共通になっていないかを確認する。** **共通である場合は、①到達経路を許可 IP 一覧で絞る、 ②集中管理の仕組みに寄せる、③機器ごとに異なる認証情報にする、のいずれかを選ぶ。** **①は最も安く、本件の PR:H という性質に対して最も効く。**
  • 日本の届出制度を経た公表は、ベンダー側の公表に無い情報を持っていることがある
    **JVN は報告者（株式会社FFRIセキュリティ 黒田浩平氏）と 情報セキュリティ早期警戒パートナーシップという枠組みを明記している**（出典1）〈重要〉—— **一方 Ruijie の公告は「外部の研究者によって報告された」とするのみで、氏名・所属が無い**（出典2）。 **逆に機種名と修正ビルド名は Ruijie 側にしかない。**
    取るべき行動 **海外ベンダーの製品について JVN の公表を見たときは、 ベンダー側の公告も必ず開く——どちらか一方では情報が揃わない。** **社内の脆弱性管理の手順に「JVN を見たらベンダー公告も確認する」を1行として入れる。** **機種・版・修正ビルドはベンダー側、報告経路・CVSS の複数版・日本語の影響説明は JVN 側にある。**
セキュリティ技術者への示唆
  • 管理 CLI から OS シェルへ抜ける経路は、組み込み機器の定番の弱点である
    **Ruijie の記述は「Web 管理画面にログインできる攻撃者が、 CLI 経由で OS コマンドを注入できる」である**（出典2。原文英語を本記録が訳した）〈重要〉—— **分類は CWE-78（OS コマンドインジェクション）**（出典1）。 **組み込み機器の管理 CLI は、内部でシェルコマンドを組み立てて実行する実装が多く、 引数に利用者入力をそのまま連結すると注入が成立する**（本記録の整理。一般論）。
    取るべき行動 **自組織が開発している機器・ツールで、管理機能が外部コマンドを呼んでいる箇所を列挙する （ping・traceroute・nslookup・tcpdump・ファームウェア更新・ログ取得・バックアップ）。** **シェルを経由しない呼び出し（引数を配列で渡す形）に直すか、 入力を許可文字の一覧で検証する。** **文字のエスケープで対処する実装は、逃げ道が残りやすいので避ける。**
  • 「どこから注入できるか」が公表されていない脆弱性は、検知ではなく到達制御で止める
    **Ruijie も JVN も、具体的な注入箇所（CLI のどのコマンド・どの入力欄か）を示していない** （出典1・2）〈未確定2〉〈重要〉—— **注入箇所が分からないと、正常な管理操作と注入を区別する条件が作れない。**
    取るべき行動 **注入箇所が非公開の脆弱性については、検知ルールを作ろうとせず、 管理画面への到達を許可 IP 一覧で絞る（Ruijie の回避策②）。** **副産物として、一覧の外からの試行が拒否として記録に残る。** **「何が来たら危ないか」が分からない場合でも、 「そこに来られること自体が異常」という形なら検知が成り立つ。**
  • 修正の適用を「自動更新が有効だから大丈夫」と仮定しない。版数を実際に数える
    **Ruijie は配布経路の1つとして「自動更新が有効な機器には更新の案内が出る」としているが、 どの機種・どの構成で有効なのかは示していない**（出典2）〈未確定3〉〈重要〉—— **アクセスポイントは「設置したら触らない」運用になりやすく、 数年前の版のまま置かれている台が出る**（本記録の評価）。 **さらに修正ビルドの公開日が示されていないため、 「いま入っている版が修正後か」をビルド名の一致で判断するしかない**〈未確定6〉。
    取るべき行動 **アクセスポイント・スイッチの版数を機械的に収集する手段を1つ作る （管理コントローラの一覧出力、SNMP、設定バックアップからの抽出のいずれか）。** **収集した版数を、ベンダーが示した修正ビルド名と突き合わせる。** **「全台更新済み」と言うために、台数を数えられる形にしておく。**
  • アクセスポイントは「こちらから通信を始めない機器」である。その性質を検知に使う
    **本件の影響は機器 OS での任意コマンド実行であり、 CVSS の評価上は当該機器の内側に留まる（S:U／SC:N・SI:N・SA:N）**（出典1）〈重要〉—— **ただし無線アクセスポイントは利用者の通信が通る機器であり、 「内側」の意味は小さくない**（本記録の評価）。 **公表された検知手段は無い。**
    取るべき行動 **アクセスポイントからの外向き通信（管理コントローラ・NTP・DNS・ ファームウェア配布元以外への通信）を既定で拒否し、拒否をログに残す。** **アクセスポイント群を1つのネットワークセグメントにまとめ、 そのセグメントからの外部到達を宛先の許可制にする。** **本件固有の対策ではないが、注入箇所が非公開である以上、 「出ていく側」で気づく構えのほうが現実的である。**
