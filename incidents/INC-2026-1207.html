INC-2026-1207チームスピリット 開発サーバから28,824件

チームスピリットのソフトウェア開発用サーバに第三者が不正ログインし、 そのサーバに保管されていた認証情報を使って同社が利用するクラウド環境からデータを取得した。 流出した個人情報は重複を除き28,824件で、要配慮個人情報35件を含む。 同社は未知の脆弱性ではなく「開発用サーバにおける設定と情報管理の不備が重なったこと」が原因としている。 2026年10月27日に確認して同日中にサーバを停止、10月30日に個人情報保護委員会へ報告し、11月6日に公表した。 その後11月16日に、利用企業の報告・通知の要否を「不要」と案内していた当初の記載を不適切だったとして訂正している

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及続報が続いている日本の組織が当事者設定不備認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年11月6日（公表。11月9日に追記、11月16日に訂正） 最終更新: 2026年11月20日

2026年11月6日、株式会社チームスピリットは、同社が利用するソフトウェア開発用サーバへの不正アクセスと情報流出を公表した（出典1）。

形はこうである。2026年10月27日、第三者が同社の開発用サーバに不正ログインし、当該サーバに保管されていた認証情報を用いて、同社が利用するクラウド環境からデータを取得した。同社は同日中にサーバを停止し、外部からの接続経路を遮断している。

原因は公表されている（出典1）。

本件は未知の脆弱性によるものではなく、当社が開発用に運用していたサーバにおける設定と情報管理の不備が重なったことが原因です。

流出した個人情報は重複を除き28,824件で、要配慮個人情報35件を含む。対象は3つに分かれる（出典1）。

  1. 「TeamSpirit」を契約している、または過去に契約していた顧客企業の一部 ——担当者・利用ユーザーの氏名・メールアドレス・ログインID・識別番号・アカウント情報、問い合わせ・依頼の記録の一部、顧客企業の従業員の勤怠記録の一部、企業に関する情報
  2. 資料請求・問い合わせ・セミナー申込等をした人の一部 —— 識別番号、会社名等
  3. 同社の従業員および退職者 —— 氏名・社員番号・業務用メールアドレス・入社日・退職日・誕生日（月日）、社内システムのユーザー名・ID・アカウント情報、業務管理システムの記録

本番環境の勤怠・工数データへの不正アクセスは確認されていないとされている。

本記録が最も重く見るのは、11月16日の訂正である（本記録の評価）〈重要〉。同社は当初、利用企業側の報告・通知の要否について「不要」とする案内を出していた。これを11月16日に「不適切だった」として訂正し、「各利用企業がご自身の判断で報告等を行うものとし、判断に必要な情報は問い合わせ窓口で提供する」という形に変えた（出典1）。

SaaS 提供者が、利用企業の法令上の判断を代わりに下そうとして、取り下げたという経緯である。利用企業の側から見れば、委託先の「報告不要」という案内を自組織の判断の代わりにしてはいけないという実例になった（本記録の評価）。

    **二次被害の監視の具体について公表に記載が無い**（本記録の確認）〈重要〉—— **流出項目に「ログインID」「社内システムのユーザー名・ID・アカウント情報」が 含まれる事案である**（出典1）—— **同社は「流出が疑われる認証情報の無効化」をおおむね完了したとしているが、 利用企業側の TeamSpirit アカウントについての扱いは明示されていない**（本記録の確認）。 **同社は「一般の利用者にパスワード変更を求めていない」としている**（出典1）〈重要〉—— **これは「ログインID は出たがパスワードは出ていない」という判断に基づくとみられるが、 公表に根拠の説明は無い**（本記録の推定）。
    侵入を防げた利用企業側で TeamSpirit の多要素認証を有効化し、ログインを許可する IP アドレス範囲を見直す（提供者が推奨している対策）
    影響を限定できた提供者名・担当者名を騙るメール・電話・SMS への注意を、経理・人事・情報システムの担当者へ名指しで周知する
    影響を限定できた自社の従業員の勤怠記録が含まれるかを提供者の窓口へ照会し、本人通知と当局報告の要否を自社で判断する

    対応の評価

    評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
    判断評価評価の根拠と留保
    **原因を「未知の脆弱性によるものではなく、 当社が開発用に運用していたサーバにおける設定と情報管理の不備が重なったこと」と 自ら述べた**（出典1。T4）〈重要〉—— **一方、攻撃手法の詳細は非公表としている。**機能した
    **当初、利用企業側の個人情報保護法上の報告・通知を「不要」と案内していたが、 2026年11月16日にこれを不適切だったとして取り下げ、 「各利用企業がご自身の判断で報告等を行うものとし、 判断に必要な情報は問い合わせ窓口で提供する」形に変えた**（出典1。T6）〈重要〉—— **公表（11月6日）から10日後の訂正である。**不十分
    **流出が疑われる認証情報の無効化をおおむね完了させた一方、 一般の利用者にはパスワード変更を求めていない（個別連絡を受けた人を除く）**（出典1）〈重要〉—— **かわりに多要素認証の設定と、ログインを許可する IP アドレス範囲の見直しを推奨している。**部分的に機能
    CISO・経営層への示唆
    • 委託先の「報告・通知は不要です」という案内を、自組織の判断の代わりにしない
      **本件の提供者は当初、利用企業側の個人情報保護法上の報告・通知を 「不要」と案内していた**（出典1）〈重要〉—— **これを2026年11月16日に「不適切だった」として取り下げ、 「各利用企業がご自身の判断で報告等を行うものとし、 判断に必要な情報は問い合わせ窓口で提供する」形に変えた。** **公表（11月6日）から10日後である**（本記録の算出）—— **その10日間、誤った案内が有効だった。** **報告義務の主体は各事業者であり、委託先が代わりに下せる判断ではない**（本記録の評価）〈重要〉—— **本件は要配慮個人情報35件を含み、顧客企業の従業員の勤怠記録の一部が出ている。**
      取るべき行動 **委託先からインシデントの通知を受けたとき、 「自社の報告・通知の要否」は必ず自社の法務・個人情報保護の担当で判断する手順にする （委託先の見解は資料の1つとして扱う）。** **委託先へ照会する内容を定型化しておく—— ①自社のデータが含まれるか、②含まれる項目、③件数、 ④要配慮個人情報の有無、⑤本人を特定できる情報が含まれるか。** **これらは本人通知と当局報告の要否を決める材料である。** **委託契約に「インシデント時に上記の情報を提供する義務」を入れる。**
    • SaaS の「本番環境は無事」を、自社データが無事であることと読み替えない
      **本件では「本番環境の勤怠・工数データへの不正アクセスは確認されていない」とされている**（出典1）。 **しかし同時に、「サービスの提供・維持のために同社が保有していた、 顧客企業の従業員の勤怠記録の一部」が流出している**（出典1）〈重要〉—— **本番のデータベースではなく、 開発・運用の過程で別の場所に置かれていた控えが対象になったとみられる**（本記録の推定）。 **侵害されたのは開発用サーバと、提供者が利用するクラウド環境である。** **利用企業が契約で意識しているのは「本番環境」だけであることが多い**（本記録の評価）。
      取るべき行動 **重要な SaaS について、提供者が自社データを本番環境以外のどこに置くかを確認する （開発・検証環境へのコピー、障害解析のための抽出、バックアップの保管先、 外部委託先への提供）。** **委託先管理の様式に「本番環境以外での自社データの取扱い」の欄を設ける。** **確認できない場合は、「見えていない範囲がある」としてリスク台帳に明示する （「本番は守られている」で止めない）。**
    • 開発環境を本番と同じ重さで管理しているかを、資産の単位で点検する
      **本件の原因は「開発用に運用していたサーバにおける 設定と情報管理の不備が重なったこと」である**（出典1）〈重要〉—— **①外部から不正ログインが成立する設定、 ②そのサーバにクラウド環境へ到達できる認証情報が保管されていたこと。** **開発環境は「本番ではない」という理由で管理の対象から外れやすい**（本記録の評価。一般論）—— **しかし本件では、開発用サーバが「鍵束」として機能し、 結果として28,824件の個人情報が出ている。**
      取るべき行動 **開発・検証用のサーバとクラウド環境を、本番と同じ資産台帳に載せる （所有者・用途・到達範囲・置かれている認証情報・廃棄の予定）。** **開発環境から到達できるクラウドの権限を、本番データを読めない範囲に限定する （権限の境界を環境ごとに分ける）。** **「開発環境だから」という理由での例外（多要素認証の免除、 外部公開の許可、長期有効な鍵の配置）を一覧にし、期限を付けて潰す。**
    • 訂正は、黙って差し替えずに「不適切だった」と書いて残す
      **本件の提供者は、当初の案内を11月16日に「不適切だった」として訂正し、 その経緯を公表ページに残している**（出典1）〈重要〉—— **当初の記載を黙って削除して差し替えていない**（本記録の確認）。 **訂正の内容は重い（報告義務の要否という法令上の論点である）が、 訂正の仕方は評価できる**（本記録の評価）—— **読者は「何がどう変わったか」を追える。**
      取るべき行動 **自組織の公表ページを更新するときは、更新日と更新内容を本文に残す （同じ URL を黙って書き換えない）。** **誤った案内を訂正する場合は、「当初の記載は不適切だった」と明記する—— 新しい記載だけを置くと、読者は自分が古い前提で動いていたことに気づけない。** **誤った案内が有効だった期間を自社でも記録しておく （本件では10日間。その間の相手方の行動に影響している）。**
    セキュリティ技術者への示唆
    • 開発用サーバに長期有効な認証情報を置かない——サーバを取られても鍵は取られない構成にする
      **本件の核はここである**（本記録の評価）〈重要〉—— **公表の表現は「当該サーバに保管されていた認証情報を用いて、 同社が利用するクラウド環境からデータを取得した」である**（出典1）。 **攻撃者は開発用サーバの中身を狙ったのではなく、 そこに置かれていた鍵を取って別の場所へ移動している。** **対応として同社は「流出が疑われる認証情報の無効化」を行っており**（出典1）、 **「疑われる」という複数形の表現から、複数の認証情報が置かれていたとみられる**（本記録の推定）。
      取るべき行動 **開発用サーバのファイルシステム上に長期有効な認証情報 （アクセスキー、APIキー、接続文字列）を置かない。** **秘密情報の保管サービス（シークレットマネージャ）から短期の資格情報を 実行時に取得する構成にする——サーバを取られても、取られるのは短期の資格情報だけになる。** **既存のサーバとリポジトリを機械的に走査して混入した認証情報を洗い出し、 検出したものは発見時点で失効させる（「使っていないから大丈夫」としない）。**
    • 開発環境の資格情報で本番相当データを読める構成になっていないかを、権限の側から確認する
      **本件では、開発用サーバの認証情報でクラウド環境のデータが取得されている**（出典1）〈重要〉—— **「本番環境の勤怠・工数データへの不正アクセスは確認されていない」とされる一方、 顧客企業の従業員の勤怠記録の一部は流出している**（出典1）—— **つまり本番のデータベース以外の場所に、同等の中身があった**（本記録の推定）。 **権限が環境をまたいで通っていたことを示す**（本記録の評価）。
      取るべき行動 **クラウドの権限設計を環境（開発・検証・本番）の単位で分け、 開発環境の資格情報から本番相当のデータストアへ到達できないことを試験で確認する （設定の確認ではなく、実際に試して拒否されることを見る）。** **データの持ち出し経路（オブジェクトストレージの一括取得、 データベースのダンプ、スナップショットの共有）を環境別に洗い出す。** **クラウドの API 呼び出しログを環境別に収集し、 「開発環境の資格情報による本番相当データへの読み取り」を警報条件にする—— 通常は起きない組み合わせである。**
    • 本番以外に置いた「サービス提供・維持のためのデータ」を棚卸しする
      **本件で流出したのは「サービスの提供・維持のために同社が保有していた、 顧客企業の従業員の勤怠記録の一部」である**（出典1）〈重要〉—— **本番のデータベースではない場所に、顧客の個人データがあった。** **障害解析のための抽出、移行の検証用のコピー、 問い合わせ対応のための控えといった経路が想定される**（本記録の推定。公表には無い）—— **いずれも「一時的に」始まり、消されずに残る**（本記録の評価。一般論）。
      取るべき行動 **本番データベース以外に顧客の個人データが存在する場所を、 経路ごとに洗い出す（障害解析用の抽出、検証環境へのコピー、 問い合わせ対応の添付ファイル、ログに出力された値）。** **各経路に保持期間と削除の担当を割り当て、自動削除を入れる。** **削除できない経路については、本番と同じ保護水準（暗号化・到達制御・監査）を適用する。** **新しい抽出を作るときに期限を必須入力にする（期限の無い抽出を作れないようにする）。**
    • 開発環境のログイン記録を本番と同じ水準で収集する
      **本件では、どのように不正ログインに気づいたかが公表されていない**（出典1。本記録の確認）〈未確定6〉—— **自社の監視なのか、クラウド事業者からの通知なのか、外部からの指摘なのか。** **不正ログインが始まった時期も公表されていない**（本記録の確認）—— **したがって滞留期間が算出できない**（本記録の明示）。 **開発環境のログが本番と同じ水準で残っていれば、 開始時期も経路も特定しやすい**（本記録の評価。一般論）。
      取るべき行動 **開発・検証環境のログイン成功・失敗、特権操作、 外部からの接続元を本番と同じ収集基盤へ送る。** **業務時間外のログイン成功と、未知の接続元からの接続を警報条件にする。** **開発環境の管理・接続の面を外部に公開せず、VPN または許可 IP 経由に限定する—— 公開されていなければ、そもそも外部からの不正ログインは成立しない。**

    自組織に当てはまるか

    該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
    観点自社に当てはまるか該当する場合に何が起きうるか
    委託・第三者部品□ 勤怠・工数・給与・経費などの SaaS を利用しており、提供者が本番環境以外のどこに自社データを置くかを確認していない**本件では「本番環境の勤怠・工数データへの不正アクセスは確認されていない」とされる一方、 「サービスの提供・維持のために同社が保有していた、 顧客企業の従業員の勤怠記録の一部」が流出している**（出典1）〈重要〉—— **利用企業が契約で意識しているのは本番環境だけであることが多い**（本記録の評価）。
    体制・契約□ 委託先からインシデントの通知を受けたとき、自社の報告・通知の要否を委託先の見解に依拠して決めている**本件の提供者は当初「報告・通知は不要」と案内し、 10日後にこれを不適切だったとして取り下げた**（出典1。本記録の算出）〈重要〉—— **報告義務の主体は各事業者であり、委託先が代わりに下せる判断ではない**（本記録の評価）。
    認証・認可□ 開発・検証用のサーバやリポジトリに、長期有効な認証情報（アクセスキー・APIキー・接続文字列）が置かれている**本件は「当該サーバに保管されていた認証情報を用いて、 クラウド環境からデータを取得した」形である**（出典1）〈重要〉—— **開発用サーバが踏み台ではなく鍵束として機能している**（本記録の評価）。
    システム構成□ 開発環境の資格情報から本番相当のデータストアへ到達できる（権限の境界が環境ごとに分かれていない）**本件では開発用サーバの認証情報でクラウド環境のデータが取得され、 結果として顧客企業の従業員の勤怠記録の一部が出ている**（出典1）〈重要〉—— **権限が環境をまたいで通っていたことを示す**（本記録の推定）。
    運用・監視□ 開発・検証環境のログイン記録や特権操作を本番と同じ水準で収集しておらず、外部から管理面に到達できる**本件ではどのように気づいたかも、不正ログインの開始時期も公表されていない**（出典1）〈未確定6〉—— **ログの水準が低いと、範囲の確定も原因の特定も遅れる**（本記録の評価。一般論）。
    データの保持□ 障害解析・移行検証・問い合わせ対応のために本番データから作った抽出・コピーに、保持期間と削除の担当が割り当てられていない**本件で流出したのは「サービスの提供・維持のために保有していた」勤怠記録の一部である**（出典1）〈重要〉—— **「一時的に」始まった抽出が消されずに残る経路は、 本番の保護を素通りする**（本記録の評価。一般論）。
