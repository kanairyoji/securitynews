さらに重要なのは、攻撃者が脆弱性を知った時期はもっと前であることだ。Mandiant は 「ARMORY CASTLE は CVE-2026-59309 の公表（2026年7月29日）より前にCVE-2026-123890 を知っていた証拠がある」 としている（出典5。原文英語）〈重要〉。傍証として示されているのは、BONESAW のビルドタイムスタンプが2026年7月13日（59309 公表の16日前）であることと、59309 を修正済みの vCenter に対して BONESAW が成功していることである（出典2・5）。ただし Mandiant 自身が、Go のビルドメタデータは改変可能だと注記している（出典2）〈差異3〉。

読み取るべきは、同じ製品の認証回避が短期間に2件続き、1件目の修正が2件目を止めなかったという事実である（本記録の評価）—— 「7月に当てたから大丈夫」は成り立たなかった。 Rapid7 も、59309 の修正を受けたシステムにも新しい更新が必要だと明示している（出典3）。

ベンダー勧告には悪用の記載が無い——勧告だけを読む運用では緊急度を測れない未確定事項出典 [1] [2] [4] [5]

2026年11月19日に出た2つの公表は、同じ脆弱性について別のことを書いている。

  • Broadcom（VMSA-2026-0009）: CVSS 9.8・回避策なし・緊急の更新。実際の悪用に関する記載は無い（出典1。本記録が取得して確認）

SecurityWeek も 「Broadcom の勧告は in-the-wild の悪用に触れていない」と記している（出典5）。BleepingComputer も「Broadcom は悪用を確認していないが、Mandiant の研究者が攻撃を文書化した」と書いている（出典4）。理由は公表されていない〈未確定3〉。

この差は運用に効く（本記録の評価）〈重要〉。脆弱性管理の優先度を「ベンダー勧告のスコアと記述」で決めている組織は、本件を「CVSS 9.8 の通常のクリティカル」として扱うことになる。一方、実態は国家支援とみられるアクターが2か月以上使っていたゼロデイであり、更新だけでなく侵害の点検が必要な事案である（出典2・5）。

本DBがこの齟齬を記録するのは、どちらかが誤りだからではない（本記録の明示）——ベンダーは自ら確認した事実しか書かない方針を取ることがあり、調査会社は自ら調べた事実を書く。読む側が両方を突き合わせないと、緊急度を測り損なう構造になっている。

認証回避のあとに起きたのは鍵の窃取で、パッチを当てても偽造トークンは残る評価・解釈出典 [2] [4] [5]

Mandiant が示した段階は次のとおりである（出典2・4）。

  1. BeyondTrust Remote Support のゼロデイ（CVE-2026-102764）で初期侵入
  2. 内部の Linux アプライアンスに Webシェル（SLIMSAVAGE・CAGEMATCH）を置き、root へ昇格、内部ネットワークを探索して VMware 基盤を探す
  3. BONESAW で CVE-2026-123890 を悪用し、ディレクトリデータベース（data.mdb／LMDB）・VMware STS の SAML 秘密署名鍵を取り出し、SSO の管理者アカウントを作成
  4. SAWSNAKE が SAML アサーションを偽造（Golden SAML）し、多要素認証を回避して任意の利用者になりすます
  5. BEARBONES（Dropbear 由来）・LAZYBONES（Slack を C2 に使う）で永続化
  6. vCenter の内部マスター暗号鍵と PostgreSQL のパスワードを奪い、ESXi ホストへ移り、ゲスト仮想マシンからNTDS・SYSTEM・SECURITY・dns を抜き出す

この並びで重要なのは、脆弱性の悪用が「入口」でしかないことである（本記録の評価）〈重要〉。奪われたのは鍵——SAML 署名鍵とマスター暗号鍵である（出典2）。署名鍵が外に出た後は、脆弱性を修正しても偽造トークンは有効なままになる（本記録の評価）。Mandiant の CTO が 「パッチの適用と、侵害の証跡の調査の両方を行うべき」と述べているのは、この構造を指している（出典5。原文英語を訳出）。

仮想化基盤は、ゲストの中身まで到達できる位置にある（本記録の整理）——本キャンペーンは ESXi 経由で Active Directory のデータベースを持ち出している。vCenter の侵害は「管理ツールの侵害」ではなく「全系の侵害」として扱うのが妥当である（本記録の評価）。

サポートが切れた vCenter 7.0 には公開修正が無く、BONESAW は 7.x でも動く対策・注意喚起出典 [1] [3] [4] [5]

修正版の一覧で、vCenter 7.0 の欄だけが版番号ではない（出典1・3）。

「vCenter 7.0 — 延長サポート契約がある場合はブロードコムのサポートに問い合わせ」（出典1。原文英語を訳出）

7.0 は2025年10月に一般サポートが終了している（出典5）。一方、Mandiant によれば BONESAW は vCenter 7.x と 8.x のアプライアンスに対して動作する（出典5）〈重要〉。

つまり、延長サポート契約を結んでいない 7.0 の利用者には、適用できる修正が存在しない状態である（本記録の整理）〈未確定4〉。この場合に残る手は、①管理面へのネットワーク到達性を絞る（出典1・4。既定拒否と管理ポートの許可リスト化）、②侵害の点検（出典2）、③更新可能な版への移行計画の前倒し（本記録の推奨）である。

本記録がこれを独立の節に立てるのは、国内でもサポート切れの版が残りやすい領域だからである（本記録の評価）——仮想化基盤は停止調整が難しく、更新が後回しになる。「クリティカルな認証回避に、修正が提供されない版がある」という状態は、移行の優先度を決める材料になる。

被害組織は公表されておらず、「誰が狙われたか」から優先度を決められない被害規模・影響範囲出典 [2] [4] [5]

Mandiant の分析には、被害組織の業種・国・件数が無い（出典2。本記録の確認）〈未確定1〉。報じられているのは、Mandiant の CTO が「複数のインシデントを調査した」と述べたことまでである（出典5）。日本の組織が被害を受けたという公表も確認できない（本記録の確認）〈未確定2〉。

この状態では「自社は対象か」を被害者像から判断できない（本記録の評価）。判断できるのは構成だけである—— 脆弱な版の vCenter があり、ネットワークから到達できるなら対象である（出典1・3）。

本キャンペーンの入口はインターネット越しの vCenter ではなく、別のゼロデイで内部に入ったうえでの内部からの到達だった（出典2・4）〈重要〉。「vCenter は外部公開していないから対象外」という切り方は成り立たない（本記録の評価）——リモートサポート製品・VPN・境界のアプライアンスが入口になれば、内部の vCenter は到達可能な位置にある。

ARMORY CASTLE は「中国関連とみられる」諜報アクターとされ、旧称 UNC5221・別名 Warp Panda である（出典2・4・5）—— Citrix NetScaler や Ivanti Connect Secure のゼロデイ悪用で知られる（出典4）。帰属の根拠は本記録が確認した範囲では示されていない〈未確定7〉ため、本記録は「とみられる」の確度をそのまま保持する。

ここが本事案でいちばん実務に効く対比である（本記録の評価）〈重要〉—— 悪用に触れていないのは Broadcom の勧告だけで、CISA（KEV への収載そのものが「悪用の証拠がある」という宣言である）とカナダ Cyber Centre は明示的に書いている。 ベンダー勧告だけを緊急度の判断材料にしている運用は、本件で「クリティカルだが悪用は不明」という誤った像を持つことになる ——〈差異1〉で記録した沈黙は、2日後も Broadcom 側では埋まっていない。

Cyber Centre の勧告には、もう一つ実務的な利点がある（本記録の整理）。対象製品の一覧に、Broadcom の勧告からは読み取りにくい分岐が明示されている。

  • VMware vCenter 8.0（8.0 U3m 未満）、および 7.0
  • VMware Cloud Foundation vCenter 5.x（5.2.5 未満）

通信事業者向けの Telco Cloud 系が対象に入っている点は、仮想化基盤の棚卸しで見落としやすい（本記録の評価）—— 「vCenter」という名前で台帳を引くと、Telco Cloud Platform の一部として入っている vCenter は出てこないことがある。

影響を受けたシステム
名称: VMware vCenter Server（VMware Directory Service／vmdird）　ベンダー: Broadcom（VMware）　CVE番号: CVE-2026-123890　バージョン: **影響: VMSA-2026-0009 で「fixed」とされた版より前のすべての vCenter** （出典1）。 **修正: VMware Cloud Foundation／vSphere Foundation 9.1.x → 9.1.1.0200、 9.0.x → 9.0.2.0200、vCenter Server 8.0 → 8.0 U3m、 VMware Cloud Foundation 5.x → 5.2.5、 Telco Cloud Platform／Infrastructure → 8.0 U3m（KB463116）**（出典1・3）。 **vCenter 7.0 は延長サポート契約者が Broadcom サポートへ問い合わせとされ、 公開修正は無い**（出典1・3）〈未確定4〉。 **CVE-2026-59309 の修正を適用済みのシステムも、新しい更新が必要である** （出典3）〈重要〉。　概要: **VMware Directory Service における認証回避の脆弱性**（出典1）—— **CVSSv3.1 基本値 9.8・重要度クリティカル、CWE-288（代替経路・代替チャネルに よる認証回避）**（出典1・3）。 **Mandiant の説明では、DCE/RPC 経由の SRP-6a セッション鍵の開示であり、 SRP 認証インターフェースにおける予測可能な UUIDv1 タイムスタンプ生成が 原因である**（出典2）。　症状: **「ネットワークアクセスができる悪意ある攻撃者が認証を回避し、 システムへ不正アクセスする可能性がある」**（出典1。原文英語を訳出）—— **Mandiant は、悪用の結果として administrator@vsphere.local の認証済みセッションが作られると説明している** （出典2・4）。 **その状態で任意のコマンド実行とファイル取得が可能になり、 vmdird の RPC インターフェース（vmdirdbcp）を通じて ディレクトリデータベース data.mdb を取得できる**（出典2・4）。　手法: **公表されている範囲は、認証不要で共有セッション鍵を得られる仕組みまでである** （出典2）——**Mandiant は CVE-2026-59309（LDAP の認可トークン処理の不備）と 「パスワードを知らずに共有セッション鍵を得られる」点で重なるが、 本件は DCE/RPC インターフェースの SRP セッション鍵開示であり別物だとしている** （出典2）。 **実際の悪用では、Go 製のツール BONESAW が使われた**（出典2）。 **実証コードの公開は本記録が確認した範囲では見られない**（本記録の確認）。　内容: **奪われるのは仮想化基盤の管理権限そのものである**（出典2・4）—— **ディレクトリデータベース（data.mdb／LMDB）・VMware STS の SAML 秘密署名鍵・ vCenter の内部マスター暗号鍵・PostgreSQL のパスワードファイルが 実際に持ち出されている**（出典2）。 **ESXi ホストへ移った後は、ゲスト仮想マシンのファイルシステムから NTDS・SYSTEM・SECURITY・dns といった Active Directory のデータが 抜き出されている**（出典2）。　preconditions: **脆弱な vCenter へのネットワーク到達性のみ**（出典1・3）—— **認証は不要**（出典1）。 **Enhanced Linked Mode の有効・無効にかかわらず影響を受ける**（出典4）。 **本キャンペーンでは、インターネットからの直接攻撃ではなく、 別のゼロデイで内部に入ったうえで内部ネットワークから到達している** （出典2・4）〈重要〉。
緩和策

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
Mandiant は脆弱性を Broadcom へ非公開で報告し、 修正が提供された2026年11月19日と同じ日に、悪用の詳細・侵害の痕跡・ YARA ルール・要塞化の手順を公表した機能した本記録の評価である。修正の提供と同時に、点検に使える粒度 （ファイルパス・アカウント名の形式・待ち受けポート・YARA）まで出している点を 評価した。ただし「悪用開始から公表まで」の長さは、 報告から修正提供までの調整期間が公表されていないため評価できない〈未確定5〉
Broadcom は VMSA-2026-0009 で CVSS・対象版・修正版・回避策の有無を示したが、 実際の悪用には触れていない。Mandiant は悪用・攻撃者名・手口・痕跡を示したが、 被害組織の業種・国・件数には触れていない部分的に機能本記録の評価である。2つの公表を合わせれば対処に必要な情報は揃うが、 どちらか一方だけでは足りない構造になっている〈差異1〉。 被害組織が示されないため、本記録も「構成が該当するか」でしか 当てはまりを判定できない（applicability 参照）
CISO・経営層への示唆
  • 仮想化基盤の認証回避は「管理ツールの脆弱性」ではなく 「全系の侵害」として扱う。影響評価を基盤単位で用意しておく。
    **本件では vCenter の侵害後、SAML 署名鍵・マスター暗号鍵・PostgreSQL の パスワードが奪われ、ESXi 経由でゲスト仮想マシンから Active Directory のデータベース（NTDS）まで持ち出されている**（出典2）〈重要〉。 **ゲスト側に EDR を入れていても、基盤側から仮想ディスクを読まれれば 記録に残らない**（本記録の評価）。
    取るべき行動 **vCenter／ESXi が侵害された場合の影響範囲を、 基盤上の全仮想マシン（ドメインコントローラを含む）として事前に定義する。** **その前提で、資格情報の全面入れ替えを含む復旧手順を用意し、所要時間を見積もる。**
  • ベンダー勧告のスコアだけで優先度を決める運用は、本件のような 「勧告に悪用が書かれていないゼロデイ」を取り落とす。
    **Broadcom の VMSA-2026-0009 には実際の悪用に関する記載が無い** （出典1。本記録が取得して確認）〈重要〉—— **一方 Mandiant は、2026年9月上旬からのゼロデイ悪用を同日に公表している** （出典2）。 **勧告だけを読む運用では、CVSS 9.8 の通常のクリティカルとして処理される** （本記録の評価）。
    取るべき行動 **脆弱性の緊急度判定に、ベンダー勧告以外の情報源 （調査会社の分析・CISA KEV・第三者の解説）を突き合わせる工程を入れる。** **「悪用の有無」の判断は、勧告の記載が無いことを「悪用なし」と読まない規則にする。**
  • パッチ適用の完了報告に「侵害の点検」を含める。鍵が出た後は更新だけでは閉じない。
    **本件では SAML 署名鍵が持ち出され、Golden SAML による 多要素認証の回避が行われている**（出典2・4）〈重要〉—— **署名鍵が外にある状態では、脆弱性を直しても偽造トークンは有効なままである** （本記録の評価）。 **Mandiant の CTO も「パッチの適用と侵害の証跡の調査の両方」を求めている** （出典5。原文英語を訳出）。
    取るべき行動 **緊急パッチの完了条件を「適用済み」から 「適用済み＋痕跡の点検済み（結果の記録を含む）」に変える。** **点検で痕跡が出た場合に、鍵と資格情報を入れ替える判断権限を事前に決める。**
  • サポートが切れた基盤ソフトは「修正が提供されない前提」で予算と移行計画を持つ。
    **vCenter 7.0 には公開修正が無く、延長サポート契約者はサポートへの 問い合わせとされている**（出典1・3）—— **一方で悪用ツールは 7.x でも動作するとされる**（出典5）〈重要〉。 **仮想化基盤は停止調整が難しく、更新が後回しになりやすい**（本記録の評価）。
    取るべき行動 **基盤ソフトのサポート終了日を一覧にし、終了後に クリティカルな脆弱性が出た場合の対応（延長契約・隔離・移行の前倒し）を あらかじめ決めておく。** **延長サポート契約の有無を資産台帳に記録する。**
セキュリティ技術者への示唆
  • vCenter の管理ポートへの到達性を既定拒否にする。回避策が無い脆弱性では 到達性の制御が唯一の時間稼ぎになる。
    **本件には回避策が無い**（出典1・3）—— **Broadcom はネットワーク制限とファイアウォールが露出低減に役立つとし** （出典4）、**Mandiant は iptables による既定拒否と管理ポート （443・2012・22・5480）の許可リスト化を提示している**（出典2）。 **攻撃は内部ネットワークからの到達で成立している**（出典2・4）〈重要〉。
    取るべき行動 **vCenter の管理面へ到達できる送信元を、踏み台（特権アクセスワークステーション） のみに絞る。** **設定は VAMI の GUI ではなくカーネルレベルで行い、GUI 経由の迂回を防ぐ。** **変更前に十分な試験を行う（到達できなくなる事故を避ける）。**
  • アプライアンスのログは、アプライアンスの中に置いたままにしない。 遡れる期間が侵害調査の上限になる。
    **悪用は2026年9月上旬から始まり、公表は11月19日である**（出典1・2）—— **70日以上前の痕跡を調べることになる**（本記録の算出）〈重要〉。 **Mandiant の要塞化ツールがカーネルイベントのリモート syslog 転送を 含んでいるのは、既定では転送されないためである**（出典2 からの整理。本記録）。
    取るべき行動 **vCenter・ESXi・境界アプライアンスのログを外部の収集基盤へ転送し、 保持期間を90日以上にする。** **転送が止まっていないかを定期的に確認する（止まった時点で調査能力が消える）。**
  • SSO 管理者アカウントの作成と、基盤アプライアンス上の待ち受けポートの変化は、 この型の攻撃で最も現実的な検知点である。
    **BONESAW は SSO 管理者アカウント（sps-…@vsphere.local の形）を作成し、 BEARBONES は TCP 53 と 33992 で待ち受けた**（出典2）〈重要〉—— **Golden SAML の段階に入ると、偽造された認証は正規の署名で検証を通るため 区別できない**（本記録の評価）。 **検知の機会は、鍵が使われる前の「作成」と「待ち受け」にある**（本記録の整理）。
    取るべき行動 **vCenter の SSO アカウント一覧を定期的に取得し、台帳との差分を通知する。** **基盤アプライアンスの待ち受けポートを棚卸しし、差分を検知対象にする。** **Mandiant 公表の YARA ルールを、アプライアンス上のファイル検査に取り込む。**
  • 更新作業そのものに制約がある。Quick Patch 不可・「Back-in-Time」制限を 計画に織り込む。
    **本件の修正は vCenter Quick Patch では適用できない**（出典3）—— **8.0 U3m と 9.0.2.0200 では「Back-in-Time」制限が入り、 VMware Cloud Foundation 9.1.1 への更新が阻まれる**（出典3）〈重要〉。 **更新中は管理インターフェースが使えなくなるが、 稼働中のワークロードは動き続けるとされている**（出典3）。
    取るべき行動 **緊急更新の手順書に、Quick Patch 不可・管理面の一時停止・ 移行計画への影響（相互運用性マトリクスの確認）を書き込む。** **移行作業中の環境は、適用順序をベンダー FAQ で確認してから着手する。**
  • ドメインコントローラを同じ仮想化基盤に置くなら、基盤の侵害が AD の侵害に直結することを前提に設計する。
    **本キャンペーンは ESXi 経由でゲストの NTDS・SYSTEM・SECURITY を 持ち出している**（出典2）〈重要〉—— **ゲスト OS 側の防御では止まらない経路である**（本記録の評価）。
    取るべき行動 **ドメイン管理者の資格情報と仮想化基盤の管理権限を、 同じ人・同じ端末・同じ認証基盤で兼ねないようにする。** **基盤侵害時の AD 復旧手順（krbtgt の2回更新を含む）を用意し、演習する。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ VMware vCenter Server（9.1.x／9.0.x／8.0／7.0）または これを含む VMware Cloud Foundation・vSphere Foundation・ Telco Cloud Platform／Infrastructure を運用している。**VMSA-2026-0009 の修正版より前のすべての版が対象である**（出典1）—— **Enhanced Linked Mode の有効・無効は関係しない**（出典4）。 **該当する場合、緊急の更新と侵害の点検の両方が必要になる**（出典2・5）。
運用・監視□ vCenter の管理面（443・2012・22・5480）へ、内部ネットワークの広い範囲から 到達できる状態になっている。**本キャンペーンの vCenter 侵害は、インターネットからではなく 内部に侵入した後の到達で成立している**（出典2・4）〈重要〉—— **「外部公開していないから対象外」は成り立たない**（本記録の評価）。
認証・認可□ vCenter の SSO 管理者アカウントの一覧を定期的に突き合わせておらず、 アカウント作成の通知も設けていない。**BONESAW は SSO 管理者アカウントを作成しており、 これが Mandiant の挙げる痕跡の1つである**（出典2）—— **Golden SAML の段階に入ると偽造認証は区別できないため、 作成の検知が現実的な機会になる**（本記録の評価）。
データの保持□ ドメインコントローラや認証基盤の仮想マシンを、同じ vSphere 基盤上で 運用している（基盤管理者と AD 管理者の権限分離もしていない）。**本件では ESXi 経由でゲストから NTDS・SYSTEM・SECURITY が持ち出されている** （出典2）〈重要〉——**該当する場合、基盤の侵害がそのまま AD の侵害になる** （本記録の評価）。
委託・第三者部品□ 境界に BeyondTrust Remote Support・VPN・リモート管理のアプライアンスを置いており、 その管理面への到達元を絞っていない。**本キャンペーンの入口は BeyondTrust Remote Support のゼロデイ （CVE-2026-102764）だった**（出典2・4）—— **該当する場合、vCenter の更新だけでは侵入経路が残る**（本記録の評価）。
体制・契約□ サポートが終了した基盤ソフト（vCenter 7.0 等）を運用しており、 延長サポート契約の有無を資産台帳で把握していない。**vCenter 7.0 には公開修正が無く、延長サポート契約者のみが サポート経由で対応できる**（出典1・3）〈重要〉—— **一方で悪用ツールは 7.x でも動作するとされる**（出典5）。 **該当する場合、当てられる修正が存在しない状態で運用していることになる。**
