公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**本件は、攻撃者が自分の攻撃基盤を認証なしで公開していたため、 段階ごとの振る舞いが例外的に細かく分かっている**（出典1）〈重要〉。 **以下は Amazon Threat Intelligence の報告に基づく。** **攻撃者が与えたのは、標的のIPアドレスの一覧と 「shell アクセスを取得せよ」という目標の変種だけである。** **各段階の判断はAIエージェントが行い、 操作者が介入したのは2校目へのトンネルを与えた場面だけである**（出典1）。

  1. 1. 偵察
    **エージェントは、大学の公開情報から実在する利用者名を約80件組み立てた**（出典1）—— **教員名簿・研究室のウェブサイト・アーカイブされたページ・学術論文を調べている。** **MONAI Label の標的に対しては、アプリケーションの枠組みを特定し、 API の端点を洗い出し、filename パラメータを持つアップロード端点を見つけた**（出典1）。 **Redis の標的に対しては、同じ機器で動く別のサービスや、 同じ場所に置かれた Qdrant の存在まで把握している**（出典1）。
  2. 2. 初期侵入
    **MONAI Label のアップロード端点の filename パラメータに対して パストラバーサルを試し、脆弱であることを確認した**（出典1）。 **「約11分で、エージェントはアプリケーションの API の把握から サーバ上の任意のファイル書き込みまで進んだ」**（原文英語の訳。出典1）〈重要〉。 **勧告によれば、`PUT /datastore/image` の `image` パラメータが検証されずに 画像IDとして使われ、解決後のパスがデータストアの内側に留まるかを 確認していなかったことによる**（出典2）。 **認証は既定で無効であり、認証を有効にしていても ANNOTATOR の権限で足りる**（出典2）。 **発見の時点で、この脆弱性に対応する勧告は存在せず未修正だった**（出典1）—— **Amazon は高い確度でゼロデイと評価している。**

    **別のセッションで、エージェントは同じ脆弱性を使って Python のリバースシェルの実行コードを `sitecustomize.py` に書き込んだ**（出典1）—— **Python がインタプリタの起動時に自動で読み込むファイルである。** **続いて学習用の API 端点を叩いて新しい Python プロセスを起動させ、 そのプロセスが実行コードを読み込んで root 権限のリバースシェルを確立した**（出典1）〈重要〉。 **権限昇格の踏み台は、アプリケーションの正規の機能（学習の起動）である** （本記録の整理）。

    **ゼロデイの発見後、人の操作者が介入した**（出典1）〈重要〉。 **操作者はエージェントに、2校目の大学のネットワークへ通じるプロキシを与えた。** **「プロキシが接続していたサーバは同じ脆弱なソフトウェアを動かしており、 操作者がゼロデイを使ってそれを侵害し、トンネルを確立したと我々は推測する」** （原文英語の訳。出典1）〈未確定3〉。 **操作者はエージェントに、そのネットワーク内の他の機器を狙うよう指示した**（出典1）。

「shell を取れ」だけを与えられたエージェントが、16時間失敗し続け、11分で当てた概観

2026年9月8日からおよそ48時間、ある攻撃者は Cairn に東アジアの大学（中国本土以外）のIPアドレスの一覧と、「shell アクセスを取得せよ」という目標の変種だけを与えた（出典1）。以後、エージェントは操作者が次の一手を選ぶことなく、自分で計画し、実行し、学びながら方針を変えた（出典1）。

同じ48時間のうちに、3つの作戦が走っている（本記録の整理）。

作戦 内容 時間 結果
Redis 複製機能の悪用・サンドボックス脱出・設定書き込み・メモリ破壊・Log4Shell・SSRF 経由の内部探索・総当たり 約16時間・148手 失敗

本記録が中心に置くのは、この時間配分である（本記録の評価）〈重要〉—— 「AIが強い」という話ではない。 人の攻撃者であれば、16時間148手の空振りの途中で手を変えるか、その日の作業を終える。 CJ Moses が書いているのは2つである（原文英語の訳。出典1）—— 「数分でゼロデイを見つけて悪用するエージェントは、多くのセキュリティ運用センターが手作業で警報をトリアージするより速く活動を完了する」、そして「失敗した Redis への作戦は、休憩も睡眠も勤務時間の制約もなく16時間連続で動いた」。

読み替えると、防御側が向き合うのは次の2つになる（本記録の評価）。①当たったときの処理時間が、警報を人が見る時間より短い。 ②当たらないときの試行が、夜間・休日・連続して続く。 前者は自動化された対応の設計の問題であり、後者は「総当たりの気配」を異常として扱えるかの問題である（本記録の整理）。

入口はアップロード端点の filename パラメータで、認証は既定で無効だった原因・手口

悪用されたのは、オープンソースの医用画像AIアプリケーション MONAI Label のパストラバーサルである（出典1・2）。MONAI Label は、研究者が医用画像にラベルを付ける作業をAIで支援する道具である（出典1）。

勧告 GHSA-qc22-rmgc-vg94 の記述は具体的である（出典2）〈重要〉。

  • PUT /datastore/image が受け取る image 問い合わせパラメータは、呼び出し側が自由に決められる。
  • サーバはこれを検証せずに画像IDとして使う。
  • LocalDatastore.add_image() が拡張子を付け、データストアの画像ディレクトリに結合し、shutil.copy() でアップロードされた内容を書き込む。
  • 解決後のパスがデータストアの内側に留まるかは確認されない。 そのため、traversal の並びを与えれば、サーバのプロセスが書ける任意の場所へ書き込みを向けられる。
  • PUT /datastore/label も、LocalDatastore.save_label() を通じて同じ作りである。

影響として勧告が挙げるのは、任意のファイル書き込みによる遠隔コード実行（アプリケーションのコードの上書き、SSH や cron の項目の追加）と、設定ファイルの上書きによるサービス妨害である（出典2）。

本記録が最も重く取ったのは、次の1文である（本記録の評価）〈重要〉—— 「認証は既定で無効であるため、サーバに到達できるネットワーク上のあらゆるクライアントが悪用できる。認証を有効にしている場合でも、ANNOTATOR の権限があれば足りる」（原文英語の訳。出典2）。

実際の攻撃では、ファイル書き込みが root の実行に変わっている（出典1）。エージェントは Python のリバースシェルを sitecustomize.py に書き込んだ——これは Python がインタプリタの起動時に自動で読み込むファイルである。 そのうえで学習用の API 端点を叩いて新しい Python プロセスを起動させ、そのプロセスが実行コードを読み込んで root 権限のシェルを確立した。 つまり、権限昇格の道具は攻撃者が持ち込んだのではなく、アプリケーションの正規の機能（学習の起動）である（本記録の整理）〈重要〉。

なお、修正を含むリリース版は勧告に示されていない〈齟齬3〉—— 「修正は Pull Request #1915 に入り、次のリリースに載る予定」とある（出典2）。

一部始終が見えたのは、攻撃者が自分の基盤を認証なしで公開していたからである発覚の端緒

2026年9月10日、Amazon Threat Intelligence は認証なしで公開されていた Cairn のインスタンスを持つサーバを発見した（出典1）。「操作者がサーバを公開したままにしていたため、プラットフォームの運用履歴——プロジェクトの設定、アクターのプロンプト、AIの出力——がインターネット上の誰からも見える状態だった」（原文英語の訳。出典1）〈重要〉。

帰属の根拠も、ここから出ている（本記録の整理）。プロンプトは簡体字で書かれ、実行されたスクリプトのタイムスタンプは中国標準時に設定されていた（出典1）。これに標的の選び方（中国にとって戦略的な関心の対象になりうる大学）を加えて、Amazon は中確度で「中国系」と評価している（出典1）。

本記録はこの発見の性質を記録しておく（本記録の評価）〈重要〉—— 防御側が見られたのは、攻撃者の運用の失敗によってである。 エージェント型の作戦が「どう計画し、どこで諦め、何を試したか」まで分かるのは、通常は起こらない。 言い換えれば、本件の詳しさは再現を期待できない（本記録の明示）—— 次の同種の作戦は、認証を掛けた基盤で動く。

したがって読者が本件から持ち帰るべきは、「このアクターの手口」ではなく「この種の道具の振る舞い方」である（本記録の評価）。

効かなかった2つの作戦が、何が効くのかを示している評価・解釈

失敗の中身は、成功の中身より役に立つ（本記録の評価）〈重要〉—— 成功したのは未知の脆弱性であり、利用者側で先に手を打てるものではなかった。 一方、失敗した2つの作戦が当たらなかった理由は、どれも既知の守りである。

①Redis（約16時間・148手）（出典1）。エージェントは複製機能を悪用した未許可コードの読み込み、スクリプトのサンドボックスからの脱出、設定ファイルへの書き込み、メモリの破壊、同じ機器の別サービスへの Log4Shell の注入、同じ場所に置かれた Qdrant の SSRF 経由での内部 Docker 構成の把握、PostgreSQL・SSH への総当たりを順に試した。 なお、この Redis は「認証なしでアクセスできる設定」だった（出典1）—— 入口は開いていたが、そこから先に進めていない。

②GPU サーバ（6時間超・30,000通り超）（出典1）。利用者名は推測ではなく、教員名簿・研究室サイト・アーカイブされたページ・学術論文から集めた約80件の実在する名前である〈重要〉。それでも有効なログインは見つからなかった。

ここから読めることを3点書く（本記録の評価）。

（a）利用者名は秘密にできない。 大学は教員名簿と論文を公開しないわけにいかない。 「名前が分かっても入れない」状態——多要素認証、鍵認証、試行の制限——が守りになる。

（b）自律エージェントは「既知の手法の網羅」に強く、そこに新しさは無い（本記録の評価）。148手の内容は、人が書いた攻撃手引きに載っているものである。 変わったのは、網羅にかかる人件費がほぼ消えたことである。

（c）同居しているサービスが経路になる。 Redis への攻撃は、同じ機器の別サービス（Log4Shell の対象）と同じ場所の Qdrant（SSRF）を経由して内部の構成把握に進んでいる（出典1）—— 研究用の機器では、1台に複数の部品が同居しやすい（本記録の指摘）。

MONAI Label を動かしている組織が、今週できること対策・注意喚起

本件で最も具体的な行動は、MONAI Label の利用者に対するものである（本記録の整理）。まず更新である〈重要〉—— 2026年11月22日に修正版 0.8.6 が公開された（出典9）。手順は pip install -U monailabel==0.8.6 またはdocker pull projectmonai/monailabel:0.8.6 であり、影響を受けるのは 0.8.5 以前のすべての版である（出典9）。初報（2026年11月21日）の時点では勧告に修正版が示されておらず、本記録は回避策を軸に書いていた〈齟齬3〉—— その部分は解消した（本記録の明示）。

ただし、更新だけでは足りない点が2つある（本記録の評価）〈重要〉。

①0.8.6 は2件のパストラバーサルを直しており、CVE が付いているのは本件で悪用された1件（CVE-2026-133968・PR #1915）だけである（出典8・9）—— もう1件はセッション取り込み（PUT /session/?uncompress=true・PR #1942）の欠陥で、CVE が無い。 CVE 番号で突き合わせる運用では、この1件が残る。

②更新は、既に書き込まれたものを消さない。 リリースノートは「0.8.5 以前のサーバが信頼できないネットワークから到達可能だった場合は、運用に戻す前に予期しないファイルの変更を確認せよ」と求めている（原文英語の訳。出典9）—— 本件では sitecustomize.py が書き換えられている（出典1）。見るべきは、データストアの外に増えたファイル、Python が起動時に自動で読み込むファイル、cron と SSH の項目である（本記録の評価）。

②Google の報告（2026年11月17日）（出典3）。Artex・CyberStrikeAI・PentAGI など、自律的な多エージェント型の攻撃用枠組みの使われ方の変化を扱っており、Cairn にも触れている。 Google は、Cairn が米国の航空宇宙分野の企業への侵入で使われたのを見たとし、標的のIPアドレスから始めて目的に至るまでをうまくこなすと書いた（出典3）。

侵入を防げた研究用の Web API を既定の認証無効のまま外に出さない　**勧告は回避策として `MONAI_LABEL_AUTH_ENABLE=True` と、 信頼できないネットワークからの到達の遮断を挙げている**（出典2）。 **本記録の評価では、これが本件で最も効いた対策である**〈重要〉—— **脆弱性が未知であっても、到達できなければ11分は始まらない。** **研究・検証用のサーバで「認証が既定で無効のまま動いている Web API」を 数え上げることが、今週できる作業である。**
権限昇格公表されていない
**AWS の報告は、被害組織側の検知について述べていない**（本記録の確認）。 **本記録の評価では、この段階は検知に向いている**〈重要〉—— **アプリケーションのプロセスが外向きの接続を張り、 かつ root で動くのは、通常の学習処理と区別できる挙動である。** **ただし、実際に監視があったかどうかは分からないため 「公表されていない」とする。**
影響を限定できたアプリケーションを非特権ユーザで動かし、書き込み先をデータに限る　**勧告の回避策の1つである**（出典2）。 **本記録の評価では、本件で決め手になりえた対策である**〈重要〉—— **`sitecustomize.py` に書けなければ、 任意のファイル書き込みは「データの汚染」にとどまり、root の実行には化けない。** **効き方を「影響範囲を限定できた」までとしたのは、 書き込み自体は依然として成立するためである**（本記録の判断）。
検知できたアプリケーションのプロセスからの外向き接続を既定で拒否する　**本記録の評価による。** **リバースシェルは外向きの接続で成立する**（出典1）。 **医用画像のラベリングのような用途では、 学習の実行に外向きの通信が要る場面は限られる**（本記録の推定）—— **許可する宛先を列挙できるなら、それ以外を拒否して記録に残せる。**
横展開公表されていない
**2校目の検知について、AWS の報告は何も述べていない**（本記録の確認）。 **そもそも2校目の侵害経路自体が Amazon の推定である**〈未確定3〉—— **本記録は、この段階について確定した事実をほとんど持たない**（本記録の明示）。
影響を限定できた同じソフトウェアを動かす機器を横断して棚卸しし、1台の侵害を前提に他を点検する　**本記録の評価による。** **本件で2校目が狙われた理由は「同じ脆弱なソフトウェアを動かしていたから」である** （出典1）。 **組織の境界を越えて同じ研究用ソフトウェアが使われるのは、 学術分野では普通である**（本記録の整理）—— **1校で侵害が見つかったとき、同じ分野の他機関にも同じ構成がある。** **分野の情報共有の枠組み（研究機関のCSIRT連携等）が意味を持つ場面である。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「警報を人が見てから動く」前提の運用は、エージェント型の攻撃に対して時間が合わない
    **本件では、API の把握から任意のファイル書き込みまで約11分で到達している**（出典1）。 **CJ Moses は「数分でゼロデイを見つけて悪用するエージェントは、 多くのセキュリティ運用センターが手作業で警報をトリアージするより速く 活動を完了する」と書き、 「組織は、自動的な対応を起こす高確度の検知を優先し、 人は個々の行動を逐一見るのではなく結果を監督する側に回るべきだ」と勧めている** （原文英語の訳。出典1）〈重要〉。 **これは「人を減らす」話ではなく、 人が入る位置を「判断」から「監督」へ動かす話である**（本記録の読み方）。
    取るべき行動 自組織の検知のうち、**人の確認を待たずに自動で遮断・隔離してよいもの**を 3つだけ選び、文書にする—— 例: 公開サーバからの外向き新規接続、`sitecustomize.py` 等の自動読み込みファイルの変更、 同一送信元からの短時間の大量認証失敗。 **選ぶ基準は「誤って発動しても業務が止まらない範囲」である。** **選べない場合、何が足りないのか（権限・合意・復旧手順）を書き出す。**
  • 研究・検証用の環境を、本番と同じ台帳に載せる
    **本件で成功した入口は研究用の医用画像AIアプリケーションであり、 失敗した標的も認証なしの Redis と研究用の GPU サーバだった**（出典1）〈重要〉。 **いずれも「研究のために外から使えるようにしてある部品」である**（本記録の整理）。 **MONAI Label は認証が既定で無効であり**（出典2）、 **この種の道具は本番システムの台帳に載らないまま動き続けやすい**（本記録の評価）。
    取るべき行動 **研究・検証・PoC 用のサーバで外部から到達できる Web API を一覧にし、 「認証の有無」「実行ユーザ」「書き込み可能な範囲」の3列を埋める。** **埋まらない行があれば、それが最初に閉じる対象である。** **部門に台帳を作らせるのではなく、 ネットワーク側から到達可能な宛先を数えるほうが早い**（本記録の評価）。
  • 「どのAIツールを検知するか」という形で対策を立てない
    **同じ月に、Artex・CyberStrikeAI・PentAGI・Cairn が それぞれ別の報告で名前を挙げられている**（出典1・3・4）。 **Gambit Security の Eyal Sela は「Cairn は Artex より重要である。汎用の道具だからだ」 「道具が汎用になるほど、課題の解き方の周りに構造が無くなるので、予測しにくくなる」と 述べている**（原文英語の訳。出典4）〈重要〉。 **ツール名を軸にした検知は、次の枠組みが出た時点で作り直しになる**（本記録の評価）。
    取るべき行動 対策の軸を**挙動**に置く—— 「公開サービスからの外向き接続」「自動読み込みファイルの変更」 「短時間に多数の API 端点へ到達する走査」「連続する認証失敗」。 **既存の検知ルールを棚卸しし、 特定のツール名・シグネチャに依存している項目に印を付け、 挙動側の代替があるかを確認する。**
  • 自組織が「AI の被害者」になる前に、取引先・共同研究先の同じ構成を想定する
    **2校目が狙われた理由は「同じ脆弱なソフトウェアを動かしていたから」である**（出典1）。 **研究用のソフトウェアは組織の境界を越えて同じものが使われる**（本記録の整理）〈重要〉。 **また、AWS は影響を受けた組織が自社の顧客でなかったため 政府機関のパートナーを通じて通知するしかなかった**（出典1）—— **通知が届く経路が細い。**
    取るべき行動 共同研究・共同事業で**同じソフトウェア構成を共有している相手**を列挙し、 片方で侵害が見つかったときに連絡する窓口を決めておく。 **自組織が通知を受ける側の経路（CSIRT の連絡先が外から見えるか）も確認する**—— **本件では、通知が届いたかどうかさえ公表されていない**〈未確定7〉。
セキュリティ技術者への示唆
  • アップロード機能は「保存先を解決した後」に検証する
    **本件の脆弱性は、呼び出し側が決める `image` パラメータを検証せずに 画像IDとして使い、拡張子を付けてディレクトリに結合して書き込み、 解決後のパスがデータストアの内側に留まるかを確認していなかったことによる**（出典2）〈重要〉。 **修正は、保存先を解決して範囲外を拒否し、 画像IDをベース名に縮め、空やドットで始まるIDに HTTP 400 を返す形になった**（出典2）。 **同じ作りが `PUT /datastore/label` にもあった**—— **1か所を直すだけでは足りなかった**（本記録の整理）。
    取るべき行動 自組織のアップロード・ファイル保存の処理を洗い出し、 **①パスを結合した後に正規化して範囲内か検証しているか、 ②ファイル名をベース名に縮めているか、 ③同じ処理が他の端点にも複製されていないか**を確認する。 **③は grep で足りる**——**同じ関数を呼ぶ箇所を数える。**
  • Python の自動読み込みファイル（sitecustomize.py 等）の変更を監視対象に入れる
    **本件では、任意のファイル書き込みが `sitecustomize.py` の上書きを経て root 権限のリバースシェルに化けている**（出典1）〈重要〉。 **`sitecustomize.py` は Python がインタプリタ起動時に自動で読み込む。** **攻撃者は新しいプロセスを自分で起こす必要さえなく、 正規の学習用 API を叩いて Python を起動させている**（出典1）—— **「実行は正規の機能に任せる」形である**（本記録の整理）。
    取るべき行動 **自動読み込みされるファイルの一覧を作る**—— Python の `sitecustomize.py` / `usercustomize.py` / `.pth`、 シェルの起動ファイル、cron、systemd の unit、SSH の `authorized_keys`。 **これらの変更をファイル完全性監視の対象に入れ、 変更時に自動で警報を出す**（人の確認を待たない）。
  • アプリケーションを非特権ユーザで動かし、書き込み先をデータだけに限る
    **勧告は回避策として「非特権ユーザで動かし、 書き込み権限をデータストアのディレクトリに限る」ことを挙げている**（出典2）。 **本記録の評価では、本件で決め手になりえた対策である**〈重要〉—— **`sitecustomize.py` に書けなければ、 任意のファイル書き込みは「データの汚染」にとどまり root の実行には化けない。**
    取るべき行動 研究・検証用に動かしているアプリケーションの**実行ユーザを確認する**。 **root で動いているものを数え、 非特権ユーザに落としたときに壊れる依存（ポート番号・書き込み先）を洗い出す。** **落とせないものには、せめて書き込み可能なディレクトリの一覧を作る。**
  • 利用者名は公開情報である前提で、認証と試行制限を設計する
    **エージェントは教員名簿・研究室サイト・アーカイブされたページ・学術論文から 約80件の実在する利用者名を組み立て、 30,000通りを超える組み合わせを SSH・管理画面・NAS・VPN・学内ポータルに試した**（出典1）。 **それでも有効なログインは見つからなかった**〈重要〉—— **この守りは実際に効いている**（本記録の整理）。 **一方で、6時間超・30,000通り超の試行が止められなかったことも事実である** （本記録の指摘）。
    取るべき行動 **外部から到達できる認証の入口を列挙し、 ①多要素認証または鍵認証の有無、②試行回数の制限、 ③連続失敗の警報の3つを表にする。** **③が無い入口は、30,000通りの試行が静かに通る**—— **本件では6時間以上続いている。**
  • CVE 番号を起点に直すと、同じリリースのもう1件が残る
    **MONAI Label 0.8.6 は2件のパストラバーサルを直したが、 CVE が付いているのは本件で悪用された1件 （CVE-2026-133968・PR #1915）だけである**（出典9）〈重要〉。 **NVD を「MONAI Label」で検索した結果も CVE-2026-133968 の1件のみだった** （2026年11月24日・本記録の確認。出典8）。 **さらに、GHSA の CVE 欄は本記録が11月21日に見た時点で「無し」だったが、 NVD には11月20日に登録されていた**〈齟齬7〉—— **CVE 番号は、勧告より遅れても早く出ることもある**（本記録の整理）。
    取るべき行動 **脆弱性管理の照合キーを CVE 番号だけにせず、 製品と版（`monailabel` < 0.8.6）でも引けるようにする。** **pip・docker で入れた OSS は、導入手順か SBOM に版を残す**—— **残っていなければ KEV を見ていても照合できない。** **勧告（GHSA）とリリースノートの両方を見る**—— **本件では、修正版の明示はリリースノート側にしか無かった。** **「CVE が無いから対象外」という判定を禁止する。**
  • 侵害の痕跡（IPアドレス）は照合に使えるが、本件では2件しかない
    **AWS が公開したのは2つのIPアドレス（142[.]4.98.145 / 142[.]4.107.34）で、 2026年9月8日から10日の記録に現れるものである**（出典1）。 **2か月以上前の、48時間の作戦のものである**（本記録の整理）〈重要〉—— **現在も使われている可能性は低い。** **本DBの方針として、抽出・掲載した痕跡は悪性を検証していない**（本記録の明示）。
    取るべき行動 **過去ログに対する遡及の照合に使う**（検知ルールへの常設ではなく）。 **照合する期間を2026年9月8日〜10日に絞れば、誤検知の負担は小さい。** **当たった場合に見るべきは、同じ時期の MONAI Label の API への到達と、 アプリケーションのプロセスからの外向き接続である。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 研究・検証・PoC のために、インターネットから到達できる Web API を動かしている （認証を既定のまま、あるいは意図的に無効にしている場合を含む）本件で成功した入口はまさにこれである（出典1・2）。 **MONAI Label は認証が既定で無効であり、 勧告は「サーバに到達できるネットワーク上のあらゆるクライアントが悪用できる」と 書いている**（出典2）。 **脆弱性が未知であっても、到達できなければ11分は始まらない**（本記録の評価）
運用・監視□ 公開サービスを root（または書き込み範囲の広い権限）で動かしている本件では、任意のファイル書き込みが `sitecustomize.py` の上書きを経て root 権限のシェルに化けた（出典1）。 **書き込み先がデータだけに限られていれば、 同じ脆弱性でも結果は「データの汚染」にとどまった**（本記録の評価）—— **脆弱性を予知できなくても、結果の重さは設計で変えられる**
認証・認可□ 利用者名が外部から収集できる（教員名簿・論文・社員紹介・プレスリリース等）状態で、 外部から到達できる認証の入口があるエージェントは公開情報から約80件の実在する利用者名を組み立てた（出典1）。 **名前を隠す対策は成り立たない**（本記録の整理）—— **多要素認証・鍵認証・試行制限があるかどうかで結果が分かれる。** **本件では、これらが効いて侵入は失敗している**
運用・監視□ セキュリティ警報の一次トリアージを人の確認に依存しており、 自動で遮断・隔離する検知を持っていない本件では当たってから任意書き込みまで約11分である（出典1）。 **CJ Moses は「人は結果を監督する側に回るべきだ」と勧めている** （原文英語の訳。出典1）—— **営業時間外・休日に11分で終わる活動を、 翌営業日のトリアージで止めることはできない**（本記録の評価）
委託・第三者部品□ 共同研究先・取引先と同じ研究用ソフトウェア構成を共有しており、 片方で侵害が起きたときに相互に連絡する経路が決まっていない本件の2校目が狙われた理由は「同じ脆弱なソフトウェアを動かしていたから」である（出典1）。 **AWS は、影響を受けた組織が自社の顧客でなかったため 政府機関のパートナーを通じて通知するしかなかった**（出典1）—— **通知が届く経路が細く、届いたかどうかも公表されていない**
データの保持□ 研究用のデータ（医用画像・被験者データ等）を、 本番と同じ管理基準の外にある環境に置いている本件で侵害されたのは医用画像のラベリングを行うアプリケーションである（出典1）。 **何が取られたかは公表されていない**〈未確定2〉—— **しかし root 権限のシェルが確立されている以上、 そのサーバ上のデータは影響の範囲に入る**（本記録の整理）。 **「研究用だから」という理由で分類・保持期間の管理を外していると、 侵害時に説明できる材料が無い**
