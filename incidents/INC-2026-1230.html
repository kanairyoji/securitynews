緊急修正が新しい攻撃経路を開けた——PHP 自身が勧告でそう書いている原因・手口

本リリースで最も重い含みを持つのは、PHP の勧告に書かれた一文である（本記録の評価）〈重要〉。

CSO Online はこう伝えている。

PHP 8.5 の新しいバックトレース脆弱性に関する PHP の勧告は、PHP2Shell のリリースである 8.5.12 での変更が、この新しい攻撃経路を到達可能にしたと述べている（出典5。原文英語を訳出）

該当するのは CVE-2026-129474（マジックメソッドのバックトレースにおけるuse-after-free。クリティカル）である（出典1・4）。PHP 8.5 では致命的エラーのバックトレースが既定で有効であり、このブランチだけが新しい攻撃面を持つ（出典4）。

専門家の評は率直である。

「緊急の修正は速く作られ、速い作業はときに新しい脆弱性を生む」（出典5。原文英語を訳出）

同じ構図は CVE-2026-126714（phpAfterShell） にもある（本記録の整理）。Xakep.ru はこう書いている。

このバグは最近修正された PHP2Shell の脆弱性と関係している——両者はアップロード進捗の情報をセッションへ書き込む仕組みを共有している。10月の緊急パッチは以前の悪用手段を除いたが、セッションファイルの書き込み中断の問題は解決しなかった。したがって PHP2Shell 向けのパッチは phpAfterShell を修正しない（出典6。原文ロシア語を訳出）

つまり、10月に「対応済み」としたブランチが、11月に再び対象になる〈重要〉。緊急対応で作った PHP 資産の台帳を捨てずに持ち続けることが、そのまま今回の作業の速度になる（出典5。本記録の整理）。

PHP-FPM の 9.2 は「接続を再利用しているか」で露出が決まる被害規模・影響範囲

最も重い CVE-2026-129289（CVSS v4.0 基本値 9.2・クリティカル）は、PHP-FPM のリクエストスマグリングである（出典2）。

ベクタはCVSS:4.0/AV:N/AC:L/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:Nであり、AT:P（攻撃前提条件あり）が付いている（出典2）〈重要〉。スコアだけでは露出の有無が分からないのは、この前提条件のためである（本記録の整理）。

成立に要るのは3つである（出典2・4）。

  1. フロントエンドがバックエンドへの永続接続を有効にしている（nginx の fastcgi_keep_conn on、Apache mod_proxy_fcgi のenablereuse=on、一部の HAProxy 構成、LSAPI）
  2. アプリケーションに php://input を開いて本体を最後まで読まずに処理を終える経路がある
  3. 既存の PHP スクリプトのパスが分かっている

Xakep.ru は 「接続再利用をしない標準的な nginx・Apache 構成はこの問題の影響を受けない」 と明記している（出典6。原文ロシア語を訳出）。

一方、成立したときの結果は重い。認証なしの攻撃者が PHP コードをワーカー権限で実行でき、ワーカーはデータベースのパスワード・API キー・クラウドの資格情報・セッションデータに到達できる（出典5）〈重要〉。

該当コードは PHP 5.6.0 以降に存在するとされる（出典2・4）——つまりサポート終了ブランチも影響を受けうるが、修正は提供されない。

phpAfterShell を「塞いだ」と言えるかは、公表されていない1点にかかっている未確定事項

CVE-2026-126714 の仕組みはこうである（出典4）。

PHP は既定でセッションデータをファイルに保存する。session_start() でファイルを読んで $_SESSION にデシリアライズし、リクエストの終わりに同じファイルへ書き戻す。その書き込みが中断されると、ファイルには新しいデータの先頭と古いデータの末尾が混在した状態が残る〈重要〉。次のリクエストで session_start() がこれをデシリアライズし、古いデータを攻撃者が制御していた場合、攻撃者が選んだオブジェクトがデシリアライズされる。

PHP の勧告が挙げる前提は3つで、うち1つが「アプリケーション内に適切なデシリアライズのガジェットチェーンがある」ことである（出典3）。これがあるかどうかで、実際にコード実行まで届くかが決まる。

ところが depthfirst は、そのガジェットチェーン無しに到達したと報告している（出典4）〈重要〉。

depthfirst は、PHP ネイティブクラスの2件目の未公表のメモリ破壊バグを連鎖させることで、アプリケーション側のガジェットなしにコード実行に到達したと報告している。我々が確認した資料のいずれも、その2件目のバグが11月19日のリリースで修正されたかを明らかにしていない（出典4。原文英語を訳出）

これは重い空白である（本記録の評価）〈未確定1〉。「アプリケーションにガジェットチェーンが無いから安全」という判断が成り立つかどうかが、この1点で決まる。本記録の作成時点（2026年11月21日）で、この点は未解決のままである。

Cloudflare は「WAF はパッチの代替ではない」と自ら書いている対策・注意喚起

Cloudflare は2026年11月19日、既存の PHP リモートコード実行ルール—— 2026年10月21日に PHP2Shell 向けに緊急リリースしたもの——の検知ロジックを phpAfterShell に対応させた（出典4）。同社は 「そのルールは公表前から phpAfterShell の攻撃パターンの一部を検知していた」 としている（出典4）。このルールは無料プランを含む既定有効のルールセットに入っており、既定の動作は Block である（出典4）。

あわせて有料プラン向けに新ルール3件が追加された（出典4）。

  • PHP-FPM（CVE-2026-129289）
  • PHP SOAP（CVE-2026-15353）
  • PHP SOAP（CVE-2026-129506）

これら3件の既定の動作は Log である〈重要〉。理由は 「検知対象の要求パターンが正当な通信にも現れうるため、既定で Block にすると正当な通信を妨げかねない」 と説明されている（出典4）。Block に変える前に、自環境の通信で誤検知が出ないかを確認する必要がある。

そして Cloudflare 自身が、WAF の限界を明示している（出典4）〈重要〉。

  • デシリアライズの段階は PHP の内部で起きるため、WAF はペイロードを仕込む要求を遮れても、読み出しそのものは遮れない
  • データベース・キュー・上流 API 経由でセッションに入る利用者由来のデータは、認識できる形で WAF を通らないことがある
  • サーバの状態に依存する4件（CVE-2026-129496・129481・129474・129182）には専用ルールが無い——エラーログ・診断出力・ワーカーの生存期間に依存するため
  • Cloudflare を経由しない通信（サービス間の内部通信、ネットワークに直接露出した PHP-FPM リスナー）は対象外

WAF は多層防御の追加の一層であり、パッチの代替ではない。完全な修正は PHP を更新してすべてのワーカーを再起動することだけである（出典4。原文英語を訳出）

バージョン番号だけでは露出を判定できない——PHP 8.2 は残り42日再発防止

対処の実務で押さえるべき点を、公表資料から整理する（本記録の整理）。

1. バージョン番号は露出の判定に足りない（出典4・5）〈重要〉

Linux ディストリビューションはバージョン番号を変えずに修正をバックポートすることがある。パッケージの完全なバージョンをディストリビューションの勧告と突き合わせること（出典4。原文英語を訳出）

CSO Online も同じ点を伝えている—— 「バージョン番号の確認は簡単な部分であり、パッケージの変更履歴のほうがバージョン文字列より多くを語る」（出典5。原文英語を訳出）。

2. 難しいのは「全部の PHP を見つけること」（出典5）

ウェブサーバ・コンテナ・ホスティングのコントロールパネル・アプライアンスが、いずれも PHP を黙って同梱しうる（出典5）。

CISO にとっての最大の問いは「PHP を動かしているか」ではなく、「どこで動かしているかを把握しているか」である（出典5。原文英語を訳出）

3. 優先順位は PHP 8.5 の外部公開サーバから（出典5）

PHP 8.5 を先に見る理由は、新しいバックトレース脆弱性に露出している唯一のブランチであり、致命的エラーのバックトレースが既定で有効だからである（出典5）。次にセッションアップロード進捗が有効な環境、そして複数のアプリケーションが1つのセッションストアを共有している構成である（出典5）。

4. PHP 8.2 は2026年12月31日で終わる（出典1・5）〈重要〉

本リリースから 42日である（本記録の算出。数値参照）。CSO Online は 「8.2 を1月まで動かすのはリスクの判断である」 とし、本リリースが 8.2 が受ける最後のセキュリティ修正の1つになりうると書いている（出典5）。PHP 8.1 以前は PHP プロジェクトから修正を受けない（出典5）。

セキュリティ技術者への示唆
  • PHP の露出をバージョン番号で判定せず、パッケージの完全なバージョンと ディストリビューションの勧告を突き合わせる。
    **Cloudflare は「Linux ディストリビューションはバージョン番号を 変えずに修正をバックポートすることがある」と明記している**（出典4） 〈重要〉。 **CSO Online が引用した専門家も「バージョン番号の確認は簡単な部分であり、 パッケージの変更履歴のほうがバージョン文字列より多くを語る」と 述べている**（出典5。原文英語を訳出）。
    取るべき行動 **`php -v` の出力だけで判定せず、 `rpm -q`／`dpkg -l` 等でパッケージの完全なバージョンを取り、 ディストリビューションの勧告と突き合わせる。** **コンテナイメージについては、ベースイメージのタグではなく イメージ内のパッケージを確認する。**
  • 確認すべき設定を具体的に絞る——接続再利用、アップロード進捗、 PHP 8.5 のバックトレース、php-cgi の露出、FPM 状態ページの到達性。
    **CSO Online が伝えた点検項目はこの5つである**（出典5）〈重要〉—— **「セッションアップロード進捗は有効か。PHP 8.5 のワーカーは エラーのバックトレースに引数を含めるか。php-cgi はインターネットに 面しているか。PHP-FPM の状態ページは外部から到達可能か」。** **これに CVE-2026-129289 の前提である接続再利用の設定が加わる** （出典2・4・6）。
    取るべき行動 **`fastcgi_keep_conn`（nginx）・`enablereuse`（Apache mod_proxy_fcgi）・ HAProxy の FastCGI 設定・LSAPI の利用を一覧にする。** **`session.upload_progress.enabled`・`zend.exception_ignore_args`・ `session.save_handler` の値を環境ごとに収集する。** **PHP-FPM／LSAPI のリスナーと状態ページへの到達元を確認する。**
  • 複数のアプリケーション・プール・コマンドライン処理が 1つのセッションストアを共有していないか確認する。
    **CVE-2026-115560 について PHP は適用範囲を広げ、 「異なるシリアライザを使い、かつセッションストアを共有する アプリケーション・プール・コマンドラインジョブが影響を受ける」と している**（出典4）〈重要〉。 **CSO Online も優先対象として「複数のアプリケーションが 1つのセッションストアを共有している構成」を挙げている**（出典5）。
    取るべき行動 **`session.save_path` を環境横断で収集し、 同じパス・同じ Redis キー空間を共有している組み合わせを洗い出す。** **共有している場合、`session.serialize_handler` の値が 一致しているかを確認する。** **共有が必要ない組み合わせは分離する。**
  • 暫定対処の副作用を把握してから入れる——接続再利用の無効化は性能を落とし、 アップロード進捗の無効化は phpAfterShell を解消しない。
    **接続再利用はもともと性能のために有効化されている設定である** （本記録の評価）〈重要〉。 **`session.upload_progress.enabled=0` については、 Xakep.ru が「phpAfterShell についてはアップロード進捗を経由する 攻撃経路だけを閉じるもので、脆弱性そのものを解消しない」と 明記している**（出典6。原文ロシア語を訳出）—— **利用者が制御できる大きな文字列をセッションに格納する アプリケーションには別の入力経路が残る**（出典4）。
    取るべき行動 **暫定対処を入れる前に、副作用（性能低下・機能停止・調査情報の欠落）を 確認し、適用期限を決める。** **アップロード進捗を無効化しても phpAfterShell が残ることを前提に、 更新の優先度を下げない。** **PHP 8.5 で `zend.exception_ignore_args=1` を入れる場合は、 障害調査の手がかりが減ることを運用側に周知する。**
  • PHP ワーカーの到達範囲を狭める（資格情報を設定ファイルから出す）。
    **CSO Online が伝えた専門家の説明では、 PHP のコード実行脆弱性を突いた攻撃者は 「PHP ワーカーが触れるものすべて——ほぼ何でも」に到達し、 ワーカーはデータベースのパスワード・API キー・クラウドの資格情報・ セッションデータを保持している**（出典5。原文英語を訳出）〈重要〉—— **示された経路は「設定ファイルを読む→顧客データベースを吐き出す→ 後で戻るためのウェブシェルを置く」である**（出典5）。
    取るべき行動 **設定ファイル内の資格情報を環境変数・シークレットストアへ移し、 ワーカープロセスが直接読める範囲を減らす。** **ウェブ公開ディレクトリへの書き込み権限を外し、 PHP ファイルの新規作成を監視する。** **データベース接続の権限を、アプリケーションが必要とする操作に絞る。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ PHP 8.2.36 未満・8.3.37 未満・8.4.28 未満・8.5.13 未満、 または 8.6.0 のリリース候補を動かしている （コンテナ・アプライアンス・ホスティングのコントロールパネルに 同梱されているものを含む）。**これが本リリースの対象範囲である**（出典2・3・4）〈重要〉—— **ただしディストリビューションがバージョン番号を変えずに バックポートすることがあるため、パッケージの完全なバージョンを 勧告と突き合わせる必要がある**（出典4）。 **該当する場合、更新とワーカーの再起動が要る。**
システム構成□ フロントエンドが PHP-FPM へのバックエンド接続を再利用している （nginx の `fastcgi_keep_conn on`、Apache `mod_proxy_fcgi` の `enablereuse=on`、一部の HAProxy 構成、LSAPI）。**これが CVE-2026-129289（CVSS 9.2）の成立条件である**（出典2・4）〈重要〉—— **接続を再利用しない標準的な構成は影響を受けない**（出典6）。 **該当する場合、認証なしでワーカー権限のコード実行に至りうるため 最優先の対象になる。** **暫定対処（接続再利用の無効化）は性能を落とす**（本記録の評価）。
データの保持□ セッションを既定のファイルセッションハンドラで保存している （`session.save_handler = files`）。**CVE-2026-126714（phpAfterShell）はファイルセッションハンドラが対象であり、 Redis・データベース等にセッションを置く環境は影響を受けない** （出典3・6）〈重要〉—— **該当する場合、セッションに利用者由来のデータが入る経路 （アップロード進捗機能、大きな文字列の格納）を点検する必要がある。**
システム構成□ PHP 8.5 を使っており、致命的エラーのバックトレースが既定のまま有効で、 `zend.exception_ignore_args` を 1 にしていない。**CVE-2026-129474 は PHP 8.5 以降のみが対象であり、 PHP の勧告は「8.5.12（PHP2Shell の緊急修正）での変更が この攻撃経路を到達可能にした」と述べている**（出典4・5）〈重要〉—— **該当する場合、PHP 8.5 を最優先の更新対象にする理由になる。** **`php.ini-production` の既定値である `zend.exception_ignore_args=1` は 実証された攻撃を防ぐ**（出典4）。
運用・監視□ 複数のアプリケーション・FPM プール・コマンドライン処理が 1つのセッションストアを共有しており、 シリアライザの設定が揃っているかを把握していない。**CVE-2026-115560 について PHP は適用範囲を広げ、 異なるシリアライザを使ってセッションストアを共有する アプリケーション・プール・コマンドラインジョブが影響を受けるとしている** （出典4）〈重要〉—— **該当する場合、1つのアプリケーションの更新だけでは塞がらない。**
体制・契約□ PHP 8.2 を本番で使っており、2026年12月31日以降の対応方針 （移行・延長サポート・リスク受容）を決めていない。**PHP 8.2 は2026年12月31日でセキュリティ修正の提供が終わる**（出典1・5） 〈重要〉—— **本リリースから42日であり、本リリースが 8.2 が受ける最後の セキュリティ修正の1つになりうる**（出典5。本記録の算出）。 **該当する場合、年末までに方針を決めないと「修正が存在しないランタイムで 運用する」状態になる。**
