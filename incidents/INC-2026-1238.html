INC-2026-1238Unit 42 が Com 系ビッシング2群を公表

Palo Alto Networks Unit 42 は2026年11月20日、「Com」に連なる攻撃者による ビッシング（電話を使った詐取）の波を2026年8月ごろから継続して観測・対応していると公表し、 新たに2つの活動クラスター CL-CRI-1264（Vortex）と CL-CRI-1274（Cinder）を示した—— いずれも IT サポートを装う電話で AiTM の偽ポータルへ誘導して資格情報と MFA 承認を奪い、 数分で未認可の MFA デバイスを登録、Microsoft 365 からスクリプトでデータを持ち出し、 Teams やメールで内部へ恐喝通知を送る。標的は金融・医療・法務で、米英豪が中心

Unit 42 は2026年11月20日、「Com」に連なる攻撃者によるビッシング攻撃の波を 複数回にわたって追跡・インシデント対応してきたと公表した（出典1）〈重要〉。 攻撃はデータ窃取と恐喝に至り、金融サービス・医療・法務といった 「価値の高いデータを大量に持つ業種」を標的にしている（出典1）。 標的組織の所在は主に米国・英国・オーストラリアである（出典1）。 帰属として示されたのは、名前付きアクターの Bling Libra（別名 ShinyHunters）と、 活動クラスター CL-CRI-1116（Redact。旧称 BlackFile）・CL-CRI-1147（Pink）・ CL-CRI-1182（Falcon）・CL-CRI-1192（Helix）、 および今回新たに公表された CL-CRI-1264（Vortex）・CL-CRI-1274（Cinder）である（出典1）。 CL-CRI-1264 は医療・製薬を中心に狙い、組織ごとに用意したサブドメインへ電話で誘導して AiTM プロキシで資格情報と MFA 承認を中継し、認証から数分のうちに未認可の MFA デバイスを登録する （出典1）——複数の事例で "Pixel 10a" という同じデバイス名が使い回されていた。 持ち出しは Python スクリプト（User-Agent は python-httpx）で Microsoft 365 の メールボックス・OneDrive・SharePoint から行われ、その後 Microsoft Teams で 従業員へ直接「データを盗んだ」と通知し Tor の交渉サイトへ誘導する（出典1）。 CL-CRI-1274 は Duo の MFA 再要求を避けるために「ログイン状態を維持する」 セッショントークンを再生し、python-requests/2.34.2 と Microsoft Graph SDK で SharePoint・OneDrive からデータを集めて持ち出し、 侵害したアカウントから社内へ恐喝のメールと Teams メッセージを送った（出典1）。 また CL-CRI-1192 の調査では、"Google Chrome" と名付けた悪性ブラウザ拡張 （manifest 1.6.111）が見つかっている（出典1）—— キーロガー、全サイトの localStorage/sessionStorage と IndexedDB の窃取、 Microsoft と Google の認証クッキーの収集、ページ内の QR コードの走査、 ウェブカメラの配信、Chrome DevTools Protocol（chrome.debugger）経由の遠隔操作を行う。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**カスタムのマルウェアを使わず、「人を電話で動かし、正規の認証とクラウドの標準機能で データを持ち出す」構成である**（出典1）〈重要〉—— **Unit 42 は「標準的なプレイブックは観測されず、ネイティブのクラウドユーティリティを 用いて実行と永続化を選択的に限定していた」と述べている。** **暗号化は行われない（データ窃取のみの恐喝）。**

  1. 1. 偵察disclosed[1]
    **攻撃者は、SSO ポータル・IT サポートページ・パスキー設定サービスを装う apex ドメインを あらかじめ登録し、標的組織を模した短命のサブドメイン（例 {company}.mfaregister[.]com）を 立てる**（出典1）。 **登録には共通の傾向がある**——**.com／.claims／.report の TLD、 claims・report・okta を含む構造、sso・mfa・2fa・auth・passkey・token・oskey 等の 認証系キーワード、enroll・setup・activate 等の操作系キーワード、 it・support・helpdesk・portal 等の内部支援系キーワード、 レジストラは NiceNIC・Cnobin・Tucows・Dominet、ネームサーバは Cloudflare**（出典1の表2）。
    根拠: Unit 42 が監視するドメイン群と登録情報の傾向（出典1の表2）
  2. 2. 初期侵入disclosed[1]
    **内部の IT サポートを装う電話（ビッシング）で、認証の問題を解決すると称して 標的組織ごとの偽ポータルへ誘導する**（出典1）〈重要〉。 **そのサーバは AiTM プロキシとして動き、入力された資格情報と MFA の承認を リアルタイムで攻撃者に渡す**（出典1）。 **業務端末と私物のモバイル端末の双方が狙われている**（出典1）。 **キットは「Doko's Panel」が共有されており、Okta を標的とする変種では 既定の backend.php が api_FyekIDWY.php に改名されている**（出典1。Push Security の報告を参照）。
    根拠: 金融サービスの1件で、資格情報の入力から MFA の番号照合プロンプトまでの AiTM の全系列がテレメトリに記録された（出典1の図3）
  3. 3. 認証情報アクセスdisclosed[1]
    **CL-CRI-1274（Cinder）は、Duo の MFA の再要求を避けるために、 「ログイン状態を維持する（keep me signed in）」で発行された永続セッショントークンを 再生した**（出典1）〈重要〉—— **同じトークンをプロキシ基盤から再生している。** **CL-CRI-1192（Helix）に帰属する調査では、"Google Chrome" と名付けた悪性ブラウザ拡張が 資格情報の窃取に使われていた**（出典1）—— **キーロガーの常駐、全サイトの localStorage／sessionStorage と IndexedDB の窃取、 Microsoft と Google の認証クッキーの収集、ページ内の QR コードの走査による ログイン／MFA トークンの取得、ウェブカメラの配信を行う。** **拡張は Chrome Web Store には無く、oskeysetup[.]com からダウンロードして 開発者モードで手動サイドロードさせる。名前を "Google Chrome" にすることで、 デバッグ中を示すブラウザの警告バナーを装っていた**（出典1）。
    根拠: 拡張の検体（folderextension.crx／.zip）の SHA-256 と配布 URL、 配布元 IP（31.42.184[.]213）、同一 C2 とハードコード API キーを共有する 1.6.112 版（出典1）
  4. 4. 永続化disclosed[1]
    **CL-CRI-1264（Vortex）は、認証から数分のうちに未認可の MFA デバイスを登録して 永続化していた**（出典1）〈重要〉—— **複数の事例で "Pixel 10a" という同じデバイス名が使い回されている。** **Com 系に共通する永続化の手口として、未認可の MFA デバイスやワークステーション オブジェクトの登録、クラウド基盤の一時資格情報の生成、 未承認の第三者 OAuth アプリやデータ同期ユーティリティの認可、 二次アカウントの用意と冗長な資格情報の収集が挙げられている**（出典1）。
    根拠: 複数事例で共通するデバイス名（Pixel 10a）と、永続化手口の列挙（出典1）
  5. 5. 検知回避disclosed[1]
    **攻撃者は、認証・権限・メールボックスの監視、カレンダー設定とメールボックスルールの変更、 セキュリティ警報イベントの消去、インフラのローテーションを行っていた**（出典1）。 **認証は残留プロキシ網（residential proxy）と商用 VPN を経由している**（出典1）。
    根拠: Com 系攻撃者に共通する手口としての列挙（出典1）
  6. 6. 収集disclosed[1]
    **汎用のメールボックスではなく、価値の高いファイル・文書・データベースを扱う 個人やシステムを選んで収集していた**（出典1）〈重要〉—— **法務ではパートナー間の通信・事務所の戦略・役員報酬・進行中の契約、 金融では私募投資のポートフォリオ・ディールパイプライン・大規模なクラウド データウェアハウス、医療では患者記録と自社研究を含むクラウドデータ基盤が対象になった。**
    根拠: 被害者像（victimology）の記述（出典1）
  7. 7. 持ち出しdisclosed[1]
    **CL-CRI-1264 は Python スクリプト（User-Agent は python-httpx）で Microsoft 365 のメールボックス・OneDrive・SharePoint の内容を自動的に持ち出した**（出典1）。 **CL-CRI-1274 は python-requests/2.34.2 と Microsoft Graph SDK を使って SharePoint・OneDrive から収集・持ち出しを行った**（出典1）。 **Com 系に共通する手口として、Rclone 等の OSS ツールとクラウドストレージの利用、 ネイティブな SaaS・REST API 経由の持ち出し、スクリプト化した HTTP 持ち出し、 SaaS から SaaS への直接転送が挙げられている**（出典1）。
    根拠: 観測された User-Agent 文字列と利用 API・ツールの列挙（出典1）
  8. 8. 影響（暗号化・破壊・改ざん）disclosed[1]
    **持ち出し後、攻撃者は従業員へ直接 Microsoft Teams のメッセージを送り、 データを盗んだと主張して Tor 上の交渉サイトへ誘導した**（出典1）〈重要〉。 **CL-CRI-1274 は、侵害したアカウントを使って社内へメールと Teams で恐喝の通知を送っている** （出典1）。 **医療では、恐喝の通知を社内のチャットチャネルに一斉に流し、 規制当局への報告を脅迫材料にしたとされる**（出典1）。 **暗号化は行われていない**（出典1）。
    根拠: 複数事例に共通する恐喝の通知経路（Teams・メール・Tor 交渉サイト）（出典1）

新しいのは手口ではなく、同じ型を使う集団が増え続けていること原因・手口

Unit 42 が示した7つの名前・クラスターは、ほぼ同じ型を使う（出典1）。

共通する型——①IT サポートを装う電話。②組織ごとに用意した偽ポータル（AiTM）で資格情報と MFA 承認を中継。③未認可の MFA デバイス登録などで永続化。④クラウドのネイティブ機能とスクリプトでデータを持ち出す。⑤Teams・メールで恐喝通知を送り、Tor の交渉サイトへ誘導（出典1）。

違いは細部に出る（出典1）—— CL-CRI-1264（Vortex）は医療・製薬に寄り、認証から数分で MFA デバイスを登録し、複数の事例で "Pixel 10a" という同じデバイス名を使い回していた。 CL-CRI-1274（Cinder）は「ログイン状態を維持する」で発行された永続セッショントークンを再生して Duo の再要求を避け、python-requests/2.34.2 と Microsoft Graph SDK でSharePoint・OneDrive からデータを集めた。

本記録の評価——この構図は防御側にとって有利な面がある。 集団が増えても型が同じなら、効く対策も同じになる ——フィッシング耐性 MFA、MFA デバイス登録の統制、API 経由の持ち出しの検知である。 逆に、集団名を追う運用（「どのグループか」を特定してから対処する）は、7つの名前が並ぶ時点で割に合わない。

暗号化しない恐喝は「ランサムウェア対策」の枠から外れる評価・解釈

本件で暗号化は行われていない（出典1）〈重要〉—— 攻撃者はデータを持ち出し、従業員へ Teams とメールで直接通知して Tor の交渉サイトへ誘導する。

Unit 42 は、暗号化から離れる動きが続いていると述べている（出典1）。同社は年次レポートの数値（2025年の恐喝事案について「暗号化を使わないものが78%」という読み方の文）を引いているが、原文の文意が一読で定まらないため、本記録は背景値として扱い、断定に使わない（齟齬2）。また同社は、暗号化を避けることが法執行の追及をかわす動機でもありうるとしつつ、Bling Libra の「Rey」「Umbreon」とされるメンバーや恐喝サイトの運営者の逮捕が報じられていることから、それだけでは目立たなくならないと述べている（出典1）。

本記録の評価——日本の組織にとっての意味は、対策の置き場が変わることである。 暗号化がないなら、バックアップと復旧は役に立たない。 効くのは、①そもそも認証を奪われないこと（フィッシング耐性 MFA）、②奪われても大量の持ち出しに気づくこと（API・エクスポートの監視）、③恐喝通知が届いた後の判断手順を先に決めておくことである。 ③は技術ではなく、経営の準備である。

狙われる条件は業種ではなく、分散した従業員と集中した SSO被害規模・影響範囲

標的の業種は金融サービス・医療・法務が中心で、建設・ハイテク・運輸物流も頻繁である（出典1）。ただし Unit 42 が挙げる「最も狙われる組織」の条件は業種ではない〈重要〉—— 分散した従業員、集中した SSO、広範なクラウドコラボレーション基盤、そして英語圏の所在である（出典1）。

業種の比重は動いている（出典1）—— 2026年8月は金融サービスが医療の約2倍。9月に医療が逆転し（CL-CRI-1264 の初観測と同時期）、10月も医療が最多で金融が並ぶ。 国では、オーストラリアが8月・9月に観測サブドメインの1%未満から10月に約13%へ上がり、米国に次ぐ2番目になった（出典1）。

攻撃者は同じ組織を繰り返し狙い、失敗した数週間後に戻ってくることもある（出典1）。

本記録の評価——「うちの業種はまだ狙われていない」は条件になっていない。 9月から10月のあいだに業種の順位と国の分布が入れ替わっていることは、標的選定が業種への執着ではなく、条件に合う組織の在庫に沿って動くことを示す（本記録の読み）。 日本の組織に直接の被害は報告されていないが、条件（分散勤務・SSO・M365／SaaS）は一致する〈未確定4〉。

悪性ブラウザ拡張は、警告バナーを「名前」で打ち消していた原因・手口

CL-CRI-1192（Helix）に帰属する調査で見つかった拡張は、"Google Chrome" という名前だった（出典1）〈重要〉。

仕組み——①Chrome Web Store には無く、oskeysetup[.]com からダウンロードして開発者モードで手動サイドロードさせる。②名前を "Google Chrome" にすることで、拡張が動いているときにブラウザが出す警告バナー（Google Chrome がこのブラウザのデバッグを開始しました）を、正常な表示に見せかける（出典1）。

機能——キーロガーの常駐、全サイトの localStorage／sessionStorage と IndexedDB の窃取、Microsoft と Google の認証クッキーの収集、ページ内の QR コードの走査によるログイン／MFA トークンの取得、ウェブカメラの配信、そして Chrome DevTools Protocol（chrome.debugger）を使った C2 遠隔操作（隠しスクリーンショット、入力イベントの送出、クリップボードの窃取、任意サイトへの遷移）である（出典1）。同じ C2 とハードコードされた API キーを共有する 1.6.112 版も見つかっている（出典1）。

Unit 42 は、CL-CRI-1192 がこの拡張を、Chromium 系ブラウザの端末から資格情報を取り出す代替手段として開発したと中程度の確度で評価している（出典1）—— 他の Com 系攻撃者と共有されている可能性には触れつつ、現時点で証拠は無いとしている。

本記録の評価——ここで効く対策は1つに絞られる。 拡張の許可リストと、開発者モードでのサイドロードの禁止である（出典1の推奨）—— 「怪しい拡張を入れない」という利用者側の注意では、名前が "Google Chrome" である相手に勝てない。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 暗号化のない恐喝を前提に、対策の置き場を認証と持ち出し検知へ移す
    **本件では暗号化が行われていない**（出典1）〈重要〉—— **データを持ち出し、従業員へ直接 Teams とメールで通知して交渉サイトへ誘導する。** **この型ではバックアップと復旧の備えが効かない**（本記録の評価）。
    取るべき行動 インシデント対応計画に「暗号化なし・持ち出しのみ」の筋書きを1本加え、 復旧ではなく①認証の遮断と再発行、②持ち出し範囲の特定、 ③恐喝通知を受けた従業員・顧客への説明を手順として書く。
  • ヘルプデスクの本人確認を、攻撃の入口として設計し直す
    **初期侵入はすべて IT サポートを装う電話である**（出典1）。 **Unit 42 の推奨の第1項目も「ヘルプデスクの検証手順の厳格化」である**（出典1）。 **本人確認が弱い窓口は、技術対策を迂回する経路になる**（本記録の評価）。
    取るべき行動 パスワード・MFA の再設定を電話だけで完了させない手順（折り返し・上長承認・ 既存デバイスでの承認）を定め、委託先の窓口にも同じ基準を契約で求める。 逆方向（攻撃者が IT を装う）への利用者側の確認経路も周知する。
  • MFA デバイスの登録と OAuth 承認を「経営が見る指標」に入れる
    **CL-CRI-1264 は認証から数分で未認可の MFA デバイスを登録していた**（出典1）〈重要〉—— **永続化の中心は ID 側の操作であり、端末のマルウェアではない。** **ID 操作の可視化は Unit 42 の推奨にも入っている**（出典1）。
    取るべき行動 月次の報告に「MFA デバイス登録の件数と異常の検知状況」「利用者が承認した 第三者 OAuth アプリの数」を加え、管理者承認への移行計画の進捗を追う。
  • 自社名を冠した偽ポータルの出現を、外部からの警告として受け取る仕組みを作る
    **攻撃者は {company}.mfaregister[.]com のように、標的組織の名前を含む 短命のサブドメインを使う**（出典1）〈重要〉—— **登録の傾向（認証系キーワード・特定のレジストラ・Cloudflare のネームサーバ）も 公表されている**（出典1の表2）。

セキュリティ技術者への示唆
  • フィッシング耐性 MFA（FIDO2／パスキー）へ移し、移行期の旧方式を監視する
    **AiTM プロキシは資格情報と MFA 承認をリアルタイムで中継する**（出典1）〈重要〉—— **番号照合やプッシュ承認では止まらない。** **実際に、資格情報の入力から番号照合プロンプトまでの全系列がテレメトリに 記録された事例がある**（出典1の図3）。
    取るべき行動 高価値データを扱う利用者から順に FIDO2／パスキーへ移行し、 移行完了まで旧方式での認証を条件付きアクセスで制限する。 移行中は旧方式の利用を監視対象にする。
  • 「ログイン状態を維持する」で発行される永続トークンの扱いを見直す
    **CL-CRI-1274 は Duo の MFA 再要求を避けるため、 "keep me signed in" の永続セッショントークンをプロキシ基盤から再生した**（出典1）〈重要〉。 **トークンが端末に紐づいていなければ、盗んだ側でそのまま使える**（本記録の読み）。
    取るべき行動 永続セッションの持続時間を短縮し、トークンを端末に紐づける仕組み（トークン保護）を 有効にする。特権操作では再認証を必須にし、全セッションを即時失効させる手順を用意する。
  • ブラウザ拡張を許可リストで管理し、開発者モードのサイドロードを禁止する
    **見つかった拡張は "Google Chrome" という名前で、警告バナーを偽装していた**（出典1）〈重要〉—— **キーロガー、認証クッキーの収集、QR コードの走査、chrome.debugger 経由の遠隔操作まで行う。** **Chrome Web Store を経由しないため、ストアの審査は防壁にならない**（本記録の読み）。
    取るべき行動 ブラウザの管理ポリシーで拡張を許可リスト方式にし、開発者モードでの読み込みを禁止する。 既存端末の拡張一覧を棚卸しし、出所不明のものを削除する。
  • クラウド API 経由の持ち出しを、User-Agent と件数で基準化して検知する
    **持ち出しは python-httpx・python-requests/2.34.2・Microsoft Graph SDK・Rclone といった手段で行われた**（出典1）〈重要〉—— **カスタムのマルウェアではないため、端末側の検知には現れにくい。**
    取るべき行動 Microsoft Graph・SaaS の API アクセスログを収集し、UA・件数・時間帯・取得量の 基準から外れるアクセスを警報にする。一括エクスポートには上限と承認を設ける。
  • 監査ログを消せない場所へ出し、警報の消去自体を検知する
    **攻撃者はセキュリティ警報イベントの消去、メールボックスルールとカレンダー設定の変更、 インフラのローテーションを行っていた**（出典1）。 **ログが消せる場所にしか無ければ、後からの範囲特定ができない**（本記録の評価）。
    取るべき行動 ID・メール・SaaS の監査ログを即時に外部の保存先へ転送し、 ログの消去・転送設定の変更・警報ルールの無効化を警報の対象にする。
