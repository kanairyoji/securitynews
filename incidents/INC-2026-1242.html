攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃者が用意したウェブページを Muse に書き出させる1回の要求から、 実行時コンテナでのコマンド実行、利用者に承認を求めない戻り経路、 そしてコンテナ外にある同じ利用者のデータと資格情報への到達までが つながった**（出典2。原文英語を訳出）〈重要〉。 **以下の段階は NebuSec が公表した検証の手順であり、 実際の攻撃者による悪用が観測されたものではない**（本記録の明示）。 **検知機会と対策は本記録の評価である。**

  1. 1. 偵察公表・報道に基づく[2]
    Muse の実行環境を解析し、ブラウザ経路が4つあること、同梱 Chromium の 版が公開修正に遅れていること、利用者 VM と実行時コンテナが 同じカーネルを共有していることを把握する。 同梱 Chromium は2026年10月初めの観測で 152.0.7977.82 だった
    根拠: NebuSec の技術記事（出典2）
  2. 2. 初期侵入公表・報道に基づく[2]
    利用者が Muse に、攻撃者が用意したページを書き出させる。 同梱 Chromium のレンダラの不具合（V8 サンドボックスを脱出する パーサの不具合 issue 554034656）でメモリ破壊を任意コード実行に変え、 PDF 書き出し用プロセスの IPC サンドボックスが無効だったため、 エージェントの権限で実行時コンテナ内のシェルコマンドを実行する
    根拠: NebuSec の技術記事（出典2）
  3. 3. 検知回避公表・報道に基づく[2]
    送出を審査する Sentinel の分類規則に合わせて要求を組む。 本体を持たない GET・HEAD・OPTIONS だけが「読み取り」と扱われ、 読み取りは既定設定では利用者の承認を求めずに外へ出られた。 併せて機微データの走査（復号後の電子メールアドレス・電話番号・ ワンタイムコード）、エントロピーのしきい値、 60分あたり 2 MiB／5 MiB の通信量のしきい値を避けて動く
    根拠: NebuSec の技術記事（出典2）
  4. 4. 持ち出し公表・報道に基づく[1] [2]
    利用者の会話履歴と保存された記憶（memories）を外部サーバへ送出する。 利用者への承認ダイアログは出なかった。あわせて会話履歴への項目の 挿入と記憶の改変も可能だった
    根拠: NebuSec の2本の記事（出典1・2）
  5. 5. 権限昇格公表・報道に基づく[2]
    実行時コンテナと利用者 VM が共有する Linux カーネル（Linux 7.0）の メモリ破壊の欠陥を突いてコンテナを脱出し、VM の root を得る。 対象のカーネルイメージを事前に入手できない制約下で、 任意のカーネル読み書きから物理メモリ経由でカーネルイメージを探し、 シンボル表を解析して必要なオフセットを求める汎用の実証コードを用いた
    根拠: NebuSec の技術記事（出典2）
  6. 6. 影響（暗号化・破壊・改ざん）公表・報道に基づく[1] [2]
    VM の root により、実行時コンテナにマウントされていなかった 永続ストレージ、Secure Credential Storage、Sentinel 自体に到達した。 利用者 VM で直接動く処理は Sentinel の cgroup の対象外であり、 審査を経ずに外へ通信できた。影響は当該利用者の VM 内に留まり、 ハイパーバイザや他テナントへの脱出は示されていない
    根拠: NebuSec の2本の記事（出典1・2）

破れたのはモデルの判断ではなく、ブラウザ・送出の分類・カーネルという土台だった原因・手口

本件で最も重いのは、壊れた場所がどこだったかである（本記録の評価）〈重要〉。

Meta は Muse の設計を自ら詳しく公開している（出典4）。要点はこうである（原文英語を訳出）。

  • 「二つの隔離されたセキュリティ領域が1台の上にある、というのが正しい心像で、root を持つ LLM エージェントではない」
  • 「Sentinel はコネクタ操作とネットワーク送出についての唯一の権限主体である。Muse は操作を提案するが、許可を与えられるのは Sentinel だけである」
  • 「エージェントは実際のトークンを一切見ない。したがってプロンプトインジェクション等で実際の秘密を吐かせようとしても無駄である」

これらは実装されていた（出典2）。NebuSec は、コンテナ内で root を得ても外部ネットワークに自由に出られなかったこと、HTTP_PROXY を消してもeBPF がソケットを Sentinel に向け直すこと、コネクタの資格情報が VM 側のワーカーに隔離されていたことを確認している。

それでも通った。通った経路は3つとも、AI の問題ではなかった（本記録の評価）〈重要〉。

  1. 同梱ブラウザの更新遅れ（出典2）。PDF 書き出しに使う Chromium のプロセスは IPC サンドボックスが無効で、レンダラの不具合1件（NebuSec は約500ドル相当と書いている）で、エージェントの権限でシェルコマンドを実行できた
  2. 送出の分類規則（出典2）。本体の無い GET・HEAD・OPTIONS だけが「読み取り」で、読み取りは既定設定では無音で出られた
  3. 共有カーネル（出典2）。コンテナと利用者 VM が同じカーネルを共有しており、カーネルのメモリ破壊で両方を同時に破れた

つまりエージェントの安全を「モデルが騙されないか」の問題として設計すると、残るのはこの3つである（本記録の評価）。Meta 自身が「実行時セルは信頼できないデータを処理する前提である」と書いていた（出典4）とおり、前提は正しかった。破れたのは前提ではなく、その前提を支える部品だった。

「読み取りは無音で通す」という設計判断が、そのまま持ち出しの経路になった評価・解釈

Sentinel の判定は、NebuSec の記述によれば次の順で行われる（出典2）。

  1. 要求を発した処理（プロセス）に紐づける
  2. 組み込みの Rego ポリシーを評価し、拒否に当たれば利用者に聞かずに拒否
  3. 残りを読み取りと書き込みに分ける
  4. 読み取りは、既定の「一部の操作で確認する」設定では無音で出られる
  5. 書き込みは、許可規則に当たらない限り承認を要する

ここで読み取りの定義が効いた——本体を持たない GET・HEAD・OPTIONS だけが読み取り（出典2。原文英語を訳出）。

Sentinel は無防備だったわけではない（出典2）。URL の各要素を16進・Base64 として復号してから電子メールアドレス・+ で始まる国際電話番号・otp や verification_code に付いた6〜8桁の値を探し、復号できない塊は文字種で4つに分けてシャノンエントロピーを測り、怪しい要求は policyguard-nvfp4 という判定モデルに送っていた。さらに60分の移動窓で 2 MiB／5 MiB の通信量のしきい値がある（数値参照）。

それでも抜けた。規則の中で動けば済むからである（本記録の評価）〈重要〉。NebuSec の記述は「それらの規則の中で動きながら、ブラウザの連鎖を使って利用者の会話履歴と記憶を、承認を出させずに我々のサーバへ送った」である（出典2。原文英語を訳出）。

ここから引き出せる一般則がある（本記録の評価）。送出の可否を HTTP の動詞で決めると、持ち出しは必ず動詞の側に寄る。持ち出す側は本体を使う必要が無い——URL に載せればよい。「読み取りだから安全」という前提が成り立つのは、読み取りの要求に情報を載せられない場合だけである。

共有カーネルは、その上に積んだ分離をまとめて無効化した被害規模・影響範囲

3段目の意味は、権限が上がったことではない（本記録の評価）〈重要〉。コンテナの中では既に root だった（出典2）。

変わったのは境界の位置である。NebuSec の記述によれば、カーネル脱出の後に到達したのは次のものである（出典2）。

到達したもの それまで隔離されていた理由
永続ストレージ 実行時コンテナにマウントされていなかった
Secure Credential Storage VM 側のサービスが保持していた
Sentinel 自体 コンテナの外のサービスだった
Sentinel を通らない送出 cgroup に付けた eBPF の対象外だった

最後の行が構造を言い当てている（本記録の整理）。Sentinel の送出強制はコンテナの cgroup に付いた eBPF で実現されていた（出典2・4）。利用者 VM で直接動く処理はその cgroup の外にあり、素通りできた。VM には自身の公開 IPv6 アドレスもあったとされる（出典2）。

つまり「コンテナの外に置いたから守られる」という設計は、コンテナと外側が同じカーネルを共有していると成立しない（本記録の評価）〈重要〉。Meta はこの点を無防備にしていたのではなく、カーネルを削り込み（KALLSYMS_ALL と /proc/kcore を無効化、io_uring を遮断）防御も入れていた（出典2・4）。それでも Linux 7.0 は複数の CVE の影響範囲に入っていた（出典2）。

なお境界は完全には破れていない（出典1・2）。Cloud Hypervisor が利用者 VM と他テナントの間に残り、NebuSec はハイパーバイザや他テナントへの脱出を示していない。これは設計の層が1枚残って効いたということである（本記録の評価）。

2026年9月の Muse の不具合とは別の事案である背景・過去事例

本記録を読むときに混同しやすい事案があるため、区別を明示する（本記録の整理）〈重要〉。

2026年9月に、Muse をめぐる別の脆弱性が報じられている。本記録の作成者が確認した範囲では、macOS 側の研究者による指摘で、Meta 側が短時間で修正を当てたとされるものである。本件（NebuSec・2026年11月20日公表）とは、発見者・経路・対象が異なる。

本記録はその9月の事案の一次資料を取得していないため、内容には踏み込まない〈未確定6〉。ここで述べるのは、「Meta Muse の脆弱性」という括りで両者を同じ事案として扱ってはならないという一点だけである（本記録の判断）。

  • **AI エージェントの安全評価を、プロンプトインジェクションの 試験で終わらせない**
    **本件で破れた3箇所（同梱ブラウザ、送出の分類規則、共有カーネル）は どれもモデルの振る舞いではなかった**（出典2）〈重要〉—— **提供者はモデル側の検査（推論の入出力を別のモデル群で検査する）を 実装していたが**（出典4）、 **起点がブラウザのメモリ破壊だったため、そこには映らない** （本記録の評価）。
    取るべき行動 **自組織のエージェント導入審査の項目に、 「同梱コンポーネントの版管理」「送出制御の判定規則」 「実行環境の隔離機構の種類」の3つを独立した欄として加える。** **プロンプトインジェクション耐性の評価結果だけでは 審査を通さない運用にする。**
  • **「資格情報をエージェントに見せない」は、 その隔離境界が破られない限りでの保証だと理解する**
    **提供者は代理トークンの仕組みで実トークンをエージェントから 隠していたが**（出典4）、 **カーネル脱出の後は資格情報保管そのものに到達された** （出典1・2）〈重要〉—— **NebuSec はこれを「組織にとってより重い risk」として 挙げている**（出典1）。
    取るべき行動 **エージェントに渡す資格情報について、 「保管場所に到達された場合に何ができるか」で範囲を設計する。** **読み取りと書き込みを分け、有効期間を短くし、 利用の記録を提供者から取得できるかを契約時に確認する。**
  • **機密性より先に、完全性（蓄積データの改変）を議題に載せる**
    **本件では会話履歴への項目挿入と記憶の改変も可能だった** （出典1・2）〈重要〉—— **持ち出しは後から気づける余地があるが、 記憶の書き換えは利用者が突き合わせる手段を持たない** （本記録の評価）—— **書き換えられた記憶は、その後のエージェントの判断に そのまま効き続ける。**
    取るべき行動 **自組織でエージェントに長期記憶を持たせる場合、 変更履歴を保持し、復元できる設計にする。** **記憶の変更を利用者が一覧・取り消しできる画面を要件に入れる。**
  • **提供者が設計を公開していることは評価軸として使えるが、 公開の有無と事案時の説明責任は別である**
    **提供者は Muse の安全設計を詳しく公開しており 報奨金制度も一般開放している**（出典4）〈重要〉—— **一方、本件について提供者自身の公表は確認できていない** 〈差異1〉—— **利用者は、研究者側の記述だけで修正の有無を判断することになる** （本記録の評価）。
    取るべき行動 **外部 AI サービスの契約・審査で、 「第三者から脆弱性を指摘された場合の利用者への通知の約束」を 明文で確認する。** **設計文書の充実度と、事案時の通知義務を別の項目として採点する。**
セキュリティ技術者への示唆
  • **送出の可否を HTTP の動詞で決めない**
    **Sentinel は本体の無い GET・HEAD・OPTIONS を読み取りと扱い、 読み取りは無音で通していた**（出典2）〈重要〉—— **持ち出す側は本体を使う必要が無く、URL に載せれば足りる** （本記録の整理）—— **提供者は URL 要素を復号して機微データを走査していたが、 走査で全部を捕まえることはできない**（出典2）。
    取るべき行動 **自組織のエージェント・自動化基盤の送出制御を見直し、 判定の入力に「要求に含まれる情報の量」と「宛先の新規性」を加える。** **動詞による分岐がある場合は、GET のクエリ・パスを 書き込みと同じ扱いにできるか検証する。**
  • **信頼できないコンテンツを描画・変換する処理は、 エージェント本体と同じ隔離境界に置かない**
    **本件の起点は、エージェントと同じコンテナで動く同梱 Chromium と、 PDF 書き出し用プロセスの IPC サンドボックス無効化だった** （出典2）〈重要〉—— **同じ提供者が別経路（VM 内の別コンテナ htch-browser、 都度用意されるブラウザ VM）を持っていたことが、 分けられる余地があったことを示している**（本記録の評価）。
    取るべき行動 **自組織で「HTML→PDF」「画像のサムネイル生成」 「外部ページの取得」を行う処理を列挙し、 それぞれが本体と同じ名前空間・同じ権限で動いていないか確認する。** **同じなら、使い捨ての実行環境に分けて成果物だけ受け渡す。**
  • **同梱コンポーネントの版の遅れを、期限付きの指標として監視する**
    **2026年10月初めの観測で、同梱 Chromium は 2026年9月3日に出たパッチ版のままだった**（出典2。数値参照）〈重要〉—— **コンテナイメージに焼き込まれたブラウザやランタイムは、 OS のパッケージ更新では動かない**（本記録の評価）—— **「更新した」の対象から外れやすい。**
    取るべき行動 **自組織のコンテナイメージに同梱されたブラウザ・ランタイム・ ライブラリを列挙し、上流の修正公開からの経過日数を自動で測る。** **期限を超えた場合に、該当機能を止めるか再ビルドするかの 判断基準を先に決めておく。**
  • **共有カーネルの上に積んだ隔離は、 カーネルが破れると同時に全部無効になると想定して設計する**
    **本件では、コンテナの外に置いた永続ストレージ・資格情報保管・ Sentinel、そして cgroup に付けた送出強制が、 カーネル脱出でまとめて無効になった**（出典2）〈重要〉—— **一方、別種の機構であるハイパーバイザの境界は残って効いた** （出典1・2）。
    取るべき行動 **信頼できないコードを動かす境界について、 重ねている機構の「種類」を数える（名前空間・cgroup・seccomp は すべて同じカーネルに依存する）。** **同種が重なっているだけなら、VM やハイパーバイザなど 別種の境界を1枚入れる。**
  • **「脆弱性がある」と「その境界を越えられる」を分けて測る**
    **NebuSec は、対象のカーネルイメージが手元に無く CPU やメモリ構成を前提にできない制約下で、 汎用の実証コードを作って試行の99.9%超で成功したとしている** （出典2。数値参照）〈差異2〉〈重要〉—— **同社はこの区別を主張の中心に置いている**（出典1）—— **「脆弱性の存在を知ることと、それが機微なデータや 資格情報への到達に使えるかを知ることは別である」 （原文英語を訳出）。**
    取るべき行動 **自組織の脆弱性管理で、環境固有の緩和（カーネルの削り込み・ イメージ非公開・構成の非標準性）を「悪用困難」の根拠に使う場合、 その前提が崩れたときの評価を併記する。** **悪用可能性の判定を、構成の秘匿に依存させない。**
