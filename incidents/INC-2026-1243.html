認証を固めても効かない——既定の Rails は認証の前にこの処理を踏む原因・手口

本件の重さは、あふれるバイト数（1バイト）ではなく到達経路にある（本記録の評価）〈重要〉。

経路はこうである（出典2・3）。

  1. HTML のフォームは GET と POST しか送れない
  2. PUT・PATCH・DELETE を模すため、多くのフレームワークがPOST の _method パラメータを受け付ける
  3. Rack の MethodOverride ミドルウェアがこれを実装しており、_method の値を大文字化する
  4. Rails はこのミドルウェアを既定のスタックに含み、古典スタイルの Sinatra も有効にしている
  5. 攻撃者は、_method のパートに旧来の文字集合を宣言しß の連続を入れた multipart の POST を送る
  6. フレームワークは要求をルーティングしている最中に、つまりアプリケーションのコードや認証の確認が走る前に、その値を大文字化する

Cloudflare の記述は「フレームワークは、まだ要求をルーティングしている段階で、アプリケーションのコードや認証の確認が走る前にその値を大文字化する」である（出典2。原文英語を訳出）。

ここから出る実務上の帰結は厳しい（本記録の評価）〈重要〉。認証・認可をどれだけ固めても、この経路には効かない。ログイン画面しか公開していないアプリケーションも、管理画面を社内からのみに制限したアプリケーションも、HTTP の要求が届く限り同じである。

一方で、到達するのは Rails と古典スタイルの Sinatra に限られる（出典3）。素の Rack と他のフレームワークは既定では露出しない。ただし Veria Labs は「旧来の符号化で受け取った文字列のcase を変えるアプリケーションのコードは、どこから来た文字列であっても影響を受けうる」と付け加えている（出典3。原文英語を訳出）——つまり自分のコードに upcase があるなら、入口は HTTP に限らない。

CVE レコードの記述自体は、処理系の欠陥としては妥当である（本記録の評価）。MITRE の説明文は「Ruby の 3.3.14、3.4.13、4.0.10 より前の版に、case 変換におけるヒープバッファオーバーフローがある。たとえば ISO-8859-1 や Windows-1252 では、バッファの外に1バイトが書かれうる」であり（出典4。原文英語を訳出）、フレームワーク経由の到達経路には触れていない。処理系そのものを見れば「文字列の case を変える処理を呼べる者」が前提になるため、AV:L になる。

だが実務の判断材料としては、これは危険な過小評価である（本記録の評価）〈重要〉。既定構成の Rails が認証前に到達する（出典2・3）という事実が分かっている以上、公開された Web サービスではネットワークから認証なしに届く。

本記録の判断：CVSS の基本値で優先順位をつける運用をしている組織は、本件で取りこぼす。到達経路が公表されている脆弱性については、基本値ではなく「自社の構成で誰が到達できるか」で判断する必要がある。

対処の難しさは、修正を当てる対象が普段の管理単位と違うところにある（本記録の評価）〈重要〉。

修正は Ruby 本体（処理系）にある（出典1・3）。したがって Rails を更新しても、gem を更新しても直らない。必要なのは Ruby 4.0.10・3.4.13・3.3.14 への更新と、背景のワーカーを含むすべての Ruby プロセスの再起動、そしてコンテナイメージの再構築である（出典2）。

さらに難しいのが同梱製品である（出典3）。GitLab・GitHub Enterprise Server・Mastodon・OpenProject・Discourse・Chatwoot は自前の Ruby を抱えているため、修正はベンダーが出すまで待つしかない。Veria Labs の一覧（2026年11月21日更新時点）では、GitHub Enterprise Server（3.22.5 以前）だけが修正版なしの状態だった。その GHES にも2026年11月22日に 3.22.6 が出て、同梱製品の修正は出そろった（出典8）〈重要〉。

ここで実務が取り違えやすいのは、システムの Ruby を更新しても同梱製品は直らないという点である（出典7・9）〈重要〉。GitLab は修正の方法を「GitLab に同梱する Ruby のバージョンを更新すること」と書いており（出典7）、直すのは OS のパッケージではなく製品そのものの版である。逆に、自前でビルドした GitLab は製品を更新しても直らず、Ruby 3.3.14 または 3.4.13 以上へ自分で入れ替える必要がある（出典7）。つまり「Ruby を更新したか」ではなく「どの Ruby を使っている構成か」で確認する作業になる（本記録の評価）。

さらに、GHES のリリースノートには CVE-2026-132825 の番号が無い（出典8）〈差異4〉。記載は「公表された複数の脆弱性を修正するため Ruby を更新した」である。CVE 番号で修正状況を突き合わせる運用は、ここで空振りする（本記録の評価）——同梱製品では、番号ではなく「同梱 Ruby の版が上がったリリースか」で判断する必要がある。

加えて、Cloudflare は見落としやすい点を1つ挙げている（出典2）。ディストリビューションのパッケージは、バージョン番号を変えずに修正を取り込むことがある——したがって ruby -v の出力だけで判断せず、パッケージの完全なバージョンをディストリビューションの勧告と突き合わせる必要がある。

回避策について、資料は一致していない（本記録の整理）。Ruby と Veria Labs は回避策を示していない（出典1・3）。Cloudflare は WAF による緩和を提供しつつ、「WAF は代償的な統制であり、修正の代わりにはならない。WAF が見ない経路からも攻撃は届きうる」と明記している（出典2。原文英語を訳出）——具体的には、オリジンに直接届く通信、内部サービス間の通信、および電子メール・ファイル取り込み・メッセージキュー・背景ジョブ経由の入力である（出典2）。

同じリリースで7件が修正されており（数値参照）、7件を同じ扱いにすると優先順位を誤る（本記録の評価）〈重要〉。
