**GnuPG プロジェクトは2026年11月20日、GPGME（GnuPG を扱うための 標準ライブラリ）に重大な脆弱性（CVE-2026-129975）があるとして GPGME 2.3.1 を公開した。** **細工した非常に長い利用者 ID を含む OpenPGP 鍵により二重解放を起こせ、 たとえば署名済みデータを送りつけることで アプリケーションからデータを持ち出せる。** **プロジェクトは「遠隔コード実行に至る悪用も否定できない」として 即時の更新を強く推奨している。** **原因は、gpg の状態行と鍵一覧を読む2つの内部関数で、 バッファを再確保した際に新しいポインタを文脈オブジェクトへ 書き戻すのが関数の末尾だったため、 読み取りエラー等で早期に戻ると解放済みの古いポインタが残る点にある。** **影響は GPGME 2.3.0 より前のすべての版を使うソフトウェアで、 Gpg4win・GnuPG Desktop・大半のメールクライアント・ 多くの XMPP クライアント・Samba・Flatpak が例として挙げられている。** **発見者は Johan Carlsson、GitLab 経由で2026年11月12日に通知され、 当初2026年11月25日としていた公表は ruby2shell の影響で 11月20日へ前倒しされた。**

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**攻撃は、細工した非常に長い利用者 ID を含む OpenPGP 鍵を 対象のアプリケーションに処理させることで成立する** （出典1）〈重要〉—— **以下の段階は、プロジェクトが公表した原因と影響の記述を 整理したものであり、実際の攻撃が観測されたものではない** （本記録の明示）〈未確定5〉。 **プロジェクトは持ち出しの経路として 「たとえば署名済みデータを送りつけること」を挙げており、 遠隔コード実行も否定できないとしている**（出典1）。 **検知機会と対策は本記録の評価である。**

  1. 1. 初期侵入公表・報道に基づく[1]
    攻撃者が、細工した非常に長い利用者 ID を含む OpenPGP 鍵を 対象に処理させる。プロジェクトが挙げた例は 「署名済みデータを送りつけること」で、 受け手の署名検証の過程で鍵が処理される
    根拠: GnuPG プロジェクトの勧告（出典1）
  2. 2. 実行確認済[1]
    gpg の状態行・鍵一覧を読む内部関数で、1024 バイトのバッファの 再確保が起き、読み取りエラー等で関数が早期に戻ることで 文脈オブジェクトに解放済みメモリを指す古いポインタが残る。 文脈の解放時に同じメモリが二度解放される
    根拠: GnuPG プロジェクトの勧告の原因説明（出典1）
  3. 3. 持ち出し公表・報道に基づく[1]
    二重解放を利用して、アプリケーションからデータを持ち出す。 プロジェクトは持ち出しの手段として 「たとえば署名済みデータを送りつけること」を挙げている
    根拠: GnuPG プロジェクトの勧告（出典1）
  4. 4. 影響（暗号化・破壊・改ざん）公表・報道に基づく[1]
    プロジェクトは「この不具合を悪用して遠隔コード実行を 仕掛けることも否定できない」としている。 実際の悪用は公表時点で報告されていない
    根拠: GnuPG プロジェクトの勧告（出典1）

鍵を1つ処理させるだけで足りる——攻撃の前提が低い原因・手口

本件の実務上の重さは、成立条件の低さにある（本記録の評価）〈重要〉。

プロジェクトの記述はこうである（出典1。原文英語を訳出）——「細工した非常に長い利用者 ID を含む OpenPGP 鍵を使うことで、二重解放を引き起こすことが可能である。この二重解放は、たとえば署名済みデータを送りつけることでアプリケーションからデータを持ち出すのに使える」。

ここで注目すべきは「たとえば署名済みデータを送りつけることで」という部分である（本記録の整理）。OpenPGP の署名検証では、署名に対応する鍵の情報が処理される。つまり攻撃者が用意するのは細工した鍵を含む署名済みデータであり、受け手が特別な操作をする必要はない。

さらに、利用者 ID は鍵の中の自由記述の領域である（本記録の補足）。名前と電子メールアドレスを入れる場所であり、長さの制限を利用者側が意識することはない。

この2つが重なると、攻撃の前提は次のようになる（本記録の評価）。

  • 攻撃者が必要なもの: 細工した鍵1つと、それを含むデータを届ける手段
  • 被害者が必要なこと: そのデータを処理すること（自動検証でも成立しうる）

プロジェクトが「即時の更新を強く推奨する」と書いているのは、この条件の低さに対応している（本記録の評価）。なお、成立に必要な利用者 ID の正確な長さは公表されていない〈未確定1〉。内部バッファの初期の大きさが 1024 バイトであること（数値参照）からそれを超える長さが要ると推測できるが、本記録は断定しない。

二重解放の検査に引っかからない形である、とプロジェクト自身が書いている評価・解釈

プロジェクトは原因を異例に詳しく説明している（出典1）。その最後の一文が、本件の性質を決めている（本記録の評価）〈重要〉。

原因の流れはこうである（出典1。原文英語を訳出）。

  1. gpg から状態行と鍵一覧を読む2つの内部関数が問題の箇所である
  2. 当初 1024 バイトのバッファを確保し、不足すれば再確保する
  3. 再確保のとき、新しいバッファへのポインタは関数内で使われる
  4. しかし文脈オブジェクトへ書き戻されるのは関数の末尾である
  5. したがって読み取りエラー等で早期に戻ると、文脈は更新されず、解放済みメモリを指す古いポインタが残る
  6. やがて文脈が解放されるとき、メモリは二度目の解放を受ける

そして——「途中に他の確保が入るため、メモリ確保機構の一般的な二重解放の検査が働かないことがある」（出典1。原文英語を訳出）。

この一文の意味は実務的である（本記録の評価）〈重要〉。二重解放を検知する仕組みに頼っている環境では、この不具合は静かに通る。 glibc の二重解放検査や、確保機構側の保護は、解放の直後に同じポインタが再び解放される典型的な形を捉える。間に別の確保が挟まると、その前提が崩れる。

本記録はここから一般則を引く（本記録の評価）。「確保機構の保護があるから、この種の欠陥は悪用に至らない」という評価は、確保と解放の順序に依存している。順序は攻撃者が入力の構造で操作できる。

なお、修正の方法も原因の記述から読み取れる（本記録の整理）——再確保したポインタを、関数の末尾ではなくその場で文脈オブジェクトへ書き戻すことである。プロジェクトは「非常に古い版にも素直に適用できる」パッチをT8557 のチケットに添付している（出典1）。

別の脆弱性の日程に引っ張られて、公表が5日前倒しになった組織の対応

本件には、脆弱性の調整済み開示の運用について1つの実例が含まれている（本記録の整理）〈重要〉。

経過はこうである（出典1。原文英語を訳出）。

  • 2026年11月12日: GitLab 経由で通知を受ける
  • 当初の計画: 2026年11月25日を調整済み公表日とする（通知から13日後）
  • 実際: 2026年11月20日に公表（通知から8日後。数値参照）

理由は本件とは無関係である——「新たな Ruby2Shell の不具合により GitLab が前倒しで更新せざるを得なくなったため、我々も GPGME の不具合を2026年11月20日に公表した」（出典1）。

ここで言う Ruby2Shell は Ruby の CVE-2026-132825 であり、本記録では別事案として扱っている（出典4）。GitLab は自前の Ruby を同梱しているため、ruby2shell の修正を前倒しで出す必要が生じた。その配布物に GPGME の修正も含まれることになり、GnuPG 側も公表を合わせざるを得なかった、という構図とみられる（本記録の推定。勧告はそこまで説明していない）〈未確定4〉。

本記録の評価: これは珍しい形の連鎖である〈重要〉。脆弱性 A の緊急の修正が、同じ配布物に含まれる脆弱性 B の秘匿期間を短くした。 配布物を共有している限り、片方の日程がもう片方を動かす。

影響を受けるのは配布元である（本記録の評価）。通知から公表まで8日という期間で、「大半のメールクライアント」（出典1）に及ぶライブラリの修正を取り込み、再ビルドし、配布するのは現実的でない。その埋め合わせとして、プロジェクトは古い版にも適用できるパッチを勧告に添付するという手を打っている（出典1）。

自分が GPGME を使っていることに気づけるか対策・注意喚起

対処の実務上の難所は、技術ではなく棚卸しである（本記録の評価）〈重要〉。

プロジェクトが挙げる影響対象は、製品名ではなく分類である（出典1）。

挙げられている対象 利用者側の自覚（本記録の評価）
Gpg4win OpenPGP を使う意図がある。気づける
GnuPG Desktop / VS-Desktop 同上
大半のメールクライアント 署名検証を自動で行っている場合、意識していない
多くの XMPP クライアント 暗号化の実装に GPGME が使われていると知らないことが多い
Samba OpenPGP を扱っている自覚はまず無い
Flatpak 配布物の署名検証に使う。利用者は意識しない

さらに「共有ライブラリ・DLL・静的リンクのいずれの形でも影響を受ける」（出典1。原文英語を訳出）。静的リンクの場合、ライブラリを更新しても直らない——プロジェクトは「静的リンクのバイナリについては、GPGME 2.3.1 に対して再ビルドすることを忘れないように」と書いている（出典1。原文英語を訳出）。

対処の選択肢は3つである（出典1）。

  1. GPGME 共有ライブラリを 2.3.1 に更新する
  2. DLL が必要な場合は、更新された Gpg4win から取得する（Gpg4win 5.1.2・2026年11月20日から利用可能。出典5）
  3. 更新できない場合は、T8557 のチケットに添付されたパッチを当てる（「非常に古い版にも素直に適用できる」）

あわせて、プロジェクトは更新が不要な対象も明示している——「GPGMEPP と GPGMEQT を更新する必要は無い」（出典1）。不要な作業を増やさないための記述であり、対応範囲を絞る材料として使える（本記録の整理）。

影響を受けたシステム

名称: GPGME を組み込むソフトウェア　ベンダー: 各配布元（Gpg4win・GnuPG Desktop・メールクライアント・XMPP クライアント・Samba・Flatpak 等）　CVE番号: CVE-2026-129975　バージョン: **プロジェクトが例として挙げたのは Gpg4win、GnuPG Desktop、GnuPG VS-Desktop、 大半のメールクライアント、多くの XMPP クライアント、 Samba、Flatpak である**（出典1。原文英語を訳出）〈重要〉—— **個別製品の影響版・修正版は本記録では確認できていない** 〈未確定2〉。 **Gpg4win については 5.1.2 が2026年11月20日から 利用可能であり、変更履歴に 「gpgme: 状態行の読み取りコードにおける二重解放を修正。 CVE-2026-129975（T8557）」と記されている** （出典5。本記録が取得して確認）。　概要: **GPGME を組み込んでいる以上、 各製品の側で修正版を取り込む必要がある**（出典1）〈重要〉—— **利用者が「自分が GPGME を使っている」と 認識していないことが多い点が本件の難所である** （本記録の評価）。　症状: **静的リンクしている場合、 共有ライブラリの更新では直らない**（出典1）〈重要〉—— **プロジェクトは「静的リンクのバイナリについては、 GPGME 2.3.1 に対して再ビルドすることを忘れないように」 と書いている**（原文英語を訳出）。　preconditions: **当該ソフトウェアが GPGME 2.3.0 より前の版を 組み込んでいること**（出典1）—— **なお GPGMEPP と GPGMEQT については 「更新する必要は無い」と明示されている**（出典1）〈重要〉—— **対応範囲を絞る材料になる**（本記録の整理）。

    取るべき行動 **脆弱性管理の起点を、CVE／NVD の登録ではなく 供給元の勧告に置く。** **自組織が依存している主要なライブラリについて、 供給元の告知経路（メーリングリスト・RSS）を 購読対象として登録する。**
セキュリティ技術者への示唆
  • **確保機構の二重解放検査を「悪用困難」の根拠に使わない**
    **プロジェクト自身が 「途中に他の確保が入るため、 メモリ確保機構の一般的な二重解放の検査が 働かないことがある」と書いている** （出典1。原文英語を訳出）〈重要〉—— **確保と解放の順序は、攻撃者が入力の構造で操作できる** （本記録の評価）。
    取るべき行動 **自組織のコードで二重解放・解放後利用の指摘を 「確保機構の保護があるから影響は低い」と評価している箇所を 洗い出し、評価を見直す。** **評価の根拠を「保護機構の存在」ではなく 「到達可能性」に置き換える。**
  • **再確保したポインタは、その場で持ち主へ書き戻す**
    **本件の原因は、再確保した新しいポインタを 文脈オブジェクトへ書き戻すのが関数の末尾だったことにある** （出典1）〈重要〉—— **早期リターンの経路が1つでもあれば、 そこで古いポインタが残る**（本記録の整理）—— **エラー処理の追加でこの種の欠陥が後から生まれる。**
    取るべき行動 **自組織のコードで `realloc` 相当の処理を洗い出し、 戻り値を構造体のメンバへ代入するのが 再確保の直後になっているか確認する。** **コードレビューの観点に 「早期リターンの経路で状態が半端にならないか」を加える。**
  • **外部から来る自由記述の長さを、処理の前に検査する**
    **攻撃の入口は OpenPGP 鍵の利用者 ID という 自由記述の領域である**（出典1）〈重要〉—— **名前と電子メールアドレスを入れる場所であり、 正常な利用で異常に長くなることはない**（本記録の評価）—— **成立に必要な長さは公表されていないが**〈未確定1〉、 **正常値から外れた入力は処理の前に弾ける。**
    取るべき行動 **自組織で外部から取り込む鍵・証明書・メタデータについて、 各フィールドの正常な長さの分布を測り、 上限を超えるものを処理前に拒否する。** **拒否した件数を記録し、攻撃の試行の指標として使う。**
  • **更新が必要な対象と不要な対象を、勧告から正確に読み取る**
    **プロジェクトは 「GPGMEPP と GPGMEQT を更新する必要は無い」と 明示している**（出典1。原文英語を訳出）〈重要〉—— **一方、静的リンクのバイナリは再ビルドが必要である**（出典1）—— **読み飛ばすと、不要な作業と必要な作業を取り違える** （本記録の評価）。
    取るべき行動 **勧告の「Solution」節を、対応範囲の定義として扱う。** **自組織の対応チケットに、 更新対象・再ビルド対象・対象外を明示的に分けて書く。**
  • **署名検証を行うプロセスの外向き通信を制限する**
    **本件の影響は「アプリケーションからデータを持ち出す」 ことである**（出典1。原文英語を訳出）〈重要〉—— **署名検証そのものは外部通信を要しない処理であり （鍵サーバからの取得を除く）、 外向き通信を絞れば持ち出しの経路を狭められる** （本記録の評価）—— **ただし持ち出しの具体的な経路は公表されていない**〈未確定1〉。
    取るべき行動 **OpenPGP の復号・署名検証を行うコンポーネントについて、 通信先を鍵サーバ等の必要な宛先に限定する。** **同じプロセスで他の機微データを扱わない構成にする。**
