Android の詐欺フレームワーク Bazuka には、操作者の管理画面に LLM が組み込まれている。

ThreatFabric の Mobile Threat Intelligence チームが、2026年10月下旬、NFC カード中継アプリの調査中に発見した（出典1）。同社は「また別の OSS を薄く包んだだけのもの」を予想していたが、見つかったのはドロッパー／ダウンローダ・コア・23個のモジュールから成る一式だった（出典1）。

公表の要点は4つである（本記録の整理）。

  • LLM が「誰を狙うか」の判断に使われている。 管理画面は近傍のサーバで動くローカルモデルとAPI 経由の大規模モデルの双方に対応する。ThreatFabric が示したロシア語のプロンプトは、端末が応答しない理由をモデルに尋ね、status・integrity・score・grant-стратег（権限付与の戦略）を返させる形になっている。同社は「関心のある被害者を特定するために AI エージェントが使われている」と書いている（原文英語）。
  • 隠蔽の手口が新しい。 ホーム画面またはロック画面のスクリーンショットを撮り、命令に応じてそれを実画面の上に重ねる。 利用者には何も起きていないように見えるまま、背後で操作が進む。
  • 権限は端末の中で自分で取る。 コアは無線デバッグを有効化してペアリング PIN を傍受し、端末内の ADB デーモンへ TLS で接続して、ADB シェル経由で権限を付与する。モジュールは DEX を InMemoryDexClassLoader で読み込むため、ディスクに残らない。
  • 標的は公表されていないが、日本語が入っている。 国・金融機関の名指しは無い。ただしコアが UI 要素を探す言語はロシア語・英語・中国語・日本語である（出典1）。

帰属は示されていない（出典1）。ThreatFabric は操作者を「サイバー犯罪者」と呼ぶにとどめ、管理画面がロシア語であること・C2 の一つがモスクワにホストされていたことを記述しながら、結論は出していない〈未確定2〉。被害者数・感染台数・検体数も公表されていない〈未確定1〉。

LLM は「誰を狙うか」の判断に入っている——操作者の管理画面に組み込まれている原因・手口出典 [1]

Bazuka の LLM 連携は、マルウェア側ではなく操作者が使う管理画面の側にある（出典1）。

  • 近傍のサーバで動くローカルモデルと、API 経由の大規模モデルの双方に対応する。具体的なモデル名は示されていない（本記録の確認）。
  • ThreatFabric が示したのはロシア語のプロンプトで、端末が応答しない理由をモデルに尋ね、status・integrity・score・grant-стратег（権限付与の戦略）を返させる形である。
  • 操作者は被害者の score（どれだけ狙う価値のある標的か）と、権限要求のダイアログを通していくための戦略をモデルに求められる。
  • 同社は「関心のある被害者を特定するために AI エージェントが使われている」と記している（原文英語）。
  • 管理画面にはAI で生成した画像・動画が多用されている。

ここは評価を分けて書く必要がある（本記録の整理）〈重要〉。

事実として公表されているのは「機能があること」と「プロンプトの形」である。 自律的に詐欺を完遂した事例も、AI 利用による成功率の変化を示す数値も無い〈未確定6〉。ThreatFabric 自身が「自動送金の機能は無い」と明記している（出典1）。

本記録の評価としては、意味は別のところにある。 感染端末が増えたときの「選別」が、人手の限界から外れるという点である。数千台の感染端末から「価値のある標的」を人が選ぶのは手間だが、score を返すモデルがあれば、その手間は台数に比例しなくなる。 防御側にとっての含意は、「一台あたりの攻撃が高度になる」よりも「規模が増えても攻撃の質が落ちない」ことである。

画面を撮って画面に重ねる——利用者には何も起きていないように見える原因・手口出典 [1]

ThreatFabric が「新しい手口」として挙げているのがこれである（出典1）。

ホーム画面またはロック画面のスクリーンショットを撮り、命令に応じてそれを実画面の上にオーバーレイとして表示する。

偽のログイン画面を重ねるのではなく、「正常な画面」を重ねる（本記録の整理）〈重要〉。利用者から見れば端末は待機しているように見え、その背後で遠隔操作が進む。「見た目で気づく」という利用者側の最後の防衛線を外す設計である（本記録の評価）。

オーバーレイ自体は他の用途にも使われている。

  • session_ui —— フィッシングの HTML オーバーレイを表示する
  • optics —— 遠隔操作・画面配信・フィッシングオーバーレイを扱う
  • コアのオーバーレイ機構 —— アクセシビリティ権限を取らせるために使われる

モジュールはDEX を InMemoryDexClassLoader で読み込むため、ディスクに保存されずメモリ上で動く（出典1）。端末のファイルを走査する種類の検査では、23個のモジュールは見えない（本記録の評価）。

権限は端末の中で自分で取る——無線デバッグの PIN を傍受して ADB に繋ぐ原因・手口出典 [1]

Bazuka のコアは、端末内で ADB（Android Debug Bridge）を自分に向けて使う（出典1）。

  1. 無線デバッグ（Wireless Debugging）を有効化する
  2. ペアリング PIN を傍受する
  3. その PIN で端末内の ADB デーモンへ TLS 接続を確立する
  4. ADB シェルのコマンドで自分に権限を付与する

モジュール側では self_adb が組み込みの ADB クライアント、device_control が ADB ブリッジ越しに多数のコマンドを実行する（出典1）。

ThreatFabric はこの手口について、「ADB ブリッジの利用はバンキング型トロイの木馬で標準になりつつある」とし、Bazuka については「現在のアーキテクチャではまだそこに至っていない」と留保を置いている（原文英語）。同社が懸念として挙げているのは次の点である（原文英語）。

「これは非常に憂慮すべき兆候である。マルウェアが各種の権限を密かに取得し、ホストアプリを削除しても生き残る独立したモジュールを展開できるようになるからだ。」

本記録の評価としては、ここが運用に最も効く〈重要〉—— 「怪しいアプリを消したから大丈夫」という復旧手順が、この方向の発展に対しては成り立たなくなる。 現時点の Bazuka はまだそこに達していないが、端末側の対処方針（初期化を選ぶ基準）を先に決めておくべき段階である（本記録の評価）。

標的の国と金融機関は公表されていないが、日本語が探索対象に入っている被害規模・影響範囲出典 [1]

ThreatFabric は標的の国・銀行・ブランドを一つも名指ししていない（出典1。本記録の確認）〈未確定1〉。被害者数も検体数も公表されていない。

公表されているのは、コアが UI 要素を探索する言語である（出典1）。

  • 英語
  • 中国語
  • 日本語

この扱いは慎重にする（本記録の整理）〈重要〉。これは「日本語環境の端末を扱える作りになっている」という公開情報であり、「日本の利用者を狙ったキャンペーンが観測された」という意味ではない。 実被害の層では、日本の利用者・金融機関の被害は確認できていない〈未確定3〉。

それでも国内の金融機関・決済事業者には意味がある（本記録の評価）—— 日本語 UI を扱える Android バンキング型の基盤が、traffer（流入役）による分業を前提とした商用の形で売られている。 配布役を集める仕組みがある製品は、売れた後に配布先が広がる。

ThreatFabric は Bazuka を既知の脅威アクターにも国家にも帰属させていない（出典1）〈未確定2〉。操作者の呼称は「サイバー犯罪者」である。

対応の評価

対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 「AI がマルウェアを自律化した」ではなく「選別の手間が消えた」と読む
    公表されているのは、管理画面が LLM に `score`（標的の価値）と 権限付与の戦略を出させる機能を持つこと、 そして ThreatFabric が「関心のある被害者を特定するために AI エージェントが 使われている」と記したことである（出典1）。 **自律的に詐欺を完遂した事例も、成功率の変化を示す数値も無く、 同社は「自動送金の機能は無い」と明記している**〈未確定6〉。 **効いているのは、感染台数が増えても標的選別が人手の限界に縛られなくなる点である** （本記録の評価）
    取るべき行動 **経営報告で「AI マルウェア」という括りを使わず、 「何が自動化されたのか」を1行で書く規律を入れる** （本件なら「標的の選別と権限要求の誘導文面」）。 そのうえで、**自社の対策が「攻撃の手数が増える」前提で持つかを点検する** ——広く薄い攻撃が前提の閾値（1端末あたりの試行回数など）は、 選別が自動化されると空振りする
  • 「怪しいアプリを削除した」で終わる端末復旧の手順を先に捨てる
    ThreatFabric は、ADB ブリッジの悪用が **「ホストアプリを削除しても生き残る独立したモジュール」**を可能にすると警告し、 **Bazuka は現時点ではまだそこに達していない**と留保している（出典1）。 **到達してから手順を考えると、最初の数件で判断を誤る**（本記録の評価）
    取るべき行動 **端末インシデントの手順に「初期化を選ぶ基準」を先に書く。** 基準の例——①アクセシビリティ権限が与えられていた ②開発者向けオプション／無線デバッグが有効化されていた ③端末が第三者の手に渡った時間がある。 **1つでも該当したらアプリ削除では終わらせず初期化**とし、 **業務データの端末側保持を減らして初期化の判断を軽くしておく**
  • 標的の国が非公表の脅威を「国外の話」として処理しない
    ThreatFabric は標的の国・金融機関を名指ししていない〈未確定1〉。 一方で**コアが UI 要素を探す言語には日本語が含まれる**（出典1）。 **「日本が狙われた」証拠は無いが、「日本語環境を扱える」ことは公表されている** （本記録の整理）—— **traffer による分業を前提にした商用製品は、売れた後に配布先が広がる**
    取るべき行動 **脅威情報の受け入れ基準に「標的国が非公表のとき、 日本語対応の記載を代理指標として見る」を加える。** **金融・決済に関わる組織は、本件を「利用者端末側の前提が崩れた事例」として アプリ側の確認フローの見直しの検討材料に回す**（本記録の評価。 どの方式が有効かは本記録では検証していない）
  • 配布経路の規制（ストア外導入の禁止）は、BYOD では効かないと認める
    入口は利用者による公式ストア外からの導入であり（出典1）、 **会社管理端末なら端末管理で禁止できるが、私物端末には強制できない** （本記録の評価）。 **本件のような基盤は、業務利用される私物端末を経由して組織の認証情報にも届く**
    取るべき行動 **私物端末で業務の認証（2要素認証コードの受信を含む）を行っている範囲を棚卸しし、 「端末が侵害された場合に何が抜けるか」を列挙する。** **2要素認証の方式が SMS に依存している範囲を特に優先する** ——Bazuka は `smsmessage`・`twofa` モジュールを持つ（出典1）
セキュリティ技術者への示唆
  • 端末側の検知を「ファイルの有無」から「挙動と設定変更」に移す
    モジュールは DEX を `InMemoryDexClassLoader` で読み込み、 **ディスクに保存されない**（出典1）。 **ファイル走査型の検査では23個のモジュールは見えない。** 一方で**アクセシビリティ権限の取得・オーバーレイの表示・ 無線デバッグの有効化は設定・挙動として観測しうる**（本記録の整理）
    取るべき行動 **MDM／EMM の検査項目に、①アクセシビリティサービスを有効にしているアプリの一覧 ②開発者向けオプションと無線デバッグ（ADB over Wi-Fi）の状態 ③画面オーバーレイ権限を持つアプリ ④提供元不明アプリの許可状態を入れ、 変化を記録する。** 端末ごとの状態の差分を日次で見る
  • 無線デバッグのペアリング PIN が端末内で傍受されうる前提で設計する
    コアは**無線デバッグを有効化し、ペアリング PIN を傍受して 端末内の ADB デーモンへ TLS 接続する**（出典1）。 **画面を読める権限があれば PIN は秘密ではない**（本記録の整理）—— **「PIN があるから安全」という前提が崩れている**
    取るべき行動 **業務端末では無線デバッグを恒久的に無効化し、 開発・検証用の端末を業務用と分離する。** **検証端末については、有効化を一時的な作業に限り、 作業後に無効へ戻すことを手順に入れる**
  • 公表された IoC を「検知の根拠」ではなく「調査の出発点」として扱う
    示されているのは `brokerok[.]org` の4サブドメイン・ 95.181.213[.]21・170.168.61[.]117・`gargona[.]cash`・ コアの SHA256・4つのポートである（出典1）。 **C2 は Cloudflare 配下にあり宛先 IP で切り分けられない。** **本記録はこれらの悪性を検証していない——照合先のテレメトリが無い**（本記録の明示）
    取るべき行動 **IoC は遡及調査（過去ログの突き合わせ）に使い、 遮断リストへ直接入れる前に自組織での誤遮断の影響を評価する。** **挙動側の指標（WebSocket の常時接続・8443／8444 のような非標準ポートへの外向き通信）を 併せて用意する**
  • フィッシング検知を「偽画面の検出」に寄せない
    Bazuka は**偽のログイン画面だけでなく、 ホーム／ロック画面の実際のスクリーンショットを重ねる**（出典1）。 **「正常な画面が表示されている」ことが、安全の証拠にならない**（本記録の評価）〈重要〉
    取るべき行動 **アプリ側では、オーバーレイ検出（他アプリの重畳の有無）と アクセシビリティ経由の入力の検出を実装の検討対象にする。** **運用側では、利用者への案内を「不審な画面に注意」から 「端末の反応が鈍いとき・勝手に操作されたときの連絡先」へ書き換える**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ 業務で使う Android 端末で、公式ストア外からのアプリ導入 （提供元不明のアプリのインストール）が技術的に可能な状態である本件の入口はここしか無い（出典1）——端末管理で禁止していれば初期侵入が成立しない
認証・認可□ アクセシビリティサービスを有効にできるアプリを制限しておらず、 有効化されているアプリの一覧を把握していないコアはオーバーレイでアクセシビリティ権限を取らせ、 これを足場に遠隔操作・入力記録・権限付与へ進む
システム構成□ 業務端末で開発者向けオプションまたは無線デバッグ（ADB over Wi-Fi）が 有効化できる状態で、その状態変化を監視していないコアは無線デバッグを有効化しペアリング PIN を傍受して 端末内の ADB 経由で権限を自己付与する——ここが最も確実な検知機会である
認証・認可□ 2要素認証に SMS を用いており、受信端末が業務端末または私物端末である`smsmessage`・`twofa` モジュールが SMS と2要素認証コードを扱う（出典1）—— 端末が侵害されると第2要素が同じ端末の中で失われる
運用・監視□ 端末インシデントの手順が「不審なアプリの削除」で終わっており、 初期化を選ぶ基準が文書化されていないThreatFabric は ADB 悪用が「ホストアプリを削除しても生き残るモジュール」を 可能にすると警告している（Bazuka は現時点では未到達）
体制・契約□ 日本語での被害報道が無いことを理由に、海外のモバイル脅威情報を 受け入れ対象から外している標的国は非公表だが、コアの UI 探索言語には日本語が含まれる（出典1）—— 実被害の層と公開情報の層を分けないと、この違いを扱えない
