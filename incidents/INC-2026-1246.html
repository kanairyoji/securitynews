INC-2026-1246FastUnlock: Windows ロック画面迂回

**2026年11月19日、研究者 MSNightmare（別名 Nightmare Eclipse）が Windows 11 のロック画面を迂回する手口 FastUnlock を GitHub で公開した**—— **「パスワードを忘れた」からアカウント回復画面に進み、Win+U で スクリーンリーダー「ナレーター」を有効にすると、 ナレーターが所有する見えない背景ウィンドウにフォーカスが移る。** **Caps Lock を押したまま矢印キーで辿ると設定画面に抜けられ、 「Bluetooth とデバイス」→「自動再生」→「リムーバブルドライブ」→ 「フォルダーを開いてファイルを表示（エクスプローラー）」と進んで、 USB メモリ上の実行ファイルをロック画面アカウント `WsiAccount` の権限で実行できる。** **エンドポイント防御ベンダー ThreatLocker が同日に追試して成立を確認し、 得られるのは管理者ではない `WsiAccount` だと報告した。** **原因は、ナレーターの UI を作り替えた際に 「ロック画面アカウントの文脈では新 UI を出さない」という確認が漏れたことで （SYSTEM として動く場合に出さない旧コードは残っている）、研究者自身がそう説明している。** **研究者は「BitLocker を迂回する」と主張し、 11月更新を適用した Windows 11 26H2 の全暗号化機を5分で突破したと述べているが、 これは暗号を破るものではない**——**TPM 単独構成では起動時に自動でディスクが 解錠されるため、ロック画面に至った時点でファイルは既に読める状態にある。** **2026年11月22日時点で修正は提供されておらず、CVE も採番されていない。 Microsoft の正式な見解は本記録では確認できなかった。** **実環境での悪用を示す情報も無い。**

初報: 2026年11月19日（研究者による GitHub 公開。リポジトリ作成は12時37分 UTC） 最終更新: 2026年11月21日（対象日。本記録の確認作業は11月22日）

Windows 11 のロック画面は、ナレーター（スクリーンリーダー）を経由して迂回できる。

2026年11月19日、研究者 MSNightmare（別名 Nightmare Eclipse）がFastUnlock と名付けた手口を GitHub で公開した（出典1）。同日、エンドポイント防御ベンダー ThreatLocker が追試し、成立を確認している（出典2）。

手順は短い（出典1）。

  1. ロック画面で「PIN を忘れた場合」（パスワードでも可）を押す
  2. Microsoft アカウントの回復画面が操作を促したところで Win+U を押し、ナレーターを有効にする
  3. ナレーターが所有する見えない背景ウィンドウにフォーカスが移る（画面には表示されないが「次へ」ボタンにフォーカスが当たっている）
  4. Caps Lock を押したまま矢印キーで辿り、「数式の読み上げ設定」のリンクをCaps + Enter で開く——設定画面に出る
  5. 「Bluetooth とデバイス」→「自動再生」→「リムーバブルドライブ」→「フォルダーを開いてファイルを表示（エクスプローラー）」
  6. USB メモリを差すと、ナレーターのフォーカスがエクスプローラーに移り、同じキー操作で USB 上の実行ファイルを起動できる

得られる権限は管理者ではない。 ThreatLocker は「WSIAccount 利用者へのアクセスが得られる。これは管理者アカウントではない」と報告している（出典2。原文英語）。物理キーボードでの文字入力はナレーター操作中に働かず、必要な場合はスクリーンキーボードを起動できたという（出典2）。

BitLocker の扱いが本件の要点である（本記録の整理）〈重要〉。研究者は「BitLocker を迂回する」と主張し、2026年11月の更新を適用した Windows 11 26H2 の全暗号化機を「見つけてから5分で」突破したと述べている（出典1）。一方、これは暗号を破るものでも鍵を復元するものでもない（出典3）—— TPM 単独構成（起動時に PIN を求めない既定の構成）では、ロック画面が出た時点でディスクは既に解錠されており、ファイルは読める状態にある。 したがって「BitLocker が破られた」のではなく、「TPM 単独構成の BitLocker は、この経路に対して保護にならない」が正確である（本記録の評価）。

2026年11月22日時点で修正は提供されておらず、CVE も採番されていない（本記録の確認）。Microsoft の正式な見解は本記録では確認できなかった〈未確定1〉。実環境での悪用を示す情報も無い（出典3）〈未確定4〉。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は研究者の公開内容（出典1）と ThreatLocker の追試（出典2）に基づく経路であり、 実環境で観測された攻撃の再構成ではない**（本記録の明示）〈重要〉—— **悪用を示す情報は無い**（出典3）。 **遠隔からの経路ではない。** 起点はロック画面にある端末への物理アクセスで、 **アカウント回復画面からナレーターを起動し、 ナレーターが所有する見えない背景ウィンドウを足場に設定画面へ抜け、 エクスプローラー経由で USB 上の実行ファイルを ロック画面アカウント `WsiAccount` の権限で動かす。** **権限昇格は起きない（管理者にはならない）。**

  1. 1. 初期侵入disclosed
    **攻撃者がロック画面の端末に物理的に触れ、「PIN を忘れた場合」 （またはパスワード）を押して Microsoft アカウントの回復画面を出す。** **回復画面が操作を促した時点で Win+U を押し、ナレーターを有効にする**（出典1）
    根拠: 研究者の公開内容（手順・画面写真・実演動画）／ThreatLocker の追試
  2. 2. 実行disclosed
    **ナレーターを有効にすると、ナレーターが所有する「背景にある見えないウィンドウ」に フォーカスが移る**（「次へ」ボタンにフォーカスが当たるが画面には見えない）。 **Caps Lock を押したまま矢印キーで辿り、「数式の読み上げ設定」のリンクを Caps + Enter で開くと設定画面に出る。** **そこから「Bluetooth とデバイス」→「自動再生」→「リムーバブルドライブ」→ 「フォルダーを開いてファイルを表示（エクスプローラー）」と進み、 USB メモリを差すとエクスプローラーにフォーカスが移って、 同じキー操作で USB 上の実行ファイルを `WsiAccount` の権限で起動できる**（出典1）。 **ThreatLocker は外付けドライブで追試に成功し、 「コードを持ち込む方法は他にもある」と述べている**（出典2）
    根拠: 研究者の公開内容（出典1）／ThreatLocker の独立した追試（出典2）
  3. 3. 収集disclosed
    **`WsiAccount` の権限で動くコードから、 既に解錠済みのディスク上のファイルに到達しうる。** **TPM 単独構成の BitLocker では、ロック画面に至った時点でディスクは 解錠されている**（出典3）—— **FastUnlock は暗号を破るものでも鍵を復元するものでもない。** **ただし `WsiAccount` で実際にどこまで到達できるかは公表されていない** 〈未確定3〉
    根拠: 研究者の記述（BitLocker 迂回の主張）／Habr の技術的説明（TPM の自動解錠）

ナレーターの UI 刷新で「ロック画面アカウントでは出さない」確認が漏れた原因・手口出典 [1]

研究者自身の説明を引用する（出典1。原文英語）。

「The vulnerability exist in the way how narrator handles UI in a locked account context, succesful exploitation results in bypassing bitlocker and executing code in the context of the lockscreen account "WsiAccount"」

本記録による訳: 「この脆弱性は、ナレーターがロック済みアカウントの文脈でUI を扱う方式に存在する。悪用が成功すると、BitLocker を迂回し、ロック画面アカウント WsiAccount の文脈でコードを実行することになる。」

原因についてはこう書かれている（原文英語）。

「In the process of giving narrator a new look, Microsoft forgot to make sure that the new UI does not run in the case it was running in the context of a lockscreen user (interestingly it still has the old code that prevents it from spawning the window if it's running as SYSTEM)」

本記録による訳: 「ナレーターに新しい見た目を与える過程で、Microsoft はロック画面利用者の文脈で動作している場合に新 UI を動かさないことの確認を忘れた（興味深いのは、SYSTEM として動作している場合にウィンドウを生成させない旧来のコードは残っていることだ）。」

ここが設計上の要点である（本記録の整理）〈重要〉—— 「出してはいけない文脈」を判定する処理そのものは存在していて、ロック画面アカウントという文脈が条件から抜けている。 UI の作り替えに伴って、既にあった安全側の判定が引き継がれなかった形である（本記録の評価）。

本記録はこの説明を研究者の記述として扱う〈差異3〉—— Microsoft 側の見解は確認できていない〈未確定1〉。研究者は、過去に自身が見つけたロック画面迂回（ZDI-21-1053 を例示）と比べて「これは使うのが極めて容易だ」とも述べている（出典1）。

得られるのは管理者ではない——しかし「管理者でない」は「無害」ではない被害規模・影響範囲出典 [1] [2]

ThreatLocker は公開と同日に追試し、こう報告している（出典2。原文英語）。

「provides access to "WSIAccount" user, which is not an administrator account」

本記録による訳: 「WSIAccount 利用者へのアクセスが得られる。これは管理者アカウントではない。」

追試で分かった実務的な細部は次のとおりである（出典2）。

  • ナレーターで操作している間、物理キーボードでの文字入力はできなかった ——必要な場合はスクリーンキーボードを起動できた
  • 実演には外付けドライブを使ったが、「端末にコードを持ち込む方法は他にもある」
  • 前提は物理アクセス・回復手順から到達できる Microsoft アカウント・Caps Lock と矢印キーでのナレーター操作の3点

ここで評価を分ける（本記録の整理）〈重要〉。

事実として、権限昇格は起きていない。 管理者にはならない。WsiAccount の権限で実際に何に到達できるかは公表されていない〈未確定3〉。

本記録の評価としては、「管理者でない」で安心するのは早い。 理由は BitLocker 側にある（次節）—— TPM 単独構成ではロック画面に至った時点でディスクが解錠済みであり、読めるファイルの範囲がそのまま露出の上限になる。 また、サインインを経ずに任意の実行ファイルが動くという事実自体が、アプリケーション許可リストや EDR の前提（「ロック中の端末では利用者のコードは動かない」）を崩す（本記録の評価）。

BitLocker は破られていない——が、TPM 単独構成はこの経路の保護にならない評価・解釈出典 [1] [2] [3]

ここが本件でもっとも誤読されやすい（本記録の整理）〈重要〉。

研究者の主張（出典1。原文英語）—— 「BitLocker を迂回する」「これを見つけてから、2026年11月の更新を適用したWindows 11 26H2 の完全に暗号化された機体を突破するまで、合計5分だった」。「適切に保護された BitLocker 機は、攻撃者が物理アクセスを持っていてもアクセスできない」という保証を破るものだとも書いている。

仕組みの側から見た実態（出典3）——

  • 多くの Windows 機は BitLocker でディスクを暗号化している。しかし標準構成ではこの脆弱性から保護されない。
  • TPM が起動時にディスクを自動的に解錠する。 Microsoft の TPM の文書は、PIN の入力を必要とせずに解錠されるこの方式を記述している。
  • したがってロック画面が出た時点で、ファイルは既に読める状態にある。
  • FastUnlock は暗号を破るものでも鍵を復元するものでもない。既に通常どおりディスクを解錠した端末の上で成立する。

両者は矛盾していない（本記録の判断）—— 「暗号を破った」のではなく「暗号が守っていない領域に入った」のである。 正確な言い方はこうなる（本記録の評価）。

TPM 単独構成の BitLocker は、「起動済みでロック画面にある端末」を守らない。FastUnlock はその領域を突く手口である。

この区別は対処の選択に直結する（本記録の整理）〈重要〉。

  • 起動時 PIN（preboot PIN）を構成すれば、電源オフ・休止状態からの起動は守られる（出典1・2・3）
  • しかし起動時 PIN は「まだ起動していない端末」しか守らない。既に起動してロック画面にある端末には効かない（出典2・3）
  • つまり、起動時 PIN と「手を離れる端末は電源オフまたは休止状態にする」はセットでなければ意味が通らない（本記録の評価）

Habr は「ディスク全体の暗号を破られるより軽い問題ではあるが、端末が第三者の手にある場合には現実の脅威である」と評している（出典3）。本記録も同じ位置に置く—— これは遠隔からの攻撃ではなく、紛失・盗難・共用端末の問題である。

修正も CVE も無く、影響する版の一覧も無い——条件で判定するしかない未確定事項出典 [1] [2] [3]

  • Microsoft の修正——提供されていない（出典3。本記録の確認）〈未確定1〉
  • Microsoft の勧告・正式な見解——確認できなかった〈未確定1〉〈差異3〉
  • CVE 番号——採番を確認できなかった
  • 影響を受ける Windows の版の公式な一覧——存在しない（出典3）〈未確定2〉
  • WsiAccount で到達できる範囲——公表されていない〈未確定3〉
  • 実環境での悪用——示す情報が無い（出典3）〈未確定4〉

研究者が確認したのは Windows 11 26H2（2026年11月の更新適用済み）のみで、「他の Windows の版は確認していないので、Windows 10 で動くかは分からない」と明記している（出典1。原文英語）。

この状態での判定方法は一つしかない（本記録の評価）〈重要〉—— 版の番号ではなく、前提条件で判定する。 Habr も「公式の一覧が出るまでは、条件に合致する端末はすべて潜在的に脆弱とみなすべきだ」としている（出典3）。条件は3つに整理できる（出典1・2・3。本記録の整理）。

  1. 攻撃者が端末に物理的に触れられるか
  2. ロック画面の回復手順（「PIN を忘れた場合」）から到達できるMicrosoft アカウントに紐づいた利用者がいるか
  3. ナレーターが利用できるか

なお、無効化の対処としてナレーターを止めるべきかは本記録では推奨しない（本記録の判断）〈重要〉—— ナレーターは支援技術であり、必要とする利用者から機能を奪うことになる。 ThreatLocker と Habr が挙げている対処も、アクセシビリティ機能の停止ではなく物理管理と起動時 PIN である（出典2・3）。

緩和策
item: **重要な端末では BitLocker の起動時 PIN（preboot PIN）を構成し、 TPM 単独での自動解錠をやめる**（出典1・2・3）。　副作用: **電源投入のたびに人が PIN を入力する必要があり、 無人起動・遠隔再起動・キオスク運用・サーバ的な使い方と両立しない** （本記録の評価）〈重要〉。 **また、起動時 PIN は「まだ起動していない端末」しか守らない** ——**既に起動してロック画面にある端末には効かない**（出典2・3）。　effect: would_prevent

CISO・経営層への示唆
  • 「画面ロック」を保護の単位として数えるのをやめる
    FastUnlock は、ロック画面にある端末でサインインを経ずに 任意の実行ファイルを動かす（出典1・2）。 **BitLocker も、TPM 単独構成では起動済みの端末を守らない**（出典3）。 **「ロックしてあるから大丈夫」「暗号化してあるから大丈夫」という 2つの前提が、同時に成り立たない状況である**（本記録の評価）
    取るべき行動 **規程と教育の文面を「席を離れるときは画面ロック」から 「端末が自分の管理下を離れるときは電源オフまたは休止状態」へ書き換える。** **対象を列挙する**——店頭・受付・工場・会議室の共用端末、 来客導線にある端末、持ち出しノート。 **「ロック画面で放置される時間」が構造的に発生する業務を先に洗い出す**
  • 起動時 PIN は「無人起動を捨てる」判断とセットで決める
    対処として研究者・ThreatLocker・Habr のいずれも **起動時 PIN（preboot PIN）**を挙げている（出典1・2・3）。 **ただし起動時 PIN は「まだ起動していない端末」しか守らず、 既に起動してロック画面にある端末には効かない**（出典2・3）。 **さらに、電源投入のたびに人の入力を要するため、 無人起動・遠隔再起動・キオスク運用と両立しない**（本記録の評価）
    取るべき行動 **端末を「起動時 PIN を課す群」と「課さない群」に分け、 課さない群には端末側に重要データを置かない運用を割り当てる。** **判断の根拠（無人起動の必要性・物理的な露出・保持データ）を 1枚の表にして残す**——**修正が出た後も、この分類は資産管理として残る**
  • 修正が無い脆弱性を「CVE が無いから管理対象外」にしない
    **2026年11月22日時点で修正・勧告・CVE のいずれも確認できていない** （本記録の確認）〈未確定1〉。 **影響する Windows の版の公式な一覧も無い**（出典3）〈未確定2〉。 **一方で手順・画面写真・実演動画は公開済みで、 必要なのは物理アクセスとキー操作の知識だけである**（出典1）
    取るべき行動 **脆弱性管理の台帳に「CVE 無し・修正無しの既知の手口」を置く欄を作り、 対処状況（物理管理・起動時 PIN の適用範囲）を記録する。** **判定は版の番号ではなく前提条件 （物理アクセス／回復手順から到達できる Microsoft アカウント／ナレーター）で行う**
  • アクセシビリティ機能を止める方向の対処を選ばない
    経路に使われるのはナレーター（スクリーンリーダー）だが、 **これは支援技術であり、必要とする利用者から機能を奪うことになる** （本記録の評価）〈重要〉。 **研究者・ThreatLocker・Habr が挙げる対処も、 アクセシビリティの停止ではなく物理管理と起動時 PIN である**（出典1・2・3）
    取るべき行動 **「迂回経路に使われた機能を止める」という反射的な対処を、 支援技術については明示的に禁じる方針を持つ。** **原因は機能の存在ではなく、ロック画面文脈での UI 判定の漏れである** （研究者の説明。出典1）——**対処は物理側で取る**
セキュリティ技術者への示唆
  • 自組織で `WsiAccount` 配下の活動が記録・遮断されるかを実機で確かめる
    実行は**ロック画面アカウント `WsiAccount` の文脈**で起こる（出典1・2）。 **アプリケーション許可リストや EDR が 「ロック中の端末では利用者のコードは動かない」ことを前提にしていると、 この経路は想定の外側に落ちる**（本記録の評価）—— **本記録はどの製品がこれを捉えるかを検証していない**
    取るべき行動 **検証用の端末（業務端末ではなく、使い捨ての検証機）で、 `WsiAccount` 配下のプロセス起動がログに残るか・許可リストが効くかを確認する。** **残らない場合は、物理統制側の対処に重みを移す判断材料にする**
  • BitLocker の構成を「暗号化の有無」ではなく「解錠の条件」で棚卸しする
    **TPM 単独構成では起動時に PIN を求めずディスクが解錠される**（出典3）—— **ロック画面に至った時点でファイルは読める状態にある。** **「BitLocker 有効」という台帳の記載だけでは、 この経路に対する保護の有無が分からない**（本記録の評価）〈重要〉
    取るべき行動 **資産台帳の BitLocker 欄を「有効／無効」から 「TPM 単独／TPM＋PIN／TPM＋USB キー」などの解錠条件に細分する。** **そのうえで、物理的な露出が高い端末群（共用・店頭・持ち出し）から 起動時 PIN の適用を検討する**
  • USB の自動再生と大容量記憶装置の接続を、端末群ごとに点検する
    研究者の経路は**「自動再生」→「リムーバブルドライブ」→ 「フォルダーを開いてファイルを表示」**を通り、 **USB メモリ上の実行ファイルが動く**（出典1）。 **ThreatLocker も外付けドライブで追試しているが、 「コードを持ち込む方法は他にもある」と述べている**（出典2）—— **USB の封じ込めは経路の一つを塞ぐだけで、根本の対処ではない**（本記録の整理）
    取るべき行動 **USB 大容量記憶装置の接続と自動再生の設定を端末群ごとに確認し、 業務上不要な群では無効化する。** **ただしこれを「対処済み」と記録しない**—— **他の持ち込み経路が残ることを台帳の注記に書く**
  • 端末が第三者の手に渡った後の扱いを、手順として先に書く
    **この手口は何も壊さず、画面上に痕跡を残さない**（本記録の評価）。 **公開されているのは手順と動画で、必要なのは物理アクセスとキー操作だけである** （出典1）。 **「見た目に異常が無い」ことが安全の証拠にならない**〈重要〉
    取るべき行動 **紛失・盗難・一時的な手放しからの復帰時の手順を書く。** **判断材料——①BitLocker の解錠条件（TPM 単独か） ②手を離れていた時間と場所 ③端末上の保持データ。** **TPM 単独構成で手を離れた時間がある端末は、 初期化と認証情報の再発行を既定の対処にする**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Windows 11 端末で BitLocker が TPM 単独構成（起動時 PIN なし）で運用されている標準構成ではこの経路から保護されない—— ロック画面に至った時点でディスクは既に解錠されている（出典3）
認証・認可□ 端末上の利用者アカウントが少なくとも1つ Microsoft アカウント（オンラインアカウント）に 紐づいており、ロック画面の回復手順から到達できる研究者と ThreatLocker がともに必須条件として挙げている（出典1・2）—— ローカルアカウントのみの端末では回復画面に至らない
運用・監視□ 端末がロック画面の状態で人の手が届く場所に置かれる時間がある （店頭・受付・工場・会議室の共用端末、来客導線にある端末）起動時 PIN は「まだ起動していない端末」しか守らない（出典2・3）—— 起動済みでロック画面にある端末がこの手口の対象である
運用・監視□ 規程・教育が「席を離れるときは画面ロック」で止まっており、 電源オフ・休止状態への移行を求めていない研究者・ThreatLocker・Habr が共通して挙げる対処が 「手を離れる端末は電源オフまたは休止状態」である（出典1・2・3）
運用・監視□ アプリケーション許可リストや EDR の有効性を 「利用者がサインインしたセッション」でしか確認していない実行はロック画面アカウント `WsiAccount` の文脈で起こる（出典1・2）—— この文脈で記録・遮断が効くかは別に確認する必要がある
体制・契約□ 脆弱性管理の対象を CVE が採番されたものに限っている本件は2026年11月22日時点で CVE も修正も確認できないが、 手順・画面写真・実演動画が公開されている（出典1）〈未確定1〉
