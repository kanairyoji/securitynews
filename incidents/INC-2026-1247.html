この事案の構造を一行で言うと、侵害されたのは基盤提供者だが、失われたのは顧客が他システムへアクセスするための鍵である（本記録の整理）〈重要〉。

Kubernetes Secret は、クラスタ内のアプリケーションが外部サービスに接続するための資格情報を置く場所である。データベースのパスワード、クラウドの API キー、コンテナレジストリの認証トークン、Git のデプロイキーなどが入る。つまり Secret を読まれた顧客は、Spot の外側にあるシステムの鍵も同時に失っている（本記録の評価）。

Rackspace の顧客向け指示がこの構造を裏づけている（出典1）。同社は Spot 内での作業（API トークンの再発行・kubeconfig の再取得）だけでなく、データベース・コンテナレジストリ・Git リポジトリ・クラウドストレージ・サードパーティサービスのログを11月17日まで遡って点検せよと求めている。基盤提供者が顧客に「我々の外のログを見よ」と言う指示は、被害の範囲を提供者側では確定できないことの表明である（本記録の整理）。

復旧を優先してアクセスを全遮断したため、顧客は指示された鍵の更新を実行できなかった組織の対応

本件の対応で最も議論を呼んだのは、管理コンソールの長時間停止である（出典1）。

停止は障害ではなく意図的なものだった。Platform9 の共同創業者 Sirish Raghuram 氏はReddit の議論で次のように説明している（出典1。原文英語を訳出）。

ご納得いただけないのは分かっているが、すべてのアクセスを遮断して環境全体を浄化することが、Spot を使うすべての方を守るために我々ができる最善だと判断した

「ご納得いただけないのは分かっているが」という前置きは、顧客から反対があったことを示している（本記録の整理）。

「漏れた鍵をすぐ替えてください」と「鍵を替える窓口は閉めます」が同時に成立していた（本記録の評価）。Rackspace 側の判断には理がある——攻撃者が同じ経路に残っている状態で顧客に操作を続けさせれば、新しいトークンもその場で読まれる。だが顧客から見れば、露出が続く時間が延びたことになる。

漏えいした認証情報から顧客クラスタの Secret、そして Spot の外側のシステムへ至る経路
layer 0 は起点（漏えいした認証情報。漏えい元は非公表）。 layer 1 は基盤（Rackspace Spot の認証を正面から通る）。 layer 2 は顧客テナント——**攻撃者は一部の顧客組織で 正当な利用者として振る舞えた。** layer 3 は攻撃者にできた操作（Pod 作成・Secret 読み取り・ ノードとボリュームの列挙）。 layer 4 は波及先——**Secret に入っていた鍵が指すのは Spot の外側であり、 Rackspace 自身が顧客に点検を求めた5系統がここに並ぶ。** layer 5 は対応（提供者側の失効・顧客側の更新）と、 その実行を妨げた管理コンソールの停止。 **点線に相当する関係——攻撃者が実際に Secret を読んだか、 鍵が実際に悪用されたか——は公表されていない。**

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入機会はあったが検知できず
**約22時間にわたるアクセスが続き、発覚は翌日の顧客からの報告であった** （出典1）〈重要〉—— **基盤提供者側で検知できなかったことは事実として言える** （本記録の整理）。 **ただし「なぜ検知できなかったか」は公表されていない**〈未確定4〉—— **ログが無かったのか、警報が出たのに判断されなかったのかは分からない。** **Rackspace が事後に「監視を強化した」と述べていることは 何らかの不足を示すが、内容は明らかにされていない**（出典1）。
—
権限昇格公表されていない
**顧客組織の側でこの「成りすまされた利用者」の活動が見えたかどうかは 公表されていない**（本記録の確認）〈未確定4〉〈重要〉—— **発覚の端緒が顧客からの報告であることから、 少なくとも1組織では何かが見えていたと考えられるが、 何を見たのかは示されていない**（本記録の整理）。 **マネージドな Kubernetes では、 顧客が自分のクラスタの監査ログにどこまで到達できるかが 提供者の設計次第であり、本件でその点は説明されていない。**
—
認証情報アクセス機会はあったが検知できず
**Secret の読み取りは Kubernetes の監査ログに残る種類の操作である** （本記録の評価）〈重要〉—— **`get`/`list` が Secret リソースに対して行われたかは 監査ログの設定次第で記録できる。** **ただし本件で監査ログが有効だったか、 顧客がそれを参照できたかは公表されていない**（本記録の確認）〈未確定4〉。 **検知の機会そのものは構造的に存在した段階である**（本記録の判断）。
—
内部探索公表されていない
**列挙が検知されたかどうかは公表されていない**（本記録の確認）〈未確定4〉—— **ノード・ボリュームの一括列挙は正常運用でも起きる操作であり、 単体では警報になりにくい**（本記録の評価）—— **Secret の読み取りと同一主体・同一時間帯で起きている点が 検知の手がかりになる。**
—
実行機会はあったが検知できず
**知らない Pod が増えることは、顧客側からも提供者側からも見える** （本記録の評価）〈重要〉—— **資源の消費・課金・ノードの稼働率として現れる。** **発覚が顧客からの報告であったことは、 この段階が顧客側で観測可能だったことを示唆する**（本記録の整理）—— **ただし報告者が何を見たのかは公表されていない**〈未確定4〉。
—
影響（暗号化・破壊・改ざん）公表されていない
**Spot の外側での悪用については、基盤提供者に検知機会が無い** （本記録の整理）〈重要〉—— **顧客が自分のデータベース・レジストリ・Git・ストレージ・ 外部サービスのログを見るしかない。** **Rackspace がまさにそれを指示しているが、 顧客がそれらのログを11月17日ぶんまで保持していなければ実行できない** （本記録の評価）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
環境を浄化するあいだ、管理コンソールへのアクセスを全面的に遮断する部分的に機能**攻撃経路の遮断という目的は達している**（本記録の評価）〈重要〉—— **11月21日に全面復旧し、再侵入の報告は無い**（出典1）。 **不十分だったのは、停止中の代替手段である**（本記録の評価）—— **「管理コンソールは止めるが、トークンの強制失効だけは 別経路（サポート窓口・限定 API）で受け付ける」という設計があれば、 顧客は露出を自力で止められた。** **そのような代替手段が用意されていたという説明は無い**（本記録の確認）。 **また「複数回の延期」が起きたこと自体が、 復旧見込みの伝達が機能しなかったことを示す**（出典1）—— **止める判断は妥当でも、止めている間の説明は不足していた。**
影響顧客への個別通知で侵害の内容・侵害指標・取るべき手順を具体的に示す一方、 公開の場では本件を告知しない不十分**通知の中身は評価できるが、公表の設計は不十分である** （本記録の評価）〈重要〉—— **根拠は、Rackspace 自身が「11月17日まで遡って外部サービスのログを見よ」と 求めていることである**（出典1）—— **その点検が必要な範囲は顧客組織の境界を越えるのに、 境界を越えて届く公表が無い。** **ただし本件は初報の段階であり、 後から公開の告知が出る可能性は残る**（本記録の留保）—— **評価を確定できるのは、調査の結果が公表されるかを見てからである。**
影響したトークンとセッションを提供者側で失効させ、 加えて顧客側にも API トークン・リフレッシュトークン・ kubeconfig・クラスタ Secret の更新を求める評価材料なし**顧客側で更新が完了したかどうかの情報が無い**（本記録の確認）〈重要〉—— **提供者側の失効は実施されたと述べられているが**（出典1）、 **指示の実行率・未実行の顧客への追跡については何も公表されていない。** **この種の指示は「出したこと」ではなく「完了を確認したこと」で 評価すべきである**（本記録の判断）。
CISO・経営層への示唆
  • 管理型 Kubernetes の採用判断に「提供者が侵害されたとき何が漏れるか」を入れる
    **本件で侵害されたのは基盤提供者だが、露出したのは顧客が 他システムへアクセスするための鍵である**（出典1）〈重要〉。 **Kubernetes Secret にはデータベース・クラウド・外部 API の 資格情報が入るため、影響は Spot の中に留まらない**（出典1）。 **Rackspace 自身が顧客に「データベース・コンテナレジストリ・ Git リポジトリ・クラウドストレージ・サードパーティサービスのログを 11月17日まで遡って点検せよ」と求めていることが、 この波及の広さを裏づけている**（出典1。原文英語を訳出）。 **つまり基盤の選定は「基盤の可用性」の話ではなく、 「自社の鍵をどこに預けるか」の話である**（本記録の評価）。
    取るべき行動 **管理型 Kubernetes・管理型 PaaS の採用審査に次の2問を加える。** **①提供者が侵害された場合、当社のどの資格情報が読み取られうるか （Secret・環境変数・サービスアカウントトークンを列挙する）。 ②その資格情報は、更新に当社の何日の作業を要するか。** **②の見積りが「分からない」である基盤には、 長期有効の鍵を置かない方針を先に決めておく**（本記録の評価）。
  • 事故時に「鍵を替えてください」と言われたとき、替える窓口が生きている前提を捨てる
    **本件では、Rackspace が顧客にトークンの再発行を求めた一方で、 その操作をする管理コンソールが長時間停止していた**（出典1）〈重要〉。 **停止は意図的なもので、Platform9 の共同創業者は 「すべてのアクセスを遮断して環境全体を浄化することが最善だと判断した」と 述べている**（出典1。原文英語を訳出）。 **提供者の側には理がある判断だが、顧客から見れば 「漏れた鍵を替えろ」と「替える窓口は閉める」が同時に起きた** （本記録の評価）—— **露出が続く時間を顧客は自力で短くできなかった。**
    取るべき行動 **自社が預けている鍵について「提供者の管理画面が使えない状態で、 その鍵を無効化できるか」を事前に確かめる。** **確かめ方は具体的に3つある**—— **①鍵を使う側（データベース・クラウド・Git）で受け入れを止められるか、 ②鍵をラップしている自社側の Secret ストアで失効させられるか、 ③提供者のサポート窓口に強制失効の手続きがあるか。** **いずれも無い鍵は、提供者の停止がそのまま自社の露出継続になる** （本記録の評価）。
  • 「影響顧客に個別通知」だけの公表では、取引先に届かない露出が残る
    **本記録が2026年11月22日に確認した時点で、 Rackspace Spot の変更履歴にも製品トップページにも本件の記載は無く、 公表の経路は影響顧客への個別通知だけであった**（出典3・4）〈差異1〉〈重要〉。 **一方、露出した Kubernetes Secret に入っていた鍵は、 顧客組織の境界を越えて使われている可能性がある**（本記録の評価）—— **共同プロジェクトの Git デプロイキー、共有レジストリの認証トークン、 取引先が発行した API キーなどである。** **個別通知は Rackspace の顧客台帳の範囲までしか届かない。**
    取るべき行動 **自社が他組織に発行している API キー・デプロイキーについて、 「相手がどの基盤に置いているか」を台帳に書く。** **そのうえで、取引先の基盤に事故があったと知ったときに 自社側から失効を発議する手順を作る**（相手の通知を待たない）。 **逆向きも同じで、自社が預かっている他社の鍵について、 自社の事故時に相手へ知らせる経路を決めておく**（本記録の評価）。
  • 初報で「影響件数」が出ない事案を、小さい事案と読み替えない
    **BleepingComputer が影響顧客数とデータ窃取の有無を問い合わせたが、 Rackspace は回答していない**（出典1）〈重要〉〈未確定1〉〈未確定3〉。 **通知にあるのは「一部の顧客組織」という表現だけである** （出典1。原文英語を訳出）。 **本件のように「何が漏れたかは顧客ごとに違い、提供者には分からない」 構造の事案では、件数が出ないこと自体が構造の帰結である** （本記録の評価）—— **個人情報の件数を数えられる事案とは性質が違う。**
    取るべき行動 **自社が利用者側にいる場合、「通知が来なかったから対象外」と結論しない。** **公表された侵害指標（本件では IP と Pod 名の接頭辞）で 自環境のログを照合し、結果をもって判断する。** **自社が提供者側にいる場合、件数を出せない事案では 「何が分からないか」を明示的に書く**（本記録の評価）—— **沈黙は「小さい事案」と読まれる。**
セキュリティ技術者への示唆
  • Kubernetes Secret から長期有効の静的な資格情報を抜く
    **攻撃者は「影響を受けた利用者のクラスタに格納された いかなる Secret も読み取れた可能性がある」** （出典1。原文英語を訳出）〈重要〉。 **本件の実害の大きさは、Secret の中身がどれだけ長く有効な鍵だったかで決まる** （本記録の評価）—— **無期限のデータベースパスワードや長期の API キーが入っていれば、 読み取られた時点で他システムへの侵入経路が渡っている。** **短期トークンであれば、有効期限が実害を限定する。**
    取るべき行動 **Secret の棚卸しを「有効期限」の列つきで行う。** **無期限・1年以上のものを洗い出し、 ①クラウドのワークロード ID（IRSA・Workload Identity 等）、 ②外部 Secret ストアからの短期払い出し、 ③定期ローテーションの自動化、のいずれかに置き換える。** **置き換えられないものには「読み取られた場合に何が使えるか」を 注記として残す**（本記録の評価）。
  • Secret リソースへの get/list を監査ログで見える状態にしておく
    **Secret の一括読み取りは正常運用ではまれであり、 検知の精度を出しやすい操作である**（本記録の評価）〈重要〉。 **本件では約22時間のアクセスの間に Secret の読み取り・ ノードとボリュームの列挙・Pod の作成が行われているが**（出典1）、 **発覚は顧客からの報告であった**（出典1）〈未確定4〉。 **監査ログが有効だったか、顧客がそれを参照できたかは公表されていない** （本記録の確認）—— **マネージドな基盤では、監査ログの設定と参照可否が 提供者の設計に依存する。**
    取るべき行動 **①自環境で Secret に対する `get`/`list` が監査ログに残るかを確認する。 ②残るなら、日常の呼び出し主体（CI のサービスアカウント等）の一覧を作り、 そこから外れた主体の読み取りを警報にする。 ③マネージドな基盤で監査ログに到達できない場合は、 その事実を「検知できない範囲」として記録し、 代わりに鍵の有効期限を短くする側で補う**（本記録の評価）。
  • 公表された侵害指標は、まず遮断ではなくログ照合に使う
    **Rackspace は IP アドレス `23.224.79.106`・ IP レンジ `23.224.0.0/15`・Pod とオブジェクト名の接頭辞 `i1`・`glm-`・`probe` を公表している**（出典1）〈重要〉。 **`23.224.0.0/15` は13万を超えるアドレスを含む広い範囲であり、 そのまま遮断すると無関係な通信を巻き込む**（本記録の評価）。 **また本記録はこれらの悪性を検証していない**（本記録の明示）—— **照合先のテレメトリを持たないためである。**
    取るべき行動 **①Pod・オブジェクト名の接頭辞 `i1`・`glm-`・`probe` を 自環境の Kubernetes 監査ログ・オブジェクト一覧で検索する （2026年11月17日前後の作成時刻と作成主体を併せて見る）。 ②IP は egress/ingress のログで過去の通信を照合する。 ③遮断は、個別 IP と照合結果を見てから決める。 /15 のレンジ遮断は副作用を評価してから行う。**
  • Pod の作成を「認証」とは別の層で絞る
    **攻撃者は一部の顧客組織で正当な利用者として振る舞えたため、 認証では止まらなかった**（出典1）〈重要〉—— **その状態で Pod を作成している**（出典1。Rackspace は事後に 「不正な Pod を削除した」と述べている）。 **「誰が」ではなく「どこから来た Pod か」を見る制御は別の層である** （本記録の評価）—— **CI・GitOps 以外から来た Pod 作成を拒否・警報にする設計であれば、 正当な利用者の資格情報を持つ攻撃者でもこの段階で止まる余地がある。**
    取るべき行動 **①Admission 制御（Validating Admission Policy・OPA Gatekeeper 等）で Pod の作成主体を承認された経路に限定する。 ②名前空間ごとに ResourceQuota と LimitRange を設定し、 資源の悪用の上限を作る。 ③「知らない Pod が増えた」ことを課金・ノード稼働率の監視と 結びつけて検知する**（本件では顧客側の気づきが発覚の端緒だった） （本記録の評価）。
  • 事故時の点検指示を実行できるだけのログ保持期間を先に確保する
    **Rackspace は顧客に対し、データベース・コンテナレジストリ・ Git リポジトリ・クラウドストレージ・サードパーティサービスのログを 2026年11月17日まで遡って点検するよう求めている** （出典1。原文英語を訳出）〈重要〉。 **これは顧客がそれらのログを当該日ぶんまで保持していることを 前提にしている**（本記録の整理）—— **保持期間が7日や14日の設定では、通知が届いた時点で 指示そのものが実行できない。** **本件では侵入（11月17日）から報道（11月21日）まで4日あり、 通知の到達はさらに後の顧客もいる。**
    取るべき行動 **「事故を知らされてから遡って調べる必要があるログ」を列挙し、 保持期間を最低90日に揃える。** **対象は本件の指示に対応させて5系統**—— **データベースの接続・クエリログ、コンテナレジストリの pull ログ、 Git のアクセスログ、オブジェクトストレージのアクセスログ、 外部 SaaS の API 監査ログ。** **保持期間を延ばせないものは「調べられない範囲」として 明示的に記録しておく**（本記録の評価）。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 管理型（マネージド）Kubernetes・管理型コンテナ基盤を外部事業者から 借りて本番または検証環境を動かしている本件で侵害されたのは基盤提供者側であり、 顧客の環境に不備があったという説明は無い（出典1）—— 顧客側の対策だけでは成立を防げない類型である
認証・認可□ Kubernetes Secret（または同等の仕組み）に、 有効期限の無い・または長期のデータベースパスワード・API キー・ デプロイキーを格納している攻撃者は「クラスタに格納されたいかなる Secret も読み取れた可能性がある」 （出典1。原文英語を訳出）—— 実害の大きさは Secret の中身の有効期間で決まる（本記録の評価）
認証・認可□ 基盤の API トークン・リフレッシュトークンを自動化ツール（CI・ デプロイパイプライン・運用スクリプト）に埋め込んでいるRackspace は顧客に「自動化ツールで使っているリフレッシュトークンの 差し替え」を求めている（出典1）—— どこに埋まっているかの一覧が無いと差し替えが完了しない（本記録の評価）
