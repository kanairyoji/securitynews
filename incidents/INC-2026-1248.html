露出したのは、管理者・技術連絡先のメールアドレス、テナント ID と表示名、初期ドメイン名、国コードと地域情報、ライセンス階層、ディレクトリ同期の状況（有効か・最後の同期時刻）、Connect Health のオンボーディング状況、そして2024年末に廃止された内部サービス向けの失効済み証明書である（出典1）。

一方、Microsoft はパスワード・パスワードのハッシュ・認証トークン・有効な暗号鍵・オンプレミスのサーバと Active Directory のトポロジー・Azure サブスクリプション情報は露出していないと明示している（出典1。原文英語を訳出）。

ここで「有効な」という限定を見落とさないことが重要である（本記録の整理）〈重要〉。失効済みの証明書は露出している。この否定は「使える鍵は出ていない」という意味であり、「鍵の類は一切出ていない」ではない。

本件の性質は、侵入が完了した事案ではなく、侵入の前段が完了した事案である（本記録の評価）〈重要〉。読み取られた情報は、単体ではどれも機密性が低く見える。だが組み合わせると次の接触が作れる。

  • 誰に送れば効くか（管理者・技術連絡先のメールアドレス）
  • どう名乗れば本物に見えるか（テナント表示名・初期ドメイン名）
  • 何を口実にすれば急がせられるか（ディレクトリ同期の状況と最後の同期時刻）
  • どの機能の話をすれば通じるか（ライセンス階層・Connect Health のオンボーディング状況）

Microsoft 自身の助言もこの読みと一致する（出典1）——同社は「露出した管理者メールアドレスとテナント情報を狙った標的型フィッシングおよびソーシャルエンジニアリングへの警戒をセキュリティ担当へ周知するよう」推奨している。

顧客は「自社が影響を受けたか」を自前のログでは確認できない被害規模・影響範囲

本件で顧客側が置かれている状況には、構造的な制約がある（本記録の整理）〈重要〉。

Microsoft 側は「利用可能なテレメトリを精査して、顧客に影響した権限のない API 呼び出しを特定した」と述べている（出典1。原文英語を訳出）。つまりどのテナントが読み取られたかを知っているのは Microsoft だけである。

一方、顧客に提供された確認手段は次の2つである。

  1. 通知を受け取ったか（Azure Service Health 経由）（出典1）
  2. aka.ms/ConnectHealth/scripts のスクリプト（出典1・2・3）

2つめには明確な限界がある。BleepingComputer はこう書いている（出典1。原文英語を訳出）—— 「ただしこのスクリプトは、侵害の際に実際にアクセスされた情報ではなく、現在の設定値を表示する」。

つまりスクリプトで分かるのは「自組織について API が何を返すか」であり、「それが読み取られたか」ではない（本記録の整理）。本記録が2026年11月22日にスクリプトの到達先を確認したところ、GitHub の AzureAD/EntraIDGovernance リポジトリに読み取り専用のPowerShell 9本が実在し、README は「Connect Health の API が自組織について返す情報を確認できるようにするための参考として提供する」と説明していた（出典3。原文英語を訳出）〈差異1〉。README に事案への言及は無い。

Microsoft は顧客に Entra の監査ログとサインインログの精査も推奨しているが（出典1）、露出したのは読み取り専用のメタデータであり、攻撃者の読み取りが顧客テナントの監査ログに残るとは述べられていない（本記録の明示）〈重要〉。

結果として、顧客が取れる現実的な立場は1つである（本記録の評価）—— 通知を受け取ったなら、列挙された5項目が露出した前提で動く。受け取っていないなら、それ以上の確認手段は無い。

109日は「侵入から検知まで」ではない（本記録の明示）。Microsoft は悪用がいつ始まったかを公表していない。BleepingComputer も「攻撃がいつ始まったのかを Microsoft は明らかにしていない」と明記している（出典1。原文英語を訳出）。

ただしこれを「だから実際は短かったのだろう」と読み替える根拠も無い（本記録の評価）〈重要〉。言えるのは上限と下限だけである——読み取られていた期間は109日を超えない。それ以上の絞り込みには、Microsoft が持っているテレメトリの精査結果が要る。

2024年末に廃止された内部サービスの証明書が、2026年11月まで API から返されていた原因・手口

露出した5項目のうち、性質が他と異なるものが1つある（本記録の整理）〈重要〉。

Microsoft は、2024年末に廃止された Microsoft 内部サービスへConnect Health エージェントを登録するために使われていた失効済み証明書が露出したと述べている（出典1）。さらに「その失効済み証明書はもう使われていないが、Connect Health の保管領域に残っており、API から返され続けていた」と説明している（出典1。原文英語を訳出）。

これは API の不備とは別の問題である（本記録の評価）〈重要〉。登録先のサービスが廃止され、証明書が失効した時点で、その証明書は保管領域から消えているべきだった。消えていなかったため、API の不備が見つかったときに「返されるもの」の一覧に乗っていた。

本記録はこれを原因の一つ「失効・期限切れ」として記録した。不備の悪用と設計・実装上の不備に加えて、使われなくなった資産が削除されないまま応答に乗り続けるという第3の原因があったという整理である（本記録の判断）。

なぜ削除されなかったのか、同様に残っている資産が他にないのかは説明されていない（本記録の確認）〈未確定8〉。Microsoft は有効な暗号鍵は露出していないとしており（出典1）、失効済み証明書の実害については言及していない。

日本の読者への含意は、自組織の API にも同じ構造がありうるという点である（本記録の評価）—— 廃止したシステム向けの資格情報・証明書・識別子が、データストアと API の応答に残っていないか。これは脆弱性診断では見つからず、棚卸しでしか見つからない種類の問題である。

MSP 経由で管理されているテナントでは、1つのアドレスの露出が複数組織に効く波及・関係先

BleepingComputer は、複数のマネージドサービス事業者（MSP）が自社の管理する複数の顧客テナントについて通知を受けたと報告している、と書いている（出典1）。ある管理者は「メールが数時間おきに届いた」と述べている（出典1）。

出所は Reddit の投稿であり、Microsoft の公表ではない（本記録の明示）〈差異2〉。

それでもこの構造は押さえておく価値がある（本記録の評価）〈重要〉。MSP が顧客テナントの管理者・技術連絡先として登録されている場合、露出した管理者メールアドレスは MSP の担当者のものである。すると次の形のなりすましが成立しうる。

  • MSP の担当者を騙る → 顧客組織に「Entra 同期の障害対応」として接触する
  • 顧客組織を騙る → MSP の担当者に「うちのテナントの設定変更」を依頼する

後者が成り立つのは、攻撃者がテナント表示名・初期ドメイン名・ライセンス階層・最後の同期時刻を持っているためである（出典1）。MSP 側からは「本物の顧客からの本物らしい依頼」に見える。

Microsoft はこの点に言及していない（本記録の確認）〈未確定4〉。本記録は構造の指摘として記録し、事実としては主張しない。

    取るべき行動 **①自社 API の応答に含まれるフィールドを一覧化し、 各フィールドについて「いまも必要か」を判定する （特に証明書・識別子・接続先情報）。 ②システム廃止の手順書に「当該システム向けの資格情報・証明書を データストアと API の応答から削除する」を項目として追加する。 ③半年ごとに、廃止済みシステムの名前でデータストアを 全文検索して残存を検出する**（本記録の評価）。
  • API の変更投入時に、テナント境界の認可判定を自動検査に組み込む
