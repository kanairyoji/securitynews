INC-2026-1250GL.iNet クラウド侵害で機器に不正プログラム

GL.iNet のクラウド遠隔管理サービス（GoodCloud）の脆弱性が悪用され、 同社のルータおよび KVM 機器の一部に不正なプログラムが仕掛けられた事案 （2026年11月20日に把握・同日にクラウド側を修正して攻撃経路を遮断・ 感染の目印は `crond -i /tmp/.log` というプロセス・ KVM 向けのベータ版修正を先に提供し安定版は11月22日予定・ 影響台数と悪用の開始時期とプログラムの挙動は公表されていない・ KVM に接続された計算機への影響は調査中）

不正アクセス・侵害委託先・再委託先起因で委託元多数に波及脆弱性続報が続いている日本に波及した海外事案設計・実装上の不備既知の脆弱性の悪用委託先・供給元起因
初報: 2026年11月20日（GL.iNet による公表。本記録が起点としたのは11月21日の研究者による共有） 最終更新: 2026年11月22日

GL.iNet は2026年11月20日、自社のクラウド遠隔管理サービスに脆弱性があることを把握し、権限のない第三者がそれを悪用して同社のルータおよび KVM 機器の一部にアクセスし、不正なプログラムを仕掛けていたと公表した（出典1・2）〈重要〉。同社は「GL.iNet はクラウド遠隔管理サービスに脆弱性を特定した」「権限のない第三者がその脆弱性を悪用した」と述べ、発見と同時にクラウド側の脆弱性を修正し「攻撃経路は遮断された」としている（出典1・2。原文英語を訳出）。ただしこの修正は、すでに機器に入り込んだプログラムを取り除くものではない（出典1・2）〈重要〉。影響するのは GoodCloud（クラウド遠隔管理）と連携させていた機器である（出典3）。感染の目印は具体的に示されている（出典1・2）〈重要〉—— 稼働中のプロセスの一覧に crond -i /tmp/.log という文字列が現れるかどうかで判定する。 ルータでは LuCI 管理画面の「Status → Processes」で tmp/.log を探すか、SSH で ps | grep tmp を実行する。KVM では Toolbox → Terminal → Access からps -a | grep tmp（RMQ1）または ps -aux | grep tmp（他機種）を実行する（出典1）。KVM 向けには修正を含むベータ版ファームウェア（多くの機種は 1.10.2 beta 以降・RMQ1 は 1.8.6 beta 以降）が先に提供され、ルータと KVM の安定版は2026年11月22日に提供予定とされている（出典1）。影響台数、悪用がいつ始まったのか、仕掛けられたプログラムが何をするのか、影響したルータの機種はいずれも公表されていない（出典1・2）〈未確定1〉〈未確定3〉〈未確定4〉。KVM に接続されていた計算機に影響が及んだかどうかは調査中である（出典1）〈重要〉。

公表されている事実は、対処に必要な範囲では具体的である（出典1・2）。

  • GL.iNet が2026年11月20日に、自社のクラウド遠隔管理サービスの脆弱性を特定した（出典1）
  • 権限のない第三者がそれを悪用し、同社のルータおよび KVM 機器の一部に不正なプログラムを仕掛けていた（出典1・2）
  • 同社は発見と同時にクラウド側を修正し、「攻撃経路は遮断された」とした（出典1）
  • ただしこの修正は、すでに感染した機器からプログラムを取り除くものではない（出典1・2）
  • 影響するのは GoodCloud（クラウド遠隔管理）と連携させていた機器とされる（出典3）
  • 感染の目印は、稼働中のプロセスに現れる crond -i /tmp/.log という文字列（出典1）

この事案の構造を一行で言うと、利用者の機器の設定がどれだけ適切でも防げなかった（本記録の評価）〈重要〉。

原因は供給元のクラウドにあり、侵害の経路はそのクラウドと機器の間の正当な管理チャネルである。パスワードを強くしても、ファームウェアを最新にしても、機器側からこの経路は閉じられない—— 閉じられる唯一の操作は GoodCloud 連携を切ることであり、それは事前の選択でしかない（本記録の評価）。

なぜクラウドの侵害が機器の操作に直結したのかは、GoodCloud の機能の性質で説明できる（本記録の整理）〈重要〉。同社の文書によれば、GoodCloud はルータの管理画面と SSH 端末をどこからでも開けるようにする基盤である。遠隔から機器の中に入れる仕組みが、そのまま攻撃者の経路になった。

なお同社は「クラウドの脆弱性」とだけ述べており、その技術的な性質は公表していない〈未確定2〉。

対応は把握・遮断・公表が同日で、点検手順も具体的に示されている組織の対応

本件の対応は、同種の事案と比べて速い（本記録の評価）〈重要〉。

注目すべきは順序である（本記録の整理）〈重要〉。安定版の修正ファームウェアが無い段階で公表している。公表時点で利用者に提供されたのは、点検手順と、KVM 向けのベータ版、および工場出荷状態への初期化という選択肢である（出典1）。

これは「直してから知らせる」ではなく「知らせてから直す」順序である。本件ではこの順序が正しい（本記録の評価）—— 機器に入り込んだプログラムは、クラウド側の修正では消えない（出典1・2）。つまり利用者が動かなければ何も終わらない事案であり、公表が遅れればその分だけ感染が居座る。

さらに評価できるのは、通知を待たせない書き方である（本記録の評価）〈重要〉。同社は影響を特定した顧客にメールで個別連絡するとしながら、「メールを待たずに機器を点検し更新してよい」と明記している（出典1）。通知の到達を前提にしない設計である。

「見つからなかった」は「感染していない」ではない対策・注意喚起

点検手順は具体的だが、限界がある（本記録の評価）〈重要〉。

公表されている目印は、稼働中のプロセスに現れるcrond -i /tmp/.log という文字列1件だけである（出典1）。これは「いま動いているか」しか分からない（本記録の整理）。

プロセスが止まっている状態で点検すれば、感染していても見つからない。同社は grep の自己表示についての注意は添えているが、プロセスが稼働していない場合については述べていない（本記録の確認）〈未確定7〉。

公表されていない指標は多い。

  • 通信先の IP アドレス・ドメイン
  • ファイルのハッシュ値
  • 永続化のために書き換えられる設定ファイル
  • プログラムの挙動〈未確定4〉

公式フォーラムでは、利用者から/etc/uci-defaults・/etc/rc.local・/etc/sysupgrade.conf を点検するよう指摘する投稿や、再起動で消える遠隔シェルを観測したという報告、指標とログの追加公開を求める声が出ている（出典5）。ただしこれらは利用者の投稿であり、GL.iNet の公表ではない（本記録の明示）〈差異1〉。本記録はこれらを事実として扱わない。

実務上の結論は1つである（本記録の評価）〈重要〉—— GoodCloud 連携を有効にしていた機器については、点検結果が陰性でも、安定版ファームウェアの適用（必要なら工場出荷状態への初期化）まで行う。点検は「感染が確定した機器を先に処置する」ための優先順位付けに使い、「対処不要の判定」には使わない。

KVM の侵害は、機器の外にある計算機に届きうる波及・関係先

本件で影響を受けたのはルータと KVM 機器だが、この2つは性質が違う（本記録の整理）〈重要〉。

KVM は、遠隔から計算機の画面と入力（キーボード・マウス）を操作する装置である。機器が侵害されれば、接続先の計算機の操作が可能になりうる。

GL.iNet 自身がこの点を調査中としている（出典1）——影響範囲の特定には「影響を受けた KVM に接続されていた計算機が影響を受けたかどうか」が含まれる。

そのうえで同社は、感染した KVM の利用者に対し、接続先の計算機について次を点検し、フルスキャンを行うよう推奨している（出典1）。

  • 見慣れないプログラム
  • 見慣れないブラウザ拡張
  • 見慣れない利用者アカウント
  • 起動時の実行項目
  • スケジュールされたタスク
  • 異常な通信

この一覧の意味は明確である（本記録の評価）〈重要〉—— 機器を足場にして接続先の計算機に何かが仕掛けられる可能性を前提にした助言である。ただし同社は、それが実際に起きたとは述べていない。

KVM が使われる場所を考えると、影響の重さが見える（本記録の評価）。KVM は、画面を直接見られない計算機——サーバラックの中、無人の拠点、自宅の自作サーバ——に対して使う。つまり KVM の先にあるのは、人の目が常に届かない計算機である。接続先の点検を推奨されても、その計算機にログインして調べる手段が KVM しかない場合、点検そのものが難しい。

    **公表された目印は、稼働中のプロセスに現れる `crond -i /tmp/.log` という文字列である**（出典1）〈重要〉。 **GL.iNet は「grep コマンド自身が表示されただけの行は 該当しない」と注意を添えているが**（出典1。原文英語を訳出）、 **プロセスが稼働していない場合については述べていない** （本記録の確認）〈未確定7〉。 **永続化の具体的な仕掛け（書き換えられる設定ファイル等）も 公表されていない。** **公式フォーラムでは利用者が `/etc/uci-defaults`・`/etc/rc.local`・`/etc/sysupgrade.conf` の 点検を指摘しているが、同社の公表ではない**（出典5）〈差異1〉。
    取るべき行動 **点検の手順を3段階で組む。** **①まず公表された手順で稼働プロセスを見る （ルータ: LuCI の Status → Processes で `tmp/.log` を検索、 または SSH で `ps | grep tmp`。 KVM: Toolbox → Terminal → Access から `ps -a | grep tmp`（RMQ1）／`ps -aux | grep tmp`（他機種））。 ②陽性の機器を先に処置する。 ③陰性でも、安定版ファームウェアを適用する。** **①の結果を「感染していない証明」として記録しない** （本記録の評価）。
  • 遠隔管理を有効にしている機器に、それを切る手順を用意しておく
    **影響するのは GoodCloud と連携させていた機器であるとされる** （出典3）〈重要〉。 **ただし事後に連携を切っても、 すでに入り込んだプログラムは消えない**（出典1） （本記録の整理）〈重要〉—— **連携を切ることは「これ以上入られない」ための措置であり、 浄化ではない。** **順序を間違えると、切ったことで安心して 機器の浄化を飛ばしてしまう。**
    取るべき行動 **遠隔管理（クラウド連携）を有効にしている機器について、 「切る手順」と「切った後に必要な作業」を1枚にまとめる。** **書くのは3点**—— **①連携を切る操作（機器側・クラウド側の両方）、 ②切った後も必要な浄化（初期化・ファームウェア適用）、 ③切ったことで失われる運用（遠隔からの設定変更ができなくなる）への 代替手段。** **③を決めていないと、業務が止まるため切れない** （本記録の評価）。
  • 小型ルータ・KVM のログを外部に送出する設定を、事前に用意する
    **悪用の開始時期が公表されていないため、 利用者は「いつからの通信を疑うべきか」を決められない** （出典1・2）〈未確定3〉〈重要〉。 **さらに、小型ルータ・KVM は通常ログを外部へ送出する設定に なっていない**（本記録の評価）—— **つまり範囲が決まらないうえ、決まっても調べる材料が無い。** **本記録はこれを本件固有の問題ではなく、 この種の機器に共通する構造の問題として整理する。**
    取るべき行動 **遠隔管理を有効にしている機器について、 次の3種のログを機器の外へ送出する設定を入れる。** **①認証ログ（管理画面・SSH の成功と失敗）、 ②設定変更のログ、③外向き通信のログ（可能な範囲で）。** **送出先は、機器が侵害されても書き換えられない場所にする** （本記録の評価）〈重要〉—— **機器上のログは、機器が侵害された時点で信頼できない。** **送出が機器の能力上できない場合は、 上流のルータ・ファイアウォールで 当該機器の通信を記録する。**
  • 感染が確定した機器は、初期化してから新しい資格情報で再構成する
    **GL.iNet は、感染していた場合の対処として 工場出荷状態への初期化、または KVM のセキュリティ修正ベータ版の 適用を挙げている**（出典1）〈重要〉—— **「いずれの場合も、安定版が出たら適用することを推奨する」** （原文英語を訳出）。 **ただしプログラムの挙動は公表されていないため**〈未確定4〉、 **機器上に保存されていた資格情報 （無線の事前共有鍵・VPN の鍵・クラウドアカウントのトークン）が 読まれたかどうかは分からない**（本記録の評価）〈重要〉。
    取るべき行動 **感染が確定した機器については、初期化・更新に加えて 機器が保持していた資格情報をすべて更新する。** **対象を列挙する**—— **①無線の事前共有鍵、②VPN の鍵・証明書、 ③機器の管理者パスワード、 ④GoodCloud 等のクラウドアカウントのパスワードと 連携トークン、⑤機器経由で到達できた内部機器の資格情報。** **⑤を忘れやすい**（本記録の評価）—— **ルータが侵害されていた期間、 その先の機器への通信は攻撃者の位置から見えていた可能性がある。**
