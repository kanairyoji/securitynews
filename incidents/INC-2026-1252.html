INC-2026-1252推論プロバイダ3社でプロンプト窃取

AI推論プロバイダ3社が数か月にわたり侵害され、利用者のプロンプトが盗まれていた—— OpenRouter は3社を切り離し125のエンドポイントから「データ無保持（ZDR）」の 資格を剥奪、盗まれた要求にはZDR指定のものも含まれていた

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害意図せぬ露出（設定不備等で外部から到達可能だった）初報のみ有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因認証情報の悪用（使い回し・推測可能・窃取）ガバナンス・組織文化（ガイドライン理解不足・丸投げ等）作業ミス・誤操作
初報: 2026年11月19日（Dragos の調査レポート公開） 最終更新: 2026年11月23日

産業制御システムのセキュリティ企業 Dragos は2026年11月19日、AI推論プロバイダ3社の内部から攻撃者が数か月にわたりデータを盗んでおり、3社はいずれも研究者が知らせるまで気づいていなかったと公表しました（出典1・2・4）。

Dragos は2026年7月から11月の5か月間、固有の URL とカナリア認証情報を埋め込んだ約200万件のプロンプトを広く使われている AI サービスへ送り、その秘密がどこで浮上するかを観測しました（出典1）。最初の侵害は2026年7月中旬です。最大のものは10月下旬のいくつかの時間帯で、その時間帯に送った要求はすべて盗まれていました（出典1）。残る2件の侵害では、盗まれた要求の一部に「データ無保持（Zero Data Retention・ZDR）」の指定が付いていました（出典1）。

これを受けて AI ルーティング基盤の OpenRouter は2026年11月22日、調査に基づき3社を切り離し（off-board）、125のエンドポイントから ZDR の資格を剥奪したと公表しました（出典2）〈重要〉。OpenRouter は「今回の知見は OpenRouter 自身の侵害や権限のないアクセスを示すものではない」と明記し、影響を受けた可能性のある顧客への通知は完了したとしています（出典2。原文英語を訳出）。

プロバイダ側で唯一、原因まで公表したのは Together AI です（出典3）〈重要〉。同社によると、AIコーディングエージェントが公開 GitHub リポジトリ xorl の開発中に、非公開の Hugging Face リポジトリへアクセスできる認証情報をコミットしてしまい、露出していた間に第三者がその認証情報を取得して保管されていたプロンプト標本をダウンロードしました。第三者は標本の中から他サービスの認証情報を探して有効性を試し、試された認証情報のうち5件が Dragos のカナリアでした（出典3。原文英語を訳出）。

侵害のほかに、Dragos は「盗まれていない」類の問題も観測しています（出典1）。ある中国の AI ラボは、2026年7月から10月に送られたプロンプトの半分以上から秘密 URL を取得しており、そこには「データを収集しない」または ZDR と指定した要求の約3分の2が含まれていました。同ラボのモデルを再販する複数の米国系ホスティング事業者が同じ収集動作を引き起こしており、ある大手の米国系事業者は1回の推論呼び出しから2か月以上たってもその URL を巡回し続けていました（出典1）。

「保存されないはず」の指定が付いた要求が盗まれていた概観

本件の核心は、件数ではなく保証の破れ方である（本記録の評価）〈重要〉。

Zero Data Retention（ZDR・データ無保持）は、「このプロンプトは保存されない」という指定である。機微なデータを扱う組織が AI を使うときの最後の砦として、契約書にも監査要件にも書かれる。

Dragos の観測では、3社の侵害のうち2件で、盗まれた要求の一部に ZDR の印が付いていた（出典1）。The Hacker News はこの点をこう書いている——「盗まれた要求の一部は、プロンプトが決して保存されないことを意味するはずの設定である Zero Data Retention として印が付けられていた」（出典4。原文英語を訳出）。

さらに侵害とは別の経路でも同じことが起きている（出典1）。ある中国の AI ラボは、2026年7月から10月に送られたプロンプトの半分以上から秘密 URL を取得しており、そこには「データを収集しない」または ZDR と指定した要求の約3分の2が含まれていた。侵害ではない。そのラボ自身が取りに来ていた。

そして同ラボのモデルを再販する複数の米国系ホスティング事業者が同じ収集動作を引き起こしていた（出典1）。つまり利用者が米国の事業者と契約していても、モデルの出所側がプロンプトの中を見に来る経路が残っていた。

OpenRouter が125のエンドポイントから ZDR の資格を剥奪したのは、この構造への対応である（出典2）。注意すべきは、125のうち「予防的に取り除いた」分が含まれることである（出典2）——これは被害の確認ではなく、保証の取り下げである（本記録の明示）〈重要〉。言い換えれば、OpenRouter は「ZDR と表示していたが、いま保証できないもの」が少なくとも125あったと認めた。

破られたのは推論の経路ではなく、試験のために残しておいたプロンプトだった原因・手口

3社の侵害のうち、原因まで公表したのは Together AI だけである（出典3）〈重要〉。その原因は、推論基盤への侵入ではなかった。

Together の説明はこうである（出典3。原文英語を訳出）——

  1. 通常のソフトウェア試験のために、プロンプトの標本を収集していた。
  2. 標本は非公開の Hugging Face リポジトリに保管していた。
  3. 公開 GitHub リポジトリ xorl の開発中に、AIコーディングエージェントが、その非公開リポジトリへのアクセスを与える認証情報をコミットした。
  4. 露出していた間に、権限のない第三者がその認証情報を取得し、標本をダウンロードした。
  5. 第三者は標本の中から他サービスの認証情報を探して有効性を試した。試された認証情報のうち5件が Dragos のカナリアだった。
  6. Together の自動スキャンが露出した認証情報を検知し、コミットを取り消した。

影響した要求は MiniMax M3・GLM-5.2・Kimi K2.6 への呼び出しで、主に2026年6月24日・7月4日・7月8日・7月14日のものである（出典3）。

この経路には3つの層があり、どれも「推論基盤の堅牢化」では塞がらない（本記録の評価）〈重要〉——

  • ①プロンプトを残していた。 推論の処理そのものは終わっていても、試験用の標本として保存されていた。ZDR が「推論経路で保存しない」ことしか保証しないなら、この層は ZDR の外にある。（OpenRouter 自身、ZDR の適用は推論プロバイダへの振り分けに限られると文書で述べている。）
  • ②AIコーディングエージェントがコミットした。人間のレビューを経ずに認証情報が公開リポジトリへ入った。Together は再発防止として「AIコーディングエージェントに関する開発手順の更新」を挙げている（出典3）。
  • ③プロンプトの中身が次の攻撃の材料だった。攻撃者は盗んだプロンプトを読んで認証情報を探している。プロンプトは「漏れたら恥ずかしい文章」ではなく認証情報の袋として扱われた。

③が本件の最も実務的な指摘である（本記録の判断）〈重要〉。Dragos がカナリアとして AWS 鍵やパスワードを埋め込んだのは、実際の利用者がそうしているからである。デバッグのためにエラーログを貼る。設定ファイルを貼る。接続文字列を貼る。それが盗まれる前提で考える必要がある。

鍵は数時間で試され、数万回のAPI呼び出しに化けた被害規模・影響範囲

Dragos が観測した、盗まれたカナリア AWS 鍵への行動は具体的である（出典1。原文英語を訳出）。

観測 内容
有効性の確認 場合によっては数時間以内

例として挙げられた鍵は2026年10月21日に配布され、翌日に最初に使われた（出典1）。

ここから読めることは3つある（本記録の評価）〈重要〉——

①プロンプトに貼った鍵は、翌日には使われている。「漏れてから気づくまで」の猶予は無い。鍵をローテーションする周期が90日なら、89日は無防備である。

②攻撃者の関心は Bedrock にある。 S3 と Secrets Manager の探索はデータを狙う動きだが、Bedrock モデルの有効化と API 鍵の作成は盗んだクラウドで推論を回す動きである（本記録の評価）——ただし Dragos は目的を断定していない。AI の計算資源そのものが窃取の対象になっているという見方は、本件の文脈と整合する。

③指標照合では検知できない。 artex-agent と artex-judge-r121 が公開の指標リストに無いと Dragos が指摘している（出典1）。既知の悪性 IP・既知のユーザーエージェントを照合する運用では、この活動は通り抜ける。

一方、マーケットプレイス側の問題は性質が違う（出典1）〈重要〉。Dragos は「販売者は家庭用回線を使う個人であった」とし、カナリアのサーバに対してログインを推測で試みたとしている。フランスの家庭用ブロードバンド回線から、プロンプト中のパスワードで SSH の root ログインを試みた人物がいた。そして漏えいは「マーケットプレイス全体」ではなく「その販売者」に付いて回っていた（出典1）。

これは組織的な侵害ではなく、最安値の売り手に要求が渡る仕組みの帰結である（本記録の整理）。価格で振り分ける設計は、価格が安い理由を問わない。

OpenRouter は3社を切り、125のエンドポイントから保証を取り下げた組織の対応

OpenRouter の対応は、公表から数えれば速い（本記録の整理）。

日付 出来事
2026年11月19日 Dragos がレポートを公開（当事者への通知はこれより前）
2026年11月21日 Together AI が自社の事案を公表
2026年11月22日 OpenRouter が対応を公表。3社を切り離し、125エンドポイントの ZDR 資格を剥奪

Dragos の公開から3日である（本記録の算出）。ただしこれは「知ってから3日」ではない（本記録の明示）〈重要〉—— Dragos は公開前に当事者へ通知しており（出典1）、OpenRouter も「研究者とプロバイダと協力して知見を理解した」としている（出典2。原文英語を訳出）。

OpenRouter が公表した対応は5つである（出典2。原文英語を訳出）——

  1. 3つのプロバイダを切り離した（調査に基づく）。
  2. 125のエンドポイントから ZDR の資格を取り除いた（研究者が指摘したプロバイダと、予防的に取り除いた追加分を含む）。
  3. 影響を受けた可能性のあるすべての顧客へ通知した（完了）。
  4. 研究者の試験手法を自社に取り入れ、継続的に検査する。
  5. 要求と応答が第三者へ転送される経路がないかを技術的に検証する。

そして ZDR 資格の回復には「適切な保証と検証」を要求するとしている（出典2）。

4と5は、本件で最も実質的な変化である（本記録の評価）〈重要〉。

4は「研究者がやったことを自分でやる」という宣言である。カナリアを自分で撒いて、委託先が約束を守っているかを継続的に測る。契約書で ZDR を取り付けることと、ZDR が守られているかを測ることは別の作業である——本件はその差が5か月ぶん開いていたことを示した。

5は「要求がどこへ転送されているか」の検証である。Dragos のレポートには、OpenRouter の経路について「この中継はトレースによって発見されたもので、マーケットプレイスでは開示されていなかった」という記述がある（出典1。原文英語を訳出）〈重要〉。つまり表示されている事業者の先に、表示されていない事業者がいた。

一方で足りないものもある（本記録の評価）〈重要〉—— 「適切な保証と検証」の内容が示されていない〈未確定〉。第三者監査なのか、自己申告なのか、技術的な試験なのかが分からない。利用組織の立場では、ZDR の表示が戻ったときに何が確かめられたのかを判断できない。

「どの事業者に渡ったか」を利用者が知らないまま契約が積み上がっている評価・解釈

本件を「推論プロバイダの話」として読むと、当てはめを誤る（本記録の判断）〈重要〉。

構造はこうである——

自社アプリ
  → SaaS ベンダー（AI 機能つき）
    → ルーティング基盤（OpenRouter 等）
      → 推論プロバイダ（価格と可用性で選ばれる）
        → モデルの出所（再販元のラボ）

日本の組織の多くは、上の2段しか契約していない（本記録の評価）。3段目以降は「ベンダーが使っているもの」であり、調達の審査票にも、委託先一覧にも載らないことがある。

本件で起きたのは、4段目が数か月にわたり侵害され、3段目も1段目も気づかなかったということである。The Hacker News の記述が最も端的である——「3社のいずれも研究者が知らせるまで気づいていなかった」（出典4。原文英語を訳出）〈重要〉。

そして5段目の問題も別に起きている。中国の AI ラボがプロンプトの半分以上から秘密 URL を取得しており、そのラボのモデルを再販する米国系事業者経由でも同じ動作が起きていた（出典1）。利用者から見れば契約相手は米国の事業者である。

ここから導かれる実務上の問いは3つである（本記録の判断）〈重要〉——

  • 自社の AI 利用で、要求がどの事業者に渡るかを列挙できるか。できないなら、ZDR の契約は「誰との約束か」が不定である。
  • 約束が守られているかを、自分で測る手段があるか。 OpenRouter は研究者の手法を取り入れると公表した（出典2）。発注元の側にも同じ選択肢がある。
  • プロンプトに何が入っているかを知っているか。攻撃者はプロンプトを認証情報の袋として扱った（出典1・3）。盗まれる前提で、入れないものを決める必要がある。

最後の点について、本件には皮肉な事実がある（本記録の整理）。Together AI は再発防止策の1つとして「機微なプロンプトデータを扱う顧客は、アカウント設定で ZDR を有効にすべきである」と述べ、新規アカウントでは ZDR を既定にしたとしている（出典3。原文英語を訳出）。しかし本件で盗まれたのは、まさに保存されていたプロンプト標本である。 ZDR の既定化は正しい対策だが、「試験のために標本を残す運用」が別に存在していたことが原因であり、顧客側の設定では防げなかった層である。

利用組織が契約していない層が侵害され、ZDR 指定の要求まで盗まれた構造
layer 0 は利用組織（日本の組織もここにいる）。 layer 1 は契約する相手——**審査票に載るのはここまでであることが多い。** layer 2 はルーティング基盤（OpenRouter）。 **OpenRouter 自身の侵害は確認されていない（出典2）。** layer 3 は推論プロバイダ——**ここが3社侵害された。** **どの3社かは公表されていない。 OpenRouter が告知をリンクした4社（Atlas Cloud・Novita・Phala・Together）が 侵害された3社と同一であるとは誰も述べていない。** layer 4 はモデルの出所——**中国のAIラボがプロンプトの半分以上から 秘密URLを取得し、その再販経路でも同じ動作が起きていた（出典1）。** layer 5 は盗まれたものとその用途。 **ZDR の印が付いた要求も盗まれていた点が本件の核心である。** layer 6 は発見と対応——**検知したのはどの当事者でもなく、 自分の秘密に目印を付けて外へ出した第三者（Dragos）である。**

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入検知した
**Together の自動スキャンが露出した認証情報を検知し、 コミットを取り消した**（出典3。原文英語を訳出）〈重要〉—— **検知の機会は存在し、仕組みは機能した。** **しかし第三者が認証情報を取得するのには間に合わなかった** （本記録の整理）〈重要〉—— **コミットから検知までの時間が公表されていないため、 「どれだけ間に合わなかったのか」は分からない**〈未確定5〉。 **ここで効くのは検知の速さではなく、 コミットが成立する前の阻止である**（本記録の評価）—— **Together 自身も再発防止の第1項に 「すべてのプルリクエストに対する認証情報の検査」を挙げている**（出典3）。
—
収集機会はあったが検知できず
**検知されていない**〈重要〉—— **The Hacker News は「3社のいずれも研究者が知らせるまで 気づいていなかった」としている**（出典4。原文英語を訳出）。 **機会は存在した**（本記録の評価）—— **非公開リポジトリからの一括ダウンロードは、 アクセス元・取得量の異常として検知しうる事象である。** **Together は検知について、 コミットの自動スキャンにしか言及していない**（出典3）—— **標本が持ち出されたことの検知には触れていない。** **本件で最も効くのは、プロンプト標本を保存しないことである** （本記録の評価）——**残っていなければ持ち出されない。**
—
認証情報アクセス検知した
**Dragos 側では検知された**（出典1・3）〈重要〉—— **カナリアを撒いた側が、試行を記録している。** **これが本件の検知の形である**（本記録の整理）〈重要〉—— **検知したのは被害側（プロバイダ）でも発注元（OpenRouter）でもなく、 「自分の秘密に目印を付けて外へ出した第三者」である。** **逆に言えば、目印を付けていない組織は 自分のプロンプトが読まれても気づけない**（本記録の評価）。
—
内部探索検知した
**カナリア鍵であるため、Dragos 側で全部が見えている**（出典1）〈重要〉—— **実環境であれば、CloudTrail の `ListBuckets` `GetSecretValue` `DescribeParameters` の 連続は検知可能な事象である**（本記録の評価）—— **ただしこれは本件で実際に検知された話ではなく、 一般則としての指摘である**（本記録の明示）。 **道具立てが Windows 上の Chrome を装うスクリプトから Boto3、AWS CLI へと変わっていること**（出典1）**は、 ユーザーエージェントでの判別が当てにならないことを示す。**
—
権限昇格検知した
**IAM ユーザーの追加と Bedrock API 鍵の作成は、 CloudTrail に必ず記録される管理操作である**（本記録の評価）〈重要〉—— **検知の機会としては最も明確な段階である。** **Bedrock の鍵を作る動きは、 盗んだクラウドの計算資源で推論を回す目的を示唆する** （本記録の評価）——**ただし Dragos は目的を断定していない。** **公開の指標リストに無いユーザーエージェントが使われている点** （出典1）**は、照合型の検知では止まらないことを示す** （本記録の整理）—— **効くのは「誰が IAM ユーザーを作ったか」の振る舞い側の検知である。**
—
持ち出し現実的な検知機会なし
**利用者側に現実的な検知の機会は無い**（本記録の評価）〈重要〉—— **これは侵害ではなく事業者自身の取得であり、 利用者のネットワークにも端末にも痕跡が出ない。** **自分が貼った URL のアクセスログを自分で見ている場合に限り 見える**（本記録の整理）—— **それが Dragos がやったことである。** **したがって対策は検知ではなく、 プロンプトに内部 URL を貼らないことである**（本記録の判断）。
—

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
**Dragos も OpenRouter も、侵害された／切り離されたプロバイダの 社名を公表しなかった**（出典1・2）〈重要〉—— **OpenRouter がリンクしたのは、 自ら告知を出した4社（Atlas Cloud・Novita・Phala・Together）への 参照だけである**（出典2）—— **「影響を受けたすべてのプロバイダが公開の投稿をしているわけではない」 と明記している**（出典2。原文英語を訳出）。部分的に機能**本記録の評価である**〈重要〉—— **研究者側の判断としては妥当である**（本記録の評価）—— **未公表の事業者を名指しすれば、 その事業者の顧客が「自分の状況を調べる手段」を得る前に 攻撃者が動く余地が生まれる。** **しかし OpenRouter の側は立場が違う**（本記録の判断）〈重要〉—— **同社は顧客に対して「あなたの要求はこの事業者へ渡っていた」と 言える唯一の主体であり、 通知を完了したと述べているのだから、 個別通知の中では経路を伝えられる位置にいる。** **公表文で社名を出さないこと自体は責められないが、 公表文だけを読む利用組織（OpenRouter の顧客のさらに先の組織）には 判定材料が残らない。** **本記録は partial とする。**
**Together AI は外部のフォレンジック調査会社および 法執行機関と連携した**（出典3。原文英語を訳出）〈重要〉—— **自社調査のみで済ませていない。**機能した**本記録の評価である**〈重要〉—— **根拠は、原因の記述の具体性である**（本記録の判断）—— **「AIコーディングエージェントが認証情報をコミットした」という 自社に不利な事実を、経路まで含めて書いている**（出典3）。 **影響したモデル（MiniMax M3・GLM-5.2・Kimi K2.6）と 日付（2026年6月24日・7月4日・7月8日・7月14日）まで出している。** **3社のうち1社だけがこの水準で公表し、 1社は公表の時点でまだ何も出していなかった**（出典1）—— **比較の中では明確に優れている。** **留保: 露出期間が公表されていないため、 「自動スキャンが機能した」という主張は検証できない**〈未確定5〉。
**OpenRouter は3社を切り離し、125のエンドポイントから ZDR の資格を剥奪した**（出典2）〈重要〉—— **125には「予防的に取り除いた追加のエンドポイント」が含まれる**（出典2）。機能した**本記録の評価である**〈重要〉—— **根拠は「予防的に取り除いた」分を含めている点である** （本記録の判断）〈重要〉—— **研究者が指摘したものだけを外せば済む場面で、 確認が済んでいないものまで資格を落としている。** **これは「ZDR と表示する以上は保証できる範囲に限る」という 方向への振り方であり、短期の商品性を犠牲にしている。** **留保2点**—— **①回復の条件（「適切な保証と検証」）が示されていないため、 この厳しさが続くかは分からない**〈未確定〉。 **②切り離された3社と、Dragos が侵害を確認した3社が 同一とは誰も述べていない**（本記録の明示）—— **数の一致だけで「侵害された3社を外した」と読んではいけない。**
**Together AI は、露出した認証情報の自動検知後にコミットを取り消し、 範囲を絞った／短命の認証情報の使用と、 可能な範囲での鍵を使わないアクセスへ移すとした** （出典3。原文英語を訳出）〈重要〉。部分的に機能**本記録の評価である**〈重要〉—— **対策の方向は正しい**（本記録の判断）—— **短命の認証情報であれば、コミットされても窓が短い。** **しかし本件で盗まれたのは認証情報の先にあった プロンプト標本そのものである**（出典3）〈重要〉—— **「標本を保存しない」「本番データではなく合成データを使う」という 対策が再発防止策に挙がっていない**（本記録の確認）—— **認証情報の管理を直しても、 同じ場所に同じものが置かれ続けるなら 次の経路で同じことが起きる**（本記録の評価）。 **本記録は partial とする。**
CISO・経営層への示唆
  • AI 利用の委託先を「契約した相手」ではなく「要求が渡る相手」で数え直す
    **本件で侵害されたのは、多くの利用組織が契約していない層である** （本記録の判断）〈重要〉—— **「自社アプリ → SaaS ベンダー → ルーティング基盤 → 推論プロバイダ → モデルの出所」という連鎖のうち、調達の審査票に載るのは上の2段である。** **侵害されたのは4段目で、3段目（OpenRouter）も気づいていなかった。** **The Hacker News は「3社のいずれも研究者が知らせるまで 気づいていなかった」としている**（出典4。原文英語を訳出）。 **さらに5段目の問題も別に起きている**—— **中国の AI ラボがプロンプトの半分以上から秘密 URL を取得しており、 同ラボのモデルを再販する米国系事業者経由でも 同じ動作が起きていた**（出典1）〈重要〉—— **利用者から見れば契約相手は米国の事業者である。**
    取るべき行動 **自社の AI 利用について「要求がどの事業者に渡るか」の一覧を作る。** **作り方**—— **①社内で使っている AI 機能つき SaaS を列挙する。 ②各ベンダーに「推論の実行事業者」と「モデルの提供元」を 文書で回答させる（下位委託先の開示として契約上求める）。 ③回答に「ルーティング基盤」「マーケットプレイス」 「価格に応じた自動振り分け」が出てきたものを分けて扱う—— この類型は渡る先が固定でない。** **一覧ができたら、機微なデータを扱う用途については ③の類型を使わない、またはプロバイダを固定（pin）する方針を決める。**
  • ZDR の契約条項を、観測で検証する仕組みに置き換える
    **ZDR（データ無保持）の指定が付いた要求が、実際に盗まれていた** （出典1・4）〈重要〉—— **3社の侵害のうち2件で、盗まれた要求の一部に ZDR の印があった**（出典1）。 **さらに侵害ではない経路でも破れている**—— **中国の AI ラボは「データを収集しない」または ZDR と指定した要求の 約3分の2から秘密 URL を取得していた**（出典1）。 **そして OpenRouter 自身が、 ZDR と表示していたエンドポイントのうち125について 資格を取り下げた**（出典2）〈重要〉—— **「ZDR と表示されていたが保証できないもの」が 少なくとも125あったという意味である。** **5か月の観測で Dragos が見つけたものは、 契約書の審査では1件も見つからなかった**（本記録の判断）。
    取るべき行動 **自社の AI 利用経路に、自前のカナリアを定期的に流す。** **必要なものは2つだけである**—— **①アクセスログを自分で見られる固有 URL （自社ドメインのサブドメインに、1回ごとに違うパスを作る）。 ②どこでも使われていない使い捨ての認証情報 （クラウドの読み取り専用で何も付与しない IAM ユーザーなど）。** **これをプロンプトに埋めて送り、 数日後・1か月後・3か月後にアクセスの有無を確認する。** **1件でも踏まれたら、 その経路の ZDR 表示は「守られていない」と判断して用途を見直す。** **この検査を四半期ごとの定例に入れ、 結果を委託先評価の記録に残す。**
  • AIコーディングエージェントに与えた権限を、インシデントの原因として棚卸しする
    **本件で原因が公表された唯一の事案の引き金は、 AIコーディングエージェントだった**（出典3）〈重要〉—— **「公開 GitHub リポジトリ `xorl` の開発中に、 AIコーディングエージェントが、非公開の Hugging Face リポジトリへの アクセスを与える認証情報をコミットした」** （出典3。原文英語を訳出）。 **Together AI は再発防止として 「AIコーディングエージェントに関する開発手順の更新」を 明示的に挙げている**（出典3）。 **これは「AI が悪さをした」話ではない**（本記録の整理）〈重要〉—— **人間なら通らないレビュー経路で、 エージェントの出力が公開リポジトリへ到達した、 という権限設計の話である。**
    取るべき行動 **自社でコーディングエージェントを使っている範囲について、 次の3点を確認して記録する。** **①エージェントが直接コミット・プッシュできるリポジトリがあるか。 あれば公開リポジトリを含むかを確認する。 ②エージェントが読める範囲に、 本番の認証情報・`.env`・秘密鍵が入っていないか。 ③すべてのプルリクエストに認証情報スキャンがかかっているか。 かかっているなら「検知後に取り消す」設計か 「マージ前に止める」設計かを区別する。** **③が「検知後に取り消す」なら、 本件と同じ窓が開いている——Together はその窓で持ち出された。**
  • 「プロンプトは保存されない」と「どこにもプロンプトが残っていない」を区別する
    **本件で盗まれたのは、推論の経路にあったプロンプトではなく、 「通常のソフトウェア試験のために」収集されて 保管されていたプロンプト標本である**（出典3）〈重要〉。 **ZDR が保証するのは推論プロバイダへの振り分けの範囲であり、 OpenRouter 自身がそう文書に書いている**（本記録の整理）。 **Together AI は再発防止として 「新規アカウントでは ZDR を既定にした」と述べているが**（出典3）、 **本件はその設定では防げなかった層で起きている** （本記録の評価）〈重要〉—— **試験のために別途収集していた標本が原因だからである。**
    取るべき行動 **AI ベンダーへの質問票に、 ZDR の有無とは別の項目として次の3つを足す。** **①推論の経路以外で、プロンプトまたは応答を保存する処理があるか （品質評価・不正検知・モデル改善・試験・ログ・キャッシュ）。 ②あるなら、保存先・保存期間・アクセスできる人の範囲を示せ。 ③その保存に本番の顧客データが入るか、合成データか。** **回答が「ZDR なので保存しません」で止まるベンダーには、 ①を項目ごとに再質問する。** **自社が AI 機能を提供する側でもあるなら、 同じ質問を自社に向けて答えを書く。**
セキュリティ技術者への示唆
  • プロンプトを「盗まれる前提の文書」として扱い、送信前に機械で止める
    **攻撃者はプロンプトを認証情報の袋として扱っている**（出典1・3）〈重要〉—— **Together の事案では、第三者が盗んだ標本の中から 他サービスの認証情報を探して有効性を試し、 5件が Dragos のカナリアだった**（出典3）。 **マーケットプレイス側では、 プロンプト中のパスワードで SSH の root ログインが試みられた**（出典1）。 **Dragos がカナリアとして AWS 鍵やパスワードを埋め込んだのは、 実際の利用者がそうしているからである**（本記録の判断）〈重要〉—— **デバッグのためにエラーログを貼る。設定ファイルを貼る。 接続文字列を貼る。** **盗まれた鍵は翌日に使われている**（出典1）。
    取るべき行動 **AI への送信経路（社内プロキシ・SDK ラッパー・ゲートウェイ）に、 送信前のスキャンと遮断を入れる。** **検出対象は最低限この5つ**—— **①クラウドのアクセス鍵（`AKIA` 等の接頭辞）、 ②`BEGIN PRIVATE KEY` を含む PEM、 ③`password=` `pwd=` を含む接続文字列、 ④Bearer トークン・API キーの形をした長い英数字列、 ⑤社内ドメインの URL（ホスト名の許可リストで判定）。** **検出時は「警告して通す」ではなく「止める」にする**—— **警告は読まれない。** **止めると業務が回らない場面があるので、 例外は「申請して期限つきで許可」の形にし、記録を残す。**
  • プロンプトに貼る内部URLをやめる。踏まれるのは2か月後でも起きる
    **Dragos は「ある大手の米国系事業者は、 1回の推論呼び出しから2か月以上たってもその URL を 巡回し続けていた」としている**（出典1。原文英語を訳出）〈重要〉。 **ある中国の AI ラボは、2026年7月から10月に送られたプロンプトの 半分以上から秘密 URL を取得していた**（出典1）。 **秘密リンクが Feishu のチャットに投稿され、 北京と上海から開かれた例もある**（出典1）。 **これは侵害ではなく事業者自身の取得である**（本記録の整理）〈重要〉—— **利用者のネットワークにも端末にも痕跡が出ないため、 検知の機会が無い。**
    取るべき行動 **プロンプトに貼る URL を、内部ホストと外部ホストで分けて棚卸しする。** **内部ホストの URL は貼らない。** **どうしても内容を渡す必要があるなら、 URL ではなく本文を貼る（取りに来られる経路を作らない）。** **また、認証なしで内容が見える社内の共有リンク （ドキュメント・課題管理・ログ閲覧）が プロンプトに入っていないかを、 送信経路のログから過去分も含めて grep する。** **見つかったリンクは、 「すでに踏まれている可能性がある」ものとして アクセスログを確認し、必要なら無効化する。**
  • IAM ユーザーの作成と Bedrock 鍵の作成を、単独で警報になる操作として扱う
    **盗まれたカナリア鍵での行動は、 探索から権限の拡張まで一貫している**（出典1）〈重要〉—— **S3 バケットの列挙、Secrets Manager と Parameter Store の探索、 Bedrock モデルの有効化の試み、Bedrock API 鍵の作成、 IAM ユーザーの追加。AWS API 呼び出しは合計で数万回。** **道具立ては Windows 上の Chrome を装うスクリプトから OrbStack 上の Boto3、Kali Linux 上の AWS CLI へと変わっている**（出典1） 〈重要〉—— **ユーザーエージェントでの判別は当てにならない。** **さらに2026年11月1日に加わった `artex-agent` と `artex-judge-r121` は公開の指標リストに存在しない**（出典1）—— **照合型の検知では止まらない。**
