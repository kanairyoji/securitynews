INC-2026-1255Ghostscript がサンドボックス脱出

PDF・PostScript の変換に使われる Ghostscript に、 **`-dSAFER` サンドボックスを抜けて任意のコードを実行させられる欠陥があった** （CVE-2026-125396・CVSS v4.0 8.5）—— **`gs_fonts.ps` の `.putgstringcopy` が特権オペレータ `.forceput` を オペランドの型を検査せずに呼ぶため、細工した PostScript／PDF で型エラーを起こし、 自前のエラーハンドラから `.forceput` を回収して save/restore をまたぐ use-after-free に持ち込める**（CVE 記述）。 **修正は2026年9月8日の Ghostscript 10.08.0 で、 それ以前の全版が対象である**（CVE の影響範囲・pwn.ai）。 **発見は pwn.ai の Paulos Yibelo で、報告を受けた Artifex の Ken Sharp が 2026年9月2日にオペランドの型検査を入れて修正した**（CVE のクレジット・修正コミット）。 **本件の要点は脆弱性そのものではなく経路である**—— **Ghostscript は多くの Linux サーバで、アップロードされた PDF・PostScript・画像の 変換や印刷・プレビューの裏側で、アプリケーションが自分で呼んだ覚えのないまま動く。** **pwn.ai は「Upload2Shell」として、CUPS の印刷・Roundcube のメール表示・ WordPress のプラグインによる未認証アップロードなど約10件のアプリケーションで レンダリング処理の権限（`lp`・`www-data` 等）でのコマンド実行を示した**（pwn.ai）。 **実環境での悪用を示す情報は無く、2026年11月18日時点の CISA KEV にも収載が無い** （本記録の確認）。

Ghostscript に -dSAFER サンドボックスを抜けて任意のコードを実行できる欠陥があり、2026年11月9日に CVE-2026-125396 として公表された（出典1）。CVE の記述はこうである（原文英語。本記録の訳）—— 「Ghostscript の 10.08.0 より前の版には、gs_fonts.ps の.putgstringcopy プロシージャに -dSAFER 迂回の脆弱性がある。同プロシージャは特権オペレータ .forceput を、オペランドの型を検査せずに呼び出している。攻撃者は細工した PostScript または PDF 文書を与えて型エラーを起こし、自前のエラーハンドラ経由で .forceput を回収し、save/restore をまたぐ use-after-free を引き起こして任意のコードを実行できる」（出典1）。CVSS v4.0 は 8.5（High）、CWE-648（特権 API の不適切な使用）である（出典1）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は発見者の公開内容（出典2）と CVE の記述（出典1）、 および修正コミット（出典3）に基づく経路であり、 実環境で観測された攻撃の再構成ではない**（本記録の明示）〈重要〉—— **悪用を示す情報は無い**〈未確定1〉。 **起点は「アプリケーションが受け取る文書」である。** **細工した PostScript／PDF が Ghostscript に渡ると、 `.putgstringcopy` の型検査の欠落を突いて `-dSAFER` を抜け、 レンダリング処理の権限でコマンドが実行される。** **権限昇格は本件の範囲ではない（`www-data`・`lp`・コンテナの uid のままである）。**

直すべき場所は、アプリケーションではなくアプリケーションが呼ぶ変換器にある原因・手口

CVE の記述は短い（出典1。原文英語）。

「Ghostscript before 10.08.0 contains a -dSAFER bypass vulnerability in the .putgstringcopy procedure in gs_fonts.ps, which calls the privileged .forceput operator without checking operand types. Attackers can supply crafted PostScript or PDF documents that trigger a type error, recover .forceput via a custom error handler, and cause a use-after-free across save/restore to execute arbitrary code」

本記録による訳: 「Ghostscript の 10.08.0 より前の版には、gs_fonts.ps の .putgstringcopy プロシージャに -dSAFER 迂回の脆弱性がある。同プロシージャは特権オペレータ .forceput を、オペランドの型を検査せずに呼び出している。攻撃者は細工した PostScript または PDF 文書を与えて型エラーを起こし、自前のエラーハンドラ経由で .forceput を回収し、save/restore をまたぐ use-after-free を引き起こして任意のコードを実行できる」

ここで重いのは、修正を書いた本人の説明である（本記録の整理）〈重要〉。Artifex の Ken Sharp は修正コミットにこう書いている（出典3。原文英語）。

「Effectively another case of recovering .forceput, in this case by causing an error and then having the error handler use it. We are in the process of eliminating, or at least absolutely minimising, the use of .forceput. Ideally we want to remove it completely precisely to avoid this sort of thing. Unfortunately that's still a work in progress; it isn't easy to undo 30 years worth of assumptions in the code. For now this prevents the problem by ensuring that the operands are the correct types, which prevents the error executing 'copy' and so avoids the custom error handler managing to execute .forceput」

本記録による訳: 「実質的には .forceput を回収するまた別の一例であり、今回はエラーを起こしてエラーハンドラにそれを使わせるという形である。我々は .forceput の使用を無くす、少なくとも絶対的に最小化する作業の途中にある。理想的には完全に取り除きたい——まさにこの種のことを避けるためである。あいにく、それはまだ進行中の作業である。コードに積み上がった30年分の前提を解くのは容易ではない。いまのところ、この修正はオペランドが正しい型であることを確かめることで問題を防いでいる。それによってエラーが copy を実行することを防ぎ、自前のエラーハンドラが .forceput を実行できるようになることを避けている」

この文からは3つのことが読める（本記録の評価）。①今回の修正は、欠陥の種類そのものを無くしたわけではない—— .forceput を回収する経路の「また別の一例」を1つ塞いだものである。 ②同じ型の欠陥が今後も出ると、開発者自身が予期している。 ③したがって「最新版に上げたから、この種の問題は終わった」とは読めない（本記録の判断）〈重要〉—— 外部から受け取った文書を変換する処理は、サンドボックスの有無とは別に、隔離して動かす前提で設計するほかない。

アプリケーションは自分が Ghostscript を呼んでいることを知らないまま呼んでいる評価・解釈

①認証を要さないウェブのアップロード—— WordPress のプラグイン Forminator 1.55.1、Essential Addons for Elementor Lite 6.7.0。いずれも実行権限は www-data。

CISO・経営層への示唆
  • 資産管理の単位を「製品」から「製品が呼ぶ部品」へ一段下げる
    **Ghostscript は、導入した記憶が無くても入っている**（出典2・7）。 **印刷・文書変換・サムネイル生成・ウェブメールの添付表示・ 文書管理・機械学習の前処理が、内部で `gs` を起動する**（出典2）。 **資産台帳が「WordPress」「CUPS」「Roundcube」の粒度で止まっていると、 本件の対象が1件も挙がらない**（本記録の評価）〈重要〉。
    取るべき行動 **「外部から受け取った文書を変換・プレビュー・印刷する機能」を 業務単位で列挙し、各機能が起動する外部プロセスを1つずつ確認する。** **確認の仕方は、アプリケーションの依存一覧ではなく、 稼働中のホスト・コンテナで `gs`／`convert`／`magick` の 実体と版を数えることである。** **コンテナイメージに同梱された版は、ホストの更新では直らないことを 明示的に点検対象に入れる。**
  • 「CVE が出たら動く」運用は、修正が出てから2か月遅れることがある
    **修正版 10.08.0 は2026年9月8日に出ているが、 CVE-2026-125396 の公表は11月9日である**（出典1・2。本記録の算出で62日） 〈重要〉。 **採番したのは開発元ではなく第三者の CNA（VulnCheck）である**（出典1）—— **上流が CVE を採番しない構造では、 修正が配られていても勧告が存在しない期間が生じる**（本記録の評価）。
    取るべき行動 **脆弱性管理の入口を CVE だけにしない。** **①利用しているディストリビューションのセキュリティ更新 （Debian DSA・Ubuntu USN 等）を独立した入口として購読する。 ②主要な OSS 部品については、上流のリリースノートを定期的に見る運用を決める。 ③「定期更新を当てている」ことを前提にできる環境と、 そうでない環境（固定版のアプライアンス・コンテナイメージ・ オンプレの印刷サーバ）を分けて管理する。**
  • CVSS の `AV:L`（ローカル）を優先度の判断にそのまま使わない
    **本件の評点は CVSS v4.0 8.5 で、攻撃元区分は LOCAL、 利用者の関与が前提とされている**（出典1）。 **一方で研究者が示した経路は、未認証のウェブフォーム・ 受信メールの表示・印刷ジョブである**（出典2）〈差異1〉。 **評点は部品の性質を測り、研究は部品の置かれ方を示している** （本記録の評価）——**両者は別のことを測っている。**
    取るべき行動 **優先度は、評点ではなく「その部品に外部からどう到達するか」で決める。** **具体的には、該当部品を呼ぶ経路のうち 「認証不要」「インターネットから到達可能」なものを先に塞ぐ。** **脆弱性管理の表に「外部到達性」の列を持ち、 評点とは別に記録する。**
  • 開発元が「同じ型の欠陥は今後も出る」と言っている部品は、隔離の対象として扱う
    **修正を書いた Artifex の開発者自身が、これを `.forceput` 回収の 「また別の一例」と呼び、根本的な除去は進行中で 「30年分の前提を解くのは容易ではない」と述べている** （出典3。本記録の訳）〈重要〉。 **「最新版に上げれば終わり」という読み方が成立しない部品である** （本記録の判断）。
    取るべき行動 **外部入力を解釈する変換器（Ghostscript・ImageMagick・ 文書/動画のデコーダ等）を「いずれ破られる部品」として扱い、 更新とは別に隔離の投資を決める。** **最低限、変換処理の実行利用者をウェブ／アプリ本体と分け、 資格情報・設定ファイル・内部ネットワークから切り離す。** **この判断は、個別の CVE の有無とは独立に行う。**
セキュリティ技術者への示唆
  • まず `gs` の実体と版を数える——アプリケーションの一覧からではなく稼働環境から
    **影響範囲は「10.08.0 より前の全版」である**（出典1）。 **確認すべきはアプリケーションの版ではなく Ghostscript の版である** （本記録の整理）—— **pwn.ai の試験環境では、Debian 13 の 10.05.1、Google の 10.05.0、 Plesk 同梱の 9.54.0 が混在していた**（出典2）。
    取るべき行動 **稼働中のホストとコンテナで `gs --version` を取り、 10.08.0 未満、または配布元が backport を明示していない版を洗い出す。** **印刷サーバ（CUPS のフィルタ）・ウェブメール・文書管理・ 画像処理のワーカー・CI のビルドイメージを個別に見る。** **Red Hat 系（RHEL・Rocky・AlmaLinux・Oracle Linux）と Fedora 安定版は、pwn.ai が修正の有無を確定できていないため、 配布元の勧告で個別に確認する**〈未確定2〉。
  • 変換プロセスからの子プロセス生成を検知の軸に置く
    **入口（アップロード・メール受信・印刷）は日常の動作であり、 そこで悪性と判定する材料は乏しい**（本記録の評価）。 **一方、実行は「文書を変換するプロセスがコマンドを起こす」形で現れる** （出典1・2）—— **`gs`・`convert`／`magick`・CUPS のフィルタ・ウェブサーバの子として シェルや外向き通信が出ることは、正常な運用では稀である** （本記録の判断）〈重要〉。
    取るべき行動 **EDR／監査ログで、`gs`・`convert`・`magick`・CUPS のフィルタ、 および `www-data`／`lp` を親とするシェル起動・ 外向きネットワーク接続を検知対象にする。** **まず平常時のベースラインを取り、 正常な子プロセス（フォント処理・一時ファイル操作）を除外してから アラートにする。**
  • 変換処理を二重に囲む——`-dSAFER` は内側の1枚でしかない
    **本件は `-dSAFER` そのものの迂回である**（出典1）。 **一方 pwn.ai は、Plesk の環境で AppArmor を強制モードにした試験では シェルの起動が阻まれたと記している**（出典2）〈重要〉—— **アプリケーション内のサンドボックスが破れても、 OS 側の強制アクセス制御が残っていれば影響が止まった例である** （本記録の整理）。
    取るべき行動 **変換処理に `seccomp`／AppArmor／SELinux のプロファイルを当て、 `execve` と外向き通信を落とす。** **コンテナで動かす場合は、専用の低権限 uid・読み取り専用ルート・ ネットワーク無効を既定にする。** **アップロード先のストレージは実行不可でマウントする。**
  • 受け付ける形式を絞る——拡張子ではなく内容で、変換器に渡す前に
    **攻撃の起点は「細工した PostScript または PDF 文書」である**（出典1）。 **pwn.ai が到達を確認した入口には、 未認証のアップロードフォームが含まれる**（出典2）。
    取るべき行動 **業務要件を確認し、PostScript／EPS を受け取る必要が無い経路では 受け付けを止める。** **判定は拡張子ではなくファイルの内容で行い、 判定の前に変換器へ渡さない順序にする。** **PDF のプレビューが要るだけなら、Ghostscript 以外の実装 （より狭い機能のレンダラ）で足りるかを検討する。**
  • 上流とアプリケーションの両方に修正があることを前提に当てる
    **Ghostscript 側（10.08.0）とは別に、 WordPress（CVE-2026-65640・7.0.4）と Roundcube（CVE-2026-114727）にも個別の修正が出ている**（出典2・4・5）。 **片方だけでは残る経路がある**（本記録の評価）。
    取るべき行動 **「部品の更新」と「アプリケーションの更新」を別の作業として台帳に持つ。** **プラグイン（Forminator・Essential Addons for Elementor 等）の 修正状況は本記録では確認できていないため、 各提供元の情報で個別に確かめる**〈未確定2〉。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 外部から受け取った PDF・PostScript・画像を、サーバ側で変換・プレビュー・ 印刷・サムネイル生成する機能があるこれらの処理は多くの場合 Ghostscript を内部で起動する（出典2・7）—— アプリケーションが直接呼んでいない場合も含む
委託・第三者部品□ ImageMagick／Imagick、CUPS、文書管理製品、ウェブメール、 ホスティング管理基盤（Plesk 等）、または機械学習の画像前処理を使っているpwn.ai が到達を確認した経路はすべてこの種の間接依存である（出典2）—— WordPress の条件は「サーバで Imagick と Ghostscript を使っていること」である（出典5）
認証・認可□ ファイルのアップロードを認証なしで受け付ける窓口がある （問い合わせフォーム・応募フォーム・資料提出）研究では WordPress プラグイン2件で未認証のまま `www-data` 権限のコマンド実行に至っている（出典2）
運用・監視□ 変換処理がウェブ／アプリ本体と同じ利用者（`www-data` 等）で動いており、 強制アクセス制御（AppArmor・SELinux・seccomp）を当てていない実行権限がそのまま影響範囲になる（出典2）—— AppArmor 強制時にシェル起動が阻まれた例が示されている（出典2）
運用・監視□ コンテナイメージ・アプライアンス・固定版の印刷サーバのように、 OS の定期更新が届かない場所で文書変換を行っている本件はディストリビューションの更新で配られた期間が長い（出典2）—— 定期更新が届かない環境は、CVE 公表まで修正の機会が無かった
体制・契約□ 脆弱性管理の入口が CVE・KEV に限られている修正（2026年9月8日）から CVE 公表（11月9日）まで62日ある（本記録の算出）—— 本件は2026年11月18日時点の KEV にも収載が無い（出典6）
