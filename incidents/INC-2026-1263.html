INC-2026-1263Tomcat クラスタに無認証で参加

Java の Web アプリケーションサーバ Apache Tomcat に、 **クラスタ通信を TLS 1.3 ＋ TLS-PSK で保護している構成では、 鍵交換の際に接続相手の身元を検証しないという欠陥があった** （CVE-2026-133325・CWE-322「entity authentication を伴わない鍵交換」）。 **クラスタ通信のポートに到達できる攻撃者は、認証を経ずに信頼されたノードとして クラスタに参加でき、クラスタ内の通信とデータに手が届く**（Apache の公表・CVE の記述）。 **対象は 11.0.28〜11.0.29・10.1.62・9.0.124 で、いずれも上記の特定構成を 採っている場合に限られる**（Apache の公表）。 **報告は2026年11月16日、公表は11月19日である**（Apache のセキュリティページ）。 **本記録の要点は、重大度の評点が提供元ごとに大きく割れていることである**〈重要〉—— **Apache 自身は CVSS を付けず「critical」と文言で述べ、 CISA-ADP は CVSS v3.1 で 9.8（Critical）を付け、 Red Hat は 8.1（Important）とした。** **Red Hat が下げた理由は「クラスタ設定が既定で無効であり、 TLS 1.3 ＋ TLS-PSK という非既定の構成を要する」ことである**（Red Hat の公表）。 **2026年11月23日時点で、修正版 11.0.30・10.1.63・9.0.125 はいずれも未リリースであり、 当面の回避策は「クラスタ通信を TLS 1.2 に切り替える」ことである**（本記録の確認）。

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月19日（Apache による公表・CVE-2026-133325 の採番） 最終更新: 2026年11月23日（本記録が CVE レコード・Tomcat の3ブランチのセキュリティページ・Red Hat の CVE ページ・NVD を取得して照合した）

Apache Tomcat のクラスタ通信に、重大（Critical）と格付けされた欠陥が公表された（出典2・3・4。2026年11月19日）。

成立する構成は限定されている——クラスタ通信を TLS 1.3 と TLS-PSK（事前共有鍵）で保護している場合である（出典1）。この構成では鍵交換の際に接続相手の身元が検証されず、クラスタ通信のサービスに到達できる攻撃者は、認証を経ずに信頼されたノードとしてクラスタに参加できる（出典1・2）。参加できれば、クラスタ内でやり取りされる通信とデータ——典型的にはセッションレプリケーションの内容——に手が届く（出典5。Red Hat の説明）。

対象は 11.0.28 から 11.0.29、10.1.62、9.0.124 である（出典1）。修正は3ブランチそれぞれにコミットされているが、2026年11月23日時点で 11.0.30・10.1.63・9.0.125 はいずれも未リリースである（出典2・3・4。各ページが「not yet released」と明記）〈未確定1〉。Apache が示す当面の回避策は、クラスタ通信を TLS 1.2 に切り替えることである（出典2・3・4）。Red Hat はこれに加えて、クラスタ通信のポートへの到達を認可済みノードに限ることを勧めている（出典5・7）。

本記録が重く見るのは、重大度の評点が提供元ごとに割れていることである〈重要〉〈差異1〉。Apache（CNA）は CVSS を付けず、重大度を「critical」という文言だけで示した（出典1。本記録が CVE レコードの metrics を確認）。CISA-ADP が後から CVSS v3.1 で 9.8（Critical・AV:N/AC:L/PR:N/UI:N）を付与し、これが NVD の画面に Secondary として並んでいる（出典1・6）。一方 Red Hat は 8.1（Important・AC:H）とし、「クラスタ設定は既定で無効であり、TLS 1.3 ＋ TLS-PSK という非既定の構成を要するため Critical ではなく Important とする」と理由を述べている（出典5。原文英語。本記録の訳）。9.8 と 8.1 の差は、AC（攻撃条件の複雑さ）を「低」と見るか「高」と見るかの差である（本記録の整理）。

読み方としては、この割れ自体が本件の実務的な核である（本記録の評価）。9.8 を見て全台の緊急対応に走ると、クラスタを使っていない大多数のTomcat に労力が流れる。8.1 を見て後回しにすると、該当構成のシステムで「ネットワークに到達できれば認証なしでクラスタに入れる」状態が放置される。 分岐点は評点ではなく、server.xml に <Cluster> があり、その通信が TLS 1.3 ＋ TLS-PSK かどうかである（本記録の整理）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下は Apache の公表（出典2・3・4）・CVE の記述（出典1）・ Red Hat の説明（出典5）に基づく経路であり、 実環境で観測された攻撃の再構成ではない**（本記録の明示）〈重要〉—— **悪用を示す情報は無い**〈未確定3〉。 **前提は「クラスタ通信が TLS 1.3 ＋ TLS-PSK で保護されている」ことである。** **この構成では鍵交換時に接続相手の身元が検証されないため、 クラスタ通信のサービスに到達できる攻撃者は、 認証を経ずに信頼されたノードとしてクラスタに参加できる。** **参加後に手が届くのは、クラスタ内でやり取りされる通信とデータである。**

  1. 1. 偵察inferred
    **攻撃者が、クラスタ通信のポートに到達できる位置を得る** （出典1・5の前提に基づく本記録の整理）—— **公表資料はこの段階の手口を記していない**（本記録の明示）。
    根拠: Red Hat の説明（「クラスタ通信ポートへネットワーク到達性のある未認証の攻撃者」）
  2. 2. 初期侵入disclosed
    **TLS 1.3 ＋ TLS-PSK の鍵交換に対し、接続相手の身元検証が行われないことを突いて、 認証を経ずにクラスタに参加する**（出典1・2・3・4）—— **CVE の記述は「Key exchange without entity authentication vulnerability in Apache Tomcat allowed an unauthenticated node to join a cluster when the cluster was secured with TLS 1.3 and TLS-PSK」** （出典1。原文英語。本記録の訳: Apache Tomcat における entity authentication を伴わない鍵交換の脆弱性により、 クラスタが TLS 1.3 と TLS-PSK で保護されている場合に、 認証されていないノードがクラスタに参加できた）。
    根拠: CVE の記述（CWE-322）／Apache の3ブランチのセキュリティページ
  3. 3. 収集disclosed
    **クラスタに参加した状態で、クラスタ内の通信とデータに到達する** （出典5・7）—— **Red Hat は「クラスタの状態情報やセッションレプリケーションのデータを 参照できる」と述べている**（出典5。原文英語。本記録の訳）。 **iThome も「クラスタ通信とデータにアクセスしうる」と報じている** （出典7。原文中国語・繁体。本記録の訳）。
    根拠: Red Hat の説明／iThome の報道

評点が 9.8 と 8.1 に割れているのは、測っている前提が違うからである評価・解釈

本件には、重大度を示す数値が3通りある（本記録の整理）〈重要〉。

提供元 評価 ベクタ
Apache Software Foundation（CNA） 文言で「critical」（CVSS 無し） —
CISA-ADP CVSS v3.1 9.8（Critical） AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Red Hat CVSS v3.1 8.1（Important） AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H

（出典1・5。本記録が CVE レコードの metrics と containers.adp、および Red Hat の CVE ページを逐語確認した）

違うのは1項目だけである——AC（Attack Complexity）をL（低）と見るか H（高）と見るかである。 他の8項目は完全に一致している。

Red Hat は H と置いた理由を書いている（出典5。原文英語）。

「Red Hat Product Security rates this vulnerability as Important rather than Critical because successful exploitation requires non-default clustering configurations employing TLS-PSK over TLS 1.3. In standard Red Hat deployments, Tomcat clustering is disabled by default.」

本記録による訳: 「Red Hat プロダクトセキュリティは本脆弱性をCritical ではなく Important と評価する。悪用の成立には、TLS 1.3 上で TLS-PSK を用いる非既定のクラスタ構成が必要だからである。Red Hat の標準的な配備では、Tomcat のクラスタ機能は既定で無効である」

つまり、9.8 は「該当構成であったとき、その欠陥はどれだけ危ないか」を測り、8.1 は「その構成に至っている環境がどれだけあるか」を割り引いている（本記録の整理）。どちらも誤りではない。

実務上の帰結は、評点をそのまま優先度に写せないことである（本記録の評価）〈重要〉。9.8 で機械的に走ると、クラスタを使っていない大多数の Tomcat に緊急対応の労力が流れる。 8.1 で後回しにすると、該当構成のシステムで「ネットワークに到達できれば認証なしでクラスタに入れる」状態が残る。 本件で先に決まるべきは評点ではなく、server.xml に <Cluster> があるかどうかである。

NVD に出ている 9.8 は、NVD が付けた値ではない評価・解釈

報道は「NVD データベースが示す CVSS 評点は 9.8」と書いている（出典7。原文中国語・繁体。本記録の訳）。画面の見え方としては正しいが、値の出所は NVD ではない（本記録の確認）〈重要〉。

本記録が確認した事実は次のとおりである（出典1・6）。

  • CVE レコードの CNA（Apache）側の metrics には CVSS が無い。 あるのは {"other": {"type": "Textual description of severity", "content": {"text": "critical"}}} だけである（出典1）
  • 9.8 は ADP コンテナにある。提供元は CISA-ADP（組織ID 134c704f-9b21-4f2e-91b3-4a467353bcc0）である（出典1）
  • NVD 上では、この 9.8 が Secondary として表示される。NVD 自身の状態は2026年11月21日 05時18分 UTC の最終更新時点でAwaiting Analysis（解析待ち）である（出典6）

なぜこれが実務に関わるか（本記録の評価）。脆弱性管理の道具は多くの場合 NVD の API を叩いて評点を取り込む。 そのとき Primary と Secondary、そして vulnStatus を見分けていないと、「NVD が 9.8 と判定した」という誤った重みで台帳に載る。 本件では、開発元が CVSS を付けず、ディストリビュータが 8.1 と評価し、第三者の ADP が 9.8 を付けた——という三者の判断の違いが、取り込みの時点で1つの数字に潰れる。

CISA-ADP による補完そのものは有用である（本記録の明示）—— CNA が CVSS を付けない CVE に機械処理可能な評点が入ることで、自動化された優先度付けが動く。 問題は、その評点が「誰の判断か」を運用側が保持していないことである。

修正版が出ていないので、取れる手は回避策しかない対策・注意喚起

2026年11月23日時点で、11.0.30・10.1.63・9.0.125 はいずれも未リリースである（出典2・3・4。本記録が3ブランチのセキュリティページを確認）〈未確定1〉。各ページは該当節を「not yet released」と記している。

一方、修正の中身は公開されている（出典2・3・4）—— 11.0 系 2e6c85ba、10.1 系 8dcddccc、9.0 系 8dac862e の3コミットが GitHub 上にある。

この状態の意味は非対称である（本記録の評価）〈重要〉。攻撃者側は修正差分から欠陥の詳細を読める。 利用者側は正式版を適用できない。 期間の長さは公表されていない。

したがって、本件で実際に実行できる手は2つに限られる（出典2・3・4・5・7）。

  1. クラスタ通信を TLS 1.2 ＋ TLS-PSK に切り替える（Apache の公式回避策）
  2. クラスタ通信ポートへの到達を認可済みノードに限る（Red Hat の推奨）

1は欠陥そのものを回避し、2は到達範囲を狭める（本記録の整理）。両方を採るのが素直である。

ただし1には後始末が付く（本記録の評価）。TLS 1.2 への固定は、暗号要件を定めた内部規程や監査基準と衝突しうる。 「脆弱性対応として一時的に戻した」ことを記録に残し、修正版のリリースを監視して 1.3 へ戻すところまでを1つの作業にしないと、回避策が恒久設定として居座る。 修正版が未リリースである脆弱性は、「対応済み」として台帳を閉じられないことが本質的な負担である（本記録の評価）。

既定でない構成だからこそ、自分の設定を見ないと該当するか分からない評価・解釈

本件の成立条件は、既定から外れた選択を2つ重ねた環境である（出典1・5。本記録の整理）。

  • クラスタ（セッションレプリケーション）を有効にしている—— Red Hat は標準配備では既定で無効と述べている（出典5）
  • そのクラスタ通信を TLS-PSK で保護し、TLS 1.3 を使っている

「既定ではない」ことは、安心の材料にも危険の材料にもなる（本記録の評価）〈重要〉。

安心の側——無差別のスキャンで広く悪用される形にはなりにくい。 クラスタ通信はインターネットに向けて公開するものではなく、該当する環境の数も限られる。

危険の側——該当する環境は、可用性を重視して複数台構成を組み、さらにノード間通信の暗号化まで検討した環境である（本記録の評価）。つまり、相対的に重要なシステムに偏る。 加えて、その設定を入れた判断は過去の設計時点にあり、いま運用している担当者が把握しているとは限らない。

確認は製品名では終わらない（本記録の整理）。「Tomcat 11.0.29 が入っているか」ではなく「その Tomcat の server.xml に <Cluster> があり、<Channel> の通信が TLS 1.3 ＋ TLS-PSK か」が分岐点である。 業務パッケージに同梱された Tomcat では、この設定はベンダー側が持っていることが多く、利用者が自分で確認できない（本記録の評価）—— その場合、照会と回答待ちの時間が対応時間に乗る。

実環境での悪用は確認できていない未確定事項

悪用を示す情報は見つけられなかった（本記録の確認）〈未確定3〉。

確認した範囲は次のとおりである。

  • CVE レコード（出典1） — 悪用に関する記述・cisaExploitAdd の記載は無い
  • Apache の3ブランチのセキュリティページ（出典2・3・4） — 記述無し
  • Red Hat の CVE ページ（出典5） — statement に悪用の言及は無い
  • NVD（出典6） — 解析待ちの状態で、悪用に関する記載は無い

「悪用されていない」とは書かない（本記録の明示）。確認できているのは「悪用の報告を見つけられなかった」ことまでである。 本件は成立条件が限られ、かつ標的が外部公開のサービスではないため、仮に悪用が起きても外部から観測されにくい（本記録の評価）—— 侵害後にクラスタへ参加する動きは、被害組織の内部ログにしか現れない。

  • 該当判定は `server.xml` を見る。バージョン一致だけでは判定にならない
    **成立条件は「クラスタ通信を TLS 1.3 ＋ TLS-PSK で保護している」ことである** （出典1・2・3・4）。 **Red Hat は標準配備ではクラスタが既定で無効と述べている**（出典5）—— **つまり、該当バージョンの大多数は対象外である可能性がある。**
    取るべき行動 **稼働中の各 Tomcat について、`server.xml` の `<Engine>`／`<Host>` 配下に `<Cluster>` 要素があるかを確認する。** **ある場合は `<Channel>` の送受信設定（`<Transport>` の TLS 設定）で プロトコルが TLS 1.3 か、鍵の方式が TLS-PSK かを確認する。** **確認結果（該当／非該当／ベンダー照会中）を資産ごとに記録し、 非該当であることの根拠も残す。**
  • 回避策を入れるなら、戻す作業までを1つのチケットにする
    **Apache の回避策は「TLS 1.2 への切り替え」である**（出典2・3・4）。 **プロトコルの世代を戻す措置であり、 修正版が出た後も放置されると恒久設定として残る**（本記録の評価）。 **修正版 11.0.30・10.1.63・9.0.125 のリリース日は公表されていない** 〈未確定1〉。
    取るべき行動 **TLS 1.2 への切り替えと、修正版適用後に TLS 1.3 へ戻す作業を 同一のチケットに含める。** **Tomcat のセキュリティページ（出典2・3・4）を定期的に確認する担当を決め、 「not yet released」の表記が消えたら作業を起こす。** **設定変更はコードまたは構成管理（Ansible 等）に残し、 手作業で入れた暫定設定が履歴から消えないようにする。**
  • クラスタのメンバー数を監視対象にする
    **本件の攻撃は「認証を経ずに信頼されたノードとして参加する」ことである** （出典1）。 **参加後の通信は仕様どおりのクラスタ通信そのものであり、 中身からは区別できない**（本記録の評価）〈重要〉—— **区別できるのは「誰が参加しているか」である。**
    取るべき行動 **クラスタのメンバー数と、メンバーの参加・離脱イベントを 監視・警報の対象にする。** **想定台数と一致しない状態を異常として扱う。** **併せて、クラスタ通信ポートへの想定外の送信元からの接続を ネットワーク側のログで記録する。**
  • セッションに載せる情報を減らしておくと、この種の欠陥の影響が小さくなる
    **Red Hat は、参加した攻撃者が到達しうる対象として 「機微なクラスタ状態やセッションレプリケーションのデータ」を挙げている** （出典5。原文英語。本記録の訳）。 **到達されるものの価値は、設計時にどれだけセッションへ載せたかで決まる** （本記録の評価）。
    取るべき行動 **セッションに保持している項目を洗い出し、 個人情報・権限情報・トークンの実体を載せていないかを確認する。** **載せる必要があるものは、セッションストアを クラスタのレプリケーションから外部ストアへ寄せ、 そこに別のアクセス制御を掛ける構成を検討する。**
  • CVE の重大度は CNA・ADP・ディストリビュータの3層で読む
    **本件では CNA（Apache）が CVSS を付けず、 ADP（CISA-ADP）が 9.8、ディストリビュータ（Red Hat）が 8.1 を付けた** （出典1・5・6）。 **NVD 自身は解析待ちである**（出典6）〈重要〉。 **1つの数値だけを見ると、どの前提に立った値かが分からない。**
    取るべき行動 **CVE を調べるときは `cveawg.mitre.org/api/cve/<ID>` で `containers.cna` と `containers.adp` を分けて見る習慣にする。** **自組織が使っているディストリビューション・製品ベンダーの CVE ページ（Red Hat・SUSE・Ubuntu 等）も併せて確認し、 評点が割れているときは割れた理由（本件では `AC`）を読む。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ Tomcat（9.0 系・10.1 系・11.0 系）を複数台構成で運用し、 クラスタ機能（セッションレプリケーション）を有効にしている本件はクラスタ通信の欠陥であり、クラスタを使っていなければ成立しない（出典1・5）—— Red Hat は標準配備ではクラスタが既定で無効と述べている（出典5）
システム構成□ クラスタ通信を TLS-PSK（事前共有鍵）で保護し、プロトコルに TLS 1.3 を使っている成立条件そのものである（出典1・2・3・4）—— TLS 1.2 を使っている場合は Apache の回避策が示す前提により対象外とされる
認証・認可□ ノード間通信の相手の正当性を、事前共有鍵を知っていることだけで担保している本件は鍵交換時に相手の身元が検証されなかった欠陥である（CWE-322・出典1）—— 鍵の共有が認証の代わりになる設計は、実装がそれを検証していることに依存する
運用・監視□ クラスタ通信のポートが、ノード以外から到達できるネットワークに置かれているRed Hat の緩和策は到達範囲の制限である（出典5・7）—— 到達できる位置を取られなければ、欠陥が残っていても参加されない
運用・監視□ 脆弱性管理の判断を、NVD や単一の CVSS 値の取り込みに委ねている本件の 9.8 は CISA-ADP の値で、NVD 自身は解析待ちであり、 開発元は CVSS を付けていない（出典1・6）—— 出所を保持していないと「NVD が 9.8 と判定した」と誤読する
委託・第三者部品□ 業務パッケージ・製品に同梱された Tomcat を使っており、 その設定ファイルを自組織で確認できない該当判定には `server.xml` の確認が要る（本記録の整理）—— 設定がベンダー側にある場合、照会と回答待ちの時間が対応時間に乗る
