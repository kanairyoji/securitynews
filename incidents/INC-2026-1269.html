INC-2026-1269Check Point 管理サーバ狙いの侵入 22組織

**GreyNoise が2026年11月23日、Check Point Security Management Server を狙う 侵入キャンペーンを公表した**——**少なくとも22の組織が影響を受け、 攻撃者は24台の Check Point 管理サーバから窃取したデータを 1台の中継用サーバに集めていた**〈重要〉。 **攻撃者が使った中心の脆弱性 CVE-2026-16232（Check Point SmartConsole の 認証バイパスから Run Script へ）は、2026年7月22日に Check Point が 修正と注意喚起を出し、同日 CISA の KEV に収載されたものである**〈重要〉—— **攻撃の観測は10月であり、修正から約3か月後に当たる。** **管理サーバで行われたのは「設定の持ち出し」だけではない**—— **ファイアウォールのデータベースと内部 CA を複製し、 新しい証明書（`pivot.p12`）を発行させ、 セキュリティポリシーの読み込みを解除する（＝ファイアウォールを無効化する） 管理タスクが100件以上投入された。** **攻撃者は被害組織の1台を踏み台（ORB／hop）に仕立て、 そこから他の被害組織の管理サーバを操っていた**〈重要〉—— **24台すべてが、踏み台に植えられた公開鍵と対になる秘密鍵を持っていた。** **GreyNoise は帰属を行っていない**—— **99個の IP はすべて ExpressVPN の出口か被害組織の Check Point 機器であり、 既知の脅威グループへの紐付けも、動機や出身国の評価も示していない。** **一方で「攻撃者は LLM とエージェント型の仕組みを使って 脆弱性の走査・悪用・ツール開発・侵害資産との自動的なやり取りを 行っていたと考える」と述べている**〈重要〉。

GreyNoise が2026年11月23日、Check Point Security Management Server を標的とする侵入キャンペーンを公表した（出典1）。同社は自前のセンサ網（Global Observation Grid）で捉えた活動を「GreyNoise Threat 13（GT13）」として追跡している。

公表の要点を同社自身がこう整理している（出典1。原文英語からの本記録の訳）。

「GreyNoise は最近、Check Point Security Management Server を標的とする侵入キャンペーンを発見した。確認された攻撃活動は2026年10月17日から11月2日のあいだで、世界で少なくとも22の異なる組織に影響している」

「攻撃者は99個の IP アドレスを使い、その多くは走査・悪用・被害組織の制御を行うための使い捨てのネットワーク基盤だった。侵害したサーバを『運用中継箱』（operational relay box／ORB）、より簡単に言えば『hop』として下流の被害組織の資産とやり取りするために使うことも含まれる。攻撃者はこの中継箱／hop を、24台の異なる Check Point Security Management Server から窃取したコマンドの結果とデータを保存するために使った」

帰属は示されていない〈重要〉。「我々は現時点で GT13 を既知の、あるいは公に追跡されている脅威グループに帰属させない。動機や出身国との整合性について評価を下すだけの情報も、現時点では持っていない」（出典1。原文英語からの本記録の訳）。

代わりに GreyNoise が踏み込んでいるのは、攻撃の作り方のほうである〈重要〉。「我々はハンズオンキーボードの活動も観測したが、現代の攻撃の多くと同様に、攻撃者は LLM とエージェント型の仕組みを使って脆弱性の走査・悪用・ツール開発・侵害資産との自動的なやり取りを行っていたと考える」（出典1。原文英語からの本記録の訳）。根拠として、2026年10月26日に24台へ一斉に投入された証明書関連の管理タスクが挙げられている—— 結果ファイルには被害組織の IP が昇順に並んでおり、自動化がそれらを順に回したことを示す（出典1）。

使われた中心の脆弱性は、修正済みのものである〈重要〉。CVE-2026-16232（Check Point SmartConsole の認証バイパスから Run Script へ）は、2026年7月22日に Check Point が最新の Jumbo hotfix（SK185169）と注意喚起を公表し、同日 CISA の KEV に収載された（出典2・3）。Check Point は当時、影響が「管理サーバが IP 制限なしでインターネットに直接面している」構成に限られるとし、暫定の緩和策として Trusted Clients を信頼できる IP／サブネットに限ることと、ファイアウォールで管理アクセスを守ることを挙げていた（出典2）。GT13 の活動が観測されたのは10月であり、修正から約3か月後である（本記録の整理）。

管理サーバで行われたことは、設定の持ち出しにとどまらない〈重要〉。Chisel のトンネル越しに CVE-2026-16232 のスクリプトを使って、複数の Check Point 管理サーバに100件を超える管理タスクが投入された（出典1）—— ファイアウォールのデータベースと内部 CA の複製、新しい証明書（pivot.p12）の発行、そしてセキュリティポリシーの読み込み解除（ファイアウォールを無効化する操作）である。 さらに Citrix NetScaler・Ivanti Connect Secure・VMware vCenter・Microsoft Exchange・Oracle TNS の資産と複数のドメインコントローラが探られた（出典1）。

GreyNoise の可視範囲は2026年11月2日ごろで途切れている（出典1）—— 「被害組織の Check Point 機器に対する攻撃者の永続的なアクセスを踏まえると、この侵入キャンペーンは継続中であると予想する」（原文英語からの本記録の訳）〈重要〉。

①のファイアウォールのデータベースには、組織のネットワークの構造と、何を通して何を止めているかが入っている。 これは「次にどこを狙えばよいか」の地図である（本記録の読み）。

CISO・経営層への示唆
  • 「修正が出ていること」と「当たっていること」を別の指標として報告させる
    **CVE-2026-16232 は2026年7月22日に Check Point が修正と注意喚起を公表し、 同日 CISA の KEV に収載された**（出典2・3）〈重要〉—— **本件で攻撃者が同じ脆弱性を使ったのは10月20日、約90日後である** （出典1。本記録の算出）。 **本記録の評価として、これは「情報が届いていなかった」事案ではない**—— **KEV に載るほど目立つ情報でも、適用の工程が追いつかなければ同じ結果になる。**
    取るべき行動 セキュリティ機器・管理サーバについて、 「KEV 収載済みの脆弱性のうち、自組織で未適用のもの」の一覧を 月次で経営に出す。件数ではなく機器名と経過日数で出す。 適用できない機器は、代替の緩和策が当たっているかを同じ表に並べる。
  • 停止の窓を要しない緩和策を、修正と同格の選択肢として持つ
    **Check Point の勧告は、ホットフィックスのほかに2つの暫定の緩和策を 挙げていた**（出典2）〈重要〉—— **①GUI クライアント（Trusted Clients）を信頼できる IP／サブネットに限る ②ファイアウォールで管理アクセスを守り信頼できる IP に限る。** **同社は影響が「管理サーバが IP 制限なしでインターネットに 直接面しているとき」に限られるとも述べていた。** **本記録の評価として、どちらも停止の窓を要しない**—— **修正の適用が運用の制約で遅れるときに取れる手が、確かに存在していた。**
    取るべき行動 重要な機器ごとに「修正を当てられないときに取る緩和策」を あらかじめ書いておく（到達経路の制限・機能の無効化・監視の強化）。 勧告が出たときに、修正の適用予定日と緩和策の適用日を別々に記録する。
  • 自組織の機器が他組織への攻撃経路になりうることを、リスクの前提に入れる
    **本件では24台の Check Point 機器のそれぞれが、 攻撃者の踏み台に植えられた公開鍵と対になる SSH 秘密鍵を持っていた** （出典1）〈重要〉—— **攻撃者が使った99個の IP はすべて商用 VPN の出口か 被害組織の機器であり、自前の C2 は1つも無かった。** **本記録の評価として、自組織の被害は「自組織のデータが出た」ことに とどまらない**—— **他組織への攻撃に使われた場合、取引先・当局・報道への説明が別途必要になる。**
    取るべき行動 インシデント対応の想定に「自組織の機器が他組織への攻撃に使われていた」 場合を加える。 その場合の①連絡先（CERT・取引先・当局）②説明の方針 ③法的な確認事項を、あらかじめ整理しておく。
  • 管理系の侵害を「設定が漏れた」ではなく「信頼の基盤が漏れた」として扱う
    **本件で管理サーバから複製されたのは、 ファイアウォールのデータベースと内部 CA である**（出典1）〈重要〉—— **さらに新しい証明書（`pivot.p12`）の発行と、 セキュリティポリシーの読み込み解除（ファイアウォールの無効化）が 管理タスクとして投入された。** **本記録の評価として、内部 CA の複製は設定の漏えいとは質が違う**—— **その CA を信頼しているすべての通信に対して、 攻撃者が正規の証明書を作れる状態になる（本記録の読み）。**
    取るべき行動 セキュリティ機器の管理サーバが持つ「信頼の基盤」を列挙する （内部 CA・証明書・共有鍵・連携用の資格情報）。 それぞれについて、侵害が疑われたときの無効化と再発行の手順と 所要時間を見積もっておく。
  • 被害組織に名前が無い公表から、自組織の確認項目を取り出す仕組みを持つ
    **本件の被害組織22社は匿名である**（出典1）〈未確定2〉〈重要〉—— **GreyNoise は政府の協力相手と CERT を通じて通知しているとする。** **本記録の評価として、名前が出ない公表は「他人事」として流されやすい**—— **しかし本件のレポートには、自組織で今すぐ確認できる項目が 具体的に書かれている（`authorized_keys`・`/etc/ld.so.preload`・ 管理タスクの監査ログ・外向きの scp の宛先）。**
    取るべき行動 ベンダーの脅威レポートを読む担当と、 そこから自組織の確認項目を抜き出して点検依頼に落とす工程を決める。 点検の結果（該当なしを含む）を記録に残す。
セキュリティ技術者への示唆
  • 管理サーバの `authorized_keys` と `/etc/ld.so.preload` を今すぐ点検する
    **本件では踏み台の `/root/.ssh/authorized_keys` への公開鍵の追記が 確認されている**（出典1）〈重要〉—— **さらに重要なのは、24台の被害機器のそれぞれが その公開鍵と対になる SSH 秘密鍵を持っていたことである** （結果ファイルが各被害基盤から scp で届いたことから判明）。 **被害機器の1台では `/etc/ld.so.preload` に登録された `/usr/lib/.libproc.so` のプリロードエラーが観測され、 GreyNoise は「機器上の implant を示すかもしれない」と述べている**（出典1）。
    取るべき行動 Check Point Security Management Server を含む管理機器について、 `authorized_keys` の全エントリ（鍵のコメントと指紋）、 `/etc/ld.so.preload` の登録内容、 予期しない秘密鍵ファイルの有無を点検する。 基準値として記録し、以後は差分を定期に見る。
  • 管理サーバの外向き接続を既定で遮断し、許可する宛先を列挙する
    **本件では管理サーバから踏み台へ scp で窃取データが送られていた** （出典1）〈重要〉—— **24台すべてが同じ踏み台へ送っていた。** **攻撃者の接続先は商用 VPN の出口か他の被害組織の正規の機器であり、 既知の悪性 IP の一覧と突き合わせても何も出ない（本記録の評価）。** **一方、管理サーバが能動的に外部へ接続するのは、 正規の運用でも限られた宛先に限られるはずである（本記録の読み）。**
    取るべき行動 管理サーバからの外向き接続を既定で遮断し、 許可する宛先（更新サーバ・ログ転送先・ライセンス確認先）を明示列挙する。 遮断できない環境では、宛先の一覧を日次で出し、新規の宛先を人が確認する。
  • 管理操作の監査ログを外部へ転送し、件数の異常を見る
    **本件では100件を超える管理タスクが投入され、 ファイアウォールのデータベースと内部 CA の複製、 証明書の発行、ポリシーの読み込み解除が行われた**（出典1）〈重要〉—— **これらはいずれも正規の管理操作として記録される種類の行為である （本記録の整理）。** **止まっていないことは、管理操作の監査ログが誰にも見られていなかったことを 示す（本記録の読み。公表に根拠は無い）。**
    取るべき行動 管理サーバの監査ログ（管理タスクの実行・ポリシーの変更・証明書の発行）を 機器の外へ転送する。 1日あたりの管理タスク件数の平常の幅を記録し、 超えた日に人が確認する通知を出す。 ポリシーの読み込み解除と内部 CA の操作は、単独で警報の対象にする。
  • セッション識別子の生成と IP 固定の設定を、自組織の製品でも確認する
    **踏み台への侵入経路は、HFS のセッション cookie の `sid` が JavaScript の `Math.random()` から引かれていたことを突いたものである** （出典1）〈重要〉—— **連続ログインで V8 の PRNG の内部状態を再構成し、 署名鍵を復元して管理者 cookie を偽造した。** **偽造された cookie には `allow_session_ip_change:true` が含まれており、 任意の IP から使えた**（出典1）。 **本記録の評価として、これは他の製品・自社開発でも起きうる型である。**
    取るべき行動 自社開発および自組織で運用する管理画面について、 ①セッション識別子が暗号学的に安全な乱数で生成されているか ②セッションを発行元 IP に紐付ける設定があるか、既定値はどちらか を確認する。 ②が無効な既定になっている製品を一覧にする。
  • 「失敗回数のしきい値」に頼らない検知を1つ持つ
    **本件の侵入は「成功したログインの連続」として現れる**（出典1）〈重要〉—— **HFS の悪用は `loginSrp1` への連続した POST（いずれも 200 OK）であり、 失敗の連続ではない。** **総当たりについても、攻撃者は被害組織向けに仕立てた 利用者名・パスワードを使っていた**（出典1。`spray_portal.py`・`comb.py`）—— **「攻撃者は標的が使いそうな名前とパスワードを 知っていたか、推測していた」（原文英語からの本記録の訳）。** **本記録の読みとして、当たりやすいパスワードを使えば 失敗回数は少なく済む（公表に根拠は無い）。**
    取るべき行動 認証の監視に、失敗回数とは別の軸を1つ加える。 同一エンドポイントへの短時間の連続要求（成功・失敗を問わない件数）、 または「普段と違う到達元 IP からの成功」を見る。 既存の警報が失敗回数だけに依存していないかを確認する。
  • 古い KEV 収載の脆弱性の棚卸しを、公開機器から先に行う
    **本件で横展開に使われた脆弱性はいずれも古い**（出典1）〈重要〉—— **CVE-2020-1472（Microsoft Netlogon）・CVE-2023-4966（Citrix NetScaler）・ CVE-2024-21893（Ivanti Connect Secure）・ CVE-2021-26855／CVE-2021-34473（Microsoft Exchange）・ CVE-2021-21972／CVE-2023-34048（VMware vCenter）。** **攻撃者は新しい脆弱性ではなく、残っている古いものを順に試している （本記録の整理）。**
    取るべき行動 VPN 機器・仮想化基盤・メール基盤・ドメインコントローラについて、 KEV 収載済みの脆弱性の適用状況を機器単位で一覧にする。 2020年〜2024年のものを先に確認する（新しいものより残っている確率が高い）。
