INC-2026-1271ASP.NET の CSRF 対策品に実悪用

**17年前に公開され、修正する者のいない ASP.NET 用の CSRF 対策ライブラリ `Idunno.AntiCsrf` に、認証不要の遠隔コード実行の穴が見つかり、 実環境での悪用が観測された**〈重要〉—— **CVE-2026-131914、CVSS 4.0 は 9.3（CRITICAL）である。** **穴は、CSRF トークンを検証する処理そのものにある**—— **`AntiCsrfModule.PreRequestHandlerExecute` が、 フォームから届いた CSRF トークンの値を、鍵を与えていない `System.Web.UI.ObjectStateFormatter` で逆シリアル化しており、 MAC も署名も検証していない（CWE-502・CAPEC-586 オブジェクトインジェクション）。** **攻撃者は、CSRF クッキーに空でない任意の値（例: `__CSRFCOOKIE=1`）を置き、 CSRF フォームフィールドに Base64 符号化した .NET のガジェットチェーンを 入れた `POST` を1回送るだけで、IIS のワーカープロセス（`w3wp.exe`）の権限で 任意コードを実行できる**〈重要〉—— **事前の認証も、正当な CSRF トークンも要らない。** **発見は、Mandiant のインシデント対応の現場である**—— **Google Cloud の FLARE が2026年11月4日に根本原因の分析を終え、 Mandiant は CNA として11月11日に CVE の採番に着手し、 11月18日に勧告と CVE を公開した。** **修正版は無い**〈重要〉—— **`Idunno.AntiCsrf` は CodePlex で公開され、 最終リリースが `0.9.1 Beta`（公式ビルドは2008年12月付）のまま 活動を終えた企画であり、維持する者も公式パッチも存在しない。** **Mandiant の勧告が示す対処は「使用をやめる」ことである。**

穴は、CSRF トークンを検証する処理の内側にあった原因・手口出典 [1]

Idunno.AntiCsrf は、ASP.NET WebForms 向けに 二重送信クッキー方式の CSRF 対策を提供する第三者の IHttpModule である （出典1）—— CodePlex（anticsrf.codeplex.com）で公開されていた。 Web.config の <httpModules> / <modules> に Idunno.AntiCsrf.AntiCsrfModule, Idunno.AntiCsrf として登録し、 <csrfSettings> で設定する。 [ConfigurationProperty] の既定値は cookieName が __CSRFCOOKIE、formFieldName が __CSRFTOKEN、 detectionResult が RaiseException である（出典1）。

AntiCsrfModule.Init は PreSendRequestHeaders と PreRequestHandlerExecute を購読し、 PreRequestHandlerExecute が各 Page ハンドラに PageLoad と PagePreRender を結び付ける（出典1）—— 処理の順は Init → PreRequestHandlerExecute → PageLoad → PagePreRender → PreSendRequestHeaders。

問題は PreRequestHandlerExecute である〈重要〉。 ISuppressCsrfCheck を実装せず [SuppressCsrfCheck] も 付いていない System.Web.UI.Page ハンドラについて、 このメソッドは Page_Load より手前で POST 要求を調べる（出典1）。 確かめるのは Request.Cookies[CsrfSettings.Settings.CookieName] と Request.Form[CsrfSettings.Settings.FormFieldName] が いずれも空でないことだけである—— クッキーが整形された GUID であることも検証せず、 <form runat="server"> の存在も要求しない。 その上で、引数なしの new ObjectStateFormatter() を作り、 Deserialize(context.Request.Form[...]) を呼び、 結果をクッキーの値と比較する（出典1）。

引数なしの ObjectStateFormatter コンストラクタは、 MAC・署名・暗号化・machineKey の検証を一切行わず、 SerializationBinder による型の制限も課さない（出典1）〈重要〉—— したがって、空でない任意のクッキー（例: Cookie: __CSRFCOOKIE=1）と、 Base64 符号化した .NET の ObjectStateFormatter ガジェットチェーンを CSRF フォームフィールドに入れて送れば、 Deserialize() の内側で任意コードが w3wp.exe の権限で動く。

検証の順序が逆であることが、本件の構造である（本記録の整理） 〈重要〉—— クッキー値が GUID かどうかの検証（GuidTryParse）は、 描画側の PagePreRender にしか実装されておらず、 Deserialize() を呼ぶ PreRequestHandlerExecute の手前には無い （出典1）。 比較する前に逆シリアル化してしまうため、 「正しいトークンかどうか」を判定する前に、コードが動く。

「ログインしていなければ安全」は成り立たない被害規模・影響範囲出典 [1] [2]

勧告は到達の容易さを「Exploitability: High」と評価している （出典1）〈重要〉。 根拠は実行の順序である。 AntiCsrfModule.PreRequestHandlerExecute は HttpApplication のパイプライン段で、 IHttpHandler.ProcessRequest と ASP.NET の Page ライフサイクル （PreInit・Init・Page_Load）より手前に動く（出典1）。

パイプライン段の認証・認可 （AuthenticateRequest / AuthorizeRequest）は、さらに手前で動く （出典1）—— つまり URL 単位で認証を要求しているページは守られる （本記録の読み）。 守られないのは次の2つである（出典1）〈重要〉—— ①匿名で到達できる .aspx ページ、 ②Page_Load の中のアプリ層のセッション確認に依存しているページ。 後者は、認可の判定が逆シリアル化より後に走るため、 判定に辿り着く前にコードが動く。

本記録の評価として、②の構成は古い WebForms アプリで 珍しいものではない—— 「ログイン画面は匿名で見せる」「権限は画面のコードで判定する」は、 2008年当時の標準的な作りである（本記録の読み。公表に根拠は無い）。 <form runat="server"> が無いページでも成立するため（出典1）、 「入力フォームの無いページは対象外」という切り分けもできない。

影響範囲はバージョン全域である（出典2）—— CVE レコードの affected は 「0 から 0.9.1.0 以下」および「0 から 0.9.1 Beta 以下」で、 既定値は affected。 存在する全バージョンが影響を受ける。

発見はインシデント対応の現場であり、被害組織は公表されていない発覚の端緒出典 [1] [2]

勧告の開示経緯は3行である（原文英語。出典1）〈重要〉—— 「2026-11-04: インシデント対応の調査中に FLARE が 脆弱性の根本原因の分析を完了」、 「2026-11-11: Mandiant CNA が周知のために CVE 採番を開始 （上流の企画は活動を終えており、ベンダーや維持者による パッチは入手できない）」、 「2026-11-18: Mandiant の勧告と CVE-2026-131914 を公開」。

1行目が本件の性格を決めている（本記録の評価）〈重要〉—— この脆弱性は、机上の監査や懸賞金制度から出てきたものではない。 誰かの環境が実際に侵害され、その対応の中で 根本原因として特定された。 勧告の Exploitability 節も 「実環境での活発な悪用が観測されている」と結んでいる（原文英語）。

それでも、被害組織・侵害の時期・件数・攻撃者は 一切公表されていない〈未確定1〉。 勧告は発見者として5名を挙げる（出典1）—— LDB、Genwei Jiang 氏と Dhanesh Kizhakkinan 氏 （Google Cloud, FLARE OTF）、 Brian Bahtiarian 氏と Lucas Kossack 氏 （Mandiant Incident Response）。 後2名の所属がインシデント対応部門であることが、 経緯の記述と整合する（本記録の読み）。

一方、CISA の Vulnrichment（ADP）が同じ CVE レコードに 2026年11月19日 01:39 UTC 付で付した SSVC の判定は Exploitation: none である（出典2）〈差異1〉〈重要〉—— Automatable: yes、Technical Impact: total は Mandiant の記述と整合するが、悪用の有無だけが食い違う。 本記録は、Mandiant が実悪用を観測した当事者であることから E:A（ATTACKED）側を採る（本記録の判断）—— ただし CISA の判定が付いた時刻は勧告の公開から数時間後であり、 反映の遅れである可能性も否定できない（本記録の読み）。

対処は「使う側だけで完結する」——当てるパッチが無いから対策・注意喚起出典 [1]

公式パッチは存在しない（出典1）〈重要〉—— 「Idunno.AntiCsrf は、既に廃止された CodePlex 上で 0.9.1 Beta（公式ビルドは2008年12月付）を最終リリースとして 活動を終えたオープンソース企画であり、 活動中の維持者も公式パッチも無い」（原文英語）。

勧告が示す対処は3段である（出典1）。 ①取り除く。 <httpModules> と <modules> から Idunno.AntiCsrf.AntiCsrfModule の登録をすべて削除し、 <configSections> の <section name="csrfSettings" ... /> と Web.config の <csrfSettings ... /> を削除し、 ISuppressCsrfCheck / [SuppressCsrfCheck] への参照を削除し、 bin/ から Idunno.AntiCsrf.dll を削除する。 ②置き換える。 System.Web.Helpers.AntiForgery、 WebForms の Page.ViewStateUserKey ＋ MAC 検証・暗号化済み ViewState、 ASP.NET Core の IAntiforgery のいずれか。 ③探して、見直す。 すべての Web.config と bin/ を Idunno.AntiCsrf / AntiCsrfModule の名前で監査し、 IIS のログで .aspx への異常な POST （HTTP 302 または 500 で cs-bytes が大きいもの）を見る。

ここで注意すべき点が1つある（本記録の評価）〈重要〉—— 攻撃が成功した要求も、応答はエラーで返る。 逆シリアル化の直後に RaiseError が走るためである（出典1）—— detectionResult="Redirect" なら errorPage へ 302、RaiseException なら PotentialCsrfException が投げられ、 customErrors が有効なら defaultRedirect へ 302、 mode="Off" なら 500。 つまり「CSRF 検知エラーが出ている」というログは、 対策が効いている証拠にも、既に侵害された証拠にも読める （本記録の読み）。 応答コードでは区別が付かない。

悪用の痕跡がある環境では、Web.config と applicationHost.config の秘密をすべて入れ替えるよう求められている （出典1）〈重要〉—— <machineKey> の鍵、暗号鍵、データベースの資格情報を含む。 併せてウェブルートに権限のないファイルが置かれていないか点検する。 本記録の評価として、<machineKey> のローテーションは 副作用が大きい—— 既存の ViewState・認証クッキー・セッションが無効になるため、 複数サーバで鍵を共有している構成では 同時に入れ替えないと利用者がログインできなくなる。 侵害が分かった日に手順を考え始めると、復旧が障害に変わる。

「防御のために足した部品」こそ、棚卸しから漏れる評価・解釈

以下は本記録の評価である〈重要〉。

本件の形は、第三者ライブラリの脆弱性として平凡である—— 逆シリアル化（CWE-502）、オブジェクトインジェクション （CAPEC-586）、鍵のない ObjectStateFormatter。 .NET の世界では長く知られた型の穴である。 平凡でないのは、穴があった場所である。

穴は、CSRF 対策の部品の中にあった〈重要〉。 セキュリティのために導入した部品が、 認証より手前のパイプライン段で、 信頼できない入力を鍵なしで逆シリアル化していた。 しかも、その部品が守っていたはずの CSRF トークンの 「正しさの比較」は、逆シリアル化の後に置かれていた—— 比較に辿り着く前に、コードが動く。

ここから出てくる問いは、資産管理のほうである（本記録の読み）。 多くの組織は、業務ロジックの依存ライブラリは棚卸ししている。 一方で「セキュリティ対策として入れた部品」は、 対策の実施記録としては残っていても、 脆弱性管理の対象台帳には載りにくい—— 入れたこと自体が「対策済み」の印になってしまうからである。 本記録は、これが本件から取れる最も移植可能な教訓だと評価する。

もう1つ、供給元が存在しない依存の扱いがある〈重要〉。 本件は patch-management（脆弱性の放置）として整理できない—— 当てるべきパッチが存在しない。 2008年に最終リリースされた部品を18年動かし続けた組織は、 「更新が無い」ことを安定の印として読んでいた可能性がある （本記録の読み。公表に根拠は無い）。 更新が止まっている依存は、安定しているのではなく、 直す者がいない状態である。 この区別は、SBOM を持っているかどうかとは別の問題である—— 台帳にバージョンが載っていても、 「上流が生きているか」は別の列である。
