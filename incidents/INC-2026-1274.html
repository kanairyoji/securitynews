INC-2026-1274Zyxel GS1900 のパッチが無効

**Zyxel の GS1900 シリーズのスイッチに対する2026年6月の修正（2.90 Patch 2）が 効いておらず、同じエクスプロイトが無変更で通ることが判明した**〈重要〉—— **Zyxel は別の脆弱性として CVE-2026-107441 を採番し、 2026年11月3日に 2.90 Patch 3 の勧告を出した。** **Binarly の解析によれば、原因は検査の順序である**—— **要求パラメータを最大140個まで格納する固定領域に対して、 サイズの検査も個数の検査も無かったのが元の穴（CVE-2026-7273）で、 Patch 2 は個数の検査を足したが、 それを「サイズ超過のパラメータをコピーした後」に行ったため、 検査の時点でカウンタは既に攻撃者の値になっていた。** **GreyNoise は、この穴を使って48か国の 996 台の GS1900 から データが持ち出されたと報告している**〈重要〉—— **持ち出されたのは設定、ハッシュ化された root の資格情報、 ネットワーク情報で、うち 564 台は工場出荷時の資格情報を 使い続けていた。** **GreyNoise はこの活動を「Kapibala」と呼び、 実行者を中国語話者とみられる単独の攻撃者（UTC+8 の可能性）と評価し、 C2 ドメイン・マルウェアファミリ・Gitea の悪用などの共通点から 「Red Heron」と同一か近縁としている。** **CVSS は Zyxel が 8.8、第三者の研究者が 9.8 と評価が分かれている。**

初報: 2026年9月21日（GreyNoise の報告） 最終更新: 2026年11月24日

Zyxel は2026年11月3日、GS1900 シリーズのスイッチに領域外書き込みの脆弱性（CVE-2026-107441）があるとして、10機種分の修正ファームウェア 2.90 Patch 3 の勧告を公開した（出典1・2）〈重要〉。CVE の記述は「Zyxel GS1900-24E ファームウェアの2.90(AAHK.2)C0 までのバージョンにおける CGI プログラムの領域外書き込みの脆弱性により、認証されていない隣接の攻撃者が細工した HTTP 要求を通じて OS コマンドを実行しうる」（原文英語。出典2）。 CWE-787（領域外書き込み）、報告者は Binarly のYegor Vasilenko 氏である（出典1・2）。

本件の重さは、これが2度目の修正だという点にある〈重要〉。元の脆弱性 CVE-2026-7273 は2026年の初夏に見つかり、Zyxel が 2.90 Patch 2 を出した時点で既に活発に悪用されていた（出典4）。2026年9月、Binarly の研究者がそのパッチが効いていないことを発見し、攻撃者が同じか極めて近いエクスプロイトで攻撃を続けていることを確認した（出典4）—— 情報は Zyxel に渡され、Zyxel はこれを別の問題として新しい識別子を割り当てた。

原因は検査の順序である（出典4）〈重要〉。Binarly によれば、脆弱性はスイッチへのネットワーク要求を処理するプログラムにある——要求されたパラメータを、最大140個まで格納できる固定のメモリ領域に置くが、パラメータのサイズの検査も、格納するパラメータの個数の検査も無かった。 エクスプロイトは、サイズが許容を超える140番目のパラメータを与える——これが領域外への書き込みを生み、プログラムのパラメータカウンタを上書きする。 次のパラメータは領域の外に書かれ、攻撃者は次に呼ばれる関数を差し替えて、自分のコマンドを実行させられる。 Patch 2 はカウンタの検査を実装したが、それを「許容を超えるサイズのパラメータをコピーした後」に行っていた—— その時点でカウンタは既に攻撃者が与えた値になっているため、検査は領域外への書き込みを止めない。 研究者は、エクスプロイトが第2のパッチに対して何の変更も無く動くと述べている。 Patch 3 ではサイズとカウンタの両方の検査が適切に実装されている。

被害の規模は、GreyNoise が報告している（出典3）〈重要〉—— 攻撃者は48か国の 996 台の ZyXEL GS1900 からデータを持ち出した。 上位3か国はイタリア（133台）、米国（129台）、台湾（123台）。 持ち出されたのは設定、ハッシュ化された root レベルの資格情報、ネットワーク情報である（出典3・4）。うち 564 台は工場出荷時の資格情報を使い続けていた（出典3）。悪用の時期は「2026年8月17日ごろ」とされる（出典3）。手口は、エクスプロイトで TFTP のコマンドを実行させて収集用のスクリプトを取得し、集めたデータを /home/web/tmp/info.txt に置いて後から回収する形である（出典3・4）。

実行者について、GreyNoise は単独の攻撃者と評価し、中国語話者で UTC+8 にいる可能性を挙げている（出典3）—— この活動群を「Kapibala」と呼ぶ。 C2 ドメインの共有、マルウェアファミリ、Gitea の悪用、その他の TTP の共通点から、「Red Heron」と同一か近縁としている（出典3）。CNews は、Red Heron を Acronis が追跡している集団とし、C++ で書かれた Linux 用インプラント「Jitterly」を使ったGitea サーバへの一連の攻撃で知られるとする（出典4）—— 9月に見つかったエクスプロイトは、Jitterly の管理に使われていたのと同じサーバに置かれていた。

評価が分かれている点が2つある。 ①CVSS——Zyxel は 8.8 と評価し、第三者の研究者は 9.8 とする（出典2・4）〈差異1〉。②攻撃を受けた機器に Patch 2 が当たっていたかは、GreyNoise も Binarly も明言していない（出典4）〈未確定3〉—— ファームウェアのバージョンも、攻撃者がどうやって管理インタフェースに到達したかも報告には書かれていない。

本件の形は、脆弱性の実悪用事案として平凡である—— ネットワーク機器の管理インタフェース、 領域外書き込み、認証不要のコマンド実行。 平凡でないのは、間に挟まった140日である。

ここから出てくる問いは3つある。

①脆弱性対応の完了判定を、何で行っているか。 多くの組織は「バージョンが上がったか」で判定する （本記録の読み。公表に根拠は無い）。 本件では、その判定が通っても防御は成立していなかった。 代わりに何を見るべきか、という問いに 一般的な答えは無い（本記録の評価）—— 利用者には修正の中身を検証する手段が無い。 現実的な対処は、 「パッチの適用を唯一の対策にしない」ことである—— 到達経路の限定を、パッチと独立に維持する。

②CVE を分けたことの代償。 Zyxel は、残った穴を CVE-2026-7273 の修正漏れとして扱わず、 別の脆弱性として採番した（出典4）〈重要〉—— 技術的な区別としては成り立つ （元は個数の検査の欠落、残ったのはサイズの検査の欠落）。 だが利用者にとっての事実は 「同じエクスプロイトが無変更で通る」ことである。 2つに分けると、 「6月の CVE には対処済み」という記録が 防御の証明として残る。 本記録の評価として、別の CVE として採番するなら、 「前のパッチでは止まらない」ことを 勧告の本文で明示する必要があった。

③勧告に悪用の記述が無い。 Zyxel の11月3日の勧告には、 実環境での悪用についての記述が無い （出典1）〈差異4〉〈重要〉—— 996 台からのデータ持ち出しが 2026年9月21日に既に公表されていたにもかかわらずである （出典3）。 勧告は報告者として Binarly の研究者を挙げるが、 「既に悪用されている」ことには触れない。 利用者が緊急度を判断する材料として、 これは欠けている（本記録の評価）。

CISO・経営層への示唆
  • 脆弱性対応の完了判定を「バージョンが上がったか」だけで行わない
    **本件では、2.90 Patch 2 を当てた機器でも 同じエクスプロイトが無変更で通った**（出典4）〈重要〉—— **6月16日の勧告から11月3日の勧告までの140日間、 「修正済み」という記録が防御の証明にならなかった （本記録の算出）。** **996 台からのデータ持ち出しはこの期間に起きている** （出典3）。 **本記録の評価として、利用者には修正の中身を 検証する手段が無い**—— **だからこそ、パッチを唯一の対策にしてはいけない。**
    取るべき行動 脆弱性対応の記録に「到達経路の限定の状態」の列を足す。 パッチの適用状況とは別に、 ①管理インタフェースがどこから到達できるか ②認証の設定が初期値でないか を機器ごとに記録する。 パッチ適用後も、この2つを対策として維持する （パッチが無効だった場合に残る唯一の防御である）。
  • 「不完全な修正」の再評価を、定期の運用に組み込む
    **Patch 2 の不備を見つけたのは、 供給元ではなく第三者の研究者である**（出典4）〈重要〉—— **Binarly が2026年9月に発見し、Zyxel に報告した。** **本記録の評価として、組織側にこれを独自に 見つける力は無い（本記録の読み）。** **できるのは、「一度対処した脆弱性」の情報を 追い続けることである—— 不完全な修正は、新しい CVE 番号で現れる。**
    取るべき行動 過去1年に対処した重大脆弱性の一覧を作り、 同じ製品・同じ部位に新しい CVE が出ていないかを 四半期ごとに確認する。 特に「既に悪用されていた脆弱性」は優先して追う （攻撃者が手放さないため）。 供給元の勧告一覧を購読し、同一系列の2件目に注意する。
  • ネットワーク機器を資産台帳に載せ、担当を明確にする
    **GS1900 は中小規模の拠点で広く使われる価格帯の スマートマネージドスイッチである**（本記録の読み。 出荷台数に関する公表は無い）〈重要〉。 **996 台のうち 564 台が工場出荷時の資格情報を 使い続けていた**（出典3）—— **約57%である（本記録の算出）。** **本記録の評価として、この比率は 「設置して以後触られていない機器」の多さを示す （本記録の読み）—— 資産台帳に載っておらず、 担当が決まっていない機器の典型である。**
    取るべき行動 スイッチ・無線 AP・UPS・NAS など 「設置して以後触らない機器」を資産台帳に載せる。 機種・ファームウェアのバージョン・ 管理インタフェースの到達範囲・認証の設定・ サポート期限・担当者 の6項目を埋める。 埋まらない機器は、その事実自体をリスクとして扱う。
  • 供給元の勧告に悪用の記述が無いことを、悪用が無い証拠と読まない
    **Zyxel の2026年11月3日の勧告には、 実環境での悪用についての記述が無い**（出典1） 〈差異4〉〈重要〉—— **996 台からのデータ持ち出しが 2026年9月21日に既に公表されていたにもかかわらずである （出典3）。** **本記録の評価として、供給元の勧告は 「製品の欠陥と修正版」を伝える文書であり、 脅威の情勢を伝える文書ではない（本記録の整理）。** **緊急度の判断には別の情報源が要る。**
    取るべき行動 脆弱性の緊急度を判定する手順に、 供給元の勧告以外の情報源を1つ以上組み込む （CISA KEV・監視事業者の報告・CVE レコードの 悪用成熟度の指標）。 供給元の勧告だけで「悪用なし」と判定しない運用に変える。
セキュリティ技術者への示唆
  • まず機種とバージョンを突き合わせ、Patch 2 を「済み」と数えない
    **影響を受けるのは10機種の `2.90(XXXX.2)C0` 以前で、 修正版は `2.90(XXXX.3)C0` である**（出典1）〈重要〉—— **Patch 2（`.2)C0`）は影響を受ける側に含まれる。** **「6月のパッチを当てた」という記録があっても、 本件の対象である（本記録の整理）。** **CVE レコードでは機種名の表記が1件揺れている** 〈差異6〉—— **勧告の表は `GS1900-24HPv2`、 CVE レコードは `GS1900-HPv2 firmware`。**
    取るべき行動 GS1900 の全台について、機種とファームウェアのバージョンを 収集する。 バージョン文字列の括弧内（AAHH・AAHI・AAZI・AAHJ・AAHL・ AAHK・ABTO・ABTP・AAHN・ABTQ）で機種を照合し、 末尾が `.2)C0` またはそれ以前のものを対象として抽出する。 `.3)C0` になっているものだけを対処済みと数える。
  • 管理インタフェースへの到達範囲を、自分で確認する
    **到達条件は管理インタフェースへの到達である** （出典2・4）〈重要〉—— **CVE は「認証されていない隣接の攻撃者」とし、 CNews は「潜在的な攻撃者が管理インタフェースに アクセスできた場合に限る」と条件を明示している。** **だが実際に48か国 996 台が悪用された**（出典3）—— **到達の経路は公表されていない**〈未確定3〉。 **CVSS が Zyxel 8.8 と第三者 9.8 で分かれているのは、 まさにこの見方の違いである**〈差異1〉。 **本記録の評価として、数字ではなく 自社の実態を確認するほうが確実である。**
    取るべき行動 各スイッチの管理インタフェースについて、 ①待ち受けているアドレスと VLAN ②どのネットワークから到達できるか ③インターネットから到達できないことの確認（外部からの走査） を実測する。 管理 VLAN に分離し、アクセス元 IP を制限する。 分離後も「同一ネットワークの別の機器が侵害された場合」は 条件が満たされることを前提に、次の項目を併せて行う。
  • 管理ネットワークからの外向き通信を既定で拒否する
    **攻撃の手口は、エクスプロイトで TFTP のコマンドを 実行させて収集用のスクリプトを取得し、 集めたデータを後から回収する形である** （出典3・4）〈重要〉。 **本記録の評価として、スイッチが TFTP で 外部からファイルを取得するのは通常の動作ではない （本記録の読み）—— この段で止める余地が最も大きい。** **持ち出しも外向きの通信であり、 出口を絞っていれば止まる。**
    取るべき行動 管理ネットワークの出口で、 ネットワーク機器からの外向き通信を既定で拒否する。 必要な通信（NTP・SNMP トラップ・syslog・ ファームウェア取得）だけを宛先と手順を指定して許可する。 TFTP は、使っていなければ明示的に拒否する。 フロー監視で、機器からの想定外の外向き通信を検知する。
  • Patch 3 を当てる前に、調査するか否かを機器ごとに決める
    **探すべき痕跡は、収集用スクリプトの残骸 （`/home/web/tmp/info.txt`）、 意図しない TFTP の通信、設定の改変である** （出典3・4。本記録の整理）〈重要〉。 **本記録の評価として、スマートマネージドスイッチは ログの保持容量が小さく、 外部転送を設定していなければ再起動で失われる （本記録の一般的な理解。 本件の機器の構成に関する公表は無い）。** **Patch 3 の適用は再起動を伴うため、 痕跡が消えうる。**
    取るべき行動 対象機器を2つに分ける。 ①管理インタフェースが広い範囲から到達できていた機器 （調査を先に行う。設定のダンプ・ファイルの確認・ ログの保全）。 ②分離されていた機器（修正を先に行う）。 判断の基準を先に決め、現場で迷わないようにする。 調査の結果を残す場所も先に決める。
  • 悪用の疑いがある機器では、設定に含まれる秘密をすべて入れ替える
    **持ち出されたのは、設定、 ハッシュ化された root レベルの資格情報、 ネットワーク情報である**（出典3）〈重要〉—— **996 台のうち 564 台は工場出荷時の資格情報を 使い続けていた（約57%。本記録の算出）。** **ハッシュ化されていても、初期値のままなら 解く必要が無い（本記録の読み）。** **本記録の評価として、入れ替えの対象は root の資格情報だけではない**（公表された推奨ではない）—— **設定には SNMP のコミュニティ名、 RADIUS の共有鍵、管理用の証明書も含まれうる。**
    取るべき行動 悪用の疑いがある機器の設定をダンプし、 含まれる秘密を列挙する（管理者の資格情報・ SNMP のコミュニティ名・RADIUS の共有鍵・ TACACS の鍵・証明書と鍵）。 連携先への影響を確認した上で、入れ替えの順序を決める （SNMP 監視・RADIUS 認証・管理システムからの接続が 同時に切れうる）。 入れ替え後に、接続性を1つずつ確認する。
