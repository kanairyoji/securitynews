INC-2026-1295FreeSWITCH の SIP に実悪用の RCE

FreeSWITCH の受信 SIP MESSAGE 処理に、**1通のメッセージで守護プロセス権限の OS コマンドが実行できる欠陥**があった（CVE-2026-116779・CVSS 9.8）—— **To ヘッダの利用者部分を `api+system%20id` と書くと、FreeSWITCH は `+` の左側を チャット protocol 名、右側を URL デコードして `switch_api_execute()` に渡す**。 **`api` は `mod_dptools` が既定で登録しているチャットインタフェースで、 `system` は OS コマンドを実行する標準 API である**。 **メモリ破壊も不正なパケットも無く、protocol 選択子とコマンド連結点が繋がっているだけ。** **SignalWire は2026年10月28日の勧告で「この経路の悪用が実際に観測されている」と述べ、 CISA は11月9日に KEV へ収載して期限を11月12日（3日後）に設定した**—— **修正は 1.11.3 で、profile 単位の `enable-chat-api-proto`（既定で無効）が 入った。1.10 系に同じ設定を書いても未知の引数として無視されるため、 設定での緩和はできず更新か該当パッチが要る**

api という protocol 名は mod_dptools が正規に登録している（出典3）〈重要〉—— mod_dptools.c:6486 でSWITCH_ADD_CHAT(chat_interface, "event", event_chat_send) とSWITCH_ADD_CHAT(chat_interface, "api", api_chat_send) が登録される。 出典3 はこの点を明示している（出典3）〈重要〉—— 「api protocol 自体は隠された裏口ではない。mod_dptools が正常に登録しているチャットインタフェースであり、設計上メッセージを通じて FreeSWITCH の API を実行できるようになっている。問題はこのインタフェースが既定で登録され、かつ profile ごとの許可一覧を持たなかったことである」（出典3。本記録が訳した）。1.11.3 の修正もインタフェースを削除せず、明示的な有効化（opt-in）に変えただけである（出典3）。

処理の流れは3つのファイルにまたがる（出典3）〈重要〉—— ①sofia_presence.c:4870 付近: To 利用者の最初の + を探し、左側を char proto[512] に複製、右側を宛先アドレスとする（宛先側に含まれる + は @ に書き換えられる）、 ②:4894: 右側を事象ヘッダ to_proto に書き込む。:5014: switch_core_chat_send(proto, event) がprotocol 名でチャットインタフェースを探す、 ③mod_dptools.c:4698・:4705: api_chat_send() が事象の to ヘッダをURL デコードし、最初の空白でコマンド名と引数に切ってswitch_api_execute() を呼ぶ。

既定値が2つ効いている（出典3）〈重要〉—— ①sofia.c:4665 は PFLAG_ENABLE_CHAT を無条件に設定するため、受信チャットは明示的に切らない限り有効である、 ②sofia.c:6118 付近の論理により、auth-messages を明示していない場合はPFLAG_AUTH_MESSAGES が設定され、stock の internal／external ではMESSAGE 認証が要求される。 external.xml の auth-calls=false は呼の認証にのみ影響し、メッセージ認証を切らない（出典3）〈重要〉—— 設定の名前が似ているため混同しやすい点である（本記録の評価）。

攻撃面は「受信 MESSAGE を受け付ける profile」で、それが既定である——ただし認証の前提条件は資料間で読みが分かれる被害規模・影響範囲出典 [1] [2] [3]

勧告は攻撃面をこう述べる（出典1）〈重要〉—— 「受信 MESSAGE を受け付ける任意の SIP profile。これが既定である。vanilla 設定は internal と external の profile でチャットを有効にしたままである」（出典1。原文英語。本記録が訳した）。vanilla では internal が 5060、external が 5080 で待ち受ける（出典3）。

前提条件の読みが分かれている〈齟齬1〉〈重要〉—— 勧告は「1通の SIP MESSAGE を受理させること」が前提であり、「MESSAGE 認証が強制されている場合は profile 上の任意の有効なアカウントで足りる」とする（出典1）。さらに「conf/vanilla/directory/default/default.xml をそのまま残している構成は、その利用者がパスワードも a1-hash も持たないため、アカウント無しで悪用できる場合がある」とする（出典1）〈重要〉。一方、出典3 は「stock の internal／external は MESSAGE 認証を既定で要求する。公開 PoC の『単包未認証』は auth-messages=false を設定した構成でのみ成立し、stock の既定値ではない」とする（出典3）。

本記録はこの2つを矛盾とは読まない（本記録の整理）〈重要〉—— 「認証は要求される」（出典3）と「vanilla の既定利用者はパスワードを持たないので認証が実質的に通る」（出典1）は両立する。 ただし、どちらの読みを採るかで「自組織は危ないか」の判定が変わる（本記録の評価）〈重要〉—— したがって実務上の確認事項は2つである—— ①profile で auth-messages が無効化されていないか、 ②directory にパスワードも a1-hash も持たない利用者が残っていないか。 本記録は、どちらの構成が多いかを示す材料を持たない（本記録の明示）。

権限は守護プロセスのものである（出典3）〈重要〉—— 出典3 の検証ではコンテナ内で root 権限で動いていたためsystem touch /tmp/fs-pwned が root 所有のファイルを作り、id は uid=0(root) を返した（出典3）。公式の推奨どおり権限を落としていれば到達点はfreeswitch サービス利用者になるが、設定・directory 利用者・ゲートウェイ資格情報・CDR の読み取りと改変、呼の経路の変更、module の読み込みは依然として可能である（出典3）〈重要〉—— 「root でないから軽い」とは読めない（本記録の明示）。

CISA は適用範囲をさらに広く見ている（出典2）〈重要〉—— 「この脆弱性はオープンソースの部品・第三者ライブラリ・protocol・独自実装に影響し、異なる製品で使われうる」（出典2。原文英語。本記録が訳した）〈未確定4〉—— FreeSWITCH を直接導入した覚えがない組織でも、製品に同梱されている可能性がある（本記録の整理）。

設定では閉じられない——1.10 系に新しい引数を書いても未知の引数として無視される対策・注意喚起出典 [1] [3]

修正は 1.11.3 である（出典1）〈重要〉—— profile 単位の新しい引数 enable-chat-api-proto が入り、明示的に有効にしない限り受信 MESSAGE は api protocol を選べない。拒否された要求には 403 を返して記録に残す。この引数は vanilla の profile と mod_sofia の見本設定ではコメントアウトされた状態で同梱される（出典1）。出典3 は修正コミットを 7015f6a73ab3d67fed5fbfc277ecfb88a74c2a86 とする（出典3）。

設定層での緩和はできない（出典3）〈重要〉—— 「1.10.11 と 1.10.12 のソースにこの関門は無い。enable-chat-api-proto=true を 1.10.10 に書いても効かず、解析器が未知の引数として無視する。設定層では緩和できず、更新するか該当するパッチを当てるしかない」（出典3。本記録が訳した）〈重要〉—— 本記録はこれを本件で最も実務的に重い記述と見る（本記録の評価）—— 「設定を1行足して様子を見る」という逃げ道が無い。

勧告が挙げる迂回策は3つで、うち2つは経路を閉じない（出典1）〈重要〉—— ①受信チャットを必要としない profile で enable-chat=false を設定する（その profile では受信 MESSAGE のチャットを完全に無効にする。これは閉じる措置である）、 ②auth-messages を有効にするだけでは不十分であり、パスワードも a1-hash も持たない directory 利用者を削除することで認証済みの悪用に縮小できるが、経路は閉じない、 ③disable_system_api_commands=true は system API だけを外すため、経路は閉じない〈重要〉—— mod_lua が読み込まれている場合（vanilla 設定が含む）、インラインの Lua が第2の到達点になる（出典1）。

したがって実務上の順序はこうなる（本記録の判断）〈重要〉—— ⓐまず enable-chat を業務で使っていない profile で false にする（即日・停止の影響が小さい）、ⓑ並行して 1.11.3 以降への更新を計画する（これが唯一の恒久対策）、ⓒ更新までの間、SIP の受信ポートに到達できる範囲を縮める（トランク事業者の IP のみ許可・内線は VPN 経由）、ⓓ守護プロセスの権限を落とす（被害の上限を下げる）。 ⓐを実行する前に「どの profile が MESSAGE を業務で使っているか」を確認すること——WebRTC のチャットや SMS ゲートウェイ連携が該当しうる（本記録の整理）。

読みどころは評点の高さではなく、「SIP の 202 応答では悪用の成否が分からない」という調査側の困難である評価・解釈出典 [1] [2] [3]

本記録は、この事案の要点を3つに整理する（本記録の評価）〈重要〉。

第一に、悪用の成否が応答から分からない。 出典3 は「SIP が 202 Accepted を返すのは、メッセージが受理されたことだけを意味し、チャットインタフェースの実行が成功したことを意味しない。処理関数は end: ラベルで一律に 200／202 を返すため、チャットの配送に失敗してもここを通る」と記し、負の対照として foo+... を送った場合も 202 が返るがファイルは作られなかったと述べている（出典3。本記録が訳した）〈重要〉。防御側にとってこれは2つの意味を持つ（本記録の評価）—— ①攻撃者の側も、応答から成功を確認できない（当て逃げになる）、 ②調査側は、SIP の記録だけでは「試みられたが失敗した」と「成功した」を区別できない。 CISA がフォレンジックのトリアージ対象（forensicTriage: Yes）としたにもかかわらず、本脆弱性に固有の痕跡が示されていないことは、この困難と無関係ではない（本記録の評価）〈未確定2〉。

第二に、「悪用が観測されている」と勧告自身が書いていた。 勧告（10月28日）の時点で既に実際の悪用があり、CISA の KEV 収載（11月9日）は12日後、期限は収載の3日後（11月12日）である（出典1・2。算出は本記録）〈重要〉—— この日程は、勧告を見た時点で既に時間が無かったことを示す（本記録の評価）。一方で、修正は設定では代替できず更新が要る（出典3）—— 通話基盤の更新に必要な検証期間と、この日程は噛み合わない（本記録の評価）〈重要〉—— だからこそ enable-chat=false による時間稼ぎの価値が高い。

第三に、これは「機能の到達範囲」の問題であり、再発しやすい類型である。 api チャットインタフェースは正規に登録された機能であり、1.11.3 の修正もそれを削除せず明示的な有効化に変えただけである（出典1・3）〈重要〉。本記録は、同じ構図が他の製品にもあると考える（本記録の評価）—— 「外部から到達できる入力が、内部の管理 API の選択子になっている」箇所である。 自組織で確認すべきは、SIP に限らず、外部入力から内部 API の名前を選べる経路の有無である（本記録の判断）。

実際に悪用された組織・時期・攻撃者はいずれも公表されておらず、修正前の悪用を見つける公式な手順も無い未確定事項出典 [1] [2] [3]

勧告は「この経路の悪用が実際に観測されている」と述べるだけである（出典1）〈重要〉〈未確定1〉—— 誰が観測したのか、いつからか、どの組織が被害を受けたのか、攻撃者は誰かのいずれも記載されていない。 CISA の KEV も、ランサムウェアキャンペーンでの使用を「不明」としている（出典2）。本記録は、悪用の規模・標的の業種・地域を推定しない（本記録の明示）。

修正前の悪用を見つける公式な手順も示されていない〈未確定2〉〈重要〉—— CISA は forensicTriage: Yes としてトリアージを求めているが、本脆弱性に固有の痕跡（どのログの、どの記録を見るか）はKEV の記載からは読めない（出典2。本記録の確認）。勧告も、修正後は拒否された要求に 403 を返して記録に残すと述べる一方、修正前の悪用の見つけ方には触れていない（出典1）。

セキュリティ技術者への示唆
  • まず `enable-chat` を業務で使っていない profile で false にする。即日できて、経路を閉じる。
    **勧告の迂回策のうち、経路を閉じるのはこれだけである**（出典1）〈重要〉—— **「受信チャットを必要としない profile では `enable-chat=false` を設定する。 これはその profile で受信 MESSAGE のチャットを完全に無効にする」** （出典1。原文英語。本記録が訳した）。 **vanilla では internal（5060）と external（5080）の両方で 受信チャットが有効であり、`sofia.c:4665` は `PFLAG_ENABLE_CHAT` を無条件に設定する**（出典1・3）〈重要〉—— **明示的に切らない限り有効である。**
    取るべき行動 **①各 profile の設定で `enable-chat` の指定を確認する （指定が無ければ有効である）、 ②`fs_cli` で `sofia status` を実行して待ち受けている profile を列挙する、 ③業務で SIP MESSAGE を使っていない profile に `<param name="enable-chat" value="false"/>` を追加して反映する** （出典1・3。整理は本記録）〈重要〉—— **実行前に、WebRTC のチャット機能・SMS ゲートウェイ連携・ プレゼンス通知が当該 profile を使っていないかを確認する。**
  • `auth-calls=false` はメッセージ認証を切らない。似た名前の設定を混同しない。
    **`sofia.c:6118` 付近の論理では、`auth-messages` を明示していない場合に `PFLAG_AUTH_MESSAGES` が設定され、stock の internal／external では MESSAGE 認証が要求される**（出典3）〈重要〉。 **一方、`external.xml` の `auth-calls=false` は呼の認証にのみ影響し、 メッセージ認証を切らない**（出典3）。 **逆に、WebRTC・通知・チャットゲートウェイからメッセージを 直接投げさせるために `auth-messages=false` を設定していた環境では、 認証の関門が消える**（出典3）〈重要〉。
    取るべき行動 **全 profile の設定で `auth-messages` を grep し、 `false` が明示されている profile を洗い出す**（本記録の推奨）〈重要〉—— **該当する profile は、`enable-chat=false` の適用を最優先にする。** **併せて、directory にパスワードも a1-hash も持たない利用者が 残っていないかを確認する（勧告の迂回策の一つ）**（出典1）。
  • SIP の 202 応答で成否を判断しない。試みと成功を区別できない。
    **「SIP が `202 Accepted` を返すのは、メッセージが受理されたことだけを 意味し、チャットインタフェースの実行が成功したことを意味しない。 処理関数は `end:` ラベルで一律に 200／202 を返すため、 チャットの配送に失敗してもここを通る」**（出典3。本記録が訳した）〈重要〉—— **負の対照として `foo+...` を送った場合も 202 が返るが、 ファイルは作られなかったと記されている**（出典3）。 **したがって、SIP の記録だけでは「試みられたが失敗した」と 「成功した」を区別できない**（本記録の整理）〈重要〉。
    取るべき行動 **調査では SIP の応答コードではなく、実行側の痕跡を見る** （本記録の推奨）〈重要〉—— **①`switch_api_execute` 経由で実行された API の記録、 ②`system`・`module_load`・`originate` 等の API の実行記録、 ③OS 側の痕跡（新規プロセス・ファイル生成・外向き通信）。** **本記録はこれらが既定の記録に残るかを検証していない**〈自己未確認2〉—— **平常時に、`system` API を1回実行して どこに何が残るかを自環境で確かめておくこと。**
  • 守護プロセスを root で動かさない。閉じる措置ではないが、被害の上限は下がる。
    **出典3 の検証では、コンテナ内で root 権限で動いていたため `system touch /tmp/fs-pwned` が root 所有のファイルを作り、 `system bash -c 'id > /dev/tcp/...'` は `uid=0(root) gid=0(root) groups=0(root)` を返した**（出典3）〈重要〉。 **公式の推奨どおり権限を落としていれば到達点は `freeswitch` サービス利用者になる**（出典3）。 **ただし権限を落としても、設定・directory 利用者・ ゲートウェイ資格情報・CDR の読み取りと改変、呼の経路の変更、 module の読み込みは依然として可能である**（出典3）〈重要〉—— **「root でないから軽い」とは読めない**（本記録の明示）。
    取るべき行動 **①実行利用者を確認する（`ps` で守護プロセスの利用者を見る）、 ②root で動いている場合は専用利用者に切り替える、 ③設定ファイル・ゲートウェイ資格情報の読み取り権限を その利用者に必要な範囲へ絞る**（本記録の推奨）〈重要〉—— **コンテナで動かしている場合は、`-u root -g root` のような 起動引数が残っていないかを確認する**（出典3 の検証環境が該当）。
  • 外部入力から内部の管理 API の名前を選べる経路が、他にもないかを探す。
    **本件は、受信 MESSAGE の To 利用者部分が チャット protocol の選択子になり、その先に OS コマンドを実行する標準 API が繋がっていた**（出典1・3）〈重要〉—— **`api` インタフェースは隠された裏口ではなく、 正規に登録された機能であり、1.11.3 の修正も削除ではなく 明示的な有効化への変更である**（出典1・3）。 **本記録は、これが「機能の到達範囲を絞っていなかった」類型であり、 同じ構図が他の製品にもあると考える**（本記録の評価）〈重要〉。
    取るべき行動 **自組織の自作・改造部分で、外部から到達できる入力が 内部 API・コマンド・module の名前を選べる箇所を棚卸しする** （本記録の推奨）〈重要〉—— **探すのは「文字列から処理を引く」構造 （ディスパッチテーブル・プラグイン名での検索・ 動的なクラス／関数の解決）である。** **見つけたら、拒否一覧ではなく許可一覧にする。**
