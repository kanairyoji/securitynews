**どのデータに実際にアクセスされたかを 記録から特定できたのかは公表されていない** （本記録の確認）〈重要〉〈未確定5〉—— **「アクセスされた可能性があると確認された」という言い回しは、 到達可能性の確認であって、 アクセスの記録に基づく特定とは読めない**（本記録の読み）。 **認証を要求しない API では、 呼び出し元を識別する手段が無いため、 誰が何を取得したかの記録そのものが 残りにくい**（本記録の評価。一般的な性質）〈重要〉—— **認証の欠如は、侵入を容易にするだけでなく、 事後の範囲確定も難しくする。**

判断評価評価の根拠と留保
**Radware は、何が持ち出されたかを確定する前に、 内部アカウントの認証情報をすべて無効化して差し替えた** （出典1）〈重要〉—— **検知当日の措置である**（本記録の読み）。機能した**本記録の評価である**（本記録の判断）〈重要〉—— **評価を「機能した」とするのは、 措置の対象（自社の内部認証情報）が Radware の権限の内側にあり、 実行によって実際にリスクが消えているためである。** **留保を置く**（本記録の明示）—— **本記録が参照できるのは同社の根本原因分析報告の引用のみであり、 差し替えが全系統に及んだかどうかは確認できていない。**
**Radware は、2026年11月25日時点で本件について 公式の声明を出さず、SEC への侵害報告も行っていない** （出典1。本記録の確認）〈重要〉—— **本件が公になったのは、匿名の情報源が 同社の根本原因分析報告を報道機関に渡したためである**（出典1）。不十分**本記録の評価である**（本記録の判断）〈重要〉—— **評価を「不十分」とするのは、 流出したものが顧客側の資産への鍵であり、 是正の実行者が顧客だからである**（本記録の評価）。 **ベンダが無効化できない認証情報について、 ベンダにできる最も強い措置は 「気づいていない利用者にも届く形で知らせること」である。** **直接の契約窓口への通知だけでは、 同じ鍵を別の用途に流用していた運用や、 保存先を共有する別のチームには届かない。** **留保を置く**（本記録の明示）—— **本記録はサイトの取得に失敗しているため、 公表が存在しないと断定はしない**〈差異2〉。
**Radware は、露出しなかったものを5項目にわたって 明示的に列挙した**（出典1）〈重要〉—— **WAF のトラフィック検査、証明書、エンドユーザーのデータ、 顧客のアプリケーショントラフィック、 クラウド DDoS サービスとそのデータ。**機能した**本記録の評価である**（本記録の判断）〈重要〉—— **「何が出ていないか」を項目で示す公表は多くない。** **顧客が取るべき行動を絞れる形になっている点を評価する。** **ただし、対象顧客の件数が公表されていないため、 自社が「一部の顧客」に当たるかは 個別の通知を待つしかない**（本記録の明示）〈未確定1〉。
CISO・経営層への示唆
  • **SaaS ベンダに預けている認証情報を棚卸しする。 ベンダが破られたとき、無効化できるのは自分だけである。**
    **本件で流出したのは Radware のデータではなく、 顧客自身のクラウド保存先への鍵である**（出典1）〈重要〉—— **AWS S3 のアクセスキー、 Azure Blob Storage のキーまたは SAS トークン、 SFTP の認証情報。** **Radware が自前でできたのは自社の内部認証情報の差し替えまでで、 顧客の鍵は顧客しか更新できない**（本記録の整理）。 **同社は「強く」助言する形をとっているが**（出典1）、 **これはベンダができる最大限であって、リスクの解消ではない** （本記録の評価）。 **そしてすでに、顧客から 「見覚えのない IP アドレスがログ書き出し先のバケットへ アクセスを試みた」という AWS の警報の報告が届いている**（出典1）。
    取るべき行動 **自組織が外部のサービス事業者に渡している認証情報を 一覧にする—— 渡した相手、渡した鍵の種類、できること（読み／書き／削除）、 対象リソース、有効期限、最終更新日、更新の手順と所要時間。** **「更新の手順」が書けない項目は、 ベンダ侵害時に更新できないということなので、 先に手順を作る。** **棚卸しの入口は、 クラウド基盤のアクセスキーの一覧と 発行者・用途の記録を突き合わせることである。**
  • **ベンダ侵害の通知は、契約窓口に届いても運用担当には届かない。 受け取った通知を社内の誰に渡すかを事前に決めておく。**
    **本件の是正は、顧客側の作業である**（出典1）〈重要〉—— **ログ書き出しの認証情報の更新と、 クラウド保存先のアクセスログの確認。** **どちらも、Radware との契約を管理している部署ではなく、 クラウド基盤を運用している部署の作業である** （本記録の評価）。 **さらに、同じ鍵を他の用途に流用していた運用や、 保存先を共有する別のチームは、 ベンダからの通知を受け取る立場にない**（本記録の評価）〈重要〉。 **Radware は公式の声明を出していないため、 契約窓口を経由しない経路が存在しない**（出典1。本記録の確認）。
    取るべき行動 **ベンダからのセキュリティ通知の受け取り口を1つに定め、 受け取った通知を「どの鍵が関係するか」で 運用担当へ割り振る手順を作る。** **割り振りの材料は、上記の認証情報の一覧である—— 一覧が無いと、通知を読んでも誰に渡すかが決まらない。** **通知から運用担当への到達までの所要時間を測る訓練を 年1回行う（実際の通知で測れた場合はそれを記録する）。**
  • **「内部専用だから認証は不要」という設計上の例外を、 自組織の中で数える。1か所の境界の崩れで全面的に開く。**
    **本件の原因は Radware 自身が1文で書いている** （出典1。本記録の訳。原文英語）〈重要〉—— **「認証を要求せずに公開インターネットから到達可能だった 内部専用の Cloud WAF 管理 API」。** **到達可能になったこと自体は、 設定変更・移行作業・既定値の変更などでどの組織でも起きる** （本記録の評価）。 **認証を要求しない実装は、それが起きた瞬間に全面的に開く** （本記録の評価）〈重要〉—— **段階的な劣化が無い。** **さらに、呼び出し元を識別できないため、 事後に誰が何を取得したかの範囲確定も難しくなる** （本記録の評価）。
    取るべき行動 **自組織のシステム一覧から、 「内部からしか到達しない前提で認証を省いている」 インターフェースを抜き出す （管理 API、内部向けの管理画面、 ヘルスチェックや設定取得のエンドポイント、 データベースの管理用の口を含む）。** **各項目に「認証を入れる」「入れられない理由」のどちらかを書かせ、 後者には境界の崩れを検知する仕組みを割り当てる。** **項目数を経営報告の指標にし、ゼロに近づける—— 1件でも残っていれば、本件と同じ型の事案が起きうる。**
  • **自社が無効化できない認証情報を漏らしたときは、 直接通知だけでは足りない。公の声明が届く層がある。**
    **Radware は2026年11月25日時点で公式の声明を出しておらず、 SEC への侵害報告も行っていない**（出典1。本記録の確認）〈重要〉。 **本件が公になったのは、匿名の情報源が 同社の根本原因分析報告を報道機関に渡したためである**（出典1）。 **顧客への通知は行われたとみられるが**（本記録の読み）、 **本件で鍵が使われる場所は顧客のクラウドアカウントであり、 その運用は顧客の中の別のチームが担っていることがある** （本記録の評価）〈重要〉。 **公の声明は、ベンダが直接通知できない層に届く唯一の手段である** （本記録の評価）。 **また、内部文書の流出という形で事実が世に出た結果、 公表の枠組みと速度を自ら決める主導権が失われている** （本記録の評価）。
    取るべき行動 **自組織の事案公表の基準に 「自社が無効化できない認証情報・鍵が露出した場合」の行を立て、 その場合は直接通知に加えて公開の告知を行うと定める。** **告知に必ず載せる項目を決める—— 更新すべき認証情報の種類、更新の手順、 確認すべきログと期間の起点、 自組織が検知した悪用の試みの有無。** **併せて、内部文書が流出した場合に 公表へ切り替える判断の権限を誰が持つかを決めておく—— 本件では、事実が先に外へ出た。**
セキュリティ技術者への示唆
  • **ベンダに渡す鍵には、送信元 IP の制限と最小権限と有効期限を付ける。 ベンダが破られるかは制御できないが、鍵が何に使えるかは制御できる。**
    **本件で顧客から報告されたのは 「見覚えのない IP アドレスがログ書き出し先のバケットへ アクセスを試みた」という AWS の警報である**（出典1）〈重要〉。 **鍵に送信元の制限が付いていれば、 流出しても別の場所からは使えない**（本記録の評価）。 **流出した鍵の用途は「ログの書き出し」であり、 必要な権限は特定のバケットへの書き込みのみである** （出典1。本記録の整理）—— **読み出しや削除の権限が付いていれば、 それは用途を超えている。**
    取るべき行動 **ベンダへ渡すクラウドの認証情報を、 ①対象リソースを特定のバケット・パスに限定、 ②操作を用途に必要なものだけに限定（ログ書き出しなら書き込みのみ）、 ③送信元 IP アドレスの範囲を制限、 ④有効期限を設定、の4点で作り直す。** **③はベンダの送信元が変わるたびに更新が必要になるので、 ベンダに通知の約束を取り付けてから入れる。** **可能な保存先では、長期の鍵をやめて 顧客側が付与する一時的な権限委任（役割の引き受け）に替える—— ベンダ側に長期の鍵が存在しない構成が最も強い。**
  • **ベンダが書き込む先のアクセスログを有効にしておく。 既定で無効な設定があり、そのままでは「確認したが分からない」になる。**
    **Radware は顧客に「少なくとも11月19日以降の想定外のアクセスについて クラウド保存先のアカウントのアクセスログを確認する」よう 求めている**（出典1。本記録の訳。原文英語）〈重要〉。 **しかし、AWS S3 のアクセスログや Azure の診断ログは 既定で有効になっていない設定があり、 その場合は確認そのものができない** （本記録の評価。一般的な性質。Radware はこの前提に触れていない）。 **本件で悪用の試みを最初に捉えたのは Radware ではなく顧客側の警報である**（出典1）〈重要〉—— **ベンダの侵害の帰結は、ベンダには見えない場所で起きる。**
    取るべき行動 **外部のサービス事業者が書き込む保存先について、 アクセスログ（データイベントの記録）が有効かを1つずつ確認する。** **有効でないものを有効にし、 保存期間が調査に足りるか（最低90日）を確かめる。** **併せて、ベンダの正規の送信元 IP 以外からのアクセスを 警報にする検知を入れる—— 本件ではこの形の警報が最初の手がかりになった。** **費用を抑えるには、ベンダが書き込む先に限って有効にすればよい。**
  • **認証を要求しない API は、侵入を容易にするだけでなく 事後の範囲確定も不能にする。影響調査の観点から認証を入れる。**
    **Radware の言い回しは 「アクセスされた可能性があると確認された情報」である** （出典1。本記録の訳。原文英語）〈重要〉—— **「アクセスされたことを確認した」ではない。** **本記録の読みでは、これは到達可能だった範囲の確認であり、 実際に何が読まれたかの特定ではない**（本記録の読み）。 **認証を要求しない API では呼び出し元を識別する手段が無いため、 誰が何を取得したかの記録そのものが残りにくい** （本記録の評価。一般的な性質）。 **その結果、同社は範囲の確定を待たずに 内部認証情報を一括で差し替える判断を取ることになった** （本記録の推定）。
    取るべき行動 **自組織の API について、 「侵害されたとき、誰が何を取得したかをログから言えるか」を 1つずつ確認する。** **言えないものを一覧にし、 呼び出し元の識別（認証）とリクエスト単位の記録を入れる。** **認証を入れる判断を「侵入を防ぐため」だけで議論すると 「内部だから不要」で終わるので、 「事故のあとに範囲を言えるため」を理由に並べる—— こちらの方が経営の判断を得やすい。**
  • **外部から見た自組織の露出面を継続的に列挙する。 攻撃の検知ではなく、構成の点検として回す。**
    **本件の API は「認証を要求せずに公開インターネットから 到達可能だった」**（出典1。本記録の訳。原文英語）〈重要〉—— **外から見えていたということは、 外から見る仕組みがあれば自分でも見つけられた** （本記録の評価）。 **到達可能になった時期は公表されていないため、 点検の頻度がどの程度あれば間に合ったかは評価できない** 〈未確定2〉—— **本記録はこれを、本件の教訓ではなく一般の策として置く** （本記録の明示）。
