INC-2026-1304hex.pm が10年前の欠陥で侵害

Erlang／Elixir の唯一の公式パッケージ登録所 hex.pm が2026年11月23日、 **認証より前に走るリクエスト本文の復元処理**を突かれて侵害された—— 2016年2月に外された安全確認が10年近く残っていた （CVE-2026-129514・CVSS 4.0 で10.0）。 Web サーバ6台で OS コマンドを実行され、悪性リクエストは69件。 運営は最初のエラーから約15分でパッチ版に入れ替えたが、 **データベースの読み取りは記録されないため、利用者の電子メールアドレス・ パスワードのハッシュ・API キーのハッシュ・二要素認証の秘密が 読まれた可能性を否定できない**。 登録所の署名鍵は交換できておらず、運営は第三者ミラーの使用停止を求めている

初報: 2026年11月24日（hex.pm によるブログ記事「Security incident on hex.pm」の公表） 最終更新: 2026年11月25日（本記録の作成。一次公表と NVD の登録内容を直接取得して裏を取った時点）

2026年11月23日18時16分（UTC）、Erlang／Elixir のパッケージ登録所 hex.pm のエラー監視（Sentry）に、見慣れないエラーが記録された（出典1）。第三者が hex.pm の脆弱性を突いて、Web サーバ上でコマンドを実行していた（出典1。原文英語。本記録が訳した）〈重要〉。

入口は、リクエスト本文の復元処理である（出典1・2）〈重要〉—— hex.pm は Erlang の外部項形式で送られた本文を復元していたが、その復元が __struct__ キーを持つマップを通した。解析は routing と認証の前に走るため、どの経路への POST でも届く。偽の構造体を処理させるとエラーになり、そのエラー報告が構造体の種別に応じた関数（Inspect プロトコルの実装）を呼ぶ。攻撃者はこれを使って、Ecto の DynamicExpr と DBConnection の :log 指定を経由し、BEAM の実行利用者の権限で OS コマンドを実行した（出典2）。

安全確認が外されたのは2016年2月23日（出典1）〈重要〉—— 10年近く前の変更が、そのまま残っていた。

攻撃は短時間で止められた（出典1。本記録が整理）〈重要〉—— 悪性リクエストは18時16分から18時29分までの69件。最初の応答が18時23分55秒、ファイアウォール規則が18時27分、全サーバがパッチ版に入れ替わったのが18時30〜31分である。

しかし「何を読まれたか」は確定していない（出典1）〈重要〉—— データベースの読み取りは記録されない。 運営は、電子メールアドレス・パスワードのハッシュ・API キーのハッシュ・二要素認証の秘密・セッション・監査ログが読まれた可能性を否定できないとしている。

パッケージの改ざんは確認されていない（出典1）—— 事案中の23件のリリースはすべて監査ログと一致し、18時以降に書かれたパッケージファイル62件・登録所ファイル186件はすべてデータベースの検査値または内容と一致した。

残っている最大の問題は、登録所の署名鍵である（出典1）〈重要〉—— 交換できた認証情報は11月24日10時42分までにほぼ全てだが、署名鍵だけは残った（鍵の交換に対応した新しい署名の仕組みを構築中）。 運営は「第三者ミラーを信用せず、パッケージは repo.hex.pm からのみ取得すること」を求めている（出典1。原文英語。本記録が訳した）。

3. 解析は routing と認証の前にエンドポイントで走るため、どの経路への POST でもここに到達する。
4. Elixir は __struct__ の値でプロトコルの実装先を決める。エラー報告がパラメータを inspect するとき、どの Inspect／Enumerable 実装が走るかをクライアント側が選べた。
5. Ecto.Query.DynamicExpr と DBConnection の :log 指定を経由する連鎖で、OS コマンドの実行に届いた。

関数の名前が示すのは「無名関数を含む項を拒否する」ことであって、「安全な値だけを通す」ことではない（本記録の読み）〈重要〉—— 構造体は通った。

この安全確認が外されたのは2016年2月23日である（出典1）〈重要〉—— 10年9か月、そのまま残っていた（本記録の算定）。

攻撃が成立した場所は「正常系」ではなく「失敗時の処理」である（本記録の評価）〈重要〉—— エラーを人間が読める形にする処理（inspect）が、実行経路になった。

運営は同じ種類の欠陥を Elixir 生態系の他のライブラリにも見つけている（出典1）—— Ash のキーセット改頁（CVE-2026-124283・ash 3.38.0 で修正）と、db_connection のストリーム構造体からの :log 適用（CVE-2026-133555）。 報道はこれに加えて分頁ライブラリ Flop も挙げている（出典3）〈差異1〉。

読まれた範囲は確定していない——データベースの読み取りが記録されていないため被害規模・影響範囲出典 [1]

確認できたこと（出典1）〈重要〉——
- パッケージの改ざん・データベースの変更・継続的な足がかりの証跡は無い
- 事案中の23件のリリースは、すべて監査ログの記録と一致した
- 18時以降に書かれたパッケージファイル62件・登録所ファイル186件は、データベースの検査値または内容と一致した
- サーバ上にシェルは見つからず、攻撃元のアドレスから新しいクラウドの鍵やアカウントが作られた形跡も無い
- 通信量は平常の範囲。例外は1台の処理サーバが毎秒0.47メガバイトに達したことだけ（通常の最大は毎秒0.29メガバイト）

否定できないこと（出典1。原文英語。本記録が訳した）〈重要〉——
- 電子メールアドレス・パスワードのハッシュ・API キーのハッシュ・二要素認証の秘密・セッション・監査ログへのアクセス
- データベースの読み取り、環境変数の読み取り、シェルコマンドの実行（いずれも記録されない）
- 侵害されたサーバからの私的パッケージの読み取り（正規の通信と区別できない）
- 私的文書とクラウド保管の直接読み取り（記録されない）
- 元に戻された変更、後から上書きされた変更（データベースとの突合では現れない可能性がある）

人数・組織数は公表されていない（本記録の確認）〈未確定4〉—— 運営自身が「何人分が読まれたか」を把握できる記録を持っていない。

本記録はこの構造を重く見る（本記録の評価）〈重要〉—— 「記録が無いから被害は確認されていない」と書くことは簡単だが、hex.pm はそう書かず、記録が無いこと自体を列挙した。

署名鍵だけが交換できず、利用者には「第三者ミラーを使うな」という制約が降りた再発防止出典 [1]

交換した認証情報（出典1）—— 保管・CDN・電子メール・データベースの認証情報、セッションとアクセストークンに署名する鍵。 11月23日20時21分に大半、データベースのパスワードは翌24日、11月24日10時42分までに「攻撃者が読みえたあらゆる認証情報」が交換された。

交換できなかったもの（出典1）〈重要〉—— 登録所の署名鍵と、影響の小さいいくつかの秘密。

理由は、いまの署名の仕組みが鍵の交換に対応していないことである（出典1。本記録の読み）〈重要〉—— 運営は鍵の交換に対応した新しい署名の仕組みを構築中で、新しい Hex クライアントは「近日中（in the coming days）」に出るとしている（原文英語。本記録が訳した）。

それまでの指示（出典1。原文英語。本記録が訳した）—— 「第三者ミラーを信用せず、パッケージは repo.hex.pm からのみ取得すること。」

利用者に求められている行動（出典1）〈重要〉——
1. hex.pm のパスワードを変更する
2. hex.pm/dashboard/security で二要素認証を再設定し、新しい回復コードを保管する
3. 新しい Hex クライアントが出たら mix local.hex --force で更新する（rebar3・Gleam を使っているなら、それらも更新する）
4. Hex を騙る電子メールに注意し、リンク先が hex.pm であることを確かめる。不審なものは security@hex.pm へ転送する

API キーについては、運営は交換不要としている（出典1）—— 128ビットの乱数を HMAC-SHA256 でハッシュして保管しているためである。 パスワードは bcrypt で保管されているが、変更が求められている。

今後の硬化策（出典1）—— plug_crypto の復元関数を「認証済みの入力にのみ安全」と文書化し、構造体を拒否する選択肢を追加する。plug は本文のパラメータとして構造体を拒否する。ecto は Inspect で binding を列挙する前に一覧かどうかを確かめる。db_connection はストリーム構造体からの :log 適用をやめる。

速さは検知の設計ではなく「例外が見えていたこと」から来ている評価・解釈出典 [1]

本記録が本件から最も学ぶべきと考えるのは、検知の経路である（本記録の評価）〈重要〉。

攻撃を最初に知らせたのは、侵入検知の仕組みではなくエラー監視（Sentry）だった（出典1）—— 偽の構造体を処理するとエラーになるため、攻撃の副作用がそのまま例外として可視化された。 最初のリクエスト（18時14分21秒）から検知（18時16分00秒）まで2分弱である（本記録の算定）。

これは幸運ではなく、構造から来ている（本記録の評価）〈重要〉—— 型の厳しい言語で、想定外の値が来たら落ちる作りになっていたからこそ、攻撃が静かに通らなかった。 「黙って通る」実装であれば、69件のリクエストは記録に残らなかった（本記録の評価）。

一方で、同じ構造が調査の限界も作った（本記録の評価）〈重要〉—— エラーは見えたが、実行されたコマンドとデータベースの読み取りは記録されていない。 見えたのは「異常が起きていること」であって「何をされたか」ではない。

ここから本記録が引く線は2つある（本記録の判断）——
1. 例外・エラーの急増は、障害の信号であると同時に攻撃の信号である。監視の宛先を運用チームだけにしない。
2. 「異常が起きたことが分かる記録」と「何をされたかが分かる記録」は別物である。前者だけ持っていると、事故のあとで最も広い範囲を「否定できない」として扱うことになる。

  • 署名鍵は「交換できる設計か」を先に確かめる。 交換手順を持たない鍵は、事故のときに交換できない。
