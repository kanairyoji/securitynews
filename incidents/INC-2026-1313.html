INC-2026-1313Todoist が本番環境を侵害される

タスク管理サービス Todoist が2026年11月22日から23日にかけて侵害された。 攻撃者は盗んだ認証情報でバージョン管理システムに入り、自動化ワークフローを 改変し、従業員の業務アカウントを経由して本番のクラウド基盤へ到達した。 利用者の約6%のメールアドレスと古い SHA1 方式のパスワードハッシュが持ち出され、 約0.003%では API トークンと Slack 連携トークンが、 約0.001%ではタスクやコメントに保存されていた認証情報が探索された

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）権限管理の不備公表されていない／不明
初報: 2026年11月24日（Doist が「Security incident in November 2026」を公表した日） 最終更新: 2026年11月25日（公表文が追記され、TechCrunch が報じた）

2026年11月24日、タスク管理サービス Todoist を提供する Doist は、本番環境が侵害され利用者情報の一部が持ち出されたことを公表した（出典1）。公表文は11月25日に追記されている。

経路は段を踏んでいる（出典1・2）。攻撃者は盗まれた認証情報で同社のバージョン管理システムとソースコードにアクセスし（11月22日から23日）、そこにある自動化ワークフローを改変した。続いて従業員の業務アカウントを乗っ取り、それを使って本番のクラウド基盤へ到達した。11月23日、利用者情報の一部が取得された。ソースコードは改変されていない。

影響の範囲は、利用者数に対する割合で公表されている（出典1）。
- 約6%——メールアドレス、古い SHA1 方式のパスワードハッシュ、アカウント作成日。同社は、この範囲についてログインセッションの不正な作成は確認されなかったとしている
- 約0.003%——Todoist の API トークンと Slack 連携のトークン。一部では /sync API を通じてプロジェクト・タスク・コメントのデータにアクセスされた
- 約0.001%——タスクやコメントの中にある認証情報らしき内容。攻撃者は手作業で検索し、その後は自動のスキャナーを使った
- 約0.001%——Todoist for Outlook で連携していたメールアカウント。件名、送信者、メール本文の冒頭（最大255文字）、添付ファイル名が対象。メール本文の全体は要求されていない

古い SHA1 方式のハッシュが残っていたのは、同社がその方式の使用をやめてから10年以上経っているが、それ以降パスワードを変えていない初期の利用者のレコードが移行されずに残っていたためである（出典1）。

同社は、攻撃者が作成したクラウドアカウントの削除、悪用された認証情報の無効化、侵入経路の遮断、内部認証情報の再発行、開発者の自動化権限の縮小を行い、11月24日05時06分（UTC）に Todoist for Outlook アドオンを無効化した（出典1）。パスワードの初期化も実施した。

利用者に求めている行動のうち、本記録が最も重いと見るのはこれである—— タスクやコメントに保存した認証情報は、該当サービス側で失効・再発行する。内容を削除しただけでは、すでにコピーされた秘密情報は無効にならない（出典1）。

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は盗まれた認証情報でバージョン管理システムとソースコードへ到達し、 そこにある自動化ワークフローを改変した（11月22日から23日）。 続いて従業員の業務アカウントを乗っ取り、本番のクラウド基盤へ入った。 11月23日、約6%の利用者のメールアドレス・古いパスワードハッシュ・ アカウント作成日を持ち出し、約0.003%では API トークンと Slack 連携トークンを 取得、約0.001%ではタスクとコメントの内容を手作業と自動スキャナーで 検索して他サービスの認証情報を探した。 約0.001%では Todoist for Outlook 経由でメールの断片を取得した。 ソースコードは改変されていない。

侵入はソースコードから始まり、ソースコードは変えられなかった概観

2026年11月24日、タスク管理サービス Todoist を提供する Doist は、本番環境が侵害され利用者情報の一部が持ち出されたことを公表した（出典1）。

経路の順序が本件の特徴である（出典1・2）。攻撃者は盗まれた認証情報で、まず同社のバージョン管理システムとソースコードへアクセスした（11月22日から23日）。そこで改変したのはソースコードではなく、自動化ワークフローである。続いて従業員の業務アカウントを乗っ取り、従業員のアクセス制御を変更したうえで、そのアカウントを使って本番のクラウド基盤へ到達した。11月23日、利用者情報の一部が取得された。

同社は、攻撃者がソースコードを一切変更していないと明記している。これは利用者にとって重要な情報である——配布物に悪意のあるコードが混ぜられた供給網汚染ではない。

しかし「コードが変わっていない」ことは「何も変わっていない」ではない。変えられたのは自動化ワークフローであり、それが本番環境への通路になった。同社が対応として開発者の自動化権限を縮小し、クラウド環境における遠隔コマンド実行の仕組みを改めたこと（出典1・2）は、ここが通路であったことの裏返しである。

影響は4つの区分に分けて、割合で公表された被害規模・影響範囲

公表は影響範囲を利用者数に対する割合で示している（出典1）。実人数も総利用者数も公表されていないが、区分ごとに「何が持ち出され、何をすべきか」が書かれている。

約6%。メールアドレス、古い SHA1 方式のパスワードハッシュ、アカウント作成日。この区分が最も大きい。古い方式のハッシュが残っていたのは、同社がその方式の使用をやめてから10年以上経つが、それ以降パスワードを変更していない初期の利用者のレコードが移行されていなかったためである。同社は、この範囲についてログインセッションの不正な作成は確認されなかったとしている。

約0.003%。Todoist の API トークンと Slack 連携のトークン。一部では、取得されたトークンを使って /sync API を通じてプロジェクト・タスク・コメントのデータにアクセスされた。

約0.001%。タスクやコメントの中にある認証情報らしき内容。攻撃者は手作業で検索し、その後は自動のスキャナーを使った。

約0.001%。Todoist for Outlook で連携していたメールアカウント。件名、送信者、メール本文の冒頭（最大255文字）、添付ファイル名。同社はメール本文の全体は要求されていないとしている。

この4区分は、性質が2つに分かれる。最初の2区分は同社が管理していたデータである。あとの2区分は、利用者が自分の判断でサービスに置いた、または連携させた情報である。したがって失効・再発行の実行主体も、利用者側になる。

攻撃者が探したのは、利用者がタスクに書き残した他サービスの鍵だった原因・手口

本件で最も読むべき一節は、攻撃者の行動である。

攻撃者は、約0.001%の利用者のタスクとコメントの内容を検索して、他サービスの認証情報——API キー、アクセストークン——を探した（出典1・2）。最初は手作業で、その後は自動のスキャナーを用いている。

これは標的が Todoist のデータそのものではなかったことを示す。タスク管理サービスは、作業のメモ置き場として使われる。「このキーで検証」「復旧用のフレーズはこれ」「一時的にここに貼る」——そうして置かれたものが、そのまま残る。攻撃者はそれを知っていた。

同社が利用者に求めた行動のうち、本記録が最も重いと見るのはここである（出典1）——タスクやコメントに保存した認証情報は、該当サービス側で失効・再発行する。内容を削除しただけでは、すでにコピーされた秘密情報は無効にならない。

この一文は、利用者が取りがちな誤った対処を先に塞いでいる。侵害を知ってコメントを消しても、攻撃者の手元にある文字列は消えない。消すべきは文字列ではなく、その文字列が開けるものである。

併せて、共有リンクで誰でもアクセスできる状態になっているプロジェクトは制限または差し替えるよう案内されている（出典1）。

対策は「権限を減らす」方向に寄っている再発防止

同社が実施した対応は、侵入経路を塞ぐものと、権限そのものを減らすものに分かれる（出典1・2）。

塞ぐ側——攻撃者が作成したクラウドアカウントの削除、悪用された認証情報の無効化、侵入経路の遮断、露出した内部認証情報の再発行、Todoist for Outlook アドオンの無効化（11月24日05時06分 UTC）、パスワードの初期化。

減らす側——開発者の自動化に与えていた権限の縮小、クラウド環境における遠隔コマンド実行の仕組みの変更、アクセストークンの有効期限の短縮、コードレビューにおける秘密情報の検知の自動化。

後者が本件の構造に対応している。攻撃者はバージョン管理システムから自動化ワークフローを経て本番へ到達した。この通路を細くすることが、同じ経路の再現を防ぐ方向である。

一方で、アドオンの無効化の時刻が分単位（05時06分 UTC）で公表されている点は、運用上の配慮として評価できる（本記録の評価）。利用者は自分の環境で連携が切れた時刻と突き合わせられる。

実人数と、最初に認証情報が盗まれた経路は公表されていない未確定事項

11月25日時点で確定していないことを明示しておく。

影響を受けた利用者の実人数は公表されていない。割合（約6%・約0.003%・約0.001%）だけが示されており、分母となる総利用者数も公表されていないため、人数は割り出せない。国別・プラン別の内訳も無い。

最初に認証情報が盗まれた経路は確定していない。同社は従業員の端末が侵害された可能性を有力な仮説として挙げたが、確認はされていないと明記している（出典1）。ここを断定しなかったことは、公表の姿勢として記録に値する。

タスク・コメントの探索で実際に有効な認証情報が見つかったかどうか、取得されたトークンが連携先（Slack・Microsoft 365）で悪用されたかどうかも公表されていない。攻撃者の帰属、検知の日時と契機、監督機関への報告の有無も示されていない。

SaaS の侵害は、自組織の秘密情報の棚卸しをその日に要求する評価・解釈

本記録の評価である。

本件を「タスク管理サービスが侵害された」とまとめると、日本の読者にとっての論点が落ちる。落ちるのは、攻撃者が探したものである。

攻撃者はタスクとコメントを検索して、他サービスの API キーとアクセストークンを探した。つまり標的は、Todoist に入っていた「他のシステムへの入口」である。Todoist を業務で使っている組織にとって、本件は自組織のクラウド・CI/CD・決済・監視の鍵が第三者に探索された可能性がある事案になる。

そして、その鍵をそこに置いたのは組織自身である。同社がどれだけ対策しても、この区分の被害は防げない。防げるのは利用者側だけである。

ここから出てくる問いは2つある。1つは「自社の秘密情報が、いまどの SaaS のテキストに残っているか」。チャット、タスク管理、ドキュメント、チケット——どれも検索できる形で残る。攻撃者が自動スキャナーで探すのであれば、防御側も同じものを探せる。

もう1つは「SaaS が侵害されたと知ったとき、自社は何時間で鍵を失効させられるか」である。本件で同社は侵入から2日で公表した。利用者側がそこから動けなければ、2日の速さは活きない。

なお、同社の公表そのものは質が高い（本記録の評価）。影響を4区分に分けて行動を書き、ハッシュ方式の残存という自社に不利な事実を書き、Outlook 経由の取得範囲を文字数で示し、攻撃者が手作業から自動スキャナーへ切り替えたことまで書き、初期の侵害経路については仮説を仮説として示して断定しなかった。「削除しても無効にならない」という一文は、利用者の誤った対処を先に塞いでいる。

影響を限定できたパスワードハッシュの方式を全レコードで統一し、 古い方式のレコードを残さない （次回ログイン時の再ハッシュ、または強制リセット）。　本記録の評価。本件で持ち出されたのは、 10年以上前にやめた方式のハッシュが残っていたレコードである。 移行が完了していれば、この区分は存在しなかった。
内部探索公表されていない
利用者コンテンツに対する横断検索が検知できたかは公表されていない。 本件では手作業から自動スキャナーへの切り替えまで把握されており、 事後の調査では見えている。

侵入を防げた秘密情報を平文で置けない作業手順にする （タスク管理・チャットへの貼り付けを技術的に検知・遮断し、 秘密情報の受け渡しは専用の保管庫経由に限る）。　本記録の評価。本件で探索対象になったのは、 利用者が自分の判断で置いた情報である。 置かせない仕組みが唯一の根本対策になる。

CISO・経営層への示唆
  • SaaS のテキスト領域に自社の秘密情報が残っていないかを、 攻撃者と同じ方法で定期に探す。
    本件で攻撃者は、タスクとコメントを手作業で検索し、 その後は自動スキャナーで API キーやアクセストークンを探した。 探された側の組織は、そこに置いたことを忘れている。
    取るべき行動 チャット・タスク管理・ドキュメント・チケットの各 SaaS について、 秘密情報らしき文字列を走査する仕組みを導入し、 四半期ごとに検出件数を報告させる。 検出されたものは失効・再発行まで追跡する。
  • 「SaaS 侵害の通知を受けてから鍵を失効させるまでの時間」を 指標として持つ。
    本件で同社は侵入から2日で公表し、利用者に失効・再発行を求めた。 利用者側が動けなければ、提供元の速さは被害抑止にならない。
    取るべき行動 利用中の SaaS ごとに「自社が預けている秘密情報」と 「失効・再発行の手順と担当」を一覧にし、 侵害通知を受けた場合の目標時間（例: 4時間以内）を定めて 年1回の演習で測る。
  • 古い認証方式のレコードが自社サービスに残っていないかを、 移行の完了率として管理する。
    本件で持ち出されたのは、同社が10年以上前にやめた SHA1 方式のハッシュが残っていたレコードである。 方式を変えたことと、全レコードが移行されたことは別である。
    取るべき行動 自社サービスのパスワードハッシュ、暗号方式、鍵長について 「現行方式のレコード比率」を監視項目にし、 残存分の移行計画（次回ログイン時の再ハッシュ、 期限を定めた強制リセット）を期限つきで持つ。
  • 公表の構造を「持ち出された項目」ではなく 「誰が何をすべきか」で組む。
    本件の公表は影響を4区分に分け、区分ごとに利用者が取るべき行動を書いた。 「削除しただけでは無効にならない」という誤解も先に塞いでいる。 項目の羅列だけでは、読者は自分が何をすべきか判断できない。
    取るべき行動 自社の公表テンプレートを、影響区分ごとの行動指示の形に組み替える。 「メールが届いていなければ対応は不要」のような 対象外の人向けの一文も定型に入れる。
  • 確定していない侵害経路を、仮説として示したうえで断定しない。
    本件で同社は、従業員の端末の侵害を有力な仮説として挙げながら、 確認されていないと明記した。 断定すると、後の訂正が信頼の毀損になる。
    取るべき行動 公表の社内規程に「確定事項」「有力な仮説」「不明」の3段を 書き分ける規則を入れ、仮説には確認されていない旨を併記させる。
セキュリティ技術者への示唆
  • CI/CD のワークフロー定義の変更を、アプリケーションコードと 同じかそれ以上の厳格さで管理する。
    本件で攻撃者が改変したのはソースコードではなく、 バージョン管理システムにある自動化ワークフローである。 コードレビューだけを見ていると、この変更は視界に入らない。
    取るべき行動 パイプラインの設定ファイルを保護対象のパスに登録し、 変更にレビューと承認を必須にする。 変更の発生そのものを別系統（チャット・SIEM）へ通報する。
  • 自動化（CI/CD）が本番環境に対して持つ権限を棚卸しし、 遠隔コマンド実行を伴う経路を無くす。
    本件で攻撃者はワークフローの改変を経て本番のクラウド基盤へ到達した。 同社は対応として開発者の自動化権限を縮小し、 クラウド環境の遠隔コマンド実行の仕組みを改めている。
    取るべき行動 パイプラインに付与しているクラウドのロールを列挙し、 必要な操作（デプロイ対象への書き込み）だけに絞る。 任意コマンドを実行できる権限が残っていれば削る。 権限の変更履歴を保持する。
  • 権限付与・ロール変更・アクセス制御の編集を、 発生のたびに通報する。
    本件で攻撃者は従業員のアクセス制御を変更している。 この操作は平常時にほとんど起きないため、 通報しても埋もれない。
    取るべき行動 IdP・クラウド・バージョン管理システムの権限変更イベントを 1か所に集約し、変更のたびにチャットへ流す。 変更者と承認者が同一の場合は別途強調する。
  • API トークンの有効期限を短くし、 1トークンあたりの呼び出し量に上限と異常検知を置く。
    本件では取得されたトークンで `/sync` API 経由の データアクセスが行われた。正規のクライアントと同じ経路を通るため、 量と速度でしか異常を見分けられない。 同社も対応としてトークンの有効期限を短縮している。
    取るべき行動 発行済みトークンの有効期限を棚卸しし、 無期限のものを期限つきへ移行する。 トークン単位の呼び出し量のベースラインを取り、 逸脱でアラートと自動失効を行う。
  • 秘密情報を SaaS のテキストに貼れない作業手順を技術で担保する。
    本件の探索対象は、利用者が自分の判断でタスクやコメントに 書き込んだ認証情報である。運用の注意喚起だけでは残り続ける。
    取るべき行動 秘密情報の受け渡しを専用の保管庫（シークレットマネージャ）に限り、 タスク管理・チャットへの貼り付けを検知して警告・遮断する仕組みを入れる。 既存のテキストに対する走査も同時に回す。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
運用・監視□ 従業員がタスク管理・チャット・ドキュメントの SaaS に、 API キー・アクセストークン・接続文字列を貼り付ける運用が 技術的に可能なままになっている。

システム構成□ CI/CD のパイプラインが本番環境に対して、 任意のコマンドを実行できる権限を持っている。
システム構成□ 従業員の業務アカウントから本番環境へ直通でき、 時限の権限昇格や踏み台を経由する構成になっていない。
データの保持□ 自社サービスの利用者パスワードについて、 古いハッシュ方式のレコードが残っている可能性がある。
委託・第三者部品□ 業務で使う SaaS について、 侵害通知を受けた場合に自社が失効・再発行すべき対象の一覧がない。
