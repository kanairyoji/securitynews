INC-2026-13191Password 従業員GitHub侵害で顧客情報

パスワード管理サービス 1Password（AgileBits）が、 **従業員の業務用 GitHub アカウントを奪われ、 そこから自社バックエンドのサービスに悪意あるコードを注入されて 顧客のアカウント管理情報を持ち出された**ことを公表した （2026年11月25日）。 **本記録は同社の一次公表を取得して確認した**（本記録の確認）—— **同社は11月19日に「従業員の業務用 GitHub アカウントへ攻撃者が アクセスした兆候」を検知して調査を始め、 攻撃者は非公開リポジトリのソースコードにアクセスし、 バックエンドのサービスへ悪意あるコードを送り込んで 顧客のアカウント管理情報をダウンロードさせた**（出典1）。 **持ち出されたのは氏名・メールアドレス・アカウントおよびユーザーの ID・ アカウント作成日時と最終サインイン日時・公開鍵・ SRP（Secure Remote Password）のパラメータ・ 招待／プロビジョニング／アカウント復旧メールのリンクに含まれるトークン・ その他の秘密ではない内部メタデータである**（出典1）。 **攻撃者は加えて非公開リポジトリのソースコードを複製し、 インフラの秘密情報を持つ CI/CD 環境にもアクセスした**（出典1）〈重要〉。 **一方、保管庫（Vault）の中身・保管庫を保護する鍵・アカウント復旧鍵・ アプリとブラウザ拡張は影響を受けておらず、 同社はアカウントパスワードと Secret Key を保持していない**（出典1）。 **影響を受けた顧客の数は公表されていない**〈未確定1〉—— **公表文は「一部の利用者（a subset of users）」とだけ書き、 招待・復旧の手続き中だった「少数の利用者」には個別に通知したとする**（出典1）。 **侵入経路（GitHub アカウントがどのように奪われたか）と攻撃者の身元も 公表されていない**〈未確定2〉。

2026年11月25日、1Password を提供する AgileBits が、自社バックエンドへの侵害を公表した（出典1）。パスワード管理サービスの事案であるため、まず「保管庫は無事か」が問われる。同社の答えは「攻撃者は保管庫にも、保管庫を保護する鍵にも、一度も到達していない（at no point）」である（出典1）。同社はアカウントパスワードと Secret Key をそもそも保持していない。

では何が起きたのか。 11月19日、同社は従業員の業務用 GitHub アカウントへ攻撃者がアクセスした兆候を検知して調査を始めた。攻撃者はそのアカウントで非公開リポジトリのソースコードにアクセスし、バックエンドのサービスに悪意あるコードを送り込んで、顧客のアカウント管理情報をダウンロードさせた（出典1）。加えて非公開リポジトリのソースコードを複製し、インフラの秘密情報を持つ CI/CD 環境にもアクセスしている。

持ち出されたのは、暗号化された秘密ではなく「アカウントの台帳」である ——氏名、ログインに使うメールアドレス、アカウントとユーザーの ID、アカウント作成日時と最終サインイン日時、公開鍵、SRP のパラメータ、招待・プロビジョニング・アカウント復旧メールのリンクに含まれるトークン、その他の秘密ではない内部メタデータ（出典1）。

この事案の読みどころは2つある（本記録の評価）。第一に、「設計で守られていた部分」と「設計の外にあった部分」が、きれいに分かれた。保管庫はゼロ知識の設計に守られて無傷だったが、アカウントの台帳はサーバ側に平文で必要な情報であり、設計では守れない。第二に、復旧用トークンという「鍵ではないが鍵に近いもの」が流出した。 同社はトークン単独ではアカウントに到達できないと説明し（SSO か、登録メールに届く認証コードが要る）、そのうえで認証コードを6桁の数字から10文字の英数字へ強化した（出典1）。総当たりへの耐性を上げる措置であり、トークンが出た前提での手当てである。

公表されていないことも明確である。 影響を受けた顧客の数、GitHubアカウントが奪われた手口、攻撃者の身元、侵入から検知までの時間——いずれも示されていない〈未確定1・2・4〉。検知（11月19日）から公表（11月25日）までは6日である（本記録の算出）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は 1Password の従業員の業務用 GitHub アカウントを奪い、 非公開リポジトリのソースコードにアクセスしたうえで、 バックエンドのサービスへ悪意あるコードを送り込んだ。 そのコードが顧客のアカウント管理情報をダウンロードした。 攻撃者はさらにソースコードを複製し、CI/CD 環境にもアクセスした。 保管庫とそれを保護する鍵には到達していない。 GitHub アカウントが奪われた手口は公表されていない。

  1. 1. 初期侵入確認済[1]
    攻撃者が、1Password の従業員の業務用 GitHub アカウントを奪った。 1Password は2026年11月19日にその兆候を検知した。
    根拠: 一次公表「we began investigating indications that an attacker had accessed an employee's corporate GitHub account」 （訳: 攻撃者が従業員の業務用 GitHub アカウントにアクセスした兆候を 調査し始めた。原文英語。出典1）。
  2. 2. 内部探索確認済[1] [2]
    攻撃者が、奪ったアカウントの権限で非公開リポジトリのソースコードに アクセスした。
    根拠: 一次公表「used the account to access source code」 （訳: そのアカウントを使ってソースコードにアクセスした。 原文英語。出典1）。 BleepingComputer も「access private source code repositories」 （訳: 非公開のソースコードリポジトリへのアクセス。原文英語）と書く （出典2）。
  3. 3. 実行確認済[1] [3]
    攻撃者が、バックエンドのサービスへ悪意あるコードを送り込んだ （push した）。1Password はこれを「malicious code」と表現している。
    根拠: 一次公表「pushed malicious code to backend services」 （訳: バックエンドのサービスへ悪意あるコードを送り込んだ。 原文英語。出典1）。 DataBreaches.net は「Malicious code sent through one employee's corporate GitHub account made 1Password's own backend services download customer records」（訳: 1人の従業員の業務用 GitHub アカウント経由で送られた悪意あるコードが、1Password 自身の バックエンドサービスに顧客レコードをダウンロードさせた。 原文英語）と要約する（出典3）。
  4. 4. 収集確認済[1]
    送り込まれたコードが、顧客のアカウント管理情報をダウンロードした。 対象は氏名・メールアドレス・アカウントおよびユーザーの ID・ アカウント作成日時と最終サインイン日時・公開鍵・SRP パラメータ・ 招待／プロビジョニング／復旧トークン・その他の内部メタデータ。
    根拠: 一次公表「downloaded administrative customer data」 （訳: 管理上の顧客データをダウンロードした。原文英語。出典1）と、 同公表に列挙されたデータ項目（出典1）。
  5. 5. 認証情報アクセス確認済[1]
    攻撃者が、非公開リポジトリのソースコードを複製し、 インフラの秘密情報を持つ CI/CD 環境にアクセスした。
    根拠: 一次公表「copied source code from private repositories and gained access to the CI/CD system, which holds infrastructure secrets」 （訳: 非公開リポジトリからソースコードを複製し、 インフラの秘密情報を保持する CI/CD システムへのアクセスを得た。 原文英語。出典1）。

1つのアカウントが、コードから本番バックエンドまで通ってしまった原因・手口出典 [1] [3]

経路は短い（出典1）。

  1. 従業員の業務用 GitHub アカウントが奪われる（手口は非公表〈未確定2〉）
  2. そのアカウントで非公開リポジトリのソースコードにアクセス
  3. バックエンドのサービスへ悪意あるコードを送り込む
  4. 送り込まれたコードが、顧客のアカウント管理情報をダウンロード
  5. 並行してソースコードを複製し、CI/CD 環境にもアクセス

本件の核心は3番である（本記録の評価）〈重要〉。従業員1人のコード基盤アカウントが奪われただけで、本番のバックエンドが攻撃者の書いたコードを実行する状態になっている。DataBreaches.net の要約はこの構造を端的に書いている——「1人の従業員の業務用 GitHub アカウント経由で送られた悪意あるコードが、1Password 自身のバックエンドサービスに顧客レコードをダウンロードさせた」（出典3。訳は本記録。原文英語）。

攻撃者は顧客データベースに侵入していない。 顧客データを読む権限を既に持っている正規のサービスに、読ませたのである。だから「外部からの不審なアクセス」としては現れにくい。

では、コードが本番へ出るまでに何があったのか。 レビューは。別人の承認は。署名の検証は。公表文はこの点に一切触れていない〈未確定3〉。同社は是正として「GitHub・CI/CD 環境・従業員端末の管理を強化し、同様の攻撃を検知する仕組みを追加した」と書くが（出典1）、何が足りなかったのかは書かない。

本記録はここを原因として断定しない（本記録の方針）。断定できる材料が無いためである。ただし、読者が自社に当てはめるときの問いははっきりしている——「開発者アカウント1つを奪われたとき、自社の本番は攻撃者のコードを実行するか」。

人数は公表されていない。公表されたのは「項目」である被害規模・影響範囲出典 [1] [2] [4] [5]

影響を受けた顧客の数は、どこにも書かれていない（出典1）〈未確定1〉。公表文の表現は「一部の利用者（a subset of users）」である。TechCrunch は、同社が顧客への通知の有無も、影響を受けた顧客数も述べていないと明記した（出典4）。BleepingComputer は「影響を受けたのは少数の利用者のみで、個別に通知された」と書くが（出典2）、これは招待・復旧の手続き中だった利用者への個別通知を指しており、アカウント管理情報を持ち出された全体の規模ではない（本記録の読み）。

数が無いことは、この事案では致命的ではない（本記録の評価）。理由は、流出した項目の性質がはっきりしているからである。氏名とログイン用メールアドレスの組は、人数が1万でも100万でも、同じ種類の危険を生む——「1Password を使っている実在の人物」の名簿である。

危険の形は2つに分かれる（本記録の整理）。

①フィッシングの材料。 攻撃者は、1Password 利用者であることを知っている相手に、1Password を装って連絡できる。本件を口実にした「アカウントを保護してください」という誘導が最も自然な形になる。同社自身が、招待・アカウント復旧を装った連絡への警戒を呼びかけている（出典1）。

②トークンと認証コードの組み合わせ。 流出したトークンは、招待・プロビジョニング・復旧メールのリンクに埋め込まれていたものである。手続きの完了には、トークンに加えて SSO か、登録済みメールへ届く認証コードが要る（出典1）。つまりトークン単独では足りない。だからこそ同社は、認証コードを6桁の数字（100万通り）から10文字の英数字へ強化した（出典1・5）。

この措置は、同社が何を恐れたかを教えている（本記録の評価）〈重要〉——トークンを持つ攻撃者が認証コードを総当たりする筋である。100万通りは、総当たりの標的として小さい。

「顧客は何もしなくてよい」と言い切るために、自社側で1点だけ直した組織の対応出典 [1] [5]

同社は顧客にパスワードの変更を求めなかった（出典1）。パスワード管理サービスの侵害で、これは一見すると強い判断に見える。しかし根拠は設計にある——アカウントパスワードと Secret Key は同社が保持しておらず、保管庫を保護する鍵は流出していない。変更しても減るリスクが無い。

代わりに、自社側で危険のある一点を直した。 招待・アカウント復旧の認証コードを6桁の数字から10文字の英数字へ延長した（出典1・5）。

大文字小文字を区別するかは公表されていないため、本記録は総数を断定しない（本記録の明示）——区別するなら約 8.39×10^17 通りになる。いずれにしても桁が違う。

この順序が参考になる（本記録の評価）〈重要〉。①流出したものを特定し、②それが単独で使えるかを設計から判断し、③使えるようになる条件（認証コードの弱さ）だけを直し、④利用者には不要な作業を求めない。「とりあえず全員パスワード変更」という対応は、作業量が膨大なうえ、変更を促すメールがそのままフィッシングの温床になる。

他の対応（出典1）——侵害された GitHub アカウントの無効化、盗まれたトークンの失効、攻撃者が設定したアクセス権の削除、影響を受けたサービスの安全な版への復旧、露出した可能性のある社内認証情報の一括更新。「攻撃者が設定したアクセス権を削除した」という一文は、攻撃者が再侵入の足場を残していたことを示す（本記録の読み）。

外部の専門家も入れた。 ただし名称・検証の範囲・完了時期は公表されていない〈未確定6〉。

ゼロ知識設計は「顧客名簿が出る」ことを防げない評価・解釈出典 [1] [2] [4]

本件を「パスワード管理サービスは安全だった」という話で終わらせると、学べるものがほとんど無くなる（本記録の評価）。

ゼロ知識の設計が守るのは、サーバが知らなくても成立する情報だけである。保管庫の中身、保管庫の鍵、アカウント復旧鍵——これらは守られた。一方、サービスを運営するために平文で必要な情報は、設計の対象外にある。誰がどのアカウントの持ち主か、どのメールでログインするか、いつ最後に入ったか。本件で出たのはこちらである。

この区別は、暗号を売り物にしているすべての事業者に当てはまる（本記録の評価）〈重要〉。エンドツーエンド暗号のメッセンジャー、暗号化ストレージ、秘密情報管理サービス——いずれも「中身は読めない」と説明する。それは正しい。しかし「誰が使っているか」は読める。そして顧客名簿は、次の攻撃（標的を絞ったフィッシング）の出発点になる。

自社の公表を準備する立場なら、ここを先に言語化しておくべきである（本記録の評価）。「当社の設計では中身は読めません」の次に、「ただし、以下の情報はサーバ側に必要であり、設計では守れません」を書けるか。1Password の公表文は、影響を受けたものと受けなかったものを並べて示すという形で、実質これを果たしている（出典1）。この形は模倣に値する（本記録の評価）。

  • メールに埋め込むトークンは、単独で効かない前提で設計し、 組み合わせる第2要素の強度を見直す。
    本件で流出したのは招待・プロビジョニング・復旧メールの トークンである（出典1）。同社はトークン単独では使えないと説明し、 そのうえで認証コードを6桁の数字（100万通り）から10文字の 英数字へ強化した（出典1・5）。
    取るべき行動 自社の招待・パスワード復旧・メール確認のリンクについて、 トークンの有効期限・使い捨て性・第2要素の有無を一覧化する。 数字6桁のワンタイムコードを使っている箇所は、 試行回数の制限とロックアウト、コード長・文字種を見直す。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ 自社のソースコード基盤（GitHub / GitLab 等）から、 本番環境へコードが自動で、または少人数の操作で到達する経路がある。
認証・認可□ 開発者・運用者のコード基盤アカウントが、SSO を経由しない直接ログインや、 SMS・TOTP のみの多要素認証で保護されている。
データの保持□ 「中身は暗号化しているから安全」と説明している一方で、 利用者の氏名・メールアドレス・最終ログイン日時などの台帳を 平文で保持している。
運用・監視□ 顧客データへの一括読み出しを、件数・頻度の基準で監視していない。
委託・第三者部品□ CI/CD 環境に、有効期限の無い静的な認証情報（クラウドの鍵・ 外部 API のトークン）を保存している。
体制・契約□ 自社が利用する SaaS ごとに「どの情報が流出したら自社は何をするか」を 事前に決めていない。
