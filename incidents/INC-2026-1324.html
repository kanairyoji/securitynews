INC-2026-1324React RSC に未認証RCE（CVSS9.5）

React Server Components に未認証のリモートコード実行（CVE-2026-126187・CVSS 4.0 で 9.5）——修正版は10月14日に npm へ出ており、脆弱性として公表されたのは11月10日だった

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月10日22時44分（UTC。GitHub Security Advisory GHSA-xqc2-xf4c-x3h3 が公開された時刻。日本時間では11月11日7時44分） 最終更新: 2026年11月26日

React の維持チームは2026年11月10日、React Server Components（RSC）の データ転送処理に未認証のリモートコード実行が成立する脆弱性があるとして 勧告 GHSA-xqc2-xf4c-x3h3 を公開した。CVE-2026-126187 が採番され、 CVSS 4.0 の基本値は 9.5（Critical）である。 影響するのは npm の react-server-dom-webpack / react-server-dom-parcel / react-server-dom-turbopack の3パッケージで、 19.0.0〜19.0.8・19.1.0〜19.1.9・19.2.0〜19.2.8・19.3.0 が対象、 修正版は 19.0.9・19.1.10・19.2.9・19.3.1 である（出典1）。 勧告は成立条件を「応答が複数の typed array と攻撃者が制御できる値を 運ぶ、きわめてまれな場合にのみ影響する」と限定している（出典1）。 本記録が npm のレジストリで確認したところ、 修正版4種はいずれも2026年10月14日に公開されており（出典2）、 勧告の公開までに27日の間がある。 同じ欠陥に対応する Next.js の勧告（GHSA-673q-mjm6-r5xr・16.4.1 で修正・CVE 無し）は 10月22日に公開された（出典3）。 2026年11月25日版の CISA KEV カタログに CVE-2026-126187 は収載されていない（出典4）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

未認証の攻撃者が、RSC に対応したサーバへ細工したペイロードを送る。 RSC のデータ転送の復元処理（信頼できないデータの逆シリアル化・CWE-502）の不備により、 応答が複数の typed array と攻撃者が制御できる値を運ぶ構成であった場合に、 サーバ上で任意のコードが実行されうる。 実際の悪用は公表されておらず、以下は勧告と CVSS ベクトルから読める範囲である。

  1. 1. 初期侵入確認済
    攻撃者が、RSC に対応したフレームワークを使うアプリケーションへ 細工したペイロードを送る。認証も利用者の操作も要らない。
    根拠: 出典1「Crafted payloads targeting frameworks supporting React Server Components can lead to remote code execution」（原文英語。本記録が訳した: 「React Server Components に対応したフレームワークを狙って細工された ペイロードは、リモートコード実行につながりうる」）。 認証・操作の不要は CVSS ベクトルの PR:N／UI:N による。
  2. 2. 実行確認済
    RSC のデータ転送の復元処理で、信頼できないデータが逆シリアル化され、 サーバ上で任意のコードが実行されうる。 成立するのは、応答が複数の typed array と攻撃者が制御できる値を運ぶ場合に限られる。
    根拠: 出典1。弱点分類は CWE-502（Deserialization of Untrusted Data）。 成立条件は勧告の「This only affects extremely rare cases where responses transport multiple typed arrays and an attacker-controlled value」 （原文英語。本記録が訳した: 「これは、応答が複数の typed array と 攻撃者が制御できる値を運ぶ、きわめてまれな場合にのみ影響する」）。

    トレードオフ: 先に修正版を置くことで、攻撃者へ手がかりを与える前に 更新の受け皿を用意できる。一方で利用者から見ると、 その27日間は「更新すべき理由」が分からない—— 定期更新の順番待ちに置かれ、変更履歴にも危険性が書かれていない。 Next.js 側が先に公表したことで、同じ欠陥の公表時期が18日ずれた。

修正版は10月14日に出ていた。危険だと公表されたのは27日後である概観

React の維持チームは2026年11月10日22時44分（UTC）、勧告 GHSA-xqc2-xf4c-x3h3 を公開した。CVE-2026-126187 が結び付き、CVSS 4.0 の基本値は 9.5（Critical）、弱点分類は CWE-502（信頼できないデータの逆シリアル化）である（出典1）。

ところが修正版そのものは、それより前に出ている。本記録が npm のレジストリで確認したところ、react-server-dom-webpack の 19.3.1・19.2.9・19.0.9・19.1.10 はいずれも2026年10月14日16時49分〜16時55分（UTC）に公開されていた（出典2）。Next.js 16.4.1 も同日17時43分である（出典3）。つまり修正は10月14日に利用者の手元へ届いており、それが未認証のリモートコード実行の修正であることが公表されたのは27日後だった。

さらに、同じ欠陥に対する Vercel 側の勧告（GHSA-673q-mjm6-r5xr）は10月22日に公開されている（出典3）。React 側の公表（11月10日）とは18日ずれている。Next.js を使っている組織は10月22日に理由を知ることができ、react-server-dom-* を他の経路で使っている組織は11月10日まで知る手段が無かった。

台湾の iThome がこれを報じたのは11月26日である（出典5）。修正版の公開から数えて43日が経っている。

原因は RSC のデータ転送における信頼できないデータの逆シリアル化である原因・手口

勧告の記述は短い。原文は「Crafted payloads targeting frameworks supporting React Server Components can lead to remote code execution. This only affects extremely rare cases where responses transport multiple typed arrays and an attacker-controlled value.」である（出典1。原文英語。本記録が訳した:「React Server Components に対応したフレームワークを狙って細工されたペイロードは、リモートコード実行につながりうる。これは、応答が複数の typed array と攻撃者が制御できる値を運ぶ、きわめてまれな場合にのみ影響する」）。

GitHub Advisory Database が付けた弱点分類は CWE-502、すなわち信頼できないデータの逆シリアル化である（出典1）。RSC はサーバで組み立てた結果を独自の形式で直列化してクライアントへ送り、クライアント側・サーバ側の双方で復元する。その復元処理に不備があった。

Next.js 側の勧告はもう一段具体的で、「App Router と Cache Component を使うアプリケーションの脆弱性がリモートコード実行につながりうる。アプリケーションには、複数の typed array を返す use cache 関数があることが要る」と述べている（出典3。原文英語。本記録が訳した）。

注意すべきは、CVSS ベクトルに AT:P（Attack Requirements: Present）が付いていることである（出典1）。攻撃者の制御外にある前提条件——該当する形の応答を返す実装があること——が要る。「まれな場合にのみ影響する」という限定と 9.5 という値は矛盾しない。条件が揃った系では、認証なしで最大の被害が出る、という意味である（本記録の整理）。

ブラウザだけで動く React アプリは対象外で、対象はサーバ側の RSC 構成に限られる被害規模・影響範囲

影響するのは npm の3パッケージである——react-server-dom-webpack、react-server-dom-parcel、react-server-dom-turbopack。対象バージョンは 19.0.0〜19.0.8、19.1.0〜19.1.9、19.2.0〜19.2.8、19.3.0 で、修正版は 19.0.9・19.1.10・19.2.9・19.3.1 である（出典1）。Next.js は 16.0.0〜16.4.0 が対象で、16.4.1 で修正された（出典3）。

勧告は影響しない条件も明記している。「アプリの React コードがサーバを使わない場合、影響を受けない」「RSC に対応したフレームワーク・バンドラ・バンドラプラグインを使わない場合、影響を受けない」（出典1。原文英語。本記録が訳した）。ブラウザだけで動く React アプリケーションは対象外である。

実務上やっかいなのは、これらのパッケージが直接の依存として宣言されていないことが多い点である（本記録の整理）。Next.js を入れれば一緒に入る。package.json に react-server-dom-* の名前が無いことは、使っていないことを意味しない。確認する場所はロックファイルと実際にデプロイされた node_modules である。

影響を受けた組織・サービスの名前も件数も公表されていない〈未確定4〉。

回避策は示されておらず、対処は更新だけである対策・注意喚起

React 側の勧告は「直ちに更新することを推奨する」と述べるのみで、設定による緩和策を示していない（出典1）。Next.js 側はより踏み込んで、「そのような use cache 関数を持つアプリケーションに既知の回避策は無い。似た関数が無いアプリケーションでも直ちに更新すべきである」と述べている（出典3。原文英語。本記録が訳した）。

これは、自己判定で先送りするなという意味である（本記録の読み）。「応答が複数の typed array を運ぶか」を機械的に判定する手段は公表されていない〈未確定2〉。該当するかを調べる時間より、更新するほうが速い。

2026年11月25日版の CISA KEV カタログ（1,805件）に CVE-2026-126187 は収載されていない（出典4。本記録がカタログ本体を取得して確認）。ただしこれは「悪用されていない」ことの証明ではなく、「米国当局が悪用を確認した記録が無い」ということである。参考までに、2025年12月の React Server Components の別の重大脆弱性CVE-2025-55182 は、公表から2日後の2025年12月5日に KEV へ収載された（出典4）。

この事案の実務上の論点は、脆弱性そのものより「黙って直っていた27日」である評価・解釈

以下は本記録の評価である。

成立条件が「きわめてまれ」と明記されている以上、この CVE に当たる組織の数は多くないと考えられる。一方で、修正版が10月14日に出てから勧告が11月10日に出るまでの27日間は、条件に当たるかどうかに関係なく、すべての利用者に影響した。

この期間、利用者から見えていたのは「19.2.9 というパッチ版が出た」ことだけである。更新の優先順位を決める材料——未認証で、認証も操作も要らず、CVSS 9.5 のリモートコード実行である——は、まだ存在しなかった。依存の更新を自動化し、パッチ版を無条件に取り込む運用をしていた組織は10月14日に守られた。更新に稟議や回帰試験の順番待ちを課していた組織は、その27日を露出したまま過ごしたことになる。

さらに、同じ欠陥の公表が React（11月10日）と Next.js（10月22日）で18日ずれた。依存の下流にいるほど情報が遅れるのではなく、この件ではフレームワーク側が先に語った。「上流の勧告だけを見る」運用では、18日遅れる。

再現性のある教訓は一つである。重大な脆弱性は、公表の前に修正として先に届くことがある。だから「勧告が出たら更新する」運用は、原理的に遅れる。

悪用の有無も、成立条件の判定方法も公表されていない未確定事項

公表されていないことを並べておく。

第一に、悪用の観測である。両勧告とも悪用に触れていない（出典1・3）。KEV にも無い（出典4）。「悪用されていない」と確認されたのではなく、語る資料が無い〈未確定1〉。

第二に、成立条件の判定方法である。「応答が複数の typed array と攻撃者が制御できる値を運ぶ」構成に自分のアプリが該当するかを調べる手順は示されていない〈未確定2〉。修正は PR 37842〜37846 として公開されているが、本記録はその差分を読んでいない〈差異3〉。

第三に、修正版の公開と勧告の公開が27日離れた理由である〈未確定3〉。

第四に、影響を受けたアプリケーションの数である〈未確定4〉。react-server-dom-* は推移的に入るため、母数そのものが誰にも分かっていない可能性がある（本記録の読み）。

緩和策
手順: **react-server-dom-webpack / parcel / turbopack を 19.0.9・19.1.10・19.2.9・19.3.1 のいずれかへ更新する**（出典1）—— **Next.js を使っている場合は 16.4.1 以降へ更新する**（出典3）。　副作用: **これらのパッケージは Next.js などを通じて推移的に入るため、 アプリの package.json に名前が出ていないことがある**（本記録の整理）〈重要〉—— **「うちは react-server-dom-* を入れていない」で終わらせると、 ロックファイルの中に残る。** **マイナー更新であっても、サーバ側レンダリングの基盤を差し替える作業であり、 本番反映には回帰確認の時間が要る。**
手順: **回避策は示されていない**（出典3）。 **Next.js の勧告は「そのような `use cache` 関数が無いアプリケーションでも 即時に更新すべき」と述べている**（出典3。本記録が訳した）。　副作用: **「自分のコードは条件に当たらない」という自己判定で更新を先送りしない、 ということである**（本記録の読み）—— **判定の手段が公表されていない以上（〈未確定2〉）、 条件該当の確認に時間をかけるより更新するほうが速い。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
修正版を先に npm へ公開し（10月14日）、 脆弱性の存在を勧告として公表したのは27日後（11月10日）だった。 Next.js 側の勧告はその中間（10月22日）に出た。部分的に機能本記録の評価。修正の提供は速く、内容も明確だった。 しかし「修正版は出ているが脆弱性は伏せられている」期間は、 利用者側の優先順位付けを誤らせる。 依存の更新を自動化していない組織ほど、この27日はそのまま露出の延長になる。 評価を確定できないのは、悪用の有無が公表されていないためである（〈未確定1〉）。
CISO・経営層への示唆
  • 「勧告が出たら更新する」運用は、原理的に遅れると認めたうえで設計する。
    本件では修正版が2026年10月14日に npm へ出ており、 それが未認証 RCE の修正だと公表されたのは11月10日だった（出典1・2）。 27日間、更新の根拠は存在しなかった。 公表を起点にする運用は、この27日を必ず失う。
    取るべき行動 依存ライブラリのパッチ版（最後の桁だけが上がる更新）について、 「脆弱性の公表を待たずに取り込む」方針を明文化し、 取り込みの自動化と回帰試験の自動化に投資する。 どの層まで自動で上げるか（patch のみか minor までか）を決裁事項として残す。
  • 上流（ライブラリ）だけでなく、直接使っているフレームワークの勧告も購読する。
    同じ欠陥について、Next.js の勧告は10月22日、React の勧告は11月10日に 公開された（出典1・3）。18日の差がある。 本件では下流のフレームワーク側が先に語った。
    取るべき行動 自組織が本番で使うフレームワーク・バンドラの GitHub Security Advisory を、 ライブラリ本体と別に購読対象へ登録する。 購読先の一覧を資産管理台帳の一部として維持し、年1回棚卸しする。
  • 「CVSS が高いが成立条件はまれ」という形の脆弱性に、判断の型を用意しておく。
    本件は CVSS 4.0 で 9.5 だが、勧告自身が「きわめてまれな場合にのみ影響する」と 限定している（出典1）。 該当するかの判定方法は公表されておらず〈未確定2〉、 調査に時間をかけるほど更新が遅れる。
    取るべき行動 「成立条件の該当調査に N 時間以上かかる場合は、調査せず更新する」という 打ち切り規則を、脆弱性対応の手順書に数字で書く。 判断者と、更新できない場合の代替（隔離・停止）の決裁者を決めておく。
  • KEV 収載の有無を、対応要否の判断基準にしない。
    CVE-2026-126187 は2026年11月25日版の KEV に無い（出典4）。 一方、2025年12月の React の別の重大脆弱性 CVE-2025-55182 は公表2日後に 収載された（出典4）。収載は悪用が観測されて初めて起きる—— 収載を待つことは、悪用が始まるまで待つことと同じである。
    取るべき行動 社内規程で「KEV 収載時は◯日以内」を定めているなら、 それとは別に「未認証・ネットワーク経由・CVSS 9以上」の基準を併記し、 収載前でも動く条件を作る。
セキュリティ技術者への示唆
  • package.json ではなくロックファイルと実デプロイ物で、react-server-dom-* の版を確認する。
    これらのパッケージは Next.js などを通じて推移的に入る（本記録の整理）。 直接の依存として書いていない組織が多く、 「うちは入れていない」という自己申告が外れる。
    取るべき行動 `npm ls react-server-dom-webpack react-server-dom-parcel react-server-dom-turbopack` を 本番と同じロックファイルで実行し、19.0.9／19.1.10／19.2.9／19.3.1 未満が 残っていないかを確かめる。 コンテナイメージを使っているなら、イメージの中でも同じ確認をする。
  • サーバ側レンダリングのプロセスを、最小権限と最小到達範囲で動かす。
    本件の CVSS ベクトルは後続システムへの影響を高（SC:H／SI:H）としている（出典1）。 RCE が成立したとき、そのプロセスから何に手が届くかで被害の広さが決まる。
    取るべき行動 レンダリング用プロセスに付与しているクラウドの資格情報・ 内部ネットワークへの到達範囲・ファイル書き込み権限を棚卸しし、 不要なものを外す。読み取り専用ファイルシステムで動くかを確かめる。
  • 逆シリアル化の成立そのものは外から見えない。実行後の挙動で捕まえる設計にする。
    本件の実行段階はアプリケーションの正規処理の中で起きるため、 WAF やリクエスト監視では正規の画面遷移と区別できない（本記録の評価）。
    取るべき行動 レンダリングプロセスからの想定外の子プロセス生成・ 外向き通信・資格情報ファイルの読み取りを検知対象に加える。 平常時のベースラインを先に取っておく（取っていないと警報が使えない）。
  • パッチ版の取り込みを、変更履歴の内容に依存せず回せるようにする。
    本件では10月14日のリリースに「未認証 RCE を修正した」という説明は無かった （説明は11月10日の勧告で初めて出た。出典1・2）。 変更履歴を読んで判断する運用は、黙って直された修正を取り落とす。
    取るべき行動 依存更新の自動 PR（Dependabot / Renovate 等）で patch 更新を自動マージする 条件を整え、その前提となる自動試験の範囲を広げる。 「説明が書かれていないから後回し」という判断を運用から消す。
