INC-2026-1331GeoServer 2脆弱性に悪用試行

GeoServer の2脆弱性（CVE-2026-120705・CVE-2026-129243）に悪用試行——5件を連鎖させると未認証でのリモートコード実行に至る構成で、修正版は数週間前に出ていた

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備

GeoServer プロジェクトは2026年11月23日、9件のセキュリティ勧告を公開した（出典1・2・4）。 このうちCVE-2026-120705（未認証の WFS GetFeatureById による XML インジェクション。 CVSS 3.1 で 8.6）と CVE-2026-129243（x/WFS のような接頭辞付きサービス名による サービスセキュリティ規則の回避。CVSS 4.0 で 8.8）について、 セキュリティ企業 watchTowr が実環境での悪用試行を観測したと報じられている（出典5）。 観測されたのは「保存クエリを作成して呼び出すことで、サーバが脆弱かを エラーで確かめる探索（error-based exploit probes）」であり、 リモートコード実行の成功例は報告されていない（出典5）。 カナダのサイバーセキュリティセンターは11月25日、勧告 AV26-1207 を出し、 公開情報として両 CVE が実際に悪用されていると伝えた（出典3）。 この2件は Rapid7 の研究者 Jonah Burgess（CryptoCat）が発見した5件の連鎖の一部で、 連鎖させると管理者権限の取得と GeoServer プロセス権限での任意コマンド実行に至る（出典5）。 研究者は2026年8月初めに開発者へ報告し、技術詳細と PoC を同週に公開した（出典5）。 修正版 2.27.7・2.28.6・3.0.2 は勧告公開の数週間前に出ている（出典1・2・5）。 Eye Security は独立に一部を発見し、CVE-2026-120705・CVE-2026-129245・CVE-2026-120704 の 3件の組み合わせで Linux と Windows の双方で未認証 RCE を実証したとしている（出典5）。 同社はインターネットから到達できる GeoServer を3,000台以上確認したという（出典5）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

未認証の攻撃者が、接頭辞付きサービス名（`x/WFS`）でサービスセキュリティの検査を回避し （CVE-2026-129243）、管理者限定の CreateStoredQuery で保存クエリを作成する。 その保存クエリを入口に、エスケープされない `${ID}` へ XML を注入して（CVE-2026-120705） ローカルファイルの読み出しと SSRF を成立させる。 これらを含む5件を連鎖させると、管理者権限の取得と GeoServer プロセス権限での 任意コマンド実行に至る（出典2・5）。 **実際に観測されたのは探索段階までであり、リモートコード実行の成功例は 報告されていない**（出典5）〈重要〉。

  1. 1. 偵察確認済
    攻撃者が、保存クエリを作成して呼び出すリクエストを送り、 **エラー応答の内容からサーバが脆弱かを判定する**。
    根拠: 出典5「Attackers sent error-based exploit probes to validate that the server is vulnerable by creating and invoking stored queries」 （原文英語。本記録が訳した: 「攻撃者は、保存クエリを作成して呼び出すことで サーバが脆弱であることを確認するための、エラーを利用した探索リクエストを送った」）。 watchTowr の観測であり、脆弱なサーバの特定が目的と見られるとされている。
  2. 2. 権限昇格確認済
    接頭辞付きサービス名（`x/WFS`）を使い、サービスセキュリティの検査を回避して、 **管理者限定の CreateStoredQuery・DropStoredQuery を未認証で実行する**（CVE-2026-129243）。
    根拠: 出典2。ディスパッチャが解決した名前と、サービスセキュリティが検査する名前が 食い違っていたことによる（CWE-863）。 勧告は本件を GHSA-hgm3-wq4h-8vvq（リモートコマンド実行の連鎖）の第2段と明記している。
  3. 3. 実行確認済
    作成した保存クエリ（または組み込みの GetFeatureById）を呼び出し、 エスケープされない `${ID}` へ XInclude を含む XML を注入する（CVE-2026-120705）。 **ローカルファイルの読み出しと、サーバから攻撃者指定 URL への接続（SSRF）が成立する。** 取得内容は「Illegal property name」エラー応答で受け取る。
    根拠: 出典1。認証も独自の保存クエリも CreateStoredQuery の権限も不要と明記されている。 取得内容が応答に現れるのはレイヤが匿名利用者に公開されている場合に限られる。
  4. 4. 影響（暗号化・破壊・改ざん）推定
    5件（および Eye Security の3件の組み合わせ）を連鎖させると、 **管理者権限の取得と、GeoServer プロセス権限での任意コマンド実行**に至る。 Eye Security は Linux・Windows 双方で未認証 RCE を実証したとしている。
    根拠: 出典5。Burgess は管理者権限の取得と任意コマンド実行を実証し、技術詳細と PoC を公開した。 出典2 は CVE-2026-129243 が GHSA-hgm3-wq4h-8vvq（リモートコマンド実行の連鎖）の 第2段であると明記している。 **ただし実環境での RCE 成功は報告されていない**（出典5）。

悪用試行が観測されたのは2件。だがこの2件は5件の連鎖の一部である概観

GeoServer プロジェクトは2026年11月23日、9件のセキュリティ勧告を公開した（出典4）。このうち2件——CVE-2026-120705（未認証の WFS GetFeatureById による XML インジェクション・CVSS 3.1 で 8.6）と CVE-2026-129243（接頭辞付きサービス名によるサービスセキュリティ規則の回避・CVSS 4.0 で 8.8）——について、セキュリティ企業 watchTowr が実環境での悪用試行を観測したと報じられている（出典5）。カナダ・サイバーセキュリティセンターは11月25日、勧告 AV26-1207 で両 CVE が実際に悪用されていると伝えた（出典3）。

観測された内容は限定的である。watchTowr によれば、攻撃者は保存クエリを作成して呼び出すことでサーバが脆弱かをエラー応答から確かめる探索を送っており、リモートコード実行に成功した事例は報告されていない（出典5）。目的は脆弱なサーバの特定と見られている。

しかし本記録が重く見るのは、この2件が単体ではないことである。Rapid7 の研究者 Jonah Burgess（CryptoCat）は5件の脆弱性を発見して2026年8月初めに報告しており、連鎖させると管理者権限の取得と GeoServer プロセス権限での任意コマンド実行に至ることを実証した（出典5）。勧告自身がその構造を書いている——CVE-2026-129243 はリモートコマンド実行の連鎖（GHSA-hgm3-wq4h-8vvq。Critical）の第2段であり、そこで作成できる保存クエリが CVE-2026-120705 の入口になる（出典2）。探索が当たったサーバには、その先がある。

文字列置換で XML を組み立て、解決前の名前で認可を検査していた原因・手口

2件の原因は、どちらも単純である。

CVE-2026-120705 は、WFS 2.0 の組み込み保存クエリ GetFeatureById が、呼び出し元の ID 値をエスケープせずに XML テンプレートへ埋め込んでいたことによる。勧告は根本原因を「${ID} を単純な文字列置換で差し替えていたため、引用符と山かっこで rid 属性から抜け出して新しい FES 要素を追加できた」と説明している（出典1）。さらに、その結果を GeoServer のエンティティリゾルバを通さずに解析していたため、XInclude が効いた。1回の未認証リクエストで、GeoServer プロセスが読めるローカルファイルの読み出しと、攻撃者が指定した URL へのサーバ側からの接続（SSRF）が成立する。取得した内容は「Illegal property name」というエラー応答に現れて攻撃者へ戻る（出典1）。

CVE-2026-129243 は認可の検査位置の問題である。ディスパッチャは x/WFS のような接頭辞付きの名前を WFS サービスへ解決するが、サービスセキュリティは解決前の名前で検査していた。一致する規則が無いため、本来は役割の確認を要する操作が無検査で通った（出典2）。既定で管理者に限定されている CreateStoredQuery・DropStoredQuery が未認証で実行でき、WFS Transaction など他の操作を制限している構成でもその保護が失われる（出典2）。レイヤ・データのセキュリティ規則は残る。

どちらも「入力をそのまま信じる」「検査する対象を間違える」という古典的な形である（本記録の評価）。新しいのは、この2つが噛み合うと認可の回避が注入の入口を用意するという点である。

更新だけでは足りない。作られた保存クエリが残る対策・注意喚起

対処は GeoServer 2.27.7・2.28.6・3.0.2 への更新である（出典1・2・3・5）。GeoTools も 33.7・34.6・35.2 へ上げる（出典1）。修正適用後に手作業の追加手順は不要とされている（出典2）。

回避策も示されている。CVE-2026-120705 についてはサービスセキュリティでWFS を匿名利用者に対して制限するか、不要なら WFS を無効化する（出典1）。CVE-2026-129243 については、前段のプロキシで service パラメータにスラッシュを含むリクエストを遮断する（クエリ文字列と XML の属性の両方。出典2）。

ただし回避策には限界がある。勧告自身が書いているとおり、匿名利用者への公開を制限してもファイルは読まれる——内容が応答に返らないだけである（出典1）。SSRF も成立する。回避策は時間を稼ぐ手段であり、更新の代替ではない（本記録の評価）。

そして本記録が最も重視するのは、勧告 GHSA-rv5g-g2r9-58rj が回避策と並べて書いている別の手順である——データディレクトリのwfs/query および workspaces/*/wfs/query を確認し、自分で作成していない保存クエリが無いか点検すること（出典2）。watchTowr が観測した探索は「保存クエリを作成して呼び出す」ものである（出典5）。つまり到達されたサーバには、設定として保存クエリが残りうる。更新だけを済ませてこの点検を飛ばせば、作られたものは残ったままである（本記録の評価）。

修正版は先に出ていた。PoC 公開の直後に探索が来ている評価・解釈

時間の並びを見ると、本件の運用上の論点が出てくる。

報告は2026年8月初め（Burgess）と9月下旬（Eye Security）。修正版 2.27.7・2.28.6・3.0.2 は勧告公開の数週間前に公開された。勧告9件が出たのが11月23日。研究者が技術詳細と PoC を公開したのが同じ週。watchTowr が悪用試行を観測したのは、その報道（11月25日）の時点までである（出典1・2・5）。

つまり、修正は先に手元へ届いていたが、それが何の修正かは数週間あとまで分からなかった（本記録の評価）。そして内容と PoC が公になった直後に、探索が始まっている。「勧告を見てから更新する」運用では、この空白期間を露出したまま過ごし、公開と同時に攻撃と競走することになる。

もうひとつは9件という数である。本件で報じられたのは2件だが、運用側が11月23日に受け取ったのは9件の勧告であり、そのうち remember-me 鍵による管理者セッション偽造（GHSA-hgm3-wq4h-8vvq）はCritical で、連鎖の本体である（出典2・4）。報道が取り上げた2件だけを見て優先度を決めると、連鎖の本体を見落とす（本記録の評価）。更新は9件まとめてのものであり、選んで適用することはできない——これは幸いな制約である（本記録の読み）。

なお GeoServer の脆弱性が狙われるのは初めてではない。2026年8月にはゼロデイとしての悪用があり、2025年には米国政府機関が GeoServer の脆弱性を突かれて侵害されたことが明らかになっている（出典5）。本記録はこれらを本件と同一視しないが、この製品が攻撃者にとって優先度の高い標的であることの背景として記録する。

**本記録の評価**。回避そのものは正規の HTTP リクエストの形で届くため、 外形だけでは正規利用と区別しにくい。 **ただし `service` の値にスラッシュが入るのは通常の利用で起きないため、 値の分布を見れば区別できる**（本記録の読み）—— 見ていなければ気づけない、という意味で「機会はあったが検知できなかった」に分類する。
侵入を防げた更新（2.27.7／2.28.6／3.0.2）を適用する。ディスパッチャが解決後のサービス ID を リクエストへ設定するよう修正され、実際に動くサービスに対して検査が行われる（出典2）。　勧告が示す修正である（出典2）。手作業の追加手順は不要とされている。
検知できたデータディレクトリの `wfs/query`・`workspaces/*/wfs/query` を定期的に点検し、 構成管理の記録と突き合わせる（出典2）。　本記録の評価。**保存クエリは設定ファイルとして残るため、 作られてしまえば痕跡になる**（本記録の読み）。 構成管理（意図した保存クエリの一覧）が無いと、何が余計かを判定できない。
実行機会はあったが検知できず
**本記録の評価**。**「Illegal property name」エラーを返す応答が異常に増えることは、 アプリケーションログから見える**（本記録の読み）〈重要〉—— **エラー応答を通じて情報を返す構造のため、エラー率そのものが指標になる。** 平常時のエラー分布を取っていなければ判定できない。
侵入を防げた更新（GeoServer 2.27.7／2.28.6／3.0.2、GeoTools 33.7／34.6／35.2）を適用する。 保存クエリの解析が GeoServer のエンティティリゾルバを経由し、 GeoTools の PreventLocalEntityResolver がリダイレクトも検査するようになる（出典1）。　勧告が示す修正である（出典1）。
影響を限定できたGeoServer プロセスが読めるファイルの範囲を最小化する （資格情報ファイル・鍵・他サービスの設定を同一プロセスから到達できない配置にする）。　本記録の評価。**読み出せるのは「GeoServer プロセスが読めるファイル」である**（出典1）—— **プロセスの到達範囲がそのまま被害の範囲になる**（本記録の読み）。
影響を限定できたGeoServer から外向きの HTTP/HTTPS 接続を、必要な宛先だけに限定する（出力方向の制御）。　本記録の評価。**SSRF はレイヤの公開設定にかかわらず成立する**（出典1 の記述から。 内容が返らない構成でも接続自体は起きる）—— **クラウドのメタデータ端点や内部 API への到達を、出力側で切る必要がある**（本記録の読み）。
影響（暗号化・破壊・改ざん）公表されていない
**実環境での成立例が報告されていないため、 どのような痕跡が残るかを示す資料が無い**（〈未確定1〉）。 一般論として、GeoServer プロセスからの想定外の子プロセス生成と 外向き通信は検知対象になる（本記録の評価）。
影響を限定できたGeoServer を動かすプロセス・コンテナを最小権限で動かし、 想定外の子プロセス生成を検知する（EDR・コンテナのランタイム監視）。　本記録の評価。**実行されるのは「GeoServer プロセスの権限」である**（出典5）—— root や広い権限で動かしていれば、そのまま被害が広がる。
侵入を防げたGeoServer をインターネットへ直接公開せず、必要な利用者・経路に限定する （専用の前段・IP 制限・認証の前置）。　本記録の評価。**本件はすべて未認証・ネットワーク経由で成立する**（出典1・2）—— 到達できなければ連鎖は始まらない。 **ただしオープンデータ配信を目的に公開している場合は、この策が採れない** （本記録の整理）。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
修正版を先に公開し（数週間前）、勧告9件を2026年11月23日にまとめて公開した（出典1・2・5）。 研究者は同週に技術詳細と PoC を公開した（出典5）。部分的に機能本記録の評価。**勧告の内容は質が高い**（本記録の読み）〈重要〉—— 根本原因（`${ID}` の文字列置換）、連鎖の中での位置（第2段であること）、 回避策（プロキシでの遮断条件）、そして**侵害の痕跡を点検する具体的なフォルダ**まで 書かれている（出典1・2）。 **一方で、修正版の公開から勧告公開までの空白期間に、 利用者が緊急性を判定する手段は無かった**（本記録の評価）—— そして悪用試行は、PoC 公開の後に観測されている（出典5）。
回避策として、WFS の匿名利用者への制限または WFS の無効化を示した（出典1）。部分的に機能本記録の評価。**勧告自身が回避策の限界を明示している点は誠実である**（本記録の読み）—— 「制限しない場合もファイルは読まれるが返らない」と書いてある（出典1）。 **したがって回避策は時間を稼ぐ手段であり、更新の代替にはならない。**
CISO・経営層への示唆
  • 外部公開している OSS 基盤について、「勧告を待たずにパッチ版を取り込む」方針を数字で決める。
    本件では修正版が勧告公開の数週間前に出ており、 その間、利用者には更新の理由が見えなかった（出典5）〈重要〉。 **そして内容と PoC が公開された直後に悪用試行が観測されている**（出典5）—— **勧告を起点にする運用は、攻撃者と同じ合図で走り出すことになる**（本記録の評価）。
    取るべき行動 インターネットに公開している OSS 基盤（GeoServer・地図サーバ・API ゲートウェイ等）の 一覧を作り、各々について「パッチ版（最後の桁の更新）は内容の説明を待たずに N 日以内に取り込む」と期限を数字で定める。 取り込みを妨げる要因（検証環境の不在・停止調整）を同時に洗い出して解消する。
  • 地理空間・オープンデータの配信基盤を、資産台帳の「公開システム」として扱う。
    GeoServer は政府機関で広く使われ、公益事業者も導入していると報じられている（出典5）。 **地図・オープンデータの配信は「公開して当然のもの」として扱われ、 セキュリティ資産の管理対象から外れやすい**（本記録の評価）。 本件はすべて未認証・ネットワーク経由で成立する（出典1・2）。
    取るべき行動 公開しているデータ配信基盤（WFS/WMS・CKAN・API）を資産台帳に明記し、 ①版、②認証の有無、③プロセスが読めるファイルの範囲、④外向き通信の許可先を 欄として持たせる。四半期ごとに版を照合する。
  • 1回の更新で複数の勧告を受け取る前提で、優先度判定の手順を用意する。
    本件で公開されたのは9件であり、報道が取り上げたのは2件である（出典4・5）。 **連鎖の本体である remember-me 鍵の脆弱性（Critical）は、 報道では主題になっていない**（本記録の確認）〈重要〉—— **報道を起点に優先度を決めると、最も重い1件を落としうる。**
    取るべき行動 脆弱性対応の手順に「同一の更新に含まれる勧告をすべて一覧化してから優先度を決める」 という段取りを明記する。 勧告が連鎖を示している場合（「step 2 of a chain」等の記述）は、 連鎖全体の最高深刻度で扱うと規定する。
  • 回避策の限界を、適用の記録と一緒に残す。
    本件の回避策（WFS の匿名公開の制限）は、**ファイルの読み出し自体は防がず、 内容が返らなくするだけである**（出典1）。SSRF も成立する。 **「回避策を適用済み」という記録だけが残ると、対応済みと誤認される**（本記録の評価）。
    取るべき行動 回避策を適用したときは、台帳に「何が防げて何が残るか」を 勧告の記述から転記して併記する。 回避策で止めた案件には更新の期限を別途設定し、期限を回避策の適用日から起算する。
セキュリティ技術者への示唆
  • 更新と同時に、作られた保存クエリの痕跡を点検する。
    勧告は回避策と並べて、データディレクトリの `wfs/query` および `workspaces/*/wfs/query` を確認し、自分で作成していない保存クエリが無いか 点検するよう書いている（出典2）〈重要〉。 **watchTowr が観測した探索は、まさに保存クエリを作成して呼び出すものである**（出典5）—— **到達されていれば設定として残りうる。**
    取るべき行動 GeoServer のデータディレクトリの `wfs/query`・`workspaces/*/wfs/query` を 一覧化し、構成管理に記録した「意図した保存クエリ」と突き合わせる。 差分があれば内容を保全してから削除する。 今後のために、保存クエリの一覧を構成管理の対象に加える。
  • GeoServer プロセスが読めるファイルの範囲と、外向き通信の許可先を絞る。
    CVE-2026-120705 で読み出せるのは「GeoServer プロセスが読めるファイル」である（出典1）—— **プロセスの到達範囲がそのまま被害の範囲になる**（本記録の読み）。 また SSRF は匿名公開を制限しても成立するため、 クラウドのメタデータ端点や内部 API へサーバ側から到達できる（本記録の評価）。
    取るべき行動 GeoServer を専用の利用者・コンテナで動かし、 ①資格情報ファイル・鍵・他サービスの設定を同一プロセスから読めない配置にする、 ②外向きの HTTP/HTTPS を必要な宛先だけに限定する（既定拒否）、 ③クラウドのメタデータ端点への到達を遮断する、を実施する。
  • 「Illegal property name」などのエラー応答の発生率を監視指標にする。
    本件の情報取得は**エラー応答を通じて行われる**（出典1）〈重要〉。 watchTowr が観測した探索も、エラーを利用して脆弱性の有無を判定するものである（出典5）。 **つまりエラー率の異常そのものが探索の指標になる**（本記録の評価）—— ただし平常時の分布を取っていなければ判定できない。
    取るべき行動 GeoServer のアプリケーションログから、エラー応答の種類別の発生率を 日次で集計して基準線を作る。 保存クエリ関連の操作（CreateStoredQuery・DropStoredQuery・GetFeature の 保存クエリ呼び出し）については、認証の有無とともに記録し、 未認証からの呼び出しを警報にする。
  • 前段のプロキシで、`service` パラメータの値の形を検査する。
    CVE-2026-129243 の回避策は、`service` にスラッシュを含むリクエストを 前段で遮断することである（出典2）。 **正規の利用で `service` にスラッシュが入ることは通常ない**（本記録の推定）—— 業務への影響が小さく、効果が明確な検査である。
    取るべき行動 GeoServer の前段（リバースプロキシ・WAF）で、クエリ文字列の `service` と XML 本文の `service` 属性の双方について、スラッシュを含む値を遮断する規則を入れる。 **遮断したリクエストを記録し、探索の到達状況を把握できるようにする。** 前段が無い構成では、この機会にプロキシを置く。
  • GeoTools を含めて版を確認する（GeoServer だけを見ない）。
    CVE-2026-120705 は GeoServer（gs-wfs-core）と GeoTools（gt-metadata）の 双方に影響範囲が示されている（出典1）。 **修正は GeoTools 側の PreventLocalEntityResolver にも入っている**（出典1）—— GeoTools を別途組み込んでいる自社アプリケーションがあれば、そちらも対象である（本記録の読み）。
    取るべき行動 GeoServer の版だけでなく、自社で GeoTools を依存として組み込んでいる アプリケーションを洗い出し、33.7・34.6・35.2 以上であることを 依存関係のロックファイルで確認する。

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ GeoServer を 2.27.6 以前・2.28.0〜2.28.5・3.0.0〜3.0.1 のいずれかで運用しており、 WFS が有効で GetFeature 操作に到達できる。
認証・認可□ WFS のレイヤを匿名利用者に公開している（オープンデータ配信等）。
認証・認可□ サービスセキュリティで操作（WFS Transaction 等）を制限している。
運用・監視□ OSS 基盤のパッチ版を、勧告や報道が出てから適用する運用である。
システム構成□ GeoServer を動かすプロセスが、資格情報ファイルや内部 API・ クラウドのメタデータ端点へ広く到達できる状態にある。
運用・監視□ GeoServer の保存クエリ（`wfs/query`・`workspaces/*/wfs/query`）を 構成管理の対象にしていない。
