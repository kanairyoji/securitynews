INC-2026-1332nfsd に12年潜んだRCE（NFS2ROOT）

Linux カーネル内蔵 NFS サーバ（nfsd）に12年潜んだ境界外書き込み「NFS2ROOT」（CVE-2026-99362）——TCP 2049 への接続だけで root を狙える構成があり、主要ディストリビューションの修正は遅れた

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月19日（kernel.org の CNA が CVE-2026-99362 を公開した日。Ubuntu のセキュリティ情報の published も同日） 最終更新: 2026年11月26日

Linux カーネルに内蔵された NFS サーバ（nfsd）に、認証も利用者の操作も要らず TCP 2049 への接続だけで境界外書き込みを起こせる脆弱性が公表された。 CVE-2026-99362、呼称 NFS2ROOT。CVE は2026年11月19日に kernel.org の CNA から公開され（出典3・4）、 CVSS 3.1 の基本値は 9.8（Critical）である（出典2。cve.org の値。Red Hat は 9.4 と評価。出典1）。 原因は2014年3月のコード変更でカーネル 3.16 に入り、12年間 LTS・各ディストリビューション・ アプライアンスのカーネルに残った（出典4・5）。 成立の筋道はこうである——クライアントが応答キャッシュのサイズを最小値まで交渉して スロットのデータ用バッファを0バイトにし、細工した COMPOUND 要求を送ると、 サーバがこれを正常処理と誤認して0バイトのバッファへ応答を書き込む（出典1・2・4）。 韓国の報道によれば、研究組織 OpenSec Intelligence は0バイトのヒープバッファに80バイトの応答が 複写され、境界外61バイトが上書きされると分析し、うち40バイトを攻撃者が制御して KASLR の回避と任意オブジェクトの解放を経てリモート root シェルに至ると説明したという（出典5）。 修正はカーネル 5.10.275・5.15.226・6.1.193・6.6.163・6.12.117・6.18.61・7.3.2・7.4-rc1 に入っている（出典4）。 一方で Ubuntu は2026年11月25日時点で 26.10・26.04 LTS が対応作業中、 24.04／22.04／20.04／18.04／16.04 LTS が未修正である（出典2。本記録が確認）。 Red Hat は RHEL の既定構成では nfsd を動かさないため攻撃面は NFSv4.1/4.2 を 公開するサーバに限られるとしている（出典1）。 2026年11月26日時点で実環境での悪用は報告されておらず、CISA KEV にも収載されていない（出典4）。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は認証なしに TCP 2049 へ接続し、NFSv4.1 のセッション確立時に 応答キャッシュのサイズを最小値まで交渉してスロットのデータ用バッファを0バイトにする。 続いて細工した COMPOUND 要求を送ると、サーバは応答がスロットに収まるかを検査せずに 書き込み、境界外へ上書きする。 書き込まれたバイトの大半はクライアントが読み出せるため、 カーネルメモリの配置の把握にも使える（出典2）。 **報じられている分析では、ここから KASLR の回避と任意オブジェクトの解放を経て リモート root シェルに至るとされる**（出典5）〈未確定7〉。 **実環境での悪用は報告されていない**（出典4）。

    攻撃者が認証なしに TCP 2049 へ接続し、NFSv4.1 のセッションを確立する。 **その際、キャッシュする応答のサイズを最小値まで交渉し、 セッションスロットのデータ用バッファを0バイトにする。**
    根拠: 出典2「クライアントは非常に小さいキャッシュ応答サイズを交渉でき、 それによってセッションスロットのデータ用バッファが0長になる」 （原文英語。本記録が訳した）。 出典4 も「キャッシュする応答のサイズを最小値まで交渉し、 スロットの応答バッファに余地が残らない状態にする」と述べている（原文英語。本記録が訳した）。
  2. 2. 実行確認済
    細工した COMPOUND 要求を送る。 **サーバは応答が交渉した上限に収まるかを検査せずにキャッシュへ書き込み、 0バイトのスロットの末尾を越えて上書きする（スラブ境界外書き込み）。**
    根拠: 出典2「細工した COMPOUND 要求によって、サーバがスロットの末尾を越えて 応答を書き込み、KASAN が検出するスラブ境界外書き込みが起きる」 （原文英語。本記録が訳した）。 **修正は「SEQUENCE 応答と、後続操作のエラー状態のための領域が、 交渉した上限に収まるかをスロットを使う前に検査する」ものである**（出典2）。 **報じられている OpenSec の分析では、0バイトのバッファへ80バイトが複写され、 境界外61バイトが上書きされる**（出典5）。

    **上書きされたバイトの大半をクライアントが読み出せることを使ってカーネルメモリの 配置を把握し、制御可能な領域から KASLR の回避と任意オブジェクトの解放へ進む。** **報じられている分析では、ここからリモート root シェルに至るとされる。**
    根拠: 出典2「クライアントはスロットを越えて書き込まれたバイトの大半を読み出せ、 これには COMPOUND のタグが含まれる」（原文英語。本記録が訳した）—— **読み出しが成立することは一次資料で確認できる。** 出典4 も「あふれたデータの多くはクライアント自身の要求から来るものであり、 サーバは上書きされたデータの多くを応答で返すため、 攻撃者がカーネルメモリの配置を把握する助けになる」と述べている（原文英語。本記録が訳した）。 **境界外61バイトのうち40バイトを攻撃者が制御し、KASLR の回避と 任意オブジェクトの解放を経て root シェルに至るという具体は、 OpenSec の分析として韓国の報道が伝えたものである**（出典5）〈未確定7〉。

TCP 2049 への接続だけで境界外書き込みが起きる。原因は2014年のコード変更である概観

Linux カーネルに内蔵された NFS サーバ（nfsd）に、認証も利用者の操作も要らずに境界外書き込みを起こせる脆弱性が公表された。CVE-2026-99362、呼称 NFS2ROOT。CVE は2026年11月19日に kernel.org の CNA から公開され（出典4）、CVSS 3.1 の基本値は 9.8（Critical）である（出典1・2）。

成立の筋道は、仕様の交渉を悪用するものである。NFSv4.1 のセッション確立時、クライアントはキャッシュする応答のサイズを交渉できる。これを最小値まで小さくすると、セッションスロットのデータ用バッファが0バイトになる。そこへ細工した COMPOUND 要求を送ると、サーバは応答がスロットに収まるかを検査せずに書き込み、スロットの末尾を越えて上書きする（出典2・4）。

Canonical の説明が示す構造が重要である——クライアントは、スロットを越えて書き込まれたバイトの大半を読み出せる（出典2）。書き込みと読み出しの双方が成立する。出典4 も、あふれたデータの多くはクライアント自身の要求から来るもので、サーバは上書きされたデータの多くを応答で返すため、攻撃者がカーネルメモリの配置を把握する助けになると述べている。

原因のコード変更は2014年3月、カーネル 3.16 に入った（出典4・5）。12年間、LTS・各ディストリビューション・アプライアンスのカーネルに残った（出典5）。修正は 5.10.275・5.15.226・6.1.193・6.6.163・6.12.117・6.18.61・7.3.2・7.4-rc1 に入り、上流のコミットの表題は「nfsd: preflight SEQUENCE replies before accepting a slot」（スロットを受け入れる前に SEQUENCE 応答を事前検査する）とされている（出典4）。

既定では動かない。しかし NFS サーバを立てている環境では主たる用途である被害規模・影響範囲

影響を受けるのは、①カーネル内蔵の nfsd が動作し、②NFSv4.1 または NFSv4.2 が有効で、③TCP 2049 に到達できる経路があるホストである（出典1・4・5）。

Red Hat はこの限定を明示している——RHEL の既定構成では nfsd を動かさないため、攻撃面は NFSv4.1/4.2 の共有を公開するよう設定された環境に限られる（出典1）。本記録はこの説明を適切と評価する（本記録の評価）。CVSS 9.8 という数字だけでは、全 Linux ホストが危険という読み方を招く。

ただし、ここには読み替えが要る（本記録の読み）。「既定では動かない」という説明は、意図して NFS サーバを運用している環境には何の軽減にもならない。そして NFS を動かす目的でそのホストを立てているなら、それは例外的な構成ではなく主たる用途である。韓国の報道は具体的な対象として、共有ファイルサーバ、Kubernetes のストレージノード、Linux ベースの NAS、セキュリティアプライアンスを挙げている（出典5）。NAS とアプライアンスはカーネルを組み込んで出荷されるため、利用者が自力で更新できないことが多い（本記録の評価）。

なお Red Hat と cve.org では評価が分かれている。Red Hat は CVSS を 9.4、完全性への影響を低（I:L）とし、影響を「サービス不能、および場合によってはコード実行」と記している（出典1）。cve.org と Canonical は 9.8、完全性への影響を高（I:H）とする（出典1・2）。そして OpenSec Intelligence の分析として報じられているのはリモート root シェルである（出典5）。運用側は、どの評価で優先度を決めるかを自分で選ぶことになる（本記録の整理）。

上流に修正はある。だが本記録の確認時点で Ubuntu の LTS 5つは未修正である対策・注意喚起

本件の運用上の核心はここにある。上流の修正は存在するのに、利用者の大半はまだ適用できない。

本記録が2026年11月27日に Canonical のセキュリティ情報で確認した状態は次のとおりである（出典2）——26.10（stonking）と 26.04 LTS（resolute）は対応作業中、24.04 LTS（noble）・22.04 LTS（jammy）・20.04 LTS（focal）・18.04 LTS（bionic）・16.04 LTS（xenial）は未修正。14.04（trusty）は影響なし。さらに linux-aws・linux-azure・linux-gcp・linux-oracle・linux-raspi・linux-gke、および FIPS 系の派生も多数が未修正とされていた。クラウド向けカーネルを使っている環境も同じ状態である。 Red Hat についても、11月26日時点で公式の Errata はまだ配布されていないと報じられている（出典5）。CVE 公開（11月19日）から8日が経っている。

この状況で採れる手段は限られる。第一に、TCP 2049 への到達を認可されたストレージ帯域に限定すること（出典1・4・5）。Red Hat は firewalld の規則を示しつつ、firewall-cmd --reload が明示的に許可されていないクライアントの接続を切断する点に注意するよう述べている（出典1）——規則の適用そのものが既存のセッションを切る。第二に、NFS が不要なら nfs-server を停止・無効化する（出典1）。第三に、暫定措置として /etc/nfs.conf で NFSv4.1・4.2 を無効化してサービスを再起動する（出典4・5）——ただしこれは NFSv4.1/4.2 に依存する運用を止める。

そして「内部ネットワークだから安全」という判断は成り立たない（本記録の評価）。出典5 は、内部網へ侵入した後に共有ファイルサーバや Kubernetes のストレージノードを掌握する経路として悪用される危険が大きいと述べている。2049 を内部網に閉じておくことは外部直接露出を減らす要因だが、それだけである。

版だけ見る点検では当たらない。4項目をホスト側で確かめる必要がある評価・解釈

本件の点検は、脆弱性スキャナの版判定では埋まらない（本記録の評価）。

理由は2つある。第一に、修正版の番号が系列ごとに異なることである—— 5.10.275・5.15.226・6.1.193・6.6.163・6.12.117・6.18.61・7.3.2（出典4）。「この版以上なら安全」という単一の基準が作れない。自ホストの系列を特定したうえで、その系列の修正版と照合する必要がある。

第二に、攻撃面の有無がホストの設定で決まることである。韓国の報道が伝える OpenSec の推奨は4項目である——①稼働サーバのカーネル版、②nfsd モジュールの読み込みの有無、③NFSv4.1・4.2 の有効状態、④TCP 2049 の開放帯域。4条件すべてに該当するなら直ちに修正カーネルへ更新して再起動する（出典5）。②③④は稼働中のホストを調べないと分からない。版だけを見れば母数が過大になり、設定を見なければ本当に危ないホストが埋もれる（本記録の評価）。

検知についても、本件は難しい側に寄っている。出典5 は、今回の攻撃が正常なNFS トラフィックの形を取るため、ネットワークシグネチャで振り分けるのが難しいと伝えている。代わりに示されているのはホスト側の痕跡である——カーネルログの nfsd4_check_resp_size 警告と、カーネルワーカーによる異常なシェル実行の痕跡（出典5）。本記録は OpenSec 自身の公表を取得できておらずこの指標を一次資料で確認していないが〈齟齬1〉、ネットワークで見えないものをホストのログで捕まえるという方向は、本件の構造と整合している（本記録の評価）。問題は、カーネルログの警告を集約して見ている組織が少ないことである。そして該当ホストが NAS やアプライアンスの場合、ログを外へ出せるかが先に問題になる（本記録の読み）。

なお2026年11月26日時点で、実環境での悪用は報告されておらず、CISA KEV にも収載されていない（出典4）。OpenSec は実証コードを非公開に保っている（出典4・5）。ただし上流の修正と攻撃原理が公になったことで、N-day としての武器化が早まるとの懸念が示されている（出典5）。

セキュリティ技術者への示唆
  • 版だけでなく「nfsd が動いているか・NFSv4.1/4.2 が有効か・2049 が誰に開いているか」を確かめる。

    出典5 は、内部網へ侵入した後に共有ファイルサーバや Kubernetes の ストレージノードを掌握する経路として悪用される危険が大きいと述べている〈重要〉。 **ストレージノードは多数の利用側が依存する集約点であり、 root を取られれば全ての永続データに手が届く**（本記録の評価）。

    /etc/nfs.conf で NFSv4.1・4.2 を無効化する暫定措置が示されているが（出典4・5）、 **NFSv4.1/4.2 の機能（セッション等）に依存する運用は止まる**（本記録の推定）—— クライアント側の対応状況によっては共有そのものが使えなくなりうる（本記録の読み）。
