INC-2026-1333発電機制御器APM802にRCE2件・ベンダー未応答

発電機制御器 Rehlko（旧 Kohler Energy）APM802 に RCE 2件——工場出荷時の認証情報・root で動くサービス・2013年頃の websockify が残り、ベンダーと CERT から応答が無いまま記事が公開された

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備権限管理の不備脆弱性の放置
初報: 2026年11月26日13時30分（UTC。Xakep の記事の公開時刻） 最終更新: 2026年11月26日

ロシアの技術誌 Xakep（Хакер）は2026年11月26日、発電機制御器 Rehlko（旧 Kohler Energy）グループの SOREEL SAS 製 APM802 に、 リモートコード実行（RCE）が成立する脆弱性2件を見つけたという研究者の記事を公開した（出典1）。 記事が挙げる内容は、①パスワード不要で到達できる websockify の RCE、 ②ベンダー独自プロトコル BASEPARAM のヒープオーバーフロー、 ③工場出荷時の認証情報、④superuser（root）の権限で動作するサービス群である（出典1）。 そして記事執筆時点で、ベンダーと CERT（インシデント対応チーム）のいずれからも 応答が無かったと述べている（出典1）〈重要〉。 研究者は隔離した試験環境で装置イメージの複製を用いて作業し、 本番ネットワークや実機の発電機には接触していないと明記している（出典1）。 APM802 は発電所・変電所・データセンターで使われる制御器で、 操作端末は MICS4 と呼ばれ、内部では Debian 上の Qt アプリケーションが動く。 発電機を制御する base モジュールとの通信には、Modbus や OPC UA ではなく ベンダー独自の BASEPARAM を使う（出典1）。 Rehlko の公開資料では、最大8系統の電力系統と最大64台の発電機セットの管理、 2N+1 までの冗長構成に対応するとされ、重要用途として病院・空港・海洋設備・ 上下水道・エネルギー施設・イベント会場が挙げられている（出典1）。 工場出荷時に外部へ露出するサービスとして、SSH・FTP・noVNC を伴う HTTP・ ポート5900/5901 の VNC・ポート8080 の websockify・ポート1514 の rsyslog が挙げられ、 版はいずれも古い。装置自身にローカルのファイアウォールは無い（出典1）。 なお本記録が読めたのは記事の無料公開部分までであり、 2件の脆弱性の技術的詳細は会員限定である〈齟齬1〉。 CVE の採番、ベンダーの勧告、CERT の勧告はいずれも確認できなかった〈未確定1〉〈齟齬2〉。

条件は厳しい。装置自身にローカルのファイアウォールが無く（出典1）、工場出荷時の認証情報があり、サービスは root で動いている。ベンダーからの応答が無いため、認証情報の変更が可能か、使っていないサービスを止めてよいかという問いにも答えが返ってこない。組み込み機器では、利用者が独断でサービスを止めると保証の対象外になる、あるいは遠隔保守が成立しなくなることがある（本記録の評価）。つまり装置に手を入れる対策は、どれもベンダーの回答に依存して止まっている。

残るのは装置の外側である。①制御器のネットワーク区画を業務ネットワークとインターネットから経路として切り離し、到達できる端末を機器単位で限定する。②その区画の通信を記録し、想定外の発信元からの接続を警報にする。③制御器から外向きの通信を必要な宛先だけに限定する。この3つは利用者側だけで実施でき、ベンダーの応答を待たずに着手できる（本記録の評価）。記事によれば装置のネットワークは管理用と base VLAN の2区画に分かれており（出典1）、設置時のネットワーク設計がそのまま到達可能性を決めている。

もうひとつ、調達の論点がある。本件で露出しているとされる構成要素の版は、いずれも10年以上前のものである（出典1）。非常用電源・空調・入退室のような設備側の制御機器は、建物の寿命に合わせて10年20年使われる一方、中に入っている汎用ソフトウェアの寿命はそれよりずっと短い（本記録の評価）。この差を埋める仕組み——更新の提供期間、脆弱性報告の受付窓口、応答の期限——を契約時に取り付けておかないと、本件のように「報告しても応答が無い」状態に利用者側が付き合うことになる。

なお参考として、websockify の C 実装については2016年にバッファオーバーフローによるリモートコード実行の勧告が公開されており、対象は 0.8.0 以下の全バージョン、回避策として Python 実装の使用が示されていた（出典3）。記事が記す搭載ビルドは2013年頃とされるが、本記録は搭載ビルドがこの既知の脆弱性に該当するかを確認していない（技術的詳細が読めないため。〈齟齬3〉）。断定はしない。

**研究者は隔離した試験環境で装置イメージの複製を用いて調査し、 本番ネットワークと実機の発電機には接触しなかった**（出典1）。機能した**本記録の評価**〈重要〉——**対象が非常用電源の制御器である以上、 稼働中の実機で試験することは、それ自体が重要施設の停電を招きかねない** （本記録の読み）。 **隔離環境に限定し、その事実を冒頭で明示した点は適切である。** **併せて、この限定が「発電機を任意に操作できるか」という論点を 未確認のまま残していることも記録する**——**本記録はその帰結を推定しない。**
CISO・経営層への示唆
  • 設備系の制御機器を調達するとき、「脆弱性報告への応答義務」を契約に書く。
    本件で記事が述べているのは、**ベンダーと CERT のいずれからも応答が無かった**という 事実である（出典1）〈重要〉。 **応答が無ければ、修正版も回避策も勧告も出ない**—— 利用者は装置の外側の対策だけで運用を続けることになる（本記録の評価）。 **そして対象は病院・データセンター・上下水道の非常用電源である**（出典1）。
    取るべき行動 発電機・空調・入退室・UPS などの設備系制御機器の調達仕様に、 ①脆弱性報告の受付窓口（連絡先と受付形式）、②報告からの一次応答の期限（日数）、 ③セキュリティ更新の提供期間（年数）、④更新の提供方法（現地作業の要否）を 条項として入れる。既存機器については、保守契約の更新時に同じ4項目を照会し、 回答が得られない機器を「ベンダー対応に期待できない機器」として台帳に印をつける。
  • 設備系機器の「中のソフトウェア」の寿命と、設備の寿命の差を台帳に書く。
    本件で露出しているとされる構成要素は OpenSSH 5.5p1・ProFTPD 1.3.3a・ lighttpd 1.4.28・x11vnc 0.9.10 など10年以上前の版であり、 websockify は2013年頃のビルドとされる（出典1）〈重要〉。 **設備は建物の寿命に合わせて長く使われるが、中の汎用ソフトウェアの寿命は短い**（本記録の評価）。
    取るべき行動 設備系制御機器の台帳に「基盤 OS とその版」「組み込まれている主要な汎用ソフトウェア」の 欄を作り、分かる範囲で記載する（分からない場合はベンダーへ照会し、 回答が無いことも記録する）。 年1回、記載した構成要素についてサポート終了の状況を確認し、 期限切れのものを抱える機器を優先的に隔離対象とする。
  • 「ベンダーが修正しない前提」でも実施できる対策を、先に区別しておく。
    本件では、認証情報の変更やサービスの停止といった装置側の対策が **すべてベンダーの回答に依存して止まっている**（本記録の評価）〈重要〉—— 組み込み機器では独断の変更が保証の対象外になりうる（本記録の読み）。 **一方でネットワーク側の隔離・監視・出力制御は利用者だけで実施できる。**
    取るべき行動 設備系機器ごとに、対策を「利用者だけで実施できるもの（ネットワーク隔離・ 通信の記録・出力方向の制限）」と「ベンダーの確認が必要なもの（認証情報の変更・ サービスの停止・ファームウェア更新）」の2欄に分けて記載する。 重大な脆弱性の報が出たとき、前者を**即日**着手し、後者は照会と並行させる。
  • 非常用電源の制御器を「停電を起こせる系」として危機管理計画に含める。
    APM802 は製品仕様上、最大8系統の電力系統と最大64台の発電機セットを管理し、 2N+1 までの冗長構成に対応するとされる（出典1）〈重要〉。 **冗長化は機器の故障に対する備えだが、制御器を握られた場合には 冗長な機器が同じ指示を受ける構成になりうる**（本記録の評価）—— **ただし本記録は、制御器の掌握から発電機の任意操作が可能とは確認していない** 〈齟齬1〉。
    取るべき行動 停電時の事業継続計画に「非常用電源の制御系が正常に動作しない場合」の 想定を加え、①手動起動の手順と権限、②制御器を経由しない状態確認の方法、 ③制御系を隔離した状態で発電機を運転できるかの確認、を文書化する。 年次の停電訓練で、制御器を信頼できない前提の手順を一度実施する。
セキュリティ技術者への示唆
  • ローカルファイアウォールを持たない機器は、区画の境界で守るしかないと設計に書く。
    記事は**装置自身にローカルの межсетевой экран（ファイアウォール）が無い**と 明記している（出典1）〈重要〉。 **工場出荷時に SSH・FTP・HTTP／noVNC・VNC（5900/5901）・websockify（8080）・ rsyslog（1514）が露出し、Remote HMI モードでは UDP 49805・49806 が追加される**（出典1）—— **装置側では1つも閉じられない前提で考える必要がある**（本記録の評価）。
    取るべき行動 設備系制御機器が属するネットワーク区画について、 ①到達できる発信元を機器単位（IP／MAC）で明示的に許可し、既定を拒否にする、 ②上記ポートへの接続を区画の境界で記録する、 ③制御器から外向きの通信を必要な宛先だけに限定する、を実装する。 実装後、**実際に許可外の端末から接続を試みて遮断を確認する**（設定だけで満足しない）。
  • 操作端末の遠隔アクセスが VNC で提供されている機器を洗い出す。
    **Rehlko の製品ページ自身が「VNC による遠隔アクセス」を機能として記載している** （出典2）〈重要〉——つまりこれは設定の不備ではなく製品の設計である。 **記事によれば搭載されている実装は x11vnc 0.9.10・Xtightvnc 1.3.9 で、 noVNC を伴う HTTP と websockify（2013年頃の C 実装ビルド）が組み合わされている**（出典1）。
    取るべき行動 設備系機器の遠隔アクセス手段を棚卸しし、VNC（5900番台）・ブラウザ経由の VNC （noVNC・websockify）を使っている機器を特定する。 それらについて、①区画の外からの到達を遮断する、 ②遠隔保守が必要な場合は踏み台（多要素認証つき）経由に限定する、 ③使用していない遠隔アクセスの停止が可能かベンダーへ照会する、を実施する。
  • ベンダー独自プロトコルを「認証されない信頼前提の経路」として扱う。
    記事は BASEPARAM を**「доверительный протокол」（信頼を前提としたプロトコル）**と 表現し、そこにヒープオーバーフローがあると述べている（出典1）〈重要〉。 **制御器と base モジュールの通信に Modbus や OPC UA ではなく独自プロトコルを 使っている**（出典1）—— **独自プロトコルは一般の検査ツールの対象外であり、 問題が見つかるのも遅れる**（本記録の評価）。
    取るべき行動 制御系の通信経路を洗い出し、ベンダー独自プロトコルを使う区間を特定する。 それらの区間を**物理的または VLAN で分離し、他の用途の通信と同居させない**。 併せて、当該区間に接続できる機器の一覧を作り、追加時の承認手順を定める。
  • 機器のログを外部へ出せるかを、導入時に確認する。
    本件の装置には rsyslog 8.2010.0 がポート1514 で動いているとされる（出典1）—— **ログの外部転送が構成されうることは読めるが、既定で有効かは不明である**（本記録の読み）〈齟齬1〉。 **組み込み機器では装置側に監視を載せられないことが多く、 ログを外へ出せるかが唯一の観測手段になる**（本記録の評価）。
    取るべき行動 設備系制御機器について、①syslog 等でログを外部へ転送できるか、 ②転送されるログに認証の成否・サービスの再起動・設定変更が含まれるか、 ③転送先を自社の集約基盤に向けられるかを確認し、可能なものを接続する。 確認できない機器は「観測できない機器」として台帳に印をつけ、 ネットワーク側の記録で補う。
