台湾の電子発票加値サービス「PayNow」（運営は奧丁丁集團傘下の立吉富線上金流）で、対外 API が権限のない異常アクセスを受け、同サービスを通じて発行された電子発票のデータが外部に取得された。PayNow の調査によれば、攻撃者はまず発票ホストに侵入してシステム設定情報と鍵を取得し、その後、多数のプロキシ IP を使って発票照会 API と発票照会ページから発票データを一括で読み出した。

被害は 2 段階に分かれる。第 1 段階は 11 月 11 日に発見された電子発票システムの対外照会 API への異常アクセスで、同日に接続可能 IP の限定・悪性発信元の遮断・既知のプログラム脆弱性の修補を行い、11 月 13 日に財政部国税局へ通報した。第 2 段階は 11 月 20 日に発見された別経路——加値中心システムの発票照会ページ——への権限なき読み出しで、同日に当該ページと API を遮断し、IP 許可リストを設定して国税局への通報を更新した。両段階とも知得から 72 時間以内に通報を完了したとしている。

重複を除いた集計で、影響を受けたのは約 500 商家・約 281 万枚の電子発票で、発行期間は 2019 年から 2026 年 11 月に及ぶ。権限なく取得されたデータには買受人（購入者）の氏名・住所・電子メール・携帯電話番号・キャリア情報（載具情報）・発票明細が含まれ、クレジットカード番号や銀行口座などの資金決済情報は含まれないとしている。

加盟店側では香帥蛋糕が 11 月 24 日に、一事製菓が同時期に事件公告を出した。一事製菓は 11 月 22 日からなりすまし詐欺メッセージを確認して事案に到達している。購入者には実際に、店舗の名義をかたる詐欺メッセージが届いている。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

攻撃者は PayNow の発票ホストに侵入してシステム設定情報と鍵を取得し、 多数のプロキシ IP アドレスを使って、電子発票システムの対外照会 API （11月11日発見）と加値中心システムの発票照会ページ（11月20日発見）の 2 経路から発票データを一括で読み出した。重複を除いて約 500 商家・ 約 281 万枚、発行期間は 2019 年から 2026 年 11 月に及ぶ。取得された データには購入者の氏名・住所・電子メール・携帯電話番号・キャリア情報・ 発票明細が含まれ、その後、加盟店をかたる詐欺メッセージが 購入者に実際に届いている。

  1. 1. 初期侵入推定[2]
    攻撃者が PayNow の発票ホスト（發票主機）に侵入した。侵入の成立経路は 公表されていない。第 1 段階の対処として「既知のプログラム脆弱性の修補」が 行われているが、それがこの侵入に使われたものかは明示されていない。
    根拠: PayNow の初歩調査「攻撃者先入侵發票主機」（出典2）。第 1 段階の対処に 「修補已知程式漏洞」が含まれる（出典2）。
  2. 2. 認証情報アクセス推定[1] [2]
    攻撃者は発票ホスト上でシステム設定情報と鍵（金鑰）を取得した。 鍵の種類・対象範囲は公表されていない。加盟店と PayNow の連携に 使用する API 鍵は本件に関係しないとされている。
    根拠: PayNow の初歩調査「取得系統設定資料與金鑰」（出典2）。加盟店向け説明 「本次事件不涉及貴司與本公司串接所使用的 API 金鑰」（出典1）。
  3. 3. 収集確認済[1] [2]
    攻撃者は取得した鍵を使い、多数のプロキシ IP アドレスを経由して、 電子発票システムの対外照会 API から発票データを一括で読み出した。 PayNow はこれを 11月11日に発見し、同日に IP の限定・発信元の遮断・ 既知の脆弱性の修補を行い、11月13日に国税局へ通報した。
    根拠: PayNow の説明「再透過大量代理 IP 位址，利用上述查詢 API 及頁面 批次讀取發票資料」、第 1 段階の経緯（出典2）。
  4. 4. 収集確認済[2]
    第 1 段階の対処後も、別経路である加値中心システムの発票照会ページから 権限なき読み出しが続いていた。PayNow は 11月20日にこれを発見し、 同日に当該ページと API を遮断して IP 許可リストを設定し、 国税局への通報を更新した。第 1 段階の発見から 9 日あいている。
    根拠: PayNow の説明「第二階段則於 11月20日發現另一個發票查詢頁面（加值中心 系統）遭未經授權讀取，這是第一階段 API 以外的另一條存取路徑」（出典2）。
  5. 5. 持ち出し確認済[1] [2]
    2 段階を合算し重複を除いて、約 500 商家・約 281 万枚の電子発票が 権限なく取得された。発行期間は 2019 年から 2026 年 11 月。取得された データには購入者の氏名・住所・電子メール・携帯電話番号・ キャリア情報・発票明細が含まれる。
    根拠: PayNow の最新の洗い出し結果（出典2）および加盟店が公開した PayNow の事件説明における項目の列挙（出典1）。
  6. 6. 影響（暗号化・破壊・改ざん）確認済[1] [2]
    取得されたデータを使った、加盟店の名義をかたる詐欺メッセージが 購入者に届いた。一事製菓は 11月22日から自社をかたる詐欺メッセージを 確認し、そこから事案の発生元を特定している。PayNow は購入者へ 「注文の異常・二重引き落とし・返金を理由に ATM やネットバンキングの 操作を指示されたら警戒し、165 反詐欺ホットラインで確認を」と 呼びかけている。
    根拠: 「目前已有買家反映收到冒用商店名義的詐騙訊息」（出典2）、 一事製菓の経緯（出典2）、加盟店が公開した詐欺防止の注意喚起（出典1）。

台湾の電子発票加値サービス「PayNow」（運営は奧丁丁集團傘下の立吉富線上金流）で、約 500 商家・約 281 万枚の電子発票データが権限なく取得された。発行期間は 2019 年から 2026 年 11 月に及ぶ。

PayNow の初歩調査によれば、攻撃の順序はこうである。攻撃者はまず発票ホストに侵入し、システム設定情報と鍵を取得した。そのうえで多数のプロキシ IP アドレスを使い、発票照会 API と発票照会ページから発票データを一括で読み出した。

本件の構造が端的に表れているのは、発見が 2 段階に分かれた経緯である。第 1 段階は 11 月 11 日。電子発票システムの対外照会 API への異常アクセスを確認し、同日に接続可能 IP の限定・悪性発信元の遮断・既知のプログラム脆弱性の修補を実施し、11 月 13 日に財政部国税局へ通報した。ここまでは速い。

第 2 段階は 11 月 20 日。加値中心システムの発票照会ページという、第 1 段階の API とは別の経路から権限なき読み出しが行われていたことを発見した。つまり、同じ発票データに到達できる経路が 2 本あり、第 1 段階で塞いだのはそのうち 1 本だった。攻撃者は鍵を持ったままで、9 日間、別の扉から読み出しを続けられた。

流出したのは連絡先ではなく、7 年分の「誰が何をいくらで買ったか」被害規模・影響範囲出典 [1] [2]

権限なく取得されたデータの中身が、本件の重さを決めている。

PayNow が挙げているのは、買受人（購入者）の氏名・住所・電子メールアドレス・携帯電話番号・キャリア情報（載具情報）、そして発票明細である。加盟店が公開した PayNow の事件説明では、注文番号・キャリア情報・購入者の氏名・電子メール・連絡電話・購入商品・取引金額と列挙されている。クレジットカード番号や銀行口座などの資金決済情報は含まれないとしている。

連絡先の一覧ではない。取引明細である。誰が、どの店で、何を、いくらで、いつ買ったかが揃っている。これは、なりすまし詐欺に最も効く材料である。「○月○日にご注文いただいた△△について、二重引き落としがありました」と言われたとき、購入者はその注文を実際にしているので、相手を本物と判断する。

実際、詐欺はすでに動いている。PayNow は「すでに購入者から、店舗の名義をかたる詐欺メッセージを受け取ったという申告がある」と述べ、消費者へ「注文の異常・二重引き落とし・返金を理由に ATM やネットバンキングの操作を指示されたら警戒し、165 反詐欺ホットラインで確認を」と呼びかけている。一事製菓はそもそも、11 月 22 日から自社をかたる詐欺メッセージを確認したことから事案に到達している。

規模の単位にも注意が要る。公表されているのは商家 約 500 社と発票 約 281 万枚で、購入者の実人数は示されていない。1 人が何枚もの発票を持つため、実人数は 281 万より少ない。一方、発票の発行期間が 2019 年からということは、7 年超の取引明細が照会可能な状態で置かれていたことになる。

当局通報は 72 時間以内、購入者には詐欺のほうが先に届いた組織の対応出典 [1] [2]

PayNow の対応は、速い部分と遅い部分が明確に分かれている。

速いのは技術的な封じ込めと当局対応である。第 1 段階（11 月 11 日）・第 2 段階（11 月 20 日）とも発見当日に遮断・修補を行い、両段階とも知得から 72 時間以内に財政部国税局へ通報した（第 1 段階は 11 月 13 日、第 2 段階は 11 月 20 日に更新）。11 月 13 日から影響を受けた加盟店への通知も始めている。

事後対策も具体的である。プログラム脆弱性の修補、発票照会 API とサンプルダウンロードへの IP 許可リストの設定、連携先が使用できるAPI 機能とデータ範囲の限定、後台システムの二段階認証、異常アクセスの即時警報機構、新版対外 API の稼働。並べてみると、これらは「鍵を持っているだけでは全件を読み出せない」状態を作るための措置であり、本来は侵害前に必要だったものである。

遅いのは購入者への到達である。加盟店向けの事件説明は 11 月 23 日付、加盟店の対外公告は 11 月 24 日。一方、一事製菓が自社をかたる詐欺メッセージを確認したのは 11 月 22 日である。購入者のもとには、事案の説明より先に詐欺が届いていた。

さらに、影響を受けた約 500 商家の一覧は公表されていない。対外公告を出したのは香帥蛋糕・一事製菓の数社で、NET は報道が言及するのみである。流出した情報が「どの店で何を買ったか」であり、詐欺はその店の名義で来るのに、購入者は警戒すべき店名を知れない。

鍵を前提にした API は、鍵が漏れた瞬間に「全件エクスポート機能」になる評価・解釈出典 [1] [2]

ここからは本記録の評価である。

本件の技術的な核心は、照会 API の設計にある。攻撃者は鍵を取得した後、多数のプロキシ IP を経由して発票データを「批次讀取」——一括で読み出した。鍵の正当性だけを見て、1 鍵あたりの読み出し量、照会できるデータの範囲、発信元を制限していなければ、照会 API は鍵が漏れた瞬間に全件エクスポート機能になる。

PayNow が事後に追加した対策を読むと、これが裏づけられる。IP 許可リストの設定、「連携先が使用できる API 機能とデータ範囲の限定」、異常アクセスの即時警報。いずれも「鍵があっても全件は取れない」状態を作るための措置である。API 鍵を認証の手段としてだけ扱い、認可の境界として設計していなかったことが、被害規模を決めた。

二つ目の論点は、封じ込めの範囲である。第 1 段階で PayNow は「発見した API」を塞いだ。しかし攻撃者は鍵を持ったままだった。同じ鍵で到達できる別の経路（加値中心システムの発票照会ページ）が残っており、9 日後にそこからの読み出しが発見された。

鍵が漏れた侵害では、経路を塞ぐより先に鍵を殺すのが順序である。そして「この鍵で到達できる経路」を全部列挙する工程が、封じ込めの手順に入っていなければならない。公開面は API だけではない。管理画面、照会ページ、サンプル（樣張）のダウンロード——同じデータストアに届く入口は、組織が思っているより多い。本件で PayNow が事後に IP 許可リストを「発票照会 API とサンプルダウンロード」の両方に設定していることは、その入口の多さを物語っている。

三つ目は、保持期間と照会可能範囲を分けていなかったことである。読み出された発票の発行期間は 2019 年から 2026 年 11 月。電子発票は税務上の証憑であり、法令上の保存義務がある。だが「保存すること」と「オンラインの照会 API から即時に読めること」は別の要件である。直近の一定期間だけを照会対象にして、それ以前を別保管にしていれば、一度の侵害で 7 年分が出ることはなかった。

日本の読者にとっての当てはまりは明確である。電子インボイス制度の下で、請求書・領収書・取引明細の発行と保管を SaaS に委託し、API で連携している組織は多い。そこに置かれるのは「誰が何をいくらで買ったか」であり、流出すれば本件と同じく自社の名義で詐欺が走る。確認すべきは 3 点——鍵の所持が全件照会と等価になっていないか、同じデータに届く公開面を全部把握しているか、オンラインで照会できる期間を必要な範囲に絞っているか。

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
第 2 段階（11月20日）で、発票照会ページおよび API を遮断した。機能した本記録の評価。発見当日に経路を止める判断は妥当である。 ただし第 1 段階（11月11日）で同じ判断を「到達可能な経路の全体」に 対して行えていれば、9 日間の継続読み出しは避けられた。
第 1 段階の発見（11月11日）から当局通報（11月13日）・加盟店への 通知開始（11月13日）までは 2 日だったが、加盟店向けの事件説明の発出は 11月23日、加盟店による対外公告は 11月24日となった。不十分本記録の評価。当局通報の速さ（72 時間以内）と、購入者への到達の 遅さが釣り合っていない。流出した情報が「取引明細」である以上、 なりすまし詐欺が来ることは予見できた。詐欺が先に届き、 加盟店が詐欺から事案を逆探知する順序になっている。
購入者への通知を、加盟店経由（加盟店が通知する／加盟店が同意すれば PayNow が代行する）という形にし、加盟店が 11月25日までに返信しない 場合は PayNow からの送付に同意したものとみなす運用にした。部分的に機能本記録の評価。みなし同意を置いた設計は、通知が止まる最悪を 避けている点で実務的である。一方、約 500 社のうち対外公告に 踏み切ったのは数社であり、購入者が「自分が対象か」を確かめる 手段は事実上ない。影響を受けた商家の一覧、または購入者が 自分の発票を照会して該当を確認できる仕組みが必要だった。
影響を受けた約 500 商家の一覧を公表しなかった。不十分本記録の評価。流出データは「どの店で何を買ったか」であり、 詐欺はその店の名義で来る。購入者が警戒すべき店名を知れないことは、 詐欺への備えを直接弱める。商家名を出せないなら、購入者自身が キャリア情報や発票番号で該当を確認できる照会窓口を用意すべきだった。
CISO・経営層への示唆
  • 取引明細の流出は「連絡先の流出」より重いと社内で位置づける。
    本件で流出したのは購入者の氏名・連絡先に加えて、購入商品と取引金額、 注文番号である。なりすまし詐欺に使えば購入者は相手を本物と判断する。 実際、事案の説明より先に詐欺メッセージが購入者に届いた。
    取るべき行動 インシデントの重大度判定に「流出データで本人が検証可能な事実 （実際の注文内容・金額・日付）を語れるか」という軸を入れる。 該当する場合は、当局通報と同じ速度で顧客への注意喚起を出す手順にする。
  • 電子インボイス・請求書・領収書の発行を SaaS に委託しているなら、 それは連絡先の委託ではなく取引明細の委託だと認識する。
    本件で侵害されたのは決済そのものではなく、発票（インボイス）の 加値サービスだった。資金決済情報は流出していないが、 取引の中身は 7 年分出ている。
    取るべき行動 委託先の棚卸しで「取引明細を保持する委託先」を独立した区分として 管理し、保持期間・照会可能範囲・API の認可設計を確認項目に入れる。 決済事業者と同じ水準の点検対象にする。
  • 委託先の侵害を、自社名義のなりすまし連絡の急増から検知できる体制を作る。
    一事製菓は 11月22日に自社をかたる詐欺メッセージを確認し、 翌日プラットフォームへ照会して事案の発生元が PayNow だと特定した。 委託先からの報告を待つのではなく、外形的な異常から到達している。
    取るべき行動 自社名義のなりすまし連絡の申告窓口を顧客向けに明示し、 申告件数を日次で集計する。平常比の急増を「委託先の侵害を疑う」 トリガーとして、委託先への照会手順につなげる。
  • 委託先の侵害時に、顧客が「自分が対象か」を確かめられる手段を用意する。
    本件では約 500 商家が影響を受けたが一覧は公表されず、対外公告を 出したのは数社だった。購入者は警戒すべき店名を知れない。 通知も加盟店経由であり、到達は加盟店の対応能力に依存する。
    取るべき行動 委託契約に「侵害時に自社が顧客へ直接通知できること」と、 通知に必要なデータ（対象者の範囲・該当の判定方法）を委託先から 受け取れることを条項として入れる。自社が影響を受けたなら、 加盟店の一社として公告を出す判断基準も決めておく。
  • 当局通報の速さと、顧客への到達の速さを別の指標として管理する。
    PayNow は両段階とも知得から 72 時間以内に当局通報を完了した。 一方、加盟店向け説明の発出は第 1 段階の発見から 12 日後で、 その前に詐欺が購入者へ届いていた。
    取るべき行動 インシデント対応規程に「当局通報」「委託元・取引先への通知」 「エンドユーザーへの注意喚起」の 3 つを別の時限目標として書き、 訓練で各々の所要時間を実測する。
セキュリティ技術者への示唆
  • API 鍵を認証の手段としてだけ扱わず、認可の境界として設計する。
    攻撃者は鍵を取得した後、多数のプロキシ IP から発票データを一括で 読み出した。鍵の正当性だけを見る API は、鍵が漏れた瞬間に 全件エクスポート機能になる。
    取るべき行動 照会系 API について、鍵ごとに「照会できるデータの範囲（自社分のみ・ 直近 N か月）」「1 回の応答件数の上限」「単位時間あたりの呼び出し上限」を サーバ側で強制する。鍵を持っていれば全件取れる経路が残っていないか、 既存 API を一本ずつ確認する。
  • 同じデータストアに到達できる公開面を全部列挙して管理する。
    本件では第 1 段階で API を塞いだ後も、加値中心システムの発票照会 ページという別経路が残り、9 日間読み出しが続いた。PayNow は事後に 「発票照会 API とサンプルダウンロード」の両方へ IP 許可リストを 設定している。入口は API だけではない。
    取るべき行動 データストア単位で「そこへ到達する公開面」の一覧（API・管理画面・ 照会ページ・ファイルダウンロード・バッチ連携）を作り、 アクセス制御の設定を一括で適用・検証できるようにする。 新しい公開面を追加したら一覧を更新する運用にする。
  • 鍵が漏れた侵害では、経路を塞ぐより先に鍵を無効化する。
    第 1 段階の対処（IP の限定・発信元の遮断・脆弱性の修補）は 発見当日に行われたが、攻撃者は鍵を持ったままだった。 発信元は多数のプロキシに分散していたため、IP の遮断では抜けられる。
    取るべき行動 封じ込め手順の第一手に「漏えいが疑われる鍵・資格情報の無効化と ローテーション」を置く。そのために、鍵を即時に無効化できる仕組みと、 無効化による影響範囲（どの連携先が止まるか）を事前に把握しておく。
  • 鍵をアプリケーションサーバの設定ファイルに置かない。
    攻撃者は発票ホストに侵入して「システム設定情報と鍵」を取得している。 ホストを取られた時点で鍵も取られる構成だった可能性が高い （鍵の保管形態は公表されていない）。
    取るべき行動 鍵管理サービス（KMS／シークレットマネージャ）から短命の資格情報を 取得する構成に移し、ホスト上の設定ファイルに長命の鍵を置かない。 鍵の参照を監査ログに記録し、通常と異なる主体・頻度での取得を警報する。
  • データの保存期間と、オンラインで照会できる期間を分ける。
    読み出された発票の発行期間は 2019 年から 2026 年 11 月に及ぶ。 税務上の保存義務はあるが、7 年分を照会 API から即時に読める状態に しておく必要があったとは限らない。
    取るべき行動 取引明細の照会 API が返せる期間を直近の一定範囲に限定し、 それ以前はオンライン照会の対象から外して別保管にする。 過去分の照会には別の認可（申請・承認・監査ログ）を要求する。
  • 発信元 IP の分散を前提に、鍵単位の総量で異常を検知する。
    攻撃者は「大量代理 IP 位址」を使って読み出した。IP ごとの閾値では 分散に抜けられる。PayNow は事後に異常アクセスの即時警報機構を 構築している。
