INC-2026-1345Zodia Custody、顧客情報が露出

Standard Chartered 傘下の機関投資家向け暗号資産カストディ事業者 **Zodia Custody** が、2026年11月26日に侵害を公表した—— **11月23日にプラットフォームへの探索（probe）の試みを検知し、 予防措置として B2B API を一時停止して追加の対策を施したうえで再開、 翌24日の継続的な監視で「権限の無い第三者が限定的な顧客情報へ アクセスしていた」ことを特定した。** **露出したのは公開済みの組織情報と、少数の顧客・従業員の 業務上の連絡先氏名およびメールアドレスである。** **「現時点の調査では権限の無い取引は無い」としている。** **公表は報道が先行した後に出されたもので（声明の冒頭が 「報道を認識している」から始まる）、影響件数・攻撃者・侵入経路は いずれも公表されていない。**

B2B API の停止は、顧客側の自動処理を直接止める業務・事業への影響

Zodia Custody が停止したのは B2B API である（出典1）。これは人が画面を操作する経路ではなく、顧客（機関投資家・取引所・資産運用者）のシステムがプログラムから呼び出す経路である（本記録の整理）。

したがって停止の影響は、「画面が使えない」ではなく「自動処理が止まる」という形で出る（本記録の評価）。カストディの API が止まれば、顧客側では入出庫の指示・残高の照会・取引所との決済の連携といった処理が止まりうる。

ところが、停止していた時間は公表されていない（出典1。本記録の確認）。声明にあるのは「一時的に（temporarily）」という語だけである。

本記録はこれを、カストディ・決済・清算のような「他社の業務が自社の稼働時間に乗っている」事業者の公表における欠けとして記録する（本記録の評価）。読者（日本の CISO）にとって要るのは、①いつから止まったか、②いつ戻ったか、③止まっている間に受け付けた指示はどう扱われたか、の3点である。 本件ではいずれも示されていない。

なお、停止そのものは予防措置として行われたと明記されている（出典1。原文英語: "As a precaution"）——本記録はこの判断を妥当なものとして評価する（後述の decisions 参照）。問題は判断ではなく、その後の説明の粒度である。

  • 顧客名と担当者アドレスの組は、それ自体が標的型フィッシングの材料になる
    **本件で露出したのは「公開済みの組織情報」と 「業務上の連絡先氏名とメールアドレス」である**（出典1）。 **単体では公開情報に近いが、 「この組織が当社の顧客である」という事実と組み合わさった時点で 公開情報ではなくなる**（本記録の整理）。 **報道でも、機関投資家を狙ったフィッシングのリスクが高まるとの 指摘が紹介されている**（出典2・3 経由）。 **カストディ事業者を装って担当者に連絡する攻撃は、 宛名・宛先・文脈がそろった状態で始められる。**
    取るべき行動 **自社が顧客・取引先の情報を預かる側である場合、 露出が起きたときの顧客への連絡に 「当社を装う連絡への注意」と 「当社からの正規の連絡経路・確認方法」を含める雛形を用意する。** **自社が顧客の側である場合、 取引先（カストディ・決済・SaaS）の侵害の報を受けたら、 その事業者を装うメールへの注意を担当部署へ即日出す。** **あわせて、資金移動・振込先変更の指示を メールだけで受け付けない手順を確認する。**
  • 「予防措置として先に止める」判断は速さで評価できるが、止めた時間を公表しないと評価は止まる
    **Zodia Custody は、原因が特定されていない段階で B2B API を予防的に停止し、 追加の対策を施してから復旧した**（出典1）。 **検知と停止は同じ日である**（本記録の算出）。 **この順序は評価できる**（本記録の評価）。 **一方で、停止していた時間は公表されていない** ——**B2B API はプログラムから呼ばれる経路であり、 停止は顧客側の自動処理を直接止めるため、 顧客にとっては停止時間が影響の大きさそのものである。**
    取るべき行動 **自社が他社の業務を支える API・基盤を提供している場合、 停止を伴う対応の公表の雛形に ①停止の開始時刻、②復旧時刻、 ③停止中に受け付けた指示の扱い、の3欄を作る。** **判断の速さだけを書いて時間を書かない公表は、 顧客が自分の影響を計算できない。**
  • 公表が報道の後になった場合、その事実は声明に残る
    **Zodia Custody の声明は 「最近のセキュリティインシデントに関する報道を認識している」 から始まっている**（出典1。原文英語）。 **検知は11月23日、不正アクセスの特定は11月24日、 声明は11月26日である**（出典1）。 **本記録の評価として、この第1文は 「顧客には連絡したが、市場への説明は後追いだった」ことを 自ら記録に残す形になっている。** **あわせて、声明のページには掲載日の表示が無い** （本記録が2026年11月27日に取得して確認した）。
    取るべき行動 **インシデントの公表手順に、 「報道が先に出た場合」の分岐を入れる。** **具体的には、①顧客・取引先への個別連絡と ②対外的な声明の公表を別のタイムラインとして持ち、 それぞれの目標時刻を決めておく。** **また、声明のページに掲載日時と改訂履歴を必ず表示する** ——**日付の無い声明は、後から経緯を検証できない。**
セキュリティ技術者への示唆
  • 探索の検知は「侵入されたか」を教えない——データ側からの確認が別に要る
    **本件では11月23日に探索の試みを検知し、 11月24日に継続的な監視によって 「権限の無い第三者がアクセスしていた」ことを特定している**（出典1）。 **つまり検知の時点では、アクセスが成立していたことは 分かっていなかった**（本記録の読み）。 **探索の遮断で終わらせていれば、 露出の事実に到達していなかった可能性がある**（本記録の評価）。
    取るべき行動 **外部からの探索・認証試行を検知したときの手順に、 「その相手の識別子（IP・API キー・セッション・利用者）で、 どのデータへの参照が成立したか」をアクセス記録から 洗い出す工程を明示的に入れる。** **そのためにアクセス記録に、 ①呼び出し元の識別、②応答に含めたレコードの範囲、 ③件数が残っているかを確認する。** **残っていなければ、それ自体が是正の対象である。**
  • B2B API の応答に顧客の識別情報と担当者情報を載せる設計は、認可の破れ1つで台帳が出る
    **本件の露出内容が API の応答由来かは公表されていない** （本記録の留保。出典1）。 **ただし、露出したものが 「組織情報」と「業務上の連絡先氏名・メールアドレス」である点は 設計上の論点を示している**（本記録の評価）—— **これらはテナント（顧客）をまたいで1つの台帳に載りやすい情報である。** **テナント境界の検査が1か所抜けると、 個別のレコードではなく一覧が出る。**
    取るべき行動 **外部公開 API の各エンドポイントについて、 応答に含まれる項目を棚卸しし、 「呼び出した顧客の業務に必要のない他顧客の識別情報・担当者情報」を 削る。** **一覧を返すエンドポイントでは、 テナント境界の検査を取得条件（クエリ）側だけでなく 応答の組み立て側にも置く（二重化する）。** **テスト項目として「別テナントの識別子を指定した場合」 「識別子を省略した場合」の2つを必ず持つ。**
  • 「件数が公表されない侵害」では、自社が対象かを待つしかない——だから受け手側の備えが要る
    **本件の影響範囲は「少数の顧客および従業員」とのみ示され、 件数も内訳も公表されていない**（出典1）。 **顧客は、個別の連絡を受けるまで自分が対象かを判断できない** （本記録の整理）。 **一方、露出した情報（組織名・担当者名・メールアドレス）は、 対象かどうかに関わらず 「その事業者を装う連絡」が増えることを意味する**（本記録の評価）。
    取るべき行動 **取引先の侵害の報を受けたときに実行する手順を用意する。** **最低限、①その取引先とやり取りしている自社の担当者と メールアドレスを一覧化する、 ②その取引先を装うメールの特徴（差出人ドメイン・ よく使われる件名）を担当者へ共有する、 ③当該取引先からの指示（振込先変更・鍵の再登録・ 認証情報の入力を求めるもの）を別経路で確認する規則を再確認する、 の3点を定義しておく。**
  • 「権限の無い取引は無い」は資産についての言明で、情報の悪用についての言明ではない
    **声明の文は "Based on our investigation to date, there have been no unauthorised transactions."（現時点の調査に基づけば、 権限の無い取引は発生していない）である**（出典1）。 **これは取引の台帳から確認できる事実であり、 露出した連絡先情報が悪用されたかどうかには触れていない** （本記録の整理）。 **悪用は顧客組織のメール環境で起きるため、 事業者のログには現れない**（本記録の評価）。
    取るべき行動 **自社がインシデントを公表する側のとき、 「確認できたこと」と「確認できる範囲の外にあること」を 文として分けて書く。** **自社が報を受ける側のとき、 「不正な取引は無い」という記述を 「悪用は無い」と読み替えない** ——**露出した情報を使った攻撃は、 公表した事業者の側では観測できない。**
