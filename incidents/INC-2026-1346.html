INC-2026-1346SoftwareOK 公式配布で RAT 混入

Windows 用フリーソフト **Q-Dir** と **DesktopOK** の配布元 **SoftwareOK の公式サイト**で、インストーラが差し替えられ、 Python 製の遠隔操作マルウェア（RAT）が配られた—— AhnLab ASEC が2026年11月25日に公表した。 **差し替え版は、埋め込んだ正規の実行ファイル（開発者 Nenad Hrg 氏の 有効な署名つき）を起動して利用者の疑いをそらしながら、 外部サーバから Python ランタイムごと RAT を取得して常駐させる。** **公式ダウンロードページ掲載のハッシュと、実際に配られたファイルの SHA-256 が一致しなくなっていた。** **直接ダウンロードした利用者だけでなく、すでに入れていた正規版の 「更新」でも悪性ファイルが生成された記録が確認されている。** **RAT はシェル・Python コードの実行、ファイルの送受信、画面の取得、 システム情報の収集を行い、1,206 個のセキュリティ製品のプロセス名と 照合して稼働中の製品を C2 へ送る。** **一方、SoftwareOK 側は本記録の確認時点（2026年11月27日）まで 改ざんの告知を出しておらず、更新履歴では 12.84・12.85 を 「誤検知（false-positive）への対応」と説明している。**

委託先・再委託先起因で委託元多数に波及不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）委託先・供給元起因公表されていない／不明
初報: 2026年11月25日 最終更新: 2026年11月27日

AhnLab ASEC が2026年11月25日、Windows 用のフリーソフト Q-Dir（4分割ファイルマネージャ）とDesktopOK（デスクトップのアイコン配置を保存・復元）の公式サイト SoftwareOK で配布されていたインストーラの一部が改ざんされていたことを公表しました（出典1）。

本件が「公式サイトだから安全」という前提を崩しているのは、届き方が2通りあったからです（出典1）。

  • 公式のダウンロードページから直接取得した場合
  • すでに入れていた正規版の「更新」を実行した場合 ——ASEC は、既存の正規プログラムの更新処理の最中にも悪性ファイルが生成されたログを確認したと述べています

確認された影響バージョン（出典1）。

製品 版
Q-Dir 12.85.0.0 / 12.84.0.0 / 12.83.0.0
DesktopOK 12.85.0.0 / 12.82.0.0

動きは次のとおりです（出典1）。

  1. 差し替え版のインストーラは、内部リソースとして正規の Q-Dir / DesktopOK の実行ファイルを抱えている。 その実行ファイルは公式ページ掲載の SHA-256 と一致し、開発者 Nenad Hrg 氏の有効な電子署名も確認された ——つまり本物が埋め込まれている
  2. 実行すると、正規プログラムを C:\Users\Public\[ファイル名] に作って起動する。 画面上は普通に動くため、利用者は改ざんに気づけない
  3. 同時に外部サーバから、展開用の正規 7-Zip（7zr.exe）と、Python ランタイムごと詰めた RAT のパッケージを取得する ——Python が入っていない環境でも動く
  4. C:\ProgramData\Microsoft\DeviceSync\b2 に展開し、スケジュールタスク \UPnp\MicrosoftEdge_dcntel で常駐させる
  5. RAT は C2（8.210.69[.]51:9876）と通信し、シェルコマンドと Python コードの実行、ファイルの送受信、画面の取得、OS・システム情報の収集を行う
  6. さらに、稼働中プロセスを内蔵の 1,206 個のセキュリティ製品プロセス名の一覧と照合し、どの製品が動いているかを C2 へ送る

本記録がもう1つ記録に残すのは、配布元側の説明です（本記録の確認）。SoftwareOK のサイトには、本記録の確認時点（2026年11月27日）まで改ざんについての告知が見当たりません。 一方、Q-Dir の更新履歴には、ASEC が悪性と判定した12.84（11月13日）と 12.85（11月21日）が「MS Windows での誤検知（false-positive virus alert）への対応」として記載され、12.84 には「実際にはウイルスは存在しなかったが、セキュリティ上の理由だけで実施した」と明記されています（出典2。原文英語）。ベンダーの分析と配布元の説明が、正面から食い違っています。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下の各段階は、AhnLab ASEC の分析レポート（出典1）に基づく事実である。** **各版の公開日は本記録が配布元の更新履歴（出典2）で確認したもので、 「その日から悪性版が配られた」という意味ではない**（本記録の明記）。 **検知の機会と対策についての注記は本記録の評価である。** **なお、正規インストーラが悪性ファイルへ置き換えられた原因と経路は 特定されていないため、その段階は chain に置かない。**

  1. 1. 初期侵入[1] [2]
    **SoftwareOK の公式サイトで配布されていた Q-Dir / DesktopOK の インストーラの一部が、悪性ファイルを含むものへ差し替えられていた** （出典1）。 **ASEC は、公式ダウンロードページから直接取得した場合だけでなく、 すでに導入していた正規プログラムの更新処理の最中にも 悪性ファイルが生成されたログを確認したと述べている。** **確認された版は Q-Dir 12.85.0.0・12.84.0.0・12.83.0.0 と DesktopOK 12.85.0.0・12.82.0.0 の5版で、 ASEC は「これまでに確認された版」であり網羅ではないとしている。** **置き換えの原因と経路は特定されていない。**
  2. 2. 検知回避[1]
    **悪性インストーラは、内部リソースとして 正規の Q-Dir / DesktopOK の実行ファイルを抱えている**（出典1）。 **埋め込まれた正規実行ファイルは公式ページ掲載の SHA-256 と一致し、 開発者 Nenad Hrg 氏名義の有効な電子署名も確認された。** **悪性インストーラは、この正規プログラムを `C:\Users\Public\[ファイル名]` に作って起動するため、 利用者の画面では期待どおりに動作する。**
  3. 3. 実行[1]
    **悪性インストーラは外部サーバから2つのファイルを取得する**（出典1）。 **`hxxps://mail.c1a2[.]top/dl/7zr.exe`（展開用の正規 7-Zip ツール）と、 `hxxps://mail.c1a2[.]top/dl/dsv2_py39_agent.7z` （Python ランタイム環境と RAT を含むパッケージ）である。** **RAT パッケージは既定で `C:\ProgramData\Microsoft\DeviceSync\b2` に展開され、 そのパスが使えない場合は `C:\ProgramData\DeviceSync\b2` のような代替が選ばれる。** **パッケージには Python ランタイムが含まれるため、 Python が導入されていない端末でも悪性スクリプトを実行できる。**
  4. 4. 永続化[1]
    **マルウェアは スケジュールタスク `\UPnp\MicrosoftEdge_dcntel` を登録して常駐する** （出典1）。 **登録されたタスクは `"[導入先]\py39\pythonw.exe" "[導入先]\py39\agent\py_client_dsv2.py"` を実行する。**
  5. 5. C2通信[1]
    **導入された Python RAT は C2 サーバ `8.210.69[.]51:9876` と通信し、 攻撃者が送るコマンドを実行する**（出典1）。 **確認された主な機能は、シェルコマンドの実行、Python コードの実行、 ファイルのアップロードとダウンロード、利用者の画面の取得、 OS・システム情報の収集である。**
  6. 6. 内部探索[1] [2]
    **RAT は稼働中プロセスの一覧を取得し、 内蔵している 1,206 個のセキュリティ製品プロセス名の一覧と照合して、 どの製品が動いているかを判定し、結果を C2 へ送る**（出典1）。 **一覧には韓国製品（AhnLab V3・ESTsecurity ALYac・ INCA Internet nProtect・Hauri ViRobot・SGA Solutions VirusChaser）と 国際的な製品（CrowdStrike Falcon・SentinelOne・Cylance・Trend Micro・ Avast・McAfee・ESET・Symantec・Kaspersky・Bitdefender・Sophos・ Fortinet・Elastic Security・Cybereason・Malwarebytes・FireEye）が含まれる。** **ASEC は、攻撃者がこの情報で感染端末のセキュリティ環境を評価し、 追加の攻撃を行うかを決めたり、検知を回避したりできると述べている。**

稼働中のセキュリティ製品を 1,206 個の一覧と照合して C2 に送る原因・手口

RAT の機能として ASEC が確認したもの（出典1）。

  • シェルコマンドの実行
  • Python コードの実行
  • ファイルのアップロードとダウンロード
  • 利用者の画面の取得（スクリーンショット）
  • OS・システム情報の収集

これに加えて、本記録が本件の特徴として記録するのが次の挙動である（出典1）。

RAT は稼働中プロセスの一覧を取得し、内蔵している 1,206 個のセキュリティ製品プロセス名の一覧と照合して、どの製品が動いているかを判定し、その結果を C2 へ送る。

ASEC は、攻撃者がこの情報を使って感染端末のセキュリティ環境を評価し、追加の攻撃を行うかを決めたり、セキュリティ製品による検知を回避したりできると述べている（出典1）。

本記録の評価として、この挙動には2つの意味がある。

  1. 攻撃者から見た「選別」の機能である ——どの端末に次の段を落とすかを決められる。 逆に言えば、EDR が入っている端末では何も起こらない（＝痕跡が残らない）可能性がある。

防御側への含意は単純ではない（本記録の評価）。「セキュリティ製品が入っていれば攻撃されない」のではなく、「入っていることを攻撃者が知る」のが本件の構造である。 したがって、製品の存在そのものではなく、製品が検知する挙動（スケジュールタスクの登録、ProgramData 配下からの pythonw.exe の実行、未知の宛先への通信）を見ることが必要になる。

公式ページのハッシュと、実際に配られたファイルが一致しなくなっていた発覚の端緒

ASEC が改ざんを確認した方法は、ハッシュの不一致である（出典1）。

分析の時点で、公式 SoftwareOK サイトからダウンロードした一部のインストーラの SHA-256 が、ダウンロードページに掲載されていたハッシュと一致しなかった（出典1）。さらに、実際に配られたファイルには、正規プログラムの機能とは無関係な「追加ファイルのダウンロードと自動実行」のコードが含まれていた。

本記録はこの点を、本件の唯一の検知の足場として記録する（本記録の評価）。

なぜ足場になったか—— ハッシュの掲載場所と、ファイルの置き場所が別だったためである（本記録の整理）。ダウンロードページに掲載されたハッシュは書き換えられておらず、配布ファイルだけが差し替えられた。 だから照合によって差が出た。

これは、配布元が掲載したハッシュと配布物を一緒に書き換えられる形の事案（例: 同じリリースにchecksums.txt を同梱していた OVHcloud の事例・INC-2026-0612）とは対照的である（本記録の整理）。本件では掲載ハッシュが生き残ったことが検知を可能にした。

ただし、この足場は利用者の側で自動的には働かない（本記録の評価）。ハッシュの照合は手作業であり、「公式サイトから落としたのだから大丈夫」という前提で省略されるのが普通である。 さらに本件では更新機能経由でも悪性ファイルが生成されており（出典1）、更新の場合は利用者がハッシュを見る機会すら無い。

ASEC が配布元に求めている対策も、ここに向いている（出典1。原文英語）。「ビルドから配布までの全工程でコード署名とハッシュ検証を行い、利用者に届く最終ファイルの完全性が保たれているかを継続的に検証すること」、そして「公式ページに掲載したハッシュと実際にダウンロードされるファイルのハッシュが一致するかを定期的に検証し、配布ファイルの異常な変更とダウンロード要求を監視すること」である。

配布元は 12.84・12.85 を「誤検知への対応」と説明しており、改ざんの告知は出ていない未確定事項

緩和策
手順: **Q-Dir / DesktopOK を使っている利用者は、 既存のプログラムを削除し、 安全と検証された最新版を再インストールする。 再インストール前に、公式ダウンロードページに掲載された SHA-256 と 実際にダウンロードしたファイルのハッシュが一致することを確認する** （出典1。ASEC の勧告）。　副作用: **「安全と検証された最新版」がどれかは示されていない** （本記録の確認）〈重要〉—— **ASEC は検証済みの版を特定しておらず、 配布元も改ざんの告知を出していない**（出典2）。 **したがってこの手順は、 「今ダウンロードできるものは安全である」という 確認されていない前提に依存する。** **また、ハッシュの照合は手作業であり、 更新機能経由では利用者が照合する機会が無い。**
手順: **削除と再インストールだけでは、 すでに導入された Python RAT は除去されない可能性があるため、 疑わしい Python 実行環境・スケジュールタスク・関連ファイル・ 外部通信の痕跡を確認し、 エンジンを最新に更新してから全体スキャンを行う** （出典1。ASEC の勧告）。　副作用: **Python を正規に使っている開発端末では、 「疑わしい Python 実行環境」の判定が難しくなる** （本記録の評価）—— **判定の手がかりを「Python があるか」ではなく 「`ProgramData` 配下に Python 一式が展開されているか」 「`pythonw.exe` がスケジュールタスクから起動されているか」に 置く必要がある。**
手順: **感染の指標が確認された場合、 当該端末をネットワークから隔離し、 追加のマルウェアの実行やデータの流出を含む 侵害の範囲を評価する**（出典1。ASEC の勧告）。　副作用: **隔離は当該端末での業務を止める**（本記録の評価）。 **また、本件の RAT はシェルと Python の実行、 ファイルの送受信、画面の取得が可能であるため、 「何が行われたか」の評価には端末のログが要る** ——**先に初期化すると評価ができなくなる。**
手順: **配布元・ソフトウェア開発者は、ビルドから配布までの全工程で コード署名とハッシュ検証を行い、 利用者に届く最終ファイルの完全性が保たれているかを継続的に検証する。 公式ページに掲載したハッシュと実際にダウンロードされるファイルの ハッシュが一致するかを定期的に検証し、 配布ファイルの異常な変更とダウンロード要求を監視する** （出典1。ASEC の勧告）。　副作用: **個人または小規模な開発者には運用の負担が重い** （本記録の評価）〈重要〉—— **本件の配布元は個人開発者が運営するフリーソフトのサイトである。** **「配布後のファイルを定期的に照合する」仕組みを持たない配布元が 多数存在することが、本件の構造的な前提である。**
手順: **本記録として付け加える対策**—— **配布元が「誤検知だった」と説明しているソフトについて、 その説明だけを根拠にセキュリティ製品の警告を 除外設定に入れないこと**（本記録の評価）。　副作用: **誤検知が実際に起きることも事実であり、 除外設定を一律に禁じると業務が止まる**（本記録の評価）。 **したがって規則は「禁止」ではなく 「除外設定の申請に、配布元の説明以外の根拠 （検体の提出結果・複数エンジンでの確認）を要求する」という形にする。**

    **本件の配布元は、公式サイトからフリーソフトを提供する 個人開発者である**（出典1・2）。 **契約関係にある委託元の名簿が存在しないため、 「影響を受けた利用者」も「影響が無かった利用者」も 配布元が特定して示すことができない**（本記録の整理）。 **実際、影響期間・ダウンロード件数・被害件数は いずれも公表されていない**（出典1。本記録の確認）。 **ASEC が「版が一覧に一致しなくてもリスクを認識すべき」と 書いているのは、この構造の結果と読める**（本記録の読み）。

  • 「どのセキュリティ製品が動いているか」が攻撃者に送られる前提で設計する
    **本件の RAT は、1,206 個のセキュリティ製品プロセス名と照合して 稼働製品を判定し、C2 へ送る**（出典1）。 **ASEC は、攻撃者がこの情報で感染端末のセキュリティ環境を評価し、 追加の攻撃を行うかを決めたり検知を回避したりできると述べている。** **つまり防御の構成そのものが、攻撃者の意思決定の入力になる** （本記録の整理）—— **EDR が入っている端末では「次の段が来ない」ため、 痕跡も残らない可能性がある**（本記録の評価）。
    取るべき行動 **「製品を入れていること」を防御の到達点に置かない。** **検知の設計を、製品の存在ではなく 挙動（スケジュールタスクの新規登録、 利用者が書き込める場所からの実行、 インタープリタの外部通信）で定義し、 その挙動が実際に警報まで届くかを定期的に試す。** **あわせて、攻撃が「選別」で止まった端末には 痕跡が残らないことを前提に、 調査の範囲を「警報が出た端末」に限定しない。**
セキュリティ技術者への示唆
  • 掲載ハッシュと配布物の置き場所が別だったことが、本件の唯一の検知の足場になった
    **ASEC が改ざんを確認したのは、 公式ダウンロードページ掲載の SHA-256 と 実際に配られたファイルのハッシュが一致しなかったためである** （出典1）。 **掲載ハッシュは書き換えられていなかった** ——**だから照合に意味が残った**（本記録の整理）。 **これは、ハッシュ一覧を配布物と同じ場所に同梱していた事案 （INC-2026-0612）とは逆の結果である。**
    取るべき行動 **自社が外部バイナリを取り込む経路について、 検証に使うハッシュを「配布元から毎回取り直す」のではなく、 自社の管理下（社内リポジトリ・CI の設定）に固定する。** **自社が配布する側である場合は、 掲載ハッシュと配布ファイルを異なる権限境界に置き、 両者が一致するかを定期的に自動照合する （ASEC が配布元向けに挙げている対策と同じ）。**
  • 正規の署名と正規のハッシュが「内側のファイル」に対して一致していても、外側は偽物でありうる
    **本件の悪性インストーラは、 公式ハッシュと一致し有効な署名を持つ正規実行ファイルを 内部リソースとして抱えている**（出典1）。 **署名鍵が盗まれたという記述は無い** ——**つまり「署名の偽造」ではなく「正規物の同梱」である** （本記録の整理）。 **したがって、埋め込まれたファイルの署名やハッシュを確認しても、 インストーラ全体の真正性は分からない。**
    取るべき行動 **検証の対象を「実行されるバイナリ」ではなく 「ダウンロードしたファイルそのもの（インストーラ）」に置く。** **アプリケーション制御（WDAC / AppLocker）の規則も、 内側の署名に依存した許可ではなく、 配布経路（社内リポジトリから配られたか）で判定する形に寄せる。**
  • 名前で「怪しいか」を判定する運用は、本件を見逃す
    **本件の展開先は `C:\ProgramData\Microsoft\DeviceSync\b2`、 スケジュールタスク名は `\UPnp\MicrosoftEdge_dcntel` である**（出典1）。 **どちらも Windows の正規の機能に見える名前が選ばれている** （本記録の評価）。 **一覧を目で見て「見慣れないもの」を探す運用では、 これらは通過する。**
    取るべき行動 **スケジュールタスクの判定基準を、名前ではなく ①いつ登録されたか、②どのプロセスが登録したか、 ③実行対象のパスがどこか、に置く。** **特に「利用者が書き込める場所 （`ProgramData`・`Users\Public`・`AppData`）配下の インタープリタを実行するタスク」を抽出する検索を用意しておく。** **端末の既知のタスク一覧を基準として保存し、差分を定期的に確認する。**
  • ランタイム同梱の RAT は、端末側の前提（Python が無い）を無効にする
    **本件の RAT パッケージには Python ランタイムが同梱されており、 Python が導入されていない端末でも悪性スクリプトを実行できる** （出典1）。 **展開に使われるのも正規の 7-Zip（`7zr.exe`）である** ——**持ち込まれるものはすべて正規のツールと、 その上で動くスクリプトである**（本記録の整理）。
    取るべき行動 **「この端末には Python（または Node.js）が入っていないから安全」という 前提を点検の根拠から外す。** **代わりに、`ProgramData`・`AppData` 配下に インタープリタの実行ファイルが存在するかを探す検索を用意する。** **出口通信の点検も、宛先の一覧ではなく プロセス単位（どの実行ファイルが外に出ているか）で行う ——C2 は変更されるが、構造は変わりにくい。**
