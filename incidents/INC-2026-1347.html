ローダーの隠れ場所は2通りです（出典1）。

  • utils という小さな自作パッケージの中（session.py・net.py・transport.py など、HTTP クライアントに見える名前が選ばれている）
  • conftest.py（12件） ——pytest はテストの収集時にこれを自動で読み込むため、import の行を仕込む必要がありません

動作は次のとおりです（出典1）。

  1. 開発者が pytest を実行する、または utils を import するアプリを起動する
  2. ローダーが Ethplorer の公開 API（API キーは freekey）と公開 RPC（ethereum.publicnode.com）を使い、ウォレット 0x3b15…ceBC6 が自分宛てに送った最新の取引を取得する
  3. その取引の input データを16進からテキストに戻し、一時的な .js ファイルとして node で実行する
  4. その JavaScript が2つ目のウォレット 0x1eEf…CEF3 を読んでC2 の IP を得る
  5. C2 から /0x/cls と /0x/ls を取得し、XOR で復号して実行する
  6. 最新のビルドでは、次段を node -i の標準入力に流すため、プロセスの引数にコードが現れない

本記録が本件の要点と見るのは3点です。

1つは、依存関係の検査に映らないことです（出典1。本記録の整理）。ローダーは標準ライブラリだけを使い、パッケージとしても配られていません。 requirements.txt や SBOM を見ても、何も出てきません。

2つめは、外側の try がすべてのエラーを握りつぶすことです（出典1）。Node.js が入っていない環境では何も起きず、何も表示されません ——失敗したことすら分かりません。

依存関係の検査に映らない——標準ライブラリだけの58行で、パッケージとしては配られていない原因・手口

本件のローダーは、サプライチェーン攻撃の典型とは置き方が違う（本記録の整理）。

典型（パッケージを汚染する形）と本件の違い（出典1に基づく）。

つまり、requirements.txt を見ても、ロックファイルを見ても、SBOM を作っても、何も出てこない（本記録の評価）。ローダーは標準ライブラリだけを使う58行の Python であり、依存関係としては存在しないからである。

隠れ場所の選び方にも意図が出ている（出典1）。

  • utils という小さな自作パッケージの中 ——ファイル名は session.py・net.py・transport.py など、HTTP クライアントに見えるものが選ばれている
  • conftest.py（12件） ——pytest がテストの収集時に自動で読み込むため、import の行を仕込む必要がない

後者は件数が少ないが、確実に動く（本記録の評価）。pytest を走らせるだけで、何も import しなくてもローダーが動く。 CI でテストを回す運用では、人の操作を待たずに実行される。

そして、動かなかったときも何も起きない（出典1）。ローダーの外側の try がすべてのエラーを握りつぶすため、Node.js が入っていない環境では何も表示されない。 「失敗したこと」すら記録に残らない（本記録の整理）。

次段のコードをブロックチェーンの取引データに置く——C2 を替えるのに配布をやり直さない原因・手口

本件の第2段は、ブロックチェーンの取引データから読み込まれる（出典1）。

流れ（出典1）。

  1. ローダーが Ethplorer の公開 API（API キーは freekey）と公開 RPC（ethereum.publicnode.com）を使い、ウォレット 0x3b1574417524c11a7403c4b232CAcBb320CceBC6 が自分宛てに送った最新の取引を取得する
  2. その取引の input データを16進からテキストに戻し、一時的な .js ファイルとして node で実行する
  3. その JavaScript が2つ目のウォレット0x1eEf0849EDa15d87f64e51C73C8442Cf3c8bCEF3 を読み、C2 の IP を得る
  4. C2 から /0x/cls と /0x/ls を取得し、XOR で復号して実行する
  5. 最新のビルドでは、次段を node -i の標準入力に流すため、プロセスの引数にコードが現れない

この構造が攻撃者に与えているもの（本記録の整理）。

  • 配布をやり直さずに次段を差し替えられる ——ウォレットに新しい取引を1件送るだけでよい。 SafeDep は、10月24日から11月11日までに8件の自分宛て取引（試験・不正なデータ・JavaScript のビルド4種）が送られたことを示している（出典1）
  • C2 を替えるのも取引1件で済む ——C2 は 166.88.134[.]75（9月4日〜12日）→ 103.179.143[.]219（10月14日〜16日）→ 95.135.181[.]151（10月16日〜11月12日）→ 95.135.181[.]84（11月12日〜現行）と推移している（出典1）
  • 取り下げられない ——ブロックチェーン上のデータは削除できない。 前回の仕組み（送り先アドレスに C2 の IP を埋め込む形）から、今回は input データに JavaScript 本体を置く形へ変わっている（出典1・2）

防御側から見た含意は、宛先による遮断が効きにくいことである（本記録の評価）。第1段の通信先は api.ethplorer.io・ethereum.publicnode.com・eth.blockscout.com という、正当な用途もある公開サービスである（出典1）。これらを一律に遮断できる組織は多くない。

したがって見るべきは宛先ではなく、「どのプロセスがそこへ出ているか」である（本記録の評価）。Python のテスト実行がブロックチェーンの API を呼び、その直後に node が起動する——この並びは、暗号資産を扱う開発でなければ説明がつかない。

  • `conftest.py` は import なしで動く——pytest がテスト収集時に読むため
    **本件では12件のローダーが `conftest.py` に置かれていた**（出典1）。 **pytest はテストの収集時に `conftest.py` を自動で読み込むため、 アプリ側に import の行を仕込む必要がない**（本記録の整理）。 **SafeDep は 「`conftest.py` のローダーは、そのフォルダで `pytest` が 走るたびに動く」と述べている。** **一方、`utils` パッケージに置かれたものは Python が `utils` を見つけられる場合にしか動かず、 検証した3件では起動コマンドが `ModuleNotFoundError` で失敗していた。**
    取るべき行動 **外部リポジトリを取り込む前の確認項目に、 `conftest.py` と `sitecustomize.py`・`usercustomize.py`・ `__init__.py` といった 「暗黙に読み込まれるファイル」の内容確認を入れる。** **CI では、テストの実行をネットワークを絞った環境で行い、 外部への通信を既定で拒否する。** **`ModuleNotFoundError` を見て import のパスを直す作業も 実行の引き金になる**——**エラーの修正を 「とりあえず動かす」で済ませない。**
  • ブロックチェーンに次段を置かれると、宛先の一覧による防御が効かない
    **第1段の通信先は `api.ethplorer.io`・ `ethereum.publicnode.com`・`eth.blockscout.com` という 正当な用途もある公開サービスである**（出典1）。 **さらに C2 は2か月半で5つ変わっている**（出典1） ——**`166.88.134[.]75` → `103.179.143[.]219` → `95.135.181[.]151` → `95.135.181[.]84`。** **C2 を替えるのに必要なのは、ウォレットへ取引を1件送ることだけで、 配布済みのコードは変えなくてよい**（出典2。本記録の整理）。
    取るべき行動 **出口通信の点検を、宛先の一覧ではなく プロセス単位（どの実行ファイルが外に出ているか）で設計する。** **特に `python`・`pythonw`・`node` の外部通信を抽出できる状態にする。** **暗号資産を扱わない開発環境では、 ブロックチェーンの公開 API・RPC への到達を 許可一覧の外に置くことを検討する。** **IP の遮断は一時的な効果しかないことを前提に、 構造（インタープリタの外部通信）で見る。**
  • Python プロセスが `node` を起動する並びは、強い検知の手がかりになる
    **本件のローダーは、復号した JavaScript を 一時ファイルに書いて `node` で実行する**（出典1）。 **最新のビルドでは次段を `node -i` の標準入力に流すため、 プロセスの引数にはコードが現れない。** **しかし「`node` が起動した」という事実自体は残る** （本記録の評価） ——**Python のテスト実行から Node.js が立ち上がる並びは、 通常の開発では説明がつきにくい。**
    取るべき行動 **開発端末・CI のプロセス記録で、 「Python を親として `node` が起動する」事象を抽出できるようにする。** **あわせて、`node -i`（対話モード）の起動と、 一時ディレクトリ配下の `.js` ファイルの実行を点検の対象にする。** **引数に現れないことを前提に、 親子関係と起動元のパスで判定を組む。**
  • 失敗しても何も残らない設計なので、「動いていない」ことは証明できない
    **ローダーの外側の `try` がすべてのエラーを握りつぶすため、 Node.js が入っていない環境では何も表示されない**（出典1）。 **SafeDep が検証した3件の例でも、 起動コマンドの多くが import エラーで失敗していたが、 その失敗はログに残っていない**（本記録の整理）。 **したがって、影響を受けた可能性のある環境について 「実行されていない」と結論づける材料が無い**（本記録の評価）。
    取るべき行動 **「実行されたかどうか」を後から判定するために、 開発端末・CI でプロセスの起動と外部通信の記録を 一定期間保持する。** **保持していない環境については、 影響の判定ができないことを前提に、 秘密情報の入れ替えの範囲を広く取る。** **SafeDep の勧告（実行された環境は侵害されたものとして扱い、 秘密情報・ブラウザの認証情報・ウォレット、 および GitHub のトークンと SSH 鍵を入れ替える）を 手順として事前に用意する。**
