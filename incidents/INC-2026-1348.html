INC-2026-1348電子政府基盤DIGITにSQLi

インドが「デジタル公共財」として10か国へ無償提供している電子政府基盤 DIGIT の 利用者・権限管理サービスに認証不要の SQL インジェクションが見つかり、 2026年11月25日に CERT-In が勧告（CIVN-2026-0570・CVE-2026-136706）を出した—— 修正は11月12日に「query builder のリファクタリング」として静かに入っており、 リリースノートにも PR の表題にも脆弱性である旨の記載が無い

脆弱性初報のみ有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備
初報: 2026年11月25日（CERT-In の勧告 CIVN-2026-0570） 最終更新: 2026年11月27日（本記録の作成。GitHub 上の修正を直接確認した時点）

インドの CERT-In は2026年11月25日、電子政府基盤 DIGIT のSQL インジェクション脆弱性について勧告 CIVN-2026-0570 を発出した（出典1。本記録が直接取得）。CVE-2026-136706。影響を受けるのは DIGIT Core v2.9 で、対処は v2.9.3 への更新である。深刻度の表示は「HIGH」。報告者は Sarthak Chauhan 氏（出典1）。

欠陥は「User and Access Control Service」の構成要素にある（出典1）。認証されていないリモートの攻撃者が、該当する API の端点へ細工した入力を送ることで、任意の SQL クエリを実行でき、データベースの情報の不正な開示・改変・削除に至りうる（出典1。原文英語。本記録が訳した）。認証が要らない点が本件の重さの中心である（本記録の評価）—— 利用者と権限を管理する部品が、認証の前に落ちる。

DIGIT の射程が問題の規模を決めている。 The Register はインドの全州・全連邦直轄地の政府と20,000を超える地方自治体が使っており、インドが「デジタル公共財」として提供した結果、モザンビーク・リベリア・セネガル・ナイジェリア・ブルンジ・エチオピア・インドネシア・ジャマイカ・スリランカの9か国でも導入が進んでいると報じた（出典4）。同紙はこれを「10か国・20億人」と表現し、CVSS は9.3だとしている（出典4）。都市・自治体単位の稼働は1,000件を超える（出典4）。Medianama は、国家都市デジタルミッションの下で DIGIT を基盤に作られた UPYOG が30の州・連邦直轄地、4,000を超える都市・町を対象にしていると報じている（出典5）。

本記録が構造上の中心と見るのは、修正の出方である（本記録の判断）〈重要〉。

本記録の作成者は GitHub 上で修正を直接辿った（出典3）—— CERT-In が対処として指す v2.9.3 は、リリースとして公開されていない。リリースの一覧（API）に v2.9.3 は無く、あるのは git のタグだけで、リリースノートの本文は空である（出典2・3。本記録の確認）〈重要〉〈差異2〉。タグが指すコミットは2026年11月12日9時39分（UTC）。その直前に取り込まれた PR #1444 の表題は「refactor(core-services): standardize query builders on bound JDBC parameters」——リファクタリングである（出典3）〈重要〉。PR の本文にも、自動生成された変更要約にも、CVE 番号も「脆弱性」の語も無い。変更要約が書いているのは「SQL のような文字列を含む値もより確実に扱えるようになった」である（出典3。原文英語。本記録が訳した）〈重要〉。

つまり修正は11月12日に入り、勧告は11月25日に出た——13日の差がある（本記録の算出）。その13日間、更新を取り込めた組織は「何から守られたのか」を知らされていない。

ただし「20億人」は影響を受けた人数ではない（本記録の明示）〈重要〉—— 導入国の人口の合計である。 実際に DIGIT に個人データを持たれている人数は公表されていない〈未確定3〉。悪用された例も、報道時点で確認されていない（出典5）〈未確定1〉。

直したのは1行ではなく「クエリの組み立て方」——そして `sort` は束縛では守れない原因・手口出典 [1] [3]

CERT-In の勧告は原因を1文で済ませている——「SQL クエリを構築する際、利用者が与えた入力の無害化が不十分であること」（出典1。原文英語。本記録が訳した）。

本記録の作成者は、修正そのものを GitHub 上で辿った（出典3）〈重要〉。

修正は PR #1444「refactor(core-services): standardize query builders on bound JDBC parameters」で、2026年11月12日7時00分（UTC）に取り込まれている（出典3）。PR 本文の説明は3点である（出典3。原文英語。本記録が訳した）。

①egov-user と egov-accesscontrol の query builder を、文字列連結から、共通の BaseQueryBuilder 契約（BaseRepository を通して束縛される getParameters()）を介したプリペアドステートメントのパラメータ束縛へ移す。

②利用者検索の sort 入力を、並べ替え可能な eg_user の列の集合に対して検証する（任意で asc／desc）。認識できない値は既定の name 順に落とす。

③query builder の単体試験を足し、触った egov-accesscontrol の試験クラスをJUnit 5 へ移す。

変更されたのは13ファイルで、本体のコードは6ファイルである（出典3）〈重要〉—— egov-accesscontrol の BaseRepository・BaseQueryBuilder・ActionFinderQueryBuilder・RoleFinderQueryBuilder・ValidateActionQueryBuilder、egov-user の UserTypeQueryBuilder。

本記録はこの修正を、技術的に筋がよいと評価する（本記録の評価）〈重要〉。

理由は②である。 パラメータ束縛は値を守るが、並べ替えの列名は SQL の構造の側に入るので、束縛では守れない（本記録の整理）〈重要〉—— ORDER BY ? は使えない。 だから sort には許可リストが要る。 この2つを同じ PR で揃えていることが、「1か所を塞いだ」のではなく「組み立て方を変えた」ことの証拠である（本記録の読み）。

自動生成された変更要約が書いている症状も、ここと一致する（出典3）—— 「アクセス制御の action・role 検索が、SQL のような文字列を含む値もより確実に扱えるようになった」「利用者検索のあいまい名条件がより確実に扱えるようになった」「利用者検索の並べ替えが、対応する列と方向を受け付ける。対応していない、あるいは機微な並べ替え項目はname 順に落ちる」（出典3。原文英語。本記録が訳した）。

「機微な並べ替え項目（sensitive sort fields）」という表現が残っているのは、並べ替えの列名から表の構造や機微な列の存在が読めてしまう問題も同時に塞いだことを示す（本記録の読み。断定はしない）〈重要〉。

ただし、どの API 端点が認証不要で到達できるかは、この差分からは分からない（本記録の留保）〈未確定4〉—— CERT-In も「affected API endpoint」としか書いていない（出典1）。

更新する側が自分で補うべき点を、本記録の評価として3つ挙げる。

①sort に独自の列名を渡している連携を洗う〈重要〉—— 許可リストに載っていない値は黙って name 順に落ちる（出典3）。「正しい入力に対しては振る舞いが変わらない」という説明は、「いまの入力が正しい」ことを前提にしている（本記録の評価）。

②更新の主体が自分かを確認する—— The Register は、地方自治体は通常、国や州が運営する大規模な実装を通してSaaS として DIGIT を使うと書いている（出典4）〈重要〉—— この場合、自治体が上げるのではなく、基盤の運営側が上げる。 自組織が「上げる側」なのか「上げてもらう側」なのかを先に決めないと、勧告を読んでも次の行動が決まらない（本記録の評価）。

③更新できない期間の記録を確保する（本記録の推奨）—— 該当 API のリクエストとデータベースのクエリを残す。 引数をそのまま残すと注入文字列と個人データがログに入るので、ログの保護と保持期間を同時に決める（本記録の評価）。

「デジタル公共財」は欠陥も無償で配る——日本の自治体共通基盤にそのまま重なる話評価・解釈出典 [1] [2] [3] [4] [5]

本記録が日本の読者に向けて言いたいことは1つである（本記録の判断）〈重要〉—— 共通基盤は、良い実装を一度に広げるのと同じ速さで、1つの欠陥を一度に広げる。

DIGIT はその性質がはっきり出た例である。 インドは自国向けのソフトウェアを「デジタル公共財」として他国へ渡す方針を採り、9か国が実装した（出典4）。渡したのは機能だけではない。egov-accesscontrol の query builder が文字列連結でクエリを組んでいたという実装の癖も、同じ形で9か国に渡っている（本記録の評価）〈重要〉。

日本に同じ構造がある。 自治体情報システムの標準化とガバメントクラウドは、「1つの基盤・標準準拠の実装を、多数の自治体が同じ形で使う」設計である（本記録の整理）。その利点は DIGIT と同じだが、弱点も同じである。

本記録が DIGIT の件から取り出せる論点は3つある（本記録の評価）。

①更新の主体と、知らされる主体がずれる。 自治体は SaaS として基盤を使うので、勧告を読んでも自分では上げられない（出典4から本記録が推論）〈重要〉。一方で、個人データに対する責任は自治体の側に残る。 「上げる人」と「責任を負う人」が違うなら、その間を埋める連絡の経路が要る。 本件では、eGov Foundation が導入先へ通知したかどうかが公表されていない（出典5）〈未確定2〉。

②「セキュリティ修正だけ追う」運用は、この形の修正を取りこぼす。 本件の修正は refactor と名乗り、リリースノートが無く、CVE に触れていない（出典3）〈重要〉。OSS を取り込んでいる組織が「CVE が付いた更新を優先する」という方針だけで動いていると、11月12日の修正は目に入らず、11月25日の勧告まで待つことになる（本記録の評価）。これは怠慢ではなく、方針の設計の穴である。

③欠陥の存在期間が分からないと、点検の範囲が決まらない。 影響するのは v2.9 で、2.9 系は2023年6月に公開され、2024年3月に「セキュリティ対策の強化を重視した」長期サポート版として出し直されている（出典2）〈重要〉。つまり欠陥は最長で3年以上存在しえた。 しかし CERT-In の勧告にも報道にも、いつから存在したかの記述が無い（出典1・5）〈未確定3〉。「悪用は確認されていない」は、この状況では「3年分のログを見た」という意味ではない（本記録の評価）〈重要〉。
