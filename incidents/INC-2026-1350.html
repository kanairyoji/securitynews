INC-2026-1350SAP が侵害を認める

**SAP SE** が2026年11月26日から27日にかけて「不審な活動を検知した」とサイバー侵害を認め、 報道（Der Spiegel・DPA・Handelsblatt）は侵害が GitHub 上で起きたこと、 従業員の認証トークンが窃取されソースコードが複製・改変されたこと、 SAP が署名鍵の差し替えと自動開発処理の停止に踏み切ったことを伝えたが、 SAP 自身は手口・範囲を一切公表せず「顧客の業務データへの不正アクセスの証拠は見つかっていない」と述べるにとどまった事案

不正アクセス・侵害続報が続いている有名事象として記録（日本と直接の関係は薄い）認証情報の悪用（使い回し・推測可能・窃取）
初報: 2026年11月26日（Der Spiegel の第一報） 最終更新: 2026年11月27日

SAP SE（ドイツ・ヴァルドルフ。企業向けソフトウェア最大手）が、2026年11月26日から27日にかけて、サイバーセキュリティ事案を調査中であることを認めた。 SAP が公表した内容はきわめて短い——「不審な活動を検知した」「顧客を守り自社サービスを保護するための措置を実施した」「現時点の調査に基づけば、顧客の業務データへの不正アクセスの証拠は見つかっていない」の3点だけである（出典1）。手口・侵入の時期・影響を受けた範囲は何も述べていない。

報道が伝えているのは、これよりはるかに重い内容である。ドイツの Der Spiegel が SAP 内部者と従業員向けの内部通知を根拠に第一報を出し（2026年11月26日）、ドイツ通信社 DPA が SAP の内部連絡を確認して不審な活動は GitHub 上で特定されたと報じた。Der Spiegel が引用した内部者は、攻撃者が SAP 従業員の認証トークンを入手し、GitHub 上に置かれたソースコードを複製し、かつ改変できる状態になったと述べている。Handelsblatt は、SAP が署名鍵を差し替え、GitHub へのアクセスを制限し、自動化された開発処理を停止したと報じた（出典1が各報道を引用）。

本記録が重く見るのは、「開発の土台そのものが疑わしくなったときに何を止めるか」という点である（本記録の判断）。署名鍵の差し替え・自動開発処理の停止は、「どのコードが信用できるか分からない」と判断したときにしか選ばない手である。 一方で、SAP の公表には「改変されたコードが顧客向けの製品に入ったか」への答えが無い ——報道はいずれも「顧客に届いた製品に改変コードが取り込まれたことを示す材料は無い」と書くが、これは SAP が否定したのではなく、誰も確認できていないという意味である（本記録の読み）。日本の読者にとっての意味は、自社の ERP ベンダーが「自社の開発環境が侵害された可能性」を認めながら、供給物の健全性について断定を避けている状態が続いていることである。

攻撃の経過

公表された範囲の事実のみ。公表されていない段階は補完せず明示しています。

**以下の段階は、SAP の公表ではなく報道の記述に基づく**（本記録の明示）。 **SAP が述べたのは「不審な活動を検知した」だけで、段階に分解できる情報が無い。** **したがって各段階の confidence は、報道が内部者・内部連絡を根拠に述べた範囲で presumed とする。** **検知の機会については、公表資料に記述が一つも無いため、 本記録は「公表されていない」と記した上で、 同種の経路に対して現実的に置ける検知点を controls に書く。**

  1. 1. 認証情報アクセス推定[1]
    **攻撃者が SAP 従業員の認証トークンを入手した** （出典1が引用する Der Spiegel の内部者証言）。 **どのような種類のトークンか（個人アクセストークン・OAuth トークン・ セッション・アプリ連携の資格情報）も、入手の方法も述べられていない。**
    根拠: **Der Spiegel が SAP 内部者の証言として報じ、SecurityWeek が引用した内容**（出典1）。 **SAP の確認は無い。**
  2. 2. 初期侵入推定[1]
    **窃取されたトークンを使って、GitHub 上の SAP のリポジトリへアクセスした** （出典1。DPA が SAP の内部連絡で「不審な活動は GitHub 内で特定された」ことを 確認したと報じている）。 **脆弱性の悪用や GitHub 側の侵害を示す記述は無い** ——**正規の資格情報による正規の経路である（本記録の読み）。**
    根拠: **DPA が確認したとされる SAP の内部連絡と、 Der Spiegel の内部者証言**（出典1）。
  3. 3. 収集推定[1]
    **GitHub 上に保管されたソースコードを複製した** （出典1が引用する Der Spiegel の内部者証言）。 **複製の対象が公開リポジトリか非公開の自社コードかは明らかになっていない** ——**SAP は GitHub 上で開発者向けツール・サンプルアプリケーション・ オープンソースプロジェクトを公開しており、 攻撃者が独自のコードに到達したかは不明である**（出典1）。
    根拠: **Der Spiegel の内部者証言**（出典1）。**SAP の確認は無い。**
  4. 4. 影響（暗号化・破壊・改ざん）推定[1]
    **GitHub 上のソースコードを改変できる状態になった** （出典1が引用する Der Spiegel の内部者証言。 原文は「複製し、かつ改変する（copy and alter）ことを可能にした」）。 **実際に何が改変されたか、どのリポジトリだったかは公表されていない。** **報道のいずれも、改変されたコードが顧客に届いたソフトウェアへ 取り込まれたことを示していない**（出典1）。
    根拠: **Der Spiegel の内部者証言**（出典1）。 **SAP が署名鍵を差し替え自動開発処理を停止したという Handelsblatt の報道は、この段階が現実の懸念だったことと整合する （本記録の読み。ただし SAP の確認ではない）。**

SAP が認めたのは3文だけで、原因も範囲も語っていない概観

SAP が SecurityWeek に対して述べたのは、次の内容である（出典1。事実）。

  • 不審な活動を検知した。
  • 顧客を守り、自社サービスを保護するための措置を実施した。
  • 「現時点の調査に基づけば、顧客の業務データへの不正アクセスの証拠は見つかっていない」（原文英語: "Based on our investigation to date, we have found no evidence of unauthorized access to customer business data." の日本語訳）。

SAP は攻撃の詳細を明らかにしなかった（出典1）。侵入の時期・検知の日付・手口・影響を受けたリポジトリ・停止した処理の範囲は、いずれも公表されていない。

本記録が注意を促すのは、この声明の射程である（本記録の読み）。「顧客の業務データへの不正アクセスの証拠は見つかっていない」は、顧客が SAP のシステムに預けている業務データについての言明であり、SAP が顧客に配っているソフトウェアが健全かどうかについての言明ではない。 本件で報じられているのはソースコードの複製と改変であって、顧客データの持ち出しではない——声明は、報じられた論点そのものには答えていない。

侵害の場所は GitHub で、入り口は従業員のトークンだったと報じられた原因・手口

以下は SAP の公表ではなく、報道の記述である（本記録の明示）。

ドイツの Der Spiegel が2026年11月26日に第一報を出した。根拠は SAP 内部者の証言と、従業員向けに出された内部通知である（出典1）。記事自体は有料会員限定で、本記録は原文を参照できていない ——本記録が確認したのは、SecurityWeek による引用である。

ドイツ通信社 DPA は SAP の内部連絡を確認し、不審な活動は GitHub 内で特定されたと報じた（出典1）。

Der Spiegel が引用した内部者は、攻撃者が SAP 従業員の認証トークンを入手し、GitHub 上に保管されたソースコードを複製し、かつ改変できる状態になったと述べている（出典1）。トークンの入手方法は述べられていない。

SAP は GitHub 上で開発者向けツール・サンプルアプリケーション・オープンソースプロジェクトを公開している（出典1）。攻撃者が独自のコードに到達したかは明らかになっていない。

本記録の評価は次のとおりである。 「トークンを使って正規の経路から入る」という筋道には、脆弱性の悪用も権限昇格も要らない。 GitHub 上の操作は、窃取されたトークンの持ち主である従業員の操作と区別がつかない形で記録される——だからこそ、「誰が」ではなく「いつもと違う何が」で見る監視が要る（本記録の判断）。

署名鍵を差し替え自動開発処理を止めたのは、供給物を信用できなくなった印である組織の対応

Handelsblatt は、SAP の緊急の保安措置が多数のチームに影響したと報じた（出典1）。報じられた措置は3つである。

  • 署名鍵（signing keys）の差し替え。
  • GitHub へのアクセスの制限。
  • 自動化された開発処理（automated development operations）の停止。

本記録はこの3つを、「開発の土台そのものを疑ったときの手」と評価する（本記録の判断）。

署名鍵の差し替えは、鍵が漏れた疑いがあるときだけでなく、「この鍵で署名された成果物が信用できるか分からない」ときにも行う。 自動開発処理の停止は、ビルドと配布のパイプラインが「改変されたコードを自動で下流へ流す装置」に変わりうるからである。 GitHub アクセスの制限は、同じ種類のトークンがまだ有効かどうかを切り分けるまでの時間を買う措置である。

これらを同時に打ったという事実は、SAP がその時点で「どのコードが健全か」を即答できなかったことを示している（本記録の評価。ただし出所は報道であり、SAP の確認ではない）。

一方で、SAP はこの措置の一つも自ら公表していない。 本記録は、ここを本件の対応上の弱点と見る—— 顧客が「自社に届いた SAP 製品は大丈夫か」を判断するための材料が、当事者から一切出ていない（本記録の評価）。

顧客に届いた製品が健全かどうかは、誰も確認できていない波及・関係先

報道のいずれも、改変されたコードが顧客に届いたソフトウェアに取り込まれたことを示していない（出典1。事実）。

本記録は、この表現を「否定」と読まない（本記録の読み）。「示す材料が無い」は「無かった」ではない。 SAP の声明も、顧客の業務データについてだけ否定しており、供給物に触れていない。

SAP は世界の大企業の業務基盤を担っており、日本でも ERP の中核として広く使われている。 本件が日本の読者にとって意味を持つのは、ここである（本記録の判断）—— 「ベンダーの開発環境が侵害されたとき、自社に届いた成果物をどう検証するか」を持っていない組織は、ベンダーが沈黙している間、何も確認できない。

本記録の時点で、SAP から顧客向けの技術的な確認手順（影響を受けた成果物の一覧・ハッシュ・署名鍵の切り替え手順・再取得が必要な配布物の指定）は出ていない。

10月の Gentlemen のリークサイト掲載は、本件とは別件とみられている関係が否定された事象

2026年10月下旬、Gentlemen ランサムウェアグループが自らのリークサイトに SAP を掲載し、同社のラテンアメリカ事業を指し示した（出典1）。SecurityWeek が確認したファイル一覧からは、攻撃者が SAP 関連のソフトウェアとソースコードを入手したことがうかがえるが、侵害されたのが SAP 自身なのか第三者なのかは明らかでない（出典1）。

SecurityWeek は「2つの事案は関係があるようには見えない」と述べている（出典1）。本記録はこの判断を引き写すが、SAP がこの点について何かを述べたという記述は確認できていない（本記録の明示）—— つまり「別件」は報道側の見立てであり、当事者の否定ではない。

リークサイトへの掲載は攻撃者側の主張であり、本記録は被害の事実として扱わない。

AI の関与は示唆されただけで、確認されていない未確定事項

Der Spiegel が引用した情報源は、攻撃が AI の支援を受けていた可能性を示唆した（出典1）。AI の関与は確認されていない。

SecurityWeek は文脈として、欧州委員会を含む複数の大規模組織が近時 AI 支援型の攻撃を受けたと公表していることに触れている（出典1）。

本記録は、この文脈を本件の裏付けとして使わない（本記録の明示）。他の組織が AI 支援型の攻撃を受けたことは、本件が AI 支援型だったことを少しも示さない。 また、「AI が使われたか」は防御側の手当てをほとんど変えない（本記録の評価）——トークンが窃取されて正規の経路で使われたのなら、打つ手はトークンの寿命・範囲・使われ方の監視であり、攻撃者が人間か自動化されているかでは変わらない。

    取るべき行動 **自社が適用しているベンダー成果物について、 ①入手時のハッシュ、②署名の検証結果、③入手日時と入手元 URL を 記録として残す仕組みを作る（すでに適用済みのぶんも遡って埋める）。** **署名検証に使う公開鍵・証明書の取得元を文書化し、 鍵が差し替えられたときに気づけるようにする。**
  • ビルドの入力と出力を結びつけ、「どの成果物が疑わしいか」に即答できるようにする
    **本件では自動開発処理が停止されたと報じられている**（出典1）。 **止めたのは、改変されたコードが成果物へ流れることを その場では排除できなかったからだと読める（本記録の評価）。** **入力（コミット）と出力（成果物）が結びついていなければ、 侵害の疑いが出た瞬間に「どれを作り直すか」が決められない。**
    取るべき行動 **ビルドのたびに、入力のコミットハッシュ・依存関係の固定版・ ビルド環境の識別子・出力のハッシュを1レコードとして保存する。** **そのうえで「特定の期間のビルドをすべて列挙する」問い合わせが 数分で返ることを、実際に試して確かめる。**
  • レビューと署名の二重化で、トークン1本の侵害がコード改変に至らないようにする
    **報じられた筋道では、攻撃者はソースコードを「複製し、かつ改変できる」 状態になった**（出典1）。 **1人分の資格情報で改変まで到達できる構成は、 トークンの窃取がそのまま供給網の問題に変わる（本記録の評価）。**
    取るべき行動 **保護された分岐への直接の書き込みを禁止し、 変更は必ずレビューを経る設定にする。** **あわせてコミット署名を必須にし、 署名の無い変更が取り込まれない構成にする。** **自動化された取り込み（ボット・自動マージ）が この2つを迂回していないかを点検する—— 迂回経路が1つあれば二重化は成立しない。**

自組織に当てはまるか

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
認証・認可□ コード基盤（GitHub・GitLab 等）に、有効期限の無い個人アクセストークンや 組織全体の読み取り権を持つ連携資格情報が存在し、最終利用日が追えていない本件で報じられた入り口はトークンの窃取である。長命で広い権限のトークンが 1本でもあれば、窃取されたときの影響範囲と持続時間がそのまま広がる
運用・監視□ コード基盤の監査ログを外部へ転送しておらず、 「普段と違う呼び出し元からの正規トークンの利用」を見る警報が無い窃取されたトークンによる操作は利用者名では異常に見えない。 ログが基盤の中にしか無いと、侵害の疑いが出た後に遡って調べることもできない
システム構成□ ビルド・配布のパイプラインが自動で下流へ成果物を流し、 入力のコミットと出力の成果物を結びつける記録が残っていない本件で SAP は自動開発処理を停止したと報じられた。 入力と出力が結びついていなければ、止めた後に「どの成果物を作り直すか」が決まらない
委託・第三者部品□ 主要なソフトウェアベンダーについて、受け取っている成果物の一覧と その検証方法（署名鍵・ハッシュの保管場所）が文書になっていない本件でベンダーからは顧客向けの確認手順が出ていない。 受け取る側に一覧が無いと、ベンダーが沈黙している間は何も確認できない
体制・契約□ 開発基盤の侵害が疑われたときに「何を止めるか」「誰が決めるか」 「どうなったら解除するか」が平時に決まっていない本件では署名鍵の差し替えと自動開発処理の停止が多数のチームに影響したとされる。 この種の決定は現場だけでは踏み切れず、平時に決めていないと判断が遅れる
データの保持□ 自社が公開しているリポジトリと非公開の自社コードが同一の組織アカウントに同居し、 権限がアカウント単位でしか分かれていない本件では公開物と独自コードのどちらが触られたかが分からない状態が続いている。 同居していると、侵害の疑いが出たときに影響範囲を切り分けられない
