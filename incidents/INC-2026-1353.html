INC-2026-1353Cacti にゲスト経由の未修正ゼロデイ

ネットワーク監視ソフトウェア **Cacti 1.2.31** に、ゲストアクセスが有効な構成で 認証を一切経ずに4回の HTTP 要求だけでコマンド実行へ至る未修正の脆弱性が見つかり、 研究者 ek0ms savi0r が2026年11月26日に実証コード（4HTTP2SHELL / 4HTTP2ROOT）を公開した事案。 数値型のゲスト設定項目への入力検証の不備・保存後に発火する二次 SQL インジェクション・ データベースに保存されたポーラーのコマンドを popen() へ渡す実装の3つが連鎖する。 CVE は未割り当てで、本記録の時点で Cacti の修正版は出ていない

脆弱性続報が続いている有名事象として記録（日本と直接の関係は薄い）設計・実装上の不備未知の脆弱性の悪用
初報: 2026年11月26日（実証コードの公開） 最終更新: 2026年11月27日

Cacti は、RRDtool を基盤にした広く使われているオープンソースのネットワーク監視ソフトウェアである。2026年11月26日、研究者 ek0ms savi0r が、Cacti 1.2.31 に対する実証コード（PoC）を公開した（出典2）。PoC には 4HTTP2SHELL および 4HTTP2ROOT という名が付けられており、CVE 識別子は本記録の時点で割り当てられていない（出典1・2）。

公開された筋道は、認証を経ない HTTP セッションから4回の要求でコマンド実行に到達するものである（出典1・2）。成立の前提はゲストアクセス（guest access）が有効であることで、Cacti ではこれは既定で無効である（出典2）。

4回の要求は次のように並ぶ（出典2）。①ゲストの利用者プロファイル画面を読み込んでセッションのクッキーとCSRF トークンを得る。②数値を期待する設定項目（preview_graphs_per_page）に非数値の値を送って保存させる。③グラフのプレビュー画面を開くと、保存された値が SQL 文へ読み込まれて発火する（二次 SQL インジェクション）。④リアルタイムグラフの端点を呼ぶと、書き換えられたデータベースの行の値がpopen() へ渡されて実行される。

本記録が本件の核心と見るのは、「監視サーバが持っている鍵束の重さ」である（本記録の判断）。Cacti は監視対象のネットワーク機器について SNMP のコミュニティ文字列や機器の認証情報を保持している（出典1）—— つまり Cacti サーバの侵害は、監視ツール1台の侵害では終わらず、監視されている側の機器群への到達手段の流出になる。 「監視は本番ではないから」という扱いで Cacti を内部から広く見える場所に置いている組織では、ここが最も薄い壁になりうる（本記録の評価）。

実行の権限については、報道のあいだで強さの表現が揺れている（出典1）。コマンドが動くのは Cacti のプロセスの権限であり、研究者が root での実行を示したのは、試験環境で Cacti がすでに root として動いていた場合である—— 4HTTP2ROOT という名前は、どの環境でも root が取れることを意味しない（本記録の明示）。

4回の要求に、偵察も認証情報の収集も含まれていない原因・手口

公開された筋道は、認証を経ない HTTP セッションから4回の要求でコマンド実行に到達する（出典1・2。事実）。

①ゲストの利用者プロファイル画面を読み込み、セッションのクッキーと CSRF トークンを得る。 ②数値を期待する設定項目（preview_graphs_per_page）に非数値の値を送り、保存させる。 ③グラフのプレビュー画面を開く。保存された値が SQL 文へ読み込まれ、二次 SQL インジェクションが発火する。 ④リアルタイムグラフの端点を呼ぶ。書き換えられたデータベースの行の値が popen() へ渡されて実行される。

本記録が注目するのは、この4回に含まれていないものである（本記録の判断）。

偵察が無い。 版の判別も、構成の探索も要らない。 認証情報の収集が無い。 フィッシングもパスワードの総当たりも不要である。 権限昇格が無い。 ゲストの権限のまま、ゲストが編集できる設定項目を経由して到達する。

攻撃の手数が少ないほど、自動化と大量の走査に向く（本記録の評価）。 4回の要求で済む筋道は、「インターネットに面した Cacti を探して順に撃つ」という形で使える。

1回目の要求が CSRF トークンの取得であることは、この経路が「正規の画面操作の形を取る」ことを意味する（本記録の読み）—— アプリケーションの側から見れば、ゲストが設定を変えただけである。

3つの小さな不備が順番に並ぶと、認証なしのコマンド実行になる評価・解釈

公開された筋道は、3つの実装上の不備の連鎖である（出典1・2。事実）。

  • 数値を期待する設定項目が、非数値の入力をそのまま保存する（入力検証の不備。ゲストが編集できる項目である）。
  • 保存された値が、後からパラメータ束縛を経ずに SQL 文へ組み込まれる（二次 SQL インジェクション。注入の瞬間と発火の瞬間が別の要求にある）。
  • データベースに保存されたポーラーのコマンドが、実行時に popen() へ渡される（保存値をそのまま実行する設計）。

本記録の評価は次のとおりである。

どの1つも単体では致命的でない。 数値欄に文字列が入っても、普通は表示が崩れるだけである。 SQL インジェクションがあっても、読み出しだけなら影響は限定される。 ポーラーのコマンドをデータベースから読むのは、Cacti のような監視ツールでは自然な設計である。

問題は3つが順番に並んでいることである。 ①が②の入力を用意し、②が③の入力を書き換える。 「保存されるだけだから安全」という前提が①を通し、「データベースの値は自分が書いたものだから安全」という前提が③を通す。 二次インジェクションが厄介なのは、まさにこの2つの前提を同時に崩すところである（本記録の評価）。

本記録が設計上の教訓として挙げるのは次の点である（本記録の判断）。「入力の検証」と「出力の安全化」のどちらか一方しかない箇所は、二次インジェクションの入口になる。 データベースを経由すると、注入と発火が別の要求・別のコード経路に分かれるため、どちらの側からも「相手が守っている」と見えてしまう。

ゲストアクセスを切っても、根の SQL インジェクションは残る対策・注意喚起

成立の前提は、ゲストアクセス（guest access）が有効であることである（出典1・2。事実）。Cacti では匿名のゲストアクセスは既定で無効とされる（出典1）。

公表されている緩和策は次のとおりである（出典1・2）。

  • ゲストアクセスを無効にする。 認証設定で指定されているゲスト利用者を外し、Console > Configuration > Users でゲストのアカウントを無効にする（出典1）。
  • Cacti の画面への到達を、VPN や管理用の信頼された区画に限定し、ファイアウォールの規則で絞る（出典2）。
  • settings_user と poller_item の2つのテーブルを点検し、予期しない文字列や書き換えられたコマンドが無いか確認する（出典2）。
  • Web サーバとポーラーを root で動かさない（出典1・2）。
  • graph_view.php について、非数値の値に関する PHP の警告がログに出ていないか監視する（出典2）。

本記録が強調したいのは、公表資料が明示している留保である（出典1）。「ゲストアクセスを無効にしても、根にある SQL インジェクションは修正されない。」

つまりゲストアクセスの無効化は、公開された経路を塞ぐだけである（本記録の読み）。 同じ二次 SQL インジェクションに、認証を経た利用者から到達する別の経路が存在しないという保証は、どこにも無い。 Cacti には、認証を要する自動化領域の二次 SQL インジェクションという別の脆弱性が過去に公表されており（本記録の確認。本件とは別物である）、この種の不備が1箇所に限られない可能性はある（本記録の評価。断定はしない）。

したがって本記録は、ゲストアクセスの無効化を「必要だが十分ではない」措置として扱う。 到達そのものを絞る（VPN・管理区画への限定）ほうが、修正版が出るまでの手当てとしては効く（本記録の判断）。

監視サーバが持っているのは監視対象への鍵束である被害規模・影響範囲

Cacti は、監視対象のネットワーク機器についてSNMP のコミュニティ文字列や機器の認証情報を保持している（出典1。事実）。出典1はここから、Cacti サーバの侵害が「監視ツールそのものよりはるかに多くを露出させうる」と述べている。

本記録はこれを本件の影響評価の中心に置く（本記録の判断）。

監視サーバは、構成上の必然として「ネットワーク上のほぼ全ての機器に到達できる場所」に置かれる。 到達できるだけでなく、到達するための資格情報を持っている。 読み取り専用の SNMP コミュニティ文字列であっても、機器の構成・インターフェースの一覧・隣接関係が引ける ——これは内部網の地図である（本記録の評価）。 書き込み可能なコミュニティ文字列や機器のログイン情報が保存されていれば、影響はさらに重い。

本記録が最も危ういと見る構成は、「監視は本番ではない」という扱いで、Cacti を内部から広く見える場所に、緩い認証のまま置いている場合である（本記録の評価）。監視ツールは重要度の評価で後回しにされやすいが、持っている資格情報の重さでは本番系と変わらない。

実行の権限について、本記録は報道の表現を割り引いて読む（本記録の明示）。コマンドが動くのは Cacti のプロセスの権限である（出典1）。研究者が root での実行を示したのは、試験環境で Cacti がすでに root として動いていた場合であり、この脆弱性がどの環境でも root を与えるわけではない（出典1）。4HTTP2ROOT という名前が過大に読まれやすい点に注意が要る。 ただし、Cacti のプロセス権限であってもデータベースへの到達と保存された資格情報の読み出しには足りる（本記録の評価）——権限が root でないことは安心の根拠にならない。

CVE が無いため、脆弱性管理の仕組みが空振りする未確定事項

本記録の時点で、本件に CVE 識別子は割り当てられていない（出典1・2）。本記録が2026年11月27日に Cacti のセキュリティアドバイザリ一覧を確認したところ、2026年11月に公表されたものは無く、本件に該当する記載も無かった（出典4。本記録の確認）。公開リリースの一覧でも、最新は release/1.2.31（2026年6月15日）であり、1.2.32 は存在しなかった（出典3。本記録の確認）。

本記録は、この「識別子が無い」という状態を運用上の最大の難点と見る（本記録の判断）。

理由は、脆弱性管理の仕組みがほぼすべて CVE 番号を軸に動いているからである。 資産台帳と脆弱性の突き合わせ、スキャナの検出、KEV（既知の悪用脆弱性）への収載、ベンダーの勧告、社内の是正期限の管理——どれも番号で回る。 番号が無い脆弱性は、これらの仕組みを素通りする（本記録の評価）。

さらに、当てられるパッチが存在しない。 直前の版（1.2.31）が公開されたのは2026年6月15日で、実証コードの公開まで164日が経っている（本記録の算出）—— 1.2.32 がすぐ出ると見込む根拠は無い。

したがって、本件に対する現実的な構えは「パッチ待ち」ではなく「到達の制限と痕跡の点検」である（本記録の判断）。 そして、CVE 番号で管理する台帳とは別に、「番号が無いが対応中の脅威」を置く欄が組織に必要になる。

「既定で無効」と「実際に無効」は別である評価・解釈

Cacti では匿名のゲストアクセスは既定で無効とされる（出典1。事実）。これは本件の深刻度を下げる重要な事実である。

一方、攻撃面管理の事業者 watchTowr は公開と同日に、「ゲストアクセスは必要だが、よくある構成である（a common config）」と述べ、自社の顧客に対して露出の有無を通知したとしている（出典1。事実）。

本記録はこの2つを並べて読む（本記録の判断）。

「既定で無効」は、新規の設置についての話である。 Cacti は長く使われているソフトウェアであり、ゲストアクセスは「ログインせずにグラフを見せたい」という正当な要求のために有効化されてきた機能である（本記録の評価）。 ダッシュボードを部門に見せる、NOC の画面に常時表示する、社内の誰でも回線の状況を見られるようにする——どれも運用上は自然な動機である。

つまり、既定値は母数を小さくするが、ゼロにはしない。 そして有効にしている組織は、「便利だから有効にした」のであって「危険を承知で有効にした」のではない（本記録の評価）。

本記録が実務への含意として挙げるのは次の点である。 自組織の Cacti がゲストアクセスを有効にしているかは、設定を見ないと分からない。 「既定で無効だから大丈夫」は、確認ではなく推測である。 なお、watchTowr の「よくある構成」という評価は同社の顧客母集団に基づくものであり、全体の分布を示すものではない（本記録の留保）。

layer 0 は認証を経ない攻撃者と、前提となる設定（ゲストアクセスの有効化。 Cacti では既定で無効）。 layer 1 から layer 4 が4回の HTTP 要求で、左から右へ順に進む—— ①ゲストプロファイル画面でセッションのクッキーと CSRF トークンを得る、 ②数値を期待する設定項目に非数値の値を保存させる、 ③グラフのプレビュー画面で二次 SQL インジェクションが発火し ポーラーの表の記録が書き換わる、 ④リアルタイムグラフの端点から書き換えられた値が popen() へ渡されて実行される。 layer 5 は実行の結果として到達しうる先——Cacti のプロセス権限でのコマンド実行と、 Cacti が保持している監視対象機器の SNMP コミュニティ文字列・認証情報。 右端はそれらの資格情報が指し示す監視対象のネットワーク機器群で、 点線は「到達手段が流出する」という関係（実際の侵害が確認されたものではない）。 下段は点検・監視で痕跡が見える3か所（settings_user・poller_item・PHP の警告）。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。

初期侵入公表されていない
**検知の機会について公表資料に記述は無い**（本記録の確認）。 **本記録の評価では、この段階だけでは検知は難しい**—— **ゲストがプロファイル画面を開くのは正常な動作であり、 1回の GET 要求として記録されるだけである。** **ただし、インターネットからのゲストアクセス自体が 想定外である組織では、接続元で異常として扱える。**
侵入を防げた**ゲストアクセスを無効にする （認証設定で指定されているゲスト利用者を外し、 Console > Configuration > Users でゲストのアカウントを無効にする）**　**出典1が示す緩和策である。** **公開された経路はこれで塞がる。** **ただし出典1は「ゲストアクセスの無効化は、 根にある SQL インジェクションを修正しない」と明記している** ——**認証を経た別の経路が無いという保証にはならない（本記録の明示）。**

実行機会はあったが検知できず
**本記録の評価である。** **この段階は、点検によって事後に発見できる**—— **出典2は緩和策として `settings_user` テーブルを点検し、 予期しない文字列が無いか確認するよう勧めている。** **「数値を期待する列に非数値が入っている」という状態は、 問い合わせ1本で見つけられる（本記録の評価）。** **即時の検知としては、アプリケーションが 入力の拒否を記録していれば拾えるが、 本件では拒否されずに保存されるため記録が残らない。**
検知できた**`settings_user` テーブルを点検し、 数値を期待する列に非数値の値が入っていないかを確認する**　**出典2が示す緩和策である。** **本記録はこれを、修正版が無い期間の定期点検として勧める** （本記録の判断）——**1日1回の問い合わせで足りる。**
侵入を防げた**数値を期待する設定項目について、 保存の時点で型と範囲を検証し、外れた入力を拒否する**　**本記録の評価による（Cacti の実装側の対策であり、 利用者が打てる手ではない）。** **連鎖の最初の環を切る対策である。**
権限昇格機会はあったが検知できず
**本記録の評価である。** **出典2は、`graph_view.php` について 非数値の値に関する PHP の警告がログに出ていないかを 監視するよう勧めている**——**つまり、 発火の際にアプリケーションが警告を出す可能性がある。** **これは「検知の機会はあるが、 PHP の警告を監視対象にしている組織は少ない」という形である （本記録の評価）。**
検知できた**`graph_view.php` に関する PHP の警告（非数値の値に関するもの）を ログ監視の対象に加える**　**出典2が示す緩和策である。** **本記録の評価では、これは費用の安い検知である**—— **アプリケーションのエラーログを集めている組織なら、 検索条件を1つ足すだけで済む。**
侵入を防げた**データベースへ渡す値を、保存元に関わらず パラメータ束縛で組む（保存済みの値も「外部入力」として扱う）**　**本記録の評価による（実装側の対策）。** **二次インジェクションを防ぐ唯一の確実な方法は、 「自分のデータベースの値は信用できる」という前提を捨てることである （本記録の判断）。**
影響（暗号化・破壊・改ざん）機会はあったが検知できず
**本記録の評価である。** **Web サーバまたはポーラーのプロセスから 予期しない子プロセスが起動する動きは、 端末の監視（EDR）やプロセスの監査で拾える（本記録の評価）。** **Cacti は正常時にも外部コマンド（RRDtool・SNMP の取得）を 多数起動するため、単純な「子プロセスの起動」では 警報が埋もれる**——**起動されるコマンドの名前で絞る必要がある。**
影響を限定できた**Web サーバとポーラーを root で動かさない**　**出典1・2が示す緩和策である。** **実行そのものは防げないが、影響の範囲を狭められる。** **本記録の留保——Cacti のプロセス権限であっても、 データベースへの到達と保存された資格情報の読み出しには足りる （本記録の評価）。**
検知できた**`poller_item` テーブルを点検し、 書き換えられたコマンドが無いかを確認する**　**出典2が示す緩和策である。** **本記録はこれを最優先の点検と見る**（本記録の判断）—— **ここに異常があれば、すでに実行された可能性がある。**
検知できた**Cacti のプロセスから起動される子プロセスを記録し、 正常時に起動されるコマンドの一覧（RRDtool・SNMP の取得等）を 基準として、一覧外のコマンドを警報の対象にする**　**本記録の評価による。** **Cacti は正常時にも外部コマンドを多数起動するため、 「子プロセスの起動」そのものでは判別できない。** **正常時の一覧を先に作ることが、この検知の前提である。**
影響を限定できた**Cacti が保持している監視対象の資格情報 （SNMP のコミュニティ文字列・機器のログイン情報）を棚卸しし、 書き込み可能なものを読み取り専用へ、 共用のものを機器ごとへ分ける**　**本記録の評価による。** **出典1が指摘するとおり、Cacti の侵害は 監視対象への到達手段の流出になる。** **実行を防げなかった場合に被害を監視ツール1台に留めるには、 持たせている鍵束を軽くしておくしかない（本記録の判断）。**

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
対応の巧拙を評価できる材料が公表資料から得られていません。
CISO・経営層への示唆
  • 監視ツールを「本番ではないもの」として扱っていないか見直す
    **Cacti は監視対象機器の SNMP コミュニティ文字列や 認証情報を保持しており、侵害は監視ツール1台に留まらない**（出典1）。 **監視ツールは重要度の評価で後回しにされやすいが、 持っている資格情報の重さでは本番系と変わらない（本記録の評価）。**
    取るべき行動 **監視・運用系のシステム（監視・構成管理・バックアップ・ ジョブ実行）を列挙し、それぞれが保持している 「他のシステムへの資格情報」の数を数える。** **数が多い順に並べ替え、上位のものの重要度区分を 本番系と同じ水準へ上げるかどうかを判断する。** **判断の記録を残す——「上げない」と決めた理由も含めて。**
  • CVE 番号が無い脅威を管理する欄を持つ
    **本件に CVE 識別子は割り当てられていない**（出典1・2・4）。 **脆弱性管理の仕組みはほぼすべて CVE 番号を軸に動いているため、 番号が無い脆弱性は台帳・スキャナ・是正期限の管理を素通りする （本記録の評価）。**
    取るべき行動 **脆弱性管理の台帳に「識別子が無いが対応中」の欄を作る。** **1件につき、①影響する製品と版、②前提条件、 ③打った緩和策、④修正版を待っているかどうか、 ⑤次に確認する日を記録する。** **CVE が後から割り当てられたら、通常の台帳へ移す。** **この欄が無いと、本件のような脆弱性が「誰も追っていない」状態になる。**
  • 「既定で無効」を確認の代わりにしない
    **Cacti では匿名のゲストアクセスは既定で無効とされる**（出典1）。 **一方、攻撃面管理の事業者は「よくある構成である」と述べ、 自社の顧客に露出を通知したとしている**（出典1）。 **既定値は母数を小さくするが、ゼロにはしない（本記録の評価）。**
    取るべき行動 **ベンダーや報道が「既定では無効」と述べた設定について、 自組織の実際の値を確認する手順を作る（推測で済ませない）。** **本件なら、自組織の Cacti すべてについて ゲストアクセスの有効・無効を列挙する。** **確認の結果を記録に残す**——**「確認した」と「大丈夫だと思う」を 区別できる状態にすることが目的である。**
  • パッチが存在しない期間を前提に、緩和策の決定権を現場に渡す
    **本記録の時点で修正版は存在せず、 直前の版（1.2.31）の公開から164日が経っている**（本記録の算出。出典3）。 **「パッチが出たら当てる」という手順しか持たない組織は、 この期間を何もせずに過ごすことになる（本記録の評価）。**
    取るべき行動 **「修正版が無い脆弱性への対応」を、 通常のパッチ適用とは別の手順として定める。** **手順には、現場が承認を待たずに打てる措置の範囲を明記する （到達経路の制限・機能の無効化・監視条件の追加）。** **業務影響が出る措置（本件なら VPN 経由への限定）については、 誰がどの期限までに判断するかを決めておく。**
セキュリティ技術者への示唆
  • 自組織の Cacti のゲストアクセスの設定を今日のうちに確認する
    **公開された経路の前提は、ゲストアクセスが有効であることである** （出典1・2）。 **既定では無効だが、「ログインせずにグラフを見せたい」という 正当な要求のために有効化されてきた機能である（本記録の評価）。** **設定を見ないと、該当するかどうかが分からない。**
    取るべき行動 **Cacti の認証設定でゲスト利用者が指定されているかを確認し、 Console > Configuration > Users でゲストのアカウントの状態を確認する。** **有効であれば、まず誰が閲覧しているかを把握する （NOC の常時表示・部門のダッシュボード）。** **閲覧の代替（認証つきの共有アカウント・ 画面の静的な公開）を用意してから無効にする。** **代替の用意に時間がかかる場合は、 先に到達経路の制限（VPN・管理区画への限定）を打つ。**
  • 到達の制限を、設定の無効化より優先する
    **公表資料は「ゲストアクセスの無効化は、 根にある SQL インジェクションを修正しない」と明記している**（出典1）。 **同じ二次インジェクションに認証を経た別の経路が 無いという保証はどこにも無い（本記録の評価）。**
    取るべき行動 **Cacti の画面への到達を、VPN か管理用の区画からのみに限定する。** **ファイアウォールの規則を書く前に、 現在どこから接続されているかを接続記録で確認する （予期しない接続元を見つけるため）。** **インターネットに面している Cacti があれば、 それを最優先で内側へ移す。**
  • データベースの2つのテーブルを点検し、点検を日次の作業にする
    **公表資料は `settings_user`（予期しない文字列）と `poller_item`（書き換えられたコマンド）の点検を勧めている**（出典2）。 **これらはログではなくデータベースの現状なので、 ログの保持期間に関わらず確認できる（本記録の読み）。**
    取るべき行動 **`settings_user` について、数値を期待する列に 非数値の値が入っていないかを確認する問い合わせを書く。** **`poller_item` について、現在の内容を一度保存し、 以後それとの差分を見る。** **両方を日次で実行し、結果を記録する—— 修正版が出るまでのあいだ続ける。** **先に「健全な状態」を記録しておくことが、 この点検が機能する前提である。**
  • Cacti のプロセスから起動される子プロセスの正常な一覧を作る
    **最終段階は、保存された値が `popen()` へ渡されて実行されることである** （出典2）。 **Cacti は正常時にも外部コマンド（RRDtool・SNMP の取得）を 多数起動するため、「子プロセスの起動」そのものでは判別できない （本記録の評価）。**
    取るべき行動 **Cacti のプロセス（Web サーバ・ポーラー）から起動される 子プロセスを1日分記録し、コマンドの名前で集計して一覧を作る。** **その一覧を基準として、一覧外のコマンドが起動されたときに 警報を出す条件を設定する。** **一覧を作る作業そのものが、 「この監視サーバは何を実行しているのか」の棚卸しになる。**
  • 保存済みの値も「外部入力」として扱う設計へ移す
    **本件の連鎖の中核は二次 SQL インジェクションである**（出典1・2）。 **注入と発火が別の要求・別のコード経路に分かれるため、 どちらの側からも「相手が守っている」と見えてしまう（本記録の評価）。** **これは Cacti 固有の問題ではなく、 自組織のコードにも同じ形がありうる。**
    取るべき行動 **自組織のコードで、データベースから読んだ値を 文字列結合で SQL 文・シェルのコマンド・ファイルのパスへ 組み込んでいる箇所を探す。** **検索の起点は、SQL 文の組み立てとコマンド実行の呼び出し （`exec`・`system`・`popen` 相当）である。** **見つかった箇所について、保存元が自分のアプリケーションであっても パラメータ束縛・引数の配列渡しへ置き換える。**
  • 監視ツールに持たせている資格情報を軽くする
    **Cacti は監視対象機器の SNMP コミュニティ文字列や 認証情報を保持しており、侵害は監視対象への到達手段の流出になる**（出典1）。 **実行を防げなかった場合に被害を監視ツール1台に留めるには、 持たせている鍵束を軽くしておくしかない（本記録の判断）。**
    取るべき行動 **Cacti に登録されている資格情報を列挙し、 ①書き込み可能な SNMP コミュニティ文字列、 ②複数の機器で共用されている資格情報、 ③監視に不要な権限を持つアカウントを特定する。** **①は読み取り専用へ、②は機器ごとへ分ける。** **③は監視に必要な最小限の権限へ落とす。** **作業量が多い場合は、重要な機器（境界・コア）から始める。**
