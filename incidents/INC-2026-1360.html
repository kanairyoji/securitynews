ロリポップ！は Q&A で「いずれも平文で保存しておりました」と明記し、他サービスを含めてパスワードの保存方法を点検・改善するとしている（出典2 Q5）。

ここが本件の核心である。 顧客情報の漏えいは「氏名・メールアドレス・都道府県」で止まったが、パスワードについてはハッシュ化されていれば漏えいしても即座に使えないところを、平文だったためにそのまま使える認証情報の漏えいになった（本記録の評価）。とりわけ105,608件の Basic 認証は顧客自身が決めた文字列であり、他サービスでの使い回しがあれば被害は GMOペパボの外へ出る。同社が「変更前のパスワードを他の Web サービスでも使っている場合はそちらも変更するよう」案内しているのは、この構造を認めたものと読める。

なお、FTP・WebDAV とユーザー専用ページのパスワードのうち、申込後に顧客が変更したものは漏えいの対象に含まれない（出典2）。仮設定のまま使い続けていた顧客だけが対象になったという形である。

調査の過程で、システムの不整合により、過去に退会手続きをした顧客の本来削除すべきデータが一部残存していたことが判明した（出典2 Q10）。該当する顧客には個別に連絡しているとされる。

件数・残存していた期間・516,564件に占める割合は公表されていない。

削除したはずのデータが漏えいの対象に入っていたという事実は、本件の中で最も一般化しやすい部分である（本記録の評価）。退会処理は「正常系では消えるが、不整合のときに何が残るか」を監視していないと気づけない種類の欠落であり、分析基盤のようにデータを集めてから使う側の仕組みでは、元のシステムでの削除がそこへ伝播しているかの確認が別途要る。

検知から遮断は同日、公表は3日後——動きは速いが、滞留期間は分からない組織の対応

公表されている日付から対応の所要を測ると次のようになる（本記録の算出）。

どこで止められたか

段階ごとに検知の機会があったか、どの対策があれば効きえたかを整理したものです。「効きえた対策」は本記録の評価であり、当事者が述べたものではありません。
段階検知の機会効きえた対策
初期侵入公表されていない
侵入そのものを検知した旨の記述は無い。検知は持ち出しの段階（監査ログのダウンロード）であり、 ログイン時点で異常として扱えたかは公表されていない
侵入を防げた社内システムの管理者・分析基盤アクセスをフィッシング耐性のある多要素認証に寄せ、長命の静的資格情報を廃する
侵入を防げた分析基盤への接続元を社内ネットワーク・特定の経路に限定し、外部からの直接到達を禁じる
影響を限定できた機械的なアクセスキーを短命化し、発行・利用・失効を台帳で追跡する
収集公表されていない
参照の段階で検知できたかは公表されていない。検知が「ダウンロード」の記録であったことから、 大量参照そのものの検知より持ち出しの検知が先に働いたと読める（本記録の読み）
影響を限定できた分析基盤に置くデータを分析に必要な粒度まで削り、氏名・連絡先・パスワードを持ち込まない
影響を限定できた元システムでの退会・削除が分析基盤へ伝播しているかを定期的に突き合わせ、残存を検出する
影響を限定できた列単位のアクセス権限（氏名・メールアドレス等）を分離し、分析用途では匿名化した列だけを見せる
認証情報アクセス現実的な検知機会なし
平文で保存されたデータが読まれたこと自体は、保存側の設計の帰結であって検知の問題ではない。 ただし検知後の強制リセットで使用可能期間は短く抑えられた
影響を限定できた認証用のパスワードを一方向ハッシュ（ソルト付き・ストレッチング）で保存し、復元できない形にする
影響を限定できた顧客が設定する Basic 認証等の資格情報も平文で保持せず、検証可能な形式に変える
影響を限定できた仮設定パスワードを初回利用時の強制変更とし、未変更のまま残らないようにする
持ち出し検知した
データ分析基盤の監査ログで不審なダウンロードを検知し、同日に経路を遮断した。 検知までの日数（侵害開始からの滞留）は公表されていない
検知できた分析基盤のダウンロード・エクスポートに量と頻度の閾値を設け、超過を即時に警報する

対応の評価

評価材料がない判断は「評価材料なし」としています。結果論で断じないための区分です。
判断評価評価の根拠と留保
漏えいが確認されたパスワードと、予防的措置の対象となるパスワードを、公表前（11月25日）に強制リセットした機能した本記録の作成者の評価である。平文で漏れたパスワードは**公表より前に無効化しないと、 公表が攻撃者への「使える資格情報がある」という通知になりうる**。 検知の翌日にリセットを完了し、その2日後に公表した順序は、この危険を踏まえた形になっている。 ただし予防的措置の範囲（どこまで広げたか）は公表されておらず、十分性は評価できない
Q&A で「いずれも平文で保存しておりました」と明記し、退会済み顧客データの残存も自ら公表した機能した本記録の作成者の評価である。漏えい公表で最も省略されやすいのが保存形式であり、 「平文」の明記は顧客が取るべき行動（他サービスのパスワード変更）の緊急度を変える。 一方で**侵入経路と認証情報の種類は非開示**であり、同業他社が同じ経路を点検する手がかりは与えられていない
ムームードメインを2026年11月24日から25日まで緊急メンテナンスで停止し、安全確認後に再開した部分的に機能本記録の作成者の評価である。影響が確定していない段階で止めた判断自体は妥当だが、 公表時点でもムームードメイン・ヘテムルの顧客情報への影響は調査中のままで、 停止・再開によって何が確認できたのかは示されていない
CISO・経営層への示唆
  • 分析基盤は「本番より守りが薄い本番データの置き場」になりがちだと見なして棚卸しする
    侵入されたのは顧客の Web サイトではなく自社の内部システムで、持ち出しの経路はデータ分析基盤だった。 基盤には氏名・連絡先・平文パスワード・退会済み顧客のデータまで入っていた
    取るべき行動 データウェアハウス・BI・ログ集約基盤に流れ込んでいる個人情報の項目を列単位で一覧にし、 「分析に不要な列（氏名・連絡先・認証情報）」を特定して流入を止める計画を四半期単位で持つ
  • パスワードの保存形式を、全サービス横断で経営が把握している状態にする
    3種のパスワード118,100件が平文で保存されていた。うち105,608件は顧客自身が設定した Basic 認証の資格情報であり、他サービスでの使い回しがあれば被害は自社の外へ出る
    取るべき行動 自社の全サービス・全システムについて「認証に使う秘密をどの形式で保存しているか」の一覧を作らせ、 平文・可逆暗号で保持しているものを洗い出して改修の期限を決める。 仮設定パスワードは初回利用時の強制変更を既定にする
  • 退会・削除の処理が「下流のデータの置き場」まで届いているかを確認する
    システムの不整合により、退会済み顧客の本来削除すべきデータが一部残存しており、 漏えいの対象に入っていた
    取るべき行動 退会・解約・削除依頼のフローについて、本番DB以外（分析基盤・バックアップ・ログ・CRM・メール配信）での 削除の到達を定期的に突き合わせる検査を運用に組み込み、結果を report として残す
  • 公表の順序を「無効化 → 通知 → 公表」で設計しておく
    GMOペパボは検知の翌日（11月25日）にパスワードの強制リセットを完了し、 その2日後（11月27日）に公表した
    取るべき行動 インシデント対応手順に「漏えいした資格情報の無効化が完了する前に公表しない」という原則と、 それでも公表を急ぐべき条件（悪用が進行中等）を明記し、広報・技術・法務の判断順序を決めておく
  • 顧客に預かっている「顧客が自ら決めた秘密」は、自社の資産より慎重に扱う
    最多の105,608件は顧客がアクセス制限機能で設定した Basic 認証のID・パスワードであり、 利用者が他サービスでも同じ文字列を使っている可能性が高い
    取るべき行動 顧客が設定する補助的な資格情報（Basic 認証・API キー・Webhook の秘密等）についても ハッシュ化・暗号化の方針を定め、顧客向けに「漏えい時は他サービスでも変更が必要になる」ことを 平時から案内しておく
セキュリティ技術者への示唆
  • 分析基盤のエクスポートに量と頻度の閾値を置き、超過を警報にする
    検知の起点はデータ分析基盤の監査ログに残った不審なデータダウンロードだった。 ログは取れていたが、持ち出しが成立した後の検知である
    取るべき行動 クエリ結果のダウンロード・テーブルのエクスポート・外部ストレージへの書き出しについて 1回あたりの行数と1日あたりの累積に閾値を設定し、超過で即時警報と自動的な一時停止をかける
  • 平文保存をコードとスキーマの両側で禁止し、検査で落とす
    仮設定パスワードも顧客設定の Basic 認証も平文で保存されていた
    取るべき行動 スキーマ定義のレビュー基準に「認証用の秘密を保持する列はハッシュ型のみ」を入れ、 既存テーブルを走査して平文・可逆暗号の秘密を検出する点検を定期実行する。 Basic 認証のように検証側の実装が平文を要求する仕組みは、ハッシュ対応の代替（bcrypt 対応の htpasswd 等）に寄せる
  • 仮設定（初期）パスワードを未変更のまま運用できない作りにする
    漏えいしたのは同社が仮設定したパスワードのうち、申込後に顧客が変更していなかった 8,322件・4,170件である。変更済みのものは対象外だった
    取るべき行動 初期パスワードは初回ログイン時に強制変更とし、一定期間未変更のアカウントを棚卸しして 失効させる運用を入れる。発行時はワンタイムの受け渡し経路を使い、保存しない
  • 分析基盤の権限を列単位・行単位で絞り、匿名化した列を既定にする
    持ち出されたのは氏名・郵便番号・都道府県・メールアドレス・生年月日と、パスワード3種である。 分析に氏名と認証情報が必要な場面は限られる
    取るべき行動 分析用途のビューを「匿名化・集約済みの列だけ」で定義し、生の個人情報列への参照は 申請・期限付き・監査ログ必須の経路に分ける。既定の権限から個人情報列を外す
  • 削除の到達を検査する突き合わせジョブを書く
    退会済み顧客のデータが分析基盤側に残存していた。 本番で消えたことは、下流で消えたことを意味しない
    取るべき行動 本番DBの退会済みキー集合と、分析基盤・バックアップ・メール配信基盤のキー集合を定期的に差分比較し、 残存を検出したら自動でチケットを起票する。差分件数を運用指標として記録する

該当する項目があれば、この事案と同じ構図が自組織でも成立しうることを意味します。
観点自社に当てはまるか該当する場合に何が起きうるか
システム構成□ BI・データウェアハウス・ログ集約などの分析基盤に、本番の個人情報を複製して集約している持ち出しの経路はデータ分析基盤であり、顧客の Web サイトやサービス本体ではなかった
データの保持□ 認証に使うパスワード・API キー・Basic 認証の資格情報を平文または可逆な形で保存している箇所がある3種のパスワード合計118,100件が平文で保存されており、漏えいがそのまま認証情報の漏えいになった
データの保持□ 退会・解約・削除依頼の処理が、分析基盤・バックアップ・外部 SaaS まで到達しているか検査していないシステムの不整合で退会済み顧客の本来削除すべきデータが残存し、漏えい対象に入っていた
認証・認可□ 社内システム・分析基盤へのアクセスに長命の静的な認証情報（固定パスワード・長期アクセスキー）を使っている侵入には認証情報が使われ、同社は使われた認証情報をすべて無効化したとしている
運用・監視□ 分析基盤のダウンロード・エクスポートの量と頻度に閾値と警報を設けていない検知は監査ログの不審なダウンロードであり、持ち出しが成立した後の気づきだった
体制・契約□ 顧客が自ら設定した資格情報を預かるサービスを提供しており、漏えい時の案内文を用意していない最多の105,608件は顧客自身が設定した Basic 認証で、他サービスでの使い回しの変更を案内する必要が生じた
