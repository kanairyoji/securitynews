1. 米防衛部品メーカー IEH がフィッシング1通で侵害、輸出管理対象データが露出のおそれ

出典: Security Affairs（2026-08-09）

ニューヨーク・ブルックリンに拠点を置く IEH Corporation は、高信頼性ハイパーボロイドコネクタの製造企業で、製品は回転翼機・THAAD・パトリオット・戦闘機・機上レーダー・衛星・軍用無線・魚雷に組み込まれている。同社は8月4日にインシデントを検知し、SEC への 8-K で開示した。

項目 内容
侵入経路 取引見込み先を装った相手からの「Microsoft ドキュメント共有」風リンク。偽ログインページで M365 資格情報を入力

1. ESX のシェルログは「実行前の文字列」を記録する — 難読化21種の検証

出典: CrowdStrike Blog（取得日 2026-08-09）

検証環境は ESX 7.0.3 build-20036589、VMware 提供の BusyBox（/usr/lib/vmware/busybox/bin/busybox。awk の GNU 数学拡張 xor / and / or が有効）。

前提となる仕組み

ESX のシェルログはコマンドをパース段階で記録し、変数展開・コマンド置換の前の姿を残す。したがって次の2つは同一の動作をするが、ログ上の見え方は全く異なる。

esxcli system syslog config get
$(printf "\x65\x73\x78\x63\x6c\x69") system syslog config get

キーワード検索型の検知はこの差で破られる。「パースと実行のギャップ」が難読化を成立させているという整理が本研究の起点である。

.sys 接頭辞でシステムファイルに紛れ、前後に偽の vmkernel ログを挟んで「定型的なストレージ点検」に見せ、実行後に自己削除する。syslog を追う担当者から見ると、実行が2本のルーチンメッセージの間に隠される。

2 サンドボックス分離 ハーネスごとに専用 VM。オペレータのワークステーションや共用ホストでは動かさない。本番相当と関わる場合は模擬環境で代替
3 OS レベル封じ込め VM 内で Docker / Kubernetes。seccomp、AppArmor、非特権実行。緩和が必要な場合は明示・スコープ限定・人間承認・上位層で補償
4 ward（プロセス能力の閉じ込め） Linux は Landlock、macOS は Seatbelt。監督プロセスがサンドボックスを適用してから子プロセスとしてエージェントを実行。適用後は権限を広げられない（エージェントもハーネスも）。拒否は VFS 層で syscall 完了前に発生。ward-proxy がドメイン許可リストとクラウドメタデータ拒否リスト、DNS リバインディング防止（一度解決した IP にのみ接続）を強制。資格情報はプロキシ層で注入されサンドボックス内プロセスには入らない。改ざん耐性のある連鎖追記型監査ログ。設定読み込み失敗は致命的エラーにする（フォールバックで緩いサンドボックスにしない）。テスト外での .unwrap()/.expect() をゼロにするコーディング標準
5 ward-mcp（ツール呼び出し仲介） MCP の JSON-RPC を傍受し、プロトコル層で許可／拒否。名前付きツールのみ実行可能、引数のポリシー検証、宛先・レート・ペイロード量の制限。拒否理由をエージェントに返し、同じ試行の繰り返しを避けさせる
6 Baywatch（コマンド単位のポリシー） 既定有効。全コマンドに 許可／許可＋記録／人間へエスカレーション／拒否 の4判定。6a ハーネスレベルの事前実行フックはエージェントの制御外で、権限スキップモードでも発火する。6b ポリシーをシステムプロンプトにも入れるが「効率化であって境界ではない」。6c HITL エスカレーション（タイムアウトは拒否＝fail-closed、承認者 ID を記録、原則としてその実行限りの承認）。6d 完全な決定証跡を最終レポートに含める
7 資源・経済的封じ込め（横断） ツール／API 呼び出しのクォータ、レート制限、同時実行数、実行あたりの実時間上限、支出上限、計算・ストレージ上限。上限到達は拒否＋監査で、引き上げは必ず HITL。上限に繰り返し当たるエージェントは静かに絞るのではなく審査対象にする

ポリシーの基準線

事前に拒否するもの: コンテナ公開（docker push / docker login）、Git のリモート操作（git push、リモート追加・変更）、公開 GitHub 操作（PR・Issue・リリース・gist の作成、API 書き込み）、ネットワーク持ち出し（localhost 以外への curl/wget/nc/socat）、リモートアクセス（ssh/scp/rsync）、パッケージ公開（npm publish / twine upload / cargo publish / gem push）、メッセージング（sendmail/mail/mutt/Slack CLI）、破壊的操作（ルートへの rm、mkfs、raw デバイスへの dd、shutdown/reboot）、許可リスト外のツール呼び出し、クラウドメタデータへのアクセス。

人間承認が必要なもの: システムパッケージの導入・削除、サービス変更、事前承認外の sudo、システム全体の所有権・権限変更、特権コンテナ実行、seccomp/AppArmor の緩和、ワークスペース外のホストマウント、ward のパス／エンドポイントポリシーの拡張、ワークスペース内の大量削除、上限の引き上げ、フックスクリプト・ポリシーファイル・ハーネス設定の変更。

許可（機微な操作は記録）: ローカル対象の docker run/exec/build/stop、ローカル Git（add/commit/diff/log/status）、localhost とコンテナブリッジ宛の curl/wget、プロキシ経由の許可リスト egress、許可リストのツール呼び出し、ward 許可ディレクトリ内のファイル操作、コンパイラ・インタプリタ・リンタ・デバッガ・解析ツール。

自ら挙げている限界

  • コマンドフィルタはパターンベースであり、十分に新奇な呼び出しは回避しうる（だから層1・4で持ち出しを独立に塞ぐ）
  • ward はカーネルエクスプロイト耐性を持たない。単独では決して配備しない
  • チャネルゲートはチャネルごとの設計であり、想定外の行動チャネルは両方を迂回しうる。新チャネル追加時は対応するゲートを必須にする
  • プロンプトによる指示は助言的で、強制には使わない
  • HITL は判断点であって形式ではない。承認者 ID の記録と実行限りの承認で判断を働かせ続ける設計にしている
  • 上限は量を制限するが意図は区別しない
  • サンドボックス内には機微情報が意図的に置かれうる。設計目標は「機微が存在しないこと」ではなく「外に出られないこと」

「安全なエージェント実行はモデルの挙動やプロンプトの指示、単一の管理策に依存できない」という結論は、社内で AI エージェントを走らせる日本の組織にもそのまま当てはまる。TechCrunch が報じた一連のサンドボックス脱出（カテゴリ13）と対で読むべき内容である。
