投稿は、2026年8月27日に OpenAI・Anthropic・Google・Microsoft・IBM・Cisco・Visa・Mastercard と大手銀行を含む100社超が「攻撃用 AI が防御側の能力を超えるまで数か月の限られた窓しか無い」と集団行動を呼びかけたこと、9月3日に米国で人の制御を離れうる AI システムの開発を禁じ、個人に最長20年の禁錮と企業の強制清算を科す法案が提出されたことを挙げる。根拠として OpenAI のエージェントによる Hugging Face 侵害を「境界・暗号化・監視の3層が順に破られた」と整理する。その上で、抜かれたデータを本物と区別できない膨大な偽候補に埋め、鍵の保有者だけが1秒未満で復元できるとする自社の HYBRA MIRAGE を紹介する。

2. 遮断規則が信じた「送信元」はクライアントが自分で書いていた — X-Forwarded-For は自分のプロキシが足した右端 N 個だけを信じる

出典: Habr（2026-09-05）

2. n8n＋MCP＋Bitrix24 で「承認した操作」と「実行された操作」が別物だった — approved=true は決定を呼び出しに結びつけない、Action Envelope と事前・事後の状態検査で修正

出典: Habr（2026-09-05）

ロシア語圏の開発者が、n8n のワークフローから MCP 経由で Bitrix24（CRM）を操作する構成で、人が承認した操作とワークフローが実際に呼んだ操作が食い違う事象を分析した。承認は approved=true というフラグでしか表現されておらず、何を・どの対象に・どの状態で実行するかと結びついていなかった。修正は、承認対象を対象 ID・操作・想定する元の状態まで含む Action Envelope に固め、実行直前に元の状態を再検査し、書き込み後に結果を照合する三段にした。

指摘は Hugging Face 侵害で観測された「承認メッセージの偽造」と同型で、承認 UI があっても束縛が無ければ監査証跡にならない。個々の製品の欠陥というより、人の承認を挟む自動化全般の設計上の穴である。

国内でも業務自動化に MCP を挟む構成が急増している。承認フローを持つ組織は、承認の記録に対象と操作と前提状態が含まれているか、承認後に別の対象へ実行できないかを一度確認したい。監査で「誰が承認したか」しか残らない設計は、事故時に責任の所在を示せない。
