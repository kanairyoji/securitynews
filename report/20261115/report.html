1. 米政府が北朝鮮「FaceStealer」の基盤を差押え——4億ドル窃取、会議で「面識のある顔」を見せる

出典: BleepingComputer（2026-11-14）

前回からの差分は、米政府がクラウド基盤を差押えて作戦を止めた点である。18か月続いた北朝鮮の社会工学「FaceStealer」で4億ドル超の暗号資産が盗まれた。FBI 警報によれば、乗っ取った Telegram・LinkedIn・Slack・Discord のアカウントでビデオ会議に誘い、待機中に秘密録画した「標的が知る人物」の映像を再生して信用させ、不具合を装って「修復」リンクからマルウェアを実行させる。録画映像は900本以上が特定され、Arctic Wolf は BlueNoroff に帰属、標的は58か国677人で創業者・役員に集中する。司法省は別途、Binance の64億ドル窃取から27億ドル超を凍結した。

1. 韓国大統領府が民・官・軍の共同対応会議——実機と構成図の乖離を潰し、SBOM を前倒し

出典: 보안뉴스（2026-11-15）

青瓦台（大統領府）国家安保室は11月13日、ソン・ギホ第3次長の主宰で「民・官・軍サイバー安保共同対応会議」を開き、8月から進めている全省庁のシステムとネットワーク構成図の全数調査の進捗を点検、国内外の主要な侵害事故の合同分析も行った。安保室は「各機関が実運用する IT 資産の現況と文書上の構成図が異なり、脆弱性が見つかっても即応できない根本的な問題があった」として、科学技術情報通信部・国家情報院・国防部にハードとソフトを通した精密な資産管理体系の確立を要求。運用状況がリアルタイムに反映される体系の早期定着、外交部門・海外ソフトウェア供給網・セキュリティコミュニティとの連携による脆弱性情報の先行入手、影響システムを即時特定するための SBOM 導入日程の前倒しも決めた。

韓国は今年、通信・カード・金融保安院と侵害が続き、政策の重心が検知や予算から「資産台帳の正確さ」へ移った。台帳が実機と合わない弱点は、攻撃の高度化とは無関係に効き続ける。

日本も能動的サイバー防御法の施行準備と並行して資産把握と SBOM が課題である。「全数調査 → 台帳の即時反映 → SBOM 前倒し」という順序は、国内の CISO が優先順位を見直す材料になる。対応の遅さを人手不足に帰する前に、構成図と現物の差を測りたい。

1. SignDrop——CLFS の保護機構を逆用して SYSTEM、任意の AV/EDR を無効化できる（未修正）

出典: Habr 情報セキュリティHUB（2026-11-14）

元 Microsoft MSRC の研究者 Abdelhamid Naceri（Nightmare Eclipse）が、Windows の Common Log File System（CLFS）ドライバのゼロデイ SignDrop を公開した。悪用するのは、Microsoft が2025年10月に CLFS への認証攻撃を防ぐため導入した保護機構そのものである。CLFS はログファイル作成時に認証ファイル（.cnpf）を生成するが、冒頭のアクセス検査は、後から別の特権プロセスがログを開くと無意味になる。Windows Defender のような特権プロセスに開かせれば認証ファイルが SYSTEM 権限で作られ、要求がエンジン自身の正規プロセスから出たように見えるため、任意のアンチウイルスの改ざん防止を迂回できる。Windows 11 26H2 と Windows Server 2025 Experimental で検証し、設置台数の約80%が影響すると見積もった。

防御アーキテクチャ・セキュリティ製品

カテゴリ: カテゴリ11「防御アーキテクチャ・セキュリティ製品」
対象日: 2026年11月15日
生成日時: 2026-11-16

総評

Fal.Con Europe 2026 の発表群のうち、前回扱った AI ゲートウェイ以外の部分が出そろった。設計上の主張は一貫しており、AI エージェントを攻撃対象としてだけでなく「内部者」として扱い、本人が頼んだこととエージェントが自分で決めたことを切り分ける。もう一つの軸は管理点の位置で、ブラウザとコンテナ受付という使用時点・投入時点に寄せている。実装側の話題は iOS Keychain の既定値とブラウザ上のハッシュ・パスワード生成の2件で、いずれも「既定のまま書くと弱くなる」種類の落とし穴を示している。

1. エージェントを「内部者」として見る——所有者の依頼と自走を切り分ける

出典: CrowdStrike Blog（2026-11-15）

前回からの差分は、エージェントの扱いが検知と調査の側に広がったことである。Dynamic Risk Scoring（Q4）はエージェントのリスクを所有者とホストと同じ0〜100の尺度に合わせる。AI Ecosystem Detections（Q4）は LLM API の乱用、盗まれた API キー、MCP サーバやエージェント基盤の侵害に検知論理を追加する。Multi-Agent Triage and Investigation（GA）はセッションを本人の依頼まで遡り、本人が書いていない指示に由来する行動を切り離す。Policy-Drift Agent Guardrails（Beta、Q4）は Charlotte AI と AgentWorks の相互作用を方針逸脱・未認可のツール呼び出しの観点で検査する。別途 Agentic Adversary Emulation（早期アクセス）が顧客承認の範囲内で本番環境の攻撃経路を探索し、是正後に再試行して効果を検証する。

評価の軸は帰属である。「本人がやったのか、エージェントが勝手にやったのか」は責任の所在に直結し、監査・規制・取締役会の関心事でもある。一方、本番環境での自律レッドチームは早期アクセス段階で、導入はまだ検証段階にある。

国内でも開発・バックオフィスにエージェントが入り始めているが、監視は人のアカウント単位にとどまる組織が多い。エージェントに人と紐づく識別子を与えて行動を所有者と結びつけて追えるようにすること、未認可のツール呼び出しを警報にすることが、製品選定より前に要る設計である。

2. 管理点を「使用時点」と「投入時点」に寄せる——ブラウザとコンテナ受付

出典: CrowdStrike Blog（2026-11-15）

Falcon Seraphic Enterprise Browser が Falcon プラットフォーム上で提供される。専用ブラウザの導入や通信の迂回を要さず、既存ブラウザの中でフィッシング・ClickFix・中間者攻撃の実行時検査、セッショントークン窃取の阻止、コピー・貼り付け・アップロードへの方針適用、拡張機能の棚卸しを行う。管理外・BYOD・業務委託先の端末にも MDM 登録なしで届く。クラウド側では Supply Chain Security for Cloud が、CI/CD とレジストリ走査で悪性の npm・PyPI パッケージを特定し、新たな判定が出た過去のイメージを再評価して稼働中のコンテナを割り出す。Kubernetes Admission Controller が投入前に警告または遮断する。

理にかなうのは、どちらも「止められる最後の地点」を選んでいることである。生成AI への貼り付けはブラウザでしか止まらず、CVE を持たない汚染パッケージは脆弱性走査では見つからないため受付時の判定が要る。背景には ALTERED SPIDER が1日で300超の依存関係を侵害した観測がある。

国内では管理外端末からの SaaS 利用と、AI コーディング支援が引き込む依存関係の増加が同時に進んでいる。製品の採否とは別に、生成AI への機密の貼り付けを技術的に止める地点が自社にあるか、コンテナの投入前に悪性パッケージの判定を入れられるかを設計として先に決めておきたい。

3. iOS Keychain——kSecAttrAccessible を書かないと既定は「解除中のみ」になる

出典: Habr 情報セキュリティHUB（2026-11-15）

Keychain は各レコードを AES-256-GCM の2つの鍵で守る。表鍵がメタデータを、行鍵が kSecValueData の秘密値を保護し、秘密値の鍵は読み出しごとに Secure Enclave を経由する。データベース自体は端末に1つの通常の SQLite ファイルで、どのレコードをどのアプリに見せるかは securityd が entitlements を検査して決める。

実務上の落とし穴は既定値である。kSecAttrAccessible を省くと kSecAttrAccessibleWhenUnlocked が適用され、画面ロック中は読めない。プッシュ受信後のバックグラウンド処理でトークンを読む設計だと、ロック中に認証が失敗する。kSecAttrAccessibleAfterFirstUnlock は起動後の初回解除以降は再起動まで読めるが、そのぶん保護は弱い。パスコードのない端末は常に解除扱いになるため WhenUnlocked が実質無制限になる点も見落とされやすい。

国内のモバイルアプリ開発でも、秘密がファイルや UserDefaults に平文で置かれている例はまだある。秘密は必ず kSecValueData に入れる（コメントやラベル属性に入れない）、アクセス可能クラスを明示する、初回起動時に明示的に消す——この3点をコードレビューの確認項目に加えたい。アプリ削除後にレコードが残ることは Apple の保証ではなく、初回起動の判定に使うのは危険である。

4. ブラウザ上のハッシュとパスワード生成——単語リストの実数を数えていなかった

出典: Habr 情報セキュリティHUB（2026-11-15）

ブラウザ内で完結するハッシュ計算機とパスワード生成器の実装記録である。crypto.subtle.digest は SHA-1／256／384／512 の4つのみで MD5・SHA-3 はなく、HTTPS か localhost でないと crypto.subtle が未定義になる。乱数は crypto.getRandomValues を使い、random32 % n では剰余による偏りが出るため棄却サンプリングで均一化している。注目すべきは著者自身が見つけた誤りで、パスフレーズ用のロシア語単語リストを7,776語相当だと思っていたが実際は一意405語で約8.7ビット／語しかなく、4語で約35ビットの「弱い」水準だった。ロシア語を2,072語（約11ビット）、英語を EFF Large Wordlist（7,772語）に差し替え、既定を6語に変更した。

教訓は、k · log₂(W) が成り立つのは語が既知の大きさのリストから等確率・独立に選ばれるときだけで、重複が入ると計算が静かに壊れるということである。実装は動いていたのに強度表示だけが誤っていた。記事は NIST SP 800-63B（2017）が構成規則の強制と定期変更の要求を撤回し、長さと予測困難性に寄せたことも整理している。

国内の多くの登録フォームは今もこの逆を要求している。空白を弾く、16文字で切る、パスワードマネージャからの貼り付けを禁じる——自社フォームがこの3つをしていないかを今日確認したい。パスフレーズを採るなら、リストの一意語数を数えて強度表示の根拠に添えることが要る。

総評

この日の材料は少ないが、いずれも「平時の帳簿と実態の差」に関わる。韓国の大統領府国家安保室は、各機関が運用している IT 資産の現況と文書上のネットワーク構成図が食い違っており、脆弱性が見つかっても即応できないことが根本問題だと指摘し、SBOM の導入時期を前倒しすると決めた。Lego の BrickLink は1週間の停止を「必要な作業」と説明し続け、売上の大半を同サイトに依存する出品者が4日で52%の減収を被った。CSET は、個別には妥当な AI 規制が合算されると自国の技術優位を削りうるという論点を提示している。

1. 資産台帳と実態が合わない——韓国が全省庁の構成図を全数調査し SBOM を前倒し

出典: 보안뉴스（2026-11-15）

韓国大統領府の国家安保室は11月13日、民・官・軍のサイバー安保共同対応会議を開き、8月から進めている全省庁のシステム・ネットワーク構成図の全数調査の進捗を点検した。同室は「各機関が実際に運用している IT 資産の現況と、文書上のネットワーク構成図が異なり、脆弱性が見つかっても即座に対応できない根本的な問題があった」とし、科学技術情報通信部・国家情報院・国防部などにハードウェアとソフトウェアを含む精密な資産管理体制の確立を要求した。最新の運用状況が実時間で反映される体制を早期に定着させる方針で、影響システムを即座に特定できるよう SBOM の導入日程も前倒しする。

評価として本質的なのは、問題を「検知できない」ではなく「対象が特定できない」と定義し直したことである。脆弱性情報を速く得ても、どの機器に載っているかが分からなければ適用順も影響範囲も決まらない。構成図を文書として維持する運用から、実時間で反映される台帳へ移す方針は、SBOM と組み合わせて初めて機能する。

日本でも政府機関・自治体・大企業で、構成図が更新されないまま運用され、脆弱性公表のたびに手作業の棚卸しから始める実態は広く見られる。今日打てる手は、資産台帳の更新が「変更申請の副産物」になっているかを確認することである。SBOM は調達要件に書くだけでは資産台帳と結びつかないため、受領した SBOM を既存の構成管理データベースと突き合わせる仕組みを設計段階で決めておきたい。

2. BrickLink の1週間停止——出品者は4日で売上52%減、説明は「必要な作業」だけだった

出典: Habr 情報セキュリティHUB（2026-11-15）

Lego が運営するブロック売買プラットフォーム BrickLink が、11月5日から12日まで停止したのち再開した。Lego は当初この停止を「必要な作業」と呼び、その後にセキュリティインシデントの影響を受けたと認めた。同社は、認可されていない第三者が利用者名と IP アドレスにアクセスした可能性があるとし、パスワード・郵便住所・金融情報は露出していないと主張している。ただし Brick Fanatics は、詳細な個人情報と購買データを含むフィッシングメールが顧客に届いていると報じている。BrickLink と Brick Owl に店舗を持つ Simon Webster は、4日間で総売上が52%減り、同期間の Brick Owl での売上は79%増えたと述べた。サイバーインシデントによる作業の予告はなかったという。

論点は2つある。公表した露出範囲（利用者名と IP）が、実際に届いているフィッシングの内容と整合しない。調査の見立てが狭いまま公表すると後から訂正が要り、信頼のコストはそちらで支払う。もう1つは告知の欠落で、プラットフォームに依存する事業者への情報提供が復旧作業の優先順位から落ちていた。

国内でも EC モール・受発注基盤・決済代行への事業依存は高く、停止時に代替チャネルへ流れた需要は戻らないことが多い。経営側の宿題は、単一チャネル依存の売上比率を把握して停止時の代替手段を事前に用意すること、そして自社が基盤側である場合は、理由を伏せた「作業中」という説明が取引先の判断を奪うと理解することである。

3. 「個別に妥当な規制」の合算が自国の AI 優位を削る——CSET の論点

出典: CSET（2026-11-14）

ジョージタウン大学 CSET は、Nvidia の Jensen Huang をめぐる論争を題材に、米国が正当な安全保障上の懸念に対応する過程で自らの技術的優位を損ないうると論じた。立論の核は、目的の異なる当事者の利害が、調整や共通の意図がなくても AI 開発の制約という同じ結果に収束しうるという点である。挙げられているのは、優位の縮小に戦略的利益を持つ中国、開発の制限や停止を求める AI 安全の提唱者、規制の明確さを求めつつ複雑な要件が有利に働く既存の AI 企業、権限が拡大しやすく縮小しにくい規制機関、雇用・プライバシー・電力消費を懸念する住民である。CSET は、ある結果が中国に利益をもたらすことは中国がそれを引き起こした証明にはならないとも明記する。

有用なのは、是非ではなく問いの立て方である。問うべきは費用が生じるかではなく、便益が費用を正当化するか、より制限の少ない代替があるか、累積した結果が技術的な競争力と両立するかで、この整理は企業の内部統制の設計にもそのまま使える。

日本の読者への含意は2つある。1つは政策動向の読み方で、米国の AI 規制が今後どちらに振れるかは単一の争点では決まらないため、自社の AI 投資計画は規制の方向を一方に賭けない構えが要る。もう1つは社内統制で、AI 利用の個別規程を部門ごとに積み上げると合算で実用が成り立たなくなる。規程追加時に累積効果を評価する手順を先に置いておきたい。
