1. 英捜査権限裁判所「アップルへの技術役務通知は秘密ではない」——政府のNCND原則に歯止め

出典: 보안뉴스 boannews（2026-11-20）

英国の捜査権限裁判所（IPT）は11月19日、アップルが技術役務通知（TCN）を受け取った事実を認めると国家安全保障が危うくなるという内務省の主張を退けた。TCNは2016年の捜査権限法に基づき内務大臣が企業へ暗号解除などの技術的措置を秘密裏に義務づける命令で、報道では暗号化された顧客データの提供を求めたとされる。政府は命令の有無を「肯定も否定もしない」（NCND）原則で通してきたが、裁判所は複数の政府関係者が承認を得て報道機関に説明した形跡があり、米政権関係者への説明も承認していたと認定し、原則からの大きな逸脱と判断した。訴訟の相当部分が公開審理に移り、本案審理は2027年前半の見込み。

命令の中身は依然非公開で、比例性判断の最終段階などは非公開証拠を要するとされた。それでも国外へ向けた令状の射程といった法解釈の争点は公開法廷で争える。アップルは2025年に英国でiCloudの高度データ保護の新規有効化を止めており、秘密命令への対抗が利用者の機能低下として現れる構図も残っている。

日本でも通信の秘密と能動的サイバー防御をめぐり、命令の存在自体を秘匿する手法が論点になる。クラウドに業務データを置く国内組織は、提供者が所在国の秘密命令にどう応じる方針かを契約・透明性報告で確認しておきたい。

日本企業も社内文書要約やコード生成に外部APIを使い、ゲートウェイ越しに安価なプロバイダへ回す構成が増えている。契約上のデータ保持条項だけに頼らず、どの下請けに回るのかを把握し、機微データの投入は自社が監査できる経路（専用契約・自社推論・リージョン固定）に限ることが現実的な線引きになる。

2. Dockerがエージェントの隔離を前面に — microVMのサンドボックスを無償提供

出典: Habr（2026-11-21）

Dockerは11月19日にブランドを変更し、標語を「build, ship, and run on trust」に改めた。中心に置かれたのはAIエージェントで、端末を与えると実行するコマンドや接続先を自分で決めてしまうため、事前に制限できる環境を売るという立て付けである。実体のSandboxesは9月から提供済みで、CLI（sbx）とローカル実行は商用利用を含め無償。各サンドボックスは独自カーネルとDocker Engineを持つmicroVMで動き、ハイパーバイザ（LinuxはKVM）が境界に入る。--clone でリポジトリの別クローンで作業でき、APIキーはホスト側に残りプロキシが差し込む。外向き通信は許可ドメインを明示する。

Claude Codeが既定で権限確認を省く設定で起動する前提に立つと、書き込み許可を与えたフォルダはホスト上でそのまま変更されるため、マウント範囲の設計が実質の防御線になる。コンテナではなくハイパーバイザ境界を使った点は妥当である。有償のAI Governanceは許可ドメイン・フォルダ・MCPツールを全社に配り、監査ログを外部へ送る。

日本でもコーディングエージェントの業務利用が広がり、開発者端末に本番資格情報が残る例が多い。無償のローカルサンドボックスは今日から適用できる具体策で、クローン作業と許可ドメインの明示を標準手順に入れたい。

3. ゼロ知識証明の検証鍵の取り違えを、コンパイル時に捕まえる

出典: Habr（2026-11-22）

評価として、ZK検証器の実装ミスは「証明が通ってしまう」形で現れるため、実行時テストでは見つけにくい。検証鍵の型を言語側で区別し、コンパイル時に不整合を落とす設計は、監査の人手に依存しない防御として筋が通る。一方で検証器そのものの正しさは別途の課題として残る。

日本でもゼロ知識証明は、ブロックチェーン決済に加えてマイナンバー関連の属性証明や年齢確認の文脈で検討が始まっている。採用を検討する組織は、ライブラリの選定時に「鍵の取り違えが型で防げるか」「ガス・計算コストの実測値が公開されているか」を評価軸に加えると、後からの作り直しを避けられる。

4. AI向けの表示を整えても、来るのは.envを探すスキャナだった

1. 「説明責任は外注できない」— 第三者を名指ししない開示慣行への批判

出典: Troy Hunt（2026-11-22）

Troy Huntは、開示通知が「第三者で起きたインシデント」と書くことで、あたかも責任が軽くなるかのように扱われている現状を批判している。今週のOptimizelyの事案では、スクリプト依存による侵害の原因が明確に同社側にあっても、影響を受けた個人に連絡するかどうかの判断はノルウェーの航空会社など委託元に委ねられ、しかもその開示では第三者の名称が示されなかった。

論点は2つに分かれる。1つは責任の所在で、データを預けた側に説明責任が残るという原則。もう1つは開示の実務で、第三者を名指ししないと利用者は「自分が使う他のサービスも同じ事業者を使っているか」を判断できない。通知の判断を委託元に委ねる構造は、公表の遅れと影響範囲の過小評価を生みやすい。

日本の公表文でも「委託先において」という表現は定番で、委託先名を書かない例が多い。個人情報保護委員会への報告義務は委託元に残るのだから、公表でも委託先名と影響範囲を書くほうが整合する。自社の開示テンプレートに、第三者名・経路・影響件数の欄を最初から設けておきたい。広報と法務だけで文面を決めず、セキュリティ部門が事実関係の記述を担保する体制も要る。
